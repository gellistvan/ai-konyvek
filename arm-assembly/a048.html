12.5 NEON-gyorsulás mérése és korlátai

12.5.1 Motiváció: a vektorizáció nem önmagában gyorsulás, hanem mérhető állítás

Az előző alfejezetben megírtuk a NEON-átiratot: a fő ciklus SS elemes lépésekben dolgozik, a maradékot skalárisan fejezzük be. Ettől a kód elvileg gyorsabb. A mérnöki kérdés azonban nem az, hogy „gyorsabb-e”, hanem az, hogy mennyivel, milyen feltételek mellett, és hol van az a pont, ahol a többletkomplexitás nem térül meg. Egy teljesítménykritikus modulban ez a döntés közvetlenül mérnöki: ha egy kernel a futásidő 8%-át adja, és a vektorizációval annak felét megnyerjük, a teljes programra eső nyereség néhány százalék — miközben a kód karbantarthatósága és hordozhatósága romlik.

Ehhez két dolog kell. Egyrészt egy reprodukálható mérési eljárás, amely azonos bemeneten, ismételt futással, szóródást is közölve hasonlítja össze a két változatot. Másrészt egy egyszerű modell, amelyhez a mért értéket viszonyítani lehet — különben nem tudjuk megmondani, hogy egy 2,3-szeres gyorsulás jó eredmény vagy figyelmeztetés. Ezt az Amdahl-törvény adja, a feltevéseivel együtt. A mérést a debugging és instrumentáció fejezet CLOCK_MONOTONIC-alapú mintavételi vázára építjük; a részletes ciklusszám-elemzést a teljesítmény-tudatos fejezet folytatja.

12.5.2 Definíció: gyorsulás, vektorizálható hányad, Amdahl-modell

Legyen TskalárT_{\text{skalár}} a skaláris változat futásideje és TneonT_{\text{neon}} a NEON-változaté, azonos bemeneten, azonos mérési intervallummal. A gyorsulás (speedup):

S=TskalárTneon.S = \frac{T_{\text{skalár}}}{T_{\text{neon}}}.

A vektorizálható hányad (vectorizable fraction) p∈[0,1]p \in [0,1]: a skaláris változat futásidejének az a része, amelyre a vektorizálás hat. Nem utasításszám-hányad: az eltérő késleltetésű, egymással átfedve végrehajtott utasítások darabszámából nem következik, mennyi időt visz el a vektorizálható rész. A maradék 1−p1-p időhányad olyan munka, amelyre a vektorizálás nem hat.

Az Amdahl-modell adott pp és a vektorizált részre vonatkozó ss gyorsítási tényező mellett:

SAmdahl(p,s)=1(1−p)+ps.S_{\text{Amdahl}}(p, s) = \frac{1}{(1-p) + \dfrac{p}{s}}.

A képlet akkor érvényes, ha a két részidő rögzített, és a vektorizálás csak a pp részt gyorsítja, azon belül egyenletesen ss-szeresen. Az s=4s = 4 ebben az alfejezetben egyszerű modellfeltevés: azt mondja ki, hogy a vektoros rész ideje pontosan a sávok számával osztódik (128 bites float32x4_t esetén 4 sáv). Ez nem az ISA-ból következő felső korlát. Abból, hogy négy float fér egy vektorregiszterbe, nem következik a mért S≤4S \le 4 általános érvénye: a vektoros ciklusban megváltozik a ciklusvezérlés aránya, az utasításkibocsátás és a függőségi láncok hatása is. A tényleges ss ezért lehet 4 alatt (például ha a memóriarendszer korlátoz) és elvben 4 felett is (például ha a skaláris változatot elemenként a ciklusvezérlés vagy egy függőségi lánc fogta vissza).

12.5.3 A mérési módszer

Munkakönyvtár: ~/arm-labor/a64/a048/ — az alfejezet minden laborfájlja ide kerül, és minden parancs innen futtatandó (a könyvtárrendet a Labor-alapkörnyezet alfejezet írja le).

mkdir -p ~/arm-labor/a64/a048
cd ~/arm-labor/a64/a048

A mérés elve: azonos bemenet, a méréstől külön korrektségi ellenőrzés kernelenként, melegítés, ismételt futás váltakozó sorrendben, valamint medián és szóródás (interkvartilis terjedelem, IQR) közlése. A váz négy lépése:

  1. Korrektség. Mindkét kernel saját kimeneti pufferbe ír, amelyet előtte NaN őrértékkel töltünk fel, és az eredményt kernelenként, külön ellenőrizzük. Ha a két kernel ugyanabba a pufferbe írna, és csak a második mérés után ellenőriznénk, egy hibás skaláris kernel eredményét a helyes NEON-kernel felülírná, és a program sikert jelentene.
  2. Melegítés. Néhány nem mért futás, hogy az első futás egyszeri költségei (laphibák, gyorsítótár-feltöltés, QEMU alatt a kódfordítás) ne torzítsák a mintát.
  3. Mérés. Körönként váltakozó sorrend (páros körben skalár–NEON, páratlanban NEON–skalár), hogy a sorrendből adódó hatás ne terhelje mindig ugyanazt a kernelt.
  4. Szóródás. A medián mellett az IQR-t is kiírjuk; egy medián szóródás nélkül nem mutatja meg, mennyire megbízható az összehasonlítás.

A deklarációk saját fejlécbe kerülnek. A függvénynevekben az f32 megkülönbözteti őket az előző alfejezet add_i32_* függvényeitől, amelyek más elemtípussal és más paramétersorrenddel dolgoznak:

/* lab-a048-add-f32.h */
#ifndef LAB_A048_ADD_F32_H
#define LAB_A048_ADD_F32_H
#include <stddef.h>

/* dst[i] = a[i] + b[i] (float), 0 <= i < n.
 * Paramétersorrend: dst, a, b, n — eltér az a047 add_i32_* függvényeitől.
 * Előfeltétel: a tömbök legalább n eleműek; dst nem fedi át részlegesen a-t vagy b-t. */
void add_f32_scalar(float *dst, const float *a, const float *b, size_t n);
void add_f32_neon  (float *dst, const float *a, const float *b, size_t n);

#endif
/* lab-a048-bench.c */
#define _GNU_SOURCE
#include <math.h>
#include <stdio.h>
#include <stdint.h>
#include <stdlib.h>
#include <time.h>
#include "lab-a048-add-f32.h"

#ifndef N
#define N      (1u << 20)   /* 1 048 576 float = 4 MiB tömbönként */
#endif
#define WARMUP 3            /* kernelenként, nem mért futások */
#define REPS   31           /* páratlan, hogy a medián egyértelmű legyen */

typedef void lab_kernel(float *dst, const float *a, const float *b, size_t n);

/* aligned_alloc: a méret a 64 többszöröse legyen (C11); a logikai elemszám n marad.
 * n == 0 esetén is foglal 64 bájtot (dokumentált minimális memóriahasználat). */
static float *alloc_f32(size_t n) {
    if (n > (SIZE_MAX - 63) / sizeof(float)) return NULL;      /* size_t túlcsordulás */
    size_t bytes = (n * sizeof(float) + 63) & ~(size_t)63;
    return aligned_alloc(64, bytes ? bytes : 64);
}

static double now_ms(void) {
    struct timespec ts;
    /* a043 mintája */
    if (clock_gettime(CLOCK_MONOTONIC, &ts) != 0) { perror("clock_gettime"); exit(2); }
    return ts.tv_sec * 1000.0 + ts.tv_nsec / 1e6;
}

static int cmp_double(const void *p, const void *q) {
    double a = *(const double *)p, b = *(const double *)q;
    return (a > b) - (a < b);
}

/* Őrérték: NaN-nal töltött pufferben egy ki nem írt elem sem mehet át. */
static void fill_nan(float *d, size_t n) {
    for (size_t i = 0; i < n; ++i) d[i] = NAN;
}

/* Indexenként eltérő, vegyes előjelű, pontosan reprezentálható bemenet:
 * a lane-csere, a[i+1] olvasás, konstans kimenet és az elhagyott tail eltérést ad. */
static float va(size_t i) { return (float)((int)(i % 13) - 6) * 0.5f; }
static float vb(size_t i) { return (float)((int)(i % 7) - 3) * 0.25f + (float)(i % 5); }
static void fill_in(float *a, float *b, size_t n) {
    for (size_t i = 0; i < n; ++i) { a[i] = va(i); b[i] = vb(i); }
}

/* Külön referencia: d[i] == va(i) + vb(i) (az összeg pontos, így == összehasonlítható). */
static int check(const char *name, const float *d, size_t n) {
    for (size_t i = 0; i < n; ++i) {
        float want = va(i) + vb(i);
        if (d[i] != want) {
            printf("FAIL %s: d[%zu] = %g (vart: %g)\n", name, i, (double)d[i], (double)want);
            return 0;
        }
    }
    return 1;
}

/* Hosszsöprés őrértékkel: n = 0..17 és a 4-gyel nem osztható / határ menti hosszak.
 * A kimenet utáni 4 elem NaN őrérték marad, a bemenet utáni elemek 1e30f csapdák. */
static int sweep(const char *name, lab_kernel *fn) {
    static const size_t extra[] = { 31, 33, 63, 65, 1023, 1025, 4099 };
    size_t cnt = 18 + sizeof extra / sizeof extra[0];
    for (size_t k = 0; k < cnt; ++k) {
        size_t n = k < 18 ? k : extra[k - 18];
        float *a = malloc((n + 4) * sizeof(float)), *b = malloc((n + 4) * sizeof(float));
        float *d = malloc((n + 4) * sizeof(float));
        if (!a || !b || !d) { free(a); free(b); free(d); return 0; }
        fill_in(a, b, n);
        for (size_t i = n; i < n + 4; ++i) { a[i] = b[i] = 1e30f; d[i] = NAN; }
        fill_nan(d, n);
        fn(d, a, b, n);
        int ok = check(name, d, n);
        for (size_t i = n; ok && i < n + 4; ++i)
            if (!isnan(d[i])) { printf("FAIL %s: n=%zu, a határon túli írás d[%zu]\n", name, n, i); ok = 0; }
        if (!ok) printf("  (hibás hossz: n = %zu)\n", n);
        free(a); free(b); free(d);
        if (!ok) return 0;
    }
    return 1;
}

/* Medián és interkvartilis terjedelem (IQR), egyszerű rangalapú kvartilisekkel. */
static void stats(double *t, int n, double *med, double *iqr) {
    qsort(t, (size_t)n, sizeof t[0], cmp_double);
    *med = t[n / 2];
    *iqr = t[(3 * n) / 4] - t[n / 4];
}

int main(void) {
    lab_kernel *fn[2] = { add_f32_scalar, add_f32_neon };
    const char *name[2] = { "add_f32_scalar", "add_f32_neon" };
    float *a = alloc_f32(N);
    float *b = alloc_f32(N);
    float *d[2] = { alloc_f32(N),    /* külön kimeneti */
                    alloc_f32(N) };  /* puffer kernelenként */
    static double t[2][REPS];
    int rc = 1;

    if (!a || !b || !d[0] || !d[1]) goto out;
    fill_in(a, b, N);

    /* 1. Korrektség a méréstől külön: mindkét kernel saját, NaN-nal töltött pufferbe ír. */
    for (int k = 0; k < 2; ++k) {
        if (!sweep(name[k], fn[k])) goto out;
        fill_nan(d[k], N);
        fn[k](d[k], a, b, N);
        if (!check(name[k], d[k], N)) goto out;
    }
    printf("ellenorzes: %s OK, %s OK\n", name[0], name[1]);

    /* 2. Melegítés: gyorsítótárak, laptábla, QEMU-kódfordítás. */
    for (int w = 0; w < WARMUP; ++w)
        for (int k = 0; k < 2; ++k) fn[k](d[k], a, b, N);

    /* 3. Mérés váltakozó sorrendben: páros körben skalár–NEON, páratlanban NEON–skalár. */
    for (int k = 0; k < 2; ++k) fill_nan(d[k], N);
    for (int r = 0; r < REPS; ++r)
        for (int j = 0; j < 2; ++j) {
            int k = j ^ (r & 1);
            double t0 = now_ms();
            fn[k](d[k], a, b, N);                   /* csak a kernel van a mérésen belül */
            t[k][r] = now_ms() - t0;
        }

    /* 4. A mért futások eredménye is helyes-e? */
    for (int k = 0; k < 2; ++k)
        if (!check(name[k], d[k], N)) goto out;

    double med[2], iqr[2];
    for (int k = 0; k < 2; ++k) stats(t[k], REPS, &med[k], &iqr[k]);
    if (med[0] <= 0 || med[1] <= 0) { rc = 2; goto out; }

    for (int k = 0; k < 2; ++k)
        printf("%-15s median %8.3f ms  IQR %6.3f ms\n", name[k], med[k], iqr[k]);
    printf("gyorsulas (median-arany): %.2fx\n", med[0] / med[1]);
    rc = 0;
out:
    free(a); free(b); free(d[0]); free(d[1]);
    return rc;
}

    lsr  x5, x3, #2              // n/4
    lsl  x5, x5, #2              // n & ~3 : a 4-tel osztható határ
    mov  x4, #0

    ldr  q1, [x2, x6]            // 4 float betöltése b-ből
    fadd v0.4s, v0.4s, v1.4s     // sáv-párhuzamos összeadás

    cmp  x4, x5

    ldr  s1, [x2, x4, lsl #2]
    fadd s0, s0, s1
    str  s0, [x0, x4, lsl #2]
    add  x4, x4, #1
    cmp  x4, x3
    b.lo 3b
4:  ret
    .size add_f32_neon, .-add_f32_neon

    .section .note.GNU-stack,"",%progbits

Kritikus megjegyzés a QEMU-korlátról. A qemu-aarch64 user-mode emuláció a guest-kódot host-utasításokra fordítja, és nem modellezi hűen a valós cache-hierarchiát, a memóriasávszélességet és a betöltési késleltetéseket. Az itt kapott idő ezért emulációs idő, nem target-ciklusszám. A QEMU-ban kapott arányból a fizikai memóriasávszélességre nem lehet következtetni, és az sem mondható általánosan, hogy a QEMU-arány a valós hardverhez képest jobb vagy rosszabb lenne — az eltérés iránya sem garantált. Natív Raspberry Pi 4/5 alatt ugyanez a bináris valódi hardveres időt ad; a kettőt mindig külön kell jelölni.

12.5.4 Az Amdahl-törvény levezetése

Levezetés. Jelölje T0T_0 a skaláris változat teljes futásidejét. Bontsuk fel két részre: p⋅T0p \cdot T_0 a vektorizálható és (1−p)⋅T0(1-p)\cdot T_0 a nem vektorizálható rész. A modell szerint a vektorizálás csak az első tagra hat, és ott ss-szeres gyorsulást ér el (azaz a vektorizált rész ideje pT0/sp T_0 / s-re csökken). Így

Tneon=(1−p)T0+pT0s.T_{\text{neon}} = (1-p)\,T_0 + \frac{p\,T_0}{s}.

A gyorsulás a definíció szerint:

S(p,s)=T0Tneon=T0(1−p)T0+pT0/s=1(1−p)+p/s.S(p,s) = \frac{T_0}{T_{\text{neon}}} = \frac{T_0}{(1-p)T_0 + p T_0/s} = \frac{1}{(1-p) + p/s}.

Két határeset érdekes:

  • A modell határértéke: ha s→∞s \to \infty (a vektorizált rész ideje nullára csökken), akkor S→11−pS \to \dfrac{1}{1-p}. Ez csak pp-től függ: ha a futásidő 10%-ára a vektorizálás nem hat, a modell szerint a gyorsulás nem haladhatja meg a 10×-et.
  • Egyszerű sávszám-modell: az s=4s = 4 feltevéssel S4(p)=1(1−p)+p/4S_4(p) = \dfrac{1}{(1-p) + p/4}. Ez a feltevésből következő modellérték, nem az ISA által garantált plafon (lásd a definíciót).

Mért SS és ismert pp mellett a modellből visszaszámítható az az seffs_{\text{eff}}, amely a mérést reprodukálná:

seff=p1S−(1−p).s_{\text{eff}} = \frac{p}{\dfrac{1}{S} - (1-p)}.

Az seffs_{\text{eff}} a modellbe illesztett szám, nem mért mennyiség: értéke a feltételezett pp-n múlik, és az seff/4s_{\text{eff}}/4 hányados nem mért sávkihasználtság. Abból, hogy seff<4s_{\text{eff}} < 4, önmagában sem cache-, sem sávkihasználási diagnózis nem következik.

Hogyan becsülhető pp? Mivel pp időhányad, utasításszámlálással (például objdump-listából) nem határozható meg. Lehetséges módszerek: natív hardveren profilozó (például perf record / perf report), amely megmutatja, a futásidő mekkora része esik a kernel vektorizálható ciklusára; vagy kísérleti felbontás, amelyben a nem vektorizálható részt (például a maradékciklust vagy a környező kódot) külön mérjük, és p=1−Tnem vekt./T0p = 1 - T_{\text{nem vekt.}}/T_0 — ennek is van torzítása, mert a részek átfedve futhatnak. Ha egyik módszer sem áll rendelkezésre, pp feltételezett érték, és az erre épülő számítás matematikai szemléltetés.

Az alábbi számítás hipotetikus számpélda: a fenti formátumú kimenet T0=12,00T_0 = 12{,}00 ms és Tneon=5,20T_{\text{neon}} = 5{,}20 ms értékét, valamint feltételezett p=0,95p = 0{,}95-öt használ. Egyik szám sem mérés eredménye; a cél az Amdahl-modell kezelésének bemutatása.

Amdahl-modell, p=0,95p=0{,}95, s→∞s\to\infty 0,60 20,0× a modell határértéke

Az utolsó sor: T=(1−p)T0=0,05⋅12,00=0,60T = (1-p)\,T_0 = 0{,}05 \cdot 12{,}00 = 0{,}60 ms, és S=1/0,05=20S = 1/0{,}05 = 20.

A hipotetikus 2,31× a modell 3,48×-os s=4s = 4 értéke alatt van. A modellbe illesztett seffs_{\text{eff}}:

seff=0,9512,31−0,05=0,950,4329−0,05=0,950,3829≈2,48.s_{\text{eff}} = \frac{0{,}95}{\tfrac{1}{2{,}31} - 0{,}05} = \frac{0{,}95}{0{,}4329 - 0{,}05} = \frac{0{,}95}{0{,}3829} \approx 2{,}48.

Ez a szám csak annyit mond: ha p=0,95p = 0{,}95 lenne, a vektorizált résznek kb. 2,5-szeresen kellene gyorsulnia ahhoz, hogy a megadott időket kapjuk. Más pp-vel más seffs_{\text{eff}} adódik (lásd az 1. feladatot), ezért belőle egyik lenti ok sem tekinthető igazoltnak.

12.5.6 Az elméleti és a mért gyorsulás eltérésének tipikus okai

Ha egy valódi mérés elmarad az s=4s = 4 modellértéktől, a következő okok jönnek szóba. Mindegyik hipotézis, amelyet natív hardveren végzett célzott méréssel kell igazolni (például nn-sweep a gyorsítótár-méretek körül, teljesítményszámlálók); a fenti hipotetikus számpéldából egyik sem következik.

  1. Memóriasávszélesség (memory bandwidth). A vektoros mag gyorsabb, de a ldr q / str q ugyanannyi bájtot mozgat, mint a skaláris változat összesen. Ha a kernel memória-kötött, a vektorizáció csak a számítási részt gyorsítja, a betöltés/kiírás idejét nem. Nagyméretű tömbökön ez gyakori ok. Fontos: ezt a hatást a QEMU nem modellezi megbízhatóan, ezért QEMU-mérésből nem lehet rá következtetni.
  2. Ciklusoverhead. A NEON-változatnak is van számlálója, összehasonlítása és elágazása — igaz, negyed annyi iterációra elosztva. Kis nn-nél ez dominál.
  3. Setup-költség. Az lsr/lsl határszámítás és a maradékciklus egyszeri, fix költség. Nagy nn-nél elhanyagolható, kis nn-nél meghatározó.
  4. Nem vektorizálható munka. Ha a ciklus feltételes ágakat, táblaindexelést, nem összefüggő hozzáférést vagy sávonként eltérő vezérlést tartalmaz, a pp értéke jelentősen csökken, és vele együtt az elérhető SS is.

Mielőtt bármelyik okot vizsgálnánk, ellenőrizzük, hogy a mért bináris valóban a kívánt kernelt futtatja: az aarch64-linux-gnu-objdump -d --disassemble=add_f32_neon lab-a048-bench kimenetében ldr q, fadd v0.4s és str q utasításoknak kell lenniük. Ha nem ezek látszanak, a mérés nem a NEON-kernelt méri (elavult objektum, rossz szimbólum, hibás linkelés — lásd a 3. feladatot).

12.5.7 Mikor NEM térül meg a vektorizáció

Nem minden vektorizálás éri meg. Négy tipikus eset:

  • Kis tömbök. Ha nn néhány tucat alatt van, a setup- és maradékciklus-költség meghaladhatja a nyereséget. A küszöb hardver- és kernel-függő; méréssel kell megállapítani, nem tippelni. Egyetlen hívás ideje ilyenkor az óra felbontásánál is kisebb lehet, ezért kötegelt mérés kell: KK egymás utáni hívást mérünk egy időablakban (adaptívan választott KK, pl. addig duplázva, amíg az ablak ≥ 1 ms), majd az időt KK-val osztjuk. Az optimalizálás elleni védelmet (volatile nyelő, asm-akadály) és az eredményellenőrzést meg kell tartani, a ciklusvezérlés overheadjét (üres kötegciklus) külön kell mérni és közölni. Elfogadható a becslés, ha az ns/hívás a KK ésszerű növelésére stabilizálódik; a jelentés a KK-t és a szóródást (IQR) is megadja, nem csak egy kis különbségből számolt gyorsulási arányt.
  • Sok elágazás. Ha a ciklusmag if-eket tartalmaz, a sávon belüli szétválás (divergencia) miatt a NEON előny eltűnik, és gyakran lassabb, mint a skaláris változat predikcióbarát ága.
  • Nem összefüggő (gather/scatter) hozzáférés. A NEON szekvenciális betöltést szeret; ha az indexek futásidőben számítottak és szétszórtak, a csomagolás (packing) költsége meghaladja a nyereséget.
  • Egyszeri végrehajtás — költségmodell, nem szabály. A „csak egyszer fut” önmagában nem dönt. A döntés mérhető feltételekből áll: a teljes munka (WW elem és elemenkénti nyereség), a setupköltség (adatátrendezés, igazítás, belépési/maradék kód), az újrafelhasználás (hányszor fut ugyanaz a kernel), a memóriaforgalom (ha a kernel sávszél-korlátos, a SIMD kevesebbet nyer) és a fejlesztési/audit cél. Egyszeri, de nagy munkánál (például egy 100 MiB-os puffer egyszeri feldolgozása) a SIMD jelentős nyereséget adhat; kis egyszeri munkánál a setup dominál. A döntést a 12.5.3 mérési szerződés szerint, a fenti költségmodellből kell meghozni, nem a „csak egyszer fut” szabályból.

Ezekben az esetekben a helyes döntés az, hogy mérünk, és a mérés alapján nem vektorizálunk.

12.5.8 Feladatok

  1. (magyarázó, alapszint — cél: megértés-ellenőrzés) A hipotetikus számpélda S=2,31S = 2{,}31 gyorsulásához vezesd le a modellbe illesztett seffs_{\text{eff}} értékét p=0,90p = 0{,}90, p=0,95p = 0{,}95 és p=0,98p = 0{,}98 feltevéssel. Mit mond az eredmény arról, mennyire függ az seffs_{\text{eff}} a feltételezett pp-től, és következik-e belőle bármilyen diagnózis?

  2. (implementációs, középszint — cél: rutinépítés) Módosítsd a mérési vázat úgy, hogy nn-t lépcsőzetesen növelje 1616-tól 10485761\,048\,576-ig, és minden nn-re írja ki a skaláris és NEON-időt. Készíts táblázatot, és állapítsd meg, melyik nn a vektorizáció megtérülési küszöbe ezen a hoston. A lab-a048-sweep.c és lab-a048-sweep build-célnevet használd.

  3. (hibakeresési/mérési, középszint — cél: rutinépítés) Egy újrafordítás után a NEON-változat mért ideje gyanúsan közel van a skalárishoz. Kolléga szerint „a GCC a -O2 szinten átírta a NEON-kódot”. Mutasd meg, hogy ez a kézzel írt .s kernelre nem lehet igaz, majd keresd meg a valódi okot aarch64-linux-gnu-nm, aarch64-linux-gnu-objdump -d --disassemble=add_f32_neon és a build-időbélyegek segítségével. Milyen hibák vezethetnek ahhoz, hogy a mért bináris nem a várt kernelt futtatja?

  4. (integráló, elmélyült — cél: fejezetek összekapcsolása: Az AAPCS64 regiszterszerződés + korábbi n=0 határeset-fegyelem) Ellenőrizd objdump-pal, hogy az add_f32_scalar és az add_f32_neon egyike sem nyúl az AAPCS64 szerint megőrzendő (callee-saved) regiszterekhez — X19–X28, illetve V8–V15 alsó 64 bitje — anélkül, hogy STP/LDP-vel visszaállítaná őket. Ezután kövesd nyomon GDB-vel mindkét kernelt n=0n=0 bemenetre: igazold, hogy a RET előtt egyetlen LDR/STR sem fut le. Mi történne, ha valamelyik kernel elfelejtené ellenőrizni az n=0n=0 esetet, és már az első iterációban olvasna a (nem létező) tömbelemből?

12.5.9 Megoldások

1. megoldás — Segítség. Az seff=p/(1/S−(1−p))s_{\text{eff}} = p / (1/S - (1-p)) képletbe helyettesíts be sorban három pp-értéket, és figyeld, mennyit változik az eredmény.

1. megoldás — Teljes megoldás. S=2,31S = 2{,}31 mellett 1/S=0,43291/S = 0{,}4329.

  • p=0,90p = 0{,}90: seff=0,90/(0,4329−0,10)=0,90/0,3329≈2,70s_{\text{eff}} = 0{,}90 / (0{,}4329 - 0{,}10) = 0{,}90/0{,}3329 \approx 2{,}70.
  • p=0,95p = 0{,}95: seff=0,95/(0,4329−0,05)=0,95/0,3829≈2,48s_{\text{eff}} = 0{,}95 / (0{,}4329 - 0{,}05) = 0{,}95/0{,}3829 \approx 2{,}48.
  • p=0,98p = 0{,}98: seff=0,98/(0,4329−0,02)=0,98/0,4129≈2,37s_{\text{eff}} = 0{,}98 / (0{,}4329 - 0{,}02) = 0{,}98/0{,}4129 \approx 2{,}37.

Ugyanabból az SS-ből a feltételezett pp-től függően más-más seffs_{\text{eff}} adódik; az seffs_{\text{eff}} tehát a modell paramétere, nem mérési eredmény. Egyik érték sem igazol memóriasávszélesség-, cache- vagy sávkihasználási problémát: ehhez pp-t időalapú módszerrel kellene megmérni (lásd „Hogyan becsülhető pp?”), és a feltételezett okot célzott, natív hardveres méréssel kellene ellenőrizni. Az seff<4s_{\text{eff}} < 4 az s=4s = 4 modellfeltevéssel sem áll ellentmondásban, mert az csak modell, nem korlát.

2. megoldás — Segítség. A bench függvény már megvan; csak egy külső ciklusba kell csomagolni, amely nn-et duplázza, és minden lépésben friss, igazított puffereket foglal. A küszöböt vizuálisan ott keresd, ahol a két görbe metszi egymást.

2. megoldás — Teljes megoldás. A sweep-váz a bench függvényt hívja meg növekvő nn-re, mindig friss (aligned) pufferekkel. A küszöb jellemzően ott van, ahol a NEON-idő először lesz kisebb a skalárisnál; tipikusan néhány száz és néhány ezer elem közé esik, de konkrét értéke host- és QEMU-verziófüggő, ezért méréssel kell megállapítani. A helyes jelentés: „ezen a hoston, ezzel a kernellel, ezen a bemeneteloszláson”. Nem általános érvényű szám.

3. megoldás — Segítség. A .s fájlt a GCC csak továbbadja az assemblernek — melyik lépésben lenne alkalma bármit „átírni”? Utána nézd meg, honnan jön a binárisban az add_f32_neon szimbólum.

3. megoldás — Teljes megoldás. A kézzel írt lab-a048-kernels.s a GCC-től csak az assemblerhez jut: a -O2 a C-forrásokra vonatkozik, a .s utasításait sem nem vektorizálja, sem nem alakítja vissza skaláris FADD-dá. Ha az add_f32_neon alatt a binárisban nem fadd v0.4s áll, a valódi ok a buildben keresendő:

  • elavult objektum: a lab-a048-kernels.o régebbi, mint a .s (a make függőségi sora hiányzik, vagy kézi build után nem fordítottuk újra) — ls -l --time-style=full-iso a két fájlra;
  • rossz objektum vagy másik függvény: egy másik .o (például az a047 könyvtárából átmásolt fájl) definiál ugyanilyen nevű függvényt — ezt előzi meg a különböző add_i32_*/add_f32_* név; aarch64-linux-gnu-nm -A *.o | grep add_ megmutatja, melyik objektum definiálja;
  • hibás linkelés: a linkparancs nem a várt objektumot kapja, vagy egy könyvtár elsőbbséget élvez — a -Wl,-Map=lab-a048.map linkertérkép megmutatja, honnan jött a szimbólum.

Javítás: tiszta újrafordítás (rm -f *.o lab-a048-bench, majd a build), és az objdump -d --disassemble=add_f32_neon ellenőrzése a mérés előtt. Az autovektorizáció vizsgálatához külön, C-ben írt kernelek kellenek (például -O2 és -O3 -fopt-info-vec összevetése); kézzel írt assemblyn ez a kérdés nem értelmezhető.

4. megoldás — Segítség. Nézd meg, mely regisztereket érinti ténylegesen a két kernel (a forrás alapján X0–X6 és V0–V1), és vesd össze az AAPCS64 regiszterszerződés callee-saved listájával — esik-e bármelyik abba a tartományba? Az n=0n=0 nyomkövetéséhez tegyél töréspontot a kernel elejére és a RET elé.

4. megoldás — Teljes megoldás. Az add_f32_scalar és az add_f32_neon kizárólag X0–X6 (az X6 a NEON-ág bájteltolása) és V0–V1 regisztereket használ — ezek egyike sem szerepel az AAPCS64 callee-saved listáján (X19–X28, V8–V15), ezért egyik kernelnek sem kell STP/LDP-vel megőriznie semmit; az objdump -d kimenetében emiatt nem is várunk ilyen utasítást. Az n=0n=0 esetben: az add_f32_scalar cbz x3, 2f-je azonnal a ret-hez ugrik; az add_f32_neon-ban a lsr/lsl 0-t számol ki x5-nek, a cbz x5, 2f idevisz, majd a cmp x4, x3 / b.hs 4f (0 és 0 egyenlő, a „higher or same” ilyenkor is teljesül) szintén a ret-hez vezet — egyik ágban sem fut le ldr/str. Ha ez a határellenőrzés hiányozna, az első iteráció egy 0 méretű tömb nemlétező elemét olvasná: ez kisebb léptékben ugyanaz a hibaosztály, amit a Záróprojekt I n*n*sizeof(float)-túlcsordulás- és n==0-ellenőrzése tárgyal (a057–a060) — ott a hiányzó korai kilépés egy egész mátrixszorzó modult tenne memóriabiztonsági szempontból megbízhatatlanná, itt egy két-utasításos kernelt.

12.5.10 Rövid összefoglaló

A NEON-gyorsulás mérése azonos bemeneten, kernelenként külön kimeneti pufferrel és a méréstől elválasztott korrektségi ellenőrzéssel, melegítés után, váltakozó sorrendű ismételt futással, medián és IQR közlésével történik; a teszt értékét egy szándékosan hibás kernel ellenpróbája igazolja. Az Amdahl-modell S=1/((1−p)+p/s)S = 1/((1-p)+p/s) alakban írja le a gyorsulást, ahol pp időhányad, nem utasításszám-hányad, és csak időalapú módszerrel becsülhető. A modell határértéke 1/(1−p)1/(1-p); az s=4s = 4 egyszerű modellfeltevés, nem az ISA-ból következő felső korlát. A mért SS-ből visszaszámolt seffs_{\text{eff}} a feltételezett pp-n múlik, ezért nem mért sávkihasználtság, és diagnózist sem igazol. QEMU-ban a kapott idő emulációs idő; belőle fizikai memóriasávszélességre nem lehet következtetni. Kis tömböknél, sok elágazásnál és szétszórt hozzáférésnél a vektorizáció jellemzően nem térül meg — ezt is mérés dönti el.

Továbbhasznált definíciók: gyorsulás (speedup); vektorizálható hányad (vectorizable fraction), mint időhányad; Amdahl-modell.

12.5.11 Források és ellenőrzési hiányok

A linkek és a dokumentumverziók közös állapota az Olvasói útmutató forrásállapot-táblájában van; itt csak az alfejezet saját megállapításai szerepelnek.

  • Arm Architecture Reference Manual for A-profile architecture (DDI0487) — az FADD (vector), LDR (immediate, SIMD&FP) és STR (immediate, SIMD&FP) kódolásának, valamint a q-regiszteres hozzáférés igazítási követelményeinek elsődleges forrása. Ellenőrizve: a link él (a developer.arm.com → support.arm.com átirányítás megerősített); a fejezetszám és a kiadásbetű az Arm-oldalak közös korlátja miatt nem ellenőrzött — a konkrét utasításkódolást a laborban kézzel kell visszakeresni.
  • Arm Neon intrinsics referencia — a NEON belső műveletek listája és szemantikája. Ellenőrizve: a link él; ugyanaz a JS-renderelési korlát érvényes, mint fent.
  • QEMU dokumentáció, user-mode fejezet — tartalmilag is ellenőrizve: a master ághoz tartozó hivatalos dokumentáció nem állít semmit a cache-hierarchia, a memóriasávszélesség vagy a betöltési késleltetés modellezéséről — a fejezet lényegében a rendszerhívás-fordítást és a szál-/memóriamodell host–guest eltéréseit tárgyalja. A fenti, „QEMU nem modellezi hűen a cache-hierarchiát” állítás ezért nem egy explicit QEMU-dokumentált korlátból, hanem a TCG (Tiny Code Generator) ismert tervezési elvéből következik: funkcionális, utasításszintű emulátor, nem cikluspontos szimulátor. A hivatkozott dokumentáció emellett a master, nem egy konkrét kiadott verzió állapotát tükrözi; a ténylegesen telepített (pl. Ubuntu 24.04 csomagolt) QEMU-verzió dokumentációja ettől eltérhet.
  • GNU Binutils kézikönyv — objdump -d és a többi binutils-eszköz referenciája. Tartalmilag ellenőrizve: a jelenlegi kiadás binutils 2.47.
  • GNU GDB kézikönyv — a disassemble és a távoli hibakeresés referenciája. Tartalmilag ellenőrizve, de verzió-megjegyzéssel: a „current” fejlesztői pillanatkép (közös verziókorlát).
  • GCC kézikönyv — a -O2 és az AArch64-specifikus kapcsolók referenciája. Tartalmilag ellenőrizve: a legújabb listázott kiadás GCC 16.2. (Korábban ez a hivatkozás tévesen a Binutils-kézikönyvvel egy közös link alá volt sorolva — a GCC a Binutilstól és a GDB-től független projekt, külön dokumentációval.)

Ellenőrzési hiányok, amelyek a fenti ellenőrzés után is ténylegesen fennmaradnak:

  1. A QEMU pontos időzítésmodellje — mennyire tér el egy adott natív host mért idejétől — sem ebben, sem korábbi munkafolyamatban nincs ellenőrizve; ehhez tényleges mérés kellene fizikai hoston és QEMU alatt egyaránt, amire ennek a könyvnek a készítése során nem került sor.
  2. A p = 0,95 vektorizálható hányad feltételezett érték, az erre épülő számítás matematikai szemléltetés. A tényleges pp időhányad, amelyet csak időalapú módszerrel (profilozás natív hardveren, a részek külön mérése) lehet becsülni; utasításszámlálással nem.
  3. A kimenetminta, a táblázat és az ábra idő- és gyorsulásértékei (12,004 ms, 5,198 ms, 2,31×) hipotetikus számpéldák — nem fizikai hoston vagy QEMU-ban lefuttatott mérés eredményei. A benchmark logikáját (külön ellenőrzés, a hibás skaláris kernel FAIL ellenpróbája) helyettesítő eszközlánccal — zig cc (Clang, musl), Unicorn-alapú AArch64 user-mode emulátorban, kisebb nn-nel — futtattuk; az ott kapott időket szándékosan nem közöljük, mert az emulátor ideje semmilyen hardverre nem jellemző.
  4. A telepített Ubuntu 24.04 LTS csomagolt gcc-aarch64-linux-gnu, qemu-user és binutils pontos verziószáma ebben a munkafolyamatban nincs lekérdezve; a fenti dokumentációs linkek ezért nem feltétlenül a laborban ténylegesen használt verzióra mutatnak.
  5. A „mikor nem térül meg” küszöböket (kis tömbök, sok elágazás) méréssel kell megerősíteni; az itt szereplő tartományok tájékoztató jellegűek.
