9.4 LoRaWAN: nagy hatótáv kis energiával

9.4.1 Motiváció: távoli üvegház gateway nélkül

A TerraSense alapértelmezett laborarchitektúrájában a ts-node szenzorcsomópont UDP-n küldi a mérési adatokat a ts-gw gatewaynek, amely aztán MQTT-n továbbítja a backend felé. Ez a modell akkor működik jól, ha a csomópont és a gateway között van megbízható helyi hálózat, például egy üvegházon belüli Wi‑Fi vagy vezetékes Ethernet.

Más a helyzet, ha a monitorozott üvegház egy távoli, infrastruktúra nélküli területen van, vagy ha egyetlen gatewaynek több, egymástól több száz méterre lévő csomópontot kellene kiszolgálnia. Ilyenkor a rövid hatótávú rádiók (BLE, Wi‑Fi) nem elegendők, a cellás kapcsolat pedig túl drága és energiaéhes lenne egy elemes szenzorhoz. A LoRaWAN ezt a rést tölti be: kilométeres hatótávot ad alacsony adatsebességgel és nagyon kis energiafogyasztással, cserébe szigorú adásgyakorisági korlátokkal. Ebben az alfejezetben megismerjük a LoRaWAN architektúráját, eszközosztályait, aktiválási módjait, és kiszámítjuk, milyen gyakran küldhet egy eszköz a duty cycle szabályok betartásával.

9.4.2 Fogalmak és működés

9.4.2.1 Architektúra és a csillag-csillag topológia

Definíció. A LoRaWAN (Long Range Wide Area Network) egy LPWAN (Low Power Wide Area Network) hálózati protokoll, amely a LoRa modulációt használja. A hálózat négy fő elemből áll:

  • End device (végberendezés): a szenzor vagy aktuátor, például a ts-node.
  • Gateway (átjáró): rádiós bázisállomás, amely a LoRa rádiójeleket IP-csomagokká alakítja. Egy gateway több ezer eszközt is kiszolgálhat. A gateway nem fejti vissza az application payloadot, csak a rádiókereteket és a vételi metaadatokat továbbítja.
  • Network server (hálózati szerver): a LoRaWAN hálózati rétegét kezeli: munkamenet-állapot, DevAddr, frame counterek, MIC-ellenőrzés, duplikátumszűrés, adaptív adatsebesség és downlink-ütemezés. A hálózati kulccsal (NwkSKey) a hálózati réteg integritását és a hálózati mezőket védi; az application payload visszafejtése nem a feladata.
  • Application server (alkalmazásszerver): az application payloadot az AppSKey kulccsal fejti vissza, dekódolja az alkalmazás sémáját, továbbítja az alkalmazás felé, és fogadja az alkalmazás parancsait. Gyakran MQTT-n vagy HTTP-n kommunikál a backenddel.
  • Join server (LoRaWAN 1.1): a gyökérkulcsokat (NwkKey, AppKey) tárolja, és a join során származtatja, majd szétosztja a munkamenetkulcsokat a network server és az application server felé. Ezzel a hálózati és az alkalmazási kulcs szétválasztható.

A LoRaWAN rádiós oldala csillag topológiájú: minden end device közvetlenül egy vagy több gatewayhez küld, az eszközök egymással nem kommunikálnak. A gatewayek IP-hálózaton (Ethernet, Wi‑Fi, cellás) csatlakoznak a network serverhez, ami egy második, hálózati csillagot alkot. Ezt a kétszintű felépítést nevezzük csillag-csillag topológiának.

Az ábra azt mutatja, hogy a ts-node LoRa rádión küld a ts-gw-nek, amely IP-n továbbít a network servernek, onnan pedig az application serverhez jut az adat. A gateway nem értelmezi és nem fejti vissza az application payloadot, csak a rádiókereteket és a vételi metaadatokat továbbítja. A MIC-et és a hálózati mezőket a network server ellenőrzi NwkSKey-jel, az application payloadot pedig az application server fejti vissza AppSKey-jel. A LoRaWAN 1.1-ben a join server osztja szét a két kulcsot, ezért a network server nem kapja meg automatikusan az application payload visszafejtéséhez szükséges kulcsot. A LoRaWAN 1.0.x-ben a kulcsszármaztatás egyszerűbb, és a network server jellemzően mindkét munkamenetkulcsot ismeri; ilyenkor a két szerep szétválasztása elsősorban üzemeltetési és szerződéses, nem kriptográfiai garancia.

9.4.2.2 Class A, B és C: downlink-ablakok

Definíció. A LoRaWAN három eszközosztályt határoz meg, amelyek abban különböznek, hogy az eszköz mikor tud downlink üzenetet fogadni:

  • Class A: minden uplink után két rövid downlink-ablakot nyit (RX1 és RX2). Az eszköz csak ezekben az ablakokban hallgat. Ez a legalacsonyabb energiafogyasztású mód, és minden LoRaWAN eszköznek támogatnia kell.
  • Class B: az eszköz ütemezett időrésekben (ping slots) is hallgat, így a downlink késleltetése kisebb, de az energiafogyasztás nagyobb. A Class B eszközök szinkronizálódnak a gateway beaconjaival.
  • Class C: az eszköz folyamatosan nyitva tartja a vevőjét, kivéve, amikor éppen ad. Ez a legkisebb downlink késleltetést adja, de csak hálózati táplálás mellett ésszerű.

A TerraSense elemes szenzorcsomópontja számára a Class A a természetes választás, mert a mérési ciklus (10 perc az Energiamodell és az elemélettartam kiszámítása alapján) ritkán igényel azonnali parancsot. A szelep vezérléséhez a parancs a következő uplink utáni RX1 vagy RX2 ablakban érkezhet meg, de ez csak a következő fogadási lehetőség, nem kézbesítési garancia: ha az uplink vagy a downlink elveszik, a parancs nem érkezik meg. Ezért a parancsnak TTL-t (lejárati időt) kell adni, az application server a TTL-en belül újrapróbálkozhat, és a szelep helyi biztonsági logikája (a Aktuátorok: biztonságos vezérlés és visszajelzés alfejezet max_on_time korlátja) a parancs hiányában is zár. A gyakorlati késleltetés így a következő uplinkig tartó várakozás plusz az esetleges újrapróbálkozások ideje, nem pedig garantáltan legfeljebb egy periódus.

9.4.2.3 OTAA vs. ABP aktiválás

Definíció. A LoRaWAN kétféle aktiválási módot kínál:

  • OTAA (Over‑The‑Air Activation): az eszköz csatlakozási kérelmet (join request) küld, amelyre a join server (LoRaWAN 1.1) vagy a network server (1.0.x) join accept üzenettel válaszol. Ezután az eszköz és a hálózat megegyezik a DevAddr azonosítóban és a munkamenetkulcsokban. A LoRaWAN 1.1-ben a join server a gyökérkulcsokból (NwkKey, AppKey) származtatja a hálózati NwkSKey és az alkalmazási AppSKey munkamenetkulcsot, és külön adja át a network servernek, illetve az application servernek. Az eszköz az application payloadot AppSKey-jel titkosítja, a MIC számításához pedig a hálózati kulcsot használja. Az OTAA lehetővé teszi a kulcsok rotációját és a biztonságos újracsatlakozást.
  • ABP (Activation By Personalization): a DevAddr és a munkamenetkulcsok előre be vannak égetve az eszközbe, így nincs join eljárás; az eszköz azonnal küldhet. Cserébe a kulcsok statikusak, a network server jellemzően mindkét kulcsot ismeri, és a frame counter elvesztése biztonsági kockázatot jelent.

A TerraSense esetében az OTAA javasolt, mert a join serverrel való időszakos újracsatlakozás lehetővé teszi a kulcsfrissítést és a biztonságos flottakezelést. Az ABP csak olyan zárt, felügyelt környezetben elfogadható, ahol a frame counter perzisztens tárolása garantált, és a network server és az application server szerepe nem válik szét kriptográfiailag.

9.4.2.4 Spreading factor, adatsebesség, rádióidő és duty cycle

Definíció. A LoRa modulációban a spreading factor (SF) azt adja meg, hogy egy szimbólum hány chipből áll: 2SF2^{SF} chipből. A chip a chirp moduláció elemi időegysége, a szimbólum pedig SFSF bit információt hordoz; a kódolási ráta, a header és a CRC miatt a tényleges adatbitráta ennél kisebb. A szimbólumidő Tsym=2SF/BWT_{\text{sym}} = 2^{SF}/BW, tehát az SF növelése exponenciálisan növeli a szimbólumidőt: 125 kHz-en SF7 esetén Tsym=1,024T_{\text{sym}} = 1{,}024 ms, SF12 esetén 32,76832{,}768 ms, ami ugyanannyi szimbólumnál 32-szer hosszabb adást jelent. Nagyobb SF nagyobb érzékenységet és hatótávot ad, de kisebb adatsebességet és hosszabb rádióidőt (time on air) eredményez. A duty cycle (adáskihasználtság) azt a szabályozási korlátot jelenti, amely megadja, hogy egy adott frekvenciasávban vagy alsávban az eszköz az idő mekkora hányadában adhat.

A LoRaWAN régiós szabályozásai – például az EU868 sávban az ETSI előírásai – jellemzően 1% vagy annál kisebb duty cycle-t írnak elő egyes alsávokra. Ez az érték ellenőrzési igényt hordoz: a pontos számok a régiótól, az alsávtól és a szabályozás aktuális verziójától függenek. A következő számításban ezért illusztratív értéket használunk.

A rádióidő nem lineárisan arányos az SF-fel: a szimbólumidő 2SF2^{SF}-fel nő, a payload szimbólumszáma pedig a payload méretétől, az SF-től és a kódolási rátától függ. A pontos LoRa idő a levegőben képletet a Rádiós technológiák összevetése alfejezet mutatta be. Ha egy eszköz rádióideje TairT_{\text{air}}, és az adott szabályozott alsávban megengedett duty cycle dd, akkor a minimális periódus:

Tmin=TairdT_{\text{min}} = \frac{T_{\text{air}}}{d}

Ebből a maximális üzenetgyakoriság:

fmax=1Tmin=dTairf_{\text{max}} = \frac{1}{T_{\text{min}}} = \frac{d}{T_{\text{air}}}

A gyakorlatban az eszköz több csatornát is használhat, de az ugyanabba a szabályozott alsávba eső csatornák adásideje összeadódik; a csatornaváltás nem nullázza a felhasznált keretet. Az EU868 alapértelmezett 868,1/868,3/868,5 MHz-es csatornái például jellemzően ugyanabba a 868,0–868,6 MHz-es alsávba esnek, ezért a három csatorna együttes adásidejére kell a korlátot betartani. A különböző alsávok külön kerettel rendelkeznek, és a hálózati szerver fair-use szabálya ettől független, további korlát lehet.

9.4.3 Döntési szempontok

A LoRaWAN akkor a legjobb választás, ha:

  • nagy hatótávra van szükség (1–10 km, nyílt terepen),
  • az adatmennyiség kicsi (napi néhány tucat üzenet, egyenként néhány tíz bájt),
  • az eszköz elemes, és az energiafogyasztás kritikus,
  • a késleltetés másodperces vagy perces nagyságrendje elfogadható.

Nem jó választás, ha:

  • nagy sávszélesség kell (például kép vagy hang átvitele),
  • azonnali downlink parancsokra van szükség,
  • az eszköz hálózati táplálású, és a fogyasztás nem szempont,
  • az adatforgalom sűrű, mert a duty cycle korlátokba ütközünk.

A Rádiós technológiák összevetése alfejezetben részletesen összehasonlítottuk a LoRaWAN-t a BLE, Wi‑Fi és cellás megoldásokkal. A TerraSense alapértelmezett laborhálózatában a rövid hatótávú BLE/UDP megoldást használjuk, de a LoRaWAN-t alternatív uplinkként tartjuk nyilván azokra a telephelyekre, ahol a ts-gw nem telepíthető a csomópont közelébe.

Továbbvitt eredmény. A LoRaWAN mint alternatív uplink döntését a TerraSense-ben a következőképpen rögzítjük: ha egy telephelyen nincs helyi ts-gw, a ts-node LoRaWAN Class A végberendezésként, OTAA aktiválással csatlakozik egy hálózati szerverhez. Az adat az application serveren keresztül MQTT-topicra kerül, és onnan a meglévő ts-backend ingest útvonalat használja. Ezt a lehetőséget a gateway szerepe: híd, puffer, biztonsági határ és a záróprojekt: a teljes TerraSense rendszer összeállítása és átvétele alfejezetek használják fel.

9.4.4 Kidolgozott példa: maximális üzenetgyakoriság a duty cycle-ből

Tegyük fel, hogy a TerraSense egyik távoli üvegházában a ts-node LoRaWAN Class A eszközként működik az EU868 sávban. Az eszköz SF7 spreading faktort használ 125 kHz sávszélességgel, a payload mérete 10 bájt. A rádióidő ezzel a beállítással körülbelül Tair=50T_{\text{air}} = 50 ms (illusztratív érték, a pontos szám a LoRa moduláció fejléc- és CRC-paramétereitől függ). A régiós szabályozás az adott szabályozott alsávra – például a 868,0–868,6 MHz-es alsávra – d=0,01d = 0{,}01 (1%) duty cycle-t ír elő (ellenőrizendő az aktuális ETSI szabályozásban).

A minimális periódus az alsávban összesített adásidőre:

Tmin=Taird=0,05 s0,01=5 sT_{\text{min}} = \frac{T_{\text{air}}}{d} = \frac{0{,}05 \text{ s}}{0{,}01} = 5 \text{ s}

A maximális üzenetgyakoriság:

fmax=dTair=0,010,05 s=0,2 üzenet/sf_{\text{max}} = \frac{d}{T_{\text{air}}} = \frac{0{,}01}{0{,}05 \text{ s}} = 0{,}2 \text{ üzenet/s}

Ez azt jelenti, hogy az eszköz az adott alsávban összesen legfeljebb 50 ms-ot adhat 5 másodpercenként, ami 50 ms-os uplink esetén átlagosan 5 másodperces küldési periódusnak felel meg. Ez a keret a csatornaváltással nem növelhető, ha a csatornák ugyanabba az alsávba esnek. A TerraSense 10 perces mérési ciklusa (T=600T = 600 s) ennél két nagyságrenddel ritkább: egy 50 ms-os uplink a 600 s-os periódus 0,0083%-át használja, tehát a duty cycle korlát nem szűk keresztmetszet ebben az alkalmazásban.

Fontos megjegyezni, hogy a duty cycle az alsávra vonatkozik, nem az egyes csatornákra és nem az eszközre. Az ugyanabba az alsávba eső csatornák adásideje összeadódik, ezért a véletlenszerű csatornaváltás nem nullázza a felhasznált keretet. A különböző alsávok külön korláttal rendelkeznek, és a hálózati szerver fair-use szabálya (például egy közösségi hálózat napi adásidő-kerete) ettől független, további korlát lehet. A tervezés során a legszigorúbb érintett alsávra és a szerver fair-use szabályára is ellenőrizni kell a rádióidőt.

9.4.5 Ellenőrzés és hibakeresés

A LoRaWAN eszközök duty cycle betartását a network server naplózza: minden frame-hez tartozik egy időbélyeg és a rádióidő. A The Things Stack vagy más LoRaWAN hálózati szerver konzolján ellenőrizhető, hogy az eszköz adásai megfelelnek-e a régiós szabályoknak. A gatewayek is jelentik a vett jel erősségét (RSSI) és a jel-zaj viszonyt (SNR), ami a hatótáv és a spreading factor beállításának ellenőrzésére használható.

9.4.6 Tipikus hibák és félreértések

  1. ABP használata frame counter mentése nélkül. Ha az eszköz újraindul és a frame counter lenullázódik, a network server ismétlésnek vagy visszajátszásnak érzékeli a frame-eket, és elutasítja azokat. A frame countert nem felejtő memóriában kell tárolni, vagy egyszerűbb OTAA-t használni, ahol a join új kulcsokat generál.

  2. Class A eszköznél azonnali downlink elvárása. Sok fejlesztő azt feltételezi, hogy a parancs azonnal eljut az eszközhöz, mint egy TCP-kapcsolatnál. A Class A eszköz csak az uplink utáni rövid RX1/RX2 ablakban hallgat, ezért a parancs legkorábban a következő uplink után érkezhet meg, és ez csak fogadási lehetőség, nem kézbesítési garancia. Uplink- vagy downlinkvesztés esetén a parancs a következő periódusban próbálható újra, ezért TTL-t, újrapróbálkozást és helyi biztonsági zárást kell tervezni. Ha másodperces garanciájú vezérlés kell, Class C vagy más technológia szükséges.

  3. A duty cycle figyelmen kívül hagyása. A LoRaWAN sávok szigorú szabályozás alatt állnak; a túlzott adáskihasználtság a hálózati szerver frame-eldobásához vezethet, és akár jogi következményei is lehetnek. Az ugyanabba a szabályozott alsávba eső csatornák adásideje összeadódik, ezért a csatornaváltás nem ad több keretet. A gyakori adatküldés igénye esetén növelni kell a periódust, csökkenteni kell a rádióidőt, vagy más technológiát kell választani.

  4. A spreading factor növelése mindig javítja a rendszert. Bár a nagyobb SF nagyobb hatótávot ad, a rádióidő is nő, ami növeli az energiafogyasztást és csökkenti a hálózati kapacitást. A cél a lehető legkisebb SF, amely még megbízható kapcsolatot ad.

9.4.7 Feladatok

9.4.7.1 (a) Fogalmi kérdés

Magyarázza el, miért nevezzük a LoRaWAN-t csillag-csillag topológiájúnak, és mi a különbség a network server és az application server szerepe között.

9.4.7.2 (b) Számolási feladat

Egy LoRaWAN eszköz az EU868 sávban SF7, 125 kHz beállítással 20 bájt payloadot küld. A rádióidő körülbelül 8080 ms (illusztratív). A duty cycle korlát 1%1\%. Számítsa ki a minimális periódust és a maximális üzenetgyakoriságot az adott szabályozott alsávra összesítve, és magyarázza el, miért nem növeli a keretet a csatornaváltás, ha a csatornák ugyanabba az alsávba esnek.

9.4.7.3 (c) Implementációs feladat a TerraSense-ben

A TerraSense távoli üvegházában a ts-node LoRaWAN-t használ, és a szelepet is vezérelnie kell. Válasszon eszközosztályt (Class A/B/C) és aktiválási módot (OTAA/ABP), és indokolja a döntést. Térjen ki arra, hogyan jut el a szelepnyitási parancs az eszközhöz.

9.4.7.4 (d) Hibakeresési feladat

Egy ABP-vel aktivált LoRaWAN eszköz működik, de áramszünet után újraindul, és ezután a hálózati szerver nem fogadja az uplinkjeit. Mi lehet az ok, és hogyan javítható?

9.4.8 Megoldások

9.4.8.1 (a)

A csillag-csillag topológia azt jelenti, hogy az end device-ok rádiós csillagban kapcsolódnak a gatewayekhez (minden eszköz közvetlenül a gatewayhez, nem egymáshoz), a gatewayek pedig IP-hálózaton egy másik csillagban a network serverhez. A network server a LoRaWAN hálózati rétegét kezeli: munkamenet-állapot, DevAddr, frame counterek, MIC-ellenőrzés, duplikátumszűrés, adaptív adatsebesség és downlink-ütemezés. A hálózati kulccsal (NwkSKey) a hálózati réteg integritását és a hálózati mezőket védi, de az application payloadot nem neki kell visszafejtenie. Az application server az application payloadot az AppSKey kulccsal fejti vissza, dekódolja az alkalmazás sémáját, továbbítja az alkalmazásnak, és fogadja az alkalmazás parancsait. A LoRaWAN 1.1-ben a join server a gyökérkulcsokból származtatja és külön osztja szét a két munkamenetkulcsot, ezért a network server nem kapja meg automatikusan az application payload kulcsát. A LoRaWAN 1.0.x-ben a kulcsszármaztatás egyszerűbb, és a network server jellemzően mindkét kulcsot ismeri; ilyenkor a hálózati és alkalmazási szerep szétválasztása üzemeltetési és szerződéses, nem kriptográfiai garancia. A MIC az integritást védi, az AppSKey pedig az alkalmazási adat bizalmasságát; a kettő külön kulcson és külön szerepkörön alapul.

9.4.8.2 (b)

A minimális periódus:

Tmin=Taird=0,08 s0,01=8 sT_{\text{min}} = \frac{T_{\text{air}}}{d} = \frac{0{,}08 \text{ s}}{0{,}01} = 8 \text{ s}

A maximális üzenetgyakoriság:

fmax=18 s=0,125 üzenet/sf_{\text{max}} = \frac{1}{8 \text{ s}} = 0{,}125 \text{ üzenet/s}

Tehát az eszköz az adott alsávban összesítve legalább 8 másodpercenként küldhet, azaz legfeljebb 0,125 üzenetet másodpercenként. Ha a három alapértelmezett csatorna ugyanabba az alsávba esik, a csatornák közötti váltás nem növeli a keretet: a 80 ms-os adások együttes idejére kell a 8 másodperces periódust betartani.

9.4.8.3 (c)

A ts-node elemes szenzorcsomópont, ezért az energiafogyasztás kritikus. A szelep vezérlése nem igényel azonnali, másodpercnél pontosabb reakciót, ezért a Class A osztály elegendő: a parancs legkorábban a következő uplink utáni RX1 vagy RX2 ablakban érkezhet meg, ami legfeljebb 10 perces várakozást jelent. Ez azonban csak a következő fogadási lehetőség, nem kézbesítési garancia; elveszett uplink vagy downlink esetén a parancs nem érkezik meg. Ezért a parancsnak TTL-t kell adni, az application server a TTL-en belül újrapróbálkozhat, a szelep helyi max_on_time logikája pedig a parancs hiányában is zár. Aktiválási módként OTAA-t választunk, mert a join serverrel való újracsatlakozás kulcsrotációt és egyszerűbb flottakezelést tesz lehetővé. Ha később mégis gyorsabb downlink kellene, át lehet térni Class B-re az ütemezett ping résekkel, de az energiafogyasztás növekedésével számolni kell.

9.4.8.4 (d)

Az ok nagy valószínűséggel az, hogy a frame counter (FCntUp) nem lett perzisztensen tárolva, és az újraindulás után az eszköz nulláról kezdi a sorszámozást. A network server ezt visszajátszásnak vagy duplikátumnak érzékeli, és elutasítja a frame-eket. A javítás: a frame countert nem felejtő memóriában (például flashben) kell tárolni, és újraindulás után onnan kell folytatni. Hosszú távon jobb megoldás az OTAA-ra való áttérés, mert a join eljárás új kulcsokat és friss frame countereket generál.

9.4.9 Rövid összefoglaló

A LoRaWAN egy LPWAN protokoll, amely csillag-csillag topológiában nagy hatótávot és alacsony energiafogyasztást biztosít. Az end device-ok rádiós csillagban gatewayekhez kapcsolódnak, a gatewayek IP-n a network serverhez; a network server a hálózati réteget (munkamenet, frame counter, MIC, downlink-ütemezés) kezeli, az application server pedig az AppSKey-jel visszafejtett application payloadot dolgozza fel. A LoRaWAN 1.1-ben a join server osztja szét a hálózati és alkalmazási munkamenetkulcsot; 1.0.x-ben a network server jellemzően mindkét kulcsot ismeri. A három eszközosztály (A, B, C) a downlink-ablakok gyakoriságában tér el; a TerraSense elemes csomópontjához a Class A illik. A Class A csak a következő uplink utáni RX1/RX2 ablakban tud fogadni; ez a következő fogadási lehetőség, nem kézbesítési garancia. A tényleges késleltetés a következő uplinkig tartó várakozás plusz az esetleges újrapróbálkozások ideje, ezért TTL, újrapróbálkozás és helyi biztonsági zárás kell. Az OTAA aktiválás biztonságosabb, mint az ABP, mert lehetővé teszi a kulcsrotációt. A spreading factor a szimbólumonkénti 2SF2^{SF} chipet és a Tsym=2SF/BWT_{\text{sym}} = 2^{SF}/BW szimbólumidőt határozza meg, ezért a rádióidő az SF-fel exponenciálisan nő. A duty cycle szabályozási korlátot ad az adásgyakoriságra: Tmin=Tair/dT_{\text{min}} = T_{\text{air}} / d, és az ugyanabba a szabályozott alsávba eső csatornák adásideje összeadódik. A példában 50 ms rádióidő és 1% alsáv-duty-cycle mellett a minimális periódus 5 s, ami bőven lehetővé teszi a TerraSense 10 perces ciklusát. Továbbvitt eredmény: a LoRaWAN-t a TerraSense-ben alternatív uplinkként kezeljük: a ts-node Class A eszközként OTAA-val csatlakozik, az adat MQTT-n át a ts-backend-be jut; ezt a gateway szerepe: híd, puffer, biztonsági határ és a záróprojekt: a teljes TerraSense rendszer összeállítása és átvétele alfejezetek használják.

9.4.10 Források és ellenőrzési hiányok

A LoRaWAN protokoll alapfogalmai stabil tudás; a hivatalos specifikációt a LoRa Alliance adja ki (LoRaWAN Specification). A fejezet a LoRaWAN 1.1 szerepkiosztását követi: a join server a gyökérkulcsokból származtatja a NwkSKey és AppSKey munkamenetkulcsot, a network server a hálózati réteget és a MIC-et kezeli, az application server az AppSKey-jel fejti vissza az application payloadot. A LoRaWAN 1.0.x eltér: ott a network server jellemzően mindkét kulcsot ismeri, ezért a két szerep kriptográfiai szétválasztása nem garantált; ezt a szöveg külön jelzi. A rádióidő pontos számítása a LoRa moduláció paramétereitől (SF, sávszélesség, payload, coding rate, header, CRC) függ, ezért a példában használt 50 ms-os érték illusztratív. A duty cycle régiós értékei – például az EU868 868,0–868,6 MHz-es alsávjára vonatkozó 1% – az aktuális ETSI szabályozásból (EN 300 220 sorozat) ellenőrizendők; a pontos korlátok alsávonként, országonként és a szabályozás verziója szerint eltérhetnek, és a hálózati szerver fair-use szabálya külön korlát. A The Things Stack vagy más LoRaWAN hálózati szerver naplózási és konfigurációs funkcióinak nevei szintén ellenőrzést igényelnek. A fejezet számításai statikus ellenőrzéssel készültek; éles LoRaWAN-adás vagy hálózati szerveres mérés nem történt.
