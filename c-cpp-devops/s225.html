43.4 Alacsony szintű és C-interop eszközök C++23-ban

Ez az alfejezet a C++23 azon eszközeit tárgyalja, amelyek közvetlenül a bájtok, a nyers memória és a C API határán dolgoznak. Ezek az eszközök akkor hasznosak igazán, ha a mögöttes objektummodell már rögzített: a bájtok és az objektumreprezentáció alapjait Bitműveletek és objektumreprezentáció C++-ban tárgyalta, a tároló újrafelhasználásának szabályait Tároló újrafelhasználása és C++ objektumszabályok, a C API határát pedig extern C és két nyelvű header mutatta be. Az itt következő anyag ezekre épít, nem ismétli meg őket.

A laborprofil továbbra is ISO C++23, explicit -std=c++23 kapcsolóval. A konkrét GCC-, Clang-, libstdc++- és libc++-támogatást ebben a fejezetben a megnevezett profilokra (lásd profiltábla) ellenőrzöttnek, másra ellenőrizetlennek tekintjük. Minden új képességhez feature-test makrót és compile probe-ot kell használni; a C++20-as fallbackot a táblázat foglalja össze. A C oldali effective type szabályai Effective type, aliasing és objektumreprezentáció nem azonosak a C++ objektum-élettartam szabályaival, ezt a start_lifetime_as tárgyalásánál külön kiemelem.

43.4.1 Bájtsorrend, bájtswap és enum-alapú típuskonverzió

A std::byteswap C++23-as függvénysablon a <bit> fejlécben. Pontos alakja:

template<class T>
constexpr T byteswap(T value) noexcept;

Feltétel: T integrál vagy felsorolás típus. Visszatérési értéke az a T, amelynek bájtjai fordított sorrendben követik a bemenetét; ha sizeof(T) == 1, az érték változatlan. A függvény nem végez endian-konverziót önmagában: csak a bájtokat cseréli. A hálózati vagy fájlformátum-sorrendet a protokoll rögzíti, a natív sorrendet a C++20 óta ismert std::endian::native mondja meg. Helyes használat például:

#include <bit>
#include <cstdint>
#include <cstdio>

constexpr std::uint32_t to_network_order(std::uint32_t v) noexcept {
    if constexpr (std::endian::native == std::endian::little) {
        return std::byteswap(v);
    } else {
        return v;
    }
}

int main() {
    std::printf("%08x\n", to_network_order(0x01020304u));
}

A buildparancs: g++ -std=c++23 -Wall -Wextra -pedantic -o netorder netorder.cpp. Little-endian gépen a kimenet 04030201, big-endian gépen 01020304; a pontos érték a std::endian::native függvényében értelmezendő. A std::byteswap tehát feltételesen használható, a std::endian ellenőrzése nélkül könnyű rossz protokollt írni.

A std::to_underlying C++23-as segédfüggvény a <utility> fejlécben:

template<class Enum>
constexpr std::underlying_type_t<Enum> to_underlying(Enum e) noexcept;

Feltétel: Enum felsorolás típus. Visszatérési értéke a felsorolás alaptípusára konvertált érték. Előnye a static_cast-tal szemben, hogy kifejezi a szándékot, és scoped enumra is ugyanúgy működik. A std::is_scoped_enum C++23-as trait a <type_traits> fejlécben igaz, ha a típus scoped enum; ezzel overloadokat lehet megkülönböztetni. Példa:

#include <cstdint>
#include <type_traits>
#include <utility>

enum class Color : std::uint8_t { red = 1, green = 2 };

static_assert(std::is_scoped_enum_v<Color>);
static_assert(std::to_underlying(Color::green) == 2);

A C++20-as fallback: static_cast<std::underlying_type_t<E>>(e), illetve a scoped enum közelítése std::is_enum_v<T> && !std::is_convertible_v<T, int> feltétellel.

43.4.2 Objektum élettartam indítása nyers memóriában

A std::start_lifetime_as (P2590) C++23-as eszköz a <memory> fejlécben. Alapalakja:

template<class T>
T* start_lifetime_as(void* p) noexcept;

A feltételek két kategóriába esnek (C++23 [obj.lifetime]). Mandates (fordítási idejű): T teljes, implicit-lifetime típus — ha nem az (például std::string), a hívás ill-formed, a fordító elutasítja; ez nem futásidejű UB. Előfeltétel (futásidejű): a [p, p + sizeof(T)) bájttartomány lefoglalt tároló, amely a p-n keresztül elérhető (reachable) tárolórész része, és alignof(T)-nek megfelelően igazított; ennek megsértése nem definiált viselkedés. Élő objektum a területen nem tiltott: a hívás a tárolót újrahasznosítja, így az átfedő, korábban élő objektumok élettartama véget ér — ugyanazokkal a korlátokkal, mint bármely tár-újrahasznosításnál (például statikus, szál- vagy automatikus tárolású const teljes objektum tárolója nem hasznosítható újra; lásd Tároló újrafelhasználása és C++ objektumszabályok (20.6)). A függvény elindítja egy T objektum élettartamát anélkül, hogy konstruktort hívna vagy bájtokat másolna; a bájtok változatlanok. A std::start_lifetime_as_array ugyanezt tömb esetére végzi. Az std::is_implicit_lifetime_v<T> trait C++23-ban eldönti, hogy T implicit-lifetime típus-e; tipikusan skalár, triviálisan másolható és triviálisan destruálható osztály, aggregate.

Kidolgozott példa:

#include <cstdint>
#include <cstdio>
#include <cstring>
#include <memory>
#include <type_traits>

struct Header {
    std::uint32_t magic;
    std::uint32_t length;
};

static_assert(std::is_implicit_lifetime_v<Header>);

int main() {
    alignas(Header) unsigned char buffer[sizeof(Header)];
    const unsigned char bytes[sizeof(Header)] = {
        0x01, 0x02, 0x03, 0x04, 0x05, 0x06, 0x07, 0x08
    };
    std::memcpy(buffer, bytes, sizeof(Header));
    Header* h = std::start_lifetime_as<Header>(buffer);
    std::printf("%08x %08x\n", h->magic, h->length);
}

A buildparancs: g++ -std=c++23 -Wall -Wextra -pedantic -o lifetime lifetime.cpp. A példa várt kimenete endianfüggő: a printf a bájtokból olvasott értéket mutatja, nem univerzális layoutot. A Header* érvényessége a buffer élettartamához kötött; ha a buffer egy dinamikusan allokált puffer, akkor a puffer felszabadítása után a Header* dangling lesz.

Három esetet érdemes szétválasztani: (1) hibás típus (std::string): fordítási hiba a Mandates miatt; (2) hibás igazítású vagy nem elérhető tároló: nem definiált viselkedés, amelyre nem várhatunk megbízható sanitizer-diagnosztikát — a helyes kód az alignas-szal és a tároló méretével előre kizárja; (3) szabályos tár-újrahasznosítás: ha a területen korábban egy másik objektum élt, annak élettartama véget ér, és a régi pointerek csak a 20.6-ban leírt feltételekkel használhatók tovább. A memcpy, az implicit objektum-létrehozás és a start_lifetime_as viszonya: a memcpy a céltárolóban implicit módon létrehozhat implicit-lifetime objektumot, de a bájtokat másolja; a start_lifetime_as a meglévő bájtokat értelmezi másolás nélkül, és explicit módon jelöli, melyik típusú objektum kezd élni. A C oldali effective type szabályai Effective type, aliasing és objektumreprezentáció ettől eltérnek: a C++23-as eszköz a C++ objektum-élettartamot indítja el, nem a C effective type-ot állítja be.

Implementációs állapot: a 2026-10-25-i ellenőrzésnél sem a GCC 13.3 libstdc++-a, sem a Clang 22 libc++-a nem definiálta a __cpp_lib_start_lifetime_as makrót, ezért a fenti példát egyik profilban sem fordítottuk le. A feature-test makró neve __cpp_lib_start_lifetime_as; ha nem definiált, a képesség nem használható. A hordozható C++20-as fallback a std::memcpy egy lokális T objektumba, ami viszont másol, és nem ugyanaz a szemantika.

43.4.3 C API és okos pointerek: out_ptr és inout_ptr

A std::out_ptr és std::inout_ptr (P1132) C++23-as eszközök a <memory> fejlécben. Céljuk, hogy egy C API T** kimeneti paraméterét közvetlenül egy okos pointerhez lehessen kötni. A std::out_ptr(p, args...) egy out_ptr_t proxyt ad vissza, amely a C API hívás idejére átadja a nyers pointer címét. A három lépés külön történik: (1) a proxy konstruktora reseteli a p okos pointert — a régi erőforrás ekkor, a C hívás előtt szabadul fel (a C++23 szerződés szerint); (2) a C API beírja az új pointert a proxy által adott címre; (3) a proxy destruktora a beírt pointerrel visszaállítja p-t (reset(új)). Ebből következik, hogy sikertelen C-hívásnál, ha az API nem ír a pointerbe, a p már üres, és a régi erőforrás elveszett. Ha a régi ownert meg kell őrizni, tranzakciós mintát kell használni: nyers ideiglenes pointerbe hívjuk az API-t, siker esetén p.reset(tmp), hiba esetén p érintetlen. Az inout_ptr más szerződés: a kezdeti pointert átadja a C API-nak (a régi erőforrás felszabadítása az API dolga, és a smart pointer nem szabadítja fel előtte), így a realloc-szerű, replace-ra tervezett API-hoz való. Az adaptert az API tulajdonlási szerződése dönti el: kizárólag új erőforrást létrehozó (out-only), siker esetén felülíró C API-hoz inout_ptr-t tenni szivárgást okozhat, ha a régi erőforrást senki nem zárja le; ilyenkor out_ptr vagy a tranzakciós minta való. Három példa: out-only (out_ptr), replace/inout (inout_ptr), failure-preserving (nyers temp + reset siker esetén).

Példa std::unique_ptr-ral:

#include <cstdint>
#include <cstdio>
#include <cstdlib>
#include <cstring>
#include <memory>

struct Header {
    std::uint32_t magic;
    std::uint32_t length;
};

extern "C" int get_buffer(unsigned char** data, std::size_t* size) {
    auto* p = static_cast<unsigned char*>(std::malloc(64));
    if (!p) return -1;
    std::memset(p, 0, 64);
    const Header init{0x47414944u, 16u};   // natív reprezentáció: minden
    std::memcpy(p, &init, sizeof init);    // később olvasott bit definiált
    *data = p;
    *size = 64;
    return 0;
}

int main() {
    std::unique_ptr<unsigned char, decltype(&std::free)> buf(nullptr, &std::free);
    std::size_t n = 0;
    if (get_buffer(std::out_ptr(buf), &n) != 0) return 1;
    if (n >= sizeof(Header)) {
        Header* h = std::start_lifetime_as<Header>(buf.get());
        std::printf("%u %u\n", h->magic, h->length);
    }
}

A buildparancs: g++ -std=c++23 -Wall -Wextra -pedantic -o outptr outptr.cpp. A std::start_lifetime_as egyetlen dolgot tesz: a megadott tárolón elindítja egy Header objektum élettartamát, a tárolóban már meglévő bájtok értelmezésével. Nem inicializál: ha a bájtok határozatlanok (például egy frissen malloc-olt pufferben), a mezők olvasása határozatlan értéket ad. Ezért a get_buffer a példában minden később olvasott bájtot beállít. A bájtsorrendet sem kezeli: a bájtokat a gép natív reprezentációjaként értelmezi. A protokollt sem validálja: a length értékének ellenőrzése a hívó feladata.

Hálózatról vagy fájlból érkező, rögzített bájtsorrendű adatnál ezért a mezőnkénti dekódolás a helyes út, amely C++20-ban is működik:

// decode_header.cpp — C++20: mezőnkénti dekódolás little-endian wire formátumból
#include <cstddef>
#include <cstdint>
#include <cstdio>
#include <cstdlib>
#include <cstring>
#include <memory>

struct Header {
    std::uint32_t magic;
    std::uint32_t length;
};

// A C oldal 8 bájtos fejlécet ad: magic és length, mindkettő little-endian.
extern "C" int get_buffer(unsigned char** data, std::size_t* size) {
    auto* p = static_cast<unsigned char*>(std::malloc(64));
    if (!p) return -1;
    std::memset(p, 0, 64);                               // minden bájt definiált
    const unsigned char wire[8] = {'D', 'I', 'A', 'G', 16, 0, 0, 0};
    std::memcpy(p, wire, sizeof wire);
    *data = p;
    *size = 64;
    return 0;
}

std::uint32_t load_le32(const unsigned char* p) noexcept {
    return std::uint32_t{p[0]} | std::uint32_t{p[1]} << 8 |
           std::uint32_t{p[2]} << 16 | std::uint32_t{p[3]} << 24;
}

int main() {
    unsigned char* raw = nullptr;
    std::size_t n = 0;
    if (get_buffer(&raw, &n) != 0) return 1;
    std::unique_ptr<unsigned char, decltype(&std::free)> buf(raw, &std::free);
    if (n < 8) return 1;                                 // méretvalidálás
    const Header h{load_le32(buf.get()), load_le32(buf.get() + 4)};
    if (h.length > n - 8) return 1;                      // protokollvalidálás
    std::printf("magic=0x%08x length=%u\n", static_cast<unsigned>(h.magic),
                static_cast<unsigned>(h.length));
}

Buildjegyzőkönyv (lab-gcc profil). A decode_header.cpp g++ -std=c++20 -Wall -Wextra -Wpedantic beállítással figyelmeztetés nélkül fordult, és magic=0x47414944 length=16 kimenettel futott, ASan/UBSan alatt is. A std::out_ptr és a std::start_lifetime_as a GCC 13.3 libstdc++-ában nem érhető el, ezért az outptr.cpp-t a lab-gcc profilban nem fordítottuk le; az a lab-next profilhoz tartozik, és ott ellenőrizendő. A C oldali fejlécben a get_buffer extern "C" blokkban deklarálandó; a kétnyelvű header részleteit extern C és két nyelvű header tárgyalta. A C függvény szerződése: siker esetén (0) új, malloc-olt puffert ír a *data-ba, hiba esetén (−1, malloc-kudarc) a *data-t nem írja. Az out_ptr viselkedése ehhez: a proxy már a létrehozásakor reseteli az okos pointert (a korábbi erőforrást felszabadítja), és a hívás után csak akkor veszi át a beírt pointert, ha az nem null. Sikernél tehát a régi erőforrás felszabadul és az új kerül a helyére; hibánál a régi szintén felszabadult, és az okos pointer üres marad — szivárgás és dupla lezárás nincs, de a régi erőforrás elveszett. Ha a hibaágban a régi erőforrásnak meg kell maradnia, inout_ptr kell: az a meglévő pointert adja át, és ha a C függvény hibánál érintetlenül hagyja, az okos pointer visszakapja; vagy manuális raw változó és csak sikernél reset. Buildjegyzőkönyv: a Clang 22 / libc++ std::out_ptr/std::inout_ptr-ével egy élő-erőforrás-számlálós próba nem üres unique_ptr-rel: out_ptr sikernél új erőforrás (élő: 1), hibánál üres pointer (élő: 0); inout_ptr sikernél új erőforrás, hibánál a régi megmaradt (élő: 1); a végén minden erőforrás felszabadult (élő: 0). A Header* érvényessége a buf élettartamához kötött: a buf felszabadítása után a pointer dangling.

43.4.4 Allokáció és string puffer

Az allocate_at_least (P0401) C++23-ban az allokátorok olyan művelete, amely legalább a kért elemszámot allokálja, és visszaadja a ténylegesen allokált elemszámot is. Két felületen érhető el: tagfüggvényként a std::allocator<T>::allocate_at_least(n), általános allokátorra pedig a std::allocator_traits<A>::allocate_at_least(a, n); std::allocate_at_least szabad függvény nincs. Az eredmény egy std::allocation_result<T*>, ptr és count taggal, ahol count >= n. A felszabadítás szerződése (C++23 [allocator.members]): ha a p egy allocate_at_least(req) hívásból származik, a deallocate(p, n) hívásban az n bármely érték lehet, amelyre req <= n <= ret.count. Kérés 10, count 16 esetén tehát a 10 és a 16 közötti bármely méret elfogadható. A count megőrzése és használata ajánlott, mert így a tényleges kapacitást a teljes élettartam alatt ismerjük, de a kért mérettel való felszabadítás nem hiba. Példa:

#include <cstdio>
#include <memory>

int main() {
    std::allocator<int> a;
    auto r = a.allocate_at_least(10);
    std::printf("count = %zu\n", r.count);
    a.deallocate(r.ptr, r.count);
}

A buildparancs: g++ -std=c++23 -Wall -Wextra -pedantic -o alloc alloc.cpp. A std::vector C++23-as implementációja használhatja ezt a növekedésnél, de ez implementációfüggő, nem garantált. A lab-gcc profil GCC 13.3-as libstdc++-ában az allocate_at_least nem érhető el (nincs __cpp_lib_allocate_at_least), ezért a példa a lab-next profilhoz tartozik, és ott ellenőrizendő.

A std::string::resize_and_overwrite (P1072) C++23-as tagfüggvény lehetővé teszi, hogy a string pufferebe közvetlenül írjunk, elkerülve a kétszeres inicializálást. Alakja:

template<class Operation>
constexpr void resize_and_overwrite(size_type n, Operation op);

Az op hívása (char* p, size_type n) szignatúrával történik; visszatérési értéke a string új mérete, amely nem lehet nagyobb n-nél. Az op csak a puffer első n karakterébe írhat, a string objektumot nem módosíthatja. Példa POSIX read-dal:

// read_up_to.cpp — C++23: legfeljebb max bájt, a limit túllépése külön állapot
#include <cerrno>
#include <cstddef>
#include <string>
#include <unistd.h>

enum class read_status { complete, limit_exceeded, error };

// Legfeljebb max bájtot olvas az fd-ből az out-ba. complete: EOF-ig minden
// adat belefért; limit_exceeded: max bájt után még volt adat (az out csak az
// első max bájt, és a forrásból egy további bájt elfogyott); error: olvasási
// hiba, az out a hiba előtti részadat, a kód err-ben.
read_status read_up_to(int fd, std::string& out, std::size_t max, int& err) {
    err = 0;
    out.resize_and_overwrite(max, [&](char* p, std::size_t n) -> std::size_t {
        std::size_t total = 0;
        while (total < n) {
            ssize_t r = ::read(fd, p + total, n - total);
            if (r < 0) {
                if (errno == EINTR) continue;
                err = errno;
                return total;
            }
            if (r == 0) break;
            total += static_cast<std::size_t>(r);
        }
        return total;
    });
    if (err != 0) return read_status::error;
    if (out.size() < max) return read_status::complete;   // EOF a limit előtt
    for (;;) {                                            // pontosan max: van még adat?
        char extra;
        ssize_t r = ::read(fd, &extra, 1);
        if (r < 0 && errno == EINTR) continue;
        if (r < 0) { err = errno; return read_status::error; }
        return r == 0 ? read_status::complete : read_status::limit_exceeded;
    }
}

A függvény neve szándékosan read_up_to, nem read_all: a siker csak a legfeljebb max bájtos prefixre szól, és a limit túllépése külön állapot (limit_exceeded), nem észrevétlen teljes siker. A túllépés észleléséhez a függvény pontosan max bájt után még egy bájtot megpróbál olvasni; ez a bájt a forrásból elfogy, ami a hívó szerződésének része. A hibaágban a string a hiba előtti részadat, a kód err-ben. Ha a lambda visszatérési értéke nagyobb n-nél, az nem definiált viselkedés.

Buildjegyzőkönyv (lab-gcc profil). g++ -std=c++23 -Wall -Wextra -Wpedantic -fsanitize=address,undefined -DREAD_UP_TO_TEST mellett egy pipe-os tesztprogrammal: max = 8 mellett 7 bájt → complete (7), 8 bájt → complete (8), 9 bájt → limit_exceeded (8); max = 0 mellett üres bemenet → complete, egy bájt → limit_exceeded; érvénytelen fd → error, EBADF. Kimenet: read_up_to: OK.

A std::string::contains és std::string_view::contains C++23-as bővítés: bool contains(basic_string_view sv) const és bool contains(char c) const. Példa:

#include <cassert>
#include <string>

int main() {
    std::string s = "GET / HTTP/1.1";
    assert(s.contains("HTTP/1.1"));
    assert(s.contains('/'));
}

A C++20-as fallback: find(...) != std::string::npos.

  1. Saját bájtcsere előjel nélküli típusra (shift és maszk).
  2. static_cast<std::underlying_type_t<E>>(e).
  3. std::is_enum_v<T> && !std::is_convertible_v<T, int>.
  4. std::memcpy egy lokális T objektumba — ez másol, nem ugyanaz a szemantika.
  5. Manuális T* raw = nullptr; c_api(&raw); if (raw) p.reset(raw);.
  6. allocate(n), a kapacitás count = n.
  7. resize(n), írás, majd resize(r).
  8. find(...) != npos.

Ellenőrzés (-std=c++23 -dM -E, <version>): a táblázat makrói közül

  • a GCC 13.3 libstdc++-ából hiányzik a start_lifetime_as, az out_ptr és az allocate_at_least makrója;
  • a Clang 22 libc++-ából csak a start_lifetime_as makrója hiányzik.

A labor első lépése lehet egy compile probe, amely hiányzó képesség esetén szándékosan fordítási hibát ad:

// interop_probe.cpp — C++23: képességleltár (<version>) + valódi minimálhívások
#include <version>      // a feature-test makrók forrása, minden más előtt
#include <bit>          // byteswap
#include <cstdint>
#include <memory>       // start_lifetime_as, out_ptr, allocator::allocate_at_least
#include <string>       // resize_and_overwrite, contains
#include <type_traits>  // is_scoped_enum
#include <utility>      // to_underlying

#if !defined(__cpp_lib_byteswap) || !defined(__cpp_lib_to_underlying) || \
    !defined(__cpp_lib_is_scoped_enum) || !defined(__cpp_lib_start_lifetime_as) || \
    !defined(__cpp_lib_out_ptr) || !defined(__cpp_lib_allocate_at_least) || \
    !defined(__cpp_lib_string_resize_and_overwrite) || \
    !defined(__cpp_lib_string_contains)
#error "A laborprofil C++23 interop-kepessegei hianyosak"
#endif

enum class E : std::uint8_t { a = 1 };
static_assert(std::byteswap(std::uint16_t{0x0102}) == 0x0201);
static_assert(std::to_underlying(E::a) == 1);
static_assert(std::is_scoped_enum_v<E>);

int main() {
    alignas(int) unsigned char buf[sizeof(int)] = {};
    int* p = std::start_lifetime_as<int>(buf);
    std::unique_ptr<int> up;
    [](int** out) { *out = nullptr; }(std::out_ptr(up));
    std::allocator<int> al;
    auto r = al.allocate_at_least(4);
    al.deallocate(r.ptr, r.count);
    std::string s;
    s.resize_and_overwrite(3, [](char* q, std::size_t) { q[0] = 'a'; return std::size_t{1}; });
    return (s.contains('a') && p != nullptr) ? 0 : 1;
}

A képességleltár a <version>-ből jön, minden makrót a saját fejléce mellett nézünk, és a makrók mellett minden képességet egy valódi minimálhívással is lefordítunk; egyetlen képességhez külön probe is írható, amely csak a saját fejléceit húzza be:

// probe_to_underlying.cpp — egyetlen képesség, csak a saját fejléceivel
#include <version>
#include <utility>
#if !defined(__cpp_lib_to_underlying) || __cpp_lib_to_underlying < 202102L
#error "std::to_underlying nem erheto el"
#endif
enum class Color { red, green = 2 };
static_assert(std::to_underlying(Color::green) == 2);
int main() {}

Buildjegyzőkönyv. A teljes probe a GCC 13.3 és a Clang 22 / libc++ alatt is a saját #error üzenetével állt meg (mindkettőből hiányzik a start_lifetime_as); a probe_to_underlying.cpp mindkettővel lefordult. A start_lifetime_as nélküli változat minimálhívásai a Clang 22 / libc++ alatt lefordultak és 0 kóddal futottak.

43.4.5 Tipikus hibák

  • A std::byteswap önmagában nem endian-konverzió; a std::endian::native ellenőrzése nélkül használva rossz protokollsorrendet ad.
  • A std::start_lifetime_as nem implicit-lifetime típusra (például std::string-re) fordítási hiba (Mandates), nem futásidejű UB.
  • A std::start_lifetime_as rosszul igazított vagy túl kicsi tárolóra: nem definiált viselkedés; az alignas és a méret előzetes rögzítése a védelem.
  • A std::out_ptr a konstruktorában resetel, ezért hibaágban elveszítheti a régi erőforrást, ha a C API nem ír a pointerbe; megőrzéshez tranzakciós minta (nyers ideiglenes pointer, siker esetén reset) kell. Az inout_ptr nem általános javítás: csak olyan API-hoz való, amely a régi erőforrást maga kezeli (replace); out-only API-hoz szivárgást okozhat.
  • A resize_and_overwrite visszatérési értéke nem lehet nagyobb a kért n-nél; ha mégis, nem definiált viselkedés.
  • Az allocate_at_least eredményét olyan mérettel deallokálni, amely kisebb a kértnél vagy nagyobb a visszaadott count-nál. A req <= n <= count tartományon belül bármely méret megengedett; a count megőrzése a legegyszerűbb, egyértelmű szabály.
  • A string::contains C++23-as; C++20-ban a find és a npos összehasonlítása szükséges.

43.4.6 Feladatok

  1. Írj egy to_network_order(std::uint32_t) függvényt, amely a hoszt byte orderből hálózati byte orderbe konvertál. Használd a std::endian és std::byteswap eszközöket. Add meg a buildparancsot, és magyarázd el, miért nem elég a std::byteswap önmagában. Ellenőrizd az eredményt little-endian és big-endian esetre.

  2. Adott a következő C API:

extern "C" int get_buffer(unsigned char** data, std::size_t* size);

amely egy malloc-olt puffert ad vissza. Készíts egy std::unique_ptr<unsigned char, decltype(&std::free)>-t, és használd std::out_ptr-t. Ezután értelmezd a puffer első sizeof(Header) bájtját std::start_lifetime_as<Header>-rel. Sorolj fel minden szükséges előfeltételt, és mondd meg, meddig érvényes a kapott Header*.

  1. Írj tesztprogramot a fenti read_up_to függvényhez: pipe-on át adj neki max - 1, max és max + 1 hosszú bemenetet, valamint max == 0 mellett üres és nem üres bemenetet, és ellenőrizd az állapotot és a string méretét. Magyarázd el, miért kell a pontosan max hosszú esetet a limit túllépésétől megkülönböztetni.

43.4.7 Megoldások

43.4.7.1 1. feladat megoldása

#include <bit>
#include <cstdint>
#include <cstdio>

constexpr std::uint32_t to_network_order(std::uint32_t v) noexcept {
    if constexpr (std::endian::native == std::endian::little) {
        return std::byteswap(v);
    } else {
        return v;
    }
}

int main() {
    std::printf("%08x\n", to_network_order(0x01020304u));
}

A std::byteswap csak bájtokat cserél; a hálózati sorrendet a protokoll rögzíti, ezért kell a std::endian::native feltétel. Little-endian gépen a várt kimenet 04030201, big-endian gépen 01020304. Ellenőrzési feltétel: a kimenet a gépi endiannek megfelelően a hálózati sorrendet tükrözze, és a program -Wall -Wextra -pedantic mellett figyelmeztetés nélkül forduljon.

43.4.7.2 2. feladat megoldása

#include <cstdint>
#include <cstdio>
#include <cstdlib>
#include <cstring>
#include <memory>

struct Header {
    std::uint32_t magic;
    std::uint32_t length;
};

extern "C" int get_buffer(unsigned char** data, std::size_t* size) {
    auto* p = static_cast<unsigned char*>(std::malloc(64));
    if (!p) return -1;
    std::memset(p, 0, 64);
    const Header init{0x47414944u, 16u};   // natív reprezentáció: minden
    std::memcpy(p, &init, sizeof init);    // később olvasott bit definiált
    *data = p;
    *size = 64;
    return 0;
}

int main() {
    std::unique_ptr<unsigned char, decltype(&std::free)> buf(nullptr, &std::free);
    std::size_t n = 0;
    if (get_buffer(std::out_ptr(buf), &n) != 0) return 1;
    if (n < sizeof(Header)) return 1;
    Header* h = std::start_lifetime_as<Header>(buf.get());
    std::printf("%u %u\n", h->magic, h->length);
}

Előfeltételek: a get_buffer sikeres hívás esetén ír a data pointerbe, és a puffer első sizeof(Header) bájtját definiált értékkel tölti fel (a start_lifetime_as nem inicializál); a puffer mérete legalább sizeof(Header); a malloc igazítása legalább alignof(Header); a Header implicit-lifetime típus; a pufferben nincs élő Header objektum. A Header* a buf élettartamáig érvényes; a buf felszabadítása után dangling. Ellenőrzési feltétel: a program csak akkor hívja meg a start_lifetime_as-t, ha a méret megfelelő, és a Header*-ot nem használja a buf felszabadítása után.

43.4.7.3 3. feladat megoldása

// read_up_to.cpp (folytatás) — tesztmain, csak -DREAD_UP_TO_TEST mellett
#ifdef READ_UP_TO_TEST
#include <cassert>
#include <cstdio>
static read_status run(const std::string& data, std::size_t max, std::string& out) {
    int fds[2];
    if (::pipe(fds) != 0) return read_status::error;
    (void)!::write(fds[1], data.data(), data.size());
    ::close(fds[1]);
    int err = 0;
    read_status s = read_up_to(fds[0], out, max, err);
    ::close(fds[0]);
    return s;
}
int main() {
    const std::size_t max = 8;
    std::string out;
    assert(run(std::string(max - 1, 'a'), max, out) == read_status::complete && out.size() == max - 1);
    assert(run(std::string(max, 'a'), max, out) == read_status::complete && out.size() == max);
    assert(run(std::string(max + 1, 'a'), max, out) == read_status::limit_exceeded && out.size() == max);
    assert(run("", 0, out) == read_status::complete && out.empty());
    assert(run("x", 0, out) == read_status::limit_exceeded && out.empty());
    int err = 0;
    assert(read_up_to(-1, out, max, err) == read_status::error && err == EBADF);
    std::puts("read_up_to: OK");
}
#endif

A tesztet a fenti read_up_to.cpp végéhez fűzzük; az #ifdef READ_UP_TO_TEST blokk miatt a main csak tesztbuildben készül el, és -DREAD_UP_TO_TEST-tel fordítjuk. A pontosan max hosszú bemenet és a max + 1 hosszú bemenet első max bájtja azonos; a különbséget csak a további olvasási kísérlet (EOF vagy újabb bájt) dönti el. E nélkül a csonkolt olvasás teljes sikerként jelenne meg. Ellenőrzési feltétel: a fenti assert-ek teljesülnek, és a program read_up_to: OK-t ír ki.

43.4.8 Összefoglaló

A C++23 alacsony szintű eszközei akkor biztonságosak, ha a mögöttes objektum-élettartam- és C API-szerződést pontosan betartjuk. A std::byteswap csak bájtcserét végez, az endian-döntést a std::endian és a protokoll adja. A std::start_lifetime_as nyers tárolóban indít implicit-lifetime objektumot, feltételei megsértése nem definiált viselkedés. A std::out_ptr és std::inout_ptr az okos pointer és a C API közötti tulajdonjog-átadást teszi kifejezővé, de a hibaág szerződését ellenőrizni kell. Az allocate_at_least, a resize_and_overwrite és a contains a teljesítmény és a kényelem irányába bővítik a standard libraryt; használatukhoz feature-test makró és a tényleges implementáció ellenőrzése szükséges.
