11.1 Path, inode, link és filesystem namespace

11.1.1 Motiváció

Szenior C++ fejlesztőként ismerős a meglepetés: egy hosszú folyamat a rename() vagy unlink() után is a régi fájltartalmat látja, a logrotate letörli a naplót, de a szolgáltatás tovább ír, a df pedig nem mutat felszabadulást. Ennek oka, hogy Linuxon a fájl nem azonos a pathnévvel. A path egy névtérbeli hivatkozás, amely egy inode-ra mutat. A nyitott fájl viszont nem a nevet, hanem az inode-ot tartja életben. Ebben az alfejezetben a VFS négy rétegét modellezzük: path, directory entry, inode és open file description, valamint a mount namespace hatását. Cél, hogy unlink, open, hard link és szimbolikus link állapotát fejből le tudd vezetni.

11.1.2 Definíció és négy rétegmodell

A fájlrendszer-névtér négy, eltérő élettartamú objektumot választ szét.

  • Pathnév és directory entry (dentry): A /srv/app/config.json névsor könyvtárbejegyzéseken keresztül oldódik fel. Egy directory entry nem tárol fájladatot, csak egy nevet és egy inode-számot. A kernel ezt dentry cache-ben tartja; a dentry nem maga a fájl.
  • Inode: A fájlrendszeren belüli metaadat-objektum. Tartalmazza a típust, méretet, blokkmutatókat, időbélyegeket, tulajdonost, jogosultságokat és a link count (st_nlink) mezőt. Az inode azonosítója per-filesystem érvényes: a (st_dev, st_ino) páros ad globálisabb eszközszintű azonosítást.
  • Open file description (OFD): Az open() syscall egy új OFD-t hoz létre, amely az inode-ra mutat. Ide tartozik a file offset és a fcntl státuszflag. A processben lévő file descriptor ehhez az OFD-hez kötődik. A dup() és fork() megosztja az OFD-t; egy második open() viszont új, független OFD-t ad.
  • Mount namespace és filesystem határ: A path resolution nem közvetlenül inode-táblán dolgozik, hanem a process mount tábláján keresztül. Egy mount pont alatt a névfeloldás átlép ugyanabba a VFS névtérbe, de másik filesystem superblock-jára. A név folyamatos lehet, az inode-tér viszont diszjunkt. Hard link csak egy filesystemen belül értelmes.

A path resolution a path komponenseket balról jobbra dolgozza fel. A kiindulás abszolút névnél a process root dentry-je, relatív névnél a process cwd dentry-je. A .. komponenst a VFS a szülő dentry szerint oldja fel. Szimbolikus linknél a feloldás rekurzívan folytatódik; a relatív link célját a linket tartalmazó könyvtárhoz képest értelmezi a kernel.

A szimbolikus link maga is inode, tartalma egy path sztring. A hard link ezzel szemben ugyanahhoz az inode-hoz tartozó második directory entry. A link() hívás növeli a link countot, az unlink() a directory entryt törli és csökkenti. A tartalom akkor szabadul fel a tárolóban, amikor a link count már nulla, és nem maradt nyitott OFD sem. A nyitott leíró tehát önálló élettartamot ad az inode-nak: unlink után a path eltűnik, de a process fd-je továbbra is olvas/ír.

11.1.3 stat, lstat, du, df eltérései

Eszköz Mit vizsgál? Fontos eltérés
stat path A path feloldása után a target inode metaadatai Szimbolikus linket követ
lstat path Maga a link inode Nem követi a linket; readlink a tartalom
du A path alatt található inode-ok tényleges blokkhasználata Hard linkeket általában egyszer számol
df A filesystem szintű kapacitás- és szabadblokk-statisztika Nem az adott path méretét méri; törölt, de nyitott fájlokat is foglaltnak lát

A du és a df közti eltérés fontos diagnosztikai jel: ha a du kicsi, de a df majdnem tele van, akkor általában törölt, de nyitott file description miatt nem felszabadult inode-blokkokra kell gyanakodni.

11.1.4 Kidolgozott példa: hard link, symlink és unlink utáni élet

  • Target: lab-vm1, UID labuser, munka a /tmp/lab-d051 könyvtárban.
  • Előfeltétel: írható /tmp, GNU coreutils, bash.
  • Rollback: csak a saját rm -rf /tmp/lab-d051 hajtható végre.
  • Ellenőrzés: stat/lstat kimenet, /proc/$$/fd tartalma.
# target: lab-vm1, uid: labuser
mkdir -p /tmp/lab-d051 && cd /tmp/lab-d051

echo "hello d051" > payload.txt
ln payload.txt hardlink.txt
ln -s payload.txt symlink.txt

stat -c '%d %i %h %s %n' payload.txt hardlink.txt symlink.txt
lstat -c '%d %i %h %s %n' symlink.txt

Várható, illusztratív kimenet — a konkrét device/inode szám a labrendszeren eltérhet:

259 1122 2 11 payload.txt
259 1122 2 11 hardlink.txt
259 1124 1 11 symlink.txt
259 1124 1 11 symlink.txt

Mindkét payload.txt és hardlink.txt ugyanazt az inode-ot (1122) használja, és a link count 2. A szimbolikus link külön inode, link count 1, mérete a cél sztring hossza.

Most töröljük a nevet, de előbb megnyitjuk a shellben:

exec 3< payload.txt
rm payload.txt hardlink.txt

# Az FD még mindig az anonim inode-ra mutat
ls -l /proc/$$/fd/3
cat <&3
stat -c '%h %n' payload.txt

Várható kimenet:

lrwx------ 1 labuser labuser 64 ... /proc/.../fd/3 -> '/tmp/lab-d051/payload.txt (deleted)'
hello d051
stat: cannot statx 'payload.txt': No such file or directory

A path megszűnt, a stat hibázik, de az FD-ből az adat még olvasható. A kernel az inode-ot a nyitott OFD miatt életben tartja; a lemezblokkok addig nem szabadulnak fel.

A jelenséget C++-ban is levezetjük:

#include <fcntl.h>
#include <unistd.h>
#include <sys/stat.h>
#include <cstdio>
#include <cerrno>

int main() {
    const char* path = "/tmp/lab-d051/anonymous.cpp-demo";
    int fd = open(path, O_RDWR | O_CREAT | O_TRUNC, 0600);
    if (fd < 0) { perror("open"); return 1; }
    if (write(fd, "alive\n", 6) < 0) { perror("write"); return 2; }
    if (unlink(path) != 0) { perror("unlink"); return 3; }

    struct stat st{};
    if (fstat(fd, &st) != 0) { perror("fstat"); return 4; }
    std::printf("unlink utan: st_nlink=%ld, megnyitva fd=%d\n", st.st_nlink, fd);

    char buf[64]{};
    ssize_t n = pread(fd, buf, sizeof(buf) - 1, 0);
    if (n > 0) std::printf("olvashato: %s", buf);

    // Itt a folyamat él; a kernel megtartja az inode-ot és a blokkokat.
    pause();
    close(fd);
}

Fordítás és futtatás:

g++ -std=c++17 -Wall -Wextra anonymous.cpp -o anonymous-demo
./anonymous-demo

Várható illusztratív kimenet:

unlink utan: st_nlink=0, megnyitva fd=3
olvashato: alive

A st_nlink=0 jelzi, hogy nincs név, de a fd még érvényes. Amint a process close()-olja az FD-t vagy kilép, az inode és a blokkok felszabadulnak.

11.1.5 Tipikus hibák és ellenpróbák

1. rm a szimbolikus linkre: nem a targetet törli. Ha a rm symlink.txt parancsot adjuk, a link inode törlődik, a payload.txt megmarad. Ezt a readlink és a lstat segítségével ellenőrizhetjük.

2. Hard link directoryra nem hozható létre. A ln /tmp/lab-d051 /tmp/dirlink általában Permission denied hibát ad, mert a könyvtárak hard linkelése megtörné a fa-egységet. Könyvtárhoz szimbolikus link vagy bind mount használandó.

3. Cross-device link hiba. Ha a cél egy másik mounted filesystemen van, a ln payload.txt /mnt/other/payload.txt Invalid cross-device link hibát ad. A path névtér folytonos, de az inode-tér nem; hard link nem léphet át superblock határt. Ilyenkor a megoldás szimbolikus link vagy másolás.

4. stat versus lstat törött symlinknél. Ha a cél nem létezik, a stat követi a linket és No such file or directory, míg az lstat sikeresen leírja a link inode-ot. A diagnózis ezért mindig lstat-tal kezdődjön, ha a path szimbolikus link lehet.

5. du és df félreértelmezése. Ha egy process unlink után is nyitva tartja a fájlt, a du /tmp nem látja, de a df telítettnek mutatja. A tettes pedig nem a path, hanem a nyitott FD. Ezért a diagnosztika nem a fájlrendszeri névtérben, hanem a process FD-táblájában folytatódik.

6. Relatív szimbolikus link áthelyezése. A relatív link a linket tartalmazó könyvtárhoz képest oldódik fel. Ha a linket új könyvtárba mozgatjuk, a cél megváltozik, mert a link célpathja továbbra is relatív a link szülőjéhez. Ezt readlink és stat együttes használatával követhetjük.

11.1.6 Feladatok

11.1.6.1 1. Magyarázó feladat: link számláló levezetése

Egy labhoston a következő műveleteket hajtjuk végre:

mkdir -p /tmp/lab-d051-f1 && cd /tmp/lab-d051-f1
echo x > a.txt
ln a.txt b.txt
ln -s a.txt s.txt
rm a.txt

Add meg, mi lesz a stat -c '%h %n' b.txt s.txt parancs várható kimenete, és mi történik a cat s.txt esetén. Indokold az inode- és link count modell alapján.

11.1.6.2 2. Adminisztrációs feladat: hard link vs. szimbolikus link cserénél

Hozz létre a labhoston /tmp/lab-d051-symlink könyvtárat. Készíts config.json fájlt, config.hardlink hard linket, és config.current szimbolikus linket erre. Írd ki a stat/lstat kimenetet, majd cseréld a config.json-t atomikusan egy új config.new tartalommal (mv config.new config.json). Várd el, hogy a config.current az új tartalomra mutasson, a config.hardlink viszont a régi inode-ot és tartalmat tartsa.

11.1.6.3 3. Diagnosztikai feladat: nyitott törölt fájl megtalálása

Egy szolgáltatás naplófájlját rm-mel törölték, de a process tovább ír. A df -h /var/log gyakorlatilag tele van, a du -sh /var/log kicsi. Keress nyitott törölt fájlokat lsof +L1 és /proc/<pid>/fd segítségével. A feladat hostja lab-vm1, UID labuser; ha lsof nem elérhető, telepítsd a lab-repositoryból. Ne rootolt rendszerben dolgozz; a cél csak a saját labprocesszed azonosítása. Dokumentáld, hogy a térnyerés csak a process leállása vagy FD lezárása után következik be.

11.1.7 Megoldások

11.1.7.1 1. Megoldás

Várható kimenet:

1 b.txt
1 s.txt
  • a.txt létrehozásakor link count = 1.
  • ln a.txt b.txt után ugyanaz az inode két névvel rendelkezik: link count = 2.
  • ln -s a.txt s.txt nem hoz hard linket, hanem külön szimbolikus link inode-ot; a s.txt link count = 1.
  • rm a.txt az eredeti nevet törli, a link count 2-ről 1-re csökken. Az a.txt path eltűnik, de b.txt továbbra is hivatkozik az inode-ra.
  • A s.txt törött szimbolikus link lesz: stat s.txt hibázik, de lstat s.txt sikeres. A cat s.txt No such file or directory hibát ad, mert a cél path a.txt már nem létezik.

11.1.7.2 2. Megoldás

# target: lab-vm1, uid: labuser
mkdir -p /tmp/lab-d051-symlink && cd /tmp/lab-d051-symlink
echo "old" > config.json
ln config.json config.hardlink
ln -s config.json config.current

stat -c '%i %h %s %n' config.json config.hardlink config.current
lstat -c '%i %h %s %n' config.current

echo "new" > config.new
mv config.new config.json

stat -c '%i %h %s %n' config.json config.hardlink config.current
cat config.current
cat config.hardlink

Postcondition: config.json új inode-ot kap, config.current a new tartalmat mutatja, mert a szimbolikus link path alapján oldódik fel; config.hardlink a régi inode-hoz köt, így továbbra is old tartalmat mutat.

11.1.7.3 3. Megoldás

# target: lab-vm1, uid: labuser
sudo lsof -nP +L1 | grep deleted

# Ha lsof nem elérhető:
ls -l /proc/[0-9]*/fd 2>/dev/null | grep deleted

Egy konkrét PID esetén:

ls -l /proc/8123/fd | grep deleted
# Például: 3 -> '/tmp/lab-d051/log.txt (deleted)'
cat /proc/8123/fd/3

A posztkondíció: azonosítjuk a PIDs folyamatot és az FD-t; a fájl nem szerepel a névtérben, de a tartalma az FD-n keresztül olvasható. A fájlrendszer kapacitás csak akkor szabadul fel, ha a folyamat bezárja az FD-t, kilép, vagy ha a szolgáltatást újraindítják. Ha konzisztens állapot kell, a recovery nem egyszerű cp, mert az író folyamat közben módosíthat.

11.1.8 Rövid összefoglaló

A pathnév nem azonos a fájllal; a könyvtárbejegyzés egy inode-ra mutat. A hard link ugyanahhoz az inode-hoz tartozó második név, és a link count azt mutatja, hány név él. Az unlink csak a nevet távolítja el; a data blokkok akkor szabadulnak fel, amikor a link count nulla és nincs nyitott file description. A szimbolikus link külön inode, amely egy path sztringet tárol, és a feloldás a link szülőkönyvtárához képest történik. A path feloldás a process rootjától vagy cwd-jétől indul, és mount pointon átlépve másik filesystemre válthat; hard link nem léphet át ezen a határon.

Továbbhasznált definíciók:

  • Inode: per-filesystem metaadat-objektum, amely a fájladatot és a link countot tárolja.
  • Hard link: egy újabb directory entry, amely ugyanahhoz az inode-hoz tartozik.
  • Open file description: az open() által létrehozott, az inode-ra mutató, offsetet és flaget tároló objektum.
