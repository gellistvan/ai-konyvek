46.2 Remote state, locking és recovery

46.2.1 Motiváció

Amikor egy csapat egyetlen fejlesztő helyett több emberrel üzemelteti ugyanazt az infrastruktúrát, a lokális terraform.tfstate fájl azonnal szűk keresztmetszetté válik. Két párhuzamos apply felülírhatja egymás állapotát, a titkos adatokat tartalmazó fájl a laptopon utazik, a rosszul mentett verzióból pedig nem tudunk visszaállni. A remote state ezt a problémát úgy oldja meg, hogy a state egy megosztott, védett, verziózott objektumtárolóba kerül, ahol a hozzáférés, a konkurencia és a helyreállítás szerződésbe foglalható. Ez az alfejezet azt tanítja meg, hogyan adjunk a state-hez ownership-, access-, backup- és concurrency-szerződést, és mi a különbség a state helyreállítása és a tényleges felhőerőforrás helyreállítása között.

46.2.2 Definíció és működés

46.2.2.1 Remote state és backend

A remote state az OpenTofu/Terraform állapotfájljának olyan tárolása, amely nem a lokális fájlrendszeren, hanem egy megosztott, hálózati szolgáltatásban él. A backend az a konfigurációs blokk, amely meghatározza, hová kerül a state, hogyan történik a lock, és milyen identitással férünk hozzá. A remote backend tipikusan objektumtárolóra (például AWS S3, Google Cloud Storage, Azure Blob) és egy lock-táblára (például AWS DynamoDB) épül.

A remote state egy állapotfájl, amely nemcsak az erőforrások azonosítóit és függőségeit tartalmazza, hanem olyan érzékeny attribútumokat is, mint:

  • adatbázis jelszavak,
  • TLS privát kulcsok,
  • IAM access key szövege,
  • belső végpontok és VPC CIDR-ek.

Ezért a remote state-et nem szabad verziókezelőbe (Git) commitolni, és a tárolón titkosítást, verziózást és szigorú hozzáférést kell biztosítani.

46.2.2.2 Remote backend és identity

A remote backendhez a klienst (OpenTofu CLI, CI runner, lokális fejlesztő) egy adott felhő-identitás nevében fér hozzá. Ez lehet:

  • lokális fejlesztő esetén egy IAM user vagy egy role-t felvevő sso login,
  • CI rendszernél egy ephemerális role,
  • szolgáltatás esetén workload identity.

A backendnek adott jogosultságot a legkisebb jogkör elve szerint kell meghatározni: a state olvasásához, írásához, lockoláshoz és feloldáshoz külön policy elemek tartoznak. Például AWS S3 esetén a s3:GetObject, s3:PutObject, s3:DeleteObject engedélyek a state fájlra, a DynamoDB-nél pedig dynamodb:GetItem, dynamodb:PutItem, dynamodb:DeleteItem a lock-táblára. Ügyelni kell arra, hogy a titkosítás (például SSE-KMS) további IAM jogot igényelhet a KMS kulcsra is.

46.2.2.3 State lock és lease

A state lock olyan kölcsönös kizárási mechanizmus, amely biztosítja, hogy egyszerre csak egy folyamat módosíthassa a state-et. Mivel a state az infrastruktúra „source of truth”-ja, két párhuzamos apply esetén az egyik a másik által már megváltoztatott valóságot próbálná frissíteni, ami elveszett update-hez vagy inkonzisztens tervekhez vezetne.

A lease a lock időhöz kötött bérlete. A háttérben a lock-tábla egy rekordot tartalmaz egy egyedi kulccsal (LockID) és egy lejárati időbélyeggel. Ha a folyamat szabályosan befejezi a műveletet, törli a rekordot; ha a folyamat megszakad, a lease lejár, és egy későbbi kísérlet átveheti a lockot. A gyakorlatban azonban a lejárat néhány perc, ezért azonnali újrapróbálkozás helyett a hibajelenség diagnosztizálása szükséges.

46.2.2.4 Interrupted apply

Ha az apply futása közben a hálózat megszakad, a CI folyamat timeoutot kap, vagy a lokális gép lefagy, a lock-rekord a táblában maradhat. A következő plan vagy apply ekkor hasonló hibát ad:

Error acquiring the state lock

Ilyenkor meg kell győződni arról, hogy valóban nincs másik aktív folyamat. Ha a lock gazdája már nem fut, akkor a force-unlock parancs törli a rekordot. A force-unlock veszélyes művelet, mert ha tévedünk, és mégis fut egy másik apply, akkor két folyamat fogja módosítani a state-et és a felhőerőforrásokat. Ezért a lease ID-t a hibaüzenetből kell kivenni, és a folyamat kilétét ellenőrizni kell.

46.2.2.5 Import, moved és state műveletek

A state nemcsak a plan/apply terméke, hanem explicit módon is manipulálható. A fontosabb műveletek:

  • Import: meglévő, a konfigurációban még nem szereplő erőforrás bevitele a state-be (tofu import). Ilyenkor a valós erőforrás azonosítóját a provider importálja, a state-be bekerül, és a plan ezután már követni tudja a driftet.
  • Moved: amikor egy erőforrás címét megváltoztatjuk a konfigurációban, a moved blokk jelzi a state-nek, hogy a régi címet az újra kell képezni, elkerülve a törlés/újraépítés folyamatot.
  • State operation: tofu state list, tofu state mv, tofu state rm, tofu state pull, tofu state push – ezek a state fájl tartalmának ellenőrzésére és alacsony szintű javítására szolgálnak. A mv egy erőforrás áthelyezése egy másik címre, a rm eltávolítása a state-ből anélkül, hogy a valós erőforrás megsemmisülne.

Ezek a műveletek mind potenciálisan veszélyesek, mert a state módosítása anélkül, hogy a valós erőforrást is módosítanánk, driftet okozhat. Ezért minden ilyen parancs előtt backupot kell készíteni.

46.2.2.6 Backup, encryption és restore

A remote state backend általában támogatja a verziózást. Ennek segítségével a state minden alkalommal mentésre kerül, amikor megváltozik. A verziózás nem helyettesíti a valós backupot, de biztosítja a rövid távú visszamenő visszaállítást. Emellett tofu state pull parancsot rendszeresen futtathatunk, és a kimenetet titkosított, hosszú távú tárolóba menthetjük.

A titkosítás két szinten történik:

  • Encryption at rest: a bucket szintjén bekapcsolt SSE-S3 vagy SSE-KMS biztosítja, hogy a tárolt state fájl ne legyen olvasható a tárhelyhez hozzáférő admin számára sem.
  • Encryption in transit: minden kérés TLS-en keresztül történik.

A restore akkor hiteles, ha utána tofu plan nem mutat semmilyen különbséget a jelenlegi konfiguráció és a visszaállított state között. Ha a state elveszett, a visszaállítás csupán a state-et hozza vissza, de a valós erőforrásokhoz képest drift lehet; ilyenkor a tofu import szükséges lehet.

46.2.2.7 State workspace, account és environment isolation

A state-t érdemes erős határokkal elkülöníteni a különböző környezetek között. Két elterjedt modell:

  • Workspace: ugyanazon backend konfigurációban a workspace megváltoztatja a state kulcsát (például workspace dev -> dev/terraform.tfstate). Ez hasznos ideiglenes ágaknál, de nem ad elég erős izolációt, mert ugyanaz a bucket és lock-tábla.
  • Separate backend config: minden környezetnek külön backend-kulcs és gyakran külön bucket, külön lock-tábla, sőt külön felhő-account. Ez a production-recommended megoldás, mert az account határ hiba esetén is védi a production state-et.

A workspace-ek és a state fájlok elkülönítése nemcsak a szervezést szolgálja, hanem a failure domain csökkentését is: ha egy fejlesztő véletlenül törli a staging state-et, az ne érintse a production-t.

46.2.3 Kidolgozott példa: S3 remote state DynamoDB lockkal

A példa egy AWS sandbox accountot használ. Hipotetikus, nem futtatott parancsok; az azonosítók és a régió tetszőlegesek, de a labon kívül nem léteznek. Cél: egy kis S3 bucket létrehozása OpenTofuval, remote state-tel és lockkal.

Előfeltételek:

  • AWS sandbox account, lab-tfstate-123456789012 nevű S3 bucket és lab-tfstate-lock nevű DynamoDB tábla a us-east-1 régióban.
  • A lokális gép (labVM) rendelkezik friss OpenTofu CLI-vel és IAM credentialokkal.

Hozzuk létre a main.tf fájlt a backend blokkal és egy egyszerű erőforrással:

terraform {
  required_version = ">= 1.6"
  backend "s3" {
    bucket         = "lab-tfstate-123456789012"
    key            = "environments/dev/terraform.tfstate"
    region         = "us-east-1"
    encrypt        = true
    dynamodb_table = "lab-tfstate-lock"
  }
}

resource "aws_s3_bucket" "example" {
  bucket = "lab-example-bucket-123456789012"
}

Futtassuk az inicializálást és az alkalmazást:

# Target: labVM (UID=1000), us-east-1 sandbox account
tofu init
tofu plan
tofu apply

Várt kimenet init után: a backend inicializálódik, a state elérési útja a S3 bucketben van. A plan során a CLI lockot szerez a DynamoDB táblán, majd a zárás után elengedi. A tofu apply létrehozza a bucketet, és a state fájl a távoli bucketbe kerül.

A state megtekintése:

tofu state list
# Várt: aws_s3_bucket.example

A lock működésének ellenőrzéséhez indítsunk egy hosszú apply folyamatot egy terminálban, majd egy másik terminálban próbáljunk plan-t futtatni:

# 1. terminál: simulate long apply (a valóságban pl. nagyméretű resource)
tofu apply -auto-approve
# 2. terminál: rögtön ezután
tofu plan

A második parancs várhatóan hibát ad:

Error acquiring the state lock: ConditionalCheckFailedException

A lock ID a hibaüzenetben látható. Ha az első folyamat szabályosan véget ér, a lock eltűnik, és a második parancs lefut. Ha az első folyamat megszakad, a lock fennmarad.

46.2.4 Hibák és ellenpróbák

46.2.4.1 Tünet: Error acquiring the state lock

Hipotézis: egy másik folyamat tartja a lockot, vagy egy korábbi megszakadt futás hagyta hátra.

Adatgyűjtés: Ellenőrizzük a DynamoDB tábla rekordját, vagy futtassunk tofu force-unlock nélkül a hibaüzenetben szereplő lock ID-t. Nézzük meg, fut-e még a másik folyamat (pl. ps aux | grep tofu).

Egy változtatás: Ha nincs aktív folyamat, használjuk a tofu force-unlock <lock_id> parancsot. Ha van aktív folyamat, ne force-unlockoljunk, hanem várjunk a lejáratig vagy állítsuk le azt a folyamatot.

Verifikáció: Újra tofu plan, ami sikeresen lefut.

Ellenpróba: Ha force-unlock után a plan ismét lock hibát ad, akkor vagy újraindult a másik folyamat, vagy a lease még nem járt le; ebben az esetben a DynamoDB tábla rekordját kell megvizsgálni.

46.2.4.2 State vs resource recovery

A tünet: a state fájl sérült vagy törlődött, de az erőforrások a felhőben megvannak. Ha csak a state-t állítjuk vissza egy backupból, a tofu plan diff-et mutat, mert a state nem tartalmazza az aktuális resource konfigurációt. Ekkor nem a state-et kell erőltetni, hanem a konfigurációt kell a state-hez igazítani: tofu import az erőforrásokra, vagy moved blokkot használni. A resource recovery más: ha a felhőerőforrás törlődik, a state-ben továbbra is szerepel, és a tofu apply újból létrehozza, ha a konfiguráció változatlan.

Ezért a kettőt mindig külön kell kezelni:

Művelet State hatás Resource hatás
tofu state rm eltávolítja a state-ből nem törli a felhőerőforrást
tofu destroy eltávolítja a state-ből törli a felhőerőforrást
tofu import hozzáadja a state-hez nem hozza létre, csak felveszi
Backup restore visszaállítja a state-et nem érinti a felhőerőforrásokat

46.2.5 Feladatok

46.2.5.1 F1 – Magyarázó feladat

Magyarázza el, mi a különbség a state lock és a lease között, és miért nem elegendő egy lokális fájlrendszerbeli lock fájl remote csapat esetén. Adjon meg egy olyan hibajelenséget, amikor a lease nem oldja meg automatikusan a problémát, és írja le, mit tesz.

Postcondition: A hallgató szövegesen meg tudja indokolni a lock szükségességét, a lease időkorlátos szerepét, és a force-unlock kockázatát.

46.2.5.2 F2 – Adminisztrációs és konfigurációs feladat

Állítson be OpenTofu remote S3 backendet DynamoDB lockkal egy sandbox accountban. A bucketben kapcsolja be a verziózást és a titkosítást (SSE-S3). Hozzon létre egy egyszerű erőforrást (például egy S3 bucketet), majd ellenőrizze, hogy a state fájl a távoli bucketben van, és hogy a lock tábla rekordja létrejön-e az apply alatt.

Postcondition: A tofu state list mutatja az erőforrást. A S3 bucketben létezik a environments/dev/terraform.tfstate objektum. A DynamoDB tábla üres a apply befejezése után.

46.2.5.3 F3 – Diagnosztikai és recovery feladat

Szimuláljon interrupted apply-t: indítson tofu apply parancsot, majd szakítsa meg (például Ctrl-C). Ellenőrizze, hogy a lock a DynamoDB táblában marad. Használja a tofu force-unlock parancsot a lock felszabadítására. Készítsen előtte tofu state pull segítségével backupot a state-ről. Törölje a state fájlt a bucketből (vagy ürítse ki), majd állítsa vissza a backup segítségével tofu state push parancsot használva. Ellenőrizze tofu plan futásával, hogy nincs diff.

Postcondition: A lock megszűnt, a state visszaállt, és a tofu plan nem mutat változtatást a jelenlegi konfigurációhoz képest.

46.2.6 Megoldások

46.2.6.1 M1 – Magyarázó

A state lock egy kizárólagos bérlet a state módosítására. A lease a bérlet időkorlátos reprezentációja: a háttértárolóban egy lejárati időt tárolnak, így ha a lockot birtokló folyamat meghal, a rendszer egy idő után újra elérhetővé válik. A lokális fájlrendszerbeli lock fájl nem működik remote csapatban, mert minden gép saját fájlrendszerrel rendelkezik, és nem látják egymás lockját. Ezenkívül a lokális lock nem képes a folyamat halála után sem felszabadulni, hacsak nincs lease mechanizmus.

A hibajelenség, amikor a lease nem segít: ha a lock lejárt, de a régi folyamat ténylegesen még fut (például hosszú apply), és az új folyamat force-unlock után ismét lockot szerez, miközben a régi még aktív. Ilyenkor a lease lejárta hamis biztonságot ad, ezért mindig ellenőrizni kell a folyamat állapotát.

46.2.6.2 M2 – Konfigurációs

A backend blokk a fentiekben látható. A bucket verziózását és titkosítását manuálisan kell bekapcsolni az AWS konzolon vagy CLI-vel. A CLI parancsok:

# Target: labVM (UID=1000), us-east-1 sandbox account
aws s3api put-bucket-versioning \
  --bucket lab-tfstate-123456789012 \
  --versioning-configuration Status=Enabled

aws s3api put-bucket-encryption \
  --bucket lab-tfstate-123456789012 \
  --server-side-encryption-configuration '{
    "Rules": [{
      "ApplyServerSideEncryptionByDefault": {
        "SSEAlgorithm": "AES256"
      }
    }]
  }'

(Megjegyzés: a aws parancs itt illusztratív; a pontos API a jelenlegi AWS CLI verziójában ellenőrizendő.)

Ezután tofu init és tofu apply. A tofu apply közben a DynamoDB tábla egy rekordot tartalmaz, a befejezés után üres. Ezt aws dynamodb scan --table-name lab-tfstate-lock parancs ellenőrizheti.

46.2.6.3 M3 – Diagnosztikai és recovery

  1. Készítsünk backupot:
tofu state pull > /tmp/dev-state-backup.tfstate
  1. Indítsunk tofu apply -auto-approve parancsot, majd egy másik terminálban kill -INT a folyamatra. A lock a táblában marad. A lock ID lekérdezése:
aws dynamodb scan --table-name lab-tfstate-lock
  1. Force-unlock:
tofu force-unlock <lock_id> -force
  1. Töröljük a state objektumot:
aws s3 rm s3://lab-tfstate-123456789012/environments/dev/terraform.tfstate
  1. Pusholjuk vissza a backupot:
tofu state push /tmp/dev-state-backup.tfstate
  1. Ellenőrizzük:
tofu plan

Várt: No changes. Your infrastructure matches the configuration.

Postcondition: A tofu plan sikeres, nincs törlés vagy létrehozás, a lock táblában nincs rekord, a state fájl visszaállt.

46.2.7 Rövid összefoglaló

A remote state a Terraform/OpenTofu állapotfájljának megosztott, védett, verziózott tárolása, amely lehetővé teszi a csapatos, reprodukálható infrastruktúrakezelést. A backendhez identitáskötött hozzáférés tartozik, a state érzékeny adatai miatt titkosítás és szigorú IAM szükséges. A state lock és a lease biztosítja, hogy egyszerre csak egy folyamat módosítsa a state-et; a megszakadt folyamatok által hátrahagyott lockot a force-unlock kezeli, de óvatosan. A state módosítható import, moved és state parancsokkal, amelyek nem érintik a valós erőforrásokat; a recovery során a state és a resource helyreállítása két külön folyamat, és a kettőt össze kell hangolni.

Továbbhasznált definíciók: remote state — az IaC állapotfájl megosztott, hálózati tárolóban lévő, verziózott és titkosított példánya; state lock/lease — a state módosítására vonatkozó, időbélyeggel ellátott kizárólagos bérlet, amely megakadályozza a párhuzamos írást; state recovery vs resource recovery — a state fájl backupból való visszaállítása, illetve a valós felhőerőforrás helyreállítása, amelyek egymástól független, de összehangolandó műveletek.
