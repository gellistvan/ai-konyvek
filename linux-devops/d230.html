46.5 Idempotens provision és interrupted change labor

46.5.1 Motiváció

Egy szenior C++ fejlesztő számára a program fordítási idejű determinizmus és a repository-ból való reprodukálhatóság magától értetődő. Az infrastruktúra-provisioning esetén ugyanez a garancia nem adódik ingyen: a felhő vagy virtualizációs API hívása távoli, állapotukat egy külön statefile tartja nyilván, és egy félbeszakadt apply után a tényleges erőforrás, a konfiguráció és a state három különböző állapotot mutathat. Ez a laborkör azt gyakoroltatja, hogyan ellenőrizzük a desired state és az observed state közötti egyezést, hogyan építsük fel a plan → apply → no-op plan ellenőrzési láncot, és hogyan lábadozzunk driftből, importból, moved műveletből, valamint félbeszakadt provisioningből anélkül, hogy a teljes erőforráskészletet megsemmisítenénk vagy a state-et kézzel hamisítanánk.

46.5.2 Definíció és működés

Az idempotens provision azt jelenti, hogy ugyanazon konfigurációból kiindulva ismételt plan/apply futtatás nem hoz létre újabb erőforrást, és a meglévőket nem módosítja indokolatlanul. Ez nem általános távoli exactly-once garancia; a konfiguráció a desired state-et írja le, a statefile a tárolt leképzést a távoli azonosítókhoz, a plan pedig a refreshelt observed state és a desired state közötti különbséget mutatja. Ha a konfiguráció és a state megegyezik a távoli erőforrással, a plan no-op plan: 0 add, 0 change, 0 destroy.

A state lock a working directory state írását védő zár. Hosszabb apply alatt egy második parancs lockhibát kaphat; a -lock-timeout opcióval megadható, hány időtartamig várakozzon a zár feloldására. A provider lock ezzel szemben a .terraform.lock.hcl fájlban rögzíti a provider verzióját és checksumjait, így a init újra lehívható reprodukálható módon. A két zár célja különböző: előbbi a state-adat integritását védi, utóbbi a provider-ellátási láncot rögzíti.

A drift olyan állapot, amikor a távoli erőforrás megváltozott a provsioneren kívül (például egy fájlt kézzel módosítottak). A plan ilyenkor change-et vagy destroy/replace-t mutat. A partial success olyan apply eredmény, amelynél egyes erőforrások létrejöttek, mások hibát kaptak; a statefile és a config szerinti következő apply csak a hiányzó vagy hibás erőforrásokat pótolja. Az import meglévő távoli objektumot visz a statebe anélkül, hogy provisioninget futtatna, a moved blokk pedig akkor frissíti a state erőforrás-címét, ha a HCL-ben átnevezzük az erőforrást. A destroy -target csak a megadott erőforrás-címeket és a tőlük függőket törli, ezért alkalmas a lab resource set explicit szűkítésére.

46.5.3 Kidolgozott példa

A példa izolált labhoston, labvm01, felhasználó lab (UID 1000), working directory /home/lab/iac/d230. A cél egy helyi, fixtúra jellegű erőforrás-készlet a local és null providerrel. A konfiguráció main.tf:

terraform {
  required_version = "~> 1.6"
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.4"
    }
    null = {
      source  = "hashicorp/null"
      version = "~> 3.2"
    }
  }
}

resource "local_file" "lab_file" {
  filename = "/home/lab/iac/d230/lab.txt"
  content  = "d230 idempotens provision\n"
}

resource "null_resource" "lab_wait" {
  provisioner "local-exec" {
    command = "echo lab_wait-ok >> /home/lab/iac/d230/lab.txt"
  }
}

A local_file erőforrás a fájlt a megadott tartalommal hozza létre; a null_resource egy állapot nélküli placeholder, amelynek provisionere egy shell parancsot futtat. A lab célja nem a szolgáltatás, hanem a state-kezelés, ezért elegendő.

Az alábbi lépések mindegyikét a lab felhasználó, a labvm01 hoston, a /home/lab/iac/d230 munkakönyvtárban hajtjuk végre.

  1. Provider inicializálás és lockfile létrehozása:
# target: labvm01, user: lab (UID 1000), workdir: /home/lab/iac/d230
tofu init
tofu providers lock -platform=linux_amd64

Várható kimenet init esetén: OpenTofu has been successfully initialized!, majd a lockfile .terraform.lock.hcl létrejön. Az aktuális provider release-t és a tofu verzióját a labor előtt ellenőrizni kell; az itt szereplő verziószámok illusztratívak.

  1. Terv készítése és apply:
tofu plan -out=lab.plan
tofu apply lab.plan

A plan kimenete: Plan: 2 to add, 0 to change, 0 to destroy. Az apply létrehozza a lab.txt-t, és a null_resource hozzáfűzi a lab_wait-ok sort. A statefile terraform.tfstate létrejön.

  1. No-op ellenőrzés:
tofu plan

Várható: No changes. Your infrastructure matches the configuration. Ezzel bizonyítottuk, hogy a provision idempotens.

  1. Drift generálása és észlelése:
echo "manual-edit" >> /home/lab/iac/d230/lab.txt
tofu plan -detailed-exitcode
echo "exit code: $?"

A plan 2-es exit code-ot ad, és a kimenet jelzi, hogy a local_file.lab_file tartalma eltér; a kézi módosítást a provider javításnak tekinti. A driftből való kiindulás:

tofu apply -auto-approve
tofu plan

Az apply visszaállítja a fájlt a desired state-be, a második plan ismét no-op.

  1. moved fixture: átnevezzük az erőforrást a HCL-ben lab_file-ról lab_data-ra. A plan destroy/create-et mutatna. Helyette moved blokk:
moved {
  from = local_file.lab_file
  to   = local_file.lab_data
}

Ezután:

tofu plan
tofu apply -auto-approve
tofu state list

A state-listában local_file.lab_data jelenik meg, a lab_file nem; a plan nem mutat destroy/create-et.

  1. State backup:
tofu state pull > lab-state-$(date -u +%Y%m%dT%H%M%SZ).json
jq '.resources | length' < lab-state-*.json

A backup fájl egy friss terraform.tfstate JSON-t tartalmaz; a jq kimenete 2. A visszaállítás csak kényszerű esetben: tofu state push lab-state-....json, de egy párhuzamos apply-t előbb le kell állítani, mert a push felülírja a state-et.

  1. Partial success szimulálása: a main.tf-ben a null_resource parancsát false-ra cseréljük:
  provisioner "local-exec" {
    command = "false"
  }

Ekkor tofu apply -auto-approve a local_file esetén sikeres, de a null_resource hibázik; az apply nem 0 exit code-ot ad, viszont a state már tartalmazza a local_file-t és a módosítást. A hibás részt javítva (például command = "true") a következő tofu apply csak a fennmaradó erőforrást frissíti, és nem kezdi újra a többit.

  1. Destroy explicit lab resource seten:
tofu destroy -target=null_resource.lab_wait
tofu state list

A null_resource.lab_wait törlődik, a local_file.lab_data megmarad. Ez a destroy csak a nevezett erőforrásra terjed ki; a teljes erőforráskészlet törléséhez tofu destroy (explicit megerősítéssel) és a munkakönyvtár takarítása szükséges.

46.5.4 Hibák és ellenpróbák

Lock timeout hiba

Tünet: Error acquiring the state lock vagy Timeout while waiting for state lock. Oka: párhuzamos apply vagy álló state lock. Adatgyűjtés: ps -ef | grep tofu. Hipotézisellenőrzés: várjunk a lock feloldására, vagy tofu apply -lock-timeout=60s. Ha a lock tartósan beragadt (például megölt folyamat maradványa), akkor a tofu force-unlock <lock-id> használható, de előbb ellenőrizni kell, hogy nincs tényleges apply futásban; a force-unlock nem rollback, hanem a lock ellenőrizetlen feloldása.

Drift észrevétlen marad

Tünet: a plan nem mutat change-et, pedig a távoli erőforrás megváltozott. Oka: a konfiguráció nem írja le a teljes desired state-et, vagy a state külsőleg frissült. Hipstézis: az apply előtti plan refresh nélkül készült. Ellenőrzés: tofu plan -refresh-only lefuttatása. Ha a provider nem támogat bizonyos attribútum refreshét, a drift nem detektálható; ilyenkor explicit disk- vagy API-ellenőrzést kell végezni.

Import rossz resource címmel

Tünet: Error: Invalid import target vagy Cannot import a resource that does not exist in the configuration. Oka: a HCL-ben nincs ilyen resource, vagy a resource típus/cím nem illik. Javítás: a main.tf-ben hozzuk létre a resource blokkot, írjuk be az importálandó erőforrást, majd tofu import local_file.lab_data /home/lab/iac/d230/lab.txt. Import után a tofu plan no-op kell legyen, ha a konfiguráció megegyezik.

Partial apply ismételt sikertelensége

Tünet: az apply újra és újra hibaüzenettel áll meg ugyanazon erőforrásnál. Oka: a provisioner vagy provider oldali függőség nem idempotens, vagy a lokális oldali feltétel nem teljesül. Adatgyűjtés: tofu state list, tofu show, provider log TF_LOG=DEBUG. Egy változtatás: a hibás erőforrást töröljük a stateből tofu state rm paranccsal, majd az apply újra provisioningel; ez veszélyes, ezért előbb backupot kell készíteni.

46.5.5 Feladatok

1. Magyarázó feladat: no-op plan értelmezése

Futtassa le a konfigurációt a példa szerint, majd készítsen egy no-op-plan.txt fájlt, amelyben a tofu plan kimenetét rögzíti. Magyarázza meg, miért bizonyítja ez a kimenet, hogy a provision idempotens, és jelölje meg, melyik rész mutatja a 0 add/change/destroy értéket.

2. Konfigurációs/adminisztrációs feladat: drift és moved

A kiinduló labresource-ből kézzel módosítsa a lab.txt fájlt úgy, hogy a tartalom már ne egyezzen a konfigurációval. Készítsen plan -detailed-exitcode-ot, mentsen el a kimenetet. Ezután állítsa vissza a fájlt apply segítségével, és ellenőrizze no-op plan-nel. Végül nevezze át az erőforrást lab_file-ról lab_moved-ra a HCL-ben, és oldja meg moved blokkal, hogy a state ne legyen destroy/create.

3. Diagnosztikai/failure feladat: partial success és recovery

Szimuláljon partial apply-t: a null_resource.lab_wait parancsát cserélje false-ra, futtasson apply-t, rögzítse az exit kódot és a terraform.tfstate állapotát. Készítsen state backupot a hibás állapotról. Javítsa a parancsot true-ra, futtasson újra apply-t, és ellenőrizze, hogy a korábban sikeres local_file nem alakult át, valamint hogy a null_resource.lab_wait frissült. Végül destruálja a null_resource-t, és igazolja, hogy a local_file megmaradt.

46.5.6 Megoldások

1. feladat

A tofu plan kimenete a konfiguráció és a state refresh utáni egyezését mutatja:

No changes. Your infrastructure matches the configuration.
Terraform will compare your desired infrastructure with the stored state of your current infrastructure.
Plan: 0 to add, 0 to change, 0 to destroy.

A 0/0/0 sor a provider által detektált változások hiányát jelenti. Ez bizonyítja, hogy a második apply nem hozna létre újra erőforrást, mert a state és a desired egyezik. Postcondition: a no-op-plan.txt a munkakönyvtárban van, tartalma a fenti kimenet, és a state local_file.lab_file-t tartalmaz.

2. feladat

Drift készítése: echo "manual-edit" >> /home/lab/iac/d230/lab.txt. A tofu plan -detailed-exitcode kimenete:

Plan: 0 to add, 1 to change, 0 to destroy.

Az exit code 2. A javítás tofu apply -auto-approve után a fájl tartalma a konfigurációban megadott, a no-op plan 0 add/0 change/0 destroy. Az átnevezés: a main.tf-ben resource "local_file" "lab_moved" { ... }, és a moved blokk:

moved {
  from = local_file.lab_file
  to   = local_file.lab_moved
}

tofu plan kimenete: Plan: 0 to add, 0 to change, 0 to destroy. tofu apply után tofu state list a local_file.lab_moved-et mutatja, a lab_file nem létezik. Postcondition: a stateben az erőforrás új címe szerepel, a fájl tartalma változatlan, no-op plan.

3. feladat

A main.tf null_resource parancsa command = "false". Az apply -auto-approve nem 0 exit code-ot ad; a state terraform.tfstate a local_file erőforrásra vonatkozóan tartalmazza a kívánt paramétereket, a null_resource pedig a hiba miatt nem frissült sikeresen. State backup: tofu state pull > partial-state-$(date -u +%Y%m%dT%H%M%SZ).json. Javítás után command = "true", tofu apply -auto-approve. A local_file no-op plan-nel igazolhatóan változatlan marad, a null_resource most már sikeresen frissül. Végül tofu destroy -target=null_resource.lab_wait, majd tofu state list: a local_file.lab_moved megmarad, a null_resource eltűnt. Postcondition: a stateben a local_file a lab_moved címen szerepel, a null_resource törölve, a backup fájl érvényes JSON.

46.5.7 Rövid összefoglaló

Ez a labor a provision folyamat ellenőrzésére tanította be az idempotens desciplinát: a plan-ből kiderül, hogy a konfiguráció, a state és a tényleges erőforrás egyezik-e; a no-op plan a reprodukálhatóság bizonyítéka. A driftből apply-vel vagy refresh-only módban lehet kilábalni; import és moved eszközökkel a state igazítható a meglévő erőforrásokhoz. Félbeszakadt apply után a state rendben lévő erőforrásai nem sérülnek, és a következő apply csak a hiányzó részeket pótolja. A destroy-t csak explicit lab resource címre szűkítve futtassuk, és minden elágazásnál készítsünk state backupot. Továbbhasznált definíciók: desired state – a konfigurációban leírt célállapot; observed state – a refreshelt távoli állapot; no-op plan – olyan plan, amely 0 add/change/destroy értéket jelez.

46.5.8 Források és ellenőrzési hiányok

  • OpenTofu dokumentáció – a moved, import, state és provider lock részletek hivatalos ellenőrzését az aktuális OpenTofu release-hez igazítva kell elvégezni.
  • HashiCorp Terraform dokumentáció – a Terraform és OpenTofu szintaktikai kompatibilitása nem teljes minden feature-re.
  • AWS dokumentáció – a lab ebben a fejezetben nem használ AWS erőforrást, de a local provider alternatívájaként a sandbox scope korlátjával használható.

A jelen szövegben szereplő providerverziók, az OpenTofu 1.6 kompatibilitási állítások és a tofu providers lock pontos viselkedése nem ellenőrzött a kiadási dokumentációban; ezeket a labor futtatása előtt a hivatalos release notes és provider registry ellenőrzésével kell alátámasztani. Nincs ténylegesen futtatott kimenet, minden megadott output illusztratív.
