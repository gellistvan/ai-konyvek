34.1 VM, hypervisor, emuláció és isolation

34.1.1 Motiváció

Egy szenior C++ fejlesztő számára a Linux processz, a syscall és a memória-kezelés ismerős: a program userspace kódból hív kernel szolgáltatásokat, a CPU privilege gyűrűt vált, a kernel elszámolja az erőforrásokat a cgroupokban. Amikor egy tesztkörnyezetben több eltérő kernelverzió, különböző disztribúció vagy egy rosszindulatú hibakód izolálása a feladat, ez a modell már nem elég. A virtuális gép (virtual machine, VM) új határt vezet be: egy teljes vendég operációs rendszer fut egy másik operációs rendszeren belül, miközben a vendég kernel számára a hardver valódinak tűnik. A VM az erőforrás- és privilege-határ, amelyet a hypervisor hoz létre a fizikai gép és a vendég között. Ennek megértése nélkül a „miért lassú a VM, miért nem indul, miért osztozik a CPU-n” kérdésekre csak tüneti válaszok adhatók.

34.1.2 Definíció és működés

A hypervisor más néven virtual machine monitor (VMM) az a szoftverréteg, amely a fizikai erőforrásokat — CPU-t, memóriát, I/O-t — egy vagy több vendég között osztja szét és izolálja. A host a fizikai gépet futtató környezet, a guest vagy vendég a virtuális gépen futó operációs rendszer. A vendég számára a hypervisor egy virtuális CPU-t (vCPU) és virtuális memóriát (vRAM) mutat: a vCPU a vendég kernel ütemezője szerint logikai processzor, valójában a host kernel egy ütemezhető szálát használja. A vRAM a vendég fizikai címtartománya, amelyet a hypervisor a host memóriájának egy részéhez rendel hozzá, gyakran lapozható módon. A vendég úgy hajtja végre saját rendszerhívásait, mintha valódi CPU-n futna, de minden privilegizált utasítás a hypervisor ellenőrzésén megy keresztül.

34.1.2.1 Emuláció és hardware-assisted virtualization

Az emuláció (emulation) és a hardver-asszisztált virtualizáció (hardware-assisted virtualization) közötti különbség a vendég és a host utasításkészlet-architektúra (ISA) viszonyában rejlik. Ha a vendég ISA megegyezik a host ISA-val, a legtöbb utasítás közvetlenül futtatható a fizikai CPU-n. A VT-x (Intel) és AMD-V (AMD) CPU kiterjesztések ezt teszik lehetővé: a CPU két végrehajtási móddal rendelkezik, a root mode a hypervisoré, a non-root mode a vendégé. A vendég privilegizált utasításai — például a CPUID, MOV CR3, HLT vagy egy I/O port hozzáférés — VM exitet váltanak ki, a CPU átadja a vezérlést a hypervisornak, amely emulálja vagy helyettesíti a műveletet, majd VM entry-vel visszaadja a futást. Ez a mechanizmus a trap-and-emulate modern megvalósítása. Az instruction emulation ezzel szemben akkor szükséges, ha a vendég ISA különbözik a hostétól, például x86_64 hoston ARM64 vendég futtatásakor, vagy amikor a CPU nem támogatja az adott virtuális eszközt. Ilyenkor a hypervisor vagy egy felhasználói szintű emulátor minden vendég utasítást beolvas, dekódol és szimulál — ez nagyságrendekkel lassabb.

A nested paging a hardver-asszisztált virtualizáció második pillére. A vendég kernel saját page table-t kezel, amely a vendég virtuális címét (guest virtual address, GVA) a vendég fizikai címére (guest physical address, GPA) képezi. A hypervisornak ezt a GPA-t kell a valódi host fizikai címre (host physical address, HPA) leképeznie. A VT-x EPT (Extended Page Tables) és az AMD-V NPT (Nested Page Tables) egy második, hypervisor által vezérelt page table szintet ad a CPU MMU-hoz, amely közvetlenül GVA→GPA→HPA fordítást végez, elkerülve a vendég page table shadowing költségét. A virtualizáció így a memóriaelérésben minimális overheaddel jár; a hiba a kétszintű page walk és a TLB nyomás miatt jelentkezik.

34.1.2.2 Type1/Type2 és trust

A hypervisorokat gyakran Type 1 és Type 2 kategóriába sorolják. A Type 1 hypervisor közvetlenül a hardveren fut, a host kernel nem egy általános célú operációs rendszer, hanem maga a hypervisor (például a Xen, VMware ESXi, vagy a Microsoft Hyper-V bizonyos konfigurációi). A Type 2 hypervisor egy meglévő operációs rendszer felett fut, mint egy folyamat (például a VirtualBox vagy a VMware Workstation). A KVM (Kernel-based Virtual Machine) ezt a dichotómiát finomítja: a KVM egy Linux kernel modul, amely a kernelben valósítja meg a CPU- és memória-virtualizációt, tehát a Linux kernel válik hypervisorrá. A QEMU a felhasználói térben futó eszközmodellt és I/O emulációt biztosítja, a libvirt pedig a menedzsmentet és a deklaratív konfigurációt. Ezért a KVM/QEMU rendszert gyakran Type 1 jellegű architektúrának tekintik, mert a CPU virtualizáció kernel módban, a hardver közvetlen irányításával történik.

A hypervisor trust boundary-ja a kulcsa az izolációnak. A hypervisor nagyobb privilégiummal fut, mint a vendég kernel: root mode-ban, a vendég kernel csak non-root mode-ban. Ha egy vendég kernelben kihasználnak egy sebezhetőséget, a támadó a vendég teljes jogkörét megszerzi, de a hypervisor feladata, hogy a vendég ne érje el más vendégek memóriáját, vCPU-ját vagy a host erőforrásait. A határ pontosan a CPU root/non-root váltáson és a nested paging által biztosított memóriaizoláción alapul. A device model ugyanakkor gyenge pont: a vendég I/O eszközei — hálózati kártya, merevlemez-vezérlő, billentyűzet — gyakran a QEMU felhasználói folyamatában emulálódnak, ami egy nagyobb támadási felületet jelent. A virtio eszközök ezen enyhítenek: a vendég és a host közötti szabványosított paravirtualizált interfész kevesebb emulációs logikát igényel, és a vhost kernel-szál kikapcsolja a QEMU-t az adatútról.

34.1.2.3 VM erőforrásígéret a host valós kapacitásához

A VM erőforrás-ígérete mindig a host valós kapacitásához kell kötni. Egy vCPU nem fizikai mag; a host scheduler egy szálat ütemez hozzá, amely tetszőleges fizikai CPU-n futhat, hacsak affinity-t nem állítunk. Ha a hoston nyolc fizikai mag van, tíz VM-et definiálunk egyenként két vCPU-val, az összesen húsz vCPU — ez CPU overcommit. Ez megengedett, de a vendégek csak akkor kapnak valós CPU-időt, ha a host scheduler az aktív szálakat futtatja; a cpu.max cgroup kvóta pedig korlátozhatja az egyes VM-folyamatokat. Hasonlóan, a vRAM a host memória egy lefoglalt vagy lapozható része. A QEMU/KVM memory back-end-je használhat hugepages-t, shared memory-t vagy memfd-et; a vendég fizikai memória a host szempontjából a QEMU processz virtuális memóriája. Overcommit lehetséges, de a host swapping vagy OOM kill a vendég teljesítményét és megbízhatóságát rontja. A d044-ben bevezetett cgroup v2 itt a VM folyamatra alkalmazható: memory.max a vendég memóriáját, cpu.max a vCPU-k által elérhető CPU-időt korlátozza.

A vCPU topológia is az erőforrás-ígérethez tartozik. A vendégben látott CPU foglalat, mag és szál beállítások befolyásolják a vendég kernel ütemezőjét és a NUMA-topológiát. Ha egy VM-hez négy vCPU-t rendelünk, de azokat egyetlen fizikai foglalat négy szálaként definiáljuk, a vendég operációs rendszer más ütemezési döntést hoz, mint ha négy külön foglalatot látna. A vCPU→pCPU affinitás és a host NUMA-node elhelyezés a d013-ban tanultak szerint határozza meg a memória-hozzáférési késleltetést. A virtuális CPU soha nem garantál fix fizikai kapacitást; csak a host scheduler és cgroup szabályok együttesen adnak felső korlátot.

34.1.2.4 Konténer mint ellenpélda

A konténer ezzel szemben nem virtualizál hardvert: ugyanazon a host kernelen fut, csupán namespace-ekkel izolálja a processz- és hálózati nézetet, cgroupokkal pedig az erőforrásokat. A vendég kernel hiánya miatt nincs vCPU, nincs vendég syscall réteg, nincs privileged utasítás elfogás. A konténer biztonsági határa a host kernel syscall ABI-ja és a seccomp/capabilities szűrő, ami lényegesen nagyobb attack surface a közös kernel miatt, viszont a CPU overhead minimális. A VM izolációs fala erősebb: a vendég kernel hibája nem közvetlenül a host kernelre hat, hanem a hypervisorra. Ezért a VM-et olyankor választjuk, amikor eltérő kernel, teljes operációs rendszer vagy erős multi-tenant elszigetelés kell; a konténert akkor, ha a gyors indulás és a nagy sűrűség a fontos.

34.1.3 Kidolgozott példa: lab VM és erőforrás-ellenőrzés

A példa egy Ubuntu Server 24.04 LTS labhoston fut. A labhost1 nevű gépen a labops felhasználó a libvirt csoport tagja, a libvirtd fut, és a /dev/kvm elérhető. A VM neve lab-vm, a lemezkép lab-vm.qcow2 az előző laborból rendelkezésre áll (az image előállítását a d171 tárgyalja). Cél: definiáljunk egy 2 vCPU, 4 GiB RAM VM-et, indítsuk el, és ellenőrizzük a host oldali szál-hozzárendelést.

Először a host CPU kapacitását és a KVM jelenlétét ellenőrizzük:

# Target: labhost1, user: labops, privilege: labops / libvirt group
lscpu | grep -E '^CPU\(s\)|^Model name|^Virtualization'
ls -l /dev/kvm

Várható kimenet (illusztratív, nem mért):

CPU(s):              8
Virtualization:      VT-x
crw-rw---- 1 root kvm 10, 232 ... /dev/kvm

A VM definíciója lab-vm.xml:

<!-- Target: labhost1; source: /home/labops/lab-vm.xml -->
<domain type='kvm'>
  <name>lab-vm</name>
  <vcpu placement='static'>2</vcpu>
  <memory unit='GiB'>4</memory>
  <os>
    <type arch='x86_64' machine='q35'>hvm</type>
    <boot dev='hd'/>
  </os>
  <devices>
    <disk type='file' device='disk'>
      <driver name='qemu' type='qcow2'/>
      <source file='/var/lib/libvirt/images/lab-vm.qcow2'/>
      <target dev='vda' bus='virtio'/>
    </disk>
    <interface type='network'>
      <source network='default'/>
      <model type='virtio'/>
    </interface>
  </devices>
</domain>

A definiálás és indítás, majd az erőforrás-hozzárendelés ellenőrzése:

# Target: labhost1, user: labops, group: libvirt
virsh define lab-vm.xml
virsh start lab-vm
virsh dominfo lab-vm
virsh vcpuinfo lab-vm

A virsh vcpuinfo várhatóan két vCPU-t mutat, mindegyikhez tartozó host CPU affinitással. A host oldalon a QEMU folyamat szálai láthatóvá teszik a vCPU-k megvalósítását:

# Target: labhost1, user: labops, privilege: ps látható saját processz
pgrep -a qemu-system-x86_64
ps -L -o pid,tid,psr,comm -p $(pgrep -f 'qemu-system-x86_64.*lab-vm')

A kimeneten a fő qemu-system-x86_64 szál mellett legalább két CPU 0 és CPU 1 nevű szál látszik, különböző psr (physical CPU) értékekkel, ha a host scheduler engedi. A vendégben nproc 2-t, free -h körülbelül 4 GiB-ot mutat. A rollback:

# Target: labhost1; csak a lab-vm saját objektumaira
virsh shutdown lab-vm
# ha nem áll le: virsh destroy lab-vm
virsh undefine lab-vm

Postcondition: a lab-vm definíció eltávolítva, a lemezkép változatlanul megmarad.

34.1.4 Hibák és ellenpróbák

Hiba 1: „A vCPU ugyanaz, mint egy fizikai mag, tehát a VM garantáltan megkapja a CPU-időt.” A vCPU-t a host kernel ütemezi; ha más processzek vagy VM-ek versengenek, a vendég csak a host scheduler által adott időt kapja. A virsh vcpuinfo csak az affinitást mutatja, nem a tényleges CPU-időt. Helyes diagnózis: host oldalon top vagy perf a QEMU szál %CPU értékére, vendégben mpstat vagy /proc/stat.

Hiba 2: „Az emuláció és a virtualizáció ugyanaz, hiszen a QEMU is emulál.” A QEMU képes tisztán szoftveres emulációra (például -M accel=tcg), de a KVM-mel kombinálva hardware-assisted virtualizációt használ. A virsh dumpxml domain type='kvm' attribútuma jelzi a KVM gyorsítást. Ha a VM „No accelerator found” hibával nem indul, a /dev/kvm hiánya vagy jogosultsági probléma a valódi ok, nem az emuláció.

Hiba 3: „A hypervisor izolációja tökéletes, a vendég nem tudja befolyásolni a hostot.” A CPU és memória izoláció erős, de a device model, a firmware és a host scheduler side channel-ek támadási felületet jelentenek. A modern hardveres mitigációk ellenére a vendégből való kiszabadulás (VM escape) lehetséges hibakategória. A mérnöki válasz a minimal device model és a vendég kernel frissítése, nem a „tökéletes” feltételezés.

Hiba 4: „Ha a vendég kernel OOM-kill-t hajt végre, az a host memóriáját is károsítja.” A vendég OOM a vendég saját memóriáját érinti; a host oldalon a QEMU processz a saját memória-limitje (cgroup vagy memory.max) alatt fut. Ha a host memória túlterhelt, a host kernel a QEMU processzt is kilőheti, de ez a host hiány, nem a vendég belső állapota.

34.1.5 Feladatok

34.1.5.1 1. Magyarázó feladat

Hasonlítsa össze a processz, a konténer és a VM izolációs határait egy táblázatban. Töltse ki az alábbi sorokat: kernel saját vagy megosztott; privilegizált utasítások futási módja; erőforrás-elszámolás; támadási felület a host felé; tipikus indítási idő; CPU overhead. Indokolja, miért nem elegendő a namespace/cgroup izoláció erős multi-tenant elszigeteléshez.

34.1.5.2 2. Adminisztrációs/konfigurációs feladat

A labhost1 gépen definiáljon egy lab-vm-spec nevű KVM VM-et, amely 1 vCPU-t, 2 GiB memóriát és egy meglévő qcow2 lemezt kap. A definícióhoz használjon explicit XML-t. A definiálás után ne indítsa el, csak a virsh dumpxml kimenetét ellenőrizze. Postcondition: a lab-vm-spec definíció létezik, nem fut, XML-ben a vCPU szám 1, a memória 2 GiB.

34.1.5.3 3. Diagnosztikai/failure/recovery feladat

A lab-vm indítása ezzel a hibaüzenettel bukik el: error: failed to get domain 'lab-vm' először, majd a virsh start lab-vm hibája error: Failed to start domain 'lab-vm' és a logban No accelerator found.. Fogalmazza meg a hipotézist, gyűjtse össze a szükséges adatokat a host oldalon (parancsokkal), hajtsa végre az egy változtatásos javítást, és ellenőrizze a VM elindulását. Térjen ki a /dev/kvm jogosultság és a CPU virtualizációs kiterjesztés hiányának megkülönböztetésére.

34.1.6 Megoldások

34.1.6.1 1. Magyarázó feladat megoldása

A processz a host kernelben fut, syscall interface-t használ, az erőforrásait a cgroupok limitálhatják, a host felé a kernel sebezhetőségei a támadási felület. A konténer ugyanazon kernelt használ, namespace-ekkel izolálja a nézeteket, cgroupokkal a resource-okat; a kernel attack surface közös, indítási idő milliszekundum, CPU overhead minimális. A VM saját vendég kernelt futtat, a vendég privileged utasításai non-root CPU módban futnak, a hypervisor trap-eli őket; a host felé a hypervisor és device model a támadási felület, indítási idő másodperc, CPU overhead alacsony, de nagyobb, mint a konténeré. A namespace/cgroup nem nyújt védelmet a kernel sebezhetőségeivel szemben, mert a rendszerhívás ugyanabba a kernelbe lép be; a VM root/non-root hardveres elkülönítése ezt a réteget leválasztja.

34.1.6.2 2. Adminisztrációs feladat megoldása

A lab-vm-spec.xml ugyanazt a struktúrát követi, mint a példa, de:

<domain type='kvm'>
  <name>lab-vm-spec</name>
  <vcpu>1</vcpu>
  <memory unit='GiB'>2</memory>
  ...
</domain>

A definiálás:

virsh define lab-vm-spec.xml
virsh dumpxml lab-vm-spec | grep -E '<vcpu|<memory'

Postcondition: a virsh list --all mutatja a lab-vm-spec-et, állapota shut off.

34.1.6.3 3. Diagnosztikai feladat megoldása

Hipotézis: a /dev/kvm nem elérhető a libvirt számára, vagy a CPU nem támogatja a VT-x/AMD-V kiterjesztést. Adatgyűjtés:

ls -l /dev/kvm
egrep -c '(vmx|svm)' /proc/cpuinfo

Ha az egrep 0-t ad, a CPU virtualizáció hiányzik, ez a No accelerator found oka. Ha a /dev/kvm létezik, de a labops nem tagja a kvm csoportnak, a chmod 666 /dev/kvm nem megengedett recept; helyette a felhasználót kell a kvm csoportba tenni, vagy a libvirt rendszerszintű jogosultságát ellenőrizni. A javítás egy változtatás: usermod -aG kvm labops és új bejelentkezés. Ellenőrzés: virsh start lab-vm, majd virsh list --all állapota running. Postcondition: a VM fut, a korábbi hiba nem tér vissza.

34.1.7 Rövid összefoglaló

A VM a host és a vendég közötti erőforrás- és privilege-határ, amelyet a hypervisor valósít meg. A hardver-asszisztált virtualizáció (VT-x/AMD-V) root/non-root CPU módokkal és nested paginggel (EPT/NPT) biztosítja, hogy a vendég kernel a legtöbb utasítását közvetlenül futtassa, de a privileged utasítások VM exit-tel a hypervisorhoz kerüljenek. A vCPU a host scheduler egy szálaként ütemezett entitás, a vRAM a host memória egy leképezett része; mindkettőt a host valós kapacitásához és cgroupszabályaihoz kell kötni. A konténer ezzel szemben ugyanazon kernelt használ, nincs vendég kernel, így kisebb izolációs fal, de kisebb overhead. Továbbhasznált definíciók: hypervisor (VMM) – a fizikai erőforrásokat izoláló és a vendég privileged utasításait elfogó réteg; hardware-assisted virtualization – a CPU root/non-root módjait és nested pagingjét használó, alacsony overheadű virtualizáció; vCPU – a vendég számára látszó logikai processzor, amely a host kernel egy ütemezett szálát használja.
