52.3 Platform secrets, federation és rotation

52.3.1 Motiváció

A DevOps platformon a titkok koncentrált hatalmat képviselnek: aki birtokolja a CI service account credentialját, a cluster admin tokenjét vagy a DB jelszót, az átlépi a réteg határát és capability-t szerez. A szenior C++ fejlesztő számára ez hasonló ahhoz, amikor egy pointer vagy egy capability túlél egy olyan határt, ahol már nem kellene: a hívó hirtelen jogosultságot nyer. A korábbi alfejezetekben láttuk a cloud IAM trust policy-t (d217) és a Kubernetes Secret/Workload Identity-t (d208). Most ezeket egy platform secret managerbe integráljuk: a forrástól a runtime-ig egy explicit credential láncot építünk, amelynek minden lépése rövid lejáratú, minimális scope-ú és auditálható. A cél nem csupán a titok elrejtése, hanem a teljes életciklus kontrollálása: kiadás, felhasználás, megújítás, rotáció, visszavonás és helyreállítás.

52.3.2 Definíció és működés

A platform secret a platformon belüli authentication és authorization során használt érzékeny adat: password, API key, private key, database credential, token. A secret manager ezeket a titkokat verziózva tárolja, hozzáférést vezérel, rotációt futtat és audit logot ad. A KMS (Key Management Service) a titkosítási kulcsok életciklus-kezelője; a secret manager a KMS mesterkulcsával titkosítja az adatkulcsot, ez az envelope encryption. A HSM (Hardware Security Module) dedikált, tamper-resistant hardver, amelyben a privát kulcsok nem exportálhatók, és minden kriptográfiai művelet a modulon belül fut. A KMS/HSM tehát a tárolás trust anchorját adja, de a hozzáférési trustot a federation adja.

Az OIDC federation a hosszú életű statikus hitelesítő helyett rövid lejáratú, identity provider (IdP) által kiállított JWT assertiont használ. A secret manager trust policy a JWT iss, sub, aud és exp claimjeit szűri, és csak a megfelelő principal számára ad belső, rövid életű tokent. A human, a CI runner és a workload ugyanazt a modellt követi:

  • Human: SSO/OIDC login, majd rövid életű platform token.
  • CI: a runner az adott projekt/job audience-hez kötött ID tokent kap, és ezt federálja a secret managerbe.
  • Workload: a pod a projected service account tokenjét mutatja be, amelyet a kubelet a megadott audience-re állít ki.

A short-lived token/lease a titokhoz kötött, megújítható hozzáférés. A lease lejártakor a secret manager automatikusan visszavonja a target rendszeren az adott credentialt. A dynamic secret (például dynamic DB credential) a secret manager és a célrendszer API-ján keresztül jön létre: a secret manager ideiglenes DB-user-t hoz létre, valid_until korláttal, és a TTL lejártakor törli. Ezzel megszűnik a statikus credential rotációjának problémája: a credential maga a rövid életű erőforrás.

A secret scanning a forráskódban, image layerben, artifactban és logokban keresi az ismert titokmintákat (például AWS key, private key header, JWT). A log/artifact exposure ellen log redaction és artifact signing szükséges. A rotation/revoke/recovery/audit pedig a titok életciklusának operatív része: a rotáció új verziót vezet be grace perioddal, a revoke azonnali, a recovery break-glass hozzáférés, az audit pedig immutable eseménynapló.

52.3.3 Kidolgozott példa

A példa egy lab környezetben mutatja be a teljes credential láncot. A lab hostok:

Név Cím Szerep UID/Privilege
lab-vault 203.0.113.10 Vault dev server vault
lab-db 203.0.113.11 PostgreSQL 16 postgres
lab-eks cluster context Kubernetes 1.31 cluster-admin

A Vault dev mode hipotetikus 1.18.3, nem production; a root token dummy lab-root, a TLS kikapcsolva. A lab-eks OIDC issuer: https://oidc.eks.eu-central-1.amazonaws.com/id/EXAMPLED539D463 (dummy). A namespace lab-app, service account lab-api-sa.

Target: lab-vault, UID vault. Előfeltétel: Vault dev mode fut a 8200 porton, a VAULT_ADDR és VAULT_TOKEN beállítva.

  1. Database dynamic secret engine bekapcsolása és konfigurálása
vault secrets enable database

vault write database/config/postgresql \
  plugin_name=postgresql-database-plugin \
  allowed_roles=lab-db-reader \
  connection_url="postgresql://{{username}}:{{password}}@lab-db.lab.internal:5432/postgres" \
  username="vault_admin" \
  password="lab-vault-admin-password" \
  tls_skip_verify=true

A tls_skip_verify csak lab, productionben nem engedhető.

  1. Dynamic credential role létrehozása
vault write database/roles/lab-db-reader \
  db_name=postgresql \
  creation_statements="CREATE ROLE \"{{name}}\" WITH LOGIN PASSWORD '{{password}}' VALID UNTIL '{{expiration}}'; GRANT SELECT ON ALL TABLES IN SCHEMA public TO \"{{name}}\";" \
  default_ttl=1h \
  max_ttl=4h

A role default_ttl=1h, tehát a kiadott DB credential egy óra múlva automatikusan revokálódik.

  1. JWT/OIDC auth method bekapcsolása
vault auth enable jwt

vault write auth/jwt/config \
  oidc_discovery_url="https://oidc.eks.eu-central-1.amazonaws.com/id/EXAMPLED539D463" \
  bound_issuer="https://oidc.eks.eu-central-1.amazonaws.com/id/EXAMPLED539D463"
  1. Workload role mapping szűk audience-szel
vault write auth/jwt/role/lab-db-reader \
  role_type=jwt \
  bound_audiences="vault.lab.internal" \
  user_claim="sub" \
  bound_subject="system:serviceaccount:lab-app:lab-api-sa" \
  policies=lab-db-reader-policy \
  ttl=1h

A bound_subject kizárólag a lab-app namespace lab-api-sa service accountját engedi; az bound_audiences a pod projected tokenjének audience-ét vault.lab.internal-re szűkíti.

  1. Policy a minimális scope-hoz
vault policy write lab-db-reader-policy - <<'EOF'
path "database/creds/lab-db-reader" {
  capabilities = ["read"]
}
EOF

A policy csak a database/creds/lab-db-reader path olvasását engedi, a Vault token ettől nem fér hozzá más secret pathhez.

  1. Workload bejelentkezés és dynamic credential kérése

A podban a projected token audience vault.lab.internal. A pod a tokenjét bemutatja:

TOKEN=$(cat /var/run/secrets/kubernetes.io/serviceaccount/token)
vault write auth/jwt/login role=lab-db-reader jwt="$TOKEN" \
  | tee /tmp/vault-response.json

VAULT_TOKEN=$(jq -r .auth.client_token /tmp/vault-response.json)
vault read -format=json database/creds/lab-db-reader

Várt kimenet (hipotetikus, nem tényleges futtatás):

{
  "request_id": "dummy-request-id",
  "lease_id": "database/creds/lab-db-reader/9fK8...",
  "lease_duration": 3600,
  "renewable": true,
  "data": {
    "username": "v-root-lab-db-XYZ",
    "password": "dummy-generated-password"
  }
}

A lease_duration 3600 másodperc; a DB user v-root-lab-db-XYZ a PostgreSQL-ben valid_until korláttal létezik. A Vault a TTL lejártakor automatikusan revokálja.

  1. Leak/rotation response – revoke és audit

Ha a password megjelenik egy CI logban vagy rossz helyen, a kontrollált válasz:

# A kiszivárgott lease azonnali revoke-ja
vault lease revoke <lease_id_from_response>

# A Vault token revoke-ja
vault token revoke <vault_token>

# Ellenőrzés a DB oldalon, hogy a dynamic user megszűnt
psql -h lab-db.lab.internal -U vault_admin -d postgres \
  -c "SELECT rolname FROM pg_roles WHERE rolname LIKE 'v-root-lab-db-%';"

A psql várt kimenete a revoke után üres, mert a Vault eltávolítja a role-t. Az audit logban a revoke esemény rögzül:

vault audit list

A rotáció a dynamic credential esetében nem kézi: a TTL lejárat és a vault lease renew adja a megújítást. Ha statikus secretet használnánk (KV v2), a rotáció külön új verzió kiadásával és a régi eltávolításával történik. A recovery break-glass hozzáférést a DB vault_admin user jelent, de annak credentialját is a secret managerben, erősebb policy-vel és saját rotation ablakkal kell tárolni.

Rollback: a wrong role mapping vagy policy esetén a Vault write/delete parancsokkal, a lab state a vault policy delete, vault auth disable, vault secrets disable lépésekkel visszaállítható. A lab-eks service account token audience beállítása a pod specben ellenőrzendő.

52.3.4 Hibák és ellenpróbák

  • Túl hosszú életű token: a federation nélküli CI token a configban napokig él. Tünet: a leakelt token a revoke előtt is használható marad. Diagnosztika: a Vault token ttl értéke 0 vagy nagyon magas. Helyes megoldás: JWT auth rövid TTL-lel, renew csak a lease-re.
  • Túl tág policy: a path "database/creds/*" enged minden dynamic role-t. Hiba: egy másik SA is kaphat DB creds-et. A scope mindig exact path + role + audience.
  • Hiányzó bound_audiences: a JWT role audience nélkül elfogadja a Kubernetes kubernetes audience tokenjét is, ami más rendszer céljára készült. Az ellenpróba: a Vault role bound_audiences nélkül a default audience token is bejelentkezhet. A javítás a role explicit audience-re szűkítése.
  • Password a CI logban: a vault read outputja véletlenül a logba kerül. A válasz: azonnali revoke, audit, majd a CI pipelineban a titkosító output redaction bevezetése. A podnak nem szabad a secretet a fájlrendszerre írni.
  • Rotációs outage: az alkalmazás cacheli a régi credentialt, és a revoke után a lekérés meghiúsul. A megoldás: grace period a rotációban, valamint az alkalmazás oldali reload ablak a lease durationön belül.

52.3.5 Feladatok

  1. Magyarázó feladat: Rajzolja fel a credential láncot a lab-app podtól a PostgreSQL-ig: projected service account token, OIDC issuer, Vault JWT auth, Vault token, database dynamic credential, DB user. Jelölje a trust boundary-ket és az egyes tokenek TTL-jét. Nevezze meg, hol történik a revoke, ha a podot törlik.

  2. Adminisztrációs/konfigurációs feladat: A lab Vaulton hozzon létre egy új JWT role-t lab-db-writer néven, amely a lab-app namespace lab-api-sa service accountját engedi vault.lab.internal audience-szel, és a lab-db-writer-policy policy-t kapja. A dynamic DB role legyen lab-db-writer, default_ttl=30m, max_ttl=1h, a creation_statements adjon SELECT, INSERT, UPDATE jogot. Konfigurálja a policy-t úgy, hogy a database/creds/lab-db-writer pathra read, a database/roles/lab-db-writer pathra read capability legyen. Ellenőrizze a scope-ot: a lab-db-reader role tokenje nem férhet hozzá a writer pathhoz.

  3. Diagnosztikai/failure/recovery feladat: A lab-app pod nem kap database credentialt; a logban permission denied hiba jelenik meg a Vault hívásánál. Hipotéziseket állítson fel, és vizsgálja meg:

    • A JWT role bound_subject megegyezik-e a pod service accountjával?
    • A bound_audiences megfelelő-e?
    • A policy path írásmódja helyes-e?
    • A Vault token TTL-je nem járt-e le? Javítsa a hibát, és ha a database password kiszivárgott egy CI logba, írja le a leak response lépéssorát (revoke, audit, rotation, recovery postcondition).

52.3.6 Megoldások

  1. A lánc: pod SA → projected token (audience=vault.lab.internal, exp 1h) → Vault JWT auth → Vault token (policy lab-db-reader-policy, ttl=1h) → Vault database engine → PostgreSQL dynamic credential (valid_until 1h) → DB user v-root-.... Trust boundary-k: Kubernetes token kiállítás, Vault JWT verifikáció, Vault policy, DB role létrehozás. A pod törlésekor a Vault token nem feltétlenül szűnik meg, de a lease a TTL lejártával vagy explicit revoke-kal szűnik.

  2. A Vault parancsok:

vault write database/roles/lab-db-writer \
  db_name=postgresql \
  creation_statements="CREATE ROLE \"{{name}}\" WITH LOGIN PASSWORD '{{password}}' VALID UNTIL '{{expiration}}'; GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA public TO \"{{name}}\";" \
  default_ttl=30m \
  max_ttl=1h

vault policy write lab-db-writer-policy - <<'EOF'
path "database/creds/lab-db-writer" {
  capabilities = ["read"]
}
path "database/roles/lab-db-writer" {
  capabilities = ["read"]
}
EOF

vault write auth/jwt/role/lab-db-writer \
  role_type=jwt \
  bound_audiences="vault.lab.internal" \
  user_claim="sub" \
  bound_subject="system:serviceaccount:lab-app:lab-api-sa" \
  policies=lab-db-writer-policy \
  ttl=30m

Ellenőrzés: a lab-db-reader tokenjével vault read database/creds/lab-db-writer kell, hogy permission denied-et adjon. A reader role tokenje nem fér hozzá a writer pathhoz, mert a reader policy nem tartalmazza.

  1. Diagnosztikai lépések:
    • kubectl get pod <pod> -n lab-app -o jsonpath='{.spec.serviceAccountName}' – a SA legyen lab-api-sa.
    • A podban a cat /var/run/secrets/kubernetes.io/serviceaccount/token token claimjét dekódolva ellenőrizni a sub értéket és az aud claimet.
    • A Vault oldalon vault read auth/jwt/role/lab-db-reader kiírja a role bindingokat.
    • Ha a bound_subject eltér, javítsd vault write auth/jwt/role/lab-db-reader ... parancs újrafuttatásával.
    • Ha a policy path rossz, javítsd a policy-t, majd ellenőrizd vault token capabilities <token> database/creds/lab-db-reader.
    • A leak response: vault lease revoke <lease_id>, vault token revoke <vault_token>, audit log ellenőrzés, a CI logban redaction vagy secret scanning, új credential kiadása a pod újraindításával. Postcondition: a kiszivárgott credential nem használható, a pod újból sikeresen kapja a credentialt, az audit log tartalmazza a revoke eseményt.

52.3.7 Rövid összefoglaló

A platform secret management nem csupán tárolás, hanem életciklus: a secret manager KMS/HSM trust anchor-ra épít, az OIDC federation rövid lejáratú identity-t ad a human/CI/workload entitásoknak, a dynamic secret pedig a célrendszeren generált, automatikusan lejáró credential. A hozzáférést minél kisebb scope-ú policy és audience/subject feltétel korlátozza. A leak response kontrollált: revoke, audit, rotation, recovery. A titok-scanning a forrástól a runtime-ig detektálja a kiszivárgást. Az egész modell lényege, hogy a hitelesítő adat ne éljen tovább, mint a felhasználási ablak.

Továbbhasznált definíciók: Secret manager – titkokat verziózó, policy-vel védő, auditáló szolgáltatás; Dynamic secret – rövid életű, automatikusan visszavont, célrendszeren generált credential; OIDC federation – rövid életű JWT assertion cseréje korlátozott trust policy-vel.

52.3.8 Források és ellenőrzési hiányok

A felsorolt hivatkozások kiindulópontok, nem olvasott, ellenőrzött bizonyítékok. Ebben a kérésben nincs webes kereső, ezért a linkeket nem nyitottam meg. A Vault, PostgreSQL, Kubernetes OIDC, AWS STS/IAM, valamint a secret scanning eszközök pontos verziói, szintaxisai és viselkedése a lab profilban és a hivatalos dokumentációban ellenőrizendők. A példa account ID, issuer, thumbprint, Vault token és db user mind hipotetikus labfixture, nem valós erőforrás. A Vault dev mode nem production; a tls_skip_verify és a root token lab-only konfiguráció.
