17.4 Core dump, kernel crash és diagnosztikai artifact

17.4.1 Motiváció

Szenior C++ fejlesztőként az interaktív debuggerrel végzett crash-elemzés természetes munkakörnyezet. Production Linuxon azonban a hibás folyamat mellett általában nem ül debugger; a diagnózishoz a kernel által kimentett memóriakép, a core dump (magkép) szolgál bizonyítékul. A core dump csak akkor hasznos diagnosztikai artifact, ha a hozzá tartozó bináris és szimbólumok is rendelkezésre állnak, és ha a gyűjtés, a tárolás, a jogosultság és a retention üzemeltetési szerződése világos. A kernel saját hibája, a kernel panic vagy oops, ettől eltérő utat igényel: ott nem a megszokott process core, hanem a teljes kernelmemória, a vmcore a cél. Ebben az alfejezetben a processcrash és a kernelcrash vizsgálati útját külön kezeljük, a build-id alapú matchingre, a systemd-coredump működésére és a kdump lehetőségére építve.

17.4.2 Definíció és működés

A core dump egy futó process address space-ének pillanatképe, amelyet a kernel generál, amikor a folyamat olyan jelzést kap, amely az alapértelmezett leállítást eredményezi (például SIGSEGV, SIGABRT, SIGBUS). A kernel két dolgot vesz figyelembe: a process RLIMIT_CORE limitjét (shellből ulimit -c) és a rendszer szintű /proc/sys/kernel/core_pattern fájlt. Ha a limit nulla, nem keletkezik core. Ha a core_pattern egyszerű fájlnév, a kernel oda ír; ha pipe karakterrel kezdődik (|), a kernel a core adatot a megadott program standard bemenetére küldi. Az Ubuntu 24.04 LTS alapértelmezésben a |/lib/systemd/systemd-coredump pipe handler fut, tehát a systemd-coredump fogadja a core-t, a journalba metaadatokat, a /var/lib/systemd/coredump/ könyvtárba pedig tömörített fájlt ír.

A systemd-coredump a core fájlt a /etc/systemd/coredump.conf beállításai szerint kezeli. A Storage=external érték esetén a /var/lib/systemd/coredump/ alatt tárolódik a fájl, Compress=yes esetén jellemzően lz4 vagy xz tömörítéssel. A fájlnév a bináris nevéből, a PID-ből és a build-id-ből generálódik, például core.labcrash.1234.2f0e3d5b...lz4. A coredumpctl parancs az így tárolt core-ok lekérdezésére, dumpolására és debuggerrel való megnyitására szolgál.

A build-id az ELF binárisba és a core-ba is bekerülő, a linker által generált egyedi azonosító. A core dumpban tárolt build-id lehetővé teszi a matching bináris és debuginfo pontos azonosítását. Ha a bináris időközben megváltozott, a debugger a build-id mismatch alapján figyelmeztet, így nem elemezhetünk téves szimbólumokkal. A disztribúció debuginfod szolgáltatása vagy a külön telepített debuginfo package a build-id alapján szolgáltatja a szimbólumokat.

A kdump a kernelcrash esetére fenntartott mechanizmus. A rendszerindításkor a kernel parancssorban megadott crashkernel= paraméterrel egy kis memóriaterületet rezerválunk. Amikor a kernel panic állapotba kerül, egy előre betöltött, második capture kernel indul, amely a lefagyott kernel memóriáját egy vmcore fájlba menti, általában a /var/crash könyvtárba. A vmcore elemzése a kernelhez tartozó vmlinux debuginfo-val, valamint a crash vagy a gdb eszközzel történik.

A core dump érzékeny adatokat tartalmazhat: heap-részleteket, stack frame-eket, environment változókat, titkos kulcsokat, session tokeneket. Ezért a systemd-coredump a fájlokat 0600 jogosultsággal tárolja, és a coredumpctl parancsot nem root felhasználóként futtatva csak a saját core-jainkhoz férünk hozzá. A core fájlok másolása, elemzése és törlése ezért explicit, célhoz kötött művelet kell legyen.

17.4.3 Kidolgozott példa

A példa célja egy szándékos processcrash előállítása, a keletkező core dump azonosítása, a build-id egyeztetése és a stack trace kinyerése a labhost1 nevű, Ubuntu 24.04 LTS labhoston. A példa felhasználója labadmin (UID 1000), a módosító parancsoknál a sudo explicit jelzi a root jogosultságot.

Először készítsünk egy egyszerű C++ programot, amely null pointerre másol, és így SIGSEGV-t vált ki. A forráskód:

// labcrash.cpp
#include <cstring>
#include <iostream>

int main(int argc, char** argv) {
    const char* message = "lab crash";
    char* buffer = nullptr;
    std::strcpy(buffer, message);  // SIGSEGV
    return 0;
}

Fordítás debug szimbólumokkal, optimalizálás nélkül, hogy a stack trace beszédes legyen:

labadmin@labhost1:~$ g++ -g -O0 -o labcrash labcrash.cpp

A futtatás a várt crash-t eredményezi:

labadmin@labhost1:~$ ./labcrash
Segmentation fault (core dumped)

A systemd-coredump elfogta a core-t. Ellenőrizzük a listában:

labadmin@labhost1:~$ coredumpctl list
TIME                            PID   UID   GID SIG COREFILE EXE
Mon 2025-05-19 10:15:22 CEST   1234  1000  1000 SIGSEGV present  /home/labadmin/labcrash

A coredumpctl info részletes metaadatokat ad a core-ról, beleértve a build-id-t:

labadmin@labhost1:~$ coredumpctl info 1234
           PID: 1234 (labcrash)
           UID: 1000 (labadmin)
           GID: 1000 (labadmin)
        Signal: 11 (SEGV)
     Timestamp: Mon 2025-05-19 10:15:22 CEST
  Command Line: ./labcrash
    Executable: /home/labadmin/labcrash
    Build ID: 2f0e3d5b7e9a1c2f4a8b6c0d1e3f5a7b9c1d2e3
    ...

A 2f0e3d5b... érték egy illusztratív build-id. A binárisban is szerepelnie kell ugyanennek az azonosítónak:

labadmin@labhost1:~$ readelf -n labcrash | grep 'Build ID'
    Build ID: 2f0e3d5b7e9a1c2f4a8b6c0d1e3f5a7b9c1d2e3

Az egyezés igazolja, hogy a core-hoz pontosan az a bináris tartozik, amelyből a crash történt. Nyissuk meg a core-t a GDB-vel a coredumpctl segítségével; ez automatikusan a Executable mező alapján keresi a binárist:

labadmin@labhost1:~$ coredumpctl debug 1234
GNU gdb (Ubuntu 14.0-1ubuntu1) ...
Core was generated by `./labcrash'.
Program terminated with signal SIGSEGV, Segmentation fault.
#0  0x00007f... in __strcpy_evex () from /lib/x86_64-linux-gnu/libc.so.6
(gdb) bt
#0  0x00007f... in __strcpy_evex ()
#1  0x000055... in main (argc=1, argv=0x7ffd...) at labcrash.cpp:8

A bt parancs a pontos forrássort mutatja, mert a debuginfo jelen van. A kernelcrash útját a következő konfigurációellenőrzéssel szemléltetjük; a labhostot nem indítjuk szándékos panic felé. A kdump foglalás és állapot ellenőrzése:

labadmin@labhost1:~$ sudo kdump-config show
...
* crashkernel reservation:
    /proc/cmdline: BOOT_IMAGE=/boot/vmlinuz-... crashkernel=512M
...

Ha a crashkernel paraméter hiányzik, a kdump nem tud vmcore-t menteni. A vmcore elemzéséhez a kernel debuginfo és a crash eszköz szükséges (utóbbi telepítése disztribúciófüggő); a parancs alakja jellemzően:

labadmin@labhost1:~$ sudo crash /usr/lib/debug/boot/vmlinux-$(uname -r) /var/crash/vmcore

A pontos parancsszintaxis és a kernel debuginfo elérési útja verziófüggő, ezért a lab környezetben ellenőrizni kell.

17.4.4 Hibák és ellenpróbák

Nincs core dump a várt helyen. Ha a core dumped üzenet elmarad, vagy a coredumpctl list üres, több réteget kell ellenőrizni. Először a process limit: ulimit -c a shellben, illetve cat /proc/<PID>/limits | grep core. Ha a limit 0, a kernel nem generál core-t. A systemd unitoknál a LimitCORE=0 beállítás is tiltó lehet. Másodszor a core_pattern: cat /proc/sys/kernel/core_pattern. Ha az nem pipe handler, vagy a handler nem fut, a core elveszhet. Harmadszor a systemd-coredump szolgáltatás állapota: systemctl status systemd-coredump. A javítás után a ulimit -c unlimited vagy a unit LimitCORE=infinity beállítás, valamint a systemctl enable --now systemd-coredump szükséges.

A GDB nem talál szimbólumokat. Ha a bináris stripped, vagy a hozzá tartozó debuginfo package hiányzik, a backtrace csak címeket mutat. A coredumpctl info build-id-je alapján a debuginfod automatikus letöltést tud végezni, vagy manuálisan a megfelelő debug package telepíthető. A build-id mismatch esetén a bináris azóta megváltozott; a régi binárist kell visszaállítani, például az artifact rendszerből.

A core fájl nem olvasható. A /var/lib/systemd/coredump/ alatti fájlok 0600 joggal, a tulajdonos user vagy root alá tartoznak. Más user nem fér hozzá, és ez helyes, mert a core érzékeny adatot tartalmaz. A coredumpctl root nélkül csak a saját core-jainkat látja.

Kernel oops van, de vmcore nincs. Ha a dmesg vagy a journal oops-ot mutat, de a /var/crash üres, a kdump nincs megfelelően konfigurálva. Ellenőrizni kell a crashkernel= kernel paramétert, a kdump-tools csomag telepítettségét és a kdump-config test kimenetét. A vmcore hiánya azt jelenti, hogy a kernelmemória pillanatképe elveszett; a diagnózis csak a naplókra korlátozódik.

17.4.5 Feladatok

17.4.5.1 1. Magyarázó feladat

Magyarázza el röviden, mi a különbség a processcrash systemd-coredump útja és a kernelcrash kdump útja között, és mi a build-id szerepe a crash artifact matchingjében. Térjen ki arra, miért nem elegendő a process core dump a kernel oops elemzéséhez.

17.4.5.2 2. Adminisztrációs feladat

A labhost1 labhoston állítsa be a systemd-coredump retention-t úgy, hogy a core fájlok összesen legfeljebb 200 MiB-ot foglalhassanak, és legalább 5 GiB szabad hely maradjon a fájlrendszeren. Hozzon létre egy core dumpot a labcrash programmal, ellenőrizze a coredumpctl list kimenetét és a core fájl jogosultságát, majd távolítsa el a core-t, és ellenőrizze a felszabadult helyet. Adja meg a szükséges parancsokat, a módosítások targetjét és a várható postconditiont.

17.4.5.3 3. Diagnosztikai / recovery feladat

A lab-cpp-service nevű systemd szolgáltatás crash-el, de a coredumpctl list nem mutat core-t. A szolgáltatás unitjában LimitCORE=0 szerepel, és a ulimit -c a service processben 0. Diagnosztizálja a hibát, állítsa be a megfelelő core limitet, indítsa újra a szolgáltatást, triggerelje a crash-t, és ellenőrizze, hogy a core dump megjelenik a coredumpctl listában. Adja meg a szükséges parancsokat és a postconditiont.

17.4.6 Megoldások

17.4.6.1 1. Magyarázó feladat megoldása

A processcrash esetén a kernel a process RLIMIT_CORE figyelembevételével a core_pattern szerint jár el. Alapértelmezésben a systemd-coredump fogadja a core-t, a journalba metaadatot, a /var/lib/systemd/coredump/ alá tömörített core fájlt ír. A build-id a core-hoz tartozó bináris egyedi azonosítója; a readelf -n a binárisból, a coredumpctl info a core-ból mutatja. Az egyezés biztosítja, hogy a GDB a helyes szimbólumokat használja. A kernelcrash esetén a normál core mechanizmus nem működik, mert a kernel nem tud saját magáról core-t generálni. A kdump a crashkernel= memóriafoglalásból indított capture kernellel a teljes kernelmemóriát vmcore-ba menti, amelyet a kernel vmlinux debuginfo-val elemzünk. Ezért a process core dump nem elegendő a kernel oops-hoz.

17.4.6.2 2. Adminisztrációs feladat megoldása

A retention beállítás a /etc/systemd/coredump.conf fájlban történik. A labhost1 hoston root jogosultsággal szerkesszük a fájlt:

[Coredump]
MaxUse=200M
KeepFree=5G
Storage=external
Compress=yes

A rendszer betöltése:

labadmin@labhost1:~$ sudo systemctl reload systemd-coredump

Core dump létrehozása a labcrash futtatásával:

labadmin@labhost1:~$ ./labcrash

Ellenőrzés:

labadmin@labhost1:~$ coredumpctl list
labadmin@labhost1:~$ sudo ls -l /var/lib/systemd/coredump/

A coredumpctl list mutatja a core-t, a ls -l pedig a fájl 0600 jogosultságát. A core eltávolítása a /var/lib/systemd/coredump/ alatti fájl törlésével (a coredumpctl nem rendelkezik remove paranccsal):

labadmin@labhost1:~$ sudo rm /var/lib/systemd/coredump/core.labcrash.*

A törlés után a coredumpctl list már nem mutatja a bejegyzést. A postcondition: a retention limit MaxUse=200M és KeepFree=5G aktív, a core eltávolítva, a tárhely felszabadult.

17.4.6.3 3. Diagnosztikai / recovery feladat megoldása

Először ellenőrizzük a szolgáltatás unitját és a process limitet:

labadmin@labhost1:~$ systemctl cat lab-cpp-service
labadmin@labhost1:~$ cat /proc/$(pgrep -f lab-cpp-service)/limits | grep core

A LimitCORE=0 jelenléte a unitban explicit tiltást jelent. A javításhoz hozzunk létre override-ot:

labadmin@labhost1:~$ sudo systemctl edit lab-cpp-service

A szerkesztőben:

[Service]
LimitCORE=infinity

Ezután töltsük be és indítsuk újra:

labadmin@labhost1:~$ sudo systemctl daemon-reload
labadmin@labhost1:~$ sudo systemctl restart lab-cpp-service

Ellenőrizzük a core_pattern-t és a systemd-coredump állapotát:

labadmin@labhost1:~$ cat /proc/sys/kernel/core_pattern
labadmin@labhost1:~$ systemctl status systemd-coredump

A core_pattern-nek |/lib/systemd/systemd-coredump értékűnek kell lennie. Triggereljük a crash-t a szolgáltatás megfelelő bemenetével, majd:

labadmin@labhost1:~$ coredumpctl list

A listában megjelenik a lab-cpp-service core-ja. A postcondition: a service crash-e esetén core dump keletkezik, a LimitCORE nem nulla, és a core artifact a coredumpctl segítségével elérhető.

17.4.7 Rövid összefoglaló

A processcrash diagnosztikai artifactja a core dump, amelyet a kernel a core_pattern alapján a systemd-coredump-nak ad át; a coredumpctl listázza, dumpolja és GDB-be nyitja. A core-hoz tartozó bináris és szimbólum a build-id alapján egyértelműen azonosítható; a readelf -n és a coredumpctl info egyezése a matching feltétele. A kernelcrash más utat igényel: a kdump crashkernel foglalásból capture kernelt indít, és a vmcore-t menti a kernel vmlinux debuginfo-val való elemzéshez. A core érzékeny adatot tartalmazhat, ezért 0600 jogosultsággal tárolandó, retention és mentési politika mellett.

Továbbhasznált definíciók: core dump – a process address space-ének kernel által kimentett pillanatképe; build-id – az ELF binárisban és a core-ban tárolt egyedi azonosító, amely a matching debuginfo eszköze; kdump – kernelcrash esetén a capture kernelből indított vmcore-mentő mechanizmus.
