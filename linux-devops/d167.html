34.2 KVM, QEMU és libvirt komponensek

34.2.1 Motiváció

Egy virtualizált szolgáltatás hibája gyakran nem a kernel, a CPU vagy a guest Linux alatt van, hanem a virtualizációs réteg rosszul értelmezett határán. A szenior C++ fejlesztő számára a resource lifetime és a syscall réteg természetes: a KVM/QEMU/libvirt stack is hasonlóan rétegelt, de a control plane (menedzsment, XML, daemon) és a data plane (vCPU futtatás, I/O, guest memória) szétválasztása itt különösen fontos. Ha egy VM bootol, a libvirt által beküldött XML config a QEMU processzbe kerül, a QEMU pedig a /dev/kvm ioctl-eszközön át vezérli a kernel virtualizációt. Ez a három komponens – kernel gyorsítás, userspace device model, management réteg – más-más verzióval, permissionnel és diagnosztikai eszközzel rendelkezik.

Az alfejezet célja, hogy a VM indítását ne „virtuális gépként” hanem e három komponens együttműködéseként lásd, és ellenőrizni tud egy hostot, mielőtt VM-et telepítesz rá. A lab parancsok Ubuntu Server 24.04 LTS (amd64) profilt feltételeznek, de a futási kimenetek itt illusztratívak; valós futtatás nélkül a pontos verziókat a labhoston kell ellenőrizni. Aktuális support matrixot és vendor-compatibilitást ez a szöveg nem állít ellenőrzöttnek.

34.2.2 Definíció és komponensmodell

A KVM (Kernel-based Virtual Machine) a Linux kernelbe épülő virtualizációs alrendszer. A KVM a hardveres virtualizációs kiterjesztéseket (Intel VT-x, AMD-V) a /dev/kvm karakteres eszközön keresztül teszi elérhetővé userspace processzeknek. A KVM önmagában nem emulál semmit: vCPU-t, memóriatartományt és I/O exit-eket ad. A guest vCPU futtatása a kernelben történik, amíg egy esemény (pl. privilegizált utasítás, device I/O) ki nem lép a guest módból.

A QEMU (Quick Emulator) egy userspace process. KVM-mel együtt nem teljes emulátor: a guest vCPU-t a KVM futtatja, a QEMU pedig a userspace device modelt, a firmware betöltését, a virtuális chipset (machine type), a PCI busz és az I/O eszközök emulációját adja. KVM nélkül a QEMU lassú, tiszta emulációra képes; KVM-mel a processz minden vCPU-hoz egy-egy szálat indít.

A libvirt egy management réteg: daemon(ok), C API, virsh CLI. Nem a VM futásának adatútja, hanem a control plane-je. A libvirt domain XML-ben definiálja a machine type-ot, firmware-t, CPU modelt, device-okat; ezt lefordítja QEMU parancssorra, elindítja a QEMU processzt, és monitorozza a lifecycle-t. A libvirt nem szükséges a QEMU/KVM futtatásához, de üzemeltethető, auditálható VM-ek esetén a kézzel indított qemu-system-x86_64 parancs helyett ez az ajánlott réteg.

Az adat- és control útvonal explicit szétválasztása:

Útvonal Komponens Mit csinál Interface/példa
Control libvirt daemon domain XML parse, QEMU indítás, lifecycle API virsh start, /var/run/libvirt/
Control QEMU monitor futó VM QMP vezérlés virsh qemu-monitor-command
Control KVM device vCPU/memory/irq létrehozás KVM_CREATE_VM, KVM_CREATE_VCPU ioctl
Data Kernel KVM guest vCPU futás, VM exit /dev/kvm ioctl
Data QEMU device model emulated/virtio I/O, interrupt injection PCI BAR, virtqueue
Data Host kernel/network/storage tényleges I/O syscall read, write, sendmsg

A QEMU processz nem vCPU kernel-szálon fut: a QEMU minden vCPU-hoz egy POSIX szálat hoz létre, amely meghívja a KVM futtatási ioctl-t. A tényleges guest utasításvégrehajtás a kernelben, a vCPU szál kontextusában történik, de a QEMU szál marad a tulajdonos a host processz schedulerében.

34.2.3 KVM, hardveres virtualizáció és nested támogatás

A KVM akkor elérhető, ha a CPU támogatja a hardveres virtualizációt, és a kernelmodul betöltődött. Intel platformon vmx, AMD-n svm flag jelzi. A /dev/kvm node permission-ellenőrzés alatt áll: ha a host user nem tagja a kvm csoportnak, vagy a udev nem hozta létre, a QEMU indítása Operation not permitted hibával megáll.

A nested virtualization lehetővé teszi, hogy egy guest VM-en belül újabb hypervisor fusson (pl. Kubernetes Node virtuális gépben konténerizált VM, vagy oktatólaborban egymásba ágyazott KVM). Ez akkor szükséges, ha a guest operációs rendszernek KVM-et kell használnia. A nested támogatás hardverfüggő, és a host kernelben modulparaméter szabályozza. Intel esetén:

# labhost: labvm1, UID: labuser
cat /sys/module/kvm_intel/parameters/nested

Ha Y az érték, a host kernel engedi a nested VMX-et. AMD-n az nested modulparaméter általában alapból engedélyezett, de a vendor dokumentáció és a support matrix ellenőrzendő. A nested bekapcsolása nem azonos a teljesítménygaranciával: a guest hypervisor megbízhatósága a vendor specifikációtól és a firmware microcode verziótól is függ.

A KVM diagnosztikájához a kernel nyomkövető eszközei (pl. trace-cmd kvm_exit események) használhatók, de a gyakorlati üzemeltetésben előbb a /dev/kvm létezése és a QEMU indítási hibaüzenete adja a leggyorsabb jelet.

34.2.4 QEMU: machine type, firmware, CPU model és device model

A QEMU a -machine paraméterrel választott machine type alapján emulált platformot hoz létre. Az x86-64 fő profil a pc (klasszikus, régi) és a q35 (Intel Q35 chipset, modernebb, PCIe). A machine type verzióspecifikus: a pc-i440fx-8.1 példa a QEMU 8.1-es kiadáshoz tartozó i440fx machine type-ot jelöli. Verzióváltásnál a régi XML-ben rögzített, altípusos machine type nem feltétlenül létezik az új QEMU-ban; ilyenkor a virsh edit vagy virt-install hibaüzenete jelzi az inkompatibilitást.

A firmware a guest boot platformja. Két fő út létezik x86-64-en: a klasszikus SeaBIOS (BIOS) és az OVMF (Open Virtual Machine Firmware), amely UEFI-t biztosít. Az OVMF szükséges UEFI boothoz, Secure Boot-hoz és a modernebb guest OS-ekhez. A libvirt firmware='efi' attribútummal választ UEFI-t; a pontos OVMF build elérési útja a distro edk2 csomagjából származik.

A CPU model azt határozza meg, hogy a guest milyen CPU-szolgáltatásokat lát. A leggyorsabb kompatibilis beállítás a host-passthrough, amely a host CPU modelljét és feature flag-jeit adja át. Ez teljesítményben ideális, de migrációnál és snapshot visszaállításnál akadhat inkompatibilitás, ha a cél host más CPU-val rendelkezik. A named model (pl. qemu64, Nehalem, Skylake-Client) stabilabb CPU-identitást ad, de kevesebb feature-t. A virsh domcapabilities megmutatja, mely modellek elérhetők.

A virtio versus emulated devices kérdés a teljesítmény és a guest driver rendelkezésre állása közötti trade-off. Az emulated device-ok (pl. e1000 hálózati kártya, ide disk) a QEMU userspace device modeljében futnak, és a guest szabványos, beépített driverét használják. A virtio paravirtuális eszközök (virtio-blk, virtio-net, virtio-scsi, virtio-rng) a host kernel/userspace számára hatékonyabb adatutat biztosítanak, de a guest oldalon szükség van a virtio_* driverre. Modern Linux guest ezeket alapból tartalmazza, régi vagy minimális guest nem. A virtio I/O vezérlés a PCI config space és a virtqueue adatszerkezetek között oszlik meg; a QEMU processz tartja karban, a kernel pedig a valós syscall-okkal végzi a tényleges I/O-t.

<!-- Illusztratív libvirt domain device részlet; nem teljes domain -->
<devices>
  <!-- Virtio blokk: hoston qcow2/lemez -->
  <disk type='file' device='disk'>
    <driver name='qemu' type='qcow2'/>
    <source file='/var/lib/libvirt/images/labvm1.qcow2'/>
    <target dev='vda' bus='virtio'/>
  </disk>
  <!-- Emulated hálózat -->
  <interface type='network'>
    <source network='default'/>
    <model type='e1000'/>
  </interface>
</devices>

A virsh dumpxml ezt a desired state-et mutatja; a hoston futó tényleges QEMU parancssor és a /proc-ban látható processz szálak az observed state.

34.2.5 libvirt: daemon, API és virsh control path

A libvirt két fő daemonmodellben létezik: a klasszikus libvirtd és a modular (split) daemonok (virtqemud, virtnetworkd, virtnodedevd stb.). Ubuntu 24.04 LTS a modular daemonokat használhatja a megfelelő csomagokkal. A virsh CLI a libvirt API-t hívja, amely a daemonnal kommunikál a helyi Unix socket-en vagy TCP/TLS remote URI-n keresztül. A data plane soha nem megy a daemonon át: a QEMU processz közvetlenül a kernel és a host erőforrások felé dolgozik, a libvirt csak életciklus-vezérlést ad.

A management permission a control path-on érvényesül. A helyi libvirt sockethez a libvirt csoport tagjai férhetnek hozzá, vagy polkit szabályok engedélyezhetik bizonyos műveletek scope-ját. A root mindig tud kezelni VM-et, de a cél laborban az alacsony jogú labuser számára érdemes a libvirt csoportba kerülni, hogy virsh ne igényeljen sudo-t. A storage pool és network pool hozzáférés is a daemon oldalán szabályozott.

A VM indítás control folyamata:

  1. virsh create vagy virsh start → libvirt API hívás.
  2. A daemon feloldja a domain név → UUID → config file (/etc/libvirt/qemu/).
  3. A daemon validálja az XML-t, ellenőrzi a permissiont.
  4. A daemon QEMU parancssort generál, és elindítja a QEMU processzt, általában libvirt userként vagy root-ként.
  5. A QEMU megnyitja a /dev/kvm eszközt, létrehoz VM-et, vCPU-kat, memóriát.
  6. A QEMU betölti a firmware-t, majd elindítja a guest vCPU-t.
  7. A guest fut; a libvirt csak a monitor socketen át látja az állapotot.

34.2.6 Kidolgozott példa: host capability és machine type ellenőrzés

A példa egy Ubuntu Server 24.04 LTS labhoston fut, labvm1 hostnévvel. A user labuser, aki a lab és kvm csoportok tagja; a sudo szükséges a kernel paraméterek olvasásához. Cél: megállapítani, hogy a host képes-e KVM-alapú VM futtatására, milyen machine type-ok vannak, és a libvirt hozzáférhető-e.

# labhost: labvm1, UID: labuser
# 1. CPU virtualizációs flag és /dev/kvm
grep -E 'vmx|svm' /proc/cpuinfo | head -1
ls -l /dev/kvm
id | tr ',' '\n' | grep -E 'libvirt|kvm'

# 2. KVM modulparaméter (Intel példa; AMD-n kvm_amd)
# UID: labuser, sudo szükséges a /sys olvasásához
sudo cat /sys/module/kvm_intel/parameters/nested
# Várt: Y vagy N

# 3. QEMU által ismert machine type-ok (csak rövid ellenőrzés)
qemu-system-x86_64 -machine help | head
# Várt: Supported machines are: pc ... q35 ... microvm ... none

# 4. libvirt host capabilities (csak a CPU model sorok)
virsh capabilities | grep '<model>' | head
# Várt például: <model>Skylake-Client-noTSX-IBRS</model>

# 5. libvirt domain capability a q35 machine type-ra
virsh domcapabilities --machine q35 | grep -E 'machine|model' | head
# Várt: a kimenet tartalmazza a host által támogatott CPU model-ek és firmware opciókat.

Ellenőrzési feltétel: A /dev/kvm létezik, a user hozzáfér, vmx vagy svm megjelenik, a virsh capabilities nem hibát ad, és a q35 machine type szerepel a QEMU helpben. Ha a virsh „failed to connect to the hypervisor” hibát ad, a daemon nem fut, vagy a user nincs a libvirt csoportban.

A parancsokat e szöveg nem futtatta, ezért a fenti kimenetek várt/illusztratív kimenetek, nem mért eredmények. A tényleges modell, a QEMU machine type verzió és a CPU modell a labhost pillanatnyi állapotától függ.

34.2.7 Hibák és ellenpróbák

1. /dev/kvm hiányzik vagy permission denied. A qemu-system-x86_64 indításakor Could not access KVM kernel module: No such file or directory vagy Permission denied jelenik meg. Ellenőrizd a /dev/kvm létét, a CPU flaget, a kvm és kvm_intel/kvm_amd modul betöltését, és a saját user kvm csoporttagságát. A javítás egy változtatás: a user hozzáadása a kvm csoporthoz, majd új login. Nem szabad a /dev/kvm mode-ját manuálisan, udev szabály nélkül globálisan írhatóvá tenni.

2. A VM bootol, de rendkívül lassú az I/O. A gyakori ok az emulated device (IDE disk, e1000) használata, amikor a guest driver a virtio-t várná, vagy fordítva. Tünet: a guest kernel dmesg-ben unknown device vagy No irq handler for vector; magas host CPU a QEMU processzben. Ellenőrizd a libvirt XML <target dev='vda' bus='...'> és <model type='...'> értékét. Egy változtatás: cserélj ide → virtio blokkot, vagy e1000 → virtio netet, majd restart. A guest oldalon a kernel driver jelenlétét is ellenőrizni kell.

3. Version skew: a libvirt nem tudja elindítani a QEMU-t a rögzített machine type miatt. A virsh start hibaüzenete gyakran: unsupported configuration: machine type 'pc-q35-8.1' is not supported by this QEMU binary. Ez akkor történik, ha a domain XML-ben rögzített machine type-ról a host QEMU csomag már leváltott, vagy a libvirt a régi QEMU verziót keresi. Ellenőrizd virsh edit-tel a domain XML machine type-ját, és a qemu-system-x86_64 -machine help aktuális listáját. Egy változtatás: a machine type frissítése a jelenlegi verziójú pc-q35-... típusra, vagy a domain újradefiniálása --machine nélkül. A guest működése a machine type váltás után nem garantált; snapshot vagy backup előtte szükséges.

4. Nested virtualizáció nem működik a guestben. A guest OS-ben a /dev/kvm hiányzik vagy a hypervisor modul nem töltődik be. A hoston ellenőrizd a nested paramétert. Ha N, a nested engedélyezéséhez modulparaméter átadás szükséges, általában /etc/modprobe.d/kvm.conf létrehozásával, majd a modul újratöltésével. Ez a host szintű változtatás reboot nélküli modulprobe-zás esetén is a futó VM-ekre hatással lehet; a rmmod és modprobe csak üres hoston, karbantartási ablakban végezhető. A labhoston a nested beállítás a dedikált labvm1-re korlátozódik, és dokumentált rollbackként a modulparaméter visszaállítását igényli.

34.2.8 Feladatok

34.2.8.1 1. Magyarázó feladat: rétegtérkép készítése

Rajzold fel szövegesen (táblázatban vagy lépéses adatúttal) egy virsh start labdemo VM indítás folyamatát. Azonosítsd, hogy a kérést melyik komponens fogadja, hol lesz belőle QEMU processz, hol érvényesül a permission, melyik réteg hozza létre a vCPU-t, és hol fut a guest utasításvégrehajtás. Ne írj kódot; a fenti virsh start lépéseket kösd komponensekhez.

34.2.8.2 2. Adminisztrációs feladat: host capability felmérés és hozzáférés

A labvm1 hoston, labuser UID-del ellenőrizd a KVM elérhetőségét, a kvm csoporttagságodat, a támogatott QEMU machine type-ok listáját, és a virsh hozzáférésedet. Ha a libvirt csoport hiányzik a userhez, add hozzá, majd ellenőrizd, hogy virsh list sudo nélkül fut. Rögzítsd egy inventory/host-capability.txt fájlba a kimenetek rövid összefoglalóját: CPU flag, /dev/kvm permission, nested paraméter, QEMU machine type lista első 5 sora, virsh capabilities CPU modell.

34.2.8.3 3. Diagnosztikai feladat: virtio vs emulated device hiba elhárítása

Készíts egy minimális labdemo domain XML-t. Használj deliberately rossz device modellt: a guest OS legyen egy Ubuntu minimal (ha elérhető) vagy más Linux, és a disk bus legyen ide, a hálózati modell e1000. Indítsd el a VM-et, majd figyeld a boot időt és a QEMU processz host CPU-ját. Cseréld a disk bus-t virtio-ra, a hálózati modellt virtio-ra, és hasonlítsd össze. Ha a guest nem bootol a váltás után, ellenőrizd a guest kernel virtio driver jelenlétét. Dokumentáld a desired és observed állapotot, és állítsd vissza az eredeti XML-t, ha nem kívánod megtartani a módosítást.

Ellenőrzés: virsh start labdemo, figyeld a boot időt; a QEMU host CPU terhelése top-ban vagy pidstat-ban a qemu-system-x86_64 processzre. A guest belépés után lspci | grep -iE 'virtio|e1000' vagy dmesg | grep -i virtio. A rollback a virsh destroy labdemo és az eredeti XML visszaállítása.

Postcondition: a módosított VM sikeresen bootol virtio eszközökkel, és a guest látja a virtio_blk/virtio_net driverokat. Ha a guest nem bootol, a hiba valószínűleg a guest kernel hiányzó virtio modulja; ekkor a guest initramfs-be kell a meghajtót beépíteni, vagy marad az emulated device a kompatibilitáshoz.

34.2.10 Rövid összefoglaló

A KVM a Linux kernel virtualizációs gyorsítója, a /dev/kvm ioctl-eszközön át vezérelt vCPU/memória primitívekkel. A QEMU userspace processz biztosítja a device modelt, a firmware betöltést, a machine type-ot és a CPU modellt, valamint a virtio vagy emulated eszközök adatútját. A libvirt a control plane daemon/API: domain XML-ből QEMU parancssort generál, életciklust kezel, de a futó VM adatútja nem halad át rajta. A machine type, firmware, CPU model és eszköztípus közötti version skew a leggyakoribb operatív hibaforrás, ezért a host capability ellenőrzése minden VM provision előtt kötelező.

Továbbhasznált definíciók: KVM — Linux kernelmodul-alapú hardveres virtualizációs réteg; QEMU — userspace emulátor/device model processz, KVM-mel gyorsítva; libvirt — VM lifecycle management daemon és API réteg a control plane-en.
