38.5 Container/Compose működtetési labor

38.5.1 Motiváció

A d189-ben felépített lokális Compose stack (C++ service, proxy és persistens adat) mostantól élesítési gyakorlat alanya. A fejlesztő gyakran csak annyit lát, hogy a container „rossz”, de a javítás akkor lesz gyors és biztonságos, ha a hibát a megfelelő réteghez rendeli: image (tartalom, digest, config), runtime (engine/daemon, containment), host (kernel, cgroup, filesystem) vagy network (bridge, DNS, port). A másik gyakori kudarc: a docker compose down -v törli a named volume-ot, ezért a fejlesztői adat elveszik. A labor célja, hogy ezt a két kockázatot egy data-safe lifecycle keretben gyakoroljuk.

38.5.2 Definíció és működés

Containerhiba rétegelése. A konténeres rendszerben a hívás útja az image-ből indított processzen, a runtime által alkalmazott cgroup/namespace-eken, a host kernel erőforrásain és a hálózati stacken át vezet. A hiba diagnosztizálásánál az első kérdés: melyik réteg tünete a hiba?
- Image/config hiba: a konténer nem indul el, hiányzó fájl, rossz belépési pont vagy rossz environment. Ellenőrzés: docker inspect, docker logs, image history, compose config.
- Runtime hiba: az engine/daemon nem érhető el, vagy a konténer létrehozása után azonnal meghal. Ellenőrzés: docker info, systemctl status docker, docker events.
- Host hiba: a hoston elfogy a lemez, inode, PID, memória, vagy a kernel OOM killer leállítja a processzt. Ellenőrzés: df -h, dmesg, /proc/sys/fs/file-nr, host metrikák.
- Network hiba: a konténer nem éri el a nevet, a portot vagy a külvilágot. Ellenőrzés: docker network inspect, getent hosts, ss -tlnp, curl a bridge IP-címre.

Digest és config-based deployment. A tag helyett digestre pinelés azt jelenti, hogy a compose.yaml-ben az image azonosítója registry/name@sha256:... alakú. Így a pull során pontosan ugyanaz a content kerül minden környezetbe; a tag mozgó célpont. A config verziót gitben tároljuk, a secretet és environmentet nem a képbe sütjük, hanem a compose env vagy .env fájljából adjuk át. A laborban a docker compose config az ellenőrző parancs, mielőtt bármit indítanánk.

Data-safe rebuild és rollback. A docker compose down alapértelmezésben nem törli a named volume-ot. A down -v viszont törli. Data-safe eljárás: mielőtt bármilyen destruktív műveletet végzünk, készítsünk docker volume inspect-et a volume leltárhoz, majd a művelet után smoke testtel bizonyítjuk az adatmegmaradást. A rebuild a down + up -d pár, ahol a volume a régi konténerből az újba költözik. Rollback esetén az image visszacserélése a config-gitből történhet, a volume-ot nem bántjuk.

Resource throttling/OOM. A Compose-ban a mem_limit (Compose v2: deploy.resources.limits.memory is) a konténer cgroup memória limitjét állítja. Amikor a konténer processze átlépi, a kernel OOM killer leállítja. A restart: unless-stopped automatikusan újraindítja. Az OOM eseményt a konténer State.OOMKilled mezője és a kernel log gyűjti. Fontos: az OOM kill nem mindig jelenik meg a konténer saját stdout-jában, a docker inspect segít.

Log/FD/mount inspect. A konténer megfigyeléséhez a docker logs (vagy podman logs) az alkalmazásnaplót, a docker inspect a mountokat, a PID-ből a /proc alrendszer az FD-ket és limiteket mutatja. Példa: docker inspect --format '{{.State.Pid}}' lab-app, majd ls -l /proc/$pid/fd. A mountokhoz: docker inspect --format '{{json .Mounts}}' lab-app.

38.5.3 Kidolgozott példa

Előfeltételek. A d189-ből létezik a lab-compose/ projekt, a saját image-ek a lokális registryben (localhost:5000) elérhetők, és a lab-app rendelkezik egy POST /allocate?size_mb=... tesztvégponttal. A labhost lab-vm1, user labuser, aki a docker csoport tagja. A projekt könyvtár: /home/labuser/lab-compose. A használt tool: Docker Compose v2.

  1. Digest lekérése és config előkészítése.

    # host=lab-vm1; user=labuser
cd /home/labuser/lab-compose
docker pull localhost:5000/lab-app:dev
docker image inspect localhost:5000/lab-app:dev --format '{{.RepoDigests}}'

    Várt kimenet: [localhost:5000/lab-app@sha256:0123...] (a pontos digest a labouran eltér). A kapott digestet írjuk be a compose fájlba:

    # compose.yaml (részlet, a teljes háromszolgáltatásos stack a d189-ből)
name: lab-stack
services:
  lab-db:
    image: localhost:5000/lab-db@${DB_DIGEST}
    environment:
      POSTGRES_USER: lab
      POSTGRES_PASSWORD: labpass
      POSTGRES_DB: labdb
    volumes:
      - lab-db-data:/var/lib/postgresql/data
    networks:
      - lab-net
    mem_limit: 512m
    restart: unless-stopped
  lab-app:
    image: localhost:5000/lab-app@${APP_DIGEST}
    environment:
      DB_HOST: lab-db
      DB_PORT: 5432
      DB_USER: lab
      DB_PASSWORD: labpass
      DB_NAME: labdb
    networks:
      - lab-net
    mem_limit: 256m
    restart: unless-stopped
    depends_on:
      - lab-db
  lab-proxy:
    image: localhost:5000/lab-proxy@${PROXY_DIGEST}
    ports:
      - "127.0.0.1:8081:80"
    networks:
      - lab-net
    mem_limit: 128m
    restart: unless-stopped
    depends_on:
      - lab-app
networks:
  lab-net:
    driver: bridge
volumes:
  lab-db-data:

    Az .env fájl tárolja a digesteket és a jelszót. A docker compose config ellenőrzi az interpolációt.

  2. Indítás és egészségellenőrzés.

    docker compose pull
docker compose up -d
docker compose ps
curl -s http://127.0.0.1:8081/health

    Várt kimenet: a lab-app, lab-proxy Up, lab-db Up, a health válasz {"status":"ok"}.

  3. Network/DNS/port ellenőrzés.

    docker compose exec lab-app getent hosts lab-db
docker network inspect lab-compose_lab-net --format '{{range .Containers}}{{.Name}} {{.IPv4Address}}{{"\n"}}{{end}}'
ss -ltnp | grep 8081

    A lab-db nevet a hálózat feloldja, a 8081-es portot a docker-proxy figyeli.

  4. Volume permission teszt.

    docker compose exec lab-app touch /data/test

    Ha a mount nem írható a konténer UID-jével, Permission denied lesz. A javítás: a volume-ot a megfelelő user/chown vagy user:group beállítással kell indítani. A példában a lab-app rootless módban fut, a /data kötet tulajdonosa 1000:1000.

  5. OOM és restart demonstrálása.
    Állítsuk a lab-app mem_limit értékét 64 MiB-ra a compose fájlban, majd indítsuk újra:

    docker compose up -d lab-app
curl -s -X POST 'http://127.0.0.1:8081/allocate?size_mb=128'
# várható: a konténer OOM-killed lesz, a restart megtörténik
sleep 2
docker inspect lab-app --format '{{.State.OOMKilled}} {{.RestartCount}}'
docker compose logs --tail 20 lab-app

    Várt kimenet: true 1, és a logban a SIGKILL / OOM nyom. A túl alacsony limit visszaállítása után a szolgáltatás stabil.

  6. Data-safe down/up.

    docker compose exec lab-db psql -U lab -d labdb -c "CREATE TABLE IF NOT EXISTS counter(n int); INSERT INTO counter VALUES (42);"
docker compose down
docker volume ls --filter name=lab-db-data
docker compose up -d
docker compose exec lab-db psql -U lab -d labdb -c "SELECT * FROM counter;"

    Várt kimenet: a down után a volume létezik, a SELECT visszaadja a 42 értéket. Ez a data-safe recreate.

  7. Log/FD/mount inspect.

    pid=$(docker inspect --format '{{.State.Pid}}' lab-app)
sudo ls -l /proc/$pid/fd | tail -n 5
cat /proc/$pid/limits | grep 'Max open files'
docker inspect lab-app --format '{{json .Mounts}}' | jq .

    A FD-lista az alkalmazás által nyitott socketeket és fájlokat mutatja; a Max open files tipikusan 1024 vagy több, de a ulimit a compose-ban módosítható.

  8. Runtime inventory és cleanup.

    # inventory
docker system df -v
docker compose ps
docker network ls --filter name=lab-compose_lab-net
docker volume ls --filter name=lab-db-data
# cleanup (csak a labor saját objektumaira; a lab-db-data volume-ot
# csak sikeres, integritásellenőrzött restore után töröljük)
docker compose down
docker compose rm -f
docker volume rm lab-db-data   # figyelem: adatvesztés!
docker network rm lab-compose_lab-net

38.5.4 Hibák és ellenpróbák

Image pull manifest unknown. Tünet: docker compose pull hibaüzenete szerint a digest nem létezik. Ok: a registry-ben nincs ilyen digest, vagy a docker pull régi cache-t használ. Ellenpróba: docker manifest inspect localhost:5000/lab-app@${APP_DIGEST}; ha a manifest hiányzik, a digest elgépelt vagy a push nem sikerült. Javítás: a CI push után újra lekérni a digestet, és a compose fájlt frissíteni.

DNS feloldás sikertelen a lab-db névre. Tünet: a lab-app logjában connection refused vagy could not translate host name. Ellenpróba: docker compose exec lab-app getent hosts lab-db; ha nincs kimenet, a konténerek nem ugyanazon a user-defined networkön vannak. Javítás: a networks szekció minden szolgáltatásnál azonos legyen, vagy a szolgáltatásnevek egyedi DNS-nevek.

Permission denied a volume mountnál. Tünet: a konténer nem tud írni a /data kötetbe. Ok: a hoston a named volume alapból root:root tulajdonú, a konténer processze nem root (pl. USER 1000). Ellenpróba: docker compose exec lab-app id, ls -ld /data. Javítás: a Dockerfile-ban RUN mkdir /data && chown 1000:1000 /data, vagy a compose-ban user: "1000:1000"; rootless Podman esetén a bind mount tulajdonosa a rootless user.

OOM-killed és restart loop. Tünet: a konténer RestartCount növekszik, minden indítás után meghal. Ellenpróba: docker inspect lab-app --format '{{.State.OOMKilled}}'; ha true, a memória limit túl alacsony. Javítás: a mem_limit emelése, vagy a C++ service memóriahasználatának csökkentése. A restart: on-failure explicit max próbálkozással megakadályozza a végtelen ciklust.

Adatvesztés a down -v miatt. Tünet: a down -v után a volume eltűnt. Ellenpróba: docker volume ls --filter name=lab-db-data. Javítás: a d100-ban tanult backupból restore, vagy a labouról készített docker volume export. A megelőzés: soha ne futtassuk a down -v-t mielőtt a backup megerősített.

Port ütközés. Tünet: docker compose up hiba bind: address already in use. Ellenpróba: ss -ltnp | grep 8081. Javítás: a hostport megváltoztatása a compose ports mezőben, vagy a másik processz leállítása.

38.5.5 Feladatok

  1. Réteghez rendelés (magyarázó). Adott négy hibatünet a labor stacken:

    1. docker compose up hiba Cannot connect to the Docker daemon;
    2. a lab-app konténer OOMKilled=true;
    3. curl http://127.0.0.1:8081/health 502 Bad Gateway;
    4. a lab-proxy nem indul, mert a config fájlban hiányzik az upstream lab-app sor.
      Rendelje mindegyiket a megfelelő réteghez (image/config, runtime, host, network), és adja meg az első diagnosztikai parancsot.

  2. Digest-pinelt deployment és OOM (adminisztrációs). Kérje le a lab-app digestjét a lokális registryből, írja be az .env fájlba, indítsa el a stacket, majd állítsa a lab-app memóriakorlátját 64 MiB-ra, és a POST /allocate?size_mb=128 kéréssel igazolja az OOM-killt. Végül állítsa vissza a 256 MiB korlátot, és ellenőrizze a stabilitást curl segítségével.

  3. Data-safe rebuild és FD diagnosztika (diagnosztikai/recovery). Végezzen el egy beszúrást a counter táblába, futtasson docker compose down parancsot, majd up -d-t, és SELECT-tel bizonyítsa, hogy az adat megmaradt. Ezután szimuláljon fájlleíró-szivárgást a lab-app-ben (pl. nyisson meg 100 socketet, de ne zárja be), az ls -l /proc/$pid/fd segítségével mutassa meg a megnövekedett FD-számot, majd állítsa vissza a szolgáltatást a korábbi image digestre, és ellenőrizze, hogy a FD-szám visszaesik.

38.5.6 Megoldások

1. feladat
a) Runtime réteg: a Docker daemon nem fut. Első parancs: systemctl status docker.
b) Host/kernel réteg: a memória limit túl alacsony. Első parancs: docker inspect lab-app --format '{{.State.OOMKilled}} {{.State.RestartPolicy.Name}}'.
c) Network/application réteg: a proxy eléri a portot, de a backend nem egészséges. Első parancs: docker compose ps, docker logs lab-proxy, majd docker compose exec lab-app ss -ltn.
d) Image/config réteg: a proxy image konfigja hibás. Első parancs: docker compose config, majd a proxy konténer docker logs.

2. feladat
Parancsok:

docker pull localhost:5000/lab-app:dev
docker image inspect localhost:5000/lab-app:dev --format '{{.RepoDigests}}'
# A kapott digestet beírjuk .env: APP_DIGEST=sha256:...
docker compose up -d
# mem_limit csökkentés a compose.yaml-ben 64m-re, majd:
docker compose up -d lab-app
curl -s -X POST 'http://127.0.0.1:8081/allocate?size_mb=128'
sleep 2
docker inspect lab-app --format '{{.State.OOMKilled}} {{.RestartCount}}'
# Várt: true 1
# Visszaállítás 256m-re, up -d, curl /health -> {"status":"ok"}

Postcondition: OOMKilled=true és RestartCount>=1 bizonyítja a throttlingot; a visszaállítás után a /health 200-at ad.

3. feladat
Parancsok:

docker compose exec lab-db psql -U lab -d labdb -c "INSERT INTO counter VALUES (7);"
docker compose down
docker volume ls --filter name=lab-db-data
docker compose up -d
docker compose exec lab-db psql -U lab -d labdb -c "SELECT * FROM counter;"
# Várt: a 7-es érték megjelenik.
# FD szivárgás: a lab-app rendelkezik egy /leak-fd?count=100 tesztvégponttal,
# vagy a konténerben futtatunk egy C++ kliensprogramot, amely sok kapcsolatot nyit.
curl -s 'http://127.0.0.1:8081/leak-fd?count=100'
pid=$(docker inspect --format '{{.State.Pid}}' lab-app)
sudo ls -l /proc/$pid/fd | wc -l   # megnövekedett
# Rollback: a korábbi digestre visszaállítás a compose fájlban, majd:
docker compose up -d lab-app
pid=$(docker inspect --format '{{.State.Pid}}' lab-app)
sudo ls -l /proc/$pid/fd | wc -l   # visszaesik

Postcondition: a counter tábla adata megmaradt a down/up után; az FD-szám a szivárgás után nő, a rollback után csökken, ezzel a data-safe és image rollback bizonyított.

38.5.7 Rövid összefoglaló

A konténerhiba megoldása a rétegazonosítással kezdődik: image/config, runtime, host, network. A digestre pinelt deployment kiszámíthatóvá teszi az image-t, a named volume pedig a data-safe restart kulcsa. A laborban a docker compose down megőrzi a volume-ot, a down -v törli, ezért a cleanup előtt mindig ellenőrizni kell a backupot. Az OOM-kill és az FD-szivárgás a host és az alkalmazás rétegét teszi láthatóvá. A gyakorlatban a docker inspect, a docker compose logs, a /proc/PID/fd és a docker volume ls a négy alapvető diagnosztikai pillér.

Továbbhasznált definíciók:
- Layer-scoped container incident: olyan hiba, amelyet az image/config, runtime, host vagy network réteg egyedi tünete alapján osztályozunk.
- Data-safe restart: docker compose down + up -d, ahol a named volume változatlan marad.
- Digest-pinelt deployment: az image azonosítás registry/name@sha256:... formában, ami elkerüli a tag mozgó célpontját.
