10.1 Syscalltól az eszközig: I/O rétegek

10.1.1 Motiváció

Egy szenior C++ fejlesztő számára a fájlba írás gyakran egyetlen write() hívás, amely „sikeresen visszatért”, így az adatot sokan tartósnak hiszik. A Linux rendszerben azonban a write() visszatérése és a médián való tényleges tartósság között több kernelréteg, cache és aszinkron ütemezés van. Ugyanez a rétegződés magyarázza, hogy miért lehet egy write() gyors, míg a hozzá tartozó fsync() nagyon lassú, vagy miért mutat az iostat await magas értéket akkor is, amikor a syscall maga rövid. Ebben az alfejezetben a read/write utat bontjuk VFS, page cache, block layer és driver rétegekre, hogy a késleltetést és a tartósságot a megfelelő rétegekhez tudja rendelni.

10.1.2 Definíció és működés

Az alábbi fogalmakat az I/O út sorrendjében használjuk.

  • File descriptor (FD): processzenkénti egész index, amely egy open file description objektumra mutat.
  • Open file description: a kernelben tárolt megosztott állapot, amely tartalmazza a fájl aktuális offsetjét, open flagjeit (O_APPEND, O_NONBLOCK), valamint a hivatkozást a VFS inode-ra. Ugyanaz a fájl több FD-n keresztül is megnyitható; a dup(), fork() vagy open() másolatok megosztott vagy független open file descriptiont hozhatnak létre.
  • VFS (Virtual File System): közös kernelbeli fájlabsztrakció, amely a file_operations műveleti táblán keresztül dispatcheli a hívást a tényleges fájlrendszer (például ext4, XFS, Btrfs) implementációjára.
  • Page cache: a kernel memóriájában lévő fájloldalak gyűjteménye, amely a buffered I/O alapja. A fájl tartalma oldalanként (jellemzően 4 KiB, THP esetén nagyobb) kerül be a memóriába. A módosított oldal dirty.
  • Block layer, blk-mq: a fájlrendszer bio-kat (block I/O kérelmeket) nyújt be, ezekből a multi-queue blk-mq keret request-eket készít. Az I/O scheduler ezeket a requesteket rendezi, merge-eli és ütemezi.
  • I/O scheduler: blk-mq alatt jellemzően mq-deadline, kyber vagy none; NVMe eszközökön gyakran nincs klasszikus scheduler, mert a device maga is mély queue-t kezel.
  • Device driver és completion: a driver a requestet hardverparanccsá alakítja, DMA-t indít, a befejezést interrupt jelzi. A driver completion callbackje ébreszti fel a várakozó syscallt.

10.1.2.1 Buffered write adatút

A write() hívás a userspace bufferből a kernelbe másol (copy_from_user). Ezután a VFS az open file description aktuális offsetjét használva a fájlrendszer write_iter metódusát hívja. A fájlrendszer a page cache megfelelő oldalait megkeresi vagy allokálja, az adatot a lapokba másolja, a módosított lapokat dirty-nek jelöli. A write() ekkor visszatérhet, mert az adat a kernel memóriájában van; a device még nem feltétlenül látta.

A tartóssághoz explicit szinkronizáció kell: fsync() vagy fdatasync(). Az fsync() a fájl adatait és a szükséges metadatait (például méret, módosítási idő) a device-ra kényszeríti, majd flush parancsot ad, ha a device write cache használatban van. Az fdatasync() a felhasználói adatra és a méretre fókuszál, nem feltétlenül minden metadata. A flush/FUA kérdését Sector, alignment, TRIM és write cache tárgyalja.

10.1.2.2 Read adatút

Olvasáskor a fájlrendszer először a page cache-ben keres. Ha az oldal uptodate, a kernel közvetlenül a lapból másol a userspace bufferbe, és nincs block I/O. Ha cache miss van, a fájlrendszer bio-t nyújt be, a block layer beolvassa a device-ról, a lap bekerül a page cache-be, majd a memória-másolás megtörténik. A beolvasott oldal a cache-ben marad, hogy a következő hozzáférés ne menjen device-ra.

10.1.2.3 Késleltetés rétegenként

Az alábbi táblázat a buffered I/O tipikus késleltetési forrásait rendeli rétegekhez. A tényleges mért értékek labfüggőek, ezért a mérésnél mindig külön kell választani a syscall időt, a page cache állapotot, a block layer queue idejét és a device completion idejét.

Réteg write() latency elem fsync() latency elem
Userspace buffer → kernel copy_from_user CPU-memcpy —
VFS / filesystem operation dispatch, offset, lock dirty oldalak felkutatása
Page cache oldalkeresés, allokáció, másolás writeback indítás
Block layer / blk-mq — (ashszinkron writeback) bio → request késleltetés
I/O scheduler — queue wait, merge, scheduling
Device driver — command submit, interrupt, completion
Device media / write cache — seek/transfer/flush

A write() syscall ideje tehát elsősorban a userspace→kernel másolás, a VFS és a page cache költsége. Az iostat await ezzel szemben a device requestek turn-around idejét mutatja, az avgqu-sz a queue mélységet. A fsync() ideje a dirty oldalak writebackjét, a block layer queue-t, a driver command feldolgozást és a device média/kiolvasási időt egyaránt tartalmazza.

10.1.3 Kidolgozott példa

Cél: megmutatni, hogy egy buffered write() rövid syscall időkkel visszatér, az fsync() viszont a block layer és a device felé szinkronizál, ezért nagyobb késleltetést mutat.

Target: labhost1, labadmin UID 1000, /mnt/lab-data mounted disposable labdisk, write access. Nem root szükséges, csak a labfilesystem jog.

Előfeltétel: /mnt/lab-data mount létezik, a labdisk név szerint kijelölt, a strace csomag telepítve.

# target: labhost1, labadmin (UID 1000)
# előfeltétel: /mnt/lab-data mounted labdisken, write access
# nem destruktív; rollback/cleanup a lab saját lab-write-test.bin fájljára terjed ki
umask 0022
mkdir -p /mnt/lab-data/lab-ioutest
cd /mnt/lab-data/lab-ioutest || exit 1

grep -E 'Dirty|Writeback' /proc/meminfo

strace -T -e trace=write,fsync,fdatasync -o /tmp/lab-ioutest.strace \
  dd if=/dev/zero of=lab-write-test.bin bs=1M count=64 conv=fsync

grep -E 'Dirty|Writeback' /proc/meminfo
grep -E 'write\(|fsync\(|fdatasync\(' /tmp/lab-ioutest.strace
stat -c '%n %s bytes' lab-write-test.bin

# cleanup
rm -f lab-write-test.bin /tmp/lab-ioutest.strace
rmdir /mnt/lab-data/lab-ioutest 2>/dev/null || true

Várható kimenet és ellenőrzés (illusztratív, nem ténylegesen futtatott mérés):

A Dirty érték a write során megnő, majd az fsync() után visszaesik. A strace kimenetében jellemzően 64 write() sor és egy fsync() sor látható:

write(1, "\0\0\0\0..."..., 1048576) = 1048576 <0.000045>
write(1, "\0\0\0\0..."..., 1048576) = 1048576 <0.000038>
...
fsync(1)                  = 0 <0.023100>

Ellenőrzési feltétel: a fájl mérete 67108864 bájt; a trace legalább egy fsync sort tartalmaz; a Dirty a futtatás előtt alacsonyabb, közben magasabb, az fsync után alacsonyabb. Ha a Dirty nem változik, akkor a mérés valószínűleg O_DIRECT vagy write-through mounton fut, vagy a fájlrendszer azonnal flush-el.

Hibajelenség: ha a write() visszatérése -1 EIO, a hiba a block layer/device rétegben keletkezett; ha az fsync hosszú, de a write gyors, akkor a szűk keresztmetszet a writeback/device útban van, nem a CPU-ban.

10.1.4 Tipikus hibák és ellenpróbák

A write() visszatérését tartósságnak tekintik. Tünet: power loss után hiányzó commit. Adatgyűjtés: Dirty oldalak nőnek, fsync nincs a trace-ben. Hipotézis: az alkalmazás nem hív fsync()/fdatasync(), vagy a device write cache nem kap flush-t. Egy változtatás: explicit fsync() a commit ponton. Verifikáció: strace -e trace=fsync mutatja a hívást, és utána a Dirty csökken.

A lassú fsync-et a CPU-ra vezetik vissza. Tünet: a write() pár tíz mikroszekundum, az fsync() több száz milliszekundum. A strace -T megmutatja, hogy a write csak page cache-be ír; az iostat -x a device await és avgqu-sz értékek növekedését mutatja. A hipotézis a device queue vagy a flush költsége. Ellenpróba: conv=notrunc,fdatasync ugyanazon adattal rövidebb, ha csak kisebb metadata kell, de a device flush akkor is benne van.

Partial write kezelés hiánya. A write() kevesebb bájtot is visszatéríthet; a programmal lassan újra kell írni a maradékot. A hiba tünete a csonka fájl, a diagnózis a write() visszatérési érték és a strace mutatja a rövid írást.

O_DIRECT használata helytelen feltételezéssel. Az O_DIRECT kikerüli a page cache-t, de nem ad automatikus FUA-t, és alignment/len megkötései vannak. A tartóssághoz O_DIRECT mellett is fsync() kell, ha a device write cache aktív. Ez összhangban van a d023 write cache szerződésével.

10.1.5 Feladatok

10.1.5.1 1. Réteg–késleltetés hozzárendelés (magyarázó szint)

Adott egy buffered write() + fsync() folyamat és az iostat -x kimenet await/avgqu-sz értéke. Készítsen táblázatot, amely hozzárendeli a következő megfigyeléseket a megfelelő rétegekhez: write() syscall idő, fsync() syscall idő, Dirty oldalak, iostat await, avgqu-sz. Indokolja, miért nem jelenik meg a write() késleltetés az await-ben.

10.1.5.2 2. Rétegelt mérés a labhoston (adminisztrációs/konfigurációs szint)

A labhost1 labhoston, labadmin UID 1000, /mnt/lab-data labdisken hozzon létre egy lab-write-test.bin nevű labfájlt. Mérje strace -T-vel a write és fsync syscall időket; rögzítse a Dirty/Writeback állapotot a write előtt, a write közben és az fsync után; ellenőrizze a fájlméretet. Tisztítsa a saját labfájlját. A jegyzőkönyvben nevezze meg, melyik megfigyelt érték melyik réteghez tartozik.

10.1.5.3 3. Lassú write/elveszett adat diagnosztika (diagnosztikai/failure/recovery szint)

Egy laboralkalmazás arról számol be, hogy a commit power cut után elveszik, és a fsync() nagyon lassú. Gyűjtsön strace -T, /proc/meminfo és iostat -x 1 adatokat. Állapítsa meg, mi a legvalószínűbb réteg (page cache, block layer queue, driver/device, flush). Hajtson végre egy ellenőrzött változtatást: például fdatasync kontroll vagy a device write cache/FUA viselkedés vizsgálata. Verifikálja a méréssel, és fogalmazza meg a tartóssági szerződést a write() visszatérés és az fsync() siker között.

10.1.6 Megoldások

10.1.6.1 1. megoldás

A write() syscall idő a userspace→kernel másolás, VFS dispatch és page cache allokáció/másolás rétegéhez tartozik. A fsync() idő a dirty oldalak writebackjéből, a block layer/blk-mq queue-ból, a scheduler döntéséből, a driver parancskezelésből és a device flush/media idejéből áll. A Dirty oldalak a page cache writeback állapotát mutatják. Az iostat await és avgqu-sz a block layer/device request completion idejét, illetve a queue mélységet írják le. A write() nem jelenik meg az await-ben, mert a buffered write a page cache-be ír, és a device request csak később, a writeback során keletkezik.

10.1.6.2 2. megoldás

A mérés parancsa megegyezik a kidolgozott példában lévővel; a Dirty nő a write közben, az fsync után csökken. A strace write sorok rövidek, az fsync nagyobb. Ez a page cache jelenlétét és a block layer eszközszintű szinkronizációját igazolja. A jegyzőkönyv postconditionje: a lab-write-test.bin és /tmp/lab-ioutest.strace törölve, a /mnt/lab-data mount tartalma eredeti, a mérési adatok a jegyzőkönyvben rögzítve.

10.1.6.3 3. megoldás

Az adatvesztés oka: a write() csak a page cache-be másol, és power loss előtt nincs fsync/FUA, a device write cache tartalma elveszhet. A lassú fsync esetén az iostat await és avgqu-sz magas; ez a block layer/device réteget teszi felelőssé. A változtatás: a commit ponton fdatasync() és szükség esetén FUA, vagy a device write cache beállítás vizsgálata. Verifikáció: a trace-ben megjelenik a fdatasync, a Dirty csökken, az await a várható device időt mutatja. A tartóssági szerződés: write() sikere = az adat a kernel page cache-ben; fsync/fdatasync sikere = a device tartóssági pontján van, feltéve, hogy a flush/FUA parancsot a device megerősítette.

10.1.7 Rövid összefoglaló

A Linux fájlműveletek útja a userspace buffertől a VFS-en, a page cache-en, a block layeren és a driveren keresztül a device médiáig tart. A write() visszatérése nem tartósság, csak annyit jelent, hogy az adat a kernel page cache-ben van; a tartóssághoz fsync()/fdatasync() és szükség szerint flush/FUA kell. A késleltetést rétegenként kell értelmezni: a buffered write leginkább a másolás és page cache költsége, az fsync a writeback, block queue, driver és device flush költsége. Az iostat await a device request completiont mutatja, nem a write() syscall idejét.

Továbbhasznált definíciók:

  • Page cache: a kernel memóriájában lévő fájloldal-gyűjtemény, amely a buffered I/O alapja.
  • Open file description: a VFS által használt megosztott állapot, amely az offsetet és az open flagjeit tartalmazza.
  • bio: a fájlrendszertől a block layer felé benyújtott blokkos I/O kérelem, amelyből a blk-mq request keletkezik.
