25.5 VLAN/bridge/bonding diagnosztikai labor

25.5.1 Működtetési cél és a labor szerződése

Egy sikertelen ping nem mondja meg, hogy hibás VLAN-tagság, hibás címzés, túl kicsi MTU vagy megszakadt kapcsolat okozza-e a kiesést. Ebben a laborban ugyanazt az adatútvonalat konfigurációból, továbbítási állapotból és csomagrögzítésből is ellenőrzöd. A változtatások menetét a Működtetési szerződés, runbook és változtatás, a hurokmentesség és a kapcsolatredundancia alapjait az STP, loop és LACP/bonding adja.

Az L2 működtetési szerződés meghatározza, hogy egy port milyen kereteket fogadhat, azokat melyik VLAN-ba sorolja, merre továbbíthatja, és kilépéskor legyen-e VLAN-címke. Ehhez hozzátartozik az MTU, a hurokmentesség és a linkhiba utáni elvárt működés is.

Minden alábbi kimenet várt vagy illusztratív, nem tényleges mérési eredmény.

Tétel Laborérték
Target és jogosultság lab-l2 nevű, izolált Ubuntu Server 24.04 LTS amd64 VM; UID 0, Bash
Eszközök Előre telepített iproute2, iputils-ping, tcpdump, coreutils
Kernel-előfeltétel Bridge, veth és bonding elérhető; a bonding driver előzetesen max_bonds=0 beállítással betöltve
Tulajdonos, lejárat A labor végrehajtója; törlés a munkamenet végén
Erőforrások Négy névtér és /run/lab-d125; nincs fizikai interfész vagy hostbridge csatlakoztatva
Konfigurációforrás Az alábbi laborleírás és parancssorozat
Tárolt állapot Hálózati állapot a kernelben; megfigyelések a /run/lab-d125 könyvtárban
Visszaút VM-konzol; az egyedi módosítások visszaállítása, végső esetben a név szerint felsorolt laborobjektumok törlése

Ez futásidejű konfiguráció, nem persistens hálózati beállítás. A VM hálózatkezelőjét nem módosítjuk.

25.5.2 Topológia és elvárt adatút

A hálózati névtér (network namespace) saját interfész-, cím-, útvonal- és szomszédállapotot biztosít. Az összeköttetéseket virtuális Ethernet-párok, azaz veth eszközök adják.

Forrás/interfész Összeköttetés Cél/interfész Portszerep
lab-a/lab-a0 veth lab-s1/lab-pa VLAN 10 access, címkézetlen
lab-s1/lab-t1 veth lab-s2/lab-t2 VLAN 10 és 20 trunk, címkézett
lab-s2/lab-pb0 veth lab-b/lab-b0 VLAN 10 access, elsődleges bondtag
lab-s2/lab-pb1 veth lab-b/lab-b1 VLAN 10 access, tartalék bondtag

Mindkét switch-névtérben egy lab-br0 Linux bridge működik. A lab-b0 és lab-b1 a lab-bond0 active-backup bond tagja.

  • Forrás: lab-a, 10.125.10.1/24, MAC 02:00:00:25:10:01.
  • Cél: lab-b, 10.125.10.2/24, bond-MAC 02:00:00:25:10:02.
  • Nincs alapértelmezett útvonal vagy router: a két végpont közvetlenül, ARP segítségével kommunikál.
  • A VLAN 20 csak a trunk engedélyezési listáján szerepel; végpont nélkül nem bizonyítjuk a teljes VLAN 20 adatútját.

A címütközés ellenőrzési tartománya ez az izolált hálózat. A létrehozáskor mindkét végpontnévtér globális IPv4-címlistájának üresnek kell lennie. A host azonos privát címtartománya önmagában nem ütközés, mert nincs összeköttetés.

Adatút: címkézetlen keret → access port PVID 10 → bridge VLAN 10 → trunkon 802.1Q-címke → második bridge VLAN 10 → címke eltávolítása → aktív bondtag.

25.5.3 Kidolgozott példa: felépítés

Az alábbi blokkok ugyanabban a root Bash-munkamenetben futtatandók. Már létező labornevek esetén állj meg; ne foglalj el ismeretlen tulajdonú objektumot.

# Target: lab-l2 VM; UID 0. Kizárólag a felsorolt új laborobjektumok.
set -euo pipefail
test "$(hostname -s)" = lab-l2
test "$(id -u)" -eq 0

for tool in ip bridge ping tcpdump timeout; do
    command -v "$tool" >/dev/null
done

for ns in lab-a lab-s1 lab-s2 lab-b; do
    test ! -e "/run/netns/$ns"
done
test ! -e /run/lab-d125

umask 077
mkdir /run/lab-d125
{
    hostname
    uname -r
    dpkg-query -W iproute2 iputils-ping tcpdump coreutils
} > /run/lab-d125/lab-profile.txt

for ns in lab-a lab-s1 lab-s2 lab-b; do
    ip netns add "$ns"
    ip -n "$ns" link set lo up
done

# Várt kimenet: mindkettő üres.
ip -n lab-a -4 address show scope global
ip -n lab-b -4 address show scope global

ip -n lab-a link add lab-a0 type veth peer name lab-pa netns lab-s1
ip -n lab-s1 link add lab-t1 type veth peer name lab-t2 netns lab-s2
ip -n lab-b link add lab-b0 type veth peer name lab-pb0 netns lab-s2
ip -n lab-b link add lab-b1 type veth peer name lab-pb1 netns lab-s2

for ns in lab-s1 lab-s2; do
    ip -n "$ns" link add lab-br0 type bridge \
        vlan_filtering 1 vlan_default_pvid 0 stp_state 0
    ip -n "$ns" link set lab-br0 up
done

lab_access() {
    ip -n "$1" link set "$2" master lab-br0
    ip netns exec "$1" bridge vlan add dev "$2" vid 10 pvid untagged
    ip -n "$1" link set "$2" up
}
lab_access lab-s1 lab-pa
lab_access lab-s2 lab-pb0
lab_access lab-s2 lab-pb1

for spec in "lab-s1 lab-t1" "lab-s2 lab-t2"; do
    read -r ns port <<< "$spec"
    ip -n "$ns" link set "$port" master lab-br0
    for vid in 10 20; do
        ip netns exec "$ns" bridge vlan add dev "$port" vid "$vid"
    done
    ip -n "$ns" link set "$port" up
done

ip -n lab-a link set lab-a0 address 02:00:00:25:10:01
ip -n lab-a address add 10.125.10.1/24 dev lab-a0
ip -n lab-a link set lab-a0 up

ip -n lab-b link add lab-bond0 address 02:00:00:25:10:02 \
    type bond mode active-backup miimon 100
for port in lab-b0 lab-b1; do
    ip -n lab-b link set "$port" master lab-bond0
    ip -n lab-b link set "$port" up
done
ip -n lab-b link set lab-bond0 type bond \
    primary lab-b0 primary_reselect always
ip -n lab-b address add 10.125.10.2/24 dev lab-bond0
ip -n lab-b link set lab-bond0 up

A vlan_default_pvid 0 szándékos: nincs automatikusan engedélyezett VLAN 1. Az access portokon a pvid a címkézetlen bejövő keretek VLAN-besorolását, az untagged a kimenő címke eltávolítását határozza meg. Ezek külön tulajdonságok.

A bridge-eken nincs IP-cím, ezért ebben az adatútban nem kell VLAN-tagságot adni a bridge saját, self portjának.

25.5.4 Konfiguráció, FDB és csomagbizonyíték

A továbbítási adatbázis (forwarding database, FDB) a megtanult forrás-MAC-címeket kapcsolja porthoz. VLAN-aware bridge esetén a VLAN-azonosító is része a keresési kulcsnak. Egy FDB-bejegyzés azonban csak tanult állapot, nem teljes elérhetőségi bizonyíték.

# Target: lab-l2; UID 0; az előbb létrehozott névterek.
ip netns exec lab-a ping -n -c 3 -W 1 10.125.10.2
ip netns exec lab-s1 bridge vlan show
ip netns exec lab-s2 bridge vlan show
ip netns exec lab-s1 bridge fdb show br lab-br0
ip netns exec lab-s2 bridge fdb show br lab-br0
ip netns exec lab-b cat /proc/net/bonding/lab-bond0
Konfiguráció / kívánt állapot Megfigyelés Postcondition
Access: VLAN 10, PVID, untagged bridge vlan show lab-pa, lab-pb0, lab-pb1: 10 PVID Egress Untagged
Trunk: VLAN 10 és 20, tagged Ugyanott lab-t1, lab-t2: mindkét VID, untagged jelző nélkül
VLAN-szűrés bekapcsolva ip -d link show lab-br0 a megfelelő névtérben vlan_filtering 1
Bond elsődleges tagja lab-b0 /proc/net/bonding/lab-bond0 Active-backup mód, aktív tag lab-b0
Tanult cél-MAC, VLAN 10 FDB forgalom után lab-s1: lab-t1; lab-s2: lab-pb0
Végponti kapcsolat ICMP-próba Három válasz, laborban várt nulla csomagvesztés

Az FDB saját és állandó multicast-bejegyzéseit ne keverd össze a végpontok dinamikusan tanult címeivel.

Most ugyanazt a forgalmat az access és a trunk oldalon is rögzítsük:

# Target: lab-l2; UID 0. Két időben korlátozott capture.
timeout 8 ip netns exec lab-s1 \
    tcpdump -l -eni lab-pa -c 6 'arp or icmp' \
    > /run/lab-d125/lab-access.txt &
lab_cap_access=$!

timeout 8 ip netns exec lab-s1 \
    tcpdump -l -eni lab-t1 -c 6 'vlan 10 and (arp or icmp)' \
    > /run/lab-d125/lab-trunk.txt &
lab_cap_trunk=$!

sleep 1
ip netns exec lab-a ping -n -c 3 -i 0.2 -W 1 10.125.10.2
wait "$lab_cap_access"
wait "$lab_cap_trunk"
cat /run/lab-d125/lab-access.txt /run/lab-d125/lab-trunk.txt

Várt fixture:

Megfigyelési pont Dekódolt keret
lab-pa Ethernet → IPv4 → ICMP; nincs 802.1Q-címke
lab-t1 Ethernet → 802.1Q, vlan 10 → IPv4 → ICMP

A timeout 124-es kilépése nem sikeres capture-ellenőrzés: nem gyűlt össze időben hat megfelelő csomag. Ellenőrizd a szűrőt, a capture indulását és az adatút működését.

Fizikai NIC-nél a VLAN-offload és a capture helye befolyásolhatja a címke láthatóságát. A címke hiányából önmagában ne következtess hibás trunkra; vesd össze a konfigurációval és a link másik oldalán készült felvétellel.

25.5.5 Bond failover és a bizonyíték határa

Az active-backup bond egyszerre egy aktív tagon továbbít. A miimon 100 névleges, 100 ms-os linkállapot-ellenőrzést kér; ez nem 100 ms-os szolgáltatás-helyreállítási garancia.

A switcholdali veth-vég leállítása a bondtag carrier-vesztését modellezi. Nem modellezi azt a hibát, amikor a link feljön, de egy távoli switch már nem továbbít.

# Target: lab-l2; UID 0. Előfeltétel: hibamentes baseline.
ip netns exec lab-a ping -n -i 0.1 -c 40 -W 1 10.125.10.2 \
    > /run/lab-d125/lab-failover.txt &
lab_probe=$!

sleep 1
ip -n lab-s2 link set lab-pb0 down
sleep 0.5
ip netns exec lab-b cat /proc/net/bonding/lab-bond0
ip netns exec lab-s2 bridge fdb show br lab-br0

if wait "$lab_probe"; then
    echo "A próbasorozat sikeres kilépéssel végződött."
else
    echo "Nem nulla ping exit status: vizsgáld a veszteséget."
fi
cat /run/lab-d125/lab-failover.txt

# Rollback: az elsődleges út helyreállítása.
ip -n lab-s2 link set lab-pb0 up
sleep 1
ip netns exec lab-b cat /proc/net/bonding/lab-bond0
ip netns exec lab-a ping -n -c 3 -W 1 10.125.10.2

Hiba közben az aktív tag várhatóan lab-b1, a cél-MAC FDB-portja pedig lab-pb1. Helyreállításkor az always elsődleges-visszaválasztási szabály miatt ismét lab-b0 várható.

Jegyezd fel a hiányzó ICMP-sorszámokat és a veszteségi arányt. A 100 ms-os próbaintervallum mellett nulla elveszett csomag sem bizonyít nulla idejű kiesést. A ping RTT-je, a próbaintervallum és az egy másodperces válaszvárási timeout külön mennyiség.

Hipotetikus flow-limit: két, egyenként C=1Gbit/sC=1\ \mathrm{Gbit/s} link esetén:

Mód Egy adatfolyam felső korlátja Összes adatfolyam együttes felső korlátja
Active-backup CC CC
Helyesen kialakított 802.3ad, megfelelő flow-elosztással Jellemzően CC Legfeljebb 2C2C

Ezek linksebesség-korlátok; a hasznos adatsebesség az overhead miatt kisebb. A hash-alapú elosztás nem garantál egyenletes terhelést. A labor Linux bridge-e nem LACP-partner, ezért puszta bondmód-váltással nem lesz működő 802.3ad aggregáció.

A két bondtag ugyanahhoz a virtuális switchhez és hosthoz tartozik: ez linkhiba-tűrési próba, nem switch- vagy hostredundancia.

25.5.6 MTU, mismatch és hurokveszély

Az IPv4 ICMP Echo-próba mérete opciók nélkül:

LIP=20B+8B+Ladat. L_{\mathrm{IP}} = 20\ \mathrm{B} + 8\ \mathrm{B} + L_{\mathrm{adat}}.

1500 B interfész-MTU mellett tehát 1472 B ICMP-adat fér el. A VLAN-címke további 4 B az Ethernet-keretben, de nem része az IP-MTU-nak; ezért nem automatikusan 1468 B a helyes adatméret.

Tünet / fixture Hipotézis Ellenpróba
A trunkon látható VLAN 10, a túloldali access porton nincs kérés Hiányzó VLAN-tagság Mindkét trunk és az access port VLAN-listája
Az egyik trunk címkézetlenül küld; a másikon nincs PVID Egress-tagging mismatch Kétoldali capture és PVID/Egress Untagged összevetése
Kis ping működik, nagy timeoutol Köztes MTU-korlát DF-es méretsöprés, portonkénti MTU
Bondtag UP, de nincs célválasz A carrier nem bizonyít teljes adatutat Capture a hibahatár két oldalán

Egy tisztán L2 bridge nem fragmentálja az IP-csomagot. Túl nagy keret eldobásakor nem támaszkodhatsz routertől származó ICMP MTU-visszajelzésre.

Hurokveszélyes topológiafixture: ha a két bridge közé második párhuzamos trunk kerül, zárt L2 út keletkezik. A jelenlegi stp_state 0 mellett broadcastvihar és MAC-flapping jelentkezhet. Ezt a második trunkot itt nem hozzuk létre. Ilyen kísérlet csak elkülönített, erőforrás-korlátozott VM-ben, konzollal és előre megtervezett megszakítással végezhető; hurokmentes működéshez a redundáns portok felhozása előtt STP-t kell konfigurálni és a blokkoló állapotot ellenőrizni. A bond két végponti kapcsolata nem ilyen hurok: a végpont nem bridge a két tag között.

25.5.7 Feladatok

  1. Magyarázat: miért nincs VLAN-címke az access capture-ben? Miért nem jelent kétszeres sávszélességet az active-backup bond? Mely közös hibaterület marad meg?
  2. Adminisztráció: tiszta baselineból állítsd a lab-s1/lab-t1 MTU-ját 1400 B-ra. Vizsgáld a 1372 és 1472 B ICMP-adatméretet DF mellett, majd állítsd vissza a konfigurációt.
  3. Diagnosztika és recovery: töröld kizárólag a VLAN 10 tagságát a lab-s2/lab-t2 portról. Capture-rel és konfigurációval azonosítsd a hibahatárt, majd egyetlen célzott módosítással javítsd.

25.5.8 Megoldások

1. Az access port kilépéskor eltávolítja a címkét, belépéskor pedig PVID alapján VLAN-ba sorol. Az active-backup egyszerre egy aktív továbbítási utat használ. A switch-névtér és a teljes VM közös hibaterület marad.

Postcondition: külön meg tudod nevezni a port szemantikáját, a kapacitáskorlátot és a demonstrált redundancia határát.

2. A 1400 B IP-csomag még elfér; az 1500 B-os a csökkentett MTU-jú útvonalon várhatóan elvész.

# Target: lab-l2; UID 0; csak lab-s1/lab-t1 módosul.
ip -n lab-s1 link set lab-t1 mtu 1400
ip -n lab-s1 link show lab-t1
ip netns exec lab-a ping -4 -n -M do -s 1372 -c 3 -W 1 10.125.10.2
ip netns exec lab-a ping -4 -n -M do -s 1472 -c 3 -W 1 10.125.10.2 \
    || echo "A nagy csomag próbája nem sikerült; ez a várt hibatünet."

# Rollback és verification.
ip -n lab-s1 link set lab-t1 mtu 1500
ip -n lab-s1 link show lab-t1
ip netns exec lab-a ping -4 -n -M do -s 1472 -c 3 -W 1 10.125.10.2

Postcondition: az MTU ismét 1500 B, és a nagy próba is sikeres. A helyi, eleve túl nagy csomag küldési hibáját különböztesd meg a köztes eldobás miatti timeouttól.

3. A hibainjektálás és visszaállítás:

# Target: lab-l2; UID 0; tiszta baseline, egyszerre egy hiba.
ip netns exec lab-s2 bridge vlan del dev lab-t2 vid 10
ip netns exec lab-s2 bridge vlan show dev lab-t2
ip netns exec lab-a ping -n -c 3 -W 1 10.125.10.2 \
    || echo "A kapcsolat hibája most várt."

# A bizonyítékgyűjtés után: célzott rollback.
ip netns exec lab-s2 bridge vlan add dev lab-t2 vid 10
ip netns exec lab-s2 bridge vlan show dev lab-t2
ip netns exec lab-a ping -n -c 3 -W 1 10.125.10.2

A korábbi capture-parancsokat lab-s2/lab-t2, illetve az aktuális aktív access port megfigyelésére alkalmazva a beérkező VLAN 10 keret még látható lehet, miközben nincs access oldali továbbítás. A régi FDB-bejegyzés nem cáfolja a hibát: a VLAN-tagság ettől független feltétel.

Postcondition: VLAN 10 tagged tagság helyreállt, VLAN 20 változatlan, a végponti próba és a tagelési ellenőrzés sikeres.

25.5.9 Cleanup

A bizonyítékokat szükség esetén előbb másold ki. Az összes időkorlátos capture és próba fejeződjön be; névtérben maradt folyamat esetén ne folytasd automatikusan a törlést.

# Target: lab-l2; UID 0. Csak ennek a labornak a saját objektumai.
for ns in lab-a lab-s1 lab-s2 lab-b; do
    if test -e "/run/netns/$ns"; then
        test -z "$(ip netns pids "$ns")"
    fi
done
for ns in lab-a lab-s1 lab-s2 lab-b; do
    if test -e "/run/netns/$ns"; then
        ip netns del "$ns"
    fi
done

rm -f /run/lab-d125/lab-profile.txt \
      /run/lab-d125/lab-access.txt \
      /run/lab-d125/lab-trunk.txt \
      /run/lab-d125/lab-failover.txt
rmdir /run/lab-d125
ip netns list

A névterekkel a bennük lévő bridge-, bond- és veth-eszközök is megszűnnek. Ellenőrzési feltétel: a négy labornév nincs a listában.

25.5.10 Rövid összefoglaló

Az L2 diagnosztika három bizonyítékot kapcsol össze: a portok konfigurációját, a tanult továbbítási állapotot és a tényleges keretutat. A sikeres kis ping nem igazolja a teljes MTU-tartományt, az FDB-bejegyzés nem igazolja a VLAN-tagságot, a carrier pedig nem igazolja a távoli elérhetőséget. A laborban célzott VLAN- és MTU-módosítás után ugyanazzal a próbával kell ellenőrizni a helyreállást. A bondteszt linkhiba-tűrést demonstrál, nem sávszélesség-összeadást vagy független switchredundanciát. A bizonyítékhoz mindig őrizd meg a kernel- és csomagprofilt is.

  • PVID: címkézetlen bejövő keretek alapértelmezett VLAN-besorolása.
  • FDB: MAC/VLAN alapján portot meghatározó továbbítási adatbázis.
  • Active-backup: egy aktív taggal működő, tartalék kapcsolatra átváltó bonding mód.
