50.4 OpenTelemetry, distributed trace és C++ instrumentation

50.4.1 Motiváció: a lassú hibás request láthatósága

A [d141] fejezet HTTP-kérések kapcsolódási, caching- és statusz-szintű viselkedését vizsgálta. A [d248] központi logplatform abban segít, hogy egy-egy szolgáltatás eseményeit kereshetővé tegye. Egy több C++ szolgáltatásból álló kéréspályán azonban a logok gyakran nem hordozzák az ok-okozati láncot: a gateway-nél látott 800 ms-os válaszidőt nem tudjuk összerendelni azzal, hogy az order service a payment hívással várakozott-e, vagy a saját adatbázis-lekérdezése volt lassú. A metrikák aggregáltan mutatják a hibákat, de nem mutatják, hogy egy adott request_id melyik service-ben bukott el. Ezt a hiányt a elosztott nyomkövetés (distributed tracing) célozza: a kérés útját egyedi azonosítóval, műveleti szegmensekkel és időbélyegekkel követi.

50.4.2 Definíciók és működés

A trace (nyomvonal) egy adott kéréshez tartozó műveletfolyam irányított, általában fagráfként ábrázolható felvétele. A gyökértől a levelekig minden csomópont ugyanazt a trace_id-t hordozza.

A span egy névvel ellátott, start- és end-időbélyeggel rendelkező műveleti időintervallum. Egy span minimálisan az alábbiakat tartalmazza:

Mező Szerep
trace_id A teljes kérés nyomvonal-azonosítója.
span_id Az adott span egyedi azonosítója a trace-en belül.
parent_span_id A szülő span azonosítója; gyökéresetben üres.
name Alacsony kardinalitású műveletnév, például OrderService.ProcessOrder.
start / end Monoton órából származtatott időtartam; a end - start adja a duration-t.
status Unset, Ok vagy Error; a span logikai sikerét jelzi.
attributes Kulcs-érték párok szabályozott, alacsony kardinalitású metaadatokhoz.
events Időbélyegzett, span-on belüli események, például egy retry pillanata.

A trace context a terjesztéshez szükséges minimális állapot: trace_id, span_id, trace_flags és opcionálisan tracestate. A context nem maga a span; a span a helyi SDK-ban élő felvételi objektum.

A propagation a context átadása szolgáltatásközi híváskor. A hívó oldalon inject, a hívott oldalon extract művelettel kerül a hordozóba, általában HTTP-fejlécbe vagy üzenet-metadatába. A W3C Trace Context szabvány ezt a HTTP-fejlécet definiálja:

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01

Formátuma version-trace_id-parent_id-trace_flags. A trace_id 32 hex, a parent_id 16 hex, a trace_flags itt 01, tehát sampled. Ha a flag 00, a downstream span creation nem rögzítendő, kivéve ha explicit felülbírálás történik.

A baggage külön W3C fejléc, például:

baggage: tenant=acme;environment=staging

Ez explicit üzleti kontextus továbbítása, nem telemetriai azonosító. Biztonsági és adatvédelmi szerződés kell hozzá: a baggage a downstream minden szolgáltatása számára látható, így jelszó, token vagy azonosítható ügyféladat nem kerülhet bele.

A sampling (mintavételezés) döntés arról, hogy egy spant megtartsunk, exportáljunk-e. A head-based sampling a trace keletkezésekor, a gyökér spanban dönt; a döntést a trace_flags továbbítja. Ez olcsó, de nem látja a kérés kimenetelét: egy ritka hiba kimaradhat. A tail-based sampling később, jellemzően az OpenTelemetry Collectorban dönt, amikor a teljes trace beérkezett. Ez lehetővé teszi „tartsd meg az Error státuszú vagy 500 ms feletti latency-vel rendelkező trace-eket” politikát, de átmeneti pufferezést és nagyobb erőforrást igényel. Ha a döntés nem megtartás, a span dropped: nem kerül tárolóba, nem kérdezhető le.

Az OpenTelemetry (OTel) komponensek API, SDK, Collector és OTLP rétegre bontják ezt a folyamatot. Az API a C++ kódban használt interfész; az SDK implementálja a sampler-t, context propagationt, batch-elt exportot. Az OTLP protokoll a telemetriai adatközlés hálózati formátuma, tipikusan gRPC vagy HTTP/JSON. A Collector receiver/processor/exporter pipeline-t futtat: OTLP-n fogad, samplinget, redakciót vagy konverziót végez, majd továbbít storage felé.

50.4.3 C++ instrumentation és az eszközhatár

A C++ fejlesztőnek itt nem az OTel SDK újratanítása a cél, hanem a telemetriai határ megértése. Az alkalmazás akkor lesz jól instrumentált, ha a műveleti határokat explicit span-né alakítjuk: HTTP-bemenet, kimenő hívás, adatbázis-lekérdezés, várólista-művelet. Az OTel C++ SDK ezt a feladatot nem végzi el automatikusan; a HTTP-kliens, gRPC vagy adatbázis-könyvtár instrumentációja vagy elérhető beépített library-ként, vagy saját wrapper span-nel oldjuk meg. Utóbbi esetben a propagation-t a saját hívási kódunkban kell elvégezni.

A fogalmi vázlat alább látható; a pontos include-ok, osztálynevek és factory-hívások az opentelemetry-cpp aktuális stabil release-től függnek, ezért éles build előtt verifikálni kell az adott verzió headerjeit:

// Fogalmi vázlat, nem ellenőrzött opentelemetry-cpp API-release-re.
#include <opentelemetry/trace/provider.h>
#include <opentelemetry/context/propagation/global_propagator.h>
#include <opentelemetry/trace/semantic_conventions.h>

auto provider = opentelemetry::trace::Provider::GetTracerProvider();
auto tracer = provider->GetTracer("lab-order-service", "1.0.0");

// Bemenő HTTP-kérésből W3C traceparent kinyerése
auto parent_ctx = opentelemetry::context::propagation::GetTextMapPropagator()
                      ->Extract(request.headers());
trace::StartSpanOptions options;
options.parent = parent_ctx;

auto span = tracer->StartSpan(
    "PaymentService.Authorize",
    {{trace::SemanticConventions::kRpcSystem, "http"},
     {trace::SemanticConventions::kServerAddress, "payment.lab.internal"}},
    options);

// RAII: a span a scope élettartamáig aktív
trace::WithActiveSpan active(span);

// Kimenő HTTP-hívás előtt inject
opentelemetry::context::propagation::GetTextMapPropagator()
    ->Inject(http_client.Headers(), [&](std::string_view k, std::string_view v) {
      http_client.SetHeader(std::string(k), std::string(v));
    });

auto result = http_client.Post("/authorize", payload);
if (!result.ok()) {
  span->SetStatus(trace::StatusCode::kError, result.error());
}
span->End();

A kód azért fontos, mert mutatja a három nem triviális határt: a bejövő context extract, a kimenő context inject, és a span status hozzárendelése. A hibás hívásnál a span csak akkor lesz Error, ha a hívás eredményét explicit módon ráírjuk. A span End() elmaradása szintén nem okoz C++ kivételt, de a span nem kerül exportra.

50.4.4 Kidolgozott példa: checkout-pálya idő- és hibafelbontása

A labortopológia három C++ szolgáltatásból és egy Collectorból áll, mind izolált lab VM-en:

Komponens Host Felelősség
svc_gateway srv1 HTTP belépés, kérés validálása
svc_order srv2 Rendelésfeldolgozás
svc_payment srv3 Fizetés, banki authorizáció
lab-collector lab-collector OTel Collector, debug exporter

A kérés a gateway-től az order service-en át a payment service-hez megy. A gateway megkapja a traceparent fejlécet, minden kimenő hívásba injectálja a contextet, és OTLP-n a collectorba küldi a span-eket.

Futtassuk le a kérést explicit trace contexttel:

# target: labhost srv1, UID=labops, account=local-lab
curl -i -H 'traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01' \
     http://srv1:8080/checkout

A kérésben a payment service 500 ms-os timeoutot ad, a gateway 502-vel tér vissza. Az alábbi span-táblázat illusztratív, nem mért laboradat:

Span Service Parent Kezdő ofszet [ms] Duration [ms] Status
GET /checkout svc_gateway — 0 810 Error
OrderService.ProcessOrder svc_order GET /checkout 15 790 Error
OrderService.DBQuery svc_order OrderService.ProcessOrder 20 280 Ok
PaymentService.Authorize svc_payment OrderService.ProcessOrder 30 500 Error

A latency-összerendelés innen: a gateway teljes 810 ms-ából 790 ms az order service, abból 500 ms a payment authorizáció és 280 ms az DB-lekérdezés. A maradék 20 ms a gateway saját validálási ideje. A root cause span a PaymentService.Authorize, mert ez a legmélyebb span, amely Error státuszt állít be. Ha a PaymentService.Authorize span hiányzik, az OrderService.ProcessOrder span hiba jelzése ugyan látható, de nem tudjuk, hogy a hiba a paymentben keletkezett.

A gyűjtő oldalán a tail sampling ezt a trace-et megtartja, mert legalább egy span Error státuszú. A konfiguráció fogalmi vázlata:

receivers:
  otlp:
    protocols:
      grpc:
        endpoint: "0.0.0.0:4317"

processors:
  tail_sampling:
    decision_wait: 10s
    num_traces: 5000
    policies:
      - name: keep-errors
        type: status_code
        status_code:
          status_codes: [ERROR]
      - name: keep-slow
        type: latency
        latency:
          threshold_ms: 500

exporters:
  debug:
    verbosity: detailed

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [tail_sampling]
      exporters: [debug]

Várt kimenet: a curl válasz HTTP/1.1 502 Bad Gateway; a collector debug exportban a fenti négy span jelenik meg, a PaymentService.Authorize span status=Error. A fizikai labor nem futott le, ezért ez várt, illusztratív kimenet, nem tényleges mérés.

Ha a bejövő traceparent flag 00 lenne, a head sampling letiltaná a rögzítést. Ha viszont a head samping be van kapcsolva a root-on, a trace nem jut el a tail samplingig — ez fontos feltétel: a tail sampling nem kap olyan trace-t, amelyet a head sampling már eldobott.

50.4.5 Tipikus hibák és ellenpróbák

A leggyakoribb hiba, hogy a kimenő HTTP-hívásból hiányzik az Inject. A hívott fél ilyenkor új gyökérspan-t hoz létre, a két szolgáltatás két külön trace-ként jelenik meg, és a latency-összefüggés elvész. Ezt a hibát a collectorban úgy látjuk, hogy a PaymentService.Authorize span parent_span_id üres, vagy a trace_id különbözik.

A második gyakori hiba a high cardinality. A span nevet nem szabad URL-paraméterrel vagy felhasználóazonosítóval bővíteni: a GET /users/123 helyett GET /users/{id}. Ugyanez vonatkozik az attribútumokra: http.url vagy user.id helyett a jelentéshez szükséges, alacsony kardinalitású http.route és http.status_code. A magas kardinalitású request_id önmagában hasznos lehet, de minden spanra plusz indexköltség; ilyenkor a trace_id gyakran elég.

A harmadik tipikus csapda a statusz téves hozzárendelése. A 404 vagy 400 HTTP-állapot nem automatikusan span Error; a span status inkább a szolgáltatás műveleti sikerét jelölje. Ha a nem létező erőforrás az üzleti API normál része, akkor Ok, a hibát az attribútum őrzi.

A negyedik a sampling rossz kombinációja: a teljes forgalomra head sampling 1%-ot állítunk, és utána tail samplingtől várjuk, hogy minden hibát megtart. A hibák 99%-át azonban a head sampling eldobja, mert a root span a kérés elején dönt. Hibaérzékeny SLO esetén érdemes a head samplinget magas arányon tartani, és a megtartást a collectorba helyezni.

Végül a baggage biztonsági hiba: a token, ügyfél-email és belső user ID baggage-ba kerül, mert „csak egy fejléc”. A baggage minden downstream service felé továbbító, így a kérés kontextusában titkot terjeszt. A titkokat továbbra is a hitelesítési rétegnek kell kezelnie, nem a telemetriai propagationnek.

50.4.6 Feladatok

50.4.6.1 1. Magyarázó feladat: traceparent elemzése

Készítsen tail sampling konfigurációt, amely megtartja az Error státuszú trace-eket, a 700 ms-nál hosszabb latency-vel rendelkező trace-eket, és minden egyéb trace-t eldob. 50.4.7 Megoldások

50.4.7.1 1. Megoldás

A trace_id 4bf92f3577b34da6a3ce929d0e0e4736, a parent_span_id 00f067aa0ba902b7, a trace_flags 00. A flag 00 azt jelenti, hogy a trace nem sampled: a downstream span-ek nem exportálódnak alapértelmezésben. Ha Debug célból mégis kell rögzíteni, a szolgáltatás saját samplerje explicit force-sample beállítást alkalmazhat; ezt az adott requestre, a state-config forrásra és a törlési időre vonatkozó naplóbejegyzéssel kell indokolni, mert a force sample megnöveli az adatvolument, és adatvédelmi következménye lehet. Postcondition: a hallgató az adott traceparent-ből egyértelműen kiolvassa a trace-azonosítót, szülő-azonosítót és mintavételi flaget; meg tudja magyarázni, miért nem exportálódik a trace alapértelmezésben.

50.4.7.2 2. Megoldás

A YAML:

receivers:
  otlp:
    protocols:
      grpc:
        endpoint: "0.0.0.0:4317"

processors:
  tail_sampling:
    decision_wait: 10s
    num_traces: 5000
    policies:
      - name: keep-errors
        type: status_code
        status_code:
          status_codes: [ERROR]
      - name: keep-slow
        type: latency
        latency:
          threshold_ms: 700

exporters:
  debug:
    verbosity: detailed

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [tail_sampling]
      exporters: [debug]

Postcondition: a YAML szintaktikailag érvényes, a Collector OTLP gRPC-n fogad, az Error és a 700 ms feletti trace-eket megtartja, a többit eldobja, és a megtartott trace-eket debug exporterre írja.

50.4.7.3 3. Megoldás

A hibagyökér a PaymentService.Authorize span lenne, mert ez a legmélyebb span, amelynek Error státuszt kellene mutatnia. A hiányzó span miatt nem tudjuk, hogy a payment hívás volt-e a hiba oka, vagy az order service saját kompenzációs logikája állította be az Error státuszt. A span hiánya fakadhat az OTel SDK batch-elt exportáló pufferének túlcsordulásából, a collectorban beállított szűk decition_wait vagy num_traces miatti tail-sampling dropból, vagy hálózati hibából. A head sampling önmagában nem indokolja a részleges hiányt, mert az általában trace-szintű döntést hoz; itt a trace többi spanja megvan, tehát egy span szintű veszteség történt. Postcondition: a hallgató a hiányzó spanból korlátozott bizonyosságú diagnózist ad, és elkülöníti a span-szintű dropot a trace-szintű samplingtől.

50.4.8 Rövid összefoglaló

A distributed trace a kérés útját trace_id-vel kötött span-ekben követi. A span a műveleti időintervallum, a trace context a terjesztéshez szükséges státusz, a W3C traceparent szabványosítsa a hívások közötti átadást. A propagation feltételezi a hívás előtti inject és a hívott oldali extract párost. A sampling dönt arról, hogy a spant megtartsuk-e: a head sampling a gyökérnél dönt, a tail sampling a teljes trace alapján. A C++ instrumentation akkor megbízható, ha a span-ek a műveleti határokat fedik, a status explicit, és az attribútumok alacsony kardinalitásúak.

  • Span: névvel, időzítéssel és szülővel rendelkező műveleti felvétel.
  • Trace context: a terjesztéshez használt trace_id, span_id, trace_flags és opcionális tracestate.
  • Sampling: döntés egy span megtartásáról és exportálásáról; head- vagy tail-alapú.
