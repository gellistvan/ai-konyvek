38.3 Container networking, volume és host boundary

38.3.1 Motiváció

A konténer hálózata és tárolója egyszerre előny és gyakori hibalehetőség. A szenior C++ fejlesztő számára a fontos kérdés nem az, hogy „működik-e a demó”, hanem hogy vissza tudjuk-e vezetni a csomag- és adatutat a host beállításaira. A kiadott port és a konténer alkalmazás tényleges listener socketje között nincs automatikus egyenlőség. A volume sem egyszerű könyvtár: a bind mount és a named volume ownership-szemantikája a host-fájlrendszerben és a konténer user namespace-ben eltérhet. Ha egy szolgáltatás nem elérhető, a válaszhoz legalább három réteget kell megvizsgálnunk: a host portfoglalását, a konténer hálózati namespace-ét (network namespace) és a tűzfal/NAT állapotot.

38.3.2 Definíciók és működés

38.3.2.1 A konténerhálózat modellje

Minden konténer rendelkezik saját hálózati namespace-szel: saját loopback interfész, route tábla, neighbour tábla és resolv.conf. A hoston a runtime egy veth (virtual Ethernet) párt hoz létre: az egyik vége a konténer eth0 interfésze, a másik a host bridge-hez (hídhoz) csatlakozik. Rootful Docker esetén az alapértelmezett bridge jellemzően docker0, a felhasználói hálózatokhoz további bridge-ek tartoznak. Rootless Podman esetén a hostoldali bridge-et netavark, vagy a beépített pasta/slirp4netns felhasználói térben futó hálózati réteg helyettesíti; itt a hoston nincs rendszer-szintű bridge, a névfeloldás és a portfordítás a felhasználó jogosultságával működik.

A host network mód (--network host) eltérő: a konténer nem kap saját network namespace-t, hanem a host hálózatát használja közvetlenül. Ez kizárja a port publish szükségességét, de csökkenti az izolációt és a konténerenkénti tűzfalszabályozást.

38.3.2.2 Port publish és alkalmazás listener

A port publish parancs szintaxisa:

# formátum: HOST_IP:HOST_PORT:CONTAINER_PORT
-p 127.0.0.1:18080:80

A hoston a publikált port (18080) nem azonos a konténer belső alkalmazásportjával (80). A Docker vagy Podman a host oldalon foglal egy socketet, és a forgalmat a konténer hálózati címére, a konténerportra továbbítja. A host ss kimenete nem a konténerprocesszt mutatja, hanem a runtime proxyfolyamatát: Docker rootful esetén docker-proxy, rootless Podman esetén rootlessport. A konténeralkalmazás a saját namespace-ében hallgat a konfigurált IP-címen és porton; ha a konténer 0.0.0.0:80 helyett 127.0.0.1:80-ra bindol, a hostról érkező, az eth0-ra címzett forgalom a konténeren belül elutasításra kerül.

A külső és a loopback adatút különbözik. Rootful Docker esetén a külső forgalom a netfilter DNAT-szabályán át éri el a bridge-et; a localhost-forgalom jellemzően a docker-proxy-n keresztül halad. A visszafelé út a conntrack kapcsolatállapot alapján áll helyre. A rootless Podman a portfordítást jellemzően felhasználói térben végzi, ezért a host nftables szabálykészletében nem feltétlenül látszik a DNAT bejegyzés.

38.3.2.3 DNS és service discovery

A konténer resolv.conf-ját a runtime állítja elő. Rootful Docker hálózatokon a beágyazott DNS-kiszolgáló gyakran a 127.0.0.11 címen válaszol a konténeren belül; a névfeloldás az azon a hálózaton lévő konténernevekre is kiterjed. Rootless Podman hálózatokon ezt a szerepet gyakran az aardvark-dns látja el. A host systemd-resolved 127.0.0.53 címét a konténer nem közvetlenül éri el, mert a konténer loopback namespace-e a hostétól eltér. Ezért a hoston látható magán-DNS-bejegyzések nem automatikusan érvényesek a konténerben.

38.3.2.4 NAT, route, MTU és IPv6

A bridge-hálózatból kimenő forgalom általában a host IP-címére fordul (SNAT), ezért a külső célállomás a host címét látja. A visszafelé úthoz conntrack bejegyzésre van szükség. A bridge interfész MTU-ja alapból 1500 bájt; ha a laborban VXLAN vagy más overlay csomagolás is megjelenik, a belső MTU-nak a külső csomagolás méretét is figyelembe kell vennie, különben a nagyobb csomagok elakadhatnak (PMTU blackhole).

IPv6 publish esetén a host oldalon külön IPv6-címre is bindolni kell, például [::1]:18080:80. Dual-stack módban figyelni kell arra, hogy a DNS rekordok sokszor csak IPv4-címet adnak vissza, és a reverse proxy/firewall is külön szabályt igényel.

38.3.2.5 Volume, bind mount és ownership

A bind mount egy host elérési utat köt a konténerbe. A host fájlrendszer UID/GID-értékeit a konténerben ugyanaz a numerikus azonosító látja, hacsak user namespace nem fordítja el. A Docker rootful alapesetben nem használ user namespace-t; a root a konténerben root a hoston is. Ekkor a hoston UID 1000 tulajdonú fájl a konténerben is 1000-ként látszik. Rootless Podman esetén a user namespace eltolja az azonosítókat: például a konténerben root UID a host felhasználó UID-jére képződik le. Ezért a bind mount fájlok tulajdonosa a konténerben meglepő lehet.

A named volume a runtime által kezelt, a konténer életciklusán túlélő mount. Új üres volume esetén a runtime gyakran átmásolja a célkönyvtár kezdeti tartalmát a képfájlból; bind mountnál ilyen copy-up nincs. A named volume host elérési útja általában a runtime tárolókönyvtárán belül van: rootful Docker esetén jellemzően /var/lib/docker/volumes/<név>/_data, rootless Podman esetén a $XDG_DATA_HOME/containers/storage alatt. A hoston a volume tartalmát a runtime felhasználója birtokolja; a konténerben a processz identitásától függ, hogy írhatja-e.

SELinux rendszeren a bind mount :z vagy :Z címke szükséges lehet; Ubuntu alapesetben AppArmor-politikát használ, ott a mount címkézés más.

38.3.2.6 Container logs és storage accounting

A konténer naplója nem a konténer writable rétegébe kerül: a runtime a naplómeghajtóval külön fájlba ír. A Docker alapértelmezett json-file naplója tipikusan /var/lib/docker/containers/<container-id>/<container-id>-json.log; Podman rootless esetén a felhasználói tároló alatt. A naplófájl korlátozás nélkül gyorsan betöltheti a lemezt, ezért max-size és max-file paraméter szükséges. A helyfoglalást a docker system df, illetve podman system df mutatja, de ez nem választja szét a writable réteget, a named volume-ot és a naplókat. A pontos anomáliát hostoldali du -x vizsgálattal kell lokalizálni.

38.3.3 Kidolgozott példa

Az alábbi parancsok nem ténylegesen futtatott laborparancsok; a kimenet várt, illusztratív.

# target: labhost1; user: laboperator (UID=1000)
# privilege: docker group (rootful Docker), sudo a host fájlrendszer vizsgálatához
# előfeltétel: Docker d187 szerint telepítve; image tag a lab inventoryban ellenőrzött

docker network create --subnet=192.168.112.0/24 lab-net
docker volume create lab-site

docker run -d --name lab-web \
  --network lab-net \
  -p 127.0.0.1:18080:80 \
  -p '[::1]:18080:80' \
  -v lab-site:/usr/share/nginx/html:ro \
  --log-opt max-size=10m --log-opt max-file=3 \
  nginx:1.27-alpine

# Várt kimenet: teljes container id

A host oldali ellenőrzéshez a publikált portot vizsgáljuk:

# target: labhost1; user: laboperator
docker port lab-web
# Várt kimenet:
# 80/tcp -> 127.0.0.1:18080
# 80/tcp -> [::1]:18080

ss -lntp | grep 18080
# Várt kimenet: a figyelő socketet a docker-proxy tartja,
# nem a konténerprocessz PID-je látszik.

A konténer belső nézőpontja:

docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' lab-web
# Várt kimenet: 192.168.112.2

docker exec lab-web cat /etc/resolv.conf
# Várt kimenet: nameserver 127.0.0.11, a beágyazott Docker DNS.

Az adatút a hoston, loopback kiensből:

Lépés Tér Cím/port Eredmény
Kiens csatlakozik host loopback 127.0.0.1:18080 docker-proxy fogadja
Proxy továbbít host bridge 192.168.112.2:80 veth-re irányít
veth fogad konténer netns eth0:80 nginx válaszol
Visszaút conntrack/proxy kapcsolódó kapcsolat válasz a kienshez

Külső forrás esetén a docker-proxy előtti lépés a host netfilter DNAT-ja, amely a host fizikai IP-jének 18080 portjáról a 192.168.112.2:80-ra fordít.

A volume hostoldali ellenőrzése:

docker volume inspect lab-site --format '{{.Mountpoint}}'
# Várt kimenet: /var/lib/docker/volumes/lab-site/_data

sudo ls -ln /var/lib/docker/volumes/lab-site/_data
# Várható: a képfájlból copy-upolt fájlok, például
# -rw-r--r-- 1 0 0 ... index.html

docker exec lab-web id
# Várható: uid=101(nginx) gid=101(nginx) groups=101(nginx)

A példa mutatja, hogy a named volume tartalma a képfájlból átmásolt root tulajdonú fájl, a konténer nginx processze pedig UID 101-ként fut. Read-only mount esetén ez működik; ha a konténernek írnia kellene, az ownership-ütközés hibát adna.

A service discovery ellenőrzése:

docker run --rm --network lab-net alpine:3.20 getent hosts lab-web
# Várt kimenet: 192.168.112.2 lab-web

A cleanup csak a labor által létrehozott objektumokra terjed ki:

docker rm -f lab-web
docker network rm lab-net
docker volume rm lab-site

38.3.5 Feladatok

38.3.5.1 1. Magyarázó feladat: publish és listener szétválasztása

Adott a következő indítás: docker run -p 0.0.0.0:18080:80 lab-web. Magyarázd el, miért nem biztos, hogy a szolgáltatás elérhető a hoston a 18080 porton, ha a konténerben az alkalmazás a 127.0.0.1:80-ra bindol. Rajzold le táblázatban a külső kapcsolat útját, és jelöld, hol akad el a forgalom.

38.3.5.2 2. Adminisztrációs feladat: rootless Podman bind mount és DNS

Hozz létre a labhost1-en rootless Podmanban egy lab-data named volume-ot és egy /srv/lab-html bind mountot. Indíts el egy lab-pod-web konténert --network subnet=192.168.112.0/24 hálózattal, -p 127.0.0.1:18081:80 publish-csel, és a bind mountot read-only módon csatold /srv/lab-html:/usr/share/nginx/html:ro formában. Ellenőrizd a hoston a DNS-beállítást (podman exec lab-pod-web cat /etc/resolv.conf), a naplófájl méretkorlátját (podman inspect vagy podman logs konfiguráció), és a service discovery működését egy második konténerből. Végül töröld a lab-prefixes objektumokat.

38.3.5.3 3. Diagnosztikai/failure feladat: netns és volume ownership hiba

Egy kolléga a következőket futtatja:

# A host /srv/lab-content könyvtára: 1000:1000, mód 0700
podman run -d --name lab-bad \
  -v /srv/lab-content:/data \
  -p 127.0.0.1:18082:8080 \
  lab-app:test

A lab-app:test processz a konténerben UID 101-ként fut, és a /data könyvtárba írni próbál. A hostról a curl 127.0.0.1:18082 kapcsolat „connection refused” hibaüzenettel tér vissza. A konténer logjában az alkalmazás a 127.0.0.1:8080-ra bindol. Lokalizáld a két hiba gyökérokát hostnézettel, javítsd egy-egy változtatással, ellenőrizd, majd írd le a rollbacket.

38.3.6 Megoldások

38.3.6.1 1. megoldás

A konténer saját loopbackja a konténer netns-én belül van. Amikor a hostról érkező forgalom a konténer eth0:80 portjára irányul, az nem azonos a konténer lo:80 címzésével. Az alkalmazás 127.0.0.1:80 bindja csak a saját névtér loopbackját fogadja, ezért az eth0-ra továbbított csomagot a rendszer eldobja. A külső kapcsolat útja: host eth0:18080 → netfilter DNAT → bridge 192.168.112.2:80 → veth → konténer eth0:80, de itt nincs listener. A javítás az alkalmazás konfigurációjának 0.0.0.0:80-ra állítása, nem a port publish megváltoztatása.

38.3.6.2 2. megoldás

# target: labhost1; user: laboperator (UID=1000); rootless Podman
podman network create --subnet 192.168.112.0/24 lab-net
podman volume create lab-data
sudo mkdir -p /srv/lab-html
echo '<h1>lab</h1>' | sudo tee /srv/lab-html/index.html

podman run -d --name lab-pod-web \
  --network lab-net \
  -p 127.0.0.1:18081:80 \
  -v /srv/lab-html:/usr/share/nginx/html:ro \
  -v lab-data:/var/lib/nginx:Z \
  --log-driver json-file \
  --log-opt max-size=10m \
  --log-opt max-file=3 \
  nginx:1.27-alpine

Ellenőrzés:

podman port lab-pod-web
ss -lntp | grep 18081
podman exec lab-pod-web cat /etc/resolv.conf
podman run --rm --network lab-net alpine:3.20 getent hosts lab-pod-web
podman system df
sudo du -x /var/lib/docker/volumes/lab-data/_data

A várható postcondition: a lab-pod-web elérhető a host loopback 18081 portján; a névfeloldás a lab-pod-web nevet a hálózaton belül visszaadja; a lab-pod-web naplója max-size és max-file korlátozással rendelkezik; a named volume a lab törlése után is megmarad, amíg explicit nem töröljük.

Cleanup:

podman rm -f lab-pod-web
podman network rm lab-net
podman volume rm lab-data
sudo rm /srv/lab-html/index.html
sudo rmdir /srv/lab-html

38.3.6.3 3. megoldás

Először a hálózati hibát vizsgáljuk. A host oldalról a ss -lntp mutatja a rootlessport publikált 18082 portját. A konténerben podman exec lab-bad ss -lntp (ha az image tartalmazza) megmutatja, hogy a processz csak 127.0.0.1:8080-ra bindol. A javítás az alkalmazás 0.0.0.0:8080 bindja; erről győződjünk meg a konténer belső ellenőrzésével, majd curl 127.0.0.1:18082 már sikeres választ ad.

A volume hibája a host /srv/lab-content UID/GID 1000:1000, a konténer processz UID 101; a könyvtár módja 0700, ezért a konténerben a 101-es UID nem léphet be. A javítás:

# A 101-es UID legyen a könyvtár tulajdonosa a hoston.
sudo chown -R 101:101 /srv/lab-content
sudo chmod 0750 /srv/lab-content

Ezután a konténerben a 101-es processz be tud írni. Az ellenőrzés: podman exec lab-bad sh -c 'echo ok > /data/test && cat /data/test'. A postcondition: a konténer hálózat elérhető a publikált porton, és a bind mount írható a konténerprocessz számára.

Rollback:

sudo chown -R 1000:1000 /srv/lab-content
sudo chmod 0700 /srv/lab-content
podman rm -f lab-bad

38.3.7 Rövid összefoglaló

A konténer hálózata önálló namespace-ekre épül; a host oldali publikált port és a konténer belső listener socketje külön vizsgálandó. A port publish a host socket és a konténerport közötti forwarding, nem pedig a konténerprocessz hoston való megjelenése. A bind mount a host fájlrendszer UID-jait és jogosultságait viszi be; a named volume a runtime által kezelt, copy-up és lifecycle szempontból más. A hibadiagnosztikához mindig a hostnézetből kell ellenőrizni a figyelő socketet, a netns-útját, a mount ownershipet és a napló/storage fogyasztást.

  • Network namespace: a kernel erőforrás-elkülönítési egysége, amelyben saját interfész, route és loopback él.
  • Port publish: a host oldali socket és a konténer belső portja közötti forwarding, amely nem garantálja, hogy a konténeralkalmazás a megfelelő címen hallgat.
  • Bind mount: host elérési út csatolása a konténerbe, a host fájlrendszer UID/GID és jogosultsági szemantikájával.
