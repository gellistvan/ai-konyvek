24.5 Két végpont packet-path labor

24.5.1 Miért kell a kérés teljes útját bizonyítani?

A „nem érhető el a szerver” nem diagnózis. Jelentheti, hogy nincs útvonal, nem működik a szomszédfelderítés, rossz címen figyel a szolgáltatás, vagy a létrejött TCP-kapcsolaton hibás alkalmazásválasz érkezik. A labor célja ezeket egyetlen, pontosan azonosított kérés történetévé összekapcsolni.

A csomagút (packet path) a csomag által érintett interfészek, továbbítási döntések és protokollfeldolgozási lépések sorozata. A visszaút külön vizsgálandó: a kérés megérkezése nem bizonyítja, hogy a válasz visszajuthat.

Két hálózati névteret (network namespace) használunk. Ezeknek külön interfész-, útvonal-, szomszéd- és socketállapotuk van. Egy virtuális Ethernet-interfészpár, a veth pair közvetlenül összeköti őket: az egyik oldalon elküldött keret a másikon fogadható. A névterek részletes adminisztrációját később a Network namespace, veth, bridge és tap tárgyalja; itt előre megadott, izolált tesztberendezésként használjuk őket.

A Socket, port, bind és kapcsolat alapján külön bizonyítjuk:

  1. az IP-cél elérhetőségét;
  2. a TCP-listener elérhetőségét;
  3. a helyes alkalmazásválaszt.

24.5.2 Laborcontract és topológia

Célgép: lab-net01, izolált Ubuntu Server 24.04 LTS amd64 VM.
Fiók: meglévő labadmin, UID 1000, engedélyezett sudo.
Jogosultság: az adminisztrációs parancsok UID 0-val futnak; a HTTP-listener UID 1000-rel.
Előfeltétel: iproute2, iputils-ping, python3, curl, tcpdump, működő systemd és VM-konzol. Hiányzó eszköznél előbb a csomagkezelési eljárással készítsd elő a VM-et.

Objektum Név, cím vagy szerep
Kliensnévtér lab-path-a
Kliensinterfész lab-a0, 10.203.120.1/32
Szervernévtér lab-path-b
Szerverinterfész lab-b0, 10.203.120.2/32
Összeköttetés lab-a0 ↔︎ lab-b0, közvetlen veth-pár
Kliensútvonal 10.203.120.2/32 dev lab-a0
Szerverútvonal 10.203.120.1/32 dev lab-b0
Listener lab-path-http.service, TCP 10.203.120.2:18080
Munkakönyvtár /run/lab-d120
Owner és lejárat labadmin; a labormenet végén eltávolítandó

A /32 egyetlen IPv4-címet jelöl. Szándékosan nem adunk közös /24 prefixet: mindkét irányhoz külön, látható útvonalat hozunk létre. A scope link azt fejezi ki, hogy a cél közvetlenül a linken érhető el, nincs köztes IP-átjáró.

Izoláció: nincs bridge, NAT, alapértelmezett útvonal vagy kapcsolat a host fizikai interfészével. A kiválasztott privát címek így nem kerülnek ki a laborból. Ellenőrizd, hogy a nevek szabadok; meglévő objektumot ne használj fel. A hoston esetleg előforduló azonos cím névtéren kívül nem ütközik, de a labor későbbi összekötése előtt új címterv-ellenőrzés szükséges.

Konfigurációforrás Az alábbi parancsok és a laborjegyzőkönyv
Megfigyelt állapot ip, ss, szolgáltatásnapló, csomagmegfigyelés

24.5.3 A két végpont felépítése

Az alábbi blokkok ugyanabban az adminisztrációs shellben követik egymást. A parancsokat a tananyag nem futtatta; minden kimenet várt, nem mérési eredmény.

# Target: lab-net01; belépés labadmin UID 1000-ről root shellbe.
sudo -i
# Target: lab-net01, host névtér, UID 0.
test "$(hostname -s)" = lab-net01 || exit 1
test "$(id -u)" = 0 || exit 1
test "$(id -u labadmin)" = 1000 || exit 1

ip netns list
ip -brief link
systemctl list-units --all lab-path-http.service --no-pager
test ! -e /run/lab-d120 || exit 1

Megállási feltétel: ha a felsorolt labornevek bármelyike már létezik, ne folytasd, és ne töröld automatikusan. Előbb azonosítsd az ownerét.

A következő blokk csak új laborobjektumokat hoz létre. Hiba esetén az alább megadott cleanup alkalmazható a már létrejött, saját objektumokra.

# Target: lab-net01, UID 0; előfeltétel: minden labornév szabad.
(
set -eu
umask 022
mkdir /run/lab-d120
mkdir /run/lab-d120/lab-www
printf 'lab packet-path OK\n' \
  > /run/lab-d120/lab-www/lab-health.txt

{
  cat /etc/os-release
  uname -r
  dpkg-query -W -f='${binary:Package}\t${Version}\n' \
    iproute2 iputils-ping python3 curl tcpdump systemd
} > /run/lab-d120/lab-profile.txt

ip netns add lab-path-a
ip netns add lab-path-b
ip link add lab-a0 type veth peer name lab-b0
ip link set lab-a0 netns lab-path-a
ip link set lab-b0 netns lab-path-b

ip -n lab-path-a link set lo up
ip -n lab-path-b link set lo up
ip -n lab-path-a addr add 10.203.120.1/32 dev lab-a0
ip -n lab-path-b addr add 10.203.120.2/32 dev lab-b0
ip -n lab-path-a link set lab-a0 up
ip -n lab-path-b link set lab-b0 up

ip -n lab-path-a route add 10.203.120.2/32 \
  dev lab-a0 scope link src 10.203.120.1
ip -n lab-path-b route add 10.203.120.1/32 \
  dev lab-b0 scope link src 10.203.120.2
)

Először ne forgalmat generálj, hanem ellenőrizd az állapotot:

# Target: lab-net01, lab-path-a és lab-path-b névtér, UID 0.
for ns in lab-path-a lab-path-b; do
  ip -n "$ns" -brief link
  ip -n "$ns" -brief addr
  ip -n "$ns" route show
  ip -n "$ns" neigh show
done

ip -n lab-path-a route get 10.203.120.2
ip -n lab-path-b route get 10.203.120.1

Várt állapot: mindkét veth-interfész működőképes, a címek és a két hostútvonal jelen vannak. A kliensoldali route get lényegi mezői:

10.203.120.2 dev lab-a0 src 10.203.120.1

Ez a kernel útvonalválasztási döntése, nem sikeres csomagküldési bizonyíték. A szomszédtábla ekkor még lehet üres.

24.5.4 Névvel azonosított listener és rétegenkénti próba

A lab-path-http.service átmeneti systemd-unit. A NetworkNamespacePath a szerver hálózati névteréhez rendeli a folyamatot; a User korlátozza a futtatási identitást. Ez demonstrációs HTTP-szerver, nem production deployment.

# Target: lab-net01, UID 0; a listener lab-path-b-ben, UID 1000-rel fut.
systemd-run --unit=lab-path-http.service --collect \
  --property=User=labadmin \
  --property=NetworkNamespacePath=/run/netns/lab-path-b \
  /usr/bin/python3 -m http.server 18080 \
  --bind 10.203.120.2 \
  --directory /run/lab-d120/lab-www

systemctl status lab-path-http.service --no-pager
ip netns exec lab-path-b ss -ltnp 'sport = :18080'

Várt ellenőrzési feltétel: az ss egy LISTEN socketet mutat 10.203.120.2:18080 címen, Python-folyamathoz kapcsolva. Az active unitállapot önmagában nem helyettesíti ezt. Ha a socket még nincs jelen, ellenőrizd a naplót, majd ismételd meg a lekérdezést:

# Target: lab-net01, host systemd journal, UID 0.
journalctl -u lab-path-http.service -n 30 --no-pager

A host névterében kiadott ss nem a szervernévtér socketjeit listázza. Ezért a megfigyelési target ugyanolyan fontos, mint maga a parancs.

24.5.4.1 Strukturált csomagmegfigyelés

A csomagrögzítés (packet capture) kijelölt megfigyelési ponton ad bizonyítékot. Most a kliens veth-interfészét figyeljük, kizárólag ARP-, ICMP- és a vizsgált TCP-forgalomra szűrve.

# Target: lab-net01, lab-path-a/lab-a0, UID 0.
ip netns exec lab-path-a tcpdump \
  -i lab-a0 -nn -e -tttt -l -s 128 \
  'arp or icmp or tcp port 18080' \
  > /run/lab-d120/lab-capture.txt \
  2> /run/lab-d120/lab-capture.log &
LAB_CAPTURE_PID=$!

sleep 1
kill -0 "$LAB_CAPTURE_PID"
cat /run/lab-d120/lab-capture.log

Csak akkor folytasd, ha a folyamat él, és a napló jelzi a lab-a0 figyelését. A sleep önmagában nem readiness-ellenőrzés.

  • -nn: ne legyen DNS- vagy portnévfeloldás.
  • -e: jelenjenek meg az Ethernet-címek.
  • -tttt: dátumos, wall-clock időbélyeg; nem monotonic mérési óra.
  • -s 128: csomagonként korlátozott rögzítési hossz.
  • -l: soronként pufferelt szöveges kimenet.

Nem használunk payloadkiíró -A kapcsolót. A szűrés és a rövid rögzítési hossz sem általános titokvédelmi garancia; itt kizárólag dummy adat mozog.

# Target: lab-net01, lab-path-a, UID 0.
# Csak a kijelölt peerszomszéd bejegyzését ürítjük.
ip -n lab-path-a neigh flush to 10.203.120.2 dev lab-a0

ip netns exec lab-path-a ping -n -c 1 -W 1 10.203.120.2

ip netns exec lab-path-a curl -4 --noproxy '*' \
  --connect-timeout 2 --max-time 4 \
  --fail --silent --show-error \
  --write-out '\nHTTP %{http_code}\n' \
  http://10.203.120.2:18080/lab-health.txt

ip -n lab-path-a neigh show
ip -n lab-path-b neigh show

kill -INT "$LAB_CAPTURE_PID"
wait "$LAB_CAPTURE_PID"
cat /run/lab-d120/lab-capture.txt
cat /run/lab-d120/lab-capture.log

A --noproxy '*' kizárja a környezetből örökölt HTTP-proxy eltérítő hatását.

Várt alkalmazásválasz: lab packet-path OK, majd HTTP 200. A szomszédtáblában a peer IP-címe mellett MAC-cím látható. A REACHABLE vagy később STALE állapot nem alkalmazásszintű állapot; a STALE önmagában nem hiba.

24.5.5 Path táblázat: melyik csomag mire bizonyíték?

Lépés Forrás → cél Várt esemény Mit bizonyít?
Útvonalválasztás Kliens IP-réteg → lab-a0 route get a megfelelő interfészt választja Van helyi továbbítási döntés
Szomszédfelderítés Kliens MAC → Ethernet broadcast ARP: kié a 10.203.120.2? A kliens MAC-címet keres
ARP-válasz Szerver MAC → kliens MAC A cél közli a MAC-címét A közvetlen L2-peer válaszol
ICMP 10.203.120.1 → .2, majd vissza Echo request és echo reply Az ICMP oda-vissza működik
TCP-nyitás .1:ideiglenes_port → .2:18080 SYN, SYN-ACK, ACK A TCP-kapcsolat felépül
HTTP Kliens → szerver GET /lab-health.txt A kérés eljut az alkalmazásig
Válasz Szerver → kliens HTTP 200 és várt törzs A vizsgált művelet sikeres
Lezárás Mindkét irány FIN/ACK-forgalom Szabályos kapcsolatlezárás történik

A szöveges capture nem feltétlenül mutatja a HTTP tartalmát; azt a curl kimenete igazolja. A TCP-adat és ACK csomagokra bontása implementáció- és időzítésfüggő. Ne várj rögzített teljes csomagszámot.

A ping előtti ARP-feloldás eredményét a TCP-próba újrahasználhatja, ezért nem kötelező újabb ARP a SYN előtt. A rövid kapcsolat után az ss már nem feltétlenül mutat ESTABLISHED sort, miközben a listener továbbra is látható.

Ez Linux-implementáción végzett megfigyelési terv. A protokoll szabályai, az eszközök kimeneti formátuma és a ténylegesen rögzített csomagsor három külön bizonyítékszint.

24.5.6 Tipikus hibák és legkisebb ellenpróbák

Tünet Első hipotézis Legkisebb következő vizsgálat
Network is unreachable Hiányzó útvonal a kezdeményező névtérben ip route get ugyanott
Szomszéd INCOMPLETE, majd FAILED Nincs sikeres ARP-válasz Linkállapot, cím, ARP capture
Ping sikeres, TCP visszautasítva Nincs listener a célcímen/porton Szervernévtérbeli ss -ltnp
SYN ismétlődik, válasz nincs Eldobás, hibás visszaút vagy célhiba Szerveroldali capture és visszaút
HTTP 404 A hálózat működik, a kért erőforrás hibás URL és kiszolgált könyvtár
Hoston üres az ss Rossz megfigyelési névtér Ugyanaz a lekérdezés lab-path-b alatt

A capture-ben látható bejövő SYN nem bizonyítja, hogy a kernel a listenerig engedte. A megfigyelési pont és a feldolgozási réteg nem ugyanaz.

Veth és egyes offloadmechanizmusok mellett checksumjelzések félrevezetők lehetnek. Egy helyi capture figyelmeztetése miatt ne kapcsold ki globálisan az offloadot vagy a tűzfalat. Előbb ellenőrizd a túloldali megfigyelést és az alkalmazási eredményt.

A módszer: hipotézis → adatgyűjtés → egy változtatás → pozitív és negatív ellenpróba.

24.5.7 Feladatok

  1. Magyarázó: miért kell útvonal mindkét névtérben? Miért keresünk MAC-címet, ha már ismerjük a cél IP-címét? Mit nem bizonyít a sikeres ping?

  2. Adminisztrációs és recovery: töröld kizárólag a kliens 10.203.120.2/32 útvonalát. Rögzítsd a route get és a HTTP-próba hibáját, majd állítsd helyre az útvonalat. Ne változtass címet vagy listenert.

  3. Diagnosztikai: a klienskonfigurációban szerepeljen tévesen a 18081 port. A ping sikeres. Döntsd el, hálózati vagy szolgáltatásvégpont-hibáról van-e szó, és javítsd a legkisebb változtatással. Capture esetén a szűrőbe vedd fel a 18081 portot is.

24.5.8 Megoldások

1. Mindkét végpont saját útvonaltáblából választ kimenő interfészt; a kérés útvonala nem hozza létre automatikusan a válaszét. Az Ethernet-keret közvetlen címzettjéhez MAC-cím kell, ezért ezen az IPv4-linken ARP működik. A ping az ICMP-választ vizsgálja, nem a TCP-listenert, a HTTP-útvonalat vagy a válasz tartalmát.

Postcondition: a magyarázat külön kezeli az IP-útvonalat, az L2-címfeloldást és az alkalmazásvégpontot.

2. A hiba és a visszaállítás:

# Target: lab-net01, lab-path-a, UID 0.
ip -n lab-path-a route del 10.203.120.2/32 dev lab-a0

ip -n lab-path-a route get 10.203.120.2
ip netns exec lab-path-a curl -4 --noproxy '*' \
  --connect-timeout 2 --max-time 4 \
  http://10.203.120.2:18080/lab-health.txt

# Rollback: pontosan az eltávolított útvonal visszaadása.
ip -n lab-path-a route add 10.203.120.2/32 \
  dev lab-a0 scope link src 10.203.120.1

ip -n lab-path-a route get 10.203.120.2
ip netns exec lab-path-a curl -4 --noproxy '*' \
  --connect-timeout 2 --max-time 4 --fail \
  http://10.203.120.2:18080/lab-health.txt

A hibás állapotban a kernel nem talál útvonalat; ehhez nem szükséges SYN-t kiküldenie. A korábban megtanult MAC-cím nem pótolja az útvonalat.

Postcondition: a helyes interfész és forráscím ismét kiválasztható, a válasz törzse pontosan a várt szöveg.

3. Az ellenpróba csak a célportot változtatja:

# Target: lab-net01, UID 0; klienspróba lab-path-a-ban.
ip netns exec lab-path-a ping -n -c 1 -W 1 10.203.120.2
ip netns exec lab-path-a curl -4 --noproxy '*' \
  --connect-timeout 2 --max-time 4 \
  http://10.203.120.2:18081/lab-health.txt

# Szerveroldali bizonyíték.
ip netns exec lab-path-b ss -ltnp 'sport = :18080'
ip netns exec lab-path-b ss -ltnp 'sport = :18081'

A labor alapállapotában 18081-en nincs listener; TCP RST és gyors kapcsolódási hiba várható. Ez nem ugyanaz, mint a timeout. A javítás a kliens célportjának visszaállítása 18080-ra, nem új listener indítása.

Postcondition: 18080 sikeres, 18081 továbbra is sikertelen; a negatív kontroll megmarad.

24.5.9 Teljes cleanup és ellenőrzése

A szükséges jegyzőkönyvet előbb archiváld saját munkaterületedre. A capture-t már leállítottuk; félbeszakadt labor esetén előbb a névtérben maradt, azonosított saját folyamatot állítsd le. A névtér nevének törlése önmagában nem állítja le a benne futó folyamatokat.

# Target: lab-net01, UID 0; kizárólag a jelen labor saját objektumai.
(
set -eu

if systemctl is-active --quiet lab-path-http.service; then
  systemctl stop lab-path-http.service
fi

for ns in lab-path-a lab-path-b; do
  if [ -e "/run/netns/$ns" ]; then
    pids=$(ip netns pids "$ns")
    if [ -n "$pids" ]; then
      printf 'Megállás: %s névtérben maradt PID-ek: %s\n' "$ns" "$pids"
      exit 1
    fi
    ip netns del "$ns"
  fi
done

# Félbeszakadt felépítésből a hoston maradt saját veth-végek.
for iface in lab-a0 lab-b0; do
  if ip link show dev "$iface" >/dev/null 2>&1; then
    ip link del dev "$iface"
  fi
done

rm -f /run/lab-d120/lab-www/lab-health.txt \
      /run/lab-d120/lab-profile.txt \
      /run/lab-d120/lab-capture.txt \
      /run/lab-d120/lab-capture.log

if [ -d /run/lab-d120/lab-www ]; then
  rmdir /run/lab-d120/lab-www
fi
if [ -d /run/lab-d120 ]; then
  rmdir /run/lab-d120
fi

ip netns list
ip -brief link
systemctl list-units --all lab-path-http.service --no-pager
)

Cleanup-postcondition: nincs laborlistener, laborhálózati névtér, labor-veth vagy munkakönyvtár. A --collect miatt a leállított átmeneti unit is eltűnik. A host eredeti címei, útvonalai és tűzfalszabályai változatlanok.

24.5.10 Rövid összefoglaló

A sikeres kérés több, egymástól független feltétel teljesülése: helyes névtér, működő interfész, megfelelő cím és útvonal, feloldott szomszéd, elérhető listener, majd helyes alkalmazásválasz. A ping csak az ICMP-próbát igazolja. A route get döntést mutat, az ss socketállapotot, a tcpdump pedig egy kijelölt ponton megfigyelt csomagokat. Egyik sem helyettesíti a többit. A legjobb ellenpróba egyetlen változót módosít, és a helyreállítás után pozitív, valamint negatív kontrollt is végez. A labor eredménye verzióprofilhoz és pontos tesztkéréshez kötött pillanatnyi bizonyíték, nem általános rendelkezésreállási garancia.

Továbbhasznált definíciók:

  • Csomagút: továbbítási és feldolgozási lépések rendezett sorozata.
  • Megfigyelési pont: a bizonyítékgyűjtés konkrét helye.
  • Negatív kontroll: szándékosan sikertelen, elkülönítő ellenpróba.
