36.2 cgroup v2 CPU/memória/IO és OOM

36.2.1 Motiváció

A konténer nem virtuális gép: a host kernel ugyanabból a processz-, memória- és I/O-készletéből fogyaszt minden névtérbe zárt munkafolyamat. Ha egy C++ szolgáltatás konténerben indul, akkor a std::thread-ek, a malloc által anon memória, a std::fstream/read/write és a socketek host erőforrásokat használnak. Kérdés: ki garantálja, hogy a “limit” tényleg a mi konténerünkre vonatkozik, és hogyan látszik a számlálás a hoston? A cgroup v2 a válasz: kernel szintű erőforrás-controller, amelyet a konténer runtime a systemd felé delegál. A Process, namespace és konténerizoláció a láthatóságot izolálja; a cgroup v2 erőforrásmodell a fizikai erőforrás-korlátok alapját adja. Ebben az alfejezetben a konténer accountingot host- és cgroup-szinten értelmezzük, majd CPU-throttle és OOM hibát diagnosztizálunk config és metrikák alapján.

36.2.2 Definíció és működés

Konténer cgroup accounting: a konténer runtime minden konténerhez létrehoz egy cgroup v2 al-hierarchia csomópontot, és a konténer összes processzét abba a cgroupba helyezi. A kernel minden erőforrás-felhasználást (CPU-idő, memória, I/O, PID-ek) az adott cgroup számlálójába könyveli, függetlenül attól, hogy a processz milyen namespace-ben fut. A host top/htop/systemd-cgtop tehát a host szemével látja a fogyasztást, még akkor is, ha a konténer belsejében csak a saját limitjét figyelheti.

A modern konténer runtime-ok (Docker, Podman, containerd) cgroup v2 hierarchiában, systemd cgroup driverrel dolgoznak. Ez azt jelenti, hogy a konténer cgroupját a systemd slice fája alá helyezik, például machine.slice vagy a user manager user@<uid>.service alá. A konténer runtime a Delegate=yes és a cgroup.subtree_control mechanizmussal kap korlátos al-hierarchiát. A korábbi cgroupfs driver közvetlenül a /sys/fs/cgroup alá írt, de a systemd driver az egyetlen tulajdonos, így elkerüli a konfliktust. Ubuntu Server 24.04 baseline-on a systemd a default.

36.2.2.1 CPU quota/weight és throttling

A cgroup v2 CPU-controllere két fő működési módot kínál:

  • cpu.max – quota/period: abszolút CPU-idő plafon. Formátuma $QUOTA $PERIOD, például 50000 100000 mikroszekundumban: minden 100 ms periódusban legfeljebb 50 ms CPU-időt fogyaszthat a cgroup összes processze együtt. Ha a futó thread-ek többet kérnének, a kernel throttlingot alkalmaz: leállítja a futást a periódus hátralévő részére. Ez akkor is bekövetkezik, ha a host teljesen idle: a quota abszolút, nem work-conserving. A --cpus=0.5 konténer flag általában ezt a cpu.max értéket állítja be.
  • cpu.weight – relatív súly: work-conserving, csak akkor érvényesül, ha a host CPU túlterhelt. A nagyobb súlyú cgroup arányosan több CPU-időt kap. Nem plafon, hanem verseny esetén prioritás. A --cpu-shares régebbi flag ezt képezi le.

A cpu.stat fájl számlálói (nr_throttled, throttled_time, usage_usec stb.) mutatják a tényleges throttlingot. Ha egy C++ szolgáltatás latency SLO-ja romlik, és a nr_throttled nő, akkor CPU limit a gyanús, nem a host CPU.

36.2.2.2 Memory max/high/cache/OOM

A memória-controller kulcsfogalmai:

  • memory.current: a cgroup aktuális memóriafelhasználása. Ez tartalmazza az anon lapokat (például a C++ new/malloc által lefoglalt heap) és a file lapokat is (page cache, mmap-elt fájlok), viszont a page cache visszanyerhető (reclaimable).
  • memory.max: hard limit. Ha a cgroup eléri, a kernel OOM killt hajt végre a cgroupban: kiválaszt egy processzt és SIGKILL-t küld. Az oom_kill esemény a memory.events fájlban jelenik meg. A memory.max=0 vagy max azt jelenti, hogy nincs limit.
  • memory.high: soft throttle. Elérésekor a kernel intenzívebb reclaimet vált ki, és a cgroup processzei lelassulhatnak, de nem kapnak azonnal OOM killt. Jó eszköz a hard OOM elkerülésére: a memory.high korábban fékez.
  • memory.swap.max: swap limit. Ha 0, a cgroup nem swapolhat (pl. --memory-swap egyenlő --memory). Ha max, korlátlan.
  • memory.stat: részletes bontás: anon, file, slab, kernel_stack, sock, shmem stb. A diagnosztikában meg kell különböztetni a tényleges anon memóriát és a visszanyerhető page cache-t.

A memory.events fontos számlálói: oom_kill, oom, max, high. Ha oom_kill > 0, akkor valódi OOM történt, és a konténer egyik processzét a kernel megölte. A max számláló azt jelzi, hogy a cgroup elérte a memory.max-ot.

36.2.2.3 IO/pids limit

A cgroup v2 I/O-controllere a io.weight és a io.max segítségével szabályozza a blokk-I/O-t. A io.max formátuma dev major:minor rbps=... wbps=... riops=... wiops=..., például egy adott lemezre. A konténer runtime --device-write-bps flagje ezt képezi le. A io.stat ad bontást eszközönként.

A pids limit (pids.max) a cgroupban lévő processzek/szálak számát korlátozza. A pids.current és pids.events (amelyben max esemény van) mutatja a túllépést. C++ szolgáltatásnál a std::thread szálak kernel szálak, így a pids limit a szálszámot is korlátozza, nem csak a processzszámot. A --pids-limit flag ezt állítja.

36.2.2.4 PSI/host pressure és noisy neighbor

A PSI (Pressure Stall Information) a cpu.pressure, memory.pressure, io.pressure fájlokban a várakozási idő arányát méri, például some avg10=... mutatja, hogy a processzek az idő egy részében erőforrásra vártak. A host szintű PSI a /proc/pressure/ alatt olvasható. Ez segít megkülönböztetni a saját limit miatti throttlingot a host szintű telítettségtől. Noisy neighbor: ha egy másik konténer telíti a host memóriáját, akkor a kernel globális reclaimet indít, és a mi konténerünk page cache-ét is visszaveszi, még akkor is, ha a mi memory.high-unk nincs elérve. A PSI itt a host memórianyomást mutatja, míg a saját memory.events a saját cgroup eseményeit.

36.2.2.5 Rootless delegation és támogatás

A rootless konténerek (Podman rootless, Docker rootless) esetén a konténer processzek egy user namespace-ben futnak, és a cgroup a user manager alá kerül. A systemd Delegate=yes beállítással a user@<uid>.service engedélyezi a saját al-cgroupok kezelését. A rootless runtime a felhasználó jogosultságával ír a saját cgroupjába. Limit szempontból a legtöbb controller elérhető: cpu.max, memory.max, pids.max stb. Vannak korlátok: a cpuset.cpus beállítás rootlessben gyakran nem működik, mert a cpuset partíciókat a rendszergazda kezeli; az io.max-hoz a megfelelő device hozzáférés kell. Az adminisztrátornak a systemd user service-ét és a cgroup.subtree_control-t kell delegálnia ahhoz, hogy a rootless konténer limitjei ténylegesen alkalmazhatóak legyenek. Ha a runtime nem tud cgroupot delegálni, a limitet a saját userspace szintjén próbálhatja érvényesíteni, de az nem kernel szintű accounting.

36.2.3 Kidolgozott példa

A példa egy konténer indítását és a cgroup v2 accounting kézi ellenőrzését mutatja. Feltételezzük, hogy a d176 laborban létrehozott lab-cpp-demo:local OCI image elérhető a Podman storage-ban; a benne lévő C++ bináris alapból CPU-bound loopot futtat, és alkalmas a throttle/OOM demonstrálására.

Target: labhost, felhasználó labuser, Podman rootless (a systemd user managerrel és Delegate=yes beállítással). Előfeltétel: a d176 labor befejezve, a cgroup v2 aktív (/sys/fs/cgroup unified), a Podman telepítve.

# 1. Konténer indítása CPU és memória limittel
# A --cpus=0.5 -> cpu.max 50000 100000
# A --memory=256M --memory-swap=256M -> memory.max 268435456 és swap 0
# A --pids-limit=64 -> pids.max 64
podman run -d --name lab-cgroup-demo \
  --cpus=0.5 \
  --memory=256M \
  --memory-swap=256M \
  --pids-limit=64 \
  lab-cpp-demo:local

# 2. Azonosítsuk a cgroup elérési útját
podman inspect lab-cgroup-demo --format '{{.State.CgroupPath}}'
# Várható kimenet (rootless): /user.slice/user-1000.slice/user@1000.service/\
#   app.slice/libpod-<id>.scope
# Vagy rövid: /user.slice/user-1000.slice/user@1000.service/...

Most a kapott CG_PATH változóval olvassuk le a limiteket és a számlálókat. A példa egy lehetséges kimenettel:

CG_PATH=$(podman inspect lab-cgroup-demo --format '{{.State.CgroupPath}}')
CG_BASE="/sys/fs/cgroup${CG_PATH}"

echo "=== cpu.max ==="
cat "$CG_BASE/cpu.max"
# Várható: 50000 100000

echo "=== memory.max / memory.swap.max ==="
cat "$CG_BASE/memory.max" "$CG_BASE/memory.swap.max"
# Várható: 268435456 / 0

echo "=== pids.max ==="
cat "$CG_BASE/pids.max"
# Várható: 64

# 3. Figyeljük a CPU-throttlingot, miközben a konténer CPU-bound loopot futtat
sleep 2
echo "=== cpu.stat (részlet) ==="
grep -E 'nr_throttled|throttled_time|usage_usec' "$CG_BASE/cpu.stat"

# Példa várt/illusztratív kimenet (nem mért, hanem a modell alapján várható):
# nr_throttled 173
# throttled_time 82345678
# usage_usec 123000000

# 4. Ellenőrizzük a memóriaeseményeket
echo "=== memory.events ==="
cat "$CG_BASE/memory.events"
# Illusztratív kimenet:
# low 0
# high 0
# max 0
# oom 0
# oom_kill 0

# 5. Takarítás
podman rm -f lab-cgroup-demo

Ellenőrzési feltétel: a cpu.max pontosan 50000 100000; a memory.max bájtban 268435456; a pids.max 64. A cpu.stat nr_throttled értéke másodpercek alatt növekszik, mert a konténer CPU-bound, és a quota miatt folyamatosan throttlingot kap. A memory.events oom_kill értéke 0, ha a memória nem fog elérni a limitre.

Hibajelenség: ha a --cpus=0.5 helyett valaki --cpu-quota=0-t ad, a konténer nem kap CPU időt, a cpu.stat nr_throttled gyorsan nő, és a szolgáltatás teljesen leáll. Ha a memória limit túl alacsony, a memory.events oom_kill 1-re vált, és a konténer egyik processze megszakad.

36.2.4 Tipikus hibák és ellenpróbák

  1. A quota és a weight keverése. Tünet: a szolgáltatás lassú, bár a cpu.weight értékét növelték. Hipotézis: a cpu.max abszolút plafonja független a cpu.weight-től. Adatgyűjtés: cat cpu.max és cat cpu.weight; cat cpu.stat | grep nr_throttled. Ha nr_throttled nő, a quota a hibás. Egy változtatás: emeld a cpu.max értékét (podman update --cpus=1.0 lab-cgroup-demo). Verifikáció: a nr_throttled nem nő tovább, bár a cpu.weight változatlan.

  2. A memory.max OOM, nem a host OOM. Tünet: a konténer processze SIGKILL-jel hal meg, de a host memória kihasználtsága alacsony. Hipotézis: a cgroup saját memory.max-a lépett érvénybe. Adatgyűjtés: grep oom_kill memory.events; ha oom_kill > 0, akkor cgroup OOM. Ellenpróba: növeld a memory.max-ot, vagy csökkentsd a memóriafoglalást. A memory.high korábbi beállítása reclaim-throttle-t okoz, de nem OOM killt; ezt a logokban a hirtelen megjelenő lassulás jelzi.

  3. A page cache túlbeszámítása. Tünet: a memory.current közel van a memory.max-hoz, és a szolgáltatás lelassul, de a tényleges heap nem nőtt. Hipotézis: a page cache (file-backed lapok) tölti ki a limitet. Adatgyűjtés: grep -E 'file|anon' memory.stat. Ha a file nagyobb, mint az anon, a fájl I/O a felelős. Egy változtatás: a memory.high csökkentése mellett a memory.stat-ból megállapítható, hogy a reclaim a cache-t szabadítja fel, nem kell OOM-t okozni. Verifikáció: memory.current csökken, oom_kill marad 0.

  4. A rootless limit nem fogan. Tünet: a rootless Podman konténer nem kapja meg a --cpus=0.5 limitet, a cpu.max továbbra is max. Hipotézis: a user manager Delegate=yes hiánya vagy a cgroup.subtree_control delegálás hiánya. Adatgyűjtés: systemctl show user@1000.service -P Delegate; ha no, akkor a korlát nem delegálható a user cgroupba. Egy változtatás: a systemd user service Delegate=yes beállítása után a Podman újraindítása. Verifikáció: a podman inspect CgroupPath alatt a cpu.max már a beállított értéket mutatja.

  5. A pids.max túllépése nem OOM. Tünet: a C++ szolgáltatás std::thread konstruktorai std::system_error-t dobnak (Resource temporarily unavailable), de a memória nem magas. Hipotézis: a pids.max limit elérése. Adatgyűjtés: cat pids.current és cat pids.max; ha egyenlő, akkor a PID/szál limit a hibás. Egy változtatás: növeld a --pids-limit-et. Verifikáció: a szálak létrejönnek, a pids.events nem nő.

36.2.5 Feladatok

36.2.5.1 F1 – Magyarázó feladat

Egy futó konténer lab-cgroup-demo cgroupjában az alábbi értékek vannak:

  • cpu.max: 30000 100000
  • cpu.weight: 100
  • cpu.stat: nr_throttled növekszik
  • memory.max: 536870912
  • memory.events: oom_kill 0

Magyarázd el, miért lehet a szolgáltatás lassú, és hogyan döntenéd el, hogy a CPU quota vagy a host terhelés okozza-e. Milyen parancsot futtatnál a host PSI ellenőrzéséhez?

36.2.5.2 F2 – Adminisztrációs/konfigurációs feladat

Indíts egy lab-cgroup-cfg nevű konténert a lab-cpp-demo:local image-ből, a következő limitekkel:

  • CPU: 0,75 vCPU
  • Memória: 512 MiB, swap nélkül
  • PIDs limit: 128

Állítsd be úgy, hogy a memórianyomásra a memory.high előbb fékezzen, mint a memory.max; ehhez használj --memory-reservation=384M flaget (a Podman ezt memory.high-ra képezi le). Ellenőrizd a cgroupban a cpu.max, memory.max, memory.high, memory.swap.max és pids.max értékét, majd távolítsd el a konténert.

36.2.5.3 F3 – Diagnosztikai/failure/recovery feladat

A lab-cgroup-fail konténer OOM-kill áldozata lett: a memory.events oom_kill értéke 2, a konténerben futó C++ szolgáltatás meghalt. A memória limit 256M, a swap limit 0. Feladat: derítsd ki a memory.stat-ból, hogy anon vagy file memória okozta-e a túlfutást; ha anon, akkor növeld a limitet 512 MiB-ra, és ha file, akkor állíts memory.high-ot 384 MiB-ra, hogy a reclaim korábban induljon. Indítsd újra a konténert, és igazold, hogy az oom_kill esemény nem nő tovább legalább 10 másodpercig.

36.2.6 Megoldások

36.2.6.1 M1

A cpu.max 30000 100000 azt jelenti, hogy a konténer processzei minden 100 ms periódusból legfeljebb 30 ms CPU-időt kaphatnak. A cpu.weight 100 alapértelmezett, de mivel a quota abszolút, a host még üresjáratban sem enged többet. A növekvő nr_throttled azt mutatja, hogy a CPU-bound szolgáltatás eléri a plafont, és a kernel leállítja a futást. A host terhelés ellenőrzéséhez a /proc/pressure/cpu-t kell olvasni: ha a host some PSI alacsony, de a cgroup nr_throttled nő, akkor a konténer saját quota a szűk keresztmetszet. Postcondition: a tanuló meg tudja különböztetni a quota-throttlingot a host CPU-nyomástól.

36.2.6.2 M2

# Target: labhost, labuser, Podman rootless
podman run -d --name lab-cgroup-cfg \
  --cpus=0.75 \
  --memory=512M \
  --memory-swap=512M \
  --memory-reservation=384M \
  --pids-limit=128 \
  lab-cpp-demo:local

CG_PATH=$(podman inspect lab-cgroup-cfg --format '{{.State.CgroupPath}}')
CG_BASE="/sys/fs/cgroup${CG_PATH}"

echo "cpu.max: $(cat $CG_BASE/cpu.max)"
echo "memory.max: $(cat $CG_BASE/memory.max)"
echo "memory.high: $(cat $CG_BASE/memory.high)"
echo "memory.swap.max: $(cat $CG_BASE/memory.swap.max)"
echo "pids.max: $(cat $CG_BASE/pids.max)"

# Várható kimenetek:
# cpu.max: 75000 100000
# memory.max: 536870912
# memory.high: 402653184
# memory.swap.max: 0
# pids.max: 128

# Cleanup
podman rm -f lab-cgroup-cfg

Postcondition: a konténer elindult, a cgroupban a limitértékek a kértnek felelnek meg; a swap limit 0, a memory.high alacsonyabb, mint a memory.max. A cleanup után a konténer nem fut.

36.2.6.3 M3

Először azonosítsuk a memóriaforrás típusát:

CG_PATH=$(podman inspect lab-cgroup-fail --format '{{.State.CgroupPath}}')
CG_BASE="/sys/fs/cgroup${CG_PATH}"
grep -E '^(anon|file|shmem|slab)' "$CG_BASE/memory.stat"

Ha az anon nagy (például 250 MiB a 256 MiB-ból), akkor a C++ heap túlfutás a valószínű ok. A recovery: álljunk le a konténerrel, indítsuk újra magasabb limittel.

podman rm -f lab-cgroup-fail
podman run -d --name lab-cgroup-fail \
  --memory=512M --memory-swap=512M \
  lab-cpp-demo:local

# Várjunk 10 másodpercet, majd ellenőrizzük
sleep 10
CG_PATH=$(podman inspect lab-cgroup-fail --format '{{.State.CgroupPath}}')
grep 'oom_kill' "/sys/fs/cgroup${CG_PATH}/memory.events"
# Várható: oom_kill 0

Ha viszont a file volt meghatározó (page cache), akkor nem a heap, hanem a fájl I/O a hibás. Ekkor a memory.high beállítás segít korábbi reclaimet kiváltani:

podman rm -f lab-cgroup-fail
podman run -d --name lab-cgroup-fail \
  --memory=256M --memory-swap=256M --memory-reservation=192M \
  lab-cpp-demo:local
sleep 10
CG_PATH=$(podman inspect lab-cgroup-fail --format '{{.State.CgroupPath}}')
grep 'oom_kill' "/sys/fs/cgroup${CG_PATH}/memory.events"
# Várható: oom_kill 0, mert a reclaim a cache-t szabadítja fel

Postcondition: az oom_kill számláló nem nő tovább az újraindítás után, a konténer fut, és a memória típusa alapján megfelelő stratégiát választottunk (limit emelés vagy memory.high korai reclaim).

36.2.7 Rövid összefoglaló

A konténer-erőforrások elszámolása a cgroup v2 hierarchiában történik, amelyet a systemd driver delegál a runtime-oknak. A CPU-nál a cpu.max abszolút plafon, a cpu.weight relatív súly; a throttle-t a cpu.stat mutatja. A memóriánál a memory.max hard OOM-kill, a memory.high soft reclaim-throttle; a memory.events oom_kill azonnali bizonyíték. A page cache a memory.current része, ezért a memory.stat anon/file bontása szükséges. A pids limit a szálakat is korlátozza, a PSI pedig elválasztja a saját limitet a host nyomástól. Rootlessben a systemd user manager Delegate=yes beállítása kell a korlátok érvényesítéséhez.

Továbbhasznált definíciók:

  • Container cgroup accounting: a konténer runtime által delegált cgroup v2 csomópontba sorolt processzek kernel szintű erőforrás-számlálása és limitálása.
  • CPU throttling: a cpu.max quota által kiváltott futásidő-korlátozás, amely idle hoston is bekövetkezik.
  • memory.events.oom_kill: a cgroup saját memória-limitjének túllépése miatt a kernel által megölt processzek száma.
