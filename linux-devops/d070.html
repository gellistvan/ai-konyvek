14.5 Package- és dependency incidenslabor

14.5.1 Motiváció: amikor a csomagkezelő szerint minden rendben, a futás mégis meghiúsul

Egy szenior C++ fejlesztő a natív build és a linker részét jól ismeri, de éles üzemeltetésben a hiba gyakran nem a forrásban van. Tipikus eset: egy éjszakai frissítés vagy kézi „gyors beavatkozás” után a szolgáltatás nem indul, a naplóban pedig csak ennyi áll:

error while loading shared libraries: libbz2.so.1.0: cannot open shared object file: No such file or directory

A bzip2 csomag telepítettnek látszik, mégis hiányzik egy megosztott könyvtára. Ez a fejezet azt a módszert építi fel, amellyel a telepített csomagadatbázis és a futtatókörnyezet valós állapota közötti eltérést hipotézisvezérelten felderítjük, javítjuk, majd rebuildelhető manifesttel és változtatási naplóval dokumentáljuk. Minden módosító parancs labhoston, izolált VM-en fut, a --force-depends típusú beavatkozást éles rendszeren soha ne alkalmazzuk.

14.5.2 Definíció és működés

A vizsgált állapot három rétege:

  1. Installed package manifest – a dpkg adatbázisa (/var/lib/dpkg/status, /var/lib/dpkg/info) tárolja, hogy melyik bináris csomag milyen verzióban és architektúrában telepített. Lekérdezése:

    dpkg-query -W -f='${binary:Package}\t${Version}\t${Architecture}\n'

    Ez a desired state a csomagkezelő szempontjából.

  2. Runtime library állapot – a dinamikus linker (ld.so) a /etc/ld.so.cache és a szabványos könyvtárkereső utak alapján oldja fel a futtatható állomány DT_NEEDED bejegyzéseit. Az ldd ezt a feloldást jeleníti meg anélkül, hogy a programot elindítaná. A hiányzó .so itt azonnal látszik.

  3. Repository és package cache állapot – az apt a /etc/apt/sources.list és /etc/apt/sources.list.d/*.sources fájlokból tudja, melyik repóból és milyen verzió telepíthető. A /var/cache/apt/archives/ a letöltött .deb csomagok gyorsítótára. Az apt-cache policy <package> mutatja a jelölt és a telepített verziót, valamint a forrást.

A package DB és a runtime inkonzisztencia azt jelenti, hogy a dpkg adatbázisa szerint egy függőség nem hiányzik, a fájlrendszerből mégis hiányzik a csomag által szolgáltatott fájl. Ennek tipikus okai: dpkg --remove --force-depends, kézi fájltörlés, sérült csomagarchívum, félbeszakadt frissítés.

14.5.3 Kidolgozott példa: hiányzó shared library javítása

A labor környezet: labhost01 VM, labuser sudo joggal, Ubuntu Server 24.04 LTS alapprofil. A csomagneveket a labor előtt ellenőrizni kell a tényleges repóban, mert a t64 átállás módosíthatja az utótagokat.

14.5.3.1 1. Baseline manifest és bizonyíték

# target: labhost01
# user: labuser, sudo szükséges a későbbi lépésekhez
mkdir -p "$HOME/package-lab/baseline"
cd "$HOME/package-lab"

dpkg-query -W -f='${binary:Package}\t${Version}\t${Architecture}\n' \
  bzip2 libbz2-1.0 > baseline/packages.tsv

ldd /usr/bin/bzip2 > baseline/ldd.txt

sha256sum /usr/bin/bzip2 > baseline/bzip2.sha256

Várt kimenet (illusztratív, nem tényleges futtatásból):

$ cat baseline/packages.tsv
bzip2       1.0.8-5    amd64
libbz2-1.0  1.0.8-5    amd64

$ grep bz2 baseline/ldd.txt
libbz2.so.1.0 => /lib/x86_64-linux-gnu/libbz2.so.1.0 (0x00007f...)

14.5.3.2 2. Hiba injektálása

A --force-depends szándékosan megkerüli a függőségellenőrzést. Csak labhoston használjuk, mert törött csomagállapotot hoz létre:

sudo dpkg --remove --force-depends libbz2-1.0

A csomagkezelő eltávolítja a libbz2-1.0 csomagot, de a bzip2 csomagot a függőségi hiba ellenére a helyén hagyja. A bzip2 bináris megmarad, a szükséges .so azonban eltűnik.

14.5.3.3 3. Diagnosztika

A hibát először a runtime oldalról látjuk:

# target: labhost01
ldd /usr/bin/bzip2

Várt kimenet:

linux-vdso.so.1 (0x00007ffd...)
libbz2.so.1.0 => not found
libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f...)
/lib64/ld-linux-x86-64.so.2 (0x00007f...)

A not found megmutatja, hogy a linker nem találja a libbz2.so.1.0 fájlt. Most ellenőrizzük a csomagadatbázist:

dpkg -l libbz2-1.0 bzip2
apt-get check
dpkg --audit

Várt eredmény:

$ dpkg -l libbz2-1.0 bzip2
Desired=Unknown/Install/Remove/Purge/Hold
| Status=Not/Inst/Conf-files/Unpacked/halF-conf/Half-inst/trig-aWait/Trig-pend
|/ Err?=(none)/Reinst-required (Status,Err: uppercase=bad)
||/ Name           Version      Architecture Description
+++-==============-============-============-=================================
un  libbz2-1.0     <none>       <none>       (no description available)
ii  bzip2          1.0.8-5      amd64        high-quality block-sorting file compressor

A libbz2-1.0 állapota un (unknown, not installed), míg bzip2 ii (installed). Az apt-get check a függőségi hiba miatt nem üres:

You might want to run 'apt --fix-broken install' to correct these.
The following packages have unmet dependencies:
 bzip2 : Depends: libbz2-1.0 but it is not installed

A dpkg --audit nem feltétlenül ad ki hibát, mert a --force-depends eltávolítás után a bzip2 csomag metainformációi nem sérültek, csak a függősége nem teljesül. Az apt-get check a függőségi szintet, a dpkg --audit a csomagjelek konzisztenciáját vizsgálja.

A repository állapot ellenőrzése:

apt-cache policy libbz2-1.0
ls -l /var/cache/apt/archives/libbz2*

Ez megmutatja, hogy a csomag letölthető-e a beállított repóból, és van-e már cache-ben a .deb.

14.5.3.4 4. Javítás

A legegyszerűbb a bzip2 függőségét újratelepíteni:

sudo apt-get -f install

Ez a törött függőséget úgy javítja, hogy telepíti a hiányzó libbz2-1.0 csomagot. Ha a cache-ben nincs meg, letölti a repóból. Élesben először always szimuláljunk:

apt-get -s -f install

A -s (simulate) megmutatja, mit tenne a rendszer, anélkül, hogy módosítana. A postcondition ellenőrzése:

# target: labhost01
ldd /usr/bin/bzip2 | grep bz2
apt-get check
dpkg-query -W -f='${binary:Package}\t${Version}\t${Architecture}\n' bzip2 libbz2-1.0

Várt kimenet:

libbz2.so.1.0 => /lib/x86_64-linux-gnu/libbz2.so.1.0 (0x00007f...)

dpkg-query -W -f='${binary:Package}\t${Version}\t${Architecture}\n' bzip2 libbz2-1.0
bzip2       1.0.8-5    amd64
libbz2-1.0  1.0.8-5    amd64

Az apt-get check üres kimenettel jelzi, hogy nincs törött függőség.

14.5.3.5 5. Provenance report és rebuildelhető manifest

A javítás után készítsünk dokumentumot a csomageredetről:

# target: labhost01
mkdir -p "$HOME/package-lab/post-fix"
cd "$HOME/package-lab"

apt-cache policy bzip2 libbz2-1.0 > post-fix/policy.txt
dpkg -s bzip2 libbz2-1.0 > post-fix/status.txt

# Rebuildelhető manifest a teljes gépről
dpkg-query -W -f='${binary:Package}\t${Version}\t${Architecture}\n' \
  > post-fix/installed-manifest-$(date -I).tsv

A policy.txt tartalmazza a repository prioritásokat, a status.txt a csomag maintained by, szekció, forrás és más metadatokat. A manifest a teljes telepített készletet rögzíti, így később egy másik hoston reprodukálható.

A változtatási napló legyen egyszerű, de ellenőrizhető:

2025-04-01 10:15 UTC labhost01 labuser
  baseline: packages.tsv, ldd.txt, bzip2.sha256
  command: sudo dpkg --remove --force-depends libbz2-1.0
  symptom: ldd /usr/bin/bzip2 -> libbz2.so.1.0 => not found
  fix: sudo apt-get -f install
  postcondition: apt-get check clean, ldd resolves libbz2.so.1.0
  rollback: sudo apt-get install --reinstall bzip2 libbz2-1.0

14.5.4 Hibák és ellenpróbák

  • ldd félrevezethet nem megbízható bináris futtatásakor, mert egyes esetekben a dinamikus linker kódot is futtathat. Ezért a laborban csak ismert, kontrollált binárist (/usr/bin/bzip2) használunk.
  • A apt-get -f install néha eltávolít csomagokat, ha a függőségi gráf másképp nem oldható fel. Ezért mindig -s szimulációval ellenőrizzük, és rollback tervet rögzítünk.
  • A dpkg --verify nem észlel minden hiányzó fájlt, mert a csomagok egy részének nincs md5sums listája, illetve a konfigurációs fájlokat külön kezeli. A jelen példában a hiányzó .so a másik csomaghoz tartozik, ezért a dpkg --verify bzip2 nem jelez hibát.
  • A dpkg --remove --force-depends élesben tilos. Helyette a függőségi gráfot módosító csomagváltozásoknál az apt szokásos parancsait használjuk, vagy dedikált labon reprodukáljuk az incidenst.
  • A package cache nem biztonsági mentés. A /var/cache/apt/archives/ gyorsítótár, nem garantáltan tartalmazza az összes régi csomagot, ezért a rollbackhez a manifest és a repository verziók használandók.

14.5.5 Feladatok

14.5.5.1 1. feladat: Baseline manifest és hipotézis felállítása

Futtasd le a fenti baseline lépéseket egy labhost01 labVM-en. Rögzítsd a bzip2 és libbz2-1.0 csomagok verzióját, architektúráját és a bzip2 ldd kimenetét. Hipotézisként írd le: mi történik, ha a libbz2-1.0 csomagot --force-depends módon eltávolítjuk? Melyik réteg (manifest, runtime, repository) mutat először hibát?

14.5.5.2 2. feladat: Hiba injektálása, diagnosztika és javítás

A labon hajtsd végre a kidolgozott példa injektálási lépését, majd a hibát a ldd, dpkg -l, apt-get check és apt-cache policy segítségével diagnosztizáld. Javítsd apt-get -f install paranccsal. Ellenőrizd a postconditiont: ldd /usr/bin/bzip2 mutatja a libbz2.so.1.0-t, az apt-get check üres, és a dpkg-query mindkét csomagot ii állapotúnak jelzi. Készíts változtatási naplót a fenti formátumban.

14.5.5.3 3. feladat: Partial upgrade állapot diagnosztikája és recovery

Szimulálj partial upgrade állapotot: indíts el egy apt install parancsot, majd szakítsd meg a folyamatot (pl. Ctrl-C a letöltés vagy a kicsomagolás közben, vagy küldj SIGSTOP-ot az apt folyamatnak egy másik terminálból, majd kill). A cél az, hogy a csomagrendszer unpacked vagy half-installed állapotú csomagot hagyjon. Diagnosztizáld a dpkg --audit, /var/log/dpkg.log és /var/log/apt/term.log segítségével. Javítsd sudo dpkg --configure -a majd sudo apt-get -f install paranccsal. Ellenőrizd, hogy az apt-get check és dpkg --audit nem jelez hibát. A bzip2 és libbz2-1.0 csomagok maradjanak telepített, konzisztens állapotban. Rögzítsd a recovery lépéseket a változtatási naplóban.

14.5.6 Megoldások

14.5.6.1 1. feladat megoldása

A baseline manifest:

# target: labhost01, user: labuser
mkdir -p "$HOME/package-lab/baseline"
cd "$HOME/package-lab"

dpkg-query -W -f='${binary:Package}\t${Version}\t${Architecture}\n' \
  bzip2 libbz2-1.0 > baseline/packages.tsv
ldd /usr/bin/bzip2 > baseline/ldd.txt
sha256sum /usr/bin/bzip2 > baseline/bzip2.sha256

Hipotézis: a dpkg --remove --force-depends eltávolítja a libbz2-1.0 csomagot, de a bzip2 bináris a helyén marad. Elsőként a runtime réteg (az ldd) fog hibát jelezni, mert a fájlszintű linkfeloldás már a program indítása előtt meghiúsul. A manifest szint csak az apt-get check futásakor mutat törött függőséget.

14.5.6.2 2. feladat megoldása

# target: labhost01, user: labuser, sudo szükséges
sudo dpkg --remove --force-depends libbz2-1.0

# Diagnosztika
ldd /usr/bin/bzip2
dpkg -l libbz2-1.0 bzip2
apt-get check
dpkg --audit
apt-cache policy libbz2-1.0

# Javítás szimulációval
apt-get -s -f install

# Tényleges javítás
sudo apt-get -f install

# Postcondition ellenőrzése
ldd /usr/bin/bzip2 | grep bz2
apt-get check
dpkg-query -W -f='${binary:Package}\t${Version}\t${Architecture}\n' bzip2 libbz2-1.0

Postcondition: az ldd a libbz2.so.1.0-t elérési úttal mutatja, az apt-get check üres, a dpkg-query mindkét csomagot telepített ii állapotban listázza. A változtatási napló a példa formátumban készül.

14.5.6.3 3. feladat megoldása

A partial upgrade szimulálásához például egy kis csomag telepítését szakítjuk meg. Például:

# target: labhost01, user: labuser, sudo szükséges
sudo apt install -y zlib1g-dev &  # háttérben
# Rövid várakozás után megszakítás
kill -STOP %1   # felfüggesztés
kill -9 %1      # erőszakos leállítás

Fontos, hogy a felfüggesztés/kill időzítését úgy válasszuk, hogy a dpkg ténylegesen csomagot bontson ki. Ha nem állítható be megbízhatóan, használjunk dpkg --unpack parancsot közvetlenül, majd a folyamat megszakítását. A lényeg a half-installed vagy unpacked állapot előidézése.

Diagnosztika:

dpkg --audit
tail -n 50 /var/log/dpkg.log
grep -i "error\|warning" /var/log/apt/term.log | tail -n 50

A dpkg --audit kilistázza azokat a csomagokat, amelyek nincsenek teljesen telepítve. A naplók a megszakadt művelet pontos pontját mutatják.

Recovery:

sudo dpkg --configure -a
sudo apt-get -f install

A dpkg --configure -a a félbemaradt konfigurációs lépéseket fejezi be, az apt-get -f install a függőségi problémákat javítja. Postcondition: dpkg --audit üres, apt-get check üres, dpkg -l bzip2 libbz2-1.0 telepített állapotú. A változtatási napló tartalmazza a megszakítás okát, a diagnosztikai bizonyítékot és a recovery parancsokat.

14.5.7 Rövid összefoglaló

A package- és dependency incidens lényege, hogy a csomagkezelő desired state adatbázisa és a fájlrendszerbeli observed state eltér egymástól. A hiányzó shared library diagnosztikája mindig három réteget vizsgál: a runtime linker ldd kimenetét, a dpkg manifestet (dpkg-query, dpkg -l) és a repository/cache állapotot (apt-cache policy). A javítás előtt szimuláljuk az apt-get -s -f install kimenetét, majd a tényleges parancs után ellenőrizzük a postconditiont. A változás mindig rebuildelhető manifestet és változtatási naplót kap, hogy a rendszer állapota reprodukálható legyen. Továbbhasznált definíciók: installed package manifest, package DB és runtime inkonzisztencia, rebuildelhető manifest.

14.5.8 Források és ellenőrzési hiányok

  • Ubuntu Server documentation – általános csomagkezelési háttér; a jelen példa verzióit nem ellenőriztem.
  • Debian documentation – a dpkg/apt működés általános leírása; a konkrét csomagnevek eltérhetnek a labhoston.
  • Linux man-pages – ldd(1), dpkg(1), apt-get(8) hivatkozások.

Ellenőrzési hiányok: a bzip2 és libbz2-1.0 csomag pontos neve, verziója és a t64 utótag az Ubuntu 24.04 LTS tényleges repójában a lab futtatása előtt ellenőrizendő. A példákban szereplő kimenetek illusztratívak, nem tényleges futtatásból származnak. Az apt install megszakításával szimulált partial upgrade időzítése környezetfüggő; szükség esetén közvetlen dpkg --unpack és megszakítás használható.
