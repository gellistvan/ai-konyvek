31.4 WireGuard, tunneling és távoli hálózat

31.4.1 Miért nem elég, hogy „felépült a VPN”?

A távoli kliens sikeresen hitelesíti az átjárót, a csomagszámlálók nőnek, az alkalmazás mégsem érhető el. Ez nem ellentmondás: a titkosított kapcsolat csak egy réteg. A működéshez helyes útvonal, visszaút, csomagméret és hozzáférési szabály is kell.

A virtuális magánhálózat (Virtual Private Network, VPN) idegen vagy nem megbízható átviteli hálózaton biztosít logikai magánhálózati kapcsolatot. A tunnel, vagyis alagút egy belső csomagot külső csomagba ágyaz. A tunnelezés önmagában nem jelent titkosítást; a WireGuard hitelesített, titkosított IP-alagutat valósít meg UDP fölött.

A WireGuard-identitás nyilvános kulcshoz kötött végpontazonosság. Nem felhasználói bejelentkezés, nem alkalmazásjogosultság, és nem a TLS-nél megismert tanúsítványlánc. Egy ellopott végpontkulcs birtokosa a kulcshoz rendelt hálózati identitást használhatja.

Az üzemeltetési szerződés ezért legalább ezt rögzítse:

Kérdés Szerződés
Ki kapcsolódhat? Tulajdonoshoz rendelt nyilvános kulcs
Milyen címeket képviselhet? Peerhez rendelt belső forrásprefixek
Merre küldünk neki? Linux-route és WireGuard-peer kiválasztása
Mit érhet el? Tűzfal- és alkalmazáspolicy
Hogyan vonjuk vissza? Peer eltávolítása, kulcsrotáció, ellenőrzés

31.4.2 Peer, kulcs és az AllowedIPs két szerepe

A partner (peer) a WireGuard konfigurációjában egy nyilvános kulccsal azonosított másik végpont. Az Endpoint ennek külső IP-címe és UDP-portja; nem maga az identitás. A végpontcím hitelesített forgalom alapján változhat, ami mobil klienseknél hasznos.

Az AllowedIPs két külön feladatot lát el:

  1. Küldéskor: a belső célcím alapján kiválasztja a peert; egyező prefixek között a leghosszabb prefix számít.
  2. Fogadáskor: ellenőrzi, hogy a hitelesített peer jogosult-e a belső csomag forráscímét használni.

Ez nem TCP/UDP-portokra vagy alkalmazásszerepkörökre vonatkozó jogosultságkezelés. Ha egy klienshez 10.204.154.1/32 tartozik, abból nem következik, hogy minden belső szolgáltatást elérhet.

A Linux útválasztása és a peer kiválasztása is külön lépés:

  1. A belső célcímhez tartozó route a WireGuard-interfészt választja.
  2. Az AllowedIPs megadja a célhoz tartozó peert.
  3. A WireGuard titkosít, majd UDP-csomagot készít.
  4. A külső célhoz, az Endpoint címéhez újabb útvonalválasztás történik.
  5. A fogadó fél hitelesít, visszafejt, forráscímet ellenőriz.
  6. A belső csomag a helyi vagy továbbítási tűzfalon halad át.

A wg set önmagában nem telepít Linux-route-okat. A wg-quick segédprogram jellemzően igen, de ezt a labor nem használja: a két állapotot külön építjük fel.

31.4.3 Kidolgozott példa: távoli kliens és belső szolgáltatás

A labor három hálózati névteret használ egyetlen VM-en. Nincs internetkapcsolat, NAT vagy fizikai hálózatmódosítás.

Célgép és jogosultság minden alábbi parancshoz: lab-vpn-vm, Ubuntu Server 24.04 LTS amd64, helyi konzol, root, UID 0. Előfeltétel a telepített iproute2, wireguard-tools, nftables, python3, curl és iputils-ping.

Névtér Interfész és cím Szerep
lab-vpn-c lab-uc: 10.203.154.1/30 Kliens külső kapcsolata
lab-vpn-c lab-wg: 10.204.154.1/30 Kliens tunnelcíme
lab-vpn-g lab-ug: 10.203.154.2/30 Átjáró, UDP/51820
lab-vpn-g lab-wg: 10.204.154.2/30 Tunnel másik vége
lab-vpn-g lab-lg: 10.205.154.1/24 Belső hálózati átjáró
lab-vpn-s lab-ls: 10.205.154.10/24 HTTP-szolgáltatás, TCP/8080

A veth-párok: lab-uc–lab-ug, illetve lab-lg–lab-ls. Más összeköttetés nincs.

Kívánt állapot: a kliens kizárólag a kijelölt szerver TCP/8080 portját érheti el továbbított forgalommal.
Konfigurációforrás: az alábbi parancssorok.
Tárolt állapot: ideiglenes kulcsok és tesztfájlok a /run/lab-d154 könyvtárban; hálózati állapot a kernelben. Újraindítást nem él túl.
Tulajdonos: a labort végző személy; lejárat: a gyakorlat vége.
Visszaállítás: a három névtér és a név szerint felsorolt fájlok eltávolítása.

Indítás előtt ellenőrizd a cím- és névütközést. Bár a címek izolált névterekbe kerülnek, az inventoryban ne szerepeljenek más labor hálózataként.

# lab-vpn-vm, UID 0; külön root Bash-munkamenet.
set -euo pipefail
test "$(hostname -s)" = lab-vpn-vm
test "$(id -u)" -eq 0

uname -r
dpkg-query -W iproute2 wireguard-tools nftables python3 curl iputils-ping
ip -br address
ip route show table all
ip netns list

test ! -e /run/lab-d154
for n in lab-vpn-c lab-vpn-g lab-vpn-s; do
    if ip netns list | grep -q "^${n}\b"; then
        echo "Már létező névtér: $n" >&2
        exit 1
    fi
done
for i in lab-uc lab-ug lab-lg lab-ls; do
    if ip link show dev "$i" >/dev/null 2>&1; then
        echo "Már létező interfész: $i" >&2
        exit 1
    fi
done

A verziókimenetet őrizd meg a jegyzőkönyvben. Ez itt verziórögzítési eljárás, nem előre ellenőrzött csomagverzió-lock.

31.4.3.1 Hálózat és kulcsok létrehozása

A következő blokkok ugyanabban a root Bash-munkamenetben folytatódnak. A generált kulcsok kizárólag ehhez az eldobható laborhoz tartoznak; privát kulcsot nem írunk a tananyagba vagy a terminálkimenetre.

umask 077
mkdir /run/lab-d154

for n in lab-vpn-c lab-vpn-g lab-vpn-s; do
    ip netns add "$n"
    ip -n "$n" link set lo up
done

ip link add lab-uc type veth peer name lab-ug
ip link set lab-uc netns lab-vpn-c
ip link set lab-ug netns lab-vpn-g

ip link add lab-lg type veth peer name lab-ls
ip link set lab-lg netns lab-vpn-g
ip link set lab-ls netns lab-vpn-s

while read -r ns dev cidr; do
    ip -n "$ns" address add "$cidr" dev "$dev"
    ip -n "$ns" link set "$dev" up
done <<'EOF'
lab-vpn-c lab-uc 10.203.154.1/30
lab-vpn-g lab-ug 10.203.154.2/30
lab-vpn-g lab-lg 10.205.154.1/24
lab-vpn-s lab-ls 10.205.154.10/24
EOF

for side in c g; do
    wg genkey > "/run/lab-d154/lab-${side}.key"
    wg pubkey < "/run/lab-d154/lab-${side}.key" \
        > "/run/lab-d154/lab-${side}.pub"
    ip -n "lab-vpn-${side}" link add lab-wg type wireguard
done

ip netns exec lab-vpn-c wg set lab-wg \
    private-key /run/lab-d154/lab-c.key \
    peer "$(cat /run/lab-d154/lab-g.pub)" \
    endpoint 10.203.154.2:51820 \
    allowed-ips 10.204.154.2/32,10.205.154.0/24

ip netns exec lab-vpn-g wg set lab-wg \
    private-key /run/lab-d154/lab-g.key \
    listen-port 51820 \
    peer "$(cat /run/lab-d154/lab-c.pub)" \
    allowed-ips 10.204.154.1/32

ip -n lab-vpn-c address add 10.204.154.1/30 dev lab-wg
ip -n lab-vpn-g address add 10.204.154.2/30 dev lab-wg

for n in lab-vpn-c lab-vpn-g; do
    ip -n "$n" link set lab-wg mtu 1420 up
done

ip -n lab-vpn-c route add 10.205.154.0/24 \
    dev lab-wg src 10.204.154.1
ip -n lab-vpn-s route add 10.204.154.1/32 via 10.205.154.1
ip netns exec lab-vpn-g sysctl -w net.ipv4.ip_forward=1

A WireGuard-interfészek eleve saját névterükben születnek, ezért külső UDP-forgalmuk is ott halad. Ez fontos: egy másik névtérben létrehozott, majd áthelyezett WireGuard-interfész külső socketje az eredeti névtérhez kötődhet.

Az átjáró nem kap előre kliens-Endpoint értéket: azt az első hitelesített kliensforgalomból tanulja meg.

31.4.3.2 Hozzáférési policy és tesztszolgáltatás

A labor átjárójának input forgalmát itt nem korlátozzuk; az izolált külső hálózaton a WireGuard UDP-portja elérhető. Éles átjárón külön input policy kell a WireGuard-porthoz és a szükséges ICMP-hibákhoz is.

ip netns exec lab-vpn-g nft -f - <<'EOF'
table inet lab-vpn {
    chain lab-forward {
        type filter hook forward priority filter; policy drop;

        ct state established,related counter accept
        iifname "lab-wg" oifname "lab-lg" \
            ip saddr 10.204.154.1 ip daddr 10.205.154.10 \
            tcp dport 8080 ct state new counter accept
        counter drop
    }
}
EOF

mkdir /run/lab-d154/lab-www
printf 'lab-ok\n' > /run/lab-d154/lab-www/index.html

ip netns exec lab-vpn-s python3 -m http.server 8080 \
    --bind 10.205.154.10 --directory /run/lab-d154/lab-www \
    > /run/lab-d154/lab-http.log 2>&1 &

A belső adatút:

Szakasz Forrás → cél Védelem
Kliens belső csomagja 10.204.154.1 → 10.205.154.10:8080 Tunnelbe irányítva
Külső átvitel 10.203.154.1 → 10.203.154.2:51820 WireGuard-titkosítás
Átjáró → szerver 10.204.154.1 → 10.205.154.10:8080 Visszafejtett IP-forgalom
Válasz Szerver → 10.204.154.1 Explicit visszaút az átjárón át

A szerver felé már nincs WireGuard-titkosítás. Éles alkalmazásnál a TLS és az alkalmazáshitelesítés továbbra is indokolt. NAT nem szükséges, mert a visszaút ismert; ezt különítsd el a címfordítás működésétől.

31.4.4 Ellenőrzés és hibakeresési sorrend

Minden alábbi eredmény várt, nem ténylegesen mért.

# lab-vpn-vm, UID 0
ip -n lab-vpn-c route get 10.205.154.10
ip netns exec lab-vpn-c curl --max-time 5 http://10.205.154.10:8080/
ip netns exec lab-vpn-c wg show lab-wg
ip netns exec lab-vpn-g nft list table inet lab-vpn

Várt postcondition:

  • A route lab-wg interfészt és 10.204.154.1 forrást választ.
  • A HTTP-válasz lab-ok.
  • A wg show sikeres kézfogásra utaló adatot és növekvő átviteli számlálókat mutat.
  • Az engedélyező tűzfalszabály számlálója nő.

Ellenpróba:

ip netns exec lab-vpn-c curl --max-time 2 \
    http://10.205.154.10:8081/ || true
ip netns exec lab-vpn-g nft list table inet lab-vpn

Várt a sikertelen kérés és a dobási számláló növekedése. A timeout önmagában nem bizonyít tűzfalhibát; itt a szabályszámláló ad hozzá bizonyítékot.

Tünet Következő ellenőrzés
Nincs kézfogás Külső route, UDP-elérhetőség, publikus kulcsok
Van kézfogás, nincs belső forgalom Linux-route és mindkét oldali AllowedIPs
Kérés eljut, válasz nem Szerver visszaútja, továbbítási policy
Kis kérés működik, nagy adat megakad MTU, PMTU és ICMP-hibák átengedése
Csak a név szerinti elérés hibás Resolver, DNS-route, split-DNS policy

Egyszerre egy dolgot változtass, majd ugyanazzal a kéréssel ellenőrizz.

31.4.5 MTU, overhead és PMTU

A tunnel csökkenti az egy külső csomagban továbbítható belső csomag méretét. WireGuard-adatcsomagnál, IP-opciók és kiterjesztő fejlécek nélkül:

  • külső IPv4: 20 B IP + 8 B UDP + 32 B WireGuard = 60 B;
  • külső IPv6: 40 B IP + 8 B UDP + 32 B WireGuard = 80 B.

A kezdeti méretkeret:

$$ M_{\text{belső}}\,[\mathrm{B}] \leq M_{\text{külső\,út}}\,[\mathrm{B}] - H_{\text{beágyazás}}\,[\mathrm{B}] $$

1500 B külső út-MTU mellett ez IPv4-nél 1440 B, IPv6-nál 1420 B. Ezek számított keretek, nem univerzális beállítások: további tunnel, kisebb külső PMTU és paddingkezelés is számít. A labor 1420 B értéke a megadott, 1500 B MTU-jú veth-úthoz megfelelő konzervatív választás.

# 1392 B ICMP-adat + 8 B ICMP + 20 B belső IPv4 = 1420 B
ip netns exec lab-vpn-c ping -c 2 -M do -s 1392 10.204.154.2

Ez a tunnelcímek közötti méretpróba, nem a HTTP-út teljes bizonyítéka. A PMTU-felderítés (Path MTU Discovery) számára szükséges ICMPv4 „fragmentation needed” és ICMPv6 „Packet Too Big” üzenetek blokkolása fekete lyukat okozhat. A TCP MSS módosítása csak TCP-re hat; nem általános javítás minden tunnelcsomagra.

31.4.6 Telephelyek, teljes tunnel és DNS

Távoli hozzáférésnél (remote access) rendszerint egy klienscímet vagy kliensprefixet rendelsz a peerhez. Telephelyek közötti kapcsolatnál (site-to-site) teljes LAN-prefixeket: mindkét átjárón kell route, továbbítás, tűzfalszabály, és a helyi gépeknek is tudniuk kell a távoli hálózat visszaútját. Az átfedő telephelyi címtartomány tervezési konfliktus; a tunnel nem oldja meg.

Osztott tunnel (split tunnel) esetén csak kijelölt hálózatok haladnak a VPN-en. A labor ilyen. Teljes tunnel (full tunnel) esetén az alapértelmezett IPv4- és szükség szerint IPv6-forgalom is: 0.0.0.0/0, illetve ::/0.

Teljes tunnelnél a külső WireGuard-végpont útját ki kell venni a tunnelből, vagy megfelelő policy routingot kell használni. Különben az alagút saját UDP-csomagjait próbálhatná önmagába küldeni. A wg-quick ezt speciális routingmechanizmussal kezeli; ne helyettesítsd ellenőrizetlen alapértelmezett-route-cserével. Az IPv6 kihagyása a kívánt teljes tunnelből megkerülő adatút lehet.

A WireGuard protokoll nem oszt DNS-konfigurációt. Külön döntés:

  • melyik resolver legyen elérhető a tunnelen;
  • mely névterek használják a belső resolvert;
  • hogyan oldható fel a VPN-végpont neve a tunnel felépülése előtt;
  • mi történjen tunnelhiba esetén.

A wg-quick DNS= mezője segédprogram-integráció, nem WireGuard-protokollfunkció; működése a helyi resolverkezelőtől függ.

31.4.7 Kulcséletciklus, keepalive és megfigyelés

A WireGuard automatikus munkamenetkulcs-frissítése nem helyettesíti a hosszú életű identitáskulcs rotációját. Rotációnál új kulcsot generálsz, a megfelelő peerkonfigurációkat módosítod, ellenőrzött forgalmat indítasz, majd visszavonod a régi kulcsot. Egy interfész privát kulcsának cseréje minden partnerét érinti. Folyamatos átálláshoz előre megtervezett, elkülönült átmeneti identitás és útvonal kell.

NAT mögötti kliensnél a PersistentKeepalive fenntarthatja az UDP-mappinget. Gyakori kiinduló érték 25 másodperc, de nem minden hálózatban szükséges vagy elegendő. A laborban nincs rá szükség.

Monitorozd külön:

  • a kézfogások időpontját és a forgalomszámlálókat;
  • az endpoint, route és peer-prefix változását;
  • a tényleges alkalmazáskérést és annak késleltetését.

Az inaktív peer régi kézfogása önmagában nem kiesés. A kézfogás időbélyege falióra-adat; az alkalmazásmérés eltelt idejéhez monoton órát használj. A wg showconf és a gépi dump kimenet titkot is tartalmazhat: ne gyűjtsd őket általános diagnosztikai naplóba.

Technológia Orientáló különbség
WireGuard IP-alagút, kulcsalapú peer, szűk konfigurációs modell; felhasználókezelés és DNS külön
OpenVPN TLS-alapú vezérlőcsatorna, bővíthető hitelesítés és konfigurációátadás; UDP vagy TCP transport
IPsec/IKE Biztonsági társítások, IKE-hitelesítés és kulcsegyeztetés; route- vagy policyalapú integráció

A választást integráció, hitelesítési követelmény, interoperabilitás és működtethetőség alapján hozd meg, ne általános sebességrangsorból.

31.4.8 Feladatok

  1. Magyarázat: miért szerepel a szerver LAN-prefixe a kliens AllowedIPs listájában, miközben az átjáró klienspeerénél csak egy /32 cím van? Mi korlátozza a TCP-portot?
  2. Konfiguráció: szűkítsd a kliens LAN-route-ját és peerprefixét kizárólag 10.205.154.10/32 címre. A HTTP működjön tovább.
  3. Failure/recovery: töröld a szerver tunnelklienshez vezető visszaútját. Bizonyítsd, hogy a kézfogás nem jelent működő alkalmazáskapcsolatot, majd állítsd helyre az útvonalat.

31.4.9 Megoldások

1. A kliens az átjárón keresztül küld a LAN-ba, és onnan származó belső forráscímeket fogad el. Az átjáró a kliens kulcsához csak annak tunnelcímét rendeli. A TCP/8080 engedélyezését az nftables végzi. Postcondition: külön megnevezhető a route, a peer/source ellenőrzés és a portszintű authorization.

2. Ugyanazon labhoston, UID 0:

ip -n lab-vpn-c route add 10.205.154.10/32 \
    dev lab-wg src 10.204.154.1
ip netns exec lab-vpn-c wg set lab-wg \
    peer "$(cat /run/lab-d154/lab-g.pub)" \
    allowed-ips 10.204.154.2/32,10.205.154.10/32
ip -n lab-vpn-c route del 10.205.154.0/24

ip netns exec lab-vpn-c curl --max-time 5 http://10.205.154.10:8080/

Postcondition: lab-ok, miközben a kliens már nem irányítja tunnelbe a teljes /24 hálózatot. Visszaállításhoz add vissza az eredeti /24 route-ot és AllowedIPs listát, majd töröld az új /32 route-ot.

3. Hibainjektálás és helyreállítás:

ip -n lab-vpn-s route del 10.204.154.1/32
ip netns exec lab-vpn-c curl --max-time 3 \
    http://10.205.154.10:8080/ || true

ip -n lab-vpn-s route show
ip netns exec lab-vpn-c wg show lab-wg
ip netns exec lab-vpn-g nft list table inet lab-vpn

ip -n lab-vpn-s route add 10.204.154.1/32 via 10.205.154.1
ip netns exec lab-vpn-c curl --max-time 5 http://10.205.154.10:8080/

A kérések átjuthatnak az engedélyező szabályon, de a szervernek nincs válaszútja. Postcondition: kizárólag az útvonal visszaállítása után ismét lab-ok.

Cleanup: állítsd le a laborhoz nyitott capture-öket, majd ugyanazon labhoston, UID 0:

for n in lab-vpn-c lab-vpn-g lab-vpn-s; do
    ip netns pids "$n" | xargs -r kill
done
sleep 1

for n in lab-vpn-c lab-vpn-g lab-vpn-s; do
    test -z "$(ip netns pids "$n")"
done

rm -f /run/lab-d154/lab-c.key /run/lab-d154/lab-c.pub \

A végfeltétel a három névtér és a munkakönyvtár hiánya; más hosthálózati objektum nem változott.

31.4.10 Rövid összefoglaló

A WireGuard működését nem egyetlen „VPN up” állapot írja le. A kulcs azonosítja a peert, az AllowedIPs a belső címekhez köti, a Linux-route kiválasztja az interfészt, a tűzfal pedig szabályozza az elérhető szolgáltatásokat. A visszaút ugyanilyen fontos. A tunnel csökkenti a használható MTU-t; a PMTU-hibák kis kérések mellett rejtve maradhatnak. Split/full tunnel esetén az IPv6 és a DNS útját is tervezni kell. A monitoring alkalmazáskéréssel egészítse ki a kézfogási adatokat.

  • Peer: nyilvános kulccsal azonosított WireGuard-partner.
  • AllowedIPs: kimenő peerválasztás és bejövő forráscím-ellenőrzés.
  • PMTU: az adott útvonalon továbbítható legnagyobb, fragmentálást nem igénylő IP-csomagméret.
