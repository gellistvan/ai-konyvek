47.4 Credentials, Vault és privilege policy

47.4.1 Motiváció és üzemeltetési probléma

Ansible a vezérlőgépen (controller) futó automatizálási feladatokat juttat el a kezelt hosztokra. A playbookok szinte mindig tartalmaznak titkokat: adatbázis-jelszót, API tokent, become jelszót, privát SSH kulcs anyagát. A gyenge üzemeltetési minta az, ha ezek a titkok plaintext formában kerülnek a Git repositoryba, a CI logba vagy a kezelt hoszt /tmp könyvtárába. A cél az, hogy a secret forrását, hozzáférését és visszafejtési életciklusát explicit módon, minimális scope-pal kezeljük, és a CI-ből származó automatizálási identitást elkülönítsük a hosszú életű statikus kulcsoktól.

47.4.2 Definíciók és működés

Ansible Vault és key access. Az Ansible Vault fájlszintű, nyugalmi titkosítást ad a vezérlőgépen tárolt YAML fájloknak. A ansible-vault encrypt és encrypt_string parancs AES-titkosítással állít elő !vault típusú tartalmat. A visszafejtéshez jelszó vagy vault password file szükséges, amelyet a controller folyamat olvas be. A jelszófájlt soha ne commitold a repositoryba; a controller felhasználó home könyvtárában, külön 0600 jogosultságú könyvtárban tárold. A Vault visszafejtés a controller memóriájában történik a parse időben, és a plaintext alapértelmezés szerint nem kerül a kezelt hosztra, kivéve, ha egy template, copy vagy command feladatban ténylegesen felhasználod. Ekkor a plaintext a feladat SSH adatfolyamába kerül.

A Vault jelszó több forrásból is megadható: --ask-vault-pass, --vault-password-file, ANSIBLE_VAULT_PASSWORD_FILE környezeti változó, vagy vault-id címke. A labban a jelszófájlt nem tesszük a repositoryba, és a CI futtató a secret-et saját secret store-jából injektálja.

External secret store lookup. A Vault nem helyettesíti a centralizált secret managert. Külső titoktárból lookup plugin kérdezhető le futásidőben, például HashiCorp Vault-ból a community.hashi_vault.vault_kv2_get, vagy felhőben AWS Secrets Manager-ből. A lookup a controllerről hálózati hívást indít, ezért a controller identitásának (például rövid életű token, OIDC role, instance profile) minimális olvasási jogot kell kapnia, és a kapcsolatot TLS-nek kell védenie. A lookup eredményét a task change output és a debug kimenet elrejtése nélkül könnyű kiszivárogtatni, ezért mindig no_log: true mellett használd.

no_log és sensitive artifact limit. A no_log: true task kulcsszó letiltja a task eredményének, argumentumának és diff kimenetének megjelenítését, valamint a controller log_path naplóba írását. Nem kriptográfiai védelem: ha egy command vagy shell maga írja ki a titkot stdoutra, a no_log nem feltétlenül szűri meg a command által generált kimenetet, ezért a parancsot is úgy kell megírni, hogy ne printeljen titkos értéket. A debug: var=secret szintén veszélyes, ha nincs no_log. A --diff mód megváltozott fájltartalmat mutathat, ezért titkos tartalmú fájlműveletnél kerüld a diff módot, vagy használj no_log-ot.

SSH host key trust és become. Az Ansible közvetlenül SSH-n keresztül csatlakozik a kezelt hoszthoz. Az SSH host key ellenőrzését soha ne kapcsold ki ANSIBLE_HOST_KEY_CHECKING=False vagy StrictHostKeyChecking=no módon. A host kulcsot előre dokumentált, trusted forrásból rögzítsd a controller known_hosts fájljában, vagy add meg ansible_ssh_known_hosts inventory változóban. Az SSH host key trust a MITM elleni elsődleges védelem a controller és a hoszt közötti úton.

A become jogosultság-emelés jelszava is titkos. Az ansible_become_password ne legyen plaintext inventoryban; Vaultban tárolt változóként add meg, és a controlleren no_log mellett futtatott feladatként használd. A target hoszton a sudoers szabály a lehető legszűkebb legyen: ne NOPASSWD: ALL, hanem konkrét parancsokra korlátozott sudoers.d sorok. Az automatizálási felhasználó (például ansible-deploy) ne legyen root, és a become-ot csak azokra a taskokra kapcsold be, amelyek valóban igénylik.

OIDC/short-lived runner credentials. A CI futtató hosszú életű privát kulcsot ne tároljon. A modern CI rendszerek rövid életű OIDC tokent bocsátanak ki a job számára, amelyet a secret manager vagy a cloud identity provider validál, és rövid életű secret-et vagy SSH tanúsítványt ad vissza. Például a futtató id-token-jellegű tokenjét használva a controller ideiglenes hozzáférést kap az Ansible Vault jelszóhoz vagy a külső secret store-hoz. Ez a minta azt eredményezi, hogy a repositoryban csak a policy, a labban a tényleges secret pedig rövid élettartamú. A pontos OIDC claim- és workflow-konfiguráció a használt CI és secret manager verziójától függ, és a lab környezetben ellenőrizendő.

Inventory/output/log data policy. Az inventory állhat statikus YAML fájlokból vagy dinamikus inventory scriptekből. Titkot csak Vault-titkosított csoport- vagy hosztváltozókban tároljunk. A dinamikus inventory script ne printeljen secret-et, és a script kimenetét is kezeljük bizalmas adatként. Az Ansible controller log_path naplója rögzítheti a feladatkimenetet, ezért a naplófájlt 0600 engedéllyel, rotate-tel és olyan elérési úttal kell kezelni, amelyből a secret nem kerülhet Gitbe vagy megosztott kötetre. A no_log mellett a naplóelemzést is tesztelni kell: a titkok ne szerepeljenek a controller naplóban vagy a CI build logban.

47.4.3 Kidolgozott példa: Vault + service secret labhoston

A példa topológiája:

Szerep Gép Felhasználó Privilege
Controller lab-ansible-ctl ansible-deploy nincs root, Vault jelszófájl olvasó
Target lab-app1 ansible-deploy SSH login, become root korlátozott sudo

Előfeltétel: a controllerről az SSH host key ellenőrzése aktív, known_hosts bejegyzés a lab-app1 hoszthoz; Ansible-core verzió a labban rögzített. A példa parancsokat illusztratív jelleggel adjuk meg, tényleges futtatás nélkül.

Először hozzuk létre a Vault jelszófájlt a controlleren, és titkosítsuk a titkokat:

# target: lab-ansible-ctl, user: ansible-deploy, privilege: saját home
install -m 700 -d ~/.ansible-secrets
umask 077
cat > ~/.ansible-secrets/lab-app1-vault.pw <<'PW'
lab-DummyVaultPass-ChangeMe
PW
chmod 600 ~/.ansible-secrets/lab-app1-vault.pw

# Változók titkosítása
ansible-vault encrypt_string --vault-password-file ~/.ansible-secrets/lab-app1-vault.pw \
  --name 'vault_ansible_become_password' 'lab-DummyBecome-ChangeMe'

ansible-vault encrypt_string --vault-password-file ~/.ansible-secrets/lab-app1-vault.pw \
  --name 'vault_lab_app_db_password' 'lab-DummyDB-pw-ChangeMe'

A parancs kimenetét másoljuk például az inventory/host_vars/lab-app1/vault.yml fájlba:

vault_ansible_become_password: !vault |
  $ANSIBLE_VAULT;1.1;AES256
  33623337313830313665353730346137626333373530383638336464373235396633373365373362
  ...
vault_lab_app_db_password: !vault |
  $ANSIBLE_VAULT;1.1;AES256
  66346163313031623466323564376539303731353464623333386135336435323163323432313463
  ...

A Vault fájl ne kerüljön Gitbe. Az inventory például:

# inventory/hosts.yml
all:
  children:
    lab:
      hosts:
        lab-app1:
          ansible_host: 192.0.2.10
          ansible_user: ansible-deploy
          ansible_become: true
          ansible_become_password: "{{ vault_ansible_become_password }}"

A playbook, amely a service konfigurációját írja le, a titkot template helyett copy content mezőbe illeszti, és no_log-ot használ:

# deploy-lab-service.yml
- name: Deploy lab service configuration with secret handling
  hosts: lab-app1
  gather_facts: true
  become: true
  vars:
    ansible_become_password: "{{ vault_ansible_become_password }}"
  tasks:
    - name: Create labops group
      ansible.builtin.group:
        name: labops
        state: present

    - name: Create labops user
      ansible.builtin.user:
        name: labops
        group: labops
        create_home: false
        shell: /usr/sbin/nologin

    - name: Write service config with DB password
      ansible.builtin.copy:
        dest: /etc/lab-service/config.env
        owner: labops
        group: labops
        mode: "0640"
        content: |
          LAB_DB_PASSWORD={{ vault_lab_app_db_password }}
      no_log: true

    - name: Verify secret present without printing it
      ansible.builtin.command: grep -q '^LAB_DB_PASSWORD=' /etc/lab-service/config.env
      changed_when: false
      no_log: true

Futtatás a controlleren:

# target: lab-ansible-ctl, user: ansible-deploy, privilege: saját home
ansible-playbook -i inventory/hosts.yml deploy-lab-service.yml \
  --vault-password-file ~/.ansible-secrets/lab-app1-vault.pw --check
ansible-playbook -i inventory/hosts.yml deploy-lab-service.yml \
  --vault-password-file ~/.ansible-secrets/lab-app1-vault.pw

Várható eredmény: a lab-app1 hoszton létrejön a labops felhasználó, a /etc/lab-service/config.env fájl jogosultsága 0640, tulajdonosa labops, és a tartalmában a LAB_DB_PASSWORD= sor szerepel. A controller naplóban és a stdouton a dummy jelszó nem látszik.

Ellenőrzés a target oldalon:

# target: lab-app1, user: ansible-deploy, privilege: sudo a stat-hoz
sudo stat -c '%a %U %G %n' /etc/lab-service/config.env
sudo grep -c '^LAB_DB_PASSWORD=' /etc/lab-service/config.env

A várt kimenet:

640 labops labops /etc/lab-service/config.env
1

A controller oldalon ellenőrizzük, hogy a secret nem került naplóba:

# target: lab-ansible-ctl, user: ansible-deploy, privilege: saját home
grep -R 'lab-DummyDB-pw' ~/ansible-lab/log/ 2>/dev/null && echo FAIL || echo OK

Ha OK, a no_log és a Vault beállítás a várt módon működik. Rollback: a service konfigurációs fájl törlése vagy a korábbi verzió visszaállítása a lab-specifikus backupból, a felhasználó és csoport törlése nem cél, csak a fájl visszaállítása a korábbi tartalomra.

Külső secret store lookupra példa, amelyet a labban a plugin verziójának és a Vault endpoint elérhetőségének ellenőrzése után lehet használni:

- name: Read API token from external Vault
  set_fact:
    vault_lab_app_api_token: >-
      {{ lookup('community.hashi_vault.vault_kv2_get', 'lab-service/api',
                 url='https://vault.lab.example.test:8200',
                 auth_method='token',
                 token=lookup('env', 'VAULT_TOKEN')) }}
  no_log: true

Itt a VAULT_TOKEN a controller környezetéből származik, nem a repositoryból. A lookup hálózati hívása a controller identitásával történik, és a no_log megakadályozza az eredmény megjelenítését. A példa semmilyen éles Vault endpointot nem feltételez; a vault.lab.example.test dokumentációs jellegű, nem létező tesztcím.

47.4.4 Tipikus hibák és ellenpróbák

  • Tünet: a CI logban megjelenik a DB jelszó. Hipotézis: egy debug vagy command feladat kiírja a titkot, vagy a no_log hiányzik. Adatgyűjtés: a CI logban keress rá a jelszó dummy értékére. Változtatás: add hozzá a no_log: true-ot az érintett taskhoz, és távolítsd el a debug: var=... sorokat. Ellenőrzés: futtasd újra a jobot, és grep segítségével igazold, hogy a titok nem szerepel a logban.

  • Tünet: a playbook futás leáll: ERROR! Attempting to decrypt but no vault secrets found. Hipotézis: a controller nem kapta meg a Vault jelszófájl elérési útját, vagy a jelszófájl jogosultsága rossz. Adatgyűjtés: ellenőrizd a --vault-password-file argumentumot, a ANSIBLE_VAULT_PASSWORD_FILE környezeti változót és a fájl stat-ját. Változtatás: állítsd be a helyes elérési utat és 0600 módot. Ellenőrzés: futtasd újra ansible-playbook-kal.

  • Tünet: a controlleren a known_hosts hiánya miatt Host key verification failed hiba lép fel. Hipotézis: a hoszt kulcsa nincs megbízható forrásból rögzítve a controlleren. Adatgyűjtés: hasonlítsd össze a labhost kézi ujjlenyomatát a known_hosts tartalmával. Változtatás: add hozzá a hosztkulcsot a ~/.ssh/known_hosts-hoz vagy az inventory ansible_ssh_known_hosts változójához. Ellenőrzés: a playbook kapcsolódás sikeres, és nincs StrictHostKeyChecking=no.

  • Tünet: a külső secret store lookup 403 hibát ad. Hipotézis: a controller identitásához tartozó policy nem engedélyezi az adott path olvasását, vagy az access token lejárt. Adatgyűjtés: a controller logjában a lookup HTTP státusza, a Vault/secret manager auditori naplója. Változtatás: adj rövid életű OIDC-alapú hozzáférést a controllernek, és szűkítsd a policy-t a szükséges path-ra. Ellenőrzés: a lookup kétszeri futtatása ugyanazt a titkot adja, és a token lejárata után 401 lép fel.

  • Tünet: a ansible-playbook --diff kimenetben a titkos tartalmú fájl változása plaintextben jelenik meg. Hipotézis: a no_log nincs beállítva a copy vagy template taskon. Adatgyűjtés: futtasd a --diff módot a titkos taskra, és nézd meg a diff kimenetet. Változtatás: no_log: true a titkos tartalmat író taskon, és kerüld a --diff-et titkos taskoknál. Ellenőrzés: a diff kimenet nem tartalmazza a jelszót.

47.4.5 Feladatok

47.4.5.1 1. Feladat: Értelmező – Vault és external store összehasonlítása

Magyarázd el a különbséget az Ansible Vault nyugalmi titkosítása és a külső secret store-ból történő futásidejű lookup között. Tégy különbséget a titok forrása, hozzáférési ideje, visszafejtési életciklusa és a controller-identitás által igényelt jogosultság szempontjából. Írj egy rövid döntési szabályt, mikor melyiket érdemes használni.

47.4.5.2 2. Feladat: Adminisztrációs konfiguráció – Vaultolt become jelszó és service config

Készítsd el a lab-app2 hoszthoz tartozó Vaultolt vault_ansible_become_password és vault_lab_app_db_password változókat. A controller user ansible-deploy, a target SSH felhasználó ansible-deploy, a become root. A service konfiguráció /etc/lab-service2/config.env 0640 jogosultsággal, labops2 tulajdonossal jöjjön létre. A titkos tartalmú task no_log: true legyen. Add meg a teljes parancsokat, a Vault fájl elrendezést, a playbook YAML-t, a futtatási parancsot, ellenőrzést és rollbacket. A postcondition legyen: a fájl jogosultsága 0640, tartalmában a LAB_DB_PASSWORD= sor szerepel, és a controller stdout/napló nem tartalmazza a dummy jelszót.

47.4.5.3 3. Feladat: Diagnosztikai/failure recovery – Titokszivárgás és Vault hiba

Egy CI futtatás során két problémát észlelsz: az egyik task debug: var=vault_lab_app_db_password kiírja a jelszót a CI logba, a másik hibaüzenet: ERROR! Attempting to decrypt but no vault secrets found. A controller user ansible-deploy, a Vault jelszófájl elérési útja ~/.ansible-secrets/lab-app1-vault.pw. Diagnosztizáld a két hibát, adatgyűjtéssel, hipotézissel, egy-egy változtatással és ellenőrzéssel. Add meg a javított playbook részletet és a futtatási parancsot úgy, hogy a debug task eltűnjön, a Vault jelszófájl pedig a megfelelő hellyel és jogosultsággal legyen megadva. A postcondition: a CI logban a dummy jelszó nem szerepel, a playbook sikeresen lefut.

47.4.6 Megoldások

47.4.6.1 1. Megoldás

Az Ansible Vault a controller fájlrendszerén nyugvó, titkosított YAML fájlokkal dolgozik. A titok forrása a repositoryban vagy a controlleren lévő Vault fájl, a visszafejtés a controller memóriájában, parse időben történik, és a jelszó a controlleren marad. A hozzáféréshez a controller usernek Vault jelszófájlra van szüksége. Az external secret store lookup futásidőben, hálózati hívással kéri le a titkot a centralizált secret managerből. A titok forrása a secret manager, a visszafejtett érték a controller memóriájában jelenik meg, a hálózati kapcsolatot TLS védi, és a controller identitásának rövid életű tokenre vagy szerepkörre van szüksége. A döntési szabály: ha a titok ritkán változik, és nincs centralizált secret manager, a Vault elég; ha több fogyasztó, audit, dinamikus rotáció vagy felhőintegráció kell, external store-t használj.

47.4.6.3 3. Megoldás

Hibaanalízis:

  1. A debug: var=vault_lab_app_db_password task kiírja a plaintext jelszót. Hipotézis: hiányzik a no_log. Adatgyűjtés: a CI logban a dummy DB jelszó megtalálható. Változtatás: töröljük a debug taskot, vagy ha valóban szükséges egy diagnosztikai task, akkor no_log: true és ne jelenítsük meg a teljes titkot. Mivel a feladat szerint a debug eltűnik, töröljük.
  2. A Vault hibaüzenet oka, hogy a controller nem találja a Vault jelszófájlt. Hipotézis: a --vault-password-file elérési út hibás, vagy a fájl nem létezik/rossz jogosultságú. Adatgyűjtés: ls -l ~/.ansible-secrets/lab-app1-vault.pw és a futtatott parancs ellenőrzése. Változtatás: a jelszófájlt a helyes elérési útra helyezzük, 0600 jogosultsággal, és a parancsban a teljes ~ helyett a $HOME-t használjuk, vagy explicit utat adunk meg.

Javított parancs:

# target: lab-ansible-ctl, user: ansible-deploy, privilege: saját home
chmod 600 ~/.ansible-secrets/lab-app1-vault.pw
ansible-playbook -i inventory/hosts.yml deploy-lab-service.yml \
  --vault-password-file ~/.ansible-secrets/lab-app1-vault.pw

Javított playbook részlet: a debug task eltávolítva, a titkos copy megtartva no_log: true mellett. A postcondition: a CI log grep nem találja a dummy jelszót, a playbook sikeresen lefut, és a target oldalon a config fájl a megfelelő jogosultsággal létezik.

47.4.7 Rövid összefoglaló

A titokkezelés Ansible alatt rétegzett: az Ansible Vault fájl titkosítással védi a nyugalmi secret-et a controlleren, a vault password file pedig külön, szűk jogosultsággal él. A külső secret store lookup futásidőben, a controller identitásával kér le titkot, így elkerülhető a plaintext repository. A no_log megakadályozza a task eredményének kiszivárgását a stdoutra és a controller logba, de nem helyettesíti a parancskimenetek tisztítását. A CI hosszú életű kulcs helyett rövid életű OIDC tokenből nyerjen hozzáférést. Az SSH host key ellenőrzése és a szűk become-policy a hálózati és hosztoldali hozzáférési határt erősíti.

Továbbhasznált definíciók: Ansible Vault — az Ansible vezérlőgépen tárolt érzékeny YAML adatok AES-alapú, jelszóval vagy jelszófájllal visszafejthető titkosítása; lookup plugin — futásidejű adatbeszerzési mechanizmus, amely külső rendszerből, például secret managerből kér le adatot a controlleren; no_log — olyan Ansible task kulcsszó, amely letiltja a task argumentumainak, eredményének és diff kimenetének naplózását és megjelenítését.
