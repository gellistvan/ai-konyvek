53.1 Database kapcsolatok, resource és health

53.1.1 Motiváció és működtetési feladat

Egy szenior C++ fejlesztő számára az adatbázis gyakran „fekete doboz”: a szerveroldali kód kiad egy SQL lekérdezést, majd valamilyen későbbi időpontban választ kap. A Linux/DevOps rendszerszemléletben azonban a PostgreSQL-szolgáltatás nem egyetlen komponens, hanem több rétegen átívelő adatút, amelyben a kapcsolatfelvétel, a tranzakció, a lock, a memória és a storage mind saját latency- és erőforrásköltséggel rendelkezik. Amikor egy C++ alkalmazás p95 latency romlását tapasztalja, a hiba lehet a TCP-kapcsolat felépítésében, a connection pool kimerülésében, egy nem indexelt lekérdezésben, lock-várakozásban vagy éppen a WAL flush lassúságában. A d261 alfejezet célja, hogy ezeket a rétegeket egy referencia PostgreSQL-szolgáltatáson működtetési szempontból láttassa: ne csak a DB belső állapotát, hanem az OS/network/storage jeleket is együtt kezeljük.

Előfeltételek: izolált labVM (például Ubuntu Server 24.04 LTS), telepített PostgreSQL (a pontos verziót az apt release rögzíti; itt illusztrációként postgresql és postgresql-contrib csomagok), root vagy sudo jogosultság a rendszerbeállításokhoz, valamint a d047 alfejezetben tárgyalt fsync/dirty page és a d223 storage fogalmai. A példákban a labhost neve labhost01, a lab database lab_db, az alkalmazás role lab_app.

53.1.2 Definíciók és scope

  • Database latency alatt a kliens oldaláról mért teljes válaszidőt értjük, amely felbontható: connection establishment + query planning/execution + lock wait + storage I/O + hálózati oda-vissza idő. E rétegek mindegyike külön mérhető, és eltérő diagnosztikai paranccsal figyelhető.
  • Connection pool/limit egy olyan erőforrásgazdálkodási korlát, amely meghatározza, hány egyidejű háttérfolyamatot (backend) indít a PostgreSQL, és ebből mennyit használhat egy alkalmazás. A pool célja a process-indítási költség elkerülése és a DB memória védelme.
  • Working set a gyakran elért adat- és indexoldalak halmaza. Ha ez nem fér a shared_buffers és az OS page cache együttes méretébe, a lekérdezések fizikai blokkiolvasásra kényszerülnek, ami nagyságrendi latency növekedést okoz.
  • WAL (Write-Ahead Log) a tranzakciók redo rekordjainak folyamatos naplója; a commit tartóssága a WAL fsync-jén múlik, nem közvetlenül a data file kiírásán.

A scope itt egyetlen PostgreSQL instance működtetése: kapcsolatkezelés, erőforráskorlát, tranzakciós lockok, memória, WAL, hitelesítés/TLS és telemetria. Nem tárgyaljuk a replikációt, failovert vagy backupot (későbbi alfejezetekben), és nem tanítunk SQL-t vagy C++ szintaxist.

53.1.3 Rétegek és operatív következmények

53.1.3.1 Kapcsolat, pool, limit és timeout

A PostgreSQL process-modellt használ: a postmaster főfolyamat minden klienskapcsolathoz egy-egy backend process-t indít (fork). Ezért minden új kapcsolat drága: memória (kb. 5–10 MiB privát terület kapcsolatonként), process-létrehozás, authentikáció és TCP handshake. A max_connections korlát túllépése után a kliensek kapcsolódási hibát kapnak: FATAL: sorry, too many clients already. A superuser_reserved_connections néhány külön slotot tart fenn adminisztrációnak, ezért egy alkalmazáspool kimerülése nem zárja ki a diagnosztikát.

Működtetési gyakorlat: alkalmazás és DB közé PgBouncer (transaction mode connection pooler) ajánlott, mert így az alkalmazás sok kliensét kevés valódi PostgreSQL backend szolgálja ki, a process-per-connection modell hátrányai nélkül. Időtúllépéseket a statement_timeout (egy SQL utasítás maximális futásideje), a connect_timeout (kliens oldali kapcsolódási timeout) és az idle_in_transaction_session_timeout (nyitott tranzakcióban tétlenül álló session lelövése) szabályoz. Ha egy C++ szolgáltatás RAII-vezérelt tranzakciója elfelejti a COMMIT-et, az utóbbi timeout nélkül hosszú ideig lockot tarthat.

53.1.3.2 Tranzakció, lock, isolation operatív következményei

A PostgreSQL alapértelmezett izolációs szintje Read Committed. Minden UPDATE/DELETE sorlockot (RowExclusiveLock) szerez, és ha egy másik tranzakció már tartja ugyanazon sort, a várakozó process wait_event_type = 'Lock', wait_event = 'transactionid' állapotba kerül. A hosszú idle in transaction olyan lockot tarthat fenn, amely blokkolja az autovacuumot és más írókat is. A deadlock (kölcsönös várakozás) a PostgreSQL által automatikusan felismerésre kerül, és az egyik tranzakció ERROR: deadlock detected hibával visszagördül. A log_lock_waits = on bekapcsolása naplózza a lockvárakozásokat; a deadlock_timeout alapértelmezetten 1 s.

Működtetési nézet: a pg_stat_activity state oszlopa (active, idle, idle in transaction, aborted) és a wait_event írja le, hogy a process éppen CPU-n fut, I/O-ra vár, lockra vár, vagy nincs teendője. A hibadiagnosztika ezért itt kezdődik, nem az alkalmazás logjában.

53.1.3.3 Query, index és working set memória

A PostgreSQL memóriahasználata három fő részből áll: a shared_buffers (a DB saját page cache-e, általában a RAM 25%-a), az OS page cache (a fájlok bufferelt olvasása), és a work_mem (rendezés, hash join, aggregation sessionönként). A query tervező akkor választ sequential scan-t, ha az index nem szelektív, vagy ha a költségbecslés szerint kevesebb I/O-t igényel. A work_mem túl alacsony értéke külső sort eredményez (external merge, temp file a pgsql_tmp alatt), ami felesleges lemez I/O-t és latency-t hoz be. A working set mérete akkor optimális, ha a gyakran olvasott adatok a shared_buffers-ben találhatók; ezt a pg_stat_database.blks_hit és blks_read arányával mérjük. Ha a blks_hit aránya 99% alatt van, az OS page cache és a shared_buffers mérete felülvizsgálandó.

53.1.3.4 WAL, checkpoint és fsync adatút

A commit tranzakció a WAL-ba írja a redo rekordot, majd a synchronous_commit = on esetén a wal_sync_method (gyakran fdatasync) kiírja a WAL fájlt a storage-ra. A data file-ok csak később, a checkpoint során frissülnek. A checkpoint_timeout (alapértelmezetten 5 perc) és a max_wal_size szabályozza, milyen gyakran fut a checkpoint. Ha a storage fsync latency magas (például write cache nem védett power loss ellen), a commit latency minden tranzakciónál megjelenik. Az OS szintű iostat és a PostgreSQL pg_stat_bgwriter (checkpoint_write_time, sync_time) együttesen mutatják meg, hogy a tartóssági határ hol szűk keresztmetszet.

53.1.3.5 Auth, TLS, role és migration

A PostgreSQL hitelesítési lánca a pg_hba.conf szabályokból áll: local kapcsolatok peer módon (OS user alapján), host kapcsolatok scram-sha-256 jelszóval vagy cert, illetve gssapi/ldap nagyobb környezetben. A ssl = on és a tanúsítvány beállításával a TCP kapcsolat TLS-titkosított. Működtetési szempontból a migration (séma) jogosultsága ne keveredjen az alkalmazás runtime jogosultságával: a lab_app role csak SELECT/INSERT/UPDATE/DELETE jogokat kapjon a szükséges táblákon, míg a lab_migrator role tulajdonosként futtathat DDL-t. A GRANT ... ON ALL TABLES IN SCHEMA folytatható, de új tábláknál a DEFAULT PRIVILEGES biztosítja a folyamatos hozzáférést.

53.1.3.6 DB/app/host telemetry

A DB belső telemetriája a pg_stat_activity, pg_stat_database, pg_stat_bgwriter, pg_stat_statements (bővítmény) nézetekből olvasható. A pg_stat_statements per query-kulcsot tárolja a total_exec_time, mean_exec_time, rows, blk_read_time, blk_write_time, wal_bytes statisztikákat, így pontosan azonosítható a legdrágább SQL és annak I/O/fsync költsége. Az OS telemetria: vmstat (CPU, swap, context switch), iostat -x (átlagos várólista, await, utilization), sar -n TCP (hálózati retransmit), ss -tnp (kapcsolatok állapota). A réteghatár-diagnosztika sorrendje: először a DB aktív sessionök és lockok, majd a lassú query-k, végül az OS I/O és CPU telítettség.

53.1.4.3 3. Kapcsolódási teszt és telemetria

# labhost01, UID 1000, kliens oldali timeout beállítás
PGPASSWORD=dummy_pw psql \
  "host=127.0.0.1 port=5432 dbname=lab_db user=lab_app sslmode=require connect_timeout=3" \
  -c 'SELECT 1 AS ok;'

Várható kimenet: ok oszlop 1 értékkel. Ha a pg_hba.conf hibás, a hiba FATAL: no pg_hba.conf entry for host ...; ha a statement_timeout túl alacsony, a hosszú query ERROR: canceling statement due to statement timeout üzenetet ad.

Aktív sessionök és lockok ellenőrzése:

-- sudo -u postgres psql -d lab_db
SELECT state, count(*) 
FROM pg_stat_activity 
GROUP BY state;

SELECT a.pid, a.usename, a.state, a.wait_event_type, a.wait_event,
       now() - a.query_start AS duration, left(a.query, 80) AS query
FROM pg_stat_activity a
WHERE a.state <> 'idle'
ORDER BY a.query_start;

SELECT l.pid, l.locktype, l.mode, l.granted, a.query
FROM pg_locks l
JOIN pg_stat_activity a ON l.pid = a.pid
WHERE l.granted = false;

Illusztratív kimenet: egy aktív process wait_event_type='Lock', wait_event='transactionid', granted='f' egy másik tranzakcióval szemben. Ekkor a lock tulajdonos PID-jét a pg_locks és pg_stat_activity összekapcsolásával azonosítjuk, majd döntünk: SELECT pg_cancel_backend(pid) (kérés megszakítás) vagy a hibás alkalmazás tranzakció bezárása.

53.1.4.4 4. Egy hibás állapot szimulációja és javítása

Simuláljuk a connection limit kimerülést: az alábbi psql snippet ciklusban nyit 51 kapcsolatot, amelyek mindegyike 30 másodpercig alvó tranzakcióban marad. Mielőtt futtatjuk, győződjünk meg arról, hogy a statement_timeout aktív és az alkalmazás pool nélkül csatlakozik.

# labhost01, tesztelési szándékkal, ne élesben
for i in $(seq 1 55); do
  (psql "host=127.0.0.1 dbname=lab_db user=lab_app sslmode=require" \
    -c "SELECT pg_sleep(30);" &)
done
# A túlcsorduló kapcsolat hibája:
# FATAL: sorry, too many clients already

A diagnosztika SELECT count(*) FROM pg_stat_activity WHERE usename='lab_app'; mutatja, hogy elérte a max_connections - superuser_reserved_connections korlátot. Rollback: a tesztprocessek leölése után a slotok felszabadulnak. Működtetési megoldás: PgBouncer bevezetése transaction poolinggal, vagy alkalmazás oldali connection timeout és retry.

53.1.5 Tipikus hibák és ellenpróbák

  1. too many clients – tünet: új kapcsolat hibával tér vissza, a régi kliensek még működnek. Hipotézis: a max_connections kimerült; a pg_stat_activity szerint a sessionök idle vagy idle in transaction állapotban ülnek. Adatgyűjtés: SELECT count(*) FROM pg_stat_activity WHERE state='idle'; Egy változtatás: idle_in_transaction_session_timeout csökkentése vagy pool bevezetése. Verifikáció: a hiba eltűnik, a sessionök száma a korlát alatt marad.
  2. Hosszú query, de a CPU nem telített – tünet: p95 query latency magas, vmstat CPU idle magas. Hipotézis: lock wait vagy I/O várakozás. Adatgyűjtés: pg_stat_activity.wait_event_type mutatja, hogy Lock vagy IO. Ha Lock, a log_lock_waits naplóbejegyzések megadják a várakozó PID-et; ha IO, az iostat -x await értéke magas, és a pg_stat_statements blk_read_time szintén. Egy változtatás: index hozzáadása (lock esetben a tranzakció rövidítése, IO esetben cache növelés). Verifikáció: a wait_event eltűnik az aktív processekből.
  3. Checkpoint I/O burst diszket telít – tünet: időszakos storage latency kiugrás iostat await-ben. Hipotézis: checkpoint túl agresszív vagy a WAL mérete túl nagy. Adatgyűjtés: pg_stat_bgwriter checkpoints_timed, checkpoints_req, checkpoint_write_time, checkpoint_sync_time. Egy változtatás: checkpoint_completion_target = 0.9 (a checkpoint írás szétterítése). Verifikáció: a burst await csökken, a checkpoint_write_time egyenletesebb.

53.1.7 Megoldások

53.1.7.1 1. Latency breakdown

A maradék 100 ms lehetséges rétegei:

  • Lock wait: ha a pg_stat_activity wait_event_type='Lock', a process tranzakciózárra vár. Ellenőrzés: SELECT * FROM pg_stat_activity WHERE wait_event_type='Lock';
  • Storage I/O: ha a query sequential scan-t végez, és a tábla hideg (nincs cache-ben), a pg_stat_database blks_read magas, az iostat -x await megnő. Ellenőrzés: iostat -x 1 5 és pg_stat_statements blk_read_time.
  • WAL flush: ha a synchronous_commit = on és a storage fsync lassú, a commitok (itt nincs commit, de ha lenne) vagy a WAL-hoz kapcsolódó írások lassúak. Ellenőrzés: pg_stat_bgwriter sync_time és iostat write await.
  • Network RTT: az alkalmazás és a DB közötti TCP latency, ha nem localhost; ping, tc vagy ss -ti mutatja a TCP RTT-t.

A pqexec 20 ms önmagában nem cáfolja a rétegeket, mert a kliens oldali mérés a teljes hívást lefedi, míg a pg_stat_statements az utasítás DB oldalú idejét adja.

A PgBouncer transaction pooling révén kevés valódi backend szolgál ki sok klienst, és a várakozó kliensek a pooler szintjén sorban állnak, nem fogyasztanak DB process-slotot.

53.1.7.3 3. Lock contention helyreállítás

A pid=102 a blokkoló: idle in transaction állapotban tart nyitva egy tranzakciót, amely sorlockot tart. A pid=101 Lock wait-en van. A tulajdonos azonosítása:

SELECT l.locktype, l.mode, l.granted, l.relation::regclass,
       a.pid, a.usename, a.state, a.query
FROM pg_locks l
JOIN pg_stat_activity a ON l.pid = a.pid
WHERE l.granted AND l.locktype = 'transactionid';

A pid=102 query-je NULL (idle in transaction), de a pg_locks mutatja a megszerzett lockot. Beavatkozás: ha az alkalmazás hibás, a tranzakciót meg kell szakítani:

SELECT pg_cancel_backend(102);

Ha ez nem szünteti meg (pl. a tranzakció éppen nem szakítható meg), akkor a pg_terminate_backend(102) a kapcsolatot bontja le. Postcondition: a pg_stat_activity-ben a pid=102 eltűnik (vagy idle-re vált), a pid=101 végrehajtja a query-t, és nincs granted=false lock a pg_locks-ban.

53.1.8 Rövid összefoglaló

A PostgreSQL működtetéséhez a latency-t connection, query, lock és storage rétegre kell bontani, mert mindegyik más diagnosztikai nézetben és más beavatkozással kezelhető. A connection pool csökkenti a process-per-connection modell költségét, a timeoutok pedig megakadályozzák az elhúzódó tranzakciók lock-tartását. A memória (shared_buffers, work_mem, page cache) és a WAL/checkpoint/fsync adatút közvetlenül befolyásolja a query és commit latency-t. A telemetria a pg_stat_activity, pg_stat_database, pg_stat_bgwriter és pg_stat_statements nézetekből, valamint az OS vmstat, iostat és ss parancsokból áll össze.

Továbbhasznált definíciók:

  • Connection pool: kapcsolat-újrafelhasználó réteg, amely kevés valódi DB backendet oszt meg sok kliens között, csökkentve a process-indítási és memóriaköltséget.
  • Working set: a gyakran hozzáfér, a cache-ben (shared_buffers + page cache) el nem férő adatoldalak halmaza; ha nem fér cache-be, a latency az I/O miatt nő.
  • WAL/fsync: a commit tartóssága a write-ahead log fsync-jén múlik; a data file-ok később, checkpointtal frissülnek.

A max_connections és work_mem értékek lab-specifikus, hipotetikus baseline-ok, nem production tuning-szabályok. A tényleges működtetés előtt ellenőrizni kell az adott PostgreSQL-kiadás release notes-ját és a distro backport szintjét.
