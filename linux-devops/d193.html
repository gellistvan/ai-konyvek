39.3 kubectl, context, namespace és diagnosztika

39.3.1 Motiváció

A kubectl kliens nem egyetlen fix clustert céloz: minden parancs egy kliensoldali context és egy szerveroldali namespace metszetében fut. A szenior fejlesztő számára hasonló, mint amikor build/debug előtt nem ellenőrzi a branch és build directory párt: a hiba gyakran nem a rendszerben, hanem a rossz targetben van. Ezért a Kubernetes diagnosztika nulladik lépése nem a Pod belseje, hanem a kliens target állapotának láthatóvá tétele: melyik kubeconfig current context aktív, melyik namespace a parancs scope-ja, és milyen jogosultsággal kérdezünk. Ezt az elvet a Működtetési szerződés, runbook és változtatás is előírja: a megfigyelési parancs forrása, a módosító parancs targetje és a rollback út együtt rögzítendő.

39.3.2 Definíciók és működés

A kubectl minden kérését a kubeconfig (Kubernetes klienskonfiguráció) alapján közvetíti az API server felé. A kubeconfig három alapfogalmat tárol:

  • cluster: API server végpont és hitelesítő CA-adat.
  • user: klienshitelesítési adatok, például client certificate vagy token.
  • context: az a híd, amely (cluster, user, namespace) hármast kapcsol össze.

A current context az aktuálisan kiválasztott híd. Ha a parancsban nincs -n, akkor a contextben tárolt namespace lesz a névtér-default. A kubeconfig tehát stored state, nem maga a cluster.

Dummy lab kubeconfig kivonat:

apiVersion: v1
kind: Config
preferences: {}
clusters:
- name: lab-cluster
  cluster:
    server: https://lab-api.internal:6443
    certificate-authority-data: dummy-ca
contexts:
- name: lab-admin@lab-cluster
  context:
    cluster: lab-cluster
    user: lab-admin
    namespace: lab-app
current-context: lab-admin@lab-cluster
users:
- name: lab-admin
  user:
    token: dummy-token

A namespace Kubernetes API objektum, amely erőforrásnevek scope-ját adja. Fontos: a namespace önmagában nem biztonsági határ; RBAC-nak és NetworkPolicy-nak is védenie kell. A contextben tárolt namespace tehát csak kliens default, nem hozzáférés bizonyítéka.

Az aktuális target ellenőrzése:

kubectl config get-contexts
kubectl config current-context
kubectl config view --minify
kubectl config set-context --current --namespace=lab-app

A kubectl config view --minify csak az aktuális contextre szűrt kimenetet ad. A set-context a kliens stored state-jét módosítja, nem a clusterben lévő objectet. A namespace létrehozása és a default beállítása:

kubectl get namespaces
kubectl create namespace lab-app
kubectl config set-context --current --namespace=lab-app

A parancssor általában kubectl [verb] [resource] [name] -n namespace -o output formátumú. A resource rövidítve is használható, például po Pod, svc Service, deploy Deployment. A -A minden namespacet lekér, de élesben ez megnöveli a jogosultsági hibasíkot, ezért diagnosztikában először a saját namespace-t használjuk.

39.3.3 Megfigyelés: get, describe, explain, logs, events

A get a Kubernetes API-ból származó objecteket listázza. A -o flag a kimenetet vezérli: wide, json, yaml, jsonpath, name. A describe ezzel szemben diagnosztikai nézet: az object spec/status mellett az Events listát is aggregálja. A describe nem független API objektum, hanem emberi hibakeresésre optimalizált; a hivatalos observed state a JSON/YAML output.

A kubectl explain a szerver OpenAPI sémájából mutatja a mezők jelentését:

kubectl explain deployment.spec.template.spec.containers.resources

A logs a Pod konténer stdout/stderr folyamát olvassa. Hasznos flag: --previous az előző, leállt konténerhez, --tail, --timestamps, -f. A --previous azért fontos, mert CrashLoopBackOff esetén az aktuális konténer lehet, hogy még nem indult el, a hiba pedig az előző processz stderrjében van.

Az események lekérdezése namespace-szinten:

kubectl get events -n lab-app --sort-by=.lastTimestamp
kubectl get events -n lab-app --field-selector involvedObject.name=lab-cpp-app-6b9c7f9f5-abcde --sort-by=.lastTimestamp

39.3.4 Száraz futtatás és diff

A változtatások nulladik lépése a client dry-run: a kubectl a YAML-t a kliens séma szerint ellenőrzi, de nem küld kérést. A server dry-run az API serverre küldi a kérést, ahol validáció és admission-lépések futhatnak, de a módosítást nem persisztálja. A kubectl diff a helyi manifest és a clusterben lévő live object közötti különbséget mutatja.

kubectl apply --dry-run=client -f lab-deployment.yaml
kubectl apply --dry-run=server -f lab-deployment.yaml
kubectl diff -f lab-deployment.yaml

A dry-run nem garantálja az éles persist sikerét: webhook side effect, annotáció vagy jogosultság még meglepheti a futó clustert. A server dry-run-hoz is jogosultság kell. A diff nem módosít; ha nincs kimenete, akkor a manifest és a live object az összehasonlítás szerint nem tér el.

39.3.5 JSONPath és JSON output

A -o json a teljes objectet adja, a -o yaml ugyanazt YAML formában. A jsonpath a mezők kiválasztására való. A Kubernetes object mezői három nagy hatókörre oszlanak: metadata, spec és status. A spec a desired state, a status a reconciliation által észlelt observed state. A JSONPath e mezőkben lépked.

Példa egy Pod fázisának és utolsó exit code-jának kinyerésére:

kubectl get pods -n lab-app -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.phase}{"\t"}{.status.containerStatuses[0].lastTerminationState.terminated.exitCode}{"\n"}{end}'

Várt, illusztratív kimenet:

lab-cpp-app-6b9c7f9f5-abcde CrashLoopBackOff    1

A JSONPath hibáinak ellenőrzésére a -o json | jq alkalmas. A custom-columns olvashatóbb táblázatot ad:

kubectl get pods -n lab-app -o custom-columns=NAME:.metadata.name,PHASE:.status.phase,RESTARTS:.status.containerStatuses[0].restartCount

39.3.6 Exec és port-forward privilegizált használata

Az exec a kubelet API-n keresztül indít processzt a Podban; a port-forward a kliens és a Pod között hoz létre tunelt. Mindkettő privileged use scope: diagnosztikához vagy interaktív hibakereséshez való, nem állandó menedzsment interfész. Az RBAC-ban a pods/exec és pods/portforward permission külön adható, ezért hiába van get pods jog, az exec még lehet tiltott.

kubectl exec -it deploy/lab-cpp-app -n lab-app -- /bin/sh
kubectl port-forward pod/lab-cpp-app-6b9c7f9f5-abcde -n lab-app 18080:8080

A port-forward alapértelmezésben a kliens 127.0.0.1 címére bind; az --address csak laborban és célzottan használható. A port-forward nem a Service-t, hanem a Pod IP-címét és portját képezi le; a source és destination explicit rögzítendő, mielőtt a forgalom elindul.

39.3.7 Auth can-i és API error classification

A diagnosztika nulladik kérdése: van-e egyáltalán jogunk a válaszhoz? A kubectl auth can-i ezt az API-val ellenőrizteti:

kubectl auth can-i get pods -n lab-app
kubectl auth can-i create deployments -n lab-app --as=lab-user
kubectl auth can-i --list -n lab-app

A --as egy másik user szemszögéből kérdez, de csak akkor működik, ha a kliens fiókjának van impersonate joga. Az API hibaüzenetek osztályozása a következő táblázat szerint segíti a hibaszűkítést:

HTTP Kategória Jellemző ok Első ellenőrzés
401 Unauthorized hiányzó vagy lejárt credential kubectl config current-context
403 Forbidden RBAC hiány kubectl auth can-i
404 NotFound rossz namespace/resource/name kubectl get ns
409 Conflict resourceVersion eltérés kubectl get -o yaml
422 Unprocessable validation kubectl explain, server dry-run
429 TooManyRequests client-side rate limit kubectl get events
500/503 Server/API hiba control plane / backing service kubectl get --raw /healthz

A 409 Conflict optimista konkurencia: a kliens régi resourceVersion alapján küld módosítást. A --v=8 flag az API request/response részleteket is megmutatja, ha szükséges.

39.3.8 Kidolgozott példa: CrashLoopBackOff diagnosztika targetellenőrzéssel

Labtarget: lab-cluster, context lab-admin@lab-cluster, namespace lab-app, UID <lab-uid>. A Pod neve lab-cpp-app-6b9c7f9f5-abcde, státusza CrashLoopBackOff. A cél a hiba root cause-ának szűkítése, nem az alkalmazáskód újraírása.

  1. Target ellenőrzése:
kubectl config current-context
kubectl config view --minify | grep namespace
kubectl auth can-i get pods -n lab-app

Várt kimenet: lab-admin@lab-cluster, namespace: lab-app, yes.

  1. Pod listázása:
kubectl get pods -n lab-app

Illusztratív kimenet:

NAME                           READY   STATUS             RESTARTS     AGE
lab-cpp-app-6b9c7f9f5-abcde    0/1     CrashLoopBackOff    12         7m
  1. Describe:
kubectl describe pod lab-cpp-app-6b9c7f9f5-abcde -n lab-app

Figyelem két mezőre: Last State: Terminated Reason: Error Exit Code: 1, valamint az Events szakaszra. Illusztratív kivonat:

State:          Waiting
  Reason:       CrashLoopBackOff
Last State:     Terminated
  Reason:       Error
  Exit Code:    1
Events:
  Type     Reason     Age                From               Message
  ----     ------     ----               ----               -------
  Warning  BackOff    61s (x25 over 7m) kubelet            Back-off restarting failed container
  1. Események és log a leállt konténerből:
kubectl get events -n lab-app --field-selector involvedObject.name=lab-cpp-app-6b9c7f9f5-abcde --sort-by=.lastTimestamp
kubectl logs pod/lab-cpp-app-6b9c7f9f5-abcde -n lab-app --previous --tail=20 --timestamps
kubectl explain pod.spec.containers.volumeMounts

A C++ processz stderrje:

2025-01-15T07:11:02Z ERR terminating: cannot open /var/lib/lab-app/state

A hiba szerint a processz a /var/lib/lab-app/state fájlt próbálja megnyitni. A describe Volume mount szekciója viszont azt mutatja, hogy a state emptyDir volume mountPath-ja /lab-app/state. A manifest server dry-runja:

kubectl apply --dry-run=server -f lab-deployment.yaml

Nem hibázik, mert a manifest szintaktikailag érvényes; a hiba a deployment spec és a runtime elvárás közötti eltérés. JSONPath kinyeri a restart countot:

kubectl get pods -n lab-app -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.containerStatuses[0].restartCount}{"\n"}{end}'

Várt kimenet:

lab-cpp-app-6b9c7f9f5-abcde   12

A fix egyetlen változtatás: a manifestben a mountPath értékét /var/lib/lab-app/state-re javítjuk. A javítás előtt kubectl diff -f lab-deployment.yaml mutatja a megváltozott mezőt, majd a rögzített rollback path mellett kubectl apply -f lab-deployment.yaml futtatható. A példa azt bizonyítja, hogy a hiba a desired/observed state eltéréséből adódott; a context target ellenőrzése nem a hibás, hanem a diagnosztika bemenete volt.

39.3.9 Hibák és ellenpróbák

  • Hiba: kubectl get pods üres, pedig a Pod fut. Tünetgyanú: a context default default namespace, a Pod viszont lab-app-ben van. Ellenőrzés: kubectl config view --minify | grep namespace, majd kubectl get pods -n lab-app. Változtatás: kubectl config set-context --current --namespace=lab-app.
  • Hiba: kubectl logs nem ad kimenetet. Tünetgyanú: a futó konténer még nem indult, vagy a crash az előző konténerben van. Ellenőrzés: kubectl get events -n lab-app --sort-by=.lastTimestamp, majd kubectl logs --previous.
  • Hiba: kubectl exec pods/exec is forbidden. Tünetgyanú: RBAC hiány, nem a Pod hibája. Ellenőrzés: kubectl auth can-i create pods/exec -n lab-app. Megoldás: ne kérjünk jogot; először a kliens oldali diagnosztikát használjuk.
  • Hiba: kubectl apply --dry-run=server 409 Conflict. Tünetgyanú: a kliens régi resourceVersion-t küld. Ellenőrzés: kubectl get -o yaml és a .metadata.resourceVersion összevetése.
  • Hiba: a JSONPath kimenet üres. Tünetgyanú: a range kifejezés nem találja a mezőt. Ellenőrzés: kubectl get pods -n lab-app -o json és jq.
  • Ellenpróba: a kubectl config set-context nem cluster módosítás. A kliens oldalon stored state; a cluster nem változott. Ellenőrizzük a ~/.kube/config backupját, mielőtt a contextet változtatjuk.

39.3.10 Feladatok

  1. Magyarázó: Kubeconfig context. Adja meg, milyen három komponenst tartalmaz a context, mit jelent a --minify, és miért nem elegendő a contextben lévő namespace a hozzáférés bizonyítására.

  2. Adminisztrációs/konfigurációs: Hozzon létre lab-app02 namespace-t, állítsa be a lab-user@lab-cluster contextben a namespace-t lab-app02-re, majd hozza létre a lab-tools Podot a lab-app02 namespace-ben. Ellenőrizze a current-context, a namespace, a Pod READY állapotát és a can-i get pods jogot. Minden módosító parancshoz target, postcondition és rollback tartozzon.

  3. Diagnosztikai/failure/recovery: A lab-app namespace-ben a lab-cpp-app Pod CrashLoopBackOff. A logs permission denied hibát mutat, a describe a securityContext mezőt jelöli. Használjon get, describe, events, logs --previous, explain, JSONPath és auth can-i parancsokat. Határozza meg a root cause-ot, hajtson végre egy változtatást, és ellenőrizze a recoveryt.

39.3.11 Megoldások

  1. A context (cluster, user, namespace) hármast kapcsol össze. A --minify az aktuális contextre szűkíti a kubeconfigot. A namespace nem RBAC, ezért a hozzáférést külön kubectl auth can-i ellenőrzés bizonyítja. Postcondition: a tanuló meg tudja fogalmazni a targetet, és meg tudja különböztetni a kliens defaultot a jogosultságtól.

  2. Példaparancsok:

kubectl create namespace lab-app02
kubectl config set-context --current --namespace=lab-app02
kubectl apply -f - <<EOF
apiVersion: v1
kind: Pod
metadata:
  name: lab-tools
  namespace: lab-app02
spec:
  containers:
  - name: tools
    image: alpine:3.20
    command: ["sleep", "600"]
EOF
kubectl get pod lab-tools -n lab-app02
kubectl auth can-i get pods -n lab-app02

Rollback: kubectl delete pod lab-tools -n lab-app02, majd kubectl delete namespace lab-app02 csak a saját lab objektumra. Postcondition: a context namespace lab-app02, a Pod Running, a can-i kimenet yes.

  1. A root cause: a Pod securityContext beállítás eltér a képfolyamat UID-jétől, ezért a fájl nem olvasható. Diagnosztikai parancsok:
kubectl config current-context
kubectl get pod lab-cpp-app -n lab-app -o yaml | grep -A5 securityContext
kubectl describe pod lab-cpp-app -n lab-app
kubectl logs pod/lab-cpp-app -n lab-app --previous
kubectl explain pod.spec.containers.securityContext
kubectl auth can-i patch pods -n lab-app

A manifestben a runAsUser mezőt a kívánt UID-re igazítjuk, majd kubectl diff -f lab-deployment.yaml, kubectl apply -f lab-deployment.yaml. A recoveryt JSONPath-tal ellenőrizzük:

kubectl get pods -n lab-app -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.phase}{"\n"}{end}'

Várt kimenet: lab-cpp-app-... Running, a CrashLoop megszűnt. Postcondition: a Pod Running, a restartCount nem nő, a manifest a desired state-t tükrözi.

39.3.12 Rövid összefoglaló

A kubectl diagnosztika nulladik lépése a kubeconfig current context és a namespace explicit ellenőrzése. A context (cluster, user, namespace) hármast kapcsol, de a namespace önmagában nem biztonsági határ. A get/describe/explain/logs/events a feltáró parancsok: a JSON/YAML a megfigyelt állapot, a describe eseményekkel a hibaszűkítés. A dry-run/diff a módosítás próbája, a can-i a jog próbája, az API statuszok a 401/403/404/409/422/429/503 osztályok szerint szűkítik a hiba helyét. Az exec/port-forward privileged scope, csak célzott diagnosztikai eszköz.

Ténylegesen továbbhasznált definíciók:

  • current context: a kubeconfig által kiválasztott cluster/user/namespace híd minden kubectl kéréshez.
  • namespace: API erőforrás-scope, nem önálló biztonsági határ.
  • server dry-run: az API server validációs és admission-lépéseket futtathat, de a módosítást nem persisztálja.
