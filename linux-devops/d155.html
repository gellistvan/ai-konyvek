31.5 Firewall/NAT/VPN lab és recovery

31.5.1 Mit bizonyít ez a labor?

Egy sikeres HTTP-kérés önmagában nem bizonyít jó tűzfal-konfigurációt. Lehet, hogy a csomag másik útvonalon haladt, egy korábbi kapcsolat állapota engedte át, vagy a tiltó szabály sohasem találkozott vele.

A policy bizonyítása itt három összekapcsolt megfigyelés:

  1. a megengedett kérés alkalmazásszinten sikerül;
  2. a tiltott kérés elbukik, és a megfelelő eldobási számláló növekszik;
  3. a csomagrögzítés (packet capture) a tervezett interfészeken és címfordításokkal mutatja az adatutat.

A visszaállítási alapállapot (saved baseline) ismert konfiguráció, amelyhez hiba esetén visszatérünk. Egy elmentett nftables-szabálykészlet azonban nem menti el az útvonalakat, a WireGuard-kulcsokat vagy a kapcsolatkövetési állapotot.

A változtatási eljárást a Működtetési szerződés, runbook és változtatás, a tunnel előfeltételeit a WireGuard, tunneling és távoli hálózat alapján használjuk.

Minden alábbi eredmény várt vagy illusztratív; tényleges laborfuttatás nem történt.

31.5.2 Laborcontract és topológia

Két dedikált Ubuntu Server 24.04 LTS VM szükséges. A példák csomag-előfeltételei: iproute2, nftables, conntrack, tcpdump, curl, python3, wireguard-tools, util-linux. A lab felhasználó UID/GID-je ebben a profilban 1000:1000.

Objektum Interfész és cím Szerep
lab-admin 192.168.155.5/24 Meglévő adminisztrációs gép
lab-fw host enp1s0, 192.168.155.10/24 SSH és konzol; ezt nem módosítjuk
lab-peer host enp1s0, 192.168.155.11/24 SSH és konzol; ezt nem módosítjuk
lab-r namespace lab-wan, 10.155.0.1/30 Router, nftables, WireGuard
lab-peer host enp7s0, 10.155.0.2/30 Külső tesztvégpont és VPN-peer
lab-c namespace lab-eth, 10.155.10.2/24 Belső kliens
lab-r namespace lab-lan, 10.155.10.1/24 Kliensoldali átjáró
lab-s namespace lab-eth, 10.155.20.2/24 Belső HTTP-szerver
lab-r namespace lab-dmz, 10.155.20.1/24 Szerveroldali átjáró
WireGuard lab-r: 10.155.30.1/30; peer: 10.155.30.2/30 Tunnel

A két enp7s0 kizárólag egymással összekötött, uplink nélküli virtuális kapcsolóhoz tartozik. Kezdetben cím nélküli, leállított, hálózatkezelő által nem kezelt interfészek. A virtuális NIC-eket a hypervisor inventoryjában MAC-cím alapján is azonosítani kell.

Indítás előtt ellenőrizd:

  • a felsorolt privát tartományok nem ütköznek meglévő route-tal;
  • a lab-* namespace-ek, interfészek, unitok és munkakönyvtárak még nem léteznek;
  • mindkét VM konzolja működik;
  • a peer host meglévő tűzfala engedi a labor interfészén a 10.155.0.1 felől érkező TCP/8080 és UDP/51820 forgalmat; a hostvédelmet nem kapcsoljuk ki;
  • a lab-admin gépről a két SSH-hozzáférés már működik, ellenőrzött hostkulcsokkal.

A konfigurációforrás a laborban létrehozott nft-fájl és a topológiatábla. A megfigyelt állapotot az ip, nft, wg, conntrack és az alkalmazáspróbák adják. A namespace-ek nem külön hosthibatartományok: a lab-fw kiesése mindhármat megszünteti.

Mindkét VM-en, lab felhasználóként rögzítsd a profilt:

31.5.3 Az izolált adatút felépítése

A következő blokk célpontja lab-fw, UID 0, Bash. Az enp7s0 namespace-be helyezése csak az előbb azonosított, dedikált NIC-re engedélyezett.

umask 077
install -d -m 0755 /run/lab-fw /run/lab-fw/lab-www
printf 'lab-ok\n' > /run/lab-fw/lab-www/lab-ok
chmod 0644 /run/lab-fw/lab-www/lab-ok

for ns in lab-r lab-c lab-s; do
    ip netns add "$ns"
    ip -n "$ns" link set lo up
done

ip link set enp7s0 netns lab-r
ip -n lab-r link set enp7s0 name lab-wan
ip -n lab-r address add 10.155.0.1/30 dev lab-wan
ip -n lab-r link set lab-wan up

for item in 'lab-c lab-lan 10.155.10' 'lab-s lab-dmz 10.155.20'; do
    read -r ns port prefix <<< "$item"
    ip link add "$port" type veth peer name lab-eth
    ip link set "$port" netns lab-r
    ip link set lab-eth netns "$ns"
    ip -n lab-r address add "$prefix.1/24" dev "$port"
    ip -n lab-r link set "$port" up
    ip -n "$ns" address add "$prefix.2/24" dev lab-eth
    ip -n "$ns" link set lab-eth up
    ip -n "$ns" route add default via "$prefix.1"
done

ip netns exec lab-r sysctl -w net.ipv4.ip_forward=1
ip netns exec lab-s setpriv --reuid=1000 --regid=1000 \
  --clear-groups python3 -m http.server 8000 \
  --bind 10.155.20.2 --directory /run/lab-fw/lab-www \
  > /run/lab-fw/lab-http.log 2>&1 &

n() { ip netns exec lab-r "$@"; }

A host ip_forward értékét nem módosítjuk. A példában használt n függvény minden parancsot a lab-r hálózati névterében hajt végre.

lab-peer, UID 0:

install -d -m 0755 /run/lab-peer /run/lab-peer/lab-www
printf 'lab-peer-ok\n' > /run/lab-peer/lab-www/lab-ok

ip address add 10.155.0.2/30 dev enp7s0

systemd-run --unit=lab-peer-http \

31.5.4 WireGuard-peer és privát route

Kizárólag eldobható laborkulcsokat generálunk. Privát kulcs nem kerül terminálkimenetbe vagy jegyzőkönyvbe.

lab-fw, UID 0:

wg genkey > /run/lab-fw/lab-wg.key
wg pubkey < /run/lab-fw/lab-wg.key > /run/lab-fw/lab-wg.pub
cat /run/lab-fw/lab-wg.pub

lab-peer, UID 0:

wg genkey > /run/lab-peer/lab-wg.key
wg pubkey < /run/lab-peer/lab-wg.key > /run/lab-peer/lab-wg.pub
cat /run/lab-peer/lab-wg.pub

Csak a két nyilvános kulcsot másold át az alábbi interaktív bemenetekhez.

lab-fw, UID 0, az előző Bash-munkamenetben:

read -r -p 'A lab-peer nyilvános kulcsa: ' LAB_PEER_PUBLIC_KEY
ip -n lab-r link add lab-wg type wireguard
n wg set lab-wg listen-port 51820 \
  private-key /run/lab-fw/lab-wg.key \
  peer "$LAB_PEER_PUBLIC_KEY" allowed-ips 10.155.30.2/32
ip -n lab-r address add 10.155.30.1/30 dev lab-wg
ip -n lab-r link set lab-wg mtu 1420 up

lab-peer, UID 0:

read -r -p 'A lab-fw nyilvános kulcsa: ' LAB_FW_PUBLIC_KEY
ip link add lab-wg type wireguard
wg set lab-wg listen-port 51820 \
  private-key /run/lab-peer/lab-wg.key \
  peer "$LAB_FW_PUBLIC_KEY" \
  endpoint 10.155.0.1:51820 \
  allowed-ips 10.155.30.1/32,10.155.20.2/32
ip address add 10.155.30.2/30 dev lab-wg
ip link set lab-wg mtu 1420 up
ip route add 10.155.20.2/32 dev lab-wg
ip route get 10.155.20.2

Várt ellenőrzés: a privát szerverhez vezető route dev lab-wg, forrása 10.155.30.2. Az AllowedIPs nem helyettesíti ezt a Linux-route-ot. Az 1420 bájtos MTU a labor 1500 bájtos külső linkjéhez választott érték, nem minden underlayre érvényes ajánlás.

31.5.5 Validált szabálykészlet és elmentett baseline

A kívánt policy:

  • belső kliens → belső HTTP-szerver: engedélyezett;
  • belső kliens → külső tesztszerver: engedélyezett, SNAT-tal;
  • külső peer → router TCP/8080: DNAT a belső szerver TCP/8000 portjára;
  • WireGuard-peer → belső szerver TCP/8000: engedélyezett, NAT nélkül;
  • minden más továbbított forgalom: tiltott.

lab-fw, UID 0:

{ printf 'flush ruleset\n'; n nft list ruleset; } \
  > /run/lab-fw/lab-initial.nft

cat > /run/lab-fw/lab-candidate.nft <<'EOF'
flush ruleset
table inet "lab-filter" {
    chain "lab-input" {
        type filter hook input priority filter; policy drop;
        iifname "lo" accept
        ct state invalid counter drop
        ct state established,related counter accept
        iifname "lab-wan" ip saddr 10.155.0.2 \
            udp dport 51820 counter accept
        counter drop
    }
    chain "lab-forward" {
        type filter hook forward priority filter; policy drop;
        ct state invalid counter drop
        ct state established,related counter accept
        iifname "lab-lan" oifname "lab-wan" \
            ip daddr 10.155.0.2 tcp dport 8080 counter accept
        iifname "lab-lan" oifname "lab-dmz" \
            ip daddr 10.155.20.2 tcp dport 8000 counter accept
        iifname "lab-wan" oifname "lab-dmz" ct status dnat \
            ip daddr 10.155.20.2 tcp dport 8000 counter accept
        iifname "lab-wg" oifname "lab-dmz" \
            ip saddr 10.155.30.2 ip daddr 10.155.20.2 \
            tcp dport 8000 counter accept
        counter drop
    }
}
table ip "lab-nat" {
    chain "lab-prerouting" {
        type nat hook prerouting priority dstnat; policy accept;
        iifname "lab-wan" ip daddr 10.155.0.1 tcp dport 8080 \
            counter dnat to 10.155.20.2:8000
    }
    chain "lab-postrouting" {
        type nat hook postrouting priority srcnat; policy accept;
        oifname "lab-wan" ip saddr 10.155.10.0/24 \
            counter snat to 10.155.0.1
    }
}
EOF

n nft -c -f /run/lab-fw/lab-candidate.nft
n nft -f /run/lab-fw/lab-candidate.nft
n nft -a list ruleset

A flush ruleset csak a kizárólag laborcélú lab-r namespace-ben megengedett. Hoston vagy megosztott routeren ezt a receptet nem szabad alkalmazni.

A -c ellenőrzi a parancsok elfogadhatóságát, de nem bizonyítja a szolgáltatás elérhetőségét. Az egyetlen nft -f tranzakció elkerüli a külön parancsok közötti részlegesen telepített szabályállapotot; az útvonalakra és más eszközökre nem ad közös tranzakciót.

Ez IPv4-es adatútlabor, nem teljes dual-stack hostbaseline. Kimenő szűrést sem valósít meg.

31.5.6 Pozitív és negatív tesztek, számlálók és capture

lab-fw, UID 0:

ip netns exec lab-c curl --noproxy '*' -fsS --max-time 3 \
  http://10.155.20.2:8000/lab-ok
ip netns exec lab-c curl --noproxy '*' -fsS --max-time 3 \
  http://10.155.0.2:8080/lab-ok

n nft -a list ruleset
ip netns exec lab-c curl --noproxy '*' -fsS --max-time 3 \
  http://10.155.20.2:8001/lab-ok
n nft -a list ruleset

Az első két válasz rendre lab-ok, illetve lab-peer-ok. A harmadik kérésnél időtúllépés várható, és a lab-forward utolsó eldobási számlálójának növekednie kell. A növekmény nem feltétlenül egy: a TCP újraküldhet.

Az önmagában kapott „connection refused” nem tűzfaltiltási bizonyíték: származhat a célgép TCP-verméből is.

lab-peer, UID 1000:

curl --noproxy '*' -fsS --max-time 3 http://10.155.0.1:8080/lab-ok
curl --noproxy '*' -fsS --max-time 3 http://10.155.20.2:8000/lab-ok
curl --noproxy '*' -fsS --max-time 3 http://10.155.20.2:8001/lab-ok

Az első kérés DNAT-on, a második WireGuardon halad; mindkettőnél lab-ok várható. A harmadiknál tiltás és forward-drop számlálónövekedés szükséges.

Külön konzolokon, lab-fw, UID 0, indíts capture-t, majd ismételd meg a kéréseket:

ip netns exec lab-r tcpdump -nli lab-wan \
  'tcp port 8080 or udp port 51820'
ip netns exec lab-r tcpdump -nli lab-dmz \
  'tcp port 8000 or tcp port 8001'

A belső SNAT előtti képet lab-lan, a dekódolt VPN-forgalmat lab-wg interfészen ugyanilyen célzott capture mutatja.

Próba Várt csomagkép belépéskor Várt csomagkép kilépéskor
SNAT lab-lan: 10.155.10.2:p → 10.155.0.2:8080 lab-wan: 10.155.0.1:q → 10.155.0.2:8080
DNAT lab-wan: 10.155.0.2:p → 10.155.0.1:8080 lab-dmz: 10.155.0.2:p → 10.155.20.2:8000
VPN lab-wan: titkosított UDP/51820 lab-dmz: 10.155.30.2:p → 10.155.20.2:8000

A p és q változó kliensport; SNAT során a port megőrizhető, de ez nem általános garancia. A visszirányú DNAT-válasznak a WAN-on 10.155.0.1:8080 forrással kell megjelennie.

Kapcsolatkövetés, lab-fw, UID 0:

n conntrack -L -p tcp -o extended
n wg show lab-wg

A kapcsolatkövetés (connection tracking) eredeti és válaszirányú tuple-jeit a capture-rel együtt értelmezd. A NAT-szabály számlálója tipikusan a kapcsolat első, leképezést létrehozó csomagjainál növekszik; a későbbi csomagokat a tárolt leképezés kezeli. Ezért a NAT- és filterszámlálók nem várhatók azonosnak.

Friss tesztkapcsolatokat használj. Egy megmaradt established állapot elfedheti az új kapcsolatokra vonatkozó hibás policyt. A teljes conntrack-tábla törlése nem megfelelő általános javítás.

31.5.7 Hibainjektálás, rollback és management-ellenőrzés

Sikeres tesztek után mentsük el a működő baseline-t, majd állítsunk be automatikus visszaállítást.

lab-fw, UID 0:

{ printf 'flush ruleset\n'; n nft list ruleset; } \
  > /run/lab-fw/lab-baseline.nft

systemd-run --unit=lab-fw-rollback --on-active=90s \
  "$(command -v ip)" netns exec lab-r \
  "$(command -v nft)" -f /run/lab-fw/lab-baseline.nft

n nft 'insert rule inet "lab-filter" "lab-forward" \
  iifname "lab-wg" ip daddr 10.155.20.2 tcp dport 8000 \
  counter drop comment "lab-failure"'

A VPN-es HTTP-kérésnek most el kell buknia. A tiltást a lánc elejére tettük, ezért az established szabály sem előzi meg.

A timer lejárta után:

  • a lab-failure szabály eltűnik;
  • a VPN-es HTTP-kérés ismét sikerül;
  • a tiltott TCP/8001 továbbra is tiltott.

Kézi rollback ugyanebben a célpontban:

n nft -c -f /run/lab-fw/lab-baseline.nft
n nft -f /run/lab-fw/lab-baseline.nft

Ezután lab-admin, UID 1000 gépről új SSH-kapcsolatokkal ellenőrizz:

ssh -o BatchMode=yes -o ConnectTimeout=5 lab@192.168.155.10 \
  'hostname; id -u'
ssh -o BatchMode=yes -o ConnectTimeout=5 lab@192.168.155.11 \
  'hostname; id -u'

A megmaradt SSH-munkamenet nem helyettesíti ezt a próbát.

Bizonyítékkorlát: a management interfészek a host namespace-ben maradtak. A labor igazolja a management elérhetőségét rollback után, de nem bizonyítja egy hostszintű SSH-policy biztonságos cseréjét. Ilyen változtatásnál már az első commit előtt konzol és előre élesített rollback szükséges.

31.5.8 ICMPv6 és SSH: visszaúti fixture

Az alábbi illusztratív IPv6-fixture, nem a fenti IPv4-labor mérési eredménye. Kliens: 2001:db8:155:1::5; szerver: 2001:db8:155:2::10, TCP/22.

Tünet és fixture-adat Hipotézis Ellenpróba és célzott javítás
SYN eléri a szervert; SYN-ACK másik átjárón távozik Hibás vagy aszimmetrikus visszaút Szerveroldali route- és policy-rule vizsgálat; a helyes visszaút beállítása
SSH-belépés sikerül, nagy átvitel megakad; ICMPv6 Packet Too Big eldobási számláló nő PMTU-visszajelzés szűrése A releváns ICMPv6 hibaüzenet engedélyezése a tényleges input/forward útvonalon
Már a helyi szomszéd feloldása sikertelen Neighbor Discovery tiltása Neighbor Solicitation/Advertisement vizsgálata a megfelelő helyi linken

Az IPv6 szomszédfelderítés linkhelyi forgalma és a továbbított kapcsolat ICMPv6-hibavisszajelzése nem ugyanaz a policykérdés. A „TCP/22 engedélyezett” állítás egyik működését sem bizonyítja. A megoldás nem az IPv6 kikapcsolása, hanem típus-, irány- és scope-helyes szabályozás.

31.5.9 Feladatok

  1. Magyarázó: miért nem bizonyítja a működő WireGuard-kézfogás a HTTP-elérhetőséget? Miért térhet el a NAT- és filterszámláló?
  2. Adminisztrációs: hajtsd végre a pozitív és negatív tesztmátrixot. Ments számlálóállapotot előtte és utána, majd készíts baseline-t. Hajtsd végre a szabályhibát és a rollbacket.
  3. Diagnosztikai: konzol mellett töröld a lab-s alapértelmezett route-ját. Vizsgáld a DNAT- és VPN-kérés hibáját, majd állítsd helyre egyetlen célzott változtatással. Melyik hibát nem javítaná az nft-baseline visszatöltése?

31.5.10 Megoldások

  1. A kézfogás a külső UDP-adatút és a kulcsazonosság működését mutatja. A belső route, AllowedIPs, forward-policy, szolgáltatás és visszaút ettől még hibás lehet. A NAT-lánc nem minden kapcsolati csomagnál végez új szabálykiértékelést.
    Postcondition: a jegyzőkönyv külön kezeli a kézfogást, HTTP-választ és csomagszámlálókat.

  2. A pozitív próbákhoz alkalmazásválasz és megfelelő adatút, a negatívhoz sikertelenség és eldobási számlálónövekedés tartozik. Rollback után mindkét típus ismétlendő, új management SSH-kapcsolatokkal.
    Postcondition: nincs lab-failure szabály; a megengedett és tiltott utak egyaránt megfelelnek.

  3. lab-fw, UID 0, hibainjektálás és ellenőrzés:

    ip -n lab-s route del default via 10.155.20.1
ip -n lab-s route get 10.155.0.2
ip -n lab-s route get 10.155.30.2

    A két route-lekérdezésnél elérhetetlenség várható. A szerveroldali capture mutathat beérkező SYN-t, de működő visszaút nincs. Javítás:

    ip -n lab-s route add default via 10.155.20.1

    Postcondition: friss DNAT- és VPN-kéréssel ismét lab-ok érkezik. Az nft-baseline nem javít route-hibát: a rollback hatókörét rétegenként kell meghatározni.

31.5.11 Cleanup és lezárás

A capture-öket előbb állítsd le. A munkakönyvtárak kizárólag e laborhoz tartozhatnak; a szükséges bizonyítékot előbb másold ki, privát kulcs nélkül.

lab-fw, UID 0:

systemctl stop lab-fw-rollback.timer lab-fw-rollback.service

for ns in lab-c lab-s lab-r; do
    ip netns pids "$ns" | xargs -r kill -TERM
done

ip -n lab-r link set lab-wan down
ip -n lab-r address del 10.155.0.1/30 dev lab-wan
ip -n lab-r link set lab-wan name enp7s0
ip -n lab-r link set enp7s0 netns 1

for ns in lab-c lab-s lab-r; do
    ip netns del "$ns"
done
rm -rf -- /run/lab-fw

lab-peer, UID 0:

systemctl stop lab-peer-http.service
ip route del 10.155.20.2/32 dev lab-wg
ip link del lab-wg
ip address del 10.155.0.2/30 dev enp7s0
ip link set enp7s0 down
rm -rf -- /run/lab-peer

A már lejárt vagy eltávolított transient unit „not loaded” jelzése önmagában nem cleanup-hiba. Ellenőrizd a namespace-ek és tunnel eltűnését, a dedikált NIC-ek kezdeti állapotát, majd ismételd meg az új SSH-kapcsolatos management-próbát. Ez a labor lezárási postconditionje.

31.5.12 Rövid összefoglaló

A tűzfal helyességét alkalmazásszintű pozitív és negatív próbák, szabályszámlálók és interfészenkénti csomagrögzítés együtt igazolják. A NAT-számláló nem teljes forgalommérő, a kapcsolatkövetés pedig korábbi állapottal befolyásolhatja az eredményt. A WireGuard-kézfogást külön kell választani a privát szolgáltatás működésétől. A rollback csak azokat a rétegeket állítja helyre, amelyeket ténylegesen kezel; a route-hibát nem javítja egy nft-fájl visszatöltése. Helyreállítás után új management-kapcsolattal ellenőrzünk, majd csak a név szerint kijelölt labobjektumokat takarítjuk el.

  • Policybizonyíték: alkalmazáseredmény, szabálytalálat és adatút összhangja.
  • Baseline: ellenőrzött, visszatölthető konfigurációállapot.
  • Visszaút: a válaszcsomag célhoz vezető útvonala és annak policyfeltételei.
