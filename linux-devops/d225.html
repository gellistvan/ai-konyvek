45.5 Cloud packet/storage/recovery labor

45.5.1 Motiváció és méréshatár

A cloudban egy alkalmazáshiba mögött gyakran egymásra rétegzett okok állnak: a guest Linux útválasztás, a provider VPC route/firewall/szolgáltatásvégpont, az IAM identity, a DNS és a tárolóréteg. Ha csak a guestben nézel, a VPC endpoint hiánya vagy az IAM tiltás a homályban marad; ha csak a provider konzoljában nézel, nem tudod, hogy az alkalmazás valóban próbált-e kapcsolódni. A d225 labor célja, hogy egy topológiafixture segítségével a provider és a guest oldali bizonyítékokat egyetlen diagnosztikai láncba kösd, és a javítást, a helyreállítást, valamint a cleanup utófeltételt ugyanabban a folyamatban bizonyítsd.

A példában AWS-szerű parancsokat és erőforrásneveket használunk, de a logika más cloud providerre is lefordítható. A parancsok explicit profile, region, VPC, instance és bucket azonosítót tartalmaznak. A módosító parancsok mindig csak a lab- prefixummal jelölt, erre a laborra létrehozott erőforrásokra terjednek ki. A példa nem éles accountot feltételez, hanem egy elkülönített sandbox vagy offline policy-fixture alapján tanít.

45.5.2 Definíciók és topológiafixture

Provider manifest: a VPC, subnet, route table, security group, IAM role/policy, VPC endpoint, bucket és volume desired-state leírókészlete. A manifest a helyreállítás és a cleanup ellenőrzésének forrása; amit nem tartalmaz, az nem tartozik a labor hatókörébe.

Flow log: a provider által rögzített hálózati eseményrekord. A VPC, subnet vagy ENI szintjén mutatja a forrás/cél/pont/port, valamint az ACCEPT/REJECT döntést anélkül, hogy a payloadot megosztaná. A flow log a hálózati réteghatárok legfontosabb provider oldali bizonyítéka.

Recovery postcondition: egy parancssorozattal igazolt állapot, amely bizonyítja, hogy az erőforrás a helyreállítás után is működik, és a cleanup nem hagy hátra labon kívüli, nem kívánt erőforrást. A postcondition tartalmazza a várt bemenetet, a várt kimenetet és a megfigyelt állapotot. Nem elegendő „a backup létezik”, mert a visszaállítás csak a sikeres smoke teszttel válik bizonyítottá – ahogyan a d100 is tanítja.

A fixture topológiája:

Erőforrás Név Leírás
VPC lab-vpc 10.44.0.0/16, DNS resolution engedélyezett
Privát subnet lab-subnet-app 10.44.10.0/24
Bastion subnet lab-subnet-bastion 10.44.20.0/24, internet gateway
Route table lab-rt-app a privát subnetre asszociálva, S3 endpoint route hiányzik
VPC endpoint lab-vpce-s3 S3 gateway endpoint, route asszociáció nélkül
Ec2 instance lab-instance-app privát subnetben, IAM role: lab-s3-role
S3 bucket lab-bucket-<account> versioning engedélyezve, fixture objektum
IAM role lab-s3-role trust: EC2, kezdetben nincs S3 policy
Flow log lab-vpc-flow a lab-vpc minden forgalmát rögzíti

A desired state: a lab-instance-app a lab-bucket lab-fixture/data.txt objektumát eléri, és a HTTP válasz 200, a tartalom pedig lab-ok. A megfigyelt állapot kezdetben timeout, majd javítás után 403 AccessDenied, a két különböző réteg két egymás utáni hibája.

45.5.3 Kidolgozott példa: privát bucket elérés javítása

A példa laborablakában először a provider manifestet olvassuk be, majd a guestből és a provider oldalról végzünk mérést. Az alábbi parancsok mind a lab profile-ban, eu-central-1 régióban futnak.

45.5.3.1 Első kör: route hiány

Bekérjük az instance és a route table állapotát:

# provider oldal, lab account, eu-central-1, lab-instance-app cél
aws ec2 describe-instances --profile lab --region eu-central-1 \
  --filters "Name=tag:Name,Values=lab-instance-app" \
  --query 'Reservations[].Instances[].[InstanceId,State,PrivateIpAddress,SubnetId]'

aws ec2 describe-route-tables --profile lab --region eu-central-1 \
  --filters "Name=association.subnet-id,Values=subnet-0a1b2c3d" \
  --query 'RouteTables[].Routes[].[DestinationCidrBlock,GatewayId,VpcEndpointId]'

aws ec2 describe-vpc-endpoints --profile lab --region eu-central-1 \
  --filters "Name=vpc-id,Values=vpc-0e1f2g3h" \
  --query 'VpcEndpoints[].[VpcEndpointId,ServiceName,State,RouteTableIds]'

Várt, illusztratív kimenet: az instance running, privát 10.44.10.10 címmel; a lab-rt-app route table csak a helyi 10.44.0.0/16 bejegyzést mutatja, az S3 endpoint lista RouteTableIds eleme üres. A VPC endpoint available állapotú, de nincs asszociálva a privát subnet route table-jéhez.

A guest oldalon a hibát tünetként rögzítjük. A lab-instance-app konzolján:

# lab-instance-app, 10.44.10.10, lab account
ip route
getent hosts lab-bucket.s3.eu-central-1.amazonaws.com
curl -Iv --max-time 10 https://lab-bucket.s3.eu-central-1.amazonaws.com/lab-fixture/data.txt

Várt kimenet: ip route nem mutat 0.0.0.0/0-t, mert a subnet privát; a DNS getent sikeresen feloldja a bucket nevet a VPC resolveren keresztül; a curl azonban timeoutot ad, mert a forgalom nem éri el a VPC endpointot.

A flow logot a provider oldalon kapcsoljuk be, majd a sikertelen curl után lekérdezzük:

# flow log létrehozása a lab-vpc-n, provider oldal
aws ec2 create-flow-logs --profile lab --region eu-central-1 \
  --resource-type VPC --resource-id vpc-0e1f2g3h \
  --traffic-type ALL \
  --log-destination-type cloud-watch-logs \
  --log-group-name lab-vpc-flow

A CloudWatch Logs Insights lekérdezés:

fields @timestamp, srcAddr, dstAddr, dstPort, action, bytes
| filter srcAddr = '10.44.10.10' and dstPort = 443
| sort @timestamp desc
| limit 20

Várt eredmény: nincs ACCEPT vagy REJECT rekord a 10.44.10.10 és az S3 endpoint között, mert a route hiány miatt a forgalom el sem jut a flow log által megfigyelt szintre. A tünet és a bizonyíték a guest timeout, a provider flow log üressége és a route table hiánya. Ez elég a hipotézishez: a privát subnet route table nem tudja, hogy az S3 forgalmat az endpointra kell küldeni.

Az első javítás a VPC endpoint és a route table asszociációja:

# provider oldali módosítás, lab- prefix, eu-central-1, lab account
aws ec2 create-vpc-endpoint-route-table-association \
  --profile lab --region eu-central-1 \
  --vpc-endpoint-id vpce-0abc1234 \
  --route-table-id rtb-0def5678

A route table ellenőrzése most már tartalmazza az S3 endpointot. A guest curl most már nem timeoutot ad, hanem HTTP 403-at. Ezzel a route réteg rendben van.

45.5.3.2 Második kör: IAM policy hiány

A 403-as válasz a guest oldalon:

HTTP/1.1 403 Forbidden
Code: AccessDenied
Message: User: arn:aws:sts::111122223333:assumed-role/lab-s3-role/i-0abcd1234
         is not authorized to perform: s3:GetObject
         on resource: arn:aws:s3:::lab-bucket-111122223333/lab-fixture/data.txt

A hibaüzenet önmagában is az IAM rétegre mutat, de az ellenpróbához ellenőrizzük a role policy meglétét:

# provider oldal, identity réteg
aws iam get-role --profile lab --role-name lab-s3-role \
  --query 'Role.[RoleName,Arn]'

aws iam list-role-policies --profile lab --role-name lab-s3-role

Várt kimenet: a role létezik, de a policy lista üres. A guestben a curl már eléri a bucketet, tehát a hálózati út és a DNS egyaránt működik. A hiba már nem a packet path, hanem a hozzáférés-engedély hiánya.

A javításhoz létrehozunk egy S3 olvasási policy-t. A lab-s3-policy.json:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::lab-bucket-111122223333/lab-fixture/*"
    }
  ]
}

Alkalmazzuk:

# provider oldali módosítás, lab- role, lab account
aws iam put-role-policy --profile lab --region eu-central-1 \
  --role-name lab-s3-role \
  --policy-name lab-s3-read-fixture \
  --policy-document file://lab-s3-policy.json

A végső smoke test a guestből:

# lab-instance-app, guest oldal
curl -s --max-time 10 https://lab-bucket.s3.eu-central-1.amazonaws.com/lab-fixture/data.txt

Várt kimenet: lab-ok. A postcondition bizonyított: a route table, az endpoint asszociáció, a DNS, a flow log és az IAM policy mind a megfelelő rétegben működik. A recovery nem egyszerűen „újra próbálkozott”, hanem a route és az identity hibát külön, ellenőrzött lépésben javította.

45.5.4 Hibák és ellenpróbák

A cloud incidensben a tüneteket a réteghez kell kötni. A leggyakoribb hibamódok:

Tünet Valószínű réteg Ellenőrzés Ellenpróba
Timeout, nincs hálózati válasz VPC route, subnet, security group ip route, flow log, aws ec2 describe-security-groups A bastionból indított próba eljut-e ugyanoda?
HTTP 403, AccessDenied IAM, bucket policy, KMS aws sts get-caller-identity, list-role-policies A role nélküli publikus teszt objektum elérhető-e?
DNS nem oldódik VPC DNS resolver, privat hosted zone getent, dig, DNS query logs IP-címmel, Host headerrel sikeres-e a kérés?
QuotaExceededException Region quota aws service-quotas get-service-quota Másik régióban vagy csökkentett méretben sikerül-e?
InvalidAMI / API eltérés Region mismatch, deprecation describe-images region, describe-subnets availability zone Ugyanaz az image másik regionban megtalálható-e?
Storage NoSuchVersion Bucket versioning, lifecycle list-object-versions, get-bucket-lifecycle Egy másik verzió head-object válasza

Az ellenpróba mindig egyetlen feltételt változtat. Ha a 403 javításához egyszerre cserélsz route table-t, security groupot és IAM policy-t, nem tudod megmondani, melyik hiba melyik rétegben volt. A sopra leírt példában a route javítása után a 403 megmaradt, ezért a hálózati réteg kizárhatóvá vált.

A region/quota/identity hibák tipikus jele: az API hívás azonnal AccessDenied, QuotaExceededException vagy UnsupportedOperation hibát ad. Ilyenkor nem a guestben kell keresni, hanem a provider control plane-ben. A guest oldali hiba pedig akkor látszik hálózatinak, ha az API válasz késik vagy timeoutol; ez regionális kapcsolati, route vagy DNS hibára utalhat.

A flow log hiányossága, hogy nem mutatja a tartalmat és nem minden esetben a teljes adatutat. A REJECT pickup mellett az üres log is értelmezhető bizonyíték, ha a forgalom nem éri el a megfigyelt erőforrást.

45.5.5 Feladatok

45.5.5.1 1. Feladat – Tünetek réteghez rendelése

A példában a lab-instance-app először timeoutot, majd 403-at adott. Magyarázd el, milyen provider oldali bizonyítékok alapján döntöd el, hogy a második hiba már nem hálózati, hanem IAM hiba. Sorold fel a rétegeket, a megfigyelt jelet és a megerősítő ellenpróbát.

45.5.5.2 2. Feladat – Object lifecycle és restore fixture

Kapcsold be a lab-bucket-<account> bucket verziókezelését, tölts fel egy lab-fixture/v2.txt objektumot, majd töröld a legfrissebb verziót. Állítsd vissza az objektumot a verziókezelésből, és bizonyítsd a postconditiont: a head-object válasz ContentLength megegyezik a manifestben rögzített hosszal. A parancsokban explicit bucket, régió és profile szerepeljen.

45.5.5.3 3. Feladat – Region/quota hibák és cleanup postcondition

Szimuláld a következő hibát: egy új lab-instance-app2 indítása QuotaExceededException hibát ad. Diagnosztizáld, hogy a hiba quota, region vagy IAM, és ne a guestben keress hálózati tünetet. Ezután hajtsd végre a teljes cleanup-t a labor összes lab- prefixumú erőforrására, és bizonyítsd, hogy egyik sem maradt meg. Namuljon mentség a policy-fixture, hogy a parancsok nem futtatottak, de a pseudocode és a postcondition ellenőrzés leírása elvárt.

45.5.6 Megoldások

45.5.6.1 1. Megoldás – Tünetek réteghez rendelése

A tünetek réteghez rendelése:

  • Network/route réteg: a guest curl timeout, az ip route nem mutat default route-ot, a provider flow log nem tartalmaz forgalmat a forrás és az S3 endpoint között, a route table nem tartalmazza az endpointot. Az ellenpróba: a VPC endpoint hozzáadása után a timeout megszűnik, ez bizonyítja a route hiányt.
  • Identity/IAM réteg: a curl most már 403 AccessDenied hibát ad, az aws sts get-caller-identity a lab-s3-role-t mutatja, a list-role-policies üres. Az ellenpróba: a policy hozzáadása után a curl 200-at ad.
  • DNS réteg: a getent hosts sikeres volt, tehát a DNS nem volt hiba. Ha sikertelen lett volna, a curl Could not resolve host jelzett volna.

A postcondition: a guestből a bucket lab-fixture/data.txt tartalma lab-ok, a flow log ACCEPT rekordot mutat a 443-as porton. Ez a három bizonyíték együtt igazolja, hogy a hálózati és identity réteg is rendben van.

45.5.6.2 2. Megoldás – Object lifecycle és restore fixture

A verziókezelés bekapcsolása:

# lab account, eu-central-1, lab-bucket, provider oldal
aws s3api put-bucket-versioning --profile lab \
  --bucket lab-bucket-111122223333 \
  --versioning-configuration Status=Enabled

Feltöltés, törlés, visszaállítás:

# upload fixture, provider oldal
echo 'v2-content' > /tmp/lab-v2.txt
aws s3api put-object --profile lab --bucket lab-bucket-111122223333 \
  --key lab-fixture/v2.txt --body /tmp/lab-v2.txt

# delete object: delete marker keletkezik a verziókezelés miatt
aws s3api delete-object --profile lab --bucket lab-bucket-111122223333 \
  --key lab-fixture/v2.txt

# a verziók listázása megmutatja a delete marker-t
aws s3api list-object-versions --profile lab \
  --bucket lab-bucket-111122223333 \
  --prefix lab-fixture/v2.txt

# a delete marker eltávolítása visszaállítja a legfrissebb verziót
# ehhez a delete marker VersionId-ját kell megadni, például:
aws s3api delete-object --profile lab --bucket lab-bucket-111122223333 \
  --key lab-fixture/v2.txt --version-id "delete-marker-version-id"

Várt kimenet: a list-object-versions először a törölt objektum DeleteMarker elemet mutat; a törlési marker eltávolítása után a head-object ismét a ContentLength-et (10 bájt) adja vissza. A postcondition: az objektum ismét elérhető, és a verziótörténetben a VersionId nem törlődött.

45.5.6.3 3. Megoldás – Region/quota hibák és cleanup postcondition

Diagnosztika:

# quota lekérdezés, provider oldal
aws service-quotas get-service-quota --profile lab --region eu-central-1 \
  --service-code ec2 --quota-code L-0263D0A3

# IAM ellenőrzés: a lab role policy tartalmaz-e az ec2:RunInstances engedélyt?
aws iam get-role-policy --profile lab --role-name lab-s3-role \
  --policy-name lab-ec2-launch-policy

# region ellenőrzés: a kért AMI elérhető-e a cél regionban?
aws ec2 describe-images --profile lab --region eu-central-1 \
  --image-ids ami-0lab0001

A QuotaExceededException a service-quota Value és Quota mezőjéből olvasható le; a hiba nem a guestben, hanem a provider control plane-ben jelentkezik. Ha a quota engedélyezett, az IAM policy hiánya AccessDenied hibát adna, ami elkülöníthető. A region hibát pedig az AMI elérhetősége mutatja.

A cleanup a lab- prefixumos erőforrásokra:

# lab-instance-app terminate
aws ec2 terminate-instances --profile lab --region eu-central-1 \
  --instance-ids i-0abcd1234

# bucket teljes tartalom törlése, verziókkal együtt
aws s3 rm s3://lab-bucket-111122223333 --recursive --profile lab

# VPC endpoint törlése
aws ec2 delete-vpc-endpoints --profile lab --region eu-central-1 \
  --vpc-endpoint-ids vpce-0abc1234

# route table, subnet, VPC törlése
aws ec2 delete-route-table --profile lab --region eu-central-1 \
  --route-table-id rtb-0def5678
aws ec2 delete-subnet --profile lab --region eu-central-1 --subnet-id subnet-0a1b2c3d
aws ec2 delete-vpc --profile lab --region eu-central-1 --vpc-id vpc-0e1f2g3h

A cleanup postcondition ellenőrzése:

# listázás: a lab- prefixumú erőforrások ne jelenjenek meg
aws ec2 describe-instances --profile lab --region eu-central-1 \
  --query 'Reservations[].Instances[].InstanceId' --filters "Name=tag:Name,Values=lab-*"
aws s3 ls --profile lab | grep 'lab-bucket'
aws ec2 describe-vpcs --profile lab --region eu-central-1 --query 'Vpcs[].[VpcId]'

Várt kimenet: üres listák, nincs lab- prefixumtal rendelkező maradék. A parancsok nem futtatottak ebben a kérésben, ezért a várt kimenet illusztratív.

45.5.7 Rövid összefoglaló

A cloud hibákat rétegenként kell lokalizálni: a provider VPC route/firewall/endpoint, az IAM identity, a DNS, a storage és a guest Linux egyaránt hibásodhat. A flow log a hálózati réteghatár provider oldali bizonyítéka, a guest ip route/curl pedig a tényleges alkalmazáskérést mutatja. A javítás után a postcondition minden rétegben mérhető: a curl 200-as válasza, a flow log ACCEPT bejegyzése és az IAM policy jelenléte együtt igazolják a helyreállítást. A cleanup csak a lab- prefixumú erőforrásokra terjed, és a leftover ellenőrzés üres listát vár. A bucket verziókezelés a törlés ellenére visszaállítható, ezért a data integrity postcondition a head-object válasz.

Továbbhasznált definíciók:

  • Provider manifest: a VPC, route, firewall, IAM, endpoint és tároló desired-state leírókészlete.
  • Flow log: a provider által rögzített hálózati esemény, amely a forrás/cél/port/pont és ACCEPT/REJECT döntést mutatja.
  • Recovery postcondition: a javítás után mérhető állapot, amely bizonyítja a szolgáltatás működését és a cleanup hatókörét.

45.5.8 Források és ellenőrzési hiányok

Ebben a kérésben nem volt webes kutatás, ezért az alábbi forráskiindulópontok nem olvasott, nem ellenőrzött bizonyítékok. Az aktuális support, API formátum és hibaüzenetek ellenőrzését a lab során kell elvégezni.

  • AWS VPC documentation – VPC endpoint, route table, flow log.
  • AWS S3 documentation – bucket versioning, lifecycle, delete-object.
  • AWS IAM documentation – role, policy, put-role-policy.
  • AWS Service Quotas documentation – quota lekérdezés és hibaüzenet.

Ellenőrzési hiányok: az AWS CLI pontos verzióját és a hívások kimeneti JSON formátumát a sandbox accountban kell validálni. A flow log CloudWatch Logs Insights lekérdezés szintaxisa és mezőnevei providerfüggők. A quota kód és a regionális eltérések a hivatalos dokumentáció alapján frissítendők. A példa illusztratív, nem futtatott labor.
