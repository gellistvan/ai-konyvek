34.3 vCPU, memória, overcommit és NUMA

34.3.1 Motiváció

A virtualizáció egyik legfélrevezetőbb telemetriája, amikor a vendég operációs rendszer (guest OS) szerint a CPU telített, a host hypervisor szerint viszont bőven van szabad processzor. KVM/QEMU környezetben a vendég CPU-ját egy host szál ütemezi; ha a host túlvállalt, akkor a vendég időt lopnak el a számításból, amit a guest külön mutatóként lát. A memóriánál hasonló kettősség: a guest láthat 2 GiB szabad memóriát, a host viszont ugyanazt a lapokat már swapra vagy ballooningba kényszerítette. A fejlesztői gyakorlatban ez a támogatási hívás tipikus félreértése: a guest high CPU nem jelenti automatikusan, hogy a workload túl lassú; könnyen lehet, hogy a hypervisor egyszerűen nem ad neki processzort. Ebben az alfejezetben a vCPU ütemezés, memory backing, NUMA elhelyezés és a host erőforrás-controller együttes modelljét építjük fel, hogy az üzemeltető a guest és a host telemetriát egyben értelmezze.

34.3.2 Definíció és működés

34.3.2.1 vCPU, scheduling, oversubscription és steal

A KVM guest minden virtuális CPU-ja (vCPU) a QEMU processz egy-egy host threadje. A hardware virtualizációs kiterjesztések (Intel VMX vagy AMD SVM) a guest user/kernel módú utasításait többnyire közvetlenül a fizikai magon futtatják; a KVM a virtuális megszakításokat, I/O-t és az időzítőket emulálja. Amikor a guest idle, a vCPU végrehajt egy HLT utasítást, és a host thread elalszik. Amikor a guest dolgozik, a vCPU thread futni szeretne, és a host Linux scheduler ugyanúgy ütemezi, mint bármely más threadet.

CPU oversubscription (CPU túlvállalás) azt jelenti, hogy az összes guest vCPU összege nagyobb, mint a host fizikai processzorok száma. Ez nem tiltott állapot; a legtöbb virtualizált szerveren ez a bevált gyakorlat, mert a guestek ritkán futnak egyszerre 100%-on. Ha mégis, akkor a runnable vCPU-k versenyeznek a host CPU-ért, a host scheduler várakozási sora nő, a guest pedig CPU steal-t vagy scheduler jitter-t érzékel.

CPU steal a guest operációs rendszer /proc/stat jában megjelenő idő, ami alatt a vCPU runnable volt, de a hypervisor nem adott neki host processzort. A guest kernel a hypervisor által szolgáltatott paravirtualizált óra alapján méri ezt. A guest top az adott ablakban a %st oszlopban mutatja; a guest /proc/stat CPU sorában a steal mező a teljes időhöz viszonyítva:
steal arány=stealuser+nice+system+idle+iowait+irq+softirq+steal\text{steal arány} = \frac{\text{steal}}{\text{user} + \text{nice} + \text{system} + \text{idle} + \text{iowait} + \text{irq} + \text{softirq} + \text{steal}}

CPU throttling különbözik a steal általános versenyétől: ha a hypervisor felső CPU-kvótát szab, a vCPU a kvóta túllépése után mesterségesen futásra képtelen, akkor is, ha a host üres. Ez a host oldali cgroup v2 cpu.max vagy a libvirt cputune quota korlát következménye. A guest ezt is steal-ként látja, de a host oldalon a cgroup cpu.stat throttled_time mezője megkülönbözteti a scheduler contentiontől.

34.3.2.2 Memória, balloon és hugepages

A guest RAM mögötti host memória a QEMU processz anonim vagy file-backed lapja. KVM a guest fizikai címeket második szintű címfordításon (Extended Page Table, EPT vagy Nested Page Table, NPT) keresztül a host fizikai lapokra képezi. A fordítás sebessége nagymértékben függ a host lapok nagyságától: a 2 MiB vagy 1 GiB hugepages lapok csökkentik a TLB miss-eket és a második szintű page walk költségét. A libvirt memoryBacking/hugepages beállítása statikus, előre elkülönített 2 MiB-os lapokat igényel a hoston.

Ballooning a virtio-balloon eszköz: a guest kernel együttműködik, és a hostnak visszaadhat fel nem használt lapokat; a guestben ez memórianyomást okoz, mert a visszavett lapoknál a guest kernel reclaimot vagy swapot indít be. A balloon nem a host swap, hanem a guest szabad memóriájának hypervisor általi visszavétele; a guest free nem feltétlenül tükrözi a host látható fizikai hátteret. A hoston a virsh dommemstat vagy a balloon driver mutatja a ténylegesen visszavett lapokat.

34.3.2.3 NUMA topology, vNUMA és pinning

A host NUMA (Non-Uniform Memory Access) node processzorokból és a hozzájuk tartozó memóriavezérlőből áll. A KVM guest virtuális NUMA topológiát kaphat, ha a libvirt <cpu><numa> cellákat definiál. Ez azért fontos, mert a guest kernel saját ütemezője a cellákon belül próbálja tartani a feladatokat és a memóriát; ha a vCPU-k a 0. host node-on futnak, de a memória a 1. node-on van, akkor a guest futása remote memóriahozzáférést szül. A vNUMA és a pin nem önmagában oldja meg a dolgot: a vCPU pin mellett explicit memória-node elhelyezés kell (libvirt numatune, memoryBacking hugepages node specifikálásával). A virsh numatune és a numastat a guest által használt host node-ok remote arányát mutatja.

34.3.2.4 Cgroup és host resource quota

A libvirt által indított QEMU folyamatok a systemd /machine.slice alá tartoznak. A cgroup v2 cpu.max a CPU-kvótát, a memory.max a memória felső határát szabályozza. Ez azt jelenti, hogy egy VM soha nem fogyaszthatja el a host teljes memóriáját, mert a cgroup local OOM megöli a leggazdagabb guest processzt, vagy a host swapot használ. A host erőforrás-controller tehát a virtualizációs ütemező alatt, a kernel szintjén további kemény korlátot ad.

34.3.2.5 Noisy neighbor és failure headroom

Noisy neighbor nek nevezzük a más VM-et, konténert vagy host folyamatot, amely ugyanazon fizikai erőforráson (CPU, L3 cache, memory bandwidth, disk, network) osztozik. Az L3 cache és a memory bandwidth contention különösen alattomos: a CPU kihasználtság 50% alatt is nagy latency növekedést okoz, mert a vCPU-k evictálják egymás cache sorait. A failure headroom az a kapacitástartalék, amelyet a hoston kihasználatlanul hagyunk, hogy egy VM burstje, egy crash loop vagy egy replikált workload ne döntse ki a többi VM-et. A pinning csökkenti a CPU topológiai bizonytalanságot, de a noisy neighbour cache/bandwidth hatást nem szünteti meg: közös utolsó szintű cache (LLC) és memóriavezérlő marad.

34.3.2.6 Guest versus host telemetria

A guest önmagában látja a belső futó folyamatokat, a saját idle/steal arányt, a saját memórianomást. A host látja a QEMU thread tényleges CPU-ját, a scheduler várakozási idejét, a cgroup pressure-t, a balloon aktuális méretét, a page fault és a node elérési statisztikákat. A diagnosztika szabálya: ha a guest magas CPU-t jelez, de a host QEMU thread CPU alacsony, akkor a vCPU contention, nem a guest belső munkája a szűk keresztmetszet. Ha a host QEMU thread CPU magas, a guest CPU is magas, akkor a workload valóban a vCPU-n dolgozik.

Jelenség Guest telemetria Host telemetria
CPU-bound workload magas %usr QEMU thread magas %CPU
CPU oversubscription magas %steal QEMU thread runnable/sleep arány, host CPU saturation
CPU quota magas %steal, alacsony %usr QEMU thread limitált burst, cgroup cpu.stat throttling
Memória balloon guest reclaim, swap virsh dommemstat, balloon méret
NUMA remote guest nehéz memória hozzáférés numastat, perf, node distance

34.3.3 Kidolgozott példa

Egy KVM hoston (lab-hv01, Ubuntu 24.04 LTS, root/sudo) dedikált lab guestet hozunk létre. Feltételezett host topológia: 8 CPU, 16 GiB RAM, két NUMA node (0: CPU 0–3, 8 GiB; 1: CPU 4–7, 8 GiB). A guest igénye: 4 vCPU, 2 GiB RAM, statikus 2 MiB hugepages backing, vCPU pinning a 4–7 CPU-ra, emulatorpin ugyanoda, virtuális topológia 1 socket / 4 core. Desired state: a guest csak a node 1 CPU-it használja, és a memóriája is lehetőleg a node 1-en van.

A libvirt domain XML kulcstöredéke:

<domain type='kvm'>
  <name>lab-cpp-guest</name>
  <uuid>a1b2c3d4-e5f6-4a7b-9c0d-0123456789ab</uuid>
  <memory unit='KiB'>2097152</memory>
  <currentMemory unit='KiB'>2097152</currentMemory>
  <vcpu placement='static'>4</vcpu>
  <cputune>
    <vcpupin vcpu='0' cpuset='4'/>
    <vcpupin vcpu='1' cpuset='5'/>
    <vcpupin vcpu='2' cpuset='6'/>
    <vcpupin vcpu='3' cpuset='7'/>
    <emulatorpin cpuset='4-7'/>
  </cputune>
  <numatune>
    <memory mode='strict' nodeset='1'/>
  </numatune>
  <cpu mode='host-passthrough' check='none'>
    <topology sockets='1' dies='1' cores='4' threads='1'/>
    <numa>
      <cell id='0' cpus='0-3' memory='2097152' unit='KiB'/>
    </numa>
  </cpu>
  <memoryBacking>
    <hugepages>
      <page size='2048' unit='KiB' nodeSet='1'/>
    </hugepages>
  </memoryBacking>
</domain>

A fenti XML a kulcstöredék; a uuid a labban egyértelmű, a teljes domain XML-nek tartalmaznia kell a szokásos device, firmware és boot részt. A numatune memory mode='strict' nodeset='1' a guest memória allokációt a 1. NUMA node-ra kényszeríti. A memoryBacking hugepages statikus 2 MiB lapot kér a megadott node-on. A cputune a vCPU-kat a 4–7 CPU-khoz köti, így a guest kernel vCPU ütemei a node 1 fizikai magjain maradnak.

Laborparancsok ellenőrzésre (root szükséges, qemu:///system):

# lab-hv01, UID=0
virsh -c qemu:///system define lab-cpp-guest.xml
virsh -c qemu:///system start lab-cpp-guest

# CPU pinning és NUMA ellenőrzése
virsh -c qemu:///system vcpupin lab-cpp-guest
virsh -c qemu:///system emulatorpin lab-cpp-guest
virsh -c qemu:///system numatune lab-cpp-guest

# Memória és hugepages
virsh -c qemu:///system dommemstat lab-cpp-guest
grep -i hugepages /proc/meminfo

Várható kimenet (illusztratív, nem mért): a vcpupin sorok azt mutatják, hogy VCPU3: 7; a numatune nodeset 1; a /proc/meminfo HugePages_Total értéke elegendő. A guestben lscpu 4 CPU-t, a /proc/cpuinfo processor 0-3, a top a %st oszlopot mutatja; nyugalmi állapotban a %st nullához közeli. Ha a hoston másik VM is fut ugyanazon node-on, akkor a guest CPU kihasználtsága mellett a host pidstat a QEMU processzre osztozik.

34.3.4 Hibák és ellenpróbák

A tipikus hiba az, hogy a guest top 100% CPU-ját a host CPU kimerülésnek feleltetjük meg. Ha a host pidstat ugyanarra a QEMU processzre alacsony százalékot mutat, akkor a vCPU runnable, de nem fut; ilyenkor a guest %steal magas. Fordított esetben, ha a host QEMU processz CPU-ja magas, de a guest %steal alacsony, akkor a workload tényleg a guest belső számítását futtatja.

A második hiba a pinning elvégzése memóriaelhelyezés nélkül. Ha a vCPU-t a node 1-hez kötjük, de a memóriát a node 0-ra tesszük, a remote access aránya megnő; a numastat -p $qemu_pid a foreign oszlopban magas arányt mutat. A javítás a numatune vagy a hugepages nodeSet helyes beállítása.

A harmadik hiba a hugepages bekapcsolása anélkül, hogy a host a vm.nr_hugepages és a HugePages_Total értékben tartalékolná a fogadó lapokat. A QEMU indítás cannot open backing store hibával bukik, vagy a guest csendben 4 KiB lapokra esik vissza.

A negyedik hiba a headroom hiánya: a host CPU túlvállalt 8 physics / 12 vCPU arányban, és egy noisy neighbour folyamatosan hozza a cache pressure-t. Ilyenkor a steal nem magas, a CPU sem 100%, de a latency szintje magas. Az ellenpróba a QEMU processz perf stat L3 cache miss és a virsh schedinfo shares növelése, vagy a noisy neighbour CPU pinningjének szűkítése.

34.3.5 Feladatok

  1. Magyarázó feladat
    Magyarázd el, miért mutathat a guest top 90% CPU-t, miközben a host pidstat a QEMU processzre 5% CPU-t mutat. Milyen guest metrika igazolja ezt, és mi a host oldali scheduler jelenség neve? Hogyan döntöd el, hogy a vCPU CPU-throttling vagy CPU oversubscription okozza a latenciát?

  2. Adminisztrációs/konfigurációs feladat
    Egy labhoston 8 CPU, node 0 CPU 0–3, node 1 CPU 4–7. Hozz létre egy lab-cpp-guest domain-t 4 vCPU, 2 GiB memória, 2 MiB hugepages, vCPU pin 4–7, emulatorpin 4–7, memória elhelyezés node 1. Add meg a libvirt XML töredéket és az ellenőrző parancsokat. Írd a desired state-et, a rollback parancsot és az expected postconditiont.

  3. Diagnosztikai/failure/recovery feladat
    Egy lab-cpp-latency guest lassú: a guest mpstat 10-es loadot mutat, a guest %steal 40%, a host pidstat a QEMU processzre 120% CPU-t mutat, de a host összes CPU kihasználtsága 60%. A hoston két másik VM fut ugyanazon a NUMA node-on, az egyik lab-noisy folyamatosan 4 CPU-t telít. Gyűjts adatot (virsh vcpuinfo, virsh schedinfo, numastat, cgroup cpu.stat). Egyetlen beavatkozással javíts a lab-cpp-latency guest steal idején, majd igazold a javulást. Mi a rollback?

34.3.6 Megoldások

  1. A guest futó feladatai futásra kész processzeket és szálakat jelentenek, de a vCPU-k nem kapnak host processzort, mert a host CPU-k más runnable vCPU-kat szolgálnak ki. Ezt a guest a hypervisor által ellátott steal időként méri. A host oldali jelenség: a vCPU thread a scheduler runnable állapotban várakozik, a schedstat wait_start/wait_max idő hosszú. Ha a guestben magas steal és alacsony CPU quota, akkor throttling; ha magas steal és a host CPU telített, akkor oversubscription. A döntés a host pidstat és a cgroup cpu.stat throttled_time mezőjéből hozható: throttlingnál a throttled_time nő.

  2. A szükséges XML-töredék a kidolgozott példában látható, a numatune és hugepages nodeSet hozzáadásával. Az adminisztrátornak:

    # lab-hv01, root
virsh -c qemu:///system define lab-cpp-guest.xml
virsh -c qemu:///system start lab-cpp-guest
virsh -c qemu:///system vcpupin lab-cpp-guest
virsh -c qemu:///system numatune lab-cpp-guest
virsh -c qemu:///system dominfo lab-cpp-guest

    Desired state: a guest vCPU-k a CPU 4–7-re pinnal rendelkeznek, a memória node 1-re allokált, a hugepages backing aktív. Rollback: virsh -c qemu:///system destroy lab-cpp-guest majd virsh -c qemu:///system undefine lab-cpp-guest. Postcondition: a virsh vcpupin minden vCPU-ra a 4–7 CPU-t mutatja, a virsh numatune nodeset 1, a guestben a numastat nem mutat távoli node-ot.

  3. A diagnózishoz először a guest mpstat %steal 40% és a host pidstat QEMU processz 120% CPU ellentmondását kell feloldani: a guest belső CPU 10-es load, de a host processz CPU 120% azt jelenti, hogy a guest tényleg fut, de a steal magas, mert a host CPU 60%-os kihasználtsága mellett a lab-noisy VM folyamatosan 4 CPU-t telít a közös node-on. A steal a guest vCPU-k versengése miatt nő. Az adatgyűjtés:

    • virsh -c qemu:///system vcpuinfo lab-cpp-latency
    • virsh -c qemu:///system schedinfo lab-cpp-latency
    • virsh -c qemu:///system schedinfo lab-noisy
    • numastat -p $(pgrep -f 'qemu.*lab-cpp-latency')
    • systemd-cgtop vagy cat /sys/fs/cgroup/machine.slice/machine-qemu\x2d.../cpu.stat

    A noisy neighbour korlátozás egyetlen beavatkozás: a lab-noisy VM vCPU pinningjét szűkíteni az 5–7 CPU-ra, vagy a virsh schedinfo lab-noisy --set cpu.shares=512. Például:

    virsh -c qemu:///system schedinfo lab-noisy --set cpu.shares=512
virsh -c qemu:///system schedinfo lab-cpp-latency --set cpu.shares=2048

    A javulást a guest mpstat steal 10% alá csökkenésével és a host pidstat értékek stabilizálódásával igazoljuk. Rollback: a shares érték visszaállítása --set cpu.shares=1024. Postcondition: a lab-cpp-latency steal 10% alatt, a lab-noisy továbbra is fut, a host CPU fenntartható 80% alatt marad.

34.3.7 Rövid összefoglaló

A KVM vCPU host szál, a guest CPU-busy nem azonos a host CPU-fogyasztással. A guest %steal a hypervisor által el nem adott futásidőt méri: CPU oversubscription vagy cgroup quota throttling következménye. A memória mögött balloon, hugepages és host oldali reclaim áll, ezért a guest free önmagában félrevezető. A NUMA pinning csak akkor hatékony, ha a vCPU és a memória egyazon host node-on van; a vNUMA topológia önmagában nem garantálja a local access-t. A host cgroup v2 és a libvirt schedinfo korlátai tervezhetővé teszik a noisy neighbor elleni védelmet, miközben failure headroomot hagyunk.

Továbbhasznált definíciók: vCPU steal, CPU oversubscription, vNUMA pinning.
