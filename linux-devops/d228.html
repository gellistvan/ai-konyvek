46.3 Module, environment és változási határ

A modul az OpenTofu/Terraform újrafelhasználható konfigurációs egysége: input változókat, belső erőforrásokat és outputokat fog össze. A jó modulhatár olyan, mint egy C++ osztály interfésze: a hívó csak az input/output szerződést látja, a belső resource-gráf implementáció marad. A határt resource ownership és blast radius szerint kell kijelölni. Ha két erőforrásnak ugyanaz a tulajdonosa, ugyanaz az életciklusa és ugyanaz a változtatási kockázata, akkor egy modulba tartozhat. Ha a hiba terjengési köre különbözik, vagy egy másik csapatnak van joga a state-hez, akkor külön modul és külön állapot kell.

46.3.1 Input, output és típusvalidáció

A modul input oldala variable, output oldala output blokkokból áll. Minden változóhoz érdemes type, description és – ahol a szemantika nem triviális – validation blokkot adni. A validáció a condition kifejezéssel történik; ha hamis, a terraform validate vagy tofu validate a megadott hibaüzenettel buktat.

variable "service_name" {
  type        = string
  description = "DNS-kompatibilis szolgáltatásnév, például lab-auth"

  validation {
    condition     = can(regex("^[a-z0-9][a-z0-9-]{1,61}[a-z0-9]$", var.service_name))
    error_message = "service_name nem érvényes DNS-címke: '${var.service_name}'."
  }
}

variable "instance_count" {
  type    = number
  default = 1

  validation {
    condition     = var.instance_count >= 1 && var.instance_count <= 8
    error_message = "instance_count 1 és 8 között lehet."
  }
}

A típus erős constraint: a map(string) mást jelent, mint a list(string), és a set(string) rendezhető deduplikált halmazt ad. A C++-ból ismert statikus típusfegyelem itt is a hibák korai kiszűrését szolgálja, de a dimenzió nem a fordítás, hanem a config-fa és a state ellenőrzése.

Az output definíciója szintén szerződés. A sensitive = true megjelölés megakadályozza, hogy a CLI tofu output vagy a plan emberi kimenete plaintext titkot mutasson. A titok így is a state-ben maradhat, ezért a state titkosítását és hozzáférését külön kell kezelni (lásd Credentials, Vault és privilege policy).

output "instance_ids" {
  value       = { for k, v in aws_instance.app : k => v.id }
  description = "Példányazonosítók erőforráskulcsonként"
}

output "dns_fqdn" {
  value       = aws_route53_record.app.fqdn
  description = "Publikus DNS-név"
  sensitive   = true
}

46.3.2 Provider-, verzió- és függőségrögzítés

A provider és a CLI verziója része a modulszerződésnek. A required_version azt mondja meg, hogy a tofu/terraform binary mely tartományban elfogadott. A required_providers a provider forrását és verziókorlátját rögzíti.

terraform {
  required_version = ">= 1.8.0, < 2.0.0" # a labprofilban használt verziót ellenőrizni kell

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.80.0" # aktuális támogatott release ellenőrizendő
    }
  }
}

A .terraform.lock.hcl fájl a provider binaryk pontos verzióját és hash-ét rögzíti. Ezt be kell commitolni a Git-re. Ha hiányzik, az init frissítheti a provirdert, és ugyanaz a config más környezetben más viselkedést adhat. A szándékos frissítés az tofu init -upgrade, de akkor a lock-fájl változása külön review tárgya. A dependency pin nem csak determinizmus: a supply-chain határon a provider binary is executable code, ezért a hash-ellenőrzés biztonsági kontroll is (lásd Source-to-runtime trust és provenance).

46.3.3 for_each, count és erőforrás-identitás

A count egy egész szám alapján hoz létre N darab, indexelt resource-ot. Az erőforrás-cím aws_instance.app[0], [1], stb. A for_each map vagy set feletti iterációt jelent, az erőforrás-cím kulccsal azonosít: aws_instance.app["blue"].

resource "aws_instance" "app" {
  count         = var.instance_count
  ami           = var.ami
  instance_type = "t3.micro"

  tags = {
    Name = "${var.service_name}-${count.index}"
  }
}

A count-alapú identitás törékeny, ha a lista közepén változik az elemek sorrendje. Például ha egy háromelemű listából töröljük a másodikat, a [1] és [2] elemek átindexelődnek, és a plan végül destroy/create műveleteket mutathat a valódi változás nélkül is. A for_each map kulcsa ezzel szemben stabil, mert a ["blue"] kulcs akkor is ugyanaz marad, ha más kulcsokat adunk hozzá vagy veszünk el.

variable "ami_ids" {
  type = map(string)
}

resource "aws_instance" "app" {
  for_each      = var.ami_ids
  ami           = each.value
  instance_type = "t3.micro"

  tags = {
    Name = "${var.service_name}-${each.key}"
  }
}

A szabály: ha a példányhalmaz identitása természetes kulccsal leírható (régió, szerep, env, név), akkor for_each; ha valóban sorszámozott, cserélhető egységekről van szó, és a sorrend nem hordoz jelentést, akkor a count is elfogadható. A count indexét soha ne használjuk tartós névnek vagy domain-címke helyén, ha a későbbi sorrendváltozás replan robbanást okoz.

46.3.4 Environment, stack és state-határ

Az environment egy deployment instance: például dev, staging, prod. Mindegyiknek külön root module mappája és külön state path/kulcsa kell legyen. Az OpenTofu/Terraform workspace mechanizmusa létezik, de gyengébb határ, mert ugyanazt a konfigurációt és sokszor ugyanazt a backendet használja, csak a state kulcs tér el; a változtatási kontroll és a resource-tulajdonos szétválasztása nehezebb. A valódi environment boundary ezért külön root module + külön backend key.

lab-tf/
  modules/app-service/
    main.tf
    variables.tf
    outputs.tf
    versions.tf
  envs/
    dev/
      main.tf
      backend.tf
    prod/
      main.tf
      backend.tf

A root module hívja a közös modult, és a hívásnál adja át az environment specifikus inputot:

# envs/prod/main.tf
module "app_service" {
  source = "../../modules/app-service"

  service_name   = "lab-auth"
  instance_count = 3
  ami_ids = {
    "blue"  = "ami-prod-blue"  # illusztratív azonosító
    "green" = "ami-prod-green"
  }

  vpc_id = data.aws_vpc.shared.id
}

A dev és prod root module egymástól függetlenül futtatható, egymás state-jét nem írja. A közös függőségek, például egy shared VPC vagy DNS-zóna, külön shared modulban és külön state-ben élnek. A fogyasztó root module ezt nem importálja közvetlenül, hanem explicit outputból vagy data source-ból olvassa, így a shared dependency tulajdonosi határa megmarad. A remote state data source olvasása is lehetséges, de azzal szigorú output-szerződést kell fenntartani, és a state-hez hozzáférést külön szabályozni.

46.3.5 Lifecycle és create-before-destroy

A lifecycle meta-blokk a resource életciklusára vonatkozó szándékot fogalmazza meg. Az alábbi beállítások léteznek:

  • create_before_destroy = true: először létrehozza az új erőforrást, és csak utána törli a régit.
  • prevent_destroy = true: tiltja a törlést, amíg a beállítást le nem vesszük.
  • ignore_changes = [...]: a felsorolt attribútumok változását a plan nem veszi figyelembe.
  • replace_triggered_by = [...]: más erőforrás vagy attribútum változása kényszerít replace-t.
resource "aws_instance" "app" {
  ami           = var.ami
  instance_type = "t3.micro"

  lifecycle {
    create_before_destroy = true
    ignore_changes        = [ami]
  }
}

A create_before_destroy nem univerzális, és a támogatottság az adott provider/resource dokumentációjában van. Például ha a resource-nak egyedi név-attribútuma van, akkor a régi még létező név ütközhet az újjal; ilyenkor a provider name_prefix-et vagy más ütközésmentes elnevezést igényel. A prevent_destroy nem a védelem, hanem a szándékosság kifejezése: ha valaki törölni próbál, a plan/apply hibát ad, de nem akadályoz meg minden külső törlést.

A plan kimenetéből a replace/destroy következményt fel kell ismerni. Az alábbi jelölések a plan szimbolikájában gyakoriak:

Jelölés a planban Jelentés Művelet
+ új erőforrás create
- meglévő erőforrás destroy
-/+ törlés, majd létrehozás replace, rövid outage lehetséges
+/- létrehozás, majd törlés replace, kevésbé outage
~ in-place frissítés update, nincs replace
<= data source olvasás refresh

A plan szövege a must be replaced kifejezést használ, ha a változás nem vihető in-place. A destroy művelet adatvesztést okoz, ha az erőforrásnak nincs külön persistens háttértárolója; például egy ephemeral root volume-ú instance replace esetén a helyi adat elveszik. A create_before_destroy ezért nem csak kényelem, hanem availability és adatbiztonsági kérdés.

46.3.6 Kidolgozott példa: C++ szolgáltatás modulja

A példa egy tipikus C++ háttérszolgáltatás (például lab-auth) modulját mutatja be, amely hálózati és számítási erőforrásokat fog össze, és explicit határt ad a hívó környezeteknek.

modules/app-service/variables.tf:

variable "service_name" {
  type        = string
  description = "DNS-kompatibilis szolgáltatásnév"

  validation {
    condition     = can(regex("^[a-z0-9][a-z0-9-]{1,61}[a-z0-9]$", var.service_name))
    error_message = "service_name nem érvényes DNS-címke."
  }
}

variable "instance_count" {
  type    = number
  default = 1

  validation {
    condition     = var.instance_count >= 1 && var.instance_count <= 8
    error_message = "instance_count 1 és 8 között lehet."
  }
}

variable "ami_ids" {
  type = map(string)
}

modules/app-service/main.tf:

resource "aws_instance" "app" {
  for_each = var.ami_ids

  ami           = each.value
  instance_type = "t3.micro"

  tags = {
    Name = "${var.service_name}-${each.key}"
  }

  lifecycle {
    create_before_destroy = true
  }
}

modules/app-service/outputs.tf:

output "instance_ids" {
  value       = { for k, v in aws_instance.app : k => v.id }
  description = "Példányazonosítók erőforráskulcsonként"
}

output "dns_fqdn" {
  value       = aws_route53_record.app.fqdn
  description = "Publikus DNS-név"
  sensitive   = true
}

A root module a envs/prod mappában hívja a modult:

# envs/prod/main.tf
module "app_service" {
  source = "../../modules/app-service"

  service_name   = "lab-auth"
  instance_count = 2
  ami_ids = {
    "blue"  = "ami-prod-blue"
    "green" = "ami-prod-green"
  }
}

A futtatás targetje a labhost, ahol a CLI és a state backend elérhető. A parancsok a envs/prod mappából futnak:

labhost:~$ cd /home/labuser/lab-tf/envs/prod
labhost:/home/labuser/lab-tf/envs/prod$ tofu init -backend-config=backend.hcl
labhost:/home/labuser/lab-tf/envs/prod$ tofu plan -out=prod.tfplan
labhost:/home/labuser/lab-tf/envs/prod$ tofu apply prod.tfplan

A várt plan kimenet a for_each kulcsokkal mutatja az identitást:

  # module.app_service.aws_instance.app["blue"] will be created
  + resource "aws_instance" "app" {
      + ami           = "ami-prod-blue"
      + instance_type = "t3.micro"
      + tags          = {
          + "Name" = "lab-auth-blue"
        }
      ...
    }

Plan: 2 to add, 0 to change, 0 to destroy.

Az ellenőrzés: tofu state list modulokkal mutatja a teljes erőforrás-címeket; ha a modulhatár jó, a tofu plan a root module szempontjából csak a modul outputjainak változását jelzi, nem a belső resource-gráfot. A tofu output -json pedig a kimenő szerződést adja.

46.3.7 Tipikus hibák és ellenpróbák

Hiba: a count.index-et használják tartós névhez, majd a lista közepén beszúrnak egy elemet. A plan [1] és [2] destroy/create műveleteket mutat, holott csak átnevezés történt.
Tünet: a planban -/+ jelenik meg, a must be replaced szöveggel, és a tags.Name csak indexben változik.
Adatgyűjtés: tofu plan -out=debug.tfplan && tofu show -json debug.tfplan | jq '.resource_changes[] | select(.change.actions[] == "delete") | .address'.
Egy változtatás: count cseréje for_each mapra, kulcs a tartós név.
Verifikáció: új tofu plan után nincs destroy/create, legfeljebb in-place update.

Hiba: sensitive kimenetet nem jelölnek meg, és a CI log a DNS-nevet vagy token-t részben plaintextben leírja.
Tünet: tofu apply konzolon az outputok szabadon megjelennek.
Megoldás: sensitive = true az outputon, és a hívó oldalon terraform output -json csak dedikált, maszkolt csatornán keresztül fusson. A state ennek ellenére érzékeny adatot tárolhat, ezért a state titkosítás külön követelmény.

Hiba: a .terraform.lock.hcl nincs commitolva. A CI ugyanazt a configot más provider-verzióval futtatja, és a plan nem reprodukálható.
Tünet: ugyanaz a Git commit helyi gépen és CI-ben eltérő provider-hash-t mutat.
Megoldás: a lock-fájl commitolása, tofu init -input=false a CI-ben, és tofu init -upgrade csak ellenőrzött dependency bump során.

Hiba: a create_before_destroy = true beállítást olyan resource-ra alkalmazzák, amely nem támogatja, például egyedi név-ütközés miatt.
Tünet: az apply már a create fázisban hibát ad, mert a régi objektum még létezik.
Megoldás: a provider dokumentációjának ellenőrzése, name_prefix használata, vagy ha nem támogatott, a -/+ elfogadása tervezett outage ablakban.

46.3.8 Feladatok

F1 – Modul szerződés for_each-szel és validációval
Készíts egy modules/local-file modult, amely egy file_map nevű map(string) inputból local_file erőforrásokat hoz létre for_each segítségével. A modul outputja adja vissza a fájlnevek listáját. A file_map kulcsokra adj egy validation szabályt: csak kisbetű, szám és kötőjel lehet a kulcsban, hossza legfeljebb 20 karakter. Hívd a modult egy envs/lab mappából { "readme" = "hello", "build-log" = "done" } map-pel. Futtasd a tofu validate és tofu plan parancsokat. A planban az erőforrás-címek module.local_file.local_file.file["readme"] és ["build-log"] alakúak legyenek.

F2 – Environment state-határ
Hozz létre két environment mappát: envs/dev és envs/prod. Mindkettő ugyanazt a modules/local-file modult hívja, de eltérő file_map inputtal. Mindkét environmenthez külön backend key tartozzon: dev/terraform.tfstate és prod/terraform.tfstate. Futtass tofu init, tofu plan, tofu apply mindkét mappában. Ellenőrizd tofu state list segítségével, hogy a dev state csak a dev kulcsokat, a prod state csak a prod kulcsokat tartalmazza.

F3 – Replace/destroy felismerés planból
Adott a következő resource a configban: egy aws_instance count = 2-vel és ami = var.ami. Változtasd meg a var.ami értéket egy másik AMI-ra. Futtasd a tofu plan -out=replace.tfplan parancsot. Olvasd ki a planból, hogy a művelet -/+ (destroy then create) vagy +/- (create before destroy). Ha -/+, add hozzá a lifecycle { create_before_destroy = true }-t, és futtass újra a plant. Figyeld meg, hogy a plan jelölése +/--re változott-e; ha a provider/resource nem támogatja, a plan továbbra is -/+ marad, és ezt a provider dokumentációja alapján indokold. Az erőforrás-cím aws_instance.app[0] és [1] marad.

46.3.9 Megoldások

F1 megoldás
A modul a modules/local-file/variables.tf-ben:

variable "file_map" {
  type = map(string)

  validation {
    condition = alltrue([
      for k in keys(var.file_map) : can(regex("^[a-z0-9-]{1,20}$", k))
    ])
    error_message = "file_map kulcs csak kisbetű, szám és kötőjel lehet, legfeljebb 20 karakter."
  }
}

modules/local-file/main.tf:

resource "local_file" "file" {
  for_each = var.file_map
  content  = each.value
  filename = "${path.module}/${each.key}.txt"
}

modules/local-file/outputs.tf:

output "file_names" {
  value = [for k in keys(var.file_map) : "${k}.txt"]
}

envs/lab/main.tf:

module "local_file" {
  source = "../../modules/local-file"

  file_map = {
    "readme"     = "hello"
    "build-log"  = "done"
  }
}

Futtatás: tofu validate és tofu plan. A planban a resource-címek module.local_file.local_file.file["readme"] és module.local_file.local_file.file["build-log"]. Postcondition: a validate hibát ad, ha a kulcsban például _ vagy nagybetű van; a plan két + create műveletet mutat.

F2 megoldás
Mindkét environment saját backend.hcl fájlt használ, például:

# envs/dev/backend.hcl
path = "dev/terraform.tfstate"
# envs/prod/backend.hcl
path = "prod/terraform.tfstate"

A backend.tf mindkét mappában megegyezik, de a terraform init -backend-config=backend.hcl mindig a megfelelő path-tel példányosul. A main.tf ugyanazt a modult hívja, csak a file_map különbözik. A tofu state list a dev mappában a dev kulcsokat, a prod mappában a prod kulcsokat mutatja. Postcondition: a két state teljesen külön van, a dev módosítás nem hat a prodra, és a tofu destroy az adott environmentben csak a saját erőforrásait törli.

F3 megoldás
A plan kimenetét tofu show -json replace.tfplan vagy a szöveges plan alapján elemezzük. A -/+ azt jelenti, hogy a destroy az új létrehozása előtt történik. Ha a resource támogatja, a lifecycle { create_before_destroy = true } hatására a plan +/--re vált. Ha nem támogatott, a plan továbbra is -/+, és a provider dokumentációja adja meg, hogy miért nem lehet a create a destroy előtt. Az ellenőrzés: a planban a resource fejléc must be replaced marad, de a műveleti sorrend jelölés változhat. Postcondition: a tanuló felismeri, hogy a -/+ destroy műveletet jelent, és a +/- jelölés a create-before-destroy szándékát mutatja.

46.3.10 Rövid összefoglaló

A modul input/output szerződés, amely resource ownership és blast radius szerint határol. A for_each kulcsos identitás stabilabb, mint a count index, ezért döntésnél a természetes kulcs az első. A provider- és verzióvadászat a .terraform.lock.hcl commitolásával és a required_version/required_providers blokkokkal determinisztikus. Az environment boundary külön root module és külön state path; a shared dependency explicit output/data source határon át látszódik. A lifecycle.create_before_destroy csak provider által támogatott resource-ra érvényes, és a plan -/+ versus +/- jelölése a rövid outage kockázatát mutatja. A sensitive = true minden olyan outputon szükséges, amely titkot vagy személyes adatot hordoz.
