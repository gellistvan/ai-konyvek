19.5 Mount- és fájlszolgáltatási incidenslabor

19.5.1 Motiváció

A hálózati fájlmount egy több rétegű elosztott állapot: a kliens oldali VFS (virtual filesystem) mount, az NFS-export, az RPC-réteg és a hálózati kapcsolat mind külön meghibásodhat. A tünet gyakran csak annyi, hogy „a fájl nem elérhető”, de a javítás attól függ, hogy a hiányzó device, az exportpolitika, a quota vagy a kapcsolat rétegében van-e a hiba. Ebben a laborban két labVM-en NFS-szolgáltatást építünk, szándékosan hibaforgatókönyveket futtatunk, és rétegenként állítjuk helyre.

19.5.2 Definíció és működés

Mount (csatolás): a Linux VFS egy elérési útvonalat (mountpoint) egy fájlrendszer gyökeréhez köt. A kliens mount -t nfs híváskor az RPC MOUNT eljárással file handle-t kér, majd ezt a VFS mount struktúrájába teszi. Hálózati megszakadásnál ez a mount megmarad, csak az I/O hibásodik.

Export (megosztás): az NFS-szerveren az /etc/exports sor és az exportfs parancs adja ki, melyik könyvtár melyik kliens IP-ről, milyen opciókkal érhető el. A rw/ro, sync, no_root_squash policy a szerver oldalán dől el. A mount kérés permission denied, ha az IP vagy az opció nem illeszkedik.

File handle: a szerver által adott, fájlobjektumra mutató NFS-azonosító. Ha a szerver oldalán az exportot áthelyezik, unmountolják vagy az inode eltűnik, a kliens a régi handle-t használva Stale file handle hibát kap.

Mount propagation: a mount-események láthatósága más mount namespace-ekben. A /proc/self/mountinfo propagation bitjei (shared, slave, private, unbindable) mutatják, hogy egy új mount egy másik namespace-ben is megjelenik-e. Ez fontos konténer és service deployment esetén, mert a gazdagépen létrehozott bind mount nem mindig jut el a service mount namespace-ébe.

A lab topológiája:

Host IP Szerep Mountpoint/Export
labnfs01 192.0.2.10/24 NFS szerver /srv/lab-export
labnfs02 192.0.2.11/24 NFS kliens /mnt/lab-nfs

A labhostokon a felhasználó labops UID 1000; a módosító parancsok sudo jogot igényelnek. Az IP-cím RFC5737 dokumentációs tartomány.

19.5.3 Kidolgozott példa

19.5.3.1 Előfeltétel

Két Ubuntu Server 24.04 LTS VM, ssh hozzáférés, labops felhasználó. A hálózat izolált labsubnet, a szerver és kliens IP-je a fenti táblázat szerint. A lab során használt NFS-verziót a rendszer csomagkezelője adja; a pontos release-t a lab build manifest rögzíti.

19.5.3.2 Szerverkonfiguráció

# labnfs01, user: labops, UID 1000, sudo szükséges
# Előfeltétel: nincs korábbi lab-export; ellenőrzés: sudo exportfs -v

sudo apt-get update
sudo apt-get install -y nfs-kernel-server
sudo mkdir -p /srv/lab-export
sudo chown labops:labops /srv/lab-export

# Lab-only export: sync írás, adott labsubnet, no_root_squash csak izolált környezetben
echo "/srv/lab-export 192.0.2.0/24(rw,sync,no_subtree_check,no_root_squash)" | sudo tee /etc/exports

sudo exportfs -ra
sudo systemctl enable --now nfs-server

Ellenőrzés:

# labnfs01, várt kimenet (illesztratív)
sudo exportfs -v
# /srv/lab-export 192.0.2.0/24(rw,sync,no_subtree_check,no_root_squash)
sudo systemctl is-active nfs-server
# active

Rollback: sudo exportfs -u *:/srv/lab-export, szükség esetén sudo rm -rf /srv/lab-export.

19.5.3.3 Kliens mount

# labnfs02, user: labops, sudo szükséges
# Előfeltétel: NFS szerver aktív, hálózat elérhető; ellenőrzés: ping 192.0.2.10
sudo apt-get update
sudo apt-get install -y nfs-common
sudo mkdir -p /mnt/lab-nfs

# soft + timeout: disconnect esetén a mount ne fagyjon le korlátlanul
sudo mount -t nfs -o rw,soft,timeo=50,retrans=3 192.0.2.10:/srv/lab-export /mnt/lab-nfs

Ellenőrzés és smoke test:

# labnfs02
mount | grep lab-nfs
# 192.0.2.10:/srv/lab-export on /mnt/lab-nfs type nfs4 (rw,relatime,vers=4.2,...)

df -hT /mnt/lab-nfs
# Filesystem                       Type Size Used Avail Use% Mounted on
# 192.0.2.10:/srv/lab-export       nfs4  ...  ...   ...   ...  /mnt/lab-nfs

echo "smoke" | tee /mnt/lab-nfs/smoke.txt
cat /mnt/lab-nfs/smoke.txt
# smoke

Rollback: sudo umount /mnt/lab-nfs.

19.5.3.4 Data integrity és recovery smoke test

A hálózati fájlmount integritását egy checksum-fájllal ellenőrizzük, hogy a read/write path ne sérüljön:

# labnfs02, user: labops
# Előfeltétel: /mnt/lab-nfs mountolt, néhány MiB szabad kapacitás
dd if=/dev/zero of=/mnt/lab-nfs/smoke.bin bs=1M count=4 status=none
sha256sum /mnt/lab-nfs/smoke.bin > /tmp/smoke.sha
cat /tmp/smoke.sha
# <hash>  /mnt/lab-nfs/smoke.bin

# Remount előtt unmount, majd újracsatolás
sudo umount /mnt/lab-nfs
sudo mount -t nfs -o rw,soft,timeo=50,retrans=3 192.0.2.10:/srv/lab-export /mnt/lab-nfs

sha256sum -c /tmp/smoke.sha
# /mnt/lab-nfs/smoke.bin: OK

Postcondition: a smoke.bin olvasható, checksum egyezik, a remount sikeres.

19.5.4 Hibák és ellenpróbák

Az alábbi táblázat tipikus mount- és fájlszolgáltatási hibákat mutat be, a tünetből hipotézisen és adatgyűjtésen át a javításig.

Tünet Hipotetikus ok Adatgyűjtés Egy változtatás Verifikáció
mount.nfs: connection timed out Szerver nem elérhető, vagy firewall blokkolja a 2049/RPC portot ping 192.0.2.10, ss -tn a szerveren Indítsuk el a szervert, vagy engedélyezzük a portot showmount -e 192.0.2.10
mount.nfs: access denied by server Export csak más IP-t enged, vagy az export nincs exportálva sudo exportfs -v, showmount -e Javítsuk a /etc/exports IP-t, exportfs -ra mount -t nfs ... sikeres
Stale file handle Szerveren az export path áthelyezve/unexportálva sudo exportfs -v, ls -ld /srv/lab-export Állítsuk vissza az exportot, kliens umount/mount cat /mnt/lab-nfs/smoke.txt oldható
No space left on device (ENOSPC) Kvóta, vagy a szerver fájlrendszere megtelt df -h kliens és szerver, du -sh Töröljünk fölösleges fájlt, vagy növeljük kapacitást df -h /mnt/lab-nfs és új fájl létrehozása
NFS server not responding Hálózati szakadás, vagy a szerver NFS service leállt systemctl status nfs-server, ping, ip -br link Hozzuk vissza a hálózati linket, vagy indítsuk a service-t systemctl is-active nfs-server, mount | grep lab-nfs

A mount propagation megfigyelése nem hiba, hanem state-ellenőrzés. A szerveren bind mountot hozunk létre, és megnézzük, milyen propagation bitet kap:

# labnfs01, user: labops, sudo szükséges
sudo mkdir -p /tmp/lab-bind
sudo mount --bind /srv/lab-export /tmp/lab-bind

cat /proc/self/mountinfo | grep lab-bind
# ... /tmp/lab-bind ... shared:105 ...

A shared:X bit azt jelenti, hogy a mount-események a mount namespace-ek között terjednek. A kliens NFS mount általában private, tehát a kliensen egy unshare -m namespace-be nem propagálódik be a gazdagép mountja. Ez akkor válik relevánssá, ha konténerből kell látni egy gazdagép oldali NFS mountot.

19.5.5 Runbook és access audit

A lab runbook minimális lépései:

  1. Állapotfelvétel: df -hT, mount -t nfs, sudo exportfs -v.
  2. Szerveroldali ellenőrzés: sudo systemctl status nfs-server, showmount -e 192.0.2.10.
  3. Hálózati réteg: ping 192.0.2.10, ss -tn | grep ':2049'.
  4. Stale handle esetén: sudo umount /mnt/lab-nfs, sudo mount ....
  5. Kapacitáshiba esetén: df -h a szerveren, du -sh /srv/lab-export.
  6. Változtatás: csak egy rétegben módosítunk, majd újra ellenőrizzük a mount és a checksum állapotot.

Access audit a szerveren:

# labnfs01, user: labops, sudo szükséges
showmount -e localhost
# Export list for localhost:
# /srv/lab-export 192.0.2.0/24

sudo cat /proc/net/rpc/auth.unix.ip
# IP address, uid, flavor és export adatok (illusztratív, NFS-verziófüggő)

journalctl -u nfs-server -n 50 --no-pager
# RPC és export naplóbejegyzések

Az audit célja, hogy megállapítsuk: az export csak a labsubnetre vonatkozik, és a kliens hozzáférései a szerver naplójában látszanak. Az NFS naplózása korlátozottabb, mint egy fájlrendszer audit log, ezért az access audit gyakran a showmount és az RPC statisztikák kombinációja.

19.5.6 Feladatok

19.5.6.1 1. Magyarázó: réteghiba-osztályozás

Adott három hibaüzenet:
a) mount.nfs: access denied by server
b) mount.nfs: connection timed out
c) Stale file handle

Melyik rétegben keresnéd a hibát, és milyen első parancsot futtatnál? Indokold a sorrendet.

19.5.6.2 2. Adminisztrációs/konfigurációs: read-only export

Hozz létre egy második exportot /srv/lab-ro néven, ro opcióval. Mountold a kliensen a /mnt/lab-ro mountpointra. Próbálj fájlt létrehozni, dokumentáld a hibát, majd ellenőrizd, hogy olvasni tudsz.

19.5.6.3 3. Diagnosztikai/failure/recovery: kapacitáskorlátos export

A szerveren hozz létre egy 10 MiB méretű tmpfs-et /srv/lab-quota néven, exportáld NFS-en. A kliensről másolj egy 20 MiB-os fájlt (dd-vel) a mountolt könyvtárba. Kapj ENOSPC-ot, diagnosztizáld a df és du parancsokkal, töröld a fölösleges fájlt, majd ellenőrizd a helyreállítást.

19.5.7 Megoldások

19.5.7.1 1. Réteghiba-osztályozás

  1. access denied az export-policy réteg hibája: a szerver nem engedélyezi a klienst. Első parancs: sudo exportfs -v a szerveren, és showmount -e 192.0.2.10 a kliensről.
  2. connection timed out a hálózati vagy RPC réteg hibája: a csomag nem éri el a szervert, vagy a port zárva. Első parancs: ping 192.0.2.10, majd ss -tn | grep ':2049' a szerveren.
  3. Stale file handle az NFS fájl-azonosító réteg hibája: a mount megtörtént, de a szerver oldali objektum eltűnt vagy az export megváltozott. Első parancs: sudo exportfs -v és ls -ld /srv/lab-export a szerveren, majd a kliensen umount/mount.

Indoklás: a mount folyamata fizikai/hálózati, majd export-policy, majd mount utáni file handle szakasz. A hibás üzenet megmutatja, melyik szakasz nem teljesült.

Postcondition: mindhárom esetben az első parancs pontosítja a réteget anélkül, hogy több dolgot módosítanánk egyszerre.

19.5.7.2 2. Read-only export

# labnfs01, user: labops, sudo szükséges
sudo mkdir -p /srv/lab-ro
echo "/srv/lab-ro 192.0.2.0/24(ro,sync,no_subtree_check)" | sudo tee -a /etc/exports
sudo exportfs -ra

# labnfs02, user: labops, sudo szükséges
sudo mkdir -p /mnt/lab-ro
sudo mount -t nfs -o ro,soft,timeo=50,retrans=3 192.0.2.10:/srv/lab-ro /mnt/lab-ro

# Írási kísérlet
echo "write" | tee /mnt/lab-ro/write.txt
# tee: /mnt/lab-ro/write.txt: Read-only file system

A hiba a VFS/Mount rétegben keletkezik: a mount ro, így a write syscall EROFS hibát ad. Az olvasás azonban működik, ha előzőleg a szerveren létrehozunk egy fájlt.

Ellenőrzés: mount | grep lab-ro mutatja (ro,...), a echo "read" > /srv/lab-ro/read.txt a szerveren, majd cat /mnt/lab-ro/read.txt a kliensen sikeres.

Postcondition: a /mnt/lab-ro csak olvasható, az írási kísérlet elakadás nélkül hibát ad, cleanup: sudo umount /mnt/lab-ro és sudo rm -rf /srv/lab-ro.

19.5.7.3 3. Kapacitáskorlátos export

# labnfs01, user: labops, sudo szükséges
sudo mkdir -p /srv/lab-quota
sudo mount -t tmpfs -o size=10M tmpfs /srv/lab-quota
echo "/srv/lab-quota 192.0.2.0/24(rw,sync,no_subtree_check,no_root_squash)" | sudo tee -a /etc/exports
sudo exportfs -ra

# labnfs02, user: labops, sudo szükséges
sudo mkdir -p /mnt/lab-quota
sudo mount -t nfs -o rw,soft,timeo=50,retrans=3 192.0.2.10:/srv/lab-quota /mnt/lab-quota

dd if=/dev/zero of=/mnt/lab-quota/big.bin bs=1M count=20 status=none
# dd: error writing '/mnt/lab-quota/big.bin': No space left on device

Diagnózis: df -h /mnt/lab-quota 10 MiB teljes méretet mutat; du -sh /mnt/lab-quota megmutatja, hogy a big.bin a kapacitást kitöltötte. A tmpfs méreténél fogva ENOSPC-t ad, ami a NFS-en keresztül is megjelenik.

Helyreállítás: töröljük a fölösleges fájlt, majd ellenőrizzük:

# labnfs02
rm /mnt/lab-quota/big.bin
df -h /mnt/lab-quota
echo "smoke" | tee /mnt/lab-quota/recovery.txt
cat /mnt/lab-quota/recovery.txt
# smoke

Postcondition: a mountolt tmpfs újra írható, a recovery.txt olvasható, a kapacitáskorlát nem sérült. Cleanup: rm /mnt/lab-quota/recovery.txt, sudo umount /mnt/lab-quota, szerveren sudo umount /srv/lab-quota, export törlés /etc/exports-ból, sudo exportfs -ra.

19.5.8 Rövid összefoglaló

A hálózati fájlmount incidensei rétegenként diagnosztizálhatók: a mount hívás szakaszában hálózati és export-policy hibákat, a mount után file handle és kapacitáshibákat látunk. A lab NFS-szervert és klienst állított fel, read-write és read-only exporttal, kapacitáskorlátos tmpfs fixture-rel, valamint mount propagation megfigyeléssel. A recovery a runbook szerint egy rétegben változtat, majd checksummal vagy smoke teszttel verifikál. Az access audit a showmount, exportfs és RPC statisztikák kombinációján alapul.

Továbbhasznált definíciók:
- Mount: egy elérési útvonal hozzákötése egy fájlrendszer gyökeréhez a VFS-ben.
- Export: NFS-szerveren egy könyvtár és IP-policy megosztása.
- File handle: a szerver által adott, fájlobjektumra mutató NFS-azonosító; stale, ha az objektum eltűnt.
