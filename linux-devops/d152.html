31.2 nftables policy és persistens firewall

31.2.1 Miért működtetési szerződés a tűzfalszabály?

Egy tűzfalváltozás akkor sikeres, ha nemcsak a tiltás működik, hanem az adminisztráció, az alkalmazásforgalom és a szükséges hálózati vezérlőforgalom is. A meglévő SSH-kapcsolat túlélése önmagában nem bizonyíték: a kapcsolatkövetés engedheti a korábban létrejött kapcsolatot, miközben minden új bejelentkezés elakad.

Az nftables szabályrendszer (ruleset) egy hálózati névtér kernelben tárolt tábláinak, láncainak, szabályainak és kapcsolódó objektumainak együttese. A lemezen tárolt konfiguráció ettől külön állapot. A cél három állapot összehangolása:

Állapot Ebben a laborban
Kívánt, desired Meghatározott SSH- és HTTP-adatutak engedélyezése
Megfigyelt, observed Kernelben betöltött szabályok, számlálók, kapcsolati próbák
Konfigurációforrás és tárolt állapot Ellenőrzött jelölt fájl, majd rendszerindításkor betöltött konfiguráció

A hookok és a kapcsolatkövetés alapjait a Netfilter hook, conntrack és állapottartás, a biztonságos adminisztráció előfeltételeit az OpenSSH, host trust és admin access tárgyalta.

31.2.2 Táblák, láncok és kiértékelés

A tábla (table) névvel rendelkező objektumcsoport. Családja határozza meg a feldolgozott forgalom körét: az ip IPv4-, az ip6 IPv6-, az inet mindkét IP-protokollcsaládhoz használható. Az inet nem jelent automatikus IPv4–IPv6-átjárást.

Az alaplánc (base chain) hookhoz csatlakozik. Négy fontos tulajdonsága:

  • type filter: csomagszűrésre szolgál;
  • hook input, output vagy forward: helyi célú, helyben keletkező vagy továbbított csomagokat vizsgál;
  • priority filter: itt a numerikus 0 prioritás neve;
  • policy drop: a lánc végéig döntés nélkül eljutó csomagot eldobja.

A kisebb prioritásérték korábbi feldolgozást jelent. Azonos hookon és prioritáson több alaplánc sorrendjére ne építs. Egy lánc accept döntése nem garantálja, hogy egy későbbi alaplánc is engedélyezni fogja a csomagot.

A közönséges lánc (regular chain) nem csatlakozik hookhoz: például jump döntéssel érhető el. A szabályok sorrendben futnak; egy termináló döntés, például accept vagy drop, lezárja az adott feldolgozási ágat.

A halmazok (sets) azonos típusú értékeket tárolnak. A leképezések (maps) kulcshoz értéket rendelnek; a döntési leképezés (verdict map) például TCP-porthoz láncugrást rendelhet. A counter az adott szabály adott pontjáig eljutott csomagokat és bájtokat számolja, nem a sikeres alkalmazáskéréseket.

31.2.3 Laborbemenet és tulajdonosi határ

Profil: Ubuntu Server 24.04 LTS amd64. Az alábbiak előkészített, izolált laborbemenetek, nem egy ismeretlen gépre alkalmazandó címbeállítások.

Gép, interfész IPv4 IPv6 Kapcsolat
lab-admin, enp1s0 10.203.0.2/24 fd42:203:1::2/64 lab-mgmt virtuális switch
lab-fw, enp1s0 10.203.0.1/24 fd42:203:1::1/64 lab-mgmt
lab-fw, enp2s0 10.203.1.1/24 fd42:203:2::1/64 lab-back virtuális switch
lab-app, enp1s0 10.203.1.2/24 fd42:203:2::2/64 lab-back

A két switchnek nincs külső uplinkje. A címeket a hypervisor, a host és az esetleges VPN címterével ütközésre ellenőrizni kell.

További előfeltételek:

  • A lab-admin backendhálózati útvonalai a lab-fw managementcímeire mutatnak; a lab-app managementhálózati visszaútjai a lab-fw backendcímeire.
  • A lab-fw gépen az IPv4- és IPv6-forwarding értéke 1; a címzés statikus, nincs DHCP- vagy DNS-függőség.
  • Mindhárom gépen létezik a lab-operator fiók, UID 1000. A lab-fw gépen rendelkezik sudo hozzáféréssel.
  • Az SSH a lab-fw és lab-app gépen mindkét IP-családon működik. A hostkulcsok ellenőrzöttek.
  • Telepített eszközök: nft, ip, ssh, curl, nc, Python 3.
  • A lab-fw hypervisorkonzolja nyitva marad.

A lab-fw gépen lépj root shellbe; az alábbi, másként nem jelölt módosítások célpontja ez a gép, UID 0:

# Target: lab-fw; account: lab-operator, majd root
sudo -i
hostname
id
uname -r
nft --version
dpkg-query -W nftables systemd iproute2
ip -br address
ip -4 route
ip -6 route
sysctl net.ipv4.ip_forward net.ipv6.conf.all.forwarding
nft -a list ruleset
systemctl is-enabled nftables ufw firewalld
systemctl is-active nftables ufw firewalld

A verziókat rögzítsd a laborjegyzőkönyvben. A hiányzó szolgáltatás vagy az inactive állapot nem feltétlenül hibajel.

Tulajdonosi kapu: ebben a profilban a kezdeti nftables-szabályrendszer üres; nincs aktív vagy rendszerindításkor más szabályokat betöltő tűzfalkonfigurátor. Eltérés esetén állj meg, és állítsd helyre az izolált baseline-t.

Az iptables -V kimenetében az nf_tables backend nftables-kompatibilitási réteget jelent. Az iptables-legacy ezzel szemben külön szabályokat kezelhet, amelyek nem láthatók az nft list ruleset kimenetében. A telepített backendeket és szabályaikat is ellenőrizni kell. Az UFW, firewalld, konténerplatform és kézi nft konfiguráció nem lehet ugyanazon policy gazdája megállapodás nélkül. Ne ezek globális kikapcsolásával „javíts” egy termelési problémát.

31.2.4 Kidolgozott szabályrendszer

A kívánt adatút:

Forrás → cél Hook a lab-fw gépen Döntés
lab-admin → lab-fw, TCP/22 input Engedélyezett
lab-app → lab-fw, új TCP/22 input Tiltott
lab-fw → lab-app, TCP/8080 output Engedélyezett
lab-admin → lab-app, TCP/8080 forward Engedélyezett
lab-fw vagy lab-admin → lab-app, új TCP/22 output vagy forward Tiltott

Hozd létre a munkakönyvtárat és a kezdeti, üres saját táblát. Ezek a nevek még nem létezhetnek:

# Target: lab-fw, UID 0
install -d -m 0700 /root/lab-fw
nft add table inet lab-filter

{
    printf 'add table inet lab-filter\ndelete table inet lab-filter\n'
    nft list table inet lab-filter
} > /root/lab-fw/lab-before.nft
chmod 0600 /root/lab-fw/lab-before.nft

A mentés most az izolált labor eredeti, szűrés nélküli állapotát képviseli; nem termelési biztonsági baseline.

Mentsd az alábbi fájlt /root/lab-fw/lab-candidate.nft néven:

add table inet lab-filter
delete table inet lab-filter

table inet lab-filter {
    set lab-mgmt4 {
        type ipv4_addr
        elements = { 10.203.0.2 }
    }

    set lab-mgmt6 {
        type ipv6_addr
        elements = { fd42:203:1::2 }
    }

    chain lab-ssh {
        counter accept
    }

    map lab-tcp-in {
        type inet_service : verdict
        elements = { 22 : jump lab-ssh }
    }

    chain lab-input {
        type filter hook input priority filter; policy drop;

        iifname "lo" counter accept
        ct state invalid counter drop
        ct state established,related counter accept
        meta l4proto { icmp, ipv6-icmp } counter accept

        iifname "enp1s0" ip saddr @lab-mgmt4 tcp dport vmap @lab-tcp-in
        iifname "enp1s0" ip6 saddr @lab-mgmt6 tcp dport vmap @lab-tcp-in

        counter drop
    }

    chain lab-output {
        type filter hook output priority filter; policy drop;

        oifname "lo" counter accept
        ct state invalid counter drop
        ct state established,related counter accept
        meta l4proto { icmp, ipv6-icmp } counter accept

        oifname "enp2s0" ip daddr 10.203.1.2 tcp dport 8080 counter accept
        oifname "enp2s0" ip6 daddr fd42:203:2::2 tcp dport 8080 counter accept

        counter drop
    }

    chain lab-forward {
        type filter hook forward priority filter; policy drop;

        ct state invalid counter drop
        ct state established,related counter accept

        iifname "enp1s0" oifname "enp2s0" ip saddr @lab-mgmt4 ip daddr 10.203.1.2 tcp dport 8080 counter accept
        iifname "enp1s0" oifname "enp2s0" ip6 saddr @lab-mgmt6 ip6 daddr fd42:203:2::2 tcp dport 8080 counter accept

        counter drop
    }
}

Az első add table létező tábla esetén is megengedett; a törlés és újralétrehozás ugyanazon tranzakció része. Nincs köztes, csomagok számára látható üres szabályrendszer. Más táblát nem érintünk, és nem használunk globális flush ruleset műveletet.

A labor szándékosan minden helyi ICMP/ICMPv6-forgalmat enged. Így nem tiltja el véletlenül az IPv6 szomszédfelderítést (Neighbor Discovery, ND), a Packet Too Big üzeneteket és más hálózati hibajelzéseket. Ez nem kész internetperem-policy: ott interfész, ICMP-típus, routerhirdetési szerep és szükség esetén sebességkorlát szerint kell szűkíteni.

A meta l4proto IPv6-kiterjesztésfejlécek mellett is a szállítási protokoll vizsgálatára való; a közvetlen ip6 nexthdr vizsgálat nem általános helyettesítője. A továbbított, kapcsolatkövetéssel összerendelhető ICMP-hibákat a related szabály engedi; a továbbított pinget ez a policy nem engedélyezi.

31.2.5 Ellenőrzés, atomi betöltés és időzített visszaállítás

Az nft -c ellenőrzi a feldolgozhatóságot és a kernel általi elfogadhatóságot, de nem bizonyít elérhetőséget:

# Target: lab-fw, UID 0
nft -c -f /root/lab-fw/lab-before.nft
nft -c -f /root/lab-fw/lab-candidate.nft

Várt eredmény: nulla kilépési kód, rendszerint üres kimenet. Nem történt tényleges futtatás ebben a tananyagban.

Betöltés előtt élesíts helyi, SSH-tól független visszaállítást:

# Target: lab-fw, UID 0
systemd-run --unit=lab-fw-rollback --on-active=180s \
    /usr/sbin/nft -f /root/lab-fw/lab-before.nft

systemctl list-timers lab-fw-rollback.timer
nft -f /root/lab-fw/lab-candidate.nft
nft -a list table inet lab-filter

A 180 másodperc monotonic időzítőhöz kötött időtartam, nem wall-clock időpont. Ha a tesztek nem férnek bele, a visszaállítás után kezdj új, megfelelő időkeretű ciklust.

Az nft -f betöltés atomi a szabályváltozásokra: hibás tranzakció nem hagy félig alkalmazott szabálysort. Nem állítja vissza a route-okat, nem írja át a lemezen tárolt konfigurációt, és nem üríti a conntrack állapotát.

31.2.6 Input-, output- és forward-próbák

A lab-app gépen, UID 1000 alatt készíts tesztadatot:

# Target: lab-app; account: lab-operator, UID 1000
mkdir "$HOME/lab-http"
printf 'lab-ok\n' > "$HOME/lab-http/index.html"

Két külön terminálban indíts egy-egy előtérben futó szervert:

# Target: lab-app; UID 1000; két külön terminál
python3 -m http.server 8080 --bind 10.203.1.2 \
    --directory "$HOME/lab-http"

python3 -m http.server 8080 --bind fd42:203:2::2 \
    --directory "$HOME/lab-http"

Ezeket célszerű már a policy betöltése előtt elindítani. Baseline-ként bizonyítsd a HTTP és a később tiltandó TCP/22 elérhetőségét is.

A lab-admin gépről:

# Target: lab-admin; UID 1000
# Input: új SSH-kapcsolatok, kapcsolatmegosztás nélkül
ssh -4 -o ControlPath=none -o ConnectTimeout=3 \
    lab-operator@10.203.0.1 true
ssh -6 -o ControlPath=none -o ConnectTimeout=3 \
    lab-operator@fd42:203:1::1 true

# Forward: várt válasz mindkétszer lab-ok
curl --noproxy '*' --max-time 3 http://10.203.1.2:8080/
curl --noproxy '*' --max-time 3 'http://[fd42:203:2::2]:8080/'

# Forward: várt sikertelenség
nc -4 -vz -w 2 10.203.1.2 22
nc -6 -vz -w 2 fd42:203:2::2 22

A lab-fw gépen ugyanezek a HTTP- és backend-SSH-próbák az output láncot vizsgálják:

# Target: lab-fw; UID 0
curl --noproxy '*' --max-time 3 http://10.203.1.2:8080/
curl --noproxy '*' --max-time 3 'http://[fd42:203:2::2]:8080/'
nc -4 -vz -w 2 10.203.1.2 22
nc -6 -vz -w 2 fd42:203:2::2 22

Végül tiltott új bejelentkezés a lab-app gépről:

# Target: lab-app; UID 1000
nc -4 -vz -w 2 10.203.1.1 22
nc -6 -vz -w 2 fd42:203:2::1 22

Elfogadási feltétel: az SSH és HTTP engedélyezett próbái sikeresek; a tiltott próbák sikertelenek, és a megfelelő lánc záró counter drop számlálója nő. A timeout önmagában nem bizonyít tűzfalhibát: ugyanezt okozhatja hiányzó route vagy visszaút is.

Sikeres tesztek után:

# Target: lab-fw, UID 0
systemctl stop lab-fw-rollback.timer
systemctl show lab-fw-rollback.service \
    -p ExecMainStartTimestampMonotonic
nft -a list table inet lab-filter

A rollback szolgáltatás indítási időbélyegének még 0 értékűnek kell lennie. Ha már lefutott, ne persistálj tévesen visszaállított állapotot: ismételd meg a változtatási ciklust.

31.2.7 Persistens betöltés egyetlen ownerrel

Az ellenőrzött fájlt tárold el:

# Target: lab-fw, UID 0
install -d -m 0700 /etc/lab-firewall
install -m 0600 /root/lab-fw/lab-candidate.nft \
    /etc/lab-firewall/lab-policy.nft

Hozd létre a /etc/systemd/system/lab-firewall.service fájlt. Nem a disztribúció globális nftables-szolgáltatását használjuk, hanem kizárólag a saját táblánkat kezelő unitot:

[Unit]
Description=Lab-owned nftables policy
DefaultDependencies=no
After=local-fs.target
Wants=network-pre.target
Before=network-pre.target shutdown.target
Conflicts=shutdown.target

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStartPre=/usr/sbin/nft -c -f /etc/lab-firewall/lab-policy.nft
ExecStart=/usr/sbin/nft -f /etc/lab-firewall/lab-policy.nft
ExecReload=/usr/sbin/nft -f /etc/lab-firewall/lab-policy.nft

[Install]
WantedBy=multi-user.target

Szándékosan nincs szabálytörlő ExecStop: a szolgáltatás leállítása nem nyitja meg automatikusan a gépet.

# Target: lab-fw, UID 0
systemctl daemon-reload
systemctl enable lab-firewall.service
nft -c -f /etc/lab-firewall/lab-policy.nft

Tervezett reboot után, konzolról ellenőrizd a unit állapotát, a szabályokat és ismételd meg a kapcsolati mátrixot. A Before= sorrendet jelent, nem önmagában fail-closed indítási garanciát: egy hibás szolgáltatás esetén a hálózat továbbindulhat. Szigorú környezetben külön, tesztelt indítási függőségi szerződés szükséges.

Rollback persistálás után: konzolról tiltsd le a saját unitot, majd töltsd vissza a mentést. Későbbi változtatásnál a korábbi lemezkonfigurációt is vissza kell állítani.

# Target: lab-fw, UID 0
systemctl disable --now lab-firewall.service
nft -f /root/lab-fw/lab-before.nft

Cleanup: a jelen labor üres kezdeti állapota esetén törölhető a lab-filter tábla, a két saját konfigurációfájl és az üres /etc/lab-firewall könyvtár; utána systemctl daemon-reload szükséges. A HTTP-szervereket Ctrl+C állítja le. Csak a saját lab-http/index.html fájlt és üres könyvtárát távolítsd el. A jegyzőkönyvet takarítás előtt őrizd meg.

31.2.8 Tipikus hibák és ellenpróbák

  • Régi SSH működik, új nem: valószínűleg az established szabály elfedi az új kapcsolatok hibáját. Vizsgáld a managementhalmazt és az új kapcsolat számlálóját.
  • IPv4 jó, IPv6 hibás: külön vizsgáld az IPv6 route-ot, neighbor állapotot és szabályt; ne tiltsd le globálisan az IPv6-ot.
  • HTTP működik a tűzfalról, kliensről nem: az output sikeréből nem következik a forward sikere. Ellenőrizd a forwardingot és a visszautat.
  • Reboot után más policy él: keresd a második ownert, a rossz fájlútvonalat vagy a sikertelen unitot.

Mindig: tünet → hipotézis → célzott adatgyűjtés → egy változtatás → ugyanazon próba megismétlése.

31.2.9 Feladatok

  1. Miért nem bizonyítja a meglévő SSH-kapcsolat és egy sikeres helyi HTTP-kérés a teljes policy helyességét?
  2. Tedd persistenssé a szabályrendszert, majd reboot után bizonyítsd mindhárom lánc működését mindkét IP-családon.
  3. Időzített rollback mellett töröld az IPv4 managementcímet a futó halmazból. Figyeld meg a meglévő SSH-t, az új IPv4 SSH-t és az IPv6 SSH-t, majd bizonyítsd a helyreállást.

31.2.10 Megoldások

  1. A meglévő SSH-t conntrack engedheti, a helyi HTTP pedig csak az output utat vizsgálja. Postcondition: a jegyzőkönyv külön új input, output és forward próbákat tartalmaz.

  2. Az ellenőrzött fájlt telepítsd, engedélyezd a saját unitot, majd konzol mellett indíts újra. Vizsgáld a systemctl status lab-firewall.service és az nft list table inet lab-filter kimenetét. Postcondition: reboot után a teljes pozitív és negatív tesztmátrix változatlanul teljesül.

  3. A már bevált persistens fájlt használd helyreállítási forrásnak:

    # Target: lab-fw, UID 0; csak sikeres 2. feladat után
systemd-run --unit=lab-fw-drill-rollback --on-active=60s \
    /usr/sbin/nft -f /etc/lab-firewall/lab-policy.nft

nft delete element inet lab-filter lab-mgmt4 '{ 10.203.0.2 }'

    Az új IPv4 SSH várhatóan elakad; a meglévő kapcsolat és az IPv6 SSH működhet. A hiba kizárólag runtime-változás, nem kerül a lemezre. Postcondition: a timer lefutása után a halmaz ismét tartalmazza a címet, és egy új IPv4 SSH-kapcsolat sikeres.

31.2.11 Rövid összefoglaló

A működtethető tűzfal nem pusztán szabálylista: ismert tulajdonos, ellenőrzött adatút, visszaállítási terv és tartós konfiguráció tartozik hozzá. Az nftables atomi betöltése megakadályozza a részleges szabályalkalmazást, de nem bizonyítja a kapcsolatok helyességét. Ehhez új kapcsolatokat, pozitív és negatív próbákat, valamint számlálóváltozást kell vizsgálni IPv4-en és IPv6-on. A meglévő SSH-kapcsolat félrevezető lehet. Távoli változtatás előtt helyi időzített rollback és független konzol szükséges. A rendszerindításkor betöltött fájl külön állapot, ezért a reboot utáni ellenőrzés sem hagyható el.

  • Alaplánc: hookhoz kapcsolt, prioritással és alapértelmezett döntéssel rendelkező lánc.
  • Verdict map: kulcsértékhez csomagfeldolgozási döntést rendelő leképezés.
  • Atomi betöltés: a szabályváltozások együttes elfogadása vagy elutasítása.
