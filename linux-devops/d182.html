37.2 OCI image, digest, tag és multiarch

37.2.1 Motiváció

Szenior C++ fejlesztőként a natív build már kézben van, de a konténerkép elosztása új identitásproblémát hoz: a latest tag és a verziószám nevek kényelmesek, ám mutálhatók. Ha a CI buildel egy app:1.0 image-et és később valaki újra kiadja ugyanezt a taget, a futó deployment már nem ugyanazt az artifactot kapja. Másik gyakori tünet az exec format error, amikor x86-64 gépen épített image-et ARM64 szerveren próbálunk futtatni. Az OCI image modell pontosan arra való, hogy a névtől, tartalomtól és platformtól függő tulajdonságokat expliciten szétválassza.

37.2.2 Definíció és működés

Az OCI image (Open Container Initiative) egy szabványos artefactum, amely három fő részből áll:

  • Config blob: JSON objektum, amely a futtató környezet metaadatait írja le: beállítandó környezeti változók, a belépési pont, a parancs, a munkakönyvtár, a felhasználó, az egészségügyi vizsgálat, a platform és a használt parancs. Tartalma nem a fájlrendszer, hanem a futtatási szerződés.
  • Layer blobok: egymásra rétegzett, tömörített tar archívumok. A legfelső rétegben a saját változás van, az alsó rétegek a bázisimage-ből származnak. A rétegek tartalom-címezhetőek, így az azonos layer egyszer tárolódik és azonosítója stabil.
  • Manifest: JSON dokumentum, amely digeste segítségével hivatkozik a config blobra és a layer blobok rendezett listájára. A manifest maga is tartalom-címezhető.

A content digest (tartalom-alapú kivonat) a blob bájtjaira számított kriptográfiai hash, általában SHA-256, például sha256:.... Az OCI distribution spec szerint a manifest digest a manifest JSON kanonikus szerializálásának hash-e. Ha a manifestben egyetlen bájt megváltozik, a digest is megváltozik, ezért a digest immutable azonosító. A tag ezzel szemben ember által olvasható mutató, mint a Git branch: a v1, latest, dev nevek bármikor átirányíthatók más digestre. A deploymenthez ezért digestet, ne taget rögzítsünk.

A platform és az architektúra az OCI image configban és manifestben szerepel. A platform descriptor három mezőből áll: architecture (például amd64 vagy arm64), os (például linux) és opcionálisan variant, os.version. Az OCI amd64 az x86-64 hardver, az arm64 az AArch64 hardver szabványos megnevezése. Ugyanaz a forráskód két különböző binárist adhat: az x86-64 ELF e_machine mezője EM_X86_64, a rendszerhívás belépés syscall utasítással történik; az AArch64 ELF EM_AARCH64, a belépés svc. A bináris ABI-ja eltérő rendszerhívás-számokat és regiszterkonvenciókat használ. A kernel execve rendszerhíváskor ellenőrzi az ELF típusát, és ismeretlen vagy nem futtatható architektúra esetén ENOEXEC hibával utasítja el.

Amikor egy registryben egy tag alatt több platformra is elérhető image van, a top-level objektum nem közvetlen manifest, hanem image index (régebbi szóhasználattal manifest list). Az index JSON tartalmazza a platform-deskriptorok listáját, mindegyik a saját manifest digestre mutat. A kliensek így a saját platformjuknak megfelelő manifestet választják ki.

A build módok közötti különbség a platform-előállítás sebességében és kockázatában van:

  • Native build: ugyanazon az architektúrán fordítunk, mint amin futni fog az image. A leggyorsabb és leghitelesebb. Hátránya, hogy minden célplatformra külön build gépre vagy CI runnerre van szükség.
  • Cross build: erős keresztfordítót (cross-compiler) használunk, például x86-64 gépen ARM64 binárist állítunk elő. A folyamat gyors, mert nincs emuláció, de a build függőségeknek és a CMake/test futtatásnak elérhetőnek kell lennie a célplatformra; a RUN lépésekben lévő teszteket nem lehet közvetlenül futtatni x86-64 hoston.
  • Emulated build: a Buildx QEMU user-mode emulációval futtatja a célplatform binárisait. Ez lehetővé teszi a teljes Dockerfile végrehajtását, de lényegesen lassabb, és nem helyettesíti a natív tesztelést. Például ARM64 build x86-64 CI-n QEMU-val hosszú percekig tarthat, és a teljesítményproblémák elfedhetők.

A rootfs a layer-ekből összeállított virtuális fájlrendszer. Az Entrypoint és a Cmd határozza meg, hogy a konténerindítás mit futtat. Exec formában JSON tömböt használunk: ENTRYPOINT ["/app/hello"]; shell formában a string a shellen keresztül értelmeződik: ENTRYPOINT /app/hello. A config metaadatai közé tartoznak még az Env, WorkingDir, User, Labels, ExposedPorts, StopSignal. Mindegyik a futtatási szerződés része, nem a fájlrendszer tartalma.

37.2.3 Kidolgozott példa

A példa célja egy minimális statikus C++ image elkészítése x86-64-re, majd a tag és digest kapcsolatának megfigyelése. A target a labvm1 nevű Ubuntu Server 24.04 LTS laborhost, a futtató UID 1000 (labuser). Előfeltétel: a podman csomag telepítve van, és a munkakönyvtár a ~/lab-oci-hello.

ssh labuser@labvm1
mkdir -p ~/lab-oci-hello && cd ~/lab-oci-hello
cat > hello.cpp <<'EOF'
#include <iostream>
int main() {
    std::cout << "lab-hello\n";
    return 0;
}
EOF

A Containerfile két fázisú: az első gcc image-ben lefordít egy statikus binárist, a második scratch bázisra másolja. A scratch üres image, nincs libc, ezért a statikus linkelés fontos; ellenkező esetben a futás no such file or directory hibát ad.

FROM gcc:13-bookworm AS build
WORKDIR /src
COPY hello.cpp .
RUN g++ -static -O2 -o /hello hello.cpp

FROM scratch
COPY --from=build /hello /hello
ENTRYPOINT ["/hello"]

Build és ellenőrzés:

cd ~/lab-oci-hello
podman build --platform linux/amd64 -t localhost/lab-hello:latest -f Containerfile .
podman image inspect --format '{{.Id}}' localhost/lab-hello:latest
podman image inspect --format '{{.Digest}}' localhost/lab-hello:latest

A várt kimenetben az Id gyakran a config blob digestje, a Digest mező a manifest digestje; pontos formátum a Podman verziójától függ, ezért ellenőrizni kell a helyi podman image inspect --help-et. A fontos szabály: a manifest digest kell a deployment rögzítéséhez.

A tag mutabilitásának demonstrálása:

podman tag localhost/lab-hello:latest localhost/lab-hello:v2
podman image inspect --format '{{.Digest}}' localhost/lab-hello:latest
podman image inspect --format '{{.Digest}}' localhost/lab-hello:v2

A két parancs ugyanazt a digestet írja ki, mert a v2 tag ugyanarra a manifestre mutat. Ha később újra buildelünk localhost/lab-hello:v2 néven, a digest megváltozik, de a korábbi digest alapján hivatkozott image változatlan marad.

Multiarch index létrehozása hipotetikus, nem ellenőrzött labregistryvel. Az alábbi parancs csak illusztratív; a labregistry.example.test cím a példához használt, nem hivatkozott éles registry, a hitelesítést és storage-ot a laborhoz külön kell beállítani.

docker buildx create --name lab-builder --use
docker buildx build --platform linux/amd64,linux/arm64 \
  -t labregistry.example.test:5000/lab-hello:v1 --push .
docker buildx imagetools inspect labregistry.example.test:5000/lab-hello:v1

A várt kimenetben az index manifest listát mutat két platformmal: linux/amd64 és linux/arm64. Az Image index nem egyetlen futtatható image, hanem az elérhető platformok leírója. A deployment oldalon a runtime kiválasztja a host architektúrájának megfelelő manifestet; ha a registryben nincs meg a host platformja, az exec format error vagy no matching manifest hiba jelenik meg.

Rollback: a létrehozott image-ek törlése a labor névteréből:

podman rmi localhost/lab-hello:latest localhost/lab-hello:v2
podman images --filter reference='localhost/lab-hello*'

37.2.4 Hibák és ellenpróbák

Tünet: standard_init_linux.go:... exec format error ARM64 hoston, miközben az image x86-64-en jól fut. Hipotézis: a deployment rossz platformot hív meg, vagy az indexben nincs ARM64 manifest. Adatgyűjtés: docker buildx imagetools inspect <image> vagy skopeo inspect --raw <image> mutatja a platform listát. Ha csak linux/amd64 van, a hiba forrása platformhiány, nem az alkalmazás. Javítás: multiarch build, vagy a célplatformra megfelelő digest kiválasztása. Ellenőrzés: futtatás a célhoston.

Tünet: deploymentben app:latest tag szerepel, és a frissítés után nem reprodukálható viselkedés. Hipotézis: a tag mutálódott. Javítás: a deployment Jegyzékben a latest helyett digestet kell használni, például app@sha256:.... A registryk beállíthatnak retention policy-t, ezért a digest hosszú távú elérhetőségét is biztosítani kell. Ellenőrzés: skopeo inspect docker://app@sha256:... ugyanazt a manifestet adja.

Gyakori tévedés: az emulált ARM64 build sikere nem jelenti, hogy a bináris nativan is helyesen fut. A QEMU eltérő kernel hívásokat vagy hardver képességeket szimulálhat, és a teljesítmény nem mérvadó. A kiadás előtti natív teszt és a digitális aláírás külön lépés.

37.2.5 Feladatok

  1. Magyarázó feladat: Adott egy OCI image név: registry.example.test/cpp-svc:1.2.3. Írd le, milyen parancsokkal lehet lekérdezni a manifest digestet, a platform descriptorokat és a config Entrypoint mezőjét. Mi a különbség a 1.2.3 tag és a lekérdezett digest között?

  2. Adminisztrációs/konfigurációs feladat: A labvm1 hoston hozz létre két platformú OCI indexet a korábbi hello.cpp felhasználásával: linux/amd64 és linux/arm64. A buildhez használj buildx-et vagy Podman manifestet, és a lab- prefixet megtartva példányosítsd a lab-hello nevet. Ellenőrizd, hogy az index két manifestre mutat.

  3. Diagnosztikai/failure/recovery feladat: Egy C++ szolgáltatás gcr.io/project/cpp-svc@sha256:111... digestet használ, de ARM64-re való indításkor az image futása exec format error hibát ad. A registryben az x86-64 hoston docker buildx imagetools inspect szerint csak linux/amd64 platform szerepel. Fogalmazd meg a diagnózist, a javítási lépéseket és az ellenőrzést.

37.2.6 Megoldások

  1. A manifest digest lekérdezéséhez skopeo inspect --raw docker://registry.example.test/cpp-svc:1.2.3 vagy crane digest registry.example.test/cpp-svc:1.2.3 használható. Ha a registry nem elérhető, localhoston Podman esetén podman image inspect --format '{{.Digest}}' adja a localhost image manifest digestjét. A platform descriptorok az indexben jelennek meg docker buildx imagetools inspect vagy skopeo inspect --raw kimenetében. A config Entrypoint mezőt skopeo inspect docker://... vagy podman image inspect mutatja. A 1.2.3 tag mutálló mutató, amely átirányítható más digestre; a digest a tartalom hash-e, immutable. Postcondition: a tanuló ki tudja választani a reprodukálható artifact azonosítót.

  2. A megoldás egy lehetséges lépéssor: docker buildx create --name lab-builder --use, majd docker buildx build --platform linux/amd64,linux/arm64 -t labregistry.example.test:5000/lab-hello:v1 --push ., végül docker buildx imagetools inspect labregistry.example.test:5000/lab-hello:v1. Ha a laborban nincs Docker Buildx, Podman manifesttel is megtehető: podman manifest create lab-hello:multi, podman manifest add --arch amd64 lab-hello:multi lab-hello:amd64, podman manifest add --arch arm64 lab-hello:multi lab-hello:arm64, podman manifest inspect lab-hello:multi. A Podman verziófüggő, ezért a pontos parancsot a labor release dokumentálja. Postcondition: az index legalább két platform descriptorral rendelkezik, és a lab- prefixű objektumok törölhetők.

  3. A diagnózis: a digest alatt csak linux/amd64 manifest áll, így az ARM64 host nem tudja futtatni. A digest immutable, tehát nem írható felül. A javítás: új multiarch build, amely linux/amd64,linux/arm64 platformokra készül, például docker buildx build --platform linux/amd64,linux/arm64 -t gcr.io/project/cpp-svc:1.2.4 --push ., majd a deploymentet az új digestre vagy a 1.2.4 tagre kell állítani, a digest rögzítésével. Az ellenőrzés: docker buildx imagetools inspect gcr.io/project/cpp-svc:1.2.4 mutassa mindkét platformot, és a futtatás ARM64 hoston sikeres legyen. Postcondition: a deployment a megfelelő platformon indul, és az immutable digest ismert.

37.2.7 Rövid összefoglaló

Az OCI image három részből áll: config, layer blobok és manifest. A manifest digestje a tartalom hash-e, immutable azonosító; a tag mutálló név, ezért deploymenthez digestet kell rögzíteni. Az image index több platformra mutató manifesteket fog össze, így a runtime a host architektúrájának megfelelő binárist választja. Az x86-64 és AArch64 eltérő ABI-t és syscall-t használ, ezért a bináris és a platform együtt része az artifact szerződésnek.

Továbbhasznált definíciók:

  • Content digest: blob tartalmából számított kriptográfiai hash, amely immutable artifact azonosító.
  • Tag: mutálló név, amely digestre mutat, és bármikor átirányítható.
  • Image index: platform-deskriptorokat tartalmazó manifest lista, amely az egyes platformok manifestjeire hivatkozik.
