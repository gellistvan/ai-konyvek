35.3 VM block storage, snapshot és backup

35.3.1 Motiváció és definíció

A VM vendéggép (guest) számára a háttértár „csak egy blokkeszköz”: a guest kernel a saját fájlrendszerét írja rá, és a host oldali fájl, LVM kötet, SAN LUN vagy hálózati storage mind ugyanúgy blokkos I/O-ként jelenik meg. A host operátornak azonban a storage backend, a cache mode és a pillanatkép (snapshot) működését ismernie kell, mert ezek határozzák meg, hogy a guest által leállított, konzisztensnek hitt adat milyen tartóssággal és visszaállíthatósággal rendelkezik.

VM block storage alatt a VM virtuális lemezét kiszolgáló perzisztens blokkeszközt értjük. A guest oldali fájlrendszer állapota a host storage rétegei felett él; a host snapshot vagy backup csak akkor nevezhető konzisztensnek, ha a guest oldal is elvégezte a szükséges flush/leállítási lépéseket. A jelen fejezet hatóköre a VM storage backend-ek, a cache/flush szemantika, a guest-oldali freeze, a host snapshot és a teljes VM backup megkülönböztetése, valamint a resize és hotplug host–guest együttműködése.

35.3.2 Storage backendek és cache mode

A libvirt/QEMU a guest lemezt többféle host storage-ból adhatja:

Backend Jellemző Előny Hátrány
File-backed qcow2/raw fájl egy fájlrendszerben egyszerű, hordozható, snapshot lánc dupla fájlrendszer- és page cache overhead
LVM volume LV a host VG-ben, akár thin pool-ból jó teljesítmény, kapacitáskezelés, thin snapshot host LVM adminisztrációt igényel
Block device közvetlen diszkpartíció, SAN LUN, NVMe namespace legkevesebb réteg, alacsonyabb latency per-VM méretezés rugalmatlanabb
Network storage RBD (Ceph), iSCSI, NFS, fiber channel shared storage, élő migráció hálózati és multipath kockázat, write-order kérdések

A QEMU cache mode meghatározza, hogy a guest write() hívása mikor és milyen szintű flush-t kap a host oldalon. A gyakorlatban a következő cache mode-okat használjuk libvirt <disk> driver attribútumával vagy cache paraméterrel:

Cache mode Jelentés Tartóssági garancia a guest fsync után
none host page cache nélkül, O_DIRECT a guest fsync -> host flush/disk write, erős
directsync O_DIRECT + guest fsync várakozás a készre legszigorúbb, lassabb
writethrough minden guest írás a host cache-en át a tárba ér guest-ig garantált a host szintjén
writeback a host cache a host által kezelt késleltetett flush-sel guest fsync nem feltétlenül éri el a lemezt; host crash esetén adatvesztés

A writeback kényelmes, mert csökkenti a látszólagos latency-t, de a guest saját naplózó fájlrendszere (journal) hiába írt fsync-et, ha a host cache elveszett. A szenior C++ fejlesztő a std::ofstream/fsync/fdatasync hívásokat úgy érzékeli, mint a guest alkalmazás tartóssági határát; a host cache mode ezt a határt a host oldalon újratárgyalja.

35.3.3 Guest filesystem freeze és konzisztens snapshot

A host snapshot készítése önmagában crash-consistent: a lemezkép olyan állapotot rögzít, mintha a guest váratlanul leállt volna. Ez a naplózó fájlrendszereknél gyakran elég a journal visszajátszásához, de nem garantálja, hogy az adatbázis vagy alkalmazás tranzakciói is befejeződtek, és nem garantálja a guest fájlrendszer metaadatainak pillanatnyi érvényességét.

Application-consistent snapshot készítéséhez a guest oldali fájlrendszer-freeze szükséges. A QEMU guest agent qemu-guest-agent szolgáltatás futtatja a vendégen a guest-fsfreeze-freeze parancsot, amely a guest fájlrendszereit quiesce állapotba hozza. Ez lehívja a guest kernel szintű syncfs-et és leállítja a további alkalmazási írásokat addig, amíg a host snapshot el nem készül, majd guest-fsfreeze-thaw jön. A freeze alatt a háttérben az alkalmazások esetleg pufferelnek, de a fájlrendszeri tranzakciók nyugalmi állapotban vannak.

A libvirt a --quiesce paranccsal kéri a guest agent freeze-t: virsh snapshot-create-as <domain> <name> --diskspec <target>,file=... --quiesce. Ha a guest agent nem fut, a parancs hibát jelez, és a snapshot nem jön létre. A freeze nem helyettesíti az adatbázis-szintű backupot; a d098-ban tanultak szerint a logical/physical backup WAL-kezeléssel az adatbázis szempontjából teljesebb garanciát ad.

35.3.4 Host snapshot versus full VM backup

A host snapshot egy pillanatkép: a VM lemez állapotát rögzíti egy adott időpontban, jellemzően a QEMU copy-on-write láncával vagy LVM snapshot-tal. A snapshot nem backup: ugyanazon a hoston él, nem véd a host meghibásodása, törlés, ransomware vagy pool corruption ellen. A teljes VM backup ezzel szemben egy külön, tartós, integritásellenőrzött másolat, amelyből a VM visszaállítható egy másik hoston vagy egy másik időpontban.

Két fő héj:

  1. Offline full VM backup: a VM leállítása után a lemezképek és a domain XML másolása egy dedikált backup tárba. Ez a legkonzisztensebb és legegyszerűbb, RTO-ja magas (leállásigény), de RPO-ja a leállás idejéhez kötött.
  2. Online full VM backup: guest filesystem freeze + host LVM/QEMU snapshot, majd a snapshot tartalmának másolása/restic/borg backupja. A QEMU external snapshot lánc esetén a snapshot fájl önmagában nem teljes; a teljes lánc (base + snapshot) kell a visszaállításhoz. A libvirt virsh blockcommit/blockpull paranccsal a lánc laposítható (merge) a backup előtt vagy után.

A teljes VM backupnak magában kell foglalnia a domain XML-t (virsh dumpxml <domain>), a hálózati definíciót, a titkokat (külön titkosított forrásból) és a guest hostname/időzóna konfigurációját, valamint a backup integritásellenőrzését. RPO/RTO és retention policy a d098-ban felépített módszertannal számítható.

35.3.5 Resize és hotplug guest/host oldal szétválasztva

A VM lemez méretnövelése két jól elkülöníthető fázisból áll: a host oldali blokkeszköz bővítése, majd a guest oldali partíció és fájlrendszer növelése. A host nem ismerheti a guest fájlrendszer méretét; a guest nem tud a host LVM/file resize lépéseiről. A kettőt lépésenként kell elvégezni.

Host oldal:

  1. Ha LVM thin pool a backend: a thin LV bővítése lvextend -L +5G /dev/mapper/vg-labthin-vm1-root.
  2. Ha qcow2 fájl: qemu-img resize /var/lib/libvirt/images/lab-vm1.qcow2 +5G.
  3. Ha a VM fut, értesíteni kell a guest virtuális csatolót: virsh blockresize <domain> vda 25G.

Guest oldal:

  1. A guest kernel érzékeli az új méretet; lsblk mutatja a nagyobb /dev/vda-t.
  2. Partíciós táblánál growpart /dev/vda 1 (vagy fdisk), majd kernel update: partprobe /dev/vda.
  3. Fájlrendszer növelése: xfs_growfs / (XFS) vagy resize2fs /dev/vda1 (ext4).

A csökkentés jóval veszélyesebb: a legtöbb fájlrendszer nem támogatja a shrink-et, és a guest migráció/backup előtt teljes ellenőrzés kell. A d087-ben bemutatott LVM VG/PV szabad PE-feltételek is érvényesek.

A hotplug új lemezt csatol a futó VM-hez: a host oldali virsh attach-disk <domain> <source> <target> --persistent --live elküldi a guestnek a virtuális eszközt; a guest kernel udev szabálya létrehozza a /dev/vdb-t. A guestnek udevadm settle és lsblk ellenőrzés után lehet mountolni. A hotremove virsh detach-disk <domain> <target> követeli meg, hogy a guesten ne legyen mountolt vagy nyitott fájl azon az eszközön, különben a guest I/O hibát észlel.

35.3.6 Kidolgozott példa: storage, resize, snapshot, backup

A példa labhoston fut, Ubuntu Server 24.04 LTS guesttel, KVM/libvirt alatt. A host storage LVM thin pool vg-labthin, a VM neve lab-vm1, a virtuális lemez /dev/vda, a backend qcow2 fájl a helyi storage pool-ban.

Előfeltételek:

  • VM fut, qemu-guest-agent telepítve és fut a guestben.
  • A hoston a libvirt és qemu-kvm verziója az Ubuntu 24.04 LTS csomagjainak felel meg.
  • Az LVM thin pool már létezik (d087 előzmény).

1. Snapshot készítés quiesce-szel (host oldal):

# Host: labhost1, UID: oper (sudo)
sudo virsh snapshot-create-as lab-vm1 snap-before-resize \
  --disk-only \
  --diskspec vda,file=/var/lib/libvirt/images/lab-vm1-snap1.qcow2 \
  --quiesce

Várt kimenet (illusztratív):

Domain snapshot snap-before-resize created

Ellenőrzés:

sudo virsh snapshot-list lab-vm1
sudo qemu-img info /var/lib/libvirt/images/lab-vm1-snap1.qcow2

qemu-img info mutatja a backing file-t (a base image), ezért a snapshot önmagában nem teljes.

2. Disk resize guest fájlrendszerrel:

# Host oldal: a qcow2 bővítése
sudo qemu-img resize /var/lib/libvirt/images/lab-vm1.qcow2 +5G
# A futó VM értesítése
sudo virsh blockresize lab-vm1 vda 25G
# Guest oldal (SSH lab-vm1, UID: labuser)
sudo growpart /dev/vda 1
sudo xfs_growfs /

Várható kimenet df -h után a / mérete 25G közelében.

3. Teljes VM backup a snapshot lánc felhasználásával:

A külső snapshot lánc miatt a pillanatnyi állapot a base image + snapshot fájl. A backuphoz először a láncot laposíthatjuk:

sudo virsh blockcommit lab-vm1 vda --base /var/lib/libvirt/images/lab-vm1.qcow2 --top /var/lib/libvirt/images/lab-vm1-snap1.qcow2 --wait --verbose

Ezután a base image már teljes a pillanatnyi állapottal (ha az eljárás sikeres), majd elvégezhető a file-bázisú backup:

sudo restic -r /mnt/backup-repo backup /var/lib/libvirt/images/lab-vm1.qcow2
sudo virsh dumpxml lab-vm1 > /var/lib/libvirt/images/lab-vm1.xml
sudo restic -r /mnt/backup-repo backup /var/lib/libvirt/images/lab-vm1.xml

A fenti restic parancs csak illusztráció; a d098-ban felépített retention és integrity ellenőrzés itt is kötelező.

35.3.7 Hibák és ellenpróbák

  • Space exhaustion a thin poolban: ha a thin pool data vagy metadata kifogy, a VM I/O hibákat észlel. Adatgyűjtés: lvs -a, vgs, dmesg | tail. Kezelés: felesleges snapshot-ok törlése, fstrim a host fájlrendszeren, thin pool bővítés vagy thin LV resize utáni monitoring. Ellenpróba: ne vágjunk bele törlésbe, amíg a pool kihasználtság nem ismert.
  • Snapshot chain corruption: ha egy external snapshot backing file elérhetetlenné válik (törlés, path változás), a VM nem indul. Adatgyűjtés: qemu-img info, virsh snapshot-list. Helyreállítás: a lánc helyreállítása a backupból vagy a base image-re való blockcommit. Ellenpróba: ne másoljunk kézzel qcow2 fájlokat a lánc megértése nélkül.
  • Hotplug utáni hiányzó eszköz: a guest nem látja a /dev/vdb-t. Adatgyűjtés: lsblk, udevadm monitor. Kezelés: udevadm trigger, partprobe, esetleg újraindítás. Ellenpróba: ne echo "- - -" > /sys/class/scsi_host/hostX/scan parancssal kísérletezgessünk, amíg a VM SCSI típusa nem ismert.
  • Quiesce hiba: virsh snapshot-create-as --quiesce hibát ad, ha a guest agent nem fut. Ellenőrzés: virsh qemu-agent-command lab-vm1 '{"execute":"guest-ping"}'. Ellenpróba: ne készítsünk „csendes” snapshotot quiesce nélkül, ha az alkalmazás integritása számít.

35.3.8 Feladatok

35.3.8.1 1. Magyarázó feladat

Dokumentáld egy adott labVM storage konfigurációját: backend típusát, cache mode-ját, a guest fájlrendszer típusát és a host storage pool szabad kapacitását. Írd le, hogy milyen feltételek mellett lesz a host snapshot ezen a VM-en application-consistent, és mi történik, ha a cache mode writeback-re van állítva. Adj meg egy ellenőrző parancssort, amellyel a guest agent és a host pool állapota megvizsgálható.

35.3.8.2 2. Adminisztrációs/konfigurációs feladat

Egy lab-vm2 VM jelenleg 20 GiB virtuális lemezzel fut, LVM thin pool backenddel. Növeld a lemezt 30 GiB-ra a következő lépésekkel: host oldali lvextend, virsh blockresize, majd guest oldali partíció- és fájlrendszer-növelés. Készíts előtte egy quiesce nélküli host snapshotot a biztonsági visszaút érdekében. Írd le a parancsokat, a várt állapotot és egy rollback tervet arra az esetre, ha a guest fájlrendszer növelése meghiúsul.

35.3.8.3 3. Diagnosztikai/failure/recovery feladat

A lab-vm3 indítása után a guest a root fájlrendszer I/O hibákat jelez. A host oldalon a qemu-img info azt mutatja, hogy a backing file lab-vm3-base.qcow2 nem található. A libvirt log szerint a korábbi blockcommit félbeszakadt, és a snapshot lánc sérült. Végezd el az adatgyűjtést, fogalmazz meg egy hipotézist a hiba okáról, és javasolj egy recovery folyamatot a rendelkezésre álló backupból. Adj meg egy ellenőrzési feltételt, amely igazolja, hogy a guest ismét egészségesen indul.

35.3.9 Megoldások

35.3.9.1 1. Megoldás

A dokumentációhoz a következő parancsok szükségesek (hostoldal, sudo):

virsh dumpxml lab-vm1 | grep -A5 '<disk'
lvdisplay /dev/vg-labthin/vm1-root
lsblk
virsh qemu-agent-command lab-vm1 '{"execute":"guest-ping"}'

Az application-consistent snapshot feltételei: a guest agent fut, a fájlrendszer quiesce-re képes, a host snapshot parancs --quiesce opciót használ, és a host storage poolban van szabad hely a snapshotnak. writeback cache mode esetén a guest fsync-je nem garantálja a host oldali tartós kiírást, ezért a guest szintű quiesce önmagában nem elég a tartóssághoz; a host cache flush policy kell hozzá. A dokumentációban szerepelnie kell ennek a kockázatnak.

Postcondition: a dokumentum tartalmazza a backend, cache mode, guest fájlrendszer, pool szabad kapacitás és a quiesce feltételek minden elemét; az ellenőrző parancsok lefuttathatók.

35.3.9.2 2. Megoldás

Host oldal (labhost, sudo):

# Snapshot a visszaúthoz
virsh snapshot-create-as lab-vm2 snap-pre-resize \
  --diskspec vda,file=/var/lib/libvirt/images/lab-vm2-snap-pre.qcow2

# LVM thin LV bővítése
lvextend -L 30G /dev/vg-labthin/lab-vm2-root

# VM értesítése
virsh blockresize lab-vm2 vda 30G

Guest oldal (SSH lab-vm2):

sudo growpart /dev/vda 1
sudo xfs_growfs /

Ellenőrzés: df -h / mutassa a növelt méretet.

Rollback: ha a guest fájlrendszer növelés meghiúsul, állítsuk le a VM-et, töröljük a jelenlegi base image-et, és állítsuk vissza a pre-resize snapshotból: a VM indítása a snapshot backing file-jára mutatva, majd a lánc laposítása. A snapshot megtartása addig kötelező, amíg a méretnövelés utáni ellenőrzés nem sikeres.

Postcondition: a guest root fájlrendszer 30 GiB kapacitású, a host LVM thin LV 30 GiB, a pre-resize snapshot létezik és qemu-img info szerint a lánc ép.

35.3.9.3 3. Megoldás

Adatgyűjtés:

qemu-img info /var/lib/libvirt/images/lab-vm3.qcow2
ls -la /var/lib/libvirt/images/
virsh dumpxml lab-vm3 | grep -A5 '<disk>'
tail -n 100 /var/log/libvirt/qemu/lab-vm3.log

Hipotézis: a korábbi virsh blockcommit megszakadt, így az aktuális top fájl egy backing file-ra hivatkozik, amely már nem létezik.

Recovery:

  1. A backup repóból állítsuk vissza a legutóbbi teljes base image-et és az azóta készült snapshot fájlokat, valamint a domain XML-t.
  2. Ellenőrizzük a qemu-img info kimenetét, hogy a backing file path létezik-e, és a virtuális méret megegyezik-e az elvárttal.
  3. Indítsuk el a VM-et; ha indul, ellenőrizzük a guest fájlrendszert fsck-kel (vészhelyzeti módban), majd a guest alkalmazást.
  4. Ha a lánc sérült, de a backupból megvan a base + snapshot, végezzünk virsh blockcommit-et egy tiszta pillanatban, hogy újra lapos láncot kapjunk.

Ellenőrzés: a guest eléri a root fájlrendszert, df -h és a demo alkalmazás health endpointja 200-at ad.

Postcondition: a VM indul, a guest root fájlrendszer hibamentes, a host oldali qcow2 lánc teljes és a domain XML a backupból visszaállítva.

35.3.10 Rövid összefoglaló

A VM block storage a host oldali blokkeszköz, amelyet a guest fájlrendszer saját blokkos eszközként lát. A host snapshot akkor lesz application-consistent, ha a guest oldali qemu-guest-agent fájlrendszer-freeze-t végez, és a host --quiesce opcióval készíti a snapshotot. Cache mode-ban a writeback csökkenti a guest fsync tartóssági garanciáját; a none/directsync a szigorúbb. A resize és hotplug mindig host és guest oldali lépésekre bontható; a host bővíti a blokkeszközt, a guest a partíciót és a fájlrendszert. A teljes VM backup különbözik a snapshot-tól: a snapshot a pillanatnyi állapot, a backup tartós, ellenőrzött másolat.

Továbbhasznált definíciók:

  • Application-consistent snapshot: olyan pillanatkép, amelynél a guest alkalmazások fájlrendszer-tranzakciói quiesce állapotban voltak, így a visszaállítás után a guest alkalmazás érvényes állapotot lát.
  • External snapshot lánc: QEMU copy-on-write snapshot fájlok sorozata, ahol egy fájl a megelőző backing file-ra hivatkozik; a teljes állapot a lánc együttesével áll elő.
  • Cache mode: a QEMU/libvirt beállítás, amely a guest írás és a host lemez közötti cache/flush viselkedést szabályozza, befolyásolva a tartósságot és a teljesítményt.
