48.2 Runner, isolation és build environment

48.2.1 Motiváció

A d236 alfejezetben a pipeline trigger-, minőség- és folyamatoldalát építettük fel. Ott a kód és a konfiguráció került előtérbe; most a számítási oldalt vizsgáljuk. A legjobb workflow is instabil lesz, ha a runner gazdagépen „valaki már hagyott egy másik libstdc++-t”, ha a build cache mérgezett, vagy ha egy külső pull request kódja véletlenül a deploy tokennel egy szobában fut. A szenior C++ fejlesztő a buildet nem csupán fordítási lépésként látja, hanem erőforrás-élettartam, izolációs határ és supply-chain bizonyíték szempontjából is: ugyanaz a forrás revision, ugyanaz a toolchain, ugyanaz a környezet, ugyanaz az artifact. A runner ennek a szerződésnek a fizikai végrehajtója.

A cél az, hogy a runner workloadhoz isolation-, credential- és resource policy-t tudjunk választani, és hogy a build környezetet image-alapú lockkal reprodukálhatóvá tegyük. A rossz döntés tünete általában nem azonnali fordítási hiba, hanem később, a release után jelentkező ABI-mismatch, credential leak vagy cache poisoning.

48.2.2 Definíciók és működés

Runner (vagy build agent): a CI orchestrator által menedzselt erőforrás, amely a job lépéseit futtatja. A runner egyszerre számítási process, identitás és state hordozó. Két fő tengely mentén osztályozzuk:

  1. Host tulajdonos: hosted runner (a szolgáltató frissíti, üzemelteti, korlátozott kontrollt ad) vagy self-hosted runner (saját VM/container, teljes kontroll, saját patching felelősség).
  2. Élettartam: ephemeral runner (minden job után törlődik) vagy tartós runner (újrahasználják).

A build environment a build lépés teljes számítási kontextusa: process image, user, kernel API, compiler, standard library, sysroot, dependencyk, környezeti változók, cache és network policy. A reprodukálhatóság itt nem azt jelenti, hogy minden byte bitre azonos; a natív C++ artifact esetén inkább azt, hogy adott forrás revision és build environment digest alapján ugyanaz a toolchain, ugyanaz a dependency és ugyanaz a build konfiguráció áll elő. A teljes bit-azonos reprodukció külön determinisztikus build konfigurációt igényel.

A job isolation a job folyamatainak erőforrás-, fájlrendszer-, hálózat- és credential határa. Ezt a d166-ban tanult VM-konténer különbséggel pontosítjuk: a konténer ugyanazt a kernelt használja, a VM saját kernel és eszközmodell mögött fut.

48.2.3 Hosted, self-hosted és ephemeral runner

A hosted runner kényelmes, mert a szolgáltató biztosítja a VM-et, a friss image-et és az ideiglenes fájlrendszert. A hosted runner általában ephemeral, tehát a job végén a teljes gazdakörnyezet megsemmisül. Hátránya, hogy a build environment nem garantált hosszú távon: a szolgáltató frissíti az operációs rendszert, a compilert, a cache szoftvert; a floating ubuntu-latest image digestje időben változik. Ha a C++ projekt egy adott glibc vagy libstdc++ ABI-t feltételez, akkor a hosted runner címke nem elég, image digestet kell rögzíteni vagy saját builder image-et használni.

A self-hosted runner saját VM-en vagy konténerben fut. Nagyobb ellenőrzést ad a toolchain, a disk, a hálózat és a credential policy felett, cserébe a miénk a patching, a runner frissítés és a hitelesítő adatok életciklusa. A self-hosted runner lehet tartós vagy ephemeral. A tartós runner gyorsabb, mert a toolchain és a cache megmarad, de a korábbi job state-je beszivároghat: /tmp maradék, SSH key, anyag, környezeti változó. Az ephemeral self-hosted runner a job után a teljes virtuális gépet eldobja, ezért a következő job tiszta state-ből indul; ez a biztonság szempontjából a legerősebb, de provision overheadet jelent.

A választás nem kizárólagos: egy szervezet gyakran a trusted belső buildjeihez tartós self-hosted runner-t használ, az untrusted PR-ekhez pedig ephemeral, minimális jogú VM runner-t.

48.2.4 VM/container/sandbox és untrusted PR

A runner izolációjának szintjei a következők:

  • Host process: a job lépései közvetlenül a runner gazdán futnak. Ez csak teljesen megbízható repository esetén elfogadható, és még ott is felesleges kockázatot hordoz.
  • Container job: a job lépései egy OCI containerben futnak. A kernel közös, ezért a kernel elleni támadások vagy egy container breakout sebezhetőség áttörheti az izolációt. A container job a leggyakoribb, de untrusted PR esetén önmagában nem elégséges.
  • VM runner: minden job vagy minden runner egy friss VM-ben fut. A kernel, az eszközvezérlők és a memória hozzáférések a hypervisor mögött vannak; a d166-ban tanult root/non-root CPU módok és nested paging adják a határt. Az untrusted fork PR kódját legalább ezen a szinten érdemes futtatni.
  • Sandbox/microVM: a gVisor, Firecracker vagy hasonló megoldás a VM izolációját kisebb overheaddel próbálja elérni. A boundary nagy, de a kisebb attack surface ellenére is marad kernel/user-space különbség.

Az untrusted PR esetén a fontos kérdés nem csupán az, hogy a kód milyen műveletet hajthat végre, hanem az is, hogy milyen credentialt, cache-t és artifact targetet érhet el. A pull_request_target trigger különösen veszélyes: az a base repository contextjében fut, ezért az untrusted kódnak ne adjunk lehetőséget arra, hogy az alapszolgáltatás credentialját lássa. A d184-ben tanult SBOM- és attestation-szemlélet itt is érvényes: a runner és az image ugyanúgy az artifact proof része, mint a compiler.

48.2.5 C++ compiler, stdlib, sysroot és build tools

A build environment lockjának része a toolchain rögzítése. A C++ projekt artifactja nem csak a saját kódjától függ, hanem a compiler verziójától, a standard library ABI-jától és a rendszerkönyvtáraktól. Például a GCC 12 és GCC 13 eltérő codegen-t adhat, a libstdc++ GLIBCXX_3.4.XX változatai pedig megkövetelhetők a futtató gépen. A -D_GLIBCXX_USE_CXX11_ABI=1 kapcsoló konzisztenciája a dependencykkel szintén build environment kérdés.

A sysroot (cross build esetén) az a target root fájlrendszer, amely a header és library path-okat adja. A toolchain file explicit CMAKE_SYSROOT, CMAKE_C_COMPILER, CMAKE_CXX_COMPILER beállításokat ad. A builder image tartalma: compiler, cmake, ninja, pkg-config, a függőségek development csomagjai, a target sysroot, valamint a debug- és bizonyítékgyűjtő eszközök (például readelf, sha256sum).

A build tools verziója is a környezet része: a CMake generator és a Ninja verzió eltérő fájl-elrendezést vagy cache formátumot használhat. A reprodukálhatósághoz nem elég a compiler verzióját megadni; a build image digestnek az egész toolchain állapotot rögzítenie kell.

48.2.6 Version pin, cache és dependency checksum

A version pin az a döntés, hogy minden bemenetet immutable azonosítóval hivatkozunk: például a container image sha256:... digestgel, a runner image verzióval, a compiler csomagverzióval. A floating tag (latest, ubuntu-22.04) nem rögzíti a tartalmat, ezért lockolni kell digestre vagy egy saját immutable image-re.

A dependency checksum a harmadik féltől letöltött artifactok hitelességét biztosítja. A package manager lockfile (conan.lock, vcpkg lock, CMake FetchContent pinned hash) mellett a repóban tárolt checksums.sha256 is használható. A cél, hogy a letöltött állomány minden bittel az elvárt legyen, ne csak a név és a verzió.

A cache a build felgyorsítására való, de a cache is artifact: a rossz kulcsolás esetén az untrusted PR cache-t ír, a main build pedig mérgezett artefaktot kap. A cache key-be be kell keverni a lockfile digestet és a releváns környezet azonosítóját, hogy a különböző dependencyk ne használhassák ugyanazt a bejegyzést. A ccache használata esetén a compiler hash és a source hash is része a cache validity ellenőrzésének.

48.2.7 Concurrency, time és resource quota

A build párhuzamossága két szinten jelenik meg: a CI job concurrency (hány párhuzamos job fut) és a build process belső párhuzamossága (-j). A concurrency group megakadályozza, hogy ugyanazon branch/PR esetén több build versenyezzen ugyanazért a runner-ért vagy cache-ért. A timeout-minutes a job maximális futásideje; ha a build deadlockol, a timeout megszakítja és a hibát jelzi. A step timeout ennél finomabb határt ad.

A resource quota a CPU, memória és disk korlátot jelenti. A hosted runner esetén a plan size korlátozza az erőforrást; a self-hosted VM-en a hypervisor vagy a host cgroup v2 ad határt. A container job esetén a runtime limit is lehetséges, de a legbiztosabb a VM szintű limit. A C++ build gyakran CPU-bound, ezért a nproc teljes gazdagép értékét a containerben is figyelembe kell venni; a cgroup v2 CPU cpuset korlátozza a látható processzorok számát, de a memória korlát a compile process OOM-jéhez vezethet, ha a parallel -j túl magas.

48.2.8 Credential exposure és runner cleanup

A runner-nek identitása van: a CI szerver által kiadott registration token, a job process számára látható GITHUB_TOKEN vagy CI_JOB_TOKEN, a container registry pull credential, a deploy token. A runner gazdagépen ezek a secret-ek a fájlrendszerben, a process env-ben és a shell historyban is megjelenhetnek. A minimális jogosultság elve itt is érvényes: a job permissions blokkja csökkenti a token scope-ot, a short-lived OIDC credential jobb, mint a long-lived static key, és a d184-ben tanult secret mount a ENV/ARG helyett megakadályozza, hogy a titok a kép rétegébe kerüljön.

A runner cleanup a job utáni állapotmentesítés. Ephemeral VM esetén maga a VM törlés a cleanup; tartós runner esetén a cleanup script feladata a workspace, a temp, a SSH agent, a git safe.directory, a Docker config és a cache credential eltávolítása. A cleanup akkor is lefusson, ha a build hibázott; a CI rendszerben a finally vagy a post step erre való. A cleanup nélküli runner fokozatosan credential-vándorlást, state leaket és nem reprodukálható buildeket okoz.

48.2.9 Kidolgozott példa

A következő példa egy GitHub Actions workflow egy lab-cpp-service C++ projekt számára. A runner self-hosted, ephemeral, Linux x64, és a job egy pinned container image-ben fut. A CI rendszer nem futtatja a példát; a kimenetek csak illusztratívak.

Target, jogosultság és előfeltétel: a .github/workflows/lab-cpp-build.yml fájl a lab-cpp-service repositoryban. A runner host lab-runner-01 (KVM VM), runner group lab, container user runner UID 1001. Előfeltétel: a runner regisztrálva van, a ghcr.io/lab-org/cpp-builder image a lab registryben elérhető, a third-party/checksums.sha256 a repóban. Módosítás: a workflow fájl. Visszagörgetés: a korábbi verzió visszaállítása.

name: lab-cpp-build

on:
  pull_request:
  workflow_dispatch:

concurrency:
  group: lab-cpp-build-${{ github.event.pull_request.number || github.sha }}
  cancel-in-progress: true

permissions:
  contents: read
  packages: read

jobs:
  build:
    runs-on: [self-hosted, ephemeral, linux, x64, lab]
    timeout-minutes: 20
    container:
      # A production policy szerint a digestet a lab registry valós értékére kell cserélni;
      # az alábbi digest dummy, a tananyag nem állítja, hogy létezik.
      image: ghcr.io/lab-org/cpp-builder@sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
      credentials:
        username: ${{ github.actor }}
        password: ${{ secrets.GITHUB_TOKEN }}
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Verify locked dependencies
        run: |
          set -euo pipefail
          sha256sum -c third-party/checksums.sha256 --strict

      - name: Cache ccache
        uses: actions/cache@v4
        with:
          path: .ccache
          key: ccache-${{ runner.os }}-${{ hashFiles('third-party/checksums.sha256') }}

      - name: Configure
        run: |
          cmake -S . -B build -G Ninja \
            -DCMAKE_BUILD_TYPE=Release \
            -DCMAKE_TOOLCHAIN_FILE="$GITHUB_WORKSPACE/cmake/toolchain-linux-x64.cmake"

      - name: Build
        run: |
          cmake --build build --parallel "$(nproc)"

      - name: Record evidence
        run: |
          sha256sum build/lab-cpp-service > build/lab-cpp-service.sha256
          readelf -n build/lab-cpp-service > build/build-id.txt

A toolchain-linux-x64.cmake a builder image elérési útvonalait rögzíti, például:

set(CMAKE_C_COMPILER /opt/toolchain/bin/gcc)
set(CMAKE_CXX_COMPILER /opt/toolchain/bin/g++)
set(CMAKE_SYSROOT /opt/toolchain/sysroot)
set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

Várható, nem ténylegesen futtatott logrészlet:

Run sha256sum -c third-party/checksums.sha256 --strict
third-party/libfoo.tar.xz: OK
...
Run cmake -S . -B build -G Ninja ...
-- The CXX compiler identification is GNU 13.2.0
...
Build completed successfully

Ellenőrzési feltétel: a job sikeres; a build/lab-cpp-service artifact létezik; a build/lab-cpp-service.sha256 és a build/build-id.txt létrejött; a container image digest a workflowban szereplő digesttel egyezik; a permissions csak contents: read és packages: read jogot ad. Hibajelenség: ha a digest nem létezik, a job már a container pull-nál meghibásodik; ha a checksum fail, a sha256sum lépés nem nulla exit kódot ad.

48.2.10 Tipikus hibák és ellenpróbák

Tünet: a build lokális fejlesztőgépen sikerül, de a CI-ben undefined reference to std::__cxx11::... vagy GLIBCXX_3.4.29 not found hiba jelenik meg. Hipotézis: a runner environmentben más libstdc++/glibc van, mint a targeten. Adatgyűjtés: ldd --version, strings /usr/lib/x86_64-linux-gnu/libstdc++.so.6 | grep GLIBCXX, readelf -n build/lab-cpp-service. Egy változtatás: pinned builder image és explicit toolchain file bevezetése. Verification: a ldd kimenet a builder image-ben megegyezik a target elvárttal.

Tünet: a self-hosted tartós runner-en a job lát egy DEPLOY_TOKEN környezeti változót, amit a workflow nem adott át. Hipotézis: a tartós gazdagép environmentje tartalmazza a secretet. Adatgyűjtés: printenv | sort, a runner gazdán a config és a systemd unit vizsgálata. Egy változtatás: ephemeral self-hosted runner bevezetése, a secret eltávolítása a gazdagépről, a job permissions minimalizálása. Verification: a job logja már nem mutatja a változót.

Tünet: a PR build cache-t ír, és a main build mérgezett artifactot kap. Hipotézis: a cache key nem különbözteti meg a trust szintet vagy a bemeneteket. Adatgyűjtés: a cache log és a lockfile hash ellenőrzése. Egy változtatás: a cache key szigorúbbá tétele a hashFiles('third-party/checksums.sha256') mellett, és az untrusted PR esetén teljesen külön cache namespace. Verification: a main build cache találata nem a PR cache, a checksum ellenőrzés továbbra is lefut.

Tünet: a job több órája fut, nem halad, és nem lép timeout. Hipotézis: hiányzik a timeout-minutes. Adatgyűjtés: a job log utolsó lépése, a runner process állapota. Egy változtatás: timeout-minutes bevezetése. Verification: a job a beállított idő után megszakad, a hibajelzés megjelenik.

48.2.11 Feladatok

  1. Magyarázó feladat: Hasonlítsa össze táblázatban a hosted, self-hosted tartós és self-hosted ephemeral runner jellemzőit: kié a host, mi a state-élettartam, milyen izolációs szint, milyen credential exposure kockázat, mikor válasszuk. Adjon példát egy C++ project esetén, amikor a self-hosted ephemeral a jó választás.

  2. Adminisztrációs/konfigurációs feladat: Készítse el a .github/workflows/lab-cpp-ping.yml workflow-t egy lab-cpp-ping C++ projekt számára. A workflow: self-hosted ephemeral Linux x64 runner, container job pinned dummy digestgel, timeout-minutes: 15, concurrency.group, ellenőrzött third-party checksum, ccache cache, minimal permissions. A postcondition: a workflow a pull_request triggerre fut, a job csak contents: read és packages: read jogot kap, a checksum fail esetén a build leáll.

  3. Diagnosztikai/failure/recovery feladat: A self-hosted tartós runner-en a build a host /usr/bin/g++-t használja a container image-ben lévő /opt/toolchain/bin/g++ helyett. A CMake cache a host path-okat őrzi a korábbi tartós state miatt. Adja meg a root cause-ot, és írja le a javítás lépéseit: ephemeral runner bevezetése, job container használata, clean build, explicit toolchain file és ellenőrzés.

48.2.12 Megoldások

  1. A táblázat lényege:
Szempont Hosted Self-hosted tartós Self-hosted ephemeral
Host tulajdonos szolgáltató mi mi
State ephemeral tartós ephemeral
Izoláció VM VM/container VM/container
Credential exposure alacsony magas közepes
Toolchain kontroll alacsony magas magas
Provision overhead alacsony alacsony magas

A self-hosted ephemeral akkor jó választás, ha a C++ projekt fix GCC/libstdc++ verziót és saját sysrootot igényel, de az untrusted PR-ek futtatása nem fér bele egy tartós, megosztott credential-lal rendelkező gazdagépbe.

  1. A workflow megfelelő YAML-ja a kidolgozott példa mintáját követi, azzal a különbséggel, hogy a repository lab-cpp-ping, a timeout 15 perc, és a checksum lépés elég a build előtt. A postcondition ellenőrzése: a permissions blokk a contents: read és packages: read jogot adja, a checksum fail a sha256sum nem nulla exit kódjával leállítja a jobot.

  2. Root cause: a tartós runner gazdagépen a korábbi build state és a host toolchain megmaradt; a job containerben a PATH tartalmazta a host path-okat, és a CMake cache a host compilert rögzítette. Javítás: (a) a runner átállítása ephemeral self-hosted VM-re, hogy a host state ne maradjon; (b) a job container beállítása a pinned image-re; (c) a CMake build dir törlése (rm -rf build) a tartós cache eltávolításához; (d) a toolchain file explicit CMAKE_CXX_COMPILER /opt/toolchain/bin/g++ beállítása; (e) a verification cmake --build build --verbose logjában a compiler path ellenőrzése.

48.2.13 Rövid összefoglaló

A runner a CI job számítási erőforrása és bizalmi határa, amelyet a host tulajdonos, az élettartam és az izolációs szint szerint választunk. Az untrusted PR-eket legalább VM szintű, minimális jogú ephemeral runneren futtassuk; a konténer önmagában nem elég. A build environment lock a container image digestből, a compiler/stdlib/sysroot verzióból és a dependency checksumból áll; a cache key a lockfile digesthez kötött, a timeout és a resource quota pedig a deadlock és az erőforrás-túllépés ellen véd. A job után a credential és a state cleanup kötelező. Továbbhasznált definíciók: runner – a CI orchestrator által menedzselt végrehajtó erőforrás; build environment – a build process image, toolchain, sysroot, dependency és policy kontextus; ephemeral – az a runner vagy job állapot, amely a futás után megsemmisül.
