21.2 OpenSSH, host trust és admin access

Az SSH hozzáférés alapja, hogy a kliens és a szerver is ellenőrzi a másik fél azonosságát, mielőtt bármilyen privileged művelet megtörténne. A host trust és a user trust két külön irányban működik: a host key a szerver azonosságát igazolja a kliens felé, a user key pedig a belépő felhasználó azonosságát igazolja a szerver felé. A rendszergazda legnagyobb hibája, ha ezt a két réteget összemossa, vagy egy konfigurációmódosítást úgy végez, hogy közben elveszíti a bejelentkezési útvonalat. Ez utóbbi miatt minden SSH-változtatásnál kötelező egy előre ellenőrzött konzol vagy out-of-band hozzáférés megtartása.

21.2.1 Definíciók és trust modell

  • Host key: az SSH szerver által a transport rétegben bemutatott nyilvános kulcs, amelyet a kliens a ~/.ssh/known_hosts fájlban tárol. Ez bizonyítja, hogy a szerver ugyanaz a gép, amelyhez a felhasználó korábban csatlakozott. Ha a host key megváltozik, a kliens REMOTE HOST IDENTIFICATION HAS CHANGED! hibát ad, mert lehetséges man-in-the-middle támadás vagy tényleges szervercsere.
  • User key: a felhasználó által birtokolt kulcs, amelyet a szerver a ~/.ssh/authorized_keys fájlban tárol. Ez bizonyítja, hogy a kliens birtokában van a privát kulcsnak, és a szerver megengedi a bejelentkezést.
  • known_hosts: a kliens oldali cache, amely a korábban elfogadott host keyeket tartalmazza. A fájl sorai hostname,ip keytype base64-encoded-public-key formájúak.
  • authorized_keys: a szerver oldali fájl, amely az engedélyezett felhasználói publikus kulcsokat tartalmazza. A fájl owner és permission nagyon szigorú: a fájl csak a felhasználó tulajdonában lehet, és nem lehet csoport/other írható. Ha a jogosultság túl engedékeny, az SSH szerver biztonságból figyelmen kívül hagyja a kulcsot.
  • sshd_config és include precedence: A szerver konfigurációját az OpenSSH általában a /etc/ssh/sshd_config fájlból olvassa. A modern Ubuntu Server 24.04 LTS rendszereken a fő konfiguráció jellemzően egy Include /etc/ssh/sshd_config.d/*.conf sort tartalmaz. Az OpenSSH dokumentációja szerint a legtöbb direktívánál az elsőként megszerzett érték lesz érvényben. Ezért a sshd_config.d könyvtárban lévő, lexikografikusan korábbi nevű fájlok felülírhatják a későbbieket, ha ugyanazt a beállítást tartalmazzák. Az include-ok a fő fájlban az adott sor pozíciójában dolgozódnak fel, így a sorrend számít. A pontos precedence-t a labhoston a man sshd_config és a sshd -T kimenetének együttes elemzésével kell ellenőrizni, mert a distro csomagolás eltérhet.

21.2.2 Kidolgozott példa: password auth kikapcsolása és konzolos rollback

A példa célja, hogy a labhoston megszüntessük a jelszavas SSH-bejelentkezést, miközben az SSH-kulcsos belépés előzetesen már működik. A változtatásokat úgy hajtjuk végre, hogy a meglévő interaktív session-ök ne szakadjanak meg, és mindvégig maradjon konzolos visszaút.

Labkörnyezet:

  • labhost: lab-ssh1.lab.internal – Ubuntu Server 24.04 LTS, OpenSSH szerver.
  • account: labops (UID 1001), sudo joggal.
  • workstation: labws.lab.internal – ahonnan a kapcsolat indul, devuser (UID 1000).
  • Konzolos hozzáférés: virsh console lab-ssh1 vagy VMware/Compute Engine serial console, aktív lab session-ben.

1. Kiinduló állapot ellenőrzése

Először ellenőrizzük, hogy jelszóval még be tudunk lépni, és van-e már kulcsos hozzáférés. A workstationön léteznie kell egy SSH-kulcspárnak:

# target: labws.lab.internal, account: devuser (UID 1000), privilege: none
ls -l ~/.ssh/id_ed25519 ~/.ssh/id_ed25519.pub 2>/dev/null || echo "nincs kulcs"

Ha nincs kulcs, generáljunk:

# target: labws.lab.internal, account: devuser (UID 1000), privilege: none
ssh-keygen -t ed25519 -a 100 -f ~/.ssh/id_ed25519 -N "" -C "labops@lab-ssh1"

2. Publikus kulcs felmásolása a szerverre

Mivel a jelszavas belépés még aktív, használhatjuk az ssh-copy-id parancsot. A labops felhasználó jelszavát nem adjuk meg a példában; a labban ez legyen egy lab-only dummy jelszó, vagy interaktívan kell beírni.

# target: labws.lab.internal, account: devuser (UID 1000), privilege: none
ssh-copy-id -i ~/.ssh/id_ed25519.pub labops@lab-ssh1

3. Kulcsos belépés tesztelése a jelszó letiltása előtt

Fontos, hogy a kulcsos autentikáció már működjön, mielőtt a jelszót letiltjuk. A -o PreferredAuthentications=publickey opcióval kényszerítsük a kulcsos utat, és ne adjunk jelszót:

# target: labws.lab.internal, account: devuser (UID 1000), privilege: none
ssh -o PreferredAuthentications=publickey -o BatchMode=yes labops@lab-ssh1 'id; hostname'

Várható kimenet: a labops UID és a lab-ssh1 hostnév látható, jelszó megadása nélkül. Ha hibát kapunk, a 700/600 jogosultságokat kell ellenőrizni.

4. Biztonsági mentés és új konfigurációs fájl létrehozása

A sshd_config változtatása előtt készítsünk mentést, és olyan include-ot használjunk, amelyet könnyen el lehet távolítani. A labhoston, konzolos session-ben:

# target: lab-ssh1 (konzol), account: labops (UID 1001), privilege: sudo
sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.labbackup
sudo mkdir -p /etc/ssh/sshd_config.d

Hozzuk létre a /etc/ssh/sshd_config.d/99-lab-hardening.conf fájlt:

# target: lab-ssh1 (konzol), account: labops (UID 1001), privilege: sudo
sudo tee /etc/ssh/sshd_config.d/99-lab-hardening.conf > /dev/null <<'EOF'
# Lab hardening d102
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
PubkeyAuthentication yes
AllowUsers labops
AllowGroups lab-admins
EOF

A AllowGroups lab-admins csak akkor működik, ha a labops user tagja a lab-admins csoportnak. Ellenőrizzük: id labops.

5. Konfiguráció szintaktikai ellenőrzése

Mielőtt újratöltjük a szolgáltatást, a sshd -t parancs ellenőrzi a konfigurációt. Ez nem változtatja meg a futó sshd állapotát:

# target: lab-ssh1 (konzol), account: labops (UID 1001), privilege: sudo
sudo sshd -t

Várható kimenet: nincs kimenet, a visszatérési érték 0. Ha hibát kapunk, a kimenet tartalmazza a fájlnevet és sorszámot.

6. Újratöltés a meglévő session-ök megszakítása nélkül

A systemctl reload ssh (vagy Ubuntu-n ssh.service) SIGHUP-ot küld a sshd-nek, amely újraolvassa a konfigurációt anélkül, hogy a meglévő session-öket megszakítaná:

# target: lab-ssh1 (konzol), account: labops (UID 1001), privilege: sudo
sudo systemctl reload sshd

Ellenőrizzük a szolgáltatás állapotát és a jelenlegi effektív beállításokat:

# target: lab-ssh1 (konzol), account: labops (UID 1001), privilege: sudo
systemctl is-active sshd
sudo sshd -T | grep -E '^(passwordauthentication|pubkeyauthentication|permitrootlogin|allowusers|allowgroups|kbdinteractiveauthentication)'

Várható kimenet: a passwordauthentication no, pubkeyauthentication yes, permitrootlogin no, allowusers labops, allowgroups lab-admins.

7. Hozzáférésellenőrzés a workstationről

Új kapcsolatot indítunk a workstationről. A jelszavas belépésnek most el kell utasítania, a kulcsosnak pedig sikerülnie kell:

# target: labws.lab.internal, account: devuser (UID 1000), privilege: none
# kulcsos belépés: sikeres
ssh -o PreferredAuthentications=publickey -o BatchMode=yes labops@lab-ssh1 'echo OK'
# jelszavas kísérlet: elutasított
ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no -o BatchMode=yes labops@lab-ssh1 'echo ERR'

A jelszavas kísérlet várhatóan Permission denied (publickey,password) hibát ad, és nem kéri a jelszót, mert a BatchMode=yes miatt nem próbálkozik interaktívan.

8. Naplózás ellenőrzése

A sikeres és sikertelen autentikációs események a journald-ben láthatók:

# target: lab-ssh1 (konzol), account: labops (UID 1001), privilege: sudo
sudo journalctl -u ssh -n 50 --no-pager | tail

Rollback (ha kizárnánk magunkat): Ha a workstationről már nem tudunk belépni, a konzolos hozzáférés továbbra is él. A rollback a 99-lab-hardening.conf eltávolításával vagy a mentett sshd_config visszaállításával történik:

# target: lab-ssh1 (konzol), account: labops (UID 1001), privilege: sudo
sudo rm /etc/ssh/sshd_config.d/99-lab-hardening.conf
# vagy teljes visszaállítás:
# sudo cp /etc/ssh/sshd_config.labbackup /etc/ssh/sshd_config
sudo sshd -t && sudo systemctl reload sshd

Ezután a jelszavas belépés újra működik, és a hiba okát lehet diagnosztizálni.

21.2.3 Gyakori hibák és ellenpróbák

Tünet: A kulcsos belépés még a jelszó kikapcsolása előtt sem működik; a szerver Permission denied (publickey) hibát ad.

Hipotézis: A ~/.ssh/authorized_keys fájl jogosultsága nem megfelelő, vagy a kulcs nem pontosan került be.

Adatgyűjtés: A szerver oldalán ellenőrizzük a naplót: journalctl -u ssh -f, és a sshd -T kimenetét. A kliens oldalán: ssh -vvv labops@lab-ssh1. A kliens verbose kimenete megmutatja, hogy a szerver elfogadta-e a publikus kulcsot.

Egy változtatás: Ellenőrizzük és állítsuk be a fájl jogosultságát:

# target: lab-ssh1 (konzol), account: labops (UID 1001), privilege: sudo
sudo chmod 700 ~labops/.ssh
sudo chmod 600 ~labops/.ssh/authorized_keys
sudo chown -R labops:labops ~labops/.ssh

Az sshd_config StrictModes yes beállítása miatt a túl engedékeny jogosultságú fájlokat az sshd figyelmen kívül hagyja. Ezután a kapcsolatot újra teszteljük.

Verification: ssh -o PreferredAuthentications=publickey -o BatchMode=yes labops@lab-ssh1 'id' sikeres.

Tünet: A frissítés után REMOTE HOST IDENTIFICATION HAS CHANGED! hibaüzenet.

Hipotézis: A szerver host key-je valóban megváltozott (pl. a VM-et újraépítették), vagy a felhasználó tévesen egy másik géphez csatlakozik.

Adatgyűjtés: Ellenőrizzük a szerveren a jelenlegi host key ujjlenyomatát:

# target: lab-ssh1 (konzol), account: labops (UID 1001), privilege: sudo
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

A kliens oldalán a ~/.ssh/known_hosts sorban hasonlítsuk össze a bejegyzést. Ha a szerver ujjlenyomata eltér, a host key valóban változott.

Egy változtatás: Ha a változás jogos (pl. lab rebuild), a régi bejegyzést távolítsuk el a kliens known_hosts-ból, és manuálisan fogadjuk el az új host key-t. Ne kapcsoljuk ki globálisan a StrictHostKeyChecking ellenőrzést:

# target: labws.lab.internal, account: devuser (UID 1000), privilege: none
ssh-keygen -R lab-ssh1
ssh -o StrictHostKeyChecking=ask labops@lab-ssh1

A kapcsolat létrejöttekor ellenőrizzük a megjelenő ujjlenyomatot a szerveren mért értékkel.

Verification: Az új known_hosts bejegyzés a szerver ujjlenyomatát tartalmazza, és a későbbi kapcsolatok figyelmeztetés nélkül működnek.

Tünet: SSH agent forwarding (ForwardAgent yes vagy ssh -A) használata közben a bastion hoszton egy másik felhasználó el tudja lopni a privát kulcsot.

Hipotézis: Az agent socket hozzáférhető egy másik, a bastionon futó felhasználó számára, mert a SSH_AUTH_SOCK Unix socket nem elég védett.

Ellenpróba: Soha ne engedélyezzük az agent forwardingot olyan köztes hoszton, amelyben nem bízunk teljesen. Helyette használjunk ProxyJump-ot (-J), amely a kliensen tartja az agentet, és a bastion csak továbbítja a kapcsolatot:

# target: labws.lab.internal, account: devuser (UID 1000), privilege: none
ssh -J labops@bastion.lab.internal labops@internal.lab.internal

Ezt a szerver oldalán a AllowAgentForwarding no beállítással is meg lehet akadályozni, ha a bastionon nincs szükség rá.

21.2.4 Feladatok

  1. Magyarázó feladat: Magyarázd el, mi a különbség a ~/.ssh/known_hosts és a ~/.ssh/authorized_keys szerepe között. Melyik fájlban milyen kulcs található, és miért nem cserélhetők fel? Milyen tulajdonosi és jogosultsági követelmények vonatkoznak az authorized_keys-re?

  2. Adminisztrációs feladat: A labhoston az Include segítségével hozz létre egy 90-lab-access.conf fájlt a sshd_config.d könyvtárban, amely:

    • csak a lab-admins csoport tagjainak enged SSH-belépést,
    • letiltja a root bejelentkezést,
    • letiltja a jelszavas autentikációt,
    • a maximális autentikációs kísérletszámot 2-re állítja. Ellenőrizd sshd -t-vel, töltsd újra a sshd-t, és a sshd -T kimenetével igazold a beállításokat. Ne felejtsd el a konzolos visszaút meglétét.

  3. Diagnosztikai/failure feladat: Egy kolléga azt jelenti, hogy a lab-ssh1-re nem tud bejelentkezni, mert a kliens REMOTE HOST IDENTIFICATION HAS CHANGED! hibát ad. A szerver nem változott; a host key ugyanaz, mint tegnap. Diagnosztizáld, mi lehet az oka, és állítsd helyre a hozzáférést anélkül, hogy globálisan letiltanád a host key ellenőrzést. (Tipp: nézd meg a known_hosts bejegyzést, az esetleges IP/hostname változást, vagy a HashKnownHosts beállítást.)

21.2.5 Megoldások

1. feladat megoldása

A ~/.ssh/known_hosts a kliens oldalon tárolja a már elfogadott szerver host keyeket. Ez bizonyítja, hogy a kliens ugyanahhoz a szerverhez csatlakozik, mint korábban. A ~/.ssh/authorized_keys a szerver oldalon tárolja a felhasználói publikus kulcsokat; ezek bizonyítják, hogy a kapcsolódó kliens a felhasználó privát kulcsát birtokolja.

Nem cserélhetők fel: a known_hosts tartalma nem engedélyez belépést, és a authorized_keys tartalma nem hitelesíti a szervert. A authorized_keys tulajdonosa a felhasználó, a jogosultságok: a ~/.ssh könyvtár 700 (tulajdonos ír/olvas/végrehajt, más semmi), a authorized_keys 600 (tulajdonos ír/olvas, más semmi). Ha a group/other is tudja írni, az sshd a StrictModes yes miatt elutasítja a kulcsot.

2. feladat megoldása

# target: lab-ssh1 (konzol), account: labops (UID 1001), privilege: sudo
sudo tee /etc/ssh/sshd_config.d/90-lab-access.conf > /dev/null <<'EOF'
# Lab access policy d102
AllowGroups lab-admins
PermitRootLogin no
PasswordAuthentication no
MaxAuthTries 2
EOF
sudo sshd -t && sudo systemctl reload sshd
sudo sshd -T | grep -E '^(allowgroups|permitrootlogin|passwordauthentication|maxauthtries)'

Várható kimenet:

allowgroups lab-admins
permitrootlogin no
passwordauthentication no
maxauthtries 2

Postcondition: A labops user, ha tagja a lab-admins csoportnak, kulccsal be tud lépni; a jelszavas bejelentkezés és a root login elutasított; a sshd konfiguráció szintaktikailag érvényes és aktív; a meglévő session-ök nem szakadtak meg. A rollback a fájl törlésével és sudo sshd -t && sudo systemctl reload sshd futtatásával érhető el.

3. feladat megoldása

A REMOTE HOST IDENTIFICATION HAS CHANGED! akkor is fellép, ha a known_hosts-ban ugyanaz a hostname, de a bejegyzés IP-címe vagy hostkey-típusa megváltozott, vagy ha a kliens known_hosts-át hash-olással tárolták, és a hostname már nem egyezik pontosan. A diagnózishoz hasonlítsuk össze a szerveren lévő host key-t a kliens known_hosts-ban találhatóval:

# target: lab-ssh1 (konzol), account: labops (UID 1001), privilege: sudo
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

A kliens known_hosts-ban keressük a bejegyzést:

# target: labws.lab.internal, account: devuser (UID 1000), privilege: none
ssh-keygen -F lab-ssh1

Ha a hostkey ujjlenyomat megegyezik, de az IP-cím vagy a hostname eltér (például a DNS-ben megváltozott az IP), a bejegyzést frissíteni kell. A biztonságos eljárás: távolítsuk el a régi bejegyzést, majd új kapcsolat létrehozásakor ellenőrizzük az ujjlenyomatot:

# target: labws.lab.internal, account: devuser (UID 1000), privilege: none
ssh-keygen -R lab-ssh1
ssh -o StrictHostKeyChecking=ask labops@lab-ssh1

Ha a hostkey ujjlenyomat tényleg eltér, és a szerveren nincs változás, akkor a kliens oldali known_hosts bejegyzés sérült vagy rossz hostnévre mutat. Ekkor is ugyanaz a javítás: a régi bejegyzés törlése és új, ellenőrzött elfogadás. Soha ne használjunk StrictHostKeyChecking=no vagy UserKnownHostsFile=/dev/null beállítást, mert az teljesen kikapcsolja a host trust ellenőrzést. Postcondition: a kliens ismét tud csatlakozni, a known_hosts bejegyzés a jelenlegi host key-t tartalmazza, és a host key-ellenőrzés érintetlen marad.

21.2.6 Rövid összefoglaló

Az OpenSSH két független bizalmi réteggel dolgozik: a host key a szerver azonosságát igazolja a kliensnek, a user key a belépő személy azonosságát a szervernek. A known_hosts a kliens oldali szerver-ujjlenyomat cache, a authorized_keys a szerver oldali engedélyezett publikus kulcsok listája. Minden sshd_config változtatás előtt végezd el a sshd -t ellenőrzést, és maradjon konzolos visszaút. A config include-oknál az OpenSSH az első megadott értéket használja, ezért a sorrendet a distribúció dokumentációjában ellenőrizni kell. Definíciók: host key = szerver azonosság bizonyítéka; user key = felhasználó azonosság bizonyítéka; sshd -t = konfiguráció szintaktikai ellenőrzés.
