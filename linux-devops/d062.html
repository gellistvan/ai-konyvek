13.2 Stream, pipe, redirection és process exit

13.2.1 Motiváció

A Unix shell nem csupán interaktív parancsbeíró: a folyamatok közötti adatcsatorna- és hibakezelési modell. Szenior C++ fejlesztőként a std::cin, std::cout, std::cerr, illetve a fork/exec/wait ismerős lehet, de a shell eltérően kezeli a hibaterjedést, az átmeneti fájlokat és a folyamatok élettartamát. Egy adminisztrációs pipeline például journalctl | grep ERROR | wc -l lehet; ha a grep nem talál semmit, a pipeline exit kódja alapértelmezés szerint a wc 0-ja, nem a grep 1-je. A hibás exit kód elrejtése éles automatizálásban hamis sikerhez vezet. Ebben az alfejezetben az FD-átirányítást, a pipe-ot mint byte streamet, a redirect sorrendet, az exit status és pipefail kezelést, valamint a subshell, environment és signal/timeout kérdéseket járjuk körül.

13.2.2 Definíció és működés

13.2.2.1 FD, stdin/stdout/stderr és dup2

Minden Linux processz egy fájlleíró-táblával (file descriptor table) indul. A Unix-konvenció szerint az első három FD a shell által megnyitott elemi csatorna:

  • 0 stdin: bemenet,
  • 1 stdout: normál kimenet,
  • 2 stderr: hibakimenet, gyakran nem pufferelt, de ez programspecifikus.

A fork-olás után a gyermekprocessz örökli ezeket az FD-ket; az exec pedig megtartja, kivéve ha FD_CLOEXEC zászló van beállítva. A shell redirection valójában nyit egy fájlt, majd dup2()-vel az adott FD-t átirányítja. A C++ std::cout a libc szintjén a 1-es FD-re ír; ezért a shell > operátora közvetlenül hat a C++ programunk kimenetére anélkül, hogy a programnak tudnia kellene róla.

A lehetséges redirection szintaxis:

  • cmd > file – stdout truncate + írás,
  • cmd >> file – stdout append,
  • cmd 2>&1 – a 2-es FD-t duplikáljuk az 1-es FD aktuális nyitott állapotára,
  • cmd < file – stdin fájlból.

A set -o noclobber megakadályozza, hogy > létező fájlt felülírjon; ez interaktív védelem, de scriptekben explicit kontroll kell.

13.2.2.2 Pipe mint byte stream

A | operátor a kernel pipe() hívására épül. Ez egy anonim, egyirányú byte stream: nincs üzenethatár, nincs rekord, nincs garancia arra, hogy az író egy write()-ja ugyanolyan darabban érkezik az olvasóhoz. Ez ugyanaz a modell, mint egy TCP socket stream: az alkalmazásnak magának kell határokat képeznie, például sorvégekkel.

A shell a pipe bal oldalát a pipe íróvégére, a jobb oldalát az olvasóvégére köti. Ha az olvasó kilép, a következő írás a bal oldalon SIGPIPE jelet kap; a default action a processz terminálása. Ez a head-es gyakori leállás: yes | head -n 1 leállítja a yes-t, pedig az „végtelen” streamet írna. A yes halálát a SIGPIPE okozza, nem a head kilépése maga.

A pipe buffer mérete kernelverziófüggő (általában 64 KiB lehet Linuxon, de ne építsünk rá); ha az olvasó lassú, az író blokkol. Ez backpressure, nem várakozási sor a shell szintjén.

13.2.2.3 Redirect sorrend és overwrite/append

A redirect parancsok sorrendje a shellben balról jobbra hajtódik végre. Ez a leggyakoribb adminhiba forrása:

# Helytelen szándék: "stderr is menjen az out.log-ba"
app 2>&1 > /tmp/out.log

Feldolgozás:

  1. 2>&1 duplikálja a 2-es FD-t az 1-es FD aktuális állapotára – ami ekkor még a terminál,
  2. > /tmp/out.log átirányítja az 1-es FD-t a fájlra.

Eredmény: stdout a fájlba megy, de stderr a terminálra. Helyes sorrend:

app > /tmp/out.log 2>&1

Itt előbb az 1-es FD-t irányítjuk a fájlra, majd a 2-est duplikáljuk arra a fájlra. Általános elv: előbb nyisd meg a célt, utána duplikálj.

Az append (>>) nem csonkol, hanem a fájl végére ír. A > truncate-et végez nyitáskor; ha ugyanabba a fájlba írunk stderrrel is, a sorrend miatt fontos, hogy a >-t egyszer értékeljük ki. Például:

app >> /tmp/out.log 2>> /tmp/err.log

Két külön FD nyílik, mindkettő appendelve.

13.2.2.4 Exit status, pipefail és PIPESTATUS

Minden processz egy 8 bites exit kóddal tér vissza (0–255); a shellben a $? az utolsó parancs exit code-ja. A konvenció: 0 siker, nem nulla hiba. Ez nem azonos a C++ main() int visszatérési értékének teljes tartományával: a shell szinten a 8 bit marad, így -1 255-re kerekedik.

Alapértelmezés szerint a pipeline exit code-ja a jobb szélső parancsé. Ez a fent említett hamis siker oka. Bashben két eszköz van:

  • set -o pipefail: a pipeline exit code a legnagyobb nem nulla jobb oldali exit code; ha mind nulla, akkor 0.
  • PIPESTATUS: egy Bash tömb, amely az előző pipeline minden tagjának exit code-ját tartalmazza.

Példa:

cat /tmp/nemletezik | grep -c 'x'
echo "exit=$? PIPESTATUS=${PIPESTATUS[*]}"

Alapértelmezés szerint az exit 0 lesz, mert a grep -c rendben lefutott. pipefail bekapcsolása után a cat 1-es hibája lesz a pipeline eredménye. Scriptekben érdemes set -o pipefail-t használni, de nem minden shell támogatja; a POSIX sh nem. Ubuntu Server 24.04 LTS labhoston a Bash az interaktív shell, de a /bin/sh dash. A hordozható automatikus scriptek #!/bin/bash shebanggel induljanak, ha Bash jellemzőt használnak.

13.2.2.5 Subshell, environment és export

Bashben a pipeline tagjai alapértelmezés szerint subshell-ben futnak (kivéve a lastpipe beállítást, ami csak a jobb oldali utolsó parancsot futtathatja a fő shellben). Ez azt jelenti, hogy a változók a subshellben lokálisak; a pipeline után a fő shellben nem látjuk a módosításukat:

count=0
printf 'a\nb\n' | while read -r line; do count=$((count+1)); done
echo "count=$count"   # még mindig 0

Ez a szokásos adminhiba. A while read hurok subshellben fut, így a count növelése nem jut vissza. Megoldás: process substitution (< <(...)) vagy a feldolgozást áthelyezni a subshellen belülre, például printf 'a\nb\n' | { while read -r line; do ...; done; echo "$count"; }.

Az export VAR=value a változót a gyermekprocesszek környezetébe helyezi. A sima VAR=value csak a shell saját változója; a gyermek nem látja. Az env VAR=value cmd egyetlen parancsra szóló environment-et ad anélkül, hogy a shell környezetét szennyezné. Ez hasonló a execve envp argumentumához, amit C++-ban setenv()/unsetenv() hívásokkal állítunk.

13.2.2.6 Signal/timeout és pipeline shutdown

A pipe szétválasztásakor a SIGPIPE a gyakori leállító jel. Ezt a shell yes | head -n 1 esetben a yes kapja. A pipeline minden tagja ugyanabban a process groupban lehet, ha a shell job-controlt használ; de a timeout utility a megadott idő után először SIGTERM-et küld a parancsnak (vagy -k opcióval SIGKILL-t). A timeout exit code 124, ha lejárt az idő, 125 ha maga a timeout hibázott, 126 ha a parancs nem futtatható, 127 ha nem található. Ez fontos a pipeline-ban: a timeout csak a közvetlen parancsot állítja le; ha a pipeline másik tagja tovább fut, a shell a pipeline exit code-ját a jobb szélsőből számítja, ezért a pipefail vagy a PIPESTATUS itt is szükséges a pontos diagnózishoz.

13.2.3 Kidolgozott példa

Tegyük fel, hogy a labhost1 Ubuntu 24.04 LTS gépen (devops felhasználó, UID 1000) egy diagnosztikai feladatot végzünk: meg akarjuk számolni, hány ERROR sor van a /var/tmp/demo-errors.txt fájlban, és a hibákat külön logba írjuk. A fájl nem létezik, ezzel szimuláljuk a pipeline hibáját. A target: labhost1, account devops, privilegizálatlan. Előfeltétel: a d061 shell parsing ismert, az FD fogalom d039-ből ismert. A módosító parancs a /tmp alatt létrehoz egy fájlt, ez rollbackszel törölhető.

# target: labhost1, UID 1000, /tmp
# előfeltétel: /tmp írható, bash 5.x
cat /var/tmp/demo-errors.txt 2>/tmp/demo-stderr.log | grep -c 'ERROR' > /tmp/demo-count.txt
echo "exit=$? pipestatus=${PIPESTATUS[*]}"
echo "stderr_file:"; cat /tmp/demo-stderr.log
echo "count_file:"; cat /tmp/demo-count.txt

Várt kimenet (illusztratív, nem mért):

exit=0 pipestatus=1 0
stderr_file:
cat: /var/tmp/demo-errors.txt: No such file or directory
count_file:
0

A grep -c 0-t írt a count fájlba és 0-val tért vissza (a -c 0 találatnál is 0 exit code, ha a bemenet olvasható; a cat 1-gyel hibázott). Ez a hamis siker: a pipeline exit=0, pedig a bemeneti fájl nem létezett. Helyes diagnózis:

set -o pipefail
cat /var/tmp/demo-errors.txt 2>/tmp/demo-stderr.log | grep -c 'ERROR' > /tmp/demo-count.txt
status=$?
echo "exit=$status pipestatus=${PIPESTATUS[*]}"

Várt kimenet: exit=1 pipestatus=1 0. A pipefail feltárja a cat hibát. Az ellenőrzési feltétel: [[ $status -eq 0 ]] sikert jelez, itt status=1. A rollback: rm -f /tmp/demo-stderr.log /tmp/demo-count.txt.

Egy másik példa a redirect sorrendre:

( echo stdout; echo stderr >&2 ) 2>&1 > /tmp/demo-redir.log

Várt kimenet: a terminálon stderr, a /tmp/demo-redir.log tartalma stdout.

13.2.4 Hibák és ellenpróbák

1. hiba: Redirect sorrend felcserélése. Tünet: a stderr üzenetek a terminálon jelennek meg, hiába vártuk a fájlban. Hipotézis: a 2>&1 előbb lett kiértékelve, mint a > cél. Adatgyűjtés: strace -e trace=dup2,openat bash -c '...' mutatja a dup2 hívások sorrendjét. Egy változtatás: a > cél elé helyezzük a 2>&1-et. Ellenőrzés: futtassuk újra, és a fájl tartalma a várt.

2. hiba: Pipeline hamis siker. Tünet: a script 0-át ad vissza, pedig a cat hibát írt. Hipotézis: alapértelmezett pipeline exit a jobb szélső. Adatgyűjtés: PIPESTATUS tömbbel. Egy változtatás: set -o pipefail a script elején. Ellenőrzés: $? most nem nulla, ha bármely tag hibázik.

3. hiba: Subshell változó elveszik. Tünet: a count változó nem nő. Hipotézis: a pipeline subshellt indít. Adatgyűjtés: printf 'a\nb\n' | while read -r line; do count=$((count+1)); done; echo "count=$count" 0-t mutat. Egy változtatás: process substitution while ...; done < <(printf 'a\nb\n') vagy a teljes feldolgozás a pipeline-on belül. Ellenőrzés: a változó látható.

4. hiba: timeout exit kód téves értelmezése. Tünet: a pipeline $? 124, de a felhasználó a jobb oldali parancs hibájára gyanakszik. Hipotézis: a timeout lejárt. Adatgyűjtés: echo "${PIPESTATUS[*]}" megmutatja a 124-et a timeout tagban. Egy változtatás: növeljük az -s jelváltást vagy a timeout értéket, és ellenőrizzük, hogy a tag kilép-e.

13.2.5 Feladatok

13.2.5.1 1. feladat – Magyarázó (15 perc)

Magyarázza el, mi a különbség az alábbi két parancs hatása között, ha a terminálra és fájlba írunk:

( echo out; echo err >&2 ) 2>&1 > /tmp/f1.log
( echo out; echo err >&2 ) > /tmp/f2.log 2>&1

Adja meg, mi jelenik meg a terminálon, és mi a /tmp/f1.log illetve /tmp/f2.log tartalma. Kövesse nyomon az FD-k állapotát a redirect kiértékelés után.

13.2.5.2 2. feladat – Adminisztrációs script (20 perc)

Készítsen egy /usr/local/bin/lab-log-error-count nevű Bash scriptet a labhost1 gépen (UID 0 szükséges a telepítéshez). A script kapjon egy logfájl-argumentumot, és írja ki az ERROR sorok számát. A script:

  • set -o pipefail-t használ,
  • grep -c 'ERROR' "$1"-et futtat,
  • ha a grep nem talál, az exit code 0 legyen, de a count 0-t írjon a stdoutra,
  • ha a bemeneti fájl nem olvasható, exit code 2 és hibaüzenet a stderrre.

Ellenőrizze a scriptet lab-log-error-count /nonexistent és egy létező fájllal. Adja meg a postconditiont és a rollbacket.

13.2.5.3 3. feladat – Diagnosztikai pipeline (25 perc)

A következő pipeline lefut, de a count változó 0 marad, holott két sor van a bemenetben:

count=0
printf 'a\nb\n' | while read -r line; do count=$((count+1)); done
echo "count=$count"

Diagnosztizálja a jelenséget, és javítsa két különböző módszerrel: process substitution használatával, valamint a feldolgozás subshellben tartásával (a teljes ciklus zárójelen belül, és ott írjuk ki a countot). Futtassa a javított változatokat, és igazolja a count=2 értéket. Adja meg, milyen más shellben (dash) miért nem működne a process substitution.

13.2.6 Megoldások

13.2.6.1 1. feladat megoldása

Első parancs: ( echo out; echo err >&2 ) 2>&1 > /tmp/f1.log

  • 2>&1 kiértékelődik először: a 2-es FD a terminálra mutat (az 1-es FD aktuális állapota).
  • > /tmp/f1.log az 1-es FD-t a fájlra irányítja.

Eredmény: stdout a fájlra megy, stderr a terminálra.

  • Terminálon: err
  • /tmp/f1.log: out

Második parancs: ( echo out; echo err >&2 ) > /tmp/f2.log 2>&1

  • > /tmp/f2.log először: 1-es FD a fájlra.
  • 2>&1 másodszor: 2-es FD duplikálva a fájlra.

Eredmény: mindkettő a fájlra.

  • Terminálon: semmi
  • /tmp/f2.log: out és err

Postcondition: a fájlok tartalma a fenti. Rollback: rm -f /tmp/f1.log /tmp/f2.log.

13.2.6.2 2. feladat megoldása

A script:

#!/bin/bash
set -o pipefail

logfile="${1:?usage: $0 LOGFILE}"
if [[ ! -r "$logfile" ]]; then
  echo "$0: cannot read '$logfile'" >&2
  exit 2
fi

count=$(grep -c 'ERROR' "$logfile")
status=$?

if (( status == 1 )); then
  # grep exit 1: no match, count is 0
  echo "0"
  exit 0
elif (( status == 0 )); then
  echo "$count"
  exit 0
else
  echo "$0: grep failed on '$logfile'" >&2
  exit "$status"
fi

Postcondition: siker esetén a script stdoutra írja a countot, az exit code 0; ha a fájl nem olvasható, exit 2; ha más hiba, a grep hibakódja. Telepítés: sudo install -m 0755 lab-log-error-count /usr/local/bin/lab-log-error-count (labhost1, root). Ellenőrzés: /usr/local/bin/lab-log-error-count /nonexistent; várt stderr hiba, exit 2. Egy létező, nulla ERROR sorú fájl esetén stdout 0, exit 0. Egy hibás fájl esetén (pl. grep crash) exit 2.

Rollback: sudo rm /usr/local/bin/lab-log-error-count.

13.2.6.3 3. feladat megoldása

A hiba oka: a pipeline jobb oldala (while read) subshellben fut, ezért a count növelés a subshell saját változóját érinti; a szülő shell count változója változatlan.

Javítás 1 (a feldolgozás a subshellben marad):

count=0
printf 'a\nb\n' | {
  while read -r line; do count=$((count+1)); done
  echo "count=$count"
}

Itt a { ... } mind a pipeline része, ugyanabban a subshellben fut; a count kiírása a subshellben történik, count=2.

Javítás 2 (process substitution):

count=0
while read -r line; do count=$((count+1)); done < <(printf 'a\nb\n')
echo "count=$count"

A process substitution a printf kimenetét egy FIFO-n vagy /dev/fd-n keresztül adja a while stdinjeként; maga a while a fő shellben fut, így a count módosítás megmarad. Postcondition: count=2 mindkét esetben. Dash shellben a process substitution (<(...)) nem támogatott, ezért ott a javítás 1 vagy átmeneti fájl használandó.

13.2.7 Rövid összefoglaló

A Unix rendszerben az FD 0/1/2 a standard be- és kimeneti csatornák; a redirection a shell dup2 szintű FD-manipulációja, ahol a sorrend balról jobbra érvényes. A pipe anonim byte stream, nincs üzenethatár; ha az olvasó bezár, az író SIGPIPE jelet kap. A pipeline alapértelmezés szerint a jobb szélső parancs exit code-ját adja; a pipefail és a PIPESTATUS a teljes pipeline hibadiagnózisát teszi lehetővé. A pipeline tagjai subshellben futnak, ezért a változók nem kerülnek vissza; az export a gyermekprocesszek környezetét határozza meg. A timeout a szabályozott pipeline leállítást ad, de a kódjait külön kell értelmezni. A továbbhasznált definíciók: pipefail, PIPESTATUS, subshell.
