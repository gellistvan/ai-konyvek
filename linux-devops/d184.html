37.4 SBOM, scanning, aláírás és build titkok

37.4.1 Motiváció

A konténerimage nem egyszerűen „lefordított program letöltve egy registryből”; a build output egy hosszú distribution lánc végpontja, amelyben forrás, buildkörnyezet, függőségek, hitelesítő adatok és futtató platform is részt vesz. Ha egy image fut, az azt jelenti, hogy a benne lévő csomagok, natív libraryk, configfájlok és beállítások a hoszttól elválasztott, de a processz erőforrásait és hálózati képességeit használó környezetben hajtódnak végre. Egy C++ szolgáltatásnál a statikusan vagy dinamikusan linkelt libraryk, a build során letöltött tarballok, a build argumentumok, sőt a Dockerfile soraiban használt titkok is bekerülhetnek az artifactba anélkül, hogy a végző fejlesztő ezt észrevenné.

Ebben az alfejezetben a build input és artifact proof szerepét foglaljuk security szerződésbe: mit tudunk állítani arról, miből készült az image, milyen ismert sebezhetőséget tartalmaz, hitelesen készült-e, és hogy build titkai nem kerültek rétegbe, metadatába vagy környezeti változóba. A cél nem valamely scanner termék felhasználói kézikönyvének ismertetése, hanem az a rendszerszemlélet, amely egy scanning találatot üzemeltetési döntéssé tud alakítani: azonnal blokkol, kivételt ad, rebuildet ír elő, vagy kompenzáló vezérlést alkalmaz a futtatókörnyezetben.

37.4.2 Definíció és működés

Az image security contractot három kérdés köré szervezzük:

  1. Miből áll az image? Erre az SBOM (Software Bill of Materials) ad választ, amely csomag- és komponensszintű nyilvántartást jelent. Az image rétegekben tárolt tartalmát a készítő eszköznek kell transzparens listaként elérhetővé tennie, nem pedig a futás közbeni találgatásnak.
  2. Milyen ismert hibái vannak? A CVE-scan az SBOM-ban szereplő komponensek verzióját veti össze sebezhetőségi adatbázissal. A scanning azonban önmagában nem döntés; a találatot component support, exploitability, deployability és posture összefüggésében kell értékelni.
  3. Megbízom-e a forrásában és a buildben? A digest verification az OCI image tartalomra mutató kriptográfiai hashre támaszkodik, a signing és attestation pedig azt igazolja, hogy a build egy adott identity alatt, adott inputokból, adott lépésekkel futott.

37.4.2.1 SBOM package/component és artifact binding

Az SBOM akkor használható, ha egyértelmű kötése van az artifacthoz. A kötéshez rendelkeznünk kell legalább az alábbi azonosítókkal:

Fogalom Példaérték Mit köt
image name registry.example.com/lab/cpp-svc publikált név
tag v1.7.0 emberi hivatkozás, nem immutable
digest sha256:9f6c... image manifest tartalma
SBOM digest sha256:3ab2... SBOM dokumentum tartalma
git revision b6c49... forrásrevision
build-id f8d9... natív binary build hash

Az SBOM és az image közötti kapcsolat ne csak a registryben egymás mellett elhelyezett fájl legyen. Célszerű valamely attestation-formátumban a digestre hivatkozó, aláírt állítást készíteni. A minimálisan ellenőrizhető, még egyszerűbb kötés a digest megjelenítése a build logban, utána az image és az SBOM hashének újraszámítása a fogyasztói oldalon.

Példa SBOM-részlet (SPDX-töredék, illusztratív):

{
  "spdxVersion": "SPDX-2.3",
  "name": "cpp-svc-image-sbom",
  "documentNamespace": "https://registry.example.com/lab/cpp-svc/v1.7.0/sbom",
  "packages": [
    {
      "name": "glibc",
      "versionInfo": "2.39-0ubuntu8",
      "supplier": "Organization:Ubuntu",
      "downloadLocation": "https://archive.ubuntu.com/ubuntu/pool/main/g/glibc/"
    },
    {
      "name": "libstdc++6",
      "versionInfo": "14.0.2-1ubuntu2",
      "supplier": "Organization:Ubuntu"
    }
  ],
  "relationships": [
    {
      "spdxElementId": "SPDXRef-Image",
      "relationshipType": "CONTAINS",
      "relatedSpdxElement": "SPDXRef-Package-glibc"
    }
  ]
}

A fenti SBOM akkor válik artifact proofá, ha a documentNamespace vagy egy külön aláírt csomag rögzíti az image digestet. A puszta SBOM nem bizonyítja, hogy az adott SBOM ahhoz az imagehez tartozik; ezt a kötést a signing vagy a dataset ellenőrzése adja.

37.4.2.2 CVE scan, base image és support lifecycle

A CVE-scan tipikus forrása a distro security metadata (Ubuntu OVAL/USN, Debian Security Tracker, Red Hat OVAL). A scanner ezt veti össze az SBOM csomagverzióival, és High, Medium, Low, Critical besorolást készít. A besorolás azonban nem az adott image futására igaz; a kockázatot az alábbi dimenziók adják:

  • Support lifecycle: a csomag a distro által támogatott-e; ha igen, a backport javítás mely verzióban van.
  • Exploitability: a sebezhetőség eléréséhez milyen feltétel kell; például network-exposed, local, vagy csak egy nem használt codepath.
  • Deployability: a hibás komponens a ténylegesen futtatott binary és library halmazban részt vesz-e.
  • Posture: milyen kompenzáló vezérlés van élesben; például a container seccomp, network policy, read-only rootfs vagy a base image minimális felülete.

Egy másik gyakori tévedés a „distroless” feltételezés, hogy a kevés csomag kevés CVE-t jelent. A gyakorlatban a minimál image kiinduló felületet csökkent, de a natív binaryk, a language runtime és az ASan/UBSan, illetve a statikusan beépített protobuf, OpenSSL vagy zlib komponensek ugyanúgy követést igényelnek. C++-ban ez különösen fontos, mert egy -static build kihúzhatja a CVE listából a distro csomagot, de beépíti a libraryt a binarybe, ahol a scanner azt már nem látja.

37.4.2.3 Signing és digest verification

A digest verification azt ellenőrzi, hogy a letöltött manifest és rétegek a várt hashra állnak össze. A signing ezen túl azt igazolja, hogy a digestet egy adott identity hagyta jóvá. Használhatunk:

  • cosign-style keyless signing: az aláíró identity rövid életű tanúsítványhoz kötött, a build rendszer Workload Identity-jéből.
  • notary / notation
  • minimális, kézi példa: cosign sign és cosign verify jellegű parancsokkal, ahol az aláíró kulcs a build rendszerben él, nem a fejlesztő gépén.

A trust identity szempontjából az érték akkor jelenik meg, ha a fogyasztó nem az image puszta tagjét, hanem a várt aláíró identityt is ellenőrzi. A verify lépés outputjában megbízható, ha az aláíró tanúsítvány kibocsátóját és a subject identityt is ellenőrizzük.

Példa (cosign-szerű, illusztratív):

cosign verify \
  --certificate-identity "https://github.com/example/cpp-svc/.github/workflows/release.yml@refs/tags/v1.7.0" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
  registry.example.com/lab/cpp-svc:v1.7.0

A parancs akkor sikeres, ha az image digestjére adott aláírás ellenőrizhető, és a tanúsítvány identity feltételei teljesülnek. Ezt a lépést a deployment pipeline-ban kell végrehajtani, nem a fejlesztői gépen.

37.4.2.4 Build secrets és layer leak

A build secret leggyakoribb hibája, hogy ARG vagy ENV formában kerül a Dockerfile-ba, mert a BuildKit a környezeti változókat a rétegekben és a végleges image historyban is tárolhatja. A hagyományos docker build cache és az image layer history a következő szenzitív adatokat őrizheti meg: privát git token, .npmrc, Maven credentials, AWS key, SSH private key, database jelszó.

A megbízható mechanizmus a BuildKit secret mount:

# syntax=docker/dockerfile:1
FROM registry.example.com/lab/cpp-base:2.0.0 AS build
RUN --mount=type=secret,id=gitlab_ci_token \
    git clone https://oauth2:$(cat /run/secrets/gitlab_ci_token)@git.example.com/lab/cpp-svc.git .
RUN --mount=type=ssh \
    cmake --preset release && cmake --build build

A build meghívása:

DOCKER_BUILDKIT=1 docker build \
  --secret id=gitlab_ci_token,env=GITLAB_CI_TOKEN \
  --ssh default \
  --tag registry.example.com/lab/cpp-svc:v1.7.0 .

A --mount=type=secret a secretet rövid életű mountként adja a build lépéshez, és nem teszi bele a végleges image layerbe. Az id a Dockerfile-ban hivatkozott nevet, az env a build időben a gazdagépről származó környezeti változót jelöli. Az SSH mount hasonlóan a default SSH agent socketet vagy a megadott kulcsot mountolja, és a build után eltűnik.

Fontos ellenőrzés, hogy a titok valóban ne legyen a rétegben. A docker history és a docker inspect az image réteg metaadatait mutatja, de a layer tartalmát közvetlenül a réteg blob exportálásával tudjuk ellenőrizni:

docker save registry.example.com/lab/cpp-svc:v1.7.0 -o /tmp/cpp-svc.tar
tar -tf /tmp/cpp-svc.tar | head

Ez a parancs a teljes image tartalmat és manifestet menti; a hitelesítő adatok keresésére grep -R "token" /tmp/cpp-svc.tar vagy a rétegek kibontása utáni vizsgálat szolgál. A kiinduló ellenőrzést azonban a build gyártósornak kell elvégeznie, nem a mentés utáni kézi keresgélésnek.

37.4.2.5 Provenance és attestation előkép

A provenance azt írja le, hogyan készült az image: forrásrevision, build konfiguráció, parancs, bemeneti artifactok, build rendszer identity. Az attestation ezt aláírt formában teszi hozzáférhetővé. A legegyszerűbb élesben használható előkép:

Mező Példaérték
subject image digest
builder BuildKit
source revision b6c49...
source repo https://git.example.com/lab/cpp-svc
build invocation cmake --preset release && cmake --build build && ctest
builder identity GitHub Actions workflow
input digests base image digest, dependency tarball digest

Ennek gépi kontrolljaként a fogyasztó a CLI-ben tudja ellenőrizni a subject digest és a builder identity egyezését. A cosign verify-attestation vagy az SLSA-provenance formátum célzott parancsa ezt a tanúsítvány identityvel együtt vizsgálja. A d184 szintjén a cél az, hogy a build rendszer az image mellett legalább ezt a hat mezőt, és az image digestre utaló subject kötést hozza létre, valamint ennek az aláírt attestationnak a digestjét deployment előtt ellenőrizzék.

37.4.2.6 Vulnerability exception és rebuild response

A scanning outputot nem csak „van-e sebezhetőség” kérdésre redukáljuk. A folyamat:

  1. Detection: scanner riaszt és SBOM-package, CVE-azonosító, severity és fix version visszakereshető.
  2. Triage: a CVE support lifecycle, exploitability és deployability vizsgálata.
  3. Decision: ha a találat az image által nem érintett codepath-ban van, vagy az image posture kompenzálja, exception (kivétel) hozható létre; egyébként rebuildet indítunk.
  4. Exception registry: az exception legyen rögzített, dátumozott, és kötelezően tartalmazza az újraértékelés határidejét.
  5. Rebuild response: a fix image építése, tesztelése, rescan, signing, deployment, és a korábbi image digest letiltása, ha a registry policy ezt támogatja.

A döntési lépésben hasznos táblázat:

Találat típus Rebuild azonnal Exception indokolt Előfeltétel
network-reachable, RCE igen nem nincs
local privilege escalation igen ritkán nem érintett interface
DoS egy nem használt könyvtárban ha base image patch elérhető ha support matrix igazolja exception regisztráció
build-time-only tool CVE nem szükséges gyakran nem kerül az image outputba

Példa a rebuild response-ra:

# exception.yaml (illusztratív)
vulnerability_exception:
  cve: CVE-2025-12345
  package: libfakelib
  version_affected: "1.2.0"
  severity: High
  reason: "Component is build-time-only; not present in final runtime layer"
  evidence:
    sbom_lookup: "purl:pkg:deb/ubuntu/libfakelib@1.2.0?arch=amd64"
    runtime_layer_check: "not-found"
  expires: "2025-12-31"
  owner: "platform-security"

A kidolgozott példában egy lab környezetben ezt a teljes folyamatot egy C++ szolgáltatás image builden hajtjuk végre.

37.4.3 Kidolgozott példa

Cél: lab-cpp-svc image készítése BuildKit titokkezeléssel, SBOM csatolással, aláírással és scanninggel. A labhost neve lab-vm-01, a registry egy lokális, izolált registry.lab.example instance, az image név registry.lab.example/lab/cpp-svc, a tag v1.7.0.

Feltételezzük, hogy a GITLAB_CI_TOKEN egy rövid életű, lab-os git token; a build a lab-vm-01 gépen történik, ahol a Docker daemon BuildKit supportja engedélyezett.

  1. A build konfiguráció:
# syntax=docker/dockerfile:1
FROM registry.example.com/lab/cpp-base:2.0.0 AS build
WORKDIR /src

# Git token titkos mount, nem kerül a layerbe
RUN --mount=type=secret,id=gitlab_ci_token \
    git clone https://oauth2:$(cat /run/secrets/gitlab_ci_token)@git.lab.example/lab/cpp-svc.git .

RUN --mount=type=ssh cmake --preset release && cmake --build build && ctest --test-dir build

FROM registry.example.com/lab/cpp-runtime:2.0.0
COPY --from=build /src/build/cpp-svc /usr/local/bin/cpp-svc
USER labapp
ENTRYPOINT ["/usr/local/bin/cpp-svc"]
  1. A build parancs, amely a secret mountot a gazdagép GITLAB_CI_TOKEN környezeti változójából táplálja, SSH agent esetén --ssh default:
cd /src/lab/cpp-svc
DOCKER_BUILDKIT=1 docker build \
  --secret id=gitlab_ci_token,env=GITLAB_CI_TOKEN \
  --ssh default \
  --label org.opencontainers.image.source=https://git.lab.example/lab/cpp-svc \
  --label org.opencontainers.image.revision=b6c49... \
  --tag registry.lab.example/lab/cpp-svc:v1.7.0 .
  1. SBOM-export (illusztratív Syft-féle parancs, a tényleges eszköz verziója ellenőrizendő):
syft registry.lab.example/lab/cpp-svc:v1.7.0 \
  -o spdx-json > cpp-svc-sbom.spdx.json
  1. Scanning (illusztratív grype-féle parancs):
grype registry.lab.example/lab/cpp-svc:v1.7.0 \
  --output json > cpp-svc-scan.json
  1. Aláírás és ellenőrzés (cosign-szerű, illusztratív):
cosign sign --key cosign.key registry.lab.example/lab/cpp-svc:v1.7.0
cosign verify --key cosign.pub registry.lab.example/lab/cpp-svc:v1.7.0
  1. Secret leak ellenőrzése:
docker save registry.lab.example/lab/cpp-svc:v1.7.0 -o /tmp/cpp-svc.tar
tar -xOf /tmp/cpp-svc.tar | grep -c "gitlab_ci_token" || true

Várható kimenet: az SBOM legalább glibc, libstdc++6, cpp-svc és libssl komponenst sorol fel; a scan output not-vulnerable a cpp-svc komponensre, de high találatot adhat egy base image réteg libssl verziójára; a verify aláírás ellenőrzött; a grep nem talál titkot az image tarballban.

Hibajelenség: ha a secretet ARG GITLAB_CI_TOKEN formában adták volna át, a docker history mutatná a ARG sort és a rétegben a token megjelenne. Ha a scanning a cpp-svc binaryre nem ad eredményt, akkor a binary source provenance ismeretlen; ezt kell felderíteni a build artifactból.

Triage: a libssl high találat esetén megvizsgáljuk, hogy a fix már elérhető-e a base image új verziójában. Ha a fix a cpp-runtime:2.0.1 tagben van, a FROM sort erre kell módosítani, a buildet újra futtatni, rescanelni, aláírni, és a deploymentben az új digestet használni. Ha a találat build-time-only komponensre vonatkozik, exception regisztrálható a fenti sémával, feltéve, hogy a runtime layer ellenőrzés bizonyítja a hiányát.

37.4.4 Hibák és ellenpróbák

37.4.4.1 1. Tünet: a scanner nem lát semmit, de a base image ismerten elavult

A hibás feltételezés, hogy a scanner alapból minden réteget ismer. Ha a base image SBOM-ja hiányzik, vagy a distro security adatbázis nem friss, a scan vakon marad. Első lépés a base image saját SBOM-jának lekérése, a scanner adatbázis frissítése (grype db update jellegű parancs), és a binary által behúzott natív libraryk listázása:

ldd cpp-svc

Ha a cpp-svc statikus libraryt tartalmaz, a binary level scan külön lépést igényel; a réteg scanner önmagában hamisan negatív lehet.

37.4.4.2 2. Tünet: a secret nem látszik a docker historyban, de attól még a rétegben van

A docker history a layer létrehozó parancsát és metaadatát mutatja, nem a réteg tartalmát. Egy rosszul használt RUN --mount=type=cache vagy COPY beemelheti a secretet anélkül, hogy a history egyértelműen mutatná. Ellenőrzés: image tarball exportálás és réteg-blob kibontás utáni grep, vagy egy direkt secret-scanner a rétegen. A biztos javítás a secret mount alkalmazása, és a cache mount titokra soha nem irányulhat.

37.4.4.3 3. Tünet: az image digest ellenőrzött, de a deployment mégis fertőzött összetevőt futtat

A digest verification csak az artifact tartalmát rögzíti; ha a build input (base image, dependency tarball, git revision) nem volt ellenőrzött, a digest nem ment meg. A megoldás a bemeneti artifactok digest-records készítése, a provenance mezők kitöltése, és a build lépésben az input digestek ellenőrzése.

37.4.4.4 4. Tünet: a vulnerability exception örökre érvényben marad

A kivételt nem elég regisztrálni; lejárati dátummal és felelőssel kell ellátni. Ha a lejárat nincs bekötve a CI-ba, a kivétel hallgatólagosan éles marad. Ellenőrzés: az exception listát a deployment pipeline minden kiadás előtt újraértékeli, és a lejárt exception blokkol.

37.4.5 Feladatok

37.4.5.1 1. Magyarázó feladat

Adott egy scan output, amely CVE-2025-11111 azonosítót mutat a libfakelib csomagra High severityvel. A libfakelib a build image build-essential jellegű csomagja, és a végső runtime image ldd vizsgálata nem hivatkozza. Írd le, hogyan döntenél a rebuild vagy az exception között, és melyik két bizonyítékot kell a döntéshez beszerezni!

37.4.5.2 2. Adminisztrációs/konfigurációs feladat

Készíts Dockerfile-t és build parancsot, amely egy GITLAB_CI_TOKEN nevű titkot BuildKit secret mounttal ad át, a forrást klónozza, lefordít egy cpp-svc binaryt, és a titok a végleges imageben nem jelenik meg. Az image registry.lab.example/lab/cpp-svc:v1.8.0 néven készüljön, és a build argumentum a gazdagép GITLAB_CI_TOKEN környezeti változójából jöjjön.

37.4.5.3 3. Diagnosztikai/failure feladat

Egy CI pipeline a cosign verify lépésben meghiúsul, pedig a fejlesztő a saját gépén sikeresen ellenőrizte. A deployment log szerint a --certificate-identity feltétel nem teljesül. A pipeline ugyanazt az image taget húzza, mint a fejlesztő. Mi a legvalószínűbb ok, milyen adatot gyűjts, és milyen hibajavítást adsz?

37.4.6 Megoldások

37.4.6.1 1. Magyarázó feladat megoldása

A döntéshez először a package support lifecycle adatát kell lekérni: van-e a libfakelib fix verzió a distro security trackerben, és az image által használt verzió patch-elhető-e. Másodszor a runtime elérhetőség vagy exploitability bizonyítását kell beszerezni: a végső image rétegben a libfakelib fájl hiányát, vagy a ldd kimenetet, amely nem hivatkozza. Ha a csomag a végső image-ben nincs jelen, az exception indokolt, de rögzíteni kell a hiány bizonyítását és a kivétel lejáratát. Ha a libfakelib bármely futó binary által linkelt, azonnali rebuild szükséges a patchelt base image verzióval.

37.4.6.2 2. Adminisztrációs/konfigurációs feladat megoldása

Dockerfile:

# syntax=docker/dockerfile:1
FROM registry.lab.example/lab/cpp-base:2.0.0 AS build
WORKDIR /src
RUN --mount=type=secret,id=gitlab_ci_token \
    git clone https://oauth2:$(cat /run/secrets/gitlab_ci_token)@git.lab.example/lab/cpp-svc.git .
RUN cmake --preset release && cmake --build build && ctest --test-dir build
FROM registry.lab.example/lab/cpp-runtime:2.0.0
COPY --from=build /src/build/cpp-svc /usr/local/bin/cpp-svc
USER labapp
ENTRYPOINT ["/usr/local/bin/cpp-svc"]

Build:

DOCKER_BUILDKIT=1 docker build \
  --secret id=gitlab_ci_token,env=GITLAB_CI_TOKEN \
  --tag registry.lab.example/lab/cpp-svc:v1.8.0 .

Postcondition: a build sikeres, a docker save-elt image tarballban a gitlab_ci_token string nem található. A végső image nem tartalmazza a forráskópot, a titkot nem tartalmazza, és a USER nem root.

37.4.6.3 3. Diagnosztikai/failure feladat megoldása

A legvalószínűbb ok, hogy a pipeline-ban más a build identity, mint a fejlesztő gépén. A cosign verify a --certificate-identity feltételnek a build rendszer workload identityjét kell megadni, nem a fejlesztő azonosítóját. A hibakereséshez gyűjtsük a pipeline logját a cosign verify teljes hibakimenetével, valamint az image digestet a registryből (docker buildx imagetools inspect). Ellenőrizzük, hogy a tanúsítvány aláíró identity a build CI service accountjából származik-e. Javításként a pipeline-ban a valós identity értékét adjuk meg, például a GitLab CI runner workload identityjét (https://git.lab.example/lab/cpp-svc//.gitlab-ci.yml@refs/tags/v1.7.0) a subject mellett. A fejlesztői gépen történő sikeres verify nem bizonyítja a pipeline jogosultságát, mert a tanúsítvány subject identity eltérhet.

37.4.7 Rövid összefoglaló

A build input és artifact proof security szerződést teremt az image és a futtatókörnyezet között. Az SBOM a komponensek gépi nyilvántartását adja; a CVE-scan ezt support lifecycle, exploitability és deployability szempontból értékeli. A signing és digest verification a bizalmi identitást köti az image tartalomhoz, nem a puszta taghez. A build titkokat BuildKit secret mounttal kell átadni, mert a rétegek és a history megőrzik az ENV/ARG tartalmat. A provenance-attestation előkép a forrás és build identitást az artifact digesthez köti. A vulnerability exception csak dokumentált, lejárattal ellátott, bizonyítékkal alátámasztott döntés lehet; minden más eset rebuild response-t igényel.

Továbbhasznált definíciók: SBOM — egy artifact komponenseinek, csomagjainak és függőségeinek géppel olvasható jegyzéke, amely a digestkötéssel együtt válik artifact proofá; attestation — aláírt állítás, amely az artifact digestet a build bemenettel, folyamattal és identityvel köti össze; build secret — a build lépéshez szükséges hitelesítő adat, amelyet úgy kell átadni, hogy a végleges image layerben ne jelenjen meg.

37.4.8 Források és ellenőrzési hiányok

A hivatkozott források kiindulópontok; a tananyag nem állítja, hogy ezeket a generálás előtt ellenőrizték. Az aktuális szintaxis, a konkrét scanner/signing eszközverzió és a support matrix a lab környezetben ellenőrizendő.

  • Docker documentation
  • Open Container Initiative
  • Podman documentation
  • SLSA specification

Ellenőrzési hiány: a példákban használt Syft, Grype és Cosign-szerű parancsok pontos verziója, flagszintaxis és kimeneti séma a tananyag lab profiljában nem rögzített. Az Ubuntu 24.04 LTS csomagjaihoz tartozó CVE-adatbázis aktuális találatai nem képezik a jelen tananyag részét; a scanning és signing lépéseket a lab kibocsátó rendszernek a tényleges eszközverzióval kell reprodukálnia.
