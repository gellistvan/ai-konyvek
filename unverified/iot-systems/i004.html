3.1 A labor felállítása: Linux host, Docker, Zephyr, Mosquitto, Java

3.1.1 Motiváció

A TerraSense rendszer minden rétegét – eszköz, gateway, broker, backend, adatbázis, megjelenítés – olyan laborban fogjuk fejleszteni, amelyben nincs szükség valódi szenzorra vagy mikrovezérlőre. Ez két dolgot követel: a labor legyen reprodukálható, és az egyes eszközök helyettesíthetők legyenek konténerben vagy natív szimulációban futó megfelelőikkel. Ebben az alfejezetben felállítjuk a közös laborkörnyezetet Ubuntu 24.04-en, és minden komponenst egy-egy füstteszttel ellenőrzünk. Aki ezt egyszer végigcsinálja, a későbbi fejezetek laborjai azonnal futtathatók lesznek.

3.1.2 A laborkörnyezet felépítése

A labor négy fő pillére:

  1. Docker Engine + Compose v2 – a broker és a backend szolgáltatások konténeres futtatásához.
  2. Zephyr RTOS, west és Zephyr SDK – a ts-node firmware-jének fejlesztéséhez és a native_sim boardon való szimulációjához.
  3. Mosquitto MQTT broker – konténerben futó központi üzenetközvetítő.
  4. Java 21 + Maven + Python 3 – a backend fejlesztéséhez, illetve segédszkriptekhez.

A host gép egyetlen erős munkaállomás is lehet: a Zephyr native_sim a host CPU-ján, a konténerek pedig a Docker hálózatán futnak, így a teljes rendszer egyetlen számítógépen is tesztelhető.

3.1.3 Döntési szempontok

Miért Docker a brokerhez és a későbbi szolgáltatásokhoz? A Mosquitto, a TimescaleDB és a Grafana telepítése és verziókezelése natívan törékeny lenne. A Docker Compose deklaratív módon írja le a szolgáltatásokat, a verziók pedig a compose.yaml-ben rögzíthetők. A konténerek ráadásul izolálják a labor által használt portokat és köteteket, a takarítás pedig egyetlen docker compose down -v paranccsal megoldható.

Miért native_sim a Zephyr célnak? A Zephyr hivatalosan támogatja a natív szimulációt, amely a firmware-t a host processzeként futtatja. Ez nem hardverhű időzítést és energiafogyasztást ad, de a szálkezelés, a protokollkód és a logika tesztelésére kiváló. A valós hardveres kiegészítés opcionális, és az Opcionális valós hardver alfejezetben jelenik meg.

Miért Java 21 és Maven? A Spring Boot 3.x-hez Java 17 vagy újabb kell; a 21 hosszú távú támogatást élvez. A Maven pedig a Spring Boot projektek leggyakoribb build-eszköze, és a C++-os CMake-hez hasonló, deklaratív életciklust ad.

Miért Python 3? A laborban kisebb segédszkripteket (például adatszimuláció, üzenetgenerálás) Pythonban írunk, mert gyorsan fejleszthető és a JSON/SenML kezelése is egyszerű.

Globális elnevezési konvenciók

  • A labor gyökere: ~/iot-labor/.
  • Minden alfejezet munkakönyvtára: ~/iot-labor/iNNN/.
  • A közös Docker Compose fájl: ~/iot-labor/stack/compose.yaml.
  • Az új laborobjektumok (fájl, konténer, topic) neve ts- vagy lab- előtagú.

Továbbvitt eredmény. Az itt létrehozott ~/iot-labor/ könyvtárszerkezetet és a stack/compose.yaml vázat használja az Miért RTOS? A Zephyr felépítése és az első alkalmazás, az MQTT a gyakorlatban: Zephyr-kliens és Mosquitto, a A ts-gw szolgáltatás C++-ban: protokollfordítás MQTT-re, a A ts-backend váza: REST API és egészségellenőrzés és a Záróprojekt: a teljes TerraSense rendszer összeállítása és átvétele alfejezet.

3.1.4 Labor: a környezet telepítése és füsttesztje

Munkakönyvtár:

mkdir -p ~/iot-labor/i004 && cd ~/iot-labor/i004

3.1.4.1 1. Alapcsomagok és git ellenőrzése

Ubuntu 24.04-en a git általában már telepítve van, de a laborkörnyezet miatt frissítjük a csomaglistát, és telepítjük az alapvető eszközöket.

sudo apt-get update
sudo apt-get install -y git curl wget python3 python3-pip \
  build-essential ca-certificates
git --version
python3 --version

Várt kimenet: például git version 2.43.0 és Python 3.12.3 (a pontos verzió a telepített csomagoktól függ).

3.1.4.2 2. Docker Engine és Compose v2 telepítése

A hivatalos Docker repository-t használjuk, hogy a legfrissebb stabil Engine-t és a Compose v2-t kapjuk. A kulcs és a repository hozzáadása után telepítjük a docker-ce csomagokat:

sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | \
  sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
echo \
  "deb [arch=amd64 signed-by=/etc/apt/keyrings/docker.gpg] \
  https://download.docker.com/linux/ubuntu noble stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io \
  docker-buildx-plugin docker-compose-plugin

Ezután a felhasználót a docker csoportba kell tenni, hogy sudo nélkül is futtathassunk konténereket:

sudo usermod -aG docker $USER
newgrp docker

Ellenőrzés:

docker --version
docker compose version

Várt kimenet: a Docker Engine és a Compose v2 verziószáma, például Docker version 27.x és Docker Compose version v2.x.

Ellenőrzési igény. Az Ubuntu 24.04 kódneve noble; ha a Docker repository URL-je megváltozik, akkor a fenti deb sor kiigazítása szükséges. A pontos Docker-verziók a telepítés időpontjától függenek.

3.1.4.3 3. A labor-könyvtárszerkezet és a közös Compose-váz létrehozása

Létrehozzuk a labor gyökérkönyvtárát, a közös stack mappát és a scripts segédkönyvtárat:

mkdir -p ~/iot-labor/stack ~/iot-labor/scripts

Most létrehozzuk a ~/iot-labor/stack/compose.yaml vázat, amely egyelőre csak a Mosquitto broker szolgáltatást tartalmazza. Ez a fájl a későbbi alfejezetekben bővül a backend és az adatbázis szolgáltatásokkal.

# ~/iot-labor/stack/compose.yaml
# Közös Docker Compose váz a TerraSense laborhoz.
# A későbbi alfejezetek további szolgáltatásokat adnak hozzá.

services:
  broker:
    image: eclipse-mosquitto:2
    container_name: lab-broker
    ports:
      - "1883:1883"
    volumes:
      - ./mosquitto/mosquitto.conf:/mosquitto/config/mosquitto.conf:ro
    healthcheck:
      test: ["CMD", "mosquitto_sub", "-t", "$$SYS/#", "-C", "1", "-W", "1"]
      interval: 10s
      timeout: 3s
      retries: 5

A compose váz egy broker nevű szolgáltatást definiál, amely az eclipse-mosquitto:2 image-et használja, a 1883-as MQTT portot publikálja a hostra, és a konfigurációs fájlt csak olvasható kötetként csatolja. A healthcheck a $SYS/# rendszertopicra iratkozik fel, és egyetlen üzenetet vár rövid időn belül. A konténer neve a lab- előtagot viseli.

A Mosquitto konfigurációs fájlhoz létrehozzuk a minimális beállítást. Az MQTT 5-ös laborokhoz majd itt lesz szükség a listener és a híd beállításaira.

mkdir -p ~/iot-labor/stack/mosquitto
cat > ~/iot-labor/stack/mosquitto/mosquitto.conf <<'EOF'
listener 1883
allow_anonymous true
EOF

Biztonsági megjegyzés. Az allow_anonymous true csak a laborban, zárt hoston elfogadható; a Biztonságos kapcsolat: TLS 1.3, mTLS és DTLS az MQTT/CoAP alatt alfejezetben hitelesítést és TLS-t kapcsolunk be.

Indítsuk el a brokert, és ellenőrizzük a konténer állapotát:

cd ~/iot-labor/stack
docker compose up -d broker
docker compose ps

Várt kimenet: a lab-broker konténer fut, a STATUS oszlopban Up (egészséges) állapottal, ha a healthcheck sikeres.

3.1.4.4 4. Zephyr: west, SDK és az első native_sim build

A Zephyr fejlesztéshez a west eszközre és a Zephyr SDK-ra van szükség. A west egy Python-alapú meta-eszköz, amely a Zephyr forrását, moduljait és a buildelési folyamatot kezeli.

pip3 install --user west
west --version

Ezután inicializáljuk a Zephyr workspace-t a ~/zephyrproject könyvtárban. A west init a Zephyr stabil kiadási ágát tölti le; a konkrét branch vagy tag a kiadási ciklustól függ, ezért ellenőrizd a hivatalos Zephyr dokumentációt.

west init ~/zephyrproject
cd ~/zephyrproject
west update

A west update letölti a Zephyr fő forrását és a manifestben hivatkozott modulokat, ami több percet is igénybe vehet.

A Zephyr SDK a hivatalos GitHub releases oldalról tölthető le. A pontos verziószám ellenőrzést igényel; a telepítő egyszerűen futtatható:

cd ~/Downloads
wget https://github.com/zephyrproject-rtos/sdk-ng/releases/download/vX.Y.Z/zephyr-sdk-X.Y.Z_linux-x86_64.tar.xz
tar xf zephyr-sdk-X.Y.Z_linux-x86_64.tar.xz
cd zephyr-sdk-X.Y.Z
./setup.sh

Ellenőrzési igény. A fenti URL-ben szereplő vX.Y.Z helyére a Zephyr SDK aktuális verzióját kell írni, és a fájlnév is ettől függ. A telepítési útmutató a Zephyr SDK dokumentációjában frissül.

A setup.sh telepíti a szükséges udev-szabályokat és beállítja a környezeti változókat. A telepítő után a west automatikusan megtalálja a SDK-t, ha az a szokásos helyen, a ~/zephyr-sdk-<version> mappában van.

3.1.4.5 5. Hello world native_sim boardon

A füstteszthez a Zephyr beépített hello_world mintáját használjuk. A -b native_sim kapcsoló a natív szimulációs boardot választja, a -d pedig a build kimeneti könyvtárát adja meg.

cd ~/zephyrproject/zephyr
west build -b native_sim samples/hello_world -d ~/iot-labor/i004/build-hello

A build sikerét a következő kimenet jelzi:

...
[ 100%] Linking C executable zephyr.exe
...

Futtassuk a szimulációt:

~/iot-labor/i004/build-hello/zephyr/zephyr.exe

Várt kimenet:

*** Booting Zephyr OS build vX.Y.Z ***
Hello World! native_sim

A native_sim a programot a host processzeként futtatja, ezért a kilépéshez Ctrl+C szükséges. A pontos verziószám a build kimenetben jelenik meg.

3.1.4.6 6. Mosquitto mosquitto_pub/mosquitto_sub próba

A brokert a compose már elindította. A füstteszthez a konténerbe lépve futtatunk egy feliratkozót és egy publikálót. Nyissunk egy második terminált, és futtassuk a feliratkozót:

docker exec -it lab-broker mosquitto_sub -t 'terrasense/gh1/n001/telemetry'

Az első terminálban publikáljunk egy tesztüzenetet:

docker exec -it lab-broker mosquitto_pub -t 'terrasense/gh1/n001/telemetry' \
  -m '{"node_id":"n001","ts":1717000000000,"temp":23.4}' -q 1

A feliratkozó terminálban megjelenik az üzenet:

{"node_id":"n001","ts":1717000000000,"temp":23.4}

A próba után a feliratkozót Ctrl+C-vel állíthatjuk le. A broker konténert később sem kell leállítani, mert a későbbi laborok is használják.

3.1.4.7 7. Java 21 és Maven telepítése

A Spring Boot 3.x-hez OpenJDK 21-et és Mavent telepítünk:

sudo apt-get install -y openjdk-21-jdk maven
java -version
mvn -version

Várt kimenet: openjdk version "21.x" és Apache Maven 3.9.x. A pontos verzió a Ubuntu csomagtárolótól függ.

3.1.4.8 8. Python 3 és a segédkönyvtár ellenőrzése

A Python 3 már telepítve van; a pip-et a labor segédszkriptjeihez használjuk majd. Hozzunk létre egy lab_hello.py fájlt az i004 munkakönyvtárban, és futtassuk:

# ~/iot-labor/i004/lab_hello.py
import json

telemetry = {"node_id": "n001", "seq": 1, "temp": 23.4}
print(json.dumps(telemetry))
python3 ~/iot-labor/i004/lab_hello.py

Várt kimenet:

{"node_id": "n001", "seq": 1, "temp": 23.4}

Ezzel minden laborpillér telepitve és füsttesztelve van.

3.1.6 Tipikus hibák és félreértések

  1. A native_sim nem valós idejű hardver. Az időzítés és az energiafogyasztás a szimulációban nem reprezentálja a valós mikrovezérlőt. Például egy 1 másodperces alvás a native_sim-ben a host CPU-idejét használja, de nem ugyanazt a fogyasztást adja, mint egy valódi nRF52840. Minden mérésnél ezt a különbséget ki kell mondani.

  2. A Docker-portpublikálás nem azonos a konténer belső hálózatával. A 127.0.0.1:1883 a hostról éri el a brokert; a konténeren belül viszont a broker szolgáltatásnév a compose hálózatán érhető el. A későbbi backend-laborokban a konténerből a brokerhez a broker hosztnéven kell csatlakozni, nem a localhost-on.

  3. A Compose v2-ben a version mező elavult. A compose.yaml elején ne adjunk meg version:-t, mert a Compose v2 figyelmen kívül hagyja, és figyelmeztetést adhat. A vázban ezért nem szerepel.

  4. A west workspace és a build könyvtár összekeverése. A west build parancsot a Zephyr forráskönyvtárból (~/zephyrproject/zephyr) kell futtatni, vagy a west-nek tudnia kell a workspace-t. Ha a build könyvtárat a labor mappába tesszük, akkor a -d kapcsolóval kell megadni, de a parancs futási helye a Zephyr forrás legyen.

3.1.7 Feladatok

3.1.7.1 (a) Fogalmi/döntési kérdés

Magyarázd el, miért érdemes a Mosquitto brokert Docker-konténerben futtatni a laborban, és miért nem a hostra telepített csomaggal dolgozunk. Térj ki a verziókezelésre és a takarításra is.

3.1.7.2 (b) Tervezési feladat

Tervezd meg a ~/iot-labor/stack könyvtár további struktúráját a későbbi szolgáltatásokhoz: PostgreSQL + TimescaleDB, Grafana, ts-backend. Hol tárolnád az adatbázis-állományokat, a konfigurációs fájlokat és a logokat, hogy a laborok között ne vesszenek el, de takarításkor könnyen törölhetők legyenek?

3.1.7.3 (c) Implementációs feladat

Egészítsd ki a ~/iot-labor/stack/compose.yaml vázat egy mqtt nevű szolgáltatással, amely ugyanazt a Mosquitto image-et használja, de a nevét lab-mqtt-re változtatod, és a 1883-as portot 1884-re képezi le a hoston, hogy a meglévő broker mellett fusson. Indítsd el, és teszteld mosquitto_pub/mosquitto_sub parancsokkal a terrasense/test topicot.

3.1.7.4 (d) Hibakeresési feladat

Egy hallgató a labor futtatása közben a következő üzenetet kapja: docker: permission denied while trying to connect to the Docker daemon socket. Mi a hiba oka, és hogyan javítható? Adj két lehetséges megoldást is, és mondd meg, melyik a biztonságosabb.

3.1.8 Megoldások

3.1.8.1 (a)

A Docker-konténer használata mellett szól, hogy a Mosquitto verzióját a compose.yaml-ben rögzíthetjük (például eclipse-mosquitto:2), így a labor minden résztvevője ugyanazt a brokerszoftvert futtatja, függetlenül a host disztribúciójától. A takarítás egyetlen docker compose down -v paranccsal megoldható, ami a konténert és a névtelen köteteket is eltávolítja. Ha a brokert natívan telepítenénk, a verziók és a függőségek eltérhetnek, a teljes eltávolítás pedig bonyolultabb lenne.

3.1.8.2 (b)

A stack könyvtárban érdemes alkönyvtárakat létrehozni szolgáltatásonként: postgres/ (init script-ek, adatkötet), grafana/ (dashboards, provisioning), ts-backend/ (Java jar vagy Dockerfile). Az adatbázis-állományokat named volume-ban tároljuk, mert azt a Compose jól kezeli, és a docker compose down -v törli. A konfigurációs fájlokat a stack/ forráskönyvtárban tartjuk, hogy gitben verziózhatók legyenek, míg a logokat a tmpfs vagy a host /var/log mappába irányíthatjuk, hogy ne növekedjenek a konténer rétegben.

3.1.8.3 (c)

A compose.yaml második szolgáltatásaként:

  mqtt:
    image: eclipse-mosquitto:2
    container_name: lab-mqtt
    ports:
      - "1884:1883"
    volumes:
      - ./mosquitto/mosquitto.conf:/mosquitto/config/mosquitto.conf:ro

Indítás:

cd ~/iot-labor/stack
docker compose up -d mqtt
docker exec -it lab-mqtt mosquitto_pub -t 'terrasense/test' -m 'hello' -q 1

Feliratkozó egy másik terminálban:

docker exec -it lab-mqtt mosquitto_sub -t 'terrasense/test'

A terrasense/test topicra érkező üzenetnek meg kell jelennie. A teszt után a szolgáltatás leállítható: docker compose down mqtt.

3.1.8.4 (d)

A hiba oka, hogy a felhasználó nem tagja a docker csoportnak, ezért a Docker daemon socketet (/var/run/docker.sock) nem éri el. Az első megoldás: sudo usermod -aG docker $USER, majd új bejelentkezés. A második megoldás: a parancsokat sudo docker ... formában futtatni, de ez kevésbé biztonságos, mert a sudo a teljes folyamatot root joggal indítja, és a root jogú konténerek további kockázatot jelentenek. A biztonságosabb a docker csoporttagság beállítása.

3.1.9 Rövid összefoglaló

Ebben az alfejezetben telepítettük a TerraSense labor teljes futtatókörnyezetét Ubuntu 24.04-en: Docker Engine-t Compose v2-vel, a Zephyr workspace-t west-tel és a Zephyr SDK-val, valamint a Java 21 + Maven és Python 3 eszközöket. Mindegyik komponenst füstteszttel ellenőriztük. Létrehoztuk a ~/iot-labor/ könyvtárszerkezetet, benne a stack/compose.yaml közös vázat, amely a lab-broker Mosquitto szolgáltatást definiálja, és a stack/mosquitto/mosquitto.conf minimalista konfigurációt. A ~/iot-labor/i004/build-hello/zephyr/zephyr.exe hello world build a Zephyr native_sim célt igazolja. Ezt a struktúrát és compose-vázat a későbbi alfejezetek bővítik a ts-backend, a TimescaleDB és a Grafana szolgáltatásaival.
