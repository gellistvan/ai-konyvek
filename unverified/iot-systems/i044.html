15.1 Ingest: MQTT-ből a backendbe, idempotensen

15.1.1 Motiváció

A TerraSense rendszerben a telemetria a terrasense/<site>/<node>/telemetry topicra érkezik, és a MQTT QoS, munkamenetek, retain, Last Will és MQTT 5 alfejezetben meghatározott konvenció szerint QoS 1-es publikálással utazik. A QoS 1 garantálja, hogy az üzenet legalább egyszer megérkezik a brokerhez, de a hálózati hibák utáni újraküldés miatt ugyanazt az üzenetet többször is kézbesítheti. Ha a backend minden egyes érkezést új sorként ír az adatbázisba, a duplikátumok torzítják az átlagot, a riasztási szabályokat és a későbbi idősoros elemzést. Ebben az alfejezetben megépítjük a ts-backend MQTT-ingest komponensét, amely validálja a sémát, és az (node_id, seq) páros mint egyedi kulcs segítségével idempotensen dolgozza fel az üzeneteket.

15.1.2 Fogalmak és működés

Definíció. (Idempotens feldolgozás) Egy feldolgozási lépés akkor idempotens, ha ugyanazt a bemeneti üzenetet többször végrehajtva ugyanazt a külső hatást érjük el, mint egyszeri végrehajtáskor. MQTT-ingest esetén ez azt jelenti, hogy a duplikált telemetriaüzenet nem hoz létre új adatsort, és nem vált ki többszörös riasztást vagy más mellékhatást.

Definíció. (Shared subscription) Az MQTT 5 shared subscription egy broker-szolgáltatás, amely lehetővé teszi, hogy egy topicüzenetet egy feliratkozási csoport több kliense közül csak egy kapjon meg. A szintaxis: $share/<csoportnév>/<topic>. Ha például két ts-backend példány fut, mindkettő a $share/ingest/terrasense/+/+/telemetry topicra iratkozik fel, és a Mosquitto egy-egy üzenetet csak az egyiküknek továbbít. Ezzel elkerülhető a párhuzamos példányok közötti duplikált feldolgozás anélkül, hogy közös állapotot kellene fenntartaniuk.

Definíció. (Dead letter) A dead letter olyan tároló (tipikusan topic vagy adatbázistábla), ahová azok az üzenetek kerülnek, amelyeket a rendszer nem tud értelmezni vagy feldolgozni. Az ingest-komponensben ez az érvénytelen JSON-üzenetek célhelye, hogy az üzemeltető később kivizsgálhassa őket anélkül, hogy a hibás üzenet blokkolná a teljes adatcsatornát.

15.1.3 Döntési szempontok

Az MQTT-kliens kiválasztásakor a Spring világban két tipikus út van: az Eclipse Paho Java kliens közvetlen használata, vagy a Spring Integration MQTT-adaptere. A TerraSense oktatási céljaihoz a Paho Java kliens mellett döntünk, mert:

  • a callback-alapú kód átláthatóan mutatja az MQTT 5 tulajdonságait (például a messageArrived metódusban elérhető MqttMessage-et);
  • a C++-os Paho kliensből ismert fogalmak (publisher, connection options) közvetlenül megjelennek;
  • a Spring Integration absztrakció kényelmes, de a jelen alfejezet tanulási célja nem a keretrendszer-konfiguráció, hanem az idempotens feldolgozás és a protokollszintű viselkedés megértése;
  • a Paho 5-ös kliense shared subscriptiont is tud, ami a többpéldányos telepítés alapja.

A választás kompromisszumait az alábbi táblázat foglalja össze.

A shared subscription használatáról akkor érdemes dönteni, ha a ts-backend több példányban fut. Egy példány esetén a normál terrasense/+/+/telemetry feliratkozás elegendő, és a topic-wildcard biztosítja, hogy minden üzenet eljusson az ingesthez. Több példánynál a $share/ingest/terrasense/+/+/telemetry használata megakadályozza, hogy ugyanazt az üzenetet mindegyik példány feldolgozza – azonban az idempotens adatmodell így is védőhálót ad, mert ha valamelyik példány mégis kétszer kapná az üzenetet, az UPSERT akkor sem hoz létre duplikátumot.

A validálás során a backend a Sémák és verziózás: kompatibilis változtatások alfejezetben rögzített elvet követi: a sémaverziót az üzenet hordozza (schema_version mező), és az ismeretlen mezőket nem dobja el, hanem naplózza. Az érvénytelen üzeneteket a dead_letter táblába írjuk, és a terrasense/ingest/dead-letter topicra is publikáljuk, hogy az üzemeltető külön fogyasztóval is figyelhesse őket.

package com.terrasense.backend;

import com.fasterxml.jackson.annotation.JsonIgnoreProperties;
import java.util.Map;

@JsonIgnoreProperties(ignoreUnknown = true)
public record TelemetryMessage(

A @JsonIgnoreProperties(ignoreUnknown = true) biztosítja, hogy az ismeretlen mezők ne okozzanak deszerializációs hibát, csak naplózzuk őket – ezzel teljesítjük a sémaverziós alfejezet követelményét.

3. Ingest szolgáltatás. A src/main/java/com/terrasense/backend/TelemetryIngestService.java tartalmazza az MQTT-kapcsolatot és a feldolgozási logikát:

package com.terrasense.backend;

import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;
import lombok.extern.slf4j.Slf4j;
import org.eclipse.paho.mqttv5.client.*;
import org.eclipse.paho.mqttv5.common.MqttMessage;
import org.springframework.stereotype.Service;
import com.fasterxml.jackson.databind.ObjectMapper;

@Slf4j
@Service
public class TelemetryIngestService {

    private final TelemetryRepository repository;
    private final ObjectMapper objectMapper;
    private MqttClient client;

    public TelemetryIngestService(TelemetryRepository repository, ObjectMapper objectMapper) {
        this.repository = repository;
        this.objectMapper = objectMapper;
    }

    @PostConstruct
    public void start() throws MqttException {
        String brokerUri = "tcp://localhost:1883";
        String clientId = "ts-backend-ingest";
        client = new MqttClient(brokerUri, clientId);
        MqttConnectionOptions options = new MqttConnectionOptions();
        options.setAutomaticReconnect(true);
        options.setCleanStart(true);
        client.connect(options);
        String topic = "terrasense/+/+/telemetry";
        client.subscribe(topic, 1, this::handleMessage);
        log.info("Feliratkozva: {}", topic);
    }

    private void handleMessage(String topic, MqttMessage message) {
        try {
            String payload = new String(message.getPayload(), java.nio.charset.StandardCharsets.UTF_8);
            TelemetryMessage telemetry = objectMapper.readValue(payload, TelemetryMessage.class);
            if (!validate(telemetry)) {
                repository.insertDeadLetter(topic, payload, "séma hiba");
                log.warn("Érvénytelen telemetria: {}", payload);
                return;
            }
            repository.upsert(telemetry);
            log.info("Ingest OK: node={}, seq={}", telemetry.node_id(), telemetry.seq());
        } catch (Exception e) {
            repository.insertDeadLetter(topic, new String(message.getPayload()), e.getClass().getSimpleName());
            log.error("Feldolgozási hiba", e);
        }
    }

    private boolean validate(TelemetryMessage m) {
        if (m.node_id() == null || m.node_id().isBlank()) return false;
        if (m.seq() < 0) return false;
        if (m.ts() < 1_600_000_000_000L || m.ts() > 4_000_000_000_000L) return false;
        return m.sensor_data() != null && !m.sensor_data().isEmpty();
    }

    @PreDestroy
    public void stop() throws MqttException {
        if (client != null && client.isConnected()) {
            client.disconnect();
            client.close();
        }
    }
}

A callback-ben csak gyors, nem blokkoló műveleteket végzünk; az adatbázisírás a repository rétegen keresztül szinkron, de a laborban a forgalom alacsony. Nagy terhelés esetén érdemes az ingestet work queue-ba vagy reaktív pipeline-ba helyezni, ezt a Eseményvezérelt feldolgozás: Kafka és a kézbesítési szemantika tárgyalja.

4. Repository az idempotens UPSERT-tel. src/main/java/com/terrasense/backend/TelemetryRepository.java:

package com.terrasense.backend;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.stereotype.Repository;

@Repository
public class TelemetryRepository {

    private final JdbcTemplate jdbc;

    public TelemetryRepository(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    public void upsert(TelemetryMessage m) {
        String sql = """
            INSERT INTO telemetry (node_id, seq, received_at, ts, schema_version, payload)
            VALUES (?, ?, NOW(), ?, ?, ?::jsonb)
            ON CONFLICT (node_id, seq)
            DO UPDATE SET
                received_at = NOW(),
                ts = EXCLUDED.ts,
                payload = EXCLUDED.payload
            """;
        jdbc.update(sql,
            m.node_id(),
            m.seq(),
            m.ts(),
            m.schema_version(),
            objectToJson(m.sensor_data()));
    }

    public void insertDeadLetter(String topic, String payload, String reason) {
        String sql = """
            INSERT INTO dead_letter (topic, payload, reason, received_at)
            VALUES (?, ?, ?, NOW())
            """;
        jdbc.update(sql, topic, payload, reason);
    }

    private String objectToJson(Object o) {
        try {
            return new com.fasterxml.jackson.databind.ObjectMapper().writeValueAsString(o);
        } catch (Exception e) {
            throw new RuntimeException(e);
        }
    }
}

A schema.sql a src/main/resources/ alatt hozza létre a táblákat:

CREATE TABLE IF NOT EXISTS telemetry (
    node_id        TEXT        NOT NULL,
    seq            BIGINT      NOT NULL,
    received_at    TIMESTAMPTZ NOT NULL,
    ts             BIGINT      NOT NULL,
    schema_version INT         NOT NULL,
    payload        JSONB       NOT NULL,
    PRIMARY KEY (node_id, seq)
);

CREATE TABLE IF NOT EXISTS dead_letter (
    id          BIGSERIAL   PRIMARY KEY,
    topic       TEXT        NOT NULL,
    payload     TEXT        NOT NULL,
    reason      TEXT,
    received_at TIMESTAMPTZ NOT NULL
);

15.1.6 Tipikus hibák és félreértések

  1. QoS 1 idempotencia nélkül. Sokan azt hiszik, hogy a QoS 1 „legalább egyszer” kézbesítése csak elméleti duplikációval jár. A PUBACK elvesztése valós hálózati hiba, ezért a backendnek mindenképp idempotensnek kell lennie; az egyedi kulcs nélküli INSERT felesleges sorokat szül.
  2. Helyi idő UTC helyett. A received_at-et az adatbázis NOW()-val állítja, ami a szerver időzónájától függhet. A TerraSense konvenció szerint mindig UTC-t használunk; a TIMESTAMPTZ típus és a Postgres UTC-re normalizálása ezt biztosítja, de az alkalmazásszintű időbélyegzőknél ügyelni kell az Instant használatára.
  3. ISR-hez hasonló blokkoló hívás a callbackben. Az MQTT callback nem megszakítás, de ha hosszú adatbázis- vagy hálózati műveletet végzünk benne, a broker felé késleltetjük a nyugtázást, és nő a memóriaigény. Nagy terhelésnél a callback csak a gyors validálást és queue-ba helyezést végezze.
  4. Shared subscription hiánya több példány esetén. MQTT 3.1.1-ben nincs shared subscription, így két backend példány ugyanazt az üzenetet mindketten megkapja. Az idempotens adatmodell véd a duplikált soroktól, de a külső mellékhatások (például értesítések) akkor is kétszer futhatnak le, hacsak nem használunk egyedi feldolgozási azonosítót.

15.1.7 Feladatok

  1. (Fogalmi) Miért nem elegendő a QoS 2 használata az idempotens feldolgozás kiváltására a teljes rendszerben?
  2. (Tervezési) Tegyük fel, hogy a hálózaton 0,5% annak a valószínűsége, hogy egy PUBACK elveszik, és az eszköz 10 000 üzenetet küld naponta. Mennyi a várható duplikált üzenetek száma naponta, ha az eszköz minden elveszett PUBACK esetén pontosan egyszer újraküldi az üzenetet?
  3. (Implementációs) Egészítsd ki a TelemetryIngestService validate metódusát úgy, hogy a sensor_data-ban csak számértékeket fogadjon el, és a temperature értéke −40 és 80 °C közé essen.
  4. (Hibakeresési) A telemetry táblában ugyanarra az (node_id, seq) párra két sor van, de a PRIMARY KEY definíció helyes. Hol lehet a hiba a feldolgozási láncban?

15.1.8 Megoldások

  1. A QoS 2 a broker és a kliens közötti hálózati duplikációt szünteti meg, de nem véd a feldolgozói szintű ismétléstől (például ha a backend egy tranzakciót visszagörget, majd újra futtatja), és nem oldja meg a különböző kiadók által küldött ugyanolyan adatokat sem. Az idempotencia a feldolgozó oldal saját felelőssége.
  2. naponta 10 000 üzenet, 0,005 veszteség → várhatóan 10000×0,005=5010\,000 \times 0{,}005 = 50 PUBACK-vész, tehát várhatóan 50 duplikált üzenet. Az idempotens ingest ezeket mind egyetlen sorba írja.
  3. Példakód:
private boolean validate(TelemetryMessage m) {
    if (m.node_id() == null || m.node_id().isBlank()) return false;
    if (m.seq() < 0) return false;
    if (m.ts() < 1_600_000_000_000L || m.ts() > 4_000_000_000_000L) return false;
    if (m.sensor_data() == null || m.sensor_data().isEmpty()) return false;
    for (Map.Entry<String, Double> e : m.sensor_data().entrySet()) {
        if (e.getValue() == null) return false;
    }
    if (m.sensor_data().containsKey("temperature")) {
        double t = m.sensor_data().get("temperature");
        if (t < -40.0 || t > 80.0) return false;
    }
    return true;
}
  1. A hiba valószínűleg a sensor_data JSON-szerializálásában van: ha a payload oszlop értéke eltér a két bejegyzésben, akkor az UPSERT DO UPDATE ága nem fut le? Nem, az egyedi kulcs akkor is megakadályozná a második sort. Ha mégis két sor van, akkor a seq értéke eltér (például long helyett String vagy a JSON-ből seq karakterláncként jön), vagy a node_id tartalmaz rejtett szóközt. Ellenőrizd a tényleges értékeket: SELECT node_id, seq, count(*) FROM telemetry GROUP BY 1,2 HAVING count(*) > 1; és a JSON-ben a seq típusát.
