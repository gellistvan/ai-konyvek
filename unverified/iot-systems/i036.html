12.2 A ts-gw szolgáltatás C++-ban: protokollfordítás MQTT-re

12.2.1 Motiváció

A TerraSense architektúrájában a ts-node szenzorcsomópont önmagában nem mindig képes közvetlenül MQTT-t küldeni a brokernek. Valós hardveren gyakran BLE GATT-értesítéssel adja át az adatot, a szimulációs laborokban pedig egy egyszerű UDP-datagrammal. A ts-gw az a Linux-gateway, amely ezt a heterogén eszközoldali forgalmat egységes MQTT-üzenetté alakítja a felhő felé. Ez a protokollfordítás nem csupán szintaktikai konverzió: a gateway normalizálja a mezőneveket, kiegészíti az időbélyeget és a seq sorszámot, elvégzi az alapvető duplikátum-/sorrendellenőrzést, majd a i028-ban már bevezetett terrasense/<site>/<node>/telemetry topicra publikál. Az alábbiakban egy adapter-alapú, RAII-t használó C++17 gateway-vázat építünk fel, amelyet a későbbi alfejezetek a store-and-forward, az üzemeltetés, a helyi feldolgozás, a biztonság és a záróprojekt során bővítenek.

12.2.2 Fogalmak és működés

Definíció (input adapter). Az input adapter a gateway bemeneti protokollját elszigetelő, lecserélhető programkomponens. Feladata, hogy egy adott forrásból (UDP, BLE GATT, soros port) nyers kereteket fogadjon, azokat előfeldolgozza, és az egységes belépési ponton adja át a gateway többi részének. A többi komponens csak az adapter által kikényszerített absztrakciót ismeri, így a protokollcsere nem érinti a normalizálót vagy a MQTT-publikálót.

Definíció (normalizált telemetria-minta). A gateway belső eseménye egy olyan, a nyers protokolltól független adatstruktúra, amely már a TerraSense telemetria-sémát tükrözi: node_id, monoton seq, UTC eseményidő epoch ms-ban, valamint a mért értékek. A normalizált minta a belső eseménysoron keresztül éri el az MQTT-publikáló réteget.

Definíció (belső eseménysor). A belső eseménysor egy szálbiztos FIFO sor, amely az egyik szálon érkező normalizált mintákat pufferként átadja egy másik szálnak. A gatewayben ez a sor választja szét a blokkoló hálózati fogadást a hálózati küldéstől, és lehetővé teszi a feldolgozás ideiglenes túlterhelésének korlátozott kezelését.

A szálak és eseményhurok viszonya a következő. Az UDP-adapter saját std::thread-ben fut: blokkoló recvfrom() hívással várja a kereteket, majd normalizálás után a std::function<void(const TelemetrySample&)> visszahívón keresztül a fő eseményhurok által figyelt sorba teszi a mintát. A fő szál wait_pop_for() hívással várakozik a sorra, és minden mintát azonnal publikál. Ez a szétválasztás azért hasznos, mert a hálózati küldés idejére az UDP-fogadó nem blokkolódik, illetve a későbbi store-and-forward bővítéskor a sor mögé tartós puffer is beiktatható. A megoldás szándékosan hasonlít a klasszikus producer–consumer mintára; a különbség az, hogy itt a fogyasztó oldal egy MQTT-kliens.

A C++-os RAII itt nem szlogen, hanem a gateway-hibakezelés alapja. A socket lezárása a UdpInputAdapter destruktorában, a MQTT-kliens felszabadítása a MqttPublisher destruktorában, a szálak joinolása a running_ atomi logikai változó és a stop() metódus együttes használatával biztosítja, hogy SIGINT-re a folyamat ne hagyjon hátra erőforrást. A stop() a socket lezárásával felébreszti a blokkoló recvfrom() hívást, így a munkaszál ki tud lépni.

A laborban UDP-adaptert használunk, mert az native_sim ts-node szimulátorból a legegyszerűbben UDP-datagramot küldhetünk. Valós hardveren a BleInputAdapter ugyanezt az interfészt implementálhatja a BlueZ D-Bus API-jával: a GATT-értesítések adatait kell normalizált mintává alakítani. A D-Bus-kód bonyolultsága miatt itt csak a vázat és a döntési szempontot tárgyaljuk; a labor a szimulált UDP-adapterre épül.

12.2.3 Döntési szempontok

Az alábbi táblázat a gateway implementációjának fő dilemmáit foglalja össze.

Kérdés Választás a laborban Indoklás / alternatíva
Szálak vagy async I/O std::thread + blokkoló hívások egyszerű, átlátható; nagy forgalomnál Boost.Asio vagy poll/epoll
Paho C vagy C++ kliens Paho C, MQTTClient.h kevesebb függőség a laborban; a C++ wrapper később bevezethető

Sor mérete korlátlan a vázban éles rendszerben felső korlát, elutasítás / lassítás, mert a memória nem végtelen

A BLE-adapter esetén a legfontosabb döntés, hogy a GATT-értesítések érkezési sorrendje önmagában nem garantálja a seq monotonitását, ezért a normalizáló rétegnek a seq ellenőrzést akkor is el kell végeznie. Az UDP-adapteren ugyanez az ellenőrzés a szimulált csomagok hibás sorrendjét szűri ki.

A szálbiztos eseménysor:

// src/EventQueue.h
#pragma once
#include <condition_variable>
#include <mutex>
#include <queue>

namespace terrasense {

template <typename T>
class EventQueue {
public:
  void push(const T& item) {
    {
      std::lock_guard<std::mutex> lk(mutex_);
      queue_.push(item);
    }
    cv_.notify_one();
  }

  bool wait_pop_for(T& item, std::chrono::milliseconds timeout) {
    std::unique_lock<std::mutex> lk(mutex_);
    if (!cv_.wait_for(lk, timeout, [this] { return !queue_.empty(); })) {
      return false;
    }
    item = queue_.front();
    queue_.pop();
    return true;
  }

private:
  std::mutex mutex_;
  std::condition_variable cv_;
  std::queue<T> queue_;
};

} // namespace terrasense

A main() összerakja a komponenseket, és a fő ciklusban publikál. A seq ellenőrzést a normalizáló végzi, de a gateway indulásakor az utolsó seq értéke nem ismert; a laborban elfogadjuk az első mintát.

// src/main.cpp
#include "EventQueue.h"
#include "MqttPublisher.h"
#include "Normalizer.h"
#include "TelemetryTypes.h"
#include "UdpInputAdapter.h"
#include <csignal>
#include <iostream>
#include <string>

using namespace terrasense;

namespace {
std::atomic<bool> running{true};

void handle_sigint(int) {
  running = false;
}
} // namespace

int main(int argc, char** argv) {
  const std::string broker_uri =
      argc > 1 ? argv[1] : "tcp://localhost:1883";
  const std::string node_id = argc > 2 ? argv[2] : "n001";
  const std::string bind_ip =
      argc > 3 ? argv[3] : "127.0.0.1";
  const uint16_t udp_port = argc > 4 ? static_cast<uint16_t>(std::stoi(argv[4]))
                                     : 12345;

  std::signal(SIGINT, handle_sigint);
  std::signal(SIGTERM, handle_sigint);

  Normalizer normalizer(node_id);
  EventQueue<TelemetrySample> queue;
  MqttPublisher publisher(broker_uri, "ts-gw-" + node_id);
  UdpInputAdapter udp(bind_ip, udp_port);

  if (!publisher.connect()) {
    std::cerr << "[ERROR] MQTT connection failed\n";
    return 1;
  }
  std::cout << "[INFO] MQTT connected\n";

  udp.start([&](const TelemetrySample& s) {
    queue.push(s);
  });
  std::cout << "[INFO] UDP adapter listening on " << bind_ip << ":"
            << udp_port << "\n";

  while (running) {
    TelemetrySample sample;
    if (queue.wait_pop_for(sample, std::chrono::milliseconds(500))) {
      std::string err;
      if (!normalizer.check_seq(sample.seq, err)) {
        std::cerr << "[WARN] dropped seq=" << sample.seq << ": "
                  << err << "\n";
        continue;
      }
      std::string topic =
          "terrasense/gh1/" + sample.node_id + "/telemetry";
      std::string payload =
          "{\"node_id\":\"" + sample.node_id + "\","
          "\"seq\":" + std::to_string(sample.seq) + ","
          "\"ts\":" + std::to_string(sample.ts_epoch_ms) + ","
          "\"temperature_c\":" + std::to_string(sample.temperature_c) + ","
          "\"humidity_rh\":" + std::to_string(sample.humidity_rh) + ","
          "\"soil_moisture_pct\":" +
          std::to_string(sample.soil_moisture_pct) + "}";
      if (publisher.publish(topic, payload, 1)) {
        std::cout << "[INFO] published " << topic << " seq="
                  << sample.seq << "\n";
      } else {
        std::cerr << "[WARN] publish failed, will retry later\n";
      }
    }
    if (!publisher.is_connected()) {
      std::cerr << "[WARN] MQTT disconnected, reconnecting...\n";
      publisher.connect();
    }
  }

  udp.stop();
  std::cout << "[INFO] gateway stopped\n";
  return 0;
}

12.2.6 Tipikus hibák és félreértések

A seq ellenőrzés hiánya. Ha a gateway egyszerűen továbbít minden UDP-keretet, a hálózati duplikátumok vagy a szimulátor újraindítása miatt a backend kétszer kaphatja ugyanazt a seq értéket. A Normalizer check_seq() metódusa kiszűri a nem növekvő vagy duplikált sorszámokat, de ezt az állapotot tartósítani kell a gateway újraindításakor, egyébként az első minta után ismét elfogadható lesz a régi seq.

A locale-függő std::stod. A magyar vagy más európai rendszerbeállítás mellett a std::stod("23.4") nem feltétlenül ugyanazt adja, mint a "23.4" tizedesvesszővel. Az IoT-üzenetekben mindig a pont a tizedesjel, ezért a normalizálóban explicit konverziót kell használni, nem a globális std::locale-ra bízni az értelmezést.

A blokkoló recvfrom() leállítása hiányzik. Ha a UdpInputAdapter::stop() nem zárja le a socketet, a munkaszál örökre várhat a recvfrom()-ban, és a folyamat nem tud tisztán kilépni. A destruktorban ezért a close(fd_) és a worker_.join() hívásának sorrendje kritikus.

A MQTT-publikálás visszatérési értékének figyelmen kívül hagyása. A QoS 1 publikálás csak akkor tekinthető kézbesítettnek, ha a MQTTClient_publish() visszatérési értéke sikert jelez, tehát a broker PUBACK-et küldött. Ha a hívás hibát ad, a gatewaynek legalább naplóznia kell, és a későbbi store-and-forward alfejezetben tartós pufferbe kell mentenie a mintát.

12.2.7 Feladatok

  1. Fogalmi kérdés. Magyarázza el, miért jobb az InputAdapter absztrakció, mint ha a main() közvetlenül az UDP-socketből olvasna, és onnan hívná a MQTT-publikálót.
  2. Tervezési feladat. Tegyük fel, hogy egy valós ts-node BLE GATT-értesítésekkel küldi az adatokat. Írja le lépésenként, hogyan implementálna egy BleInputAdapter osztályt a meglévő InputAdapter interfész alapján, milyen BlueZ D-Bus objektumokat kellene figyelni.
  3. Implementációs feladat. Egészítse ki a Normalizer::parse() metódust úgy, hogy a hiányzó seq mezőt a legutolsó ismert seq + 1 értékkel pótolja, és ezt a laborban tesztelje a send_udp.py segítségével "T:23.4;RH:61.2;SM:34" bemenettel.
  4. Hibakeresési feladat. Indítsa el a ts-gw-t, majd a ts-node szimulátor helyett egy Python szkriptből küldjön 5 másodpercig folyamatosan növekvő seq-ű UDP-kereteket. Állítsa le a brokert, majd indítsa újra. Mit tapasztal a publikálás visszatérési értékével, és hogyan viselkedik az újracsatlakozás? Javasoljon javítást a tartós puffer bevezetésével a store-and-forward alfejezet módszere szerint.

12.2.8 Megoldások

  1. Megoldás. Az adapter leválasztja a gateway magját a bemeneti protokollról. Ha később BLE-re vagy soros portra váltunk, csak az adaptert kell kicserélni, a normalizáló és a publikáló réteg érintetlen marad. Emellett az adapter határozza meg a nyers adatok fogadásának és leállításának életciklusát, így a main() nem keveredik a socket-kezelés részleteibe.

  2. Megoldás. A BleInputAdapter indulásakor csatlakozni kell a BlueZ D-Bus rendszerbuszhoz, majd a org.bluez Adapter1 interfészen keresztül a megfelelő adaptert, az Device1 interfészen a ts-node eszközt, végül a GattCharacteristic1 interfészen a telemetria-karakterisztikát kell megtalálni. Ezután StartNotify hívással kell feliratkozni az értesítésekre. Minden értesítés nyers bájtjait a Normalizer-rel kell feldolgozni, és a SampleHandler visszahívót hívni. A leállítás StopNotify hívással és a D-Bus kapcsolat lezárásával történik.

  3. Megoldás. A Normalizer-t ki kell egészíteni egy last_seq_ és have_last_seq_ tagváltozóval. A parse()-ban, ha nincs seq mező, akkor seq = have_last_seq_ ? last_seq_ + 1 : 1;. Ezután a check_seq() a szokásos módon ellenőrzi a monotonitást. A laborban a send_udp.py hiányzó seq-gel küldött üzenete után a gateway seq=43-at publikál, feltéve, hogy előtte a seq=42-es üzenet már megérkezett.

  4. Megoldás. A folyamatos küldés során a MQTTClient_publish() a broker leállása után hibát ad, mert a kapcsolat megszakad. A main() ciklusban a publisher.is_connected() hamis lesz, és a publisher.connect() újra próbálkozik. A hiba alatt a sorba beérkező minták nem vesznek el azonnal, mert a sor tartja őket, de a sor nem tartós: ha a folyamat közben leáll, az adatok elvesznek. A megoldás a store-and-forward alfejezetben tárgyalt tartós puffer: a publikálási hiba esetén a mintát fájlba kell menteni, és a kapcsolat visszaállása után vissza kell tölteni.

12.2.9 Rövid összefoglaló

A ts-gw egy adapter-alapú, C++17-ben megvalósított Linux-gateway. Az InputAdapter absztrakció mögött a UdpInputAdapter fogadja a szimulált ts-node UDP-kereteit; valós hardveren ugyanezt az interfészt valósíthatja meg egy BlueZ D-Bus BleInputAdapter. A Normalizer a nyers T:…;RH:…;SM:…;seq:… szöveget TelemetrySample-lé alakítja, seq ellenőrzést végez, és a node_id/seq/ts mezőket biztosítja. A szálbiztos EventQueue elválasztja a blokkoló fogadást a publikálástól. A MqttPublisher Paho MQTT C klienst használ QoS 1-gyel, újracsatlakozással. A build CMake-kel, a labor teljes lánca UDP-küldéstől a terrasense/gh1/n001/telemetry topicig terjed. Továbbvitt eredmény: a ~/iot-labor/i036/ alatt létrejött ts-gw váz a store-and-forward, az üzemeltetés, a helyi feldolgozás, a biztonság és a záróprojekt alapja lesz.
