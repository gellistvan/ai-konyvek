14.3 A ts-backend váza: REST API és egészségellenőrzés

14.3.1 Motiváció

Az előző alfejezetben bevezettük a Spring Bootot mint a TerraSense backendjének keretrendszerét. A ts-gw már képes MQTT-n telemetriát küldeni a lab-broker felé, de a rendszernek még nincs olyan szolgáltatása, amely a felhő oldalon fogadja, tárolja és kiszolgálja ezeket az adatokat. Ebben az alfejezetben elkészítjük a ts-backend válogatóját: egy olyan minimális, de konténerben futtatható Spring Boot alkalmazást, amely már most fel tud mutatni REST végpontokat, egészségellenőrzést és konfigurációt. A memóriabeli adattárolót szándékosan ideiglenesnek szánjuk – a későbbi alfejezetekben kicseréljük MQTT-ingestre, TimescaleDB-re és eszközárnyékra. A váz azonban már most meghatározza a csomagszerkezetet, a konfigurációs stílust és a konténeres futtatás módját, amelyet a Ingest: MQTT-ből a backendbe, idempotensen, a Idősoros adatbázisok és adatmodellezés, a Parancsok és konfiguráció lefelé: kézbesítés, nyugtázás, időkorlát és a Megfigyelhetőség végponttól végpontig: metrikák, naplók, nyomkövetés alfejezetek is használni fognak.

14.3.2 Fogalmak és működés

Definíció. A REST API (Representational State Transfer) HTTP-alapú, erőforrásokra épülő interfész, ahol az erőforrásokat URI-k azonosítják, a műveleteket pedig a HTTP-metódusok (GET, POST, PUT, DELETE) fejezik ki. A válasz általában JSON, a státusz pedig a szabványos HTTP-állapotkód.

Definíció. Az egészségellenőrzés (health check) olyan olvasási pont, amely jelzi, hogy a szolgáltatás él-e, és képes-e az alapvető funkcióira. A Spring Bootban ezt a Spring Boot Actuator modul biztosítja, amely további üzemeltetési végpontokat is kínál, például metrikákat (/actuator/metrics), környezeti infókat (/actuator/info) és konfigurációs részleteket.

Definíció. Az alkalmazásprofil (profile) a konfiguráció egy nevesített változata. A dev profil például részletes naplózást és memóriabeli tárolót, a prod profil szigorúbb beállításokat és valódi adatbázis-kapcsolatot használhat.

A háromrétegű belső felépítés elválasztja a HTTP-kezelést, az alkalmazási logikát és az adatelérést. Jelenleg minden réteg egyetlen osztályból vagy memóriabeli mapból áll:

A DeviceController fogadja a kéréseket, a InMemoryDeviceService elvégzi a keresést és a validálást, a ConcurrentHashMap pedig a legutolsó méréseket tárolja kulcs-érték párként. Ez a felosztás lehetővé teszi, hogy később a memóriabeli tárolót adatbázisra cseréljük anélkül, hogy a REST végpontok kódját meg kellene változtatni.

14.3.4.4 4. lépés: Memóriabeli service

Hozzuk létre az InMemoryDeviceService osztályt a src/main/java/com/terrasense/backend/service/InMemoryDeviceService.java fájlban:

package com.terrasense.backend.service;

import com.terrasense.backend.model.Telemetry;
import org.springframework.stereotype.Service;

import java.util.List;
import java.util.Map;
import java.util.Optional;
import java.util.concurrent.ConcurrentHashMap;

@Service
public class InMemoryDeviceService {

    private final Map<String, Telemetry> latestTelemetry = new ConcurrentHashMap<>();

    public InMemoryDeviceService() {
        // Labor-minta; élesben ezt az MQTT-ingest tölti majd fel.
        latestTelemetry.put("n001", new Telemetry("n001",
            1734567890123L, 22.5, 61.0, 34.0));
        latestTelemetry.put("n002", new Telemetry("n002",
            1734567895123L, 23.1, 58.5, 31.0));
    }

    public List<String> listDeviceIds() {
        return latestTelemetry.keySet().stream().sorted().toList();
    }

    public Optional<Telemetry> findLatest(String nodeId) {
        return Optional.ofNullable(latestTelemetry.get(nodeId));
    }
}

A konstruktorban feltöltött mintaadatok lehetővé teszik a REST-végpontok azonnali tesztelését. Az Optional használatával a controller később kényelmesen kezeli a hiányzó eszközt.

14.3.4.5 5. lépés: REST controller

Készítsük el a DeviceController osztályt a src/main/java/com/terrasense/backend/controller/DeviceController.java fájlban:

package com.terrasense.backend.controller;

import com.terrasense.backend.model.Telemetry;
import com.terrasense.backend.service.InMemoryDeviceService;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

import java.util.List;

@RestController
@RequestMapping("/api/devices")
public class DeviceController {

    private final InMemoryDeviceService deviceService;

    public DeviceController(InMemoryDeviceService deviceService) {
        this.deviceService = deviceService;
    }

    @GetMapping
    public List<String> listDevices() {
        return deviceService.listDeviceIds();
    }

    @GetMapping("/{nodeId}/latest")
    public ResponseEntity<Telemetry> latest(@PathVariable String nodeId) {
        return deviceService.findLatest(nodeId)
            .map(ResponseEntity::ok)
            .orElse(ResponseEntity.notFound().build());
    }
}

A @GetMapping és a @PathVariable a Spring Web deklaratív REST-kezelését mutatja: a metódus visszatérési értéke automatikusan JSON-szerializálódik.

14.3.6 Tipikus hibák és félreértések

  1. A health check nem egyenlő a rendszer egészségével. Az Actuator /actuator/health végpontja csak azt igazolja, hogy a Spring kontextus felállt, és a beépített indikátorok nem jeleztek hibát. Azt nem tudja megmondani, hogy a MQTT-kapcsolat él, a TimescaleDB elérhető, vagy a legutóbbi mérés friss-e. A későbbi alfejezetekben ezért saját health indikátorokat és alkalmazásszintű metrikákat adunk hozzá.

  2. A memóriabeli tároló nem perzisztens. Ha a konténer újraindul, a konstruktorban betöltött mintaadatok visszaállnak, a futás közben hozzáadott mérések eltűnnek. Ez a váz szándékos része, de élesben azonnal megjelenne az adatvesztés. A Idősoros adatbázisok és adatmodellezés alfejezetben a memóriabeli service-t TimescaleDB-alapú repository-ra cseréljük.

  3. A környezeti változók felülbírálják a YAML-t, de nem mindig közvetlenül. A Spring Bootban a SPRING_PROFILES_ACTIVE például a profil aktiválását szabályozza, míg a SERVER_PORT a portot. A property-k kötésekor a Spring relaxed bindingot használ: a YAML-ben server.port, a környezeti változóban SERVER_PORT ugyanazt a beállítást éri el. Nem minden környezeti változó ilyen; a management.endpoints.web.exposure.include például nem rövidíthető MANAGEMENT_ENDPOINTS_WEB_EXPOSURE_INCLUDE-ra a pontok miatt.

  4. A 404 nem feltétlenül hibát jelent. A ResponseEntity.notFound().build() szándékosan 404-et ad ismeretlen eszköz esetén. Ez gyakori félreértés: a kliens hibásan hibakeresést indít, pedig a szerver helyesen jelzi, hogy az erőforrás nem létezik. A megfelelő státuszkódok használata fontos az API-fogyasztók számára.

14.3.7 Feladatok

  1. Fogalmi/döntési kérdés: Miért használunk a REST API-ban /api előtagot, és miért hasznos, ha az Actuator végpontjait nem ugyanazon az útvonalon tesszük közzé? Fogalmazz meg egy olyan helyzetet, amikor a /api nélküli nyílt Actuator kockázatot jelent.

  2. Számítási/tervezési feladat: Tegyük fel, hogy az eszközlista 1000 eszközből áll, és minden eszköz nevét n001, n002, … formátumban tároljuk. Becsüld meg a GET /api/devices válasz JSON-méretét, ha minden azonosító átlagosan 4 karakter, a JSON tömb szintaxisa pedig ["n001","n002",...]. A vessző és az idézőjelek is karakterek. Nagyságrendileg hány bájt lesz? (A tényleges méret a UTF-8 kódolástól és a szerializációtól függ, itt elég a közelítő becslés.)

  3. Implementációs feladat a TerraSense-ben: Bővítsd az InMemoryDeviceService osztályt egy updateTelemetry(Telemetry) metódussal, amely beilleszti vagy felülírja a legutóbbi mérést. Ez a metódus később az MQTT-ingest feldolgozásakor fog kelleni. Írj hozzá egy @PostMapping végpontot is a DeviceController-be, amely fogad egy új mérést, és beírja a service-be. Teszteld curl segítségével.

  4. Hibakeresési/kiterjesztési feladat: A ts-backend konténer elindul, de a curl http://localhost:8080/actuator/health hosszú ideig nem ad választ, majd Connection timed out jelenik meg. Sorolj fel legalább három lehetséges okot, és mindegyikre adj egy-egy diagnosztikai lépést a docker logs vagy a docker inspect parancs segítségével.

14.3.8 Megoldások

14.3.8.1 1. Fogalmi kérdés

Az /api előtag elkülöníti a publikus, üzleti REST erőforrásokat az üzemeltetési belső végpontoktól. Ha az Actuator végpontjai is nyilvánosan, api előtag nélkül lennének elérhetőek, egy támadó könnyebben felderíthetné a belső állapotot (/actuator/health, /actuator/env, /actuator/metrics). A security azt is lehetővé teszi, hogy az /actuator/** útvonalra szigorúbb hozzáférés-vezérlést alkalmazzunk, míg az /api útvonalakra más szabályok vonatkoznak. A TerraSense esetében a dashboard és a külső kliensek az /api-t, a monitoring pedig az /actuator-t használja.

14.3.8.2 2. Méretbecslés

Egy azonosító JSON-ban így néz ki: "n001" = 1 idézőjel + 4 karakter + 1 idézőjel = 6 karakter. A tömb elemei között vessző van. 1000 elemnél a vesszők száma 999, egyenként 1 karakter. A nyitó és záró szögletes zárójel 2 karakter. Így a teljes hossz:

1000⋅6+999⋅1+2=6000+999+2=7001 karakter 1000 \cdot 6 + 999 \cdot 1 + 2 = 6000 + 999 + 2 = 7001 \text{ karakter}

UTF-8 kódolással, ha minden karakter 1 bájt (a példa karakterei ASCII), a válasz mérete körülbelül 7,0 kB. Ha a szerializáció még szóközöket vagy sortöréseket ad hozzá, a méret kissé nőhet, de nagyságrendileg 7 kB marad. Ez jól mutatja, hogy a JSON mérete sok kis azonosítónál a szintaxis miatt gyorsan nő; nagyobb listáknál érdemes lapozást vagy rövidebb kódolást használni.

14.3.8.3 3. Implementációs feladat

Az InMemoryDeviceService bővítése:

public void updateTelemetry(Telemetry telemetry) {
    latestTelemetry.put(telemetry.nodeId(), telemetry);
}

A DeviceController bővítése:

@PostMapping("/{nodeId}/latest")
public ResponseEntity<Void> updateLatest(@PathVariable String nodeId,
                                         @RequestBody Telemetry telemetry) {
    if (!nodeId.equals(telemetry.nodeId())) {
        return ResponseEntity.badRequest().build();
    }
    deviceService.updateTelemetry(telemetry);
    return ResponseEntity.noContent().build();
}

A @PostMapping és @RequestBody a beérkező JSON-t automatikusan Telemetry objektummá alakítja. A noContent() a 204-es státuszt adja vissza, jelezve, hogy a kérés sikeres, de nincs választest.

Tesztelés:

curl -i -X POST http://localhost:8080/api/devices/n003/latest \
  -H 'Content-Type: application/json' \
  -d '{"nodeId":"n003","ts":1734567900000,"temperature":21.0,"humidity":55.0,"soilMoisture":29.5}'

Ezután a GET /api/devices/n003/latest a friss adatot adja vissza.

14.3.8.4 4. Hibakeresési feladat

Lehetséges okok:

  • A konténer nem is fut. docker ps -a | grep ts-backend megmutatja az állapotot. Ha Exited, nézd meg a docker logs ts-backend naplót, valószínűleg a JAR nem indul el (pl. rossz package vagy port).
  • A port-hozzárendelés hiányzik vagy ütközik. docker port ts-backend mutatja a port-hozzárendelést. Ha nincs 0.0.0.0:8080, akkor a hostról nem érhető el. Ha a 8080-as port már foglalt, a Compose indításkor hibát ad; cseréld a host portot, például 8081:8080.
  • A Spring Boot a konténeren belül nem a 8080-as porton figyel. A Dockerfile EXPOSE 8080-at ad, de a application.yaml-ben server.port: 8080 van; ha ezt felülbírálod SERVER_PORT környezeti változóval, a port-hozzárendelés elavul. Ellenőrizd a docker logs ts-backend első sorait: a Tomcat started on port ... mutatja a tényleges portot.
  • A konténer hálózata nem éri el a hostot. Ha network_mode: host vagy más hálózati beállítás van, a port-hozzárendelés másként működik. docker inspect ts-backend mutatja a hálózati módot; a Compose-ban a ports beállítás bridge hálózatot feltételez.
