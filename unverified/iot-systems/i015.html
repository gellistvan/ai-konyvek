6.3 Aktuátorok: biztonságos vezérlés és visszajelzés

Az aktuátorok vezérlése az a pont, ahol az IoT-rendszer visszahat a fizikai világra. Egy szenzor hibás olvasása kellemetlen, de egy hibásan nyitva maradt öntözőszelep eláraszthat egy üvegházat, vagy egy beragadt fűtőrelé tönkreteheti a termést. A TerraSense üvegházában a talajnedvesség-szenzorok adatai alapján akarjuk nyitni és zárni az öntözőszelepet; ehhez olyan szoftver kell, amelyik akkor is biztonságos állapotba kerül, ha egy parancs elvész, a tápfeszültség pillanatra kimarad, vagy a visszajelző érzékelő meghibásodik.

6.3.1 Aktuátorok és vezérlő kimenetek

Definíció. Az aktuátor (actuator) olyan eszköz, amely elektromos jelet fizikai hatássá alakít: mozgássá, hővé, fénnyé vagy áramlássá. IoT-kontextusban jellemzően szelep, relé, motor, fűtőszál vagy LED.

A mikrovezérlő kimenete általában logikai szintű GPIO jel, amely ritkán tud közvetlenül nagy teljesítményű terhelést kapcsolni. A leggyakoribb felépítés az, hogy a GPIO egy relét vagy egy félvezető kapcsolót (tranzisztort, MOSFET-et, SSR-t) vezérel, az pedig a tényleges eszközt kapcsolja. Egy mágnesszelep (solenoid valve) esetén a nyitáshoz és a záráshoz is lehet külön kimenet, de az ipari és kerti öntözőrendszerekben sokszor normally closed (NC) szelepet használnak: áram hatására nyit, áramtalanítva zár. Ez már egy passzív fail-safe tulajdonság.

/* GPIO-kimenet egy szelep számára Zephyr-ben */
#include <zephyr/drivers/gpio.h>

#define VALVE_NODE DT_ALIAS(valve)
static const struct gpio_dt_spec valve_gpio =
    GPIO_DT_SPEC_GET(VALVE_NODE, gpios);

void valve_hw_open(const struct gpio_dt_spec *gpio, bool open)
{
    /* NC szelep: 1 = nyit, 0 = zár */
    gpio_pin_set_dt(gpio, open ? 1 : 0);
}

Ha a szelep nem csak kétállapotú, hanem arányosan állítható (például motoros keverőszelep), akkor PWM kimenetet használunk. A PWM kitöltési tényezője határozza meg a motor pillanatnyi sebességét vagy egy fűtőelem teljesítményét, és a vezérlő szoftverben ugyancsak egy 0–100% közötti értékkel modellezhető.

A biztonságos alapállapot két szinten jelenik meg:

  1. Hardveres alapállapot: a kimenet áramtalanítva milyen állapotba kerül. NC szelepnél ez zárt, egy fűtőrelénél kikapcsolt, egy motoros zsaluzónál nyitott vagy zárt attól függően, hogy mi a biztonságos az adott folyamatra nézve.
  2. Szoftveres alapállapot: ha a vezérlő szoftver fut, de nem kap érvényes frissítést vagy hibát észlel, milyen állapotot ír elő. Ezt watchdoggal, időkorláttal és szándékos „safe state” függvénnyel valósítjuk meg.

A TerraSense öntözőszelepének biztonságos alapállapota zárt, tehát a szoftveres fail-safe is zárást kell, hogy előírjon, ha elveszett a kapcsolat vagy lejárt a maximális öntözési idő.

6.3.2 Szelepvezérlés időkorláttal és visszajelzéssel

Definíció. A maximális bekapcsolási idő (maximum on-time) az az időtartam, ameddig egy aktuátor megszakítás nélkül aktív állapotban maradhat. Ha a vezérlő eddig nem kapott érvényes leállító parancsot, akkor az aktuátort saját hatáskörben biztonságos állapotba állítja.

A maximális bekapcsolási idő véd a szoftverhibák, eltűnt hálózati parancsok és hibás szenzoradatok ellen. Például ha a talajnedvesség-szenzor beragad „száraz” értékre, az öntözés ne folyhasson órákig: a vezérlő legfeljebb 10 percig tarthatja nyitva a szelepet, utána automatikusan zár.

A visszajelzés (feedback) azt jelenti, hogy a rendszer nem csak kiadja a parancsot, hanem ellenőrzi is az aktuátor tényleges állapotát. Egy NC mágnesszelepnél a visszajelzés lehet:

  • Áramkör-megszakításos mikrokapcsoló a szelep végállásáról.
  • Átfolyásmérő vagy nyomáskapcsoló a vezetékben.
  • Áramérzékelő a relé kimenetén, amely azt mutatja, hogy valóban folyik-e áram a tekercsbe.

Ha a parancsolt állapot (requested) és a visszajelzett állapot (reported) tartósan eltér, akkor hibát jelzünk: a szelep lehet, hogy mechanikusan beragadt, a relé nem kapcsolt, vagy a visszajelző érzékelő hibás. Az ilyen eltérésre a biztonságos válasz általában az, hogy a szelepet megkíséreljük zárni, a hibát pedig naplózzuk és jelentjük a backend felé. A visszajelzés nélküli nyílt hurkú vezérlés csak akkor elfogadható, ha a kockázat kicsi, és a rendszer más szinten (például túlfolyásgátló, mechanikus nyomáskapcsoló) már védve van.

/* Szelepvezérlő állapot időkorláttal és visszajelzéssel */
struct valve_ctrl {
    const struct gpio_dt_spec gpio;   /* kimeneti GPIO */
    bool requested_open;              /* parancsolt állapot */
    bool reported_open;               /* visszajelzett állapot */
    int64_t on_deadline_ms;           /* mikor kell lezárni */
    int64_t max_on_time_ms;           /* maximális bekapcsolási idő */
    bool hw_present;                  /* szimulációban false */
};

int valve_set_target(struct valve_ctrl *v, bool open)
{
    if (!v) return -EINVAL;

    v->requested_open = open;
    if (!v->hw_present) {
        /* natív szimulációban csak naplózzuk */
        v->reported_open = open;
    } else {
        valve_hw_open(&v->gpio, open);
        /* valós hardveren a visszajelzést később olvassuk */
    }
    if (open) {
        v->on_deadline_ms = k_uptime_get() + v->max_on_time_ms;
    } else {
        v->on_deadline_ms = 0;
    }
    return 0;
}

int valve_tick(struct valve_ctrl *v)
{
    if (!v) return -EINVAL;

    /* 1. időkorlát ellenőrzése */
    if (v->requested_open && v->on_deadline_ms != 0 &&
        k_uptime_get() >= v->on_deadline_ms) {
        printk("valve: max on-time exceeded, forcing close\n");
        return valve_set_target(v, false);
    }

    /* 2. visszajelzés olvasása valós hardveren */
    if (v->hw_present) {
        /* pl. egy bemeneti GPIO-t olvasunk */
        /* v->reported_open = gpio_pin_get_dt(&sense_pin); */
    }

    /* 3. eltérés kezelése */
    if (v->reported_open != v->requested_open) {
        /* rövid türelmi idő után hiba; itt most azonnal jelezzük */
        printk("valve: feedback mismatch, req=%d rep=%d\n",
               v->requested_open, v->reported_open);
        return -EIO;
    }
    return 0;
}

A fenti valve_set_target() függvény idempotens: ugyanazzal az állapottal többször meghívva nem váltogat, hanem ugyanazt az eredményt adja. Ez döntő különbség a váltás (toggle) szemantikához képest. Ha az MQTT-kapcsolat rövid megszakadása miatt ugyanaz a „nyisd ki” parancs kétszer érkezik meg, a toggle parancs kétszeri végrehajtása hibásan zárt állapotot eredményezne; az idempotens set_target(true) viszont egyszer nyit, másodjára semmit sem változtat. Az idempotencia tehát a parancs megismételhetőségét biztosítja, ami az at-least-once kézbesítés (QoS 1) természetes következménye.

Az ábrán látható, hogy a parancsra a csomópont először nyugtát küld, majd a tényleges állapotot jelenti. A nyugta önmagában még nem bizonyítja, hogy a szelep mechanikusan is átváltott; ezért kell a külön visszajelző üzenet. A MQTT QoS, munkamenetek, retain, Last Will és MQTT 5 alfejezetben látjuk majd, hogyan lehet ezt a nyugtázást QoS 1-gyel megbízhatóvá tenni.

A visszajelzés típusa szerint is dönthetünk:

  • Nincs visszajelzés: elfogadható, ha a rendszer más módon védett (pl. mechanikus nyomáskapcsoló, túlfolyásgátló).
  • Végálláskapcsoló: kétállapotú szelepnél elég.
  • Analóg visszajelzés: arányos szelepnél potenciométer vagy 4–20 mA-es jeladó.

A TerraSense-ben a labor első változatában a visszajelzést szimuláljuk, de a szoftver interfészét úgy alakítjuk ki, hogy később valós GPIO-visszajelzésre cserélhető legyen.

A labor célja egy olyan szelepvezérlő modul elkészítése, amelyet a későbbi alfejezetekben MQTT-parancsfeldolgozóval kötünk össze. Most a parancsot egy egyszerű szimulált bemenetről kapjuk, a GPIO-t pedig a native_sim célon csak naplózzuk.

Fájlok:

valve.h

#ifndef VALVE_H
#define VALVE_H

#include <zephyr/kernel.h>
#include <zephyr/device.h>

struct valve_ctrl {
    bool requested_open;
    bool reported_open;
    bool hw_present;
    int64_t on_deadline_ms;
    int64_t max_on_time_ms;
};

int valve_init(struct valve_ctrl *v, int64_t max_on_time_ms,
               bool hw_present);

bool valve_is_open(const struct valve_ctrl *v);

#endif

valve.c

#include "valve.h"
#include <zephyr/kernel.h>
#include <zephyr/logging/log.h>
#include <errno.h>

LOG_MODULE_REGISTER(valve, LOG_LEVEL_INF);

int valve_init(struct valve_ctrl *v, int64_t max_on_time_ms,
               bool hw_present)
{
    if (!v) return -EINVAL;
    v->requested_open = false;
    v->reported_open = false;
    v->hw_present = hw_present;
    v->on_deadline_ms = 0;
    v->max_on_time_ms = max_on_time_ms;
    return 0;
}

int valve_set_target(struct valve_ctrl *v, bool open)
{
    if (!v) return -EINVAL;

    if (v->requested_open == open) {
        /* idempotens: nem váltunk, csak frissítjük az időzítőt */
        if (open) {
            v->on_deadline_ms = k_uptime_get() + v->max_on_time_ms;
        }
        return 0;
    }

    v->requested_open = open;
    if (!v->hw_present) {
        v->reported_open = open;
        LOG_INF("valve: simulated %s", open ? "open" : "closed");
    } else {
        /* valós GPIO-írás itt lenne */
        /* gpio_pin_set_dt(&valve_gpio, open ? 1 : 0); */
        /* visszajelzést később olvassuk */
        LOG_INF("valve: hardware output set to %s",
                open ? "open" : "closed");
    }
    if (open) {
        v->on_deadline_ms = k_uptime_get() + v->max_on_time_ms;
    } else {
        v->on_deadline_ms = 0;
    }
    return 0;
}

bool valve_is_open(const struct valve_ctrl *v)
{
    return v ? v->reported_open : false;
}

int valve_tick(struct valve_ctrl *v)
{
    if (!v) return -EINVAL;

    if (v->requested_open && v->on_deadline_ms != 0 &&
        k_uptime_get() >= v->on_deadline_ms) {
        LOG_WRN("max on-time exceeded, forcing close");
        return valve_set_target(v, false);
    }

    if (v->reported_open != v->requested_open) {
        LOG_ERR("feedback mismatch: requested=%d reported=%d",
                v->requested_open, v->reported_open);
        return -EIO;
    }
    return 0;
}

main.c

#include <zephyr/kernel.h>
#include <zephyr/logging/log.h>
#include "valve.h"

LOG_MODULE_REGISTER(main, LOG_LEVEL_INF);

int main(void)
{
    struct valve_ctrl valve;
    int err;

    /* max 10 másodperc, szimulált GPIO-val */
    err = valve_init(&valve, 10000, true);
    if (err) {
        LOG_ERR("valve_init failed: %d", err);
        return err;
    }

    /* szimulált parancs: nyitás */
    err = valve_set_target(&valve, true);
    if (err) {
        LOG_ERR("valve_set_target failed: %d", err);
    }

    while (1) {
        err = valve_tick(&valve);
        if (err == -EIO) {
            LOG_ERR("valve feedback error, closing");
            valve_set_target(&valve, false);
        }
        k_sleep(K_MSEC(1000));
    }
    return 0;
}

6.3.5 Ellenőrzés és hibakeresés

A labor futtatásakor a következőket ellenőrizzük:

  1. A nyitás után 10 másodperccel a valve_tick valóban lezár, és a logban max on-time exceeded üzenet jelenik meg.
  2. Ha kétszer egymás után hívjuk meg a valve_set_target(&valve, true) függvényt, a második hívás nem vált, és a requested_open megmarad true-nak.
  3. Ha a visszajelzést szándékosan eltérítjük (pl. a szimulált reported_open értékét átírjuk false-ra, miközben requested_open true), a valve_tick -EIO hibát ad, és a main lezárja a szelepet.

6.3.6 Tipikus hibák és félreértések

  1. Toggle parancs használata idempotens állapotbeállítás helyett. Ha a backend toggle_valve() szemantikát küld, akkor egy elveszett nyugta miatti újraküldés kétszer fordítja meg az állapotot, és a szelep éppen az ellenkezőjére kerül. A parancs mindig konkrét célállapotot írjon elő: set_valve(true) vagy set_valve(false).
  2. A maximális bekapcsolási idő elhanyagolása. Ha csak a backend parancsára hagyatkozunk, akkor egy hálózati kiesés vagy szoftverhiba esetén a szelep végtelen ideig nyitva maradhat. Az időkorlát az eszköz helyi védelme, és a backendtől függetlenül működnie kell.
  3. A visszajelzés azonnali ellenőrzése mechanikus rendszerben. A relé és a szelep mechanikus átállása több tíz milliszekundum is lehet; ha azonnal olvassuk a végálláskapcsolót, hamis hibát kapunk. Türelmi időt kell beiktatni.
  4. A fail-safe alapállapot félreértése. A szoftveres fail-safe nem helyettesíti a hardveresen biztonságos állapotot. Ha a mikrokontroller lefagy, a szoftveres zárás nem fut le; ezért kell az NC szelep vagy külső védőrelé.

6.3.7 Feladatok

  1. Fogalmi, döntési kérdés: Miért idempotens a valve_set_target(open) parancs, és miért hibás az MQTT-alapú parancskiadásnál a valve_toggle()? Mondjon egy konkrét forgatókönyvet, ahol az utóbbi kárt okoz.
  2. Számolási, tervezési feladat: Egy 24 V-os mágnesszelep tekercse 0,5 A áramot vesz fel nyitott állapotban. Ha a szelep naponta átlagosan 6 percet van nyitva, mennyi energiát fogyaszt havonta (30 nap)? Mennyi legyen a maximális bekapcsolási idő, ha egy öntözési ciklus legfeljebb 0,5 liter vizet engedhet át, és a szelep átfolyása 2 l/min? (Az energia számításához használja a P=U⋅IP = U \cdot I összefüggést.)
  3. Implementációs feladat a TerraSense-ben: Bővítse a labor valve_tick függvényét egy feedback_pin bemenettel: ha a hw_present igaz, olvassa le a megadott GPIO bemenetet, és rendelje hozzá a reported_open mezőhöz. Adjon hozzá 2 másodperc türelmi időt, mielőtt eltérést jelezne.
  4. Hibakeresési, kiterjesztési feladat: A laborban a valve_set_target(false) nem naplózza a zárást, ha a szelep már zárva volt. Módosítsa a függvényt úgy, hogy minden állapotváltozást (nyitás és zárás) logoljon, akkor is, ha az idempotens hívás miatt nincs tényleges váltás. Indokolja, miért fontos ez a nyomkövetés szempontjából.

6.3.8 Megoldások

  1. A set_target(open) ugyanazt a célállapotot írja elő, így ha a parancs kétszer érkezik meg, másodszor nem változtat. A toggle() viszont minden híváskor ellenkező állapotba viszi a kimenetet. Tegyük fel, hogy a backend toggle() parancsot küld, mert a felhasználó rákattintott egy gombra, de a nyugta elveszik, és az MQTT QoS 1 újraküldés miatt a parancs másodszor is megérkezik. Az első hívás nyitja, a második zárja a szelepet, pedig a felhasználó nyitni akart. Ha a parancs set_target(true) lett volna, a második hívás már nem változtatott volna.

  2. A szelep napi energiafogyasztása nyitott állapotban: P=24V⋅0,5A=12WP = 24\ \text{V} \cdot 0{,}5\ \text{A} = 12\ \text{W}. Naponta 6 perc = 0,1 óra, tehát Enap=12W⋅0,1h=1,2WhE_\text{nap} = 12\ \text{W} \cdot 0{,}1\ \text{h} = 1{,}2\ \text{Wh}. Havonta Ehónap=1,2Wh⋅30=36WhE_\text{hónap} = 1{,}2\ \text{Wh} \cdot 30 = 36\ \text{Wh}. A maximális bekapcsolási idő: ha legfeljebb 0,5 liter vizet szabad átengedni, és az átfolyás 2 l/min, akkor tmax=0,5l2l/min=0,25min=15st_\text{max} = \frac{0{,}5\ \text{l}}{2\ \text{l/min}} = 0{,}25\ \text{min} = 15\ \text{s}.

  3. A valve_tick bővítése türelmi idővel:

int valve_tick(struct valve_ctrl *v)
{
    static int64_t mismatch_start_ms;

    if (v->requested_open && v->on_deadline_ms != 0 &&
        k_uptime_get() >= v->on_deadline_ms) {
        printk("valve: max on-time exceeded, forcing close\n");
        return valve_set_target(v, false);
    }

    if (v->hw_present && v->feedback_pin.port != NULL) {
        v->reported_open = gpio_pin_get_dt(&v->feedback_pin) ? true : false;
    }

    if (v->reported_open != v->requested_open) {
        if (mismatch_start_ms == 0) {
            mismatch_start_ms = k_uptime_get();
        } else if (k_uptime_get() - mismatch_start_ms > 2000) {
            printk("valve: feedback mismatch for >2 s\n");
            mismatch_start_ms = 0;
            return -EIO;
        }
    } else {
        mismatch_start_ms = 0;
    }
    return 0;
}
  1. A naplózás minden hívásnál akkor is fontos, ha nincs állapotváltozás, mert a parancs ismétlődése és a rendszer viselkedése így rekonstruálható. A módosított valve_set_target:
int valve_set_target(struct valve_ctrl *v, bool open)
{
    if (!v) return -EINVAL;

    if (v->requested_open != open) {
        LOG_INF("valve: state change to %s", open ? "open" : "closed");
        v->requested_open = open;
        /* GPIO-írás és visszajelzés-frissítés itt */
    } else {
        LOG_DBG("valve: redundant set_target(%s), no change",
                open ? "open" : "closed");
    }
    if (open) {
        v->on_deadline_ms = k_uptime_get() + v->max_on_time_ms;
    } else {
        v->on_deadline_ms = 0;
    }
    return 0;
}

6.3.9 Rövid összefoglaló

Ebben az alfejezetben megterveztük a TerraSense öntözőszelepének vezérlését. Az aktuátor egy NC mágnesszelep, amelyet GPIO-val és relével kapcsolunk; a biztonságos alapállapot zárt. A valve_ctrl modul (fájlok: valve.h, valve.c, main.c a ~/iot-labor/i015/ könyvtárban) idempotens valve_set_target(open) parancsot valósít meg, maximális bekapcsolási időt tart, és a valve_tick ellenőrzi a visszajelzést, eltérés esetén hibát jelez. A labor a native_sim célon fut, ahol a GPIO-t szimuláljuk; valós hardveren a visszajelző GPIO bemenetet kell bekötni. A továbbvitt eredmény a valve_set_target idempotens parancsfüggvény, amelyet az MQTT-parancsoknál (MQTT QoS, munkamenetek, retain, Last Will és MQTT 5), a lefelé irányuló parancsoknál (Parancsok és konfiguráció lefelé: kézbesítés, nyugtázás, időkorlát) és az eszközárnyéknál (Eszközárnyék és digitális iker: kívánt és jelentett állapot) használunk fel.

6.3.10 Források és ellenőrzési hiányok

A Zephyr GPIO API (gpio_pin_set_dt, gpio_pin_get_dt, GPIO_DT_SPEC_GET) stabil, a példa a Zephyr aktuális dokumentációjának mintáját követi, de a pontos függvénynevek és makrók verziófüggőek; használat előtt ellenőrizze a telepített Zephyr verziójának dokumentációját. A relé, szelep és félvezető kapcsoló paraméterei (élettartam, kapcsolási idő) nagyságrendi értékek, a konkrét adatlapoktól függenek. A native_sim board GPIO-szimulációs képessége korlátozott, ezért a labor szimulált módot használ; a valós hardver bekötése az Opcionális valós hardver: fejlesztőkártyák és szenzorok alfejezetben ismertetett eszközökhöz igazodik.
