15.4 PAM, NSS, LDAP/Kerberos és SSSD

A login hibák akkor válnak nehezen diagnosztizálhatóvá, ha ugyanaz a tünet három különböző rétegben keletkezhet: a felhasználó ismeretlen (identity lookup), a jelszó rossz (authentication), vagy a belépési szabály megtagadta a sessiont (account/session policy). A Unix-környezet ezt két többrétegű rendszerre bontja: a Name Service Switch (NSS) a névfeloldást, a Pluggable Authentication Modules (PAM) pedig a hitelesítési és session-döntéseket kezeli. Directory integráció esetén LDAP, Kerberos és az SSSD cache/offline rétege közéjük ékelődik, ami további hibalehetőségeket hoz be.

15.4.1 Definíció és működés

Az NSS egy adminisztrátori szabályozású dispatch réteg a glibc-ben. A getpwnam(3), getgrnam(3), getspnam(3) hívások a /etc/nsswitch.conf sorrendje szerint kérdezik az adatforrásokat. Az adatforrás lehet helyi fájl (files), rendszerd (systemd), SSSD (sss) vagy akár közvetlen LDAP, illetve NIS. A felhasználói oldali lekérdezést a getent passwd <user> vagy az id <user> parancs teszi láthatóvá. Az NSS nem tárol; delegál. A files modul a /etc/passwd, /etc/group, /etc/shadow tartalmát adja, az sss modul pedig az SSSD cache-én keresztül kérdez. Ha egy user a directoryban létezik, de a NSS nem adja vissza, a validációs réteg hibáját kell keresni.

A PAM egy adminisztratív módon komponálható policy-keret, amely a hitelesítési láncot négy fázisra bontja. A auth fázis a bizonyításra, az account fázis az engedélyező feltételekre, a session fázis a sessionkörnyezet beállítására, a password fázis a jelszóváltásra szolgál. Minden login service külön PAM-konfigurációt kap a /etc/pam.d/<service> alatt. Az Ubuntu jellemzően @include common-auth stílusú include-okat használ; az egyes modulok stackben összekapcsolva required, requisite, sufficient vagy optional vezérléssel futnak. A PAM nem tárol felhasználót, hanem a moduljain keresztül kérdez, és a stack eredményét összegzi. A pam_sss.so például az SSSD-nek delegálja az authentication és account döntéseket.

Az LDAP egy directory-protokoll, amely identity adatot szolgáltat. A user objektum posixAccount objectClass-szal és uidNumber, gidNumber, homeDirectory, loginShell attribútumokkal reprezentálja a POSIX identitást. A csoport posixGroup objectClass-szal és memberUid vagy member attribútummal tárolja a tagságot. Az LDAP nem hitelesítő protokoll; a bind vagy search adatot ad, hacsak nem valamilyen extensible módon használjuk. Az SSSD tipikusan LDAP search-öt használ az identity feloldásra.

A Kerberos egy hitelesítő-protokoll, amely ticketekkel bizonyítja az identitást. A user a jelszavával kér Ticket Granting Ticket-et (TGT), majd service ticketeket használ a szolgáltatásokhoz. A KDC (Key Distribution Center), realm, principal és keytab fogalma ide tartozik. A Kerberos erősen függ az időtől, a DNS-től és a névazonosságtól.

Az SSSD egy rendszerdémon, amely a remote identity/auth backendeket helyi cache-sel, offline döntéssel és egységes PAM/NSS interfésszel köti össze. A konfigurációs fájl /etc/sssd/sssd.conf, benne [sssd], [nss], [pam] és [domain/lab.example.net] szekciókkal. A domains sor mondja meg, hogy mely domaineket kezel, a services sor a nss, pam és opcionálisan sudo szolgáltatásokat kapcsolja be. Az id_provider = ldap az LDAP-t, az auth_provider = krb5 a Kerberost használ. A cache_credentials = true jelszó-cachet enged offline loginhoz; az entry_cache_timeout a névfeloldási cache lejáratát adja meg. Az SSSD cache miatt a directory-kérdés nem feltétlenül éri el azonnal a kiszolgálót.

A rétegek közötti szétválasztást mutatja az alábbi táblázat:

Kérdés Rendszer Példa parancs/API Jellemző hiba
Létezik-e a user? NSS getent passwd lab-ssh-user No passwd entry
Igazolta-e magát? PAM auth auth stack Authentication failure
Engedélyezett-e a belépés? PAM account account stack account locked, access denied
Mely csoportok? NSS/SSSD id lab-ssh-user group membership hiányos
Session felépült-e? PAM session session stack session setup failed

15.4.2 Kidolgozott példa

Hipotetikus labtopológia: labhost-1 Ubuntu 24.04 LTS SSSD kliens, ldap.lab.example.net (RFC5737 szerint 192.0.2.11) LDAP directory, kdc.lab.example.net (192.0.2.12) Kerberos KDC. A felhasználó lab-ssh-user, UID 10001, csoport lab-ssh-group.

A kliens SSSD konfigurációja /etc/sssd/sssd.conf:

[sssd]
domains = lab.example.net
services = nss, pam

[nss]
filter_users = root
filter_groups = root

[pam]
offline_credentials_expiration = 2

[domain/lab.example.net]
id_provider = ldap
auth_provider = krb5
chpass_provider = krb5
access_provider = simple

ldap_uri = ldaps://ldap.lab.example.net
ldap_search_base = dc=lab,dc=example,dc=net
ldap_user_search_base = ou=users,dc=lab,dc=example,dc=net
ldap_group_search_base = ou=groups,dc=lab,dc=example,dc=net
ldap_tls_cacert = /etc/sssd/pki/lab-ca.crt

krb5_realm = LAB.EXAMPLE.NET
krb5_server = kdc.lab.example.net
krb5_kpasswd = kdc.lab.example.net
krb5_canonicalize = false

cache_credentials = true
entry_cache_timeout = 600

A fájlt root tulajdonban, 0600 módban kell tartani. A sssd.conf pontos mezői az SSSD kiadástól függenek; a labban man sssd.conf és az Ubuntu csomag verziója ellenőrzendő. A PAM include-ok /etc/pam.d/sshd alatt tipikusan @include common-auth, @include common-account, @include common-session.

A /etc/nsswitch.conf kiinduló sorai:

passwd: compat systemd sss
group: compat systemd sss
shadow: compat sss

Ezután a tünet: ssh lab-ssh-user@labhost-1 közlemény Permission denied, please try again.. A diagnózis lépésenként:

  1. getent passwd lab-ssh-user nem ad kimenetet; a user ismeretlen a NSS rétegben.
  2. journalctl -u sssd.service -n 20 megmutatja, hogy az SSSD backend ldap_search failed: TLS error hibát rögzít.
  3. systemctl status sssd szerint a szolgáltatás active, tehát a process fut, de a domain hiba miatt nem szolgálja az identity kérdéseket.
  4. sssctl domain-status lab.example.net szerint Offline.
  5. getent hosts ldap.lab.example.net üres, tehát a DNS nem oldja fel a LDAP nevet. Hipotézis: a DNS hibája miatt az SSSD nem tud csatlakozni a directoryhoz, ezért NSS üres.
  6. A lab DNS szerverén a hiányzó ldap A rekord pótlása, majd a kliens cache-ének tisztítása nélkül systemctl restart sssd elindítja a domain újra felfedezését.
  7. Ellenőrzés: getent hosts ldap.lab.example.net visszaadja 192.0.2.11; sssctl domain-status lab.example.net szerint Online; getent passwd lab-ssh-user visszaadja a POSIX adatokat; sssctl user-checks -s ssh lab-ssh-user szerint user is authorized (a sssctl pontos opciója verziófüggő). A login sikeres.

15.4.3 MFA/SSH/console eltérő út

A console és az SSH nem ugyanazon a PAM service-en át megy. Az SSH-daemon a sshd service-t használja, a console login service-t. Mindkettő NSS-t kérdez a felhasználó létének eldöntésére, de a PAM policy eltérhet: például az SSH-n lehet publickey és password is, a console tipikusan password. Az SSH publickey autentikációt az sshd a PAM-tól függetlenül is csinálhat, de ha UsePAM yes, a PAM account és session fázisai ugyanúgy érvényesek. AZ MFA bevezetése PAM auth stackben újabb modulokkal történik, például pam_sss.so plusz egy egyszeri jelszó modul (OATH/TOTP) hozzáadásával. Az SSH keyboard-interactive mechanizmusa a PAM challenge-respose-ra van utalva.

15.4.4 Clock/DNS/TLS mint identity dependency

A Kerberos óra-csúszása (clock skew) alapértelmezés szerint legfeljebb néhány perc lehet. Ha a kliens és a KDC órája eltér, a TGT kérés KRB5KDC_ERR_CLOCK_SKEW hibát ad. A chronyc tracking vagy systemd-timesyncd segítségével ellenőrizhető. A DNS a hostnevek feloldásán és a realm canonicalizáción keresztül közvetlenül befolyásolja a Kerberos működését. Az LDAP ldaps kapcsolat a CA tanúsítvány és a szerver hostname ellenőrzésén keresztül hibatünetet mutat, ha a tanúsítvány lejárt vagy a név nem illik. Mindhárom függőség az identity hibákat gyakran a login közmondásos Permission denied mögé rejti, ezért a NSS/PAM rétegek mellett az infrastruktúra-függőségeket is vizsgálni kell.

15.4.5 Tipikus hibák és ellenpróbák

  • getent passwd üres, de ldapsearch talál user-t: SSSD domain konfiguráció hibás, a search base vagy filter rossz, a user nem posixAccount, vagy az NSS-ben hiányzik az sss. Ellenpróba: sssctl domain-status és sssctl user-checks.
  • Authentication failure: a user létezik, de a jelszó rossz, vagy a Kerberos PREAUTH_FAILED. Ellenőrző parancs: journalctl -u sssd -u sshd, saját kinit trace. Ne keverjük az account denieddel.
  • Account denied: a PAM auth sikeres, de az account fázis megtagadja. Ezt a pam_access, pam_succeed_if, expiry vagy policy okozza. Ellenpróba: sssctl user-checks -s ssh <user>, amely mutatja az account policy döntést.
  • SSSD cache stale: a csoporttagság vagy jelszóváltozás nem frissül azonnal. sssctl cache-expire -u <user> vagy a legacy sss_cache -E üríti a cachet.
  • Offline bejelentkezés: ha a directory/KDC nem elérhető, és cache_credentials = true nincs beállítva, az offline login meghiúsul. A [pam] offline_credentials_expiration szabályozza a cache-elt jelszó élettartamát.
  • sssd.conf rossz permission: a daemon nem indul, a journalctl -u sssd Permission denied hibát mutat. Fix: chmod 0600 /etc/sssd/sssd.conf.
  • NSS files előbb sss előtt: ha lokális user ugyanolyan névvel létezik, a directory user árnyékolási hibája lép fel; az id a lokális rekordot adja. A sorrend az adminisztrátori döntés.

A diagnosztika elve: először a NSS szintjét, azután a PAM hitelesítési fázist, majd a PAM account/session fázist, végül a hálózati függőségeket vizsgáljuk. Minden lépésben egy változtatás és annak verifikációja, nem egyszerre több.

15.4.6 Feladatok

  1. Magyarázó feladat: Egy labuser login SSH-n Permission denied hibát ad. getent passwd labuser visszaadja a felhasználót; journalctl -u sshd sorban Failed password for labuser olvasható. Milyen réteg hibázik? Írja le a diagnosztikai lépéseket, és sorolja fel, milyen további adatok kellenek a pontos okhoz.

  2. Adminisztratív/konfigurációs feladat: A labhoston a directory felhasználók nem elérhetők. Készítse el az /etc/sssd/sssd.conf fájlt LDAP id_provider, Kerberos auth_provider, cache/offline policy beállításokkal. Módosítsa a /etc/nsswitch.conf-et. Állítsa be a fájljogot, indítsa újra az SSSD-t, és ellenőrizze getent passwd lab-ssh-user kimenetét. Adja meg a rollback lépéseket is.

  3. Diagnosztikai/failure/recovery feladat: A Kerberos ticket-alapú login hirtelen Permission denied hibát ad. A napló szerint a kinit Clock skew too great hibát rögzít. Gyűjtsön adatokat a kliens órájáról és a KDC elérhetőségéről. Állítsa helyre a bejelentkezést úgy, hogy a postcondition a sikeres TGT-kérés legyen.

15.4.7 Megoldások

  1. Mivel a NSS visszaadja a felhasználót, az identity fine. A Failed password az auth réteg hibája. Hipotézisek: rossz jelszó, Kerberos preauthentication fail, PAM modul rossz ösztön, vagy a pam_sss nem hívódik. Adatgyűjtés: journalctl -u sssd -n 100, sssctl user-checks -s ssh labuser (ha elérhető), grep -R 'pam_sss' /etc/pam.d/. Ha Kerberos PREAUTH_FAILED, a jelszó nem megfelelő vagy a kliens óra csúszik. Egyszerre egy változtatás: először az óra ellenőrzés, majd a jelszó-teszt. Postcondition: journalctl friss auth sora sikeres, a sssctl user-checks szerint user is authorized.

  2. A fenti konfigurációs példa használható. A fájl létrehozása után:

sudo install -m 0600 /tmp/sssd.conf.lab /etc/sssd/sssd.conf
sudo sed -i 's/^passwd:.*/passwd: compat systemd sss/; s/^group:.*/group: compat systemd sss/; s/^shadow:.*/shadow: compat sss/' /etc/nsswitch.conf
sudo systemctl restart sssd
getent passwd lab-ssh-user
sssctl domain-status lab.example.net

Elvárás: getent visszaadja a user POSIX adatait, sssctl szerint a domain Online. Rollback: a korábbi config visszaállítása, systemctl restart sssd, sssctl cache-expire -E ha szükséges.

  1. Adatgyűjtés: timedatectl status, chronyc tracking (vagy systemctl status systemd-timesyncd), getent hosts kdc.lab.example.net, journalctl -u sssd. A Clock skew too great azt jelzi, hogy a kliens óra eltér a KDC-től. Helyreállítás: telepített chrony esetén chronyc makestep, vagy systemctl restart systemd-timesyncd. Ellenőrzés: kinit -p lab-ssh-user párbeszéd, vagy a sikeres SSH login. Postcondition: a kliens és a KDC időeltérése a megengedett értéken belül, a Kerberos TGT létrejön.

15.4.8 Rövid összefoglaló

Az NSS a névfeloldási lánc, a PAM a hitelesítési döntési lánc. Az LDAP identitástartót, a Kerberos hitelesítő-protokollt biztosít, az SSSD pedig cache-sel és offline policyval köti őket a helyi rendszerhez. A login hibáknál először mindig válasszuk szét: identity lookup, authentication, account/session. Directory hiba forrása DNS, TLS, óra-csúszás vagy cache-lejárat is lehet. Definíciók: NSS = glibc modul-lánc a passwd/group/shadow névfeloldáshoz. PAM = stack-alapú auth/account/session policy. SSSD = identity/auth broker cache-sel és offline tudással.
