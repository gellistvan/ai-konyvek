43.2 etcd, quorum, backup és restore

43.2.1 Motiváció

A Kubernetes control plane működése közben az etcd tárolja a cluster desired state magját: minden Deployment, Service, ConfigMap, Secret, RBAC objektum, PV/PVC leíró, namespaces és a legtöbb kiegészítő API-resource adatát. A node-ok, a kubelet és a workloadok újraindulhatnak, de ha az etcd adat elveszik, a cluster elveszíti a „miért így nézzen ki a rendszer” tervét. A container image-ek és az application persistent volume-ok külön védhetők, viszont az etcd nélkül a Kubernetes API gyakorlatilag üres lesz, így a cluster state-et konzisztens, helyreállítható és rendszeresen ellenőrzött adatként kell kezelni. Nem elég a fájlrendszer-szintű backup; a running etcd-ről konzisztens pillanatfelvétel kell, mert a plain file copy a memóriában lévő, még nem fsync-elt állapotot is tartalmazhat, illetve inkonzisztens lehet. A d047-ben tárgyalt fsync tartóssági határ és a d099-ben tárgyalt disaster recovery keret itt konkrét adatbázis-szintű folyamatot kap.

43.2.2 Definíció és működés

43.2.2.1 Consensus, member, leader és quorum

Az etcd egy elosztott, kulcs-érték jellegű state store, amely a Raft consensus algoritmust használja. A cluster member-ekből áll; minden member egy-egy etcd server process, tipikusan egy control plane node-on. Egy adott időben az egyik member a leader, a többi follower. A write request a leaderhez megy; a leader bejegyzi a logba, replikálja a bejegyzést a follower-ökhöz, és csak akkor tekinti commitáltnak, ha a quorum (többség) tartósan megerősítette. A committed entry utána kerül alkalmazásra a state machine-ben, tehát olvashatóvá válik lineáris olvasás esetén.

Definíció: quorum – egy nn méretű etcd cluster esetén a quorum

Q=⌊n2⌋+1 Q = \left\lfloor \frac{n}{2} \right\rfloor + 1

tag. Az etcd csak akkor elérhető írásra és lineáris olvasásra, ha legalább QQ tag elérhető, egymással kommunikál, és a leader ismeri a quorumot. Ha a cluster ennél több tagot veszít, read-only állapotba kerül, és a Kubernetes API server is elveszíti a write-ot, ami gyakran etcdcluster: cannot create resource ... vagy Unavailable API hiba formájában látszik.

Az availability és a hibatűrés a tagok számától függ:

Tagok száma Quorum Tűrt hibás tag Megjegyzés
1 1 0 Lab vagy ideiglenes teszt, nem production
3 2 1 Minimális production HA cluster
5 3 2 Nagyobb hibatűrés, nagyobb replikációs költség

A 4 tag nem előnyös: a quorum 3, tehát ugyanúgy csak 1 hibát tűr, mint a 3, de több disk és network overhead. A production etcd-t általában 3 vagy 5 memberre méretezik.

A Raft leader election során a tagok term-ekben versenyeznek. Ha a current leader leáll, a follower-ök választást indítanak; a clustert az új leader veszi át. A read request lineáris konszisztenciájához is quorum ellenőrzés kell, mert anélkül egy izolált follower régi adatot szolgáltathatna. Az etcdben a Serializable read viszont nem igényel quorumot, de nem lineáris.

43.2.2.2 Latency, fsync, disk és network függőség

A commit path során az etcd a logot a leader és a quorumot adó follower-ök diskjére fsync-kel írja, mielőtt a művelet sikeresnek minősül. Ezért a commit latency legalább akkora, mint a legrosszabb lassú disk a quorumban; egyetlen lassú SSD vagy hálózati partíció növelheti a tail latency-t. A hozzávetőleges commit time:

Tcommit≈max(tleader fsync,tquorum median of(RTT2+tfollower fsync)) T_{\text{commit}} \approx \max\left(t_{\text{leader fsync}},\ t_{\text{quorum median of}} \left(\frac{\text{RTT}}{2} + t_{\text{follower fsync}}\right)\right)

ahol: - tleader fsynct_{\text{leader fsync}} a leader lokális WAL fsync ideje, - RTT\text{RTT} a leader és follower közötti round-trip time, - tfollower fsynct_{\text{follower fsync}} a follower lokális fsync ideje.

Ha az etcd disk write cache úgy van beállítva, hogy power loss esetén adatvesztés lehetséges, az fsync nem ad valódi tartóssági garanciát; ezért az etcd dokumentációja alacsony latency SSD-t és power-loss protected write cache-t ajánl. A network RTT a control plane node-ok közötti kapcsolat késleltetése; ha a follower-ök távoli failure domainben vannak, a commit latency növekszik, de a durability javul a failure domain szétválasztással. A journald és a d047-ben tanult fsync szabályok itt is érvényesek.

43.2.2.3 Snapshot, restore és member identity

A Raft log folyamatos növekedését az etcd időszakos snapshot-okkal tömöríti. Az etcdctl snapshot save egy konzisztens pillanatfelvételt készít, amely a snapshot időpontjában committed state-et tartalmazza. A snapshot nem a futó data directory másolata, hanem az etcd által generált, ellenőrzött artifact. A snapshot fájl tartalmazza a key-value adatokat, a revisiont, a total key countot és a checksumot.

A restore során az etcdctl snapshot restore egy új data directory-t hoz létre. Az etcd a data dirben tárolt member identity-hez kötődik: member ID, cluster ID, peer URL, name. Egy snapshot restore alapértelmezésben új single-node cluster-t készít, amelynek az initial cluster state új, és a további membereket explicit módon kell felvenni. Ha egy meglévő, több tagú etcd clusterbe akarunk egy snapshotot visszaállítani, akkor nem egyszerűen a data dirbe másoljuk a fájlt, mert a régi member ID és cluster ID ütközhet. A hivatalos disaster recovery eljárás szerint vagy az egész etcd clustert a snapshotból újraépítjük, vagy a snapshotból egy új membert indítunk, és a többit explicit member add paranccsal illesztjük hozzá.

A peer URL-ek és a certificate-ek is részei a member identity-nek. A restored data dirben a --initial-advertise-peer-urls és --initial-cluster paramétereknek egyezniük kell a későbbi systemd unit és a peer certificate Subject Alternative Name (SAN) értékeivel, különben az etcd elutasítja a peer kapcsolatot.

43.2.2.4 Cluster object backup versus application volume backup

Az etcd snapshot a Kubernetes object state-et menti: Deployment spec, Service ClusterIP, Secret adat, RBAC, CRD, namespace és hasonló. Ez nem tartalmazza: - a container image rétegeit vagy registry-digesteket, - a PersistentVolume on-disk adatokat (például egy PostgreSQL database data dirje), - az alkalmazás logjait vagy a node local cache-t.

Egy teljes recovery ezért általában három különálló mentést igényel: etcd snapshot a cluster object state-hez, PV snapshot/backup az application data-hoz, és a control plane PKI/config backup a cert/key/encryption anyagokhoz. A d099-ben tárgyalt RPO az etcd snapshot időszerűségétől függ, az application data esetén pedig a PV snapshot időszerűségétől.

43.2.2.5 Encryption keys és certificates recovery

Ha a Kubernetes API server encryption-at-rest engedélyezett a Secrets számára, akkor az etcd tárolt Secret tartalom titkosított. A titkosításhoz használt key gyakran a control plane node-on található configuration fájlban van, például /etc/kubernetes/encryption-config.yaml. Ezt a fájlt az etcd snapshot mellett kell menteni, mert a snapshot visszaállítható ugyan, de a kulcs nélkül a Secrets nem dekódolhatók.

A Kubernetes control plane emellett PKI-ra épül: a cluster CA, apiserver cert, kubelet client cert, admin cert és etcd peer/server cert kulcsfontosságú. A restore akkor lesz használható, ha az etcd adatot visszaállítjuk, de a control plane node-okon a megfelelő cert/key párok jelen vannak, és a CA-t a kubelet, apiserver és admin client is elfogadja. A kubeadm esetén ezek jellemzően /etc/kubernetes/pki/ alatt vannak. A cert/key recovery ezért nem külön etcd probléma, hanem a control plane recovery része.

43.2.2.6 Supported recovery procedure és data verification

A hivatalos, verziózott etcd recovery eljárás nem „egy parancs mindenre”, hanem ellenőrzött lépéssor: snapshot mentés, snapshot status ellenőrzés, a memberek izolálása, restore új data dirbe, peer URL és cert konfiguráció, az etcd systemd unit indítása, majd data verification. A verification nem csak annyi, hogy a daemon fut; a tartalmat is tesztelni kell. Az etcdctl snapshot status a fájl integritását és a revision adatot mutatja. A restore után etcdctl get lekérdezéssel ellenőrizhető, hogy a várt kulcsok – például a Kubernetes /registry/deployments prefix – jelen vannak, és kubectl get mutatja a recovery időpontjában érvényes API objektumokat.

A példa környezet: - Cluster: lab-cluster - Control plane node-ok: lab-cp0, lab-cp1, lab-cp2 - Etcd memberek: ugyanezen a három node-on, 3 tag - Cél: snapshot készítése lab-cp0-on, majd izolált restore teszt egy disposable könyvtárba

A példa feltételezi a kubeadm által generált cert path-eket; más telepítő esetén az elérési utak és a peer URL-ek eltérhetnek.

43.2.3.1 Előfeltétel és inventory

A lab host lab-cp0 state: - OS: Ubuntu Server 24.04 LTS, patched kernel - Etcd cert-ek: /etc/kubernetes/pki/etcd/ - Etcd data dir: /var/lib/etcd - Privilege: root vagy sudo

A módosító parancsok itt snapshotot és disposable restore könyvtárat hoznak létre, az élő etcd adatot nem írják. A cleanup csak a megadott lab- prefixű fájlokra terjed ki.

43.2.3.2 Snapshot készítése

Az etcd member lista lekérdezése a lab-cp0 node-on:

# target: lab-cp0, account: root, context: lab-cluster
# cél: member lista, leader azonosítása
etcdctl member list     \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

Várható kimenet (illusztratív):

8e9e6e... started lab-cp0 https://192.0.2.10:2380 false
1f8a6c... started lab-cp1 https://192.0.2.11:2380 false
b57f3d... started lab-cp2 https://192.0.2.12:2380 true

A true oszlop a leadert jelöli. A példa address az RFC5737 dokumentációs címtartomány, a lab saját címe attól eltérhet.

Ezután snapshot készítése:

# target: lab-cp0, root, lab-cluster
# cél: konzisztens etcd snapshot + checksum, retention
BACKUP_DIR="/var/backups/etcd"
SNAPSHOT_FILE="${BACKUP_DIR}/snapshot-$(date -u +%Y%m%dT%H%M%SZ).db"

mkdir -p "${BACKUP_DIR}"

etcdctl snapshot save "${SNAPSHOT_FILE}" \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

sha256sum "${SNAPSHOT_FILE}" > "${SNAPSHOT_FILE}.sha256"
ls -lh "${SNAPSHOT_FILE}" "${SNAPSHOT_FILE}.sha256"

Várható kimenet:

Snapshot saved at /var/backups/etcd/snapshot-20250408T120000Z.db
-rw------- 1 root root 2.3M Apr  8 12:00 snapshot-...db
-rw------- 1 root root   99 Apr  8 12:00 snapshot-...db.sha256

A snapshot jogosultsága alapból korlátozott; a fájlt off-node, dedicated backup locationre kell másolni, mert a helyi node disk nem ad failure domain védelmet.

43.2.3.3 Snapshot status ellenőrzés

# target: lab-cp0, root, lab-cluster
etcdctl snapshot status "${SNAPSHOT_FILE}" --write-out=table

Várható kimenet:

+----------+----------+------------+------------+
|   HASH   | REVISION | TOTAL KEYS | TOTAL SIZE |
+----------+----------+------------+------------+
| 8f3a...d |  1234567 |       1234 | 2.3 MB     |
+----------+----------+------------+------------+

A REVISION és a TOTAL KEYS azt mutatja, hogy a snapshot nem üres, és a HASH az integritást biztosítja.

43.2.3.4 Disposable restore teszt

Az élő cluster adatirányát nem módosítjuk; a restore egy új, izolált data dir készítését jelenti. Mivel a lab-cp0-on futó etcd már foglalja a 2379/2380 portokat, a restore teszt peer URL-nek 2480-at használunk, és nem indítjuk a daemont, csak a data dir létrehozását ellenőrizzük:

# target: lab-cp0, root, lab-cluster
RESTORE_DIR="/var/lib/etcd-lab-restore-test"

etcdctl snapshot restore "${SNAPSHOT_FILE}" \
  --name lab-restore-test \
  --initial-cluster "lab-restore-test=https://127.0.0.1:2480" \
  --initial-cluster-token "lab-restore-token" \
  --initial-advertise-peer-urls "https://127.0.0.1:2480" \
  --data-dir "${RESTORE_DIR}"

ls -ld "${RESTORE_DIR}"

Várható kimenet:

2025-04-08 12:00:00 ... restored snapshot to /var/lib/etcd-lab-restore-test
drwx------ 3 root root 4096 Apr  8 12:00 /var/lib/etcd-lab-restore-test

A restore során az etcd létrehozza a member/ alkönyvtárat az új member ID-vel. Ez a lépés még nem módosítja az élő cluster taglistáját; valódi recoverynél a további lépések a peer URL és a systemd unit frissítése, majd a kubelet irányítása.

43.2.4 Tipikus hibák és ellenpróbák

A plain file copy mint snapshot. Ha valaki futó etcd data dir másolatát használja, az a snapshot pillanatában memóriában lévő nem commitált állapot miatt inkonzisztens lehet. Tünet: a restore után az etcd bad snapshot vagy unexpected EOF hiba. Helyes eljárás: mindig etcdctl snapshot save.

Cert mismatch. A restored etcd nem indul, vagy a peer connection hibát ad: x509: certificate signed by unknown authority. Hipotezis: a --cacert, --cert vagy --key path nem a restored data dirhez tartozó node PKI-jából való. Ellenpróba: openssl x509 -noout -subject -issuer a cert-en, és etcdctl --endpoints ... member list a restored endpointon.

Restore a meglévő clusterbe peer URL frissítés nélkül. Ha a snapshotot visszaállítjuk egy tag data dirjébe, de a régi member ID és cluster ID megmarad, a többi member elutasítja a connectet, és split-brain vagy member ID mismatch lép fel. Ezért a restore-t új initial cluster-token és új name megadásával kell tervezni, és a többi membert szabályozottan hozzáadni.

Lassú disk vagy network. A commit latency növekedése látszik az etcd metrikákban (etcd_disk_wal_fsync_duration_seconds, etcd_network_peer_round_trip_time_seconds). Ha a p99 fsync 20 ms fölé nő, a leader election timeout közelében lehet a határ. Tünet: a kubectl parancsok lassulnak, etcdctl endpoint health ingadozó. A diagnózis a node disk IOPS és a peer RTT mérése; a javítás a disk vagy a network path cseréje, nem a timeout globális növelése.

Csak etcd snapshot, de a Secrets titkosítási kulcs nincs mentve. A restore sikeres, de a Secret-ek olvashatatlanok. Tünet: kubectl get secret -n app hiba, az apiserver logban decrypt error. Az encryption config és key mentése ugyanabba a recovery artifactbe kell.

43.2.5 Feladatok

43.2.5.1 1. Magyarázó feladat: quorum és member availability

Egy etcd cluster 5 tagból áll. Számold ki a quorumot, és add meg, hány tag hirtelen leállása után marad írható a cluster. Magyarázd el, mit jelent, ha 3 tag leáll, és miért nem elegendő a 2 elérhető tag. Feltételezd, hogy a hálózat a maradék tagok között rendben van.

43.2.5.2 2. Adminisztrációs/konfigurációs feladat: automatikus etcd snapshot

Írj egy bash scriptet lab-etcd-snapshot.sh néven, amely a lab-cp0 node-on, root jogosultsággal: - létrehozza a /var/backups/etcd könyvtárat, - timestamp alapú snapshot fájlt készít, - SHA-256 checksumot ír, - a 7 napnál régebbi snapshotokat törli, - a script legyen set -euo pipefail-lel idempotensen futtatható. A script ne használjon éles cloud storage-ot; a cél a lokális lab backup könyvtár. Ellenőrizd, hogy a snapshot fájl és a checksum megjelenik.

43.2.5.3 3. Diagnosztikai/failure/recovery feladat: one-member restore és control plane visszatérés

A lab-cp0 etcd data directory-ja korrupt lett, a member nem indul el. A cluster jelenleg egy membere sem ér quorumot, mert korábban mindhárom tag ugyanazon a node-hálózati failure domainen volt, és a kiesés mindent érintett. A snapshot fájl rendelkezésre áll. Tervezd meg a recovery lépéseket egy támogatott single-node restore esetén: milyen parancsokkal állítasz vissza egy új data dir-t, milyen cert és peer URL konfigurációt használsz, és hogyan ellenőrzöd, hogy a cluster object state visszatért-e? Add meg a postconditiont, és azt is, miért nem szabad a régi, korrupt data dir-t egyszerűen felülírni.

43.2.6 Megoldások

43.2.6.1 1. Quorum és member availability

Az n=5n=5 esetén a quorum:

Q=⌊52⌋+1=2+1=3 Q = \left\lfloor \frac{5}{2} \right\rfloor + 1 = 2 + 1 = 3

Tehát a cluster írható, ha legalább 3 tag elérhető. Így 2 tag leállása esetén a maradék 3 tag quorumot ad, a cluster írható. 3 tag leállása esetén 2 tag marad, ami kevesebb, mint Q=3Q=3, ezért a cluster read-only/írásképtelen. A 2 elérhető tag nem tudja garantálni, hogy egy korábbi write ne csak a másik oldalon commitálódott; ezért a Raft biztonsági tulajdonsága miatt nem írhat.

Postcondition: a cluster 2 tag-kiesés után is írható; 3 tag-kieséskor a write útvonal leáll, de a 2 tag adatot nem korrumpál, és a kiesés visszaállása után újra quorumot érhetnek el.

43.2.6.2 2. Automatikus etcd snapshot script

A script:

#!/usr/bin/env bash
set -euo pipefail

# Lab etcd snapshot script
# Target: lab-cp0, root, lab-cluster

BACKUP_DIR="/var/backups/etcd"
ETCD_ENDPOINT="https://127.0.0.1:2379"
CA_CERT="/etc/kubernetes/pki/etcd/ca.crt"
SERVER_CERT="/etc/kubernetes/pki/etcd/server.crt"
SERVER_KEY="/etc/kubernetes/pki/etcd/server.key"
TIMESTAMP="$(date -u +%Y%m%dT%H%M%SZ)"
SNAPSHOT_FILE="${BACKUP_DIR}/snapshot-${TIMESTAMP}.db"

mkdir -p "${BACKUP_DIR}"

etcdctl snapshot save "${SNAPSHOT_FILE}" \
  --endpoints="${ETCD_ENDPOINT}" \
  --cacert="${CA_CERT}" \
  --cert="${SERVER_CERT}" \
  --key="${SERVER_KEY}"

sha256sum "${SNAPSHOT_FILE}" > "${SNAPSHOT_FILE}.sha256"

# Retention: töröld a 7 napnál régebbi lab snapshot fájlokat
find "${BACKUP_DIR}" -maxdepth 1 -type f -name 'snapshot-*.db' -mtime +7 -delete

ls -lh "${SNAPSHOT_FILE}" "${SNAPSHOT_FILE}.sha256"

Ellenőrzés: a parancs kimenetén látszik a snapshot és a .sha256 fájl; a find a 7 napnál régebbieket törli. A set -euo pipefail miatt bármely etcdctl hiba leállítja a scriptet, így nem generál üres checksumot.

Postcondition: a /var/backups/etcd alatt az adott lab-cp0 node-on van legalább egy snapshot + checksum pár, a régi fájlok a retention után 7 napnál nem régebbiek.

43.2.6.3 3. One-member restore tervezése

A recovery lépéssor:

  1. Snapshot kiválasztása: a legfrissebb, etcdctl snapshot status által ellenőrzött snapshot, például /var/backups/etcd/snapshot-<id>.db.

  2. Új data dir restore: a korrupt /var/lib/etcd helyett új példány, például /var/lib/etcd-lab-restored, az etcdctl snapshot restore paranccsal, single-node initial cluster-t használva:

    # target: lab-cp0, root
etcdctl snapshot restore "${SNAPSHOT_FILE}" \
  --name lab-cp0-restored \
  --initial-cluster "lab-cp0-restored=https://192.0.2.10:2380" \
  --initial-cluster-token "lab-restore-token" \
  --initial-advertise-peer-urls "https://192.0.2.10:2380" \
  --data-dir "/var/lib/etcd-lab-restored"

    A peer URL a node tényleges lab címét használja, a cert SAN-nek tartalmaznia kell.

  3. Cert és unit frissítése: a /etc/kubernetes/pki/etcd/ cert-eket a restored data dir-hez illesztjük; a systemd unit --data-dir, --name, --initial-advertise-peer-urls paraméterét frissíteni kell, majd systemctl daemon-reload és systemctl start etcd.

  4. Control plane indítás: miután az etcd health OK, a kube-apiserver-t újraindítjuk, és kubectl get nodes segítségével ellenőrizzük, hogy a Kubernetes API látja a node-okat.

  5. Data verification: etcdctl get --prefix /registry/ mutatja a Kubernetes objektumok jelenlétét; kubectl get deployment --all-namespaces és kubectl get secret -n lab-app ellenőrzi a konkrét lab objektumokat.

A régi korrupt data dir-t nem szabad egyszerűen felülírni, mert a benne lévő member ID és journal adatok ütközhetnek a többi taggal; a hivatalos recovery új member identity-t és új cluster config-ot épít.

Postcondition: az etcd cluster újra írható; a lab-app namespace Deployment és Secret objectek jelen vannak a snapshot időpontjától kezdve; a control plane kubectl API válaszol; az RPO a snapshot időpontja, az RTO a mérési terv szerinti recovery idő.

43.2.7 Rövid összefoglaló

Az etcd a Kubernetes object state elosztott, konszenzus alapú tárolója; a quorum határozza meg, hány tag kiesését tűri a cluster írásra. A snapshot biztonságos, konzisztens mentési forma, amelyet a member identity, cert/key és encryption anyagok mellett kell kezelni. A restore-t mindig új member identity-vel, támogatott eljárással, adatverifikációval kell végrehajtani, nem a futó data dir másolásával. Az etcd snapshot csak a Kubernetes object state-et menti, az application volume és a PKI külön recovery artifactet igényel. Az fsync latency, a disk és a network kritikus a commit path-on.

Továbbhasznált definíciók:

  • Quorum: a consensus működéshez szükséges többség, Q=⌊n/2⌋+1Q=\lfloor n/2\rfloor+1 tag; ennyi tag megerősítése kell a commit-hoz.
  • etcd snapshot: konzisztens, ellenőrzött pont-in-time mentés, amely a committed key-value state-et tartalmazza.
  • Member identity: az etcd tag egyedi azonosítója, cluster ID-ja, peer URL-je és kapcsolódó certificate konfigurációja; restore-nál újra kell állítani.

43.2.8 Források és ellenőrzési hiányok

A fejezetben használt alapelvek a stabil etcd/Raft fogalmakon alapulnak. Az alábbi hivatalos források kiindulópontok, de jelen kérésben nem ellenőriztem őket; a pontos verzióspecifikus parancsok, zászlók és eljárások a lab környezetben ellenőrzendők:

  • Kubernetes documentation
  • etcd documentation
  • libvirt documentation
  • Google SRE book

Ellenőrzési hiányok: a használt etcdctl verzió és a Kubernetes storage version nem rögzített; a kubeadm cert path-ek a példában feltételezettek, más telepítő esetén eltérhetnek. A snapshot restore flag nevei, a peer URL és a cert SAN pontos illesztése a lab release ellenőrzését igényli. A snapshot retention script itt lokális lab célra készült, nem production backup storage-ra.
