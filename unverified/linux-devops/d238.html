48.3 C++ build/test/sanitizer és image artifact

48.3.1 Motiváció és cél

Egy szenior C++ fejlesztő gyakran úgy tekint a CI-re, mint „csak egy másik gépre”, pedig a CI feladata itt nem a szintaxis ellenőrzése, hanem az, hogy a release artifact visszakereshető, reprodukálható és ABI-szempontból auditálható legyen. A lokálisan működő bináris nem bizonyíték arra, hogy ugyanaz a forrás, ugyanaz a toolchain és ugyanaz a runtime dependency adja a production artifactot. A d238 alfejezet ezért a meglévő C++ tudást arra használja, hogy felépítsen egy CI-native build mátrixot (build matrix) és artifact szerződést.

Nem tanítunk újra C++ szintaxist, CMake-alapú targetet, tesztelési alapot vagy pointerkezelést. A cél a fordítási, tesztelési és csomagolási réteg üzemeltetési szerződése.

48.3.2 Definíció: build mátrix és artifact szerződés

A build mátrix dimenziók kontrollált halmaza, amelyben minden cella egy explicit bemeneti kombinációt jelent: architektúra, compiler, build mode, sanitizer, test scope és dependency-készlet. A mátrix akkor üzemeltethető, ha minden cellához tartozik:

  • source revision,
  • toolchain verzió,
  • fordítási környezet,
  • teszteredmény,
  • artifact checksum,
  • postcondition.

A release artifact itt nem csupán a natív bináris. Az artifact szerződés legalább a következőket köti össze: source revision, build identity, native build-id, image digest, config és data schema verzió, SBOM, test report, valamint retention policy. A provenance az a bizonyítéklánc, amely az artifactot a bemenetekhez és a buildfolyamathoz köti, például SLSA-szerűen.

A d068-ban tárgyalt ELF DT_NEEDED, SONAME, symbol version és RUNPATH itt azért tér vissza, mert az artifact runtime szerződése ugyanolyan fontos, mint a fordítási mátrix. A d237-ben tárgyalt izolált runner adja azt a környezetet, ahol a build nem a fejlesztő gépétől függ.

48.3.3 Buildmátrix dimenziók

A mátrixot nem érdemes minden dimenzió descartes-szorzataként futtatni, mert a sanitizer és a build mode egy része inkompatibilis vagy zajos. A tervezésnél a dimenziókat először külön kell felvenni, majd a cellákat indoklással szűkíteni.

Dimenzió Példaérték Diagnosztikai cél
Architektúra x86_64, aarch64 ABI, pointerméret, memóriamodell, endianness
Compiler g++, clang++ warning, optimalizáció, sanitizer-támogatás
Build mode Debug, RelWithDebInfo, Release assertions, optimalizáció, debug adat
Sanitizer none, address, undefined, thread memóriahiba, UB, data race
Test scope unit, integration gyors visszajelzés vagy valós függőség

A lab alapelve, hogy a toolchain verzió ne a CI provider aktuális „latest” címkéjéből jöjjön. Az Ubuntu Server 24.04 LTS lab esetén a g++ és clang++ verzióját a lab toolchain.lock rögzíti; a pontos verziószámot jelen alfejezet nem ellenőrzi. Az architektúra sem pusztán a runner címkéje: CMAKE_SYSTEM_PROCESSOR, a használt C++ standard és a -march/-mtune explicit bemenet.

A determinisztikus bemenet része a tiszta checkout, a dependency lock és a fordítási flag rögzítése. A CMake/Ninja páros azért jó, mert a CMakeCache.txt szövegesen mutatja a konfigurációs döntéseket, a Ninja pedig szigorúan a bemeneti fájlok alapján épít. A reprodukálhatóságot a következők javítják:

  • -ffile-prefix-map=<abs_source>=. vagy -fdebug-prefix-map=...,
  • -Wl,--build-id=sha1,
  • -DNDEBUG csak a Release és RelWithDebInfo módban,
  • fix C++ standard, például -DCMAKE_CXX_STANDARD=20,
  • CMAKE_INSTALL_RPATH_USE_ORIGIN=ON, hogy a telepített bináris a saját könyvtárához képest keressen.

48.3.4 Sanitizer scope és elszigetelés

A sanitizer cellákat nem szabad egyetlen nagy „mindent bekapcsolunk” fordításba zsúfolni. A cél az, hogy a hibát a legközelebbi forrásnál kapjuk el, de a futási környezet ne hamisítsa meg az eredményt.

AddressSanitizer (ASan) a unit tesztek és a fókuszált integrációs tesztek alatt hasznos. Célja a heap/stack/global buffer overflow, use-after-free és hasonló memóriahibák. A binárist -fsanitize=address -fno-omit-frame-pointer -g flaggel kell fordítani. Az ASAN_OPTIONS beállítások közül a labban inkább szigorítunk, például strict_string_checks=1:detect_stack_use_after_return=1:halt_on_error=1, minthogy globálisan kikapcsolnánk a leak detectiont.

UndefinedBehaviorSanitizer (UBSan) a -fsanitize=undefined mellett -fno-sanitize-recover=all beállítással futtatható, hogy az első UB leállítsa a tesztet, ne csak logoljon. A signed overflow, shift, null dereference és hasonlók a C++ kódban valós hibák lehetnek.

ThreadSanitizer (TSan) kizárólag a szálkezelést tesztelő unit tesztekre való, és nem kombinálható ASan-nel. A TSan saját memory mappinget használ, ezért a labban külön cella kell. A TSan-zaj csökkentésére suppression file használható, de a globális kikapcsolás nem elfogadott.

Az integrációs teszteket nem kell minden sanitizer alatt futtatni, mert a külső folyamatok és a hálózat olyan hibákat is produkálhat, amelyek nem a vizsgált bináris hibái. A labban az integrációs teszt RelWithDebInfo build mode alatt fut, a sanitizeres unit tesztek pedig Debug módban.

48.3.5 Artifactkör: SBOM, package, image, debug

A release artifact nem állhat meg a csupasz binárisnál. A lab a következő artifact osztályokat különbözteti meg:

  • natív bináris: a telepített, stripelt executable vagy library,
  • debug artifact: a különválasztott debug symbol és a hozzá tartozó build-id,
  • test report: CTest JUnit XML,
  • SBOM: Software Bill of Materials, amely a source revision mellett felsorolja a build toolokat, a DT_NEEDED függőségeket, a runtime csomagokat és a bináris hasheket,
  • native package: CPack DEB,
  • container image: runtime image digesttel.

A debug symbol és a build-id összekapcsolása a d068-ban bemutatott nativeszerződés gyakorlati következménye. A strip --strip-unneeded után a bináris kisebb, de a readelf -n továbbra is mutatja a build-id-t. A külső debug fájl a objcopy --add-gnu-debuglink segítségével visszakereshető. Ha a debug fájl és a bináris build-id-je eltér, a debugger vagy a symbolizer rossz forrást fog mutatni.

A konténerkép esetén a build stage-ben futtatunk mindent, a runtime stage-be pedig csak a binárist és a szükséges runtime függőségeket másoljuk. A debug symbol ne kerüljön a production image-be; az külön artifact.

48.3.6 Kidolgozott példa

A példa egy lab-cpp-svc nevű szolgáltatást épít. A cél egy x86_64-es RelWithDebInfo release artifact, külön debug fájllal, SBOM-mal és DEB csomaggal. A parancsokat a tananyaggenerátor nem futtatja; az alábbi kimenet várt/illusztratív.

Mező Érték
labhost lab-runner-01
repository lab-cpp-svc
source revision 0a1b2c3d
arch x86_64
compiler g++
build mode RelWithDebInfo
install prefix /opt/lab-cpp-svc
artifact store lab-cicd-artifacts/release
image lab-registry.example/lab-cpp-svc:0.1.0

A konfiguráció és a build:

cmake -S . -B build -G Ninja \
  -DCMAKE_BUILD_TYPE=RelWithDebInfo \
  -DCMAKE_CXX_COMPILER=g++ \
  -DCMAKE_INSTALL_PREFIX=/opt/lab-cpp-svc \
  -DCMAKE_CXX_STANDARD=20 \
  -DCMAKE_CXX_FLAGS_RELWITHDEBINFO="-O2 -g -DNDEBUG -ffile-prefix-map=$(pwd)=." \
  -DCMAKE_SHARED_LINKER_FLAGS="-Wl,--build-id=sha1" \
  -DCMAKE_INSTALL_RPATH_USE_ORIGIN=ON

cmake --build build --parallel
ctest --test-dir build --output-on-failure \
  --output-junit dist/test-results/junit.xml

cmake --install build --prefix dist/relwithdebinfo

install -d dist/debug
objcopy --only-keep-debug \
  dist/relwithdebinfo/bin/lab-cpp-svc \
  dist/debug/lab-cpp-svc.debug

strip --strip-unneeded dist/relwithdebinfo/bin/lab-cpp-svc
objcopy --add-gnu-debuglink=dist/debug/lab-cpp-svc.debug \
  dist/relwithdebinfo/bin/lab-cpp-svc

sha256sum \
  dist/relwithdebinfo/bin/lab-cpp-svc \
  dist/debug/lab-cpp-svc.debug \
  > dist/SHA256SUMS

readelf -n dist/relwithdebinfo/bin/lab-cpp-svc | grep "Build ID"

A CPack DEB csomaghoz a CMakeLists a következőket tartalmazza:

install(TARGETS lab-cpp-svc RUNTIME DESTINATION bin)
set(CPACK_GENERATOR "DEB")
set(CPACK_PACKAGE_VERSION "0.1.0")
set(CPACK_PACKAGE_CONTACT "lab@example.invalid")
set(CPACK_DEBIAN_PACKAGE_MAINTAINER "lab@example.invalid")
include(CPack)

A csomag létrehozása:

cmake --build build --target package
dpkg-deb --info build/lab-cpp-svc-0.1.0-Linux.deb

Az SBOM minimális, de a labban ellenőrzött adattal bővítendő. Az alábbi JSON csak a formátumot mutatja, a hash placeholder:

{
  "format": "CycloneDX",
  "specVersion": "1.5",
  "components": [
    {
      "type": "application",
      "name": "lab-cpp-svc",
      "version": "0.1.0",
      "hashes": [
        {"alg": "SHA-256", "content": "replace-with-real-sha256"}
      ]
    }
  ]
}

Várt kimenet:

Build ID: a1b2c3d4e5f6...
100% tests passed, 0 tests failed out of 12
SHA256SUMS contains two entries
DEB package contains /opt/lab-cpp-svc/bin/lab-cpp-svc

Ellenőrzési feltétel: a dist/relwithdebinfo/bin/lab-cpp-svc fájl readelf -n kimenetében szerepel ugyanaz a build-id, mint a dist/debug/lab-cpp-svc.debug fájlban; a DEB csomagban lévő bináris hash megegyezik a dist/SHA256SUMS első sorával.

48.3.7 Tipikus hibák és ellenpróbák

Az első tipikus hiba, hogy a fejlesztő a lokális gépen ASan alatt futtatja a tesztet, de a CI-ben a release artifact egy másik toolchainnel készül. Ilyenkor a tünet lehet, hogy a felhasználó gépen GLIBCXX_3.4.XX not found hiba jelenik meg. A hipotézis nem az, hogy a kód rossz, hanem az, hogy a runtime ABI nem azonos. Adatgyűjtés: readelf -d, readelf -Ws és a target csomag symbol version listája. Egy változtatás: a build matrixban a target arch és a runtime image ugyanazt a toolchain verziót használja, majd a verifikáció a tényleges container digest alapján történik.

A második hiba, hogy a debuginfo nem illeszkedik. Ha a binárist a strip után újrafordítják, a build-id megváltozik, de a régi .debug fájl marad a CI artifactban. A tünet az, hogy a debugger rossz függvényhatárokat mutat. Az ellenpróba az, hogy a .debug létrehozása és a bináris stripje ugyanabból a build könyvtárból történik, majd a build-id párosítást a readelf -n parancs mindkét fájlra ellenőrzi.

A harmadik hiba, hogy a TSan és az ASan egy közös buildben fut. A tünet a FATAL: ThreadSanitizer: unexpected memory mapping üzenet. A javítás nem a sanitizer kikapcsolása, hanem a mátrix szétválasztása: az ASan és a TSan külön cellában, külön binárissal.

A negyedik gyakori hiba, hogy a release buildben az assert aktív marad, mert a CMAKE_BUILD_TYPE=Release mellett hiányzik a -DNDEBUG. Ennek tünete, hogy a teljesítménymérés alatt az éles bináris váratlanul lassú. Az ellenőrzés a compile_commands.json és a CMakeCache.txt áttekintése.

48.3.8 Feladatok

48.3.8.1 1. Feladat — Build mátrix tervezése

Adott a lab-cpp-svc alkalmazás egyszerű C++ forráskóddal és CTest unit tesztekkel, valamint egy x86_64 és egy aarch64 lab runner. Tervezd meg a mátrixot a következő dimenziókkal: architektúra, compiler, build mode, sanitizer és test scope. Add meg, melyik cellában indokolt az ASan, az UBSan, a TSan, és melyik cella futtat integrációs tesztet. Ne írj konfigurációt, csak a táblázatot és az indoklást.

48.3.8.2 2. Feladat — Release artifact és debug csomag előállítása

A lab-cpp-svc forrásban hozz létre egy RelWithDebInfo buildet, válaszd le a debug fájlt, majd készíts DEB csomagot. A parancsokat a lab-runner-01 hoston, lab-cicd accounttal, a lab-cpp-svc repository 0a1b2c3d revízióján futtasd. Ellenőrizd, hogy a bináris stripelt-e, a build-id megmaradt-e, a DEB csomag tartalmazza-e a megfelelő binárist, és a dist/SHA256SUMS mindkét artifactot tartalmazza.

48.3.8.3 3. Feladat — ABI mismatch diagnosztikája

A lab-cpp-svc egy aarch64 konténerben a következő hibát adja:

lab-cpp-svc: /lib/aarch64-linux-gnu/libstdc++.so.6: version `GLIBCXX_3.4.32' not found

A CI futtatása sikeres volt x86_64-en. Hipotézist kell alkotnod, adatot gyűjteni, egy változtatást végrehajtani, majd a verifikációt elvégezni. A feladatban a parancsok mellett add meg a postconditiont is.

48.3.9.3 3. Megoldás

A hipotézis: az aarch64 image nem a lab által rögzített libstdc++ verziót használja, vagy a bináris nem a cél architektúrán készült. Adatgyűjtés:

file dist/relwithdebinfo/bin/lab-cpp-svc
readelf -h dist/relwithdebinfo/bin/lab-cpp-svc | grep Machine
readelf -d dist/relwithdebinfo/bin/lab-cpp-svc | grep NEEDED
readelf -Ws dist/relwithdebinfo/bin/lab-cpp-svc | grep GLIBCXX_3.4.32

Ha a gépi kód AArch64, de a futtató konténer libstdc++ verziója alacsonyabb, akkor az image runtime stage-ét kell javítani, például a megfelelő libstdc++6 csomagverzióval. Ha a bináris még x86-64, akkor a CI mátrixban az aarch64 runner nem kapott CMAKE_CXX_COMPILER célarchitektúrájú toolchaint.

Egy változtatás: a runtime image FROM rétege és a build matrix arch mezője egyaránt a lab aarch64 baseline-ját használja, majd a binárist újrafordítjuk.

Verifikáció:

readelf -h dist/aarch64/bin/lab-cpp-svc | grep Machine
docker run --platform linux/arm64 \
  lab-registry.example/lab-cpp-svc:0.1.0 \
  /usr/local/bin/lab-cpp-svc --version

Postcondition: a futtató image és a bináris Machine mezője AArch64, a readelf -d által igényelt GLIBCXX_3.4.32 elérhető a cél image libstdc++ verziójában, és a konténerben a --version sikeresen lefut.

48.3.10 Rövid összefoglaló

A CI-native build mátrix nem a fordítóparancsok gyűjteménye, hanem explicit bemenetek és postconditionök halmaza. A release artifact akkor megbízható, ha a source revision, a toolchain, az architektúra, a build mode és a sanitizer dimenzió egyértelműen származik le, és az eredményhez debug build-id, test report, SBOM és checksum kötődik. A sanitizer cellákat el kell szigetelni; az ASan/TSan kombinálása, a debuginfo mismatch és a rossz runtime libstdc++ ABI gyakori hibaforrás. A javítás mindig a bemeneti cella vagy a runtime image pontosítását jelenti, nem a védelem globális kikapcsolását.

Továbbhasznált definíciók: build matrix — architektúra, compiler, build mode, sanitizer és test scope dimenziók kontrollált kombinációja, amely minden cellához explicit bemenetet és postconditiont rendel; artifact szerződés — a release objektumhoz kötött source revision, build-id, digest, SBOM, test report és retention policy együttese; provenance — az artifactot a forráshoz, a toolchainhez és a buildlépéshez kapcsoló bizonyítéklánc.
