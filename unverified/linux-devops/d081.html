17.1 journald, syslog és naplóút

17.1.1 Motiváció

Egy üzemeltetett Linux hoszton a napló (log) az elsődleges operatív nyom. Ha egy C++ szolgáltatás éjszaka elhasal, a fejlesztő nem szinkron módon debuggolja, hanem a rendszer által rögzített időrendi eseményekből állapítja meg, mi történt. A systemd-journald a legtöbb modern Linux disztribúción – így az Ubuntu Server 24.04 LTS baseline-on is – a naplóút központi eleme. A journald nem egyszerűen egy szövegfájlba ír; strukturált mezőkkel, bootonként indexelt, bináris tárolóval dolgozik. A sysadminnak pontosan kell tudnia, mi kerül a journalba, mi marad volatile (reboot után elvesző) tárolóban, és mi továbbítódik a hagyományos syslog/rsyslog világ felé. Ebben az alfejezetben a logüzenetet a keletkezésétől a helyi tárolásig és továbbításig követjük.

17.1.2 Definíció és működés

A journal a systemd által kezelt, strukturált, bináris naplótároló; rendszerint a systemd-journald.service szolgáltatás tölti meg. A syslog ezzel szemben a klasszikus, szöveges üzenetformátum és protokoll, facility és severity értékekkel. A rsyslog egy moduláris syslog daemon, amely képes a journald-vel együttműködni, és hagyományos /var/log/syslog fájlokat is előállítani.

A journald több forrásból gyűjt:

  1. Kernel: a kernel printk üzenetei a /dev/kmsg eszközön át érkeznek a journald-be.
  2. Syslog API: a folyamatok által meghívott syslog(3) hívás a /dev/log socketre ír. Ubuntu 24.04 LTS baseline-on a /dev/log tipikusan a /run/systemd/journal/dev-log journald socketre mutat, tehát a syslog üzenetek először a journald-be kerülnek.
  3. Service stdout/stderr: ha egy systemd unit StandardOutput=journal és StandardError=journal beállítással fut (ez a modern systemd default), a service manager a folyamat standard kimeneteit és hibakimeneteit egy socketen át közvetlenül a journald-nek küldi. Egy natív C++ szolgáltatás std::cout és std::cerr írása is ezen az úton landol a journalban.
  4. Közvetlen journal API: a folyamat a sd_journal_print(3) vagy hasonló függvénnyel is küldhet bejegyzéseket.

A journal üzenetekhez mezőket rendel. A fontosabb structured journal field-ek:

Mező Jelentés
MESSAGE Az üzenet szövege
PRIORITY Numerikus prioritás 0–7 (emerg..debug)
_SYSTEMD_UNIT A küldő systemd unit neve
_PID A küldő folyamat PID-je
_BOOT_ID A boot session azonosítója (nem a machine-id!)
_UID, _GID A küldő folyamat felhasználói/csoport azonosítója
_COMM, _EXE A folyamat neve és elérési útja
SYSLOG_FACILITY A syslog facility értéke
SYSLOG_IDENTIFIER A syslog azonosító (programnév)

A boot ID (_BOOT_ID) az adott indítási session egyedi azonosítója, amely lehetővé teszi a reboot előtti és utáni üzenetek szétválasztását. A machine-id a hosztspecifikus azonosító, a boot ID bootonként változik. Ez kulcsfontosságú, ha egy szenior fejlesztő egy napos loghalmazban egy több napja indult egyszeri eseményt keres.

A runtime journal a /run/log/journal alatt tárolódik; a /run tipikusan tmpfs, ezért reboot után elveszik. A persistent journal a /var/log/journal alatt tárolódik, így túléli a rebootot. A systemd-journald.conf Storage= beállítása vezérli a viselkedést:

  • volatile: csak /run/log/journal, lemezes tárolás nélkül;
  • persistent: /var/log/journal használata;
  • auto: ha a /var/log/journal könyvtár létezik, persistent, ellenkező esetben volatile.

Az Ubuntu 24.04 LTS baseline-on az auto a gyakori default; a pontos ellenőrzés a labhoston szükséges. A persistent journalhoz a könyvtárat is létre kell hozni, vagy a Storage=persistent beállítással együtt a journald létrehozhatja – ezt a példában ellenőrizzük.

A journald rate limit-et alkalmaz a bejövő üzenetekre. Az alapértelmezett RateLimitIntervalSec=30s és RateLimitBurst=1000 azt jelenti, hogy 30 másodpercen belül 1000-nél több üzenet esetén a többlet eldobásra kerül. Ilyenkor a journalba egy Suppressed ... messages from ... bejegyzés kerül. Kernel üzeneteknél Missed N kernel messages jelenhet meg. Ez az elveszett log, amelyet diagnosztikában figyelembe kell venni.

A journalctl a journalból való lekérdezés alapvető eszköze. Fontos szűrők:

  • -u <unit>: adott systemd unit üzenetei;
  • -_PID=<pid>: adott PID;
  • -b [ID]: aktuális vagy adott boot;
  • -k: csak kernel üzenetek;
  • -p <prio>: prioritásszint (pl. warning, err);
  • --since "..." --until "...": időablak;
  • -o short-precise, -o verbose, -o json: kimeneti formátum.

17.1.3 Kidolgozott példa

Cél: a lab-syslog1 labhoston persistens journalt állítunk be, egy teszt systemd unit kimenetét rögzítjük, és a journald syslog/rsyslog kapcsolatot ellenőrizzük.

Target: lab-syslog1 VM; felhasználó: lab-admin (UID 1000). A módosító parancsokhoz sudo jog szükséges.

Előfeltétel: a d080 laborban használt izolált labhost fut, systemd aktív, a lab-admin user a sudo csoportban van.

1. lépés – persistent journal beállítása

# labhost: lab-syslog1, user: lab-admin (UID 1000)
sudo cp /etc/systemd/journald.conf /etc/systemd/journald.conf.lab-bak
sudo install -d -g systemd-journal -m 2755 /var/log/journal
sudo sed -i 's/^#\?Storage=.*/Storage=persistent/' /etc/systemd/journald.conf
sudo systemctl restart systemd-journald

Várható kimenet: a systemctl restart után nincs hibakimenet.

Ellenőrzés:

# labhost: lab-syslog1
journalctl --disk-usage
journalctl --list-boots | tail -n 3
ls -ld /var/log/journal

Várható: a --disk-usage értéke nagyobb, mint korábban; a --list-boots a jelenlegi bootot mutatja, a /var/log/journal könyvtár létezik. A persistens tároló a reboot után is megtartja az adatokat.

Rollback: sudo cp /etc/systemd/journald.conf.lab-bak /etc/systemd/journald.conf && sudo systemctl restart systemd-journald. A létrehozott /var/log/journal könyvtár törlése nem szükséges, ha a default Storage=auto visszaáll; de ha tiszta vol.

2. lépés – teszt unit stdout/stderr capture

Hozzunk létre egy systemd unitot, amely egy sorozat kimenetet ír:

# /etc/systemd/system/lab-logtest.service
[Unit]
Description=Lab journald stdout/stderr capture test
After=systemd-journald.service

[Service]
Type=oneshot
ExecStart=/bin/sh -c 'echo "lab-logtest info message"; echo "lab-logtest error message" >&2'
StandardOutput=journal
StandardError=journal
SyslogIdentifier=lab-logtest

A unit telepítése és indítása:

# labhost: lab-syslog1, user: lab-admin
sudo tee /etc/systemd/system/lab-logtest.service >/dev/null <<'EOF'
[Unit]
Description=Lab journald stdout/stderr capture test
After=systemd-journald.service

[Service]
Type=oneshot
ExecStart=/bin/sh -c 'echo "lab-logtest info message"; echo "lab-logtest error message" >&2'
StandardOutput=journal
StandardError=journal
SyslogIdentifier=lab-logtest
EOF
sudo systemctl daemon-reload
sudo systemctl start lab-logtest.service

Az üzenetek szűrése:

# labhost: lab-syslog1
journalctl -u lab-logtest.service -b -o short-precise

Várható kimenet (időbélyegek nélkül, illusztratív):

lab-syslog1 lab-logtest[12345]: lab-logtest info message
lab-syslog1 lab-logtest[12345]: lab-logtest error message

A verbose formátum megmutatja a strukturált mezőket:

journalctl -u lab-logtest.service -b -o verbose

Várható:

...
_SYSTEMD_UNIT=lab-logtest.service
_PID=12345
PRIORITY=6
MESSAGE=lab-logtest info message
SYSLOG_IDENTIFIER=lab-logtest
_BOOT_ID=...

3. lépés – syslog/rsyslog kapcsolat ellenőrzése

# labhost: lab-syslog1
systemctl is-active rsyslog.service
ls -l /dev/log
journalctl -u rsyslog.service -b -n 10

Várható: az rsyslog aktív, a /dev/log a /run/systemd/journal/dev-log-ra mutat, és a journald-ben megjelennek a rsyslog saját bejegyzései. A ForwardToSyslog=yes esetén a journald a /run/systemd/journal/syslog socketen továbbítja az üzeneteket a rsyslog felé, amely /var/log/syslog fájlba írja azokat; ezt a tail -n 5 /var/log/syslog parancs mutathatja.

4. lépés – rate limit demonstráció

# labhost: lab-syslog1, user: lab-admin
for i in $(seq 1 2000); do logger -t lab-ratetest "message $i"; done
journalctl -t lab-ratetest -b | tail -n 5

Várható: a lab-ratetest azonosítójú üzenetek nem tartalmazzák mind a 2000 bejegyzést; a végén egy Suppressed ... messages from lab-ratetest sor jelenik meg. Ez mutatja a rate limit működését; a journald az üzenetek egy részét eldobta.

17.1.4 Hibák és ellenpróbák

Tünet: reboot után eltűntek a logok

Hipotézis: a journal csak runtime tárolóban van. Adatgyűjtés: ls -ld /var/log/journal – ha a könyvtár nem létezik, a Storage=auto volatile módot használ. Változtatás: persistent journal beállítása a fenti módon. Verifikáció: journalctl --list-boots a reboot után is mutatja a korábbi bootot.

Tünet: egy alkalmazás több ezer logüzenete közül sok hiányzik

Hipotézis: rate limit. Adatgyűjtés: journalctl -t lab-ratetest -b | grep -c message és journalctl -t lab-ratetest -b | grep Suppressed. Ha a Suppressed sor megjelenik, a limit elnyelte a többletet. Változtatás: RateLimitIntervalSec=0 vagy nagyobb RateLimitBurst a /etc/systemd/journald.conf-ban, majd systemctl restart systemd-journald. Verifikáció: a tesztüzenetek száma megnő, nincs Suppressed.

Tünet: a systemd unit stdout/stderr kimenete nem jelenik meg a journalban

Hipotézis: a unitban StandardOutput=inherit vagy StandardError=inherit van, és a folyamat nem terminálhoz kötött. Adatgyűjtés: systemctl show -p StandardOutput -p StandardError lab-logtest.service. Változtatás: StandardOutput=journal és StandardError=journal beállítása. Verifikáció: journalctl -u lab-logtest.service -b mutatja a kimenetet.

Tünet: a syslog fájl /var/log/syslog nem frissül, pedig a journald kap üzeneteket

Hipotézis: a rsyslog nem fut vagy a ForwardToSyslog ki van kapcsolva. Adatgyűjtés: systemctl is-active rsyslog.service, journalctl -u rsyslog.service, grep ForwardToSyslog /etc/systemd/journald.conf. Változtatás: a rsyslog indítása vagy a ForwardToSyslog=yes beállítása. Verifikáció: tail -f /var/log/syslog közben logger -t lab-syslogtest "hello".

17.1.5 Feladatok

  1. Magyarázó feladat: Rajzolja le szöveges táblázat vagy lépéses adatút formájában a logger -t lab-feladat1 "hello" üzenet útját a syslog API hívástól a journald-ig és a rsyslog /var/log/syslog fájljáig. Nevezze meg a socketeket, a tárolási rétegeket és a továbbítási pontokat.

  2. Adminisztrációs/konfigurációs feladat: Állítsa be a persistens journalt a lab-syslog1 hoston, hozzon létre egy lab-logcapture.service unitot, amely a standard kimenetre és hibakimenetre is ír egy-egy sort, majd a journalctl segítségével igazolja, hogy a két üzenet a journalban van. Dokumentálja a postconditiont.

  3. Diagnosztikai/failure/recovery feladat: A labhoston egy teszt folyamat 2000 azonos SYSLOG_IDENTIFIER-rel rendelkező üzenetet küld, de a journal csak körülbelül 1000-et tartalmaz. Végezze el a diagnózist, állítsa a journald rate limitjét úgy, hogy a teszt forgalom elvesztés nélkül bekerüljön, majd bizonyítsa a javítást. Végül állítsa vissza az eredeti rate limit beállításokat.

17.1.6 Megoldások

1. feladat megoldása

A várható adatút:

  1. A logger folyamat meghívja a syslog(3) függvényt, amely a /dev/log Unix socketre ír.
  2. A /dev/log szimbolikus link a /run/systemd/journal/dev-log socketre mutat, tehát a journald fogadja az üzenetet.
  3. A journald az üzenetet a _PID, _UID, SYSLOG_FACILITY, SYSLOG_IDENTIFIER mezőkkel együtt a journaltárolóba írja (/run/log/journal vagy /var/log/journal).
  4. Ha a ForwardToSyslog=yes beállítás aktív, a journald a /run/systemd/journal/syslog socketen továbbítja az üzenetet.
  5. A rsyslog az imuxsock moduljával olvassa ezt a socketet, majd az /var/log/syslog fájlba írja az üzenetet.

Postcondition: a journalctl -t lab-feladat1 -b és a grep lab-feladat1 /var/log/syslog is mutatja az üzenetet.

2. feladat megoldása

A persistens journal beállítása a kidolgozott példa 1. lépése szerint történik. A unit létrehozása:

# /etc/systemd/system/lab-logcapture.service
[Service]
Type=oneshot
ExecStart=/bin/sh -c 'echo "lab-capture stdout"; echo "lab-capture stderr" >&2'
StandardOutput=journal
StandardError=journal
SyslogIdentifier=lab-logcapture

Telepítés és ellenőrzés:

sudo tee /etc/systemd/system/lab-logcapture.service >/dev/null <<'EOF'
[Service]
Type=oneshot
ExecStart=/bin/sh -c 'echo "lab-capture stdout"; echo "lab-capture stderr" >&2'
StandardOutput=journal
StandardError=journal
SyslogIdentifier=lab-logcapture
EOF
sudo systemctl daemon-reload
sudo systemctl start lab-logcapture.service
journalctl -u lab-logcapture.service -b -o short-precise

Postcondition: a journal kimenetben megjelenik mindkét sor; a systemctl show -p StandardOutput lab-logcapture.service értéke journal.

3. feladat megoldása

Diagnózis:

journalctl -t lab-ratetest -b | grep -c message
journalctl -t lab-ratetest -b | grep Suppressed

Ha a Suppressed sor megjelenik, a journald rate limitje eldobta a többletet. A javítás a /etc/systemd/journald.conf fájlban:

[Journal]
RateLimitIntervalSec=0
RateLimitBurst=0

A 0 érték kikapcsolja a limitet. A módosítás után:

sudo cp /etc/systemd/journald.conf /etc/systemd/journald.conf.lab-ratelimit-bak
sudo sed -i 's/^#\?RateLimitIntervalSec=.*/RateLimitIntervalSec=0/;s/^#\?RateLimitBurst=.*/RateLimitBurst=0/' /etc/systemd/journald.conf
sudo systemctl restart systemd-journald
for i in $(seq 1 2000); do logger -t lab-ratetest2 "message $i"; done
journalctl -t lab-ratetest2 -b | grep -c message
journalctl -t lab-ratetest2 -b | grep Suppressed

Várható: a grep -c message 2000-et mutat, a Suppressed nem jelenik meg.

Rollback: sudo cp /etc/systemd/journald.conf.lab-ratelimit-bak /etc/systemd/journald.conf && sudo systemctl restart systemd-journald.

Postcondition: a teszt forgalom elvesztés nélkül bekerül a journalba; az eredeti rate limit konfiguráció visszaáll.

17.1.7 Rövid összefoglaló

A journald a modern Linux naplóút központja: kernel, syslog API és systemd unit stdout/stderr üzeneteket gyűjt strukturált mezőkkel. A journalctl szűrőkkel – -u, -_PID, -b, -p – pontosan kérdezi le a bootonként elkülönített adatokat. A persistent journal (/var/log/journal) reboot után is megőrzi a logokat, míg a runtime journal (/run/log/journal) volatile. A journald rate limitje eldobhatja az üzeneteket, ezt Suppressed bejegyzés jelzi. A syslog/rsyslog kapcsolat a /dev/log és a ForwardToSyslog mechanizmuson át valósul meg. A systemd unitok szabványos StandardOutput=journal és StandardError=journal beállítással rögzítik a C++ szolgáltatások kimenetét.

Legfontosabb, továbbhasznált definíciók: journal – structured, bináris naplótároló, mezőkkel; persistent journal – /var/log/journal alatt tárolt, rebootot túlélő napló; rate limit – a journald által alkalmazott bejövő üzenetkorlát, amely elnyelt üzeneteket Suppressed bejegyzéssel jelez.
