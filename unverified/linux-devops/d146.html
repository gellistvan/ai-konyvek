30.1 iproute2, rtnetlink és runtime config

30.1.1 Miért objektumokat vizsgálunk, nem „a hálózatot”?

Egy szolgáltatás nem éri el a szomszédos gépet. Az interfész látszólag aktív, a konfigurációs fájlban szerepel az IP-cím, mégsem működik a kapcsolat. Üzemeltetési szempontból ezek külön állítások: a konfiguráció szándékot ír le, az interfész állapota pedig még nem bizonyít megfelelő címzést, útvonalválasztást vagy szomszédfelderítést.

A futásidejű hálózati állapot (runtime network state) a kernelben jelenleg létező hálózati objektumok és beállítások együttese. Az iproute2 eszközkészletből elsősorban az ip és a bridge segítségével kérdezzük le és módosítjuk. A korábban tanult visszaútvonal-vizsgálatot és L2 diagnosztikát most egységes objektummodellbe rendezzük.

Objektum Mit ír le? Alaplekérdezés Mit nem bizonyít?
link Interfész, típus, MTU, kapcsolatok, állapot ip link show IP-elérhetőséget
address / addr Interfészhez rendelt cím, prefix, élettartam ip address show Megfelelő visszautat
route Célprefixhez tartozó továbbítási vagy eldobási döntés ip route show table all Hogy ezt a táblát választják
rule Az útvonaltábla-választás szabályai ip rule show A következő ugrás elérhetőségét
neigh IPv4 ARP-, illetve IPv6 ND-szomszédállapot ip neigh show Alkalmazásszintű működést

Az objektumok hálózati névtérhez (network namespace) tartoznak. A névtér itt izolációs eszköz: saját interfészeket, útvonaltáblákat és szomszédállapotot biztosít. Részletes felépítését a Network namespace, veth, bridge és tap tárgyalja.

30.1.2 Rtnetlink, részletes nézet és gépi feldolgozás

Az rtnetlink a kernel hálózati alrendszerének Netlink-alapú vezérlő- és értesítési felülete; az ip számos művelete a NETLINK_ROUTE interfészen keresztül működik. Ez helyi kernel–userspace kommunikáció, nem IP-hálózaton küldött adminisztrációs protokoll.

A működés három formája:

  1. Lekérdezés: objektumok és attribútumaik kiolvasása.
  2. Módosítás: például cím vagy útvonal létrehozása.
  3. Értesítés: a kernel jelzi bizonyos objektumok változását.

A módosítás sikeres visszaigazolása azt bizonyítja, hogy a kernel elfogadta a kérést. Nem bizonyítja, hogy a távoli végpont válaszol. A hálózati módosításokhoz jellemzően az érintett névtérben érvényes CAP_NET_ADMIN jogosultság kell; a labor névtér-létrehozását rootként végezzük.

Fontos kapcsolók:

  • -d: részletes, például interfésztípus-specifikus attribútumok;
  • -s: támogatott objektumoknál statisztikák, például interfészszámlálók;
  • -j: strukturált JSON-kimenet;
  • -4, -6: címcsalád explicit kiválasztása;
  • -n NÉV: megnevezett hálózati névtér.

Az UP adminisztratív engedélyezést, a LOWER_UP alsó rétegbeli linkjelzést jelent. Egyik sem végponttól végpontig tartó próba. A virtuális interfészek state UNKNOWN állapota sem feltétlenül hiba.

JSON-feldolgozáskor mezőnevekre, ne szövegoszlopokra építs. Kezeld a hiányzó opcionális mezőket és a verziófüggő részleteket. Több egymás utáni JSON-lekérdezés nem atomi pillanatkép: közben más folyamat módosíthatja az állapotot. Az interfészszámlálók különbségét azonos objektumon és ismert mérési időközben értékeld; az újralétrehozás megszakíthatja a számlálók folytonosságát.

30.1.3 Kidolgozott labor: öt nézet ugyanarról az adatútról

Célgép: lab-net01, izolált Ubuntu Server 24.04 LTS amd64 VM. Az adminisztrátor lab, UID 1000; az alábbi parancsok sudo -i után, rootként, UID 0-val értendők. Más gépen ne hajtsd végre őket. Webes ellenőrzés és tényleges laborfuttatás itt nem történt; minden eredmény várt eredmény.

Előfeltételek: elérhető VM-konzol, telepített iproute2, procps és iputils-ping; a két névtér még nem létezik. Nem módosítjuk a host menedzsmentinterfészét, útvonalait vagy tűzfalát.

Elem Érték
Owner A labor adminisztrátora
Élettartam Az aktuális labormenet végéig
Konfiguráció forrása Az alábbi parancslista
Tárolt állapot A két névtér kernelállapota; nincs tartós hálózati konfiguráció
Elvárt állapot Két aktív végpont, működő közvetlen IPv4-kapcsolat
Megfigyelt állapot ip-lekérdezések, események, ping; a tanuló rögzíti

A felhasznált privát tartomány 10.146.0.0/30. Ellenőrizd a helyi labor-inventoryban és a host címei, útvonalai között, hogy nincs már más célra lefoglalva. Az izoláció miatt az átfedés itt nem feltétlenül okozna adatúthibát, de későbbi összekötésnél veszélyessé válhat.

# Target: lab-net01; root, UID=0; csak olvasás.
hostname
id
cat /etc/os-release
uname -r
ip -V
dpkg-query -W iproute2 procps iputils-ping systemd

ip netns list
ip -br address show
ip -4 route show table all

A kernel- és csomagkiadásokat a jegyzőkönyvben rögzítsd; a „24.04” önmagában nem pontos verzióprofil. Névütközés esetén állj meg: meglévő névteret ne használj és ne törölj.

Forrásnévtér Interfész Cím Cél
lab-ip146-a lab-a0 10.146.0.1/30 10.146.0.2, lab-b0
lab-ip146-b lab-b0 10.146.0.2/30 10.146.0.1, lab-a0

A veth virtuális Ethernet-interfészpár: az egyik vég által továbbított keret a másik végre kerül. Nincs bridge, router vagy külső kapcsolat.

# Target: lab-net01; root, UID=0.
# Előfeltétel: mindkét névtérnév szabad.
ip netns add lab-ip146-a
ip netns add lab-ip146-b

ip -n lab-ip146-a link add lab-a0 type veth peer name lab-b0
ip -n lab-ip146-a link set lab-b0 netns lab-ip146-b

ip -n lab-ip146-a link set lo up
ip -n lab-ip146-b link set lo up
ip -n lab-ip146-a link set lab-a0 up
ip -n lab-ip146-b link set lab-b0 up

ip -n lab-ip146-a address add 10.146.0.1/30 dev lab-a0
ip -n lab-ip146-b address add 10.146.0.2/30 dev lab-b0

ip -n lab-ip146-a route add table 146 \
    10.146.0.0/30 dev lab-a0 src 10.146.0.1
ip -n lab-ip146-a rule add priority 10146 \
    from 10.146.0.1/32 table 146

Hiba után ne folytasd vakon a parancslistát: ellenőrizd, mely objektumok jöttek létre. A parancsok sorozata nem tranzakció.

A címazonosítók hozzárendelése normál esetben automatikusan létrehozza a kapcsolódó hálózat útvonalát a main táblában, valamint helyi bejegyzéseket a local táblában. A 146-os tábla és az 10146 prioritású szabály ettől külön, explicit laborállapot. A kisebb szabályprioritás korábbi kiértékelést jelent.

# Target: lab-net01; root, UID=0; vizsgált névtér: lab-ip146-a.
ip -n lab-ip146-a -d -s link show dev lab-a0
ip -n lab-ip146-a -4 address show
ip -n lab-ip146-a -4 route show table all
ip -n lab-ip146-a -4 rule show
ip -n lab-ip146-a -4 neigh show

ip -n lab-ip146-a -4 route get 10.146.0.2 from 10.146.0.1
ip netns exec lab-ip146-a ping -n -I 10.146.0.1 -c 3 -W 1 10.146.0.2
ip -n lab-ip146-a -4 neigh show dev lab-a0

# Ugyanezek strukturált formában:
ip -n lab-ip146-a -j -d -s link show
ip -n lab-ip146-a -j -4 address show
ip -n lab-ip146-a -j -4 route show table all
ip -n lab-ip146-a -j -4 rule show
ip -n lab-ip146-a -j -4 neigh show

Várt ellenőrzési feltételek:

  • a címek a megfelelő interfészeken szerepelnek;
  • a forráscímmel végzett útvonallekérdezés a 146-os táblát és a lab-a0 interfészt választja;
  • mindhárom ICMP-kérésre válasz érkezik;
  • a próba után megjelenik a 10.146.0.2 szomszéd bejegyzése.

Az induláskor üres szomszédtábla normális. A STALE állapot használható, de régebben megerősített szomszédinformációt jelent, nem bizonyított hibát. A FAILED viszont sikertelen felderítésre utal; ilyenkor az L2-utat és a másik végpontot kell vizsgálni.

30.1.4 Események: mi változott a két lekérdezés között?

Második konzolon, szintén a lab-net01 VM-en rootként indítsd:

# Target: lab-net01; root, UID=0; csak megfigyelés.
ip -n lab-ip146-a -ts monitor link address route rule neigh

Ezután az első konzolon:

# Target: lab-net01; root, UID=0; kizárólag saját labinterfész.
ip -n lab-ip146-a link set dev lab-a0 mtu 1400
ip -n lab-ip146-a link show dev lab-a0

# Rollback az itt létrehozott veth kezdeti, 1500 B-os MTU-jára:
ip -n lab-ip146-a link set dev lab-a0 mtu 1500
ip -n lab-ip146-a link show dev lab-a0

Várható a két linkváltozás értesítése. Az események pontos formátuma verziófüggő.

Az ip monitor nem csomagrögzítő és nem teljes auditnapló: nem mutat minden továbbított csomagot, nem azonosítja megbízhatóan a változtatás kezdeményezőjét, és túlterhelésnél értesítések veszhetnek el. A -ts időbélyeg falióra-domainhez tartozik, nem monoton időmérési garancia.

Vizsgálatkor indíts megfigyelőt, gyűjts kezdeti állapotot, végezz egy változtatást, majd kérdezd le újra az érintett objektumokat. Szigorúan konzisztens állapotfelvételhez a változtatókat is kontrollálni kell; az eseményfigyelés önmagában nem teszi atomivá a lekérdezéseket.

30.1.5 Bridge, VLAN és bond: a linknézet további rétegei

A host alapértelmezett hálózati névterében az alábbiak kizárólag olvasnak:

# Target: lab-net01; root, UID=0; alapértelmezett hálózati névtér.
ip -d -s link show type bridge
ip -d -s link show type vlan
ip -d -s link show type bond

bridge -j -d link show
bridge -j vlan show
bridge -j fdb show

if test -r /proc/net/bonding/lab-bond0; then
    cat /proc/net/bonding/lab-bond0
fi

Ebben a minimális laborban az üres eredmény helyes: ilyen objektumokat nem hoztunk létre.

Meglévő, dedikált L2-laborban:

  • Bridge: az interfész–master kapcsolat, a portállapot, a VLAN-tagság és az FDB külön nézet. A bridge puszta létezése nem bizonyít továbbítást.
  • VLAN-interfész: a -d mutatja többek között a VLAN-azonosítót és a kapcsolódó alsó interfészt. Ez nem azonos a bridge-port engedélyezett VLAN-listájával.
  • Bond: a mód, az aktív tag és a taginterfészek állapota együtt értelmezendő. Az aggregált számláló elrejtheti egyetlen tag hibáját.

Üres eredménynél először a névteret ellenőrizd, ne rögtön az eszköz hiányát állapítsd meg.

30.1.6 Forwarding és RPF: melyik beállítás hol hat?

A sysctl kernelparamétereket kezel; a hálózati paraméterek jelentős része névtérhez kötött. Ezért a lekérdezést is a megfelelő névtérben kell végezni.

# Target: lab-net01; root, UID=0; csak lab-ip146-a paramétereinek olvasása.
ip netns exec lab-ip146-a sysctl \
    net.ipv4.ip_forward \
    net.ipv4.conf.all.rp_filter \
    net.ipv4.conf.default.rp_filter \
    net.ipv4.conf.lab-a0.rp_filter \
    net.ipv6.conf.all.forwarding \
    net.ipv6.conf.lab-a0.forwarding \
    net.ipv6.conf.lab-a0.accept_ra

A labor közvetlen szomszédai között nincs IP-továbbítás: a helyben keletkező és helyben végződő forgalomhoz nem kell forwarding. Az IPv4 ip_forward a névtér routerként történő működését szabályozza; módosítása más IPv4-paramétereket is alapértékekre állíthat, ezért nem mellékhatásmentes kapcsoló.

A visszaútvonal-alapú forrásellenőrzés (reverse path filtering, RPF) IPv4-beállítása:

  • 0: nincs ilyen ellenőrzés;
  • 1: szigorú mód, a forráshoz vezető legjobb visszaút a bejövő interfészt használja;
  • 2: laza mód, a forrásnak valamely interfészen elérhetőnek kell lennie.

Az effektív rp_filter az all és az adott interfész értékének maximumából adódik. Az all=1, interfészérték 0 tehát nem jelent kikapcsolt ellenőrzést. A default az új interfészek kezdeti értékéhez szolgál mintaként; nem azonos az all jelentésével.

IPv6-nál nincs ugyanilyen rp_filter. A forwarding és a routerhirdetések elfogadása összefügg: az accept_ra=1 routerüzemben nem jelent feltétlen RA-elfogadást. Aszimmetrikus adatútnál először a forráscímet, szabályokat és visszautat bizonyítsd; ne globális védelemkikapcsolással próbálj javítani.

30.1.7 Runtime változtatás és konfigurációgazda

A konfigurációgazda (configuration owner) az adott interfész kívánt állapotát érvényesítő komponens.

Réteg Példa Jelentés
Kívánt állapot Jóváhagyott címzési terv Ennek kell teljesülnie
Konfigurációforrás /etc/netplan/*.yaml Tartós adminisztrációs bemenet
Gazda systemd-networkd vagy NetworkManager Érvényesíti, frissíti a konfigurációt
Megfigyelt állapot ip address, ip route Ami most a kernelben van
Egyéb tárolt állapot DHCP-lease, generált futásidejű fájl Nem feltétlenül elsődleges konfigurációforrás

A Netplan konfigurációt generáló réteg, nem az ip által módosított kernelobjektumok tartós tárolója. Egy ip address add nem írja át a Netplan YAML-t. A manager későbbi újrakonfigurálása, lease-változás vagy újraindítás eltüntetheti, illetve felülírhatja az ideiglenes állapotot.

A laborban a gazda a saját parancslistánk; újraindítás után a névterek sem maradnak meg. Normál hostinterfésznél egyértelmű gazdát kell választani. Ennek felépítését a Netplan, networkd és NetworkManager folytatja.

30.1.8 Feladatok

  1. Magyarázat: miért nem bizonyít elérhetőséget az UP, a helyes main tábla és egy STALE szomszéd együtt sem?
  2. Adminisztráció: adj a lab-a0 interfészhez ideiglenesen 192.0.2.10/32 címet. Ellenőrizd a címet és a helyi útvonalat, majd távolítsd el. Mi marad meg reboot után?
  3. Diagnosztika és recovery: a 146-os táblába vegyél fel blackhole útvonalat kizárólag 10.146.0.2/32 célra. Bizonyítsd, hogy a main tábla változatlansága ellenére megszakad a próba, majd célzottan állítsd helyre.

30.1.9 Megoldások

1. Az UP adminisztratív állapot. A szabályok más táblát választhatnak, mint a main; a STALE pedig nem friss elérhetőségi bizonyíték. Következő ellenpróba a forráscímmel végzett route get, majd azonos forrású adatútteszt.

Postcondition: külön tudod megnevezni a linkállapot, a kiválasztott útvonal és a tényleges válasz bizonyítékát.

2. A dokumentációs cím itt kizárólag az izolált névtér helyi címe:

# Target: lab-net01; root, UID=0; saját lab-ip146-a névtér.
ip -n lab-ip146-a address add 192.0.2.10/32 dev lab-a0
ip -n lab-ip146-a -4 address show dev lab-a0
ip -n lab-ip146-a -4 route show table local

# Rollback:
ip -n lab-ip146-a address del 192.0.2.10/32 dev lab-a0
ip -n lab-ip146-a -4 address show dev lab-a0
ip -n lab-ip146-a -4 route show table local

A hozzáadás helyi útvonalat is létrehoz; a törlés eltávolítja a címhez kapcsolódó állapotot. Tartós konfiguráció nem keletkezik.

Postcondition: a dokumentációs cím és helyi útvonala hiányzik; az eredeti cím megmarad.

3. A konkrétabb /32 útvonal nyer a 146-os tábla /30 útvonala ellen:

# Target: lab-net01; root, UID=0; célzott hibainjektálás.
ip -n lab-ip146-a route add blackhole 10.146.0.2/32 table 146

ip -n lab-ip146-a -4 rule show
ip -n lab-ip146-a -4 route show table main
ip -n lab-ip146-a -4 route show table 146
ip -n lab-ip146-a -4 route get 10.146.0.2 from 10.146.0.1
ip netns exec lab-ip146-a ping -n -I 10.146.0.1 -c 3 -W 1 10.146.0.2

# Recovery: kizárólag az injektált útvonal törlése.
ip -n lab-ip146-a route del blackhole 10.146.0.2/32 table 146
ip -n lab-ip146-a -4 route get 10.146.0.2 from 10.146.0.1
ip netns exec lab-ip146-a ping -n -I 10.146.0.1 -c 3 -W 1 10.146.0.2

A hibás állapotban a lekérdezés és a ping hibát jelezhet; a pontos hibaüzenet implementációfüggő. A szomszédbejegyzés ettől még megmaradhat.

Postcondition: a blackhole bejegyzés hiányzik, az útvonalkiválasztás ismét megfelelő, három válasz érkezik.

A labor végén állítsd le a monitort Ctrl-C-vel, majd:

# Target: lab-net01; root, UID=0.
# Csak az ebben a menetben létrehozott névterek törölhetők.
ip netns pids lab-ip146-a
ip netns pids lab-ip146-b

# Ha nincs bennük megmaradt laborfolyamat:
ip netns del lab-ip146-a
ip netns del lab-ip146-b
ip netns list

Cleanup-postcondition: egyik labornévtér sem szerepel a listában; a host menedzsmenthálózata változatlan.

30.1.10 Rövid összefoglaló

A hálózati diagnózis egymáshoz kapcsolt kernelobjektumok vizsgálata. A link, cím, útvonal, szabály és szomszéd külön kérdésre válaszol; egyik nézet sem helyettesíti az adatúttesztet. A részletes és JSON-kimenet pontosabb adatgyűjtést ad, de több lekérdezés nem alkot automatikusan konzisztens pillanatképet. Az eseményfigyelés segít rekonstruálni a változást, teljes auditot azonban nem biztosít. Módosítás előtt azonosítsd a névteret és a konfigurációgazdát, utána ellenőrizd a kiválasztott útvonalat és a tényleges kapcsolatot. Az ideiglenes javítást külön kell átvezetni a tartós konfigurációba.

  • Runtime állapot: a kernel jelenlegi hálózati objektumai és beállításai.
  • Rtnetlink: hálózati objektumokat kezelő kernel–userspace interfész.
  • Konfigurációgazda: a kívánt hálózati állapot érvényesítéséért felelős komponens.

30.1.11 Források és ellenőrzési hiányok

Az alábbiak ellenőrzési kiindulópontok, nem ebben a munkamenetben olvasott források:

  • ip(8) — objektumok, kapcsolók, JSON-kimenet.
  • rtnetlink(7) — kernel–userspace hálózati interfész.
  • ip-monitor(8) — hálózati változások megfigyelése.
  • bridge(8) — port-, VLAN- és FDB-nézetek.
  • Linux kernel: IP sysctl — forwarding, RPF és RA-paraméterek.

Ellenőrzési hiányok: a konkrét Ubuntu kernel- és csomagkiadás, a hozzá tartozó helyi kézikönyvek, a JSON-mezők és eseményformátumok, valamint a labor tényleges kimenete futtatással ellenőrizendő. A hivatkozott online dokumentáció nem automatikusan a rögzített Ubuntu-profil dokumentációja.
