48.5 CI pipeline és artifact review labor

48.5.1 Motiváció

Egy szenior C++ fejlesztő lokális buildje gyakran hallgatólagos állapottól függ: telepített toolchain, cache, környezeti változó, sőt a fejlesztő ~/.ssh kulcsa vagy éppen egy régi, nem dokumentált munkakönyvtár. Amikor ezt a buildet éles környezetbe kell juttatni, a kérdés nem az, hogy „nálam lefordul-e”, hanem az, hogy egy tiszta, izolált runneren, a revisionból, a deklarált dependency-fixture-tel, visszakereshető módon ugyanazt az artifactot állítjuk-e elő. A CI pipeline (continuous integration pipeline) ennek a szerződésnek a gépiesítése: minden egyes commit vagy merge request egy rövid életű, auditálható munkafolyamatot indít, amelynek kimenete nem csupán egy bináris, hanem egy bizonyítéklánc.

Ehhez a fejezethez nem szükséges éles cloud account vagy publikus repository. A példa izolált lab-cpp-svc nevű repositoryt feltételez, amelyben egy C++ service fordul. A futtatás nem kötelező, és a tananyag-generátor sem futtat parancsot. A runner, action verzió és image-aláírási eszköz konkrét támogatottságát a labor tulajdonosának a saját környezetében kell ellenőriznie.

48.5.2 Definíció és működés

A CI pipeline artifact contract az a gépi ellenőrzéssel leírható megállapodás, amely rögzíti:

  • Revision: a buildet egyértelműen azonosító commit SHA, nem pedig egy mozgó latest címke.
  • Build environment: a runner és a toolchain deklarált, reprodukálható leírása.
  • Input graph: forrás, dependency-fixture, cache és secret-hivatkozások.
  • Output artifact: digesttel, aláírással és retention szabállyal ellátott termék.
  • Evidence: logok, tesztjelentések, artifact digest és provenance adat.

A pipeline gyakorlatilag egy revision → build → test → artifact irányított gráf. A revisionból a checkout lépés anyagot készít. A build lépés a forrást és a függőségi cache-t fogyasztja, majd object fájlokat és végül egy release artifactot állít elő. A test lépés a build kimenetét futtatja izolált fixture-tel. Az artifact publish lépés a tesztelt terméket digesttel és opcionálisan aláírással letétbe helyezi. A gráf élei explicit függőségek; ha egy cache miss miatt a cache réteg üres, a build lépés akkor is lefut, csak lassabban.

A cached dependency fixture olyan előre elkészített, verziózott bemenet, amelyet a teszt nem a hálózatról tölt le futás közben, hanem a pipeline cache-ből vagy egy deklarált artifactból nyer. Ez csökkenti a külső függőséget és a flaky hálózati hibát.

A secret-free log azt jelenti, hogy a pipeline logjaiból nem nyerhető ki érdemi titok: token, jelszó, private key, cookie vagy belső endpoint hitelesítő adat. A GitHub Actions és GitLab CI egyaránt kínál maskingot, de a legerősebb védelem az, ha a secret eleve nem kerül parancssori argumentumba vagy környezeti változó logolt részébe.

A workload identity OIDC (OpenID Connect) alapon lehetővé teszi, hogy a pipeline rövid életű, felhasználónév/jelszó vagy hosszú életű token nélkül igazolja magát egy külső rendszer felé. A CI rendszer aláírt OIDC tokent bocsát ki, amelyet a célplatform egy megbízhatósági relációban ellenőriz. Így a secret nem is létezik tartós formában.

48.5.3 Kidolgozott példa: C++ service build és review

A labor egy lab-cpp-svc nevű C++ projektet használ. A repository tartalma:

  • src/ – a service forrása.
  • tests/ – unit és integration tesztek.
  • fixtures/ – dependency-fixture: például egy kisméretű válaszfájl, tesztkonfiguráció.
  • CMakeLists.txt – build definíció.
  • .github/workflows/ci.yml – a pipeline.

A GitHub Actions workflow vázlatosan:

name: lab-cpp-svc-ci
on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read
  # id-token: write csak akkor, ha OIDC-s külső hívás van
  # jelen példában nincs, ezért nem állítjuk be

jobs:
  build-test:
    runs-on: ubuntu-24.04 # ellenőrzendő, hogy a lab runner támogatja-e
    steps:
      - name: Checkout revision
        uses: actions/checkout@v4 # action verzió ellenőrizendő

      - name: Cache build directory
        uses: actions/cache@v4
        with:
          path: |
            build/
            .ccache/
          key: lab-cpp-svc-${{ runner.os }}-${{ hashFiles('CMakeLists.txt', 'src/**', 'tests/**') }}
          restore-keys: |
            lab-cpp-svc-${{ runner.os }}-

      - name: Configure
        run: cmake -S . -B build -DCMAKE_BUILD_TYPE=RelWithDebInfo

      - name: Build
        run: cmake --build build --parallel 2

      - name: Test with fixture
        env:
          # Secret-free: a fixture elérési útja nyílt, nem tartalmaz tokent
          LAB_FIXTURE_DIR: fixtures
        run: ctest --test-dir build --output-on-failure

      - name: Upload artifact
        uses: actions/upload-artifact@v4
        with:
          name: lab-cpp-svc-bin
          path: build/lab-cpp-svc
          retention-days: 7

A példában a cache kulcsot a CMakeLists.txt, a src/** és a tests/** hashéből számoljuk. Ha ezek változnak, a kulcs új lesz, tehát cache miss következik be. A restore-keys lehetővé teszi egy régebbi cache visszaállítását, ami gyorsabb részleges újjáépítést adhat, de nem garantálja a pontos egyezést. A teszt a fixtures könyvtárból olvas, nem a hálózatról, így a dependency-fixture lokálisan elérhető.

A várt kimenet egy sikeres pipeline run: a checkout rögzíti a commit SHA-t, a build előállítja a lab-cpp-svc binárist, a teszt 100% tests passed üzenetet ad, az artifact feltöltése pedig egy SHA-256 digestet rögzít a logban.

Ellenőrzési feltétel:

  • A pipeline run oldalán a revision megegyezik a commit SHA-val.
  • A build lépés nem mutat error: kimenetet.
  • A teszt lépés ctest return code-ja 0.
  • Az artifact letölthető, és a lokális sha256sum megegyezik a pipeline által jelentett digesttel.
  • A logban nem szerepel ghp_, glpat-, id_rsa, BEGIN PRIVATE KEY vagy hasonló secret minta.

48.5.4 Review, retention és cleanup evidence

Az artifact akkor válik release candidate-té, ha egy humán vagy automatizált review elvégzi a következő ellenőrzéseket:

  1. Revision match: a pipeline a várt branchen futott, a checkout nem egy ref találgatás volt.
  2. Test evidence: a tesztjelentést és a flaky ismétlést rögzítették.
  3. Artifact identity: a digestet egy független helyről is ellenőrizték, nem csak a pipeline logjából.
  4. Provenance (származási adat): a buildhez használt toolchain, dependency és input hash rögzítve van.
  5. Secret audit: a logban nem található secret, a secret a CI titoktárolójában maradt, és csak környezeti változóként, szűken scope-olt lépésben volt jelen.

A retention-days: 7 azt jelenti, hogy a feltöltött artifact hét nap után automatikusan törlődik a CI tárhelyéről. Ez egy retention policy része. A cleanup evidence azt dokumentálja, hogy a régi artifactok és cache-ek ténylegesen törlődtek, és a jelenlegi tárolóban csak az engedélyezett, még szükséges elemek vannak.

A példában nincs image build, de ha a következő lépés egy OCI image, akkor a kimenetet digesttel kell publikálni. Például egy hipotetikus cosign jellegű aláírás:

# Hipotetikus, nem futtatott parancs
cosign sign --yes lab-registry.invalid/lab-cpp-svc@sha256:$(cat image-digest.txt)

Ez a parancs egy belső lab-registry.invalid nevet használ, amely a laborban semmilyen külső DNS-t nem igényel; a név az RFC 6761 szerinti invalid TLD-t használja. Az image-digest.txt a build lépés által számított digestet tartalmazza. Az aláírás után a kimenet egy signature objektum, amelyet a review során ellenőrizni kell.

48.5.5 Tipikus hibák és ellenpróbák

48.5.5.1 1. Cache miss miatt „failing test” a friss függőség miatt

Tünet: a pipeline egy korábbi futásnál sikeres volt, majd cache miss után a teszt hibázik, mert a dependency-fixture hiányzik vagy elavult.

Hipotézis: a cache restore-keys egy olyan régi állapotot hozott vissza, amelyben a fixtures/ tartalma nem egyezik a revisionhöz.

Adatgyűjtés: a pipeline logjában a cache lépés Cache restored from key helyett Cache not found vagy restored from eltérő kulcsot mutat. A tesztlog hiányzó fájlra utal.

Egy változtatás: a dependency-fixture-t a repositoryba kell bevonni hash-kulcsként, és a cache kulcsot úgy képezni, hogy a fixtures/** is szerepeljen a hashFiles listában. Emellett a cache-ből való visszaállítást nem szabad kizárólagos forrásként kezelni: ha a fixture hiányzik, a pipeline explicite hibázzon, ne csendben használjon régi adatot.

Verification: tiszta munkakönyvtárból indított futtatásnál a cache miss nem okoz hiányzó fixture hibát, mert a repository tartalmazza azt.

48.5.5.2 2. Secret megjelenik a logban

Tünet: a pipeline logjában egy ghp_ kezdetű sor vagy egy Authorization: Bearer ... kimenet látható.

Hipotézis: a secret parancssori argumentumba került, például docker login -u token -p ${{ secrets.REGISTRY_TOKEN }} formában, vagy egy hibakereső env kiírás történt.

Adatgyűjtés: a pipeline log visszakeresése a secret mintára. A CI rendszer általában automatikusan maskolja a titkokat, ha a titok értéke a logban szerepel, de ez nem véd minden esetben.

Egy változtatás: a secret átadása környezeti változóval, és az érintett lépésben a log kiírás minimalizálása. A hibakereső parancsokat például set -x módban tilos futtatni, ha az a titkot érintheti. Ha mégis megtörtént, a secret revoke-ot kell kapnia, a logot pedig törölni vagy retencionálisan felülvizsgálni.

Verification: a secret rotáció után a régi érték a logban már nem érvényes.

48.5.5.3 3. Az artifact digest nem ellenőrzött

Tünet: a release során egy nem aláírt, csak latest taggel hivatkozott artifact kerül kiszolgálásra.

Hipotézis: a pipeline ugyan feltöltötte a binárist, de a review csak a fájlnevet nézte, nem a digestet.

Adatgyűjtés: az artifact letöltése után a sha256sum összehasonlítása a pipeline build lépésében rögzített digesttel.

Egy változtatás: a pipeline a build után számítsa a digestet, és azt egy külön artifactként vagy metadata fájlként is publikálja. A review szempontlistája kötelezően tartalmazza a digest ellenőrzést.

Verification: a lokálisan számított digest megegyezik a pipeline által rögzített értékkel, és a review jegyzőkönyvben szerepel az ellenőrzés időpontja.

48.5.6 Feladatok

  1. Magyarázó feladat: Adott a fenti ci.yml. Rajzold fel szövegesen a revision → build → test → artifact gráfot, és nevezd meg, melyik lépés melyik bemenetet fogyasztja, és melyik kimenetet állítja elő. Azonosítsd a cache kulcs számításának összetevőit, és mondd meg, mi történik, ha a tests/ könyvtár megváltozik, de a src/ nem.

  2. Adminisztrációs/konfigurációs feladat: Készíts egy labor pipeline-configot lab-cpp-svc néven, amely:

    • kizárólag a main branch push eseményére fut,
    • buildel és tesztel,
    • a teszt artifactot retention-days: 3 értékkel tölti fel,
    • a cache kulcsban a fixtures/** hash is szerepel. A feladatban ne futtass semmit; csak a YAML és a desired state megadása, valamint a cleanup szabály dokumentálása szükséges. A lab- prefixet tartsd be minden új elnevezésnél.

  3. Diagnosztikai/failure/recovery feladat: Egy pipeline run cache miss után a tesztelés Failed to open fixture: missing lab-cpp-svc/fixtures/input.json hibát ad. A logban nincs secret, de a cache lépés Cache not found üzenetet mutat. Készíts javítási tervet a tünetre, amely tartalmazza: hipotézist, adatgyűjtést, egyetlen változtatást és verification postconditiont. Tételezd fel, hogy a fixtures/input.json ténylegesen szerepel a repositoryban, de a cache visszaállítás nem töltötte be azt.

48.5.7 Megoldások

48.5.7.1 1. feladat megoldása

A gráf:

  • revision (commit SHA) → actions/checkout → munkakönyvtár (working tree)
  • munkakönyvtár + cache → Configure → build/ generált konfiguráció
  • build/ + forrás → Build → lab-cpp-svc bináris
  • lab-cpp-svc + fixtures/ → Test → tesztjelentés
  • lab-cpp-svc → Upload artifact → lab-cpp-svc-bin artifact

A cache kulcs a CMakeLists.txt, src/** és tests/** hashéből képződik. Ha a tests/ változik, de a src/ nem, a hash megváltozik, tehát cache miss következik be. A restore-keys révén azonban egy korábbi, részben egyező cache visszaállhat, ami gyorsíthatja a buildet. A fixture nem szerepel a kulcsban, ezért a fenti hibánál a hiányzó fixture miatt a cache nem segít, mert a fixture a repositoryban van, nem a cache-ben.

Postcondition: a gráf minden éle ismert, és a cache miss ok-okozati kapcsolata a kulcsváltozáshoz világos.

48.5.7.2 2. feladat megoldása

name: lab-cpp-svc-ci
on:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  build-test:
    runs-on: ubuntu-24.04 # ellenőrizendő
    steps:
      - uses: actions/checkout@v4
      - uses: actions/cache@v4
        with:
          path: |
            build/
            .ccache/
          key: lab-cpp-svc-${{ runner.os }}-${{ hashFiles('CMakeLists.txt', 'src/**', 'tests/**', 'fixtures/**') }}
          restore-keys: |
            lab-cpp-svc-${{ runner.os }}-
      - run: cmake -S . -B build -DCMAKE_BUILD_TYPE=RelWithDebInfo
      - run: cmake --build build --parallel 2
      - run: ctest --test-dir build --output-on-failure
      - uses: actions/upload-artifact@v4
        with:
          name: lab-cpp-svc-bin
          path: build/lab-cpp-svc
          retention-days: 3

Desired state: a pipeline csak main push-ra fut; a cache kulcs tartalmazza a fixtures/** hashét; az artifact 3 napig őrződik. Cleanup szabály: a 3 napos retention automatikus, emellett a cache és a régi artifactok manuálisan vagy policy szerint törölhetők a CI felületen a lab-cpp-svc-* azonosítók alapján.

Postcondition: a konfiguráció a labor elvárásait tükrözi, nem tartalmaz secretet, és a lab- prefixet használ.

48.5.7.3 3. feladat megoldása

Hipotézis: a cache miss miatt a pipeline nem töltötte be a fixtures/input.json fájlt, mert az a cache-ből hiányzott, de a teszt lépés kizárólag a cache-ből várta, nem a repository checkoutból.

Adatgyűjtés: a pipeline logban a checkout lépés sikerességét kell ellenőrizni, különösen, hogy a fixtures/input.json szerepel-e a checkoutolt fájlok listájában. Ehhez a checkout után egy ls -l fixtures/input.json futtatás is használható. A hibaüzenet azt mutatja, hogy a teszt nem találta a fájlt.

Egy változtatás: a teszt lépésben ne a cache-re támaszkodjunk a fixture eléréséhez; a fixture mindig a GITHUB_WORKSPACE/fixtures elérési út alatt legyen, és a ctest ezt az abszolút vagy a munkakönyvtárhoz relatív utat használja. A cache kulcsot továbbra is úgy képezzük, hogy a fixtures/** hash szerepeljen, de a fixture jelenlétét a checkout garantálja, nem a cache.

Verification: tiszta cache indítással a checkout után a ls -l fixtures/input.json kimenet -rw-r--r-- sikeresség, a teszt 100% tests passed eredményt ad. A cache hit/miss állapot nem befolyásolja a fixture elérhetőségét.

Postcondition: a teszt minden cache állapotnál a repositoryból nyeri a fixture-t, így a hiba megszűnik, és a log továbbra is secret-free.

48.5.8 Rövid összefoglaló

A CI pipeline contract a revisiontól az artifactig követhető, izolált bizonyítékláncot állít elő. A build, teszt és publish lépések gráfja explicit bemenet-kimenet szerződést ad, a cache pedig csak gyorsító, nem igazságforrás. A dependency-fixture a repository része; cache miss esetén is jelen kell lennie. A secret kezelés a titoktárolóban marad, a log secret-free, a kilépő identitás OIDC-alapú, a kimeneti artifact digesttel és opcionálisan aláírással rendelkezik. A review ellenőrzi a revision egyezést, a teszt evidence-et, a digestet és a retention/cleanup szabályt.

Továbbhasznált definíciók:

  • CI pipeline artifact contract: a pipeline inputjait, lépéseit, kimeneteit és azok mérhető tulajdonságait rögzítő megállapodás.
  • Cached dependency fixture: verziózott, élő hálózati hívást nem igénylő tesztbemenet.
  • Secret-free log: olyan pipeline kimenet, amelyből semmilyen érvényes titok nem nyerhető ki.
