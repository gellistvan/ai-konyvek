44.4 Accountbaseline, audit, költség és cleanup

44.4.1 Motiváció

Egy cloud account akkor is költséget termel, ha a labmérnök éppen nem használja: futó instance, orphan EBS volume, nyitott security group vagy elfelejtett managed service. A Linux hosztoknál a Inventory, source of truth és drift fejezetben tanult desired/observed/drift modell itt is érvényes, de a failure domain most már az account, a régió és a provider API. A d219 célja, hogy a lab accountot erőforrásscope, ownership és visszavonhatóság szerint tudd kezelni: minden erőforrás azonosítható, költsége jelzett, auditja visszakereshető, és a cleanup tervezetten, nem pánikszerűen történik. A C++ build/image artifact szerződéshez hasonlóan itt is a hiányzó owner metadata a leggyakoribb root cause.

44.4.2 Definíció és működés

Account baseline az account kívánt állapota: IAM, hálózati beállítások, audit logok, biztonsági defaultok, költségkeret és cleanup policy. A desired state verziózott repositoryban él (IaC vagy YAML baseline dokumentum), az observed state a provider API-ból kérdezhető le. A kettő különbsége a drift; javítás egy változós, ahogy a d111 is előírja.

A resource ownership a cloud provider tag/label konvenciója. AWS-ben tag, GCP-ben label, Azure-ben tag; ebben a fejezetben AWS referenciát használunk, a GCP/Azure mappinget jelöljük. A minimálisan kötelező kulcsok: Owner, Environment, Expiration, LabId. A tag nem dekoráció, hanem az inventory, a költségfelosztás és a reaper bemenete.

A billing és usage elkülönítése döntő. A usage a valós API-óra, GB-hónap, IOPS, request darabszám, amit a provider mér. A billing pénzügyi elszámolás: számla, adó, kedvezmény, savings plan, committed use discount, elkülönített account vagy szervezeti szintű support. A usage adat gyorsabb és részletesebb, de a számlázott díj csak a számlázási ciklus végén, currency, tax és discount figyelembevételével válik ismertté. Ezért a tananyagban használt árak hipotetikusak, hacsak hivatalos, aktuális pricing oldalról nem ellenőrizték őket.

A budget alert threshold alapú értesítés, például napi vagy havi forecast. Ez nem hard spending cap: a provider nem állítja le a szolgáltatást automatikusan a költségkeret átlépésekor. A leállítás a mi feladatunk, vagy SCP/automation segítségével épül. A téves feltételezés az egyik leggyakoribb cloud hibajelenség.

Az audit log/config history a provider API hívások nyomvonala. AWS CloudTrail, GCP Cloud Audit Logs, Azure Activity Log rögzíti, hogy ki, mikor, milyen API hívást indított. Ehhez jár a konfiguráció history: AWS Config (vagy az IaC Git history) megmutatja a resource konfigurációjának változását. A desired IaC repository Git history-ja a mi own auditunk, a CloudTrail pedig a tényleges API események bizonyítéka.

A security baseline/public exposure azt nézi, hogy az account defaultjai ne engedjenek internetről elérhető adminfelületet. A leggyakoribb hiba a security group 0.0.0.0/0 SSH bejegyzése, a public IP automatikus hozzárendelése, a public S3 bucket vagy a root access key. A javítás itt sem védelemkikapcsolás, hanem minimális jogosultság és explicit allowlist.

Az ephemeral lab/retention azt jelenti, hogy minden erőforrásnak van élettartama. Az Expiration tag vagy lifecycle policy biztosítja, hogy a lab végén a resource törölhető legyen. Orphan resource az, amelynek hiányzik az owner vagy a lab azonosítója, ezért sem inventoryba, sem costback szerepeltetésbe nem köthető. A cleanup manifest lista azokról a saját labresource-okról, amelyekre a törlés kiterjedhet.

A következő táblázat a minimális tag konvenciót foglalja össze:

Kulcs Példa érték Cél
Owner lab-neo felelős, support kapcsolat
Environment sandbox éles és lab elkülönítése
Expiration 2025-12-31T23:59:59Z ephemeral lifecycle, cleanup trigger
LabId d219 inventory és visszakereshetőség

44.4.3 Kidolgozott példa

A példa AWS sandbox accountot használ, dummy account ID 123456789012, CLI profile lab-sandbox, régió eu-west-1. A parancsok nem futtatottak, a kimenetek illusztratívak. A hipotetikus óradíj t3.small estén 0.03 USD; ez a hivatalos pricing oldalon ellenőrizendő.

44.4.3.1 1. Identity és jelenlegi state

# target: account=123456789012, profile=lab-sandbox, region=eu-west-1
# privilege: sts:GetCallerIdentity (read-only)
aws sts get-caller-identity --profile lab-sandbox

Várt kimenet:

{
  "UserId": "AIDASAMPLE",
  "Account": "123456789012",
  "Arn": "arn:aws:iam::123456789012:user/lab-admin"
}

Ezután lekérjük az összes tag-gel ellátott erőforrást:

aws resourcegroupstaggingapi get-resources \
  --profile lab-sandbox --region eu-west-1 \
  --query 'ResourceTagMappingList[].{Resource:ResourceARN,Tags:Tags}' \
  --output json

Várt kimenet:

[
  {
    "Resource": "arn:aws:ec2:eu-west-1:123456789012:instance/i-0d219sample",
    "Tags": [
      {"Key": "Name", "Value": "d219-lab-vm"},
      {"Key": "Environment", "Value": "sandbox"}
    ]
  }
]

Itt már látható a hiány: az instance-nek nincs Owner, Expiration és LabId tagje, tehát orphan inventory szempontból.

44.4.3.2 2. Tag hozzáadása

# target: i-0d219sample, account/profile/region mint fent
# privilege: ec2:CreateTags
# előfeltétel: az instance létezik, a profile írni képes
# rollback: régi tagkészlet visszaállítása vagy delete-tags
aws ec2 create-tags \
  --profile lab-sandbox --region eu-west-1 \
  --resources i-0d219sample \
  --tags \
    Key=Owner,Value=lab-neo \
    Key=Environment,Value=sandbox \
    Key=Expiration,Value=2025-12-31T23:59:59Z \
    Key=LabId,Value=d219

Ellenőrzés:

aws ec2 describe-tags \
  --profile lab-sandbox --region eu-west-1 \
  --filters Name=resource-id,Values=i-0d219sample \
  --query 'Tags[].{Key:Key,Value:Value}' --output json

Várt kimenet:

[
  {"Key": "Owner", "Value": "lab-neo"},
  {"Key": "Environment", "Value": "sandbox"},
  {"Key": "Expiration", "Value": "2025-12-31T23:59:59Z"},
  {"Key": "LabId", "Value": "d219"}
]

44.4.3.3 3. Budget alert

AWS Budgets globális service, ezért a CLI régiója us-east-1 a példában, de a desired state a fő régiótól független. A desired baseline:

# account-baseline.yaml kivonat (desired state)
account_id: "123456789012"
audit:
  cloudtrail_enabled: true
  config_enabled: true
budget:
  monthly_limit_usd: 10.00       # hipotetikus, nem hivatalos díj
  alert_threshold_percent: 80
security:
  public_ssh_allow_any: false
  s3_public_block: true
tags:
  required: ["Owner", "Environment", "Expiration", "LabId"]

A budget ellenőrzése:

aws budgets describe-budgets \
  --profile lab-sandbox --account-id 123456789012 --region us-east-1 \
  --query 'Budgets[].{Name:BudgetName,Limit:BudgetLimit.Unit,Amount:BudgetLimit.Amount}' \
  --output json

Várt kimenet (illusztratív):

[
  {
    "Name": "d219-monthly-lab",
    "Limit": "USD",
    "Amount": "10.0"
  }
]

A burn rate számítása:

burn rate=current month costmonthly budget \text{burn rate} = \frac{\text{current month cost}}{\text{monthly budget}}

Ha a havi költség 8.5 USD, a burn rate 0.85; a budget alert 0.8 felett értesít, de nem állít le semmit.

44.4.3.4 4. Cleanup manifest

A cleanup manifest a saját labresource-ok listája, amelyekre a törlés kiterjedhet:

# cleanup-d219.yaml (lab specifikus, nem provider globális)
account_id: "123456789012"
region: "eu-west-1"
resources:
  - id: i-0d219sample
    type: ec2-instance
    owner: lab-neo
    expiration: "2025-12-31T23:59:59Z"
    action: terminate
  - id: vol-0d219vol
    type: ebs-volume
    owner: lab-neo
    expiration: "2025-12-31T23:59:59Z"
    action: delete

A törlés csak a felsorolt azonosítókkal hajtható végre, név/serial/ARN alapján, nem wildcarddal.

44.4.4 Tipikus hibák és ellenpróbák

Hard cap feltételezése. A labfelhasználó azt hiszi, hogy a budget alert leállítja a szolgáltatást; valójában csak SNS értesítés érkezik. Tünet: a költségkeret átlépése után a futó instance továbbra is fut. Ellenőrzés: aws budgets describe-budgets mutatja az alertet, de a aws ec2 describe-instances mutatja a running állapotot. Hipotézis: nincs automatizált leállítás. Egy változtatás: SCP vagy EventBridge szabály, amely a budget alertre leállítja a lab instance-eket. Verifikáció: újabb alert szimulációval ellenőrizzük.

Hiányzó Expiration tag. A cleanup reaper nem találja a resource-t, ezért az orphan marad. Tünet: a havi költség folyamatos, de az inventory nem rendel hozzá lab ID-t. Ellenőrzés: describe-tags üres vagy hiányos. Javítás: tag hozzáadása, majd a reaper dry-run ellenőrzése, amely a manifestből törli a jelölt resource-t.

Public exposure. A security group 0.0.0.0/0 SSH-t enged; a tünet a vulnerability scan alert vagy a hirtelen bejövő brute force. Ellenőrzés: aws ec2 describe-security-groups --query 'SecurityGroups[?IpPermissions[?IpRanges[?CidrIp==0.0.0.0/0]]].GroupId'. Javítás: a revoke-security-group-ingress a 0.0.0.0/0 SSH szabályra, majd explicit allowlist a lab VPN IP-jére. Nem vesszük ki a security groupot, nem kapcsoljuk ki a firewallt.

Audit log hiánya. A CloudTrail nincs bekapcsolva, ezért a költségkiugrás idején nincs API log. Tünet: a cost explorer mutatja a növekedést, de a CloudTrail híváslista üres. Ellenőrzés: aws cloudtrail describe-trails. Javítás: trail létrehozása, S3 bucket delivery, majd a következő eseményre log.

Hypotetikus ár kontra számla. A tananyagban használt 0.03 USD/t3.small óra csak illusztráció; a tényleges számla régiótól, egress díjtól, savings plan-tól és adótól függ. Tünet: a becsült havi költség 9 USD, a számla 14.20 USD. Ellenőrzés: a billing console Cost and Usage Report-ja, nem a pricing oldal példaértéke. Javítás: a budgetet a tényleges havi átlaghoz igazítjuk, a hipotetikus óradíjat pedig hivatalos pricing oldallal helyettesítjük.

44.4.5.2 2. Adminisztrációs/konfigurációs feladat

A sandbox account 123456789012, profile lab-sandbox régió eu-west-1. Az instance i-0d219sample fut, de nincs kötelező tagje. Hozd létre a Owner=lab-neo, Environment=sandbox, Expiration=2025-12-31T23:59:59Z, LabId=d219 tageket, és ellenőrizd a describe-tags kimenettel. 44.4.5.3 3. Diagnosztikai/failure/recovery feladat

Egy nap alatt a sandbox account költsége háromszorosára nőtt. A describe-instances azt mutatja, hogy i-0d219sample fut, és hozzárendelt public IP van. A CloudTrail logban RunInstances és AuthorizeSecurityGroupIngress hívás látszik. A security group sg-0d219sg 0.0.0.0/0-ről engedi a 22-es portot. Hipotéziseidet tárgasd, és válassz egy root cause javítást, amely nem globális védelemkikapcsolás. Módosíts egy változót, és ellenőrizd.

44.4.6 Megoldások

44.4.6.1 1. Magyarázó feladat megoldása

Az i-0lab1 orphan, mert nincs Owner és Expiration; az inventory nem tudja felelőshöz és időhöz kötni. Az i-0lab2-ből hiányzik a LabId, tehát a lab specifikus cleanup nem tudja hozzárendelni a megfelelő manifesthez. Az S3 bucket LabId-je megvan, de nincs Owner; ha a bucket publikus, a felelős ismeretlen. A cleanup során az i-0lab1 és az S3 bucket kimaradhat, mert a reaper csak azokat törli, amelyek LabId és Expiration taggel egyaránt rendelkeznek. Postcontition: az inventory minden erőforrása rendelkezik a három kötelező tagből álló minimális készlettel.

44.4.6.2 2. Adminisztrációs feladat megoldása

# tag hozzáadása
aws ec2 create-tags \
  --profile lab-sandbox --region eu-west-1 \
  --resources i-0d219sample \
  --tags Owner=lab-neo Environment=sandbox \
          Expiration=2025-12-31T23:59:59Z LabId=d219

# ellenőrzés
aws ec2 describe-tags \
  --profile lab-sandbox --region eu-west-1 \
  --filters Name=resource-id,Values=i-0d219sample \
  --query 'Tags[].{Key:Key,Value:Value}' --output json

Cleanup manifest cleanup-d219.yaml:

account_id: "123456789012"
region: "eu-west-1"
resources:
  - id: i-0d219sample
    type: ec2-instance
    owner: lab-neo
    expiration: "2025-12-31T23:59:59Z"
    action: terminate

Dry-run ellenőrzés:

# csak a manifestben lévő ID keresése; nem törlés
aws ec2 describe-instances \
  --profile lab-sandbox --region eu-west-1 \
  --instance-ids i-0d219sample \
  --query 'Reservations[].Instances[].InstanceId' --output text
# várt kimenet: i-0d219sample

Postcondition: az i-0d219sample rendelkezik mind a négy kötelező taggel, és a cleanup manifest pontosan ezt az instance-t tartalmazza terminate actionnel. A dry-run nem hajt végre destroy műveletet.

44.4.6.3 3. Diagnosztikai feladat megoldása

A költségnövekedés oka a running instance és a public SSH bejegyzés; a CloudTrail AuthorizeSecurityGroupIngress mutatja, hogy a 0.0.0.0/0 szabályt explicit módon létrehozták. A root cause nem az instance létezése, hanem a nyitott admin surface, amely kihasználható, és a lab policy tiltja. Egy változós javítás:

# a public SSH allow törlése
aws ec2 revoke-security-group-ingress \
  --profile lab-sandbox --region eu-west-1 \
  --group-id sg-0d219sg \
  --protocol tcp --port 22 --cidr 0.0.0.0/0

# explicit allowlist a lab VPN IP-re (dummy példa)
aws ec2 authorize-security-group-ingress \
  --profile lab-sandbox --region eu-west-1 \
  --group-id sg-0d219sg \
  --protocol tcp --port 22 --cidr 192.0.2.10/32

Ellenőrzés:

aws ec2 describe-security-groups \
  --profile lab-sandbox --region eu-west-1 \
  --group-ids sg-0d219sg \
  --query 'SecurityGroups[].IpPermissions[?FromPort==`22`].IpRanges[].CidrIp' --output json
# várt kimenet: ["192.0.2.10/32"]

Ha a 22-es portra nincs további üzleti allowlist, az SSH elérhetetlenné válik a public internetről. Postcondition: a security group sg-0d219sg 22-es portján nincs 0.0.0.0/0, csak a lab VPN dummy IP 192.0.2.10/32. A cleanup manifest továbbra is tervezetten tudja törölni az instance-t.

44.4.7 Rövid összefoglaló

A cloud account baseline a kívánt és megfigyelt állapot különbségét audit, tags, security és költség dimenzióban kezeli. Az account baseline verziózott desired állapot: IAM, hálózat, audit, budget és cleanup szabályok. A resource ownership minimálisan Owner, Environment, Expiration, LabId tageket jelent; ezek az inventory és a reaper bemenetei. A cleanup manifest a saját lab-azonosítók explicit listája, amelyre a törlés kiterjedhet. A billing nem azonos a usage-vel: a budget alert threshold, nem hard spending cap. A public exposure javítása allowlist, nem védelemkikapcsolás.

44.4.8 Források és ellenőrzési hiányok

A d219 cloud provider szolgáltatásai gyorsan változnak; az itt megadott parancsok, JSON mezők és service nevek nem futtatott, nem ellenőrzött illusztrációk. A hipotetikus óradíj (0.03 USD) nem hivatalos aktuális díj. A tényleges AWS CLI verzió, a Budgets API pontos mezőneve, a CloudTrail/Config képességek, valamint a GCP/Azure megfelelő szolgáltatások az adott sandboxban és az aktuális hivatalos dokumentációból ellenőrizendők.
