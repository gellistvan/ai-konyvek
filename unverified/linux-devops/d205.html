41.5 Cluster packet-path és volume incidenslabor

41.5.1 Motiváció

A Kubernetes-hibák gyakran a pod vagy a Deploy-állapot tünetében jelennek meg, miközben a tényleges hiba a CNI, a CSI, a Gateway controller vagy a host mount rétegben van. A CrashLoopBackOff és a Pending állapot önmagában nem elég; a diagnózishoz a Linux/network/storage rétegeken át kell haladni. Ez a labor a d204-ben bemutatott service-to-service trust és NetworkPolicy ismereteket, valamint a d155-ben tárgyalt firewall/NAT diagnosztikát és a d100-ban bemutatott backup/restore módszert kapcsolja a Kubernetes packet path és volume path incidenseihez. A cél, hogy a hallgató ne kapkodjon, hanem minden rétegből bizonyítékot gyűjtsön.

41.5.2 Definíciók és működés

Packet path alatt a kliens kérésének útját értjük a DNS névfeloldástól a Service clusterIP-jén át az EndpointSlice-ok által kiválasztott Pod IP-ig, majd a pod network namespace-éig. A út minden szakaszán más rendszer tulajdonol: CoreDNS/Resolve, kube-proxy/CNI, kubelet/network plugin. Ha egy szakasz hibás, a hiba a felette lévő rétegben jelentkezik: például az üres EndpointSlice azt jelenti, hogy a Service selector nem talál megfelelő podot, de a DNS még visszaadja a clusterIP-t.

Volume path alatt a PVC resource-tól a StorageClass-on és a CSI driveren át a node attach/kubelet mount pontig vezető utat értjük. A pendling PVC a VolumeBinding vagy a CSI driver szintjén akad el; a running pod mount hibája a node-on a kubelet és a kernel mount pontja között keresendő. A Pending PVC/attach/mount/UID hiba három eltérő root cause-t takar: a PVC Pending a kontrollerben, az attach timeout a node/CSP API-ban, a mount UID mismatch a pod securityContext-jában és a volume tulajdonosában.

A data-safe restore olyan helyreállítás, amely nem írja felül a még élő adatot: a snapshotból külön PVC-t készítünk, külön podban ellenőrizzük a fájlok integritását, és csak ezután cseréljük a production volume-ot. Az evidence report operatív jegyzőkönyv, amely rétegenként rögzíti a tünetet, a mért állapotot, a hipotézist, az egy változtatást, a rollbacket és az utóellenőrzést.

41.5.3 Kidolgozott példa: lab-web gateway és lab-data restore incidens

A lab környezetben egy lab-cluster nevű Kubernetes cluster fut, két névtérrel: lab-net és lab-vol. A lab-net namespace-ben egy lab-gw Gateway, egy lab-web-route HTTPRoute és egy lab-web Service található, amely a lab-web-deploy podjaihoz vezet. A lab-vol namespace-ben egy lab-data-pvc PVC, egy lab-data-pv PV és egy lab-data-snap VolumeSnapshot létezik. A pod egy C++ szolgáltatás, amely a /data/important.bin fájlba ír.

41.5.3.1 A) DNS → Service → Endpoint → Pod út ellenőrzése Gateway-backend hibánál

Tünet: A külső kliens lab-web.example.test címen TLS-kézfogás után HTTP 502-t kap; a podok Running és Ready állapotúak.

Első adatgyűjtés:

kubectl --context lab-cluster -n lab-net get gateway,httproute
kubectl --context lab-cluster -n lab-net describe httproute lab-web-route

A describe kimenetben a backendRefs section lab-web-old nevű Service-t hivatkozik a lab-web helyett. Ezt megerősíti, hogy a tényleges lab-web Service nem szerepel a route-ban. A Service állapota egészséges:

kubectl --context lab-cluster -n lab-net get endpointslices \
  -l kubernetes.io/service-name=lab-web -o wide

A kimenet mutatja, hogy az EndpointSlice nem üres, a pod IP-k szerepelnek. A debug podból a Service név feloldható:

kubectl --context lab-cluster -n lab-net exec -it lab-debug -- \
  nslookup lab-web.lab-net.svc.cluster.local

Root cause: A Gateway controller a HTTPRoute-ban megadott backendRefs alapján a lab-web-old Service-hez próbál forgalmat irányítani; mivel az nem létezik, a controller 502-t küld. A Service, a pod és a DNS út önmagában helyes.

Javítás:

# lab-web-route.yaml, módosított backendRefs
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: lab-web-route
  namespace: lab-net
spec:
  parentRefs:
  - name: lab-gw
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /
    backendRefs:
    - name: lab-web
      port: 8080
kubectl --context lab-cluster -n lab-net apply -f lab-web-route.yaml

Ellenőrzés: A debug podból curl -v http://lab-web.lab-net.svc.cluster.local:8080/health 200-at ad; a Gateway controller logja nem jelez hibát. Rollback: a korábbi route-verzió visszaállítása kubectl apply -f lab-web-route-previous.yaml paranccsal, ha a javítás nem lenne megfelelő.

41.5.3.2 B) Policy/DNS/MTU hiba diagnosztikája

Tünet: A podok közötti HTTP hívások átlagosan időnként 2–5 mp-ig akadoznak, a CoreDNS logjában i/o timeout figyelhető meg, a lab-web pod olykor Readiness probe failed állapotba kerül. A NetworkPolicy lab-web-egress a DNS-forgalmat engedélyezi, de a tünet nem szűnik meg.

Adatgyűjtés:

kubectl --context lab-cluster -n lab-net get networkpolicy lab-web-egress -o yaml
kubectl --context lab-cluster -n lab-net exec -it lab-debug -- \
  ping -M do -s 1472 10.244.2.10

A ping -M do -s 1472 a podból a másik pod IP-jét közvetlenül nem éri el, de a kisebb csomag (-s 1400) igen. A node-on a host bridge és a pod interfész MTU értékei:

ssh lab-node1 'ip link show | grep -E "mtu|bridge|veth"'

A host bridge MTU 1500, míg a CNI által létrehozott pod interfész MTU 1450. A CNI konfigurációban a mtu érték 1450, de a host oldalán a bridge nem lett ehhez igazítva. Emiatt az 1450 bájtnál nagyobb, fragmenálódó csomagok elvesznek, a DNS nagy válaszai TCP-re esnek vissza, ami a timeoutokhoz vezet.

Hipotézis: A Policy megegyezik a desired state-tel; a DNS timeout nem a CoreDNS hibája, hanem az MTU mismatch miatt a nagy UDP csomagok eldobódnak.

Javítás:

ssh lab-node1 sudo ip link set dev cni0 mtu 1450
ssh lab-node1 sudo ip link set dev fabian0 mtu 1450

A podok újraütemezése:

kubectl --context lab-cluster -n lab-net rollout restart deployment/lab-web-deploy

Ellenőrzés: A podból a ping -M do -s 1450 most már sikeres; a CoreDNS logja nem mutat timeoutot. Rollback: a bridge MTU visszaállítása 1500-ra, ha a javítás más tünetet okozna.

41.5.3.3 C) Volume út: PVC attach, mount és UID hiba

Tünet: A lab-data-pvc PVC Pending, a hozzá tartozó pod Pending; a kubectl describe pvc lab-data-pvc eventje waiting for a volume to be created, either by external provisioner or by system administrator.

Diagnózis:

kubectl --context lab-cluster -n lab-vol get pvc,pv,pods -o wide
kubectl --context lab-cluster -n lab-vol get events --sort-by=.lastTimestamp
kubectl --context lab-cluster -n lab-vol get csidriver

A csidriver resource lab.csi.example.io létezik, de a csi-lab-node pod a kube-system namespace-ben CrashLoopBackOff. A node-on a CSI driver plugin socket hiányzik:

ssh lab-node1 'ls -l /var/lib/kubelet/plugins_registry/lab.csi.example.io/'

A plugin.sock nem található, mert a CSI driver pod indítása során egy MountVolume.SetUp failed jelet ad. A root cause a node runtime containerd configjában megadott plugin-registry elérési út hibája. A javítás a CSI driver pod újraindítása, előtte a node cordon és drain:

kubectl --context lab-cluster drain lab-node1 --ignore-daemonsets --delete-emptydir-data
kubectl --context lab-cluster -n kube-system rollout restart daemonset lab-csi-node
kubectl --context lab-cluster uncordon lab-node1

A PVC a következő kubectl get pvc során Bound lesz. A pod elindul, de a RunContainerError event mkdir /data: permission denied üzenettel jelenik meg. A pod securityContext-jában runAsUser: 1000 szerepel, de a volume-on a /data könyvtár tulajdonosa root:root és 0755. Az írási jogosultságot a fsGroup: 1000 beállítással oldjuk meg:

# deployment patch
spec:
  template:
    spec:
      securityContext:
        runAsUser: 1000
        fsGroup: 1000
kubectl --context lab-cluster -n lab-vol apply -f lab-web-deploy-fsgroup.yaml

Ellenőrzés: A pod Running, a /data/important.bin írható, a kubectl exec sikeres. Rollback: a fsGroup eltávolítása és a pod újraindítása, ha a csoportváltozás nem kívánt mellékhatást okoz.

41.5.3.4 D) Snapshot/reclaim/restore és integrity

Egy nem szándékos kubectl delete pvc lab-data-pvc parancs a reclaimPolicy: Delete miatt törölte a PV-t is. A VolumeSnapshot lab-data-snap rendelkezésre áll; az eredeti adat elveszett, de a snapshotból visszaállítható.

Data-safe restore:

kubectl --context lab-cluster -n lab-vol get volumesnapshot lab-data-snap

A restore PVC-t külön néven hozzuk létre:

# restore-pvc.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: lab-data-restored
  namespace: lab-vol
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: lab-sc
  dataSource:
    name: lab-data-snap
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io
  resources:
    requests:
      storage: 1Gi
kubectl --context lab-cluster -n lab-vol apply -f restore-pvc.yaml
kubectl --context lab-cluster -n lab-vol get pvc lab-data-restored -w

Ha a PVC Bound, egy ellenőrző podot indítunk, amely csak olvashatóan mountolja a volume-ot, és kiszámítja a fájl checksumját:

kubectl --context lab-cluster -n lab-vol run restore-check \
  --image=busybox --restart=Never --rm -it -- \
  sh -c "mount -o ro /dev/data-volume /mnt/data && sha256sum /mnt/data/important.bin"

A várt hash a backup manifestből ismert: d41d8cd98f00b204e9800998ecf8427e (példa, nem a tényleges fájlra). Ha a checksum egyezik, a restore integritása igazolt. Csak ezután irányítjuk a production deploymentet az új PVC-hez:

kubectl --context lab-cluster -n lab-vol set volume deployment/lab-web-deploy \
  --add --name=lab-data --claim-name=lab-data-restored

Postcondition: Az adat nem sérült, a service smoke test sikeres, a régi PVC/PV név szerint eltakarítható.

41.5.4 Hibák és ellenpróbák

Service ClusterIP pingelése: A ClusterIP nem ICMP-cél; a ping sikertelensége nem bizonyítja a Service hibáját. Helyette curl-t használjunk a podból. DNS-t a host resolverrel ellenőrizni: A host /etc/resolv.conf nem a Kubernetes DNS-t használja; a podban kell futnia a tesztnek. NetworkPolicy deny és CoreDNS blokkolás összekeverése: Ha a DNS timeout, de a policy engedi, ellenőrizzük az MTU-t és a CNI állapotát, mielőtt a policy-t módosítjuk. PVC Pending-et a kapacitásnak tulajdonítani: A Pending leggyakrabban a StorageClass/CSI hiba; a describe pvc eventjeiből kiderül. A mount UID hibájánál a runAsUser-t a fsGroup-gal összekeverni: Az fsGroup nem változtatja a pod futási UID-jét, de a volume engedélyeit a csoportra állítja. Data-safe restore nélkül felülírni a meglévő adatot: A snapshotból külön PVC-t hozzunk létre, és a checksumot ellenőrizzük, mielőtt a production PV-re cserélünk.

41.5.5 Feladatok

1. Magyarázó feladat. Az alábbi kimeneteket kapod: a lab-web Service ClusterIP-je feloldható, az EndpointSlice üres, de a pod fut. Melyik rétegben keresnéd a hibát, és milyen sorrendben hajtanád végre a diagnosztikai lépéseket? Indokold a lépéseket.

2. Adminisztrációs feladat. A lab-vol namespace-ben hozz létre egy VolumeSnapshot-ot a lab-data-pvc PVC-ről, majd töröld a PVC-t (a PV-t is), végül restore-olj a snapshotból egy új PVC-t. Ellenőrizd a fájl checksumját. A parancsokban jelöld a target, privileges, előfeltétel, ellenőrzés és rollback elemeket.

3. Diagnosztikai/failure/recovery feladat. A pod lab-web-stateful-0 Pending, a PVC Bound, de a pod eventje MountVolume.SetUp failed for volume "lab-data-pv" : write-protected device. A CSI driver pod egészséges a node-on. Lépésről lépésre diagnosztizáld a PV, node mount és pod securityContext állapotát, és javítsd a hibát. Utána futtass egy smoke tesztet a lab-web service elérésére.

41.5.6 Megoldások

1. megoldás. Az üres EndpointSlice azt jelenti, hogy a Service selector nem talál megfelelő pod labelt. A hibát a Service-pod label tengelyen keresnénk: kubectl describe svc lab-web -n lab-net és kubectl get pods -n lab-net --show-labels. Ha a selector helytelen, a Service-t módosítjuk; ha a pod label hiányzik, a podot annotáljuk. A DNS feloldás működik, mert a clusterIP létezik; a hiba a Service-től a podig terjedő szakaszon van. Postcondition: Az EndpointSlice nem üres, a podból a Service elérése 200-at ad.

2. megoldás. A VolumeSnapshot létrehozása:

# snapshot.yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: lab-data-snap
  namespace: lab-vol
spec:
  volumeSnapshotClassName: lab-snapclass
  source:
    persistentVolumeClaimName: lab-data-pvc
kubectl --context lab-cluster -n lab-vol apply -f snapshot.yaml
kubectl --context lab-cluster -n lab-vol wait --for=jsonpath='{.status.readyToUse}'=true volumesnapshot/lab-data-snap
kubectl --context lab-cluster -n lab-vol delete pvc lab-data-pvc
kubectl --context lab-cluster -n lab-vol apply -f restore-pvc.yaml
kubectl --context lab-cluster -n lab-vol wait --for=jsonpath='{.status.phase}'=Bound pvc/lab-data-restored
kubectl --context lab-cluster -n lab-vol run restore-check --image=busybox --restart=Never --rm -it -- sh -c "sha256sum /mnt/data/important.bin"

A checksum egyezése után a podot újra rákötjük az új PVC-re. Postcondition: A lab-data-restored PVC Bound, az integritás igazolt, a service smoke teszt sikeres.

3. megoldás. A write-protected device hiba arra utal, hogy a PV readOnly: true beállítással jött létre, vagy a nodeon a device mount read-only. Adatgyűjtés:

kubectl --context lab-cluster -n lab-vol get pv lab-data-pv -o yaml
ssh lab-node1 'mount | grep lab-data'

Ha a PV spec readOnly, akkor a PV-t módosítjuk; ha a device read-only, a nodeon a mount opciókat nézzük. A pod securityContext readOnlyRootFilesystem nem releváns itt. A javítás után a pod Running, a volume írható. Postcondition: A pod Running, a /data/important.bin írása sikeres, a service elérése 200.

41.5.7 Rövid összefoglaló

A Kubernetes hálózati hibákat a DNS→Service→Endpoint→Pod úton, a storage hibákat a PVC→PV→StorageClass→CSI attach→mount úton rétegről rétegre kell visszavezetni. A tünet nem azonos a root cause-szal; a Gateway 502 hátterében backendRef mismatch, a DNS timeout hátterében MTU mismatch állhat. A volume hibák a Pending, attach, mount és UID mismatch szintjein jelentkeznek. A data-safe restore során a snapshotból külön PVC-t készítünk, checksummal igazoljuk az integritást, és csak ezután cserélünk production volume-ot. Az evidence report rétegenként rögzíti a mért állapotot, a javítást és a rollbacket.

  • Packet path: a DNS-től a Service clusterIP-jén át a pod IP-ig vezető út.
  • Volume path: a PVC-től a CSI driveren át a node mountig vezető út.
  • Data-safe restore: integritás-ellenőrzött helyreállítás külön PVC-re, a production adat felülírása nélkül.

41.5.8 Források és ellenőrzési hiányok

A forráskiindulópontok nem ellenőrzött dokumentációk, nem tekintem őket olvasottnak. A változó technológiai állítások a labkörnyezet verziójától függenek.

  • Kubernetes dokumentáció
  • Kubernetes Gateway API specifikáció
  • Cilium dokumentáció
  • Ceph releases

Ellenőrzési hiányok: a konkrét CNI/CSI verziók, a Gateway controller implementációja, a VolumeSnapshot API pontos viselkedése, a StorageClass és reclaimPolicy kombinációja, valamint a node host mount state tényleges laborfuttatás nélkül nem igazolható. A parancsok illusztratív kimenetek; a valós labkörnyezetben a verziókat, support matrixot és a CNI/CSI driver naplóit rögzíteni kell.
