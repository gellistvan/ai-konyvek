37.3 Registry auth, push/pull és retention

37.3.1 Motiváció és definíció

A build pipeline eredménye akkor válik futó szolgáltatássá, ha a Kubernetes node vagy a céleszköz le tudja húzni a tárolt image-et. A registry ezért nem egyszerű HTTP fájlszerver, hanem elérhetőséggel, hitelesítéssel, integritással és retention élettartammal rendelkező szolgáltatás. Ha a DNS-feloldás, a TLS-lánc, a token-scope vagy a manifest bármely rétege hibás, a pull nem jön létre, és a hiba a fejlesztő buildjétől függetlenül áll elő.

Az előzményekből d182 az OCI image, digest és tag modellt, d142 a TLS- és tanúsítványláncot, d111 az inventory, desired state és drift fogalmát adja. Itt ezeket a registry mint artifact distribution szolgáltatás üzemeltetési nézetébe kapcsoljuk.

Registry endpoint: az a hálózati erőforrás, amely az OCI Distribution API-t kiszolgálja; a repository nevekkel és reference-ekkel együtt értelmezett, ezért nem csak IP-cím vagy port. Például https://registry.lab.example:5000 az endpoint, amelyen belül a lab-team/cpp-service repository érhető el.

OCI Distribution API: szabványos HTTP API image manifestek és blobok feltöltésére, lekérdezésére és törlésére; a specifikáció biztosítja, hogy a Docker, Podman, containerd, skopeo és más OCI-kliens közös protokollt beszéljen. A scope itt a regisztrációkliens és registry közötti hitelesített, tartalomcímzett műveletekre terjed ki, nem a node-ra való kép pull scheduler működésére.

A munkafolyamatot így modellezzük:

Ppull=DNS→TCP/TLS→Auth→Manifest→Blobs P_{pull} = \text{DNS} \rightarrow \text{TCP/TLS} \rightarrow \text{Auth} \rightarrow \text{Manifest} \rightarrow \text{Blobs}

ahol minden lépés előfeltétele a következőnek; a digest-verifikáció a manifest és blob réteg integritását együtt zárja.

37.3.2 Registry endpoint és OCI Distribution API

A registry elérhetőség értékelése mindig a fenti lánc mentén halad. A DNS-feloldás a service name, port és feloldott címek közötti kapcsolatot ellenőrzi; a TLS a hitelesítést; a HTTP az API elérhetőségét. Az endpoint állapota tehát nem bináris: a curl https://registry... sikeréhez mindhárom rétegnek működnie kell.

A leggyakoribb OCI Distribution API műveletek:

Művelet Metódus Példa útvonal Cél
API discovery GET /v2/ végpont verzió és support ellenőrzése
Tag lista GET /v2/<name>/tags/list referencia felsorolás
Manifest HEAD/GET/PUT/DELETE /v2/<name>/manifests/<reference> manifest és digest műveletek
Blob létezés HEAD /v2/<name>/blobs/<digest> tartalomcímzett blob ellenőrzés
Blob upload POST/PUT /v2/<name>/blobs/uploads/ rétegfeltöltés

A reference lehet tag (1.0.0) vagy digest (sha256:...). A tag mutálható, a digest immutable. Emiatt a laborban mindig digestet kérünk, amikor a tényleges artifactot azonosítjuk, a tag csak kényelmi index.

A registry endpoint láthatósága a build agent, a Kubernetes node és a fejlesztői gép felől azonos vizsgálattal történik: getent hosts, openssl s_client, curl -I /v2/. A /v2/ API-válasz rate-limit és auth szempontból is diagnosztikus; a 401 válasz a hitelesítés szükségességéről árulkodik, a 200-as válasz az API elérhetőségét jelenti.

37.3.3 Auth token/scope és credential helper

A hitelesítés modellje a Bearer token. A kliens először a registrytől 401 Unauthorized választ kap, amely WWW-Authenticate headerben hirdeti a token-szerver realmjét, service nevét és scope-ját. A kliens ezután a felhasználó hitelesítőadataival tokent kér a realmből, majd azt Authorization: Bearer <token> headerben csatolja a registry API-műveletekhez.

A token scope a jogosultság határát jelöli, nem csupán a user létezését. Például:

repository:lab-team/cpp-service:pull
repository:lab-team/cpp-service:pull,push

Az első csak pullra használható, a második pushra is. A credential helper ezt a hitelesítési folyamatot automatizálja: a docker login / podman login parancs lekéri a tokent, és a CLI konfigurációjában tárolja. A tárolás helye ~/.docker/config.json, illetve ~/.config/containers/auth.json. A helper maga gyakran külső bináris, például egy vállalati Vault-tal integrált credential helper; ezt a konfigurációban credHelpers kulccsal jelöljük.

A labregistryben a htpasswd-hitelesítés beépített realm használatával demonstrálható:

# registry lab config.yml kivonat
version: 0.1
auth:
  htpasswd:
    realm: "registry.lab.example:5000/auth"
    path: /auth/htpasswd

A user hozzáadása a htpasswd fájlhoz a registry üzemeltető művelete; a kliens oldalán a podman login kezeli a tokencserét. A login után érdemes ellenőrizni, hogy a mentett credential tényleg a kívánt endpointra vonatkozik: a config fájlban a key a teljes endpoint, nem csak a registry hostname.

37.3.4 Push/pull/digest verify

A push nem egyszerű fájl feltöltés, hanem OCI Distribution API szekvencia. A kliens először a blobokat tölti fel, majd manifestet ír. A manifest PUT után a registry visszaadja az artifact manifest digestjét; ez az érték az immutable referencia.

A pull során a kliens a manifestet kéri le, megkapja a blob digest listát, letölti a blobokat, és minden réteg tartalmát ellenőrzi a manifestben hivatkozott digest ellen. Ez a digest verify: nem elég a tag azonosítása, a tartalmat a manifestben rögzített sha256 értékekhez kell kötni.

Fontos különbség: a podman push utáni Digest: sha256:... a manifest digest; a blob réteg digest-ek pedig a manifest layers[].digest mezői. A referenciaintegritás akkor teljes, ha a manifest digestet és a blob digesteket együtt tudjuk reprodukálni. A laborban ezt a skopeo inspect vagy a crane digest parancs mutatja meg.

A deployment protokollban a manifest digestet kell pin-elni, nem a taget. A Kubernetes pod spec-ben ez közvetlenül nem mindig lehetséges, mert a konténer spec image mezője taget vár; ilyenkor a digestet imagePullPolicy és a registryben rögzített tag-replace workflow kezeli. A legtisztább megoldás a digest-prefixelt image név a pod specben.

37.3.5 Proxy mirror/cache és air gap

A proxy registry (registry mirror) egy köztes HTTP gyorsítótár. A kliens a mirrorhoz fordul; ha a kért manifest nincs cache-ben, a mirror lekéri az upstream registryből, tárolja, majd továbbítja. A mirror célja a network egress csökkentése és a pull latency javítása, de nem helyettesíti az upstream auth policy-t, mert a mirror csak az artifact-ot cache-ezi.

A Podman és Docker konfigurációjában a mirror deklarative megadható. Például a labban a host /etc/containers/registries.conf fájlja:

# /etc/containers/registries.conf lab kivonat
unqualified-search-registries = ["registry.lab.example:5000"]

[[registry]]
prefix = "docker.io"
location = "mirror.lab.example:5000"

Az air gap környezetben nincs egress; a mirror nem tud upstreamhez fordulni. Ilyenkor az image-et szállítható köztes formátumba kell írni, majd a céloldali registrybe importálni. A skopeo copy megőrzi a digestet:

# labhost1, lab-user UID 1000; egress nélkül a közvetlen copy nem futhat
skopeo copy docker://registry.lab.example:5000/lab-team/cpp-service:1.0.0 dir:./lab-airgap
# céloldali, egress nélküli registrybe
skopeo copy dir:./lab-airgap docker://registry.airgap.lab:5000/lab-team/cpp-service:1.0.0

A dir: köztes formátum manifest és blob mellett hordozza az integritási adatokat, ezért a digest-verify a céloldalon újra futtatható.

37.3.6 Retention/garbage collection/referenced blob

A registry tárolója content-addressable: a blobokat digestjük azonosítja, a manifestek hivatkoznak rájuk. A tag törlése önmagában nem törli a blobokat, mert más tag vagy manifest tovább hivatkozhat rájuk. A garbage collection (GC) az a folyamat, amely a hivatkozás nélküli blobokat ténylegesen felszabadítja.

A retention policy azt adja meg, hogy mely tag-ek vagy manifestek őrződnek meg, és melyek törölhetők. A megadás mindig a registry product specifikus API-ján vagy konfigurációján keresztül történik; a labregistry Docker Distribution image-ben nincs beépített retention, ezért ott a törlés API-műveletekkel, a GC pedig a registry image parancsával demonstrálható. A retention policy-t tehát ne a kliens docker rmi parancsával keverjük: az a helyi cache-ből töröl, nem a registryből.

A referenced blob fogalma: a blob akkor törölhetetlen, ha legalább egy manifest schemaVersion szerinti hivatkozásában szerepel. Amíg a hivatkozó manifest nem törlődött, a GC-nek meg kell tartania a blobot. Ez a hivatkozási gráf a retention célja: mindig a manifest-törlés az előfeltétel, a blob törlés csak utána következhet.

A labban a retention policy karbantartása így válik ellenőrizhetővé: a tag lista, a manifest digest lekérés, a DELETE művelet és a GC utáni du méretváltozás külön lépésekben jelentkezik.

37.3.7 Rate limit/egress és availability

A registry mint szolgáltatás rate limit alá eshet. Ha a kliens túl sok requests-et ad, a registry 429 Too Many Requests HTTP választ adhat, gyakran Retry-After headerrel. Az anonim pull korlátozott, a bejelentkezett user többet kaphat; a policy a provider által meghatározott.

A registry availability nem azonos a registry endpoint elérhetőségével. A node-on már letöltött image cache, a Kubernetes imagePullPolicy és a replicaset process mind külön réteg. A pod csak akkor lép kép pullra, ha a node nem rendelkezik az image-t, vagy a pull policy ezt előírja. A read-only file system és a registry SLO szempontjából a lekért artifact digest rögzítése csökkenti a mutálódó tagre mutató dependencyt.

A rate limit és egress hibát a registry oldali log, a curl -I válasz és a kliens HTTP-napló együttesen jelzi. A metric a pull kérés száma, a manifest és blob letöltési ideje; a nagy blob pull a throughput méréshez tartozik. Az availability service level indicator (SLI) a sikeres pull időbeli aránya; a rate limit által visszautasított kéréseket a policy explicit módon kizárhatja vagy belevonhatja.

37.3.8 Kidolgozott példa: labregistry push és digest verify

A példa a labhost1 Ubuntu 24.04 VM-en fut, lab-user UID 1000, a lab-user a Podman group tagja. A registry a lab hálózatban fut, dokumentációs címpéldában 192.0.2.10 IP-vel, service név registry.lab.example:5000. A lab DNS /etc/hosts bejegyzésre épül, a TLS tanúsítvány subject CN registry.lab.example.

1. DNS és TLS ellenőrzés:

# labhost1, lab-user UID 1000
getent hosts registry.lab.example
openssl s_client -connect registry.lab.example:5000 \
  -servername registry.lab.example </dev/null 2>/dev/null | \
  openssl x509 -noout -subject -dates

Várható kimenet:

192.0.2.10  registry.lab.example
subject=CN = registry.lab.example
notBefore=...   notAfter=...

2. Login és push:

# labhost1, lab-user UID 1000; REGISTRY_USER/PASSWORD a lab inventory dummy változóból
podman login registry.lab.example:5000 \
  --username "$LAB_REGISTRY_USER" --password-stdin <<<"$LAB_REGISTRY_PASSWORD"

podman tag localhost/lab-cpp-service:latest \
  registry.lab.example:5000/lab-team/cpp-service:1.0.0

podman push registry.lab.example:5000/lab-team/cpp-service:1.0.0

Várható záró sor:

Digest: sha256:ab12... (a tényleges manifest digest)

3. Pull és digest verify:

# digest pinning a tag helyett
REG_DIGEST=$(skopeo inspect \
  docker://registry.lab.example:5000/lab-team/cpp-service:1.0.0 | \
  jq -r .Digest)

echo "$REG_DIGEST"
# Várható: sha256:ab12... (megegyezik a push visszaadott digesttel)

podman pull "registry.lab.example:5000/lab-team/cpp-service@${REG_DIGEST}"
# Várható: a letöltött image digest azonos

Ellenőrzési feltétel: a podman images --digests kimenetben a megfelelő image digest megegyezik $REG_DIGEST értékével.

4. Retention demonstráció:

# Tag lista lekérés
TOKEN=$(curl -fsS -u "$LAB_REGISTRY_USER:$LAB_REGISTRY_PASSWORD" \
  "https://registry.lab.example:5000/auth?scope=repository:lab-team/cpp-service:pull,push&service=registry.lab.example:5000" \
  | jq -r .token)

curl -fsS -H "Authorization: Bearer $TOKEN" \
  "https://registry.lab.example:5000/v2/lab-team/cpp-service/tags/list"
# Várható: {"name":"lab-team/cpp-service","tags":["1.0.0"]}

# A manifest digest lekérése a DELETE-hez
curl -I -H "Authorization: Bearer $TOKEN" \
  "https://registry.lab.example:5000/v2/lab-team/cpp-service/manifests/1.0.0" \
  | grep -i docker-content-digest

# DELETE reference
curl -X DELETE -H "Authorization: Bearer $TOKEN" \
  "https://registry.lab.example:5000/v2/lab-team/cpp-service/manifests/sha256:..."

# GC a registry konténerben (a registry image verziójától függ)
podman exec registry-lab bin/registry garbage-collect \
  /etc/docker/registry/config.yml

A GC utáni blob felszabadulást a registry storage kötet méretváltozása mutatja. A retention policy itt implicit; production registry product esetén a policy megadás vagy a webes API, vagy konfigurációs YAML.

37.3.9 Hibák és ellenpróbák

Hiba: dial tcp: lookup registry.lab.example: no such host.
Hipotézis: a DNS-feloldás nem éri el a lab domain nevet.
Adatgyűjtés: getent hosts registry.lab.example, dig +short registry.lab.example.
Egy változtatás: a lab host /etc/hosts bejegyzését hozzáadni, vagy a lab DNS A rekordját javítani.
Verifikáció: getent hosts ismételt futtatása a várt IP-t adja.

Hiba: certificate signed by unknown authority.
Hipotézis: a kliens nem bízik meg a lab registry CA-ban.
Adatgyűjtés: openssl s_client -showcerts a lánc megtekintéséhez.
Egy változtatás: a lab CA certet a Podman/Docker trust store-ba másolni (/etc/docker/certs.d/registry.lab.example:5000/ca.crt vagy Podman esetén a trust store konfigurálása).
Verifikáció: podman pull újraindítása, a TLS kapcsolat sikeres.

Hiba: unauthorized: authentication required, bár a login korábban sikeres volt.
Hipotézis: a credential helper nem a megfelelő endpointra ad token; vagy a token scope hiányos.
Adatgyűjtés: podman login --get-login registry.lab.example:5000, podman push --log-level=debug a token kérés megtekintéséhez.
Egy változtatás: a credential config endpoint key törlése a ~/.config/containers/auth.json fájlból, majd új podman login.
Verifikáció: a push sikeres, a debug logban a Authorization: Bearer header jelen van.

Hiba: push után a podman images --digests más digestet mutat, mint a manifest inspect.
Hipotézis: a helyi image réteg digest eltér a registry manifestben rögzítettől; vagy a tag mutálódott.
Adatgyűjtés: skopeo inspect a registry manifest digestre, és a helyi podman image inspect RepoDigests mezőjére.
Egy változtatás: a deploy reference-et digestre cserélni, ahogy a példában.
Verifikáció: a podman pull @digest sikeres, a podman rmi a taget törli, de a digest image megmarad.

37.3.10 Feladatok

1. Magyarázó feladat

Írd le, miért nem elegendő a podman push visszatérési értéke a registry artifact integritás bizonyításához, és miért kell a manifest digest mellé a blob digesteket is ellenőrizni. Sorold fel az OCI Distribution API három olyan műveletét, amely a digest-verify szempontjából releváns.

2. Adminisztrációs/konfigurációs feladat

A labregistryben hozz létre egy lab-team repository-t, végpontot, login konfigurációt, és tölts fel egy image-t. Ezután rögzítsd a manifest digestet fájlba, és bizonyítsd a pull utáni azonosságot. A feladat célja a credential helper és digest-pinning használata; a push és pull parancsok mellett a skopeo inspect kimenet is szerepeljen.

3. Diagnosztikai/failure feladat

A build agent nem tud pullolni a registryből, a hiba toomanyrequests. A kezdeti hipotézis az, hogy a registry túlterhelt vagy rate limit lépett életbe. Nyújts diagnosztikai eljárást: milyen HTTP kódot vársz, hogyan olvasod le a Retry-After headert, és milyen registry logot vizsgálnál. Adj meg egy változtatást, amely a pull rate limitet csökkenti anélkül, hogy az auth policy-t megsértené.

37.3.11 Megoldások

1. megoldás

A podman push visszatérési kódja csak a művelet sikerességét jelzi, nem a tartalom integritását. A manifest digest a manifest tartalmát hash-eli; a blob rétegek digestjei a manifestben hivatkoznak. Ha egy blob sértül, a manifest digest változatlan marad, ezért a réteghash ismerete nélkül a sérülést nem észleljük. A három releváns OCI Distribution API művelet: HEAD /v2/<name>/manifests/<reference> a digest lekéréshez, GET /v2/<name>/blobs/<digest> a rétegek letöltéséhez, HEAD /v2/<name>/blobs/<digest> a blob létezésének ellenőrzéséhez. A helyes podman pull @digest mindhárom műveletet elvégzi a kliensben. Postcondition: a pull után a kliens képes a manifest és blob digesteket együttesen ellenőrizni.

2. megoldás

# labhost1, lab-user UID 1000; login, push, digest pinning
podman login registry.lab.example:5000 \
  --username "$LAB_REGISTRY_USER" --password-stdin <<<"$LAB_REGISTRY_PASSWORD"

podman tag localhost/lab-cpp-service:latest \
  registry.lab.example:5000/lab-team/cpp-service:1.0.0

podman push registry.lab.example:5000/lab-team/cpp-service:1.0.0

skopeo inspect docker://registry.lab.example:5000/lab-team/cpp-service:1.0.0 \
  | jq -r .Digest > /tmp/lab-cpp-service.digest

cat /tmp/lab-cpp-service.digest
# Várható: sha256:... (a manifest digest)

podman pull "registry.lab.example:5000/lab-team/cpp-service@$(cat /tmp/lab-cpp-service.digest)"

podman images --digests registry.lab.example:5000/lab-team/cpp-service

Indoklás: a skopeo inspect a registryben tárolt artifact-ot kérdezi le, függetlenül a lokális cache-től. A podman pull @digest a manifest digestet pin-eli; a podman images --digests kimenetben az azonosítónak egyeznie kell. Postcondition: a lokális image digest megegyezik a /tmp/lab-cpp-service.digest fájl tartalmával.

3. megoldás

A toomanyrequests hibát a 429 Too Many Requests HTTP válasz jelzi. A Retry-After header a várakozási időt adja meg. A diagnosztikai eljárás:

# curl a registry /v2/ API-ra, auth nélkül is lehet 401, de a 429 a rate limit
curl -I "https://registry.lab.example:5000/v2/"
# Várható: HTTP/1.1 429 Too Many Requests, Retry-After: 3600

curl -I "https://registry.lab.example:5000/v2/" | grep -i retry-after

A registry oldali logban a rate limiter eseményeket a registry konténer stdoutja vagy a journal mutatja; a podman logs registry-lab a bejövő kérések számát és a rate limit döntést rögzíti. Az egy változtatás: használjon a build agent egy pull-through mirror cache-t (a konfigurációt a host /etc/containers/registries.conf fájl tartalmazza), így az ismételt kérések a mirrorból indulnak, nem az upstream registryből. A hitelesítés változatlan marad, mert a mirror az upstream autentikációt továbbítja. Postcondition: a build agent image pull kérés nem lép túl az upstream provider rate limitjén, a mirrorból a podman pull sikeres.

37.3.12 Rövid összefoglaló

A registry endpoint elérhetősége és hitelesítése a DNS, TLS, Auth és Manifest rétegek együttes működésétől függ. A push/pull mindig digest-verify mellett történik: a tag mutálható, a manifest digest immutable referencia. A credential helper a token-scope-ot kezeli; a scope meghatározza a pull/push jogot. A mirror cache csökkenti az egress terhelést, de az air gap eszköz nélkül nem érhető el; ilyenkor skopeo copy köztes dir: formátummal szállít. A retention policy a tag/manifest törlés és a hivatkozatlan blob GC sorrendjét rögzíti. A rate limit és availability külön service réteg.

  • Digest: az artifact tartalomra számított immutable hash, hivatkozási azonosító.
  • Credential helper: a registry hitelesítőadat-tárolást és token-cserét végző klienskomponens.
  • Referenced blob: olyan blob, amelyet legalább egy manifest hivatkozik, ezért a GC nem törölheti.
