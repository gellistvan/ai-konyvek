58.1 Verzió, support, deprecation és technológiai térkép

58.1.1 Motiváció

A szenior C++ fejlesztő a saját buildjében megszokta, hogy a függőségeket, a toolchain verzióját és a shared library ABI-t explicit módon rögzíti. Ugyanez az igény az infrastruktúránál is fennáll: egy production cluster vagy egy lab host attól reprodukálható, hogy minden réteghez tartozik verzió, támogatási állapot, forrás és eltéréskezelés. A „legfrissebb dokumentáció” gyakran a legújabb, de nem a futó release-re vonatkozik. A d286 célja, hogy a hallgató support matrixot (támogatási mátrixot) készítsen, és meg tudja különböztetni a stabil kiadást a fejlesztői vagy deprecated (elavult, megmaradt, de eltávolításra jelölt) állapottól.

58.1.2 Definíció és működés

58.1.2.1 Support matrix

A support matrix olyan, forrásokkal és dátummal ellátott táblázat, amely egy adott környezethez köti a komponensek verzióját és állapotát. Nem pusztán „mi fut” leltár, hanem annak eldöntése, hogy az adott kombinációt támogatottnak, karbantartottnak vagy csak development állapotúnak tekintjük-e. A mátrix sorai legalább a következő mezőket tartalmazzák: component, version, state, source, date, fallback, skew_note. A state megkülönbözteti a stabil, deprecated, dev-only, experimental és removed állapotokat. A date az ellenőrzés időpontja, a fallback pedig az a módszer, amellyel akkor dolgozunk, ha a hivatalos forrás nem elérhető.

A mátrixot nem elég egyszer elkészíteni: a CI/CD pipeline vagy a release audit során újra kell validálni, különösen dependency frissítés, Kubernetes minor upgrade vagy disztribúcióverzió-váltás előtt.

58.1.2.2 Technológiai térkép

A d286 területén a technológiai térkép azt a réteget írja le, amely a szolgáltatás release artifactjától a futó infrastruktúráig terjed. A d285–d290 referenciafejezetben ez a térkép összekapcsolja a korábbi ismereteket. Az alábbi csoportokat érdemes külön kezelni:

  • OS/kernel/systemd: Az Ubuntu Server 24.04 LTS a lab baseline. A pontos kernel és systemd csomagverziót a lab image rögzíti; a kernel.org latest dokumentum nem feltétlenül erre a distro backportra vonatkozik.
  • Container runtime: A containerd verzióját a Kubernetes CRI támogatási mátrixszal együtt kell olvasni.
  • Kubernetes/API/addon: A Kubernetes version skew policy határozza meg, mekkora verzióeltérés engedhető a control plane, a kubelet, a kubectl és az addonok között. A pontos toleranciát hivatalos forrásból kell ellenőrizni; a d286 keretrendszerében erre csak rátekintünk. Az API-k közül a v1 stabil, míg a v1beta1 és v1alpha1 fokozatosan deprecated vagy experimental lehet. A feature gate-ekkel engedélyezett képességek esetén külön állapotmező szükséges.
  • Ingress/Gateway/controller: Az Ingress API a networking.k8s.io/v1 alatt stabil, de az egyes ingress-controllerek karbantartási állapota projektenként eltérő. A Gateway API csatornái külön stable/experimental jelölést kaphatnak. A controller maintenance state, például „archived”, „maintained, but not recommended” vagy „actively maintained”, forrásból igazolandó.
  • QEMU/Ceph: A master és a latest dokumentáció fejlesztői állapotot jelölhet; a production döntéshez a distro stabil csomagját és a release-specifikus dokumentációt kell használni. A QEMU esetében a lab a distro csomagot futtatja, nem a git masteret. A Ceph latest dokumentációja a development ágakra mutathat.
  • Ansible/IaC/Helm/OTel: Az ansible-core és a collections külön-külön életciklust követ; a playbookban a collection verziót pinelni kell. Az OpenTofu/Terraform provider lock file rögzíti a használt provider verziót. A Helm supported Kubernetes version mátrixot közöl. Az OTel egyes jelek (metrics, logs, traces) API-stabilitási szintje különbözik; a C++ instrumentation esetén a stable és experimental névterek ismert szétválasztást adnak.

58.1.2.3 Date, source, fallback

A mátrix csak akkor használható bizonyítékként, ha minden állításhoz tartozik ellenőrzési dátum és forrás. A forrás legyen hivatalos release note, project docs vagy distro policy. A fallback az a helyi, parancssori ellenőrzési módszer, amely akkor is működik, ha a webes forrás nem elérhető. Az ettől való eltérést dokumentálni kell; a state=unverified jelölés elfogadható, ha a döntést még nem lehet bizonyítottan meghozni.

58.1.3 Kidolgozott példa

A példa célja egy lab-scope support matrix létrehozása. Az alábbi parancsok izolált lab környezetben futnak; a <...> értékek ellenőrizendők.

# target: lab-vm-01; user: labadmin (UID 1000)
# előfeltétel: lab-vm-01 SSH-n elérhető; lab kubeconfig a ~/.kube/config
# scope: lab, nem production

# Helyi verziók gyűjtése:
cat /etc/os-release | grep '^\(NAME\|VERSION_ID\)=' 
uname -r
systemctl --version | sed -n '1p'
containerd --version
kubectl version --output=yaml | sed -n '1,60p'

Várt kimenet (illusztratív, nem futtatott):

NAME="Ubuntu"
VERSION_ID="24.04"
Linux lab-vm-01 6.8.0-<lab-kernel> ...
systemd 255.4-1ubuntu8.4
containerd 1.7.19+ubuntu24.04
kubectl v1.29.14
...

A gyűjtött adatokat rögzítjük egy YAML mátrixban:

# Cél: lab scope; a <...> placeholder ellenőrizendő.

kind: SupportMatrix
scope: lab-vm-01
generated_at: "ELLENŐRZÉSRE VÁR"
fallback_policy: "ha egy sor forrása nem elérhető, a row state=unverified"
rows:
  - component: "distro"
    version: "Ubuntu Server 24.04 LTS"
    state: "lab_lts_baseline"
    source: "https://ubuntu.com/server/docs/"
    source_date: "<ellenőrizendő>"
    fallback: "/etc/os-release"
    skew_note: "n/a"
  - component: "kernel"
    version: "<lab-kernel-package-version>"

    source: "https://docs.kernel.org/"

    fallback: "apt-cache policy linux-image-generic"
    skew_note: "distro release policy, nem kernel.org latest"
  - component: "systemd"
    version: "<lab-systemd-version>"
    state: "distro_release"
    source: "https://ubuntu.com/server/docs/"
    source_date: "<ellenőrizendő>"
    fallback: "systemctl --version"
    skew_note: "n/a"
  - component: "containerd"
    version: "<lab-containerd-version>"
    state: "stable_for_cri"
    source: "https://kubernetes.io/docs/"
    source_date: "<ellenőrizendő>"
    fallback: "containerd --version"
    skew_note: "CRI compatibility ellenőrizendő"
  - component: "kubernetes"
    version: "<lab-k8s-minor>"
    state: "supported_minor"
    source: "https://kubernetes.io/docs/"
    source_date: "<ellenőrizendő>"
    fallback: "kubectl version --output=yaml"
    skew_note: "hivatalos version skew policy ellenőrizendő"
  - component: "ingress_controller"
    version: "<lab-ingress-controller>"

    source: "<project-release-page>"
    source_date: "<ellenőrizendő>"

    skew_note: "ne használj master/latest tag-et productionként"
  - component: "gateway_api"

    source: "https://kubernetes.io/docs/"
    source_date: "<ellenőrizendő>"

  - component: "qemu"

  - component: "ansible_core"

  - component: "opentofu"
    version: "<lab-opentofu>"
    state: "stable_release"
    source: "https://opentofu.org/docs/"
    source_date: "<ellenőrizendő>"
    fallback: "tofu version"
    skew_note: "provider constraints ellenőrizendő"
  - component: "helm"
    version: "<lab-helm>"
    state: "supported_with_k8s_minor"
    source: "https://helm.sh/docs/"
    source_date: "<ellenőrizendő>"
    fallback: "helm version"
    skew_note: "Kubernetes támogatási mátrix ellenőrizendő"
  - component: "otel"
    version: "<lab-otel-version>"

    source: "https://opentelemetry.io/docs/"
    source_date: "<ellenőrizendő>"
    fallback: "release notes of the instrumented C++ library"

  - component: "ceph"
    version: "n/a lab baseline"
    state: "dev_only_docs_if_latest"

A mátrix létrehozása után egy egyszerű ellenőrzés kiszűri a kitöltetlen placeholdereket:

# target: lab-vm-01; user: labadmin (UID 1000)
# előfeltétel: ~/lab-support/matrix.yml létezik
if grep -n '<' ~/lab-support/matrix.yml; then
  echo "Hiba: kitöltetlen placeholder maradt a mátrixban." >&2
  exit 1
fi
echo "OK: a mátrix nem tartalmaz placeholder értéket."

A mátrixnak nem ez az egyetlen validációja: a state mező értékeit is kontrollálni kell, például regex segítségével.

58.1.4 Hibák és ellenpróbák

Tünet: kubectl apply -f ingress.yaml hibát ad: no matches for kind "Ingress" in version "extensions/v1beta1".
Hipotézis: A forrásdokumentum egy újabb Kubernetes clusterre szólt, ahol ez az API már removed, vagy a manifest deprecated API-t használ.
Adatgyűjtés: kubectl api-resources --api-group=networking.k8s.io.
Egy változtatás: A manifestet átírjuk networking.k8s.io/v1 Ingressre, és ellenőrizzük a controller saját specifikációját.
Verification: kubectl explain ingress --api-version=networking.k8s.io/v1 és a resource újbóli létrehozása.

Tünet: QEMU indításkor ismeretlen kapcsoló, pedig a dokumentáció szerint létezik.
Hipotézis: A felhasználó a master dokumentációt nézte, nem a distro verzióját.
Adatgyűjtés: qemu-system-x86_64 --version, apt-cache policy qemu-system-x86.
Egy változtatás: A rendszer saját man oldalát vagy a distro release dokumentációját használja.
Verification: A kapcsoló megjelenik a qemu-system-x86_64 --help kimenetben.

Tünet: Ansible playbook indításakor module not found in collection üzenet.
Hipotézis: A collection legújabb verziója nem kompatibilis a lab ansible-core verziójával.
Adatgyűjtés: ansible --version, ansible-galaxy collection list.
Egy változtatás: A requirements.yml-ben rögzített collection verziót a release-hez igazítjuk.
Verification: ansible-playbook --syntax-check playbook.yml.

A mátrixkészítés leggyakoribb hibája, hogy a latest dokumentációt stabil dokumentációnak tekintik. Ez az ellenpróbák egyik tanulsága: ha a mátrixból hiányzik a date és a fallback, az még nem bizonyíték, hanem csak emlékeztető. A dev_only_docs_if_latest állapot nem engedi meg a production decisiont.

58.1.5 Feladatok

  1. Magyarázó: Adott egy lab Ubuntu 24.04 LTS host és egy Ceph latest dokumentációra mutató hivatkozás. Határozza meg, milyen state értéket venne fel a support matrixban, és miért nem elegendő a latest hivatkozás. Legalább egy mondatban térjen ki a fallback módszertanra.

  2. Adminisztrációs: Hozza létre a lab-support-matrix.yml fájlt a lab hoston, legalább három réteggel: OS, Kubernetes, ingress controller. A /etc/os-release, kubectl version és a kontroller Helm chart verziója alapján töltse ki az adatokat. Minden sor tartalmazzon source-t, date-et és fallback-et. A megoldás ne tartalmazzon <...> placeholdert.

  3. Diagnosztikai/failure recovery: Egy auditor észleli, hogy a production playbook egy latest-re mutató QEMU dokumentációt használ. Az Ön feladata a javítás: cserélje a hivatkozást a distro release dokumentációjára, rögzítse a mátrixban a state=distro_release értéket, és validálja a playbookot. Ellenőrizze, hogy a módosítás után ne maradjon latest vagy master hivatkozás a mátrixban.

58.1.6 Megoldások

  1. A Ceph latest dokumentáció fejlesztői állapotot jelölhet, ezért a support matrixban state=dev_only_docs_if_latest értéket vennénk fel. A source mezőbe a Ceph release notes URL-je kerül, a date az ellenőrzés napját rögzíti. A fallback a distro Ceph csomag verziója vagy a stable release notes lenne. Postcondition: a döntés nem hivatkozik latest/dev dokumentációra production state-ként.

  2. Példa parancsokkal:

# target: lab-vm-01; user: labadmin (UID 1000)
# előfeltétel: a lab cluster elérhető, a kubeconfig a ~/.kube/config
cat /etc/os-release | grep '^\(NAME\|VERSION_ID\)='
kubectl version --output=yaml | grep '^  gitVersion:'
kubectl get svc -n ingress-nginx -o jsonpath='{.items[*].metadata.name}' 2>/dev/null || echo "ingress controllert lab scope-ban kell telepíteni"

A YAML fájlban szerepelnie kell a fenti sémának, például:

apiVersion: lab/v1
kind: SupportMatrix
scope: lab-vm-01
generated_at: "2025-XX-XX"
rows:
  - component: "OS"
    version: "Ubuntu Server 24.04 LTS"
    state: "lab_lts_baseline"
    source: "https://ubuntu.com/server/docs/"
    date: "2025-XX-XX"
    fallback: "/etc/os-release"
  - component: "kubernetes"
    version: "<lab-k8s-minor>"
    state: "supported_minor"
    source: "https://kubernetes.io/docs/"
    date: "2025-XX-XX"
    fallback: "kubectl version --output=yaml"
  - component: "ingress_controller"
    version: "<lab-ingress-controller>"
    state: "maintenance? stable? dev-only?"
    source: "<project-release-page>"
    date: "2025-XX-XX"
    fallback: "helm metadata"

Postcondition: grep '<' lab-support-matrix.yml nem ad találatot, minden sorban nem üres a state és date. A source nem latest vagy master.

  1. A javítási lépések:
# target: lab-vm-01; user: labadmin (UID 1000)
# előfeltétel: a playbook a ~/lab-playbooks/qemu-setup.yml
sed -i.bak 's#https://www.qemu.org/docs/master/#https://ubuntu.com/server/docs/#g' ~/lab-playbooks/qemu-setup.yml
grep -n 'qemu.org/docs/master' ~/lab-playbooks/qemu-setup.yml && exit 1 || echo "nincs master hivatkozás"

# a mátrixban a qemu sor módosítása:
sed -i 's/dev_only_docs_if_latest/distro_release/' ~/lab-support/matrix.yml
grep -n 'qemu' ~/lab-support/matrix.yml

Postcondition: a playbookban nincs latest/master hivatkozás; a mátrix qemu sora distro_release állapotot mutat, és a source a distro release dokumentációra mutat.

58.1.7 Rövid összefoglaló

A d286 arra tanít, hogy a verziót és a támogatási állapotot forrással, dátummal és fallbackkel rögzített support matrixban kell kezelni. A stabil kiadást meg kell különböztetni a deprecated, dev-only, experimental és removed állapotoktól. A technológiai térkép különbséget tesz a distro release, a Kubernetes API skew és a fejlesztői dokumentáció között. A mátrix nem statikus: release-váltáskor újra validálni kell. A latest vagy master hivatkozás nem production bizonyíték.

Továbbvitt definíciók: support matrix – forrással és dátummal ellátott verzió- és támogatási táblázat; version skew – engedélyezett verzióeltérés a kapcsolódó komponensek között; dev-only docs – fejlesztői ágat leíró dokumentáció, amely nem alkalmazható automatikusan stabil kiadásra.

58.1.8 Források és ellenőrzési hiányok

Ebben a kérésben nincs webes keresőeszköz, ezért az aktuális verziókat, support dátumokat és hivatalos skew policy számokat nem tekintjük ellenőrzöttnek. A példákban a <...> placeholderek kitöltése a lab release-audit része. A megadott kiindulópontok:

  • Kernel documentation – kiindulópont, nem olvasott bizonyíték.
  • Kubernetes documentation – kiindulópont, nem olvasott bizonyíték.
  • SRE book – fogalmi kiindulópont.
  • RFC editor – specifikációs kiindulópont.
  • Ubuntu Server documentation – kiindulópont, nem olvasott bizonyíték.

Ellenőrzési hiányok: a Kubernetes version skew policy pontos tűréshatárai, a Kubernetes aktuális támogatott minor verziói, az ingress-controller maintenance state, a QEMU és Ceph distro release dokumentációja, az Ansible-core és collection kompatibilitás, az OpenTofu/Helm/OTel támogatott kiadásai, valamint a lab release-ek pontos csomagverziói. Mindezek használat előtt a hivatalos project/distro dokumentációból ellenőrizendők, és a support matrix date mezőjében rögzítendők.
