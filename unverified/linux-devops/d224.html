45.4 Managed database/K8s/serverless operation

45.4.1 Motiváció: miért más a managed szolgáltatás üzemeltetése?

Egy szenior C++ fejlesztő számára a saját hosztolt adatbázis, Kubernetes klaszter vagy ütemező telepítése ismert fogalom, de a cloud managed szolgáltatásoknál a hibák és a felelősségi határok máshová esnek. Ha a PostgreSQL lekérdezés lassul, nem biztos, hogy a mi indexünk hibás: lehet, hogy a cloud provider a háttérben tárolási replikációt futtat, vagy a hálózati proxy limitálja a kapcsolatokat. Ha a serverless függvény első hívása 800 ms, az nem a mi kódunk hibája, hanem a hidegindítási (cold start) mechanizmus következménye. A managed szolgáltatás nem azt jelenti, hogy „nincs több üzemeltetési teendő”, hanem hogy a felelősség áthelyeződik: a mélyebb infrastruktúra a provideré, de a konfiguráció, a kapacitáskorlát, a hálózati integráció, a titokkezelés és az alkalmazásoldali viselkedés nálunk marad. Ezt a szerződést pontosan rögzíteni kell, mert incidensnél ez dönti el, kinek kell cselekednie.

45.4.2 Definíció és működés: control plane, data plane és shared responsibility

Managed service alatt olyan cloud erőforrást értünk, amelyet a provider API-n keresztül hozunk létre, és a provider üzemelteti annak vezérlési síkját (control plane) – például a replikációt, a backup-ütemezést, a frissítéseket, a monitorozó ügynököket –, valamint bizonyos adat síkbeli (data plane) komponenseket, mint a tároló motor, a hálózati load balancer vagy a futtató runtime. Az alkalmazásunk, a sémánk, a query-k, a connection pool, a titkok és a hálózati hozzáférési szabályok viszont a mi felelősségünk maradnak. Ezt hívjuk shared responsibility modell-nek.

A felelősségi határokat a következő táblázat foglalja össze egy tipikus managed adatbázisra, de a logika más managed szolgáltatásokra is analóg:

Réteg Átvett felelősség (provider) Maradó felelősség (customer)
Control plane Szerverek, OS patchelés, motor frissítés, backup orchestration, HA konfiguráció, metrics export API hívások jogosultsága, paramétercsoportok, maintenance window beállítása
Data plane Tároló motor (engine) futtatása, storage réteg, replikáció, snapshot készítés Adatmodell, séma, query teljesítmény, indexek, tranzakciók, connection management
Hálózat VPC integráció, belső proxying, managed endpoint Security group szabályok, VPC/subnet kiválasztása, IAM policy a hálózati hozzáféréshez
Biztonság Titkosítás at rest (alapértelmezett), engine-level access control alapok IAM szerepkörök, secret tárolás/rotáció, SSL/TLS konfiguráció az ügyfél oldalán, parameter-level auth (pl. pg_hba)
Monitoring és incidens Eszközállapot, provider oldali metrikák, storage full, instance health Alkalmazásoldali telemetria, SLI/SLO, alerting a saját metrikákra, kapacitástervezés a mi workloadunkra

A control plane versus data/app ownership tehát a kulcs: amit a provider API-ja elrejt, az az ő dolga, amit a mi kódunk és konfigurációnk befolyásol, az a miénk. Ez a felelősségi mártix a provider dokumentációjából olvasható ki, és minden service-re egyedileg kell elkészíteni.

45.4.3 Kidolgozott példa: managed PostgreSQL létrehozása és operatív limitjei

Tegyük fel, hogy a laborban egy elkülönített sandbox accountot használunk, a provider pedig az általános cloud CLI parancsot biztosítja. A target azonosítása: host=lab-customer-vm, account=lab-account-123, region=eu-sandbox-1. Az alábbi parancs egy managed PostgreSQL adatbázist hoz létre a lab-vpc hálózatban, a lab-db néven, 20 GiB tárhellyel, multi-AZ replikációval és 14 napos backup retentionnel. A konkrét paraméterek, limitek és verziók a provider aktuális dokumentációjában ellenőrizendők; itt oktatási célú, illusztratív értékek szerepelnek.

cloud db create --name lab-db \
  --engine postgres --engine-version 16 \
  --account lab-account-123 \
  --region eu-sandbox-1 \
  --vpc lab-vpc \
  --allocated-storage 20 \
  --backup-retention-period 14 \
  --multi-az \
  --instance-class db.t3.small \
  --master-username lab_app \
  --master-password 'dummy-not-for-production'

A parancs válasza (rövidített, várt JSON):

{
  "DBInstanceIdentifier": "lab-db",
  "DBInstanceStatus": "creating",
  "Engine": "postgres",
  "EngineVersion": "16.1",
  "AllocatedStorage": 20,
  "MultiAZ": true,
  "BackupRetentionPeriod": 14
}

Várható kimenet és ellenőrzés: A létrehozás után a cloud db describe --name lab-db --account lab-account-123 --region eu-sandbox-1 paranccsal le kell kérni a valós állapotot. A postcondition: az adatbázis available státuszban van, a MultiAZ értéke true, a kapcsolati végpont (Endpoint) elérhető a lab VPC-ből, és a BackupRetentionPeriod megegyezik a konfigurációval. Ellenőrzési feltétel: a cloud db describe kimenetében a DBInstanceStatus == "available", és a security group a 5432 portot csak a lab alhálózatból engedi be.

Hibajelenség, ha a paraméterek hibásak: például ha a --backup-retention-period túl nagy, a provider ValidationError hibát ad; ha a --allocated-storage túl kicsi, a működés közben storage full keletkezik, amit a provider metrikája jelez.

45.4.4 Tipikus hibák és ellenpróbák

  1. Kapcsolati limit túllépés
    • Tünet: az alkalmazás FATAL: too many connections hibát kap a managed DB-től.
    • Hipotézis: a connection pool mérete meghaladja az adatbázis max_connections paraméterét, vagy a kapcsolatok számát a provider instance osztály maximalizálja.
    • Adatgyűjtés: cloud db metrics --name lab-db --metric DatabaseConnections, valamint az alkalmazás logjában a hiba időbélyege.
    • Egy változtatás: csökkentjük az alkalmazás connection pool méretét (pl. 100-ról 50-re), és/vagy emeljük az adatbázis max_connections paraméterét egy paramétercsoporton keresztül (ha a provider korlát engedi).
    • Verifikáció: a metrika nem éri el a korlátot, és az alkalmazás hibaaránya nullára csökken.
  2. Verziófrissítési kockázat
    • Tünet: a provider maintenance ablakban major verzió upgrade történt, és az alkalmazás connection timeout hibákat lát.
    • Hipotézis: az upgrade hosszabb ideig tartott, mint a mi timeoutunk, vagy a motor új verziója nem kompatibilis a driverrrel.
    • Adatgyűjtés: a provider event log, az adatbázis uptime és az alkalmazás oldali latency idősor.
    • Javítás: előre beállított maintenance window-t használunk, a frissítést először egy staging replica-n teszteljük, és az alkalmazás timeout-ját a provider által garantált downtime-nál kisebbre állítjuk.
    • Verifikáció: a frissítés után a connection pool újracsatlakozik, és a tranzakciók sikeresek.
  3. Serverless cold start latencia
    • Tünet: egy serverless függvény első hívása 800 ms, a továbbiak 50 ms.
    • Hipotézis: a függvény hideg (nincs meleg instance), és a provider inicializálja a runtime-ot, valamint a mi init kódunk lassú.
    • Adatgyűjtés: a provider Duration és InitDuration metrikái, log.
    • Javítás: optimalizáljuk az init kódot (C++ esetén a statikus inicializáció és a nagy memóriaallokáció kerülése), vagy provisioned concurrency-t állítunk be, ha a provider támogatja.
    • Verifikáció: a p99 latency a meghatározott SLO alá kerül.
  4. Titokkezelési hiba
    • Tünet: az adatbázis jelszava plaintext formában szerepel a repository-ban, és a cloud provider IAM policy tiltja a hardcoded credentialt.
    • Hipotézis: a fejlesztő a --master-password paramétert beégette a parancsba, vagy a secret nem a provider titokkezelőjéből jön.
    • Javítás: a jelszót a cloud secret szolgáltatással tároljuk, és az alkalmazás runtime-ba injektáljuk (pl. environment variable, de a secret managerből).
    • Verifikáció: a kódban nincs titok, és az access log szerint a titok csak az alkalmazás szerepköréből olvasható.
  5. Hálózati függőség hibája
    • Tünet: az alkalmazás nem éri el a managed DB endpointot.
    • Hipotézis: a security group nem engedi be a 5432 portot a lab VPC-ből, vagy a route table nem tartalmazza a provider által publikált endpoint hálózatot.
    • Adatgyűjtés: cloud ec2 describe-security-groups --name lab-db-sg, valamint nc -zv lab-db...cloud 5432 a lab VM-ből.
    • Javítás: a security group inbound szabályát módosítjuk a helyes CIDR-re.
    • Verifikáció: a kapcsolat teszt sikeres, és a query végrehajtható.

45.4.5 Feladatok

  1. Magyarázó feladat: Készíts egy felelősségi táblázatot egy managed Kubernetes szolgáltatásra (pl. EKS/GKE-szerű) a következő dimenziókban: control plane, worker node, pod hálózat, storage, addonok, monitoring. Jelöld, hogy provider vagy customer felelősség, és adj rövid indoklást minden sorhoz.

  2. Adminisztrációs/konfigurációs feladat: Írj egy OpenTofu/Terraform konfigurációt, amely létrehoz egy managed PostgreSQL adatbázist a lab-account-123 fiókban, eu-sandbox-1 régióban, beállítva a backup retention 14 napra, a multi-AZ replikációt, és egy security group-ot, amely csak a lab-vpc 10.0.1.0/24 alhálózatából enged be a 5432 portra. A titkokat ne tedd a kódba, használj provider secret_manager resource-t.

  3. Diagnosztikai/failure/recovery feladat: Adott egy incidens: a lab alkalmazás időnként connection timeout hibákat kap a managed DB felé, és a provider metrikán látható, hogy a DB CPU-ja 90% feletti, de a connection count alacsony. Végezz hipotézisvezérelt diagnosztikát: sorold fel a lehetséges okokat, milyen adatot gyűjtenél, milyen egy változtatást hajtanál végre, és mivel ellenőriznéd a javulást.

45.4.6 Megoldások

  1. Magyarázó feladat megoldása
    A táblázat a managed Kubernetes-re (példa generikus provideri terminológiával, aktuális limitek ellenőrizendők):

    Dimenzió Provider Customer Indoklás
    Control plane (API szerver, etcd, ütemező) Igen Nem A provider üzemelteti és frissíti.
    Worker node (EC2/VM) Részben Igen A node alapszintű OS-jét a provider adja, de a node frissítése, drain-elése és a rá telepített konténer runtime konfiguráció a miénk. Ha managed node group-ot használunk, a provider többet átvállal, de a csomópontok életciklusa még mindig közös.
    Pod hálózat (CNI) Részben Igen A CNI plugint a provider telepíti, de a NetworkPolicy-k és a hálózati szegmentáció konfigurálása a mi felelősségünk.
    Storage (PV/PVC) Részben Igen A StorageClass és a CSI driver a provider integrációja, de a PV-k méretezése, backup policy, reclaim policy a miénk.
    Addonok (DNS, ingress, monitoring) Részben Igen A provider biztosít addon-okat, de a verziófrissítést és a konfigurációt gyakran mi kezeljük vagy koordináljuk.
    Monitoring és naplózás Részben Igen A provider gyűjt control plane metrikákat, de az alkalmazás és a workload telemetria, alerting, dashboard a miénk.

  2. Adminisztrációs/konfigurációs feladat megoldása
    Az alábbi OpenTofu konfiguráció a lab fiókban létrehozza a kért erőforrásokat. A titok a provider secret_manager erőforrásában tárolódik. A kód oktatási célú, a provider és a resource típusok fiktívek; a tényleges szintaxis ellenőrizendő a választott provider dokumentációjában.

    provider "cloud" {
  account = "lab-account-123"
  region  = "eu-sandbox-1"
}

resource "cloud_secret_version" "db_master_password" {
  secret_id = cloud_secret.db_master.id
  secret_string = "dummy-password-generated-by-secret-manager"
}

resource "cloud_db" "lab_db" {
  name       = "lab-db"
  engine     = "postgres"
  version    = "16.1"
  vpc        = "lab-vpc"
  subnet_ids = ["subnet-lab-1", "subnet-lab-2"]
  allocated_storage    = 20
  backup_retention     = 14
  multi_az              = true
  instance_class        = "db.t3.small"
  master_username       = "lab_app"
  master_password = cloud_secret_version.db_master_password.secret_string
}

resource "cloud_security_group" "lab_db_sg" {
  name        = "lab-db-sg"
  vpc         = "lab-vpc"
  description = "Allow PostgreSQL from lab application subnet"

  ingress {
    from_port   = 5432
    to_port     = 5432
    protocol   = "tcp"
    cidr_blocks = ["10.0.1.0/24"]
  }
}

resource "cloud_db_security_group_attachment" "lab_db_sg_attach" {
  db_identifier = cloud_db.lab_db.id
  security_group_id = cloud_security_group.lab_db_sg.id
}

    Postcondition: A terraform apply sikeres lefutása után a DB available státuszú, a backup retention 14 nap, a MultiAZ aktív, és a security group csak a 10.0.1.0/24 hálózatból enged be. A titok nem jelenik meg a state fájlban plaintext (ha a provider titkosítja a state-et).

  3. Diagnosztikai/failure/recovery feladat megoldása

    • Lehetséges okok:
      1. A DB CPU-ja magas, mert a query-k nem hatékonyak (pl. hiányzó index, rossz tervezett join).
      2. A DB instance osztály túl kicsi a munkaterheléshez.
      3. A hálózati proxy vagy a connection pool a saját oldalon lassít.
      4. A provider storage I/O throttle-t alkalmaz.
    • Adatgyűjtés:
      • Provider metrikák: CPUUtilization, DatabaseConnections, FreeableMemory, IOPS, ReadLatency, WriteLatency.
      • Alkalmazás log: hiba időbélyeg, tranzakció időtartam.
      • DB engine oldali statisztika: pg_stat_statements a lassú lekérdezésekre.
    • Hipotézis tesztelés: A CPU magas és a connection count alacsony, tehát nem a kapcsolatszám a szűk keresztmetszet. A leggyakoribb ok a lassú query vagy a túl kevés erőforrás. Amennyiben a query tervezés hibás, a DB CPU terheli, és a driver timeoutba fut.
    • Egy változtatás: Először azonosítjuk a leglassúbb query-t (pg_stat_statements), és hiányzó indexet adunk hozzá, vagy optimalizáljuk a lekérdezést. Ha ez nem oldja meg, akkor skálázzuk az instance osztályt.
    • Verifikáció: A CPUUtilization átlaga 60% alá csökken, az alkalmazás timeout hibáinak aránya nullára esik, és a p99 latency a tranzakciókra az SLO alatt marad.

45.4.7 Rövid összefoglaló

A managed szolgáltatásoknál a provider átvállalja a control plane és bizonyos data plane elemek üzemeltetését, de a felelősség megoszlik: a konfiguráció, az adatmodell, a titkok, a hálózati hozzáférés és az alkalmazásoldali limitációk a fogyasztónál maradnak. A működtetési szerződést minden service-re táblázatban kell rögzíteni. A legfontosabb operatív kockázatok a kapcsolati limit, a verziófrissítés, a serverless cold start, a titokkezelés és a hálózati dependency. A recovery mindig adatvezérelt: provider metrika + alkalmazás log + egy változtatás + verifikáció.

  • Shared responsibility modell: A provider és a fogyasztó közötti felelősségmegosztás a managed szolgáltatás rétegeire.
  • Control plane: A szolgáltatás vezérlési és menedzsment funkciói (API, scheduling, backup, monitoring), amelyeket a provider birtokol.
  • Cold start: Az a latencianövekedés, ami akkor jelentkezik, amikor egy serverless függvénynek nincs meleg instance-a, és a runtime + init kód inicializálása szükséges.
