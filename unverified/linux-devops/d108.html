22.3 strace, ftrace, eBPF és dinamikus megfigyelés

22.3.1 Motiváció

Egy szenior C++ fejlesztő számára a futó processz kívülről gyakran fekete doboz: tudjuk, hogy a program egy adott ponton vár, de nem tudjuk, hogy a read() rendszerhívás (syscall) blokkol-e a diszken, a futex() egy lockon, vagy a connect() a hálózaton. A log és a core dump gyakran már csak a következményt mutatja. A dinamikus megfigyelés (dynamic tracing) ebben a réteghatáron ad bizonyítékot: rögzíti a userspace process által kiadott syscallokat és a kernel belső eseményeit anélkül, hogy a programot újra kellene buildelni. Három eszközcsaládot különítünk el: az strace syscall trace-t, a kernel ftrace infrastruktúráját, valamint az eBPF programozott, alacsony overheadű megfigyelést. Ez a fejezet az eszközök célját, privilege- és verziófeltételeit, valamint a production overhead keretét tanítja. A d107 CPU- és scheduler-profilozásra, a d103 a sandbox és MAC korlátozásokra épít, ezért azokat itt nem ismételjük.

22.3.2 Definíció és működés

22.3.2.1 Syscall tracing: strace

Az strace a ptrace() kernel interfészt használja: a tracer process a trace-elt process minden syscall belépésénél és kilépésénél értesül. A -T opció a syscall időtartamát (latency) is rögzíti, a -e trace= szűrővel csökkenthető a zaj, az -y az FD-khez tartozó fájlnevet dekódolja, a -f pedig a forkolt gyerekeket és szálakat is követi. A fő cél a hibás syscall, az FD-életciklus és a váratlan latency azonosítása, nem a teljesítményprofil. Az strace minden eseménynél megállítja a trace-elt processzt, ezért overheadje nagy, production futás közben csak szűk scope-pal és tervezett ablakban használható.

22.3.2.2 Kernel event tracing: ftrace

Az ftrace a kernel beépített tracing alrendszere. A tracepoint a kernel forráskódban elhelyezett, alacsony költségű horgony, például egy scheduler esemény vagy egy syscall belépés. A kprobe dinamikusan bármely kernelcímen elhelyezett csapda, lefordított kernelben, a /sys/kernel/tracing/kprobe_events interface-en keresztül. A user probe (uprobe) userspace függvényre vagy utasításra illeszthető. Az ftrace a tracefs-en (/sys/kernel/tracing/ vagy /sys/kernel/debug/tracing/) konfigurálható, olvasásra a trace vagy trace_pipe fájl szolgál.

22.3.2.3 eBPF: verifier és attach point

Az eBPF (extended Berkeley Packet Filter) a kernelben futó, JIT-fordított, eseményvezérelt program. A program betöltése előtt a kernel verifier ellenőrzi: a memória-hozzáférés határait, a pointer-aritmetikát, a végtelen ciklus tilalmát, a program méretét és a kernel verziójához tartozó utasításkészletet. Az attach point határozza meg, hogy az eBPF program honnan kap eseményt: tracepoint, kprobe, raw tracepoint, fentry/fexit, perf event, network hook (TC, XDP), socket, cgroup, stb. Az attach point meghatározza a program kontextusát és a megfigyelhető adatokat.

22.3.2.4 bpftrace és BCC

A bpftrace magas szintű, awk-szerű szkriptnyelv eBPF programok gyors írására. A BCC (BPF Compiler Collection) Python/C keretrendszer ugyanerre. Mindkettő a kernel eBPF képességeire épül, ezért a kernelverzió és az eszközrelease kompatibilitása kritikus. Hivatalos toolprofile: a disztribúció stabilized csomagját vagy a projekt verziózott release-ét használjuk, nem a master ágat. A belső programbetöltésnél a bpftrace/BCC feloldja a tracepoint neveket és a kernel struktúráit, ezért ezek a definíciók verziófüggők.

22.3.2.5 Privilege és sensitive payload

Az strace a saját UID-hez tartozó processzt trace-elheti, ha a kernel.yama.ptrace_scope engedi (jellemzően 1: ugyanazon szülő). Más UID trace-eléséhez CAP_SYS_PTRACE kell. Az eBPF betöltéshez kernel 5.8-tól CAP_BPF és CAP_PERFMON elegendő, korábbi kerneleknél CAP_SYS_ADMIN; a nem privilegizált eBPF-et a kernel.unprivileged_bpf_disabled sysctl tilthatja. A sensitive payload a syscall argumentumokban vagy pufferekben található: például a write() bufferben jelszó, token, PII, a read() visszatérő adatban ügyféladat. A trace kimenetét ezért ugyanolyan adatvédelmi kezelés alá kell vonni, mint a production logot; soha ne rögzítsünk nyers read/write puffert, ha a tartalma nem ismert.

22.3.2.6 Production overhead budget

A tracing overhead mindig a módosított kódút gyakoriságának és az eseményenkénti költség szorzata. Az strace minden syscallnál kétszeri context switch-et és stopot okoz, ezért például 20 ezres syscall/s terhelésnél domináns lehet. A tracepoint megvalósítás egy üres függvényhívásnál is olcsóbb, ha a trace ki van kapcsolva, de ha bekapcsolt eseményen szűrő nélkül gyűjtünk, a trace_pipe olvasása és a tárolás torzít. Az eBPF a JIT-nak és a map-alapú aggregációnak köszönhetően általában a legkisebb overheadű, de a program futási ideje és a map mérete itt is mérhető. Production előtt mindig rögzítünk baseline-t és mérjük a tracing nélküli, valamint a tracing melletti latency/throughput különbséget.

22.3.3 Kidolgozott példa

Cél: a lab-svc nevű C++ szolgáltatás egy indításkori fájlműveletnél váratlanul lassú. Hipotézis: egy read() syscall blokkol a diszk I/O-n. A labtarget az labvm01 Ubuntu Server 24.04 LTS, account labuser, UID 1000. A program a /home/labuser/lab-trace/ könyvtárban van, a lab kimenete a saját lab-trace/ alá kerül, nem módosít production állapotot.

22.3.3.1 1. C++ lab program

// /home/labuser/lab-trace/lab-svc.cpp
#include <fstream>
#include <string>
#include <chrono>
#include <thread>

int main() {
    const std::string path = "/home/labuser/lab-trace/data.txt";
    std::ofstream os(path, std::ios::out | std::ios::binary);
    os << "lab-message";
    os.close();

    std::ifstream is(path, std::ios::in | std::ios::binary);
    std::string s;
    is >> s;
    is.close();

    std::this_thread::sleep_for(std::chrono::milliseconds(50));
    return 0;
}

A kód nem tanít C++ szintaxist; a lényeg a syscall adatút: open, write, close, open, read, close.

22.3.3.2 2. strace syscall/latency és FD

# target: labvm01 / account labuser / UID 1000
# privilege: labuser, saját process trace
# előfeltétel: lab-svc lefordítva
cd /home/labuser/lab-trace
strace -f -T -e trace=openat,read,write,close -o strace.out ./lab-svc
cat strace.out

Várható, illusztratív kimenet:

openat(AT_FDCWD, "/home/labuser/lab-trace/data.txt", O_WRONLY|O_CREAT|O_TRUNC, 0666) = 3 <0.000123>
write(3, "lab-message", 11) = 11 <0.000076>
close(3) = 0 <0.000041>
openat(AT_FDCWD, "/home/labuser/lab-trace/data.txt", O_RDONLY) = 3 <0.000118>
read(3, "lab-message", 8192) = 11 <0.000085>
close(3) = 0 <0.000038>

Az FD 3 az első openat visszatérési értékeként jelenik meg, ezt a write és read használja. A <...> zárójel a syscall latency másodpercben. A -e trace= szűrés nélkül a mmap, mprotect, brk, futex, nanosleep is megjelenne. A kimenet a lab saját könyvtárába kerül, és csak labuser olvashatja.

22.3.3.3 3. ftrace tracepoint

# target: labvm01 / account labuser, de a tracefs miatt root szükséges
# privilege: root, vagy tracefs mount és group jogosultság
# előfeltétel: tracefs mountolt; labvm01-en ellenőrizendő: mount | grep tracefs
sudo mount -t tracefs tracefs /sys/kernel/tracing
sudo bash -c 'cd /sys/kernel/tracing; echo 1 > events/syscalls/sys_enter_read/enable; echo 1 > tracing_on'
sudo head -20 /sys/kernel/tracing/trace_pipe
sudo bash -c 'cd /sys/kernel/tracing; echo 0 > events/syscalls/sys_enter_read/enable; echo 0 > tracing_on'

Várható kimeneti sor (illusztratív):

 lab-svc-4211  [001] ...1  1234.567890: sys_enter_read: fd: 0x3, buf: 0x7ffd..., count: 0x2000

Az fd hexadecimális. A trace_pipe olvasásakor a fogyasztó blokkol, ezért a példa csak 20 sort kér. A parancs végén mindkét kapcsolót kikapcsoljuk, ez a rollback.

22.3.3.4 4. eBPF/bpftrace minimális példa

# target: labvm01
# privilege: CAP_BPF + CAP_PERFMON, vagy root; kernel 5.8+ verzió ellenőrizendő
# előfeltétel: bpftrace disztribúció-csomag telepítve, verzió a kernelhez illesztve
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_read { @[comm] = count(); }'

Várható kimenet (illusztratív):

@[lab-svc]: 12
@[sshd]: 4

A program a sys_enter_read tracepointra attachol, processzenként számolja a belépéseket, és az aggregátumot a kilépéskor (Ctrl-C) írja ki. A comm a process neve. A bpftrace a mögöttes eBPF programot a verifiernek küldi; ha a kernel túl régi vagy a tracepoint nem létezik, hibaüzenetet kapunk.

22.3.4 Hibák és ellenpróbák

Túl széles strace production alatt. Ha minden syscallt trace-elünk, a latency mérés torzul, és a process válaszideje megnő. Ellenpróba: először a baseline latency rögzítése tracing nélkül, majd szűrt trace (-e trace=read,write,openat) csak a gyanús folyamatra, rövid ablakban. A -T latency értéket a mért külső latency-vel össze kell hasonlítani.

Sensitive payload kiszivárgása. A strace -s 200 a syscall pufferek tartalmát is kiírja. Ha a buffer jelszót vagy tokent tartalmaz, az a trace fájlba kerül. Ellenpróba: használjunk -s 0-t vagy ne rögzítsünk adatot; a trace kimenetet titkosított labpartícióra tegyük, és a lab végén töröljük. A production trace kimenete soha ne kerüljön megosztott loggyűjtőbe nyers formában.

eBPF verifier hiba. Egy bpftrace szkript például határok nélküli indexelés miatt R2 unbounded memory access hibával bukhat el. Ellenpróba: a hibát a verifier outputból pontos szakaszra azonosítjuk, egyetlen változtatást teszünk (például explicit hossz-ellenőrzés), majd újra betöltjük. A verifier szövege nem a C++ futásidejű hibája, hanem a kernel biztonsági ellenőrzése.

Capability hiánya. Permission denied az eBPF betöltésnél gyakran CAP_BPF vagy CAP_PERFMON hiányát jelzi, nem a szkript hibáját. Ellenpróba: capsh --print-tel ellenőrizzük az aktuális capability-ket, és a parancsot a megfelelő, minimális jogosultságú userrel futtatjuk. A kernel.unprivileged_bpf_disabled=1 a nem privilegizált betöltést tiltja.

ftrace trace_pipe elárasztás. A trace_pipe olvasása folyamatos adatot termel, és ha a fogyasztó nem olvassa elég gyorsan, a kernel dropolja az eseményeket. Ellenpróba: először szűrjünk a set_event vagy a events/.../filter segítségével, és csak rövid, head-del lezárt ablakot olvassunk.

22.3.5 Feladatok

  1. Magyarázó feladat. Az alábbi strace kimenet egy hálózati szolgáltatásnál rögzült. Azonosítsa az FD 4 létrejöttét, és indokolja meg, miért lehet hibás a read(4, ..., 4096) = -1 EAGAIN értelmezése, ha a socket non-blocking volt.
openat(AT_FDCWD, "/run/lab-svc.sock", O_RDWR|O_CREAT, 0600) = 4
write(4, "lab-ping", 8) = 8 <0.000089>
read(4, 0x7ffd12ab, 4096) = -1 EAGAIN (Resource temporarily unavailable)

  1. Adminisztrációs/konfigurációs feladat. Az labvm01 hoston engedélyezze root joggal az ftrace sys_enter_read tracepointját, rögzítsen legfeljebb 10 eseményt a trace_pipe-ból, majd kapcsolja ki a trace-et. Adja meg a parancssort és a rollbacket explicit ellenőrzéssel. A trace kimenet ne tartalmazhasson ügyféladatot.

  2. Diagnosztikai/failure/recovery feladat. A lab-svc frissítése után a read syscallok száma a feltételezés szerint megnőtt. Használjon strace-t szűrt trace-szel a read syscallok számának és latency összegének összehasonlítására a régi és az új binárison. Majd tervezzen production overhead budget szempontjából biztonságosabb eBPF mérést: adja meg a tracepointot, a gyűjtő mapet, a privilege- és verziófeltételt, valamint a baseline mérés szükségességét.

22.3.6 Megoldások

  1. Az FD 4 a openat(..., "/run/lab-svc.sock", ...) = 4 visszatérésből keletkezik. Az EAGAIN nem feltétlenül hiba, hanem non-blocking socketnél a „most nincs adat, próbáld később” jelzés; a programnak a syscall hibakezelésében errno alapján kell különbséget tennie a valódi hiba és az erőforrás átmeneti hiánya között. Postcondition: a tanuló meg tudja különböztetni az FD-hozzárendelést és a non-blocking retry szemantikát.

  2. Parancsok:

# target: labvm01 / root
# privilege: root
sudo mount -t tracefs tracefs /sys/kernel/tracing
sudo bash -c 'cd /sys/kernel/tracing; echo 1 > events/syscalls/sys_enter_read/enable; echo 1 > tracing_on'
sudo head -10 /sys/kernel/tracing/trace_pipe
sudo bash -c 'cd /sys/kernel/tracing; echo 0 > events/syscalls/sys_enter_read/enable; echo 0 > tracing_on'
# ellenőrzés
sudo cat /sys/kernel/tracing/events/syscalls/sys_enter_read/enable
# várt: 0

Rollback: az utolsó két echo 0 kapcsolja ki a trace-et; a mountot le lehet csatolni sudo umount /sys/kernel/tracing ha saját mount volt. Postcondition: a tracepoint engedélyezése 0, a trace_pipe olvasás megszűnt, a kimenetben nincs puffertartalom.

  1. A diagnosztikai összehasonlítás:
# target: labvm01 / labuser
# privilege: labuser, saját process
cd /home/labuser/lab-trace
strace -f -c -e trace=read -o read-count-new.txt ./lab-svc-new
strace -f -c -e trace=read -o read-count-old.txt ./lab-svc-old
cat read-count-new.txt read-count-old.txt

A -c syscall statisztikát ad: hívások száma, összidő, hiba. A két statisztika a hipotézist megerősíti vagy cáfolja. A production eBPF terv: tracepoint syscalls:sys_exit_read, map @read_count = count() és @read_latency = hist(nsecs); a privilégium CAP_BPF + CAP_PERFMON (kernel 5.8+), a verziófeltétel: a disztribúció kernel és a bpftrace release illeszkedik, a tracepoint létezik; baseline mérés: a bpftrace futása nélküli, majd a futó mérés alatti p95 latency rögzítése. Postcondition: a strace mérés bizonyítja a syscall szám vagy latency változást, az eBPF terv rendelkezik privilege, scope, verzió és overhead kontrollal.

22.3.7 Rövid összefoglaló

A dinamikus megfigyelés a syscall és kernel események réteghatárán ad bizonyítékot. Az strace a ptrace()-re épül, FD- és latency-debugra való, de nagy overheadje miatt productionban csak szűk scope-pal használható. Az ftrace tracepoint, kprobe és uprobe kernelbeli horgonyokat biztosít alacsonyabb költséggel. Az eBPF programozott megfigyelést tesz lehetővé: a kernel verifier ellenőrzi a biztonságot, az attach point határozza meg az eseményforrást. bpftrace/BCC ennek magas szintű felülete. Minden trace sensitive payloadot hordozhat, ezért a kimenet adatvédelmi kezelése és a privilege minimalizálás kötelező. Továbbhasznált definíciók: tracepoint – kernelben rögzített, alacsony költségű eseményhorgony; eBPF verifier – kernel biztonsági ellenőrző a betöltés előtt; attach point – az eBPF program eseményforrása.
