9.5 Memória-, swap- és cgroup labor

9.5.1 Motiváció

Egy üzemeltetett Linux szolgáltatásnál a legkellemetlenebb memóriaproblémák ritkán reprodukálhatók a fejlesztői gépen. A host free kimenete még „elég memóriát” mutat, miközben a service belassul, vagy a cgroup OOM killer (out-of-memory killer) leöli a folyamatot. A feladat ilyenkor nem a host egészének kimerítése, hanem az, hogy egy korlátozott, megismételhető laborban megértsük, hogyan számolja el a Linux a memóriát process és cgroup nézetben, mi történik egy túl alacsony MemoryMax limitnél, és milyen bizonyítékokból lehet javítási tervet készíteni. A cél az alábbiakban az, hogy a szenior fejlesztő a C++ allocator és virtual memory hátterét a Linux üzemeltetési modelljéhez kösse anélkül, hogy a hostot veszélyeztetné.

9.5.2 Definíció és működés

A d044 alfejezetben bevezetett cgroup v2 memóriamodell szerint a kernel minden cgroup számára karbantartja a memory.current számlálót: ez az adott cgroupba tartozó processzorok és kernel-struktúrák által jelenleg foglalt, fizikailag lefoglalt memóriát jelenti. A d041 és d042 alfejezetek alapján a virtuális címfoglalás malloc/mmap esetén nem azonnal fizikai lapfoglalás; a lapok demand-zero vagy file-backed módon akkor jönnek létre, amikor a processz címeire először írunk.

A processz nézetben a leggyakrabban használt mutatók:

  • RSS (resident set size): a processzhez tartozó, fizikai RAM-ban lévő lapok, swap nélkül.
  • PSS (proportional set size): a megosztott lapok arányosított része; több processzt is tartalmazó mappingek vizsgálatánál igazságosabb.
  • USS (unique set size): csak az adott processz által privát módon használt lapok.

A cgroup nézet memory.current ettől eltér: tartalmazza az anon (névtelen) lapokat, a file (page cache) lapokat, a kernel stack, slab és socket memóriát is, még akkor is, ha azok nem jelennek meg a processz RSS-ében. Ezért a ps RSS és a cgroup memory.current összehasonlítása fontos diagnosztikai lépés.

A kernel PSI (Pressure Stall Information) felülete a /proc/pressure/memory alatt azt mutatja, hogy a processz(ek) mennyi időt várakoztak memória-visszanyerésre (reclaim) az adott időablakban. A some avg10=... azt jelzi, hogy legalább egy processz stallolt; a full avg10=... azt, hogy minden processz. A PSI ezért jobb „lassulásmérő”, mint a pillanatnyi szabad memória.

A systemd MemoryHigh és MemoryMax propertyket a cgroup v2 memory.high és memory.max írja be. A MemoryHigh egy puha limit, amelyik throttlingot és agresszív reclaimet indít; a MemoryMax kemény felső határ, amelynél a kernel a cgroupon belül OOM killt hajthat végre. A Restart=on-failure és a StartLimitBurst/StartLimitIntervalSec együtt szabályozza, hogy egy OOM miatt elhalt service ne jusson végtelen újraindulási ciklusba.

A C++ allocator szempontjából a std::vector/malloc által visszaadott virtuális terület csak akkor válik RSS-sé, ha írunk bele. Az ilyen foglalásokat a kernel gyakran demand-zero page-ként adja vissza: minden lap ugyanarra a nullás lapra mutat, amíg írás nem éri. Ezért a „memória fogy” állítás csak akkor igaz, ha a mért mutató a memory.current vagy a tényleges RSS, nem a processz virtuális mérete (VSZ, VmSize).

A transparent hugepage (THP) a kernel 2 MiB-os (x86-64) lapokba is összefoghat anon mappingeket; a AnonHugePages az smaps-ban látható. Ez nem csökkenti a memóriaszámítást, de befolyásolja a reclaim és a mérési pontosságot. NUMA esetén a numa_maps/numastat megmutatja, hogy a memória melyik NUMA node-on van; egyetlen node-os laborban ez triviális, de a fogalmi modellt akkor is megfigyelhetjük.

9.5.3 Kidolgozott példa

A labor a labhost1 nevű izolált Ubuntu Server 24.04 LTS labVM-en fut; a parancsokat labuser (UID 1000) adja, a rendszermódosításokhoz sudo van. A laborerőforrások lab- prefixet kapnak; a host memóriáját nem visszük a 80%-os kihasználtság fölé.

Előfeltétel: a g++ telepítése és a systemd cgroup v2 mount ellenőrzése:

# labhost1; labuser (uid=1000)
g++ --version | head -n 1
test "$(stat -fc %T /sys/fs/cgroup/)" = "cgroup2fs" && echo "cgroup v2 OK"

Készítsünk egy rövid, kizárólag a memóriaviselkedést vizsgáló programot, amely paraméterként MiB-ot kap, foglal, érinti a memóriát, majd 30 másodpercig fut. Ez nem új C++ nyelvi oktatás, hanem a Linux memóriamodellhez kötött mérőeszköz:

// lab_mem_alloc.cpp
#include <chrono>
#include <cstdlib>
#include <cstring>
#include <iostream>
#include <thread>
#include <vector>

int main(int argc, char **argv) {
    if (argc != 2) {
        std::cerr << "usage: lab_mem_alloc MIB\n";
        return 2;
    }
    const std::size_t mib = std::stoull(argv[1]);
    std::vector<char> buffer(mib * 1024 * 1024);
    std::memset(buffer.data(), 0x55, buffer.size()); // touch: lapok resident lesznek
    std::this_thread::sleep_for(std::chrono::seconds(30));
    return 0;
}

Fordítás és telepítés:

# labhost1; labuser -> sudo a telepítéshez
g++ -std=c++20 -O2 -Wall -Wextra -o lab_mem_alloc lab_mem_alloc.cpp
sudo install -o root -g root -m 0755 lab_mem_alloc /usr/local/bin/lab_mem_alloc

Indítsuk a programot systemd transient unitban, kemény 128 MiB korláttal; a program viszont 256 MiB-ot próbál foglalni és érinteni. Így a MemoryMax alatt várhatóan OOM kill következik be. A Restart=on-failure a crash loopot is demonstrálja, amit a StartLimitBurst korlátoz:

# labhost1; labuser -> sudo: rendszerszintű systemd-run
sudo systemd-run \
  --unit=labmemtest \
  --property=MemoryHigh=96M \
  --property=MemoryMax=128M \
  --property=MemorySwapMax=0 \
  --property=Restart=on-failure \
  --property=StartLimitIntervalSec=30 \
  --property=StartLimitBurst=3 \
  /usr/local/bin/lab_mem_alloc 256

A foglalás viselkedését külön terminálból figyeljük. A process- és cgroup nézetet egyszerre használjuk:

# labhost1; labuser; csak olvasás
systemctl show labmemtest -p MainPID -p ControlGroup -p MemoryCurrent -p MemoryPeak -p Result
pgrep -f lab_mem_alloc | head -n 1
ps -o pid,rss,vsz,cmd -p "$(pgrep -f lab_mem_alloc | head -n 1)"
grep -E '^(Rss|Pss|AnonHugePages)' /proc/"$(pgrep -f lab_mem_alloc | head -n 1)"/smaps_rollup
grep -E '^anon |^file |^slab ' /sys/fs/cgroup/system.slice/labmemtest.service/memory.stat
cat /proc/pressure/memory

Az első sorban a MainPID még élhet, a MemoryCurrent folyamatosan nő, ahogy a memset ír. Illusztratív közbenső kimenet:

MainPID=11234
ControlGroup=/system.slice/labmemtest.service
MemoryCurrent=67108864
MemoryPeak=67108864
Result=success

A 128 MiB-on a kernel a cgroupban OOM killt hajt végre; a process SIGKILL-t kap, a systemd ezt oom-kill resultként mutatja. A MemoryPeak értéke a limithez közeli, a MainPID egy újraindított processzre vált:

MainPID=11280
ControlGroup=/system.slice/labmemtest.service
MemoryCurrent=0
MemoryPeak=134217728
Result=oom-kill

A naplóban a kernel és a systemd nézet is látható:

# labhost1; labuser; csak olvasás
journalctl -u labmemtest -b --no-pager | tail -n 30
journalctl -k -b --no-pager | grep -i 'Killed process' | tail -n 5

Várható, nem mért, hibajelenséget mutató sorok:

labmemtest.service: A process of this unit has been killed by the OOM killer.
Memory cgroup out of memory: Killed process 11234 (lab_mem_alloc) total-vm:...
systemd[1]: labmemtest.service: Failed with result 'oom-kill'.

A memória-limit és restart politika kapcsolatát a systemctl status labmemtest mutatja. Ha a unit többször elhal, a StartLimitBurst elérése után start-limit-hit állapotba kerül, és nem próbálkozik tovább:

systemd[1]: labmemtest.service: Start request repeated too quickly.
systemd[1]: labmemtest.service: Failed with result 'start-limit-hit'.

A THP/NUMA megfigyeléshez a futó PID-et használjuk, mielőtt a limit elérné:

# labhost1; labuser; csak olvasás; ha a PID él
PID=$(pgrep -f lab_mem_alloc | head -n 1)
cat /sys/kernel/mm/transparent_hugepage/enabled
grep -E '(AnonHugePages|FileHugePages)' /proc/$PID/smaps | head -n 5
cat /proc/$PID/numa_maps | head -n 5
# ha a numactl csomag telepítve van:
numastat -p $PID

Az /sys/kernel/mm/transparent_hugepage/enabled tényleges kimenete a kernelprofil függvénye; a laborban például [madvise] never vagy [always] madvise never lehet. A numa_maps pedig legalább egy NUMA node-hoz rendeli a mappingeket; a labVM gyakran egyetlen node-ot lát.

A labor végén cleanup:

# labhost1; labuser -> sudo
sudo systemctl stop labmemtest.service 2>/dev/null || true
sudo systemctl reset-failed labmemtest.service 2>/dev/null || true
sudo rm /usr/local/bin/lab_mem_alloc
rm -f lab_mem_alloc lab_mem_alloc.cpp

Postcondition: a labmemtest.service nem aktív, nem failed; a lab_mem_alloc bináris nem létezik; a labor egyéb folyamatai és a host memóriaállapota nem károsodtak.

9.5.4 Hibák és ellenpróbák

Tünet: a service OOM killt kap, de a free -h sok szabad memóriát mutat.
Hipotézis: a MemoryMax cgroup limit alacsony, nem a host memória fogyott el.
Adatgyűjtés: systemctl show labmemtest -p MemoryMax, journalctl -k | grep 'Memory cgroup', cat /sys/fs/cgroup/system.slice/labmemtest.service/memory.max.
Egy változtatás: növeld a MemoryMax értéket a tényleges munkakészlet fölé, vagy csökkentsd a program által foglalt MiB-ot.
Verification: a process 30 másodpercig fut, Result=success, MemoryPeak a limit alatt marad.

Tünet: a malloc/vector hívás sikeres, mégis OOM kill jön később.
Hipotézis: a Linux overcommit miatt a vector kontraktor csak virtuális címet foglal; a lapok a memset írásnál jönnek létre, és ott ütköznek a cgroup limitbe.
Adatgyűjtés: cat /proc/sys/vm/overcommit_memory, journalctl -k.
Javítás: ne a vector visszatérését tekintsd sikernek; a tényleges lapérintést is mérni kell. A tervezésnél a MemoryHigh/MemoryMax headroomot a peak working setre kell igazítani.

Tünet: a service ismételten újraindul, majd start-limit-hit állapotba kerül.
Hipotézis: a Restart=on-failure OOM után is újraindul, de a túl alacsony limit miatt mindig újra elhal.
Adatgyűjtés: systemctl status labmemtest, journalctl -u labmemtest -b.
Javítás: változtass egyszerre egy dolgot: emeld a MemoryMax-ot a munkakészlet fölé, és systemctl reset-failed labmemtest.service; ne kapcsold ki globálisan a cgroup limitet.

Tünet: a process RSS nagyon alacsony, de a cgroup memory.current magas.
Hipotézis: a memory.current tartalmazza a page cache, slab és kernel stack memóriát, ami az RSS-ben nem jelenik meg.
Adatgyűjtés: grep -E '^anon |^file |^slab ' /sys/fs/cgroup/.../memory.stat.
Következmény: a service-es diagnosztikában ne csak a ps RSS-t figyeld; a cgroup memory.current az operatív számláló.

A THP/NUMA megfigyelésnél gyakori hiba, hogy a mérést a service rövid élettartama miatt kihagyjuk. Érdemes a mérést a MemoryHigh alatt, a memset lefutása után, de a 30 másodperces sleep közben végezni. A másik hiba, hogy a MemoryCurrent=0 értékből arra következtetünk, hogy nincs memória fogy; valójában a PID már lecserélődött OOM után.

9.5.5 Feladatok

9.5.5.1 1. Magyarázó feladat

Futtasd a lab_mem_alloc programot korlát nélkül systemd-run-ben, 128 MiB-tal, majd 256 MiB-tal is. Minden futásnál rögzítsd a process RSS-t (ps), a cgroup memory.current értéket és a smaps_rollup Rss/Pss/AnonHugePages értékeket. Magyarázd el, miért lehet a memory.current nagyobb a process RSS-nél, és miért nem elegendő a std::vector méretéből következtetni a fizikai memóriafoglalásra.

9.5.5.2 2. Adminisztrációs/konfigurációs feladat

Készíts tartós systemd unitot labmemtest-svc.service néven, amely a lab_mem_alloc programot 192 MiB paraméterrel futtatja. Állíts be MemoryHigh=160M, MemoryMax=256M, MemorySwapMax=0, Restart=on-failure, StartLimitIntervalSec=30 és StartLimitBurst=3 értékeket. Indítsd el, és ellenőrizd, hogy a service 30 másodpercig fut, nem OOM-ol, és a memory.current a MemoryHigh alatt stabilizálódik. Írd le a pull request/runbook szintű állapotot: desired state, observed state, várt postcondition.

9.5.5.3 3. Diagnosztikai/failure/recovery feladat

A laborban a labmemtest service OOM-killt szenvedett, majd start-limit-hit állapotba került. Gyűjts bizonyítékot journalctl, systemctl show, PSI, smaps és numa_maps segítségével. Készíts root-cause alapú javítási tervet: döntsd el, hogy a MemoryMax növelése vagy a program munkakészletének csökkentése indokolt. Módosíts pontosan egy változót, indítsd újra a service-t, és ellenőrizd, hogy a 30 másodpercnyi futás OOM nélkül teljesül.

9.5.6 Megoldások

9.5.6.1 1. Megoldás

A korlát nélküli futtatáshoz:

# labhost1; labuser -> sudo
sudo systemd-run --unit=labmemtest-open --property=MemoryMax=infinity /usr/local/bin/lab_mem_alloc 128
sleep 5
systemctl show labmemtest-open -p MainPID -p ControlGroup -p MemoryCurrent -p MemoryPeak
PID=$(pgrep -f lab_mem_alloc | head -n 1)
ps -o pid,rss,vsz,cmd -p "$PID"
grep -E '^(Rss|Pss|AnonHugePages)' /proc/$PID/smaps_rollup
grep -E '^anon |^file |^slab ' /sys/fs/cgroup/system.slice/labmemtest-open.service/memory.stat
# cleanup
sudo systemctl stop labmemtest-open.service
sudo systemctl reset-failed labmemtest-open.service

A 128 MiB toucholt lap után az RSS és a cgroup memory.current közelít egymáshoz, de a cgroup tartalmazhat néhány MiB kernel stacket/slab-et is. A 256 MiB-os változatnál a memory.current ~256 MiB körül lesz, a PSS/RSS szintén. A magyarázat: a memory.current a cgroup teljes memóriaéletciklusát tartalmazza; a process RSS csak a processhez rendelt anon/file resident lapokat; a shared lapok PSS körül látszanak. A std::vector::resize nem garantál fizikai foglalást addig, amíg a memset nem ír a lapokra. Postcondition: a unit leállt, a bináris megmarad(t), de a labor clean.

9.5.6.2 2. Megoldás

A tartós unit:

# /etc/systemd/system/labmemtest-svc.service
# labhost1; labuser -> sudo a telepítéshez
[Unit]
Description=Lab memory-limited service

[Service]
ExecStart=/usr/local/bin/lab_mem_alloc 192
MemoryHigh=160M
MemoryMax=256M
MemorySwapMax=0
Restart=on-failure
StartLimitIntervalSec=30
StartLimitBurst=3

[Install]
WantedBy=multi-user.target

Telepítés és indítás:

# labhost1; labuser -> sudo
sudo install -o root -g root -m 0755 lab_mem_alloc /usr/local/bin/lab_mem_alloc
sudo cp labmemtest-svc.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl start labmemtest-svc
sleep 5
systemctl status --no-pager labmemtest-svc
systemctl show labmemtest-svc -p MainPID -p MemoryCurrent -p MemoryPeak -p Result
grep -E '^anon |^file |^slab ' /sys/fs/cgroup/system.slice/labmemtest-svc.service/memory.stat

Desired state: aktív service, Result=success, MemoryCurrent 192 MiB körül, MemoryMax 256 MiB. Observed state: a systemd unit active (running), MainPID stabil, MemoryCurrent < MemoryPeak <= MemoryHigh. A postcondition: a service 30 másodperc után kilépett, a unit inactive (dead); a labor nem hagy futó processzt. A rollback: sudo systemctl stop labmemtest-svc, sudo rm /etc/systemd/system/labmemtest-svc.service, sudo systemctl daemon-reload.

9.5.6.3 3. Megoldás

Diagnosztikai lépések:

# labhost1; labuser; csak olvasás
systemctl status --no-pager labmemtest
journalctl -u labmemtest -b --no-pager | grep -E 'OOM|oom-kill|start-limit'
journalctl -k -b --no-pager | grep -i 'Killed process' | tail -n 5
cat /proc/pressure/memory

A mért/kimutatott MemoryPeak az illusztratív limit 128 MiB, a program 256 MiB-ot igényelt; tehát a hiba oka a limit és a working set eltérése. A javítási terv: emeljük a MemoryMax-ot 256 MiB-ról 320 MiB-ra, és a MemoryHigh-t 224 MiB-ra; a programot 256 MiB-tal futtatjuk. Egyszerre csak egy változót módosítunk: a limitet. A rollback: a régi unit file visszaállítása.

# labhost1; labuser -> sudo
sudo systemctl stop labmemtest.service 2>/dev/null || true
sudo systemctl reset-failed labmemtest.service
sudo sed -i 's/MemoryMax=128M/MemoryMax=320M/' /run/systemd/transient/labmemtest.service.d/ 2>/dev/null || true
# tartós unitnál a unit file szerkesztése

Ha transient unit a példából, akkor a korrekt megoldás tartós unit visszaállítása, majd systemctl start. Ellenőrzés:

sudo systemctl start labmemtest-svc
sleep 5
systemctl show labmemtest-svc -p MainPID -p MemoryCurrent -p MemoryPeak -p Result
journalctl -u labmemtest-svc -b --no-pager | tail -n 20

Várható: a service active (running), Result=success, MemoryPeak ~256 MiB, MemoryCurrent 256 MiB alatt. A PSI some értéke a foglalás alatt emelkedhet, de a 30 másodperces futás után visszaesik. Postcondition: OOM nem következik be, a start-limit feloldódott, a service újra rendesen elindítható.

9.5.7 Rövid összefoglaló

A memóriaüzemeltetésben a processz RSS és a cgroup memory.current más kérdésre válaszol: az RSS az adott processz resident lapjait, a cgroup a teljes memóriaélettér számlálóját mutatja. A MemoryMax a cgroup v2 kemény limitje, a MemoryHigh puha throttling; a Restart=on-failure és StartLimitBurst együttesen kezeli a crash loopot. A labor a lab_mem_alloc C++ programmal, systemd-run/unit korlátokkal és smaps/PSI/NUMA megfigyeléssel bizonyítja, hogy a mallocolt memória csak lapérintés után válik residentté, és hogy a túl alacsony limit OOM killhez, nem a host kimerüléséhez vezet. A javítási terv mindig egy változóra koncentráljon: emeljük a limitet, vagy csökkentsük a munkakészletet, és mérjük a cgroup MemoryPeak-ot.

Továbbhasznált definíciók: RSS a processhez tartozó fizikai resident lapok; memory.current a cgroup aktuális, fizikailag foglalt memória mennyisége; OOM kill a kernel által a cgroup memory.max túllépésekor végrehajtott processz leállítás.
