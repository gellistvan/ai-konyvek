25.3 Linux bridge, OVS és virtuális L2 hálózat

25.3.1 Miért nem elég „létrehozni egy bridge-et”?

Virtuális gépek vagy konténerek összekapcsolásakor két külön feladat jelenik meg: Ethernet-keretek továbbítása a végpontok között, illetve a Linux rendszer saját IP-elérhetősége. A kettő összekeverése olyan hibákat okozhat, amelyeknél a végpontok kommunikálnak egymással, de a host nem érhető el — vagy éppen fordítva.

A hálózati híd (bridge) második rétegbeli továbbító: portjaira érkező Ethernet-kereteket továbbít a megfelelő portokra. A Linux bridge egyben hálózati interfészként is megjelenik. Ez az interfész biztosítja a helyi hálózati verem kapcsolódását a híddal összekötött Ethernet-tartományhoz.

A bridge működéséhez nem kell IP-cím. IP-címet akkor rendelünk hozzá, ha maga a Linux rendszer is IP-végpont legyen ezen a hálózaton.

Az alábbi labor a VLAN-tagolás ismeretére épít. Nem használ fizikai uplinket, így a VM menedzsmenthálózatát nem módosítja.

25.3.2 A bridge adatútja és állapota

A továbbítási adatbázis (forwarding database, FDB) a cél-MAC-címet kimeneti porthoz rendeli. VLAN-szűrés mellett a VLAN-azonosító is része a keresésnek: ugyanaz a MAC-cím különböző VLAN-okban külön bejegyzéssel szerepelhet.

A Linux bridge egyszerűsített adatútja:

  1. A keret megérkezik egy bridge-porton.
  2. A bridge ellenőrzi a portállapotot és a VLAN-besorolást. Címkézetlen keretnél a port PVID-je számít.
  3. Engedélyezett tanulás esetén a forrás-MAC-címből frissíti az FDB-t.
  4. A cél-MAC-cím és a VLAN alapján választ továbbítási irányt.
  5. Ismert unicast cél esetén a kiválasztott portra továbbít; ismeretlen unicast és broadcast esetén rendszerint a VLAN többi megfelelő állapotú portjára szór.
  6. A kimeneti port VLAN-beállítása szerint megtartja vagy eltávolítja a címkét.

Ez egyszerűsített modell: a multicast-kezelés, a portonkénti elárasztási beállítások, a fenntartott vezérlőcímek és a csomagszűrés módosíthatják az eredményt.

A helyi MAC-címre küldött keret nem feltétlenül egy másik portra megy: a bridge a helyi hálózati veremnek is átadhatja. Ezért kell külön kezelni:

  • a bridge-portokat, amelyek kereteket hoznak és visznek;
  • a bridge-interfészt, amely a helyi IP-végpont kapcsolódási pontja.

A bridge-hez kapcsolt portokra általában nem konfigurálunk IP-címet. A host IP-címe a bridge-interfészre kerül. A porton hagyott korábbi cím zavaró útvonalakat és ARP-viselkedést eredményezhet; attól, hogy valamelyik próba működik, a konfiguráció még nem helyes.

25.3.2.1 Milyen eszköz lehet bridge-port?

Eszköz Szerepe
Fizikai Ethernet-interfész Kapcsolat egy külső Ethernet-hálózathoz
Virtuális Ethernet-pár egyik vége (veth) A pár másik végével Ethernet-kereteket cserél; a két vég külön hálózati névtérben is lehet
TAP-interfész (tap) Ethernet-kereteket közvetít a kernel és egy felhasználói program, például virtuálisgép-monitor között

A veth pár nem önmagában switch: két összekötött interfész. A TAP pedig nem automatikusan bridge vagy router. A későbbi VM- és konténerhálózat ezekből az építőelemekből áll össze.

25.3.2.2 Bridge, router és NAT

Művelet Döntés alapja IP-kezelés
Bridge-továbbítás Cél-MAC és VLAN Normál L2-továbbításkor nem csökkenti az IP TTL-jét
Útválasztás (routing) Cél-IP és útválasztási szabályok IP-hálózatok között továbbít; IPv4-nél csökkenti a TTL-t
Hálózati címfordítás (NAT) Címfordítási szabály és gyakran kapcsolatállapot IP-címet, esetenként portot ír át

A NAT nem a bridge szinonimája, és nem szükséges minden útválasztáshoz. Ha a host bridge-interfészén IP-cím van, attól még nem lesz bekapcsolva az IP-továbbítás.

25.3.3 Kidolgozott labor: két végpont és egy helyi hostcím

Célgép: lab-l2, izolált Ubuntu Server 24.04 LTS amd64 VM.
Fiók és jogosultság: a laborhoz engedélyezett adminisztrátor, a parancsok root shellben, UID 0-val.
Előfeltétel: iproute2, iputils-ping és procps telepítve; VM-konzol rendelkezésre áll.

A hálózati névtér (network namespace) saját interfész-, útvonal- és szomszédtáblát biztosít. Itt három ilyen névteret használunk; ezek nem külön kernelek és nem külön VM-ek. Az ip -n NÉV az adott névtérben konfigurál, az ip netns exec NÉV ott indít parancsot.

Objektum Interfész és kapcsolat IPv4 Szerep
lab-a névtér lab-ea ↔︎ lab-pa 10.123.20.10/24 A végpont
lab-sw névtér lab-pa, a lab-br0 portja Nincs konfigurált IPv4 VLAN 20 access port
lab-sw névtér lab-pb, a lab-br0 portja Nincs konfigurált IPv4 VLAN 20 access port
lab-b névtér lab-eb ↔︎ lab-pb 10.123.20.20/24 B végpont
lab-sw névtér lab-br0 10.123.20.1/24 Helyi hostvégpont

A lab-sw névtér képviseli a kapcsolóként is működő Linux host hálózati vermét. Nem kapcsolódik a VM alapértelmezett hálózati névteréhez.

Laborállapot-szerződés:

  • Tulajdonos és élettartam: a laborozó; az adott munkamenet.
  • Bemenet: az alábbi parancssor és címterv.
  • Kívánt állapot: mindhárom IP-végpont elérhető ugyanabban a VLAN-ban; nincs külső kapcsolat vagy IP-routing.
  • Megfigyelt állapot: interfész-, VLAN-, FDB-, útvonal- és ping-kimenetek.
  • Konfigurációforrás: az alábbi parancssor; nem Netplan vagy más hálózatkezelő.
  • Tárolt állapot: nincs perzisztens hálózati konfiguráció; az állapot a kernelben él.
  • Visszaállítás és cleanup: kizárólag a három név szerint felsorolt névtér törlése.

25.3.3.1 Előellenőrzés

Minden további parancs célja a lab-l2, UID 0. Ha bármelyik létrehozási lépés hibázik, állj meg; ne folytasd feltételezett állapotból.

# lab-l2; root shell; UID 0
test "$(hostname -s)" = lab-l2 || exit 1
test "$(id -u)" -eq 0 || exit 1

uname -r
dpkg-query -W iproute2 iputils-ping procps
ip -4 route show table all
ip netns list

for ns in lab-sw lab-a lab-b; do
    if ip netns list | awk '{print $1}' | grep -Fxq "$ns"; then
        printf 'Már létező névtér: %s\n' "$ns"
        exit 1
    fi
done

for dev in lab-pa lab-ea lab-pb lab-eb; do
    if ip link show dev "$dev" >/dev/null 2>&1; then
        printf 'Már létező interfész: %s\n' "$dev"
        exit 1
    fi
done

A kiírt verziókat rögzítsd a laborjegyzőkönyvben. A 10.123.20.0/24 tartomány használatát egyeztesd a laborinventárral. Ha ütközik más laborhálózattal, válassz másik privát /24-et, és minden címet következetesen módosíts. A névtérizoláció itt megakadályozza a közvetlen route-ütközést, de a címütközés egy későbbi összekapcsoláskor hibává válhat.

25.3.3.2 Létrehozás

# lab-l2; UID 0; kizárólag az előellenőrzött laborobjektumok
ip netns add lab-sw
ip netns add lab-a
ip netns add lab-b

for ns in lab-sw lab-a lab-b; do
    ip -n "$ns" link set dev lo up
done

ip link add lab-pa type veth peer name lab-ea
ip link set lab-pa netns lab-sw
ip link set lab-ea netns lab-a

ip link add lab-pb type veth peer name lab-eb
ip link set lab-pb netns lab-sw
ip link set lab-eb netns lab-b

ip -n lab-sw link add name lab-br0 type bridge \
    vlan_filtering 1 vlan_default_pvid 0 stp_state 0
ip -n lab-sw link set dev lab-br0 address 02:00:00:12:30:01

ip -n lab-sw link set dev lab-pa master lab-br0
ip -n lab-sw link set dev lab-pb master lab-br0

ip netns exec lab-sw bridge vlan add \
    dev lab-pa vid 20 pvid untagged
ip netns exec lab-sw bridge vlan add \
    dev lab-pb vid 20 pvid untagged
ip netns exec lab-sw bridge vlan add \
    dev lab-br0 vid 20 pvid untagged self

ip -n lab-sw addr add 10.123.20.1/24 dev lab-br0
ip netns exec lab-sw sysctl -w net.ipv4.ip_forward=0

ip -n lab-a link set dev lab-ea address 02:00:00:12:30:0a
ip -n lab-b link set dev lab-eb address 02:00:00:12:30:0b
ip -n lab-a addr add 10.123.20.10/24 dev lab-ea
ip -n lab-b addr add 10.123.20.20/24 dev lab-eb

ip -n lab-sw link set dev lab-br0 up
ip -n lab-sw link set dev lab-pa up
ip -n lab-sw link set dev lab-pb up
ip -n lab-a link set dev lab-ea up
ip -n lab-b link set dev lab-eb up

A vlan_default_pvid 0 elkerüli az automatikus alapértelmezett VLAN-tagságot: minden szükséges besorolás explicit.

A portokon a pvid untagged a címkézetlen bemenet VLAN 20-ba sorolását és a címkézetlen kimenetet adja. A bridge-eszközön a self a helyi bridge-végpont VLAN-tagságát állítja, nem a többi portét. Ez szükséges ahhoz, hogy a közvetlenül a lab-br0 interfészre tett IP-cím a VLAN 20-ban működjön.

Az STP itt tudatosan kikapcsolt: a két végponttal alkotott topológiában nincs hurok. Ezt ne másold át redundáns fizikai topológiára; annak szabályait az STP, loop és LACP/bonding tárgyalja.

25.3.3.3 Ellenőrzés és várt eredmény

# lab-l2; UID 0; olvasás és forgalmi próba
ip -n lab-sw -d link show dev lab-br0
ip netns exec lab-sw bridge link show
ip netns exec lab-sw bridge vlan show
ip -n lab-sw -4 addr show
ip -n lab-a -4 route show

ip netns exec lab-a ping -n -c 3 -W 1 10.123.20.20
ip netns exec lab-a ping -n -c 3 -W 1 10.123.20.1
ip netns exec lab-sw ping -n -c 3 -W 1 10.123.20.20

ip netns exec lab-sw bridge fdb show br lab-br0

Várt, nem ténylegesen mért eredmény:

Ellenőrzés Elvárt állapot
Bridge-portok lab-pa és lab-pb: master lab-br0, state forwarding
VLAN-tábla Mindkét port és lab-br0: VLAN 20, PVID, Egress Untagged
Hostcím 10.123.20.1/24 kizárólag a lab-br0 interfészen
A útvonala Közvetlen, scope link útvonal a /24 hálózatra; nincs szükség alapértelmezett átjáróra
Ping-próbák Mindhárom próba sikeres
FDB forgalom után A MAC-címe lab-pa, B MAC-címe lab-pb, VLAN 20

Az FDB-ben helyi és állandó bejegyzések is látszanak; nem minden sor tanult végpont.

A két adatút eltér:

  • A → B: lab-ea → lab-pa → FDB/VLAN-döntés → lab-pb → lab-eb.
  • A → helyi host: lab-ea → lab-pa → bridge helyi átadás → lab-br0 IPv4-verme.

A → B esetén a 10.123.20.1 nem átjáró, és nem vesz részt IP-routerként a továbbításban.

25.3.4 Hibakeresés: mit bizonyít az FDB?

Az FDB-bejegyzés azt mutatja, hogy a bridge egy forrás-MAC-címet az adott port felől megtanult. Nem bizonyítja, hogy a cél IP-verme válaszol, a visszaút működik vagy a célalkalmazás elérhető.

Szándékosan távolítsuk el B portjának VLAN-tagságát:

# lab-l2; UID 0; hibainjektálás kizárólag a lab-pb porton
ip netns exec lab-sw bridge vlan del dev lab-pb vid 20

ip netns exec lab-a ping -n -c 3 -W 1 10.123.20.20
ip netns exec lab-a ping -n -c 3 -W 1 10.123.20.1

ip netns exec lab-sw bridge link show
ip netns exec lab-sw bridge vlan show
ip netns exec lab-sw bridge fdb show br lab-br0
ip -n lab-sw -s link show dev lab-pb
ip -n lab-a neigh show dev lab-ea

Várt tünet: A → B sikertelen, A → helyi host továbbra is sikeres. Az interfész közben maradhat UP, és a bridge-port forwarding.

Ez ellenpróba arra a téves hipotézisre, hogy minden működő link automatikusan továbbítja az adott VLAN forgalmát. A korábban megtanult szomszéd- vagy FDB-bejegyzések állapota nem helyettesíti a VLAN-tábla ellenőrzését.

Egyetlen javítás:

# lab-l2; UID 0; rollback és verification
ip netns exec lab-sw bridge vlan add \
    dev lab-pb vid 20 pvid untagged

ip netns exec lab-a ping -n -c 3 -W 1 10.123.20.20
ip netns exec lab-sw bridge vlan show
ip netns exec lab-sw bridge fdb show br lab-br0

További jellegzetes hibák:

Tünet Hipotézis és ellenpróba
A és B kommunikál, a host nem Ellenőrizd a lab-br0 IP-címét és self VLAN-tagságát
Port UP, mégsem továbbít Ellenőrizd a bridge-tagságot, forwarding állapotot és VLAN-tagságot
Nem látszik dinamikus FDB-bejegyzés Generálj forgalmat a végpont felől; ellenőrizd a tanulást és az öregedést
L2-állapot helyes, ping mégsem működik Vizsgáld az IP-címet, útvonalat, szomszédállapotot és az adott névtér szűrési szabályait

Ne globális tűzfalkikapcsolással próbáld „megjavítani” a hidat. A szűrés külön réteg: előbb azonosítsd a ténylegesen érintett szabályt és adatútvonalat.

25.3.5 Open vSwitch mint alternatíva

Az Open vSwitch (OVS) programozható virtuális kapcsoló. Egyszerű L2-kapcsolásra is alkalmas, de összetettebb szabályozást, vezérlőszoftverhez kapcsolódást és overlay-adatutakat is támogathat.

Linux bridge OVS-fogalom
Bridge-eszköz OVS bridge és hozzá tartozó adatút
Bridge-port OVS Port; ez egy vagy több Interface objektumot foghat össze
Kernelben élő bridge-konfiguráció OVSDB-ben tárolt konfiguráció, amelyet vezérlőfolyamatok alkalmaznak
FDB-alapú kapcsolás A szabályoktól függően hagyományos MAC-tanulásos kapcsolás vagy explicit flow-feldolgozás

Az OVS-ben a konfigurációs adatbázis, az alkalmazott adatútszabályok és a tanult MAC-állapot külön vizsgálati pont. Az OVSDB-be írt kívánt konfiguráció önmagában nem bizonyítja a működő adatutat.

Az OpenFlow NORMAL művelete hagyományos kapcsolási feldolgozást kér; más szabályok ettől eltérő viselkedést adhatnak. Külső OpenFlow-controller nem minden OVS-telepítéshez szükséges.

A host IP-végpontját OVS-nél tipikusan belső (internal) interfész képviseli, nem a kapcsolóba bevont fizikai uplink. A Linux bridge parancsait nem alkalmazzuk automatikusan OVS-portokra. A konkrét OVS-csomag, adatút-implementáció és kernelkompatibilitás külön verzióellenőrzést igényel.

25.3.6 Feladatok

  1. Magyarázó: Miért működhet A → B akkor is, ha a lab-br0 nem rendelkezik IP-címmel? Melyik cím alapján tanul, és melyik alapján továbbít a bridge?
  2. Adminisztrációs: Távolítsd el kizárólag a bridge IPv4-címét. Igazold, hogy A → B működik, a hostcím viszont nem érhető el. Ezután állítsd vissza.
  3. Diagnosztikai: Állítsd le a lab-pb portot. A link-, VLAN- és FDB-állapotból különítsd el ezt a hibát a korábbi VLAN-tagsági hibától, majd állítsd helyre.

25.3.7 Megoldások

25.3.7.1 1. A kapcsolás nem igényel host-IP-t

A bridge a bejövő keret forrás-MAC-címéből tanul, és cél-MAC plusz VLAN alapján továbbít. A és B ugyanabban az IP-alhálózatban közvetlenül keresik egymást; nem a hostot használják átjáróként.

Postcondition: a magyarázat különválasztja a bridge továbbítási szerepét a helyi IP-veremtől.

25.3.7.2 2. A helyi végpont ideiglenes eltávolítása

# lab-l2; UID 0; csak a labor bridge-címe változik
ip -n lab-sw addr del 10.123.20.1/24 dev lab-br0
ip netns exec lab-a ping -n -c 3 -W 1 10.123.20.20
ip netns exec lab-a ping -n -c 3 -W 1 10.123.20.1

# Rollback
ip -n lab-sw addr add 10.123.20.1/24 dev lab-br0
ip netns exec lab-a ping -n -c 3 -W 1 10.123.20.1

A hostcím eltávolítása nem szünteti meg a portok közötti L2-adatutat.

Postcondition: a cím visszaállt, A → B és A → host sikeres.

25.3.7.3 3. Linkhiba és VLAN-hiba elkülönítése

# lab-l2; UID 0
ip -n lab-sw link set dev lab-pb down
ip netns exec lab-a ping -n -c 3 -W 1 10.123.20.20
ip netns exec lab-sw bridge link show
ip netns exec lab-sw bridge vlan show
ip netns exec lab-sw bridge fdb show br lab-br0

# Rollback és ellenőrzés
ip -n lab-sw link set dev lab-pb up
ip netns exec lab-a ping -n -c 3 -W 1 10.123.20.20
ip netns exec lab-sw bridge link show

A VLAN-tagság megmarad, de a port nem továbbító állapotú. A dinamikus FDB változása másodlagos bizonyíték, nem önmagában a gyökérok.

Postcondition: lab-pb ismét forwarding, VLAN 20 tagsága helyes, A → B sikeres.

25.3.7.4 Laborlezárás

Ne maradjon háttérfolyamat a névterekben. Az alábbi első három parancs várt kimenete üres; nem üres eredménynél előbb azonosítsd és állítsd le a saját laborfolyamatot.

# lab-l2; UID 0; kizárólag a labor saját névterei
ip netns pids lab-a
ip netns pids lab-b
ip netns pids lab-sw

ip netns del lab-a
ip netns del lab-b
ip netns del lab-sw

ip netns list

A folyamatmentes névterek megszűnésével a bennük létrehozott virtuális eszközök is megszűnnek. Ellenőrizd, hogy egyik labor-névtér sem szerepel a listában.

25.3.8 Rövid összefoglaló

A Linux bridge portok között továbbít Ethernet-kereteket, miközben saját interfésze a helyi hálózati verem kapcsolódási pontja. A továbbításhoz nem kell IP-cím; a host eléréséhez igen. VLAN-szűrésnél a porttagság és a helyi bridge-végpont tagsága külön ellenőrzendő. Hibakereséskor a linkállapotot, a bridge-port állapotát, a VLAN-táblát, az FDB-t és az IP-szomszédállapotot együtt vizsgáljuk. Egy sikeres ping vagy egyetlen FDB-bejegyzés csak részleges bizonyíték. Az OVS más konfigurációs és adatútmodellel ad virtuális kapcsolást; nem teszi szükségtelenné ugyanezeket a réteghatár-ellenőrzéseket.

Továbbhasznált definíciók:

  • Bridge-port: a kapcsoló továbbítási adatútjába bevont interfész.
  • FDB: MAC-címet és VLAN-t továbbítási porthoz rendelő adatbázis.
  • Helyi bridge-végpont: a host hálózati vermének kapcsolódása a bridge-hez.
