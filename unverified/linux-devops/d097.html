20.2 Fájlbackup, restic/borg és repository lifecycle

20.2.1 Motiváció

Egy C++ projekt gyakran nem csak a Git repositoryból áll. A build artefaktumok, előre generált adatbázisok, konfigurációs titkok nélküli állapotfájlok, benchmark bemenetek és a fejlesztői környezet is elveszhet. Az rsync -a --delete egyirányú tükrözés, amely csak a jelenlegi állapotot másolja. Ha a forrásból véletlenül törlünk, ha korrupció lép fel, vagy ha vissza kell állítani a tegnapi verziót, az rsync-tükör nem segít. A d096 alfejezetben tárgyalt Backupstratégia, retention és RPO/RTO szerint a backup csak akkor létezik, ha a visszaállítás bizonyított. Ehhez versioned backup kell: immutábilis, időbélyegzett recovery pointok, amelyek több korábbi állapotot is megőriznek. A restic és a Borg két olyan, aktív közösséggel rendelkező eszköz, amely titkosított, deduplikált repositoryt épít. Ebben az alfejezetben a restic-et használjuk fő példaként, és a Borg koncepcionális párját is bemutatjuk.

20.2.2 Deklaratív cél és definíciók

Versioned backup repository: olyan, jellemzően content-addressed adattároló, amelyben minden backup egy immutable snapshot, és a közös tartalmú blokkokat deduplikálják. A snapshot egy adott időponthoz tartozó állapotot jelent, amelyet egy azonosítóval lehet visszaállítani. A deduplikáció a forrásfájlokat változó méretű chunkokra bontja, és minden chunkot a tartalomból számított erős hash (például SHA-256) azonosít. A hash egyben a hitelesítés alapja is.

Incremental retention: a recovery pointok megtartására vonatkozó szabály, amely nem elégszik meg a „mindent megtartunk” vagy a „csak a legutolsót” modellel. Például napi 7, heti 4, havi 6 snapshot megtartása lehetővé teszi, hogy a tegnapi hibát percek alatt, a tavalyi állapotot pedig órák alatt állítsuk vissza. A restic forget parancsa törli a snapshotokat, a prune pedig ténylegesen felszabadítja a már nem hivatkozott chunkokat.

Politika és repository-életciklus: a backup repository életciklusa az inicializálástól (key és metadata létrehozása), a snapshotok készítésén, ellenőrzésén és a retention törlésen át a teljes helyreállítási próbáig tart. A restic repository egy lock mechanizmussal védi a párhuzamos írásokat.

20.2.3 Restic/Borg eszközprofil

A restic és a Borg is a fenti modellt valósítja meg, de eltérő komponensekkel.

A restic egyetlen statikus binárisból áll, és a repository formátumát a restic init hozza létre. A repository könyvtár tartalmazza a config, a key fájlt, az adatokat és az indexeket. A restic encryption- és integrity-ellenőrzése a repository jelszóból levezetett kulccsal történik; a jelszó elvesztése az adatok elvesztését jelenti. A repository konfigurációja így egyfajta „kulcstartó”, amelyhez a jelszó a mesterkulcs.

A Borg a borg init --encryption=repokey-blake2 opcióval hoz létre repositoryt. A repokey módban a titkosító kulcs a repositoryban van, de a jelszóval védett; a keyfile módban a kulcsot egy külön fájlba menti a kliens. A Borg különbsége, hogy a deduplikáció mellett opcionális erős tömörítést is végez, és a repository tömörített, hitelesített csomagokból áll.

Mindkét eszköznél ugyanaz a repository-szerződés: a repository path, a jelszó és a backup policy együttesen határozza meg a visszaállítási képességet. A jelszót és a kulcsfájlt nem szabad a backup adattal együtt tárolni.

20.2.4 Példa: titkosított repository és end-to-end restore

A labhost legyen labhost01, a felhasználó backup, a forrás könyvtár /srv/labdata, a repository pedig /srv/backup/restic-repo. A példa Ubuntu Server 24.04 LTS alatti, diszponibilis laborlemezen fut, dummy jelszóval. Feltételezzük, hogy a restic csomag telepítve van, de a csomagverziót a lab kezdetén ellenőrizni kell.

Előkészítés és repository inicializálás:

# labhost01, UID 1000 backup
sudo mkdir -p /srv/backup /srv/labdata
sudo chown backup:backup /srv/backup /srv/labdata

export RESTIC_REPOSITORY=/srv/backup/restic-repo
export RESTIC_PASSWORD='dummy-lab-password-123'   # csak labor; ne commitold

restic init

Várható kimenet: created restic repository és a repository-könyvtárban config, key, data, index elemek.

Első backup, exclude szabályokkal:

restic backup /srv/labdata \
  --exclude='build' \
  --exclude='*.o' \
  --exclude='.cache' \
  --exclude-file=/srv/backup/labdata-excludes.txt

Az exclude fájl tartalma például:

# labdata-excludes.txt
build/
tmp/
*.o

A --exclude és --exclude-file szabályok nemcsak a fájlokat, hanem a könyvtárakat is kihagyják, de a minta értelmezése a restic verziójától függ; a pontos szabályrendszer ellenőrizendő.

Snapshotok listázása és integrity check:

restic snapshots
restic check
restic stats --mode raw-data

A restic check alapértelmezésben a repository struktúráját ellenőrzi; a teljes adatbeolvasáshoz --read-data kell.

Restore próba egy izolált könyvtárba:

rm -rf /tmp/restore-test
restic restore latest --target /tmp/restore-test
diff -r --no-dereference /srv/labdata /tmp/restore-test/srv/labdata

A restore target alatt a forrás abszolút útvonala jelenik meg, ezért a diff a /tmp/restore-test/srv/labdata utat hasonlítja. Ha a diff nem ad kimenetet, a visszaállítás tartalmilag megegyezik a forrással. A owner/group, ACL és xattr visszaállításához a restore-t root jogosultsággal kell futtatni; ellenkező esetben a restic csak a jogos járműveket állítja vissza.

Retention policy alkalmazása:

restic forget --keep-daily 7 --keep-weekly 4 --keep-monthly 6
restic prune
restic check

A forget a snapshotokat törli, a prune a repositoryban maradt, nem hivatkozott blokkokat foglalja vissza. A prune egy lock alatt fut, és nagyobb repository esetén időigényes lehet.

Monitor példa, amely a legutóbbi snapshot korát és a restore próba sikerét rögzíti:

#!/usr/bin/env bash
set -uo pipefail
export RESTIC_REPOSITORY=/srv/backup/restic-repo
# RESTIC_PASSWORD-t a caller biztosítja; ne logold

if ! restic snapshots --json > /tmp/snapshots.json 2> /tmp/restic.err; then
  echo "ERROR restic snapshots: $(cat /tmp/restic.err)"
  exit 1
fi

# A JSON séma verziófüggő; ez a példa csak a struktúra megvilágítására szolgál.
last_epoch=$(jq -r '.[-1].time // empty' /tmp/snapshots.json)
if [ -z "$last_epoch" ]; then
  echo "ERROR no snapshot"
  exit 1
fi

echo "restic_last_snapshot_epoch=${last_epoch}"

A monitor kimenete nem mérés, hanem a mentés eredményét írja le. A restore próbát nem elegendő egyszer elvégezni: ütemezett, napi gyakoriságú „restore drill” kell, amely a visszaállított fájlok ellenőrzőösszegét is összeveti.

20.2.5 Hibák és ellenpróbák

Tünet: az rsync tükör sikeres, de a felhasználó vissza akar térni egy tegnapi állapothoz.
Diagnózis: a tükrözés nem verziózott, nincs snapshot, legfeljebb egy korábbi tükör.
Javítás: vezessük be a restic repositoryt, és a policy szerint készítsünk snapshottokat.

Tünet: a restic parancs hibát ad: Fatal: unable to create lock ... already locked.
Diagnózis: valamely korábbi backup megszakadt, és a lock fájl bennmaradt.
Javítás: ellenőrizzük, hogy tényleg nincs futó backup; ha nincs, restic unlock. Egyetlen változtatás, majd ellenőrzés.

Tünet: a forget sikeres, de a repository mérete nem csökken.
Diagnózis: a forget csak a snapshotokat törli, a blokkok felszabadítása a prune feladata.
Javítás: restic prune futtatása.

Tünet: a restore parancs sikeres, de a visszaállított fájlban hiányzik egy ACL vagy setuid bit.
Diagnózis: a restore nem root jogosultsággal futott, ezért a jogosultságok egy részét nem tudta visszaállítani.
Javítás: rootként futtatott restore, vagy a backup eleve olyan user alatt készült, aki nem olvashat mindent. A backup készítése előtt döntsük el, hogy milyen metadata-t akarunk.

Tünet: a restic check sikeres, de egy régi fájl tartalma korrupt.
Diagnózis: az alap check csak a struktúrát nézi, nem olvas be minden adatot.
Javítás: rendszeres restic check --read-data futtatása, legalább a retention időablakkal összehangolva.

20.2.6 Feladatok

20.2.6.1 1. feladat – Magyarázó

Magyarázd el, miért nem elegendő egy rsync -a --delete tükör egy production Linux hoszton a backup stratégiához. Milyen szolgáltatást ad hozzá a restic repository a recovery point, a retention és a titkosítás tekintetében? A válaszban ne telepíts semmit; a d096 modellre hivatkozz.

20.2.6.2 2. feladat – Adminisztrációs/konfigurációs

A labhost01 labhoston hozz létre restic repositoryt /srv/backup/restic-repo néven, készíts backupot a /srv/labdata könyvtárról a build könyvtár kihagyásával, alkalmazd a --keep-daily 7 --keep-weekly 4 --keep-monthly 6 retention policy-t, majd futtass prune és check parancsot. A jelszó legyen dummy-lab-password-123. Írd le a parancsokat és azok posztfeltételét.

20.2.6.3 3. feladat – Diagnosztikai/failure/recovery

A backup monitor szerint a tegnapi éjszakai backup meghiúsult, és a restic snapshots is hibát ad: unable to create lock ... already locked. Tételezd fel, hogy semmilyen más backup nem fut a hoszton. Diagnosztizáld a hibát, végezd el a recovery-t, majd bizonyítsd a helyreállítást egy restic restore latest --target /tmp/restore-recovery próbával. A cél: a repository újra használható legyen, és a visszaállítás tartalma megegyezzen az aktuális /srv/labdata tartalmával.

20.2.7 Megoldások

20.2.7.1 1. feladat megoldása

Az rsync-tükör egyetlen, folyamatosan felülírt állapotot tart. Ha a forrásban törlés vagy korrupció történik, a tükrözés ugyanazt a hibát másolja, és nincs korábbi recovery point. A restic repository ezzel szemben időbélyegzett immutábilis snapshotokat tart, amelyekből a forget --keep-* policy szerint meghatározott számú marad meg. A deduplikáció miatt a korábbi snapshotok is hatékonyan tárolódnak. A repository titkosítása biztosítja, hogy a backup adat nyugalmi állapotban is védett legyen. A restore próba pedig azt igazolja, hogy a visszaállítás nemcsak elméleti lehetőség.

20.2.7.2 2. feladat megoldása

# labhost01, backup user, RESTO rajta
sudo mkdir -p /srv/backup /srv/labdata
sudo chown backup:backup /srv/backup /srv/labdata

export RESTIC_REPOSITORY=/srv/backup/restic-repo
export RESTIC_PASSWORD='dummy-lab-password-123'

restic init
restic backup /srv/labdata --exclude='build'
restic snapshots
restic forget --keep-daily 7 --keep-weekly 4 --keep-monthly 6
restic prune
restic check

Posztfeltétel: a repository létezik, legalább egy snapshot megtalálható, a retention policy után legfeljebb a policy szerinti snapshotok maradnak, a prune lefutott, és a check nem jelez hibát. A build könyvtár tartalma nem szerepel a snapshotban.

20.2.7.3 3. feladat megoldása

# labhost01, backup user
export RESTIC_REPOSITORY=/srv/backup/restic-repo
export RESTIC_PASSWORD='dummy-lab-password-123'

# 1. Diagnózis: megvizsgáljuk, van-e futó restic processz
ps -ef | grep '[r]estic'

# 2. Ha nincs futó backup, a lock maradványt feloldjuk
restic unlock

# 3. Ellenőrizzük a repositoryt
restic check

# 4. Restore próba
rm -rf /tmp/restore-recovery
restic restore latest --target /tmp/restore-recovery
diff -r --no-dereference /srv/labdata /tmp/restore-recovery/srv/labdata

Posztfeltétel: a lock feloldódott, a restic check sikeres, a diff nem ad kimenetet, tehát a visszaállított tartalom megegyezik a forrással. A backup újra ütemezhető.

20.2.8 Rövid összefoglaló

A restic és a Borg verziózott, titkosított backup repositoryt épít. A backup csak akkor igazolt, ha a restore próba eléred a tartalmi egyezést. A repository inicializálása során keletkező kulcs és jelszó szétválasztása, az exclude/include szabályok, a forget/prune retention policy, valamint a rendszeres check és unlock együttesen adják a megbízható recovery képességet. A monitor rögzíti a legutóbbi snapshot időpontját és a restore drill sikerét.

Definíciók:

  • Versioned backup repository: immutábilis snapshotok deduplikált, titkosított tárolója.
  • Incremental retention: snapshotok megtartására vonatkozó, időablak-alapú politika.
  • Repository lock: a backup repository párhuzamos írói elleni, ügyféloldali lock mechanizmus, amely hiba esetén unlock-kal oldható.
