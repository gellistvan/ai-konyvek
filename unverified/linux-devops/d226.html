46.1 Declarative infrastructure, provider és state

46.1.1 Motiváció

Egy szenior C++ fejlesztő a buildrendszerében megszokta, hogy a make vagy CMake függőségi gráf alapján, helyesen topologikus sorrendben hívja a fordítót, és csak akkor épít újra, ha a forrás vagy a függőség ténylegesen megváltozott. Amikor viszont felhő-erőforrásokat (VM, hálózat, tár) kell létrehozni, a manuális CLI-hívások nem adnak ilyen garanciát: a sorrend könnyen elromlik, az állapot a fejünkben vagy egy scriptben él, és a környezet idővel „elsodródik” a dokumentációtól. Az Infrastructure as Code (IaC) a buildrendszerhez hasonló fegyelmet vezet be: deklaratív konfigurációból gráfot épít, és a gráf szerint hajtja végre a távoli provider API-hívásokat, miközben egy külön állapotfájlban rögzíti a hozzárendelést a konfiguráció és a tényleges erőforrás között.

Ebben az alfejezetben az IaC alapfogalmait vezetjük be. A cél, hogy a korábbi d111 inventory/SoT fejezetből ismert desired state, observed state és drift fogalmakat továbbvigyük az infrastruktúraprogramozásba, és programozói szemmel is értékeljük a provider API műveletek függőségi és idempotencia-tulajdonságait.

46.1.2 Config, state és tényleges erőforrás

Az IaC három, egymástól élesen elválasztott állapotot használ:

  • Config (desired state): a verziózott HCL-ben (Hashicorp Configuration Language) vagy más deklaratív nyelven leírt kívánt állapot. Ez adja meg, mi létezzen, nem azt, hogy hogyan jöjjön létre. A config a source of truth; a Git repositoryban él, review-n megy keresztül.
  • State (stored state): a Terraform/OpenTofu által karbantartott állapotfájl, amely a configban szereplő erőforrásokat a provider által visszaadott tényleges azonosítóhoz (id, arn, DNS-név stb.) rendeli. Ez nem egyszerű cache: a működéshez szükséges a függőségi gráf kiszámításához, a törlés és frissítés megtervezéséhez, valamint az importáláshoz.
  • Actual resource (observed state): a provider API-ja által éppen látott valós erőforrás. Ez a valóság, amit a refresh művelet kérdez le, és ez alapján derül ki a drift.

A három állapot kapcsolata:

Fogalom Példa Honnan származik
Config / desired aws_s3_bucket.lab_artifact deklaráció Git repository
State / stored "aws_s3_bucket.lab_artifact" → "id": "lab-artifact-xyz" A legutóbbi apply eredménye
Actual / observed a bucket ténylegesen létezik-e az AWS konzolban Provider API hívás

Az erőforrások HCL-ben resource, a csak olvasható adatok data blokkban jelennek meg. A provider blokk választja ki és konfigurálja a felhőszolgáltatót vagy más API-t; a module pedig újrafelhasználható, paraméterezett alrendszer-config csomag. Az alábbi példa egy üres resource blokk és egy provider konfiguráció vázlata:

# provider konfiguráció: region, credential forrás
provider "aws" {
  region = "eu-west-1"
}

# resource: az erőforrás típusa "aws_s3_bucket", a helyi neve "lab_artifact"
resource "aws_s3_bucket" "lab_artifact" {
  bucket = "lab-artifact-demo"
}

A data blokk már létező erőforrást olvas be anélkül, hogy az életciklusát kezelné. A module segítségével ugyanez a konfiguráció paraméterezhető, például a bucket neve változóként adható át.

46.1.3 Desired state és resource graph

A Terraform/OpenTofu nem szekvenciálisan futtat parancsokat, hanem a configból egy függőségi gráfot (resource graph) épít. A gráf csúcsai az erőforrások és a data-source-ok, az élei a HCL-ben megjelenő referencia-kapcsolatok. Például:

resource "random_pet" "bucket_suffix" {
  length = 2
}

resource "aws_s3_bucket" "lab_artifact" {
  bucket = "lab-artifact-${random_pet.bucket_suffix.id}"
}

Itt az aws_s3_bucket.lab_artifact függ a random_pet.bucket_suffix tulajdonságtól. A gráf él: random_pet.bucket_suffix → aws_s3_bucket.lab_artifact. A gráf aciklikus, ezért topologikus sorrendben párhuzamosítható: a fundamentális sorrendben a random_pet létrehozása megelőzi a bucket létrehozását, mert a bucket neve a random_pet.id-től függ.

A gráfot a terraform graph parancs is ki tudja rajzolni, de a plan outputban is megjelenik a sorrend. A make build graphtól való hasonlóság nem véletlen: a cél, hogy csak a ténylegesen változó erőforrásokat módosítsuk, és a függőségi irányokat mindig előrevetítsük.

46.1.4 Plan, apply és external side effect

A plan fázis három lépést végez:

  1. Refresh: a provider API-kból frissíti a state-hez tartozó erőforrások aktuális tulajdonságait, hogy a state a tényleges állapotot tükrözze.
  2. Diff: összehasonlítja a configban leírt desired state-et a refreshed state-ből számolt aktuális állapottal. Ha az erőforrás nincs a state-ben, akkor létrehozást (create) tervez; ha létezik, de a paraméterek eltérnek, frissítést (update); ha a configból törölve lett, de a state-ben szerepel, törlést (delete).
  3. Order: a gráf alapján meghatározza a műveletek biztonságos sorrendjét. A törlés általában fordított függőségi sorrendben történik.

Az apply a planben kiszámított gráf szerint valóban meghívja a provider API-ját. Minden ilyen hívás külső mellékhatással (external side effect) jár: VM-et indít, hálózati interfészt készít, DNS-rekordot hoz létre. Ez nem csak egy fordítás: a hibás sorrend vagy egy megszakadt futtatás valódi, talán nem triviálisan visszaállítható változást okoz a felhőben. Ezért a plan kimenetét mindig review-zni kell, és az apply előtt explicit jóváhagyást kérni, például a -auto-approve elhagyásával.

A HCL config létrehozása és a futtatás minimális lépései:

# 1. Inicializálás: provider pluginok, modulok, backend letöltése
terraform init

# 2. Plan: az aktuális állapot frissítése és a függőségi gráf szerinti változások előrejelzése
terraform plan

# 3. Apply: a terv végrehajtása a provider API-n keresztül
terraform apply

46.1.5 Statefile: nem csak cache, hanem szükséges mapping

A statefile gyakran JSON formátumú, és a .tfstate kiterjesztésű helyi fájlban vagy távoli backendben él. Egy leegyszerűsített részlet:

{
  "version": 4,
  "terraform_version": "1.8.0",
  "resources": [
    {
      "mode": "managed",
      "type": "random_pet",
      "name": "bucket_suffix",
      "provider": "provider[\"registry.terraform.io/hashicorp/random\"]",
      "instances": [
        {
          "schema_version": 0,
          "attributes": {
            "id": "brief-marmot",
            "length": 2
          }
        }
      ]
    }
  ]
}

A statefile szerepe többrétű:

  • Azonosító leképezés: a configbeli név (random_pet.bucket_suffix) és a provider által visszaadott tényleges azonosító (id = "brief-marmot") közötti kapcsolat. A provider csak az id-t ismeri, a HCL referencia viszont a configbeli nevet használja.
  • Függőségi gráf újraépítése: Ha elveszne a state, egy későbbi terraform plan nem tudná eldönteni, hogy a aws_s3_bucket.lab_artifact bucket neve a random_pet.bucket_suffix.id-ből származik-e, ezért minden erőforrást újként látna, ami törléshez vagy duplikációhoz vezethet.
  • Életciklus-metaadatok: a state tárolja a provider által visszaadott teljes attribútumhalmazt, beleértve a sensitive értékeket is (pl. jelszó hash), a függőségeket, a line számot a configban, és a depends_on implicit éleit.
  • Importálás alapja: a terraform import a meglévő actual resource-t regisztrálja a state-be anélkül, hogy újra létrehozná.

A statefile tehát nem egy gyorsítótár, amit törölhetünk; ez a híd a minket érdeklő desired state és a provider által látott actual resource között. Ennek a mappingnek az elvesztése gyakran manuális feladatot, importálást vagy akár teljes újraépítést igényel. A termelési használatban a state remote backendben van, lockolva, verziózva (lásd d227).

46.1.6 Drift és out-of-band change

Az out-of-band change (sávon kívüli változás) olyan módosítás, amely nem a Terraform/OpenTofu alkalmazáson keresztül történt: például valaki a webkonzolban kézzel töröl egy bucketet, vagy a CLI-vel módosít egy security group szabályt. A következő terraform plan során a refresh észleli, hogy a state-ben tárolt attribútumok nem egyeznek a provider API által visszaadottakkal. Ez a drift: az observed state eltér a config (desired) által rögzített állapottól.

A terv ilyenkor általában a config által előírt állapotot visszaállító műveletet jelez. Ha a bucket eltűnt, a plan újra létrehozza. Ha csak egy attribútum változott meg, a plan in-place frissítést mutat. Ha a bucket a configban már nem szerepel, de a state-ben még igen, a plan törlésre fog javaslatot tenni, függetlenül attól, hogy az actual resource még létezik-e.

A drift kezelése a d111-ből ismert elv szerint történik: vagy a source of truth-ot frissítjük, vagy a megfigyelt állapotot állítjuk vissza. Az IaC esetében ez a config módosítása vagy az apply végrehajtása, illetve az out-of-band módosítás importálása a configba.

46.1.7 OpenTofu/Terraform támogatott profil

A könyv a Terraform és az OpenTofu fogalmát párhuzamosan használja, mert az OpenTofu a Terraform BUSL licence után indult nyílt forráskódú fork, és a HCL nyelv, a resource graph, a statefile koncepciója kompatibilis maradt. A generálás időpontjában a támogatott stabil kiadások, a provider support matrix és a hashicorp/aws vagy hashicorp/random provider verziók a hivatalos dokumentációból ellenőrizendők. Az alábbi általános irányelvek viszont stabilak:

  • A HCL és a statefile formátum alapvetően kompatibilis a két projekt között a fork idején, de a későbbi feature-ök és a backend-támogatás eltérhet. Különböző verziójú CLI-k ne írják ugyanazt a statefile-t.
  • Az Ubuntu 24.04 LTS disztribúció által szállított csomagok nem feltétlenül a legfrissebb stabil verziók; a laborban a projekt hivatalos release-jét vagy egy verziózott letöltést érdemes használni, a hash ellenőrzésével.
  • A required_version és required_providers korlátozások a configban egyfajta ABI-kontrollként szolgálnak: biztosítják, hogy a gráfot ugyanaz a függvénykönyvtár-verzió számolja, amelyre a config íródott. Ez hasonló ahhoz, ahogy a C++ projekt rögzíti a szabványt (-std=c++20).

A pontos verziókat és support mátrixot a kutatás hiánya miatt nem adom meg; az ellenőrzési hiányok között jelölöm.

46.1.8 Kidolgozott példa: véletlen névből függő S3 bucket

A következő példa egy izolált sandboxban futtatható, hipotetikus AWS-fiókot használ; a tényleges futtatáshoz éles account és credential kell, amit a szabályok szerint a laborhoz külön kell biztosítani. A config:

terraform {
  required_version = ">= 1.8"
  required_providers {
    random = {
      source  = "hashicorp/random"
      version = ">= 3.6, < 4.0"
    }
    aws = {
      source  = "hashicorp/aws"
      version = ">= 5.0, < 6.0"
    }
  }
}

provider "aws" {
  region = "eu-west-1"
}

resource "random_pet" "bucket_suffix" {
  length = 2
}

resource "aws_s3_bucket" "lab_artifact" {
  bucket = "lab-artifact-${random_pet.bucket_suffix.id}"
}

A várt terraform plan kimenet (illusztratív, nem tényleges futtatás):

Terraform will perform the following actions:

  # random_pet.bucket_suffix will be created
  + resource "random_pet" "bucket_suffix" {
      + id     = (known after apply)
      + length = 2
    }

  # aws_s3_bucket.lab_artifact will be created
  + resource "aws_s3_bucket" "lab_artifact" {
      + bucket = (known after apply)
    }

Plan: 2 to add, 0 to change, 0 to destroy.

A kimenet mutatja, hogy a bucket érték „known after apply”, mert függ a random_pet.id-től, ami csak a create után derül ki. A gráf topologikusan sorrendezi: előbb a random_pet, utána a bucket.

Az apply után a statefile (részlet) így néz ki:

{
  "version": 4,
  "resources": [
    {
      "mode": "managed",
      "type": "random_pet",
      "name": "bucket_suffix",
      "instances": [
        {
          "attributes": { "id": "brief-marmot", "length": 2 }
        }
      ]
    },
    {
      "mode": "managed",
      "type": "aws_s3_bucket",
      "name": "lab_artifact",
      "instances": [
        {
          "attributes": { "bucket": "lab-artifact-brief-marmot" }
        }
      ]
    }
  ]
}

Ha most valaki kézzel törli a bucketet a konzolon, a következő terraform plan először refresh-el, és a state-ben lévő bucket ténylegesen nem létezik. A plan ezt mutatja:

  # aws_s3_bucket.lab_artifact will be created
  + resource "aws_s3_bucket" "lab_artifact" {
      + bucket = "lab-artifact-brief-marmot"
    }

Plan: 1 to add, 0 to change, 1 to destroy.

A terv nem tudja, hogy a bucket valaha létezett; a provider visszajelzése alapján hiányzik, ezért újra létrehozza. Ez a drift javítás egyik módja: az apply visszaállítja a desired state-et. A másik út, ha a bucket törlése szándékos, akkor a configból el kell távolítani az erőforrást, és apply-val törölni a state-ből is.

46.1.9 Tipikus hibák és ellenpróbák

  1. Cycle észlelése: Ha két erőforrás kölcsönösen egymásra hivatkozik, a gráf ciklust tartalmaz, és a terraform plan hibát ad: Cycle: aws_security_group.a, aws_security_group.b. Ez általában tervezési hibát jelez, nem valós függőséget. Megoldás: a referencia irányát explicit depends_on-nal vagy a config átstrukturálásával kell feloldani.

  2. Statefile elvesztése: Ha a .tfstate törlődik, de a tényleges erőforrások léteznek, a terraform plan mindent újként mutat, és az apply duplikálhat. A helyes lépés: terraform import <resource> <id> minden meglévő erőforrásra, majd plan. A statefile tehát nem egy frissíthető cache, hanem a source of truth része.

  3. Out-of-band módosítás félreértelmezése: A plan által mutatott destroy nem feltétlenül jelenti a bucket törlését; ha a bucket a configban van, de a state-ben nem, a plan létrehozást jelez. Ha viszont a bucket a state-ben van, de a configból töröltük, akkor a plan törlést javasol, még akkor is, ha a bucket ténylegesen létezik. Ez a config mint desired state következménye.

  4. Provider verzió inkompatibilitás: Ha a statefile-t egy újabb Terraform/OpenTofu verzió nyitja meg, a version lock és a state schema frissülhet. A visszafelé kompatibilitás nem garantált, ezért a generáláskori stabil verziót rögzíteni kell, és a frissítést tesztelt módon, külön backenddel végezni.

  5. Partial apply: Ha az apply hálózati hiba miatt megszakad, a statefile inkonzisztens lehet: néhány erőforrás létrejött, más nem. A következő terraform plan képes felismerni a tényleges állapotot a refresh segítségével, de a megszakadt művelet során létrejött erőforrások állapota a provider függvénye. A jövőbeli fejezet d227 tárgyalja a lockolást és a recovery-t.

46.1.10 Feladatok

46.1.10.1 1. feladat (magyarázó): resource graph és provider hívási sorrend

Tekintsd a következő HCL konfigurációt:

resource "aws_vpc" "lab_vpc" {
  cidr_block = "10.0.0.0/16"
}

resource "aws_subnet" "lab_subnet" {
  vpc_id     = aws_vpc.lab_vpc.id
  cidr_block = "10.0.1.0/24"
}

resource "aws_instance" "lab_vm" {
  ami           = "ami-12345678"
  instance_type = "t3.micro"
  subnet_id     = aws_subnet.lab_subnet.id
  depends_on    = [aws_vpc.lab_vpc]
}

Rajzold fel a függőségi gráfot, és add meg a provider hívási sorrendet a create fázisban. Indokold, hogy a depends_on = [aws_vpc.lab_vpc] miért szigorúan véve redundáns ebben a konfigurációban.

46.1.10.2 2. feladat (adminisztrációs/konfigurációs): helyi drift gyakorlat

Készíts egy új munkakönyvtárat lab-iac-state néven. Hozz létre benne egy main.tf fájlt az alábbi tartalommal:

terraform {
  required_version = ">= 1.8"
  required_providers {
    random = {
      source  = "hashicorp/random"
      version = ">= 3.6, < 4.0"
    }
    local = {
      source  = "hashicorp/local"
      version = ">= 2.5, < 3.0"
    }
  }
}

resource "random_pet" "demo" {
  length = 2
}

resource "local_file" "demo_output" {
  content  = random_pet.demo.id
  filename = "${path.module}/demo.txt"
}

Futtasd a terraform init, terraform plan, terraform apply parancsokat. Ellenőrizd a terraform state list és a terraform state show random_pet.demo kimenetét. Ezután kézzel töröld a demo.txt fájlt, és futtass újra terraform plan-t. Írd le, mit mutat a terv, és miért. Végül futtass terraform apply-t, és bizonyítsd a demo.txt visszaállítását.

46.1.10.3 3. feladat (diagnosztikai/failure/ recovery): out-of-band törlés

Hipotetikus szituáció: Az előző gyakorlat random_pet.demo erőforrása a terraform apply után a state-ben szerepel, de egy külső beavatkozás során a valós erőforrás (a véletlenszerű azonosító) elveszett. A terraform plan ezt fogja mutatni: a random_pet.demo létrehozásra kerül, mert a provider API szerint nem létezik, míg a local_file.demo_output tartalma is változik, mert új id jön létre. Indokold, miért elegendő önmagában a terraform apply a drift megszüntetésére, és miért nem szabad ilyenkor terraform state rm random_pet.demo-t futtatni először. Milyen adatgyűjtési lépéssel igazolnád, hogy a state és a config is konzisztens az apply után?

46.1.11 Megoldások

46.1.11.1 1. feladat megoldása

A gráf élei:

  • aws_vpc.lab_vpc → aws_subnet.lab_subnet, mert a subnet hivatkozik a VPC id-jére.
  • aws_subnet.lab_subnet → aws_instance.lab_vm, mert az instance subnet_id-je a subnet id-jét használja.
  • Emellett a depends_on = [aws_vpc.lab_vpc] közvetlen élt ad a VPC és az instance közé.

A create sorrend: először a VPC, majd a subnet, végül az instance. A redundáns depends_on azért szükségtelen, mert az instance a subnet-re hivatkozik, a subnet pedig a VPC-re, így a tranzitív függőség már biztosítja a helyes sorrendet. A depends_on ott hasznos, ha nincs közvetlen attribútum-referencia, de a létrehozási sorrend mégis fontos (pl. egy olyan erőforrásnál, ami policy-t állít be egy másik service-ben).

Postcondition: A gráf aciklikus, topologikus sorrend a VPC → subnet → instance. A terraform plan nem jelez ciklust.

46.1.11.2 2. feladat megoldása

A parancsok sorrendje:

terraform init
terraform plan
terraform apply
terraform state list
# kimnet: random_pet.demo, local_file.demo_output
terraform state show random_pet.demo

A demo.txt törlése után a terraform plan ezt mutatja (várható, illusztratív):

Terraform will perform the following actions:

  # local_file.demo_output will be created
  + resource "local_file" "demo_output" {
      + content  = "brief-marmot"
      + filename = "./demo.txt"
    }

Plan: 1 to add, 0 to change, 0 to destroy.

Azért, mert a refresh során a provider a helyi fájlrendszerben nem találja a fájlt, tehát az observed state hiányt jelez. A local_file erőforrás létezik a state-ben, de az actual hiányzik, ezért a plan újra létrehozza. Az apply visszaállítja a fájlt a state-ben tárolt content alapján.

Postcondition: A demo.txt ismét létezik a random_pet.demo.id értékével. A terraform state list továbbra is ugyanazt a két erőforrást mutatja, a state-ben nem jött létre duplikátum.

46.1.11.3 3. feladat megoldása

A terraform apply azért elegendő, mert a state és a config konzisztens maradt: a desired state szerint a random_pet.demo-nek léteznie kell, a state is azt tárolja, hogy korábban létezett, de a refresh szerint az actual hiányzik. Ez a drift egyértelműen a config irányába való visszaállítást igényel: az apply újra létrehozza a random_pet-et, majd frissíti a local_file tartalmát.

Ha viszont először terraform state rm random_pet.demo-t futtatunk, a state-ből eltávolítjuk a mappinget, de a config továbbra is deklarálja az erőforrást. Ekkor a plan a random_pet-et vadonatúj erőforrásként kezelné, és a local_file tartalma is frissülne az új id-re, ami nem javítja a driftet, hanem új konzisztens állapotot hoz létre egy felesleges state manipulációval. A state rm csak akkor indokolt, ha az erőforrást ténylegesen ki akarjuk venni a menedzselésből, például az import előtt vagy ha a configból már töröltük.

Az apply utáni verifikáció: terraform state show random_pet.demo és cat demo.txt – mindkettőnek ugyanazt az id-t kell mutatnia, mint az apply előtti state-ben, vagy ha az új id eltér, akkor a local_file tartalma is ezt tükrözi. A terraform plan ezután nem jelez változást.

Postcondition: A random_pet.demo ismét létezik, a state és a config konzisztens, a demo.txt a jelenlegi id-t tartalmazza, és a terraform plan üres (0 to add, 0 to change, 0 to destroy).

46.1.12 Rövid összefoglaló

A declarative infrastructure három állapotot különböztet meg: a config a desired state, a statefile a stored mapping, az actual resource a provider által látott observed state. A HCL resource gráfot definiál, amelyből a Terraform/OpenTofu topologikus sorrendben képezi le a provider API-hívásokat. A plan refresh, diff és sorrend szerint előre jelzi a módosításokat; az apply tényleges külső mellékhatásokkal jár. A statefile nem cache, hanem az azonosító-leképezés és a függőségi gráf forrása; elvesztése importálást igényel. A drift a config és az actual resource eltérése, amit a plan jelzi és az apply vagy a config módosítása old fel. Továbbhasznált definíciók: resource graph, state mapping, drift.
