33.3 VXLAN/EVPN, underlay és SDN

33.3.1 Motiváció

Egy klasszikus, kizárólag VLAN-alapú adatközponti hálózatban a második réteg (L2) kiterjed, ahogy a munkaterhelést vagy a bérlőt szolgáló VLAN-t több switchen átvezetjük. A VLAN-azonosító 12 bites mezője legfeljebb 4094 hálózatot enged meg, a nagy L2 broadcast-tartomány pedig flappoló MAC-táblát, loopveszélyt és széles hiba-tartományt hoz létre. A spine–leaf IP-fabric ezzel szemben stabil, jól méretezhető és ECMP-alapú, de a kiszolgálók néha a kiinduló switchen kívülre kerülnek, és a bérlői L2-szegmenseket mégsem akarjuk minden levélen VLAN-ként üzemeltetni. A VXLAN–EVPN ezt a két igényt köti össze: az underlay (a fizikai IP-hálózat) csak a tunnel végpontok elérését biztosítja, az overlay pedig a bérlői kereteket szállítja az L3-hálózaton keresztül, VNI-vel elkülönítve.

Szenior C++ fejlesztőként itt is tulajdonviszony- és adatút-modellezésről van szó: az underlay route tábla azt mondja meg, hogyan érhető el egy másik VTEP; az overlay route/MAC-tábla pedig azt, hogy az adott bérlői cél melyik VTEP mögött van. A hibakereséskor ezt a két tulajdonost mindig külön kell vizsgálni, mert a tünet gyakran keveredik.

33.3.2 Definíció és működés

Underlay alatt azt a fizikai vagy fizikailag route-olt IP-hálózatot értjük, amely a loopback- vagy VTEP-címek elérését biztosítja. Az underlay lehet OSPF, IS-IS vagy eBGP alapú; jelen fejezetben számunkra az a lényeg, hogy a VTEP-IP-k között stabil IP-route létezik, és a keret az adott MTU-val fragmentálás vagy eldobás nélkül átfér. Overlay alatt a bérlői L2/L3 forgalom olyan továbbítását értjük, amely egy beágyazott (encapsulated) csomagban halad az underlay felett.

A VXLAN (Virtual eXtensible LAN) egy UDP-alapú beágyazási protokoll. A bérlői Ethernet-keretet egy VXLAN-fejléccel, majd UDP-fejléccel, majd külső IP-fejléccel látjuk el. A VNI (VXLAN Network Identifier) 24 bites azonosító, tehát elméletileg körülbelül 16 millió szegmens lehetséges. A VTEP (VXLAN Tunnel Endpoint) az az eszköz, amely a beágyazást és kicsomagolást végzi. A VTEP lehet Linux kernel, Open vSwitch, hypervisor vswitch vagy fizikai switch.

A VXLAN csomag felépítése:

Réteg Mező Megjegyzés
Underlay L2 külső Ethernet-fejléc A kábel/switch L2-címei
Underlay L3 külső IP-fejléc Forrás/cél IP: VTEP-IP-k
Transport UDP Általában célport 4789
Overlay header VXLAN 8 bájt: flags + VNI
Overlay L2 belső Ethernet-keret Az eredeti bérlői keret, beleértve a belső MAC-címeket

Amikor egy bérlői MAC-cím ismeretlen, a VXLAN adatsík vagy broadcast/multicast/unicast replikációval küld BUM-forgalmat, vagy a control plane már ismeri a MAC–VTEP hozzárendelést. A statikus VXLAN-konfigurációban kézzel töltjük a bridge FDB-t remote bejegyzésekkel. A flood-and-learn modell törékeny: ismeretlen unicast elárasztást, ARP-elárasztást és nagy broadcast-tartományt örököl. Az EVPN ezt BGP-vel oldja meg.

Az EVPN (Ethernet VPN) nem új adatsík, hanem control plane: a VTEP-ek MP-BGP-n keresztül hirdetik a bérlői MAC/IP-ket és a VNI-hozzárendelést. A BGP EVPN address family a következő főbb route-típusokat használja:

  • Route Type 2: MAC/IP advertisement – adott MAC és opcionálisan IP a VTEP-től.
  • Route Type 3: Inclusive Multicast Ethernet Tag route – BUM-replikációs lista.
  • Route Type 5: IP prefix route – L3 elérés az overlayben.

Az RT (Route Target) biztosítja a VNI/tenant import/export szétválasztást. Így a VNI-hez tartozó route-állapot és az underlay route-állapot külön BGP-táblákban él: az underlay címek a globális IPv4/IPv6 unicast AF-ben, az overlay címek az EVPN AF-ben.

Az SDN controller és a datapath kapcsolata ugyanezt a szétválasztást magasabb szinten ismétli. A controller a kívánt végpont-térképet és policy-t egy nyílt vagy zárt API-n keresztül programozza; a datapath (kernel, OVS, smartNIC, eBPF) a tényleges csomagokat továbbítja. A Linux bridge, az Open vSwitch és a CNI-ek (például Cilium, Calico, Flannel) különböző datapath/control plane kombinációkat valósítanak meg:

  • Linux bridge + static FDB: egyszerű, tanulásra alkalmas, de nem skálázódik.
  • Linux bridge + EVPN (FRR): kernel datapath, BGP control plane.
  • OVS + OpenFlow/OVN: flow-alapú datapath, SDN controller.
  • Kernel eBPF + Cilium: programozott datapath policy-val.

A konténer- és Kubernetes-hálózatban gyakran ugyanez a VXLAN/GENEVE technika fut, de a CNI plugin automatikusan kezeli a VTEP-eket, VNI-ket, route-okat és MTU-t. A kézi labor ezért nem a modern platform helyettesítése, hanem a láthatóvá tétel eszköze.

33.3.3 Kidolgozott példa

A labort két Linux hoszton hozzuk létre, ahol minden hoszt egy VTEP és egy bérlői bridge. Az underlay OSPF helyett a lab kedvéért statikus route-ot használunk; a proof csak a VXLAN-rétegek ellenőrzésére szolgál.

Topológia

Elem Interface IP Szerep
lab-leaf1 eth0 192.0.2.10/24 underlay leaf1
lab-leaf1 lo 10.0.0.1/32 VTEP IP
lab-leaf2 eth0 192.0.2.20/24 underlay leaf2
lab-leaf2 lo 10.0.0.2/32 VTEP IP
lab-tenant-a1 veth 192.0.2.101/24 bérlő végpont VNI 10001
lab-tenant-a2 veth 192.0.2.102/24 bérlő végpont VNI 10001

Az underlay MTU-t 1550 bájtra emeljük a használt interface-en, hogy a 1500 bájtos belső IP-csomag ne fragmentálódjon. Ezt a lab VLAN/interface típusától függően a switch oldalon is engedélyezni kell; a lab ellenőrzése előtt ping -M do -s 1472 próba szükséges.

Parancsok lab-leaf1-en

# TARGET: lab-leaf1, UID: root (vagy sudo -n)
# Előfeltétel: eth0 192.0.2.10/24, lo 10.0.0.1/32, underlay route 10.0.0.2 felé
ip link add vxlan100 type vxlan id 10001 remote 10.0.0.2 dev eth0 dstport 4789
ip link add br100 type bridge
ip link set vxlan100 master br100
ip link set lab-tenant-a1 master br100
ip link set vxlan100 up
ip link set br100 up
ip link set lab-tenant-a1 up
bridge fdb show dev vxlan100

Várható kimenet a statikus remote után:

00:00:00:00:00:00 dst 10.0.0.2 self permanent

Parancsok lab-leaf2-n

Ugyanez, csak a remote IP az 10.0.0.1, és a lab-tenant-a2 port kerül a br100 bridge-be.

Ellenőrzés

A lab-tenant-a1 névtérből pingeljük a lab-tenant-a2 IP-t. Mivel a két bérlői IP azonos L2-szegmensbe tartozik, a bridge flood-and-learn módon megtanulja a MAC–VTEP hozzárendelést. A bridge fdb show br100 várt sorai:

<MAC-cím> dev vxlan100 dst 10.0.0.2 self
<helyi MAC-cím> dev lab-tenant-a1 master br100

A csomagfogás a lab-leaf1 eth0 interfészén:

tcpdump -n -i eth0 udp port 4789 -c 2

Várt csomag:

IP 192.0.2.10.xxxxx > 192.0.2.20.4789: UDP, length 106

A belső MAC-címeket és a VXLAN-fejlécet a tcpdump -nn -i eth0 udp port 4789 -vv mutatja, de a részletes bontáshoz Wireshark vagy tshark -V szükséges. A kulcsminta az outer IP 192.0.2.x, az UDP-port 4789, a VXLAN VNI 10001, valamint a belső Ethernet-fejlécben a bérlői MAC-címek.

MTU-ellenőrzés

A bérlői névtérben:

ping -M do -s 1472 -c 2 192.0.2.102

A -s 1472 1500 bájtos IP-csomagot jelent (1472 + 20 IP + 8 ICMP). Ha az underlay útvonalon bármely eszköz 1500-as klasszikus IP-MTU-val dolgozik, a külső UDP-datagram túl nagy lesz, és a DF bit miatt a válasz Frag needed lehet. A megoldás vagy a belső MTU csökkentése, vagy az underlay MTU emelése. A pillanatnyi alagút használhatóságát ip -d link show vxlan100 is jelzi.

33.3.4 Hibák és ellenpróbák

Az overlay hibáknál először mindig az underlay elérhetőséget és MTU-t zárjuk ki, mert a VXLAN csak ezután kerülhet szóba.

Underlay unreachable

Tünet: a VXLAN-interface felmegy, de a távoli bérlő nem elérhető; a bridge fdb bejegyzés ott van. Ellenőrzés: ping 10.0.0.2 és ip route get 10.0.0.2. Ha az underlay route hiányzik, a külső IP-csomag nem hagyja el a hosztot. Javítás: route hozzáadása a lab-leaf1-en:

ip route add 10.0.0.2/32 via 192.0.2.1 dev eth0

Ellenpróba: traceroute 10.0.0.2; ha a következő hop nem a spine, akkor policy-routing hibát keresünk.

MTU black hole

Tünet: kis ping (64 bájt) működik, nagy (1472) nem; a TCP-kapcsolat a handshake után elakad. Ellenőrzés: ping -M do -s 1472 a bérlő azonos szegmensben. Hipotézis: az underlay MTU túl alacsony, vagy a tunnel overhead rosszul van beállítva. Javítás: a belső MTU-t csökkentjük, például 1450 bájtra, hogy legalább 1400 bájtos belső IP-t tartsunk, vagy az underlay fizikai MTU-t emeljük. A d158 szerint az ICMP Frag needed elvesztése miatt a hiba méretfüggő elakadásként jelentkezik; a VXLAN esetén az underlay DF-válaszát a külső IP-fejre kapjuk, és a kernel ezt nem feltétlenül írja vissza a belső socketre.

Stale FDB

Tünet: a ping csak az egyik irányba működik, vagy hosszú flood után sem épül fel a forgalom. Ellenőrzés: bridge fdb show br100. Ha a távoli MAC dst mezője régi VTEP-re mutat, a keret rossz helyre megy. Javítás: statikus FDB-t törölni és újraprogramozni, vagy EVPN-est használni, ahol a BGP frissíti. A bridge tanulás flood-and-learn korlátaira itt nem szabad globális megoldásként hivatkozni.

VNI mismatch

Tünet: a VTEP-ek elérik egymást, de a csomagok a fogadó oldalon nincsenek a bridge-ben; tcpdump mutatja a VXLAN-t, de a bérlő nem kap. Ellenőrzés: bridge -d link show vxlan100 mindkét oldalon; a VNI-k azonosak-e. Javítás: az interface újra létrehozása a helyes id értékkel. Ez a hiba az EVPN RT import/export félrekonfigurálásához hasonlít: a datapath felépül, de a tenant-állapot nem találkozik.

33.3.5 Feladatok

  1. Magyarázó feladat
    Rajzolja fel a csomagok rétegezését: belső Ethernet, VNI, UDP, outer IP, underlay L2. Határozza meg, melyik mező melyik tulajdonoshoz tartozik, és mi történik, ha az outer IP-cím nem egyezik a VTEP loopback-kel.

  2. Konfigurációs feladat
    A lab-leaf1 és lab-leaf2 hosztokon hozzon létre VNI 10002 alagutat a 10.0.0.1 és 10.0.0.2 VTEP-ek között. A bérlői bridge br200, a bérlő végpontok IP-je 192.0.2.111/24 és 192.0.2.112/24. Ellenőrizze pinggel, bridge fdb show-val és tcpdump-pal. Az MTU-t úgy állítsa, hogy 1400 bájtos belső IP-csomag ne fragmentálódjon.

  3. Diagnosztikai feladat
    A bérlői ping destination host unreachable hibát ad, de a VTEP-ek közötti ping működik. Gyűjtsön bizonyítékot: ip route get 10.0.0.2, bridge fdb show, ip -d link show vxlan100, és határozza meg a hibát. Próbálja ki azt a hibainjekciót is, hogy a VNI-t az egyik oldalon 10099-re állítja.

33.3.6 Megoldások

  1. A csomag rétegei kívülről befelé: underlay L2, outer IP (VTEP-IP-k), UDP (4789), VXLAN fejléc (VNI), belső Ethernet-fejléc. Az outer IP az underlay tulajdona; a VNI és a belső Ethernet a bérlő tulajdona. Ha az outer IP nem a VTEP loopback, az underlay route-tábla tévesen többé-kevésbé elérhetővé teheti, de a return traffic a hibás címet fogja használni forrásként, és a másik fél no such VNI vagy RPF hibát adhat.

  2. A lab-leaf1-en:

    ip link add vxlan200 type vxlan id 10002 remote 10.0.0.2 dev eth0 dstport 4789
ip link set vxlan200 mtu 1450
ip link add br200 type bridge
ip link set vxlan200 master br200
ip link set lab-tenant-b1 master br200
ip link set vxlan200 up
ip link set br200 up
ip link set lab-tenant-b1 up

    A lab-leaf2-n ugyanez a remote 10.0.0.1 IP-vel. Ellenőrzés: ping -M do -s 1372 -c 2 192.0.2.112 (az 1372 + 28 = 1400). A tcpdump mutatja az UDP 4789 csomagot. A bridge fdb show br200 tartalmazza a távoli dst bejegyzést.

  3. A VTEP-ek elérhetők, de a bérlő nem, tehát az overlay adatsíkban vagy a bridge-ben van hiba. ip route get 10.0.0.2 igazolja az underlay route-ot. bridge fdb show hiányzó vagy téves bejegyzést mutathat. ip -d link show vxlan100 megmutatja a VNI-t. Ha a VNI az egyik oldalon 10099, a másik oldal a 10001 csomagot nem fogadja be a br100-ba. Javítás: a VNI-t mindkét oldalon azonos értékre állítani, majd bridge fdb ellenőrzés. A teszt végén pontosan a labor által létrehozott vxlan100, br100, vxlan200 objektumokat töröljük; a labhost más konfigurációját nem módosítjuk.

33.3.7 Rövid összefoglaló

A VXLAN a bérlői Ethernet-keretet UDP-be ágyazza, és a VNI-vel különíti el a tenantokat. Az underlay route felelős a VTEP-IP-k eléréséért; az overlay route/MAC-tábla felelős azért, hogy melyik VTEP mögött van a bérlői cél. A kettő közötti MTU-eltérés a belső csomagok méretfüggő eldobását okozhatja, ezért az underlay MTU-t a belső MTU plusz VXLAN/outer IP/UDP overhead fölé kell emelni, vagy a belső MTU-t csökkenteni. Az EVPN ezt a MAC/IP–VTEP hozzárendelést BGP-n hirdeti, így a flood-and-learn korlátokat megszünteti. A Linux bridge, OVS és CNI-k ugyanezt a modellt valósítják meg különböző control plane-ekkel.

  • VNI: 24 bites VXLAN tenant-azonosító.
  • VTEP: a VXLAN beágyazást és kicsomagolást végző végpont.
  • Underlay/overlay: a fizikai IP-elérés és a bérlői beágyazott forgalom rétege.

Az alábbi kiindulópontok a fejezettérképből származnak; ebben a munkafolyamatban nem történt webes forrásolvasás vagy laborfuttatás, ezért a pontos szintaxis, a támogatott kernel-verzió és a friss implementációs viselkedés ellenőrzése külön kutatást igényel:

Ellenőrizendő: a használt iproute2/kernel VXLAN-szintaxis, a bridge FDB remote viselkedése, a BGP EVPN route-type támogatás a pontos FRR-verzióban, valamint a CNI pluginek aktuális MTU- és VNI-alapértékei.
