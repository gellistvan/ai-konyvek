15.5 Permission- és hozzáférési incidenslabor

15.5.1 Motiváció

A hozzáférési hibák a leggyakoribb Linux üzemeltetési incidensek, és a legtöbbször nem a program logikája, hanem a process credential, a path vagy a config owner hibás. A szenior fejlesztői ösztön ilyenkor a chmod 777 vagy a sudo chown -R, de ez a hiba okát nem tárja fel, és a javítás szélesebb hozzáférést adhat a szükségesnél. Ebben a laborban egy izolált labhost01 gépen rekonstruálunk hozzáférési hibákat, és minden javítást a legszűkebb szükséges joggal végzünk el.

15.5.2 Definíció és működési modell

Egy Linux hozzáférési döntés négy rétegben történik:

  1. Identity resolution (NSS): a kernel/szolgáltatás a felhasználónevet UID-re, a csoportneveket GID-re oldja.
  2. Session és authorization (PAM/sudo): a belépés vagy jogosultságdelegálás engedélyezi-e a konkrét felhasználóvá válást.
  3. Process credential: a futó process tényleges effective UID, effective GID és supplementary group listája. Ez a startkor készült pillanatkép; az /etc/group későbbi változása a futó processre nem hat.
  4. Object permission és path traversal: a fájlra a műveletnek megfelelő r, w vagy x jog kell. Könyvtáron a r a listázás, az x a bejárás (directory traversal). A fájl eléréséhez a path minden közbülső directory-ján x jog kell.

A hozzáférési incidens itt azt jelenti, hogy egy elvárt hozzáférés meghiúsul, vagy éppen túl széles hozzáférést találunk. A javítás akkor jó, ha az observed state-et a desired state-be hozza, és a változtatás a lehető legkisebb jogot adja.

15.5.3 Laborfixture

A labor a labhost01 Ubuntu Server 24.04 LTS alapprofilján fut. A módosító parancsokat labadmin felhasználó futtatja sudo-val. Minden objektum lab- prefixet kap. A cleanup kizárólag ezekre az objektumokra terjed ki.

A szándékos hibát a lab-svc szolgáltatásuser hozzáférésére építjük:

# target: labhost01, user: labadmin (sudo)
# előfeltétel: a lab-* user/group nem létezik
set -euo pipefail
sudo groupadd --system lab-data-owner
sudo groupadd --system lab-app
sudo useradd --system --no-create-home --home-dir /run/lab-svc --gid lab-app lab-svc
sudo useradd --system --no-create-home --home-dir /home/lab-dev --groups lab-data-owner lab-dev
sudo mkdir -p /srv/lab-app/data
sudo chown root:lab-data-owner /srv/lab-app/data
sudo chmod 0750 /srv/lab-app/data
echo 'hello lab' | sudo install -o lab-dev -g lab-data-owner -m 0640 /dev/stdin /srv/lab-app/data/input.dat
sudo setfacl -m u:lab-svc:r-- /srv/lab-app/data/input.dat
# szándékos hiba: lab-svc nem tagja a lab-data-owner csoportnak,
# így a /srv/lab-app/data könyvtáron nincs traverse (x) joga.

A fájlon a named user ACL megadja az olvasást, de a könyvtár path komponensén a belépés hiányzik. Ez tökéletesen modellezi a gyakori esetet, amikor valaki csak a fájljogot javítja, a könyvtárjogot nem.

15.5.4 Kidolgozott példa: path denial ACL-javítással

Indítsuk a diagnózist:

# target: labhost01, user: labadmin; csak olvasás
id lab-svc
sudo -u lab-svc -- cat /srv/lab-app/data/input.dat
namei -l /srv/lab-app/data/input.dat
getfacl -p /srv/lab-app/data/input.dat
getfacl -p /srv/lab-app/data

Várható, illusztratív kimenet:

uid=995(lab-svc) gid=992(lab-app) groups=992(lab-app)
cat: /srv/lab-app/data/input.dat: Permission denied
f: /srv/lab-app/data/input.dat
drwxr-xr-x root root /
drwxr-xr-x root root srv
drwxr-xr-x root root lab-app
drwxr-x--- root lab-data-owner data
-rw-r-----+ lab-dev lab-data-owner input.dat

A getfacl a fájlon mutatja, hogy a user:lab-svc:r-- jog rendben van. A könyvtáron nincs lab-svc bejegyzés. A namei -l bizonyítja, hogy a /srv/lab-app/data directory drwxr-x--- root lab-data-owner, tehát a lab-svc sem tulajdonos, sem csoporttag, sem other joggal nem rendelkezik.

A hipotézis: a fájl ACL jó, de a path traverse miatt a kernel a könyvtárnál denyel. A legszűkebb javítás nem a fájl chmod, hanem egy ACL a könyvtáron, amely csak traverse jogot ad:

# target: labhost01, user: labadmin; módosító
# előfeltétel: a fenti fixtúra létezik
# desired state: lab-svc traverse-elheti a /srv/lab-app/data könyvtárat,
# de továbbra sem listázhatja azt
sudo setfacl -m u:lab-svc:--x /srv/lab-app/data

# ellenőrzés
getfacl -p /srv/lab-app/data
sudo -u lab-svc -- cat /srv/lab-app/data/input.dat
# várható kimenet: hello lab

# rollback, ha szükséges:
# sudo setfacl -x u:lab-svc /srv/lab-app/data

A getfacl kimenete a könyvtáron:

user::rwx
user:lab-svc:--x
group::r-x
mask::r-x
other::---

A lab --x jog csak a bejárást engedi. A listázás továbbra is denied, amit smoke testtel igazolunk:

# target: labhost01, user: labadmin; read-only
sudo -u lab-svc -- test -r /srv/lab-app/data/input.dat
echo "file_readable=$?"      # várt: 0
sudo -u lab-svc -- test -x /srv/lab-app/data
echo "dir_traverse=$?"       # várt: 0
sudo -u lab-svc -- test -r /srv/lab-app/data
echo "dir_listable=$?"       # várt: 1, mert nincs read jog a könyvtáron

Ez a postcondition: a szolgáltatásuser kiolvashatja a konkrét fájlt, de nem listázhatja a teljes könyvtárat. A chmod 777 ehhez képest a listázást is megadta volna, ami felesleges hozzáférés.

15.5.5 Umask és file owner hiba

Gyakori deploy hiba: a runner root alatt fut, és a létrehozott fájl owner root:root, 0600 joggal, pedig a szolgáltatásnak kell olvasnia.

# target: labhost01, user: labadmin; szándékos hiba
sudo mkdir -p /srv/lab-app/state
sudo sh -c 'umask 077; echo "debug: sample" > /srv/lab-app/state/lab-app.conf'
stat -c '%U:%G %a %n' /srv/lab-app/state/lab-app.conf
# kimenet: root:root 600 /srv/lab-app/state/lab-app.conf

A lab-svc olvasási kísérlete Permission denied. A diagnosztikai bizonyíték a stat kimenete: az owner nem a szolgáltatás, és a mode 600 a csoportot sem engedi. A legszűkebb javítás:

# target: labhost01, user: labadmin; módosító
sudo chown lab-svc:lab-app /srv/lab-app/state/lab-app.conf
sudo chmod 0640 /srv/lab-app/state/lab-app.conf

# ellenőrzés
sudo -u lab-svc -- test -r /srv/lab-app/state/lab-app.conf && echo smoke-ok
# rollback: sudo rm -f /srv/lab-app/state/lab-app.conf

Hosszabb távon a deploy script ne hagyatkozzon a shell umaskra, hanem install-t használjon:

# target: labhost01, user: labadmin; módosító, desired state explicit
echo 'debug: sample' | sudo install -o lab-svc -g lab-app -m 0640 /dev/stdin /srv/lab-app/state/lab-app.conf

Az install explicit owner/group/mode paramétert kap, így a véletlen umask nem írja felül a desired state-et.

15.5.6 Service credential és supplementary group

Egy futó process a startkor kapott group listát tárolja. Ha a lab-svc usert később hozzáadjuk egy csoporthoz, a régi processben a változás nem jelenik meg.

# target: labhost01, user: labadmin; módosítás a credential snapshot demonstrálására
sudo groupadd --system lab-data-read
sudo -u lab-svc -- sleep 300 &
sleep 1
pid=$(pgrep -u lab-svc -x sleep | head -n1)
grep '^Groups:' /proc/$pid/status
# kimenet: Groups: 992        # a lab-app GID, régi pillanatkép

sudo usermod -aG lab-data-read lab-svc
id lab-svc
# kimenet: groups=992(lab-app),995(lab-data-read)
grep '^Groups:' /proc/$pid/status
# kimenet továbbra is Groups: 992

# új process már az új group listát kapja
sudo -u lab-svc -- id
# kimenet: groups=992(lab-app),995(lab-data-read)

kill "$pid" 2>/dev/null || true
# rollback: sudo gpasswd -d lab-svc lab-data-read

A diagnosztikában ezért mindig meg kell különböztetni a névfeloldást (id lab-svc) és a futó process tényleges credentialjét (/proc/<pid>/status). A szolgáltatás újraindítása szükséges ahhoz, hogy az új supplementary group érvényre jusson; a systemd service lifecycle teljes bemutatása a d076-ban következik.

15.5.7 Sudo rule ellenőrzés konzollal

A sudo hiba nem mindig a filesystem jogosultság. A denial lehet magában a sudoers szabályban is. Hozzunk létre egy szűk szabályt:

# target: labhost01, user: labadmin; módosító
echo 'lab-dev ALL=(lab-svc) NOPASSWD: /usr/bin/cat /srv/lab-app/data/input.dat' | sudo tee /etc/sudoers.d/lab-app
sudo chmod 0440 /etc/sudoers.d/lab-app
sudo visudo -c
# rollback: sudo rm /etc/sudoers.d/lab-app

A szabályt root-ként ellenőrizzük:

# target: labhost01, user: labadmin; read-only
sudo -l -U lab-dev

Várható kimenet:

User lab-dev may run the following commands on labhost01:
    (lab-svc) NOPASSWD: /usr/bin/cat /srv/lab-app/data/input.dat

A szimulált futás lab-dev identitással:

# target: labhost01, user: labadmin, a lab-dev szimulálásához; read-only
sudo -u lab-dev -- sudo -n -u lab-svc -- /usr/bin/cat /srv/lab-app/data/input.dat
# várt: hello lab

sudo -u lab-dev -- sudo -n -u lab-svc -- /usr/bin/cat /srv/lab-app/data/other.dat
# várt: sudo: command not allowed

A sudo -n non-interaktív módban fut, így elkülöníthető a „jelszót kér” és a „tiltott” eset. A sudo -l -U csak a szabályt listázza, a tényleges futást a szimulált hívás igazolja.

15.5.8 NSS/PAM backend napló

Ha a hiba nem a fájljog, hanem a user/group feloldás vagy a PAM session, akkor a névfeloldást és a naplót is ellenőrizni kell:

# target: labhost01, user: labadmin; read-only
getent passwd lab-svc
getent group lab-data-owner
journalctl -t sshd -n 50 --no-pager | grep lab-svc
journalctl _COMM=sudo -n 50 --no-pager

A getent a NSS konfiguráción keresztül oldja fel a nevet. Ha a kimenet üres, akkor nem a fájljog a hiba, hanem a NSS backend (például sssd vagy LDAP) elérhetetlen vagy cache-elt. A PAM denial a hívó szolgáltatás naplójában jelenik meg, jellemzően sshd vagy sudo alatt. Ha a rendszer d074-ben bemutatott SSSD/LDAP backendet használ, a journalctl -u sssd -n 50 a backend oldali hibát mutatja.

A pontos naplóüzenet a distro és a PAM modulverzió függvénye, ezért a labor során mindig a tényleges üzenetet kell rögzíteni, nem a sablonból másolni.

15.5.9 Gyakori hibák és ellenpróbák

  • Csak a fájl getfacl-jét nézzük. A namei -l vagy a könyvtár getfacl nélkül a path traverse hiba láthatatlan marad. Ha a fájl ACL jó, de Permission denied, akkor a path komponensek x jogát kell ellenőrizni.
  • A chmod 777 mint „gyors megoldás”. A fájl és a könyvtár listázási jogot is kaphat, ami túl széles. A setfacl -m u:lab-svc:--x pontosabb.
  • A supplementary group változás után a futó daemon még mindig denyel. Az id lab-svc már mutatja az új csoportot, de a /proc/<pid>/status nem frissül. A folyamat restart szükséges.
  • A root deploy script owner/mode hibája. A stat kimenete bizonyíték. A javítás install -o -g -m, ne a futó szolgáltatásra tegyük a jogot chmod -R-rel.
  • A sudo jelszókérelem és a rule denial összekeverése. A sudo -n kimenete különválasztja a „password required” és a „command not allowed” esetet.

15.5.10 Feladatok

15.5.10.1 1. Feladat: Path denial magyarázó diagnózis

A labhost01 gépen a lab-svc user nem tudja olvasni a /srv/lab-app/data/input.dat fájlt. Adottak a következő tények:

  • getfacl -p /srv/lab-app/data/input.dat mutatja: user:lab-svc:r--.
  • namei -l /srv/lab-app/data/input.dat a data könyvtárnál: drwxr-x--- root lab-data-owner.
  • id lab-svc kimenete: groups=992(lab-app).

Magyarázza meg rétegenként, mi okozza a denialt. Milyen legszűkebb változtatást adna a könyvtáron, és miért nem elég a fájl chmod? Ne hajtsa végre a javítást.

15.5.10.2 2. Feladat: ACL-fixture és access smoke test

Hozza létre a laborfixture-öt a fenti lab- prefixszel. Állítsa be a desired state-et:

  • A lab-svc user olvashatja a /srv/lab-app/data/input.dat fájlt.
  • A lab-svc user traverse-elheti a /srv/lab-app/data könyvtárat.
  • A lab-svc user ne listázhassa ugyanezt a könyvtárat.

Futtasson smoke testet a három állításra. Adja meg a rollbacket és a cleanup parancsot.

15.5.10.3 3. Feladat: Umask/file owner diagnosztika és recovery

Egy deploy script root alatt futott, és létrehozta a /srv/lab-app/state/lab-app.conf fájlt umask 077 mellett. A lab-svc szolgáltatás nem tudja olvasni. Diagnosztizálja a hibát stat és sudo -u lab-svc -- test -r segítségével. Javítsa a legszűkebb módon, majd smoke testtel igazolja. A megoldásban adjon install alapú megelőzést is. Adja meg a postconditiont és a rollbacket.

15.5.11 Megoldások

15.5.11.1 1. Megoldás

A fájl ACL user:lab-svc:r-- rendben van, tehát a fájlobject szintjén a read jog megvan. A path traverse azonban a kernel VFS path resolution során minden directory komponensre x jogot követel. A /srv/lab-app/data directory drwxr-x--- root lab-data-owner, a lab-svc nem tulajdonos, nem tagja a lab-data-owner csoportnak, és az other class nem ad x-et. Ezért a kernel már a directoryn denyel, mielőtt a fájl ACL-t kiértékelné.

A legszűkebb javítás:

sudo setfacl -m u:lab-svc:--x /srv/lab-app/data

Ez csak a bejárást engedi, a listázást nem. A fájl chmod nem oldja meg a path traverse hiányát.

15.5.11.2 2. Megoldás

# target: labhost01, user: labadmin; módosító
set -euo pipefail
sudo groupadd --system lab-data-owner
sudo groupadd --system lab-app
sudo useradd --system --no-create-home --home-dir /run/lab-svc --gid lab-app lab-svc
sudo useradd --system --no-create-home --home-dir /home/lab-dev --groups lab-data-owner lab-dev
sudo mkdir -p /srv/lab-app/data
sudo chown root:lab-data-owner /srv/lab-app/data
sudo chmod 0750 /srv/lab-app/data
echo 'hello lab' | sudo install -o lab-dev -g lab-data-owner -m 0640 /dev/stdin /srv/lab-app/data/input.dat
sudo setfacl -m u:lab-svc:r-- /srv/lab-app/data/input.dat
sudo setfacl -m u:lab-svc:--x /srv/lab-app/data

# smoke test
sudo -u lab-svc -- test -r /srv/lab-app/data/input.dat && echo file-readable
sudo -u lab-svc -- test -x /srv/lab-app/data && echo dir-traversable
sudo -u lab-svc -- test -r /srv/lab-app/data || echo dir-listing-denied

Postcondition: a három ellenőrzés rendre sikeres, a harmadik dir-listing-denied üzenettel fut. Rollback az ACL eltávolítása, cleanup a lab objektumok törlése:

# target: labhost01, user: labadmin; cleanup
sudo setfacl -x u:lab-svc /srv/lab-app/data 2>/dev/null || true
sudo rm -f /srv/lab-app/data/input.dat
sudo rmdir /srv/lab-app/data 2>/dev/null || true
sudo rmdir /srv/lab-app 2>/dev/null || true
sudo userdel lab-svc
sudo userdel lab-dev
sudo groupdel lab-data-owner
sudo groupdel lab-app

15.5.11.3 3. Megoldás

Diagnózis:

# target: labhost01, user: labadmin; read-only
stat -c '%U:%G %a %n' /srv/lab-app/state/lab-app.conf
sudo -u lab-svc -- test -r /srv/lab-app/state/lab-app.conf
echo "$?"

A stat kimenete root:root 600; a test -r visszatérési értéke 1. A hiba oka: a fájl owner root, mode 600, így a lab-svc sem owner, sem group, sem other jogot nem kap.

Legszűkebb javítás:

# target: labhost01, user: labadmin; módosító
sudo chown lab-svc:lab-app /srv/lab-app/state/lab-app.conf
sudo chmod 0640 /srv/lab-app/state/lab-app.conf

# smoke test
sudo -u lab-svc -- test -r /srv/lab-app/state/lab-app.conf && echo smoke-ok

Megelőzés a jövőbeli deployhoz:

echo 'debug: sample' | sudo install -o lab-svc -g lab-app -m 0640 /dev/stdin /srv/lab-app/state/lab-app.conf

Postcondition: stat kimenete lab-svc:lab-app 640, a lab-svc olvasása sikeres. Rollback: sudo rm -f /srv/lab-app/state/lab-app.conf, majd a directory eltávolítása, ha már nem szükséges.

15.5.12 Rövid összefoglaló

A hozzáférési denial diagnosztikája rétegenként halad: NSS-feloldás, PAM/sudo authorizáció, futó process credential, majd object permission és path traverse. A fájl ACL önmagában nem elegendő, ha a könyvtár komponensen hiányzik az x jog; a bizonyíték a getfacl és a namei -l együttes kimenete. A javítás legyen a legszűkebb szükséges jog, például setfacl -m u:lab-svc:--x traverse-re, ne chmod 777. A deploy script explicit install -o -g -m paraméterrel kerülje az umask/root owner hibát. A futó process group listája startkori pillanatkép, ezért a supplementary group változás után a szolgáltatást újra kell indítani.
