37.1 Dockerfile/Containerfile és reprodukálható build

37.1.1 Motiváció

Egy C++ szolgáltatás productionbe juttatása nem ér véget a lefordított binárissal. Ha a futtató környezetet nem verziózzuk ugyanolyan szigorúan, mint a forráskódot, akkor az ABI-környezet, a shared library-k, a felhasználói azonosítók és a konfigurációs útvonalak mind eltérhetnek a fejlesztői géptől. A gyakori tünet: a bináris lokálisan tökéletesen fut, a konténerben viszont error while loading shared libraries, hiányzó libssl.so.3, megváltozott glibc, vagy éppen egy gyors javítás után percekig tartó újrabuild, mert a csomagtelepítés is újrafut. A Dockerfile/Containerfile ezt a build- és runtime-szerződést explicit, verziózott és reprodukálható artifacttá teszi.

37.1.2 Definíció és működés

OCI image alatt az OCI (Open Container Initiative) által meghatározott, rétegzett, tartalomcímezhető fájlrendszer-pillanatképekből és manifestből álló artifactot értjük. A layer egy-egy fájlrendszerbeli különbség, amelyet a Containerfile egy utasítása hoz létre. A Containerfile/Dockerfile az image buildelésének deklaratív receptje; a build context az a könyvtár, amelyet a build folyamat bemenetként lát. A digest egy tartalomra számított, rögzített azonosító, például sha256:..., amely a taggel ellentétben nem mozdul el. Reprodukálható build (reproducible build) alatt azt értjük, hogy azonos bemenetből, azonos buildelési időben vagy eltérő gépen is azonos artifact-azonosítóhoz vagy legalább azonos viselkedéshez jutunk; ehhez a gyorsan változó registry-t, csomagverziót és build-bemenetet explicit kontroll alá kell vonni.

A layer cache modellje a következő: minden utasítás bemenete egy cache key, amely az utasítás típusából, argumentumaiból, a szülő layer azonosítójából, a felhasznált build argból, valamint COPY/ADD esetén a másolt fájlok tartalom hashéből áll. Ha bármelyik bemenet megváltozik, az adott utasítástól kezdve minden downstream layer érvénytelen, és újrafut. Emiatt a COPY sorrend és a .dockerignore tartalma közvetlen buildteljesítmény- és biztonsági kérdés.

Az alapvető utasítások:

  • FROM image:tag@digest AS stage: alapréteg kiválasztása, lehetőleg digestgel.
  • ARG name=default: build-time változó; a RUN sorban használva cache-invalidációt okozhat, ha megváltozik.
  • RUN: tetszőleges parancs a layerben.
  • COPY source dest: fájl másolása a build contextből vagy korábbi stage-ből.
  • ENV key=value: runtime környezeti változó.
  • USER uid:gid: a további utasítások és a futtatási default felhasználója.
  • WORKDIR path: munkakönyvtár a további utasítások számára.

A multi-stage build két külön image-szintet választ szét: a builder stage tartalmazza a teljes fordítói eszközláncot, a fejlesztői függőségeket és a forráskódot; a runtime stage már csak a futtatáshoz szükséges shared library-ket, a binárist és a konfigurációt tartalmazza. Ez nem csak méret, hanem attack surface szempontból is szerződés: a runtime image-ben nem marad compiler, sem forrás, sem build-time secret. A d068ban tárgyalt ELF readelf -d és ldd elemzés itt válik működtetési inputtá: abból derül ki, hogy a runtime stage-be mely csomagokat kell telepíteni.

A determinisztikus input három szinten jelenik meg:

  1. Base image: a ubuntu:24.04 tag mozoghat; a ubuntu:24.04@sha256:<digest> nem. A Digeszt a lab során a registryből kell lekérdezni.
  2. Csomagtelepítés: az apt-get install -y csomag önmagában nem reprodukálható, mert a repository snapshot időben változik. Éles rendszerben csomagverzió-rögzítést, privát mirror snapshotot vagy SBOM-rögzítést kell használni. Oktatási példánkban a réteg a frissítések felvételére szolgál, de a csomag neveket és verziókat a lab aktuális kiadása szerint ellenőrizni kell.
  3. Build arg: az ARG olyan, mint egy függvényparaméter. Ha a CMAKE_BUILD_TYPE megváltozik, a RUN cmake utáni layer érvénytelen lesz – ez kívánatos is. A build argban átadott időbélyeg vagy Git rev viszont indokolatlan cache-törést okozhat, ezért az ilyen metadatot a binárisba csak explicit, verziózott módon érdemes bevezetni.

37.1.3 Kidolgozott példa

Vegyünk egy lab-cpp-service nevű C++ szolgáltatást, amelynek forrásprojektje a következőképpen épül fel:

/home/labuser/lab-cpp-service/
├── CMakeLists.txt
├── CMakePresets.json
├── .dockerignore
├── cmake/
├── include/lab-cpp-service/
└── src/

A build context a . könyvtár. A .dockerignore kizárja a helyi buildtermékeket és érzékeny fájlokat:

build/
.build/
*.o
*.so
*.a
.deb
.env
.git
.gitignore
.cache

A cél: builder stage lefordítja a szolgáltatást, runtime stage csak a szükséges artifactokat és függőségeket tartalmazza. A Containerfile:

# syntax=docker/dockerfile:1
# A digestet a lab során kell lekérdezni és behelyettesíteni.
FROM ubuntu:24.04@sha256:<ubuntu-24.04-digest> AS builder
ARG CMAKE_BUILD_TYPE=RelWithDebInfo
ARG DEBIAN_FRONTEND=noninteractive
RUN apt-get update \
 && apt-get install -y --no-install-recommends \
        build-essential cmake ninja-build pkg-config libssl-dev \
 && rm -rf /var/lib/apt/lists/*
WORKDIR /src
COPY CMakeLists.txt CMakePresets.json ./
COPY cmake/ cmake/
COPY include/ include/
COPY src/ src/
RUN cmake -S . -B /tmp/build -G Ninja \
        -DCMAKE_BUILD_TYPE="${CMAKE_BUILD_TYPE}" \
        -DCMAKE_CXX_FLAGS="-O2 -g -Wall -Wextra -Wpedantic" \
        -DCMAKE_INSTALL_PREFIX=/opt/lab-cpp-service \
 && cmake --build /tmp/build \
 && cmake --install /tmp/build

FROM ubuntu:24.04@sha256:<ubuntu-24.04-digest> AS runtime
# A libssl3t64 package nevet a lab aktuális Ubuntu 24.04 kiadása szerint ellenőrizni kell!
ARG DEBIAN_FRONTEND=noninteractive
RUN apt-get update \
 && apt-get install -y --no-install-recommends \
        ca-certificates libssl3t64 \
 && rm -rf /var/lib/apt/lists/*
RUN groupadd --system --gid 10001 lab-service \
 && useradd --system --uid 10001 --gid 10001 \
        --home-dir /opt/lab-cpp-service --create-home \
        --shell /usr/sbin/nologin lab-service
COPY --from=builder --chown=10001:10001 /opt/lab-cpp-service /opt/lab-cpp-service
USER 10001:10001
WORKDIR /opt/lab-cpp-service
ENV APP_ENV=production
ENTRYPOINT ["/opt/lab-cpp-service/bin/lab-cpp-service"]
CMD ["--config", "/opt/lab-cpp-service/etc/config.yaml"]

A build futtatása a labvm-02 gépen, labuser joggal, rootless Podman használatával:

# Előfeltétel: base image beszerzése és a tényleges digest behelyettesítése
podman pull ubuntu:24.04
podman image inspect ubuntu:24.04 --format '{{.Digest}}'

# Reprodukálható build: nem húzunk új taget, a digestet használjuk
podman build \
  --file Containerfile \
  --tag localhost/lab-cpp-service:1.0.0 \
  --target runtime \
  --build-arg CMAKE_BUILD_TYPE=RelWithDebInfo \
  --pull=never \
  /home/labuser/lab-cpp-service

Várható kimenet: a builder stage végén Successfully built, majd a runtime stage létrejötte. A rétegek vizsgálata:

podman image history localhost/lab-cpp-service:1.0.0

A historyban a builder utasításai nem jelennek meg, mert a --target runtime csak a runtime stage-et jelöli. A runtime image-ben nem lesz build-essential, cmake vagy gcc.

A futtatás ellenőrzése:

podman run --rm --user 10001:10001 \
  localhost/lab-cpp-service:1.0.0 --help

Várható kimenet a szolgáltatás Help szövege, például verzió és használati opciók. Ha a binary hiányzó shared library miatt nem indul, a podman run --entrypoint /bin/sh segítségével lehet belépni a diagnosztikához.

37.1.4 Hibák és ellenpróbák

Tünet: Bármely forráskódváltozás után a teljes csomagtelepítés újrafut, a build több perces.

Hipotézis: A COPY src/ a RUN apt-get install elé került, így minden forrásváltozás invalidálja az összes downstream layert.

Adatgyűjtés: A build naplóban megfigyelhető, hogy az apt-get install layer RUN sora CACHED helyett RUN lesz, és utána minden réteg RUN.

Egy változtatás: A Containerfile-ben a COPY CMakeLists.txt és COPY cmake/ kerüljön a csomagtelepítés elé, de a COPY src/ és COPY include/ csak utána. A build kontextusból a forrás változása így csak a forrással kapcsolatos layer-ekre hat. A csomagtelepítő réteg cache-ben marad.

Verification: Egyetlen sor módosítása után újrabuildelve a apt-get install rétegnél CACHED jelenjen meg.

Tünet: Ugyanazzal a FROM ubuntu:24.04-gyel végrehajtott build tegnap más image-digestet adott, mint ma.

Hipotézis: A tag változott a registryben, ezért az image tartalma eltolódott.

Adatgyűjtés: podman image inspect ubuntu:24.04 --format '{{.Digest}}' a build előtt és után eltérő digestet mutat.

Egy változtatás: A FROM sorba digestet kell írni: ubuntu:24.04@sha256:<digest>, és a buildet --pull=never paraméterrel kell futtatni, hogy a helyi, rögzített digestet használja.

Verification: Ugyanaz a podman build parancs azonos base digest-tel és azonos source tartalommal azonos image ID-t eredményez.

Tünet: A konténer indításkor libssl.so.3: cannot open shared object file hibával kilép, pedig a builderben lefordult a bináris.

Hipotézis: A builder stage-ben telepített libssl-dev csak a fejlesztői csomag; a runtime image-ben nem a megfelelő runtime csomag van, vagy az nincs telepítve.

Adatgyűjtés: A builder stage-ben ldd /opt/lab-cpp-service/bin/lab-cpp-service vagy readelf -d /opt/lab-cpp-service/bin/lab-cpp-service megmutatja a DT_NEEDED bejegyzéseket. A runtime image-ben podman run --rm --entrypoint /bin/sh localhost/lab-cpp-service:1.0.0 -c 'find /usr/lib -name "libssl.so*"' futtatható.

Egy változtatás: A runtime stage-be fel kell venni a szükséges runtime csomagot, például libssl3t64 (a pontos nevet az Ubuntu 24.04 csomaglistája adja). Ha a bináris más függőséget is igényel, azt is fel kell venni.

Verification: Újrabuild és podman run --rm ... --help sikeresen lefut, a ldd futtatás nélkül is elindul.

37.1.5 Feladatok

  1. Magyarázó feladat: Adott egy rossz sorrendű Containerfile, amelyben COPY . /src a WORKDIR után azonnal, a RUN apt-get install előtt szerepel. Írd le, miért invalidálódik a csomagtelepítő réteg minden forrásváltozáskor, és milyen sorrendű COPY műveletekkel lehet elérni, hogy a függőségtelepítés cache-ben maradjon. Elemezd a cache key és a tartalom hash fogalmával.

  2. Adminisztrációs/konfigurációs feladat: A fenti lab-cpp-service példaprojektben hozd létre a .dockerignore-t és a Containerfile-t, legalább builder és runtime stage-re bontva. A base image ubuntu:24.04 legyen digest-pinned. Buildeld az image-et --pull=never paraméterrel, majd futtasd --help-pel. Ellenőrizd a podman image history kimenettel, hogy a runtime image nem tartalmaz CMake/GCC csomagokat. Utána takarítsd el az image-et (csak a localhost/lab-cpp-service:1.0.0 taget).

  3. Diagnosztikai/failure/recovery feladat: A kolléga egy olyan image-et buildelt, amelyben a runtime szakasz nem telepítette a szolgáltatás egyik shared library-jét. A konténer indításakor error while loading shared libraries: libstdc++.so.6: cannot open shared object file hibát kapsz. Vedd szemügyre a builder stage binárisát a readelf -d vagy ldd parancsokkal, és határozd meg, mi lehet a hiba a runtime stage-ben. Javítsd a Containerfile-t, építsd újra, és igazold, hogy a szolgáltatás megfelelő UIDdel indul. Fogalmazz meg egy ellenőrzési lépést, amely megakadályozza, hogy a runtime dependency lista hamisan teljes legyen.

37.1.6 Megoldások

1. feladat megoldása:
A RUN cache key nem függ a build contextben lévő fájlok tartalmától; a COPY utasítás cache key viszont igen. Ha a COPY . /src a csomagtelepítő RUN elé kerül, akkor minden forrásfájl-változás megváltoztatja a másolt réteg hashét, és az összes utána következő RUN, így az apt-get install is újrafut. Ha a COPY CMakeLists.txt, cmake/ korábban, de a gyakran változó src/ és include/ később van, akkor a csomagtelepítő réteg a forrásváltozásoktól függetlenül CACHED maradhat. A cache key a szülő layer digest, az utasítás típusa, argumentumai, a build arg értékei és a másolt tartalom hash alapján számítódik.

2. feladat megoldása:
A .dockerignore a build/, .git/, *.o, *.so, *.a, .env bejegyzéseket tartalmazza. A Containerfile a fenti példa alapján készül. A build parancs:

podman build --file Containerfile --tag localhost/lab-cpp-service:1.0.0 \
  --target runtime --build-arg CMAKE_BUILD_TYPE=RelWithDebInfo --pull=never .

Az image historyban a build-essential vagy cmake réteg nem szerepel; a futtatás --help-pel sikeres. A cleanup:

podman rmi localhost/lab-cpp-service:1.0.0

A postcondition: az image eltávolítva, a builder alatt létrejött ideiglenes stage nem marad meg.

3. feladat megoldása:
A builder binárison futtatott readelf -d /opt/lab-cpp-service/bin/lab-cpp-service | grep NEEDED és ldd megmutatja, hogy a bináris libstdc++.so.6-ot igényel. A hiba akkor léphet fel, ha a runtime stageben a COPY --from=builder után nem a megfelelő libstdc++6 csomag van telepítve, vagy ha a runtime base image nem tartalmazza az alap C++ runtime-ot. Feltéve, hogy a runtime image ubuntu:24.04, a libstdc++6 alapból jelen van; a hiba valószínűbb oka, hogy a szolgáltatás olyan RPATH-tal rendelkezik, amely a builder stage /usr/lib/x86_64-linux-gnu útvonalára mutat, de a runtime image-ben nem létezik, vagy a LD_LIBRARY_PATH rossz. A javítás: a Containerfile-ben ne használj fejlesztői RPATH-t; a runtime legyen kompatibilis a libstdc++6 elérhetőségével, vagy telepíts libstdc++6-ot explicit módon. Az ellenőrző lépés: a build után podman run --rm --entrypoint /bin/sh localhost/lab-cpp-service:1.0.0 -c 'ldd /opt/lab-cpp-service/bin/lab-cpp-service' és minden DT_NEEDED elemre van elérhető fájl.

37.1.7 Rövid összefoglaló

A Dockerfile/Containerfile a C++ szolgáltatás build- és runtime-szerződését rögzíti. A multi-stage build elválasztja a teljes toolchainnel rendelkező builder imageet a minimális runtime image-től, amit a d068 ELF dependency elemzése alapján lehet pontosan méretezni. A layer cache kulcsa az utasítás bemenetére épül; a COPY sorrend és a .dockerignore a build gyorsaságát és reprodukálhatóságát is meghatározza. A base image tag helyett digest-pin, a csomagverziók rögzítése és a build arg explicit kontrollja ad determinisztikus inputot; a registry- és csomagfrissítési politika a rebuild-trigger. A hibakeresés a réteg-cache, a digest és a runtime dependency háromszögében mozog: tünetből hipotézis, egy változtatás, verifikáció.

Továbbhasznált definíciók: Layer – egy utasítás által létrehozott, tartalomcímezhető fájlrendszerbeli különbség; digest – tartalomra számított, rögzített artifact-azonosító; multi-stage build – builder és runtime stage szétválasztása minimalisztikus futtatóképpel.
