14.1 apt/dpkg és rpm/dnf működési modell

14.1.1 Motiváció

Szenior C++ fejlesztőként a saját binárisoddal együtt könyvtárfüggőségeket is szállítasz: ha a libstdc++.so.6 soname-t hivatkozod, a hoszton ezt egy adott csomagverzió biztosítja, adott ABI-szinttel. A Linux hoszt üzemeltetésekor nem elég a forrásból buildelt artifact: a disztribúció csomagkezelője a teljes telepített rendszer verzió-, fájl- és szkript-állapotát követi. Ez az alfejezet a két meghatározó család, az apt/dpkg és az rpm/dnf rétegeit, a repository metadata és a helyi package database közötti különbséget, valamint a konfigurációs fájl és maintainer szkript felelősségét tanítja.

14.1.2 Definíció és működés

14.1.2.1 High-level resolver és low-level package database

A Linux csomagkezelés általában két rétegre válik szét. A high-level resolver repository metadata és policy alapján függőséget old fel, csomagot tölt le, sorrendez és hívja a low-level eszközt. A low-level package database a telepített csomagok helyi állapotát, fájllistáját, conffile-jait és maintainer szkriptjeit tárolja, és a tényleges install/remove műveletet végzi.

Csomagcsalád High-level resolver Low-level tool Helyi állapot DB Package formátum Repository konfiguráció
Debian/Ubuntu apt, apt-get dpkg /var/lib/dpkg/status, /var/lib/dpkg/info/ .deb (ar archive) /etc/apt/sources.list, /etc/apt/sources.list.d/*
RHEL/Fedora dnf (régebben yum) rpm /var/lib/rpm/ .rpm (cpio + header) /etc/yum.repos.d/*.repo

Az apt a Packages/InRelease fájlokat letölti, indexeli, és az apt-cache policy ebből számítja a candidate verziót. Az rpm a repository repomd.xml metaadatát használja a dnf resolver alatt.

14.1.2.2 Version, architecture és dependency

Egy csomag azonosítója a name, version, release/revision és architecture együttese. Debianban például a libc6 csomag version mezője gyakran distro revisiont is tartalmaz; architecture: amd64, arm64, i386, all. RPM-ben: x86_64, aarch64, noarch. A Provides virtuális csomagnévvel a resolver kielégíthet alternatívákat, például mail-transport-agent.

A dependency lehet:

  • Depends: kötelező, hiány esetén a csomag nem konfigurálható.
  • Recommends: alapértelmezetten telepítendő, de --no-install-recommends opcióval elhagyható.
  • Suggests: opcionális, nem automatikus.
  • Breaks/Conflicts: összeférhetetlenség.

RPM-ben a Requires, Recommends és Suggests hasonló; a Requires(pre) azt jelöli, hogy a függőség már a scriptlet előtt jelen kell legyen.

14.1.2.3 Package file owner és config file

A low-level database nyilvántartja, hogy egy fájl melyik csomaghoz tartozik, és egy konfigurációs fájl conffile-e. A módosított conffile frissítéskor nem kerül csendben felülírásra: a csomagkezelő három irányú merge-et vagy promptot kínál, mert a lokális operátori állapot a desired state-től eltérő observed state lehet. A nem konfigurációs fájlok módosítása viszont elveszhet a csomagfrissítéskor, ezért a konténer- és IaC-felfogásban immutábilis réteget és külön szerződött adatkönyvtárat használunk.

14.1.2.4 Maintainer script/trigger és service restart

A csomagok maintainer szkriptjei a telepítési folyamat hookjai:

  • Debian .deb: preinst, postinst, prerm, postrm.
  • RPM: %pre, %post, %preun, %postun.

A postinst gyakran deb-systemd-invoke restart vagy systemctl preset segítségével kezeli a systemd unitot. A trigger egy feldolgozási halasztás, tipikusan ldconfig vagy install-info futtatása az összes csomag befejezése után. A csomagfrissítés service restartja nem univerzális garancia: a csomag policy és a maintainer script, illetve az operátor systemd unit state dönti el.

14.1.2.5 Atomic/transactional distro kitekintés

A klasszikus csomagfrissítés fokozatos, ezért egy megszakított tranzakció részben konfigurált állapotot hagyhat. Az rpm család régen is tranzakció-központúbb; a modern image-based disztribúciók (például rpm-ostree, Fedora CoreOS) egy új, teljes root filesystem generációt állítanak elő, és boot-time atomikusan váltanak. Ez nem a hagyományos dpkg/apt path, de üzemeltetési szempontból hasznos a rollback és immutability megértéséhez.

14.1.3 Kidolgozott példa

Target: labhost01, Ubuntu Server 24.04 LTS amd64; felhasználó: labuser; sudo jogosultság.

Először frissítjük a repository metadata indexét. Ez nem telepít csomagot, de módosítja a /var/lib/apt/lists tartalmát, ezért sudo szükséges.

# target: labhost01, labuser, sudo
sudo apt update

Várható, illusztratív kimenet: a noble, noble-updates, noble-security repositoryk InRelease fájljai Fetched-ként jelennek meg, hash-ellenőrzés után.

Ellenőrizzük a repository által kínált candidate verziót és a telepített állapotot:

apt-cache policy libc6
dpkg-query -W -f='${Package} ${Version} ${Architecture}\n' libc6

Várt kimenet (a verziószám aktuális ellenőrzést igényel):

libc6:
  Installed: 2.39-0ubuntu8.4
  Candidate: 2.39-0ubuntu8.4
  Version table:
 *** 2.39-0ubuntu8.4 500
        500 http://archive.ubuntu.com/ubuntu noble-updates/main amd64 Packages
...

Ez mutatja, hogy a repository metadata és a telepített csomag verziója egyezik. A libc6 package tulajdonolja a core shared library fájlt:

dpkg -L libc6 | grep '/lib/x86_64-linux-gnu/libc.so.6$'
dpkg -S /usr/bin/bash

Várt kimenet:

/lib/x86_64-linux-gnu/libc.so.6
bash: /usr/bin/bash

Az első parancs a csomag fájllistájából mutatja a tulajdonolt fájlt; a második a fordított lekérdezés: a path-hoz tartozó csomag.

Konfigurációs fájl esetén megnézzük a login csomag conffile-jait:

dpkg-query -W -f='${Conffiles}\n' login

Várt kimenet illusztráció szerint: /etc/login.defs valamint az aktuális MD5 hash. Ez a hash jelzi a package által ismert original state-et; ha a lokális fájl módosult, a csomagkezelő ezt felismeri.

RHEL-családon a példaprofil külön host lenne; a modell parancsok ott:

# Külön RHEL-család példaprofil, nem az Ubuntu labhoston
rpm -q --qf='%{NAME}-%{VERSION}-%{RELEASE}.%{ARCH}\n' nginx
rpm -qf /etc/ssh/sshd_config

14.1.4 Hibák és ellenpróbák

Tünet: dpkg -i csomag.deb után a csomag unpacked, de nem installed, mert a függősége hiányzik. Hipotézis/adatgyűjtés: dpkg-query -W -f='${Status}\n' csomag és apt-get -s install csomag. Egy változtatás: fusson sudo apt-get -f install, ami a resolverrel pótolja a low-level dependencyt. Verification: dpkg-query -W -f='${Status}\n' install ok installed; majd dpkg --configure -a üres.

Tünet: apt-get install régi verziót kínál. Ok: elavult repository metadata. Javítás: sudo apt update előbb; utána apt-cache policy csomag candidate verziója megváltozik.

Tünet: apt-get install zlib1g:i386 hibát ad. Ok: a multiarch architecture nincs engedélyezve: dpkg --print-foreign-architectures nem tartalmazza az i386-et. Javítás: engedélyezés után wasm? Nem, processzor-architektúra. Elkerülendő a felesleges engedélyezés.

14.1.5 Feladatok

  1. Magyarázó feladat. Az Ubuntu labhoston az /etc/ssh/sshd_config fájl melyik csomaghoz tartozik, és conffile-e? A konfigurációs állapot módosult-e a csomag adatbázisához képest? Add meg a lekérdezés parancsát, és értelmezd a kimenetet.

  2. Adminisztrációs feladat. Telepítsd a dstat csomagot a labhoston (mindig explicit target, sudo). Ellenőrizd a telepített verziót és a függőségeket. Majd rollbackként távolítsd el a csomagot a konfigurációjával együtt.

  3. Diagnosztikai feladat. Szimulálj félbeszakadt installt: sudo dpkg --unpack egy .deb-et, majd próbáld meg apt-get install-tel rendezni a függőséget. Mit mond a dpkg --audit? Milyen sorrendben futtatod a dpkg --configure -a és/vagy apt-get -f install parancsot? Mi a postcondition?

14.1.6 Megoldások

  1. A dpkg -S /etc/ssh/sshd_config parancs a openssh-server csomagot adja. Conffile ellenőrzés: dpkg-query -W -f='${Conffiles}\n' openssh-server | grep sshd_config. Ha a hash különbözik, a helyi fájl módosult. Postcondition: nincs rendszermódosítás, csak diagnózis.

  2. Telepítés: sudo apt-get update && sudo apt-get install -y --no-install-recommends dstat. Ellenőrzés: dpkg-query -W -f='${Version}\n' dstat, függőségek: apt-cache depends dstat. Rollback: sudo apt-get remove -y --purge dstat, majd dpkg-query -W -f='${Status}\n' dstat üres/deinstalled. Postcondition: nincs dstat csomag és nincs saját config a hoszton.

  3. A dpkg --unpack után a csomag half-installed állapotban van, a dpkg --audit felsorolja. Először sudo apt-get -f install történjen, hogy a resolver letöltse a hiányzó függőséget, majd sudo dpkg --configure -a minden függő csomagot konfigurál. Postcondition: dpkg --audit üres, minden érintett csomag install ok installed.

14.1.7 Rövid összefoglaló

A csomagkezelő két rétege a repository metadata alapján dolgozó high-level resolver (apt/dnf) és a helyi telepített állapotot kezelő low-level package database (dpkg/rpm). A repository metadata a letölthető verziókat, a package database a telepített verziót, architektúrát, fájllistát, conffile-t és maintainer szkripteket követi. A dpkg/rpm klasszikus tranzakciója fokozatos, ezért hibás megszakítás esetén dpkg --audit, dpkg --configure -a és apt-get -f install juttat konzisztens állapotba. Az image-based kiadások ezt atomi root generációval váltják ki.

Továbbhasznált definíciók:

  • Repository metadata: a csomagrepository által aláírt, indexelt leírása az elérhető csomagok verziójának, architektúrájának és függőségeinek.
  • Package database: a low-level tool helyi állapota a telepített csomagokról, fájllistáról, conffile-okról és maintainer szkriptekről.
  • Conffile: olyan konfigurációs fájl, amelyet a csomag tulajdonol, de a helyi operátori módosítást a csomagfrissítés nem írja felül automatikusan.
