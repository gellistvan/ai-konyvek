43.1 Clusterprofil, bootstrap és HA topológia

43.1.1 Motiváció

A d167-ben felépített libvirt-KVM laborban egyetlen VM indítása jól kontrollálható. Egy Kubernetes cluster viszont több node-ból, közös control plane-ből, etcd-ből, load balancerből, CNI/CSI/DNS addonból és csatlakoztatott credentials-ekből áll. Ha ezeket ad hoc módon, dokumentálatlan verziókkal bootstrapeljük, akkor az első upgrade vagy control-plane node kiesés olyan unknown-unknown hibát hoz, amelyet a szenior C++ fejlesztő a build/dependency világából “dependency hell”-ként ismer. A clusterprofil ezért nem egy telepítési jegyzet, hanem a clusster desired state leírása: verzió, runtime, cgroup, network, storage, topology, failure domain és credential lifecycle. A d210-ben megismert RBAC/admission biztonsági rétegek csak akkor működnek, ha ez a profil előre rögzített, auditálható és reprodukálható.

43.1.2 Definíció és működés

A clusterprofil az a verziózott, géppel olvasható vagy explicit dokumentált leírás, amely egy Kubernetes cluster összes komponensének kiadását, konfigurációját, hálózati címtartományait, csomópontjait és failure domain hozzárendelését rögzíti. A bootstrap az a folyamat, amelyben üres, előkészített Linux node-okból control plane és worker node-ok, majd működő cluster lesz. A HA control plane olyan topológia, amelyben a kube-apiserver és az etcd több node-on fut, és a többségi quorum megtartása mellett egy node kiesése nem állítja le az API-t.

Két alapvető üzemeltetési modell létezik:

  • Self-managed (például kubeadm): a cluster tulajdonosa telepíti, frissíti és menti az etcd-et, a control plane komponenseket és a node-okat. Teljes kontroll, cserébe a control plane, certifikátumok, etcd backup/restore és verzióskew is a mi felelősségünk.
  • Managed (felhőszolgáltató Kubernetes API-ja): a cloud provider a control plane-t és az etcd-et menedzseli, a felhasználó node-okat, workload-ot, CNI/CSI és policy összeállítást üzemeltet. A managed nem jelenti azt, hogy nincs verzió- és addon-kompatibilitási feladat, csak a felelősségi határ máshol van.

A version skew a Kubernetes komponensek megengedett maximális verzióeltérése. A gyakorlatban a kubelet nem lehet újabb a kube-apiservernél, és legfeljebb pár minor verzióval lehet régebbi; a kubeadm, kubectl, kubelet és apiserver közötti megengedett eltérést a hivatalos support matrix rögzíti. A container runtime (például containerd) és a CNI/CSI plugin verzióját ugyanígy kezelni kell: egy új Kubernetes minor gyakran újabb runtime- vagy CNI-verziót követel, így a profilba a teljes support mátrix beletartozik, nem csak a v1.X.Y string.

A laborban kubeadm self-managed clustert használunk, mert a cél a látható rétegek tanulása; felhőben a managed control plane fekete dobozként viselkedne.

43.1.3 Kidolgozott példa

A labor célja egy 3 control-plane + 1 worker node-os HA topológia egyetlen libvirt hoston. A példa verziói hipotetikusak; a tényleges laborban a hivatalos Kubernetes, containerd, CNI és Linux kernel support mátrixot ellenőrizni kell. A példában a v1.31.0 jelölésű verziót használjuk.

Labtopológia és failure domain

Név Szerep IP vCPU/RAM/disk (lab illusztratív) Failure domain
lab-lb kube-apiserver LB (DNS) 10.42.0.10 2/2 GiB/20 GiB labhost1
lab-cp1 control plane + etcd tag 10.42.0.11 2/4 GiB/40 GiB labhost1
lab-cp2 control plane + etcd tag 10.42.0.12 2/4 GiB/40 GiB labhost1
lab-cp3 control plane + etcd tag 10.42.0.13 2/4 GiB/40 GiB labhost1
lab-worker1 worker 10.42.0.21 2/4 GiB/40 GiB labhost1

A laborban minden node ugyanazon a libvirt hoston fut, ezért a fizikai failure domain közös: egy host újraindítás vagy tápkimaradás az összes node-ot érinti. Ez a laborra elfogadható, de productionben a control plane node-okat külön rackbe, switchbe és tápkörbe kellene tenni, az etcd quorum miatt legalább három node-ot. A dokumentáció lab-lb.lab nevet 10.42.0.10 IP-re mutató lab DNS-rekordként feltételezzük; ennek hiányában a node-ok /etc/hosts bejegyzése is elegendő.

1. Közös host-prerekvizitek minden node-on

# Target: lab-cp1, lab-cp2, lab-cp3, lab-worker1
# UID: root (sudo); minden módosító parancs lab előtti állapotból indul
sudo modprobe overlay
sudo modprobe br_netfilter
printf 'overlay\nbr_netfilter\n' | sudo tee /etc/modules-load.d/k8s.conf
printf 'net.ipv4.ip_forward = 1\nnet.bridge.bridge-nf-call-iptables = 1\n' \
  | sudo tee /etc/sysctl.d/99-kubernetes.conf
sudo sysctl --system

A bridge-nf-call-iptables régebbi kernelben szükséges, modern nftables/i iptables-nft esetén is megőrizzük, mert a pod network bridge-n átmenő forgalmat a netfilternek látnia kell. A cgroup v2 ellenőrzése:

# Target: minden node (root)
stat -fc %T /sys/fs/cgroup/
# Várt (Linux 5.8+ default): cgroup2fs

2. Container runtime és kubeadm binárisok telepítése

A pontos apt repository, GPG key és csomagverzió a hivatalos Kubernetes dokumentációból ellenőrizendő; itt a parancs a telepítési modellt mutatja:

# Target: minden node (root)
K8S_VERSION=v1.31.0            # hipotetikus labverzió, ellenőrizendő
sudo apt-get update
sudo apt-get install -y containerd kubelet kubeadm kubectl
sudo apt-mark hold containerd kubelet kubeadm kubectl

A containerd rendszerszintű cgroup driverét systemd-re állítjuk, mert a kubelet is systemd cgroup driverrel fut:

# Target: minden node (root)
sudo mkdir -p /etc/containerd
containerd config default | sudo tee /etc/containerd/config.toml >/dev/null
sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml
sudo systemctl restart containerd

A sed itt illusztratív és törékeny; productionben a teljes containerd konfigurációt a clusterprofil részeként kell verziózni.

3. Bootstrap profil a kubeadm számára

# cluster-profile.yaml
# Cél: lab-cp1; nem közvetlenül éles klaszterre, a verziók ellenőrizendők
apiVersion: kubeadm.k8s.io/v1beta3
kind: ClusterConfiguration
kubernetesVersion: v1.31.0
controlPlaneEndpoint: "lab-lb.lab:6443"
networking:
  podSubnet: "10.244.0.0/16"
  serviceSubnet: "10.96.0.0/12"
apiServer:
  certSANs:
    - "lab-lb.lab"
---
apiVersion: kubeadm.k8s.io/v1beta3
kind: InitConfiguration
nodeRegistration:
  name: "lab-cp1"
  kubeletExtraArgs:
    cgroup-driver: "systemd"

Az első control plane inicializálása:

# Target: lab-cp1 (root)
sudo kubeadm init \
  --config=cluster-profile.yaml \
  --upload-certs

A --upload-certs segítségével a második és harmadik control plane node a kubeadm join --control-plane --certificate-key úton kapja meg a control plane certifikátumokat. A várt kimenet tartalmazza a kubeadm join parancsot a worker és a control plane node-ok számára, valamint azt, hogy a cluster inicializálása sikeres volt.

4. Admin kubeconfig és CNI

# Target: lab-cp1, user labuser (UID 1000)
mkdir -p "$HOME/.kube"
sudo cp /etc/kubernetes/admin.conf "$HOME/.kube/config"
sudo chown "$(id -u):$(id -g)" "$HOME/.kube/config"

A pod network addon nélkül a node-ok NotReady állapotban maradnak, a CoreDNS pod Pending lesz. A CNI manifest kiválasztása a clusterprofil része; a laborban a CNI dokumentációjában szereplő, pinned verziójú manifestet használjuk:

# Target: lab-cp1, context lab-cluster
kubectl apply -f lab-cni.yaml

A lab-cni.yaml a kiválasztott CNI (például Calico, Cilium vagy Flannel) hivatalos manifestje. A pod CIDR-t ehhez igazítottuk (10.244.0.0/16). A CNI telepítése után várható:

kubectl get nodes
# Várt: lab-cp1 Ready, age < 5 perc
kubectl get pods -n kube-system
# Várt: coredns Running, calico/cilium/flannel podok Running

5. Control plane és worker join

A második control plane node:

# Target: lab-cp2 (root)
sudo kubeadm join lab-lb.lab:6443 \
  --token <token> \
  --discovery-token-ca-cert-hash sha256:<hash> \
  --control-plane \
  --certificate-key <key>

A <token>, <hash> és <key> a kubeadm init kimenetéből származik; a token 24 óra TTL-t kap, a certificate key rövid életű. A lab-cp3 join ugyanígy történik. A worker join:

# Target: lab-worker1 (root)
sudo kubeadm join lab-lb.lab:6443 \
  --token <token> \
  --discovery-token-ca-cert-hash sha256:<hash>

Végső ellenőrzés:

# Target: lab-cp1, context lab-cluster
kubectl get nodes -o wide
# Várt: 4 Ready node, a control-plane node-okon control-plane role
kubectl get endpoints -n default kubernetes
# Várt: 10.42.0.11:6443,10.42.0.12:6443,10.42.0.13:6443

A control-plane endpoint (lab-lb.lb:6443) a node-ok kubeconfigjában marad, de a kube-apiserver certifikátum SAN listája tartalmazza a lab-lb.lab nevet, így a TLS-verification akkor is működik, ha a load balancer valamelyik control-plane node IP-jére mutat.

43.1.4 Hibák és ellenpróbák

Tünet: A kubeadm init leáll, mert a kubelet nem tudja elindítani a control plane podjait.
Hipotézis: A containerd cgroup driver SystemdCgroup beállítása nem került érvényesítésre.
Adatgyűjtés: sudo journalctl -u kubelet -n 50 --no-pager és crictl ps -a.
Egy változtatás: sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml && sudo systemctl restart containerd.
Verifikáció: sudo crictl ps mutatja a futó kube-apiserver, etcd, controller-manager, scheduler konténereket.

Tünet: A node NotReady, a CoreDNS pod Pending.
Hipotézis: A CNI addon nem települt, vagy rossz pod CIDR-t adtunk.
Adatgyűjtés: kubectl describe node lab-cp1 | grep NetworkReady, kubectl get pods -n kube-system.
Egy változtatás: A clusterprofilban rögzített CNI manifest alkalmazása (kubectl apply -f lab-cni.yaml).
Verifikáció: A NetworkReady condition True, a CoreDNS pod Running.

Tünet: A kubeadm join lefut, de a node nem jelenik meg a kubectl get nodes listában.
Hipotézis: A bootstrap token lejárt, vagy a discovery CA hash nem egyezik.
Adatgyűjtés: kubeadm token list az első control plane-on, openssl x509 -in /etc/kubernetes/pki/ca.crt -sha256 -noout -fingerprint.
Egy változtatás: Új token és hash generálása: sudo kubeadm token create --print-join-command, majd a worker node-on az új paranccsal join.
Verifikáció: A node kubectl get nodes kimenetben megjelenik, és a kubelet a join után regisztrálja magát.

Tünet: etcd quorum hiba a második control plane join után.
Hipotézis: A control plane node-ok között hálózati packet loss vagy az etcd peer URL téves; a 3 node egyike még a régi, egyedülálló etcd cluster tagja.
Adatgyűjtés: sudo crictl logs <etcd-container>, journalctl -u etcd vagy kubectl logs -n kube-system etcd-lab-cp1.
Egy változtatás: Ellenőrizni a --etcd-servers/--initial-cluster paramétereket a kubeadm configban, majd a sérült etcd tag újraindítása vagy a kubeadm reset után újrajoin.
Verifikáció: kubectl get pods -n kube-system minden etcd pod Running, az API elérhető a lab-lb.lab:6443 endpointon.

43.1.5 Feladatok

  1. Magyarázó feladat: Miért van szükség legalább három etcd tagra a HA control plane-ben, és miért nem elég két node? Milyen különbség van a stacked és az external etcd topológia között a bootstrap, backup és failure domain szempontjából? Indokolja a labor topológiáját.

  2. Konfigurációs feladat: A labhoston építsen egy új, önálló HA clustert a fenti topológia szerint. Készítse el a cluster-profile.yaml profilt, futtassa a host-prerekviziteket, a kubeadm init-et, a CNI telepítést, majd csatlakoztassa a második és harmadik control plane node-ot, végül egy worker node-ot. Adja meg a szükséges parancsokat, és írja le az expected postcondition-t.

  3. Diagnosztikai/failure feladat: A clusterben a lab-worker1 node hirtelen NotReady lett, és a kubectl describe node lab-worker1 azt mutatja, hogy a kubelet leállt. A node-ot újraindították, de a kubelet nem indul el, mert a CA tanúsítvány és a bootstrap credential érvénytelenné vált. Hogyan állítja helyre a node-ot anélkül, hogy a többi node-ot vagy az API-servert bántaná? Írja le a diagnosztikai lépéseket, a helyreállítást és a postcondition-t.

43.1.6 Megoldások

  1. Az etcd Raft-konzisztens, ezért a quorum (többség) eléréséhez páratlan számú tag szükséges. Két node esetén egy node kiesése nem ad többséget, így a cluster nem tud commitolni, az API nem működik. Három node esetén egy kiesés is megtartja a quorumot (2/3), ez a minimális production HA. A stacked topológiában az etcd a control plane node-okon fut, így kevesebb VM/operációs cost, de a kube-apiserver és az etcd failure domainje közös. Az external etcd külön node-okon fut, így a control plane és az etcd karbantartása függetlenül ütemezhető, de több node-ot kell üzemeltetni. A laborban stacked topológiát használunk, mert a cél az oktatás és a minimális erőforrás; productionben az etcd disk I/O és a control plane CPU-ról külön failure domainbe érdemes tenni.

  2. A parancsok a fenti kidolgozott példában szerepelnek. A várható postcondition: mind a 4 node Ready; kubectl get pods -n kube-system minden pod Running; a kubernetes service endpoints három control-plane IP-t tartalmaz; a kubectl get cs vagy az API health endpoint 200-at ad; a cluster profil YAML a git repóban van, és kubectl version --output=yaml megadja a kubelet/apiserver verzióját.

  3. A node újraindítása után a kubelet nem indul, ha a /etc/kubernetes/kubelet.conf érvénytelen, vagy a bootstrap token lejárt. Diagnosztikai lépések: a worker node-on journalctl -u kubelet -n 100; ha a hiba Unauthorized vagy x509: certificate signed by unknown authority, akkor a CA cert nem érvényes. Helyreállítás: a worker node-on sudo kubeadm reset --force (csak a saját lab-worker1 node-on), majd az API-servertől új token kérése: az első control plane-on sudo kubeadm token create --print-join-command, és a worker node-on az új paranccsal sudo kubeadm join. Postcondition: a node újra regisztrálódik, Ready lesz, és a korábbi podok a scheduler újraütemezése után futnak, a többi node változatlan.

43.1.7 Rövid összefoglaló

A Kubernetes clusterprofil a verzió, runtime, cgroup, network, storage, topology és credential lifecycle együttes desired state-je. Self-managed kubeadm esetén a control plane, etcd, certifikátumok és version skew a cluster üzemeltetőjének felelőssége; managed Kubernetes ezt a control plane-t kimozgatja, de a node-ok, addonok és policy továbbra is a felhasználóé. A HA control plane legalább három etcd tagot igényel, páratlan quorummal. A bootstrap során a CNI hiánya blokkolja a DNS-t, a cgroup v2 és a systemd cgroup driver mismatch pedig a kubelet indítását. A clusterprofil legyen géppel olvasható, és a certifikátum-, token- és node-életciklus minden lépését rögzítse.

Továbbhasznált definíciók: Clusterprofil — verziózott leírás egy Kubernetes cluster kívánt állapotáról. Version skew — a Kubernetes komponensek megengedett maximális verzióeltérése. HA control plane — olyan control-plane/etcd topológia, amely egy node kiesését is elviseli többségi quorummal.
