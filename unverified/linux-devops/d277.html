56.2 CI image, Helm/Kustomize és GitOps delivery

A d240 pipeline outputja egy natív C++ release artifact és egy container image, de a deployment szempontjából a tag nem identitás. A d277 célja, hogy a konténerartifactot változatlan digesttel vigye végig a környezeteken, és minden lépéshez mérhető bizonyítékot kapcsoljon. A fejlesztői szempont ismerős: ha egy release buildet minden környezetre újrafordítanánk, az olyan, mintha egy megosztott könyvtárnak minden fogyasztónál más-más build-id-je lenne; a diagnosztika, a visszafejtés és a rollback is megszűnik reprodukálhatónak lenni.

56.2.1 Definíció és működés

A delivery lánc itt a natív build/bináris artifact előállításától a futó podig terjed. A cél egy olyan bizonyítéklánc, amely megválaszolja: milyen forrásból, milyen bemenetekkel, milyen tesztekkel, melyik image digestből és milyen environment konfigurációval lett a clusterben ténylegesen futó processz.

A kulcsfogalmak:

  • Immutable artifact promotion: az artifact egy tartalomalapú azonosítóval — itt container image digest, a natív binárisnál a tartalom SHA-256 és a build-id — utazik a környezetek között. A tag csak emberi név, a digest a hivatkozás.
  • GitOps reconcile: a cluster desired state-ét egy Git repository tartalmazza, a GitOps agent pedig folyamatosan kiegyenlíti az observed state-et a desired state-hez. A kézi kubectl apply nem része a promotionnek.
  • Release evidence: a kiadást leíró, verziózott, lehetőleg aláírt bizonyítékcsomag; tartalmazza a source revisiont, pipeline futást, binary hasheket, SBOM-ot, attestationt, rendered manifest digestet, policy validation eredményt és rollout eredményt.
  • Data-compatible rollback: olyan visszaállítás, ahol a régebbi bináris a jelenlegi adat- és konfigurációformátumot még kezelni tudja. A config migration ezért expand/contract mintát igényel: az új kód először olvassa a régi formátumot, a régi kódot addig nem cseréljük le, amíg minden új fogyasztó stabil nem lett.

A lánc lépései:

  1. Native test/build/image pipeline: a forrásrevisionből egyetlen Linux amd64 release binárist készítünk, teszteket és sanitizer vizsgálatot futtatunk. A binárist tömörített archívumba csomagoljuk, és SHA-256-tal azonosítjuk. A build rögzíti a build-id-t, a libc és a linker környezetet, mert egy natív C++ service ABI-függőségei a konténer runtime image-től is függenek.
  2. SBOM, digest, attestation és registry: a konténer build ugyanezt a binárist helyezi egy minimal runtime rétegbe. A build nem második fordítást végez, hanem artifactot telepít. A registry-be push során a rendszer SBOM-ot (software bill of materials) és provenance attestationt készít. A promotion hivatkozás mindig @sha256:... formátumú.
  3. Rendered manifest/policy validation: a Helm chart vagy Kustomize overlay a környezeti values-szal rendered manifestet állít elő. Ezt API séma-szinten (kubeconform) és policy-szinten (conftest, OPA/Gatekeeper) ellenőrizzük, még a GitOps sync előtt.
  4. GitOps reconcile és environment promotion: a promotion nem közvetlen cluster művelet, hanem Git commit a megfelelő environment path-on. A staging sikeres kiértékelése után ugyanaz az image digest jelenik meg a prod desired state-ben.
  5. Probe, rollout, PDB, canary: a Deployment rolling update során readiness/liveness probe-okkal, PodDisruptionBudgettel és opcionálisan canary lépésekkel biztosítjuk, hogy a forgalom csak egészséges podokra kerüljön. A canary részletes gyakorlatát a Progressive delivery és recovery labor tartalmazza.
  6. Release evidence és config migration: a kiadás csak akkor nevezhető késznek, ha a release evidence fájl létrejött, és a configVersion váltás kompatibilitási feltételeit ellenőriztük.

56.2.2 Kidolgozott példa

A példa labtargetjei: gitops-lab-control (UID 1000), cluster context lab-staging, később lab-prod, namespace lab-payment, Argo CD app lab-payment-staging. A service neve payment-srv, a repository platform-deploy. A product repository payment-srv tartalmazza a C++ forrást és a pipeline-t. A dummy digestek helyettesítők; a laborban a tényleges pipeline generálja őket.

A natív CI pipeline releváns része (nem futtatott minta):

name: release-payment-srv
on:
  push:
    tags: ["release/payment-srv/*"]
permissions:
  contents: read
  id-token: write
jobs:
  build-test:
    runs-on: ubuntu-24.04 # lab-fixture: runner verzió rögzítendő
    steps:
      - uses: actions/checkout@lab-pinned-checkout
      - name: cache dependency fixture
        uses: actions/cache@lab-pinned-cache
        with:
          path: .cache
          key: payment-srv-fixture-${{ hashFiles('fixtures/**') }}
      - name: configure
        run: |
          cmake -S . -B build \
            -DCMAKE_BUILD_TYPE=RelWithDebInfo \
            -DPAYMENT_PLATFORM=linux-amd64 \
            -DPAYMENT_ENABLE_SANITIZERS=ON
      - name: build
        run: cmake --build build --target payment-srv
      - name: test
        run: ctest --test-dir build --output-on-failure
      - name: package binary
        run: |
          tar --zstd -cf build/payment-srv-linux-amd64.tar.zst \
            -C build/bin payment-srv
          sha256sum build/payment-srv-linux-amd64.tar.zst \
            > build/payment-srv-linux-amd64.tar.zst.sha256
      - name: store binary artifact
        uses: actions/upload-artifact@lab-pinned-upload
        with:
          name: payment-srv-linux-amd64
          path: build/payment-srv-linux-amd64.tar.zst
          retention-days: 14
  image:
    needs: build-test
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@lab-pinned-checkout
      - name: build and push image
        env:
          IMAGE: ghcr.io/lab-org/payment-srv
        run: |
          docker buildx build \
            --platform linux/amd64 \
            --sbom=true \
            --provenance=mode=min \
            -t "${IMAGE}:v0.4.2" \
            --push .
      - name: resolve digest
        env:
          IMAGE: ghcr.io/lab-org/payment-srv
        run: |
          digest="$(docker buildx imagetools inspect "${IMAGE}:v0.4.2" \
            --format '{{ .Manifest.Digest }}')"
          {
            echo "IMAGE_DIGEST=${digest}"
            echo "IMAGE_REF=${IMAGE}@${digest}"
          } >> "${GITHUB_ENV}"
      - name: sign image
        env:
          IMAGE: ghcr.io/lab-org/payment-srv
        run: |
          cosign sign --yes \
            --oidc-issuer https://token.actions.githubusercontent.com \
            "${IMAGE}@${IMAGE_DIGEST}"
      - name: attest provenance
        env:
          IMAGE: ghcr.io/lab-org/payment-srv
        run: |
          cosign attest --yes \
            --type slsaprovenance \
            --predicate build/payment-srv-attestation.json \
            "${IMAGE}@${IMAGE_DIGEST}"

56.2.3 Tipikus hibák és ellenpróbák

A tag promotálása digest helyett. Tünet: a klusterben lévő pod image mezője payment-srv:v0.4.2, és a git log szerint a promotion sikeres, mégis más kód fut. Hipotézis: a registryben a tagot időközben újratolták. Adatgyűjtés: docker buildx imagetools inspect a tag digestjére, és kubectl get pod -l app=payment-srv -o jsonpath='{.items[0].status.containerStatuses[0].imageID}' összehasonlítás. Ellenpróba: a desired state-ben tag szerepel, nem @sha256. Javítás: a values image.digest mezőre áll át, a taget csak CI kényelemként használjuk. Verifikáció: a pod imageID digestje megegyezik a release evidence image digestjével.

A rendered manifest nincs a GitOps repositoryban. Tünet: a CI-ben a helm template más eredményt ad, mint amit az Argo CD szinkronizál, mert a clusterben egy korábbi kubectl apply maradt. Hipotézis: a GitOps source nem a teljes desired state, hanem részleges overlay. Adatgyűjtés: argocd app diff lab-payment-staging és kubectl get all -n lab-payment -o yaml összehasonlítása. Ellenpróba: a diff a payment-srv Deployment image digest mezőben eltér. Javítás: minden módosítást a Git repository path-on kell commitolni, és az app sync policy automated + self-heal. Verifikáció: az argocd app diff üres, a kubectl apply-t nem használjuk.

A config migration egyirányú. Tünet: a v2 release rollout közben a régebbi pod ConfigMap parse hibát logol, a readiness probe nem válaszol. Hipotézis: a v2 config mezőneveket átneveztük, de a régi bináris nem ismeri őket. Adatgyűjtés: kubectl logs -l app=payment-srv --tail=50, a ConfigMap kubectl get cm payment-srv-config -n lab-payment -o yaml. Ellenpróba: a configVersion mező 2, de a deployment podjai között még v1 image fut. Javítás: először a v2 binárisnak kell tudnia olvasni a v1 configot; a rollout után átállunk v2 configra; rollback esetén a v1 binárisnak is olvasnia kell v2-t, vagy a config értéket a revert commit is visszaállítja. Az adatbázis séma esetén hasonló expand/contract migráció kell: az új séma először write-compatible, destruktív oszloptörlés csak a stabil lefutás után.

A rollout a PDB-t megsérti. Tünet: kubectl rollout status hosszan fut, a kubectl get pods egy pod Pending. Hipotézis: a maxUnavailable: 0 és a maxSurge: 1 ellenére a cluster nem tud új podot ütemezni, mert az adott nodeSelector vagy resource request túl magas. Adatgyűjtés: kubectl get events -n lab-payment --sort-by=.metadata.creationTimestamp | tail -20, kubectl get rs -n lab-payment, kubectl explain pod.spec. Ellenpróba: a PDB szerint legalább két pod egészségesnek kell lennie, de a scheduler nem talál szabad erőforrást. Javítás: a deployment resource requestjét a platform capacity budgethez igazítjuk, vagy a promotion előtt a kubectl top nodes és a kubectl describe nodes | grep -A5 Allocated értékeket ellenőrizzük. Verifikáció: a rollout maxSurge többlet podja ténylegesen elindul, a PDB status Allowed disruptions értéke nem csökken.

A hibakeresés során egy változtatást érdemes egyszerre végezni: először a digestet rögzítjük, utána a configVersion feltételt, végül a resource requestet. A GitOps diff és a release evidence minden lépésben megmondja, mi változott.

56.2.4 Feladatok

  1. Magyarázó feladat. Adott ez a deployment hivatkozás: ghcr.io/lab-org/payment-srv:v0.4.2. Magyarázza el, miért nem elegendő ez a promotion azonosító, és milyen bizonyíték hiányzik ahhoz, hogy a forrástól a futó podig egyértelmű legyen a lánc. Listázza a hiányzó mezőket, és adjon meg egy helyes image hivatkozást a dummy digesttel.

  2. Adminisztrációs feladat. A platform-deploy repositoryban a staging values jelenleg image.digest: sha256:old-digest. Készítse elő a v0.4.2 promotion commitot egy fiktív új digesttel. Renderelje le a manifestet, futtassa a kubeconform és conftest validálást, majd Argo CD sync parancsot adjon a staging alkalmazásra. A kimenetben mutassa be a várható image mezőt és a rollout státuszt.

  3. Diagnosztikai/failure feladat. A staging rollout után a podok Running állapotúak, de Ready nem lesznek. A naplóban Config parse error: unknown key settings.retry.milliseconds látszik. A rollout előtti pod még v1 image volt, a ConfigMap v2-t ír. Határozza meg a kiváltó okot, dolgozzon ki adatgyűjtési lépéseket, és hajtsa végre a data-compatible rollbacket a Git rebase/revert és Argo CD sync segítségével.

56.2.6 Rövid összefoglaló

A d277 a CI artifacttól a cluster desired state-ig vezethető immutable láncot tanítja. A natív C++ build egyetlen binary artifactot állít elő; a container build azt telepíti, SBOM-mal, digestsztel és attestationnel látja el. A GitOps promotion ugyanazt a digestet mozgatja environmentek között, a környezeti különbséget a rendered manifest values adja. A rollout biztonságát probe-ok, PDB és rolling/canary stratégia adja; a rollback csak akkor érvényes, ha a config és data migration visszafelé is kompatibilis. Továbbhasznált definíciók: immutable artifact promotion, GitOps reconcile, data-compatible rollback.
