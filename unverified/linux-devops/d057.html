12.2 Telepítés, partition és elérhetőség

12.2.1 Motiváció

Egy Linux hoszt üzembe állítása akkor válik működtethetővé, ha a telepítés nem egyszeri, megismételhetetlen kattintgatás, hanem verziózott, auditálható telepítési profilból (installation profile) hajtható végre. A szenior C++ fejlesztő a build automatizálásából ismeri a reprodukálhatóság és az artifact ellenőrzés értékét; ugyanez a szemlélet kell egy új VM kiépítéséhez. Ennek a szakasznak a célja, hogy egy rögzített profillal, hitelesített forrásból, konzol- és SSH-eléréssel rendelkező Linux hosztot hozzunk létre, majd az üzemeltetéshez szükséges alaptermék-nyilvántartást (inventory) rögzítsük. A mélyebb lemezkezelést a Block device, partition, LVM és titkosítás adminisztrációja, a mountok részletes szemantikáját a Mount, fstab és namespace tárgyalja.

12.2.2 Telepítési profil definíció és működési rétegek

Definition. A telepítési profil az az újraépíthető, verziózott specifikáció, amely az operációs rendszer image forrását, integritás-ellenőrző adatát, a platform által elvárt boot és lemez layoutot, az admininstrációs hozzáférést, a hálózati minimumprofilt, valamint a konzol/SSH recovery útvonalat írja le.

A telepítés rétegei:

  1. Forrás image réteg: az ISO vagy cloud image beszerzése, ellenőrző összeg (checksum) és aláírás ellenőrzése. Ez adja az artifact identitását.
  2. Installer/provision réteg: az automatizált telepítő inputja (Ubuntu Server 24.04 LTS esetén autoinstall/cloud-init seed), amely a lemezt, a felhasználót, a hálózatot és az SSH-t állítja be.
  3. Boot és mount réteg: UEFI firmware, boot loader, /boot és a root filesystem mountjai. A rendszer itt válik elérhetővé.
  4. Elérhetőségi réteg: konzol, SSH, hálózat és DNS. A recovery útvonal akkor is megmarad, ha a hálózati elérés kiesik.
  5. Post-install inventory réteg: a telepített állapot rögzítése és a biztonsági frissítések alkalmazása.

Az egyes rétegek kimenete ellenőrizhető állapotot ad; ha a következő réteg hibázik, a korábbi rétegek állapotából indítható a diagnosztika.

12.2.3 Kidolgozott példa: lab-vm1 telepítése

A példa az izolált lab infrastruktúrában (Izolált, újraépíthető Linux labor) fut. Az inventory:

Szerep Host/VM Account Privilege Hálózat Megjegyzés
Hypervisor lab-hv-01 lab-admin sudo root mgmt telepítés vezérlése
Új VM lab-vm1 lab-admin sudo a VM-ben lab-net célrendszer
Telepítési kép ISO — — — disztribútor release oldala

A példa IP a 192.0.2.10 documentation cím; a tényleges lab DHCP-t a d003 inventory adja. A módosító parancsok a lab-hv-01 gazdagépen futnak, lab-admin felhasználóval és sudo-val.

12.2.3.1 1. ISO hitelesség és checksum

A forrás ISO és az ellenőrző összeg URL-jét a lab release jegyzék tárolja. Az itteni URL és hash nem ellenőrzött, csak a folyamatot mutatja:

# target: lab-hv-01, user: lab-admin, privilege: user
mkdir -p ~/lab-install && cd ~/lab-install
curl -fL -o ubuntu-server-24.04-live-server-amd64.iso "<release-url>/ubuntu-server-24.04-live-server-amd64.iso"
curl -fL -O "<release-url>/SHA256SUMS"
sha256sum -c <(grep 'ubuntu-server-24.04.*amd64.iso' SHA256SUMS)

A grep a SHA256SUMS fájlból csak a kívánt ISO sort adja, a sha256sum -c pedig a sorban szereplő hash-t ellenőrzi. A valós hash értéket a letöltött SHA256SUMS fájlból kell rögzíteni, nem elég az oldalon látott értékre hagyatkozni.

12.2.3.2 2. Telepítő seed profil

Az Ubuntu autoinstall számára a user-data rögzíti a hostidentitást, SSH-t, minimális lemezelrendezést és hálózatot. A jelszó csak példa, saját hash-t mkpasswd -m sha-512 paranccsal kell generálni:

#cloud-config
autoinstall:
  version: 1
  identity:
    hostname: lab-vm1
    username: lab-admin
    # Példa hashelt jelszó; dummy, nem éles.
    password: "$6$rounds=656000$example..." 
  ssh:
    install-server: true
    allow-pw: false
    authorized-keys:
      - "ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIexample lab-admin@lab-hv-01"
  storage:
    layout:
      name: lvm
      match:
        size: largest
  network:
    version: 2
    ethernets:
      enp1s0:
        dhcp4: true

A meta-data mellé:

instance-id: lab-vm1
local-hostname: lab-vm1

Az lvm layout automatikusan hozza létre a UEFI ESP-t, a /boot-ot, a root és swap logikai köteteket. Az elkülönített adatterületet a storage admin mélyíti; itt a példa csak a minimális, reprodukálható alapréteget célozza. A tervezett layout:

Mount Eszköz példa FS Méret Szerep
/boot/efi vda1 vfat 1 GiB UEFI ESP
/boot vda2 ext4 2 GiB kernel/initramfs
/ vg0/root ext4 15 GiB OS
swap vg0/swap swap 2 GiB swap
/srv/data vg0/data ext4 maradék alkalmazásadatok

12.2.3.3 3. Telepítés indítása

# target: lab-hv-01, user: lab-admin, privilege: sudo
sudo virt-install \
  --name lab-vm1 \
  --memory 4096 \
  --vcpus 2 \
  --disk path=/var/lib/libvirt/images/lab-vm1.qcow2,format=qcow2,size=20 \
  --network network=lab-net,model=virtio \
  --boot uefi \
  --cdrom /home/lab-admin/lab-install/ubuntu-server-24.04-live-server-amd64.iso \
  --cloud-init user-data=/home/lab-admin/lab-install/user-data,meta-data=/home/lab-admin/lab-install/meta-data \
  --noautoconsole

A virt-install részletei a KVM, QEMU és libvirt komponensek témakörhöz tartoznak; itt a profil az irányadó. A telepítés után a hypervisor oldalon virsh list --all mutatja a VM-et.

12.2.3.4 4. Network, DNS és SSH ellenőrzés

A VM DHCP-ről kap IP-t. Az első belépés SSH-val, a seedben megadott kulccsal:

# target: lab-hv-01, user: lab-admin, privilege: user
ssh -i ~/.ssh/lab_admin lab-admin@192.0.2.10 -- hostnamectl

SSH kiesése esetén a konzol a recovery útvonal:

# target: lab-hv-01, user: lab-admin, privilege: sudo
sudo virsh console lab-vm1
# kilépés: Ctrl+]

A konzolon bejelentkezve a hálózati állapot akkor is ellenőrizhető, ha a hálózat nem elérhető a gazdáról.

12.2.3.5 5. Post-install inventory és frissítések

Az alaptermék-nyilvántartáshoz a következő adatokat rögzítjük a VM-en:

# target: lab-vm1, user: lab-admin, privilege: sudo az utolsó parancsnál
hostnamectl
uname -r
lsblk -o NAME,FSTYPE,SIZE,MOUNTPOINTS
findmnt --real
systemctl is-system-running
resolvectl status

A frissítés módosító művelet, ezért előtte a hypervisoron VM snapshot készül (a snapshot kezelést lásd VM block storage, snapshot és backup). A frissítés és az újraindítás utáni ellenőrzés:

# target: lab-vm1, user: lab-admin, privilege: sudo
sudo apt update
sudo apt full-upgrade -y
sudo systemctl reboot

Reboot után újra ellenőrizzük az SSH-elérést és a rendszer állapotát.

12.2.4 Hibák és ellenpróbák

Tünet: a telepítő lefut, de az SSH login nem fogadja a kulcsot.
Hipotézis: a user-data-ban rossz a publikuskulcs-formátum.
Adatgyűjtés: ssh -vvv kimenet, valamint cloud-init status és /var/log/cloud-init.log a konzolon.
Egy változtatás: a seedben a authorized-keys sort javítani kell, majd a VM-et törölni és újraépíteni.
Ellenőrzés: az SSH belépés újrapróbálása.

Tünet: a VM elérhető IP-n, de a DNS nem old fel neveket.
Hipotézis: az autoinstall network profil nem kapott DNS beállítást, és a cloud-init netplanja nem vette át a DHCP DNS-t.
Adatgyűjtés: networkctl status, resolvectl status, /etc/netplan/*.yaml, /etc/resolv.conf.
Egy változtatás: a netplan configban dhcp4-overrides: use-dns: true beállítása, majd netplan apply.
Ellenőrzés: dig vagy resolvectl query egy belső névre.

Tünet: frissítés után a VM nem bootol.
Hipotézis: initramfs vagy kernel/video illesztőhiba, boot menü beavatkozás szükséges.
Adatgyűjtés: hypervisor konzol (virsh console) kimenet, GRUB menü.
Egy változtatás: boot során egy korábbi kernel választása a menüben, vagy a mentett VM snapshot visszaállítása.
Ellenőrzés: a VM ismét csatlakozik a lab hálózathoz, SSH/konzol elérhető.

12.2.5 Feladatok

12.2.5.1 Feladat 1: Telepítési profil írása

Készítsen egy egylapos telepítési profil specifikációt a lab-vm1 hoszthoz az alábbi adatokkal: Ubuntu Server 24.04 LTS amd64, UEFI boot, minimálisan /boot/efi, /boot, root, swap; admin user lab-admin; hálózat DHCP; SSH key és konzol recovery. Írja le, milyen mezőket kell rögzíteni a release jegyzékben az image hitelességéhez.

12.2.5.2 Feladat 2: Automatizált telepítés

Generáljon egy SSH kulcsot lab-admin felhasználóhoz, készítse el a user-data és meta-data fájlt a fenti profilhoz, indítsa el a virt-install parancsot a lab-hv-01 gazdagépen, majd ellenőrizze a VM elérését SSH-val és konzollal. A lab hálózati IP a documentation tartományból 192.0.2.10.

12.2.5.3 Feladat 3: SSH recovery diagnosztika

A lab-vm1 a konzolon elérhető, de az SSH kapcsolat timeoutot ad. A cél: a konzolon gyűjtsön adatot, állapítsa meg, hogy a hiba a hálózatban, a DNS-ben, a tűzfalban vagy az SSH szolgáltatásban van, és állítsa helyre. Rögzítse a hibás és a javított állapotot.

12.2.6 Megoldások

12.2.6.1 Megoldás 1

A profil mezői: forrás URL és ellenőrző hash típusa/értéke; boot mód (UEFI); minimális lemezelrendezés; mountpontok és filesystem; admin user; SSH publikus kulcs; hálózati mód (DHCP); konzol recovery mód. A release jegyzékben rögzíteni kell a pontos image verziót, a letöltött SHA256SUMS fájlt, a hash-t, a letöltés dátumát és a forrás URL-t. Postcondition: a profil egyértelmű, más mérnök ugyanazt a gépet tudja újraépíteni.

12.2.6.2 Megoldás 2

A kulcsgenerálás ssh-keygen -t ed25519 -f ~/.ssh/lab_admin -C lab-admin@lab-vm1. A seedben a publikus kulcsot kell a authorized-keys listába illeszteni. A virt-install parancs a fenti mintával futtatható; a diszk mérete 20 GiB, a hálózat lab-net. A telepítés után ssh -i ~/.ssh/lab_admin lab-admin@192.0.2.10 -- systemctl is-system-running ellenőrzi az elérést; a konzol sudo virsh console lab-vm1. Postcondition: a VM SSH-n és konzolon keresztül elérhető, a hostname lab-vm1, az admin user lab-admin.

12.2.6.3 Megoldás 3

A konzolon először a hálózati interfész állapotát és a routeokat ellenőrizzük: ip -br a, ip route. Ha nincs IP vagy route, a netplan configot vizsgáljuk és javítjuk netplan apply-jal. Ha az IP megvan, a DNS megfelelő resolvectl status-szal. Ha minden hálózati elérés rendben, az SSH szolgáltatás státuszát systemctl status ssh-val vizsgáljuk, és a ss -tlnp | grep ':22' portfigyelést ellenőrizzük. A tűzfal esetén nft list ruleset vagy ufw status mutatja a szabályt. A gyakori hiba az, hogy a cloud-init hálózat konfig nem írta be a DHCP DNS-t; a javítás a netplan use-dns: true beállítása és netplan apply. Postcondition: az SSH a 192.0.2.10 dokumentációs címen elérhető, a DNS feloldás működik, a hiba és a javítás state rögzítve van.

12.2.7 Rövid összefoglaló

A Linux VM telepítését telepítési profilként kell kezelni: verziózott forrásimage, hitelesség-ellenőrzés, automatikus installer seed, UEFI és minimális lemezelrendezés, admin user, hálózati/DNS minimum, valamint konzol/SSH recovery. A telepítés után inventory és biztonsági frissítés következik, snapshot rollbackkel. A példában Ubuntu Server 24.04 LTS autoinstall/cloud-init folyamatot használtunk; a pontos release/version ellenőrzendő. Ez a fejezet a storage admin és a hypervisor réteg felé nyit: a lemezelrendezés, a snapshot és a boot hiba mély kezelését későbbi szakaszok tanítják. Az állapotok desired, observed, config-source és stored állapotként dokumentáltak.

Továbbhasznált definíciók: telepítési profil, recovery path, image hitelesség.

12.2.8 Források és ellenőrzési hiányok

  • Ubuntu Server documentation — kiindulópont, nem ellenőrzött; az autoinstall/cloud-init release-specifikus mezőit hivatalos dokumentációból kell ellenőrizni.
  • Debian documentation — distro kontraszt, ebben a példában nem használt; a Debian telepítőprofil eltérő.
  • systemd — boot/mount egységekhez hivatkozott, itt nem kifejtett.

Ellenőrzési hiányok: a konkrét Ubuntu 24.04 ISO URL és SHA256SUMS hash, az aktuális autoinstall/cloud-init verzió és mezőkészlet, a virt-install --cloud-init opció pontos elérhetősége, a generált lvm layout automatikus partícióméretei, valamint az aktuális kernel/csomagfrissítések verziószintje. Ezeket a lab release jegyzékből és a hivatalos vendor dokumentációból kell ellenőrizni.
