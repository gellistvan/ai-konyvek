11.5 Filesystem szemantika és döntési labor

11.5.1 Motiváció

Egy hosztot üzemeltető szenior fejlesztő számára a leggyakoribb és legfélrevezetőbb hibajelenség, amikor a df -h szabad helyet mutat, egy fájl létrehozása mégis „No space left on device” hibával tér vissza, vagy amikor a lemezhasználat 90%-ot jelez, de a du -sh /data összege csak 50%. A különbség oka a fájlrendszer-szemantikában rejlik: a pathnév, az inode és a blokkfoglalás más-más erőforrást képvisel. Ez a labor ezeket a réteghatárokat teszi mérhetővé, és bemutatja, hogy a fájlrendszer nem csupán egy névtér, hanem memória-, CPU- és adattartóssági szerződés is. A döntés, hogy ext4, XFS, Btrfs vagy tmpfs legyen-e egy adott mount, nem ízlés kérdése, hanem a workload latency-, durability- és metadata-igényének következménye.

11.5.2 Definíció és működés

11.5.2.1 Sparse file, open-deleted file és inode exhaustion

A sparse file (ritka fájl) olyan fájl, amelynek logikai mérete nagyobb, mint a ténylegesen lefoglalt blokkok összege. A lyukak (hole) nullának olvashatók, de nem foglalnak fizikai blokkot a háttértáron. A ls -l a logikai méretet mutatja, a du (alapértelmezés szerint) a lefoglalt blokkokat. Például egy 1 GiB-os truncate-tel létrehozott fájl logikai mérete 1 GiB, de gyakorlatilag nulla blokkot foglal. A C++ program is létrehozhat ilyet pwrite-tel vagy fallocate-cal (utóbbi garantáltan lefoglalja a blokkokat, előbbi nem).

Az open-deleted file (megnyitott, majd törölt fájl) az a fájl, amelyet egy processz megnyit, majd a fájlrendszerből unlink-kel eltávolítanak. A fájl a processz fájlleíróján (FD) keresztül továbbra is elérhető, és a blokkjai foglaltak maradnak, amíg minden FD nem záródik be. A df ezért továbbra is foglaltnak mutatja a blokkokat, míg a du nem látja, mert a fájlnak már nincs neve a könyvtárhierarchiában. A diagnózishoz lsof +L1 vagy /proc/PID/fd szükséges.

Az inode exhaustion (inode-kimerülés) akkor következik be, amikor a fájlrendszerben az összes inode lefoglalásra került, de a blokkterület még szabad. A df -h alacsony kihasználtságot mutat, a df -i viszont 100%-ot. Az ext4-ben az inode-ok számát a formázáskor rögzítik (alapértelmezés: kb. 1 inode per 16 KiB), XFS-ben dinamikus, de a fájlrendszer méretétől függően limit lehet; Btrfs-ben gyakorlatilag nem fogy el külön inode-tábla. Sok kis fájl (például cache, session, build artifact) gyorsan kimeríti az inode-okat.

11.5.2.2 tmpfs/ramfs és memória accounting

A tmpfs egy memóriaalapú fájlrendszer, amely a page cache-t használja háttértárként: a fájl tartalma a RAM-ban él, és swappelhető, ha van swap. A size= mount opcióval felső korlát adható meg; ezen felül írni ENOSPC hibát ad. A ramfs egy régebbi, egyszerűbb implementáció, amely nem swappelhető, és nincs méretkorlátja – ha betelik a RAM, a kernel OOM-killerhez nyúl. A modern Linuxon ezért tmpfs ajánlott. A tmpfs fájlok a cgroup v2 memory.current számlálójában is megjelennek, tehát a konténer memórialimitjét terhelik. A df a tmpfs méretét a mount opcióból és a felhasznált memóriából számolja, nem egy lemezblokk-táblából.

11.5.2.3 overlayfs előkép

Az overlayfs egy virtuális fájlrendszer, amely két (vagy több) könyvtárat rétegez: a lowerdir read-only alsó réteg, az upperdir írható felső réteg, a workdir pedig a copy-up művelet ideiglenes munkakönyvtára. Amikor egy alsó rétegbeli fájlt módosítanak vagy törölnek, a rendszer a fájlt előbb a felső rétegbe másolja (copy-up), majd ott hajtja végre a változást. Az alsó réteg érintetlen marad. Ez az alapja a konténer image rétegeknek: az image rétegek lowerdir-ként, a konténer írható rétege upperdir-ként szolgál. A d055-ben csak a szemantikát mutatjuk be, a részletes konténerintegráció a konténer image, build, registry és artifact alfejezetben következik.

11.5.2.4 Latency, durability és metadata workload

A fájlrendszer tradeoffjait a workload típusa határozza meg. A metadata workload sok kis fájl létrehozása, törlése, átnevezése és jogosultságváltása; ez az inode-műveleteket, a journalt és a könyvtárbejegyzéseket terheli. A durability azt fejezi ki, hogy egy fsync vagy power loss után mennyi adat van garantáltan visszaállítható állapotban. A journaling módok (writeback, ordered, data=journal) különböző latency-durability kompromisszumot adnak: az ordered mód alapértelmezett, a data=journal a legbiztonságosabb, de a leglassabb. Az ext4/XFS inkább a szekvenciális és alacsony latency, a Btrfs/OpenZFS a snapshot, checksum és adatintegritás irányába optimalizál.

11.5.3 Kidolgozott példa

A példában minden módosító parancs a labhost1 hoszton fut, labadmin felhasználóval, sudo jogosultsággal. A létrehozott objektumok mind lab- prefixet kapnak, és a végén teljes cleanup történik. A lemezfoglalás egy loopback fájl, nem fizikai eszköz.

11.5.3.1 1. Disposable mount és sparse file

# target: labhost1, user: labadmin, privilege: sudo
# Előfeltétel: /var/tmp írható, loop modul elérhető
sudo truncate -s 1G /var/tmp/lab-fs.img
sudo mkfs.ext4 -L lab-fs /var/tmp/lab-fs.img
sudo mkdir -p /mnt/lab-fs
sudo mount -o loop /var/tmp/lab-fs.img /mnt/lab-fs
# Ellenőrzés:
lsblk -o NAME,SIZE,FSTYPE,LABEL /dev/loop0
df -h /mnt/lab-fs

A truncate-tel létrehozott fájl logikai mérete 1 GiB, de a du -h /var/tmp/lab-fs.img csak néhány KiB-ot mutat, mert a blokkok még nincsenek lefoglalva. A mkfs.ext4 lefoglalja a szükséges metadata blokkokat.

11.5.3.2 2. Sparse file és open-deleted file

# Sparse file a mountponton belül
sudo dd if=/dev/zero of=/mnt/lab-fs/sparse bs=1M count=0 seek=1024
ls -lh /mnt/lab-fs/sparse   # 1.0G logikai méret
du -h /mnt/lab-fs/sparse    # 0K tényleges blokk

# Open-deleted file
sudo dd if=/dev/zero of=/mnt/lab-fs/deleteme bs=1M count=100
# Háttérfolyamat nyitja a fájlt, és megtartja az FD-t
sudo -u labadmin bash -c 'exec 3<>/mnt/lab-fs/deleteme; echo $$ > /tmp/lab-fd.pid; sleep 1000' &
sleep 1
sudo rm /mnt/lab-fs/deleteme
# A df még mindig foglaltnak mutatja a 100M-ot, a du nem látja
df -h /mnt/lab-fs | grep lab-fs
du -sh /mnt/lab-fs
# A processz FD-je megmutatja a törölt fájlt
PID=$(cat /tmp/lab-fd.pid)
sudo ls -l /proc/$PID/fd/3   # 'deleted' jelzés

Várható kimenet: a df -h 100M-mel nagyobb használatot mutat, mint a du -sh /mnt/lab-fs. A /proc/PID/fd/3 szimbolikus link célja /mnt/lab-fs/deleteme (deleted). A processz leállítása után (kill $PID) a blokkok felszabadulnak.

11.5.3.3 3. Inode exhaustion

# Kisméretű, alacsony inode-számú fájlrendszer
sudo truncate -s 20M /var/tmp/lab-inode.img
sudo mkfs.ext4 -N 1000 /var/tmp/lab-inode.img   # 1000 inode
sudo mkdir -p /mnt/lab-inode
sudo mount -o loop /var/tmp/lab-inode.img /mnt/lab-inode
# Sok üres fájl létrehozása
for i in $(seq 1 2000); do sudo touch /mnt/lab-inode/file$i; done
# Az inode-tábla betelik, a blokkterület alig használt
df -i /mnt/lab-inode   # IUse% 100%
df -h /mnt/lab-inode   # Use% néhány százalék

A touch parancs az 1000. fájl után No space left on device hibát ad, miközben a df -h még sok szabad blokkot mutat.

11.5.3.4 4. tmpfs memória accounting

sudo mkdir -p /mnt/lab-tmpfs
sudo mount -t tmpfs -o size=512M tmpfs /mnt/lab-tmpfs
sudo dd if=/dev/zero of=/mnt/lab-tmpfs/testfile bs=1M count=100
# A memória használat növekszik; a free -h a buff/cache sorban mutatja
free -h
# Ha van cgroup v2 a shell alatt, a memory.current is növekszik
cat /sys/fs/cgroup/memory.current

Várható kimenet: a free -h buff/cache oszlopa ~100M-rel nő. A cat /sys/fs/cgroup/memory.current értéke is nő, ha a shell egy cgroupba tartozik. A df -h /mnt/lab-tmpfs a tmpfs aktuális használatát mutatja.

11.5.3.5 5. overlayfs copy-up

sudo mkdir -p /mnt/lab-overlay/{lower,upper,work,merged}
echo "original" | sudo tee /mnt/lab-overlay/lower/file.txt
sudo mount -t overlay overlay -o lowerdir=/mnt/lab-overlay/lower,upperdir=/mnt/lab-overlay/upper,workdir=/mnt/lab-overlay/work /mnt/lab-overlay/merged
cat /mnt/lab-overlay/merged/file.txt   # original
echo "modified" | sudo tee /mnt/lab-overlay/merged/file.txt
# Az alsó réteg érintetlen, a felsőben megjelenik a másolat
cat /mnt/lab-overlay/lower/file.txt    # original
cat /mnt/lab-overlay/upper/file.txt    # modified

11.5.3.6 6. Teljes cleanup

# Háttérfolyamat leállítása, ha fut
if [ -f /tmp/lab-fd.pid ]; then kill $(cat /tmp/lab-fd.pid) 2>/dev/null || true; fi
# Unmount minden lab mountpont
sudo umount /mnt/lab-fs /mnt/lab-inode /mnt/lab-tmpfs /mnt/lab-overlay/merged 2>/dev/null || true
# Fájlok törlése
sudo rm -f /var/tmp/lab-fs.img /var/tmp/lab-inode.img /tmp/lab-fd.pid
sudo rm -rf /mnt/lab-fs /mnt/lab-inode /mnt/lab-tmpfs /mnt/lab-overlay
# Ellenőrzés:
mount | grep -E 'lab-(fs|inode|tmpfs|overlay)'   # üres kimenet
ls /var/tmp/lab-*.img   # nincs ilyen fájl

A cleanup csak a lab- prefixű objektumokat érinti, más mountpont vagy fájl nem sérül.

11.5.4 Hibák és ellenpróbák

Tünet: df -h 90%-ot mutat, de du -sh /data csak 50%. Hipotézis: open-deleted fájl foglalja a blokkokat. Adatgyűjtés: lsof +L1 | grep /data megmutatja a törölt, de nyitott fájlokat. Egy változtatás: a folyamat újraindítása vagy az FD bezárása felszabadítja a blokkokat. Verification: df -h csökkenése.

Tünet: touch /mnt/lab-inode/file1001 hibát ad, de df -h sok szabad helyet mutat. Hipotézis: inode kimerülés. Adatgyűjtés: df -i /mnt/lab-inode 100%-ot mutat. Egy változtatás: felesleges fájlok törlése, vagy a fájlrendszer újraformázása nagyobb -N értékkel. Verification: df -i csökken, új fájl létrehozható.

Gyakori hiba: a tmpfs size= elhagyása. Ha nincs méretkorlát, a tmpfs akár a teljes RAM-ot és swapet elfogyaszthatja, ami OOM killhez vezet. A free -h és a cgroup memory.current figyelése nélkül a tmpfs használata rejtett memóriaszivárgást okozhat. Az overlayfs esetében a workdir hiánya vagy a lowerdir és upperdir azonos fájlrendszeren kívülisége mount hibát ad; a copy-up művelet pedig többlet I/O-t generál, ezért nagy fájlok módosítása lassú lehet.

11.5.5 Feladatok

11.5.5.1 1. Magyarázó feladat

Egy Linux hoszton a /var fájlrendszer df -h szerint 85%-ban tele van, de a du -sh /var összege a teljes kapacitásnak csak 40%-át adja. Sorold fel a lehetséges okokat, és mindegyikhez adj egy parancsot vagy eljárást, amellyel igazolható a hipotézis. Ne futtass semmit, csak a diagnosztikai tervet írd le.

11.5.5.2 2. Adminisztrációs/konfigurációs feladat

Hozz létre egy 256 MiB méretű tmpfs mountot /mnt/lab-tmpfs-task néven. Írj bele pontosan 200 MiB adatot egyetlen fájlba, majd ellenőrizd a memóriahasználatot free -h és a cgroup memory.current segítségével. Ezután csökkentsd a tmpfs méretét 128 MiB-re remounttal, és figyeld meg, mi történik a meglévő fájllal. A feladat végén teljes cleanup szükséges.

11.5.5.3 3. Diagnosztikai/failure/recovery feladat

Egy 30 MiB-os ext4 fájlrendszerben (/var/tmp/lab-task3.img) hozz létre annyi üres fájlt, hogy a fájlok létrehozása No space left on device hibát adjon. A df -h szerint van szabad hely, de a df -i 100%-ot mutat. Diagnosztizáld a hibát, majd oldd meg a problémát: töröld a felesleges fájlokat, és igazold, hogy új fájl létrehozható. A végén teljes cleanup.

11.5.6 Megoldások

11.5.6.1 1. Megoldás

Lehetséges okok és diagnózisuk: - Open-deleted fájlok: lsof +L1 | grep /var vagy for p in /proc/[0-9]*/fd/*; do ls -l $p 2>/dev/null | grep deleted | grep /var; done – a törölt, de nyitott fájlok blokkjai foglaltak maradnak. - Sparse file: du --apparent-size -sh /var és du -sh /var összehasonlítása; a logikai méret nagyobb, mint a lefoglalt blokk. - Mount shadowing: egy másik mountpont elrejtheti az alatta lévő könyvtár tartalmát; mount | grep /var ellenőrzi, hogy van-e nested mount. - Inode kimerülés: df -i /var – ha 100%, akkor sok kis fájl foglalja az inode-okat, de a blokkterület szabad. Postcondition: minden hipotézishez tartozik egy konkrét ellenőrző parancs, amely eldönti, melyik ok áll fenn.

11.5.6.2 2. Megoldás

# target: labhost1, user: labadmin, privilege: sudo
sudo mkdir -p /mnt/lab-tmpfs-task
sudo mount -t tmpfs -o size=256M tmpfs /mnt/lab-tmpfs-task
sudo dd if=/dev/zero of=/mnt/lab-tmpfs-task/testfile bs=1M count=200
free -h
cat /sys/fs/cgroup/memory.current
# Remount kisebb mérettel
sudo mount -o remount,size=128M /mnt/lab-tmpfs-task
# A meglévő fájl megmarad, de a tmpfs mérete 128M-re csökken; ha a fájl nagyobb, a kernel nem törli, de a df 128M-t mutat, és további írás ENOSPC-t adhat.
df -h /mnt/lab-tmpfs-task
# Cleanup
sudo umount /mnt/lab-tmpfs-task
sudo rm -rf /mnt/lab-tmpfs-task

Indoklás: a tmpfs remount méretcsökkentése nem törli a meglévő adatokat, de a fájlrendszer felső határa csökken. A free -h buff/cache oszlopa a 200 MiB íráskor növekszik, a memory.current a cgroup teljes memóriahasználatát mutatja. Postcondition: a mount megszűnt, a memória felszabadult, nincs lab-tmpfs-task könyvtár.

11.5.6.3 3. Megoldás

# target: labhost1, user: labadmin, privilege: sudo
sudo truncate -s 30M /var/tmp/lab-task3.img
sudo mkfs.ext4 -N 2000 /var/tmp/lab-task3.img
sudo mkdir -p /mnt/lab-task3
sudo mount -o loop /var/tmp/lab-task3.img /mnt/lab-task3
# Inode kimerülés előidézése
for i in $(seq 1 5000); do sudo touch /mnt/lab-task3/file$i 2>/dev/null || break; done
# Diagnózis
df -h /mnt/lab-task3   # kevés blokk használt
df -i /mnt/lab-task3   # 100% inode
# Recovery: felesleges fájlok törlése (pl. a páros sorszámúak)
sudo find /mnt/lab-task3 -type f -name 'file*' -delete
# Ellenőrzés: új fájl létrehozható
sudo touch /mnt/lab-task3/newfile
# Cleanup
sudo umount /mnt/lab-task3
sudo rm -f /var/tmp/lab-task3.img
sudo rm -rf /mnt/lab-task3

Indoklás: a -N 2000 korlátozza az inode-ok számát. A touch sorozat a 2000. fájl után meghiúsul. A törlés felszabadítja az inode-okat, így az új fájl sikeres. Postcondition: a fájlrendszer újra használható, a cleanup után nincs lab-task3 objektum.

11.5.7 Rövid összefoglaló

A fájlrendszer-szemantika három erőforrást különböztet meg: blokkterület, inode-tábla és path névtér. A sparse file logikai mérete nagyobb, mint a lefoglalt blokkok; az open-deleted fájl a pathból törölve is foglalja a blokkokat, amíg az FD él; az inode exhaustion akkor jelentkezik, ha sok kis fájl van, miközben a blokkterület szabad. A tmpfs a memóriát használja háttértárként, és a cgroup memóriába számít; az overlayfs a copy-up mechanizmussal rétegezi a read-only alsó és írható felső réteget. A fájlrendszer-választást a workload latency-, durability- és metadata-igénye határozza meg. A laborban minden objektum lab- prefixszel jött létre, és a cleanup teljes volt.

Továbbhasznált definíciók: sparse file – nagy logikai méret, kevés lefoglalt blokk; open-deleted file – törölt, de nyitott FD-vel továbbra is foglalt fájl; inode exhaustion – az inode-tábla kimerülése, miközben blokkterület marad.
