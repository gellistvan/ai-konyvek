38.4 Compose és többservice-s lokális stack

38.4.1 Motiváció

Egy konténer önmagában ritkán elég: egy lokális fejlesztői vagy laborrendszerhez webszolgáltatás, adatbázis, cache és debugsebesség együtt kell. A Compose-fájl ezt a több szolgáltatásból álló lokális stacket deklaratív módon írja le: mely service-ek induljanak, milyen hálózaton beszéljenek, milyen köteteket csatoljanak, milyen titkokat kapjanak. A cél nem az, hogy a parancsokat kézzel futtassuk, hanem hogy a kívánt állapotot verziókezelt konfigurációként, ellenőrizhetően reprodukáljuk.

Ez a fejezet feltételezi, hogy a konténer életciklusát, a lokális hálózatot és a volume-kezelést a d188-ban már megismertük. A d143-as readiness fogalom itt kulcsfontosságú: egy konténer futása nem jelenti azt, hogy alkalmazása kérést is tud fogadni.

38.4.2 Definíció és működés

A Compose-fájl egy lokális, egy hosztra értelmezett Compose-projekt desired state leírása. A projekt scope határozza meg, hogy az erőforrások melyik névvel és címkével tartoznak össze. A leírás legfontosabb elemei:

Elem Mit ír le Példa
services futtatandó konténerek image-e, életciklusa, erőforrásai api, db, cache
networks service-ek közötti hálózatok backend
volumes nevű, tartós adatterületek db-data, cache-data
secrets érzékeny fájlok konténerbe juttatása db_password
projektnév prefix a hálózatok, volume-ok, konténerek elé lab-cpp-stack

A Compose nem klaszter-orchestrátor: egyetlen hoszton, a helyi konténer-motorból indít, és nem osztja el a terhelést több gépen.

38.4.2.1 Services, networks, volumes és projekt scope

A projektnév alapértelmezésben a könyvtár neve, de célszerű explicit name: mezővel rögzíteni, hogy más útvonalról futtatva is azonos legyen a scope. A service-ek a közös hálózaton a service-névvel oldják fel egymást, például az api konténer db:5432 címen éri el az adatbázist. A named volume az adatokat a konténer életciklusán túl is megőrzi; itt a db-data és a cache-data leválasztása azt is jelzi, hogy a két tartóssági igény különbözik.

A volume nem backup. A named volume a hoszt lokális container-storage területén él, és a projekt down -v nélkül megmarad, de a hoszt storage hibája, tévedésből törlés vagy migration nélküli gépcsere ellen nem véd.

38.4.2.2 Indulási sorrend és readiness

A depends_on rövid formája csak elindítja a függőséget, de nem várja meg, hogy az használható legyen. Ha az api service depends_on: [db] módon indul, a db konténer processze lehet, hogy már fut, de a PostgreSQL még nem fogad kapcsolatot. Ez a klasszikus startup race.

A hosszú forma a Compose Specification szerint feltételt is adhat:

depends_on:
  db:
    condition: service_healthy
  cache:
    condition: service_started

A service_healthy azt jelenti, hogy a függő service a healthcheck által meghatározott állapotúvá válik. Ez azonban verzió- és implementációfüggő: a Docker Compose v2 támogatja, de a Podman Compose vagy régebbi tooling esetében ellenőrizni kell, hogy a condition mezőt nem hagyja-e figyelmen kívül. A biztonságos alkalmazás akkor is újrapróbálkozik indításkor, ha a healthcheck később elérhetővé válna.

A healthcheck nem egyenlő az alkalmazás readinessével. A konténerhealthcheck lehet például pg_isready, ami az adatbázis kapcsolódási készségét jelzi, de a service attól még lehet terhelés alatt vagy függő migrációban. A forgalmi readiness fogalma a d143 szerint ennél szigorúbb: csak akkor küldünk érdemi kérést, ha az alkalmazás saját readiness-próbája is sikeres.

38.4.2.3 Config interpolation és secret kezelés

A Compose-fájlban ${VAR} helykitöltővel külső értékeket interpolálhatunk. Az alapértelmezett értékek beépíthetők: ${POSTGRES_TAG:-16}. A változókat a Compose a projektkönyvtár .env fájljából, illetve a shell környezetből is olvashatja; a pontos precedencia eszközfüggő.

A jelszót vagy titkos tokent ne tegyük sima environment változóba vagy .env-be, ha az verziókezelt. A Compose secrets része a titkot fájlként csatolja a konténerbe, például /run/secrets/db_password. A PostgreSQL hivatalos image-e esetében a POSTGRES_PASSWORD_FILE erre a fájlos átadásra szolgál; a pontos támogatást az adott image változatánál ellenőrizni kell.

38.4.2.4 Profiles, resource limit és override

A profiles listával olyan service-eket jelölünk, amelyek alapértelmezésben nem indulnak. A debug konténer például csak --profile debug kapcsolóval jön létre. Ez megakadályozza, hogy a normál docker compose up fölösleges segédkonténereket indítson, miközben a definíció egyetlen forrásból olvasható.

Az erőforráslimit fontos egy lokális stacknél is, mert a cache vagy az API memóriahasználata kimerítheti a fejlesztői VM-et. A hagyományos Compose a cpus és mem_limit mezőket támogatja; a deploy.resources.limits szintaxis hordozhatóbbnak tűnik, de a helyi motor nem minden implementációban alkalmazza. A laben tehát a működő mezőt kell preferálni, és a docker compose config kimenetén ellenőrizni, hogy a sikeres parse nem elvetett beállítást takar-e.

Több fájllal override-olhatunk: docker compose -f compose.yaml -f compose.debug.yaml. A compose.override.yaml a Docker Compose hagyományos implicit override fájlja, de a labreprodukálhatóság kedvéért jobb explicit -f sorrenddel hivatkozni rá, mert a Podman Compose ezt eltérően kezelheti.

38.4.2.5 Restart, update, recreate és data retention

A restart: unless-stopped a konténerprocessz újraindítását kéri a motortól, ha a konténer leáll. Ez nem hosztszintű automatikus indulás, és nem véd a hoszt újraindítása ellen, ha a motornak nincs startup-politikája.

A szokásos műveletek közötti különbség:

Művelet Hatás a konténerre Hatás a named volume-ra
docker compose up -d hiányzó service-eket létrehoz, configváltozáskor rekreál megtart
docker compose pull új image-t tölt le, futó konténert nem cserél megtart
docker compose up -d --force-recreate minden service-t újra létrehoz megtart
docker compose down konténerek és projektnet törlése megtart
docker compose down -v konténerek, projektnet és named volume törlése törli

A rekreáció során a named volume-ok adatmegmaradása a lényeg: a konténer újjászülethet, de az adatbázis fájljai a volume-ban maradnak. A down -v tehát destruktív művelet, és csak explicit tisztításkor szabad futtatni.

38.4.2.6 Local stack versus cluster availability

A Compose-féle local stack availability-je a hoszt és a lokális container-motor hatáskörében marad. Ha a hoszt leáll, a benne lévő összes Compose service is leáll; nincs másik node-ra ütemezés, nincs elosztott quorum. A restart policy és a healthcheck a processzszintű hibát csökkenti, de a hosztszintű rendelkezésre állást nem adja meg. Kubernetesben ezt majd a d39–d43 tárgyalja, ahol a scheduler, a replikáció és a node failure domain már külön réteg.

38.4.3 Kidolgozott példa

A példa a lab-cpp-stack projektet három service-szel indítja: C++ API, PostgreSQL, Redis. A lab tárgya lab-comp-01, a felhasználó labuser (UID 1000), a projekt könyvtára /home/labuser/lab-comp-01/lab-cpp-stack. A parancsok a docker compose beépülő modult használják; a motor és a compose verzióját a d188 profiljában rögzítettük, itt nem ellenőrizzük újra.

name: lab-cpp-stack

services:
  api:
    image: registry.lab.example/lab-cpp-api:1.0.0
    init: true
    restart: unless-stopped
    environment:
      BIND_ADDR: "0.0.0.0:8080"
      REDIS_URL: "redis://cache:6379/0"
      DB_PASSWORD_FILE: "/run/secrets/db_password"
    ports:
      - "${API_BIND:-127.0.0.1}:${API_PORT:-8080}:8080"
    depends_on:
      cache:
        condition: service_started
      db:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "/opt/lab-cpp-api/bin/readiness_probe", "-url", "http://127.0.0.1:8080/healthz"]
      interval: 5s
      timeout: 3s
      retries: 12
      start_period: 30s
    volumes:
      - ./config/api.yaml:/etc/lab-cpp-api/config.yaml:ro
    secrets:
      - db_password
    networks:
      - backend
    mem_limit: 512m
    cpus: 1.0

  db:
    image: docker.io/library/postgres:${POSTGRES_TAG:-16}
    restart: unless-stopped
    environment:
      POSTGRES_USER: lab
      POSTGRES_DB: lab
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U lab -d lab"]
      interval: 5s
      timeout: 3s
      retries: 12
      start_period: 10s
    secrets:
      - db_password
    volumes:
      - db-data:/var/lib/postgresql/data
    networks:
      - backend

  cache:
    image: docker.io/library/redis:${REDIS_TAG:-7}
    restart: unless-stopped
    command: ["redis-server", "--appendonly", "yes", "--maxmemory", "128mb", "--maxmemory-policy", "noeviction"]
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 3s
      timeout: 2s
      retries: 10
      start_period: 5s
    volumes:
      - cache-data:/data
    networks:
      - backend

secrets:
  db_password:
    file: ./secrets/db_password.txt

networks:
  backend:
    driver: bridge

volumes:
  db-data:
  cache-data:

A debug service külön override fájlban él, hogy normál indításkor ne jöjjön létre:

# compose.debug.yaml
services:
  debug:
    image: docker.io/library/alpine:${ALPINE_TAG:-3.20}
    profiles: ["debug"]
    command: ["sh", "-c", "while true; do sleep 60; done"]
    depends_on:
      api:
        condition: service_started
    networks:
      - backend

Az indítás előtt a titokfájlt létre kell hozni. A dummy jelszó csak labcélra szolgál, éles rendszerbe természetesen nem kerülhet.

# lab-comp-01, labuser, UID 1000
mkdir -p /home/labuser/lab-comp-01/lab-cpp-stack/secrets
umask 077
printf 'lab-dummy-password\n' > /home/labuser/lab-comp-01/lab-cpp-stack/secrets/db_password.txt

cd /home/labuser/lab-comp-01/lab-cpp-stack
docker compose config --quiet
docker compose config --images
docker compose up -d
docker compose ps --format 'table {{.Name}}\t{{.State}}\t{{.Status}}'
curl -fsS http://127.0.0.1:8080/healthz

Várható kimenet: a config --quiet nulla hibakóddal tér vissza; a ps táblázatban a cache és a db running és healthy állapotú, az api a start_period után válik healthyvé; a curl HTTP 200-at ad. Ezután a debug profillal ellenőrizhető a DNS-feloldás:

docker compose -f compose.yaml -f compose.debug.yaml up -d --profile debug
docker compose -f compose.yaml -f compose.debug.yaml exec debug sh -c 'getent hosts api db cache'

Az api, db és cache nevek feloldódnak a backend hálózaton. A leállítás a named volume-okat megtartja:

docker compose -f compose.yaml -f compose.debug.yaml down
docker volume ls --filter name=lab-cpp-stack_db-data

A kimenetben a lab-cpp-stack_db-data volume megmarad. A docker compose down -v ezt is törölné, ezért a tisztításnál név szerint és csak a labprojektben szabad kijelölni.

38.4.4 Tipikus hibák és ellenpróbák

Startup race a depends_on rövid formájával. Ha az API a db konténer processzindulása után azonnal kapcsolódni próbál, a PostgreSQL még nem biztos, hogy elfogadja a kapcsolatot. Tünet: az API induláskor connection refused, majd crash-loopol. Hipotézis: a dependency nem readiness-alapú. Adatgyűjtés: docker compose ps és a db logjainak figyelése. Javítás: condition: service_healthy és healthcheck; egy változtatással induljunk, majd docker compose up -d és az API log ellenőrzése.

A healthcheck nem alkalmazásreadiness. A pg_isready csak az adatbázis szintjét igazolja, a C++ API saját migrációja vagy cache-elérése még hibás lehet. Tünet: a db healthy, az API mégis 500-at ad. Az ellenpróba: fusson a saját readiness-probe a konténerben; ne a db healthcheckére építsünk.

Titok environment-ben vagy verziókezelt .env-ben. A jelszó a docker inspect kimenetéből is kiolvasható lehet, illetve commitolódhat. Tünet: secret a Git historyban. Helyes állapot: secrets fájl, chmod 600 és .gitignore; a konténer a /run/secrets/db_password fájlt olvassa.

A docker compose down -v véletlen adattörlést okoz. Tünet: a stack újraindítása után üres adatbázis. Ellenőrzés a törlés előtt: docker volume ls --filter name=lab-cpp-stack és név szerinti kijelölés. Ha a törlés megtörtént, a visszaállítás csak a d096–d100 backup/restore szerződése alapján lehetséges; a volume önmagában nem backup.

A resource limit nincs érvényben. A docker compose config lehet helyes, de a helyi tooling bizonyos deploy.resources mezőket figyelmen kívül hagy. Ellenpróba: docker stats --no-stream a futó konténeren; ha a limit nem látszik, használjunk a régi Compose szerinti mem_limit/cpus mezőt.

38.4.5 Feladatok

  1. Magyarázó feladat. Rajzold fel szövegesen a lab-cpp-stack konténerei közötti kapcsolatokat: melyik service milyen hálózaton éri el a másikat, hol van healthcheck és miért nem elég a depends_on rövid formája. Nevezd meg, hogy a db-data volume mikor marad meg és mikor törlődik.

  2. Adminisztrációs/konfigurációs feladat. Egészítsd ki a megadott compose.yaml-t egy compose.debug.yaml override-dal, hogy legyen egy debug profile-ú service, és az API mem_limit értéke legyen 256 MiB a debug indításban anélkül, hogy az alapfájlt módosítanád. Tedd ki a configot docker compose config paranccsal, és ellenőrizd, hogy a debug service csak --profile debug esetén jelenik meg. A megoldásban a parancsoknak explicit labtargetet kell tartalmaznia.

  3. Diagnosztikai/failure feladat. Szimuláld, hogy az adatbáziskonténer lecserélődik, de az adatnak meg kell maradnia. Futtasd le a szükséges docker compose parancsokat az adatbázis service rekreálásához, igazold, hogy a db-data volume a rekreáció után is létezik, majd igazold a különbséget a docker compose down és a docker compose down -v között. Hibajelenségként elemezd, mit tapasztalnál, ha valaki tévesen down -v-t futtatna, és milyen előfeltételnek kellene teljesülnie a visszaállításhoz.

38.4.6 Megoldások

  1. A megoldás lényege: az api a backend hálózaton db:5432 és cache:6379 címeket használ; a db és cache ugyanezen a hálózaton van, külső forgalmat csak az API fogad a 127.0.0.1:8080 porton. A depends_on rövid forma nem vár a db healthyre, ezért az API migráció/kapcsolódás előtt elhasalhat. A db-data named volume az up/down/force-recreate műveletek során megmarad, csak a down -v törli. Postcondition: a megvalósult hálózat és adatéletciklus a Compose desired state szerint értelmezhető.

  2. A compose.debug.yaml tartalma a fejezetben szereplő debug service, valamint:

services:
  api:
    mem_limit: 256m

A parancs:

cd /home/labuser/lab-comp-01/lab-cpp-stack
docker compose -f compose.yaml -f compose.debug.yaml --profile debug config > /tmp/lab-cpp-stack-rendered.yaml
grep -n 'mem_limit' /tmp/lab-cpp-stack-rendered.yaml
docker compose -f compose.yaml -f compose.debug.yaml config --services
docker compose -f compose.yaml -f compose.debug.yaml --profile debug config --services

Postcondition: az első config --services a debug service-t nem tartalmazza, a második --profile debug viszont igen. Az api alatt a renderelt configban mem_limit: 256m látható, az alap compose.yaml változatlan.

  1. Rekreáció:
cd /home/labuser/lab-comp-01/lab-cpp-stack
docker compose up -d --force-recreate db
docker volume ls --filter name=lab-cpp-stack_db-data
docker compose down
docker volume ls --filter name=lab-cpp-stack_db-data

A --force-recreate db az adatbázist új konténerből indítja, de a named volume megmarad. A down után a volume továbbra is listázódik. Ha viszont valaki docker compose down -v futtatna, a db-data törlődne, és a stack újra up indítása üres adatbázist hozna létre. A visszaállításhoz előzetes backupból kellene a d100 szerinti restore-t futtatni; ennek hiányában a down -v visszafordíthatatlan adatvesztést okoz. Postcondition: a named volume a rekreáció és a down után is létezik; a down -v veszélye explicit rollback/restore előfeltétellel dokumentált.

38.4.7 Rövid összefoglaló

A Compose-fájl egy lokális több service-ből álló stack desired stateje: service-eket, hálózatokat, named volume-okat és titkokat rendel egy projekt scope alá. A depends_on csak indít, a healthcheck és a condition: service_healthy viszont readinesshez közeli kaput ad; ezek támogatása verziófüggő. A titkokat fájlként csatoljuk, a profillal a debug service-eket alapból rejtjük, az override fájlokkal pedig a környezeteket különítjük el. A named volume túléli a konténer-rekreációt, de a down -v destruktív. A Compose hosztszintű availability-je nem helyettesíti a klaszter szintű ütemezést.

  • Compose-projekt: egy lokális stack service-, hálózat-, volume- és secret-definícióinak közös scope-ja.
  • Healthcheck: konténeren belüli, ismételt állapotpróba, amely a service_healthy feltétel alapja.
  • Named volume: a konténer élettartamától független, névvel címzett lokális adatterület.
