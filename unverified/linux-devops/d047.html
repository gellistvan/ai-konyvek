10.2 write, fsync, flush és crash consistency

10.2.1 Motiváció

Egy C++ szolgáltatás indításkor beolvassa a /etc/myapp/config.json fájlt. Amikor a vezérlő API frissíti a konfigurációt, a program open(O_TRUNC) + write() + close() sorozattal ír. Az alkalmazás fejlesztője úgy véli, a write() visszatérése után az adat a lemezen van. Ez a feltételezés hamis: a write() sikere csak annyit garantál, hogy az adat a kernel page cache-ébe került, azaz a processz oldaláról olvasható. Ha ebben a pillanatban a tápfeszültség megszakad, a dirty adat elveszhet, a fájl üres vagy félig írt maradhat. A d046 bemutatta az I/O rétegeket; jelen alfejezet a tartóssági szerződést határolja pontosan program, kernel, fájlrendszer és eszköz között.

10.2.2 Definíció és működés

10.2.2.1 Buffered write és dirty page

A Linux VFS rétegében a write() a processz userspace pufferéből a kernel page cache-be másol. A megváltozott lap dirty page. A write() normál esetben a másolás után visszatér, anélkül hogy a blokkréteghez nyúlna. A háttérben a kernel writeback mechanizmusa idővel kiírja a dirty page-eket. A dirty page-ek tehát a rendszer futó állapotában konzisztensek, de power-loss esetén nem tartósak.

10.2.2.2 fsync és fdatasync

A fsync(int fd) rendszerhívás két dolgot tesz: elindítja az adott fájlhoz tartozó dirty adat- és metaadatoldalak kiírását, majd megvárja, amíg a blokkréteg és az eszköz visszaigazolja, hogy azok tartósan a médiumra kerültek. Ez utóbbi gyakran egy device flush műveletet jelent. A fdatasync(int fd) szűkebb garancia: csak az adatok és a visszaolvasáshoz szükséges minimális metaadatok (pl. a fájlméret) kiírását kéri. Ha a fájlméret nem változott, a fdatasync() elkerülheti például az mtime frissítését. A sync() rendszerhívás az egész rendszer dirty oldalait indítja ki, de a visszatérése után nem feltétlenül várta meg az összes eszközt. (Ez a sync() szemantika függ a kernelverziótól; régebben a sync csak ütemezett, az fsync viszont várt. Modern Linuxban a sync() is vár, de az fsync az egyes fájlra vonatkozó garancia.)

10.2.2.3 Device flush

A storage eszköz gyakran rendelkezik írási gyorsítótárral (write cache). Az eszköz a cache-be írt adatot már késznek jelezheti, miközben a médiumra még nem került. A fsync ezért a blokkrétegben flush/barrier kérést ad ki, amely a cache kiürítésére utasítja az eszközt. Ha az eszköz power-loss protected cache-el rendelkezik, a flush után az adat tartós; ha nem, a tartósság nem garantálható, még akkor sem, ha az eszköz nem jelez hibát.

10.2.2.4 Atomic rename versus durability

A POSIX rename() ugyanazon fájlrendszeren belül atomikusan cseréli a névbejegyzéseket. Ez process szintű láthatósági garancia: egyetlen másik processz sem lát félig kész állapotot; a régi vagy az új fájl jelenik meg. Ez azonban nem durability garancia: a névbejegyzés változása a directory inode-jában dirty adat, amely power-loss esetén elveszhet. A tartós frissítéshez a directoryt is fsyncelni kell.

10.2.2.5 Directory fsync és névbejegyzés

A directory maga is fájl, pontosabban inode, amelynek adata a nevek és az inode-számok párosai. Amikor a rename() lefut, a szülő directory tartalma módosul. Ha a rename után csak a file data-t fsynceljük, a directory bejegyzés nincs kiírva. Crash esetén a fájlrendszer-visszaállítás során a régi név vagy a hiányzó név jelenhet meg. A protokoll ezért megköveteli a directory fájldeszkriptor fsync hívását.

10.2.2.6 Filesystem journal és CoW előkép

A journaled fájlrendszerek (ext4, XFS) a metaadat-változásokat előbb a journalba írják, majd commitolnak, végül a tényleges helyükre írnak. A journal commit is flush-t igényel. Ha a power-loss a commit előtt történik, a tranzakció visszajátszás nélkül elvész; ha a commit után, a visszajátszás helyreállítja a konzisztens állapotot. A copy-on-write (CoW) fájlrendszerek (Btrfs, ZFS) az új adatot új blokkba írják, majd egy atomi mutatófrissítéssel teszik láthatóvá. Itt a mutatófrissítés atomicitása és tartóssága a meghatározó, nem a felülírás.

A következő táblázat összefoglalja a rétegek tartóssági vállalását:

Réteg Művelet Tartóssági vállalás
Program write() Adat a kernel page cache-ben; power-loss után nem garantált.
Kernel VFS fsync()/fdatasync() Dirty adat/metadata kiírása és várakozás a blokkréteg visszaigazolására.
Blokkréteg flush/barrier Eszköz cache kiürítése a médiumra.
Fájlrendszer rename() Atomikus névcsere azonos filesystemen; durability nélkül.
Eszköz cache flush Power-loss protected cache esetén tartós médium állapot.

10.2.2.7 Power-loss cache és szerverhiba

A szerverhiba kétféle lehet: kernel crash vagy áramszünet. Kernel crash esetén a page cache tartalma elveszik, mert a memória nem íródik ki; az eszköz cache viszont megmaradhat, ha van tápellátása. Áramszünet esetén mind a page cache, mind a nem védett eszköz cache elveszik. A gyakorlatban a rendszertervezőnek fel kell tételeznie, hogy az fsync nélküli write-ok elveszhetnek, és a védelem nélküli eszköz cache is veszélyes. A tartós protokollnak mindig explicit fsync/flush hívással kell zárnia.

10.2.3 Kidolgozott példa

A következő C++ függvénypár egy JSON konfigurációs fájlt frissít. Az első a naiv, a második a crash-consistent protokollt valósítja meg.

#include <fcntl.h>
#include <unistd.h>
#include <string>
#include <stdexcept>
#include <cerrno>

void write_config_naive(const std::string& path, const std::string& data) {
    int fd = open(path.c_str(), O_WRONLY | O_CREAT | O_TRUNC, 0600);
    if (fd < 0) throw std::runtime_error("open");
    if (write(fd, data.data(), data.size()) != static_cast<ssize_t>(data.size())) {
        throw std::runtime_error("write");
    }
    close(fd);
    // Nincs fsync: power-loss esetén a fájl lehet üres vagy félig írt.
}

void write_config_durable(const std::string& dir,
                          const std::string& name,
                          const std::string& data) {
    std::string tmp = dir + "/" + name + ".tmp";
    int fd = open(tmp.c_str(), O_WRONLY | O_CREAT | O_TRUNC, 0600);
    if (fd < 0) throw std::runtime_error("open tmp");

    if (write(fd, data.data(), data.size()) != static_cast<ssize_t>(data.size())) {
        throw std::runtime_error("write tmp");
    }
    if (fsync(fd) != 0) throw std::runtime_error("fsync tmp");
    if (close(fd) != 0) throw std::runtime_error("close tmp");

    std::string final_path = dir + "/" + name;
    if (rename(tmp.c_str(), final_path.c_str()) != 0) {
        throw std::runtime_error("rename");
    }

    int dirfd = open(dir.c_str(), O_RDONLY | O_DIRECTORY);
    if (dirfd < 0) throw std::runtime_error("open dir");
    if (fsync(dirfd) != 0) throw std::runtime_error("fsync dir");
    close(dirfd);
}

Feltételek:

  • A dir és a name ugyanazon a fájlrendszeren van, így a rename atomikus.
  • A fsync a fájl adatát és metaadatait kiírja; a fdatasync is használható, mert a fájlméret változása miatt a size metadata is kiíródik. Az fsync a biztonság kedvéért a teljes metaadatot kéri.
  • A close() nem garantál tartósságot; ezért hívjuk meg az fsync-et a close előtt.
  • A rendszernek a storage eszközön a write cache-re vonatkozó garanciáit a kernel nem tudja ellenőrizni; ezt az üzemeltetési szerződésben külön kell rögzíteni.

Várható kimenet:

A naiv verzió után a fájl azonnal olvasható, de egy kill -9 utáni újrainduláskor a tartalom lehet üres. A tartós verzió a rename után a fájl a régi vagy az új tartalommal jelenik meg; nem lehet félig írt állapot. A tmp fájl nem marad.

Ellenőrzés strace-szal:

strace -e trace=write,fsync,rename,close ./config_writer_durable /etc/myapp config.json '{"port":8080}'

A várt kimenetben szerepel:

write(3, "{\"port\":8080}", 12) = 12
fsync(3) = 0
close(3) = 0
rename("/etc/myapp/config.json.tmp", "/etc/myapp/config.json") = 0
openat(AT_FDCWD, "/etc/myapp", O_RDONLY|O_DIRECTORY) = 4
fsync(4) = 0
close(4) = 0

Ez igazolja, hogy a protokoll minden tartóssági lépést végrehajtott.

10.2.4 Hibák és ellenpróbák

1. close() után azt hinni, hogy az adat tartós.
Tünet: a config elveszik power-loss után. Hipotézis: a close nem végez fsyncet. Adatgyűjtés: strace hiányzó fsync hívása. Egy változtatás: fsync(fd) hozzáadása a close előtt. Verifikáció: crash szimuláció után a fájl tartalma helyes.

2. rename után nincs directory fsync.
Tünet: a fájl tartalma megvan, de a neve nem létezik a crash után. Hipotézis: a directory bejegyzés dirty maradt. Adatgyűjtés: a journalban a rename commit hiánya. Egy változtatás: fsync(dirfd). Verifikáció: a crash után a névbejegyzés a várt állapotban van.

3. Temp fájl más fájlrendszeren.
Tünet: rename EXDEV hibával tér vissza. Hipotézis: a temp fájl nincs a célfájllal azonos mounton. Adatgyűjtés: df vagy stat a két útvonalra. Egy változtatás: a temp fájlt a célfájl könyvtárába írni. Verifikáció: a rename sikeres.

4. Az eszköz cache nem power-loss protected.
Tünet: minden fsync ellenére power-loss után sérült adat. Hipotézis: az eszköz write cache bekapcsolva, de nincs védelem. Adatgyűjtés: a tároló specifikációja, hdparm -W vagy smartctl write cache állapot. Egy változtatás: az eszköz cache letiltása vagy power-loss protected eszköz használata. Verifikáció: áramtalanítási teszt.

10.2.5 Feladatok

1. Magyarázó feladat. Magyarázd el, miért lehet egy write() visszatérése után az adat elvesztése power-loss esetén, és mi a különbség a fsync és fdatasync között. Milyen esetekben elegendő a fdatasync?

2. Adminisztrációs/konfigurációs feladat. Írj egy C++ vagy shell programot, amely egy megadott fájlt tartósan frissít atomi rename-nel. A program a lab-write-atomic nevet használja. Készíts strace kimenetet, amely bizonyítja a protokoll lépéseit, és teszteld a rename atomi láthatóságát két párhuzamos olvasóval.

3. Diagnosztikai/failure/recovery feladat. Egy szolgáltatás a konfigurációs fájlt open(O_TRUNC) + write + close sorozattal ír. Egy áramszünet után a fájl 0 bájt hosszú. Állapítsd meg a kiváltó okot, javítsd a frissítési protokollt, és írj egy ellenőrző eljárást, amely a rename előtti és utáni állapotot is ellenőrzi.

10.2.6 Megoldások

1. Megoldás. A write() a userspace és a kernel page cache közötti másolást végzi; a dirty page-ek a memóriában vannak, és a kernel ütemezi a kiírást. Power-loss esetén a memória tartalma elveszik. A fsync a fájl adat- és metaadatdirty oldalait kiírja, és megvárja az eszköz flush-t. A fdatasync csak az adatokat és a minimálisan szükséges metaadatokat írja ki. Ha a fájlméret nem változik, a fdatasync elkerülheti az mtime frissítést, így gyorsabb lehet. A fdatasync akkor elegendő, ha a tartóssághoz nincs szükség a teljes metadata frissítésére; például egy meglévő, változatlan méretű adatfájl módosításakor.

2. Megoldás. A fenti write_config_durable megvalósítja a protokollt. A strace kimenetben a write, fsync, rename, fsync(dirfd) sorrendnek kell szerepelnie. A párhuzamos olvasó teszt: indítsunk egy olvasót, amely folyamatosan olvassa a fájlt, miközben a frissítő cseréli. Azt tapasztaljuk, hogy az olvasó mindig a régi vagy az új teljes tartalmat látja, soha nem félig írtat. Postcondition: a fájl tartalma az új, a temp fájl nem létezik, és a directory bejegyzés tartós.

3. Megoldás. A kiváltó ok: a write utáni tartóssági szinkronizáció hiánya. Az open(O_TRUNC) törli a fájlt, a write a dirty page-be ír, a close nem flush-el. A javítás: a fájlt temp néven létrehozni, fsync a temp fájlon, rename a célra, majd fsync a directoryn. Az ellenőrzés: szimuláljuk a power-losst a program kill -9 és a gép újraindításával. A fájl a crash után a régi vagy az új tartalommal létezik, nem üres.

10.2.7 Rövid összefoglaló

A write() csak a page cache-be ír; a dirty page-ek power-loss esetén elveszhetnek. A fsync/fdatasync explicit tartóssági határt ad: kiírja a dirty adatokat és metaadatokat, majd megvárja az eszköz flush-t. Az atomi rename process szintű láthatóságot ad, de a névbejegyzés tartósságához a szülő directory fsync is szükséges. A crash-consistent protokoll ezért temp fájl írása, fsync, rename, directory fsync. A storage write cache power-loss védelmét külön kell ellenőrizni.

Továbbhasznált definíciók:

  • Dirty page: a page cache-ben módosított, de a blokkrétegbe még ki nem írt lap; power-loss esetén nem tartós.
  • fsync: rendszerhívás, amely a fájl dirty adat- és metadataoldalait kiírja, és megvárja az eszköz cache flush befejezését.
  • Atomic rename + directory fsync: ugyanazon fájlrendszeren atomi névcsere, amely process szinten félig kész állapot nélkül látszik, és a directory fsync a névbejegyzést tartóssá teszi.
