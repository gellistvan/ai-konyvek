19.4 NFS, SMB és hálózati file service

19.4.1 Motiváció

Egy C++ szolgáltatás gyakran több gépen fut: build artifact, közös konfiguráció, loggyűjtés vagy feldolgozandó adat kerül hálózati fájlmegosztásra, legyen az NFS vagy SMB. A szenior fejlesztő eddig a fájlkezelést helyi path-okon gondolta végig; a hálózati fájlmegosztás azonban új hibamódokat vezet be: hálózati késés, hitelesítési eltérés, kliens cache és érvénytelenné vált file handle. Ezért a remote filesystem accessnél az identity, a cache és a failure szemantikát is üzemeltetni kell, nem csupán a fájl elérését. Ez az alfejezet az NFSv4 és SMB/CIFS működtetési szerződését tanítja meg.

19.4.2 Definíció és működés

19.4.2.1 NFSv4, export, mount és locking

Az NFS (Network File System) a Unix/Linux hálózati fájlhozzáférési protokollja. Az NFSv4 stateful: a kliens és szerver kapcsolatot tart fenn, a mount és locking a protokoll része, nem külön rpcbind-orientált szolgáltatás. A szerver egy könyvtárat exportál az /etc/exports és az exportfs -a segítségével; a kliens a mount -t nfs4 hívással csatolja. A file handle a szerver oldali azonosító, amely egy inode-ra és namespace-re mutat; ha a szerveren változik a fájlrendszer vagy újraindul a szolgáltatás, a handle érvénytelenné válhat (stale handle). A locking NFSv4-ben a lease mechanizmushoz kötődik: a kliensnek időben meg kell újítania a lease-t, egyébként a szerver a zárakat felszabadíthatja. A nolock mount opció ezért kerülendő, mert megkerüli a konzisztenciát.

19.4.2.2 SMB/CIFS és share identity

Az SMB (Server Message Block, a CIFS a régebbi elnevezés) a Windows hálózati megosztás protokollja; Linuxon a Samba szerver biztosítja. Az SMB share-eket a szerver smb.conf fájlja definiálja, és a kliens a mount -t cifs paranccsal csatlakozik, megadva a share nevét, felhasználónevet és jelszót. A share identityt a szerver hitelesíti: a share-hez tartozó SMB felhasználó (pl. smbpasswd) dönt arról, hogy a kliens milyen jogokkal fér hozzá. A fájlhozzáférés a szerveren futó SMB process UID/GID-jével történik, így a kliens UID-je kevésbé közvetlen, mint az NFS AUTH_SYS esetén.

19.4.2.3 UID/GID mapping, root squash és auth

Az NFSv4 alapértelmezésben AUTH_SYS hitelesítést használ: a kliens elküldi a hívó UID/GID-t, a szerver pedig ezt fogadja el. Ez feltételezi, hogy a UID/GID névtér a gépek között konzisztens. Eltérés esetén a jogosultságok tévesek: a kliens user 1001 a szerveren más felhasználót jelenthet. A root squash opció a kliens root felhasználóját a szerveren nobody UID-re (általában 65534) képezi le, így védi a szervert a kompromittált kliens root ellen. A no_root_squash ezt kikapcsolja, ami csak szigorúan ellenőrzött, read-only vagy jól izolált export esetén fogadható el. A all_squash minden kliens usert nobody-ra képez le. Az SMB ezzel szemben a szerver által hitelesített SMB user alapján, a szerver UID/GID-jével dolgozik, tehát a kliens oldali UID mapping nem kerül közvetlenül a fájlrendszerre.

19.4.2.4 Client cache/lease és failover

Az NFS kliens attribútum- és adat cache-t használ a round-trip-ek csökkentésére. A close-to-open konzisztencia azt jelenti, hogy a többi kliens nem feltétlenül látja azonnal a változást, amíg a fájl megnyitása vagy close nem történik meg. A mount opciók közül az actimeo az attribútum cache időzítését szabályozza; a noac letiltja a cache-t, de jelentős lassulást okoz. A failover során a hard mount (alapértelmezett) a szerver elérhetetlensége esetén a syscall-t blokkolja, amíg a kapcsolat nem áll helyre; a soft mount timeout után hibát ad, de adatsérülést okozhat, ha a write megszakad. A nconnect opció több TCP kapcsolatot nyit, ami javítja a párhuzamos átvitelt.

19.4.2.5 Latency, timeout és stale handle

Minden NFS művelethez hálózati RTT és szerver oldali feldolgozás adódik. A mount timeo opciója a server response timeout decisecondben, a retrans pedig az ismétlések számát adja meg. A stale handle (ESTALE) akkor fordul elő, ha a fájlrendszerre mutató handle már nem érvényes, például az exportált directory-t a szerveren újra mountolták, vagy a file törlődött. A hiba megjelenhet a ls vagy cat során is; a kezelés általában a mount újraépítése. A latency clinic célja, hogy a hálózati és a permission hibát elkülönítsük.

19.4.2.6 Mount policy és service ordering

A kliensen a hálózati mountnak a hálózat felállása után kell megtörténnie. Az /etc/fstab _netdev opciója jelzi a hálózati függőséget; a x-systemd.automount késlelteti a mount-ot az első hozzáférésig. A szerveren az NFS service-nek a megosztott fájlrendszer mountja után kell indulnia, ezt a systemd unit ordering biztosítja (pl. After=local-fs.target). Ha a sorrend hibás, az export nem lesz aktív, és a kliens mount sikertelen.

19.4.3 Kidolgozott példa

Két labVM: lab-nfs-server (192.168.50.10) és lab-nfs-client (192.168.50.20). Cél: /srv/nfs/lab-share exportálása, kliens mount, írás/olvasás teszt, root squash demonstrálása.

  1. Szerver beállítás – target: lab-nfs-server, UID 0 (sudo).
# lab-nfs-server, UID 0 (sudo)
sudo apt-get update
sudo apt-get install -y nfs-kernel-server
sudo mkdir -p /srv/nfs/lab-share
sudo chown labuser:labgroup /srv/nfs/lab-share
sudo chmod 775 /srv/nfs/lab-share
echo '/srv/nfs/lab-share 192.168.50.0/24(rw,sync,no_subtree_check)' | sudo tee /etc/exports
sudo exportfs -ra
sudo exportfs -v

Várható kimenet: az exportfs -v mutatja a share-t, például /srv/nfs/lab-share 192.168.50.0/24(rw,sync,no_subtree_check). Ellenőrzés: systemctl is-active nfs-server és ss -tlnp | grep 2049.

  1. Kliens mount – target: lab-nfs-client, UID 0 (sudo).
# lab-nfs-client, UID 0 (sudo)
sudo apt-get update
sudo apt-get install -y nfs-common
sudo mkdir -p /mnt/lab-nfs
sudo mount -t nfs4 -o rw,hard,intr,nconnect=2 192.168.50.10:/srv/nfs/lab-share /mnt/lab-nfs
df -hT /mnt/lab-nfs

Várható kimenet: a df -hT mutatja a mount típusát nfs4, méretét és a /mnt/lab-nfs-t. Ezután teszt írás/olvasás:

# lab-nfs-client, as labuser (UID 1001)
echo "hello lab" > /mnt/lab-nfs/test.txt
cat /mnt/lab-nfs/test.txt

Várható: a fájl létrejön, a tartalom hello lab. A szerveren ls -ln /srv/nfs/lab-share/test.txt mutatja UID 1001-et.

  1. Root squash demonstrálás – target: lab-nfs-client és lab-nfs-server.
# lab-nfs-client, UID 0 (sudo)
sudo touch /mnt/lab-nfs/root-write-test

Várható hibajelenség: touch: cannot touch '/mnt/lab-nfs/root-write-test': Permission denied, mert a root a szerveren nobody-ként próbál írni, aki nem tagja a labgroup-nak, így nincs joga a 775 módú share-hez.

  1. Rollback / cleanup – a példa után az export eltávolítható:
# lab-nfs-client, UID 0 (sudo)
sudo umount /mnt/lab-nfs

# lab-nfs-server, UID 0 (sudo)
sudo exportfs -u 192.168.50.0/24:/srv/nfs/lab-share

19.4.4 Hibák és ellenpróbák

Tünet: a kliens mount parancsa időtúllépésig vár, majd mount.nfs: requested NFS version or transport protocol is not supported hibát ad.
Hipotézis: a szerver NFS service nem fut, vagy a hálózati tűzfal blokkolja a 2049/tcp portot.
Adatgyűjtés: a szerveren systemctl is-active nfs-server, ss -tlnp | grep 2049; a kliensen ping -c3 192.168.50.10.
Változtatás: ha a service nem fut, sudo systemctl start nfs-server; ha a port nincs nyitva, a labnetwork-re korlátozott tűzfalszabály.
Verifikáció: a mount újrapróbálása.

Tünet: a mount létrejött, de a felhasználó Permission denied hibát kap, vagy a root nem tud írni.
Hipotézis: root_squash, vagy UID mismatch a kliens és szerver között.
Adatgyűjtés: a szerveren ls -ln /srv/nfs/lab-share, a kliensen id labuser.
Változtatás: a share-en a labuser UID vagy a csoport jogosultságok beállítása, vagy a UID-k összehangolása.
Verifikáció: sudo -u labuser touch /mnt/lab-nfs/test2.txt.

Tünet: ls /mnt/lab-nfs fut, de cat /mnt/lab-nfs/file ESTALE hibát ad.
Hipotézis: a file handle érvénytelen, mert a szerveren a share újra mountolódott, vagy az export megváltozott.
Adatgyűjtés: mount | grep lab-nfs, df -hT /mnt/lab-nfs.
Változtatás: sudo umount /mnt/lab-nfs && sudo mount -t nfs4 ....
Verifikáció: cat /mnt/lab-nfs/file sikeres.

19.4.5 Feladatok

  1. Magyarázó feladat: Írd le a root_squash, no_root_squash és all_squash export opciók hatását. Hogyan lehet a szerveren ellenőrizni, hogy a kliens root milyen UID-ként jelenik meg? Mutasd be a parancsokat.

  2. Adminisztrációs/konfigurációs feladat: Állíts be egy NFS share-t lab-share néven a lab-nfs-server gépen, és mountold a lab-nfs-client gépen. A share a labuser UID 1001 számára írható, de a root nem írhatja. Add meg az /etc/exports sort, a mount opciókat, és ellenőrizd a működést.

  3. Diagnosztikai/failure/recovery feladat: A lab-nfs-client gépen a ls /mnt/lab-nfs mutatja a fájlokat, de egy fájl olvasása Permission denied hibát ad, míg egy másik fájl olvasása ESTALE hibát. Hogyan különíted el a hálózati hibát, a filepermission hibát és a stale handle-t? Mi a recovery mindkét hibára?

19.4.6 Megoldások

  1. A root_squash a kliens root UID-jét a szerveren nobody-ra képezi le; a no_root_squash megtartja a root UID-t; az all_squash minden kliens usert squash-el. A kliens root írjon egy fájlt a share-re, majd a szerveren ls -ln /srv/nfs/lab-share mutatja, hogy a fájl tulajdonosa 65534 (nobody), nem 0. Postcondition: a kliens root hatékony UID-je a szerveren nem root, így a szerver jogosultsági kontrollja érvényesül.

  2. Példa /etc/exports: /srv/nfs/lab-share 192.168.50.0/24(rw,sync,no_subtree_check,root_squash). A share könyvtárában a labuser UID 1001 és labgroup GID 1001 legyen, mód 775. A kliens mount opciói: -o rw,hard,intr,nconnect=2. A root squash biztosítja, hogy a root ne írhasson, a labuser viszont igen. Postcondition: a mount aktív, a labuser echo test > /mnt/lab-nfs/test.txt sikeres, a sudo touch /mnt/lab-nfs/root hibát ad.

  3. A hálózati hiba kizárható ping és ss -tlnp | grep 2049 segítségével. A permission hiba elkülönítése: a szerveren ls -ln /srv/nfs/lab-share és a kliens id. Ha a fájlok tulajdonosa a megfelelő UID, de a kliens más UID-ként próbál olvasni, az a permission. A stale handle: a df -hT és a file handle érvénytelenségét jelzi, hogy a többi fájl olvasható. Recovery: permission hibánál jogosultságok javítása a szerveren; stale handle esetén sudo umount /mnt/lab-nfs && sudo mount .... Postcondition: mindkét hiba elhárítása után a fájl olvasható, és a mount konzisztens.

19.4.7 Rövid összefoglaló

A hálózati fájlmegosztás (NFS, SMB) új hibamódokat hoz: identity mapping, kliens cache, lease, timeout és stale handle. Az NFSv4 a mount és locking protokollt a szerver és kliens között kezeli; az export opciók, mint a root_squash, a szerver védelmét szolgálják. Az SMB share identity a szerveren hitelesít, nem a kliens UID-jét használja. A mount policy és service ordering biztosítja a megbízható felépülést. A gyakori hibákat (permission denied, stale handle, mount timeout) címzett diagnosztikával kell elkülöníteni. Definíciók: NFS = hálózati fájlhozzáférési protokoll Unix rendszerekhez. File handle = a szerver által kiadott azonosító az exported fájlhoz. Stale handle = érvénytelenné vált file handle, ami ESTALE hibát okoz.
