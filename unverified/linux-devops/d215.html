43.5 Cluster restore és nodefailure labor

43.5.1 Motiváció

Egy Kubernetes cluster üzemeltetésében a node-ok kiesése és az etcd adatbázis sérülése eltérő helyreállítási utat igényel. Ha összekeverjük a control plane állapot (cluster objektumok, Deployment, Service, RBAC) és az alkalmazásadatok (PVC, PV, külső adatbázis) recovery-jét, akkor inkonzisztens állapotot hozunk létre, vagy adatvesztést okozunk. A labor célja, hogy egy eldobható clusterben gyakoroljuk a nodekiesés és az etcd snapshot restore következményeinek ellenőrzését, valamint a restaurálás utáni smoke tesztek futtatását.

A gyakorlat során külön igazoljuk a cluster és az alkalmazásadat helyreállítását: az etcd snapshot a Kubernetes API objektumok állapotát rögzíti, de a PersistentVolume-okban tárolt felhasználói adatokat nem tartalmazza. Ezért a restore előtt inventory-t készítünk, és a restore után külön ellenőrizzük a workload, a DNS, a volume és a hozzáférési rétegeket.

43.5.2 Definíció és működés

A laborban három réteget különböztetünk meg:

  • Control plane inventory: etcd memberek, API server, scheduler, controller manager, certificate és kubeconfig állapot.
  • Workload inventory: Deployment, StatefulSet, PodDisruptionBudget (PDB), Service és EndpointSlice objektumok.
  • Data inventory: PersistentVolumeClaim (PVC), PersistentVolume (PV), StorageClass és a ténylegesen csatolt volume.

Az etcd snapshot restore a Kubernetes dokumentáció által támogatott út a control plane állapot visszaállítására. A restore során az etcd adatbázist egy korábbi konzisztens állapotba állítjuk vissza. Ez nem érinti a node-okon futó kubelet állapotát és a volume-ok tartalmát, ezért a restore után újra kell egyeztetni a kubelet és az API server állapotát. A restore nem helyettesíti az alkalmazásadatok biztonsági mentését; ahhoz VolumeSnapshot vagy storage-szintű backup szükséges.

A Node NotReady állapot azt jelzi, hogy a kubelet nem tudja jelenteni a node állapotát az API servernek. Ennek oka lehet a node leállítása, hálózati szakadás vagy a kubelet processz összeomlása. A DiskPressure condition akkor jelenik meg, ha a kubelet által figyelt fájlrendszer (nodefs vagy imagefs) kihasználtsága meghaladja a küszöbértéket. Ekkor a kubelet pod-evictiont hajthat végre, hogy felszabadítson helyet.

A PodDisruptionBudget (PDB) korlátozza, hogy egy önkéntes drain során hány replikát lehet egyidejűleg elérhetetlenné tenni. Ha a PDB túl szigorú, a kubectl drain blokkolódik, és ezt fel kell oldani a karbantartási ablakban.

A certificate/access recovery akkor válik szükségessé, ha az etcd restore után a tanúsítványok lejártak vagy a CA nem egyezik. Ilyenkor a kubeadm alapú clusterben a kubeadm certs renew paranccsal újítjuk meg a komponensek tanúsítványait, majd újraindítjuk a static podokat.

43.5.3 Kidolgozott példa

A példa egy három node-os eldobható labclustert feltételez: lab-cp (control plane), lab-w1 és lab-w2 (workerek). A cluster verziója a lab support matrix szerint ellenőrizendő; a példa Kubernetes 1.29.x-et feltételez. A parancsokban a lab-admin@lab-cluster context és a lab-ns namespace szerepel. A műveletekhez sudo jogosultság szükséges a control plane node-on.

43.5.3.1 Inventory készítése

Első lépésként rögzítjük a kiindulási állapotot:

# Target: lab-cp (control plane), user: lab-admin, UID: 1000
# Előfeltétel: kubectl hozzáférés a lab-admin kubeconfigjával

kubectl --context lab-admin@lab-cluster get nodes -o wide
kubectl --context lab-admin@lab-cluster -n lab-ns get deploy,rs,pods,pdb,svc,endpointslices
kubectl --context lab-admin@lab-cluster -n lab-ns get pvc,pv,storageclass

Várható kimenet (illusztratív):

NAME      STATUS   ROLES           AGE   VERSION
lab-cp    Ready    control-plane   2d    v1.29.x
lab-w1    Ready    <none>          2d    v1.29.x
lab-w2    Ready    <none>          2d    v1.29.x

NAME                     READY   UP-TO-DATE   AVAILABLE   AGE
deployment.apps/lab-app  3/3     3            3           1d

NAME                                          STATUS   VOLUME   CAPACITY
persistentvolumeclaim/lab-data                 Bound    pv-lab   1Gi

43.5.3.2 etcd snapshot mentése

A control plane node-on az etcdctl elérhető a kubeadm által telepített konténerből vagy a host parancssorból. A snapshot mentéséhez a következő parancsot használjuk:

# Target: lab-cp, user: root, UID: 0
# Előfeltétel: /backup könyvtár létezik és írható
sudo ETCDCTL_API=3 etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /backup/etcd-snapshot-$(date +%Y%m%d).db

Várható kimenet:

Snapshot saved at /backup/etcd-snapshot-20250101.db

Ellenőrzés: a fájl mérete nagyobb, mint 0, és a snapshot status parancs megmutatja a konzisztenciát.

43.5.3.3 Node NotReady fixture

A lab-w1 node kiesését szimuláljuk egy drain és leállítás kombinációjával:

# Target: lab-cp, user: lab-admin, UID: 1000
kubectl --context lab-admin@lab-cluster cordon lab-w1
# Előfeltétel: a lab-w1 node Ready, a PDB engedi a drain-t
kubectl --context lab-admin@lab-cluster drain lab-w1 \
  --ignore-daemonsets --delete-emptydir-data --timeout=120s

Várható kimenet:

node/lab-w1 cordoned
node/lab-w1 drained

Ezután leállítjuk a node-ot (például SSH-n keresztül sudo shutdown -h now). Az API serverben a node állapota néhány tíz másodperc után NotReady lesz:

kubectl --context lab-admin@lab-cluster get nodes
NAME      STATUS     ROLES           AGE   VERSION
lab-cp    Ready      control-plane   2d    v1.29.x
lab-w1    NotReady   <none>          2d    v1.29.x
lab-w2    Ready      <none>          2d    v1.29.x

43.5.3.4 DiskPressure fixture

A lab-w2 node-on a kubelet által figyelt nodefs kihasználtságát ideiglenesen megnöveljük egy nagy fájl létrehozásával. Ez a node filesystem szintjén történik, nem a Kubernetes volume-ban:

# Target: lab-w2, user: root, UID: 0
# Előfeltétel: legalább 1 GiB szabad hely a nodefs-en
sudo dd if=/dev/zero of=/tmp/fill-disk bs=1M count=1024

A kubelet rövid időn belül frissíti a node conditiont:

kubectl --context lab-admin@lab-cluster describe node lab-w2 | grep -A5 Conditions

Várható kimenet (illusztratív):

Conditions:
  Type             Status  LastHeartbeatTime                 LastTransitionTime                Reason                       Message
  ----             ------  -----------------                 ------------------                ------                       -------
  MemoryPressure   False   ...
  DiskPressure     True    ...                               2025-01-01T10:00:00Z             KubeletHasDiskPressure       kubelet has disk pressure

A kubelet pod-evictiont hajthat végre, ha a disk pressure meghaladja a küszöböt. A teszt után a fájlt töröljük:

sudo rm /tmp/fill-disk

43.5.3.5 etcd snapshot restore

Feltételezzük, hogy a control plane etcd adatbázisa sérült, és a snapshotból állítjuk helyre. A restore előtt leállítjuk a kubeletet, hogy a static podok ne írjanak az etcd-be:

# Target: lab-cp, user: root, UID: 0
sudo systemctl stop kubelet
# Az etcd adatkönyvtárat elmentjük biztonsági okból
sudo mv /var/lib/etcd /var/lib/etcd.bak
# Restore az adott snapshotból
sudo ETCDCTL_API=3 etcdctl snapshot restore /backup/etcd-snapshot-20250101.db \
  --name lab-cp \
  --data-dir=/var/lib/etcd \
  --initial-cluster lab-cp=https://127.0.0.1:2380 \
  --initial-advertise-peer-urls https://127.0.0.1:2380 \
  --initial-cluster-token lab-etcd-cluster
# Jogosultság beállítása és indítás
sudo chown -R etcd:etcd /var/lib/etcd
sudo systemctl start kubelet

Várható kimenet: a kubelet elindítja a static podokat, és az etcd csatlakozik. Ellenőrzés:

sudo ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key endpoint health

43.5.3.6 Deployment/PDB/DNS/volume smoke tests

A restore után ellenőrizzük a workload és az adat réteget:

# Target: lab-cp, user: lab-admin, UID: 1000
kubectl --context lab-admin@lab-cluster -n lab-ns get deploy lab-app
kubectl --context lab-admin@lab-cluster -n lab-ns get pdb lab-app-pdb
kubectl --context lab-admin@lab-cluster -n lab-ns get svc lab-app-svc

DNS teszt egy ideiglenes pod segítségével:

kubectl --context lab-admin@lab-cluster -n lab-ns run dns-test --image=busybox:1.36 --rm -it -- nslookup lab-app-svc

A volume adat integritását egy egyszerű írás/olvasás ciklussal ellenőrizzük:

kubectl --context lab-admin@lab-cluster -n lab-ns exec deploy/lab-app -- sh -c 'echo test > /data/test.txt && cat /data/test.txt'

43.5.3.7 Certificate és access recovery

Ha a restore után a tanúsítványok lejártak vagy a kubeconfig nem érvényes, a kubeadm parancsokat használjuk:

# Target: lab-cp, user: root, UID: 0
sudo kubeadm certs renew all
sudo systemctl restart kubelet

A kubeconfig frissítése a kubeadm init által létrehozott admin.conf alapján történik, ha szükséges. A hozzáférés ellenőrzése:

kubectl --context lab-admin@lab-cluster auth can-i get nodes

43.5.4 Hibák és ellenpróbák

  • Az etcd snapshot nem tartalmazza a felhasználói adatokat. Ha valaki a volume-ok tartalmát az etcd restore-tól várja, adatvesztés következik be. A production adatokhoz VolumeSnapshot vagy storage-szintű backup szükséges, és az alkalmazásadat restore-t külön kell igazolni.
  • A restore után a node-ok és pod-ok állapota nem automatikusan konvergens. A node-ok a kubelet újraindulásakor újra regisztrálódnak, de ha a snapshot a node törlése előtt készült, a törölt node objektum visszaállhat, és a rajta lévő podok Terminating vagy Unknown állapotban ragadhatnak. Ilyenkor a node-ot újra kell törölni és a podokat újraütemezni.
  • A PDB blokkolhatja a drain-t. Ha a PDB maxUnavailable értéke túl alacsony, a kubectl drain timeoutot kap. A megoldás a PDB átmeneti módosítása vagy a karbantartási ablakban a replikák számának növelése, de ezt a change jegyzőkönyvben rögzíteni kell.
  • A DiskPressure eviction nem érinti a PersistentVolume-t. A kubelet csak az ephemeral tárolót (emptyDir, log) takarítja, a PVC-k tartalmát nem törli. Ha a volume-on lévő adat sérült, az más root cause, például a CSI driver hibája.
  • A tanúsítványok lejárata a restore után is fennállhat. Az etcd snapshot visszaállít egy régi állapotot, de ha a tanúsítványok a snapshot készítésekor már közel jártak a lejárathoz, a restore után azonnal lejárhatnak. Ilyenkor a kubeadm certs renew és a static podok újraindítása szükséges.

43.5.5 Feladatok

43.5.5.1 F1 – Inventory és recovery modell magyarázata

Készítsen inventory-t az adott labclusterben: sorolja fel a control plane etcd membereket, a workload Deployment/PDB/Service objektumokat és a data PVC/PV/StorageClass elemeket. Magyarázza el, miért nem elegendő az etcd snapshot a felhasználói adatok helyreállításához, és milyen kiegészítő mentés szükséges.

43.5.5.2 F2 – Node NotReady és drain adminisztráció

Egy worker node-on hajtson végre cordon és drain műveletet, majd állítsa le a node-ot. Ellenőrizze, hogy a node NotReady állapotba kerül, és a rajta lévő podok a PDB szabályai szerint újraütemeződnek. A drain során tapasztalt esetleges PDB blokkolást oldja fel indoklással. A végén törölje a node-ot a clusterből, és ellenőrizze a deployment replikák számát.

43.5.5.3 F3 – DiskPressure és etcd restore diagnosztika

A másik worker node-on idézzen elő DiskPressure állapotot a nodefs feltöltésével. Figyelje meg a kubelet eviction viselkedését, majd szüntesse meg a nyomást. Ezután a control plane node-on készítsen etcd snapshotot, szimuláljon etcd adatbázis sérülést (például a /var/lib/etcd tartalmának áthelyezése), és hajtsa végre a snapshot restore-t. Futtassa a Deployment/PDB/DNS/volume smoke teszteket, és készítsen rövid post-incident review-t a lépésekről és a helyreállítási időkről.

43.5.6 Megoldások

43.5.6.1 F1 megoldás

Az inventory parancsok:

kubectl --context lab-admin@lab-cluster get nodes -o wide
sudo ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key member list
kubectl --context lab-admin@lab-cluster -n lab-ns get deploy,pdb,svc,pvc,pv

Indoklás: Az etcd snapshot a Kubernetes API objektumait (Deployment, Service, PVC, RBAC) tartalmazza, de a PersistentVolume-okban lévő adatokat nem. A PVC/PV csak hivatkozás a storage backendre; a tényleges adat a storage rendszerben van. Ezért szükséges a VolumeSnapshot vagy a storage-szintű replikáció/backup, és ezek restore-ja külön igazolandó.

Postcondition: Az inventory dokumentált, és a recovery modellben a control plane és adat réteg elkülönítve szerepel.

43.5.6.2 F2 megoldás

A parancsok:

kubectl --context lab-admin@lab-cluster cordon lab-w1
kubectl --context lab-admin@lab-cluster drain lab-w1 --ignore-daemonsets --delete-emptydir-data --timeout=120s
ssh lab-w1 'sudo shutdown -h now'
kubectl --context lab-admin@lab-cluster get nodes

Ha a drain blokkolódik a PDB miatt, ellenőrizzük a PDB maxUnavailable értékét, és indokolt esetben a replikák számát ideiglenesen növeljük, vagy a PDB-t módosítjuk. A drain után a node leáll, és a kubelet nem jelent állapotot, így a node NotReady lesz. A podok a PDB által engedett mértékben átütemeződnek a maradék node-ra. A node törlése:

kubectl --context lab-admin@lab-cluster delete node lab-w1

Postcondition: A lab-w1 node törölve, a deployment replikái mind Ready állapotúak a megmaradt node-okon, a PDB továbbra is érvényes.

43.5.6.3 F3 megoldás

DiskPressure előidézése:

sudo dd if=/dev/zero of=/tmp/fill-disk bs=1M count=1024
kubectl --context lab-admin@lab-cluster describe node lab-w2 | grep -A5 Conditions

A kubelet DiskPressure=True conditiont állít, és pod-evictiont hajthat végre. Ezután:

sudo rm /tmp/fill-disk

Az etcd restore lépései a fenti kidolgozott példában szerepelnek. A smoke tesztek:

kubectl --context lab-admin@lab-cluster -n lab-ns get deploy lab-app
kubectl --context lab-admin@lab-cluster -n lab-ns run dns-test --image=busybox:1.36 --rm -it -- nslookup lab-app-svc
kubectl --context lab-admin@lab-cluster -n lab-ns exec deploy/lab-app -- sh -c 'echo test > /data/test.txt && cat /data/test.txt'

Postcondition: A cluster API elérhető, a deployment telepítve, a DNS feloldás működik, a volume írható/olvasható. A post-incident review dokumentálja a restore időt, a snapshot korát és az adatvesztés mértékét.

43.5.7 Rövid összefoglaló

Az etcd snapshot restore a cluster control plane állapotát állítja vissza, de nem helyettesíti az alkalmazásadatok mentését. A nodekiesés és a disk pressure különböző tüneteket okoz: a NotReady a kubelet kapcsolat megszakadását, a DiskPressure a nodefs telítettségét jelzi. A restore után a workload, DNS és volume smoke tesztekkel igazoljuk a rétegek működését. A PDB korlátozza a drain során elérhetetlenné váló replikákat, a tanúsítványok lejárata pedig a kubeadm certs renew paranccsal kezelhető. A post-incident review a root cause-t és a helyreállítási időt dokumentálja.

  • etcd snapshot: a Kubernetes API objektumok egy időpontra vonatkozó konzisztens mentése.
  • DiskPressure: node condition, amely a nodefs túl magas kihasználtságát jelzi, és evictiont válthat ki.
  • Smoke test: gyors, alapvető ellenőrzés a rendszer fő útvonalainak működésére.

43.5.8 Források és ellenőrzési hiányok

A forráskiindulópontok nem ellenőrzött dokumentációk; a konkrét lépések a labkörnyezet verziójától függenek.

  • Kubernetes dokumentáció
  • etcd dokumentáció
  • libvirt dokumentáció
  • SRE könyvek

Ellenőrzési hiányok: a Kubernetes és etcd pontos verziója, a kubeadm restore lépéseinek hivatalos dokumentációja, a DiskPressure küszöbértékek alapértelmezett értékei, a kubelet eviction pontos viselkedése.
