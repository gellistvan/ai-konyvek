53.5 Stateful service és recovery incidenslabor

A stateful szolgáltatások üzemeltetése nem ér véget a processz újraindításával: a PostgreSQL-ben lévő tranzakciós állapot, a Redis cache-ben lévő nem tartós adat, és a RabbitMQ queue-ban lévő kézbesítetlen üzenet más-más recovery-szerződést igényel. Ez a labor három hibamódot kapcsol össze egy alkalmazás adatútján: kapcsolatkimerülést, fogyasztói lemaradást és lemeznyomást. A cél, hogy a tanuló a tünet mögötti erőforrás- és alkalmazásállapotot különválassza, majd a helyreállítást a domain-invariánshoz kösse.

53.5.1 Definíció és működés

A stateful service contract egy szolgáltatás üzemeltetési szerződése, amely rögzíti az identitást, a tartós adatot, a backup/recovery módot és a kapacitáskorlátokat. A domain invariant olyan alkalmazási igazság, amelynek a hiba és a recovery során is teljesülnie kell: például egy rendelésazonosító legfeljebb egyszer kerül be a végleges tárolóba, miközben a queue legalább egyszer kézbesítheti az üzenetet.

A három szolgáltatás eltérő tartóssági szintet ad. A PostgreSQL a tranzakciókat WAL-ba írja, és csak akkor tekinti committed-nek, ha a WAL flush megtörtént. A PITR (point-in-time recovery) a base backup és a WAL-szegmensek visszajátszásával egy adott időpontra állít helyre; ezért a DB restore utáni smoke test nem csupán a séma meglétét, hanem a várható tranzakciós tartalmat is ellenőrzi. A Redis alapbeállítása cache: az adat nem tartós, és a maxmemory-policy szerint evictálhat. A cache loss elfogadható, ha a cache-ből hiányzó kulcsot a DB-ből újra lehet tölteni, de a laborban ez akkor igazolható, ha a repopulation után a cache találati aránya visszaáll. A RabbitMQ queue legalább egyszer (at-least-once) szemantikát ad: ha a consumer ack előtt elhal, az üzenet újra kézbesül. A termelő és a consumer közötti idempotens feldolgozás a domain invariant része.

A diagnosztika során a resource state és az application state elkülönítése: a kapcsolatkimerülés lehet erőforrás-limit (max_connections) vagy alkalmazás kapcsolatszivárgás; a lemeznyomás lehet a WAL, a queue paging vagy a Redis RDB snapshot következménye. Az incident timeline-ban minden méréshez forrás, időbélyeg és mért érték tartozik.

53.5.3 Fixture-ök

A labor négy hibamódot használ:

  1. Connection exhaustion: a PostgreSQL max_connections limitjét 10-re csökkentjük, az alkalmazás connection pool-ja 20 kapcsolatot nyit. Az eredmény: a lab-api HTTP 503-at vagy timeout-ot ad, a pg_stat_activity telített.
  2. Queue consumer lag: a lab-orders queue consumerét leállítjuk, a termelő 100 üzenetet küld. Az üzenetek felhalmozódnak, a queue depth és a memória/disk használat nő.
  3. Disk pressure: a Redis RDB snapshot könyvtárában (/var/lib/lab-redis) egy nagy, nem törölhető fájlt hozunk létre, amíg a fájlrendszer 95%-ra telik. A Redis BGSAVE meghiúsul, és a cache írások hibát adnak.
  4. Cache loss és message duplication: a Redis-t FLUSHALL-lal töröljük; a queue consumer ack előtt elhal, így az üzenetek újra kézbesülnek. A feldolgozó idempotencia-kulcs nélkül duplikátumot ír a DB-be.

53.5.4 Kidolgozott példa

A példában a lab-api felhasználói hibákat jelez. A diagnosztika lépései a következők.

53.5.4.1 1. Tünet és kezdeti adatgyűjtés

A lab-api 09:00-kor 503-as válaszokat ad. A lab-admin SSH-n labvm01-re lép, és az alkalmazás naplóját ellenőrzi:

# target: labvm01, UID: labadmin
journalctl -u lab-api --since "09:00" --no-pager | tail -n 50

Várt kimenet részlet:

lab-api: ERROR db connection failed: too many connections

Ez a DB erőforráslimitre utal. Ellenőrizzük a PostgreSQL aktív kapcsolatait:

# target: labvm01, UID: labadmin
sudo -u labdb psql -h /run/lab-postgresql -d labdb -c "
SELECT count(*) AS active, max_conn, state
FROM pg_stat_activity CROSS JOIN pg_settings
WHERE pg_settings.name='max_connections'
GROUP BY state, max_conn;"

Várt kimenet:

 active | max_conn | state
--------+----------+--------
     10 |       10 | active

A hipotézis: a max_connections nem elegendő, vagy a kapcsolatok szivárognak. A pg_stat_activity-ből kiderül, hogy a kapcsolatok idle in transaction állapotban vannak, ami az alkalmazás hosszú tranzakciójára utal. A laborban a max_connections 20-ra állítása azonnali mitigáció, de a valódi javítás a tranzakció lerövidítése.

53.5.4.2 2. Kapcsolat helyreállítás

# target: labvm01, UID: labadmin
sudo -u labdb psql -h /run/lab-postgresql -d labdb -c "ALTER SYSTEM SET max_connections = 20;"
sudo systemctl reload lab-postgres

A reload után az új érték érvényes. Ellenőrzés:

# target: labvm01, UID: labadmin
sudo -u labdb psql -h /run/lab-postgresql -d labdb -c "SHOW max_connections;"

Várt kimenet: 20.

A lab-api most 200-at ad. De a disk pressure még 09:10-kor jelentkezik: a Redis BGSAVE hiba:

# target: labvm01, UID: labadmin
journalctl -u lab-redis --since "09:10" --no-pager | grep -E "BGSAVE|disk"

53.5.4.3 3. Disk pressure

A df ellenőrzése:

# target: labvm01, UID: labadmin
df -h /var/lib/lab-redis

Várt: 95%-os használat.

A fájlrendszer megtelt; a Redis nem tud snapshotot írni. A laborban a nagy fájlt a cleanup script azonosítja. A diagnosztika:

# target: labvm01, UID: labadmin
sudo du -sh /var/lib/lab-redis/* 2>/dev/null | sort -h | tail -n 5

A legnagyobb fájl egy /var/lib/lab-redis/tmp/bigfile.bin, amelyet a laborfixture hozott létre. A mitigáció: a fájl törlése, majd a Redis BGSAVE újra:

# target: labvm01, UID: labadmin
sudo rm /var/lib/lab-redis/tmp/bigfile.bin
sudo -u labcache redis-cli -h 127.0.0.1 -p 6379 BGSAVE

A BGSAVE visszatér: Background saving started. Ellenőrzés: LASTSAVE időbélyeg frissül.

53.5.4.4 4. Queue lag és message duplication

09:20-kor a queue depth nő. A RabbitMQ management API-ból:

# target: labvm01, UID: labadmin
curl -s -u labqueue:dummy-password "http://127.0.0.1:15672/api/queues/%2F/lab-orders" | jq '{messages_ready, messages_unacknowledged, memory}'

Várt kimenet:

{"messages_ready": 98, "messages_unacknowledged": 2, "memory": 52428800}

A consumer leállt, az üzenetek nem ack-elődnek. A labor consumer-scriptje (/usr/local/bin/lab-orders-consumer) egy SIGTERM után elhalt. Újraindítás:

# target: labvm01, UID: labadmin
sudo systemctl restart lab-orders-consumer

A consumer újra kézbesíti az unacked üzeneteket. A DB labdb.orders táblájában a processing_id alapján kell deduplikálni:

SELECT processing_id, count(*) FROM labdb.orders GROUP BY processing_id HAVING count(*) > 1;

Várt: nincs sor. A laborban a consumer idempotens: a feldolgozás előtt INSERT ... ON CONFLICT (processing_id) DO NOTHING.

Ha duplikátum keletkezik, akkor a domain invariant sérült. A recovery nem a duplikátumok törlésével kezdődik, hanem a feldolgozó idempotencia-javításával, majd a duplikátumok tranzakcionális eltávolításával.

53.5.4.5 5. Backup/PITR és data smoke test

A disk pressure után a labbackup ellenőrzi a legutóbbi snapshotot. A labbackup script lab-restic-check futtatása:

# target: labvm01, UID: labadmin
sudo restic -r /var/backups/lab-stateful check

A várt kimenet: no errors were found.

A PITR teszteléséhez a labban külön állítható egy labdb-recovery instance, amely a restic-ből a base backup-ot és a WAL-t játssza vissza egy megadott időpontra. A parancs a labbackup wrapperrel:

# target: labvm01, UID: labadmin
sudo /usr/local/bin/lab-pitr-restore --manifest /etc/lab-backup/manifest.yaml --target-time "09:15:00" --recovery-instance labdb-recovery

Várt: az instance elindul, a pg_dump-ból vett smoke test lefut.

A smoke test a következőt ellenőrzi:

# target: labvm01, UID: labadmin
sudo -u labdb psql -h /run/lab-postgresql -d labdb -c "
SELECT count(*) FROM labdb.orders WHERE created_at < '2025-01-01T09:15:00+00:00';"

A count egyezik a backup manifestben rögzített expected_orders értékkel.

53.5.4.6 6. Incident timeline és SLO

Az incidens timeline:

Időpont Esemény
09:00 Első 503, alert: lab-svc p95 hiba
09:03 Diagnosis: DB connection exhausted
09:05 Mitigation: max_connections 20, reload
09:10 Redis BGSAVE hiba; disk pressure
09:12 Cleanup: bigfile.bin törlése
09:20 Queue lag észlelés
09:25 Consumer restart
09:40 PITR restore teszt és data smoke test
09:45 Utóteszt: lab-api p95 < 200 ms, error budget csökkenés

Az SLO-számítás: 30 perces ablakban a hiba időtartama 9:00-tól 9:20-ig 20 perc. A hibás kérések aránya a 9:00–9:05 között a DB hiba miatt 100%, a többi időben a cache nem okoz hibát. A lab-svc havi error budgetjéből a 20 perces teljes hibás ablak 20/43200≈0,046%20/43200 \approx 0,046\% burn-nek felel meg (a pontos képletet a lab manifest rögzíti).

53.5.5 Hibák és ellenpróbák

Gyakori hiba, hogy a tanuló a FLUSHALL-t production cache-en futtatja, vagy a rm -rf /var/lib/postgresql/*-t a recovery során. A laborban a cache flush csak a lab-redis instance-on megengedett, és a DB adatkönyvtárat soha nem töröljük a PITR előtt.

Egy másik hiba a connection limit emelése a connection leak diagnosztizálása nélkül. A max_connections növelése memóriát fogyaszt, és elrejti a szivárgást; a pg_stat_activity-ben az idle in transaction állapotú kapcsolatok tartósan nyitva maradnak. A laborban a mitigáció után a hibás tranzakciót is be kell zárni.

A message duplication javításakor a duplikátumok törlése önmagában nem megoldás, ha a fogyasztó továbbra is nem idempotens. Előbb a consumer-t kell javítani, majd a duplikátumokat tranzakcionálisan eltávolítani.

A disk pressure esetén a Redis és a PostgreSQL adatkönyvtárának a rm -rf parancs használata a labban tilos; csak a fixture által létrehozott fájlokat szabad törölni. A cleanup script lab-cleanup csak a lab- prefixű fájlokat érinti.

53.5.6 Feladatok

53.5.6.1 1. Fogalomtérkép a három service recovery-szerződéséről

  • Sorolja fel a labdb, labcache és labqueue tartóssági szintjét, megengedett adatvesztését és recovery-módját.
  • Adja meg mindegyiknél a domain invariánst.

53.5.6.2 2. Labfixture beállítása és disk pressure incidens

  • Csökkentse a labdb max_connections-ét 10-re, állítsa le a lab-orders-consumer-t, majd hozza létre a Redis snapshot-könyvtárban a bigfile.bin fájlt.
  • Hajtsa végre a backupot a manifest szerint.
  • Indukálja a disk pressure hatást, állítsa helyre a Redis BGSAVE-t, és ellenőrizze a backup integritást.

53.5.6.3 3. Összetett incidens diagnosztika és recovery

  • A lab-api 503-at és duplicate rendelést jelez. A queue depth magas, a DB kapcsolat limit elérte, a Redis cache üres.
  • Készítsen incident timeline-t, hajtsa végre a recovery-t, és igazolja a data smoke test-tel, hogy a domain invariáns teljesül.
  • Utána számolja ki a lab-svc SLO-hatását.

53.5.7 Megoldások

53.5.7.1 1. Fogalomtérkép

  • labdb (PostgreSQL): tartós, WAL-alapú tranzakciók; adatvesztés csak a committed tranzakciókban megengedett az RPO-n belül; recovery: PITR. Domain invariant: minden committed tranzakció visszaállítható a PITR időpontig.
  • labcache (Redis): nem tartós, eviction megengedett; adatvesztés teljes cache loss esetén is megengedett, mert a DB-ből újraépíthető; domain invariant: a cache-ből hiányzó kulcs mindig megbízhatóan betölthető a DB-ből.
  • labqueue (RabbitMQ): legalább egyszer kézbesítés; üzenetvesztés nem megengedett a durable queue és publisher confirm mellett; duplikáció megengedett, de az idempotens consumer-rel a deduplikált hatás garantált. Domain invariant: minden egyes processing_id legfeljebb egyszer kerül a DB orders táblába.

53.5.7.2 2. Fixture setup és disk pressure

A parancsok a labhost-on:

# target: labvm01, UID: labadmin
sudo -u labdb psql -h /run/lab-postgresql -d labdb -c "ALTER SYSTEM SET max_connections = 10;"
sudo systemctl reload lab-postgres
sudo systemctl stop lab-orders-consumer
sudo dd if=/dev/zero of=/var/lib/lab-redis/tmp/bigfile.bin bs=1M count=800
sudo /usr/local/bin/lab-backup --manifest /etc/lab-backup/manifest.yaml

A Redis BGSAVE hiba ellenőrzése:

# target: labvm01, UID: labadmin
sudo -u labcache redis-cli -h 127.0.0.1 -p 6379 BGSAVE

Várt kimenet: (error) MISCONF Redis is configured to save RDB snapshots, but it is currently unable to persist on disk.

Helyreállítás:

# target: labvm01, UID: labadmin
sudo rm /var/lib/lab-redis/tmp/bigfile.bin
sudo -u labcache redis-cli -h 127.0.0.1 -p 6379 BGSAVE
sudo restic -r /var/backups/lab-stateful check

A postcondition: a Redis BGSAVE sikeres, a restic check no errors, a bigfile.bin nem létezik.

53.5.7.3 3. Összetett incidens

A diagnosztika parancsai:

  • DB kapcsolatok: pg_stat_activity count > 10.
  • Queue depth: curl a RabbitMQ management API-ra, messages_ready > 50.
  • Cache: redis-cli DBSIZE 0.

A recovery sorrend:

  1. DB max_connections 20-ra és tranzakció zárás.
  2. Queue consumer restart, idempotencia-javítás.
  3. Cache repopulation a DB-ből.
  4. Data smoke test: a labdb.orders-ben a processing_id egyedi, és a count egyezik a manifesttel.

A timeline-t a fenti táblázathoz hasonlóan kell kitölteni. A SLO-hatás: a 30 perces ablak 15 percében a lab-api p95 hibás volt, ez a lab-svc error budget 15/43200≈0,035%15/43200 \approx 0,035\% elégetése.

53.5.8 Rövid összefoglaló

A stateful service recovery a tartóssági szint és a domain invariant mentén különül el: a PostgreSQL PITR-re állítható vissza és tranzakciós integritást igényel; a Redis cache loss esetén a DB-ből újraépíthető; a RabbitMQ legalább egyszer kézbesít, ezért a consumer idempotenciája kötelező. A diagnosztika a resource state és az application state különválasztásával indul, majd a mitigáció a kapacitás növelése vagy a hibás erőforrás eltávolítása. A labban a connection exhaustion, a queue lag és a disk pressure fixture-k a teljes incident timeline-t gyakoroltatják a backup és a data smoke test integrálásával. A recovery sikerességét a domain invariant ellenőrzése és a SLO-hatás utótesztje adja.

Továbbhasznált definíciók:
- Domain invariant: az alkalmazás által megkövetelt, a hiba és a recovery során is érvényes állapotfeltétel, például az üzenet feldolgozásának idempotens hatása.
- At-least-once delivery: a queue olyan szemantikája, amelyben az üzenet elvesztése nem megengedett, de a duplikált kézbesítés lehetséges.
- PITR: a DB base backup és WAL-szegmensek visszajátszásával egy adott időpontra történő helyreállítás.
