13.5 Automatizálási és diagnosztikai shell-labor

13.5.1 Motiváció

A d064-ben felépített adminisztrációs scriptek – idempotencia, hibakezelés, lock, részleges parancshiba – csak akkor válnak működtethetővé, ha a kimenetük determinisztikus, és a hibautakat tesztelni tudjuk. Egy read-only inventory scriptnek soha nem szabad megváltoztatnia a host állapotát, de attól még ugyanolyan hibái lehetnek, mint egy író scriptnek: speciális fájlnevek, lock contention, parancs meghiúsulása vagy nem megfelelő jogosultság. A cél, hogy a shell scriptet ugyanúgy ellenőrizhető automatizmusként kezeljük, mint egy C++ unit tesztet: legyen fixture, legyen várt output, legyen diagnosztikai exit code, és a változtató művelethez legyen runbook, rollback és verifikáció.

13.5.2 Definíció és működés

Read-only inventory script alatt olyan parancsfájlt értünk, amely a megadott baseline gyűjtést csak olvasással végzi el, a host tartós állapotát nem módosítja, és a kimenetet rendezett, várt alakban adja vissza. A read-only itt nem jelenti azt, hogy semmilyen ideiglenes fájl nem keletkezik: a /tmp alatti lock directory és ideiglenes munkakönyvtár használata megengedett, de a célrendszer konfigurációját, naplóit vagy csomagjait nem írjuk.

Fixture (tesztberendezés) egy előre legyártott, reprodukálható bemeneti könyvtár vagy állapot, amely tartalmazza a szándékosan nehéz eseteket is. Hibainjektálás (fault injection) azt jelenti, hogy a teszt során valamelyik feltételt szándékosan rosszra állítjuk – nemlétező könyvtár, már meglévő lock, sérült input –, és ellenőrizzük, hogy a script a megfelelő nem nulla exit code-dal és hibaüzenettel áll le.

Lock contention akkor lép fel, amikor ugyanaz a script egyszerre több példányban próbál futni. A mkdir atomikus: ha a lock directory létrehozása EEXIST hibát ad, akkor egy másik példány már dolgozik, ezért a második futásnak azonnal ki kell lépnie. A temporary file-ok mindig mktemp-pel készüljenek, és trap-pel takarítsuk őket, mert a script megölésekor is maradhat zárolt állapot.

A ShellCheck statikus elemző shell scriptekhez; a Bash parsing, idézés, escaping és pipefail buktatóit jelzi. A Bats (Bash Automated Testing System) shell szintű tesztkeret, amelyben a @test blokkok a script tényleges futtatásával ellenőrzik a kimenetet és az exit code-ot. A kettő nem helyettesíti egymást: a ShellCheck a szintaktikus és szemantikus gyanús mintákat, a Bats a viselkedést teszteli.

13.5.3 Kidolgozott példa

A laborhoston (labhost-01, Ubuntu Server 24.04 LTS lab VM, labadmin UID 1000) a következő read-only inventory scriptet használjuk. A script nem igényel root jogot, kivéve ha a felhasználó a rendszer teljes fájlrendszerét szeretné felderíteni; a példában egy saját fixture könyvtárat adunk meg.

#!/usr/bin/env bash
# lab-inventory.sh - read-only baseline inventory
# Target: labhost-01 (Ubuntu Server 24.04 LTS lab VM)
# UID: labadmin (1000), no root write operations.
# Usage: ./lab-inventory.sh [BASELINE_DIR]
set -uo pipefail

BASELINE_DIR="${1:-/opt/lab-fixture}"

# Lock directory, atomic mkdir protects against concurrent runs.
LOCK_DIR="${TMPDIR:-/tmp}/lab-inventory.lock"
if ! mkdir "$LOCK_DIR" 2>/dev/null; then
  echo "ERROR: inventory already running (lock $LOCK_DIR)" >&2
  exit 3
fi

WORK_DIR="$(mktemp -d /tmp/lab-inventory.XXXXXX)" || {
  rmdir "$LOCK_DIR" 2>/dev/null || true
  exit 4
}

cleanup() {
  rm -rf "$WORK_DIR"
  rmdir "$LOCK_DIR" 2>/dev/null || true
}
trap cleanup EXIT

err() {
  echo "INVENTORY_FAIL: $*" >&2
  exit 2
}

# 1. Identity
[ -f /etc/os-release ] || err "missing /etc/os-release"
# shellcheck disable=SC1091
. /etc/os-release
printf 'identity.hostname=%s\n' "$(hostname -s)" > "$WORK_DIR/out.txt" || err "hostname"
printf 'identity.os=%s\n' "$NAME" >> "$WORK_DIR/out.txt"
printf 'identity.os_version=%s\n' "$VERSION_ID" >> "$WORK_DIR/out.txt"

# 2. Kernel and uptime
printf 'kernel.release=%s\n' "$(uname -r)" >> "$WORK_DIR/out.txt" || err "uname"
IFS=' .' read -r up _ </proc/uptime || err "uptime"
printf 'kernel.uptime_s=%s\n' "$up" >> "$WORK_DIR/out.txt"

# 3. Memory
memory_kB="$(awk '/MemTotal/ {print $2}' /proc/meminfo)" || err "meminfo"
printf 'memory.total_kB=%s\n' "$memory_kB" >> "$WORK_DIR/out.txt"

# 4. CPU model, pipefail catches grep failure.
cpu_model="$(grep -m1 '^model name' /proc/cpuinfo | cut -d: -f2- | sed 's/^ *//')" || err "cpuinfo"
printf 'cpu.model=%s\n' "$cpu_model" >> "$WORK_DIR/out.txt"

# 5. Fixture inventory, whitespace-safe with NUL delimiter.
if [ ! -d "$BASELINE_DIR" ]; then
  err "BASELINE_DIR not found: $BASELINE_DIR"
fi
find "$BASELINE_DIR" -xdev -type f -print0 2> "$WORK_DIR/find.err" > "$WORK_DIR/files.nul" || {
  cat "$WORK_DIR/find.err" >&2
  err "find $BASELINE_DIR"
}
FILE_COUNT=0
while IFS= read -r -d '' _; do
  FILE_COUNT=$((FILE_COUNT+1))
done < "$WORK_DIR/files.nul"
printf 'filesystem.fixture_count=%s\n' "$FILE_COUNT" >> "$WORK_DIR/out.txt"

# Deterministic output: sorted by key.
LC_ALL=C sort "$WORK_DIR/out.txt"

A while IFS= read -r -d '' _; do ... done a find -print0 által előállított NUL-terminált rekordokat dolgozza fel. Ez azért szükséges, mert a shellben a szóköz, pontosvessző vagy új sor a fájlnév része lehet; a for f in $(find ...) típusú megoldás szétvágja a nevet, és a * is globbingot végez. A read -d '' a NUL-t használja rekordhatárnak, az IFS= üres beállítás pedig megakadályozza a whitespace trimmelését.

A script a kiírás előtt minden sort a LC_ALL=C sort-tal rendez. Ez a determinisztikus output miatt fontos: ha a jövőben új mezőt adunk hozzá, a diff még mindig stabil marad, és a különböző rendszerek közötti eltéréseket soronként tudjuk vizsgálni. A kimeneti sorok kulcs=érték felépítésűek.

Hozzuk létre a whitespace- és speciáliskarakter-fixture-t:

labadmin@labhost-01:~$ mkdir -p "/tmp/lab-fixture/with space"
labadmin@labhost-01:~$ mkdir -p /tmp/lab-fixture/empty
labadmin@labhost-01:~$ printf 'x\n' | tee "/tmp/lab-fixture/with space/file name;with*specials.log" \
    "/tmp/lab-fixture/plain.txt" >/dev/null
labadmin@labhost-01:~$ touch "/tmp/lab-fixture/with space/.hidden"

Várt kimenet (illusztratív, a tényleges uptime/memória a labhost mérésén múlik):

identity.hostname=labhost-01
identity.os=Ubuntu
identity.os_version=24.04
kernel.release=6.8.0-45-generic
kernel.uptime_s=12345
memory.total_kB=2048000
cpu.model=Intel(R) Xeon(R) Platinum 8175M CPU @ 2.50GHz
filesystem.fixture_count=3

Az ellenőrzéshez a Bats tesztfájlt használjuk (test_lab_inventory.bats). A setup() blokk új, izolált fixture-t készít, a teardown() takarít.

#!/usr/bin/env bats
# test_lab_inventory.bats - Bats tests for lab-inventory.sh
# Target: labhost-01 labadmin, no root expected.
setup() {
  FIXTURE_DIR="$(mktemp -d /tmp/lab-fixture.XXXXXX)"
  mkdir -p "$FIXTURE_DIR/with space"
  printf 'x\n' > "$FIXTURE_DIR/with space/file name;with*specials.log"
  printf 'x\n' > "$FIXTURE_DIR/plain.txt"
  touch "$FIXTURE_DIR/with space/.hidden"
}

teardown() {
  rm -rf "$FIXTURE_DIR"
}

@test "missing BASELINE_DIR yields INVENTORY_FAIL and status 2" {
  run ./lab-inventory.sh /no/such/lab-dir
  [ "$status" -eq 2 ]
  [[ "$output" =~ INVENTORY_FAIL ]]
}

@test "deterministic sorted output with whitespace-safe count" {
  run ./lab-inventory.sh "$FIXTURE_DIR"
  [ "$status" -eq 0 ]
  expected="filesystem.fixture_count=3"
  [[ "$output" =~ $expected ]]
  first_key=$(printf '%s\n' "$output" | head -n1 | cut -d= -f1)
  [ "$first_key" = "cpu.model" ]
}

@test "lock contention reports status 3" {
  LOCK_DIR="${TMPDIR:-/tmp}/lab-inventory.lock"
  mkdir "$LOCK_DIR"
  run ./lab-inventory.sh "$FIXTURE_DIR"
  [ "$status" -eq 3 ]
  [[ "$output" =~ already\ running ]]
  rmdir "$LOCK_DIR"
}

A ShellCheck futtatása:

labadmin@labhost-01:~$ shellcheck lab-inventory.sh

A példában a SC1091 figyelmeztetést lokálisan letiltottuk, mert az /etc/os-release nem statikusan elemezhető script. A Bats futtatás:

labadmin@labhost-01:~$ bats test_lab_inventory.bats
1..3
ok 1 missing BASELINE_DIR yields INVENTORY_FAIL and status 2
ok 2 deterministic sorted output with whitespace-safe count
ok 3 lock contention reports status 3

13.5.4 Hibák és ellenpróbák

Special filename / whitespace tünet: ha a script for f in $(find ...)-et használ, a fájlnév szóköznél kettészakad, * és ; shell metakarakterként viselkedik. A Bats teszt csak a fájlok számát ellenőrzi, de a hibás mennyiség azonnal jelzi a problémát. A megoldás a -print0 és read -d ''.

Partial command failure tünet: ha egy pipeline közepén lévő parancs meghibásodik, a pipeline exit code-ja a pipeline utolsó parancsáé lesz. set -o pipefail nélkül a grep | cut | sed hibája rejtve maradhat. A hibainjektálás: távolítsuk el ideiglenesen a /proc/cpuinfo-t? Ez nem lehetséges read-only laborban. Helyette használjunk egy nem létező baseline könyvtárat: a find hibája a pipefail nélkül is a pipeline utolsó sed-jének sikereként jelenne meg. A script a find hibát a WORK_DIR/files.nul írása közben a || ágban kezeli, így a hiba exit 2 lesz.

Lock contention tünet: két párhuzamos futtatásnál a második processz a mkdir EEXIST miatt exit 3-mal leáll. Ha a script a lock-ot a trap nélkül nem takarítaná, a lefutás után a következő futás is lock-olt maradna. Ezért a cleanup() rmdir-el, és a trap-et a sikeres lock után állítjuk be.

Temporary file és rollback: a /tmp alatti fájlokat mindig trap cleanup EXIT takarítsa. Ha a script megszakad (SIGINT), a trap fut, de csak a lock directory-t és a munkakönyvtárat takarítja. A trap nem fut, ha SIGKILL-t kap, ezért a lock directory-t a következő futás az EEXIST hibával jelzi; ilyenkor kézzel kell ellenőrizni, hogy nincs-e élő példány.

Runbook és rollback: egy író scriptnél a runbook a művelet előtti, műveleti és utáni lépést rögzíti. Például a /etc/motd frissítés:

#!/usr/bin/env bash
# lab-motd-update.sh - controlled /etc/motd update
# Target: labhost-01
# UID: root (sudo -H -u root)
set -uo pipefail

NEW_MOTD="$1"
[ $# -eq 1 ] || { echo "usage: $0 NEW_MOTD_FILE" >&2; exit 2; }
[ -f "$NEW_MOTD" ] || { echo "ERROR: new motd not found: $NEW_MOTD" >&2; exit 2; }

BACKUP="/var/backups/motd.lab.$(date +%Y%m%dT%H%M%S)"
cp -a /etc/motd "$BACKUP" || { echo "ERROR: backup failed" >&2; exit 1; }

rollback() {
  cp -a "$BACKUP" /etc/motd
  echo "ROLLBACK: restored $BACKUP" >&2
}
trap 'rollback' ERR

install --mode=0644 "$NEW_MOTD" /etc/motd || { echo "ERROR: install failed" >&2; exit 1; }
# Verify: non-empty and exact content match.
[ -s /etc/motd ] || { echo "ERROR: empty /etc/motd after update" >&2; exit 1; }
diff -u /etc/motd "$NEW_MOTD" >/dev/null || { echo "ERROR: verify diff failed" >&2; exit 1; }

trap - ERR
echo "OK: /etc/motd updated; backup at $BACKUP"

A runbook lépései: (1) root jog és új fájl meglétének ellenőrzése, (2) backup cp -a-val, (3) install a célhelyre, (4) diff -u verifikáció, (5) hiba esetén a trap ERR rollback. A rollback teszt: üres NEW_MOTD fájl esetén az install sikeres, de a diff -u hibát jelez, a trap ERR lefut, és az eredeti /etc/motd visszaáll. A backup fájl megmarad a további diagnózishoz.

13.5.5 Feladatok

  1. Magyarázó feladat. Írd le, miért használ a script find -print0-t és while IFS= read -r -d '' _-t, és miért hibás a for f in $(find ...) megoldás. Adj példát olyan fájlnévre, ahol a hiba azonnal látható.

  2. Adminisztrációs/konfigurációs feladat. A kidolgozott példa alapján hozd létre a lab-inventory.sh-t a labhost-01 hoston labadmin UID-dal. Készítsd el a /tmp/lab-fixture/with space könyvtárat és benne legalább két speciális nevű fájlt. Futtasd a scriptet a fixture könyvtárral, és mentsd a kimenetet /tmp/lab-inventory.out fájlba. Ellenőrizd, hogy a filesystem.fixture_count megegyezik a várt értékkel, és a kimenet rendezett kulcsú.

  3. Diagnosztikai/failure/recovery feladat. Futtass két lab-inventory.sh példányt párhuzamosan, és ellenőrizd, hogy a második a lock contention miatt exit 3-mal áll le. Ezután távolítsd el a lock directory-t, és ellenőrizd, hogy a script újra fut. Végül futtasd a lab-motd-update.sh-t egy üres /tmp/lab-motd.bad fájlal root joggal; várd, hogy a script rollback-et hajt végre, és a /etc/motd tartalma az eredeti marad.

13.5.6 Megoldások

  1. A for f in $(find ...) a shell word splitting után a szóközt, tabulatort, új sort és glob karaktereket is határolóként értelmezi. A file name;with*specials.log fájlnévben a szóköz két elemet, a ; új parancsot indítana, a * pedig a munkakönyvtár fájljaira terjeszkedne. A find -print0 NUL byte-ot ír, amit a shell read -d ''-vel tud kezelni, így a fájlnév egyetlen rekord marad. Postcondition: a filesystem.fixture_count pontos, és nincs fájlnév-fragmentáció.

  2. A parancsok:

    labadmin@labhost-01:~$ mkdir -p "/tmp/lab-fixture/with space"
labadmin@labhost-01:~$ printf 'x\n' > "/tmp/lab-fixture/with space/file name;with*specials.log"
labadmin@labhost-01:~$ printf 'x\n' > "/tmp/lab-fixture/plain.txt"
labadmin@labhost-01:~$ touch "/tmp/lab-fixture/with space/.hidden"
labadmin@labhost-01:~$ chmod +x lab-inventory.sh
labadmin@labhost-01:~$ ./lab-inventory.sh /tmp/lab-fixture > /tmp/lab-inventory.out
labadmin@labhost-01:~$ grep 'filesystem.fixture_count' /tmp/lab-inventory.out
filesystem.fixture_count=3
labadmin@labhost-01:~$ sort -c /tmp/lab-inventory.out && echo sorted
sorted

    A postcondition: a kimeneti fájl rendezett, a fixture count 3, és a script a futás után nem hagy maga után lock-ot vagy ideiglenes fájlt.

  3. Az első lock contention teszt:

    labadmin@labhost-01:~$ ./lab-inventory.sh /tmp/lab-fixture & ./lab-inventory.sh /tmp/lab-fixture & wait

    Az egyik futás sikeres, a másik a ERROR: inventory already running üzenettel és exit 3-mal áll le. Ha a lock directoryt kézzel töröljük:

    labadmin@labhost-01:~$ rmdir /tmp/lab-inventory.lock
labadmin@labhost-01:~$ ./lab-inventory.sh /tmp/lab-fixture >/dev/null
labadmin@labhost-01:~$ echo $?
0

    A motd rollback teszt:

    labadmin@labhost-01:~$ sudo -H -u root ./lab-motd-update.sh /tmp/lab-motd.bad
ERROR: verify diff failed
ROLLBACK: restored /var/backups/motd.lab.20250315T101000
labadmin@labhost-01:~$ diff -u /etc/motd /var/backups/motd.lab.20250315T101000 && echo restored
restored

    Postcondition: az eredeti /etc/motd tartalma változatlan, a backup fájl létezik és azonos az aktuális állapottal, a hibás üres fájl a rendszerben nem maradt aktív.

13.5.7 Rövid összefoglaló

A read-only inventory script akkor működtethető, ha a kimenete determinisztikus, a hibautak teszteltek, és a fájlneveket NUL-termináltan kezeli. A fixture és a hibainjektálás a shell scriptet ugyanolyan ellenőrizhetővé teszi, mint egy natív unit teszt: a lock contention, a partial command failure és a speciális fájlnevek mind külön teszttel fedhetők. A ShellCheck statikus analízissel a Bash buktatókat, a Bats pedig viselkedéstesztekkel a script contractját ellenőrzi. Író scriptnél a runbook, a backup és a trap ERR rollback biztosítja, hogy a sikertelen változtatás ellenőrzött módon álljon helyre. Három továbbhasznált definíció: read-only inventory script, fixture/hibainjektálás, lock contention.
