45.1 VPC/VNet, subnet, routing és cloud firewall

A cloud hálózati réteg tanulásakor a Linux kernelben szerzett fogalmakból érdemes kiindulni, de a provider policy máshol helyezkedik el. A NAT, mint cím- és portfordítás alfejezet SNAT/DNAT és conntrack modellje, valamint a Routing/overlay haladó labor underlay/overlay elkülönítése pontosan azt a szétválasztást készíti elő, amelyre itt szükség van: a VPC/VNet a provider software-defined networkjének overlay-je, a route table és a security csoportok a control és data plane szabályai, a guest kernel továbbra is a saját netfilter láncait futtatja.

A leggyakoribb félreértés, hogy a „public” és „private” subnet elnevezés biztonsági garanciát hordoz. A valóságban csak a route table és a tűzfalszabályok döntenek. Ezt a fejezet egy konkrét AWS-referencián vezeti le, de a fogalmak GCP/Azure megfelelőire is alkalmazhatók.

45.1.1 Definíció és hatókör

A VPC (Virtual Private Cloud) az AWS, a VNet az Azure, a VPC network a GCP elnevezése. A definíció: egy adott provider régiójában, egy account scope-on belüli, logikailag izolált IP-címtér, amelyhez IPv4 és opcionálisan IPv6 prefixeket rendelnek. Az izoláció a provider hálózati fabricjében valósul meg, nem a guest OS-ben; a tenantok forgalma nem keveredik, még akkor sem, ha azonos RFC 1918 címtartományt használnak. A VPC önmagában nem tartalmaz internet-hozzáférést, NAT-ot, DNS-t vagy tűzfalat; ezeket explicit erőforrások adják.

A subnet a VPC címterének availability zone-hoz kötött partíciója. Minden subnet egy AZ-hoz tartozik, és egy route table-hez van hozzárendelve. A public/private jelző konvenció: a public subnet route table-je tartalmaz egy default route-ot (0.0.0.0/0 vagy ::/0) egy Internet Gateway (IGW) felé; a private subneté nem, hanem tipikusan egy NAT gateway felé mutat. Az IGW regionális, redundáns, címfordítás nélküli kapu; a public IPv4-cím és a private IP közötti 1:1 leképezést a provider hálózati réteg végzi. A NAT gateway egy managed SNAT-ot végző eszköz, amely lehetővé teszi a private források kimenő internetét anélkül, hogy bejövő kapcsolatot engedne. A d153 SNAT-definíciója itt is érvényes: a forrás IP és port lecserélődik, a kapcsolatállapot tárolódik, a válasz visszafordul.

A private endpoint a provider belső szolgáltatásainak (például object storage, database API) elérésére injektált hálózati interface a VPC-ben; a forgalom nem hagyja el a provider hálózatát. A Security Group (SG) állapottartó tűzfal, amely az ENI szintjén érvényesül. Alapállapota: minden inbound deny, minden outbound allow. Csak engedélyező szabályok vannak, deny szabály nincs. A Network ACL (NACL) stateless, subnet szintű, sorszámozott szabálylistát alkalmaz, ahol explicit allow és deny is lehetséges. A kettőt együtt kell értelmezni, mivel különböző rétegekben dolgoznak.

A peering két VPC/VNet közötti közvetlen összeköttetés, nem tranzitív; a transit gateway hub-and-spoke topológiát ad, a VPN IPsec tunnel, a Direct Connect/Interconnect dedikált fizikai kapcsolat a provider hálózatába. A d165 alfejezet BGP/underlay fogalmai itt hasznosak, mert a transit gateway route propagation is control-plane konfiguráció.

45.1.2 Packet path levezetés

A levezetéshez egy példa topológiát használunk: VPC 10.0.0.0/16, public subnet 10.0.1.0/24, private subnet 10.0.2.0/24. A public subnetben egy web instance (10.0.1.10, public IP 198.51.100.10), a private subnetben egy app instance (10.0.2.20). A VPC route table-ök: public default route IGW felé, private default route NAT gateway felé.

Bejövő HTTPS flow a web instance felé:

  1. A külső kliens TCP SYN-et küld 198.51.100.10:443-ra. Az internetes útválasztás a provider edge-re juttatja.
  2. Az IGW a public IP-t a private IP-re (10.0.1.10) fordítja, és a csomagot a VPC fabricbe injektálja.
  3. A public subnet NACL inbound szabályai stateless módon ellenőrzik: például 0.0.0.0/0 tcp/443 allow. Ha nincs ilyen szabály, a csomag REJECT.
  4. A web instance ENI-jéhez rendelt SG inbound szabályai: ha a 443-as port engedélyezett, a csomag továbbhalad. Mivel az SG stateful, a válasz automatikusan engedélyezett.
  5. A guest kernelben a csomag megjelenik; ha van nftables/iptables, az további szűrést végezhet. Alapesetben elfogadja.
  6. A válasz a fordított úton halad. A NACL-nek kimenő szabályt is kell engednie, jellemzően 1024–65535 ephemeral portok.

Kimenő HTTPS flow az app instance felől:

  1. Az app instance (10.0.2.20) TCP SYN-et küld 203.0.113.25:443-ra. A guest route table default route-ja a subnet routerére mutat.
  2. A VPC route table a private subnetben a 0.0.0.0/0 destination-t a NAT gatewayre irányítja.
  3. A NAT gateway SNAT-ot hajt végre: a forrás 10.0.2.20 private IP-t lecseréli a saját public IP-jére és egy ephemeral portra. A kapcsolat állapotát tárolja.
  4. A válasz a NAT gatewayre érkezik, a conntrack mapping visszafordítja, és a csomag eljut az app instance-hoz.
  5. A private subnet bejövő NACL-nek engednie kell az ephemeral portokat, különben a válasz REJECT.

Ebből látható: a public/private név csak a route table-t jelzi, a tényleges elérést a SG, NACL és route konfiguráció együtt határozza meg.

45.1.3 Kidolgozott példa: lab-d221 VPC

Target: lab-sandbox AWS account 123456789012, region us-east-1, owner lab-user. Hipotetikus költségkeret: 20 USD/hó (nem ellenőrzött ár), expiry 48 óra, cleanup törli a VPC-t és minden hozzá tartozó erőforrást.

A desired state:

# Offline fixture: lab-d221 VPC desired state, nem provider API séma.
# Az azonosítók lab- prefixszel, expiry és owner megjelöléssel.
account_id: "123456789012"
region: us-east-1
owner: lab-user
expiry: "2025-12-31T23:59:59Z"
cleanup: "delete on expiry"
vpc:
  name: lab-d221-vpc
  ipv4_cidr: 10.0.0.0/16
  ipv6: false
subnets:
  - name: lab-d221-public-a
    az: us-east-1a
    cidr: 10.0.1.0/24
    route_table: lab-d221-rt-public
    kind: public
  - name: lab-d221-private-a
    az: us-east-1a
    cidr: 10.0.2.0/24
    route_table: lab-d221-rt-private
    kind: private
gateways:
  - name: lab-d221-igw
    type: internet
  - name: lab-d221-nat
    type: nat
    public_ip: lab-d221-eip
route_tables:
  - name: lab-d221-rt-public
    routes:
      - dest: 10.0.0.0/16
        target: local
      - dest: 0.0.0.0/0
        target: lab-d221-igw
  - name: lab-d221-rt-private
    routes:
      - dest: 10.0.0.0/16
        target: local
      - dest: 0.0.0.0/0
        target: lab-d221-nat
security_groups:
  - name: lab-d221-sg-web
    inbound:
      - cidr: 0.0.0.0/0
        port: 443
        proto: tcp
        action: allow
    outbound: allow_all
  - name: lab-d221-sg-app
    inbound:
      - cidr: 10.0.0.0/16
        port: 8080
        proto: tcp
        action: allow
    outbound: allow_all

Ellenőrzés: a describe-route-tables, describe-subnets, describe-security-groups, describe-nat-gateways kimenete megegyezik a desired state-tel. A postcondition: a public subnetből egy teszt instance eléri az internetet, a private instance kimenő internetet a NAT gatewayen át ér el, a web instance HTTPS választ ad. Mivel offline fixture, ezek várt eredmények, nem tényleges mérés.

A flow log bekapcsolása:

aws ec2 create-flow-logs \
  --resource-type VPC \
  --resource-ids vpc-0abc123def456 \
  --traffic-type ALL \
  --log-destination-type cloud-watch-logs \
  --log-destination arn:aws:logs:us-east-1:123456789012:log-group:lab-d221-flow-logs \
  --tag-specifications 'ResourceType=vpc-flow-log,Tags=[{Key=Name,Value=lab-d221-vpc-flow-log}]'

A flow logban egy REJECT bejegyzés például akkor jelenik meg, ha a NACL vagy SG eldobja. A guest tcpdump ezt nem látja.

45.1.4 Hibák és ellenpróbák

1. „A private subnet biztonságos.” A private subnet csak annyit jelent, hogy nincs default route IGW felé. Ha a route table hibás, vagy ha a NACL túlzottan enged, a hálózat nem védett. A biztonságot a security group és a NACL adja, nem a név.

2. SG stateful félreértése a NACL-hez képest. Ha egy SG inbound engedélyt ad, a válasz automatikusan engedélyezett; NACL-nél külön kimenő szabály kell. Gyakori hiba, hogy valaki csak inbound NACL-t állít be, és a válaszforgalom elakad.

3. NAT gateway hiánya vagy rossz route. A private subnetből kimenő internet csak akkor működik, ha a route table a NAT gatewayre mutat és a NAT gateway a public subnetben van. Ha az IGW-t használják, a private instance is kaphat public címet, de az más topológia.

4. Flow log értelmezése. REJECT bejegyzés jelentheti, hogy a NACL vagy SG elutasította, de a route hiánya nem mindig jelenik meg ugyanott. Ha a csomag egyáltalán nem hagyja el a subnetet a rossz route miatt, a flow logban hálózati interface szinten lehet sikertelen vagy nincs bejegyzés. A flow log nem helyettesíti a guest tcpdumpot.

5. Guest firewall és provider policy keverése. Ha a guest iptables blokkol, a flow log ACCEPT-et mutat, de az alkalmazás nem válaszol. Fordítva, ha a provider blokkol, a guest tcpdump nem lát csomagot. A diagnosztika során először ellenőrizd a flow logot, majd a guest tcpdumpot.

6. IPv6 dual-stack hiánya. Ha a VPC-ben nincs IPv6 prefix, a guest IPv6 csomagok nem haladnak. Ha az egress-only IGW vagy IPv6 route hiányzik, a kimenő IPv6 forgalom megszakad.

7. Managed DNS félreértése. A cloud DNS (például Route53 Resolver) a VPC-hez tartozó DHCP által hirdetett resolver lehet, de a private hosted zone csak akkor érhető el, ha a VPC-n be van kapcsolva a resolver.

45.1.5 Feladatok

F1 – Magyarázó feladat: Adott a fenti VPC. Írd le lépésenként, mi történik, amikor egy külső kliens 198.51.100.10:443 felé küld HTTPS kérést, és a web instance 10.0.1.10-n fut. Melyik rétegben milyen ellenőrzés történik? Mi kell ahhoz, hogy a válasz visszajusson?

F2 – Konfigurációs feladat: A YAML desired state alapján állítsd össze az AWS CLI parancssorozatot (vagy offline mockban) a VPC, subnetek, IGW, NAT gateway, route table-ek és security group-ok létrehozására. Adj meg legalább négy ellenőrző parancsot a postcondition igazolására. Rollback: mi a helyes törlési sorrend?

F3 – Diagnosztikai/failure feladat: A private subnetben lévő app instance nem tudja elérni a külső https://example.com címet. A flow log a private subnet ENI-re ACCEPT bejegyzéseket mutat, de a guest tcpdump csak SYN-eket lát, SYN-ACK-et nem. Mi a legvalószínűbb root cause? Milyen további ellenőrzésekkel erősíted meg, és hogyan javítod?

45.1.6 Megoldások

M1 megoldás: A kliens TCP SYN-je a public IP-re érkezik; az IGW 1:1 NAT-ot végez 10.0.1.10-re. A public subnet NACL inbound ellenőrzi a 443-as portot (stateless). Az SG a web instance ENI-jén ellenőrzi az inbound 443-at (stateful). A guest kernelben a web szerver elfogadja. A válasz a fordított úton: az SG automatikusan engedi a kimenőt; a NACL-nek szüksége van kimenő ephemeral tartományra; az IGW visszafordítja a private IP-t a public IP-re. A route table local bejegyzése a VPC-n belüli forgalmat kezeli. Feltétel: a NACL-nek a 0.0.0.0/0 kimenő 1024–65535 tartományt explicit engednie kell, különben a válasz nem jut ki.

M2 megoldás: A parancsok sorrendje: VPC létrehozása, subnetek, IGW létrehozása és attach, EIP allokálás, NAT gateway létrehozása a public subnetben, route table-ek létrehozása, route-ok hozzáadása, subnet asszociációk, security group-ok létrehozása és szabályok engedélyezése. Ellenőrzés: aws ec2 describe-vpcs --vpc-ids vpc-0abc123def456, aws ec2 describe-subnets --filters Name=vpc-id,Values=vpc-0abc123def456, aws ec2 describe-route-tables --filters Name=vpc-id,Values=vpc-0abc123def456, aws ec2 describe-security-groups --group-ids sg-0.... Rollback: először a NAT gateway törlése, EIP release; IGW detach és törlés; subnetek törlése; route table-ek törlése; végül a VPC törlése. Indoklás: a függőségi lánc miatt a NAT gateway aktív mappingje és az IGW attach gátolja a törlést.

M3 megoldás: A flow log ACCEPT a private subnet ENI-re azt mutatja, hogy a provider policy engedte a kimenő SYN-et. A guest tcpdump SYN-eket lát, SYN-ACK-et nem. A legvalószínűbb root cause: a NAT gateway nem működik megfelelően – nincs EIP, rossz subnetben van, vagy a route table default route-ja nem a NAT gatewayre mutat, hanem egy nem megfelelő célra. Mivel a SYN a guestből kimegy, de a válasz nem érkezik, a kimenő csomag elveszik a provider hálózatban. Ellenőrzés: aws ec2 describe-route-tables --route-table-id <private-rt> – a default route céljanak a NAT gateway ID-jét kell mutatnia; aws ec2 describe-nat-gateways --nat-gateway-ids <nat-id> – az állapotnak available-nek kell lennie, és a hozzá tartozó EIP-nek léteznie kell. Javítás: helyes route beállítás, NAT gateway a public subnetben, EIP társítás. Ha a flow log a NAT gateway ENI-n REJECT-et mutat, akkor a public subnet NACL blokkolja, azt is javítani kell.

45.1.7 Rövid összefoglaló

A VPC/VNet egy accounton belüli, régióhoz kötött, izolált IP-címtér. A subnet public vagy private jellege csak a route table default route-jából következik, nem biztonsági attribútum. A Security Group állapottartó, ENI-szintű tűzfal; a Network ACL stateless, subnet-szintű. A provider flow log és a guest tcpdump más réteget lát, ezért a hibakereséshez mindkettőt össze kell vetni. A kimenő internet a NAT gateway SNAT-ján keresztül működik; a bejövő a public IP 1:1 NAT-ján.

  • VPC/VNet: provider régióban elkülönített IP-címtér, amelyhez route table, subnet és tűzfalszabályok tartoznak.
  • Security Group: állapottartó, interface-szintű engedélyező tűzfal.
  • Network ACL: stateless, subnet-szintű, sorszámozott szabályokkal dolgozó tűzfal.
