10.3 Buffered/direct/async I/O és diagnosztika

10.3.1 Motiváció

Egy C++ szolgáltatás latency SLO-ja romlik, miközben a benchmark szép számokat mutat. A fejlesztő a std::fstream-mel mért írási sebességet látja, de a production adatbázis vagy storage motor nem ugyanazt az elérési utat használja: a page cache miatt a write() memóriába dolgozik, a tényleges device flush később vagy a durable media nem a benchmarknak megfelelő állapotban van. A réteghatárok és az API-módok közötti különbség nélkül a mérés félrevezető: a cache találati arány, a writeback késleltetés és az alignment hibák mind más-más rétegben jelentkeznek. Ez az alfejezet a buffered, direct és async I/O API-módokat, azok lifetime és alignment szerződéseit, valamint a diagnosztikát tanítja, hogy a mért szám mögött látni lehessen a kernel adatutat.

10.3.2 Definíció és működés

A buffered I/O (lásd d047 alfejezetet) a Linux page cache-en keresztül ír és olvas. A read()/write() syscall a user buffer és a page cache között másol, a kernel pedig writeback, tornyosulás és fsync hívással tartja a tartósságot. Az alkalmazás előnye az egyszerűség: tetszőleges buffer, offset és hossz, a kernel kezeli a lapozást, a prefetch-et és a scheduling tuple-t. Hátránya: duplikált másolás, cache trashing, és a tartóssági szerződés nem explicit.

A direct I/O (O_DIRECT) megkerüli a page cache-t. A syscall közvetlenül a device felé viszi az adatot, a user bufferből DMA útba. A szerződés szigorú: a user buffer, a file offset és a hossz logical block size-hoz (általában 4 KiB) igazítva kell legyen, különben EINVAL. A hívás szinkron a syscall szintjén, de a device write cache még mindig képes az adatot a volatile cache-be venni; a durable állapot csak fsync-kel garantált. Direct I/O akkor hasznos, ha az alkalmazás saját cache-t, adatbázis puffert vagy flash-re optimalizált réteget üzemeltet.

Az mmap felület a fájlt a processz virtuális címterébe képezi. A hozzáférés page faulton keresztül tölti be a lapokat a page cache-ből, a dirty lapokat a kernel writeback írja ki. Nincs explicit read/write syscall, de a memória hozzáférés processz-kontextusban fut; a módosítások msync-ig vagy a writebackig nem feltétlenül device-on. mmap tisztán olvasásnál kényelmes, írásnál a lapozási trash és a SIGBUS hiba lehetősége miatt diagnosztikai nehézség.

A sync/async completion elválasztja a syscall visszatérését az adat tényleges elkészültétől. A szinkron read/write a hívás visszatérésekor a másolás megtörtént – a direct I/O-nál a buffer tartalma már nem használható, amíg a hívás nem tért vissza. Az async I/O a completion csatornát (Linux AIO io_submit/io_getevents, vagy io_uring) használ: a buffer lifetime a completion beérkezéséig, nem a submit call visszatéréséig tart. A io_uring a modern kernel asynchronous I/O felülete (kernel 5.1+), amely submission/completion ring buffert használ; a verziószámot a labhoston ellenőrizni kell, mert a régebbi kerneleken csak a libaio vagy az O_DIRECT szinkron út elérhető. A buffer lifetime megszegése use-after-free vagy adatcsere hibához vezet.

A short IO részleges read/write: a kernel kevesebb bájtot másolhat vagy írhat, mint a kért hossz. Szinkron read-nél a signal, a socket vagy a csonka device ad; write-nél hasonlóan. Az alkalmazásnak ciklusban kell újrapróbálni, nem pedig hibaként eldobni. A direct I/O és a nagy blokkok esetén a short IO gyakoribb, mert a device queue, a flexibilis layout vagy a signal megszakíthatja a hosszabb utat.

10.3.3 Kidolgozott példa

A labhost: lab-vm01, UID 1000, user: labuser. A dedicated labkönyvtár: /srv/lab-data egy ext4 filesystemen. A cél megmérni a buffered és direct írási utat, cache hideg állapotban. A futtatható C++ program (io-modes.cpp) méri az 1 MiB-os írást, és váltogatja az O_DIRECT flag-et. Az ellenőrzés: a stat -c %o /srv/lab-data/io-test.bin mutatja az optimális I/O block size-ot (4K).

#define _GNU_SOURCE
#include <fcntl.h>
#include <unistd.h>
#include <cstdlib>
#include <cstring>
#include <cerrno>
#include <cstdio>
#include <chrono>
#include <cstdint>

int main(int argc, char** argv) {
    const size_t size = 1ULL * 1024 * 1024; // 1 MiB
    void* buf = nullptr;
    if (posix_memalign(&buf, 4096, size) != 0) {
        std::perror("posix_memalign");
        return 1;
    }
    std::memset(buf, 0x5a, size);

    bool direct = (argc > 1 && std::strcmp(argv[1], "direct") == 0);
    int flags = O_WRONLY | O_CREAT | O_TRUNC;
    if (direct) flags |= O_DIRECT;

    int fd = open("/srv/lab-data/io-test.bin", flags, 0644);
    if (fd < 0) {
        std::perror("open");
        std::free(buf);
        return 1;
    }

    auto start = std::chrono::steady_clock::now();
    ssize_t written = 0;
    while (written < (ssize_t)size) {
        ssize_t rc = write(fd, static_cast<char*>(buf) + written, size - written);
        if (rc < 0) {
            if (errno == EINTR) continue;
            std::perror("write");
            close(fd);
            std::free(buf);
            return 1;
        }
        written += rc; // short write kezelés
    }
    // Tartóssági pont: direct esetén is kell fsync, mert a device write cache lehet volatile
    if (fsync(fd) < 0) {
        std::perror("fsync");
    }
    auto end = std::chrono::steady_clock::now();

    double ms = std::chrono::duration<double, std::milli>(end - start).count();
    std::printf("mode=%s bytes=%zu elapsed_ms=%.2f\n",
                direct ? "direct" : "buffered", size, ms);
    close(fd);
    std::free(buf);
    return 0;
}

A fordítás és futtatás a labhoston:

# target: lab-vm01, user: labuser, uid=1000, cwd: /home/labuser
# előfeltétel: /srv/lab-data ext4, size >= 1 GiB
g++ -O2 -std=c++17 io-modes.cpp -o io-modes

# Page cache hideg állapot (root/sudo szükséges a drop_caches-hoz)
sync
echo 3 | sudo tee /proc/sys/vm/drop_caches

./io-modes buffered
./io-modes direct

Várható, illusztratív kimenet (hipotetikus, nem mért):

mode=buffered bytes=1048576 elapsed_ms=0.98
mode=direct bytes=1048576 elapsed_ms=1.35

A direct írás lassabb első hideg cache mellett, mert nincs page cache és a fsync a device write cache miatt többet várakozik. Ha a buffered írás után a drop_caches nélkül fut a direct, a page cache még tartalmazhatja a buffered írás lapjait, de O_DIRECT esetén ez nem számít: a direct út nem a page cache-ből olvas. A mérési jegyzőkönyvben fel kell tüntetni a filesystem típusát, a page cache állapotát, a processz scheduler class, a fsync jelenlétét.

10.3.4 Hibák és ellenpróbák

Hiba 1: EINVAL O_DIRECT esetén. Ha a buffer nem 4K-aligned (pl. new[]-ból származik), a write EINVAL hibát ad. Diagnosztika: perror, majd stat -c %o ellenőrzése, a buffer címének és az offsetnek a maradékosztálynak megfelelő igazítása. Ellenpróba: malloc és posix_memalign közötti különbség; a malloc általában 16 byte-hoz igazított, nem elég.

Hiba 2: Short write figyelmen kívül hagyása. Ha a program csak a write visszatérését vizsgálja, és nem ciklusban retry-ol, a fájl tartalma hiányos lehet. A write 0 bájtot is visszaadhat; ez nem feltétlenül hiba. A helyes minta a fenti példában látható: while (written < size).

Hiba 3: Async buffer lifetime megsértése. A io_uring submit call gyorsan visszatér, de a buffer még a kernel használatában lehet. Ha az alkalmazás a stack bufferre mutató pointert ad le, majd a függvény visszatér, a completion beérkezésekor use-after-free következik be. Diagnosztika: AddressSanitizer, vagy io_uring debug. A verzióellenőrzés: uname -r (kernel 6.8 az Ubuntu 24.04 LTS-ben) és a liburing csomag verziója; a régi kerneleken az io_uring opcode-ok hiányozhatnak.

Hiba 4: A benchmark a page cache-t méri, nem a device sebességet. A dd vagy fio buffered módban nagy memóriára meleg cache mellett irreálisan magas értéket mutat. Először drop_caches vagy direct=1 fio-ban, és a --direct=1 esetén az alignmentet az fio kezeli. A mérési jegyzőkönyvben rögzítendő a fsync megléte, mert anélkül a write cache is torzít.

Ellenpróba: tmpfs-en az O_DIRECT nem támogatott; a próbálkozás EINVAL hibát ad. Ez jó gyors teszt arra, hogy az alkalmazás helyesen kezeli a hiányzó direct támogatást, például fallback buffered módra.

10.3.5 Feladatok

  1. Magyarázó: Miben különbözik a buffered és direct írás tartóssági szerződése? Milyen alignment feltételeket kell teljesíteni a O_DIRECT-hez, és miért?

  2. Adminisztrációs: A lab-vm01-en a /srv/lab-data könyvtárban futtasd le a kidolgozott példát háromszor: hideg cache-sel buffered, hideg cache-sel direct, majd meleg cache-sel buffered. Rögzítsd az időket, a kernel verziót, a filesystem típust és a stat -c %o értékét. Értelmezd a különbséget.

  3. Diagnosztikai: Módosítsd a programot úgy, hogy a buffer new[]-ból származzon (malloc-kal) és O_DIRECT flaggel fusson. Jegyezd fel a hibát, az errno-t. Javítsd posix_memalign-re, és futtasd újra. Sikeres-e a direct írás? Ha tmpfs-en próbálod, mi történik?

10.3.6 Megoldások

1. feladat megoldása: A buffered írás a page cache-be megy, és a write() visszatérése nem jelenti az adat tartósságát; a kernel writeback aszinkron. Direct írásnál a write() közvetlenül a device-ra másol, de a device volatile write cache miatt a tartósságot külön fsync biztosítja. A O_DIRECT alignment feltétele: a user buffer címe, a file offset és a hossz a filesystem logical block size (általában 4 KiB) egész számú többszöröse kell legyen. Ennek oka a kernel/DMA korlát, mert a közvetlen device hozzáférés nem tud tetszőleges címről másolni. Postcondition: a tanuló meg tudja mondani, miért kaphat EINVAL hibát, és hogyan kell ellenőrizni a block size-ot.

2. feladat megoldása: A futtatás sorrendje:

# target: lab-vm01, UID 1000, cwd: /srv/lab-data
sync; echo 3 | sudo tee /proc/sys/vm/drop_caches
./io-modes buffered   # hideg cache, page cache miss, writeback késleltetés; sebesség a device-hoz közeli

sync; echo 3 | sudo tee /proc/sys/vm/drop_caches
./io-modes direct     # hideg cache, közvetlen device út; sebesség a device-ra jellemző

./io-modes buffered   # meleg cache: page cache találat, gyors

A várt trend: hideg cache-sel a buffered és direct hasonló nagyságrendű, meleg cache-sel a buffered sokkal gyorsabb, mert nem megy device-ra. A stat -c %o érték és a kernel verzió rögzítendő. Postcondition: a tanuló el tudja választani a cache hatást a device sebességtől.

3. feladat megoldása: A new[] a malloc-hoz hasonlóan általában 16 byte-hoz igazított, nem 4K-hoz. Az O_DIRECT hívásnál a write EINVAL hibát ad, mert a buffer címe nem felel meg. A posix_memalign(&buf, 4096, size) használata megoldja az alignmentet. Ha a fájl tmpfs-en van, az open O_DIRECT-tel EINVAL hibát adhat, mert a tmpfs nem támogatja a direct I/O-t – ez a diagnosztikai ellenpróba. Postcondition: a tanuló a hibát képes az errno, a filesystem típus és a buffer cím ismeretében root-cause-ra vezetni, és nem a kernel hibáját feltételez.

10.3.7 Rövid összefoglaló

A buffered I/O a page cache-en át dolgozik, a write() nem garantál tartósságot; a direct I/O (O_DIRECT) a cache-t megkerüli, de a user buffer, az offset és a hossz logical block size-hoz igazított kell legyen, különben EINVAL. A direct írás után is szükség lehet fsync-re a device volatile cache miatt. Az async I/O (libaio, io_uring) a buffer lifetime-ot a completionig hosszabbítja; a short read/write ciklusban retryolandó. A benchmark csak akkor értelmes, ha a page cache state, a fsync és a filesystem típus rögzítve van. Továbbhasznált definíciók: buffered I/O, O_DIRECT alignment contract, async completion buffer lifetime.
