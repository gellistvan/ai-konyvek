43.4 Node/control-plane health és cluster incident

43.4.1 Motiváció

A Kubernetes cluster incidense ritkán az alkalmazás logjában kezdődik. A C++ fejlesztő processz-szintű gondolkodása itt kiegészül egy elosztott vezérlési és adatátviteli modellel: a kubectl get pods által mutatott Pending vagy CrashLoopBackOff gyakran egy alacsonyabb réteg, például Node condition (csomópont-állapot), kubelet eviction (kilakoltatás) vagy etcd-lassulás következménye. A tanulási cél az, hogy a tünetet ne a Pod YAML-jában, hanem a node/control-plane határon kezdjük keresni. A fejezetben a lab- parancsok mindig explicit targetet, jogosultságot és ellenőrzést kapnak.

43.4.2 Definíció és működés

A cluster két fő síkra osztható. A control plane az API-servert, a scheduler-t, a controller-manager-t és az etcd-t foglalja magában; a data plane a kubeleteket, a container runtime-ot, a CNI/CSI pluginokat és a Pod-hálózatot. Ez a megkülönböztetés azért fontos, mert a node pressure és a DNS-hiba gyakran data plane jelenség, míg az API-timeout és az etcd-latency control plane jelenség.

A Node condition olyan kernel- és kubelet-által karbantartott állapotjelző, amelyet a Kubernetes API-ban a Node objektum status.conditions mezője tárol. A leggyakoribb típusok:

  • Ready: a kubelet képes podokat futtatni és a node regisztrálva van.
  • MemoryPressure, DiskPressure, PIDPressure: a kubelet által számított erőforrásnyomás.
  • NetworkUnavailable: a CNI hálózat nem konfigurált.

A pressure az eviction előfutára: a kubelet az --eviction-hard és --eviction-soft küszöbök alapján dönt a Pod kilakoltatásáról, mielőtt a kernel OOM-killer aktívvá válna. Ez különbözik a CPU-throttlingtól, mert a CPU-nál nincs eviction, csak scheduling késleltetés. A rendszer telítettségét (saturation) tehát erőforráscsoportonként kell mérni, nem egyetlen CPU-átlaggal.

Az availability az API-kérések sikeres aránya, míg a saturation a várakozó munka mennyisége. A kettőt külön kezeljük: egy etcd kvóta betelhet úgy, hogy az API még elérhető, de a kérések latenciája nő.

43.4.2.1 API latency/error/etcd health

A control plane health ellenőrzésére a Kubernetes read-only végpontjai alkalmasak:

# target: lab-control-1 (control plane, admin)
# read-only ellenőrzés
kubectl get --raw /readyz?verbose
kubectl get --raw /livez?verbose

A readyz a control plane komponensek függőségeit ellenőrzi; a ?verbose megmutatja, melyik komponens nem ready. Gyakori kimenet, ha az etcd lassú:

[+]ping ok
[+]log ok
[+]etcd ok
[+]poststarthook/start-kube-apiserver-admission-initializer ok
...

Ha az etcd nem OK, akkor a kubectl kérések etcdserver: request timed out jellegű hibát adnak. Az etcd saját diagnosztikája a cert könyvtárával futtatható:

# target: lab-control-1 (control plane, root)
# előfeltétel: etcdctl telepítve és /etc/kubernetes/pki/etcd cert elérhető
ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  endpoint health --cluster

A hibaarányt a kube-apiserver metricsban a apiserver_request_total és a apiserver_request_duration_seconds_bucket mutatja. A PromQL-lekérdezés például:

sum(rate(apiserver_request_total{job="apiserver",code=~"5.."}[5m])) by (resource)

43.4.2.2 Kubelet/runtime logs és node condition

Ha a node nem Ready, a kubectl describe node a state-t mutatja:

# target: lab-client (admin workstation, cluster context: lab-cluster)
kubectl describe node lab-worker-1

A kimenetben figyelni kell a Conditions szekcióra és az Events-re. A Ready=False okát a Message mező magyarázza. A node console-on a kubelet naplója:

# target: lab-worker-1 (node console, root)
journalctl -u kubelet -n 100 --no-pager
systemctl status kubelet

A container runtime szintjén a crictl használható (ha containerd fut):

# target: lab-worker-1 (node console, root)
crictl ps -a
crictl logs <container-id>

43.4.2.3 Disk/memory/PID pressure és eviction

A kubelet a node filesystemet, memóriát és PID-számot figyeli. A küszöböket a /var/lib/kubelet/config.yaml tartalmazza, például:

# cél: lab-worker-1 kubelet config, root
evictionHard:
  memory.available: "500Mi"
  nodefs.available: "10%"
  nodefs.inodesFree: "5%"
  pid.available: "1000"
evictionSoft:
  memory.available: "1Gi"
evictionSoftGracePeriod:
  memory.available: "1m"

Amikor a memória rendelkezésre állása az evictionHard.memory.available alá csökken, a kubelet evicteli a legkisebb priority class-szal rendelkező Podot, és a node MemoryPressure=True állapotba kerül. A DiskPressure az image- és container-réteg filesystemjére, nem a Pod emptyDir kötetére vonatkozik; a PIDPressure a node összes processzére.

43.4.2.4 CNI/CSI/DNS control/data plane

A hálózati hiba lehet a CNI plugin hibája. Az ellenőrzés a Pod-hálózat adatsíkjában:

# target: lab-worker-1 (node console, root)
ip addr show cni0
ip route

A CNI podok naplója a kube-system névtérből gyűjthető. Hasonlóan a CSI illesztőprogramok a PersistentVolume-csatolásnál hibázhatnak; ilyenkor a Pod ContainerCreating állapotban marad. A DNS hibák gyakran a CoreDNS podok restartjából vagy a service IP eléréséből erednek:

# target: lab-client (admin workstation, cluster context: lab-cluster)
kubectl get pods -n kube-system -l k8s-app=kube-dns
kubectl logs -n kube-system -l k8s-app=kube-dns --tail=50

A Pod belsejéből a DNS-feloldás tesztelhető, de előbb a Pod-nak futnia kell. A kubectl exec ugyanazt a service IP-t használja, mint a Pod.

43.4.2.5 Certificate/API dependency expiry

A kubeadm által létrehozott tanúsítványok lejártával a control plane komponensek közötti mTLS megszakad. Az ellenőrzés:

# target: lab-control-1 (control plane, root)
kubeadm certs check-expiration

A lejárat megújítható, de ez a control plane komponensek újraindítását is igényli. A nem kubeadm telepítésnél a certifikátumok nem automatikusan rotálódnak; a CA-t és a kiszolgálói certet külön kell ellenőrizni.

43.4.2.6 kubectl versus node console recovery

Ha az API elérhetetlen, a kubectl önmagában nem diagnosztikai eszköz. Ilyenkor a node console-on kell dolgozni: a kubelet naplójából, a static pod manifestekből (/etc/kubernetes/manifests/) és az etcd helyi állapotából kell meghatározni, hogy a control plane előbb áll-e helyre, mint a data plane. A parancsok targetje ilyenkor explicit node és root jogosultság.

43.4.3 Kidolgozott példa

A labclusterben lab-worker-1 node hirtelen NotReady, a lab-app névtérben futó lab-api Pod Pending, a kubectl get pods időnként timeouttal tér vissza.

Első lépés a node állapot:

# target: lab-client, cluster context: lab-cluster, user: lab-admin
kubectl get nodes

Várt kimenet:

NAME             STATUS     ROLES    AGE   VERSION
lab-control-1    Ready      master   35d   v1.30.0
lab-worker-1     NotReady   <none>   35d   v1.30.0
lab-worker-2     Ready      <none>   35d   v1.30.0

A kubectl describe node lab-worker-1 a következő conditionöket mutatja:

Conditions:
  Type             Status  LastHeartbeatTime                 LastTransitionTime                Reason                       Message
  ----             ------  -----------------                 ------------------                ------                       -------
  MemoryPressure   True    Mon, 01 Jan 2024 10:12:00 +0000   Mon, 01 Jan 2024 10:10:00 +0000   KubeletHasInsufficientMemory kubelet has insufficient memory available
  DiskPressure     False   ...
  PIDPressure      False   ...
  Ready            False   ...

Mivel a Ready=False oka MemoryPressure, a node console-on a memóriaállapot:

# target: lab-worker-1 (node console, root)
free -h
systemctl status kubelet
journalctl -u kubelet -g evict -n 20 --no-pager

Várt kimenet: a free -h Mem: available értéke 400 MiB alatt van, a journal pedig hasonló sort tartalmaz:

kubelet[1234]: Evicting pod lab-api-7f8d9b6c4d-abcde_lab-app(...) to reclaim memory

A root cause tehát a memórianyomás, nem a control plane. Az etcd ellenőrzés ezt megerősíti:

# target: lab-control-1 (control plane, root)
ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  endpoint health --cluster

Várt kimenet: minden etcd tag healthy, a latency normál. A hiba tehát data plane pressure.

A javítás két részből áll. Először a lab-worker-1-en evictálunk egy alacsony prioritású, nem kritikus lab-batch Podot, hogy a node felszabaduljon, majd a kubeletet újraindítjuk a state rendezése miatt:

# target: lab-worker-1 (node console, root)
# előfeltétel: a lab-batch Pod nem production, törölhető
kubectl delete pod lab-batch-xyz --grace-period=30 --wait=true

De kubectl nem elérhető a pressure miatt? A kubelet eviction magától is kilakoltat, ezért a delete inkább a kubelet által már evictált Pod végleges törlése az API-ból. A node console-on:

# target: lab-client, cluster context: lab-cluster
kubectl delete pod lab-api-7f8d9b6c4d-abcde --grace-period=0 --force

A node Ready visszaállását a következő ellenőrzi:

# target: lab-client, cluster context: lab-cluster
kubectl wait --for=condition=Ready node/lab-worker-1 --timeout=120s

A lab-api Pod újra ütemezése után a kubectl get pods -n lab-app -w mutatja a Running állapotot. Ha a memória továbbra is kevés, a kubelet MemoryPressure újra bekapcsol; ekkor a node kapacitás bővítése vagy a Pod resource limit csökkentése a hosszú távú megoldás.

43.4.4 Hibák és ellenpróbák

Gyakori hiba, hogy a Pending Podnál rögtön a scheduler vagy a resource request hiányát keresik, miközben a node MemoryPressure=True feltétel már a válasz. Ellenpróba: kubectl describe pod az Events szekcióban a FailedScheduling vagy a Evicted szöveget mutatja – a kettőt külön kell választani.

A második hiba, hogy a node NotReady állapotot az API-server timeoutjának tulajdonítják. Az ellenpróba az etcdctl endpoint health és a kubectl get --raw /readyz?verbose, amely megmutatja, hogy a control plane független-e a node pressure-től.

A harmadik hiba, hogy a tanúsítvány lejáratát nem ellenőrzik, amíg a kubelet nem tud csatlakozni az API-hoz. A kubeadm certs check-expiration futtatása előfeltételként megelőzheti a TLS-hibákból adódó regressziót.

43.4.5 Feladatok

43.4.5.1 1. Feladat: Rétegazonosítás

Adottak a következő megfigyelések egy labclusterben:

  • kubectl get nodes: lab-worker-1 NotReady, MemoryPressure=True.
  • kubectl get pods -n lab-app: lab-api-xyz Pending, lab-batch-xyz Evicted.
  • etcdctl endpoint health --cluster: minden tag healthy.

Magyarázza meg, melyik réteg hibásodott meg, és miért nem a control plane a root cause.

43.4.5.2 2. Feladat: Eviction threshold konfigurálása

Egészítse ki a lab-worker-1 kubelet configját egy evictionHard szabállyal, amely memory.available<300Mi esetén azonnal kilakoltatja a podokat, és pid.available<500 esetén PIDPressure-t jelez. Írja le a módosítás utáni kubelet-újraindítást és a rollbacket.

43.4.5.3 3. Feladat: Incidens-diagnosztika és recovery

A lab-worker-2 node NotReady, a rajta futó lab-web Pod ContainerCreating állapotban ragadt. A node console-on a free -h normál memóriát mutat, de a df -h szerint a /var/lib/kubelet 98%-ig telt. Diagnosztizálja a hibát, határozza meg a node condition-t, és végezzen el egy olyan recovery-t, amely nem törli a kritikus adatot.

43.4.6 Megoldások

43.4.6.1 1. Feladat megoldása

A data plane hibásodott meg. A MemoryPressure=True a kubelet által mért node erőforrásnyomás, nem a control plane sérülése. Az etcd health ellenőrzés megerősíti, hogy a control plane rendelkezésre áll. Az Evicted Pod a kubelet eviction működésének bizonyítéka. A helyes lépés a memória felszabadítása vagy a node kapacitás bővítése, nem az API-server újraindítása. Postcondition: a node Ready=True, a Pod Running.

43.4.6.2 2. Feladat megoldása

A /var/lib/kubelet/config.yaml módosítása:

# target: lab-worker-1 (root), előfeltétel: kubelet config megléte
evictionHard:
  memory.available: "300Mi"
  pid.available: "500"

A kubelet újraindítása:

# target: lab-worker-1 (node console, root)
systemctl restart kubelet
systemctl status kubelet

Ellenőrzés: a node condition csak akkor változik, ha a küszöb alá csökken az erőforrás. A rollback a config eredeti verziójának visszaállítása és újabb systemctl restart kubelet. Postcondition: a kubelet az új thresholdot használja, a node condition a config szerint frissül.

43.4.6.3 3. Feladat megoldása

A df -h a /var/lib/kubelet 98%-os telítettségét mutatja, ami DiskPressure=True-t vált ki a kubeletben. A node NotReady lesz, így a Pod ContainerCreating marad, mert a runtime nem tud image-et vagy containert létrehozni. A recovery:

# target: lab-worker-2 (node console, root)
# nem törlünk critical adatot, csak felesleges containereket és lezárt pod-logokat
crictl rm $(crictl ps -a -q --state=exited)

Ezután a kubelet újraértékeli a filesystemet:

# target: lab-worker-2 (node console, root)
systemctl restart kubelet

Ellenőrzés: df -h szerint a használat 85% alá csökken, a kubectl describe node lab-worker-2 DiskPressure=False értéket mutat, a Pod Running. Postcondition: a node Ready, a kritikus kötetek sértetlenek.

43.4.7 Rövid összefoglaló

A Kubernetes incidens diagnosztikája a node condition és a control plane health párhuzamos ellenőrzésével kezdődik. A MemoryPressure, DiskPressure és PIDPressure jelzi a data plane erőforrástelítettséget, míg az API /readyz és az etcd health a control plane állapotot tükrözi. A CNI/CSI/DNS hibák a Pod ContainerCreating vagy Pending állapotában jelennek meg, a tanúsítvány-lejárat pedig az API-dependency szintjén okoz TLS-hibát. A recovery során először a node console-on gyűjtünk kernel/runtime adatot, majd egyetlen réteget módosítunk, és a node conditionnal ellenőrizzük a javítást. Továbbhasznált definíciók: node condition, eviction threshold, data plane.
