26.5 Dual-stack és return-path diagnosztikai labor

26.5.1 Miért kell a visszaútvonalat is bizonyítani?

A kliens időtúllépése önmagában nem bizonyítja, hogy a kérés nem jutott el a szerverig. Lehet, hogy a szerver megkapta a TCP-kapcsolat kezdeményezését, de a válasz más útvonalon indul, hibás szabályba ütközik, vagy nem talál útvonalat a klienshez.

Az előremenő útvonal (forward path) a konkrét forrásból a célhoz vezető továbbítási döntések sorozata. A visszaútvonal (return path) a válaszcsomag saját forrásával és céljával meghatározott útvonal. Nem feltétlenül ugyanazok az interfészek vesznek részt bennük. Az aszimmetrikus útválasztás (asymmetric routing) önmagában nem hiba; viszont ütközhet állapottartó tűzfalak vagy szigorú forrásellenőrzés feltételezéseivel.

A laborban két router, két végpont és két párhuzamos routerközi kapcsolat segítségével különítjük el:

  • az útvonalkiválasztást;
  • a következő ugrás szomszédfelderítését;
  • a csomag tényleges megjelenését;
  • az alkalmazásszintű sikert.

A korábbi Routing domain, VRF és dynamic routing előkép alapján itt nem vezetünk be dinamikus routingprotokollt: minden útvonal explicit, ezért a hibák eredete követhető.

26.5.2 Laborszerződés és topológia

Célgép: lab-routing, izolált Ubuntu Server 24.04 LTS amd64 VM.
Jogosultság: minden parancs ezen a VM-en, UID 0 jogosultságú Bash-munkamenetben futtatandó. Az ip -n és az ip netns exec megadja a konkrét hálózati névteret.
Előfeltétel: telepített iproute2, procps, python3, curl, tcpdump; működő VM-konzol; engedélyezett IPv6 a labkörnyezetben.

A hálózati névtér (network namespace) saját interfészekkel, útvonalakkal és szomszédtáblával rendelkezik. Nem kapcsoljuk a labor egyik interfészét sem a host hálózatához.

26.5.3 A topológia felépítése

Először ellenőrizd a célt és az ütközéseket. Az útvonallistákban keresd a kijelölt tartományokat; a névtéren belüli izoláció ellenére minden átfedést dokumentálj, és ne készíts kapcsolatot a host felé.

# Cél: lab-routing, UID 0; közös Bash-munkamenet.
test "$(hostname -s)" = lab-routing || exit 1
test "$(id -u)" -eq 0 || exit 1

ip -4 route show table all
ip -6 route show table all
ip netns list

for ns in lab-c lab-r1 lab-r2 lab-s; do
    test ! -e "/run/netns/$ns" || exit 1
done
for dev in lab-c0 lab-r1c lab-r1a lab-r2a \
           lab-r1b lab-r2b lab-r2s lab-s0; do
    if ip link show dev "$dev" >/dev/null 2>&1; then
        echo "Névütközés: $dev"
        exit 1
    fi
done

LAB=$(mktemp -d /tmp/lab-d130.XXXXXX)
{
    cat /etc/os-release
    uname -r
    dpkg-query -W iproute2 procps python3 curl tcpdump
    python3 --version
} > "$LAB/lab-versions.txt"

A konkrét telepített csomag- és kernelkiadás kerül a jegyzőkönyvbe; itt nem állítunk aktuálisan ellenőrzött patchverziót.

A virtuális Ethernet-pár (veth pair) két végét külön névtérbe helyezzük:

for ns in lab-c lab-r1 lab-r2 lab-s; do
    ip netns add "$ns"
    ip -n "$ns" link set lo up
done

lab_pair() {
    ip link add "$2" type veth peer name "$4"
    ip link set "$2" netns "$1"
    ip link set "$4" netns "$3"
}

lab_pair lab-c  lab-c0  lab-r1 lab-r1c
lab_pair lab-r1 lab-r1a lab-r2 lab-r2a
lab_pair lab-r1 lab-r1b lab-r2 lab-r2b
lab_pair lab-r2 lab-r2s lab-s  lab-s0

while read -r ns dev v4 v6; do
    ip -n "$ns" link set "$dev" up
    ip -n "$ns" addr add "$v4" dev "$dev"
    ip -n "$ns" -6 addr add "$v6" dev "$dev"
done <<'EOF'
lab-c  lab-c0  10.203.10.2/24 2001:db8:130:10::2/64
lab-r1 lab-r1c 10.203.10.1/24 2001:db8:130:10::1/64
lab-r1 lab-r1a 10.203.12.1/30 2001:db8:130:12::1/64
lab-r2 lab-r2a 10.203.12.2/30 2001:db8:130:12::2/64
lab-r1 lab-r1b 10.203.13.1/30 2001:db8:130:13::1/64
lab-r2 lab-r2b 10.203.13.2/30 2001:db8:130:13::2/64
lab-r2 lab-r2s 10.203.20.1/24 2001:db8:130:20::1/64
lab-s  lab-s0  10.203.20.2/24 2001:db8:130:20::2/64
EOF

for ns in lab-r1 lab-r2; do
    ip netns exec "$ns" sysctl -qw net.ipv4.ip_forward=1
    ip netns exec "$ns" sysctl -qw net.ipv6.conf.all.forwarding=1
done

# Szándékosan többutas routerek: loose forrásellenőrzés
# kizárólag a négy lab-tranzitinterfészen.
for ns in lab-r1 lab-r2; do
    for suffix in a b; do
        ip netns exec "$ns" sysctl -qw \
            "net.ipv4.conf.${ns}${suffix}.rp_filter=2"
    done
done

Az IPv4 rp_filter=2 azt ellenőrzi, hogy a forrás valamely interfészen elérhető-e, nem követeli meg ugyanazt a visszairányú interfészt. Ez a tervezett aszimmetria előfeltétele, nem hibakeresési célú globális védelemkikapcsolás. A host beállításait nem módosítjuk.

Az útvonalak:

ip -n lab-c route add default via 10.203.10.1
ip -n lab-c -6 route add default via 2001:db8:130:10::1
ip -n lab-s route add default via 10.203.20.1
ip -n lab-s -6 route add default via 2001:db8:130:20::1

ip -n lab-r1 route add 10.203.20.0/24 via 10.203.12.2
ip -n lab-r2 route add 10.203.10.0/24 via 10.203.12.1
ip -n lab-r1 -6 route add 2001:db8:130:20::/64 \
    via 2001:db8:130:12::2
ip -n lab-r2 -6 route add 2001:db8:130:10::/64 \
    via 2001:db8:130:12::1

sleep 2
for ns in lab-c lab-r1 lab-r2 lab-s; do
    ip -n "$ns" -6 addr show tentative
    ip -n "$ns" -6 addr show dadfailed
done

Várt ellenőrzés: az utolsó lekérdezések üresek. A két másodperc nem garancia: tentative esetén várj és ellenőrizz újra; dadfailed esetén vizsgáld a címütközést. Ne kapcsold ki a duplikáltcím-ellenőrzést (Duplicate Address Detection, DAD).

26.5.4 Útvonalleltár és dual-stack szolgáltatásteszt

A kettős protokollverem (dual stack) itt azt jelenti, hogy ugyanaz a próbaszolgáltatás IPv4-en és IPv6-on is elérhető. Két külön listenerrel tesszük ezt egyértelművé; nem függünk az IPv4-mapped IPv6 socketbeállításoktól.

printf 'lab-d130 OK\n' > "$LAB/lab-health.txt"

ip netns exec lab-s python3 -m http.server 8080 \
    --bind 10.203.20.2 --directory "$LAB" \
    > "$LAB/lab-http4.log" 2>&1 &
LAB_HTTP4=$!

ip netns exec lab-s python3 -m http.server 8080 \
    --bind 2001:db8:130:20::2 --directory "$LAB" \
    > "$LAB/lab-http6.log" 2>&1 &
LAB_HTTP6=$!

sleep 1
ip netns exec lab-s ss -lnt 'sport = :8080'

for ns in lab-c lab-r1 lab-r2 lab-s; do
    echo "=== $ns ==="
    ip -n "$ns" -br addr
    ip -n "$ns" -4 rule show
    ip -n "$ns" -6 rule show
    ip -n "$ns" -4 route show table all
    ip -n "$ns" -6 route show table all
    ip -n "$ns" neigh show
done

Ha nincs mindkét listener, előbb a megfelelő szervernaplót vizsgáld. Routingot nem javítunk egy el sem indult szolgáltatás miatt.

ip netns exec lab-c curl --noproxy '*' -4 -fsS \
    --connect-timeout 2 --max-time 5 \
    http://10.203.20.2:8080/lab-health.txt

ip netns exec lab-c curl --noproxy '*' -6 -g -fsS \
    --connect-timeout 2 --max-time 5 \
    'http://[2001:db8:130:20::2]:8080/lab-health.txt'

Várt, nem mért kimenet: mindkét parancs lab-d130 OK szöveget ad, sikeres kilépéssel. A numerikus cím kizárja a DNS-t; a --noproxy '*' a környezeti HTTP-proxykat kerüli meg, nem biztonsági ellenőrzést.

Az útvonalkiválasztást a tényleges csomagparaméterekkel kérdezd le:

ip -n lab-c route get 10.203.20.2
ip -n lab-r1 route get 10.203.20.2 \
    from 10.203.10.2 iif lab-r1c
ip -n lab-r2 route get 10.203.10.2 \
    from 10.203.20.2 iif lab-r2s
ip -n lab-s -6 route get 2001:db8:130:10::2 \
    from 2001:db8:130:20::2

ip -n lab-c neigh show dev lab-c0
ip -n lab-r1 -6 neigh show dev lab-r1a

A route get nem küld próbacsomagot. A from és az iif nélkül egy router helyben generált csomagját modellezheted a továbbított csomag helyett.

Második, szintén lab-routing gépen nyitott UID 0 terminálban indíts csomagrögzítést (packet capture), majd ismételd a HTTP-próbákat:

ip netns exec lab-r2 timeout 15 tcpdump -n -i any \
    'arp or icmp or icmp6 or tcp port 8080'
Irány Forrás → cél Alaphelyzeti út
Kérés 10.203.10.2 → 10.203.20.2:8080 kliens → R1 → A → R2 → szerver
Válasz 10.203.20.2:8080 → kliens ideiglenes portja szerver → R2 → A → R1 → kliens

Az IPv6-adatút ugyanilyen. Az any capture több interfészen is láthatja ugyanazt a továbbított csomagot; ez nem automatikusan TCP-újraküldés.

26.5.5 Három kicsi hibafixture

Mindig csak egy hibát vezess be, gyűjts bizonyítékot, majd állítsd vissza az alaphelyzetet.

1. Túl tág IPv6-prefix. Egy téves, közvetlenül kapcsoltnak tekintett /48 útvonal a távoli szervert helyi szomszéddá teszi:

ip -n lab-c -6 route add 2001:db8:130::/48 dev lab-c0
ip -n lab-c -6 route get 2001:db8:130:20::2
# Most ismételd az IPv6 HTTP-próbát.
ip -n lab-c -6 neigh show dev lab-c0

# Rollback:
ip -n lab-c -6 route del 2001:db8:130::/48 dev lab-c0

Várt bizonyíték: nincs via a célhoz kiválasztott útvonalban; a kliens közvetlenül a szerverhez küld szomszédkérést (Neighbor Solicitation). A szomszédbejegyzés előbb INCOMPLETE, később FAILED lehet. A hiba a prefix, nem az ND működése. Statikus szomszédbejegyzés vagy proxy-ND nem helyes javítás.

2. Hibás IPv4 default gateway.

ip -n lab-c route replace default via 10.203.10.254
ip -n lab-c route get 10.203.20.2
# Most ismételd az IPv4 HTTP-próbát.
ip -n lab-c neigh show dev lab-c0

# Rollback:
ip -n lab-c route replace default via 10.203.10.1

A route létezik, de a nem létező következő ugrás ARP-felderítése sikertelen. A via megjelenése tehát nem bizonyít használható adatútvonalat.

3. Hibás helyi forráscím.

ip -n lab-c addr show dev lab-c0
ip netns exec lab-c curl --noproxy '*' -4 \
    --interface 10.203.10.99 --connect-timeout 2 --max-time 5 \
    http://10.203.20.2:8080/lab-health.txt

A cím nincs a klienshez rendelve. Várt jelenség: helyi bindhiba, nem távoli timeout; TCP SYN sem indul. Nincs hálózati állapotváltozás, a rollback a hibás forráskötés elhagyása.

26.5.6 Aszimmetrikus visszaút és policy rule

A szabályalapú útválasztás (policy routing) nemcsak a célprefix alapján dönthet. Most a szerver IPv4-forráscíméhez külön táblát rendelünk R2-n:

ip -n lab-r2 route add table 100 10.203.13.0/30 \
    dev lab-r2b scope link
ip -n lab-r2 route add table 100 10.203.10.0/24 \
    via 10.203.13.1 dev lab-r2b
ip -n lab-r2 rule add priority 100 \
    from 10.203.20.2/32 lookup 100

ip -n lab-r2 rule show
ip -n lab-r2 route show table 100
ip -n lab-r2 route get 10.203.10.2 \
    from 10.203.20.2 iif lab-r2s

Várt döntés: table 100, via 10.203.13.1, dev lab-r2b. A kérés továbbra is A-n, a válasz B-n halad. Ismételt IPv4 HTTP-teszttel és R2 capture-rel bizonyítsd, hogy ez működő aszimmetria.

Ezután kizárólag a visszaútvonalat rontjuk el:

ip -n lab-r2 route replace table 100 \
    blackhole 10.203.10.0/24

# Most ismételd mindkét HTTP-próbát és az R2 capture-t.
ip -n lab-r2 route show table 100
ip -n lab-r2 rule show

# Recovery: az aszimmetrikus, működő állapot visszaállítása.
ip -n lab-r2 route replace table 100 10.203.10.0/24 \
    via 10.203.13.1 dev lab-r2b

Várt bizonyítéklánc:

  1. Az IPv4 SYN eljut a szerverig.
  2. A SYN-ACK megjelenik R2 szerveroldali interfészén.
  3. A válasz nem távozik egyik tranzitinterfészen sem.
  4. A forráscímre illeszkedő szabály a blackhole útvonalat választja.
  5. Az IPv6-próba továbbra is sikeres.

A blackhole terminális döntés: nem jelent „keress tovább a main táblában” utasítást. Emiatt a hibátlan main tábla önmagában félrevezető bizonyíték.

Visszatérés az eredeti, szimmetrikus állapothoz:

ip -n lab-r2 rule del priority 100 \
    from 10.203.20.2/32 lookup 100
ip -n lab-r2 route del table 100 10.203.10.0/24
ip -n lab-r2 route del table 100 10.203.13.0/30

26.5.7 IPv6-ellenpróbák és diagnosztikai sorrend

Az IPv4 sikere nem igazolja az IPv6 működését. IPv6-hibánál külön vizsgáld:

  1. Címállapot: van megfelelő cím, nincs tentative vagy dadfailed?
  2. Route: a cél helyi vagy routeren át érhető el?
  3. ND: a következő ugrás feloldható? A STALE önmagában nem hiba.
  4. ICMPv6: látható szomszédfelderítés, elérhetetlenségi vagy Packet Too Big üzenet?
  5. Visszaút és listener: a szerver válaszol-e, és merre?

A labor statikus címzést és default route-ot használ, ezért nem várunk routerhirdetést (Router Advertisement, RA). SLAAC-alapú hálózaton viszont az RA hiánya vagy elutasítása lényeges bizonyíték:

ip netns exec lab-c sysctl \
    net.ipv6.conf.lab-c0.accept_ra \
    net.ipv6.conf.lab-c0.accept_ra_defrtr \
    net.ipv6.conf.lab-c0.autoconf

ip netns exec lab-c timeout 15 tcpdump -n -i lab-c0 icmp6

Az RA-ból származó default route és a prefixinformáció külön állapot. Egy érvényes IPv6-cím nem garantál default route-ot. Az általános ICMPv6-tiltás ND- és útvonal-MTU-hibát is okozhat; javításkor a hibás szabályt és a szükséges üzenettípust azonosítsd. Ne az IPv6 vagy a tűzfal globális kikapcsolása legyen az „ellenpróba”.

26.5.8 Feladatok

  1. Magyarázó: miért nem bizonyítja a helyes main útvonaltábla a működő visszautat? Milyen adat különíti el a hibás default gatewayt a túl tág IPv6-prefixtől?
  2. Adminisztrációs: építsd fel a topológiát, készíts verzió- és útvonalleltárt, majd bizonyítsd külön mindkét IP-család HTTP-elérését.
  3. Diagnosztikai és recovery: hozd létre a működő aszimmetriát, majd a blackhole hibát. Dokumentáld a hipotézist, a capture-t, az egyetlen javítást és az ismételt tesztet.

26.5.9 Megoldások

  1. A szabálylista más táblát választhat; a szomszédfelderítés és a forwarding is külön feltétel. Hibás gatewaynél a route get téves via címet mutat, és annak ARP-felderítése sikertelen. Túl tág prefixnél nincs gateway: közvetlen ND indul a távoli célhoz. Postcondition: a magyarázat megkülönbözteti a kiválasztást és a kézbesíthetőséget.

  2. A két listener, két sikeres HTTP-válasz, üres DAD-hibalista és az A tranzitot mutató lekérdezések együtt adják az elfogadási bizonyítékot. Egyetlen sikeres ping nem elég. Postcondition: a konkrét verzióprofil mellett IPv4-en és IPv6-on is visszaér a próbaadat.

  3. Először A irányú kérés és B irányú válasz mellett sikeres HTTP-t kell látni. A hiba után R2 még megkapja a SYN-ACK-ot, de eldobja. A táblabejegyzés visszaállítása után újra működik az IPv4; végül a policy eltávolításával visszatér az A/A út. Postcondition: nincs lab-policy szabály, és mindkét család tesztje sikeres.

26.5.10 Takarítás

Állítsd le a capture-öket. Csak a név szerint létrehozott, kizárólag e laborhoz használt névtereket és folyamataikat töröld:

for ns in lab-c lab-r1 lab-r2 lab-s; do
    if test -e "/run/netns/$ns"; then
        for pid in $(ip netns pids "$ns"); do
            kill "$pid"
        done
        ip netns del "$ns"
    fi
done
wait "$LAB_HTTP4" "$LAB_HTTP6" 2>/dev/null || true
ip netns list

Várt postcondition: egyik labnévtér sem szerepel a listában. A bizonyítékkönyvtár megmarad; archiválás után a saját, ismert fájlok külön törölhetők:

rm -- "$LAB/lab-health.txt" "$LAB/lab-versions.txt" \
      "$LAB/lab-http4.log" "$LAB/lab-http6.log"
rmdir -- "$LAB"

26.5.11 Rövid összefoglaló

A routinghiba bizonyításához a kérés és a válasz útját külön kell rekonstruálni, a tényleges forráscímmel és bejövő interfésszel. Az útvonallekérdezés kiválasztást mutat; a szomszédtábla következőugrás-felderítést; a capture csomagjelenlétet; a HTTP-próba alkalmazásszintű eredményt. Egyik sem helyettesíti a többit. Az aszimmetria lehet szándékos és működőképes, míg egy forrásfüggő szabály a hibátlan main tábla mellett is megszakíthatja a visszautat. IPv6-nál az ND, ICMPv6 és szükség esetén RA vizsgálata a diagnózis része. A javítást mindkét IP-családon újra kell ellenőrizni.

  • Visszaútvonal: a válaszcsomag paraméterei alapján választott adatút.
  • Aszimmetria: eltérő előremenő és visszairányú út.
  • Policy routing: szabályokkal vezérelt útvonaltábla-választás.

26.5.12 Források és ellenőrzési hiányok

Az alábbiak ellenőrzési kiindulópontok, nem ebben a munkamenetben olvasott források. Webes ellenőrzés és laborfuttatás nem történt.

  • ip-route(8) — route lookup, táblák, blackhole.
  • ip-rule(8) — szabálysorrend és táblaválasztás.
  • Linux kernel: IP sysctl — rp_filter, forwarding és RA-beállítások.
  • RFC 4861: Neighbor Discovery for IP version 6 — ND és RA.
  • RFC 4443: ICMPv6 — ICMPv6-hibaüzenetek.

Nyitott ellenőrzés: a rögzített Ubuntu/kernel/iproute2-profil pontos viselkedése és kimenete, továbbá az RFC-k státusza, frissítései és erratái. A helyi, csomaghoz tartozó kézikönyveket részesítsd előnyben az eltérő verziójú online dokumentációval szemben.
