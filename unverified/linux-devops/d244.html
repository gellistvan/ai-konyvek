49.4 Helm, Kustomize és configuration overlay

49.4.1 Motiváció

A GitOps reconciliation (lásd GitOps reconciliation és desired state) akkor működik üzemeltethetően, ha a repositoryban lévő forrásból determinisztikusan ugyanazt a desired object-állapotot tudjuk előállítani. A Helm és a Kustomize más-más configgeneration modellt képvisel: a Helm template-et és values-t, a Kustomize base-t és overlay-t használ. A közös üzemeltetési hiba, hogy valaki a template/overlay forrást tekinti desired state-nek, és a renderelt kimenetet nem ellenőrzi policy és deploy előtt. A szenior C++ fejlesztő számára ez olyan, mintha a preprocesszált forrást vagy a template instantiation bemenetét auditálnánk a lefordított artifact helyett: a forrás fontos, de a cluster azt a kézzel fogható erőforrás-leírást fogja alkalmazni, amely a renderelés eredménye. Ezért a configgeneration egy build pipeline: stabil bemenet, determinisztikus render, validáció és diff, majd kontrollált deploy.

49.4.2 Definíció és működés

A rendered config a source template/overlay és a környezeti input (Helm values.yaml, Kustomize patch/overlay) determinisztikus kiértékeléséből előálló Kubernetes YAML halmaz. Ez a desired object, vagyis az a clustererőforrás-állapot, amelyet a reconciliation el akar érni. A source template/overlay önmagában nem desired object; a cluster API szervere nem ismeri a Go template-et vagy a Kustomize kustomization.yaml-t.

A Helm modellben a chart egy Chart.yaml metadata, values.yaml default values és templates/* sablonok csomagja. A helm template a chartot és a megadott values-rétegeket egyesíti, és a kimenetet stdoutra írja. A release a chart és values egy példánya a clusterben, release name-hez kötve; a helm install/upgrade létrehozza vagy módosítja a release-t, a helm history mutatja a release verzióit. A release state maga is a clusterben, Secret erőforrásként tárolódik a Helm storage driverében, de ez elkülönül az alkalmazás Secret erőforrásaitól.

A Kustomize modellben a base a közös, környezetfüggetlen Kubernetes manifestek halmaza, amelyet egy kustomization.yaml ír le. Az overlay egy adott környezetre vonatkozó kustomization.yaml, amely resources-ként hivatkozza a base-t, és patch-eket, generátorokat, valamint névtranszformereket alkalmaz. A kustomize build a base és overlay egyesítéséből renderelt YAML-t állít elő. A Kustomize nem template; a patch típusa strategic merge patch, JSON patch (JSON-6902) vagy transformer lehet. A configMapGenerator és secretGenerator determinisztikus hash-tilleszt a generált erőforrás nevéhez, így a tartalom változásakor a hivatkozó Deployment pod template-je is frissül, ami új rolloutot vált ki.

A configgeneration réteghatára tehát: source input (chart/values, base/overlay) → render/transform → rendered config → policy/validation → apply/reconcile. A GitOps repository általában a source-t tárolja; a CI vagy a GitOps eszköz rendereli és validálja, mielőtt a clusterre kerülne. Az Ansible template-nél tanult effective variable itt párhuzamba állítható a Helm values precedence-szabályával, de itt nem hostonként assemblylünk, hanem clusterenként egy desired state-et állítunk elő.

A Kubernetes API capability/version ellenőrzése a rendered configra vonatkozik. Minden manifest apiVersion és kind mezővel jelöli ki az API csoportot és verziót. A cluster API szerver csak a neki ismert API-verziókat fogadja el; a deprecated vagy eltávolított API-verziók (extensions/v1beta1 Deployment, apps/v1beta1 StatefulSet) hibát vagy figyelmeztetést adnak. A kubectl api-resources megmutatja a cluster által kiszolgált API-verziókat, a kubectl explain az egyes erőforrásmezőket ismerteti. A leghatékonyabb ellenőrzés a kubectl apply --dry-run=server, mert ezt maga a cluster API szerver validálja az aktuális séma szerint.

A schema/config validation a rendert megelőző és követő lépésekre oszlik. A Helm chart tartalmazhat values.schema.json-t, amely a values JSON Schema-ja; a helm lint és a helm template/install validálja a values-t a render előtt. A Kustomize esetén nincs beépített values-séma, ott a rendered manifestet kell a cluster szerver-oldali dry-run-jával vagy külső validátorral ellenőrizni. A naming stabilitása is ide tartozik: a resource-neveknek determinisztikusnak kell maradniuk, mert a nemdeterminisztikus név (például randAlphaNum a Deployment nevében) folyamatos diffet és indokolatlan rolloutot okoz. A Kustomize namePrefix/nameSuffix determinisztikus, de a selector label-ek és a Service hivatkozások frissítését ellenőrizni kell.

A Secret kezelés fontos része a configgeneration trust határának. A Git repository és a Helm values nem tárolhat plain text titkot. A Secret erőforrást vagy külső Secret management rendszerből (ExternalSecret, SOPS, Vault injection, a konkrét eszközt a class kiadásához kell ellenőrizni) kell injektálni, vagy a chart csak a Secret hivatkozását hozza létre, a tartalom a clusterben külön életciklussal él. A Secret drift akkor keletkezik, ha a Secret tartalma a desired state-től eltér, de a kubectl diff a Secret értékét nem mutatja. A hash-suffixes generátorok (Kustomize secretGenerator) segítenek észlelni a tartalomváltozást, mert a Secret neve megváltozik, és a hivatkozó Deployment új rolloutot kap.

A rollback chart/state/data határa élesen elválik. A helm rollback a release historyban tárolt chart-ot és values-t állítja vissza a cluster config state-be; ez a rollout, a Service, a ConfigMap stb. állapotát érinti, de nem nyúl a persistent volume tartalmához, nem futtat database migration rollbacket, nem módosít külső rendszert. A Kustomize esetén a Git revert a desired state visszaállítását jelenti, de a clusterben lévő adatréteg (PVC, DB) nem tér vissza. A config rollback tehát nem adat-visszaállítás; az RPO/RTO és a data restore külön fejezetekhez tartozik.

49.4.3 Kidolgozott példa

A példa célja egy lab-api nevű C++ HTTP service konfigurációjának renderelése, validálása és deploy előtti ellenőrzése egy izolált labclusteren. Labor target:

  • cluster/context: lab-cluster
  • namespace: lab-cd-ns
  • Helm chart: ./lab-chart
  • Kustomize base: ./deploy/base
  • Kustomize overlay: ./deploy/overlays/staging
  • image: registry.lab.example/lab-api:1.2.3
  • jelen UID: labadmin, kubeconfig a labhome kézben.

A chart szerkezete:

lab-chart/
  Chart.yaml
  values.yaml
  values.schema.json
  templates/
    deployment.yaml
    service.yaml

Chart.yaml:

apiVersion: v2
name: lab-api
version: 1.2.0
appVersion: "1.2.3"

values.yaml:

replicaCount: 2
image:
  repository: registry.lab.example/lab-api
  tag: "1.2.3"
service:
  port: 8080

values.schema.json:

{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "properties": {
    "replicaCount": {"type": "integer", "minimum": 1},
    "image": {
      "type": "object",
      "properties": {
        "repository": {"type": "string", "minLength": 1},
        "tag": {"type": "string", "minLength": 1}
      },
      "required": ["repository", "tag"],
      "additionalProperties": false
    },
    "service": {
      "type": "object",
      "properties": {
        "port": {"type": "integer", "minimum": 1, "maximum": 65535}
      },
      "required": ["port"],
      "additionalProperties": false
    }
  },
  "required": ["replicaCount", "image", "service"],
  "additionalProperties": false
}

templates/deployment.yaml:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}-api
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app: lab-api
  template:
    metadata:
      labels:
        app: lab-api
    spec:
      containers:
        - name: api
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: 100m
              memory: 64Mi
            limits:
              cpu: 500m
              memory: 256Mi

templates/service.yaml:

apiVersion: v1
kind: Service
metadata:
  name: {{ .Release.Name }}-api
spec:
  selector:
    app: lab-api
  ports:
    - port: {{ .Values.service.port }}
      targetPort: 8080

A render és validáció parancsai:

# Cél: lab-cluster/kubeconfig labadmin
# Módosító parancs nincs; csak olvasás és render.
helm lint ./lab-chart

helm template lab-api ./lab-chart \
  --namespace lab-cd-ns \
  > /tmp/lab-api-rendered.yaml

# Szerver-oldali séma- és API-validáció:
kubectl --context lab-cluster apply --dry-run=server \
  -f /tmp/lab-api-rendered.yaml -n lab-cd-ns

Várható kimenet: a helm lint „1 chart(s) linted, 0 chart(s) failed” üzenetet ad; a helm template a Deployment és Service YAML-ját írja ki; a kubectl apply --dry-run=server sikeres, és jelzi, hogy a resource-ok érvényesek. Ha az API-verzió vagy a mezők hibásak, a dry-run hibát ad.

A Kustomize overlay ugyanahhoz a service-hez:

deploy/base/deployment.yaml:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: lab-api
spec:
  replicas: 2
  selector:
    matchLabels:
      app: lab-api
  template:
    metadata:
      labels:
        app: lab-api
    spec:
      containers:
        - name: api
          image: registry.lab.example/lab-api:1.2.3
          ports:
            - containerPort: 8080

deploy/base/service.yaml:

apiVersion: v1
kind: Service
metadata:
  name: lab-api
spec:
  selector:
    app: lab-api
  ports:
    - port: 8080
      targetPort: 8080

deploy/base/kustomization.yaml:

apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - deployment.yaml
  - service.yaml

deploy/overlays/staging/kustomization.yaml:

apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../../base
patches:
  - target:
      kind: Deployment
      name: lab-api
    patch: |
      - op: replace
        path: /spec/replicas
        value: 3

Renderelés és validáció:

kustomize build deploy/overlays/staging \
  > /tmp/lab-api-staging.yaml

kubectl --context lab-cluster apply --dry-run=server \
  -f /tmp/lab-api-staging.yaml -n lab-cd-ns

# Diff a live állapottal, ha a namespace már létezik:
kubectl --context lab-cluster diff \
  -f /tmp/lab-api-staging.yaml -n lab-cd-ns

Várható kimenet: a kustomize build a patched Deploymentet és a Service-t írja ki, a Deployment replicas értéke 3. A dry-run sikeres, a diff tiszta, ha a clusterben már ezt a konfigurációt alkalmazták.

A release telepítése és rollback:

# Módosító parancs: létrehoz egy release-t.
# Target: lab-cluster, namespace lab-cd-ns, UID labadmin.
# Előfeltétel: a fenti dry-run sikeres volt.
helm --kube-context lab-cluster install lab-api ./lab-chart \
  --namespace lab-cd-ns

# Ellenőrzés: a release state látható.
helm --kube-context lab-cluster status lab-api -n lab-cd-ns

# Rollback példa (ha később upgrade lenne):
helm --kube-context lab-cluster rollback lab-api 1 -n lab-cd-ns

A helm rollback a release history alapján visszaállítja a chart configot; nem töröl PVC-t, nem módosít DB-t.

49.4.4 Tipikus hibák és ellenpróbák

  1. A rendered output nincs validálva, csak deploy közben derül ki a hiba. Tünet: a helm install vagy a GitOps sync sikertelen, a hibás YAML vagy invalid field későn jelenik meg. Hipotézis: a configgeneration kihagyta a dry-run-t. Adatgyűjtés: helm lint, helm template, kubectl apply --dry-run=server. Egy változtatás: a CI pipeline render után kötelezően futtasson kubectl apply --dry-run=server-t, mielőtt commitolna vagy syncelne. Verification: a dry-run tiszta, a deploy sikeres.

  2. Deprecated API-verzió a rendered configban. Tünet: a dry-run hibát ad: no matches for kind "Deployment" in version "extensions/v1beta1". Hipotézis: a chart vagy base elavult API-t használ. Adatgyűjtés: kubectl api-resources | grep Deployment, kubectl explain deployment. Egy változtatás: frissítsd az apiVersion-t apps/v1-re, és a mezőket a jelenlegi sémához igazítsd. Verification: a dry-run sikeres.

  3. Nemdeterminisztikus resource-név a Helm template-ben. Tünet: a GitOps diff minden reconciliation után változást mutat, a Deployment neve véletlenszerű, a rolloutok indokolatlanok. Hipotézis: a template a resource nevébe randAlphaNum-ot vagy timestampet generál. Adatgyűjtés: helm template kétszer, diff. Egy változtatás: fix resource-név, például {{ .Release.Name }}-api. Verification: két render azonos, a GitOps diff tartósan tiszta.

  4. Secret drift nem látható a diffben. Tünet: a kubectl diff tiszta, de az alkalmazás a régi jelszóval próbálkozik. Hipotézis: a Secret értékét a values plain textben tároltuk, és a Secret hibás; a diff nem mutatja a Secret tartalmat. Adatgyűjtés: kubectl get secret <name> -o yaml, de a base64 csak a tesztértékre korlátozódjon, ne logolj éles titkot. Egy változtatás: titok kezelése külső rendszerrel, a Git repositoryban csak hivatkozás; a Secret értékének változásakor hash-based Secret név vagy rollback-marker kell. Verification: az alkalmazás a megfelelő titkot kapja, a forrásrepo titokmentes.

  5. A helm rollback-tól adat-visszaállítást várnak. Tünet: a konfiguráció visszaáll, de a DB séma félkész marad, az alkalmazás hibázik. Hipotézis: a rollback konfigurációs határát nem tisztázták. Adatgyűjtés: helm history lab-api -n lab-cd-ns, alkalmazás log. Egy változtatás: adatbázis-migration rollback vagy restore, nem helm rollback. Verification: az alkalmazás sikeresen kommunikál a DB-vel.

49.4.5 Feladatok

  1. Magyarázó feladat. Hasonlítsa össze a Helm helm template és a Kustomize kustomize build kimenetét abban a tekintetben, hogy mi a source input, mi a desired object, és hogyan érvényesül a validációs határ. Fogalmazza meg, miért nem elég a chart/overlay source-t versionálni.

  2. Adminisztrációs/konfigurációs feladat. Készítsen Helm values.schema.json-t a példa chartjához, és próbálja renderelni replicaCount: 0 értékkel. Ellenőrizze a hibát, majd állítsa vissza replicaCount: 2-re, és futtasson helm lint, helm template, valamint kubectl apply --dry-run=server ellenőrzést. Adja meg a postconditiont.

  3. Diagnosztikai/failure/recovery feladat. A lab Git repositoryban egy base manifestben apiVersion: apps/v1beta1 szerepel a Deploymentre. A kubectl apply --dry-run=server hibát ad. Diagnosztizálja a hibát a kubectl api-resources és kubectl explain deployment segítségével, javítsa a manifestet apps/v1-re, és ellenőrizze dry-run-nal. Postcondition: a dry-run hibamentes, és a git diff a javítást mutatja.

49.4.6 Megoldások

  1. A helm template és a kustomize build egyaránt rendered configot állít elő, de más forrásból. A Helm chart a Chart.yaml, values.yaml és templates/* Go template-ek; a values rétegek a default, a parent chart és a felhasználói -f/--set értékek. A helm template ezt a template-et és values-t egyesíti a desired objectté. A Kustomize kustomization.yaml a base manifesteket és az overlay patch-eket egyesíti; a kustomize build a patch-eket alkalmazza, és a generátorok hash-t illeszt. A validációs határ a rendered configon van: a source (chart vagy base) önmagában nem a cluster API szerver inputja; a cluster a renderelt YAML-t validálja. Ezért a source versionálása mellett a rendered outputot is ellenőrizni kell, hogy a cluster verifyt adott API-sémára futtassunk.

  2. A values.schema.json a fenti JSON Schema, amely replicaCount-ra minimum: 1-et ír elő. replicaCount: 0 esetén a helm template hibát ad, mert a JSON Schema validáció elutasítja. A hibaüzenet jelzi a minimum megsértését. A helyes values után a helm lint 0 hibát, a helm template a Deploymentben replicas: 2 értéket, a dry-run pedig sikeres applyeredményt ad. Postcondition: a chart lint tiszta, a rendered manifest apps/v1 API-val és replicaCount: 2-vel valid.

  3. A kubectl api-resources | grep Deployment megmutatja, hogy a cluster apps/v1-et szolgál ki, nem apps/v1beta1-et. A kubectl explain deployment a jelenlegi apps/v1 Deployment sémáját mutatja. A manifestben az apiVersion: apps/v1beta1 csere apps/v1-re, a mezők ellenőrzése után a dry-run hibamentes. Postcondition: a base manifest API-verziója apps/v1, a dry-run sikeres, a Git diff a javítást tartalmazza.

49.4.7 Rövid összefoglaló

A Helm és a Kustomize más configgeneration modellt képvisel, de közös a szabály: a source template/overlay csak input, a cluster a renderelt desired objectet validálja és alkalmazza. A Helm chart a values-sablonokat, a Kustomize a base és overlay patch-eket egyesíti determinisztikus YAML-lá. A rendered configot a policy és deploy előtt helm lint-tel, kubectl apply --dry-run=server-rel, valamint API- és sémaellenőrzéssel kell auditálni. A Secret értékét kívül kell tartani a configgeneration forrásán, a driftet hash-alapú névvel vagy külső Secret managerrel kezeljük. A helm rollback és a Git revert a config state-et állítja vissza, nem az adatot.

Továbbhasznált definíciók:

  • Rendered config: a source template/overlay és a környezeti input determinisztikus kiértékeléséből előálló Kubernetes YAML halmaz, amely a desired object.
  • Desired object: az a clustererőforrás-állapot, amelyet a reconciliation a clusterben elérni akar.
  • Release state: a Helm release-hez kötött chart, values és manifest, amely a clusterben Secret-ként is tárolt; a rollback erre, nem az adatra vonatkozik.

49.4.8 Források és ellenőrzési hiányok

Az alfejezet nem végez valós webes kutatást; a Helm, Kustomize és Kubernetes API-verziók pontos, verziófüggő viselkedését a hivatalos dokumentáció aktuális, ellenőrzött kiadásából kell megerősíteni. A példában használt Helm values.schema.json, a dry-run szerver-oldali validáció és a Kustomize patch-formátumok stabil, általános alapok, de a konkrét Kubernetes cluster API-verziói, a Helm storage driver és a Kustomize generator hash algoritmusa az adott verziótól függ. A külső validátorok (például kubeconform, pluto) verziója és a deprecated API-listája ellenőrizendő.
