38.1 Engine, runtime, shim és CRI

A konténer-futtatási lánc rétegei gyakran egyetlen fekete doboznak tűnnek a fejlesztő számára: a docker run vagy podman run parancs után elindul egy processz, és ennyi. A szenior C++ fejlesztőként meglévő processz- és syscall-ismeret azonban lehetővé teszi, hogy ezt a láncot pontosan szétválasszuk. Ez azért fontos, mert a hibakeresés, a privilege policy és a Kubernetes-integráció mind más rétegben dől el. Ha például a docker CLI permission denied hibát ad, az nem a kernel namespaces, hanem a Unix socket authority határa. Ha a Kubernetes alatt a pod cgroup-jai nem jönnek létre, az a cgroup driver ownership hibája. Ebben az alfejezetben a CLI-től a runc-ig követjük az adatutat, és minden rétegre megadjuk, ki a tulajdonos, milyen jogosultsággal fut, és hogyan kell diagnosztizálni.

38.1.1 Definíció és működés

A konténer-futtatási stacket három nagy csoportra bontjuk: a felhasználói CLI (command line interface), a daemon vagy high-level runtime (engine, containerd), és a low-level OCI runtime (runc). Ezen kívül két speciális elem: a shim processz és a CRI (Container Runtime Interface).

CLI (docker, podman): A docker parancs egy kliensprogram, amely REST API-kérést küld a Docker daemonnak. Maga a CLI nem végez semmilyen kernelműveletet a konténer számára; minden hatalom a daemon kezében van. A podman ezzel szemben daemon nélküli (fork-exec modell): a CLI processz közvetlenül hívja a low-level runtime-ot, és a CLI processz jogosultsága lesz a konténer jogosultsága. A docker CLI általában a /var/run/docker.sock Unix sockethez csatlakozik, míg a podman szükség esetén egy user-scope socketet is indíthat (például $XDG_RUNTIME_DIR/podman/podman.sock).

Daemon / engine: A dockerd egy rootful daemon, amely a host root jogosultságával fut. A CLI által küldött API-kéréseket ő hajtja végre: image pull, container create, start, stop, network, volume. A Docker daemon a containerd-et használja high-level runtime-ként. A Docker daemon és a containerd közötti kapcsolat gRPC alapú, és a daemon hosszú életű szolgáltatás. A Docker daemon szolgáltatás neve a systemd-ben docker.service, és a socketet a docker.socket unit aktiválhatja (socket activation).

Containerd: A containerd egy high-level container runtime daemon, amelyet a CNCF projektként fejlesztenek. A Docker mellett a Kubernetes is ezt használja, de a Kubernetes esetében a kubelet a CRI protokollon keresztül beszél hozzá. A containerd felelős a container lifecycle menedzseléséért, az image-ek tárolásáért, a container rootfs előkészítéséért, a snapshotterekért, a hálózati pluginekért és a CRI pluginért. A containerd rootful daemon, és a /run/containerd/containerd.sock socketen hallgat.

Shim: A containerd minden konténerhez egy containerd-shim-runc-v2 processzt indít. A shim a tényleges parent processze a konténerben futó PID 1-nek. A shim három fontos dolgot old meg: (1) leválasztja a konténer életciklusát a containerd daemonról, így a daemon újraindítása nem öli meg a futó konténereket; (2) kezeli a container stdin/stdout/stderr streamjét; (3) visszaadja az exit status-t a daemonnak. A Podman esetében a shim-szerepet a conmon tölti be, amely egy kisebb, C-ben írt monitor.

Runc (low-level OCI runtime): A runc az OCI (Open Container Initiative) runtime specification referenciaimplementációja. A runc kap egy config.json fájlt és egy rootfs-t, majd létrehozza a Linux namespace-eket, cgroup-okat, seccomp szűrőt, capabilities bounding set-et, mountokat, és végül exec-eli a tényleges konténerprocesszt. A runc processz a konténer létrehozása után általában azonnal kilép; a futó konténernek a shim a parentje. A runc tehát a legalsó réteg, amelyik közvetlen kernel syscallokat hajt végre (clone, unshare, pivot_root, prctl stb.).

OCI runtime vs CRI interface: Az OCI runtime specifikáció a konténer izolációját írja le (namespaces, cgroups, mounts, hooks), és ezt a runc implementálja. A CRI egy Kubernetes-specifikus gRPC API, amelyet a kubelet hív a container runtime-tal való kommunikációhoz. A containerd a io.containerd.grpc.v1.cri pluginjával implementálja a CRI-t, és a CRI-kéréseket lefordítja OCI runtime hívásokká. A Docker daemon nem CRI-kompatibilis; a Kubernetes korábban a dockershim réteggel hidalt, de ezt eltávolították. Emiatt a modern Kubernetes cluster containerd-et használ. A Podman esetében nincs CRI implementáció a Kuberneteshez; a Podman-t inkább fejlesztői és lokális deployment eszközként használjuk, míg a Kubernetes alatt containerd-et.

Rootful/rootless daemon policy: A dockerd rootful daemon; a daemon processz a host root jogosultságával fut, és bármilyen privilégizált konténert indíthat. A Docker sockethez való hozzáférés tehát host authority. A rootless Docker (dockerd rootless) a daemon processzt a felhasználó UID-jén futtatja, és user namespace mappinget használ, de a daemon-jelleg megmarad. A Podman rootless by default: nincs daemon, a CLI a felhasználó jogosultságával fut, és minden konténer user namespace-ben, a felhasználó UID-jére mappelve jön létre. A containerd rootful daemon, és rootless módja nem az általános usage.

Socket access és host authority: A Docker daemon Unix socketje /var/run/docker.sock, tulajdonosa root:docker. A docker csoport tagság valójában root jogosultságot ad a hoston, mert a daemon API-ján keresztül --privileged konténert lehet indítani, ami bind mountolhatja a host fájlrendszert. A Podman rootless socketje a felhasználó saját runtime könyvtárában van, és csak az adott user fér hozzá. A containerd socketje /run/containerd/containerd.sock, szintén root tulajdonú. A management access tehát mindig privilege határ: aki a sockethez írhat, az irányíthatja a runtime-ot, amely host szintű műveleteket végez.

Systemd/cgroup driver ownership: A container runtime és a systemd közötti cgroup hierarchia tulajdonosa dönti el, hogy ki kezeli a cgroup tree-t. A systemd cgroup driver azt jelenti, hogy a systemd delegálja a cgroup scope-okat, és a runtime egy systemd scope-ba helyezi a konténert. A cgroupfs driver pedig közvetlenül a /sys/fs/cgroup alá ír. A kettő keverése duplikált cgroup fákat és hibás OOM killer viselkedést okoz. A Docker daemon a exec-opts: ["native.cgroupdriver=systemd"] beállítással, a containerd a SystemdCgroup = true konfigurációval használja a systemd drivert. A Podman alapértelmezetten systemd drivert használ, akár rootful, akár rootless.

Runtime verzió/config/plugin támogatás: A containerd config.toml-ja deklarálja a runtime-ok listáját, például [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc] alatt a runtime_type, binary_name és SystemdCgroup mezőket. A Docker daemon daemon.json-ban a runtimes map segítségével adhatunk meg alternatív runtime-okat (pl. nvidia). A Podman a --runtime flaggel választ runtime-ot, de default a crun vagy runc. A verzió compatibility mindig ellenőrizendő: a containerd és a runc verzióskew API hibákat okozhat, például ha a runc túl régi a containerd által elvárt OCI specifikációhoz.

38.1.2 Kidolgozott példa

A példa egy Ubuntu Server 24.04 LTS labhoston fut, neve lab-vm1. A felhasználó labuser, aki nem tagja a docker csoportnak. A Docker CE és a containerd telepített, a verziók illusztratívak, a laborban ellenőrizendők.

Lépés 1: A daemon rétegek állapota.

# Target: lab-vm1, labuser, sudo szükséges a systemctl ellenőrzéshez
# Előfeltétel: Docker CE és containerd telepítve
sudo systemctl status docker --no-pager
sudo systemctl status containerd --no-pager
docker --version
sudo runc --version

Várható kimenet: docker.service active (running), containerd.service active (running), Docker version 27.x, runc version 1.1.x. A pontos verzió a labhoston ellenőrizendő.

Lépés 2: A containerd CRI plugin konfigurációja.

# Target: lab-vm1, labuser, sudo szükséges a config olvasásához
sudo cat /etc/containerd/config.toml

Várható, hogy a [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc] szekcióban runtime_type = "io.containerd.runc.v2" és SystemdCgroup = true szerepel. Ez mutatja a CRI plugin és az OCI runtime kapcsolatát.

Lépés 3: Minimális konténer és a folyamatfa.

# Target: lab-vm1, labuser, sudo szükséges a docker parancshoz (nincs docker csoport)
# Előfeltétel: a daemonok futnak
sudo docker run -d --name lab-d186-test --rm nginx:1.27-alpine sleep 300
sudo docker ps --filter name=lab-d186-test
sudo pstree -p | grep -A5 -B5 'sleep 300'

Várható folyamatfa (részlet): dockerd -> containerd -> containerd-shim-runc-v2 -> sleep 300. A run parancs --rm flagje biztosítja, hogy a kilépés után a konténer törlődik, tehát nincs külön rollback.

Lépés 4: A shim és a runc processzek azonosítása.

# Target: lab-vm1, labuser, sudo szükséges
sudo ps -eo pid,ppid,comm,args | grep -E 'containerd-shim|runc|sleep 300'

Várható: a containerd-shim-runc-v2 processz a sleep 300 parentje, és a shim parentje a containerd daemon. A runc processz nem marad futva, mert a konténer indítása után kilép.

Lépés 5: Podman rootless futtatás.

# Target: lab-vm1, labuser, nem root, rootless
# Előfeltétel: podman telepítve
podman info --format '{{.Host.Security.Rootless}}'  # expected: true
podman run --rm --name lab-d186-podman-test alpine:3.20 echo "rootless podman"
id -u

Várható: true, majd a szöveg, és az id -u a labuser UID-jét mutatja (nem 0). A folyamatfa itt: podman -> conmon -> runc -> echo, vagy a podman közvetlenül hívja a runc-ot. A conmon a Podman shim-szerepű processze.

Lépés 6: Socket hozzáférési határ teszt.

# Target: lab-vm1, labuser, docker csoport nélkül
docker ps  # elvárt: permission denied
sudo docker ps  # elvárt: működik
ls -l /var/run/docker.sock

Várható: Permission denied a labuser számára, a socket root:docker tulajdonú. Ez demonstrálja a socket hozzáférés jelentette host authority-t.

Rollback: A docker run --rm és podman run --rm automatikusan törli a konténereket; a sleep 300 megszakítása után nem marad állapot. A config megtekintése nem módosít.

38.1.3 Tipikus hibák és ellenpróbák

Hiba: cgroup driver mismatch. Tünet: Kubernetes alatt a pod cgroup-jai nem találhatók, OOM killer hibák, vagy a docker info Cgroup Driver: cgroupfs értéket mutat. Hipotézis: a daemon nem systemd drivert használ, miközben a systemd és a kubelet systemd cgroup hierarchiát vár. Adatgyűjtés: docker info --format '{{.CgroupDriver}}', cat /etc/containerd/config.toml | grep -A2 runc. Egy változtatás: a Docker daemon.json-ban exec-opts: ["native.cgroupdriver=systemd"], a containerd config.toml-ban SystemdCgroup = true, majd sudo systemctl restart docker containerd. Verifikáció: docker info --format '{{.CgroupDriver}}' returns systemd.

Hiba: Docker socket permission denied. Tünet: a docker ps parancs permission denied hibát ad. Hipotézis: a felhasználó nincs a docker csoportban, vagy a socket tulajdonosa/jogosultsága hibás. Adatgyűjtés: ls -l /var/run/docker.sock, id labuser. Egy változtatás: ne adjuk a felhasználót a docker csoporthoz, mert ez host authority-t ad; helyette sudo docker vagy rootless Podman. Verifikáció: sudo docker ps működik, vagy podman run --rm alpine echo ok futtatható a labuser-rel.

Hiba: runtime version skew. Tünet: a containerd logban runtime handler not supported vagy shim crash. Hipotézis: a runc verzió nem kompatibilis a containerd által elvárt OCI specifikációval. Adatgyűjtés: sudo runc --version, sudo containerd --version, containerd log. Egy változtatás: a support matrix szerint frissíteni a runc-ot, majd sudo systemctl restart containerd. Verifikáció: a shim elindul, a konténer fut.

Hiba: rootless Podman indítása sikertelen. Tünet: Error: could not get runtime: operation not permitted. Hipotézis: a kernel unprivileged_userns_clone le van tiltva. Adatgyűjtés: sysctl kernel.unprivileged_userns_clone. Egy változtatás: engedélyezni a user namespace-eket (sysctl kernel.unprivileged_userns_clone=1) vagy rootful futtatás. Verifikáció: podman run --rm alpine echo ok működik.

38.1.4 Feladatok

  1. Magyarázó feladat. Írja le szövegesen a Docker és a Podman futtatási láncát a CLI-től a kernelig, és jelölje meg, melyik komponens rendelkezik root jogosultsággal. Indokolja, miért nem a CLI az authority határ.

  2. Konfigurációs feladat. A labhoston (lab-vm1) állítsa be a containerd CRI pluginját systemd cgroup driverre, és a Docker daemon daemon.json-ját is systemd driverre. Ellenőrizze a docker info kimenetben a Cgroup Driver értékét. Adja meg a módosító parancsok targetjét, előfeltételét, ellenőrzését és rollbackjét.

  3. Diagnosztikai feladat. A lab-vm1 hoston a labuser a docker ps parancsra permission denied hibát kap. A felhasználó root jogosultság nélkül szeretne konténereket futtatni. Diagnosztizálja a socket hozzáférést, és válasszon biztonságos megoldást rootless Podman vagy sudo között. Indokolja a választást, és mutassa meg, hogy a futtatott konténer processz a labuser UID-jén fut.

38.1.5 Megoldások

  1. A Docker lánc: docker CLI (user) → /var/run/docker.sock (root:docker tulajdon) → dockerd (root) → containerd (root) → containerd-shim-runc-v2 (root) → runc (root) → konténerprocessz (root, ha nincs user namespace). A Podman: podman CLI (user) → conmon (user) → runc (user) → konténerprocessz (user, user namespace). Az authority határ a daemon socket vagy a daemon processz, mert a CLI csak egy klienst indít; a kernelprivilege-t a daemon/runtime gyakorolja. A sockethez való írási jog ugyanazt a hatalmat adja, mint a daemon root jogosultsága.

  2. A containerd config.toml-ban a CRI plugin runtime szekciójában SystemdCgroup = true beállítás szükséges. A Docker daemonhoz hozzon létre /etc/docker/daemon.json fájlt:

{
  "exec-opts": ["native.cgroupdriver=systemd"]
}

Módosító parancsok (target: lab-vm1, sudo szükséges):

sudo mkdir -p /etc/docker
echo '{"exec-opts": ["native.cgroupdriver=systemd"]}' | sudo tee /etc/docker/daemon.json
sudo systemctl restart docker

Ellenőrzés: sudo docker info --format '{{.CgroupDriver}}' → systemd. Rollback: a daemon.json törlése vagy visszaállítása, majd sudo systemctl restart docker. Postcondition: minden új konténer a systemd cgroup hierarchiában jön létre.

  1. A ls -l /var/run/docker.sock kimenete root:docker tulajdonost mutat. A labuser nincs a docker csoportban, ezért permission denied. Adatgyűjtés: id labuser nem mutatja a docker csoportot. Biztonságos megoldás: rootless Podman, mert nem ad host root authority-t. Telepítés után (sudo apt install podman) a labuser futtathat: podman run --rm alpine echo ok. A processz ellenőrzése: ps -o user,pid,comm -p $(pgrep -n -f 'echo ok') a labuser UID-jét mutatja. Ha a Podman nem elérhető, a sudo docker run alternatíva, de a sudo jogot limitálni kell dedikált parancsokra. Az indoklás: a rootless Podman nem igényel daemon-socket hozzáférést, így nincs kitett host authority.

38.1.6 Rövid összefoglaló

A konténer-futtatási lánc három fő rétegből áll: a felhasználói CLI, a daemon vagy high-level runtime (Docker daemon, containerd), és a low-level OCI runtime (runc). A Docker rootful daemonnal dolgozik a /var/run/docker.sock socketen keresztül, ahol a socket hozzáférés host authority-t jelent; a Podman daemon nélkül, rootless by default fut. A containerd CRI pluginja a Kubernetes runtime interface-t implementálja, és OCI runtime-ot hív. A shim (Docker esetén containerd-shim, Podman esetén conmon) leválasztja a konténer életciklusát a daemontól. A cgroup driver ownership a systemd és a runtime közötti megegyezésen múlik.

Továbbhasznált definíciók: OCI runtime – a konténer izolációt megvalósító processz (például runc), amely a kernel namespaces/cgroups hívásokat végzi; CRI – gRPC alapú Kubernetes container runtime interface; shim – a konténer és a daemon közötti hosszú életű processz, amely lehetővé teszi a daemon újraindítását a konténer leállítása nélkül.
