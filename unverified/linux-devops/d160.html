32.5 Komplex hálózati incidenslabor

32.5.1 Motiváció és vizsgálati szerződés

„A szolgáltatás néha nem érhető el” még nem hibadiagnózis. Ugyanezt a tünetet okozhatja hibás névfeloldás, hiányzó visszaút, csomagszűrés, tanúsítványhiba vagy az útvonal MTU-jának felderítési zavara. Ráadásul az első hiba elfedheti a másodikat.

A bizonyítékos gyökérokjelentés (root cause report) összekapcsolja a felhasználói tünetet, az érintett adatútvonalat, a közvetlen megfigyeléseket és a hibát előidéző mechanizmust. Az időbeli együttjárás önmagában nem elég: meg kell mutatni, hogy a célzott változtatás hogyan módosítja ugyanannak a próbának az eredményét.

Az ellenpróba (counterfactual test) egyetlen feltételt változtat meg. Például a DNS megkerülése rögzített IP-címmel úgy, hogy a TLS-szervernév és a tanúsítvány-ellenőrzés változatlan marad.

A labor a TLS/proxy és end-to-end elérhetőségi labor, a Teljes Linux bottleneck diagnosztikai labor és a Link/transport/app throughput és latency mérés módszereit kapcsolja össze. Az alábbi kimenetek és hibajelenségek várt eredmények; futtatás nem történt.

32.5.2 Topológia, állapot és korlátok

Minden parancs célpontja az izolált lab-netdiag VM, Ubuntu Server 24.04 LTS amd64 rendszerrel, dedikált Bash-munkamenetben, root, UID 0 jogosultsággal. Előfeltétel a telepített iproute2, nftables, dnsmasq-base, bind9-dnsutils, openssl, curl, python3 és tcpdump. Maradjon elérhető a VM konzolja.

A DNS explicit szervert használ; nem támaszkodunk a host resolverére. Két önaláírt tanúsítvány készül, mindkettő explicit megbízható a labor kliensének. Így a rossz tanúsítvány névhibát, nem ismeretlen kibocsátót modellez. Ez oktatási fixture, nem éles PKI-recept.

# lab-netdiag; root, UID 0; ugyanaz a munkamenet
printf '10.203.160.6 lab-api.test\n' > "$D/lab-hosts"
ip netns exec lab-d160-s dnsmasq --no-daemon \
    --conf-file=/dev/null --no-hosts --no-resolv \
    --interface=lab-s0 --bind-interfaces \
    --listen-address=10.203.160.6 --local=/test/ \
    --addn-hosts="$D/lab-hosts" --user=root \
    > "$D/lab-dns.log" 2>&1 &
DNS_PID=$!

for kind in good bad; do
    name=lab-api.test
    test "$kind" = good || name=lab-other.test
    openssl req -x509 -newkey rsa:2048 -nodes -days 2 \
        -subj "/CN=$name" -addext "subjectAltName=DNS:$name" \
        -keyout "$D/lab-$kind.key" -out "$D/lab-$kind.crt"
done
cat "$D/lab-good.crt" "$D/lab-bad.crt" > "$D/lab-trust.pem"

printf 'lab-ok\n' > "$D/lab-www/lab-small.txt"
head -c 262144 /dev/zero > "$D/lab-www/lab-large.bin"

cat > "$D/lab-server.py" <<'PY'
import http.server, os, ssl, sys
os.chdir(os.path.join(os.path.dirname(__file__), "lab-www"))
server = http.server.ThreadingHTTPServer(
    ("10.203.160.6", 8443), http.server.SimpleHTTPRequestHandler)
context = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)
context.load_cert_chain(sys.argv[1], sys.argv[2])
server.socket = context.wrap_socket(server.socket, server_side=True)
server.serve_forever()
PY

lab_tls_start() {
    ip netns exec lab-d160-s python3 "$D/lab-server.py" \
        "$D/lab-$1.crt" "$D/lab-$1.key" \
        >> "$D/lab-tls.log" 2>&1 &
    TLS_PID=$!
}
lab_tls_start good
ip netns exec lab-d160-s ss -lntup

A szolgáltatás csak a lab-www könyvtárat szolgálja ki; a kulcsfájlokat nem. A várt hallgató port DNS esetén 53, HTTPS esetén 8443. Ha még nem láthatók, ne kezdd el a baseline mérését: ellenőrizd a naplókat és ismételd meg a portvizsgálatot.

32.5.4 Azonos próba minden állapotban

A próba két fájlt kér le, fájlonként ötször, sorosan. A DNS-választ közvetlenül használja, miközben a TLS-ben továbbra is lab-api.test szerepel. A LAB_IP kizárólag az ellenpróba felülbírálása.

# lab-netdiag; root, UID 0
cat > "$D/lab-probe.sh" <<'BASH'
#!/bin/bash
D=/var/tmp/lab-d160
for object in lab-small.txt lab-large.bin; do
    for attempt in 1 2 3 4 5; do
        answer=$(ip netns exec lab-d160-c dig \
            @10.203.160.6 lab-api.test A +short +time=1 +tries=1)
        address=${LAB_IP:-$answer}
        case "$address" in
            10.203.160.5|10.203.160.6) ;;
            *) echo "$object attempt=$attempt DNS_FAIL"; continue ;;
        esac
        ip netns exec lab-d160-c curl --noproxy '*' \
            --silent --show-error --fail \
            --cacert "$D/lab-trust.pem" \
            --resolve "lab-api.test:8443:$address" \
            --connect-timeout 2 --max-time 5 \
            --output "$D/lab-result.body" \
            --write-out "$object attempt=$attempt http=%{http_code} bytes=%{size_download} connect_s=%{time_connect} tls_s=%{time_appconnect} total_s=%{time_total}\n" \
            "https://lab-api.test:8443/$object"
        rc=$?
        body_ok=no
        if test "$rc" -eq 0 &&
            cmp -s "$D/lab-www/$object" "$D/lab-result.body"; then
            body_ok=yes
        fi
        echo "curl_exit=$rc body_ok=$body_ok"
    done
done
BASH

lab_run() {
    python3 - "$D/lab-probe.sh" <<'PY'
import subprocess, sys, time
start = time.monotonic()
subprocess.run(["bash", sys.argv[1]], check=True)
print("window_s=", time.monotonic() - start)
PY
}
lab_run > "$D/lab-A-baseline.txt" 2>&1

Elfogadási feltétel: tíz sikeres kérés, mindegyiknél HTTP 200 és body_ok=yes. A fájlméretek 7 B és 262 144 B. A script sikeres kilépése önmagában nem acceptance: a sorokat kell értékelni.

Az ablak időtartama monoton órával mért. Az elért próbálkozási ráta:

λ=NΔt,e=N−GN, \lambda = \frac{N}{\Delta t}, \qquad e = \frac{N-G}{N},

ahol N=10N=10 a próbálkozások száma, GG a sikeresek száma, Δt\Delta t az ablak hossza másodpercben; λ\lambda egysége kérés/s, ee dimenzió nélküli hibaarány.

Ez zárt hurkú smoke test, nem kapacitásbenchmark. A curl idői nem tartalmazzák a külön dig futását. A hibás kérések és timeoutok külön maradjanak láthatók; tíz mintából ne állíts megbízható p99-et.

32.5.5 Kidolgozott kevert incidens: hibás DNS és csomageldobás

Először készíts csomagnyomot a kliensnél és a routernél:

# lab-netdiag; root, UID 0
ip netns exec lab-d160-c tcpdump -ni lab-c0 -s 0 \
    -w "$D/lab-client.pcap" 'port 53 or port 8443 or icmp' \
    2> "$D/lab-client-capture.log" &
CPID=$!
ip netns exec lab-d160-r tcpdump -ni any -s 0 \
    -w "$D/lab-router.pcap" 'port 53 or port 8443 or icmp' \
    2> "$D/lab-router-capture.log" &
RPID=$!

lab_fw_on() {
    ip netns exec lab-d160-r nft -f - <<'NFT'
table ip "lab-d160-fw" {
    chain "lab-forward" {
        type filter hook forward priority 0; policy accept;
        ip daddr 10.203.160.6 tcp dport 8443 counter drop
    }
}
NFT
}
lab_fw_off() {
    ip netns exec lab-d160-r nft \
        'delete table ip "lab-d160-fw"'
}

printf '10.203.160.5 lab-api.test\n' > "$D/lab-hosts"
kill -HUP "$DNS_PID"
lab_fw_on
lab_run > "$D/lab-B-broken.txt" 2>&1

A rossz DNS-cím a router saját címe. Ott nincs HTTPS-listener, ezért rendszerint gyors kapcsolatelutasítás várható. Ez még nem mutatja meg a helyes szerverhez vezető út hibáját.

Az ellenpróba rögzíti a helyes IP-t:

# lab-netdiag; root, UID 0
LAB_IP=10.203.160.6 lab_run > "$D/lab-C-bypass-dns.txt" 2>&1
ip netns exec lab-d160-r nft \
    'list table ip "lab-d160-fw"'

Várt különbség: a gyors elutasítás timeouttá változik, és nő a szűrőszabály számlálója. A DNS megkerülése tehát nem javította meg a szolgáltatást; feltárt egy második hibát.

Most egyesével javíts:

# lab-netdiag; root, UID 0
printf '10.203.160.6 lab-api.test\n' > "$D/lab-hosts"
kill -HUP "$DNS_PID"
lab_run > "$D/lab-D-dns-fixed.txt" 2>&1

lab_fw_off
lab_run > "$D/lab-E-repaired.txt" 2>&1

# Kontrollált visszaállítás a tűzfalhibás állapotba:
lab_fw_on
lab_run > "$D/lab-F-rollback.txt" 2>&1
lab_fw_off
lab_run > "$D/lab-G-final.txt" 2>&1

Az E és G állapotban tíz siker várható; D és F állapotban nem. Ez ugyanazzal a teszttel igazolja a javítás és annak visszavonása hatását. Éles incidensben hibás állapotot csak jóváhagyott, biztonságos környezetben állítunk vissza.

32.5.6 Mit láttunk, és mit következtetünk?

A rögzített esemény (captured event) és a következtetett esemény (inferred event) külön oszlopot kapjon:

Bizonyíték Megengedett következtetés Amit még nem bizonyít
DNS-válaszban .5 szerepel A vizsgált resolverút rossz címet adott Minden kliens ugyanazt kapta
Router bemenetén SYN látszik A SYN elérte ezt a mérési pontot Elhagyta a routert
Célzott drop számláló nő Csomagok illeszkedtek az eldobó szabályra A laboron kívüli forgalom állapota
TLS-névellenőrzési hiba Az ellenőrzés eljutott a tanúsítványig A HTTP-kiszolgálás működése
Javítás után helyes választest A meghatározott próba sikeres Tartós SLO-teljesítés

Gyűjts előtte–utána hálózati kernel- és interfészszámlálókat:

# lab-netdiag; root, UID 0; minden vizsgált állapotban
ip -n lab-d160-c -s link show dev lab-c0
ip netns exec lab-d160-c nstat -az \
    TcpRetransSegs TcpExtTCPTimeouts IpOutNoRoutes
ip -n lab-d160-c route get 10.203.160.6
ip -n lab-d160-s route get 10.203.160.1
ip netns exec lab-d160-s ss -lntp

A számlálók különbségét értelmezd, ne csak az abszolút értéket. Ezek névtérhez tartozó hálózati hostoldali adatok; a CPU és a kernel közös. Egy hostoldali CPU-terhelési ellenpróba segíthet kizárni, hogy a próbagenerátor vagy a szerver ütemezési késése uralja az eredményt.

A capture lezárása után ellenőrizd az elvesztett csomagokra vonatkozó jelentést:

# lab-netdiag; root, UID 0
kill -INT "$CPID" "$RPID"
wait "$CPID" "$RPID"
tcpdump -nn -r "$D/lab-router.pcap"
cat "$D/lab-client-capture.log" "$D/lab-router-capture.log"

A capture-ből hiányzó csomag önmagában nem bizonyít hálózati eldobást. Rossz interfész, szűrő vagy capture-vesztés is okozhatja. A router any felvételén ugyanaz a továbbított csomag több interfésznél is megjelenhet; ez nem automatikusan retransmission. A virtuális interfészek offloadjai a látható csomagméretet is torzíthatják.

32.5.7 További dokumentált hibakártyák

Ezeket külön, egészséges alapállapotból futtasd.

Eset Beavatkozás Célzott ellenőrzés és visszaút
TLS Rossz nevű tanúsítvány betöltése curl ellenőrzési hiba; jó tanúsítvánnyal újraindítás
Route Szerver default route törlése Visszaút lekérdezése; route visszaadása
MTU Router kliensoldali MTU csökkentése ICMP „fragmentation needed”, végponti TCP-állapot
PMTU black hole Az előző mellett a szükséges ICMP eldobása ICMP-drop számláló; csak az eldobás megszüntetése 
# lab-netdiag; root, UID 0
# TLS: injektálás, majd rollback
kill "$TLS_PID"; wait "$TLS_PID"
lab_tls_start bad
# Futtasd a lab_run próbát és vizsgáld a naplót.
kill "$TLS_PID"; wait "$TLS_PID"
lab_tls_start good

# Route: injektálás, majd rollback
ip -n lab-d160-s route del default via 10.203.160.5
# lab_run; route get 10.203.160.1
ip -n lab-d160-s route add default via 10.203.160.5

A route-hiba a DNS-választ is blokkolhatja: az első látható DNS-timeout nem bizonyít DNS-konfigurációs hibát.

A PMTU-esethez friss laborállapotot használj. A már megtanult kisebb PMTU elfedheti az újonnan injektált ICMP-eldobást.

# lab-netdiag; root, UID 0; friss, egészséges labor
ip netns exec lab-d160-s sysctl -w net.ipv4.tcp_mtu_probing=0
ip -n lab-d160-r link set lab-rc mtu 1280
ip netns exec lab-d160-r nft -f - <<'NFT'
table ip "lab-d160-pmtu" {
    chain "lab-output" {
        type filter hook output priority 0; policy accept;
        icmp type destination-unreachable icmp code 4 counter drop
    }
}
NFT

# lab_run, capture, számlálóvizsgálat
ip netns exec lab-d160-r nft \
    'list table ip "lab-d160-pmtu"'

# Célzott javítás: az alacsonyabb MTU megmarad.
ip netns exec lab-d160-r nft \
    'delete table ip "lab-d160-pmtu"'
# Ismét ugyanaz a lab_run.

# Topológiai rollback:
ip -n lab-d160-r link set lab-rc mtu 1500

A szerver felől érkező, túl nagy, nem fragmentálható IPv4-csomaghoz a routernek ICMP-visszajelzést kell küldenie. Ennek eldobása megakadályozhatja az alkalmazkodást. Már a TLS-kézfogás is elakadhat; a „kis válasz működik” nem kötelező tünet. A csökkentett MTU önmagában nem bizonyított gyökérok.

32.5.8 Feladatok

  1. Magyarázó: a router bemenetén SYN látható, kimenetén nem. Adj három hipotézist és mindegyikhez elkülönítő bizonyítékot.
  2. Adminisztrációs: hajtsd végre a DNS+tűzfal incidens A–G sorozatát. Készíts állapotonként siker/összes, hibaarány és időablak táblázatot.
  3. Diagnosztikai és recovery: vizsgáld meg a PMTU-esetet, majd javítsd az ICMP-kezelést az 1280 B MTU megtartásával. Készíts rövid postmortemet és regressziós smoke teszttervet.

32.5.9 Megoldások

  1. Lehetséges ok a szűrés, a hiányzó útvonal vagy a hiányos capture. Előbbihez célzott szabályszámláló, másodikhoz route-lekérdezés és esetleges ICMP-hiba, harmadikhoz megfelelő interfész/szűrő és capture-vesztési jelentés kell. Postcondition: a jelentés nem nevezi bizonyítottnak a tűzfalhibát pusztán csomaghiányból.

  2. A baseline, teljes javítás és végállapot elvárt eredménye 10/10 siker. A DNS javítása önmagában nem elég; az IP-felülbírálás megváltoztatja a hibajelenséget. A tűzfalváltoztatás visszavonása reprodukálja a timeoutot. Postcondition: minden állapothoz ugyanazon próbaverzió kimenete, verzióprofil és számlálódifferencia tartozik.

  3. Az eldobó szabály eltávolítása után a letöltésnek a kisebb MTU mellett is sikerülnie kell. Postcondition: helyes választest, megszűnő timeout, működő PMTU-visszajelzés. A postmortem tartalmazza a hatást, időrendet, bizonyítékot, mechanizmust, javítást, rollbacket és nyitott bizonytalanságokat. Regresszióként ellenőrizze a DNS-t, a TLS-nevet, a kétirányú útvonalat és a nagyobb választestet is.

Az evidence megőrzése után a cleanup csak a három saját névtérre terjedjen ki:

# lab-netdiag; root, UID 0
for ns in lab-d160-c lab-d160-r lab-d160-s; do
    for pid in $(ip netns pids "$ns"); do kill "$pid"; done
done
wait
for ns in lab-d160-c lab-d160-r lab-d160-s; do
    test -z "$(ip netns pids "$ns")" || exit 1
    ip netns del "$ns"
done
# /var/tmp/lab-d160 megmarad evidence-ként.

32.5.10 Rövid összefoglaló

A komplex hálózati incidensben az első látható hiba gyakran csak az első elért réteg hibája. A DNS megkerülése feltárhat tűzfalhibát; a TLS-timeout mögött PMTU-probléma is állhat. A megbízható vizsgálat rögzített topológiát, minimális próbát, több mérési pontot és számlálódifferenciákat használ. A javítást és annak kontrollált visszavonását ugyanazzal a teszttel kell ellenőrizni. A jelentés különítse el a közvetlen megfigyelést a következtetéstől, és nevezze meg a bizonyíték korlátait. A sikeres smoke test nem kapacitásmérés és nem tartós rendelkezésreállási bizonyíték.

  • Gyökérok: bizonyítékokkal alátámasztott, a hibát előidéző mechanizmus.
  • Ellenpróba: egyetlen feltételt módosító elkülönítő vizsgálat.
  • Regressziós smoke test: a korábbi hibát gyorsan felismerő, ismételhető ellenőrzés.
