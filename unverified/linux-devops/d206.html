42.1 Authn, RBAC és service account

42.1.1 Motiváció

Egy szenior C++ fejlesztő a saját Linux hosztján root-ként vagy sudo-val dolgozik, de egy Kubernetes clusterben minden API-hívás egy identitáshoz kötött. A CI/CD pipeline, a mikroszolgáltatás és az interaktív kubectl is más-más identitást képvisel. Ha egy pod a Kubernetes API-t hívja, vagy egy fejlesztő kubectl get pods-ot futtat, a válasz 401 Unauthorized vagy 403 Forbidden lehet. A kettő más hibaréteget jelez: a 401 hitelesítési (authentication, authn), a 403 engedélyezési (authorization, authz) probléma. A Linux capabilities-hez hasonlóan a Kubernetes is legkisebb jogosultságot (least privilege) támogat; a Role/RoleBinding és a ServiceAccount a namespace-be ágyazott identitásmodell alapelemei.

42.1.2 Definíció és rétegmodell

Authentication (authn): az API-kérelem érkező identitásának megállapítása. A Kubernetes API server a kérést valamelyik támogatott hitelesítési mechanizmussal köti egy User-höz, Group-hoz vagy ServiceAccount-hoz. Az eredmény a user.Info: név, UID, csoportok, extra attribútumok.

Authorization (authz): a hitelesített identitásnak milyen API-műveletet engedünk. A Kubernetes RBAC ezt a Subject (User, Group, ServiceAccount) és a Role/ClusterRole közötti bindinggal fejezi ki. Az authz nem állapítja meg, hogy a kérés payload-ja sért-e policy-t; az a harmadik réteg, az admission (d207), amely itt nincs tárgyalva.

ServiceAccount: a pod identitása a clusterben. Minden névtérben van egy default service account. A pod a spec.serviceAccountName mezővel választhat identitást; ha nem ad meg, a default service accountot kapja. A service account nem interaktív user, hanem a workload identitása.

Role és ClusterRole: szabályhalmaz (rules), amely erőforrásokhoz (resources) és műveletekhez (verbs) társít. A Role mindig egy adott namespace-ben él, tehát namespaced scope-ú. A ClusterRole cluster-scope-ú, de használható namespaced bindinggal is, ilyenkor a hatása az adott namespace-re korlátozódik. A RoleBinding vagy ClusterRoleBinding köti össze a subjecteket a role-okkal; a scope-ot végső soron a binding típusa és a namespace határozza meg, nem a Role neve.

A kérés útja az API serverben: hitelesítés → engedélyezés → admission → object-művelet. Ebből a d206 az első két állomást tárgyalja.

42.1.3 Authentication és identity integráció

A Kubernetes API server a kube-apiserver konfigurációban engedélyezett hitelesítési módszereket használja. A leggyakoribbak:

  • Client certificate: a kubeconfig users[].user.client-certificate-data mezőjében megadott X.509 tanúsítvány. A Common Name a username, az Organization mezők a csoportok. A cert aláírását az API server hiteles CA-jából kell származnia. Ez a módszer egyszerű, de a cert lejáratát és visszavonását külön kezelni kell.

  • OIDC (OpenID Connect): az API server egy OIDC provider id_token token-jét fogadja. A kubectl --token vagy --token-file paraméterrel küldi. A token claimjei alapján a sub az username, a groups claim a csoportok. OIDC esetén az identitás source-ja külső, és a token érvényességét az API server csak a provider aláírásával ellenőrzi.

  • ServiceAccount bound token: a pod a projected volume-ból kap egy időkorlátos, audience-kötött, pod UID-jához rögzített token-t. Ezt az API server a TokenRequest API-val adja ki; nem hosszú élettartamú Secret, hanem rövid lejáratú, automatikusan rotálandó hitelesítő adat. A régi, Secret-be ágyazott service account token mára elavult.

A kubectl auth whoami (újabb verziókban) megmutatja az aktuális identitást, de a klasszikus módszer kubectl config view és kubectl auth can-i --list. A d206-ban a service account token-t és az impersonation-t használjuk a tanulási célok miatt.

42.1.4 RBAC modell: verbs, resource, subresource

Egy rules elem a következő mezőket tartalmazza:

  • apiGroups: az erőforrás API csoportja; a core API-v1 erőforrásoknál "" üres string.
  • resources: az erőforrások neve, például pods, deployments, services.
  • resourceNames: opcionálisan egyedi erőforrásnevek, ha csak specifikus objektumokra engedélyezünk.
  • verbs: a művelet. A leggyakoribb: get, list, watch, create, update, patch, delete, deletecollection. Az * mindent enged.
  • subresources: az erőforrás alerőforrásai, például pods/log, pods/exec, pods/status, deployments/scale.

Fontos: a kubectl logs a pods/log subresource-t kéri, tehát a get pods engedély önmagában nem elegendő a kubectl logs-hoz. Hasonlóan a kubectl exec a pods/exec subresource-t használja.

A binding mezői:

  • subjects: lista, amely User, Group vagy ServiceAccount elemeket tartalmaz. ServiceAccount esetén a namespace mező is kötelező, még akkor is, ha a binding egy ClusterRoleBinding.
  • roleRef: hivatkozás egy Role-ra vagy ClusterRole-ra az apiGroup, kind, name szerint. A roleRef nem a namespace-re mutat; a RoleBinding esetén a Role a RoleBinding namespace-ében kell hogy legyen.

A scope-ot a binding típusa határozza meg:

  • RoleBinding egy namespace-ben él, és a subjectek csak az adott namespace-erőforrásokra kapnak jogot. Hivatkozhat Role-ra (same namespace) vagy ClusterRole-ra (cluster-scope role leszűkítve a RoleBinding namespace-ére).
  • ClusterRoleBinding cluster-scope: a subjectek cluster-szintű, namespaced erőforrásokra minden névtérben, illetve cluster-scope erőforrásokra (például nodes, namespaces, persistentvolumes) kapnak jogot.

42.1.5 Bound service account token működése

A pod a /var/run/secrets/kubernetes.io/serviceaccount/token fájlban kapja a token-t, ha a service account automountServiceAccountToken mezője nem tiltott. A token egy JWT, amelyet a Kubernetes control plane írt alá. A token bennfoglalt adatai: a service account neve, namespace, pod UID, audience, expiration. A kubectl create token parancs is használható, hogy az adminisztrátor kívülről kérjen egy rövid token-t, például CI/CD célra:

kubectl --context lab-cluster-admin --namespace lab-d206 create token lab-d206-reader --duration=15m

A token lejárta után az API server 401-et ad, nem 403-at. A token audience-nek meg kell egyeznie az API server elvárt audience-ével, különben a hitelesítés sikertelen.

42.1.6 Kidolgozott példa: Role, ServiceAccount, RoleBinding és can-i

Topológia:

  • Cluster: lab-cluster
  • Admin context: lab-cluster-admin (cluster-admin jog)
  • Namespace: lab-d206
  • ServiceAccount: lab-d206-reader
  • Desired state: a service account a lab-d206 namespace-ben get, list, watch jogot kap a pods erőforrásra, de semmi mást.

1. Namespace létrehozása:

kubectl --context lab-cluster-admin create namespace lab-d206 --dry-run=client -o yaml | kubectl --context lab-cluster-admin apply -f -

2. Role YAML manifest:

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: lab-d206-pod-reader
  namespace: lab-d206
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
kubectl --context lab-cluster-admin apply -f role.yaml

3. ServiceAccount manifest:

apiVersion: v1
kind: ServiceAccount
metadata:
  name: lab-d206-reader
  namespace: lab-d206
kubectl --context lab-cluster-admin apply -f serviceaccount.yaml

4. RoleBinding manifest:

apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: lab-d206-reader-binding
  namespace: lab-d206
subjects:
- kind: ServiceAccount
  name: lab-d206-reader
  namespace: lab-d206
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: lab-d206-pod-reader
kubectl --context lab-cluster-admin apply -f rolebinding.yaml

5. Ellenőrzés impersonation és auth can-i használatával:

A kubectl auth can-i az admin user impersonation jogával kérdezi le, hogy a service account milyen műveletet kapott. Az impersonation-t az --as flag aktiválja, a subject teljes neve system:serviceaccount:lab-d206:lab-d206-reader.

kubectl --context lab-cluster-admin --namespace lab-d206 auth can-i get pods --as=system:serviceaccount:lab-d206:lab-d206-reader
# Várt kimenet: yes

kubectl --context lab-cluster-admin --namespace lab-d206 auth can-i get services --as=system:serviceaccount:lab-d206:lab-d206-reader
# Várt kimenet: no

kubectl --context lab-cluster-admin --namespace lab-d206 auth can-i list pods --as=system:serviceaccount:lab-d206:lab-d206-reader
# Várt kimenet: yes

kubectl --context lab-cluster-admin --namespace lab-d206 auth can-i create pods --as=system:serviceaccount:lab-d206:lab-d206-reader
# Várt kimenet: no

A --list opció megmutatja az összes engedélyt:

kubectl --context lab-cluster-admin --namespace lab-d206 auth can-i --list --as=system:serviceaccount:lab-d206:lab-d206-reader

A várt kimenetben csak a pods erőforrás get, list, watch engedélyei szerepelnek.

6. Cluster-Scope párhuzam: ClusterRole és ClusterRoleBinding

Ha ugyanezt az engedélyt cluster scope-ban szeretnénk a nodes erőforrásra, akkor ClusterRole-t kell használni, mert a nodes nem namespaced erőforrás:

apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: lab-d206-node-reader
rules:
- apiGroups: [""]
  resources: ["nodes"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: lab-d206-node-reader-binding
subjects:
- kind: ServiceAccount
  name: lab-d206-reader
  namespace: lab-d206
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: lab-d206-node-reader
kubectl --context lab-cluster-admin apply -f clusterrole.yaml
kubectl --context lab-cluster-admin auth can-i get nodes --as=system:serviceaccount:lab-d206:lab-d206-reader
# Várt kimenet: yes

A RoleBinding namespaced scope-ot ad, a ClusterRoleBinding cluster scope-ot. A lab-d206-pod-reader Role egy lab-d206 namespace-re korlátozott engedély, még akkor is, ha egy másik namespace-ű RoleBinding próbálná használni – a Role nem létezik más namespace-ben.

7. Rollback és cleanup:

kubectl --context lab-cluster-admin delete namespace lab-d206
# A namespace törlése eltávolítja a benne lévő Role, ServiceAccount, RoleBinding objektumokat is.

42.1.7 Hibák és ellenpróbák

401 Unauthorized vs 403 Forbidden. A 401 az authn réteg hibája: hiányzó, lejárt, rossz audience-ű token, vagy érvénytelen client cert. A 403 az authz hibája: az identitás ismert, de nincs RBAC engedélye. A kubectl hibaüzenetében a cannot list resource "pods" in API group "" in the namespace "lab-d206" típusú szöveg mellett a HTTP state-code utal a rétegre. A diagnózishoz kubectl auth can-i --list az adott user kontextusában.

Hibás ns vagy roleRef. Ha a RoleBinding roleRef.kind mezője ClusterRole, de a roleRef.name egy nem létező ClusterRole, akkor a RoleBinding létrejöhet, de a hivatkozott role nem található. Az engedélyek így nem lesznek aktívak. A kubectl describe rolebinding megmutatja a roleRef-et.

Subresource hiánya. A get pods engedély nem ad logs-ot. A kubectl logs 403-at ad. A Role hozzá kell, hogy adja a pods/log subresource-t.

Impersonation hiánya. A --as flag használatához az admin usernek impersonate verb-joga kell legyen a cél user-re. Ha nincs, a can-i válasza no, de nem a vizsgált service account hibája, hanem az admin saját joghiánya. Ilyenkor a cluster-admin szerep biztosítja.

Least privilege és break-glass. A * verbs és * resources túl széles. A helyes gyakorlat: minden ServiceAccount csak a szükséges erőforrásokat és műveleteket kapja. Vészhelyzetre egy külön break-glass ClusterRoleBinding készíthető, amelyet csak incidenskor alkalmazunk, és az API audit logban az impersonation vagy a binding létrehozása nyomot hagy. A break-glass bindingot a hiba elhárítása után azonnal el kell távolítani.

42.1.8 Feladatok

F1. Magyarázó feladat

Hozd létre a fenti Role, ServiceAccount, RoleBinding objektumokat a lab-d206 namespace-ben. Ellenőrizd az engedélyeket auth can-i --list segítségével. Válaszold meg: miért yes a get pods és miért no a get services az impersonált service account számára? Mit mutat a auth can-i --list kimenet a RoleBinding után, ha a Role nem létezett volna?

F2. Adminisztrációs feladat

Készíts egy új ServiceAccount lab-d206-log-reader néven, amely a lab-d206 namespace-ben a pods/log subresource-ra get, list, watch jogot kap. Használj Role-t lab-d206-log-reader-role és RoleBinding-ot lab-d206-log-reader-binding néven. Hozz létre egy podot serviceAccountName: lab-d206-log-reader mezővel. Ellenőrizd a jogot admin oldalról kubectl --context lab-cluster-admin --namespace lab-d206 auth can-i get pods/log --as=system:serviceaccount:lab-d206:lab-d206-log-reader. Posztkondíció: a pod csak a log olvasására jogosult, de a pod get-re nem, tehát a kubectl get pods impersonálva no legyen.

F3. Diagnosztikai feladat

Egy fejlesztő panaszolja: kubectl --context lab-dev --namespace lab-d206 get pods 403-at ad. Írj rövid runbookot a hibakereséshez, amely tartalmazza:

  1. Az authn vs authz eldöntését: kubectl --context lab-dev --namespace lab-d206 auth whoami vagy auth can-i --list.
  2. A hiányzó engedély azonosítását: hasonlítsd össze az admin --as-es auth can-i --list kimenetével.
  3. A javítást: hozz létre egy Role-t lab-d206-dev-pod-reader és RoleBinding-ot lab-d206-dev-pod-reader-binding, amely a fejlesztő user-ét (például csoport lab-dev-group) a pod get, list, watch-ra köti a lab-d206 namespace-ben.
  4. Az ellenőrzést és rollbacket.

Posztkondíció: a fejlesztő a lab-d206 namespace-ben csak pod get, list, watch jogot kap, az API audit logban a RoleBinding létrehozása látszik.

42.1.9 Megoldások

F1 megoldás

A kubectl auth can-i --list --as=system:serviceaccount:lab-d206:lab-d206-reader --namespace lab-d206 kimenetében a Role által engedélyezett pods get, list, watch jelenik meg. A get services azért no, mert a Role resources mezője csak pods-t tartalmaz. Ha a Role nem létezne, a RoleBinding létrejönne, de a roleRef hivatkozás nem oldódik fel; a auth can-i --list üres lenne, vagy a describe rolebinding hibát mutatna a hiányzó Role miatt.

F2 megoldás

A Role YAML:

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: lab-d206-log-reader-role
  namespace: lab-d206
rules:
- apiGroups: [""]
  resources: ["pods/log"]
  verbs: ["get", "list", "watch"]

ServiceAccount és RoleBinding a fenti mintához hasonlóan. A pod manifest:

apiVersion: v1
kind: Pod
metadata:
  name: lab-d206-log-reader-pod
  namespace: lab-d206
spec:
  serviceAccountName: lab-d206-log-reader
  containers:
  - name: app
    image: busybox
    command: ["sleep", "3600"]

Ellenőrzés:

kubectl --context lab-cluster-admin --namespace lab-d206 auth can-i get pods/log --as=system:serviceaccount:lab-d206:lab-d206-log-reader
# Várt: yes

kubectl --context lab-cluster-admin --namespace lab-d206 auth can-i get pods --as=system:serviceaccount:lab-d206:lab-d206-log-reader
# Várt: no

A pod belső token-je az API serverhez /var/run/secrets/kubernetes.io/serviceaccount/token útvonalon érhető el.

F3 megoldás

Runbook:

  1. Authn ellenőrzése: ha kubectl --context lab-dev --namespace lab-d206 auth whoami hibát ad, akkor a context nem érvényes; ha a user felismerhető, de 403 van, akkor authz.
  2. kubectl --context lab-dev --namespace lab-d206 auth can-i --list — ha a pod list hiányzik, akkor RBAC hiba.
  3. A Role és RoleBinding létrehozása a lab-dev-group csoportra:
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: lab-d206-dev-pod-reader
  namespace: lab-d206
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: lab-d206-dev-pod-reader-binding
  namespace: lab-d206
subjects:
- kind: Group
  name: lab-dev-group
  apiGroup: rbac.authorization.k8s.io
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: lab-d206-dev-pod-reader
  1. Alkalmazás és ellenőrzés: kubectl --context lab-cluster-admin apply -f fix.yaml, majd kubectl --context lab-dev --namespace lab-d206 auth can-i list pods yes legyen. A rollback a RoleBinding törlésével lehetséges, ha túl széles lenne.

42.1.10 Rövid összefoglaló

Az API-hívások hitelesítése (authn) User, Group vagy ServiceAccount identitást állapít meg client cert, OIDC token vagy bound service account token alapján. Az RBAC engedélyezés (authz) Role/ClusterRole és RoleBinding/ClusterRoleBinding párokkal ad jogot erőforrásokra, subresource-okra és verbs-ekre. A Role namespace-scope-ú, a ClusterRole cluster-scope, de ClusterRole namespaced bindinggal szűkíthető. A kubectl auth can-i és az --as impersonation segítségével az engedélyeket biztonságosan ellenőrizhetjük. A 401 authn, a 403 authz hibát jelez. A legkisebb jogosultság elvét mindig kövessük, vészhelyzetre pedig külön, auditált break-glass binding szolgál.

Definíciók: Authn – identitás megállapítása; RBAC – szerep alapú hozzáférés-szabályozás; Bound service account token – rövid élettartamú, pod UID-jához kötött token.
