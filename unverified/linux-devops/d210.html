42.5 RBAC/admission/secret diagnosztikai labor

42.5.1 Motiváció és laborkontraktus

Egy Kubernetes clusterben a „Forbidden” üzenet egyszerre jelenthet API authorizációs hibát, admission denialt, quota-sértést vagy hálózatpolitikai blokkot. A diagnosztika akkor pontos, ha ezeket a rétegeket külön tudjuk kérdezni. Ez a labor pozitív és negatív acceptance teszteket ír elő egy lab-tenant nevű elszigetelt namespace-ben, ahol minden teszt identity, scope, desired state és observed state szerint rögzített.

A labor nem éles klaszteren fut. A labctx context a laborclusterre mutat, a labadmin felhasználó namespace-létrehozási és impersonate joggal rendelkezik. A példák kiadási adatait a labor inventory rögzíti, mert a Kubernetes, a CNI és a Pod Security implementáció verziófüggő lehet.

42.5.2 Definíciók

  • RBAC denial: az API server az autentikáció után a Role/ClusterRole/RoleBinding/ClusterRoleBinding alapján megtagadja a kérést. Tipikus HTTP státusz: 403, az audit eseményben authorization.k8s.io/decision: forbid.
  • Admission denial: az API authorizáció engedélyezné a kérést, de egy admission webhook, Pod Security admission, ResourceQuota vagy más policy elutasítja. A hibaüzenet általában a konkrét policyra mutat.
  • Workload token/secret access: a Pod által használt projected service account token hitelesíti a munkaterhelést. A Secrethez való API-hozzáférés akkor is lehet RBAC-denial, ha a Secret egyébként volume-ban csatolva elérhető.
  • Can-i matrix: kubectl auth can-i vagy a SelfSubjectAccessReview API segítségével készített táblázat, amely identitynként és verb/resource páronként rögzíti az engedélyt.

A labor desired/observed állapotokat választ el. A desired az acceptance tesztben elvárt kimenet, az observed a tényleges API válasz. A config-source a YAML-fájl commitja, a stored state az etcd-ben tárolt objektum.

kubectl -n lab-tenant create serviceaccount lab-sa-report

42.5.4 Minimal Role és can-i matrix

Első acceptance tesztünk az, hogy a lab-sa-report csak get és list jogot kap a Pod objektumokra, minden más API műveletet megtagadunk. A Role a namespace-scope, a RoleBinding pedig csak a lab-sa-report identityhöz köt.

# lab-minimal-rbac.yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: lab-tenant
  name: lab-role-report
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: lab-tenant
  name: lab-rb-report
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: lab-role-report
subjects:
  - kind: ServiceAccount
    name: lab-sa-report
    namespace: lab-tenant

Alkalmazzuk és futtassuk a mátrixot:

# target: labctx/lab-tenant, labadmin
kubectl apply -f lab-minimal-rbac.yaml

for verb in get list create delete; do
  printf '%-6s pods: ' "$verb"
  kubectl auth can-i "$verb" pods \
    --as=system:serviceaccount:lab-tenant:lab-sa-report \
    -n lab-tenant
done

printf 'get secrets: '
kubectl auth can-i get secrets \
  --as=system:serviceaccount:lab-tenant:lab-sa-report \
  -n lab-tenant

Várt mátrix:

identity verb/resource várt
lab-sa-report get pods yes
lab-sa-report list pods yes
lab-sa-report create pods no
lab-sa-report delete pods no
lab-sa-report get secrets no

Ha az observed eltér, először az audit log authorization döntését nézzük, majd a RoleBinding subjects mezőjét. Gyakori hiba, hogy a ServiceAccount neve jó, de a namespace nem egyezik, vagy a RoleBinding a namespace-ben máshová kerül.

42.5.5 Pod security/admission rejection fixture

Most tiltsuk le a lab-tenant namespace-ben a privileged Podokat a Pod Security admission segítségével:

# target: labctx/lab-tenant, labadmin
kubectl label namespace lab-tenant \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/warn=restricted \
  --overwrite

A negatív fixture a lab-sa-reject identityvel próbál privileged securityContextet indítani:

# lab-reject-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: lab-pod-privileged
  namespace: lab-tenant
spec:
  serviceAccountName: lab-sa-reject
  containers:
    - name: c
      image: labtools:1.0-fixture
      command: ["sleep", "3600"]
      securityContext:
        privileged: true
# target: labctx/lab-tenant, labadmin
kubectl apply -f lab-reject-pod.yaml

Várt, illusztratív API deny:

Error from server (Forbidden): error when creating "lab-reject-pod.yaml":
pods "lab-pod-privileged" is forbidden: violates PodSecurity
"restricted:latest": privileged (container "c" must not set
securityContext.privileged=true)

A hibaüzenet pontos szövege Kubernetes-verziónként változhat, de a diagnosztikai szempont a döntő: amikor a kubectl auth can-i create pods yes, és a kubectl apply create pod mégis Forbidden, akkor admission vagy quota réteget vizsgálunk, nem RBAC-ot. A pod létre sem jön, ezt a következővel ellenőrizzük:

kubectl -n lab-tenant get pod lab-pod-privileged
# várt: Error from server (NotFound): pods "lab-pod-privileged" not found

42.5.6 Workload token/secret access

Adjunk a lab-sa-report számára egy szűk Secret-hozzáférést, de csak a lab-app-secret nevű Secret get műveletére. A list és más Secretek továbbra is denied:

# lab-secret-reader.yaml
apiVersion: v1
kind: Secret
metadata:
  namespace: lab-tenant
  name: lab-app-secret
type: Opaque
stringData:
  api_key: dummy-value
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: lab-tenant
  name: lab-role-secret-reader
rules:
  - apiGroups: [""]
    resources: ["secrets"]
    resourceNames: ["lab-app-secret"]
    verbs: ["get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: lab-tenant
  name: lab-rb-secret-reader
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: lab-role-secret-reader
subjects:
  - kind: ServiceAccount
    name: lab-sa-report
    namespace: lab-tenant

Alkalmazás után bővítsük a mátrixot:

kubectl apply -f lab-secret-reader.yaml
kubectl auth can-i get secret lab-app-secret \
  --as=system:serviceaccount:lab-tenant:lab-sa-report -n lab-tenant
# várt: yes

kubectl auth can-i list secrets \
  --as=system:serviceaccount:lab-tenant:lab-sa-report -n lab-tenant
# várt: no

kubectl auth can-i get secret lab-other \
  --as=system:serviceaccount:lab-tenant:lab-sa-report -n lab-tenant
# várt: no

Most indítsunk egy restricted-kompatibilis Podot a lab-sa-report identityvel, és csatoljuk a Secretet volume mount-ként is. Így egyszerre teszteljük a Pod indítását admission alatt, a projected token meglétét és a Secret-hozzáférést:

# lab-token-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: lab-token-test
  namespace: lab-tenant
spec:
  serviceAccountName: lab-sa-report
  automountServiceAccountToken: true
  containers:
    - name: tools
      image: labtools:1.0-fixture
      command: ["sh", "-c", "sleep infinity"]
      securityContext:
        allowPrivilegeEscalation: false
        capabilities:
          drop: ["ALL"]
        runAsNonRoot: true
        runAsUser: 1000
        runAsGroup: 3000
        seccompProfile:
          type: RuntimeDefault
      volumeMounts:
        - name: app-secret
          mountPath: /etc/lab-secret
          readOnly: true
  volumes:
    - name: app-secret
      secret:
        secretName: lab-app-secret

A Pod elindítása pozitív admission teszt: a restricted policy alatt a fenti securityContext engedélyezett, mert nem kér privileged, hostPath, extra capability vagy host namespace hozzáférést.

kubectl apply -f lab-token-pod.yaml
kubectl -n lab-tenant get pod lab-token-test
# várt observed: Running

A workload token API-hozzáférést a Pod belsejéből teszteljük. Az alábbi parancs a projected token nevű fájlt olvassa, és a Kubernetes API-n lekéri a Secretet:

# target: labctx/lab-tenant, labadmin
kubectl -n lab-tenant exec lab-token-test -- sh -c '
  TOKEN=$(cat /var/run/secrets/kubernetes.io/serviceaccount/token)
  curl -sS -o /tmp/secret.json -w "%{http_code}\n" \
    -H "Authorization: Bearer $TOKEN" \
    --cacert /var/run/secrets/kubernetes.io/serviceaccount/ca.crt \
    https://kubernetes.default.svc/api/v1/namespaces/lab-tenant/secrets/lab-app-secret
'
# várt: 200

Negatív teszt ugyanezzel a token nel, de list secrets:

kubectl -n lab-tenant exec lab-token-test -- sh -c '
  TOKEN=$(cat /var/run/secrets/kubernetes.io/serviceaccount/token)
  curl -sS -o /dev/null -w "%{http_code}\n" \
    -H "Authorization: Bearer $TOKEN" \
    --cacert /var/run/secrets/kubernetes.io/serviceaccount/ca.crt \
    https://kubernetes.default.svc/api/v1/namespaces/lab-tenant/secrets
'
# várt: 403

42.5.7 Quota és NetworkPolicy együtt

A multi-tenancy laborban a ResourceQuota és a NetworkPolicy ugyanabban a namespace-ben élhet. Elsőként állítsunk be egy olyan quota-t, amely a Secretek számát egyre korlátozza. Mivel a lab-app-secret már létezik, egy második Secretnek denied kell lennie:

# lab-quota.yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  namespace: lab-tenant
  name: lab-quota
spec:
  hard:
    secrets: "1"
kubectl apply -f lab-quota.yaml

kubectl -n lab-tenant create secret generic lab-extra-secret \
  --from-literal=key=value
# várt, illusztratív:
# Error from server (Forbidden): secrets "lab-extra-secret" is forbidden:
# exceeded quota: lab-quota, requested: secrets=1, used: secrets=1,
# limited: secrets=1

Ez ismét admission-réteg, nem RBAC: kubectl auth can-i create secrets --as=labadmin általában yes. A hibából az exceeded quota szöveg azonosítja a ResourceQuota okot.

A NetworkPolicy-t egy lab-echo Podra alkalmazzuk. Csak az access: allowed labelű Podok ingress-e engedélyezett:

# lab-echo-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: lab-echo
  namespace: lab-tenant
  labels:
    app: lab-echo
spec:
  containers:
    - name: echo
      image: labtools:1.0-fixture
      command:
        - sh
        - -c
        - |
          python3 -c 'import http.server;http.server.HTTPServer(("0.0.0.0",8080),http.server.SimpleHTTPRequestHandler).serve_forever()'
      ports:
        - containerPort: 8080
      securityContext:
        allowPrivilegeEscalation: false
        capabilities:
          drop: ["ALL"]
        runAsNonRoot: true
        runAsUser: 1000
        runAsGroup: 3000
        seccompProfile:
          type: RuntimeDefault
---
apiVersion: v1
kind: Service
metadata:
  namespace: lab-tenant
  name: lab-echo
spec:
  selector:
    app: lab-echo
  ports:
    - port: 8080
      targetPort: 8080
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  namespace: lab-tenant
  name: lab-echo-np
spec:
  podSelector:
    matchLabels:
      app: lab-echo
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              access: allowed
      ports:
        - protocol: TCP
          port: 8080
kubectl apply -f lab-echo-pod.yaml
kubectl -n lab-tenant get pod lab-echo
# várt: Running

kubectl -n lab-tenant exec lab-token-test -- \
  curl --max-time 2 -sS -o /dev/null -w '%{http_code}\n' \
  http://lab-echo:8080/
# várt: nem 200; jellemzően 000, timeout vagy connection refused

Ezután adjuk meg a lab-token-test Podnak az access=allowed labelet, és ismételjük meg a kérést:

kubectl -n lab-tenant label pod lab-token-test access=allowed --overwrite
kubectl -n lab-tenant exec lab-token-test -- \
  curl --max-time 5 -sS -o /dev/null -w '%{http_code}\n' \
  http://lab-echo:8080/
# várt: 200

A rollback a label törlése:

kubectl -n lab-tenant label pod lab-token-test access- 2>/dev/null || true

42.5.8 Audit event és credential rotation

A denial okát audit oldalon is rögzíteni kell. Ha a laborcluster nem teszi elérhetővé az API server audit logját, használjunk lab-fixture-t. Az alábbi illusztratív esemény a lab-sa-report list secrets RBAC-denialját mutatja:

{
  "kind": "Event",
  "level": "RequestResponse",
  "verb": "list",
  "resource": "secrets",
  "namespace": "lab-tenant",
  "user": {
    "username": "system:serviceaccount:lab-tenant:lab-sa-report"
  },
  "responseStatus": {
    "code": 403
  },
  "annotations": {
    "authorization.k8s.io/decision": "forbid"
  }
}

Az audit event mezői és a policy formátuma Kubernetes-verzió és az API server konfiguráció szerint változhat, ezért a minta nem állandó bizonyíték, hanem diagnosztikai irány.

A Secret rotation-t ugyanazon a lab-app-secret volume mounton keresztül teszteljük:

export OLD_VALUE="dummy-value"
export NEW_VALUE="dummy-value-v2"

# Visszaállítási pont rögzítése
kubectl -n lab-tenant get secret lab-app-secret -o yaml > lab-app-secret-backup.yaml

# Rotate
kubectl -n lab-tenant create secret generic lab-app-secret \
  --from-literal=api_key="$NEW_VALUE" \
  --dry-run=client -o yaml | kubectl apply -f -

# Wait, majd ellenőrzés a Podban
for i in $(seq 1 30); do
  value=$(kubectl -n lab-tenant exec lab-token-test -- cat /etc/lab-secret/api_key)
  if [ "$value" = "$NEW_VALUE" ]; then
    echo "rotated: $value"
    break
  fi
  sleep 2
done

Várt postcondition: a mounted Secret értéke dummy-value-v2, a régi dummy-value nem szerepel a kubectl get secret lab-app-secret -o yaml kimenetben.

Ha a Pod environment változóból olvassa a Secretet, nem elég a Secret mutation, mert a környezeti változó nem frissül. Ilyenkor kubectl -n lab-tenant delete pod lab-token-test && kubectl apply -f lab-token-pod.yaml vagy Deployment rollout szükséges. A labor a volume mountos változatot használja, mert az mutatja a kubelet aszinkron propagation tulajdonságát is.

42.5.9 Tipikus hibák és ellenpróbák

Jelenség Hipotézis Adatgyűjtés
kubectl get secret 403 RBAC hiány kubectl auth can-i get secrets --as=... és audit event
kubectl create pod 403, de auth can-i create pods yes Admission, PSA, quota kubectl apply hibaszöveg, ResourceQuota status
Pod Running, Secret API 403 Token vagy RBAC Podból curl a token nel, kubectl auth can-i --as=...
Pod Running, curl a Service-re timeout NetworkPolicy kubectl get networkpolicy, label, teszt access=allowed
Secret mount értéke nem frissül Env var vagy kubelet propagation kubectl describe pod, kubectl exec

Gyakori hiba, hogy a diagnosztika kubectl get hibaszöveget néz anélkül, hogy megkérdezné az authorizációs réteget. Egy másik tipikus hiba, hogy a quota-sértést RBAC-ként kezelik, vagy minden Forbidden láttán szélesebb Role-t adnak. Ehelyett először a deny rétegét kell bizonyítani, majd egyetlen változtatást végrehajtani.

42.5.10 Feladatok

42.5.10.1 1. Magyarázó feladat: can-i matrix minimális identityvel

Készíts egy lab-tenant namespace-ben új lab-sa-metrics ServiceAccountot, majd adj neki Role-t, amely csak get és list műveletet enged a pods resource-ra. Futtasd a kubectl auth can-i parancsot a get, list, create és delete verbekre. Rögzítsd táblázatban a desired és observed eredményeket. Miért nem elegendő a kubectl get pods hibaszöveg önmagában a diagnózishoz?

42.5.10.2 2. Adminisztrációs/konfigurációs feladat: Pod Security és Secret rotation

Állítsd a lab-tenant namespace-t pod-security.kubernetes.io/enforce=restricted szintre. Próbálj elindítani egy privileged Podot, majd egy restricted-kompatibilis lab-sa-report Podot lab-app-secret mounttal. Forgass a lab-app-secret értékét dummy-value helyett dummy-value-v2 értékre, és ellenőrizd, hogy a Pod a volume mountból az új értéket látja. Rögzítsd a rollback miatt az előző Secret YAML-t.

42.5.10.3 3. Diagnosztikai/failure/recovery feladat: egy deny és egy policyváltozás

Egy jelentkező hiba szerint a lab-token-test Pod nem éri el a lab-echo Service-t. Új hibaüzenet érkezik lab-extra-secret létrehozásánál is. Diagnosztizáld, hogy az első NetworkPolicy, a második ResourceQuota okból álljon elő. Javítsd a NetworkPolicy-t úgy, hogy a lab-token-test Pod access=allowed labelt kap, majd rollbackeld a labelt. A ResourceQuota esetén töröld a felesleges titkot vagy a quota hard limitet a gyakorlat szabályainak megfelelően. Rögzítsd a postconditiont és a cleanup parancsokat.

Postcondition: a mátrix mind a négy verbnél a Role szabályainak megfelel.

42.5.11.2 2. Megoldás

A namespace-t a kubectl label namespace ... paranccsal állítjuk be. A privileged Pod alkalmazása várhatóan admission deny, a restricted Pod lab-token-test várhatóan Running. Secret rotation előtt lab-app-secret-backup.yaml mentés kötelező. A rotation parancs:

kubectl -n lab-tenant create secret generic lab-app-secret \
  --from-literal=api_key="dummy-value-v2" \
  --dry-run=client -o yaml | kubectl apply -f -

A volume mount a Secret tartalmát aszinkron frissíti; a for loop legfeljebb 30×2 másodpercet vár. Ha a Pod environment változót használ, Pod-újraindítás szükséges. Postcondition: kubectl -n lab-tenant exec lab-token-test -- cat /etc/lab-secret/api_key értéke dummy-value-v2, és a backup visszaállítható a kubectl apply -f lab-app-secret-backup.yaml paranccsal.

42.5.11.3 3. Megoldás

A NetworkPolicy esetén a lab-echo-np Nem engedi be a lab-token-test Podot, mert nincs access: allowed label. A hiba: curl nem 200, hanem timeout vagy reset. A diagnosztika:

kubectl -n lab-tenant get networkpolicy lab-echo-np -o yaml
kubectl -n lab-tenant get pod lab-token-test --show-labels

A javítás a kubectl -n lab-tenant label pod lab-token-test access=allowed --overwrite, majd curl --max-time 5 http://lab-echo:8080/ várt 200. A rollback a kubectl -n lab-tenant label pod lab-token-test access- parancs.

A lab-extra-secret hiba az lab-quota miatt keletkezik, mert a secrets: "1" hard limitet a lab-app-secret már felhasználja. A javítás törölheti a lab-extra-secret létrehozási kísérletet, vagy emelheti a quota limitet a labor contract szerint. A legbiztonságosabb lab-megoldás a quota törlése:

kubectl -n lab-tenant delete resourcequota lab-quota

Postcondition: a NetworkPolicy esetében a lab-token-test label törlése után a curl ismét nem 200; a ResourceQuota törlése után a lab-extra-secret létrehozása csak akkor lehetséges, ha a labor szándékosan újra alkalmazza a quota-t. A cleanup: kubectl delete ns lab-tenant.

42.5.12 Lab cleanup és secret-free report

A labor végén a teljes lab-tenant namespace törlése a legegyszerűbb rollback:

# target: labctx, labadmin
kubectl delete namespace lab-tenant
rm -f -- lab-minimal-rbac.yaml lab-reject-pod.yaml lab-secret-reader.yaml \
  lab-token-pod.yaml lab-quota.yaml lab-echo-pod.yaml lab-app-secret-backup.yaml

A jelentés nem tartalmazhat valós vagy dummy Secret értéket, tokent vagy Bearer header töredéket:

grep -R -E '(dummy-value|api_key|Bearer [A-Za-z0-9._-]+|serviceaccount/[^ ]+token)' \
  lab-report/ || echo "secret-free"

Ha a grep talál, az értékeket [REDACTED] jelöléssel kell helyettesíteni, és a fájlokat újra ellenőrizni. A labor fixture-kben használt dummy-value nem éles credential, de a secret-free report így is azt tanítja, hogy az audit jelentés ne váljon credential-forrássá.

42.5.13 Rövid összefoglaló

A Kubernetes diagnosztikában a Forbidden jelenséget rétegek szerint kell szétválasztani: RBAC, admission, quota és NetworkPolicy. A kubectl auth can-i --as=... a ServiceAccount identityvel kérdez le authorizációs döntést, a Pod Security admission a privileged konténert utasítja el, a ResourceQuota a Secret-számot korlátozza, a NetworkPolicy pedig a Podok közötti ingress-t. A Secret rotation volumen esetén aszinkron, ezért a Podban loop-pal vagy rollout restertel ellenőrzik. A labor a scope-ot a lab-tenant namespace-re korlátozza, a rollbacket minden változásnál mentett manifestből végzi, és a jelentést secret-free állapotúnak kell zárni.

Továbbhasznált definíciók:

  • RBAC denial: API-authorizációs elutasítás HTTP 403 és authorization.k8s.io/decision: forbid audit-annotációval.
  • Admission denial: policy-webhook, Pod Security vagy ResourceQuota általi elutasítás, amely a kérés objektumát nem engedi tárolni.
  • Can-i matrix: identity/verb/resource szerinti authorizációs táblázat, amely desired/observed módon rögzíti az elfogadó és elutasító teszteket.
