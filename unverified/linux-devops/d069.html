14.4 Patch, kernelupdate és rebootterv

14.4.1 Motiváció

Egy szenior C++ fejlesztő a frissítést gyakran a forráskód, a build artifact és a release pipeline felől látja: újrafordítjuk a binárist, lefuttatjuk a teszteket, kiadjuk az új image-et. Egy Linux hoszton azonban a csomagfrissítés más művelet: a disztribúció repositoryjában lévő bináris csomagokat cseréljük, miközben a futó folyamatok, a natív shared libraryk, a kernel és a konfiguráció állapota megmarad. Ha ezt a patching folyamatot nem tervezzük meg, a szolgáltatásunk a frissítés után is a régi, sebezhető kódot futtathatja, vagy a restart/reboot rossz ütemezése leállást okozhat. A cél az, hogy a patchváltozást szolgáltatás és reboot szerint elemző, canary és rollback feltétellel ellenőrzött karbantartási folyamatot alakítsunk ki.

14.4.2 Definíció és működés

A patch itt nem általános szoftverjavítást, hanem egy adott disztribúciós csomag azonos verziószámú, de módosított kiadását jelenti. A security advisory a gyártó vagy a disztribúció által kiadott biztonsági értesítés, amely egy CVE-azonosítóhoz tartozó sebezhetőséget és a javító csomagot azonosítja. Az Ubuntu USN, a Debian DSA azonosítót használ. A distro backport azt jelenti, hogy a disztribúció a stabil kiadásban tartott régebbi upstream verzióhoz visszaportolja a hibajavítást, hogy a főverzió és az ABI ne változzon. Ez a szenior C++ fejlesztő számára azt jelenti, hogy például a libssl.so.3 soname változatlan marad, tehát a natív dependency-vel linkelt C++ programot nem kell újrafordítani a patch után. A futó processzek azonban a régi library inode-ot tartják mapelve, ezért a tényleges kódváltáshoz a folyamatot újra kell indítani.

A restart required fogalma két szintre bontható:

  1. Service restart: ha egy userspace shared library frissül, akkor a könyvtárat használó szolgáltatást újra kell indítani, hogy az új kódot töltse be. Az Ubuntu needrestart eszköze a processzekhez mapelt libraryk és a frissített csomagok összevetésével mutatja meg, melyik szolgáltatást kell újraindítani.
  2. Kernel reboot: ha a frissítés kernelcsomagot is érint, a futó kernel nem cserélhető le egyszerűen, ezért a hosztot újra kell indítani. A disztribúció a /var/run/reboot-required fájlban jelzi ezt, a /var/run/reboot-required.pkgs pedig a frissített kernelcsomagokat tartalmazza. A live patching csak kivételes esetben kerüli meg a rebootot, és korlátozott sebezhetőségi körre alkalmazható.

Az unattended update olyan automatikus frissítési mód, amely a biztonsági csomagokat a háttérben telepíti. Ez kényelmes, de nem garantálja, hogy a szolgáltatás restartja vagy a kernel reboot a megfelelő időben történik meg. A controlled update ezzel szemben ember vagy pipeline által vezérelt, jóváhagyott frissítés, amely canary hoston először fut, majd a fleetre terjesztjük. A canary host egy kiválasztott, reprezentatív vagy alacsonyabb kockázatú gép, amelyen a frissítést először hajtjuk végre, és a smoke test sikere után engedjük tovább.

A dependency diff a frissítés előtti csomaglista és a frissítés utáni lista összehasonlítása, hogy lássuk, pontosan mely native libraryk és szolgáltatások érintettek. A smoke test egy minimális, kritikus egészségellenőrzés, amely a szolgáltatás elindulását, portját vagy webválaszát vizsgálja. Az audit pedig a változtatás naplózását és a későbbi visszakereshetőséget jelenti.

A csomagfrissítés során a dpkg konfigurációs fájloknál három lehetőséget adhat: a régi config megtartása, az új bevezetése, vagy interaktív merge. A config merge fontos, mert egy frissítés felülírhatja a lokális finomhangolást. A package downgrade nem általános, triviális művelet: az apt-get install pkg=oldversion parancs visszaállíthatja a csomag binárisait, de ha a csomag adatbázis-sémát, config formátumot vagy adatfájl-struktúrát változtatott, a downgrade után a szolgáltatás még inkonzisztens lehet. Ezért a megbízható rollback a hostsnapshot vagy a virtuális gép snapshotja, nem pedig a csomag downgrade.

14.4.3 Kidolgozott példa

A példa egy izolált labhostot használ, lab-host-canary-1 néven. A hoston fut egy C++ szolgáltatás, lab-cpp-svc, amely a libssl3t64 natív libraryt használ, és a 8080-as porton figyel. A felhasználó labadmin (UID 1000), sudo joggal. A cél egy biztonsági backport telepítése, a szolgáltatás újraindítása, majd egy kernelcsomag frissítéséhez tartozó rebootterv végrehajtása. Az alábbi verziók illusztratívak, a labhoston ellenőrizendők.

Target Privilege Előfeltétel Ellenőrzés Rollback
lab-host-canary-1, UID labadmin sudo lab-cpp-svc aktív, snapshot készült systemctl is-active, port, kernel verzió virtuális gép snapshot vagy boot entry

A frissítés előtt áttekintjük a repository állapotát és a tervezett változást:

# lab-host-canary-1, labadmin, sudo
sudo apt update
apt list --upgradable
apt-get --dry-run upgrade
apt changelog libssl3t64 | head -n 30

A --dry-run megmutatja, hogy a libssl3t64 frissítésén kívül a linux-image-generic is frissül. A changelog a USN-xxxx-1 bejegyzést tartalmazza. A canary frissítést két lépésben végezzük: először a userspace libraryt, majd a kernelcsomagot.

# Userspace library frissítése
sudo apt-get install --only-upgrade libssl3t64

# Listázza a frissített libraryt használó futó processzeket
sudo needrestart -v

# C++ szolgáltatás újraindítása, mert a régi libssl maradt mapelve
sudo systemctl restart lab-cpp-svc

# Smoke test: aktív, port figyelve, nincs fatal a logban
systemctl is-active lab-cpp-svc
ss -ltn | grep ':8080'
journalctl -u lab-cpp-svc --since "5 minutes ago" --no-pager | grep -E 'fatal|error' || true

A needrestart -v kimenete azt mutatja, hogy a lab-cpp-svc process még a régi libssl.so.3 inode-ot használja. A restart után a smoke test sikeres. Ezután a kernelcsomag frissítése következik:

# Kernel frissítés
sudo apt-get install --only-upgrade linux-image-generic

# Reboot szükséges?
cat /var/run/reboot-required
cat /var/run/reboot-required.pkgs

# Reboot a canary hoston
sudo reboot

A /var/run/reboot-required fájl létezik, és a linux-image-5.15.0-xxx csomagot mutatja. A reboot után a canary host újra elérhető, és a smoke test ismételt:

# lab-host-canary-1, labadmin, sudo
uname -r
systemctl is-active lab-cpp-svc
ss -ltn | grep ':8080'

A uname -r a frissített kernelverziót adja, a szolgáltatás aktív. Ha bármelyik ellenőrzés sikertelen, a rollback a VMsnapshot visszaállítása, vagy a korábbi kernel boot entry kiválasztása a GRUB menüből. A csomag downgrade-et ebben a példában nem tekintjük elsődleges rollbacknek, mert a kernel és a userspace libraryk inkonzisztens kombinációját okozhatja.

14.4.4 Hibák és ellenpróbák

Tünet: a lab-cpp-svc a libssl3t64 frissítés után nem figyel a 8080-as porton, de a systemctl azt mutatja, hogy a unit aktív volt, majd exited.
Hipotézis: a szolgáltatás processze a frissítés előtt indult, és a frissített libraryt nem töltötte be; a unit nem rendelkezett automatikus restarttal a library update után.
Adatgyűjtés: systemctl status lab-cpp-svc, ss -ltnp | grep 8080, grep 'deleted' /proc/$(pgrep -f lab-cpp-svc)/maps. A maps fájlban a libssl.so.3 bejegyzés deleted jelzésű, ami a régi inode-ot mutatja.
Egy változtatás: sudo systemctl restart lab-cpp-svc.
Verifikáció: ss -ltn | grep ':8080' ismét megjelenik, és a journalctl -u lab-cpp-svc nem tartalmaz SIGSEGV vagy fatal hibát.

Tünet: a csomagfrissítés során a dpkg konfigurációs promptot dob fel, és a lab-cpp-svc.conf felülíródik az új gyári értékkel, elveszítve a testre szabott portot.
Hipotézis: a frissítés előtt nem mentettük a konfigurációt, és a dpkg alapértelmezett választása az új fájl bevezetése volt.
Adatgyűjtés: dpkg-query -W -f='${Conffiles}' lab-cpp-svc vagy a config backup hiányának ellenőrzése.
Egy változtatás: a konfigurációt a saját backupból visszaállítjuk, majd systemctl restart lab-cpp-svc.
Verifikáció: ss -ltn mutatja a saját portot, a szolgáltatás aktív.

Tünet: a kernelcsomag frissítése után a uname -r még mindig a régi kernelt mutatja, pedig a csomag települt.
Hipotézis: a szolgáltató elmulasztotta a rebootot, vagy a reboot a canary hoston nem történt meg.
Adatgyűjtés: cat /var/run/reboot-required, dpkg -l linux-image-* | grep '^ii', uname -r. A futó kernel és a telepített kernel eltér.
Egy változtatás: sudo reboot, majd újra ellenőrzés.
Verifikáció: a uname -r megegyezik a telepített linux-image-generic meta csomag célverziójával, és a /var/run/reboot-required törlődött.

A fenti hibák mutatják, hogy a patching nem fejeződik be a csomag telepítésével: a restart és a reboot elengedhetetlen, a konfigurációt külön kezelni kell, és a canary hoston elvégzett smoke test segít a hiba elszigetelésében a teljes flotta előtt.

14.4.5 Feladatok

  1. Magyarázó feladat: Adott egy Ubuntu biztonsági advisory, amely a linux-image-generic és a libssl3t64 csomagok frissítését írja elő. Magyarázza el, miért van szükség restartra a libssl esetén, és miért rebootra a kernel esetén. Miben más a distro backport hatása a C++ natív függőségre, mint egy upstream library soname váltás?

  2. Adminisztrációs feladat: A lab-host-canary-1 hoston hajtson végre egy ellenőrzött frissítést: ellenőrizze a repository listát, szimulálja a frissítést, telepítse a libssl3t64 csomagot, indítsa újra a lab-cpp-svc szolgáltatást, majd ha a /var/run/reboot-required megjelent, ellenőrizze a reboot utáni állapotot. A parancsokat a target, privilege, ellenőrzés és rollback megadásával dokumentálja.

  3. Diagnosztikai/failure feladat: A frissítés után a lab-cpp-svc nem indul el, és a journalban symbol lookup error: undefined symbol: ... hiba jelenik meg. Diagnosztizálja, hogy a szolgáltatás melyik libraryt próbálja betölteni, miért nem találja a szimbólumot, és hogyan javítja a hibát anélkül, hogy a csomagot downgrade-né. A megoldás tartalmazza a szükséges parancsokat és a postconditiont.

14.4.6 Megoldások

1. megoldás: A libssl3t64 userspace library, ezért a futó folyamatok a process indulásakor mapelik be a .so fájlt. A library frissítése új inode-ot hoz létre, de a régi folyamat továbbra is a régi inode-ot használja; a restart szükséges az új kód betöltéséhez. A kernel esetében a futó kernel image nem cserélhető le csak processzrestarttal, mert a kernel maga a futó rendszer, tehát reboot kell. A distro backport az adott stabil kiadáson belül megtartja a soname-et, így a C++ programot nem kell újrafordítani, csak a folyamatot újraindítani. Az upstream soname váltás ezzel szemben libssl.so.4 típusú új major verziót jelent, ami ABI törést okoz, és a C++ binárist újra kell linkelni.

2. megoldás: A parancsok a lab-host-canary-1 hoston, labadmin UID, sudo joggal:

# Target: lab-host-canary-1, UID labadmin, sudo
sudo apt update
apt list --upgradable
apt-get --dry-run upgrade
sudo apt-get install --only-upgrade libssl3t64
sudo needrestart -v
sudo systemctl restart lab-cpp-svc
systemctl is-active lab-cpp-svc
ss -ltn | grep ':8080'
cat /var/run/reboot-required

Ha a /var/run/reboot-required létezik:

sudo reboot
# Reboot után
uname -r
systemctl is-active lab-cpp-svc
ss -ltn | grep ':8080'

Postcondition: a libssl3t64 frissített verzióban telepített, a lab-cpp-svc aktív és a 8080-as portot figyeli, a futó kernel megegyezik a frissített linux-image-generic célverzióval. Az ellenőrzés: a fenti parancsok kimenete, a frissítés előtti állapothoz képest. Rollback: virtuális gépsnapshot visszaállítás.

3. megoldás: A symbol lookup error azt jelenti, hogy a process egy régebbi vagy inkompatibilis libssl.so.3-at talál, vagy a frissítés után a library symbol verziója megváltozott. Diagnosztika:

# lab-host-canary-1, labadmin, sudo
journalctl -u lab-cpp-svc -b --no-pager | grep -E 'symbol lookup error|undefined symbol'
ldd /usr/local/bin/lab-cpp-svc | grep ssl
readelf -Ws /usr/lib/x86_64-linux-gnu/libssl.so.3 | grep '<keresett_symbol>'
grep 'libssl' /proc/$(pgrep -f lab-cpp-svc)/maps

Ha a maps mutatja, hogy a folyamat a régi, deleted inode-ot használja, a javítás a szolgáltatás újraindítása. Ha a ldd a frissített libraryt mutatja, de a szimbólum hiányzik, akkor a library verzió nem egyezik a bináris által igényelttel; ebben az esetben a csomag downgrade nem biztonságos, hanem a C++ binárist kell újrafordítani a megfelelő library fejlesztőcsomaggal, vagy a rendszer library pathból ki kell zárni a sérült kópiát. Postcondition: systemctl is-active lab-cpp-svc aktív, a port figyel, a journalctl nem tartalmaz symbol lookup error bejegyzést.

14.4.7 Rövid összefoglaló

A patching folyamat ellenőrizhető módja a frissítés előtti repository-diffből, a canary hoston történő telepítésből, a restart/reboot végrehajtásából és a smoke testből áll. A disztribúciós backport a stabil kiadáson belül megőrzi az ABI-t, ezért a natív C++ binárist általában nem kell újraépíteni, de a futó processzeket újra kell indítani. A kernel frissítése rebootot igényel, amit a disztribúció a reboot-required fájlban jelez. A csomag downgrade nem helyettesíti a snapshot-alapú rollbacket, mert a config és adat formátum nem mindig visszafelé kompatibilis.

  • Distro backport: a stabil kiadás régebbi upstream verziójához visszaportolt javítás, amely lehetőleg megőrzi az ABI-kompatibilitást.
  • Canary host: kiválasztott gép, amelyen a frissítést először hajtják végre, és a smoke test után terjesztik tovább a fleetre.
  • Restart required: a frissített libraryt használó futó folyamatok újraindításának szükségessége; kernel esetén reboot formájában.
