28.5 DNS/DHCP/idő diagnosztikai labor

28.5.1 Miért kell együtt vizsgálni a nevet, címet és időt?

A „nem érhető el a szolgáltatás” tünet mögött eltérő hibák állhatnak: rossz DNS-cél, megmaradt negatív gyorsítótár, hibás DHCP-opció vagy a hitelesítést megtörő óraeltérés. A szolgáltatások újraindítása önmagában nem bizonyítja, hogy ezek közül melyik javult meg.

Az infrastruktúra-diagnosztika itt az alkalmazási igényt kiszolgáló név-, cím- és időfüggőségek bizonyítékalapú elkülönítését jelenti. A füstteszt (smoke test) rövid, megismételhető ellenőrzés, amely megmutatja, hogy a szükséges alapfunkciók működnek-e; teljes helyességet nem bizonyít.

A labor a Működtetési szerződés, runbook és változtatás változtatási rendjét alkalmazza. Az idővizsgálat a NTP, chrony, PTP és clock hibák fogalmaira épül. Az alábbi kimenetek és fixture-adatok vártak vagy illusztratívak; tényleges futtatás nem történt.

28.5.2 Laborszerződés és topológia

Három Ubuntu Server 24.04 LTS amd64 VM szükséges. Kizárólag konzolról dolgozz; a teszthálózatnak nincs fizikai uplinkje, NAT-ja vagy más DHCP-szervere.

VM Interfész, MAC IPv4-cím Szerep
lab-infra ens3 10.77.28.1/24, statikus BIND DNS, dnsmasq DHCP
lab-a ens3, 52:54:00:28:00:0a DHCP: 10.77.28.10/24 Kontrollkliens
lab-b ens3, 52:54:00:28:00:0b DHCP: 10.77.28.11/24 Hibainjektálási kliens
lab-infra lo 192.0.2.80/32 Helyi HTTP-tesztvégpont

A 192.0.2.80 dokumentációs címet kizárólag ebben az izolált laborban használjuk. A kliensek számára alhálózaton kívüli cél, ezért eléréséhez a DHCP-ből kapott átjáró kell. A csomag a lab-infra helyi címére érkezik: IP-forwarding bekapcsolása nem szükséges.

Forrás → cél Adatút Ellenőrzött függőség
Kliens → 10.77.28.1:53 Közvetlen Ethernet, UDP/TCP DNS, átjáró nélkül
Kliens UDP 68 ↔︎ szerver UDP 67 Broadcast, illetve unicast DHCP
Kliens → 192.0.2.80:8080 Következő ugrás: 10.77.28.1 Útvonal és HTTP
lab-b ↔︎ lab-infra Offline idő-fixture Óraeltérés és korreláció

Indítási kapuk:

  • A virtuális switch valóban izolált; a címek és MAC-címek nem ütköznek.
  • Az ens3 kezdetben cím nélküli, nincs rá Netplan- vagy más tartós hálózatkezelő-konfiguráció. A klienseken a futó systemd-networkd lesz az egyetlen tulajdonos.
  • A klienseken fut a systemd-resolved; az /etc/resolv.conf a /run/systemd/resolve/stub-resolv.conf fájlra mutat.
  • Előre telepített eszközök: iproute2, tcpdump, dnsutils, curl; az infrastruktúragépen bind9, dnsmasq, python3.
  • A csomagok alapértelmezett DNS/DHCP-példányai nem futnak. A szükséges portokat célzott szabályok engedik; ne kapcsold ki globálisan a tűzfalat vagy az AppArmort.

Mindhárom gépen rögzítsd a tényleges verziókat:

# Cél: lab-infra, lab-a és lab-b; UID=0, külön-külön
hostname
uname -r
systemd --version
dpkg-query -W -f='${binary:Package}\t${Version}\n'
ip -br link
ip -br address
ip route

A csomagkiadások nincsenek megadva az inputban: a verziójegyzék és a VM-image azonosítója nélkül a laborprofil még nem reprodukálhatóan rögzített. A tulajdonos a laborozó, a lejárat a gyakorlat vége; felhős erőforrás nem szükséges.

28.5.3 Kidolgozott példa: elkülönített infrastruktúraszolgáltatások

Minden következő módosítás konzolról, rootként történik. Újrafuttatás előtt ellenőrizd az állapotot: az alábbi felépítés nem általánosan idempotens telepítő.

28.5.3.1 DNS és HTTP

# Cél: lab-infra; UID=0
umask 022
ip link set ens3 up
ip address add 10.77.28.1/24 dev ens3
ip address add 192.0.2.80/32 dev lo

cat > /etc/bind/lab-d140.conf <<'EOF'
options {
    directory "/var/cache/bind";
    pid-file "/var/cache/bind/lab-d140.pid";
    session-keyfile "/var/cache/bind/lab-d140.key";
    listen-on { 10.77.28.1; };
    listen-on-v6 { none; };
    recursion no;
    allow-query { 10.77.28.0/24; localhost; };
    allow-transfer { none; };
};
controls {};
logging {
    category queries { default_stderr; };
};
zone "lab.test" {
    type primary;
    file "/etc/bind/lab-d140.zone";
};
EOF

cat > /etc/bind/lab-d140.zone <<'EOF'
$ORIGIN lab.test.
$TTL 60
@ IN SOA lab-ns.lab.test. hostmaster.lab.test. (
    100 300 60 3600 60
)
@       IN NS lab-ns.lab.test.
lab-ns  IN A 10.77.28.1
lab-web IN A 192.0.2.80
EOF

named-checkconf -z /etc/bind/lab-d140.conf

Csak sikeres ellenőrzés után indítsd a szolgáltatásokat:

# Cél: lab-infra; UID=0
systemd-run --unit=lab-d140-dns --collect \
  /usr/sbin/named -g -u bind -c /etc/bind/lab-d140.conf

install -d -m 0755 /var/lib/lab-d140
printf 'lab-ok\n' > /var/lib/lab-d140/index.html

systemd-run --unit=lab-d140-http --collect --uid=nobody \
  --property=WorkingDirectory=/var/lib/lab-d140 \
  /usr/bin/python3 -m http.server 8080 --bind 192.0.2.80

Ez csak a lab.test zóna autoritatív DNS-kiszolgálója, nem internetes rekurzív resolver. Az IPv4-re korlátozás tudatos laborprofil, nem IPv6-hibák javítási receptje. A HTTP-kiszolgáló kizárólag tesztcél.

28.5.3.2 DHCP és klienskonfiguráció

# Cél: lab-infra; UID=0
cat > /etc/dnsmasq.d/lab-d140.conf <<'EOF'
port=0
interface=ens3
bind-interfaces
dhcp-authoritative
dhcp-range=10.77.28.100,10.77.28.119,255.255.255.0,10m
dhcp-host=52:54:00:28:00:0a,set:lab-a,10.77.28.10
dhcp-host=52:54:00:28:00:0b,set:lab-b,10.77.28.11
dhcp-option=option:router,10.77.28.1
dhcp-option=tag:lab-b,option:router,10.77.28.1
dhcp-option=option:dns-server,10.77.28.1
dhcp-leasefile=/var/lib/misc/lab-d140.leases
log-dhcp
log-facility=-
EOF

dnsmasq --test --conf-file=/etc/dnsmasq.d/lab-d140.conf

Sikeres szintaxisellenőrzés után:

# Cél: lab-infra; UID=0
systemd-run --unit=lab-d140-dhcp --collect \
  /usr/sbin/dnsmasq --keep-in-foreground \
  --conf-file=/etc/dnsmasq.d/lab-d140.conf

A port=0 kikapcsolja e példány DNS-funkcióját. A BIND és a dnsmasq így nem versenyez az 53-as portért.

# Cél: lab-a és lab-b; UID=0, külön-külön
cat > /run/systemd/network/lab-d140.network <<'EOF'
[Match]
Name=ens3

[Network]
DHCP=ipv4
IPv6AcceptRA=no
LinkLocalAddressing=no
Domains=~lab.test

[DHCPv4]
UseDNS=yes
UseRoutes=yes
UseDomains=no
EOF

networkctl reload
networkctl reconfigure ens3
networkctl status ens3
resolvectl status ens3

A ~lab.test útválasztási tartomány: a zóna lekérdezéseit az ehhez a linkhez rendelt DNS-szerver felé irányítja, nem keresési utótag.

28.5.4 Állapotmodell és füsttesztek

Állapotfajta Példa
Kívánt állapot Mindkét kliens DNS-e és átjárója 10.77.28.1
Konfigurációforrás DNS-zóna, dnsmasq-konfiguráció, .network fájl
Tárolt állapot DHCP-lease-fájl; a resolver memóriabeli gyorsítótára
Megfigyelt állapot Kernelútvonal, resolvercél, DNS-válasz, HTTP-eredmény

A konfiguráció átírása nem jelenti automatikusan a kliensállapot megváltozását.

# Cél: lab-a és lab-b; UID=0, külön-külön
ip -4 address show dev ens3
ip route get 192.0.2.80
resolvectl status ens3
dig @10.77.28.1 lab-web.lab.test A +noall +answer
getent ahostsv4 lab-web.lab.test
curl --noproxy '*' --connect-timeout 2 --max-time 4 \
  http://lab-web.lab.test:8080/

Várt postcondition:

  • a kliens a saját fenntartott címét használja;
  • az útvonal via 10.77.28.1 dev ens3;
  • a közvetlen DNS-lekérdezés és a rendszer névfeloldása is 192.0.2.80 címet ad;
  • a HTTP-válasz lab-ok.

A közvetlen dig megkerüli a helyi resolver célválasztását és gyorsítótárát. Ezért önmagában nem helyettesíti a getent és az alkalmazási teszt eredményét.

28.5.5 Hibainjektálás: helyes cím, rossz átjáró

A lab-b DHCP-opcióját változtatjuk meg; lab-a kontroll marad.

# Cél: lab-infra; UID=0
cp /etc/dnsmasq.d/lab-d140.conf /etc/dnsmasq.d/lab-d140.good

sed -i \
  's/^dhcp-option=tag:lab-b,option:router,.*/dhcp-option=tag:lab-b,option:router,10.77.28.254/' \
  /etc/dnsmasq.d/lab-d140.conf

dnsmasq --test --conf-file=/etc/dnsmasq.d/lab-d140.conf

A szintaxisellenőrzés várhatóan sikeres: nem bizonyítja az átjáró létezését. Utána:

# Cél: lab-infra; UID=0
systemctl restart lab-d140-dhcp
# Cél: lab-b; UID=0
networkctl renew ens3

Várd meg a DHCP-választ; a megújítás nem feltétlenül fejeződik be a parancs visszatéréséig. Ismételd a füstteszteket.

Várt hibakép: a DNS működik, a HTTP időtúllépéssel hibázik. Az ip route get 192.0.2.80 a .254 címet mutatja; az ip neigh show dev ens3 ott INCOMPLETE vagy később FAILED állapotot jelezhet. A lab-a változatlanul működik.

Ez az ellenpróba a DNS-hibát és a teljes infrastruktúragép-kiesést gyengíti, a hibás DHCP-útvonal hipotézisét erősíti.

Rollback:

# Cél: lab-infra; UID=0
cp /etc/dnsmasq.d/lab-d140.good /etc/dnsmasq.d/lab-d140.conf
dnsmasq --test --conf-file=/etc/dnsmasq.d/lab-d140.conf

Sikeres ellenőrzés után:

# Cél: lab-infra; UID=0
systemctl restart lab-d140-dhcp
# Cél: lab-b; UID=0
networkctl renew ens3

A rollback csak akkor teljes, ha a kliensútvonal ismét .1 felé mutat, és a névvel végzett HTTP-teszt sikeres. A szerverkonfiguráció visszamásolása önmagában kevés.

28.5.6 Negatív DNS-cache és serial: külön állapotok

A negatív gyorsítótár (negative cache) nemlétező névre vagy rekordtípusra kapott választ tárol. Az NXDOMAIN nem azonos az időtúllépéssel: az előbbi DNS-válasz, az utóbbi válaszhiány.

A kezdeti zónából hiányzik a lab-new.lab.test. Kérdezd le a kliens resolverén keresztül:

# Cél: lab-b; UID=0
dig @127.0.0.53 lab-new.lab.test A +noall +comments +authority

A negatív TTL alapja a SOA rekord TTL-jének és SOA MINIMUM mezőjének kisebbike; itt mindkettő 60 s. A resolver saját korlátai ezt tovább módosíthatják.

Illusztratív fixture, nem mért idősor:

Relatív idő Autoritatív állapot Kliensállapot
0 s Serial 100, a név hiányzik NXDOMAIN eltárolva
5 s Serial 101, az új A rekord már létezik Még lehet gyorsítótárazott NXDOMAIN
61 s Serial 101 Új lekérdezés már pozitív választ kaphat

A zónasorszám, azaz SOA serial a zónaverziót jelzi, különösen a másodlagos szerverek számára. Növelése nem küld cache-invalidation üzenetet a klienseknek.

Első lépésként ne üríts cache-t: hasonlítsd össze a közvetlen autoritatív és a helyi resolverválaszt. Csak az evidencia rögzítése után használj célzott laborbeavatkozást:

# Cél: lab-b; UID=0
resolvectl flush-caches

Ez a teljes helyi resolved-cache-t üríti, nem csak egy rekordot.

28.5.7 Óraeltérés és napló–lekérdezés–capture korreláció

A vendégórát nem állítjuk el. Az alábbi jelölt offline fixture egy lab-b gépen 120 s-mal siető órát modellez.

Bizonyíték Fixture-adat
lab-b csomagfelvétel 12:02:05.000, DNS-kérés
lab-infra csomagfelvétel 12:00:05.002, ugyanaz a kérés
Azonosító UDP 10.77.28.11:54123 → 10.77.28.1:53, DNS ID 0x4a21
Feltételezett referencia lab-infra órája
Modell szerinti eltérés lab-b: +120 s

A nyers időbélyegek különbsége nem hálózati késleltetés. A monoton időbélyeg sem hasonlítható közvetlenül külön gépek között. A fixture relatív óraeltérést modellez, nem bizonyítja a referencia UTC-helyességét.

A valódi adatgyűjtéshez, külön konzolon:

# Cél: lab-infra; UID=0; leállítás: Ctrl-C
tcpdump -ni ens3 -s 0 -vvv \
  '(port 53 or udp port 67 or udp port 68 or tcp port 8080)'
# Cél: lab-infra; UID=0
journalctl -b -u lab-d140-dns -u lab-d140-dhcp \
  -n 80 -o short-iso-precise
cat /var/lib/misc/lab-d140.leases

Korrelációs kulcsok:

  • DNS: klienscím, forrásport, kérdés és típus; a capture-ben tranzakcióazonosító is.
  • DHCP: MAC/client identifier és tranzakcióazonosító; figyeld az ACK-ban átadott opciókat.
  • Idő: referencia, eltérés, bizonytalanság és órakorrekció. A journal short-monotonic formátuma ugyanazon boot eseménysorrendjének vizsgálatára használható.

A HTTP-teszt sikere nem zárja ki az időhibát: ebben a laborban nincs TLS- vagy tokenérvényességi ellenőrzés. A DNS, DHCP és tesztalkalmazás közös hostja tudatos közös hibadomén; a kontrollkliens ezt nem szünteti meg.

28.5.8 Feladatok

  1. Magyarázó: miért működik a DNS rossz átjáró mellett? Miért nem bizonyít resolverhelyességet a közvetlen dig?
  2. Konfigurációs: hozd létre a lab-new.lab.test rekordot serialnöveléssel. Mutasd ki a közvetlen és gyorsítótárazott válasz különbségét, majd állítsd vissza a zónát.
  3. Diagnosztikai és recovery: állítsd elő a hibás DHCP-átjárót. Rögzíts hipotézist, bizonyítékot, egy javítást és postconditiont. Magyarázd meg az idő-fixture látszólag fordított eseménysorrendjét.

28.5.9 Megoldások

1. A DNS-szerver közvetlenül kapcsolódó alhálózatban van, eléréséhez nincs szükség az alapértelmezett átjáróra. A HTTP-célhoz viszont kell. A közvetlen dig nem vizsgálja az alkalmazás által használt resolverutat.

Postcondition: a magyarázat külön azonosítja a célcímet, következő ugrást és resolverréteget.

2. Először kérdezd le a még hiányzó nevet lab-b helyi resolverén át, majd:

# Cél: lab-infra; UID=0
cp /etc/bind/lab-d140.zone /etc/bind/lab-d140.zone.good
sed -i 's/100 300 60 3600 60/101 300 60 3600 60/' \
  /etc/bind/lab-d140.zone
printf '\nlab-new IN A 192.0.2.80\n' >> /etc/bind/lab-d140.zone
named-checkzone lab.test /etc/bind/lab-d140.zone

Sikeres ellenőrzés után indítsd újra csak a labor DNS-példányát:

# Cél: lab-infra; UID=0
systemctl restart lab-d140-dns
# Cél: lab-b; UID=0
dig @10.77.28.1 lab-new.lab.test A
dig @127.0.0.53 lab-new.lab.test A

Ha közben lejárt a negatív TTL, az eltérés már nem látszik; ez nem hiba. Visszaállításkor a régi tartalmat új seriallal publikáld:

# Cél: lab-infra; UID=0
cp /etc/bind/lab-d140.zone.good /etc/bind/lab-d140.zone
sed -i 's/100 300 60 3600 60/102 300 60 3600 60/' \
  /etc/bind/lab-d140.zone
named-checkzone lab.test /etc/bind/lab-d140.zone

Sikeres validálás után ismét systemctl restart lab-d140-dns. Postcondition: közvetlen lekérdezéssel serial 102 és az új névre NXDOMAIN; a kliens a korábbi pozitív választ még annak TTL-jéig tarthatja.

3. A döntő bizonyíték az ACK routeropciója, a kliens tényleges útvonala és a sikertelen szomszédfelderítés együtt. A javítás a hibás opció visszaállítása, majd lease-megújítás. Postcondition: mindkét kliensen sikeres, névvel végzett HTTP-teszt. Az idő-fixture eseményeit csomagazonosság kapcsolja össze; a különböző órák nyers időbélyegeiből nem számítható RTT.

28.5.10 Lezárás és cleanup

Előbb exportáld a verziójegyzéket, konfigurációkat és eredményeket. A runbook minimuma: target, tünet, hipotézis, ellenpróba, változtatás, rollback és alkalmazási postcondition.

# Cél: lab-a és lab-b; UID=0, külön-külön
networkctl down ens3
rm /run/systemd/network/lab-d140.network
networkctl reload
resolvectl revert ens3
ip -4 address show dev ens3
ip route

Ellenőrizd, hogy a labor DHCP-címe és útvonala eltűnt. A linket ne konfiguráld újra más tulajdonossal.

# Cél: lab-infra; UID=0
systemctl stop lab-d140-http lab-d140-dhcp lab-d140-dns
ip address del 192.0.2.80/32 dev lo
ip address del 10.77.28.1/24 dev ens3
ip link set ens3 down

rm -f /etc/bind/lab-d140.conf \
  /etc/bind/lab-d140.zone /etc/bind/lab-d140.zone.good \
  /etc/dnsmasq.d/lab-d140.conf /etc/dnsmasq.d/lab-d140.good \
  /var/lib/misc/lab-d140.leases \
  /var/cache/bind/lab-d140.pid /var/cache/bind/lab-d140.key \
  /var/lib/lab-d140/index.html
rmdir /var/lib/lab-d140

A törlés csak felsorolt laborobjektumokra terjed ki; a journal megmarad. MAC-tiltás vagy portütközés esetén annak konkrét okát vizsgáld, ne védelmet kapcsolj ki.

28.5.11 Rövid összefoglaló

A név-, cím- és időhibák közös alkalmazási tünetet okozhatnak, de eltérő állapotrétegekben élnek. A közvetlen DNS-lekérdezés, a rendszerresolver, a DHCP-válasz és a kernelútvonal külön bizonyíték. A kontrollkliens segít elkülöníteni a kliensspecifikus hibát a közös infrastruktúra kiesésétől. Óraeltérés mellett az eseményeket protokollazonosítókkal kapcsoljuk össze, nem pusztán időbélyeg alapján. A rollback akkor kész, amikor a kliens megfigyelt állapota és az alkalmazási teszt is helyes. Az infrastruktúra közös hostja továbbra is közös hibadomén.

  • Negatív cache: nemlétezést jelző DNS-válasz időkorlátos tárolása.
  • SOA serial: DNS-zónaverzió, nem klienscache-ürítési utasítás.
  • Postcondition: a változtatás után bizonyítandó, megfigyelhető állapot.

28.5.12 Források és ellenőrzési hiányok

Nem történt webes forrásolvasás vagy laborfuttatás. Ellenőrzési kiindulópontok:

  • BIND 9 dokumentáció — a telepített kiadás konfigurációja és naplózása.
  • dnsmasq kézikönyv — címfoglalás, tagek, DHCP-opciók.
  • RFC 2308 – Negative Caching of DNS Queries — különösen a negatív válaszok TTL-kezelése.
  • RFC 2131 – Dynamic Host Configuration Protocol — lease és kliensállapotok.
  • chrony dokumentáció — referencia- és óraállapot értelmezése.

Nyitott ellenőrzés: a pontos Ubuntu-csomagkiadások, helyi AppArmor-szabályok, resolved-cache-viselkedés és szolgáltatásindítás. Az RFC-k státuszát, frissítéseit és hibajegyzékét külön ellenőrizni kell. A pontos helyi viselkedéshez a telepített systemd.network, resolvectl, named és dnsmasq kézikönyvek az elsődleges verzióillesztett támpontok.
