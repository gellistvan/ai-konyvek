58.2 Linux admin parancs- és állapotindex

58.2.1 Motiváció

Egy szenior C++ fejlesztő számára a parancsok önmagukban még nem adnak diagnosztikai képességet. A fontos az, hogy adott üzemeltetési kérdésnél a megfelelő rétegben, a megfelelő adatforrásból, a legkisebb jogosultsággal gyűjtsön bizonyítékot, vagy szándékos módosításkor meg tudja mondani: mi a célpont, mi a preconditio, és hogyan áll vissza az előző állapot. Ez a fejezet nem parancs-cheat sheet, hanem visszakereső index: diagnosztikai kérdés → parancs → adatforrás → cél/scope → mutáció esetén recovery.

58.2.2 Definíció és működés

Linux admin parancs- és állapotindex egy olyan kategorizált, réteghez kötött keresőállomány, amely egy parancshoz a következőket rendeli: cél, tipikus üzemmód (read-only vagy scoped mutation), szükséges jogosultság és mögöttes állapotforrás (/proc, /sys, Netlink, SA, journal, CI platform). A read-only parancs nem módosít rendszerállapotot, csak olvas; a scoped mutation nevesített targetre korlátozódik, előfeltétellel és rollbackkel. A parancs kimenete soha nem „igaz”, hanem verzió- és rendszerállapot-függő megfigyelés, ezért a forrás és a hipotézis rögzítendő.

58.2.3 Parancsindex kategóriák szerint

58.2.3.1 CPU, memória, process, IO, syscall

  • Read-only: lscpu, nproc, uptime, ps -eo, pidstat, top, htop, mpstat, vmstat, free -h, iostat -x, iotop, perf stat, strace -c, ltrace -c.
  • Elsődleges adatforrások: /proc/cpuinfo, /proc/stat, /proc/meminfo, /proc/loadavg, /proc/pressure/*, /proc/<pid>/stat, /proc/<pid>/io, /proc/diskstats.
  • Célok: CPU telítettség, futó szál, page fault, IOPS, syscall arány.
  • Példa: ps -o pid,tid,user,comm,pcpu,pmem,args -C app; pidstat -d 1 5.

58.2.3.2 Eszköz, fájlrendszer, mount, backup

  • Read-only: lsblk -o NAME,SIZE,MODEL,SERIAL,MOUNTPOINTS, blkid, df -hT, du -xhd1, findmnt, mount -l, fdisk -l, lvs, mdadm --detail, btrfs filesystem show, zpool status, restic snapshots.
  • Mutáló, targeted: lvcreate, lvresize, mkfs.*, mount, umount, mdadm --manage, btrfs subvolume create, restic backup.
  • Célok: blokk device kiadás, mount összefüggés, backup RPO/RTO, degraded állapot.
  • Minden formázás/delete előtt SERIAL szerint kijelölt disposable labdisk szükséges.

58.2.3.3 Identitás, SSH, MAC, service, log

  • Read-only: id, getent passwd, getent group, sudo -l -U user, systemctl status, journalctl -u, ausearch --start today --message AVC, aa-status, sestatus, ss -lntp.
  • Mutáló: systemctl start/stop/restart, useradd, usermod, passwd, sudo /usr/sbin/visudo, aa-enforce, restorecon (RHEL család).
  • Adatforrások: /etc/passwd, /etc/group, /etc/sudoers, /etc/pam.d, /etc/ssh/sshd_config, /etc/audit/auditd.conf, journald binary logok.

58.2.3.4 Hálózat: ip, ss, dig, tcpdump, nft, tc

  • Read-only: ip -br address, ip route get 192.0.2.1 from 198.51.100.2 iif eth0, ip neigh show, ip -s link, ss -s, ss -lntup, dig +short example.com A, resolvectl status, tcpdump -n -i eth0 tcp port 443, nft list ruleset, tc -s qdisc show dev eth0.
  • Mutáló: ip address add/del, ip route add/delete, ip link set dev, ss nincs mutáció, nft add/delete rule, tc qdisc add/change/delete.
  • Adatforrás: Netlink a kernelbe, kivéve dig UDP/TCP a resolvernek, tcpdump raw socketet.

58.2.3.5 VM, konténer, kubectl, IaC, configmgmt

  • Read-only: virsh list --all, virsh domblklist, docker ps -a, podman ps -a, ctr -n k8s.io containers list, kubectl get events --sort-by=.metadata.creationTimestamp, kubectl describe node, kubectl top node, tofu show, terraform show, ansible-playbook --check --diff, helm list, argocd app list.
  • Mutáló: virsh start/destroy, docker run/stop, kubectl apply --namespace, tofu apply -target, ansible-playbook --limit, helm upgrade, argocd app sync.
  • A kubectl mindig explicit context/cluster/namespace mellett; a cloud profile/account/region mellette.

58.2.4 Read-only versus scoped mutation jelölések

Parancs Tipikus mód Cél/scope Jogosultság Fő adatforrás
ps -eo read-only process lista user /proc/<pid>
iostat -x read-only block device user /proc/diskstats
journalctl -u read-only unit log adm/systemd-journal journal file
systemctl restart app-cxx scoped mutation unit root/sudo systemd/unit
ip address add 192.0.2.2/24 dev eth0 scoped mutation interface/cím root Netlink
nft add rule inet filter input tcp dport 22 accept scoped mutation rule table/chain root nftables
kubectl apply -n lab -f job.yaml scoped mutation namespace/object RBAC API server
ansible-playbook -l lab-vm-01 site.yml scoped mutation inventory host SSH user target host
mkfs.ext4 /dev/disk/by-id/... destructive scoped serial által kijelölt labdisk root VFS/device

A read-only ne keverje a --check vagy show jellegű művelettel a tényleges mutációt. Pl. ansible-playbook --check nem garantál, hogy minden modul pontos diffet adott; terraform show nem futtat provider mutációt.

58.2.5 Módosító művelet kerete

Egy szándékos mutációnak legyen kitölthető kerete:

  1. Cél: például unit=lab-uploader.service, interface=eth0, table=inet filter, ns=lab.
  2. Precondition: a jelenlegi állapot és a terv ellenőrzése read-only módon, backup/artifact mentés.
  3. Mutáció: egy darab, minimális targetű parancs.
  4. Verification: a desired és observed state összehasonlítása, nemcsak exit code.
  5. Rollback: az előző állapothoz tartozó parancs vagy artifact-recovery.

A pre/post állapotot címkézni kell; a rollback nem szinonimája a „majd megoldjuk”.

58.2.6 Kidolgozott példa

Kiindulás: egy C++ szolgáltatás által használt lab-vm-01 diszkje hirtelen nagy IOPS-t mutat; a kérdés: ki ír, és hogyan állítjuk le célzottan, dokumentálva a visszaállítást. A labhost lab-vm-01, account labops, a lab hangulatjelben a service csak lab.

# labhost=lab-vm-01, uid=labops, device=/dev/vdb (serial=LABDISK01)
# 1. read-only: terhelés azonosítása
iostat -xz 1 3 /dev/vdb

# várt: %util magas, w_await megnő, r/s alacsony
# 2. read-only: ki ír?
pidstat -d 1 5

# várt: PID 401, kB_wr/s magas
# 3. read-only: folyamat azonosítás
ps -o pid,user,comm,args -p 401
cat /proc/401/io

# várt: /usr/bin/lab-uploader, write_bytes növekszik
# 4. precondició: unit konfiguráció mentése
systemctl cat lab-uploader.service > /var/tmp/lab-uploader.unit.$(date +%F).backup

# 5. scoped mutation: cél lab-uploader.service
systemctl stop lab-uploader.service

# 6. verification: terhelés visszaesik
iostat -xz 1 3 /dev/vdb

# 7. rollback, ha rossz döntés volt:
systemctl start lab-uploader.service

A cél a lab-uploader.service, a mutáció egy darab stop, a rollback az elmentett unit és start. A stop nem töröl és nem formáz; a labor cleanup ettől függetlenül csak a labdiskre terjedhet.

58.2.7 Tipikus hibák és ellenpróbák

  • kill -9 azonnal, előzetes SIGTERM és journal nélkül. A processz és a hozzá tartozó state recovery nélkül áll le; először systemctl stop vagy kill -TERM.
  • sudo minden read-only parancs elé: sok parancs user joggal is lát systemd-t, csak a részletes process- vagy netstat -p kér jogosultságot; minimalizáld a privilege tért.
  • ip address add elveszik reboot után, ha nincs persistens beállítás; a hálózati state két domain: runtime és config-source.
  • nft list ruleset vs. iptables -L: régi parancs mögött más tábla lehet, különböző adatforrásból dolgozhatsz. Ellentmondás esetén a iptables-nft kontra nft list ruleset kompatibilitásáról a dokumentációt nézd.
  • kubectl apply context nélkül: a local fájl a current-context miatt rossz clusterbe kerülhet; explicit context/namespace mindig.
  • Az ansible-playbook --check nem minden modulnál mutat valós diffet; szükséges a --diff és éles előtt staging inventory.
  • tcpdump -i any nem minden kernel/kaperon konfigurációban viselkedik azonosan; célzott interface jobb a packet pathhoz.

58.2.8 Feladatok

  1. Magyarázó: Válaszd szét a következő parancsokat read-only és scoped mutation kategóriára, indokold az adatforrást: ss -lntup, ip addr add 192.0.2.10/24 dev eth0, journalctl -u postfix, kubectl apply -n lab -f pod.yaml, iostat -x /dev/vdb.
  2. Adminisztrációs/konfigurációs: Állíts le egy lab-batch.service nevű, CPU-t fogyasztó rendszerszolgáltatást a fenti minta alapján, add meg target, precondition, mutáció, verification, rollback.
  3. Diagnosztikai/failure/recovery: Egy C++ szolgáltatás nem tud bindolni a 0.0.0.0:8443 portra. Keresd meg a hibát, azonosítsd a ütköző processzt, és ha a lab service a hibás, állítsd le célzottan, mérd, hogy a port felszabadult.

58.2.9 Megoldások

  1. ss -lntup read-only, Netlink socket adat; journalctl -u postfix read-only, journal adat; iostat -x /dev/vdb read-only, /proc/diskstats. ip addr add és kubectl apply -n lab -f pod.yaml scoped mutation, target: interface, ill. namespace/object.

  2. Cél: unit=lab-batch.service a lab-vm-01 hoston. Precondition: systemctl cat lab-batch.service > /var/tmp/lab-batch.unit.backup és systemctl status lab-batch.service. Mutáció: systemctl stop lab-batch.service. Verification: systemctl is-active lab-batch.service és pidstat -u a CPU visszaesésére. Rollback: systemctl start lab-batch.service. Postcondition: a service inaktív vagy visszaállt, nem töröltünk.

  3. Read-only: ss -lntp | grep 8443. Ha PID 777 a lab-app, akkor ps -o pid,user,comm,args -p 777. Hipotézis: a lab-app journalctl -u lab-app.service --since "-10 min" szerint már kétszer indult. Scoped mutation: systemctl stop lab-app.service. Verification: ss -lntp | grep 8443 üres. Rollback: systemctl start lab-app.service, ha a service config nem rossz. Postcondition: port szabad.

58.2.10 Rövid összefoglaló

A Linux admin parancs- és állapotindex a parancsokat cél, scope, jogosultság és adatforrás szerint köti a rendszerállapothoz. A read-only parancs csak megfigyel, a scoped mutation nevesített targetre korlátozódik, és mindig előfeltétel, verifikáció és rollback keretben hajtódik végre. A diagnosztikai kérdés felől keressük a réteget és a parancsot, majd a kimenetet az adatforrás verziójával együtt értelmezzük. A példák diszk IOPS terhelés és port foglaltság feloldását mutatják be.

Továbbhasznált definíciók: read-only parancs, scoped mutation, pre/postcondition.
