42.4 Namespace, quota és tenant trust boundary

42.4.1 Motiváció és definíció

Egy fejlesztő természetes módon használja a C++ namespace-t: logikai névtér, amely elkerüli a névütközést, de nem ad linkage, memória- vagy hozzáférési izolációt. A Kubernetes Namespace erőforrása hasonló csapda: a cluster erőforrásait rendezi logikai csoportokba, de önmagában nem biztonsági határ. Ha egy szolgáltatást több bérlő (tenant) közös clusterén futtatunk, akkor a namespace csak az első réteg. A többi réteget explicit módon kell megtervezni: erőforrás-korlát, RBAC, hálózati politika és admission-szabály. A cél mindig a robbanási sugár (blast radius) csökkentése, nem pedig annak feltételezése, hogy a namespace elszigetel.

Definíció (namespace trust boundary, soft multi-tenancy): A Kubernetes Namespace egy cluster-scoped API objektum, amelyben a namespaced API erőforrások (Pod, Service, Secret, ConfigMap, stb.) egyedi névvel élnek. A namespace akkor válik valódi tenant bizalmi határrá, ha a következő vezérléseket együtt alkalmazzuk:

  • RBAC: ki melyik namespace erőforrásaihoz férhet hozzá,
  • ResourceQuota / LimitRange: milyen erőforrásmennyiséget fogyaszthat a bérlő,
  • NetworkPolicy: milyen hálózati forgalom léphet be és ki a namespace Podjaihoz,
  • Admission: milyen munkaterhelés-specifikáció kerülhet a namespace-be.

Ez az együttes a soft multi-tenancy. A kernel, a container runtime és a node továbbra is közös, ezért ez nem hard isolation.

42.4.2 ResourceQuota, LimitRange és fairness

A ResourceQuota a namespace szintjén aggregált, kemény korlátot ad. Például korlátozhatja a Podok számát, a CPU/memória összesített requests és limits értékét, a PersistentVolumeClaimek számát, a Secret/ConfigMap darabszámot. A quota az admission fázisban lép működésbe: ha egy új erőforrás létrehozása túllépné a hard korlátot, az API-kiszolgáló 403 Forbidden hibát ad. A quota azonban önmagában nem fairness-eszköz: egy bérlő egyetlen nagy Poddal is kimerítheti a namespace erőforrásait, ha a többi Pod nem kap requestet.

A LimitRange per-object szintű szabályokat ad: minimális és maximális kérés/limit, valamint default értékek, ha egy Pod vagy container nem határoz meg requestet/limitet. Ezáltal minden Pod kap egy minimális, előrejelezhető erőforrás-igényt, és a quota számítás alapja egyenletesebb. A kettő együtt adja a fairness alapját: a ResourceQuota a teljes namespace határát, a LimitRange az egyes munkaterhelések minimális/maximális keretét.

A quota kihasználtsága például:

Ucpu=∑requests.cpuquota.cpu⋅100%U_{cpu} = \frac{\sum requests.cpu}{quota.cpu} \cdot 100\%

ahol a nevező a hard quota, a számláló a namespace-ben lévő összes Pod CPU requests összege. Ez a százalék mutatja, mennyi fejlesztési headroom marad.

42.4.3 RBAC, NetworkPolicy és admission három együtt

A három vezérlés más-más réteget zár le, ezért egyetlen réteg kihagyása lyukat hagy:

  • RBAC nélkül: a bérlő felhasználói vagy service accountjai hozzáférhetnek más namespace-ek objektumaihoz, törölhetik azokat, vagy kiolvashatják a Secreteket.
  • NetworkPolicy nélkül: a Podok a cluster hálózatán általában elérhetik egymást IP-címen vagy Service ClusterIP-n keresztül. A namespace nem hoz létre hálózati elszigetelést. Egy lab-tenant-b Pod curl-rel elérheti a lab-tenant-a Service backendjét, hacsak a CNI hálózati politika ezt nem tiltja.
  • Admission nélkül: egy bérlő privileged: true containert, hostPath kötetet vagy hostNetwork: true Podot hozhat létre, ami gyakorlatilag a namespace minden policy-jét megkerüli. A Pod Security Standards (PSS) vagy policy engine (OPA, Kyverno) admission szinten korlátozza ezt.

A három réteg együttesen biztosítja, hogy a bérlő csak a saját namespace-ében, a megengedett hálózati útvonalakon és a megengedett workload-specifikációval működjön.

42.4.4 Node sharing, kernel és runtime trust

A legfontosabb korlát: a namespace nem Linux namespace. A Kubernetes Podok ugyanazon a node kernelén, ugyanazon a kubelet és container runtime folyamaton osztoznak. A node host kernel, a CRI runtime, a CNI plugin és a kubelet egy közös trusted computing base (TCB). Ha egy bérlő Podja kernel exploit-ot használ, vagy a container runtime hibája miatt kitör a konténerből, akkor a node-on futó összes Pod és azok Secret kötete veszélybe kerül. A namespace határai ilyenkor semmit nem védenek.

Ezért a soft multi-tenancy csak akkor elfogadható, ha:

  1. a munkaterhelések nem privilegizáltak, és admission korlátozza a privileged, hostPath, hostNetwork, hostPID használatát,
  2. a node kernel, runtime és CSI/CNI komponensei rendszeresen patcheltek,
  3. a bérlők RBAC-ja nem teszi lehetővé node-szintű erőforrások írását,
  4. a hálózati politika default deny és csak a szükséges egress/ingress engedélyezett.

Ha erős izoláció szükséges, akkor a bérlőt külön node-ra kell ütemezni taint/toleration és nodeSelector segítségével, vagy külön clusterre, vagy külön cloud accountra kell helyezni. A dedicated node pool közepes izoláltság: továbbra is közös a cluster control plane és az etcd, de a munkaterhelések kernel/runtime szinten el vannak választva. A dedicated cluster erős izoláltság, de magas működtetési költség. A kiválasztás a valószínűsíthető károkon és a compliance követelményeken múlik.

Példa dedicated node poolra:

apiVersion: v1
kind: Node
metadata:
  name: lab-a-node-1
  labels:
    tenant: lab-tenant-a
spec:
  taints:
  - effect: NoSchedule
    key: tenant
    value: lab-tenant-a

A tenant Pod specifikációja pedig:

apiVersion: v1
kind: Pod
metadata:
  name: lab-a-app
  namespace: lab-tenant-a
spec:
  nodeSelector:
    tenant: lab-tenant-a
  tolerations:
  - key: tenant
    operator: Equal
    value: lab-tenant-a
    effect: NoSchedule
  containers:
  - name: app
    image: registry.example.com/lab-a:1.0.0

42.4.5 Secret, log és metrics visibility

A namespace-scoped erőforrások (Secret, ConfigMap) attól még nem válnak automatikusan rejtetté, ha az RBAC nem korlátoz: aki get secrets jogot kap a namespace-ben, az minden Secretet kiolvashat. A Secret kötetek a node fájlrendszerén, a kubelet által kezelt tmpfs-ben materializálódnak. A node root felhasználója, vagy egy olyan privileged Pod, amely a host fájlrendszerhez fér, hozzáférhet ezekhez a Secretekhez. Ezért a Secret hozzáférési modellt namespace-réteg mellett RBAC réteggel is tervezni kell.

A logok hasonló problémát jelentenek: a kubectl logs a kubelet és a container runtime naplójából olvas. A node-on futó bármilyen hozzáféréssel rendelkező folyamat láthatja a konténerlogokat. A központi logplatform (pl. Loki, ELK) szintén külön hozzáférés-vezérlést igényel: ha a bérlő a platformban széles indexhez fér hozzá, más tenant logjait is láthatja. A metrics ugyanígy: a kubelet/cAdvisor node szintű CPU, memória, nyitott fájl statisztikát szolgáltat, ami gyakran aggregált, és a Prometheus RBAC dönti el, ki férhet a sorozatokhoz. A ServiceMonitor, PodMonitor és RecordingRule szintén namespace-scoped API objektumok, de a lekérdezési jogosultság a Prometheus/Grafana szintjén dől el. A tenant modellben ezeket a visibility csatornákat külön kell lehatárolni.

42.4.6 Blast radius és policy exception

A blast radius azt írja le, hogy egy bérlő hibája, hibás konfigurációja vagy kompromittálódása milyen széles körben okoz kárt. A namespace, quota, RBAC és hálózati politika együtt szűkíti ezt. De minden kivétel (exception) növeli a robbanási sugarat. Ha például engedélyezünk egy cross-namespace egress-t, mert a lab-tenant-b szolgáltatás el kell érje a lab-tenant-a adatbázisát, akkor ezzel:

  • hálózati útvonalat nyitunk két tenant között,
  • valószínűleg a cél adatbázis eléréséhez szükséges Secretet is oda kell adnunk,
  • nő a hibás hozzáférés vagy adatkiszivárgás kockázata.

Az ilyen kivételeket nem szabad defaultként engedélyezni. Jó gyakorlat: minden kivételt ticketben rögzíteni, lejárati idővel ellátni, dokumentálni, és automatikus review-val újraértékelni. A policy exception önmagában is policy: a kivételre vonatkozó szabályt is verziókezelni és auditálni kell. Az admission policy engine (pl. Kyverno/OPA) kikényszerítheti, hogy minden namespace erőforrás rendelkezzen a tenant: lab-tenant-a label-lel, és ezzel a nem odavaló erőforrás létrehozását blokkolhatja.

42.4.7 Kidolgozott példa

Labtarget: lab-cluster Kubernetes cluster, kubectl context lab-cluster. Cél: lab-tenant-a namespace-ben erőforrás-korlátot és default deny hálózati politikát állítunk be, hogy a bérlő ne tudja kimeríteni a cluster erőforrásait és ne érje el más tenant Podjait.

A CNI ebben a példában NetworkPolicy-t támogató implementációt feltételez; ennek ellenőrzése szükséges.

1. lépés: namespace és ResourceQuota + LimitRange létrehozása.

kubectl --context lab-cluster create namespace lab-tenant-a
apiVersion: v1
kind: ResourceQuota
metadata:
  name: lab-tenant-a-quota
  namespace: lab-tenant-a
spec:
  hard:
    requests.cpu: "4"
    requests.memory: "8Gi"
    limits.cpu: "8"
    limits.memory: "16Gi"
    pods: "20"
    persistentvolumeclaims: "10"
    services: "10"
    secrets: "50"
    configmaps: "50"
---
apiVersion: v1
kind: LimitRange
metadata:
  name: lab-tenant-a-limit
  namespace: lab-tenant-a
spec:
  limits:
  - type: Container
    default:
      cpu: 500m
      memory: 512Mi
    defaultRequest:
      cpu: 250m
      memory: 256Mi
    max:
      cpu: "2"
      memory: 4Gi
    min:
      cpu: 50m
      memory: 64Mi

A fenti YAML-t kubectl apply-jal alkalmazzuk. A ResourceQuota a requests.cpu összeget 4 magban korlátozza, a LimitRange pedig minden új containernek ad 250m CPU requestet, ha a Pod nem határoz meg értéket.

2. lépés: default deny hálózati politika.

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: lab-tenant-a-default-deny
  namespace: lab-tenant-a
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress

Ez a politika minden ingress és egress forgalmat letilt a namespace Podjai felé és felől. A valódi alkalmazáshoz kell egy engedélyező politika a szükséges forgalomra, például az egészségügyi probe-okhoz és a DNS-hez:

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: lab-tenant-a-allow-core
  namespace: lab-tenant-a
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress
  ingress:
  - from:
    - podSelector: {}
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
          # a CNI/runtime egészségügyi ellenőrzéséhez szükséges namespace
  egress:
  - to:
    - podSelector: {}
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
    ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53

3. lépés: ellenőrzés.

kubectl --context lab-cluster describe resourcequota -n lab-tenant-a
kubectl --context lab-cluster describe limitrange -n lab-tenant-a

A ResourceQuota leírásában a Used kezdetben 0. Hozzunk létre egy Podot request nélkül:

apiVersion: v1
kind: Pod
metadata:
  name: lab-a-app
  namespace: lab-tenant-a
spec:
  containers:
  - name: app
    image: registry.example.com/lab-a:1.0.0

A Pod specifikációja nem tartalmaz resources.requests vagy limits mezőt. A LimitRange miatt az API-kiszolgáló a Pod spec.containers[0].resources.requests értékét 250m CPU-ra és 256Mi memóriára állítja be. Ezt a kubectl get pod lab-a-app -n lab-tenant-a -o yaml kimenetében ellenőrizzük.

Várt kimenet: a ResourceQuota Used mezője mostantól tartalmazza a Pod request értékét; a Pod create nem hibázik. Ha egy másik Podot próbálunk létrehozni úgy, hogy a requests.cpu összeg túllépné a 4 magos korlátot, az API 403 Forbidden hibát ad exceeded quota üzenettel.

4. lépés: cross-namespace elérés tesztje.

Indítsunk egy Podot a lab-tenant-b namespace-ben, majd próbáljunk hozzáférni a lab-tenant-a Service-hez. A NetworkPolicy default deny miatt a kapcsolat nem jön létre: a hívás timeoutot ad. Ha a default deny nélkül tesztelünk, a kapcsolat korábban létrejön, és ez mutatja a hiányzó hálózati politika hatását.

Hibajelenség: a cross-namespace hívás akkor is működhet, ha a NetworkPolicy nincs a CNI által érvényesítve. Ilyenkor a hálózati izoláció nem valós; a CNI-t és a NetworkPolicy supportot ellenőrizni kell.

42.4.8 Tipikus hibák és ellenpróbák

  1. Feltételezés: a namespace hálózati elérhetőséget is elválaszt.
    Tünet: a lab-tenant-b Pod eléri a lab-tenant-a Service-t. Adatgyűjtés: kubectl get networkpolicy -A, kubectl describe networkpolicy -n lab-tenant-a. Ha nincs default deny, a hiba oka a hiányzó politika. Változtatás: hozzunk létre default deny NetworkPolicy-t, majd verifikáljuk a hívás timeoutját. Ne feledjük a DNS egress engedélyezését, mert a Podok különben még a feloldást sem tudják elvégezni.

  2. A LimitRange nem érvényesül meglévő Podokra.
    A LimitRange csak új Podok létrehozásakor lép be. Ha egy korábban létrehozott Podnak nincsenek requestjei, a LimitRange nem módosítja. A kubectl get limitrange -n lab-tenant-a -o yaml segítségével ellenőrizzük a szabályt, de a meglévő Podot újra kell indítani vagy törölni, hogy a default érvényesüljön.

  3. A ResourceQuota túl szigorú vagy túl laza.
    Ha a requests.cpu quota 4, de a tenant alkalmazás átlagosan 6 magot igényel, a Podok folyamatosan Pending vagy FailedScheduling állapotba kerülnek. A kubectl describe resourcequota -n lab-tenant-a megmutatja a Used-ot. Növeljük a quota-t csak indokolt kapacitástervezés alapján, ne töröljük a korlátot. Az ellenkező hiba: a quota magas, de a LimitRange hiányzik, így egyetlen nagy Pod monopolizálhatja a namespace erőforrásait; bevezetjük a LimitRange-ot max értékkel.

  4. Secret hozzáférés szélesre nyitása.
    Ha a bérlő service accountja get secrets jogot kap a saját namespace-ében, az összes Secretet eléri. Tünet: a bérlő alkalmazás olyan titkot is olvas, amelyet nem lenne szabad. Változtatás: szűkítsük a RBAC-ot, például csak a szükséges Secretekre vagy service accountokra; ellenőrizzük kubectl auth can-i get secrets -n lab-tenant-a --as system:serviceaccount:lab-tenant-a:default paranccsal.

  5. Admission hiánya miatt privileged Pod kiszökése.
    Ha a bérlő létrehozhat privileged: true Podot, a namespace/quota/network policy semmit sem ér. Tünet: egy Pod hostPath / hostNetwork eléréssel fut. Adatgyűjtés: kubectl get pod -n lab-tenant-a -o yaml | grep -E "privileged|hostPath|hostNetwork". Változtatás: Pod Security Admission vagy policy engine bevezetése, amely restricted szintet kényszerít ki.

42.4.9 Feladatok

42.4.9.1 1. feladat – Magyarázó

Magyarázza el röviden, hogy a Kubernetes Namespace miért nem tekinthető biztonsági határnak önmagában. Adjon meg egy konkrét feltételt, amelyben a namespace izoláltsága elégtelen, és nevezze meg azt a vezérlőt, amely ezt a hiányt pótolja.

42.4.9.2 2. feladat – Adminisztrációs/konfigurációs

Hozzon létre egy lab-tenant-a namespace-t ResourceQuota-val (legfeljebb 4 CPU request, 8Gi memória request, 20 Pod) és LimitRange-ot (default request 250m CPU/256Mi; max 2 CPU/4Gi). Hozzon létre egy Podot, amely nem ad meg erőforrás-requestet. Igazolja, hogy a LimitRange beállította a default request értéket, és a ResourceQuota Used mezője növekedett.

42.4.9.3 3. feladat – Diagnosztikai/failure/recovery

A lab-tenant-b Pod eléri a lab-tenant-a Service-t. Telepítsen default deny NetworkPolicy-t a lab-tenant-a namespace-re, majd engedélyezze a DNS egress forgalmat a kube-system namespace felé. A diagnózis során először mutassa meg, hogy a hálózati politika hiányzott, majd állítsa helyre, és ellenőrizze, hogy a cross-namespace hívás timeoutot ad, de a DNS feloldás továbbra is működik.

42.4.10 Megoldások

42.4.10.1 1. feladat megoldása

A Kubernetes Namespace logikai névtér: API objektumokat csoportosít, de nem hoz létre hálózati elkülönítést, kernel szintű sandboxot vagy automatikus per-namespace biztonsági hozzáférést. Egy konkrét feltétel: ha nincs NetworkPolicy, a lab-tenant-b Podja bármely más namespace Service-jét elérheti a cluster hálózaton. A hiányt a NetworkPolicy pótolja, mert az explicit ingress/egress forgalmi engedélyeket állít be. A másik hiány: ha nincs admission, a bérlő privileged container futtathat, amely kernel szinten kiszökhet; ezt Pod Security Admission vagy policy engine előzi meg. Postcondition: a hallgató képes megnevezni a namespace határait és a szükséges kiegészítő vezérléseket.

42.4.10.3 3. feladat megoldása

Először ellenőrizzük a meglévő hálózati politikákat:

kubectl --context lab-cluster get networkpolicy -n lab-tenant-a

Ha a lista üres, a cross-namespace hívás azért működik, mert nincs default deny. Hozzuk létre a default deny politikát:

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: lab-tenant-a-default-deny
  namespace: lab-tenant-a
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress

Ezután engedélyezzük a DNS-t:

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: lab-tenant-a-allow-dns
  namespace: lab-tenant-a
spec:
  podSelector: {}
  policyTypes:
  - Egress
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
    ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53

Ellenőrzés: a cross-namespace hívás mostantól timeoutot ad, mert a default deny letiltja az ingress és egress forgalmat. A DNS feloldásnak továbbra is működnie kell, mert a kube-system namespace felé nyitott egress engedélyezett. Ha a DNS még mindig nem működik, ellenőrizzük, hogy a CNI valóban érvényesíti-e a NetworkPolicy-t, és hogy a DNS port valóban az 53-as UDP/TCP. Postcondition: a lab-tenant-a namespace-ben default deny van, a hálózati hozzáférés minimálisra szűkült, és a diagnózis során megerősítettük a korábbi nyitott állapotot.

42.4.11 Rövid összefoglaló

A Kubernetes Namespace logikai API-csoportosítás, nem biztonsági határ. Tenant trust boundary-t csak a ResourceQuota/LimitRange, RBAC, NetworkPolicy és admission együttesen ad. A ResourceQuota a namespace szintű aggregált korlátot, a LimitRange a per-object default/min/max értékeket szolgáltatja. A NetworkPolicy default deny nélkül a namespace-ek közötti forgalom nyitott. A Secret/log/metrics láthatósága és a közös node kernel továbbra is megkerüli a namespace határait, ezért erős izoláltsághoz dedicated node/cluster/account szükséges. Minden policy exception növeli a blast radius-t, ezért azt indoklással, lejárattal és auditálással kell kezelni.

Továbbhasznált definíciók:

  • Soft multi-tenancy: namespace-szintű izoláció ResourceQuota, RBAC, NetworkPolicy és admission együttes használatával; a node kernel és runtime megosztott.
  • ResourceQuota/LimitRange: a quota a namespace erőforrások kemény aggregált korlátja, a LimitRange az egyes Pod/container szintű default/min/max szabály.
  • NetworkPolicy default deny: olyan hálózati politika, amely minden ingress/egress forgalmat letilt, és csak kifejezetten engedélyezett forgalmat enged át.

42.4.12 Források és ellenőrzési hiányok

  • Kubernetes Documentation — kiindulópont a ResourceQuota, LimitRange, NetworkPolicy és Namespace témakörökhöz, ebben a kérésben nem ellenőriztem.
  • Cilium Documentation — kiindulópont a NetworkPolicy érvényesítés és a CNI hálózati izoláció ellenőrzéséhez, ebben a kérésben nem ellenőriztem.
  • Sigstore Documentation — a workload identity és supply chain kapcsolódó forrás, ebben az alfejezetben közvetlenül nem használtam.

Ellenőrzési hiányok: A példákban használt API-verziók (v1 ResourceQuota, LimitRange, NetworkPolicy) stabilnak tekinthetők, de a pontos Kubernetes minor verzió, a CNI implementáció NetworkPolicy supportja, valamint a kubernetes.io/metadata.name label viselkedése a megadott labclusterben nem ellenőrzött, mert nincs kutatási jegyzet és webes eszköz. A példák csak illusztratívak, nem futtatottak. A registry.example.com és a node nevek dummy labazonosítók.
