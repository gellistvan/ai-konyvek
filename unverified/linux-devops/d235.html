47.5 Linux service fleet playbook labor

47.5.1 Motiváció

Egyetlen labhoston a d115 acceptance script már bizonyította a kívánt állapotot. Két gépből álló flottában viszont már nem az a kérdés, hogy egy parancs kézi futtatása sikeres-e, hanem hogy ugyanazt a desired state-et ismételhetően, auditálhatóan és részleges hibánál is visszafelé vezethetően érjük el. A cél egy lab-cpp-service nevű C++ szolgáltatás host baseline-jának Ansible playbookból való előállítása: users, packages, storage, service és config rétegek egyaránt szerepelnek.

A szolgáltatás binárisa itt kiadott, immutable artifactnak tekintendő; nem a buildelését ismételjük. A playbook a runtime hozzáférhetőség, konfiguráció, adatkönyvtár és systemd lifecycle állapotot menedzseli.

47.5.2 Definíció, határok és labtopológia

Fleet baseline: a flotta minden hostjára érvényes, verziókövetett desired state halmaz. Ezt Ansible inventory és role egészíti ki gépspecifikus változókkal.

Role: újrahasználható task, template, file és handler csomag. A d235 szerepe lab-cpp-service, benne a négy üzemeltetési réteg taskjai.

Idempotencia: egy playbook ismételt futtatása nem okoz további megfigyelhető állapotváltozást, amennyiben a host már a desired state-ben van. Ansible modulok döntően ezt a property-t biztosítják, de ez nem általános elosztott exactly-once tranzakció a playbook szintjén.

Drift: amikor az observed state eltér a config-source és a desired state kombinációjától, például valaki kézzel módosítja a target hoston a config fájlt.

Health gate: egy futtatás során a deploy után elvégzett alkalmazás-egészségellenőrzés, amely serial batch alatt csak a sikeres hostot engedi tovább.

A lab két célgépet és egy control állomást feltételez:

Topológia elem Cím/elérés Funkció
ansible-lab-control lab hálózati namespace inventory, playbook, artifactök
labhost-01 192.0.2.31 első célhost
labhost-02 192.0.2.32 második célhost
lab-svc UID/GID 3001 a C++ szolgáltatás futó identitása
lab-cpp-service systemd unit mindkét target szolgáltatás-lifecycle

A példa nem végez lemezformázást, partíciótörlést vagy cloud erőforrás-létrehozást. A /srv/lab-cpp-service mount egy előre elkészített, LABCPPSVC címkéjű ext4 filesystemre hivatkozik. A módosító parancsok a labhostokon become-mal futnak; a control gépen csak olvasható inventory és artifactkezelés történik.

47.5.3 Role felépítése és működése

A role öt feladatcsoportot kapcsol össze:

  1. Identity: rendszeruser/group létrehozása a futó szolgáltatásnak.
  2. Packages: a szolgáltatáshoz szükséges host csomagok jelenlétének biztosítása.
  3. Storage: adatkönyvtár és mount állapot.
  4. Config: JSON config template kiírása validációval.
  5. Service: systemd unit telepítése, daemon-reload, enable és start.

A handler restart lab-cpp-service csak akkor fut, ha a config vagy unit template ténylegesen megváltozik. Ez az Ansible event-driven deploy modellje, hasonló ahhoz, amikor C++ fejlesztőnél egy build-output csak akkor kerül linkelésre, ha a source grátulál változott. Itt a changed state a modul által összehasonlított objektumeltérésből adódik, nem egyszerű időbélyegből.

A template validáció fontos réteghatár: a JSON config szintaktikailag helyes lehet, de a szolgáltatás runtime szempontból egy port=0 értékre rosszul reagál. A template modul validate opciója csak a szintaktikai réteget zárja le. A health gate külön zárja a futtathatóságot.

47.5.4 Kidolgozott példa: playbook, inventory és role

Előfeltételek:

  • a control gépen Ansible van telepítve, és az SSH key-hitelesítés mindkét target lab felhasználójához működik;
  • a targeteken a lab usernek passwordless sudo joga van;
  • a diszk label létezik: LABCPPSVC.

Inventory inventory/hosts.yml:

---
all:
  children:
    lab_cpp_fleet:
      hosts:
        labhost-01:
          ansible_host: 192.0.2.31
          ansible_user: lab
        labhost-02:
          ansible_host: 192.0.2.32
          ansible_user: lab
  vars:
    ansible_become: true
    ansible_python_interpreter: /usr/bin/python3

A két host külön sorakozik, így a driftszimuláció név szerint végezhető. A 192.0.2.0/24 RFC 5737 dokumentációs tartomány; élesben a tényleges labcímeket kell inventoryban rögzíteni.

Group vars inventory/group_vars/lab_cpp_fleet.yml:

---
svc_packages:
  - libmicrohttpd12
  - jq
  - libcap2-bin
svc_data_label: LABCPPSVC
svc_listen: "127.0.0.1"
svc_port: 8080
svc_data_dir: "/srv/lab-cpp-service"
svc_worker_threads: 4

A csomagnevek ellenőrzése a lab Ubuntu 24.04 kiadására tartozik; a példa nem állítja, hogy a kiadástól függetlenül ugyanezek a nevek érvényesek.

Role taskok roles/lab-cpp-service/tasks/main.yml:

---
- name: Ensure lab service group
  ansible.builtin.group:
    name: lab-svc
    gid: 3001
    system: true

- name: Ensure lab service user
  ansible.builtin.user:
    name: lab-svc
    uid: 3001
    group: lab-svc
    home: /var/lib/lab-cpp-service
    create_home: false
    shell: /usr/sbin/nologin
    system: true

- name: Install required host packages
  ansible.builtin.apt:
    name: "{{ svc_packages }}"
    state: present
    update_cache: true
    cache_valid_time: 3600

- name: Ensure service data directory exists
  ansible.builtin.file:
    path: /srv/lab-cpp-service
    state: directory
    owner: lab-svc
    group: lab-svc
    mode: "0750"

- name: Mount lab data filesystem
  ansible.builtin.mount:
    path: /srv/lab-cpp-service
    src: "LABEL={{ svc_data_label }}"
    fstype: ext4
    opts: "defaults,noatime"
    state: mounted
  notify: restart lab-cpp-service

- name: Ensure config directory
  ansible.builtin.file:
    path: /etc/lab-cpp-service
    state: directory
    owner: root
    group: lab-svc
    mode: "0750"

- name: Render validated service config
  ansible.builtin.template:
    src: config.json.j2
    dest: /etc/lab-cpp-service/config.json
    owner: root
    group: lab-svc
    mode: "0640"
    validate: "python3 -m json.tool %s"
  notify: restart lab-cpp-service

- name: Render systemd unit
  ansible.builtin.template:
    src: lab-cpp-service.service.j2
    dest: /etc/systemd/system/lab-cpp-service.service
    owner: root
    group: root
    mode: "0644"
    validate: "systemd-analyze verify --no-pager %s"
  notify: restart lab-cpp-service

- name: Enable and start service
  ansible.builtin.systemd:
    name: lab-cpp-service
    state: started
    enabled: true
    daemon_reload: true

A validate értékek a skill-boundaryt jelölik: a JSON előállítás előtti syntax check megfogja a törött configot, de nem a hibás szemantikát. A systemd unit systemd-analyze verify ellenőrzése a unit file szintaktikáját fogja; az Ansible a temp fájlt a %s helyére írja.

Handler roles/lab-cpp-service/handlers/main.yml:

---
- name: restart lab-cpp-service
  ansible.builtin.systemd:
    name: lab-cpp-service
    state: restarted
    daemon_reload: true

Az ansible.builtin.systemd modul neve ansible-core verziófüggő lehet; a d286 technológiai státuszfejezetben ellenőrizendő, hogy az adott ansible-core kiadásban systemd vagy systemd_service a hivatalos name. Itt a labcontrollra telepített core változathoz rendelt nevet használjuk.

Config template roles/lab-cpp-service/templates/config.json.j2:

{
  "listen": "{{ svc_listen }}",
  "port": {{ svc_port }},
  "data_dir": "{{ svc_data_dir }}",
  "worker_threads": {{ svc_worker_threads }}
}

Service unit template roles/lab-cpp-service/templates/lab-cpp-service.service.j2:

[Unit]
Description=lab-cpp-service
After=network.target

[Service]
User=lab-svc
Group=lab-svc
ExecStart=/opt/lab-cpp-service/bin/lab-cpp-service --config /etc/lab-cpp-service/config.json
WorkingDirectory={{ svc_data_dir }}
Restart=on-failure
RestartSec=5
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=full
ProtectHome=true

[Install]
WantedBy=multi-user.target

A ProtectSystem=full és ProtectHome=true a systemd sandbox határait erősíti. A C++ szolgáltatásnak ezekkel kompatibilisnek kell lennie: ne írjon a /usr, /boot, /etc rendszerútvonalakra, csak a /srv/lab-cpp-service adatkönyvtárba.

A két hoston a soros változtatást és health gate-et egy deploy/verify playbook foglalja össze playbooks/deploy_and_verify.yml:

---
- name: lab-cpp-service fleet baseline with health gate
  hosts: lab_cpp_fleet
  gather_facts: true
  serial: 1
  max_fail_percentage: 0
  become: true
  tasks:
    - name: Deploy and verify with rollback window
      block:
        - name: Snapshot pre-change service config
          ansible.builtin.copy:
            remote_src: true
            src: /etc/lab-cpp-service/config.json
            dest: /etc/lab-cpp-service/config.json.pre-play
            force: true
          ignore_errors: true

        - name: Apply lab-cpp-service role
          ansible.builtin.include_role:
            name: lab-cpp-service

        - name: Health check after deploy
          ansible.builtin.uri:
            url: "http://127.0.0.1:{{ svc_port }}/health"
            status_code: 200
            timeout: 5
          register: health_result
          until: health_result.status == 200
          retries: 12
          delay: 5

      rescue:
        - name: Capture service log on failure
          ansible.builtin.shell: journalctl -u lab-cpp-service --no-pager -n 100
          register: svc_log
          failed_when: false

        - name: Show captured log tail
          ansible.builtin.debug:
            var: svc_log.stdout_lines

        - name: Restore pre-play config
          ansible.builtin.copy:
            remote_src: true
            src: /etc/lab-cpp-service/config.json.pre-play
            dest: /etc/lab-cpp-service/config.json
            owner: root
            group: root
            mode: "0640"
          failed_when: false

        - name: Restart after rollback
          ansible.builtin.systemd:
            name: lab-cpp-service
            state: restarted
            daemon_reload: true
          failed_when: false

        - name: Explicit fail with rescue note
          ansible.builtin.fail:
            msg: "Host failed health gate; rollback attempted. Inspect journalctl and config."

A serial: 1 eredménye: a playbook előbb a labhost-01-en fut végig, és csak sikeres health után lép a labhost-02-re. A max_fail_percentage: 0 azt jelzi, hogy bármely hosthiba a play futtatását leállítja a hátralévő célok számára. Ez nem tranzakció: az első host már az új desired state-ben maradhat, míg a második rollback kísérletet kap.

47.5.5 Futtatási várhatóságok

Első alkalommal a várt összkép nagyjából:

labhost-01 : ok=10 changed=8 unreachable=0 failed=0
labhost-02 : ok=10 changed=8 unreachable=0 failed=0

A pontos szám az előkészítettségtől függ. Itt csomagtelepítés, mount, config, unit és service feladatok változnak. A health check a changed számlálóban nem feltétlenül jelenik meg, mivel a uri modul nem konfigurációt módosít.

Közvetlenül utána második futtatás, amikor a hostok már a kívánt állapotban vannak:

labhost-01 : ok=10 changed=0 unreachable=0 failed=0
labhost-02 : ok=10 changed=0 unreachable=0 failed=0

Ez a repeated no-op bizonyítéka. A changed=0 azt jelenti, hogy a modulok a jelenlegi állapotot a desired state-ben találták, és egyik handler sem futott. A health check ugyanakkor továbbra is lefut; az idempotencia nem egyenlő az ellenőrzés elhagyásával.

Drift injektálás céljából labhost-02-n kézzel csökkentsük a worker_threads értékét, például 4-ről 1-re. A játszott playbook újra lefuttatása során a template mismatch egyetlen changed taskot ad, majd a handler újraindítja a szolgáltatást. A labhost-01 javítás nélkül changed=0 marad. Ez a scope-os drift correction: a play nem terjeszti szét a változást az egész flottára, hanem a driftszenvedő hostra redukálja.

47.5.6 Failure injection és rescue

A lab célzott hibaszimulációt is igényel. Futtassuk egy hibás svc_port override-dal:

cd /home/lab/ansible-fleet-live
ansible-playbook -i inventory/hosts.yml playbooks/deploy_and_verify.yml -e svc_port=0

A root labcontroll használata nem szükséges; a példa a lab user home-jából indul. A svc_port=0 felülírja a group varst. A JSON template valid lesz, mert a 0 szám, viszont a szolgáltatás health endpoint elérhetetlen, vagy a health check rossz portot vizsgál. A block így a health tasknál hibába fut, a rescue lefut, visszaállítja a backupot, megkísérli az újraindítást, majd explicit fail üzenetet ad. A játszma nem hamis PASS-t ad; a részleges rollout látható marad.

A rescue önmagában nem garancia. A Restart after rollback után nem futtatunk ismételt health ellenőrzést, csak failed_when: false mellett újraindítunk. Ha a rollback alatt a config visszaállítása sikeres, a következő futtatásnak ismét zöldnek kell lennie. Azt is igazolni kell:

ansible-playbook -i inventory/hosts.yml playbooks/deploy_and_verify.yml

A kimenet a két hoston várhatóan:

labhost-01 : ok=10 changed=0 unreachable=0 failed=0
labhost-02 : ok=10 changed=0 unreachable=0 failed=0

Ha a rescue nem tudta visszaállítani a konfigurációt, akkor a labhost-02-on changed=1 és esetleges health hiba marad; ilyenkor a labollback helyett a labkonzolon kell a journalctl logot és a template diffet ellenőrizni.

47.5.7 Runbook, inventory és artifactkezelés

A futás előtt készítsünk runbook artifactot:

RUN_ID="$(date +%Y%m%d-%H%M%S)"
mkdir -p artifacts/runbook-live-$RUN_ID
cp inventory/hosts.yml inventory/group_vars/lab_cpp_fleet.yml artifacts/runbook-live-$RUN_ID/
ansible-inventory -i inventory/hosts.yml --list > artifacts/runbook-live-$RUN_ID/inventory.json 2>/dev/null
ansible-playbook -i inventory/hosts.yml playbooks/deploy_and_verify.yml > artifacts/runbook-live-$RUN_ID/playbook.log 2>&1
sha256sum artifacts/runbook-live-$RUN_ID/* > artifacts/runbook-live-$RUN_ID/SHA256SUMS

A SHA256SUMS segít az inverse mappingben: ha egy későbbi audit szerint a config hibás volt, a pontosan rögzített inventory és group_vars hash hozzárendelhető a playbook kimenethez. Ez nem helyettesíti a backup/restore szerződést, csak a control plane artifactöt auditálja. A target hoston a pre-play snapshot config.json.pre-play, a tényleges remote backup storage e helyett külön, a d097 és d099 szerint kezelendő.

47.5.8 Hibák és ellenpróbák

  1. A playbook missing sudo password hibával áll meg. Tünet: MODULE FAILURE és Incorrect sudo password a targeteken. Hipotézisünk: inventory userhez nincs passwordless sudo, vagy a become a control felhasználó kontextusában nem megfelelő. Adatgyűjtés: ansible -i inventory/hosts.yml lab_cpp_fleet -m ping -vvv. Egy módosítás: inventory ansible_become_pass-t ne adjunk hozzá plaintextben; inkább a labhoz tartozó SSH key és sudoers-szabály legyen javítva. Verification: ansible -i inventory/hosts.yml lab_cpp_fleet -m command -a 'id lab-svc' -b sikeres.

  2. A template validáció megfogja a hibás JSON-t, de a service mégis elszáll. Tünet: config task ok, service start failed, health check unreachable vagy status != 200. Hipotézis: a config szintaktikailag helyes, de a szolgáltatás futás közben a port vagy data_dir értéket elutasítja. Adatgyűjtés: journalctl -u lab-cpp-service --no-pager -n 100, valamint a handlerek sorrendjének ellenőrzése. Egy változtatás: a role ne hagyjon hátra daemon_reload nélküli systemd startot; a health check maradjon. Verification: a futtatás után a health check until ciklusa legalább egyszer 200-at kapjon.

  3. A drift correction élőben is újraindítja a szolgáltatást. Ez nem hiba, de a deploy review-nek tudnia kell jelezni, hogy a template changed és a handler restart együtt jár. Ha a C++ service hosszú warmup-ot igényel, a health check retries értékét újra kell méretezni. A retries és delay laborértékei nem számított guaranteek; a service startup próbáját a d108 és d109 szerint kell jellemezni.

47.5.9 Feladatok

47.5.9.1 1. feladat – magyarázó/analízis

Egészítse ki az inventory-t egy harmadik labhosttal, labhost-03 néven. Ne futtassa le a playbookot. Sorolja fel, hogy a serial: 1 milyen futtatási interleavinget ad, ha labhost-03 health checkje csak a második health próbálkozásra lesz 200. Adja meg, mennyiben lesz a hiba a deploy naplóban megkülönböztethető a labhost-01 sikeresen lefutó batchétől.

47.5.9.2 2. feladat – adminisztrációs/konfigurációs

Írjon egy rövid Ansible taskot, amely a lab-cpp-service configot egy YAML-címkével ellátott comment mezővel bővíti, például "deploy_env": "lab-live". A task használjon template-et, validálja a JSON-t, és csak akkor indítson restartot, ha a config ténylegesen megváltozott. Válassza meg a megfelelő module-paramétereket.

47.5.9.3 3. feladat – diagnosztikai/failure/recovery

Szimuláljon driftet a labhost-02-on úgy, hogy a config worker_threads értékét 4-ről 2-re csökkenti. Futtassa a playbookot. Rögzítse a hands-on hibakeresési lépéseket: miért changed a labhost-02 config task, miért nem changed a labhost-01-en? Futtassa ismét a playbookot, és ellenőrizze a restored state-et plusz a postconditiont: a lab-cpp-service mindkét hoston fut, a health 200, és a second run changed=0 mindkét targeten.

47.5.10 Megoldások

47.5.10.1 1. feladat megoldása

A harmadik host felvétele a hosts alá:

        labhost-03:
          ansible_host: 192.0.2.33
          ansible_user: lab

A serial: 1 miatt a batch sorrend: labhost-01, majd labhost-02, végül labhost-03. A health check until ciklusban 12 próbát végez 5 másodperces késleletéssel. Ha labhost-03 a második próbálkozásra lesz 200, akkor a host nem hibás, hanem sikeresen deployolt, csak a health task ok=1 changed=0 retries=1 jellegű naplóbejegyzést ad. A postcondition: a flotta runbook artifactban pontosan megőrzi, melyik host batchben hány health retry történt, használhatóságot adva a hibaelemzéshez.

Ezt követően a control gépen:

A handler csak labhost-02-n fut, restartálja a szolgáltatást. A második futtatás várhatóan changed=0 mindkét hoston:

labhost-02 : ok=10 changed=0 unreachable=0 failed=0

47.5.11 Rövid összefoglaló

A d235 a Linux service fleet baseline Ansible-alapú megvalósítását tanítja: inventory, role, group_vars, template validáció és handler együttesen adnak verziókövethető desired state-et. A serial: 1 és health gate korlátozza a rollout hatáskörét, a rescue a config rollback kísérletét adja. A repeated no-op és drift correction egyaránt a modulok idempotenciájára épül, nem feltételez elosztott exactly-once tranzakciót. A runbook artifact a control oldali inventory, log és hash csomagot kezeli; a remote backup ettől elkülönül.

Továbbhasznált definíciók:

  • Fleet baseline: inventory és role által meghatározott, hostokra érvényes desired state halmaz.
  • Idempotencia: ismételt alkalmazás nem hoz létre további megfigyelhető állapotváltozást.
  • Drift: a host tényleges állapotának eltérése a desired state-től.
  • Health gate: a deploy után elvégzett, retry-olt egészségellenőrzés, amely a serial rollout folytatását engedélyezi.

  • Ansible dokumentáció
  • Ubuntu Server documentation
  • libvirt

Ellenőrzési hiányok: a jelen alfejezetben nem ellenőriztem az aktuális Ansible-core systemd modulnevét (systemd vs. systemd_service), a libmicrohttpd12 csomag pontos elérhetőségét az Ubuntu 24.04 LTS amd64 baseline-ban, a systemd-analyze verify template-ben való validációs viselkedését hordozható %s helyettesítéssel, valamint a cél szolgáltatás pontos port- és config-szemantikáját. Ez utóbbi a lab saját C++ service szerződése, és a d286 technológiai térkép alapján kerül rögzítésre.
