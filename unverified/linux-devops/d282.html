57.2 Developer–platform API és operation readiness

57.2.1 Motiváció és cél

A d281 szerinti belső fejlesztői platform (internal developer platform, IDP) nem attól lesz üzemeltethető, hogy van egy Kubernetes cluster és egy CI pipeline. A platform csak akkor tud felelősséget vállalni, ha a rákerülő szolgáltatás betart egy írott, ellenőrizhető szerződést. A „majd szólok, ha valami nem megy” modell nem működik. A szenior C++ fejlesztő által írt service akkor lesz része a platformnak, ha a fejlesztő megadja, mit tud a program, a platform pedig garantálja, milyen runtime feltételeket ad hozzá. Ezt a határt nevezzük itt developer–platform API-nak. Az operational readiness (üzemeltethetőségi készenlét) ennek a szerződésnek az a tulajdonsága, hogy a szolgáltatás éles forgalomba engedhető, diagnosztikai úton állapota ellenőrizhető, hibája behatárolható és rollbackelhető.

A gyenge rendszergazdai alapokkal érkező szenior fejlesztő itt kap egy olyan ellenőrzőlistát, amely a saját alkalmazását a platform runtime, telemetry, security és data követelményeihez köti.

57.2.2 Definíció és működés

A developer–platform API az alkalmazás és a platform közötti, verziózott, leírható interface. Nem csak HTTP endpointokat jelent, hanem négy területet: runtime contract, config/data contract, artifact contract és capacity/ownership contract.

A runtime contract a folyamat életciklusát és megfigyelhetőségét írja le. A liveness (életjel) vizsgálat azt mondja meg, hogy a folyamat él-e; a readiness (kész) vizsgálat azt, hogy a szolgáltatás ténylegesen tud-e kérést fogadni. A liveness és readiness nem ugyanaz. A shutdown (leállás) contract megadja a graceful drain idejét: hány másodpercig fogadjon még kérést a folyamat a stop jelzés után. A telemetry API a metrics, log és trace kivezetését rögzíti.

A config/secret/data contract meghatározza, milyen konfigurációs séma szerint indul a szolgáltatás, mely titkokra hivatkozik környezeti változó vagy fájl-ref szerint, és milyen adatséma-verziót vár az adatbázistól. Itt fontos a schema versioning: az alkalmazás és az adatbázis sémája közötti mismatch a leggyakoribb readiness-zöld, runtime-piros hiba.

Az artifact contract az ABI/architecture/provenance kérdéseket kezeli. A sztenderd C++ build-id, az OCI image digest, az SBOM és a source revision azért kerül a szerződésbe, hogy bármely éles hibánál reprodukálható legyen, melyik natív build futott.

A capacity és dependency budget a resource request/limit, a minimális replika, a p95 latency budget és a külső függőségek listája. Ha egy függőség nincs a szerződésben, a platform diagnosztikája nem látja át a hibát.

A service ownership contract az on-call rotát, a runbook URL-t és az incident kommunikációs csatornát köti a szolgáltatáshoz. Enélkül a platform csak „valakihez” tudja delegálni a hibát.

Az operational readiness review (ORR) az a formális kapu, ahol a fenti területek mindegyikét checklist alapján ellenőrzi a platform. A checklist elem lehet required vagy exception. Az exception akkor engedhető, ha a szolgáltatás explicit, korlátozott ideig tartó kivételt kér, dokumentált kockázattal és tulajdonossal. A felülvizsgálat kimenete nem „jó” vagy „nem jó”, hanem az, hogy a szerződés pontjaira milyen bizonyíték van.

57.2.3 Kidolgozott példa: lab-order-service platformra vitele

A példában a lab-order-service nevű C++ szolgáltatást visszük platformra. A labtarget: lab-cluster Kubernetes context, lab-order namespace, a forrásrepository git@git.lab.example:lab/order-service.git. A platform contract séma itt hipotetikus, ellenőrzött szervezeti séma hiányában nem állítjuk, hogy létező nyílt specifikáció. A valós projektben a séma forrása a platform saját OpenAPI/policy definíciója kell legyen.

A szolgáltatás adatmodellje egy orders táblát használ. A fejlesztő az alábbi contract manifestet adja le a platform repository-ba:

# gitops/platform/contracts/lab-order-service.yaml
apiVersion: platform.lab.example/v1
kind: OperabilityContract
metadata:
  name: lab-order-service
  namespace: lab-order
  owner: order-oncall
spec:
  runtime:
    readiness:
      path: /readyz
      max_latency_ms: 1000
      dependencies:
        - lab-db
        - lab-object-storage
    liveness:
      path: /healthz
    shutdown:
      grace_seconds: 30
      drain_timeout_seconds: 15
    telemetry:
      metrics_path: /metrics
      log_format: json
      trace_propagation: ["w3c"]
  config:
    schema: config/v2
    secret_refs:
      - DB_CREDENTIAL
      - JWT_SIGNING_KEY
  data:
    schema_version: db/v3
    migration_strategy: expand-contract
  artifact:
    source_revision_required: true
    build_id_required: true
    image_digest_required: true
    sbom_required: true
    architectures: [amd64]
  capacity:
    resources:
      requests: {cpu: "100m", memory: "128Mi"}
      limits: {cpu: "500m", memory: "512Mi"}
    replica_min: 2
    replica_max: 6
    p95_latency_budget_ms: 200
  dependencies:
    - name: lab-db
      type: tcp
      endpoint: lab-db:5432
      protocol: postgresql
      tls: true
    - name: lab-object-storage
      type: https
      endpoint: storage.lab.example
  ownership:
    on_call_rotation: order-oncall
    runbook_url: https://wiki.lab.example/runbook/order-service
    incident_channel: "#order-incidents"

A C++ oldalon a readiness handler azt ellenőrzi, hogy a két külső függőség rövid, timeouttal védett híváson belül elérhető-e, és hogy a várt sémaverzió egyezik-e:

// lab-order-service/readiness_handler.cpp - szemléltető vázlat
struct Readiness {
    bool db_ok = false;
    bool storage_ok = false;
    bool schema_ok = false;
};

Readiness check_readiness() {
    Readiness r;
    r.db_ok = db.ping(std::chrono::milliseconds(500));
    r.storage_ok = storage.ping(std::chrono::milliseconds(500));
    if (r.db_ok) {
        r.schema_ok = db.schema_version() == "db/v3";
    }
    return r;
}

A platform a curl-t használó readiness ellenőrzést futtatja a service mesh vagy a kubelet oldaláról. A parancs explicit targettel:

# Labtarget: lab-admin CLI, context: lab-cluster, namespace: lab-order
kubectl --context lab-cluster -n lab-order \
  exec -it deploy/lab-order-service -- \
  curl --max-time 2 -s http://localhost:8080/readyz

A várható kimenet:

{"status":"ready","db":"ok","storage":"ok","schema":"db/v3"}

A platform emellett ellenőrzi a metrics pathot (/metrics) Prometheus-scrape formában, a logok JSON-struktúráját és az artifact digestet. Ha bármelyik elem hiányzik, a promotion gate nem engedi tovább a deploymentet. A readiness válasz 503 Service Unavailable akkor, ha a DB nem elérhető, a séma eltér, vagy a folyamat éppen drainel.

57.2.4 Tipikus hibák és ellenpróbák

Az egyik leggyakoribb hiba, hogy a liveness és a readiness szerepet cserél. Ha a liveness endpoint a DB-t is ellenőrzi, átmeneti DB-lassuláskor a kubelet újraindítja a folyamatot, miközben a folyamat maga egészséges volt. Ez a fölösleges újraindítás megtöri a request pathot. A readiness ellenőrizhet külső függőséget, de rövid, timeouttal védett hívásokkal kell dolgoznia, különben maga válik terhelővé.

Másik tipikus hiba, hogy a readiness cache-el. Ha a cache 10 másodpercig zöldet mond egy időközben elhalt DB-helyzet után, a platform forgalmat küld egy valójában nem működő podba. A cache használható, de a TTL-je legyen rövid, és a friss állapot mindig lekérdezhető legyen.

A config/secret hibák közül a leggyakoribb a plaintext secret beégetése a manifestbe. A contract mindig csak secret_ref-et tartalmazzon, a tényleges értéket a platform secretkezelője adja a runtime-nak. A séma verzió mismatch esete: a fejlesztő db/v4 séma szerint buildel, a platform db/v3 mellett ad adatbázist. A readiness zöld lehet, ha a schema ellenőrzés hiányzik, de a runtime SQL exceptiont dob. A schema versionnek explicit része kell legyen a readiness válasznak.

Az artifact területen gyakori hiba, hogy a C++ build-id hiányzik a release képből, mert a container build --strip vagy nem debuglink. Ilyenkor a core dump vagy a profilozó visszafejtés lehetetlen. A platformnak a build_id_required: true miatt a promóció előtt ellenőriznie kell a readelf -n kimenetét.

57.2.5 Feladatok

57.2.5.1 F1 – Readiness és shutdown contract megtervezése

A lab-order-service a fenti manifestet használja. Tervezze meg a readiness/liveness/shutdown endpointok viselkedését. Adja meg: - mely dependency-ket ellenőrzi a readiness, - milyen timeouttal, - mi a liveness válasza akkor, ha a process él, de a readiness piros, - hány másodpercig tart a graceful shutdown, és milyen sorrendben állítja le az HTTP listener és a DB connection pool.

Várt kimenet: Egy rövid szöveges specifikáció, nem kód.

57.2.5.2 F2 – Platform contract manifest készítése

Készítsen OperabilityContract-ot a lab-upload-service nevű szolgáltatáshoz. A szolgáltatás: - használ egy lab-db PostgreSQL-függőséget, - használ egy lab-object-storage HTTPS-függőséget, - titkai: UPLOAD_SIGNING_KEY, DB_CREDENTIAL, - adatséma: db/v5, - CPU/memória: request 200m/256Mi, limit 1/1Gi, - readiness maximum latency: 800 ms.

Írja be a manifestet YAML formátumban, namespace: lab-upload, owner: upload-oncall. A secret értékeket ne adja meg, csak a neveket.

57.2.5.3 F3 – Promotion failure diagnosztika

A CI/CD pipeline a lab-order-service új verzióját nem engedi promotionre. Az ORR gate az alábbi hibát adja:

promotion blocked: readiness check failed: dependency lab-db: connection refused

Melyik rétegben keresi a hibát: network, DNS, config, secret, adatbázis, vagy a readiness implementáció? Milyen adatot gyűjt, mielőtt egyetlen változtatást végrehajt? 57.2.6 Megoldások

57.2.6.1 F1 – Readiness és shutdown contract megtervezése

A liveness endpoint GET /healthz semmilyen külső függőséget nem ellenőriz. A process él, a HTTP server szál fut; a válasz mindig 200, amíg a process önmagában nem halt meg. A readiness GET /readyz ellenőrzi: - lab-db PostgreSQL: TCP connect és SELECT 1, timeout 500 ms, - lab-object-storage: HTTPS ping, timeout 500 ms, - sémaverzió: db/v3, amennyiben a DB readiness zöld.

Ha a readiness piros, a liveness akkor is 200, mert a process életben van. A graceful shutdown 30 s grace alatt a platform először leveszi a podot a Service-ből, leállítja az új kérések fogadását, majd a folyamat drain_timeout_seconds: 15 alatt befejezi a folyamatban lévő HTTP kéréseket, utána zárja a DB connection poolt, végül kilép. A leállítási sorrend nem a DB pool zárással kezdődik, mert a folyamatban lévő kérések még DB-t használnak.

57.2.6.2 F2 – Platform contract manifest készítése

Elvárás egy minimálisan valid manifest:

apiVersion: platform.lab.example/v1
kind: OperabilityContract
metadata:
  name: lab-upload-service
  namespace: lab-upload
  owner: upload-oncall
spec:
  runtime:
    readiness:
      path: /readyz
      max_latency_ms: 800
      dependencies: [lab-db, lab-object-storage]
    liveness:
      path: /healthz
    shutdown:
      grace_seconds: 30
      drain_timeout_seconds: 15
  config:
    secret_refs: [UPLOAD_SIGNING_KEY, DB_CREDENTIAL]
  data:
    schema_version: db/v5
  artifact:
    image_digest_required: true
    build_id_required: true
    sbom_required: true
    architectures: [amd64]
  capacity:
    resources:
      requests: {cpu: "200m", memory: "256Mi"}
      limits: {cpu: "1", memory: "1Gi"}
    replica_min: 2
  dependencies:
    - name: lab-db
      type: tcp
      endpoint: lab-db:5432
      protocol: postgresql
      tls: true
    - name: lab-object-storage
      type: https
      endpoint: storage.lab.example

A postcondition: a manifest a gitops/platform/contracts/ könyvtárban van, a secret mezők csak reference-k, az YAML parse-olható, a metadata.owner és a namespace kitöltött.

57.2.6.3 F3 – Promotion failure diagnosztika

A platform oldaláról a rétegek sorrendje: először a readiness implementáció, utána a service network, végül a DB maga. A connection refused tipikusan network/DNS vagy config/secret szintű, nem adatbázis túlterhelés. Adatgyűjtés egyetlen változtatás nélkül:

# Labtarget: lab-admin CLI, context: lab-cluster, namespace: lab-order
kubectl --context lab-cluster -n lab-order get endpoints lab-db
kubectl --context lab-cluster -n lab-order get pods -l app=lab-db -o wide
kubectl --context lab-cluster -n lab-order exec -it deploy/lab-order-service -- \
  curl --max-time 2 -v http://localhost:8080/readyz
kubectl --context lab-cluster -n lab-order logs deploy/lab-order-service --tail=50

A connection refused azt jelenti, hogy a service IP feloldódott, de a port nem válaszol. A lehetséges okok: a DB pod épp CrashLoopBackOff állapotban, a selector nem talál podot, vagy a credential miatt a pool nem tud connectelni. Ha a readiness logban dial tcp 10.0.0.10:5432: connect: connection refused szerepel, akkor a network path jó, a DB process nincs a porton. A javítás: a DB pod újraindítása és a restarthiba megszüntetése, például a DB_CREDENTIAL secret hiányzó kulcsának pótlása. A readiness újbóli futtatása után a válasz 200 és db: "ok". A postcondition: a promotion újra futtatva zöld, a pod readiness state Ready, és a platform logban a dependency lab-db ellenőrzés ok.

57.2.7 Rövid összefoglaló

A developer–platform API az alkalmazás és platform közötti, verziózott, írott szerződés. Az operational readiness a szolgáltatás élesre engedhetőségét biztosítja checklist és bizonyítékok alapján. A readiness endpoint ellenőrzi a függőségeket és a sémaverziót, a liveness a process életét, a shutdown a graceful drain sorrendjét. A config/secret/data contract titokrefeket és sémaverziót ír elő, az artifact contract source revisiont, build-id-t, image digestet és SBOM-ot. A capacity/dependency budget és az ownership contract a platform diagnosztikáját és az on-call felelősséget adja meg. Az operational readiness review minden pontra bizonyítékot kér, az exception dokumentált, időben korlátozott kockázat.
