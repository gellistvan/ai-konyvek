49.1 Release, environment és immutable promotion

49.1.1 Motiváció és definíció

A d240 fejezetben a CI pipeline forráskódból buildelt, tesztelt, majd image artifactot állított elő. A mostani kérdés: hogyan jut el ez az artifact a staging (átmeneti) környezetből a production (éles) környezetbe anélkül, hogy közben újrafordítanánk? A release nem csupán a bináris, hanem a forrás, a build, a konfiguráció, a deploy sorrend és az adatséma összehangolt, auditálható egysége. Az immutable promotion gondolata ugyanaz, mint a C++ ABI-ban a programkönyvtár: a build artifactot content-addressed digest azonosítja, és változatlanul hivatkozzuk minden környezetben; a környezetspecifikus viselkedést kizárólag a config és a külső binding adja.

Definíció. Release (kibocsátás): verziózott, auditálható egység, amely összeköti a source revisiont, a build identity-t, az immutable artifact digestet, az environment mappingot, a config- és adatséma-verziókat, a deployment sorrendet, az acceptance feltételeket és a rollback feltételeket. Immutable promotion (változtathatatlan előléptetés): ugyanannak a digestnek a mozgatása stagingből prodba rebuild nélkül; a környezeti eltérést kizárólag config és secret version változtatja.

49.1.2 Build once, digest és provenance

A pipeline build once elven dolgozik: a forrásból egyszer készül image artifact, amelyet a registryben a manifest digest azonosít, például sha256:<64 hexa>. Ez a digest a tartalomra hivatkozik, ezért ha újrafordítjuk ugyanazt a forrást, akkor is egy másik digest keletkezik, hacsak a build nem bitreprodukálható. A promotion akkor helyes, ha a stagingben és a prodban ugyanaz a digest jelenik meg. Ha a prodban egy új build készül, az már nem ugyanaz a release, hanem egy másik artifact, amelyet külön kell validálni.

A provenance (származási adat) rögzíti, hogy az artifact melyik source revisionből, melyik build pipeline-ból és milyen build paraméterekkel készült. Ez hasonló a debuggolt binárisnál használt build ID szerepéhez: a digest önmagában nem bizonyítja a forrást, csak a binary azonosságát; a provenance egy attestation/adatfájl, amely a CS/CI rendszer hitelesített aláírásával kapcsolja a digestet a commit hash-hez és a pipeline run azonosítójához. C++ projektnél a determinisztikus build nem garantált; ezért a promotion során a digest-összehasonlítás a mérvadó, nem a tag, a sourcediff vagy a feltételezett “ugyanaz a kód”.

49.1.3 Artifact/config/environment mapping

A release artifact és a környezeti config külön életciklusú. Az artifact tartalmazza a C++ programot és annak futási függőségeit; a config tartalmazza az endpointokat, a resource limiteket, a feature flageket, a log szinteket és a titkos referenciákat. Ugyanaz az artifact más-más configgal fut stagingben és prodban. A mapping explicit: a release manifest environmentenként megadja, melyik config revision és secret version tartozik az adott artifact digesthez.

Environment Artifact digest Config revision Secret version Acceptance gate
staging sha256:111... (dummy) config-456 staging-db-secret-v3 p95 < 100 ms; readiness 1/1
production sha256:111... (dummy) config-457 prod-db-secret-v1 canary 5% error rate < 0,01%

A config verziót a GitOps repositoryban tároljuk, így a release mapping nem csak szándék, hanem verziókövetett, ellenőrizhető állapot. A promotion során az artifact nem változik, csak a target environmentet váltjuk: a staging elfogadása után ugyanazt a digestet a prod config revisionnel alkalmazzuk.

49.1.4 Deploy sorrend és adat-/sémamigráció

A release gyakran adatbázis-sémaváltozással jár. A deploy sorrend nem tetszőleges: az adatbázis-migrációt és az alkalmazástelepítést úgy kell ütemezni, hogy közben a régi és az új alkalmazásverzió is működőképes maradjon. A leggyakoribb biztonságos minta az expand/contract (kibővítés majd szűkítés), amely lépésenként rollbackelhető:

  1. Expand: a séma bővítése visszafelé kompatibilis módon, például új oszlop NULL-ként vagy default értékkel; a régi és az új alkalmazás is tudja használni.
  2. Deploy: az új artifactot fokozatosan bevezetjük a stagingben, majd a prodban; a d198-as rolling update constraint biztosítja, hogy a rollout alatt legalább replicas−maxUnavailablereplicas - maxUnavailable pod fut.
  3. Contract: amikor az új verzió már stabilan fut, a régi sémát eltávolítjuk.

Ez a sorrend lehetővé teszi, hogy a prod rollout közben bármikor visszaálljunk az előző release-re, mert a schema még kompatibilis a régi kóddal. Ha a migráció nem kompatibilis, akkor a prod deploy előtt le kell futtatni, de ezt a release manifest külön migrációs lépésként jelöli, és a rollback tervnek tartalmaznia kell a séma-visszaállítási lépést is.

49.1.5 Staging/prod parity és failure domain

A staging és a prod két külön failure domain (meghibásodási tartomány), de a cél a parity (egyenértékűség): a staging úgy viselkedjen, mint a prod, amennyire a gyakorlatban lehetséges. A parity elemei: ugyanaz a Kubernetes API-verzió és admission policy, közel azonos resource limits, ugyanaz a monitoring és log schema, és a prodot terhelő adatsémával kompatibilis tesztadatok. A staging azonban nem fedi le a prod valódi hálózati forgalmát és adateloszlását, ezért a parity nem teljes.

A failure domain explicit: a staging és a prod ne osztozzon ugyanazon a Kubernetes clusteren, adatbázis-példányon vagy tárfiókon. Ha a staging deploy hibát okoz, az ne érintse a prodot. Másrészt a prod éles forgalmat bonyolít, így a release előléptetés előtti staging acceptance teszt csak csökkenti, de nem szünteti meg a prod kockázatot. Ezért a prod promotion gyakran canary vagy fokozatos rollout, amely a prod failure domainen belül figyeli a rendelkezésre állást és az error rátát.

49.1.6 Credential/environment boundary

A hitelesítő adatok környezeti határa kritikus: a prod secret nem kerülhet stagingbe, és a staging config nem hivatkozhat a prod DB connection stringre. A release manifest secret_version mezője environmentenként külön titokverziót azonosít. A deploy pipeline a target environment alapján oldja fel a megfelelő secretet, és soha nem keveri a credentialtartományokat. A staging és a prod között hálózati és RBAC határ is van: a staging deployer nem férhet a prod secretmanagerhez, és a prod deployer sem a stagingéhez. Ez a boundary ugyanaz a trust boundary, mint a C++ sandboxban a jogosultságcsökkentés: a folyamat csak a szükséges környezeti erőforrásokhoz fér.

49.1.7 Release manifest és audit

A release manifest egy strukturált leíró, amely egy release teljes szerződését rögzíti. Tartalma legalább:

  • release ID, source revision, build identity, artifact digest;
  • environment mapping: config revision, secret version, acceptance feltételek;
  • deployment order és data migration ID;
  • rollback target release ID;
  • owner, expiry, audit log hivatkozás.

Példa (dummy adatokkal, placeholder digest):

# release-manifest.yaml – illusztratív, nem futtatandó
release:
  id: "REL-2025-04-01-001"
  source_revision: "abc123"              # Git commit (dummy)
  build_identity: "pipeline-run-1024"    # CI run ID (dummy)
  artifact:
    image: "registry.example.com/lab/lab-payment"
    digest: "sha256:REPLACE_WITH_ARTIFACT_DIGEST"
    provenance: "build-provenance-1024.slsa"  # dummy
  environments:
    - name: staging
      config_revision: "config-456"
      secret_version: "staging-payment-db-secret-v3"
      acceptance:
        - "p95 latency < 100 ms"
        - "readiness 1/1"
      rollback_to: "REL-2025-03-01-000"
    - name: production
      config_revision: "config-457"
      secret_version: "prod-payment-db-secret-v1"
      acceptance:
        - "canary 5% error rate < 0.01%"
      rollback_to: "REL-2025-03-01-000"
  deployment_order:
    - step: "staging-deploy"
      action: "set image to digest"
    - step: "staging-acceptance"
      gate: "manual"
    - step: "prod-promote"
      action: "set image to digest"
  data_migration:
    id: "DB-MIG-123"
    expand_contract_step: "expand"
  audit:
    owner: "platform-team"
    expiry: "2025-04-08"

A release audit rögzíti: ki indította a promotiont, mikor, mi volt a desired state, és mi lett az observed state. A GitOps controller vagy a CI/CD rendszer naplózza a rollout historyt. Ez az audit biztosítja, hogy minden prod változtatás visszakereshető és reprodukálható legyen.

49.1.8 Kidolgozott példa

Tegyük fel, hogy a lab-payment C++ microservice új release-jét készítettük el a d240 pipeline-ban. A pipeline outputja a digest sha256:REPLACE_WITH_ARTIFACT_DIGEST. A release manifest a fenti. A cél: staging deploy, acceptance, majd prod promote.

Előfeltétel: a lab cluster kontextusa lab-cluster, a namespace-ek staging és prod, a deployment neve lab-payment. A target a staging namespace, a felhasználó lab-admin, jogosultság deployment frissítés.

# target: lab-cluster/staging namespace, UID: lab-admin
# Előfeltétel: a staging config revision config-456 active, secret version staging-payment-db-secret-v3 elérhető
# Desired state: a staging deployment a megadott digestet futtatja
kubectl --context lab-cluster -n staging set image deployment/lab-payment \
  app=registry.example.com/lab-payment@sha256:REPLACE_WITH_ARTIFACT_DIGEST

# Rollout állapot ellenőrzése, d198-ból ismert rolling update constraint szerint
kubectl --context lab-cluster -n staging rollout status deployment/lab-payment

# Acceptance ellenőrzés: podok image digestje megegyezik a release manifest digestgel
kubectl --context lab-cluster -n staging get pods -l app=lab-payment \
  -o jsonpath='{range .items[*]}{.metadata.name} {.spec.containers[*].image}{"\n"}{end}'

Várható kimenet: a rollout status successfully rolled out, az image digest a megadott érték. Az acceptance tesztelés (p95 latency, readiness) lefut; ha sikeres, a prod promote következik:

# target: lab-cluster/prod namespace, UID: lab-admin
# Előfeltétel: a staging acceptance sikeres, a prod config revision config-457 active
# Desired state: a prod deployment ugyanazt a digestet futtatja
kubectl --context lab-cluster -n prod set image deployment/lab-payment \
  app=registry.example.com/lab-payment@sha256:REPLACE_WITH_ARTIFACT_DIGEST

kubectl --context lab-cluster -n prod rollout status deployment/lab-payment

Rollback felkészülten:

# Rollback a korábbi release-re, ha a prod rollout hibát mutat
kubectl --context lab-cluster -n prod rollout undo deployment/lab-payment

A rollback postcondition: a prod a korábbi release digestet futtatja, az audit log bejegyzi a visszaállítást.

49.1.9 Tipikus hibák és ellenpróbák

  1. Rebuild promotion helyett. A csapat úgy dönt, hogy a prod image-et újra buildeli latest taggel, mert “gyorsabb”, vagy a staging image-en már nincs meg a legújabb commit. Ez megtöri az immutable promotiont. Ellenpróba: a prod pod image digestjét hasonlítsuk össze a staging pod digestjével; ha különböznek, akkor nem ugyanaz a release. A release manifest digest mezője pedig nem egyezik.

  2. Tag használata digest helyett. A manifestben image: registry.example.com/lab-payment:latest szerepel. A tag nem immutable, a tartalom változhat; a későbbi ellenőrzés nem bizonyítja, hogy a prodban ugyanaz fut, mint amit stagingben elfogadtunk. Ellenpróba: kubectl get pod -o jsonpath image mezőjében digestet kell látni, nem taget; a manifest pedig digestet ír elő.

  3. Prod secret staging configban. A staging test harness véletlenül a prod DB endpointot és secretet kapja, mert a config repositoryban rossz override-ot használtak. Ellenpróba: a staged pod környezeti változóiban megjelenik a prod hosztnév; a secret manager access log mutatja a staging deployer próbálkozását. A release manifest secret version mezője és a config diff gyorsan elárulja.

  4. Séma migráció nem visszafordítható. A commit közvetlenül töröl egy oszlopot a prod DB-ben, mielőtt az új artifact stabil lenne. Ha a prod rollout kudarcot vall, a régi kód már nem tud futni. Ellenpróba: a rollback terv a release manifest hiányában nem tudja elvégezni a DB visszaállítást; az expand/contract lépések hiányoznak.

  5. Staging és prod közös DB. A staging a prod adatbázishoz csatlakozik ugyanazzal a secret verzióval. A staging load tesztje tönkreteheti a prodot. Ellenpróba: a staging pod connection stringje a prod endpointot mutatja; a network policy tiltja a staging namespace és a prod DB hálózati kapcsolatát.

49.1.10 Feladatok

  1. Magyarázó feladat. Adott egy release manifest, amelyben az artifact.image értéke registry.example.com/lab-payment:latest, és a production.secret_version megegyezik a staging.secret_version értékével. Melyik két alapelvet sérti, és mi lehet a következménye?

  2. Adminisztrációs/konfigurációs feladat. Készíts egy release manifestet a saját lab-cpp-api szolgáltatásodhoz. A szolgáltatásnak legyen staging és production environmentje, külön config revision és secret version, acceptance feltételként p95 latency < 50 ms, rollback_to egy korábbi release ID. A manifest minden mezőjét töltsd ki, és add meg az environment mapping táblázatot Markdown formában.

  3. Diagnosztikai/failure feladat. A stagingben a rollout sikeres, de az acceptance p95 latency 150 ms, ami meghaladja a 100 ms limitet. A prod promote nem indul. Milyen adatokat gyűjtesz, milyen hipotéziseket vizsgálsz, és mi a rollback/előléptetési döntés? Írd le a diagnosztikai lépéseket és a végső postconditiont.

49.1.11 Megoldások

  1. Megoldás. A latest tag nem immutable: a későbbi petyhüdt image-ek nem biztosítják, hogy a prod ugyanazt futtatja, mint a stagingben validált artifact. A digest használata kötelező. A közös secret_version a staging és a prod credential boundary megsértése: a prod secretet a staging is hozzáférheti, így a staging hiba vagy a titok kiszivárgása a prodot is érinti. Következmény: a stagingben tesztelt release nem azonos a prodban futóval, illetve a prod hitelesítő adat kompromittálódhat. Postcondition: a manifestben digest szerepel, és environmentenként külön secret version.

  2. Megoldás. Példa manifest, dummy adatokkal:

# release-manifest.yaml
release:
  id: "REL-2025-04-02-001"
  source_revision: "def456"
  build_identity: "pipeline-run-2048"
  artifact:
    image: "registry.example.com/lab/lab-cpp-api"
    digest: "sha256:REPLACE_WITH_ARTIFACT_DIGEST"
    provenance: "build-provenance-2048.slsa"
  environments:
    - name: staging
      config_revision: "config-100"
      secret_version: "staging-cpp-api-secret-v1"
      acceptance:
        - "p95 latency < 50 ms"
      rollback_to: "REL-2025-03-15-000"
    - name: production
      config_revision: "config-101"
      secret_version: "prod-cpp-api-secret-v2"
      acceptance:
        - "p95 latency < 50 ms"
        - "error rate < 0.01%"
      rollback_to: "REL-2025-03-15-000"
  deployment_order:
    - step: "staging-deploy"
      action: "set image to digest"
    - step: "staging-acceptance"
      gate: "manual"
    - step: "prod-promote"
      action: "set image to digest"
  data_migration:
    id: "DB-MIG-456"
    expand_contract_step: "expand"
  audit:
    owner: "platform-team"
    expiry: "2025-04-09"

Mapping táblázat:

Environment Artifact digest Config revision Secret version Acceptance
staging sha256:... (dummy) config-100 staging-cpp-api-secret-v1 p95 < 50 ms
production sha256:... (dummy) config-101 prod-cpp-api-secret-v2 p95 < 50 ms; error rate < 0,01%

Postcondition: a manifest tartalmazza az összes kötelező mezőt, a digest placeholder konzisztens, a secret version environmentenként különböző.

  1. Megoldás. A staging rollout sikeres, de a p95 latency túllépi a limitet. Adatgyűjtés: a staging pod CPU/memória használata, a DB query idő, a hálózati RTT a staging és a DB között, a korábbi release p95 értéke ugyanazon a staging környezetben, valamint a config diff. Hipotézisek: az új kód rosszabb algoritmust használ; a config túl alacsony CPU limit miatt throttling; a DB tesztadatok nem reprezentatívak vagy a migráció zárolja a táblát. Egy változtatás: a korábbi release-t visszaállítjuk a stagingben, és újra lefuttatjuk ugyanazt a tesztet. Ha a p95 visszaáll 100 ms alá, akkor a regresszió az új artifacthoz köthető, és a prod promote nem indul. Ha a korábbi release is lassú a stagingben, akkor a staging környezet vagy a DB tesztfürt a hibás, nem az artifact. Postcondition: a staging deployment visszaáll a korábbi release-re, a hiba forrása azonosított, a prod a korábbi release-n marad; a következő release manifestben rollback_to az utolsó ismert jó release ID.

49.1.12 Rövid összefoglaló

A release nem bináris, hanem source, build, artifact digest, config, adatséma és deploy order összehangolt szerződése. Az immutable promotion során a CI pipeline egyszer buildel, és ugyanazt a digestet mozgatjuk stagingből prodba; a config és a secret version environmentenként változik. A deploy order adatbázis-séma esetén expand/contract mintát követ, hogy a rollout közben mindkét verzió kompatibilis maradjon. A staging és prod külön failure domain, de parityre törekszik; a credential boundary megakadályozza a prod titkok stagingbe szivárgását. A release manifest auditálható, és minden environment transitionhöz acceptance és rollback feltételt köt.

Továbbhasznált definíciók:

  • Immutable promotion: ugyanazon artifact digest környezetek közötti, rebuild nélküli mozgatása, kizárólag config változtatással.
  • Release manifest: strukturált leíró, amely a release artifact, config, adatséma, deploy order, acceptance és rollback feltételeit rögzíti.
  • Expand/contract migration: olyan séma migrációs minta, amely először kompatibilis bővítést hajt végre, majd a régi sémát csak az új stabil működése után távolítja el.
