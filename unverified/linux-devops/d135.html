27.5 Loss/latency/TCP diagnosztikai labor

27.5.1 Mit akarunk bizonyítani?

A „lassú a TCP” nem diagnózis. Ugyanazt az alacsony átviteli sebességet okozhatja csomagvesztés, nagy körülfordulási idő, szűk fogadóablak, alkalmazási korlát vagy CPU-terhelés. Ebben a laborban ismert hibát injektálunk, majd csomagfelvétellel, socketállapottal és számlálókkal bizonyítjuk a következményét.

A hálózati hibaemuláció (network impairment emulation) szabályozott késleltetés, veszteség vagy más továbbítási eltérés bevezetése. Linuxon a tc netem egy interfész kimeneti sorfegyelmében (queueing discipline, qdisc) késleltetheti vagy eldobhatja a csomagokat. Nem közvetlenül „TCP-hibát” állítunk be: a TCP az így módosított csomagútra reagál.

Három külön bizonyítékszintet kezelünk:

  • Beállítás: milyen netem-szabályt kértünk?
  • Megvalósulás: nőtt-e az érintett sor eldobásszámlálója?
  • Transporthatás: látható-e újraküldés, RTT-változás vagy előrehaladás-hiány?

A labor az Időtúllépések és kapcsolatkapacitás, a NIC-diagnosztikai labor és a Mérési jegyzőkönyv módszereire épít. Az alábbi eredmények várakozások, nem tényleges futtatásból származó adatok.

27.5.3 Elkülönített környezet felépítése

Először ellenőrizzük a targetet és a címtervet:

# Target: lab-tcpvm; UID 0; ugyanaz a Bash a teljes laborban.
set -euo pipefail
export LC_ALL=C
test "$(hostname -s)" = lab-tcpvm
test "$(id -u)" -eq 0

for cmd in ip tc ss nstat iperf3 tcpdump ethtool python3 timeout; do
    command -v "$cmd" >/dev/null
done

ip -4 address show
ip -4 route show table all
ip netns list

A két privát /30 tartományt vessük össze a laborinventárral. Bár nem kapcsoljuk őket a host hálózatához, ne használjunk azonos címeket más, később összeköthető laborban. Ütközésnél előbb a teljes címtervet módosítsuk.

# Módosítás: kizárólag új lab-* namespace-ek és a bizonyítékkönyvtár.
for ns in lab-tcp-c lab-tcp-r lab-tcp-s; do
    test ! -e "/run/netns/$ns"
done
OUT=/root/lab-d135
mkdir -m 0700 "$OUT"   # Meglévő könyvtárnál megáll: nem írunk felül korábbi futást.

{
    date -u '+wall_clock_UTC=%FT%TZ'
    uname -a
    dpkg-query -W iproute2 iperf3 tcpdump ethtool python3
    printf '%s\n' \
      'owner=laborresztvevo; expiry=foglalkozas_vege' \
      'TCP; P=1; offered=20 Mbit/s; measured=12 s; omitted=2 s; MTU=1500'
} > "$OUT/lab-profile.txt"

for ns in lab-tcp-c lab-tcp-r lab-tcp-s; do
    ip netns add "$ns"
    ip -n "$ns" link set lo up
done

ip -n lab-tcp-c link add lab-c0 type veth \
    peer name lab-r0 netns lab-tcp-r
ip -n lab-tcp-r link add lab-r1 type veth \
    peer name lab-s0 netns lab-tcp-s

while read -r ns dev addr; do
    ip -n "$ns" address add "$addr" dev "$dev"
    ip -n "$ns" link set "$dev" mtu 1500 up
    ip netns exec "$ns" ethtool -K "$dev" tso off gso off gro off
    ip netns exec "$ns" ethtool -k "$dev"
done > "$OUT/lab-offload.txt" <<'EOF'
lab-tcp-c lab-c0 10.203.135.1/30
lab-tcp-r lab-r0 10.203.135.2/30
lab-tcp-r lab-r1 10.203.135.5/30
lab-tcp-s lab-s0 10.203.135.6/30
EOF

ip -n lab-tcp-c route add default via 10.203.135.2
ip -n lab-tcp-s route add default via 10.203.135.5
ip netns exec lab-tcp-r sysctl -w net.ipv4.ip_forward=1

ip netns exec lab-tcp-s iperf3 -s -B 10.203.135.6 -p 5201 \
    > "$OUT/lab-server.log" 2>&1 &
sleep 1
ip netns exec lab-tcp-s ss -ltn 'sport = :5201'

Várt ellenőrzés: a szerver LISTEN állapotban figyel a kijelölt címen. Sikertelen offload-beállításnál ne folytassuk észrevétlenül: az eltérő profilt külön kell dokumentálni.

A szegmentálási és összevonási tehermentesítés (segmentation/receive offload) miatt a capture egy bejegyzése nem feltétlenül felel meg egy hálózati csomagnak. A TSO/GSO/GRO kikapcsolása itt a mérési profil része, nem általános teljesítményjavító recept. A checksum-offload továbbra is okozhat látszólag hibás ellenőrzőösszeget a küldőoldali felvételben; ez önmagában nem sérült hálózati adat bizonyítéka.

27.5.4 Egy mérés: terhelés és három megfigyelési csatorna

A workload egy TCP-adatfolyam, kliensből szerverbe, 20 Mbit/s célsebességgel. Az iperf3 -b itt a felkínált alkalmazási terhelést korlátozza; nem garantálja az elért sebességet. A két másodperces kihagyott bevezető szakaszt 12 másodperces értékelt szakasz követi.

A különböző adatkapcsolatok külön kliensportot kapnak. Az iperf3 vezérlőkapcsolata más forrásportot használhat.

# Target: lab-tcpvm; UID 0.
lab_run() {
    local tag=$1 port=$2
    local cap_c cap_s mon rc=0

    printf '%s %s port=%s\n' "$(date -u +%FT%TZ)" "$tag" "$port" \
        >> "$OUT/lab-runs.txt"

    ip netns exec lab-tcp-c nstat -az TcpRetransSegs TcpExtTCPTimeouts \
        > "$OUT/$tag.before.nstat"
    ip netns exec lab-tcp-r tc -s qdisc show \
        > "$OUT/$tag.before.tc"

    ip netns exec lab-tcp-c tcpdump -nn -i lab-c0 -s 128 -U \
        -w - 'tcp port 5201' \
        > "$OUT/$tag.client.pcap" 2> "$OUT/$tag.client.capture.log" &
    cap_c=$!
    ip netns exec lab-tcp-s tcpdump -nn -i lab-s0 -s 128 -U \
        -w - 'tcp port 5201' \
        > "$OUT/$tag.server.pcap" 2> "$OUT/$tag.server.capture.log" &
    cap_s=$!

    sleep 1
    kill -0 "$cap_c" "$cap_s"

    ip netns exec lab-tcp-c python3 -u - "$port" \
        > "$OUT/$tag.ss" <<'PY' &
import subprocess, sys, time
while True:
    print(f"monotonic_ns={time.monotonic_ns()}", flush=True)
    subprocess.run(["ss", "-tinm", f"sport = :{sys.argv[1]}"], check=True)
    time.sleep(0.2)
PY
    mon=$!

    timeout --signal=TERM --kill-after=2s 25s \
        ip netns exec lab-tcp-c iperf3 \
        -c 10.203.135.6 -p 5201 --cport "$port" \
        -P 1 -b 20M -O 2 -t 12 --connect-timeout 2000 -J \
        > "$OUT/$tag.json" 2> "$OUT/$tag.stderr" || rc=$?

    printf '%s\n' "$rc" > "$OUT/$tag.exit"
    kill -TERM "$mon"
    wait "$mon" 2>/dev/null || true
    kill -INT "$cap_c" "$cap_s"
    wait "$cap_c" || true
    wait "$cap_s" || true

    ip netns exec lab-tcp-c nstat -az TcpRetransSegs TcpExtTCPTimeouts \
        > "$OUT/$tag.after.nstat"
    ip netns exec lab-tcp-r tc -s qdisc show \
        > "$OUT/$tag.after.tc"
}

A capture-naplókban ellenőrizzük az indulást és a kernel által capture közben eldobott csomagok számát. Hiányzó handshake vagy capture-veszteség esetén a negatív bizonyíték — „nem érkezett meg” — meggyengül.

27.5.5 Kontrollált profilok és baseline-visszaállítás

# Target: lab-tcpvm, lab-tcp-r namespace; UID 0.
lab_run lab-base 40101

tc_cmd=(ip netns exec lab-tcp-r tc)
"${tc_cmd[@]}" qdisc add dev lab-r0 root netem limit 2000 delay 20ms
"${tc_cmd[@]}" qdisc add dev lab-r1 root netem limit 2000 delay 20ms
lab_run lab-delay 40102

"${tc_cmd[@]}" qdisc replace dev lab-r1 root \
    netem limit 2000 delay 20ms loss random 1%
lab_run lab-loss 40103

# Rövid, teljes adatirányú eldobás: a connect timeout ellenpróbája.
"${tc_cmd[@]}" qdisc replace dev lab-r1 root \
    netem limit 2000 delay 20ms loss 100%
lab_run lab-timeout 40104

# Rollback: csak a labor két qdisc-je.
"${tc_cmd[@]}" qdisc del dev lab-r0 root
"${tc_cmd[@]}" qdisc del dev lab-r1 root
lab_run lab-restored 40105

"${tc_cmd[@]}" -s qdisc show

Várt, nem mért viselkedés:

Profil Várakozás
Baseline Elérhető célsebesség, nincs szándékos eldobás
Késleltetés RTT körülbelül a baseline + 40 ms
Veszteség Nem feltétlenül pontosan 1% eldobás; újraküldések megjelenhetnek
Timeout A SYN nem jut el a szerverhez; nem épül fel a kapcsolat
Visszaállított Nincs netem; új kapcsolat visszatér a baseline közelébe

A timeoutpróbánál a két másodperces kapcsolódási korlátot az iperf3 kezeli; a 25 másodperces külső korlát külön biztonsági háló. A timeout 124-es státusza más esemény, mint az iperf3 saját kapcsolódási hibája. Az adatport szerinti ss-mintázás ilyenkor üres maradhat, mert már a vezérlőkapcsolat felépítése elakad.

A qdisc limit sorbejegyzéseket korlátoz. Megtelő sor további eldobást okozhat: a tc összesített dropértéke nem feltétlenül kizárólag a beállított véletlen veszteségből származik.

27.5.6 Handshake, újraküldés és ablak: a bizonyítás menete

# Target: lab-tcpvm; UID 0; csak a labor bizonyítékfájljainak olvasása.
tcpdump -nn -tttt -S -r "$OUT/lab-loss.client.pcap" 'tcp port 5201'
tcpdump -nn -tttt -S -r "$OUT/lab-loss.server.pcap" 'tcp port 5201'
cat "$OUT/lab-loss.before.nstat" "$OUT/lab-loss.after.nstat"
cat "$OUT/lab-loss.before.tc" "$OUT/lab-loss.after.tc"

A -S abszolút szekvenciaszámokat mutat. Vizsgáljuk külön a vezérlő- és adatkapcsolatot:

  1. Handshake: SYN, SYN–ACK, ACK; a SYN-ekben MSS és window scale opció.
  2. Adat: mely bájttartományt küldte el a kliens?
  3. ACK/SACK: mely tartományok érkezését jelzi a fogadó?
  4. Újraküldés: megjelenik-e később ugyanaz a bájttartomány?
  5. Keresztellenőrzés: nőtt-e a kliens TcpRetransSegs számlálója és a router dropértéke?

Az ismételt bájttartomány újraküldést jelezhet, de önmagában nem bizonyítja, hogy az eredeti adatcsomag veszett el: ACK-veszteség, átrendeződés vagy téves veszteségbecslés is lehetséges. Erős bizonyíték a router eldobása, a két capture eltérése és a socket újraküldési állapotának együttes változása.

Az ss -i rtt értéke Linux által becsült, simított RTT, milliszekundumban; nem alkalmazási válaszidő. A cwnd torlódási ablak tipikusan szegmensekben szerepel. A fogadó által hirdetett ablak (receive window, rwnd) más korlát. A capture win mezőjét a handshake-ben egyeztetett skálázással kell értelmezni; a SYN ablakmezője még nem skálázott.

Számított nagyságrendi ellenőrzés:

D=20000000bit/s×0,040s8bit/B=100000B. D = \frac{20\,000\,000\ \mathrm{bit/s}\times0{,}040\ \mathrm{s}} {8\ \mathrm{bit/B}} =100\,000\ \mathrm{B}.

Ennyi úton lévő adat szükséges a célsebességhez, ha az RTT 40 ms és az overheadet elhanyagoljuk. Ha a használható küldési ablak ennél kisebb, a célsebesség nem tartható. Az összefüggés előfeltételeit a BDP és throughput rész tárgyalja.

27.5.7 Throughput, RTT és hisztogram értékelése

Az alábbi összesítés a fogadóoldali hasznos átviteli sebességet és a periodikusan mintázott ss RTT-becslések eloszlását írja ki:

# Target: lab-tcpvm; UID 0; csak olvasás.
python3 - "$OUT" <<'PY'
import json, pathlib, re, sys
root = pathlib.Path(sys.argv[1])
bins = [(0, 5), (5, 20), (20, 35), (35, 50), (50, 100),
        (100, float("inf"))]
for tag in ("lab-base", "lab-delay", "lab-loss", "lab-restored"):
    report = json.loads((root / f"{tag}.json").read_text())
    received = report["end"]["sum_received"]
    rtts = [float(v) for v in re.findall(
        r"\brtt:([0-9.]+)/", (root / f"{tag}.ss").read_text())]
    print(tag, "receiver_Mbit/s=", received["bits_per_second"] / 1e6,
          "receiver_window_s=", received["seconds"])
    print("RTT-becslés hisztogram [ms], mintaszám:",
          [(lo, hi, sum(lo <= x < hi for x in rtts)) for lo, hi in bins])
PY

Ez nem csomagonkénti RTT-hisztogram, hanem közel 200 ms-onként vett, simított socketbecslések hisztogramja. A mintázás a teljes futást lefedi, míg az átviteli összesítés kihagyja a bevezető szakaszt; ezt a jegyzőkönyvben külön jelöljük.

A pcap időbélyege itt wall-clock-domainhez tartozik. A socketminták időpontja monoton órából származik; a kettőt nem vonjuk ki közvetlenül egymásból.

Minden profilt legalább háromszor, új kapcsolatokkal és egyedi portokkal ismételjünk. Rögzítsük a tényleges időablakot, mediánt és tartományt. A 20 Mbit/s elérése nem bizonyítja a veth maximális kapacitását: csak a korlátozott workload kiszolgálását.

# Target: lab-tcpvm; UID 0; csak a három dedikált namespace.
for ns in lab-tcp-c lab-tcp-r lab-tcp-s; do

27.5.9 Feladatok

  1. Magyarázó: Miért körülbelül 40 ms az RTT-növekedés két, egyenként 20 ms-os qdisc esetén? Miért nem kötelező csökkennie a throughputnak?
  2. Adminisztrációs: A delayprofilból kiindulva csak a lab-r0 késleltetését növeld 40 ms-ra. Mérj új kapcsolattal, majd állítsd vissza.
  3. Diagnosztikai és recovery: A throughput alig változott a lossprofilban. Bizonyítsd vagy cáfold a veszteséget három megfigyelési csatornával, majd igazold a baseline helyreállítását.

27.5.10 Megoldások

  1. Az adat és a visszatérő ACK összesen két késleltetési ponton halad át. Ha az ablak és az erőforrások elegendők, a 20 Mbit/s továbbra is teljesíthető. Postcondition: az RTT-t és a hasznos átvitelt külön metrikaként értékeled.

  2. A delayprofil aktív állapotában:

    # Target: lab-tcpvm / lab-tcp-r; UID 0.
ip netns exec lab-tcp-r tc qdisc replace dev lab-r0 root \
    netem limit 2000 delay 40ms
lab_run lab-asym 40106
ip netns exec lab-tcp-r tc qdisc replace dev lab-r0 root \
    netem limit 2000 delay 20ms

    A várakozás baseline + körülbelül 60 ms RTT. Postcondition: a mérés ezt nagyságrendileg alátámasztja, majd mindkét irány ismét 20 ms-os.

  3. Vesd össze a qdisc dropkülönbségét, a TcpRetransSegs különbségét és a két pcap megfelelő bájttartományait. A throughput önmagában nem dönt. Töröld a két qdisc-t, majd új kapcsolattal ismételj. Postcondition: nincs netem, nincs injektált eldobás, az új futás a baseline szórásával összeegyeztethető.

27.5.11 Rövid összefoglaló

A transporthiba bizonyításához a konfiguráció, a sorstatisztika, a socketállapot és a csomagfelvétel együtt szükséges. A késleltetés növekedése nem jelent automatikusan kisebb throughputot, az újraküldés pedig önmagában nem azonosítja az elveszett csomagot. A workloadot, az irányt, az offload-profilt és az értékelési időablakot minden összehasonlításban rögzíteni kell. A periodikusan mintázott, simított RTT nem csomagonkénti késleltetéseloszlás. A helyreállítást új kapcsolattal mérjük, mert a korábbi TCP-állapot átmenetileg tovább élhet a hálózati hiba megszüntetése után is.

Továbbhasznált definíciók:

  • Qdisc: interfészhez rendelt csomagsorolási és továbbítási szabály.
  • Goodput: időegység alatt átvitt hasznos alkalmazási adat.
  • Baseline: rögzített profillal felvett összehasonlítási referencia.
