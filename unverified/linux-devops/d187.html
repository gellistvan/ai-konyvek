38.2 Container lifecycle, config és shutdown

A stateful konténer üzemeltetésének legnagyobb hibája nem a build, hanem az a feltételezés, hogy a konténer elindítása és leállítása ugyanaz, mint egy processzé. A rendszergazdai szerződés itt válik el a fejlesztői buildtől: a konténerképek nem futnak, amíg explicit konfigurációval, erőforrás- és adatparaméterekkel nem hozunk létre belőlük egy futó konténert. A docker run kényelmes parancs elrejti a mögöttes lifecycle lépéseket, így a hibakeresésnél nem tudunk réteghatárt mutatni. Ez az alfejezet a konténer életciklusát a create/start/exec/stop/remove primitívektől a graceful shutdownig és a log retentionig vezeti végig, és megadja a readiness, a restart és a delete adathatásának szerződését.

38.2.1 Definíció és működés

A konténer nem VM, hanem egy Linux processzhalmaz, amelyet a container runtime (Docker, Podman, containerd+shim) hoz létre az OCI runtime spec alapján. A state machine ezért processz-szemantikát tükröz, de a runtime config réteget ad hozzá:

  • Created: a konténer leírója létrejött, a fájlrendszerrétegek előkészítve, de processz még nem fut. Létrehozó parancs: docker create (nem a docker run, mert az create+start egyben).
  • Started / Running: a PID1 elindult a konténer namespace-ben. Létrehozó parancs: docker start.
  • Paused: a processzhalmaz felfüggesztve SIGSTOP/kontinuáció szemantikával. Parancs: docker pause / unpause.
  • Exited: a PID1 kilépett valamilyen exit kóddal, a runtime megtartja a konténer metaadatait és logjait, amíg explicit docker rm nem törli.
  • Dead: a runtime belső, átmeneti állapota; felhasználói szempontból a stoptól az automatikus eltakarításig tart.

A docker exec nem hoz létre új konténert, hanem a már futó konténerbe injektál egy további processzt ugyanabban a namespace-ben. Ebből következik, hogy az exec indította processz nem él túl a konténer leállítását, és ugyanazt a PID namespace-t, hálózatot, IPC-t és mount namespace-t látja, mint a PID1.

A konténer PID1-jének speciális Linux signal szemantikája van: a kernel nem alkalmazza az implicit SIGTERM/SIGINT kezelőt, mint más processzeknél, mert feltételezi, hogy a PID1 felelős az init szerepért. Ha a PID1 egy sima C++ program, amely nem telepít signal handlert, akkor a SIGTERM nem fog leállítani, csak a SIGKILL. A Docker/Podman stop ezt úgy oldja fel, hogy alapértelmezés szerint először SIGTERM-et küld, majd --stop-timeout (alapértelmezés 10 másodperc) letelte után SIGKILL-t. Ha a programnak graceful shutdownra kell képesnek lennie, akkor a C++ kódban a SIGTERM-et el kell kapnia, drainelnie kell a munkát, és nullás exit kóddal kilépnie. Ha a bináris nem módosítható, akkor a docker run --init opcióval a runtime egy kis init processzt (például tini) indít PID1-ként, amely továbbítja a signalt a valódi alkalmazásnak.

A konténer image-nek immutable-nek kell lennie: a futáshoz szükséges konfigurációt, titkokat és adatokat a contieneő launch specjéből adunk, nem sütjük be a buildbe. A build-time ARG-ok a build engedélyezett paraméterei, a runtime ENV-ok a futás környezetét adják. A titkokat nem ENV-ben, hanem secret mounttal, tmpfs mounttal vagy legalább read-only volume-ként szolgáltatjuk. A 12-factor app elv itt a config és a code elválasztását jelenti: ugyanaz a digest, különböző környezetekben más-más config mounttal.

A resource policy a host kernel cgroup v2 rétegét használja: --memory, --cpus, --pids-limit, --device, --cap-drop és --cap-add. A default root konténer túl gyakran kap minden capabilityt; a legkisebb privilege elve szerint --cap-drop ALL és csak a szükséges --cap-add megengedett. A --user UID[:GID] a konténer processz user namespace nélkül is fontos, mert a host UID/GID látszik. A mount policy szempontjából a --read-only --tmpfs /tmp + named volume kombináció az ajánlott alap: a root filesystem csak olvasható, a hagyományos írási pontok tmpfs-en, a tartós adat néven nevezett volume-on.

A healthcheck és a restart policy különböző réteg, nem felcserélhető. A Docker HEALTHCHECK a futó konténerben futtat egy parancsot, és a starting, healthy, unhealthy állapotot kezeli. A docker run --restart (no, on-failure, always, unless-stopped) csak a konténer exit eseményére reagál, tehát ha a processz fut, de a szolgáltatás logikailag nem működik, a restart policy nem segít. A compose spec depends_on: condition: service_healthy ilyenkor biztosít startup dependency-t, de ez csak compose környezetben van. A mi baseline laborunkban a healthcheck inkább a monitoring és readiness kapuja, mint automatizált restart ok.

A graceful stop szerződés a docker stop --time és a containerd shim közötti interakció: a timeout elérése előtt a PID1-nek le kell state-elnie a portot, fel kell szabadítania a kapcsolatokat, ki kell írnia a szükséges állapotot, majd kilépnie. Ha ez nem történik meg, a SIGKILL után a kill leak, lévő kapcsolatok megszakadnak, és a logokból hiányzik az ok. A log retention a json-file driver esetén a host /var/lib/docker/containers/<id>/ alatt van, és --log-opt max-size/max-file paraméterekkel korlátozható. A docker rm csak a logot és a konténer metaadatait törli; a named volume-ok addig megmaradnak, amíg docker volume rm nem törli őket.

38.2.2 Kidolgozott példa

A következő példa egy minimális, read-only konténer, amely gracefull shutdown-t és healthchecket valósít meg. A C++ program SIGTERM-et fogad, SIGINT-et kezel, readiness válaszra /healthz endpointot ad.

Dockerfile:

# syntax=docker/dockerfile:1
FROM ubuntu:24.04 AS builder
RUN apt-get update && apt-get install -y --no-install-recommends build-essential
COPY lab-app.cpp /src/lab-app.cpp
RUN g++ -std=c++20 -Wall -Wextra -O2 /src/lab-app.cpp -o /lab-app

FROM ubuntu:24.04
RUN apt-get update && apt-get install -y --no-install-recommends libstdc++6 && rm -rf /var/lib/apt/lists/*
COPY --from=builder /lab-app /usr/local/bin/lab-app
USER 1001:1001
EXPOSE 8080
ENTRYPOINT ["/usr/local/bin/lab-app"]
HEALTHCHECK --interval=5s --timeout=3s --start-period=10s --retries=2 \
  CMD ["/usr/local/bin/lab-app", "--healthcheck"]

A C++ program vázlata (a valódi implementation nem cél, a signal kezelés és a readiness a lényeg):

#include <atomic>
#include <csignal>
#include <chrono>
#include <iostream>
#include <thread>

std::atomic<bool> running{true};

void handle_signal(int) { running.store(false); }

int main(int argc, char** argv) {
    if (argc > 1 && std::string{argv[1]} == "--healthcheck") {
        // itt ellenőrizzük a folyamat liveness-ét; kilépés 0 ha OK
        return running.load() ? 0 : 1;
    }
    std::signal(SIGTERM, handle_signal);
    std::signal(SIGINT, handle_signal);

    // a valódi HTTP szerver indítása; itt csak szimuláljuk
    while (running.load()) {
        std::this_thread::sleep_for(std::chrono::milliseconds(100));
    }
    std::cout << "draining...\n";
    std::this_thread::sleep_for(std::chrono::milliseconds(500));
    std::cout << "graceful exit\n";
    return 0;
}

A build és a futtatás a labhoston, lab-vm01, UID 1000, a labnetes repo lab-cpp-app mappájában:

# target: lab-vm01, account: labuser, uid: 1000
cd /opt/lab-cpp-app
docker build -t lab-cpp-app:1.0.0 .
docker volume create lab-cpp-app-data
docker run -d \
  --name lab-cpp-app-prod \
  --restart unless-stopped \
  --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=16m \
  --cap-drop ALL \
  --user 1001:1001 \
  --env APP_LISTEN=0.0.0.0:8080 \
  --publish 127.0.0.1:8080:8080 \
  --volume lab-cpp-app-data:/var/lib/lab-cpp-app:rw \
  --log-opt max-size=10m \
  --log-opt max-file=3 \
  lab-cpp-app:1.0.0

Várt kimenet: a docker inspect --format '{{.State.Health.Status}}' lab-cpp-app-prod 10 másodperc után healthy; curl -s http://127.0.0.1:8080/healthz 200-as válasz; docker stop --time 15 lab-cpp-app-prod nyomán a logban a draining... és graceful exit, a konténer exiting, a named volume megmarad. Annak ellenőrzése, hogy a konténer valóban read-only és nem ír a rootba:

docker exec lab-cpp-app-prod touch /should-fail
# várt: "Read-only file system"
docker exec lab-cpp-app-prod touch /tmp/should-work
# várt: sikeres

38.2.3 Hibák és ellenpróbák

A leggyakoribb hiba: a PID1 nem kezeli a SIGTERM-et, ezért a docker stop 10 másodperc után SIGKILL-t küld, és a drain, a transaction completion, a külső state update elveszik. Ellenpróba: docker stop --time 30 lab-cpp-app-prod, és közben a logot figyeljük; ha a graceful exit nem jelenik meg, a konténer a SIGKILL miatt halt meg, a docker inspect ExitCode=137. A javítás: --init használata vagy signal handler.

A másik tipikus hiba a docker rm-el az adatvesztés. A docker run névtelen volume-okkal létrehozott konténer docker rm-je nem törli az implicit volume-ot, de ha docker rm -v-t használunk, vagy a docker compose down -v, a volume eltűnik. Az explicit named volume külön életciklust él, és a docker volume inspect mutatja a független state-et. A recreate során (docker rm + docker run ugyanazzal a --volume) a named volume megőrzi az adatot.

A healthcheck hibás parancs vagy túl korai start-period esetén a konténer starting,unhealthy váltakozásában ragad. A restart policy és a healthcheck félreértése oda vezet, hogy a --restart always nem indítja újra a logikailag egészséges, de hibás endpointot mutató processzt. A diagnosztika: docker inspect --format '{{json .State.Health}}', docker logs -f.

A log retention hiánya a host lemez telítődéséhez vezet; a --log-opt max-size nélkül a json-file log növekszik, és csak a Docker daemon restartjáig rotáció nincs. A host-monitoring akkor mutat No space left on device, ha a konténer stdouteja nagy.

38.2.4 Feladatok

  1. Magyarázó feladat: Adja meg, mi a különbség a docker create, docker start, docker exec, docker stop és docker rm célja, és milyen host erőforrás (namespace, cgroup, mount, network) mikor jön létre, mikor szűnik meg. Indokolja, miért fontos a PID1 signal forwarding a stop idején.

  2. Adminisztrációs/konfigurációs feladat: Készítsen egy lab-cpp-app Dockerfile-t a fenti C++ mintából, amelyben a program SIGTERM-et kezel, /healthz endpointot ad. Futtassa read-only, --cap-drop ALL, named volume-lal. A feltétel: a docker exec lab-cpp-app-prod touch /should-fail parancsnak Read-only file system hibát, a docker exec lab-cpp-app-prod cat /var/lib/lab-cpp-app/testfile a named volume tartalmát kell mutatnia. Ellenőrizze a healthchecket, írja be a parancsokat.

  3. Diagnosztikai/failure feladat: A konténer most nem áll le 10 másodperc alatt: a docker stop lab-cpp-app-prod mindig SIGKILL-t küld. A logban nincs graceful exit. Adjon adatgyűjtési lépéseket, azonosítsa a hibát, majd javítsa --init opcióval vagy a kód módosításával. Postcondition: a docker stop --time 15 után a konténer exit code 0, a logban a graceful exit sor, a named volume sértetlen.

38.2.5 Megoldások

  1. A create létrehozza a konténer fájlrendszerrétegeit, mount névteret, cgroup entryt, hálózati névteret és a config struktúrát, de nem indít processzt. A start elindítja a PID1-et a namespacében. Az exec a futó konténerbe injektál processzt, nem hoz létre új namespacet. A stop először SIGTERM, majd timeout után SIGKILL. A rm törli a konténer metaadatait, logjait; a named volume-ot nem. A PID1 signal forwarding nélkül a konténer nem tud graceful shutdown-t végrehajtani, mert a kernel nem alkalmaz implicit handlert a PID1-re; ezért kell --init vagy a program saját kezelése.

  2. A megoldás vázlata: a fenti Dockerfile és run parancs. A named volume létrehozása: docker volume create lab-cpp-app-data, majd a volume-on elhelyezni egy testfile fájlt külön docker run --rm --volume lab-cpp-app-data:/mnt alpine sh -c 'echo ok > /mnt/testfile' paranccsal. A konténer futtatása a fent megadott paraméterekkel. Ellenőrzés:

    docker exec lab-cpp-app-prod sh -c 'cat /var/lib/lab-cpp-app/testfile'
# várt: ok
docker exec lab-cpp-app-prod touch /should-fail
# várt: Read-only file system
docker inspect --format '{{.State.Health.Status}}' lab-cpp-app-prod
# várt: healthy

    A docker rm előtti docker stop után a named volume megmarad: docker volume inspect lab-cpp-app-data CreatedAt nem változik a rm során.

  3. Adatgyűjtés: docker inspect --format '{{json .State}}' lab-cpp-app-prod, docker logs --tail 50 lab-cpp-app-prod. A hiba a SIGTERM handler hiánya. A gyors javítás: docker rm -f lab-cpp-app-prod, majd a run parancsban --init hozzáadásával újra létrehozni. A pontos javítás a C++ kódban std::signal(SIGTERM, handle_signal); behelyezése, rebuild. Postcondition: docker stop --time 15 lab-cpp-app-prod után a docker inspect --format '{{.State.ExitCode}}' lab-cpp-app-prod 0, a logban a graceful exit sor, a volume docker volume inspect lab-cpp-app-data továbbra is megvan.

38.2.6 Rövid összefoglaló

A konténer életciklusa create/start/exec/stop/remove primitívekből áll, és a runtime process-szemantikát használ. A docker run csak gyorsított create+start; a pontos működtetéshez explicit docker create, docker start és docker stop --time szükséges. A PID1 signal kezelése a graceful shutdown feltétele: ha a program nem kezeli a SIGTERM-et, a --init vagy a C++ handler beépítése kötelező. A config, titok és adat nem része az immutable image-nek; read-only root, tmpfs és named volume adja a tartós adat egyszerű modelljét. A healthcheck az alkalmazás-logikai readiness-t, a restart policy a processz-exit eseményt kezeli, ezért nem felcserélhetők.

Továbbhasznált definíciók:

  • Container state machine: a konténer állapotai: created, running, paused, exited, dead; a runtime ezeken keresztül validálja a lifecycle parancsokat.
  • Graceful shutdown: a stop során a PID1-nek SIGTERM hatására drainel, leállítja az új kéréseket, befejezi a folyamatban lévőket, majd nullás exit kóddal kilép, mielőtt a timeout SIGKILL-t ad.
  • Immutable image: a konténerkép nem tartalmaz környezet-specifikus konfigurációt vagy titkot; a runtime config env, mount és secret paraméterekkel szolgálja ki.

38.2.7 Források és ellenőrzési hiányok

Ez a lecke a megadott kiinduló dokumentációs hivatkozásokra támaszkodik, de a generálás időpontjában nem történt webes ellenőrzés. A parancsok szintaktikája és a verzió-specifikus viselkedés (például a --init, --stop-timeout, HEALTHCHECK pontos működése, a log driver defaultja) a használt Docker/Podman verziójában ellenőrizendő. A kidolgozott példa parancsai nem lettek ténylegesen futtatva; a kimenet várt/illusztratív. A Docker vs Podman CLI eltérések a példában nincsenek külön feltüntetve, de a koncepcionális modell azonos. A containerd közvetlen ctr lifecycle parancsai külön réteget képeznek, és itt nem kerültek kidolgozásra.
