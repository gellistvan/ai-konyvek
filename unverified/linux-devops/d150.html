30.5 Persistens és namespace network labor

30.5.1 Mit bizonyít a labor?

A hálózat működése és konfigurációjának tartóssága két külön állítás. A sikeres ping nem bizonyítja, hogy újraindítás után megmarad a címzés; egy helyes Netplan-fájl pedig nem bizonyítja, hogy a válaszcsomag visszatalál.

Persistens hálózati konfiguráció az a tárolt konfiguráció és aktiválási mechanizmus, amelyből a kívánt hálózati állapot újraindítás után ismét előáll. A hálózati névtér (network namespace) és a benne létrehozott interfész önmagában futásidejű objektum: nem válik tartóssá attól, hogy nevet adunk neki.

Ebben a laborban:

  • a host virtuális hídját Netplan és systemd-networkd kezeli;
  • két namespace-t, a hozzájuk tartozó veth-párokat és a forgalomformálást egy dedikált systemd-unit építi fel;
  • a DNS- és mérőfolyamatok szándékosan ideiglenesek;
  • nincs NAT, külső hálózati kijárat vagy globális tűzfalmódosítás.

A teljes topológia egy VM-en belül marad. Ez egyben közös hibaterület (failure domain): a két namespace nem jelent két független gépet.

30.5.2 Inventory, címterv és állapottulajdonos

Minden alábbi parancs célpontja: lab-netvm, izolált Ubuntu Server 24.04 LTS amd64 VM, root shell, UID 0. A reboothoz és a Netplan alkalmazásához működő VM-konzol szükséges; ne kizárólag SSH-ra támaszkodj.

Előfeltétel: telepített iproute2, netplan.io, systemd, dnsmasq-base, bind9-dnsutils, iperf3, tcpdump és nftables. A labor nem telepít csomagot, és nem indít disztribúciós DNS-szolgáltatást.

30.5.3 Baseline és profilvalidálás

Az első futás előtt minden felsorolt lab-* objektumnévnek és létrehozandó fájlnak szabadnak kell lennie. Meglévő, ismeretlen eredetű objektumot ne „takaríts el” a labor kedvéért.

  bind9-dnsutils iperf3 tcpdump nftables \

A rögzített kernel- és csomagverziók adják a tényleges futás profilját; itt nem állítunk helyettük kitalált pontos kiadásokat. Ismétléskor a profilkülönbségeket is dokumentálni kell.

Ellenőrizd az összevont Netplan-konfigurációt és az esetleges kézi networkd-/NetworkManager-profilokat. Egy széles illesztésű profil nem veheti át a labinterfészeket. Meglévő bridge-/inet-szűrés szintén befolyásolhatja a forgalmat; ilyenkor annak gazdájával kell egyeztetni, nem globálisan kikapcsolni a védelmet.

30.5.4 A persistens híd létrehozása

A renderer csak a laborhídra vonatkozik, nem változtatja meg a menedzsmentinterfész gazdáját.

# lab-netvm, UID 0; előfeltétel: konzol és szabad fájlnév.
test ! -e /etc/netplan/90-lab-net.yaml
install -m 0600 /dev/null /etc/netplan/90-lab-net.yaml
cat > /etc/netplan/90-lab-net.yaml <<'EOF'
network:
  version: 2
  bridges:
    lab-br0:
      renderer: networkd
      interfaces: []
      addresses:
        - 10.203.150.1/24
        - 10.203.151.1/32
      dhcp4: false
      dhcp6: false
      accept-ra: false
      link-local: []
      ignore-carrier: true
      optional: true
      parameters:
        stp: false
        forward-delay: 0
EOF

netplan generate
netplan get

A generate a konfiguráció feldolgozhatóságát ellenőrzi és backendfájlokat generál; nem végponti hálózati teszt. Hiba esetén ne alkalmazd a konfigurációt.

# lab-netvm, UID 0, VM-konzolról.
netplan apply
networkctl status lab-br0
ip -4 address show dev lab-br0

Várt állapot: mindkét cím látszik, a híd networkd által kezelt, a menedzsmentcím és alapértelmezett útvonal változatlan. Port nélkül még lehet NO-CARRIER; ezt az ignore-carrier mellett nem kell IP-konfigurációs hibának tekinteni.

A netplan try nem helyettesíti a konzolt és a konkrét visszaállítási tervet: virtuális eszközök és hídfunkciók visszagörgetésének vannak korlátai. Rollbackként kizárólag a saját YAML-t távolítjuk el, majd újragenerálunk és alkalmazunk; a megmaradt saját híd törlése külön lépés lehet.

30.5.5 Namespace, veth és formálás újraépítése

Az alábbi szkript kizárólag a név szerint kijelölt objektumokat kezeli. Az up újraépít: azonos végállapotot céloz, de nem megszakításmentes művelet. Ha valamelyik namespace-ben folyamat fut, megtagadja a törlést.

# lab-netvm, UID 0; előfeltétel: szabad /usr/local/sbin/lab-net.
cat > /usr/local/sbin/lab-net <<'EOF'
#!/bin/bash
set -euo pipefail

exists_ns() {
    ip netns list | grep -Eq "^$1( |$)"
}

case "${1:-}" in
down)
    for n in lab-c lab-s; do
        if exists_ns "$n" && [ -n "$(ip netns pids "$n")" ]; then
            echo "Futó folyamat a namespace-ben: $n" >&2
            exit 1
        fi
    done
    for n in lab-c lab-s; do
        if exists_ns "$n"; then ip netns del "$n"; fi
    done
    for d in lab-vc lab-vs lab-pc lab-ps; do
        if ip link show dev "$d" >/dev/null 2>&1; then
            ip link del dev "$d"
        fi
    done
    rm -f /etc/netns/lab-c/resolv.conf
    if [ -d /etc/netns/lab-c ]; then rmdir /etc/netns/lab-c; fi
    ;;
up)
    "$0" down

    # A network-online.target önmagában nem bizonyítja ezt a címet.
    for i in {1..30}; do
        if ip -4 -o address show dev lab-br0 2>/dev/null |
           grep -q 'inet 10.203.150.1/24 '; then break; fi
        sleep 1
    done
    ip -4 -o address show dev lab-br0 |
        grep -q 'inet 10.203.150.1/24 '

    for n in lab-c lab-s; do
        ip netns add "$n"
        ip -n "$n" link set lo up
    done
    ip link add lab-vc type veth peer name lab-pc
    ip link add lab-vs type veth peer name lab-ps
    ip link set lab-pc netns lab-c
    ip link set lab-ps netns lab-s

    for d in lab-vc lab-vs; do
        ip link set "$d" master lab-br0
        ip link set "$d" up
    done
    ip -n lab-c address add 10.203.150.10/24 dev lab-pc
    ip -n lab-s address add 10.203.150.20/24 dev lab-ps
    ip -n lab-c link set lab-pc up
    ip -n lab-s link set lab-ps up
    ip -n lab-s route replace 10.203.151.1/32 via 10.203.150.1

    install -d -m 0755 /etc/netns/lab-c
    printf 'nameserver 10.203.150.20\n' \
        > /etc/netns/lab-c/resolv.conf

    tc qdisc replace dev lab-vs root handle 1: htb default 10
    tc class replace dev lab-vs parent 1: classid 1:10 \
        htb rate 10mbit ceil 10mbit burst 32k
    tc qdisc replace dev lab-vs parent 1:10 handle 10: fq_codel
    ;;
*)
    echo "Használat: $0 up|down" >&2
    exit 2
    ;;
esac
EOF
chmod 0750 /usr/local/sbin/lab-net

cat > /etc/systemd/system/lab-net.service <<'EOF'
[Unit]
Description=Lab namespace topology
Wants=network-online.target
After=network-online.target systemd-networkd.service

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/local/sbin/lab-net up
ExecStopPost=/usr/local/sbin/lab-net down
TimeoutStartSec=60

[Install]
WantedBy=multi-user.target
EOF

systemctl daemon-reload
systemctl enable --now lab-net.service
systemctl status lab-net.service --no-pager
bridge link show master lab-br0
ip -n lab-s route show
tc -s class show dev lab-vs

Az ExecStopPost sikertelen indítás után is lehetőséget ad a részlegesen létrejött saját állapot eltakarítására.

Várt kimenet: active (exited), két hídport, szerveroldali /32 visszaút, valamint 1:10 HTB-osztály 10Mbit sebességgel. A formálás a lab-vs kimenő, vagyis szerver felé vezető irányát érinti; nem mindkét irány összesített korlátja.

30.5.6 DNS, visszaút és mérés

A két tesztfolyamat transient systemd-unitként indul. Ezek nem lesznek reboot után automatikusan jelen, és a topológia leállítása a függőségeik miatt őket is leállítja.

# lab-netvm, UID 0; előfeltétel: aktív lab-net.service.
systemd-run --unit=lab-net-dns --collect \
  --property=Requires=lab-net.service \
  --property=After=lab-net.service \
  /usr/sbin/ip netns exec lab-s /usr/sbin/dnsmasq \
  --keep-in-foreground --conf-file=/dev/null \
  --no-resolv --no-hosts --bind-interfaces \
  --listen-address=10.203.150.20 \
  --host-record=lab-svc.test,10.203.150.20 \
  --pid-file=/run/lab-net-dns.pid

systemd-run --unit=lab-net-iperf --collect \
  --property=Requires=lab-net.service \
  --property=After=lab-net.service \
  /usr/sbin/ip netns exec lab-s /usr/bin/iperf3 \
  -s -B 10.203.150.20

ip netns exec lab-c ping -c 3 10.203.150.20
ip netns exec lab-c dig +time=2 +tries=1 \
  @10.203.150.20 lab-svc.test A
ip netns exec lab-c dig +time=2 +tries=1 lab-svc.test A

ip route get 10.203.150.20 from 10.203.151.1
ip -n lab-s route get 10.203.151.1
ping -I 10.203.151.1 -c 3 10.203.150.20

Az első DNS-próba explicit szervert használ. A második az ip netns exec által beillesztett namespace-specifikus resolv.conf fájlt ellenőrzi. Várt válasz: NOERROR, A rekordként 10.203.150.20, DNS-szerverként ugyanez a cím.

Ez még nem bizonyítja minden alkalmazás NSS-feloldási útját. Különösen nem szabad a host 127.0.0.53 című resolverét automatikusan elérhetőnek feltételezni: a namespace saját loopbackkel rendelkezik.

A hostforrásos ping visszaútja:

lab-s → 10.203.150.1 átjáró → host helyi 10.203.151.1 cím

# lab-netvm, UID 0; ugyanaz a profil és 15 s-os TCP workload.
ip netns exec lab-c iperf3 -c 10.203.150.20 -t 15 -J \
  > /root/lab-net-evidence/forward.json
ip netns exec lab-c iperf3 -c 10.203.150.20 -t 15 -R -J \
  > /root/lab-net-evidence/reverse.json
tc -s class show dev lab-vs
tc -s qdisc show dev lab-vs
Workload Formálás az adatirányon Illusztratív fixture Tényleges mérés
Kliens → szerver 10 Mbit/s 9,4 Mbit/s JSON-ból kitöltendő
Szerver → kliens Nincs ilyen adatirányú korlát 220 Mbit/s JSON-ból kitöltendő

A fixture kitalált oktatási adat, nem benchmark és nem elvárt minimum. A fordított TCP-teszt ACK-forgalma továbbra is áthalad a formált irányon. Az alkalmazási hasznos sebesség nem azonos a qdisc által elszámolt bájtsebességgel; CPU-terhelés és protokolltöbblet is számít. A konfiguráció mellett az 1:10 osztály növekvő számlálója bizonyítja, hogy a megfelelő adatútvonalon mértünk.

30.5.7 Reboot és célzott hibakeresés

Konzolról indítsd újra a VM-et, majd ugyanazon a célponton, UID 0-ként ellenőrizz:

# lab-netvm, UID 0, konzolról; megszakítja a VM futó munkáit.
systemctl reboot
# lab-netvm, UID 0, új belépés után.
cat /proc/sys/kernel/random/boot_id
systemctl is-enabled lab-net.service
systemctl is-active lab-net.service
networkctl status lab-br0
ip -4 address show dev lab-br0
ip netns list
bridge link show master lab-br0
ip -n lab-s route show
tc class show dev lab-vs

Postcondition: új bootazonosító, változatlan kívánt címzés, két namespace, két hídport, visszaút és HTB-osztály. A számlálók újrakezdése normális. A DNS- és iperf3-próbákhoz a transient unitokat ismét indítani kell.

Tünet Hipotézis Ellenpróba
Bridge-cím van, namespace nincs Unit nem engedélyezett vagy hibás journalctl -b -u lab-net.service
IP működik, DNS nem Hiányzó folyamat vagy rossz resolverút Explicit és implicit dig összevetése
Kliensping működik, hostforrásos nem Hiányzó szerver-visszaút ip -n lab-s route get 10.203.151.1
Formálás látszólag hatástalan Rossz irány vagy interfész Forward/reverse teszt és osztályszámláló

Csomagszintű bizonyítékhoz egy második root konzolon:

# lab-netvm, UID 0; csak a saját labhíd forgalmának megfigyelése.
timeout 15 tcpdump -ni lab-br0 -c 20 'arp or icmp or port 53'

Egy megfigyelt kérés nem bizonyít sikeres válaszutat. Egyszerre egy hibahipotézist vizsgálj, egy változtatást alkalmazz, majd ismételd meg ugyanazt a próbát.

30.5.8 Cleanup és baseline-visszaállítás

Zárd be a namespace-ekben futó kézi munkameneteket. A unit leállításakor a függő tesztszolgáltatások is leállnak; ha a szkript maradó folyamatot jelez, annak tulajdonosát vizsgáld meg, ne töröld erőből az állapotot.

# lab-netvm, UID 0, konzolról; csak felsorolt laborobjektumok.
systemctl disable --now lab-net.service
/usr/local/sbin/lab-net down

rm -f /etc/systemd/system/lab-net.service
rm -f /usr/local/sbin/lab-net
rm -f /etc/netplan/90-lab-net.yaml
rm -f /run/lab-net-dns.pid
systemctl daemon-reload

netplan generate
netplan apply
if ip link show dev lab-br0 >/dev/null 2>&1; then
    ip link del dev lab-br0
fi

ip netns list
ip -br address
ip route show table all
netplan get
nft list ruleset

Ha a leállítás vagy a down hibával tér vissza, a fájltörlésekkel ne folytasd. Az evidence-könyvtár szándékosan megmarad.

A baseline-visszaállítás feltétele: nincs labor-namespace, labinterfész, labunit vagy labprofil; a menedzsmentcím, alapértelmezett útvonal, eredeti Netplan-konfiguráció és tűzfalpolicy változatlan. Az interfészindexek és dinamikus számlálók bájtszintű azonossága nem követelmény. Egy újabb reboot után sem szabad visszatérnie laborobjektumnak.

30.5.9 Feladatok

  1. Magyarázó: miért nem kell IP-forwarding a kliens–szerver teszthez, és miért kell külön visszaút a host /32 forráscíméhez?
  2. Adminisztrációs: módosítsd a formálást tartósan 20 Mbit/s-ra, majd reboot után igazold a konfigurációt és az adatúton való érvényesülését.
  3. Diagnosztikai: távolítsd el kizárólag a szerver /32 visszaútját. Bizonyítsd, hogy a kliensoldali DNS továbbra is működik, miközben a hostforrásos ping hibás; állítsd helyre a szerződést.

30.5.10 Megoldások

  1. A két namespace azonos IPv4-alhálózaton, hídon keresztül kommunikál. A /32 hostcím viszont kívül esik a szerver kapcsolt prefixén, és nincs alapértelmezett útvonala. Postcondition: az adatútban külön szerepel az L2-hídtovábbítás és a hostnak címzett IP-válasz.

  2. A /usr/local/sbin/lab-net HTB-sorában a rate és ceil egyaránt 20mbit legyen. A runtime tc class change önmagában nem tartós javítás. Reboot után ellenőrizd a tc class show dev lab-vs eredményét, indítsd újra a tesztfolyamatokat, és mérj azonos workloaddal. Postcondition: 20 Mbit/s konfigurált osztály és növekvő számláló; az alkalmazási throughput eltérését nem keverjük konfigurációvesztéssel.

  3. A célzott hibainjektálás és javítás:

    # lab-netvm, UID 0; előfeltétel: aktív topológia és DNS-tesztfolyamat.
ip -n lab-s route del 10.203.151.1/32 via 10.203.150.1
ping -I 10.203.151.1 -c 3 10.203.150.20
ip netns exec lab-c dig +time=2 +tries=1 lab-svc.test A
ip -n lab-s route get 10.203.151.1

# Rollback: visszaállítás a tárolt konfigurációval egyező állapotra.
ip -n lab-s route replace 10.203.151.1/32 via 10.203.150.1
ping -I 10.203.151.1 -c 3 10.203.150.20

    A DNS-kliens kapcsolt hálózaton van, ezért a hiba nem érinti ugyanúgy. Postcondition: a route lookup ismét átjárót talál, és a hostforrásos ping sikeres.

30.5.11 Rövid összefoglaló

A tartósságot nem a konfigurációfájl léte, hanem új boot után előálló és ellenőrzött állapot bizonyítja. A laborban a Netplan/networkd birtokolta a hidat, a dedikált systemd-unit pedig a namespace-eket, veth-párokat, visszautat és formálást. A DNS-folyamatok és mérések külön életciklust kaptak. A sikeres kapcsolt hálózati teszt nem bizonyította a más forráscímhez tartozó visszautat, a HTB-beállítás pedig önmagában nem bizonyította az adatút érintettségét. A cleanup része a konfigurációforrás eltávolítása és a baseline újbóli ellenőrzése, nem pusztán az interfészek törlése.

  • Persistens konfiguráció: újraindításkor állapotot előállító tárolt forrás és aktiválás.
  • Állapotgazda: egy hálózati objektum konfigurációjáért felelős komponens.
  • Visszaút: a válaszcsomag célcíméhez választott továbbítási út.

30.5.12 Források és ellenőrzési hiányok

Nem történt webes forrásolvasás vagy laborfuttatás. A kimenetek várt állapotok, a számpéldák jelölt fixture-adatok.

  • Netplan dokumentáció — YAML, backend és alkalmazási mechanizmusok.
  • ip-netns(8) — namespace-életciklus és /etc/netns konfiguráció.
  • ip-link(8) — veth és linkkezelés.
  • tc-htb(8) — osztályalapú formálás.

Nyitott ellenőrzési igény: a tényleges Ubuntu-image csomagverziói, a Netplan és networkd helyi profilillesztése, a meglévő szűrés, valamint a reboot- és cleanup-próba eredménye. A telepített verzióhoz tartozó helyi manoldalak elsőbbséget élveznek egy eltérő kiadás webes leírásával szemben.
