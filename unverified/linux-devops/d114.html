23.4 Automatizált hostkarbantartás szerződése

23.4.1 Motiváció

Egy háromgépes labfleetet egyesével karbantartani shell parancsokkal nagy hibalehetőség: az egyik hoston sikerül a csomagtelepítés, a másikon elhasal a sudo, a harmadik pedig ki sem derül, mert a parancssor már kilépett. A szenior C++ fejlesztő ismeri az erőforrás-életciklust és a kivételbiztos kódot: a hosztkarbantartás ugyanilyen szerződést igényel. A d114 alfejezet olyan futtatási szerződést ad, amely kis fleetre azonnal használható, per-host eredményt közöl, és a hibahatárt explicit módon kezeli. Ez a szerződés később Ansible/IaC alá is átvihető anélkül, hogy a működtetési elvet meg kellene változtatni.

23.4.2 Definíció és működés

Az automatikus hosztkarbantartási szerződés (automated host maintenance contract) a következő elemekből áll:

  • Bemenet: inventory, desired state, hitelesítési scope, hibahatár.
  • Preflight: read-only előfeltétel-ellenőrzés a hoston, például lemez, sudo, csomagforrás.
  • Check mode: módosítás nélkül megmondja, milyen állapotváltozás szükséges.
  • Apply: idempotens, célállapotot előállító lépés.
  • Per-host result: minden hostra egyértelmű állapot: ok, preflight_failed, check_failed, apply_failed vagy aborted.
  • Összegzés és hibahatár: a futtató dönt a folytatásról, a részleges hiba nem hallgatható el.
  • Audit: parancs, host, timestamp, állapotváltozás és napló.

A per-host result azért létfontosságú, mert egy többgépes futás nem globális tranzakció. Nincs distributed commit, ezért a részleges siker (partial failure) normál üzemi állapot. A runner kilépési kódja a legrosszabb hibaszint legyen, de a state fájl minden host tényleges eredményét megőrzi. A rollbacket nem a teljes fleetre kell globálisan alkalmazni, hanem a hibás hoston külön javítani, miközben a többi host ok állapota megmarad.

A párhuzamosságot (concurrency) a max_parallel paraméter és az inventory sorrend szabályozza. Egyszerre legfeljebb N hoston futhat a feladat. A stop feltétel circuit breaker (áramkör-megszakító): ha a befejezett hostok hibaaránya meghaladja a beállított limitet (például 0,50), a fennmaradó hostokat aborted állapottal zárjuk, és a futó leáll. Ez megakadályozza, hogy egy szisztémás hiba a maradék gépeken is kárt okozzon. Párhuzamos futtatásnál a breaker a befejezett hostok csúszó ablakát nézi, ezért a döntés nem pontosan az inventory sorrend, de a state fájl minden hostra determinisztikus lezárást ad.

A check mode a preflight után, de apply előtt fut. A preflight a host elérhetőségét és a minimális erőforrás-előfeltételt ellenőrzi, a check mode pedig a desired és observed állapot különbségét írja le módosítás nélkül. E kettő együtt a dry-run szerződés.

A configuration/IaC határok előképe a jelenlegi shell szerződésben: az inventory a source of truth, a preflight/apply script a konfigurációt kódolja, a state fájl az observed. Később ugyanez a három szerep lesz Ansible inventory/playbook/facts. A szerződés nem az implementáció, hanem a futtatási contract, így továbbörökíthető.

A credential minimális scope: nem root SSH-t használunk, hanem labmaint felhasználót, aki csak a szükséges scripteket futtathatja sudo -n-nel. A sudoers drop-in pontosan felsorolja a parancsokat. A retry és idempotencia összetartozik: az apply lépésnek konvergensnek kell lennie; a retry csak akkor engedett, ha a lépés idempotens, és a változtatási naplóban rögzítjük az újrapróbát. A napló tartalmazza a timestampot, hostot, usert, commandot, resultot és a preflight/check kimenet pathját.

23.4.3 Kidolgozott példa

A cél: három labhoston telepítjük a chrony csomagot és aktiváljuk a szolgáltatást. A cél nem a chrony mély ismerete, hanem a karbantartási szerződés bemutatása.

Topológia és hitelesítés:

Host SSH user sudo scope
lab-host-01 labmaint csak a két maintenance script
lab-host-02 labmaint csak a két maintenance script
lab-host-03 labmaint csak a két maintenance script

A sudoers drop-in mindhárom hoston (/etc/sudoers.d/labmaint):

labmaint ALL=(root) NOPASSWD: /usr/local/sbin/lab-preflight.sh, /usr/local/sbin/lab-apply-chrony.sh

A preflight script read-only, nem telepít és nem konfigurál:

#!/usr/bin/env bash
set -euo pipefail
if [[ $EUID -ne 0 ]]; then echo "must be root via sudo" >&2; exit 1; fi
if ! df -P / | awk 'NR==2 {exit !($5+0 < 90)}'; then
  echo "root filesystem usage >= 90%" >&2
  exit 1
fi
apt-cache policy chrony | grep -q 'Candidate:' || {
  echo "no candidate package" >&2
  exit 1
}

Az apply script támogatja a --check módot, és idempotens, mert csak akkor telepít, ha a csomag hiányzik, és a systemctl enable --now konvergens:

#!/usr/bin/env bash
set -euo pipefail
if [[ ${1:-} == "--check" ]]; then
  if dpkg-query -W -f='${Status}' chrony 2>/dev/null | grep -q 'install ok installed' \
     && systemctl is-enabled --quiet chrony \
     && systemctl is-active --quiet chrony; then
    echo "no changes needed"
  else
    echo "would install/enable/start chrony"
  fi
  exit 0
fi
if ! dpkg-query -W -f='${Status}' chrony 2>/dev/null | grep -q 'install ok installed'; then
  apt-get install -y chrony
fi
systemctl enable --now chrony

A fleet runner a lab-maint-wrapper.sh. A példa szándékosan max_parallel=1 értékkel futtat, hogy a circuit breaker determinisztikusan ellenőrizhető legyen; a max_parallel növelésével a kód ugyanazt a state fájlt és hibaküszöböt használja, de a döntés a befejezett hostok ablakán alapul.

#!/usr/bin/env bash
set -u

inventory="${1:-inventory.txt}"
max_parallel="${2:-2}"
failure_ratio_limit="${3:-0.50}"
state_file="maintenance-state.tsv"
lock="$state_file.lock"
logfile="maint-$(date -u +%Y%m%dT%H%M%SZ).log"

: > "$state_file"
log() { printf '%s\n' "$*" | tee -a "$logfile"; }

run_one() {
  host="$1"
  result=""
  if ! ssh -o BatchMode=yes -o ConnectTimeout=5 labmaint@"$host" \
      'sudo -n /usr/local/sbin/lab-preflight.sh' >"/tmp/${host}.pre" 2>&1; then
    result="preflight_failed"
  elif ! ssh -o BatchMode=yes labmaint@"$host" \
      'sudo -n /usr/local/sbin/lab-apply-chrony.sh --check' >"/tmp/${host}.check" 2>&1; then
    result="check_failed"
  elif ! ssh -o BatchMode=yes labmaint@"$host" \
      'sudo -n /usr/local/sbin/lab-apply-chrony.sh' >"/tmp/${host}.apply" 2>&1; then
    result="apply_failed"
  else
    result="ok"
  fi
  ( flock -x 200
    printf '%s\t%s\t%s\n' "$host" "$result" "$(date -u +%H:%M:%S)" >> "$state_file"
  ) 200>"$lock"
}

abort_remaining() {
  while read -r host; do
    [[ -z "$host" || "$host" == \#* ]] && continue
    ( flock -x 200
      printf '%s\taborted\t%s\n' "$host" "$(date -u +%H:%M:%S)" >> "$state_file"
    ) 200>"$lock"
  done
  log "Circuit breaker open: remaining hosts marked aborted"
}

hosts=()
while read -r host; do
  [[ -z "$host" || "$host" == \#* ]] && continue
  hosts+=("$host")
done < "$inventory"

pids=()
attempted=0
for host in "${hosts[@]}"; do
  while (( ${#pids[@]} >= max_parallel )); do
    for i in "${!pids[@]}"; do
      pid="${pids[$i]}"
      if ! kill -0 "$pid" 2>/dev/null; then
        wait "$pid" || true
        unset 'pids[i]'
      fi
    done
    if [[ -s "$state_file" ]]; then
      ended=$(awk -F'\t' 'NF{print}' "$state_file" | wc -l)
      failed=$(awk -F'\t' '$2 != "ok" {n++} END{print n+0}' "$state_file")
      ratio=$(awk -v f="$failed" -v e="$ended" 'BEGIN{if(e>0) printf "%.2f", f/e; else print "0.00"}')
      if awk -v r="$ratio" -v limit="$failure_ratio_limit" 'BEGIN{exit !(r>limit)}'; then
        log "Circuit breaker open: failed/ended=$ratio > $failure_ratio_limit"
        abort_remaining < <(printf '%s\n' "${hosts[@]}" | tail -n +$((attempted+1)))
        for pid in "${pids[@]}"; do wait "$pid" 2>/dev/null || true; done
        exit 3
      fi
    fi
    sleep 0.1
  done

  if [[ -s "$state_file" ]]; then
    ended=$(awk -F'\t' 'NF{print}' "$state_file" | wc -l)
    failed=$(awk -F'\t' '$2 != "ok" {n++} END{print n+0}' "$state_file")
    ratio=$(awk -v f="$failed" -v e="$ended" 'BEGIN{if(e>0) printf "%.2f", f/e; else print "0.00"}')
    if awk -v r="$ratio" -v limit="$failure_ratio_limit" 'BEGIN{exit !(r>limit)}'; then
      log "Circuit breaker open: failed/ended=$ratio > $failure_ratio_limit"
      abort_remaining < <(printf '%s\n' "${hosts[@]}" | tail -n +$((attempted+1)))
      for pid in "${pids[@]}"; do wait "$pid" 2>/dev/null || true; done
      exit 3
    fi
  fi

  run_one "$host" &
  pids+=("$!")
  attempted=$((attempted+1))
done

for pid in "${pids[@]}"; do
  wait "$pid" || true
done

ok_count=$(awk -F'\t' '$2=="ok"{n++}END{print n+0}' "$state_file")
success=$(awk -F'\t' '$2!="ok"{n++}END{print n+0}' "$state_file")
total=$(awk -F'\t' 'NF{print}' "$state_file" | wc -l)
log "Result total=$total ok=$ok_count not_ok=$success state_file=$state_file"
if [[ $success -gt 0 ]]; then
  exit 1
fi

Az inventory tartalma:

lab-host-01
lab-host-02
lab-host-03

Futtatás:

./lab-maint-wrapper.sh inventory.txt 1 0.50

Várható kimenet, ha minden host rendben:

maintenance-state.tsv:

lab-host-01 ok  12:00:01
lab-host-02 ok  12:00:03
lab-host-03 ok  12:00:05

Log:

Result total=3 ok=3 not_ok=0 state_file=maintenance-state.tsv

Ha a lab-host-02-n a sudoers drop-in hibás, a preflight sikertelen, az apply nem fut le, és a state fájl a következő:

lab-host-01 ok  12:00:01
lab-host-02 preflight_failed    12:00:03
lab-host-03 ok  12:00:05

A hibaarány 1/3 ≈ 0,33, ami nem nagyobb, mint 0,50, így a lab-host-03 is lefut. Ha a lab-host-01 és lab-host-02 is preflight hibát ad, a befejezett arány 2/2 = 1,0 > 0,5, a lab-host-03 indítása előtt a breaker megszakítja a futást:

lab-host-01 preflight_failed    12:00:01
lab-host-02 preflight_failed    12:00:03
lab-host-03 aborted 12:00:05

A postcondition a következő: a state fájl minden hostra zárt állapotot ad, a chrony a sikeres hostokon telepítve és fut, a hibás hostokon nem módosít, a log és a state együtt auditálható. Az ellenőrző parancs:

awk -F'\t' '$2=="ok" {ok++} $2!="ok" {bad++} END {printf "ok=%d bad=%d\n", ok, bad}' maintenance-state.tsv

23.4.4 Hibák és ellenpróbák

Gyakori hiba, hogy a runner set -e-t használ, és az első sikertelen SSH-nál kilép; ekkor a többi host állapota ismeretlen marad. A javítás: ne set -e, hanem per-host if/else; a state fájl minden host lezárását tartalmazza. Másik hiba: a circuit breaker a pending hostokat is hibának számítja; a helyes arány csak a befejezett hostokra vonatkozik, a fennmaradókat aborted jelöli. Az idempotencia hiánya: ha az apply script újraindítja a szolgáltatást anélkül, hogy a desired állapotot nézné, az újrafuttatás indokolatlan restartot okoz; a check mode itt mutatja, hogy a dpkg-query és systemctl alapján nincs szükség változtatásra.

Tünetből hipotézis: a host preflight_failed, mert a sudo -n nem fut. Adatgyűjtés: a hoston sudo -n /usr/local/sbin/lab-preflight.sh; echo $?. Egy változtatás: javítsd a sudoers drop-in-t. Ellenőrzés: futtasd újra a wrappert, a state ok.

A credential minimális scope hibája, ha a labmaint user ALL=(ALL) NOPASSWD: ALL jogot kap; ekkor egy kompromittált SSH kulcs teljes hosthozzáférést ad. A helyes: a sudoers drop-in csak a két scriptet engedi. Az audit napló hiánya azt eredményezi, hogy a változás visszafejthetetlen; mindig legyen state fájl és log, mert a shell runner nem rendelkezik natív tranzakcióval.

23.4.5 Feladatok

  1. Magyarázó feladat: Indokold meg, miért nem globális rollback kell a partial failurenél, és milyen per-host állapotokat vezetnél be. Miben különbözik a preflight_failed a apply_failed posztkondíciója?

  2. Adminisztrációs/konfigurációs feladat: Hozd létre a labmaint usert, a sudoers drop-in-t, a preflight és apply scriptet a fenti szerződés szerint. Futtasd a wrappert, és ellenőrizd a state fájlt.

  3. Diagnosztikai/failure recovery feladat: Szimulálj hibát úgy, hogy a lab-host-02 sudoers drop-in-jét átnevezed vagy kommenteled. Futtasd a wrappert, rögzítsd a state fájlt, majd állítsd vissza a drop-in-t. Igazold, hogy a log és a state egyértelműen azonosítja a hibás hostot.

23.4.6 Megoldások

  1. Megoldás: A globális rollback egy többgépes műveletnél azt jelentené, hogy a sikeres hostokat is visszaállítjuk, ami felesleges állapotváltozás és újabb hibalehetőség. Ehelyett per-host state van: ok (desired elérve), preflight_failed (beavatkozás tilos), check_failed (a dry-run nem írja le a tervet), apply_failed (a változtatás nem sikerült), aborted (a circuit breaker miatt nem indult). A preflight_failed azt jelenti, hogy nem volt szabad módosítani, a apply_failed azt, hogy a módosítás közben hiba történt; utóbbinál további hostszintű diagnosztika és rollback szükséges.

  2. Megoldás: Mindhárom hoston futtasd az alábbi parancsokat; a postcondition: labmaint létezik, a sudoers drop-in csak a két scriptre érvényes, a scriptek telepítve:

    sudo useradd --system --home /home/labmaint --shell /bin/bash labmaint
sudo mkdir -p /etc/sudoers.d
echo 'labmaint ALL=(root) NOPASSWD: /usr/local/sbin/lab-preflight.sh, /usr/local/sbin/lab-apply-chrony.sh' | sudo tee /etc/sudoers.d/labmaint
sudo chmod 440 /etc/sudoers.d/labmaint
sudo cp lab-preflight.sh /usr/local/sbin/
sudo cp lab-apply-chrony.sh /usr/local/sbin/
sudo chmod 755 /usr/local/sbin/lab-preflight.sh /usr/local/sbin/lab-apply-chrony.sh

    Ezután a runner hoston:

    ssh-copy-id labmaint@lab-host-01
ssh-copy-id labmaint@lab-host-02
ssh-copy-id labmaint@lab-host-03
./lab-maint-wrapper.sh inventory.txt 1 0.50

    Az ellenőrzés: grep chrony? Inkább awk a state fájlra, vagy SSH-n systemctl is-active chrony.

  3. Megoldás: A lab-host-02-n:

    sudo mv /etc/sudoers.d/labmaint /etc/sudoers.d/labmaint.bak
sudo visudo -c

    Futtasd a wrappert. A state fájlban lab-host-02 mellett preflight_failed jelenik meg, a log rögzíti a kimenetet. A recovery:

    sudo mv /etc/sudoers.d/labmaint.bak /etc/sudoers.d/labmaint
sudo chmod 440 /etc/sudoers.d/labmaint
sudo visudo -c
./lab-maint-wrapper.sh inventory.txt 1 0.50

    A postcondition: a state fájlban minden host ok, a chrony aktív, a hibás időszak a logból visszakövethető.

23.4.7 Rövid összefoglaló

Az automatikus hostkarbantartás akkor auditálható, ha a fleet feladatot per-host resulttal és explicit hibahatárral futtatjuk. A preflight és a check mode módosítás nélkül ellenőrzi az előfeltételeket és a desired/observed különbséget, így az apply csak akkor fut, ha a host készen áll. A circuit breaker a hibaarány alapján megállítja a maradék hostokat, a partial failure pedig nem globális rollback, hanem state fájlban rögzített lezárás. Három továbbhasznált definíció: automated host maintenance contract, per-host result, circuit breaker.
