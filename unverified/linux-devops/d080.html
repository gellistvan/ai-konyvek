16.5 Service deploy, debug és rollback labor

16.5.1 Motiváció

Egy C++ worker daemon üzemeltetése nem áll meg a bináris lefordításánál és átmásolásánál. A systemd unit a szolgáltatás futási szerződése: megmondja, melyik user futtat, milyen resource limit véd, milyen configot olvas, és hogyan áll le. Ha ezt a szerződést nem verifikáljuk deploy előtt, egy rossz Restart=on-failure beállítás könnyen úgynevezett failure loop-ba viszi a szolgáltatást: a worker elindul, hibával kilép, a systemd újraindítja, majd ismét hiba, amíg a daemon el nem éri a start limitet. A rollback sem csupán a régi bináris visszamásolása; a current release pointer, a config séma és a running process együtt alkot egy visszaállítható release-t. Ez a labor egy deploystraightforward, de teljes service contractját mutatja be.

16.5.2 Definíció és működés

A service release contract egy bináris artifactból, verzióval és build identitással ellátott manifestből, sémázott configból, valamint a systemd unitból és drop-injaiból áll. A unit verify a systemd szintaktikai és unit-tulajdonságok szerinti ellenőrzése, például systemd-analyze verify. Nem helyettesíti az alkalmazás configjának validálását; a kettő egymástól elkülönülő réteg. A failure loop azt jelenti, hogy a processz sikertelenül lép ki, a Restart= policy ismételten újraindítja, és a PID1 végül a start-limit találat után megtagadja a további indítást. A rollback itt nem fájlok visszamásolását jelenti, hanem a current symlink visszairányítását egy korábban már bevált release-re, majd a service restartját.

A systemd három fő réteget fog össze: a unit definíciót, a PID1 által létrehozott cgroupot és a journald-t. A systemctl daemon-reload újraolvassa a unit fájlokat, de a már futó service-t nem restarted. A systemctl start indítja a processzt a unit [Service] szekciója szerint, a systemctl stop leállítja, a systemctl restart stop/start párt hajt végre. A systemctl show -p Property parancs a betöltött unit aktuális observed state-jét mutatja, beleértve a PID1 által érvényesített resource control értékeket is. A journal a journalctl -u <unit> csatornán keresztül kapcsolható össze metric extractionnel.

16.5.3 Kidolgozott példa

A laborban a lab-vm1 hoston root felhasználó deployol. A worker neve lab-worker, a release 0.1.0, az előző stabil release 0.0.9. A service user lab-worker rendszerfiók, shell nélkül. A binary a /opt/lab-worker/releases/<version>/bin/lab-worker, a current symlink erre mutat, az adatkönyvtár /var/lib/lab-worker, a config /etc/lab-worker/lab-worker.toml.

Először készítsük el a usert és a könyvtárstruktúrát:

# lab-vm1, root
id lab-worker || useradd --system --home-dir /nonexistent --shell /usr/sbin/nologin lab-worker

install -d -o root -g lab-worker -m 0750 /opt/lab-worker/releases/0.1.0/bin
install -d -o root -g lab-worker -m 0750 /opt/lab-worker/releases/0.0.9/bin
install -d -o root -g lab-worker -m 0750 /etc/lab-worker
install -d -o lab-worker -g lab-worker -m 0750 /var/lib/lab-worker

Telepítsük a release artifactot. A manifest.json az artifact tulajdonosát, forrásrevisionjét és build identitását rögzíti:

# lab-vm1, root
install -m 0755 /tmp/lab-worker-0.1.0/bin/lab-worker /opt/lab-worker/releases/0.1.0/bin/lab-worker
install -m 0644 /tmp/lab-worker-0.1.0/manifest.json /opt/lab-worker/releases/0.1.0/manifest.json
ln -sfn /opt/lab-worker/releases/0.1.0 /opt/lab-worker/current
install -m 0640 /tmp/lab-worker-0.1.0/config/lab-worker.toml /etc/lab-worker/lab-worker.toml

A manifest leírja a release-t:

{
  "binary": "lab-worker",
  "version": "0.1.0",
  "source_revision": "lab-src-111",
  "build_id": "lab-worker-0.1.0-20250101",
  "artifact_owner": "platform-lab",
  "config_schema_version": 1,
  "binary_sha256": "replace-with-sha256-from-build"
}

A config megadja a listen címet, state dir-t és log szintet:

# /etc/lab-worker/lab-worker.toml
version = "0.1.0"
listen = "127.0.0.1:8081"
state_dir = "/var/lib/lab-worker"
log_level = "info"

A unit a worker futási szerződése. A ProtectSystem=full a /usr, /boot és /etc fájlrendszereket read-onlyvá teszi, a ReadWritePaths csak a state dir-t engedi. A Restart=on-failure az érdemi hibáknál újraindít, de a SuccessExitStatus= nélkül a SIGTERM-es leállást nem tekinti hibának. A drop-in a resource control értékeket adja meg:

# /etc/systemd/system/lab-worker.service
[Unit]
Description=lab-worker C++ daemon
After=network.target

[Service]
User=lab-worker
Group=lab-worker
ExecStart=/opt/lab-worker/current/bin/lab-worker --config /etc/lab-worker/lab-worker.toml
Restart=on-failure
RestartSec=2s
TimeoutStopSec=15s
KillSignal=SIGTERM
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=full
ProtectHome=true
ReadWritePaths=/var/lib/lab-worker

[Install]
WantedBy=multi-user.target
# /etc/systemd/system/lab-worker.service.d/10-resource.conf
[Service]
CPUWeight=100
MemoryHigh=512M
MemoryMax=768M
TasksMax=64
IOWeight=100

A deploy után mindig verifikáljuk a unitot és a configot:

# lab-vm1, root
systemd-analyze verify /etc/systemd/system/lab-worker.service /etc/systemd/system/lab-worker.service.d/10-resource.conf
sudo -u lab-worker /opt/lab-worker/current/bin/lab-worker --config /etc/lab-worker/lab-worker.toml --config-check
systemctl daemon-reload

A --config-check a worker saját, release-szerződésbe foglalt opciója. Ha a config sémája nem egyezik, a bináris nem indul el, és hibakódot ad.

Indítsuk el és végezzünk start/readiness/stop smoke test-et:

# lab-vm1, root
systemctl start lab-worker.service
systemctl is-active lab-worker.service
systemctl show -p ActiveState -p SubState -p MainPID lab-worker.service
journalctl -u lab-worker.service --since "-2 minutes" --no-pager
ss -lnp | grep 8081

A systemctl is-active kimenete active kell legyen, a SubState running, a MainPID egy pozitív PID, a journalban a worker listening on 127.0.0.1:8081 üzenete, a ss kimenetben a listener socket. A resource limit és permission fixture ellenőrzése:

# lab-vm1, root
systemctl show -p User -p Group -p MemoryHigh -p MemoryMax -p CPUWeight -p NoNewPrivileges -p ProtectSystem lab-worker.service
sudo -u lab-worker touch /etc/lab-worker/test
# expected: touch: cannot touch '/etc/lab-worker/test': Permission denied

A MemoryHigh a memory throttle pont, a MemoryMax a hard limit. A permission fixture mutatja, hogy a worker user nem tudja módosítani a /etc alatti configot, még ha a fájl mode engedné is, mert a ProtectSystem=full read-only mountot biztosít.

A metrikát a journalból és a systemd propertykből nyerjük ki. Ez illusztratív jq alapú extrakció:

# lab-vm1, root
journalctl -u lab-worker.service -o json --since "-10m" | jq -s 'length as $n | {log_lines_10m: $n, errors_10m: ([.[] | select(.PRIORITY <= 3)] | length)}'
systemctl show lab-worker.service -p CPUUsageNSec -p MemoryCurrent -p NRestarts | awk -F= '{gsub(/[A-Z]/,"_&"); gsub(/^_/,""); printf "lab_worker_%s %s\n", tolower($1), $2}'

Az átalakítás a rendszerd tulajdonságneveket Prometheus-szerű metrika névvé normalizálja. A pontos property nevek a labhost systemd verziójától függenek, így ezeket ellenőrizni kell.

A rollback a current symlink visszairányítása és a service restartja:

# lab-vm1, root
ln -sfn /opt/lab-worker/releases/0.0.9 /opt/lab-worker/current
systemctl restart lab-worker.service
/opt/lab-worker/current/bin/lab-worker --version
systemctl is-active lab-worker.service
journalctl -u lab-worker.service --since "-1 minute" --no-pager

A desired state: a current symlink a 0.0.9-re mutat, a --version a 0.0.9-et írja ki, a service active, a journalban nincs hiba. A rollback akkor hiteles, ha a korábbi release binárisa és configja változatlanul működik.

16.5.4 Hibák és ellenpróbák

A leggyakoribb hiba a failure loop. Tünet: a systemctl status lab-worker.service kimenetében start-limit-hit vagy a Restart számlálója gyorsan növekszik. Hipotézis: a config file sérült, a state dir hiányzik, vagy a worker exit code nem nulla. Adatgyűjtés:

# lab-vm1, root
journalctl -u lab-worker.service -n 50 --no-pager
systemctl show -p NRestarts lab-worker.service
systemctl show -p ExecMainCode -p ExecMainStatus lab-worker.service

Ha a journalban config parse failed: invalid listen szerepel, a configot javítjuk. Ezután a failure state resetelése és az indítás:

# lab-vm1, root
systemctl reset-failed lab-worker.service
systemctl start lab-worker.service
systemctl is-active lab-worker.service

A reset-failed törli a start-limit számlálót; anélkül a javított config ellenére sem indul újra a service.

A shutdown hiba tünete: a systemctl stop 15 másodpercnél tovább tart, a journalban Main process exited, code=killed, status=9/KILL. Hipotézis: a worker nem kezeli a SIGTERM-et, ezért a TimeoutStopSec=15s után a systemd SIGKILL-t küld. A diagnózist a journal és a processz exit state visszaigazolja. A javítás a worker oldalán a SIGTERM gracefull kezelése, vagy ha átmeneti mentés kell, a TimeoutStopSec és a KillSignal módosítása. A laborban a SIGKILL ténye a systemctl status kimenetéből is látszik.

A version mismatch ellenpróbája: a config version = "0.1.0", de a régi 0.0.9 binary --config-check-je elutasítja, mert a séma 0. A rollback során tehát nem elég a symlinket cserélni; a hozzá tartozó config sémát is vissza kell állítani, vagy a config verziót a régi release szerint kell megadni. Ezért tároljuk a configot a release manifestben.

16.5.5 Feladatok

16.5.5.1 F1 – Unit verify és effektív resource policy

A lab-vm1 hoston futtasd a systemd-analyze verify parancsot a lab-worker.service unitra és a drop-inra, majd a systemctl cat lab-worker.service kimenetéből állapítsd meg, hogy mekkora a MemoryHigh és MemoryMax érték. Magyarázd el, miért kell a MemoryHigh értékét a MemoryMax alá vinni, és miért nem elég a MemoryMax önmagában a jól működő terheléshez.

16.5.5.2 F2 – Release deploy, smoke test és rollback

A lab-vm1 root felhasználójaként deployold a 0.1.0 release-t a fenti manifesttel, configgal, userrel és unit drop-innal. Indítsd a service-t, ellenőrizd a readiness-t, majd rollbackelj a 0.0.9 release-re. A feladat postconditionje: a current symlink a 0.0.9-re mutat, a lab-worker --version a 0.0.9-et írja ki, a systemctl is-active lab-worker.service kimenete active, és a journalban az utolsó 2 percben nincs error szintű üzenet.

16.5.5.3 F3 – Failure loop diagnosztika és recovery

A lab-worker.toml configban állítsd a listen mezőt érvénytelen abc értékre, majd indítsd el a service-t. Diagnosztizáld a kialakult failure loopot a journal, az NRestarts és a start-limit állapot alapján. Javítsd a configot, resetteld a failure state-et, és indítsd a service-t. Igazold, hogy a service aktív, a MainPID pozitív, és a journalban a config parse failed nem szerepel.

16.5.6 Megoldások

16.5.6.1 F1 megoldása

# lab-vm1, root
systemd-analyze verify /etc/systemd/system/lab-worker.service /etc/systemd/system/lab-worker.service.d/10-resource.conf
systemctl cat lab-worker.service

A systemctl cat mutatja a unit és a drop-in összefésült képét. A MemoryHigh=512M, MemoryMax=768M. A MemoryHigh a cgroup v2 memória-throttle pontja, amely a processzt lassítja, amikor a felhasználás eléri a beállított értéket. A MemoryMax a kemény limit, amely felett a kernel OOM kill-t hajthat végre a cgroupban. Ha a MemoryHigh nagyobb a MemoryMax-nál, a throttle pont soha nem érhető el a hard limit előtt, így a MemoryHigh hatástalan. A MemoryHigh alacsonyabbra állítása a hirtelen memóriakitörés esetén ad lassulást és observability ablakot, mielőtt a MemoryMax OOM-ot váltana ki.

16.5.6.2 F2 megoldása

Postcondition: current a 0.0.9-re mutat, a --version kimenete 0.0.9, a service active, és a journal nem tartalmaz level=error bejegyzést az utóbbi percben.

16.5.6.3 F3 megoldása

A configot rontsd el:

# /etc/lab-worker/lab-worker.toml
version = "0.1.0"
listen = "abc"
state_dir = "/var/lib/lab-worker"
log_level = "info"

Indítás után a systemd Restart=on-failure miatt többször újraindítja a service-t, amíg a start-limit el nem éri:

# lab-vm1, root
systemctl start lab-worker.service
systemctl status lab-worker.service --no-pager -l
journalctl -u lab-worker.service -n 50 --no-pager
systemctl show -p NRestarts lab-worker.service
systemctl show -p ActiveState -p SubState -p Result lab-worker.service

A hipotézis: a listen mező érvénytelen, a worker --config-check és a valódi indítás is hibával kilép. A journalban config parse failed: invalid listen szerepel. A Restart számláló növekszik, a Result start-limit hibát mutat.

Javítás: a listen visszaállítása 127.0.0.1:8081-re:

# lab-vm1, root
# szerkeszd a configot
systemctl reset-failed lab-worker.service
systemctl start lab-worker.service
systemctl is-active lab-worker.service
systemctl show -p MainPID lab-worker.service
journalctl -u lab-worker.service --since "-1 minute" --no-pager

Postcondition: a service active, a MainPID pozitív, a journalban nincs config parse failed, és a NRestarts nem növekszik tovább.

16.5.7 Rövid összefoglaló

A service deploy akkor ismételhető, ha a bináris artifact, verzió, config séma, unit és drop-in egyaránt verifikált. A systemd-analyze verify a unit syntaxisát, a worker --config-check az alkalmazásconfigot validálja; a kettő együttesen védi ki a failure loopot. A resource control és permission fixture a systemctl show propertykben ellenőrizhető, a journal és a propertyk metrikává normalizálhatók. A rollback a current symlink cseréjéből és a service restartjából áll, de a config sémának is a release-hez kell tartoznia. Továbbhasznált definíciók: service release contract, failure loop, rollback symlink.

16.5.8 Források és ellenőrzési hiányok

  • systemd.io – általános systemd koncepciók; a jelen példa verzióit nem ellenőriztem.
  • Linux man-pages – systemctl(1), systemd.service(5), systemd.exec(5), systemd.resource-control(5) hivatkozások.
  • Ubuntu Server documentation – általános systemd háttér.

Ellenőrzési hiányok: a lab-worker bináris, a --config-check opció, a manifest.json séma és a config példa nem valós laborból származik, hanem illusztratív. A systemctl show --property nevek, például CPUUsageNSec, MemoryCurrent, a labhost tényleges systemd verzióján ellenőrizendők. A MemoryHigh és MemoryMax viselkedése a cgroup v2 kernelparaméterektől függ. A ss -lnp | grep 8081 kimenete csak akkor jelenik meg, ha a worker ténylegesen listenel az adott porton. A rollback példában a 0.0.9 release binárisa és configja a laborban előzetesen elérhető; a pontos artifact útvonalat a lab inventoryban rögzíteni kell.
