32.3 MTU, PMTU, loss és asymmetry

32.3.1 Miért működik a ping, miközben megáll az adatátvitel?

Egy VPN-en át elérhető szolgáltatás TCP-kapcsolata felépül, a rövid kérés sikeres, a nagyobb feltöltés viszont időtúllépéssel megszakad. Ez nem feltétlenül alkalmazáshiba: a kézfogás kis csomagjai átjuthatnak olyan útvonalon is, amelyen a nagy adatcsomagok elakadnak.

Három hipotézist kell elkülöníteni:

  • Méretfüggő hiba: bizonyos csomagméret fölött megszűnik a továbbítás.
  • Csomagvesztés (packet loss): például túlterhelés, fizikai hiba vagy szűrés miatt csomagok vesznek el.
  • Aszimmetrikus útvonal (asymmetric path): az oda- és visszaút eltér; ez önmagában szabályos, de egy útvonal- vagy tűzfelfeltételezés miatt hibává válhat.

A döntő bizonyíték nem egyetlen timeout, hanem a méretfüggés, a továbbítási pontokon látott csomagok és a vezérlőüzenetek összhangja.

32.3.2 Interfész-MTU, útvonal-MTU és visszajelzés

Az interfész-MTU (interface MTU) az interfészen továbbítható IP-csomag mérethatára, az IP-fejléccel együtt. Ethernetnél a szokásos 1500 B IP-MTU nem tartalmazza az Ethernet-fejlécet és az FCS-t.

Az útvonal-MTU (Path MTU, PMTU) az adott irányban, adott útvonalon fragmentálás nélkül továbbítható legnagyobb IP-csomag mérete. Egyszerű, beágyazás nélküli útvonalon:

PMTU[B]=miniMTUi[B] PMTU\;[\mathrm{B}] = \min_i MTU_i\;[\mathrm{B}]

Az útvonal változhat, és a két irány PMTU-ja eltérhet. A helyi ip link ezért önmagában nem bizonyítja a végpontok közötti használható méretet.

Mechanizmus IPv4 IPv6
Router fragmentálhat? Igen, ha a DF nincs beállítva Nem
Túl nagy, nem továbbítható csomag DF mellett eldobás és ICMP-visszajelzés Eldobás és ICMPv6-visszajelzés
Mérethiba visszajelzése ICMP Destination Unreachable, type 3/code 4 ICMPv6 Packet Too Big, type 2/code 0
Fragmentálás helye Forrás vagy megfelelő router Csak a forrás

A DF (Don’t Fragment) IPv4-fejlécbit megtiltja a fragmentálást. Az IPv4-fragmentumokat a cél állítja össze; egyetlen fragmentum elvesztése az egész eredeti datagram elvesztését okozhatja. A TCP-szegmentálás ettől külön mechanizmus.

A klasszikus útvonal-MTU-felderítés (Path MTU Discovery, PMTUD) a túl nagy csomagra kapott visszajelzés alapján csökkenti a küldési méretet. Ha ez a visszajelzés eltűnik, MTU-fekete lyuk (MTU black hole) alakulhat ki: a nagy csomag elvész, a küldő nem kap használható magyarázatot.

Az „ICMP tiltva van” ezért nem ártalmatlan biztonsági beállítás. Ugyanakkor nem minden unreachable üzenet mérethiba: a port-elérhetetlenség például mást jelent. A tűzfalnak a szükséges, megfelelő forgalomhoz kapcsolható visszajelzéseket kell kezelnie; nem az összes védelmet kell kikapcsolni. IPv6-ban emellett a szomszédfelderítés is ICMPv6-ra támaszkodik, ahogy az IPv6, SLAAC, ND és dual stack tárgyalja.

A csomagolási rétegben végzett MTU-felderítés, a PLPMTUD, próbákkal és nyugtázási információval ICMP nélkül is alkalmazkodhat. Ez implementációfüggő: egy sikeres TCP-átvitel nem bizonyítja, hogy az ICMP-visszaút hibátlan.

32.3.3 Overlay és VPN: a külső fejlécek is helyet foglalnak

Beágyazáskor a belső IP-csomaghoz külső fejlécek kerülnek:

MTUbelső[B]≤PMTUkülső[B]−Hbeágyazás[B] MTU_{\mathrm{belső}}\;[\mathrm{B}] \leq PMTU_{\mathrm{külső}}\;[\mathrm{B}] - H_{\mathrm{beágyazás}}\;[\mathrm{B}]

Számított példa: WireGuard-adatcsomagnál, további beágyazás és IP-opciók nélkül, az alap többlet külső IPv4 esetén 20 + 8 + 32 = 60 B, IPv6 esetén 40 + 8 + 32 = 80 B. Így 1500 B külső PMTU mellett a számított felső korlát rendre 1440 B és 1420 B. A paddinget, további tunneleket és az implementáció viselkedését külön ellenőrizni kell.

A „minden VPN MTU-ja 1420” tehát nem általános szabály. A WireGuard, tunneling és távoli hálózat működtetési szerződését a tényleges külső adatúthoz kell igazítani.

A TCP MSS-korlátozása célzott kerülőmegoldás lehet, de csak a TCP-re hat; a túl nagy UDP-datagramot vagy a hibás ICMP-kezelést nem javítja meg.

32.3.4.1 Hibainjektálás és méretfüggő ellenpróba

Még az első nagy próba előtt dobd el az első router által generált fragmentálási visszajelzést:

# Target: lab-net32 / lab-mtu-r1, root UID 0.
ip netns exec lab-mtu-r1 nft -f - <<'NFT'
table ip lab-pmtu {
    chain lab-output {
        type filter hook output priority 0; policy accept;
        icmp type 3 icmp code 4 counter drop
    }
}
NFT

# Target: lab-net32 / lab-mtu-c, root UID 0.
for size in 1200 1252 1253; do
    ip netns exec lab-mtu-c \
        ping -4 -n -M do -c 2 -W 1 -s "$size" 10.158.2.2
done

IPv4-opciók nélkül a teljes Echo Request mérete:

LIP[B]=20B+8B+Lpingpayload[B] L_{\mathrm{IP}}\;[\mathrm{B}] =20\;\mathrm{B}+8\;\mathrm{B}+L_{\mathrm{ping\ payload}}\;[\mathrm{B}]

Ping payload Teljes IP-csomag Várt eredmény
1200 B 1228 B Siker
1252 B 1280 B Siker
1253 B 1281 B Timeout, a drop-számláló nő

IPv6-nál, kiterjesztett fejlécek nélkül, ugyanezen MTU-hoz 1280 − 40 − 8 = 1232 B Echo payload tartozna.

A reprodukálható, egybájtos határ erős bizonyíték. Mégsem elég önmagában: az Echo-forgalom külön is szűrhető.

32.3.4.2 Alkalmazási kérésméret-fixture

Az alábbi kis HTTP-szerver dummy tartalmat fogad, és csak a teljes kérés beolvasása után ad sikeres választ. Ugyanabban a root shellben indítsd:

# Target: lab-net32 / lab-mtu-s, root UID 0; izolált labfolyamat.
ip netns exec lab-mtu-s python3 - <<'PY' &
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

class Handler(BaseHTTPRequestHandler):
    def do_POST(self):
        self.connection.settimeout(6)
        n = int(self.headers.get("Content-Length", "0"))
        if not 0 <= n <= 8192:
            self.send_error(413)
            return
        data = self.rfile.read(n)
        body = f"received={len(data)}\n".encode()
        self.send_response(200 if len(data) == n else 400)
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

ThreadingHTTPServer(("10.158.2.2", 8080), Handler).serve_forever()
PY
LAB_HTTP_PID=$!

ip netns exec lab-mtu-s ss -ltn 'sport = :8080'

Csak akkor folytasd, ha a socket LISTEN állapotú.

# Target: lab-net32 / lab-mtu-c, root UID 0.
lab_requests() {
    for size in 64 4096; do
        printf 'request_body_B=%s\n' "$size"
        head -c "$size" /dev/zero |
            ip netns exec lab-mtu-c curl --noproxy '*' --http1.1 \
                --connect-timeout 2 --max-time 5 -sS \
                -H 'Expect:' --data-binary @- \
                -w '\nhttp_code=%{http_code}\n' \
                http://10.158.2.2:8080/
    done
}
lab_requests

Várt: a 64 B kérésre received=64, HTTP 200 érkezik; a 4096 B kérés időtúllépéssel elakad. Ez utóbbi nem egyetlen 4096 B IP-csomag: a TCP szegmensekre bontja. A fixture alkalmazási tünetet ad, a pontos MTU-határt a DF-es ping bizonyítja.

Két további root terminálban rögzíts a router két oldalán:

# Target: lab-net32, root UID 0; egy-egy külön terminál.
ip netns exec lab-mtu-r1 tcpdump -ni lab-r1c -s 0 \
    'icmp or tcp port 8080'
# Target: lab-net32, root UID 0.
ip netns exec lab-mtu-r1 tcpdump -ni lab-r1m -s 0 \
    'icmp or tcp port 8080'

Ismételd a próbákat, majd kérdezd le a számlálót:

ip netns exec lab-mtu-r1 nft list table ip lab-pmtu

A nagy DF-es ping a bejövő interfészen látszik, a köztes linken nem; a kapcsolódó ICMP-drop számlálója nő. A nagy TCP-átvitelnél újraküldések várhatók. A TCP-capture csomagméreteit az offload miatt a tcpdump, Wireshark és captureértelmezés korlátaival értékeld.

Egyetlen javítás: távolítsd el a hibás visszajelzés-szűrést.

# Target: lab-net32 / lab-mtu-r1, root UID 0.
ip netns exec lab-mtu-r1 nft delete table ip lab-pmtu

ip netns exec lab-mtu-c \
    ping -4 -n -M do -c 2 -W 1 -s 1253 10.158.2.2
lab_requests
ip -n lab-mtu-c route get 10.158.2.2

A túl nagy DF-es ping továbbra sem lesz sikeres: most fragmentálási visszajelzés vagy a már megtanult MTU miatti helyi message too long várható. A TCP-kéréseknek viszont sikerülniük kell. Ez a helyreállítás postconditionje.

A PMTU-cache elfedheti az újrainjektált hibát. Ismételhető kísérlethez a saját névtereket építsd újra; ne a host teljes hálózati állapotát ürítsd.

32.3.5 Aszimmetrikus útvonal vagy szűrés?

A fordított útvonal ellenőrzése (reverse-path filtering, RPF) a beérkező IPv4-csomag forráscíméhez tartozó visszaút alapján ellenőriz.

Linuxon az rp_filter fontos értékei:

  • 1, strict: a megfelelő visszaútnak a beérkezési interfészre kell mutatnia;
  • 2, loose: a forrás valamely interfészen keresztül legyen elérhető;
  • 0: ez az ellenőrzés kikapcsolt.

Az effektív értéknél az all és az interfészbeállítás maximuma számít. Az IPv4-es rp_filter nem általános IPv6-védelem.

# Target: lab-net32 / lab-mtu-r1, root UID 0; csak megfigyelés.
ip -n lab-mtu-r1 rule show
ip -n lab-mtu-r1 route show table all
ip -n lab-mtu-r1 route get 10.158.1.2
ip netns exec lab-mtu-r1 sysctl \
    net.ipv4.conf.all.rp_filter \
    net.ipv4.conf.lab-r1c.rp_filter
ip netns exec lab-mtu-r1 nft list ruleset

Policy routingnál a tényleges forráscímet, bejövő interfészt és esetleges packet markot is figyelembe kell venni; egy egyszerű route get nem minden esetben modellezi a teljes döntést.

Bizonyíték Következő hipotézis / ellenpróba
Éles mérethatár, nagy DF-es csomag elakad PMTU és túl nagy csomagra adott visszajelzés vizsgálata
Kis és nagy csomagok is vesznek terhelésfüggően Queue-drop, hibaszámlálók, terhelés csökkentése
A válasz másik tűzfalon tér vissza Conntrack-állapot és szabályszámlálók mindkét eszközön
Csomag ingress capture-ben látszik, tovább nem RPF, route és tűzfal elkülönített vizsgálata
Célport zárva vagy alkalmazás hibázik RST, HTTP-válasz és szerveroldali állapot ellenőrzése

Az aszimmetria nem automatikusan hiba. Strict RPF azonban eldobhat szabályos aszimmetrikus forgalmat. Állapottartó tűzfalnál pedig a visszaút másik eszköze nem feltétlenül ismeri a kapcsolat állapotát.

Hibás route esetén a route-ot javítsd. Tervezett aszimmetriánál dokumentált, célzott loose RPF és megfelelő forráscím-szűrés lehet indokolt. A globális védelemkikapcsolás egyik esetben sem gyökérok-alapú megoldás.

32.3.6 Rollback és cleanup

Állítsd le a két foreground capture-t Ctrl+C-vel. Az eredeti root shellben:

# Target: lab-net32, root UID 0.
kill "$LAB_HTTP_PID"
wait "$LAB_HTTP_PID" 2>/dev/null || true

for n in lab-mtu-c lab-mtu-r1 lab-mtu-r2 lab-mtu-s; do
    if [ -z "$(ip netns pids "$n")" ]; then
        ip netns del "$n"
    else
        echo "Maradt folyamat; előbb azonosítsd: $n"
        ip netns pids "$n"
    fi
done
ip netns list

A névterek törlése eltávolítja saját interfészeiket, route-jaikat, nftables-állapotukat és sysctl-beállításaikat. Postcondition: egyik felsorolt labnévtér sem marad meg; a host hálózati konfigurációja változatlan.

32.3.7 Feladatok

  1. Magyarázat: 1400 B PMTU mellett mekkora a legnagyobb IPv4-, illetve IPv6-Echo payload, opciók és kiterjesztett fejlécek nélkül? Miért nem következik ebből ugyanekkora maximális HTTP-kérésméret?

  2. Konfiguráció: friss labtopológián, minden forgalompróba előtt állítsd a köztes link mindkét végét 1360 B MTU-ra. Vezesd le a két szomszédos IPv4-pingméretet, amelyekkel a határ vizsgálható. Add meg a rollbacket.

  3. Diagnózis és recovery: a kliensnél nincs ICMP-visszajelzés. Az egyik esetben nő a router lab-pmtu számlálója. A másikban a visszajelzés kilép a routerből, de másik tűzfalon halad vissza. Milyen bizonyíték és javítás szükséges?

32.3.8 Megoldások

  1. IPv4-nél 1400 − 20 − 8 = 1372 B, IPv6-nál 1400 − 40 − 8 = 1352 B. A TCP adatfolyamot szegmensekre bontja, ezért egy HTTP-kérés sok IP-csomagból állhat. Postcondition: az alkalmazási adatmennyiséget és az egyedi IP-csomag méretét külön kezeled.

  2. Friss, még PMTU-t nem tanult kliens mellett:

ip -n lab-mtu-r2 link set lab-r2m mtu 1360
ip -n lab-mtu-r1 link show lab-r1m

# Rollback az eredeti labprofilra:

    1332 B payload pontosan 1360 B IP-csomag; 1333 B már túl nagy. Postcondition: a határ mindkét interfész konfigurációjával és a csomagpróbával egyezik; a visszajelzés megléte külön dokumentált.

  3. Az első esetben a szabályszámláló és az ingress capture együtt bizonyítja a helyi visszajelzés-szűrést. Töröld a hibainjektáló táblát, majd ismételd a nagy HTTP-kérést. A második esetben rögzíts a visszaúti tűzfal előtt és után, vizsgáld a route-okat, szabályszámlálókat és kapcsolatállapotot. Az aszimmetria önmagában még nem bizonyít eldobást. Postcondition: a szükséges visszajelzés eléri a küldőt, a nagy kérés sikeres, más védelem változatlan.

32.3.9 Rövid összefoglaló

A részleges elérhetőséget nem egyetlen pinggel, hanem kontrollált méretlépcsőkkel és alkalmazási próbával vizsgáljuk. Az interfész-MTU helyi korlát; a végpontok közötti használható méretet a teljes útvonal és a beágyazási többlet határozza meg. A túl nagy csomag eldobása helyes működés lehet, a szükséges visszajelzés elvesztése viszont tartós elakadást okozhat. Az aszimmetrikus útvonal önmagában szabályos, de strict RPF-fel vagy eltérő állapottartó tűzfalakkal ütközhet. A bizonyítékhoz több megfigyelési pont, route-adatok és számlálók szükségesek. Javítás után ugyanazzal a fixture-rel ellenőrzünk.

  • PMTU: az adott útvonal és irány fragmentálás nélküli IP-mérethatára.
  • MTU black hole: méretfüggő elakadás használható méret-visszajelzés nélkül.
  • RPF: forráscím-ellenőrzés a fordított útvonal alapján.
