42.2 Admission, Pod Security és policy-as-code

42.2.1 Motiváció

Egy Kubernetes clusterben a role-based access control (RBAC) azt dönti el, hogy egy felhasználó vagy service account mely API erőforrásokat hívhatja. A RBAC azonban nem vizsgálja a kérelemben lévő objektum tartalmát: ha valaki jogosult Pod létrehozására, RBAC szempontból létrehozhat egy privileged: true konténert, ami a node kernelét közvetlenül eléri. Hasonlóképpen egy fejlesztő véletlenül hostPath volume-ot csatolhat, vagy elavult, hamarosan eltávolított API verziót használhat. A biztonsági baseline ilyenkor nem opcionális: a cluster üzemeltetője szeretné ezeket a workload követelményeket automatikusan, auditálhatóan és a GitOps folyamat részévé téve kikényszeríteni. Erre szolgál az admission control (beengedés-vezérlés) réteg, amely az API szerverben a kérelem tartalmát ellenőrzi vagy módosítja, mielőtt az etcd-ben tárolódna.

42.2.2 Admission, Pod Security és policy-as-code definíciója

Az admission controller az API szerver olyan bővítő fázisa, amely a hitelesítés és a RBAC engedélyezés után, de az etcd-be írás előtt fut. Két fő típusa van:

  • Mutating admission webhook: módosíthatja a beérkező objektumot, például default értékeket állíthat be, vagy sidecar konténert injektálhat. A webhook egy JSON patch választ ad vissza.
  • Validating admission webhook: eldönti, hogy a kérelem megfelel-e a policynek. Elutasítás esetén hibaüzenetet küld, és a kérelem nem kerül tárolásra.

A kérés útja a következő sorrendben zajlik:

Lépés Komponens Feladat Hibamód
1 authenticator Ki a hívó? 401 Unauthorized
2 authorizer Van-e joga a művelethez? 403 Forbidden
3 mutating admission Módosítható-e a kérelem? webhook error/timeout
4 validating admission Megfelel-e a policynek? 403 Forbidden, webhook error
5 etcd Tárolás, stored state létrehozás storage error

A webhook alapú admission a ValidatingWebhookConfiguration vagy MutatingWebhookConfiguration erőforrással konfigurálható. Minden webhook rendelkezik timeoutSeconds értékkel és failurePolicy mezővel, amelyek a rendelkezésre állást közvetlenül befolyásolják: ha a policy engine nem elérhető, a failurePolicy: Fail minden érintett kérést blokkol, míg a failurePolicy: Ignore csendben átengedi az ellenőrzés nélküli kéréseket. Ezt a hibamódot a policy kritikussága alapján kell megválasztani.

A Pod Security Standards (PSS) három beépített biztonsági szintet definiál:

  • privileged: nincs korlátozás, a legszabadabb; csak olyan workloadoknak, amelyek ténylegesen kernel- vagy node-hozzáférést igényelnek.
  • baseline: minimális védelem, tiltja a host namespace-eket, a privileged módot, a hostPath-ot, és korlátozza a capability-ket.
  • restricted: a legszigorúbb, a baseline-on felül előírja például a runAsNonRoot: true, seccompProfile, readOnlyRootFilesystem és capabilities.drop: ["ALL"] beállításokat.

A Pod Security Admission (PSA) a Kubernetes beépített admission controllerje, amely namespace label-ek alapján érvényesíti a PSS szinteket. A leggyakoribb label-ek:

  • pod-security.kubernetes.io/enforce: blokkolja a nem megfelelő Podokat.
  • pod-security.kubernetes.io/audit: csak audit logba ír, de nem blokkol.
  • pod-security.kubernetes.io/warn: figyelmeztetést ad a kliensnek, de nem blokkol.

A PSA a cluster verziójával együtt frissíti a beépített szabályrendszert. A namespace-en az pod-security.kubernetes.io/enforce-version label segítségével egy adott PSS verzióra rögzíthető a policy, de ez nem váltja ki az elavult API-k ellenőrzését.

A policy-as-code megközelítés azt jelenti, hogy a policy is verziózott, tesztelhető és review-zott artifact, nem pedig kézzel bekapcsolt flag. A custom policy eszközök közé tartozik:

  • ValidatingAdmissionPolicy (VAP): a kube-apiserverben futó, CEL (Common Expression Language) alapú policy, amely külön webhook szolgáltatás nélkül működik. A ValidatingAdmissionPolicy objektum tartalmazza a szabályt, a ValidatingAdmissionPolicyBinding pedig a hatókört (namespace selector, object selector) és a validationActions értékét (Deny, Warn, Audit).
  • OPA/Gatekeeper és Kyverno: önálló policy engine-ek, amelyek webhookot telepítenek, és összetett szabályokat, mutating műveleteket vagy generatív policy-ket is támogatnak. Verziójuk a deploymenttől függ, nem a Kubernetes core-tól.

Az elavult (retired) API-k capability ellenőrzése szintén admission policy feladata lehet: a VAP CEL kifejezésében a request.apiVersion és request.kind mezők hozzáférhetők, így blokkolható például egy olyan Ingress létrehozás, amely már nem támogatott API verziót használ. Ez azért fontos, mert egy deprecation előtti policy megakadályozza, hogy a workload olyan API-ra épüljön, amely a következő cluster upgrade során megszűnik.

42.2.3 Kidolgozott példa: PSA restricted és VAP hostPID tiltás

A következő példa egy izolált lab clusterben fut, ahol a context lab-admin, a namespace lab-ns. A cél: a namespace-re PSA restricted enforcement bekapcsolása, majd egy custom VAP policy, amely a hostPID beállítást tiltja. A példa a módosító parancsok mellett megadja a targetet, a várható kimenetet és a rollbacket.

Előfeltétel: a cluster rendelkezik a ValidatingAdmissionPolicy API-val (a pontos verziót ellenőrizni kell; a jelen leírás illusztratív). A lab-ns még nem létezik.

  1. Namespace létrehozása PSA restricted enforce-menttel:
# lab-ns.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: lab-ns
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/warn: restricted
kubectl --context lab-admin apply -f lab-ns.yaml

Várható kimenet: namespace/lab-ns created.

Ellenőrzés:

kubectl --context lab-admin get ns lab-ns -o yaml | grep pod-security

A kimenetben megjelennek a pod-security.kubernetes.io/enforce és warn label-ek.

  1. Próbáljunk létrehozni egy privileged Podot:
# lab-priv.yaml
apiVersion: v1
kind: Pod
metadata:
  name: lab-priv
  namespace: lab-ns
spec:
  containers:
  - name: app
    image: busybox:1.36
    securityContext:
      privileged: true
kubectl --context lab-admin apply -f lab-priv.yaml

Várható kimenet (illusztratív):

Error from server (Forbidden): pods "lab-priv" is forbidden: violates PodSecurity "restricted:latest": privileged (container "app" must not set securityContext.privileged=true)

A kérés nem kerül etcd-be, tehát a lab-priv pod nem jön létre.

Rollback: a namespace törlése vagy a PSA label eltávolítása:

kubectl --context lab-admin delete ns lab-ns
  1. Custom VAP policy a hostPID tiltására (illusztratív, verziófüggő mezőnevek):
# vap-deny-hostpid.yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: deny-hostpid
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
    - apiGroups: [""]
      apiVersions: ["v1"]
      resources: ["pods"]
  validations:
  - expression: "!has(object.spec.hostPID) || !object.spec.hostPID"
    message: "hostPID must be false"
# vap-binding-lab-ns.yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: deny-hostpid-lab-ns
spec:
  policyName: deny-hostpid
  validationActions: [Deny]
  matchResources:
    namespaceSelector:
      matchLabels:
        kubernetes.io/metadata.name: lab-ns
kubectl --context lab-admin apply -f vap-deny-hostpid.yaml
kubectl --context lab-admin apply -f vap-binding-lab-ns.yaml

Ellenőrzés: hozzunk létre egy Podot, ahol hostPID: true:

# lab-hostpid.yaml
apiVersion: v1
kind: Pod
metadata:
  name: lab-hostpid
  namespace: lab-ns
spec:
  hostPID: true
  containers:
  - name: app
    image: busybox:1.36
kubectl --context lab-admin apply -f lab-hostpid.yaml

Várható kimenet: Error from server (Forbidden): pods "lab-hostpid" is forbidden: ValidatingAdmissionPolicy 'deny-hostpid' with binding 'deny-hostpid-lab-ns' denied request: hostPID must be false (a pontos üzenet formátuma verziófüggő).

Rollback: a VAP és binding törlése:

kubectl --context lab-admin delete validatingadmissionpolicybinding deny-hostpid-lab-ns
kubectl --context lab-admin delete validatingadmissionpolicy deny-hostpid

A példa jól mutatja a rétegek közötti különbséget: a PSA restricted már eleve tiltja a hostPID-et, ezért a VAP itt redundáns, de egy éles környezetben a VAP további, org-specifikus ellenőrzést adhat, például image registry szűrést.

42.2.4 Hibák és ellenpróbák

A failurePolicy: Ignore csendben megkerüli a policy-t. Ha a webhook engine leáll, a failurePolicy: Ignore minden érintett kérést ellenőrzés nélkül átenged. Ez availability szempontból kényelmes, de security gapet nyit. Tünet: a policy által tiltott objektumok hirtelen létrejönnek, miközben a policy engine podok hibát jeleznek. A diagnózishoz kubectl get validatingwebhookconfigurations és a policy engine podok állapotát kell megnézni. A megoldás általában a policy engine magas rendelkezésre állású kialakítása, nem a tartós Ignore.

A failurePolicy: Fail availability kiesést okoz. Ha a policy engine replikái leállnak, minden új Pod vagy Deployment létrehozás blokkolódik. A hibaüzenet gyakran context deadline exceeded vagy no response from webhook. Ezért a kritikus validáló webhookok mögé legalább két replika, PodDisruptionBudget és readiness probe szükséges. A timeout érték ne legyen túl alacsony, mert a kiértékelés terhelés alatt lassulhat.

A PSA nem retroaktív. Ha a namespace-en bekapcsoljuk a restricted enforcementet, a már futó Podok nem kerülnek újra ellenőrzésre. A rollout során a meglévő nem megfelelő workloadokat külön fel kell deríteni, például kubectl get pods -A -o json és PSS ellenőrzéssel, majd újra kell indítani őket.

A VAP CEL kifejezés hibája blokkolhat. Ha a CEL kifejezés rossz típusú, például !has(object.spec.hostPID) || !object.spec.hostPID helyett object.spec.hostPID == false, és a mező hiányzik, a kiértékelés hibát ad. failurePolicy: Fail esetén az ilyen hiba minden kérést blokkol. Ezért minden VAP policy-t dry-runnal kell tesztelni.

Az exception túl széles. A pod-security.kubernetes.io/exempt: true label a namespace összes Podját mentesíti a PSA alól, ezért csak időhöz kötött, dokumentált exception esetén használható. Az exception ownership hiánya compliance problémát jelent; a policy rollout során az exception-öket is verziózni és tulajdonost rendelni kell.

42.2.6 Megoldások

42.2.6.1 1. megoldás

A PSA a Kubernetes beépített admission controllerje, amely a PSS három standard szintjét (privileged, baseline, restricted) érvényesíti namespace label-ek alapján. Előnye, hogy nincs külön webhook komponens, ezért nincs hálózati timeout vagy fail open probléma; a szabályok a cluster verziójával együtt frissülnek. A custom policy viszont egyedi, org-specifikus feltételeket tud ellenőrizni, például:

  • csak meghatározott container registry-ből származó image engedélyezése;
  • bizonyos label-ek meglétének előírása;
  • elavult API verziók blokkolása (request.apiVersion);
  • komplex, több mezőt összehasonlító szabályok.

A PSA restricted például előírja a runAsNonRoot-ot, de nem tudja ellenőrizni, hogy a konténer image egy belső registryből származik-e. Ehhez OPA/Gatekeeper, Kyverno vagy VAP szükséges, amely az image mezőt vizsgálja. A PSA tehát a standard biztonsági baseline-t, a custom policy az üzleti és platform-specifikus követelményeket kényszeríti ki.

42.2.6.2 2. megoldás

A VAP policy hostNetwork tiltására:

# vap-deny-hostnetwork-audit.yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: deny-hostnetwork
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
    - apiGroups: [""]
      apiVersions: ["v1"]
      resources: ["pods"]
  validations:
  - expression: "!has(object.spec.hostNetwork) || !object.spec.hostNetwork"
    message: "hostNetwork must be false"
# vap-binding-lab-ns-audit.yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: deny-hostnetwork-lab-ns
spec:
  policyName: deny-hostnetwork
  validationActions: [Audit]
  matchResources:
    namespaceSelector:
      matchLabels:
        kubernetes.io/metadata.name: lab-ns
kubectl --context lab-admin apply -f vap-deny-hostnetwork-audit.yaml
kubectl --context lab-admin apply -f vap-binding-lab-ns-audit.yaml

Ezután dry-run teszttel ellenőrizzük, hogy a policy észlelné-e a tiltott beállítást:

kubectl --context lab-admin apply --dry-run=server -f lab-hostnetwork.yaml

Várható kimenet audit módban: a kérés nem blokkolódik, de az audit logban megjelenik a figyelmeztetés. A dry-run nem hozza létre az objektumot, de a policy kiértékelés lefut.

Ha az audit eredmények megfelelőek, váltunk Deny-re:

# módosított binding: validationActions: [Deny]
kubectl --context lab-admin apply -f vap-binding-lab-ns-deny.yaml

Postcondition: a hostNetwork: true Pod létrehozása a lab-ns-ben Forbidden hibával elutasításra kerül; a hostNetwork nélküli Podok továbbra is létrehozhatók.

42.2.6.3 3. megoldás

Diagnosztikai lépések:

kubectl --context lab-admin get validatingwebhookconfigurations

Keressük meg a failurePolicy: Fail webhookot és a hozzá tartozó service-t.

kubectl --context lab-admin get pods -n policy-engine
kubectl --context lab-admin get events -n policy-engine --sort-by=.lastTimestamp

Ha a policy engine podok CrashLoopBackOff vagy Pending állapotban vannak, a hiba okát a pod logok mutatják. A recovery első lépése a deployment újraindítása vagy skálázása:

kubectl --context lab-admin rollout restart deployment/policy-engine -n policy-engine
kubectl --context lab-admin rollout status deployment/policy-engine -n policy-engine

Ezután ismételjük meg a Deployment létrehozást a lab-ns-ben:

kubectl --context lab-admin apply -f deployment.yaml

Ha a kérés sikeres, a webhook újra elérhető.

A failurePolicy: Ignore ideiglenes használata akkor lehet indokolt, ha a policy engine hosszabb kiesése miatt az üzleti kritikus API-k teljesen blokkolnak, és a kiesés hatása nagyobb, mint a policy megkerülésének kockázata. Ez azonban csak dokumentált, időhöz kötött, és a security csapat által jóváhagyott döntés lehet. Az ideiglenes Ignore alatt az audit logokat fokozottan figyelni kell, és a policy engine mielőbbi helyreállítása kötelező.

42.2.7 Rövid összefoglaló

Az admission control az API szerver azon rétege, amely a kérelem tartalmát a tárolás előtt ellenőrzi vagy módosítja. A Pod Security Admission a beépített PSS szinteket namespace label-ekkel érvényesíti, míg a custom policy (ValidatingAdmissionPolicy, OPA, Kyverno) egyedi, org-specifikus szabályokat kényszerít ki. A webhook alapú policy-k failurePolicy és timeoutSeconds beállításai közvetlenül befolyásolják a cluster availabilityét: a Fail biztonságos, de kiesést okozhat, az Ignore availability-barát, de csendben megkerüli a policy-t. A policy rollout során audit/warn módból fokozatosan érdemes áttérni enforce-ra, az exception-öket pedig ownerrel és lejárattal dokumentálni kell.

Továbbhasznált definíciók: admission controller – az API szerver azon komponense, amely a hitelesítés és RBAC után, az etcd-be írás előtt ellenőrzi vagy módosítja a kérést; Pod Security Admission (PSA) – beépített admission controller, amely a Pod Security Standards szinteket namespace label-ek alapján érvényesíti; ValidatingAdmissionPolicy (VAP) – a kube-apiserverben futó, CEL-alapú validating policy, amely külön webhook nélkül működik.

42.2.8 Források és ellenőrzési hiányok

A jelen kérésben nincs webes keresőeszköz, ezért az aktuális támogatási állapotokat, a VAP API pontos mezőneveit, a PSS profilok részletes szabályait és a webhook timeout viselkedését nem ellenőriztem. Az alábbi linkek kiindulópontok, nem olvasott, ellenőrzött források:

  • Kubernetes Pod Security Standards
  • Pod Security Admission
  • Dynamic Admission Control
  • ValidatingAdmissionPolicy
  • OPA Gatekeeper
  • Kyverno

Különösen ellenőrizendő: a használt Kubernetes verzióban a ValidatingAdmissionPolicy API elérhetősége és stabilitási szintje, a matchConstraints és validationActions mezők pontos szintaxisa, a CEL függvények elérhetősége, valamint a Pod Security Standards pontos szabálylistája az adott release-ben.
