31.3 SNAT, DNAT és hálózati címfordítás

31.3.1 Miért nem elég egy porttovábbítási szabály?

Egy szolgáltatás a belső címen elérhető, a közzétett címen azonban időtúllépést ad. Ettől még lehet helyes a címfordítás: hiányozhat a továbbítási engedély, hibás lehet az útvonal, vagy a válasz elkerülheti a fordítást végző gépet. A diagnosztika ezért három külön kérdést tesz fel:

  1. Routing: merre kell továbbítani a csomagot?
  2. Tűzfal: szabad-e továbbítani?
  3. NAT: melyik cím vagy port változzon meg?

A hálózati címfordítás (Network Address Translation, NAT) itt a Linux kapcsolatkövetésére épülő, állapottartó cím- és esetenként portátírást jelenti. A forráscím-fordítás (Source NAT, SNAT) a forrásoldalt, a célcím-fordítás (Destination NAT, DNAT) a céloldalt módosítja. A porttovábbítás (port forwarding) rendszerint DNAT-ot, megfelelő routingot és tűzfalszabályt együtt igényel.

A NAT nem biztonsági határ. Nem hitelesít, nem titkosít, és önmagában nem helyettesíti a hozzáférési szabályokat. Az alapokat a routing és forwarding modellje, illetve az nftables policy működtetése adja.

31.3.2 A kapcsolat leképezése és a hookok sorrendje

A TCP-kapcsolatot egy adott hálózati névtérben és kapcsolatkövetési zónában a protokoll, valamint a forrás- és célcím/port azonosítja. A kapcsolatkövetés (connection tracking, conntrack) tárolja az eredeti és a válaszirány összetartozását.

Állapottartó nftables NAT esetén az új kapcsolat első csomagja választ NAT-leképezést. A későbbi csomagokra, beleértve a válaszokat, a kernel a tárolt leképezést alkalmazza. Következmények:

  • a NAT-szabály számlálója nem teljes forgalmi bájtszámláló;
  • szabálymódosítás után egy meglévő kapcsolat még a régi leképezést használhatja;
  • a NAT-állapot elvesztése megszakíthatja a kapcsolatokat.

A laborban továbbított csomag egyszerűsített útja:

Feldolgozási pont Feladat A csomag fontos jellemzője
Bejövő interfész megfigyelése Beérkezett csomag rögzítése Még a bejövő, vezetéken látható címzés
prerouting, dstnat prioritás DNAT A célcím és célport megváltozhat
Route lookup Kimenő interfész kiválasztása Már a módosított cél alapján
forward, filter prioritás Továbbítás engedélyezése DNAT utáni cél, SNAT előtti forrás
postrouting, srcnat prioritás SNAT A forráscím és forrásport megváltozhat
Kimenő interfész megfigyelése Kiküldött csomag rögzítése Már a kimenő címzés

Ez a tranzitút; a router saját folyamatából indított kapcsolat nem járja be ugyanígy a prerouting és forward hookot. Ezért a routeren futtatott curl nem helyettesíti a külső klienses ellenpróbát.

A masquerade dinamikus SNAT: a kimenő interfész címéből választ fordítási címet. Változó című uplinkhez hasznos; statikus címnél az explicit snat to könnyebben auditálható. Interfész- vagy címváltozáskor nem várható a meglévő kapcsolatok átlátszó megőrzése.

31.3.3.2 NAT és hozzáférési policy

# Target: lab-net01, UID 0; szabálybetöltés csak lab-nat-r névtérben.
cat >/run/lab-d153.nft <<'NFT'
table ip "lab-nat" {
    chain "lab-pre" {
        type nat hook prerouting priority dstnat; policy accept;
        iifname { "lab-rx", "lab-br0" } ip daddr 192.0.2.1 \
            tcp dport 18080 counter dnat to 10.203.0.20:8080
    }

    chain "lab-forward" {
        type filter hook forward priority filter; policy drop;
        ct state invalid drop
        ct state established,related counter accept

        iifname "lab-br0" oifname "lab-rx" \
            ip saddr 10.203.0.10 ip daddr 192.0.2.2 \
            tcp dport 9000 ct state new counter accept

        iifname { "lab-rx", "lab-br0" } oifname "lab-br0" \
            ip daddr 10.203.0.20 tcp dport 8080 \
            ct status dnat ct state new counter accept
    }

    chain "lab-post" {
        type nat hook postrouting priority srcnat; policy accept;
        oifname "lab-rx" ip saddr 10.203.0.0/24 \
            counter snat to 192.0.2.1

        iifname "lab-br0" oifname "lab-br0" \
            ip saddr 10.203.0.0/24 ip daddr 10.203.0.20 \
            tcp dport 8080 ct status dnat \
            counter snat to 10.203.0.1 comment "lab-hairpin"
    }
}
NFT

ip netns exec lab-nat-r nft -c -f /run/lab-d153.nft
ip netns exec lab-nat-r nft -f /run/lab-d153.nft
ip netns exec lab-nat-r nft list table ip lab-nat

# Csak dummy tartalmat kiszolgáló, eldobható laborfolyamatok.
ip netns exec lab-nat-s python3 -m http.server 8080 \
    --bind 10.203.0.20 --directory /run/lab-d153-www \
    >/run/lab-d153-s.log 2>&1 &

ip netns exec lab-nat-x python3 -m http.server 9000 \
    --bind 192.0.2.2 --directory /run/lab-d153-www \
    >/run/lab-d153-x.log 2>&1 &

A -c szintaktikai/kerneloldali ellenőrzés, nem adatútbizonyíték. A konfiguráció csak IPv4-re és a tranzitforgalomra vonatkozik; nem teljes router-hardening, és nem módosít IPv6-védelmet.

31.3.3.3 Három kapcsolat ellenőrzése

Előbb az ss kimenetében ellenőrizzük a listen socketeket, majd indítsuk a próbákat:

# Target: lab-net01, UID 0; minden végrehajtási névtér explicit.
ip netns exec lab-nat-s ss -lnt
ip netns exec lab-nat-x ss -lnt

ip netns exec lab-nat-c curl --noproxy '*' \
    --connect-timeout 2 --max-time 4 http://192.0.2.2:9000/

ip netns exec lab-nat-x curl --noproxy '*' \
    --connect-timeout 2 --max-time 4 http://192.0.2.1:18080/

ip netns exec lab-nat-c curl --noproxy '*' \
    --connect-timeout 2 --max-time 4 http://192.0.2.1:18080/

ip netns exec lab-nat-r conntrack -L -p tcp -o extended
cat /run/lab-d153-s.log /run/lab-d153-x.log

Várt postcondition: mindhárom kérés lab-nat-ok választ kap. A tényleges kliensportot a capture vagy a conntrack-kimenet adja; az alábbi p, q, r jelölések nem mért értékek.

Kapcsolat Eredeti irány Router után
Kimenő SNAT 10.203.0.10:p → 192.0.2.2:9000 192.0.2.1:q → 192.0.2.2:9000
Külső DNAT 192.0.2.2:p → 192.0.2.1:18080 192.0.2.2:p → 10.203.0.20:8080
Hairpin 10.203.0.10:p → 192.0.2.1:18080 10.203.0.1:r → 10.203.0.20:8080

A NAT lehetőség szerint megtarthatja a forrásportot, de ezt nem szabad garantáltnak tekinteni.

A külső DNAT válaszútjának levezetése:

  1. A backend válasza: 10.203.0.20:8080 → 192.0.2.2:p.
  2. A cél nem helyi alhálózat, ezért a backend a 10.203.0.1 átjárónak küldi.
  3. A router conntrack-állapota felismeri a válaszirányt.
  4. A külső interfészen már 192.0.2.1:18080 → 192.0.2.2:p látható.

Külön „vissza-DNAT” szabály nem szükséges. A visszaútnak viszont ugyanahhoz a megfelelő NAT-állapothoz kell jutnia.

31.3.4 Hairpin és az eredeti forrás láthatósága

A hairpin NAT azt teszi lehetővé, hogy belső kliens a szolgáltatás közzétett címén érje el a belső backendet.

A laborban puszta DNAT után a backend a 10.203.0.10 klienscímet látná. Mivel ugyanazon alhálózaton vannak, közvetlenül válaszolna neki, megkerülve a router L3 NAT-feldolgozását. A kliens azonban a 192.0.2.1:18080 végponttal kezdeményezett kapcsolatot, nem a 10.203.0.20:8080 végponttal.

A szűken célzott hairpin SNAT a forrást 10.203.0.1-re fordítja. Így a backend a routernek válaszol, amely mindkét fordítást visszaalkalmazza.

Ennek ára az eredeti forrás láthatóságának (source visibility) elvesztése:

  • külső DNAT-nál a backend itt 192.0.2.2-t lát;
  • hairpinnél 10.203.0.1-et lát;
  • kimenő SNAT-nál a külső szerver 192.0.2.1-et lát.

A NAT nem helyez el automatikusan HTTP Forwarded fejlécet. Proxy által továbbított kliensazonosságot csak meghatározott, megbízható proxyhatáron szabad elfogadni. Alternatíva lehet eltérő belső DNS-válasz vagy más routingtopológia, saját működtetési szerződéssel.

31.3.5 Capture, kapacitás és hibakeresési ellenpróbák

Két külön konzolon indított megfigyelés:

# Target: lab-net01, UID 0; leállítás Ctrl-C-vel.
ip netns exec lab-nat-r tcpdump -ni lab-rx -nn \
    'tcp and (port 18080 or port 9000)'
# Target: lab-net01, UID 0.
ip netns exec lab-nat-r tcpdump -ni lab-br0 -nn \
    'tcp and (port 8080 or port 18080 or port 9000)'

Külső DNAT-nál a külső capture 18080, a belső 8080 célportot mutat. Ez nem ellentmondás: más hookok előtti és utáni csomagot figyelünk. Hairpinnél a be- és kilépés ugyanazon bridge-interfészhez tartozhat; mindig a teljes cím/port négyest és az irányt vizsgáljuk.

Tünet Hipotézis és ellenpróba
Külső SYN látszik, belső nem DNAT-találat, forwarding, route és filter ellenőrzése
Backend SYN-t kap, de nincs megfelelő külső válasz Backend return route, listener és conntrack vizsgálata
Új szabály után csak régi kapcsolat működik Új kapcsolat indítása; régi mapping elkülönítése
Csak hairpin hibás Közvetlen backend-válaszút és hairpin SNAT ellenőrzése
Kimenő ping hibás, HTTP működik A labor policy csak megadott TCP-forgalmat enged; ez nem NAT-hiba

A portkimerülés (port exhaustion) és a conntrack-tábla telítődése külön jelenség. Egy fordított forráscímhez, azonos távoli végponthoz és protokollhoz véges számú megkülönböztethető portleképezés tartozik. A tényleges korlát függ a portkészlettől, céloktól, implementációtól és timeoutoktól.

Hipotetikus állandósult modellben:

N≈λT N \approx \lambda T

ahol λ\lambda az új leképezések üteme [kapcsolat/s], TT az átlagos állapotfoglalási idő [s], NN az átlagos állapotszám [kapcsolat]. Így 500 kapcsolat/s × 90 s = 45 000 kapcsolat: egy feltételezett 40 000-es keret kevés. Ez nem mért Linux-korlát.

Az inaktivitási időkorlát (idle timeout) lejárta törölheti a leképezést, miközben az alkalmazás még élőnek gondolja kapcsolatát. A TCP-állapotfüggő timeout, a UDP-állapot és egy cloud NAT szolgáltatás időkorlátja eltérhet. Keepalive csak megfelelő időzítéssel segít, és nem helyettesíti az alkalmazási újracsatlakozást.

Cloud NAT gateway, konténeres portpublikálás és Kubernetes Service mögött is találkozhatunk hasonló címfordítással, de a tényleges adatút lehet más implementációjú. A service mesh proxyja pedig gyakran lezár egy kapcsolatot és újat nyit: nem egyszerűen NAT. A konkrét platformon külön ellenőrizendő a forráscím-megőrzés, portkeret, timeout, állapottulajdonos és hibaterület.

31.3.6 Feladatok

  1. Magyarázó: írd le a kimenő SNAT és a hairpin válaszirányának cím/port négyeseit. Miért nem elegendő egy helyes NAT-szabály?
  2. Adminisztrációs: építsd fel a labort, ellenőrizd a három engedélyezett kérést. Negatív próbaként próbáld elérni belülről a 192.0.2.2:9001 végpontot.
  3. Diagnosztikai és recovery: töröld csak a lab-hairpin megjegyzésű szabályt és az érintett klienskapcsolatok állapotát. Capture-rel igazold a hibát, majd állítsd vissza a szabályt.

31.3.7 Megoldások

1. SNAT-nál a külső válasz először 192.0.2.2:9000 → 192.0.2.1:q, majd visszafordítva 192.0.2.2:9000 → 10.203.0.10:p. Hairpinnél a backend válasza 10.203.0.20:8080 → 10.203.0.1:r, a klienshez pedig 192.0.2.1:18080 → 10.203.0.10:p érkezik. Postcondition: a kliens ugyanazt a távoli végpontot látja, amellyel kapcsolatot kezdeményezett; routing és filter külön igazolt.

2. A három válasz mellett ellenőrizni kell a naplózott forráscímeket és a szabályszámlálókat is:

# Target: lab-net01, UID 0.
ip netns exec lab-nat-c curl --noproxy '*' \
    --connect-timeout 2 --max-time 4 http://192.0.2.2:9001/
ip netns exec lab-nat-r nft list table ip lab-nat

A negatív próba várhatóan timeouttal végződik. Önmagában ez nem bizonyít tűzfalszűrést: a külső capture-ben a továbbított SYN hiányát is ellenőrizni kell. Postcondition: csak a szerződés szerinti adatút engedélyezett.

3. A szabályazonosítót az aktuális állapotból olvassuk ki:

# Target: lab-net01, UID 0; kizárólag a labor hairpin szabálya.
h=$(ip netns exec lab-nat-r nft -a list chain ip lab-nat lab-post |
    awk '/comment "lab-hairpin"/ {print $NF}')
if [[ "$h" =~ ^[0-9]+$ ]]; then
    ip netns exec lab-nat-r nft delete rule ip lab-nat lab-post handle "$h"
fi

ip netns exec lab-nat-r conntrack -D -p tcp \
    --orig-src 10.203.0.10 --orig-dst 192.0.2.1 --dport 18080

A nulla törölt kapcsolat önmagában nem hiba: lehet, hogy már lejárt. Ezután új hairpin kérést kell indítani. Bridge-netfilter beállítástól függően a közvetlen visszirány külön szűrésbe is ütközhet; a lényeg a helyes, NAT-on átmenő válaszút hiánya.

Visszaállítás:

# Target: lab-net01, UID 0.
ip netns exec lab-nat-r nft 'add rule ip "lab-nat" "lab-post" iifname "lab-br0" oifname "lab-br0" ip saddr 10.203.0.0/24 ip daddr 10.203.0.20 tcp dport 8080 ct status dnat counter snat to 10.203.0.1 comment "lab-hairpin"'

ip netns exec lab-nat-r conntrack -D -p tcp \
    --orig-src 10.203.0.10 --orig-dst 192.0.2.1 --dport 18080

ip netns exec lab-nat-c curl --noproxy '*' \
    --connect-timeout 2 --max-time 4 http://192.0.2.1:18080/

Postcondition: új kapcsolat sikeres, a backend ismét 10.203.0.1 forrást lát. A conntrack-tábla globális ürítése nem szükséges.

31.3.7.1 Rollback és cleanup

A teljes rollback a kizárólag ehhez a laborhoz létrehozott névterek eltávolítása. Előbb állítsuk le a capture-öket. Az alábbi takarítás csak a felsorolt, a létrehozáskor szabadnak ellenőrzött laborobjektumokra használható:

# Target: lab-net01, UID 0.
for n in lab-nat-c lab-nat-s lab-nat-x lab-nat-r; do
    if ip netns list | awk '{print $1}' | grep -Fxq "$n"; then
        ip netns pids "$n" | xargs -r kill -TERM --
        sleep 1
        if test -z "$(ip netns pids "$n")"; then
            ip netns del "$n"
        else
            echo "Még fut folyamat ebben a névtérben: $n" >&2
        fi
    fi
done

rm -f /run/lab-d153-www/index.html
rmdir /run/lab-d153-www
rm -f /run/lab-d153.nft /run/lab-d153-s.log /run/lab-d153-x.log
ip netns list

Cleanup-postcondition: nincs megmaradt lab-nat-* névtér vagy laborfolyamat; a host eredeti hálózati konfigurációja változatlan.

31.3.8 Rövid összefoglaló

A NAT kapcsolatállapothoz rendelt cím- és portfordítás, nem útválasztó algoritmus és nem hozzáférési policy. A DNAT utáni cél alapján történik a route lookup; a forward szűrés általában még az SNAT előtti forrást látja. A válasznak vissza kell jutnia a megfelelő kapcsolatállapothoz. Hairpinnél ezt gyakran külön SNAT biztosítja, az eredeti forrás láthatóságának elvesztésével. A capture-ek eltérése ezért lehet teljesen helyes: különböző feldolgozási pontokat mutatnak. Változtatás után új kapcsolatot kell vizsgálni, mert a korábbi mapping megmaradhat. Portkeretet, állapottábla-kapacitást és timeoutot külön kell kezelni.

  • SNAT: a forrásoldali cím vagy port fordítása.
  • DNAT: a céloldali cím vagy port fordítása.
  • Hairpin NAT: belső szolgáltatás elérése belső kliensből a közzétett címen.

31.3.9 Források és ellenőrzési hiányok

Nem történt webes forrásolvasás vagy laborfuttatás. Elsődleges ellenőrzési kiindulópontok:

  • nftables – hivatalos kézikönyv
  • nftables wiki – Performing Network Address Translation
  • Netfilter conntrack-tools

Nyitott ellenőrzések: a konkrét Ubuntu-kernel és csomagverziók; bridge-netfilter állapot; tényleges conntrack-időkorlátok és portfoglalás; a három adatút capture-bizonyítéka. Cloud- és konténerplatformon a NAT-implementációt, támogatási profilt, kvótákat és timeoutokat külön, verzióhoz kötötten kell ellenőrizni.
