32.4 Link/transport/app throughput és latency mérés

32.4.1 Miért nem elég egyetlen „Mbit/s” szám?

Egy szolgáltatás lassúságánál három külön kérdésre keresünk választ:

  1. Mekkora adatsebességet enged az átviteli út?
  2. Mennyit használ ebből egy adott transzportkapcsolat?
  3. Milyen gyorsan teljesül a felhasználó tényleges művelete?

A névleges linkráta (link rate), a hasznosadat-sebesség (goodput) és az alkalmazási válaszidő nem felcserélhető. Egy nagy TCP-adatfolyam kihasználhatja az útvonalat, miközben a rövid kérések TLS-kézfogásra, szerveroldali sorra vagy adatbázisra várnak. Fordítva: egy kis válaszokat adó szolgáltatás alacsony hálózati adatsebesség mellett is lehet CPU-limitált.

A cél nem egyetlen maximális érték előállítása, hanem a korlátozó réteg szűkítése. Ehhez a Kapacitás- és mérési jegyzőkönyv labor módszerét alkalmazzuk, és feltételezzük, hogy az MTU, PMTU, loss és asymmetry alfejezetben tárgyalt útvonalhibákat már ellenőriztük.

32.4.2.1 Névleges linkráta és hasznos adat: levezetés

Számított modell: 1 Gbit/s teljes duplex Ethernet, VLAN nélkül, 1500 bájtos IP-csomag, 20 bájtos IPv4- és 20 bájtos TCP-fejléc, teljes méretű keretek, veszteség nélkül.

Egy keretben a TCP-hasznos adat:

Lhasznos=1500−20−20=1460B. L_{\mathrm{hasznos}} = 1500-20-20 = 1460\ \mathrm{B}.

Az átviteli időt az Ethernet-fejléc, az FCS, a preambulum/SFD és a keretközi rés is terheli. Utóbbi nem keretadat, de 12 bájtnyi átviteli idővel számolunk:

Lidőegyenérték=1500+14+4+8+12=1538B. L_{\mathrm{időegyenérték}} =1500+14+4+8+12=1538\ \mathrm{B}.

Így az egyirányú TCP-hasznosadat-sebesség elméleti felső korlátja:

Gmax=109bit/s×14601538≈949,3Mbit/s. G_{\max} =10^9\ \mathrm{bit/s}\times\frac{1460}{1538} \approx949{,}3\ \mathrm{Mbit/s}.

Ez nem benchmarkígéret. TCP-opciók, kisebb csomagok, alagutak, újraküldések és végponti korlátok csökkenthetik. A fordított irányú ACK-forgalomnak is működő út kell; megosztott vagy aszimmetrikus szűkület esetén külön korlátozhat.

32.4.2.2 RTT, BDP és socket buffer

A sávszélesség–késleltetés szorzat (bandwidth-delay product, BDP) azt közelíti, mennyi adatnak kell egyszerre úton lennie az út kitöltéséhez:

BDP=C×RTT8. BDP=\frac{C\times RTT}{8}.

Itt CC bit/s, az RTT másodperc, a BDP bájt. Számított példa: 1 Gbit/s és 20 ms esetén:

BDP=109×0,0208=2500000B≈2,38MiB. BDP=\frac{10^9\times0{,}020}{8} =2\,500\,000\ \mathrm{B}\approx2{,}38\ \mathrm{MiB}.

Egy folyam egyszerűsített korlátmodellje:

G≲min(C,8WeffRTT,Gvégpont), G\lesssim\min\left( C,\frac{8W_{\mathrm{eff}}}{RTT},G_{\mathrm{végpont}} \right),

ahol WeffW_{\mathrm{eff}} bájtban megadott effektív küldési ablak: legfeljebb a torlódási ablak és a vevő által hirdetett ablak minimuma. Ha ez 256 KiB, 20 ms RTT mellett az ablakkorlát körülbelül 104,9 Mbit/s.

A socketpuffer mérete nem azonos ezzel az ablakkal. A Linux automatikus pufferhangolása, a TCP-állapot és a memóriakönyvelés is számít. Az iperf3 -w ezért nem közvetlen „ennyit tartunk úton” beállítás; Linuxon a kért és kijelzett pufferméret is eltérhet. Először ss -tinm állapottal vizsgáljunk, ne globális pufferemeléssel kezdjünk.

test -z "$(sudo ip netns list)" || exit 1

sudo ip netns add lab-rx
sudo ip link add lab-vtx type veth peer name lab-vrx

sudo ip link set lab-vrx netns lab-rx

sudo ip -n lab-rx address add 10.159.0.2/24 dev lab-vrx

32.4.3.1 TCP-folyamok, irányok és UDP

Külön terminálban indítsuk a szervert:

# Target: lab-perf / lab-rx; szerverfolyamat: lab, UID 1000.
sudo ip netns exec lab-rx runuser -u lab -- \
  iperf3 -s -B 10.159.0.2 -p 5201

A kliensmérések sorosan futnak. A három ismétlés minimális ismételhetőségi ellenőrzés, nem erős statisztikai bizonyíték.

# Target: lab-perf / lab-tx; kliensfolyamatok: lab, UID 1000.
cd "$HOME/lab-d159" || exit 1
for run in 1 2 3; do
  sudo ip netns exec lab-tx runuser -u lab -- \
    iperf3 -c 10.159.0.2 -t 30 -O 3 -P 1 -J \
    > "lab-tcp-p1-${run}.json"

  sudo ip netns exec lab-tx runuser -u lab -- \
    iperf3 -c 10.159.0.2 -t 30 -O 3 -P 4 -J \
    > "lab-tcp-p4-${run}.json"

  sudo ip netns exec lab-tx runuser -u lab -- \
    iperf3 -c 10.159.0.2 -t 30 -O 3 -P 1 -R -J \
    > "lab-tcp-reverse-${run}.json"

  sudo ip netns exec lab-tx runuser -u lab -- \
    iperf3 -c 10.159.0.2 -u -b 50M -l 1200 -t 30 -J \
    > "lab-udp-50M-${run}.json"
done
  • -P 1 egy, -P 4 négy párhuzamos adatfolyam. Az összesített növekedés nem bizonyítja, hogy egyetlen alkalmazáskapcsolat gyorsult.
  • -R esetén a szerver küldi az adatot. Ez külön futás, nem egyidejű kétirányú terhelés.
  • -O 3 kezdeti szakaszt hagy ki a statisztikából; ettől a workload még nem feltétlenül állandósult.
  • UDP-nél az 50 Mbit/s célzott küldési ráta, nem garantált fogadott teljesítmény. A vevőoldali sebességet, elveszett és sorrenden kívüli datagramokat is értékeljük.
  • Az UDP-jitter nem RTT és nem alkalmazási percentilis.

Várt eredményforma: TCP-nél küldő- és vevőoldali bájt/sebesség, elérhető újraküldési adatok; UDP-nél vevőoldali veszteség és jitter. A pontos JSON-sémát a rögzített iperf3-kiadás szerint ellenőrizzük. A küldő által elfogadott bájtok helyett a vevőoldali eredmény legyen a goodput alapja.

32.4.4 CPU, offload, RSS és IRQ: végponti korlátok

A méréssel egy időben, más terminálokban gyűjtsünk adatot:

# Target: lab-perf; megfigyelés: lab, UID 1000.
mpstat -P ALL 1 35
pidstat -u -t -C iperf3 1 35

# Target: lab-perf; névtérbe lépéshez sudo.
sudo ip netns exec lab-tx ss -tinm '( dport = :5201 )'
sudo ip -n lab-tx -s link show dev lab-vtx
sudo ip -n lab-rx -s link show dev lab-vrx
sudo ip netns exec lab-tx ethtool -k lab-vtx

Az összesített 25% CPU egy négymagos gépen jelenthet egyetlen teljesen elfoglalt magot. Az iperf3 párhuzamos folyamainak szálkezelése kiadásfüggő: a verziót és a tényleges szálankénti CPU-terhelést együtt értelmezzük.

Fizikai NIC esetén további rétegek jelennek meg:

  • A tehermentesítés (offload), például TSO/GSO/GRO, csökkentheti a csomagonkénti CPU-munkát. Emiatt a capture-ben látott „csomag” nem mindig egyetlen vezetéken megjelent keret.
  • A vételi oldali skálázás (receive-side scaling, RSS) több vételi sorra oszthatja a folyamokat. Egy folyam rendszerint egy sorhoz kötődik.
  • A megszakítások (IRQ), a softirq-feldolgozás, a sorok és a CPU-affinitás elhelyezése befolyásolja a kapacitást.
  • Virtuális NIC-nél a vendég több sora mögött is lehet közös hostoldali szűkület.

Az ethtool -l, ethtool -S, /proc/interrupts és /proc/softirqs következő adatgyűjtési pont lehet egy külön, azonosított NIC-profilban. A veth-labor ezek fizikai működését nem igazolja.

Ne kapcsoljunk ki minden offloadot „a tiszta mérésért”: ezzel más workloadot hozunk létre. Először rögzítsük az állapotot; kontrollált összehasonlításnál csak egy változót módosítsunk.

32.4.5 Alkalmazási terhelés és percentilisek

A nyers adatfolyam nem tartalmaz kérésfeldolgozási költséget. Készítsünk egyszerű, TLS nélküli HTTP-fixture-t:

# Target: lab-perf; account: lab, UID 1000; csak saját labfájl.
truncate -s 65536 "$HOME/lab-d159/lab-payload.bin"

# Külön terminál; target: lab-rx; folyamat: lab, UID 1000.
sudo ip netns exec lab-rx runuser -u lab -- \
  python3 -m http.server 8080 --bind 10.159.0.2 \
  --directory /home/lab/lab-d159

Ez diagnosztikai fájlkiszolgáló, nem termelési C++-szolgáltatásmodell. Az alábbi kliens 200 kérést végez, kérésenként új kapcsolattal. Az időmérés monoton órán történik; nincs DNS-feloldás vagy TLS.

# Target: lab-perf / lab-tx; kliens: lab, UID 1000.
sudo ip netns exec lab-tx runuser -u lab -- python3 - \
  > "$HOME/lab-d159/lab-app.json" <<'PY'
import http.client, json, math, time

samples = []
good = 0
start = time.perf_counter_ns()
for _ in range(200):
    t0 = time.perf_counter_ns()
    c = http.client.HTTPConnection("10.159.0.2", 8080, timeout=2)
    ok = False
    try:
        c.request("GET", "/lab-payload.bin")
        r = c.getresponse()
        body = r.read()
        ok = r.status == 200 and len(body) == 65536
    except (OSError, http.client.HTTPException):
        pass
    finally:
        c.close()
    samples.append((time.perf_counter_ns() - t0) / 1e6)
    good += int(ok)

elapsed = (time.perf_counter_ns() - start) / 1e9
ordered = sorted(samples)
def percentile(p):
    return ordered[math.ceil(p * len(ordered)) - 1]

print(json.dumps({
    "attempts": len(samples), "good": good,
    "errors": len(samples) - good,
    "elapsed_s": elapsed, "good_requests_per_s": good / elapsed,
    "good_body_bytes_per_s": good * 65536 / elapsed,
    "all_attempts_p50_ms": percentile(0.50),
    "all_attempts_p95_ms": percentile(0.95),
    "all_attempts_p99_ms": percentile(0.99),
    "all_attempts_latency_ms": samples
}, indent=2))
PY

Postcondition: 200 próbálkozás, alapesetben 200 helyes válasz; eltérésnél a hibaarányt is közöljük. A percentilisek minden próbálkozás eltelt idejét tartalmazzák, tehát hibáknál nem nevezhetők sikeres válaszok percentiliseinek. A socket timeout nem általános, teljes kérésre vonatkozó határidő.

A hisztogram (histogram) gyakoriságokat rendel időintervallumokhoz. Rögzítsük a kosárhatárokat, elemszámot, mérési ablakot és hibakezelést. A fenti nyers mintákból utólag új hisztogram készíthető; pusztán egy p99-értékből nem.

Kétszáz mintánál a leglassabb egy százalék mindössze két megfigyelés: ez gyenge bizonyíték a ritka késleltetésekre. Több futás p99-értékeinek átlaga sem a közös mintahalmaz p99-e.

A kliens zárt hurkú (closed-loop): megvárja a választ, utána küld újat. Lassuláskor így csökkenti a felkínált terhelést. Ez koordinált kihagyást (coordinated omission) okozhat egy rögzített érkezési intenzitású szolgáltatáshoz képest. Nyílt hurkú mérésnél előre ütemezett kérések, a kliens saját késésének elszámolása és külön terhelésgenerátor-kapacitásvizsgálat kell.

Az üresjárati ping RTT-je nem alkalmazási latency. Terhelés alatt növekvő RTT pedig önmagában még nem bizonyít hálózati sorproblémát: ugyanaz a CPU futtatja a mérőfolyamatokat is.

A torlódási és hibakori tartalék (headroom) tervezési feltétel. Ha a választott maximális kihasználtság uu, a hibás állapotban igazolt, adott késleltetési és hibaarány-célt teljesítő kapacitás CdegradedC_{\mathrm{degraded}}, akkor:

Ltervezett≤uCdegraded. L_{\mathrm{tervezett}}\le u\,C_{\mathrm{degraded}}.

Hipotetikus példa: 800 kérés/s hibakori kapacitás és 70%-os tervezési kihasználtság mellett legfeljebb 560 kérés/s a választott terhelés. A 70% nem univerzális szabály. Terheléslépcsőkön kell keresni azt a tartományt, ahol a p99 vagy a hibaarány romlani kezd, majd a kiesett erőforrással is megismételni a próbát.

32.4.7 Feladatok

  1. Magyarázó: számítsd ki a BDP-t 200 Mbit/s és 40 ms mellett. Mekkora elméleti adatsebességet enged 512 KiB effektív TCP-ablak?
  2. Adminisztrációs: építsd fel a labort, és készíts összehasonlító táblázatot az egyfolyamos, négyfolyamos, fordított irányú és UDP-mérés három ismétléséből. Rögzítsd a CPU-profilt és a verziókat is.
  3. Diagnosztikai/recovery: a két veth-interfész kimenetére adj egyenként 10 ms késleltetést. Mérd újra az RTT-t, az egyfolyamos TCP-t és a HTTP-fixture-t. Távolítsd el a módosítást, majd ellenőrizd a helyreállást.

32.4.8 Megoldások

  1. A BDP:

    200000000×0,0408=1000000B≈0,954MiB. \frac{200\,000\,000\times0{,}040}{8} =1\,000\,000\ \mathrm{B}\approx0{,}954\ \mathrm{MiB}.

    Az ablakkorlát:

    8×512×10240,040≈104,9Mbit/s. \frac{8\times512\times1024}{0{,}040} \approx104{,}9\ \mathrm{Mbit/s}.

    Indoklás: a választott ablak kisebb a teljes út kitöltéséhez szükséges adatmennyiségnél. Postcondition: a számítás külön kezeli a bit/s, bájt és másodperc egységeket.

  2. A TCP-sorok vevőoldali goodputot, irányt, folyamdarabszámot, újraküldést és CPU-adatot tartalmazzanak; UDP-nél kínált/fogadott ráta, veszteség és jitter szerepeljen. Ne csak a legjobb futást közöljük.

    Postcondition: az eredményből visszaállítható a workload és a verzióprofil; a virtuális út eredménye nincs fizikai Ethernet-kapacitásként feltüntetve.

  3. Először ellenőrizzük a meglévő sorütemezőt; csak a labor friss veth-interfészeit módosítjuk:

    # Target: lab-perf; UID 0 sudo útján; csak lab-vtx és lab-vrx.
sudo ip netns exec lab-tx tc qdisc show dev lab-vtx
sudo ip netns exec lab-rx tc qdisc show dev lab-vrx

sudo ip netns exec lab-tx tc qdisc add dev lab-vtx root netem delay 10ms
sudo ip netns exec lab-rx tc qdisc add dev lab-vrx root netem delay 10ms

    Várt jelenség: körülbelül 20 ms többlet-RTT, ütemezési eltérésekkel. Az egyfolyamos TCP nem szükségszerűen lassul arányosan: az ablak növekedése kompenzálhat. A rövid HTTP-műveletekben a kapcsolatfelépítés is megjelenik. A küldőoldali netem, az offload és a TCP queue-kezelése kölcsönhatásba léphet; ez nem fizikai WAN-hitelesítés.

    Visszaállítás:

    # Target: lab-perf; UID 0 sudo útján.
sudo ip netns exec lab-tx tc qdisc del dev lab-vtx root
sudo ip netns exec lab-rx tc qdisc del dev lab-vrx root

    Postcondition: nincs laborban hozzáadott netem; az RTT és a workload eredménye visszatér az ismétlésekben megfigyelt alapállapoti tartományba.

A teljes labor takarításakor állítsuk le Ctrl-C-vel a két szervert, várjuk meg a kliensek kilépését, majd:

# Target: lab-perf; csak a felsorolt saját névterek törölhetők.
test -z "$(sudo ip netns pids lab-tx)" &&
  sudo ip netns del lab-tx
test -z "$(sudo ip netns pids lab-rx)" &&
  sudo ip netns del lab-rx

sudo ip netns list

A névterekkel a veth-pár és annak sorütemezői is megszűnnek. A ~/lab-d159 könyvtár szándékosan megmarad mérési bizonyítékként.

32.4.9 Rövid összefoglaló

A hálózati benchmark eredménye csak mérési határral, iránnyal, időablakkal és workloadprofillal értelmezhető. A névleges linkráta nem azonos a TCP-vevő hasznosadat-sebességével, és egyik sem írja le önmagában az alkalmazás válaszidejét. Az egy- és többfolyamos, illetve fordított irányú próbák CPU-, ablak- és adatútkorlátokat segítenek elkülöníteni. A percentilishez elemszám, hibaarány és terhelésgenerálási modell is kell. A használható kapacitást a latency- és hibacélokkal együtt, hibás állapotban is ellenőrizni kell. Egyetlen VM névterei reprodukálható funkcionális labort adnak, de fizikai linket és független végpontokat nem igazolnak.

  • Goodput: a vevőnek átadott hasznos adat sebessége.
  • BDP: a kapacitás és RTT szorzatából adódó úton lévő adatmennyiség.
  • Headroom: a terhelés és az igazolt kapacitás közötti tervezett tartalék.

32.4.10 Források és ellenőrzési hiányok

Elsődleges ellenőrzési kiindulópontok; ebben a munkafolyamatban nem történt webes forrásolvasás vagy laborfuttatás:

  • ESnet – Invoking iperf3: kapcsolók, irányok, UDP és socketpufferek.
  • Linux kernel – Scaling in the Linux Networking Stack: RSS, RPS, RFS és XPS.
  • tcp(7): Linux TCP és pufferkezelés.
  • tc-netem(8): késleltetésemuláció és módszertani korlátok.
  • RFC 9293 – Transmission Control Protocol: TCP-ablak és transzportszemantika.

Ellenőrzési hiányok: rögzítendő a tényleges Ubuntu kernel- és csomagkiadás, az iperf3 szálkezelése és JSON-sémája, valamint a virtuális környezet CPU-korlátai. Fizikai méréshez külön NIC-/driver-/firmware-, link-, RSS-/IRQ- és hypervisorprofil szükséges. Az RFC aktuális kapcsolatait és erratáit, valamint a dokumentáció kiadásilleszkedését külön forrásellenőrzésben kell vizsgálni.
