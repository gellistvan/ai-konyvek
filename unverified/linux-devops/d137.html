28.2 Authoritative/recursive DNS és diagnosztika

28.2.1 Miért kell külön vizsgálni az adatgazdát és a feloldót?

Egy DNS-módosítás után az alkalmazás még a régi címre kapcsolódik. Ez nem feltétlenül hibás zónabetöltés: lehet érvényes gyorsítótár-bejegyzés, eltérő belső nézet vagy az alkalmazás saját cache-e. A diagnózis alapja ezért két külön kérdés:

  1. Mit szolgáltat most a zóna adatgazdája?
  2. Mit kap a kliens a ténylegesen használt feloldótól?

Az előző alfejezet hierarchikus modelljét most működő laborra fordítjuk le. A példák várt viselkedést mutatnak; tényleges futtatás és aktuális támogatásellenőrzés nem történt.

28.2.2 Zóna, delegáció és cache: három külön állapot

A zóna (zone) egy autoritatív módon kiszolgált DNS-adathalmaz. Nem feltétlenül azonos egy teljes domain részfával: a delegált gyermekzóna már másik felelősségi kör.

A delegáció (delegation) szülőzónában elhelyezett NS-rekordokkal jelöli ki a gyermekzóna névszervereit. Ha a névszerver neve a delegált gyermek alatt található, a szülőben címadat, úgynevezett glue rekord is szükséges lehet a körkörös függőség feloldásához.

A SOA-rekord sorozatszáma, a serial, a zónaverzió összehasonlítására szolgál, különösen elsődleges és másodlagos szerver között. Nem cache-érvénytelenítő üzenet. A szokásos YYYYMMDDnn alak konvenció; az összehasonlítás 32 bites sorozatszám-aritmetikát követ.

Állapot Példa Ellenőrzés
Konfigurációforrás zónafájl a lemezen named-checkzone
Betöltött autoritatív állapot aktuális SOA és A rekord célzott dig, AA jelző
Resolver tárolt állapota pozitív vagy negatív cache lekérdezés a resolverhez
Kívánt állapot jóváhagyott név–cím kapcsolat összevetés a változtatási tervvel

A névből címre történő feloldás (forward lookup) tipikusan A/AAAA-rekordot használ. A fordított feloldás, a reverse lookup, IPv4-nél az in-addr.arpa fa PTR-rekordját keresi. A két irány külön zónaadat: egyik módosítása nem hozza létre automatikusan a másikat.

28.2.3 Eszközprofil és izolált labortopológia

A profil Ubuntu Server 24.04 LTS amd64, disztribúciós BIND 9 autoritatív szerverrel és Unbound rekurzív feloldóval. Előfeltétel a baseline image-ben telepített bind9, bind9-utils, dnsutils, unbound és iproute2. A pontos csomagkiadást rögzíteni kell; az aktuális támogatási és biztonsági állapot nyitott ellenőrzési feladat.

Minden következő parancs célja lab-dnsvm, UID 0, egy dedikált root Bash-munkamenetben. A szolgáltatások saját, uplink nélküli hálózati névtérben futnak; a host DNS-konfigurációját nem módosítjuk.

Objektum Cím vagy hely Szerep
lab-dns namespace, lo négy helyi /32 cím izolált adatút, nincs alapértelmezett útvonal
kliens 10.203.0.10 dig forráscíme
szülő BIND 10.203.0.53:53, UDP/TCP test. zóna
gyermek BIND 10.203.0.54:53, UDP/TCP lab.test. és reverse zóna
Unbound 10.203.0.55:53, UDP/TCP rekurzió és cache
lab-www.lab.test. A: 10.203.0.80 csak DNS-adat; nincs webszerver

A címek kizárólag az új namespace-ben léteznek. Nincs veth, bridge vagy külső route, ezért nem kapcsolódnak egy esetleg azonos címzésű vállalati hálózathoz.

Adatút: kliens → Unbound → szülői referral → gyermek autoritatív válasz → Unbound cache → kliens. Mindhárom szerver ugyanazon VM failure domainjében van: ez szerepelkülönítés, nem magas rendelkezésre állás.

28.2.3.1 Előkészítés

A könyvtárak és a namespace neve nem lehet korábban használatban. Sikertelen előellenőrzésnél álljunk meg.

# Target: lab-dnsvm; UID 0.
test "$(hostname -s)" = lab-dnsvm || exit 1
test "$(id -u)" -eq 0 || exit 1

for path in /etc/bind/lab-dns /etc/unbound/lab-dns \
            /var/cache/bind/lab-dns; do
    test ! -e "$path" || exit 1
done
if ip netns list | grep -q '^lab-dns[[:space:]]\|^lab-dns$'; then
    exit 1
fi

install -d -m 0755 /etc/bind/lab-dns /etc/unbound/lab-dns
install -d -o bind -g bind -m 0750 \
    /var/cache/bind/lab-dns \
    /var/cache/bind/lab-dns/parent \
    /var/cache/bind/lab-dns/child

{
    hostname
    uname -r
    systemd --version
    dpkg-query -W bind9 bind9-utils dnsutils unbound iproute2
} > /var/cache/bind/lab-dns/lab-profile.txt

ip netns add lab-dns
ip -n lab-dns link set lo up
for octet in 10 53 54 55; do
    ip -n lab-dns addr add "10.203.0.${octet}/32" dev lo
done
ip -n lab-dns route show table all

Az inventory tulajdonosa a labor résztvevője; lejárata a munkamenet vége. Kívánt utófeltétel: csak a felsorolt címek és helyi útvonalak, külső elérhetőség nélkül.

28.2.3.2 Autoritatív konfiguráció

A szülő delegálja a lab.test. zónát. A gyermek ugyanazt az NS-nevet közli saját zónájában.

# Target: lab-dnsvm; UID 0.
cat > /etc/bind/lab-dns/lab-parent.zone <<'EOF'
$ORIGIN test.
$TTL 300
@ IN SOA lab-ns.test. hostmaster.test. (
  2025010101 3600 600 86400 60 )
  IN NS lab-ns.test.
lab-ns IN A 10.203.0.53
lab IN NS lab-ns.lab.test.
lab-ns.lab IN A 10.203.0.54
EOF

cat > /etc/bind/lab-dns/lab-forward.zone <<'EOF'
$ORIGIN lab.test.
$TTL 300
@ IN SOA lab-ns.lab.test. hostmaster.lab.test. (
  2025010101 3600 600 86400 60 )
  IN NS lab-ns.lab.test.
lab-ns IN A 10.203.0.54
lab-www IN A 10.203.0.80
EOF

cat > /etc/bind/lab-dns/lab-reverse.zone <<'EOF'
$ORIGIN 0.203.10.in-addr.arpa.
$TTL 300
@ IN SOA lab-ns.lab.test. hostmaster.lab.test. (
  2025010101 3600 600 86400 60 )
  IN NS lab-ns.lab.test.
80 IN PTR lab-www.lab.test.
EOF

cat > /etc/bind/lab-dns/lab-parent.conf <<'EOF'
options {
    directory "/var/cache/bind/lab-dns/parent";
    pid-file "/var/cache/bind/lab-dns/parent/lab-named.pid";
    listen-on { 10.203.0.53; };
    listen-on-v6 { none; };
    recursion no;
    allow-query { 10.203.0.0/24; };
    allow-transfer { none; };
};
controls {};
zone "test." {
    type primary;
    file "/etc/bind/lab-dns/lab-parent.zone";
};
EOF

cat > /etc/bind/lab-dns/lab-child.conf <<'EOF'
options {
    directory "/var/cache/bind/lab-dns/child";
    pid-file "/var/cache/bind/lab-dns/child/lab-named.pid";
    listen-on { 10.203.0.54; };
    listen-on-v6 { none; };
    recursion no;
    allow-query { 10.203.0.0/24; };
    allow-transfer { none; };
    querylog yes;
};
controls {};
logging {
    channel lab_queries {
        file "/var/cache/bind/lab-dns/child/lab-queries.log"
             versions 2 size 1m;
        severity info;
        print-time yes;
    };
    category queries { lab_queries; };
};
zone "lab.test." {
    type primary;
    file "/etc/bind/lab-dns/lab-forward.zone";
};
zone "0.203.10.in-addr.arpa." {
    type primary;
    file "/etc/bind/lab-dns/lab-reverse.zone";
};
EOF

A zónafájlokban a teljes nevek végén álló pont jelentős: nélküle a parser hozzáfűzi az aktuális $ORIGIN értéket. A controls {}; az izolált példányok külön adminisztrációs vezérlőportját tiltja le, nem a DNS-kiszolgálást.

28.2.3.3 Rekurzív feloldó és indítás

Az Unbound stub-zone beállítása ismert autoritatív szerverhez irányítja a keresést; nem azonos egy másik rekurzív resolverhez küldő forward-zone beállítással. A reverse zóna itt explicit helyi stub, nem nyilvánosan delegált tartomány.

# Target: lab-dnsvm; UID 0.
cat > /etc/unbound/lab-dns/lab-unbound.conf <<'EOF'
server:
    interface: 10.203.0.55
    outgoing-interface: 10.203.0.55
    access-control: 10.203.0.0/24 allow
    username: "unbound"
    chroot: ""
    directory: "/etc/unbound"
    pidfile: ""
    use-syslog: no
    logfile: ""
    local-zone: "test." nodefault
    local-zone: "10.in-addr.arpa." nodefault

stub-zone:
    name: "test."
    stub-addr: 10.203.0.53

stub-zone:
    name: "0.203.10.in-addr.arpa."
    stub-addr: 10.203.0.54
EOF

named-checkconf -z /etc/bind/lab-dns/lab-parent.conf &&
named-checkconf -z /etc/bind/lab-dns/lab-child.conf &&
unbound-checkconf /etc/unbound/lab-dns/lab-unbound.conf || exit 1

ip netns exec lab-dns named -g -u bind \
    -c /etc/bind/lab-dns/lab-parent.conf \
    > /var/cache/bind/lab-dns/lab-parent.log 2>&1 &

ip netns exec lab-dns named -g -u bind \
    -c /etc/bind/lab-dns/lab-child.conf \
    > /var/cache/bind/lab-dns/lab-child.log 2>&1 &

ip netns exec lab-dns unbound -d \
    -c /etc/unbound/lab-dns/lab-unbound.conf \
    > /var/cache/bind/lab-dns/lab-resolver.log 2>&1 &

sleep 1
ip netns exec lab-dns ss -luntp

Várt eredmény: mindhárom címen UDP- és TCP-listener az 53-as porton. A háttérfolyamat sikeres elindítása önmagában nem bizonyítja a zónák kiszolgálhatóságát.

28.2.4 Lekérdezések és bizonyítékok

# Target: lab-dnsvm; UID 0; namespace: lab-dns.
ip netns exec lab-dns dig -b 10.203.0.10 \
    @10.203.0.53 lab-www.lab.test. A +norecurse

ip netns exec lab-dns dig -b 10.203.0.10 \
    @10.203.0.54 lab-www.lab.test. A +norecurse

ip netns exec lab-dns dig -b 10.203.0.10 \
    @10.203.0.55 lab-www.lab.test. A

ip netns exec lab-dns dig -b 10.203.0.10 \
    @10.203.0.55 -x 10.203.0.80

ip netns exec lab-dns dig -b 10.203.0.10 \
    @10.203.0.55 lab-www.lab.test. A +tcp

ip netns exec lab-dns dig -b 10.203.0.10 \
    @10.203.0.55 lab-missing.lab.test. A
Próba Várt megfigyelés
Szülő, rekurzió nélkül referral: gyermek NS az authority, glue az additional részben
Gyermek közvetlenül NOERROR, aa, A = 10.203.0.80
Unbound NOERROR, ra, rendszerint nincs aa
Reverse PTR = lab-www.lab.test.
TCP ugyanaz az érdemi válasz, mint UDP-n
Nem létező név NXDOMAIN, negatív cache-hez SOA

Az ismételt resolverlekérdezés TTL-je általában csökken. A közvetlen autoritatív válasz újra a zónában megadott TTL-t adja. A Query time egyetlen lekérdezés megfigyelése, nem benchmark.

A dig +trace saját iteratív bejárást végez, nem a szokásos resolver cache-ét vizsgálja:

# Target: lab-dnsvm; UID 0; szándékosan hiányos trace-topológia.
ip netns exec lab-dns dig -b 10.203.0.10 \
    @10.203.0.53 lab-www.lab.test. A +trace

Ez a labor nem szolgáltat DNS-gyökérzónát. A trace kezdeti gyökér-NS lekérdezése ezért várhatóan elakad; ez nem bizonyít gyermekzónahibát. Nyilvános hierarchián a trace gyökér → TLD → autoritatív útvonalat tár fel, de ehhez a kliensnek közvetlen UDP/TCP 53-as hozzáférés kell a bejárt szerverekhez. A +trace önmagában nem teljes DNSSEC-validálás.

28.2.5 Hibajelenségből hipotézis

Tünet Jelentés és első ellenpróba
NXDOMAIN A megkérdezett nézet szerint a név nem létezik. Közvetlenül kérdezzük a gyermek szervert; vizsgáljuk a negatív cache-t.
NOERROR, üres answer Lehet NODATA: a név létezik, de a kért rekordtípus nincs.
SERVFAIL A resolver nem tudott használható választ előállítani: hibás delegáció, elérhetetlen szerver, DNSSEC-hiba vagy más feldolgozási probléma.
timeout A kliens nem kapott választ a határidőig; ez nem DNS RCODE. Ellenőrizzük a listenert, útvonalat, UDP/TCP különbséget.
REFUSED A szerver policy alapján elutasította a kérést; például nem enged rekurziót.

A lekérdezésnapló bizonyítja, hogy egy kérdés eljutott a szerverhez, de nem helyettesíti a teljes response vizsgálatát.

# Target: lab-dnsvm; UID 0.
tail -n 20 /var/cache/bind/lab-dns/child/lab-queries.log

Cache-találatkor nem feltétlenül jelenik meg új gyermekoldali kérdés. Éles környezetben a query log érzékeny neveket tartalmazhat: hozzáférés, rövid megőrzés és terhelési korlát szükséges. A napló wall-clock időbélyegét ne keverjük a lekérdezés időtartamával.

28.2.6 TTL, változtatás és rollback

A „DNS propagation” többnyire nem globális továbbítás, hanem eltérő időpontokban lejáró cache-ek következménye.

Például a rekord TTL-je 300 s, a tervezett új TTL 30 s:

  1. A TTL-t előre csökkentjük, növeljük a serialt, ellenőrzünk és újratöltünk.
  2. Miután minden autoritatív példány az új TTL-t adja, legalább a korábbi 300 s-ot kivárjuk.
  3. Módosítjuk a címet, ismét új seriallal.
  4. Az autoritatív és resolverválaszt külön ellenőrizzük.

Ez TTL-t betartó cache-ekre vonatkozó terv. Alkalmazáscache és serve-stale policy külön feltétel.

A labor negatív TTL-je a SOA TTL és a SOA utolsó, MINIMUM mezőjének minimuma: itt min(300s,60s)=60s\min(300\,\mathrm{s},60\,\mathrm{s})=60\,\mathrm{s}. Egy most létrehozott név ezért egy korábban NXDOMAIN-t kapott resolvernél még hiányozhat.

Rollbackkor a régi rekordértéket új, nagyobb seriallal adjuk ki. Ez sem vonja vissza azonnal a már cache-elt új címet; a régi és új végpont átmeneti együttélését a szolgáltatásnak kell kezelnie.

28.2.7 Split DNS és bizalmi határok

Az osztott DNS (split DNS) ugyanarra a névre klienshelytől vagy resolverválasztástól függően eltérő választ ad. VPN vagy alkalmazásba épített DoH miatt egy nyilvános resolver megkérdezése nem bizonyítja a belső nézet hibáját.

  • DNSSEC: adateredetet és integritást ellenőriz aláírási lánccal és bizalmi horgonnyal; nem titkosít. Az AA nem kriptográfiai bizonyíték, az AD csak megbízható resolver és elérési út mellett értelmezhető.
  • DNS over TLS, DoT; DNS over HTTPS, DoH: a kliens–resolver szakaszt titkosítja és megfelelő tanúsítványellenőrzéssel hitelesíti. Nem teszi automatikusan hitelessé az autoritatív adatot.
  • A labor aláíratlan magánhierarchia, külön resolverkonfigurációval; nem demonstrál nyilvános DNSSEC-validálást.

DNSSEC-eredetű SERVFAIL esetén a resolvernapló, DS/DNSKEY-lánc, aláírásérvényesség és rendszeróra vizsgálandó. A globális validáláskikapcsolás nem javítás.

28.2.8 Feladatok

  1. Magyarázó: Miért működhet a közvetlen gyermeklekérdezés, miközben a resolver SERVFAIL választ ad? Miért nem segít önmagában a serial növelése egy régi A rekordot adó cache-en?
  2. Adminisztrációs: Csökkentsd a forward zóna alapértelmezett TTL-jét 30 s-ra. Ellenőrizd betöltés előtt és után, majd tervezd meg a visszaállítást.
  3. Diagnosztikai/recovery: A resolver NXDOMAIN-t ad, de az autoritatív szerver már ismeri a nevet. Adj bizonyítékgyűjtési és javítási tervet globális cache-ürítés nélkül.

28.2.9 Megoldások

  1. A közvetlen próba megkerüli a szülői delegációt, ezért hibás NS vagy glue mellett is sikerülhet. Ellenőrizzük a szülő referralját, majd az abban megadott végpontot. A serial a zónaverzióhoz tartozik, a resolver adatának érvényességét a TTL szabályozza. Utófeltétel: a teljes delegációs út és a közvetlen válasz összhangban van.

  2. A következő módosítás a labor kezdeti állapotára érvényes:

# Target: lab-dnsvm; UID 0.
cp /etc/bind/lab-dns/lab-forward.zone \
   /etc/bind/lab-dns/lab-forward.before

sed -i -e 's/^\$TTL 300$/\$TTL 30/' \
       -e 's/2025010101/2025010102/' \
       /etc/bind/lab-dns/lab-forward.zone

named-checkconf -z /etc/bind/lab-dns/lab-child.conf &&
kill -HUP "$(cat /var/cache/bind/lab-dns/child/lab-named.pid)"

ip netns exec lab-dns dig -b 10.203.0.10 \
    @10.203.0.54 lab-www.lab.test. A +norecurse
ip netns exec lab-dns dig -b 10.203.0.10 \
    @10.203.0.54 lab.test. SOA +norecurse

Utófeltétel: az autoritatív TTL 30 s, a serial 2025010102. A resolver régi TTL-je átmenetileg szabályos. Rollbackhez a mentett tartalmat 2025010103 seriallal állítjuk vissza, majd ugyanúgy ellenőrizzük és újratöltjük.

  1. Rögzítsük ugyanarra a teljes névre és típusra az autoritatív pozitív választ, valamint a resolver NXDOMAIN-válaszát és SOA TTL-jét. A laborban várjuk ki a negatív cache legfeljebb 60 s-os élettartamát, majd ismételjük meg. Utófeltétel: a resolver is pozitív választ ad. Ha nem, vizsgáljuk a tényleges resolvercímet, delegációt és split-DNS policyt; ne feltételezzünk automatikusan cache-hibát.

28.2.9.1 Leállítás és cleanup

Az alábbi eljárás csak a dedikált namespace folyamatait és a felsorolt laborkönyvtárakat érinti. Az evidence-et szükség esetén előbb archiváljuk.

# Target: lab-dnsvm; UID 0.
for pid in $(ip netns pids lab-dns); do
    kill -TERM "$pid"
done
sleep 2
test -z "$(ip netns pids lab-dns)" || exit 1

ip netns del lab-dns
rm -rf -- /etc/bind/lab-dns /etc/unbound/lab-dns \
           /var/cache/bind/lab-dns

ip netns list

Utófeltétel: nincs lab-dns namespace; a host eredeti resolver- és szolgáltatáskonfigurációja változatlan.

28.2.10 Rövid összefoglaló

A DNS-diagnosztika külön kezeli a konfigurációforrást, a betöltött autoritatív adatot és a resolver cache-ét. A közvetlen gyermeklekérdezés nem ellenőrzi a delegációt, a sikeres resolverválasz pedig származhat régi cache-ből. Az NXDOMAIN negatív válasz, a SERVFAIL feldolgozási kudarc, a timeout válaszhiány. Változtatás előtt a korábbi TTL-lel számolunk; rollbackkor új serial szükséges, de a cache-ek nem ürülnek ki automatikusan. A forward és reverse adat külön kezelendő. A query log célzott bizonyíték, adatvédelmi és terhelési költséggel. DNSSEC az adatbizalmat, DoT/DoH az átviteli szakasz védelmét szolgálja.

  • Delegáció: szülőzónában rögzített felelősségátadás.
  • Serial: a zóna összehasonlítható verziójelzője.
  • Negatív cache: hiányt jelző DNS-válasz időkorlátos tárolása.

28.2.11 Források és ellenőrzési hiányok

Az alábbiak ellenőrzési kiindulópontok, nem ebben a munkamenetben olvasott források:

  • BIND 9 dokumentáció — autoritatív konfiguráció, zónabetöltés, naplózás; a telepített kiadáshoz illesztendő.

  • RFC 4033: DNS Security Introduction and Requirements — DNSSEC bizalmi modell.
  • RFC 7858: DNS over TLS és RFC 8484: DNS over HTTPS — titkosított resolverelérés.
