23.5 Sysadmin köztes projekt és review

23.5.1 Motiváció

Egy Linux szolgáltatáshost akkor lép túl a „telepítve van, és most éppen fut” állapoton, ha a működtetési készültséget (operational readiness) bizonyítékkal igazoljuk. A szenior C++ fejlesztő számára az exit 0 build és a sikeres unit teszt megszokott visszajelzés, de a host rétegben ugyanezt a szerepet az automatikus elfogadási teszt (acceptance test) tölti be: a kívánt állapotot hasonlítja a megfigyelthez, és PASS/FAIL döntést ad. A d115 köztes projekt a korábbi sysadmin fejezeteket – package, user, storage, service, backup, hardening, inventory – egyetlen review-ba integrálja, mielőtt a tanuló a hálózati és Kubernetes fejezetek felé továbblépne.

23.5.2 Definíció és auditmodell

Sysadmin köztes projekt: egy izolált labhoston a d071–d114 alatt felépített Linux stack készültségének ellenőrzése. A cél nem új konfiguráció tervezése, hanem a meglévő host működtetési szerződésének hiányosságait feltáró, ismételhető review.

Acceptance test: olyan gépi ellenőrzés-sorozat, amely egyértelmű PASS vagy FAIL kimenetet ad, és a kimenetet időbélyeggel, valamint hashsel rögzíti. Az összegyűjtött kimenet az auditbizonyíték (audit evidence). Az acceptance teszt nem helyettesíti a hibakeresést, de megállapítja, hogy a host beléphet-e a megerősített üzemeltetési állapotba.

Operation readiness: a host azon tulajdonsága, hogy a szolgáltatás a felhasználói forgalmat kiszolgálja, és a rutin karbantartás, továbbá a hiba utáni helyreállítás a meglévő runbookkal végrehajtható.

A review a következő rétegeket járja be:

Réteg Ellenőrzési pont Acceptance feltétel
OS és package OS-verzió, csomagforrás Ubuntu 24.04 LTS, apt update hiba nélkül
Identitás és jog UID/GID, config permission labapp user létezik, offajta 640
Storage mount és kapacitás systemctl is-system-running, df rendben
Service systemd unit, aktív állapot lab-worker.service active
SSH és security sshd effektív paraméterek, AppArmor PermitRootLogin no, PasswordAuthentication no
Resource limits MemoryMax, CPUQuota, Restart limit nem infinity, restart beállított
Backup snapshot, restore restic snapshot létezik, restore smoke sikeres
Monitoring metrics/log endpoint node_exporter HTTP 200
Config/inventory forrás és drift inventory hash egyezik

A fenti sorrend réteghatár szerint halad: előbb a host identitása és állapota, utána a szolgáltatás, végül a recovery és a bizonyíték.

23.5.3 Kidolgozott példa

A példa hostja lab-review-01, felhasználói labadmin (UID 1000, sudo) és labapp (UID 1001), a szolgáltatás lab-worker.service, a mentési felhasználó labbackup. A labhost Ubuntu Server 24.04 LTS amd64, a példa az izolált labVM-en fut. Az alábbi lab-acceptance.sh script nem módosít, csak olvas; a cél az auditbizonyíték PASS/FAIL táblázatba gyűjtése.

#!/usr/bin/env bash
set -euo pipefail

HOST="lab-review-01"
OUT="/var/tmp/${HOST}-acceptance-$(date +%Y%m%dT%H%M%S).txt"
PASS=0; FAIL=0

check() {
  local name="$1"; local result="$2"; local detail="$3"
  if [[ "$result" == "PASS" ]]; then PASS=$((PASS+1)); else FAIL=$((FAIL+1)); fi
  printf '%-40s %-4s %s\n' "$name" "$result" "$detail" | tee -a "$OUT"
}

# OS baseline
. /etc/os-release
[[ "$VERSION_ID" == "24.04" ]] && R=PASS || R=FAIL
check "os_ubuntu_2404" "$R" "VERSION_ID=$VERSION_ID"

# Service identity
id -u labapp >/dev/null 2>&1 && R=PASS || R=FAIL
check "user_labapp_exists" "$R" "uid=$(id -u labapp 2>/dev/null || echo missing)"

stat -c '%U:%G %a' /srv/labapp/config.yaml 2>/dev/null | grep -q 'labapp:labapp 640' && R=PASS || R=FAIL
check "config_permission" "$R" "$(stat -c '%U:%G %a' /srv/labapp/config.yaml 2>/dev/null || echo missing)"

# systemd és szolgáltatás
systemctl is-system-running >/dev/null 2>&1 && R=PASS || R=FAIL
check "systemd_system_running" "$R" "$(systemctl is-system-running 2>&1 || true)"

systemctl is-active --quiet lab-worker.service && R=PASS || R=FAIL
check "service_active" "$R" "$(systemctl is-active lab-worker.service 2>&1 || true)"

# SSH baseline
sshd -T 2>/dev/null | grep -qi '^permitrootlogin no$' && R=PASS || R=FAIL
check "sshd_permitrootlogin_no" "$R" "effective sshd setting"

sshd -T 2>/dev/null | grep -qi '^passwordauthentication no$' && R=PASS || R=FAIL
check "sshd_passwordauth_no" "$R" "effective sshd setting"

# Resource limits
MemoryMax=$(systemctl show lab-worker.service -p MemoryMax --value 2>/dev/null || echo missing)
[[ "$MemoryMax" != "infinity" && -n "$MemoryMax" ]] && R=PASS || R=FAIL
check "service_memory_limit" "$R" "MemoryMax=$MemoryMax"

# Backup: snapshot létezik
sudo -u labbackup restic -r /srv/backup/labapp snapshots >/dev/null 2>&1 && R=PASS || R=FAIL
check "backup_snapshot_exists" "$R" "restic snapshot"

# Monitoring endpoint
curl -fsS http://127.0.0.1:9100/metrics >/dev/null 2>&1 && R=PASS || R=FAIL
check "node_exporter_metrics" "$R" "http://127.0.0.1:9100/metrics"

# Inventory és runbook
[[ -f /etc/lab/inventory.yaml ]] && R=PASS || R=FAIL
check "inventory_exists" "$R" "/etc/lab/inventory.yaml"

[[ -f /etc/lab/runbook.md ]] && R=PASS || R=FAIL
check "runbook_exists" "$R" "/etc/lab/runbook.md"

printf 'PASS=%d FAIL=%d EVIDENCE=%s\n' "$PASS" "$FAIL" "$OUT" | tee -a "$OUT"
[[ "$FAIL" -eq 0 ]]

A script lefuttatása labadmin joggal, a lab-review-01 konzolján, előfeltétel hogy a labapp, labbackup user és a fenti elérési utak léteznek. Módosítást nem végez; a sudo -u labbackup sor csak a mentési repó olvasását teszi lehetővé. A várt, illusztratív kimenet:

os_ubuntu_2404                           PASS VERSION_ID=24.04
user_labapp_exists                       PASS uid=1001
config_permission                        PASS labapp:labapp 640
systemd_system_running                   PASS running
service_active                           PASS active
sshd_permitrootlogin_no                  PASS effective sshd setting
sshd_passwordauth_no                     PASS effective sshd setting
service_memory_limit                     PASS MemoryMax=512M
backup_snapshot_exists                   PASS restic snapshot
node_exporter_metrics                    PASS http://127.0.0.1:9100/metrics
inventory_exists                         PASS /etc/lab/inventory.yaml
runbook_exists                           PASS /etc/lab/runbook.md
PASS=12 FAIL=0 EVIDENCE=/var/tmp/lab-review-01-acceptance-20250101T120000.txt

A snapshot létezése önmagában kevés a helyreállítási képesség igazolásához; ezért a review második fele a backup restore smoke check. A labbackup userrel, a cél a labapp adatkönyvtár tartalmának bitre pontos visszaállítása egy kijelölt átmeneti könyvtárba:

# Cél: lab-review-01, labbackup (sudo -u labbackup)
# Előfeltétel: a restic repository /srv/backup/labapp korábban sikeres snapshottal rendelkezik.
# Ellenőrzés: a legfrissebb snapshot visszaállítás után a fájlok diff nélkül egyeznek.
sudo -u labbackup restic -r /srv/backup/labapp check --read-data-subset=1%
sudo -u labbackup restic -r /srv/backup/labapp restore latest \
  --target /var/tmp/labapp-restore-smoke
diff -r /srv/labapp/data /var/tmp/labapp-restore-smoke/srv/labapp/data && \
  echo "RESTORE_SMOKE PASS"
# Cleanup: csak a kijelölt smoke könyvtárat töröljük.
rm -rf /var/tmp/labapp-restore-smoke

A restore smoke diff -r kimenete üres, ha a visszaállítás bitre pontos. A --read-data-subset=1% a nagy repository mellett is ellenőrzi a pack integritását anélkül, hogy a teljes állományt olvasná. A rm -rf kizárólag a /var/tmp/labapp-restore-smoke kijelölt labkönyvtárra mutat.

Az incident drill a process recovery-t gyakorolja. A lab-worker.service unitja beállított Restart=on-failure-rel; a SIGKILL utáni automatikus újraindulás így ellenőrizhető:

# Cél: lab-review-01, labadmin
# Előfeltétel: az acceptance script minden pontja PASS; karbantartási ablak.
# Rollback baseline: a drill előtt biztosítjuk a szolgáltatás restartját.
systemctl restart lab-worker.service
# Drill: a főfolyamatot SIGKILL-jel állítjuk le.
systemctl kill -s SIGKILL lab-worker.service
sleep 3
# Ellenőrzés: a systemd Restart= policy újraindította a szolgáltatást.
systemctl is-active --quiet lab-worker.service && echo "RECOVERY_DRILL PASS"

A kill -s SIGKILL nem hagy esélyt a clean shutdownra; a systemd csak akkor indítja újra, ha a Restart= beállítás ezt engedi. A drill után a healthcheck HTTP 200-at ad, bizonyítva a process recovery-t.

23.5.4 Inventory, runbook és patch policy

A review harmadik eleme a karbantartási szerződés. A /etc/lab/inventory.yaml a host desired state-jét írja le: package lista, UID/GID, systemd unitok, filesystem mountok, SSH policy, backup repository. A runbook /etc/lab/runbook.md a szolgáltatás indítását, leállítását, naplózását és a leggyakoribb hibaeseteket – OOM, disk tele, config hiba – írja le. A patch policy az apt források lab-review-01-re kijelölt time windowját, a unattended-upgrades security-only beállítását és a kernelupdate utáni reboot-triggert rögzíti. A d114 automatizált karbantartás szerződéséből ismert, hogy a patch előtti/utáni drift-riport akkor megbízható, ha a desired state versioned inventory fájlban van.

23.5.5 Hibák és ellenpróbák

A legnagyobb hiba a hamis magabiztosság: a systemctl is-active csak annyit jelent, hogy a process fut, de semmit sem mond arról, hogy a labapp válaszol-e HTTP-n. Amikor a node_exporter endpoint PASS, de az alkalmazás healthcheckje hiányzik, a szolgáltatás láthatóan aktív, miközben a backend végpont hibás. A javítás egyértelmű: a script bővül curl -fsS http://127.0.0.1:8080/healthz ellenőrzéssel.

A backup acceptance gyakori hibája, hogy a snapshot létezése nem bizonyítja a visszaállíthatóságot. A restic repository sérült packját a snapshots parancs még ki tudja listázni, a restore viszont meghiúsul. A check --read-data-subset=1% hozzáadása felfedi a sérülést. A hibakereséshez restic check --read-data-subset=20% futtatható, ha a gyors ellenőrzés nem elég.

A security review kockázata a lockout. Ha a hardening során a PasswordAuthentication no beállítás érvényes, de a kulcsos belépés nem tesztelt, a labadmin kizárhatja magát. A negative access test – kulcs nélküli jelszavas belépés elutasítása – és a recovery console-on kulcsos SSH pozitív tesztje együttesen ad biztosítékot. A sshd -t a konfigurációs szintaxisra, a sshd -T az effektív értékekre vonatkozik; egyik sem helyettesíti a tényleges belépési kísérletet.

A config drift gyakori forrása a kézi módosítás. Ha az inventory YAML a labapp/config.yaml hashét nem őrzi, a drifttel kapcsolatos hibát csak akkor vesszük észre, amikor a szolgáltatás már megbukott. A javítás: a desired state fájl sha256sum értéke, és az acceptance script ezt hasonlítja a tényleges fájlhoz.

23.5.6 Feladatok

  1. Magyarázó feladat. Tervezze meg a lab-review-01 elfogadási sorrendjét! Válasszon ki legalább hat ellenőrzést a fenti táblázatból, és indokolja, miért ebben a sorrendben kell ezeket futtatni. Térjen ki arra, hogy a hostidentitást miért a service-ellenőrzés előtt kell elvégezni.

  2. Adminisztrációs/konfigurációs feladat. Bővítse a lab-acceptance.sh scriptet egy HTTP 200-as healthcheckkel a labapp szolgáltatásra, valamint a /srv/labapp/config.yaml inventory hash-összehasonlításával. Ezután csökkentse a lab-worker.service MemoryMax értékét 100M-ra, futtassa az elfogadási scriptet, és magyarázza meg, miért jelenik meg FAIL a resource-limit sorban. Állítsa vissza a korábbi limitet.

  3. Diagnosztikai/failure/recovery feladat. A lab-worker.service a SIGKILL drill után nem indul újra, és a journalctl OOMKill üzenetet mutat. Gyűjtse be a naplót, azonosítsa a túl alacsony MemoryMax értéket, emelje meg a limitet, indítsa újra a szolgáltatást, és bizonyítsa a healthcheck sikeres válaszát.

23.5.7 Megoldások

  1. Az ellenőrzési sorrend például: (1) OS verzió, (2) user létezése, (3) config permission, (4) systemd állapot, (5) service active, (6) SSH effective. A hostidentitást az OS és a user szintjén ellenőrizni kell, mielőtt a service állapotára hivatkoznánk: ha a labapp user hiányzik, a service hiába aktív, a jogosultsági modell sérült. Az SSH-t a security review során külön kell validálni, mert a lockout kockázatot kizárólag negative/positive tesztekkel kezeljük. Postcondition: a script a megadott sorrendben ad PASS/FAIL táblázatot, és a hostidentitási hibák nem maradnak rejtve.

  2. A bővített script a következő sorokkal egészül ki:

curl -fsS http://127.0.0.1:8080/healthz >/dev/null 2>&1 && R=PASS || R=FAIL
check "service_healthz" "$R" "http://127.0.0.1:8080/healthz"

expected_hash=$(cat /etc/lab/inventory-desired-config.sha256 2>/dev/null || echo missing)
actual_hash=$(sha256sum /srv/labapp/config.yaml 2>/dev/null | awk '{print $1}')
[[ "$expected_hash" == "$actual_hash" ]] && R=PASS || R=FAIL
check "config_drift" "$R" "expected=$expected_hash actual=$actual_hash"

A MemoryMax=100M átállítás systemctl set-property lab-worker.service MemoryMax=100M paranccsal történik, majd a systemctl daemon-reload és a service restart szükséges. Az elfogadási script service_memory_limit sora MemoryMax=104857600 értéket mutat, ami nem infinity, ezért PASS; a hibát a service_active vagy a service_healthz FAIL jelzi, ha a szolgáltatás a korlátozás miatt nem tud elindulni. A rollback: systemctl set-property lab-worker.service MemoryMax=512M, majd systemctl restart lab-worker.service. Postcondition: a healthcheck ismét 200-at ad, a config hash egyezik.

  1. A diagnosztika lépései: journalctl -u lab-worker.service -n 50 -p err megmutatja az OOMKill bejegyzést. A systemctl show lab-worker.service -p MemoryMax --value alacsony értéket ad. A javítás systemctl set-property lab-worker.service MemoryMax=1G, majd systemctl restart lab-worker.service. A végén curl -fsS http://127.0.0.1:8080/healthz és systemctl is-active --quiet lab-worker.service igazolja a felépülést. Postcondition: a szolgáltatás a megnövelt korlát mellett aktív, a healthz 200-at ad, és a journalctl nem mutat új OOM bejegyzést.

23.5.8 Rövid összefoglaló

A sysadmin köztes projekt egyetlen labhoston foglalja össze a korábbi fejezetek üzemeltetési gyakorlatát: az acceptance script PASS/FAIL döntéseket gyűjt a host identitás, jogosultság, systemd, SSH, resource limit, backup, monitoring és inventory rétegekről. A backup snapshot megléte önmagában nem elég; a restore smoke checknek diff-tel alátámasztottan kell igazolnia a visszaállíthatóságot. A process recovery drill a Restart= policy-t SIGKILL-lel teszteli. A hiányzó backup/access/monitoring szerződés a script FAIL soraiban válik láthatóvá, nem a feltételezésekben.

Továbbhasznált definíciók:
- Acceptance test: a desired state és a megfigyelt állapot gépi összehasonlítása, mely PASS/FAIL kimenetet ad.
- Audit evidence: az acceptance teszt időbélyegzett, hashsel rögzített kimenete.
- Restore smoke check: a backupból végrehajtott, korlátozott célú visszaállítás, amely diff-fel igazolja az adat bitre pontos megegyezését.
