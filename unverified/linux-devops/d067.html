14.2 Repository trust, pinning és mirror

14.2.1 Motiváció

A csomagtelepítés akkor biztonságos, ha nemcsak azt tudjuk, mit telepítünk, hanem azt is, hogy a csomag valóban a megjelölt forrásból származik, és a forrás verziója nem változott meg azóta, hogy jóváhagytuk. Egy kiadott C++ alkalmazás production image-e akkor reprodukálható, ha a csomagforrások, a prioritások és a kulcsok egyértelműen rögzítettek. Ha a repository trust, pinning és mirror politika laza, akkor egy harmadik fél csomagja felülírhat egy kritikus rendszerkönyvtárat, vagy egy régi, sebezhető verzió ragadhat be a rendszerben.

Ez az alfejezet a csomagforrás hitelességét, a repository kulcsok hatókörét, a harmadik fél források kezelését, a mirror/proxy működését, valamint a verziópinning és hold kockázatait tárgyalja. A cél, hogy a repository politika auditálható, reprodukálható és biztonsági frissítésekre alkalmas legyen.

14.2.2 Repository trust modell: signed metadata és package signature

A Debian/Ubuntu apt és az RPM-alapú rendszerek eltérő aláírási modellt használnak, de a közös elv az: a csomagtároló metadata (leíró adat) aláírással igazolja a csomagok listáját és hash-eit.

14.2.2.1 Signed metadata versus package signature

A Debian/Ubuntu modellben a repository közzéteszi a kiadási metadata (Release/InRelease/Release.gpg) fájlokat. Az InRelease beágyazott OpenPGP-aláírást tartalmaz, míg a Release mellett külön Release.gpg aláírás található. Ez a metadata tartalmazza a csomagindexek (pl. Packages, Sources) SHA256 hash-eit. A csomagok maguk nem feltétlenül aláírtak; a lánc a metadata aláírásból és a hash-ekből áll. Így elegendő a repository kulcsot megbízni, és az apt minden letöltött indexcsomagot ellenőriz.

Ezzel szemben az RPM-alapú rendszerek (Fedora, RHEL) a repomd.xml és a hozzá tartozó repomd.xml.asc aláírást ellenőrzik, de a csomagok gyakran külön csomag-aláírást is hordoznak. A repository szintű aláírás a tranzakció-határt, a csomag-aláírás a build-forrást igazolja.

A package signature (csomag-aláírás) csak az egyes csomag hitelességét igazolja, de nem igazolja, hogy a csomag az adott repository kiadási állapotába tartozik. A signed metadata ezt a teljes kiadási állapotot rögzíti, így a rollback vagy régi index visszajátszása ellen is véd. A repository trust lánc ezért a metadata aláírást tekinti a gyökérnek.

14.2.2.2 Repository kulcs scope és keyring

Az apt az OpenPGP kulcsokat keyring fájlokban tárolja. Modern, biztonságos elrendezésben minden repository-hoz saját keyring tartozik, és a forrásbejegyzés signed-by opcióval mutat rá:

deb [signed-by=/usr/share/keyrings/lab-repo.gpg] https://packages.lab.invalid/ubuntu stable main

A régi apt-key add parancs a globális /etc/apt/trusted.gpg kulcstartóba írt, ahol a kulcs minden más repository-ra is érvényes volt. Ez a kulcs scope megsértése: ha egy harmadik fél kulcsa globálisan megbízott, akkor bármely repository bejegyzését aláírhatná, függetlenül attól, hogy mi az adott forrás tulajdonosa. A modern gyakorlat ezért:

  • a kulcsokat a /usr/share/keyrings/ könyvtárba menti, root által írható helyre;
  • a forráslistában minden repository-hoz signed-by opcióval rendeli a kulcsot;
  • a kulcs fingerprintjét (ujjlenyomat) explicit módon, külön csatornán ellenőrzi.

Fontos, hogy a kulcs importálás előtt megjelenített ujjlenyomata az ellenőrzési alap; a gpg --show-keys --fingerprint kimenetét a repository hivatalos dokumentációjával kell összevetni. A példában a lab-repo kulcs egy labgenerált, nem titkos tesztkulcs, így a fingerprint ellenőrzése a laborban történik.

14.2.3 Harmadik fél repository és source policy

Harmadik fél repository használata esetén a forráspolitika legyen minimális és auditálható:

  • Minimal trust: csak azt a komponenst és architektúrát engedélyezzük, amelyre szükség van. Kerüljük a deb https://thirdparty.example all main típusú túl széles bejegyzéseket. A stable vagy main komponens mellett a contrib/non-free csak akkor szerepeljen, ha ténylegesen kell.
  • Explicit release csatorna: a repository bejegyzés ne mutasson latest vagy rolling kiadásra, hanem konkrét kódnévre vagy verzióra. Így a kiadási állapot reprodukálható.
  • Separate source list: minden harmadik fél forrás külön fájlba kerüljön /etc/apt/sources.list.d/ alatt, így a forrás eltávolítása és auditálása egyszerű.
  • Korlátozott csomagok: pinning segítségével biztosítjuk, hogy a harmadik fél repositoryból csak a megjelölt csomagok települjenek, és ne írja felül a disztribúció által kezelt csomagokat.

A pinning az apt prioritási rendszere. A /etc/apt/preferences.d/ alatt lévő fájlokban megadhatjuk, hogy egy adott csomag vagy globális minta melyik forrásból származó verzióját részesítse előnyben. A prioritások: 1000 felett downgrade-et is enged; 990 az explicit default release; 500 a normál; 100 alacsony; -1 tiltás. A biztonság kedvéért harmadik fél csomagoknál 700-as prioritást használunk: magasabb, mint a default 500, de nem erőltet downgrade-et.

14.2.4 Mirror, proxy/cache és offline rebuild

A mirror a hivatalos repository teljes vagy részleges másolata. Belső hálózatban a frissítések gyorsabbak, és a külső hálózati kitettség csökken. A mirror frissítése azonban időzített; ha a tükör lemarad, a biztonsági frissítések késnek. A mirror snapshot készítése azt jelenti, hogy a repository állapotát egy időpillanatban rögzítjük, így reprodukálható telepítést kapunk.

A proxy/cache (pl. Apt-Cacher NG, Squid) a csomagletöltést gyorsítja, de nem hitelesíti a tartalmat; a hitelességet az apt aláírás-ellenőrzése biztosítja. A cache nem helyettesíti a mirror snapshotot.

Az offline rebuild a forráskódból történő csomagépítést jelenti: a deb-src bejegyzésekkel letöltjük a forráscsomagot, majd apt-get build-dep és dpkg-buildpackage segítségével saját környezetben fordítjuk. Ez akkor hasznos, ha a bináris csomag készletéből hiányzik egy architektúra, vagy ha a szállító által aláírt bináris nem megbízható. A rebuild során a forráskód provenance-át (származási láncát) a .dsc, Build-Depends és a source hash-ek igazolják.

14.2.5 Pin/hold és stale security update kockázat

A hold (visszatartás) megakadályozza egy csomag automatikus frissítését akkor is, ha az apt upgrade fut. Ezt az apt-mark hold csomag paranccsal lehet beállítani. A hold hasznos lehet, ha egy adott verziótól való eltérés azonnal regressziót okozna, de súlyos kockázatot hordoz: ha a csomaghoz később biztonsági frissítés érkezik, a hold megakadályozza a sebezhetőség javítását. Ezért a hold csak időkorlátos, felülvizsgálati dátummal ellátott, dokumentált kivétel legyen.

A stale security update kockázat azt jelenti, hogy a rögzített verzió egyre régebbi lesz, és a hozzá tartozó CVE-k nem javulnak. A hold policy ezért:

  • a hold okát a változáskezelési jegyben rögzítjük;
  • lejárati dátumot rendelünk hozzá;
  • ha lehetséges, a pinninget inkább egy harmadik fél, patchelt csomagra irányítjuk, mintsem a frissítést teljesen letiltjuk.

14.2.6 Kidolgozott példa: lab-repo trust és pinning

A cél egy lab-repo nevű, izolált labor repository bejegyzése a labhoston, kizárólag a labtool csomaghoz. A repository kulcsa külön keyringben van, és a pinning 700-as prioritást ad a labtool csomagnak a lab-repo-ból származó verziójához.

Labkörnyezet: lab1 VM, Ubuntu Server 24.04 LTS amd64, felhasználó labuser sudo joggal, a repository URL https://packages.lab.invalid/ubuntu.

Előfeltétel: a lab-repo a laborhálózatban elérhető, a labor saját tesztkulcsa (lab-repo-pubkey.asc) a labuser home könyvtárában van. Az alábbi parancsok nem futnak le a tananyag generálása során; a kimenet illusztratív.

14.2.6.1 1. Kulcs importálása és ujjlenyomat ellenőrzése

sudo gpg --no-default-keyring \
  --keyring /usr/share/keyrings/lab-repo.gpg \
  --import /home/labuser/lab-repo-pubkey.asc

gpg --no-default-keyring \
  --keyring /usr/share/keyrings/lab-repo.gpg \
  --show-keys --fingerprint

Várt kimenet (illusztratív, nem valós kulcsérték):

pub   rsa4096 2025-01-01 [SC]
      1234 5678 9ABC DEF0 1234 5678 9ABC DEF0 1234 5678
uid           Lab Repository <lab-repo@lab.invalid>

A fingerprintt a labor jegyzőkönyvében rögzített értékkel kell összevetni.

14.2.6.2 2. Forrásbejegyzés létrehozása

echo "deb [signed-by=/usr/share/keyrings/lab-repo.gpg] \
  https://packages.lab.invalid/ubuntu stable main" | \
  sudo tee /etc/apt/sources.list.d/lab-repo.list

14.2.6.3 3. Pinning beállítása

A /etc/apt/preferences.d/lab-repo.pref:

Package: labtool
Pin: origin packages.lab.invalid
Pin-Priority: 700

Az origin mező a Release fájl Origin értékének felel meg, nem az URL-nek. A 700-as prioritás lehetővé teszi a preferált forrásból való telepítést, de nem enged downgrade-et 1000 fölé.

14.2.6.4 4. Frissítés és ellenőrzés

sudo apt update
apt-cache policy labtool

Várt kimenet:

labtool:
  Installed: (none)
  Candidate: 1.2.0
  Version table:
     1.2.0 700
        700 https://packages.lab.invalid/ubuntu stable/main amd64 Packages

Ha a kimenetben a 700 prioritás jelenik meg, a pinning működik. Ha a repository nem érhető el, az apt update hibát jelez, de a konfiguráció akkor is ellenőrizhető.

14.2.7 Tipikus hibák és ellenpróbák

Hiba 1: A harmadik fél repository felülírja a disztribúció csomagját.

Tünet: apt upgrade után a rendszer core library-jei harmadik fél verziójúak. Hipotézis: a repository globális prioritása magasabb, mint a hivatalos. Adatgyűjtés: apt-cache policy <csomag> és a /etc/apt/preferences.d/ tartalma. Egy változtatás: pinninget csak a szükséges csomagra szűkíteni. Ellenőrzés: apt-cache policy újra.

Hiba 2: A labtool csomag nem frissül biztonsági frissítésre, mert hold alatt van.

Tünet: apt-mark showhold kiírja. Hipotézis: a hold lejárt, de a jegy nem intézkedett. Adatgyűjtés: apt-cache policy labtool és a biztonsági forrás elérhetősége. Megoldás: hold feloldása (sudo apt-mark unhold labtool), majd a biztonsági verzió telepítése. Ellenőrzés: apt-cache policy a javított verziót mutatja.

Hiba 3: Nem megbízható kulcs miatt az apt update hibát ad.

Tünet: Err:1 https://packages.lab.invalid/ubuntu stable InRelease The following signatures couldn't be verified.... Hipotézis: a keyring kulcs hiányzik vagy a forrás signed-by rossz. Adatgyűjtés: ls -l /usr/share/keyrings/lab-repo.gpg, grep -R signed-by /etc/apt/sources.list.d/. Megoldás: kulcs újraimportálása vagy signed-by javítása. Ellenőrzés: apt update sikeres.

14.2.8 Feladatok

14.2.8.1 1. Magyarázó feladat

Magyarázza el, mi a különbség a signed metadata és a package signature között. Miért nem elegendő önmagában a csomag-aláírás a repository trust lánc biztosításához? Térjen ki arra, hogy a régi apt-key add miért sérti a kulcs scope-ot.

14.2.8.2 2. Adminisztrációs feladat

A labVM-en hozzon létre egy lab-repo forrásbejegyzést a fenti minta alapján. Importálja a tesztkulcsot a /usr/share/keyrings/lab-repo.gpg keyringbe, és állítson be 700-as prioritást kizárólag a labtool csomaghoz. Ellenőrizze az apt-cache policy labtool kimenetét.

Postcondition: a /etc/apt/sources.list.d/lab-repo.list létezik, a lab-repo.gpg keyring csak ezt a repository-t hitelesíti, a labtool candidate 700-as prioritással a lab-repo-ból jön.

14.2.8.3 3. Diagnosztikai/failure feladat

Egy kolléga egy harmadik fél repositoryt adott hozzá, és most a libssl csomag a harmadik fél verziójára mutat, ráadásul egy régebbi verzióra downgrade-el. Az apt-cache policy libssl kimenetében a 1001 prioritás jelenik meg a harmadik fél forrásnál. Diagnosztizálja a hibát, és módosítsa a pinninget úgy, hogy a hivatalos Ubuntu biztonsági forrás kapjon magasabb prioritást, de a harmadik fél ne írhassa felül a rendszerkönyvtárat. Ellenőrizze a policy kimenetét.

14.2.9 Megoldások

14.2.9.1 1. Megoldás

A signed metadata a repository teljes kiadási állapotát aláírja: a Release/InRelease fájl hash-ekkel hivatkozik minden indexre. Ez véd a régi index visszajátszása ellen. A package signature csak az egyes csomag integritását igazolja, de nem köti a repository snapshot-hoz. A apt-key add globális trustot adott: bármely repository bejegyzést aláírhatott a kulcs, így a scope nem volt korlátozva; a modern signed-by ezt repository-szinten szűkíti.

14.2.9.2 2. Megoldás

A parancsok a fenti kidolgozott példában szerepelnek. A kritikus lépés a fingerprint ellenőrzése az importálás után. A pinning fájlban a Pin: origin az Origin mezőt célozza, nem az URL-t. A apt-cache policy kimenetén a 700-as prioritás igazolja a kívánt állapotot.

14.2.9.3 3. Megoldás

Hiba: a harmadik fél repository prioritása 1001, ami downgrade-et is enged. Megoldás: a harmadik fél repositoryhoz tartozó pinningben a prioritást 100 alá vagy -1-re állítani, vagy a libssl csomagra pozitív pinninget adni a hivatalos security forrásra. Például:

Package: libssl*
Pin: release a=ubuntu-security
Pin-Priority: 990

Package: *
Pin: origin thirdparty.example
Pin-Priority: 100

Ellenőrzés: apt-cache policy libssl a hivatalos verziót mutatja magasabb prioritással. Postcondition: a libssl a hivatalos disztribúcióból frissül, a harmadik fél nem befolyásolja.

14.2.10 Rövid összefoglaló

A repository trust a signed metadata aláírásán alapul; a csomag-aláírás önmagában nem biztosít kiadási állapotot. A kulcsokat repository-szintű keyringgel és signed-by opcióval szűkítjük, így egy harmadik fél kulcs nem terjed ki más forrásokra. A pinning preferenciát ad, a hold frissítést tilt, de utóbbi stale security update kockázatot hordoz. A mirror/proxy gyorsít, de a hitelességet nem helyettesíti; az offline rebuild a forrásprovenance-t igazolja. A változtatásokat auditálni és lejárati dátummal kezelni kell.

Továbbhasznált definíciók: - Signed metadata: a repository kiadási állapotát hash-ekkel rögzítő, OpenPGP-vel aláírt leíró adat. - Pinning: az apt prioritási szabálya, amely egy adott csomag vagy minta forrását és verzióját preferálja. - Hold: csomagfrissítés visszatartása, amely biztonsági frissítések elmaradását okozhatja.

14.2.11 Források és ellenőrzési hiányok

  • Ubuntu Server documentation — általános kiindulópont, nem olvasott bizonyíték.
  • Debian documentation — általános kiindulópont, nem olvasott bizonyíték.
  • Linux man-pages — a apt-get, sources.list, apt_preferences, gpg man oldalak a tananyag írásakor ellenőrizendők.

Ellenőrzési hiányok: a konkrét Ubuntu 24.04 csomagverziók, a default repository komponensek, a deb822 formátum pontos szintaxisa, valamint a harmadik fél repository kulcsok és pinning mezők pontos értékei a lab során ellenőrizendők. A technológiai állítások a verzióprofilban rögzített Ubuntu Server 24.04 LTS-re vonatkoznak, de a generálás pillanatában aktuális support státuszuk nem ellenőrzött.
