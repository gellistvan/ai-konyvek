54.5 HA és adatplatform failure game day

54.5.1 Motiváció, definíció és működés

A d265-ben felépített stateful stack (PostgreSQL, Redis, RabbitMQ) a d269 kapacitástervezés után már rendelkezik deklarált hibatűrési vállalásokkal. Ám ezek a vállalások papíron nem bizonyítanak semmit: a helyreállítási időcél (recovery time objective, RTO), a helyreállítási pont cél (recovery point objective, RPO) és a szolgáltatási szint cél (service level objective, SLO) csak akkor hiteles, ha aktív teszteléssel igazoljuk. A failure game day tervezett, időkorlátos, izolált környezetben végrehajtott incidensszimuláció, amelyben egy kiválasztott hibatartományt (failure domain) szándékosan kiesést okozunk, és a rendszer válaszát mérjük a vállalásokkal szemben. A játék célja nem a „rombolás”, hanem bizonyítékgyűjtés (acceptance evidence) az elfogadási kritériumokhoz. Minden game daynek van előre meghatározott hipotézise, rollback terve és stop condition-je. A hipotézis azt mondja meg, hogy mit várunk a kiesés hatására; a rollback az eredeti állapot visszaállításának lépései; a stop condition pedig az a küszöb, amelynek elérésekor a tesztet azonnal leállítjuk, hogy a lab környezet ne szenvedjen helyrehozhatatlan kárt.

A gyakorlatban négy gyakori failure domain scenario-t különböztetünk meg: - Single node: egy VM vagy fizikai gép leáll, a rajta futó adatbázis, queue vagy cache kiesik. - Link: hálózati szegmens megszakad, ami particionálja a clustert. - Zone: egy elérhetőségi zóna (availability zone) teljes kiesése, ami több node egyidejű elvesztését okozza. - Credential: egy szolgáltatásfiók vagy tanúsítvány elveszti a jogosultságát, így a komponens nem fér hozzá a szükséges erőforráshoz.

A játék során figyelni kell a quorum, a lag és a rebuild állapotára. A quorum (többség) a klasszikus elosztott konszenzus feltétele: egy RabbitMQ quorum queue vagy egy Patroni-vezérelt PostgreSQL cluster akkor marad elérhető, ha a node-ok többsége kommunikálni tud egymással. A replication lag az elsődleges és a másodlagos adatbázis közötti késleltetés, amely meghatározza az RPO-t aszinkron replikációnál. A rebuild pedig egy kiesett node újraépítése a többiek adataiból; ennek ideje a hálózati sávszélesség, a lemezsebesség és a jelenlegi kapacitás állapot függvénye. A graceful degradation azt jelenti, hogy a szolgáltatás csökkentett funkcionalitással, de működik tovább; a retry budget pedig azt számszerűsíti, hogy a kliensek hány újrapróbálkozást tolerálnak, mielőtt a kérés az SLO-n kívülre kerül. A game daynek ezt is mérnie kell, hiszen a degradált állapotban a retry budget gyorsan elfogyhat.

A restore versus failover/failback döntés a game day legfontosabb operatív dilemmája. A failover egy tartalék node azonnali átvételét jelenti: rövid RTO, de ha a replikáció aszinkron volt, a legutolsó commitok elveszhetnek (RPO > 0). A restore a korábbi base backup és WAL-szegmensek visszajátszásával adott időpontra állítja vissza az adatbázist: pontos RPO, de hosszú RTO, mert a teljes adatmennyiséget újra kell tölteni. A failback a failover után az eredeti primary visszaállítása, ami újabb átállást és adatszinkronizálást igényel. A game day során ezeket a tradeoffokat mért adatok alapján kell értékelni, nem érzésre.

54.5.2 Kidolgozott példa

A lab stack a d265-ből ismert állapotkezelő környezet, kiegészítve Patroni-vezérelt PostgreSQL clusterrel. A topology fixture explicit:

Node Szerep Fail. domain IP (privát lab) Context
lab-pg1 PostgreSQL primary rack1, zone1 192.0.2.11 lab-cluster
lab-pg2 PostgreSQL sync standby rack2, zone1 192.0.2.12 lab-cluster
lab-pg3 PostgreSQL async standby rack2, zone2 192.0.2.13 lab-cluster
lab-mq1..3 RabbitMQ quorum queue rack1/2, zone1 192.0.2.21..23 lab-cluster
lab-redis1..3 Redis Sentinel rack1/2, zone1 192.0.2.31..33 lab-cluster

A labtarget: labadmin sudo jogú user a PostgreSQL node-okon, postgres adatbázis-user, a lab-cluster Kubernetes context a monitoring komponensekhez, a lab-stateful namespace a Prometheus/Grafana számára. A stack Ubuntu Server 24.04 LTS, PostgreSQL 16, RabbitMQ 3.13 (a pontos verziókat és support matrixokat ellenőrizni kell a labban). A monitoring Prometheus node_exporter-t és postgres_exporter-t használ.

A game day célja a PostgreSQL single node kiesésének tesztelése. A hipotézis: „Ha a lab-pg1 node-ot leállítjuk, akkor a Patroni 10 másodpercen belül észleli a kimaradást, a lab-pg2-t primaryvá lépteti elő, az írás 30 másodpercen belül újra elérhető lesz, RPO = 0 commitált tranzakció (a sync standby miatt), és az SLO 99% felett marad az 1 perces hibablakban.” A stop condition: ha az RTO meghaladja a 60 másodpercet, vagy adatvesztést észlelünk, a tesztet leállítjuk és rollbacket hajtunk végre.

A játék lépései:

  1. Baseline rögzítése. A lab-pg1-en lefuttatjuk:

    # target: lab-pg1, user: postgres
psql -h lab-pg1 -U postgres -c "SELECT application_name, sync_state, pg_wal_lsn_diff(flush_lsn, replay_lsn) AS lag_bytes FROM pg_stat_replication;"

    Várható kimenet: lab-pg2 sync_state = sync, lag_bytes = 0; lab-pg3 = async, lag > 0. Ez bizonyítja, hogy a sync replika valós, tehát RPO írási oldalon nulla.

  2. Marker tranzakció. A játékmester beszúr egy marker sort:

    psql -h lab-pg1 -U postgres -c "CREATE TABLE IF NOT EXISTS game_day_marker(id int primary key, note text, ts timestamptz);"
psql -h lab-pg1 -U postgres -c "INSERT INTO game_day_marker VALUES (1, 'pre-failover', now());"

  3. Failure injection. A labadmin leállítja a primaryt:

    # target: lab-pg1, user: labadmin
ssh labadmin@lab-pg1 "sudo systemctl stop postgresql"

    A stopperóra elindul. A klienst szimuláló script folyamatosan írni próbál, és a hibákat naplózza.

  4. Automatikus failover. A Patroni (amely a lab-pg1-en fut, de a konfiguráció a DCS-ben van) észleli a kimaradást, és a lab-pg2-t promótálja. A játékmester ellenőrzi:

    # target: lab-pg2, user: postgres
psql -h lab-pg2 -U postgres -c "SELECT pg_is_in_recovery();"

    Várható kimenet: f (false), azaz a node már primary. A stopperóra leolvasása: ha t <= 30 s, az RTO vállalás teljesült.

  5. RPO ellenőrzés. A marker sor lekérdezése az új primaryn:

    psql -h lab-pg2 -U postgres -c "SELECT * FROM game_day_marker WHERE id = 1;"

    Ha a sor megvan, RPO = 0, azaz egyetlen commit sem veszett el.

  6. SLO mérés. A Prometheus query a hibablak alatti írási latenciára:

    histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket{service="stateful", namespace="lab-stateful"}[1m])) by (le))

    A játék során a mérést a Grafana-ban vagy a Prometheus UI-ban végezzük; a q99 latency nem haladhatja meg a 2 másodpercet, és a kéréshiba-arány nem nőhet 1% fölé az 1 perces ablakban.

  7. Rollback vagy lezárás. Ha a stop condition nem lépett életbe, a failover sikeres. Az incidenst a játékmester zárja: a lab-pg1 újraindítása esetén a Patroni visszaveszi mint standby, és a rebuild megkezdődik. A jegyzőkönyvbe bekerül a mért RTO, RPO, SLO.

Az alábbi vezérlő script a mérés automatizálására szolgál a játékmester VM-jén:

#!/usr/bin/env bash
# Target: lab-runner, user: labadmin, context: lab-cluster
set -euo pipefail
PG_PRIMARY="lab-pg1"
PG_STANDBY="lab-pg2"
PG_USER="postgres"

echo "=== Baseline replication state ==="
psql -h "$PG_PRIMARY" -U "$PG_USER" -c \
  "SELECT application_name, sync_state, pg_wal_lsn_diff(flush_lsn, replay_lsn) AS lag_bytes FROM pg_stat_replication;"

echo "=== Insert pre-failover marker ==="
psql -h "$PG_PRIMARY" -U "$PG_USER" -c \
  "CREATE TABLE IF NOT EXISTS game_day_marker(id int primary key, note text, ts timestamptz);"
psql -h "$PG_PRIMARY" -U "$PG_USER" -c \
  "INSERT INTO game_day_marker VALUES (1, 'pre-failover', now());"

echo "=== Stop primary (failure injection) ==="
ssh labadmin@"$PG_PRIMARY" "sudo systemctl stop postgresql"
START_EPOCH=$(date +%s)

echo "=== Wait for new primary ==="
RTO=0
for i in $(seq 1 100); do
    if psql -h "$PG_STANDBY" -U "$PG_USER" -c "SELECT pg_is_in_recovery();" 2>/dev/null | grep -q "f"; then
        END_EPOCH=$(date +%s)
        RTO=$((END_EPOCH - START_EPOCH))
        echo "New primary available after ${RTO}s"
        break
    fi
    sleep 1
done

if [ "$RTO" -eq 0 ] || [ "$RTO" -gt 60 ]; then
    echo "STOP CONDITION: RTO exceeded 60s or no failover. Rollback required."
    exit 1
fi

echo "=== RPO check ==="
psql -h "$PG_STANDBY" -U "$PG_USER" -c "SELECT * FROM game_day_marker WHERE id = 1;"

echo "=== SLO check: consult Prometheus for q99 latency and error rate ==="
echo "Run query in Prometheus: histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket{service='stateful', namespace='lab-stateful'}[1m])) by (le))"

Várható kimenet: a baseline sync_state = sync, a marker bekerül, a script New primary available after ~20s üzenetet ad, majd a marker sor sikeresen megjelenik. A Prometheus query várhatóan q99 ~ 0.9 s, a hibaarány 0% az ablakban. Ha a script STOP CONDITION üzenettel kilép, a játékmester azonnal végrehajtja a rollbacket: a lab-pg1 újraindítása, Patroni visszapromóció, és a cluster állapotának ellenőrzése.

54.5.3 Hibák és ellenpróbák

A leggyakoribb hiba a hipotézis nélküli játék: ilyenkor a mérés értelmezhetetlen, mert nincs referenciaérték. Mindig rögzíteni kell a baseline-t, például a replikációs laget és a tranzakciós rátát a failure előtt. A második tipikus hiba a stop condition hiánya: ha a teszt túl sokáig tart, a lab környezet elnyújtott kiesésbe kerül. A stop condition legyen konkrét szám, például RTO > 60 s. Harmadik hiba: a régi primary visszatérése után split-brain alakul ki, mert a fencing (előzetes node-izolálás) elmarad. Ilyenkor a Patroni nem tudja eldönteni, melyik node a valódi primary; a diagnózis a patronictl list parancs kimenetéből indul, a megoldás a régi node hálózati elszigetelése, majd a clusterhez való csatlakoztatás mint standby. Negyedik csapda a restore és a failover összekeverése: ha a failover adatvesztéssel járna (async replika, lag nagy), a restore a helyes választás, de ez hosszabb RTO-val jár. A game daynek mindkét útvonalat mérnie kell, hogy a döntés adatalapú legyen. Végül a retry budget figyelmen kívül hagyása téves SLO-értékeléshez vezet: ha a kliens oldali újrapróbálkozások miatt a felhasználó nem érzékeli a kiesést, a szerveroldali metrika túl szigorú lehet.

54.5.4 Feladatok

  1. Magyarázó feladat (failure domain és mérési terv). Tervezz meg egy game day forgatókönyvet a lab-mq1 RabbitMQ node hálózati linkjének megszakítására. Fogalmazd meg a hipotézist, a stop conditiont, és sorold fel, milyen metrikákat figyelnél a quorum, a lag és a rebuild kapcsán. Melyik restore/failover stratégia a várhatóan optimális, és miért?

  2. Adminisztrációs feladat (PostgreSQL failover game day). Hajtsd végre a kidolgozott példa lépéseit a lab stackeden. Rögzítsd a mért RTO, RPO és SLO értékeket a jegyzőkönyvbe. Ha a stop condition életbe lép, hajtsd végre a rollbacket, és dokumentáld az eltérést a hipotézistől. Ellenőrizd, hogy a lab-pg1 visszakerült-e standby szerepbe, és a sync_state ismét sync.

  3. Diagnosztikai feladat (split-brain és postmortem). A játék során a lab-pg1 véletlenül újraindul, és mind a lab-pg1, mind a lab-pg2 primarynak gondolja magát. Azonosítsd a hibát a patronictl list és a pg_stat_replication segítségével. Oldd fel a split-brain állapotot a régi node hálózati elszigetelésével, majd csatlakoztasd a clusterhez standbyként. Írd meg a rövid postmortemet: kiváltó ok, hatás, megoldás, és a jövőbeni fencing policy.

54.5.5 Megoldások

  1. A hipotézis: „Ha a lab-mq1 linkjét megszakítjuk, a quorum queue vezetője 5 másodpercen belül átkerül a másik két node-ra, az üzenetek nem vesznek el, és a queue elérhetősége nem esik 99% alá 1 perces ablakban.” Stop condition: ha a queue több mint 20 másodpercig elérhetetlen, leállunk. Mérendő: rabbitmq-diagnostics cluster_status, queue lag, rabbitmq_queue_consumer_count, rebuild idő a link helyreállása után. A failover (quorum queue leader election) részesítendő előnyben, mert nincs adatvesztés, és az RTO kicsi. Postcondition: a queue újra elérhető, minden üzenet megvan, a cluster quorum helyreállt.

  2. A fenti script futtatása után a jegyzőkönyvben szerepelnie kell: RTO = 22 s, RPO = 0 commitált tranzakció, SLO q99 latency = 1.1 s, error rate = 0%. Ha a stop condition aktiválódik, a rollback: ssh labadmin@lab-pg1 "sudo systemctl start postgresql", majd patronictl switchover lab-cluster (ha szükséges). Postcondition: a lab-pg2 primary, a lab-pg1 sync standby, a sync_state = sync.

  3. A patronictl list két primaryt mutat; a megoldás a lab-pg1-en sudo iptables -A INPUT -p tcp --dport 5432 -j DROP (vagy sudo systemctl stop patroni), majd a lab-pg2-n patronictl restart lab-cluster a kóbor primary visszaminősítésére. Ezután a hálózati izoláció feloldása, a lab-pg1 újraindítása, és a Patroni automatikusan standbyba állítja. A postmortem: kiváltó ok a leállított node nem tervezett visszatérése volt; a hatás 45 másodperc read/write blokk; a megoldás a fencing hiányosság pótlása; az acceptance evidence a sikeres split-brain feloldás utáni data integrity check.

54.5.6 Rövid összefoglaló

A failure game day a hibatűrési vállalások aktív, hipotézisvezérelt tesztje, amely a kiválasztott failure domain kiesését szimulálja izolált labban. A játék során a quorum, a lag, a rebuild és a capacity state megfigyelésével mérjük az RTO-t, RPO-t és SLO-t. A restore és a failover/failback közötti döntést mindig mért adatokra alapozzuk: a failover rövid RTO-t ad, de esetleg adatvesztéssel; a restore pontos RPO-t, de hosszú RTO-val. A stop condition és a rollback előre meghatározott, a postmortem pedig a jegyzőkönyv alapján ad elfogadási bizonyítékot. A játék nem helyettesíti a monitoringot, de teszteli annak riasztási láncát is.

Továbbhasznált definíciók:
- Failure domain: olyan fizikai vagy logikai komponens, amelynek kiesése közös upstream hibát okoz (node, link, zone, credential).
- Stop condition: a game day során mért küszöb, amelynek elérésekor a tesztet azonnal leállítjuk és rollbacket hajtunk végre.
- Quorum: a cluster többségi konszenzusa, amely nélkül a leadership és az írási elérhetőség elveszik.
