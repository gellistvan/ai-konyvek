17.3 Audit, eseménykorreláció és operatív nyom

17.3.1 Motiváció

Amikor egy Linux szolgáltatás viselkedése megváltozik, a sysadmin első kérdése általában nem az, hogy mi hibás, hanem hogy mi változott. A service log megmutatja a hibát vagy az üzleti eseményt, de gyakran nem mutatja meg, hogy ki és milyen jogosultsággal nyúlt a konfigurációhoz, ki futtatott sudo parancsot, vagy éppen melyik deploy hozta be az új binárist. Az audit ezt a hiányzó operatív nyomot (audit trail) adja hozzá: kernel szinten rögzíti a fájlhozzáférést, a privilege eseményeket és a rendszerhívásokat, még akkor is, ha az alkalmazás nem naplóz, vagy ha a naplóját eltávolították.

17.3.2 Definíció és működés

17.3.2.1 Audit és application log elhatárolása

Az audit log célja a biztonsági és üzemeltetési szempontból releváns, ki–mit–mikor–honnan jellegű események megbízható rögzítése. Ez kernel támogatással készül, ezért akkor is működik, ha az alkalmazás hibás, vagy ha egy támadó megpróbálja törölni az alkalmazásnaplót. Az application log ezzel szemben az alkalmazás belső állapotát és üzleti eseményeit írja le: request ID, hibaüzenet, cache találat, processing time. A kettő komplementer: az audit log a változást, az application log a hatást mutatja.

17.3.2.2 auditd szabályok és eseménymezők

A Linux Audit rendszerben a kernel audit alrendszere gyűjti az eseményeket, az auditd daemon pedig a /var/log/audit/audit.log fájlba írja őket. A leggyakrabban használt szabályforma a fájl watch:

-w /etc/lab-app/config.json -p wa -k lab_app_config

A -p wa azt jelenti, hogy write és attribute változás eseményeket rögzítünk; a -k lab_app_config pedig egy kereshető címkét (key) rendel az eseményhez. A syscall szabály ezzel szemben adott rendszerhívás-családokat figyel, például minden openat hívást egy directoryra. A syscall szabály erősebb, de nagyságrendekkel nagyobb tárhely- és CPU-igényű, ezért csak indokolt esetben használjuk.

Egy tipikus audit bejegyzés mezői:

  • type: az esemény típusa, például SYSCALL, PATH, PROCTITLE.
  • msg=audit(epoch:serial): időbélyeg és sorszám.
  • auid: audit user ID, az eredeti bejelentkezett felhasználó; sudo után is az eredeti user marad.
  • uid, euid, suid, fsuid: a folyamat valós, effektív, saved és filesystem UID-je.
  • pid, ppid, ses, comm, exe: folyamatazonosítók és a végrehajtott program.
  • key: a szabályhoz rendelt címke, ami a keresést és a korrelációt egyszerűsíti.

A uid=root auid=labop kombináció tipikus sudo-s eset: a folyamat ténylegesen rootként fut, de az eredeti felhasználó labop. Ezért az auid az auditban az elsődleges felelősségi azonosító.

17.3.2.3 Auth, sudo, service és kernel log forrásai

Az operatív timeline több forrásból áll össze:

  • Auth log: a PAM, SSH, login és sudo események a systemd-journald-ben _SYSTEMD_UNIT vagy a klasszikus /var/log/auth.log alatt jelennek meg. A sudo bejegyzés megmutatja a hívó usert, a TTY-t, a munkakönyvtárat és a parancsot.
  • Service log: a systemd unitok standard output/error csatornája a journald-be kerül. Egy lab-app.service esetén journalctl -u lab-app.service a service saját application logját adja.
  • Kernel log: a kernel saját üzenetei (dmesg, journalctl -k) a hardver, OOM-killer, seccomp és hálózati hibákról adnak nyomot.

17.3.2.4 Óraszinkron és correlation ID

A több forrásból származó timeline akkor megbízható, ha a hostok órája szinkronban van. A timedatectl show -p NTPSynchronized és a chronyc tracking segítségével ellenőrizhető, hogy a wall clock NTP-szinkronban van. A correlation ID ezen túl egy konkrét művelet végigkövetésére használt egyedi azonosító, amelyet a deploy pipeline generál, a configba tesz, és a service logjába is beír. Így az audit file-változás és az application log közötti kapcsolat nem csak időablakon, hanem logikai azonosítón is alapul.

17.3.2.5 Configuration, version és deploy marker

A deploy során fontos, hogy a változás ne legyen névtelen. A deploy marker egy olyan struktúrált üzenet, amely tartalmazza a deploy ID-t, a version-t, a commit hash-t és az artifact digestet. Ezt a deploy script a journald-be írja, például:

printf 'deploy_id=%s commit=%s version=%s\n' \
  "$deploy_id" "$commit_id" "$version" \
  | sudo systemd-cat -t lab-deploy -p notice

A konfigurációs fájl verzióját, hashét és a deploy ID-t külön is rögzíthetjük. Ettől az auditesemény, a deploy marker és a service indítás egyetlen változási láncot alkot.

17.3.2.6 Sensitive data és hozzáférési policy

Az audit log érzékeny adatot tartalmazhat: parancssori argumentumokat, fájlneveket, környezeti változókat, felhasználóneveket. Ezért a hozzáférési policy alapja, hogy az audit log csak root és a dedikált audit csoport tagjai számára olvasható. A /var/log/audit/audit.log alapból 0600 jogosultságú. Kerülni kell a titkok parancssori argumentumban való átadását, mert a sudo és az audit PROCTITLE mező pontosan ezt rögzíti. Jelszót, tokent és API kulcsot környezeti változóban, file descriptorban vagy dedicated secret mountban kell átadni, ahogyan a d073 is tanította.

17.3.2.7 Audit backlog és teljesítményfeltétel

Az audit alrendszer nem korlátlan puffer: a kernelnek van backlog_limit értéke, amely a feldolgozásra váró események maximális számát adja. Ha a backlog eléri a limitet, a kernel a failure policy szerint jár el: csendben eldob, printk üzenetet ír, vagy akár panicol. A backlog_wait_time beállítás esetén a generáló folyamatok várnak, ami latency-növekedést okoz. A túl széles audit szabály, például -a always,exit -S all, gyorsan telíti a buffert és mérhető CPU-overheadet ad. A teljesítményfeltétel tehát: annyi és csak annyi audit szabály legyen, amennyi a operatív nyomhoz ténylegesen szükséges. A file watch olcsóbb, mint a minden syscall figyelése.

17.3.3 Kidolgozott példa

A példa célja a lab-audit01 VM-en (labop user, sudo jog) egy konfigurációcsere rögzítése, deploy markerrel és utólagos timeline-nal.

Előfeltétel: az auditd telepítve és fut, a lab service lab-app.service már journald-be naplóz.

# lab-audit01, user: labop, UID: 1000, root műveletek sudo-val
id
sudo systemctl is-active auditd
sudo mkdir -p /etc/lab-app
echo '{"version":"1.0.0","listen":"127.0.0.1:8080"}' \
  | sudo tee /etc/lab-app/config.json >/dev/null

Persistens audit szabály létrehozása:

sudo sh -c 'echo "-w /etc/lab-app/config.json -p wa -k lab_app_config" \
  > /etc/audit/rules.d/lab-app.rules'
sudo systemctl restart auditd
sudo auditctl -l

Várható ellenőrző kimenet:

-w /etc/lab-app/config.json -p wa -k lab_app_config

Most a deploy markerrel ellátott változtatás:

deploy_id=lab-deploy-2025-01-15T14-03-00Z
commit_id=abc123def
version=1.1.0

printf '{"version":"%s","listen":"127.0.0.1:8080","deploy_id":"%s"}\n' \
  "$version" "$deploy_id" > /tmp/lab-app-config.json

sudo install -m 0644 /tmp/lab-app-config.json /etc/lab-app/config.json

printf 'deploy_id=%s commit=%s version=%s\n' \
  "$deploy_id" "$commit_id" "$version" \
  | sudo systemd-cat -t lab-deploy -p notice

A C++ service a lab-app.service indulásakor a deploy markerrel és correlation ID-vel ír logot:

// lab-app: egyszerűsített config reload log a std::cerr-en
std::cerr << "{\"event\":\"config_reload\",\"version\":\""
          << version << "\",\"deploy_id\":\"" << deploy_id
          << "\",\"correlation_id\":\"" << correlation_id << "\"}\n";

Az audit esemény kinyerése:

sudo ausearch -k lab_app_config -i

Illusztratív várható kimenet:

type=PROCTITLE msg=audit(2025.01.15 14:03:01.234:10) :
  proctitle=install -m 0644 /tmp/lab-app-config.json /etc/lab-app/config.json
type=PATH msg=audit(2025.01.15 14:03:01.234:10) :
  item=0 name=/etc/lab-app/config.json inode=123456
type=SYSCALL msg=audit(2025.01.15 14:03:01.234:10) :
  arch=x86_64 syscall=openat success=yes exit=3
  auid=labop uid=root gid=root euid=root suid=root fsuid=root
  pid=1234 comm=install exe=/usr/bin/install key=lab_app_config

A auid=labop uid=root mezőpár mutatja, hogy labop sudo-val rootként futtatta a cserét.

A timeline összeállítása egy ablakban:

Idő (wall clock) Forrás Esemény Actor / korreláció
14:03:00 journald lab-deploy deploy_id=... version=1.1.0 commit=abc123def deploy pipeline
14:03:01 audit lab_app_config install file write auid=labop, uid=root
14:03:01 sudo log COMMAND=/usr/bin/install ... labop TTY=pts/0
14:03:01 journald lab-app config_reload correlation_id=9f8e… 
journalctl -t lab-deploy --since "2025-01-15 14:02:50" --until "2025-01-15 14:04:00"
sudo journalctl -b -u sudo --since "2025-01-15 14:02:50" --until "2025-01-15 14:04:00"
journalctl -u lab-app.service --since "2025-01-15 14:02:50" --until "2025-01-15 14:04:00"

A posztfeltétel ellenőrzése: a szabály aktív, az ausearch tartalmazza a key=lab_app_config bejegyzést, a lab-deploy marker a journald-ben látható, és a lab-app logban szerepel ugyanaz a deploy_id.

17.3.4 Hibák és ellenpróbák

A szabály eltűnik reboot után. Tünet: a változtatás után rögtön működik, de később nincs audit bejegyzés. Hipotézis: a szabály csak auditctl -w-vel lett beállítva, nem került a rules.d fájlba. Adatgyűjtés: sudo auditctl -l a reboot után üres. Javítás: a szabály beírása /etc/audit/rules.d/lab-app.rules fájlba, majd sudo systemctl restart auditd és ismételt auditctl -l. Verifikáció: a szabály reboot után is aktív.

A file watch nem látja a rename-et. Ha a deploy atomi csereként rename()-eli a config fájlt, a fájl inode-ja helyett a szülő directory bejegyzése változik. Ilyenkor a file watch nem feltétlenül rögzíti az eseményt. Megoldás: a szülő directoryt is figyelni kell, például -w /etc/lab-app -p wa -k lab_app_config_dir. Ellenőrzés: a rename deploy után ausearch -k lab_app_config_dir tartalmazza az eseményt.

A timeline órahibás. Ha a hostok NTP-szinkronja nem működik, a korreláció hamis átrendeződést mutat. timedatectl show -p NTPSynchronized értéke no. Javítás: a chrony/NTP beállítása, újramérés, majd a timeline újraépítése.

A túl széles syscall szabály megtelíti a backlogot. Tünet: latency-növekedés a service-ben és lost növekedés az auditctl -s kimenetében. A széles -S all szabályt eltávolítjuk, és csak a tényleges file watchot tartjuk meg. Mérés: sudo auditctl -s értékei a javítás előtt és után; a lost érték ne növekedjen.

A correlation ID hiányzik. Ha a deploy marker és a service log nem használ közös azonosítót, csak időablakra hagyatkozhatunk. Javítás: a deploy ID a configba kerül, a service pedig a logba írja. A journalctl -t lab-app | grep deploy_id lesz a verifikáció.

17.3.5 Feladatok

  1. Magyarázó feladat. Hasonlítsa össze az audit log és az application log célját egy lab-app szolgáltatás esetében. Milyen mezőket használna a két forrás összekapcsolására, és miért fontos az auid a uid mellett?

  2. Adminisztrációs feladat. Hozzon létre persistens audit watch-ot /etc/lab-app/config.json fájlra lab_app_config key-jel. Telepítse a deploy markert lab-deploy-2025-01-15T15-00-00Z ID-vel, 1.2.0 verzióval és def456abc commit hash-sel. Módosítsa a configot az új verzióra, majd ellenőrizze, hogy az audit bejegyzés, a deploy marker és a service log azonos deploy ID-t tartalmaz-e.

  3. Diagnosztikai feladat. A laborban a lab-app config fájlja reggel 03:00-kor megváltozott, de a deploy pipeline nem futott. Az előző jó config a /opt/lab-app/backup/config.json.1.1.0 fájlban van. Állapítsa meg, ki és milyen paranccsal változtatott, milyen verzió lett aktív, és állítsa vissza az 1.1.0-s verziót úgy, hogy a visszaállítás is auditált legyen. Végül ellenőrizze a backlog státuszt, és magyarázza el, miért elegendő a file watch, miért nem kell teljes syscall audit.

17.3.6 Megoldások

  1. Az audit log a privilegizált műveleteket és fájlhozzáféréseket rögzíti, az application log a service állapotát és üzleti eseményeit. A korrelációhoz az auid (eredeti user), a ses (session ID), a key (audit címke), a deploy_id és a correlation ID használható. Az auid azért fontos, mert sudo után is az eredeti felhasználót mutatja, szemben a root-ra változó uid-dal.

  2. A várható parancsok:

sudo sh -c 'echo "-w /etc/lab-app/config.json -p wa -k lab_app_config" \
  > /etc/audit/rules.d/lab-app.rules'
sudo systemctl restart auditd
sudo auditctl -l

deploy_id=lab-deploy-2025-01-15T15-00-00Z
commit_id=def456abc
version=1.2.0
printf '{"version":"%s","listen":"127.0.0.1:8080","deploy_id":"%s"}\n' \
  "$version" "$deploy_id" > /tmp/lab-app-config.json
sudo install -m 0644 /tmp/lab-app-config.json /etc/lab-app/config.json
printf 'deploy_id=%s commit=%s version=%s\n' \
  "$deploy_id" "$commit_id" "$version" \
  | sudo systemd-cat -t lab-deploy -p notice

Ellenőrzés:

sudo ausearch -k lab_app_config -i | grep -q 'key=lab_app_config'
journalctl -t lab-deploy --since "2025-01-15 15:00:00" --until "2025-01-15 15:02:00" \
  | grep -q 'deploy_id=lab-deploy-2025-01-15T15-00-00Z'
journalctl -u lab-app.service --since "2025-01-15 15:00:00" --until "2025-01-15 15:02:00" \
  | grep -q 'lab-deploy-2025-01-15T15-00-00Z'

Posztfeltétel: a config verziója 1.2.0, az audit bejegyzés key=lab_app_config címkével létezik, a deploy marker és a service log ugyanazt a deploy ID-t tartalmazza.

  1. A diagnosztika lépései:
sudo ausearch -k lab_app_config -ts today 03:00 -i
sudo ausearch -ui labop -ts today 02:50 -te today 03:10 -i
sudo journalctl -b -u ssh --since "2025-01-15 02:50:00" --until "2025-01-15 03:10:00"
sudo last -F labop | head

A várható bizonyíték: az audit esemény auid=labop uid=root comm=install vagy comm=nano, a sudo logban a COMMAND=/usr/bin/install ... bejegyzés, a last outputban a bejelentkezés. A visszaállítás:

sudo install -m 0644 /opt/lab-app/backup/config.json.1.1.0 /etc/lab-app/config.json
printf 'deploy_id=lab-restore-2025-01-15T10-00-00Z commit=abc123def version=1.1.0\n' \
  | sudo systemd-cat -t lab-restore -p notice
sudo ausearch -k lab_app_config -i | tail -n 20
sudo auditctl -s

Posztfeltétel: a config újra 1.1.0, a visszaállítás auditálva van, a backlog lost értéke nem növekedett, és a file watch szabály elegendő a config változás rögzítéséhez teljes syscall audit nélkül.

17.3.7 Rövid összefoglaló

Az audit trail a rendszer biztonsági és változási eseményeinek kernel szinten előállított, jogosultságtól független nyoma; a Linux auditd a fájl-watch és syscall szabályok alapján gyűjti, az auid mező pedig megőrzi az eredeti felhasználó azonosságát. A correlation ID egy deploy vagy request szintű egyedi azonosító, amely az audit, a sudo, a service és a deploy marker eseményeit közös logikai láncba fűzi. Az audit backlog a kernel pufferének kihasználtsága, amelynek telítődése latency-növekedést vagy elveszett eseményeket okoz, ezért a szabályokat szűken kell tartani. Az audit és az application log célja különbözik: az audit a változást, az application log a hatást mutatja.

17.3.8 Források és ellenőrzési hiányok

A jelen kérésben nem áll rendelkezésre webes keresőeszköz, ezért a technológiai állítások nem tekinthetők aktuálisan ellenőrzött bizonyítéknak. Az alábbi források kiindulópontként szolgálnak, de az auditctl, auditd, ausearch és a systemd-journald mezők pontos szintaxisa az Ubuntu Server 24.04 labkörnyezetben ellenőrizendő:

  • Linux man-pages — man 5 audit.rules, man 8 auditctl, man 8 ausearch, man 8 auditd.
  • Ubuntu Server documentation — auditd és journald üzemeltetési dokumentáció.
  • systemd.io — journald mezők és systemd-cat viselkedése.

Ellenőrzési hiány: a jelen példa az auditd alapvető szabályaira épül, de a kernel audit backlog pontos viselkedése és a systemd journald mezők illeszkedése a labban futtatandó.
