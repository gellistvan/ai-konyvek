48.1 Git workflow, trigger és quality gate

48.1.1 Motiváció és definíció

A szenior C++ fejlesztő a Git commit, branch és pull request (PR) fogalmát ismeri; a delivery törésvonala azonban nem a git merge pillanatában, hanem a tesztelt commit és a deployolt artifact közötti bizonyítékláncon jelenik meg. Ha a CI pipeline a rossz commitot teszteli, vagy a branch policy nem kényszeríti ki a merge előtti ellenőrzést, a main branch-en megjelenő hibát a fejlesztői build nem fogta el. A fejezet fókusza ezért a delivery trigger, a változatazonosítás és a quality gate kapcsolata.

A következő definíciók a d236 további szakaszaiban használt fogalmak:

  • CI trigger: olyan version control esemény vagy szolgáltatói feltétel, amely meghatározza, hogy egy adott commitra, tagre vagy merge-kísérletre melyik pipeline indul. A trigger nem maga a teszt; a trigger és a tesztelt változat összekötése a pipeline bemenete.
  • Tested revision: a forrásfában pontosan azonosított commit (például git rev-parse HEAD), amelyre a tesztek lefutottak. A PR trigger esetén ez általában a PR head SHA, merge queue esetén pedig a szimulált merge commit SHA.
  • Deployed artifact: a forrásból épített, verzióval és content hash-sel azonosítható futtatható csomag, például image digest vagy natív binary build-id. A deployment csak akkor hibátlanul visszakövethető, ha a tested revisionből származó artifactot futtatja.
  • Quality gate: a pipeline azon policyhalmaza, amely megmondja, hogy egy változtatás beléphet-e a következő fázisba, például merge vagy deploy. A gate a required checks, protected refs és egyéb repository szabályok kombinációja.
  • Protected ref: olyan branch vagy tag, amelyre közvetlen push nem engedélyezett; a módosítás csak PR-en, meghatározott ellenőrzéseken keresztül kerülhet be.
  • Merge queue: a PR merge előtti automatizált sor, amely a PR-t a cél branch friss állapotára illesztve újrateszteli; a tesztek a merge-kísérlet commitján futnak, nem csupán a PR head commitján.

48.1.2 Trigger és tested revision

A trigger típusa meghatározza, hogy a pipeline melyik commitot látja. A leggyakoribb triggerek:

  • Push: a pipeline a pusholt commiton fut, például a main branch headjén. Ez alkalmas gyors visszajelzésre, de nem jelenti automatikusan a merge utáni integrációs állapot tesztelését, ha a push egy feature branchre érkezik.
  • Pull request: a pipeline a PR head commitján fut. A cél branch aktuális állapotával való kombinációt nem feltétlenül teszteli, mert a PR head commit nem tartalmazza a cél branch azon változásait, amelyeket a merge hozzáadna.
  • Tag: a pipeline a tagre mutató commiton fut; ez release artifact jelölésre alkalmas, de önmagában nem bizonyítja, hogy a commitból előállt artifact a tagre mutatott.
  • Merge queue: a pipeline a PR cél branchre illesztett, ideiglenes merge commiton fut. Ez a trigger közelíti meg legjobban a tényleges merge utáni állapot tesztelését, mert a konfliktusfeloldás és a kombinált fa együtt vizsgálható.

A tested revisiont a trigger határozza meg; a pipeline logban expliciten rögzíteni kell, hogy melyik SHA-ról van szó. A git commit SHA önmagában nem garantálja, hogy a teszt eredménye a deployolt artifacthoz tartozik; a build lépésnek ugyanabból a revisionből kell kiindulnia.

48.1.3 Trunk-based és release branch tradeoff

A branch policy a trigger és a quality gate mellett határozza meg, milyen gyorsan és milyen biztonsággal integrálódnak a változtatások.

  • Trunk-based: a fejlesztők rövid életű feature branchről nyitnak PR-t a main branchre. A main mindig releasable; a merge queue és a required checks akadályozzák meg a törött main-t. Előnye a gyors integráció, kevés merge konfliktus és a deployment frequency növelése. Hátránya, hogy erős tesztlefedettséget és szigorú quality gate-et igényel, mert a main minden commitja potenciálisan deployolható.
  • Release branch: a stabil release ágat külön karbantartják, a hotfix külön ágon készül, majd cherry-pickkel kerül be. Előnye az izolált stabil állapot és a lassú változás. Hátránya a párhuzamos ágak közötti drift, a késői integráció és a többlet tesztelési pont, mert a release branch és a main külön-külön is validálandó.

A d236 fókuszában a trunk-based a merge queue-val kombinálva csökkenti a “PR zöld, merge után piros” hibaosztályt, mert a teszt a merge-kísérlet commiton fut. A release branch ezt a hibát a stabil ágon előrehozott staging teszttel tudja ellensúlyozni, de a cherry-pick miatt a tested revision és a deployed artifact közötti nyomvonal bonyolultabb.

48.1.4 Quality gate, protected refs és required checks

A quality gate a pipeline kimenete és a repository policy találkozása. A protected ref megakadályozza a közvetlen push-t, például a main branchre. A required checks olyan pipeline jobok, amelyeknek zöldnek kell lenniük a merge előtt. A merge queue ezt kiegészíti azzal, hogy a required checks a merge queue ideiglenes commitján futnak, nem a PR headen.

A protected branch beállításában meg kell adni:

  • a védett ref neve, például main;
  • a required status check kontextusok, például build-test;
  • a szigorú mód, amely megköveteli a branch friss állapotát a merge előtt;
  • opcionálisan a merge queue aktiválása.

A GitHub Actions és a GitLab CI szintaxisa eltér; a példa a GitHub Actions fogalmi modelljét használja. A pontos triggerfeltételek és a merge queue bekapcsolásának API-paraméterei az aktuális szolgáltatói dokumentációban ellenőrizendők.

48.1.5 Tested commit versus deployed artifact

A tesztelt commit és a deployolt artifact nem szinonima. A tested commit a forrásfa egy állapota, míg a deployed artifact a build eredménye: natív bináris, image digest vagy csomag. A kettő közötti kapcsolatot a pipeline artifact manifestben rögzíti, például:

  • source_revision: a checked out commit SHA;
  • build_id: a natív binary build-id vagy image digest;
  • config_schema_version: a deployhoz tartozó konfiguráció verziója.

Ha a deployment egy olyan artifactot futtat, amely nem a tested commitból készült, a quality gate eredménye irreleváns. A d236 utáni fejezetekben az artifact promotion és az SLSA provenance ezt a bizonyítékláncot bővíti; itt az a lényeg, hogy a pipeline trigger és a tested revision kötelezően megadja a kiindulópontot.

48.1.6 Flaky test és pipeline feedback

A flaky test olyan teszt, amely ugyanazon code revision esetén időnként zöld, időnként piros. A natív C++ tesztekben gyakori ok a nem determinisztikus sorrend, a globális tesztállapot, a timing függés vagy a megosztott erőforrás. A pipeline feedback megbízhatóságát a flaky test aláássa, mert a required check időnként hamis negatív eredményt ad: a fejlesztő újra futtat, és a merge queue továbbhalad, de a valódi hibát elfedheti a zaj.

A quality gate-ben a flaky testet két szinten kell kezelni:

  1. Rövid távon: a nem determinisztikus teszteket quarantinába helyezzük, és csak a reprodukálható, determinisztikus tesztek maradnak a required checksben. A quarantinában a teszt továbbra is futhat, de az eredmény nem blokkolja a merge-t; a hibajegy fixet kap.
  2. Hosszú távon: a flaky testet determinisztikussá kell tenni, például a tesztadatok izolálásával, a sorrendi függés megszüntetésével vagy a timing helyett explicit synchronization használatával.

A pipeline feedback ideje nem csak a futási idő; a flaky test miatti újra futtatás és a hibás gate a lead time for changes mutatót rontja.

48.1.7 DORA measurement definíciók kontextusban

A DORA-mutatók a delivery teljesítményét mérik; a d236-ban a trigger és a quality gate ezek bemenetét adja. A négy alapmutató:

  • Deployment frequency: a productionba kerülő deploymentek gyakorisága. A trunk-based development és a gyors merge queue növelheti, mert a main minden merge-e releasable.
  • Lead time for changes: a commit-tól a productionba kerülésig tartó idő. A pipeline trigger késése, a required checkek futási ideje és a merge queue várakozása mind hozzájárul.
  • Change failure rate: a productionba került változtatások azon hányada, amely hibát okoz. A tested revision és a merge queue csökkenti a merge utáni hibák egy részét, mert a kombinált állapot már a merge előtt tesztelve van.
  • Failed deployment recovery time: a hibás deployment visszaállításának ideje. A tested commit és a deployed artifact közötti azonosítás gyors rollbacket tesz lehetővé, mert ismert, melyik artifactot kell visszavonni.

Ezek a mutatók itt kontextuális definíciók; a d251 foglalkozik majd az SLI/SLO és error budget mérési módszertanával. A d236 tanulsága, hogy a trigger és a quality gate nem önmagáért való adminisztráció, hanem a DORA-mutatók javításának eszköze.

48.1.8 Kidolgozott példa

A gyakorlópélda laborrepository-ja github.com/lab-org/lab-cpp-svc. A cél a main branch védelme, merge queue aktiválása és a CI pipeline hozzáigazítása. A módosító parancsok targetje a repository és a .github/workflows/ci.yml fájl. A GitHub Actions workflow a push, pull_request és merge_group triggerekre épül.

Előfeltétel: a repository létezik, a main branch a kezdeti commitot tartalmazza, és a fejlesztő rendelkezik write joggal a repositoryra. A branch protection beállításához admin jog szükséges.

A workflow fájl tartalma:

# .github/workflows/ci.yml
name: lab-cpp-svc-ci
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  merge_group:
    types: [checks_requested]

jobs:
  build-test:
    runs-on: ubuntu-24.04
    steps:
      - name: Checkout tested revision
        uses: actions/checkout@v4
        with:
          ref: ${{ github.event.pull_request.head.sha || github.sha }}
      - name: Configure
        run: cmake -S . -B build -DCMAKE_BUILD_TYPE=RelWithDebInfo
      - name: Build
        run: cmake --build build -j2
      - name: Run unit tests
        run: ./build/lab-cpp-svc --self-test
      - name: Run sanitizer smoke
        run: ./build/lab-cpp-svc --self-test --sanitizer-leak

A runs-on: ubuntu-24.04 a labor Ubuntu 24.04 LTS baseline-jára utal; a GitHub-hosted runner pontos címkéje az aktuális dokumentációban ellenőrizendő. A ref kifejezés a pull request eseménynél a PR head SHA-t, egyéb eseménynél a github.sha értéket adja; merge queue esetén a github.sha a merge queue ideiglenes commitjára mutat.

A branch protection beállítása a repository admin számára, például gh CLI-vel:

gh api -X PUT "repos/lab-org/lab-cpp-svc/branches/main/protection" \
  -f required_status_checks.strict=true \
  -f required_status_checks.contexts[]=build-test \
  -f enforce_admins=false

Ez a parancs a main branchre kötelezővé teszi a build-test checket. A strict=true megköveteli, hogy a branch friss állapotú legyen a merge előtt. A merge queue aktiválása külön API hívást igényel; a pontos paraméterek a szolgáltató dokumentációjában ellenőrizendők.

Várható kimenet: egy PR nyitásakor a pull_request trigger lefuttatja a build-test jobot a PR head commitján. A merge queue bekapcsolása után a merge_group trigger a szimulált merge commiton is lefuttatja ugyanazt a jobot. Ha mindkettő zöld, a PR merge-elhető. A main branchre közvetlen push a védett ref miatt sikertelen.

Ellenőrzési feltétel: a Checks tab zöld, a git log --oneline --decorate --all --graph megmutatja a merge queue commitot, és a gh pr checks <pr> kimenetben a build-test a merge queue kontextusban is sikeres.

Rollback: ha a pipeline konfiguráció hibás, a workflow fájlt visszaállítjuk az előző revízióra; a branch protectiont a gh api -X DELETE "repos/lab-org/lab-cpp-svc/branches/main/protection" paranccsal kapcsoljuk ki. A laborban csak a saját lab-org/lab-cpp-svc repository módosul, más repositoryra nem terjed ki.

48.1.9 Hibák és ellenpróbák

Az alábbi gyakori hibák a trigger és a quality gate félreértéséből származnak.

Tünet: a PR zöld, de a merge után a main build eltörik.
Hipotézis: a pull_request trigger csak a PR head commiton futott; a cél branch azon változásai, amelyek a merge után együttesen fordítási vagy tesztelési hibát okoznak, nem voltak tesztelve.
Adatgyűjtés: a git log --oneline --decorate --all --graph megmutatja, hogy a PR head commit és a main head commit különbözött-e; a workflow logban a checkout SHA és a job indító eseménye szerepel.
Egy változtatás: aktiváljuk a merge queue-t, és adjuk hozzá a merge_group triggert a workflowhoz.
Verification: új PR esetén a merge_group trigger lefut a kombinált commiton; ha a build továbbra is zöld, a merge biztonságos.

Tünet: a merge queue beragadt, a PR nem merge-elhető, de a checkek zöldek.
Hipotézis: a merge_group trigger nem fut, mert a required check kontextusa nem egyezik meg a workflow job nevével, vagy a workflow triggeréből hiányzik a merge_group.
Adatgyűjtés: gh pr checks <pr> és a gh api repos/{owner}/{repo}/branches/main/protection kimenete megmutatja, hogy a branch protection milyen contextet vár, és a workflow milyen nevet ad a jobnak.
Egy változtatás: a build-test job nevet és a required check kontextust egymáshoz igazítjuk, vagy a workflow triggerét kiegészítjük a merge_group eseménnyel.
Verification: a merge queue újra feldolgozza a PR-t; a gh pr checks kimenetben a merge queue kontextus is zöld lesz.

Tünet: a build-test check hol zöld, hol piros ugyanarra a commitra.
Hipotézis: flaky teszt van a lab-cpp-svc --self-test futtatásban, például egy unit teszt a sorrendtől függ.
Adatgyűjtés: a workflow logban szereplő tesztnév és a lokális ctest --repeat until-pass:5 -R <test> futtatás megmutatja a nem determinisztikus esetet.
Egy változtatás: a flaky tesztet quarantinba helyezzük a required checkből, és a determinisztikus teszteket megtartjuk a gateben. A quarantinált teszt külön non-blocking jobban fut.
Verification: a required check determinisztikusan zöld; a flaky teszt hibajegye megnyitva, a javítás a d240 szerinti artifact review része lesz.

48.1.10 Feladatok

48.1.10.1 1. Magyarázó feladat: trigger és tested revision

Adott a lab-org/lab-cpp-svc repository és a következő Git history:

  • main head: a1b2c3
  • feature/gate branch head: d4e5f6
  • A PR a feature/gate-ből a main-be nyílik.
  • A workflow on szakasza a példa szerinti push, pull_request és merge_group triggereket tartalmazza.

Határozd meg, melyik commit SHA szerepel a workflow logban a pull_request trigger és a merge_group trigger esetén. Magyarázd meg, miért nem elegendő a pull request trigger eredménye a merge biztonságának igazolásához.

48.1.10.2 2. Adminisztrációs feladat: workflow és branch protection

A labor repositoryban a .github/workflows/ci.yml jelenleg csak a push eseményre tartalmaz triggert. Egészítsd ki a workflowt pull_request és merge_group triggerekkel. Állítsd be a main branchre a required checket a build-test jobra, és aktiváld a strict módot. A módosító parancsok targetje, előfeltétele és rollbackje legyen egyértelmű. Postcondition: a PR csak akkor merge-elhető, ha a build-test a PR head-en és a merge queue commiton is zöld.

48.1.10.3 3. Diagnosztikai feladat: flaky test és merge queue

A merge queue beragadt, mert a build-test job a sanitizer-leak smoke tesztben időnként piros. A teszt logban a LeakSanitizer nem jelez valódi szivárgást, de a test_order_dependent teszt a parallel futtatás során időnként ütközik. Diagnosztizáld a hibát a pipeline log és ctest ismételt futtatása alapján. Javasolj egy változtatást a quality gate-ben és a tesztkódban, majd add meg az ellenőrzési feltételt. Postcondition: a merge queue determinisztikusan zöld, a flaky teszt quarantinban van, és a valódi determinisztikus tesztek futnak a gateben.

48.1.11 Megoldások

48.1.11.1 1. Megoldás

A pull_request trigger a PR head commit d4e5f6-en fut, mert a workflow ref kifejezése a github.event.pull_request.head.sha értéket veszi. A merge_group trigger a merge queue ideiglenes commitján fut, amely a d4e5f6 és a main head a1b2c3 kombinált állapota; ennek SHA-ja a github.sha. A pull request trigger önmagában nem igazolja a merge biztonságát, mert a main head folyamatosan mozoghat, és a kombinált állapot nem azonos a PR headdel. A merge queue a tényleges merge-kísérletet teszteli, ezért a gate számára ez az irányadó.

48.1.11.2 2. Megoldás

A workflow módosítása:

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  merge_group:
    types: [checks_requested]

A branch protection beállítása a gh CLI-vel a példa szerint. Előfeltétel: a repository admin jog és a gh CLI hitelesítése. Target: github.com/lab-org/lab-cpp-svc, branch main. A módosítás után a required check build-test. Rollback: a workflow fájl visszaállítása a korábbi revízióra, és a branch protection törlése. Postcondition ellenőrzése: egy új PR esetén a gh pr checks kimenetben a build-test mind a pull_request, mind a merge_group kontextusban zöld; a merge gomb csak a required checkek sikere után aktív.

48.1.11.3 3. Megoldás

A diagnózishoz a workflow logból kinyerjük a test_order_dependent teszt nevét, majd lokálisan ctest --repeat until-pass:10 -R test_order_dependent futtatással igazoljuk a nem determinisztikus viselkedést. A quality gate változtatása: a test_order_dependent tesztet kivesszük a build-test jobból, és külön, non-blocking flaky-quarantine jobba helyezzük. A workflow YAML-ben a required check továbbra is a build-test; a quarantin job nem blokkol. A tesztkódban a hibát megszüntetjük a globális állapot izolálásával vagy explicit sorrendi függés megszüntetésével. Ellenőrzési feltétel: a build-test három egymást követő futtatása zöld; a flaky-quarantine job továbbra is naplózza a hibát; a merge queue újra feldolgozza a PR-t és a required checkek determinisztikusan zöldek.

48.1.12 Rövid összefoglaló

A d236 a Git delivery trigger, a tested revision és a quality gate kapcsolatát tanítja. A CI trigger határozza meg, melyik commiton fut a pipeline; a merge queue a PR-t a cél branchre illesztett kombinált commiton teszteli, ezért erősebb bizonyíték a merge biztonságára. A tested revision és a deployed artifact közötti explicit kapcsolat nélkül a pipeline eredménye nem vihető át a deploymentre. Továbbhasznált definíciók:

  • Tested revision: az a forrás commit SHA, amelyre a CI pipeline ténylegesen lefutott.
  • Quality gate: a merge vagy deploy előtti kötelező ellenőrzések és protected ref policyk együttese.
  • Merge queue: a PR merge-kísérletét a cél branch friss állapotán újratesztelő automatizált sor.
