29.5 TLS/proxy és end-to-end elérhetőségi labor

29.5.1 Mit bizonyít az, hogy „elérhető”?

Az edge végpont akkor használható, ha a kliens megfelelő címre jut, létrejön a TCP-kapcsolat, sikeres a hitelesített TLS-kézfogás, majd az alkalmazás megfelelő HTTP-választ ad. Egy nyitott port, egy érvényes tanúsítvány vagy egy 200 OK önmagában nem bizonyítja mindezt.

Végponttól végpontig tartó elérhetőség (end-to-end availability): egy meghatározott kliensnézőpontból, névvel, bizalmi tárral és időkorláttal végrehajtott, szemantikailag ellenőrzött kérés sikeressége.

A labor ugyanazon izolált VM-en vizsgálja a rétegeket. Ez reprodukálható hibakeresési környezet, nem többhostos rendelkezésreállási bizonyíték. Az előző tanúsítvány-életciklus és DNS/idő diagnosztika itt egyetlen kérésútban találkozik.

29.5.2 Laborszerződés és adatút

Minden parancs célpontja lab-edge, Ubuntu Server 24.04 LTS amd64 VM. A normál fiók lab-admin, UID 1000; kizárólag a csomagrögzítéshez kell sudo, UID 0. Minden blokk ugyanabban a Bash-munkamenetben fut, kivéve a külön jelölt második terminált.

Előfeltétel: telepített nginx, openssl, curl, dnsutils, dnsmasq-base, iproute2, tcpdump, python3; működő labkonzol. A rendszer nginx-szolgáltatását, resolverét és bizalmi tárát nem módosítjuk.

A fájlokban tárolt állapotot külön kezeljük a megfigyelt tanúsítványtól, folyamattól és backendválasztól. Minden komponens közös hosthibadoménben van.

29.5.3 Kidolgozott példa: CA, két backend és TLS edge

29.5.3.1 Rövid életű labor-PKI

A lánc: gyökér-hitelesítésszolgáltató (root CA) → köztes hitelesítésszolgáltató (intermediate CA) → szervertanúsítvány. A kliens csak a gyökeret kapja bizalmi horgonyként; a szerver a levél- és köztes tanúsítványt küldi.

A titkosítatlan privát kulcsok kizárólag ehhez az eldobható laborhoz használhatók. Nem kerülnek rendszerbizalmi tárba, repositoryba vagy másik gépre.

# lab-edge, lab-admin, UID 1000; munkakönyvtár: $LAB
openssl req -x509 -newkey rsa:2048 -noenc -sha256 -days 2 \
  -subj "/CN=lab-d145-root" \
  -keyout lab-root.key -out lab-root.crt \
  -addext "basicConstraints=critical,CA:TRUE,pathlen:1" \
  -addext "keyUsage=critical,keyCertSign,cRLSign"

cat > lab-int.ext <<'EOF'
basicConstraints=critical,CA:TRUE,pathlen:0
keyUsage=critical,keyCertSign,cRLSign
subjectKeyIdentifier=hash
authorityKeyIdentifier=keyid,issuer
EOF

openssl req -new -newkey rsa:2048 -noenc \
  -subj "/CN=lab-d145-intermediate" \
  -keyout lab-int.key -out lab-int.csr
openssl x509 -req -in lab-int.csr -CA lab-root.crt \
  -CAkey lab-root.key -set_serial 2 -days 2 -sha256 \
  -extfile lab-int.ext -out lab-int.crt

cat > lab-leaf.ext <<'EOF'
basicConstraints=critical,CA:FALSE
keyUsage=critical,digitalSignature,keyEncipherment
extendedKeyUsage=serverAuth
subjectAltName=DNS:lab-edge.test
EOF

openssl req -new -newkey rsa:2048 -noenc \
  -subj "/CN=lab-edge.test" \
  -keyout lab-leaf.key -out lab-leaf.csr
openssl x509 -req -in lab-leaf.csr -CA lab-int.crt \
  -CAkey lab-int.key -set_serial 3 -days 1 -sha256 \
  -extfile lab-leaf.ext -out lab-leaf.crt

cat lab-leaf.crt lab-int.crt > lab-chain.pem
cp lab-chain.pem lab-chain.good.pem
openssl verify -CAfile lab-root.crt -untrusted lab-int.crt \
  -purpose sslserver -verify_hostname lab-edge.test lab-leaf.crt

Várt eredmény: lab-leaf.crt: OK. Ez fájlalapú láncellenőrzés, nem bizonyítja, hogy az edge ugyanezt küldi.

29.5.3.2 Egészséges és forgalomfogadásra kész backend

Az egészséges (healthy) folyamat képes működni; a kész (ready) példány az adott szolgáltatási szerződés szerint fogadhat forgalmat. Például az alkalmazás élhet úgy, hogy még nincs betöltve az adatállománya.

A fixture /healthz végpontja mindig 200-at ad; a readiness és a többi útvonal 503-at ad egy név szerint kijelölt jelzőfájl jelenlétében.

cat > lab-backend.py <<'PY'
import sys, time
from pathlib import Path
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

port = int(sys.argv[1])
root = Path(sys.argv[2])

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        ready = not (root / f"lab-unready-{port}").exists()
        status = 200 if self.path == "/healthz" or ready else 503
        marker = root / f"lab-inflight-{port}"
        slow = self.path == "/slow" and status == 200
        self.log_message("begin id=%s",
                         self.headers.get("X-Lab-ID", "-"))
        if slow:
            marker.touch()
        try:
            if status == 200:
                time.sleep({"/slow": 4, "/stall": 8}.get(self.path, 0))
            body = f"lab-backend-{port} ready={ready}\n".encode()
            self.send_response(status)
            self.send_header("Content-Type", "text/plain")
            self.send_header("Content-Length", str(len(body)))
            self.end_headers()
            self.wfile.write(body)
        except (BrokenPipeError, ConnectionResetError):
            pass  # A timeouttesztben a proxy már lezárhatta a kapcsolatot.
        finally:
            if slow:
                marker.unlink(missing_ok=True)

ThreadingHTTPServer(("127.0.0.1", port), Handler).serve_forever()
PY

python3 lab-backend.py 18081 "$LAB" > lab-backend-18081.log 2>&1 &
LAB_B1_PID=$!
python3 lab-backend.py 18082 "$LAB" > lab-backend-18082.log 2>&1 &
LAB_B2_PID=$!

 /usr/sbin/dnsmasq --conf-file=/dev/null --no-daemon \
  --port=1053 --listen-address=127.0.0.1 --bind-interfaces \
  --no-hosts --no-resolv --address=/lab-edge.test/127.0.0.1 \
  > lab-dns.log 2>&1 &
LAB_DNS_PID=$!

29.5.3.3 Dedikált nginx-példány

A labor aktív–tartalék topológiát használ. Nincs aktív readiness-lekérdezés, automatikus újrapróbálkozás vagy passzív kivonás: így a hibák nem rejtőznek el második backend mögött.

cat > lab-nginx.conf <<EOF
daemon off;
worker_processes 1;
worker_shutdown_timeout 10s;
pid $LAB/lab-nginx.pid;
error_log $LAB/lab-error.log info;

events { worker_connections 128; }

http {
    client_body_temp_path $LAB/lab-body;
    proxy_temp_path $LAB/lab-proxy;
    fastcgi_temp_path $LAB/lab-fastcgi;
    uwsgi_temp_path $LAB/lab-uwsgi;
    scgi_temp_path $LAB/lab-scgi;

    log_format lab '\$time_iso8601 id=\$http_x_lab_id status=\$status '
                   'upstream=\$upstream_addr us=\$upstream_status '
                   'rt=\$request_time urt=\$upstream_response_time';
    access_log $LAB/lab-access.log lab;
    ssl_protocols TLSv1.2 TLSv1.3;

    upstream lab_pool {
        server 127.0.0.1:18081 max_fails=0;
        server 127.0.0.1:18082 backup;
    }

    server {
        listen 127.0.0.1:18443 ssl default_server;
        ssl_reject_handshake on;
    }

    server {
        listen 127.0.0.1:18443 ssl;
        server_name lab-edge.test;
        ssl_certificate $LAB/lab-chain.pem;
        ssl_certificate_key $LAB/lab-leaf.key;

        location / {
            proxy_pass http://lab_pool;
            proxy_http_version 1.1;
            proxy_set_header Connection close;
            proxy_set_header Host \$host;
            proxy_set_header X-Lab-ID \$http_x_lab_id;
            proxy_connect_timeout 1s;
            proxy_read_timeout 6s;
            proxy_next_upstream off;
        }
    }
}
EOF

lab_nginx() {
    /usr/sbin/nginx -p "$LAB/" -c "$LAB/lab-nginx.conf" \
        -e "$LAB/lab-error.log" "$@"
}
lab_reload() {
    lab_nginx -t && lab_nginx -s reload
}

cp lab-nginx.conf lab-nginx.good.conf
lab_nginx -t &&
    lab_nginx > lab-nginx-start.log 2>&1 &
LAB_NGINX_PID=$!

A reload aszinkron: a jelzés elküldése még nem bizonyítja az új állapotot. Minden változtatás után új klienskapcsolattal ellenőrizz; legfeljebb öt másodpercig ismételd a próbát, majd sikertelenségnél vizsgáld a naplót.

29.5.4 Egy kérés rétegenkénti vizsgálata

# lab-edge, lab-admin, UID 1000
dig @127.0.0.1 -p 1053 lab-edge.test A +noall +answer
LAB_IP=$(dig @127.0.0.1 -p 1053 lab-edge.test A +short)
test "$LAB_IP" = 127.0.0.1 || { echo "Hibás DNS-válasz"; exit 1; }

ss -lntp | grep -E ':(18443|18081|18082)[[:space:]]'

openssl s_client -connect "$LAB_IP:18443" \
  -servername lab-edge.test -verify_hostname lab-edge.test \
  -verify_return_error -CAfile "$LAB/lab-root.crt" \
  -showcerts </dev/null

lab_curl() {
    curl --noproxy '*' --silent --show-error --max-time 10 \
      --cacert "$LAB/lab-root.crt" \
      --resolve "lab-edge.test:18443:$LAB_IP" "$@"
}
lab_curl -v -H 'X-Lab-ID: lab-baseline' \
    https://lab-edge.test:18443/

tail -n 10 lab-access.log lab-error.log

Várt ellenőrzési lánc:

Réteg Bizonyíték Amit nem bizonyít
DNS A rekord: 127.0.0.1 A rendszerresolver ugyanígy válaszol
TCP ss: listenerek; sikeres kapcsolat TLS vagy alkalmazás helyessége
TLS érvényes lánc, megfelelő név backend readiness
HTTP 200 és lab-backend-18081 ready=True más kliensút vagy más host elérhetősége

A --resolve a dig által ellenőrzött címet használja, miközben megőrzi a TLS-nevet és a HTTP-hostnevet. Ez kontrollált DNS-bypass, nem a rendszerresolver tesztje.

A TLS szervernév-jelzését (Server Name Indication, SNI) a kliens a kézfogásban küldi; a HTTP Host fejléc csak később következik.

A napló dátuma és a pcap időbélyege falióra-domain; órahibánál ne kizárólag ezekkel korrelálj. Használd a lab-baseline azonosítót is. Az rt és urt másodpercben megadott időtartam, nem abszolút időbélyeg; konkrét implementációjuk óraforrását ez a labor nem validálja.

29.5.5 Hibainjektálás, ellenpróba és javítás

29.5.5.1 Hiányzó köztes tanúsítvány

cp lab-leaf.crt lab-chain.pem
lab_reload
lab_curl https://lab-edge.test:18443/

# Visszaállítás
cp lab-chain.good.pem lab-chain.pem
lab_reload
lab_curl --fail https://lab-edge.test:18443/

Várt hibajelenség: a konfigurációteszt sikerülhet, de a kliens tanúsítvány-ellenőrzési hibát jelez, tipikusan 60-as curl-kóddal. Az s_client -showcerts csak a levéltanúsítványt mutatja.

A helyes javítás a szerverlánc pótlása. A -k, a köztes tanúsítvány bizalmi horgonnyá tétele vagy a védelem globális kikapcsolása nem megfelelő javítás. A postcondition: kizárólag a gyökérrel bízó kliens ismét sikeres.

29.5.5.2 SNI- és órafixture

openssl s_client -connect 127.0.0.1:18443 -noservername \
  -verify_hostname lab-edge.test -verify_return_error \
  -CAfile lab-root.crt </dev/null

openssl x509 -in lab-leaf.crt -noout -dates
LAB_FUTURE=$(( $(date +%s) + 36 * 3600 ))
openssl verify -attime "$LAB_FUTURE" \
  -CAfile lab-root.crt -untrusted lab-int.crt \
  -purpose sslserver -verify_hostname lab-edge.test lab-leaf.crt

SNI nélkül a default TLS-szerver elutasítja a kézfogást. Ellenpróba: ugyanaz a cím helyes -servername értékkel sikeres. Egy kézzel beállított HTTP Host fejléc nem javítja a korábban meghiúsult TLS-kézfogást.

Az -attime a kliens ellenőrzési falióráját modellezi, Unix-epoch másodpercben. Frissen létrehozott PKI-nál 36 óra múlva a levél már lejárt, a kétnapos CA-k még érvényesek. A host óráját nem módosítjuk. Valódi incidensben a tanúsítvány érvényességét és a kliens időszinkronját külön ellenőrizd.

29.5.5.3 Healthy nem egyenlő ready

touch lab-unready-18081
curl --noproxy '*' -i http://127.0.0.1:18081/healthz
curl --noproxy '*' -i http://127.0.0.1:18081/readyz
lab_curl -i https://lab-edge.test:18443/
rm -- lab-unready-18081

Várt eredmény: 200, 503, 503. A proxy nem találja ki a readiness jelentését. A naplóban status=503, us=503 és az elsődleges backend címe különíti el ezt a TLS-hibától. HTTP 503 mellett a curl önmagában sikeres kilépési kódot is adhat; automatizált elfogadási próbához használj --fail kapcsolót és tartalomellenőrzést.

29.5.5.4 Timeout, kiürítés és reload

lab_curl -i -H 'X-Lab-ID: lab-timeout' \
    https://lab-edge.test:18443/stall

Várt eredmény: körülbelül hat másodperc után 504; az error log upstream-olvasási timeoutot jelez. A backend nyolc másodpercig nem küld választ. A proxy_read_timeout két olvasás közötti várakozási korlát, nem általános teljes kérésdeadline. A curl tíz másodperces teljes korlátja ettől külön szerződés.

A kiürítés (drain) során előbb megszüntetjük az új forgalom kiosztását, majd megvárjuk a folyamatban lévő kéréseket:

curl --noproxy '*' --fail http://127.0.0.1:18082/readyz

lab_curl --fail -H 'X-Lab-ID: lab-drain' \
  https://lab-edge.test:18443/slow > lab-slow.result &
LAB_REQUEST_PID=$!

if timeout 2s bash -c \
  'until test -f "$LAB/lab-inflight-18081"; do sleep 0.05; done'
then
    sed -i 's/18081 max_fails=0;/18081 max_fails=0 down;/' \
        lab-nginx.conf
    lab_reload
else
    echo "Nem figyeltünk meg folyamatban lévő kérést; a teszt nem értékelhető."
fi

wait "$LAB_REQUEST_PID"
cat lab-slow.result
lab_curl --fail https://lab-edge.test:18443/

Várt postcondition: a korábban indított kérés az elsődleges backendről sikeresen befejeződik; az új kapcsolaton küldött kérés már lab-backend-18082 választ kap. A reload alatti régi worker még kiszolgálhat meglévő kapcsolatokat. A tíz másodperces worker_shutdown_timeout kemény felső korlát: nem garantál tetszőleges hosszúságú kérésbefejezést.

29.5.6 Rollback és takarítás

A rollback csak addig használható, amíg a rövid életű labor-tanúsítvány érvényes:

# lab-edge, lab-admin, UID 1000
cp lab-nginx.good.conf lab-nginx.conf
cp lab-chain.good.pem lab-chain.pem
rm -f -- lab-unready-18081 lab-unready-18082
lab_reload
lab_curl --fail https://lab-edge.test:18443/

Elfogadási feltétel: hitelesített TLS, 200, ismét az elsődleges backend. Ezután a kizárólag ehhez a laborhoz tartozó folyamatokat és könyvtárat távolítjuk el:

lab_nginx -s quit
wait "$LAB_NGINX_PID"

# Ugyanaz a shell; a PID-változók a fent indított folyamatokhoz tartoznak.
kill -TERM "$LAB_DNS_PID" "$LAB_B1_PID" "$LAB_B2_PID"
wait "$LAB_DNS_PID" "$LAB_B1_PID" "$LAB_B2_PID" || :

cd "$HOME" || exit 1
test "$LAB" = "$HOME/lab-d145" && test ! -L "$LAB" &&
    rm -r -- "$LAB"

ss -H -lntup | grep -E ':(1053|18443|18081|18082)([[:space:]]|$)'

Várt végállapot: nincs laborlistener és nincs laborkönyvtár. A fájltörlés nem bizonyít fizikai kulcsmegsemmisítést; VM-snapshot vagy külső mentés tartalmazhat másolatot. Emiatt a labor-CA soha ne kapjon laboron kívüli bizalmat.

29.5.7 Feladatok

  1. Magyarázó: Miért nem elegendő a nyitott TCP-port és a /healthz 200-as válasza az edge elfogadásához?
  2. Konfigurációs: Ürítsd ki az elsődleges backendet reload segítségével, majd állítsd vissza. Bizonyítsd a folyamatban lévő kérés befejeződését és az új kérés célpontját.
  3. Diagnosztikai: Egy társad válasszon a hiányzó köztes tanúsítvány, SNI-hiány, readiness-hiba és timeout közül. Készíts rétegenkénti bizonyítéktáblát; csak egy változtatással javíts, majd ismételd meg ugyanazt a klienspróbát.

29.5.8 Megoldások

  1. A TCP csak kapcsolatfelépítést, a health endpoint csak saját szerződését bizonyítja. Kell DNS/címellenőrzés, névhelyes és megbízható TLS, valamint szemantikai alkalmazáspróba. Postcondition: minden réteghez megnevezett bizonyíték és bizonyítási korlát tartozik.

  2. Előbb igazold a tartalék readinessét; indíts lassú kérést, majd a marker megjelenése után állítsd down állapotba az elsődlegest és reloadolj. A régi kérés befejezése előtt ne állítsd le a backendet. Postcondition: régi kérés → 18081; új kérés → 18082; rollback után új kérés → 18081.

  3. TLS-lánchibánál showcerts és root-only validáció dönt; SNI-hibánál azonos címen a névjelzés változtatása; readiness-hibánál upstream 503; timeoutnál 504 és upstream timeoutnapló. Postcondition: a javított eredeti próba sikeres, a bizalmi ellenőrzés változatlanul bekapcsolt, és a napló az elvárt backendet mutatja.

29.5.9 Rövid összefoglaló

A laborban a DNS, TCP, TLS és HTTP külön bizonyítási réteg maradt, miközben ugyanazt a szolgáltatási kérést vizsgáltuk. A helyes javítás a hibás állapot tulajdonosát célozta: szerverláncot, kliensnévjelzést, ellenőrzési időt vagy backendforgalmat. A readiness, timeout és kiürítés külön szerződés; egyik sem következik pusztán a folyamat életéből. A reload elfogadása új klienskapcsolaton megfigyelt állapotot igényelt. A napló és a csomagnyom együtt erősebb bizonyítékot adott, de a közös host és a kontrollált resolverút korlátozta az eredmény általánosíthatóságát.

  • Readiness: az adott példány alkalmassága új szolgáltatási kérés fogadására.
  • Drain: új forgalom kizárása a folyamatban lévő munka befejezésének megengedésével.
  • SNI: TLS-kézfogásban küldött szervernév.

29.5.10 Források és ellenőrzési hiányok

Nem történt webes forrásolvasás vagy laborfuttatás. A kimenetek várt eredmények, nem mérések. Elsődleges ellenőrzési kiindulópontok:

  • Nginx: Controlling nginx — reload és worker-életciklus.
  • Nginx HTTP SSL module — lánc és kézfogás-elutasítás.
  • Nginx HTTP proxy module — timeout és újrapróbálkozás.
  • OpenSSL 3.0: openssl-s_client — SNI és szerverellenőrzés.
  • OpenSSL 3.0: openssl-verify — név, cél és ellenőrzési idő.
