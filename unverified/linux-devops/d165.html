33.5 Routing/overlay haladó labor

33.5.1 Motiváció

Adatközponti fabric alatt egy alkalmazáskimaradás gyakran két rétegben egyszerre jelentkezik: a fizikai vagy IP-útvonali underlay kiesik, miközben a VXLAN overlay ugyanarról a forgalomról már nem is tud. A hibakeresés akkor hatékony, ha a két réteget külön bizonyítékokkal lokalizáljuk, majd control-plane változtatás után konvergenciát mérünk. Ebben a laborban egy kicsinyített, de valódi FRR/namespace topológián gyakoroljuk az underlay/overlay szétválasztást, a single link/node failure utáni reconvergence-t és a VXLAN encapsulation adatútjának ellenőrzését.

33.5.2 Definíció és működés

Az underlay az a hálózati réteg, amely tényleges IP-kapcsolatot és útvonalakat biztosít a hálózati eszközök között. Legyen BGP-alapú, spine–leaf felépítésű IP-fabric: minden leaf két spine-nal peerel, így egy link kiesése után is marad alternatív útvonal.

Az overlay ezen a transporton szeparált, címzett virtuális hálózatot hoz létre. A VXLAN egy UDP-s encapsulation (RFC 7348): a belső Ethernet frame-et egy külső IP/UDP fejlécbe csomagolja, és a VXLAN Network Identifier (VNI) azonosítja a tenant hálózatot. A VTEP (VXLAN Tunnel Endpoint) a fogadó/küldő pont: esetünkben minden leaf egy VTEP, amely a belső bridge-ben VXLAN portként jelenik meg.

A control plane a BGP prefixek cseréjét és a VTEP loopback címek elérhetőségét terjeszti. A data plane a tényleges VXLAN payload továbbítást végzi. A konvergencia az az idő, amíg egy hiba után az útvonalválasztás újra jóvá lesz, és a forgalom ismét át tud haladni az alternatív úton.

A laborban FRR-t (Free Range Routing) használunk BGP daemonként, network namespace-eket eszköziportunkénti izolációra, Linux bridget VXLAN-összekötésre.

33.5.3 Laborterv és topológia

A labhost labvm01, UID root (a módosító parancsok előfeltétele). A dedicated labobjektumok mind lab- előtaggal készülnek; cleanup csak ezekre terjed ki.

Namespace Szerep Loopback/overlay
lab-spine1 spine, AS 65000 –
lab-spine2 spine, AS 65000 –
lab-leaf1 leaf, AS 65010 10.255.0.1/32 VTEP
lab-leaf2 leaf, AS 65020 10.255.0.2/32 VTEP
lab-h1 host 1 192.168.100.1/24
lab-h2 host 2 192.168.100.2/24

Underlay linkek /31 pont-pont alhálózatokkal:

Link leaf IP spine IP
lab-le1-sp1 ↔︎ lab-sp1-le1 10.0.0.0/31 10.0.0.1/31
lab-le1-sp2 ↔︎ lab-sp2-le1 10.0.1.0/31 10.0.1.1/31
lab-le2-sp1 ↔︎ lab-sp1-le2 10.0.2.0/31 10.0.2.1/31
lab-le2-sp2 ↔︎ lab-sp2-le2 10.0.3.0/31 10.0.3.1/31

A leaf-eken lab-br0 bridge, alá lab-vxlan0 VXLAN interface kerül. A hostok lab-h1 és lab-h2 egy-egy veth párral csatlakoznak a bridge-hez. Az overlay MTU 1450 byte, mert az underlay MTU 1500, és a VXLAN overhead tipikusan 50 byte. A VXLAN-encapsulált frame 1500 + 50 = 1550 byte lenne, ezért a belső hálózatnak kisebb MTU-t adunk.

33.5.4 Kidolgozott példa: namespace/VXLAN/bridge setup és FRR konfiguráció

A következő script részlet a topológia hálózati rétegét hozza létre. A script nem futtat, és a példa nem tartalmaz éles adatot.

#!/usr/bin/env bash
set -euo pipefail
# Labhost: labvm01, UID: root, disposable lab-only objektumok.
NS="lab-spine1 lab-spine2 lab-leaf1 lab-leaf2 lab-h1 lab-h2"
for ns in $NS; do ip netns add "$ns"; done

# leaf1 uplinkek
ip link add lab-le1-sp1 type veth peer name lab-sp1-le1
ip link add lab-le1-sp2 type veth peer name lab-sp2-le1
ip link set lab-le1-sp1 netns lab-leaf1
ip link set lab-le1-sp2 netns lab-leaf1
ip link set lab-sp1-le1 netns lab-spine1
ip link set lab-sp2-le1 netns lab-spine2

# leaf2 uplinkek
ip link add lab-le2-sp1 type veth peer name lab-sp1-le2
ip link add lab-le2-sp2 type veth peer name lab-sp2-le2
ip link set lab-le2-sp1 netns lab-leaf2
ip link set lab-le2-sp2 netns lab-leaf2
ip link set lab-sp1-le2 netns lab-spine1
ip link set lab-sp2-le2 netns lab-spine2

# host veth-ek
ip link add lab-h1-veth type veth peer name lab-leaf1-h1
ip link add lab-h2-veth type veth peer name lab-leaf2-h2
ip link set lab-h1-veth netns lab-h1
ip link set lab-h2-veth netns lab-h2
ip link set lab-leaf1-h1 netns lab-leaf1
ip link set lab-leaf2-h2 netns lab-leaf2

# IP-címek, underlay
ip netns exec lab-leaf1 ip addr add 10.0.0.0/31 dev lab-le1-sp1
ip netns exec lab-spine1 ip addr add 10.0.0.1/31 dev lab-sp1-le1
ip netns exec lab-leaf1 ip addr add 10.0.1.0/31 dev lab-le1-sp2
ip netns exec lab-spine2 ip addr add 10.0.1.1/31 dev lab-sp2-le1
ip netns exec lab-leaf2 ip addr add 10.0.2.0/31 dev lab-le2-sp1
ip netns exec lab-spine1 ip addr add 10.0.2.1/31 dev lab-sp1-le2
ip netns exec lab-leaf2 ip addr add 10.0.3.0/31 dev lab-le2-sp2
ip netns exec lab-spine2 ip addr add 10.0.3.1/31 dev lab-sp2-le2

# linkek up
for ns in $NS; do ip netns exec "$ns" ip link set lo up; done
ip netns exec lab-leaf1 ip link set lab-le1-sp1 up
ip netns exec lab-leaf1 ip link set lab-le1-sp2 up
ip netns exec lab-leaf2 ip link set lab-le2-sp1 up
ip netns exec lab-leaf2 ip link set lab-le2-sp2 up
ip netns exec lab-spine1 ip link set lab-sp1-le1 up
ip netns exec lab-spine1 ip link set lab-sp1-le2 up
ip netns exec lab-spine2 ip link set lab-sp2-le1 up
ip netns exec lab-spine2 ip link set lab-sp2-le2 up

# leaf loopback (VTEP source)
ip netns exec lab-leaf1 ip addr add 10.255.0.1/32 dev lo
ip netns exec lab-leaf2 ip addr add 10.255.0.2/32 dev lo

# bridge, VXLAN, host csatolás leaf1-en
ip netns exec lab-leaf1 ip link add lab-br0 type bridge
ip netns exec lab-leaf1 ip link add lab-vxlan0 type vxlan id 100 local 10.255.0.1 dstport 4789 nolearning
ip netns exec lab-leaf1 ip link set lab-vxlan0 master lab-br0
ip netns exec lab-leaf1 bridge fdb append 00:00:00:00:00:00 dev lab-vxlan0 dst 10.255.0.2
ip netns exec lab-leaf1 ip link set lab-vxlan0 up
ip netns exec lab-leaf1 ip link set lab-leaf1-h1 master lab-br0
ip netns exec lab-leaf1 ip link set lab-leaf1-h1 up
ip netns exec lab-leaf1 ip link set lab-br0 up
ip netns exec lab-leaf1 ip link set lab-leaf1-h1 mtu 1450
ip netns exec lab-h1 ip link set lab-h1-veth mtu 1450

# leaf2 oldalon hasonló
ip netns exec lab-leaf2 ip link add lab-br0 type bridge
ip netns exec lab-leaf2 ip link add lab-vxlan0 type vxlan id 100 local 10.255.0.2 dstport 4789 nolearning
ip netns exec lab-leaf2 ip link set lab-vxlan0 master lab-br0
ip netns exec lab-leaf2 bridge fdb append 00:00:00:00:00:00 dev lab-vxlan0 dst 10.255.0.1
ip netns exec lab-leaf2 ip link set lab-vxlan0 up
ip netns exec lab-leaf2 ip link set lab-leaf2-h2 master lab-br0
ip netns exec lab-leaf2 ip link set lab-leaf2-h2 up
ip netns exec lab-leaf2 ip link set lab-br0 up

ip netns exec lab-h1 ip addr add 192.168.100.1/24 dev lab-h1-veth
ip netns exec lab-h2 ip addr add 192.168.100.2/24 dev lab-h2-veth
ip netns exec lab-h1 ip link set lab-h1-veth up
ip netns exec lab-h2 ip link set lab-h2-veth up

A FRR BGP konfigurációja minden namespace-ben saját fájlba kerül. A leaf1-re példaként:

hostname lab-leaf1
router bgp 65010
 bgp router-id 10.255.0.1
 no bgp default ipv4-unicast
 neighbor 10.0.0.1 remote-as 65000
 neighbor 10.0.0.1 timers 1 3
 neighbor 10.0.1.1 remote-as 65000
 neighbor 10.0.1.1 timers 1 3
 address-family ipv4 unicast
  network 10.255.0.1/32
  neighbor 10.0.0.1 activate
  neighbor 10.0.1.1 activate
 exit-address-family

A spine1 konfigurációja:

hostname lab-spine1
router bgp 65000
 bgp router-id 10.0.0.1
 no bgp default ipv4-unicast
 neighbor 10.0.0.0 remote-as 65010
 neighbor 10.0.0.0 timers 1 3
 neighbor 10.0.2.0 remote-as 65020
 neighbor 10.0.2.0 timers 1 3
 address-family ipv4 unicast
  neighbor 10.0.0.0 activate
  neighbor 10.0.2.0 activate
 exit-address-family

A másik oldalak ebből analóg módon következnek. A labban az FRR daemon a namespace-ben:

ip netns exec lab-leaf1 /usr/lib/frr/zebra -d -f /etc/frr/frr.conf
ip netns exec lab-leaf1 /usr/lib/frr/bgpd -d -f /etc/frr/frr.conf

A parancsok pontos daemonútvonala és a config path a disztribúció verziójától függ; az Ubuntu 24.04 LTS-hez tartozó FRR csomagverziót ellenőrizni kell.

33.5.5 Ellenőrzés: underlay, overlay, payload path

Az underlay bizonyítékát a BGP session és a tanult prefixek adják:

ip netns exec lab-leaf2 vtysh -c 'show bgp ipv4 unicast summary'
ip netns exec lab-leaf2 vtysh -c 'show bgp ipv4 unicast 10.255.0.1/32'
ip netns exec lab-leaf2 ip route show

Elvárt kimenet: a 10.255.0.1/32 prefixet lab-leaf2 mindkét spine-on át látja, és a show bgp a session state értékeként Established-et mutat.

Az overlay payload path-ja a következő lépésekben ellenőrizhető:

  1. h1 és h2 közötti ping a belső hálózaton.
  2. Capture a leaf1 uplinkjén, hogy a VXLAN UDP 4789 forgalom látszik.
  3. A bridge FDB entry ellenőrzése.
ip netns exec lab-leaf1 bridge fdb show dev lab-vxlan0
ip netns exec lab-h1 ping -c 3 192.168.100.2
ip netns exec lab-leaf1 tcpdump -ni lab-le1-sp2 -c 5 'udp port 4789'

A bridge fdb kimenetében látszik a dst 10.255.0.2, a ping sikeres, a tcpdump pedig encapsulált VXLAN frame-et mutat.

Az MTU ellenőrzése DF beállítással:

ip netns exec lab-h1 ping -M do -s 1422 -c 3 192.168.100.2

A payload 1422 byte; az ICMP 8 plusz IP 20 headerrel együtt 1450 byte, ami a beállított belső MTU-nak felel meg. Ha a kimenet Frag needed hibát ad, a belső MTU rossz.

33.5.6 Single link/node failure és konvergenciamérés

A failure fixture egyetlen link leállítása. A lab-leaf2 és lab-spine1 közötti linket kapcsoljuk le, így a lab-leaf2 VTEP loopbackjéhez vezető underlay útnak át kell térnie lab-spine2-n keresztül.

A mérést időbélyegzett pinggel végezzük:

ip netns exec lab-h1 ping -D -i 0.2 192.168.100.2 > /tmp/lab-ping.log &
PING_PID=$!
sleep 2
ip netns exec lab-leaf2 ip link set lab-le2-sp1 down
sleep 8
kill "$PING_PID"
grep -E '^\[[0-9]' /tmp/lab-ping.log

A ping -D az EPOCH időbélyeget adja. A hibainjekció előtt minden csomagnak 64 bytes válasza van. A linkdown utáni első másodpercekben a BGP default hold/időzítőktől függően kiesés látható. Hipotetikus, illusztratív laboradat:

idősor [s] válasz megjegyzés
0.0–2.0 success kiinduló állapot
2.2 timeout underlay failure után
2.4–4.4 timeout BGP hold timer még nem járt le
4.6 success alternatív path aktív, VXLAN folyamat újra megy

A konvergenciát a linkdown pillanata és az első sikeres válasz között számítjuk: kb. 2.4 s a hipotetikus példában. A lab beállítás 1 s keepalive, 3 s hold timer, ezért ilyen nagyságrendű. Ha a konvergencia az elvártnál lassabb, gyorsabb timert vagy BFD-t kell alkalmazni.

A route bizonyítékot a linkdown után:

ip netns exec lab-leaf1 vtysh -c 'show bgp ipv4 unicast 10.255.0.2/32'
ip netns exec lab-leaf1 ip route get 10.255.0.2

A kimenet azt mutatja, hogy a következő hop 10.0.1.1 (spine2) lett.

33.5.7 Gyakori hibák és ellenszer

  1. Overlay timeout, de underlay OK. A VTEP loopback ping lab-leaf1 → 10.255.0.2 sikeres, de a belső ping mégsem megy. Ilyenkor a VXLAN bridge-FDB entry hiányos vagy a host veth nincs a bridge-ben. Ellenőrzés: bridge fdb show és bridge link show. Fix: a 00:00:00:00:00:00 flood entry beírása.

  2. MTU mismatch. A belső interfészek 1500 MTU-val maradtak, a VXLAN DF bit miatt a nagy csomagok nem mennek át, a kicsik igen. Ellenőrzés: ping -M do -s 1422. Fix: a belső bridge és host veth MTU 1450-re állítása.

  3. Nem konvergáló BGP route. A linkdown után a backup path nem jelenik meg; a BGP session nem Established. Oka lehet rossz AS, rossz neighbor IP, vagy hiányzó network hirdetés. Ellenőrzés: show bgp ipv4 unicast summary. Fix: a config javítása, majd a BGP session restartja.

  4. Stale FDB entry. Ha a VXLAN data plane learning korábbi bejegyzéseket hagy hátra, a bridge fdb régi dst-t mutat. Megoldás: statikus flood entry használata, és bridge fdb delete a régi entry törlésére.

  5. Túl lassú konvergencia. A default BGP hold timer 180 s. Ez a labban elfogadhatatlan. Explicit neighbor ... timers 1 3 vagy BFD szükséges. A rollbacknél a szándékos gyorsítás után a configot vissza kell állítani a defaultokra, ha a lab célja a viselkedés bemutatása.

33.5.8 Feladatok

  1. Magyarázó feladat. A fenti topológiában azonosítsd be egy h1 → h2 ping adatútján a következő rétegeket: belső Ethernet frame, VNI 100, outer IP 10.255.0.1 → 10.255.0.2, UDP 4789, underlay útválasztás. Listázd, hogy a leaf1 bridge, vxlan0, spine1, spine2 és leaf2 bridge melyik réteghez tartozik.

  2. Adminisztrációs/konfigurációs feladat. Építsd fel a topológiát, állítsd be a FRR BGP timereket 1 3 értékkel. Injektálj single link failure-t a lab-le2-sp1 leállításával. Mérd a konvergenciát időbélyegzett pinggel, és utána állítsd vissza a linket. A mérés után készíts rollbacket a BGP timer default értékekre (pl. a timers sor eltávolításával) és igazold, hogy a session továbbra is Established.

  3. Diagnosztikai/failure/recovery feladat. Szimuláld a hibát: h1 ping h2 irányába timeout, miközben a VTEP loopback ping 10.255.0.2 sikeres. A leaf2 bridge lab-br0 alól törölj egy bridge fdb entry-t vagy töröld a host veth master kapcsolatát. Helyezd vissza, és tcpdump/capture segítségével bizonyítsd, hogy a hiba az overlay layer-ben volt, nem az underlayben.

33.5.9 Megoldások

  1. A payload path rétegei:

    • belső Ethernet frame: overlay L2 a h1 és h2 között;
    • VNI 100: overlay tenant azonosító a VXLAN fejlécben;
    • outer IP 10.255.0.1 → 10.255.0.2: underlay transport, a VTEP loopbackek;
    • UDP 4789: VXLAN dest port, underlay transport;
    • underlay útválasztás: BGP-learned route a spine-okon.
      A leaf1 lab-br0 és vxlan0 az overlay bridge- és VTEP-side részei; a spine-ok az underlay forwardingot végzik; leaf2 lab-br0 az overlay belépési oldala.

  2. A konvergenciamérés lépései a fenti kódban. A BGP timer explicit neighbor ... timers 1 3 sorokat tartalmazó configgal. A linkdown után a ping rövid kiesést mutat, majd a backup path átveszi a forgalmat. A rollback a timers sorok törlése és a BGP session újraindítása; a postcondition show bgp ipv4 unicast summary Established session, és a show ip route továbbra is mindkét VTEP loopbacket tartalmazza.

  3. A diagnosztika: a sikeres VTEP ping bizonyítja az underlayt, a belső ping timeout az overlay hibájára utal. A leaf2 bridge bridge link show kimenetében a host veth nem szerepel masterként. A helyreállítás ip link set lab-leaf2-h2 master lab-br0. A capture a leaf2 lab-vxlan0-on beérkező VXLAN frame-et mutat, de a h2 veth felé nem továbbítódik. Postcondition: h1 ping h2 sikeres, a bridge link show mutatja a host veth-et master alatt.

33.5.10 Rövid összefoglaló

Az alfejezet a VXLAN overlay és BGP underlay együttes diagnosztikáját tanítja. A labor FRR/namespace topológiával, VXLAN bridge- és MTU-konfigurációval, valamint single link failure fixture segítségével méri a control-plane konvergenciát. A rétegzett ellenőrzés sorrendben: underlay route/bgp evidence, overlay bridge/FDB, payload path capture. Továbbhasznált definíciók: underlay – a tényleges IP transport és útválasztási réteg; VXLAN – UDP 4789 feletti L2 encapsulation VNI azonosítóval; konvergencia – az idő a hiba bekövetkezése és a helyreállt forgalomátvitel között.
