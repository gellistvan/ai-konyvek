39.5 Első Kubernetes service és state diagnosztika

39.5.1 Motiváció

A d185 alfejezetben előállított, aláírt, nonroot, read-only root fájlrendszerrel futó C++ OCI image önmagában csak verziózott release artifact. Egyetlen konténer futtatása még nem szolgáltatás: ahhoz deklaráltan specifikálni kell az életciklust, a hálózati végpontot és a diagnosztikai felületet. A Kubernetes API objektumai – Pod, Service, ConfigMap – adják ezt a desired state (kívánt állapot) réteget, amelyből a control plane folyamatosan reconciliationnel (kiegyenlítéssel) állítja elő az observed state-et (megfigyelt állapotot). A szenior C++ fejlesztő számára ez a resource lifetime és az immutable artifact fogalmának kiterjesztése: az image digest ugyanolyan pontos azonosító, mint egy build-id; a config a környezet és a release szétválasztása, mint a C++ kód és a runtime beállítás szétválasztása.

39.5.2 Definíció és működés

A Pod a legkisebb ütemezhető egység a Kubernetesben. Egy Pod egy vagy több konténert futtat közös network namespace-ben, így ugyanazon a loopback interfészen és IPC névtéren osztoznak; a container resource limitjeit a cgroup v2 biztosítja. A Pod specifikációja tartalmazza az image referenciát, portokat, erőforrás-igényeket (requests/limits), probe-okat és securityContext-et. A d185-ben kialakított nonroot, read-only root image ebben a modellben explicit runAsNonRoot és readOnlyRootFilesystem beállítást igényel.

A Service egy stabil hálózati végpont az azonos label selectorral rendelkező Podok halmazához. A ClusterIP típusú Service a cluster belső virtuális IP-jét használja, a selector alapján kiválasztott Podok targetPort-jaira irányítja a forgalmat. A Service mögött a control plane EndpointSlice objektumokat tart karban, így a Podok IP-címének változása nem érinti a klienst. A ConfigMap a környezeti kulcs-érték párokat választja le a release artifactról; a Pod envFrom direktívával injektálja ezeket környezeti változóként.

Az image digest az OCI manifest tartalomcímezett SHA-256 azonosítója. A d185-ben bemutatott registry.example.com/lab-cpp-app:0.1.0@sha256:... formátum a tag-et (mutató) és a digestet (pontos artifact) együtt hordozza, így a pod manifest determinisztikusan hivatkozik a release-re. A namespace a Kubernetesben erőforrások elkülönítésére szolgál: a Pod, Service, ConfigMap nevek egy namespace-n belül egyediek, az eltérő namespace-ek között nem láthatók.

A kubectl state/log/event három diagnosztikai adatforrást jelent. A kubectl get az objektumok desired specifikációját és observed státuszát mutatja; a kubectl describe részletes conditionöket, eseményeket és konténer-állapotokat ad; a kubectl logs a konténer stdout/stderr kimenetét szolgáltatja; a kubectl get events a control plane által generált műveleti eseményeket rögzíti. A livenessProbe azt ellenőrzi, hogy a folyamat él-e – ha nem, a kubelet újraindítja a konténert; a readinessProbe azt, hogy a szolgáltatás fogad-e kéréseket – ha nem, a Service kiveszi a Podot a forgalomból.

A Kind/k3d/minikube labprofil egyetlen gazdagépen futó Kubernetes cluster. A Kind Docker konténerekben futtatja a node-okat, a k3d a k3s disztribúciót Dockerben, a minikube pedig VM-ben vagy Dockerben. Bár az API azonos, a hálózati beállítások és a tároló runtime eltérhet; a labban a Kind cluster a reprodukálható baseline. A támogatott verziók és a CNI pontos állapota a labor telepítési manifestjében rögzítendő – e dolgozat nem állít aktuálisan ellenőrzött sort.

39.5.3 Kidolgozott példa

A példa egy lab-d195 namespace-ben futtat egy lab-app C++ HTTP szolgáltatást. A Pod image registry.example.com/lab-cpp-app:0.1.0@sha256:1111111111111111111111111111111111111111111111111111111111111111 – a tényleges digestet a labor registryből kell lekérdezni (docker manifest inspect vagy skopeo inspect), a fenti hash illusztráció. A Service a cluster belső 8080-as portján teszi elérhetővé a Podot.

namespace.yaml:

apiVersion: v1
kind: Namespace
metadata:
  name: lab-d195

configmap.yaml:

apiVersion: v1
kind: ConfigMap
metadata:
  name: lab-app-config
  namespace: lab-d195
data:
  LISTEN_PORT: "8080"
  LOG_LEVEL: "info"

pod.yaml:

apiVersion: v1
kind: Pod
metadata:
  name: lab-app
  namespace: lab-d195
  labels:
    app: lab-app
spec:
  containers:
  - name: app
    image: registry.example.com/lab-cpp-app:0.1.0@sha256:1111111111111111111111111111111111111111111111111111111111111111
    ports:
    - containerPort: 8080
      name: http
    envFrom:
    - configMapRef:
        name: lab-app-config
    resources:
      requests:
        memory: "64Mi"
        cpu: "100m"
      limits:
        memory: "128Mi"
        cpu: "500m"
    readinessProbe:
      httpGet:
        path: /readyz
        port: 8080
      initialDelaySeconds: 2
      periodSeconds: 5
      timeoutSeconds: 1
      failureThreshold: 3
    livenessProbe:
      httpGet:
        path: /healthz
        port: 8080
      initialDelaySeconds: 10
      periodSeconds: 10
      timeoutSeconds: 1
      failureThreshold: 3
    securityContext:
      runAsNonRoot: true
      readOnlyRootFilesystem: true
  securityContext:
    runAsNonRoot: true

service.yaml:

apiVersion: v1
kind: Service
metadata:
  name: lab-app-svc
  namespace: lab-d195
spec:
  selector:
    app: lab-app
  ports:
  - port: 8080
    targetPort: http
  type: ClusterIP

A módosító parancsok előtt rögzítjük a labtargetet: cluster/context: kind-lab-cluster; namespace: lab-d195; privileged: namespace admin a cluster contextben; előfeltétel: a Kind cluster fut, a kubeconfig a kind-lab-cluster contextre mutat, a C++ image a registryben elérhető. Az alkalmazás:

kubectl --context=kind-lab-cluster apply -f namespace.yaml
kubectl --context=kind-lab-cluster --namespace=lab-d195 apply -f configmap.yaml
kubectl --context=kind-lab-cluster --namespace=lab-d195 apply -f pod.yaml
kubectl --context=kind-lab-cluster --namespace=lab-d195 apply -f service.yaml

Ellenőrzés (verification) a várt observed state ellen:

kubectl --context=kind-lab-cluster --namespace=lab-d195 get pods -o wide
kubectl --context=kind-lab-cluster --namespace=lab-d195 get svc lab-app-svc -o wide
kubectl --context=kind-lab-cluster --namespace=lab-d195 describe pod lab-app
kubectl --context=kind-lab-cluster --namespace=lab-d195 logs pod/lab-app
kubectl --context=kind-lab-cluster --namespace=lab-d195 get events --sort-by=.lastTimestamp

A várt kimenet (illusztratív, tényleges futtatás nélkül): kubectl get pods a lab-app oszlopban 1/1 Running értéket mutat; a get svc a lab-app-svc ClusterIP típusú szolgáltatást jelez; describe pod a Conditions: Ready=True és a probe success bejegyzéseket tartalmazza; logs a C++ alkalmazás indítási üzenetét (Listening on 0.0.0.0:8080) adja; az events a Pulled, Created, Started, Ready eseményeket sorolja.

A Service belső elérhetőségét egy ideiglenes debug podból is ellenőrizhetjük:

kubectl --context=kind-lab-cluster --namespace=lab-d195 run lab-debug --rm -it --image=curl/curl:latest -- sh -c 'curl -fsS http://lab-app-svc:8080/healthz'

A lab-debug pod törlődik a --rm miatt; a parancs a Várt kimenet: 200 OK vagy a /healthz endpoint által definiált egészségjelző válasz.

A cleanup a labor név szerinti objektumaira terjed ki:

kubectl --context=kind-lab-cluster delete namespace lab-d195 --wait

Rollback hálózat-, quota- vagy clusterhiba esetén ugyanez a parancs, mert a namespace törlése minden benne lévő objektumot eltávolít. Az assert: kubectl --context=kind-lab-cluster get ns lab-d195 NotFound állapotot ad vissza.

39.5.4 Tipikus hibák és ellenpróbák

Az alábbi hibák mindegyikénél a diagnosztikai eljárás: tünet azonosítása kubectl get pods / describe / events alapján, hipotézis felállítása, adatgyűjtés, egyetlen változtatás a manifestben, majd verifikáció. Nem globálisan kikapcsolunk, hanem rétegenként szűkítünk.

Tünet Hipotézis Adatgyűjtés Javítás
ImagePullBackOff A digest hibás, a registry nem elérhető, vagy auth hiányzik kubectl describe pod lab-app – Events: Failed to pull image; kubectl logs üres A manifestben a helyes digest, imagePullSecret hozzáadása vagy registry reachability javítása
CrashLoopBackOff A C++ process nem nulla exit kóddal lép ki kubectl get pods – CrashLoopBackOff; kubectl logs pod/lab-app – hibaüzenet; describe – Last State: Terminated, exit code 1 vagy 139 (SIGSEGV) A ConfigMap LISTEN_PORT ellenőrzése, a C++ kód hibájának javítása, vagy a liveness probe pathja
OOMKilled A memórialimit túl alacsony a process számára kubectl describe pod lab-app – Last State: Terminated, Reason: OOMKilled, Exit Code: 137 A resources.limits.memory növelése a tényleges RSS mérése alapján
Ready=False – Probe failed A readiness HTTP probe 400/500-at kap vagy timeout kubectl describe pod lab-app – Events: Warning: Unhealthy Readiness probe failed: HTTP probe failed with statuscode: 500; kubectl logs – a /readyz hibát jelez A readiness path javítása a manifestben, vagy az alkalmazás readiness logikájának helyes implementálása

Az ellenpróba (counterexample) lényege: ha kubectl get pods Running-ot mutat, az nem jelenti azt, hogy a Service ténylegesen elérhető. A Ready oszlopnak 1/1-nek kell lennie, és a Service EndpointSlice listája alapján a Pod IP-je a rendeltetési helyen szerepel. A diagnózis során mindig a legalacsonyabb rétegből indulunk: image pull, konténer start, konfiguráció, erőforrás, majd probe. Egyetlen változtatás után ismételten futtatjuk a verifikációs parancsot.

39.5.5 Feladatok

  1. Magyarázó feladat: Ismertesse, miért használunk image digestet a tag helyett a Pod manifestben, és milyen szerepe van a namespace-nek a Service selector működésében. Térjen ki a desired és observed state közötti különbségre.

  2. Adminisztrációs/konfigurációs feladat: Hozzon létre egy új lab-d195-ex namespace-t, benne egy lab-app-ex Podot (a fenti Pod manifest mintájára, de a tag helyett a labor registryből meghatározott points digesttel) és egy lab-app-svc-ex ClusterIP Service-t. Ellenőrizze a Service belső elérhetőségét kubectl run --rm debug poddal és a Service EndpointSlice objektumával. Postcondition: a Pod 1/1 Running, a debug curl 200 OK választ ad, a namespace törlése sikeres.

  3. Diagnosztikai/failure feladat: Szándékosan hibás image digesttel hozzon létre egy lab-broken-pull Podot a lab-d195 namespace-ben. Figyelje meg az ImagePullBackOff állapotot a kubectl get pods és describe kimenetében, majd javítsa a manifestet a helyes digestre. Ezt követően állítsa a readiness probe path-jét nem létező /readyz-broken értékre, alkalmazza, és diagnosztizálja a Ready=False állapotot. Végül állítsa vissza az eredeti manifestet. Írja le, milyen szerepe van a kubectl get events parancsnak a hiba lokalizálásában.

39.5.6 Megoldások

  1. Megoldás: Az image digest tartalomcímezett, a manifest által hivatkozott artifact revision immutabilis; a tag ugyanazon névvel később más image-re mutathat, ami driftet okoz a cluster és a release között. A namespace név- és hálózati erőforrás-elkülönítést ad; a Service selector csak a saját namespace-beli Podokat választja ki, így a lab-d195 és a lab-d195-ex nevek nem ütköznek. A desired state a manifestben írt szándék, az observed state a control plane által mért tényleges állapot; a reconciliation a kettő eltérését folyamatosan csökkenti.

  2. Megoldás: A namespace létrehozása a fenti namespace.yaml mintájára, a Pod és Service alkalmazása. A debug pod:

    kubectl --context=kind-lab-cluster --namespace=lab-d195-ex run lab-debug-ex --rm -it --image=curl/curl:latest -- sh -c 'curl -fsS http://lab-app-svc-ex:8080/healthz'

    Az EndpointSlice ellenőrzése:

    kubectl --context=kind-lab-cluster --namespace=lab-d195-ex get endpointslice -o wide

    Postcondition: a Pod IP-je az EndpointSlice-ban szerepel, a curl 200-at ad, a Pod Ready=True. A cleanup: kubectl delete namespace lab-d195-ex --wait.

  3. Megoldás: A hibás digest manifest alkalmazása után:

    kubectl --context=kind-lab-cluster --namespace=lab-d195 get pods
kubectl --context=kind-lab-cluster --namespace=lab-d195 describe pod lab-broken-pull | grep -A5 Events

    A describe Events Failed to pull image üzenetet mutat. A javítás a manifest image mezőjének helyes digestre cserélése és kubectl apply. A readiness probe törése után a Pod Running de Ready=False, a describe Unhealthy Readiness probe failed eseményt ad. A kubectl get events --sort-by=.lastTimestamp a control plane eseményeit időrendben jeleníti meg, ami a pull, start, probe hibák lokalizálásánál az elsődleges diagnosztikai eszköz. Postcondition: a Pod 1/1 Running, a Service forgalma a Podra irányul, a namespace tisztán törölt.

39.5.7 Rövid összefoglaló

A Kubernetesben a C++ image release-ből API objektumokkal lesz futó szolgáltatás. A Pod a konténert futtatja, a Service stabil hálózati végpontot ad, a ConfigMap a környezeti paramétereket választja le. Az image digest pontos, immutable artifact azonosító, a namespace az erőforrások elkülönítésére szolgál. A diagnosztika alapja a kubectl get, describe, logs és events hármas: a tünetet a Pod státusza, a részletek és a control plane események együtt azonosítják. A hibák – ImagePullBackOff, CrashLoopBackOff, OOMKilled, probe failure – rétegenkénti egyváltozós javítást igényelnek. A laborban a Kind cluster a reprodukálható baseline, de verzióját ellenőrizni kell. Továbbhasznált definíciók: Pod (legkisebb ütemezhető egység közös network namespace-szel), Service (stabil hálózati végpont label selectorral), reconciliation (desired és observed state kiegyenlítése).
