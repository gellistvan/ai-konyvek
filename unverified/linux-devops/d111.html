23.1 Inventory, source of truth és drift

23.1.1 Az inventory, a source of truth és a drift fogalma

Az üzemeltetett hostok akkor biztonságosak, ha egy adott időpontban meg tudjuk mondani, milyen állapotban kell lenniük, mi a tényleges állapotuk, és mi az, amit korábban rögzítettünk. Ezt a fegyelmet magyarul inventory (leltár) és source of truth (igazságforrás, SoT) néven szokás összefoglalni. A C++ fejlesztői gyakorlatból ismert build identity és reproducible artifact gondolat közvetlenül alkalmazható: a host állapota ugyanúgy verziózott termék, mint egy release binary, csak itt a kernel, a csomagok, a konfigurációs fájlok és a firmware a „build output”.

A három állapot pontos elkülönítése:

  • Desired state (kívánt állapot): a verziózott SoT-ban leírt, szándékolt állapot. Például egy YAML fájl, amely előírja, hogy a labhost01 milyen kernel-sorozaton, milyen csomaglistán és milyen sshd_config-hash-en legyen.
  • Observed state (megfigyelt állapot): az adott hoston egy friss, parancsokkal begyűjtött állapot. Ez a pillanatnyi valóság, nem feltétlenül egyezik a desired vagy recorded állapottal.
  • Recorded state (rögzített állapot): egy korábbi megfigyelés vagy audit, amelyet dokumentáltunk és verzióztunk. Például a d060 golden host baseline report: „ekkor ilyen volt a host”.

A drift (eltérés) az a jelenség, amikor az observed state nem egyezik a desired state-tel, és az eltérést nem fedi le nyitott, jóváhagyott exception. A driftet nem csak észlelni kell, hanem ownership (felelősség) és remediation policy (javítási szabály) szerint kezelni. Az exception policy azt mondja meg, mikor elfogadható átmeneti drift, ki hagyja jóvá, mikor jár le, és milyen kompenzáló kontroll vonatkozik rá.

23.1.2 Rétegek: mit gyűjtsünk, és honnan tudjuk a kívánt állapotot?

Egy host inventory nem csupán gépnév és IP-cím. A működtetési döntéshez az alábbi adatokat kell legalább rögzíteni:

  • Host identity: hostname, OS release, kernel release, boot time, machine-id.
  • Owner/environment/failure domain: ki a szolgáltatás gazdája, milyen környezetben fut (lab, staging, production), melyik rackben, node-on, rack switch-en van. A failure domain kifejezés azt írja le, milyen közös hardveres, hálózati vagy tápellátási parent-en osztozik a host más hostokkal. Ha két production host ugyanabban a rackben vagy ugyanazon a switch-en van, egy rack táp-/switchhiba közös kiesést okozhat.
  • Package state: telepített csomagok és verziók. Egy csomagfrissítés security fixet és viselkedésváltozást is hozhat.
  • Config state: konfigurációs fájlok tartalma, tulajdonosa, módja, hash-e. A hash jó arra, hogy determinisztikusan detektáljunk változást.
  • Firmware state: BIOS/UEFI, BMC, NIC firmware. Ez gyakran kimarad, de security baseline-nál fontos.
  • Service state: systemd unitok desired/enabled/failed állapota, mert a hoszton futó szolgáltatások a hoszt használhatóságát jelentik.
  • Runtime tuning: sysctl, cgroup, limit, scheduler beállítások, ha azok a baseline részei.

A desired állapot forrása több helyen élhet: egy Git repository, egy CMDB (configuration management database) vagy egy IaC definíció. A gyakorlatban a Git repository a leghasznosabb, mert minden változás commit-ként verzió­zott, diffelhető, és auditálható. A dynamic discovery ezzel szemben a hostokat folyamatosan vagy ütemezetten lekérdezve frissíti az observed állapotot. A kettő nem helyettesíti egymást: a discovery nélküli SoT elavul, a SoT nélküli discovery pedig egy megfigyeléshalmaz, amelyből nem tudjuk, mi a szándékolt cél.

A d060 baseline, mint recorded state, jó kiindulópont, de nem maga a SoT. A SoT-nak dizájnból kell előállnia: ha egy hostot újraépítenek, a SoT-ból kell tudni rekonstruálni a kívánt hostot.

23.1.3 Kidolgozott példa: labhost01 inventory és drift detektálás

A példa labtargetje labhost01, a lab host account labops (UID 1000). A host egy Ubuntu Server 24.04 LTS lab VM. A SoT repository-t lab-inventory néven hozzuk létre. A cél, hogy a csomagok és a kritikus konfiguráció driftjét automatikusan lehessen detektálni.

23.1.3.1 1. Inventory collection script

A script a host tényleges állapotát egy munkakönyvtárba gyűjti. A firmware-olvasás VM-en korlátozott lehet, ezért a hiba kezelése explicit.

#!/usr/bin/env bash
# Target: labhost01
# Account: labops (UID 1000)
# Privilege: a legtöbb adat nem igényel root-ot; a firmware olvasás
#             hypervisor expozíciótól függ, ezért sudo szükséges lehet.
# Precondition: /tmp/lab-inventory/collected könyvtár létrehozható.
# Rollback: nincs, mert csak olvas.
set -euo pipefail

COLLECT_ROOT="${1:-/tmp/lab-inventory/collected}"
HOSTNAME="$(hostnamectl status --static)"
OUT="$COLLECT_ROOT/$HOSTNAME"
mkdir -p "$OUT"

hostnamectl status --static > "$OUT/hostname.txt"
uname -r > "$OUT/kernel.txt"
grep '^VERSION_ID=' /etc/os-release | cut -d= -f2 | tr -d '"' > "$OUT/os_version.txt"
dpkg-query -W -f='${binary:Package}\t${Version}\n' | sort > "$OUT/packages.tsv"
sha256sum /etc/ssh/sshd_config > "$OUT/config_digest.txt"
systemctl --state=failed --plain --no-legend > "$OUT/failed_units.txt"

if cat /sys/class/dmi/id/bios_version > "$OUT/firmware_version.txt" 2>/dev/null; then
  :
else
  echo "unavailable" > "$OUT/firmware_version.txt"
fi

Futtatás:

./lab-inventory-collect.sh

Várt kimenet: nincs stdout; a $OUT alatt létrejött hostname.txt, kernel.txt, os_version.txt, packages.tsv, config_digest.txt, failed_units.txt, firmware_version.txt.

23.1.3.2 2. Source of truth repository

A kívánt állapotot Gitben verziózzuk. A YAML nem a package-verziók teljes listáját tartalmazza, hanem a package-list fájlra hivatkozik, ami a d060 baseline verziójából származik. Így a csomag-kívánt állapot nem a YAML-on belül duplikált, hanem egyetlen hivatkozott fájl.

# lab-inventory/hosts/labhost01.yaml
hostname: labhost01
owner: platform-team
environment: lab
failure_domain:
  node: lab-vm
  rack: lab-rack-A
  shared_switch: lab-switch-1
kernel_series: 6.8
package_list: package-lists/labhost01.packages.tsv
config_files:
  - path: /etc/ssh/sshd_config
    sha256: <a_d060_baseline_bol_rogzitett_hash>
    source: configs/labhost01/etc/ssh/sshd_config

A <a_d060_baseline_bol_rogzitett_hash> helyére a tényleges laborban a d060 sha256sum kimenetének értéke kerül. A package-lists/labhost01.packages.tsv a baseline-ból származó, verziózott csomaglista.

23.1.3.3 3. Drift detektálás

A detektálás az observed és a desired közti diff:

diff -u \
  lab-inventory/package-lists/labhost01.packages.tsv \
  /tmp/lab-inventory/collected/labhost01/packages.tsv

Várt kimenet, ha nincs drift: nincs kimenet, exit status 0. Ha a hoston egy openssh-server frissült, a diff a következőhöz hasonló:

--- lab-inventory/package-lists/labhost01.packages.tsv
+++ /tmp/lab-inventory/collected/labhost01/packages.tsv
@@ -12,7 +12,7 @@
-openssh-server   1:9.6p1-3ubuntu13~24.04.1
+openssh-server   1:9.6p1-3ubuntu13~24.04.2

Ez drift. A feladat nem az, hogy azonnal automatikusan visszaállítsuk a csomagot, hanem hogy döntsünk: lehetséges, hogy ez egy jóváhagyott security frissítés. Ha igen, a SoT package-list fájlt frissíteni kell, vagy exception kell. Ha nem jóváhagyott, a csomag visszaállítható a apt install openssh-server=<baseline-verzió> paranccsal, de előtte az okot kell megérteni.

23.1.4 Hibák és ellenpróbák

A leggyakoribb hiba, hogy a drift detektálást false positive-ként kezeljük, és kikapcsoljuk az ellenőrzést. Ehelyett minden drifthez a következő ciklus tartozik:

  1. Tünet: diff van a package-list vagy config hash között.
  2. Hipotézis: kézi változtatás, automatizált frissítés, rossz baseline, vagy illetéktelen beavatkozás.
  3. Adatgyűjtés: meg kell nézni a systemd journalban, apt historyban, shell historyban, és a SoT git log-ban, hogy van-e megfelelő változtatási rekord.
  4. Egy változtatás: vagy a SoT-t kell commitolni a tényleges, jóváhagyott állapothoz, vagy a hoston kell visszaállítani a kívánt állapotot. Minden más beavatkozás egyszerre két változóval rontja a diagnózist.
  5. Verification: újra futtatni a gyűjtőt és a diffet, majd a change logban rögzíteni a postcondition-t.

Gyakori hiba az is, hogy a manuális változtatást nem írják vissza a SoT-ba. Például valaki SSH-val belép, módosítja az /etc/systemd/system/lab-service.service unitot, és működik is. A következő drift detection ugyan jelez, de az okot nem a host hibás állapotában, hanem a hiányzó SoT commitban kell keresni. Ezt a folyamatot a reproducibility (újraépíthetőség) védi: ha a SoT-ból egy tiszta host reprodukálható, a kézi módosítás nem maradhat az egyetlen forrás.

A CMDB akkor hasznos, ha az owner, environment és failure domain adatok egy helyen élnek, és a discovery frissíti őket. Ha a CMDB csak statikus, és a hostok átkerülnek egy másik rackbe, a drift észlelés nem fog segíteni, mert a CMDB nem az observed állapotot hasonlítja. A dynamic discovery ezt a hiányt csökkenti: a racket, switchet vagy VM hostot a hypervisor/DCIM API-ból is be lehet gyűjteni.

A change log és retention szempontjából a Git history a legjobb minimális megoldás. Minden SoT változáshoz kötelező commit message, amely tartalmazza a host nevet, a változás okát és a linket az exception ticketre. Példa:

labhost01: package-list frissítés openssh-server 9.6p1-3ubuntu13~24.04.2
Security update, change window: 2025-XX-XX 22:00 UTC
Owned by: platform-team
Exception: EX-1234

A retention policy a bizonyítási követelménytől függ: a labban minimum addig kell tartani a drift riportokat és change logot, amíg a lab auditja tart. Productionban ez általában az adott compliance policy által meghatározott idő.

23.1.5 Feladatok

23.1.5.1 Feladat 1 (magyarázó)

Az alábbi adatokat gyűjtötted labhost02-ről:

  • desired kernel series: 6.8
  • recorded baseline (d060): kernel=6.8.0-50-generic
  • observed: kernel=6.8.0-52-generic
  • a change logban nincs bejegyzés a kernel frissítéséről.

Melyik állapot melyik? Van-e drift? Indokold, és mondd meg, mi lenne a helyes első lépés.

23.1.5.2 Feladat 2 (adminisztrációs/konfigurációs)

Hozd létre a lab-inventory repository-t a labhost01 hostra. Készítsd el a SoT YAML-t, és a d060 baseline-ból töltsd ki a package-lists/labhost01.packages.tsv és a sshd_config hash mezőt. Futtasd a gyűjtő scriptet, majd generálj drift riportot. A megoldásban add meg a parancsokat, targetet, privilege-t és a várt postcondition-t.

23.1.5.3 Feladat 3 (diagnosztikai/failure recovery)

A labhost03 drift riportja a következőket mutatja: az /etc/ssh/sshd_config digest eltér a SoT-tól, és a /etc/sudoers.d/labops fájl hiányzik. A journalban egy root által végrehajtott usermod és egy vim /etc/ssh/sshd_config bejegyzés látható, de nincs change log. Diagnosztizáld a driftet, állítsd vissza a kívánt állapotot a SoT-ból, készítsd el a change log bejegyzést, és ellenőrizd, nincs-e további drift.

23.1.6 Megoldások

23.1.6.1 Megoldás 1

A kernel_series=6.8 része a desired state, a kernel=6.8.0-50-generic a recorded baseline, a 6.8.0-52-generic az observed state. A desired és observed eltérés a konkrét kernel-verzióban van, tehát drift. Az első lépés nem a visszaállítás, hanem az ok tisztázása: a change logban nincs nyom. Ellenőrizni kell az apt history-t (grep "linux-image" /var/log/dpkg.log), a journalt és a reboot időt. Ha biztonsági frissítés, akkor a SoT kernel desired state-jét frissíteni kell. Ha illetéktelen, akkor a hostot kell rollbackelni. Postcondition: a drift ok vagy exception-tel, vagy SoT commit-tal lezárt.

23.1.6.2 Megoldás 2

Létrehozás:

# Target: labhost01, account: labops, privilege: sudo a git remote push-hoz
mkdir -p lab-inventory/{hosts,package-lists,configs/labhost01/etc/ssh,detection}
cd lab-inventory
git init
# Másold be a d060 package-list fájlt:
cp /tmp/baseline/labhost01.packages.tsv package-lists/labhost01.packages.tsv
# Készítsd el a hosts/labhost01.yaml-t a fenti minta alapján, és a configs
# fájlt a SoT-ba.
git add .
git commit -m "Initial SoT for labhost01 from d060 baseline"

Futtatás:

./lab-inventory-collect.sh
diff -u lab-inventory/package-lists/labhost01.packages.tsv \
     /tmp/lab-inventory/collected/labhost01/packages.tsv > detection/drift-$(date +%F).txt

Várt postcondition: a detection/drift-$(date +%F).txt üres, ha nincs drift; a git status tiszta; a SoT commit létrejött. Ha a diff nem üres, a driftet a 3. pont hibakezelése szerint kell osztályozni.

23.1.6.3 Megoldás 3

A drift eltűnt sudoers.d/labops fájl és a megváltozott sshd_config kézi beavatkozásra utal. A javítás sorrendje:

  1. Hipotézis: egy admin kézzel módosított a hoston, de nem vezette vissza a SoT-ba; a labops user eltávolítása/hiánya egyben hozzáférési kockázat.
  2. Adatgyűjtés: journalctl -u ssh.service, grep -r labops /var/log/, id labops ellenőrzése.
  3. Visszaállítás: a SoT-ból a configs/labhost03/etc/ssh/sshd_config másolása, a hash ellenőrzése, a sudoers.d/labops fájl rekonstruálása a SoT-ban tárolt artifactból. Példa:
# Target: labhost03, account: labops, privilege: sudo
sudo cp lab-inventory/configs/labhost03/etc/ssh/sshd_config /etc/ssh/sshd_config
sudo chown root:root /etc/ssh/sshd_config
sudo chmod 644 /etc/ssh/sshd_config
sha256sum /etc/ssh/sshd_config
sudo ls -l /etc/sudoers.d/labops
  1. Change log: a SoT git commitban rögzíteni a recovery tényt:
labhost03: restore sshd_config and sudoers.d/labops from SoT
Root cause: unlogged manual change; no change ticket.
Owner: platform-team
Postcondition: drift detection clean, access restored.
  1. Verification: a gyűjtő script és a diff újrafuttatása; a systemctl restart ssh után egy SSH smoke test a lab konzolból, hogy a távoli hozzáférés ne korlátozódjon. Postcondition: a drift riport üres, a labops user hozzáférése működik, a change log bejegyzés létezik.

23.1.7 Rövid összefoglaló

A hoszt inventory a kívánt, megfigyelt és rögzített állapot pontos elkülönítésén alapul. A source of truth verziózott repository, amelyből a host állapota reprodukálható; a dynamic discovery csak az observed állapotot frissíti. A drift a kívánt és megfigyelt eltérés, amelyet nem fed le jóváhagyott exception. A javítás mindig egy változós: vagy a SoT-t frissítjük, vagy a hostot állítjuk vissza. A change log Git historyként, owner, environment és failure domain adatokkal ad auditálható nyomot. Továbbhasznált definíciók: desired state, observed state, drift.
