35.5 VM provision és recovery zárólabor

35.5.1 Motiváció

A VM-provision és recovery zárólabor célja, hogy egyetlen, reprodukálható forrásból újraépítsünk egy működő virtuális gépet, és egy host failure szimulációja után bizonyítsuk a helyreállítás képességét. Szenior fejlesztőként a resource lifetime fogalma ismerős: a VM is egy erőforrás, amelynek létrehozását, állapotát, failure domainjét és felszabadítását explicit szerződéssel kell kezelni. A laborban nem programozási, hanem üzemeltetési döntéseket hozunk: image, hálózat, storage, backup és restore sorrendje mind a VM életciklusát határozza meg.

35.5.2 Definíciók

  • Source profile: a VM létrehozásához szükséges összes, versioned input: golden image referencia (URI és checksum), cloud-init sablonok, domain XML spec, hálózati és storage paraméterek, valamint a backup repository azonosítója. Ez a desired state forrása.
  • Recovery manifest: gépi ellenőrzésre alkalmas YAML, amely a désiré state-et postconditionökkel írja le, és a restore lépések függőségeit, ellenőrzéseit rögzíti.
  • Smoke check: minimális, de a kritikus útvonalat lefedő ellenőrzés: boot, hálózat, DNS, SSH, felhasználó és szolgáltatás állapota.
  • Artifact provenance: minden artifactra (image, seed ISO, domain XML, backup snapshot) rögzített verzió, checksum vagy commit, amely a létrehozás inputját egyértelműen azonosítja.

35.5.3 Rétegek és működési elv

A VM-provision három rétegen halad át:

  1. Host réteg: libvirt storage pool, network bridge, golden image könyvtár, backup hozzáférhetőség.
  2. VM spec réteg: domain XML, cloud-init seed ISO, disk volume (thin-provisioned backing file), hálózati csatolás.
  3. Guest réteg: felhasználói identitás, csomagok, szolgáltatások, alkalmazásadatok, backup kliens.

A recovery azért több, mint a domain újradefiniálása, mert a guest belső állapotát is vissza kell állítani. A munkafolyamat:

source profile (git commit)
  -> golden image ellenőrzés (checksum)
  -> cloud-init seed ISO build
  -> qcow2 disk volume létrehozás backing file-ból
  -> libvirt domain define + start
  -> cloud-init smoke check
  -> backup restore (ha van adat)
  -> postcondition check
  -> artifact provenance rögzítés

A desired state a profilban van; a tényleges observed state a virsh, ssh és guest parancsokból. A recovery rehearsal során a kettőt összehasonlítjuk.

A provision parancsok a labhost0-n, labadmin felhasználóval, sudo-val:

# 0. Előfeltétel ellenőrzés
virsh -c qemu:///system pool-info lab-vms
virsh -c qemu:///system net-info lab-net0
ip link show lab-net0

# 1. Golden image checksum ellenőrzés
sha256sum /var/lib/libvirt/images/base/ubuntu-24.04-minimal-cloudimg-amd64.img

# 2. Cloud-init seed ISO build
cloud-localds /var/lib/libvirt/images/base/labvm0-seed.img \
  user-data.yaml network-config.yaml metadata.yaml

# 3. Thin-provisioned disk volume létrehozás backing file-ból
qemu-img create \
  -f qcow2 \
  -F qcow2 \
  -o backing_file=/var/lib/libvirt/images/base/ubuntu-24.04-minimal-cloudimg-amd64.img,backing_fmt=qcow2 \
  /var/lib/libvirt/images/lab-vms/labvm0.qcow2 10G

# 4. Domain XML definiálás és indítás
virsh -c qemu:///system define labvm0-domain.xml
virsh -c qemu:///system start labvm0

# 5. IP lekérdezés DHCP bérletből
virsh -c qemu:///system net-dhcp-leases lab-net0 | grep labvm0

A domain XML (labvm0-domain.xml):

<domain type='kvm'>
  <name>labvm0</name>
  <memory unit='MiB'>2048</memory>
  <vcpu>2</vcpu>
  <os>
    <type arch='x86_64' machine='q35'>hvm</type>
    <boot dev='hd'/>
  </os>
  <devices>
    <disk type='file' device='disk'>

    </disk>
    <disk type='file' device='cdrom'>
      <source file='/var/lib/libvirt/images/base/labvm0-seed.img'/>
      <target dev='sdb' bus='sata'/>
      <readonly/>
    </disk>
    <interface type='bridge'>
      <source bridge='lab-net0'/>
      <mac address='52:54:00:12:34:01'/>
      <model type='virtio'/>
    </interface>
    <serial type='pty'/>
    <console type='pty'/>

</domain>

A smoke check:

# DNS
dig +short labvm0.lab.internal @10.13.0.1

# SSH + user + service ellenőrzés
ssh -o BatchMode=yes labadmin@labvm0.lab.internal \
  'id; hostname --fqdn; systemctl is-active qemu-guest-agent; df -h /; cat /etc/cloud/build.info'

Várható kimenet:

10.13.0.10
uid=1000(labadmin) gid=1000(labadmin) groups=1000(labadmin),4(adm),27(sudo)
labvm0.lab.internal
active

Disk expansion:

# Host oldal
virsh -c qemu:///system shutdown labvm0
virsh -c qemu:///system undefine labvm0 --nvram
qemu-img resize /var/lib/libvirt/images/lab-vms/labvm0.qcow2 20G
virsh -c qemu:///system define labvm0-domain.xml
virsh -c qemu:///system start labvm0

# Guest oldal
ssh labadmin@labvm0 'sudo growpart /dev/vda 1 && sudo resize2fs /dev/vda1 && df -h /'

Várható: a root filesystem 10G-ről 20G-ra nő, a cloud-init nem fut ismét, a korábbi adatok megmaradnak.

Restore rehearsal és host failure fixture:

# Adatkészlet a VM-en
ssh labadmin@labvm0 'sudo sh -c "echo dbdata > /srv/labdata/db.txt; date > /srv/labdata/created_at"'

# Backup a VM-ről a host restic repojába
ssh labadmin@labvm0 'sudo restic -r sftp:labbackup@10.13.0.1:restic/labvm0 \
  --password-file /etc/lab-backup-pass backup /srv/labdata'

# Host failure szimuláció: domain és disk törlése
virsh -c qemu:///system destroy labvm0 2>/dev/null || true
virsh -c qemu:///system undefine labvm0 --remove-all-storage --nvram

# Újraépítés a profilból (a fenti provision lépések ismétlése)

# Restore a guestre
ssh labadmin@labvm0 'sudo mkdir -p /srv/labdata && sudo restic \
  -r sftp:labbackup@10.13.0.1:restic/labvm0 \
  --password-file /etc/lab-backup-pass restore latest --target / && \
  cat /srv/labdata/db.txt'

A --remove-all-storage törli a labvm0 qcow2 diskjét is, így a recovery tiszta inputból és backupból történik. A golden image backing file megmarad, a restic repo a hoston van.

Guest+host diagnosztikai report:

#!/usr/bin/env bash
set -euo pipefail
REPORT_DIR="/var/tmp/lab-reports/d175-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$REPORT_DIR"
virsh -c qemu:///system dumpxml labvm0 > "$REPORT_DIR/domain.xml"
qemu-img info /var/lib/libvirt/images/lab-vms/labvm0.qcow2 > "$REPORT_DIR/disk-info.txt"
virsh -c qemu:///system domiflist labvm0 > "$REPORT_DIR/iflist.txt"
ssh labadmin@labvm0 'ip addr; ip route; systemctl --failed --no-pager' > "$REPORT_DIR/guest-network-and-failed.txt"
sha256sum "$REPORT_DIR"/* > "$REPORT_DIR/SHA256SUMS"
echo "$REPORT_DIR"

A report a source profile commit hash-ével és a restic snapshot ID-val együtt artifact provenance-t ad. A cleanup csak a lab objektumait törli:

virsh -c qemu:///system destroy labvm0 2>/dev/null || true
virsh -c qemu:///system undefine labvm0 --remove-all-storage --nvram
rm -f /var/lib/libvirt/images/base/labvm0-seed.img
rm -rf /var/tmp/lab-reports/d175-*  # csak a saját report

35.5.5 Hibák és ellenpróbák

Tünet Hipotézis Adatgyűjtés Egy változtatás Ellenőrzés
A VM nem kap IP-címet A seed ISO hiányos, vagy a bridge nem engedi a DHCP-t virsh net-dhcp-leases lab-net0, virsh console labvm0, guest journalctl -u cloud-init A seed ISO újragenerálása network-config-tal, a domain újraindítása ip addr show enp1s0 a guestben mutat IP-t
A cloud-init nem futtatja a usert A meta-data instance-id hiányzik cat /var/lib/cloud/instance/instance-id, cloud-init status --wait metadata.yaml-ben instance-id hozzáadása, seed ISO újraépítés id labadmin a guestben sikeres
Disk resize után a filesystem kicsi marad A partition tábla nem nőtt, a resize2fs a partícióra nem vonatkozik lsblk, df -h, parted /dev/vda print growpart /dev/vda 1, majd resize2fs /dev/vda1 df -h / a guestben 20G
Restore után a db.txt hiányzik A restic repo path vagy password rossz, a snapshot nem tartalmazza az adatot restic snapshots --group-by host, restic ls latest /srv/labdata A repo path javítása a profilban, backup ismétlése cat /srv/labdata/db.txt
SSH key nem enged be A cloud-init user config nem került a seedbe, vagy a key formátuma rossz ssh -vvv labadmin@..., guest cloud-init status --long A user-data ssh_authorized_keys javítása, seed újragenerálás ssh -o BatchMode=yes sikeres
A domain define hibát ad: file not found A disk pool path vagy a seed ISO elérési útja rossz ls -l /var/lib/libvirt/images/..., virsh pool-list --all Az XML-ben a teljes elérési út javítása a pool-ön belül virsh define sikeres

Gyakori hiba, hogy a --remove-all-storage a thin-provisioned backing file-t is törli, mert a golden image a pool volume-listájában van. Ezt úgy kerüljük ki, hogy a golden image a base könyvtárban él, a pool-ban csak a volume-ok.

35.5.6 Feladatok

35.5.6.1 1. feladat: Source profile és recovery manifest összeállítása

Készíts saját ~/lab-profiles/d175-profile.yaml-t a fenti minta alapján, és írj hozzá egy recovery-manifest.yaml-t, amely a desired state-et (VM, hálózat, DNS, backup) és a postconditionöket tartalmazza. Magyarázd el, miért kell különválasztani a golden image-et a thin-provisioned disk volume-tól.

35.5.6.2 2. feladat: Újraépítés és disk expansion

A labhost0-n építsd újra a labvm0-at a profilból, futtasd le a smoke checket, bővítsd a disket 20G-ra, és ellenőrizd a filesystem méretét. Rögzítsd a parancsokat és a kimeneteket.

35.5.6.3 3. feladat: Failure fixture, report és cleanup

Indítsd a VM-et, hozz létre adatot a /srv/labdata alatt, készíts restic backupot, majd szimulálj host failure-t a domain és a disk törlésével. A profilból és a backupból állítsd helyre a VM-et, futtasd a diagnosztikai report scriptet, ellenőrizd az adatot, majd töröld a lab objektumokat.

35.5.7 Megoldások

35.5.7.1 1. feladat megoldása

A profil a teljes specifikáció, a manifest a recovery gép által feldolgozható ellenőrzéseit tartalmazza. Példa manifest:

postconditions:
  - name: "domain-defined"
    command: "virsh -c qemu:///system list --all | grep -q labvm0"
  - name: "vm-ssh"
    command: "ssh -o BatchMode=yes -o ConnectTimeout=5 labadmin@labvm0.lab.internal 'exit 0'"
  - name: "dns"
    command: "dig +short labvm0.lab.internal @10.13.0.1 | grep -q '^10\\.13\\.0\\.10$'"
  - name: "data-file"
    command: "ssh labadmin@labvm0 'cat /srv/labdata/db.txt' | grep -q dbdata"

A golden image és a disk volume szétválasztása azért fontos, mert a recovery során a disk volume törölhető, de a golden image-nek változatlannak kell maradnia. A thin-provisioned backing file nem másolja az image tartalmát, csak hivatkozik rá. Ha a golden image a pool-ban élne, a --remove-all-storage tévedésből megsemmisíthetné.

35.5.7.2 2. feladat megoldása

A parancsok a kidolgozott példában szerepelnek. A postcondition: virsh list --all mutatja a labvm0-t, df -h / a guestben 20G, dig +short labvm0.lab.internal @10.13.0.1 10.13.0.10, az SSH smoke sikeres.

35.5.7.3 3. feladat megoldása

Az adat és backup a restore rehearsal parancsokkal. A failure után a recovery: a profilból új domain és disk, majd a guestre restic restore. A report scriptet futtatva a guest-network-and-failed.txt üres (nincs failed unit), és a db.txt tartalma dbdata. A cleanup után virsh list --all nem tartalmazza a labvm0-t, a disk fájl és a seed ISO nem létezik.

35.5.8 Rövid összefoglaló

A VM provision és recovery zárólabor a source profile-ból indított reprodukálható építést és a backupból való helyreállítást gyakorolja. A golden image és a thin-provisioned disk szétválasztása lehetővé teszi a teljes recoveryt a domain és a disk elvesztése után is. A cloud-init seed ISO a felhasználói, hálózati és identitás konfigurációt szállítja, a smoke check pedig a DNS, SSH és szolgáltatás állapotot ellenőrzi. A diagnosztikai report és az artifact provenance bizonyítja, hogy a desired state a manifest szerint teljesült. A cleanup csak a lab-prefixű objektumokat törli, a baseline image és a backup repo megmarad.

Továbbhasznált definíciók:
- Source profile: a VM létrehozásához és működtetéséhez szükséges versioned inputok együttese.
- Recovery manifest: a desired state postconditionöket és a restore lépéseket gépi ellenőrzésre leíró specifikáció.
- Smoke check: minimális, kritikus útvonalat lefedő ellenőrzés.
