55.4 Incidensek: DNS/TLS/FD/OOM/disk/network

55.4.1 Motiváció

Egy üzemeltetett Linux szolgáltatásnál a felhasználó által látott hiba ritkán közvetlenül a gyökérok. A „nem tölt be az oldal” mögött DNS, TLS-lánc, route, reverse proxy, backend, elfogyott FD, OOM, telített disk vagy párhuzamosan futó háttérterhelés is állhat. Ebben a záróprojekt-incidensgyakorlatban ezért nem egyetlen hibát javítunk, hanem kontrollált, névvel azonosított labhibákkal gyakoroljuk a hipotézisvezérelt recoveryt. A cél az, hogy a szenior C++ fejlesztő a Linux stacket ugyanúgy diagnosztizálja, mint egy natív release artifact hibáját: tünet, bizonyíték, egy változtatás, verification.

A korábbi d160 hálózati incidensmódszertan és d110 teljes Linux bottleneck diagnosztika itt egy szolgáltatásszintű gyakorlatban fut össze. Ami ott egy rétegen belül tanult, az itt több függőségi és erőforrásrétegen keresztül jelenik meg.

55.4.2 Definíció és működés

Incidens (incident): egy szolgáltatás tervezett állapotától (desired state) való, felhasználót érintő eltérés. A lab gyakorlatban fault injection segítségével szándékosan hozunk létre incidenst. A fixture itt a hibás állapot pontos leírása: melyik gépen, melyik fájlban, melyik parancs hajtotta végre, és mi a várt tünet.

A recovery műveleteket meg kell különböztetni:

  • Mitigation: ideiglenesen csökkenti a user impactot, de a gyökérok megmaradhat. Például FD-limit emelése, ha a szolgáltatás FD leak-es.
  • Rollback: a release artifactot, konfigurációt vagy route-ot visszaállítja egy ismert jó állapotba. Nem garantálja, hogy az adatintegritás is helyreállt.
  • Restore: adatot vagy teljes fájlrendszert ellenőrzött backupból állít vissza. Csak sikeres, integritásellenőrzött restore után tekinthető igazolt recoverynek.

A diagnosztika alapja a tünet-réteg hozzárendelés. Egy tünetet nem elég látni, a réteget is azonosítani kell:

Tünet Valószínű réteg Elsődleges bizonyíték
A név rossz IP-t ad vagy timeout DNS/NSS/hosts getent ahosts, dig, /etc/hosts
TLS kézfogás hiba, „unable to get local issuer certificate” TLS-lánc, trust openssl s_client, openssl verify
TCP SYN után timeout, DNS/TLS rendben route, firewall, PMTU ip route get, ss -tn, tcpdump
accept: Too many open files FD-limit /proc/PID/limits, FD-count
Process exit 9/KILL, OOM-kill log memória/cgroup systemctl status, journalctl -k
Magas latency, magas I/O wait blokk-I/O, cgroup throttle iostat -xz, pidstat -d, /proc/pressure/io
No space left on device, töredéknyi szabad blokk inode/quota df -h, df -i, quota
HTTP 502/504 backend/proxy nginx error log, backend systemd state
Adat sérült vagy hiányzik storage/alkalmazás durabilitása checksum, backup restore

A labban minden módosítás lab- prefixszel nevesített disklab/disposable erőforráson történik. A hibainjektálás előtt mindig baseline-t rögzítünk; a recovery után ugyanazzal a smoke teszttel ellenőrzünk.

55.4.3.1 Labtopológia és baseline

A gyakorlat a d273-ban felépített stacket használja:

Objektum Cím/Interfész Szerep
lab-lb 192.0.2.10/24, 198.51.100.10/24 Nginx TLS reverse proxy
lab-app-a 198.51.100.20/24 lab-order-svc systemd service
lab-app-b 198.51.100.21/24 ugyanaz a service, második backend
lab-client 192.0.2.50/24 teszt kliens
lab-backup 198.51.100.30/24 restic repository

A dokumentációs címek az RFC 5737 tartományból valók. Az élő név lab-svc.example, amely az A rekorddal a lab-lb 192.0.2.10-es címére mutat.

Baseline ellenőrzés:

# target: lab-client, user: lab-admin, privilege: sudo
getent ahosts lab-svc.example
curl -sS -o /dev/null -w '%{http_code}\n' https://lab-svc.example/health
# várt kimenet:
# 192.0.2.10 STREAM lab-svc.example
# 200

# target: lab-lb, user: lab-admin, privilege: sudo
openssl verify -CAfile /etc/ssl/lab/lab-ca-chain.pem /etc/ssl/lab/lab-leaf.pem
ip route get 198.51.100.20
# várt kimenet:
# /etc/ssl/lab/lab-leaf.pem: OK
# 198.51.100.20 dev eth1 src 198.51.100.10

Ez a három ellenőrzés egyszerre mutatja a DNS-, TLS- és route-függőséget. Ha bármelyik eltér, a hiba már a kapcsolat felépítése előtt jelentkezik.

55.4.3.2 Hibafixture: wrong DNS, TLS chain, route

Wrong DNS: a lab-client DNS-feloldását egy hibás /etc/hosts sorral térítjük el a forgalom elől. Ez jól szimulálja a rossz DNS-rekordot, de NSS szinten könnyen visszafordítható.

# target: lab-client, user: lab-admin, privilege: sudo
echo '192.0.2.99 lab-svc.example' | sudo tee -a /etc/hosts

# tünet és bizonyíték
curl -sS -v https://lab-svc.example/health 2>&1 | grep -E 'Trying|Connected|failed'
getent ahosts lab-svc.example
# várt/illusztratív: Trying 192.0.2.99..., connection timed out
# getent: 192.0.2.99 STREAM lab-svc.example

A hipotézis: a névfeloldás rossz célt ad, nem a proxy vagy a hálózat hibás. Ellenőrzésként a getent mutatja a hibás IP-t. Rollback:

sudo sed -i '/192.0.2.99 lab-svc.example/d' /etc/hosts
getent ahosts lab-svc.example
# postcondition: ismét 192.0.2.10

TLS chain: a lab-lb Nginx chain fájljában csak a leaf certet hagyjuk meg, a köztes CA kikerül a chainből. A kliens ekkor nem tudja felépíteni a láncot.

# target: lab-lb, user: lab-admin, privilege: sudo
sudo cp /etc/ssl/lab/lab-fullchain.pem /etc/ssl/lab/lab-fullchain.pem.bak
sudo cp /etc/ssl/lab/lab-leaf.pem /etc/ssl/lab/lab-fullchain.pem
sudo nginx -t && sudo systemctl reload nginx

# target: lab-client
curl -sS -v https://lab-svc.example/health 2>&1 | grep -E 'SSL certificate problem|openssl'
# target: lab-lb
openssl s_client -connect lab-svc.example:443 -servername lab-svc.example -showcerts | sed -n '/BEGIN CERTIFICATE/,/END CERTIFICATE/p' | grep -c 'BEGIN CERTIFICATE'
# várt/illusztratív: 1, tehát csak leaf van a chainben

A tünet „SSL certificate problem: unable to get local issuer certificate”. A curl hibája önmagában félrevezethető lenne: lehetne rossz CA store vagy órahiba is. Ezért a lab-lb oldalán nézzük meg, mit ad ki a szerver. A lab-fullchain.pem-ben csak egy cert van, a lab-leaf.pem másolata. Rollback:

sudo cp /etc/ssl/lab/lab-fullchain.pem.bak /etc/ssl/lab/lab-fullchain.pem
sudo nginx -t && sudo systemctl reload nginx
curl -sS -o /dev/null -w '%{http_code}\n' https://lab-svc.example/health
# postcondition: 200

Route fixture: a kliensen a 198.51.100.0/24 hálózatra rossz gatewayt állítunk be. A DNS és a proxy sorrendben jó, a TCP SYN mégis elveszik.

# target: lab-client, user: lab-admin, privilege: sudo
sudo ip route replace 198.51.100.0/24 via 192.0.2.99 dev eth0

# bizonyíték
ip route get 198.51.100.20
# várt/illusztratív: 198.51.100.20 via 192.0.2.99 dev eth0 ... unreachable
ping -c1 192.0.2.10
ping -c1 198.51.100.20
# a proxy elérhető, a backend nem; a route-fixture a különbség

Rollback:

sudo ip route replace 198.51.100.0/24 via 192.0.2.10 dev eth0
ip route get 198.51.100.20
curl -sS -o /dev/null -w '%{http_code}\n' https://lab-svc.example/health
# postcondition: route via 192.0.2.10, HTTP 200

55.4.3.3 Erőforrás-hibák: FD leak, OOM, throttle, IO bottleneck

Az erőforrás-incidensek közös jellemzője, hogy a külső tünet későn jelentkezik, mert a deployment eleinte működik. A labban a lab-order-svc release artifactjait a lab-install-release helper telepíti. A helper a natív binaryt, a source revisiont, a build-id-t és a systemd unit verzióját együtt írja le.

FD leak: telepítjük a 0.2.0-fdleak jelű hibás release-t. Minden health-kérés után egy socket/file descriptor nyitva marad.

# target: lab-app-a, user: lab-admin, privilege: sudo
sudo lab-install-release lab-order-svc 0.2.0-fdleak
sudo systemctl restart lab-order-svc

# terhelés
for i in $(seq 1 300); do curl -sS http://127.0.0.1:18080/health >/dev/null || break; done

# miután az FD-limit közelébe ért:
PID=$(systemctl show -p MainPID --value lab-order-svc)
test "$PID" != "0" || exit 1
sudo ls "/proc/$PID/fd" | wc -l
sudo grep 'Max open files' "/proc/$PID/limits"
sudo journalctl -u lab-order-svc -n 30 --no-pager
# várt/illusztratív:
# fd count: 1019
# Max open files: 1024
# accept4: Too many open files

A hipotézis az FD-limit elérés, a bizonyíték a magas FD-count és a Max open files = 1024. A mitigation egy ideiglenes LimitNOFILE drop-in, de a gyökérok megmarad:

sudo mkdir -p /etc/systemd/system/lab-order-svc.service.d
cat <<'EOF' | sudo tee /etc/systemd/system/lab-order-svc.service.d/10-fd-mitigation.conf
[Service]
LimitNOFILE=4096
EOF
sudo systemctl daemon-reload
sudo systemctl restart lab-order-svc

A valódi recovery a jó release visszaállítása és a provizórikus drop-in eltávolítása:

sudo lab-install-release lab-order-svc 0.1.9-good
sudo rm /etc/systemd/system/lab-order-svc.service.d/10-fd-mitigation.conf
sudo systemctl daemon-reload
sudo systemctl restart lab-order-svc

# terheléses postcondition
for i in $(seq 1 300); do curl -sS http://127.0.0.1:18080/health >/dev/null || break; done
PID=$(systemctl show -p MainPID --value lab-order-svc)
sudo ls "/proc/$PID/fd" | wc -l
# postcondition: FD-count stabil, jóval 1024 alatt; a limit nem emelt

OOM: a 0.2.1-oom release memóriafogyasztása folyamatosan nő. A unitra szigorú memóriakonténert teszünk, hogy a hiba a lab virtuális adatlemezen és ne a host memóriáját feszítse.

# target: lab-app-a, user: lab-admin, privilege: sudo
cat <<'EOF' | sudo tee /etc/systemd/system/lab-order-svc.service.d/10-oom-fixture.conf
[Service]
MemoryHigh=384M
MemoryMax=512M
EOF
sudo systemctl daemon-reload
sudo lab-install-release lab-order-svc 0.2.1-oom
sudo systemctl restart lab-order-svc
# a release a MemoryHigh/MemoryMax alatt először működik, majd OOM-kill következik

Az OOM-nál a bizonyítékot a restart előtt kell rögzíteni:

sudo systemctl status lab-order-svc --no-pager
# várt/illusztratív: code=killed, status=9/KILL
sudo journalctl -u lab-order-svc -k --no-pager | grep -i -E 'oom|killed process'
systemctl show lab-order-svc -p MemoryCurrent -p MemoryPeak
# MemoryPeak közel a MemoryMax-hoz; MemoryCurrent után OOM-kill után lényegesen kisebb

A recovery a jó release visszaállítása, majd a hibás fixture drop-in eltávolítása. A MemoryGuard csak akkor marad meg, ha a d273 baseline kifejezetten előírja; itt a rollbackhez megszüntetjük.

sudo systemctl stop lab-order-svc
sudo lab-install-release lab-order-svc 0.1.9-good
sudo rm /etc/systemd/system/lab-order-svc.service.d/10-oom-fixture.conf
sudo systemctl daemon-reload
sudo systemctl restart lab-order-svc
systemctl show lab-order-svc -p SubState -p MemoryCurrent
# postcondition: active/running; MemoryCurrent tartósan a baseline alatt

Throttle/IO bottleneck: itt nem a service release hibás, hanem a rendszerkonfiguráció fogja vissza a szolgáltatást. A lab-order-svc service alá egy drop-in mesterségesen CPUQuota=10%-ot és IORreadBandwidthMax-ot adhat. A méréshez a d273-ban használt Prometheus lab_order_request_duration_seconds metrikát vagy a lokális lab_bench --quantiles eszközt használjuk.

# target: lab-app-a, user: lab-admin, privilege: sudo
cat <<'EOF' | sudo tee /etc/systemd/system/lab-order-svc.service.d/10-throttle.conf
[Service]
CPUQuota=10%
IOReadBandwidthMax=/dev/vdb 2M
EOF
sudo systemctl daemon-reload
sudo systemctl restart lab-order-svc

# mérés: előtte az IOPS-t és a p50/p95-öt rögzítjük, a throttle alatt ismét
iostat -xz 1 5
systemd-cgtop --depth=1 --iterations=5
# lab_bench --url http://127.0.0.1:18080/health --quantiles p50,p95,p99

A bizonyíték itt a request latency és a blokk-IO várakozás egyidejű növekedése. A hibás drop-in eltávolítása a recovery:

sudo rm /etc/systemd/system/lab-order-svc.service.d/10-throttle.conf
sudo systemctl daemon-reload
sudo systemctl restart lab-order-svc
# postcondition: a p50/p95 visszatér a baseline közelébe, a CPUQuota és IO limit megszűnik

55.4.3.4 Disk/inode/quota és service data

A „write nem sikerül” tünetet könnyű félreértelmezni, ha csak df -h-t nézünk. A labban inode kimerülést okozunk a service adatkönyvtárában:

# target: lab-app-a, user: lab-admin, privilege: sudo
sudo -u lab-svc mkdir -p /srv/lab-order-svc/lab-fill
for i in $(seq 1 10000); do sudo -u lab-svc touch "/srv/lab-order-svc/lab-fill/f$i"; done

# bizonyíték
df -h /srv
df -i /srv
sudo -u lab-svc find /srv/lab-order-svc/lab-fill -type f | wc -l
# várt/illusztratív: df -h mutat még szabad blokkot, de df -i 100% használt

A tünet a service oldalán No space left on device lehet akkor is, ha blokk szinten van szabad kapacitás. Ennek oka az inode kimerülés. A rollback csak a lab-fixture törlése:

sudo rm -rf /srv/lab-order-svc/lab-fill
df -i /srv
sudo -u lab-svc touch /srv/lab-order-svc/.write-test
sudo -u lab-svc rm /srv/lab-order-svc/.write-test
# postcondition: inode-használat a baseline, a service adatkönyvtára írható

Kvóta esetén a bizonyíték a quota vagy xfs_quota report kimenete, és a recovery a per-user limit feloldása vagy emelése. A service adatknál mindig rögzítjük a használt adatútvonalat: /srv/lab-order-svc, a tulajdonost, a backup idősorát és a du -x --max-depth=2 kimenetet.

55.4.3.5 Backend failure és proxy drain

A lab-lb Nginx upstream konfigurációja:

upstream lab_backend {
    server 198.51.100.20:18080 max_fails=2 fail_timeout=30s;
    server 198.51.100.21:18080;
}

A backend leállítása előtt nem szeretnénk 5xx-et adni. A proxy drain azt jelenti, hogy a maintenance alá vont backendet először kivonjuk a routing döntésből, majd megvárjuk, amíg az aktív kapcsolatok lecsengenek, és csak utána állítjuk le a service-t.

# target: lab-lb, user: lab-admin, privilege: sudo
cat <<'EOF' | sudo tee /etc/nginx/conf.d/lab-upstream.conf
upstream lab_backend {
    server 198.51.100.20:18080 max_fails=2 fail_timeout=30s down;
    server 198.51.100.21:18080;
}
EOF
sudo nginx -t && sudo systemctl reload nginx

# target: lab-app-a
sudo systemctl stop lab-order-svc

# target: lab-client
curl -sS -o /dev/null -w '%{http_code}\n' https://lab-svc.example/health
# várt/illusztratív: 200, mert a lab-app-b továbbra is kiszolgál

A recovery a leállított backend vizsgálata/javítása után a down kulcsszó eltávolítása és reload:

# target: lab-lb
sudo cp /etc/nginx/conf.d/lab-upstream.conf /etc/nginx/conf.d/lab-upstream.conf.bak
# a down sor törlése a lab-app-a server elől
sudo nginx -t && sudo systemctl reload nginx
# target: lab-app-a
sudo systemctl start lab-order-svc
# postcondition: mindkét backend újra aktív; curl 200

Ha mindkét backend kiesne, a tünet 502 lesz. Ezt a log bizonyítja, nem elég a curl hibakód. A hiba különválasztásához mindig rögzítjük:

# target: lab-lb
sudo tail -n 50 /var/log/nginx/error.log
# target: lab-app-a és lab-app-b
systemctl is-active lab-order-svc
ss -lntp | grep 18080

55.4.3.6 Backup restore és data integrity

A backup csak akkor jelent valós recoveryt, ha a restore utáni adat checksummal és szolgáltatáshealth-tel igazolt. A gyakorlatban restic repository-t használunk a lab-backup gépen.

Injektálás: a service aktuális adatfile-ját felülírjuk hibással.

# target: lab-app-a, user: lab-svc
echo corrupt > /srv/lab-order-svc/orders/current.dat
sha256sum /srv/lab-order-svc/orders/current.dat

A restore előtt a repository legfrissebb snapshotját kérjük le, majd egy külön target könyvtárba restore-olunk, hogy az élő adatot ne írjuk felül bizonyíték előtt:

# target: lab-app-a, user: lab-svc
sudo -u lab-svc restic -r /srv/lab-backup/repo \
  --password-file /etc/lab-backup/password.txt snapshots --latest 1

sudo -u lab-svc mkdir -p /tmp/lab-restore
sudo -u lab-svc restic -r /srv/lab-backup/repo \
  --password-file /etc/lab-backup/password.txt restore latest --target /tmp/lab-restore

# helyreállított fájl ellenőrzése
sudo -u lab-svc sha256sum /tmp/lab-restore/srv/lab-order-svc/orders/current.dat

A két checksum különbözősége igazolja a sérülést. Ha a restore file hasha ismert a backup manifestből, akkor először azt ellenőrizzük, és csak utána írjuk vissza:

sudo -u lab-svc cp /tmp/lab-restore/srv/lab-order-svc/orders/current.dat \
  /srv/lab-order-svc/orders/current.dat
sudo -u lab-svc sha256sum /srv/lab-order-svc/orders/current.dat
sudo systemctl restart lab-order-svc
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:18080/health
# postcondition: checksum egyezik a restore-tel; health 200

A restic restore --target paramétere nem az élő adatot írja felül, ezért a cp előtt a checksum-összehasonlítás bizonyítható. A rollout/backup műveleteknél mindig meg kell nevezni, hogy a snapshot/replication nem azonos a backup/restore-ral; a konténerekben vagy VM snapshotban is lehetnek félig írt adatfájlok.

55.4.3.7 Timeline, evidence és postmortem

A labban minden incidensről a következő formátumú idővonalat készítjük. Az időértékek falikór-időben (wall clock) vannak, illusztratívak:

T+perc Esemény Megfigyelt állapot Bizonyíték
0 Baseline 200 health curl -w, getent, openssl verify
4 Wrong DNS fixture client timeout getent ahosts rossz IP
9 DNS rollback névfeloldás jó getent ahosts
11 TLS chain fixture SSL certificate problem openssl s_client chain
16 TLS rollback 200 curl
21 Route fixture timeout, proxy ping jó ip route get
26 Route rollback 200 curl

A postmortem vezető szempontjai:

  1. Mi volt a felhasználói tünet?
  2. Mi volt a gyökérok, és milyen bizonyíték támasztotta alá?
  3. Mi volt a contributing factor, amit nem kell gyökéroknak nevezni?
  4. A mitigation, rollback és restore közül melyik mit oldott meg?
  5. Melyik mérést kell regressziós smoke tesztként megtartani?

Például a wrong DNS incidensnél a gyökérok a hibás /etc/hosts sor, a contributing factor a reverse proxyhoz tartozó névfeloldás cache-elése lehetett. A tanulság nem az, hogy „rossz a DNS”, hanem hogy a curl timeoutot DNS-bizonyíték nélkül nem szabad route-hibaként kezelni.

55.4.4 Hibák és ellenpróbák

A tünetet azonnal a rossz réteghez kötjük. A connection timed out nem feltétlenül route-hiba. Ellenpróba: getent ahosts lab-svc.example, ip route get 198.51.100.20, ss -tn state syn-sent '( dport = :443 )'. Ha a név rossz IP-t ad, az a DNS réteg; ha a route célorientáció helyes, de a SYN nem hagyja el a gépet, a route/ACL/firewall a következő.

A TLS chain hibáját kizárólag a kliensnapjából diagnosztizáljuk. A curl hibaüzenete nem mondja meg, hogy a szerver chain hiányos vagy a kliens CA store rossz. Ellenpróba a lab-lb oldali openssl s_client és openssl verify; a két oldal összevetése mutatja az eltérő chain-t.

Az OOM bizonyítékot a restart elrontja. Ha a MemoryPeak és a status=9/KILL nem rögzítettük, a friss systemd state csak a restart kísérletet mutatja. A labban előbb journalctl -k-t és systemctl show-t rögzítünk, utána restart.

A disk tele van, de df -h szerint nincs tele. Ellenpróba a df -i. A blokk-kapacitás és inode-kapacitás külön erőforrás; egy fájlrendszerben az inode-kimerülés ugyanolyan írásképtelenséget okoz.

A proxy drain elmarad. Ha a backendet leállítjuk, mielőtt a proxy routing döntéséből kivontuk volna, aktív kérések esnek el. Ellenpróba a ss -tnp és az Nginx access log aktív kapcsolatai. A drain sorrend: remove from upstream, reload, active connections drain, stop service.

A restore azonnal felülírja az élő adatot. Ellenpróba: először /tmp/lab-restore-ba restore-olunk, ott checksumot számolunk, és csak azután másoljuk vissza. Ha a backup maga sérült, a rossz restore nem rontja tovább az élő adatot.

A rollbacket összekeverjük a restore-ral. A rossz release visszavonása nem hozza vissza a törölt adatfile-t. Az adatsérülésnél rollback utáni restore is kell, és a healthcheck az adat sértetlenségét igazolja.

55.4.5 Feladatok

55.4.5.1 1. feladat: tünet-réteg hozzárendelés

A lab-client-en a curl https://lab-svc.example/health hibát ad: SSL certificate problem: unable to get local issuer certificate. A getent ahosts lab-svc.example visszaadja a 192.0.2.10-et. Az ip route get 198.51.100.20 rendben mutatja a via-t. Melyik réteg a legerősebb hipotézis? Milyen parancssal döntöd el, hogy a kliens CA store vagy a szerver TLS chain hibás? Ne telepíts semmit.

55.4.5.2 2. feladat: DNS/route fixture recovery

Készítsd el a labban a wrong DNS és a wrong route fixture-t a fenti parancsokkal. Mindkét hibát külön állítsd vissza, és igazold a postconditiont. A módosító parancsoknál nevezd meg a targetet, a privileget, a rollbacket és a vegyes ellenőrzést. Külön figyelj arra, hogy a DNS-hiba és a route-hiba tünete hasonló lehet.

55.4.5.3 3. feladat: FD leak/OOM diagnosztika és timeline

Telepítsd a 0.2.0-fdleak release-t, terheld a health endpointot, majd rögzítsd a tünetet és a FD-countot. Állítsd helyre a jó release-t. Ezután telepítsd a 0.2.1-oom release-t, figyeld a service state-et, majd készíts postmortem-t. A postmortem tartalmazza a gyökérokot, a contributing factort, a mitigation/rollback lépéseket és a regressziós smoke tesztet.

55.4.5.4 4. feladat: disk/inode, backup restore és data integrity

Töltsd fel inode-okkal a lab-order-svc service adatkönyvtárát, diagnosztizáld a No space left on device tünetet, majd tisztítsd a lab-fixture-t. Ezután rontsd el a current.dat adatfile-t, és bizonyítsd a backupból való restore-t: checksum, restart, healthcheck. A megoldásban indokold, miért restore-olsz előbb /tmp/lab-restore-ba, és miért nem közvetlenül az élő adatkönyvtárba.

55.4.6 Megoldások

55.4.6.1 1. feladat megoldás

A legvalószínűbb réteg a TLS trust/chain, mert a DNS-feloldás és a route is rendben van. A döntő bizonyíték a lab-lb-n futtatott:

# target: lab-lb, user: lab-admin, privilege: sudo
openssl s_client -connect lab-svc.example:443 -servername lab-svc.example -showcerts
openssl verify -CAfile /etc/ssl/lab/lab-ca-chain.pem /etc/ssl/lab/lab-leaf.pem

Ha a verify helyesen felépített CAfile mellett is hibát ad, a szerver által kiküldött chain hiányos. Ha csak a kliens CA store a hiányos, a lab-lb lánc valid. Postcondition: a hibaforrás egyértelműen az egyik oldalhoz rendelve, nem a DNS illetve a route.

55.4.6.2 2. feladat megoldás

A parancsok megegyeznek a kidolgozott példa wrong DNS és route fixture szakaszaival. A DNS-visszaállítás után:

# target: lab-client
getent ahosts lab-svc.example
# várt: 192.0.2.10

A route-visszaállítás után:

# target: lab-client
ip route get 198.51.100.20
# várt: 198.51.100.20 via 192.0.2.10 dev eth0
curl -sS -o /dev/null -w '%{http_code}\n' https://lab-svc.example/health
# várt: 200

A DNS-hiba és a route-hiba elkülönítése: a DNS-fixture alatt a getent ahosts rossz IP-t ad; route-fixture alatt a getent jó, de a ping 192.0.2.10 és a ping 198.51.100.20 közül az utóbbi nem megy. Ez a két ellenpróba megakadályozza a tünet összemosását.

55.4.6.3 3. feladat megoldás

A release telepítése után a tünet akkor jelenik meg, ha a /proc/PID/limits és a FD-count együtt mutatja a kimerülést:

PID=$(systemctl show -p MainPID --value lab-order-svc)
sudo ls "/proc/$PID/fd" | wc -l
sudo grep 'Max open files' "/proc/$PID/limits"
# várt: FD-count 1024 környékén, Max open files 1024

A jó release visszaállítása után FD-count ismét stabil alacsony. Az OOM-nál a systemctl status lab-order-svc nem Restarting, hanem failed vagy activating, és a journalctl -k OOM-kill bejegyzést ad. A MemoryPeak a MemoryMax közelében van.

A postmortem:

  • Gyökérok: a 0.2.1-oom release memóriafogyasztása növekedett; a cgroup MemoryMax=512M elérése után OOM-kill.
  • Contributing factor: a health requestek a memóriaelfogyás előtt is magas kihasználtságot okoztak, de az OOM-ot a release okozta.
  • Mitigation: a service systemctl stop-ja, hogy megőrizzük a bizonyítékot; ha szükséges, a loadbalancerből kivonás.
  • Rollback: 0.1.9-good release visszaállítása, a 10-oom-fixture drop-in eltávolítása.
  • Regressziós smoke teszt: 5 perces health-terhelés után a MemoryCurrent nem közelíti a limitet, FD-count stabil, HTTP 200.

55.4.6.4 4. feladat megoldás

Az inode-fixture felszámolása:

sudo rm -rf /srv/lab-order-svc/lab-fill
df -i /srv
sudo -u lab-svc touch /srv/lab-order-svc/.write-test
sudo -u lab-svc rm /srv/lab-order-svc/.write-test
# postcondition: write test sikerült; df -i megegyezik a baseline-nal

A restore sorrend: előbb snapshot list, külön restore, checksum, utána felülírás. Ennek oka, hogy ha a backup snapshot sérült, a közvetlen felülírás tovább rontaná az élő adatot. A külön restore-tal ellenőrizhető a hasha, és a cp csak akkor hajtódhat végre, ha a restore integritása igazolt.

sudo -u lab-svc restic -r /srv/lab-backup/repo \
  --password-file /etc/lab-backup/password.txt restore latest --target /tmp/lab-restore

sudo -u lab-svc sha256sum /tmp/lab-restore/srv/lab-order-svc/orders/current.dat
sudo -u lab-svc cp /tmp/lab-restore/srv/lab-order-svc/orders/current.dat \
  /srv/lab-order-svc/orders/current.dat
sudo -u lab-svc sha256sum /srv/lab-order-svc/orders/current.dat
sudo systemctl restart lab-order-svc
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:18080/health
# postcondition: checksum egyezik, health 200, a service a restore után fut

55.4.7 Rövid összefoglaló

A kontrollált incidenslab a tünetet előbb rendeli erőforrásvagy dependency-réteghez, és csak utána változtat. A DNS, TLS-lánc és route mind függőségi hiba; a hibás /etc/hosts, a hiányos CA chain és a rossz route ugyanazt a látszólagos timeoutot adhatja, ezért mindegyikhez külön bizonyíték kell. Az FD leak, OOM, throttle és IO bottleneck erőforráshiba; itt a release, a cgroup limit és a /proc adatok választják el a hibatípust. A backend failure-nél a proxy drain megelőzi az 5xx-et, a restore pedig csak checksumolt backupból, külön targetből írja vissza az élő adatot. A timeline és postmortem a megfigyelést, a gyökérokot és a regressziós smoke tesztet külön kezeli.

  • Fixture: szándékosan hibás, névvel és postconditionnel azonosított labállapot.
  • Rollback: release/konfiguráció visszaállítása ismert jó állapotba; nem adatrestore.
  • Restore: adat integritásellenőrzött visszaállítása backupból; minimum checksum és szolgáltatáshealth igazolja.
