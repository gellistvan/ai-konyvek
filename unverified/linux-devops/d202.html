41.2 Ingress API, Gateway API és edge routing

Egy Kubernetes Service önmagában legfeljebb L4-es elérést ad egy ClusterIP:Port vagy egy felhőszolgáltatói terheléselosztó LoadBalancer IP:port mögött. Amint hosztnév, HTTPS-termináció, path/header alapú irányítás vagy kereszt-névtér engedélyezés kell, ez a forgalmat L7-es szerződéssé teszi. Az Ingress API és a Gateway API egyaránt ezt a kívánt edge-forgalmi szerződést írja le, de a kettő felelősségi modellje eltér. A cél nem csak az objektumok létrehozása, hanem annak megértése is, hogy a routing-szerződés és a tényleges adatút két különböző állapot: az erőforrás a kívánt állapot, a controller pedig a megfigyelt, tényleges állapot.

41.2.1 Definíció: Ingress és Gateway API felelősségi határa

Az Ingress a Kubernetes klasszikus L7-es edge API objektuma. Az networking.k8s.io/v1 verzió rules listában ad meg hosztot, path-t és backend.service hivatkozást. A TLS-t spec.tls alatt, kubernetes.io/tls típusú Secret referenciával kezeli. Az Ingress önmagában csak a szándékot rögzíti; az adatutat egy Ingress controller valósítja meg.

A Gateway API szétválasztja az infrastruktúra-felelősséget és az alkalmazás-felelősséget:

  • GatewayClass: controller implementation kiválasztása; hasonló szerep, mint az IngressClass.
  • Gateway: egy vagy több L4/L7 listener, például HTTPS a 443-as porton, TLS-terminációval.
  • HTTPRoute: L7 forgalmi szabály: hoszt, path, header, backend Service referenciák.

Az API object és a controller implementation felelősségét mindig külön kell kezelni. Egy HTTPRoute nem „működik” attól, hogy létrejött; a controllernek el kell fogadnia a route-ot, és a tényleges proxy/load balancer konfigurációjába kell illesztenie. A diagnózis során ezért először az objektum spec és status közötti rést kell megnézni.

41.2.2 Ingress API történeti és kompatibilitási szerep

Az Ingress a Kubernetesben hosszú ideig az egyetlen szabványos L7-es edge API volt, ezért számos controller és meglévő rendszer továbbra is ezt használja. A hátránya, hogy az alkalmazáscsapatok és a platformcsapatok gyakran egyetlen YAML-ben keverik a route-szándékot a controller-specifikus annotációkkal, ami gyenge hordozhatóságot eredményez. A Gateway API ezt a feszültséget oldja fel, de az Ingress API kompatibilis belépőpont marad, és a controller-implementációk gyakran mindkettőt támogatják.

A Gateway API nem helyettesíti automatikusan az Ingress API-t; a labon egyidejűleg is létezhetnek. Az Ingress spec.ingressClassName mezője köti össze az IngressClass-szal, míg a Gateway API GatewayClass erőforrása a spec.controllerName mezővel azonosítja a controller-t. A döntést tehát nem „Ingress vagy Gateway API” alapon érdemes meghozni, hanem a platform által kínált controller-támogatás és a szolgáltatási szerződés kifelé mutatott API-ja alapján.

41.2.3 GatewayClass, Gateway, HTTPRoute és controller support

A Gateway API objektumok a clusterbe CRD-ként települnek. A lab akkor tudja használni a gateway.networking.k8s.io/v1 API-verziót, ha a telepített CRD-k tartalmazzák. Ezt a lab indítása előtt ellenőrizni kell:

kubectl --context=lab-cluster api-resources \
  | grep gateway.networking.k8s.io

A GatewayClass spec.controllerName értékét a kiválasztott controller dokumentációjából kell venni. Például az Envoy Gateway, NGINX Gateway Fabric vagy Cilium Gateway API implementáció különböző controllerName értéket regisztrál. Ez nem cserélhető szabadon: ha egy másik controller fut, a GatewayClass nem lesz Accepted, és a hozzá tartozó Gateway nem kap adatutat.

A controller support/maintenance státusz ellenőrzése tehát négy lépésből áll:

  1. A cluster CRD-verziója: kubectl get crd gateways.gateway.networking.k8s.io -o yaml.
  2. A controller-pod képe és verziója: kubectl get pods -n gateway-system -o yaml.
  3. A GatewayClass status.conditions Accepted feltétele.
  4. A Gateway status.addresses és status.conditions Programmed feltétele.

A labpéldában feltételezünk egy lab.example.com/gateway-controller controllerName értéket, mert a példa izolált, és nem kötődik egyetlen valós controller release-hez sem. Éles clusternél ezt a leképezést ellenőrizni kell.

41.2.4 L4/L7 routing és cross-namespace authorization

A Gateway API-ban a listener a L4-es belépési pont: protokoll, port, hostname és TLS-mód. Ha a listener protocol: HTTPS és tls.mode: Terminate, akkor a Gateway a TLS-t befejezi, és a dekódolt HTTP-forgalmat L7-es HTTPRoute döntések elé tárja. Ha a listener protocol: TLS és tls.mode: Passthrough, akkor a Gateway nem bontja a TLS-t; ilyenkor L4-es TLSRoute vagy TCPRoute használható.

A HTTPRoute a listenerhez parentRefs listával csatlakozik. A Gateway hallgatója csak akkor fogadja el a route-ot, ha a route hosztneve illeszkedik a listener hosztnevére, és a névtér-engedély megengedi. A Gateway spec.listeners[].allowedRoutes.namespaces mező szerint Same (csak a Gateway névterében lévő route-ok), All (minden névtérben lévő route) vagy Selector (címke szerint szűrt névterek). Alapértelmezésben Same.

A HTTPRoute backendRefs listája egy másik névtérben lévő Service-re csak akkor mutathat, ha a cél névtérben ReferenceGrant (korábbi nevén ReferencePolicy) engedélyezi. Ez explicit cross-namespace authorization: nem a hívó route ad magának jogot, hanem a cél szolgáltatást birtokló névtér ad engedélyt a hivatkozásra. A ReferenceGrant fontos biztonsági határ: például a web névtérben futó route csak akkor érhet el egy data névtérben lévő Service-t, ha a data névtér ezt engedélyezi.

A controller a route-ot akkor is ResolvedRefs True állapotba tudja tenni, ha a backend Service hivatkozás érvényes, de a podok közül egy sem Ready. Ezért a route-state önmagában nem bizonyítja az adatúti elérhetőséget; a backend EndpointSlice és a pod readiness együttes ellenőrzése kell.

41.2.5 Kidolgozott példa: HTTPS edge egy HTTPRoute-tal

A labfeltételezések:

  • lab-cluster context elérhető.
  • edge és app névtér létezik.
  • app névtérben lab-web:80 és lab-api:8080 Service-ek futnak, mögöttük legalább egy-egy Ready pod.
  • A dummy TLS-tanúsítványt edge névtérben hozzuk létre; a hosztnév lab.example.com a dokumentációs tartományhoz hasonló, lab-only használatra.

Először önaláírt, lab-only tanúsítványt készítünk, és titkot hozunk létre:

openssl req -x509 -newkey rsa:2048 -nodes \
  -keyout lab-edge-tls.key -out lab-edge-tls.crt \
  -days 30 -subj "/CN=lab.example.com" \
  -addext "subjectAltName=DNS:lab.example.com"

kubectl --context=lab-cluster -n edge create secret tls lab-edge-tls \
  --cert=lab-edge-tls.crt --key=lab-edge-tls.key \
  --dry-run=client -o yaml > edge-tls-secret.yaml

kubectl --context=lab-cluster -n edge apply -f edge-tls-secret.yaml

A GatewayClass, Gateway és HTTPRoute YAML-ja:

# gatewayclass.yaml
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: lab-gatewayclass
spec:
  controllerName: lab.example.com/gateway-controller
# gateway.yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: lab-edge-gw
  namespace: edge
spec:
  gatewayClassName: lab-gatewayclass
  listeners:
  - name: https
    protocol: HTTPS
    port: 443
    hostname: lab.example.com
    allowedRoutes:
      namespaces:
        from: All
    tls:
      mode: Terminate
      certificateRefs:
      - kind: Secret
        name: lab-edge-tls
# httproute.yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: lab-httproute
  namespace: app
spec:
  parentRefs:
  - name: lab-edge-gw
    namespace: edge
  hostnames:
  - lab.example.com
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /api
    backendRefs:
    - name: lab-api
      port: 8080
  - backendRefs:
    - name: lab-web
      port: 80

Hierarchia: a GatewayClass mondja meg, melyik controllerhez tartozik a Gateway; a Gateway listener a szolgáltatási bejárat; a HTTPRoute az alkalmazáscsapat routing-szerződése. Az edge névtér a belépési infrastruktúrát birtokolja, az app névtér a route-ot és a backendek nevét tartalmazza. Az allowedRoutes.namespaces.from: All engedi, hogy az app névtérben lévő route csatlakozzon az edge névtérben lévő Gateway-hez.

Telepítés és állapot-ellenőrzés:

kubectl --context=lab-cluster apply -f gatewayclass.yaml
kubectl --context=lab-cluster apply -f gateway.yaml
kubectl --context=lab-cluster apply -f httproute.yaml

kubectl --context=lab-cluster -n edge get gateway lab-edge-gw
kubectl --context=lab-cluster -n app get httproute lab-httproute

kubectl --context=lab-cluster -n edge get gateway lab-edge-gw \
  -o jsonpath='{.status.conditions}' | jq
kubectl --context=lab-cluster -n app get httproute lab-httproute \
  -o jsonpath='{.status.parents}' | jq

Várható, illusztratív kimenet a Gateway-re:

NAME          CLASS              ADDRESS       PROGRAMMED   AGE
lab-edge-gw   lab-gatewayclass   192.0.2.10    True         5m

A HTTPRoute parent feltételeiben Accepted és ResolvedRefs egyaránt True, a parentRef lab-edge-gw az edge névtérben. Ezután adatúti ellenőrzés:

GW_IP=$(kubectl --context=lab-cluster -n edge get gateway lab-edge-gw \
  -o jsonpath='{.status.addresses[0].value}')
curl -k --resolve lab.example.com:443:$GW_IP \
  https://lab.example.com/api/health

Várható kimenet: {"status":"ok"} vagy a lab-api pod által adott válasz. A -k a lab-only önaláírt tanúsítvány miatt kell; élesben megbízható láncot kell használni.

41.2.6 Gyakori hibák és ellenpróbák

41.2.6.1 A HTTPRoute nem Accepted

A HTTPRoute status.parents[].conditions Accepted: False, a reason például NoMatchingListenerHostname. A hipotézis: a route hosztneve nem illeszkedik a listener hosztnevére, vagy a route nem csatlakozhat a Gateway névteréhez. Adatgyűjtés:

kubectl --context=lab-cluster -n app get httproute lab-httproute -o yaml
kubectl --context=lab-cluster -n edge get gateway lab-edge-gw -o yaml

Változtatás: javítsa a hostnames mezőt, vagy a Gateway allowedRoutes mezőjét. Rollback a korábbi YAML-ra; ellenőrzés a parents[].conditions újraolvasásával.

41.2.6.2 ResolvedRefs False: backend hiba

Ha a HTTPRoute ResolvedRefs False, a reason gyakran BackendNotFound vagy RefNotPermitted. A BackendNotFound esetén ellenőrizze, hogy a hivatkozott Service és port létezik-e:

kubectl --context=lab-cluster -n app get service lab-api
kubectl --context=lab-cluster -n app get endpointslices \
  -l kubernetes.io/service-name=lab-api

Ha a Service más névtérben van, és RefNotPermitted a reason, akkor ReferenceGrant hiányáról van szó. Ilyenkor a cél névtérnek kell engedélyt adnia:

# referencegrant.yaml
apiVersion: gateway.networking.k8s.io/v1beta1
kind: ReferenceGrant
metadata:
  name: allow-web-to-api
  namespace: data
spec:
  from:
  - group: gateway.networking.k8s.io
    kind: HTTPRoute
    namespace: app
  to:
  - group: ""
    kind: Service

A ReferenceGrant API-csoport/version itt v1beta1 lehet a telepített CRD szerint; ellenőrzés: kubectl api-resources | grep referencegrant.

41.2.6.3 TLS Secret vagy tanúsítvány hiba

A Gateway listener status.conditions mezőjében InvalidCertificateRef vagy CertificateNotFound jelenhet meg. A leggyakoribb ok: a Secret nem kubernetes.io/tls típusú, hiányzik a tls.crt vagy tls.key, vagy a tanúsítvány hosztneve nem egyezik a listener hosztnevvel. Ellenőrzés:

kubectl --context=lab-cluster -n edge get secret lab-edge-tls -o yaml
openssl x509 -in lab-edge-tls.crt -noout -subject -ext subjectAltName

A megoldás a Secret javítása, nem a TLS-kliens ellenőrzés globális letiltása. A d144-ben tárgyalt tanúsítványlánc-validáció itt is érvényes: a cert nem attól jó, hogy a Secret létezik, hanem attól, hogy a kliens a hosztnévhez tartozó láncot kapja.

41.2.6.4 Backend readiness 503

A ResolvedRefs True mellett is előfordulhat, hogy a kliens 503 választ kap. Ilyenkor a hiba nem a route specifikációban van, hanem a backend adatúton: a pod nem Ready, vagy a Service port nem egyezik a pod konténerportjával. Ellenőrzés:

kubectl --context=lab-cluster -n app get endpoints lab-api
kubectl --context=lab-cluster -n app get pods -l app=lab-api \
  -o jsonpath='{.items[*].status.conditions[?(@.type=="Ready")]}'

41.2.6.5 LB/edge source identity

A Gateway mögötti backend a kliens forrás IP-jét nem feltétlenül látja: ha a Gateway L7-es terminációt végez, a backend a proxy IP-címét látja. A X-Forwarded-For fejléc csak akkor hiteles, ha a proxy-lánc minden tagja explicit trust alatt áll, és a Gateway-be belépő fejlécet a controller megfelelően kezeli. Ez a forrásazonosság a hitelesítési (auth) réteggel is összefügg: az edge routing feladata a kliensorigin megőrzése vagy továbbítása, de a backendnek nem szabad megbíznia benne pusztán azért, mert a kliens küldte. A Gateway controller dokumentációja szerint ellenőrizni kell a proxy protokollt, a Service externalTrafficPolicy beállítását, vagy a platform által kínált forrás IP megőrzést.

41.2.7 Feladatok

41.2.7.1 1. feladat – magyarázó

Készítsen táblázatot arról, hogy a Gateway, HTTPRoute, GatewayClass és ReferenceGrant erőforrások közül melyik mit állít elő: L4-es bejáratot, L7-es routing-szerződést, controller-kiválasztást vagy cross-namespace engedélyt. Állapítsa meg, mi a különbség a Gateway status.conditions és a HTTPRoute status.parents[].conditions jelentése között.

41.2.7.2 2. feladat – adminisztrációs/konfigurációs

A labon hozzon létre egy GatewayClassot lab-gwclass néven, egy Gatewayt lab-gw néven edge névtérben, valamint egy HTTPRoute-ot lab-route néven app névtérben. A listener legyen HTTPS, hostneve lab.example.com, és TLS-terminációt végezzen egy lab-only lab-tls Secret-ből. A route irányítsa a /api prefixet a lab-api:8080 Service-re, minden más path-t a lab-web:80 Service-re. Ellenőrizze a Programmed, Accepted, ResolvedRefs állapotokat és az adatút válaszát. Adjon meg explicit target contextet, névteret, alkalmazott YAML-okat és postcondition ellenőrzést.

41.2.7.3 3. feladat – diagnosztikai/failure/recovery

A clusterben a lab-route status.parents[].conditions ResolvedRefs: False, reason RefNotPermitted. A route a data névtérben lévő lab-api Service-re hivatkozik, de a data névtérben nincs engedélyező objektum. Diagnosztizálja a hiányzó ReferenceGrant okot, hozza létre a megfelelő engedélyt, majd igazolja, hogy a route ResolvedRefs True és a /api/health kérés megérkezik a backendhez. Ne módosítsa a route-ot más névtérbe való áthelyezéssel; a feladat célja a cross-namespace trust megértése.

41.2.8 Megoldások

41.2.8.1 1. feladat megoldása

Erőforrás Felelősség Megfigyelt állapot
GatewayClass Controller implementation kiválasztása status.conditions Accepted
Gateway L4/L7 belépési pont, listener, TLS status.conditions Programmed, status.addresses
HTTPRoute L7 routing-szerződés, backendRefs status.parents[].conditions Accepted, ResolvedRefs
ReferenceGrant Cross-namespace Service hivatkozás engedélye nem forgalomirányít; a route ResolvedRefs feltételét közvetve javítja

A Gateway status.conditions a Gateway erőforrás egészére vonatkozik, például hogy a controller adatutat programozott-e. A HTTPRoute status.parents[] feltételei azt mutatják, hogy egy adott Gatewayhez mint szülőhöz viszonyítva a route elfogadható-e, és a backendRefs feloldható-e.

41.2.8.2 2. feladat megoldása

A YAML-ok megegyeznek a kidolgozott példával, de a nevek lab-gwclass, lab-gw, lab-route és a Secret lab-tls. A Secret létrehozása után:

kubectl --context=lab-cluster apply -f gwclass.yaml
kubectl --context=lab-cluster apply -f gw.yaml
kubectl --context=lab-cluster apply -f route.yaml
kubectl --context=lab-cluster -n edge get gateway lab-gw -o yaml
kubectl --context=lab-cluster -n app get httproute lab-route -o yaml

Postcondition: a Gateway status.conditions Programmed: True, a HTTPRoute parents[].conditions Accepted: True és ResolvedRefs: True, valamint a curl --resolve hívás a várt HTTP 200-at adja. Indoklás: a listener TLS-terminációhoz szükséges hitelesítő anyag a Secret referencián keresztül elérhető; a route hosztneve illeszkedik; a Service-ek léteznek és van Ready podjuk.

41.2.8.3 3. feladat megoldása

A data névtérnek kell ReferenceGrant-et létrehoznia:

apiVersion: gateway.networking.k8s.io/v1beta1
kind: ReferenceGrant
metadata:
  name: allow-app-to-data-api
  namespace: data
spec:
  from:
  - group: gateway.networking.k8s.io
    kind: HTTPRoute
    namespace: app
  to:
  - group: ""
    kind: Service

Alkalmazás:

kubectl --context=lab-cluster apply -f referencegrant.yaml
kubectl --context=lab-cluster -n app get httproute lab-route \
  -o jsonpath='{.status.parents[].conditions}' | jq

A ResolvedRefs True lesz, ha a route hivatkozott Service és port is érvényes. Postcondition: a route hivatkozik a data névtérben lévő lab-api Service-re, a data névtér explicit engedélyt adott, és az adatút curl szinten is HTTP 200-at mutat. Ez a megoldás megtartja a cross-namespace trust szerződést: a hívó fél nem kap közvetlen jogot, a cél névtér adja az engedélyt.

41.2.9 Rövid összefoglaló

A Gateway API szétválasztja a controller-kiválasztást, a L4/L7 belépési pontot és az L7 routing-szerződést. Az Ingress API kompatibilis, de kevésbé hatékony felelősségi modellt ad. A diagnózis során a Gateway és HTTPRoute status feltételei külön olvasandók; a ResolvedRefs nem bizonyítja a pod readiness-sel mérhető adatút működését. A TLS Secret és a cross-namespace ReferenceGrant egyaránt explicit engedély, nem pedig globális hozzáférés. A forrás IP hitelességét a proxy-lánc trust határozza meg.

  • GatewayClass: a Gateway API controller implementation kiválasztása.
  • HTTPRoute: L7 forgalmi routing-szerződés, hoszt/path és backendRefs.
  • ReferenceGrant: a cél névtér engedélye, hogy egy HTTPRoute cross-namespace Service-re hivatkozhasson.
