54.3 Ceph, SAN/NAS és object/block/file fabric

54.3.1 Motiváció és definíciós határ

A lokális RAID egyetlen szerveren belül ad blokkszintű redundanciát, de a platformszolgáltatások akkor is működnek, ha egy teljes node vagy rack kiesik. A szenior C++ fejlesztő számára ez azért releváns, mert a modern alkalmazások storage-át nem egyetlen diszk, hanem elosztott rendszer adja: a VM-ek RBD image-ből bootolnak, a Kubernetes PVC-k Ceph volume-okra mutatnak, az objektumtároló bucketek pedig ugyanabban a clusterben laknak. A Ceph egy software-defined storage (SDS) rendszer, amely egyetlen RADOS (Reliable Autonomic Distributed Object Store) rétegre épít block, file és object hozzáférést.

A tárgyalás során három fogalmat használunk újra:

  • Placement Group (PG): objektumok logikai csoportja, amely a pool OSD-kre való kiosztásának atomi egysége. Minden pool rendelkezik pg_num értékkel; az objektum hash alapján kerül PG-be.
  • CRUSH: pseudo-random elhelyezési algoritmus, amely a cluster mapból és az OSD súlyokból számítja ki, mely OSD-k tárolják az adott PG replikáit vagy erasure coding darabjait. Nincs központi lookup tábla, ezért a client is képes kiszámolni a cél OSD-t.
  • Recovery headroom: az a szabad kapacitás és I/O sáv, amely lehetővé teszi a PG-k helyreállítását anélkül, hogy a client I/O-t megfojtanák. A hiánya full pool és lassú recovery állapothoz vezet.

A fejezet a d267 quorum fogalmaira, a d024 RAID write penalty modelljére és a d223 cloud storage durability fogalmaira épít.

54.3.2 Ceph architektúra és adatút

A Ceph cluster minimálisan monitorokból, OSD-kből és clientekből áll. A komponensek szerepe élesen elkülönül:

  • Monitor: a cluster térképét (monmap, OSD map, PG map, CRUSH map) és a hitelesítést tartja. A monitorok quorum alapú konzisztenciát használnak; a quorum elvesztése esetén a cluster nem frissíthető, és a clientek nem kapnak új mapot.
  • OSD (Object Storage Daemon): egy háttérdiszkért felelős daemon. Az OSD tárolja az objektumokat, kezeli a replikációt, a recoveryt, a scrubot és a client I/O-t. Egy node-on több OSD futhat, de a PG replikái különböző hostokra kerülnek a CRUSH failure domain szabályai szerint.
  • Metadata Server (MDS): kizárólag a CephFS namespace-ét és metadata műveleteit szolgálja. A fájl tartalma objektumokban van, a metadata az MDS-ben.
  • RADOS Gateway (RGW): S3/Swift REST API-t ad; bucket, object, versioning, lifecycle és ACL műveleteket kezel.

Az írási út egy RBD volume-nál a következő:

  1. A client (librbd vagy kernel rbd) az image blokkjait objektumokra bontja, kiszámítja a PG-t.
  2. A CRUSH meghatározza a primary OSD-t és a replikákat.
  3. A client elküldi az írást a primary OSD-nek.
  4. A primary OSD naplózza, alkalmazza a lokális store-ba, és párhuzamosan elküldi a replikáknak.
  5. A client akkor kap ack-ot, ha legalább min_size replika megerősítette az írást.

Olvasásnál a client közvetlenül a primary OSD-től kér, nincs központi gateway; ezért a hálózat kelet-nyugati forgalma terhelődik, és a tail latency a leglassabb replika elérésétől függ.

A Ceph három hozzáférési formája:

  • RBD (RADOS Block Device): thin-provisioned blokkeszköz, snapshot, clone és layering támogatással. Linux kernel rbd modul vagy librbd (QEMU, Kubernetes CSI) használja. Jó VM boot volume és adatbázis volume.
  • CephFS: POSIX szemantikájú megosztott fájlrendszer, MDS daemonokkal. Jó shared home, log, CI workspace.
  • RGW: S3/Swift API-t adó object gateway. Jó web asset, backup cél, data lake.

A monitorok nem érintik az adatút késleltetését, de a map frissítések miatt a client session fenntartása kritikus. A CephFS csak MDS-ekkel használható, az RGW pedig HTTP protokollt beszél.

Egy példa lab cluster topológiája:

Komponens Node IPv4 Szerep
mon.0..2 lab-ceph-mon01..03 192.0.2.11..13 monitor quorum
osd.0..11 lab-ceph-osd01..03 192.0.2.21..23 4 OSD/node, 12 OSD
mds lab-ceph-mds01 192.0.2.31 CephFS metadata
rgw lab-ceph-rgw01 192.0.2.32 S3 gateway

A CRUSH szabály úgy van beállítva, hogy egy PG replikái különböző hostokra kerüljenek, így egy node kiesése nem veszíti el az adatot.

54.3.3 Replication, erasure coding és recovery headroom

A replikáció (size=3) a legegyszerűbb adatvédelmi mód: minden PG három példányban van. A kapacitás overhead 3x, tehát 100 TiB hasznos adat 300 TiB nyers kapacitást igényel. Az írási I/O overhead: minden logikai write 3 fizikai write-ot generál. A min_size=2 azt jelenti, hogy két replika megerősítése elegendő az ack-hoz, de a PG degradált (degraded) állapotba kerül, ha egy replika hiányzik.

Az erasure coding (EC) parity alapú: például k=4, m=2 (4+2) esetén az objektumot 4 adatdarabra és 2 parity darabra bontja, 6 OSD-re írja. A kapacitás overhead 6/4 = 1.5x, tehát 100 TiB hasznos adat 150 TiB nyers kapacitást igényel. Az írási út drágább, mert a client vagy a primary OSD encode-ol, és minden write több OSD-t érint; az olvasás csak k darabot igényel, de a small random write büntetése nagy. EC-t főleg RGW object pool-hoz és hideg RBD-hez használnak.

A rebalance akkor történik, ha az OSD súlyok változnak, új OSD kerül be, vagy a CRUSH map módosul. A ceph osd reweight, ceph osd crush reweight és a ceph balancer (upmap mód) segítségével a PG-k egyenletesebben oszlanak el. A rebalance során a PG-k átkerülnek más OSD-kre, ami extra I/O-t generál.

A recovery headroom a szabad kapacitás és I/O sáv. A ceph status mutatja a recovery, backfill, degraded, undersized állapotokat. A backfill a teljes PG adatátmásolás, a recovery a delta szinkronizálás. Ha a cluster túl telített (pl. 85% fölött), a recovery lassul, és a full ratio elérésekor az írás leáll. A kapacitástervezésben legalább 20-30% szabad kapacitást és egy kieső OSD-nyi headroomot kell tartani.

Az iSCSI SCSI parancsokat TCP-n visz, a NVMe-oF az NVMe parancsokat RDMA/TCP-n; mindkettő block storage. A NAS fájlrendszer-szemantikát ad, a client a fájlon dolgozik, nem a blokkon. A Ceph RBD-t iSCSI gateway-jel is ki lehet tenni, de a natív librbd/kernel rbd hatékonyabb.

54.3.5 CSI és VM/application storage path

A Kubernetes a Ceph-hez CSI driverekkel csatlakozik:

  • rbd.csi.ceph.com block volume-ot ad, jellemzően RWO (ReadWriteOnce) node attach-tal.
  • cephfs.csi.ceph.com file volume-ot ad, RWX (ReadWriteMany) megosztott mount-tal.

A StorageClass, PVC, PV lánc: a StorageClass parameters tartalmazza a pool nevet, a clusterID-t, a csi.storage.k8s.io/provisioner-secret-name és a node-stage-secret-name titkokat. A CSI driver a volume megkötése után rbd map-pal vagy rbd-nbd-vel csatolja a node-hoz, majd a kubelet mountolja a podba.

VM-eknél: libvirt/QEMU közvetlen librbd-t használ, így a VM blokkeszköze Ceph volumeként jelenik meg; a live migration a forrás és cél node-on is hozzáfér a Ceph image-hez, nincs szükség blokkmásolásra.

54.3.6 Kidolgozott példa: kapacitástervezés, full pool diagnosztika

A lab cluster a fenti inventory-val rendelkezik. A cél: RBD pool létrehozása replikációval, size=3, min_size=2, 256 PG, 10 TiB hasznos adat tervezése. A rendelkezésre álló nyers kapacitás 12 OSD x 4 TiB = 48 TiB. Hasznos kapacitás 3x replikációval: 16 TiB. A 10 TiB hasznos adat 30 TiB nyerset igényel, így a cluster 62.5% telített, ami még a 85% full ratio alatt van, de már nincs sok recovery headroom.

Parancsok a monitor node-on, ceph user:

# lab-ceph-mon01, UID=ceph, privilege=sudo
sudo -u ceph ceph osd pool create lab-rbd-pool 256 256 replicated
sudo -u ceph ceph osd pool set lab-rbd-pool size 3
sudo -u ceph ceph osd pool set lab-rbd-pool min_size 2
sudo -u ceph ceph osd pool application enable lab-rbd-pool rbd

RBD image létrehozása és csatolása a lab VM-hez:

# lab-ceph-mon01
sudo -u ceph rbd create lab-rbd-pool/lab-db-01 --size 100G --image-feature exclusive-lock,object-map,fast-diff,layering
# lab-ceph-client01, root
rbd map lab-rbd-pool/lab-db-01
mkfs.xfs /dev/rbd0
mount /dev/rbd0 /var/lib/mysql-lab

A telítettség megfigyelése:

# lab-ceph-mon01
sudo -u ceph ceph df
sudo -u ceph ceph osd df

Várt kimenet (illusztratív, nem mért):

--- RAW STORAGE ---
CLASS  SIZE     AVAIL    USED     RAW USED  %RAW USED
hdd    48 TiB   18 TiB   30 TiB   30 TiB     62.50

--- POOLS ---
POOL          ID  PGS  STORED  OBJECTS  USED     %USED  MAX AVAIL
lab-rbd-pool   3  256  10 TiB   262144  30 TiB   62.50    16 TiB

A ceph osd df megmutatja, ha egy OSD %USE magas, és a PG-k nem egyenletesen oszlanak el. Ha az egyik OSD eléri a 85%-ot, a cluster HEALTH_WARN állapotba kerül, full flag esetén az írás leáll. A kapacitásprobléma javítása: OSD hozzáadása, felesleges snapshot törlése, vagy a pool pg_num csökkentése (utóbbi óvatosan).

A full pool szimulálása és megszüntetése (lab, nem production):

# lab-ceph-mon01
sudo -u ceph ceph osd set full
# Írási kísérlet a clienten hibát ad
rbd resize lab-rbd-pool/lab-db-01 --size 110G
# Hiba: "pool lab-rbd-pool is full"
sudo -u ceph ceph osd unset full

54.3.7 Tipikus hibák és ellenpróbák

  1. Egy OSD full: a CRUSH nem egyenletesen oszlik el, ha az OSD súlyok hibásak. ceph osd df megmutatja, ceph osd reweight-by-utilization korrigálhat.
  2. PG stuck: ceph health detail jelzi, ha a PG down, degraded, stuck unclean, stuck inactive. A ceph pg dump_stuck megtalálja. A javítás: OSD visszaállítás, monitor map frissítés, vagy a pool size csökkentése.
  3. Recovery storm: egy node kiesésekor az összes PG egyszerre kezd backfillt, ami a client I/O-t megfojtja. A osd_max_backfills, osd_recovery_max_active, osd_recovery_sleep paraméterek szabályozzák.
  4. Monitor quorum loss: ha 3 monitorból 2 elérhetetlen, a cluster nem módosítható, de a meglévő client session-ök bizonyos ideig működhetnek. A monitorokat külön failure domainbe kell tenni, és a quorumot vissza kell állítani.
  5. Scrub hibák: a scrub és deep-scrub a PG-k integritását ellenőrzi. Ha a scrub hibát talál, a PG inconsistent állapotba kerül; ilyenkor a ceph pg repair óvatosan használható, de előbb az adat elérhetőségét és a replikákat ellenőrizni kell.

54.3.8 Feladatok

  1. Magyarázó feladat: Egy Ceph clusterben 12 OSD van, egyenként 8 TiB. Számítsd ki a hasznos kapacitást size=3 replikációval és 4+2 EC-vel. Add meg a kapacitás overheadet és a szabad recovery headroomot, ha a cluster 70% telítettséget céloz.

  2. Adminisztrációs/konfigurációs feladat: Hozz létre egy CephFS pool-t és egy RGW bucketet a lab clusterben, majd csatold fel a CephFS-t a lab-client node-ra, és írj egy 1 MiB-os fájlt. A bucketbe tölts fel egy objektumot az S3 API-val.

  3. Diagnosztikai/failure/recovery feladat: Állíts le egy OSD-t a lab clusterben, figyeld meg a ceph status kimenetét, majd indítsd újra az OSD-t, és ellenőrizd a recoveryt. Írd le, melyik paramétert állítanád be, ha a recovery túl lassú, és miért.

54.3.9 Megoldások

  1. Nyers kapacitás = 12 * 8 TiB = 96 TiB. Replikáció size=3: hasznos = 96 / 3 = 32 TiB. EC 4+2: overhead = 6/4 = 1.5, hasznos = 96 / 1.5 = 64 TiB. 70% telítettség replikációnál: 32 * 0.7 = 22.4 TiB használt, szabad = 9.6 TiB hasznos (28.8 TiB nyers). EC-nél: 64 * 0.7 = 44.8 TiB használt, szabad = 19.2 TiB hasznos (28.8 TiB nyers). A recovery headroom a nyers szabad kapacitás; egy OSD kiesésekor 8 TiB nyers adat helyreállításához legalább 8 TiB szabad nyers kell replikációnál, tehát a 28.8 TiB elegendő, de a 85% full ratio alatt kell maradni.

  2. Példa parancsok:

# lab-ceph-mon01
sudo -u ceph ceph osd pool create lab-cephfs-metadata 64 64
sudo -u ceph ceph osd pool create lab-cephfs-data 256 256
sudo -u ceph ceph fs new lab-cephfs lab-cephfs-metadata lab-cephfs-data
# lab-client01
sudo mkdir /mnt/lab-cephfs
sudo mount -t ceph 192.0.2.11,192.0.2.12,192.0.2.13:/ /mnt/lab-cephfs -o name=admin,secretfile=/etc/ceph/admin.secret
sudo dd if=/dev/zero of=/mnt/lab-cephfs/lab-test.bin bs=1M count=1
# RGW S3
sudo apt install s3cmd -y
s3cmd --configure --host=lab-ceph-rgw01 --host-bucket=lab-test-bucket --access_key=lab-access --secret_key=lab-secret
s3cmd mb s3://lab-test-bucket
echo test | s3cmd put - s3://lab-test-bucket/lab-object.txt
  1. Az OSD leállítása:
# lab-ceph-osd01
sudo systemctl stop ceph-osd@0
# lab-ceph-mon01
sudo -u ceph ceph status

Várt kimenet: degraded, undersized, recovery folyamatban. Az OSD újraindítása után a ceph status HEALTH_OK lesz, amikor a recovery kész. Lassú recovery esetén osd_max_backfills=1, osd_recovery_max_active=2, osd_recovery_sleep=0.1 beállítás csökkenti a client I/O-ra gyakorolt hatást, de növeli a recovery időt.

54.3.10 Rövid összefoglaló

A Ceph egyetlen RADOS objekt tárolóra épít block (RBD), file (CephFS) és object (RGW) hozzáférést. A monitor quorum a cluster mapet tartja, az OSD-k a PG-ket replikálják vagy erasure codinggal kódolják a CRUSH által kiszámított failure domainek szerint. A replikáció egyszerűbb, de nagyobb kapacitás overhead; az EC jobb kapacitás, de drágább write. A recovery headroom a szabad kapacitás és I/O sáv, amely nélkül a full pool leállítja az írást. A CSI és a QEMU librbd adja a VM/container storage pathot; a block SAN alacsony latency, a file NAS megosztást, az object REST skálázhatóságot ad.

Továbbhasznált definíciók:

  • Placement Group (PG): objektumok logikai csoportja, amely a pool OSD-kre való kiosztásának atomi egysége.
  • Recovery headroom: az a szabad kapacitás és I/O sáv, amely lehetővé teszi a PG-k helyreállítását anélkül, hogy a client I/O-t megfojtanák.
  • CRUSH: pseudo-random elhelyezési algoritmus, amely a cluster mapból számítja ki a PG replikáinak OSD helyét.
