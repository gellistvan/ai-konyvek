30.3 Network namespace, veth, bridge és tap

30.3.1 Miért kell külön hálózati verem?

Egy konténerben a 127.0.0.1 nem a hostot jelenti, egy VM hálózati kártyája pedig nem egyszerűen „egy új IP-cím a hoston”. Üzemeltetéskor azt kell megmondanunk, melyik hálózati verem hozza meg az útvonalválasztási döntést, és milyen objektum viszi tovább a csomagot a következő veremhez.

A hálózati névtér (network namespace, netns) a Linux hálózati állapotának elkülönített példánya. Saját hálózati interfészekkel, loopbackkel, útvonaltáblákkal, szomszédtáblákkal, hálózati tűzfalszabályokkal és socket-portnévtérrel rendelkezik. Emiatt két namespace-ben külön folyamat hallgathat ugyanazon a TCP-porton.

Ez nem külön kernel: a namespace-ek közös hoston, közös kernelhibatartományban működnek. Nem kapnak automatikusan külön fájlrendszert, CPU-keretet vagy teljes biztonsági határt.

C++-kapcsolatként: a socket a létrehozásakor kapcsolódik hálózati namespace-hez. Egy már megnyitott socket nem költözik át attól, hogy a szál később másik namespace-be lép. Az erőforrás élettartama és a végrehajtási környezet váltása külön kérdés.

30.3.2 A négy építőelem és a határaik

Objektum Feladat Amit önmagában nem biztosít
Network namespace Saját hálózati verem és állapot Összeköttetés más namespace-szel
veth pár Két összekapcsolt, Ethernet-jellegű virtuális interfész IP-cím, útvonal vagy kapcsolás több végpont között
Linux bridge Ethernet-keretek kapcsolása portok között IP-routing vagy címfordítás
TAP / TUN Kernel és felhasználói program közötti csomagátadás Teljes VM- vagy VPN-megvalósítás

A virtuális Ethernet-pár (virtual Ethernet pair, veth) egyik végén kiküldött keret a másik vég fogadási oldalán jelenik meg. A két vég lehet külön namespace-ben; mindegyik vég egyszerre pontosan egy namespace-hez tartozik.

A TAP Ethernet-kereteket ad át egy felhasználói térben futó programnak, a TUN pedig IP-csomagokat, Ethernet-fejléc nélkül. A program tipikusan a /dev/net/tun megnyitásával és megfelelő ioctl művelettel kapcsolódik hozzájuk:

  • TAP-ról olvasáskor a program a kernel által az interfészre kiküldött keretet kapja;
  • TAP-ra íráskor a program fogadott keretet injektál a kernelbe;
  • TUN esetén ugyanez IP-csomagokkal történik, ezért TUN nem közönséges Ethernet-bridge-port.

A bridge működése az előző bridge-alfejezet szerinti. Most az a fontos, hogy egy bridge és közvetlen portjai ugyanabban a namespace-ben legyenek. A másik namespace-hez a veth pár túlsó vége kapcsolódik.

30.3.3 Laborcontract és topológia

Profil: Ubuntu Server 24.04 LTS amd64, lab-net01 izolált VM.
Fiók: labadmin, UID 1000; módosításhoz sudo, UID 0.
Előfeltétel: iproute2, iputils-ping, libc-bin, procps; működő VM-konzol. A management interfészhez nem nyúlunk.

Az egy interfész–egy állapotgazda szabály itt is érvényes. A labor lab-* interfészeit kizárólag az alábbi kézi parancssor kezeli; a host hálózatkezelőjének profiljai nem illeszkedhetnek rájuk. Ezt indulás előtt ellenőrizd a meglévő konfigurációban. Ne a hálózatkezelő globális leállításával teremts helyet a labornak.

30.3.3.1 Előellenőrzés és létrehozás

A verziókat a tényleges VM-ről rögzítsd; az alábbi anyag nem állít konkrét csomagkiadáson végrehajtott tesztet.

# Target: lab-net01; labadmin, UID 1000.
test "$(hostname -s)" = lab-net01 || exit 1
test "$(id -u)" = 1000 || exit 1

uname -r
ip -Version
dpkg-query -W iproute2 iputils-ping libc-bin procps systemd
ip -br address
ip -4 route show table all
ip netns list

A 10.203.148.0/24 nem ütközhet a VM, VPN vagy más labor használt tartományával. Meglévő namespace-ek címzését és útvonalait is ellenőrizd. Konfliktus esetén állj meg, és módosítsd következetesen a teljes címtervet.

A létrehozás előbb ellenőrzi a nevek szabadságát. Hiba után nem folytatjuk vakon; a részlegesen létrejött állapotot a takarítási terv szerint bontjuk vissza.

# Target: lab-net01; labadmin -> sudo, UID 0.
sudo bash <<'BASH'
set -eu

for ns in lab-a lab-b; do
    if ip netns list | grep -q "^${ns}\([[:space:]]\|$\)"; then
        echo "Foglalt namespace: $ns" >&2
        exit 1
    fi
done
for dev in lab-br0 lab-va lab-vb lab-a0 lab-b0 lab-tap0; do
    if ip link show dev "$dev" >/dev/null 2>&1; then
        echo "Foglalt interfésznév: $dev" >&2
        exit 1
    fi
done
test ! -e /etc/netns/lab-a

ip netns add lab-a
ip netns add lab-b

ip link add name lab-br0 type bridge stp_state 0
ip address add 10.203.148.1/24 dev lab-br0
ip link set dev lab-br0 up

ip link add lab-va type veth peer name lab-a0
ip link add lab-vb type veth peer name lab-b0
ip link set dev lab-a0 netns lab-a
ip link set dev lab-b0 netns lab-b

ip link set dev lab-va master lab-br0
ip link set dev lab-vb master lab-br0
ip link set dev lab-va up
ip link set dev lab-vb up

ip -n lab-a link set dev lo up
ip -n lab-b link set dev lo up
ip -n lab-a address add 10.203.148.11/24 dev lab-a0
ip -n lab-b address add 10.203.148.12/24 dev lab-b0
ip -n lab-a link set dev lab-a0 up
ip -n lab-b link set dev lab-b0 up
BASH

Az STP kikapcsolása itt a szándékosan hurokmentes, uplink nélküli topológia tulajdonsága, nem általános üzemeltetési ajánlás.

A namespace-ben kezdetben létező lo interfészt külön fel kell hozni. A host működő loopbackje nem helyettesíti azt.

30.3.3.2 Ellenőrzés és a csomagút levezetése

# Target: lab-net01; megfigyelés UID 1000, namespace-műveletek sudo/UID 0.
sudo ip -n lab-a -br address
sudo ip -n lab-a route show
sudo ip -n lab-b -br address
bridge link show master lab-br0

sudo ip netns exec lab-a ping -n -c 3 -W 1 10.203.148.12
sudo ip netns exec lab-a ping -n -c 3 -W 1 10.203.148.1
ping -n -c 3 -W 1 10.203.148.11

sudo ip -n lab-a neighbor show
bridge fdb show br lab-br0

Várt eredmény, nem mért kimenet: a pingek sikeresek; lab-a útvonaltáblájában szerepel a közvetlen 10.203.148.0/24 hálózat, de nincs default route. A szomszédtáblában megjelenik a cél MAC-címe, a bridge FDB-jében pedig a megfelelő porton megtanult MAC. Az állapot lehet például REACHABLE vagy később STALE; egyik pillanatnyi értéket sem szabad örök invariánsnak tekinteni.

A 10.203.148.11 → 10.203.148.12 adatút:

  1. A lab-a socketje a lab-a útvonaltábláját használja.
  2. A közvetlen hálózati útvonal miatt a cél saját MAC-címét keresi ARP-val, nem a hostot használja átjárónak.
  3. A keret kilép lab-a0 interfészen, és megérkezik lab-va fogadási oldalára.
  4. lab-va bridge-portként átadja a keretet lab-br0 kapcsolási adatútjának.
  5. A bridge a cél MAC-cím alapján lab-vb felé továbbít; az ARP broadcastot a megfelelő többi porton is kiküldi.
  6. A keret lab-b0 interfészen belép lab-b hálózati vermébe.

Itt nincs hostoldali IP-routing, ezért a sikerhez nem kell net.ipv4.ip_forward=1. Bridge-tűzfalszabály vagy a br_netfilter integráció ugyanakkor befolyásolhatja a forgalmat.

30.3.4 Hogyan kapcsolódik ehhez VM és konténer?

A tipikus konténer hálózati végpontja egy namespace-be helyezett veth vég. A másik vég a host bridge-éhez kapcsolódhat. A konténerindító rendszer ezen felül életciklust, címkiosztást és szabályokat kezel.

A VM ezzel szemben saját kernelt és hálózati vermet futtat. Egy lehetséges adatút:

Forrás → cél Adatút
Konténer → konténer Namespace → veth → host bridge → veth → namespace
VM → konténer Guest NIC → virtuális eszköz backendje → TAP → bridge → veth → namespace
Host → konténer Host IP-verem → bridge helyi végpont → veth → namespace

A QEMU TAP-backendet használhat; például vhost-net gyorsítással az adatút egy része nem a QEMU felhasználói folyamatán halad át.

Hozzunk létre egy TAP-portot, VM indítása nélkül:

# Target: lab-net01; labadmin -> sudo/UID 0.
# A TAP-hoz kapcsolódásra a labadmin UID 1000 kap jogosultságot.
sudo ip tuntap add dev lab-tap0 mode tap user 1000
sudo ip link set dev lab-tap0 master lab-br0
sudo ip link set dev lab-tap0 up
sudo ip tuntap show dev lab-tap0
ip -details link show dev lab-tap0

Postcondition: létezik egy tartós TAP-objektum a bridge-en. Program még nem csatlakozott hozzá; NO-CARRIER ezért nem feltétlenül konfigurációs hiba. Ez nem bizonyít működő VM-hálózatot. A persist itt a fájlleíró bezárásán túli élettartamot jelenti, nem reboot utáni újraépítést.

30.3.5 Loopback, névfeloldás és konfigurációgazda

A network namespace önmagában nem választja szét az /etc/resolv.conf vagy /etc/hosts fájlokat. Az ip netns exec azonban az /etc/netns/NÉV/ megfelelő fájljait külön mount namespace segítségével a megszokott helyükre tudja csatolni.

Készítsünk szándékos DNS-hibafix­túrát: a hoston esetleg működő 127.0.0.53 resolvercímet átvisszük egy olyan namespace-be, ahol nincs DNS-szerver.

# Target: lab-net01; labadmin -> sudo/UID 0.
sudo install -d -m 0755 /etc/netns/lab-a
sudo tee /etc/netns/lab-a/hosts >/dev/null <<'EOF'
127.0.0.1 localhost
10.203.148.12 lab-b.test
EOF
sudo tee /etc/netns/lab-a/resolv.conf >/dev/null <<'EOF'
nameserver 127.0.0.53
options timeout:1 attempts:1
EOF

sudo ip netns exec lab-a getent -s files hosts lab-b.test
sudo ip netns exec lab-a cat /etc/resolv.conf
sudo ip netns exec lab-a ss -lun
sudo ip netns exec lab-a getent -s dns ahostsv4 lab-b.test

Várt eredmény: a fájlalapú feloldás sikeres, a kényszerített DNS-feloldás sikertelen. A két eredmény nem ellentmondás: külön névfeloldási forrást vizsgálunk.

A helyes DNS-javítás egy ténylegesen elérhető resolver és szükség esetén útvonal biztosítása, vagy resolver indítása az adott namespace-ben. A host loopbackcímének bemásolása nem ilyen javítás.

A getent -s itt tudatos ellenpróba. Egy szokásos alkalmazás az NSS-konfigurációt követi; például egy megosztott /run alatti Unix-socketen elérhető hostszolgáltatás módosíthatja a feloldási utat. A network namespace nem teljes fájlrendszer-izoláció.

30.3.6 Namespaced és hostszintű sysctl

A kernelparamétereknél nem elég azt nézni, hogy a parancsot namespace-ben futtatjuk-e.

# Target: lab-net01; csak olvasás; namespace-belépés sudo/UID 0.
sysctl net.ipv4.ip_forward vm.swappiness
sudo ip netns exec lab-a sysctl net.ipv4.ip_forward vm.swappiness

A net.ipv4.ip_forward namespace-enkénti hálózati állapot. A vm.swappiness viszont hostszintű memóriakezelési beállítás: az ip netns exec nem teszi helyivé. Más /proc/sys/net/ paraméterek hatóköre kernelverzió- és implementációfüggő is lehet; ne következtess pusztán a névből.

Újabb hálózati rendszerek építésekor minden módosított sysctlhez rögzítsd: hatóköre, tulajdonosa, eredeti értéke, szükségessége és rollbackje.

30.3.8 Feladatok

  1. Magyarázó: vezesd le a lab-a → lab-b és a lab-a → 10.203.148.1 csomagutat. Melyik esetben kap szerepet a host IP-verme?

  2. Adminisztrációs: hozd létre a labort és a TAP-portot. Igazold külön az interfészállapotot, a kapcsolási útvonalat és a fájlalapú névfeloldást. Mi maradna meg reboot után?

  3. Diagnosztikai/recovery: a konzol megtartása mellett idézz elő linkhibát:

    # Target: lab-net01; labadmin -> sudo/UID 0.
sudo ip -n lab-b link set dev lab-b0 down

    Gyűjts bizonyítékot, javíts egyetlen változtatással, majd ismételd meg az eredeti kapcsolati próbát. Ezután külön magyarázd meg a DNS-fixture hibáját.

30.3.9 Megoldások

  1. A namespace-ek közötti csomagút bridge-kapcsolás; a host IP-verme nem route-olja a csomagot. A .1 cím viszont a bridge helyi végpontjáé, így a keret a host IP-verméhez kerül. Postcondition: külön szerepel a magyarázatban a kapcsolás és a helyi IP-kézbesítés.

  2. Az ip -n …, bridge link, FDB és ping együtt adnak bizonyítékot. A getent -s files csak a fájlalapú feloldást igazolja. Reboot után az /etc/netns/lab-a/ fájljai megmaradhatnak, de az itt kézzel létrehozott namespace-eket és linkeket újra kell építeni. Postcondition: nincs összekeverve a tárolt fájl és a működő hálózat.

  3. A ping hibája mellett vizsgáld mindkét veth-véget; egy régi FDB-bejegyzés nem bizonyít élő kapcsolatot. A javítás:

    # Target: lab-net01; labadmin -> sudo/UID 0.
sudo ip -n lab-b link set dev lab-b0 up
sudo ip netns exec lab-a ping -n -c 3 -W 1 10.203.148.12

    Postcondition: a numerikus kapcsolat helyreáll. A DNS ettől még hibás, mert a namespace saját 127.0.0.53 címén nincs resolver; ez külön gyökérok.

30.3.10 Rollback és takarítás

Előbb ellenőrizd a namespace-ekben futó folyamatokat:

# Target: lab-net01; labadmin -> sudo/UID 0.
sudo ip netns pids lab-a
sudo ip netns pids lab-b

A laborban üres listát várunk. Nem üres listánál előbb azonosítsd és szabályosan állítsd le a saját folyamatokat. A név törlése nem feltétlenül szünteti meg az élő hivatkozásokkal rendelkező namespace-t.

A teljesen felépített labor bontása:

# Target: lab-net01; labadmin -> sudo/UID 0.
sudo ip tuntap del dev lab-tap0 mode tap
sudo ip link delete dev lab-va
sudo ip link delete dev lab-vb
sudo ip link delete dev lab-br0
sudo ip netns delete lab-a
sudo ip netns delete lab-b
sudo rm -- /etc/netns/lab-a/hosts /etc/netns/lab-a/resolv.conf
sudo rmdir -- /etc/netns/lab-a

ip netns list
ip -br link
ip -4 route show table all

Részleges létrehozás után csak az igazoltan létrejött saját objektumok bontási sorait használd. Végfeltétel: a felsorolt namespace-ek, interfészek és konfigurációfájlok eltűntek; a management hálózat változatlan.

30.3.11 Rövid összefoglaló

A network namespace saját hálózati állapotot ad, de nem külön kernelt és nem automatikusan külön konfigurációs fájlokat. A namespace-ek összekötését külön objektumok biztosítják. A laborban a veth párok Ethernet-kereteket visznek a host bridge-éhez, amely IP-forwarding nélkül kapcsol a végpontok között. A TAP egy VM-backendhez vagy más programhoz kapcsolódhat; létezése önmagában nem bizonyít működő adatutat. A loopback, a DNS-feloldás és a sysctl hatókör külön ellenőrzendő. A diagnózis alapja mindig a konkrét forrás, cél, namespace és interfészlánc, nem pusztán egy sikeres vagy sikertelen ping.

  • Network namespace: elkülönített Linux hálózati állapot.
  • Veth pár: két összekapcsolt virtuális Ethernet-interfész.
  • TAP/TUN: Ethernet-, illetve IP-szintű kernel–program csomaginterfész.

30.3.12 Források és ellenőrzési hiányok

Az alábbiak dokumentációs kiindulópontok, nem ebben a munkamenetben olvasott vagy ellenőrzött források:

  • network_namespaces(7) — izolált hálózati állapot és élettartam.
  • ip-netns(8) — név szerinti namespace-kezelés és /etc/netns.
  • veth(4) — veth párok működése.
  • Linux kernel: Universal TUN/TAP device driver — felhasználói csomaginterfész.
  • Linux kernel: IP sysctl — hálózati kernelparaméterek.

Ellenőrzési hiányok: a konkrét Ubuntu kernel- és csomagverzió, a helyi hálózatkezelő illesztési szabályai, a bridge-szűrés és az egyes sysctlök adott kernelbeli hatóköre helyi ellenőrzést igényel. A parancsok és kimeneti elvárások nem tényleges futtatási jegyzőkönyv.
