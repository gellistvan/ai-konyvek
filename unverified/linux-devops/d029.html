6.4 InfiniBand, RoCE, RDMA és speciális hálózatok

6.4.1 Motiváció

A hagyományos TCP alapú hálózati adatút jól ismert: a C++ backend send() hívást ad, a kernel átmásolja a felhasználói puffert a kernelbufferbe, a TCP-stack hozzáadja a fejlécet, a hálózati interfész (NIC) DMA-val átmozgatja, a fogadó oldalon interrupt, recv, majd újabb másolás történik. Minden tranzakciónál CPU-munka, memóriasávszélesség és több mikroszekundum késleltetés keletkezik. Egy 10 vagy 100 GbE linket akár több mag is csak a TCP-feldolgozásra foglalhat le.

A Remote Direct Memory Access (RDMA) ezt a réteget úgy kerüli meg, hogy a hálózati adapter közvetlenül ír vagy olvas a távoli gép regisztrált memóriaterületéből, az alkalmazás CPU-jának közreműködése nélkül. Ez azonban nem egyszerűen egy „gyorsabb NIC” beszerzése: a memóriaregisztráció, a speciális fabric és a torlódásvezérlés feltételeket szab. Az elosztott kulcs-érték tárak, HPC MPI, NVMe-oF storage és GPU-klaszterek üzemeltetéséhez ezért az RDMA-t rendszerszinten, nem pedig csak API-szinten kell érteni.

6.4.2 Definíció és működés

6.4.2.1 RDMA képesség és a hagyományos TCP adatút

Az RDMA definíciója: olyan hálózati kommunikáció, amelyben a hálózati interfész a távoli alkalmazás memóriájába kontroller (NIC/HCA) DMA-művelettel ér el, miközben a távoli CPU nem vesz részt a másolásban, és a kernel sem végez protokollfeldolgozást a tranzakció kritikus útján. A hagyományos TCP adatút:

felhasználói puffer → kernel socket buffer → TCP/IP → NIC TX ring
→ hálózat → NIC RX ring → kernel TCP/IP → socket buffer → recv() → felhasználói puffer

Az RDMA adatút ezzel szemben:

regisztrált memóriarégió → QP work request → NIC DMA read/write
→ távoli regisztrált memóriarégió → Completion Queue (CQ) befejezés

Nincs kernelbe másolás, nincs interrupt a távoli CPU-n, nincs context switch. Az RDMA kommunikáció építőelemei:

  • Queue Pair (QP): a küldő és fogadó munkaelemek várakozási sora. Minden QP-hez tartozik egy Send Queue (SQ) és egy Receive Queue (RQ). A befejezett műveleteket egy Completion Queue (CQ) közli.
  • Memory Region (MR): regisztrált, a hálózati adapter által elérhető memóriatartomány. A regisztráció során az operációs rendszer vagy a driver rögzíti (pinning) a lapokat, leképezi a virtuális címeket, és lkey (local key) / rkey (remote key) párt ad vissza. Az alkalmazás a work requestben ezt a kulcsot adja meg.

Ez a modell a NVMe, SCSI, queue és host controller alfejezetben megismert submission/completion queue párok általánosítása: ott az NVMe parancsok, itt az alkalmazás RDMA work requestjei töltik a gyűrűket, de a DMA-alapú, alacsony overheadű elérés elve ugyanaz.

A memory registration azért feltétel, mert a NIC DMA-ja hosszú ideig, az alkalmazás CPU-jától függetlenül hivatkozhat a lapokra. Ha a lap kikerülne a swapre, vagy a címleképezés megváltozna, a DMA hibás adatot érne el. C++ analógia: ha egy std::array<char, 4096> data() mutatóját adjuk át egy aszinkron műveletnek, a puffer élettartamának és méretének stabilnak kell maradnia; egy std::vector push_back utáni reallokáció ugyanúgy érvényteleníti a regisztrált régiót, mint egy RDMA művelet közbeni lapozás. Ez a zero-copy előnyért cserébe erős élettartam-fegyelmet kíván.

6.4.2.2 InfiniBand fabric

Az InfiniBand (IB) nem Ethernet: saját link layer, saját keretek, saját eszközök. Az IB fabricelemet HCA (Host Channel Adapter) és switch alkotja; a subnetet egy Subnet Manager (SM) konfigurálja: kiosztja a LID (Local Identifier) azonosítókat, beállítja az útvonalakat, kezeli a kaszkádot. Az IB link réteg credit-based flow control-t használ: a küldő csak akkor adhat, ha a fogadó oldali buffer garantáltan szabad. Emiatt az IB fabric lossless: nincs csomagvesztés a forgalom torlódása miatt, csak hardverhiba esetén. A Virtual Lane (VL) mechanizmus több független forgalmi osztályt visz párhuzamosan; a Service Level (SL) a csomag prioritását jelöli. Ez a hardveres forgalmi garancia alapozza meg az RDMA determinisztikus késleltetését.

6.4.2.3 RoCE és iWARP

Az RDMA Ethernet alapú adatközpontokban is elérhető. Két fontos protokollcsalád:

  • RDMA over Converged Ethernet (RoCE): RoCEv1 közvetlenül Ethernet keretben (EtherType), nem routolható; a RoCEv2 IP és UDP réteget ad hozzá, így IP-routing szempontból szállítható. A RoCEv2 az IB transport header-t helyezi UDP datagramba, jellemzően 4791 portra. Előnye a meglévő Ethernet infrastruktúra, de a hálózatnak lossless-nek kell lennie, különben a teljesítmény összeomlik.
  • iWARP (Internet Wide Area RDMA Protocol): az RDMA-t TCP kapcsolat felett szállítja, ezért nem igényel lossless fabricet, veszteséges WAN is elviseli. A TCP-stack miatt azonban nagyobb a szoftveres overhead, és a memory semantics nem minden esetben teljesen zero-copy.

A fő különbségek:

Tulajdonság InfiniBand RoCEv2 iWARP
Link IB fabric Ethernet/IP/UDP Ethernet/IP/TCP
Lossless követelmény Igen (credit) Igen (PFC/ECN) Nem
Késleltetés Alacsony Alacsony Közepes
Routing LID/GID, SM IP routolható IP routolható
Adaptáció Komplett IB switch Ethernet switch + config Ethernet bárhol

6.4.2.4 PFC/ECN és congestion management

A RoCEv2 elveszített csomag esetén rosszul teljesít, mert a retransmission az alkalmazás vagy a transport réteg szintjén drága. Ezért az Ethernet hálózatot lossless-sé kell tenni legalább a RoCE forgalom prioritásosztályán. Két mechanizmus:

  • Priority Flow Control (PFC) IEEE 802.1Qbb: egy switch, amikor a fogadó buffer eléri a küszöböt, „pause” keretet küld a szomszédjának a megjelölt 802.1p priority osztályra. Az adott prioritás forgalmát leállítja; ez head-of-line blockingot okozhat, és a pause terjedhet. A PFC-t az összes érintett switchen és NIC-en per-priority kell konfigurálni; rossz beállítása holtpontot eredményezhet.
  • Explicit Congestion Notification (ECN): a switch az IP fejléc ECN bitjeit megjelöli, ha a queue hossza meghaladja a küszöböt; a fogadó a jelzést visszaküldi a küldőnek, aki csökkenti a sebességet (például DCQCN algoritmussal). Az ECN a PFC-nél finomabb, nem blokkolja a teljes linket, ezért a modern RoCE hálózatokon gyakran együtt használják, gondosan hangolva.

A lossless fabric fogalma tehát nem azt jelenti, hogy bármilyen hiba nélkül működik, hanem hogy a tervezett túlterheléskor nem veszít csomagot, hanem backpressure-t alkalmaz. A C++ alkalmazásban ez a várakozási sor analógiája: a PFC olyan, mintha a szálbiztos üzenetsorba full write blockolna, az ECN pedig mint a visszajelzéses rate limiting.

6.4.2.5 NVMe-oF és storage fabric

A NVMe, SCSI, queue és host controller alfejezetben látott NVMe submission/completion queue párok nem csak PCIe lokális buszon működnek. A Non-Volatile Memory Express over Fabrics (NVMe-oF) az NVMe parancsokat hálózati transportba csomagolja: RDMA (RoCEv2, IB), TCP, vagy Fibre Channel. Az NVMe/RDMA a legkisebb késleltetést adja, mert a parancs és az adat közvetlenül a target memóriájába kerül, kernel nélkül. Az NVMe/TCP egyszerűbb, standard Etherneten fut, de magasabb processzorköltséggel. A storage fabric tehát ugyanazt a lossless infrastruktúrát használja, mint a HPC RDMA; ezért a hálózati tervezésnél a storage és compute forgalmat együtt kell vizsgálni.

6.4.2.6 HPC/GPU interconnect

A HPC klaszterekben az InfiniBand a de facto interconnect; az MPI library a QP-ket használja a tagok közötti üzenetküldésre, gyakran RDMA-val. A GPU-klaszterekben a node-on belüli kapcsolatot NVLink/NVSwitch biztosítja, a node-ok közötti kommunikációra pedig IB/RoCE vagy specializált fabric (például HPE Slingshot, Cray) szolgál. A GPU direct RDMA (GDR) lehetővé teszi, hogy a NIC közvetlenül a GPU memóriába írjon, elkerülve a CPU memóriába másolást. Ez a téma a jelen alfejezet hatáskörén túlmutat, de a memory registration és lossless követelmény ugyanaz: a GPU memóriát is regisztrálni kell és pinnelni, a hálózatnak pedig congestion mentesnek kell lennie. Az aktuális GPU interconnect specifikációkat a gyártói dokumentációban kell ellenőrizni.

6.4.3 Kidolgozott példa

A laborban nincs fizikai RDMA NIC; az Ubuntu Server 24.04 LTS labVM általában csak egy virtuális Ethernet NIC-et kap. Ezért a következő példa egy elkülönített, illusztratív lab-rdma01 labhoston futtatandó, ahol egy mlx5_0 RDMA eszköz elérhető, mert a feladat célja a diagnosztikai parancsok bemutatása. A parancsok nem módosítanak állapotot, így nincs szükség rollbackre.

Input/topology: lab-rdma01 (UID 1000, labops), egy mlx5_0 RoCEv2 NIC eth2 netdevvel, IP 192.0.2.10/24. A lab-rdma02 a másik oldal.

Desired state: a mlx5_0 port ACTIVE állapotú, a rdma link mutatja a linkup állapotot, és a memóriazár korlát unlimited.

Ellenőrző parancsok:

#!/usr/bin/env bash
set -euo pipefail

# Labhost: lab-rdma01, UID 1000, labops; diagnosztika, nem módosít.
echo "== rdma link =="
rdma link show || true

echo "== ibv_devinfo (verbosely) =="
if command -v ibv_devinfo >/dev/null 2>&1; then
    ibv_devinfo -v || true
else
    echo "ibv_devinfo nincs telepítve (rdma-core/ibverbs-utils)"
fi

echo "== sysfs state =="
for dev in /sys/class/infiniband/*; do
    [ -e "$dev" ] || continue
    dev_name=$(basename "$dev")
    echo "device=$dev_name"
    cat "$dev/ports/1/state" 2>/dev/null || echo "nincs port state"
    cat "$dev/ports/1/phys_state" 2>/dev/null || true
done

echo "== netdev ring buffer =="
ip -br link show
ethtool -g eth2 || true

echo "== memlock limit =="
ulimit -l

Várt kimenet illusztratív fixture alapján (fizikai mérés nélkül): - rdma link show egy sort ad mlx5_0/1 state ACTIVE physical_state LINK_UP. - ibv_devinfo -v megjeleníti a hca_id: mlx5_0, transport: InfiniBand, port: 1, state: PORT_ACTIVE (4), max_qp_wr, max_mr_size mezőket. - A sysfs state 4: ACTIVE lehet. - ulimit -l unlimited kell legyen a memory registrationhez; ha 64 vagy más alacsony érték, a regisztráció Cannot allocate memory hibát ad.

Ha a fizikai RDMA hiányzik, a rdma link show nem ír ki sort, az ibv_devinfo nem talál eszközt. Ez a postcondition: a parancsoknak hiba nélkül kell lefutniuk, de a hiányzó eszköz jelzése elfogadott diagnosztikai eredmény.

6.4.4 Hibák és ellenpróbák

Tünet: egy RoCEv2 alapú C++ szolgáltatás nem tud regisztrálni memóriát; a hiba Cannot register memory vagy ibv_reg_mr failed: Cannot allocate memory.
Hipotézis: az ulimit -l (max locked memory) alacsony, a memóriapinning limitbe ütközik.
Adatgyűjtés: ulimit -l, /etc/security/limits.conf, systemd unit LimitMEMLOCK.
Egy változtatás: a service unitjában állítsd be LimitMEMLOCK=infinity, majd systemctl daemon-reload és restart.
Ellenőrzés: ulimit -l a folyamatban unlimited, a regisztráció sikeres.
Rollback: a unit korábbi LimitMEMLOCK értékét visszaállítani.
Ellenpróba: a LimitMEMLOCK=infinity nem oldja meg, ha a cgroup v2 memory.lock limitje is alacsony; azt is vizsgálni kell.

Tünet: RoCEv2 benchmark alacsony throughput, magas tail latency, ethtool -S eth2 pause keretek vagy ECN jelzések nőnek.
Hipotézis: nincs PFC vagy ECN konfigurálva a switch oldalon, vagy a queue buffer túl kicsi.
Adatgyűjtés: ethtool -S eth2 | grep -E 'ecn|pause|tx_prio', ethtool -g eth2, switch telemetria.
Egy változtatás: a PFC-t csak a kijelölt 802.1p priority-ra (például 3) engedélyezni, és a switch buffer küszöböt beállítani; az összes switch és NIC beállítása után.
Ellenőrzés: tesztek, hogy a veszteség nulla, a PFC pause keretek csak a terhelési csúcsokon jelennek meg.
Rollback: PFC letiltása, visszaállítás.
Ellenpróba: a PFC bekapcsolása head-of-line blockingot okozhat; a hálózati mérést a tényleges workloaddal kell validálni, nem csak pinggel.

Tünet: NVMe-oF initiator nvme discover -t rdma -a 192.0.2.10 -s 4420 timeout.
Hipotézis: RoCE version mismatch (target RoCEv1, initiator RoCEv2), rossz IP-routing vagy hiányzó PKey.
Adatgyűjtés: rdma link show, ibv_devinfo -v, ip route, tűzfalszabályok.
Egy változtatás: a target RoCEv2 beállítását ellenőrizni, a 4791 UDP portot a tűzfalon engedélyezni.
Ellenőrzés: nvme discover sikeres, a target megjelenik.
Rollback: a tűzfalszabály és a target verzió visszaállítása.

6.4.5 Feladatok

  1. Magyarázó feladat. Hasonlítsa össze a TCP és az RDMA adatútvonalat egy 4 KiB üzenet küldésekor. Sorolja fel az RDMA memory registration lépéseit, és magyarázza el, miért szükséges a lapok pinningje. Válaszában ne tanítsa újra a C++ szintaxist, de használhat C++ élettartam-analógiát.

  2. Adminisztrációs/konfigurációs feladat. Írjon egy bash szkriptet check_rdma.sh néven, amely a lab-rdma01 hoston (UID 1000, labops) ellenőrzi: (a) van-e bármilyen RDMA eszköz a rdma link kimenetében; (b) az ulimit -l korlát unlimited; (c) ha van mlx5_0, akkor a sysfs ports/1/state értéke 4: ACTIVE. A szkript hibát jelezzen nem nulla exit kóddal, ha valamelyik feltétel nem teljesül. A szkript ne módosítson rendszerállapotot.

  3. Diagnosztikai/failure/recovery feladat. A lab-rdma01 hoston az NVMe-oF initiator nem találja a targetet a nvme discover -t rdma -a 192.0.2.10 -s 4420 paranccsal. A hibakeresés során az ibv_devinfo -v azt mutatja, hogy a helyi NIC RoCEv2, de a target oldalán a napló szerint a transport RoCEv1. Írja le a diagnosztikai lépéseket, és adja meg a target oldali javító parancsokat (root felhasználóval, a kijelölt lab-target01 hoston), beleértve az ellenőrzést és a rollbacket. A parancsok ne tartalmazzanak éles jelszót vagy titkot.

6.4.6 Megoldások

  1. A TCP út: application buffer → kernel copy → TCP/IP header → NIC TX ring → network → NIC RX ring → kernel TCP/IP → receive buffer → application copy. Az RDMA út: registered MR → QP WR → NIC DMA read/write → remote registered MR → CQ. A memory registration: az alkalmazás lefoglal egy stabil, átmeneti lapozásmentes puffert; meghívja az ibv_reg_mr-t; a driver rögzíti a lapokat (pinning) így a lapok nem íródnak ki swapre; visszaad lkey/rkey-t. A pinning azért szükséges, mert a NIC DMA a CPU-tól függetlenül hivatkozik a fizikai lapokra; ha a lap kikerülne a swapre, a DMA hibás adatot érne el. C++ analóg: egy std::array<char, 4096> adatát adjuk aszinkron műveletnek; a puffer nem mozdulhat a művelet alatt, ahogy a std::vector reallokáció sem megengedett.

Postcondition: a tanuló meg tudja különböztetni a két adatútvonalat, és meg tudja indokolni a memory registration szükségességét.

  1. A check_rdma.sh tartalma:
#!/usr/bin/env bash
set -euo pipefail
# Labhost: lab-rdma01, labops UID 1000, nem módosít.
fail=0

echo "== RDMA device presence =="
if ! rdma link show | grep -q 'link'; then
    echo "HIBA: nincs RDMA eszköz" >&2
    fail=1
else
    echo "RDMA eszköz jelen van"
fi

echo "== memlock limit =="
memlock=$(ulimit -l)
if [ "$memlock" != "unlimited" ]; then
    echo "HIBA: ulimit -l nem unlimited (jelenleg: $memlock)" >&2
    fail=1
else
    echo "memlock unlimited"
fi

echo "== sysfs mlx5_0 state =="
if [ -e /sys/class/infiniband/mlx5_0/ports/1/state ]; then
    state=$(cat /sys/class/infiniband/mlx5_0/ports/1/state)
    echo "state=$state"
    if [ "$state" != "4: ACTIVE" ]; then
        echo "HIBA: nem ACTIVE (jelenleg: $state)" >&2
        fail=1
    fi
else
    echo "mlx5_0 port state nem elérhető" >&2
    fail=1
fi

exit "$fail"

Indoklás: a szkript csak olvas; a hibákat nem nulla exit kóddal jelzi, így CI-ben is használható. A grep 'link' a rdma link show kimenetében a link mlx5_0/1 sort keresi; itt a pontos kimeneti formátum illusztratív.

Postcondition: a szkript minden feltétel teljesülése esetén 0-val, egyébként 1-gyel tér vissza, anélkül hogy bármit módosítana.

  1. Diagnosztika: a nvme discover timeout után ellenőrizni kell a helyi rdma link-et, az IP címet, a tűzfalszabályt (nft list ruleset), és a target transport beállítását. A hiba azonosítása: a target RoCEv1 módban van, a lab-rdma01 initiator RoCEv2-t használ. Javítás a targeten (lab-target01, root UID 0):
# Előfeltétel: a target aktuális konfigurációjáról mentés készült:
# cp /etc/nvme-target.conf /etc/nvme-target.conf.rollback
# Módosító parancs: a target RoCEv2 transport beállítása (illusztratív).
# Target: lab-target01, root.
echo "transport=rdma" > /etc/nvme-target.conf
echo "addr_family=ipv4" >> /etc/nvme-target.conf
echo "addr=192.0.2.10" >> /etc/nvme-target.conf
echo "port=4420" >> /etc/nvme-target.conf
echo "rdma_driver=rocev2" >> /etc/nvme-target.conf
# Konfiguráció újratöltése:
systemctl reload nvme-target.service

# Ellenőrzés az initiatoron (lab-rdma01, labops):
nvme discover -t rdma -a 192.0.2.10 -s 4420
# Várt: a target subsystem listában megjelenik.

# Rollback:
cp /etc/nvme-target.conf.rollback /etc/nvme-target.conf
systemctl reload nvme-target.service

Indoklás: a target és initiator transport verziójának egyeznie kell; a tűzfalon az UDP 4791 port engedélyezése is szükséges RoCEv2 esetén. A systemctl reload nem teljes restart; a pontos service és config név a tényleges NVMe-oF implementációtól függ, ezért a példa illusztratív.

Postcondition: az initiator nvme discover sikeresen felsorolja a targetet; a rollback után az eredeti konfiguráció áll helyre.

6.4.7 Rövid összefoglaló

Az RDMA a hagyományos TCP adatúttól abban különbözik, hogy a hálózati adapter közvetlenül ír/olvas a távoli regisztrált memóriába, kernel másolás és távoli CPU interrupt nélkül. A feltétel a memory registration (pinning, lkey/rkey) és a lossless fabric: az InfiniBand credit-based flow control, a RoCEv2 PFC/ECN mechanizmusokkal biztosítja a csomagvesztés nélküli működést. Az NVMe-oF ezt a továbbítást storage parancsokra hasznosítja, a HPC/GPU interconnect pedig a node-ok közötti RDMA-ra.

  • Remote Direct Memory Access (RDMA): hálózati interfész közvetlen hozzáférése a távoli regisztrált memóriaterülethez.
  • Queue Pair (QP) és Completion Queue (CQ): az RDMA work requestek és befejezések kommunikációs modellje.
  • Lossless fabric: olyan hálózat, amely a torlódást csomagvesztés helyett flow control vagy ECN jelzés útján kezeli.

A példákban használt mlx5_0, eth2, nvme-target.service és a kimeneti mezők illusztratív fixture elemek; egyetlen fizikai RDMA mérésnek sem nevezhetők. Külön ellenőrizendő az OFED/Mellanox/NVIDIA verziókompatibilitás, a switch PFC/ECN konfiguráció, az IBTA RoCEv2 specifikáció, az IEEE 802.1Qbb és az NVMe-oF specifikáció pontos hivatkozása.
