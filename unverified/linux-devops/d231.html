47.1 Inventory, SSH, module és playbook

47.1.1 Motiváció

Az előző shell adminisztrációs gyakorlatban megírtuk a loopot, a hibakezelést, a rollbacket és a lockfájlt is. Egy fleet méretű állapotkezelésnél ez a megközelítés törékeny: a script azonnal futtat, nem ellenőrzi, hogy a rendszer már a kívánt állapotban van-e, és a hibás futtatás részleges állapotot hagyhat maga után. Az Ansible ezt a problémát deklaratív modellre cseréli: az inventory megadja a célszámítógépeket, a module leírja a kívánt állapotot, a playbook pedig ezeket kontrollált, ismételhető módon hajtja végre. A cél most az, hogy a szenior C++ fejlesztő a meglévő shell script tudását úgy alakítsa át, hogy megértse, mit ad hozzá az Ansible, és hogyan kerülheti el a nem idempotens parancsok okozta driftet.

47.1.2 Definíció és működés

47.1.2.1 Inventory, group, host és connection

Az inventory az Ansible által kezelt hosztok és csoportjaik leírása. Statikus inventory esetén INI vagy YAML fájl, dinamikus inventory esetén pedig egy külső script vagy plugin szolgáltatja az adatokat. A legalapvetőbb elem a host, például egy lab VM. A hosztokat group nevű logikai csoportokba szervezzük; egy hoszt több csoportba is tartozhat, és a group változók a benne lévő összes hosztra érvényesek. A hoszt-szintű változók viszont felülírják a group szintű értékeket. Az inventoryban megadott ansible_host, ansible_user, ansible_port és ansible_connection változók definiálják a kapcsolat módját. Az ansible_connection alapértelmezés szerint ssh, ezért az Ansible a meglévő OpenSSH infrastruktúrát használja: a host key ellenőrzést, a user key párokat és a config include-okat már a OpenSSH, host trust és admin access részben láttuk.

A legfontosabb különbség a shell scripthez képest, hogy az Ansible soha nem a teljes parancslistát másolja a célgépre, hanem minden egyes module-t külön, a target hoszttal felépített SSH vagy WinRM kapcsolaton keresztül futtat. Egy inventory-részlet:

all:
  children:
    lab_linux:
      hosts:
        lab-node-01:
          ansible_host: 192.0.2.11
        lab-node-02:
          ansible_host: 192.0.2.12
      vars:
        ansible_user: labadmin
        ansible_become: true
        ansible_become_user: root
        ansible_become_method: sudo

Itt a lab_linux group mindkét hosztra vonatkozóan megadja a belépő felhasználót és a privilegizált végrehajtást. A hoszt nevét (lab-node-01) az SSH-kapcsolat is felhasználja, de a ansible_host felülbírálhatja az IP-címet vagy DNS-nevet.

47.1.2.2 SSH, become és secret scope

Az Ansible alapértelmezett kapcsolata SSH-t használ, mind user jelszóval, mind key alapú hitelesítéssel. A become (angolul privilege escalation) mechanizmus a belépő userből a kívánt rendszerfelhasználóvá (jellemzően root) vált. Az ansible_become: true, ansible_become_user: root és ansible_become_method: sudo változók ezt vezérlik. A jelszó scope-ja kritikus: a plaintext user jelszó és become jelszó ne kerüljön az inventory változóba, mert az inventory verziózható fájl, és a jelszó könnyen kiszivárog. A --ask-pass és --ask-become-pass kapcsolókkal interaktív jelszó kérés történik, vagy Ansible Vault használatával titkosított változókban tároljuk a jelszavakat. A C++ fejlesztői párhuzam: ez olyan, mint amikor egy process environmentjébe nem teszünk éles secretet, hanem key management rendszerben tartjuk.

A kapcsolat ellenőrzéséhez az --check és --diff mód használható. --check módban az Ansible csak jelzi, milyen változtatást végezne, de nem hajtja végre. Ez hatalmas különbség a shell scripthez képest, ahol a dry-run-t külön kell leprogramozni.

47.1.2.3 Module, action plugin és collection

A module az Ansible legkisebb önálló munkavégző egysége. Minden module egy adott erőforrást kezel, például az ansible.builtin.apt csomagokat telepít, a ansible.builtin.copy fájlt állít elő, a ansible.builtin.service szolgáltatást indít le/állít meg. A module felelős az idempotens végrehajtásért: mielőtt változtatna, lekérdezi a jelenlegi állapotot, és csak akkor ír, ha a kívánt állapot eltér. Ezzel szemben a ansible.builtin.shell és ansible.builtin.command module minden futtatásnál lefuttatja a megadott parancsot; ezek nem idempotensek, mert nem ellenőrzik az eredményt. Például egy chrony csomag telepítésére az apt module többszöri futtatásnál másodszor ok helyett nem ír semmit, míg a shell: apt install chrony minden egyes lefutásnál ténylegesen végrehajtja a parancsot.

Az action plugin a module lokális oldali komponense: a célgépre általában csak a module kódja kerül, de bizonyos esetekben (például template renderelés) a control node-on is fut kód. A collection modulok, action pluginök, inventory pluginök és egyéb kiegészítők csomagja. Az ansible.builtin a core részét képezi, és az ansible-core csomagban érkezik; a többi modul az Ansible Galaxy-n vagy privát registryn keresztül telepíthető. A teljesen kvalifikált modulnév (FQCN) namespace.collection.module, például community.general.ufw. A C++-os világban ez hasonló a névtér és a library tagoláshoz: a builtin modulok a standard library, a collectionök pedig külső függőségek.

47.1.2.4 Task, play, handler

A task egyetlen module meghívása, esetleg paraméterekkel és name-mel ellátva. A play egy inventory csoportra vagy hosztra vonatkozik, és taskok listáját hajtja végre. A playbook egy vagy több play-t tartalmaz. A handler olyan speciális task, amelyet egy másik task notify hívása indít el, és csak akkor fut le, ha az adott task ténylegesen megváltoztatta a hosztot. A handler tipikus példája a szolgáltatás újraindítása konfiguráció módosulása után. Ez biztosítja, hogy a felesleges újraindítások elmaradjanak.

---
- name: Alap Linux baseline
  hosts: lab_linux
  become: true
  gather_facts: true
  tasks:
    - name: chrony csomag telepítve
      ansible.builtin.apt:
        name: chrony
        state: present
        update_cache: true
      notify: Restart chrony service

    - name: MOTD beállítása
      ansible.builtin.copy:
        content: |
          lab managed node
        dest: /etc/motd
        owner: root
        group: root
        mode: "0644"

  handlers:
    - name: Restart chrony service
      ansible.builtin.service:
        name: chrony
        state: restarted

Ebben a példában a notify csak akkor indítja el a Restart chrony service handlert, ha az apt module ténylegesen telepített vagy frissítette a chrony csomagot. Ha a csomag már korábban telepítve volt, a handler nem fut le.

47.1.2.5 Facts és dynamic inventory

A facts a managed hosztról futás közben begyűjtött adatok összessége. Az Ansible alapértelmezés szerint minden play elején lefuttatja a setup module-t, és a visszaadott JSON-adatokat az ansible_facts változóba gyűjti. Például ansible_facts['distribution'] az Ubuntu, ansible_facts['os_family'] a Debian értéket adja. A facts lehetővé teszi, hogy a playbook vagy a template az adott rendszerhez igazítsa a konfigurációt. A facts dinamikus, futás közben keletkezik, szemben az inventory statikus adataival.

A dynamic inventory egy script vagy plugin, amely az inventory adatokat futásidőben, külső forrásból (például cloud API, libvirt, CMDB) állítja elő. A scriptnek JSON-formátumot kell visszaadnia, és az ansible-inventory paranccsal lehet ellenőrizni. A statikus inventory a labVM-ek esetén megfelelő; a production cloud esetén viszont a cloud dynamic inventory plugin elkerüli a kézzel karbantartott CSV/YAML folyamatos frissítését.

47.1.2.6 Versioned ansible-core és collection support

Az ansible-core és a collections verzióinak explicit rögzítése ugyanolyan fontos, mint a C++ projekt dependency lockja. Az ansible-core tartalmazza a core modulokat és a végrehajtó motort; a collections külön verziószámot kapnak, és gyorsan változhatnak. Éles rendszernél a requirements.yml fájlban rögzítjük a collectionök verzióját, a pipeline pedig telepíti azokat. A verziófüggetlen ansible csomag kontra ansible-core megkülönböztetését is ismerni kell: az előbbi a legacy megközelítés, ahol minden beépített modul együtt érkezett, az utóbbi pedig a modern, modularizált forma. A támogatott verziók és compatibility matrix gyorsan változik, ezért minden lab és production környezetben a tényleges ansible-core --version és ansible-galaxy collection list kimenete az ellenőrzési alap.

47.1.3 Kidolgozott példa

A labunkban legyen egy control node (lab-ansible-ctl) és két managed host (lab-node-01, lab-node-02). A control node-on a labadmin felhasználóval dolgozunk, uid=1000. A managed hostokra SSH belépés labadmin userrel történik, és a hozzá tartozó privát kulcs a ~/.ssh/id_ed25519 fájlban van. A cél: telepítsük a chrony csomagot, állítsuk be a /etc/motd fájlt, és bizonyítsuk az idempotenciát.

Inventory fájl (lab-inventory.yml):

all:
  children:
    lab_linux:
      hosts:
        lab-node-01:
          ansible_host: 192.0.2.11
        lab-node-02:
          ansible_host: 192.0.2.12
      vars:
        ansible_user: labadmin
        ansible_ssh_private_key_file: ~/.ssh/id_ed25519
        ansible_become: true
        ansible_become_user: root
        ansible_become_method: sudo

Playbook (lab-baseline.yml):

---
- name: Alap Linux baseline
  hosts: lab_linux
  become: true
  gather_facts: true
  tasks:
    - name: Ensure chrony package
      ansible.builtin.apt:
        name: chrony
        state: present
        update_cache: true
      notify: Restart chrony

    - name: Ensure MOTD content
      ansible.builtin.copy:
        content: |
          lab managed node - do not edit manually
        dest: /etc/motd
        owner: root
        group: root
        mode: "0644"

  handlers:
    - name: Restart chrony
      ansible.builtin.service:
        name: chrony
        state: restarted

Első futtatás ellenőrzés módban:

labadmin@lab-ansible-ctl:~$ ansible-playbook -i lab-inventory.yml lab-baseline.yml --check --diff

Várható kimenet: a taskok changed állapotúak, és a diff megmutatja, hogy a MOTD fájl létrejön vagy módosul. A --check mód nem telepíti a csomagot, csak szimulál.

Tényleges futtatás:

labadmin@lab-ansible-ctl:~$ ansible-playbook -i lab-inventory.yml lab-baseline.yml

Első futás: az apt task changed, a copy task changed. A handler changed (restart).

Azonnali második futtatás:

labadmin@lab-ansible-ctl:~$ ansible-playbook -i lab-inventory.yml lab-baseline.yml

Második futás: az apt task ok, a copy task ok. A handler nem fut le. Ez a module szintű idempotencia: az eszköz a kívánt állapotot már fennállónak látja, és nem hajt végre írást.

Shell kontra module ad-hoc:

labadmin@lab-ansible-ctl:~$ ansible lab-node-01 -i lab-inventory.yml -m ansible.builtin.shell -a 'uptime'

Ez minden futtatásnál changed eredményt ad, mert a shell parancs mindig lefut. Ugyanez a file module-lal:

labadmin@lab-ansible-ctl:~$ ansible lab-node-01 -i lab-inventory.yml -m ansible.builtin.file -a 'path=/tmp/lab-marker state=touch mode=0644'

Első futás: changed; második futás: ok. A file module ellenőrzi, hogy a fájl létezik-e és a mode egyezik-e.

Become kontextus ellenőrzése:

labadmin@lab-ansible-ctl:~$ ansible lab_linux -i lab-inventory.yml -m ansible.builtin.command -a 'id' --become

A kimenetnek uid=0(root) sort kell mutatnia, bizonyítva a become sikeres escalationt.

47.1.4 Hibák és ellenpróbák

1. Missing sudo password

Ha az inventoryban ansible_become: true van, de a sudo jelszót kér, a playbook a következő hibát adja:

fatal: [lab-node-01]: FAILED! => {"msg": "Missing sudo password"}

Ok: nincs --ask-become-pass interaktív kérés, vagy nincs NOPASSWD sudo rule a labadmin felhasználónak. Megoldás: futtassuk a playbookot a --ask-become-pass kapcsolóval, vagy adjunk ansible_become_password Vault-ban titkosított változót. A diagnózishoz ansible lab-node-01 -m ping -vvv --become kimenete megmutatja a hiba forrását.

2. Host key verification failure

Az első csatlakozáskor az Ansible az OpenSSH known_hosts hiánya miatt hibát dob. A shell scriptnél a felhasználó manuálisan elfogadhatta a host keyt, de az Ansible headless futásban nem interaktív. A hosszú távú megoldás a host keyk előzetes injektálása a known_hosts-ba, nem a host_key_checking = False globális kikapcsolása, ami security regressiont jelent. A labban használhatunk ssh-keyscan parancsot a tényleges host keyk rögzítésére.

3. A shell module nem idempotens

Sokan a copy modul helyett shell: echo 'lab managed node' > /etc/motd-t használnak. Ez minden futásnál módosítja a fájlt, még akkor is, ha a tartalom azonos. A második futás is changed eredményt ad, így a felesleges restart handler is lefut. A hibaüzenethez tartozó tünet: a playbook mindig changed, és a restart minden alkalommal megtörténik. A javítás az, hogy állapotkezelő module-t (copy, template, file) használunk.

4. Group variable precedence zavar

Ha a lab_linux group ansible_user: ubuntu értéket ad, de egy hoszt-szintű változó ansible_user: labadmin-t tartalmaz, akkor a hoszt-szintű nyer. Ez a félreértések forrása: nem az utolsó definíció győz, hanem a változó precedence szabály. Az ansible-inventory -i lab-inventory.yml --host lab-node-01 parancs megmutatja az effektív hosztváltozókat. A hiba tünete: Permission denied (publickey) a control SSH logban, mert a hoszt nem a várt userrel próbál belépni.

5. Facts hiányzó kulcs

Ha a playben gather_facts: false, de a template az ansible_facts['distribution'] kulcsot használja, undefined variable hibát kapunk. A megoldás vagy a facts begyűjtése, vagy a kulcs hiányának explicit kezelése default filterrel. A hibaüzenet dict object' has no attribute 'distribution' formában jelenhet meg, ami a C++ fejlesztő számára az uninitialized member hozzáféréshez hasonló.

47.1.5 Feladatok

47.1.5.1 1. Magyarázó feladat: idempotencia megkülönböztetése

Írd le röviden, mi a különbség az alábbi két Ansible hívás között, ha mindkettőt másodszor is futtatjuk ugyanazon a lab hoszton:

ansible lab-node-01 -i lab-inventory.yml -m ansible.builtin.file -a 'path=/tmp/lab-marker state=touch mode=0644'
ansible lab-node-01 -i lab-inventory.yml -m ansible.builtin.shell -a 'touch /tmp/lab-marker'

Melyik lesz ok és melyik changed a második futásnál? Indokold a module belső működése alapján.

47.1.5.2 2. Adminisztrációs/konfigurációs feladat: inventory és playbook készítése

Készíts egy lab-inventory.yml inventory fájlt két hoszthoz: lab-node-01 és lab-node-02, IP-címük 192.0.2.11 és 192.0.2.12. A hosztokat tedd a lab_linux csoportba, és állítsd be a labadmin userrel történő belépést, valamint a sudo become-et rootra. Írj egy lab-baseline.yml playbookot, amely:

  • biztosítja a openssh-server csomagot present állapotban,
  • elhelyezi a /etc/issue.net fájlban a lab managed node szöveget copy modullal.

Futtasd a playbookot --check üzemmódban, majd élesben. Add meg a postconditiont: milyen állapotnak kell fennállnia a managed hostokon a sikeres futás után?

47.1.5.3 3. Diagnosztikai/failure feladat: become hiba javítása

A playbook futtatásakor az alábbi hibát kapod:

fatal: [lab-node-01]: FAILED! => {"msg": "Missing sudo password"}

A hoszt egyébként elérhető, a ping module pong választ ad. Milyen sorrendben ellenőriznéd a hibát? Add meg a konkrét parancsot a diagnózishoz, a valószínű okot, és egy biztonságos javítást, amely nem hagy plaintext jelszót az inventoryban. Mi lesz a postcondition a javítás után?

47.1.6 Megoldások

47.1.6.1 1. Magyarázó feladat megoldása

A file module idempotens: a második futás előtt ellenőrzi, hogy a /tmp/lab-marker fájl létezik-e, és a mode 0644-e. Ha mindkettő teljesül, nem hajt végre semmilyen műveletet, és ok eredményt ad. A shell module ezzel szemben mindig lefuttatja a touch /tmp/lab-marker parancsot, függetlenül attól, hogy a fájl már létezik-e. Ezért a második futásnál is changed lesz az eredmény. Ez a különbség az állapotkezelő module és a parancsot futtató module között. Postcondition: a file module második futtatása után a fájl létezik, ugyanazzal a mode-dal; a shell module második futtatása után a fájl létezése garantált, de a felesleges parancs mindenképpen lefut.

47.1.6.2 2. Adminisztrációs/konfigurációs feladat megoldása

Inventory (lab-inventory.yml):

all:
  children:
    lab_linux:
      hosts:
        lab-node-01:
          ansible_host: 192.0.2.11
        lab-node-02:
          ansible_host: 192.0.2.12
      vars:
        ansible_user: labadmin
        ansible_ssh_private_key_file: ~/.ssh/id_ed25519
        ansible_become: true
        ansible_become_user: root
        ansible_become_method: sudo

Playbook (lab-baseline.yml):

---
- name: Lab baseline
  hosts: lab_linux
  become: true
  gather_facts: true
  tasks:
    - name: Ensure openssh-server is present
      ansible.builtin.apt:
        name: openssh-server
        state: present
        update_cache: true

    - name: Ensure issue.net content
      ansible.builtin.copy:
        content: |
          lab managed node
        dest: /etc/issue.net
        owner: root
        group: root
        mode: "0644"

Ellenőrzés:

ansible-playbook -i lab-inventory.yml lab-baseline.yml --check --diff
ansible-playbook -i lab-inventory.yml lab-baseline.yml

Postcondition: mindkét hoszton az openssh-server csomag telepített, a /etc/issue.net tartalma pontosan lab managed node, tulajdonosa root:root, mode 0644. A második futtatásnak ok eredményt kell adnia, és nem szabad changed-et mutatnia.

47.1.6.3 3. Diagnosztikai/failure feladat megoldása

Diagnózis:

labadmin@lab-ansible-ctl:~$ ansible lab-node-01 -i lab-inventory.yml -m ping -vvv --become

A --become hatására az SSH kapcsolat létrejön, de a sudo a jelszó hiánya miatt nem tud végrehajtódni. A verbose kimenetben látható a sudo prompt és a hiba. A valószínű ok: a labadmin usernek nincs NOPASSWD sudo rule-ja, és az inventoryban vagy parancssorban nem adtunk meg jelszót. A javítás egyik biztonságos módja: futtassuk a playbookot --ask-become-pass kapcsolóval, hogy a jelszó prompton jelenjen meg, ne kerüljön a verziózott inventoryba. Alternatíva: az ansible_become_password változót Ansible Vault titkosított fájlban tároljuk. A postcondition: a labadmin user a sudo segítségével root jogosultsággal futtathatja a module-okat, de a jelszó nem szerepel plaintext inventoryban, és a git diff nem mutatja a titkot. A hiba megszűnik, a playbook ok-kal fut le.

47.1.7 Rövid összefoglaló

Az Ansible deklaratív hostállapot-kezelést nyújt: az inventory a célhosztokat és a kapcsolat paramétereit írja le, a module az idempotens erőforrás-kezelést végzi, a playbook pedig playekbe és taskokba szervezi a kívánt állapotot. A shell command/shell module-okkal ellentétben az állapotkezelő module-ok második futtatásnál ok-t adnak, mert ellenőrzik a jelenlegi állapotot. A become mechanizmus kontrollált privilege escalationt ad SSH-ra építve, de a jelszavak scope-ját Vault vagy interaktív kérés tartja biztonságban. A facts futás közben a céllószerről gyűjt adatot, a dynamic inventory pedig külső forrásból építi az inventoryt. Az ansible-core és a collections verzióit explicit támogatási matrix szerint kell rögzíteni. Három továbbhasznált definíció: inventory, module, idempotencia.
