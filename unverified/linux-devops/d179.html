36.4 Capabilities, seccomp, MAC és rootless

36.4.1 Motiváció

Egy konténerben futó szenior C++ szolgáltatás gyakran ugyanolyan bináris, mint amit korábban natív hoston futtattunk. A különbség üzemeltetési szempontból az, hogy a kernel erőforrás- és jogosultsághatárait nem a fejlesztői gépen, hanem több tenant teljes shared kernelén kell kijelölnünk. Ha egy konténer root felhasználóval indul, a processz alapértelmezés szerint olyan Linux capability készletet kap, amelyből még mindig sokkal több hozzáfér, mint a feladatához szükséges. A cél nem az, hogy „ne legyen root”, hanem az, hogy a konténer pontosan azt a minimális jogosultsághalmazt kapja, amit a hívott syscallok igényelnek, és a kernel további rétegekkel (seccomp, MAC, rootless mapping) visszatartsa a kitörést akkor is, ha a C++ kód hibázik.

36.4.2 Definíciók és OCI runtime spec

A Linux capabilities modell a privilegizált műveleteket névvel ellátott képességekre bontja. A CAP_NET_BIND_SERVICE például csak az 1024 alatti TCP/UDP portok bindolását engedélyezi, a CAP_SYS_ADMIN viszont mountok, namespace-ek és számos adminisztratív syscall felett rendelkezik. A kernel minden processzhez több capability halmazt tart nyilván: a bounding set a folyamat által megszerezhető képességek felső korlátja, az effective a ténylegesen érvényes képesség, az ambient pedig az exec utáni öröklődést szabályozza.

Az OCI runtime spec (Open Container Initiative) ezeket a Linux-specifikus mezőket szabványos config.json formátumban rögzíti, így a Docker, Podman, containerd és a runc/crun runtime-ok ugyanazt a security konfigurációt alkalmazzák. A releváns mezők a process.capabilities, process.noNewPrivileges, linux.seccomp, linux.maskedPaths, linux.readonlyPaths, valamint a namespace és mount definíciók. A konténerfuttató parancssori kapcsolói ezeket a mezőket töltik ki, ezért érdemes a CLI-t és az eredményül kapott JSON-t együtt értelmezni.

36.4.3 Capability bounding és default drop

A konténerindításnál az a biztonságos irány, ha először minden képességet eldobunk, majd csak a ténylegesen szükségeseket adjuk hozzá. Ezt a gyakorlatot nevezzük default drop elvnek. Például egy HTTP szolgáltatás, amely 80-as portot köt, de nem mountol fájlrendszert, nem módosít hálózati interfészt és nem olvas más processzek memóriáját, a következő minimális halmazt igényli:

  • CAP_NET_BIND_SERVICE a 80-as port bindolásához,
  • CAP_DAC_OVERRIDE csak akkor, ha a user nem rendelkezik a fájlokon a szükséges DAC joggal,
  • semmi más.

A Docker és Podman alapértelmezett capability listája is szűkített, de még mindig tartalmaz olyan képességeket, amelyekre egy tipikus web service-nek nincs szüksége. Ezért explicite --cap-drop ALL-t kell használni, majd --cap-add-del visszaadni a szükségeseket.

36.4.4 Seccomp, AppArmor és SELinux

A seccomp nem MAC, hanem syscall-szűrő a kernel belépési pontján. A konténer runtime-ok alapértelmezett seccomp profilja blokkolja a veszélyes vagy ritkán szükséges syscallokat: például a mount, a ptrace, a reboot, a keyctl, a bpf és a kexec_load egy részét. Ha a C++ processz egy ilyen syscallt hív, EPERM hibát kap. A seccomp tehát a kernel támadási felületét csökkenti, nem a hagyományos fájlhozzáférést korlátozza.

Az AppArmor és a SELinux ezzel szemben MAC rétegek: a rendszergazda által definiált, a processz tulajdonosától független szabályok. Az Ubuntu 24.04 LTS alapprofilban AppArmor-t használ, a RHEL-család jellemzően SELinuxot. A konténer runtime a konténer processzhez egy adott AppArmor profile-t vagy SELinux domain-t rendel. A Docker/Podman által beállított default profilok tovább szűkítik a hozzáférést, de a denialt mindig a kernel logból, például apparmor="DENIED" vagy AVC bejegyzésből kell bizonyítani, és soha nem a védelem kikapcsolásával kezeljük.

36.4.5 Read-only rootfs és no-new-privileges

A read-only rootfs azt jelenti, hogy a konténer root filesystemje ro mounttal van csatolva. A processz nem tud a rendszerfájlokba írni, csak ideiglenes vagy volume mountokra. Ez különösen fontos akkor, ha a C++ alkalmazás hibás, és például path traversal vagy overrun miatt írna. A gyakorlatban a szolgáltatásnak szüksége lehet /tmp írásra: ezt tmpfs mounttal, a perzisztens adatokat pedig volume mounttal biztosítjuk.

A no-new-privileges azt garantálja, hogy a processz akkor sem tud emelni jogosultságot, ha seteuid/root bitű binárist futtat, vagy file capabilityvel rendelkező programot indít. Ez a kernelben egy processz flag, és rendszerint process.noNewPrivileges=true értékkel kérjük az OCI specben.

36.4.6 Privileged, host namespaces és device mount scope

A privileged mód nem egyszerűen „több jog”, hanem a konténer elszigetelés nagyrészének kiiktatása: minden capability, minden device mount, a host namespace-ek elérése, és általában a seccomp/MAC korlátozás feloldása. Ezt kizárólag akkor szabad használni, ha a feladat valóban kernel- vagy hardverszintű hozzáférést igényel, például egy belső hálózati eszköz diagnosztikája. Ilyenkor is jobb a host namespace-t vagy a device mountot külön engedélyezni, mint a teljes privileged kapcsolót.

A host namespaces (--pid host, --net host, --ipc host) szintén veszélyesek: a konténer processz a host processztérében, hálózati stackjén vagy IPC objektumain osztozik, így egy hiba közvetlenül érintheti a hostot. A device mount (--device /dev/sdb) közvetlen hardver-hozzáférést ad; ezt név és serial alapján, dedikált labdiskre, ellenőrzött cleanup után szabad csak alkalmazni.

36.4.7 Rootless korlátozások és service ownership

A rootless konténerfuttatás során a konténer runtime és a konténer processz a hoston egy normál felhasználó UID-je alatt fut, a kernel user namespace mapping segítségével. A konténerben látszó root (UID 0) a hoston a felhasználó saját UID-jére vagy egy alárendelt UID-re képződik le. Ennek következményei:

  • A konténer kitörése esetén a támadó a hoston csak a felhasználó jogait kapja, nem a host rootot.
  • A konténer processz a saját user namespace-ében kaphat CAP_NET_BIND_SERVICE képességet, így a konténer network namespace-ében bindolhat 80-as portot, de a hostra port publikáláskor a host 80-as portját a rootless user nem foglalhatja el – hacsak a rendszergazda nem módosítja az net.ipv4.ip_unprivileged_port_start sysctl értékét.
  • Bizonyos mountok (például loop device, NFS, Ceph) rootless módban korlátozottak, és a host hálózati eszközeihez sem fér hozzá.

A service ownership kérdése más: a rootless futtatás a hoston a felhasználó felelőssége, míg a workload authorization attól függ, kinek a nevében fut a szolgáltatás a konténeren belül. Kubernetesben például a pod service accountja és a konténer UID-je együtt határozza meg a hozzáférést, nem a host user. A two fogalom összekeverése hibás policyhez vezet: a rootless nem helyettesíti a workload azonosítást, csak a host szintű privilege-t csökkenti.

36.4.8 Kidolgozott példa

A lab-httpd C++ szolgáltatás (jelölt, izolált labVM) 80-as TCP portot bindol, a /var/log/lab-httpd könyvtárba ír naplót, és a /etc/ssl/lab-httpd könyvtárból olvas tanúsítványt. Futtassuk Podman alatt, rootless módban a labops felhasználóval, minimális jogosultsággal.

Előfeltétel: a lab-* diszkek és volume-ok korábban létre lettek hozva, a labops user a podman csoport tagja, és a C++ image a registry.lab.internal registryből elérhető.

# target: lab-vm01, user: labops (UID 1000), rootless podman
# előfeltétel: /srv/lab-httpd/log könyvtár a hoston, read-only ezt nem érinti

podman run -d --name lab-httpd \
  --user 1000:1000 \
  --cap-drop ALL \
  --cap-add NET_BIND_SERVICE \
  --security-opt no-new-privileges \
  --read-only \
  --tmpfs /tmp:rw,size=64m,uid=1000,gid=1000 \
  -v /srv/lab-httpd/log:/var/log/lab-httpd:rw \
  -p 8080:80 \
  registry.lab.internal/cpp-httpd:1.0

Ellenőrzés:

# target: lab-vm01, user: labops
podman inspect lab-httpd --format '{{.HostConfig.CapDrop}} {{.HostConfig.CapAdd}} {{.HostConfig.ReadonlyRootfs}} {{.HostConfig.SecurityOpt}}'
# Várt: [ALL] [NET_BIND_SERVICE] true [no-new-privileges]

podman exec lab-httpd grep 'Cap\|NoNewPrivs\|Seccomp' /proc/self/status
# Várt (rövidítve):
# CapInh: 0000000000000000
# CapAmb: 0000000000000400  (csak CAP_NET_BIND_SERVICE bit)
# NoNewPrivs: 1
# Seccomp: 2  (filter mode)

A rootfs írási hibája:

podman exec lab-httpd touch /forbidden
# Várt: touch: cannot touch '/forbidden': Read-only file system

Rollback: podman rm -f lab-httpd && podman volume prune – csak a saját lab-objektumra.

A fenti parancs az OCI specben körülbelül így jelenik meg:

{
  "process": {
    "user": {"uid": 1000, "gid": 1000},
    "capabilities": {
      "bounding": ["CAP_NET_BIND_SERVICE"],
      "effective": ["CAP_NET_BIND_SERVICE"],
      "permitted": ["CAP_NET_BIND_SERVICE"],
      "inheritable": [],
      "ambient": ["CAP_NET_BIND_SERVICE"]
    },
    "noNewPrivileges": true
  },
  "linux": {
    "seccomp": {"defaultAction": "SCMP_ACT_ERRNO"},
    "readonlyPaths": ["/proc", "/sys"],
    "maskedPaths": ["/proc/kcore", "/proc/latency_stats"]
  }
}

A defaultAction: SCMP_ACT_ERRNO azt jelenti, hogy a seccomp a nem engedélyezett syscallokra EPERM hibát ad; a konkrét syscalls whitelist a runtime default profilja alapján töltődik ki.

36.4.9 Hibák és ellenpróbák

Tünet: A konténer nem indul, a naplóban Operation not permitted látható, és a C++ szolgáltatás a setuid() hívás után EPERM-et kap.
Hipotézis: A no-new-privileges megakadályozza a seteuid bináris futtatását, vagy a seccomp blokkolja a setuid syscallt.
Adatgyűjtés: podman inspect lab-httpd mutatja, hogy a no-new-privileges be van kapcsolva; strace -e trace=setuid a konténerben megmutatja a hívó binárist.
Egy változtatás: Távolítsuk el a seteuid bitet a binárisból, és a szolgáltatást kizárólag a futtató user jogával futtassuk. Ha valódi seteuid szükséges, akkor a konténer nem lehet no-new-privileges; ilyenkor a kockázatot MAC és seccomp ellensúlyozza, de ezt dokumentálni kell.
Verifikáció: A konténer elindul, a /proc/self/status NoNewPrivs: 0, az alkalmazás nem kísérel meg jogemelést.

Tünet: A szolgáltatás nem tud írni a /var/log/lab-httpd alá, Read-only file system hibát kap.
Hipotézis: A --read-only rootfs miatt a /var/log is írásvédett, és nem lett külön volume mount.
Adatgyűjtés: podman exec lab-httpd mount | grep ' / ' megmutatja a ro flaget.
Egy változtatás: Adjunk tmpfs vagy named volume mountot a log könyvtárhoz. A fenti példában -v /srv/lab-httpd/log:/var/log/lab-httpd:rw már ezt teszi.
Verifikáció: podman exec lab-httpd touch /var/log/lab-httpd/test sikeres, de touch /forbidden továbbra is Read-only file system.

Tünet: Rootless Podman -p 80:80 publikálásnál hiba: cannot listen on the TCP port 80: permission denied.
Hipotézis: A hiba a host oldali bindből fakad, mert a rootless user nem köthet 80-as portot a host network namespace-ében; a konténer saját netns-ében a CAP_NET_BIND_SERVICE megvan, de a hostra publikálás más művelet.
Adatgyűjtés: Próbáljuk a konténer nélkül, a hoston python3 -m http.server 80-at. Ha az is permission denied, akkor host szintű korlát.
Egy változtatás: Használjunk 8080-as host portot: -p 8080:80. Ha mindenképpen 80 kell, a sysctl net.ipv4.ip_unprivileged_port_start=80 engedélyezi, de ez szélesebb rést nyit minden nem root processznek, ezért csak explicit policy felülvizsgálat után.
Verifikáció: curl http://localhost:8080 válaszol, a host ss -ltn mutatja a 8080-as foglalást podman alatt.

36.4.10 Feladatok

36.4.10.1 1. feladat (magyarázó)

Egy C++ szolgáltatás a TCP 80-as portot bindolja, a /etc/ssl/service könyvtárból TLS tanúsítványt olvas, és a /var/log/service alá ír. Sorolja fel, milyen Linux capabilityre van szüksége, és indokolja, miért nem adnánk --privileged módot. Nevezze meg azt a mac réteget is, amely Ubuntu 24.04 LTS alatt alapból aktív.

36.4.10.2 2. feladat (adminisztrációs/konfigurációs)

Hozzon létre egy rootless Podman konténert lab-secure néven a fenti szolgáltatásból: user 1000, --cap-drop ALL --cap-add NET_BIND_SERVICE, no-new-privileges, read-only rootfs, tmpfs a /tmp-hez, volume a /var/log/service-hez. Ellenőrizze a podman inspect és a /proc/self/status kimenettel, hogy a bounding set csak a kért capabilityt tartalmazza, a NoNewPrivs=1, a Seccomp=2, és a rootfs read-only. Írja le a rollback parancsot is.

36.4.10.3 3. feladat (diagnosztikai/failure/recovery)

Rootless Podman konténer -p 80:80 publikálással nem tud elindulni; a hiba permission denied. Vizsgálja meg, hogy a hiba a host oldali bindből fakad-e, és nevezze meg a két lehetséges megoldást. Melyik megoldás őrzi meg jobban a host szintű házirendet? Magyarázza el a különbséget a rootless futtatás és a workload authorization között.

36.4.11 Megoldások

36.4.11.1 1. feladat megoldása

A szükséges capability CAP_NET_BIND_SERVICE, mert a 80-as port 1024 alatti, és a folyamat user UID nem 0. A TLS tanúsítvány olvasása nem igényel capabilityt; a /etc/ssl/service fájlokra a megfelelő user/group/other DAC jog elegendő. A naplóírás sem capability kérdés, hanem mount és DAC kérdés. A --privileged azért nem kell, mert minden képességet és device mountot megadna, például CAP_SYS_ADMIN-t, CAP_SYS_PTRACE-t, ami egy HTTP service esetén indokolatlan. Az Ubuntu 24.04 LTS alap MAC rétege az AppArmor, a konténerhez a runtime default AppArmor profile-t rendel.

Postcondition: A szolgáltatás minimális képességhalmazzal fut, a MAC layer aktív, a tűzfal és a seccomp továbbra is véd.

36.4.11.2 2. feladat megoldása

# target: lab-vm01, user: labops (rootless podman)
# előfeltétel: /srv/lab-secure/log könyvtár
podman run -d --name lab-secure \
  --user 1000:1000 \
  --cap-drop ALL --cap-add NET_BIND_SERVICE \
  --security-opt no-new-privileges \
  --read-only \
  --tmpfs /tmp:rw,size=32m,uid=1000,gid=1000 \
  -v /srv/lab-secure/log:/var/log/service:rw \
  -p 8080:80 \
  registry.lab.internal/cpp-httpd:1.0

# ellenőrzés
podman inspect lab-secure --format '{{.HostConfig.CapDrop}} {{.HostConfig.CapAdd}} {{.HostConfig.ReadonlyRootfs}} {{.HostConfig.SecurityOpt}}'
podman exec lab-secure grep 'Cap\|NoNewPrivs\|Seccomp' /proc/self/status

Várt kapcsolódó mezők: CapBnd csak a CAP_NET_BIND_SERVICE bitet tartalmazza, NoNewPrivs=1, Seccomp=2. A touch /forbidden a konténerben Read-only file system hibát ad. Rollback: podman rm -f lab-secure. Cleanup: podman volume prune csak a saját lab volume-ok után, ellenőrzött névlistával.

Postcondition: A konténer fut, a kért porton válaszol, a rootfs írásvédett, a processz no-new-privileges és seccomp filterrel védett.

36.4.11.3 3. feladat megoldása

A hiba a host oldali bindből fakad, mert a host 80-as portja a rootless user számára nem elérhető. Ezt igazolja: a konténer nélkül, a hoston egy nem root processz bind 80 hívása is permission denied hibát ad. A két megoldás:

  1. Magas host port használata: -p 8080:80, ami nem igényel extra jogot.
  2. A sysctl net.ipv4.ip_unprivileged_port_start=80 beállítása, ami minden nem root folyamat számára engedélyezi a 80-as portot.

Az első őrzi meg jobban a házirendet, mert nem nyitja meg a low port tartományt az összes usernek. A rootless futtatás a host szintű isolationt adja: a konténer processz nem a host rootot használja. A workload authorization ezzel szemben azt határozza meg, hogy a szolgáltatás milyen identitással fér a hálózathoz, fájlokhoz és külső API-khoz; a rootless nem pótolja ezt, csak a host kockázatot csökkenti.

Postcondition: A konténer rootless módban fut, a host port 8080-on elérhető, a low port bind nem veszélyezteti a többi host folyamatot.

36.4.12 Rövid összefoglaló

A konténerprivilege-policy legfontosabb rétegei: a Linux capabilities a root jogosultság finom felbontása, ahol a bounding set és a default drop elv minimalizálja a processz által elérhető képességeket. A seccomp syscall-szűrővel, az AppArmor/SELinux MAC szabályokkal tovább csökkenti a kernel támadási felületét. A read-only rootfs és a no-new-privileges megakadályozza a rendszerfájlok módosítását és a jogemelést. A rootless futtatás user namespace mappinggel a host root hozzáférést szünteti meg, de a workload authorization továbbra is szükséges. A privileged módot és a host namespace-eket kizárólag indokolt, scope-olt esetben szabad használni, és minden denialt naplóval bizonyítva kell javítani.

Továbbhasznált definíciók: Linux capabilities – a privilegizált műveletek névvel ellátott képességekre bontott halmaza; seccomp – kernelbeli syscall-szűrő, amely EPERM hibával utasítja el a nem engedélyezett hívásokat; rootless – konténerfuttatás user namespace mappinggel, ahol a hoston a tényleges processz egy normál felhasználó UID-jén fut.
