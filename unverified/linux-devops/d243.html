49.3 GitOps reconciliation és desired state

49.3.1 Motiváció

A d242 push-alapú CD-folyamata akkor érvényesíti a kívánt állapotot, amikor a pipeline kubectl apply vagy helm upgrade parancsot futtat. A sikeres kiadás után a Kubernetes-klaszterben lévő tényleges állapot (actual state) attól még idővel eltérhet attól a konfigurációtól, amelyet a Git-tároló hiteles, elvárt állapotként (desired state) rögzít. Ezt a konfigurációs eltérést nevezzük driftnek. A drift forrása lehet kézi kubectl edit, mentő módú patch, egy másik operátor, felügyeleti rendszer vagy akár egy korábbi kiadás maradványa.

A GitOps ezt a problémát úgy kezeli, hogy a Git a konfiguráció source of truth-ja, és egy kontroller folyamatosan, pull-alapon közelíti a klaszter actual state-jét a Git desired state-hez. Ez a d192-ben megismert reconciliation-gondolatot terjeszti ki a teljes konfigurációforrásra: a Git commit a kívánt, az Argo CD vagy Flux kontroller a pull-alapú reconciliationt végzi, a status pedig a sync és health állapotot mutatja.

49.3.2 Definíció és működés

A GitOps (Git Operations) az OpenGitOps alapelvek szerint négy követelményt rögzít. A konfiguráció deklaratív, tehát a manifestek a kívánt állapotot írják le. A konfiguráció versioned és immutable, tehát a Git commit hash és a release artifact azonosítható. A konfiguráció pulled automatically, tehát a kontroller húzza a Git-változást, nem a CI pipeline push-olja a klaszterre. A konfiguráció continuously reconciled, tehát a kontroller folyamatosan érzékeli és javítja a driftet. Ebben a modellben a desired state a Git-fa egy adott commitjában tárolt manifesthalmaz, az actual state pedig a Kubernetes API-ban megfigyelt resource-ok összessége.

A reconciliation tipikusan a következő adatúton halad:

Lépés Forrás Cél Hitelesítés Megjegyzés
1. Pull Git repository Repo server / source controller SSH privát kulcs vagy HTTPS token A revisiont a commit hash azonosítja
2. Manifest-kibontás Repo server application controller belső service account plain YAML, Kustomize vagy Helm
3. Diff Git revision Kubernetes API live state cluster service account RBAC mezőszintű, háromutas diff
4. Apply/prune application controller Kubernetes API cluster service account RBAC a diff által igényelt műveletek
5. Status feedback Kubernetes API operátor/telemetria API olvasás sync/health/error

A kontroller egy webhook vagy periodikus polling hatására lekéri a repository adott revisionjét, kibontja a manifesteket, háromutas diff-et számol a Git manifest, a cluster live objektum és az utolsó alkalmazott konfiguráció (last-applied) között, majd végrehajtja a szükséges apply, illetve törlési műveleteket. Ezt a folyamatot Argo CD-ban sync, Flux-ban reconciliation vagy apply kifejezéssel illetik.

Az eszközprofil tekintetében a könyv a CNCF Argo CD és Flux projektek támogatott stabil kiadását veszi alapul. Az Argo CD az Application CRD köré épül, és külön repószervert, application controllert, API-t és UI-t futtat. A Flux a GitOps Toolkit kontrollerekkel (Source, Kustomization, HelmRelease) dolgozik. Az aktuális, támogatott Kubernetes minor, Argo CD- és Flux-verziók support matrixát a labor kiadási dokumentációja alapján kell rögzíteni.

49.3.3 Sync, diff, health, prune és ownership

A GitOps reconciliation két legfontosabb állapotjelzője a sync és a health. A sync azt mutatja, hogy a Git manifest és a cluster élő állapota egyezik-e; az out-of-sync állapot driftet jelez. A health azt mutatja, hogy az erőforrás saját readiness/feltételei szerint egészséges-e. Például egy Deployment manifest 3 replikát ír elő, a clusterben viszont csak 2 fut: a sync out-of-sync, a health pedig lehet Healthy, ha a 2 létező Pod egészséges.

A diff a desired Git manifest és a live API-object közötti mezőszintű eltérést adja. A prune az automatikus takarításhoz szükséges: ha egy erőforrás kikerül a Git manifestből, a kontroller törli a clusterből azt, amit korábban alkalmazott. Ehhez a kontroller címkéket vagy annotationt helyez el a resource-okon (például app.kubernetes.io/instance: lab-demo). A prune soha nem lehet globális: mindig a saját Application vagy Flux Kustomization által birtokolt, név szerint azonosított erőforrásokra vonatkozik.

A GitOps kontroller által alkalmazott resource-ok így kapnak egyértelmű tulajdonosi jelölést. Az ownerReferences itt nem a GitOps Application tulajdonát jelöli, hanem a resource-ok közötti Kubernetes-ownership-t; a GitOps-tulajdonos a tracking label/annotation. A d192-ben tanult ownerReferences tehát továbbra is érvényes, de a GitOps prune a tracking annotáció alapján dönt.

49.3.4 Repo/cluster identity és secrets

A GitOps kontroller két identitástartománnyal dolgozik. A Git repository hitelesítéséhez SSH privát kulcs vagy HTTPS token szükséges; ezt a kontroller titkában tároljuk, soha nem a GitOps repositoryban. A cluster oldalán a kontroller Kubernetes ServiceAccount-ot használ, és ahhoz RBAC szerepkör tartozik. Ennek a ServiceAccountnak minimális, a cél namespace-ekre korlátozott jogosultságot kell kapnia.

A manifestekben tárolt titkok külön kezelést igényelnek. A plaintext Secret-et nem szabad a Git historyba tenni, mert a history megmarad, és a titok kiszivárgásakor a teljes history-t kompromittáltnak kell tekinteni. Helyette olyan eszközt használunk, amely titkosított, verziózott állapotot tárol a Gitben (például SOPS), vagy a klaszterben lévő secretet külső forrásból szinkronizálja (például External Secrets), esetleg lepecsételt titkot készít (Sealed Secrets). A tényleges plain secret a labban mindig dummy adat, és a support matrix szerint ellenőrzött eszközverziót kell használni.

49.3.5 Manual drift és emergency change

A manual drift akkor keletkezik, ha valaki közvetlenül a Kubernetes API-n módosítja a resource-t, megkerülve a Git source of truth-ot. Ha a GitOps kontroller automated sync-je engedélyezett, a következő reconcile során a driftet visszaállítja. Ez a self-healing viselkedés, amely Argo CD-ban a syncPolicy.automated.selfHeal: true, Flux esetén a Kustomization spec.force vagy reconciliation beállításaival érhető el.

Az üzemeltetési gyakorlatban előfordulhat olyan kritikus hiba, amikor nem várható meg a Git commit és a kontroller polling. Az emergency change ilyenkor a következő ellenőrzött, ideiglenes mentő mód szerint hajtható végre: először leállítjuk a kontroller automatikus sync-jét, majd a clusteren végrehajtjuk a szükséges patch-et, ezután azonnal beírjuk a változtatást a Git manifestbe, végül visszaállítjuk az automated sync-et. Ez nem a GitOps megkerülése, hanem szabályozott, rövid életű kivétel, amelyet a lehető legrövidebb időn belül normalizálni kell. Soha ne hagyjuk a manual emergency change-t a Git-től eltérő állapotban.

49.3.6 Reconciliation failure/feedback loop

A kontroller a reconciliation sikertelenségét (például érvénytelen manifest, RBAC-denial, képfuttatási hiba) nem a CI pipeline státuszában, hanem a GitOps resource status-ában és eseményeiben jeleníti meg. Argo CD-nál az Application SyncFailed vagy OutOfSync, a health Degraded; Fluxnál a Kustomization Ready=False. A feedback loop tehát a következő: Git push → kontroller pull → diff → sync → status-frissítés → alert/webhook/metric → operátor visszajelzés. Ehhez a kontrollert be kell kötni a megfigyelő platformba (metrics, notification). A hibás commit javítása elsősorban Git reverttel vagy új javító committal történik, nem közvetlen cluster patch-csel.

49.3.7 Kidolgozott példa

A labor egy izolált Kubernetes-klasztert használ. A környezet: labcluster Kubernetes context, argocd namespace az Argo CD kontrollernek, lab-demo target namespace az alkalmazásnak, labvm01 a munkaállomás, amelyen a git és a kubectl fut. A Git repository elérési útja git@git.invalid:lab/gitops.git; ez szándékosan nem valós, a laborban egy elérhető, inventory-ban igazolt repo használandó. A Git revision a main ág, a 1.2.3 image tag pedig kiindulási, verzió-lockolt artifact.

A desired state az overlays/dev könyvtárban tárolt manifest:

# app/overlays/dev/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: lab-demo
  namespace: lab-demo
spec:
  replicas: 3
  selector:
    matchLabels:
      app.kubernetes.io/instance: lab-demo
  template:
    metadata:
      labels:
        app.kubernetes.io/instance: lab-demo
    spec:
      containers:
        - name: app
          image: registry.invalid/lab/app:1.2.3

Az Argo CD Application manifest:

# argocd/lab-demo-app.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: lab-demo
  namespace: argocd
spec:
  project: default
  source:
    repoURL: git@git.invalid:lab/gitops.git
    targetRevision: main
    path: overlays/dev
  destination:
    server: https://kubernetes.default.svc
    namespace: lab-demo
  syncPolicy:
    automated:
      prune: true
      selfHeal: true

A manifestet a labcluster contextben alkalmazzuk, cluster-admin vagy a cél namespace-re jogosult ServiceAccount jogosultsággal:

kubectl --context labcluster apply -f argocd/lab-demo-app.yaml
kubectl --context labcluster -n argocd get application lab-demo \
  -o custom-columns='SYNC:.status.sync.status,HEALTH:.status.health.status,REV:.status.sync.revision'

Várt, illusztratív kimenet:

SYNC    HEALTH    REV
Synced  Healthy   abc1234...

Ez azt jelenti, hogy a Git abc1234 commit manifestjét a kontroller alkalmazta, a resource-ok tükrözik a desired állapotot, és a Deployment egészséges. A selfHeal: true arra utasítja a kontrollert, hogy a driftet automatikus sync-kel javítsa. A config-source a Git, a stored state az Argo CD Application status-a, az observed state pedig a Kubernetes Deployment.

Manual drift szimulálása:

kubectl --context labcluster -n lab-demo scale deployment/lab-demo --replicas=2
sleep 90
kubectl --context labcluster -n argocd get application lab-demo \
  -o custom-columns='SYNC:.status.sync.status,HEALTH:.status.health.status'

A várható, illusztratív kimenet rövid ideig OutOfSync, majd a selfHeal ismét Synced-et állít vissza; a Deployment visszaáll 3 replikára. Ez a folyamat a manual drift javítása, nem deployment rollback.

Hibás commit rollbackje Git reverttel:

# Hibás commit: image tag 9.9.9, ami nem létezik
git -C gitops commit -am "broken image tag"
git -C gitops push
kubectl --context labcluster -n argocd get application lab-demo \
  -o custom-columns='SYNC:.status.sync.status,HEALTH:.status.health.status'

# Rollback a Git revert commit létrehozásával
git -C gitops revert HEAD --no-edit
git -C gitops push
kubectl --context labcluster -n argocd get application lab-demo \
  -o custom-columns='SYNC:.status.sync.status,HEALTH:.status.health.status'

A hibás commit után a sync lehet Synced, de a health Degraded vagy Progressing lesz. A Git revert létrehoz egy új commitot, a kontroller alkalmazza, és a Deployment visszaáll az egészséges 1.2.3 image tagre. Ez a valódi source-of-truth rollback: a Git history, a GitOps status.sync.revision és a cluster live state együtt változik.

49.3.8 Tipikus hibák és ellenpróbák

  1. A Git revert és a resource rollback összekeverése. A kubectl rollout undo deployment/lab-demo a Deployment kontroller által kezelt replicasetek közül az előzőre áll vissza; nem változtat a Git-history-n, és a GitOps kontroller a következő reconcile során felülírhatja a Git desired state szerint. Ellenpróba: kubectl rollout undo után várjunk egy reconcile-t, és figyeljük meg, hogy a Deployment visszatér a Git manifest szerinti állapotba. A Git revert a source of truth-ot is módosítja, tehát a valódi rollback.

  2. Manual edit a clusteren. A változtatást a kontroller selfHeal visszaírja; ez a tünet, nem hiba. Ellenpróba: argocd app diff vagy a Flux diff mutatja a driftet. A manual edit nem állandó javítás.

  3. Plaintext Secret a Gitben. A Git history megmarad, a titok kiszivárog. Helyette SOPS, Sealed Secrets vagy External Secrets. Ellenpróba: a Git history-t átvizsgálva ne legyen plain secret.

  4. A prune túl agresszív. Ha a tracking label nem egyértelmű, más erőforrás is törlődhet. Ellenőrzés: a labban mindig lab- prefixű erőforrásokra korlátozva, a prune a saját Application által birtokolt resource-okra terjed ki.

  5. A health és a sync összekeverése. A sync siker nem jelenti a Pod alkalmazás egészségét. Ellenpróba: hibás image tag esetén a sync lehet Synced, de a health Degraded.

49.3.9 Feladatok

  1. Magyarázó feladat: Egy Argo CD Application status.sync.status értéke OutOfSync, a health.status pedig Healthy. Magyarázd el, mi lehet a különbség, és milyen lépésekkel azonosítanád a driftet anélkül, hogy módosítanád a clusteret.

  2. Adminisztrációs/konfigurációs feladat: Állíts be egy Argo CD Applicationt a fenti lab-demo mintára, amely prune: true és selfHeal: true beállítással rendelkezik. Ellenőrizd, hogy a sync Synced, a health Healthy. Módosítsd a Git manifest replikaszámát 3-ról 4-re, majd pushold. Igazold, hogy a Deployment replikaszáma követi a változást.

  3. Diagnosztikai/failure/recovery feladat: Szimulálj hibás commitot: módosítsd a Deployment image tagjét nem létező registry.invalid/lab/app:9.9.9 értékre, majd pushold. Figyeld meg a health állapotot. Hajtsd végre a rollbacket Git reverttel, és igazold, hogy a Deployment visszatér az egészséges 1.2.3 image-re.

49.3.10 Megoldások

  1. A Sync: OutOfSync azt mutatja, hogy a Git manifest és a cluster live state között eltérés van: például a replikák száma, egy label vagy egy image tag más. A Health: Healthy azt jelenti, hogy a Deployment jelenlegi, élő állapota a readiness/feltételei szerint jól működik. Diagnózis: argocd app diff lab-demo vagy kubectl --context labcluster diff -f app/overlays/dev/deployment.yaml a Git manifest ellen. A status.sync.revision megmutatja, hogy a kontroller milyen Git revisiont alkalmazott utoljára. Postcondition: a driftet azonosítottuk anélkül, hogy módosítottuk volna a Git forrást vagy a cluster resource-t.

  2. Alkalmazzuk az Application manifestet. A sync/health ellenőrzése után módosítsuk a Git manifest replicas értékét 4-re, majd git push. A kontroller automatikus sync-je frissíti a Deploymentet. Ellenőrzés:

kubectl --context labcluster -n lab-demo get deployment lab-demo \
  -o custom-columns='REPLICAS:.spec.replicas,READY:.status.readyReplicas'
kubectl --context labcluster -n argocd get application lab-demo \
  -o custom-columns='SYNC:.status.sync.status,HEALTH:.status.health.status,REV:.status.sync.revision'

Postcondition: a Git HEAD a 4-replikás commit, a cluster live spec.replicas 4, a health Healthy, a sync Synced.

  1. A hibás image commit után a sync Synced lehet, de a health Degraded vagy Progressing. A kubectl -n argocd get application lab-demo mutatja a degraded állapotot. A git revert létrehoz egy új commitot, a kontroller alkalmazza, és a Deployment visszaáll a jó image tagre. Ellenőrzés:
kubectl --context labcluster -n lab-demo get deployment lab-demo \
  -o custom-columns='IMAGE:.spec.template.spec.containers[0].image,READY:.status.readyReplicas'
kubectl --context labcluster -n argocd get application lab-demo \
  -o custom-columns='SYNC:.status.sync.status,HEALTH:.status.health.status,REV:.status.sync.revision'

Postcondition: a Git HEAD a revert commit, a cluster image registry.invalid/lab/app:1.2.3, a health Healthy, a sync Synced.

49.3.11 Rövid összefoglaló

A GitOps a Git repository-t source of truth-nak tekinti, ahol a desired state deklaratív manifestek formájában, verziózottan él. A kontroller pull-alapon, folyamatos reconciliationnel közelíti az actual state-t a desired-hez, és a driftet selfHeal/prune mechanizmussal javítja. A rollout undo és a Git revert közötti különbség fontos: az utóbbi a source of truth-ot is változtatja. Az emergency manual change csak ideiglenes, ellenőrzött mentő mód lehet. Továbbhasznált definíciók: GitOps, reconciliation, drift.
