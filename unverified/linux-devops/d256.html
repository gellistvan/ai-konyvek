52.1 Source-to-runtime trust és provenance

52.1.1 Motiváció

A szenior C++ fejlesztő a builderedményt gyakran kész, aláírt artifactként kezeli; a GitOps és a release automation azonban más bizonyítékot követel. Egy OCI image latest tagje mutálható, a forrásrepo HEAD mutatója időben változik, a hosszú életű CI private key kompromittálódhat. A source-to-runtime trust lánc azt a kérdést válaszolja meg: honnan tudja a futtató környezet, hogy az adott digest melyik forrásból, milyen build inputból és melyik építő által készült? A puszta aláírás csak a ki kérdésre ad részleges választ; a provenance a mi és hogyan kérdésre is. Az üzemeltetési hiba akkor keletkezik, amikor a release trust boundary-n egyedül a signature ellenőrzése fut, és a policy nem zárja ki a rossz source vagy a nem pinelt függőség esetét.

52.1.2 Definíció és megkülönböztetés

A provenance (származásigazolás) olyan aláírt állítás, amely az artifact digestet a forrásidentitással, a build folyamattal és a felhasznált függőségekkel köti össze. A signature (aláírás) ezzel szemben kizárólag egy kulcsbirtokos jóváhagyását bizonyítja, de nem írja le a build bemenetet. Az attestation általánosabb fogalom: bármely, az artifact digesthez kötött aláírt állítás; a provenance ennek egyik típusa. A digest binding az artifactot a tartalmából számított, kriptográfiai hash alapján azonosítja – nem a mutálható tagen keresztül. Az SBOM a komponensek géppel olvasható jegyzéke; önmagában nem bizonyíték, csak ha ugyanahhoz a digesthez kötött, mint a futtatott artifact. A verification policy a release trust boundary-n alkalmazott szabály, amely megadja, mely signer, source repo, builder és függőség elfogadott.

Állítás Mit bizonyít? Mit nem bizonyít?
Signature A kulcs birtokosa jóváhagyta a digestet A build input helyességét, a source származását
Provenance A source, builder, build input és digest kapcsolatát A függőségek sebezhetőség-mentességét
SBOM Az artifact komponenseinek listáját A komponensek megbízhatóságát
Vulnerability scan Adott ismert CVE-k jelenlétét vagy hiányát Az ismeretlen sérülékenységek hiányát

52.1.3 Működés rétegenként

52.1.3.1 Source identity és review

A forrás azonosítója a Git commit hash – lehetőleg SHA-256 – és a repository URL, nem a branch vagy a tag. A protected branch policy megköveteli a pull request alapú review-t, ahol legalább egy maintainer jóváhagyása szükséges. A commit hash akkor kerül be a provenance-be, amikor a CI a release workflow-t a checkoutolt commiton futtatja. A mutálható refs/heads/main ebben a kontextusban nem elfogadható, mert a build pillanatában még nem tudjuk, hogy később milyen commitra mutat.

52.1.3.2 Build input és dependency pin

A C++ projekt build inputja a forrásfájlok, a buildscriptek (CMakeLists.txt, conanfile.py, vcpkg.json) és a függőségi lockfile. A lockfile pinelése nem a verziószámra, hanem a dependency digestre vagy package revisionre vonatkozik. Egy conan.lock például rögzítheti, hogy a spdlog/1.13.1 melyik csomag variánsból és revisionből épül. Ha a lockfile hiányzik, a CI a feloldáskor az aktuális, esetleg módosított csomagot húzza be; a provenance-ben a resolvedDependencies üres vagy * értéket kap. Ez a floating dependency állapota. A pinelt bemenet a build input hashének része, így a provenance bizonyítja, hogy az adott digesthez milyen összetevők tartoznak.

52.1.3.3 Builder/runner trust és OIDC

A builder nem lehet hosszú életű private key-t tároló, osztatlan futtatókörnyezet. A CI runner ephemeral, izolált végrehajtó, amely a provider OIDC federationjéből rövid életű tokent kap. Ez a token a workflow-ra és a repo-ra vonatkozó állításokat hordoz, például iss=https://token.actions.githubusercontent.com, subject=repo:lab/cpp-sensor:ref:refs/tags/v1.0.0. A Sigstore keyless modell ezt a tokent fogadja el: a Fulcio rövid életű certificate-et ad ki, a Rekor transparency logba bejegyzés kerül. A verifikáló így nem egy előre megosztott kulcsot ellenőriz, hanem a CI identitását, a cert érvényességi idejét és a tlog bejegyzést. A builder kompromittálódása esetén a támadó legfeljebb rövid ideig tud aláírást generálni, és a tlog utólagos bejegyzése nehezen törölhető.

52.1.3.4 SLSA

A Supply-chain Levels for Software Artifacts (SLSA) a build integritását fokozatokba rendezi. A tananyag a stabil kiadást használja; a generálás időpontjában a SLSA 1.x a kiindulópont, de a lab release jegyzékben rögzíteni kell a pontos verziót. Lényeges követelményei:

  • Build input complete: a source és a függőségek hashét rögzíteni kell.
  • Provenance generation: a build folyamat aláírt provenance-t állít elő.
  • Hardened build platform: a builder izolált, ephemeral, és a CI rendszer csak a megfelelő környezetben futtathatja a release lépést.

A SLSA szint nem a kód minőségét, hanem a build folyamat ellenőrizhetőségét méri. Az L1 még csak dokumentáció, az L2 aláírt provenance, az L3 további build platform követelményeket támaszt.

52.1.3.5 Attestation, SBOM és digest binding

A provenance attestation gyakran az in-toto Statement formátumot használja:

{
  "_type": "https://in-toto.io/Statement/v1",
  "subject": [
    {
      "name": "lab-registry.example.com/lab/cpp-sensor",
      "digest": {
        "sha256": "5f70bf18a086007016e948b04aed3b82103a36bea41755b6cddfaf10ace3c6ef"
      }
    }
  ],
  "predicateType": "https://slsa.dev/provenance/v1",
  "predicate": {
    "buildDefinition": {
      "buildType": "https://github.com/actions/build@v1",
      "externalParameters": {
        "source": {
          "uri": "git+https://git.example.com/lab/cpp-sensor.git",
          "digest": {
            "sha1": "abcdef0123456789abcdef0123456789abcdef01"
          }
        }
      },
      "resolvedDependencies": [
        {
          "uri": "pkg:conan/spdlog@1.13.1",
          "digest": {
            "sha256": "dependency-package-digest"
          }
        }
      ]
    },
    "runDetails": {
      "builder": {
        "id": "https://github.com/lab/cpp-sensor/.github/workflows/release.yml"
      }
    }
  }
}

Ezt az állítást a builder privát kulcsa vagy a Sigstore keyless certje írja alá. Az SBOM (SPDX vagy CycloneDX) ugyanarra a digestre hivatkozik, így a policy ellenőrizheti, hogy a komponenslista tényleg a futtatott image-hez tartozik. A digest binding minden lépésben kötelező: a promotion manifest, a provenance, az SBOM és a scan report mind ugyanazt a sha256:... értéket hivatkozzák.

52.1.3.6 Sigstore keyless/identity/transparency modell

A Sigstore három komponensre épül: Fulcio rövid életű X.509 certificate-et ad az OIDC identity alapján; Rekor append-only transparency logba rögzíti az aláírást; Cosign (vagy hasonló kliens) végzi az aláírást és a verifikációt. A keyless folyamatban a CI OIDC tokenje alapján a Fulcio certja a workflow identityt tartalmazza, például a subject alternatív névben. A Rekor bejegyzés időbélyeggel és a certre mutató hivatkozással igazolja, hogy az aláírás egy adott pillanatban létezett. A verifikáló nem bízik egy hosszú életű kulcsban; azt ellenőrzi, hogy a cert a megbízható issuer-től származik, a tlog bejegyzés érvényes, és a certben szereplő identity megfelel a policy-nek.

52.1.3.7 Verification policy és a vulnerability proof korlátja

A release trust boundary-n a policy nem csak a signature érvényességét vizsgálja. A minimális szabály:

  • a digest szerepel a promotion manifestben;
  • a provenance aláírás érvényes;
  • a provenance subject.digest megegyezik a release digesttel;
  • a source repo és commit megfelel a policy requiredSource mezőjének;
  • a builder identity megfelel a requiredIdentity reguláris kifejezésnek;
  • a resolvedDependencies nem üres, és a lockfile hash-e rögzített;
  • az SBOM digest kötése fennáll.

A vulnerability proof nem automatikus következménye a provenance-nek. Az, hogy az artifact aláírt, forrásazonosított és pinelt függőségekből készült, nem jelenti azt, hogy a függőségek CVE-mentesek. A scan külön bizonyíték: az SBOM bemenetére a policy a támogatott scanner verziójával lefuttatja a CVE-szűrést, és a HIGH vagy CRITICAL találat a release blokkolását eredményezi. A provenance tehát a származás, a scan a sebezhetőség állítása; a kettő nem helyettesíthető.

52.1.4 Kidolgozott példa: lab-cpp-sensor release verificáció

A lab-verify-01 Ubuntu 24.04 LTS labhost a release trust boundary gate-et futtatja. A cél image lab-registry.example.com/lab/cpp-sensor:v1.0.0, digestje sha256:5f70bf18.... A policy fájl a release-policy.yaml:

# target: lab-verify-01, file: /etc/lab/trust/release-policy.yaml
# admin: lab-admin, privilege: sudo (root) a /etc/lab/trust írásához
apiVersion: trust.lab.example.com/v1
kind: ReleaseVerificationPolicy
metadata:
  name: cpp-sensor-release
spec:
  target:
    registry: lab-registry.example.com
    repository: lab/cpp-sensor
  subject:
    digestAlgorithm: sha256
  requiredIdentity:
    issuer: https://token.actions.githubusercontent.com
    subjectRegExp: "^https://github.com/lab/cpp-sensor/.github/workflows/release.yml@refs/tags/v[0-9]+\\.[0-9]+\\.[0-9]+$"
  requiredSource:
    git:
      url: https://git.example.com/lab/cpp-sensor.git
      commitPattern: "^[0-9a-f]{40}$"
  requireSbom: true
  sbomTypes:
    - spdx
    - cyclonedx
  requireDependencyPin: true
  vulnerability:
    mode: scan-required
    scanner: trivy   # példa; a lab verziójában ellenőrizendő
    maxSeverity: HIGH

A verifikáló script a lab-verify user jogosultságával fut, és a policy motor a lab image verziójában ellenőrzendő CLI-jét hívja. A következő vázlat a determinisztikus lépéseket mutatja:

#!/usr/bin/env bash
# target: lab-verify-01, user: lab-verify, privilege: unprivileged
# A konkrét CLI szintaxis a lab release jegyzék szerint ellenőrizendő.
set -euo pipefail

IMAGE="lab-registry.example.com/lab/cpp-sensor"
TAG="v1.0.0"
DIGEST="sha256:$(skopeo inspect --format '{{.Digest}}' "docker://${IMAGE}:${TAG}")"
# skopeo vagy crane; a lab image tartalmazza valamelyiket

ATTESTATION_FILE="./provenance.intoto.jsonl"
SBOM_FILE="./sbom.spdx.json"

# 1. Trust policy ellenőrzés: provenance, source, builder, dependency pin, SBOM binding
lab-trust-policy verify \
  --policy /etc/lab/trust/release-policy.yaml \
  --image "${IMAGE}@${DIGEST}" \
  --attestation "${ATTESTATION_FILE}" \
  --sbom "${SBOM_FILE}" \
  --source-commit "$(git -C /srv/lab/cpp-sensor rev-parse HEAD)" \
  --output ./verify-report.json

# 2. Vulnerability scan külön bizonyítékként, nem a provenance része
lab-vuln-scan \
  --image "${IMAGE}@${DIGEST}" \
  --sbom "${SBOM_FILE}" \
  --policy /etc/lab/trust/vuln-policy.yaml \
  --output ./scan-report.json

# 3. Promotion gate: mindkét report PASS szükséges
if [[ "$(jq -r '.status' ./verify-report.json)" != "PASS" ]]; then
  echo "Trust verification FAILED" >&2
  exit 1
fi

if [[ "$(jq -r '.summary.severity.HIGH' ./scan-report.json)" -gt 0 ]]; then
  echo "HIGH severity vulnerability found; promotion blocked" >&2
  exit 1
fi

echo "Promotion allowed for ${IMAGE}@${DIGEST}"

Várható kimenet sikeres esetben: a verify-report.json status mezője PASS, a subject.digest megegyezik a release digesttel, a requiredSource és requiredIdentity teljesül, a resolvedDependencies nem üres. A scan-report.json summary.severity.HIGH értéke 0. A script ezután engedélyezi a promotion lépést.

Ellenőrzési feltétel: ha a source repo a policy-től eltérő, a report status értéke FAIL, a hibaüzenet a requiredSource.git.url mezőre mutat. Ha a függőség pin hiányzik, a requireDependencyPin ellenőrzés bukik. Ha a scanner HIGH találatot jelez, a promotion gate a második feltételben blokkol.

A signature érvényessége önmagában nem elég. Ha az üzemeltető csak cosign verify-t futtat, a rossz source repo esete átcsúszik. A policy ezt a requiredSource mezővel zárja ki. A policy fájlt magát is verziózni és aláírni kell; ha a trust boundary szabályai módosíthatók, a támadó a saját forkját engedélyezheti.

A builder oldalán a hosszú életű CI secret a legnagyobb kockázat. Ha a runner egy évig élő private key-t kap, a kompromittálódás után a támadó aláírást hamisíthat. Az OIDC keyless modell rövid életű certje ezt az ablakot percekre szűkíti, a Rekor tlog pedig utólagos nyomot hagy.

F1. Fogalmi különbségtétel (magyarázó). Olvassa el a [d184] és [d239] összefoglalóit, majd írjon egy legfeljebb 15 soros érvelést arról, miért nem elegendő a signature ellenőrzése a source-to-runtime trust biztosításához. Nevezze meg, milyen állítást ad a provenance, és milyen supply-chain támadást hárít el.

F2. Verification policy konfiguráció (adminisztrációs). A lab-verify-01 VM-en hozza létre a fenti release-policy.yaml fájlt a /etc/lab/trust/ könyvtárban, sudo jogosultsággal. Használjon dummy registry nevet és kitalált digestet; a valós lab erőforrások nevét a lab manifestből helyettesítse be. Futtassa a verifikáló scriptet egy kiadott lab-cpp-sensor:v1.0.0 image-re, és rögzítse a verify-report.json kimenetet. A policy követelje meg a source repo-t, a builder identity-t és a dependency pin-t.

F3. Incidensdiagnosztika és recovery. A release pipeline egy v1.0.1 image-t tolt prod-ba, de a verify report status értéke FAIL, a hiba pedig requiredSource.git.url mismatch. A tényleges provenance-ben a source https://git.example.com/lab/cpp-sensor-fork.git. Diagnosztizálja a kiváltó okot. Milyen azonnali lépést tesz a prod rollout leállítására, és milyen javítást hajt végre a pipeline-ban? Postcondition: a prod csak a hivatalos repo-ból származó digestet futtat.

52.1.7 Megoldások

F1. A signature a kulcsbirtokos jóváhagyását bizonyítja, de nem írja le a build inputot. Ha a forrásrepo egy forkból származik, vagy a függőségek nem pineltek, az aláírás akkor is érvényes. A provenance a source commit, a builder identity és a resolvedDependencies állításait köti az artifact digesthez. Ez a supply-chain módosítás – például a fork-ból indított release – ellen véd, mert a policy a source URL-t és a dependency digestet is ellenőrzi.

F2. A fájl létrehozása:

sudo tee /etc/lab/trust/release-policy.yaml >/dev/null <<'EOF'

kind: ReleaseVerificationPolicy

  name: cpp-sensor-release
spec:
  target:
    registry: lab-registry.example.com
    repository: lab/cpp-sensor
  subject:
    digestAlgorithm: sha256
  requiredIdentity:
    issuer: https://token.actions.githubusercontent.com

  requiredSource:
    git:
      url: https://git.example.com/lab/cpp-sensor.git

sudo chmod 0640 /etc/lab/trust/release-policy.yaml

A script futtatása után a verify-report.json status értéke PASS, ha minden feltétel teljesül. A report tartalmazza a digestet, az identity-t, a source commitot és a dependency pin ellenőrzés eredményét. Postcondition: a policy fájl a lab-verify-01-en elérhető, a futtatás reportja archivált a lab artifact tárolóban.

F3. A kiváltó ok: a release workflow egy fork repository-ból indult, vagy a pipeline a fork URL-t vette fel a source mezőbe. A prod rollout azonnali leállítása: a v1.0.1 image promócióját törölni, a prod deployment visszaállítása a korábbi v1.0.0 digestre. A javítás: a pipeline a hivatalos repo release jobját használja, a fork nem szerepel a policy requiredSource mezőjében. A postcondition ellenőrzése: a verify report a hivatalos source URL-re PASS értéket ad, és a prod manifest csak a hivatalos repo commit digestjével egyező artifactot hivatkozik.

52.1.8 Rövid összefoglaló

A source-to-runtime trust a forrástól a futásig minden átmenetnél digesthez kötött bizonyítékot követel. A signature csak a signer identitását igazolja; a provenance a source commit, a build input és a builder identity állításait is rögzíti. A verification policy a release trust boundary-n a digestet, a source repo-t, a dependency pin-t és az SBOM kötést ellenőrzi, és a vulnerability scan külön bizonyítékként fut, nem a provenance részeként. A Sigstore keyless modell rövid életű OIDC certet és transparency logot használ a hosszú életű kulcs kiváltására.

Továbbhasznált definíciók: Provenance — az artifact digestet a forrásidentitással, a build bemenettel és a builder identityvel összekötő aláírt állítás; Verification policy — a release trust boundary-n alkalmazott szabály, amely a digest, signer, source, builder és függőség elfogadási feltételeit rögzíti; Digest binding — az artifact tartalmi hash alapján történő azonosítása, amely a mutálható taget kizárja a trust döntésből.
