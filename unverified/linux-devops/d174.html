35.4 Provision, migration, upgrade és shutdown

35.4.1 Motiváció

Egy VM életciklus-művelete – létrehozás, indítás, felfüggesztés, leállítás, migrálás, törlés – más-más adat- és menedzsmentállapotot érint. A futó szolgáltatást üzemeltető mérnöknek minden átmenethez előfeltételt, postconditiont és visszaállítási pontot kell rendelnie; a virsh destroy például sokszor gyors, de nem helyettesíti a rendezett leállítást. Ebben az alfejezetben egy változtatási runbook (change runbook) szerződést építünk a VM-ekhez a VM block storage, snapshot és backup és a Rolling karbantartás és change window elveire. A cél, hogy a VM management state (libvirt domain konfiguráció és futási állapot) és data state (vendégfájlrendszer, alkalmazás tranzakció, alkalmazásmemória) mindig külön kezelt, ellenőrzött állapotban maradjon.

35.4.2 Definíció és működés

A VM életciklus az alábbi fő állapotokkal írható le. A libvirt terminológiájában:

  • Create (define + start): A virsh define egy tartós domainkonfigurációt hoz létre, a virsh start pedig elindítja a vendéget. Ezzel szemben a virsh create csak átmeneti domain, amelynek konfigurációja a leállításkor elveszik. A tartós konfiguráció a VM menedzsmentállapota, míg a futó állapot az virsh domstate kimenetben figyelhető meg.

  • Start/stop: A virsh start előfeltétele a meglévő disk, hálózat, definiált domain XML és a megfelelő erőforrás-hozzáférés. A virsh shutdown az ACPI vagy guest agent felé küldött rendezett leállítási kérést indít; a vendég operációs rendszer leállítja a fájlrendszert és az alkalmazásokat. A virsh reboot hasonló, de újraindít. A forced stop (virsh destroy) a vendéget azonnal leállítja anélkül, hogy az OS befejezné az írási műveleteket; a lemez állapota crash-consistent lesz, ezért csak akkor használható, ha a rendezett leállítás nem válaszol, és a postcondition elfogadja a journal replay kockázatát.

  • Suspend/resume kétértelmű lehet. A virsh suspend ACPI S3 alvó állapotba viszi a vendéget, amelyet a hardver és a guest képességektől függően nem mindig támogat. A virsh managedsave ezzel szemben a futó VM teljes memóriatartalmát lemezre menti, leállítja a domain-t, majd a következő virsh start automatikusan visszaállítja. Ez hasznos karbantartási előkészület, de nem backup, mert a mentett memória a pillanatnyi futó állapot, nem a lemezen lévő adat.

  • Delete (undefine + storage cleanup): A virsh undefine a domain konfigurációját távolítja el; a tárterület külön törlendő. A törlésnek mindig kellően kijelölt, lab prefixszel ellátott erőforrásokra kell korlátozódnia, és csak az inventoryban felsorolt disk/serial azonosítóval lehet végrehajtani. Rollback pont ilyenkor a legutolsó snapshot/backup.

A live migration egy futó VM áthelyezése egyik hostról a másikra minimális vendégleállással. A libvirt virsh migrate parancs előfeltétele, hogy a memória- és CPU-állapot átvihető legyen, miközben a lemez és a hálózat konfigurációja a célhoston is elérhető legyen. Két alapvető tárolási eset van. Shared storage esetén mindkét host ugyanazt a háttértárat látja (NFS, SAN, Ceph), így a lemezadatokat nem kell átvinni; csak a memória és a CPU-állapot vándorol. Block migration esetén a lemezképeket is másolni kell, ami --copy-storage-all (teljes másolat) vagy --copy-storage-inc (inkrementális) móddal történik. A block migration lassabb, és a lemezkép átvitele alatt a vendég folyamatosan ír; a libvirt a konzisztencia érdekében a végső átkapcsolás előtt szinkronizál, de a műveletet snapshot vagy replication nélkül nem szabad éles adatbázisnál futtatni.

A device passthrough (például VFIO PCI GPU, USB eszköz, SR-IOV VF) a vendéget közvetlenül a fizikai eszközhöz köti. Az ilyen VM-ek általában nem migrálhatók élőben, mert a hardver a forrásállomáshoz kötött. Version compatibility: a libvirt/QEMU domain XML közötti machine type (pc-q35-..., pc-i440fx-...) és CPU modellek határozzák meg, hogy egy adott pillanatkép vagy élő állapot egy másik hoston ugyanúgy viselkedik-e. A célnál előforduló eltérő QEMU/libvirt verzió, kernel vagy CPU feature szintén migrációs hibát okoz.

Az inventory és lease/owner szerződés biztosítja, hogy minden VM-nek van azonosítható tulajdonosa, lejárata, törlési felelőse és erőforráslistája. Az inventory a desired state; a tényleges observed state (virsh domstate, lsblk, csatlakozási pontok) ettől eltérhet. A lease megújítása nélkül lejárt erőforrásokat a cleanup folyamat eltávolíthatja. Ez megakadályozza az árva lemezeket, el nem engedett IP-címeket, és a tulajdonosváltásnál explicit képet ad.

A postcondition minden átmenet után leírja, hogy mit kell mérni. Például a shutdown postconditionje: virsh domstate == shut off, guest agent nem elérhető, a lemez a journal replay után konzisztens, és a hálózati kapcsolat megszakadt. A migrate postconditionje: a célhoston running, a forráson nem fut, a network endpoint válaszol, és a storage az elvárt poolban van. A rollback pont a pre-migration snapshot, az XML konfiguráció backup és a guest agent által megerősített quiesce.

35.4.3 Kidolgozott példa

A lab-cpp-vm nevű VM a lab-hv-a hoszton fut, owner ada, lejárat 2026-01-01T00:00:00Z. Az inventory manifest:

host: lab-hv-a
vm:
  name: lab-cpp-vm
  state: running
  owner: ada
  expiry: "2026-01-01T00:00:00Z"
resources:
  disk: lab-cpp-vm-data
  disk_serial: "VM-DATA-001"
  network: lab-br-green
  mac: "ca:fe:00:00:00:01"
  taps:
    - lab-tap-01
  passthrough: false
postcondition:
  state: running
  agent: true
  health_endpoint: "http://lab-cpp-vm.lab.example:8080/health"

A tartós domain létrehozása és indítása (módosító parancs, előfeltétel és ellenőrzés kommentben):

# target: lab-hv-a, user: lab_admin, privilege: sudo
# Előfeltétel: lab-cpp-vm.xml létezik, lab-cpp-vm-data lemezkép elérhető, lab-br-green híd létezik
sudo virsh define lab-cpp-vm.xml
sudo virsh start lab-cpp-vm

# Várható kimenet: Domain 'lab-cpp-vm' started
# Ellenőrzés:
virsh domstate lab-cpp-vm          # running
virsh guest-sync lab-cpp-vm        # guest agent szinkron
# Rollback: virsh shutdown lab-cpp-vm; virsh undefine lab-cpp-vm (csak a saját diszk törlése nélkül)

Rendezett leállítás guest agenttel, 60 másodperces timeouttal, majd managedsave karbantartás előtt:

# target: lab-hv-a, user: lab_admin
# Előfeltétel: guest agent fut a vendégben, a VM az inventory szerint running
virsh shutdown --mode agent lab-cpp-vm

# Időtúllépés esetén ellenőrizni kell, nem automatikusan destroy-t futtatni:
timeout 60 virsh domstate lab-cpp-vm | grep "shut off"
if [ $? -ne 0 ]; then echo "Soft shutdown failed, inspect"; fi

# Karbantartás előtti rollback pont: memóriaállapot mentése
virsh managedsave lab-cpp-vm
virsh domstate lab-cpp-vm          # shut off
# Visszaállítás: virsh start lab-cpp-vm  (automatikusan visszaállítja a managedsave állapotot)

Élő migráció példa DNS-hálózaton, blokkos tárhellyel. A célhost lab-hv-b, a cél elérés SSH-n. A migráció előtt a lab-cpp-vm XML-t és snapshotot készítünk:

# target: lab-hv-a, user: lab_admin
# Előfeltételek:
# - lab-hv-b elérhető SSH-n, a libvirt/qemu verziók kompatibilisek
# - a célhoston a lab-br-green hálózat létezik
# - a VM nem rendelkezik nem migrálható passthrough eszközzel
# - a lab-cpp-vm disk kép (lab-cpp-vm-data) block migrate
# Ellenőrzés: forrás és cél domcapabilities összevetése
virsh domcapabilities --domain lab-cpp-vm > /tmp/lab-cpp-vm-domcap.xml
ssh lab_admin@lab-hv-b "virsh domcapabilities" > /tmp/lab-hv-b-domcap.xml
# Rollback pont:
virsh snapshot-create-as lab-cpp-vm pre-migrate --disk-only --atomic
virsh dumpxml lab-cpp-vm > lab-cpp-vm-pre-migrate.xml

# Módosító parancs:
sudo virsh migrate --live --persistent --verbose \
  --copy-storage-all \
  lab-cpp-vm qemu+ssh://lab_admin@lab-hv-b.lab.example/system

# Várható kimenet: Migration completed successfully.
# Ellenőrzés a célhoston:
ssh lab_admin@lab-hv-b "virsh domstate lab-cpp-vm"   # running
curl -sSf http://lab-cpp-vm.lab.example:8080/health || echo "health failed"
# Rollback: ha a cél nem postcondition, a forráson a snapshot reverttel és a memória nincs érintve.
# Csak sikeres ellenőrzés után: virsh undefine lab-cpp-vm a forráson; a célon a domain tartós.

A törlés előtt az inventoryból ellenőrzött erőforrások felszabadítása, és kizárólag a kijelölt lab disk:

# target: lab-hv-a, user: lab_admin
# Előfeltétel: a VM leállt, backup sikeresen visszaállítható, lease lejárt, owner jóváhagyta
virsh undefine lab-cpp-vm --remove-all-storage
# A --remove-all-storage veszélyes; labon csak akkor, ha az inventoryban
# a disk_serial és a storage pool egyezik.
# Postcondition: virsh list --all nem mutatja a domain-t, a lemezkép törlődött.
# Rollback: a backupból a lemezkép és a XML újra építhető.

35.4.4 Hibák és ellenpróbák

Tünet: A virsh migrate hibát ad: unsupported configuration: CPU mode 'host-passthrough' not supported. Hipotézis: A célhost CPU-generációja eltér. Adatgyűjtés: lscpu, virsh capabilities, virsh domcapabilities mindkét hoston. Egy változtatás: A domain XML-ben cpu mode='host-passthrough' helyett host-model beállítás, vagy a forrás CPU feature-ök explicit felsorolása. Verification: Újra virsh define és virsh migrate --live kísérlet. A postcondition a célhoston running.

Tünet: A vendég a virsh destroy utáni indításkor journal replay-t mutat. Hipotézis: A forced stop megszakította a fájlrendszer tranzakciót. Adatgyűjtés: journalctl -k, dmesg, guest fájlrendszer logok. Megoldás: A leállítás előtt alkalmazás drain (d112), majd guest agent soft shutdown. A forced stop csak végső eszköz. Verification: Újraindítás után a journal replay befejeződik, az alkalmazás konzisztens.

Tünet: A virsh suspend után a VM nem ébred. Hipotézis: A guest ACPI/PM nem támogatott, vagy a hardver nem ébreszti. Adatgyűjtés: virsh domstate (paused vagy pmsuspended). Megoldás: virsh resume; ha nem működik, virsh managedsave/virsh start a memóriaállapot mentéséhez. A suspend nem minden laborban megbízható; a managedsave jobb karbantartási előkészület.

Tünet: A migráció közben a forrás paused állapotban marad, a cél nem fut. Hipotézis: Hálózati/tárhely hiba a végső átkapcsolásnál. Adatgyűjtés: virsh domstate forrás, virsh list --all cél, journalctl -u libvirtd mindkét oldalon. Rollback: A forráson virsh resume indítja a VM-et, mert a memória még ott van. A pre-migrate snapshot és XML biztosítja a korábbi állapotot. Postcondition: a forrás újra running, a célról a domain eltávolítva.

35.4.5 Feladatok

  1. Magyarázó feladat: Fogalmazza meg a create/start/stop/suspend/delete átmenetek postconditionjét és rollback pontját. Mi a különbség a virsh create és virsh define + virsh start között?

  2. Adminisztrációs/konfigurációs feladat: Készítsen egy teljes lifecycle runbookot a lab-cpp-vm számára: inventory manifest, define/start, karbantartás előtti managedsave, rendezett leállítás guest agenttel, törlés. Adja meg minden parancsnál a targetet, előfeltételt, várható kimenetet és ellenőrzést.

  3. Diagnosztikai/failure/recovery feladat: Egy futó lab-cpp-vm migrációja során a célhoston a VM nem indul el, a forrás paused állapotban van, a libvirt log unsupported configuration: CPU feature hibát mutat. A mérnök gyorsan virsh destroy-t akar futtatni a forráson. Magyarázza el, miért nem ez a helyes első lépés, milyen adatokat gyűjtene, és hogyan állítaná helyre a szolgáltatást rollback pontokkal.

35.4.6 Megoldások

  1. Megoldás: A virsh create átmeneti domain-t indít, amely leállításkor eltűnik; a virsh define tartós konfigurációt tárol, amelyet a virsh start indít el. A postcondition create-nél: a domain az inventorynak megfelelően létezik, virsh list --all mutatja, a disk és hálózat elérhető. Rollback: virsh undefine és a disk törlése csak a kijelölt lab objektumokon. start postcondition: domstate == running, guest agent válaszol. Rollback: virsh shutdown. stop postcondition: domstate == shut off, a disk rendezett lezárás után konzisztens. Rollback: virsh start. suspend/managedsave: a memória mentve, a domain leállt; rollback: virsh start (restore). delete: a domain és a disk nem látható; rollback: backupból.

  2. Megoldás: A runbook a fenti kidolgozott példában látható. A módosító parancsok target lab-hv-a, user lab_admin, privilege sudo. Előfeltétel: az inventory manifest lab-cpp-vm.inventory.yml létezik, a lemezkép serial VM-DATA-001, a hálózat lab-br-green, a lease owner ada. A managedsave előtt győződjünk meg, hogy a guest agent fut, és a pillanatnyi memóriaállapot nem tartalmaz kötelező tranzakciót. A törlés csak lejárt lease után, a backup visszaállíthatóságának igazolásával. Postcondition: az inventory desired state és az observed state egyezik.

  3. Megoldás: A forrás VM paused állapota azt jelenti, hogy a memória még a forrás hoston van; a virsh destroy ezt megsemmisítené, és a vendég adatállapota crash-consistent, nem rendezett lenne. Először a forráson virsh domstate és a libvirt log (journalctl -u libvirtd -f) ellenőrzése, majd a CPU feature-ök összevetése (virsh capabilities, virsh domcapabilities). A hiba okát a domain XML cpu mode beállításában vagy a hardver különbségben keressük. Rollback: a forrás virsh resume paranccsal futóvá tehető, mert a memória még ott van; a pre-migrate snapshot és XML biztosítja a korábbi konfigurációt. A célpostcondition az, hogy a forrás running, az alkalmazás health endpoint válaszol, és a céloldali domain nem fut. A javítás után a CPU mode host-model beállítással újra lehet próbálkozni.

35.4.7 Rövid összefoglaló

A VM-ek életciklusát change runbook szerint, előfeltételekkel, postconditionnel és rollback pontokkal kell kezelni. A virsh define/start tartós konfigurációt hoz létre; a virsh shutdown --mode agent rendezett leállítást ad, míg a virsh destroy forced stop, amely csak végső eszköz. A live migration shared storage esetén csak a memóriát, block migration esetén a lemezképet is mozgatja, és CPU/version/device passthrough feltételekhez kötött. A passthrough eszközök és az eltérő CPU mode gyakori migrációs akadályok. Az inventory és lease/owner biztosítja az erőforrások tulajdonosát, lejáratát és cleanupját. A postcondition az observed state desired state-nek való megfelelését méri; a rollback pont a snapshot, XML backup és a guest agent quiesce.

  • Live migration: futó VM áthelyezése minimális downtime-val; shared storage vagy block migration esetén a lemez adat mozgatásával.
  • Postcondition: az átmenet utáni ellenőrizendő állapot (domstate, guest agent, health, storage konzisztencia).
  • Lease/owner: az erőforrás tulajdonosát, lejáratát, törlési felelősét rögzítő inventory szerződés.
