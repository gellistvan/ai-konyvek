31.1 Netfilter hook, conntrack és állapottartás

31.1.1 Miért kell a szabály előtt a csomagútvonalat megérteni?

Egy szolgáltatás elérhetetlenségét nem lehet pusztán a tűzfalszabályok szövegéből megmagyarázni. Először azt kell tudni, hogy a csomag melyik hálózati névtérben halad, helyi vagy továbbított forgalom-e, és melyik szűrési pontot érinti. A router input szabálya például nem védi automatikusan a mögötte lévő szervert.

A Netfilter csatlakozási pontja (hook) a Linux hálózati feldolgozásának olyan pontja, ahol regisztrált feldolgozók vizsgálhatják, módosíthatják vagy eldobhatják a csomagot. Az nftables szabályrendszert biztosít ezekhez; a kapcsolatkövetés (connection tracking, conntrack) pedig csomagokon átívelő állapotot tart fenn.

A labor a Persistens és namespace network labor névtérmodelljére épít. A kapcsolatkövetési timeoutokat megkülönböztetjük a Keepalive, retry, timeout és kapcsolatkapacitás alkalmazási időkorlátaitól.

31.1.2 Hookok, irányok és útvonalválasztás

Az alábbi modell normál, útválasztott IPv4/IPv6-forgalomra vonatkozik. Nem tárgyalja a bridge-családot, az XDP-t vagy a gyorsított flowtable-adatutat.

Hook Mikor érinti a csomag? Tipikus szerep
prerouting Beérkezés után, a helyi kézbesítés/továbbítás útválasztási döntése előtt Korai vizsgálat; kapcsolatkövetéshez kapcsolódó feldolgozás
input Ha a cél az adott hálózati névtér helyi címe Helyi szolgáltatások védelme
forward Ha a csomag másik végpont felé továbbítandó Routeren áthaladó forgalom szűrése
output Helyben előállított IP-csomagnál Helyi folyamatok kimenő forgalmának szűrése
postrouting A kimenő interfész felé, útválasztás után Kimenő útvonal késői feldolgozása

A három alapút:

  1. Helyi kézbesítés: bejövő interfész → prerouting → útválasztás → input → helyi protokollverem.
  2. Továbbítás: bejövő interfész → prerouting → útválasztás → forward → postrouting → kimenő interfész.
  3. Helyi küldés: helyi folyamat → kezdeti útvonalválasztás → output → postrouting → kimenő interfész.

Az output előtt tehát már történik útvonalválasztás; bizonyos későbbi módosítások újabb útvonalkeresést igényelhetnek. Az input nem a hálózati kártya „bejövő oldala”, hanem a helyi kézbesítés útja. A forward csomagja ugyanabban a névtérben nem járja be az input és output hookot.

Egy nftables alaplánc (base chain) hookhoz kapcsolódik. A szokásos lánc csak akkor fut, ha másik szabály odairányítja a feldolgozást.

31.1.2.1 A prioritás ugyanazon hookon belül rendez

A kisebb numerikus prioritás korábban fut. Szokásos kapcsolatkövetett IP-feldolgozásban a conntrack vizsgálata a prerouting és output hookon körülbelül a -200 prioritási ponton történik; az nftables priority filter értéke 0. Ezért az ilyen prioritású szűrés már használhatja a ct state mezőt.

Ez nem az összes hook közös idővonala: a forward szabály nem előzheti meg a prerouting feldolgozását pusztán kisebb prioritással. Azonos prioritású láncok sorrendjére ne építs működési szerződést.

Az accept sem feltétlenül végleges engedély: egy később futó alaplánc vagy hook még eldobhatja a csomagot. A drop viszont megszakítja az adott csomag további normál feldolgozását.

31.1.3 Csomagállapot és kapcsolatállapot

A conntrack rendszerint protokoll, forrás- és célcím, valamint portok alapján társítja a csomagokat bejegyzésekhez. Az eredeti és válaszirányhoz külön cím-/portkombináció tartozik. Az állapot a hálózati névtérhez, és további elkülönítés használatakor conntrack-zónához is kötött.

ct state Jelentés Amit nem bizonyít
new Új kapcsolatot indító, vagy még csak egy irányban látott kapcsolat csomagja Nem kizárólag az első TCP SYN
established Olyan kapcsolathoz tartozik, amelynél a kapcsolatkövetés már válaszforgalmat is felismer Nem alkalmazási siker vagy hitelesítés
related Egy másik követett kapcsolathoz rendelhető új forgalom Nem tetszőleges „hasonló” kapcsolat
invalid Nem sorolható érvényes követett kapcsolatba, például hibás vagy az ismert állapottal összeegyeztethetetlen Nem automatikusan támadás

A new állapotban lehet SYN-újraküldés, illetve válasz nélküli UDP-forgalom is. UDP-nél nincs TCP-szerű kézfogás: a conntrack megfigyelt csomagirányok és időkorlátok alapján dolgozik.

A related fontos példája az ICMP-hibaüzenet. A benne idézett eredeti csomag alapján a kernel összekapcsolhatja a hibát egy meglévő bejegyzéssel. A protokollsegédek által létrehozott kapcsolatok külön mechanizmust jelentenek; alkalmazásprotokoll-segéd automatikus jelenlétét nem feltételezzük.

A ct state established nem azonos a conntrack TCP-protokollkövetőjének ESTABLISHED állapotával. Már a SYN–ACK is lehet ct state established, miközben a teljes TCP-kézfogás még nem fejeződött be. Hasonlóképpen, egy lezáródó TCP-kapcsolat bejegyzése még megmaradhat.

Létezik untracked állapot is, például explicit kapcsolatkövetés-kikerülésnél; ezt a labor nem használja. Az is fontos, hogy egy hiányzó bejegyzés nem szükségszerűen eredményez invalid besorolást: a protokollkövetési beállítások, például a TCP laza követése, befolyásolják az eredményt.

31.1.4.2 2. Szűrés és hookszámlálók

# lab-netfilter; UID 0; konfiguráció a lab-nf-r névtérhez
cat > /var/tmp/lab-nf151/lab-rules.nft <<'EOF'
table inet "lab-nf151" {
    chain "lab-pre" {
        type filter hook prerouting priority filter; policy accept;
        counter
    }
    chain "lab-in" {
        type filter hook input priority filter; policy accept;
        counter
    }
    chain "lab-out" {
        type filter hook output priority filter; policy accept;
        counter
    }
    chain "lab-post" {
        type filter hook postrouting priority filter; policy accept;
        counter
    }
    chain "lab-fwd" {
        type filter hook forward priority filter; policy drop;
        ct state invalid counter drop
        ct state established,related counter accept
        meta l4proto { icmp, ipv6-icmp } counter accept
        iifname "lab-r0" oifname "lab-r1" ip saddr 10.151.1.0/30 ip daddr 10.151.2.2 tcp dport 8080 ct state new counter accept
        iifname "lab-r0" oifname "lab-r1" ip6 saddr fd42:151:1::/64 ip6 daddr fd42:151:2::2 tcp dport 8080 ct state new counter accept
        counter drop
    }
}
EOF

ip netns exec lab-nf-r nft -c -f /var/tmp/lab-nf151/lab-rules.nft
ip netns exec lab-nf-r nft -f /var/tmp/lab-nf151/lab-rules.nft
ip netns exec lab-nf-r nft -a list ruleset

Az inet család IPv4-et és IPv6-ot kezel; ARP-t nem. Az összes ICMP engedélyezése itt tudatos labor-egyszerűsítés, nem kész éles perempolicy. A helyi input/output láncok csak megfigyelési pontok.

Várt, nem mért eredmények:

  • Mindkét HTTP/8080-próba lab-ok választ ad.
  • A TCP/8081-próba timeouttal, várhatóan curl 28 kóddal zárul. Az azonnali kapcsolat-visszautasítás más bizonyíték: tipikusan elért célgép vagy explicit reject válasza.
  • A routernek címzett ping az input és output számlálóját érinti; a szerverhez menő HTTP a forward számlálóit.
  • A conntrack-listában a két családhoz külön bejegyzések láthatók, közvetlenül a próba után akár már TIME_WAIT állapotban.

A számlálók pontos értékét nem rögzítjük előre: újraküldés, háttérbeli IPv6-forgalom és HTTP-kapcsolatzárás is befolyásolja.

31.1.5 Timeout, kapacitás és ICMP-függőségek

A kapcsolatkövetési timeout azt szabályozza, meddig marad meg egy állapot megfelelő frissítés nélkül. Protokoll- és állapotfüggő; nem azonos sem az alkalmazás deadline-jával, sem a socket teljes élettartamával. A timeout lejárta önmagában nem értesíti megbízhatóan a két alkalmazást.

# lab-netfilter; UID 0; lab-nf-r; csak lekérdezés
ip netns exec lab-nf-r sysctl \
    net.netfilter.nf_conntrack_count \
    net.netfilter.nf_conntrack_max \
    net.netfilter.nf_conntrack_tcp_timeout_established \
    net.netfilter.nf_conntrack_udp_timeout \
    net.netfilter.nf_conntrack_udp_timeout_stream
ip netns exec lab-nf-r conntrack -S

Egy egyszerű, stacionárius modellben:

N≈λT N \approx \lambda T

ahol NN az átlagos bejegyzésszám [bejegyzés], λ\lambda az új bejegyzések üteme [bejegyzés/s], TT az átlagos bent tartózkodási idő [s], a lezárás utáni megőrzéssel együtt.

Hipotetikus számítás: 2000bejegyzés/s×120s=240000bejegyzés2000\ \text{bejegyzés/s}\times120\ \text{s}=240\,000\ \text{bejegyzés}. Ez egy feltételezett 262 144-es kapacitás 91,6%-a; egyik szám sem állított Linux-alapérték. A tényleges memóriaigény nem egyetlen univerzális bájt/bejegyzés szorzó.

Telítődéskor új kapcsolatok hibázhatnak, miközben régiek még működnek. Vizsgáld a foglaltságot, a statisztikák időbeli változását és a kernelnaplót együtt. Az insert_failed önmagában nem teljes diagnózis. A timeout vak csökkentése megszakíthat ritkán kommunikáló kapcsolatokat; a korlát növelése pedig memóriát és megfelelő hash-kapacitást igényel. A névterek továbbra is közös kernelt és fizikai erőforrásokat használnak, ezért ebben a laborban nem idézünk elő kimerülést.

Az IPv4 útvonal-MTU-felderítés és az IPv6 működése is ICMP-re támaszkodik. IPv6-ban a Packet Too Big mellett a szomszédfelderítés is ICMPv6. A Neighbor Solicitation/Advertisement üzenetek nem általában related állapotú válaszok egy TCP-kapcsolatra: a helyi link vezérlőforgalmát külön kell kezelni. A „minden ICMP tiltva” policy ezért nem biztonságos hibajavítás.

31.1.6 Tipikus hibák és ellenpróbák

  • Nem növekvő szabályszámláló: először a névteret, hookot és útvonalat ellenőrizd, ne újabb engedélyező szabályt adj.
  • Új kapcsolat működik, régi elakad: vizsgáld a conntrack-időkorlátot és az aszimmetrikus csomagutat is.
  • Új tiltás ellenére régi kapcsolat él: az előrébb álló established engedélyezés lehet az ok. A szabálycsere nem törli automatikusan a kapcsolatkövetési táblát.
  • Csak nagy adatátvitel akad: ellenőrizd a PMTU-hoz szükséges ICMP-hibákat; a sikeres TCP-kézfogás nem zárja ki az MTU-hibát.

A diagnosztikai ciklus: tünet → egy hipotézis → számláló és állapot lekérdezése → egy célzott változtatás → ugyanazon próba megismétlése.

31.1.7 Feladatok

  1. Magyarázó: sorold fel a router hookjait a kliens–szerver HTTP-kérésre és a routernek címzett pingre. Miért nem alkalmazási egészségjel a ct state established?
  2. Adminisztrációs: adj külön számlálót a router input láncához, kizárólag a kliens IPv4 ICMP echo-request csomagjaira. Igazold pinggel, majd külön HTTP-próbával az érintettségét.
  3. Failure/recovery: szúrj be a forward lánc elejére TCP/8080-tiltást. Bizonyítsd számlálóval a hibát, majd állítsd vissza a fájlban tárolt állapotot. Ne töröld a teljes conntrack-táblát.

31.1.8 Megoldások

1. HTTP: prerouting → forward → postrouting. Routernek címzett pingkérés: prerouting → input; helyi válasza: output → postrouting. A conntrack nem érti az HTTP-válasz üzleti helyességét. Postcondition: a kiválasztott lánc megfelel a csomag helyi vagy továbbított szerepének.

2. A külön szabály csak számol, nem ad új engedélyt:

# lab-netfilter; UID 0; lab-nf-r
ip netns exec lab-nf-r nft \
  'insert rule inet "lab-nf151" "lab-in" ip saddr 10.151.1.2 icmp type echo-request counter comment "lab-local-echo"'

Ismételd meg a pinget, olvasd ki a szabályokat, majd végezz HTTP-próbát és olvasd ki ismét. Postcondition: a célzott számláló pingre növekszik, a továbbított HTTP miatt nem.

3. A hibaszabály az established engedélyezés elé kerül:

# lab-netfilter; UID 0; lab-nf-r; szándékos, izolált hiba
ip netns exec lab-nf-r nft \
  'insert rule inet "lab-nf151" "lab-fwd" tcp dport 8080 counter drop comment "lab-fault"'

A HTTP-próba timeoutja és a lab-fault számláló növekedése együtt támasztja alá a hipotézist. A visszaállítás egy nftables-tranzakcióban történik:

# lab-netfilter; UID 0; lab-nf-r; rollback a konfigurációforrásra
{
    printf 'delete table inet "lab-nf151"\n'
    cat /var/tmp/lab-nf151/lab-rules.nft
} | ip netns exec lab-nf-r nft -f -

Ez eltávolítja a második feladat számlálóját is. Postcondition: mindkét HTTP/8080-próba újra sikeres, TCP/8081 továbbra is tiltott. A szabályszámlálók újraindultak; a conntrack-állapot nem lett globálisan törölve.

31.1.8.1 Cleanup

Csak a labor saját, felsorolt objektumait távolítjuk el:

# lab-netfilter; UID 0; kizárólag a dedikált laborobjektumok
for ns in lab-nf-c lab-nf-r lab-nf-s; do
    ip netns pids "$ns" | xargs -r kill
done
wait "$lab_pid4" "$lab_pid6" 2>/dev/null || true

for ns in lab-nf-c lab-nf-r lab-nf-s; do
    ip netns del "$ns"
done

rm -f /var/tmp/lab-nf151/lab-http4.log \
      /var/tmp/lab-nf151/lab-http6.log \
      /var/tmp/lab-nf151/lab-rules.nft \
      /var/tmp/lab-nf151/lab-www/lab-response.txt
rmdir /var/tmp/lab-nf151/lab-www /var/tmp/lab-nf151

ip netns list
ip -br link

Cleanup-postcondition: a három névtér és négy veth-végpont eltűnt; a menedzsmenthálózat változatlan.

31.1.9 Rövid összefoglaló

A tűzfalszabály hatása csak a hálózati névtér, a csomagirány, az útvonalválasztás és a hook ismeretében vezethető le. A helyi és továbbított forgalom eltérő láncokat érint; az engedélyezés után későbbi szűrés még eldobhatja a csomagot. A conntrack csomagokon átívelő, időkorlátos állapotot tart fenn, de nem igazolja az alkalmazás működését. Kapacitását az új bejegyzések üteme és megőrzési ideje együtt terheli. IPv4-ben és IPv6-ban is szükség van megfelelő ICMP-forgalomra. A labor bizonyítéka a célzott próba és a hozzá illeszkedő számlálóváltozás.

  • Hook: csatlakozási pont a kernel csomagfeldolgozásában.
  • Conntrack: kapcsolatokhoz rendelt, időkorlátos kernelállapot.
  • ct state: az aktuális csomag kapcsolatkövetési besorolása.

31.1.10 Források és ellenőrzési hiányok
