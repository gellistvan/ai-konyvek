43.3 Upgrade, version skew és node lifecycle

43.3.1 Motiváció és fogalmi alapok

Egy Kubernetes cluster hosszú élettartamú, és a benne futó komponensek verziója nem fagyasztható be. A biztonsági javítások, hibajavítások és új API-k rendszeres verzióváltást igényelnek. Ha a clustert ad-hoc módon, sorrend és előfeltételek nélkül frissítik, a control plane és a kubelet verzióeltérése (skew) API-kompatibilitási hibát, a node-ok drain nélküli újraindítása pedig szolgáltatáskiesést okoz. A cél egy olyan upgrade-folyamat, amelynél a workload disruption mérhetően alacsony marad, a rollback pedig csak olyan mértékben lehetséges, amennyire a backup és a restore-infrastruktúra ténylegesen biztosítja.

Definíció: Az upgrade a Kubernetes-komponensek (control plane, kubelet, kubectl, container runtime, addonok) verzióváltásának ellenőrzött, dokumentálható folyamata. A version skew a komponensek közötti verzióeltérés, amelyet a hivatalos version skew policy szabályoz. A node drain a pod-ok eviction API-n keresztül történő, tervezett átköltöztetése egy node karbantartás előtt. A deprecated API olyan API-csoport/verzió, amely még működik, de a közelgő Kubernetes kiadásban már eltávolításra kerül.

43.3.2 Verziókompatibilitás és skew szabály

A Kubernetes komponensek nem függetlenül verziózott elemek: a kube-apiserver, a kubelet és a kubectl között megengedett verzióeltérést a hivatalos policy rögzíti. A szabályok magva a következő:

  • A kube-apiserver a referenciaverzió. A kubelet nem lehet újabb nála, tehát vkubelet≤vapiserverv_{kubelet} \le v_{apiserver}.
  • A kubelet legfeljebb NN minor verzióval lehet régebbi, ahol NN a policy aktuális értéke. Ugyanez érvényes a kube-apiserver és a kube-controller-manager, illetve kube-scheduler között.
  • A kubectl általában N+1N+1 minor verzióval lehet újabb vagy NN minor verzióval régebbi, mint a kube-apiserver.
  • A container runtime (például containerd, CRI-O) nem a Kubernetes API-kompatibilitás része, de a csomagkezelővel frissítendő, mert a kubelet újabb verziója új CRI funkciókat várhat el.

Például ha az apiserver verziója v1.29.2, akkor a kubelet lehet v1.28.5 (egy minor régebbi), de v1.30.0 már nem. A pontos NN értékét a generáláskor támogatott Kubernetes miner kiadás hivatalos dokumentációjából kell leolvasni; ez a tananyag nem állít aktuális értéket. Mérésekről lévén szó, a verziókat a kubectl version -o json vagy kubectl get nodes -o custom-columns=NAME:.metadata.name,KUBELET:.status.nodeInfo.kubeletVersion paranccsal ellenőrizzük.

Ellenőrzési igény: a jelenleg támogatott Kubernetes-sorozat és a hozzá tartozó NN skew érték, valamint a deprecated/removed API-k listája a hivatalos Kubernetes dokumentációból ellenőrzendő.

43.3.3 Deprecated és removed API kezelése

Az upgrade előtt a clustert meg kell vizsgálni, hogy milyen API-csoport/verziókat használnak a tárolt objektumok. Ha egy Deployment a apps/v1beta1 csoportot használja, azonnali hiba nem feltétlenül lép fel, de a következő minor verzióban az API eltűnik, és a kube-apiserver már nem tudja kiszolgálni az adott erőforrást. Az upgrade egyik legfontosabb preflight lépése a használt API-k feltérképezése:

kubectl --context lab-cluster-admin get apiservices
kubectl --context lab-cluster-admin get crd -o custom-columns=NAME:.metadata.name,VERSIONS:.spec.versions[*].name

A deprecated API warning a kubectl get kimenetén jelenhet meg: Warning: apps/v1beta1 Deployment is deprecated in v1.16+, unavailable in v1.22+; use apps/v1 Deployment. Ha ilyet látunk, az érintett manifestet át kell írni, mielőtt az upgrade a control plane-t új verzióra emeli. A CRD esetében a spec.versions[*].storage és a served flag határozza meg, hogy a kube-apiserver mely verziókat tárolja és szolgálja ki. A régi tárolt verzió migrációja külön művelet, és nem helyettesíti a manifest-fordítást.

43.3.4 Backup, preflight és canary

A d212-ben tárgyalt etcd backup itt előfeltétel: ha az upgrade során korruptálódik a tárolt állapot, csak az etcd snapshotból lehet visszaállítani. A folyamat ezért:

  1. Backup: kubectl proxy vagy etcdctl snapshot save a control plane node-on. A snapshotot a clusteren kívül tároljuk, mert az upgrade során a control plane node is lecserélődhet.
  2. Preflight: Node health, API deprecated, CRD-státusz, PDB-k, daemonsetek, local data ellenőrzése.
  3. Canary: Egy alacsony forgalmú Deployment vagy StatefulSet a munkaterhelés reprezentatív mintájaként elindít egy kéréspályát, és ezt a mérőrendszer figyeli, mielőtt a teljes cluster upgrade elkezdődik. A canary nem a technikai upgrade biztonságát garantálja, hanem azt, hogy az upgrade alatt a szolgáltatás end-to-end működőképes marad-e.

43.3.5 Upgrade sorrend: control plane, majd node-ok

A Kubernetes upgrade nem párhuzamos node-frissítés. A helyes sorrend:

  1. Control plane node: a kube-apiserver, controller-manager, scheduler frissítése. Ez kubeadm alapú clusterben tipikusan a kubeadm upgrade apply paranccsal történik. Az etcd a control plane része, de a verziófrissítést a kubeadm kezeli; az etcd adatsíkon az adat konzisztenciáját a quorum és a Raft protokoll biztosítja.
  2. Node-ok: a kubelet és a container runtime frissítése. Minden node-ot drainelünk, frissítjük a csomagokat, majd uncordon.

A kubelet és a kube-apiserver közötti fent említett skew miatt a node-ok frissítése nem húzódhat hónapokig: a kubelet túl régi verziója az apiserverhez képest megsérti a policy-t, és a node NotReady-nek tűnhet, mert a kubelet nem érti az új API-verziót. A gyakorlatban egy node-onkénti rolling upgrade alatt ez a veszély minimális.

43.3.6 Drain, PDB, daemonsets és local data

A node drain a pod-ok eviction API-ját használja. A drain csak akkor hajtható végre, ha a pod-okra vonatkozó PodDisruptionBudget (PDB) megengedi a tervezett evikciót. Ha egy PDB minAvailable: 2-t ír elő, és a drain a nem futó replica-kat próbálja eviktálni, a művelet blokkolódik, és a kubectl drain hibát ad vissza. A megoldás nem a PDB törlése, hanem a replica-k átütemezése más node-ra.

A daemonsetek aktív pod-jai nem eviktálhatók a daemonset controller által menedzselt módon. A kubectl drain-nél az --ignore-daemonsets flag engedi, hogy a daemonset pod-ok a node-on maradjanak a drain alatt; a node leállítása esetén ezek a pod-ok a node törlésével elvesznek, de a controller újraindítja őket más node-on, amint a node-ok ismét rendelkezésre állnak.

A local data – például emptyDir vagy local PersistentVolume – a drain szempontjából kritikus. Az emptyDir pod-ok eviktálása adatvesztést okoz, mert az emptyDir a pod-hoz kötött. A kubectl drain általában megtagadja a local storage-al rendelkező pod-ok eviktálását, hacsak nem kényszerítjük --delete-emptydir-data flaggel. Ez a flag azonban azt jelenti, hogy elfogadjuk az adatvesztést. A production clusterekben a local data-val rendelkező workloadokhoz node-onkénti rutint és backupot kell használni.

43.3.7 Node replace és reboot

A node-ok nem örök életűek: biztonsági frissítés, hardverhiba vagy csere miatt a node-ot ki kell vonni a forgalomból. A folyamat:

  1. Cordon: a node SchedulingDisabled állapotba kerül, a scheduler nem helyez rá új pod-ot.
  2. Drain: a meglévő pod-ok átkerülnek más node-ra.
  3. Reboot vagy karbantartás.
  4. Uncordon: a node ismét fogadhat pod-okat.

A node replace ennél tovább megy: régi node törlése kubectl delete node, majd új node hozzáadása. A delete előtt meg kell győződni arról, hogy minden állapot (PV, config, local secret) más node-on vagy backupban biztonságban van. A certificate renewal (kubeadm certs renew all) a kubelet node-hoz kapcsolódó tanúsítványainak megújítása, amelyet az upgrade előtt érdemes elvégezni, ha a tanúsítvány lejárati ideje rövid.

43.3.8 Downgrade és restore: miért nem egyszerű a rollback?

A Kubernetes cluster verziójának downgrade-je nem támogatott. A control plane és a node-ok komponenseinek visszafejlesztése inkompatibilis állapotot hozhat létre: a kubelet újabb verziója az apiserver régebbi verziójával nem működik, és a tárolt API-objektumok sem feltétlenül visszafelé kompatibilisek. A kizárólagos visszaút az etcd snapshot restore: ha a backup készült az upgrade előtt, akkor a teljes cluster állapot visszaállítható arra a pontra, de ez leállással jár, és az upgrade után keletkezett adatok elvesznek. A d212-ben bemutatott restore tehát az upgrade rollback mechanizmusa, nem pedig egy kényelmes kubectl rollout undo művelet. A workload szintű rollback (Deployment revision) külön fogalom, és nem vonatkozik a cluster verziójára.

43.3.9 Kidolgozott példa: egy node upgrade kubeadm clusterben

Labtarget: lab-k8s-cluster (context: lab-cluster-admin), control plane node lab-k8s-cp1, worker node lab-k8s-worker1, namespace lab-upgrade-demo. A példa verziója illusztratív: 1.28-asról 1.29-esre történő upgrade, a pontos verzió a hivatalos support matrixból ellenőrizendő. A művelet root jogosultságot igényel a control plane node-on.

1. Preflight – API deprecated és node health:

kubectl --context lab-cluster-admin get nodes -o wide
kubectl --context lab-cluster-admin -n lab-upgrade-demo get deploy,sts,ds
kubectl --context lab-cluster-admin -n lab-upgrade-demo get pdb
kubectl --context lab-cluster-admin get crd -o custom-columns=NAME:.metadata.name,STORAGE:.spec.versions[?(@.storage==true)].name

Várt kimenet: a node-ok Ready, a deploymentek Available, a CRD storage verziója friss.

2. Control plane upgrade (kubeadm):

sudo kubeadm upgrade plan
sudo kubeadm upgrade apply v1.29.2
sudo apt-get update && sudo apt-get upgrade -y kubelet kubectl
sudo systemctl restart kubelet

3. Worker node drain és upgrade:

kubectl --context lab-cluster-admin get pdb -n lab-upgrade-demo
kubectl --context lab-cluster-admin drain lab-k8s-worker1 --ignore-daemonsets --delete-emptydir-data --timeout=120s
sudo apt-get update && sudo apt-get upgrade -y kubelet
sudo systemctl restart kubelet
kubectl --context lab-cluster-admin uncordon lab-k8s-worker1

Postcondition: a kubectl get nodes minden node Ready; a kubectl get pods -A minden pod Running vagy Completed; a kubelet és apiserver verzió közötti skew a policy szerinti tartományon belül van.

Hiba tünet: ha a drain elakad, és kubectl drain hibaüzenete cannot evict pod as it would violate the pod's disruption budget, akkor a PDB túl szoros. Ilyenkor a deploy replicaszámot vagy a PDB-t kell módosítani, de nem szabad a PDB-t törölni a termelési környezetben.

43.3.10 Feladatok

1. (magyarázó) Skew ellenőrzés Adott egy cluster, ahol az apiserver verziója v1.29.2, a kubelet verziója a worker node-on v1.27.4, a kubectl kliens v1.30.0. Tegyük fel, hogy a policy szerint a kubelet legfeljebb 2 minor verzióval lehet régebbi, a kubectl pedig legfeljebb 2 minor verzióval lehet újabb. Értékeld, hogy az összes komponens megfelel-e a skew szabálynak, és ha nem, jelöld meg, hol sérül.

2. (adminisztrációs) Node drain és upgrade szimuláció A lab-k8s-cluster clusterben a lab-k8s-worker2 node-on fut egy lab-upgrade-demo névtérben lévő lab-deploy deploy és egy lab-ds daemonset. Készítsd el a parancssort, amely a node-ot cordonolja, draineli, majd az upgrade után uncordonolja. A drain során a daemonset podokat hagyd figyelmen kívül, és ha az emptyDir-t használó podok eviktálásra kerülnek, az adatvesztést vállaljuk. Add meg az ellenőrző parancsot is.

3. (diagnosztikai) Deprecated API és restore Egy upgrade során a kube-apiserver a következő hibát írja a logba: the server rejected our request for an unknown reason (get deployments.apps) és a kubectl get deploy warningot ad: extensions/v1beta1 Deployment is deprecated. Melyik lépést hagyták ki a preflightből, és hogyan lehet a clustert helyreállítani, ha az upgrade közben az apiserver nem indult el? Vázold a diagnosztikai lépéseket és a helyreállítás parancsait.

43.3.11 Megoldások

1. Megoldás Az apiserver v1.29.2, a kubelet v1.27.4 (2 minor régebbi), ez éppen a megengedett határon belül van, tehát megfelel. A kubectl v1.30.0 (1 minor újabb), ami szintén megengedett. A komponensek közötti verzióeltérés a feltételezett policy szerint érvényes. Postcondition: a cluster skew megfelel a policynek, a node-ok és a control plane együttműködnek.

2. Megoldás

kubectl --context lab-cluster-admin cordon lab-k8s-worker2
kubectl --context lab-cluster-admin drain lab-k8s-worker2 --ignore-daemonsets --delete-emptydir-data --timeout=120s
# upgrade lépések a node-on
sudo apt-get update && sudo apt-get upgrade -y kubelet
sudo systemctl restart kubelet
kubectl --context lab-cluster-admin uncordon lab-k8s-worker2

Ellenőrzés: kubectl --context lab-cluster-admin get nodes – a lab-k8s-worker2 Ready, a lab-k8s-worker2 nem SchedulingDisabled, a podok Running. Postcondition: a node ismét fogad podot, a daemonset podok újraindultak, a deploy podjai a node-on vannak.

3. Megoldás A preflightből kimaradt a deprecated API ellenőrzés. A régi extensions/v1beta1 Deployment manifestet át kellett volna írni apps/v1-re. Ha az apiserver nem indult el, a restore az etcd snapshotból történik:

sudo etcdctl snapshot restore /backup/etcd-snapshot.db --data-dir /var/lib/etcd-restore
sudo kubeadm init phase etcd local --config=kubeadmcfg.yaml
sudo systemctl restart kubelet

Ezután a manifesteket javítani kell, és a control plane-t újra kell indítani. Postcondition: az apiserver fut, a deprecated API nem okoz hibát, a workload elérhető.

43.3.12 Rövid összefoglaló

A Kubernetes upgrade verzió-sorrendje kötött: a control plane-t először, majd a node-okat drainelve frissítjük. A kubelet nem lehet újabb a kube-apiservernél, és a megengedett eltérést a version skew policy rögzíti. A deprecated API-kat az upgrade előtt fel kell térképezni, mert a removed API már nem szolgálja ki a clustert. A drain a PDB-t tiszteletben tartja, a daemonseteket figyelmen kívül hagyhatjuk, de a local data elvesztését explicit flaggel vállaljuk. A cluster verzió downgrade-je nem támogatott, csak etcd restore ad visszaállítást, és az adatvesztéssel jár.

Továbbhasznált definíciók:

  • Version skew: a Kubernetes komponensek verzióeltérése, amelyet a hivatalos policy korlátoz.
  • Deprecated API: olyan API-csoport/verzió, amely még jelen van, de a következő Kubernetes kiadásban eltávolításra kerül.
  • Node drain: a pod-ok eviction API-n keresztül történő, tervezett eltávolítása egy node-ról karbantartás előtt.
