35.2 VM bridge/NAT/routed hálózat

35.2.1 Motiváció

A VM csak akkor működtethető szolgáltatásként, ha a guest csomagjai pontosan megválaszolhatók, és a hibát nem a host, a guest, a switch vagy a külső hálózat együttes találgatásával keressük. A libvirt több hálózati módot kínál: a default NAT kényelmes laborhoz, de a bridged a külső hálózatban teszi láthatóvá a VM-et, a routed pedig a hostot használja L3 átjáróként, anélkül hogy az L2 szegmensbe beadná. A döntés policy és elérhetőség kérdése: bejusson-e kívülről közvetlenül, milyen upstream gateway legyen, és hol keletkezzen DHCP/DNS. A d172 célja, hogy a guest packet utat tap/vnet, Linux bridge, route, forwarding és host firewall rétegek szerint bizonyíthatóan le tudjuk vezetni, így egy kiesést ne próbálgatással, hanem layerenkénti teszttel lokalizáljunk.

35.2.2 Definíciók és működési modell

35.2.2.1 Tap/vnet és Linux bridge

A libvirt QEMU guest hálózata a hoston egy tap eszközként jelenik meg. A tap a host kernelbe tartozó karakteres hálózati eszköz: a guest virtuális NIC-jének (virtio-net) TX/RX oldalát a QEMU process a tap fájldeszkriptoron keresztül éri el. A libvirt a vnet prefixet használja ezekre (például vnet0), de a típusuk tap. A Linux bridge L2-forwarding eszköz: MAC-táblát épít, broadcastot, multicastingot és ismeretlen unicastot eláraszt, tanult unicastot portra továbbít. A bridge tagjai lehetnek fizikai NIC-ek, tap/vnet eszközök és veth párok. A STP, learning és flooding beállítások a bridge attribútumai. A libvirt “bridge network” módja egy meglévő Linux bridge-hez csatolja a tap eszközt. A host stack nem feltétlenül kap IP-t a bridge interfészen; a guest és a külső hosztok ugyanabba az L2 szegmensbe kerülnek.

35.2.2.2 Libvirt default NAT versus custom network

A libvirt default hálózat (default) általában egy NAT-alapú hálózat: a libvirt létrehoz egy virbr0 bridge-et, amely a host szempontjából egy belső subnet – általában 192.168.122.0/24 – és a host a bridge interfészen 192.168.122.1 címet kap. A libvirt egy belső dnsmasq-ot indít DHCP/DNS kiszolgálóként. A guest → external forgalom a hoston SNAT-on (Masquerade) megy keresztül, ezért kívülről nem látható a guest címe. Ez a mód alkalmas kimenő hálózati hozzáférést igénylő labra, de bejövő kapcsolat indításához DNAT szükséges, és a külső hálózat sosem látja a guest MAC/címét.

A custom network lehet: - bridged: megadott host bridge-hez csatlakoztatja a guesteket, nincs libvirt DHCP, a külső DHCP vagy statikus cím az irányadó. - routed: a libvirt a host routing-táblájába bejegyzést tesz a belső subnetre, a guest default gateway a host belső interfész címe. Nincs L2 bridge a külső hálózat felé. - isolated: csak guestek közötti L2, nincs host forwarding, nincs külső útvonal. - NAT: mint a default, de saját subnet/retekszabállyal.

35.2.2.3 Routed és bridged, VLAN

Bridged esetén a guest ugyanabba az L2 szegmensbe kerül, mint a host fizikai NIC-je. A host kernel bridge-je a fizikai NIC-et veszi fel tagként; a guest tap eszköz is ide kerül. A guest saját MAC-címmel, a külső DHCP-ből kaphat IP-t. A host IP-je ilyenkor a fizikai NIC-ről átkerülhet a bridge interfészre, vagy a fizikai NIC IP nélkül marad, ha a hostnak nincs szüksége hálózatra azon a szegmensen. A bridge az L2-t kiterjeszti, így a switch a host portján több MAC-címet lát. Ez a módszer akkor szükséges, ha a VM-nek a fizikai hálózatban megegyező L2 broadcast domainben kell lennie (például PXE, DHCP, mDNS, multicast).

Routed esetén a VM-ek külön subnetet kapnak, például 10.10.0.0/24, és a host a belső bridge-en 10.10.0.1 címet visel. A host kernel IP-forwardingot kapcsol be a guest forgalomhoz. A külső hálózat felé a host útválaszt; a külső routereknek vagy a hoston lévő statikus route-nak ismernie kell a belső subnet elérését. Ha a külső hálózat routere nem tud a belső subnetről, akkor a hostnak SNAT-ot kell végeznie, és a mód gyakorlatilag guest NAT viselkedést ad, de a forwarding explicit host route-táblával és policyvel.

VLAN: ha a VM egy adott 802.1Q VLAN-ba kerüljön, a host bridge-hez VLAN-tagelt interfészt kell kötni. A Linux bridge VLAN-filterezést támogat: a bridge portokra bridge vlan add paranccsal adható meg, mely VLAN-ok mehetnek. Libvirtben egy VLAN-tagged bridge-hez a guestet ugyanúgy csatoljuk, de a porton a PVID/trunk beállítást kell ellenőrizni. A guest általában tagletlenül látja a címét, míg a bridge kifelé a VLAN-taget hozzáteszi.

35.2.2.4 DHCP/DNS/IPAM a guest hálózatban

A libvirt saját hálózati definíciójában <dhcp> szakasszal engedélyezi a beépített dnsmasq-ot. A dnsmasq a libvirt network által kijelölt címterületből oszt IP-t, és opcionálisan DNS-t is ad a guesteknek. A default NAT hálózat a 192.168.122.0/24 subnetet kezeli. Custom NAT/routed networkben <ip address='10.10.0.1' netmask='255.255.255.0'> alatt <dhcp><range start='10.10.0.100' end='10.10.0.200'/><host mac='52:54:00:...' ip='10.10.0.10'/></dhcp> szabályozható. A bridged hálózatban a libvirt nem indít DHCP-t; a külső DHCP a felelős. A host DNS-t a guest a DHCP-ben kapja, vagy statikus konfigurációból. A libvirt a DNS forwardingot a host /etc/resolv.conf-ból tanulja, de a dnsmasq saját cache-t és szolgáltatásneveket is kínál.

35.2.2.5 Host firewall és forwarding

A hostnak a guest forgalomhoz IP-forwardingot kell engedélyeznie: net.ipv4.ip_forward=1 (routed esetén). A bridge esetén Layer 2 forwarding nem igényel IP-forwardingot a bridge számára, de ha a host maga is IP-t kommunikál, az IP stacknek külön route kell. A modern Linux bridge-netfilter hatással lehet a L2-forwardingra: ha a kernelben a br_netfilter és a bridge-nf-call-iptables aktív, az eldobott csomagok, vagy conntrack problémák léphetnek fel. Ezt a VM hálózati policyben explicit kezelni kell; például a net.bridge.bridge-nf-call-iptables=0 beállítás, vagy a megfelelő nftables szabály. A NAT módhoz a host nftables SNAT szabályt igényel, jellemzően a MASQUERADE a kimenő interfészen. A routed módban a host forward chain szabályai érvényesek a guest-tranzitra. A firewall szabályok forrása a guest subnet, cél a külső, és a state-tracking conntrack.

35.2.2.6 Virtio NIC/capture/MTU

A virtio-net egy paravirtualizált NIC: a guest driver számára a QEMU a tap eszközön át továbbít. A guestben a virtio_net modul egy normál Ethernet interfészt mutat, de a host-oldali QEMU a memóriában osztott virtqueue-kat használ. A teljesítményt a multi_queue, tx/rx queue száma és a vhost-net accelerator befolyásolja. A libvirt <interface type='...'> alatt <model type='virtio'/>, <driver name='vhost' queues='2'/> adható. A capture a hoston a tap interfészen vagy a bridge porton történik; a guest-capture és host-capture időzítése illettve MAC címek eltérőek lehetnek. Az MTU a virtuális útvonalon kritikus: ha a külső hálózat 9000 bájtos jumbo frame-et használ, de a tap vagy a bridge 1500-at, a guest nagy csomagjai eldobódnak, vagy ICMP fragmentation needed hiányában timeout jelentkezik. A guest MTU-t a DHCP-ben vagy a hálózati config-ban a teljes útvonal legkisebb értékéhez kell igazítani.

35.2.3 Kidolgozott példa: custom routed libvirt network

Labtarget: lab0 Ubuntu Server 24.04 LTS host, UID user sudo-val; libvirt és QEMU telepítve; a virtuális hálózat neve lab-routed, subnet 10.10.0.0/24, host bridge virbr1, guest lab-vm1. Cél: a guest kap IP-t a libvirt DHCP-től, a host felé eléri a 10.10.0.1-et, és a külső 192.0.2.10-et a host SNAT-on keresztül, miközben a külső hálózat nem látja a guest címét.

Lépés 1: desired state – libvirt network definíció.

Fájl: lab-routed.xml.

<network>
  <name>lab-routed</name>
  <forward mode='route'/>
  <bridge name='virbr1' stp='on' delay='0'/>
  <ip address='10.10.0.1' netmask='255.255.255.0'>
    <dhcp>
      <range start='10.10.0.100' end='10.10.0.200'/>
      <host mac='52:54:00:11:22:33' name='lab-vm1' ip='10.10.0.10'/>
    </dhcp>
  </ip>
</network>

A <forward mode='route'/> a hostnak route-ot, de nem NAT-ot ír elő; a libvirt automatikusan beállítja a forwardingot. A 10.10.0.0/24 route a hoston a virbr1 felé mutat.

Lépés 2: network aktiválás.

sudo virsh net-define lab-routed.xml
sudo virsh net-start lab-routed
sudo virsh net-autostart lab-routed
ip -br addr show virbr1
ip route show 10.10.0.0/24

Várható kimenet (illusztratív):

virbr1            UP             10.10.0.1/24
10.10.0.0/24 dev virbr1 proto kernel scope link src 10.10.0.1

A libvirt ekkor elindítja a dnsmasq-ot a lab-routed network DHCP-re.

Lépés 3: guest hálózati csatolás.

A VM interfész XML-részlete (a virsh edit lab-vm1 során):

<interface type='network'>
  <source network='lab-routed'/>
  <mac address='52:54:00:11:22:33'/>
  <model type='virtio'/>
</interface>

A guest indítása után a libvirt létrehozza a vnet0 tap eszközt, és a virbr1 bridge tagjaként hozzáadja. Ellenőrzés:

sudo virsh domiflist lab-vm1
ip link show virbr1
bridge link show virbr1

Várható: a bridge link show kiírja a vnet0 portot forwarding vagy learning állapotban.

Lépés 4: guest állapot.

A guestben (a cloud-init DHCP klienssel) kapnia kell IP-t. Ellenőrzés a guestből:

ip -br addr show enp1s0
ip route show default
ping -c1 10.10.0.1

Várható (a DHCP a fenti statikus host bejegyzés alapján):

enp1s0           UP             10.10.0.10/24
default via 10.10.0.1 dev enp1s0
PING 10.10.0.1 (10.10.0.1) 56(84) bytes of data.
64 bytes from 10.10.0.1: icmp_seq=1 ttl=64 time=0.231 ms

Lépés 5: kimenő külső elérés SNAT-tel.

A routed mode önmagában nem fordíthatja a 10.10.0.0/24-et a külső felé (a külső router nem tudja a belső subnetet). Ezért a hoston explicit SNAT szabályt adunk:

sudo nft add table ip lab-nat
sudo nft 'add chain ip lab-nat postrouting { type nat hook postrouting priority srcnat; policy accept; }'
sudo nft add rule ip lab-nat postrouting ip saddr 10.10.0.0/24 oifname "enp1s0" masquerade
sudo sysctl -w net.ipv4.ip_forward=1

Ellenőrzés a külső cím felé (a 192.0.2.10 dokumentációs cél, a laborban a host gatewayét vagy <lab-external-host>-ot használjunk):

# hoston
ip route get 192.0.2.10
# guestben
ping -c1 192.0.2.10

A host SNAT miatt a külső host a 192.0.2.5 (host külső) címét látja. A guest külső címe marad 10.10.0.10.

Lépés 6: packet path levezetés.

Pont Eszköz Forrás IP Cél IP Döntés
Guest virtio-net TX enp1s0 a guestben 10.10.0.10 192.0.2.10 default route 10.10.0.1
QEMU emuláció virtqueue → tap vnet0 10.10.0.10 192.0.2.10 QEMU ír a tap-ra
Host bridge virbr1 port vnet0 10.10.0.10 192.0.2.10 MAC-tábla tanul, továbbít a virbr1 L3-hoz
Host routing host IP stack 10.10.0.10 192.0.2.10 ip_forward=1; route az enp1s0-ra
Host SNAT enp1s0 kimenő 192.0.2.5 192.0.2.10 masquerade
Külső hálózat switch/router 192.0.2.5 192.0.2.10 válasz a 192.0.2.5 felé
Visszaút conntrack 192.0.2.10 10.10.0.10 conntrack visszaállítja a fordítást, route a virbr1 felé
Host bridge virbr1 192.0.2.10 10.10.0.10 MAC-tanulás a vnet0-ra
QEMU/tap vnet0 192.0.2.10 10.10.0.10 virtqueue, guest fogad

Várható teljes állapot: a guest eléri a host 10.10.0.1-et és a külső célt; a külső 192.0.2.10 nem látja a 10.10.0.10 forrást; a virbr1-hez tartozó porton a vnet0 aktív.

35.2.4 Hibák és ellenpróbák

1. Guest kap IP-t, de a külső nem elérhető. Adatgyűjtés: guest ip route show default; host ip route show 10.10.0.0/24; host sysctl net.ipv4.ip_forward; host nft list ruleset. Ha a forwarding nincs bekapcsolva, a host eldobja a transitot. Ha a NAT szabály hiányzik, a külső host nem tudja a választ visszaküldeni. Hipotézisellenőrzés: ping a guestből a host enp1s0 külső címére; ha a host külső címét eléri, de a külsőt nem, a NAT vagy a külső router a gond. Egy változtatás, utána új kapcsolat tesztje.

2. A guest nem kap DHCP-t. Ellenőrizni kell a libvirt network állapotát: virsh net-dhcp-leases lab-routed; ha üres, a dnsmasq nem fut, vagy a guest interfész nem a megfelelő hálózatra csatlakozik. A virsh net-info lab-routed kiírja az aktív state-t. A bridge link show virbr1-ben a vnet0-nak ott kell lennie. Ha a guestben a link down, a virtio-net vagy az interface modell hibás. A DHCP kérést a hoston tcpdump -i virbr1 port 67 or port 68-cal lehet figyelni.

3. MTU mismatch. Ha a külső hálózat jumbo frame-et használ (MTU 9000), a guestben az alapértelmezett 1500-as MTU miatt a nagy csomagok a host bridge-en is 1500-nal mennek, a fizikai interfész 9000-et vár, ami nem okoz hibát (kifelé a 1500-as frame a 9000-es úton belefér), de a visszairányban a 9000-es frame a 1500-as tap-re nem fér, a bridge eldobja, és a TCP általában nem tudja átméretezni, mert az ICMP fragmentation needed elvész. Tünet: nagy letöltés időzítésben meghal. Hipotézis: ip link show a guest, host bridge és fizikai interfész MTU-ját mutatja. Ellenpróba: állítsuk minden szegmensen azonos MTU-ra (például ip link set dev vnet0 mtu 1500 a bridge oldalon, ha a külső 1500, vagy emeljük mindet 9000-re). A guest MTU-t a DHCP-ben is át lehet adni.

4. Capture a hoston nem mutatja a guest forgalmát. Ha a tcpdump -i enp1s0 a fizikai interfészen fut, a kimenő guest forgalom a tap-en, bridge-en, majd a routing stacken keresztül az enp1s0-on már SNAT-oldali forrás címmel jelenik meg. Ha a tcpdump -i virbr1-en futtatjuk, a guest forrás 10.10.0.10 marad. A réteg szerint válasszuk a megfelelő capture pontot. A virtio-net offload (például TSO) miatt a capture nem mutatja az összes részt; a guestben ethtool -K enp1s0 tso off ideiglenes a diagnosztikához.

35.2.5 Feladatok

35.2.5.1 Feladat 1: Módválasztás és policy

Magyarázza el, hogy egy adott belső szolgáltatás – például egy C++ fejlesztői build gyorsítótár – eléréséhez miért a bridged, miért a routed vagy miért a NAT módot választaná. Határozza meg a guest láthatóságát, a DHCP forrását és a host firewall felelősségét mindhárom esetben.

35.2.5.2 Feladat 2: Custom bridged hálózat létrehozása (adminisztrációs)

A lab0 hoston hozzon létre egy Linux bridge-et br0 néven, csatolja hozzá a fizikai enp1s0 interfészt (a host IP címét átvéve a bridge-re), majd definiáljon egy libvirt hálózatot lab-bridged néven, amely a br0-hoz kapcsol, és indítson egy VM-et ezzel a hálózattal. A guest kapjon a külső DHCP-től IP-t (a laborban használjon dokumentációs subnetet). Írja le a szükséges parancsokat, a desired state-et, az ellenőrzést és a rollback lépéseket.

35.2.5.3 Feladat 3: Hibadiagnosztika (diagnosztikai)

Egy lab-vm2 a libvirt lab-routed hálózaton eléri a 10.10.0.1-et, de nem éri el a külső 192.0.2.10-et. A host a saját külső interfészén normálisan eléri a célt. A hoston a nft list ruleset nem mutat masquerade-ot a 10.10.0.0/24-re. A guest ip route default útvonala 10.10.0.1-en vezet. Lokalizálja a hibát, adjon egy javító parancssort, és adjon meg egy olyan ellenőrzést, amely a javítás után a guest szemszögéből igazolja a kimenő elérést.

35.2.6 Megoldások

35.2.6.1 Megoldás 1: Módválasztás

A bridged mód akkor indokolt, ha a VM-nek azonos L2 szegmensben kell lennie a külső kliensekkel vagy szolgáltatásokkal – például ha a gyorsítótárnak közvetlenül a fejlesztői hálózatban kell broadcast DNS-t, mDNS-t, vagy a külső hálózat felé nincs NAT réteg. A guest IP-t a külső DHCP-től kap, MAC-címe a fizikai switchen látható, ezért a külső tűzfal látja a forgalmat. A host firewall nem avatkozik a bridge L2 továbbításba, csak ha IP-t is forgalmaz.

A routed mód akkor jó, ha a VM egy belső subnetben van, a host az L3 átjáró, és a külső hálózaton nem szükséges L2 láthatóság. A DHCP-t a libvirt dnsmasq adja, a host firewall a forward láncon szabályoz, és a külső hálózat nem látja a guest MAC-et, de a guest forrás IP-je a külső felé csak akkor jelenik meg, ha a külső router ismeri a belső subnet útvonalát; különben SNAT kell.

A NAT mód akkor megfelelő, ha a VM-eknek csak kimenő hozzáférés kell, és a külső hálózat felől semmilyen guest címet nem akarunk kitenni. A libvirt dnsmasq DHCP-t ad, a host conntrack SNAT-ot végez. A külső szolgáltatásoknak a guest mindig a host külső címén látszik. Ez a legegyszerűbb, de bejövő kapcsolathoz DNAT szükséges, és a hibakeresésnél a forrás átalakulása miatt a külső logok nem mutatják a guestet.

35.2.6.2 Megoldás 2: Custom bridged hálózat

A hoston a enp1s0 IP-jét a br0-ra kell helyezni, hogy a host is elérhető maradjon. Netplan YAML (a d150 state gazda elv szerint):

network:
  version: 2
  renderer: networkd
  ethernets:
    enp1s0:
      dhcp4: false
      dhcp6: false
  bridges:
    br0:
      interfaces: [enp1s0]
      dhcp4: true
      dhcp6: false

A Netplan alkalmazása:

sudo netplan apply
ip -br addr show br0

Várható: a br0 megkapja a külső DHCP IP-t, az enp1s0 csak tag, nincs IP.

Libvirt network fájl lab-bridged.xml:

<network>
  <name>lab-bridged</name>
  <forward mode='bridge'/>
  <bridge name='br0'/>
</network>

Aktiválás:

sudo virsh net-define lab-bridged.xml
sudo virsh net-start lab-bridged
sudo virsh net-autostart lab-bridged

A VM interfész típusa type='network' a source network='lab-bridged'-re, virtio modellel. A libvirt a vnet1-et (például) a br0-hoz csatolja. Ellenőrzés: bridge link show br0, virsh domiflist lab-vm1. A guest a külső DHCP-től kap címet. Rollback: VM leállítása, virsh net-destroy lab-bridged, virsh net-undefine lab-bridged, majd a Netplan visszaállítása (az eredeti enp1s0 DHCP) és netplan apply. Postcondition: a host hálózata visszaáll a bridgelt előtti baseline-ra, a br0 eltávolítva, a VM nem fut.

35.2.6.3 Megoldás 3: Hibadiagnosztika

A tünet azt mutatja, hogy a guest eléri a host belső címet, a route rendben, de a kimenő SNAT hiányzik. A nft list ruleset nem tartalmaz masquerade szabályt a 10.10.0.0/24-re, ezért a host a guest csomagjait 10.10.0.10 forrással küldi a külső interfészre, a külső router pedig nem tudja a választ visszairányítani. A javítás:

sudo nft add table ip lab-nat
sudo nft 'add chain ip lab-nat postrouting { type nat hook postrouting priority srcnat; policy accept; }'
sudo nft add rule ip lab-nat postrouting ip saddr 10.10.0.0/24 oifname "enp1s0" masquerade

Ellenőrzés a guestben:

ping -c1 192.0.2.10
ip -br addr show enp1s0

A ping sikeres válasza igazolja, hogy a conntrack a visszaútra is konzisztens. A hoston conntrack -L | grep 10.10.0.10 mutathatja az SNAT bejegyzést. Postcondition: a guest eléri a külső célt, a külső hoszton a forrás 192.0.2.5 (host külső) marad, a nft list ruleset tartalmazza a masquerade-ot, a ip_forward=1 aktív.

35.2.7 Rövid összefoglaló

A VM hálózati mód választása elérhetőségi és policy-kérdés: a bridged az L2-t terjeszti ki, a routed a hostot L3 átjáróvá teszi, a NAT a host conntrackjével fedi el a guest forrását. A libvirt default NAT hálózata a virbr0-ra épít belső dnsmasq-ot; custom networkben a bridge, route és DHCP szándékosan szabályozható. A guest packet útja mindig tap/vnet, Linux bridge, host routing és tűzfal rétegen halad. A hibát e rétegeken kell sorban ellenőrizni: bridge port, DHCP-lease, host route, forwarding, SNAT, firewall, MTU. A capture pontja határozza meg, melyik forrás/cél címet látjuk; a virtio-offload torzíthatja a képet.

  • Linux bridge: L2-forwarding eszköz, amely MAC-tanulással továbbít a tagok között.
  • Routed VM hálózat: a host IP-forwardinggal L3 átjáróként szolgál a guest subnet felé.
  • SNAT/Masquerade: a guest kimenő forráscímének lecserélése a host kimenő interfész címére, conntrack visszafordítás mellett.

35.2.8 Források és ellenőrzési hiányok

Nem történt webes forrásolvasás vagy laborfuttatás. A parancsok és XML-ek a libvirt/Ubutu dokumentációjának stabil fogalmi modelljéből származnak, nem aktuálisan futtatott bizonyítékból. A megadott kiindulópontok:

  • libvirt hálózati dokumentáció
  • QEMU networking
  • Ubuntu Server docs
  • cloud-init

Nyitott ellenőrzési igények: a tényleges libvirt és QEMU verzió az Ubuntu 24.04 LTS-ben; a br_netfilter és bridge-nf-call-iptables alapértelmezés; a dnsmasq konfiguráció pontos lehetőségei; az MTU viselkedés a tap/virtio úton; a Netplan bridge definíció engineje (networkd) és a libvirt network-route mód együttműködése. A SNAT példában a 192.0.2.5 és 192.0.2.10 RFC5737 dokumentációs címek, a tényleges laborban a host külső interfészének címét kell használni.
