21.3 SELinux, AppArmor és seccomp

21.3.1 Motiváció: amikor a fájlmód már nem elég

Egy Linux szolgáltatásnál a hagyományos DAC (discretionary access control) ellenőrzés azt dönti el, hogy a folyamat aktuális UID/GID-je, a fájl owner/group módja és az ACL-ek alapján egy művelet elvégezhető-e. Ez azonban törékeny határt ad: ha a folyamat lefutó kódja sebezhető, a támadó ugyanazokkal a jogokkal él tovább, mint maga a process. A MAC (mandatory access control) ezt a határt nem a tulajdonos döntésére bízza, hanem rendszerszintű policy-ből, a kernelbe épített enforcement pontokon. Szenior fejlesztőként a kapcsolódó rétegek ismerősek: a syscall a kernel felé vezető stabil belépési pont (d032), a capability és a service user pedig a folyamat minimális privilegizálásának eszköze (d073). Ebben az alfejezetben a SELinux, az AppArmor és a seccomp rétegeit tanítjuk meg úgy, hogy a hibát bizonyítékból javítsuk, ne a policy globális kikapcsolásából.

21.3.2 Definíciók: DAC, MAC, LSM és seccomp

A DAC döntése a fájlrendszer objektum tulajdonosi jogosultságaihoz és a folyamat identitásához kötött: a tulajdonos szabadon megváltoztathatja a jogosultságokat. A MAC olyan mandatory access control, ahol a döntést rendszerszintű policy határozza meg, és a tulajdonos ezt nem írhatja felül. A Linux kerneleben a MAC-ot az LSM (Linux Security Module) keretrendszer valósítja meg: a kernel a védett objektumok felé vezető kódszakaszokban hívja a regisztrált LSM hookokat, és a hook által hozott DENY döntés felülírja a DAC által már megadott engedélyt. A művelet csak akkor sikerülhet, ha a DAC és a MAC is engedélyezi.

A seccomp (secure computing) nem MAC, hanem syscall-szűrő: a folyamatot elindító vagy a folyamat maga korlátozza, hogy mely kernelbeli syscall belépési pontok hívhatók. A seccomp nem fájlutat, hanem syscall-számot, architektúrát és néhány syscall-argumentumot vizsgál; így a célja a kernel támadási felületének csökkentése, nem az állomány-hozzáférési döntés helyettesítése.

21.3.3 SELinux: label és type enforcement

A SELinux a RHEL-család elsődleges MAC rendszere. A döntés alapja a security context, amely minden processre és objektumra rákerül:

system_u:system_r:httpd_t:s0

A mezők: SELinux user, role, type, valamint a level. A gyakorlatban az enforcement a type enforcement (TE) réteg: a policy szabályai azt mondják meg, hogy egy source type (process domain) milyen target type-on, milyen object class-on és milyen permissionöket kaphat. A fájl context az inode-hoz kötött security.selinux xattr-ből vagy a kernelelméből származik; a döntés nem a path-tól függ, az ls -l nem mutatja. A ps -eZ, ls -Z és id -Z adja a contextet.

A label beállítása SELinuxban nem chmod kérdése. A semanage fcontext a rendszerszintű context-leképezést rögzíti, a restorecon pedig a meglévő fájlon a policy szerint javítja a labelt. A chcon csak ideiglenes, nem policy-állapot, ezért éles javításra alkalmatlan.

A denialt az AVC (Access Vector Cache) logolja, tipikusan az audit alrendszerbe. Ez a log a minimális policy-módosítás bizonyítéka: megmutatja, milyen source domain, target type, class és permission hiányzott.

21.3.4 AppArmor: path/profile modell

Az AppArmor az Ubuntu és Debian alapértelmezett MAC rendszere. A döntés alapja egy profile, amely a program hívási útjához kapcsolódik, és benne fájl path-okra, capabilitykre, hálózati műveletekre, mountokra stb. ad explicit engedélyt. A profile default deny: ami nincs engedélyezve, az megtagadott. A aa-status mutatja a profil betöltött állapotát. A aa-enforce a profile-t kényszerítő módba kapcsolja, az aa-complain csak naplóz; az utóbbi tanulásra való, productionben nem védelem.

A label itt nem inode-okra, hanem a folyamatot elindító path-ra és a profile-ban megadott path-szabályokra épül. Ha a programot más útvonalról másolják, a profile nem illeszkedik. A symlink és a rename is path-alapú témákat vet fel; ezeket az adminisztrációnál figyelni kell.

21.3.5 Seccomp syscall filter célja

A seccomp filter a folyamat syscall-támadási felületét csökkenti. Két klasszikus módja: SECCOMP_SET_MODE_STRICT, amely csak read, write, _exit és sigreturn hívásokat enged; és SECCOMP_SET_MODE_FILTER, amely egy BPF-programmal dönt. A döntés akciója lehet allow, kill, trap, vagy errno. A konténer runtime-ok (például Docker/Podman, containerd) gyakran alapértelmezett seccomp profile-t alkalmaznak, a Kubernetes pedig seccompProfile mezőt ad.

Rendszerszintű systemd szolgáltatásnál a seccomp filter deklaratívan is megadható:

[Service]
ExecStart=/opt/lab/bin/lab-svc /var/lib/lab-svc/data
User=lab-svc
NoNewPrivileges=true
SystemCallFilter=~@clock @module @mount
SystemCallErrorNumber=EPERM

A SystemCallFilter= lista a rendszerhívás-csoportokat adja meg, a ~ a tiltást jelenti. A pontos szintaxis systemd-verziófüggő, ezért a labrendszeren ellenőrizendő. A seccomp hibája gyakran EPERM vagy SIGSYS, nem EACCES; ez segít elkülöníteni a DAC/MAC hibától.

21.3.6 Distro/kernel/runtime támogatás

A kernel LSM-ek konfigurációfüggőek. Ubuntu Server 24.04 LTS-n az AppArmor van elsődlegesen bekapcsolva, RHEL-családon a SELinux. Egy hoston a SELinux és az AppArmor egyidejű kényszerítő használata production jelleggel nem szokványos; a disztribúció által választott LSM és a kernel lsm= paramétere a mérvadó. A labon az alábbiakkal ellenőrizhető:

grep -E 'CONFIG_SECURITY|CONFIG_SECURITY_APPARMOR|CONFIG_SECURITY_SELINUX' "/boot/config-$(uname -r)"
aa-status

A runtime rétegben a konténerek kaphatnak saját AppArmor/SELinux labelt és seccomp profile-t; ez már a konténer runtime-hoz kötött, és a verziók szerint változhat.

21.3.7 Kidolgozott példa: AppArmor denial javítása minimális policy-módosítással

A kiinduló rendszer: lab-vm, Ubuntu Server 24.04 LTS, adminisztrátor labops sudo joggal. A szolgáltatásfelhasználó lab-svc (UID 2001), a program /opt/lab/bin/lab-svc, az adatfájl /var/lib/lab-svc/data.

A C++ szolgáltatás egyszerű olvasóprogram:

#include <fcntl.h>
#include <unistd.h>
#include <cstdio>
#include <cstring>

int main(int argc, char** argv) {
    if (argc != 2) {
        std::fprintf(stderr, "usage: %s PATH\n", argv[0]);
        return 2;
    }
    int fd = open(argv[1], O_RDONLY);
    if (fd < 0) {
        std::perror("open");
        return 1;
    }
    char buf[128];
    ssize_t n = read(fd, buf, sizeof(buf) - 1);
    if (n < 0) {
        std::perror("read");
        return 1;
    }
    buf[n] = '\0';
    std::fputs(buf, stdout);
    close(fd);
    return 0;
}

Fordítás, a DAC-jogosultságok beállítása és a service user ellenőrzése:

# labops@lab-vm, UID 1000, sudo szükséges
g++ -std=c++20 -Wall -Wextra -O2 -o lab-svc lab-svc.cpp

sudo install -d -m 0750 -o lab-svc -g lab-svc /var/lib/lab-svc
sudo install -m 0755 -o lab-svc -g lab-svc ./lab-svc /opt/lab/bin/lab-svc
printf 'lab-svc data\n' | sudo tee /var/lib/lab-svc/data >/dev/null
sudo chown lab-svc:lab-svc /var/lib/lab-svc/data
sudo chmod 0640 /var/lib/lab-svc/data
id lab-svc

Ezután a DAC szerint a lab-svc user olvashatja a data fájlt. Az AppArmor profile-t szándékosan szűkre vesszük, hogy a denial reprodukálható legyen:

sudo tee /etc/apparmor.d/opt.lab.bin.lab-svc >/dev/null <<'PROFILE'
include <tunables/global>

profile lab-svc /opt/lab/bin/lab-svc {
  include <abstractions/base>
  /opt/lab/bin/lab-svc mr,
}
PROFILE

sudo apparmor_parser -r /etc/apparmor.d/opt.lab.bin.lab-svc
sudo aa-enforce /opt/lab/bin/lab-svc

Várható futtatási kimenet:

sudo -u lab-svc /opt/lab/bin/lab-svc /var/lib/lab-svc/data
# open: Permission denied

A DAC engedné, de az AppArmor profile nem tartalmaz engedélyt a /var/lib/lab-svc/data path-ra, ezért a MAC tagad. A bizonyíték a kernel log:

journalctl -k --grep 'apparmor="DENIED"' --since '5 minutes ago'

Várható, illusztratív log:

audit: type=1400 audit(...): apparmor="DENIED" operation="open" profile="lab-svc" name="/var/lib/lab-svc/data" pid=... comm="lab-svc" requested_mask="r" denied_mask="r" fsuid=2001 ouid=2001

A javítás: ne chmod 777, ne aa-complain élesben. Adjuk hozzá a minimális olvasási engedélyt a profile-hoz:

sudo tee /etc/apparmor.d/opt.lab.bin.lab-svc >/dev/null <<'PROFILE'
include <tunables/global>

profile lab-svc /opt/lab/bin/lab-svc {
  include <abstractions/base>
  /opt/lab/bin/lab-svc mr,
  owner /var/lib/lab-svc/data r,
}
PROFILE

sudo apparmor_parser -r /etc/apparmor.d/opt.lab.bin.lab-svc

Újra futtatva a program sikeresen kimenetet ad:

lab-svc data

Ellenőrzés: aa-status mutatja a lab-svc profile-t enforce módban, és a journalctl nem produksál új apparmor="DENIED" bejegyzést a futtatáshoz. A chmod 0666 ellenpróba nem oldja meg a MAC-denialt; a profile-módosítás az egyetlen helyes út.

21.3.8 SELinux példa: AVC-denial és minimális label javítás

Ugyanaz a szemlélet RHEL-családon, SELinuxszal: egy webszolgáltatás httpd_t domainje nem olvashat egy var_t típusú fájlt. A DAC 0644 lehet, a denial mégis fennáll. Az AVC log:

type=AVC msg=audit(...): avc:  denied  { read } for  pid=... comm="httpd" name="index.html" dev="vda1" ino=... scontext=system_u:system_r:httpd_t:s0 tcontext=unconfined_u:object_r:var_t:s0 tclass=file permissive=0

A log mezői közül a scontext a source domain, a tcontext a target label, a tclass az object class, a permissive=0 pedig azt mutatja, hogy a döntés kényszerített volt. A javítás:

# RHEL labhost, sudo user labops
sudo semanage fcontext -a -t httpd_sys_content_t '/srv/www(/.*)?'
sudo restorecon -Rv /srv/www
ls -Z /srv/www/index.html
# unconfined_u:object_r:httpd_sys_content_t:s0

Ez a minimális policy-módosítás a chmod -R 777 helyett. A setenforce 0 sem javítás, mert az csak a teljes SELinux enforcement kikapcsolása lenne.

21.3.9 Tipikus hibák és ellenpróbák

A rétegek szétválasztása a magyarázat kulcsa. A namei -l a path-felbontást és a DAC-bitjeidet mutatja; az AppArmor/SELinux log pedig a MAC-denialt. A strace a syscall hibáját mutatja: ha a rendszerhívás EPERM-et ad, gyanakodjunk seccompra; ha EACCES, akkor DAC vagy MAC. A log forrása a journalctl és/vagy az audit.

Réteg Döntés alapja Tipikus bizonyíték Helyes javítás
DAC UID/GID, mode, ACL ls -l, namei -l, getfacl chmod, chown, setfacl
SELinux type/context ausearch -m avc, ls -Z semanage fcontext, restorecon, policy-engedély
AppArmor path/profile apparmor="DENIED", aa-status profile-szabály, aa-logprof
seccomp syscall-szám, argumentum strace EPERM/SIGSYS syscall-filter szűkítés, SystemCallFilter

A leggyakoribb hibák:

  • A DAC és a MAC keverése. A chmod 777 nem oldja meg a SELinux/AppArmor tagadást, csak szélesebb DAC-nyílást ad. A helyes javítás a policy/label.
  • restorecon elmaradása. A semanage fcontext rögzíti a kívánt contextet, de a meglévő fájlokon a restorecon futása szükséges.
  • A aa-complain élesben hagyása. A complain módban a denial csak logolt, így a szolgáltatás futhat, de a MAC már nem véd.
  • A seccomp denialt fájlhibának nézni. A seccomp általában EPERM vagy SIGSYS, nem EACCES.
  • Globális kikapcsolás. setenforce 0, aa-disable vagy aa-complain élesben nem megoldás, mert a teljes védelmet eltávolítja. Diagnosztikai célból, jól körülhatárolt időre permissive mód használható, de a záró állapot az enforcing profile kell legyen.

21.3.10 Feladatok

21.3.10.1 1. feladat: Réteg meghatározása bizonyítékból

Adott az alábbi kimenet:

suso -u lab-svc /opt/lab/bin/lab-svc /var/lib/lab-svc/data
# open: Permission denied

ls -l /var/lib/lab-svc/data
# -rw-r----- 1 lab-svc lab-svc 15 Nov  1 10:00 /var/lib/lab-svc/data

aa-status | grep lab-svc
# lab-svc (enforce)

Melyik réteg tagad, és milyen további bizonyítékot kellene gyűjteni a pontos profile-döntéshez? Válaszát a DAC/MAC fogalmi modelljével indokolja.

21.3.10.2 2. feladat: Minimális AppArmor profile készítése

Készítse el a fenti lab-svc profile-t úgy, hogy a szolgáltatás a saját binaryjét olvashatja, a /var/lib/lab-svc/data fájlt olvashatja, de más /var/lib/lab-svc/-n belüli fájlt nem írhatja. Loadolja be a profile-t, és futtassa a szolgáltatást. Ellenőrizze, hogy a denial log megszűnt-e, és az aa-status enforce módot mutat-e. Ne használjon chmod-ot a MAC-hiba javítására.

21.3.10.3 3. feladat: SELinux AVC-denial javítása

Egy RHEL labhoston a /srv/www/index.html fájlt a HTTP-szolgáltatás nem tudja olvasni, annak ellenére, hogy ls -l szerint www-data-nak olvasási joga van. Gyűjtse ki az AVC-denialt, azonosítsa a tcontext-et, hozzon létre megfelelő semanage fcontext szabályt, futtassa a restorecon-t, és bizonyítsa, hogy a ls -Z context httpd_sys_content_t. A záró állapot legyen SELinux enforcing.

21.3.11 Megoldások

21.3.11.1 1. feladat megoldása

A ls -l alapján a DAC engedné: a fájl lab-svc tulajdonú, a tulajdonosi olvasás bit be van kapcsolva. A aa-status | grep lab-svc mutatja, hogy az AppArmor profile enforce módban van. Tehát a denialt a MAC, azon belül az AppArmor hozza. A pontos döntéshez a kernel logot kell megnézni:

journalctl -k --grep 'apparmor="DENIED"' --since '5 minutes ago'

A log profile="lab-svc", operation="open", name="/var/lib/lab-svc/data" mezői mutatják a hiányzó r jogot. A profile módosítása szükséges, nem DAC-változtatás.

21.3.11.2 2. feladat megoldása

A profil:

include <tunables/global>

profile lab-svc /opt/lab/bin/lab-svc {
  include <abstractions/base>
  /opt/lab/bin/lab-svc mr,
  owner /var/lib/lab-svc/data r,
}

A owner feltétel megszorítja, hogy a fájl a lab-svc user tulajdonában legyen. A profile nem enged más /var/lib/lab-svc/ alatti fájlt, mert a default deny miatt a profile-ban lévő szabályoknál szélesebb engedély nincs. Betöltés és ellenőrzés:

sudo apparmor_parser -r /etc/apparmor.d/opt.lab.bin.lab-svc
sudo aa-enforce /opt/lab/bin/lab-svc
sudo -u lab-svc /opt/lab/bin/lab-svc /var/lib/lab-svc/data
# lab-svc data

journalctl -k --grep 'apparmor="DENIED"' --since '5 minutes ago'
# nem jelenik meg új DENIED a futtatáshoz

aa-status | grep lab-svc
# lab-svc (enforce)

Postcondition: a profile enforced, a szolgáltatás olvassa a data fájlt, és az audit log nem mutat új denialt.

21.3.11.3 3. feladat megoldása

# RHEL labhost, sudo user labops
sestatus
# SELinux status: enabled, mode: enforcing

ausearch -m avc -ts recent
# avc: denied { read } ... scontext=...httpd_t... tcontext=...var_t...

A tcontext var_t, a source httpd_t. A javítás a path-hoz tartozó SELinux type beállítása:

sudo semanage fcontext -a -t httpd_sys_content_t '/srv/www(/.*)?'
sudo restorecon -Rv /srv/www
sudo systemctl restart httpd
ls -Z /srv/www/index.html
# unconfined_u:object_r:httpd_sys_content_t:s0
ausearch -m avc -ts recent | grep '/srv/www'
# nem jelenik meg új denial

Postcondition: SELinux enforcing, a /srv/www context httpd_sys_content_t, a web service hozzáfér a fájlhoz, és az AVC denial eltűnt.

21.3.12 Rövid összefoglaló

A Linux jogosultság rétegelt: a DAC (owner/group/mode/ACL) ellenőrzését a MAC (mandatory access control) LSM-szabályok egészítik ki, és a művelet csak akkor sikerül, ha mindkettő engedélyez. A SELinux type enforcement dolgozik, a hibát AVC-logból, semanage fcontext és restorecon eszközzel javítjuk. Az AppArmor path/profile modellben a aa-status, a kernel denial log és a profile minimális bővítése adja a javítást. A seccomp nem MAC, hanem syscall-filter; a kernel támadási felületét csökkenti, hibája gyakran EPERM. A denialt sohasem chmod 777-tel, hanem policy-bizonyíték alapján, minimális módosítással kezeljük. Továbbhasznált definíciók: DAC – tulajdonosi döntésű hozzáférés-vezérlés; MAC – rendszerszintű, tulajdonos által felül nem írható hozzáférés-vezérlés; seccomp – syscall-szűrő a kernelbeli belépési pontok korlátozására.
