16.1 Szálak, Send és Sync: data race fordítási időben kizárva

16.1.1 Motiváció

A C++ std::thread használatakor a fordító nem tudja megmondani, hogy egy megosztott objektumhoz való hozzáférés biztonságos-e. A data race definiálatlan viselkedés (UB), amelyet a szabvány csak tilt, de a fordítási folyamat nem ellenőriz. A Rust ezzel szemben a típusrendszerbe építi a szálbiztonságot: a Send és Sync marker trait-ek segítségével a fordító már fordítási időben kizárja a data race-hez vezető leggyakoribb mintákat. Ez a „félelem nélküli párhuzamosság” (fearless concurrency) alapja.

16.1.2 Fogalmak és szabályok

Definíció. A std::thread::spawn egy új operációsrendszer-szálat indít, és JoinHandle<T>-t ad vissza. A szignatúrája (egyszerűsítve):

pub fn spawn<F, T>(f: F) -> JoinHandle<T>
where
    F: FnOnce() -> T,
    F: Send + 'static,
    T: Send + 'static,

A F: FnOnce() -> T azt jelenti, hogy a closure egyszer lefuttatható, és a benne lévő értékeket elkölti. A 'static korlát azt követeli meg, hogy a closure nem tartalmazhat nem-'static referenciát; a szál a fő szál élettartamától függetlenül futhat. Ezért a closure-t általában move kulcsszóval írjuk, hogy a környezetéből tulajdonba vegye a szükséges értékeket, ne csak kölcsönözze őket. A korlát kikényszeríti, hogy a szál a saját adatával dolgozzon, vagy olyan adattal, amelynek a teljes élettartama garantáltan elég hosszú.

Definíció. A Send és Sync úgynevezett auto trait-ek: a fordító automatikusan implementálja őket egy típusra, ha minden mezőjük is Send/Sync. A szabályok:

  • Send: a típus értéke tulajdonjoggal átadható egy másik szálnak. Más szóval a mozgatás szálhatáron keresztül biztonságos.
  • Sync: a típusra mutató &T megosztható több szál között, azaz a referencia használata párhuzamosan biztonságos.

Ezek az auto trait-ek a fordító számára ismert belső szabályokból származnak. Például:

  • A primitív típusok (i32, bool, char, &str, stb.), valamint a String, Vec<T>, Box<T> általában Send + Sync, ha a belső típus is az.
  • Az Rc<T> nem Send és nem Sync, mert a referenciaszámláló növelése nem atomikus; két szál egyszerre módosíthatná a számlálót, ami data race.
  • Az Arc<T> (atomic reference counted) Send + Sync, ha T: Send + Sync, mert a számláló atomikus.
  • A RefCell<T> Send, ha T: Send, de nem Sync, mert a futásidejű kölcsönzés-számláló nem szálbiztos.
  • A Mutex<T>, RwLock<T>, AtomicUsize és társai tipikusan Send + Sync, ha a belső típus megfelelő; ezek a szálbiztos szinkronizációs primitívek.
  • A nyers mutatók (*const T, *mut T) nem Send és nem Sync, mert a memória hozzáférés szinkronizálása a programozó felelőssége.

Szabály. A Rust adatverseny-mentességi garanciája: ha a kód safe Rustban lefordul, akkor a data race kizárt. A Send/Sync auto trait-ek a típusrendszeren keresztül biztosítják, hogy egy érték ne jusson el olyan szálhoz, ahol a memóriához való hozzáférés nincs szinkronizálva. A szabály megszegése fordítási hibát okoz, nem UB-t.

16.1.3 C++ ↔︎ Rust összevetés

Tekintsünk egy tipikus C++ data race példát: két szál egyszerre növel egy közös int-et, szinkronizáció nélkül.

#include <thread>
#include <iostream>

int main() {
    int counter = 0;
    std::thread t1([&] { for (int i = 0; i < 1'000'000; ++i) ++counter; });
    std::thread t2([&] { for (int i = 0; i < 1'000'000; ++i) ++counter; });
    t1.join();
    t2.join();
    std::cout << counter << '\n'; // UB: data race
}

A C++ fordító ezt lefordítja, de a viselkedés definiálatlan – a kimenet nem garantált. A Rust megfelelő kódja fordítási hibát ad:

use std::thread;

fn main() {
    let mut counter = 0;
    thread::scope(|s| {
        s.spawn(|| {
            for _ in 0..1_000_000 {
                counter += 1; // hiba: counter nem Send/Sync
            }
        });
    });
}

A fordító hibaüzenete (a lényeg, a pontos szöveg verziófüggő, hibakód E0502 vagy E0373 jellemzően) arra utal, hogy a counter változóra hivatkozó closure nem teljesíti a Send vagy a 'static korlátot, mert a counter nem védett. A helyes Rust-megoldás Mutex vagy atomikus típus használata, amit az Mutex, RwLock, csatornák és a megosztott rkv alfejezet tárgyal.

A különbség: a C++ UB-t hagy a programban, a Rust pedig kikényszeríti a szinkronizációt a típusrendszeren keresztül.

16.1.4 Kidolgozott példa: szálak indítása move closure-rel és Rc vs. Arc

A következő laborban a szálak indítását, a move closure-t és az Rc/Arc különbséget gyakoroljuk.

Munkakönyvtár: ~/rust-labor/r033/

Hozzuk létre a projektet:

cd ~/rust-labor
cargo new r033
cd r033

Nyissuk meg a src/main.rs fájlt, és írjuk be az alábbi, szándékosan hibás kódot:

use std::rc::Rc;
use std::thread;

fn main() {
    let data = Rc::new(vec![1, 2, 3, 4, 5]);

    let handle = thread::spawn(move || {
        println!("Az adat hossza: {}", data.len());
    });

    handle.join().unwrap();
}

Futtassuk a cargo run parancsot. A fordító hibát ad, a hibakód jellemzően E0277: Rc<Vec<i32>> cannot be sent between threads safely. A hiba oka, hogy az Rc nem Send, ezért a move closure nem teljesíti a thread::spawn F: Send korlátját. Az Rc referenciaszámlálója nem atomikus, ezért két szál egyszerre módosíthatná, ami data race-hez vezetne.

Javítás: cseréljük le az Rc-t Arc-ra:

use std::sync::Arc;
use std::thread;

fn main() {
    let data = Arc::new(vec![1, 2, 3, 4, 5]);

    let handle = thread::spawn(move || {
        println!("Az adat hossza: {}", data.len());
    });

    handle.join().unwrap();
}

Futtassuk újra a cargo run parancsot. Várt kimenet:

Az adat hossza: 5

Ez a példa azt mutatja, hogy az Arc atomikus referenciaszámlálóval rendelkezik, ezért Send + Sync, míg az Rc nem az. Az Arc klónozása szálak között is biztonságos:

use std::sync::Arc;
use std::thread;

fn main() {
    let data = Arc::new(vec![1, 2, 3, 4, 5]);

    let mut handles = vec![];
    for _ in 0..4 {
        let data_clone = Arc::clone(&data);
        let handle = thread::spawn(move || {
            println!("Hossz: {}", data_clone.len());
        });
        handles.push(handle);
    }

    for handle in handles {
        handle.join().unwrap();
    }
}

Figyeljük meg: a move closure-rel minden szál saját Arc klónt kap, és a számláló atomikusan növekszik.

Ábra: Az Arc megosztása szálak között.

Az ábra azt mutatja, hogy az Arc másolatai ugyanarra a kupacobjektumra mutatnak, és a referenciaszámláló atomikusan növekszik. Az Rc ugyan hasonló elrendezésű, de a számláló növelése nem atomikus, ezért nem Send.

16.1.5 Scoped threads: kölcsönzés szálakba

A thread::spawn 'static korlátja miatt nem tudunk kölcsönzött referenciákat átadni a szálnak. A std::thread::scope ezt a korlátot oldja fel: a scope garantálja, hogy a benne indított szálak befejeződnek, mielőtt a scope-ból kilépünk. Így a szálak kölcsönözhetnek olyan adatokat, amelyek a scope-on kívül élnek, de nem 'static.

use std::thread;

fn main() {
    let mut data = vec![1, 2, 3, 4, 5];

    thread::scope(|s| {
        s.spawn(|| {
            println!("Első szál: {:?}", data);
        });

        s.spawn(|| {
            // A második szál módosíthatja is, ha nincs más kölcsönzés.
            data.push(6);
        });
    });

    println!("A scope után: {:?}", data);
}

Várt kimenet (a szálak sorrendje nem garantált, de a println! utáni módosítás miatt az első szál a [1, 2, 3, 4, 5]-öt látja, a második szál a push-t hajtja végre, és a fő szál a [1, 2, 3, 4, 5, 6]-ot írja ki):

Első szál: [1, 2, 3, 4, 5]
A scope után: [1, 2, 3, 4, 5, 6]

Fontos, hogy a fenti példában a két closure egyszerre hozzáfér a data-hoz; ha az első szál olvas, a második módosít, az ütközik a kölcsönzési szabállyal. A valós kódban ezt Mutex-szel vagy úgy kell megoldani, hogy a szálak ne férjenek hozzá egyszerre. A scope lényege, hogy a 'static korlát helyett a scope élettartama garantálja a biztonságot, de a kölcsönzési szabály továbbra is érvényes.

16.1.6 Tipikus hibák és átállási csapdák

  1. Rc használata szálak között. A leggyakoribb hiba, amikor a C++-os shared_ptr mintájára Rc-t próbálunk megosztani. A Rc nem Send és nem Sync; a megoldás Arc. A hibaüzenet (E0277) világos: a típus nem teljesíti a Send korlátot. Továbbvitt eredmény. Ez a különbségtétel az Mutex, RwLock, csatornák és a megosztott rkv alfejezetben az Arc<Mutex<Store>> mintához vezet; a Send-határok az aszinkron kódban, a C ABI pedig az FFI-ban használja a Send/Sync fogalmát.

  2. move closure elfelejtése. Ha a closure nem move, a környezetéből kölcsönzött értékek nem 'static, ezért a thread::spawn hibát ad. A hibakód E0373 vagy E0521 jellemzően. A megoldás a move használata, vagy ha a kölcsönzés szükséges, a thread::scope alkalmazása.

  3. RefCell<T> megosztása. A RefCell futásidejű kölcsönzést biztosít, de nem szálbiztos. Ha több szálból akarunk hozzáférni, a Mutex vagy RwLock a megfelelő választás. Ez a hiba gyakran akkor jelentkezik, amikor az Rc<RefCell<T>> mintát próbáljuk több szálra kiterjeszteni; a helyettesítés Arc<Mutex<T>>.

  4. 'static korlát figyelmen kívül hagyása. A thread::spawn által megkövetelt 'static azt jelenti, hogy a closure-nek nem lehet nem-'static referenciája. Ha a fő szál adatait szeretnénk látni, a move closure-rel tulajdonba kell venni az értéket, vagy Arc-ot használni.

16.1.8 Megoldások

16.1.8.1 1. Feladat megoldása

A kód nem fordul le, mert Rc nem Send. A hibaüzenet jellemzően E0277. Javítás: cserélje Rc-t Arc-ra:

use std::sync::Arc;
use std::thread;

fn main() {
    let s = Arc::new(String::from("hello"));
    let handle = thread::spawn(move || {
        println!("{}", s);
    });
    handle.join().unwrap();
}

16.1.8.2 2. Feladat megoldása

Idiomatikus Rust-átírás:

use std::sync::Arc;
use std::thread;

fn main() {
    let v = Arc::new(vec![1, 2, 3, 4, 5]);
    let v_clone = Arc::clone(&v);
    let handle = thread::spawn(move || {
        for x in v_clone.iter() {
            print!("{} ", x);
        }
    });
    handle.join().unwrap();
}

A kimenet: 1 2 3 4 5.

16.1.8.3 3. Feladat megoldása

Először hozzuk létre a fájlt, ha nem létezik. A Store egyelőre üres:

// rkv-core/src/store.rs
use std::sync::{Arc, Mutex};

#[derive(Default)]
pub struct Store {
    // A tényleges adattagokat később adjuk hozzá.
}

#[derive(Clone)]
pub struct SharedStore {
    inner: Arc<Mutex<Store>>,
}

impl SharedStore {
    pub fn new() -> Self {
        Self {
            inner: Arc::new(Mutex::new(Store::default())),
        }
    }

    pub fn report(&self) -> String {
        let guard = self.inner.lock().unwrap();
        format!("A tároló állapota: {:?}", *guard)
    }
}

A report metódus egy szálban is hívható, mert a Mutex biztosítja a kizárólagos hozzáférést, és az Arc a megosztást.

16.1.8.4 4. Feladat megoldása

A hibát a thread::spawn 'static korlátja okozza. Javítás thread::scope-pal:

use std::thread;

fn main() {
    let data = vec![10, 20, 30];
    thread::scope(|s| {
        s.spawn(|| {
            println!("{:?}", data);
        });
    });
}

A thread::scope garantálja, hogy a szál befejeződik, mielőtt a data kimegy a hatókörből.

16.1.9 Rövid összefoglaló

A Rust std::thread::spawn egy 'static korlátos, Send closure-t vár el, és JoinHandle<T>-t ad vissza, amelynek join metódusa várja a szál végét. A Send és Sync auto trait-ek fordítási időben garantálják, hogy egy típus értéke átadható (Send) vagy referenciája megosztható (Sync) szálak között. Az Rc<T> nem Send, mert nem atomikus referenciaszámlálót használ; az Arc<T> viszont Send + Sync, ha T is az. A thread::scope lehetővé teszi nem-'static referenciák kölcsönzését szálakba, mert a scope garantálja a szálak befejeződését. A C++-ban a data race UB, a Rustban a Send/Sync rendszer kizárja a versenyhelyzetet a safe kódban. Továbbvitt eredmény. A Send/Sync fogalma alapozza meg a Mutex, RwLock, csatornák és a megosztott rkv alfejezet Arc<Mutex<Store>> mintáját, a Future-ök és async/await Send-határait, és a C ABI FFI-biztonsági megfontolásait.

16.1.10 Források és ellenőrzési hiányok

A pontos hibaüzenetek (E0277, E0373, E0502) verziófüggők, ezért csak a hibakódot és a hiba lényegét adtam meg.
