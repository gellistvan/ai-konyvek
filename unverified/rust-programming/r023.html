11.3 I/O és szerializáció: fájlok, pufferelés, serde

11.3.1 Motiváció

C++-ban az iostream-réteg (std::ifstream, std::ofstream, std::cin) pufferel, formáz és kényelmes operátorokat ad, de a hibakezelés gyakran „utólagos”: a streamek hibazászlókat állítanak, és a kódban ez a rész gyakran ellenőrizetlen marad. Rustban minden I/O-művelet Result-ot ad; a ? operátorral a hibaterjedés explicit, a fordító pedig figyelmeztet, ha egy Result-ot figyelmen kívül hagynánk. A std::io traitjei ráadásul nem fájlra vagy socketre szabottak: ugyanaz a Read/Write implementáció működik fájllal, hálózattal, pufferrel vagy éppen egy teszt-Vec-kel.

Ebben az alfejezetben ezeket a trait-eket használjuk, bemutatjuk a serde-alapú szerializációt, és egy valódi, hibatűrő perzisztenciaréteget építünk az rkv számára: snapshot plusz hozzáfűzéses napló. Ez lesz a FileStore, amelyet később a Storage trait mögé emelünk, és a hálózati szerver is használ majd.

11.3.2 Fogalmak és szabályok

Definíció. A std::io::Read trait egy bájtsorozat olvasását modellezi. A központi metódusa:

fn read(&mut self, buf: &mut [u8]) -> io::Result<usize>;

A read legfeljebb buf.len() bájtot olvas be, és a ténylegesen beolvasott bájtok számát adja vissza. A 0 érték a fájl végét (EOF) jelenti normál esetben. A trait kényelmi metódusokat is ad: read_to_end, read_to_string, read_exact.

Szabály. Soha ne feltételezd, hogy egyetlen read hívás teleolvassa a puffert. A read_exact garantálja a teljes puffer beolvasását, a read_to_end pedig a teljes bemenetet gyűjti be. Fájl esetén a gyakorlatban gyakran működik a teli puffer, de hálózaton, pipe-on csomagokban érkezhet az adat.

Definíció. A std::io::Write trait a kimeneti bájtsorozatot modellezi:

fn write(&mut self, buf: &[u8]) -> io::Result<usize>;
fn flush(&mut self) -> io::Result<()>;

A write a puffer egy részét is kiírhatja; a teljes puffer garantált kiírásához a write_all kényelmi metódust vagy a writeln! makrót használjuk. A flush a pufferelt adatot azonnal a háttérbe küldi.

Definíció. A std::io::BufRead a Read-et belső pufferrel bővíti, és sorolvasó kényelmi metódusokat ad: read_line, lines, split. A BufReader<T> egy Read implementáló típus köré húz puffert; a BufWriter<T> egy Write implementáló típus köré.

Definíció. A Path nem birtokló, platformfüggetlen nézet egy fájlrendszerbeli elérési útra; a PathBuf ennek birtokló, módosítható változata. Ez hasonló a std::string_view és a std::string viszonyához, csak itt fájlrendszeri utakra.

Definíció (atomikus csere). Ha egy állapotfájlt úgy mentünk, hogy először egy ideiglenes fájlt írunk tele, flush-elünk és sync_all-lal a lemezre kényszerítjük, majd std::fs::rename-nel a végleges névre nevezzük át, a meglévő állapotfájl soha nem lesz félkész. Linuxon a rename azonos fájlrendszeren atomikus csereként működik; ahhoz, hogy maga a csere is túlélje az áramkimaradást, a szülőkönyvtárat is szinkronizálni kell. A flush csak a Rust-oldali puffert üríti az operációs rendszer felé, a lemezre írást nem garantálja. A Rust File::create a célfájlt lenullázva nyitja meg, ezért önmagában nem alkalmas törésbiztos mentésre.

Definíció (hozzáfűzéses napló). Az append-only log minden mutációs műveletet a fájl végéhez fűz. Újraindításkor a legutóbbi snapshotot betöltjük, majd a naplót sorról sorra visszajátsszuk. A compact művelet tartós snapshotot készít, és csak ezután nullázza le a naplót.

11.3.3 C++ és Rust összevetés

C++-ban a fájl olvasása és a hiba ellenőrzése gyakran így néz ki:

#include <fstream>
#include <iostream>
#include <string>

int main() {
    std::ifstream in("input.txt");
    if (!in) {
        std::cerr << "open failed\n";
        return 1;
    }
    std::string line;
    while (std::getline(in, line)) {
        std::cout << line << '\n';
    }
    if (in.bad()) return 2; // sokszor elmarad
}

A Rust-változat minden lépés Result-ját továbbadja:

use std::fs::File;
use std::io::{self, BufRead, BufReader};

fn main() -> io::Result<()> {
    let file = File::open("input.txt")?;
    for line in BufReader::new(file).lines() {
        println!("{}", line?);
    }
    Ok(())
}

A különbség: a ? nem hagyja, hogy a File::open vagy a sorolvasás hibája észrevétlen maradjon. A lines() a sor elejét és végét leválasztja, de a sortörést nem adja vissza; a C++ getline ugyanezt teszi eltérő vonalazási részletekkel. A Rust File nem pufferelt, ezért a hatékony sorolvasáshoz BufReader kell; a C++ streamek alapból pufferelnek.

11.3.4 Kidolgozott példa: generikus Read/Write

A Read és Write trait-ek ereje abban van, hogy nem kötődnek fájlhoz. Ugyanaz a függvény működik fájllal, bájttömbbel vagy hálózati streammel:

use std::io::{self, Read, Write};

fn copy_all<R: Read, W: Write>(mut from: R, mut to: W) -> io::Result<u64> {
    io::copy(&mut from, &mut to)
}

Szerializációhoz a serde a deriválható Serialize és Deserialize trait-eket adja. Az rkv-core Cargo.toml-jába a következő függőségek kerülnek:

Példa JSON-mentésre:

use serde::{Deserialize, Serialize};
use std::collections::BTreeMap;
use std::fs::File;
use std::io::{BufWriter, Write}; // a Write trait kell a flush() híváshoz

#[derive(Serialize, Deserialize)]
struct Config {
    port: u16,
    entries: BTreeMap<String, Vec<u8>>,
}

fn save_config(config: &Config, path: &str) -> std::io::Result<()> {
    let file = File::create(path)?;
    let mut writer = BufWriter::new(file);
    serde_json::to_writer(&mut writer, config)?;
    writer.flush()?;
    Ok(())
}

A serde_json::to_writer bármely Write implementáló típusra dolgozik, ezért a BufWriter pufferezését egyszerűen kihasználjuk. A flush a Write trait metódusa, ezért a traitet importálni kell (use std::io::Write); e nélkül a hívás E0599-cel nem fordul le. A ? itt a serde_json::Error-t is io::Error-rá alakítja, mert a serde_json biztosít ilyen From implementációt. Bináris formátumhoz a bincode crate használható; az rkv nem használja, és mivel az 1.x és a 2.x főverzió API-ja jelentősen eltér, a használatához a választott főverzió docs.rs-oldalát kell követni.

A serde_json olvasható és könnyen debuggolható, ezért az rkv naplójához és snapshotjához ezt használjuk. A bináris bincode kisebb, de olvashatatlan; beágyazott vagy nagy forgalmú rendszereknél jobb választás lehet.

use std::collections::HashMap;
use std::fs::{self, File, OpenOptions, TryLockError};
use std::io::{self, BufRead, BufReader, BufWriter, Write};
use std::path::{Path, PathBuf};
use serde::{Deserialize, Serialize};

use crate::{Error, Result};

#[derive(Debug, Clone, Serialize, Deserialize)]
struct Snapshot {
    data: HashMap<String, Vec<u8>>,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
enum LogEntry {
    Set { key: String, value: Vec<u8> },
    Delete { key: String },
}

pub struct FileStore {
    data: HashMap<String, Vec<u8>>,
    log_writer: BufWriter<File>,
    snapshot_path: PathBuf,
    /// Egy sikertelen naplóírás után igaz: a tároló nem fogad több írást.
    poisoned: bool,
}

impl FileStore {
    pub fn open(snapshot_path: impl AsRef<Path>, log_path: impl AsRef<Path>) -> Result<Self> {
        let snapshot_path = snapshot_path.as_ref().to_path_buf();
        let log_path = log_path.as_ref();

        // Kizárólagos használat: a naplófájlra tett zár miatt egyszerre csak
        // egy FileStore (egy folyamat) írhatja a tárolót. A zár a fájl
        // lezárásakor, a FileStore eldobásakor oldódik fel.
        let log_file = OpenOptions::new().create(true).append(true).open(log_path)?;
        match log_file.try_lock() {
            Ok(()) => {}
            Err(TryLockError::WouldBlock) => {
                return Err(Error::Io(io::Error::new(
                    io::ErrorKind::WouldBlock,
                    "a tárolót már egy másik FileStore használja",
                )));
            }
            Err(TryLockError::Error(e)) => return Err(e.into()),
        }

        let mut data = HashMap::new();
        if snapshot_path.exists() {
            let file = File::open(&snapshot_path)?;
            let reader = BufReader::new(file);
            let snap: Snapshot = serde_json::from_reader(reader)?;
            data = snap.data;
        }

        let valid_len = replay_log(log_path, &mut data)?;
        if log_file.metadata()?.len() > valid_len {
            // Csonka (nem commitolt) utolsó rekord levágása, hogy az új
            // bejegyzések ne félkész sor mögé kerüljenek.
            log_file.set_len(valid_len)?;
            log_file.sync_all()?;
        }
        let log_writer = BufWriter::new(log_file);

        Ok(Self {
            data,
            log_writer,
            snapshot_path,
            poisoned: false,
        })
    }

    pub fn get(&self, key: &str) -> Option<&Vec<u8>> {
        self.data.get(key)
    }

    pub fn set(&mut self, key: String, value: Vec<u8>) -> Result<()> {
        let entry = LogEntry::Set { key: key.clone(), value: value.clone() };
        self.append_entry(&entry)?;
        // Csak a tartós naplórekord után módosul a memóriabeli állapot.
        self.data.insert(key, value);
        Ok(())
    }

    pub fn delete(&mut self, key: &str) -> Result<()> {
        if !self.data.contains_key(key) {
            return Ok(());
        }
        let entry = LogEntry::Delete { key: key.to_string() };
        self.append_entry(&entry)?;
        self.data.remove(key);
        Ok(())
    }

    fn ensure_healthy(&self) -> Result<()> {
        if self.poisoned {
            return Err(std::io::Error::other(
                "a napló egy korábbi írási hiba óta sérült; nyisd meg újra a tárolót",
            )
            .into());
        }
        Ok(())
    }

    /// Commit-szerződés: a teljes rekord (JSON + '\n') kiírása, flush és
    /// sync_data. Csak Ok esetén szabad a memóriabeli állapotot módosítani.
    fn append_entry(&mut self, entry: &LogEntry) -> Result<()> {
        self.ensure_healthy()?;
        let mut line = serde_json::to_vec(entry)?;
        line.push(b'\n');
        let res = self
            .log_writer
            .write_all(&line)
            .and_then(|()| self.log_writer.flush())
            .and_then(|()| self.log_writer.get_ref().sync_data());
        if let Err(e) = res {
            // A pufferben vagy a fájlban félkész rekord maradhatott:
            // vakon nem folytatjuk a naplózást.
            self.poisoned = true;
            return Err(e.into());
        }
        Ok(())
    }

    pub fn list(&self, prefix: Option<&str>) -> Vec<(String, Vec<u8>)> {
        let mut items: Vec<_> = self
            .data
            .iter()
            .filter(|(k, _)| prefix.is_none_or(|p| k.starts_with(p)))
            .map(|(k, v)| (k.clone(), v.clone()))
            .collect();
        items.sort_by(|a, b| a.0.cmp(&b.0));
        items
    }

    pub fn save_snapshot(&mut self) -> Result<()> {
        self.ensure_healthy()?;
        let tmp_path = self.snapshot_path.with_extension("json.tmp");
        // A File::create az ideiglenes fájlt nullázza le, a régi snapshotot nem.
        let file = File::create(&tmp_path)?;
        let mut writer = BufWriter::new(file);
        serde_json::to_writer(&mut writer, &Snapshot { data: self.data.clone() })?;
        writer.flush()?;
        writer.get_ref().sync_all()?; // 1. az új tartalom a lemezen van
        drop(writer);
        fs::rename(&tmp_path, &self.snapshot_path)?; // 2. atomikus csere
        sync_parent_dir(&self.snapshot_path)?; // 3. maga a csere is tartós
        Ok(())
    }

    pub fn compact(&mut self) -> Result<()> {
        self.save_snapshot()?; // 1–3. lépés: az új snapshot tartós
        // 4. Csak ezután dobható el a napló.
        let log = self.log_writer.get_mut();
        log.set_len(0)?;
        log.sync_all()?;
        Ok(())
    }
}

/// POSIX-on a rename a szülőkönyvtár szinkronizálása után tartós.
#[cfg(unix)]
fn sync_parent_dir(path: &Path) -> Result<()> {
    let dir = match path.parent() {
        Some(p) if !p.as_os_str().is_empty() => p,
        _ => Path::new("."),
    };
    File::open(dir)?.sync_all()?;
    Ok(())
}

#[cfg(not(unix))]
fn sync_parent_dir(_path: &Path) -> Result<()> {
    // Nem POSIX-platformon könyvtár így nem szinkronizálható; lásd a
    // tartóssági modellt a labor után.
    Ok(())
}

/// Visszajátssza a naplót, és visszaadja az utolsó teljes rekord végének
/// bájtpozícióját.
fn replay_log(path: &Path, data: &mut HashMap<String, Vec<u8>>) -> Result<u64> {
    let file = match File::open(path) {
        Ok(f) => f,
        Err(e) if e.kind() == std::io::ErrorKind::NotFound => return Ok(0),
        Err(e) => return Err(e.into()),
    };
    let mut reader = BufReader::new(file);
    let mut line = Vec::new();
    let mut valid_len = 0u64;
    loop {
        line.clear();
        let n = reader.read_until(b'\n', &mut line)?;
        if n == 0 || line.last() != Some(&b'\n') {
            // Fájl vége, vagy sorvégjel nélküli csonka rekord: ez utóbbi
            // sosem kapott Ok-t, mert az append_entry a teljes sort írja.
            break;
        }
        valid_len += n as u64;
        if line.trim_ascii().is_empty() {
            continue;
        }
        // A sorvégjellel lezárt, de hibás rekord valódi sérülés: hiba.
        let entry: LogEntry = serde_json::from_slice(&line)?;
        match entry {
            LogEntry::Set { key, value } => {
                data.insert(key, value);
            }
            LogEntry::Delete { key } => {
                data.remove(&key);
            }
        }
    }
    Ok(valid_len)
}

A felhasznált újabb std API-k: a File::try_lock az 1.89-től, a trim_ascii az 1.80-tól, az io::Error::other az 1.74-től stabil; a könyv rögzített toolchainje (1.99.1) mindhármat tartalmazza.

11.3.5.0.3 3. Unit tesztek

A tesztek a file_store.rs alján kapnak helyet, és a perzisztencia egy-egy esetét külön ellenőrzik: csak snapshotból, csak naplóból, illetve snapshotból és az utána írt naplóból való újranyitást; a törlést és a felülírást; azt, hogy a commitolt rekord az eldobás előtt már a fájlban van; a csonka utolsó rekordot; a hibázó naplóírást; és a kettős megnyitás elutasítását. Ha a replay_log hívását kikapcsolnánk, legalább a log_only_reopen teszt elbukna: a tartósságot így nem puszta fájllétezéssel, hanem a visszaolvasott állapottal igazoljuk. A failed_append_leaves_committed_state a modulon belüli privát mezőhöz fér hozzá, és a naplóírót egy csak olvasásra megnyitott fájlra cseréli: ez a Write implementáció biztosan hibával tér vissza.

Kódblokk — fájl: rkv-core/src/store/file_store.rs · művelet: beillesztés a fájl végére · ellenőrzés: cargo test -p rkv-core file_store → 8 sikeres teszt

#[cfg(test)]
mod tests {
    use super::*;

    /// Tesztenként egyedi, üres könyvtár (a név a tesztet, a pid a futást különíti el).
    fn fresh_dir(name: &str) -> (PathBuf, PathBuf) {
        let dir = std::env::temp_dir().join(format!(
            "rkv-file-store-{name}-{}",
            std::process::id()
        ));
        let _ = std::fs::remove_dir_all(&dir);
        std::fs::create_dir_all(&dir).unwrap();
        (dir.join("state.json"), dir.join("append.log"))
    }

    fn get(store: &FileStore, key: &str) -> Option<Vec<u8>> {
        store.get(key).cloned()
    }

    #[test]
    fn snapshot_only_reopen() {
        let (snap, log) = fresh_dir("snap");
        {
            let mut store = FileStore::open(&snap, &log).unwrap();
            store.set("a".into(), b"1".to_vec()).unwrap();
            store.set("b".into(), b"2".to_vec()).unwrap();
            store.compact().unwrap();
        }
        assert_eq!(std::fs::metadata(&log).unwrap().len(), 0); // a napló üres
        let store = FileStore::open(&snap, &log).unwrap();
        assert_eq!(get(&store, "a"), Some(b"1".to_vec()));
        assert_eq!(get(&store, "b"), Some(b"2".to_vec()));
    }

    #[test]
    fn log_only_reopen() {
        let (snap, log) = fresh_dir("log");
        {
            let mut store = FileStore::open(&snap, &log).unwrap();
            store.set("a".into(), b"1".to_vec()).unwrap();
            store.set("b".into(), b"2".to_vec()).unwrap();
            store.delete("a").unwrap();
            store.set("b".into(), b"3".to_vec()).unwrap(); // felülírás
        }
        assert!(!snap.exists()); // csak a napló hordozza az állapotot
        let store = FileStore::open(&snap, &log).unwrap();
        assert_eq!(get(&store, "a"), None);
        assert_eq!(get(&store, "b"), Some(b"3".to_vec()));
    }

    #[test]
    fn snapshot_plus_new_log() {
        let (snap, log) = fresh_dir("both");
        {
            let mut store = FileStore::open(&snap, &log).unwrap();
            store.set("a".into(), b"1".to_vec()).unwrap();
            store.compact().unwrap();
            store.set("b".into(), b"2".to_vec()).unwrap();
            store.delete("a").unwrap();
        }
        let store = FileStore::open(&snap, &log).unwrap();
        assert_eq!(get(&store, "a"), None);
        assert_eq!(get(&store, "b"), Some(b"2".to_vec()));
    }

    #[test]
    fn commit_is_in_file_before_drop() {
        let (snap, log) = fresh_dir("commit");
        let mut store = FileStore::open(&snap, &log).unwrap();
        store.set("k".into(), b"v".to_vec()).unwrap();
        // A store még él, nem futott Drop és nem hívtunk flush-t:
        // az Ok után a rekordnak már a fájlban kell lennie.
        let text = std::fs::read_to_string(&log).unwrap();
        assert!(text.ends_with('\n') && text.contains("\"k\""));
    }

    #[test]
    fn torn_tail_is_dropped() {
        let (snap, log) = fresh_dir("torn");
        {
            let mut store = FileStore::open(&snap, &log).unwrap();
            store.set("a".into(), b"1".to_vec()).unwrap();
        }
        // Összeomlás közbeni, félbemaradt rekord szimulálása.
        let mut f = OpenOptions::new().append(true).open(&log).unwrap();
        f.write_all(br#"{"Set":{"key":"b","val"#).unwrap();
        drop(f);

        let mut store = FileStore::open(&snap, &log).unwrap();
        assert_eq!(get(&store, "a"), Some(b"1".to_vec()));
        assert_eq!(get(&store, "b"), None);
        store.set("c".into(), b"3".to_vec()).unwrap();
        drop(store);

        let store = FileStore::open(&snap, &log).unwrap();
        assert_eq!(get(&store, "c"), Some(b"3".to_vec()));
    }

    #[test]
    fn failed_append_leaves_committed_state() {
        let (snap, log) = fresh_dir("fail");
        let mut store = FileStore::open(&snap, &log).unwrap();
        store.set("a".into(), b"1".to_vec()).unwrap();

        // Szándékosan hibázó író: csak olvasásra nyitott fájl.
        store.log_writer = BufWriter::new(File::open(&log).unwrap());
        assert!(store.set("b".into(), b"2".to_vec()).is_err());
        assert_eq!(get(&store, "b"), None); // a memória nem változott
        assert!(store.set("c".into(), b"3".to_vec()).is_err()); // mérgezett
        assert!(store.compact().is_err());
        drop(store);

        let store = FileStore::open(&snap, &log).unwrap();
        assert_eq!(get(&store, "a"), Some(b"1".to_vec()));
        assert_eq!(get(&store, "b"), None);
        assert_eq!(get(&store, "c"), None);
    }

    #[test]
    fn second_open_is_rejected() {
        let (snap, log) = fresh_dir("lock");
        let first = FileStore::open(&snap, &log).unwrap();
        assert!(matches!(FileStore::open(&snap, &log), Err(Error::Io(_))));
        drop(first); // a zár feloldódik
        assert!(FileStore::open(&snap, &log).is_ok());
    }

    #[test]
    fn compact_is_idempotent() {
        let (snap, log) = fresh_dir("idem");
        let mut store = FileStore::open(&snap, &log).unwrap();
        store.set("a".into(), b"1".to_vec()).unwrap();
        store.compact().unwrap();
        store.compact().unwrap();
        drop(store);
        let store = FileStore::open(&snap, &log).unwrap();
        assert_eq!(get(&store, "a"), Some(b"1".to_vec()));
    }
}

Commit-szerződés. A set és a delete csak akkor tér vissza Ok-val, ha a teljes, sorvégjellel lezárt naplórekord kiíródott, és a sync_data is sikerült; a memóriabeli állapotot csak ezután módosítjuk. Err esetén két dolog garantált: a memóriabeli állapot nem tartalmazza a műveletet, és a tároló mérgezett lesz, vagyis minden további írás és compact hibát ad, amíg újra nem nyitjuk. A művelet tartós kimenetele viszont Err után bizonytalan: ha a rekord kiíródott, de a sync_data hibázott, az újranyitás a műveletet már tartalmazhatja. Ez minden naplózó adatbázis közös tulajdonsága; a hívó ilyenkor újranyitással és olvasással tudja meg az eredményt.

Tartóssági modell. Az alábbi garanciák Linuxon, helyi POSIX-fájlrendszeren (ext4, XFS) érvényesek, feltéve, hogy a háttértár a gyorsítótár-ürítési kéréseket betartja. Hálózati fájlrendszerre (NFS, SMB) és nem POSIX-platformra a könyv nem ad garanciát. Windowson a könyvtár nem szinkronizálható a fenti módon, ott a MoveFileExW MOVEFILE_WRITE_THROUGH kapcsolója a megfelelő eszköz (ellenőrzési igény). A compact lépései és az összeomlás utáni helyreállítás:

Összeomlás pontja Lemezen maradó állapot Újranyitás eredménye
1. az ideiglenes snapshot írása vagy sync_all-ja közben régi snapshot + teljes napló (+ félkész .json.tmp) a régi snapshot + napló visszajátszása: teljes állapot
2. a rename előtt vagy közben régi vagy új snapshot, mindkét esetben teljes napló a csere atomikus, a teljes állapot visszaáll
3. a rename után, a könyvtár sync_all-ja előtt a régi vagy az új könyvtárbejegyzés tartós mint a 2. pontban
4. a napló csonkolása közben új snapshot + teljes vagy üres napló a napló a snapshotra visszajátszva ugyanazt az állapotot adja

A 4. sor azért helyes, mert a napló Set/Delete rekordjainak sorrendben való újrajátszása a snapshot állapotára ugyanazt a végállapotot adja: a snapshot már a napló végének állapota, az újrajátszás pedig csak ugyanezeket az értékeket írja felül. A napló eldobása ezért csak a 3. lépés után biztonságos.

Kizárólagos használat és ideiglenes fájl. A FileStore::open a naplófájlra kizárólagos zárat tesz (File::try_lock), ezért ugyanazt a tárolót egyszerre csak egy FileStore nyithatja meg; a második megnyitás Error::Io (WouldBlock) hibát kap. A zár miatt a snapshot ideiglenes fájljának rögzített neve (state.json.tmp) sem ütközhet: egyetlen író van. A zár tanácsadó (advisory) jellegű: csak a szintén zárat kérő folyamatokat tartja távol, egy a fájlt zár nélkül író külső program ellen nem véd.

Mit igazol és mit nem a teszt. A fenti unit tesztek a bezárás-újranyitást (snapshotból, naplóból és a kettőből), azt, hogy a commitolt rekord az eldobás előtt már a fájlban van, a csonka utolsó rekordot, a hibázó írót és a kettős megnyitást ellenőrzik. Nem igazolják az áramkimaradás-tűrést: a processz leállása után az operációs rendszer lapgyorsítótára megmarad, ezért az fsync hiánya ilyen teszttel nem mutatható ki. A fázisonkénti hibainjektálási tervhez minden táblázatsor elé egy hibapont kerül (például egy fail_at: Option<Phase> mező csak tesztbuildben, amely a megadott fázisban Err-t ad vagy std::process::abort()-ot hív), utána újranyitás és állapot-összevetés következik. Valódi áramkimaradást virtuális gépben, a lemez hirtelen leválasztásával, vagy a Linux dm-flakey / dm-log-writes eszközével lehet modellezni; ez a könyv laborján kívül esik.

A napló megnyitásánál az OpenOptions::new().append(true).create(true) biztosítja, hogy a fájl létezzen, és minden írás a végére kerüljön. A replay_log a hiányzó naplófájlt elfogadja első indításkor, a tényleges I/O-hibát viszont továbbadja.

Továbbvitt eredmény. A FileStore perzisztenciáját a Trait-ek és generikusok: sablonok és concepts helyett alfejezet a Storage trait mögé emeli, a Az rkv hálózati szerver: TCP, protokoll, kecses leállás alfejezetben a rkv-server használja, a Záróprojekt: az rkv teljes rendszerként alfejezetben pedig a teljes rendszer része lesz.

Ellenőrzési pont. Az rkv-core a Store mellett a FileStore-t is exportálja (rkv_core::FileStore, a store/file_store.rs-ben), az Error a Serialization variánssal teljes. A cargo test -p rkv-core a 7 korábbi unit teszt mellett a 8 file_store tesztet is sikeresen futtatja (Rust 1.99.1, serde 1, serde_json 1, thiserror 2). Az rkv-cli változatlanul fordul (cargo build --workspace); a CLI-t a Trait-ek és generikusok: sablonok és concepts helyett alfejezet köti a FileStore-hoz, amikor a két tároló közös Storage trait mögé kerül.

11.3.6 Tipikus hibák és átállási csapdák

  1. Egyetlen read hívásra alapozni. A read nem garantálja, hogy a puffer tele lesz; a read_to_end, read_to_string vagy read_exact használata a helyes. C++-os beidegződés, hogy a istream::read teljes rekordot vár; Rustban ez explicit.

  2. A writeln! eredményét elhagyni. A writeln! io::Result-ot ad; ha nem használjuk a ?-et, a kód lefordulhat #[must_use] figyelmeztetéssel, de a hiba elveszik. A könyvtári kódban mindig ?.

  3. A BufWriter Drop-jára hagyatkozni. A BufWriter Drop-implémenzciója megpróbálja ugyan a puffert kiüríteni, de a hibát elnyeli. Ha a lemez megtelt, az adatvesztés némán következhet be. A fontos kimeneteket explicit flush-sel zárjuk; ha tartósság is kell, utána sync_all/sync_data következik.

  4. A File::create atomikus cserével való összekeverése. A File::create azonnal lenullázza a célfájlt. Ha a mentés közben a processz leáll, az eredeti állapot is elveszik. A helyes minta: ideiglenes fájl, flush, sync_all, rename, majd a szülőkönyvtár szinkronizálása.

  5. A napló visszajátszásának túlzott szigora. Ha a processz a naplósor felénél áll le, a serde_json parse hiba lehet. A szigorú ? ilyenkor a teljes indítást megakadályozza. Az rkv ezért különbséget tesz: a sorvégjel nélküli, csonka utolsó rekordot eldobja és levágja (az soha nem kapott Ok-t), a sorvégjellel lezárt, de hibás rekordot viszont sérülésként jelzi, és megtagadja az indítást.

11.3.7 Feladatok

  1. Fogalmi kérdés. A Read::read miért adhat vissza Ok(0)-t, és mit jelent ez? Hogyan olvasnád be egy fájl teljes tartalmát anélkül, hogy előre ismernéd a méretét?

  2. C++-kód átírása. Az alábbi C++ program soronként beolvas egy fájlt, és a sorok elé írja a sorszámot. Írd át idiomatikus Rustra ? operátorral és BufReader-rel.

#include <fstream>
#include <iostream>
#include <string>

int main() {
    std::ifstream in("input.txt");
    std::string line;
    int n = 1;
    while (std::getline(in, line)) {
        std::cout << n++ << ": " << line << '\n';
    }
}

  1. rkv-bővítés. Egészítsd ki a FileStore-t egy compact utáni megerősített lezárással: a compact végén a sync_all mellett ellenőrizd, hogy a snapshot fájl tényleg létezik és olvasható. Írj hozzá tesztet, amely két compact hívást hajt végre, és ellenőrzi az állapotot.

  2. Hibajavítás. Az alábbi kód szándékosan hibásan feltételezi, hogy egyetlen write mindig kiírja a teljes puffert, és a Drop elintézi a flush-t. Javítsd a kódot úgy, hogy a hiba ne vesszen el.

use std::fs::File;
use std::io::Write;

fn save(path: &str, data: &[u8]) -> std::io::Result<()> {
    let mut f = File::create(path)?;
    f.write(data)?;
    Ok(())
}

11.3.8 Megoldások

  1. Az Ok(0) normál esetben a fájl végét jelenti. A teljes tartalom beolvasásához read_to_end (bájtok) vagy read_to_string (UTF-8 szöveg) kell; ezek tetszőleges hosszúságú adatot kezelnek.

  2. Rust változat:

use std::fs::File;
use std::io::{self, BufRead, BufReader};

fn main() -> io::Result<()> {
    let file = File::open("input.txt")?;
    for (i, line) in BufReader::new(file).lines().enumerate() {
        println!("{}: {}", i + 1, line?);
    }
    Ok(())
}
  1. A compact kiegészítése:
pub fn compact(&mut self) -> Result<()> {
    self.save_snapshot()?;
    // Megerősítés a napló eldobása előtt: a snapshot létezik, olvasható,
    // és pontosan a memóriabeli állapotot tartalmazza.
    let file = File::open(&self.snapshot_path)?;
    let snap: Snapshot = serde_json::from_reader(BufReader::new(file))?;
    if snap.data != self.data {
        return Err(std::io::Error::other("a mentett snapshot eltér az állapottól").into());
    }
    let log = self.log_writer.get_mut();
    log.set_len(0)?;
    log.sync_all()?;
    Ok(())
}

Az ellenőrzés a napló csonkolása előtt fut: ha hibát talál, a napló érintetlen marad, így a régi snapshot és a napló továbbra is helyreállítható. Teszt két compact hívással: a második hívásnak idempotensnek kell lennie, és a FileStore::open utáni get értékek nem változhatnak. Ez a teszt is csak a logikai helyességet igazolja, az áramkimaradás-tűrést nem (lásd a tartóssági modellt).

  1. Javított kód:
use std::fs::File;
use std::io::{BufWriter, Write};

fn save(path: &str, data: &[u8]) -> std::io::Result<()> {
    let file = File::create(path)?;
    let mut writer = BufWriter::new(file);
    writer.write_all(data)?;
    writer.flush()?;
    Ok(())
}

A write helyett write_all, a pufferelt kimenetnél pedig explicit flush biztosítja a hibák terjedését.

11.3.9 Rövid összefoglaló

Ebben az alfejezetben megismerkedtünk a Rust I/O traitjeivel. A Read, Write és BufRead generikus absztrakciót adnak fájlok, hálózati streamek és pufferek fölé; a BufReader és BufWriter explicit pufferelést biztosít. A std::io::Result és a ? minden I/O-hibát explicit terjedést kényszerít ki. A serde Serialize/Deserialize deriválásokkal a serde_json JSON formátumba szerializál; bináris formátumhoz a bincode crate használható verzióellenőrzéssel. Elkészítettük az rkv FileStore típusát a rkv-core/src/store/file_store.rs fájlban, amely JSON snapshotot és hozzáfűzéses naplót használ. A FileStore::open, set, delete, list, save_snapshot és compact metódusok a Result hibakezeléssel dolgoznak. Az atomikus csere ideiglenes fájllal, sync_all-lal, fs::rename-nel és a könyvtár szinkronizálásával védi az állapotfájlt; a naplóírás commit-szerződése szerint a memória csak a tartós naplórekord után változik. Továbbvitt eredmény: a FileStore perzisztenciája a Trait-ek és generikusok: sablonok és concepts helyett, a Az rkv hálózati szerver: TCP, protokoll, kecses leállás és a Záróprojekt: az rkv teljes rendszerként alfejezetek alapja.

11.3.10 Források és ellenőrzési hiányok

A fejezet a Rust standard könyvtár stabil std::io és std::fs API-jára épít. A serde és a serde_json főverziója 1, a pontos verziót a Cargo.lock rögzíti. A bincode 1.x és 2.x API-ja jelentősen eltér (bincode::serialize szemben a bincode::serde::encode_to_vec-kel), ezért a fejezet a serde_json-t használja. Az atomikus rename Linuxon azonos fájlrendszeren atomikus; a tartóssági modell a fejezetben megadott Linux/POSIX környezetre érvényes, Windows és macOS viselkedése eltérhet.
