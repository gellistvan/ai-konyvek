11.3 I/O és szerializáció: fájlok, pufferelés, serde

11.3.1 Motiváció

C++-ban az iostream-réteg (std::ifstream, std::ofstream, std::cin) pufferel, formáz és kényelmes operátorokat ad, de a hibakezelés gyakran „utólagos”: a streamek hibazászlókat állítanak, és a kódban ez a rész gyakran ellenőrizetlen marad. Rustban minden I/O-művelet Result-ot ad; a ? operátorral a hibaterjedés explicit, a fordító pedig figyelmeztet, ha egy Result-ot figyelmen kívül hagynánk. A std::io traitjei ráadásul nem fájlra vagy socketre szabottak: ugyanaz a Read/Write implementáció működik fájllal, hálózattal, pufferrel vagy éppen egy teszt-Vec-kel.

Ebben az alfejezetben ezeket a trait-eket használjuk, bemutatjuk a serde-alapú szerializációt, és egy valódi, hibatűrő perzisztenciaréteget építünk az rkv számára: snapshot plusz hozzáfűzéses napló. Ez lesz a FileStore, amelyet később a Storage trait mögé emelünk, és a hálózati szerver is használ majd.

11.3.2 Fogalmak és szabályok

Definíció. A std::io::Read trait egy bájtsorozat olvasását modellezi. A központi metódusa:

fn read(&mut self, buf: &mut [u8]) -> io::Result<usize>;

A read legfeljebb buf.len() bájtot olvas be, és a ténylegesen beolvasott bájtok számát adja vissza. A 0 érték a fájl végét (EOF) jelenti normál esetben. A trait kényelmi metódusokat is ad: read_to_end, read_to_string, read_exact.

Szabály. Soha ne feltételezd, hogy egyetlen read hívás teleolvassa a puffert. A read_exact garantálja a teljes puffer beolvasását, a read_to_end pedig a teljes bemenetet gyűjti be. Fájl esetén a gyakorlatban gyakran működik a teli puffer, de hálózaton, pipe-on csomagokban érkezhet az adat.

Definíció. A std::io::Write trait a kimeneti bájtsorozatot modellezi:

fn write(&mut self, buf: &[u8]) -> io::Result<usize>;
fn flush(&mut self) -> io::Result<()>;

A write a puffer egy részét is kiírhatja; a teljes puffer garantált kiírásához a write_all kényelmi metódust vagy a writeln! makrót használjuk. A flush a pufferelt adatot azonnal a háttérbe küldi.

Definíció. A std::io::BufRead a Read-et belső pufferrel bővíti, és sorolvasó kényelmi metódusokat ad: read_line, lines, split. A BufReader<T> egy Read implementáló típus köré húz puffert; a BufWriter<T> egy Write implementáló típus köré.

Definíció. A Path nem birtokló, platformfüggetlen nézet egy fájlrendszerbeli elérési útra; a PathBuf ennek birtokló, módosítható változata. Ez hasonló a std::string_view és a std::string viszonyához, csak itt fájlrendszeri utakra.

Definíció (atomikus csere). Ha egy állapotfájlt úgy mentünk, hogy először egy ideiglenes fájlt írunk tele, flush-elünk, majd std::fs::rename-nel a végleges névre nevezzük át, a meglévő állapotfájl soha nem lesz félkész. Linuxon az rename azonos fájlrendszeren atomikus csereként működik. A Rust File::create a célfájlt lenullázva nyitja meg, ezért önmagában nem alkalmas törésbiztos mentésre.

Definíció (hozzáfűzéses napló). Az append-only log minden mutációs műveletet a fájl végéhez fűz. Újraindításkor a legutóbbi snapshotot betöltjük, majd a naplót sorról sorra visszajátsszuk. A compact művelet snapshotot készít, és lenullázza a naplót.

11.3.3 C++ ↔︎ Rust összevetés

C++-ban a fájl olvasása és a hiba ellenőrzése gyakran így néz ki:

#include <fstream>
#include <iostream>
#include <string>

int main() {
    std::ifstream in("input.txt");
    if (!in) {
        std::cerr << "open failed\n";
        return 1;
    }
    std::string line;
    while (std::getline(in, line)) {
        std::cout << line << '\n';
    }
    if (in.bad()) return 2; // sokszor elmarad
}

A Rust-változat minden lépés Result-ját továbbadja:

use std::fs::File;
use std::io::{self, BufRead, BufReader};

fn main() -> io::Result<()> {
    let file = File::open("input.txt")?;
    for line in BufReader::new(file).lines() {
        println!("{}", line?);
    }
    Ok(())
}

A különbség: a ? nem hagyja, hogy a File::open vagy a sorolvasás hibája észrevétlen maradjon. A lines() a sor elejét és végét leválasztja, de a sortörést nem adja vissza; a C++ getline ugyanezt teszi eltérő vonalazási részletekkel. A Rust File nem pufferelt, ezért a hatékony sorolvasáshoz BufReader kell; a C++ streamek alapból pufferelnek.

11.3.4 Kidolgozott példa: generikus Read/Write

A Read és Write trait-ek ereje abban van, hogy nem kötődnek fájlhoz. Ugyanaz a függvény működik fájllal, bájttömbbel vagy hálózati streammel:

use std::io::{self, Read, Write};

fn copy_all<R: Read, W: Write>(mut from: R, mut to: W) -> io::Result<u64> {
    io::copy(&mut from, &mut to)
}

Szerializációhoz a serde a deriválható Serialize és Deserialize trait-eket adja. Az rkv-core Cargo.toml-jába a következő függőségek kerülnek:

[dependencies]
serde = { version = "1", features = ["derive"] }
serde_json = "1"
# opcionális bináris formátum; az API-t ellenőrizni kell a docs.rs-en
bincode = "1"

Példa JSON-mentésre:

use serde::{Deserialize, Serialize};
use std::collections::BTreeMap;
use std::fs::File;
use std::io::BufWriter;

#[derive(Serialize, Deserialize)]
struct Config {
    port: u16,
    entries: BTreeMap<String, Vec<u8>>,
}

fn save_config(config: &Config, path: &str) -> std::io::Result<()> {
    let file = File::create(path)?;
    let mut writer = BufWriter::new(file);
    serde_json::to_writer(&mut writer, config)?;
    writer.flush()?;
    Ok(())
}

A serde_json::to_writer bármely Write implementáló típusra dolgozik, ezért a BufWriter pufferezését egyszerűen kihasználjuk. Bináris formátumhoz a bincode crate használható; a pontos API verziófüggő:

let bytes = bincode::serialize(config)?;
let decoded: Config = bincode::deserialize(&bytes)?;

A serde_json olvasható és könnyen debuggolható, ezért az rkv naplójához és snapshotjához ezt használjuk. A bináris bincode kisebb, de olvashatatlan; beágyazott vagy nagy forgalmú rendszereknél jobb választás lehet.

11.3.5 Labor: rkv FileStore snapshot + napló

Munkakönyvtár: ~/rust-labor/rkv/

A labor a rkv-core könyvtári crate-ben valósítja meg a FileStore-t. A cél: a tároló állapota túlélje a processz újraindítását. A mentés kettős: egy JSON snapshot plusz egy JSON-soronkénti hozzáfűzéses napló. A FileStore még konkrét típus; a közös Storage traitet a Trait-ek és generikusok: sablonok és concepts helyett alfejezet vezeti be.

11.3.5.0.1 1. Függőségek és hibatípus

A rkv-core/Cargo.toml kiegészül a fenti serde és serde_json függőséggel. A rkv-core/src/error.rs tartalmazzon std::io::Error és serde_json::Error átalakításokat:

use thiserror::Error;

#[derive(Debug, Error)]
pub enum Error {
    #[error(transparent)]
    Io(#[from] std::io::Error),
    #[error("JSON hiba: {0}")]
    Serde(#[from] serde_json::Error),
}

pub type Result<T> = std::result::Result<T, Error>;

Ha a Result alias még nem létezik, most hozd létre; minden I/O-hibát ezen keresztül terjesszünk.

11.3.5.0.2 2. Modul és FileStore

Hozd létre a rkv-core/src/store/mod.rs fájlt:

mod file_store;
pub use file_store::FileStore;

A rkv-core/src/lib.rs-ben a pub mod store; sorral publikáld a modult. A FileStore implementációja:

use std::collections::HashMap;
use std::fs::{self, File, OpenOptions};
use std::io::{BufRead, BufReader, BufWriter, Write};
use std::path::{Path, PathBuf};
use serde::{Deserialize, Serialize};

use crate::{Error, Result};

#[derive(Debug, Clone, Serialize, Deserialize)]
struct Snapshot {
    data: HashMap<String, Vec<u8>>,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
enum LogEntry {
    Set { key: String, value: Vec<u8> },
    Delete { key: String },
}

pub struct FileStore {
    data: HashMap<String, Vec<u8>>,
    log_writer: BufWriter<File>,
    snapshot_path: PathBuf,
    log_path: PathBuf,
}

impl FileStore {
    pub fn open(snapshot_path: impl AsRef<Path>, log_path: impl AsRef<Path>) -> Result<Self> {
        let snapshot_path = snapshot_path.as_ref().to_path_buf();
        let log_path = log_path.as_ref().to_path_buf();

        let mut data = HashMap::new();
        if snapshot_path.exists() {
            let file = File::open(&snapshot_path)?;
            let reader = BufReader::new(file);
            let snap: Snapshot = serde_json::from_reader(reader)?;
            data = snap.data;
        }

        replay_log(&log_path, &mut data)?;

        let log_file = OpenOptions::new()
            .create(true)
            .append(true)
            .open(&log_path)?;
        let log_writer = BufWriter::new(log_file);

        Ok(Self {
            data,
            log_writer,
            snapshot_path,
            log_path,
        })
    }

    pub fn get(&self, key: &str) -> Option<&Vec<u8>> {
        self.data.get(key)
    }

    pub fn set(&mut self, key: String, value: Vec<u8>) -> Result<()> {
        self.data.insert(key.clone(), value.clone());
        let entry = LogEntry::Set { key, value };
        serde_json::to_writer(&mut self.log_writer, &entry)?;
        self.log_writer.write_all(b"\n")?;
        Ok(())
    }

    pub fn delete(&mut self, key: &str) -> Result<()> {
        if self.data.remove(key).is_some() {
            let entry = LogEntry::Delete { key: key.to_string() };
            serde_json::to_writer(&mut self.log_writer, &entry)?;
            self.log_writer.write_all(b"\n")?;
        }
        Ok(())
    }

    pub fn list(&self, prefix: Option<&str>) -> Vec<(String, Vec<u8>)> {
        let mut items: Vec<_> = self
            .data
            .iter()
            .filter(|(k, _)| prefix.map_or(true, |p| k.starts_with(p)))
            .map(|(k, v)| (k.clone(), v.clone()))
            .collect();
        items.sort_by(|a, b| a.0.cmp(&b.0));
        items
    }

    pub fn save_snapshot(&mut self) -> Result<()> {
        self.log_writer.flush()?;
        let tmp_path = self.snapshot_path.with_extension("json.tmp");
        let file = File::create(&tmp_path)?;
        let mut writer = BufWriter::new(file);
        serde_json::to_writer(&mut writer, &Snapshot { data: self.data.clone() })?;
        writer.flush()?;
        drop(writer);
        fs::rename(&tmp_path, &self.snapshot_path)?;
        Ok(())
    }

    pub fn compact(&mut self) -> Result<()> {
        self.save_snapshot()?;
        self.log_writer.get_mut().set_len(0)?;
        self.log_writer.get_mut().sync_all()?;
        Ok(())
    }
}

fn replay_log(path: &Path, data: &mut HashMap<String, Vec<u8>>) -> Result<()> {
    let file = match File::open(path) {
        Ok(f) => f,
        Err(e) if e.kind() == std::io::ErrorKind::NotFound => return Ok(()),
        Err(e) => return Err(e.into()),
    };
    let reader = BufReader::new(file);
    for line in reader.lines() {
        let line = line?;
        if line.trim().is_empty() {
            continue;
        }
        let entry: LogEntry = serde_json::from_str(&line)?;
        match entry {
            LogEntry::Set { key, value } => {
                data.insert(key, value);
            }
            LogEntry::Delete { key } => {
                data.remove(&key);
            }
        }
    }
    Ok(())
}
11.3.5.0.3 3. Unit teszt

A FileStore állapotának túlélése egyszerű tesztben ellenőrizhető. A tesztet a file_store.rs alján helyezzük el:

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn replay_log_rebuilds_state() {
        let dir = std::env::temp_dir().join(format!(
            "rkv-file-store-test-{}",
            std::process::id()
        ));
        std::fs::create_dir_all(&dir).unwrap();
        let snap = dir.join("state.json");
        let log = dir.join("append.log");
        let _ = std::fs::remove_file(&snap);
        let _ = std::fs::remove_file(&log);

        {
            let mut store = FileStore::open(&snap, &log).unwrap();
            store.set("a".into(), b"1".to_vec()).unwrap();
            store.delete("a").unwrap();
            store.set("b".into(), b"2".to_vec()).unwrap();
            store.compact().unwrap();
        }

        let mut store = FileStore::open(&snap, &log).unwrap();
        assert_eq!(store.get("a"), None);
        assert_eq!(store.get("b").cloned(), Some(b"2".to_vec()));
    }
}

Futtatás:

cargo test -p rkv-core

Várt kimenet (rövidítve, a teszt neve szerepel):

running 1 test
test store::file_store::tests::replay_log_rebuilds_state ... ok

A compact hívás a snapshotot atomikusan lecseréli, a naplót lenullázza, majd a sync_all a fájltartalmat a lemezre kényszeríti. A második FileStore::open a snapshotot tölti be, és a napló már üres.

A napló megnyitásánál az OpenOptions::new().append(true).create(true) biztosítja, hogy a fájl létezzen, és minden írás a végére kerüljön. A replay_log a hiányzó naplófájlt elfogadja első indításkor, a tényleges I/O-hibát viszont továbbadja.

Továbbvitt eredmény. A FileStore perzisztenciáját a Trait-ek és generikusok: sablonok és concepts helyett alfejezet a Storage trait mögé emeli, a Az rkv hálózati szerver: TCP, protokoll, kecses leállás alfejezetben a rkv-server használja, a Záróprojekt: az rkv teljes rendszerként alfejezetben pedig a teljes rendszer része lesz.

11.3.6 Tipikus hibák és átállási csapdák

  1. Egyetlen read hívásra alapozni. A read nem garantálja, hogy a puffer tele lesz; a read_to_end, read_to_string vagy read_exact használata a helyes. C++-os beidegződés, hogy a istream::read teljes rekordot vár; Rustban ez explicit.

  2. A writeln! eredményét elhagyni. A writeln! io::Result-ot ad; ha nem használjuk a ?-et, a kód lefordulhat #[must_use] figyelmeztetéssel, de a hiba elveszik. A könyvtári kódban mindig ?.

  3. A BufWriter Drop-jára hagyatkozni. A BufWriter Drop-implémenzciója megpróbálja ugyan a puffert kiüríteni, de a hibát elnyeli. Ha a lemez megtelt, az adatvesztés némán következhet be. A fontos kimeneteket explicit flush-sel, vagy sync_all-lal zárjuk.

  4. A File::create atomikus cserével való összekeverése. A File::create azonnal lenullázza a célfájlt. Ha a mentés közben a processz leáll, az eredeti állapot is elveszik. A helyes minta: ideiglenes fájl, flush, rename.

  5. A napló visszajátszásának túlzott szigora. Ha a processz a naplósor felénél áll le, a serde_json parse hiba lehet. A szigorú ? ilyenkor a teljes indítást megakadályozza. A robusztusabb megoldás a csonka utolsó sor eldobása, vagy az állapot snapshotjának gyakori készítése. Az rkv első verziójában a szigorú viselkedést választjuk; a hiba jelzi a sérülést.

11.3.7 Feladatok

  1. Fogalmi kérdés. A Read::read miért adhat vissza Ok(0)-t, és mit jelent ez? Hogyan olvasnád be egy fájl teljes tartalmát anélkül, hogy előre ismernéd a méretét?

  2. C++-kód átírása. Az alábbi C++ program soronként beolvas egy fájlt, és a sorok elé írja a sorszámot. Írd át idiomatikus Rustra ? operátorral és BufReader-rel.

#include <fstream>
#include <iostream>
#include <string>

int main() {
    std::ifstream in("input.txt");
    std::string line;
    int n = 1;
    while (std::getline(in, line)) {
        std::cout << n++ << ": " << line << '\n';
    }
}

  1. rkv-bővítés. Egészítsd ki a FileStore-t egy compact utáni megerősített lezárással: a compact végén a sync_all mellett ellenőrizd, hogy a snapshot fájl tényleg létezik és olvasható. Írj hozzá tesztet, amely két compact hívást hajt végre, és ellenőrzi az állapotot.

  2. Hibajavítás. Az alábbi kód szándékosan hibásan feltételezi, hogy egyetlen write mindig kiírja a teljes puffert, és a Drop elintézi a flush-t. Javítsd a kódot úgy, hogy a hiba ne vesszen el.

use std::fs::File;
use std::io::Write;

fn save(path: &str, data: &[u8]) -> std::io::Result<()> {
    let mut f = File::create(path)?;
    f.write(data)?;
    Ok(())
}

11.3.8 Megoldások

  1. Az Ok(0) normál esetben a fájl végét jelenti. A teljes tartalom beolvasásához read_to_end (bájtok) vagy read_to_string (UTF-8 szöveg) kell; ezek tetszőleges hosszúságú adatot kezelnek.

  2. Rust változat:

use std::fs::File;
use std::io::{self, BufRead, BufReader};

fn main() -> io::Result<()> {
    let file = File::open("input.txt")?;
    for (i, line) in BufReader::new(file).lines().enumerate() {
        println!("{}: {}", i + 1, line?);
    }
    Ok(())
}
  1. A compact kiegészítése:
pub fn compact(&mut self) -> Result<()> {
    self.save_snapshot()?;
    if !self.snapshot_path.exists() {
        return Err(std::io::Error::new(
            std::io::ErrorKind::Other,
            "snapshot mentése után a fájl nem létezik"
        ).into());
    }
    self.log_writer.get_mut().set_len(0)?;
    self.log_writer.get_mut().sync_all()?;
    Ok(())
}

Teszt két compact hívással: a második hívásnak idempotensnek kell lennie, és a FileStore::open utáni get értékek nem változhatnak.

  1. Javított kód:
use std::fs::File;
use std::io::{BufWriter, Write};

fn save(path: &str, data: &[u8]) -> std::io::Result<()> {
    let file = File::create(path)?;
    let mut writer = BufWriter::new(file);
    writer.write_all(data)?;
    writer.flush()?;
    Ok(())
}

A write helyett write_all, a pufferelt kimenetnél pedig explicit flush biztosítja a hibák terjedését.

11.3.9 Rövid összefoglaló

Ebben az alfejezetben megismerkedtünk a Rust I/O traitjeivel. A Read, Write és BufRead generikus absztrakciót adnak fájlok, hálózati streamek és pufferek fölé; a BufReader és BufWriter explicit pufferelést biztosít. A std::io::Result és a ? minden I/O-hibát explicit terjedést kényszerít ki. A serde Serialize/Deserialize deriválásokkal a serde_json JSON formátumba szerializál; bináris formátumhoz a bincode crate használható verzióellenőrzéssel. Elkészítettük az rkv FileStore típusát a rkv-core/src/store/file_store.rs fájlban, amely JSON snapshotot és hozzáfűzéses naplót használ. A FileStore::open, set, delete, list, save_snapshot és compact metódusok a Result hibakezeléssel dolgoznak. Az atomikus csere ideiglenes fájllal és fs::rename-nel védi az állapotfájlt. Továbbvitt eredmény: a FileStore perzisztenciája a Trait-ek és generikusok: sablonok és concepts helyett, a Az rkv hálózati szerver: TCP, protokoll, kecses leállás és a Záróprojekt: az rkv teljes rendszerként alfejezetek alapja.

11.3.10 Források és ellenőrzési hiányok

A fejezet a Rust standard könyvtár stabil std::io és std::fs API-jára épít. A serde és serde_json crate-ek API-ja stabil, de a pontos verziókat a docs.rs-en ellenőrizni kell. A bincode 1.x és 2.x API-ja jelentősen eltér (bincode::serialize szemben a bincode::serde::encode_to_vec stb. függvényekkel); a konkrét crate-verzió és szignatúra ellenőrzést igényel. Az atomikus rename Linuxon azonos fájlrendszeren atomikus; Windows és macOS viselkedését a platformfüggő megjegyzéseknél kell pontosítani.
