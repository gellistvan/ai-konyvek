12.1 Trait-ek és generikusok: sablonok és concepts helyett

12.1.1 Motiváció

C++-ban egy sablonos függvény deklarációja alig mond valamit arról, mit vár el a típusparamétertől. A használat helyén derül ki, hogy a T-nek kell-e operator+-a, operator<-e, vagy éppen size() tagfüggvénye. Ez a duck typing időnként nagyon rugalmas, de a hibaüzenetek a példányosítás mélyén keletkeznek, és gyakran több száz sorból kell kihámozni, hogy mi hiányzott. A C++20 concepts ezt orvosolja, de a nyelv továbbra is megengedi a korlát nélküli sablonokat, és a hibák továbbra is a sablon használatakor és nem a definíciójakor jelentkeznek.

A Rust ezzel szemben a generikus kódot már a definíció helyén, a típusparaméterre kimondott trait boundok alapján ellenőrzi. Ha a típusparaméter nem elégíti ki a boundot, a fordító a definícióban mutatja a hibát – nem a hívó fél kódjában. Ez a különbség nem csupán kényelem: a Rust generikusoknál a függvény törzse csak a bound által garantált műveleteket használhatja, ezért a generikus API már a deklarációkor dokumentált és ellenőrzött.

12.1.2 Fogalmak és szabályok

Definíció. A trait olyan viselkedési interfész, amely metódusok szignatúráját írja elő, és opcionálisan törzsüket is tartalmazhatja. A traitet egy típusra az impl Trait for Type blokkal implementáljuk.

Definíció. A trait bound egy generikus paraméterre kimondott elvárás: T: TraitName. Azt jelenti, hogy a generikus függvény vagy típus törzsében a T-re csak a TraitName által garantált metódusok hívhatók.

Szabály. Generikus függvényben vagy impl blokkban a Rust fordító a törzset a trait boundok alapján, a konkrét típus ismerete nélkül ellenőrzi. Ha a bound nem ad elég műveletet, a hiba a definíció sorára mutat.

Például egy Rust trait definíciója és megvalósítása:

trait Summary {
    fn summarize(&self) -> String;

    // default metódus, amelyet az implementáló felülírhat
    fn short_summary(&self) -> String {
        self.summarize().chars().take(40).collect()
    }
}

struct Article {
    title: String,
    author: String,
}

impl Summary for Article {
    fn summarize(&self) -> String {
        format!("{} by {}", self.title, self.author)
    }
}

Egy generikus függvény bounddal:

fn print_summary<T: Summary>(item: &T) {
    println!("{}", item.summarize());
}

Bonyolultabb esetben a where klauzula javítja az olvashatóságot:

fn print_both<T, U>(x: &T, y: &U)
where
    T: Summary,
    U: std::fmt::Debug,
{
    println!("{x:?}; {}", y.summarize());
}

Definíció. A monomorfizálás az a fordítási folyamat, amelyben a generikus kód minden használt konkrét típuskombinációra lefordul. Az int_f64 például print_both::<i32, f64> konkrét kódot kap, akárcsak a C++ sablonpéldányosítás. Ez futásidőben nulla absztrakciós költséget eredményez, cserébe növelheti a bináris méretét.

Generikus definíció                     Példányosított kód
┌──────────────────────────┐            ┌────────────────────────┐
│ fn largest<T: PartialOrd>│  fordítás  │ largest::<i32>         │
│ (a: T, b: T) -> T        │ ─────────► │ largest::<f64>         │
│ { if a > b { a } else    │            │ largest::<&str>        │
│     { b } }              │            └────────────────────────┘
└──────────────────────────┘            C++-ban ugyanez a sablon
                                        példányosítás; Rustban a
                                        boundot a definíció előtt
                                        ellenőrzi a fordító.

Az impl Trait szintaktikai egyszerűsítés. Argumentumpozícióban:

fn print_summary2(item: &impl Summary) {
    println!("{}", item.summarize());
}

Ez pontosan ugyanaz, mint a T: Summary paraméter, csak a T nevet nem köti. Visszatérési pozícióban viszont más a szerepe: azt mondja, hogy a függvény visszatér egy olyan típussal, amelyik implementálja a traitet, de a konkrét típust a fordító választja meg – egyetlen konkrét típust. Az alábbi nem fordul le:

// Ez a változat szándékosan nem fordul le:
fn make_bool_or_int(flag: bool) -> impl std::fmt::Display {
    if flag {
        42
    } else {
        "hello"
    }
}

A hiba lényege: a függvény két különböző konkrét típust adna vissza (i32 és &str), az impl Display pedig nem dyn Display, ezért nem lehet több típus egyetlen visszatérési pozícióban. A pontos hibaüzenet verziófüggő, de a lényeg mindig ez.

12.1.3 C++ ↔︎ Rust összevetés

C++ sablon duck typinggal:

#include <iostream>
#include <string>

template <typename T>
T max_value(T a, T b) {
    return (a > b) ? a : b; // T-nek operator>-t kell adnia
}

int main() {
    std::cout << max_value(3, 5) << '\n';              // ok
    std::string s = max_value("x", "y");               // hiba: const char* operator>
    return 0;
}

A C++ hiba a max_value használatakor, a sablon belsejében jelentkezik, és azzal függ össze, hogy a const char*-ra nincs operator>.

Rust megfelelő:

fn max_value<T: PartialOrd>(a: T, b: T) -> T {
    if a > b { a } else { b }
}

fn main() {
    println!("{}", max_value(3, 5));
    // A "x" és "y" &str típusú; a &str PartialOrd,
    // ezért a definíció lefordul, és a használat is.
    println!("{}", max_value("x", "y"));
}

A Rust a PartialOrd boundot a definícióban ellenőrzi: a > művelet ebből a boundból következik. Ha a T nem PartialOrd, a hiba a definícióban vagy a hívásnál jelezné, hogy a bound nem teljesül, de a függvény törzse már a definícióban érvényes.

C++20 concepts ugyanezt a szándékot fejezi ki, de a másik irányból: a sablon fejében mondjuk ki, hogy T total orderinget vár. A Rust ezt nem opcionálisan teszi, hanem a generikusok alapvető működéseként.

12.1.4 Kidolgozott példa

A lenti generikus Rust függvény szándékosan hibás, mert a T-nek nincs boundja:

// Ez a változat szándékosan nem fordul le:
fn add_one<T>(x: T) -> T {
    x + 1
}

fn main() {
    let n = add_one(41);
    println!("{n}");
}

A hiba lényege: a binary + műveletet nem lehet alkalmazni a T típusra, mert a T-ről semmit sem tud a fordító. Ezt a hibaüzenet általában E0369 kóddal jelzi, és a definíción belül arra a sorra mutat, ahol a + szerepel. A javítás:

use std::ops::Add;

fn add_one<T>(x: T) -> T
where
    T: Add<i32, Output = T> + From<i32>,
{
    x + 1
}

fn main() {
    let n = add_one(41);
    println!("{n}");
}

Itt a From<i32> bound teszi lehetővé, hogy az 1 literálból T legyen, az Add<i32, Output = T> pedig a + műveletet garantálja. A kód lefordul, és a konkrét i32 típusra monomorfizálódik.

12.1.5 Labor: az rkv Storage traitje

Munkakönyvtár: ~/rust-labor/rkv

A laborban létrehozzuk a Storage traitet a rkv-core crate-ben, és két implementációt készítünk: MemStore-t memóriabeli HashMap-mel, FileStore-t JSON-fájllal. A Storage trait lesz a későbbi szerver és CLI közös absztrakciója.

Továbbvitt eredmény. A Storage traitet a Asszociált típusok, koherencia, operátorok és derive alfejezet bővíti, a Trait objektumok és dinamikus diszpécs tárgyalja dyn Storage-ként, a Unit-, integrációs és dokumentációs tesztek teszteli, a Mutex, RwLock, csatornák és a megosztott rkv pedig szálbiztossá teszi.

Lépések:

use std::collections::HashMap;
use std::fs::File;
use std::path::PathBuf;

use serde::{Deserialize, Serialize};

use crate::error::Error;

/// Kulcs-érték tároló absztrakció.
///
/// A `Storage` trait írja elő a parancsok végrehajtásához
/// szükséges műveleteket. A kulcs `String`, az érték `Vec<u8>`
/// a [Structok és metódusok: impl blokkok, asszociált függvények](#r007)
/// alfejezet döntése szerint.
pub trait Storage {
    fn get(&self, key: &str) -> Result<Option<Vec<u8>>, Error>;
    fn set(&mut self, key: String, value: Vec<u8>) -> Result<(), Error>;
    fn delete(&mut self, key: &str) -> Result<bool, Error>;
    fn list(&self, prefix: Option<&str>) -> Result<Vec<String>, Error>;
}

/// A Command enum a beérkező parancsot reprezentálja.
/// Ha korábban már létrehoztad, ne duplikáld.
pub enum Command {
    Get(String),
    Set(String, Vec<u8>),
    Delete(String),
    List(Option<String>),
}

/// A parancsok feldolgozásának eredménye.
pub enum Response {
    Ok,
    Value(Vec<u8>),
    NotFound,
    Keys(Vec<String>),
    Err(String),
}

/// Memóriabeli tároló.
#[derive(Debug, Default)]
pub struct MemStore {
    data: HashMap<String, Vec<u8>>,
}

impl Storage for MemStore {
    fn get(&self, key: &str) -> Result<Option<Vec<u8>>, Error> {
        Ok(self.data.get(key).cloned())
    }

    fn set(&mut self, key: String, value: Vec<u8>) -> Result<(), Error> {
        self.data.insert(key, value);
        Ok(())
    }

    fn delete(&mut self, key: &str) -> Result<bool, Error> {
        Ok(self.data.remove(key).is_some())
    }

    fn list(&self, prefix: Option<&str>) -> Result<Vec<String>, Error> {
        let keys = self
            .data
            .keys()
            .filter(|k| prefix.map_or(true, |p| k.starts_with(p)))
            .cloned()
            .collect();
        Ok(keys)
    }
}

/// Fájl-alapú, (még) nem atomikus pillanatkép-tároló.
///
/// Minden `set`/`delete` után a teljes HashMap JSON-ként íródik ki.
/// A naplót és az atomikus fájlcserét későbbi laborokban adjuk hozzá.
#[derive(Debug)]
pub struct FileStore {
    path: PathBuf,
    data: HashMap<String, Vec<u8>>,
}

impl FileStore {
    pub fn open(path: impl Into<PathBuf>) -> Result<Self, Error> {
        let path = path.into();
        let data = if path.exists() {
            let file = File::open(&path)?;
            serde_json::from_reader(file)?
        } else {
            HashMap::new()
        };
        Ok(Self { path, data })
    }

    fn persist(&self) -> Result<(), Error> {
        let file = File::create(&self.path)?;
        serde_json::to_writer(file, &self.data)?;
        Ok(())
    }
}

impl Storage for FileStore {
    fn get(&self, key: &str) -> Result<Option<Vec<u8>>, Error> {
        Ok(self.data.get(key).cloned())
    }

    fn set(&mut self, key: String, value: Vec<u8>) -> Result<(), Error> {
        self.data.insert(key, value);
        self.persist()
    }

    fn delete(&mut self, key: &str) -> Result<bool, Error> {
        let removed = self.data.remove(key).is_some();
        self.persist()?;
        Ok(removed)
    }

    fn list(&self, prefix: Option<&str>) -> Result<Vec<String>, Error> {
        let keys = self
            .data
            .keys()
            .filter(|k| prefix.map_or(true, |p| k.starts_with(p)))
            .cloned()
            .collect();
        Ok(keys)
    }
}

/// Generikus parancsvégrehajtás bármely `Storage` implementációra.
///
/// A `S: Storage` bound garantálja, hogy a `Command` minden ágában
/// a `Storage` négy metódusa hívható.
pub fn apply<S: Storage>(store: &mut S, command: &Command) -> Result<Response, Error> {
    match command {
        Command::Get(key) => Ok(match store.get(key)? {
            Some(value) => Response::Value(value),
            None => Response::NotFound,
        }),
        Command::Set(key, value) => {
            store.set(key.clone(), value.clone())?;
            Ok(Response::Ok)
        }
        Command::Delete(key) => Ok(if store.delete(key)? {
            Response::Ok
        } else {
            Response::NotFound
        }),
        Command::List(prefix) => Ok(Response::Keys(store.list(prefix.as_deref())?)),
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn mem_store_get_set_delete() {
        let mut store = MemStore::default();
        store.set("k".into(), b"v".to_vec()).unwrap();
        assert_eq!(store.get("k").unwrap(), Some(b"v".to_vec()));
        assert!(store.delete("k").unwrap());
        assert_eq!(store.get("k").unwrap(), None);
        assert!(!store.delete("k").unwrap());
    }

    #[test]
    fn mem_store_list_has_prefix_filter() {
        let mut store = MemStore::default();
        store.set("alpha".into(), b"1".to_vec()).unwrap();
        store.set("beta".into(), b"2".to_vec()).unwrap();
        let keys = store.list(Some("a")).unwrap();
        assert_eq!(keys, vec!["alpha".to_string()]);
    }
}

12.1.6 Tipikus hibák és átállási csapdák

  1. A C++-os duck typing elvárása. Ha egy Rust generikus függvényben a T-re x.doSomething()-et hívsz, a boundot ki kell mondanod. A hiba nem a hívóban, hanem a definícióban jelenik meg; sok C++-fejlesztő a hívás helyére görgetve keresi a hibát, és meglepődik.

  2. A clone() mindenütt a borrow checker „legyőzésére” és a generikusok egyszerűbbé tételére nem idiomatikus. Ha a Storage get metódusa miatt klónozni kell a Vec<u8>-at, az lehet elfogadható, de gyakran jobb visszaadni &[u8]-ot vagy Option<&Vec<u8>>-at, ha az élettartam engedi. A laborban a MemStore::get cloned()-ot használ, mert a Storage trait a belső adattól független Option<Vec<u8>>-at ad vissza; ez konzisztens, de a forró úton némi másolással jár.

  3. Az impl Trait félreértése visszatérési típusként. Az impl Trait nem hoz létre heterogén gyűjteményt. Ha egy függvény két különböző konkrét típust adna vissza, a kód nem fordul le; ilyenkor dyn Trait kell (lásd később).

  4. A where klauzula elkerülése. Hosszú, egymásba ágyazott boundok esetén a where szakasz növeli az olvashatóságot, és közelebb áll a C++ concepts requires deklarációjához.

12.1.7 Feladatok

  1. (a) Lefordul-e és miért? Az alábbi Rust kód lefordul-e? Ha nem, mi a hiba lényege?
fn print_debug<T>(x: T) {
    println!("{:?}", x);
}
  1. (b) C++-kód átírása idiomatikus Rustra. Írd át az alábbi C++ sablont Rustra trait bounddal:
template <typename T>
T add_twice(T a, T b) {
    return (a + b) + b;
}

Vigyázz: a Rust + művelet a std::ops::Add traitből jön; a T-nek nem elég Add-ot adni, az Add Output típusa is T kell legyen.

  1. (c) Implementációs feladat az rkv-ban. Bővítsd a Storage traitet egy contains metódussal, amely igazat ad, ha a kulcs létezik. Implementáld MemStore-ra és FileStore-ra is. A contains hívja a get-et, és a map(|v| v.is_some()) értéket adja vissza, vagy közvetlenül a HashMap::contains_key-et.

  2. (d) Hibajavítás / refaktorálás. A jelenlegi FileStore a memóriában tartja a teljes adatbázist, és minden set/delete után teljesen újraírja a fájlt. Tervezd meg szövegesen, hogyan vezetnéd be a snapshot + append-only log perzisztenciát a FileStore-ba úgy, hogy a Storage trait szignatúrája ne változzon. Milyen hibamódokra kellene felkészülnöd?

12.1.8 Megoldások

  1. Nem fordul le. A println!("{:?}", x) a T-re a Debug traitet követeli meg. Mivel a T-re nincs bound, a fordító a definícióban jelzi, hogy a T nem kielégítően korlátozott. A javítás: fn print_debug<T: std::fmt::Debug>(x: T) vagy fn print_debug(x: &impl std::fmt::Debug).

  2. Rust megoldás:

use std::ops::Add;

fn add_twice<T>(a: T, b: T) -> T
where
    T: Add<T, Output = T> + Copy, // Copy a b újrahasználásához
{
    (a + b) + b
}

A Copy bound azért kell, mert a + művelet az első argumentumot move-olja. C++-ban az a és b másolhatóak vagy referenciaként adódnak át; Rustban a + az Add trait self paraméterét veszi át, így a-t és b-t egynél többször használni csak Copy esetén lehet.

  1. A Storage trait bővítése:
pub trait Storage {
    // ... eddigi metódusok ...
    fn contains(&self, key: &str) -> Result<bool, Error> {
        Ok(self.get(key)?.is_some()) // default metódus
    }
}

A default metódust MemStore és FileStore örökli, de ha szükséges, felülírhatják.

  1. Tervezési válasz (részletes kóddal itt nem kivitelezve). A FileStore a memóriabeli HashMap-et kiegészítené egy snapshot-fájllal és egy naplófájllal. A set/delete során a parancsot append-only módon naplóba írná (SET/DEL bejegyzések, sorozatszámmal), és a memóriabeli állapotot frissítené. A persist a napló kiírása után ritkán (pl. méret- vagy időalapú küszöb átlépésekor) új snapshotot készítene, és a naplót csonkolná. A fájlcserét atomikusan kellene megoldani: a snapshotot ideiglenes fájlba írjuk, majd rename-mel cseréljük, hogy a folyamat közbeni összeomlás ne hagyjon félkész állapotot. A betöltés során a napló bejegyzéseit a snapshotra játszva állítanánk helyre a memóriabeli állapotot. A Storage trait szignatúrája nem változna, mert a perzisztencia a FileStore belső ügye.

12.1.9 Rövid összefoglaló

Ebben az alfejezetben bevezettük a traitet mint viselkedési interfészt és a generikusokat trait boundokkal. A trait definíciójából és az impl Trait for Type blokkból kiindulva megmutattuk, hogy a boundok a generikus törzset már a definícióban ellenőrzik, szemben a C++ sablonok példányosításkori duck typingjával. A monomorfizálás Rustban ugyanúgy konkrét típusonként fordít, mint a C++ sablonpéldányosítás, de a fordító a boundok miatt előre garantálja az interfészt. Az impl Trait argumentumként a névtelen generikus paramétert, visszatérésként egyetlen konkrét típust jelent. A laborban létrehoztuk a rkv-core/src/storage.rs-ben a Storage traitet (get, set, delete, list metódusokkal), valamint a MemStore és FileStore implementációkat. A generikus apply függvény a Command enumot bármely S: Storage típusra futtatja. A Storage traitet a későbbi alfejezetek tovább bővítik és tesztelik.

12.1.10 Források és ellenőrzési hiányok

A fejezet a Rust referencia és a hivatalos dokumentáció alábbi kiindulópontjaira támaszkodik: https://doc.rust-lang.org/book/, https://doc.rust-lang.org/reference/. Nem állítom, hogy ezeket a linkeket ebben a kérésben ellenőriztem; a trait, a generikusok, a trait boundok, a monomorfizálás és az impl Trait stabil nyelvi fogalmak. A pontos fordítói hibaüzenetek szövege verziófüggő. A laborban szereplő Error típus a korábbi alfejezetekben (Saját hibatípusok: enum-hibák, thiserror, anyhow, I/O és szerializáció: fájlok, pufferelés, serde) készült thiserror/serde alapokra épül; a pontos Error-enum és a From implementációk a rkv-core tényleges állapotától függnek, ezért a laborban a crate::error::Error használatát egyeztetni kell a meglévő hibakezelési modullal. A serde_json HashMap<String, Vec<u8>> szerializációja működik, de a FileStore naplóval és atomikus cserével való bővítése későbbi labor feladata.
