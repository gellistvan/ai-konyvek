13.2 Iterátorok: lusta adapterek és saját iterátor

13.2.1 Motiváció

C++-ban egy vektor elemeinek szűrése és transzformálása gyakran kézi ciklussal történik: indexelünk, push_back-et hívunk, ellenőrizzük a határokat, és közben könnyen elkövetünk off-by-one hibát vagy véletlenül módosítjuk a bejárt konténert. A C++20 std::ranges már kínál lusta view-kat, de a Rust iterátorai ezt a szemléletet a nyelv szerves részeként, trait-alapú, egységes felülettel valósítják meg. A Rust iterátorlánc kifejező, lusta, és a fordító a borrow checkerrel garantálja, hogy az iteráció közben nem érvénytelenítjük a gyűjteményt. Ebben az alfejezetben megismerjük az Iterator trait-et, a három alapvető iterátortípust, az adaptereket, és saját iterátort írunk az rkv kulcsainak bejárására.

13.2.2 Fogalmak és szabályok

Definíció. Az Iterator trait egyetlen kötelező metódust ír elő: a next-et, amely Option<Self::Item>-et ad vissza. Az Item asszociált típus az iterátor által szolgáltatott elem típusa. A trait számos további metódust (adaptereket és fogyasztókat) default implementációval biztosít, amelyek a next-re épülnek.

pub trait Iterator {
    type Item;
    fn next(&mut self) -> Option<Self::Item>;
    // map, filter, fold, collect, ...
}

Definíció. A lusta adapter (lazy adapter) olyan iterátor-transzformáció, amely a next hívásakor végzi el a számítást. A fogyasztó (consumer) olyan metódus, amely végighúzza az iterátort, és értéket, gyűjteményt vagy mellékhatást állít elő. A map, filter, enumerate, zip, take, skip, flat_map adapterek; a collect, fold, count, sum, for_each és a for ciklus fogyasztók. Amíg nincs fogyasztó, az adapterlánc egyetlen elemet sem dolgoz fel.

Szabály. A for ciklus szintaktikai cukor: a for x in iterable kifejezés az iterable értéken meghívja az IntoIterator::into_iter-et, majd addig hívja a kapott iterátor next-jét, amíg az Some-ot ad. A &v és &mut v is implementálja az IntoIterator-t, így a for &x in &v a v.iter()-nek, a for x in &mut v a v.iter_mut()-nak felel meg.

Szabály. Három alapvető iterátortípus létezik:

  • iter(): &T elemeket ad, a gyűjteményt nem fogyasztja, a kollekció kölcsönzött marad.
  • iter_mut(): &mut T elemeket ad, a gyűjteményt nem fogyasztja, de a kölcsönzési szabályok szerint egyszerre csak egy &mut lehet.
  • into_iter(): T elemeket ad, a gyűjteményt elfogyasztja; utána a kollekció már nem használható, mert a tulajdonjog átkerült az iterátorba.

Szabály. A collect az iterátort B típusú gyűjteménnyé alakítja, ha B implementálja a FromIterator<Self::Item> trait-et. Ha az elemek Result<T, E> típusúak, akkor a Result<Vec<T>, E> is implementálja a FromIterator-t: a gyűjtés az első Err-nél leáll, és Err-t ad; ha minden elem Ok, akkor Ok(Vec<T>) lesz az eredmény. Hasonlóan működik Option esetén is.

A fenti ábra azt mutatja, hogy az adapterek csak egy leírást építenek fel; a tényleges munka a collect hívásakor történik meg, amikor a fogyasztó sorban meghívja a next-et a lánc végén.

13.2.3 C++ ↔︎ Rust összevetés

C++20 ranges segítségével lusta view-kat fűzhetünk össze:

#include <iostream>
#include <ranges>
#include <vector>

int main() {
    std::vector<int> v = {1, 2, 3, 4, 5, 6};
    auto result = v
        | std::views::filter([](int x) { return x % 2 == 0; })
        | std::views::transform([](int x) { return x * x; });

    for (int x : result) {
        std::cout << x << ' ';
    }
}

Rustban ugyanez idiomatikusan:

fn main() {
    let v = vec![1, 2, 3, 4, 5, 6];
    let result: Vec<_> = v
        .iter()
        .filter(|&&x| x % 2 == 0)
        .map(|&x| x * x)
        .collect();
    println!("{result:?}");
}

A különbség lényeges: a C++ ranges view-k a begin()/end() és a koncepciók köré épülnek, míg a Rust az Iterator trait egységes next() metódusára. A Rust verzióban a closure-ök explicit mintát kapnak: v.iter() &i32 elemeket ad, a filter predikátuma ezért &&i32-et kap (&&x), a map pedig &x-et. A C++-ban a lambda paramétere int (a view értékként adja át az elemet). A Rust collect típusinferencia a turbofish (::<Vec<_>>) segítségével egyértelmű, míg a C++-ban C++23-ig explicit konstruktor vagy std::ranges::to kellett. Mindkét megoldás zero-cost absztrakció: a fordító inline-eli a hívásokat, és a generált kód gyakorlatilag megegyezik a kézi cikluséval.

13.2.4 Kidolgozott példa: lustaság és a Result gyűjtése

A lustaság megértéséhez nézzünk egy hibás kódot, amelyben nincs fogyasztó:

fn main() {
    let v = vec![1, 2, 3, 4, 5];
    v.iter().map(|x| {
        println!("{x}");
        x * 2
    });
}

Ez a program nem ír ki semmit. A map csak egy új iterátort ad vissza, de a next-et soha nem hívja meg senki, mert nincs fogyasztó. A lánc eredményét el kellene tárolni, vagy meg kell hívni a collect-et.

Helyes változat:

fn main() {
    let v = vec![1, 2, 3, 4, 5];
    let doubled: Vec<_> = v.iter().map(|&x| x * 2).collect();
    println!("{doubled:?}");
}

Most a collect végighúzza az iterátort, és a map lefut minden elemen. Várt kimenet: [2, 4, 6, 8, 10].

A Result elemeket tartalmazó iterátor gyűjtése gyakori hibaforrás. Tekintsük a következő függvényt:

fn parse_all(items: Vec<&str>) -> Result<Vec<i32>, std::num::ParseIntError> {
    items
        .iter()
        .map(|s| s.parse::<i32>())
        .collect::<Result<Vec<_>, _>>()
}

fn main() {
    let ok = parse_all(vec!["1", "2", "3"]);
    let err = parse_all(vec!["1", "x", "3"]);
    println!("{ok:?}");
    println!("{err:?}");
}

A collect a FromIterator implementációt használja: ha minden parse Ok-t ad, akkor Ok(vec![1, 2, 3]); ha az egyik Err, akkor a gyűjtés leáll, és Err(ParseIntError) lesz az eredmény. A hiányzó turbofish (::<Result<Vec<_>, _>>) esetén a fordító E0282 hibát ad, mert nem tudja kitalálni a célgyűjtemény típusát. A típus explicit megadása a turbofish-sel vagy a függvény visszatérési típusának annotálásával szünteti meg a hibát.

13.2.5 Labor: saját iterátor az rkv kulcsainak bejárására

Ebben a laborban saját iterátort implementálunk az rkv-core crate-ben, amely a MemStore kulcsainak bejárását teszi lehetővé. A cél egy Keys típus, amely az Iterator trait-et implementálja, és a MemStore::keys() metódus ezt adja vissza.

Munkakönyvtár: ~/rust-labor/rkv (a workspace gyökere). Az önálló kísérletekhez hozzunk létre egy új projektet: ~/rust-labor/r029 (cargo new r029), de az rkv-t módosítjuk a workspace-ben.

A korábbi alfejezetekben a MemStore belső tárolója HashMap<String, Vec<u8>> lett. Ezt használjuk most. Nyissuk meg az rkv-core/src/store.rs fájlt, és adjuk hozzá a Keys iterátort.

Először a szükséges importok:

use std::collections::HashMap;
use std::collections::hash_map;

A Keys struct egy meglévő hash_map::Keys iterátort csomagol be, hogy a saját típusunkat adja:

pub struct Keys<'a> {
    inner: hash_map::Keys<'a, String, Vec<u8>>,
}

Majd implementáljuk az Iterator trait-et:

impl<'a> Iterator for Keys<'a> {
    type Item = &'a str;

    fn next(&mut self) -> Option<Self::Item> {
        self.inner.next().map(|k| k.as_str())
    }
}

A hash_map::Keys iterátor next metódusa Option<&String>-et ad; a map ezt alakítja Option<&str>-ré. Az élettartam 'a a MemStore belső HashMap-éhez kötődik, így a visszaadott referenciák addig érvényesek, amíg a tároló él.

Végül a MemStore kap egy keys metódust:

impl MemStore {
    pub fn keys(&self) -> Keys<'_> {
        Keys {
            inner: self.data.keys(),
        }
    }
}

A MemStore definíciója a meglévő kódban:

pub struct MemStore {
    data: HashMap<String, Vec<u8>>,
}

Ha a data mező más nevet visel, igazítsuk hozzá. A keys metódus visszatérési típusa Keys<'_>: az elision szabályai szerint a visszatérési élettartam az &self élettartamához kötődik.

Most használjuk az iterátort a Storage trait list metódusának megvalósításában. A MemStore list metódusa a self.keys()-t használja a prefix szűréshez:

impl Storage for MemStore {
    fn list(&self, prefix: &str) -> Vec<String> {
        self.keys()
            .filter(|k| k.starts_with(prefix))
            .map(|k| k.to_owned())
            .collect()
    }
    // a többi metódus...
}

Ez a kód egy tipikus iterátorlánc: szűrés, transzformáció, gyűjtés. A filter csak a prefixet tartalmazó kulcsokat engedi tovább, a map String-gé alakít, a collect pedig Vec<String>-et épít.

Végül adjunk egy tesztet, amely ellenőrzi a keys iterátor működését:

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn keys_iterates_all_keys() {
        let mut store = MemStore::new();
        store.set("alpha".to_string(), b"1".to_vec()).unwrap();
        store.set("beta".to_string(), b"2".to_vec()).unwrap();
        let mut keys: Vec<_> = store.keys().collect();
        keys.sort();
        assert_eq!(keys, vec!["alpha", "beta"]);
    }
}

A MemStore::new() és a set metódus a korábbi laborokból ismertek; ha a szignatúrák eltérnek, igazítsuk hozzá. A teszt futtatása:

cd ~/rust-labor/rkv
cargo test -p rkv-core

Várt kimenet: a teszt sikeres, a keys iterátor helyesen visszaadja a kulcsokat.

A labor eredményeként az rkv-core/src/store.rs fájlban megjelent a Keys<'a> iterátor és a MemStore::keys() metódus. Ezt az iterátort később a gyűjteményekkel foglalkozó alfejezetben, a párhuzamos iterátoroknál és a teljesítményhangolásnál is használni fogjuk.

13.2.6 Tipikus hibák és átállási csapdák

  1. A lustaság elfelejtése. A v.iter().map(...) önmagában nem végez semmilyen munkát; a lánc csak akkor fut le, ha egy fogyasztót (például collect, for_each vagy fold) is meghívunk. Ez a hiba csendben maradhat, mert a program lefordul, de nem csinálja a várt műveletet.

  2. A collect típusának elhagyása. A let result = iterator.collect(); gyakran E0282 hibát ad, mert a fordító nem tudja megállapítani a célgyűjtemény típusát. A megoldás a turbofish (collect::<Vec<_>>()) vagy a változó típusának annotálása.

  3. iter_mut és iter keverése. Ha iter()-rel kapott &T referenciát próbálunk módosítani, a fordító hibát jelez. Hasonlóan, ha iter_mut-ot használunk, miközben más shared referenciák élnek a gyűjteményre, a borrow checker elutasítja a kódot. A megoldás a kölcsönzési szabályok betartása: vagy csak iter, vagy csak iter_mut, de nem egyszerre.

  4. into_iter tulajdonjogvesztés. Az into_iter elfogyasztja a gyűjteményt; ha utána még hivatkozunk rá, fordítási hiba lép fel. Ha szükségünk van a gyűjteményre az iteráció után, használjunk iter-t vagy iter_mut-ot.

13.2.7 Feladatok

  1. Lefordul-e és miért? Adott a következő kód:
let v = vec![1, 2, 3];
let it = v.iter().map(|x| x + 1);
println!("{}", v[0]);

Lefordul-e? Magyarázd meg az iter és az into_iter közötti különbséget ebben a kontextusban!

  1. C++-kód átírása idiomatikus Rustra. Az alábbi C++ kód egy vektor összes páros elemének négyzetét számítja ki kézi ciklussal:
std::vector<int> result;
for (int x : v) {
    if (x % 2 == 0) {
        result.push_back(x * x);
    }
}

Írd át idiomatikus Rust iterátorláncra! Ügyelj a collect típusának megadására.

  1. Implementációs feladat az rkv-ban. A MemStore::keys() jelenleg a belső HashMap kulcsait adja. Egészítsd ki a Keys iterátort úgy, hogy a next metódus csak a nem üres értékű kulcsokat adja vissza (az értékük hossza nagyobb, mint 0). Módosítsd a keys metódust, hogy a data mezőből építse fel a Keys iterátort a belső hash_map::Iter segítségével, és a next az első nem üres értékű kulcsig lépkedjen.

  2. Hibajavítás/refaktorálás. A következő kód szándékosan hibás:

fn sum_of_squares(v: &Vec<i32>) -> i32 {
    let squares = v.iter().map(|x| x * x);
    squares.sum()
}

fn main() {
    let v = vec![1, 2, 3];
    println!("{}", sum_of_squares(&v));
}

Ez a kód lefordul és működik, de van egy stilisztikai és egy hatékonysági javaslat. Módosítsd a függvényt, hogy elkerüld a felesleges temporális változót, és magyarázd el, miért működik a sum fogyasztó a lusta map után!

13.2.8 Megoldások

  1. Lefordul-e? Igen, lefordul. A v.iter() a vektort nem fogyasztja, csak kölcsönzi; az it egy lusta iterátor, amely a next hívásakor dolgozik. A v[0] kifejezés a vektor indexelése, amihez nem szükséges a tulajdonjog. Ha azonban v.into_iter()-et használtunk volna, a v tulajdonjoga átkerült volna az iterátorba, és a v[0] hivatkozás E0382 hibát adna, mert a v már érvénytelen. Az iter tehát nem fogyasztó, az into_iter pedig igen.

  2. C++ → Rust átírás. Az idiomatikus Rust iterátorlánc:

let result: Vec<i32> = v
    .iter()
    .filter(|&&x| x % 2 == 0)
    .map(|&x| x * x)
    .collect();

A v.iter() &i32 elemeket ad; a filter predikátuma &&x-et kap, mert a filter az elem referenciáját adja a closure-nek. A map a páros elemek négyzetét számítja, a collect pedig Vec<i32>-t épít. A típus annotálása a result változón egyértelműsíti a collect célgyűjteményét.

  1. Implementációs feladat megoldása. A Keys iterátort módosítjuk, hogy a belső hash_map::Iter segítségével csak a nem üres értékű kulcsokat adja:
use std::collections::hash_map;

pub struct Keys<'a> {
    inner: hash_map::Iter<'a, String, Vec<u8>>,
}

impl<'a> Iterator for Keys<'a> {
    type Item = &'a str;

    fn next(&mut self) -> Option<Self::Item> {
        while let Some((k, v)) = self.inner.next() {
            if !v.is_empty() {
                return Some(k.as_str());
            }
        }
        None
    }
}

impl MemStore {
    pub fn keys(&self) -> Keys<'_> {
        Keys {
            inner: self.data.iter(),
        }
    }
}

A hash_map::Iter a HashMap iterátora, amely (k, v) párokat ad. A next metódus addig lép, amíg nem talál egy nem üres értéket; ha nincs több elem, None-t ad. Az élettartam annotációk biztosítják, hogy a visszaadott &str referenciák a self.data-hoz kötődnek.

  1. Hibajavítás/refaktorálás. A függvény működik, de a squares temporális változó felesleges. Idiomatikusabb változat:
fn sum_of_squares(v: &[i32]) -> i32 {
    v.iter().map(|x| x * x).sum()
}

A sum fogyasztó a map által visszaadott lusta iterátoron hívódik; a sum végighúzza a láncot, kiszámítja a négyzetek összegét. A &Vec<i32> paramétert &[i32]-re cseréltük, mivel a slice általánosabb: mind Vec-re, mind más slice-okra működik. A sum a x * x értékeket i32-ként adja össze, mert az Iterator Item-je i32 (a map closure &i32-et kap, de x * x már érték).

13.2.9 Rövid összefoglaló

Az Iterator trait a next metódusra épül, és az Item asszociált típussal adja meg az elem típusát. A for ciklus az IntoIterator-t használja, a iter, iter_mut és into_iter pedig a kölcsönzési és tulajdonjogi szemantikát különbözteti meg. Az adapterek (map, filter, enumerate, zip, take, skip, flat_map, fold) lusták: csak akkor futnak le, ha egy fogyasztó (collect, sum, for_each) végighúzza a láncot. A collect::<Result<Vec<_>, _>>() rövidre zár az első hibánál. A laborban az rkv-core/src/store.rs fájlban létrehoztuk a Keys<'a> iterátort és a MemStore::keys() metódust, amely a kulcsokat &str elemekként adja. Ezt az iterátort a későbbi alfejezetek – a gyűjtemények (Vec, HashMap, BTreeMap és társaik; az Entry API), a párhuzamos iterátorok (Adatpárhuzamosság rayonnal) és a teljesítményoptimalizálás (Teljesítmény: mérés, profilozás, allokáció, release-beállítások) – használják majd.
