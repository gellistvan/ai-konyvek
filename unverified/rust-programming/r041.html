17.5 Naplózás és megfigyelhetőség: tracing

17.5.1 Motiváció

Egy C++-ban írt TCP-szerver naplózása gyakran std::cerr-re írt sorokból vagy egy spdlog-hoz hasonló könyvtárból áll. A kérések nyomon követéséhez kézzel kell egyedi azonosítókat (request_id) generálni, és minden logüzenetbe beilleszteni. A konkurrens kérések esetén a naplóbejegyzések összekeverednek, és utólag nehéz rekonstruálni, hogy melyik sor melyik kéréshez tartozott. A szűrés szintje és modulja gyakran fordítási időben rögzült, vagy bonyolult konfigurációt igényel.

A Rust tracing crate-je ezt a problémát strukturált naplózással és span-ekkel oldja meg. Egy span egy műveleti hatókör (például egy kérés feldolgozása), amelybe a benne lévő események automatikusan beletartoznak. Így egyetlen #[instrument] attribútummal minden kéréshez kapunk egy azonosítót, és a napló szűrése futás közben, környezeti változóval állítható. Az rkv-server már rendelkezik a Stats típusú atomikus számlálókkal a Atomikus műveletek és memóriarendezés alfejezetből; ebben a laborban ezeket tesszük megfigyelhetővé.

17.5.2 Fogalmak és szabályok

Definíció. A tracing crate három alapfogalma:

  • Event (tracing::info!, debug!, warn!, error!, trace!): egy időpontban bekövetkező esemény, hasonló a klasszikus naplóbejegyzéshez, de strukturált mezőket tartalmazhat.
  • Span (tracing::span! vagy a #[instrument] attribútum): egy időintervallumot átfogó, hierarchikus kontextus. A span-ek egymásba ágyazhatók, és az események a legbelső aktív span-hez tartoznak.
  • Subscriber: a naplófogyasztó, amely a span-eket és eventeket megkapja, és formázva kiírja, szűri vagy továbbítja. A tracing-subscriber a leggyakoribb implementáció.

Definíció. Az EnvFilter a tracing-subscriber szűrője, amely környezeti változóból (RUST_LOG) olvassa be a naplózási szinteket, például:

RUST_LOG=info
RUST_LOG=rkv_server=debug
RUST_LOG=info,tokio=warn

Ez modulonként (crate-enként) állítja be a minimális szintet.

Szabály. A #[tracing::instrument] attribútum egy függvényre írva automatikusan span-t nyit a függvény belépésekor, és bezárja kilépéskor. Alapértelmezés szerint a span neve a függvény neve, és a paramétereket strukturált mezőkként rögzíti (ha azok implementálják a Debug trait-et; a skip paraméterrel kihagyhatók).

Szabály (async kontextus). Async függvényekben a span-eknek át kell ívelniük az .await pontokon. A tracing modern verziói (0.1.x) a tracing-futures integrációval és az Instrument trait-tel ezt automatikusan kezelik; a #[instrument] async függvényekre is működik, mert a proc-macro a jövőt instrumentálja.

17.5.3 C++ ↔︎ Rust összevetés

C++-ban egy szokásos időmérő és naplózó scope-segéd:

#include <spdlog/spdlog.h>
#include <chrono>

class ScopedLog {
public:
    ScopedLog(const std::string& name)
        : name_(name), start_(std::chrono::steady_clock::now()) {
        spdlog::info("{} start", name_);
    }
    ~ScopedLog() {
        auto ms = std::chrono::duration_cast<std::chrono::milliseconds>(
            std::chrono::steady_clock::now() - start_).count();
        spdlog::info("{} end ({} ms)", name_, ms);
    }
private:
    std::string name_;
    std::chrono::steady_clock::time_point start_;
};

void handle_request(const Request& req) {
    ScopedLog log("handle_request");
    // ...
}

A Rust megfelelője ugyanez, de nyelvi szinten és async-tudatosan:

#[tracing::instrument]
async fn handle_request(socket: TcpStream) {
    // ...
}

A különbség: a Rust #[instrument] nem csupán időt mér, hanem egy span-t hoz létre, amely a naplófogyasztó számára hierarchiát jelent. A formázott kimenetben a span-azonosító és az átfutási idő automatikusan megjelenik, a strukturált mezők pedig gépi feldolgozásra is alkalmasak. C++-ban ehhez kézi request_id-t kellene átadni minden loghívásnak.

17.5.4 Kidolgozott példa: tracing alapok

Először egy önálló kis programot írunk, hogy lássuk a span-ek és az EnvFilter működését.

Munkakönyvtár: ~/rust-labor/r041-tracing/

cargo new r041-tracing
cd r041-tracing

Cargo.toml:

[dependencies]
tracing = "0.1"
tracing-subscriber = { version = "0.3", features = ["env-filter"] }

src/main.rs:

use tracing::{info, debug, warn, Level};
use tracing_subscriber::EnvFilter;

#[tracing::instrument]
fn compute(value: u64) -> u64 {
    debug!(value, "számítás indul");
    let result = value * 2;
    info!(result, "számítás kész");
    result
}

fn main() {
    tracing_subscriber::fmt()
        .with_env_filter(EnvFilter::from_default_env())
        .init();

    warn!("példa indul");
    compute(21);
}

Futtatás alapértelmezett RUST_LOG nélkül:

cargo run

Várt kimenet (az időbélyeg formátuma változhat):

2025-01-01T10:00:00.000000Z  WARN r041_tracing: példa indul
2025-01-01T10:00:00.000100Z  INFO r041_tracing: compute: számítás kész, result: 42
2025-01-01T10:00:00.000200Z  INFO r041_tracing: compute: span closed, value: 21

A debug! üzenet nem jelenik meg, mert az alapértelmezett szint INFO. Ezt módosíthatjuk:

RUST_LOG=debug cargo run

Ekkor a debug! is megjelenik, és a span-események is részletesebbek. Az EnvFilter::from_default_env() a RUST_LOG környezeti változót olvassa; ha nincs beállítva, az alapértelmezett szint INFO (ebből kimarad a trace és a debug).

17.5.5 Labor: naplózás és metrikák az rkv-serverben

Munkakönyvtár: ~/rust-labor/rkv/

A korábbi Az rkv hálózati szerver: TCP, protokoll, kecses leállás alfejezetben létrehoztuk az rkv-server binárist, amely tokio TCP-szervert futtat, és a Store-t használja. A Atomikus műveletek és memóriarendezés alfejezetben a Store már tartalmaz egy Arc<Stats> mezőt atomikus számlálókkal. Most ezt tesszük megfigyelhetővé.

17.5.5.1 1. Függőségek hozzáadása

Az rkv-server/Cargo.toml [dependencies] szakaszához adjuk hozzá:

[dependencies]
tracing = "0.1"
tracing-subscriber = { version = "0.3", features = ["env-filter"] }

17.5.5.2 2. Subscriber inicializálása

Az rkv-server/src/main.rs elején inicializáljuk a tracing subscriber-t. Ügyeljünk arra, hogy ezt csak egyszer tegyük meg, még a tokio runtime elindítása előtt:

use tracing::info;
use tracing_subscriber::EnvFilter;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    tracing_subscriber::fmt()
        .with_env_filter(EnvFilter::from_default_env())
        .init();

    info!("rkv-server indul");
    // ... a korábbi szerverindítási kód
}

17.5.5.3 3. Kérések instrumentálása

A kapcsolatkezelő függvényre tegyünk #[tracing::instrument] attribútumot. Mivel a függvény async, és a Store-t, valamint a socketet paraméterként kapja, a skip opcióval jelezzük, hogy ezeket ne próbálja Debug formátumban kiírni:

#[tracing::instrument(skip(store, socket))]
async fn handle_connection(store: Arc<Store>, socket: TcpStream) -> anyhow::Result<()> {
    let mut reader = BufReader::new(socket);
    let mut line = String::new();
    loop {
        line.clear();
        let n = reader.read_line(&mut line).await?;
        if n == 0 {
            break;
        }
        let cmd = parse_command(line.trim())?;
        // A parancsot is instrumentálhatjuk:
        let span = tracing::info_span!("handle_command", %cmd);
        let _enter = span.enter();
        let response = store.execute(cmd)?;
        write_response(&mut reader, response).await?;
    }
    Ok(())
}

A %cmd a Display megvalósítást használja, így a span mezője olvasható marad. Ha a Command enum implementálja a Display trait-et, akkor ez működik; ha nem, használjuk a ?cmd (Debug) formát.

17.5.5.4 4. Metrikák periodikus kiírása

A Store már rendelkezik stats() getterrel, amely Arc<Stats>-ot ad vissza. Az atomikus számlálók AtomicU64 típusúak. Egy külön tokio taskban periodikusan kiírjuk az értékeket:

use std::time::Duration;
use std::sync::atomic::Ordering;

async fn metrics_loop(store: Arc<Store>) {
    let mut interval = tokio::time::interval(Duration::from_secs(10));
    loop {
        interval.tick().await;
        let stats = store.stats();
        info!(
            get = stats.get_count.load(Ordering::Relaxed),
            set = stats.set_count.load(Ordering::Relaxed),
            delete = stats.delete_count.load(Ordering::Relaxed),
            list = stats.list_count.load(Ordering::Relaxed),
            "metrikák"
        );
    }
}

Indítsuk el ezt a taskot a main-ben:

tokio::spawn(metrics_loop(store.clone()));

Ez a task a Relaxed rendezéssel olvassa a számlálókat, ami elegendő, mert a metrikák pontos sorrendje nem kritikus; csak időszakos jelentést adunk. Az atomikus műveletek az Atomikus műveletek és memóriarendezés alfejezetben leírtak szerint garantálják a számlálók integritását.

17.5.5.5 5. Szűrés környezeti változóval

A szerver futtatása előtt beállíthatjuk a kívánt szintű naplózást:

RUST_LOG=info cargo run -p rkv-server

Ez mindent naplóz INFO szinttől felfelé. Ha csak a saját crate naplóit szeretnénk DEBUG szinten, a külső crate-eket (például a tokio belső üzeneteit) pedig WARN szinten:

RUST_LOG=rkv_server=debug,tokio=warn cargo run -p rkv-server

A RUST_LOG támogatja a többszörös modulszűrést vesszővel elválasztva.

17.5.5.6 Várt kimenet

Egy SET kulcs ertek kérés után a metrika task legközelebbi tickjekor a következőhöz hasonló sor jelenik meg:

2025-01-01T10:00:10.000Z  INFO rkv_server: metrikák, get: 0, set: 1, delete: 0, list: 0

A kapcsolatkezelés során a span-ek a formázott kimenetben behúzva jelennek meg, jelezve a hierarchiát.

17.5.6 Tipikus hibák és átállási csapdák

  1. A subscriber többszöri inicializálása. Ha például egy tesztmodulban minden teszt lefutásakor meghívjuk a tracing_subscriber::fmt().init()-et, a második hívás SetGlobalDefaultError hibát ad. Megoldás: a subscriber-t egyszer, a main-ben vagy egy Once/OnceCell segítségével inicializáljuk, vagy a tesztekben a try_init() metódust használjuk, amely csendben elnyeli a hibát.

  2. Span-ek elvesztése async kódban. Ha egy async függvényben explicit módon hozunk létre span-t a span.enter() metódussal, az .await pont után a span nem marad aktív, mert a future megszakad. A megoldás a tracing::Instrument trait használata (future.instrument(span)) vagy a #[tracing::instrument] attribútum, amely a teljes future-t instrumentálja.

  3. Túlzott strukturálás. Minden kis lépést span-be csomagolni zajossá teszi a naplót. A span-eket műveleti határokhoz (például kérés, parancs) rendeljük, ne minden egyes függvényhíváshoz.

  4. A RUST_LOG figyelmen kívül hagyása. Ha az EnvFilter::from_default_env() helyett fix szintet adunk meg, akkor a futás közbeni szűrés nem működik. Mindig az EnvFilter-t használjuk, hogy a környezeti változóval szabályozhassuk a naplózást.

17.5.7 Feladatok

  1. Fogalmi kérdés. Mi történik, ha a compute függvényben a #[tracing::instrument] attribútumot elhagyjuk, de a függvényen belül továbbra is van info! makró? A kimenetben mi változik a span nélkül?

  2. C++ átírás. A következő C++ kódrészlet egy kérést naplóz request_id-vel. Írd át Rustra tracing span-nel úgy, hogy a request_id ne legyen kézzel átadott paraméter, hanem a span automatice rögzítse.

void handle_request(int request_id, const Request& req) {
    spdlog::info("request {}: start", request_id);
    // ...
    spdlog::info("request {}: end", request_id);
}

  1. Implementáció. Az rkv-server-hez adj hozzá egy új metrikát: az aktív kapcsolatok számát. Használj AtomicU64-et a Stats struktúrában, növeld a kapcsolat kezdetekor, csökkentsd a végén, és írd ki a metrics_loop-ban.

  2. Hibajavítás. A következő kód nem fordul le, mert a subscriber-t kétszer inicializálja. Javítsd úgy, hogy a második inicializálás ne okozzon hibát.

fn init_logging() {
    tracing_subscriber::fmt().init();
}

fn main() {
    init_logging();
    init_logging(); // hibát okoz
    info!("hello");
}

17.5.8 Megoldások

  1. Fogalmi kérdés. A span nélkül az info! event-ek továbbra is megjelennek, de nem tartoznak egyetlen műveleti kontextushoz sem. A formázott kimenetben nem lesz span-azonosító, és a compute függvény belépését/kilépését nem látjuk automatikusan. Az event-ek lapos listát alkotnak, és nem lehet őket összekapcsolni.

  2. C++ átírás. A Rust változat span-t használ:

#[tracing::instrument(skip(req))]
fn handle_request(req: &Request) {
    info!("feldolgozás kezdődik");
    // ...
    info!("feldolgozás kész");
}

A request_id-t nem kell explicit paraméterként átadni; a span automatikusan kap egy azonosítót, és a naplófogyasztó kimenetében megjelenik. Ha mégis szeretnénk a saját azonosítót, a span mezőjébe tehetjük: tracing::info_span!("handle_request", request_id).entered().

  1. Implementáció. A rkv-core/src/stats.rs-ben:
use std::sync::atomic::AtomicU64;

#[derive(Debug, Default)]
pub struct Stats {
    pub get_count: AtomicU64,
    pub set_count: AtomicU64,
    pub delete_count: AtomicU64,
    pub list_count: AtomicU64,
    pub active_connections: AtomicU64,
}

A kapcsolatkezelő függvény elején:

store.stats().active_connections.fetch_add(1, Ordering::Relaxed);

Végül a metrics_loop-ban:

active = stats.active_connections.load(Ordering::Relaxed),
  1. Hibajavítás. Használjunk try_init-et, amely nem hibázik, ha már van subscriber:
fn init_logging() {
    let _ = tracing_subscriber::fmt().try_init();
}

fn main() {
    init_logging();
    init_logging(); // most már nem okoz hibát
    info!("hello");
}

17.5.9 Rövid összefoglaló

A tracing crate strukturált naplózást és hierarchikus span-eket biztosít. Az eventek (info!, debug!, warn!, error!) klasszikus naplóbejegyzések, míg a span-ek műveleti hatókörök, amelyeket a #[tracing::instrument] attribútum automatikusan nyit és zár. A tracing-subscriber EnvFilter-je a RUST_LOG környezeti változóval modulonként és szintenként szűri a naplót. Async kódban a #[instrument] a teljes future-t instrumentálja, így a span-ek átívelnek az .await pontokon. Az rkv-serverben hozzáadtuk a tracing és tracing-subscriber függőségeket, inicializáltuk a subscriber-t a main-ben, a kapcsolatkezelőt #[tracing::instrument]-tel jelöltük, és egy metrics_loop tokio taskban periodikusan kiírjuk a Stats atomikus számlálóit. Továbbvitt eredmény. A megfigyelhető szerver ezen naplózási és metrika-rétege biztosítja a Záróprojekt: az rkv teljes rendszerként alfejezetben a rendszer állapotának áttekintését.
