12.2 Asszociált típusok, koherencia, operátorok és derive

12.2.1 Motiváció

C++-ban a generikus kód gyakran a típus „belsejében” lévő típusokat használ: az std::vector<T>::value_type, az iterátor value_type-ja vagy egy konténer key_type-ja. Ezek konvenciók, amelyeket a template paraméterből kell kitalálni, és a fordító csak akkor tudja ellenőrizni, ha egy concept vagy std::iterator_traits segít. Rustban ezt a szerepet az asszociált típus tölti be: a trait részeként deklaráljuk, hogy az implementáló típus milyen típust ad hozzá. Így a generikus függvény egyértelműen hivatkozhat T::Item-re, anélkül hogy a hívó oldalán paraméterezni kellene. Ugyanez a filozófia vezet a koherencia-szabályhoz is: a Rust nem enged idegen trait idegen típusra való implementálását, mert így garantálja, hogy egy (trait, típus) párhoz globálisan egyetlen implementáció tartozik. Ez elsőre korlátozásnak tűnik, valójában a generikus API-k kiszámíthatóságát védi.

12.2.2 Asszociált típusok

Definíció. Az asszociált típus (associated type) egy traitben deklarált típusnév, amelyet az implementáló típus ad meg. A trait törzsében type Item; formában szerepel, az implementációban pedig type Item = KonkrétTípus;.

A standard könyvtár legismertebb példája az Iterator:

trait Iterator {
    type Item;
    fn next(&mut self) -> Option<Self::Item>;
}

Az asszociált típus előnye, hogy a generikus kód nem Iterator<u32>-t ír, hanem egyszerűen I: Iterator, és a függvényben I::Item-ként hivatkozik az elem típusára. Ha a Iterator generikus paramétert használna, akkor egy típushoz több Iterator<u32>, Iterator<String> implementáció is tartozhatna, ami a legtöbb iterátornál értelmetlen: egy iterátor egyfajta elemet ad.

Szabály. Ha egy típushoz természeténél fogva egyetlen kapcsolódó típus tartozik, asszociált típust használj. Ha ugyanarra a típusra több, egymástól független implementációra van szükséged, amelyek csak a paraméterben térnek el, generikus paramétert használj.

A különbség szemléltetése:

// Generikus paraméter: több implementáció lehetséges.
trait Parser<T> {
    fn parse(&self, input: &str) -> Option<T>;
}

impl Parser<i32> for MyParser { /* ... */ }
impl Parser<String> for MyParser { /* ... */ }

// Asszociált típus: egy implementáció, egy Output.
trait Parser {
    type Output;
    fn parse(&self, input: &str) -> Option<Self::Output>;
}

impl Parser for MyParser {
    type Output = i32;
    // ...
}

C++-ban hasonló célt szolgál a tag-típus vagy az std::iterator_traits:

template <typename T>
struct my_iterator {
    using value_type = T;
    // ...
};

template <typename T>
concept an_iterator = requires(T it) {
    typename T::value_type;
    { it.next() } -> std::same_as<typename T::value_type>;
};

A Rust fordító azonban nem csak jelzi, hanem a trait definíciójakor kötelezi az implementálót, hogy az asszociált típust is megadja. Ha lemarad, a hibakód jellemzően E0046: a trait nem teljes, mert hiányzik az Item asszociált típus.

12.2.3 Koherencia és az orphan rule

Definíció. Az orphan rule (árvaszabály) kimondja: idegen traitet idegen típusra nem implementálhatsz. Az implementáció csak akkor érvényes, ha legalább a trait vagy a típus lokális az aktuális crate-ben. A koherencia pedig azt jelenti, hogy egy adott (trait, típus) párhoz egyetlen implementáció tartozhat, így nem kerülhetnek ütközésbe különböző crate-ek impl-jei.

Ez a C++-tól eltérő modell. C++-ban a std::hash teljes specializálása user-defined típusra megengedett a std névtérben:

struct MyType { int x; };

namespace std {
    template<>
    struct hash<MyType> {
        size_t operator()(const MyType& t) const noexcept {
            return std::hash<int>{}(t.x);
        }
    };
}

Rustban nem nyitogathatjuk a standard könyvtárat. Ha viszont a saját típusunkra akarunk idegen traitet implementálni, az mindig szabályos:

struct MyType { x: i32 }

impl std::fmt::Display for MyType {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        write!(f, "MyType({})", self.x)
    }
}

A tipikusan tiltott eset az, amikor mindkettő idegen:

// Ez a változat szándékosan nem fordul le:
impl std::fmt::Display for Vec<i32> {
    // ...
}

A hibakód E0117, lényege: a Display trait és a Vec típus is idegen; a Rust megtagadja az implementációt, mert az egy másik crate-ben okozhatna ütközést. A szokásos megkerülés a newtype minta: becsomagoljuk az idegen típust egy lokális típusba.

struct WrappedVec(Vec<i32>);

impl std::fmt::Display for WrappedVec {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        write!(f, "{:?}", self.0)
    }
}

Szabály. Ha idegen típusra kell idegen trait képessége, hozz létre egy lokális struct Wrapper(InnerType) típust, és arra implementáld a traitet. A wrapper mezőt ne fedd fel automatikusan Deref implementációval, mert az elrejtheti a típushatárokat; a későbbi Newtype, PhantomData, typestate alfejezet ezt részletesen tárgyalja.

12.2.4 Operátor-túlterhelés trait-ekkel

Rustban nincs szabad operator+ függvény, hanem a standard könyvtár std::ops moduljának trait-jeit implementáljuk. A + kifejezés az Add trait add metódusává íródik át, a [] az Index/IndexMut hívása.

struct Point { int x, y; };

Point operator+(Point a, Point b) {
    return {a.x + b.x, a.y + b.y};
}

Rustban:

#[derive(Debug, Clone, PartialEq, Eq)]
struct Point { x: i32, y: i32 }

impl std::ops::Add for Point {
    type Output = Point;

    fn add(self, rhs: Self) -> Self::Output {
        Self { x: self.x + rhs.x, y: self.y + rhs.y }
    }
}

Lényeges különbség: az eredmény típusa nem a függvény szignatúrájában van, hanem az asszociált Output típus adja. Ezzel például Vector + Vector -> Vector és Vector * Vector -> f64 is kifejezhető, de egy típusra egy Add implementáció egy Rhs paraméterre csak egy Output-tal rendelkezhet.

Az Index szintén trait, és a visszatérési érték kötelezően referencia:

impl std::ops::Index<usize> for Point {
    type Output = i32;

    fn index(&self, index: usize) -> &Self::Output {
        match index {
            0 => &self.x,
            1 => &self.y,
            _ => panic!("Point index out of range"),
        }
    }
}

C++-ban a const és nem const operator[] különbözteti meg az olvasást és az írást; Rustban az Index csak olvas, az IndexMut pedig &mut Self::Output-ot ad. Fontos, hogy az Index szerződése pánik hibás index esetén, nem ad Option-t. Ha az indexelés hibázhat, írj inkább get metódust Option/Result visszatéréssel.

Az egyenlőséghez és rendezéshez a PartialEq, Eq, PartialOrd, Ord trait-ek tartoznak. A PartialEq lehet részleges egyenlőség: például f32::NAN != f32::NAN igaz, ezért a lebegőpontos típusok nem Eq. Az Eq marker trait, amely a teljes reflexivitást ígéri, vagyis minden a-ra a == a. A PartialOrd/Ord ugyanezt a részleges/teljes megkülönböztetést hozza a rendezésre. A Hash trait pedig arra való, hogy egyenlő értékek hash-e megegyezzen, de a hash nem titkosítási eszköz.

12.2.5 Derive-lok és szemantikai következményeik

A #[derive(...)] arra utasítja a fordítót, hogy ismert szabályok alapján implementálja a felsorolt traiteket. A leggyakoribb derive-ok:

#[derive(Debug, Clone, PartialEq, Eq, Hash, Default, PartialOrd, Ord)]
struct Command {
    name: String,
    priority: u32,
}

Szabály. A derive-ok mezőnkénti (strukturális) szemantikát adnak. A generált kód minden mezőre megköveteli ugyanazt a traitet, így ha egy mező nem Eq, a Eq derive sem fordul le.

A fontosabb szemantikai következmények:

  • Debug: fejlesztői, {:?} formátum; nem a felhasználói Display.
  • Clone: explicit, potenciálisan drága másolás; soha nem implicit.
  • PartialEq/Eq: mezőnkénti strukturális egyenlőség. Ha lebegőpontos mező van, az Eq derive hibás, mert f64 nem Eq.
  • Hash: a mezők hash-ét kombinálja, konzisztens a PartialEq-vel; ha ketten egyenlők, a hash-ük is azonos. Nem kriptográfiai hash.
  • Default: minden mezőre a Default értékét használja, így a mezőknek is Default-nak kell lenniük.
  • PartialOrd/Ord: a mezősorrendben lexikografikus rendezést ad. Ez gyakran nem a természetes üzleti rendezés; ha a mezők sorrendje véletlenszerű, a rendezés is kiszámíthatatlan. Ilyenkor inkább kézzel implementáld a traitet.

12.2.6 Blanket implementációk röviden

A blanket implementáció (blanket implementation) olyan generikus impl, amely egy egész típuscsaládra vonatkozik. A standard könyvtárban ilyen például:

impl<T: fmt::Display> ToString for T {
    fn to_string(&self) -> String {
        // ...
    }
}

Minden Display-et implementáló típushoz ad egy ToString implementációt. Ugyanígy működik a From/Into páros: ha T: From<U>, akkor U: Into<T> is automatikusan teljesül. A blanket impl-ek azért fontosak, mert csökkentik a boilerplate-et, de a koherencia miatt a fordító ellenőrzi, hogy ne ütközzenek kézzel írt impl-ekkel. Az orphan rule különösen szigorú blanket impl-eknél, mert egy idegen blanket impl sok típusra terjedhet ki.

12.2.7 Kidolgozott példa: labor az asszociált típusokkal és operátorokkal

Munkakönyvtár: ~/rust-labor/r025/

Hozd létre a labort, és írd meg a src/main.rs fájlt:

cargo new r025
cd r025

Cargo.toml:

[package]
name = "r025"
version = "0.1.0"
edition = "2024"

Ha a telepített stable toolchain nem támogatja a 2024-es editiont, használj 2021-et.

src/main.rs:

use std::fmt;

struct Counter {
    current: u32,
    end: u32,
}

impl Counter {
    fn new(start: u32, end: u32) -> Self {
        Self { current: start, end }
    }
}

impl Iterator for Counter {
    type Item = u32;

    fn next(&mut self) -> Option<Self::Item> {
        if self.current <= self.end {
            let value = self.current;
            self.current += 1;
            Some(value)
        } else {
            None
        }
    }
}

#[derive(Debug, Clone, PartialEq, Eq, Hash, Default, PartialOrd, Ord)]
struct Point {
    x: i32,
    y: i32,
}

impl std::ops::Add for Point {
    type Output = Point;

    fn add(self, rhs: Self) -> Self::Output {
        Self {
            x: self.x + rhs.x,
            y: self.y + rhs.y,
        }
    }
}

impl std::ops::Index<usize> for Point {
    type Output = i32;

    fn index(&self, index: usize) -> &Self::Output {
        match index {
            0 => &self.x,
            1 => &self.y,
            _ => panic!("Point index out of range"),
        }
    }
}

struct WrappedVec(Vec<i32>);

impl fmt::Display for WrappedVec {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "[")?;
        for (i, value) in self.0.iter().enumerate() {
            if i > 0 {
                write!(f, ", ")?;
            }
            write!(f, "{value}")?;
        }
        write!(f, "]")
    }
}

fn main() {
    let sum = Point { x: 1, y: 2 } + Point { x: 3, y: 4 };
    println!("sum = {sum:?}");

    let p = Point::default();
    println!("p = {p:?}, p[0] = {}", p[0]);

    let counter = Counter::new(1, 3).collect::<Vec<_>>();
    println!("counter = {counter:?}");

    let wrapped = WrappedVec(vec![10, 20, 30]);
    println!("wrapped = {wrapped}");
}

Futtasd:

cargo run

Várt kimenet:

sum = Point { x: 4, y: 6 }
p = Point { x: 0, y: 0 }, p[0] = 0
counter = [1, 2, 3]
wrapped = [10, 20, 30]

A példa egyszerre mutatja az asszociált típust (Iterator::Item), a derive-olt strukturális egyenlőséget és rendezést, az Add/Index operátor-trait-eket, valamint a newtype-mintát az orphan rule megkerülésére.

Továbbvitt eredmény. Az itt bemutatott Iterator::Item asszociált típus és a derive-készlet a(z) A standard trait-ek: konverziók, formázás, Default, Deref, Borrow alfejezetben a Display, Deref és Borrow implementációk, a(z) Iterátorok: lusta adapterek és saját iterátor alfejezetben a saját iterátor, a(z) Vec, HashMap, BTreeMap és társaik; az Entry API alfejezetben a hash-kulcsok Hash/Eq követelményei, a(z) Deklaratív és procedurális makrók alfejezetben a derive-makrók, valamint a(z) Newtype, PhantomData, typestate és const generikusok alfejezetben a newtype-minta alapjául szolgál.

12.2.8 Tipikus hibák és átállási csapdák

  1. Generikus paraméter asszociált típus helyett. Ha egy típushoz egyértelműen egyetlen kapcsolódó típus tartozik, a generikus paraméter fölösleges impl-ekhez és turbofish-zűrzavarhoz vezet. Például trait Storage<K, V> helyett inkább type Key és type Value asszociált típus, ha a típus természetesen meghatározza a kulcsot és az értéket.

  2. Eq, Ord, Hash derive lebegőpontos mezőkkel. Az f32/f64 típusok nem implementálják az Eq, Ord és Hash traiteket, mert a NaN és a -0.0/+0.0 szemantikája sértené a szerződést. Ha ilyen mező van, ne erőltesd a derive-ot.

  3. Index hibakezelésre. Az Index szerződése pánik; ha a kulcs hiányozhat, a HashMap-nél használd a get metódust, és add vissza Option-t. Az Index csak akkor való, ha a hibás index programhiba.

  4. Newtype és Deref automatikus kitevése. Sokan Deref-fel teszik láthatóvá a belső típust, hogy ne kelljen delegálni a metódusokat. Ez elrejti a típushatárt, és a későbbi override-ok meglepő viselkedést okozhatnak. A newtype célja éppen a határok megőrzése.

  5. PartialOrd derive mezősorrendre bízva. A mezősorrend lexikografikus rendezése gyakran nem a kívánt üzleti rendezés. Ha a rendezésnek van jelentése, írj explicit impl-et, vagy dokumentáld a mezősorrendet.

12.2.9 Feladatok

12.2.9.1 a) Lefordul-e és miért?

impl std::fmt::Display for Vec<i32> {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        write!(f, "{self:?}")
    }
}

Válaszolj: lefordul-e ez a kód? Ha nem, melyik szabályt sérti, és hogyan javítanád?

12.2.9.2 b) C++-kód átírása idiomatikus Rustra

Add meg a Rust megfelelőjét a következő C++ típusnak, beleértve az összeadást és az egyenlőségvizsgálatot:

struct Size {
    int w;
    int h;
};

Size operator+(Size a, Size b) {
    return {a.w + b.w, a.h + b.h};
}

bool operator==(Size a, Size b) {
    return a.w == b.w && a.h == b.h;
}

12.2.9.3 c) Implementációs feladat az rkv-ban

Az rkv-core crate Command enumjára add a Debug, Clone, PartialEq, Eq, Hash derive-okat. Az enum a Get(String), Set(String, Vec<u8>), Delete(String), List(Option<String>) változatokat tartalmazza. Indokold meg, miért nem adunk PartialOrd-ot Ord-dal.

12.2.9.4 d) Hibajavítás

Az alábbi derive nem fordul le. Miért? Javítsd ki, és indokold a választott megoldást.

#[derive(Debug, Clone, PartialEq, Eq, PartialOrd, Ord, Hash)]
struct Celsius(f64);

12.2.10 Megoldások

12.2.10.1 a)

Nem fordul le. A Display trait és a Vec<i32> típus is idegen, ezért az orphan rule (hibakód E0117) tiltja az implementációt. Megoldás a newtype:

struct ListVec(Vec<i32>);

impl std::fmt::Display for ListVec {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        write!(f, "{:?}", self.0)
    }
}

12.2.10.2 b)

#[derive(Debug, Clone, PartialEq, Eq)]
struct Size {
    w: i32,
    h: i32,
}

impl std::ops::Add for Size {
    type Output = Size;

    fn add(self, rhs: Self) -> Self::Output {
        Self {
            w: self.w + rhs.w,
            h: self.h + rhs.h,
        }
    }
}

Az egyenlőséget a PartialEq/Eq derive generálja; az összeadást az Add trait asszociált Output típusával adjuk meg.

12.2.10.3 c)

#[derive(Debug, Clone, PartialEq, Eq, Hash)]
pub enum Command {
    Get(String),
    Set(String, Vec<u8>),
    Delete(String),
    List(Option<String>),
}

A String és Vec<u8> mindegyik felsorolt traitet implementálja, így a derive lefordul. PartialOrd-ot és Ord-ot szándékosan nem adunk, mert a parancsok között nincs természetes rendezés; a sorrend bevezetése félrevezető lenne a protokoll-feldolgozásban és a későbbi bővítéseknél.

12.2.10.4 d)

A f64 típus nem implementálja az Eq, Ord és Hash traiteket a NaN és az előjeles nulla problémái miatt, ezért a derive nem fordul le. Javítás: távolítsd el az Eq, Ord, Hash derive-okat, vagy ha szükség van teljes egyenlőségre és hash-re, tárold a biteket például u64-ben, és ott kezeld a kanonikus -0.0 problémát. A legegyszerűbb változat:

#[derive(Debug, Clone, PartialEq, PartialOrd)]
struct Celsius(f64);

12.2.11 Rövid összefoglaló

Az asszociált típus a trait részeként deklarált típusnév, amelyet az implementáló típus ad meg; a generikus paraméter helyett akkor használjuk, ha egy típushoz egyetlen kapcsolódó típus tartozik, mint az Iterator::Item esetében. Az orphan rule kimondja, hogy idegen traitet idegen típusra nem implementálhatunk; a megoldás a newtype, például struct WrappedVec(Vec<i32>). Az operátorok trait-ek: az Add asszociált Output típussal, az Index pánikkal, míg a PartialEq/Eq, PartialOrd/Ord és Hash a részleges/teljes szemantikát rögzítik. A #[derive(Debug, Clone, PartialEq, Eq, Hash, Default, PartialOrd, Ord)] mezőnkénti strukturális implementációt generál, ezért a mezőknek is teljesíteniük kell a megfelelő traiteket. A blanket impl-ek, mint az impl<T: Display> ToString for T, a koherencia szabályai mellett nyújtanak automatikus implementációkat. Továbbvitt eredmények: az Iterator::Item asszociált típus és a derive-készlet alapozza meg a(z) A standard trait-ek: konverziók, formázás, Default, Deref, Borrow, a(z) Iterátorok: lusta adapterek és saját iterátor, a(z) Vec, HashMap, BTreeMap és társaik; az Entry API, a(z) Deklaratív és procedurális makrók és a(z) Newtype, PhantomData, typestate és const generikusok alfejezeteket.

12.2.12 Források és ellenőrzési hiányok

A pontos hibaüzenetek szövege verziófüggő; a hibakódok (E0046, E0117) stabilak. A 2024-es edition elérhetősége az adott stable toolchainben ellenőrzendő. A lebegőpontos típusok Eq/Ord/Hash hiánya a Rust stabil szabálya.
