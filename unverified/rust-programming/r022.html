11.2 Saját hibatípusok: enum-hibák, thiserror, anyhow

11.2.1 Motiváció

C++-ban a hibakezelés gyakran kivételhierarchiákon alapul: std::runtime_error, std::ios_base::failure, saját store_error osztályok. A hívó fél számára azonban nem mindig világos, hogy egy függvény pontosan milyen kivételeket dobhat, és a catch blokkok sorrendje, illetve a catch (...) gyakran elfedi a hibák valódi típusát. Ha egy Store::load függvény fájlművelet közben std::ios_base::failure-t, rossz adatformátum esetén std::runtime_error-t dob, a hívó kód csak a what() szövegére hagyatkozhat, vagy bonyolult dynamic_cast vizsgálatokat írhat.

A Rust ezt a problémát a hibák típusként való modellezésével oldja meg: egy függvény Result<T, E>-t ad vissza, ahol E általában egy saját enum. A hívó match segítségével pontosan meg tudja különböztetni az egyes hibaeseteket, a fordító pedig ellenőrzi, hogy minden lehetséges variánst kezelünk-e. A ? operátorral a hibák automatikusan konvertálhatók a saját típusunkra, ha biztosítjuk a megfelelő From implementációkat. Ebben az alfejezetben megtervezzük az rkv könyvtár saját Error típusát, és bevezetjük az alkalmazásoldali anyhow-t a kontextusgazdag hibakezeléshez.

11.2.2 Fogalmak és szabályok

Definíció (hiba trait). A Rust standard könyvtárában a std::error::Error trait jelöli azokat a típusokat, amelyek hibaként használhatók. A trait két alapvető metódust ír elő: a Display-ből örökölt fmt-et az ember által olvasható leíráshoz, és a Debug-ot a diagnosztikai kiíráshoz. Ezen kívül opcionálisan felülírható a source() metódus, amely a hibát kiváltó alacsonyabb szintű hibát adja vissza, ha van ilyen.

Definíció (hibalánc, source-lánc). Ha egy magasabb szintű hiba egy alacsonyabb szintű hibát burkol be – például egy fájlműveleti hiba egy io::Error-t –, akkor a két hibát láncba fűzhetjük. A Rust Error trait source() metódusa ezt a láncot teszi bejárhatóvá: minden hiba visszaadhatja az őt kiváltó okot. A Display implementáció általában a közvetlen hibát írja le, a lánc további elemeit a leképező eszközök (pl. anyhow {:#} formázása) jelenítik meg.

Szabály (könyvtár vs. alkalmazás hibastratégiája). Könyvtári kódban saját, strukturált hibatípust (enum) használjunk, amely pontosan felsorolja a lehetséges hibaeseteket, és From implementációkkal támogatja a ? operátort. Alkalmazásban (CLI, szerver) gyakran elegendő az anyhow::Result<T> (vagy anyhow::Error), amely típuserázott hibákat kezel, és kontextust adhatunk hozzájuk. A kettő közötti határ a hívó fél szerződése: ha a hívónak programozottan kell döntenie a hibáról, használjunk enumot; ha csak emberi olvasásra és naplózásra kell, az anyhow praktikusabb.

Szabály (a ? operátor From-konverziója). A ? operátor egy Result<T, E> értéken meghívva a hiba esetén megkísérli a hibát From<E> for F segítségével konvertálni a környező függvény F hibatípusára. Ezért ha a hibatípusunkra implementáljuk a From<io::Error>-t, akkor a File::open(...)? kifejezés automatikusan a mi hibánkká alakítja az I/O hibát.

11.2.3 C++ ↔︎ Rust összevetés

Tekintsünk egy C++ függvényt, amely egy fájlból olvas be egy egész számot, és különböző hibákat dob:

#include <fstream>
#include <stdexcept>
#include <string>

class parse_error : public std::runtime_error {
public:
    explicit parse_error(const std::string& msg) : std::runtime_error(msg) {}
};

int load_count(const std::string& path) {
    std::ifstream file(path);
    if (!file.is_open()) {
        throw std::ios_base::failure("cannot open file");
    }
    int value = 0;
    file >> value;
    if (file.fail()) {
        throw parse_error("invalid integer");
    }
    return value;
}

A hívónak két különböző kivételt kell elkapnia, ráadásul ezek típusa nem derül ki a függvény szignatúrájából. A Rust megfelelője saját hibát enummal írja le:

use std::{fmt, fs, io, num::ParseIntError};

#[derive(Debug)]
enum LoadError {
    Io(io::Error),
    Parse(ParseIntError),
}

impl fmt::Display for LoadError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            LoadError::Io(e) => write!(f, "I/O hiba: {e}"),
            LoadError::Parse(e) => write!(f, "számformátum hiba: {e}"),
        }
    }
}

impl std::error::Error for LoadError {
    fn source(&self) -> Option<&(dyn std::error::Error + 'static)> {
        match self {
            LoadError::Io(e) => Some(e),
            LoadError::Parse(e) => Some(e),
        }
    }
}

fn load_count(path: &str) -> Result<i32, LoadError> {
    let content = fs::read_to_string(path)?;   // io::Error -> LoadError
    let value = content.trim().parse::<i32>()?; // ParseIntError -> LoadError
    Ok(value)
}

A ? operátor automatikusan konvertálja a hibákat, mert a LoadError implementálja a megfelelő From-okat. A hívó match-csel pontosan kezelheti a helyzetet. A fenti kézzel írt Display és Error implementáció azonban sok boilerplate; a thiserror derive ezt jelentősen lerövidíti, amint a laborban látni fogjuk.

11.2.4 Labor: az rkv Error típusa és anyhow a CLI-ben

Ebben a laborban létrehozzuk az rkv-core könyvtár saját hibatípusát a thiserror crate segítségével, és bevezetjük az anyhow-t a rkv-cli binárisban.

Munkakönyvtár: ~/rust-labor/rkv

11.2.4.1 1. lépés: Függőségek hozzáadása

Nyissuk meg az rkv-core/Cargo.toml fájlt, és vegyük fel a thiserror-t:

Ellenőrzési igény: a thiserror 2.x a jelenlegi főverzió; ha a környezetben 1.x érhető el, a példák kódja változatlanul működik (a derive attribútumok azonosak). A pontos API-t a docs.rs-en ellenőrizni kell.

Ezután adjuk hozzá az anyhow-t az rkv-cli/Cargo.toml-höz:

[dependencies]
clap = { version = "4", features = ["derive"] }
anyhow = "1"

11.2.4.2 2. lépés: Az rkv-core hibatípusa

Cseréljük le az rkv-core/src/error.rs tartalmát a következőre:

// rkv-core/src/error.rs
use std::io;
use thiserror::Error;

/// Az rkv tároló hibáinak típusa.
#[derive(Debug, Error)]
pub enum Error {
    /// Fájl- vagy egyéb I/O művelet hibája.
    #[error("I/O hiba: {0}")]
    Io(#[from] io::Error),

    /// A kért kulcs nem található a tárolóban.
    #[error("kulcs nem található: {0}")]
    KeyNotFound(String),

    /// Érvénytelen parancs vagy protokollüzenet.
    #[error("érvénytelen parancs: {0}")]
    InvalidCommand(String),
}

A #[derive(Error)] automatikusan implementálja a std::error::Error traitet, és a #[error("...")] attribútumok a Display-et. A #[from] attribútum az Io variánson generálja a From<io::Error> for Error implementációt, így a ? operátor közvetlenül használható minden io::Result<T>-t visszaadó hívásnál.

Ellenőrizzük, hogy a crate fordul-e:

cd ~/rust-labor/rkv
cargo check -p rkv-core

Várt kimenet: a fordító nem jelez hibát.

11.2.4.3 3. lépés: Kontextus az anyhow-val a CLI-ben

A rkv-cli/src/main.rs jelenleg a clap-pal feldolgozza a parancssort, de a parancsok még nincsenek megvalósítva. Módosítsuk úgy, hogy a main visszatérési típusa anyhow::Result<()> legyen, és a parancsvégrehajtás egyelőre todo!()-val jelezze a hiányzó funkciót. A hibához kontextust adunk, ha a tároló megnyitása később meghiúsul.

// rkv-cli/src/main.rs
use anyhow::{Context, Result};
use clap::{Parser, Subcommand};
use rkv_core::Error;

#[derive(Parser)]
#[command(name = "rkv-cli", version, about = "rkv parancssori kliens")]
struct Cli {
    #[command(subcommand)]
    command: Command,
}

#[derive(Subcommand)]
enum Command {
    /// Érték lekérdezése
    Get { key: String },
    /// Érték beállítása
    Set { key: String, value: String },
    /// Kulcs törlése
    Del { key: String },
    /// Kulcsok listázása
    List { prefix: Option<String> },
}

fn run(cli: Cli) -> Result<()> {
    match cli.command {
        Command::Get { key } => {
            println!("GET {key}");
            // Itt lesz a Store megnyitása és a get hívása a r023-ban.
            let _ = open_store().with_context(|| format!("tároló megnyitása a GET {key} parancshoz"))?;
            todo!("a tároló GET művelete a r023-as alfejezetben készül el");
        }
        Command::Set { key, value } => {
            println!("SET {key} {value}");
            let _ = open_store().with_context(|| format!("tároló megnyitása a SET {key} parancshoz"))?;
            todo!("a tároló SET művelete a r023-as alfejezetben készül el");
        }
        Command::Del { key } => {
            println!("DEL {key}");
            let _ = open_store().with_context(|| format!("tároló megnyitása a DEL {key} parancshoz"))?;
            todo!("a tároló DEL művelete a r023-as alfejezetben készül el");
        }
        Command::List { prefix } => {
            println!("LIST {}", prefix.as_deref().unwrap_or(""));
            let _ = open_store().with_context(|| "tároló megnyitása a LIST parancshoz")?;
            todo!("a tároló LIST művelete a r023-as alfejezetben készül el");
        }
    }
    Ok(())
}

fn open_store() -> Result<(), Error> {
    // A tényleges tároló-megnyitás a r023-ban készül; most csak a hibakonverziót mutatjuk.
    Ok(())
}

fn main() -> Result<()> {
    let cli = Cli::parse();
    run(cli)
}

A with_context (illetve a context) metódus az anyhow::Context traitből származik: ha a Result Err értéket tartalmaz, az anyhow::Error-hoz hozzáfűzi a megadott szöveges kontextust. A Rust-nak külön with_context változata van a lusta kiértékeléshez (a formázott hibaüzenet csak hiba esetén készül el). Figyeljük meg, hogy a run függvény anyhow::Result<()>-t ad vissza, a main pedig egyszerűen továbbadja ezt – ilyenkor a Rust a Debug formázással kiírja a hibát és a láncát, ha a program hibával lép ki.

A open_store függvény egyelőre Ok(())-t ad, de a visszatérési típusa Result<(), rkv_core::Error>. Ez lehetővé teszi, hogy a későbbi fejezetekben valódi I/O-t végezzünk, és a ? automatikusan a saját Error-rá konvertáljon.

11.2.4.4 4. lépés: Teszt a hibatípushoz

Adjunk egy egyszerű egységtesztet az rkv-core/src/lib.rs-be vagy az error.rs aljára, amely ellenőrzi a From<io::Error> konverziót és a Display-et:

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn io_error_converted_to_error() {
        let io_err = io::Error::new(io::ErrorKind::NotFound, "file not found");
        let err: Error = io_err.into();
        match err {
            Error::Io(_) => {}
            _ => panic!("nem Io variáns lett"),
        }
    }

    #[test]
    fn display_contains_message() {
        let err = Error::KeyNotFound("k1".into());
        let text = err.to_string();
        assert!(text.contains("kulcs nem található"));
        assert!(text.contains("k1"));
    }
}

Futtassuk a teszteket:

cargo test -p rkv-core

Várt kimenet: minden teszt sikeres.

Ez a labor létrehozta az Error típust az rkv-core/src/error.rs fájlban, és az anyhow-t a rkv-cli/src/main.rs-ben. A következő alfejezetben a tényleges fájl I/O-t és a szerializációt fogjuk hozzáadni, és ott a ? operátor automatikusan fogja használni a most definiált From<io::Error>-t.

11.2.5 Tipikus hibák és átállási csapdák

  1. unwrap/expect a könyvtárban. C++-ban megszokott, hogy hibás fájlműveletnél kivételt dobunk; Rustban a File::open(path).expect("nem nyitható") pánikot okoz a könyvtári kódban, ami a hívó alkalmazás összeomlásához vezet. Ehelyett minden felhasználói bemenettől függő műveletnek Result-ot kell visszaadnia, és a ? operátort kell használni. A pánik csak ténylegesen helyrehozhatatlan programozói hibánál elfogadható (pl. belső invariáns megsértése).

  2. anyhow használata könyvtári API-ban. Az anyhow::Error típuserázott, a hívó nem tud match-elni a konkrét hiba variánsokra. Ha egy könyvtár Result<T, anyhow::Error>-t ad vissza, a hívó kód elveszíti a típusbiztonságot, és nem tud programozottan döntést hozni. A könyvtárban mindig saját enumot használjunk; az alkalmazásban az anyhow már elfogadható, mert ott a hibák emberi fogyasztásra és naplózásra valók.

  3. Box<dyn Error> örökölt reflexe. C++-ban a std::exception polimorfikus hivatkozás a természetes; Rustban a Box<dyn Error> hasonló, de elveszíti a variánsok szerinti szétválasztást. Ehelyett enumot használjunk, amely lehetővé teszi a match-et, és a Forrást a source() láncban megőrzi.

  4. A forráslánc elvesztése kézi konverziónál. Ha a hibát map_err(|e| Error::Io(e))-val konvertáljuk, a source() lánc nem jön létre automatikusan, hacsak nem implementáljuk a source-ot kézzel. A thiserror #[from] attribútuma ezt megoldja: generálja a From implementációt és a source() metódust is.

11.2.6 Feladatok

11.2.6.1 a) Fogalmi kérdés

Egy könyvtár fejlesztője a következő függvényt írja:

fn load_config(path: &str) -> Result<String, Box<dyn std::error::Error>> {
    let content = std::fs::read_to_string(path)?;
    Ok(content)
}

Miért nem ideális ez a hibatípus egy olyan könyvtárban, ahol a hívónak meg kell különböztetnie a „fájl nem található” és a „JSON formátum hiba” eseteket? Hogyan lehetne jobbá tenni? Fogalmazd meg a választ a könyvtár vs. alkalmazás stratégia alapján.

11.2.6.2 b) C++-kód átírása idiomatikus Rustra

Adott a C++ függvény:

#include <stdexcept>
#include <fstream>

int read_seed(const std::string& path) {
    std::ifstream file(path);
    if (!file) throw std::runtime_error{"cannot open seed file"};
    int seed;
    file >> seed;
    if (file.fail()) throw std::runtime_error{"invalid seed format"};
    return seed;
}

Írd át Rustra a laborban bemutatott Error enum mintájára: hozz létre egy SeedError enumot a thiserror használatával, amely io::Error-t és ParseIntError-t tud burkolni, majd írd meg a read_seed függvényt Result<i32, SeedError> visszatéréssel. Használd a ? operátort.

11.2.6.3 c) Implementációs feladat az rkv-ban

Bővítsd az rkv-core Error enumját egy Serialization variánssal, amely serde_json::Error-t fogad be #[from]-mal. Ehhez vedd fel a serde_json = "1" függőséget az rkv-core/Cargo.toml-be. Írj egy függvényt parse_record(data: &str) -> Result<(), Error> néven, amely a serde_json::from_str::<serde_json::Value>(data)? kifejezést használja, és sikeres parse esetén Ok(())-t ad. Futtasd a teszteket.

11.2.6.4 d) Hibajavítás és refaktorálás

Tekintsd a következő Rust kódot:

fn process_file(path: &str) -> Result<(), Box<dyn std::error::Error>> {
    let data = std::fs::read_to_string(path)?;
    let value: i32 = data.trim().parse()?;
    println!("{value}");
    Ok(())
}

Refaktoráld a process_file függvényt úgy, hogy a laborban definiált rkv_core::Error-t használja, és adj hozzá kontextust az anyhow segítségével egy CLI-hívásban: ha a fájl nem nyitható, a hibaüzenet tartalmazza a fájl elérési útját. (Tipp: a process_file-t hívó kód anyhow::Result<()>-t adjon vissza, és használja a with_context metódust.)

11.2.7 Megoldások

11.2.7.1 a) Megoldás

A Box<dyn Error> típuserázott: a hívó nem tudja, hogy a hibát io::Error vagy serde_json::Error okozta-e. A match nem tud különbséget tenni, csak a source() láncot tudja bejárni, ami körülményes. Könyvtárban saját enumot kell használni, például:

#[derive(Debug, thiserror::Error)]
pub enum ConfigError {
    #[error("I/O hiba: {0}")]
    Io(#[from] std::io::Error),
    #[error("JSON hiba: {0}")]
    Json(#[from] serde_json::Error),
}

A hívó így match-csel pontosan kezelheti a variánsokat. Az anyhow::Error csak alkalmazásban ajánlott, ahol nincs szükség programozott döntésre.

11.2.7.2 b) Megoldás

use std::{fs, io, num::ParseIntError};
use thiserror::Error;

#[derive(Debug, Error)]
enum SeedError {
    #[error("I/O hiba a seed fájlnál: {0}")]
    Io(#[from] io::Error),

    #[error("érvénytelen seed formátum: {0}")]
    Parse(#[from] ParseIntError),
}

fn read_seed(path: &str) -> Result<i32, SeedError> {
    let content = fs::read_to_string(path)?;
    let seed = content.trim().parse::<i32>()?;
    Ok(seed)
}

A ? operátor automatikusan konvertálja az io::Error-t és a ParseIntError-t a SeedError megfelelő variánsaira a generált From-ok révén.

11.2.7.3 c) Megoldás

Az rkv-core/Cargo.toml:

[dependencies]
thiserror = "2"
serde_json = "1"

Az rkv-core/src/error.rs frissített változata:

use std::io;
use thiserror::Error;

#[derive(Debug, Error)]
pub enum Error {
    #[error("I/O hiba: {0}")]
    Io(#[from] io::Error),

    #[error("kulcs nem található: {0}")]
    KeyNotFound(String),

    #[error("érvénytelen parancs: {0}")]
    InvalidCommand(String),

    #[error("szerializációs hiba: {0}")]
    Serialization(#[from] serde_json::Error),
}

A parse_record függvény az rkv-core/src/lib.rs-ben vagy egy új modulban:

pub fn parse_record(data: &str) -> Result<(), Error> {
    // A `?` automatikusan Error::Serialization-vá alakítja a serde_json hibát.
    let _: serde_json::Value = serde_json::from_str(data)?;
    Ok(())
}

A cargo test -p rkv-core lefuttatása után minden tesztnek sikeresnek kell lennie.

11.2.7.4 d) Megoldás

A könyvtári függvény saját hibával:

// rkv-core/src/lib.rs (vagy egy megfelelő modulban)
pub fn process_file(path: &str) -> Result<(), Error> {
    let data = std::fs::read_to_string(path)?;
    let value: i32 = data.trim().parse().map_err(|_| Error::InvalidCommand("nem szám".into()))?;
    println!("{value}");
    Ok(())
}

A parse hiba ParseIntError, amit egyelőre InvalidCommand-ra képezünk le, mert az Error-ban nincs parse variáns. (A későbbi fejezetekben ezt finomíthatjuk.)

A CLI-ben:

use anyhow::Context;
use rkv_core::process_file;

fn main() -> anyhow::Result<()> {
    let path = "/tmp/rkv-seed.txt";
    process_file(path).with_context(|| format!("fájl feldolgozása: {path}"))?;
    Ok(())
}

Ha a fájl nem nyitható, az anyhow a láncban megőrzi az eredeti rkv_core::Error-t, és a kiíráskor a kontextus is megjelenik.

11.2.8 Rövid összefoglaló

Az rkv könyvtár saját hibatípusa az rkv_core::Error enum, amelyet a thiserror derive-tal definiáltunk az rkv-core/src/error.rs fájlban. A variánsok: Io(#[from] io::Error), KeyNotFound(String), InvalidCommand(String), és a feladatban hozzáadott Serialization(#[from] serde_json::Error). A #[from] attribútumok generálják a From implementációkat, így a ? operátor automatikusan konvertálja az alacsonyabb szintű hibákat, és a source() lánc is megmarad. A rkv-cli binárisban bevezettük az anyhow::Result-et és a with_context metódust, hogy a hibákhoz emberi olvasásra szánt kontextust adjunk. A könyvtár és az alkalmazás közötti határ: könyvtárban strukturált enum, alkalmazásban anyhow a rugalmasságért. Továbbvitt eredmény: az Error típus a későbbi fejezetekben a tényleges I/O-műveletek, a Storage trait, a hálózati szerver és az FFI hibakezelésének alapja.

11.2.9 Források és ellenőrzési hiányok

  • A std::error::Error trait és a From konverziók a Rust standard könyvtár stabil részei; a pontos metódus-szignatúrák a hivatalos dokumentációban ellenőrizhetők.
  • A thiserror és az anyhow crate-ek API-ja a docs.rs-en érhető el: https://docs.rs/thiserror/, https://docs.rs/anyhow/. A fenti példák a 2.x (thiserror) és 1.x (anyhow) főverziókra épülnek; a pontos verziók és attrribútumok a telepített környezettől függően ellenőrizendők.
  • A cargo check, cargo test parancsok kimenete a nightly/stable toolchain verziójától függ; a bemutatott „nincs hiba” várt kimenet általános, de a figyelmeztetések szövege eltérhet.
  • A laborban használt todo!() makró a későbbi alfejezetekben valós implementációra cserélendő; a jelen alfejezetben a hibaterjedés szerkezetét demonstrálja.
