19.2 C++-együttműködés a cxx crate-tel és a fokozatos migráció

19.2.1 Motiváció: a C ABI alacsony szintű, a cxx biztonságos hidat épít

Az előző alfejezetben (C ABI: extern “C”, repr(C), bindgen és cbindgen) láttuk, hogy a Rust és C/C++ közötti átjárás a C ABI-n keresztül kézzel írt, unsafe blokkokkal tűzdelt, hibalehetőségekkel terhelt kódot jelent. A mutatók átadása, a stringek és vektorok kézi konvertálása, a hibakezelés errno vagy saját hibakódok formájában mind fokozott figyelmet igényel. Ráadásul a C++ osztályok, kivételek, std::string és std::unique_ptr közvetlenül nem férnek hozzá a Rust oldalról.

A cxx crate ezt a problémát oldja meg azzal, hogy biztonságos, típusos C++-hidat generál. A #[cxx::bridge] modulban deklaráljuk a C++ és Rust közötti interfészt, és a cxx-build eszköz legenerálja mindkét oldal wrapper kódját. Ennek köszönhetően a gyakori típusok (std::string, std::vector, std::unique_ptr, Rust String, Vec, Box) automatikusan konvertálódnak, a C++ kivételek Rust Result-tá alakulnak, a Rust Result pedig C++ kivétellé. A híd használata a támogatott típusok körében nem igényel unsafe-et.

Továbbvitt eredmény. Az itt elkészített C++-integrációt a Záróprojekt: az rkv teljes rendszerként alfejezet használja fel, ahol a C++-kliens a Rust tárolóval együttműködve mutatja be a fokozatos migráció eredményét.

19.2.2 Fogalmak és szabályok

Definíció. A #[cxx::bridge] egy olyan modul, amely a Rust és C++ közötti interfészt írja le. A modul belsejében extern "Rust" blokkban a Rust oldalon implementált, C++-ból hívható függvényeket és típusokat deklaráljuk; extern "C++" blokkban pedig a C++ oldalon definiált, Rustból hívható elemeket. A cxx-build crate a bridge modul alapján generálja a szükséges C++ és Rust wrapper kódot.

Szabály. A cxx bridge-ben csak a crate által támogatott típusok használhatók. Ilyenek többek között: - Rust oldalon: String, &str, Vec<T>, &[T], Box<T>, Result<T, E>, UniquePtr<T>, SharedPtr<T>; - C++ oldalon: std::string, std::vector<T>, std::unique_ptr<T>, std::shared_ptr<T>, rust::String, rust::Str, rust::Vec<T>, rust::Box<T>, rust::Error. A nem támogatott típusoknál a generált kód fordítási hibát ad.

Kivétel ↔︎ Result. A cxx automatikusan kezeli a hibák átalakítását: - Ha egy Rust függvény Result<T, E>-t ad vissza (ahol E implementálja a std::fmt::Display trait-et), akkor a C++ oldalon a függvény T-t ad vissza, és hiba esetén rust::Error kivételt dob. A C++ kód try/catch blokkal kezelheti. - Ha egy C++ függvény a bridge-ben Result<T, E> visszatéréssel van deklarálva, akkor a C++ implementáció T-t ad vissza, és hiba esetén E típusú kivételt dobhat; a generált wrapper ezt Err-ré alakítja a Rust oldalon.

19.2.3 C++ ↔︎ Rust összevetés

A cxx előnye a kézzel írt C ABI-val szemben szembetűnő. Hasonlítsuk össze egy stringet visszaadó függvényt.

C ABI (C ABI: extern “C”, repr(C), bindgen és cbindgen alfejezetből):

// C++ oldal
extern "C" {
    char* rkv_get(const char* key); // hívó felel a free()-ért
}
// Rust oldal
#[no_mangle]
pub unsafe extern "C" fn rkv_get(key: *const c_char) -> *mut c_char {
    // kézi CString konverzió, memóriakezelés, unsafe
}

cxx-szel:

#[cxx::bridge]
mod ffi {
    extern "Rust" {
        fn rkv_get(key: &str) -> Result<String, String>;
    }
}
// C++ oldal
std::string value = rkv_get("key"); // automatikus konverzió, kivételkezelés

A különbség: a cxx generálja a konverziós és memóriakezelési kódot, a típusok ellenőrzöttek, és a hívó nem férhet rossz mutatóhoz. A Rust oldalon nincs unsafe.

19.2.4 Kidolgozott példa: C++ osztály használata Rustból

A cxx nemcsak C++-ból Rust hívását teszi lehetővé, hanem fordítva is. Tegyük fel, hogy van egy meglévő C++ Logger osztályunk:

// logger.h
#pragma once
#include <string>

class Logger {
public:
    void log(const std::string& message);
};

A Rust oldalról szeretnénk naplózni. A #[cxx::bridge] modulban deklaráljuk az osztályt és a metódust:

// src/lib.rs
#[cxx::bridge]
mod ffi {
    unsafe extern "C++" {
        include!("rkv-cxx/include/logger.h");

        type Logger;

        fn log(self: &Logger, message: &str);
    }
}

A cxx-build generál egy Rust Logger típust, amely egy C++ std::unique_ptr<Logger>-t burkol. A C++ oldali implementációt a build rendszerben le kell fordítani. A Rust oldalon a Logger példányt a UniquePtr kezelésével kapjuk meg, és a metódust biztonságosan hívhatjuk:

fn do_something(logger: &ffi::Logger) {
    logger.log("Hello from Rust");
}

A unsafe extern "C++" blokk jelzi, hogy a deklarált C++ típusok és függvények tényleges létezését a programozó garantálja; a hívás maga azonban biztonságos, mert a generált wrapper ellenőrzi a típusokat és élettartamokat.

19.2.5 Labor: C++ CLI, amely az rkv-t használja cxx-szel

Munkakönyvtár: ~/rust-labor/rkv/

Ebben a laborban létrehozunk egy rkv-cxx crate-et, amely cxx-híddal teszi elérhetővé az rkv tároló alapműveleteit C++-ból. A C++ oldalon egy parancssori eszközt (cpp-client) készítünk, amely a SET, GET, DEL és LIST parancsokat hajtja végre.

19.2.5.1 1. lépés: az rkv-cxx crate létrehozása

A workspace gyökerében adjuk hozzá az új crate-et:

cargo new --lib rkv-cxx

A Cargo.toml-ba:

[package]
name = "rkv-cxx"
version = "0.1.0"
edition = "2024"

[dependencies]
cxx = "1"
rkv-core = { path = "../rkv-core" }

[build-dependencies]
cxx-build = "1"

19.2.5.2 2. lépés: a bridge modul és a Rust implementáció

A src/lib.rs tartalma:

use std::sync::{Mutex, OnceLock};
use rkv_core::{MemStore, Store};

#[cxx::bridge]
mod ffi {
    extern "Rust" {
        fn rkv_set(key: String, value: Vec<u8>) -> Result<(), String>;
        fn rkv_get(key: &str) -> Result<Vec<u8>, String>;
        fn rkv_del(key: &str) -> Result<(), String>;
        fn rkv_list(prefix: &str) -> Result<Vec<String>, String>;
    }
}

struct GlobalStore(Mutex<Store<MemStore>>);

static STORE: OnceLock<GlobalStore> = OnceLock::new();

fn store() -> &'static GlobalStore {
    STORE.get_or_init(|| GlobalStore(Mutex::new(Store::new(MemStore::default()))))
}

fn rkv_set(key: String, value: Vec<u8>) -> Result<(), String> {
    let mut store = store().0.lock().map_err(|e| e.to_string())?;
    store.set(key, value).map_err(|e| e.to_string())
}

fn rkv_get(key: &str) -> Result<Vec<u8>, String> {
    let store = store().0.lock().map_err(|e| e.to_string())?;
    store.get(key).map_err(|e| e.to_string())
}

fn rkv_del(key: &str) -> Result<(), String> {
    let mut store = store().0.lock().map_err(|e| e.to_string())?;
    store.delete(key).map_err(|e| e.to_string())
}

fn rkv_list(prefix: &str) -> Result<Vec<String>, String> {
    let store = store().0.lock().map_err(|e| e.to_string())?;
    store.list(prefix).map_err(|e| e.to_string())
}

Itt feltételezzük, hogy a Store a korábbi alfejezetekben definiált generikus típus, és a MemStore egy memóriaalapú implementáció. A set, get, delete, list metódusok Result-ot adnak vissza. A pontos szignatúrákat a Structok és metódusok: impl blokkok, asszociált függvények alfejezet rögzítette; ha eltérnek, igazítsd a kódot.

19.2.5.3 3. lépés: a build.rs

A rkv-cxx/build.rs:

fn main() {
    cxx_build::bridge("src/lib.rs")
        .file("src/lib.rs")
        .flag_if_supported("-std=c++20")
        .compile("rkv-cxx");
}

Ez a Rust build során lefordítja a C++ oldali wrapper kódot, és a staticlib részévé teszi.

19.2.5.4 4. lépés: a C++ CLI

A cpp-client/main.cpp:

#include "rkv-cxx/src/lib.rs.h"
#include <iostream>
#include <string>
#include <vector>

void usage() {
    std::cerr << "Használat: cpp-client <SET key value | GET key | DEL key | LIST [prefix]>\n";
}

int main(int argc, char** argv) {
    if (argc < 2) {
        usage();
        return 1;
    }
    std::string cmd = argv[1];
    try {
        if (cmd == "SET" && argc == 4) {
            std::string key = argv[2];
            std::string value = argv[3];
            std::vector<uint8_t> bytes(value.begin(), value.end());
            rkv_set(key, bytes);
            std::cout << "OK\n";
        } else if (cmd == "GET" && argc == 3) {
            auto value = rkv_get(argv[2]);
            std::string s(value.begin(), value.end());
            std::cout << "VALUE " << s << "\n";
        } else if (cmd == "DEL" && argc == 3) {
            rkv_del(argv[2]);
            std::cout << "OK\n";
        } else if (cmd == "LIST" && (argc == 2 || argc == 3)) {
            std::string prefix = argc == 3 ? argv[2] : "";
            auto keys = rkv_list(prefix);
            for (const auto& k : keys) {
                std::cout << k << "\n";
            }
        } else {
            usage();
            return 2;
        }
    } catch (const rust::Error& e) {
        std::cerr << "ERR " << e.what() << "\n";
        return 3;
    }
    return 0;
}

A generált header (rkv-cxx/src/lib.rs.h) elérési útja a cxx-build konfigurációjától függ; a pontos útvonalat a target/cxxbridge/ könyvtárban kell ellenőrizni.

19.2.5.5 5. lépés: build és futtatás

Először buildeljük a Rust crate-et:

cargo build -p rkv-cxx --release

Ezután fordítsuk a C++ CLI-t. A pontos include és library elérési utakat a generált fájlok alapján kell megadni (ellenőrzési igény):

g++ -std=c++20 -I target/cxxbridge -I $(rustc --print sysroot)/lib/rustlib/src/rust/library \
    cpp-client/main.cpp -L target/release -lrkv_cxx -lpthread -ldl -o cpp-client/cpp-cli

Futtassuk:

./cpp-client/cpp-cli SET name "Rust"
./cpp-client/cpp-cli GET name
./cpp-client/cpp-cli LIST ""
./cpp-client/cpp-cli GET unknown

Várt kimenet:

OK
VALUE Rust
name
ERR Key not found

19.2.6 Build-integráció: CMake + Cargo

A laborban kézzel fordítottuk a C++ oldalt, de valódi projektben érdemes a build rendszert integrálni. A corrosion egy CMake-modul, amely lehetővé teszi Cargo crate-ek beillesztését a CMake buildbe: a CMake meghívja a Cargo-t, és a generált staticlib-et automatikusan linkeli. A használata körülbelül így néz ki (a pontos API-t ellenőrizni kell):

# CMakeLists.txt (vázlat, ellenőrzési igénnyel)
find_package(Corrosion REQUIRED)
corrosion_import_crate(MANIFEST_PATH ../rkv-cxx/Cargo.toml)
add_executable(cpp-client main.cpp)
target_link_libraries(cpp-client PUBLIC rkv-cxx)

A corrosion előnye, hogy a Cargo által kezelt függőségek és feature-ök automatikusan beépülnek a CMake targetekbe, így a C++ és Rust oldal egyetlen build paranccsal fordítható. A pontos konfigurációt a corrosion dokumentációjában kell ellenőrizni.

19.2.7 Migrációs stratégia: perem-modulok, új kód Rustban, tesztlefedettség

A cxx ideális eszköz egy meglévő C++-kódbázis fokozatos Rustra migrálásához. A stratégia lépései:

  1. Perem-modulok azonosítása. Keressük meg azokat a modulokat, amelyek jól elkülöníthetők, és interfészük stabil. Ilyen például az rkv esetében a tárolóréteg, a parancsértelmezés vagy a naplózás.
  2. Új kód Rustban. A kiválasztott modult Rustban újraimplementáljuk, és a cxx bridge-en keresztül tesszük elérhetővé a C++ oldal számára. A régi C++ hívások változatlanul működnek, mert a bridge ugyanazt az interfészt nyújtja.
  3. Tesztlefedettség megőrzése. A meglévő C++ unit teszteket változatlanul futtatjuk a cxx hídon keresztül, így azonnal észleljük a viselkedésbeli eltéréseket. Emellett a Rust oldalon is írunk teszteket (lásd Unit-, integrációs és dokumentációs tesztek).
  4. Fokozatos csere. Miután egy modul stabilan működik Rustban, a C++ implementációt eltávolíthatjuk, vagy a hívókat átirányíthatjuk közvetlenül a Rust API-ra. A cxx lehetővé teszi, hogy a C++ oldal std::unique_ptr-t, std::string-et és más típusokat kapjon, így a migráció nem igényel nagy átírásokat.
  5. Határ felügyelete. A határon átívelő típusokat érdemes egyszerű, stabil formában tartani, hogy a bridge karbantartása minimális legyen.

19.2.8 Teljesítmény a határon

A cxx híd teljesítménye általában közel van a kézzel írt C ABI-hoz, mert a generált kód nem végez felesleges másolást a megosztott típusoknál. A rust::Vec<T> és rust::String a Rust oldali memóriát látják, így a C++ oldal közvetlenül olvashatja, módosíthatja őket. A Box<T> és std::unique_ptr mozgatással adódnak át, nem történik mély másolás.

A határon való átlépés azonban nem inlinelhető, és minden hívás függvényhívási költséggel jár. A kivételek (rust::Error) dobása és elkapása szintén drágább, mint a hibakód visszaadása, ezért a gyakori hibákat (pl. „key not found”) érdemes Result-tal kezelni, és csak a váratlan esetekre hagyni a kivételt. A teljesítményt mindig mérni kell; a cxx önmagában nem jelent észrevehető overheadet a tipikus parancs-válasz forgatókönyvekben.

19.2.9 Tipikus hibák és átállási csapdák

  1. A generált header include útvonalának elfelejtése. A cxx-build a generált headert a target/cxxbridge/ könyvtárba teszi, de a points elérési út a crate nevétől és a modul helyétől függ. Ha a C++ oldal nem találja a headert, ellenőrizd a build rendszer include path-ját, és a cxx dokumentációjában a pontos elnevezést.
  2. A kivételkezelés elhanyagolása a C++ oldalon. Ha a Rust függvény Result-ot ad vissza, a C++ hívás rust::Error kivételt dobhat. Ha nincs try/catch, a program terminál. A C++ oldalon mindig kezeljük a kivételt, vagy tervezzük meg, hogy a hiba ne érje el a határt.
  3. Nem támogatott típus használata a bridge-ben. A cxx csak a dokumentált típusokat támogatja. Ha például egy saját Rust structot akarunk átadni, azt a cxx nem tudja automatikusan leképezni; ilyenkor a C ABI-s megoldás vagy a típus kézi konvertálása szükséges.
  4. Az élettartamok figyelmen kívül hagyása. A &str és &[T] a bridge-ben csak addig érvényes, amíg a mögöttes adat él. A C++ oldalon a rust::Str vagy rust::Slice nem tárolható el a függvényhíváson túl anélkül, hogy a Rust oldali adatot is életben tartanánk.

19.2.10 Feladatok

19.2.10.1 1. feladat (fogalmi kérdés)

Lefordul-e az alábbi bridge modul? Ha nem, miért?

#[cxx::bridge]
mod ffi {
    extern "Rust" {
        fn get_data() -> Result<Vec<u8>, MyError>;
    }
}

#[derive(Debug)]
struct MyError;
impl std::fmt::Display for MyError {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        write!(f, "MyError")
    }
}

19.2.10.2 2. feladat (C++ kód átírása)

Írd át az alábbi C ABI-s Rust függvényt cxx bridge-re. A függvény egy stringet kap, és egy stringet ad vissza, hiba esetén nullptr-t.

#[no_mangle]
pub unsafe extern "C" fn reverse(s: *const c_char) -> *mut c_char {
    // ...
}

19.2.10.3 3. feladat (implementációs feladat)

Bővítsd az rkv-cxx crate-et egy rkv_count() függvénnyel, amely visszaadja a tárolóban lévő kulcsok számát. Add hozzá a bridge-hez, implementáld a Rust oldalon, és egészítsd ki a C++ CLI-t COUNT paranccsal.

19.2.10.4 4. feladat (refaktorálás)

A C++ CLI jelenleg közvetlenül a bridge függvényeket hívja. Refaktoráld úgy, hogy a parancsértelmezés és a tárolóműveletek külön modulba kerüljenek a Rust oldalon: hozz létre egy rkv_ops modult, amely a globális Store-t kezeli, és a bridge függvények csak delegáljanak. Ez a szétválasztás előkészíti a Záróprojekt tesztelhetőségét.

19.2.11 Megoldások

19.2.11.1 1. feladat megoldása

Nem fordul le, mert a cxx a Result hibájának típusát (MyError) nem tudja C++ kivétté alakítani, mivel nem szerepel a támogatott típusok között, és a bridge-ben a hibát át kell konvertálni String-gé. A javítás: Result<Vec<u8>, String>.

#[cxx::bridge]
mod ffi {
    extern "Rust" {
        fn get_data() -> Result<Vec<u8>, String>;
    }
}

fn get_data() -> Result<Vec<u8>, String> {
    Err("MyError".to_string())
}

19.2.11.2 2. feladat megoldása

#[cxx::bridge]
mod ffi {
    extern "Rust" {
        fn reverse(s: &str) -> Result<String, String>;
    }
}

fn reverse(s: &str) -> Result<String, String> {
    Ok(s.chars().rev().collect())
}

A C++ oldalon a függvény std::string-et ad vissza, és hiba esetén rust::Error kivételt dob.

19.2.11.3 3. feladat megoldása

A bridge bővítése:

extern "Rust" {
    fn rkv_count() -> Result<usize, String>;
}

Implementáció:

fn rkv_count() -> Result<usize, String> {
    let store = store().0.lock().map_err(|e| e.to_string())?;
    Ok(store.len())
}

A C++ CLI-ben:

} else if (cmd == "COUNT" && argc == 2) {
    auto count = rkv_count();
    std::cout << count << "\n";
}

19.2.11.4 4. feladat megoldása

Hozz létre egy ops modult a lib.rs-ben:

mod ops {
    use super::*;
    use std::sync::Mutex;
    use rkv_core::{MemStore, Store};

    pub struct GlobalStore(Mutex<Store<MemStore>>);
    static STORE: OnceLock<GlobalStore> = OnceLock::new();

    pub fn store() -> &'static GlobalStore {
        STORE.get_or_init(|| GlobalStore(Mutex::new(Store::new(MemStore::default()))))
    }
}

A bridge függvények ezután az ops::store()-t használják. A rkv_set, rkv_get, rkv_del, rkv_list, rkv_count függvények a modulban definiált segédfüggvényekre delegálnak, amelyek a Result-ot String hibává alakítják.

19.2.12 Rövid összefoglaló

A cxx crate biztonságos, típusos hidat generál Rust és C++ között. A #[cxx::bridge] modulban extern "Rust" és extern "C++" blokkokkal deklaráljuk a határon átívelő függvényeket és típusokat; a cxx-build legenerálja a wrapper kódot. A megosztott típusok (String, Vec, Box, UniquePtr, stb.) automatikusan konvertálódnak, a Rust Result C++ rust::Error kivétellé, a C++ kivétel Rust Err-ré alakul. A labor létrehozta az rkv-cxx crate-et a workspace-ben, amely a Store<MemStore>-t teszi elérhetővé C++-ból; a cpp-client/main.cpp egy parancssori CLI, amely a SET, GET, DEL, LIST és COUNT parancsokat hajtja végre. A build-integrációhoz a corrosion ajánlott. A migrációs stratégia perem-modulok cseréjére épül, megőrizve a C++ teszteket. Továbbvitt eredmény: a C++-integráció a Záróprojekt: az rkv teljes rendszerként záróprojektben teljes rendszerként működik együtt a Rust tárolóval.

19.2.13 Források és ellenőrzési hiányok

  • A cxx crate pontos API-ja, a támogatott típusok listája és a generált header elérési útja a docs.rs-en ellenőrizendő.
  • A corrosion CMake-integráció pontos szintaxisa a projekt dokumentációjában ellenőrizendő; a példa vázlatos.
  • A cxx-build által generált fájlok elnevezése és az include! útvonalak a crate verziójától függően változhatnak.
