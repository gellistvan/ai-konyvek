17.4 Az rkv hálózati szerver: TCP, protokoll, kecses leállás

17.4.1 Motiváció

Egy C++-ban írt TCP-szerver tipikusan a következő mintát követi: egy accept ciklus, minden kapcsolatnak egy std::thread, és egy osztott, mutexszel védett állapot. A kecses leállás (graceful shutdown) azonban gyakran utólag kerül be, és ilyenkor jönnek a jellegzetes hibák: a szálak nem tudnak egy atomi bool leállítási flagre időben reagálni, a join a blokkoló recv miatt lefagy, a nyitott kapcsolatokra nem lehet hatni. A Rust async modellben a leállítás is elsőrendű állampolgár: a futó feladatok (taskok) megszakíthatók, ahelyett hogy egy blokkoló hívásban ragadnának. Ebben az alfejezetben az rkv-hoz építünk egy tokio-alapú TCP-szervert, amely soronkénti szöveges protokollt beszél, és graceful shutdownnal áll le: új kapcsolatokat nem fogad, a folyamatban lévő parancsokat befejezi, és a klienseket hagyja kilépni.

17.4.2 Fogalmak és szabályok

Definíció. A keretezés (framing) az a szabály, amely meghatározza, hol kezdődik és végződik egy üzenet egy bájtfolyamban. A mi szerverünknél a keretezés egy sor vége (\n): minden parancs egyetlen sorból áll, a válasz is soronkénti (a LIST kivételével, ahol több VALUE sor és egy záró OK sor érkezik).

Definíció. A kecses leállás (graceful shutdown) olyan leállítási folyamat, amely során a szerver nem szakítja meg azonnal az aktív kapcsolatokat, hanem: (1) leállítja az új kapcsolatok fogadását, (2) jelzi a klienseknek, hogy a folyamatban lévő művelet befejezése után lépjenek ki, és (3) megvárja a futó taskok befejeződését.

Szabály. Ha egy MutexGuard-ot .await ponton át tartunk, a kritikus szakasz akár tetszőlegesen hosszú ideig zárva maradhat, ami csökkenti az áteresztőképességet, és Mutex-függő holtversenyt okozhat. Async kódban a zárat csak rövid, nem .await-elő szakaszra szerezhetjük meg, és a .await előtt el kell engednünk.

A tokio két választ ad a megosztott állapotra: a std::sync::Mutex (vagy RwLock) és a tokio::sync::Mutex. A hálózati szerverben a tárolóművelet nem blokkol (memóriában vagy gyors fájlművelet), ezért a std-változat elegendő; a tokio::sync::Mutex akkor jön jól, ha a védett szakasz maga is .await-el.

Definíció. A tokio_util::sync::CancellationToken egy olyan jelzés, amelyet cancel() hívással lehet bekapcsolni, és a váró taskok .cancelled()-re ébrednek. Jól használható a leállítási jel terjesztésére: minden task kap egy klónt, és select!-ben versenyezteti a normál eseménnyel.

17.4.3 C++ ↔︎ Rust összevetés

Egy C++ szerver vázlata szálakkal és leállítási flaggel:

#include <atomic>
#include <iostream>
#include <thread>
#include <vector>
#include <sys/socket.h>
#include <netinet/in.h>

std::atomic<bool> stop{false};

void handle_client(int fd) {
    char buf[1024];
    while (!stop) {
        ssize_t n = recv(fd, buf, sizeof(buf), 0);
        if (n <= 0) break;
        // feldolgozás...
    }
    close(fd);
}

int main() {
    int listener = socket(AF_INET, SOCK_STREAM, 0);
    // bind, listen...
    std::vector<std::thread> threads;
    while (!stop) {
        int fd = accept(listener, nullptr, nullptr);
        threads.emplace_back(handle_client, fd);
    }
    // leállítás: stop = true; majd join...
}

A probléma: ha a kliens nem küld adatot, a recv blokkol, és a stop flaget soha nem veszi észre; a join a blokkoló szálon függ. Ezt jellemzően poll-lal, shutdown hívással vagy timeouttal kell megkerülni. A Rust/tokio szerver ehelyett select!-ben figyeli a megszakítást, és a task kilép a futó .await-ből akkor is, ha épp sorra várt.

A Rust szerver fő hurka:

use std::sync::{Arc, Mutex};
use tokio::net::TcpListener;
use tokio_util::sync::CancellationToken;
use rkv_core::{Storage, MemStore};

async fn run_server(listener: TcpListener, store: Arc<Mutex<dyn Storage>>, token: CancellationToken) {
    loop {
        tokio::select! {
            _ = token.cancelled() => break,
            res = listener.accept() => {
                let (socket, addr) = match res {
                    Ok(v) => v,
                    Err(e) => { eprintln!("accept error: {e}"); continue; }
                };
                let store = Arc::clone(&store);
                let token = token.clone();
                tokio::spawn(async move {
                    if let Err(e) = handle_client(socket, store, token).await {
                        eprintln!("client {addr}: {e}");
                    }
                });
            }
        }
    }
}

A különbség: a select! a listner accept és a leállítási token között választ; ha a token megszakad, a ciklus kilép anélkül, hogy új kapcsolatot fogadna. A futó klienstaskokat nem öljük meg, hanem ők is figyelik a saját tokenjüket, ahogy az alábbi laborban látni fogjuk.

17.4.4 A protokoll és a válaszformátum

Az rkv-szerver protokollja soralapú. A kliens egyetlen sora egy parancsot tartalmaz:

GET <kulcs>
SET <kulcs> <érték>
DEL <kulcs>
LIST [<prefix>]

A szerver válaszai:

OK                  – SET és DEL sikeres; LIST lezáró sora
VALUE <kulcs> <érték>  – GET találat vagy LIST elem
NOTFOUND            – GET/DEL nem létező kulcs esetén
ERR <üzenet>        – hibás parancs vagy belső hiba

A LIST válasza: minden egyező kulcshoz egy-egy VALUE sor, majd egy OK sor. Egy munkamenet nc-vel:

$ nc localhost 8080
SET hello world
OK
GET hello
VALUE hello world
LIST he
VALUE hello world
OK
DEL hello
OK
GET hello
NOTFOUND

A sorokban a kulcs és az érték nem tartalmazhat szóközt, mert a protokollt szóközökkel tagoljuk; a parsert az rkv-core Tokenizer típusa valósítja meg, és a Command::parse visszaadja a Command enumot.

17.4.5 Keretezés: BufReader::lines

A bejövő adatfolyam bájtok sorozata. A tokio::io::BufReader belső puffert tart, és a .lines() metódus egy AsyncBufReadExt-traiten keresztül egyszerre egy sort ad vissza. A next_line() egy Future, amely a \n karakterig tartó szakaszt várja; így a TCP-ből folyamatosan olvashatunk, nem kell magunk pufferezni.

A klienst kezelő függvény eleje:

use tokio::net::TcpStream;
use tokio::io::{BufReader, AsyncBufReadExt, AsyncWriteExt, BufWriter};

async fn handle_client(socket: TcpStream, store: Arc<Mutex<dyn Storage>>, token: CancellationToken)
    -> anyhow::Result<()>
{
    let (read_half, write_half) = socket.into_split();
    let mut lines = BufReader::new(read_half).lines();
    let mut writer = BufWriter::new(write_half);

    loop {
        let line = tokio::select! {
            _ = token.cancelled() => break,
            res = lines.next_line() => match res? {
                Some(l) => l,
                None => break, // kliens bontotta a kapcsolatot
            },
        };

        let response = process_line(&line, &store);

        tokio::select! {
            _ = token.cancelled() => break,
            res = writer.write_all(response.as_bytes()) => {
                res?;
                writer.write_all(b"\n").await?;
            }
        }
    }
    Ok(())
}

A socket.into_split() az olvasó- és íróoldalt különválasztja. A BufReader a read_half-ból olvas, a BufWriter a write_half-ra pufferel. A select! azt jelenti: ha a leállítási token megszakad, a next_line()-re váró task is azonnal kilép, mert a select! csak a befejeződő jövővel foglalkozik. Ugyanez igaz a válasz írására is.

A tokio_util::codec modul kifinomultabb keretezést ad: például hosszprefixes vagy szigorúbb szöveges protokollt (any_delimiter, LinesCodec), és a Framed típus Stream-ként kezeli a bejövő kereteket. A mi protokollunknál a BufReader::lines elegendő; a codecalapú megoldást a Kecses leállás nem igényli, de nagyobb rendszereknél érdemes megfontolni.

17.4.6 Megosztott állapot Arc<Mutex<dyn Storage>>-kal

A szerver több klienssel dolgozik, ezért a tárolót minden tasknak el kell érnie. A típus Arc<Mutex<dyn Storage>>: az Arc biztosítja a közös tulajdonjogot a taskok között, a Mutex a kizárólagos hozzáférést a tárolóhoz. A dyn Storage trait-objektum azt jelenti, hogy a szerver nem tudja, hogy MemStore vagy FileStore van mögötte, csak a Storage trait metódusait hívja – ugyanúgy, ahogy egy C++ interfész mögé rejtett MemStore/FileStore implementációt használnánk.

A kritikus rész a parancs feldolgozása:

fn process_line(line: &str, store: &Arc<Mutex<dyn Storage>>) -> String {
    let command = match Command::parse(line) {
        Ok(cmd) => cmd,
        Err(e) => return format!("ERR {e}"),
    };

    {
        let mut guard = store.lock().expect("storage lock poisoned");
        match execute(&mut *guard, command) {
            Ok(response) => response,
            Err(e) => format!("ERR {e}"),
        }
    }
}

Itt a MutexGuard hatóköre a belső blokkra korlátozódik: a guard létrejön, a tárolóművelet lefut, majd a blokk vége elengedi a zárat. A process_line nem .await-el, tehát nincs esély arra, hogy a zárat egy Future belsejében tartsuk. A válasz stringje ezután kerül a writer.write_all(...).await-hez, már zár nélkül.

Ha a zárat az .await-ig kiterjesztenénk, például így:

// Ez a változat szándékosan rossz tervezési mintát mutat:
async fn handle_client_bad(socket: TcpStream, store: Arc<Mutex<dyn Storage>>) {
    let mut lines = BufReader::new(socket).lines();
    while let Ok(Some(line)) = lines.next_line().await {
        let mut guard = store.lock().unwrap();  // std Mutex zára itt elengedhető lenne,
        // de ha tokio::sync::Mutex-et használunk, a guard .await-en át tartása
        // holtversenyt okozhat.
        let response = execute(&mut *guard, Command::parse(&line).unwrap());
        // ... itt .await a válaszírásnál; a guard még élne
        drop(guard); // ez csak a példában jelzi a helyes elengedést
    }
}

A tokio Mutex guardja nem Send, és a .await alatt tartva más taskok kizárásra kerülnek; a std::sync::Mutex esetén is fennáll, hogy hosszú hálózati írás alatt a zár blokkolja a többi klienst. Ezért a fenti process_line mintája a helyes.

17.4.7 Kecses leállás CancellationToken-nel

A leállítás folyamata a következő: 1. A main függvény létrehoz egy CancellationToken példányt. 2. Egy külön task figyeli a Ctrl-C jelet tokio::signal::ctrl_c().await segítségével, majd meghívja a token.cancel()-t. 3. A listener select!-ben figyeli a token.cancelled()-et, így az accept ciklus kilép, és nem fogad új kapcsolatot. 4. A klienstaskok a saját select!-jeikben észreveszik a megszakítást, befejezik az aktuális sort, és kilépnek. 5. A szerver main függvénye a run_server visszatérése után befejeződik.

A teljes főprogram:

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let addr = std::env::args().nth(1).unwrap_or_else(|| "127.0.0.1:8080".to_string());
    let listener = TcpListener::bind(&addr).await?;
    println!("rkv-server listening on {addr}");

    let store: Arc<Mutex<dyn Storage>> = Arc::new(Mutex::new(MemStore::new()));
    let token = CancellationToken::new();
    let shutdown_token = token.clone();

    tokio::spawn(async move {
        if let Err(e) = tokio::signal::ctrl_c().await {
            eprintln!("ctrl_c failed: {e}");
            return;
        }
        println!("shutdown signal received");
        shutdown_token.cancel();
    });

    run_server(listener, store, token).await;
    println!("shutdown complete");
    Ok(())
}

A tokio::signal::ctrl_c() a Unix SIGINT jelet aszinkron módon várja. A haladóbb alkalmazások tracing-gel naplózhatják az eseményeket; ezt a Naplózás és megfigyelhetőség alfejezetben tesszük hozzá.

A leállítás és a klienskezelés kapcsolatát foglalja össze az alábbi ábra:

Az ábrán látható, hogy a SET parancs feldolgozása közben érkező SIGINT nem szakítja félbe a tároló műveletet; a token megszakad, de a kliens csak a válasz elküldése után lép ki. Ez a kecses leállás lényege.

17.4.8.2 2. lépés: az rkv-server/src/main.rs megvalósítása

A fenti main.rs kódot kiegészítjük a process_line és execute függvényekkel. A következő teljes fájl:

use std::sync::{Arc, Mutex};

use anyhow::Result;
use rkv_core::{Command, Error, MemStore, Storage};
use tokio::io::{AsyncBufReadExt, AsyncWriteExt, BufReader, BufWriter};
use tokio::net::{TcpListener, TcpStream};
use tokio_util::sync::CancellationToken;

#[tokio::main]
async fn main() -> Result<()> {
    let addr = std::env::args().nth(1).unwrap_or_else(|| "127.0.0.1:8080".to_string());
    let listener = TcpListener::bind(&addr).await?;
    println!("rkv-server listening on {addr}");

    let store: Arc<Mutex<dyn Storage>> = Arc::new(Mutex::new(MemStore::new()));
    let token = CancellationToken::new();
    let shutdown_token = token.clone();

    tokio::spawn(async move {
        if let Err(e) = tokio::signal::ctrl_c().await {
            eprintln!("ctrl_c failed: {e}");
            return;
        }
        println!("shutdown signal received");
        shutdown_token.cancel();
    });

    run_server(listener, store, token).await;
    println!("shutdown complete");
    Ok(())
}

async fn run_server(listener: TcpListener, store: Arc<Mutex<dyn Storage>>, token: CancellationToken) {
    loop {
        tokio::select! {
            _ = token.cancelled() => break,
            res = listener.accept() => {
                let (socket, addr) = match res {
                    Ok(v) => v,
                    Err(e) => { eprintln!("accept error: {e}"); continue; }
                };
                let store = Arc::clone(&store);
                let token = token.clone();
                tokio::spawn(async move {
                    if let Err(e) = handle_client(socket, store, token).await {
                        eprintln!("client {addr}: {e}");
                    }
                });
            }
        }
    }
}

async fn handle_client(
    socket: TcpStream,
    store: Arc<Mutex<dyn Storage>>,
    token: CancellationToken,
) -> Result<()> {
    let (read_half, write_half) = socket.into_split();
    let mut lines = BufReader::new(read_half).lines();
    let mut writer = BufWriter::new(write_half);

    loop {
        let line = tokio::select! {
            _ = token.cancelled() => break,
            res = lines.next_line() => match res? {
                Some(l) => l,
                None => break,
            },
        };

        let response = process_line(&line, &store);

        tokio::select! {
            _ = token.cancelled() => break,
            res = writer.write_all(response.as_bytes()) => {
                res?;
                writer.write_all(b"\n").await?;
            }
        }
    }
    Ok(())
}

fn process_line(line: &str, store: &Arc<Mutex<dyn Storage>>) -> String {
    let command = match Command::parse(line) {
        Ok(cmd) => cmd,
        Err(e) => return format!("ERR {e}"),
    };

    {
        let mut guard = store.lock().expect("storage lock poisoned");
        match execute(&mut *guard, command) {
            Ok(response) => response,
            Err(e) => format!("ERR {e}"),
        }
    }
}

fn execute(store: &mut dyn Storage, command: Command) -> std::result::Result<String, Error> {
    match command {
        Command::Get(key) => match store.get(&key)? {
            Some(value) => Ok(format!("VALUE {key} {value}")),
            None => Ok("NOTFOUND".to_string()),
        },
        Command::Set(key, value) => {
            store.set(key, value)?;
            Ok("OK".to_string())
        }
        Command::Delete(key) => {
            if store.delete(&key)? {
                Ok("OK".to_string())
            } else {
                Ok("NOTFOUND".to_string())
            }
        }
        Command::List(prefix) => {
            let items = store.list(prefix.as_deref())?;
            let mut out = String::new();
            for (k, v) in items {
                out.push_str(&format!("VALUE {k} {v}\n"));
            }
            out.push_str("OK");
            Ok(out)
        }
    }
}

A process_line visszaadhat többsoros választ a LIST esetén; a handle_client a végére mindig egy \n-t tesz, így a LIST záró OK sora is sortörést kap. A write_all(response.as_bytes()).await és a kiegészítő \n írása után a BufWriter puffereli az adatokat.

17.4.8.4 4. lépés: integrációs teszt

Hozzuk létre az rkv-server/tests/server.rs fájlt. A teszt a szervert egy tokio taskban indítja, és egy TCP-klienssel kommunikál:

use std::sync::{Arc, Mutex};

use rkv_core::{MemStore, Storage};
use rkv_server::run_server;
use tokio::io::{AsyncBufReadExt, AsyncWriteExt, BufReader, BufWriter};
use tokio::net::TcpListener;
use tokio_util::sync::CancellationToken;

#[tokio::test]
async fn set_get_delete() {
    let listener = TcpListener::bind("127.0.0.1:0").await.unwrap();
    let addr = listener.local_addr().unwrap();
    let store: Arc<Mutex<dyn Storage>> = Arc::new(Mutex::new(MemStore::new()));
    let token = CancellationToken::new();
    let server = tokio::spawn(run_server(listener, store, token.clone()));

    let stream = tokio::net::TcpStream::connect(addr).await.unwrap();
    let (read_half, write_half) = stream.into_split();
    let mut reader = BufReader::new(read_half).lines();
    let mut writer = BufWriter::new(write_half);

    writer.write_all(b"SET hello world\n").await.unwrap();
    writer.write_all(b"GET hello\n").await.unwrap();
    writer.write_all(b"DEL hello\n").await.unwrap();
    writer.write_all(b"GET hello\n").await.unwrap();
    writer.flush().await.unwrap();

    let lines: Vec<String> = [
        reader.next_line().await.unwrap().unwrap(),
        reader.next_line().await.unwrap().unwrap(),
        reader.next_line().await.unwrap().unwrap(),
        reader.next_line().await.unwrap().unwrap(),
    ]
    .to_vec();

    assert_eq!(lines, vec!["OK", "VALUE hello world", "OK", "NOTFOUND"]);

    token.cancel();
    server.await.unwrap();
}

A run_server függvényt pub-ként kell elérhetővé tenni az rkv-server binárisban, például a main.rs-ben pub async fn run_server(...)-ként. A teszt cargo test -p rkv-server paranccsal futtatható.

17.4.8.5 5. lépés: leállítási teszt

Indítsuk el a szervert, majd küldjünk egy Ctrl-C-t. A terminálban a kimenet:

rkv-server listening on 127.0.0.1:8080
^Cshutdown signal received
shutdown complete

Ha egy kliens éppen kapcsolódva van, a leállítás után a kliens a következő parancs után connection reset értesülést kap, de a szerver előtte a token miatt már nem vár a következő sorra.

17.4.9 Tipikus hibák és átállási csapdák

  1. Zár tartása .await-en át. A tokio MutexGuard nem Send, és nem szabad .await-en át tartani. Ha mégis megteszed, a task várakozás közben birtokolja a zárat, a többi task áll, és a tokio scheduler futásidejű panic-et is adhat. A megoldás a fenti process_line-minta: a zár hatóköre rövid, szinkron blokk, és a válaszírást zár nélkül végezzük.

  2. A leállítási jel elfelejtése a kliensben. Ha a kliens task nem figyeli a CancellationToken-t, a szerver leállási kérése után a kliens a next_line()-ra vár, és a szerver futó taskjai sosem érnek véget. Minden .await-et – különösen a hosszú I/O-t – select!-ben kell a token.cancelled()-tel párhuzamosítani.

  3. unwrap mindenhol a záron. A store.lock().expect(...) a laborban indokolt, mert a mérgezés (poisoning) a tároló hibája utáni váratlan állapot. Éles kódban a könyvtári rétegben Result-et adj vissza, és a binárisban csak a legfelső szinten expect-elj. A fejezet példájában a process_line String-et ad, ezért a hiba szöveggé alakítása elfogadható.

  4. A LIST válaszának rossz keretezése. Ha minden VALUE sor után a handle_client külön \n-t írna, a LIST belső sortörései és a hozzáfűzés dupla sortörést eredményezne. A process_line egyetlen stringet épít, benne a szükséges \n-ekkel, és a handle_client csak a válasz végére tesz egyet.

17.4.10 Feladatok

17.4.10.1 a) Lefordul-e és miért?

Az alábbi tokio kliens task select!-ben a token.cancelled()-et és a lines.next_line()-t versenyezteti:

let line = tokio::select! {
    _ = token.cancelled() => break,
    res = lines.next_line() => res?,
};

Miért nem okoz ez lefordulási hibát? Mi történik, ha a token már a select! előtt meg volt szakítva?

17.4.10.2 b) C++ kód átírása idiomatikus Rustra

Adott egy egyszerű C++ echo-szerver, amely minden bejövő sort visszaküld. Írd át a kapcsolatkezelőt Rust/tokio select!-tel és CancellationToken-nel kecses leállással. A szerver globális leállási flag helyett tokent használjon.

17.4.10.3 c) Implementálási feladat az rkv-ban

Bővítsd az rkv-server execute függvényét úgy, hogy a LIST parancs a kulcsok szerint rendezve adja vissza az elemeket, és a LIST válasza mindig OK sort zárjon. Ellenőrizd a MemStore list metódusának visszatérési sorrendjét; ha nem rendezett, a szerverben rendezd.

17.4.10.4 d) Refaktorálás vagy tervezési döntés

A leállítás során a kliens, amelyik épp next_line()-re vár, csak a token megszakadásakor lép ki. Ha a kliens nem küld adatot, a leállás azonnal megtörténik, de mi van akkor, ha egy kliens folyamatosan küld parancsokat? Tervezz egy időkorlátot: a leállás után legfeljebb 5 másodpercig engedjük a folyamatban lévő parancsok befejezését, utána kényszerítsük a kilépést. Milyen tokio eszközöket használnál?

17.4.11 Megoldások

17.4.11.1 a) Megoldás

Nem fordulási hiba, mert a select! makró minden ág egy Future-t vár. A token.cancelled() egy azonnal elérhető jövőt ad, ha a token már megszakadt; ekkor a select! ezt az ágat választja, és a break kiugrik a ciklusból. Ha a token nincs megszakítva, a next_line() ág vár. A res? az ágban csak akkor fut, ha a sor olvasása befejeződött. A break értéke (), a select! kifejezés egyenértékű a hurok törzsével; a let line = ... nem hajtódik végre, mert a break-kel elhagyjuk a ciklust.

17.4.11.2 b) Megoldás

A C++ echo-szerver kapcsolatkezelőjének Rust megfelelője:

async fn echo_client(socket: TcpStream, token: CancellationToken) -> Result<()> {
    let (read_half, write_half) = socket.into_split();
    let mut lines = BufReader::new(read_half).lines();
    let mut writer = BufWriter::new(write_half);

    loop {
        let line = tokio::select! {
            _ = token.cancelled() => break,
            res = lines.next_line() => match res? {
                Some(l) => l,
                None => break,
            },
        };
        tokio::select! {
            _ = token.cancelled() => break,
            res = writer.write_all(line.as_bytes()) => {
                res?;
                writer.write_all(b"\n").await?;
            }
        }
    }
    Ok(())
}

17.4.11.3 c) Megoldás

Az execute Command::List ágában a let mut items = store.list(prefix.as_deref())?; után rendezzük:

Command::List(prefix) => {
    let mut items = store.list(prefix.as_deref())?;
    items.sort_by(|a, b| a.0.cmp(&b.0));
    let mut out = String::new();
    for (k, v) in items {
        out.push_str(&format!("VALUE {k} {v}\n"));
    }
    out.push_str("OK");
    Ok(out)
}

A list metódus visszatérési típusa Result<Vec<(String, String)>, Error>; a rendezés a kulcsok szerint növekvő. A String kulcsok lexikografikus rendezése megfelel a protokollnak.

17.4.11.4 d) Megoldás

A tervezési döntés: a tokio timeout-ja és a CancellationToken kombinálható. A leállítási szakaszban a fő task a token megszakítása után elindít egy timeout(Duration::from_secs(5))-t, és a kliens taskokat egy JoinSet-ben várja. A JoinSet minden taskot megvár, de a timeout segítségével 5 másodperc után kilép. A kliens taskok továbbra is a saját tokent figyelik, de a fő task a JoinSet bontásával eldobja őket. Egy másik lehetőség a tokio::time::timeout minden egyes sor olvasására a kliensben, hogy a leállás után ne várjunk új parancsra.

Példa a leállítási szakaszra:

let _ = tokio::time::timeout(Duration::from_secs(5), async {
    while let Some(res) = join_set.join_next().await {
        if let Err(e) = res {
            eprintln!("task error: {e}");
        }
    }
}).await;

17.4.12 Rövid összefoglaló

Ebben az alfejezetben megépítettük az rkv-server tokio-alapú TCP-szervert, amely soralapú szöveges protokollt beszél: GET, SET, DEL, LIST parancsokat fogad, és OK, VALUE, NOTFOUND, ERR válaszokat ad. A keretezéshez BufReader::lines-t használunk; a tokio_util::codec-et nagyobb, összetettebb protokollokhoz említettük. A megosztott állapot Arc<Mutex<dyn Storage>>, amelyben a process_line szinkron blokkjában rövid időre szerzünk zárat, és soha nem tartjuk .await-en át. A kecses leállást tokio_util::sync::CancellationToken valósítja meg: a main tokio::signal::ctrl_c()-re indít egy taskot, amely cancel()-t hív; a listener és a klienstaskok select!-ben figyelik a tokent, így az új kapcsolatok fogadása leáll, a folyamatban lévő parancsok befejeződnek. A laborban létrehoztuk az rkv-server crate-et, a run_server és handle_client függvényeket, és integrációs tesztet írtunk. Továbbvitt eredmény: az rkv-server bináris, a run_server és a process_line függvény a Naplózás és megfigyelhetőség és a Záróprojekt alapja.
