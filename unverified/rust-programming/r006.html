3.3 Tuple-ök, tömbök és az első pillantás a slice-okra

3.3.1 Motiváció

C++-ban több visszatérési értéket általában std::pair-rel, std::tuple-pal vagy kimenő paraméterekkel adunk vissza; a strukturált kötés (structured binding) C++17 óta teszi ezt kényelmessé. A tömböknél a C++ fejlesztő hozzászokott ahhoz, hogy a std::vector/std::array operator[]-je általában nem ellenőrzi a határokat, és a hibás indexelés definiálatlan viselkedést okozhat. Rust ezt a két területet alapvetően másként kezeli: a tuple és a destrukturálás nyelvi szintű, a tömbindexelés pedig mindig határellenőrzött, és a biztonságos alternatíva Option-t ad vissza. Ebben az alfejezetben ezeket az alapvető típusokat nézzük meg, majd bevezetjük a slice fogalmát, amely a Rust referenciavilág egyik legfontosabb eleme.

3.3.2 Fogalmak és szabályok

Definíció. A tuple heterogén, fix méretű érték, amely több különböző típusú értéket csomagol egybe. A típusa (T1, T2, ...), például (i32, String, bool). A mezők elérése nullától indexelt: t.0, t.1, stb. A tuple literálja (érték1, érték2, ...). A zéró elemű tuple az egység (unit) típus: (), amely a C++ void-hoz hasonlítható, de értékként is létezik.

Definíció. A tömb típusa [T; N], ahol N a típus része, és fordítási időben ismert. Például [i32; 5] öt darab i32-et tartalmaz. A méret nem változtatható futás közben; dinamikus méretű gyűjteményekhez Vec<T>-t használunk, amelyről később lesz szó.

Definíció. A slice egy folytonos tartományra mutató, nem tulajdonos nézet. Típusa &[T] (osztott) vagy &mut [T] (megváltoztatható). A slice egy úgynevezett fat pointer: két gépi szóból áll, egy mutatóból és egy hosszból. A hossz mindig az elemek számát adja meg, nem bájtokban.

Szabály. A tömb és slice indexelése a [] operátorral mindig határellenőrzött. Ha az index kívül esik a tartományon, a program pánikba esik (panic!), és az adott szál leáll; ez nem definiálatlan viselkedés, hanem jól meghatározott hiba. A get(index) metódus Option<&T>-t ad vissza: Some a sikeres, None a hibás indexre.

Szabály. A &[T] slice nem lehet önálló tulajdonos; a mögöttes elemeket mindig egy tömb, Vec<T> vagy más tároló birtokolja. A let s: [i32] önálló slice-típus nem fordul le, mert a méret nem ismert fordítási időben. A slice-ok élettartamát a kölcsönzés-ellenőrző garantálja, így nincs felszabadított memóriára mutató érvénytelen slice.

3.3.3 C++ ↔︎ Rust összevetés

A több visszatérési érték C++-ban std::tuple-pal és strukturált kötéssel:

#include <string>
#include <tuple>

std::tuple<int, std::string> parse(const std::string& line) {
    auto pos = line.find(':');
    if (pos == std::string::npos) {
        return {0, line};
    }
    return {
        std::stoi(line.substr(0, pos)),
        line.substr(pos + 1)
    };
}

// Használat:
auto [code, text] = parse("42:hello");

Rustban a tuple a nyelv része, és a destrukturálás közvetlenül let-ben történik:

fn parse(line: &str) -> (i32, &str) {
    let pos = line.find(':').unwrap_or(line.len());
    (line[..pos].parse().unwrap(), &line[pos + 1..])
}

// Használat:
let (code, text) = parse("42:hello");

A különbség: Rustban nincs std::tuple sablonosztály, mert a tuple beépített típus; a destrukturálás nem igényel C++17-es kiterjesztést, és a &str slice élettartamát a borrow checker követi. A parse példában a .unwrap() csak a dolgozat rövidsége miatt szerepel; a hibakezelésről a Result, a ? operátor és a panic helye alfejezetben lesz szó.

A tömbindexelés C++-ban gyakran ellenőrizetlen, Rustban mindig ellenőrzött:

#include <array>

std::array<int, 3> a{1, 2, 3};
int x = a[5]; // UB: definiálatlan viselkedés
let a = [1, 2, 3];
let x = a[5]; // panic! index out of bounds

A biztonságos alternatíva Rustban:

let a = [1, 2, 3];
match a.get(5) {
    Some(v) => println!("{v}"),
    None => println!("nincs ilyen index"),
}

C++20-tól a std::span<const int> hasonló szerepet tölt be, mint a Rust &[i32], de a Rust slice-ot a borrow checker életciklus-szabályai védik, és nem lehet null, valamint a hossza mindig érvényes a mutatójával együtt.

3.3.4 Kidolgozott példa

Vegyünk egy olyan függvényt, amely egy slice minimumát, maximumát és összegét adja vissza tuple-ben. A szándékosan naiv változat indexeléssel kezdődik, és üres bemenetre futásidejű hibát okoz:

fn min_max_sum(values: &[i32]) -> (i32, i32, i32) {
    let mut min = values[0]; // üres slice-nál panic!
    let mut max = values[0];
    let mut sum = 0;
    for &v in values {
        min = min.min(v);
        max = max.max(v);
        sum += v;
    }
    (min, max, sum)
}

fn main() {
    let arr = [15, -3, 22, 7, 10];
    let middle: &[i32] = &arr[1..4];
    println!("middle = {middle:?}");
    let (min, max, sum) = min_max_sum(middle);
    println!("min = {min}, max = {max}, sum = {sum}");
}

A middle kimenete [-3, 22, 7], a statisztika pedig min = -3, max = 22, sum = 26. Ha a bemeneti slice üres, például &arr[..0], a values[0] kifejezés pánikba esik: panic! index out of bounds. Ez hasonlít a C++ std::array ellenőrizetlen hozzáféréséhez, de itt nincs UB, hanem kontrollált leállás.

A javított változat Option-t ad vissza, és a split_first segítségével nem indexel:

fn min_max_sum(values: &[i32]) -> Option<(i32, i32, i32)> {
    let (first, rest) = values.split_first()?;
    let mut min = *first;
    let mut max = *first;
    let mut sum = *first;
    for &v in rest {
        min = min.min(v);
        max = max.max(v);
        sum += v;
    }
    Some((min, max, sum))
}

A ? operátor itt Option-ban működik: ha a slice üres, a split_first() None-t ad, és a függvény azonnal None-nal tér vissza. A main már ilyenkor is biztonságosan tudja kezelni a hibát:

match min_max_sum(&arr[..0]) {
    Some((min, max, sum)) => println!("min = {min}, max = {max}, sum = {sum}"),
    None => println!("A bemeneti slice üres."),
}

A min.max(v) és min.min(v) metódusok a std::cmp::Ord trait által biztosítottak, és idiomatikusan fejezik ki a szándékot.

3.3.5 Memóriaábra: tömb és slice

A slice fat pointer felépítését a következő memóriaábra szemlélteti. Az egyszerűség kedvéért a cél egy Vec, mert annak a kupacpuffere jól ábrázolható; a tömb slice esetén a cél a stacken lenne, de a pointer célja ugyanolyan.

A v egy Vec<i32>, amely a stacken három mezőt tart: a kupacpuff erre mutató ptr-t, az aktuális elemszámot (len = 3) és a lefoglalt kapacitást (cap = 3). Az s slice szintén a stacken van, de csak két mezője van: ptr és len = 2. Nincs külön kapacitás, mert a slice nem birtokol; a mögöttes puffer életciklusát a borrow checker a kölcsönzés idejére biztosítja. A szöveges példában &arr[1..4] esetén a cél a stacken lévő tömb, a hossz pedig három, de a fat pointer elve ugyanaz.

Továbbvitt eredmény. A fat pointer gondolata – az, hogy egy referencia több adatot hordozhat, mint egyetlen gépi cím – a Slice-ok, String és &str, UTF-8 alfejezetben a String/&str párosnál, a Trait objektumok és dinamikus diszpécs alfejezetben pedig a dinamikus dispatch-nél tér vissza.

3.3.6 Tipikus hibák és átállási csapdák

  1. A [] határellenőrzés figyelmen kívül hagyása. A C++ fejlesztő azt gondolhatja, hogy a Rust a[i] ugyanolyan olcsó, mint a C++ a[i] release módban. Bár a Rust határellenőrzése általában kicsi többletköltséggel jár, forró ciklusokban érdemes az iterátorokat vagy a get-et használni, mert az előbbieknél a fordító gyakran el tudja távolítani a fölösleges ellenőrzéseket. A get és a map/and_then kombinációja ráadásul kifejezőbb.

  2. A get után azonnali unwrap. A arr.get(i).unwrap() pontosan ugyanazt a pánikot váltja ki, mint a arr[i] indexelés, csak rosszabb stílusban. Ha a hívó tudja, hogy az index érvényes, akkor a [] a megfelelő; ha nem tudja, akkor az Option-t kell kezelni match-csel, if let-tel vagy ?-tel.

  3. A tuple mezők számozásának félreértése. A Rust tuple mezői nullától kezdődnek, mint a C++ std::get<0> indexei. A (1, 2, 3).3 nem fordul le, mert nincs negyedik mező. A destrukturálás megkerüli a .0/.1 jelölést, és olvashatóbb kódot ad.

  4. A slice mint „pointer + hossz” félreértelmezése. Bár a slice valóban fat pointer, a Rust típusrendszerében a hossz a stacken lévő érték része, és a mutató nem lehet null. A C++ std::span-hez képest a Rust slice-ot a borrow checker is védi, ezért nem fordul elő felszabadított memóriára mutató slice, és a &mut [T] slice egyedüliségét a kölcsönzési szabály garantálja.

3.3.7 Feladatok

  1. Lefordul-e és miért? Vizsgáljuk meg az alábbi kódot:

    let tuple = (1, 2, 3);
let x = tuple.3;

    Fordul-e a kód? Ha nem, miért, és mi a javítás?

  2. C++-kód átírása idiomatikus Rustra. Adott a következő C++ függvény, amely egy std::array<int, 4>-ből visszaadja az első és az utolsó elem különbségét, ha a tömb nem üres:

    #include <array>
#include <optional>

std::optional<int> first_last_diff(const std::array<int, 4>& a) {
    return a.front() - a.back(); // ha üres lenne, UB lenne
}

    Írjunk Rust függvényt, amely [i32; 4] bemenetre Option<i32>-t ad vissza, és nem indexeléssel, hanem first() és last() metódussal, vagy split_first-fel dolgozik.

  3. Implementációs feladat. Hozzunk létre önálló r006 crate-et a ~/rust-labor/r006/ könyvtárban (cargo new r006 --bin). A main.rs tartalmazzon egy describe függvényt, amely egy &[i32] slice-ra visszaad egy (i32, i32, i32, f64) tuple-t: minimum, maximum, összeg és átlag. Használjon split_first-et és Option-t, hogy üres slice esetén ne pánikoljon. A main készítsen slice-ot egy tömb egy részéből, és írja ki a tuple mezőit.

  4. Hibajavítás és refaktorálás. Az alábbi kód arr.get(i).unwrap()-ot használ, ami pánikot okozhat:

    fn print_element(arr: &[i32], i: usize) {
    let v = arr.get(i).unwrap();
    println!("elem = {v}");
}

    Refaktoráljuk a függvényt úgy, hogy ne pánikoljon, hanem Option-t adjon vissza, vagy match-csel írjon ki üzenetet. Melyik a jobb API-tervezés, és miért?

3.3.8 Megoldások

  1. Lefordul-e és miért? A kód nem fordul le. A hiba lényege no field '3' on type '(i32, i32, i32)'; a tuple mezői nullától indexeltek, ezért a legnagyobb érvényes index a 2. A javítás let x = tuple.2; vagy let (x, _, _) = tuple;.

  2. C++-kód átírása idiomatikus Rustra.

    fn first_last_diff(a: &[i32; 4]) -> Option<i32> {
    let first = a.first()?;
    let last = a.last()?;
    Some(last - first)
}

    A first() és last() metódusok a slice-API részei, és Option<&i32>-t adnak vissza. A ? a None esetén azonnal visszatér, így a függvény üres (bár itt a tömb mérete fix) vagy hibás esetben is biztonságos. Alternatív megoldás a split_first és a last kombinációja is lehet.

  3. Implementációs feladat. A main.rs:

    fn describe(values: &[i32]) -> Option<(i32, i32, i32, f64)> {
    let (first, rest) = values.split_first()?;
    let mut min = *first;
    let mut max = *first;
    let mut sum = *first;
    for &v in rest {
        min = min.min(v);
        max = max.max(v);
        sum += v;
    }
    let avg = sum as f64 / values.len() as f64;
    Some((min, max, sum, avg))
}

fn main() {
    let arr = [8, 3, 12, 5, 9, 1];
    let part: &[i32] = &arr[1..5];
    match describe(part) {
        Some((min, max, sum, avg)) => {
            println!("min = {min}, max = {max}, sum = {sum}, átlag = {avg:.2}");
        }
        None => println!("A slice üres."),
    }
}

    A cargo run kimenete: min = 3, max = 12, sum = 29, átlag = 7.25. A part slice a [3, 12, 5, 9] elemet fedi le.

  4. Hibajavítás és refaktorálás. A get(i).unwrap() helyett a függvény Option-t ad vissza:

    fn print_element(arr: &[i32], i: usize) -> Option<()> {
    let v = arr.get(i)?;
    println!("elem = {v}");
    None
}

    Vagy a hívó oldalon történik a kezelés:

    match arr.get(i) {
    Some(v) => println!("elem = {v}"),
    None => println!("nincs ilyen index"),
}

    Az Option-t visszaadó változat jobb API-tervezés, mert a hívó döntheti el, hogyan kezeli a hibát, nem a könyvtár függvénye pánikol. A match-es változat a különálló side effect esetén is gyakori, de nem helyettesíti a hibaterjesztést.

3.3.9 Rövid összefoglaló

A tuple Rustban beépített heterogén, fix méretű típus; destrukturálása let (a, b) = t; alakban történik, és így a C++ std::tuple/std::tie/structured binding kényelmét nyújtja. A tömb [T; N] mérete a típus része. Az indexelés [] operátorral mindig határellenőrzött, hibás indexnél panic! lép fel, nem UB; a get(i) Option<&T>-t ad. A slice &[T] fat pointer: mutató és hossz, nem tulajdonos nézet, és a borrow checker garantálja az élettartamát. Továbbvitt eredmény: a fat pointer gondolatát a &str és &[T] részletes tárgyalása a Slice-ok, String és &str, UTF-8, valamint a dinamikus dispatch a Trait objektumok és dinamikus diszpécs alfejezetben viszi tovább.

3.3.10 Források és ellenőrzési hiányok

A tuple, a tömb, a get és a slice stabil nyelvi elemei; a hivatalos leírások a Rust Reference és a Rust Book dokumentációjában találhatók. A példákban szereplő pontos panic! üzenetek és a fordító hibaüzeneteinek szövege verziófüggő; ellenőrzésre érdemes a fejezet készítésekor használt toolchainen. A split_first, first, last és a min/max metódusok a standard könyvtár stabil API-jának részei, de a pontos szignatúrákat a docs.rs-en érdemes ellenőrizni.
