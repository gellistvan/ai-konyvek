23.1 no_std, embedded-hal és Embassy: Rust mikrovezérlőn

23.1.1 Motiváció

Egy tapasztalt C++ beágyazott fejlesztő pontosan tudja, milyen érzés, amikor a hibakeresés nem a logikáról, hanem arról szól, hogy valamelyik megszakításkezelő túlírta a másik regiszterét. A C++11–C++20 hiába ad RAII-t, okosmutatókat és erős típusokat, a tipikus beágyazott C/C++ kód mégis gyakran makrókba, volatile pointerekbe, kézi regisztercímekbe és globális perifériaobjektumokba fut. A GPIOB->ODR |= (1 << 5) stílusú sorok nem típusbiztosak, semmi nem akadályozza meg, hogy egy bemenetre konfigurált lábon feszültséget írjunk, és az ownership hiánya mindenféle rejtett aliasolási hibát enged.

A Rust válasza erre nem csupán „más szintaxis”, hanem a típusrendszer és az ownership bevonása a hardver erőforrásainak modellezésébe. Ugyanaz a Rust, amit a host-oldali rkv szerverben megismertünk, std nélkül is működik mikrovezérlőn. Amit a Pin, Unpin, async trait-ek és Send-határok és a Newtype, PhantomData, typestate és const generikusok alfejezetekben tanultunk, most a fizikai hardveren kap szerepet.

23.1.2 Fogalmak és szabályok

Definíció. A no_std környezet olyan Rust-környezet, amelyben a std könyvtár nem érhető el. A std a core és az alloc fölé épül, és olyan szolgáltatásokat ad, mint a thread, a fájlrendszer, a dinamikus időzítés vagy a standard I/O. A no_std tehát nem azt jelenti, hogy semmilyen könyvtár nincs.

Szabály. #![no_std] crateszintű attribútummal a crate lemond a std-ről. Ekkor a core könyvtár automatikusan elérhető: ez tartalmazza a legalapvetőbb elemeket, például az Option, Result, Iterator, Clone, Copy, Send, Sync, Sized, a slice és a str típusokat, valamint a core::ptr, core::mem, core::ops, core::fmt modulokat. Az alloc könyvtár a Vec, String, Box, Arc és hasonló, kupacot igénylő típusokat biztosítja, de csak akkor, ha a program rendelkezik globális allokátorral.

Szabály. A std-től megfosztott bináris programban nincs normál main; helyette #![no_main] attribútumot használunk, és a belépési pontot magunk definiáljuk #[no_mangle] pub extern "C" fn _start függvénnyel, vagy a platform-specifikus HAL adja. #![no_std] binárisban kötelező egy #[panic_handler] függvény, amely fn(&PanicInfo) -> ! szignatúrájú, és soha nem tér vissza.

Definíció. A beágyazott Rust-ökoszisztéma szokásos rétegződése: PAC (Peripheral Access Crate), HAL (Hardware Abstraction Layer), embedded-hal traitek, majd driverek és alkalmazás. A PAC a gyártó által definiált regiszterek szintjét adja, a HAL típusbiztos, kényelmes periféria-API-t, az embedded-hal traitek pedig gyártófüggetlen interfészeket.

Szabály. A perifériák szingletonok: minden fizikai periféria — például egy GPIO-blokk vagy egy UART-vezérlő — egyetlen Rust-értékként jelenik meg. A take() metódus Option-t ad vissza, és a tulajdon elvétele után a típus nem klónozható, nem Copy. Ezáltal a fordító garantálja, hogy két kódrészlet nem vezérelheti ugyanazt a hardvert.

Definíció. A typestate minta a periféria üzemmódját típusparaméterként ábrázolja: például Pin<P, Input<Floating>> és Pin<P, Output> különböző típusok. A konfiguráció tehát fordítási időben rögzül, és a Pin<P, Input<Floating>> típuson egyszerűen nincs set_high metódus.

23.1.3 C++ ↔︎ Rust összevetés

A tipikus C++ beágyazott GPIO-kezelő osztály így nézhet ki:

// cpp
class GpioPin {
  public:
    enum class Mode { Input, Output, InputPullUp };

    void configure(Mode mode) {
      mode_ = mode;
      // ... registers ...
    }

    void set_high() {
      // Feltételezi, hogy a láb Output módban van!
      // ... registers ...
    }

  private:
    Mode mode_;
};

A C++ megoldásban az üzemmód futási idejű adattag, a set_high() hívás helyessége a fejlesztő fegyelmén múlik. Rossz üzemmód esetén a hiba legfeljebb futás közben derül ki, vagy egyáltalán nem.

Rustban a typestate ezt a hibát fordítási időben zárja ki:

// rust (vázlat, konkrét PAC/HAL API nem szükséges hozzá)
use core::marker::PhantomData;

pub struct Pin<const P: u8, MODE> {
    _mode: PhantomData<MODE>,
}

pub struct Input<MODE>(PhantomData<MODE>);
pub struct Floating;
pub struct PullUp;
pub struct Output;
pub struct PushPull;

impl<const P: u8> Pin<P, Input<Floating>> {
    pub fn into_pull_up_input(self) -> Pin<P, Input<PullUp>> {
        // SAFETY: a gyártói referencia szerint a P láb konfigurálható
        // bemeneti felhúzó üzemmódba, és az adott hardver csak a mi
        // tulajdonunkban van, mert a take() korábban lefutott.
        unsafe { configure_input_pull_up_register(P) };
        Pin { _mode: PhantomData }
    }

    pub fn into_push_pull_output(self) -> Pin<P, Output> {
        // SAFETY: a konfiguráció után a láb kimenetként fog viselkedni;
        // a regiszterhez tartozó invariánsok teljesülnek.
        unsafe { configure_push_pull_output_register(P) };
        Pin { _mode: PhantomData }
    }
}

impl<const P: u8> Pin<P, Output> {
    pub fn set_high(&mut self) {
        // SAFETY: az Output mód már garantálja, hogy a kimeneti regiszter
        // írható; a `&mut self` kizárja az aliasolást.
        unsafe { write_output_high(P) };
    }

    pub fn set_low(&mut self) {
        unsafe { write_output_low(P) };
    }
}

A Pin<P, Input<Floating>> értéken nincs set_high: a metódus csak a Pin<P, Output> típuson létezik. Az into_ konverziók felemésztik a régi értéket, és az új üzemmódnak megfelelő típust adják vissza. Ez a destruktív mozgatás pontosan azt az ownership-gondolkodást használja, amit az Ownership: minden értéknek egy tulajdonosa van alapozott meg.

23.1.4 A no_std könyvtárak rétegződése

Az alábbi ábra a beágyazott Rust tipikus rétegződését mutatja:

A rétegek felülről lefelé haladva: az alkalmazás csak a driverek és a HAL típusait látja. A PAC a gyártói regiszterek elrendezését írja le, gyakran unsafe hozzáféréssel. A HAL ebből a nyers rétegből biztonságos absztrakciót épít, és az Unsafe Rust: szuperképességek és felelősség alfejezetben tanult elv érvényesül: az unsafe blokkok a legbelső rétegbe kerülnek, a kívülről látható API safe. Az embedded-hal traitek e fölé a gyártóspecifikus HAL fölé helyeznek egy közös interfész-réteget. Egy I2C-szenzor driver például nem az STM32 vagy RP2040 konkrét típusát, hanem az embedded_hal::i2c::I2c trait implementációját fogadja el, így a driver újrahasznosítható bármely támogatott MCU-n.

23.1.5 Embassy: async taskok a megszakítások helyett

A hagyományos beágyazott C++ kódban a nem blokkoló várakozást gyakran megszakításokkal, callbackekkel vagy eseményzászlókkal oldjuk meg. Például egy LED villogtatása rendszerint egy timer-interrupt és egy globális számláló köré épül. A Rust async ehelyett lehetővé teszi, hogy a várakozási logikát lineáris kódban írjuk le, miközben az executor a várakozás idején más taskokat futtat.

Az Embassy ezt a modellt viszi beágyazott környezetbe. A Future pollozását a Future-ök és async/await alfejezetben megismertük; Embassyben a pollozás nem egy host OS szálon, hanem a mikrokontroller megszakításaihoz kötve történik. Amikor a Timer::after(...).await fut, a future az executorra bízza a task felfüggesztését, a hardver timer pedig megszakítással ébreszti fel újra.

// rust (vázlat; a konkrét periféria-típus targetfüggő, ellenőrizendő,
// és az Embassy API pontos neveit a docs.rs-en ellenőrizni kell)
#![no_std]
#![no_main]

use embassy_executor::Spawner;
use embassy_time::{Duration, Timer};

// A `Toggleable` itt a HAL-rétegben definiált, Output módú lábat
// absztraháló trait; a konkrét példány a targettől függ.
trait Toggleable {
    fn toggle(&mut self);
}

#[embassy_executor::main]
async fn main(_spawner: Spawner) -> ! {
    // `led` létrehozása a HAL/PAC réteg segítségével történik.
    // A konkrét típus például `stm32::gpio::Output` vagy
    // `rp_pico::gpio::Pin<Output>` lehet.
    let mut led = create_led_output();

    loop {
        led.toggle();
        Timer::after(Duration::from_millis(500)).await;
    }
}

A fenti kódban a led.toggle() szinkron művelet, a várakozás viszont async. A Timer::after által visszaadott future a hardver idősítőjére épül, és az embassy-time könyvtár gondoskodik a megszakításvezérelt ébresztésről. A no_std és no_main itt is jelen van, de a main makró generálja a belépési pontot és a panic-kezelést.

Szabály. Embassy async taskok futtatásához szükséges egy executor. A #[embassy_executor::main] makró egy beépített main-executort konfigurál, de a taskokat általában a Spawner segítségével indítjuk, és a felhasznált Embassy-runtime-hoz a targetnek megfelelő feature-öket kell bekapcsolni a Cargo.toml-ban. A pontos API és a feature-ök verziófüggők.

23.1.6 Labor: no_std kísérlet

Munkakönyvtár: ~/rust-labor/r050/

A labor célja, hogy a no_std korlátait kis léptékben megtapasztaljuk, mielőtt valódi mikrokontrolleres targetre váltanánk. Készíts egy no_std könyvtárcrate-et, amely csak a core-t használja:

mkdir -p ~/rust-labor/r050
cd ~/rust-labor/r050
cargo new --lib nostd-core --vcs none
cd nostd-core

A src/lib.rs tartalma:

// rust
#![no_std]

pub fn clamp(value: i32, min: i32, max: i32) -> i32 {
    if value < min {
        min
    } else if value > max {
        max
    } else {
        value
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn clamp_bounds() {
        assert_eq!(clamp(5, 0, 10), 5);
        assert_eq!(clamp(-3, 0, 10), 0);
        assert_eq!(clamp(11, 0, 10), 10);
    }
}

Fordítsd le és futtasd a teszteket:

cargo test

A könyvtárcrate no_std módban is gond nélkül fordul a host gépen, mert nem használ std-t. Próbáld ki, mi történik, ha String-et vagy Vec-et akarsz létrehozni a clamp függvényben: a fordító hibát ad, mert az alloc nincs engedélyezve. Ez a kísérlet előkészíti, hogy miért fontos a no_std réteg tudatos használata.

Opcionális labor. A valós beágyazott futtatás QEMU-ban vagy fizikai kártyán ennek a fejezetnek a keretein túlmutat, de a teljesség kedvéért érdemes megemlíteni. Egy ARM Cortex-M target esetén például a thumbv7em-none-eabihf target telepítése után egy hasonló vázlat fordítható:

rustup target add thumbv7em-none-eabihf

A teljes bináris futtatáshoz azonban linker-szkript, boot-kód és a célhardverhez illeszkedő memory.x fálj is szükséges; ezek pontos tartalma függ a választott MCU-tól, és a QEMU-val való emuláció beállításait ellenőrizni kell a cortex-m és cortex-m-rt crate-ek aktuális dokumentációjában.

23.1.7 Tipikus hibák és átállási csapdák

  1. Vec és String használata no_std kódban automatikusan. A std-hez kötött típusok nem érhetők el, hacsak nem engedélyezzük az alloc-ot és nem biztosítunk globális allokátort egy beágyazott targeten. A Box, Rc, Arc és Weak alfejezetben tanult Box is csak akkor elérhető, ha az alloc jelen van és allokátor van konfigurálva.

  2. A panic_handler hiánya. A no_std binárisban a panic! makró futási idejű hibát jelez, de ennek kezelése nincs beépítve. Fordítói/linkelési hiba keletkezik, ha a program nem definiál #[panic_handler]-t. A host-oldali std automatikusan ad panichandler-t, a beágyazott világban ezt kézzel kell megadni.

  3. A periféria-singleton klónozása. A take() által visszaadott periféria nem Clone és nem Copy. A gyakori vágy, hogy két helyen is hozzáférjünk ugyanahhoz a perifériához, arra csábít, hogy unsafe pointereket vagy RefCell-t használjunk. A helyes Rust-idióma az, hogy a perifériát csatornán vagy Arc<Mutex<...>> mögé tesszük, ahogyan a Mutex, RwLock, csatornák és a megosztott rkv tette a host-oldali Store-ral.

  4. A typestate kikerülése. Az into_push_pull_output utáni Pin<P, Output> típus nem engedi a bemeneti konfigurációs metódust, de ha a fejlesztő a hardverregisztert unsafe közvetlenül írja, akkor a typestate által adott garancia elveszik. A szabály itt is: az unsafe csak a legalsó rétegben, világos // SAFETY: indoklással.

23.1.8 Feladatok

  1. Fogalmi kérdés. Mondd meg, melyik típus érhető el #![no_std] környezetben alloc nélkül: Option, String, Vec, Result, Arc, core::iter::Map. Indokold.

  2. C++-kód átírása idiomatikus Rustra. Adott egy C++ generátorfüggvény, amely egy std::vector<int>-et ad vissza, és egy beágyazott hőmérséklet-szenzor kalibrációs értékeit olvassa. Írd át a logikát no_std-kompatibilis Rustra, amely statikusan lefoglalt puffert vagy a heapless::Vec típust használ. (A heapless útvonalat ellenőrizni kell a docs.rs-en.)

  3. Typestate GPIO implementáció az rkv-mintában. Hozz létre az rkv workspace-től függetlenül egy rkv-embedded nevű gyakorló crate-et a ~/rust-labor/r050/rkv-embedded/ könyvtárban. Valósíts meg egy Pin<const P: u8, MODE> vázlatot Input<Floating>, Input<PullUp> és Output típusokkal, valamint into_pull_up_input, into_push_pull_output, set_high, set_low metódusokkal. A regiszter-hozzáférést egy üres unsafe fn hívással szimuláld. Fordíttasd le a crate-et.

  4. Refaktorálási döntés. Az Embassy async LED-villogtatóban szeretnénk a LED-et egy másik taskból is vezérelni. Milyen típusú megosztást választanál, és miért? Írd le a kódvázat a Spawner és az embassy_sync::Mutex felhasználásával. (A pontos API-t ellenőrizni kell.)

23.1.9 Megoldások

  1. Az Option, Result és a core::iter::Map elérhetők, mert a core-ban vannak. A String, Vec és Arc nem elérhetők alloc nélkül, mert kupacfoglalást igényelnek. Az alloc csak akkor adja ezeket, ha a crate bekapcsolja az extern crate alloc; sort és van globális allokátor.

  2. A C++ std::vector<int> helyett statikus puffer vagy heapless::Vec használható. Egy lehetséges Rust-változat:

// rust
#![no_std]

// A heapless::Vec használatakor a crate a Cargo.toml-ban:
// heapless = "0.8" (ellenőrizendő a főverzió)
use heapless::Vec;

pub fn read_calibration_values<const N: usize>(sensor: &dyn Sensor)
    -> Vec<i32, N>
{
    let mut values = Vec::new();
    for i in 0..N {
        if let Some(v) = sensor.read_calibration(i) {
            // A push itt is hibát ad, ha a puffer tele van.
            let _ = values.push(v);
        }
    }
    values
}

pub trait Sensor {
    fn read_calibration(&self, index: usize) -> Option<i32>;
}

A Vec<i32, N> a heapless crate típusa, amely statikus kapacitással rendelkezik. A no_std ezt tökéletesen támogatja, mert nincs dinamikus allokáció.

  1. A rkv-embedded crate src/lib.rs tartalma:
// rust
#![no_std]

use core::marker::PhantomData;

pub struct Pin<const P: u8, MODE> {
    _mode: PhantomData<MODE>,
}

pub struct Input<MODE>(PhantomData<MODE>);
pub struct Floating;
pub struct PullUp;
pub struct Output;

impl<const P: u8> Pin<P, Input<Floating>> {
    pub fn into_pull_up_input(self) -> Pin<P, Input<PullUp>> {
        // SAFETY: szimulált konfiguráció; a valódi regiszter-hozzáférés
        // invariánsait a PAC dokumentációja adja.
        unsafe { configure_input_pull_up(P) };
        Pin { _mode: PhantomData }
    }

    pub fn into_push_pull_output(self) -> Pin<P, Output> {
        // SAFETY: szimulált konfiguráció.
        unsafe { configure_push_pull_output(P) };
        Pin { _mode: PhantomData }
    }
}

impl<const P: u8> Pin<P, Output> {
    pub fn set_high(&mut self) {
        // SAFETY: az Output mód birtoklása kizárja, hogy bemeneti regisztert
        // írnánk; a &mut self biztosítja a kizárólagos hozzáférést.
        unsafe { write_output_high(P) };
    }

    pub fn set_low(&mut self) {
        unsafe { write_output_low(P) };
    }
}

unsafe fn configure_input_pull_up(_pin: u8) {}
unsafe fn configure_push_pull_output(_pin: u8) {}
unsafe fn write_output_high(_pin: u8) {}
unsafe fn write_output_low(_pin: u8) {}

A cargo build parancs a rkv-embedded könyvtárban a no_std könyvtárcrate-et sikeresen lefordítja.

  1. A LED megosztásához két task között embassy_sync::Mutex<...> típust érdemes használni, mert az Embassy runtime-hoz illeszkedő, async-barát mutex, amely nem blokkolja a taskokat. A kódváz:
// rust (vázlat)
use embassy_sync::Mutex;
use embassy_sync::blocking_mutex::raw::CriticalSectionRawMutex;

struct SharedLed {
    led: Mutex<CriticalSectionRawMutex, Option<Led>>,
}

#[embassy_executor::task]
async fn blink(shared: &'static SharedLed) {
    let mut guard = shared.led.lock().await;
    if let Some(led) = guard.as_mut() {
        led.toggle();
    }
}

A static élettartam itt a beágyazott világban gyakori, mert a periféria-singletonok általában a program teljes életére szólnak. A pontos Embassy-szinkronizációs típus neve és a CriticalSectionRawMutex elérhetősége verziófüggő; a fenti vázlat ellenőrzést igényel.

23.1.10 Rövid összefoglaló

A no_std környezet a std könyvtár elhagyását jelenti, de a core mindig elérhető, az alloc opcionális. A beágyazott Rust-ökoszisztéma rétegei: PAC → HAL → embedded-hal traitek → driverek. A perifériák szingletonok, a take() egyszeri ownershipet ad. A typestate minta a GPIO-láb üzemmódját típusparaméterként kezeli, így a Pin<P, Output> típus rendelkezik set_high metódussal, a Pin<P, Input<Floating>> nem. Az Embassy a Rust async modellt viszi beágyazott környezetbe: a Timer::after(...).await megszakításvezérelt ébresztéssel várakozik, miközben más taskok futhatnak. A #![no_std] binárisban #![no_main] és #[panic_handler] szükséges. Továbbvitt eredmény. A Összefoglalás: C++→Rust fordítási kézikönyv és továbbtanulás ezt a rétegződést és a no_std-elméletet használja tovább: a beágyazott és host-oldali Rust ugyanazokra a típusrendszeri alapokra épül, és a C++-ból hozott minták itt is az ownership, a generikusok és a trait-ek nyelvére fordíthatók.

23.1.11 Források és ellenőrzési hiányok

  • A Rust Reference #![no_std], #![no_main] és panic_handler leírása a doc.rust-lang.org-on elérhető, de a konkrét szakaszok verziófüggők.
  • Az embedded-hal trait-dokumentációja a docs.rs-en ellenőrzendő; az 1.x-es OutputPin::set_high/set_low szignatúrája a felhasznált főverzió szerint változhat.
  • Az Embassy embassy-executor, embassy-time és embassy-sync API-ja gyorsan fejlődik; a kódvázlatokban jelzett típusokat és makrókat a jelenlegi stable toolchainre a docs.rs-en ellenőrizni kell.
  • A QEMU-val történő emuláció pontos beállításait és a cortex-m-rt linker-szkriptjének aktuális leírását a kapcsolódó dokumentációval kell ellenőrizni.
  • A heapless::Vec főverziója és no_std-kompatibilitása a crate aktuális dokumentációjában ellenőrizendő.
