21.1 Newtype, PhantomData, typestate és const generikusok

21.1.1 Motiváció

A C++ típusrendszere sok esetben túl megengedő. Ha egy függvény métert és másodpercet vár, akkor is elfogad két double értéket, ha véletlenül felcseréljük őket. Hasonlóképpen egy std::string azonosító és egy felhasználónév ugyanaz a típus, ezért a fordító nem jelez, ha a kettőt összekeverjük. A sablonok és a std::array méretei fordítási időben ismertek, de a típusok közötti kapcsolatokat – például azt, hogy egy mátrixszorzás csak akkor lefordítható, ha a belső dimenziók egyeznek – nem mindig lehet természetesen kifejezni. Végül a C++ std::true_type/std::false_type tag dispatch technikája működik, de zajos és nem közvetlenül az állapotátmeneteket modellezi.

A Rust válasza: a típusrendszer aktív tervezési eszköz. A newtype minta új, egymással nem összekeverhető típusokat hoz létre; a typestate minta az objektum állapotát a típusparaméterbe kódolja; a PhantomData a birtoklási és variancia-információkat teszi explicitté; a const generikusok pedig a méreteket teszik a típus részévé. Ezáltal a hibás állapotátmenetek, a mértékegység-keverések és a rossz méretű mátrixok már fordítási időben kizárhatók.

21.1.2 Fogalmak és szabályok

21.1.2.1 Newtype

Definíció. A newtype olyan tuple-struct, amely pontosan egy mezőt tartalmaz, és célja, hogy a belső típusból új, elkülönült típust hozzon létre anélkül, hogy futásidőben extra költséget jelentene.

Szabály. A newtype típus nem örökli a belső típus trait-implementációit; a kívánt viselkedést derive-tal vagy kézi delegálással kell biztosítani. A newtype megkerüli az orphan rule-t, mert a saját típusunkra idegen traitet is implementálhatunk.

A mértékegység-biztonság érdekében a newtype a leghatékonyabb eszköz: Meters(f64) és Seconds(f64) külön típusok, így az m + s kifejezés fordítási hibát ad.

21.1.2.2 Typestate

Definíció. A typestate olyan programtervezési minta, amelyben az objektum állapota a típus paramétere, és az állapotváltó műveletek új típusú értéket adnak vissza, miközben a régi értéket elfogyasztják.

Szabály. A Connection<S> generikus típus S paramétere jelöli az állapotot (Closed, Open). Az impl Connection<Closed> blokkban definiált open metódus Connection<Open>-t ad vissza, az impl Connection<Open> blokkban definiált close pedig Connection<Closed>-t. A send csak a Connection<Open> impl blokkban létezik, így a Connection<Closed>-on való hívása fordítási hibát ad (E0599, „method not found”).

21.1.2.3 PhantomData

Definíció. A PhantomData<T> zéró méretű marker típus, amely azt jelzi a fordítónak, hogy a struktúra úgy viselkedik, mintha T típusú értéket birtokolna – anélkül, hogy valóban tárolná.

Szabály. Ha egy struct típusparamétert vagy lifetime-ot deklarál, de az nem jelenik meg a mezőiben, akkor a PhantomData szükséges a helyes birtoklási, élettartam- és variancia-információk megadásához. A PhantomData<&'a T> covariant 'a és T felett, míg a PhantomData<fn(T)> és a PhantomData<Cell<T>> invariant T felett.

21.1.2.4 Const generikusok

Definíció. A const generikus olyan generikus paraméter, amely értéket (pl. usize méretet) vesz fel, nem típust. A Rust a const kulcsszóval jelöli, például struct Matrix<T, const R: usize, const C: usize>.

Szabály. A const generikusok a típus részévé teszik a méretet, így a fordító ellenőrizni tudja a méretkompatibilitást. Például a [[T; C]; R] mezőben R és C a típusparaméterek, így minden (R, C) kombináció külön típust alkot.

21.1.3 C++ ↔︎ Rust összevetés

21.1.3.1 Strong typedef és newtype

C++-ban a strong typedef általában egy wrapper osztályt jelent:

class Meters {
    double v_;
public:
    explicit Meters(double v) : v_(v) {}
    double value() const { return v_; }
};

Meters operator+(Meters a, Meters b) {
    return Meters(a.value() + b.value());
}

Rustban ugyanez a newtype minta:

#[derive(Debug, Clone, Copy, PartialEq)]
struct Meters(f64);

impl std::ops::Add for Meters {
    type Output = Self;
    fn add(self, rhs: Self) -> Self {
        Meters(self.0 + rhs.0)
    }
}

A különbség: a Rust newtype nem enged implicit konverziót, és a derive(Clone, Copy) automatikusan érték szerint másolhatóvá teszi, míg a C++ wrapper kézzel írt másoló konstruktort és operátorokat igényel. Ráadásul a Rust newtype zéró költségű absztrakció: a Meters ábrázolása azonos az f64-ével.

21.1.3.2 Tag dispatch és typestate

C++-ban a tag dispatch funkciótúlterheléssel és tag típusokkal oldjuk meg:

template <typename T>
void process(T x, std::true_type) { /* integral */ }

template <typename T>
void process(T x, std::false_type) { /* not integral */ }

template <typename T>
void process(T x) {
    process(x, std::is_integral<T>{});
}

Rustban a typestate minta az állapotokat típusparaméterként kezeli, és a metódusok rendelkezésre állása az állapottól függ. Ez közvetlenebbül fejezi ki az állapotgépet, és a hibás állapotátmenet nem fordítható le.

21.1.3.3 Const generikusok és std::array

C++-ban a méretet sablonparaméterként adjuk meg:

template <typename T, std::size_t R, std::size_t C>
struct Matrix {
    std::array<std::array<T, C>, R> data;
};

Rustban a const generikus ugyanezt a célt szolgálja:

struct Matrix<T, const R: usize, const C: usize> {
    data: [[T; C]; R],
}

A Rust verzióban a típusrendszer automatikusan garantálja, hogy Matrix<f64, 3, 4> és Matrix<f64, 4, 3> különböző típusok, ezért a nem megfelelő méretű mátrixszorzás mul metódusa nem fordítható le.

21.1.4 Kidolgozott példa: typestate Connection

Vegyünk egy hálózati kapcsolatot, amely lehet zárt (Closed) vagy nyitott (Open). Zárt állapotban az open hívható, de a send nem; nyitott állapotban a send és a close hívható.

use std::marker::PhantomData;

struct Closed;
struct Open;

struct Connection<State> {
    addr: String,
    state: PhantomData<State>,
}

impl Connection<Closed> {
    pub fn new(addr: impl Into<String>) -> Self {
        Connection {
            addr: addr.into(),
            state: PhantomData,
        }
    }

    pub fn open(self) -> Result<Connection<Open>, std::io::Error> {
        // A valóságban itt TCP-kapcsolatot nyitnánk.
        Ok(Connection {
            addr: self.addr,
            state: PhantomData,
        })
    }
}

impl Connection<Open> {
    pub fn send(&self, data: &[u8]) -> Result<usize, std::io::Error> {
        // Itt küldenénk a hálózaton keresztül.
        Ok(data.len())
    }

    pub fn close(self) -> Connection<Closed> {
        Connection {
            addr: self.addr,
            state: PhantomData,
        }
    }
}

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let conn = Connection::new("localhost:8080");
    // conn.send(b"hello")?; // Ez a sor fordítási hibát ad!
    let conn = conn.open()?;
    let n = conn.send(b"hello")?;
    println!("{n} bájt elküldve");
    let _conn = conn.close();
    Ok(())
}

A hibás sor kommentezve van. Ha ténylegesen beírjuk, a fordító a következőhöz hasonló hibát ad (a pontos szöveg verziófüggő):

error[E0599]: no method named `send` found for struct `Connection<Closed>` in the current scope
 --> src/main.rs:...
  |
  |     conn.send(b"hello")?;
  |         ^^^^ method not found in `Connection<Closed>`

A javítás: először open-nel nyissuk meg a kapcsolatot, és csak utána hívjuk a send-et, ahogy a fenti kódban tesszük.

flowchart LR
    A[Connection<Closed>] -->|open()| B[Connection<Open>]
    B -->|send()| B
    B -->|close()| A

A fenti ábra a Connection típus állapotátmeneteit mutatja. A send csak az Open állapotban létezik, ezért a zárt állapotban való hívása fordítási hibát ad. Ez a typestate minta lényege: az állapotgép érvénytelen átmenetei a típusrendszer segítségével kizárhatók.

21.1.5 Tipikus hibák és átállási csapdák

  1. Új típus létrehozása Deref implementációval a belső típusra. Bár a Deref kényelmes lehet, hogy a newtype gyakorlatilag úgy viselkedjen, mint a belső típus, ez megtöri az absztrakciót, és visszahozza az implicit konverzió problémáját. Helyette explicit metódusokat vagy a From/Into konverziókat használjunk, ha szükséges.

  2. A PhantomData elfelejtése. Ha egy struktúra típusparamétert deklarál, de nem használja azt egyetlen mezőben sem, a fordító a „parameter T is never used” hibát ad. A megoldás egy PhantomData<T> mező felvétele. Hasonlóan, ha a lifetime paraméter nem jelenik meg, a PhantomData<&'a ()> jelzi az élettartam-kötést.

  3. A const generikusok túlzott használata. Ha minden méretet const generikussá teszünk, a monomorfizáció miatt sok különböző típus jön létre, ami növeli a fordítási időt és a bináris méretét. Csak akkor használjunk const generikust, ha a méret valóban a típus részét kell képezze (pl. mátrixműveletek, fix méretű pufferek), és ne akkor, ha a méret csak futásidőben ismert.

  4. A typestate és az enum összekeverése. Bár az enum is modellezhet állapotokat, a typestate minta előnye, hogy a hibás metódushívás már fordítási időben kiderül, míg az enum esetén a match futásidőben kezeli az állapotokat. A typestate különösen akkor hasznos, ha az állapotokhoz eltérő metóduskészletek tartoznak.

21.1.6 Feladatok

21.1.6.1 a) Lefordul-e és miért?

Az alábbi kód szándékosan tartalmaz egy hibát. Fordulna-e le? Ha nem, miért? Mi a pontos hibakód?

use std::marker::PhantomData;

struct Closed;
struct Open;

struct Connection<S> {
    state: PhantomData<S>,
}

impl Connection<Closed> {
    fn new() -> Self {
        Connection { state: PhantomData }
    }
    fn open(self) -> Connection<Open> {
        Connection { state: PhantomData }
    }
}

impl Connection<Open> {
    fn send(&self) {}
    fn close(self) -> Connection<Closed> {
        Connection { state: PhantomData }
    }
}

fn main() {
    let conn = Connection::<Closed>::new();
    conn.send();
}

21.1.6.2 b) C++ kód átírása idiomatikus Rustra

Adott a következő C++ strong typedef osztály:

class UserId {
    int value_;
public:
    explicit UserId(int v) : value_(v) {}
    int value() const { return value_; }
    bool operator==(UserId rhs) const { return value_ == rhs.value_; }
};

Írj Rust newtype-ot, amely UserId(u32) néven definiálja a típust, Copy, Clone, Debug, PartialEq, Eq, Hash és Ord tulajdonságokkal, és adj hozzá egy From<UserId> for u32 és From<u32> for UserId konverziót! Mutasd meg, hogyan lehet UserId értéket HashMap kulcsaként használni.

21.1.6.3 c) Implementálj Session typestate-et az rkv-serverben

Az rkv-server crate-ben hozz létre egy Session<State> típust, amely egy TcpStream-et és egy állapotot tárol. Az állapotok: Anonymous és Authenticated { user: String }. Az Anonymous állapotban a new és az authenticate metódusok, az Authenticated állapotban a user és a logout metódusok érhetők el. Az authenticate ellenőrizze a jelszót (pl. konstans felhasználónév/jelszó pár), és hiba esetén adja vissza a Session<Anonymous>-t? (Tipp: a sikeres hitelesítés után Session<Authenticated> jön létre; a hibás jelszó esetén a self-et visszaadhatjuk, vagy Result-et használhatunk.) A user metódus adja vissza a bejelentkezett felhasználó nevét. Gondoskodj arról, hogy a logout után ne lehessen user-t hívni. Ez a feladat előkészíti az API-tervezés Rustban alfejezetben tárgyalt ergonomikus API-kat.

21.1.6.4 d) Refaktorálás: PhantomData hozzáadása

Adott egy nyers mutatót tároló struktúra, amelyből hiányzik a PhantomData:

struct RawBuffer<T> {
    ptr: *mut T,
    len: usize,
}

Ez a kód lefordul? Ha nem, miért? Ha igen, milyen problémák merülhetnek fel a varianciával és a birtoklással kapcsolatban? Írd át a struktúrát úgy, hogy a típus helyesen jelezze a birtoklást és a varianciát! Milyen PhantomData típust választanál, ha a RawBuffer a T-t birtokolja, és miért?

21.1.7 Megoldások

21.1.7.1 a) Lefordul-e és miért?

Nem fordul le. A Connection<Closed> típuson nincs send metódus, mert az csak a Connection<Open> impl blokkban van definiálva. A hiba kódja E0599 (method not found). A megoldás az, hogy előbb open-nel nyissuk meg a kapcsolatot, és csak utána hívjuk a send-et, vagy távolítsuk el a hibás hívást.

21.1.7.2 b) C++ kód átírása idiomatikus Rustra

use std::collections::HashMap;

#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, PartialOrd, Ord)]
struct UserId(u32);

impl From<UserId> for u32 {
    fn from(id: UserId) -> Self {
        id.0
    }
}

impl From<u32> for UserId {
    fn from(v: u32) -> Self {
        UserId(v)
    }
}

fn main() {
    let mut map = HashMap::new();
    let id = UserId::from(42);
    map.insert(id, "Alice");
    let raw: u32 = id.into();
    println!("{raw}");
    assert_eq!(map.get(&UserId(42)), Some(&"Alice"));
}

A derive(Eq, Hash, Ord) lehetővé teszi a HashMap kulcsként való használatot. A From implementációk explicit konverziót biztosítanak a newtype és a belső típus között.

21.1.7.3 c) Session typestate az rkv-serverben

Hozz létre egy session.rs fájlt az rkv-server/src/ könyvtárban:

// rkv-server/src/session.rs
use std::net::TcpStream;

pub struct Anonymous;
pub struct Authenticated {
    user: String,
}

pub struct Session<State> {
    conn: TcpStream,
    state: State,
}

impl Session<Anonymous> {
    pub fn new(conn: TcpStream) -> Self {
        Session {
            conn,
            state: Anonymous,
        }
    }

    pub fn authenticate(
        self,
        user: &str,
        password: &str,
    ) -> Result<Session<Authenticated>, (Session<Anonymous>, AuthError)> {
        // Egyszerű konstans ellenőrzés; valós alkalmazásban adatbázisból jönne.
        if user == "admin" && password == "secret" {
            Ok(Session {
                conn: self.conn,
                state: Authenticated {
                    user: user.to_string(),
                },
            })
        } else {
            Err((self, AuthError::InvalidCredentials))
        }
    }
}

impl Session<Authenticated> {
    pub fn user(&self) -> &str {
        &self.state.user
    }

    pub fn run_command(&mut self, _cmd: crate::Command) -> crate::Response {
        // Itt hajtanánk végre a parancsot.
        crate::Response::Ok
    }

    pub fn logout(self) -> Session<Anonymous> {
        Session {
            conn: self.conn,
            state: Anonymous,
        }
    }
}

#[derive(Debug)]
pub enum AuthError {
    InvalidCredentials,
}

impl std::fmt::Display for AuthError {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        match self {
            AuthError::InvalidCredentials => write!(f, "invalid credentials"),
        }
    }
}

impl std::error::Error for AuthError {}

A main.rs-ben a modul betöltése és a használat:

mod session;

fn main() {
    // Tegyük fel, hogy van egy TcpStream.
    let stream = std::net::TcpStream::connect("127.0.0.1:8080").unwrap();
    let sess = session::Session::new(stream);
    match sess.authenticate("admin", "secret") {
        Ok(sess) => {
            println!("Bejelentkezve: {}", sess.user());
            // sess.user(); // logout után nem elérhető.
            let _anon = sess.logout();
        }
        Err((_sess, e)) => {
            eprintln!("Hiba: {e}");
        }
    }
}

Ez a példa mutatja, hogy a user metódus csak hitelesített állapotban hívható, a logout pedig visszaad egy névtelen Session-t, így a típusrendszer garantálja az állapotok helyes sorrendjét.

21.1.7.4 d) Refaktorálás: PhantomData hozzáadása

Az eredeti RawBuffer<T> kód lefordul, mert a T paraméter megjelenik a ptr mező típusában (*mut T), így a fordító nem panaszkodik. Azonban a nyers mutató nem ad birtoklási információt: a RawBuffer lehet, hogy birtokolja a T-t, de a típus ezt nem jelzi. Emellett a *mut T varianciája covariant, ami nem mindig megfelelő. Ha a RawBuffer birtokolja a T-t, akkor a típusnak invariantnak kell lennie T felett, hogy elkerüljük a típusbiztonsági réseket. A megoldás:

use std::marker::PhantomData;
use std::cell::Cell;

struct RawBuffer<T> {
    ptr: *mut T,
    len: usize,
    _marker: PhantomData<Cell<T>>, // invariáns T felett, birtoklást jelez
}

A PhantomData<Cell<T>> invariánssá teszi a típust T felett, és azt jelzi, hogy a RawBuffer birtokolja a T-t. Ha csak covariancia kellene, PhantomData<T> is elég lenne; ha nem birtokoljuk a T-t, akkor PhantomData<&'a T> vagy PhantomData<*const T> lehetne a megfelelő choice. A Cell a belső mutabilitás miatt invariáns, ezért gyakran használják, ha a típus ténylegesen módosítható adatot tárol.

21.1.8 Rövid összefoglaló

Ebben az alfejezetben a Rust típusrendszerének haladó eszközeit tanulmányoztuk. A newtype minta tuple-struct egyetlen mezővel új, típusbiztos típust hoz létre, amely megkerüli az orphan rule-t, és nem örökli a belső típus traiteket. A typestate minta az állapotot típusparaméterként kezeli: a Connection<Closed> és Connection<Open> típusokra külön impl blokkok biztosítják a megfelelő metódusokat, így a hibás állapotátmenetek fordítási hibát adnak (E0599). A PhantomData<T> zéró méretű marker, amely a birtoklást, az élettartamot és a varianciát jelzi, például PhantomData<Cell<T>> invariáns T felett. A const generikusok, mint a Matrix<T, const R: usize, const C: usize>, a méreteket a típus részévé teszik, így a mátrixműveletek méretkompatibilitása fordítási időben ellenőrizhető. Továbbvitt eredmények: a typestate minta és a Session<State> típus (rkv-server/src/session.rs) előkészíti az API-tervezés Rustban alfejezet ergonomikus API-irányelveit, valamint az no_std, embedded-hal és Embassy beágyazott állapotgépeit.

21.1.9 Források és ellenőrzési hiányok

A leírt nyelvi szabályok a stabil Rust Reference és a The Rust Programming Language dokumentációjából származnak; ezek a newtype, typestate, PhantomData és const generikusok esetében régóta stabilak. A const generikusok már stabilak, de a használatuk bizonyos korlátai (pl. adt_const_params nightly feature) nem részei ennek az anyagnak. A crate-ek (pl. thiserror, serde) verziói a Cargo.toml-ban főverzióval adhatók meg, és a pontos API-t a docs.rs-en ellenőrizni kell. A hibaüzenetek (pl. E0599) kódja stabil, de a pontos szöveg verziófüggő. A forráskiindulópontok a Rust API Guidelines, a Rust Reference és a Rust Book, de ezeket ebben a kérésben nem tudtam közvetlenül ellenőrizni.
