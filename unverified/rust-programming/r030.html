14.1 Vec, HashMap, BTreeMap és társaik; az Entry API

A C++ STL-ben a konténerválasztás sokszor rutinszerű: std::vector az általános dinamikus tömb, std::map a rendezett asszociatív tároló, std::unordered_map a hash-alapú. Rustban a Vec, a BTreeMap és a HashMap hasonló szerepet töltenek be, de az alapértelmezések eltérnek, és a Rust-idiómák más megoldásokat kínálnak a gyakori frissítési mintákra. Ez az alfejezet a legfontosabb std-gyűjteményeket, a választási szempontokat és az Entry API-t tárgyalja, majd az rkv mintaprojektet rendezett tárolóra állítja át.

14.1.1 Fogalmak és szabályok

Definíció. A Rust std könyvtárának gyűjteményei (collections) a C++ STL-hez hasonlóan adatszerkezeteket valósítanak meg, de a tulajdonlási és kölcsönzési szabályokkal összhangban. A főbb típusok:

  • Vec<T>: folytonos, dinamikusan növekvő tömb; a std::vector<T> megfelelője.
  • VecDeque<T>: két végén bővíthető sor (deque); a std::deque<T>-hez hasonló, de Rustban egyetlen gyűrűpuffer, nem blokkokból áll.
  • LinkedList<T>: láncolt lista; a std::list<T> megfelelője, de ritkán használjuk.
  • HashMap<K, V>: hash-tábla, rendezetlen; a std::unordered_map<K, V>-nek felel meg.
  • BTreeMap<K, V>: B-fa alapú, kulcs szerint rendezett asszociatív tároló; a std::map<K, V> megfelelője.
  • HashSet<K> és BTreeSet<K>: halmazok; a std::unordered_set és std::set megfelelői.

Szabály. A Rust gyűjtemények komplexitási garanciái hasonlóak az STL-hez: Vec O(1) indexelés, amortizált O(1) push; VecDeque O(1) beszúrás mindkét végén; HashMap átlagosan O(1) művelet; BTreeMap O(log n) beszúrás, keresés, törlés. A BTreeMap iterációja kulcs szerint rendezett, a HashMap iterációja tetszőleges sorrendű.

Szabály. A HashMap alapértelmezett hasherje a Rustban a SipHash családba tartozik, amely véletlenszerű kulcsot használ, és DoS-támadások ellen véd. Ez biztonságosabb, de általában lassabb, mint a C++ std::unordered_map gyakori implementációi. Ha a teljesítmény kritikus, és a kulcsok nem támadhatók, a BuildHasher paraméterrel más hasher (például a FxHashMap a rustc-hash crate-ből) állítható be.

14.1.2 C++ ↔︎ Rust összevetés

A legfontosabb különbség: a C++-ban a rendezett std::map a klasszikus asszociatív tároló, a Rustban a HashMap az alapértelmezett, a BTreeMap a rendezett alternatíva. Ezt tükrözi az alábbi táblázat:

C++ STL típus Rust típus Rendezett Komplexitás
std::vector<T> Vec<T> nem O(1) index; amortizált O(1) push_back
std::deque<T> VecDeque<T> nem O(1) beszúrás elején és végén
std::list<T> LinkedList<T> nem O(1) beszúrás bárhol, de nincs O(1) index
std::unordered_map<K,V> HashMap<K,V> nem átlagos O(1)
std::map<K,V> BTreeMap<K,V> igen, kulcs szerint O(log n)
std::unordered_set<K> HashSet<K> nem átlagos O(1)
std::set<K> BTreeSet<K> igen O(log n)

A C++-ban a std::map rendezett, ezért a Rust fejlesztők gyakran tévesen a HashMap-et tekintik rendezettnek. Rustban a rendezetlen tároló a HashMap, a rendezett a BTreeMap.

A Vec és a std::vector működése szinte azonos. A kapacitás és az újrafoglalás is hasonló: a Vec capacity() metódusa, with_capacity(), reserve(), shrink_to_fit() mind ugyanúgy viselkednek, mint a C++ megfelelői. A különbség a mozgatásban rejlik: ha a Vec újrafoglaláskor mozgatja az elemeket, a Copy típusok másolódnak, a nem Copy típusok destruktív mozgatást szenvednek el, ami után a régi elemek nem érvényesek. Ez a Rust mozgatási szemantikájának következménye.

A LinkedList Ritkán használjuk, mert rossz a cache-lokalitása, és nem biztosít O(1) indexelést. A C++ std::list-hez hasonlóan akkor hasznos, ha gyakori a tetszőleges pozíciójú beszúrás és törlés, és nincs szükség indexelésre. A Rust közösség javaslata szerint a legtöbb esetben Vec vagy VecDeque jobb választás.

14.1.3 Az Entry API

Definíció. Az Entry API a HashMap és BTreeMap asszociatív tárolók frissítési mintáját egyszerűsíti. Az entry(key) metódus egy Entry enumot ad vissza, amelynek két variánsa: Occupied (a kulcs létezik) és Vacant (a kulcs nem létezik). Az Entry objektum lehetővé teszi, hogy egyetlen kereséssel beszúrjunk vagy módosítsunk egy értéket, elkerülve a dupla keresést és a kölcsönzési konfliktusokat.

Szabály. A HashMap::entry és BTreeMap::entry metódusok &mut self-et igényelnek, és Entry objektumot adnak vissza. Az or_insert(default) beszúrja a default értéket, ha a kulcs hiányzik, és visszaad egy &mut V-t; az or_insert_with(f) lustán hívja az f függvényt; az and_modify(closure) csak meglévő érték esetén futtatja a closure-t.

A C++-ban a tipikus frissítési minta:

std::unordered_map<std::string, int> counters;
for (const auto& word : words) {
    auto it = counters.find(word);
    if (it == counters.end()) {
        counters.emplace(word, 1);
    } else {
        ++it->second;
    }
}

Rustban ugyanez az Entry API-val:

use std::collections::HashMap;

let mut counters: HashMap<String, i32> = HashMap::new();
for word in words {
    let count = counters.entry(word).or_insert(0);
    *count += 1;
}

A Rust verzió egyetlen keresést végez, és a kölcsönzés-ellenőrző számára is biztonságos, mert az entry egyetlen &mut kölcsönzést tart fenn a teljes művelet alatt.

14.1.4 Kölcsönzési szabály és gyűjteménykezelés

A get_mut metódus mutable referenciát ad vissza, amely a térkép kölcsönzését jelenti. Ha ugyanabban a hatókörben ezután a térképet újra módosítani próbáljuk, a borrow checker hibát ad:

let mut map = HashMap::new();
map.insert("alma", 1);
let value = map.get_mut("alma").unwrap();
map.insert("korte", 2);   // hiba: a map-et már mutable-ként kölcsönöztük
*value += 1;

Ez a kód szándékosan nem fordul le:

error[E0499]: cannot borrow `map` as mutable more than once at a time

A pontos hibaüzenet verziófüggő, de a hibakód stabil. A probléma az, hogy a get_mut visszaadott &mut referenciájának élettartama a map kölcsönzéséhez kötött, és az insert újabb &mut-ot igényel. Az Entry API ezt a problémát elegánsan megoldja, mert a teljes frissítési művelet egyetlen kölcsönzésen belül marad:

map.entry("korte").or_insert(2);
if let Some(value) = map.get_mut("alma") {
    *value += 1;
}

14.1.5 Labor: rkv BTreeMap-re váltása rendezett listázáshoz és tartomány-lekérdezéshez

Munkakönyvtár: ~/rust-labor/rkv/

A korábbi fejezetekben az rkv-core crate Store típusa HashMap<String, Vec<u8>>-at használt belső tárolóként. Most áttérünk BTreeMap-re, hogy a List parancs kulcsai rendezettek legyenek, és tartomány-lekérdezést is támogassunk.

  1. Nyissuk meg a rkv-core/src/store.rs fájlt, és ellenőrizzük a jelenlegi Store definíciót. A items mező típusa valószínűleg HashMap<String, Vec<u8>>.

  2. Cseréljük le az importot:

use std::collections::HashMap;

helyett:

use std::collections::BTreeMap;
  1. Módosítsuk a Store structot:
pub struct Store {
    items: BTreeMap<String, Vec<u8>>,
}
  1. A Store::new metódusban a konstruktor hívását is frissítsük:
items: BTreeMap::new(),

  1. A List parancs kiszolgáló metódusa már eddig is self.items.keys()-t használt, ami mostantól kulcs szerint rendezett sorrendben adja vissza az elemeket. Ha a metódus a Vec<String>-et épít, nincs más teendő; a rendezés automatikus.

  2. Adjunk hozzá egy range metódust a Store-hoz, amely a BTreeMap::range-re támaszkodik:

pub fn range(&self, start: &str, end: &str) -> impl Iterator<Item = (&str, &[u8])> + '_ {
    self.items
        .range(start.to_string()..end.to_string())
        .map(|(k, v)| (k.as_str(), v.as_slice()))
}

A range metódus a start és end kulcsok közötti tartományt adja vissza (a start zárt, az end nyitott intervallum). A visszaadott iterátor a &self-hez kötött élettartammal rendelkezik, ezért kell a + '_ az impl Iterator szignatúrájában. A start.to_string()..end.to_string() ideiglenes Range<String> objektumot hoz létre, de a BTreeMap::range ezt azonnal feldolgozza, nem tárolja el.

  1. Írjunk egy tesztet a store.rs alján található #[cfg(test)] modulban:
#[test]
fn range_returns_ordered_subset() {
    let mut store = Store::new();
    store.insert("a".into(), vec![1]);
    store.insert("b".into(), vec![2]);
    store.insert("c".into(), vec![3]);
    let got: Vec<_> = store
        .range("a", "c")
        .map(|(k, v)| (k.to_string(), v.to_vec()))
        .collect();
    assert_eq!(
        got,
        vec![
            ("a".to_string(), vec![1]),
            ("b".to_string(), vec![2]),
        ]
    );
}
  1. Futtassuk a teszteket:
cargo test -p rkv-core

Várható kimenet: minden teszt sikeres.

  1. Ellenőrizzük, hogy a rkv-cli is lefordul:
cargo build -p rkv-cli

Eredmény: Az rkv-core Store típusa mostantól BTreeMap<String, Vec<u8>>-at használ, a List parancs kimenete rendezett, és a Store rendelkezik egy range metódussal.

Továbbvitt eredmény. Az rkv-core Store típusa ezen a ponton rendezett tárolót használ (BTreeMap<String, Vec<u8>>), és új range metódust kap. Ezt a rendezett tárolót teszi szálbiztossá a Mutex, RwLock, csatornák és a megosztott rkv alfejezet, a teljesítményét méri a Teljesítmény: mérés, profilozás, allokáció, release-beállítások alfejezet, és a záróprojekt is erre épít.

14.1.6 Tipikus hibák és átállási csapdák

  1. Klónozás a borrow checker “legyőzésére”. Amikor egy get_mut hívás után a térképet módosítani kell, a fejlesztő klónozza a kulcsot, hogy kikerülje a kölcsönzési konfliktust. Ez felesleges allokációhoz vezet. Az Entry API a helyes megoldás: map.entry(key).and_modify(...).or_insert(...).

  2. LinkedList használata std::list-et keresve. A C++ fejlesztők gyakran választanak std::list-et, mert a std::vector beszúrása a közepén O(n). Rustban a Vec ugyanez, de a legtöbb esetben a Vec vagy VecDeque jobb a cache-lokalitás miatt. A LinkedList ritkán indokolt.

  3. HashMap alapértelmezett hasher lassúságának figyelmen kívül hagyása. A Rust HashMap alapértelmezett hasherje DoS-rezisztens, de lassabb, mint a C++ std::unordered_map gyakori implementációi. Ha a kulcsok nem támadhatók, érdemes más hashert használni.

  4. unwrap a gyűjtemény-hozzáféréseknél. Az indexelés (map[&key]) panikolhat, ha a kulcs hiányzik. Használj get-et vagy az Entry API-t, amely explicit módon kezeli a hiányzó kulcsot.

14.1.7 Feladatok

  1. Lefordul-e és miért? Az alábbi Rust kód lefordul-e? Ha nem, mi a hiba oka, és hogyan javítanád idiomatikusan?
let mut map = HashMap::new();
map.insert("alma", 1);
let value = map.get_mut("alma").unwrap();
map.insert("korte", 2);
*value += 1;
  1. C++-kód átírása idiomatikus Rustra. Írd át az alábbi C++ kódot Rustra, használva az Entry API-t:
std::map<std::string, int> counters;
for (const auto& word : words) {
    auto it = counters.find(word);
    if (it == counters.end()) {
        counters.emplace(word, 1);
    } else {
        ++it->second;
    }
}

  1. Implementációs feladat az rkv-ban. Adj egy range_prefix metódust az rkv-core Store típusához, amely a megadott prefixszel kezdődő kulcsokat adja vissza rendezett sorrendben. Használd a BTreeMap::range-t, kihasználva, hogy a String lexikografikusan rendezett.

  2. Tervezési döntés. Az rkv szerverének naplózásához időbélyeg szerint rendezett eseményeket kell tárolni, és gyakran kell tartomány-lekérdezést végezni. Milyen Rust gyűjteményt választanál, és miért?

14.1.8 Megoldások

  1. A kód nem fordul le, mert a get_mut &mut kölcsönzést ad a map-re, és ez a kölcsönzés a value változó élettartamáig tart. Az insert újabb &mut-ot igényel, ami ütközik. A hiba E0499 (cannot borrow map as mutable more than once at a time). Javítás: szűkítsd a value hatókörét:
{
    let value = map.get_mut("alma").unwrap();
    *value += 1;
}
map.insert("korte", 2);

Vagy használd az Entry API-t:

map.entry("korte").or_insert(2);
if let Some(value) = map.get_mut("alma") {
    *value += 1;
}
  1. Az idiomatikus Rust megoldás:
use std::collections::BTreeMap; // vagy HashMap

let mut counters: BTreeMap<String, i32> = BTreeMap::new();
for word in words {
    *counters.entry(word).or_insert(0) += 1;
}
  1. A range_prefix metódus megvalósítása:
pub fn range_prefix(&self, prefix: &str) -> impl Iterator<Item = (&str, &[u8])> + '_ {
    let start = prefix.to_string();
    // A legnagyobb Unicode kódpont hozzáfűzésével biztosítjuk,
    // hogy minden prefixszel kezdődő kulcs a tartományba essen.
    let end = format!("{prefix}\u{10FFFF}");
    self.range(&start, &end)
}
  1. A BTreeMap (vagy BTreeSet az eseményekhez, ha a kulcs az időbélyeg) a megfelelő választás, mert kulcs szerint rendezett, így a tartomány-lekérdezések O(log n) időben elvégezhetők, és az iteráció rendezett sorrendben történik. A HashMap nem garantál rendezettséget, ezért a naplóhoz nem alkalmas.

14.1.9 Rövid összefoglaló

A Rust std gyűjteményei közül a Vec<T> a std::vector, a VecDeque<T> a std::deque, a HashMap<K,V> a std::unordered_map, a BTreeMap<K,V> az std::map, a halmazok pedig a HashSet/BTreeSet megfelelői. A legfontosabb különbség, hogy a Rust HashMap rendezetlen, a rendezett tároló a BTreeMap. Az Entry API (entry, or_insert, or_insert_with, and_modify) egyetlen kereséssel oldja meg a beszúrást és frissítést, elkerülve a dupla keresést és a kölcsönzési konfliktusokat. A laborban az rkv-core Store típusát BTreeMap<String, Vec<u8>>-ra állítottuk át, így a List parancs rendezett, és új range metódust adtunk hozzá. Továbbvitt eredmény: a rendezett Store és a range metódus alapja a későbbi szálbiztos megosztott rkv-nak, a teljesítménymérésnek és a záróprojektnek.

14.1.10 Források és ellenőrzési hiányok

A fejezet a Rust std dokumentációjára (doc.rust-lang.org/std) és a The Rust Programming Language könyv 8. fejezetére támaszkodik. A pontos API-k (pl. BTreeMap::range, HashMap::entry) a stabil Rust részei, de a szignatúrák ellenőrizhetők a docs.rs-en. A hibaüzenetek pontos szövege verziófüggő; a hibakódok stabilak. A BTreeMap belső implementációja B-fa, de a pontos invariánsok nem része a stabil szerződésnek. A Vec újrafoglalási stratégiája nem garantált, bár gyakorlatban duplázó. Az rkv labor feltételezi a korábbi fejezetekben kialakított Store struktúrát; ha az érték típusa korábban String volt, akkor a Vec<u8>-ra váltást is jelezni kell.
