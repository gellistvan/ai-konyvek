16.2 Mutex, RwLock, csatornák és a megosztott rkv

16.2.1 Motiváció

C++-ban a szálbiztos megosztott állapot kézi fegyelmet igényel: a std::mutex és a védett adat külön tagváltozók, és a fordító nem tudja, melyik zár melyik adatot védi. Ha elfelejtünk lock_guard-ot írni, adatversenyt kapunk; ha rossz sorrendben zárunk, holtpontot. A Rust ezt a típust egyesíti: a Mutex<T> és az RwLock<T> birtokolja a védett értéket, és a zár megszerzése egy RAII guardot ad, amelyen keresztül csak a zár élettartama alatt férhetünk az adathoz. Ez a Belső mutabilitás: Cell, RefCell és a futásidejű kölcsönzés alfejezetben megismert RefCell<T> szálbiztos párja: a zár futásidejű kölcsönzést valósít meg, de ott nem pánikol kölcsönzési szabálysértéskor, hanem blokkol.

16.2.2 Fogalmak és szabályok

Definíció. A std::sync::Mutex<T> kölcsönös kizárást (mutual exclusion) biztosító szinkronizációs primitív. A T érték a zár mögött él; a lock() metódus LockResult<MutexGuard<'_, T>> értéket ad vissza. A MutexGuard<'_, T> egy RAII guard, amely Deref<T>-et és DerefMut<T>-et implementál, tehát &T-ként vagy &mut T-ként használható. Amikor a guard eldobódik (például kimegy a hatókörből), a zár automatikusan felszabadul.

Szabály. A Mutex<T> akkor Sync, ha T: Send; a MutexGuard<'_, T> pedig Send, ha T: Send, de soha nem Sync. Ez megakadályozza, hogy a guardot több szálon keresztül használjuk.

Definíció. A std::sync::RwLock<T> többszörös olvasó / egy író zárat biztosít. A read() metódus RwLockReadGuard-ot, a write() metódus RwLockWriteGuard-ot ad. Egyszerre több read guard élhet, de write guard csak egyedül. A RwLock nem támogatja a read-guard upgrade-jét write-guard-ra, ezért a read lock alatt nem szabad write-ot kérni ugyanarra a zárra, mert holtpontot kaphatunk.

Szabály. Ha egy szál pánikol, miközben a Mutex vagy RwLock guardot tartja, a zár mérgezetté (poisoned) válik. A következő lock()/read()/write() hívás Err(PoisonError<_>) értéket ad vissza; a belső adat az into_inner() metódussal nyerhető ki. Gyakran unwrap()-ot használunk, mert a pánik már megtörtént, és a konzisztens állapotot a pánik miatt amúgy sem garantálhatjuk.

Definíció. Az std::sync::mpsc modul több termelő, egy fogyasztó (multi-producer, single-consumer) csatornát ad. A Sender<T> klónozható, a Receiver<T> nem. A send() blokkol, ha a puffer tele van, a recv() blokkol, ha üres. Ha az összes Sender eldobódik, a recv() Err(RecvError) értékkel tér vissza, és a Receiver feletti for ciklus automatikusan leáll.

Röviden. A std::sync::Condvar feltételváltozót ad, amely egy MutexGuard-ot vár a wait() hívásakor, elengedi a zárat, amíg értesítik, majd újra megpróbálja megszerezni. Sok esetben a csatornák vagy a magasabb szintű absztrakciók kiváltják. A külső parking_lot crate gyorsabb, de API-kompatibilis alternatívát; a crossbeam csatornái pedig több fogyasztót is támogatnak (lásd az ellenőrzési hiányokat).

16.2.3 C++ ↔︎ Rust összevetés

A C++-ban a zár és az adat külön van; a védett hozzáférést minden metódusban kézzel kell biztosítani:

#include <mutex>
#include <map>
#include <string>
#include <optional>

class Store {
    std::mutex mtx;
    std::map<std::string, std::string> data;
public:
    void set(std::string key, std::string value) {
        std::lock_guard<std::mutex> lock(mtx);
        data[std::move(key)] = std::move(value);
    }
    std::optional<std::string> get(const std::string& key) {
        std::lock_guard<std::mutex> lock(mtx);
        auto it = data.find(key);
        if (it != data.end()) return it->second;
        return std::nullopt;
    }
};

Rustban a Mutex<HashMap<...>> magában foglalja a zárat és az adatot, és a metódusok &self-et vesznek, mert a zár belső mutabilitást ad:

use std::collections::HashMap;
use std::sync::Mutex;

pub struct Store {
    data: Mutex<HashMap<String, String>>,
}

impl Store {
    pub fn new() -> Self {
        Self { data: Mutex::new(HashMap::new()) }
    }

    pub fn set(&self, key: String, value: String) {
        let mut guard = self.data.lock().unwrap();
        guard.insert(key, value);
    }

    pub fn get(&self, key: &str) -> Option<String> {
        let guard = self.data.lock().unwrap();
        guard.get(key).cloned()
    }
}

A kulcskülönbség: a Rust-fordító típusrendszerrel kényszeríti ki, hogy a HashMap-et csak a MutexGuard-on keresztül érjük el. A C++-ban semmi sem akadályozza meg, hogy a data-t zár nélkül olvassuk vagy írjuk.

16.2.4 Kidolgozott példa: szálbiztos számláló

A legegyszerűbb szálbiztos megosztott állapot egy Arc<Mutex<i32>>. Több szál növeli a számlálót, és a MutexGuard RAII-ja biztosítja a zár felszabadítását:

use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..10 {
        let counter = Arc::clone(&counter);
        let handle = thread::spawn(move || {
            for _ in 0..1000 {
                let mut guard = counter.lock().unwrap();
                *guard += 1;
            }
        });
        handles.push(handle);
    }

    for handle in handles {
        handle.join().unwrap();
    }

    println!("végső érték: {}", *counter.lock().unwrap());
}

Várt kimenet (gépfüggő sorrendű, de a végső érték determinisztikus): végső érték: 10000. Ha a zár kimaradna, adatverseny jönne létre; a Rust ezt a Sync határral megakadályozza, mert a Mutex nélkül az Arc<i32> nem lenne Sync, és a thread::spawn nem fordulna le.

16.2.5 Labor: szálbiztos rkv Store és csatornás munkásszál

Munkakönyvtár: ~/rust-labor/rkv/. A labor célja az rkv-core crate Storage traitjének és MemStore implementációjának szálbiztossá tétele, egy Store wrapper bevezetése, valamint egy munkásszál-minta csatornával.

16.2.5.1 1. lépés: a Storage trait átalakítása

Keressük meg az rkv-core/src/lib.rs-ben (vagy a storage.rs modulban) a Storage traitet. A korábbi alfejezetekben a metódusok &mut self-et használtak, hogy a belső HashMap-et módosítsák. A szálbiztos változathoz minden metódus &self legyen, mert a zár belül ad mutabilitást:

// rkv-core/src/storage.rs
use std::collections::HashMap;
use std::sync::{Arc, RwLock};
use crate::error::Error;

pub trait Storage: Send + Sync {
    fn get(&self, key: &str) -> Result<Option<Vec<u8>>, Error>;
    fn set(&self, key: String, value: Vec<u8>) -> Result<(), Error>;
    fn delete(&self, key: &str) -> Result<bool, Error>;
    fn list(&self, prefix: &str) -> Result<Vec<String>, Error>;
}

A Send + Sync szuperhatárok jelzik, hogy a trait implementációi több szálon át használhatók. (A pontos hibakezelést lásd a Saját hibatípusok: enum-hibák, thiserror, anyhow alfejezetben.)

16.2.5.2 2. lépés: a MemStore szálbiztosítása

A MemStore a belső HashMap-et Arc<RwLock<...>>-ban tárolja, így a példány klónozható, és minden klón ugyanarra az állapotra mutat:

// rkv-core/src/storage.rs
#[derive(Clone)]
pub struct MemStore {
    data: Arc<RwLock<HashMap<String, Vec<u8>>>>,
}

impl MemStore {
    pub fn new() -> Self {
        Self {
            data: Arc::new(RwLock::new(HashMap::new())),
        }
    }
}

impl Storage for MemStore {
    fn get(&self, key: &str) -> Result<Option<Vec<u8>>, Error> {
        let guard = self.data.read().unwrap();
        Ok(guard.get(key).cloned())
    }

    fn set(&self, key: String, value: Vec<u8>) -> Result<(), Error> {
        let mut guard = self.data.write().unwrap();
        guard.insert(key, value);
        Ok(())
    }

    fn delete(&self, key: &str) -> Result<bool, Error> {
        let mut guard = self.data.write().unwrap();
        Ok(guard.remove(key).is_some())
    }

    fn list(&self, prefix: &str) -> Result<Vec<String>, Error> {
        let guard = self.data.read().unwrap();
        let mut keys: Vec<String> = guard
            .keys()
            .filter(|k| k.starts_with(prefix))
            .cloned()
            .collect();
        keys.sort();
        Ok(keys)
    }
}

16.2.5.3 3. lépés: a Store wrapper

A Store egy vékony, klónozható réteg az Arc<dyn Storage> felett, amely delegál a trait metódusokra. Mivel a Storage metódusai &self-et vesznek és a trait Send + Sync, az Arc<dyn Storage> szálbiztosan megosztható:

// rkv-core/src/store.rs
use std::sync::Arc;
use crate::error::Error;
use crate::storage::Storage;

#[derive(Clone)]
pub struct Store {
    inner: Arc<dyn Storage>,
}

impl Store {
    pub fn new<S: Storage + 'static>(storage: S) -> Self {
        Self {
            inner: Arc::new(storage),
        }
    }

    pub fn get(&self, key: &str) -> Result<Option<Vec<u8>>, Error> {
        self.inner.get(key)
    }

    pub fn set(&self, key: String, value: Vec<u8>) -> Result<(), Error> {
        self.inner.set(key, value)
    }

    pub fn delete(&self, key: &str) -> Result<bool, Error> {
        self.inner.delete(key)
    }

    pub fn list(&self, prefix: &str) -> Result<Vec<String>, Error> {
        self.inner.list(prefix)
    }
}

Írjunk egy tesztet, amely több szálból hajt végre SET műveleteket, majd ellenőrzi a tároló állapotát:

// rkv-core/tests/store_threads.rs

16.2.5.5 5. lépés: csatornás munkásszál-minta

A közvetlenül megosztott Store helyett gyakran kényelmesebb egy munkásszálat (worker) indítani, amely egy csatornán fogadja a parancsokat, és egy másikon küldi vissza a válaszokat. Ez centralizálja a zárolást, és a hívó szálak nem blokkolnak a záron.

Először definiáljunk egy parancs- és választípust. A Command enum hasonló a fő típusokhoz, a Response a szerver válaszait képviseli (lásd a Az rkv mintaprojekt indítása alfejezetet):

// rkv-core/src/worker.rs
use std::sync::mpsc;
use std::thread;
use crate::error::Error;
use crate::store::Store;

pub enum Command {
    Get(String),
    Set(String, Vec<u8>),
    Delete(String),
    List(Option<String>),
}

pub enum Response {
    Value(Vec<u8>),
    Ok,
    NotFound,
    List(Vec<String>),
    Err(Error),
}

pub struct Worker {
    store: Store,
    rx: mpsc::Receiver<Command>,
    tx_resp: mpsc::Sender<Response>,
}

impl Worker {
    pub fn spawn(store: Store) -> (mpsc::Sender<Command>, mpsc::Receiver<Response>) {
        let (tx_cmd, rx) = mpsc::channel();
        let (tx_resp, rx_resp) = mpsc::channel();

        let worker = Worker { store, rx, tx_resp };
        thread::spawn(move || worker.run());

        (tx_cmd, rx_resp)
    }

    fn run(&self) {
        for cmd in self.rx.iter() {
            let resp = match cmd {
                Command::Get(key) => match self.store.get(&key) {
                    Ok(Some(v)) => Response::Value(v),
                    Ok(None) => Response::NotFound,
                    Err(e) => Response::Err(e),
                },
                Command::Set(key, value) => match self.store.set(key, value) {
                    Ok(()) => Response::Ok,
                    Err(e) => Response::Err(e),
                },
                Command::Delete(key) => match self.store.delete(&key) {
                    Ok(_) => Response::Ok,
                    Err(e) => Response::Err(e),
                },
                Command::List(prefix) => {
                    let p = prefix.unwrap_or_default();
                    match self.store.list(&p) {
                        Ok(keys) => Response::List(keys),
                        Err(e) => Response::Err(e),
                    }
                }
            };
            if self.tx_resp.send(resp).is_err() {
                break; // a válaszcsatorna lezárult, nincs több kliens
            }
        }
    }
}

A spawn elindítja a munkásszálat, és visszaadja a parancssender és válaszreceiver párt. A hívó szálak a Command-okat küldik, és a Response-okat fogadják. A for cmd in self.rx.iter() ciklus automatikusan leáll, ha az összes parancssender eldobódik.

A következő diagram a munkásszál és a hívó szál közötti üzenetváltást mutatja:

A hívó oldal használata:

// rkv-cli/src/main.rs (részlet)
use rkv_core::{MemStore, Store, worker::{Command, Response}};
use std::sync::mpsc;

fn main() {
    let store = Store::new(MemStore::new());
    let (tx, rx) = rkv_core::worker::Worker::spawn(store);

    tx.send(Command::Set("nev".into(), "ertek".into_bytes())).unwrap();
    tx.send(Command::Get("nev".into())).unwrap();

    // a válaszok sorrendje megegyezik a parancsok sorrendjével
    let resp = rx.recv().unwrap(); // Response::Ok
    let resp = rx.recv().unwrap(); // Response::Value(b"ertek")
    println!("{:?}", resp); // itt a példában nem kell Debug, csak szemléltetés
}

A Response enumhoz #[derive(Debug)] szükséges, ha ki szeretnénk írni.

Több hívó szál esetén klónozzuk a tx-et, és minden szál a saját klónján keresztül küld parancsot. A munkásszál sorosan dolgozza fel őket, így a Store zárolása nem okoz versenyt sem.

16.2.6 Tipikus hibák és átállási csapdák

  1. A guard referencia kiengedése a zárból. Ha a MutexGuard-ra hivatkozó referenciát próbálunk kivinni a guard hatóköréből, a borrow checker hibázik. Például:
let guard = mutex.lock().unwrap();
let reference = &guard;
drop(guard);
println!("{}", *reference); // E0505: cannot move out of guard because it is borrowed

A hibaüzenet (E0505) arra figyelmeztet, hogy a guard eldobása után a referencia érvénytelen. A helyes megoldás, hogy a hozzáférést a guard hatókörén belül végezzük, vagy az adatot klónozzuk.

  1. Read és write lock keverése ugyanazon a záron. A RwLock read guardja mellett nem lehet ugyanazon a szálon write guardot szerezni, mert az holtponthoz vezethet. Például:
let read_guard = rwlock.read().unwrap();
let write_guard = rwlock.write().unwrap(); // itt a szál örökre vár

A megoldás: vagy ne szerezzünk write-ot read alatt, vagy használjunk try_write()-ot, és ha kell, engedjük el a read guardot előtte.

  1. Poisoning elrejtése unwrap()-pel. Ha egy szál pánikol a zár alatt, a lock().unwrap() pánikot dob, ami könnyen hibás hibakezeléshez vezet. A jobb megoldás a unwrap_or_else(|e| e.into_inner()) mintával a belső adat kinyerése, ha a pánik utáni állapot is konzisztensnek tekinthető.

  2. Csatorna lezárás nem kezelése. Ha az összes Sender eldobódik, a recv() Err-t ad. A for ciklus automatikusan leáll, de a kézi recv() hívásoknál a hiba elágazást kezelni kell, különben a program pánikolhat.

16.2.7.2 (b) C++ kód átírása idiomatikus Rustra

Az alábbi C++ osztály egy szálbiztos gyűjtőt valósít meg. Írja át Rustra Arc<Mutex<Vec<T>>> használatával úgy, hogy a push és a get_all metódusok szálbiztosak legyenek, és a típus Clone-olható legyen.

#include <mutex>
#include <vector>
#include <string>

class Collector {
    std::mutex mtx;
    std::vector<std::string> items;
public:
    void push(std::string item) {
        std::lock_guard<std::mutex> lock(mtx);
        items.push_back(std::move(item));
    }
    std::vector<std::string> get_all() {
        std::lock_guard<std::mutex> lock(mtx);
        return items;
    }
};

16.2.7.4 (d) Hibajavítás és tervezési döntés

A következő kód holtpontot okozhat két RwLock-kal. Magyarázza el, miért, és adjon két lehetséges javítást: (1) zársorrend rögzítése, (2) try_write használata visszalépéssel.

use std::sync::{Arc, RwLock};

fn transfer(from: &RwLock<i32>, to: &RwLock<i32>) {
    let mut a = from.write().unwrap();
    let mut b = to.write().unwrap();
    *a -= 1;
    *b += 1;
}

fn main() {
    let a = Arc::new(RwLock::new(10));
    let b = Arc::new(RwLock::new(20));
    // két szál: transfer(&a, &b) és transfer(&b, &a)
}

16.2.8 Megoldások

16.2.8.1 (a)

A kód lefordul, és a kimenet gépfüggő sorrendű, de mindkét szál kiírja a vektort. A Mutex zárja miatt az adathozzáférés szálbiztos; a guard a println! után automatikusan eldobódik. A handle.join() biztosítja a szál befejezését, de mivel a data Arc-ja a fő szálban is él, nincs adatverseny.

16.2.8.2 (b)

use std::sync::{Arc, Mutex};

#[derive(Clone)]
pub struct Collector {
    items: Arc<Mutex<Vec<String>>>,
}

impl Collector {
    pub fn new() -> Self {
        Self {
            items: Arc::new(Mutex::new(Vec::new())),
        }
    }

    pub fn push(&self, item: String) {
        let mut guard = self.items.lock().unwrap();
        guard.push(item);
    }

    pub fn get_all(&self) -> Vec<String> {
        let guard = self.items.lock().unwrap();
        guard.clone()
    }
}

A Clone az Arc klónozásával megosztja a belső állapotot, így minden klón ugyanazt a gyűjtőt látja.

16.2.8.3 (c)

A Worker teszt:

// rkv-core/tests/worker.rs
use rkv_core::{MemStore, Store, worker::{Command, Response}};
use std::sync::Arc;

#[test]
fn worker_processes_commands() {

    let (tx, rx) = rkv_core::worker::Worker::spawn(store);

    let mut handles = vec![];
    for i in 0..4 {
        let tx = tx.clone();
        handles.push(thread::spawn(move || {
            for j in 0..100 {

    }
}

Futtatás: cargo test -p rkv-core --test worker. A teszt sikeres, mert a worker sorosan dolgozza fel a parancsokat, és a list végén 400 kulcsot lát.

16.2.8.4 (d)

A holtpont oka: ha az egyik szál from-ként a-t, to-ként b-t zárol, a másik pedig fordítva, mindkettő megkapja az első zárat, és a másodikra vár; egyik sem engedi el az elsőt. Megoldás 1: minden szál rögzített sorrendben zár, például a RwLock pointerek címe szerint, vagy azonos sorrendű paraméterekkel. Megoldás 2: try_write() hívás, és ha sikertelen, az első zár eldobása után újra próbálkozás.

16.2.9 Rövid összefoglaló

A Mutex<T> és RwLock<T> a Rust szálbiztos belső mutabilitás alapjai: a zár birtokolja a védett adatot, a guard RAII-ja biztosítja a felszabadítást. A Mutex egy írót, a RwLock több olvasót vagy egy írót enged. Az mpsc csatornák több termelő / egy fogyasztó üzenetküldést adnak. A laborban az rkv Storage traitjét &self metódusokra alakítottuk, a MemStore Arc<RwLock<HashMap>>-ot kapott, és bevezettük a klónozható, Arc<dyn Storage>-ra épülő Store típust. A Worker csatornás munkásszál-mintát valósít meg a parancsok feldolgozására. Továbbvitt eredmény: a szálbiztos Store (rkv-core/src/store.rs) a Storage traittel és a MemStore Arc<RwLock<HashMap>> alapú implementációjával, valamint a Worker csatornás mintája (rkv-core/src/worker.rs) a Atomikus műveletek és memóriarendezés, a Az rkv hálózati szerver és a Záróprojekt alfejezetek alapja.

16.2.10 Források és ellenőrzési hiányok

A std::sync::Mutex, RwLock és mpsc stabil API-ját a hivatalos std dokumentáció alapján ismertettem. A parking_lot és crossbeam crate-ek pontos verzióit és API-it a docs.rs-en ellenőrizni kell (főverzió: parking_lot = "0.12", crossbeam = "0.8"). A RwLock fairness-viselkedése platformfüggő; a lock()/read()/write() unwrap() mintája a poisoning kezelésére csak akkor biztonságos, ha a pánik utáni állapot nem okoz további inkonzisztenciát. A Worker csatornás példa a Response enum Debug implementációját igényli, ha kiírjuk; ez a thiserror-os Error típusnál automatikus lehet. A pontos hibaüzenet szövege (pl. E0505) verziófüggő.
