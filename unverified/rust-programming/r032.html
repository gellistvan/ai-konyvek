15.2 Property-alapú tesztelés és benchmark

15.2.1 Motiváció

C++-ban a tesztelés gyakran kézzel kiválasztott példákkal történik, legfeljebb néhány véletlen értékkel. A property-alapú tesztelés – vagyis olyan tulajdonságok megfogalmazása, amelyek minden lehetséges bemenetre igazak – csak külső könyvtárakkal érhető el. A mikrobenchmarkoknál hasonló a helyzet: a fejlesztő std::chrono-val mér, de a fordító optimalizálása és a mérési zaj miatt a kapott szám gyakran félrevezető. A Rust ökoszisztéma ezt a két problémát a proptest és a criterion crate-ekkel oldja meg: a property-teszt generátorokkal és zsugorítással találja meg a hibás bemeneteket, a criterion pedig statisztikailag megalapozott mérést ad.

15.2.2 Fogalmak és szabályok

Definíció. A property-alapú tesztelés (property-based testing) során nem konkrét bemenetekre írunk tesztet, hanem egy invariánst fogalmazunk meg, amelynek minden lehetséges bemenetre teljesülnie kell. A keretrendszer véletlen bemeneteket generál, ellenőrzi az invariánst, és ha talál egy ellenpéldát, zsugorítással (shrinking) megkeresi a lehető legkisebb hibás bemenetet.

Szabály. A proptest a proptest! makróval definiált tesztfüggvényeket futtatja. A generátorokat a Strategy trait írja le; a leggyakoribb beépített stratégia az any::<T>(). Ha egy teszt elbukik, a proptest automatikusan menti a hibás bemenetet egy regressziós fájlba (alapértelmezés szerint a proptest-regressions könyvtárba), hogy a hiba reprodukálható legyen.

Definíció. A benchmark egy kód futási idejének ismételt, statisztikailag értelmezhető mérése. A criterion a mérésekből becsli a mediánt és a konfidenciaintervallumot (alapértelmezés szerint 95%-os szinten). A konfidenciaintervallum azt az értéktartományt adja meg, amelybe a mérési sorozat ismétlése esetén a várható érték nagy valószínűséggel bel esik.

Szabály. A benchmarkban a mért kód bemenetét és kimenetét black_box-ba kell csomagolni, különben a Rust fordító (és a C++ optimalizáló is) kioptimalizálhatja a mért számítást, így a mérés hamis eredményt ad. A cargo bench alapértelmezés szerint release módban fut, ami a valós produkciós teljesítményt közelíti.

15.2.3 C++ ↔︎ Rust összevetés

C++-ban a kézi véletlen teszt gyakran csak néhány beépített értéket használ, és nem ad automatikus zsugorítást:

#include <cassert>
#include <random>
#include <unordered_map>
#include <string>

int main() {
    std::mt19937 rng(42);
    std::uniform_int_distribution<int> dist(0, 9);
    std::unordered_map<std::string, std::string> map;
    for (int i = 0; i < 100; ++i) {
        auto key = "k" + std::to_string(dist(rng));
        auto value = "v" + std::to_string(dist(rng));
        map[key] = value;
        assert(map[key] == value);
    }
    return 0;
}

Ez a teszt nem fogalmaz meg invariánst, és ha elbukik, nem segít megtalálni a minimális ellenpéldát. A Rust proptest ezzel szemben deklaratívan írja le az invariánst, és automatikusan zsugorít:

use proptest::prelude::*;
use rkv_core::{MemStore, Storage};

proptest! {
    #[test]
    fn set_then_get_returns_value(key in any::<String>(), value in any::<String>()) {
        let mut store = MemStore::new();
        store.set(&key, value.clone()).unwrap();
        prop_assert_eq!(store.get(&key).unwrap(), Some(value));
    }
}

A prop_assert_eq! makró ugyanazt ellenőrzi, mint az assert_eq!, de a proptest képes a generált bemeneteket és a hibaüzenetet a teszt kontextusába illeszteni. A key és value generálása a String típusból az any::<String>() stratégiával történik; a stratégia a hiba esetén a kulcsot és az értéket is zsugorítja.

A benchmark terén is hasonló a különbség. C++-ban a kézi mérés:

#include <chrono>
#include <unordered_map>
#include <string>

int main() {
    using Clock = std::chrono::high_resolution_clock;
    auto start = Clock::now();
    std::unordered_map<std::string, std::string> map;
    for (int i = 0; i < 1000; ++i) {
        map[std::to_string(i)] = "value";
    }
    auto end = Clock::now();
    auto ns = std::chrono::duration_cast<std::chrono::nanoseconds>(end - start).count();
    // Probléma: a fordító optimalizálhat, a mérés túl rövid, a cache-hatás torzít.
}

A Rust criterion ezt megoldja a statisztikai elemzéssel és a black_box-szal:

use criterion::{black_box, criterion_group, criterion_main, Criterion};
use rkv_core::{MemStore, Storage};

fn bench_get(c: &mut Criterion) {
    let mut store = MemStore::new();
    store.set("key", "value".to_string()).unwrap();
    c.bench_function("MemStore::get", |b| {
        b.iter(|| {
            let value = store.get(black_box("key")).unwrap();
            black_box(value);
        });
    });
}

criterion_group!(benches, bench_get);
criterion_main!(benches);

A black_box megakadályozza, hogy a fordító kioptimalizálja a get hívását vagy az eredmény felhasználását.

15.2.4 Kidolgozott labor: proptest és criterion az rkv-ban

A laborban az rkv workspace rkv-core crate-jéhez adunk property-tesztet és benchmarkot. Feltételezzük, hogy a korábbi döntés alapján az rkv érték típusa String; ha ez másképp lett rögzítve, a generátorok értelemszerűen módosulnak.

15.2.4.1 1. lépés: függőségek

Nyissuk meg az rkv-core/Cargo.toml fájlt, és adjuk hozzá a dev-függőségeket:

[dev-dependencies]
proptest = "1"
criterion = "0.5" # ellenőrizendő a docs.rs-en

[[bench]]
name = "benchmark"
harness = false

A harness = false azt jelenti, hogy a benchmarkot nem a beépített tesztkeret futtatja, hanem a criterion saját criterion_main! belépési pontja.

15.2.4.2 2. lépés: property-teszt

Hozzuk létre az rkv-core/tests/storage_proptest.rs fájlt:

use proptest::prelude::*;
use rkv_core::{MemStore, Storage};

proptest! {
    #[test]
    fn set_then_get_returns_value(key in any::<String>(), value in any::<String>()) {
        let mut store = MemStore::new();
        store.set(&key, value.clone()).unwrap();
        prop_assert_eq!(store.get(&key).unwrap(), Some(value));
    }

    #[test]
    fn delete_after_set_returns_none(key in any::<String>(), value in any::<String>()) {
        let mut store = MemStore::new();
        store.set(&key, value).unwrap();
        store.delete(&key).unwrap();
        prop_assert_eq!(store.get(&key).unwrap(), None);
    }
}

A MemStore és a Storage trait az rkv-core crate-ből származik. A set_then_get_returns_value invariáns a beillesztés és a visszaolvasás konzisztenciáját fejezi ki; a delete_after_set_returns_none pedig a törlés helyességét ellenőrzi.

Futtassuk a tesztet:

cd ~/rust-labor/rkv
cargo test -p rkv-core --test storage_proptest

Várható kimenet:

running 2 tests
test set_then_get_returns_value ... ok
test delete_after_set_returns_none ... ok

test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out

A proptest alapértelmezés szerint több száz véletlen bemenetet generál, és a generált kulcsok és értékek a String típus teljes terét fedik le.

15.2.4.3 3. lépés: a zsugorítás bemutatása szándékos hibával

A zsugorítás szemléltetéséhez írjunk egy szándékosan hibás get implementációt a MemStore helyett egy ideiglenes típusba. Ezt nem az rkv kódjába, hanem a tesztfájlba helyezzük:

use proptest::prelude::*;
use rkv_core::{Error, Storage};

struct BuggyStore {
    map: std::collections::HashMap<String, String>,
}

impl Storage for BuggyStore {
    fn set(&mut self, key: &str, value: String) -> Result<(), Error> {
        self.map.insert(key.to_string(), value);
        Ok(())
    }
    fn get(&self, key: &str) -> Result<Option<String>, Error> {
        // Szándékos hiba: 10 karakternél hosszabb kulcsra mindig None-t ad.
        if key.len() > 10 {
            Ok(None)
        } else {
            Ok(self.map.get(key).cloned())
        }
    }
    fn delete(&mut self, key: &str) -> Result<(), Error> {
        self.map.remove(key);
        Ok(())
    }
    fn list(&self, prefix: Option<&str>) -> Result<Vec<String>, Error> {
        Ok(self.map.keys().cloned().collect())
    }
}

proptest! {
    #[test]
    fn buggy_get_fails_for_long_keys(key in any::<String>(), value in any::<String>()) {
        let mut store = BuggyStore { map: Default::default() };
        store.set(&key, value.clone()).unwrap();
        prop_assert_eq!(store.get(&key).unwrap(), Some(value));
    }
}

A teszt futtatásakor a proptest talál egy hosszú kulcsot, amelyre a get None-t ad, majd a zsugorító addig rövidíti a kulcsot, amíg meg nem találja a minimális hosszúságot (itt a 11 karakter). A hibaüzenet tartalmazni fogja a zsugorított ellenpéldát és a fájlt, ahová mentette:

thread 'buggy_get_fails_for_long_keys' panicked at 'Test failed: ...
minimal failing input: key = "aaaaaaaaaaa", value = ""
    successes: 123
    local rejects: 0
    ...

A konkrét szöveg verziófüggő, de a zsugorított kulcs mindig a lehető legrövidebb hibás bemenet lesz.

15.2.4.4 4. lépés: criterion benchmark

Hozzuk létre az rkv-core/benches/benchmark.rs fájlt:

use criterion::{black_box, criterion_group, criterion_main, Criterion};
use rkv_core::{MemStore, Storage};

fn bench_set(c: &mut Criterion) {
    let mut store = MemStore::new();
    c.bench_function("MemStore::set", |b| {
        b.iter(|| {
            store.set(black_box("key"), black_box("value".to_string())).unwrap();
        });
    });
}

fn bench_get(c: &mut Criterion) {
    let mut store = MemStore::new();
    store.set("key", "value".to_string()).unwrap();
    c.bench_function("MemStore::get", |b| {
        b.iter(|| {
            let value = store.get(black_box("key")).unwrap();
            black_box(value);
        });
    });
}

criterion_group!(benches, bench_set, bench_get);
criterion_main!(benches);

Futtassuk a benchmarkot:

cargo bench -p rkv-core --bench benchmark

A criterion több száz iterációt futtat, melegítési fázist tart, és statisztikát számol. A kimenet a mért gépfüggő adatokat mutatja, például:

MemStore::set          time:   [1.234 us 1.245 us 1.258 us]
                       change: [-0.5% +0.3% +1.1%] (p = 0.67 > 0.05)
                       No change in performance detected.
MemStore::get          time:   [0.987 us 0.995 us 1.003 us]

A szögletes zárójelben a konfidenciaintervallum alsó határa, mediánja és felső határa szerepel; az értékek illusztratívak és gépenként eltérnek. A p = 0.67 > 0.05 azt jelenti, hogy nincs szignifikáns változás az előző futtatáshoz képest.

A benchmark a black_box miatt a String allokációt is méri; a set esetén a HashMap bővülése és a felülírás is része a mérésnek. Ezért a kapott számok az adott művelet teljes költségét tükrözik, nem csak a szűken vett logikát.

15.2.5 Ábra

Az ábra a proptest folyamatát mutatja: a generátor véletlen bemenetet állít elő, a teszt ellenőrzi az invariánst, hiba esetén a zsugorító minimalizálja az ellenpéldát, majd a hiba bekerül a regressziós fájlba. A következő futtatáskor a proptest először ezeket a mentett eseteket ellenőrzi, így a korábban megtalált hibák nem vesznek el.

15.2.6 Tipikus hibák és átállási csapdák

  1. Túl szűk generátor. Ha a property-tesztben csak rövid, fix hosszúságú String-eket generálunk (például "[a-z]{1,5}"), a hosszú kulcsokkal kapcsolatos hibák sosem derülnek ki. Az any::<String>() széles teret fed le, de ha a hibát speciális bemenet váltja ki, szükség lehet egyéni Strategy-re, például prop::collection::vec(any::<u8>(), 0..100).

  2. Benchmark black_box nélkül. Ha a mért függvény kimenetét nem csomagoljuk black_box-ba, a Rust (és a C++ is) kioptimalizálhatja a teljes számítást. A b.iter closure visszatérési értékét mindig black_box-szal kell elrejteni, és a bemeneteket is célszerű black_box-ba tenni, hogy az optimalizáló ne tudjon konstans-számítást végezni.

  3. A benchmark eredményét abszolút igazságként kezelni. A mikrobenchmarkok a CPU gyorsítótárától, az operációs rendszer ütemezőjétől és a linkelési sorrendtől is függnek. A criterion konfidenciaintervalluma segít az ingadozás számszerűsítésében, de a mérések mindig gépfüggőek. A teljesítményt a Teljesítmény: mérés, profilozás, allokáció, release-beállítások alfejezetben tárgyaljuk részletesen.

15.2.7 Feladatok

15.2.7.1 (a) Fogalmi kérdés

Lefordul-e a következő proptest teszt, és ha igen, milyen hibát találhat?

use proptest::prelude::*;
use rkv_core::{MemStore, Storage};

proptest! {
    #[test]
    fn list_returns_same_keys(key in any::<String>(), value in any::<String>()) {
        let mut store = MemStore::new();
        store.set(&key, value).unwrap();
        let keys = store.list(None).unwrap();
        prop_assert!(keys.contains(&key));
    }
}

Válaszát indokolja!

15.2.7.2 (b) C++ kód átírása Rustra

Írja át idiomatikus proptest tesztre a következő C++ tesztet, amely azt ellenőrzi, hogy két különböző kulcs beszúrása után a list mindkét kulcsot visszaadja:

#include <cassert>
#include <unordered_map>
#include <string>

int main() {
    std::unordered_map<std::string, std::string> map;
    map["a"] = "1";
    map["b"] = "2";
    auto count = map.count("a") + map.count("b");
    assert(count == 2);
    return 0;
}

15.2.7.3 (c) Implementációs feladat az rkv-ban

Írjon property-tesztet az rkv-core crate-hez, amely azt az invariánst ellenőrzi, hogy a list(Some(prefix)) csak olyan kulcsokat ad vissza, amelyek a prefix-szel kezdődnek. Használja az any::<String>() generátort a kulcsokra, és a proptest prop_assert! makróját.

15.2.7.4 (d) Benchmark refaktorálás

A következő benchmarkot egy fejlesztő black_box nélkül írta meg:

use criterion::{criterion_group, criterion_main, Criterion};
use rkv_core::{MemStore, Storage};

fn bench_delete(c: &mut Criterion) {
    let mut store = MemStore::new();
    store.set("key", "value".to_string()).unwrap();
    c.bench_function("MemStore::delete", |b| {
        b.iter(|| {
            store.delete("key").unwrap();
        });
    });
}

criterion_group!(benches, bench_delete);
criterion_main!(benches);

Mi a probléma? Írja át a benchmarkot helyesen, és magyarázza el, miért fontos a black_box használata.

15.2.8 Megoldások

15.2.8.1 (a)

A teszt lefordul, és egy potenciális hibát találhat: a list(None) a MemStore összes kulcsát visszaadja, de ha a list implementációja nem adja vissza a frissen beszúrt kulcsot, a teszt hibát jelez. A proptest zsugorítással minimális kulcsot talál. A teszt nem hibás, de a list(None) invariánsa nem elég erős: nem ellenőrzi, hogy a kulcs pontosan egyszer szerepel, és hogy más kulcsok nem jelennek meg. Erősebb invariáns lenne: a list(None) hosszának egyenlőnek kell lennie a beszúrt kulcsok számával, vagy a list által visszaadott lista rendezett.

15.2.8.2 (b)

use proptest::prelude::*;
use rkv_core::{MemStore, Storage};

proptest! {
    #[test]
    fn two_keys_are_listed(
        key1 in any::<String>(),
        key2 in any::<String>(),
        value1 in any::<String>(),
        value2 in any::<String>(),
    ) {
        prop_assume!(key1 != key2);
        let mut store = MemStore::new();
        store.set(&key1, value1).unwrap();
        store.set(&key2, value2).unwrap();
        let keys = store.list(None).unwrap();
        prop_assert!(keys.contains(&key1));
        prop_assert!(keys.contains(&key2));
    }
}

A prop_assume! makró elutasítja azokat a generált eseteket, ahol a két kulcs egyenlő, így a teszt csak különböző kulcsokra fut.

15.2.8.3 (c)

use proptest::prelude::*;
use rkv_core::{MemStore, Storage};

proptest! {
    #[test]
    fn list_with_prefix_filters_keys(
        prefix in any::<String>(),
        suffix in any::<String>(),
        value in any::<String>(),
    ) {
        let key = format!("{prefix}{suffix}");
        let mut store = MemStore::new();
        store.set(&key, value).unwrap();
        let keys = store.list(Some(&prefix)).unwrap();
        if keys.contains(&key) {
            prop_assert!(key.starts_with(&prefix));
        }
    }
}

Ez az invariáns gyenge, mert a keys.contains csak akkor fut, ha a kulcs szerepel; erősebb teszt lenne, ha azt ellenőriznénk, hogy a list által visszaadott összes kulcs a prefixszel kezdődik. A feladat célja a prefix-szűrés helyességének ellenőrzése; a robustus teszt a következő lenne:

proptest! {
    #[test]
    fn list_with_prefix_filters_all_keys(
        prefix in any::<String>(),
        suffix in any::<String>(),
        value in any::<String>(),
    ) {
        let key = format!("{prefix}{suffix}");
        let mut store = MemStore::new();
        store.set(&key, value).unwrap();
        let keys = store.list(Some(&prefix)).unwrap();
        for k in &keys {
            prop_assert!(k.starts_with(&prefix));
        }
    }
}

15.2.8.4 (d)

A probléma az, hogy a store.delete("key") visszatérési értékét nem használjuk fel, és a bemenet sem black_box. A Rust fordító a delete hívását akár ki is optimalizálhatja, mert a Result értéke nincs felhasználva. A helyes benchmark:

use criterion::{black_box, criterion_group, criterion_main, Criterion};
use rkv_core::{MemStore, Storage};

fn bench_delete(c: &mut Criterion) {
    let mut store = MemStore::new();
    store.set("key", "value".to_string()).unwrap();
    c.bench_function("MemStore::delete", |b| {
        b.iter(|| {
            let result = store.delete(black_box("key"));
            black_box(result);
        });
    });
}

criterion_group!(benches, bench_delete);
criterion_main!(benches);

A black_box(result) megakadályozza, hogy a fordító eltávolítsa a hívás hatását; a black_box("key") pedig azt biztosítja, hogy a bemenet ne legyen fordítási időben ismert konstans.

15.2.9 Rövid összefoglaló

A proptest crate lehetővé teszi, hogy az rkv MemStore implementációjára invariánsokat fogalmazzunk meg generátorokkal és automatikus zsugorítással. A laborban létrehoztuk az rkv-core/tests/storage_proptest.rs fájlt, amely a set-get konzisztenciát és a delete utáni None-t ellenőrzi. A criterion benchmarkot az rkv-core/benches/benchmark.rs fájlban adtuk hozzá, amely a set és get műveleteket méri black_box használatával. A konfidenciaintervallum értelmezése és a black_box elengedhetetlen a megbízható méréshez. Továbbvitt eredmény. Ez a benchmark-módszertan (release mód, black_box, konfidenciaintervallum) alapozza meg a Teljesítmény: mérés, profilozás, allokáció, release-beállítások alfejezetben tárgyalt haladó méréseket.

15.2.10 Források és ellenőrzési hiányok

  • A proptest és criterion crate-ek pontos verziószámait és API-ját a docs.rs-en kell ellenőrizni; a criterion = "0.5" csak főverzió-megjelölés.
  • A proptest regressziós fájlok pontos elnevezése és a prop_assume! pontos szemantikája verziófüggő.
  • A fejezetben bemutatott futási idők illusztratívak, gépfüggőek, és nem tekinthetők mért értéknek.
  • A C++ példákban a std::chrono mérés korlátai jól ismertek; a Google Benchmark DoNotOptimize használata analóg a Rust black_box-szal, de ennek részletei nem részei ennek az alfejezetnek.
