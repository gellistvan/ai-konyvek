17.1 Future-ök és async/await: mi történik a motorháztető alatt

17.1.1 Motiváció

Ha C++-ban tíz TCP-kapcsolatot akarunk egyszerre kiszolgálni, a hagyományos megoldás gyakran tíz szál. Minden szál saját veremmel, saját ütemezési állapottal rendelkezik, és a kernel egy-egy blokkoló read hívás közben felfüggeszti. Ez tíz szál esetén még elfogadható; százezer kapcsolatnál már memória- és ütemezési katasztrófa. A C++20 bevezette a korutinokat, a Rust pedig a Future-alapú async/await modellt: a cél mindkét nyelvben az, hogy egy feladat felfüggesztéséhez ne kelljen külön szál, hanem egy kisméretű állapotgép tárolja, hol tart a művelet.

A Rust megközelítés lényege: az async fn hívása nem hajtja végre a függvény törzsét. Ehelyett egy olyan értéket ad vissza, amelyet egy úgynevezett executor polloz. Ez a fejezet azt mutatja meg, mi történik a motorháztető alatt: mit tartalmaz a Future, mi a poll, mi a Waker, és miért van szükség Pin-re.

17.1.2 Fogalmak és szabályok

Definíció. A Future trait egy olyan értéket ír le, amely egy később rendelkezésre álló eredményt képvisel. A szabványos definíció leegyszerűsítve:

pub trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

pub enum Poll<T> {
    Ready(T),
    Pending,
}

A poll hívás az egyetlen mód, ahogy a future haladást érhet el. A Ready(value) azt jelenti, hogy az eredmény elkészült, a Pending pedig azt, hogy a future még nem tud befejeződni; az executor később újra fogja hívni a poll-t.

Szabály. Az async fn hívása nem fut le azonnal: a hívás egy impl Future<Output = T> értéket hoz létre, amely a függvény állapotgépét tartalmazza. A függvény törzse csak akkor kezd el futni, amikor valaki meghívja a poll metódust.

A Waker szerepe: amikor egy future Pending értéket ad vissza, el kell tárolnia valahol a Context-ből kinyert Waker-t. Ez jelzi az executor számára, hogy a future-t érdemes újra pollozni. Ha a jövőben egy esemény bekövetkezik — például egy socket olvashatóvá válik —, a megfelelő komponens meghívja a Waker::wake() metódust, és az executor újra ütemezi a future-t. A Waker tehát az a kommunikációs csatorna a future és az executor között, amely lehetővé teszi, hogy a future ne pörögjön folyamatosan, hanem letargikusan várjon.

Szabály. A Rust standard könyvtár nem tartalmaz beépített async runtime-et. Az async fn és a Future csak a nyelvi és könyvtári alapszint; az executor és a reaktor — az I/O eseményeket figyelő komponens — külső crate-ekből, jellemzően a Tokio-ról származik.

17.1.3 C++ ↔︎ Rust összevetés

C++20-ban egy korutin vázlata:

#include <coroutine>
#include <iostream>

struct Task {
    struct promise_type {
        Task get_return_object() { return {}; }
        std::suspend_never initial_suspend() { return {}; }
        std::suspend_never final_suspend() noexcept { return {}; }
        void return_void() {}
        void unhandled_exception() {}
    };
};

Task compute() {
    co_await std::suspend_never{};
    std::cout << "hello from coroutine\n";
}

A Rust megfelelő gondolati párja:

async fn compute() {
    println!("hello from async fn");
}

A látszólagos hasonlóság mögött fontos különbségek vannak. A C++ korutinoknál a visszatérési típus promise_type-ja határozza meg a korutin viselkedését, és a felfüggesztés a co_await kifejezéssel történik. A Rust-ban az async fn egy Future értéket ad, és a felfüggesztési pont a .await posztfix művelet. A C++ korutin frame-je gyakran dinamikusan allokálódik, bár a fordító elideálhatja; a Rust async fn állapotgépe általában inline tárolódik a future értékben, és akár nulla allokációval is használható. A legfontosabb különbség a végrehajtási modell: a Rust future passzív, az executor húzza a poll-on keresztül; a C++ korutinok is külső resumálásra várnak, de a nyelv szabadabban engedi a coroutine_handle közvetlen folytatását, és a co_await általánosabb felfüggesztési mechanizmust takar.

17.1.4 Kidolgozott példa: kézzel pollozott Future

Először nézzük a leggyakoribb kezdő hibát:

async fn greet() -> String {
    "hello".into()
}

fn main() {
    let s = greet();
    println!("{s}");
}

Ez a változat szándékosan nem fordul le: a greet() hívás eredménye impl Future<Output = String>, nem String, ezért a println! nem tudja formázni. A hibaüzenet lényege: „greet() returns impl Future<Output = String>, which does not implement Display”. A javítás egy executor és egy .await hozzáadása:

#[tokio::main]
async fn main() {
    let s = greet().await;
    println!("{s}");
}

Ahhoz, hogy lássuk, mit csinál az executor, implementáljunk egy nagyon egyszerű future-t. A következő Remind az első pollozásnál még Pending, a másodiknál Ready lesz, és közben értesíti a wakert:

use std::future::Future;
use std::pin::Pin;
use std::task::{Context, Poll, Waker};

struct Remind {
    ready: bool,
}

impl Future for Remind {
    type Output = &'static str;

    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<&'static str> {
        if self.ready {
            Poll::Ready("megvan!")
        } else {
            self.ready = true;
            // Értesítsük az executort, hogy érdemes újra pollozni.
            cx.waker().wake_by_ref();
            Poll::Pending
        }
    }
}

fn main() {
    let future = Remind { ready: false };
    let waker = Waker::noop();
    let mut cx = Context::from_waker(&waker);
    let mut pinned = Box::pin(future);

    match pinned.as_mut().poll(&mut cx) {
        Poll::Pending => println!("első poll: Pending"),
        Poll::Ready(s) => println!("első poll: Ready({s})"),
    }
    match pinned.as_mut().poll(&mut cx) {
        Poll::Pending => println!("második poll: Pending"),
        Poll::Ready(s) => println!("második poll: Ready({s})"),
    }
}

A Waker::noop() stabil a standard könyvtárban, de pontos verziója eszközlánctól függ; a fenti kód a 2021-es és 2024-es editionnel is fordul. A Box::pin a Pin miatt szükséges, mert a poll Pin<&mut Self> típusú paramétert vár. Várt kimenet:

első poll: Pending
második poll: Ready(megvan!)

A Remind példa megmutatja a modell lényegét: a future nem fut, amíg pollozva nincs; Pending esetén a wakerrel jelzi az újrapollozási igényét; a Ready pedig a végeredményt tartalmazza.

17.1.5 Mi van egy async fn állapotgépében?

Egy async fn lefordításakor a Rust fordító egy olyan struktúrát generál, amely a függvény lokális változóit tárolja, és egy Future implementációt ad hozzá. A .await pontoknál a generált poll meghívja a belső future poll metódusát; ha az Pending, akkor a külső future is Pending-et ad vissza. Ha a belső Ready, akkor a külső folytatja a következő utasítással.

Tekintsük ezt a vázlatot:

async fn example(a: u32) -> u32 {
    let x = a + 1;
    let y = read_value().await;
    x + y
}

A generált állapotgép nagyjából így gondolkodik:

  1. Állapot 0: x = a + 1, hívja read_value().poll(...).
  2. Ha read_value Ready(y), állapot 1: visszaadja Ready(x + y).
  3. Ha read_value Pending, menti a wakert, és visszaadja Pending.

Az állapotgép tehát a .await pontokon felfüggeszti magát, és a poll legközelebbi hívásakor ott folytatja, ahol abbahagyta.

Miért nincs beépített runtime? A Rust standard könyvtár csak a Future, a poll és a Waker alapfogalmát definiálja. A valódi ütemezés — mikor, melyik szálon, hány future-t pollozzon az executor — tudatosan a felhasználóra van bízva. Ez lehetővé teszi, hogy a Tokio egyaránt kiszolgáljon egy beágyazott eszköz eseményhurkolóját és egy nagy teljesítményű hálózati szervert. A C++-hoz hasonlóan a Rustban sincs „egyetlen igaz” async futtató, de a Tokio a de facto standard.

17.1.6 Pin: az önhivatkozó állapotgép problémája

Az async fn-ek egyik elsőre meglepő tulajdonsága, hogy miért kell Pin-t használni. A C++-ban megszokott mozgatási szemantikából tudjuk: egy objektum memóriabeli mozgatása után a rá mutató nyers címek érvénytelenné válnak. Ha egy async fn törzse egy .await pont felett tart életben egy referenciát, például:

async fn read_to_end(&mut self) {
    while !self.buf_full() {
        let n = self.reader.read(&mut self.buf).await?;
        // ...
    }
}

akkor a generált állapotgép önhivatkozóvá válhat: az egyik mezője referencia egy másik mezőjére mutat. Ha a future-t ezután megmozgatjuk, a referencia érvénytelen lesz. A Pin<&mut Self> azt garantálja, hogy a future nem mozdul el a pollozás során. A Future::poll ezért vesz Pin<&mut Self>-et, és a tipikus használat Box::pin vagy a tokio::pin! makró.

A Pin tehát nem misztikum: típusrendszerbeli garancia arra, hogy egy önhivatkozó értéket ne lehessen biztonságos kódból elmozdítani. A következő, Pin, Unpin, async trait-ek és a Send-határok alfejezet ezt mélyebben ki fogja fejteni.

17.1.7 Ábra: a Future életciklusa az executorban

Az ábra azt hangsúlyozza, hogy a future életét az executor pollozása vezérli. A Pending nem hiba: a future ilyenkor adja át magát az ütemezőnek, és csak akkor jelentkezik újra, ha a waker jelzi, hogy a várt erőforrás elérhető.

17.1.8 Async vs. szálak: döntési tábla

Szempont Async/Future Szál
Sok rövid, I/O-igényes feladat Kiváló: kis memórianyom, gyors váltás Sok szál nagy veremköltséget jelent
CPU-igényes, hosszú számítás Rossz, ha egy executor szálat blokkolja Jó, ha a feladat tényleg párhuzamos
Egyszerű szinkron kód .await fertőzés, executor kell Egyszerű thread::spawn
Hibaelkülönítés Egy pánik a taskot veszi le, de a runtime marad A szál pánikja a szálat öli meg
Memória Kis állapotgépek 2–8 MiB verem szálanként
Megfelelő Rust-megoldás Tokio spawn std::thread vagy rayon

A döntési szabály: ha a feladat döntően várakozás — hálózat, fájlművelet, időzítő —, az async jobb. Ha a feladat ténylegesen számol, használjunk szálat vagy a rayon crate-et, és ne blokkoljunk async taskot hosszú CPU-munkával.

17.1.9 Tipikus hibák és átállási csapdák

  1. Az async fn hívása .await nélkül. A visszatérési érték impl Future, nem a várt String vagy u32. A fordító ilyenkor Future típusú értéket mutat, és a hibaüzenetben a Display hiánya vagy a típuseltérés jelenik meg.

  2. .await szinkron kódban. A .await csak async fn-ben vagy async blokkban használható. A következő nem fordul le, a hiba lényege E0728:

fn main() {
    async { 1 + 1 }.await;
}

  1. Blokkoló hívás async taskban. A std::thread::sleep vagy egy nagy read_to_string egy async fn-ben blokkolja az executor egy szálát, tönkretéve a többi task ütemezését. Helyette tokio::time::sleep-et és async I/O-t kell használni.

  2. A Waker elfelejtése. Ha egy Future Pending-et ad, de nem regisztrálja a wakert, az executor nem fogja tudni, mikor érdemes újrapollozni; a future örökre felfüggesztve marad. Saját Future implementációban erre különösen figyelni kell.

17.1.10 Feladatok

17.1.10.1 1. Fogalmi ellenőrzés

Mit jelent a Future::poll Pending visszatérési értéke? Mi a különbség aközött, hogy egy async fn hívása Ready-vel tér vissza, és aközött, hogy a hívás maga Ready értéket ad?

17.1.10.2 2. C++-kód átírása

Írd át a következő C++20 std::async alapú kódot idiomatikus Rust async kódra Tokio spawn használatával:

#include <future>
#include <iostream>

int compute() { return 40 + 2; }

int main() {
    auto fut = std::async(std::launch::async, compute);
    std::cout << fut.get() << "\n";
}

17.1.10.3 3. Implementáció: saját DelayedReady future

Készíts egy önálló crate-et a ~/rust-labor/r037/ munkakönyvtárban (cargo new r037). Implementálj egy DelayedReady struktúrát, amely az első poll-nál Pending-et ad, eltárolja a wakert, és egy külső wake() hívás után a második poll-nál Ready(42)-t ad vissza. A main-ben kézzel pollozd.

17.1.10.4 4. Hibajavítás: blokkoló hívás async taskban

Adott a következő async függvény:

async fn wait_a_second() {
    std::thread::sleep(std::time::Duration::from_secs(1));
}

Miért problémás ez a Tokio executor szempontjából? Javítsd tokio::time::sleep használatára, és magyarázd el a különbséget.

17.1.11 Megoldások

17.1.11.1 1. Fogalmi ellenőrzés

A Pending nem azt jelenti, hogy a future fut, hanem azt, hogy jelenleg nem tud befejeződni; a future-nek ilyenkor regisztrálnia kell a wakert, hogy az executor később újra pollozza. Amikor egy async fn hívása egy future-t ad vissza, az egy érték, amelynek a típusa impl Future<Output = T>; a függvény törzse még nem futott. A Ready a poll visszatérési értéke, és azt jelzi, hogy a future kész.

17.1.11.2 2. C++-kód átírása

#[tokio::main]
async fn main() {
    let fut = tokio::spawn(compute());
    let result = fut.await.unwrap();
    println!("{result}");
}

async fn compute() -> i32 {
    40 + 2
}

A tokio::spawn egy JoinHandle-t ad vissza, amely maga is Future. A compute() azonnal visszaad egy future-t, amelyet a Tokio runtime egy külön taskként ütemez. A .await a JoinHandle-on várja meg a task eredményét.

17.1.11.3 3. Implementáció: DelayedReady

use std::future::Future;
use std::pin::Pin;
use std::task::{Context, Poll, Waker};

struct DelayedReady {
    waker: Option<Waker>,
    woke: bool,
}

impl DelayedReady {
    fn wake(&mut self) {
        self.woke = true;
        if let Some(waker) = self.waker.take() {
            waker.wake();
        }
    }
}

impl Future for DelayedReady {
    type Output = i32;

    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<i32> {
        if self.woke {
            Poll::Ready(42)
        } else {
            self.waker = Some(cx.waker().clone());
            Poll::Pending
        }
    }
}

fn main() {
    let future = DelayedReady { waker: None, woke: false };
    let waker = Waker::noop();
    let mut cx = Context::from_waker(&waker);
    let mut pinned = Box::pin(future);

    assert!(pinned.as_mut().poll(&mut cx).is_pending());

    // Kívülről jelezzük a készenlétet.
    pinned.as_mut().get_mut().wake();
    // A fenti get_mut() veszélyes lenne önhivatkozó future esetén;
    // itt a DelayedReady nem önhivatkozó, ezért biztonságos.

    match pinned.as_mut().poll(&mut cx) {
        Poll::Ready(v) => println!("ready: {v}"),
        Poll::Pending => println!("még mindig pending"),
    }
}

Ez a példa előkészíti a tokio taskok és a JoinHandle alfejezetet, ahol a valódi executor végzi el ugyanezt a pollozási és waker-kezelési feladatot.

17.1.11.4 4. Hibajavítás: blokkoló hívás

A std::thread::sleep blokkolja az aktuális szálat. A Tokio executor egy szálon több száz vagy több ezer async taskot futtat; ha egy task blokkolja a szálat, az összes többi task is megáll. Ráadásul a blokkolás alatt a timer vagy I/O események sem tudnak lefutni. A javítás:

async fn wait_a_second() {
    tokio::time::sleep(std::time::Duration::from_secs(1)).await;
}

A tokio::time::sleep egy olyan future-t ad, amely a Tokio timer-reaktorjában regisztrálja a wakert, és azonnal Pending-et ad; a szál így szabadon pollozhat más taskokat. Ez az alapja a Tokio: taskok, I/O, csatornák, select és megszakítás alfejezetnek.

17.1.12 Rövid összefoglaló

A Future trait a Rust aszinkron modelljének alapja: a poll metódus Ready-t vagy Pending-et ad, a Waker pedig lehetővé teszi az executor értesítését. Az async fn hívása egy impl Future állapotgépet hoz létre, de nem futtatja a függvényt; a futás csak a pollozással kezdődik. A standard könyvtár nem tartalmaz runtime-et, ezért a Tokio biztosítja az executort és a reaktort. A Pin az önhivatkozó async állapotgép mozgatását akadályozza meg. A C++20 korutinokkal szemben a Rust Future poll-alapú, passzív, és a .await a felfüggesztési pont. A döntési szabály: sok várakozó I/O-ra async, hosszú CPU-munkára szál vagy rayon. Ez a modell készíti elő a Pin, Unpin, async trait-ek és Send-határok, a Tokio taskok és csatornák, valamint az rkv hálózati szerver alfejezeteket.
