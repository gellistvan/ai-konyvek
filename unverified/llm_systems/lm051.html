14.3 JSON schema, function calling és constrained decoding

A generatív modell alapértelmezés szerint szöveget ad vissza, nem pedig gépileg garantáltan feldolgozható adatszerkezetet. Amikor egy alkalmazásnak kulcs–érték párokra, típusos mezőkre vagy egy API paraméterlistájára van szüksége, a „válaszolj JSON-ben” utasítás önmagában gyakran kevés. A modell valószínűségi alapon, tokenről tokenre generál, és a JSON szintaxis nem kemény kényszer, hanem csak egy tanult statisztikai minta. Ezért a strukturált kimenet megbízható előállítása három rétegből áll: explicit sémadefinícióból, lehetőség szerint constrained decodingból, valamint utólagos validációból és hibakezelésből. Ebben az alfejezetben ezt a három pillért járjuk körül, és a JSON-sémát, a function calling mechanizmust, valamint a grammar-vezérelt dekódolást egyetlen egységes mérnöki keretben helyezzük el.

14.3.1 A strukturált kimenet problémája

Az LLM szöveggenerálás során minden lépésben a következő token feltételes valószínűségi eloszlásából mintavételez:

pθ(xt∣x<t)=softmax(zt), p_\theta(x_t \mid x_{<t}) = \operatorname{softmax}(z_t),

ahol ztz_t a logitvektor. A JSON formátum azonban nem egyetlen token, hanem egy karaktersorozat, amelynek szintaktikai szabályai a generálás teljes hosszában érvényesülnek. A modell paraméterei nem garantálják, hogy a generált szekvencia a JSON nyelvtanhoz tartozik: egy zárójel elhagyása, egy vessző felcserélése vagy egy felesleges magyarázó mondat a kimenet elején azonnal érvényteleníti az egész adatszerkezetet.

A gyakorlatban a hibák leggyakoribb formái a következők:

  • markdown kerítés (```json ... ```) a nyers JSON körül,
  • hiányzó vagy felesleges vessző,
  • string helyett szám, vagy szám helyett string,
  • a séma által nem ismert mező hallucinálása,
  • a kért típusoktól eltérő mezőértékek,
  • a generálás elejére írt magyarázó szöveg.

A strukturált kimenet megbízható előállítása ezért nem pusztán prompttervezési kérdés. A prompt megfogalmazza a szerződést, a JSON-séma formalizálja azt, a constrained decoding pedig a dekódoló szintjén kényszeríti ki a szintaktikai érvényességet. Az utólagos validáció ezt a láncot zárja be, és a hibákból visszacsatolást ad a rendszernek.

14.3.2 JSON-séma mint verziózott szerződés

A JSON-séma egy deklaratív nyelv, amellyel megadhatjuk, milyen mezők, típusok és értékkészletek fogadhatók el egy JSON objektumban. A schema nem csak a modellnek szól; ugyanolyan fontos a fogyasztó oldali validáció, a tesztelés és a dokumentáció szempontjából is. A schema egy verziózott szoftverartefaktum, akárcsak a prompt: ha megváltozik, a rendszer viselkedése megváltozik, ezért a verziót és a változásokat nyilvántartjuk.

Példaként vegyünk egy könyvkereső asszisztenst, amely a felhasználó szabad szöveges kéréséből egy keresési paramétereket tartalmazó objektumot állít elő. Ehhez a következő sémát definiálhatjuk:

{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "properties": {
    "query": {"type": "string"},
    "limit": {"type": "integer", "minimum": 1, "maximum": 20},
    "language": {"type": "string", "enum": ["hu", "en", "de"]},
    "topic": {"type": "string", "enum": ["llm", "data", "security", "other"]},
    "allow_preprint": {"type": "boolean"}
  },
  "required": ["query", "limit", "language", "topic", "allow_preprint"],
  "additionalProperties": false
}

A required tömb felsorolja azokat a mezőket, amelyeknek mindenképpen jelen kell lenniük. Az additionalProperties: false lezárja az objektumot: semmilyen más kulcs nem jelenhet meg. Ez a szigorú séma gyakran megelőzi a hallucinált mezőket, ugyanakkor kockázatot is hordoz: ha a modell egy hasznos, de a sémában nem szereplő mezőt adna, az érvénytelen lesz. A tervezés során ezért külön döntést igényel, hogy egy mezőt kötelezővé, opcionálissá vagy tiltottá teszünk.

A sémát a promptba is beillesztjük, de nem feltétlenül a teljes JSON-schema formátumban. A modell számára gyakran hatékonyabb egy kompakt, típusos leírást adni, míg a validációhoz a teljes JSON-sémát használjuk. A kettő nem feltétlenül ugyanaz a szöveg: a promptban a séma magyarázó, például „a limit egy 1 és 20 közötti egész szám”, a validációban pedig gépi ellenőrzésre alkalmas formalizmus.

A séma verziózására a promptverziózással azonos szabályok vonatkoznak. Ha a séma változik, a golden seteket újra kell értékelni, mert a változás megváltoztathatja a modell által generált kimenetek elfogadhatóságát. A séma nemcsak a generálás előtt, hanem a generálás után is szerepel: a validátor ugyanabból a verzióból dolgozik.

14.3.3 Function calling: a hívási szándék mint strukturált kimenet

A function calling a strukturált kimenet egyik leggyakoribb alkalmazási mintája. A fogalom félrevezető lehet: a modell nem közvetlenül hív meg egy függvényt, és nem futtat kódot. A function calling során a modell egy hívási szándékot ad vissza, amely egy függvény nevéből és egy JSON paraméterobjektumból áll. Az alkalmazás felelőssége, hogy ezt a hívást validálja, a megfelelő biztonsági ellenőrzésekkel végrehajtsa, majd a visszatérési értéket újra a modell elé tárja.

A kérésben a modell számára egy vagy több eszközleírást adunk meg. Az eszközleírás egy sémája a hívható függvénynek:

{
  "name": "search_books",
  "description": "Keresés a könyvtári katalógusban.",
  "parameters": {
    "type": "object",
    "properties": {
      "query": {"type": "string"},
      "limit": {"type": "integer", "minimum": 1, "maximum": 20},
      "language": {"type": "string", "enum": ["hu", "en", "de"]},
      "topic": {"type": "string", "enum": ["llm", "data", "security", "other"]},
      "allow_preprint": {"type": "boolean"}
    },
    "required": ["query", "limit", "language", "topic", "allow_preprint"],
    "additionalProperties": false
  }
}

A modell válasza ebben az esetben nem hagyományos szöveg, hanem egy tool_call objektum, például:

{
  "name": "search_books",
  "arguments": {
    "query": "nagy nyelvi modellek",
    "limit": 5,
    "language": "hu",
    "topic": "llm",
    "allow_preprint": true
  }
}

A hívási ciklus a következő:

  1. A felhasználó szabad szöveges kérést ad.
  2. A modell a rendelkezésre álló eszközök és a bemenet alapján eldönti, hogy szükséges-e eszközhívás, és ha igen, melyik eszközt milyen paraméterekkel kell meghívni.
  3. Az alkalmazás validálja a paramétereket, elvégzi a biztonsági ellenőrzéseket, majd végrehajtja a függvényt.
  4. A függvény visszatérési értékét tool_result formában visszaküldi a modellnek.
  5. A modell a felhasználói kérés és az eszköz eredménye alapján megfogalmazza a végső, szabad szöveges választ.

A function calling tehát a strukturált kimenetet egy eszközvezérlési protokollba ágyazza. Az eszközök leírása maga a séma, a visszatérő arguments pedig a generált JSON. A mechanizmus akkor is használható, ha valójában nem akarunk külső függvényt hívni, hanem egyszerűen csak megbízható JSON-t szeretnénk kapni: ilyenkor a „függvény” egy kitalált, de jól definiált sémájú hívás, amelyet az alkalmazás közvetlenül feldolgoz.

A function calling nem varázslat. A háttérben ugyanaz a modell generál, és a szolgáltatás vagy a keretrendszer felelőssége, hogy a arguments mező JSON-jét constrained decodinggal vagy utólagos validációval megbízhatóvá tegye. A modell számára a séma része a promptnak: az eszközleírás bekerül a rendszerüzenetbe, és a modell ebből tanulja meg, milyen paramétereket várnak tőle. Ezért a sémát ugyanolyan gondosan kell tervezni, mint bármely más promptot.

14.3.4 Constrained decoding: grammar és logit-maszkolás

A constrained decoding célja, hogy a generálás minden egyes lépésében csak azok a tokenek legyenek megengedettek, amelyek az adott formális nyelvtan szerint érvényes folytatást eredményeznek. JSON esetén ez azt jelenti, hogy a { után csak kulcs vagy zárójel jöhet, a kulcs után csak kettőspont, egy string lezárása után csak vessző vagy zárójel, és így tovább. A nyelvtan lehet JSON-séma, reguláris kifejezés, context-free grammar vagy a szolgáltatás által támogatott nyelvtanformátum, például GBNF.

A technikai megvalósítás szempontjából a constrained decoding egy logit-maszkolási lépés. A modell minden lépésben kiszámítja a következő token logitvektorát, amelynek alakja [batch_size, vocab_size]. A dekódoló ezután egy engedélyezett tokenhalmazt határoz meg:

𝒜t={i∈V:az i token érvényes folytatása a nyelvtannak}, \mathcal{A}_t = \{ i \in V : \text{az } i \text{ token érvényes folytatása a nyelvtannak} \},

ahol VV a szókészlet. A tiltott tokenek logitját mínusz végtelenre állítjuk:

z′t(i)={zt(i)ha i∈𝒜t,−∞ha i∉𝒜t. z'_t(i) = \begin{cases} z_t(i) & \text{ha } i \in \mathcal{A}_t,\\ -\infty & \text{ha } i \notin \mathcal{A}_t. \end{cases}

Ezután a softmax normalizálást alkalmazzuk, így a tiltott tokenek valószínűsége pontosan nulla lesz. A generálás tehát matematikailag garantáltan nem léphet ki a nyelvtanból, függetlenül attól, hogy greedy, hőmérsékletes vagy top-p mintavételezést használunk.

A gyakorlatban a nyelvtan kiértékelése tokenizáló-specifikus. A tokenizáló nem karaktereket, hanem altokeneket ad, és egy JSON-nyelvtan ellenőrzéséhez a dekódolónak tudnia kell, hogy egy adott token milyen karakterláncot képvisel, és az adott pozícióban a teljes eddigi prefixszel együtt milyen állapotba kerül a nyelvtan automatájában. Ez a folyamat költséges lehet, ezért a hatékony megvalósítások előre kiszámított automatákat, token-trie struktúrákat és gyors állapotátmeneteket használnak.

Fontos különbséget tenni a szintaktikai és a szemantikai érvényesség között. A constrained decoding garantálja, hogy a kimenet érvényes JSON, de nem garantálja, hogy a JSON szemantikailag megfelel a felhasználó szándékának. A modell például a language mezőbe a sémában nem szereplő, de szintaktikailag szabályos stringet is generálhat, ha a grammar csak annyit ír elő, hogy string legyen. Az enum típusú mezők esetén a grammar általában már a megengedett értékekre is szorít, de a szabad szöveges mezőknél a szemantikai ellenőrzés továbbra is az alkalmazás feladata.

A constrained decoding és a function calling kapcsolata szoros. A legtöbb modern szolgáltatás, amikor function callingot kérünk, a arguments mezőt constrained decodinggal állítja elő, így a JSON szintaxis garantált. Ez azonban nem mentesít a validáció alól: a séma type, required, enum és additionalProperties feltételeit a generálás után is ellenőrizni kell, mert a constrained decoding implementációja nem feltétlenül fedi le a teljes JSON-sémát.

A constrained decoding gyakorlati megvalósításai közé tartoznak a grammar-vezérelt dekódolók, mint például a llama.cpp GBNF, az Outlines, a vLLM guided decoding, valamint a szolgáltatók által elérhetővé tett strukturált kimenetek. A pontos képességek és a szintaktikai fedettség verzióról verzióra változik, ezért a felhasználás előtt ellenőrizni kell az adott keretrendszer dokumentációját és a támogatott sémaelemek listáját. A könyv nem egyetlen eszközt reklámoz; a cél annak megértése, hogy a constrained decoding egy általános mérnöki minta, amelyet bármelyik implementációban alkalmazhatunk.

14.3.5 A sémából grammar, a grammarból garantált szintaxis

A fejlesztő általában nem kézzel írja a grammart, hanem a JSON-sémából állítja elő a constrained decoding nyelvtant. A JSON-schema és a grammar közötti átalakítás nem triviális, mert a JSON-schema olyan feltételeket is tartalmazhat, amelyeket egy context-free grammar nem tud kifejezni, például függőségek a mezők között vagy numerikus korlátok. A gyakorlatban a keretrendszerek a sémát egy olyan közelítő grammar-ré alakítják, amely a szintaktikai szerkezetet garantálja, a finomabb szemantikai korlátokat pedig a validátorra hagyják.

Példánkban a limit mező minimum: 1 és maximum: 20 korlátját a grammar nem feltétlenül tudja kikényszeríteni, mert a grammar szintjén az összes számjegy-szekvencia érvényes egész szám lehet. A modell így generálhat limit: 99 értéket is, amely szintaktikailag helyes, de a séma szerint érvénytelen. Ezért a constrained decoding önmagában nem elegendő; a generált JSON-t mindig át kell futtatni a JSON-séma validátoron.

A grammarból nyert garancia ugyanakkor jelentős érték. Ha a generálás során a modell nem tudja elrontani a JSON szintaxisát, a hibakezelési ciklusból kikerül a leggyakoribb hibák egész osztálya. A rendszer így kevesebb újrapróbálkozást igényel, és a downstream fogyasztó stabilabb kimenetet kap.

14.3.6 Tipikus hibák és javítási rétegek

A strukturált kimenet előállításánál a hibákat célszerű rétegenként osztályozni, mert a javítási stratégia attól függ, hogy a hiba hol keletkezik.

  1. Szintaktikai hiba: a kimenet nem érvényes JSON. Javítása elsősorban constrained decodinggal vagy a generálás megismétlésével történhet. A markdown kerítés eltávolítása posztprocesszálással is megoldható, de ez nem helyettesíti a szintaktikai garanciát.

  2. Szemantikai sémaeltérés: a kimenet érvényes JSON, de nem felel meg a sémának: hiányzó kötelező mező, ismeretlen mező, rossz típus, az enum-on kívüli érték. Ezt a JSON-séma validátor fogja meg. A javítás gyakran a hibaüzenet promptba való visszacsatolásával és újragenerálással történik.

  3. Szemantikai tartalmi hiba: a kimenet séma szerint helyes, de a tartalma nem tükrözi a felhasználói szándékot. Például a query mező üres, vagy a topic értéke nem egyezik a szövegben leírt témával. Ezt a hibát csak a feladat szintjén lehet mérni, emberi vagy modellalapú kiértékeléssel.

A javítási rétegek közül a legolcsóbb a prompt javítása, ezután jön a validáció és újrapróbálkozás, majd a constrained decoding bevezetése. A constrained decoding bevezetése növeli a generálás késleltetését és számítási költségét, ezért csak akkor indokolt, ha a szintaktikai hibák aránya jelentős, vagy ha a rendszernek erős garanciákat kell adnia.

A hibakezelési ciklusban a modell generál, a validátor ellenőrzi a sémát, a hibaüzenetet visszacsatoljuk a promptba, majd újra generálunk. Ez a visszacsatolás hatékony, mert a modell figyelme ráirányul arra, hogy mit rontott el. A visszacsatolást azonban körültekintően kell megfogalmazni: ne adjunk ki belső stack trace-t a felhasználónak, és ne szivárogtassunk ki érzékeny adatokat a hibanaplóba.

14.3.9 A notebook szerkezete

A reprodukálható notebook öt lépésből áll.

  1. Környezet és verziók. A cella kiírja a Python, a PyTorch, a Transformers és a jsonschema verzióját, és menti a pip freeze kimenetét. A seedet torch.manual_seed(42) hívással rögzítjük, a generálásnál pedig do_sample=False (greedy) módot használunk, hogy a kimenet reprodukálható legyen.

  2. Séma és prompt építése. A sémát JSON-schema formátumban definiáljuk. A prompt a modell chat template-jét használja. A rendszerüzenetben elhelyezzük a feladat leírását és a sémát, a felhasználói üzenetbe pedig a szabad szöveges kérést. A generálás előtt a séma és a prompt szövegét elmentjük a reprodukciós csomag részeként.

  3. Generálás. A modellt betöltjük, és a generate függvénnyel legfeljebb 128 új tokent generálunk. A generált szöveget eltávolítjuk a promptból, és nyers kimenetként naplózzuk.

  4. Validáció és hibakezelés. A generált szöveget először megtisztítjuk az esetleges markdown kerítéstől, majd json.loads és jsonschema.validate segítségével ellenőrizzük. Ha a validáció sikertelen, a hibaüzenetet visszacsatoljuk a promptba, és újra generálunk. A folyamatot legfeljebb háromszor ismételjük.

  5. Mérés és eredmények. A notebook rögzíti, hány próbálkozás kellett az érvényes JSON-hoz, milyen típusú hiba lépett fel, és mi a végleges JSON. A mért értékeket a futtató tölti ki, a várt eredményt a séma írja le.

14.3.10 Példa notebook

Az alábbi kód szemléltetés, nem végrehajtandó utasítás. A [MÉRENDŐ] jelölések helyére a tényleges futtatás során kapott értékek kerülnek.

import json
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer
from jsonschema import validate, ValidationError

SEED = 42
MODEL_ID = "HuggingFaceTB/SmolLM2-135M-Instruct"  # ellenőrizendő revízió
MAX_ATTEMPTS = 3
MAX_NEW_TOKENS = 128

torch.manual_seed(SEED)

# A séma ugyanaz, mint a szövegben fent.
schema = {
    "$schema": "https://json-schema.org/draft/2020-12/schema",
    "type": "object",
    "properties": {
        "query": {"type": "string"},
        "limit": {"type": "integer", "minimum": 1, "maximum": 20},
        "language": {"type": "string", "enum": ["hu", "en", "de"]},
        "topic": {"type": "string", "enum": ["llm", "data", "security", "other"]},
        "allow_preprint": {"type": "boolean"}
    },
    "required": ["query", "limit", "language", "topic", "allow_preprint"],
    "additionalProperties": False
}

tokenizer = AutoTokenizer.from_pretrained(MODEL_ID)
model = AutoModelForCausalLM.from_pretrained(MODEL_ID, torch_dtype=torch.float32)

system_msg = (
    "Te egy könyvtári kereső asszisztens vagy. "
    "A felhasználó kéréséből készíts JSON objektumot a következő séma szerint:\n"
    f"{json.dumps(schema, ensure_ascii=False, indent=2)}\n"
    "Csak a JSON-t add vissza, magyarázat nélkül, markdown kerítés nélkül."
)

user_text = (
    "Keresek magyar nyelvű könyveket a nagy nyelvi modellekről, "
    "maximum 5 találat, preprint is érdekel."
)

def make_prompt(user_text, schema_json, previous_error=None):
    messages = [
        {"role": "system", "content": system_msg},
        {"role": "user", "content": user_text},
    ]
    if previous_error:
        messages.append({
            "role": "user",
            "content": f"Az előző kimenet érvénytelen volt: {previous_error} "
                       "Javítsd ki, és csak a JSON-t add vissza."
        })
    return tokenizer.apply_chat_template(
        messages, tokenize=False, add_generation_prompt=True
    )

def generate(prompt):
    inputs = tokenizer(prompt, return_tensors="pt")
    with torch.no_grad():
        outputs = model.generate(
            **inputs,
            max_new_tokens=MAX_NEW_TOKENS,
            do_sample=False,
            pad_token_id=tokenizer.eos_token_id,
        )
    generated_ids = outputs[0][inputs.input_ids.shape[1]:]
    return tokenizer.decode(generated_ids, skip_special_tokens=True)

def clean_json(text):
    # Példa: ```json ... ``` kerítés eltávolítása, ha jelen van.
    if text.startswith("```"):
        text = text.split("```", 2)[1]
        if text.startswith("json"):
            text = text[4:]
    return text.strip()

def validate_json(text, schema):
    try:
        data = json.loads(clean_json(text))
        validate(instance=data, schema=schema)
        return data, None
    except json.JSONDecodeError as e:
        return None, f"JSONDecodeError: {e}"
    except ValidationError as e:
        return None, f"ValidationError: {e.message}"

previous_error = None
final_data = None
attempts = 0

for attempt in range(1, MAX_ATTEMPTS + 1):
    attempts = attempt
    prompt = make_prompt(user_text, schema, previous_error)
    raw = generate(prompt)
    print(f"Próbálkozás {attempt}: {raw[:200]}")  # [MÉRENDŐ]
    data, error = validate_json(raw, schema)
    if error is None:
        final_data = data
        break
    previous_error = error

if final_data is None:
    raise RuntimeError(f"Nem sikerült valid JSON-t generálni {MAX_ATTEMPTS} próbálkozás után.")

print("Érvényes JSON generálva.")  # [MÉRENDŐ]
print(json.dumps(final_data, ensure_ascii=False, indent=2))  # [MÉRENDŐ]

A fenti kódban a generálás greedy módban fut, így reprodukálható, de a hőmérséklet 0-ra állításával a modell mindig ugyanazt a kimenetet adja. Ha hibás, akkor a visszacsatolás nélkül a greedy dekódolás ugyanazt a hibát ismétli; ezért a retry ciklus csak akkor hatékony, ha a generálás nem teljesen determinisztikus. A laborban ezért érdemes a generálást do_sample=True és rögzített seeddel, valamint alacsony hőmérséklettel futtatni, hogy a hibajavítási ciklusnak legyen esélye eltérő kimenetet adni. A fenti kódban a do_sample=False a reprodukálhatóságot szolgálja; a futtató választhat mintavételezést is, de akkor a seedet és a hőmérsékletet rögzíteni kell.

A várt eredmény a séma szerinti JSON, a mért eredmény pedig a notebook által kiírt final_data és a próbálkozások száma. A notebookot a requirements.txt fájllal együtt, a generált JSON-nal és a validációs loggal együtt kell elmenteni.

14.3.11 Összefoglalás

A strukturált kimenet megbízható előállítása nem egyszeri prompttrükk, hanem rétegzett mérnöki folyamat. A JSON-séma a szerződés, a function calling az alkalmazási minta, a constrained decoding pedig a szintaktikai garancia. A három réteg közül egyik sem helyettesíti a másikat: a séma nélkül nincs mit validálni, a function calling nélkül nehéz a hívási szándékot közvetíteni, a constrained decoding nélkül pedig a modell szabadon eltérhet a JSON nyelvtantól. A laborban bemutatott validációs és hibakezelési ciklus a rendszer utolsó védelmi vonala, amely a dekódoló hibáit is elkapja, és visszacsatolást ad a generálásnak.
