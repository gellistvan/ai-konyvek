22.1 Token- és GPU-költség modellezése

A nyelvi modell alapú rendszerek költsége ritkán írható le egyetlen számmal. A fejlesztés során a tokenalapú API-díj tűnik a legkézenfekvőbbnek, produkcióban azonban a GPU-óra, a kihasználtság és a kiszolgált terhelés együtt határozzák meg, hogy egy adott megoldás gazdaságilag fenntartható-e. Ebben az alfejezetben a költségmodell építőelemeit járjuk körbe: mit jelent a tokenár, hogyan számolunk GPU-órával, miként befolyásolja a terhelés és a kihasználtság a fajlagos költséget, és mely hibák vezetnek leggyakrabban rossz döntéshez. A fejezet végén egy reprodukálható notebook-labor három eltérő terhelési profilon mutatja be a modellt.

22.1.1 1. Az LLM-költség összetevői

Az LLM-alkalmazás teljes költségét három nagy csoportra bonthatjuk:

  1. Tokenalapú költségek – amikor külső API-t használunk, az árazás jellemzően a feldolgozott input- és output-tokenek száma alapján történik. Ez a modell használatának közvetlen, változó költsége.
  2. Számítási kapacitás költsége – amikor saját modellt hosztolunk, a GPU-k, CPU-k, memória és a kapcsolódó infrastruktúra óra- vagy havidíjas költsége. Ez akkor is felmerül, ha a kapacitás nincs teljesen kihasználva.
  3. Fix és működési költségek – adattárolás, hálózati forgalom, monitorozás, naplózás, biztonsági eszközök, valamint az emberi munka (üzemeltetés, kiértékelés, jogi átvilágítás).

Ebben az alfejezetben az első két csoportra koncentrálunk, mert ezek modellezhetők közvetlenül token- és GPU-óra alapon. A fix költségeket a következő egységekben (make-or-buy, ROI) részletezzük.

Fontos elv: a költségmodell mindig két számítási utat különít el:

  • Várt érték – a tervezett terhelés, a dokumentált árazás és a feltételezett kihasználtság alapján levezetett érték.
  • Mért érték – a valós rendszerből, terheléstesztből vagy számlából származó adat.

A kettő eltérése a modell pontosságát és a feltételezések minőségét mutatja. A laborban ezt a két oszlopot explicit módon szétválasztjuk.

22.1.2 2. Tokenár és API-költség

A tokenalapú API-árazás általában input és output tokenenként vagy egymillió tokenre vetítve adott. Az output tokenek jellemzően drágábbak, mert a generálás során a modell minden egyes output token előállításához újra és újra feldolgozza a teljes eddigi szekvenciát, miközben az input feldolgozása egyszeri, párhuzamosítható művelet. A pontos árak modellenként és szolgáltatónként eltérnek, és a gyártói dokumentációban ellenőrizendők; itt a képletekhez helyőrző árakat használunk.

Jelölje:

  • pinp_{\text{in}} az input tokenek egységárát (például USD per 1 millió token),
  • poutp_{\text{out}} az output tokenek egységárát,
  • TinT_{\text{in}} a feldolgozott input tokenek számát,
  • ToutT_{\text{out}} a generált output tokenek számát.

Ekkor egy API-hívás vagy egy számlázási időszak tokendíja:

CAPI=pin⋅Tin+pout⋅Tout. C_{\text{API}} = p_{\text{in}} \cdot T_{\text{in}} + p_{\text{out}} \cdot T_{\text{out}}.

A gyakorlatban a tokeneket milliós nagyságrendben számoljuk, így a képletben a pp értékeket gyakran USD / 1M token dimenzióban adjuk meg, a TT értékeket pedig millió tokenben. A mértékegység-egyezést mindig ellenőrizni kell: ha pp dimenziója USD / 1M token, akkor TT-t is millió tokenben kell behelyettesíteni, különben hat nagyságrendnyi hibát kapunk.

Példa. Tegyük fel, hogy egy modell input ára 0,500{,}50 USD per 1M token, output ára 1,501{,}50 USD per 1M token. Egy hónapban a rendszer 120120 millió input tokent és 3030 millió output tokent dolgoz fel. Ekkor:

CAPI=0,50⋅120+1,50⋅30=60+45=105 USD. C_{\text{API}} = 0{,}50 \cdot 120 + 1{,}50 \cdot 30 = 60 + 45 = 105 \text{ USD}.

Ez a legegyszerűbb, de még mindig gyakran elrontott számítás. A tipikus hiba, hogy valaki csak az input tokent veszi figyelembe, vagy a teljes tokent egyetlen árral szorozza. A másik gyakori hiba a szó és token összekeverése: egy angol nyelvű szövegben átlagosan egy token körülbelül 0,75 szónak felel meg, de ez nyelvtől, tokenizertől és szövegtípustól függ. A költségmodellhez mindig a tokenizer encode kimenetének hosszát kell alapul venni, nem a szavak számát.

Egyes szolgáltatók cache-kedvezményt adnak: ha ugyanazt a promptot ismételten elküldjük, a cache-elt input tokenek olcsóbbak. Ezt a költségmodellben külön tokenkategóriaként kell szerepeltetni:

CAPI=pin, friss⋅Tin, friss+pin, cache⋅Tin, cache+pout⋅Tout. C_{\text{API}} = p_{\text{in, friss}} \cdot T_{\text{in, friss}} + p_{\text{in, cache}} \cdot T_{\text{in, cache}} + p_{\text{out}} \cdot T_{\text{out}}.

A cache találati arány a promptok ismétlődésétől és a cache időablakától függ; ezt a paramétert a terhelési profil részeként kell megbecsülni.

22.1.3 3. GPU-óra és saját hoszting

Saját hoszting esetén a költség alapegysége a GPU-óra. Egy adott GPU típus (például A100, H100, L4) bérleti vagy amortizációs óradíja ismert, és a szükséges GPU-k számát a terhelésből vezetjük le. A GPU-óra költség modellje:

CGPU=nGPU⋅thours⋅pGPU/hour, C_{\text{GPU}} = n_{\text{GPU}} \cdot t_{\text{hours}} \cdot p_{\text{GPU/hour}},

ahol:

  • nGPUn_{\text{GPU}} a párhuzamosan futó GPU-k száma,
  • thourst_{\text{hours}} az üzemidő órában,
  • pGPU/hourp_{\text{GPU/hour}} egy GPU óradíja (bérleti díj vagy teljes bekerülési költség amortizálva az élettartamra, energia- és hűtési költséggel együtt).

A GPU-óra csak akkor hasonlítható össze az API tokendíjjal, ha kiszámítjuk a fajlagos tokenköltséget:

ptoken, saját=CGPUTtotal, p_{\text{token, saját}} = \frac{C_{\text{GPU}}}{T_{\text{total}}},

ahol TtotalT_{\text{total}} az adott időszakban kiszolgált összes input és output token – vagy az egyszerűség kedvéért az összes generált output token, ha a költséget a generált tartalomra vetítjük. A konzisztens nevező kiválasztása döntő: ha API-val hasonlítunk, ugyanazt a tokenhalmazt kell mindkét oldalon szerepeltetni.

Példa. Egyetlen L4 GPU óradíja 0,700{,}70 USD. A modell egy hónapban (720 óra) folyamatosan fut, és ezalatt 1,21{,}2 milliárd output tokent generál. A GPU-költség:

CGPU=1⋅720⋅0,70=504 USD. C_{\text{GPU}} = 1 \cdot 720 \cdot 0{,}70 = 504 \text{ USD}.

A fajlagos tokenköltség:

ptoken, saját=5041,2 milliárd token=0,42 USD / 1M token. p_{\text{token, saját}} = \frac{504}{1{,}2 \text{ milliárd token}} = 0{,}42 \text{ USD / 1M token}.

Ez első pillantásra versenyképes lehet egy 1,501{,}50 USD per 1M token output árú API-hoz képest, de a kép csak akkor teljes, ha a GPU valóban ki is szolgálta ezt a tokenmennyiséget. Ha a GPU kihasználtsága alacsony, a fajlagos költség meredeken emelkedik – ezt a következő szakasz tárgyalja.

22.1.4 A GPU-óra ár meghatározása

A pGPU/hourp_{\text{GPU/hour}} érték nem csupán a felhőszolgáltató által listázott óradíj. Saját hardver esetén a teljes tulajdonlási költség (TCO) elemei:

  • hardver bekerülési költsége osztva az amortizációs élettartammal,
  • energiafogyasztás és hűtés,
  • adatközponti hely, hálózat,
  • karbantartás és tartalék alkatrészek,
  • a hardver elavulásából adódó kockázat.

Egy gyakori egyszerűsítés, hogy a teljes TCO-t a hardver listaárának 1,3–1,5-szeresére becsüljük az élettartamra vetítve, majd ezt óradíjra osztjuk. Ez a szorzó azonban erősen függ a helyszíntől és az energiaártól, ezért minden modellben explicit feltételezésként kell rögzíteni.

22.1.5 4. Terhelés, throughput és kapacitástervezés

A terhelés definiálja, hogy hány felhasználó, milyen gyakran, mekkora bemenettel és kimenettel éri el a rendszert. A költségmodellhez legalább a következő paramétereket kell becsülni:

  • QPS (queries per second, másodpercenkénti kérések) vagy RPM (requests per minute),
  • átlagos input token kérésenként,
  • átlagos output token kérésenként,
  • átlagos párhuzamosság vagy csúcs/párhuzamosság, ha a terhelés időben változik,
  • napi vagy havi összes kérés és ebből a teljes tokenmennyiség.

A terhelésből számítható a szükséges GPU-k száma egy adott modell és hardver esetén. Ehhez ismernünk kell a modell átviteli sebességét (throughput) token per másodpercben, amely a következőktől függ:

  • a modell mérete és architektúrája,
  • a hardver típusa,
  • a batch mérete,
  • a szekvencia hossza,
  • a használt precision (FP16, BF16, INT8, INT4),
  • az inferencia motor (vLLM, TGI, TensorRT-LLM stb.).

A pontos throughputot mindig méréssel kell meghatározni, nem katalógusadatokból. A költségmodellben ezért a throughput bemeneti paraméter, amelyet a labor notebook egy MEASURED konstansként kezel, szemben a EXPECTED becsléssel.

A minimálisan szükséges GPU-k száma közelítőleg:

nGPU≈szükséges output token/segy GPU output token/s. n_{\text{GPU}} \approx \frac{\text{szükséges output token/s}}{\text{egy GPU output token/s}}.

Az input tokeneket is figyelembe kell venni, mert a prefill fázis számítási igénye más, mint a generálásé. A gyakorlatban a teljes throughputot a prefill és a decode fázis együttesen határozza meg; a pontos modellhez a következő fejezetekben tárgyalt folyamatos batching és PagedAttention ismerete szükséges. Itt elég annyi, hogy a költségmodellben ne becsüljük alá a batch és a szekvencia hossz hatását: egy hosszú inputokat feldolgozó RAG-rendszer sokkal több GPU-órát igényel ugyanannyi output tokenre, mint egy rövid chat-üzeneteket generáló chatbot.

22.1.6 5. Kihasználtság és effektív tokenköltség

A saját hoszting leggyakoribb buktatója a kihasználtság figyelmen kívül hagyása. Ha egy GPU rendelkezésre áll, de nincs elegendő kérés a teljes kapacitás kihasználásához, akkor a fajlagos tokenköltség a kihasználtsággal fordítottan arányosan nő.

Legyen u∈(0,1]u \in (0,1] a GPU-idő azon hányada, amelyben a hardver ténylegesen hasznos inferenciát végez (a várakozási, hidegindítási, skálázási és karbantartási időt nem számítva). Az effektív GPU-óradíj ekkor:

pGPU, eff=pGPU/houru. p_{\text{GPU, eff}} = \frac{p_{\text{GPU/hour}}}{u}.

Ez azt fejezi ki, hogy ha egy 0,70 USD/óra díjú GPU-t csak 40%-os kihasználtsággal futtatunk, akkor a ténylegesen hasznos számítási óráért:

0,700,40=1,75 USD \frac{0{,}70}{0{,}40} = 1{,}75 \text{ USD}

fizetünk. Az effektív tokenköltség ebből adódóan:

ptoken, saját=pGPU, eff⋅thoursTtotal, p_{\text{token, saját}} = \frac{p_{\text{GPU, eff}} \cdot t_{\text{hours}}}{T_{\text{total}}},

vagy másképpen: ha a GPU teljes kihasználtság mellett XX tokent tudna generálni óránként, akkor uu kihasználtságnál a tényleges óránkénti tokenmennyiség X⋅uX \cdot u, és a fajlagos költség ennek megfelelően magasabb.

A kihasználtság nem csak a kereslet hiányából adódhat. A batch méret és a maximális szekvencia hossz is meghatározza, hogy a GPU memóriája mennyi párhuzamos kérést tud fogadni. Ha a memória korlát miatt a batch méret alacsony, akkor a GPU számítási egységei kihasználatlanok maradnak, és a throughput csökken. Ezért a költségmodellben a batch méretet és a KV cache memóriaigényét is össze kell kötni a hardver specifikációjával. A korábbi fejezetekből ismert, hogy a KV cache mérete:

MKV=2⋅L⋅H⋅dhead⋅nlayers⋅batch⋅bytes, M_{\text{KV}} = 2 \cdot L \cdot H \cdot d_{\text{head}} \cdot n_{\text{layers}} \cdot \text{batch} \cdot \text{bytes},

ahol LL a szekvenciahossz, HH a figyelmi fejek száma, dheadd_{\text{head}} a fejméret, nlayersn_{\text{layers}} a rétegek száma, bytes pedig a precision bájtjai. Ez a memóriaigény közvetlenül korlátozza a maximális batch méretet, tehát a kihasználtságot és ezen keresztül a költséget is. A költségmodellnek nem kell ezt a képletet minden lépésben újraszámolnia, de a hardver memóriáját és a modell KV cache igényét explicit paraméterként kell kezelnie.

22.1.7 6. Gyakori hibák és helyes megoldásaik

  1. A token és a szó összekeverése.
    Tévhit: „Egy 1000 szavas dokumentum 1000 token.”
    Valóság: a tokenizálás a szavakat gyakran több tokenre bontja, és a speciális karakterek, kódok, magyar toldalékok tovább növelik a darabszámot.
    Helyes megoldás: mindig a tokenizerrel számoljunk, és a költségmodellben a tokenek számát rögzítsük.

  2. Csak az input vagy csak az output token árával számolás.
    Tévhit: „A modell olcsó, mert az input token 0,50 USD.”
    Valóság: az output token gyakran 2–5-ször drágább, és a generált válaszok hossza jelentős.
    Helyes megoldás: a teljes költségképletben mindkét irány szerepeljen, a terhelési profilból pedig külön TinT_{\text{in}} és ToutT_{\text{out}} adódjon.

  3. A kihasználtság elhanyagolása a saját hosztingnál.
    Tévhit: „Az L4 óradíja 0,70 USD, tehát olcsóbb, mint az API.”
    Valóság: ha a GPU csak 30%-ban fut, az effektív óradíj 2,33 USD, és a fajlagos tokenköltség könnyen az API fölé kerül.
    Helyes megoldás: a modellben mindig szerepeljen a kihasználtsági tényező, és a döntés előtt mérjük is meg.

  4. A batch méret hatásának figyelmen kívül hagyása.
    Tévhit: „Egy GPU elegendő, mert a modell 50 token/s sebességgel generál.”
    Valóság: a throughput batch-től függ, és a memória korlát miatt előfordulhat, hogy csak kis batch fér el, így a számítási egységek kihasználatlanok.
    Helyes megoldás: a tényleges throughputot adott batch méret és szekvencia hossz mellett mérjük, és ezt használjuk a kapacitástervezésben.

  5. A fix költségek teljes elhanyagolása.
    Tévhit: „A tokenköltség az egyetlen költség.”
    Valóság: a monitorozás, naplózás, adattárolás, hálózat és a csapat ideje is költség.
    Helyes megoldás: a token- és GPU-költség mellett külön kategóriaként tüntessük fel a működési költségeket, és csak a teljes kép alapján hozzunk döntést.

22.1.8 7. Labor: költségmodell három terhelésre

A labor célja, hogy egy reprodukálható notebookban modellezzük három, egymástól jól elkülöníthető terhelési profil teljes költségét, összehasonlítva az API- és a saját GPU-alapú utat. A notebook a fejezet elveit követi: rögzített seed, környezet, adatverzió, valamint a várt és mért értékek szétválasztása.

22.1.9 Követelmények

  • Környezet: Python 3.12+, numpy, pandas, matplotlib. A requirements.txt vagy uv.lock rögzíti a csomagverziókat.
  • Determinizmus: a notebook elején seed = 42, a véletlenszám-generátor használata esetén numpy.random.default_rng(seed); ahol nincs véletlen, a determinizmus a konstansokból adódik.
  • Adat: a terhelési profilok konstansként definiáltak a notebookban; az adatverziót a notebook élén kommentben rögzítjük, például DATA_VERSION = "2025-01-15-profiles-v1".
  • Két oszlop: minden számítás egy EXPECTED (a bemeneti paraméterekből levezetett) és egy MEASURED (a labor során futtatott ellenőrző számításból kapott) értéket ad vissza. A notebook a kettőt egy táblázatban megjeleníti, és az eltérést explicit módon jelzi.

22.1.11 A notebook felépítése

A notebook a következő cellákat tartalmazza:

  1. Konstansok: SEED, DATA_VERSION, GPU_PRICING, API_PRICING, UTILIZATION, THROUGHPUT.
  2. Profilok definíciója: a három terhelési profil mint dataclass vagy dict.
  3. Tokenköltség-számítás: mindhárom profilra kiszámítja a havi input/output tokent és az API-díjat a fenti képletekkel.
  4. GPU-kapacitás-számítás: a mért throughput alapján kiszámítja a szükséges GPU-k számát, majd a kihasználtsággal korrigált GPU-órát és a fajlagos tokenköltséget.
  5. Összehasonlítás: táblázat a három profilra: API_COST, GPU_COST, EFFECTIVE_TOKEN_COST, UTILIZATION.
  6. Validáció: egy-egy assert ellenőrzi, hogy a számított API-költség megegyezik az EXPECTED értékkel; a MEASURED értékeket a notebook cella kimenete adja.

A notebook nem futtat valódi modellt; a THROUGHPUT értékét a fejezetben leírt módon mérésből kell behelyettesíteni, de a laborban egy megadott, dokumentált becsléssel dolgozunk, amelyet EXPECTED címkével látunk el. A kódvázlat:

# cost_model.py
from dataclasses import dataclass

@dataclass(frozen=True)
class WorkloadProfile:
    name: str
    rps: float
    avg_input_tokens: int
    avg_output_tokens: int
    hours_per_day: float
    requests_per_month: int

@dataclass(frozen=True)
class Pricing:
    api_input_per_mtok: float
    api_output_per_mtok: float
    gpu_hour: float
    utilization: float  # 0 < u <= 1
    gpu_throughput_tokens_per_sec: float  # mért output token/s

def monthly_tokens(profile: WorkloadProfile) -> tuple[int, int]:
    # helyőrző: a valós számítás a requests_per_month-ból indul
    total_input = profile.requests_per_month * profile.avg_input_tokens
    total_output = profile.requests_per_month * profile.avg_output_tokens
    return total_input, total_output

def api_cost(tokens_in: int, tokens_out: int, price: Pricing) -> float:
    return (price.api_input_per_mtok * tokens_in / 1_000_000 +
            price.api_output_per_mtok * tokens_out / 1_000_000)

def gpu_cost(tokens_out: int, price: Pricing, hours: float) -> float:
    # szükséges GPU-k becslése a mért output throughput-ból
    required_gpus = (tokens_out / hours / 3600) / price.gpu_throughput_tokens_per_sec
    return required_gpus * hours * price.gpu_hour / price.utilization

A fenti kód nem produkálható végrehajtható utasításként valós adatokkal; a labor résztvevője a konkrét profilokat és a mért throughputot behelyettesíti. A reprodukálhatóság érdekében a notebook a EXPECTED értékeket egy külön validation.json fájlban tárolja, amely a környezetverzióval együtt rögzített.

22.1.12 Ellenőrző kérdések

A fejezet végén ellenőrizze a megértést:

  1. Egy rendszer havi 400M input és 100M output tokent dolgoz fel. Az API input ára 0,40 USD/1M token, output ára 1,20 USD/1M token. Mennyi a havi tokendíj? (Válasz: 160 + 120 = 280 USD.)
