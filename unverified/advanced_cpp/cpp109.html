28.4 Observer vs. pub-sub és eseménybiztonság

Az eseményvezérelt rendszerekben két alapvető értesítési modellt különíthetünk el: a közvetlen observer (megfigyelő) mintát és a közvetett publish–subscribe (pub-sub) mintát. A kettő közötti különbség nem pusztán szintaktikai: meghatározza a komponensek közötti kapcsolat szorosságát, az élettartam kezelését, a szálbiztonsági stratégiát, a hibaterjedés módját és a tesztelhetőséget. Ebben az alfejezetben a két modellt C++20/23 eszközökkel vizsgáljuk meg, kiemelve a tipikus buktatókat és a helyes implementációs mintákat. A labor egy reprodukálható, összehasonlító példát ad, amely döntési mátrixszal és mérési naplóval zárul.

28.4.1 Az observer minta: közvetlen értesítés

Az observer mintában a subject (tárgy, megfigyelt objektum) nyilvántartja a hozzá regisztrált observer (megfigyelő) objektumokat, és állapotváltozáskor közvetlenül meghívja azok frissítő metódusait. A kapcsolat tehát szoros: a subject ismeri a megfigyelőit, és a hívás szinkron módon, a subject notify metódusát futtató szálon történik.

Egy leegyszerűsített, de a lényegi tulajdonságokat mutató implementáció a következő:

#include <functional>
#include <vector>
#include <memory>
#include <mutex>
#include <algorithm>

struct SensorData {
    int sensor_id;
    double value;
};

class Subject {
public:
    using Token = std::size_t;

    Token subscribe(std::function<void(const SensorData&)> cb) {
        std::lock_guard lock{mtx_};
        Token token = next_token_++;
        callbacks_.push_back({token, std::move(cb)});
        return token;
    }

    void unsubscribe(Token token) {
        std::lock_guard lock{mtx_};
        std::erase_if(callbacks_, [token](const auto& entry) {
            return entry.token == token;
        });
    }

    void notify(const SensorData& data) {
        // Másolat készítése a mutex alatt, hogy a callback ne a zárolt szakaszban fusson.
        std::vector<std::function<void(const SensorData&)>> snapshot;
        {
            std::lock_guard lock{mtx_};
            snapshot.reserve(callbacks_.size());
            for (const auto& entry : callbacks_) {
                snapshot.push_back(entry.cb);
            }
        }
        // Szinkron callback hívás a hívó szálán, mutex nélkül.
        for (const auto& cb : snapshot) {
            cb(data);
        }
    }

private:
    struct CallbackEntry {
        Token token;
        std::function<void(const SensorData&)> cb;
    };

    std::mutex mtx_;
    std::vector<CallbackEntry> callbacks_;
    Token next_token_ = 0;
};

A fenti kódban a subscribe egy egyedi tokent ad vissza, amellyel az observer leiratkozhat. A notify kizárólag a callback lista másolatát készíti el a mutex alatt, majd a másolaton kívül hajtja végre a hívásokat. Ezzel elkerüljük, hogy a callbackek a Subject belső mutexét tartsák, ami holtpontot okozhatna, ha egy callback például újra belépne a subjectbe, vagy más szálra várna.

Az observer minta előnyei:

  • Determinizmus: a notify hívás sorrendje általában a regisztráció sorrendjét követi, és minden callback ugyanabban a szálban fut.
  • Egyszerű hibakezelés: a callback kivétele közvetlenül a hívó szálra terjed, így a notify hívója dönthet arról, hogyan kezeli.
  • Alacsony késleltetés: nincs üzenetsor vagy szálváltás, a hívás közvetlen.

Hátrányai:

  • Szoros csatolás: a subjectnek ismernie kell a megfigyelőit, és a megfigyelőknek a subjectet. Ez megnehezíti a moduláris felépítést és a tesztelést.
  • Élettartam-problémák: ha egy observer anélkül semmisül meg, hogy leiratkozna, a subject függő pointert/function objektumot tart, és a notify undefined behaviorhez vezethet. A tokenes leiratkozás RAII-objektumba csomagolható, de ez további tervezést igényel.
  • Szálbiztonsági korlátok: a szinkron hívás azt jelenti, hogy a callbackek a producer szálán futnak, ami hosszú műveletek esetén blokkolja a termelőt, és nehéz párhuzamosítani.

28.4.2 A pub-sub minta: közvetett értesítés

A pub-sub mintában a résztvevők nem ismerik egymást. A publisher (közzétevő) egy broker (üzenetközvetítő) felé publikál eseményeket, a subscriber (előfizető) pedig ugyanezen a csatornán keresztül regisztrál az adott témára. A broker feladata a routing és az esetleges aszinkron kézbesítés. A C++-ban ez jellemzően egy saját eseménybuszt jelent, de akár hálózati üzenetsor (pl. AMQP, MQTT) is lehet.

Egy egyszerű, aszinkron brokert mutat be a következő kód, amely egyetlen worker szálon fogyasztja a munkasort, és weak_ptr-rel követi a subscriberek élettartamát:

#include <deque>
#include <functional>
#include <memory>
#include <mutex>
#include <stop_token>
#include <thread>
#include <vector>
#include <optional>
#include <condition_variable>
#include <string>
#include <cstddef>
#include <utility>

class EventBus {
public:
    using SubscriberId = std::size_t;

    // A feliratkozó a tokent birtokolja; a token életben tartja a callbacket.
    // A bus csak weak_ptr-t tárol, így a token eldobásakor a callback lejár,
    // és a dispatch kihagyja.
    struct SubscriptionToken {
        SubscriberId id;
        std::shared_ptr<std::function<void(const SensorData&)>> keep_alive;
    };

    SubscriptionToken subscribe(std::string topic,
                                std::function<void(const SensorData&)> cb) {
        std::lock_guard lock{mtx_};
        auto id = next_id_++;
        auto cb_ptr = std::make_shared<std::function<void(const SensorData&)>>(std::move(cb));
        subscribers_.push_back({id, std::move(topic), cb_ptr});
        return {id, std::move(cb_ptr)};
    }

    void unsubscribe(SubscriberId id) {
        std::lock_guard lock{mtx_};
        std::erase_if(subscribers_, [id](const Subscription& s) { return s.id == id; });
    }

    void publish(std::string topic, SensorData data) {
        {
            std::lock_guard lock{mtx_};
            queue_.push_back({std::move(topic), std::move(data)});
        }
        cv_.notify_one();
    }

    void run(std::stop_token stoken) {
        while (!stoken.stop_requested()) {
            std::unique_lock lock{mtx_};
            cv_.wait(lock, [&] {
                return stoken.stop_requested() || !queue_.empty();
            });
            if (stoken.stop_requested() && queue_.empty()) break;
            auto item = std::move(queue_.front());
            queue_.pop_front();
            lock.unlock();
            dispatch(item);
        }
    }

private:
    struct Subscription {
        SubscriberId id;
        std::string topic;
        std::weak_ptr<std::function<void(const SensorData&)>> cb;
    };

    struct QueuedEvent {
        std::string topic;
        SensorData data;
    };

    void dispatch(const QueuedEvent& item) {
        std::vector<std::shared_ptr<std::function<void(const SensorData&)>>> callbacks;
        {
            std::lock_guard lock{mtx_};
            for (const auto& sub : subscribers_) {
                if (sub.topic == item.topic) {
                    if (auto cb = sub.cb.lock()) {
                        callbacks.push_back(std::move(cb));
                    }
                }
            }
        }
        // A callbackek a broker szálán futnak.
        for (const auto& cb : callbacks) {
            (*cb)(item.data);
        }
    }

    std::mutex mtx_;
    std::condition_variable_any cv_;
    std::deque<QueuedEvent> queue_;
    std::vector<Subscription> subscribers_;
    SubscriberId next_id_ = 0;
};

A publish a hívó szálon csak a munkasorba helyezi az eseményt, majd értesíti a worker szálat. A run fut a worker szálon, kiveszi a sor elejét, és meghívja a megfelelő callbackeket. A subscriberek weak_ptr segítségével tárolódnak, így ha az eredeti subscriber objektum megsemmisül, a broker nem hívja a callbacket, de a regisztrációt később takaríthatjuk.

A pub-sub előnyei:

  • Laza csatolás: a publisher és a subscriber egymástól függetlenül fejleszthető, tesztelhető, akár külön folyamatban is futhat.
  • Aszinkronitás: a publisher nem blokkolódik a subscriberek lassú működése miatt; a terhelést a broker és a subscriberek szálai nyelik el.
  • Skálázhatóság: több broker vagy több worker szál könnyebben bevezethető.

Hátrányai:

  • Nincs determinisztikus sorrend: a callbackek végrehajtási sorrendje a worker szál ütemezésétől és a sorrendtől függ; több publisher esetén az események sorrendje nem garantált.
  • Hibaterjedés bonyolultabb: a callback kivétele nem éri el a publishert, ezért külön hibacsatorna vagy hibakezelő kell.
  • Nagyobb késleltetés és overhead: a munkasor, a mutex és a szinkronizáció költsége megnő, plusz a szálváltás.

28.4.3 Coupling, lifetime és thread safety összehasonlítása

28.4.3.1 Coupling (csatolás)

Az observer minta esetén a subject és az observer közötti kapcsolat közvetlen. A subject tárolja a callbackeket, és az observernek ismernie kell a subjectet, hogy regisztrálhasson. Ez a szoros csatolás gyors és egyszerű kódot eredményez, de nehezíti a komponensek cseréjét és az egységtesztelést: a tesztben a subject valós példányát kell használni, vagy mockolni kell a kapcsolatot.

A pub-sub minta esetén a kapcsolat közvetett. A résztvevők csak a buszt ismerik, és a témák neve egyezik meg. Ez a laza csatolás lehetővé teszi, hogy a publisher és a subscriber külön modulban, sőt külön folyamatban fusson, és a tesztelés során a buszt könnyen helyettesíthetjük egy fake implementációval. Az ára a nagyobb indirekció és a nehezebb hibakeresés.

28.4.3.2 Lifetime (élettartam)

Observer esetén az élettartam-kezelés kritikus. Ha egy observer leiratkozás nélkül semmisül meg, a subjectben tárolt std::function vagy nyers pointer dangling marad, és a notify hívása undefined behavior. A helyes megoldás a RAII elv alkalmazása: a subscribe visszaad egy token, amelyet egy külön Subscription RAII-osztály birtokol, és annak destruktora automatikusan leiratkozik. Példa:

class Subscription {
public:
    Subscription(Subject& s, Subject::Token token)
        : subject_(&s), token_(token) {}

    ~Subscription() {
        if (subject_) subject_->unsubscribe(token_);
    }

    Subscription(const Subscription&) = delete;
    Subscription& operator=(const Subscription&) = delete;

    Subscription(Subscription&& other) noexcept
        : subject_(std::exchange(other.subject_, nullptr)),
          token_(std::exchange(other.token_, 0)) {}

    Subscription& operator=(Subscription&& other) noexcept {
        if (this != &other) {
            if (subject_) subject_->unsubscribe(token_);
            subject_ = std::exchange(other.subject_, nullptr);
            token_ = std::exchange(other.token_, 0);
        }
        return *this;
    }

private:
    Subject* subject_;
    Subject::Token token_;
};

Ezzel a felhasználó nem felejtheti el a leiratkozást, ha a Subscription objektum élettartama a megfigyelő objektuméval együtt ér véget.

Pub-sub esetén a broker jellemzően std::weak_ptr-rel tárolja a subscriber callbacket, mint a fenti példában. Ekkor a broker nem tartja életben a subscribert, és a megsemmisült subscriber callbackje nem hívódik. A regisztráció azonban továbbra is ott maradhat a brokerben, ami memóriaszivárgáshoz vezethet, ha nem takarítjuk. Ezt periodikusan, például a dispatch során a weak_ptr::expired() ellenőrzéssel eltávolíthatjuk. Egy másik gyakori megoldás a subscriber oldali RAII token, amely a brokeren megszünteti a regisztrációt.

28.4.3.3 Thread safety (szálbiztonság)

Az observer minta szinkron jellege miatt a callback a hívó szálon fut. Ha a notify hívás egy producer szálon történik, akkor a callbackek is ott futnak, ami miatt a producer blokkolódhat. A belső lista védelmére mutex kell, de a callbackeket a mutexen kívül kell végrehajtani, ahogy a fenti példában tettük. A szálbiztonság így megvalósítható, de a skálázhatóság korlátozott: a callbackek párhuzamosítása nehéz, és a reentrant hívások (callbackből a subject módosítása) külön odafigyelést igényelnek. A notify közbeni unsubscribe például nem érinti a már elkészített pillanatképet, tehát a leiratkozott observer egy utolsó hívást még kaphat – ezt a szemantikát dokumentálni kell.

Pub-sub esetén a broker belső állapotát (sor, subscriber lista) mutex védi, és a callbackek a broker szálán futnak. Ezzel a publisher és a subscriber szálai elválnak, ami jobb párhuzamosságot tesz lehetővé. Azonban a subscriber callbackek továbbra is sorban futnak, hacsak nem vezetünk be több worker szálat vagy subscriberenkénti sort. A publisher szálbiztonsága egyszerű: a publish csupán egy mutex alatti push, amely rövid ideig tart.

28.4.4 Hibaterjedés

Az observer minta esetén a callbackek kivételei közvetlenül a notify hívó szálára terjednek. Ez lehetővé teszi, hogy a hívó fél try/catch blokkot alkalmazzon, és el tudja dönteni, hogy mi történjen a hibákkal. A következő példa a kivételek gyűjtését mutatja:

void notify_with_error_collection(const SensorData& data) {
    std::vector<std::function<void(const SensorData&)>> snapshot;
    // ... (mutex alatti másolat)
    std::vector<std::exception_ptr> errors;
    for (const auto& cb : snapshot) {
        try {
            cb(data);
        } catch (...) {
            errors.push_back(std::current_exception());
        }
    }
    if (!errors.empty()) {
        // Naplózás vagy továbbítás a hívónak.
        // Ebben a példában az első kivételt újra dobjuk.
        std::rethrow_exception(errors.front());
    }
}

Ez a stratégia rugalmas, de a notify hívójának tisztában kell lennie azzal, hogy a callbackek hibái a saját kontextusában jelennek meg.

A pub-sub minta aszinkron jellege miatt a callback kivétele nem éri el a publishert. A brokerben a dispatch hívás során a kivételt el kell kapni, és valamilyen hibacsatornán vagy hibakezelőn keresztül kell továbbítani. Egy lehetséges megoldás, hogy a subscriber callbackje nem dob kivételt, hanem egy std::expected-et ad vissza, és a broker ezt a hibát egy külön hibakezelőnek továbbítja. C++23-ban az std::expected erre alkalmas.

Példa hiba-csatornára:

class EventBus {
public:
    void set_error_handler(std::function<void(std::exception_ptr)> handler) {
        std::lock_guard lock{mtx_};
        error_handler_ = std::move(handler);
    }

private:
    void dispatch(const QueuedEvent& item) {
        // ...
        for (const auto& cb : callbacks) {
            try {
                (*cb)(item.data);
            } catch (...) {
                auto eptr = std::current_exception();
                std::function<void(std::exception_ptr)> handler;
                {
                    std::lock_guard lock{mtx_};
                    handler = error_handler_; // másolat
                }
                if (handler) {
                    handler(eptr);
                } else {
                    // Alapértelmezés: naplózás, vagy a program leállítása
                    // a hiba jellegétől függően. Itt std::terminate hívása nem
                    // feltétlenül jó, de jelzi a nem kezelt hibát.
                    std::terminate();
                }
            }
        }
    }

    std::function<void(std::exception_ptr)> error_handler_;
};

A hibakezelő beállítása a brokeren biztosítja, hogy a subscriberek hibái ne vesszenek el, de a publisher oldali hívó nem értesül közvetlenül. Ez fontos tervezési különbség.

28.4.5 Tesztelés

Az observer minta tesztelése viszonylag egyszerű, mert a hívás szinkron és determinisztikus: a notify hívás után a teszt ellenőrizheti, hogy a callbackek meghívták-e a megfelelő metódusokat. A tesztben elegendő egy std::vector napló, amelybe a callbackek bejegyzéseket tesznek.

A pub-sub minta tesztelése bonyolultabb, mert a dispatch aszinkron. A tesztnek meg kell várnia, amíg a worker szál feldolgozza az üzenetet. Erre használhatunk std::promise/std::future, std::latch (C++20) vagy std::barrier (C++20) szinkronizációs eszközöket. A determinizmus érdekében a tesztben egyetlen publishert használjunk, és az események sorrendjét a munkasor FIFO jellege garantálja, ha csak egy szál produkál. Több publisher esetén a sorrend nem garantált, ezért a teszt csak a halmazbeli teljesülést ellenőrizze.

A szálbiztonságot és az élettartamot sanitizerekkel ellenőrizhetjük. A buildben a -fsanitize=thread,undefined,address kapcsolók használata javasolt (GCC/Clang). A laborhoz tartozó mérési napló rögzíti a sanitizer futások eredményét.

28.4.6 Labor: döntési mátrix és reprodukálható mérés

A labor célja, hogy ugyanazt a funkcionalitást observer és pub-sub módon is megvalósítsuk, teszteljük, és a két megoldást egy döntési mátrixban összehasonlítsuk. A példa egy egyszerű szenzoros rendszer: egy SensorHub (a subject vagy publisher) időnként SensorData eseményeket bocsát ki, és egy Display (observer vagy subscriber) megjeleníti azokat.

28.4.6.1 Implementáció

A fent bemutatott Subject és EventBus osztályokat használjuk. A Display mindkét esetben egy callbacket regisztrál, amely a kapott adatot egy naplóba írja. Az observer verzióban a Display a Subject-re iratkozik fel, a pub-sub verzióban pedig az EventBus-ra.

A teljes kód a labor mappában található, a CMakeLists.txt tartalma:

cmake_minimum_required(VERSION 3.20)
project(observer_pubsub_lab LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 23)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

add_executable(observer_demo observer_demo.cpp)
add_executable(pubsub_demo pubsub_demo.cpp)

target_compile_options(observer_demo PRIVATE -Wall -Wextra -Wpedantic)
target_compile_options(pubsub_demo PRIVATE -Wall -Wextra -Wpedantic)

# Sanitizer build opcionálisan:
# cmake -S . -B build-sanitize -DENABLE_SANITIZERS=ON

    target_compile_options(observer_demo PRIVATE -fsanitize=thread,undefined -fno-omit-frame-pointer)
    target_link_options(observer_demo PRIVATE -fsanitize=thread,undefined)
    target_compile_options(pubsub_demo PRIVATE -fsanitize=thread,undefined -fno-omit-frame-pointer)
    target_link_options(pubsub_demo PRIVATE -fsanitize=thread,undefined)
endif()

enable_testing()
add_test(NAME observer_basic COMMAND observer_demo)
add_test(NAME pubsub_basic COMMAND pubsub_demo)

A demók fordíthatóak és futtathatóak. Az observer demó például:

#include "subject.hpp"
#include <iostream>
#include <vector>
#include <cassert>

int main() {
    Subject subject;
    std::vector<SensorData> received;

    {
        auto sub = Subscription(subject, subject.subscribe(
            [&](const SensorData& d) { received.push_back(d); }));

        SensorData data{1, 23.5};
        subject.notify(data);

        assert(received.size() == 1);
        assert(received.front().sensor_id == 1);
        assert(received.front().value == 23.5);
    } // a Subscription destruktora itt automatikusan leiratkozik

    // A blokk után a Subscription már nem él, ezért a második notify nem
    // okoz újabb bejegyzést.
    subject.notify({2, 30.0});
    assert(received.size() == 1);

    std::cout << "Observer demo OK\n";
}

A pub-sub demó hasonló, de ott a run szálat el kell indítani és leállítani:

#include "event_bus.hpp"
#include <iostream>
#include <vector>
#include <cassert>
#include <thread>
#include <chrono>

int main() {
    EventBus bus;
    std::vector<SensorData> received;
    std::mutex mtx;

    // A token életben tartja a callbacket; amíg a token él, a bus hívhatja.
    auto token = bus.subscribe("sensor",
        [&](const SensorData& d) {
            std::lock_guard lock{mtx};
            received.push_back(d);
        });

    std::jthread worker([&](std::stop_token stoken) {
        bus.run(stoken);
    });

    bus.publish("sensor", {1, 23.5});

    // Várunk, amíg a callback lefut.
    std::this_thread::sleep_for(std::chrono::milliseconds(50));

    {
        std::lock_guard lock{mtx};
        assert(received.size() == 1);
        assert(received.front().sensor_id == 1);
        assert(received.front().value == 23.5);
    }

    worker.request_stop();
    worker.join();

    std::cout << "Pub-sub demo OK\n";
}

A fenti példák szándékosan egyszerűek, de a laborban a tesztelést CTest keretrendszerrel, sanitizerekkel és determinisztikus várakozással (pl. std::promise segítségével) végezzük.

28.4.6.2 Mérési napló

A mérési naplóban rögzíteni kell a környezetet:

  • Fordító: GCC 13.2, Clang 17, MSVC 19.38 (ahol elérhető)
  • Standard: C++23
  • Optimalizáció: -O2 (release), -O0 (debug)
  • Hardver: a naplóban megadott CPU, RAM, operációs rendszer
  • Futások száma: minden mérés 10 futtatás átlaga

A mért mennyiségek:

  • Átlagos késleltetés egy callback hívásnál (observer: notify ideje, pub-sub: a publikálástól a callback végéig)
  • Átlagos throughput 10 000 eseményre
  • Memóriahasználat a broker esetén a sor maximális hossza és a regisztrált subscriberek száma alapján

A várható eredmény: az observer kisebb késleltetést és nagyobb throughputot mutat, mert nincs munkasor és szinkronizáció, míg a pub-sub nagyobb késleltetéssel, de a publisher szálának kisebb blokkolásával jár. A mérési napló ezt számszerűsíti, és külön oszlopban jelzi a mért és a várt értékeket.

28.4.6.3 Döntési mátrix

A labor végén a következő döntési mátrixot kell kitölteni, amely a fejezet tanulságait foglalja össze:

Szempont Observer Pub-sub
Csatolás Szoros, közvetlen Laza, közvetett
Élettartam-kezelés RAII token szükséges weak_ptr vagy token, broker takarítás
Szálbiztonság Szinkron, a hívó szál fut Aszinkron, szeparált szálak
Hibaterjedés Kivétel a hívóhoz Hibacsatorna, nem éri el a publisert
Determinizmus Erős, sorrend garantált Gyengébb, sorrend nem garantált
Skálázhatóság Korlátozott Könnyen bővíthető

A mátrix nem abszolút, hanem iránymutató; a pontos választás a konkrét követelményektől függ.

28.4.7 Összefoglalás és önellenőrző kérdések

Az observer és a pub-sub közötti választás alapvetően a csatolás és a szinkronitás igénye alapján dől el. Az observer egyszerű és determinisztikus, de szoros csatolást és gondos élettartam-kezelést igényel. A pub-sub laza csatolást és aszinkronitást ad, de bonyolultabb hibakezelést és nagyobb futási költséget. A helyes döntéshez mérlegelni kell a komponensek közötti függőséget, a teljesítménykritikus utat, a hibaterjedési követelményeket és a skálázhatósági igényeket.

Önellenőrző kérdések:

  1. Miért fontos a callbackeket a mutexen kívül meghívni az observer notify metódusában?
  2. Hogyan oldható meg, hogy egy pub-sub broker ne tartson életben egy megsemmisült subscribert?
  3. Miért nem tudja a pub-sub publisher közvetlenül kezelni a subscriber callback kivételeit? Milyen alternatív hibakezelési stratégiát ismer?
  4. A laborban mért késleltetésbeli különbség hogyan indokolja az observer és a pub-sub közötti választást?

Teszteset (példa): A laborhoz tartozó CTest teszt futtatása ctest --test-dir build paranccsal, valamint a sanitizer build cmake -S . -B build-sanitize -DENABLE_SANITIZERS=ON && cmake --build build-sanitize && ctest --test-dir build-sanitize. A teszteknek sikeresen le kell futniuk, és a mérési naplót a labor könyvtárban kell elhelyezni.
