4.3 Objektum-élettartam, storage duration és lifetime

Az objektumok élettartama a C++ egyik legfontosabb absztrakciója, amely közvetlenül kapcsolódik a memóriabiztonsághoz, a RAII-hoz és az optimalizálhatósághoz. Amikor egy objektum „él”, a nyelv garantálja, hogy a memóriája érvényes, az értéke stabil, és a destruktora – ha van – pontosan egyszer fog lefutni. Ha ezt a szabályt megsértjük, undefined behaviorhez (UB) jutunk, ami gyakran biztonsági réseket vagy nehezen reprodukálható hibákat okoz. Ebben az alfejezetben az objektum keletkezésének, élettartamának és megszűnésének szabályait vizsgáljuk meg, különös tekintettel a storage duration (tárolási időtartam) fogalmára és a placement new használatára.

4.3.1 Az objektum és a tároló fogalma

A C++ szabvány megkülönbözteti a tárolót (storage) és az objektumot. A tároló egy memóriaterület, amely megfelelő méretű és igazított (aligned) ahhoz, hogy egy adott típusú objektumot befogadjon. Az objektum akkor jön létre, amikor a tárolóban megkezdődik az élettartama. Az objektum élettartama akkor kezdődik, amikor:

  • a megfelelő típusú, megfelelően igazított tároló rendelkezésre áll, és
  • ha a típus nem triviális inicializációjú, akkor az inicializáció (konstruktor) befejeződik.

Az élettartam akkor ér véget, amikor:

  • az objektum destruktora (ha van) meghívásra kerül, vagy
  • a tároló újrahasznosításra kerül, vagy felszabadul.

Fontos, hogy a tároló élettartama és az objektum élettartama nem feltétlenül esik egybe. Például egy malloc által lefoglalt memóriaterület tárolóként létezik, de amíg nem helyezünk bele objektumot new-val vagy std::construct_at-tel, addig nincs ott semmilyen (nem triviális) objektum. Hasonlóképpen, egy delete után a tároló felszabadul, és az objektum élettartama véget ér, de maga a tárterület már nem elérhető.

A tárolási időtartam (storage duration) azt határozza meg, hogy a tároló mikor jön létre és mikor szűnik meg, és ebből következően mikor élhet benne objektum. A C++ négyféle tárolási időtartamot ismer: automatic, static, thread és dynamic.

4.3.2 Automatic storage duration

Az automatikus tárolási időtartam az, amit a leggyakrabban használunk: a függvényblokkokban, static, extern vagy thread_local nélkül deklarált lokális változók esetében. A tároló a blokkba való belépéskor jön létre (gyakorlatilag a stacken), és a blokk elhagyásakor szűnik meg.

Az automatikus változók élettartama a deklaráció pontjától a blokk végéig tart, de a megsemmisítés fordított sorrendben történik a konstrukcióhoz képest. Ez a szabály teszi lehetővé, hogy a RAII objektumok biztonságosan hivatkozzanak egymásra, és hogy a destruktorok determinisztikusan fussanak le kivétel esetén is.

#include <iostream>
#include <string>

void f() {
    std::string a = "először";
    std::string b = "másodszor";
    // a és b automatikus tárolási időtartamú.
    // a blokk végén a destruktorok sorrendje: b, majd a.
}

Az automatikus tárolási időtartamú objektumok élettartama a deklarációtól a blokk végéig tart, de ha a vezérlés a deklaráció előtt ugrik be (pl. goto), a viselkedés UB. A fordítók általában figyelmeztetnek az ilyen esetekre.

4.3.3 Static storage duration

A statikus tárolási időtartamú objektumok a program teljes futási ideje alatt élnek. Ide tartoznak:

  • globális és névtér szintű változók,
  • static adattagok,
  • függvény-lokális static változók,
  • string literálok.

A statikus objektumok tárolója a program indulásakor jön létre, és a program befejezésekor szűnik meg. Az élettartamuk azonban nem feltétlenül kezdődik a program indulásával, mert az inicializáció lehet deferred (halasztott) – ez különösen fontos a függvény-lokális statikus változóknál.

A statikus inicializáció két szakaszra oszlik:

  1. Constant initialization – ha az objektum inicializálható konstans kifejezéssel, akkor ez fordítási időben vagy a program indulásakor, a dinamikus inicializáció előtt megtörténik. Az ilyen objektumok élettartama gyakorlatilag azonnal megkezdődik.
  2. Dynamic initialization – minden más statikus objektum a program indulásakor, a main meghívása előtt, a fordítási egységen belüli megjelenési sorrendben inicializálódik (a constant initialization befejezése után). A különböző fordítási egységek közötti sorrend azonban nem garantált, ami az ún. static initialization order fiasco-hoz vezethet. Ezt a problémát általában függvény-lokális statikus változókkal kerüljük el.
// fiasco példa: két fordítási egység globális változója egymásra hivatkozik.
// a.cpp:
int global_a = 42;

// b.cpp:
extern int global_a;
int global_b = global_a + 1; // UB, ha global_a még nem inicializálódott.

// Megoldás: függvény-lokális statikus.
int get_global_a() {
    static int a = 42; // thread-safe, első híváskor inicializálódik.
    return a;
}

A statikus objektumok megsemmisítése a program befejezésekor, az inicializáció befejezésének fordított sorrendjében történik. A konstans inicializálású objektumok megsemmisítése is része ennek a sorrendnek, de ha egy objektum destruktora soha nem fut le (pl. std::exit vagy std::quick_exit esetén), akkor az UB vagy implementációfüggő, ezért kerülendő.

A függvény-lokális static változók inicializálása thread-safe: a C++11 óta a szabvány garantálja, hogy ha több szál egyszerre éri el az első hívást, az inicializáció pontosan egyszer fut le, és a többi szál megvárja. Ez a Meyers-singleton alapja.

class Singleton {
public:
    static Singleton& instance() {
        static Singleton s; // thread-safe, lazy initialization
        return s;
    }
private:
    Singleton() = default;
};

4.3.4 Thread storage duration

A thread_local kulcsszóval deklarált objektumok minden szál számára külön példányban léteznek. A tároló a szál indulásakor jön létre, és a szál befejezésekor szűnik meg. Az egyes szál-példányok élettartama hasonló a statikus objektumokéhoz, de az inicializáció és a megsemmisítés az adott szálhoz kötött.

thread_local int tls_counter = 0;

void increment() {
    ++tls_counter;
    // Minden szál saját számlálóval rendelkezik.
}

A thread_local változók destruktorai a szál kilépésekor futnak le, a konstrukció fordított sorrendjében. Ha a szál std::thread objektum megsemmisítésekor még fut, a program std::terminate-t hív, így a thread_local destruktorok nem futnak le. Ezt a helyzetet el kell kerülni a std::jthread és a megfelelő csatlakoztatási mechanizmus használatával.

4.3.5 Dynamic storage duration

A dinamikus tárolási időtartamú objektumokat explicit módon hozzuk létre a new kifejezéssel, és explicit módon szüntetjük meg a delete kifejezéssel (illetve a std::allocator vagy más alacsony szintű mechanizmusokkal). A tároló a new kifejezés kiértékelésekor jön létre a heapen, és a delete kifejezéskor szabadul fel.

A dinamikus objektum élettartama a new kifejezésben meghívott konstruktor befejezésétől a delete kifejezésben meghívott destruktor végéig tart. Ha a new nem inicializálja az objektumot (pl. new int), az élettartam akkor is megkezdődik, de az érték indeterminált, kivéve, ha az objektum triviálisan default-inicializálható és a new kifejezés ()-t használ (value-initialization).

int* p = new int;          // élettartam kezdődik, de *p indeterminált.
int* q = new int();        // value-initialization, *q == 0.
delete p;                  // élettartam véget ér, tároló felszabadul.
delete q;

Fontos megjegyezni, hogy a malloc és a free nem hoz létre és nem szüntet meg objektumot. A malloc csak tárolót foglal, de nem kezdi meg az objektum élettartamát, ezért malloc eredményére közvetlenül nem szabad objektumként hivatkozni, csak placement new vagy std::construct_at után.

#include <cstdlib>
#include <new>

void* raw = std::malloc(sizeof(int));
int* p = new (raw) int(42);  // placement new: élettartam kezdődik raw-ban.
// Használjuk *p-t.
p->~int();                    // destruktor explicit hívása.
std::free(raw);               // tároló felszabadítása.

A dinamikus tárolás elengedhetetlen a futásidőben változó méretű adatokhoz, de manuális memóriakezelést igényel. A modern C++ inkább okos mutatókat (std::unique_ptr, std::shared_ptr) ajánl, amelyek RAII-elven biztosítják a delete meghívását.

4.3.6 Placement new és a lifetime kezdete

A placement new lehetővé teszi, hogy egy adott, már létező tárolóterületen explicit módon elindítsuk egy objektum élettartamát anélkül, hogy új memóriát foglalnánk. A szintaxis a new (ptr) T(args...) alakú, ahol ptr egy megfelelően igazított, elegendő méretű memóriaterületre mutat. A placement new nem hívja meg a operator new-t, így a tároló felszabadítása sem delete-tel történik.

#include <new>
#include <cstddef>
#include <type_traits>

struct Widget {
    int value;
    explicit Widget(int v) : value(v) {}
    ~Widget() { /* naplózás */ }
};

int main() {
    alignas(Widget) std::byte buffer[sizeof(Widget)];
    Widget* w = new (buffer) Widget(42); // élettartam kezdődik
    // használjuk w-t
    w->~Widget();                        // élettartam véget ér, destruktor explicit hívása
    // buffer továbbra is létezik, de nincs benne Widget objektum.
}

A C++20 bevezette a std::construct_at és std::destroy_at segédfüggvényeket, amelyek kényelmesebbé és biztonságosabbá teszik a lifetime kezelést, mivel a const és volatile minősítőket is helyesen kezelik.

#include <memory>
#include <new>

alignas(Widget) std::byte buffer[sizeof(Widget)];
Widget* w = std::construct_at(reinterpret_cast<Widget*>(buffer), 42);
// ...
std::destroy_at(w);

A placement new után a destruktor explicit meghívása kötelező, ha a típusnak van nem triviális destruktora. Ha elmulasztjuk, a destruktor nem fut le, ami erőforrás-szivárgáshoz vagy UB-hez vezet. Ha a típus triviálisan destruálható, a destruktor elhagyható, de a kód akkor is helyesebb, ha explicit hívjuk.

4.3.6.1 Alignment követelmények

A placement new által használt tárolónak megfelelően igazítottnak kell lennie a típushoz képest. Az igazítás (alignment) határozza meg, hogy a memóriacím osztható-e a típus által megkövetelt értékkel. Ha nem, a viselkedés UB. A alignas kulcsszóval biztosíthatjuk a szükséges igazítást:

alignas(Widget) std::byte buffer[sizeof(Widget)];

A std::aligned_storage C++23-ban elavult, helyette a fenti minta ajánlott. A std::aligned_alloc vagy a operator new túlterhelése is használható, de a legegyszerűbb a alignas.

4.3.6.2 Objektum újrahasznosítása

Egy objektum élettartama akkor is véget érhet, ha a tárolóját újrahasznosítjuk egy másik objektum számára, anélkül hogy a destruktort meghívnánk. Ez akkor megengedett, ha az új objektum típusa trivially destructible, vagy ha a régi objektum típusa trivially destructible, vagy ha a tároló std::byte, unsigned char, char típusú (ezek bármikor újrahasznosíthatók). Ellenkező esetben a destruktor explicit meghívása nélküli újrahasznosítás UB.

struct Trivial { int x; };  // trivially destructible

alignas(Trivial) std::byte buf[sizeof(Trivial)];
Trivial* t1 = new (buf) Trivial{1};
t1->~Trivial(); // opcionális, de ajánlott
Trivial* t2 = new (buf) Trivial{2}; // új élettartam ugyanabban a tárolóban

C++20-tól létezik az implicit-lifetime types fogalma: ha egy típus triviálisan másolható, triviálisan destruálható, és nincs nem triviális default konstruktora, akkor bizonyos műveletek (pl. malloc utáni memcpy) implicit módon létrehozhatják az objektumot. Ez a szabály megkönnyíti az alacsony szintű kódot, de a részletek ellenőrzést igényelnek a fordítói támogatás tekintetében (C++20).

4.3.7 Tipikus hibák és elkerülésük

  1. Dangling pointer/reference: automatikus objektumra mutató pointer a blokk elhagyása után.

    int* p;
{
    int local = 42;
    p = &local;
}
// *p használata UB, mert local élettartama véget ért.

    Megoldás: ne adjunk vissza mutatót vagy referenciát automatikus objektumra, vagy használjunk okos mutatót.

  2. Use-after-free: dinamikus objektum delete utáni használata.

    int* p = new int(10);
delete p;
std::cout << *p; // UB

    Megoldás: RAII, std::unique_ptr, std::shared_ptr.

  3. Double destroy: ugyanazon objektum destruktorának többszöri meghívása.

    Widget* w = new Widget(1);
delete w;
delete w; // UB: a második delete felszabadít egy már felszabadított tárolót

    Hasonlóan placement new esetén:

    alignas(Widget) std::byte buffer[sizeof(Widget)];
Widget* w = new (buffer) Widget(1);
w->~Widget();
w->~Widget(); // UB

  4. Nem megfelelő alignment: placement new rosszul igazított tárolóval.

    char buffer[sizeof(Widget)]; // char alignment általában 1, Widget nagyobbat igényel
Widget* w = new (buffer) Widget(1); // UB

  5. memcpy nem triviálisan másolható típusra: csak trivially copyable típusok másolhatók memcpy-vel. Más típus esetén a konstruktor és destruktor elmarad, ami UB.

    std::string s1 = "hello";
std::string s2;
std::memcpy(&s2, &s1, sizeof(s1)); // UB: std::string nem trivially copyable

  6. Statikus inicializációs sorrend: globális objektumok közötti függőség. Megoldás: függvény-lokális statikus.

  7. Élettartam vége utáni hozzáférés: például egy destruktor után a tagváltozókhoz való hozzáférés, vagy referencia taggal rendelkező objektum destruktora után a referencia használata.

  8. std::launder szükségessége: ha egy const objektumot vagy referencia tagot tartalmazó objektumot placement new-val újrahasznosítunk, a régi pointer használata UB lehet, mert a fordító feltételezheti, hogy a const tag nem változik. Ilyenkor std::launder-rel kell „megtisztítani” a mutatót. Ez egy haladó téma, de a lifetime szempontjából fontos.

    struct X { const int n; };
alignas(X) char buf[sizeof(X)];
X* p = new (buf) X{1};
// ...
X* q = new (buf) X{2}; // új élettartam
int n = p->n; // UB, mert p még a régi objektumra mutat
int m = std::launder(p)->n; // OK

4.3.8 Labor: lifetime- és alignment-példa

A labor célja, hogy egy kis, reprodukálható programmal demonstráljuk az objektum élettartamának kezdetét és végét, valamint a placement new és az alignment együttes használatát. A program egy LifetimeTracker osztályt használ, amely naplózza a konstrukciót, a destruktort és a másolást/mozgatást. Egy AlignedBuffer osztály sablon segítségével kezeljük a tárolót, és biztosítjuk a helyes igazítást.

4.3.8.1 A kód

#include <cstddef>
#include <iostream>
#include <memory>
#include <new>
#include <string>
#include <type_traits>
#include <vector>

struct LifetimeTracker {
    inline static int alive = 0;
    inline static int constructions = 0;
    inline static int destructions = 0;

    int id;
    std::string name;

    explicit LifetimeTracker(int i, std::string n = "unnamed")
        : id(i), name(std::move(n)) {
        ++alive;
        ++constructions;
        std::cout << "LifetimeTracker constructed: id=" << id
                  << ", name=" << name << ", alive=" << alive << '\n';
    }

    LifetimeTracker(const LifetimeTracker& other)
        : id(other.id), name(other.name) {
        ++alive;
        ++constructions;
        std::cout << "LifetimeTracker copy-constructed: id=" << id
                  << ", alive=" << alive << '\n';
    }

    LifetimeTracker(LifetimeTracker&& other) noexcept
        : id(other.id), name(std::move(other.name)) {
        ++alive;
        ++constructions;
        std::cout << "LifetimeTracker move-constructed: id=" << id
                  << ", alive=" << alive << '\n';
    }

    ~LifetimeTracker() {
        --alive;
        ++destructions;
        std::cout << "LifetimeTracker destroyed: id=" << id
                  << ", alive=" << alive << '\n';
    }
};

template <typename T>
struct AlignedBuffer {
    alignas(T) std::byte storage[sizeof(T)];

    T* ptr() noexcept {
        return reinterpret_cast<T*>(storage);
    }

    const T* ptr() const noexcept {
        return reinterpret_cast<const T*>(storage);
    }
};

int main() {
    using T = LifetimeTracker;

    // 1. Automatikus storage duration
    {
        T auto_obj(1, "auto");
        std::cout << "Inside scope, alive=" << T::alive << '\n';
    }
    std::cout << "After scope, alive=" << T::alive << '\n';

    // 2. Dynamic storage duration
    T* dyn_obj = new T(2, "dynamic");
    std::cout << "After new, alive=" << T::alive << '\n';
    delete dyn_obj;
    std::cout << "After delete, alive=" << T::alive << '\n';

    // 3. Placement new egy igazított bufferben
    AlignedBuffer<T> buf;
    std::cout << "Alignment of buffer: " << alignof(decltype(buf.storage)) << '\n';

    T* placed = std::construct_at(buf.ptr(), 3, "placed");
    std::cout << "After construct_at, alive=" << T::alive << '\n';
    std::cout << "Placed object id: " << placed->id << '\n';

    // A destruktor explicit meghívása, mert nem használunk delete-et.
    std::destroy_at(placed);
    std::cout << "After destroy_at, alive=" << T::alive << '\n';

    // 4. Ellenőrzések
    if (T::alive != 0) {
        std::cerr << "ERROR: alive count should be 0, got " << T::alive << '\n';
        return 1;
    }
    if (T::constructions != 3) {
        std::cerr << "ERROR: constructions should be 3, got " << T::constructions << '\n';
        return 1;
    }
    if (T::destructions != 3) {
        std::cerr << "ERROR: destructions should be 3, got " << T::destructions << '\n';
        return 1;
    }
    std::cout << "All lifetime checks passed.\n";
    return 0;
}

4.3.8.2 Build és futtatás

A labor buildjéhez az alábbi parancsokat használjuk, rögzített fordítókkal és standardverzióval:

GCC 13, C++20, sanitizerek:

g++ -std=c++20 -Wall -Wextra -Wpedantic -Werror \
    -fsanitize=address,undefined -fno-omit-frame-pointer \
    -o lifetime_lab lifetime_lab.cpp
./lifetime_lab

Clang 17, C++20, sanitizerek:

clang++ -std=c++20 -Wall -Wextra -Wpedantic -Werror \
    -fsanitize=address,undefined -fno-omit-frame-pointer \
    -o lifetime_lab lifetime_lab.cpp
./lifetime_lab

MSVC 19.38, C++20:

cl /std:c++20 /W4 /WX /EHsc /Zi lifetime_lab.cpp
lifetime_lab.exe

Az AddressSanitizer és az UndefinedBehaviorSanitizer futás közben ellenőrzi a memóriakezelést és a lifetime szabályokat. Ha bármilyen UB lenne, a program hibaüzenettel leáll.

4.3.8.3 Várt kimenet és mérési napló

A program a konstruktorok és destruktorok számát, valamint az élettartamok közötti átmeneteket naplózza. A várt viselkedés:

  • Összesen 3 konstrukció (automatikus, dinamikus, placement) és 3 destruktor.
  • Minden pillanatban az alive számláló értéke megegyezik az aktuálisan élő objektumok számával.
  • A futás végén az alive, constructions és destructions értékei rendre 0, 3, 3.

A mért eredmény a program kimenetében látható. A teszt a program végén automatikusan ellenőrzi az elvárásokat, így a mért és várt értékek közvetlenül összehasonlíthatók. A mérési naplóban rögzítsük a fordító verzióját, a standardverziót, az optimalizálási szintet (itt -O0 alapértelmezett, de érdemes -O2-vel is lefuttatni), valamint a sanitizerek jelenlétét. A futási idő nem releváns ebben a példában, mert a hangsúly a lifetime eseményeken van.

Megjegyzés: A std::construct_at és std::destroy_at C++20-tól érhető el. Ha a célplatformon nem elérhető, a placement new és explicit destruktor hívás használható, de a C++20-as verzió ajánlott.

4.3.10 Összegzés

Ebben az alfejezetben áttekintettük az objektumok élettartamának és a tárolási időtartamoknak a szabályait. Láttuk, hogy az objektum élettartama nem pusztán a memória meglétét jelenti, hanem a konstruktor és destruktor által határolt intervallumot. A négy storage duration típus (automatic, static, thread, dynamic) eltérő életciklusokat biztosít, és mindegyiknek megvannak a maga buktatói. A placement new és a std::construct_at lehetővé teszi az objektumok létrehozását előre lefoglalt tárolóban, de megköveteli a helyes igazítást és a destruktor kézi meghívását. A leggyakoribb hibák a lógó pointerek, a use-after-free, a double destroy és a nem megfelelő alignment. Ezek elkerülése érdekében a RAII, az okos mutatók és a sanitizerek használata javasolt. A következő egység (Non-copyable, non-movable és ownership) ezekre az alapokra építve tárgyalja a non-copyable, non-movable és ownership fogalmakat.
