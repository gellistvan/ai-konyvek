26.1 Undefined behavior és biztonsági kockázatok

A C++ szabvány szerint bizonyos programok viselkedése nincs definiálva: a fordító nem garantál semmilyen eredményt, és a program futása bármilyen módon alakulhat. Ez az undefined behavior (UB) nem egyszerűen „hiba”, hanem a nyelv szemantikájának szándékos rése, amely teret ad az optimalizálónak, de egyben a legveszélyesebb biztonsági kockázatok forrása. Ebben az alfejezetben az UB fő típusait, a signed overflow, az objektum-élettartam, a strict aliasing és a misalignment problémáit vizsgáljuk meg, hangsúlyozva a biztonsági következményeket és az ellenőrzés módszertanát.

26.1.1 Mi az undefined behavior?

Az undefined behavior olyan programkonstrukció, amelyre a szabvány nem ír elő semmilyen megfigyelhető viselkedést. A program ilyenkor: - lefordulhat, de a fordító tetszőleges kódot generálhat, - futhat „helyesen”, összeomolhat, vagy bármi mást tehet, - a viselkedés változhat optimalizálási szint, fordítóverzió vagy akár a környező kód függvényében.

A UB nem összekeverendő a nem specifikált (unspecified) vagy implementációfüggő (implementation-defined) viselkedéssel. Az előbbinél a szabvány több lehetőséget enged meg, de az eredményt dokumentálni kell; az utóbbinál a fordító szabadon választ, de a választás konzisztens. A UB esetén nincs semmilyen garancia.

A UB elsődleges oka a teljesítmény: a szabványalkotók szándékosan hagynak olyan eseteket definiálatlanul, amelyeket nehéz vagy költséges lenne ellenőrizni futásidőben. Például a signed overflow ellenőrzése minden aritmetikai műveletnél lassítaná a kódot, ezért a C++ azt mondja: ha túlcsordul egy előjeles egész, az UB. A fordító így feltételezheti, hogy a művelet nem csordul túl, és ennek megfelelően optimalizál.

Biztonsági szempontból a UB azért kritikus, mert a támadók kihasználhatják a nem definiált viselkedésű kódot: például egy out-of-bounds hozzáférés lehetővé teheti memóriaterületek olvasását vagy írását, ami adatszivárgáshoz vagy tetszőleges kód végrehajtásához vezethet. A modern rendszerekben a UB kiküszöbölése a hardening alapja.

26.1.2 Az UB típusai

A szabvány számos UB-forrást sorol fel. Gyakorlati szempontból a leggyakoribb és legveszélyesebb kategóriák:

26.1.2.1 Memóriakezelési hibák

  • Out-of-bounds hozzáférés: tömb vagy konténer határain túli olvasás/írás.
  • Use-after-free: egy felszabadított memória használata.
  • Double free: ugyanazon pointer kétszeri felszabadítása.
  • Null pointer dereferencia: nullptr vagy NULL pointer megszüntetése.

26.1.2.2 Objektum-élettartam megsértése

  • Objektum használata a konstruktor lefutása előtt vagy a destruktor után.
  • Élettartam nélküli tároló (std::aligned_storage) újraértelmezése megfelelő konstrukció nélkül.
  • Változó élettartamának manuális megszüntetése (p->~T()) anélkül, hogy újra konstruálnánk.

26.1.2.3 Aritmetikai UB

  • Signed integer overflow: előjeles egész túlcsordulás.
  • Nullával osztás, INT_MIN / -1.
  • Lebegőpontos érték átalakítása olyan egészre, amely nem reprezentálható.

26.1.2.4 A típus- és aliasing szabályok megsértése

  • Strict aliasing violation: egy objektumot nem kompatibilis típusú pointeren keresztül érünk el.
  • Unió aktív tagjától eltérő tag olvasása (C++-ban bizonyos esetek kivételével UB).
  • reinterpret_cast olyan típusra, amely nem megfelelő.

26.1.2.5 Alignment és reprezentáció

  • Misaligned access: olyan memória elérése, amely nem felel meg a típus igazítási követelményének.
  • Bitmezők nem szabványos elrendezésű használata (implementációfüggő, de gyakran UB határán).

26.1.2.6 Versenyhelyzetek (data race)

  • Két szál szinkronizáció nélkül írja/olvassa ugyanazt a nem atomi objektumot, és legalább az egyik írás.

26.1.2.7 Egyéb

  • const objektum módosítása const_cast-tal.
  • Végtelen rekurzió vagy üres main-ből való kilépés nélkül.
  • Nem void függvény végén a return elhagyása (kivéve main).

A következőkben a három kiemelt témát – signed overflow, lifetime, strict aliasing és misalignment – részletezzük.

26.1.3 Signed overflow

Az előjeles egész típusok (int, long, stb.) aritmetikája a szabvány szerint UB, ha az eredmény nem reprezentálható a típusban. Például:

#include <limits>
#include <iostream>

int main() {
    int x = std::numeric_limits<int>::max();
    int y = x + 1;   // UB: signed overflow
    std::cout << y << '\n';
}

A program kimenete bármi lehet: a várt „wrap-around” (-2147483648) csak egy lehetséges viselkedés, de a fordító optimalizálhatja a kifejezést, feltételezve, hogy x + 1 sosem csordul túl. Például a Clang -O2 szinten a fenti kódot akár konstanssá is hajthatja, vagy úgy dönthet, hogy az if (x + 1 < x) feltétel mindig hamis, ami téves következtetéshez vezet.

A signed overflow UB-ját a fordítók kihasználják: - Feltételezik, hogy a ciklusváltozó nem csordul túl, így a ciklus-feltétel egyszerűsíthető. - Aritmetikai azonosságokat alkalmaznak, amelyek csak UB-mentes programokra érvényesek.

Biztonsági következmény: ha a program egy felhasználó által befolyásolt értéket ad össze, és a túlcsordulás UB, akkor a támadó esetleg elérheti, hogy a program hibás döntést hozzon (pl. méretellenőrzés megkerülése). Bár a signed overflow nem közvetlen memóriahiba, a belőle fakadó logikai hibák súlyos következményekkel járhatnak.

Megoldás: használjunk unsigned aritmetikát (ahol a túlcsordulás jól definiált, modulo 2^N), vagy ellenőrizzük a műveletet biztonságos segédfüggvényekkel. C++20-tól elérhetők a std::cmp_* függvények, C++26 felé pedig a checked aritmetika. A legjobb gyakorlat: kerüljük a felhasználói bemenetből származó előjeles egészek ellenőrizetlen műveleteit.

Laborpélda (ellenőrzött UB):

// signed_overflow_ub.cpp
#include <iostream>
#include <limits>

int main() {
    int x = std::numeric_limits<int>::max();
    int y = x + 1;  // UB
    std::cout << "y = " << y << '\n';
}

Fordítás UBSan-nel:

g++ -std=c++20 -O2 -Wall -Wextra -pedantic -fsanitize=undefined -fno-sanitize-recover=all -o signed_overflow_ub signed_overflow_ub.cpp

A program futásakor az UBSan jelentést ír ki, például:

runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'

Ez a mért eredmény. A várt eredmény (dokumentált): a program UB, a szabvány nem garantál kimenetet; az UBSan hibát jelez. Fontos: a sanitizer nem a „helyes” viselkedést mutatja, hanem a hibát detektálja. Élesben a program bármit tehet.

26.1.4 Objektum-élettartam és lifetime UB

Az objektumok élettartama a konstruktor sikeres befejeződésétől a destruktor hívásáig tart. Az élettartamon kívüli hozzáférés UB. Gyakori esetek:

26.1.4.1 Use-after-free

#include <iostream>

int* create_int(int value) {
    int* p = new int(value);
    return p;
}

int main() {
    int* p = create_int(42);
    delete p;
    std::cout << *p << '\n';  // UB: use-after-free
}

A delete p után a *p olvasása UB. A gyakorlatban a memória tartalma még megmaradhat, de a fordító újra felhasználhatja a tárterületet, és a program bármikor összeomolhat vagy hibás adatot adhat.

26.1.4.2 Dangling pointer

#include <iostream>

int* get_pointer() {
    int local = 10;
    return &local;  // UB: visszatérés után a pointer érvénytelen
}

int main() {
    int* p = get_pointer();
    std::cout << *p << '\n';  // UB
}

26.1.4.3 Élettartam megsértése placement new nélkül

#include <new>
#include <iostream>

struct Widget { int x; };

int main() {
    alignas(Widget) char buffer[sizeof(Widget)];
    Widget* w = reinterpret_cast<Widget*>(buffer);  // Önmagában nem UB, de az objektum még nem létezik
    std::cout << w->x << '\n';  // UB: az objektum élettartama nem kezdődött el
}

Helyes megoldás: new (buffer) Widget{42}; majd a destruktor explicit hívása.

26.1.4.4 Az élettartam és az optimalizáló

A fordító feltételezi, hogy az objektumok élettartama szabályos. Ha egy pointert felszabadítunk, a fordító úgy kezelheti, hogy a memória tartalma érvénytelen, és a későbbi hozzáférés bármit eredményezhet. Ez lehetővé teszi a memória újrahasznosítását és agresszív optimalizálást.

Biztonsági következmény: a use-after-free a legkihasználtabb memóriahibák egyike. A támadó gondoskodhat arról, hogy a felszabadított memória területére új objektum kerüljön, és a régi pointeren keresztül azt módosítsa vagy olvassa, ami tetszőleges kód végrehajtásához vezethet.

Laborpélda (use-after-free):

// use_after_free_ub.cpp
#include <iostream>

int main() {
    int* p = new int(42);
    std::cout << *p << '\n';
    delete p;
    std::cout << *p << '\n';  // UB
    return 0;
}

Fordítás ASan-nel:

clang++ -std=c++20 -O1 -g -fsanitize=address -fno-omit-frame-pointer -o use_after_free_ub use_after_free_ub.cpp

Futáskor az AddressSanitizer hibát jelez:

ERROR: AddressSanitizer: heap-use-after-free on address ...

A várt eredmény: UB, a program viselkedése nem definiált; az ASan detektálja a hibát. A mért eredmény: az ASan leállítja a futást és jelzi a pontos helyet.

26.1.5 Strict aliasing

A C++ strict aliasing szabálya szerint egy objektumot csak bizonyos típusú kifejezéseken keresztül szabad elérni. A szabály (a C++ szabvány [basic.lval] szakasza) lényege:

  • Az objektum dinamikus típusa határozza meg a hozzáférést.
  • Egy pointer vagy referencia csak akkor használható az objektum elérésére, ha a típusa kompatibilis (pl. azonos, vagy unsigned char, char, std::byte, vagy egy szülő típus, vagy egy tag típusa).
  • A reinterpret_cast olyan típusra, amely nem felel meg ezeknek, UB-hez vezet.

Gyakori példa:

float f = 1.0f;
int* p = reinterpret_cast<int*>(&f);
int i = *p;  // UB: strict aliasing violation

A fordító feltételezheti, hogy egy int* és egy float* nem ugyanarra a memóriára mutatnak, ezért optimalizálhatja a memóriaeléréseket. Ha mégis ugyanarra mutatnak, az eredmény UB.

Egy másik gyakori eset:

struct A { int x; };
struct B { int x; };

A a{42};
B* b = reinterpret_cast<B*>(&a);
int y = b->x;  // UB: A és B nem kompatibilis típusok

Megengedett kivételek: - char, unsigned char, std::byte pointerrel bármely objektum bájtjai olvashatók. - Az unió aktív tagjának megfelelő típusú hozzáférés (C++20-ig szigorúbb, C++20 után kicsit enyhült, de még mindig korlátozott). - A memcpy és bit_cast használata típusos újraértelmezéshez.

Biztonsági következmény: a strict aliasing megsértése lehetővé teszi, hogy a fordító téves feltételezésekkel éljen az aliasokról, ami hibás kódgeneráláshoz vezet. Például a program azt hiszi, hogy egy változó értéke változatlan, mert a fordító nem látja a másik típusú pointeren keresztüli írást. Ez logikai hibákat, adatszivárgást vagy nem várt viselkedést okozhat.

Helyes megoldás: használjunk std::bit_cast-ot (C++20) vagy memcpy-t:

float f = 1.0f;
int i;
static_assert(sizeof(f) == sizeof(i));
std::memcpy(&i, &f, sizeof(i));  // jól definiált

Vagy C++20:

int i = std::bit_cast<int>(f);

Laborpélda (strict aliasing):

// strict_aliasing_ub.cpp
#include <iostream>
#include <cstring>

float get_float() {
    float f = 1.0f;
    // UB: strict aliasing violation
    int* p = reinterpret_cast<int*>(&f);
    *p = 0x3f800000;  // 1.0f bitmintája
    return f;
}

int main() {
    float result = get_float();
    std::cout << result << '\n';
}

Fordítás -O2 -Wall -Wextra -pedantic kapcsolókkal. A program kimenete várt (dokumentált): UB, így nincs garantált eredmény. A mért eredmény: a kód lefordul, fut, és valószínűleg 1-et ír ki, de ez nem bizonyíték a helyességre. UBSan (-fsanitize=undefined) nem mindig detektálja a strict aliasing megsértését, ezért erre a célra a -fstrict-aliasing és statikus elemzők használata javasolt.

26.1.6 Misalignment

Minden C++ típusnak van egy alignment követelménye: a memóriacímnek a típus méretének megfelelő hatványának többszörösének kell lennie. Például egy int általában 4 bájtos, és 4 bájtos igazítást igényel. Ha egy pointer olyan címre mutat, amely nem felel meg az alignment követelménynek, a hozzáférés misaligned, és UB.

Példa:

char buffer[sizeof(int) + 1];
int* p = reinterpret_cast<int*>(buffer + 1);  // buffer+1 nem biztos, hogy 4-gyel osztható
int x = *p;  // UB: misaligned access

A misaligned access hardveresen is problémás lehet: egyes architektúrák (pl. ARM, MIPS) hardveres kivételt váltanak ki, míg mások (x86) lassabban, de tolerálják. Azonban a szabvány szempontjából mindenképpen UB.

Biztonsági következmény: a misaligned access gyakran crash-hez vagy adatkorrupcióhoz vezet. Beágyazott rendszerekben különösen kritikus, ahol a hardver nem támogatja a nem igazított hozzáférést. Támadók kihasználhatják a helytelenül igazított pointereket arra, hogy a program nem várt memóriaterületet érjen el.

Helyes megoldás: használjunk megfelelő igazítást (alignas, std::aligned_storage), vagy másoljuk az adatot memcpy-vel egy igazított változóba. C++20-tól a std::assume_aligned jelzi a fordítónak az igazítást, de a programozó felelőssége a tényleges igazítás biztosítása.

Laborpélda (misalignment):

// misalignment_ub.cpp
#include <iostream>
#include <cstring>

int main() {
    alignas(int) char buffer[sizeof(int) * 2];
    char* raw = buffer + 1;  // szándékosan nem igazított
    int* p = reinterpret_cast<int*>(raw);
    std::cout << *p << '\n';  // UB
}

Fordítás UBSan-nel (-fsanitize=undefined) és futtatás. Az UBSan jelzi:

runtime error: load of misaligned address ... for type 'int'

A várt eredmény: UB, a program viselkedése nem definiált. A mért eredmény: az UBSan hibát jelez; más rendszeren a program lefagyhat vagy hibás adatot adhat.

26.1.7 Biztonsági következmények összefoglalása

A fent bemutatott UB-kategóriák mindegyike biztonsági kockázatot jelent:

  • A signed overflow logikai hibákhoz vezethet, amelyekkel a támadó megkerülheti a méretellenőrzéseket, vagy helytelen erőforrás-allokációt idézhet elő.
  • A lifetime UB (use-after-free, dangling pointer) közvetlen memóriahiba, amely tetszőleges kód végrehajtását teheti lehetővé.
  • A strict aliasing megsértése hibás kódgeneráláshoz vezet, amely adatszivárgást vagy nem várt viselkedést okozhat.
  • A misalignment crash-hez vagy adatkorrupcióhoz vezet, különösen beágyazott környezetben.

A biztonságos C++ fejlesztés alapelve: nulla UB tolerancia. Ennek eléréséhez: - Fordítsunk magas figyelmeztetési szinten (-Wall -Wextra -Wpedantic -Wconversion -Wsign-conversion). - Használjunk sanitizereket: ASan (memóriahibák), UBSan (UB), TSan (data race). - Alkalmazzunk statikus elemzőket: Clang Static Analyzer, Cppcheck, PVS-Studio. - A kritikus kódot fuzzoljuk. - Tartsuk be a C++ Core Guidelines ajánlásait.

26.1.8 Labor: UB-példák elemzése

A labor célja, hogy az olvasó reprodukálható környezetben, rögzített fordítóval és standardverzióval elemezze a fenti UB-példákat, elkülönítve a várt és mért eredményeket.

26.1.8.1 Környezet

  • Fordító: GCC 13.2 (vagy Clang 17)
  • Standard: C++20
  • Opciók: -O2 -Wall -Wextra -Wpedantic -fsanitize=undefined -fno-sanitize-recover=all
  • Platform: x86-64 Linux (vagy más dokumentált rendszer)

26.1.8.2 Buildparancsok

Minden példa külön fordítható:

# signed overflow
g++ -std=c++20 -O2 -Wall -Wextra -Wpedantic -fsanitize=undefined -fno-sanitize-recover=all -o signed_overflow_ub signed_overflow_ub.cpp

# use-after-free (ASan)
clang++ -std=c++20 -O1 -g -fsanitize=address -fno-omit-frame-pointer -o use_after_free_ub use_after_free_ub.cpp

# strict aliasing (csak statikus elemzés vagy -O2 megfigyelés)
g++ -std=c++20 -O2 -Wall -Wextra -Wpedantic -fstrict-aliasing -o strict_aliasing_ub strict_aliasing_ub.cpp

# misalignment (UBSan)
g++ -std=c++20 -O2 -Wall -Wextra -Wpedantic -fsanitize=undefined -fno-sanitize-recover=all -o misalignment_ub misalignment_ub.cpp

26.1.8.3 Tesztcsomag és mérési napló

A labor során minden programot futtassunk, és rögzítsük a kimenetet. A mérési napló tartalmazza:

  • A pontos fordítóverziót (g++ --version).
  • A buildparancsot.
  • A program kimenetét.
  • A várt eredményt (dokumentált, UB miatt nincs garantált kimenet).
  • A mért eredményt (a sanitizer jelzése vagy a program viselkedése).
  • A következtetést.

Példa mérési napló bejegyzésre:

Példa: signed_overflow_ub.cpp
Fordító: g++ (Ubuntu 13.2.0-23ubuntu4) 13.2.0
Build: g++ -std=c++20 -O2 -Wall -Wextra -Wpedantic -fsanitize=undefined -fno-sanitize-recover=all -o signed_overflow_ub signed_overflow_ub.cpp
Futtatás: ./signed_overflow_ub
Várt eredmény: UB, nincs definiált kimenet; az UBSan-nel a program leáll és hibát jelez.
Mért eredmény: "runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'"
Következtetés: a sanitizer detektálta a signed overflow UB-t.

26.1.8.4 Ellenőrző kérdések

  1. Miért tekinthető a signed overflow veszélyesebbnek, mint az unsigned overflow? (Válasz: az unsigned overflow jól definiált modulo 2^N, míg a signed overflow UB, így a fordító bármit feltételezhet.)
  2. Hogyan kerülhető el a strict aliasing megsértése, ha egy float bitjeit szeretnénk int-ként olvasni? (Válasz: std::bit_cast vagy memcpy.)
  3. Mi a különbség a use-after-free és a dangling pointer között? (Válasz: a use-after-free egy felszabadított memória használata, a dangling pointer egy olyan objektumra mutat, amelynek az élettartama már lejárt, de a memória nem feltétlenül felszabadított, pl. lokális változó egy függvény visszatérése után.)

26.1.9 Összefoglalás

Ebben az alfejezetben áttekintettük az undefined behavior fő típusait, és részletesen megvizsgáltuk a signed overflow, a lifetime megsértés, a strict aliasing és a misalignment problémáit. Mindegyik példa rámutatott arra, hogy a UB nem egyszerűen „rossz kód”, hanem olyan konstrukció, amelynél a fordító semmilyen garanciát nem vállal, és a program viselkedése tetszőleges lehet. A biztonsági következmények súlyosak, ezért a modern C++ fejlesztésben a UB kiküszöbölése alapvető követelmény. A következő alfejezetben a sanitizerek, a statikus elemzés és a fuzzing gyakorlati alkalmazásával foglalkozunk, amelyek segítenek ezen hibák detektálásában.
