4.2 Move szemantika, RVO és Rule of 0/3/5

A move szemantika a C++11 egyik legfontosabb nyelvi újítása, amely lehetővé teszi az erőforrások átvételét másolás helyett. Alapja az rvalue referencia (T&&) és az a felismerés, hogy a temporális objektumok erőforrásait biztonságosan el lehet lopni, mert a forrás objektumra a kifejezés kiértékelése után többé nincs szükség. A move nem új művelet, hanem túlterhelések és castok kombinációja: a megfelelő túlterhelés kiválasztását az értékkategória, a tényleges erőforrásátvételt pedig a move konstruktor vagy move assignment operátor végzi el.

Az előző alfejezetben (Értékkategóriák és referenciák) megismertük az értékkategóriákat: a prvalue, xvalue, glvalue, lvalue és rvalue fogalmát. A move szemantika szempontjából a legfontosabb az rvalue referencia, amely kizárólag rvalue-hoz kötődhet. Ha egy kifejezés rvalue, akkor a fordító a T&& paraméterű túlterhelést választja a const T& helyett. A std::move ezt a választást befolyásolja, de önmagában nem mozgat semmit: csupán egy static_cast<T&&> típusú castot hajt végre. Ennek megértése kulcsfontosságú a helyes C++ kód írásához.

4.2.1 1. A move konstruktor és a move assignment

Tegyük fel, hogy van egy Buffer osztályunk, amely dinamikusan lefoglalt karaktertömböt kezel. A klasszikus másoló konstruktor új memóriát foglal, majd elemenként átmásolja a tartalmat. A move konstruktor ezzel szemben egyszerűen átveszi a másik objektum mutatóját és méretét, a forrás objektumot pedig üres, de érvényes állapotba hozza.

#include <cstddef>
#include <algorithm>
#include <utility>

class Buffer {
    char* data_;
    std::size_t size_;
public:
    // Konstruktor
    explicit Buffer(std::size_t size)
        : data_(new char[size]), size_(size) {}

    // Copy konstruktor
    Buffer(const Buffer& other)
        : data_(new char[other.size_]), size_(other.size_) {
        std::copy(other.data_, other.data_ + size_, data_);
    }

    // Move konstruktor
    Buffer(Buffer&& other) noexcept
        : data_(std::exchange(other.data_, nullptr)),
          size_(std::exchange(other.size_, 0)) {}

    // Copy assignment
    Buffer& operator=(const Buffer& other) {
        if (this == &other) return *this;
        delete[] data_;
        data_ = new char[other.size_];
        size_ = other.size_;
        std::copy(other.data_, other.data_ + size_, data_);
        return *this;
    }

    // Move assignment
    Buffer& operator=(Buffer&& other) noexcept {
        if (this == &other) return *this;
        delete[] data_;
        data_ = std::exchange(other.data_, nullptr);
        size_ = std::exchange(other.size_, 0);
        return *this;
    }

    ~Buffer() { delete[] data_; }
};

A move konstruktor paramétere Buffer&&, amely csak rvalue-hoz kötődik. A std::exchange segítségével egyszerűen és kivételbiztosan adjuk át az erőforrást, és a forrás objektumot egyidejűleg alapállapotba tesszük. A move assignment operátor először felszabadítja a jelenlegi erőforrást, majd átveszi a másik objektum erőforrását. A noexcept specifikáció kiemelten fontos: ha a move művelet nem garantáltan kivételmentes, a standard konténerek (például std::vector) reallocation során nem használják, hanem biztonsági okokból a másoló konstruktorra esnek vissza. A részletesebb magyarázatot a hibákról szóló szakaszban találjuk.

Az implicit move konstruktor és assignment operátor akkor generálódik, ha az osztálynak nincs felhasználó által deklarált destruktora, copy konstruktora, copy assignment operátora, move konstruktora vagy move assignment operátora. Ebben az esetben a fordító minden tagot megpróbál mozgatni; ha egy tag mozgatása nem lehetséges, a generált move művelet töröltként viselkedik. A primitív típusok (int, double, mutatók) esetében a mozgatás ugyanaz, mint a másolás.

A move konstruktor és a move assignment operátor közötti különbség hasonló a copy megfelelőikéhez: a konstruktor egy új objektumot épít fel a forrás erőforrásainak átvételével, az assignment operátor pedig egy már létező objektumot állít át. Mindkét műveletnek meg kell hagynia a forrás objektumot érvényes, de meghatározatlan állapotban; a destruktorának hívhatónak kell lennie, és a forrás objektumon továbbra is hívhatók a más műveletek, feltéve, hogy azok nem támaszkodnak a korábbi állapotra.

4.2.2 2. Rule of 0, Rule of 3, Rule of 5

A C++ alapvető osztálytervezési irányelvei közé tartoznak a „Rule of 0”, „Rule of 3” és „Rule of 5” néven ismert szabályok. Ezek segítenek elkerülni a memóriakezelési hibákat és az erőforrás-szivárgást.

Rule of 0 (nulladik szabály) szerint ha egy osztály nem kezel közvetlenül erőforrást, akkor ne deklaráljunk benne destruktort, copy konstruktort, copy assignment operátort, move konstruktort vagy move assignment operátort. A tagok és azok típusai (például std::string, std::vector, std::unique_ptr) felelnek a saját erőforrásaikért, így a generált műveletek helyesen fognak viselkedni. Ez a szabály a modern C++ alapvető ajánlása: a kompozíció biztosítja a helyes működést, és kevesebb kód kevesebb hibalehetőséget jelent.

Rule of 3 (hármas szabály) azt mondja, hogy ha egy osztálynak szüksége van egyéni destruktorra, copy konstruktorra vagy copy assignment operátorra, akkor valószínűleg mindháromra szüksége van. A hátteret az erőforrás-kezelés adja: ha például dinamikus memóriát foglalunk, akkor a destruktornak fel kell szabadítania, a copy konstruktornak mély másolatot kell készítenie, a copy assignmentnek pedig a régi erőforrást fel kell szabadítania és a másik erőforrásáról mély másolatot kell készítenie. Ha bármelyik hiányzik, az dupla felszabadításhoz, szivárgáshoz vagy sekély másoláshoz vezethet.

Rule of 5 (ötös szabály) a C++11 óta kiegészíti a hármas szabályt: ha az osztály a copy műveletek vagy a destruktor miatt erőforrást kezel, akkor érdemes a move konstruktort és a move assignment operátort is megvalósítani. A move műveletek lehetővé teszik, hogy az erőforrás átadásakor elkerüljük a felesleges másolást, ami különösen konténerekben és temporálisok esetén jelentős teljesítményjavulást hozhat. Ha az osztály nem másolható (például std::unique_ptr-et tartalmaz), akkor a copy műveletek törölhetők, de a move műveleteket érdemes megtartani.

A generálási szabályok pontosak: ha az osztályban van felhasználó által deklarált destruktor, akkor a move konstruktor és move assignment nem generálódik implicit módon. A copy konstruktor és copy assignment azonban továbbra is implicit generálható, de ez a viselkedés C++11 óta deprecated, és a fordítók figyelmeztethetnek. Ha az osztályban van felhasználó által deklarált move konstruktor vagy move assignment, akkor a copy műveletek töröltként (deleted) viselkednek, kivéve, ha expliciten deklaráljuk őket. Ezért a Rule of 5 azt javasolja, hogy ilyenkor mind az öt műveletet expliciten kezeljük: vagy megvalósítjuk, vagy =default/=delete specifikációval jelezzük.

Az =default és =delete használatával szabályozhatjuk a generált függvényeket. Például:

class NonCopyable {
public:
    NonCopyable() = default;
    NonCopyable(const NonCopyable&) = delete;
    NonCopyable& operator=(const NonCopyable&) = delete;
    NonCopyable(NonCopyable&&) = default;
    NonCopyable& operator=(NonCopyable&&) = default;
};

Ez az osztály mozgatható, de nem másolható. Fontos megjegyezni, hogy ha csak a move konstruktort töröljük, a copy konstruktor továbbra is használható, mert a const T& paraméter rvalue-hoz is kötődik. Így egy T t = std::move(other); kifejezés a copy konstruktort hívná, ami lehet, hogy nem a kívánt viselkedés. A mozgathatóság letiltásához mindkét move műveletet expliciten törölni kell, vagy a copy műveleteket is törölni.

4.2.3 3. Copy elision, RVO és NRVO

A copy elision (másoláselhagyás) egy fordítóoptimalizálás, amely lehetővé teszi, hogy bizonyos helyzetekben a másoló vagy move konstruktor hívása elmaradjon. A C++17 óta egyes esetekben ez nem csak optimalizálás, hanem kötelező nyelvi szabály.

RVO (Return Value Optimization) akkor lép fel, amikor a függvény egy prvalue-t ad vissza, például return T(...);. Ilyenkor a hívó kontextusában közvetlenül felépülhet az objektum, anélkül, hogy ideiglenes és a másoló/move konstruktor meghívódna.

NRVO (Named Return Value Optimization) akkor fordul elő, ha egy lokális, névvel rendelkező objektumot adunk vissza:

Buffer make_buffer() {
    Buffer local(1024);
    // ...
    return local;
}

A NRVO során a fordító a lokális local objektumot közvetlenül a hívó kontextusában foglalhatja le, így nincs másolás vagy mozgatás. A NRVO nem kötelező, de a modern fordítók (GCC, Clang, MSVC) általában elvégzik optimizált build esetén. A szabvány megköveteli, hogy a copy vagy move konstruktor elérhető legyen, mert a kódnak fordítania kellene akkor is, ha az elision nem történik meg. Ez fontos különbség a prvalue esetéhez képest.

A C++17-ben bevezetett guaranteed copy elision azt jelenti, hogy bizonyos esetekben a másolás vagy mozgatás nem csak elhagyható, hanem kötelezően nem történik meg. Ilyen például, amikor egy prvalue-t használunk egy objektum inicializálására:

T t = T(); // nincs másolás vagy mozgatás

Ilyenkor a T() prvalue-t közvetlenül a t létrehozására használjuk, és a copy/move konstruktor nem hívódik meg, még akkor sem, ha törölt. Hasonlóan, a return T(); sem hív másoló vagy move konstruktort: a hívó oldali objektum mezői közvetlenül inicializálódnak. Ez azt is jelenti, hogy az alábbi osztály C++17-ben lefordul, bár nem másolható és nem mozgatható:

struct NonMovable {
    NonMovable() = default;
    NonMovable(const NonMovable&) = delete;
    NonMovable(NonMovable&&) = delete;
};

NonMovable make() { return NonMovable{}; } // OK C++17-től

A copy elision tehát két szinten működik: a garantált prvalue elision a nyelv része, míg a NRVO a fordítási időben alkalmazott optimalizálás. Mindkettő célja a felesleges erőforrás-mozgatások elkerülése.

Az implicit move a return utasításban azt jelenti, hogy ha egy lokális változót vagy egy érték szerinti paramétert adunk vissza, akkor a fordító automatikusan rvalue-nak tekinti, így a move konstruktort választja, ha az elérhető, és a copy elision nem valósul meg. Ezt a viselkedést a C++11 vezette be, és a legtöbb esetben kívánatos. Ha a move konstruktor nem elérhető, de a copy konstruktor igen, akkor a copy konstruktor hívódik.

A std::move explicit használata a return utasításban (return std::move(local);) általában hiba, mert megakadályozza az NRVO-t, és a move konstruktor kényszerített hívására kényszeríti a fordítót. Ez ritkán indokolt; ha a lokális objektumot tovább akarjuk adni egy másik függvénynek, akkor természetesen szükséges a std::move.

4.2.4 4. Gyakori hibák és csapdák

A move szemantika helyes használata számos buktatót rejt, amelyeket fontos felismerni.

A std::move nem mozgat, hanem castol. Ez az egyik leggyakoribb félreértés. A std::move definíciója lényegében static_cast<T&&>(x), tehát csak az értékkategóriát változtatja meg. A tényleges erőforrásátvételt a meghívott move konstruktor vagy move assignment operátor végzi. Ezért ha egy osztálynak nincs move konstruktora, a std::move után is a copy konstruktor hívódik, feltéve, hogy az elérhető.

A move konstruktor noexcept hiánya. A standard konténerek erős kivételbiztonsági garanciákat nyújtanak, amelyek megkövetelik, hogy az erőforrásokat csak akkor lehessen mozgatni, ha a move művelet nem dob kivételt. Ha a move konstruktor nem noexcept, a std::vector reallocation során a std::move_if_noexcept segítségével a copy konstruktort hívja, ami jelentős teljesítménycsökkenést eredményezhet. Például:

class Widget {
public:
    Widget(Widget&&); // nem noexcept
};

std::vector<Widget> v;
v.reserve(10);
v.push_back(Widget{});

A fenti kódban a push_back során a vektor kapacitása növekedésekor a move konstruktor helyett a copy konstruktor hívódik, mert a move konstruktor nem garantálja a kivételmentességet. Ezért a move műveleteket mindig noexcept-nek kell jelölni, ha valóban nem dobhatnak kivételt.

A moved-from objektum állapota. A move után a forrás objektum érvényes, de meghatározatlan állapotú. Ez azt jelenti, hogy a destruktor hívható, és más műveletek is végrehajthatók, amelyek nem támaszkodnak az objektum korábbi értékére. Például a Buffer osztályban a data_ nullptr lesz, a size_ pedig 0, így a destruktor biztonságosan hívható delete[]-val. Nem szabad azonban a moved-from objektumot használni anélkül, hogy új értéket adnánk neki, mert az eredmény definiálatlan viselkedéshez vezethet.

Self-move assignment. A b1 = std::move(b1); kifejezés veszélyes, mert a move assignment operátor gyakran először felszabadítja a jelenlegi erőforrást, majd átveszi a forrás erőforrását. Ha a forrás és a cél ugyanaz az objektum, akkor a saját erőforrását felszabadítanánk, majd a felszabadított mutatót használnánk. Ezért a move assignment operátornak ellenőriznie kell a this != &other feltételt, ahogy a fenti példában is látható.

A const tagok és a referencia tagok. Ha egy osztály const tagot tartalmaz, a move konstruktor nem tudja azt mozgatni, mert a const tagból nem lehet ellopni az erőforrást; a move konstruktor ilyenkor másolni fogja azt a tagot. Hasonlóan, a referencia tagok nem rendelhetők át, így a move assignment operátor nem generálható implicit módon, és saját implementációra vagy =delete-re van szükség.

A virtuális destruktor hatása. Ha egy bázisosztálynak virtuális destruktora van, az felhasználó által deklarált destruktornak számít, ami letiltja az implicit move műveleteket. Ezért a leszármazott osztályokban a move műveletek nem generálódnak automatikusan, és a Rule of 5-öt alkalmazni kell.

A std::unique_ptr és a move. A std::unique_ptr nem másolható, csak mozgatható. A mozgatása noexcept, így a std::vector<std::unique_ptr<int>> elemeinek áthelyezésekor a move konstruktor hívódik, ami hatékony. Ez jól mutatja a Rule of 0 előnyét: ha egy osztály std::unique_ptr-et tartalmaz, akkor a generált move műveletek helyesen viselkednek.

4.2.5 5. Labor: move- és copy-viselkedés mérése

A labor célja, hogy reprodukálható módon mérjük meg a másolások és mozgatások számát egy std::vector feltöltése során, és összehasonlítsuk a copy elision be- és kikapcsolásával.

Feladat: Készítsünk egy Instrumented osztályt, amely globális számlálókkal követi a copy konstruktor, move konstruktor, copy assignment és move assignment hívásait. A számlálókat static inline int tagokkal valósítjuk meg, hogy osztálydefinícióban inicializálhatók legyenek.

#include <cassert>
#include <string>
#include <utility>
#include <vector>

struct Instrumented {
    static inline int copy_ctor_count = 0;
    static inline int move_ctor_count = 0;
    static inline int copy_assign_count = 0;
    static inline int move_assign_count = 0;

    std::string data;

    explicit Instrumented(const std::string& s) : data(s) {}

    Instrumented(const Instrumented& other) : data(other.data) {
        ++copy_ctor_count;
    }

    Instrumented(Instrumented&& other) noexcept
        : data(std::move(other.data)) {
        ++move_ctor_count;
    }

    Instrumented& operator=(const Instrumented& other) {
        if (this != &other) {
            data = other.data;
            ++copy_assign_count;
        }
        return *this;
    }

    Instrumented& operator=(Instrumented&& other) noexcept {
        if (this != &other) {
            data = std::move(other.data);
            ++move_assign_count;
        }
        return *this;
    }

    ~Instrumented() = default;
};

Instrumented make_inst() {
    Instrumented local{"named"};
    return local; // NRVO-képes
}

int main() {
    // Alaphelyzet
    Instrumented::copy_ctor_count = 0;
    Instrumented::move_ctor_count = 0;
    Instrumented::copy_assign_count = 0;
    Instrumented::move_assign_count = 0;

    std::vector<Instrumented> v;
    v.reserve(10);

    // prvalue beszúrása – garantált elision miatt nincs copy/move
    v.push_back(Instrumented{"first"});

    // NRVO-képes visszatérés – a copy/move elhagyható
    v.push_back(make_inst());

    // Ellenőrzés: a move konstruktor hívódhat a vector reallocation során
    assert(Instrumented::move_ctor_count >= 0); // pontos érték a mérési naplóban

    return 0;
}

A labor feladata, hogy a fenti kódot lefordítsa a megadott környezetben, és rögzítse a számlálók értékeit. A méréshez használjunk naplófájlt, amelyben elkülönítjük a mért és a várt értékeket.

Buildelési utasítások:

  • GCC 13.2 (Linux, x86-64):
    g++ -std=c++20 -O2 -Wall -Wextra -Wpedantic -fsanitize=address,undefined -o lab_move lab_move.cpp
  • Clang 17 (Linux, x86-64):
    clang++ -std=c++20 -O2 -Wall -Wextra -Wpedantic -fsanitize=address,undefined -o lab_move lab_move.cpp
  • MSVC 2022 (Windows, x64):
    cl /std:c++20 /O2 /W4 /fsanitize=address /Fe:lab_move.exe lab_move.cpp

A copy elision kikapcsolásához GCC/Clang esetén adjuk hozzá a -fno-elide-constructors kapcsolót. MSVC-nél a copy elision a /Zc:nrvo kapcsolóval szabályozható; a garantált elision azonban C++17-ben nem kapcsolható ki.

Mérési napló minta:

Fordító / verzió Standard Kapcsolók Copy ctor Move ctor Copy assign Move assign Megjegyzés
GCC 13.2 C++20 -O2 mért: … mért: … mért: … mért: … várt: …
GCC 13.2 C++20 -O2 -fno-elide-constructors mért: … mért: … mért: … mért: … várt: …
Clang 17 C++20 -O2 mért: … mért: … mért: … mért: … várt: …
MSVC 2022 C++20 /O2 mért: … mért: … mért: … mért: … várt: …

A várt értékeket a szabvány és a fordító viselkedése alapján határozzuk meg. Például a garantált elision esetén a prvalue beszúrásakor nem várunk copy vagy move konstruktor hívást. A push_back során a vektor növekedésekor, ha a move konstruktor noexcept, akkor move konstruktor hívódhat; ha a copy elision ki van kapcsolva, akkor a make_inst() visszatérése során move konstruktor hívható. A pontos számok rögzítését a labor során kell elvégezni.

Teszteset: A fenti main függvényben az assert csak azt ellenőrzi, hogy a move konstruktor nem negatív, de a laborban ennél pontosabb ellenőrzést kell végezni. Például a következő teszt hozzáadható:

void test_guaranteed_elision() {
    Instrumented::copy_ctor_count = 0;
    Instrumented::move_ctor_count = 0;
    Instrumented inst{"test"};
    Instrumented inst2 = Instrumented{"other"};
    // A C++17 garantált elision miatt sem copy, sem move ctor nem hívódik.
    assert(Instrumented::copy_ctor_count == 0);
    assert(Instrumented::move_ctor_count == 0);
}

Ezt a függvényt a main-ben meghívva további bizonyítékot kapunk a copy elision működésére. A labor jegyzőkönyvében rögzíteni kell, hogy a teszt lefutott, és a mért értékek megegyeznek a vártakkal.
