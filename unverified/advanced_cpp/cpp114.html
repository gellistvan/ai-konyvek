30.1 RTTI és custom reflection

A futásidejű típusinformáció (RTTI) és a saját, makró- vagy sablonalapú tükrözés a C++ dinamikus és statikus világának határán helyezkedik el. Az egyik oldalon a nyelv beépített, futásidejű mechanizmusai állnak, amelyek a polimorf hierarchiákban teszik lehetővé a biztonságos típusvizsgálatot és konverziót. A másik oldalon olyan, a nyelv által közvetlenül nem biztosított képességeket építünk, mint a tagnevek, enumértéknevek vagy típuslisták elérése. E két terület ismerete elengedhetetlen akkor, amikor pluginrendszert, gyárfüggvényeket, szerializációt vagy generikus tesztelő keretrendszert készítünk, és akkor is, amikor a C++ korlátait értékeljük.

30.1.1 A futásidejű típusinformáció: typeid és type_info

A C++ RTTI-je két fő építőelemre támaszkodik: a typeid operátorra és a dynamic_cast operátorra. Mindkettő csak akkor működik a tényleges dinamikus típus szerint, ha a kifejezés polimorf típusú, tehát legalább egy virtuális függvénye van. Ennek oka, hogy a futásidejű típusinformációt a fordító a virtuális függvénytábla (vtable) mellett tárolja, és a dinamikus típus lekérdezése a vtable-n keresztül történik.

30.1.2 A typeid operátor

A typeid operátor std::type_info típusú, konstans referenciát ad vissza. A type_info osztály a <typeinfo> fejlécben található, és az alábbi fontos műveleteket támogatja:

  • operator== és operator!=: típusazonosság vizsgálata,
  • name(): implementációfüggő, nullával lezárt karaktersorozat,
  • before(const type_info&): implementációfüggő rendezés,
  • hash_code(): a típushoz tartozó, implementációfüggő hash-érték.

A type_info nem másolható és nem mozgatható; a typeid által visszaadott objektum élettartama a program végéig tart. Ezért ha tárolni szeretnénk, nem a type_info* címét kell elmenteni, hanem a megfelelő wrapper osztályt (lásd a std::type_index szakaszt).

Kritikus különbség a polimorf és a nem polimorf kifejezések között:

#include <iostream>
#include <typeinfo>

struct NonPolymorphic {};

struct Base {
    virtual ~Base() = default;
};
struct Derived : Base {};

int main() {
    NonPolymorphic np;
    NonPolymorphic& np_ref = np; // statikus típus
    std::cout << typeid(np_ref).name() << '\n'; // NonPolymorphic, mindig

    Derived d;
    Base& b_ref = d; // polimorf alosztály referencia
    std::cout << typeid(b_ref).name() << '\n'; // Derived, dinamikus
}

Ha a kifejezés nem polimorf, a typeid a statikus típust adja. Ha a kifejezés polimorf, akkor a tényleges dinamikus típust kérdezi le, kivéve, ha a kifejezés üres (például nullptr dereferencia), ami undefined behavior.

A typeid operátor típusra is alkalmazható: typeid(int) egy std::type_info objektumot ad. Ilyenkor nincs dinamikus értékelés, nincs szükség polimorfizmusra.

A type_info::name() értéke nem hordozható. A GCC és Clang tipikusan a mangled névhez közeli, de nem garantált formát ad, az MSVC más formátumot használ. Ezt csak naplózáshoz, diagnosztikához használjuk, ne tegyük programlogika alapjává. A type_info::hash_code() szintén implementációfüggő, és nem garantáltan stabil két futtatás között.

30.1.3 A dynamic_cast operátor

A dynamic_cast biztonságos típuskonverzió polimorf hierarchiában. Négy alakja van:

  1. Upcast: dynamic_cast<Base*>(derived_ptr) – mindig sikeres, a statikus típuskonverzióval egyenértékű, de a polimorfizmus miatt futásidőben is működik. Ritkán van szükség explicit dynamic_cast-re, mert az implicit konverzió elegendő.

  2. Downcast: dynamic_cast<Derived*>(base_ptr) – csak akkor ad nem-nullptr pointert, ha a base_ptr által mutatott tényleges objektum Derived típusú vagy annak leszármazottja. A pointer változat esetén sikertelenségkor nullptr-t ad. A referenciaváltozat (dynamic_cast<Derived&>(base_ref)) sikertelenségkor std::bad_cast kivételt dob, amely a <typeinfo> fejlécben található.

  3. Crosscast: ha egy osztály több öröklési ágból származik, akkor a dynamic_cast segítségével testvérosztályok között is konvertálhatunk. Ehhez a tényleges objektumnak mindkét típusból származnia kell.

  4. Void-ra cast: dynamic_cast<void*>(ptr) a leginkább leszármaztatott objektum kezdőcímére mutató pointert ad vissza.

Példa downcast használatára:

void handle_shape(Base* p) {
    if (auto* c = dynamic_cast<Circle*>(p); c != nullptr) {
        c->draw_circle_specific();
    } else if (auto* r = dynamic_cast<Rectangle*>(p); r != nullptr) {
        r->draw_rectangle_specific();
    }
}

A dynamic_cast működéséhez a bázisosztálynak polimorfnak kell lennie, tehát legalább egy virtuális függvénye van. Ha a bázis nem polimorf, a fordítási hiba: a dynamic_cast csak polimorf hierarchiában érvényes.

30.1.4 A std::type_index osztály

Mivel a std::type_info nem másolható és nem rendezhető szabványos módon, a szabvány bevezeti a std::type_index osztályt a <typeindex> fejlécben. Ez egy wrapper, amely:

  • tartalmaz egy const std::type_info* mutatót,
  • definiálja az operator== és operator!= összehasonlítást,
  • definiálja az operator< rendezést,
  • a std::hash specializációját.

Így a std::type_index használható std::map és std::unordered_map kulcsaként. Mindig ezt használjuk, ha típuskulcsot tárolunk.

Példa factory-regisztrációra:

#include <functional>
#include <map>
#include <memory>
#include <typeindex>
#include <typeinfo>
#include <type_traits>

struct Shape {
    virtual ~Shape() = default;
    virtual void draw() const = 0;
};

struct Circle : Shape {
    void draw() const override { /* ... */ }
};

struct Rectangle : Shape {
    void draw() const override { /* ... */ }
};

std::map<std::type_index, std::function<std::unique_ptr<Shape>()>> shape_factory;

template<typename T>
void register_shape() {
    static_assert(std::is_base_of_v<Shape, T>, "T must derive from Shape");
    shape_factory[std::type_index(typeid(T))] = [] {
        return std::make_unique<T>();
    };
}

template<typename T>
std::unique_ptr<Shape> create_shape() {
    auto it = shape_factory.find(std::type_index(typeid(T)));
    return it != shape_factory.end() ? it->second() : nullptr;
}

Itt a std::type_index garantálja a kulcsok összehasonlíthatóságát és hash-elhetőségét. A std::type_index típusú kulcsok mögött a type_info objektumok referencia-stabilitása áll, ezért biztonságos.

30.1.5 Saját tükrözés makrókkal és sablonokkal

A C++ nyelv hagyományosan nem biztosít általános célú, futásidejű reflectiont a tagnevek, típusok vagy enumértékek elérésére. A C++26 reflection ezen változtatni fog, de a mai gyakorlatban a szükséges képességeket makrókkal és sablonmeta-programozással építjük. Ennek két fő iránya van:

  • Makróalapú reflection: az előfeldolgozó segítségével generálunk kódot, amely stringeket és típuslistákat állít elő.
  • Sablonalapú reflection: típustulajdonságokat, típuslistákat és meta-algoritmusokat használunk, amelyek fordítási időben biztosítanak információt, de tagneveket nem tudnak közvetlenül stringgé alakítani.

Mindkettő korlátozott, de célzott feladatokra (enum stringgé alakítása, tagok tuple-lé alakítása, típusnyilvántartás) jól használható.

30.1.6 Makróalapú enum-tükrözés és az X-makró technika

A leggyakoribb makrós reflection-feladat az, hogy egy enum értékeit összekapcsoljuk a nevükkel. A naiv megoldás gyakran hibás:

#define ENUM_WITH_STRING(EnumName, ...)                                  \
    enum class EnumName { __VA_ARGS__ };                                 \
    inline constexpr std::string_view to_string(EnumName e) {            \
        static constexpr std::string_view names[] = { #__VA_ARGS__ };    \
        auto index = static_cast<std::size_t>(e);                        \
        return (index < std::size(names)) ? names[index] : "unknown";    \
    }

Ez a kód nem működik, mert a #__VA_ARGS__ a teljes argumentumlistát egyetlen stringgé alakítja, a vesszőkkel együtt, így a names tömb egyetlen stringet tartalmaz. A helyes megoldás az X-makró technika:

#define SHAPE_KIND_LIST(X) \
    X(Circle)              \
    X(Rectangle)           \
    X(Triangle)

enum class ShapeKind {
#define X(name) name,
    SHAPE_KIND_LIST(X)
#undef X
};

inline constexpr std::string_view to_string(ShapeKind kind) {
    switch (kind) {
#define X(name) case ShapeKind::name: return #name;
        SHAPE_KIND_LIST(X)
#undef X
    }
    return "unknown";
}

inline constexpr ShapeKind from_string(std::string_view s) {
#define X(name) if (s == #name) return ShapeKind::name;
    SHAPE_KIND_LIST(X)
#undef X
    throw std::invalid_argument("invalid shape kind");
}

Itt a makró egyetlen helyen (a SHAPE_KIND_LIST listában) definiálja az összes elemet, és minden felhasználási hely egy X makrót definiál, amely az aktuális elemet megfelelő kóddá alakítja. Ez a technika elkerüli a vesszőproblémát, mert az elemek nem egyetlen variadikus argumentumként érkeznek, hanem az X(name) hívások során. Az enum értékek névpárokként jelennek meg, és a to_string/from_string függvények szinkronban maradnak. Az X-makró hátránya, hogy a from_string lineáris keresést végez, ami kis enumoknál elfogadható, nagyobbaknál optimalizálható (pl. rendezett táblával).

A fenti from_string hibát dob ismeretlen string esetén. Ha kivétel nélküli környezetben dolgozunk, használhatunk std::optional-t vagy std::expected-et, de a példában a kivétel egyszerű és világos.

30.1.7 Makróalapú tag-tükrözés

Az osztályok tagjainak tükrözése makrókkal úgy lehetséges, hogy minden taghoz egy stringet és egy hozzáférést generálunk. Az egyszerű, de korlátozott megoldás:

#define REFLECT_MEMBERS(Type, ...)                                     \
    static constexpr auto reflected_members() {                         \
        return std::tuple{__VA_ARGS__};                                \
    }

Ez azonban nem ad tagneveket. A tagnevek eléréséhez párosítanunk kell a tagot és a nevét. Egy lehetséges megközelítés:

struct Point {
    double x;
    double y;
};

constexpr auto reflect(Point& p) {
    return std::tuple{std::pair{"x", &Point::x}, std::pair{"y", &Point::y}};
}

Ez már C++17-ben is működik, de minden osztályhoz kézzel kell megírni a reflect függvényt. Makróval ezt generálhatjuk:

#define REFLECTABLE(Type, ...)                                          \
    constexpr auto reflect(Type& obj) {                                 \
        return std::tuple{__VA_ARGS__};                                  \
    }

A hívás azonban így néz ki:

REFLECTABLE(Point, std::pair{"x", &Point::x}, std::pair{"y", &Point::y})

Ez már működik, de a std::pair helyett jobb egy dedikált struktúrát használni, hogy a tükrözött tagok neve és pointere típusbiztosan tárolható legyen. A makrós generálás tipikus hátránya, hogy a hibák üzenete nehezen olvasható, és a makrók nem értik a típusrendszert.

30.1.8 Sablonalapú reflection: típuslisták és típusmanipuláció

A sablonokkal nem lehet tagneveket stringgé alakítani, de típusokat, típuslistákat és típusok közötti kapcsolatokat tudunk kifejezni. A legfontosabb eszköz a type list:

template<typename... Ts>
struct type_list {};

using ShapeTypes = type_list<Circle, Rectangle, Triangle>;

Egy ilyen listán meta-algoritmusokat futtathatunk, például fordítási idejű iterációt:

template<typename List>
struct list_size;

template<typename... Ts>
struct list_size<type_list<Ts...>> : std::integral_constant<std::size_t, sizeof...(Ts)> {};

template<typename List, typename F>
void for_each_type(F&& f) {
    [&]<typename... Ts>(type_list<Ts...>) {
        (f.template operator()<Ts>(), ...);
    }(List{});
}

Ezután a for_each_type<ShapeTypes>([](auto tag){ ... }) hívás minden típusra lefut. A sablonos megközelítés erőssége, hogy típusbiztos, és a fordító ellenőrzi a típusok érvényességét. Gyengesége viszont, hogy nem ad futásidejű stringeket a típusnevekről, hacsak nem használunk compiler-specifikus trükköket (például __PRETTY_FUNCTION__ elemzését), amelyek nem hordozhatók.

A sablonalapú reflection gyakran azért elegendő, mert a generikus kódban nem a tagnevekre, hanem a típusokra és azok tulajdonságaira van szükség. Például egy gyárfüggvénynél a type_list alapján regisztrálhatunk minden típust:

template<typename... Ts>
void register_all(type_list<Ts...>) {
    (register_shape<Ts>(), ...);
}

A register_all<ShapeTypes>({}) hívás mindhárom típust regisztrálja a factory-ba. A sablonok tehát az ismétlődő kódot generálják, de nem tükröznek neveket.

30.1.9 Labor: RTTI- és reflection-példa

A fejezet laborja egy kis, de teljes rendszert épít, amely bemutatja az RTTI és a custom reflection együttes használatát.

30.1.10 Feladat

Készíts egy programot, amely:

  1. Definiál egy Shape absztrakt ősosztályt virtuális destruktorral és draw() tagfüggvénnyel.
  2. Definiál Circle, Rectangle, Triangle leszármazottakat.
  3. Definiál egy ShapeKind enumot, amelyet X-makróval tükröz (to_string, from_string).
  4. Létrehoz egy factory-t, amely std::type_index kulccsal regisztrálja a típusokat, és a ShapeKind alapján is tud példányosítani.
  5. A program assert-ekkel ellenőrzi a működést, beleértve a dynamic_cast downcastet, a type_index kulcsokat, a tükrözés round-tripet.

A kód legyen C++20 szabványú, és fordítható GCC, Clang és MSVC alatt.

30.1.11 A labor kódja

#include <cassert>
#include <functional>
#include <iostream>
#include <map>
#include <memory>
#include <stdexcept>
#include <string_view>
#include <typeindex>
#include <typeinfo>
#include <type_traits>

// X-makró lista az enum elemekhez
#define SHAPE_KIND_LIST(X) \
    X(Circle)              \
    X(Rectangle)           \
    X(Triangle)

enum class ShapeKind {
#define X(name) name,
    SHAPE_KIND_LIST(X)
#undef X
};

inline constexpr std::string_view to_string(ShapeKind kind) {
    switch (kind) {
#define X(name) case ShapeKind::name: return #name;
        SHAPE_KIND_LIST(X)
#undef X
    }
    return "unknown";
}

inline constexpr ShapeKind from_string(std::string_view s) {
#define X(name) if (s == #name) return ShapeKind::name;
    SHAPE_KIND_LIST(X)
#undef X
    throw std::invalid_argument("invalid shape kind");
}

// Polimorf Shape hierarchia
struct Shape {
    virtual ~Shape() = default;
    virtual void draw() const = 0;
};

struct Circle : Shape {
    void draw() const override { std::cout << "Circle\n"; }
};

struct Rectangle : Shape {
    void draw() const override { std::cout << "Rectangle\n"; }
};

struct Triangle : Shape {
    void draw() const override { std::cout << "Triangle\n"; }
};

// Factory type_index alapján
std::map<std::type_index, std::function<std::unique_ptr<Shape>()>> shape_factory;

template<typename T>
void register_shape() {
    static_assert(std::is_base_of_v<Shape, T>, "T must derive from Shape");
    shape_factory[std::type_index(typeid(T))] = [] {
        return std::make_unique<T>();
    };
}

template<typename T>
std::unique_ptr<Shape> create_shape() {
    auto it = shape_factory.find(std::type_index(typeid(T)));
    return it != shape_factory.end() ? it->second() : nullptr;
}

// Factory ShapeKind alapján (a tükrözést használja)
std::unique_ptr<Shape> create_shape(ShapeKind kind) {
    switch (kind) {
#define X(name) case ShapeKind::name: return create_shape<name>();
        SHAPE_KIND_LIST(X)
#undef X
    }
    return nullptr;
}

int main() {
    // Regisztráció
    register_shape<Circle>();
    register_shape<Rectangle>();
    register_shape<Triangle>();

    // 1. type_index factory ellenőrzés
    auto c = create_shape<Circle>();
    assert(c != nullptr);
    assert(dynamic_cast<Circle*>(c.get()) != nullptr);
    assert(dynamic_cast<Rectangle*>(c.get()) == nullptr);

    auto t = create_shape<Triangle>();
    assert(t != nullptr);
    assert(dynamic_cast<Triangle*>(t.get()) != nullptr);

    // 2. ShapeKind tükrözés round-trip
    assert(to_string(ShapeKind::Circle) == "Circle");
    assert(to_string(ShapeKind::Rectangle) == "Rectangle");
    assert(to_string(ShapeKind::Triangle) == "Triangle");
    assert(from_string("Rectangle") == ShapeKind::Rectangle);
    assert(from_string("Triangle") == ShapeKind::Triangle);

    // 3. ShapeKind alapú factory
    auto sk = create_shape(ShapeKind::Rectangle);
    assert(sk != nullptr);
    assert(dynamic_cast<Rectangle*>(sk.get()) != nullptr);

    std::cout << "All tests passed.\n";
}

A kód önállóan fordítható és futtatható. A from_string hibát dob ismeretlen string esetén; a tesztben ezt nem váltjuk ki, de a kód tartalmazza a kivételt.

30.1.14 A labor értékelése

A labor akkor tekinthető sikeresnek, ha:

  • a program minden asserten hibamentesen átmegy,
  • a create_shape(ShapeKind) és a create_shape<T>() egyaránt helyes,
  • a from_string és a to_string konzisztens,
  • a dynamic_cast ellenőrzések helyesen különbséget tesznek a típusok között.

30.1.15 Tipikus hibák és helyes megoldások

A RTTI és a custom reflection használata során több gyakori hiba fordul elő. Ezek ismerete segít elkerülni a nem hordozható vagy hibás kódot.

30.1.16 Statikus típusú typeid nem polimorf hierarchiában

Ha egy pointer nem polimorf típusra mutat, a typeid(*ptr) a statikus típust adja, nem a ténylegeset. Például:

struct BaseNonPoly {};
struct DerivedNonPoly : BaseNonPoly {};

void check(BaseNonPoly* p) {
    // HIBA: typeid a statikus típust látja
    if (typeid(*p) == typeid(DerivedNonPoly)) { /* soha nem teljesül */ }
}

A megoldás: ha dinamikus típusvizsgálatra van szükség, a bázisosztálynak polimorfnak kell lennie (legalább egy virtuális függvény). Gyakran elegendő virtuális destruktort adni.

30.1.17 type_info::name() összehasonlítása

A name() által visszaadott stringet ne hasonlítsuk össze közvetlenül, mert az nem hordozható. Még ugyanazon a platformon is változhat a formátum. A helyes megoldás a typeid által visszaadott type_info objektumok operator== használata, vagy ha kulcsként kell, akkor std::type_index.

// ROSSZ:
if (std::string(typeid(T).name()) == "Circle") { ... }

// JÓ:
if (typeid(T) == typeid(Circle)) { ... }
// vagy:
if (std::type_index(typeid(T)) == std::type_index(typeid(Circle))) { ... }

30.1.18 dynamic_cast nullptr ellenőrzés elmulasztása

Pointer downcast után mindig ellenőrizni kell a nullptr-t, mielőtt a pointert használnánk. A referencia változatnál pedig std::bad_cast kivételre kell számítani.

// ROSSZ:
auto* p = dynamic_cast<Circle*>(base_ptr);
p->circle_specific(); // nullptr dereference lehet

// JÓ:
auto* p = dynamic_cast<Circle*>(base_ptr);
if (p) { p->circle_specific(); }

30.1.19 typeid nullptr dereferencia

A typeid(*ptr) kifejezés undefined behavior, ha ptr nullptr. Polimorf típus esetén a typeid a vtable-n keresztül deríti ki a dinamikus típust, ami nullptr esetén ugrás a semmibe.

// ROSSZ:
Base* p = nullptr;
auto& ti = typeid(*p); // UB

// JÓ:
if (p) { typeid(*p); }

30.1.20 RTTI kikapcsolása -fno-rtti esetén

A -fno-rtti (GCC/Clang) vagy /GR- (MSVC) kapcsolóval a dynamic_cast és a typeid polimorf hierarchiában nem működik: a kód nem fordul, vagy undefined behavior lép fel. Ezért ha ilyen kapcsolót használunk (például beágyazott rendszerekben), a kódot ennek megfelelően kell megtervezni. A laborunkban ezt a kapcsolót nem használjuk, ezért a kód feltételezi az RTTI elérhetőségét.

30.1.21 X-makró vesszőhiba

A naiv #__VA_ARGS__ stringizálás a vesszőket is beleteszi, ami hibás stringtömböt eredményez. Az X-makró technika ezt elkerüli, de figyelni kell arra, hogy az X(name) hívásban a name ne tartalmazzon vesszőt vagy más speciális karaktert. Ha egy enum elem neve ütközne valamivel, akkor át kell nevezni.

30.1.22 Makrók túlzott használata

A makrók nehezen debuggolhatók, nem típustudatosak, és a hibákat gyakran csak a fordítási hiba után lehet nehezen visszafejteni. Ezért csak olyan esetekben használjuk őket, ahol a sablonok nem elegendők (például stringek generálására). A generikus kódban részesítsük előnyben a sablonokat és a type traiteket.

30.1.23 Összefoglalás és önellenőrző kérdések

Ebben az alfejezetben áttekintettük a C++ futásidejű típusinformációját: a typeid operátort, a std::type_info osztályt, a dynamic_cast operátort és a std::type_index wrappert. Láttuk, hogyan használhatók ezek biztonságos downcastre, típuskulcsok készítésére és factory-regisztrációra. Ezután bemutattuk a saját tükrözés két fő irányát: a makróalapú X-makró technikát, amely enumértékeket és tagokat kapcsol össze stringekkel, valamint a sablonalapú típuslistákat és meta-algoritmusokat. A laborban egy teljes, fordítható példát építettünk, amely a két technikát kombinálja.

Önellenőrző kérdések:

  1. Mi a különbség a typeid viselkedésében polimorf és nem polimorf típusok esetén?
  2. Miért jobb a std::type_index mint a type_info* kulcsként?
  3. Milyen esetekben dob std::bad_cast-ot a dynamic_cast referenciára?
  4. Hogyan működik az X-makró technika, és milyen előnyei vannak a #__VA_ARGS__ stringizálással szemben?
  5. Mi a saját, makró- vagy sablonalapú reflection fő korlátja a nyelvi reflectionhöz képest?

Gyakorlati feladat:

Bővítsd a laborprogramot egy ShapeKind-hez tartozó std::map<ShapeKind, std::type_index> táblával, amely az enum érték és a típus type_index-e közötti megfeleltetést rögzíti. Írj egy függvényt, amely ShapeKind-ből std::type_index-et ad, és ellenőrizd, hogy a type_index megegyezik a typeid(Circle) eredményével. Ez a bővítés jól mutatja a tükrözés és az RTTI összekapcsolását.

A következő egység (30.2) erre az alapra építve bemutatja a C++26 reflection lehetőségeit és a library-megoldásokat, amelyek a makrók és a sablonok korlátait hivatottak meghaladni.
