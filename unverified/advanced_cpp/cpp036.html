10.3 Mixin-ek és policy-based design

A policy-based design a C++ sablonmeta-programozás egyik legfontosabb építőköve: olyan osztálysablonok tervezését jelenti, amelyek viselkedését kis, független „politika” osztályokkal paraméterezzük. A technika szorosan kapcsolódik a keverékosztályok (mixin) fogalmához, és a gyakorlatban a statikus polimorfizmus egyik leghatékonyabb formája. Ebben az alfejezetben a politikák és a kompozíció sablonokkal történő megvalósítását, a policy class és host class szerepét, valamint a testreszabhatóság és a kódduplikáció közötti egyensúlyt vizsgáljuk. A cél, hogy az olvasó képes legyen saját, policy-alapú osztályt tervezni, felismerni a tipikus hibákat, és megindokolni, mikor érdemes ezt a megoldást választani a virtuális függvényekkel szemben.

10.3.1 A politika fogalma: policy class

A policy-based design alapgondolata, hogy egy osztály viselkedésének bizonyos aspektusait – például a memóriafelszabadítás módját, a zárolási mechanizmust, a naplózási csatornát vagy a növekedési stratégiát – külön osztályokba szervezzük ki. Ezeket az osztályokat policy class-oknak nevezzük. Egy policy class jellemzően nem tartalmaz adattagot, vagy csak minimális állapotot; a lényege az interfész, amelyet a host class elvár. A policy class nem virtuális függvényekkel dolgozik, hanem statikus, fordítási időben ismert interfésszel. Ez lehetővé teszi a fordító számára az inline-olást és az agresszív optimalizálást.

A policy class gyakran egyszerű struktúra vagy osztály, például:

struct NoLock {
    void lock() {}
    void unlock() {}
};

struct MutexLock {
    std::mutex m;
    void lock() { m.lock(); }
    void unlock() { m.unlock(); }
};

Mindkét osztály ugyanazt a két tagfüggvényt (lock, unlock) biztosítja, de eltérő módon. Ez a közös felület az, amit a host class a sablonparaméterként kapott politikától elvár.

10.3.2 A host class

A host class az az osztálysablon, amely a politikákat felhasználja. A politikákat általában sablonparaméterként adjuk át, és a host class vagy örökli őket, vagy tartalmazza őket. Az örökléses megközelítés gyakori, mert így a politika tagfüggvényei közvetlenül elérhetők a host class-on belül, és a fordító üres alaposztály-optimalizálást (EBO, empty base optimization) alkalmazhat, ha a politika nem tartalmaz adattagot.

Példa egy egyszerű host class-ra, amely egy erőforrás zárolását és felszabadítását politizálja:

template<typename T,
         typename LockPolicy = NoLock,
         typename ReleasePolicy = DeleteRelease<T>>
class Resource : private LockPolicy, private ReleasePolicy {
    T* ptr = nullptr;
public:
    explicit Resource(T* p) : ptr(p) {}

    ~Resource() {
        this->lock();
        this->release(ptr);
        this->unlock();
    }

    Resource(const Resource&) = delete;
    Resource& operator=(const Resource&) = delete;

    Resource(Resource&& other) noexcept
        : ptr(other.ptr) {
        other.ptr = nullptr;
    }

    Resource& operator=(Resource&& other) noexcept {
        if (this != &other) {
            this->lock();
            this->release(ptr);
            ptr = other.ptr;
            other.ptr = nullptr;
            this->unlock();
        }
        return *this;
    }

    T* get() const { return ptr; }

    void reset(T* p = nullptr) {
        this->lock();
        T* old = ptr;
        ptr = p;
        this->release(old);
        this->unlock();
    }
};

Ebben a példában a LockPolicy és a ReleasePolicy a két politika. A host class privát módon örökli őket, mert a politika nem része a publikus interfésznek; az öröklés pusztán implementációs eszköz. A this->lock() hívás azért szükséges, mert a lock név a függő alaposztályból származik, és a kétszakaszos névfeloldás miatt explicit minősítést igényel (vagy using deklarációt).

A ReleasePolicy itt sablonparaméterként egy osztálysablont vár, amelyet a T típussal példányosítunk. Ez tipikus megoldás, amikor a politika a kezelt típus ismeretét igényli.

10.3.3 Politikák és kompozíció sablonokkal

A policy-based designban a politika és a host class viszonya nem klasszikus „is-a” kapcsolat, hanem inkább „implementáció része” viszony. A privát öröklés ezt jól kifejezi: a host class nem válik a politika altípusává, csupán újrahasznosítja annak kódját.

A mixin kifejezés olyan osztálysablonra utal, amelyet kifejezetten arra terveztek, hogy más osztályok alaposztályaként szolgáljon, és további funkcionalitást adjon hozzá. A policy class gyakran mixin-ként viselkedik: a host class „összekeveri” magában a kiválasztott politikákat. A mixin-ek többnyire nem a fő absztrakciót alkotják, hanem keresztmetszeti viselkedést adnak hozzá, mint például a naplózás, a szinkronizáció vagy az objektumszámlálás.

A kompozíció sablonokkal tehát azt jelenti, hogy a host class nem egyetlen nagy, minden funkciót magában foglaló osztály, hanem kisebb, cserélhető építőelemekből áll össze. Ez a tervezési elv nagyban csökkenti a kódduplikációt, mert ugyanaz a host class sokféle konfigurációban újrahasznosítható.

10.3.4 Több politika kombinálása

Egy host class egynél több politikát is fogadhat. A sorrendnek általában nincs hatása, de ha a politikák közötti függőség van, akkor a sorrendet dokumentálni kell. Például:

template<typename T,
         typename LockPolicy = NoLock,
         typename AllocPolicy = std::allocator<T>>
class SafeContainer : private LockPolicy, private AllocPolicy {
    // ...
};

Itt a LockPolicy a szálbiztonságért, az AllocPolicy a memóriafoglalásért felel. A host class mindkettőt örökli, és a műveletek során megfelelően hívja őket. A politika interfészét a host class feltételezi: a LockPolicy-nak lock()/unlock(), az AllocPolicy-nak allocate()/deallocate() tagfüggvényekkel kell rendelkeznie. Ezt az elvárást C++20-ban concept-ekkel is kifejezhetjük, ami javítja a hibaüzeneteket.

10.3.5 Testreszabhatóság és kódduplikáció

A policy-based design elsődleges előnye, hogy a testreszabhatóságot úgy biztosítja, hogy közben minimálisra csökkenti a kódduplikációt. Gondoljunk egy olyan konténerre, amelynek több viselkedési dimenziója van: növekedési stratégia, szálbiztonság, memóriaforrás. Ha minden kombinációhoz külön osztályt írnánk, a kód robbanásszerűen nőne. Ehelyett a host class-t egyszer megírjuk, és a politikák cseréjével állítjuk elő a kívánt változatokat.

Példa egy Vector osztálysablonra, amely a növekedési politikát és az allokátort paraméterként kapja:

struct ExponentialGrowth {
    size_t next_capacity(size_t current, size_t required) const {
        size_t cap = current ? current : 1;
        while (cap < required) cap *= 2;
        return cap;
    }
};

struct FixedGrowth {
    size_t increment = 16;
    size_t next_capacity(size_t current, size_t required) const {
        return std::max(required, current + increment);
    }
};

template<typename T,
         typename GrowthPolicy = ExponentialGrowth,
         typename Alloc = std::allocator<T>>
class Vector : private GrowthPolicy, private Alloc {
    T* data_ = nullptr;
    size_t size_ = 0;
    size_t capacity_ = 0;
public:
    // ...
    void push_back(const T& value) {
        if (size_ == capacity_) {
            size_t new_cap = this->next_capacity(capacity_, size_ + 1);
            reserve(new_cap);
        }
        // ...
    }
};

Ebben a példában a Vector osztály kódja egyszer íródik meg, de a GrowthPolicy cseréjével exponenciális vagy lineáris növekedést kapunk. A FixedGrowth politikának ráadásul van egy adattagja (increment), amelyet a host class örököl, és így az objektum méretéhez hozzájárul. Az üres ExponentialGrowth esetén az EBO miatt nem nő a méret.

A politika-alapú megközelítés a virtuális függvényekkel szemben a következő előnyöket kínálja:

  • Nincs futásidejű indirekció: a politika tagfüggvényeit a fordító általában be tudja inline-olni, mert a konkrét típus fordítási időben ismert.
  • Nincs vtable költség: az objektum nem tartalmaz vtable-mutatót, és a hívás nem igényel dinamikus diszpécselést.
  • Jobb optimalizálhatóság: a statikus kötés lehetővé teszi a konstans propagációt, a hurokfelgöngyölítést és más optimalizációkat.
  • Rugalmasabb interfész: a politika nem kényszerül közös absztrakt alaposztályba, így szabadon definiálhat extra tagfüggvényeket, amelyeket a host class kihasználhat.

Ugyanakkor vannak hátrányai is:

  • Fordítási idő: minden politika-kombináció külön példányosítást eredményez, ami növeli a fordítási időt és a bináris méretet.
  • Hibaüzenetek: ha a politika nem teljesíti az elvárt interfészt, a hibák a sablonpéldányosítás mélyén jelentkeznek, és hosszú, nehezen értelmezhető üzeneteket adnak. C++20 concept-ekkel ez mérsékelhető.
  • Kódméret: a sok példányosítás duplikált gépi kódhoz vezethet, bár ez gyakran elfogadható a futásidejű előnyökért cserébe.

10.3.6 Standard library példák

A C++ szabványkönyvtár több helyen is alkalmazza a policy-based design elvét. A legismertebb példák:

  • std::unique_ptr<T, Deleter>: a felszabadítás politikája a Deleter sablonparaméter. Alapértelmezésben std::default_delete<T>, de tetszőleges hívható objektum vagy függvénymutató is megadható.
  • std::char_traits<CharT>: a karaktertípusok műveleteit (összehasonlítás, másolás, EOF stb.) paraméterezi.
  • std::allocator<T>: a memóriafoglalás politikája, amely a konténerekben cserélhető.
  • std::pmr::polymorphic_allocator<T>: futásidejű memóriaforrást használó allokátor, amely a policy-alapú és a virtuális megközelítés közötti hibrid.

Ezek a példák azt mutatják, hogy a nyelv maga is támaszkodik erre a technikára, és a felhasználói kódban is érdemes követni.

10.3.7 Tipikus hibák és megoldások

10.3.7.1 A politika interfészének be nem tartása

A leggyakoribb hiba, hogy a felhasználó olyan politikát ad meg, amely nem biztosítja a host class által elvárt tagfüggvényeket vagy típusokat. Például a fenti LockPolicy esetén a lock()/unlock() hiánya fordítási hibát okoz, de a hibaüzenet a host class belsejére mutat, ami zavaró lehet. C++20-ban concept-ekkel ezt érdemes megelőzni:

template<typename P>
concept LockPolicyConcept = requires(P p) {
    { p.lock() } -> std::same_as<void>;
    { p.unlock() } -> std::same_as<void>;
};

template<LockPolicyConcept LockPolicy = NoLock>
class Resource { /* ... */ };

Ekkor a hiba a sablonparaméter megadásánál, érthetőbb formában jelenik meg.

10.3.7.2 A politikák közötti nem dokumentált függőség

Ha a politikák állapota vagy interfésze egymástól függ, akkor a sorrend és a konstrukció módja fontos. Például ha egy LockPolicy és egy AllocPolicy közösen használ egy erőforrást, akkor a host class-nak garantálnia kell a megfelelő sorrendű inicializálást és destruálást. A privát öröklés esetén az alaposztályok konstruktorai a megadott sorrendben futnak le, ami általában a sablonparaméterek sorrendjét követi. Ezt dokumentálni kell.

10.3.7.3 A túlzott sablonparaméterezés

Bár a policy-based design rugalmas, a túl sok politika bevezetése rontja az olvashatóságot és a karbantarthatóságot. Ha egy osztály öt vagy több politikát igényel, érdemes megfontolni, hogy egyes politikákat összevonjunk, vagy átgondoljuk a tervezést. A politika-szám növekedése exponenciálisan növeli a lehetséges kombinációk számát, ami a tesztelési terhet is növeli.

10.3.7.4 A virtuális függvények indokolatlan elkerülése

A policy-based design nem minden esetben jobb, mint a virtuális függvények. Ha a politikát futásidőben kell cserélni, vagy ha a politika típusa csak dinamikusan ismert (például plugin-eknél), akkor a virtuális függvények vagy a type erasure a megfelelő eszköz. A policy-based design elsősorban akkor előnyös, ha a konkrét típus fordítási időben ismert, és a teljesítmény kritikus.

10.3.8 Labor: policy-based osztály tervezése

Ebben a laborban egy olyan erőforrás-kezelő osztályt tervezünk, amely a zárolási és a felszabadítási politikát sablonparaméterként kapja. A feladat célja, hogy a résztvevő:

  1. Elkészítse a Resource host class-t és a NoLock, MutexLock, DeleteRelease, CustomRelease policy osztályokat.
  2. Megvalósítson egy virtuális függvényes változatot ugyanarra a funkcióra.
  3. Méréssel igazolja a policy-based megoldás előnyét a virtuális változattal szemben.
  4. A mérési naplóban elkülönítse a várt és a mért eredményeket.

10.3.9 A kód

#include <iostream>
#include <memory>
#include <mutex>
#include <chrono>
#include <vector>
#include <cassert>

// -------- Lock policies --------
struct NoLock {
    void lock() {}
    void unlock() {}
};

struct MutexLock {
    std::mutex m;
    void lock() { m.lock(); }
    void unlock() { m.unlock(); }
};

// -------- Release policies --------
struct DeleteRelease {
    template<typename T>
    void release(T* p) { delete p; }
};

struct CustomRelease {
    template<typename T>
    void release(T* p) {
        // Példa: egyedi naplózás vagy erőforrás-visszaadás
        // Itt egyszerűen töröljük, de a valóságban lehet más.
        delete p;
    }
};

// -------- Host class (policy-based) --------
template<typename T,
         typename LockPolicy = NoLock,
         typename ReleasePolicy = DeleteRelease>
class Resource : private LockPolicy, private ReleasePolicy {
    T* ptr = nullptr;
public:
    explicit Resource(T* p) : ptr(p) {}

    ~Resource() {
        this->lock();
        this->release(ptr);
        this->unlock();
    }

    Resource(const Resource&) = delete;
    Resource& operator=(const Resource&) = delete;

    Resource(Resource&& other) noexcept
        : ptr(other.ptr) {
        other.ptr = nullptr;
    }

    Resource& operator=(Resource&& other) noexcept {
        if (this != &other) {
            this->lock();
            this->release(ptr);
            ptr = other.ptr;
            other.ptr = nullptr;
            this->unlock();
        }
        return *this;
    }

    T* get() const { return ptr; }

    void reset(T* p = nullptr) {
        this->lock();
        T* old = ptr;
        ptr = p;
        this->release(old);
        this->unlock();
    }
};

// -------- Virtuális változat --------
struct ResourceBase {
    virtual ~ResourceBase() = default;
    virtual void reset(int* p = nullptr) = 0;
};

struct MutexResource final : ResourceBase {
    std::mutex m;
    int* ptr;
    explicit MutexResource(int* p) : ptr(p) {}
    ~MutexResource() override {
        m.lock();
        delete ptr;
        m.unlock();
    }
    void reset(int* p = nullptr) override {
        m.lock();
        int* old = ptr;
        ptr = p;
        delete old;
        m.unlock();
    }
};

// -------- Benchmark segédfüggvény --------
template<typename F>
double measure(F&& f, int iterations = 1000000) {
    auto start = std::chrono::high_resolution_clock::now();
    for (int i = 0; i < iterations; ++i) {
        f(i);
    }
    auto end = std::chrono::high_resolution_clock::now();
    std::chrono::duration<double, std::nano> ns = end - start;
    return ns.count() / iterations; // átlagos ns / művelet
}

int main() {
    constexpr int N = 1000000;

    // 1. Policy-based teszt
    {
        using PBResource = Resource<int, MutexLock, DeleteRelease>;
        PBResource r(new int(42));
        assert(*r.get() == 42);

        double avg_ns = measure([&](int) {
            r.reset(new int(42));
        }, N);
        std::cout << "Policy-based reset átlag: " << avg_ns << " ns\n";
    }

    // 2. Virtuális teszt
    {
        MutexResource r(new int(42));
        assert(*r.ptr == 42);

        double avg_ns = measure([&](int) {
            r.reset(new int(42));
        }, N);
        std::cout << "Virtuális reset átlag: " << avg_ns << " ns\n";
    }

    return 0;
}

10.3.11 Tesztesetek és elvárt eredmény

A fenti kód két assert-et tartalmaz, amelyek a helyes működést ellenőrzik. Emellett egy egyszerű tesztprogramot is írhatunk, amely a Resource mozgatását, a reset működését és a NoLock/CustomRelease kombinációt is ellenőrzi. Az elvárt eredmény: a program hiba nélkül lefut, az assert-ek nem jeleznek hibát, és a kimenetben két átlagos időérték jelenik meg.

10.3.12 Mérési napló

A mérési naplóban a várt és a mért eredményeket külön kell feltüntetni. A várt eredmény az elmélet alapján: a policy-based változat reset műveletének gyorsabbnak kell lennie, mert a lock()/unlock() és a delete hívások statikusan kötöttek, míg a virtuális változatban a reset virtuális hívás és a destruktor is virtuális indirekciót tartalmaz. A pontos különbség a hardvertől és a fordítótól függ, de irányadóan a policy-based változat 10–40%-kal gyorsabb lehet.

10.3.14 Összefoglalás

A mixin-ek és a policy-based design a C++ sablonmeta-programozás erőteljes eszközei. Lehetővé teszik, hogy egy osztály viselkedését kisméretű, cserélhető építőelemekkel paraméterezzük, csökkentve a kódduplikációt és javítva a testreszabhatóságot. A politika osztályok statikus interfészt biztosítanak, amelyet a host class használ; a privát öröklés a mixin stílust valósítja meg, és kihasználja az üres alaposztály-optimalizálást. A megközelítés futásidőben hatékonyabb, mint a virtuális függvények, mert nincs indirekció és lehetővé teszi az inline-olást, azonban növelheti a fordítási időt és a bináris méretet. A gyakorlatban a szabványkönyvtár több komponense is ezt a mintát követi, ami mutatja a technika érettségét és fontosságát. A következő alfejezetben a teljesítményre és a karbantarthatóságra gyakorolt hatásokat vizsgáljuk részletesebben, és összevetjük a policy-based designt más statikus polimorfizmus-technikákkal.
