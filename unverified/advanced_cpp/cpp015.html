5.2 Modules és header units

5.2.1 A modulok mint a header-problémák megoldása

A hagyományos C++ fordítási modell egyik legnagyobb gyakorlati fájdalma a szövegszerű include. Amikor egy fordítási egységben #include <vector> szerepel, a preprocesszor beilleszti a teljes fejléc forrásszövegét, majd a fordító elölről kezdi az elemzést. Ez nem csupán lassú, hanem számos nyelvi és eszközláncproblémát is okoz:

  • Ismételt fordítás: ugyanazt a fejlécet minden fordítási egységben újra és újra elemezni kell, ami a nagy rendszereknél a fordítási idő jelentős részét teszi ki.
  • ODR-kockázat: a fejlécekben definiált inline függvények, sablonok és konstansok minden fordítási egységben új példányt hoznak létre. A linker ugyan összeolvasztja őket, de a szabály megsértése (pl. eltérő makró-definíciók miatt eltérő kód) undefined behaviorhez vezethet.
  • Makrószivárgás: a fejlécben definiált makrók a befoglaló fordítási egységben is láthatók maradnak, így a #define max(a,b) tönkreteheti a std::max hívását, vagy éppen fordítva. A fejlécek sorrendje befolyásolhatja a fordítást, ami karbantarthatatlanná teszi a kódot.
  • Rejtett függőségek: egy fejléc használhat egy másik fejlécet anélkül, hogy azt a fogyasztónak tudnia kellene. Ez a „működik, mert véletlenül include-oltad” jelenséghez vezet, ami a build izolációját gyengíti.
  • Körkörös include: két fejléc kölcsönösen hivatkozik egymásra, amit include guardokkal és forward deklarációkkal lehet csak feloldani, de ez törékeny mintákhoz vezet.

A C++20-ban bevezetett modulok ezeket a problémákat hivatottak kezelni. A modul nem szövegszerű beillesztés, hanem a fordítási egységek egy új szervezési formája, amelyben az interfész és az implementáció szétválik, a függőségek explicitté válnak, a makrók nem szivárognak át, és a fordító a modul interfészt egyszer lefordítja, majd annak lefordított reprezentációját (ún. Binary Module Interface, BMI) használja a többi fordítási egységben. Ez a megközelítés csökkenti a fordítási időt, javítja az izolációt és kiküszöböli a makró- és include-sorrendből adódó hibák nagy részét.

Fontos leszögezni: a modulok nem a névtereket helyettesítik, hanem a fordítási egységek szervezésének új rétegét adják. Egy modul exportálhat típusokat, függvényeket, sablonokat, sőt akár egész névtereket is, de a fogyasztó továbbra is a hagyományos névtér-szabályok szerint éri el az entitásokat. A modul neve azonosító, nem feltétlenül kapcsolódik fájlnévhez vagy névtérhez.

5.2.2 Module interface és implementation unit

A modulok alapvető építőkövei a modul egységek (module units). Ezek közül a legfontosabb a module interface unit, amelyet az export module deklaráció vezet be. Ez az egység deklarálja a modul nevét, és meghatározza, hogy mely entitások láthatók a modult importáló fordítási egységek számára.

A legegyszerűbb modul interfész így néz ki:

// math_utils.cppm – module interface unit
export module math_utils;

export int add(int a, int b) {
    return a + b;
}

export int multiply(int a, int b);

Itt az export module math_utils; deklarálja a modult. Az export kulcsszó a függvények előtt azt jelenti, hogy ezek az entitások elérhetők lesznek az importálók számára. A multiply függvénynek csak a deklarációja van itt, a definíciója külön egységben, az implementation unitben található.

Az implementation unit a következőképpen néz ki:

// math_utils.cpp – module implementation unit
module math_utils;

int multiply(int a, int b) {
    return a * b;
}

Ennek az egységnek a deklarációja nem tartalmazza az export kulcsszót, tehát nem interfész, hanem a modul belső implementációja. Az implementation unit automatikusan hozzáfér minden olyan entitáshoz, amelyet a modul interfésze deklarál vagy definiál, de az itt definiált entitások nem láthatók kívülről, hacsak az interfészben nem lettek exportálva. A multiply definíciója itt kap helyet, és az interfészben lévő deklarációval párosul.

A modul interfész és implementation unit közötti kapcsolat a következő:

  • Az interfészben lévő deklarációk (mint a multiply deklaráció) a modul összes egységében láthatók, tehát az implementation unit definiálhatja őket.
  • Az implementation unitben definiált entitások nem exportálódnak automatikusan; csak az interfészben export-tal jelölt entitások válnak a modul külső API-jává.
  • Ha egy függvényt az interfészben export nélkül deklarálunk, az a modulon belül használható, de kívülről nem érhető el. Ez lehetővé teszi belső segédfüggvények elrejtését.

A gyakorlatban a modul interfész gyakran tartalmaz inline definíciókat (ahogy az add), sablonokat és deklarációkat, míg a nagyobb implementációk az implementation unitbe kerülnek. Ez a szétválasztás hasonló a header/source felosztáshoz, de a modul interfész nem szövegszerűen kerül beillesztésre, így a header-problémák nagy része megszűnik.

5.2.3 Az export és import szabályai

A export kulcsszó csak a modul interfész egységben jelenhet meg, és csak a modul deklaráció után. Többféle szintaxisa van:

  • Egyedi entitás exportálása: export int f();
  • Export blokk: export { int g(); double h(); } – a blokkban lévő összes deklaráció exportálva lesz.
  • Névtér exportálása: export namespace utils { int helper(); } – a névtérben lévő deklarációk exportálva lesznek, de a névtér neve nem, tehát a fogyasztó utils::helper() formában éri el.

Az import deklaráció használatával egy fordítási egység elérhetővé teszi egy másik modul interfészét:

// main.cpp
import math_utils;
#include <iostream>

int main() {
    std::cout << math_utils::add(2, 3) << '\n';
}

Fontos megérteni: az import math_utils; nem szövegszerű beillesztés, hanem a modul által exportált entitások név láthatóságát biztosítja a fordítási egységben. A math_utils::add hívás itt a modul add függvényét éri el. A #include <iostream>-ot itt hagyományos fejlécként használjuk, de később látni fogjuk, hogy header unitként is importálható.

Az export és import kombinálásával újraexportálás is lehetséges:

export module geometry;

export import math_utils; // math_utils összes exportált entitása a geometria modul része lesz

Ezzel egy modul aggregálhat más modulok API-ját, ami hasznos nagy rendszerekben.

5.2.4 Module partíciók

A nagyobb modulokat fel lehet osztani partíciókra. A partíció a modul egy belső egysége, amelynek neve a modul neve után kettősponttal következik. A partíciók lehetővé teszik az interfész és az implementáció további szervezését anélkül, hogy a modul neve sérülne.

Példa egy modul partícióra, amely az interfész egy részét tartalmazza:

// geometry_core.cppm – interfész partíció
export module geometry:core;

export struct Point {
    double x, y;
};

export double distance(const Point& a, const Point& b);

A partíció deklarációja export module geometry:core;. A partíció nevét a modul neve és a kettőspont után kell megadni. Az export itt azt jelzi, hogy ez a partíció interfész-partíció, és az általa exportált entitások a modul többi része számára láthatók lesznek.

A modul fő interfésze ezt a partíciót importálja:

// geometry.cppm – fő interfész
export module geometry;

export import :core; // a :core partíció exportált entitásai a modul külső API-jává válnak

A export import :core; szintaxis azt jelenti, hogy a geometry:core partíció által exportált entitások a geometry modul részeként exportálódnak. A fogyasztó számára csak a geometry modulnév látszik, a partíciók belső szervezési részletek.

Az implementation partíció hasonló, de nem tartalmazza az export kulcsszót:

// geometry_impl.cpp – implementation partíció
module geometry:impl;

import :core; // hozzáfér a core partíció interfészéhez

double distance(const Point& a, const Point& b) {
    double dx = a.x - b.x;
    double dy = a.y - b.y;
    return std::sqrt(dx*dx + dy*dy);
}

Az implementation partíció module geometry:impl; deklarációval kezdődik, és nem exportál. A modul fő interfészének vagy más partícióinak importálnia kell ezt a partíciót, ha használni akarják a definícióit. A partíciók segítségével elkerülhető, hogy egyetlen hatalmas interfész fájl legyen, miközben a modul egységes marad.

5.2.5 Header units

A modulok bevezetése mellett a C++20 támogatja a header unitok fogalmát is. Egy hagyományos header fájl (#include-landó) importálható modulként, ha import "header.h"; vagy import <header>; szintaxist használunk. Ebben az esetben a fejlécet a fordító elkülönített fordítási egységként kezeli, és a belőle exportált entitások (tipikusan az összes deklaráció, inline definíció és sablon) elérhetővé válnak az importálóban.

Ez fontos különbség a hagyományos #include-hoz képest:

  • Makrók: a header unitként importált fejléc makrói nem szivárognak át az importáló fordítási egységbe. Ez alól kivétel, ha a makrót a fejléc explicit módon exportálja (ami a gyakorlatban ritka, és nem ajánlott). A makrók általában nem exportálódnak, ami segít elkerülni a makróütközéseket.
  • Include guardok: a header unit esetén a fejlécet a fordító egyszer elemzi, és a belső include guardok nem befolyásolják a többi fordítási egységet. Nincs szükség arra, hogy a fogyasztó include guardokat kezeljen.
  • Függőségek: a header unit által include-olt egyéb fejlécek nem válnak automatikusan láthatóvá az importálóban, hacsak azok nem lettek exportálva. Ez csökkenti a rejtett függőségeket.

A header unit importálása a következőképpen néz ki:

// main.cpp
import <iostream>;   // standard fejléc header unitként
import "legacy_config.h"; // saját header unitként
#include "other_header.h" // hagyományos include továbbra is működik

int main() {
    std::cout << "Hello\n";
}

Fontos megjegyezni, hogy a standard fejlécek header unitként való importálása a C++23-ban vált széles körben támogatottá, de a C++20-as implementációkban is elérhető lehet. A import <iostream>; hatására a std::cout és a standard könyvtár többi eleme elérhetővé válik, anélkül hogy a teljes fejléc szövegét minden fordítási egységben újra kéne elemezni. A pontos támogatottság azonban a toolchain verziójától függ, ezért a laborban ezt ellenőrizni kell.

5.2.6 Build rendszer és fordítási folyamat

A modulok bevezetése alapvetően megváltoztatja a build folyamatot. A hagyományos make/ninja alapú rendszerekben a fejlécek függőségi gráfja implicit, míg a moduloknál a modulok közötti importok explicit függőségi éleket képeznek, amelyeket a build rendszernek fel kell oldania.

A fordítási folyamat a következő lépésekből áll:

  1. Module interface unit fordítása: az interfész egységet le kell fordítani, és a fordító egy Binary Module Interface (BMI) fájlt állít elő. Ez a fájl a modul exportált entitásainak lefordított reprezentációja, amelyet a fogyasztó fordítási egységek használnak.
  2. Module implementation unit fordítása: az implementation unitet ugyanúgy le kell fordítani, de neki szüksége van a saját modul interfészének BMI-jére.
  3. Fogyasztó fordítási egységek fordítása: a import modul; deklarációt tartalmazó egységeknek szükségük van a modul BMI-jére.
  4. Header unitok fordítása: a header unitok is BMI-t vagy hasonló lefordított reprezentációt igényelnek.

A build rendszernek tehát ismernie kell a modulok közötti függőségeket, és a megfelelő sorrendben kell lefuttatnia a fordítási parancsokat. Ezt a feladatot a modern CMake (3.28+) beépítetten támogatja a FILE_SET CXX_MODULES konstrukcióval.

Egy lehetséges CMake konfiguráció:

cmake_minimum_required(VERSION 3.28)
project(modules_lab CXX)

# Modul könyvtár létrehozása
add_library(math_utils)
target_sources(math_utils
    PUBLIC FILE_SET CXX_MODULES FILES math_utils.cppm
    PRIVATE math_utils.cpp
)
target_compile_features(math_utils PUBLIC cxx_std_20)

# Fogyasztó alkalmazás
add_executable(test_app main.cpp)
target_link_libraries(test_app PRIVATE math_utils)
target_compile_features(test_app PRIVATE cxx_std_20)

# Header unit importálása (ha szükséges)
# A saját header unitot a fogyasztó számára elérhetővé kell tenni.
# Ez a rész implementációfüggő; az alábbi sor egy lehetséges megközelítés.
# target_sources(test_app PRIVATE FILE_SET CXX_MODULES FILES legacy_config.h)

A FILE_SET CXX_MODULES a CMake 3.28-tól kezdve kezeli a modul interfész fájlokat. A .cppm kiterjesztés nem kötelező, de gyakori; a CMake a fájl tartalma alapján azonosítja a modul interfészt.

A parancssori fordítás esetén a GCC, Clang és MSVC különböző kapcsolókat igényel:

  • GCC (14+): a C++20 módban a modulok alapértelmezetten támogatottak, de korábbi verziókban -fmodules-ts kapcsoló kellett. A modul interfészt így fordíthatjuk: g++ -std=c++20 -x c++ -c math_utils.cppm -o math_utils.o. A -x c++ azért kell, mert a .cppm kiterjesztést a GCC nem ismeri alapból. A modul BMI automatikusan generálódik, és a fogyasztó fordításakor a g++ -std=c++20 -c main.cpp parancs megtalálja a BMI-t, ha az elérhető a include útvonalon vagy explicit módon megadjuk.
  • Clang: clang++ -std=c++20 -fmodules -fbuiltin-module-map -c math_utils.cppm -o math_utils.o – de a -fmodules inkább a Clang moduljaira vonatkozik, a C++20 modulokhoz -fmodules-ts kellett régebben, újabban -std=c++20 elég. A pontos kapcsolók verziófüggők.
  • MSVC: /std:c++20 /interface /TP math_utils.cppm vagy /std:c++20 /module:interface – a Visual Studio build rendszere automatikusan kezeli a modulokat.

Mivel a toolchain-ek gyorsan fejlődnek, a könyv írásakor a fenti kapcsolók egy adott verzióra vonatkoznak, és a pontos parancsokat mindig a használt fordító dokumentációjában kell ellenőrizni.

5.2.7 Labor: modul- és header unit vázlat

A fejezet laborja egy kis, reprodukálható modulrendszert épít fel. A cél, hogy az olvasó a gyakorlatban is megtapasztalja a modulok és header unitok használatát, és ellenőrizze a build folyamatot.

Specifikáció:

  • Készítsünk egy math_utils modult, amely két függvényt exportál: add és multiply.
  • Készítsünk egy legacy_config.h fejlécet, amely egy legacy_double inline függvényt és egy LEGACY_MODE makrót tartalmaz.
  • A főprogram importálja a math_utils modult, és importálja a legacy_config.h fájlt header unitként (vagy #include-olja, ha a toolchain nem támogatja a header unit importot).
  • A program írja ki az add(2,3), multiply(2,3) és legacy_double(4) értékeit.

Fájlok:

math_utils.cppm (module interface unit):

export module math_utils;

export int add(int a, int b) {
    return a + b;
}

export int multiply(int a, int b);

math_utils.cpp (module implementation unit):

module math_utils;

int multiply(int a, int b) {
    return a * b;
}

legacy_config.h:

#ifndef LEGACY_CONFIG_H
#define LEGACY_CONFIG_H

inline int legacy_double(int x) {
    return x * 2;
}

#define LEGACY_MODE 1

#endif

main.cpp:

import math_utils;
import "legacy_config.h"; // header unit import; ha nem támogatott, használjunk #include "legacy_config.h"
#include <iostream>

int main() {
    std::cout << math_utils::add(2, 3) << ' '
              << math_utils::multiply(2, 3) << ' '
              << legacy_double(4) << '\n';
}

Build lépések:

A reprodukálhatóság érdekében rögzítsük a toolchain-t és a szabványverziót. A példában GCC 14-et és C++20-at használunk, de a parancsok a fentiek szerint adaptálhatók.

A CMake build:

cmake_minimum_required(VERSION 3.28)
project(modules_lab CXX)

add_library(math_utils)
target_sources(math_utils
    PUBLIC FILE_SET CXX_MODULES FILES math_utils.cppm
    PRIVATE math_utils.cpp
)
target_compile_features(math_utils PUBLIC cxx_std_20)

add_executable(test_app main.cpp)
target_link_libraries(test_app PRIVATE math_utils)
target_compile_features(test_app PRIVATE cxx_std_20)
# Header unit beállítása (ha a toolchain támogatja):
# target_sources(test_app PRIVATE FILE_SET CXX_MODULES FILES legacy_config.h)

A build futtatása:

cmake -S . -B build -G Ninja
cmake --build build
./build/test_app

Mérési napló:

A labor során mérjük a következőket:

  • Fordítási idő: a teljes build idő (cmake --build build idő). Ezt legalább háromszor futtassuk, és vegyük a mediánt.
  • Bináris méret: a létrejött végrehajtható fájl mérete.
  • Futási kimenet: a program kimenete.

A mért és várt eredményt külön táblázatban rögzítsük:

Mérőszám Mért érték (medián) Várt tartomány
Build idő (s) 1.23 < 5
Bináris méret (KB) 45 20–100
Kimenet “5 6 8” “5 6 8”

A várt tartományok tájékoztató jellegűek; a cél a reprodukálhatóság és a modulok használatának igazolása, nem a teljesítményoptimalizálás.

Ellenőrzés:

A labor során ellenőrizzük, hogy:

  • A modul interfész és implementation unit helyesen van-e szétválasztva.
  • A header unit importálása (ha támogatott) megszünteti-e a makrószivárgást: a LEGACY_MODE makró nem érhető el a main.cpp-ben, míg a #include esetén igen. Ezt egy fordítási hibával demonstrálhatjuk: ha a main.cpp-ben hivatkozunk LEGACY_MODE-ra, akkor header unit import esetén fordítási hibát kapunk, include esetén pedig nem.
  • A build rendszer helyesen kezeli-e a modul függőségeket: ha a main.cpp-t a modul interfész nélkül próbáljuk fordítani, a fordítás hibát ad.

A labor átadandó eredménye a build parancsok, a forrásfájlok, a mérési napló és a futtatási kimenet.

5.2.8 Tipikus hibák és elkerülésük

A modulok használata során számos gyakori hiba merülhet fel, amelyeket érdemes előre ismerni.

  1. Export szintaxis hibás használata:
    • Az export csak a modul interfész egységben jelenhet meg, és csak a modul deklaráció után. Az implementation unitben vagy a partícióban (ha nem interfész partíció) az export használata fordítási hibát okoz.
    • Az export nem alkalmazható minden deklarációra, például nem lehet exportálni egy static változót vagy egy belső linkage-ű entitást. A modul interfészben csak olyan entitás exportálható, amelynek külső linkage-je van.
  2. A modul nevének ütközése:
    • Két modul nem viselheti ugyanazt a nevet ugyanabban a programban. A modul neve globális azonosító, ezért a nagy rendszerekben ügyelni kell az egyedi nevekre (pl. cég vagy projekt prefix).
  3. Helytelen partícióhasználat:
    • A partíció nevének a modul nevével kell kezdődnie, kettősponttal elválasztva. A module :part; deklaráció hiányos modulnév esetén hibás.
    • A partíciók közötti importálásnál a partíció nevét kell használni, nem a modul nevét: import :core; a helyes, import geometry:core; nem szükséges (bár egyes implementációk elfogadhatják).
  4. A globális modul fragment figyelmen kívül hagyása:
    • Ha a modul interfészben #include direktívát szeretnénk használni, akkor azt a globális modul fragmentben kell elhelyezni, amely a module; deklarációval kezdődik az export module előtt. Ez a rész csak preprocesszor direktívákat tartalmazhat, és az itt include-olt fejlécek entitásai nem lesznek a modul részei, hacsak nem exportáljuk őket külön.

Példa a globális modul fragmentre:

module;
#include <cstdint> // ez a fejléc nem lesz a modul része
export module mymod;

export std::int64_t get_value(); // itt a std::int64_t már látható, mert a globális fragmentben include-oltuk

Helytelen, ha a module; deklaráció után próbálunk #include-ot használni: ilyenkor a preprocesszor direktíva a modul deklaráció után érvénytelen, mert a modul interfészben már nem lehet hagyományos fejléceket include-olni.

  1. Header unit nem megfelelő kezelése:
    • Nem minden header alkalmas header unitként való importálásra. Ha a header kódból függ a makrók szivárgásától, vagy ha a header állapotot tart fenn include guardokon keresztül, a header unit importálása más viselkedést eredményezhet. Általában a jól megírt, önálló fejlécek működnek header unitként, de ezt tesztelni kell.
    • A header unit importálása nem teszi a makrókat elérhetővé. Ha a fogyasztó kód a fejlécben definiált makrót szeretné használni, akkor a hagyományos #include-ot kell választania.
  2. Build rendszer hiányos konfigurációja:
    • Ha a build rendszer nem ismeri a modulok függőségeit, akkor a párhuzamos fordítás során versenyhelyzet alakulhat ki a BMI fájlok generálásakor. A modern CMake kezeli ezt, de a kézi makefile-okban explicit függőségi szabályokat kell írni.
    • A modul interfészeket mindig a fogyasztó fordítási egységek előtt kell lefordítani. Ha a BMI hiányzik, a fordítás hibát ad.

5.2.9 Összefoglalás

A C++20 modulok a header-alapú fejlesztés strukturális problémáira adnak választ: megszüntetik a szövegszerű include ismétlődését, csökkentik a makrók és a rejtett függőségek okozta kockázatokat, és explicitté teszik a függőségi gráfot. A modul interfész és implementation unit szétválasztása lehetővé teszi a kód szervezését, a partíciók a nagy modulok belső tagolását, a header unitok pedig fokozatos átmenetet biztosítanak a hagyományos fejlécekről a modulokra.

A modulok bevezetése azonban nem triviális: a build rendszereknek, a toolchaineknek és a fejlesztőknek is alkalmazkodniuk kell. A gyakorlati használathoz elengedhetetlen a build folyamat pontos ismerete, a hibák korai felismerése és a reprodukálható tesztek alkalmazása. A laborban felépített kis modulrendszer ezt a folyamatot gyakoroltatja, és megalapozza a következő fejezetben tárgyalt ranges és views témakört, amely a modulokra épülő modern C++ programozás egy másik kulcsterülete.

5.2.10 Önellenőrző kérdés

Miben különbözik a import <vector>; (header unit) a #include <vector> direktívától a makrók és a fordítási idő szempontjából? Magyarázza el, miért nem szivárog át a vector fejlécben definiált makró a fogyasztó fordítási egységbe header unit importálásakor.
