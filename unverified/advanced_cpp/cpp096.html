25.3 Pimpl, compilation firewall és plugin API

A fordítási és bináris határok megértése nélkül a Pimpl és a plugin API csupán trükknek tűnik. A C++ fordítási modellje a fordítási egységekre (translation unit, TU) épül: minden .cpp fájl a benne szereplő #include direktívák után egy önálló egységet alkot, amelyet a fordító külön dolgoz fel. A TU-k közötti kapcsolatot a deklarációk teremtik meg: egy headerben deklarált függvény vagy osztály lehetővé teszi, hogy más TU-k hivatkozzanak rá anélkül, hogy ismernék a definícióját. Ez a fordítási határ: amit a header tartalmaz, az minden azt include-oló TU-ba bekerül, így annak bármilyen változása az összes érintett TU újrafordítását kényszeríti ki.

A bináris határ ezzel szemben a lefordított objektumfájlok, statikus könyvtárak és megosztott könyvtárak közötti interfész. Itt már nem forráskód, hanem gépi kód, szimbólumtábla és hívási konvenciók léteznek. A bináris határon az osztályok elrendezése, a virtuális függvénytábla (vtable) felépítése, a függvények névmanipulációja (name mangling) és a paraméterátadás módja mind rögzített. Ha ezek bármelyike megváltozik, a bináris kompatibilitás megszakad, és a régi binárisok nem működnek együtt az új könyvtárral.

A Pimpl (pointer-to-implementation) minta éppen e két határ kezelésére szolgál: a fordítási határon csökkenti a függőséget, a bináris határon pedig stabil ABI-t biztosít. A plugin API-k pedig a bináris határ legszigorúbb formáját valósítják meg: olyan interfészt, amely akár különböző fordítóval vagy nyelvvel készült binárisok között is működik.

25.3.1 Pimpl és opaque pointer

A Pimpl alapötlete, hogy az osztály publikus headerje ne tartalmazza a privát adattagok típusát, csak egy mutatót egy előre deklarált, nem teljes típusra. A tényleges adattagok a .cpp fájlban definiált struktúrában élnek. Ezt a mutatót gyakran opaque pointernek nevezik, mert a header szempontjából a mutatott típus átlátszatlan.

Tekintsünk egy naiv Logger osztályt, amelynek privát adattagjai között szerepel egy std::ofstream és egy std::mutex:

// naive_logger.h
#include <fstream>
#include <mutex>
#include <string>

class Logger {
public:
    explicit Logger(std::string filename);
    void log(std::string_view message);

private:
    std::ofstream file_;
    std::mutex mutex_;
    std::string filename_;
};

Ennek a headernek minden felhasználója kénytelen include-olni a <fstream>, <mutex> fejléceket, és a privát adattagok bármilyen változása – például egy új puffer hozzáadása – újrafordítja az összes include-oló TU-t. Ráadásul az osztály mérete és elrendezése a bináris határon is rögzül, így a könyvtár frissítésekor a felhasználó binárisai elavulhatnak.

A Pimpl verzió a következő:

// logger.h
#include <memory>
#include <string_view>
#include <string>

class Logger {
public:
    explicit Logger(std::string filename);
    ~Logger();                      // destruktor a cpp-ben

    Logger(Logger&&) noexcept;      // move konstruktor
    Logger& operator=(Logger&&) noexcept;

    Logger(const Logger&) = delete; // másolás letiltva
    Logger& operator=(const Logger&) = delete;

    void log(std::string_view message);

private:
    class Impl;                     // előre deklarált, nem teljes típus
    std::unique_ptr<Impl> pImpl_;
};

A header mostantól csak a std::unique_ptr és a std::string_view deklarációit igényli, a nehéz fejléceket (<fstream>, <mutex>) nem. Az Impl osztály definíciója a .cpp fájlban található:

// logger.cpp
#include "logger.h"
#include <fstream>
#include <mutex>

class Logger::Impl {
public:
    explicit Impl(std::string filename)
        : file_(std::move(filename)), mutex_() {}

    void log(std::string_view message) {
        std::lock_guard<std::mutex> lock(mutex_);
        file_ << message << '\n';
    }

private:
    std::ofstream file_;
    std::mutex mutex_;
};

Logger::Logger(std::string filename)
    : pImpl_(std::make_unique<Impl>(std::move(filename))) {}

Logger::~Logger() = default;  // itt az Impl teljes típusa ismert

Logger::Logger(Logger&&) noexcept = default;
Logger& Logger::operator=(Logger&&) noexcept = default;

void Logger::log(std::string_view message) {
    pImpl_->log(message);
}

A destruktor default definíciója a .cpp fájlban létfontosságú: ha a headerben lenne, a std::unique_ptr destruktora nem tudná felszabadítani a nem teljes Impl típust, mert a delete operátorhoz szükség van a teljes típusra. A C++ szabály szerint a std::unique_ptr destruktora static_assertet végez a teljes típusra, így a hibát fordítási időben észleljük, de a helyes megoldás az, hogy a destruktort abban a TU-ban definiáljuk, ahol az Impl teljes.

A move műveletek defaultként a .cpp-ben vannak definiálva, mert a std::unique_ptr move konstruktora és értékadója szintén teljes típust igényel a destruktorhoz hasonlóan. A copy műveletek törölve vannak, mert a std::unique_ptr nem másolható; ha másolható Logger-t akarunk, kézzel kell implementálni a copy konstruktort és értékadót, amelyek új Impl-et hoznak létre.

A Pimpl minta tehát a következő előnyöket nyújtja:

  1. Fordítási tűzfal (compilation firewall): a privát adattagok változása nem érinti a header felhasználóit, így a build idő jelentősen csökkenhet nagy projektekben.
  2. Bináris stabilitás: az osztály mérete és elrendezése a headerben csak egy std::unique_ptr marad, amelynek mérete platformonként és szabványos könyvtárverziónként állandó (általában egy mutató). Így a privát implementáció bővítése nem változtatja meg az osztály layoutját, és a felhasználó binárisok újrafordítás nélkül működhetnek.
  3. Jobb izoláció: a header nem szivárogtatja ki a belső típusokat, csökkentve a névütközéseket és a felesleges include-okat.

Hátrányai is vannak: minden objektum egy heap allokációt igényel, a hívások egy indirekción mennek keresztül, és a kód bonyolultabbá válik. A std::unique_ptr használata miatt az osztály automatikusan nem másolható; ha másolásra van szükség, azt explicit módon kell megvalósítani, ami gyakran az Impl mély másolását jelenti.

25.3.2 Kivételbiztonság és erőforrás-kezelés

A Pimpl konstruktorban a std::make_unique<Impl> hívás kivételt dobhat, például ha a fájl megnyitása sikertelen. Ebben az esetben a std::unique_ptr konstruktora még nem vette át a memória tulajdonjogát, így nem történik szivárgás. Ha a konstruktor törzsében dobunk kivételt, a már létrehozott pImpl_ automatikusan felszabadul, mert a tagok destruktorai lefutnak. Ez a RAII elv természetes következménye.

A destruktor default definíciója akkor is helyes, ha az Impl destruktora kivételt dob – ami nem ajánlott, de ha megtörténik, a std::unique_ptr garantálja a memória felszabadítását. A noexcept specifikáció a destruktoron implicit, így ha az Impl destruktora kivételt dob, a program std::terminate-et hív.

25.3.3 Pimpl és ABI stabilitás

A Pimpl egyik legfontosabb alkalmazási területe a bináris kompatibilitás megőrzése. Tegyük fel, hogy egy megosztott könyvtár Logger osztályt exportál. Ha a naiv verzióban hozzáadunk egy std::string buffer_; adattagot, az osztály mérete megváltozik, és minden olyan kliens bináris, amely a régi headerrel lett lefordítva, hibásan fog működni, mert a tagok eltolása eltolódik. A Pimpl verzióban az osztály mérete változatlan marad, mert a headerben csak egy mutató van. A bővítés az Impl osztályt érinti, amely a .cpp fájlban van, így a kliens binárisok továbbra is érvényesek maradnak.

Fontos megjegyezni, hogy a Pimpl önmagában nem garantál teljes ABI kompatibilitást: ha a publikus függvények szignatúrája változik, vagy a névmanipuláció eltér, a bináris kompatibilitás megszakad. A Pimpl csak a privát adattagok változásától véd.

25.3.4 C ABI és plugin loading

A plugin API-k olyan bináris interfészek, amelyek lehetővé teszik, hogy a program futás közben töltsön be további kódbővítményeket. A plugin lehet külön folyamatban, de a leggyakoribb esetben ugyanabban a folyamatban, dinamikus könyvtárként töltődik be. A plugin határán a C++ típusok, kivételek, RTTI és memóriaallokátorok használata veszélyes, mert ezek ABI-ja nem stabil a különböző fordítók és verziók között. Ezért a plugin interfészeket gyakran C ABI-val definiálják: extern "C" függvények, egyszerű C típusok, és opak mutatók.

A C ABI alapelve:

  • A függvények extern "C" deklarációval rendelkeznek, így a nevük nem lesz névmanipulált, és a hívási konvenció a platform C konvencióját követi.
  • A paraméterek és visszatérési értékek csak olyan típusok lehetnek, amelyek elrendezése C-ben is definiált: alap típusok, mutatók, struktúrák, amelyek nem tartalmaznak C++-specifikus elemeket (virtuális függvények, std::string, stb.).
  • A hibakezelés visszatérési kódokkal vagy hibakódokkal történik, nem kivételekkel, mert a kivételek a C ABI-n keresztül nem terjednek.
  • A memóriakezelés explicit: a plugin által lefoglalt memóriát a plugin szabadítja fel, vagy a gazdaprogram egy megadott callback segítségével.

Egy egyszerű plugin interfész például egy szöveges üzeneteket feldolgozó modul:

// plugin_api.h (C ABI)
#ifdef __cplusplus
extern "C" {
#endif

// Opaque handle: a plugin belső állapotát rejti.
typedef struct plugin_handle_t plugin_handle_t;

// Plugin API verziója. A gazdaprogram ezzel ellenőrzi a kompatibilitást.
int plugin_api_version(void);

// Létrehoz egy plugin példányt. A visszatérési érték NULL hiba esetén.
plugin_handle_t* plugin_create(void);

// Feldolgoz egy üzenetet. Visszatérés: 0 siker, -1 hiba.
int plugin_process(plugin_handle_t* handle, const char* message,
                   char* output, size_t output_size);

// Felszabadítja a plugin példányt.
void plugin_destroy(plugin_handle_t* handle);

#ifdef __cplusplus
}
#endif

A plugin_handle_t egy opak típus: a gazdaprogram csak mutatót lát, a tényleges definíciót a plugin tartalmazza. Ez ugyanaz az opaque pointer elv, mint a Pimpl esetében, de itt a C ABI szintjén.

A plugin implementációja C++-ban a következő lehet:

// plugin_impl.cpp
#include "plugin_api.h"
#include <string>
#include <cstring>

struct plugin_handle_t {
    std::string prefix;
};

extern "C" int plugin_api_version(void) {
    return 1;
}

extern "C" plugin_handle_t* plugin_create(void) {
    try {
        return new plugin_handle_t{"[plugin] "};
    } catch (...) {
        return nullptr;
    }
}

extern "C" int plugin_process(plugin_handle_t* handle, const char* message,
                              char* output, size_t output_size) {
    if (!handle || !message || !output) return -1;
    try {
        std::string result = handle->prefix + message;
        if (result.size() + 1 > output_size) return -2; // puffer túl kicsi
        std::strncpy(output, result.c_str(), output_size);
        return 0;
    } catch (...) {
        return -1;
    }
}

extern "C" void plugin_destroy(plugin_handle_t* handle) {
    delete handle;
}

A gazdaprogram dinamikusan tölti be a plugint. POSIX rendszeren a dlopen, dlsym, dlclose függvényekkel, Windows-on a LoadLibrary, GetProcAddress, FreeLibrary függvényekkel. A példa POSIX-rendszerre:

// host.cpp
#include "plugin_api.h"
#include <dlfcn.h>
#include <iostream>
#include <string>
#include <cstring>

int main() {
    void* lib = dlopen("./libplugin.so", RTLD_NOW);
    if (!lib) {
        std::cerr << "dlopen failed: " << dlerror() << '\n';
        return 1;
    }

    auto version_fn = reinterpret_cast<int (*)()>(
        dlsym(lib, "plugin_api_version"));
    auto create_fn = reinterpret_cast<plugin_handle_t* (*)()>(
        dlsym(lib, "plugin_create"));
    auto process_fn = reinterpret_cast<int (*)(plugin_handle_t*, const char*, char*, size_t)>(
        dlsym(lib, "plugin_process"));
    auto destroy_fn = reinterpret_cast<void (*)(plugin_handle_t*)>(
        dlsym(lib, "plugin_destroy"));

    if (!version_fn || !create_fn || !process_fn || !destroy_fn) {
        std::cerr << "missing symbols\n";
        dlclose(lib);
        return 1;
    }

    if (version_fn() != 1) {
        std::cerr << "incompatible plugin version\n";
        dlclose(lib);
        return 1;
    }

    plugin_handle_t* handle = create_fn();
    if (!handle) {
        std::cerr << "plugin_create failed\n";
        dlclose(lib);
        return 1;
    }

    char buffer[256];
    int rc = process_fn(handle, "hello", buffer, sizeof(buffer));
    if (rc == 0) {
        std::cout << "Result: " << buffer << '\n';
    } else {
        std::cerr << "plugin_process failed with code " << rc << '\n';
    }

    destroy_fn(handle);
    dlclose(lib);
    return 0;
}

A példa jól mutatja a C ABI használatát: a reinterpret_cast a függvénypointerekre, a dlsym által visszaadott void* átalakítása, a verzióellenőrzés, a hibakezelés, és az erőforrások felszabadítása. A plugin_handle_t opak típus, a gazdaprogram nem fér hozzá a belső std::string taghoz.

25.3.5 A plugin API tervezési szempontjai

A plugin interfész tervezésekor a következő szempontokat kell figyelembe venni:

  1. Verziókezelés: a plugin API-nak mindig tartalmaznia kell egy verziószámot, amelyet a gazdaprogram a betöltéskor ellenőriz. Ez lehet egy függvény (plugin_api_version()), vagy egy struktúra, amely a verziót és a funkciópointereket tartalmazza. A verziószám növelése jelzi az inkompatibilis változásokat.

  2. Hibakezelés: a C ABI-n keresztül nem dobhatunk kivételeket, ezért minden függvénynek visszatérési kóddal kell jeleznie a sikert vagy hibát. A hibakódok értelmezését dokumentálni kell. A plugin implementációban minden kivételt el kell kapni, és hibakóddá kell alakítani.

  3. Memóriakezelés: a plugin által lefoglalt memória felszabadítását a plugin végzi, mert a gazdaprogram esetleg más allokátort használ. Ha a gazdaprogram ad át puffert, annak méretét explicit paraméterben kell megadni, és a plugin nem írhat túl rajta.

  4. Szálbiztonság: ha a plugin függvényeit több szálból hívják, a plugin belső állapotát szinkronizálni kell. A C ABI nem tartalmaz szinkronizációs primitíveket, ezért a plugin dokumentációjában rögzíteni kell a szálbiztonsági garanciákat.

  5. Nyelvfüggetlenség: a C ABI lehetővé teszi, hogy a plugin más nyelven (C, Rust, Python CFFI) is implementálható legyen. Ez növeli a rugalmasságot, de a típusoknak C-kompatibilisnek kell lenniük.

25.3.6 Tipikus hibák és elkerülésük

A Pimpl és plugin API használata során a következő hibák gyakoriak:

  • Hiányzó destruktor a headerben: Ha a destruktort a headerben deklaráljuk ~Logger() = default; és az Impl nem teljes, a fordító hibát ad, mert a std::unique_ptr destruktora nem tudja törölni a nem teljes típust. A megoldás: a destruktort a .cpp fájlban definiáljuk.

  • Másolás engedélyezése véletlenül: Ha a Pimpl osztályban elfelejtjük törölni a copy konstruktort, a fordító implicit módon megpróbálja lemásolni a std::unique_ptr tagot, ami hibát okoz. A másolást explicit módon kell kezelni.

  • Kivétel a plugin határon: Ha a plugin függvényben kivétel dobódik, és az nem kerül elkapásra a extern "C" függvényen belül, a kivétel átlépi a C ABI határt, ami undefined behavior. Minden plugin függvényt try/catch blokkba kell zárni.

  • Nem megfelelő verzióellenőrzés: A gazdaprogramnak mindig ellenőriznie kell a plugin verzióját a betöltés után, különben inkompatibilis plugin esetén a viselkedés nem definiált.

  • Szimbólumnevek ütközése: Ha a plugin több extern "C" függvényt exportál, és két plugin ugyanazt a nevet használja, ütközés léphet fel. Ezt elkerülhetjük egyedi előtagokkal vagy a szimbólumok dinamikus betöltésénél a teljes elérési útvonal használatával.

  • Erőforrás-szivárgás a plugin életciklusban: A gazdaprogramnak mindig párosítania kell a create és destroy hívásokat, és a dlclose előtt minden handle-t fel kell szabadítani. A dlclose után a plugin kódja már nem elérhető, így a handle-ek használata utánuk undefined behavior.

25.3.7 Labor: Pimpl- és plugin-API tervezése

A labor célja a fenti minták gyakorlati alkalmazása. A hallgató feladata:

  1. Készítsen egy Config osztályt Pimpl mintával, amely egy JSON-szerű konfigurációt tárol. A header csak a publikus interfészt tartalmazza, a privát implementáció a .cpp fájlban van. Az osztály támogassa a move szemantikát, a másolást mély másolással, és a destruktort a .cpp-ben definiálja.

  2. Tervezzen egy plugin API-t C ABI-val egy egyszerű szűrő modulhoz, amely szöveges üzeneteket transzformál (pl. nagybetűsítés, előtag hozzáadása). A plugin API tartalmazzon verziókezelést, hibakódokat, opak handle-t, és a memória kezelését.

  3. Valósítsa meg a plugint és a gazdaprogramot, amely dinamikusan tölti be a plugint, ellenőrzi a verziót, feldolgoz egy üzenetet, és felszabadítja az erőforrásokat.

25.3.8 Build és tesztkörnyezet

A labor elvégzéséhez a következő build konfigurációt javasoljuk:

  • Fordító: GCC 13 vagy Clang 17, C++20 standard (-std=c++20).
  • Optimalizáció: -O2 -g a fejlesztéshez, -O3 -DNDEBUG a méréshez.
  • Figyelmeztetések: -Wall -Wextra -Wpedantic -Wconversion -Wsign-conversion.
  • Sanitizerek: -fsanitize=address,undefined a teszteléshez.
  • Dinamikus könyvtár: -fPIC -shared a plugin fordításhoz.
  • Linkelés: -ldl POSIX rendszeren a dlopen használatához.

A build parancsok például (Linux, GCC):

# Pimpl osztály fordítása
g++ -std=c++20 -O2 -Wall -Wextra -Wpedantic -c config.cpp -o config.o

# Plugin fordítása megosztott könyvtárrá
g++ -std=c++20 -O2 -fPIC -shared plugin_impl.cpp -o libplugin.so

# Gazdaprogram fordítása
g++ -std=c++20 -O2 -Wall -Wextra -Wpedantic host.cpp config.o -ldl -o host

25.3.9 Tesztcsomag

A tesztek a következő eseteket fedik le:

  • A Config osztály konstrukciója és destruálása nem szivárog (ASan ellenőrzés).
  • A Config másolása mély másolatot hoz létre, a módosítás nem érinti az eredetit.
  • A plugin betöltése sikeres, a verzió ellenőrzése megtörténik.
  • A plugin process függvénye hibásan null mutatóval hívva -1-et ad vissza.
  • A gazdaprogram a destroy után nem hívja a plugint.

A teszteket egy egyszerű C++ teszt keretrendszerrel (pl. Catch2, doctest) vagy saját assert alapú main-nel lehet futtatni.

25.3.10 Mérési napló

A mérési naplóban rögzíteni kell a következőket:

  • Fordítási idő: a Pimpl verzió és a naiv verzió build ideje. A várt eredmény: a Pimpl verzió headerjének változása nem érinti a függő TU-kat, így a build idő csökken.
  • Bináris méret: a Pimpl osztályt használó kliens bináris mérete változatlan marad, ha az Impl bővül.
  • Futásidő: a Pimpl indirekció költsége mérhető egy benchmarkkal, amely sok hívást végez. A várt eredmény: a költség minimális, de nem nulla.

A mérési naplóban külön kell választani a mért értékeket a várt értékektől, és rögzíteni kell a hardver, az operációs rendszer, a fordító verzióját és az optimalizációs szintet.
