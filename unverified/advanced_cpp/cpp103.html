27.2 Behavioral patterns

A viselkedési tervezési minták a GoF (Gang of Four) katalógus harmadik nagy csoportját alkotják. Míg a létrehozási minták az objektumok létrehozásának módját, a szerkezeti minták pedig az osztályok és objektumok összekapcsolását szervezik, a viselkedési minták az objektumok közötti felelősségmegosztást, kommunikációt és vezérlési folyamatot írják le. Céljuk, hogy a rendszer viselkedését rugalmasan, újrafelhasználhatóan és a konkrét osztályoktól függetlenül lehessen megvalósítani.

A modern C++ alapvetően megváltoztatta e minták megvalósítási lehetőségeit. A klasszikus, öröklésen és absztrakt interfészeken alapuló megközelítések gyakran helyettesíthetők értékalapú polimorfizmussal (std::variant + std::visit), type erasure-rel (std::function, std::any), lambda kifejezésekkel és sablonparaméterekkel (policy-based design). A cél nem a minták elvetése, hanem annak felismerése, hogy melyik eszköz mikor ad jobb teljesítményt, karbantarthatóságot vagy fordítási időt. Ebben az alfejezetben a három leggyakrabban előforduló viselkedési mintát – a Strategy, az Observer és a Visitor – vizsgáljuk meg, különös tekintettel a modern C++-os alternatívákra.

27.2.1 Strategy minta

27.2.2 A minta célja és hagyományos megvalósítása

A Strategy minta egy algoritmuscsalád tagjait egymással felcserélhetővé teszi, és az algoritmus kiválasztását a futásidőre bízza. A kontextus objektum nem ismeri a konkrét algoritmus részleteit, csak egy absztrakt interfészen keresztül hivatkozik rá. Klasszikus, öröklésalapú megvalósítása a következő elemekből áll:

  • Strategy (absztrakt interfész): definiálja a műveletet, amit a konkrét stratégiák implementálnak.
  • ConcreteStrategy: az interfész egy-egy konkrét megvalósítása.
  • Context: tárol egy Strategy referenciát vagy pointert, és a művelet elvégzésekor delegálja a hívást.
#include <iostream>
#include <memory>
#include <string>

class SortStrategy {
public:
    virtual ~SortStrategy() = default;
    virtual void sort(std::vector<int>& data) const = 0;
};

class QuickSort : public SortStrategy {
public:
    void sort(std::vector<int>& data) const override {
        // ... quicksort implementáció
        std::ranges::sort(data); // példa kedvéért
    }
};

class MergeSort : public SortStrategy {
public:
    void sort(std::vector<int>& data) const override {
        // ... mergesort implementáció
        std::ranges::stable_sort(data); // példa
    }
};

class Sorter {
    std::unique_ptr<SortStrategy> strategy_;
public:
    explicit Sorter(std::unique_ptr<SortStrategy> s)
        : strategy_(std::move(s)) {}

    void setStrategy(std::unique_ptr<SortStrategy> s) {
        strategy_ = std::move(s);
    }

    void sort(std::vector<int>& data) const {
        strategy_->sort(data);
    }
};

Ez a megoldás működik, de minden új stratégiához új osztályt kell létrehozni, ami boilerplate kódot és indirekciót okoz. Ráadásul a Sorter csak SortStrategy-ből származó objektumokat tud tárolni, ami virtual call overheadet jelent.

27.2.3 Modern C++ alternatívák

27.2.3.1 std::function alapú stratégia

Ha a stratégia csupán egyetlen hívható függvényt igényel, akkor a legegyszerűbb és leggyakoribb megoldás az std::function használata:

#include <functional>
#include <vector>
#include <algorithm>
#include <iostream>

class Sorter {
    std::function<void(std::vector<int>&)> sortFn_;
public:
    explicit Sorter(std::function<void(std::vector<int>&)> f)
        : sortFn_(std::move(f)) {}

    void sort(std::vector<int>& data) const {
        sortFn_(data);
    }
};

int main() {
    std::vector<int> v{3, 1, 2};
    Sorter quickSorter([](std::vector<int>& d){ std::ranges::sort(d); });
    quickSorter.sort(v);

    Sorter stableSorter([](std::vector<int>& d){ std::ranges::stable_sort(d); });
    stableSorter.sort(v);
}

Ez rendkívül rugalmas: bármilyen lambdát, függvényt, funktort vagy akár bindolt függvényt átadhatunk. A hátránya, hogy az std::function típus-erasure-t végez, ami általában dinamikus memóriafoglalással jár (kivéve kis függvényobjektumok esetén, ahol az implementációk gyakran small buffer optimization-t alkalmaznak), valamint a hívás indirekción keresztül történik. A legtöbb alkalmazásban ez elhanyagolható, de extrém hot path-okban érdemes megfontolni más megoldást.

27.2.3.2 Sablonparaméteres (policy-based) megoldás

Ha a stratégia típusa fordítási időben ismert, akkor a leghatékonyabb megoldás a sablonparaméter használata. Ezt a technikát a policy-based design (lásd 27.4) részletesen tárgyalja, de a Strategy mintára is alkalmazható:

template <typename SortPolicy>
class Sorter {
    SortPolicy policy_;
public:
    void sort(std::vector<int>& data) const {
        policy_.sort(data);
    }
};

struct QuickSortPolicy {
    void sort(std::vector<int>& data) const { std::ranges::sort(data); }
};

Itt nincs virtual call és nincs indirekció, viszont a Sorter típusa függ a policy típusától, így futásidőben nem cserélhető. Ha a stratégia cserélhetősége futásidőben követelmény, akkor az std::function vagy a klasszikus interfész a megfelelő választás.

27.2.3.3 std::variant alapú stratégia

Ha a lehetséges stratégiák halmaza zárt (azaz ismert és ritkán változik), akkor az std::variant használata értékalapú, futásidejű polimorfizmust biztosít:

#include <variant>
#include <vector>
#include <algorithm>

struct QuickSort {
    void sort(std::vector<int>& d) const { std::ranges::sort(d); }
};
struct MergeSort {
    void sort(std::vector<int>& d) const { std::ranges::stable_sort(d); }
};

using SortStrategy = std::variant<QuickSort, MergeSort>;

class Sorter {
    SortStrategy strategy_;
public:
    Sorter(SortStrategy s) : strategy_(std::move(s)) {}

    void sort(std::vector<int>& data) const {
        std::visit([&](const auto& s){ s.sort(data); }, strategy_);
    }
};

Ez a megközelítés elkerüli a dinamikus memóriafoglalást, és a hívás a std::visit segítségével gyakran vtable nélkül, generált függvénypointer-táblán keresztül történik. A hátránya, hogy új stratégia hozzáadása a std::variant módosítását igényli, ami a teljes kód újrafordításával járhat.

27.2.5 Observer minta

27.2.6 A minta célja és hagyományos megvalósítása

Az Observer minta egy-a-többhöz függőséget definiál az objektumok között: amikor egy Subject (megfigyelt objektum) állapota megváltozik, minden regisztrált Observer értesítést kap. Ezt a mintát publish-subscribe mintának is nevezik. A klasszikus C++-os implementáció általában a következő:

#include <vector>
#include <memory>
#include <iostream>
#include <string>

class Observer {
public:
    virtual ~Observer() = default;
    virtual void update(const std::string& message) = 0;
};

class Subject {
    std::vector<std::shared_ptr<Observer>> observers_;
public:
    void attach(std::shared_ptr<Observer> obs) {
        observers_.push_back(std::move(obs));
    }

    void detach(std::shared_ptr<Observer> obs) {
        std::erase(observers_, obs);
    }

    void notify(const std::string& msg) {
        for (const auto& obs : observers_) {
            obs->update(msg);
        }
    }
};

class ConcreteObserver : public Observer {
    std::string name_;
public:
    explicit ConcreteObserver(std::string name) : name_(std::move(name)) {}
    void update(const std::string& msg) override {
        std::cout << name_ << " received: " << msg << '\n';
    }
};

Ez a minta számos veszélyt rejt magában:

  • Élettartam-kezelés: ha az observer megsemmisül, de a subject még tárolja a pointert, dangling pointerhez vezet. A std::shared_ptr enyhítheti, de körkörös referenciákat okozhat (subject -> observer -> subject).
  • Értesítés közbeni módosítás: ha egy observer az update során leiratkozik vagy új observer-t ad hozzá, az a observers_ vektor iterálása közben UB-t vagy hibát okozhat.
  • Kivételbiztonság: ha egy observer kivételt dob, a többi nem kap értesítést, és a subject állapota inkonzisztens lehet.
  • Konkurencia: több szálból történő regisztrálás/értesítés esetén szinkronizáció szükséges.

27.2.7 Modern C++ megvalósítás callbackekkel

A modern C++ a hagyományos observer interfész helyett gyakran egyszerűbb, típus-erasure alapú callback regisztrációt alkalmaz. A std::function lehetővé teszi, hogy bármilyen hívható entitást (lambda, függvény, funktor) regisztráljunk observerként, anélkül hogy közös absztrakt osztályt kellene származtatni.

#include <functional>
#include <vector>
#include <string>
#include <algorithm>
#include <iostream>

class EventSource {
public:
    using Callback = std::function<void(const std::string&)>;

private:
    std::vector<Callback> callbacks_;

public:
    // Visszaad egy azonosítót, amivel le lehet iratkozni.
    [[nodiscard]] std::size_t subscribe(Callback cb) {
        callbacks_.push_back(std::move(cb));
        return callbacks_.size() - 1;
    }

    void unsubscribe(std::size_t id) {
        if (id < callbacks_.size()) {
            callbacks_[id] = nullptr; // helyben invalidálás
        }
    }

    void notify(const std::string& event) {
        // Másolat, hogy a notify közbeni módosítások ne okozzanak UB-t.
        auto snapshot = callbacks_;
        for (const auto& cb : snapshot) {
            if (cb) {
                cb(event);
            }
        }
    }
};

Ebben a példában a subscribe egy indexet ad vissza, amellyel később le lehet iratkozni. A notify egy másolaton iterál, így ha egy callback módosítja a callbacks_ vektort, az nem befolyásolja az aktuális iterációt. A leiratkozás nullptr-re állítással történik, ami egyszerű, de a “lyukak” fokozatosan halmozódnak; komolyabb rendszerekben érdemes törölni a vektorból (pl. swap-and-pop vagy std::erase a notify végén).

A konkurencia kezelésére a legegyszerűbb megoldás egy std::mutex és std::lock_guard használata a subscribe, unsubscribe és notify elején. Komolyabb, nagy teljesítményű eseményrendszerekben (pl. lock-free callback listák) a megoldás bonyolultabb, de ez a fejezet keretein túlmutat.

27.2.8 Observer és reentrancy

Fontos kihívás a reentrancy (újra belépés): ha egy callback a notify futása közben újra meghívja ugyanazon EventSource notify metódusát, az végtelen rekurzióhoz vagy inkonzisztens állapothoz vezethet. A másolaton való iteráció segít, de ha a callback új notify-t indít, akkor az új hívás a callbacks_ aktuális állapotát látja. Ez lehet kívánatos vagy sem, de tudni kell róla. Egy lehetséges védekezés egy bool notifying_ flag bevezetése, amely megakadályozza a rekurzív notify hívásokat.

27.2.9 Alternatív megoldások

  • std::ranges és view-k: nem közvetlenül observer, de eseményfolyamoknál használhatók.
  • Boost.Signals2: jól bevált, szálbiztos observer implementáció, amely kezeli a leiratkozást, a prioritásokat és a slot-élettartamot.
  • Saját signal-slot mechanizmus: a fenti callback-listás megoldás továbbfejlesztése.

27.2.10 Visitor minta

27.2.11 A minta célja és hagyományos megvalósítása

A Visitor minta kettős dispatching-et valósít meg: lehetővé teszi, hogy egy objektumstruktúra elemein új műveleteket hajtsunk végre anélkül, hogy magukat az elemeket módosítanánk. A klasszikus megoldásban minden elem rendelkezik egy accept(Visitor&) metódussal, amely visszahívja a látogató megfelelő visit túlterhelését.

#include <iostream>
#include <memory>
#include <vector>

// Előre deklarációk
class Circle;
class Rectangle;

class ShapeVisitor {
public:
    virtual ~ShapeVisitor() = default;
    virtual void visit(Circle& c) = 0;
    virtual void visit(Rectangle& r) = 0;
};

class Shape {
public:
    virtual ~Shape() = default;
    virtual void accept(ShapeVisitor& v) = 0;
};

class Circle : public Shape {
public:
    double radius;
    explicit Circle(double r) : radius(r) {}
    void accept(ShapeVisitor& v) override { v.visit(*this); }
};

class Rectangle : public Shape {
public:
    double width, height;
    Rectangle(double w, double h) : width(w), height(h) {}
    void accept(ShapeVisitor& v) override { v.visit(*this); }
};

class AreaVisitor : public ShapeVisitor {
public:
    double totalArea = 0.0;
    void visit(Circle& c) override {
        totalArea += 3.14159 * c.radius * c.radius;
    }
    void visit(Rectangle& r) override {
        totalArea += r.width * r.height;
    }
};

int main() {
    std::vector<std::unique_ptr<Shape>> shapes;
    shapes.push_back(std::make_unique<Circle>(2.0));
    shapes.push_back(std::make_unique<Rectangle>(3.0, 4.0));

    AreaVisitor areaVisitor;
    for (auto& s : shapes) {
        s->accept(areaVisitor);
    }
    std::cout << "Total area: " << areaVisitor.totalArea << '\n';
}

Ez a megoldás nyitott a műveletekre (új ShapeVisitor osztály hozzáadásával új művelet adható), de zárt a típusokra (új Shape származtatott osztály hozzáadása az összes létező visitor módosítását igényli). A kettős dispatch a v.visit(*this) hívásban valósul meg: a statikus típus itt Circle& vagy Rectangle&, így a megfelelő túlterhelés hívódik.

27.2.12 Modern C++ alternatíva: std::variant + std::visit

Ha a típushalmaz zárt és a cél a gyors, értékalapú polimorfizmus, akkor a std::variant és a std::visit sokkal kifejezőbb és hatékonyabb megoldást kínál:

#include <variant>
#include <vector>
#include <iostream>
#include <numbers>
#include <algorithm>

struct Circle { double radius; };
struct Rectangle { double width, height; };

using Shape = std::variant<Circle, Rectangle>;

double area(const Shape& s) {
    return std::visit([](const auto& shape) -> double {
        using T = std::decay_t<decltype(shape)>;
        if constexpr (std::is_same_v<T, Circle>) {
            return std::numbers::pi * shape.radius * shape.radius;
        } else if constexpr (std::is_same_v<T, Rectangle>) {
            return shape.width * shape.height;
        }
    }, s);
}

int main() {
    std::vector<Shape> shapes;
    shapes.emplace_back(Circle{2.0});
    shapes.emplace_back(Rectangle{3.0, 4.0});

    double total = 0.0;
    for (const auto& s : shapes) {
        total += area(s);
    }
    std::cout << "Total area: " << total << '\n';
}

Ez a megoldás értékalapú: nincs dinamikus memóriafoglalás a polimorfizmus miatt, és a std::visit generált kódja gyakran közvetlen függvényhívásokat használ, nem vtable-t. A hátránya, hogy a Shape típus zárt, új típus hozzáadása a variant definícióját módosítja, és minden std::visit hívást frissíteni kell (bár a fordító segít a kihagyott típusokkal).

27.2.13 Mikor melyiket válasszuk?

  • Klasszikus visitor: ha a típushalmaz bővülése ritka, de új műveletek gyakoriak, és a hierarchia szükséges (pl. open set of derived classes). Ezt a megoldást érdemes választani akkor is, ha a típusok nem ismertek előre, vagy ha a hierarchia része más absztrakciók.
  • std::variant + std::visit: ha a típushalmaz zárt, és a cél a minimalista, gyors, értékalapú megoldás. Különösen alkalmas beágyazott rendszerekben, játékokban, pénzügyi alkalmazásokban, ahol a heap allokáció és a virtual call overhead kerülendő.

A kettő kombinálható is: pl. egy variant tárolhat típusokat, majd a std::visit egy klasszikus visitor interfészt hív meg.

27.2.14 Type erasure és variant a viselkedési mintákban

A fenti példákban láthattuk, hogy a modern C++ két fontos eszköze – a type erasure és a variant – hogyan támogatja a viselkedési mintákat.

  • Type erasure (pl. std::function, std::any, std::function_ref C++26-ban) lehetővé teszi, hogy különböző típusú, de azonos hívható interfésszel rendelkező entitásokat egységesen kezeljünk. Ez ideális a Strategy és az Observer mintákban, ahol a konkrét algoritmus vagy callback típusa nem ismert a kontextus számára. A type erasure ára egy indirekciós szint és esetleg dinamikus memóriafoglalás.

  • std::variant: zárt típushalmazt kezel értékalapúan, és a std::visit segítségével műveleteket hajthatunk végre rajtuk. Ez a Visitor minta természetes megvalósítása, mivel a variant típusai az elemek, a std::visit látogatói pedig a műveletek. A variant előnye a vtable nélküli polimorfizmus és a cache-barát tárolás.

A két eszköz gyakran kiegészíti egymást. Például egy Strategy esetében, ha a stratégiák halmaza zárt, a variant jobb teljesítményt ad; ha nyitott, a type erasure (std::function) a rugalmasabb. A választásnál figyelembe kell venni a típusok bővíthetőségét, a fordítási időt és a teljesítményigényt.

27.2.15 Labor: Strategy, Observer és Visitor példa reprodukálható buildben

A labor célja, hogy a fenti három mintát egy kis, fordítható és tesztelhető projektben implementáld. A projektnek tartalmaznia kell egy-egy egyszerű példát mindhárom mintára, és legalább néhány automatikus tesztet.

27.2.16 Követelmények

  • Fordító és standard: válassz egyet a háromból (például GCC 13.2, Clang 17, MSVC 19.38), és használd a C++20 szabványt (-std=c++20 vagy /std:c++20).
  • Build rendszer: használj CMake-et (legalább 3.20), vagy írj egy egyszerű Makefile-t / build parancsot.
  • Kapcsolók: engedélyezd a figyelmeztetéseket: -Wall -Wextra -Wpedantic -Werror (MSVC esetén /W4 /WX). Futtasd a teszteket AddressSanitizer (-fsanitize=address,undefined) alatt is.
  • Tesztelés: legyen legalább 5 teszteset, amelyek ellenőrzik a minták működését. Használhatsz egyszerű assert-eket vagy egy lightweight teszt keretrendszert (például Catch2, doctest). A tesztfutásnak egyértelműen jelentenie kell a sikert/sikertelenséget.
  • Mérési napló: rögzítsd a következő adatokat:
    • Fordítási idő (time paranccsal vagy CMake build idővel).
    • A létrejött bináris méretét (size vagy ls -l).
    • A tesztek futási idejét (time paranccsal).
    • A használt fordító pontos verzióját (g++ --version, clang++ --version, cl).
    • Az optimalizációs szintet (pl. -O2).
    • A várt eredményeket a mért értékekkel összehasonlítva: a szövegben különítsd el, mit vártál, és mit mértél.

27.2.17 Minta implementációk

27.2.17.1 Strategy labor

Hozz létre egy Strategy példát, amely számítási műveleteket végez el. Például egy DiscountCalculator kontextus, amely különböző kedvezménystratégiákat (pl. nincs kedvezmény, százalékos, fix összegű) tud alkalmazni. Használj std::function-t a stratégia tárolására. Teszteld mindhárom stratégiát.

27.2.17.2 Observer labor

Készíts egy egyszerű eseményforrást (EventSource), amely std::function<void(int)> callbackeket fogad. Regisztrálj két vagy három callbacket, értesítsd őket, majd iratkozz le az egyikről, és ellenőrizd, hogy nem kap több értesítést. Figyelj a notify közbeni módosításra: teszteld, hogy ha egy callback leiratkozik a notify alatt, nem történik UB.

27.2.17.3 Visitor labor

Implementálj egy kis kifejezésfa-kiértékelőt. Definiálj Expr variantot, amely lehet Constant, Add, Multiply (rekurzív módon). Használj std::visit-et egy evaluate függvényben, amely kiszámolja a kifejezés értékét. Teszteld néhány bemenettel, és hasonlítsd össze a várt kimenettel.

Teszt futási idő (várt: <0.1s, mért: 0.04s)
Tesztek eredménye: 5/5 sikeres
Sanitizer futás: tiszta, nincs hiba

A fenti labor elvégzése során a hallgató gyakorlati tapasztalatot szerez a három minta modern C++-os megvalósításában, és megtanulja a reprodukálható build és tesztelés fontosságát.

27.2.20 Gyakori hibák és elkerülésük

27.2.21 Strategy

  • Túlzott absztrakció: minden stratégiához külön absztrakt osztályt létrehozni gyakran felesleges, ha a stratégia egyetlen függvény. Használj std::function-t vagy sablonparamétert, hacsak nincs nyomós ok az öröklésre.
  • Élettartam: ha a Context nyers pointert tárol a stratégiára, gondoskodni kell arról, hogy a stratégia tovább éljen, mint a Context. std::unique_ptr vagy std::function (ami másolja a callable-t) megoldja.
  • Teljesítmény: ha a stratégia hot path-ban van, kerüld az std::function indirekcióját, ha a típus fordítási időben ismert.

27.2.22 Observer

  • Dangling pointer: ha az observer megsemmisül, de a subject még hivatkozik rá. Használj std::weak_ptr-t a callback helyett, vagy leiratkozási mechanizmust. A callback-listás megoldásnál a lambda élettartamát a regisztráló félnek kell biztosítania.
  • Reentrancy: notify közbeni módosítások. Iterálj másolaton, és dokumentáld a viselkedést.
  • Kivétel: ha egy observer kivételt dob, döntsd el, hogy megszakítja-e az értesítést (try-catch a notity-ban), vagy a kivételt továbbengeded.
  • Konkurencia: szálbiztosságot explicit módon kell kezelni; a std::mutex alap megoldás elegendő lehet.

27.2.23 Visitor

  • Kettős dispatch hiánya: ha a accept metódusban typeid-et vagy dynamic_cast-ot használsz, az nem igazi visitor, és a bővíthetőség sérül. Mindig a v.visit(*this) mintát kövesd.
  • Körkörös include: a klasszikus visitor implementációjában gyakori a körkörös függőség. Használj előre deklarációt.
  • Új típus hozzáadása: emlékezz, hogy új típus esetén minden visitor-t frissíteni kell. Ha ez gyakori, fontold meg a variant alapú megoldást.

27.2.24 Type erasure és variant

  • std::function small buffer optimization: ne feltételezd, hogy az std::function nem foglal heap-et; ha nagy a callable, akkor foglal. Ha elengedhetetlen a heap elkerülése, használj std::function_ref-et (C++26) vagy saját type erasure-t.
  • Variant méret: a variant mérete a legnagyobb elem méretéhez igazodik; ha egy elem nagy, az összes példány nagy lesz. Gondold át a típusok kialakítását.
  • std::visit túlterhelés: ha a std::visit túl sok típust kezel, a generált kód nagy lehet, és a fordítási idő megnőhet.

27.2.25 Önellenőrző kérdések

  1. Adott egy stratégiai mintát igénylő rendszer, ahol a stratégiák halmaza nyitott, és a futásidejű cserélhetőség követelmény. Melyik C++ eszközt választanád, és miért? Hasonlítsd össze az std::function és az absztrakt interfész alapú megoldást a teljesítmény és a karbantarthatóság szempontjából.

  2. Egy objektumstruktúrában gyakran adunk hozzá új műveleteket, de a típushalmaz zárt és ritkán változik. Melyik visitor-megvalósítás a megfelelőbb: klasszikus visitor vagy std::variant + std::visit? Indokold a választ, és térj ki a fordítási időre és a futási teljesítményre is!

  3. Hogyan kerülnéd el a dangling pointer problémát egy callback-alapú observer megvalósításban? Mutass be legalább két különböző megoldást, és értékeld azok előnyeit és hátrányait!
