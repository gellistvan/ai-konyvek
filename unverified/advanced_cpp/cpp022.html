7.1 SFINAE és enable_if

A sablon-metaprogramozás egyik legnagyobb erejű, de gyakran félreértett eszköze a SFINAE (Substitution Failure Is Not An Error). Ebben az alfejezetben a helyettesítési hiba fogalmát, a feltételes túlterhelést, valamint a std::enable_if és a void_t használatát járjuk körül. A cél, hogy ne csak másolni tudd a szokásos mintákat, hanem pontosan értsd, mi történik a fordítóban, és hogyan kerülheted el a tipikus csapdákat.

7.1.1 Helyettesítési hiba és a túlterhelési halmaz

Amikor egy függvénysablont meghívsz, a fordító a sablonparaméterek dedukciója után helyettesíti a konkrét típusokat a sablon paramétereibe. Ha a helyettesítés sikeres, a függvény jelöltként bekerül a túlterhelési halmazba. Ha a helyettesítés hibát okoz, az alapértelmezés szerint fordítási hibának számítana. A SFINAE szabály azonban azt mondja ki: ha a hiba közvetlenül a helyettesítés során, a függvény deklarációjának immediate context-ében keletkezik, akkor nem fordítási hiba, hanem egyszerűen kikerül a jelölt a túlterhelési halmazból. A többi jelölt továbbra is versenyben marad.

Ez a mechanizmus lehetővé teszi, hogy a típus tulajdonságaitól függően különböző függvényváltozatokat engedélyezzünk vagy tiltsunk le anélkül, hogy futásidőben bármit is ellenőriznénk. A feltételes túlterhelés pontosan ezt használja ki: a sablonparaméterekből képzett feltétel alapján dől el, hogy egy adott túlterhelés jelölt-e.

Nézzünk egy egyszerű példát:

#include <iostream>
#include <type_traits>

template<typename T>
typename std::enable_if<std::is_integral_v<T>, void>::type
print(T value) {
    std::cout << "integral: " << value << '\n';
}

template<typename T>
typename std::enable_if<std::is_floating_point_v<T>, void>::type
print(T value) {
    std::cout << "floating: " << value << '\n';
}

int main() {
    print(42);        // integral
    print(3.14);      // floating
    // print("hello"); // fordítási hiba: nincs megfelelő overload
}

Itt a std::enable_if a visszatérési típusban található. Az enable_if<cond, T>::type akkor létezik, ha cond igaz; ha hamis, a type nincs definiálva, így a helyettesítés meghiúsul, és a jelölt kiesik. A std::is_integral_v<T> és std::is_floating_point_v<T> a <type_traits>-ből származó segédfeltételek. A void típus a visszatérési érték, mivel a függvény valójában nem ad vissza semmit (a void a std::enable_if második paraméterének alapértelmezett értéke).

A fenti példában a két túlterhelés kölcsönösen kizárja egymást: minden T-re legfeljebb az egyik enable_if feltétele igaz, így nincs kétértelműség. Ha egyszerre mindkettő igaz lenne (például egy char esetén, amely lehet integrál is, de nem lebegőpontos), akkor a túlterhelési szabályok döntenének, vagy kétértelműséget kapnánk.

7.1.2 A “substitution failure” pontos hatóköre

Fontos megérteni, hogy a SFINAE csak az immediate context-ben fellépő hibákra vonatkozik. Ez gyakorlatilag a függvény deklarációjának fejrészét jelenti: a sablonparaméterek, a visszatérési típus, a paramétertípusok, valamint a template paraméterekre vonatkozó kifejezések. Ha a hiba a függvény törzsében, vagy egy mélyebben beágyazott típusdefinícióban (például egy osztálysablon belsejében) keletkezik, az már nem számít SFINAE-nak, hanem hard error.

Példa arra, amikor a hiba nem SFINAE:

template<typename T>
void f() {
    typename T::nonexistent x; // hiba a függvénytörzsben
}

Itt a T::nonexistent hiánya a függvény törzsében derül ki, amikor a sablont példányosítjuk. Ez már nem a helyettesítés során, hanem a példányosításkor jelentkezik, és fordítási hibához vezet. A SFINAE csak a deklarációban lévő kifejezésekre vonatkozik, ezért a feltételeket mindig oda kell tenni.

Hasonlóképpen, ha egy feltétel nem függ a sablonparamétertől (non-dependent), a hiba már a sablon definíciójakor jelentkezik, nem a helyettesítéskor. Például:

template<typename T>
typename std::enable_if<false, void>::type
g() { }

Ez a kód önmagában is fordítási hibát ad, mert a false feltétel miatt a type nem létezik, és ez a sablon definíciójakor derül ki, nem a meghívásakor. A feltételnek mindig a sablonparamétertől kell függnie ahhoz, hogy a SFINAE működjön.

7.1.3 std::enable_if használati formái

A std::enable_if többféleképpen beilleszthető a függvénysablonba:

  1. Visszatérési típusként – ahogy a fenti példában láttuk. Hátránya, hogy a visszatérési típus bonyolult lehet, és nehéz olvasni, ha a feltétel hosszú.

  2. Template paraméterként – egy alapértelmezett, nem típus template paraméterrel:

template<typename T, typename std::enable_if<std::is_integral_v<T>, int>::type = 0>
void print(T value) { ... }

Ez a forma akkor hasznos, ha több túlterhelést szeretnénk, és el akarjuk kerülni a visszatérési típus zsúfoltságát. A nem típus paraméter alapértelmezett értéke 0, a típus pedig int (vagy bármilyen más típus), ha a feltétel igaz. Ha a feltétel hamis, a type hiányzik, így a sablon érvénytelen, és a jelölt kiesik.

  1. Függvényparaméterként:
template<typename T>
void print(T value, typename std::enable_if<std::is_integral_v<T>, int>::type* = nullptr) { ... }

Itt a második paraméter típusa int*, és az alapértelmezett érték nullptr. Ha a feltétel hamis, a típus nem létezik. Ez a forma néha jobban olvasható, de a hívás helyén a második argumentumot nem adjuk meg, így csak a default értékkel működik.

Mindhárom forma egyenértékű a SFINAE szempontjából. A választás ízlés és kódolási stílus kérdése, de a visszatérési típusos változat a leggyakoribb a régebbi kódokban, míg a template paraméteres változat modern, C++17-ben bevezetett std::enable_if_t-vel rövidebb.

A C++14 óta elérhető a std::enable_if_t<cond, T> alias, ami typename std::enable_if<cond, T>::type helyett használható. A fenti példa így rövidebb:

template<typename T>
std::enable_if_t<std::is_integral_v<T>, void> print(T value) { ... }

7.1.4 void_t és a detekciós minta

A SFINAE másik fontos építőköve a void_t. Ezt a C++17-ben a szabvány nem definiálja, de a std::void_t C++17 óta elérhető a <type_traits> fejlécben. A definíciója rendkívül egyszerű:

template<typename...>
using void_t = void;

Ez az alias bármilyen típuslistát void-ra alakít. A kulcsfontossága abban rejlik, hogy ha a típuslistában olyan kifejezés szerepel, amely érvénytelen, a helyettesítés meghiúsul. Ezt kihasználva detektálhatjuk, hogy egy típus rendelkezik-e egy bizonyos taggal vagy kifejezéssel.

Példa: detektáljuk, hogy egy típusnak van-e value_type tagtípusa:

#include <type_traits>
#include <vector>

template<typename T, typename = void>
struct has_value_type : std::false_type {};

template<typename T>
struct has_value_type<T, std::void_t<typename T::value_type>> : std::true_type {};

static_assert(has_value_type<std::vector<int>>::value);
static_assert(!has_value_type<int>::value);

Magyarázat: az elsődleges sablonnak van egy második, alapértelmezett void típusú template paramétere, és std::false_type-ból származik. A speciális változat akkor illeszkedik, ha a második template argumentum std::void_t<typename T::value_type> kifejezés érvényes, azaz T-nek van value_type tagtípusa. Ekkor a speciális változat std::true_type-ból származik. Ha nincs ilyen tag, a std::void_t helyettesítése meghiúsul, ezért a speciális változat nem jön létre, és az elsődleges sablon marad érvényben.

Ez a minta nagyon hasonló a detection idiom-hoz, amelyet a következő alfejezetben részletesebben tárgyalunk, de a void_t alapvető eszköze annak.

7.1.5 Gyakorlati minta: feltételes túlterhelés tagfüggvényeknél

A SFINAE nem csak szabad függvényeknél, hanem osztálysablonok tagfüggvényeinél is használható. Például egy konténerosztály get() metódusát csak akkor szeretnénk engedélyezni, ha a tárolt típus másolható; egy move() metódust, ha mozgatható. Egy lehetséges megoldás:

#include <type_traits>
#include <utility>

template<typename T>
class wrapper {
    T value;
public:
    template<typename U = T>
    std::enable_if_t<std::is_copy_constructible_v<U>, U>
    get_copy() const {
        return value;
    }

    template<typename U = T>
    std::enable_if_t<std::is_move_constructible_v<U>, U>
    get_move() {
        return std::move(value);
    }
};

Itt a tagfüggvények sablonok, és a U alapértelmezett típusa T. A std::enable_if_t a visszatérési típusban van. Ha T nem másolható, a get_copy sablon helyettesítése meghiúsul, így az a tagfüggvény nem létezik az adott példányosításban. Fontos, hogy a tagfüggvény sablon legyen, különben a feltétel nem függne a sablonparamétertől, és a hibát már az osztály definíciójakor észlelné a fordító.

Egy másik gyakori eset, amikor egy osztály konstruktorát szeretnénk csak bizonyos típusokra engedélyezni. Például egy any-szerű osztály konstruktora csak akkor legyen elérhető, ha a típus másolható:

template<typename T>
class any_like {
public:
    template<typename U, typename = std::enable_if_t<std::is_copy_constructible_v<U>>>
    any_like(U&& value) { ... }
};

Itt a második template paraméter alapértelmezett értéke a std::enable_if_t kifejezés, ami void-ot ad, ha a feltétel igaz. Ha a feltétel hamis, a konstruktor sablon nem illeszkedik, így nem lehet azt a típust használni.

7.1.6 Tipikus hibák és elkerülésük

7.1.7 1. A feltétel nem a sablonparamétertől függ

Ahogy fentebb említettük, a std::enable_if<false, ...> típusú kifejezések fordítási hibát okoznak a sablon definíciójakor, mert a feltétel nem függ a sablonparaméterektől. Mindig győződj meg arról, hogy a feltétel tartalmazza legalább az egyik sablonparamétert (közvetlenül vagy decltype-pal, sizeof-pal stb.).

7.1.8 2. A hiba a függvénytörzsben keletkezik

A SFINAE nem működik a függvénytörzsben lévő kifejezésekre. Ha például egy függvény a törzsében hív meg egy nem létező tagfüggvényt, az hiba lesz a példányosításkor, nem SFINAE. A feltételeket mindig a deklarációban kell elhelyezni, a típusokban vagy a template paraméterekben.

7.1.9 3. Kétértelműség a túlterhelések között

Ha két túlterhelés feltétele egyszerre igaz, a fordító túlterhelési szabályai döntenek. Ha a két függvény szignatúrája azonos (kivéve a visszatérési típust, ami nem vesz részt a túlterhelés feloldásában), akkor kétértelműség lép fel. Például:

template<typename T>
std::enable_if_t<std::is_integral_v<T>, void> f(T) {}

template<typename T>
std::enable_if_t<!std::is_integral_v<T>, void> f(T) {}

Ez a két túlterhelés együttesen lefedi az összes típust, de minden T-re pontosan az egyik lesz érvényes, így nincs kétértelműség. Azonban ha a feltételek átfednek, például std::is_arithmetic_v<T> és std::is_integral_v<T>, akkor egy int esetén mindkettő igaz, és a fordító nem tud dönteni (kivéve, ha az egyik jobban illeszkedik a paraméterekre, ami itt nem áll fenn). Ilyenkor vagy pontosítani kell a feltételeket, vagy további túlterhelési szabályokat kell alkalmazni.

7.1.10 4. A std::enable_if rossz elhelyezése

Gyakori hiba, hogy a std::enable_if-et nem a függvénysablonban, hanem egy osztálysablon paraméterében próbálják használni, ahol nincs túlterhelés, így a SFINAE nem érvényesül. Például:

template<typename T, typename = std::enable_if_t<std::is_integral_v<T>>>
class MyClass { ... };

Itt ha a feltétel hamis, a sablon második paramétere érvénytelen, ami fordítási hibát okoz, nem pedig a túlterhelési halmazból való kiesést. Ez a minta nem SFINAE, hanem egyszerűen hibás sablondefiníció. A helyes megoldás ilyenkor a részleges specializáció vagy a tagfüggvények SFINAE-ja.

7.1.11 5. A void_t detekciónál a vártnál szélesebb illeszkedés

A void_t-s detekciónál ügyelni kell arra, hogy a kifejezés pontosan azt vizsgálja, amit szeretnénk. Például ha egy size() tagfüggvény meglétét akarjuk detektálni, a std::void_t<decltype(std::declval<T>().size())> kifejezés akkor is érvényes lehet, ha a size() visszatérési típusa bármi, nem feltétlenül size_t. Ha a visszatérési típust is szeretnénk ellenőrizni, azt is bele kell foglalni a kifejezésbe, például std::void_t<decltype(std::declval<T>().size()), typename std::enable_if<std::is_same_v<decltype(std::declval<T>().size()), std::size_t>>::type>.

7.1.12 Labor: SFINAE-alapú függvényimplementálás

Ebben a laborban egy olyan függvényt implementálunk, amely a típus tulajdonságai alapján választ a különböző kiíratási formátumok között. A függvény neve format_value, és a következő viselkedést várjuk el:

  • Ha a típus integrál, a kimenet legyen "integer: " előtaggal és a szám decimális alakjával.
  • Ha a típus lebegőpontos, a kimenet legyen "floating: " előtaggal és a szám tizedesvesszővel, fixpontos formátumban, 2 tizedesjeggyel.
  • Ha a típus std::string, a kimenet legyen "string: " előtaggal és idézőjelek között.
  • Egyéb típusra fordítási hibát kell kapnunk (nincs megfelelő túlterhelés).

A függvény visszatérési értéke legyen std::string. Használj SFINAE-t (std::enable_if_t) a túlterhelések feltételes engedélyezéséhez. A laborhoz tartozik egy tesztprogram, amely a fenti három esetet ellenőrzi, valamint egy negatív teszt, amely egy nem támogatott típusra hívja a függvényt – ennek fordítási hibát kell okoznia.

Build parancs (példa GCC-vel):

g++ -std=c++20 -Wall -Wextra -pedantic -Werror -O2 lab.cpp -o lab

Fordítói verzió: GCC 13.2 (vagy újabb), standard: C++20 (a std::enable_if_t C++14, a std::is_integral_v C++17, így a C++17 is elegendő lenne, de a labor C++20-at használ).

Tesztesetek:

#include <cassert>
#include <string>
#include <type_traits>
#include <sstream>

// format_value implementációk...

int main() {
    assert(format_value(42) == "integer: 42");
    assert(format_value(3.14159) == "floating: 3.14");
    assert(format_value(std::string("hello")) == "string: \"hello\"");
    // static_assert(!std::is_invocable_v<decltype(format_value<int>), int>); // nem szükséges, de ellenőrizhető
}

A tesztprogram lefuttatása után a kimenetnek üresnek kell lennie (nincs hiba), és a visszatérési értékeknek meg kell felelniük a várt értékeknek.

Mérési napló: a labor részeként rögzíteni kell a fordítási időt (például time g++ ...), a generált bináris méretét (size lab), és a tesztprogram futási idejét. A mért és a várt eredményt külön kell feltüntetni: a várt eredmény a fenti assert-ek teljesülése, a mért pedig a tényleges futási kimenet és a futási idő. A mérési naplóban dokumentáljuk a használt operációs rendszert, a hardvert, a fordító verzióját és a standardverziót.

Megoldási vázlat (a labor elvégzéséhez használható, de a részletes implementációt az olvasóra bízzuk):

template<typename T>
std::enable_if_t<std::is_integral_v<T>, std::string>
format_value(T value) {
    return "integer: " + std::to_string(value);
}

template<typename T>
std::enable_if_t<std::is_floating_point_v<T>, std::string>
format_value(T value) {
    std::ostringstream oss;
    oss << "floating: " << std::fixed << std::setprecision(2) << value;
    return oss.str();
}

template<typename T>
std::enable_if_t<std::is_same_v<std::decay_t<T>, std::string>, std::string>
format_value(T&& value) {
    return "string: \"" + value + "\"";
}

A harmadik túlterhelésnél std::decay_t-t használunk, hogy a const char*-hez hasonló típusok ne illeszkedjenek, csak a std::string. Ha a hívás format_value("hello") lenne, az nem illeszkedne, mert a feltétel hamis, és így fordítási hibát kapnánk, ami a kívánt viselkedés.

  2. Az alábbi kódban a fejlesztő egy print függvényt szeretne csak integrál típusokra engedélyezni std::enable_if-fel. Mi a hiba, és hogyan javítanád?

    template<typename T>
void print(T value) {
    typename std::enable_if<std::is_integral<T>::value, void>::type dummy;
    // ...
}

  3. Miért van szükség a typename kulcsszóra a std::enable_if<...>::type kifejezésben? Mi történik, ha elhagyjuk?
