32.2 Implementáció és optimalizálás

A záróprojekt (32.1) során rögzítettük a rendszer követelményeit és architektúráját. Most a tervből működő, mérhető implementációt készítünk. A fejezetben egy egyszerű, de valósághű adatfeldolgozó csővezetéket valósítunk meg, és bemutatjuk az optimalizálás ciklusát: mérés – elemzés – átalakítás – ismételt mérés. A hangsúly a modern C++ eszközök tudatos használatán és a reprodukálható mérési módszertanon van, nem pedig a trükkös kódrészleteken.

32.2.1 Az architektúra leképezése kódba

A tervezett rendszer fő komponensei: bemeneti olvasó, szűrő, transzformáló, aggregáló és kimeneti író. Ezeket a komponenseket önálló, tesztelhető egységekként valósítjuk meg, és egy Pipeline osztály köti össze őket. Az interfészeket C++20 concept-ekkel írjuk le, így a fordító már fordítási időben ellenőrzi a komponensek kompatibilitását. A komponensek sablonparaméterek, hogy a feldolgozó típusok cserélhetők legyenek anélkül, hogy a Pipeline forráskódját módosítanánk.

Kezdjük a rekord definíciójával. A SensorRecord a 32.1-ben bevezetett mt::Sample implementációs megfelelője: a timestamp a timestamp_us mezőnek, a sensor_id és a value pedig a Sample azonos nevű mezőinek felel meg. A laborban használt rövidebb név csak a példa olvashatóságát szolgálja.

// Egy bemeneti szenzoradat (a 32.1 MiniTelemetry mt::Sample rekordja)
struct SensorRecord {
    std::uint64_t timestamp;
    double value;
    std::uint32_t sensor_id;
};

A rekord triviálisan másolható és mozgatható, ami megkönnyíti az érték szerinti átadást a feldolgozási láncban.

Most definiáljuk a komponensek interfészeit concept-ekkel:

template<typename Reader>
concept Reader = requires(Reader r) {
    { r.next() } -> std::convertible_to<std::optional<SensorRecord>>;
};

A Reader concept előírja, hogy a next() tagfüggvény std::optional<SensorRecord>-ot adjon vissza, amely a bemenet végét std::nullopt-tal jelzi.

template<typename Filter>
concept Filter = requires(Filter f, const SensorRecord& rec) {
    { f(rec) } -> std::convertible_to<bool>;
};

template<typename Transform>
concept Transform = requires(Transform t, const SensorRecord& rec) {
    { t(rec) } -> std::convertible_to<SensorRecord>;
};

template<typename Aggregator>
concept Aggregator = requires(Aggregator a, const SensorRecord& rec) {
    { a.add(rec) } -> std::same_as<void>;
    { a.result() } -> std::same_as<double>;
};

Ezek a concept-ek nemcsak dokumentálják a komponensek elvárt működését, hanem fordítási időben megakadályozzák a nem kompatibilis típusok használatát. A hibaüzenetek így sokkal olvashatóbbak, mint a hagyományos sablonhibák.

A Pipeline osztály:

template<Reader READER, Filter FILTER, Transform TRANSFORM, Aggregator AGG>
class Pipeline {
public:
    Pipeline(READER reader, FILTER filter, TRANSFORM transform, AGG agg)
        : reader_(std::move(reader)),
          filter_(std::move(filter)),
          transform_(std::move(transform)),
          agg_(std::move(agg))
    {}

    double run() {
        while (auto rec = reader_.next()) {
            if (filter_(*rec)) {
                agg_.add(transform_(*rec));
            }
        }
        return agg_.result();
    }

private:
    READER reader_;
    FILTER filter_;
    TRANSFORM transform_;
    AGG agg_;
};

A konstruktor paraméterként veszi át a komponenseket, és std::move-tal továbbítja azokat a tagváltozókba. Ez lehetővé teszi, hogy a komponensek hatékonyan mozgathatók legyenek, és a Pipeline birtokolja az erőforrásaikat (RAII). A run() tagfüggvény szekvenciálisan dolgozza fel a rekordokat: beolvas, szűr, transzformál, aggregál. A ciklus mindaddig fut, amíg az olvasó std::nullopt-ot nem ad vissza.

A konkrét komponensek:

class FileReader {
public:
    explicit FileReader(std::istream& input) : input_(input) {}
    std::optional<SensorRecord> next() {
        SensorRecord rec;
        if (!(input_ >> rec.timestamp >> rec.value >> rec.sensor_id)) {
            return std::nullopt;
        }
        return rec;
    }
private:
    std::istream& input_;
};

class PositiveFilter {
public:
    bool operator()(const SensorRecord& rec) const noexcept {
        return rec.value > 0.0;
    }
};

class ScaleTransform {
public:
    explicit ScaleTransform(double factor) : factor_(factor) {}
    SensorRecord operator()(const SensorRecord& rec) const noexcept {
        return {rec.timestamp, rec.value * factor_, rec.sensor_id};
    }
private:
    double factor_;
};

class SumAggregator {
public:
    void add(const SensorRecord& rec) noexcept {
        sum_ += rec.value;
    }
    double result() const noexcept {
        return sum_;
    }
private:
    double sum_ = 0.0;
};

Ez a referencia implementáció egyszerű, de működő és tesztelhető. A FileReader a formázott beolvasást (operator>>) használja, ami kényelmes, de számos rejtett költséggel járhat, mint például a std::locale kezelése és a számformátumok feldolgozása. A PositiveFilter és a ScaleTransform noexcept jelöléssel jelzi, hogy nem dobnak kivételt – ez fontos a fordító számára az optimalizáláshoz és a kivételbiztonsági garanciákhoz. A SumAggregator egyszerű összegzést végez.

A Pipeline használata:

#include <sstream>
#include <cassert>

void test_pipeline() {
    std::istringstream input(
        "100 1.5 1\n"
        "200 -0.5 1\n"
        "300 2.0 2\n"
        "400 0.0 2\n"
        "500 3.5 1\n"
    );
    FileReader reader(input);
    PositiveFilter filter;
    ScaleTransform transform(2.0);
    SumAggregator agg;
    Pipeline<FileReader, PositiveFilter, ScaleTransform, SumAggregator> pipeline(
        std::move(reader), std::move(filter), std::move(transform), std::move(agg));
    double result = pipeline.run();
    // Pozitív értékek: 1.5, 2.0, 3.5 -> 2-szeres: 3, 4, 7 -> összeg: 14
    assert(result == 14.0);
}

Ez a teszt ellenőrzi a pipeline helyes működését, és a laborban kiindulópontként szolgál.

32.2.3 Mérés és profilozás: a kiindulópont

Mielőtt bármilyen optimalizálásba kezdenénk, rögzítenünk kell a mérési környezetet. Ez a labor kötelező eleme. A mérési naplónak legalább az alábbi adatokat kell tartalmaznia:

  • Fordító: pl. GCC 13.2.0, Clang 17.0.6, MSVC 19.38. Pontos verzióval; a verziók változhatnak, ezért a laborban ellenőrizni kell.
  • C++ szabvány: C++20 vagy C++23, ahogy a build beállítja.
  • Optimalizáció: -O3 -DNDEBUG (vagy az adott fordító megfelelője).
  • Hardver: CPU modell, memória, operációs rendszer.
  • Input méret: a rekordok száma és a bemenet jellege (pl. 10 000 000 rekord).
  • Futtatások száma: legalább 5, a statisztikai szórás csökkentése érdekében.
  • Mért idő: átlag, medián, szórás.
  • Várt idő: becslés vagy korábbi mérés alapján.

A benchmarkhoz a Google Benchmark könyvtárat használjuk, de bármilyen stabil időmérés megfelel. A könyvtár API-ja változhat, ezért az aktuális verziót a laborban ellenőrizni kell. A benchmark kód:

#include <benchmark/benchmark.h>

static void BM_Pipeline(benchmark::State& state) {
    // Bemeneti adat előkészítése memóriában
    std::stringstream input;
    // ... feltöltés 10 000 000 rekorddal ...
    for (auto _ : state) {
        input.clear();
        input.seekg(0);
        FileReader reader(input);
        PositiveFilter filter;
        ScaleTransform transform(2.0);
        SumAggregator agg;
        Pipeline<FileReader, PositiveFilter, ScaleTransform, SumAggregator> pipeline(
            std::move(reader), std::move(filter), std::move(transform), std::move(agg));
        auto result = pipeline.run();
        benchmark::DoNotOptimize(result);
    }
}
BENCHMARK(BM_Pipeline)->Unit(benchmark::kMillisecond);

A benchmark::DoNotOptimize megakadályozza, hogy a fordító eltávolítsa a számítást, mert a result változót a benchmark keretrendszer „használja”.

A profilozáshoz Linuxon a perf record és a perf report eszközök használhatók, Windows-on a Visual Studio Profiler, macOS-en pedig az Instruments. A profilozás célja, hogy azonosítsuk a tényleges forró pontokat, mielőtt optimalizálnánk. A tipikus eredmény ebben a példában: a FileReader::next() formázott beolvasása viszi el az idő nagy részét, mivel a std::istream és a std::locale réteg nagyon lassú a nyers karakterfeldolgozáshoz képest.

32.2.4 Első optimalizálás: alacsony szintű beolvasás

A profilozás eredménye alapján az első lépés a beolvasás optimalizálása. A std::from_chars (C++17-től egész számokra, C++20-tól lebegőpontos számokra) sokkal gyorsabb, mert nem használ lokált, nem dob kivételt, és közvetlenül a karakterpufferből dolgozik. Cserébe a hibakezelést nekünk kell megvalósítani, és a bemeneti formátumnak szigorúan meghatározottnak kell lennie.

Új olvasó komponens:

class FastFileReader {
public:
    explicit FastFileReader(std::string_view data) : data_(data) {}

    std::optional<SensorRecord> next() {
        if (data_.empty()) return std::nullopt;
        SensorRecord rec{};
        auto [ptr, ec] = std::from_chars(data_.data(), data_.data() + data_.size(), rec.timestamp);
        if (ec != std::errc{}) return std::nullopt;
        ++ptr; // térköz átlépése
        auto [ptr2, ec2] = std::from_chars(ptr, data_.data() + data_.size(), rec.value);
        if (ec2 != std::errc{}) return std::nullopt;
        ++ptr2;
        auto [ptr3, ec3] = std::from_chars(ptr2, data_.data() + data_.size(), rec.sensor_id);
        if (ec3 != std::errc{}) return std::nullopt;
        data_.remove_prefix(ptr3 - data_.data());
        return rec;
    }
private:
    std::string_view data_;
};

Ez a kód a bemenetet std::string_view-ként kapja, ami azt feltételezi, hogy a teljes bemenet a memóriában van. A next() minden hívásnál a std::from_chars segítségével kiolvas három értéket, majd a remove_prefix-szel eltávolítja a feldolgozott részt a nézetből. A hibakezelés egyszerű: ha a konverzió hibát jelez, std::nullopt-ot adunk vissza. Fontos, hogy a ++ptr feltételezi, hogy a számok között pontosan egy szóköz van. A valós bemenetnél robosztusabb parse szükséges, de a laborban a bemenet formátuma rögzített.

A FastFileReader megfelel a Reader concept-nek, így a Pipeline osztály változtatás nélkül használhatja. Ez mutatja a concept-alapú tervezés előnyét: a komponensek cserélhetők, amíg az interfészük illeszkedik.

A benchmarkban a FastFileReader-t használva a beolvasási idő jelentősen csökken. A mérési naplóban ezt dokumentáljuk.

32.2.5 Második optimalizálás: párhuzamos feldolgozás

A rekordok feldolgozása független, így a feldolgozást párhuzamosíthatjuk. Azonban a bemeneti adatfolyam szekvenciális olvasása miatt a párhuzamosítás nem triviális: vagy előbb beolvassuk az összes rekordot egy vektorba, vagy a feldolgozó szálak maguk olvasnak egy közös szinkronizált forrásból. Az egyszerűség kedvéért feltesszük, hogy a bemenet elfér a memóriában, és a rekordokat egy std::vector-ba töltjük.

A párhuzamos összegzés naiv megvalósítása std::atomic<double>-tal:

double parallel_sum_naive(const std::vector<SensorRecord>& records, double scale) {
    std::atomic<double> sum{0.0};
    std::vector<std::jthread> threads;
    std::size_t num_threads = std::thread::hardware_concurrency();
    std::size_t chunk_size = (records.size() + num_threads - 1) / num_threads;
    for (std::size_t i = 0; i < num_threads; ++i) {
        std::size_t begin = i * chunk_size;
        std::size_t end = std::min(begin + chunk_size, records.size());
        threads.emplace_back([&records, begin, end, scale, &sum] {
            double local = 0.0;
            for (std::size_t j = begin; j < end; ++j) {
                const auto& rec = records[j];
                if (rec.value > 0.0) local += rec.value * scale;
            }
            // Atomi összeadás
            auto current = sum.load(std::memory_order_relaxed);
            while (!sum.compare_exchange_weak(current, current + local,
                                              std::memory_order_relaxed,
                                              std::memory_order_relaxed)) {}
        });
    }
    for (auto& t : threads) t.join();
    return sum.load();
}

Ez a kód működik, de a std::atomic<double> gyakori frissítése a szálak versenyéhez vezet, és a compare_exchange_weak ciklus sok iterációt végezhet. Ráadásul a std::atomic<double> nem mindig lock-free, és a platformfüggő viselkedést is figyelembe kell venni.

Helyette jobb minta a per-szál részösszeg, majd a részösszegek egyesítése. Ezzel a párhuzamos szakaszban nincs szükség atomi műveletre, kivéve a végén, ha a részösszegeket egyetlen szál adja össze. A false sharing elkerülése érdekében a részösszegeket cache-line méretre igazított struktúrába helyezzük.

struct alignas(std::hardware_destructive_interference_size) AlignedSum {
    double value = 0.0;
};

double parallel_sum(const std::vector<SensorRecord>& records, double scale) {
    std::size_t num_threads = std::thread::hardware_concurrency();
    std::size_t chunk_size = (records.size() + num_threads - 1) / num_threads;
    std::vector<AlignedSum> partial_sums(num_threads);
    std::vector<std::jthread> threads;

    for (std::size_t i = 0; i < num_threads; ++i) {
        std::size_t begin = i * chunk_size;
        std::size_t end = std::min(begin + chunk_size, records.size());
        threads.emplace_back([&records, begin, end, scale, &partial_sums, i] {
            double local = 0.0;
            for (std::size_t j = begin; j < end; ++j) {
                const auto& rec = records[j];
                if (rec.value > 0.0) local += rec.value * scale;
            }
            partial_sums[i].value = local;
        });
    }
    for (auto& t : threads) t.join();

    double total = 0.0;
    for (const auto& ps : partial_sums) {
        total += ps.value;
    }
    return total;
}

A std::hardware_destructive_interference_size C++17 óta elérhető, de nem minden platformon garantált. Ha a szabványos érték nem elérhető, akkor 64-et használhatunk. A laborban ezt ellenőrizni kell.

Ez a párhuzamos megvalósítás már jól skálázódik, és elkerüli a hamis megosztást (false sharing). A std::jthread automatikusan csatlakozik a destruktorában, így ha kivétel keletkezik, a szálak nem maradnak lógva.

A párhuzamos összegzést integrálhatjuk egy új aggregátorba, vagy a Pipeline::run()-t módosíthatjuk, hogy párhuzamosan dolgozzon. A laborban a hallgató feladata lehet egy ParallelSumAggregator létrehozása, amely a add() hívásokat eltárolja, és a result() hívásakor párhuzamosan összegez.

32.2.6 Tipikus hibák és elkerülésük

A fejezet során felismerhetővé válnak a leggyakoribb hibák, amelyeket a záróprojekt során el kell kerülni:

  1. Túl korai optimalizálás
    Csak profilozás után optimalizáljunk. A referencia implementáció egyszerű, de jól mérhető. Az optimalizálás előtt mindig igazoljuk méréssel, hogy az adott kódrészlet valóban szűk keresztmetszet.

  2. Benchmark hibák
    A mérési környezetet pontosan rögzíteni kell. A benchmarknak megfelelő bemelegítési időt kell adni, és a DoNotOptimize vagy hasonló technikával meg kell akadályozni, hogy a fordító eltávolítsa a mért kódot. A dead code elimination gyakori csapda: ha az eredményt nem használjuk fel, a fordító kihagyhatja a számítást.

  3. False sharing
    Párhuzamos kódban, ha több szál ugyanabba a cache line-ba ír, a teljesítmény drámaian romlik. A per-szál részösszegeket cache-line méretre igazított struktúrába kell helyezni.

  4. Rossz atomics használat
    A std::atomic<double> közvetlen használata párhuzamos összegzésnél hatékonytalan és bonyolult. A per-szál részösszeg minta egyszerűbb és gyorsabb. Ha atomics szükséges, a megfelelő memory_order kiválasztása kritikus; a std::memory_order_relaxed nem mindig elegendő, ha szinkronizációra is szükség van.

  5. A std::from_chars hibakezelésének elhanyagolása
    A std::from_chars nem dob kivételt, hanem hibakódot ad. A hibakód ellenőrzése kötelező; különben a parse csendben rossz adatot adhat, ami nem elfogadható.

  6. Move szemantika helytelen használata
    A Pipeline konstruktorában std::move-tal adjuk át a komponenseket, de a run() metódusban a transform_(*rec) kifejezés lemásolja a rekordot. Ha a rekord nagy lenne, érdemes lenne a transzformálónak rvalue referenciát is támogatnia, de ezt csak akkor tegyük, ha a profilozás indokolja.

  7. A párhuzamos kód determinizmusának elvesztése
    A párhuzamos összegzés során a lebegőpontos összeadás sorrendje megváltozik, ami kismértékű eltérést okozhat a szekvenciális eredményhez képest. Ezt a tesztekben figyelembe kell venni: a várt eredményt toleranciával kell összehasonlítani, vagy a párhuzamos összegzést úgy kell megtervezni, hogy a részek összeadása meghatározott sorrendben történjen.

  8. A std::hardware_destructive_interference_size hordozhatósága
    Bár a szabvány definiálja, nem minden fordító ad értelmes értéket. Ha nem elérhető, konzervatív 64 byte-os igazítást használjunk, és ezt a kódban kommentben jelezzük.

32.2.7 Labor: implementációs és optimalizálási terv

A labor célja, hogy a hallgató a fent bemutatott pipeline-t implementálja, méréseket végezzen, és dokumentálja az optimalizálási lépéseket. Az átadandó eredmény a forráskód, a CMake build, a tesztek, a benchmarkok, a mérési napló és egy rövid elemzés.

Feladatok:

  1. Implementálja a referencia pipeline-t
    Hozza létre a SensorRecord, a FileReader, a PositiveFilter, a ScaleTransform, a SumAggregator és a Pipeline osztályokat a fentiek szerint. Készítsen egységteszteket a komponensekhez és a pipeline-hoz.

  2. Hozzon létre reprodukálható buildet
    Készítsen CMakeLists.txt-t, amely legalább GCC, Clang és MSVC (ahol elérhető) támogatását jelzi. A fordítási kapcsolók: -O3 -DNDEBUG, C++20 szabvány. A build és a tesztek futtatása egyetlen parancsot igényeljen (pl. cmake --build build && ctest --test-dir build). A laborban legalább az egyik fordítóval futtasson.

  3. Állítsa be a benchmark környezetet
    Használja a Google Benchmark könyvtárat (vagy saját időmérést). A benchmark kódot a fentiekhez hasonlóan készítse el. Rögzítse a bemeneti adat előállítását: pl. 10 000 000 rekord generálása determinisztikus módon.

  4. Végezze el a mérést
    Mérje a referencia implementációt legalább 5 futtatással, és jegyezze fel az átlagot, mediánt, szórást. A mérési naplóban adja meg a fordítót, szabványt, optimalizációt, hardvert, input méretet és a futtatások számát.

  5. Profilozás
    Végezzen profilozást (perf, Visual Studio Profiler, Instruments), és azonosítsa a forró pontokat. A laborban elegendő a legfőbb szűk keresztmetszetet leírni.

  6. Optimalizálja a beolvasást
    Implementálja a FastFileReader-t std::from_chars segítségével. Ellenőrizze, hogy a std::from_chars lebegőpontos konverziója elérhető-e az adott fordítóval; ha nem, egész számokra optimalizáljon, vagy használjon alternatív parse-t. Futtassa a teszteket és a benchmarkot, és rögzítse az eredményt.

  7. Párhuzamosítsa a feldolgozást
    Készítsen párhuzamos összegzést per-szál részösszegekkel, cache-line igazítással. Futtassa a teszteket és a benchmarkot. Ügyeljen a determinizmusra és a lebegőpontos eltérésekre.

  8. Hasonlítsa össze a mért és várt eredményeket
    A mérési naplóban külön oszlopban adja meg a várt időt (becslés vagy korábbi mérés alapján). Elemezze az eltéréseket: ha a mért idő jelentősen eltér a várttól, indokolja (pl. gyorsítótár-méret, CPU-terhelés, párhuzamosítási overhead).

  9. Dokumentálja a tanulságokat
