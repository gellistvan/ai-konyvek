21.4 Lock-free és wait-free struktúrák

A lock-free programozás a konkurens rendszerek egyik legnehezebb, de leginkább kifizetődő területe. Célja, hogy a szálak közötti szinkronizációt ne hagyományos zárakkal (mutexekkel), hanem atomi műveletekkel és gondosan megtervezett algoritmusokkal valósítsuk meg. Ezzel elkerülhetők a holtpontok, csökkenthető a várakozási idő, és gyakran jobb skálázhatóság érhető el. Ebben az alfejezetben a zárak nélküli adatszerkezetek alapfogalmait, a gyakorlati mintát (egy lock-free queue-t), valamint az ellenőrzés módszereit mutatjuk be. Előfeltételként feltételezzük az atomi műveletek és a memóriarendezés ismeretét (lásd Atomic műveletek és fences), itt a hangsúlyt a magasabb szintű szerkezetekre és a memóriavisszanyerésre helyezzük.

21.4.1 Progress garanciák

A lock-free adatszerkezeteket a progress garancia szerint osztályozzuk. Három fő kategória létezik:

  • Obstruction-free (akadálymentes): Egy szál akkor tud előrehaladni, ha a többi szál nem akadályozza. Ez a leggyengébb garancia: ha egy szálat felfüggesztenek, más szálak is elakadhatnak. Példa: egy egyszerű spinlock.
  • Lock-free (zármentes): A rendszer egésze garantáltan előrehalad valamelyik szálon, függetlenül attól, hogy más szálak mit csinálnak. Ez azt jelenti, hogy legalább egy szál mindig befejezi a műveletét véges lépésben, de az egyes szálak akár végtelen ideig is várakozhatnak (kiéheztetés). A legtöbb gyakorlati lock-free adatszerkezet ebbe a kategóriába tartozik.
  • Wait-free (várakozásmentes): Minden szál garantáltan befejezi a műveletét véges számú lépésben, függetlenül a többi szál ütemezésétől. Ez a legerősebb garancia, de általában bonyolultabb és nagyobb többletköltséggel jár.

A gyakorlatban a lock-free struktúrák széles körben elterjedtek, mert jó kompromisszumot kínálnak a teljesítmény és a bonyolultság között. A wait-free algoritmusokat főleg valós idejű rendszerekben használják, ahol a garantált válaszidő kritikus.

21.4.2 Alapépítőelem: CAS

A lock-free algoritmusok leggyakoribb primitívje a compare-and-swap (CAS). A C++-ban ezt a std::atomic compare_exchange_weak és compare_exchange_strong tagfüggvényei valósítják meg. A CAS atomikusan összehasonlítja az atomi objektum aktuális értékét egy elvárt értékkel, és ha egyezik, akkor lecseréli egy új értékre; ellenkező esetben az elvárt értéket frissíti az aktuálisra. A compare_exchange_weak engedélyezi az álsikert (spurious failure), ezért ciklusban kell használni, míg a strong garantáltan csak valódi eltérés esetén vall kudarcot. A lock-free ciklusok tipikus mintája:

std::atomic<int> counter{0};
int expected = counter.load(std::memory_order_relaxed);
do {
    // számítás expected alapján
    int desired = expected + 1;
} while (!counter.compare_exchange_weak(expected, desired,
             std::memory_order_release, std::memory_order_relaxed));

Itt a memory_order_release a sikeres csere memóriarendezése, a memory_order_relaxed pedig a sikertelen cseréé. Ez a minta biztosítja, hogy a többi szál által megfigyelt írások megfelelő sorrendben látszódjanak.

21.4.3 Lock-free stack (oktatási példa)

A legegyszerűbb lock-free adatszerkezet a verem (stack). Az alábbi példa csak a lock-free logikát mutatja be, a memóriavisszanyerést szándékosan elhagyjuk, hogy a következő szakaszban tárgyalhassuk a problémát.

#include <atomic>

template <typename T>
class lock_free_stack {
    struct node {
        T data;
        node* next;
        node(const T& data) : data(data), next(nullptr) {}
    };
    std::atomic<node*> head_;
public:
    lock_free_stack() : head_(nullptr) {}

    void push(const T& data) {
        node* new_node = new node(data);
        new_node->next = head_.load(std::memory_order_relaxed);
        while (!head_.compare_exchange_weak(
            new_node->next, new_node,
            std::memory_order_release,
            std::memory_order_relaxed)) {
            // újrapróbálkozás
        }
    }

    bool pop(T& result) {
        node* old_head = head_.load(std::memory_order_relaxed);
        while (old_head &&
               !head_.compare_exchange_weak(
                   old_head, old_head->next,
                   std::memory_order_acquire,
                   std::memory_order_relaxed)) {
            // újrapróbálkozás
        }
        if (!old_head) return false;
        result = old_head->data;
        // Figyelem: itt nem szabadítjuk fel old_head-ot,
        // mert más szálak még hivatkozhatnak rá. Lásd a szöveget.
        return true;
    }
};

A push művelet létrehoz egy új csomópontot, beállítja a next pointerét az aktuális fejre, majd CAS segítségével megpróbálja a fejet az új csomópontra cserélni. Ha más szál közben módosította a fejet, a CAS sikertelen lesz, és a ciklus újrapróbálkozik. A pop hasonló: olvassa a fejet, megpróbálja a fejet a következő csomópontra cserélni, és ha sikerül, visszaadja az adatot.

A memóriavisszanyerés hiánya azonban súlyos hibához vezethet: ha egy szál a pop után azonnal felszabadítaná a régi fejet, egy másik szál, amely még a head_ régi értékét olvasta, use-after-free hibát kapna. Ezért a lock-free struktúrákban a memóriavisszanyerést gondosan meg kell oldani.

21.4.4 ABA probléma

A fenti stack példában a memóriavisszanyerés hiánya mellett az ABA probléma is felmerül. Képzeljük el a következő forgatókönyvet:

  1. Az 1. szál a pop műveletben olvassa a fejet (legyen A csomópont), majd megszakad.
  2. A 2. szál végrehajt egy pop-ot, eltávolítja A-t, majd felszabadítja a memóriáját.
  3. A 2. szál ezután egy push-t hajt végre, amely új csomópontot foglal le. A memóriaallokátor véletlenül ugyanazt a címet adja vissza, mint A címe volt (ez gyakori a gyors allokátoroknál).
  4. Az 1. szál folytatja, és a head_-re vonatkozó compare_exchange hívást hajtja végre. Mivel a head_ aktuális értéke megegyezik az A címmel (ami most az új B csomópont címe), a CAS sikeres lesz, és az 1. szál B-t távolítja el, nem a régi A-t. Ez hibás állapotot eredményez.

Az ABA probléma akkor fordul elő, ha egy atomi pointer értéke megváltozik, majd visszatér az eredeti értékre, és egy másik szál ezt nem észleli. A megoldás általában az, hogy a pointerhez egy verziószámot (tag) rendelünk, és a CAS-t a pointer+tag kombinációra végezzük. Ezt hívják tagged pointernek.

C++-ban a tagged pointer megvalósítható egy 16 bájtos atomi típus használatával, ha a platform támogatja a double-word CAS-t. Például a GCC és a Clang biztosítja a __atomic_compare_exchange_n függvényt 16 bájtos típusokra is, ha a hardver támogatja (pl. x86-64 CMPXCHG16B). A C++ szabvány jelenleg nem definiál ilyen típust, de a C++26 tervek között szerepel a std::atomic<std::pair<T*, uintptr_t>> vagy hasonló (ellenőrzés szükséges). Gyakorlati megoldásként használhatunk platformfüggő kódot, vagy egy külön std::atomic<uintptr_t>-t, ahol a pointer alsó bitjeit használjuk verziószámként, de ez csak akkor működik, ha a pointerek igazítása biztosít szabad biteket (például 4 bájtos igazítás esetén az alsó 2 bit szabad).

struct tagged_ptr {
    node* ptr;
    uintptr_t tag;
};

std::atomic<tagged_ptr> head_; // feltételezi, hogy a tag 16 bájtos és atomi

A compare_exchange_weak így a teljes 16 bájtot cseréli, beleértve a taget is, így az ABA nem fordulhat elő, mert a tag minden egyes módosításkor növekszik.

21.4.5 Lock-free queue (Michael-Scott)

A lock-free sor (queue) az egyik legismertebb lock-free adatszerkezet, amelyet Maged Michael és Michael Scott publikált 1996-ban. Az algoritmus egy dummy csomópontot használ, amely mindig a sor elején áll, és két atomi pointert tart karban: head_ és tail_. Az enqueue a tail_ mögé fűzi az új csomópontot, a dequeue pedig a head_ utáni első csomópontot távolítja el.

Az alábbi kód a Michael-Scott queue vázlatát mutatja, memóriavisszanyerés nélkül (a memóriavisszanyerést a következő szakaszban tárgyaljuk).

#include <atomic>

template <typename T>
class lock_free_queue {
    struct node {
        T data;
        std::atomic<node*> next;
        node() : data{}, next(nullptr) {}
        node(const T& data) : data(data), next(nullptr) {}
    };
    std::atomic<node*> head_;
    std::atomic<node*> tail_;
public:
    lock_free_queue() {
        node* dummy = new node();
        head_.store(dummy, std::memory_order_relaxed);
        tail_.store(dummy, std::memory_order_relaxed);
    }

    ~lock_free_queue() {
        // Egyszerű felszabadítás, feltételezve, hogy nincs aktív szál.
        while (node* old_head = head_.load(std::memory_order_relaxed)) {
            head_.store(old_head->next, std::memory_order_relaxed);
            delete old_head;
        }
    }

    void enqueue(const T& data) {
        node* new_node = new node(data);
        node* last;
        while (true) {
            last = tail_.load(std::memory_order_relaxed);
            node* next = last->next.load(std::memory_order_relaxed);
            if (last == tail_.load(std::memory_order_relaxed)) {
                if (next == nullptr) {
                    if (last->next.compare_exchange_weak(
                        next, new_node,
                        std::memory_order_release,
                        std::memory_order_relaxed)) {
                        break;
                    }
                } else {
                    // Segítünk a tail_ frissítésében, ha más szál elakadt.
                    tail_.compare_exchange_weak(
                        last, next,
                        std::memory_order_release,
                        std::memory_order_relaxed);
                }
            }
        }
        // A tail_ frissítése, ha szükséges.
        tail_.compare_exchange_strong(
            last, new_node,
            std::memory_order_release,
            std::memory_order_relaxed);
    }

    bool dequeue(T& result) {
        node* first;
        while (true) {
            first = head_.load(std::memory_order_relaxed);
            node* last = tail_.load(std::memory_order_relaxed);
            node* next = first->next.load(std::memory_order_relaxed);
            if (first == head_.load(std::memory_order_relaxed)) {
                if (first == last) {
                    if (next == nullptr) {
                        return false; // üres sor
                    }
                    // Segítünk a tail_ frissítésében.
                    tail_.compare_exchange_weak(
                        last, next,
                        std::memory_order_release,
                        std::memory_order_relaxed);
                } else {
                    result = next->data;
                    if (head_.compare_exchange_weak(
                        first, next,
                        std::memory_order_acquire,
                        std::memory_order_relaxed)) {
                        break;
                    }
                }
            }
        }
        // A régi first csomópontot itt nem szabadítjuk fel,
        // mert más szálak még olvashatják. Lásd a szöveget.
        return true;
    }
};

Az algoritmus működése:

  • Az enqueue először betölti a tail_ pointert, majd megvizsgálja a mögötte lévő next pointert. Ha az next nullptr, akkor a sor vége valóban a last csomópont, és a CAS segítségével megpróbálja az új csomópontot a last->next-re írni. Ha sikerül, az új csomópont bekerült a sorba, és a tail_-t frissíti (ha más szál nem tette meg). Ha a next nem nullptr, akkor egy másik szál már hozzáfűzött egy csomópontot, de még nem frissítette a tail_-t, ilyenkor a jelenlegi szál segít a tail_ frissítésében.
  • A dequeue először betölti a head_-et, a tail_-t és a head_->next-et. Ha a head_ megegyezik a tail_-lel, akkor a sor vagy üres, vagy a tail_ elmaradt a head_ mögött. Ha a next nullptr, a sor üres. Egyébként segít a tail_ frissítésében. Ha a head_ nem egyezik a tail_-lel, akkor van kivehető elem: a head_->next adatát visszaadjuk, és a head_-et a next-re cseréljük CAS segítségével. A régi head_ csomópont felszabadítása később történik.

A memóriarendezések: az enqueue memory_order_release-t használ a sikeres CAS-nál, hogy a közzétett adat látható legyen a fogyasztó számára. A dequeue memory_order_acquire-t használ a sikeres cserénél, hogy a kivett adat olvasása előtt lássa a termelő által publikált írásokat. A relaxed memóriarendezés a nem kritikus részeken elegendő.

A fenti kód azonban nem memóriabiztos: a régi first csomópontot a dequeue után nem szabadíthatjuk fel azonnal, mert egy másik szál még éppen a head_ régi értékét olvasta, vagy a first->next-hez fér hozzá. A memóriavisszanyerés problémáját a következő szakaszban tárgyaljuk.

21.4.6 Memóriavisszanyerés lock-free környezetben

A lock-free adatszerkezetekben a legnagyobb kihívás a memóriavisszanyerés. A hagyományos, zárakkal védett struktúrákban a felszabadítás biztonságos, mert a zár kizárja a többi szálat. Lock-free esetben azonban egy szál nem tudhatja, hogy egy csomópontra más szálak még hivatkoznak-e. A probléma megoldására több stratégia létezik:

  1. Hazard pointer (veszélypointer): Minden szál regisztrál egy vagy több globális hazard pointert. Mielőtt egy szál egy csomópontot követne (például head_->next olvasása előtt), a hazard pointert beállítja arra a csomópontra, majd ellenőrzi, hogy a pointer még mindig érvényes-e (azaz a csomópont még a struktúrában van). A felszabadítás előtt a szál ellenőrzi, hogy egyetlen más szál hazard pointere sem mutat a csomópontra. Ha igen, a felszabadítást elhalasztja, amíg a hazard pointerek meg nem változnak. A hazard pointer módszer általános, de többletköltsége van a hazard pointerek karbantartása miatt.

  2. Epoch-based reclamation (EBR): A szálak belépnek egy “read-side critical section”-be, amelyet egy globális epoch (korszak) számláló véd. A memóriavisszanyerésre váró csomópontokat listákban tárolják. Amikor minden szál elhagyta az aktuális epochot, az adott epochhoz tartozó csomópontok felszabadíthatók. Az EBR gyorsabb, mint a hazard pointer, mert nincs per-művelet regisztráció, de a visszanyerés késleltetett, és a szálak nem blokkolódhatnak a kritikus szakaszban (ha egy szál felfüggesztődik, a visszanyerés megakad).

  3. Reference counting (referenciaszámlálás): Minden csomóponthoz egy atomi számláló tartozik. A lock-free referencia-számlálás általában kettős számlálást igényel (külső és belső), mert a csomópont elérése közben a számláló növelése és a struktúrából való eltávolítás versenyt okozhat. Anthony Williams “C++ Concurrency in Action” című könyvében részletesen bemutat egy ilyen lock-free queue-t.

  4. RCU (read-copy-update): Főleg kernel környezetben használják. Az olvasók egyáltalán nem használnak szinkronizációt, az írók pedig új verziót hoznak létre, és a régi verziót csak akkor szabadítják fel, ha minden olvasó elhagyta a kritikus szakaszt. A felhasználói térben ritkábban alkalmazzák.

A gyakorlatban a hazard pointer és az EBR a legelterjedtebb. A következő vázlat egy hazard pointer rendszer API-ját mutatja:

class hazard_pointer {
public:
    static hazard_pointer& acquire();  // Szálhoz rendelt hazard pointer lekérése
    void protect(std::atomic<node*>& ptr); // A hazard pointer beállítása
    void reset();                       // Hazard pointer törlése
    static void retire(node* p);        // Csomópont visszavonása (késleltetett felszabadítás)
};

A protect függvény tipikusan egy ciklust hajt végre: beállítja a hazard pointert a jelenlegi értékre, majd újra ellenőrzi, hogy a pointer nem változott-e. Ha változott, újrapróbálja. A retire hozzáadja a csomópontot egy visszavonási listához, és időnként ellenőrzi, hogy a hazard pointerek nem hivatkoznak-e a listában lévő elemekre; ha nem, felszabadítja őket.

21.4.7 Linearizálhatóság és progress garancia a gyakorlatban

A lock-free adatszerkezetek helyességét a linearizálhatóság fogalmával írhatjuk le. A linearizálhatóság azt jelenti, hogy minden művelet egyetlen atomi ponton fejti ki hatását, és ez a pont a művelet kezdete és vége között van. A Michael-Scott queue esetében:

  • Az enqueue linearizációs pontja a last->next sikeres CAS művelete, amikor az új csomópont bekerül a sorba.
  • A dequeue linearizációs pontja a head_ sikeres CAS művelete, amikor a régi dummy csomópontot eltávolítják, és a head_ a következőre mutat.

Ezek a pontok biztosítják, hogy a műveletek sorrendje konzisztens legyen.

A lock-free garancia azt jelenti, hogy ha több szál verseng, legalább az egyikük mindig előrehalad. A fenti algoritmusokban ez teljesül, mert a CAS ciklusokban a sikertelen kísérlet azt jelenti, hogy egy másik szál sikeres volt. A wait-free garancia erősebb, de a lock-free queue nem wait-free: egy szál elvileg végtelen ideig is próbálkozhat, ha folyamatosan más szálak nyerik a versenyt. A gyakorlatban azonban a lock-free struktúrák is jól teljesítenek, mert a versengés ritkán extrém.

21.4.8 Gyakori hibák és elkerülésük

A lock-free programozás számos buktatót rejt. A leggyakoribb hibák:

  • ABA probléma: Ahogy fentebb tárgyaltuk, a pointer értékének újrafelhasználása hibás CAS-t eredményezhet. Megoldás: tagged pointer vagy double-word CAS.
  • Memóriavisszanyerés elmulasztása: Ha egy csomópontot túl korán felszabadítunk, use-after-free hiba lép fel. Ha soha nem szabadítunk fel, memóriaszivárgás. Megoldás: hazard pointer, EBR, vagy referencia-számlálás.
  • Helytelen memóriarendezés: A relaxed memóriarendezés túlzott használata adatversenyhez vezethet. A szükséges release/acquire párokat gondosan meg kell tervezni. Például a push esetén a release biztosítja, hogy a csomópont adatai láthatóak legyenek, mielőtt a csomópont láthatóvá válik a struktúrában.
  • False sharing: A lock-free struktúrákban gyakran egymáshoz közeli atomi változók vannak, amelyek ugyanabba a cache line-ba kerülnek. Ez teljesítményromláshoz vezethet. A megoldás a cache line padding (pl. alignas(64)).
  • Nem atomi hozzáférés: Minden megosztott változót atomikusan kell elérni. A node->data mezőt például csak akkor olvashatjuk, ha a csomópont már nem lehet a struktúrában (vagy a hozzáférés szinkronizált).
  • Összetett invariáns megsértése: A Michael-Scott queue-ban a tail_ pointer elmaradhat a tényleges sor végétől, ezért az enqueue és dequeue segítik egymást a tail_ frissítésében. Ha ezt elhagyjuk, a sor inkonzisztenssé válhat.

Ezek a hibák nehezen reprodukálhatók, ezért kiemelten fontos a tesztelés: stressz tesztek, ThreadSanitizer (TSAN), AddressSanitizer (ASAN), és model checkerek (pl. CDSChecker) használata.

21.4.9 Labor: lock-free queue vázlata

A labor célja egy lock-free queue vázlatának implementálása C++20-ban, a Michael-Scott algoritmus alapján, memóriavisszanyerési stratégiával (hazard pointer vagy EBR). A hallgató feladata, hogy a fenti lock_free_queue osztályt kiegészítse a memóriavisszanyeréssel, és tesztelje többszálú környezetben.

Build és tesztkörnyezet:

  • Fordító: GCC 13 vagy Clang 16 (ellenőrzés szükséges a pontos verzióhoz)
  • Standard: C++20
  • Kapcsolók: -std=c++20 -O2 -Wall -Wextra -pedantic -pthread
  • Sanitizerek: -fsanitize=thread (TSAN) a teszteléshez, -fsanitize=address (ASAN) a memóriahibákhoz
  • Tesztcsomag: egy producer-consumer teszt, ahol N termelő és M fogyasztó szál véletlenszerű számú elemet ad/vesz ki, majd ellenőrizzük, hogy minden elem pontosan egyszer került ki, és nincs adatvesztés.
  • Mérési napló: rögzíteni kell a futtatások számát, az input méretet, a futási időt, az átlagot és a szórást. A várt eredmény: a queue helyesen működik, nincs TSAN hiba, és a teljesítmény skálázódik a szálak számával.

Példa build parancs:

g++ -std=c++20 -O2 -Wall -Wextra -pedantic -pthread -fsanitize=thread -o lfqueue_test main.cpp
./lfqueue_test

A tesztprogram vázlata:

#include <atomic>
#include <thread>
#include <vector>
#include <cassert>
#include <iostream>

// ... lock_free_queue definíció ...

int main() {
    constexpr int num_producers = 4;
    constexpr int num_consumers = 4;
    constexpr int items_per_producer = 10000;
    lock_free_queue<int> queue;
    std::atomic<int> total_consumed{0};
    std::atomic<bool> done{false};

    std::vector<std::thread> producers;
    for (int i = 0; i < num_producers; ++i) {
        producers.emplace_back([&queue, i]() {
            for (int j = 0; j < items_per_producer; ++j) {
                queue.enqueue(i * items_per_producer + j);
            }
        });
    }

    std::vector<std::thread> consumers;
    for (int i = 0; i < num_consumers; ++i) {
        consumers.emplace_back([&queue, &total_consumed, &done]() {
            int value;
            while (true) {
                if (queue.dequeue(value)) {
                    total_consumed.fetch_add(1, std::memory_order_relaxed);
                } else if (done.load(std::memory_order_relaxed)) {
                    break;
                } else {
                    std::this_thread::yield();
                }
            }
        });
    }

    for (auto& t : producers) t.join();
    done.store(true, std::memory_order_relaxed);
    for (auto& t : consumers) t.join();

    std::cout << "Total consumed: " << total_consumed.load() << '\n';
    assert(total_consumed.load() == num_producers * items_per_producer);
    return 0;
}

A mérés során dokumentálni kell a hardvert (CPU, memória), az operációs rendszert, a fordítóverziót, és a futtatások számát. A várt eredmény: a fenti tesztben minden elem pontosan egyszer kerül kiolvasásra, és a TSAN nem jelez adatversenyt.
