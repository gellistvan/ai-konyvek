15.3 Iterator adapters és view-k

Az iterátorok absztrakciót adnak a pozícióra, de gyakran nem elég a nyers begin()/end() pár: szükség lehet fordított bejárásra, elemek mozgatására, vagy arra, hogy egy algoritmus kimenetét közvetlenül egy konténerbe szúrjuk be. Az iterator adapterek pontosan ezt teszik: egy meglévő iterátort csomagolnak be, és megváltoztatják annak viselkedését anélkül, hogy a mögöttes tartományt módosítanák. A range view-k ennek a gondolatnak a magasabb szintű megfelelői: egy teljes range-et burkolnak be, és lusta, komponálható transzformációkat tesznek lehetővé.

Ebben az alfejezetben a C++20/23 szabvány három fontos iterátoradapterét – std::reverse_iterator, std::move_iterator és az insert_iterator családot –, valamint a std::ranges::view fogalmát és a leggyakoribb view-kat tekintjük át. A cél nem a teljes felsorolás, hanem annak megértése, hogyan épülnek fel ezek az eszközök, és hogyan használhatók biztonságosan egy összetett pipeline-ban.

15.3.1 Iterator adapterek általában

Az iterátoradapter egy olyan osztálysablon, amely egy vagy több mögöttes iterátort tárol, és az iterátor interfészt (operator*, operator++, operator--, operator+=, operator== stb.) úgy valósítja meg, hogy a műveletek a tárolt iterátoron más szemantikával hajtódnak végre. Az adapter nem változtatja meg a mögöttes tartományt, csak a hozzáférés módját. A standard adapterek általában a std::iterator interfészt követik, és a base() tagfüggvénnyel elérhetővé teszik a mögöttes iterátort, ha szükség van rá.

Az adapterek tipikus felhasználási területei: - Fordított bejárás – std::reverse_iterator - Mozgató szemantika kikényszerítése – std::move_iterator - Beszúrás kimeneti iterátorként – std::back_insert_iterator, std::front_insert_iterator, std::insert_iterator - Speciális stream-műveletek – std::istream_iterator, std::ostream_iterator (ezek szigorúan véve nem adapterek, de hasonló szerepet töltenek be)

A C++20 ranges könyvtárában a view-k gyakran belsőleg ilyen adapterekre épülnek: például a std::views::reverse egy std::ranges::reverse_view-t hoz létre, amelynek begin() és end() tagfüggvényei std::reverse_iterator-okat adnak vissza.

15.3.2 std::reverse_iterator

A std::reverse_iterator<Iter> egy olyan adapter, amely egy kétirányú vagy véletlen hozzáférésű iterátort csomagol be, és a bejárást megfordítja. Ha egy tartományt [begin, end) intervallummal adunk meg, a fordított tartomány [rbegin, rend) lesz, ahol rbegin a std::make_reverse_iterator(end) és rend a std::make_reverse_iterator(begin).

A legfontosabb tulajdonság, amely sok hibát okoz, a base() és a dereferencia viszonya. A reverse_iterator<It> mindig az általa tárolt base iterátor előtti elemre mutat. Formálisan, ha ri egy reverse_iterator, akkor *ri egyenlő *(ri.base() - 1) (random access iterátorok esetén). Általános kétirányú iterátornál ez *std::prev(ri.base()).

Ez a kialakítás lehetővé teszi, hogy a félintervallumok konzisztensek maradjanak: ha rbegin() a reverse_iterator(end()), akkor annak dereferálása az utolsó elemet adja, mert end() - 1 az utolsó elem. A rend() a reverse_iterator(begin()), amelynek dereferálása begin() - 1 lenne, ami érvénytelen, ezért a rend() nem dereferálható. Ez a megoldás garantálja, hogy a [rbegin, rend) intervallum ugyanazokat az elemeket tartalmazza, mint [begin, end), csak fordított sorrendben.

Példa:

#include <iostream>
#include <iterator>
#include <vector>

int main() {
    std::vector<int> v{1, 2, 3, 4, 5};

    // Fordított bejárás explicit reverse_iterator-ral
    for (auto ri = std::make_reverse_iterator(v.end());
         ri != std::make_reverse_iterator(v.begin());
         ++ri) {
        std::cout << *ri << ' ';   // 5 4 3 2 1
    }
    std::cout << '\n';

    // A base() és a dereferencia viszonya
    auto ri = std::make_reverse_iterator(v.end());   // az utolsó elemre mutat
    std::cout << "*ri = " << *ri << '\n';            // 5
    std::cout << "ri.base() == v.end(): "
              << (ri.base() == v.end()) << '\n';     // true
}

Törlés reverse_iterator-ral: Ha egy elemet törölni akarunk, akkor nem szabad a reverse_iterator-t közvetlenül átadni a erase függvénynek, mert az a base() iterátort várná, de a szemantika más. A helyes megoldás a base() használata, ügyelve arra, hogy a base() az elem után mutat. Ha ri a törlendő elemre mutat, akkor a törlendő iterátor std::prev(ri.base()). Példa:

#include <algorithm>
#include <iostream>
#include <iterator>
#include <vector>

int main() {
    std::vector<int> v{1, 2, 3, 4, 5};
    auto ri = std::find(v.rbegin(), v.rend(), 3);  // ri a 3-ra mutat
    if (ri != v.rend()) {
        // Helyes: a base() - 1 törlése
        v.erase(std::next(ri).base());  // vagy v.erase(std::prev(ri.base()));
    }
    for (int x : v) std::cout << x << ' ';  // 1 2 4 5
}

A std::next(ri).base() azért működik, mert ri a 3-ra mutat, ri + 1 a 2-re, annak base() pedig a 3-at tartalmazó iterátorra mutat (mivel a base() mindig eggyel mögötte van). A std::prev(ri.base()) közvetlenül is használható, de figyelni kell, hogy a prev csak kétirányú iterátoron érhető el.

15.3.3 std::move_iterator

A std::move_iterator<Iter> egy olyan adapter, amely a mögöttes iterátor operator* visszatérési értékét jobbérték-referenciává alakítja. Ezáltal a fogyasztó algoritmusok (pl. std::copy, std::insert, konstruktorok) a std::move segítségével mozgató konstruktort vagy mozgató értékadást hívnak a másoló változat helyett. Ez akkor hasznos, ha a forrás tartomány elemeire a továbbiakban nincs szükség, és a mozgatás olcsóbb, mint a másolás (például std::string, std::vector, okos mutatók).

A std::make_move_iterator(it) segédfüggvény létrehoz egy std::move_iterator-t. A base() tagfüggvény visszaadja a mögöttes iterátort.

Példa:

#include <iostream>
#include <iterator>
#include <string>
#include <vector>

int main() {
    std::vector<std::string> forras = {"alma", "banan", "citrom"};
    std::vector<std::string> cel;
    cel.reserve(forras.size());

    cel.insert(cel.end(),
               std::make_move_iterator(forras.begin()),
               std::make_move_iterator(forras.end()));

    for (const auto& s : cel) std::cout << s << ' ';  // alma banan citrom
    std::cout << '\n';

    // A forrás elemei moved-from állapotban vannak, ami érvényes, de nem meghatározott.
    // A méretük általában 0 lesz, de erre nem szabad építeni.
    std::cout << "forras[0].empty(): " << forras[0].empty() << '\n'; // általában true
}

Fontos: A move_iterator csak nem konstans iterátorokon hatékony. Ha a mögöttes iterátor konstans (pl. const std::string*), akkor a reference típusa const std::string&, és a move_iterator nem tud mozgatni, mert a const elemekből nem lehet elvenni az erőforrást. Ilyenkor a másolás történik. A std::move_iterator tehát nem egy varázseszköz, hanem csak akkor segít, ha a forrás ténylegesen nem konstans.

A move_iterator használata után a forrás konténer elemei moved-from állapotban vannak. Ez az állapot érvényes, de a konkrét tartalom implementációfüggő. A forrás konténer mérete nem változik, de az elemek értéke általában üres vagy alapértelmezett. A forrást csak akkor szabad újra használni, ha az elemeket újra inicializáljuk (pl. clear() és új értékek beillesztése).

15.3.4 insert_iterator család

Az insert_iterator egy kimeneti iterátor, amely egy konténerbe szúr be elemeket. Három változata van:

  • std::back_insert_iterator<Container> – a push_back() tagfüggvényt hívja.
  • std::front_insert_iterator<Container> – a push_front() tagfüggvényt hívja (csak olyan konténereknél, ahol van ilyen, pl. std::list, std::deque).
  • std::insert_iterator<Container> – az insert(pos, value) tagfüggvényt hívja egy megadott pozícióba.

Ezeket a std::back_inserter(container), std::front_inserter(container) és std::inserter(container, pos) segédfüggvényekkel hozhatjuk létre.

Az insert_iterator adapter működése: az operator* visszaadja magát az iterátort, az operator= pedig meghívja a megfelelő beszúró tagfüggvényt. Az operator++ (prefix és postfix) no-op, mert a beszúrás után az iterátor továbbra is ugyanoda mutat. Ez lehetővé teszi, hogy a szabványos algoritmusok (pl. std::copy, std::ranges::copy, std::fill) kimeneti iterátorként használják.

Példa:

#include <algorithm>
#include <iostream>
#include <iterator>
#include <list>
#include <vector>

int main() {
    std::vector<int> v = {1, 2, 3, 4, 5};
    std::vector<int> w;
    std::list<int> l;

    // back_insert_iterator: a végére szúr be
    std::copy(v.begin(), v.end(), std::back_inserter(w));
    // w = {1,2,3,4,5}

    // front_insert_iterator: a elejére szúr be, így a sorrend megfordul
    std::copy(v.begin(), v.end(), std::front_inserter(l));
    // l = {5,4,3,2,1}

    // insert_iterator: adott pozíció elé szúr be
    std::vector<int> z;
    auto it = z.begin();
    std::copy(v.begin(), v.end(), std::inserter(z, it));
    // z = {1,2,3,4,5}

    for (int x : w) std::cout << x << ' ';
    std::cout << '\n';
    for (int x : l) std::cout << x << ' ';
    std::cout << '\n';
    for (int x : z) std::cout << x << ' ';
}

Fontos: Az insert_iterator a konténerre mutató pointert vagy referenciát tárol, ezért a konténer élettartamának túl kell élnie az iterátor használatát. Ha a konténer megsemmisül, az iterátor érvénytelenné válik, és a használata undefined behavior. Emellett a front_insert_iterator csak olyan konténereknél használható, amelyeknek van push_front tagfüggvénye.

15.3.5 Range view-k

A C++20 ranges könyvtárában a view egy olyan range, amely olcsón másolható és mozgatható (jellemzően O(1)O(1) költséggel), és általában nem birtokol elemeket, hanem csak hivatkozik rájuk, vagy lustán generálja azokat. A std::ranges::view concept ezt formalizálja: egy range akkor view, ha a másolása és mozgatása O(1)O(1), és a destruktora O(1)O(1) (ha van eleme, akkor minden elemét megtartja). A view-k tehát lusta módon működnek: amíg nem iterálunk rajtuk, semmilyen számítás nem történik.

A view-k legfontosabb tulajdonsága a komponálhatóság: a | (pipe) operátorral összekapcsolhatók, és így deklaratív pipeline-okat építhetünk. Például:

#include <iostream>
#include <ranges>
#include <vector>

int main() {
    std::vector<int> v = {1, 2, 3, 4, 5, 6};

    auto pipeline = v
                  | std::views::reverse
                  | std::views::filter([](int x) { return x % 2 == 0; })
                  | std::views::transform([](int x) { return x * 10; });

    for (int x : pipeline) {
        std::cout << x << ' ';   // 60 40 20
    }
}

Itt a v | std::views::reverse egy std::ranges::reverse_view-t hoz létre, amely a v-re hivatkozik, és az iteráció során std::reverse_iterator-okat ad vissza. A | std::views::filter(...) ezt tovább csomagolja egy filter_view-ba, amely csak a páros elemeket engedi át. Végül a transform_view minden elemet megszoroz 10-zel. Az egész pipeline lusta: amikor a for ciklus elkezd iterálni, akkor történik csak a tényleges szűrés és transzformáció.

A view-k mögött gyakran iterátoradapterek állnak. Például a reverse_view::iterator egy std::reverse_iterator, a transform_view::iterator egy belső adapter, amely a operator*-ban alkalmazza a transzformációs függvényt, a filter_view::iterator pedig egy olyan adapter, amely operator++-nál addig lép, amíg a predikátum nem teljesül.

A standard view-k széles választéka érhető el (C++20 és C++23). Néhány fontos:

  • std::views::all – a range-et view-vá alakítja (ha lvalue, ref_view; ha rvalue, owning_view).
  • std::views::reverse – fordított bejárás.
  • std::views::filter – elemek szűrése predikátummal.
  • std::views::transform – elemek transzformálása függvénnyel.
  • std::views::take, std::views::drop, std::views::take_while, std::views::drop_while – résztartományok.
  • std::views::join, std::views::split – tartományok lapítása és szétválasztása.
  • std::views::common – a view-t olyan range-gé alakítja, amelynek begin és end azonos típusú.
  • std::views::iota – számsorozat generálása.
  • std::views::zip, std::views::enumerate (C++23) – párhuzamos bejárás.

A pipe operátor használatához a view-k úgynevezett range adaptor closure objektumokat biztosítanak. Ezek olyan hívható objektumok, amelyek egy range-et várnak, és view-t adnak vissza. A std::views::reverse például egy ilyen closure, ezért használható v | std::views::reverse formában is, nem csak std::views::reverse(v) hívásként.

15.3.6 View és borrowed range

Amikor view-kat használunk, kulcsfontosságú az élettartam kérdése. Egy view általában nem birtokolja az elemeket, hanem hivatkozik egy mögöttes range-re. Ha az a range megsemmisül, a view iterátorai érvénytelenné válnak, és a használatuk undefined behavior. Ezért a view-kat nem szabad úgy tárolni, hogy a mögöttes range rövidebb élettartamú legyen.

A std::ranges::borrowed_range concept azt jelzi, hogy egy range iterátorai nem függenek a range objektum élettartamától. Az ilyen range-ekből készült view-k biztonságosak akkor is, ha a view-t a range megsemmisülése után is használjuk. Példák borrowed range-ekre:

  • std::span<T> – a mögöttes tömbre mutat, a span másolása nem érinti az iterátorokat.
  • std::string_view – hasonló.
  • std::ranges::subrange egy pointerpárból – a subrange csak két iterátort tárol, nincs mögöttes objektum, amelytől az élettartam függne.
  • A std::views::all egy lvalue range-re alkalmazva ref_view-t hoz létre, amely a range-re mutató referenciát tárol, de mivel a range eleve kívül él, a view nem birtokol semmit, és az iterátorok a range-re mutatnak – ez borrowed_range, feltéve, hogy a range maga is borrowed vagy legalább a view használata alatt életben van.

Fontos azonban, hogy a legtöbb view nem borrowed_range. Például a filter_view iterátora tartalmazza a mögöttes range iterátorát és magának a filter_view-nak a pointerét, hogy a predikátumot elérje. Ha a filter_view megsemmisül, az iterátor érvénytelenné válik. Ezért egy filter_view-t nem szabad úgy átadni, hogy az eredeti view objektum már ne létezzen.

Példa a biztonságos és nem biztonságos használatra:

#include <iostream>
#include <ranges>
#include <vector>

// HIBÁS: a visszaadott view egy lokális vektorra hivatkozik,
// amely a függvény visszatérésekor megsemmisül.
/*
auto bad() -> std::ranges::filter_view<
                  std::ranges::ref_view<std::vector<int>>,
                  decltype([](int x) { return x > 0; })> {
    std::vector<int> v{1, -2, 3};
    return v | std::views::filter([](int x) { return x > 0; });
}
*/

// Megoldás: a range-et a hívó biztosítja, és a view csak addig él,
// amíg a range is él.
void print_positive(const std::vector<int>& v) {
    auto view = v | std::views::filter([](int x) { return x > 0; });
    for (int x : view) {
        std::cout << x << ' ';
    }
    std::cout << '\n';
}

int main() {
    std::vector<int> v{1, -2, 3, -4, 5};
    print_positive(v);  // 1 3 5
}

A bad függvényben a lokális v vektor megsemmisül, és a visszaadott view érvénytelenné válik. Ez a hiba a gyakorlatban nehezen debuggolható, mert a view másolása olcsó, és a hiba csak később, az iteráció során jelentkezik. A megoldás az, hogy a view-t soha ne tároljuk el hosszú távra, ha a mögöttes range nem biztosítja az élettartamát. Ha mégis szükséges egy függvényből view-t visszaadni, akkor a range-et is át kell adni (pl. std::span-ként) és a view csak addig érvényes, amíg a span mögötti adat él.

A std::ranges::borrowed_range concept segítségével ellenőrizhetjük, hogy egy adott view biztonságos-e:

static_assert(std::ranges::borrowed_range<std::string_view>);
static_assert(std::ranges::borrowed_range<std::span<int>>);
static_assert(!std::ranges::borrowed_range<std::ranges::filter_view<
                  std::ranges::ref_view<std::vector<int>>,
                  decltype([](int x) { return x > 0; })>>);

A harmadik esetben a filter_view nem borrowed, mert az iterátorai a view belső állapotára hivatkoznak.

15.3.7 Labor: adaptor-pipeline tervezése

A labor célja egy olyan pipeline megvalósítása, amely egyszerre használ iterátoradaptereket és range view-kat, és amelyet reprodukálhatóan, mérésekkel együtt futtatunk. A feladat a következő:

  1. Adott egy std::vector<std::string> forrás, amely üres stringeket is tartalmazhat.
  2. Készítsünk egy view pipeline-t, amely:
    • megfordítja a sorrendet (std::views::reverse),
    • kiszűri az üres stringeket (std::views::filter),
    • minden megmaradt string hosszát egész számmá alakítja (std::views::transform).
  3. Az eredmény view-t egy std::vector<int>-be gyűjtjük std::back_insert_iterator segítségével.
  4. Ezután a forrás stringjeit std::move_iterator-ral áthelyezzük egy másik std::vector<std::string>-be.
  5. Mérjük mindkét fázis futásidejét, és ellenőrizzük az eredményeket a várt értékekkel.

A build és a mérés rögzített környezetben történik:

  • Fordító: GCC 13.2.1
  • Szabvány: C++20
  • Fordítási kapcsolók: -O2 -Wall -Wextra -Wpedantic -fsanitize=address,undefined
  • Hardver: x86_64, 4 mag, 8 GB RAM (a konkrét környezettől függően változhat)
  • Futtatások száma: 5 (a labor során átlagoljuk)

A program kódja:

#include <algorithm>
#include <chrono>
#include <iostream>
#include <iterator>
#include <ranges>
#include <string>
#include <vector>

int main() {
    using namespace std::chrono;

    std::vector<std::string> forras = {"egy", "", "harom", "negy", "", "ot"};
    std::vector<int> hosszak;
    hosszak.reserve(forras.size());

    // 1. fázis: view pipeline és back_insert_iterator
    auto start = steady_clock::now();
    auto view = forras
              | std::views::reverse
              | std::views::filter([](const std::string& s) { return !s.empty(); })
              | std::views::transform([](const std::string& s) {
                    return static_cast<int>(s.size());
                });
    std::ranges::copy(view, std::back_inserter(hosszak));
    auto end = steady_clock::now();
    auto ido1 = duration_cast<microseconds>(end - start).count();

    // 2. fázis: move_iterator
    std::vector<std::string> cel;
    cel.reserve(forras.size());
    start = steady_clock::now();
    cel.insert(cel.end(),
               std::make_move_iterator(forras.begin()),
               std::make_move_iterator(forras.end()));
    end = steady_clock::now();
    auto ido2 = duration_cast<microseconds>(end - start).count();

    // Várt eredmények
    // A forrás: {"egy"(3), ""(0), "harom"(5), "negy"(4), ""(0), "ot"(2)}
    // Reverse sorrend: "ot"(2), ""(0 skip), "negy"(4), "harom"(5), ""(0 skip), "egy"(3)
    // Tehát hosszak: {2, 4, 5, 3}
    const std::vector<int> vart_hosszak = {2, 4, 5, 3};
    const std::vector<std::string> vart_cel = {"egy", "", "harom", "negy", "", "ot"};

    bool ok1 = (hosszak == vart_hosszak);
    bool ok2 = (cel.size() == vart_cel.size());
    if (ok2) {
        for (std::size_t i = 0; i < cel.size(); ++i) {
            if (cel[i] != vart_cel[i]) {
                ok2 = false;
                break;
            }
        }
    }

    std::cout << "Meresi naplo\n";
    std::cout << "1. fazis (view pipeline): " << ido1 << " us\n";
    std::cout << "2. fazis (move_iterator): " << ido2 << " us\n";
    std::cout << "Vart hosszak: [2,4,5,3] -> "
              << (ok1 ? "egyezik" : "Hiba!") << '\n';
    std::cout << "Vart cel: [egy,,harom,negy,,ot] -> "
              << (ok2 ? "egyezik" : "Hiba!") << '\n';

    return (ok1 && ok2) ? 0 : 1;
}

A program lefordítása és futtatása:

g++ -std=c++20 -O2 -Wall -Wextra -Wpedantic -fsanitize=address,undefined \
    -o labor_pipeline labor_pipeline.cpp
./labor_pipeline

A futtatás során a sanitizerek ellenőrzik a memóriabiztonságot és az undefined behavior esetleges előfordulását. A mérési naplóban a mért időket és a várt eredményeket külön jelöljük. Mivel a futásidő erősen függ a hardvertől és a terheléstől, a laborban legalább ötször futtassuk a programot, és átlagoljuk az időket. Az ilyen kis adathalmazon a mért idők általában néhány mikroszekundum körüliek, de a cél nem a pontos teljesítményelemzés, hanem a pipeline helyes működésének és a mérési módszertan bemutatása.

A mérési napló például így nézhet ki (a konkrét értékek a környezettől függenek):

15.3.8 Gyakori hibák és diagnosztika

Az iterátoradapterek és view-k használata során több tipikus hiba fordul elő:

  1. Dangling view – Ha egy view-t egy lokális range-ből hozunk létre, és a view-t a range megsemmisülése után használjuk, undefined behaviorhez vezet. A fordító nem mindig figyelmeztet, mert a view másolása olcsó, és a hiba csak futásidőben jelentkezik. A megoldás: a range élettartamát mindig biztosítsuk, vagy használjunk borrowed range-eket (pl. std::span) ha lehetséges.

  2. reverse_iterator::base() félreértése – A base() nem ugyanarra az elemre mutat, mint a reverse_iterator, hanem eggyel mögé. Törlésnél ezt figyelembe kell venni, különben rossz elemet törlünk vagy érvénytelen iterátort kapunk.

  3. move_iterator konstans iterátoron – Ha a forrás konténer konstans, a move_iterator nem mozgat, csak másol. Ez néha meglepetést okoz, mert a kód ugyanúgy lefordul, de a teljesítmény elmarad a várttól.

  4. insert_iterator és a konténer élettartama – Az insert_iterator a konténerre mutató pointert tárol. Ha a konténer megsemmisül, az iterátor érvénytelenné válik. Ez különösen akkor veszélyes, ha az iterátort egy algoritmusnak adjuk át, és a konténer időközben megsemmisül.

  5. View-k konstans jellege – Ha a mögöttes range konstans, a view iterátorai is konstans referenciát adnak. Ez azt jelenti, hogy a transform vagy filter nem tudja módosítani az elemeket. Ha módosításra van szükség, a range-nek nem konstansnak kell lennie, és a view-t úgy kell használni, hogy a mögöttes range módosítható maradjon.

15.3.10 Teszteset

A labor program önmagában is tartalmaz ellenőrzést, de írhatunk egy egyszerű unit tesztet is a pipeline helyességére:

#include <algorithm>
#include <cassert>
#include <iterator>
#include <ranges>
#include <string>
#include <vector>

void test_pipeline() {
    std::vector<std::string> forras = {"a", "", "bb", "ccc"};
    std::vector<int> hosszak;

    auto view = forras
              | std::views::reverse
              | std::views::filter([](const std::string& s) { return !s.empty(); })
              | std::views::transform([](const std::string& s) {
                    return static_cast<int>(s.size());
                });
    std::ranges::copy(view, std::back_inserter(hosszak));

    // Várt: forras = {"a"(1), ""(0), "bb"(2), "ccc"(3)}
    // Reverse: "ccc"(3), "bb"(2), ""(0 skip), "a"(1) -> {3,2,1}
    assert((hosszak == std::vector<int>{3, 2, 1}));
}

int main() {
    test_pipeline();
    return 0;
}

Ezt a tesztet lefordítva és futtatva ellenőrizhetjük a pipeline helyes működését. A laborban ezt a tesztet is futtassuk a sanitizerekkel együtt, hogy a memóriabiztonság is igazolt legyen.

15.3.11 Összefoglalás

Az iterátoradapterek és a range view-k a C++20/23 egyik leghatékonyabb absztrakciós eszközei. A reverse_iterator, move_iterator és az insert_iterator család lehetővé teszi a meglévő iterátorok viselkedésének finomhangolását anélkül, hogy a mögöttes adatszerkezetet megváltoztatnánk. A view-k pedig ezt a gondolatot emelik range szintre: lusta, komponálható pipeline-okat építhetünk, amelyek deklaratív módon írják le az adatfeldolgozást. A biztonságos használat kulcsa az élettartamok gondos kezelése, különösen a view-k esetében, ahol a borrowed_range fogalom segít eligazodni. A laborban bemutatott pipeline jól szemlélteti, hogyan kombinálhatók ezek az eszközök egyetlen reprodukálható, mérhető programban.
