15.2 Saját iterátorok

A saját iterátor írása akkor válik szükségessé, amikor egy egyedi adatszerkezetet szeretnénk beilleszteni a szabványos algoritmusok, a range-ek és a tartományalapú for ciklusok ökoszisztémájába. Az előző alfejezet (Iterátorkategóriák és hierarchia) bemutatta az iterátorkategóriákat és azok követelményhierarchiáját; itt arra összpontosítunk, hogyan kell ezeket a követelményeket egy konkrét, saját osztályban megvalósítani. A cél nem csupán egy működő iterátor, hanem olyan típus, amely a C++20 fogalomrendszerében is helytálló, és a szabványos algoritmusokkal együttműködik.

15.2.1 A saját iterátor követelményei

Mielőtt kódot írnánk, érdemes pontosan látni, mit vár el a nyelv és a szabványos könyvtár egy iterátortól. A C++20 előtt a követelményeket a szabvány szövege és az std::iterator_traits specializációja írta le; a C++20 óta a <iterator> fejlécben definiált fogalmak, mint például az std::input_iterator, std::forward_iterator, std::bidirectional_iterator, std::random_access_iterator és std::contiguous_iterator, közvetlenül ellenőrizhetők. A gyakorlatban egy egyedi iterátor akkor használható a szabványos algoritmusokkal, ha:

  1. Rendelkezik a szükséges belső típusdefiníciókkal (value_type, difference_type, reference, pointer, iterator_category vagy iterator_concept), vagy ezeket az std::iterator_traits specializációján keresztül elérhetővé teszi.
  2. Megvalósítja a dereferencia műveletet (operator*), az inkrementálást (operator++ pre- és posztváltozat) és – a kategóriától függően – az összehasonlítást (operator==), a dekrementálást, a véletlen hozzáférést vagy a pointer-aritmetikát.
  3. A tagfüggvények const helyességűek, és a másolható/mozgatható szemantika a várt módon működik.

A C++20 fogalomrendszerrel való kompatibilitás érdekében a legegyszerűbb úgy definiálni az iterátort, hogy az megfeleljen az std::forward_iterator fogalomnak, ha csak előrehaladó iterációra van szükség. Ehhez a minimális felület:

class iterator {
public:
    using value_type = T;         // az elem típusa
    using difference_type = std::ptrdiff_t;
    using reference = T&;         // vagy const T& konstans iterátornál
    using pointer = T*;           // vagy const T*
    using iterator_category = std::forward_iterator_tag;
    // C++20: az iterator_concept opcionálisan megadható
    using iterator_concept = std::forward_iterator_tag;

    iterator() = default;
    reference operator*() const;
    pointer operator->() const;
    iterator& operator++();
    iterator operator++(int);
    friend bool operator==(const iterator&, const iterator&);
};

A C++20 fogalmak azonban automatikusan kikövetkeztetik a value_type-ot, ha az std::iter_value_t sablon számára elérhető, ezért a belső típusok megadása nem feltétlenül kötelező, de a hordozhatóság és a régebbi kódbázisokkal való kompatibilitás miatt erősen ajánlott. Az std::iterator_traits elsődleges sablonja megpróbálja kiolvasni a belső típusokat, ezért ha az iterátor magában hordozza őket, nincs szükség külön specializációra.

A C++20 bevezette az iterator_concept tagot is, amely lehetővé teszi, hogy a fogalom-ellenőrzés finomabb legyen, mint a hagyományos iterator_category. Például egy régi típus std::forward_iterator_tag kategóriával is lehet std::random_access_iterator a fogalom szerint, ha megadja az iterator_concept-et std::random_access_iterator_tag-ként és biztosítja a megfelelő műveleteket. A szövegben a példák esetén a hagyományos iterator_category mellett az iterator_concept megadását is bemutatjuk, mert ez a modern ajánlás.

15.2.2 begin, end és az iterátor kapcsolata

Ahhoz, hogy egy konténer saját iterátorral rendelkezzen, definiálnunk kell a begin() és end() tagfüggvényeket (vagy szabad függvényeket, ha a típust nem módosíthatjuk). A tartományalapú for ciklus és a legtöbb szabványos algoritmus ezeket hívja. A begin() az első elemre mutató iterátort adja vissza, az end() pedig a „one-past-the-last” elemet jelölő iterátort. Az end() iterátor soha nem dereferálható, és az összehasonlítás alapján jelzi a tartomány végét.

A C++20 std::ranges névterében a std::ranges::begin és std::ranges::end testreszabási pont objektumok (CPO-k) vannak, amelyek először a tagfüggvényeket keresik, majd a szabad függvényeket. Így ha a konténerünk begin() tagfüggvénnyel rendelkezik, az automatikusan működik a range-ekkel is.

Egy egyszerű konténer vázlata:

template<typename T, std::size_t N>
class fixed_array {
    T data_[N];
public:
    using value_type = T;
    using iterator = /* saját iterátor típus */;
    using const_iterator = /* konstans iterátor */;

    iterator begin() noexcept { return iterator(data_); }
    iterator end() noexcept { return iterator(data_ + N); }
    const_iterator begin() const noexcept { return const_iterator(data_); }
    const_iterator end() const noexcept { return const_iterator(data_ + N); }
    // ...
};

A const túlterhelés biztosítja, hogy konstans objektumon a begin() és end() konstans iterátort adjon, ami elengedhetetlen a helyes használathoz. A noexcept megadása opcionális, de a gyakorlatban jó, mert a konténer elemeihez való hozzáférés nem dob kivételt.

15.2.3 operator* és operator++

A dereferencia operátor visszatérési típusa az iterátor reference típusa, amely általában T& (vagy const T& konstans iterátornál). A operator* tipikus megvalósítása:

T& operator*() const { return *ptr_; }

ahol ptr_ egy T* típusú tag. A const minősítés a függvényen azt jelenti, hogy az iterátor objektum maga nem módosul a dereferencia során, ami mindig igaz, hiszen a mutatott elemhez férünk hozzá, nem az iterátorhoz.

Az inkrementálás pre- és posztváltozata:

iterator& operator++() {
    ++ptr_;
    return *this;
}

iterator operator++(int) {
    iterator tmp = *this;
    ++ptr_;
    return tmp;
}

A posztinkremens visszatérési típusa mindig érték, és a szabványos megvalósítási minta a fenti: másolatot készítünk, növeljük az aktuálisat, majd a másolatot adjuk vissza. Fontos, hogy a posztinkremens hívása után az eredeti iterátor már a következő elemre mutat, a visszaadott másolat pedig a régi állapotot tükrözi.

Az összehasonlítás C++20-ban leegyszerűsödött: elég az operator== definiálása, mert az operator!= automatikusan generálódik a == negáltjaként. A C++20 előtti kóddal való kompatibilitáshoz azonban érdemes mindkettőt megadni, vagy legalább az operator!=-t is. Példa:

friend bool operator==(const iterator& a, const iterator& b) noexcept {
    return a.ptr_ == b.ptr_;
}
// C++20-ban a != automatikus

A friend deklarációval a függvény hozzáfér a privát tagokhoz, és lehetővé teszi, hogy az összehasonlítás szimmetrikus legyen. A noexcept itt is indokolt.

15.2.4 Proxy reference és arrow

Az eddigi példákban a dereferencia valódi referenciát (T&) adott vissza. Vannak azonban olyan esetek, amikor ez nem lehetséges: például ha a tárolt elemek nem közvetlenül a memóriában helyezkednek el, hanem tömörítve, bitenként, vagy egy távoli adatforrásból származnak. Ilyenkor az iterátor operator* nem tud T&-et visszaadni, mert nincs tényleges T objektum, amelyre mutathatna. A megoldás az úgynevezett proxy reference: egy olyan segédosztály, amely érték szerint viselkedik, és konverziós operátorral vagy tagfüggvényekkel biztosítja a hozzáférést az alatta lévő elemhez.

A klasszikus példa az std::vector<bool> iterátora, amely bitenként tárolja az elemeket, és az operator* egy std::_Bit_reference típusú proxyt ad vissza. A proxy objektum általában támogatja a operator T() konverziót és a operator=(T) értékadást, így a felhasználó számára majdnem úgy viselkedik, mint egy T&.

A probléma azonban az operator-> művelettel jelentkezik. Ha az iterátor operator* egy proxy objektumot ad vissza, akkor az operator-> nem tud egyszerűen &(*this)-et visszaadni, mert a proxy nem feltétlenül rendelkezik címmel. A C++ szabvány szerint az operator-> úgy működik, hogy a hívás eredményének típusától függően a fordító rekurzívan alkalmazza az operator->-t mindaddig, amíg egy nyers pointert nem kap. Tehát ha a proxy osztály is definiál egy operator->-t, amely a tényleges elemre mutató pointert ad vissza, akkor a lánc működik.

Nézzünk egy konkrét példát: egy BitVector osztály, amely bitenként tárolja a logikai értékeket. Az iterátor operator* egy BitReference proxyt ad vissza:

class BitReference {
    std::byte* byte_;
    std::size_t bit_;
public:
    BitReference(std::byte* b, std::size_t bit) : byte_(b), bit_(bit) {}

    operator bool() const {
        return (*byte_ & mask()) != std::byte{0};
    }

    BitReference& operator=(bool value) {
        if (value)
            *byte_ |= mask();
        else
            *byte_ &= ~mask();
        return *this;
    }

    // operator-> a tényleges bool-ra mutató pointert ad vissza
    bool* operator->() {
        // Itt egy ideiglenes bool jön létre – ez veszélyes!
        // A helyes megoldáshoz lásd a szöveget.
        return nullptr; // helytelen, csak illusztráció
    }
private:
    std::byte mask() const noexcept {
        return std::byte{1} << bit_;
    }
};

A fenti operator-> megvalósítás nyilvánvalóan hibás, mert nem létezik tartós bool objektum, amelyre mutathatna. A proxy referencia operator-> megvalósítása csak akkor lehetséges, ha van egy tényleges tárolt objektum, amelyre mutathatunk. Mivel a bitvektor nem tárol bool objektumokat, az operator-> használata a BitReference-en értelmetlen. A szabványos std::vector<bool> iterátor nem is biztosít operator->-t, vagy ha biztosít, az visszaad egy segédobjektumot, amelynek van operator->-je, de az eredmény nem használható biztonságosan. A gyakorlatban a proxy reference esetén az operator-> gyakran elhagyható, vagy csak akkor biztosítható, ha a proxy mögött van egy tartós objektum. Ezt a korlátozást a felhasználónak tudomásul kell vennie: az ilyen iterátor nem teljesíti a std::forward_iterator fogalmat, ha az operator-> hiányzik, mert a fogalom megköveteli az operator-> meglétét. Ezért az std::vector<bool> iterátora nem is std::forward_iterator, hanem csak std::input_iterator.

Ha viszont a proxy mögött van egy valódi tárolt objektum (például egy másik konténerben), akkor az operator-> megvalósítható úgy, hogy a proxy operator-> visszaadja a mögöttes objektum pointerét. Például egy olyan iterátor, amely egy std::map értékeit adja vissza, és a proxy egy std::pair<const Key, Value>&-re mutat, akkor az operator-> egyszerűen a pár pointerét adja vissza. Ebben az esetben a proxy referencia nem is feltétlenül szükséges, mert a map iterátor operator* eleve referenciát ad.

Összefoglalva: ha az operator* valódi referenciát ad, akkor az operator-> triviálisan megvalósítható &**this formában. Ha az operator* proxy-t ad, akkor az operator->-t a proxy osztályban kell megvalósítani, és a lánc addig folytatódik, amíg nyers pointert nem kapunk. Ha a proxy nem tud érvényes pointert szolgáltatni, az iterátor nem használható operator->-szal, és legfeljebb std::input_iterator fogalmat teljesíthet.

15.2.5 Tipikus hibák és elkerülésük

A saját iterátor írása során számos buktatóval találkozhatunk. Az alábbiakban a leggyakoribb hibákat és a helyes megoldást foglaljuk össze.

Hiányzó belső típusdefiníciók. Ha az iterátor nem adja meg a value_type, difference_type, reference, pointer és iterator_category tagokat, az std::iterator_traits elsődleges sablonja nem tudja kikövetkeztetni őket, és a szabványos algoritmusok fordítási hibát okoznak. A hibaüzenet gyakran rejtélyes, ezért már a definícióban érdemes ellenőrizni a típusokat.

Hibás posztinkremens. A posztinkremens visszatérési típusának értéknek kell lennie, nem referenciának. Ha véletlenül iterator&-et adunk vissza, az vágó referenciát eredményez, és a hívó az ideiglenes objektumra mutató referenciát kap, ami nem biztonságos. A fent bemutatott sablon pontos használata elkerüli ezt.

A dereferencia const helyességének hiánya. A operator*-ot const tagfüggvényként kell deklarálni, különben a konstans iterátorokon nem lehet elemet olvasni, és a const_iterator nem lesz használható. Hasonlóan, a operator-> is legyen const.

Az összehasonlítás hiánya. A forward_iterator fogalom megköveteli az operator== meglétét. Ha nem definiáljuk, a range-alapú for ciklus nem tudja eldönteni, hol a tartomány vége. Fontos, hogy az end() iterátorral való összehasonlítás mindig konzisztens legyen: a begin()-ből elindulva az inkrementálás során pontosan akkor érjük el az end()-et, amikor a tartomány végére értünk.

Proxy reference és arrow helytelen használata. Mint fentebb láttuk, a proxy esetén az operator-> nem triviális. A legnagyobb hiba az, ha a fejlesztő &**this-et próbál visszaadni, vagy egy ideiglenes objektumra mutató pointert ad vissza. Ez futás közben undefined behavior-hez vezet. A megoldás vagy a operator-> elhagyása (és ezzel az iterátor besorolása input_iterator-ként), vagy egy olyan proxy tervezése, amely biztonságosan tud pointert szolgáltatni.

A begin/end konzisztenciája. Egy konténer begin() és end() függvényeinek ugyanazt az iterátortípust kell visszaadniuk. Ha az egyik iterator-t, a másik const_iterator-t ad vissza, az összehasonlítás nem működik, mert a típusok különböznek. A szabványos konténerekben a konstans iterátorok és a nem konstans iterátorok közötti összehasonlítás általában támogatott, de ehhez konverziós konstruktort vagy barát összehasonlító függvényeket kell írni. Az egyszerűség kedvéért lehet, hogy a begin() és end() mindig ugyanazt az iterátortípust adja vissza, és a konstans esetben az elemekhez való hozzáférés const minősített referenciát ad. Ez a gyakorlatban elfogadható, ha a konténer nem igényli a konstans iterátorok szigorú szétválasztását.

15.2.6 Labor: Saját iterátor implementálása

A következő labor célja, hogy az olvasó saját kezűleg implementáljon egy iterátort egy egyszerű konténerhez, és ellenőrizze annak helyességét a C++20 fogalomrendszerével. A feladat egy RingBuffer (ciklikus puffer) iterátora, amely véges kapacitású, és a tárolt elemeket a beillesztés sorrendjében járja be.

15.2.7 Specifikáció

  • A RingBuffer<T, N> osztály rögzített N kapacitású, T típusú elemeket tárol.
  • A push_back(const T&) és push_back(T&&) függvények hozzáadnak egy elemet; ha a puffer tele van, a legrégebbi elem felülíródik.
  • A begin() és end() tagfüggvények visszaadják az iterátort a legrégebbi elemre, illetve a „one-past-the-last” pozícióra.
  • Az iterátor teljesítse a std::forward_iterator fogalmat.
  • Az iterátor operator* valódi T& referenciát adjon vissza (nem proxy-t), ezért az operator-> triviálisan &**this formában megvalósítható.
  • A konténer const változata is támogatott legyen: konstans iterátorral, amely const T&-et ad vissza.

15.2.8 Kiinduló váz

Az alábbi kód egy lehetséges kiindulópont, amelyet a labor során ki kell egészíteni és tesztelni. A kommentek jelzik a kitöltendő részeket.

#include <cstddef>
#include <iterator>
#include <type_traits>
#include <cassert>
#include <algorithm>
#include <vector>

template<typename T, std::size_t N>
class RingBuffer {
    static_assert(N > 0, "RingBuffer requires positive capacity");
    T data_[N];
    std::size_t head_ = 0; // legrégebbi elem indexe
    std::size_t size_ = 0; // aktuális elemszám

public:
    using value_type = T;
    using size_type = std::size_t;
    using difference_type = std::ptrdiff_t;

    // Iterátor deklaráció
    class iterator;
    class const_iterator;

    // Konstruktor
    RingBuffer() = default;

    // push_back
    void push_back(const T& value) {
        if (size_ < N) {
            data_[(head_ + size_) % N] = value;
            ++size_;
        } else {
            // felülírjuk a legrégebbit
            data_[head_] = value;
            head_ = (head_ + 1) % N;
        }
    }

    void push_back(T&& value) {
        if (size_ < N) {
            data_[(head_ + size_) % N] = std::move(value);
            ++size_;
        } else {
            data_[head_] = std::move(value);
            head_ = (head_ + 1) % N;
        }
    }

    size_type size() const noexcept { return size_; }
    bool empty() const noexcept { return size_ == 0; }

    // begin és end
    iterator begin() noexcept;
    iterator end() noexcept;
    const_iterator begin() const noexcept;
    const_iterator end() const noexcept;
    const_iterator cbegin() const noexcept;
    const_iterator cend() const noexcept;

private:
    // A iterátorok barát hozzáférést kapnak
    friend class iterator;
    friend class const_iterator;
};

15.2.9 Az iterátor implementáció

A RingBuffer::iterator osztály a head_ indexet és a pufferhez tartozó mutatót tárolja. Egy iterátor a puffer egy elemének pozícióját jelöli, és a size_ értékétől függetlenül a teljes [0, capacity] tartományban mozoghat. Az end() iterátor a head_ + size_ pozíciót jelöli, ami a ciklikus tárolás miatt (head_ + size_) % N indexre mutat. A begin() a head_-re mutat.

template<typename T, std::size_t N>
class RingBuffer<T, N>::iterator {
    RingBuffer* owner_;
    std::size_t pos_;   // abszolút pozíció a ciklikus tárolóban (0..capacity-1)

    // privát konstruktor a barátoknak
    iterator(RingBuffer* owner, std::size_t pos) : owner_(owner), pos_(pos) {}
    friend class RingBuffer<T, N>;
    friend class RingBuffer<T, N>::const_iterator;

public:
    using value_type = T;
    using difference_type = std::ptrdiff_t;
    using reference = T&;
    using pointer = T*;
    using iterator_category = std::forward_iterator_tag;
    using iterator_concept = std::forward_iterator_tag;

    iterator() = default;

    reference operator*() const {
        return owner_->data_[pos_];
    }
    pointer operator->() const {
        return &(operator*());
    }

    iterator& operator++() {
        ++pos_;
        if (pos_ >= N) pos_ = 0; // valójában az abszolút pozíciót növeljük, nem ciklikusan
        return *this;
    }

    iterator operator++(int) {
        iterator tmp = *this;
        ++(*this);
        return tmp;
    }

    friend bool operator==(const iterator& a, const iterator& b) {
        return a.owner_ == b.owner_ && a.pos_ == b.pos_;
    }
    // C++20: != automatikus
};

A fenti megvalósításban az operator++ csak növeli a pos_-t, de nem veszi figyelembe a puffer ciklikusságát, mert az abszolút pozíciót lineárisan kezeljük. A begin() a head_-re mutat, az end() pedig a (head_ + size_) % N-re, ezért az iteráció során a pos_ lineárisan növekszik, és amikor eléri az end()-et, az összehasonlítás megállítja a ciklust. Ez a modell működik, de ügyelni kell arra, hogy a pos_ ne lépje túl az N értéket; az operator++ egyszerűen ++pos_-t csinál, és mivel az end() pozíciója legfeljebb N-1 lehet, a növelés során a pos_ elérheti az N-et, ami már kívül esik a tömbön. Ezért az operator++-ban ellenőrizni kell, hogy ha pos_ eléri az N-et, akkor a ciklikusság miatt visszaáll 0-ra? De ez nem helyes, mert az end() pozíciója a (head_ + size_) % N, ami nem feltétlenül 0. A jobb megoldás az abszolút index helyett a ciklikus indexet használni, és az end()-et külön flag-gel jelölni. A fenti vázban a pos_ valójában a ciklikus index, de akkor az operator++-ban a (pos_ + 1) % N kell, és az end() pozíciója (head_ + size_) % N. Azonban ekkor a begin() és end() összehasonlítása nem működik, mert a begin() head_, az end() (head_ + size_) % N, és ha size_ == N, akkor a kettő ugyanaz, ami üres tartományt jelentene, pedig tele van. Ezért a RingBuffer iterátorának megvalósításához egy abszolút pozíciót kell használni, amely független a ciklikus tárolástól, és a dereferencia során a data_[pos_ % N] értéket adjuk vissza. A begin() az abszolút head_, az end() az abszolút head_ + size_. Az operator++ egyszerűen növeli az abszolút pozíciót. Ez a legegyszerűbb és helyes.

Javított iterátor:

template<typename T, std::size_t N>
class RingBuffer<T, N>::iterator {
    RingBuffer* owner_;
    std::size_t abs_pos_;   // abszolút pozíció a tárolás kezdete óta

    iterator(RingBuffer* owner, std::size_t abs_pos)
        : owner_(owner), abs_pos_(abs_pos) {}

    friend class RingBuffer<T, N>;
    friend class RingBuffer<T, N>::const_iterator;

public:
    using value_type = T;
    using difference_type = std::ptrdiff_t;
    using reference = T&;
    using pointer = T*;
    using iterator_category = std::forward_iterator_tag;
    using iterator_concept = std::forward_iterator_tag;

    iterator() = default;

    reference operator*() const {
        return owner_->data_[abs_pos_ % N];
    }
    pointer operator->() const {
        return &(operator*());
    }

    iterator& operator++() {
        ++abs_pos_;
        return *this;
    }
    iterator operator++(int) {
        iterator tmp = *this;
        ++(*this);
        return tmp;
    }

    friend bool operator==(const iterator& a, const iterator& b) {
        return a.owner_ == b.owner_ && a.abs_pos_ == b.abs_pos_;
    }
};

A begin() és end() implementációja:

template<typename T, std::size_t N>
typename RingBuffer<T, N>::iterator
RingBuffer<T, N>::begin() noexcept {
    return iterator(this, head_);
}

template<typename T, std::size_t N>
typename RingBuffer<T, N>::iterator
RingBuffer<T, N>::end() noexcept {
    return iterator(this, head_ + size_);
}

A konstans iterátor hasonló, de const RingBuffer* típust használ, és const T&-et ad vissza.

15.2.10 Ellenőrzés fogalmakkal

A C++20 fogalomrendszer lehetővé teszi, hogy fordítási időben ellenőrizzük az iterátor kategóriáját:

static_assert(std::forward_iterator<RingBuffer<int, 8>::iterator>);
static_assert(std::forward_iterator<RingBuffer<int, 8>::const_iterator>);

Ha az iterátor hiányos, a static_assert részletes diagnosztikát ad, ami segít a hibakeresésben.

15.2.11 Tesztelés

A laborhoz írjunk egy egyszerű tesztprogramot, amely ellenőrzi a RingBuffer és iterátora működését:

#include <cassert>
#include <vector>
#include <algorithm>
#include <ranges>
#include <iostream>

int main() {
    RingBuffer<int, 4> rb;
    rb.push_back(1);
    rb.push_back(2);
    rb.push_back(3);
    rb.push_back(4); // tele
    rb.push_back(5); // 1 felülíródik

    std::vector<int> expected = {2, 3, 4, 5};
    std::vector<int> actual;
    for (int x : rb) {
        actual.push_back(x);
    }
    assert(actual == expected);

    // Konstans iterátor teszt
    const auto& crb = rb;
    std::vector<int> const_actual;
    for (const auto& x : crb) {
        const_actual.push_back(x);
    }
    assert(const_actual == expected);

    // Algoritmusokkal való kompatibilitás
    auto it = std::find(rb.begin(), rb.end(), 3);
    assert(it != rb.end());
    assert(*it == 3);

    std::cout << "RingBuffer iterator tests passed\n";
    return 0;
}

15.2.13 Összefoglalás

A saját iterátor írása alapvető készség a C++ programozó számára, mert lehetővé teszi egyedi adatszerkezetek integrálását a szabványos algoritmusok és range-ek világába. A sikeres implementáció kulcsa a követelmények pontos ismerete: a belső típusok, a dereferencia, az inkrementálás és az összehasonlítás helyes megvalósítása. A proxy reference és az operator-> speciális esetei további figyelmet igényelnek, mert a hibás megoldások undefined behavior-höz vezethetnek. A C++20 fogalmak használata fordítási időben ellenőrzi az iterátor megfelelőségét, és megkönnyíti a hibakeresést.

A labor során az olvasó egy RingBuffer iterátort készít el, amely teljesíti a std::forward_iterator fogalmat, és teszteli azt a szabványos algoritmusokkal. A mérési napló rögzíti a build és futási körülményeket, biztosítva a reprodukálhatóságot. A következő alfejezet (Iterator adapters és view-k) erre az alapra építve az iterátoradaptereket és a view-kat tárgyalja, amelyek lehetővé teszik a meglévő iterátorok átalakítását és a lusta kiértékelésű range-ek létrehozását.
