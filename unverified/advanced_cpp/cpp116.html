30.3 Embedded DSL és parser generators

A beágyazott nyelvek (embedded domain-specific language, EDSL) és a generált parser két, látszólag különböző terület, amelyek valójában ugyanazt a problémát oldják meg: hogyan adhatunk egy jól meghatározott, szűk feladatkörhöz kifejező, de a C++ típusrendszerébe és életciklus-szabályaiba illeszkedő nyelvet. A külső DSL-ek – például a buildrendszerek konfigurációs nyelvei, a tesztleíró nyelvek vagy a lekérdező nyelvek – általában külön grammarral rendelkeznek, és egy lexert, illetve parsert igényelnek. A belső DSL-ek ezzel szemben a C++ szintaxisára építenek: túlterhelt operátorokkal, metódusláncolással és expression template-ekkel alakítanak ki olyan kódot, amely úgy néz ki, mintha egy saját nyelvet használnánk, valójában azonban a C++ fordító ellenőrzi a típusokat és az élettartamot. A generált parser e két világ közé lép: egy grammar leírásból olyan C++ kódot állít elő, amely a bemenetet elemezve absztrakt szintaxisfát (AST) vagy közvetlen műveleteket hoz létre.

Ebben az alfejezetben először a belső DSL-eket vizsgáljuk, különös tekintettel az expression template-ekre, amelyeket a 10.1 alfejezetben már részletesen tárgyaltunk; itt a nyelvtervezési szempontokra és a grammarra való leképezésre koncentrálunk. Ezután a külső parser generátorok alapelveit tekintjük át, beleértve az ANTLR-t és a parsing expression grammar (PEG) alapú eszközöket. Végül egy kézzel írt, rekurzív leszállású (recursive descent) parser minta következik, amely a legegyszerűbb, függőségmentes belépő a parser íráshoz. A fejezetet egy labor zárja, amelyben egy kis aritmetikai DSL-t valósítunk meg mindkét megközelítéssel, reprodukálható mérési naplóval.

30.3.1 Belső DSL-ek és expression template-ek

A belső DSL-ek alapötlete, hogy a befogadó nyelv (host language) szintaxisát úgy használjuk, mintha egy saját nyelvet beszélnénk. C++-ban erre a legfontosabb eszközök:

  • operátortúlterhelés,
  • metódusláncolás (fluent interface),
  • tag dispatch és típusos tag-ek,
  • lambdák és std::function,
  • expression template-ek.

Az expression template-ek különösen alkalmasak olyan DSL-ek építésére, amelyek kifejezéseket írnak le, például mátrixműveleteket, vektoros számításokat vagy szabályalapú illesztéseket. A technika lényege, hogy az operátorok nem azonnal végrehajtják a műveletet, hanem egy fa struktúrát építenek, amelyet később értékelünk ki. Ez lehetővé teszi a kifejezés újrahasznosítását, átalakítását, vagy éppen hatékonyabb kiértékelését, például a felesleges átmeneti objektumok elkerülését.

Nézzünk egy egyszerű, vektoros belső DSL-t, amely a + és * operátorokat túlterheli, és a kifejezést expression template-ként tárolja. A példa didaktikus, a std::vector-hoz képest szándékosan leegyszerűsített, de jól mutatja a nyelvtervezés és a C++ típusrendszer összjátékát.

#include <cstddef>
#include <iostream>
#include <vector>

template <typename L, typename R, typename Op>
struct Expr {
    const L& lhs;
    const R& rhs;
    Expr(const L& l, const R& r) : lhs(l), rhs(r) {}
    auto operator[](std::size_t i) const -> double {
        if constexpr (std::is_same_v<Op, std::plus<>>) {
            return lhs[i] + rhs[i];
        } else if constexpr (std::is_same_v<Op, std::multiplies<>>) {
            return lhs[i] * rhs[i];
        }
        // Más művelet esetén fordítási hiba: nem támogatott.
        static_assert(sizeof(Op) == 0, "Unsupported operation");
    }
};

struct Vec {
    std::vector<double> data;
    explicit Vec(std::vector<double> d) : data(std::move(d)) {}
    auto operator[](std::size_t i) const -> double { return data[i]; }
    std::size_t size() const { return data.size(); }
};

template <typename L, typename R>
auto operator+(const L& l, const R& r) {
    return Expr<L, R, std::plus<>>(l, r);
}

template <typename L, typename R>
auto operator*(const L& l, const R& r) {
    return Expr<L, R, std::multiplies<>>(l, r);
}

template <typename E>
auto evaluate(const E& expr, std::size_t i) {
    return expr[i];
}

Itt a Vec osztály csak az adatot tárolja, míg a + és * operátorok egy Expr objektumot hoznak létre, amely referenciákkal hivatkozik a két operandusra. A kiértékeléskor a [] operátor rekurzívan hívódik, és a műveletet a std::plus<> vagy std::multiplies<> típus határozza meg. Ez a kód C++20-ban már kihasználhatja a std::is_same_v és a constexpr if eszközöket, de a lényeg a késleltetett kiértékelés.

A fenti példa egy belső DSL, amelynek grammarja szorosan kötődik a C++ szintaxisához: a kifejezések operátorokból és operandusokból állnak, és a fordító ellenőrzi a típusokat. A hátrány az, hogy a nyelv kifejezőerejét a C++ operátorai korlátozzák; például nem lehet saját precedenciát bevezetni, és a kifejezések hosszú láncai nehezen olvashatók lehetnek.

Egy másik elterjedt minta a fluent interface, ahol a metódusok láncolásával építünk utasításokat. Például egy egyszerű SQL-szerű lekérdezés DSL így nézhet ki:

auto result = query()
    .select("name", "age")
    .from("users")
    .where("age > 30")
    .order_by("name");

Itt a query() egy olyan objektumot ad vissza, amelynek minden metódusa egy újabb, módosított állapotot hoz létre vagy módosítja az aktuálist. A fluent interface nem igényel operátortúlterhelést, de erősen támaszkodik a névvel ellátott metódusokra és a láncolható kialakításra. A grammar itt a metódushívások sorrendjében rejlik, amelyet a fordító csak részben tud ellenőrizni: a típusok biztosíthatják, hogy bizonyos metódusok csak bizonyos állapotokban hívhatók, de a szemantikai helyességet gyakran futásidőben kell validálni.

30.3.2 Nyelvtanok és parser típusok

A külső DSL-ek és a generált parser esetén a központi fogalom a grammar (nyelvtan). Egy grammar formálisan megadja, hogy milyen karaktersorozatok tartoznak a nyelvhez. A leggyakoribb formalizmusok a környezetfüggetlen grammatikák (context-free grammar, CFG) és a parsing expression grammar (PEG). A CFG-t produkciókkal írjuk le, például:

Expr    := Term (('+' | '-') Term)*
Term    := Factor (('*' | '/') Factor)*
Factor  := NUMBER | '(' Expr ')'

Ez a grammar egy egyszerű aritmetikai nyelvet ír le, ahol a NUMBER terminális. A CFG-k esetében a parsernek általában egy lexerre (tokenizerre) és egy parserre van szüksége: a lexer a karaktersorozatot tokenekké alakítja, a parser pedig a tokenekből elemzi a nyelvtant.

A PEG ezzel szemben egy másfajta formalizmus: a választás operátor (/) determinisztikus, a szabályok sorrendben próbálódnak, és az első sikeres ágat választja, backtracking nélkül. Ez azt jelenti, hogy a PEG nem támogatja a balrekurziót, de a parsing idő lineáris lehet (packrat parsing esetén). Egy PEG nyelvtan így nézhet ki:

Expr    <- Term (('+' / '-') Term)*
Term    <- Factor (('*' / '/') Factor)*
Factor  <- NUMBER / '(' Expr ')'

A különbség első ránézésre kicsi, de a PEG determinisztikus választása miatt a nyelvtanírás szabályai eltérnek: a balrekurzió végtelen ciklust okozna, és a választás sorrendje számít.

A parser generátorok ezekből a nyelvtanokból állítanak elő kódot. A legismertebb eszközök:

  • ANTLR (ANother Tool for Language Recognition): Java alapú parser generátor, amely C++ targettel is rendelkezik. A grammar fájlban megadjuk a lexer és parser szabályokat, majd az ANTLR legenerálja a megfelelő C++ osztályokat. A generált parser általában listener és visitor mintát használ az AST feldolgozására. Az ANTLR 4 verziójától a parser a szabályokat rekurzív leszállással hajtja végre, és a hibaüzenetek testreszabhatók. A konkrét C++ API és a generált kód felépítése azonban verziófüggő, ezért használat előtt mindig ellenőrizni kell a hivatalos dokumentációt.
  • PEGTL (Parsing Expression Grammar Template Library): C++17/20 template metaprogramozáson alapuló, header-only könyvtár, amely a PEG formalizmust használja. A grammar szabályokat C++ típusokkal fejezzük ki, így a parser fordítási időben épül fel. Előnye a nulla függőség és a jó fordítási hibakeresés, hátránya a sablonmetaprogramozásból adódó hosszabb fordítási idő.
  • Boost.Spirit: régebbi, de még mindig elterjedt EDSL parser keretrendszer, amely a Boost része. A grammar-t C++ expression template-ekkel írjuk le, és a parser közvetlenül a kódba ágyazódik. A Spirit klasszikus változata (Qi) és a modern X3 változata is elérhető; a X3 tisztább, header-only és C++14/17 kompatibilis.
  • Kézzel írt parser: rekurzív leszállású parser, amelyet a legtöbb esetben egyszerű megírni, és teljes kontrollt ad a hibakezelés és a teljesítmény felett.

A generált parser előnye, hogy a grammar egy helyen van dokumentálva, a parser kódja konzisztens, és a hibakezelés beépített. Hátránya, hogy a generált kód mérete és fordítási ideje megnőhet, a buildelés bonyolultabb, és a generált kód feletti kontroll korlátozottabb. A kézi parser ezzel szemben függőségmentes, de a grammar és a kód szinkronban tartása karbantartási kockázatot jelent.

30.3.3 Kézi parser: rekurzív leszállás

A kézi parser leggyakoribb mintája a rekurzív leszállás (recursive descent). A grammar minden nemterminális szabályához egy-egy metódust írunk, amely a tokenfolyamot fogyasztja, és visszaadja az adott részkifejezés értékét vagy AST csomópontját. A precedencia kezelésére vagy külön szinteket vezetünk be (például parse_expr, parse_term, parse_factor), vagy precedencia-climbing (operátorprecedencia-elemzés) technikát használunk.

A következő példa egy egyszerű aritmetikai kifejezés parser, amely támogatja a +, -, *, / operátorokat, a zárójeleket és a számokat. A parser std::string_view-t használ a bemenet kezelésére, és kivételeket dob, ha hibát talál. A hibakezelés itt szándékosan minimalista, de a laborban majd kibővítjük.

#include <cctype>
#include <iostream>
#include <stdexcept>
#include <string>
#include <string_view>

class Parser {
public:
    explicit Parser(std::string_view input) : input_(input) {}

    auto parse() -> double {
        double result = parse_expr();
        skip_whitespace();
        if (!input_.empty()) {
            throw std::runtime_error("Unexpected trailing input");
        }
        return result;
    }

private:
    std::string_view input_;

    void skip_whitespace() {
        while (!input_.empty() && std::isspace(input_.front())) {
            input_.remove_prefix(1);
        }
    }

    bool consume(char c) {
        skip_whitespace();
        if (!input_.empty() && input_.front() == c) {
            input_.remove_prefix(1);
            return true;
        }
        return false;
    }

    auto parse_number() -> double {
        skip_whitespace();
        std::size_t len = 0;
        while (len < input_.size() && std::isdigit(input_[len])) {
            ++len;
        }
        if (len == 0) {
            throw std::runtime_error("Expected number");
        }
        double value = 0.0;
        for (std::size_t i = 0; i < len; ++i) {
            value = value * 10.0 + (input_[i] - '0');
        }
        input_.remove_prefix(len);
        return value;
    }

    auto parse_factor() -> double {
        skip_whitespace();
        if (consume('(')) {
            double value = parse_expr();
            if (!consume(')')) {
                throw std::runtime_error("Expected ')'");
            }
            return value;
        }
        return parse_number();
    }

    auto parse_term() -> double {
        double value = parse_factor();
        while (true) {
            skip_whitespace();
            if (consume('*')) {
                value *= parse_factor();
            } else if (consume('/')) {
                value /= parse_factor();
            } else {
                break;
            }
        }
        return value;
    }

    auto parse_expr() -> double {
        double value = parse_term();
        while (true) {
            skip_whitespace();
            if (consume('+')) {
                value += parse_term();
            } else if (consume('-')) {
                value -= parse_term();
            } else {
                break;
            }
        }
        return value;
    }
};

Ez a parser a grammar hierarchiáját tükrözi: parse_expr hívja a parse_term-et, az a parse_factor-t. A precedencia a hívási sorrendből adódik: a * és / erősebben köt, mint a + és -. A zárójelek a parse_factor-ban kapnak helyet, így a felhasználó felülbírálhatja a precedenciát.

A kézi parser előnye, hogy nincs külső függőség, a hibakezelés pontosan a kódban van, és a teljesítmény optimalizálható. Hátránya, hogy a grammar változásai könnyen elavulttá teszik a kódot, és a nagyobb nyelvek esetén a parser bonyolultsága gyorsan nő.

30.3.4 Labor: DSL- és parser-vázlat

A labor célja, hogy az olvasó saját kezűleg tapasztalja meg a belső DSL és a kézi parser közötti különbséget, és reprodukálható méréseket végezzen. A feladat egy mini aritmetikai DSL, amely támogatja a négy alapműveletet, a zárójeleket, és egy egyszerű változó-hozzárendelést. A parsert kézzel írjuk, a belső DSL-t pedig expression template-ekkel valósítjuk meg, hogy összehasonlíthassuk a kód olvashatóságát, a fordítási időt és a futási teljesítményt.

30.3.5 Eszközök és build

A laborhoz a következő eszközöket rögzítjük (a konkrét verziók a futtatás időpontjában ellenőrizendők):

  • Fordító: GCC 13 vagy újabb (C++20 támogatással), illetve Clang 17 vagy újabb.
  • Standard: C++20.
  • Build rendszer: CMake 3.25 vagy újabb.
  • Optimalizáció: -O2 -DNDEBUG (release), valamint -O0 -g a debug tesztekhez.
  • Figyelmeztetések: -Wall -Wextra -Wpedantic -Wconversion -Wsign-conversion.
  • Sanitizerek: a tesztfutáshoz AddressSanitizer és UndefinedBehaviorSanitizer (-fsanitize=address,undefined).
  • Statikus elemzés: clang-tidy a modernize-* és performance-* szabályokkal.

A buildparancs például:

cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DCMAKE_CXX_STANDARD=20
cmake --build build --parallel
ctest --test-dir build --output-on-failure

30.3.7 Mérési napló

A mérésekhez a következő paramétereket rögzítjük:

  • Beviteli méret: 10, 100, 1000 és 10000 darab, véletlenszerűen generált, de érvényes kifejezés.
  • Futtatások száma: minden méretnél 1000 ismétlés, majd az átlagos futási idő és a szórás.
  • Fordítási idő: a parser.cpp egyszeri fordítása -O2 szinten, time paranccsal mérve.
  • Bináris méret: a generált futtatható állomány mérete ls -l vagy size paranccsal.
  • Memóriahasználat: /usr/bin/time -v vagy Valgrind Massif használata (opcionális).

A mérési naplóban külön oszlopban szerepel a mért érték és az elvárt érték. Az elvárt érték egy becslés, például lineáris skálázódás a bemenet méretével, vagy a kézi parser esetén a memóriahasználat közel konstans (a rekurzív hívások miatt a verem mérete nő, de a heap allokáció minimális). 30.3.8 Eredmények értelmezése

A várt eredmény: a kézi parser futási ideje lineárisan növekszik a bemenet méretével, mivel minden karaktert egyszer olvas be. A memóriahasználat a bemenet méretétől függetlenül közel állandó, ha nem allokálunk AST csomópontokat, hanem közvetlenül kiértékelünk. A belső DSL expression template esetén a fordítási idő nagyobb lehet a sablonpéldányosítások miatt, de a futási idő összemérhető a kézzel írt kóddal, mivel a template-ek a fordítási időben oldódnak fel. A mérési naplónak ezeket a tendenciákat kell igazolnia vagy cáfolnia.

30.3.9 Gyakori hibák és helyes megoldások

A parser és DSL fejlesztés során számos tipikus hiba fordul elő, amelyeket érdemes előre ismerni.

30.3.9.1 Balrekurzió a grammar-ban

A CFG-k esetén gyakori, hogy a fejlesztő balrekurzív szabályt ír, például:

Expr := Expr '+' Term | Term

Ez a szabály a rekurzív leszállású parserben végtelen ciklust okoz, mert a parse_expr azonnal önmagát hívja anélkül, hogy fogyasztana a tokenfolyamból. A megoldás a grammar átalakítása jobbrekurzív vagy iteratív formára:

Expr := Term (('+' | '-') Term)*

A PEG nyelvekben a balrekurzió eleve nem megengedett, ezért ott a grammar írásakor már a tervezésnél figyelni kell erre.

30.3.9.2 Operátor precedencia helytelen kezelése

A precedencia kezelése akkor hibásodik meg, ha a grammar szintjei nincsenek megfelelően szétválasztva. Például ha a + és a * ugyanabban a szabályban szerepel, akkor a kifejezések rosszul értékelődnek ki. A helyes megoldás a precedenciaszintek szerinti tagolás: a szorzás és osztás egy alacsonyabb szintű szabályban, az összeadás és kivonás egy magasabb szintűben. A fenti kézi parser példa ezt a hierarchiát követi.

30.3.9.3 Tokenizálási hibák

A lexer felelős a bemenet tokenekre bontásáért. Hibát okoz, ha a lexer nem kezeli a whitespace-t, nem ismeri fel a számokat lebegőpontos formában, vagy érvénytelen karaktereket hagy figyelmen kívül. A helyes megoldás a lexer szigorú validálása: minden karaktert fel kell ismerni, és ismeretlen karakter esetén hibát kell dobni. A fenti példában a parse_number csak egész számokat kezel, ezért a laborban ki kell bővíteni a tizedestört és a kitevő kezelésével.

30.3.9.4 A parser állapotának helytelen kezelése

A rekurzív leszállású parserben a pozíciót mindig a bemeneti nézet (std::string_view) módosításával tartjuk nyilván. Ha a parser visszaállítja a pozíciót egy hibás ág után, akkor a backtracking működhet, de a mi determinisztikus parserünk ezt nem teszi. A hibás állapotkezelés tipikus jele, hogy a parser nem fogyasztja a tokeneket, vagy túl sokat fogyaszt. A megoldás a tokenfogyasztás konzisztens szabálya: minden consume hívás pontosan egy tokent fogyaszt, és a pozíciót csak sikeres fogyasztás esetén módosítja.

30.3.9.5 Memóriaszivárgás a generált AST-ben

Ha a parser AST csomópontokat hoz létre, és azokat nyers pointerekkel kezeli, akkor a kivételbiztonság sérülhet, és szivárgás léphet fel. A megoldás a std::unique_ptr és a RAII alkalmazása, vagy az AST építésének elkerülése, ha a parser közvetlenül kiértékeli a kifejezést (mint a fenti példában). A generált parser esetén általában a generált kód már smart pointereket használ, de a saját visitor vagy listener kódban ügyelni kell a tulajdonlásra.

30.3.9.6 Túlzott operátorterhelés a DSL-ben

A belső DSL-eknél csábító, hogy a C++ operátorait olyan jelentéssel ruházzuk fel, amely eltér a megszokottól. Például a | operátor használata a függvénykompozícióra vagy a << operátor használata a streamelésen kívül más műveletre zavaró lehet. A helyes megoldás a konvenciók betartása: az operátorok jelentése legyen összhangban a C++ közösségi elvárásaival, és a DSL dokumentációjában egyértelműen jelezze a túlterhelések szemantikáját.

30.3.9.7 A generált parser hibakeresésének nehézsége

A generált parser kódja gyakran nagy és bonyolult, a hibaüzenetek pedig a generált fájlokra mutatnak, nem a grammarra. A megoldás a grammar szintű tesztelés: a grammarhoz tartozó teszteseteket a generált parseren futtatjuk, és a hibákat a grammar szintjén javítjuk, nem a generált kódban. Az ANTLR például lehetővé teszi a grammar tesztelését a generálás előtt, a PEGTL pedig a C++ típusrendszeren keresztül ad fordítási idejű visszajelzést.

30.3.10 Összefoglalás

Ebben az alfejezetben áttekintettük a beágyazott DSL-ek és a generált parser alapelveit. A belső DSL-ek a C++ szintaxisára építenek, és expression template-ekkel vagy fluent interface-szel valósíthatók meg. A külső DSL-ek grammarral rendelkeznek, amelyből parser generátorok (ANTLR, PEGTL, Boost.Spirit) vagy kézzel írt rekurzív leszállású parser állíthat elő elemző kódot. A kézi parser a legközvetlenebb módja a grammar implementálásának, és teljes kontrollt ad a hibakezelés és a teljesítmény felett. A labor során egy mini aritmetikai DSL-t valósítottunk meg, és reprodukálható méréseket végeztünk. A gyakori hibák – balrekurzió, precedencia, tokenizálás, állapotkezelés, memóriaszivárgás, operátor-túlterhelés – megelőzhetők a fent leírt irányelvek betartásával.
