24.2 Error codes, expected és variant

A 24.1-ben a kivételkezelés a nem várt, gyakran helyreállíthatatlan hibák csatornája volt. Ebben az alfejezetben a hibakezelés másik, a C++-ban legalább annyira fontos oldalát vizsgáljuk: amikor a meghiúsulás a művelet normál szerződésének része, és a hívót arra kényszerítjük, hogy a hibát a visszatérési érték típusában, ne pedig egy külön kivételes úton kezelje.

24.2.1 Várt hiba, értékalapú szerződés

A hibakód- és értékalapú hibakezelés közös kiindulópontja az a felismerés, hogy nem minden hiba váratlan esemény. Ha egy konfigurációs fájl hiányzik, a felhasználó érvénytelen portot adott, vagy egy hálózati peer nem elérhető, az a művelet szintjén gyakran várt állapot. Az ilyen hibákat nem érdemes kivételként kezelni, mert a hívó közvetlenül, determinisztikus költséggel akar dönteni. A visszatérési értékbe ágyazott hiba ezt a döntést a típusrendszer részévé teszi.

A modern C++ két fő eszközt kínál erre:

  • std::error_code: minimális, olcsón másolható hibakód, amely platformfüggő int értéket és egy hibakategória-azonosítót hordoz.
  • std::expected<T,E>: C++23-tól elérhető érték-vagy-hiba tároló, amely monadikus műveletekkel láncolható.

Ezeket gyakran kombináljuk std::expected<T, std::error_code> formában, de a hibatípus lehet saját enum class, std::variant, vagy bármilyen kis, másolható állapot is.

24.2.2 std::error_code és std::error_condition

Az <system_error> fejléc std::error_code típusa két dolgot tárol: egy int value() hibakódot és egy const std::error_category& referenciát. A kategória adja meg a kód értelmezési tartományát, például POSIX errno, Windows rendszerhiba vagy saját alkalmazáshiba.

A std::error_code fontos tulajdonságai:

  • triviálisan másolható, nem foglal dinamikus memóriát, ezért költsége nagyon alacsony;
  • bool konverziója pontosan akkor igaz, ha a hibakód értéke nem nulla, tehát if (ec) { /* hiba */ } jól olvasható;
  • message() szöveges leírást ad, de a szöveget gyakran lokálisan, a kategória message() függvényéből kell előállítani;
  • clear() nullára állítja, és a kategóriát a std::system_category()-ra cseréli.

A C++ szabványos std::filesystem műveletei gyakran két túlterhelést kínálnak: egy dobó és egy nem dobó változatot. A nem dobó változat std::error_code& kimeneti paramétert kap:

std::error_code ec;
auto size = std::filesystem::file_size("missing.cfg", ec);
if (ec) {
    std::cerr << ec.message() << '\n';
}

A nyers hibakódok azonban nem mindig hordozhatók. Ugyanaz a value() más platformon mást jelenthet. A hordozható összehasonlításhoz a szabvány a std::error_condition típust és a std::errc felsorolást adja. A std::error_code std::errc-vel való összehasonlítása a kategória default_error_condition() mechanizmusán keresztül hordozható feltételt képez:

if (ec == std::errc::no_such_file_or_directory) {
    // hiányzó fájl
}

Itt a kód mögött az std::error_category default_error_condition() függvénye dolgozik, amely a platformnatív hibakódot hordozható std::error_condition-né képezi. A std::generic_category() a POSIX errno hordozható kategória, a std::system_category() pedig a platform natív rendszerhibáit jelöli.

24.2.3 Egyéni hibakód-kategória

Saját hibakód-tartomány bevezetéséhez három elemet kell összehangolnunk:

  1. egy enum class hibakódot,
  2. egy std::error_category leszármazottat,
  3. a make_error_code() függvényt és a std::is_error_code_enum specializációt.

Tekintsünk egy konfigurációkezelő hibaterét:

enum class ConfigError {
    missing_file,
    parse_error,
    invalid_value,
    io_error
};

class ConfigErrorCategory final : public std::error_category {
public:
    const char* name() const noexcept override {
        return "config";
    }

    std::string message(int ev) const override {
        switch (static_cast<ConfigError>(ev)) {
        case ConfigError::missing_file:
            return "missing configuration file";
        case ConfigError::parse_error:
            return "cannot parse configuration";
        case ConfigError::invalid_value:
            return "invalid configuration value";
        case ConfigError::io_error:
            return "configuration I/O error";
        default:
            return "unknown config error";
        }
    }

    static const std::error_category& get() {
        static ConfigErrorCategory instance;
        return instance;
    }
};

std::error_code make_error_code(ConfigError e) {
    return {static_cast<int>(e), ConfigErrorCategory::get()};
}

namespace std {
    template<>
    struct is_error_code_enum<ConfigError> : true_type {};
}

A std::is_error_code_enum specializáció engedélyezi, hogy a ConfigError értékből implicit std::error_code keletkezzen:

std::error_code ec = ConfigError::invalid_value;
if (ec == ConfigError::invalid_value) {
    // a kategória és a kód is stimmel
}

A kategóriában soha ne tároljunk változó állapotot. A fenti get() statikus singleton ezért biztonságos: a std::error_category referenciastabilitását a szabvány megköveteli, és a kategória virtuális függvényei tisztán a kód alapján dolgoznak.

24.2.4 std::expected<T,E>: érték vagy hiba

A C++23 <expected> fejlécének std::expected<T,E> típusa egy olyan tároló, amely vagy egy T értéket, vagy egy E hibát tartalmaz. A has_value() tagfüggvény jelzi, hogy melyik állapot aktív. A std::expected nem allergiás a hibára: a hiba tárolása nem foglal külön csatornát, hanem a visszatérési érték részévé válik.

Konstrukció értékkel:

std::expected<Config, ConfigError> result = Config{};

Konstrukció hibával a std::unexpected jelölőt használja:

std::expected<Config, ConfigError> bad =
    std::unexpected{ConfigError::missing_file};

A std::unexpected a C++23 hibatokozó típusa; a std::unexpected{hiba} kifejezésből CTAD következteti az E típust. Ha a fordító régebbi szabványosítási fázisból származik, explicit std::unexpected<ConfigError>{...} is használható.

Az érték elérése:

  • value() hiba állapotban std::bad_expected_access<E> kivételt dob, tehát ellenőrzött, de kivételt használó hozzáférés;
  • operator*() és operator->() csak akkor használható, ha has_value() igaz; hiba állapotban a viselkedés UB, tehát csak akkor szabad hívni, ha a hívó előzőleg ellenőrzött;
  • error() érték állapotban ugyancsak UB, hiba állapotban viszont konstans referenciát ad a tárolt hibára.

Példa egy egyszerű, nem dobó parse-oló függvényre:

std::expected<int, ConfigError> parse_port(std::string_view text) {
    int port{};
    auto [ptr, ec] =
        std::from_chars(text.data(), text.data() + text.size(), port);

    if (ec != std::errc{}) {
        return std::unexpected{ConfigError::parse_error};
    }
    if (ptr != text.data() + text.size() ||
        port < 1 || port > 65535) {
        return std::unexpected{ConfigError::invalid_value};
    }
    return port;
}

A std::expected<void,E> részleges specializáció akkor hasznos, ha a sikernek nincs értéke, csak a hiba hiánya vagy jelenléte:

std::expected<void, ConfigError> save_config(
    const Config& cfg,
    const std::filesystem::path& p)
{
    if (cfg.port == 0) {
        return std::unexpected{ConfigError::invalid_value};
    }
    std::ofstream out(p);
    if (!out) {
        return std::unexpected{ConfigError::io_error};
    }
    out << "name=" << cfg.name
        << "\nport=" << cfg.port << '\n';
    return {};
}

Itt a return {}; sikeres, érték nélküli elvárt eredményt hoz létre.

24.2.5 Monadikus műveletek

A std::expected igazi ereje a monadikus API. Ahelyett, hogy minden hívásnál if (!result) return result; lépéseket írnánk, a hibaterjedést a tároló maga végzi el.

A legfontosabb műveletek:

  • and_then(F): ha hiba van, a hibát változatlanul továbbítja; ha érték van, meghívja F-et az értékkel, és F egy új std::expected-et ad vissza.
  • or_else(F): ha érték van, az értéket tartja; ha hiba van, meghívja F-et a hibával, és a hibakezelő új std::expected-et adhat vissza.
  • transform(F): érték esetén az értéket leképezi, hiba esetén a hibát érintetlenül hagyja.
  • transform_error(F): hiba esetén a hibát leképezi, érték esetén az értéket tartja.
  • value_or(default_value): hiba esetén a megadott alapértelmezést adja.
  • error_or(default_error): érték esetén a megadott alaphibát adja.

A monadikus lánc akkor a leghasznosabb, ha egy több lépésből álló művelet minden rétege std::expected-et ad vissza. Tegyük fel, hogy a konfiguráció betöltése három függvényre bontható:

std::expected<std::string, ConfigError> read_file(
    const std::filesystem::path& p)
{
    std::ifstream in(p);
    if (!in) {
        return std::unexpected{ConfigError::missing_file};
    }

    std::ostringstream ss;
    ss << in.rdbuf();
    if (in.bad()) {
        return std::unexpected{ConfigError::io_error};
    }
    return ss.str();
}

std::expected<Config, ConfigError> parse_config(
    const std::string& text)
{
    // egyszerű "name=...", "port=..." sorok feldolgozása
}

std::expected<Config, ConfigError> validate_config(Config cfg)
{
    if (cfg.port < 1 || cfg.port > 65535) {
        return std::unexpected{ConfigError::invalid_value};
    }
    return cfg;
}

Ezekből a betöltés egyetlen kifejezésben fűzhető fel:

std::expected<Config, ConfigError> load_config(
    const std::filesystem::path& p)
{
    return read_file(p)
        .and_then(parse_config)
        .and_then(validate_config);
}

Ha a fájl hiányzik, a read_file hibát ad, és a parse_config és validate_config hívás elmarad; a hiba változatlanul továbbterjed. Ha a fájl beolvasható, de a tartalom hibás, a parse_config hibája terjed tovább. A kód lineáris olvasású, nincs elágazás a hibakezelésre, és a hibacsatorna a típusból következik.

Az or_else akkor hasznos, ha egy hibából helyreállítás lehetséges:

std::expected<Config, ConfigError> load_config_or_default(
    const std::filesystem::path& p)
{
    return load_config(p).or_else(
        [](ConfigError e) -> std::expected<Config, ConfigError> {
            if (e == ConfigError::missing_file) {
                return Config{};
            }
            return std::unexpected{e};
        });
}

A transform értékleképezésre, a transform_error hibakonverzióra való:

auto port_text = parse_port("8080")
    .transform([](int p) { return p + 1; })
    .transform_error([](ConfigError e) {
        return std::error_code{e};
    });

Itt a második lépésben a hibatípus ConfigError-ról std::error_code-ra változik. A monadikus API tehát nemcsak a vezérlési utat rövidíti, hanem típusbiztos módon alakítja a hibatartományt is.

24.2.6 std::variant szerepe és korlátai

A C++17 óta elérhető std::variant<T,E> is használható érték-vagy-hiba tárolóként. A std::variant előnye, hogy heapmentes, több alternatívát is kezel, és a hibatípus nem különbözik kivételes csatornától. A hibaeset azonban csak konvenció: a típus nem mondja meg, melyik alternatíva a siker és melyik a hiba.

Példa:

std::variant<Connection, std::error_code> connect(
    std::string_view address)
{
    // ...
    return Connection{...};
}

void use_connection() {
    auto r = connect("localhost");
    if (std::holds_alternative<Connection>(r)) {
        auto& conn = std::get<Connection>(r);
        // ...
    } else {
        auto ec = std::get<std::error_code>(r);
        std::cerr << ec.message() << '\n';
    }
}

A std::variant használata hiba- vagy értéktípusokra a következő problémákat veti fel:

  • Nincs beépített and_then/or_else, ezért minden hívásnál kézzel kell vizsgálni a holds_alternative-ot.
  • Ha a hiba- és értéktípus azonos, a típus alapján nem dönthető el az állapot; csak az index() segít.
  • A std::get<T> rossz alternatíva esetén std::bad_variant_access-t dob, ami ismét kivételt visz a várt hiba kezelésébe.
  • A hiba- és értékalternatívák konvenciója idővel kódvizsgálat nélkül feledésbe merül.

Mindez nem jelenti azt, hogy a std::variant rossz eszköz. Akkor érdemes használni, ha a visszatérési értéknek több, egymástól független, nem hiba állapota is van, például egy kapcsolat lehet Connected, Pending vagy Rejected. Ha viszont egyértelmű a siker/meghiúsulás felosztás, a C++23 std::expected jobban kifejezi a szándékot.

24.2.7 Tervezési döntések és tipikus hibák

A hibakód- és értékalapú hibakezelés nem helyettesíti a kivételkezelést, hanem kiegészíti. Az alábbi elvet érdemes követni:

  • Várt hiba, amelyet a hívó kezelni akar: std::expected, std::error_code, std::optional.
  • Váratlan hiba, invariáns-sérülés, programhiba: kivétel, assert, std::contracts (a jövőben).
  • Erőforrás-felszabadítás, tranzakció-visszagörgetés: RAII, kivételbiztonság; az std::expected nem mentesít a destruktorok helyes megírása alól.

A rétegek között hibrid megoldás is kialakítható. Az alsó, nem dobó réteg std::expected-et ad, a felső, kivételt váró réteg pedig a hibát std::system_error-rá alakítja:

template<class T, class E>
T get_or_throw(std::expected<T, E> exp)
{
    if (!exp) {
        throw std::system_error{make_error_code(exp.error())};
    }
    return std::move(exp).value();
}

Ez a híd csak akkor működik, ha make_error_code(E) elérhető, ami a saját ConfigError esetében az egyéni kategória miatt igaz. Az átalakításnál ne feledjük, hogy a kivétel dobása már nem a hibakód-csatorna, hanem a kivételes csatorna része.

Tipikus hibák:

  1. UB az operator* hívással
    A std::expected<T,E>::operator* hiba állapotban UB. Csak akkor használjuk, ha a hívó előzőleg ellenőrizte a has_value()-t, vagy használjuk a value()-t, amely ellenőrzötten dob.

  2. Hiba visszatérése std::unexpected nélkül
    A return ConfigError::parse_error; nem hoz létre std::expected-et. A hiba visszatéréséhez std::unexpected{ConfigError::parse_error} kell.

  3. A hibakód és a kivétel keverése ugyanabban a függvényben
    Ha egy függvény egyes hibajeleit dobja, másokat std::expected-ben adja vissza, a hívó nem tudja eldönteni, melyik csatornát figyelje. A függvény szerződése legyen egyértelműen dobó vagy nem dobó.

  4. A nyers int hibakód hordozhatósági illúziója
    Az int érték kategória nélkül nem hordozható. Ha két különböző kategóriájú std::error_code value()-ját hasonlítjuk össze, hibásan egyezést kaphatunk. Mindig a kategóriával együtt, vagy std::error_condition-nel hasonlítsunk.

  5. A std::variant felcserélt alternatívái
    A std::variant<T,E> konvenciója nem védett. Ha a hívó oldal std::get<T>-t hív, de a tároló éppen E-t tartalmaz, std::bad_variant_access keletkezik. Az std::expected ezt a hibát a típus szintjén kiküszöböli.

  6. A default konstruktor félreértése
    Az std::expected<T,E> default konstruktora, ha T default konstruálható, értéket hoz létre. Ez kényelmes, de hibakeresésnél félrevezető lehet, mert a hiba elmaradása néma. Használjuk tudatosan.

  7. Túl nagy hibatípus
    Az std::expected érték szerint tárolja a hibát. Ha a hibatípus nagy stringet vagy pufferet tartalmaz, a hiba út drágává válik. Ilyenkor a kontextus kerüljön std::shared_ptr-be, vagy használjunk std::error_code-ot a részletek nélkül.

24.2.8 Labor: expected-alapú API tervezése

A labor célja egy nem dobó, monadikus konfigurációbetöltő API megvalósítása és ellenőrzése. A kód C++23-at igényel, mert a std::expected ott standard.

Feladat

  1. Definiáld a ConfigError enum osztályt a fenti értékekkel (missing_file, parse_error, invalid_value, io_error).
  2. Implementáld a ConfigErrorCategory osztályt, a make_error_code() függvényt és a std::is_error_code_enum specializációt.
  3. Írd meg a read_file() függvényt, amely std::expected<std::string, ConfigError>-t ad vissza.
  4. Implementáld a parse_config() függvényt, amely egyszerű "kulcs=érték" sorokból Config-ot épít, és hiba esetén ConfigError::parse_error-t ad.
  5. Add meg a validate_config() függvényt, amely a portot érvényes tartományba ellenőrzi.
  6. A load_config() függvény monadikus lánccal kösse össze a három lépést.
  7. Teszteld a sikeres és a hibás utakat.

A Config struktúra legyen:

struct Config {
    std::string name;
    int port{0};
};

A load_config magja:

std::expected<Config, ConfigError> load_config(
    const std::filesystem::path& p)
{
    return read_file(p)
        .and_then(parse_config)
        .and_then(validate_config);
}

Build és teszt

Egy reprodukálható build parancs GCC 13 vagy újabb, illetve Clang 16 vagy újabb esetén:

g++ -std=c++23 -Wall -Wextra -Wpedantic -Werror \
    -fsanitize=address,undefined -O1 -g \
    resource_lab.cpp -o resource_lab

A labor kódját a fenti kapcsolókkal, majd release módban is fordítsd le. A release buildhez használj -O2 -DNDEBUG kapcsolót, de a hibakereső teszteket a sanitizeres változaton futtasd.

Egyszerű tesztváz:

void run_tests() {
    // hiányzó fájl
    auto missing = load_config("missing.cfg");
    assert(!missing.has_value());
    assert(missing.error() == ConfigError::missing_file);

    // hibás tartalom
    {
        std::ofstream out("bad.cfg");
        out << "name=localhost\nport=invalid\n";
    }
    auto bad = load_config("bad.cfg");
    assert(!bad.has_value());
    assert(bad.error() == ConfigError::parse_error);

    // helyes tartalom
    {
        std::ofstream out("valid.cfg");
        out << "name=localhost\nport=8080\n";
    }
    auto ok = load_config("valid.cfg");
    assert(ok.has_value());
    assert(ok->port == 8080);
    assert(ok->name == "localhost");
}

A value() hibaeseti viselkedését külön ellenőrizd:

bool caught = false;
try {
    (void)bad.value();
} catch (const std::bad_expected_access<ConfigError>& ex) {
    caught = true;
    (void)ex;
}
assert(caught);

Mérési napló

A mérési naplóban a várt és a mért eredményt külön oszlop választja el. A laborban a várt viselkedést ismerjük; a mért értékeket a saját környezetedben rögzítsd. Itt nem közlünk nem reprodukált mérési adatot, csak a napló szerkezetét.

A várt eredmények a nyelvi és API-szerződésből következnek; a mért értékeket a futás után kell beírni. A méréshez használhatsz time parancsot, a bináris mérethez pedig size-et. A benchmark futtatásnál rögzítsd a fordító verzióját, az optimalizációs szintet, a hardvert és az ismétlésszámot.

24.2.9 Önellenőrző kérdés

Miért veszélyesebb a std::expected<T,E>::operator* hiba állapotban való hívása, mint a value() hívása, és milyen kódolási szabállyal kerülhető el a legtöbb hiba?

A válasz lényege: az operator* hiba állapotban UB-t ad, így a hibakereső buildben sem feltétlenül detektálható; a value() ezzel szemben ellenőrzötten dob. A szabály: csak akkor használjunk operator*/operator->-t, ha a hívás előtt ellenőriztük has_value()-t, illetve kritikus kódban preferáljuk a value()-t.

24.2.10 Átvezetés a következő egységhez

A std::expected és az std::error_code a hibát a visszatérési érték szintjére emeli. A következő egység, a 24.3, a szerződésekkel, az assert-tel és a constexpr hibakezeléssel egészíti ki ezt a képet: ott a hiba nemcsak futásidőben, hanem már fordítási időben, a függvény előfeltétele és a típusok szintjén is megjelenik.
