20.2 Object pool és freelist

20.2.1 Bevezetés

Az előző alfejezetben (Memory pool és arena) a nyers memóriakezelés alapjait, a poolok és arénák általános céljait tekintettük át. Most egy konkrét, gyakorlatban is jól használható építőkövet vizsgálunk meg: az objektumpoolt és a hozzá szorosan kapcsolódó free list (szabadlista) mechanizmust. A cél nem csupán egy újabb konténer bemutatása, hanem annak megértése, hogy miként választható szét a nyers memória foglalása és felszabadítása az objektumok tényleges élettartamától. Ez a szétválasztás az, ami lehetővé teszi a gyakori, azonos méretű objektumok allokációjának drasztikus felgyorsítását, valamint a heap fragmentációjának csökkentését.

A fejezet végére képes leszel megtervezni és implementálni egy sablon alapú, fix méretű objektumpoolt, amely intrusive free listet használ. Megismered a tipikus hibákat – például a dupla felszabadítást, az élettartam kezelésének hibáit és a szálbiztonság félreértését –, és megtanulod, hogyan kerüld el ezeket. A laborfeladat során reprodukálható méréssel igazolod, hogy a pool valóban gyorsabb lehet a nyers new/delete párosnál.

20.2.2 Az objektumok újrahasznosításának alapelve

A C++ nyelvben a dinamikus allokáció két, logikailag jól elkülöníthető lépésből áll:

  1. Nyers memória foglalása – ezt a ::operator new vagy egy alacsony szintű allocator végzi. Az eredmény egy megfelelően igazított, de még nem inicializált memóriaterület, amelynek mérete legalább sizeof(T).
  2. Objektum létrehozása – a new kifejezés a nyers memórián meghívja a T konstruktorát (placement new), és visszaad egy T* mutatót.

A delete hasonlóan két lépésre bomlik: először a destruktor fut le, majd a memória visszakerül a szabad tárba.

Egy objektumpool ezt a két fázist explicit módon szétválasztja. A pool előre lefoglal egy nagy, kontiguus memóriablokkot (vagy egy fix méretű tömböt), és ebből oszt ki kisebb, azonos méretű darabokat. Amikor egy objektumra van szükség, a pool egy szabad darabot ad, amelyen a konstruktor lefut. Amikor az objektumra már nincs szükség, a destruktor lefut, de a memória nem kerül vissza az operációs rendszerhez vagy az általános heaphez – a pool újra felveszi a szabad listájára. A memória tehát újrahasznosításra kerül.

Ez a mechanizmus különösen akkor előnyös, ha:

  • sok azonos típusú, rövid élettartamú objektumot hozunk létre és szüntetünk meg;
  • az objektumok létrehozása és megsemmisítése viszonylag olcsó, de a memóriafoglalás/felszabadítás költsége nagy (például a heap lockolása, a szabad listák kezelése);
  • a fragmentáció elkerülése fontos (beágyazott rendszerek, valós idejű alkalmazások);
  • a cache-lokális hozzáférés javítása kívánatos.

Fontos megjegyezni, hogy a pool nem csökkenti a konstruktor és destruktor futási idejét; csupán a memória allokációjának és felszabadításának költségét optimalizálja. Ha a konstruktor maga drága (például hálózati erőforrást foglal), a pool haszna korlátozott lehet.

20.2.3 Free list és intrusive list

A free list a szabad memóriadarabok nyilvántartásának legegyszerűbb módja. Ahelyett, hogy külön konténert (például std::vector-t) tartanánk fenn a szabad pointereknek, a szabad darabok saját memóriájukat használják a lista következő elemének mutatójának tárolására. Ezt nevezzük intrusive list-nek, mert a lista csomópontja be van ágyazva a tárolt elembe, nem külön allokált.

Egy ilyen lista minimális definíciója:

struct FreeNode {
    FreeNode* next;
};

Amikor egy memóriadarab szabad, a területén egy FreeNode objektumot helyezünk el, és a next mutatót a lista következő szabad elemének címére állítjuk. Amikor a darabot kiosztjuk, a FreeNode adat felülíródik a tényleges T objektummal, így a lista mutatója elvész – ezért kell a kiosztás előtt elmenteni a következő pointert.

Az intrusive lista előnyei:

  • Nincs külön memóriafoglalás a listaelemek számára: a mutató a már meglévő, szabad területen tárolódik.
  • Rendkívül gyors beszúrás és törlés: csak pointerek átírása.
  • Nincs cache-miss a lista csomópontjainak eléréséhez a szabad területhez képest, mert a csomópont maga a memóriadarab.

Hátrányai:

  • A szabad darab méretének legalább akkorának kell lennie, mint egy FreeNode mérete (általában egy mutató). Ez a gyakorlatban szinte mindig teljesül sizeof(T) >= sizeof(void*) esetén, de nagyon kicsi típusoknál problémát okozhat.
  • Az intrusive lista nem típusbiztos: a FreeNode és a T típus ugyanazon a memórián osztozik, ezért gondos élettartam-kezelést igényel.
  • A lista csak a szabad elemeket követi, a foglaltakat nem, így nem alkalmas például a pool teljes kihasználtságának naplózására.

20.2.4 Egy fix méretű objektumpool tervezése

A következőkben egy sablon alapú, fix kapacitású objektumpoolt építünk fel. A pool egy std::array-t használ nyers tárolóként, és intrusive free listet kezel. A tároló minden eleme egy Slot struktúra, amely elegendő helyet biztosít egy T objektum számára, és megfelelően igazított:

template <typename T, std::size_t N>
class ObjectPool {
    struct Slot {
        alignas(T) unsigned char storage[sizeof(T)];
    };

    struct FreeNode {
        FreeNode* next;
    };

    std::array<Slot, N> slots_;
    FreeNode* free_head_ = nullptr;

public:
    // ...
};

A Slot struktúra első tagja a storage tömb, amelynek kezdőcíme megegyezik a Slot objektum kezdőcímével, mivel a Slot standard-layout és nincs előtte más tag. Ez a tulajdonság később lehetővé teszi a mutatók közötti biztonságos konverziót.

A konstruktor felépíti a free listet úgy, hogy az összes slotot egymás után láncolja:

ObjectPool() {
    for (auto& slot : slots_) {
        auto* node = reinterpret_cast<FreeNode*>(slot.storage);
        node->next = free_head_;
        free_head_ = node;
    }
}

Itt minden slot kezdetben szabad, ezért a storage területén elhelyezhetünk egy FreeNode-t. A reinterpret_cast azért biztonságos, mert a storage egy unsigned char tömb, amely bármilyen triviális típus tárolására alkalmas, és a FreeNode triviálisan másolható. A FreeNode beírása a memóriába megkezdi annak élettartamát, így a next pointer érvényes lesz.

Az allokáció (objektum létrehozása) a következőképpen történik:

template <typename... Args>
T* allocate(Args&&... args) {
    if (!free_head_) {
        throw std::bad_alloc{};   // vagy egyéni kivétel
    }

    FreeNode* node = free_head_;
    free_head_ = node->next;      // eltávolítjuk a listából

    // A node memóriáján létrehozzuk a T objektumot.
    T* p = ::new (static_cast<void*>(node)) T(std::forward<Args>(args)...);
    return p;
}

Látható, hogy a node pointer a szabad memóriára mutat, amelyet korábban FreeNode-ként használtunk. A placement new segítségével ezen a területen most egy T objektumot hozunk létre. A static_cast<void*>(node) a memória címét adja meg, ahonnan a T konstruktora dolgozhat. A node pointert a továbbiakban nem szabad használni, mert a memórián most már T objektum él.

A felszabadítás (objektum megsemmisítése) két lépésből áll: a destruktor meghívása, majd a memória visszahelyezése a free listre:

void deallocate(T* p) {
    if (!p) return;   // védelem a nullpointer ellen

    p->~T();   // a T objektum élettartamának vége

    // Visszaalakítjuk a Slot pointerét, mivel a p a Slot storage-jára mutat.
    Slot* slot = reinterpret_cast<Slot*>(p);   // lásd alább
    FreeNode* node = reinterpret_cast<FreeNode*>(slot->storage);
    node->next = free_head_;
    free_head_ = node;
}

A reinterpret_cast<Slot*>(p) mögött az a feltevés áll, hogy p pontosan a Slot::storage kezdetére mutat. Ez igaz, mert a placement new-t mindig a slot.storage címére hívtuk. A C++ szabvány szerint a standard-layout struct első tagjának címe megegyezik a struct címével, ezért a storage-ra mutató pointer egyben a Slot-ra mutató pointer is. A reinterpret_cast itt a gyakorlatban minden ismert platformon helyes; a szigorúan szabványos megoldás a static_cast<Slot*>(static_cast<void*>(p)) lenne, de a reinterpret_cast is elfogadott, ha a típusok standard-layoutok. A p destruktor utáni állapotában a memória nyers, így a FreeNode újbóli elhelyezése szabályos.

Fontos: a deallocate nem hívja a delete-et, és nem is adja vissza a memóriát az operációs rendszernek. A memória a pool tulajdonában marad, és készen áll egy újabb allokációra.

20.2.5 Kényelmi interfész okos mutatóval

A nyers allocate/deallocate páros könnyen hibához vezethet: a felhasználónak manuálisan kell ügyelnie arra, hogy minden allokált objektum visszakerüljön a poolba, és hogy a destruktor pontosan egyszer fusson le. Ezt a felelősséget célszerű RAII elvű burkolóba csomagolni. A poolhoz tartozó unique_ptr-szerű osztály a következőképpen nézhet ki:

template <typename T, std::size_t N>
class ObjectPool {
    // ... (korábbi részek)

public:
    template <typename... Args>
    std::unique_ptr<T, void(*)(T*)> make_unique(Args&&... args) {
        T* p = allocate(std::forward<Args>(args)...);
        return {p, [this](T* ptr) { deallocate(ptr); }};
    }
};

Ez a megoldás egy std::unique_ptr-t ad vissza, amelynek egyedi deleterje a pool deallocate függvényét hívja. A lambda elkapja a this pointert, így a pool élettartama alatt használható. Ügyeljünk arra, hogy a pool élettartama fedje le az összes kiadott okos mutató élettartamát; ellenkező esetben a deleter egy megsemmisült poolra mutatna.

A fenti interfész biztosítja, hogy:

  • a konstruktor pontosan egyszer fut le;
  • a destruktor pontosan egyszer fut le;
  • a memória visszakerül a poolba;
  • nincs memóriaszivárgás, még kivétel esetén sem.

20.2.6 Tipikus hibák és elkerülésük

Az objektumpoolok kézi élettartam-kezelése számos buktatót rejt. Az alábbiakban a leggyakoribbakat tekintjük át, és mindegyikhez megadjuk a helyes eljárást.

20.2.7 1. Dupla felszabadítás

Ha ugyanazt a pointert kétszer adjuk át a deallocate-nak, a destruktor kétszer fut le, és a memória kétszer kerül a free listre. Az első visszaadás után a memórián már FreeNode objektum él, így a második p->~T() hívás egy érvénytelen, nem létező T objektum destruktorát próbálja meghívni – ez undefined behavior. A free listbe való kétszeri beszúrás ráadásul ciklust okozhat a listában, ami későbbi allokációk során végtelen ciklushoz vagy memóriahibához vezet.

Megoldás: sose hívjuk a deallocate-ot közvetlenül a felhasználói kódból, ha van RAII burkoló. Ha nyers pointereket adunk ki, dokumentáljuk, hogy a tulajdonosnak pontosan egyszer kell visszaadnia. A fejlesztés során használjunk Asserts-eket: a pool nyilvántarthatja a foglalt elemek számát, és a destruktorban ellenőrizheti, hogy minden vissza lett adva.

20.2.8 2. Use-after-free

A deallokáció után a pointer érvénytelen, de a memória továbbra is a pool tulajdonában van. Ha a régi pointert használjuk, az UB. A hiba különösen alattomos, mert a memória tartalma még nem feltétlenül változott meg, így a kód látszólag működhet.

Megoldás: a RAII burkoló megszűnése után ne tartsunk nyers pointereket. Ha mégis szükséges, állítsuk a pointert nullptr-re a felszabadítás után. Használjunk statikus elemzőt és sanitizereket (lásd a labor részt).

20.2.9 3. Kivételbiztonság hiánya

Ha a T konstruktora kivételt dob, a pool allocate függvénye a memóriát már eltávolította a free listről, de a T nem jött létre. A memória elveszne, hacsak nem gondoskodunk a visszaadásáról.

Megoldás: az allocate függvényben használjunk RAII guardot, amely kivétel esetén visszateszi a memóriát a free listre. Például:

template <typename... Args>
T* allocate(Args&&... args) {
    if (!free_head_) throw std::bad_alloc{};

    FreeNode* node = free_head_;
    free_head_ = node->next;

    struct Guard {
        ObjectPool* pool;
        FreeNode* node;
        ~Guard() {
            if (node) {
                node->next = pool->free_head_;
                pool->free_head_ = node;
            }
        }
    } guard{this, node};

    T* p = ::new (static_cast<void*>(node)) T(std::forward<Args>(args)...);
    guard.node = nullptr;   // sikeres létrehozás, ne adjuk vissza
    return p;
}

Így ha a konstruktor kivételt dob, a guard destruktora automatikusan visszahelyezi a memóriát a listába.

20.2.10 4. Alignment problémák

Ha a tároló nincs megfelelően igazítva a T típushoz, a placement new UB-hez vezet. A alignas(T) használata a Slot::storage deklarációjában garantálja a helyes igazítást. Emellett a sizeof(T) méretű tároló elegendő, mert a Slot nem tartalmaz más tagot.

20.2.11 5. Szálbiztonság félreértése

Az alap objektumpool nem szálbiztos. Ha két szál egyszerre hívja az allocate-ot vagy a deallocate-ot ugyanazon a poolon, adatverseny alakul ki a free_head_ mutatón és a szabad elemek next pointerein. A szálbiztos működéshez külső zárat (például std::mutex) kell alkalmazni, vagy szálankénti poolt kell használni (lásd a következő szakaszt).

20.2.12 Thread-local pool

Sok alkalmazásban az objektumokat ugyanaz a szál hozza létre és szünteti meg, amelyik használja. Ilyenkor a pool szintű szinkronizáció felesleges, sőt rontja a teljesítményt. A thread-local pool kihasználja, hogy minden szál saját, független példányt kap, így az allokációk és felszabadítások lock nélkül végrehajthatók.

C++-ban ezt a thread_local kulcsszóval érhetjük el:

thread_local ObjectPool<Widget, 64> widget_pool;

void worker() {
    auto w = widget_pool.make_unique(/* konstruktor argumentumok */);
    // használat...
} // a w destruktora visszaadja a poolnak

A thread_local változó minden szálban külön példányban létezik, és a szál kilépésekor automatikusan megsemmisül. A pool destruktorának ilyenkor ellenőriznie kell, hogy minden objektum vissza lett-e adva; ha nem, az hibát jelez (például assert).

A thread-local pool előnyei:

  • Nincs szinkronizációs költség.
  • Jobb cache-lokalitás: a szál által használt memória valószínűleg ugyanazon a NUMA-nódon vagy cache-vonalon marad.
  • Egyszerű implementáció: nem kell szálbiztosítani a poolt.

Hátrányai és megfontolások:

  • Ha egy szálon létrehozott objektumot egy másik szálon szabadítunk fel, az a másik szál pooljában érvénytelen pointerhez vezet – a pointer nem arra a poolra mutat, amelyikből származik. Ezért a thread-local pool csak akkor használható, ha a szálak közötti átadás nem történik, vagy ha az átadást explicit módon kezeljük (például üzenetsorral visszairányítjuk a tulajdonos szálra).
  • A thread-local változók növelik a szálankénti memóriaigényt, és a szálak létrehozásakor a konstruktoruk lefut, ami némi indítási költséget jelenthet.
  • Ha a szál hosszú élettartamú, és a pool mérete nem elegendő, a pool kifulladhat; ilyenkor vagy nagyobb N-t választunk, vagy visszaesünk egy globális, zárolt poolra.

A gyakorlatban gyakran kombinálják a thread-local poolt egy globális, mutexszel védett fallback pool-lal. Ha a lokális pool üres, a szál a globálisból kér memóriát; ha a lokális pool túl sok szabad elemet halmoz fel, néhányat visszaad a globálisnak. Ez a minta részletesebben a következő alfejezetben (Fragmentáció és allokációs stratégiák) kerül elő.

20.2.13 A pool használatának gyakorlati példája

A következő kód egy teljes, működő példát mutat be: definiál egy Widget struktúrát, létrehoz egy ObjectPool<Widget, 8> példányt, majd RAII okos mutatókkal allokál és szabadít fel objektumokat.

#include <array>
#include <cstddef>
#include <memory>
#include <new>
#include <stdexcept>
#include <utility>
#include <cassert>

template <typename T, std::size_t N>
class ObjectPool {
    struct Slot {
        alignas(T) unsigned char storage[sizeof(T)];
    };

    struct FreeNode {
        FreeNode* next;
    };

    std::array<Slot, N> slots_;
    FreeNode* free_head_ = nullptr;
    std::size_t allocated_count_ = 0;   // diagnosztikai célra

public:
    ObjectPool() {
        for (auto& slot : slots_) {
            auto* node = reinterpret_cast<FreeNode*>(slot.storage);
            node->next = free_head_;
            free_head_ = node;
        }
    }

    ~ObjectPool() {
        // A destruktorban ellenőrizzük, hogy minden objektum vissza lett adva.
        assert(allocated_count_ == 0 && "ObjectPool destroyed with live objects");
    }

    ObjectPool(const ObjectPool&) = delete;
    ObjectPool& operator=(const ObjectPool&) = delete;

    template <typename... Args>
    T* allocate(Args&&... args) {
        if (!free_head_) {
            throw std::bad_alloc{};
        }

        FreeNode* node = free_head_;
        free_head_ = node->next;

        struct Guard {
            ObjectPool* pool;
            FreeNode* node;
            bool dismissed = false;
            ~Guard() {
                if (!dismissed) {
                    node->next = pool->free_head_;
                    pool->free_head_ = node;
                }
            }
        } guard{this, node};

        T* p = ::new (static_cast<void*>(node)) T(std::forward<Args>(args)...);
        guard.dismissed = true;
        ++allocated_count_;
        return p;
    }

    void deallocate(T* p) {
        if (!p) return;

        p->~T();
        --allocated_count_;

        Slot* slot = reinterpret_cast<Slot*>(p);
        FreeNode* node = reinterpret_cast<FreeNode*>(slot->storage);
        node->next = free_head_;
        free_head_ = node;
    }

    template <typename... Args>
    std::unique_ptr<T, void(*)(T*)> make_unique(Args&&... args) {
        T* p = allocate(std::forward<Args>(args)...);
        return {p, [this](T* ptr) { deallocate(ptr); }};
    }

    std::size_t capacity() const noexcept { return N; }
    std::size_t allocated() const noexcept { return allocated_count_; }
};

struct Widget {
    int id;
    double value;

    Widget(int i, double v) : id(i), value(v) {}
};

int main() {
    ObjectPool<Widget, 4> pool;

    {
        auto w1 = pool.make_unique(1, 1.5);
        auto w2 = pool.make_unique(2, 2.5);
        assert(pool.allocated() == 2);

        // w1 és w2 itt automatikusan visszakerül a poolba.
    }

    assert(pool.allocated() == 0);

    // A pool újra felhasználja ugyanazt a memóriát.
    auto w3 = pool.make_unique(3, 3.5);
    assert(pool.allocated() == 1);

    return 0;
}

A kódban látható, hogy a pool kapacitása 4, de csak annyi objektumot hozunk létre, amennyi éppen szükséges. A make_unique által visszaadott std::unique_ptr garantálja, hogy a destruktor pontosan akkor fut le, amikor a mutató kimegy a hatókörből, és a memória visszakerül a poolba.

20.2.14 Labor: object pool és freelist tervezése, mérése

A labor célja, hogy a fenti elveket egy konkrét, reprodukálható környezetben alkalmazd, és méréssel igazold a pool előnyeit a hagyományos new/delete-hez képest.

20.2.15 Feladatleírás

  1. Implementálj egy ObjectPool<T, N> osztályt a fent bemutatott elvek alapján. Az osztály:

    • intrusive free listet használjon;
    • biztosítson allocate és deallocate műveleteket;
    • legyen kivételbiztos a konstruktor kivétele esetén;
    • tartalmazzon egy make_unique interfészt RAII-hoz.

  2. Készíts egy benchmark programot, amely összehasonlítja a pool és a new/delete sebességét azonos számú allokáció és felszabadítás esetén. Például hozz létre 100 000 azonos típusú objektumot, mindegyiket azonnal szabadítsd fel, és mérd az eltelt időt. Ismételd meg a mérést legalább 5-ször, és számíts átlagot, szórást.

  3. Ellenőrizd a pool helyességét:

    • Fordítsd le -Wall -Wextra -pedantic kapcsolókkal, és győződj meg arról, hogy nincs figyelmeztetés.

    • Futtasd a tesztet AddressSanitizer és UndefinedBehaviorSanitizer alatt:

      g++ -std=c++20 -O1 -g -fsanitize=address,undefined -fno-omit-frame-pointer -o pool_test pool_test.cpp
./pool_test

    • Írj néhány egységtesztet (például: kapacitás túllépése kivételt dob; a make_unique után a memória visszakerül; a destruktor nem szivárog).

  4. Rögzítsd a mérési naplót a következő adatokkal:

    • fordítási környezet (fordító, verzió, standard, optimalizációs szint);
    • hardver (CPU, RAM, operációs rendszer);
    • a benchmark futtatások eredményei (időtartamok, átlag, szórás);
    • a mért és a várt eredmények elkülönítve.

20.2.17 Példa benchmark váz

#include <chrono>
#include <iostream>
#include <memory>

// Az ObjectPool definíciója itt...

struct TestObject {
    int a;
    double b;
    char c;
    TestObject(int _a, double _b, char _c) : a(_a), b(_b), c(_c) {}
};

constexpr std::size_t kIterations = 100000;

double measure_new_delete() {
    auto start = std::chrono::high_resolution_clock::now();
    for (std::size_t i = 0; i < kIterations; ++i) {
        TestObject* obj = new TestObject(1, 2.0, 'x');
        delete obj;
    }
    auto end = std::chrono::high_resolution_clock::now();
    return std::chrono::duration<double, std::micro>(end - start).count();
}

double measure_pool(ObjectPool<TestObject, 1024>& pool) {
    auto start = std::chrono::high_resolution_clock::now();
    for (std::size_t i = 0; i < kIterations; ++i) {
        auto obj = pool.make_unique(1, 2.0, 'x');
        // a destruktor automatikusan visszaadja a poolnak
    }
    auto end = std::chrono::high_resolution_clock::now();
    return std::chrono::duration<double, std::micro>(end - start).count();
}

int main() {
    ObjectPool<TestObject, 1024> pool;
    // ...
    // Futtatások, átlagolás, kiírás
}

A mérési naplóban tüntesd fel, hogy a pool kapacitása (1024) elegendő-e a maximális egyidejű objektumszámhoz; ha nem, a pool kifullad, és kivételt dob, ami torzítja a mérést.

20.2.18 Várt eredmény

A pool esetén azt várjuk, hogy az allokáció/deallokáció gyorsabb lesz, mint a new/delete, mert a pool nem végez heap-hívást minden egyes alkalommal. A különbség mértéke függ a hardvertől, a heap implementációjától és a konstruktor/destruktor költségétől. Egyszerű, triviális konstruktorú típusnál a pool akár 5–10-szeres gyorsulást is mutathat, de ha a konstruktor drága, az arány kisebb. A mért és a várt értéket mindig külön dokumentáld.

Ebben az alfejezetben megismerkedtünk az objektumpoolok és a free listek alapelveivel.
