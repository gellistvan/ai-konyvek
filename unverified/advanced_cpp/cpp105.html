27.4 Policy-based design és metaprogramming patterns

A policy-based design (politika-alapú tervezés) olyan C++-tervezési minta, amely a viselkedést apró, jól definiált interfésszel rendelkező osztályokra – úgynevezett politikákra (policy) – bontja, és ezeket a hosztosztály template paramétereként adja át. A cél a fordítási idejű, statikus polimorfizmus: a konkrét viselkedés kiválasztása a sablonpéldányosításkor történik, így nincs virtuális hívásból adódó futási költség, a fordító pedig képes az egész rendszert optimalizálni. A minta Alexadrescu Modern C++ Design című könyvéből vált ismertté, és azóta is a C++ sablonmeta-programozás egyik alappillére.

A politika nem más, mint egy osztály vagy struktúra, amely egyetlen, szűk felelősségi kört valósít meg, és statikus tagfüggvényeken vagy típusdefiníciókon keresztül kommunikál. A hosztosztály ezeket a politikákat használja, de nem követeli meg tőlük, hogy egy közös alaposztályból származzanak; elég, ha az elvárt interfészt teljesítik. Ez a „duck typing” a sablonok világában: ha a politika rendelkezik a szükséges műveletekkel, akkor használható.

Vegyünk egy egyszerű példát: egy naplózó komponens, amelynek a kimeneti célját politikaként adjuk meg. A ConsoleLogger és a FileLogger egyaránt rendelkezik egy log statikus tagfüggvénnyel, a hosztosztály pedig ezt hívja:

struct ConsoleLogger {
    static void log(std::string_view msg) {
        std::cout << msg << '\n';
    }
};

struct NullLogger {
    static void log(std::string_view) noexcept {}
};

template <typename LoggerPolicy>
class Service {
public:
    void do_work() {
        // ...
        LoggerPolicy::log("work done");
    }
};

Service<ConsoleLogger> s1;
Service<NullLogger> s2;

Itt a Service viselkedése a LoggerPolicy cseréjével módosul, anélkül hogy a Service forráskódját érintenénk. A NullLogger üres implementációja lehetővé teszi, hogy a naplózást teljesen kiiktassuk – a fordító valószínűleg eltávolítja a hívást, így nulla futási költséggel.

A politika-alapú tervezés előnyei:

  • Rugalmasság: ugyanaz a hosztosztály sokféle kombinációban példányosítható.
  • Teljesítmény: nincs virtuális függvényhívás, a fordító inline-olhat, a konstans kifejezések fordítási időben kiértékelhetők.
  • Kódújrafelhasználás: a politikák önállóan tesztelhetők és más komponensekben is használhatók.

Hátrányai közé tartozik a megnövekedett fordítási idő, a nagyobb bináris méret (minden kombináció külön kódot generál), valamint a hibaüzenetek nehézkessége, ha a politika nem teljesíti az elvárt interfészt. A C++20 concepts ezen a téren jelentős javulást hoz.

27.4.1 Policy, mixin és tag dispatch

A politikát gyakran összekeverik két másik sablontechnikával: a mixinnel és a tag dispatch-csel. Bár mindhárom a statikus polimorfizmus eszköze, eltérő szerepet töltenek be.

  • Policy: template paraméterként átadott, jellemzően statikus interfésszel rendelkező osztály. A hosztosztály nem örökli a politikát, hanem meghívja annak tagfüggvényeit. A politika önálló, nem függ a hosztosztály típusától.

  • Mixin: olyan osztálysablon, amely a hosztosztályt öröklés útján egészíti ki funkcionalitással. Gyakran CRTP-t (Curiously Recurring Template Pattern) használ, hogy a származtatott osztály típusát elérje. A mixin a hosztosztály részeként viselkedik, és közvetlenül hozzáfér annak védett tagjaihoz. Például egy EnableSharedFromThis<T> vagy egy NonCopyable mixin. A mixin nem cserélhető olyan egyszerűen, mint egy policy, mert az öröklési hierarchiába épül be, de alkalmas arra, hogy keresztmetszeti funkciókat adjon hozzá.

  • Tag dispatch: egy függvény túlterhelésének kiválasztása egy típuscímke (tag) alapján. A policy-alapú kódban gyakran használjuk arra, hogy a politika típusától függően más-más implementációt válasszunk. A tag dispatch a std::true_type/std::false_type vagy egyéni üres struktúrák segítségével történik. C++17 óta sok esetben if constexpr-rel helyettesíthető, de a tag dispatch továbbra is fontos, amikor a kiválasztást függvénytúlterhelésre bízzuk, nem pedig elágazásra.

Nézzünk egy példát mindháromra. Tegyük fel, hogy egy konténer memóriafoglalási stratégiáját szeretnénk testreszabni.

// Politikák
struct MallocAlloc {
    template <typename T>
    static T* allocate(std::size_t n) {
        return static_cast<T*>(::operator new(n * sizeof(T)));
    }
    template <typename T>
    static void deallocate(T* p, std::size_t) noexcept {
        ::operator delete(p);
    }
};

struct PoolAlloc {
    // egyszerűsített pool, a lényeg az interfész
    template <typename T>
    static T* allocate(std::size_t n) {
        // valós poolból foglal
        return static_cast<T*>(::operator new(n * sizeof(T)));
    }
    template <typename T>
    static void deallocate(T* p, std::size_t) noexcept {
        ::operator delete(p);
    }
};

// Mixin: nem másolható képesség
template <typename Derived>
class NonCopyable {
protected:
    NonCopyable() = default;
    ~NonCopyable() = default;
    NonCopyable(const NonCopyable&) = delete;
    NonCopyable& operator=(const NonCopyable&) = delete;
};

// Tag dispatch: a foglalás típusától függően más-más inicializálás
struct init_zero {};
struct init_default {};

template <typename T>
void initialize_memory(T* p, std::size_t n, init_zero) {
    std::memset(p, 0, n * sizeof(T));
}
template <typename T>
void initialize_memory(T* p, std::size_t n, init_default) {
    for (std::size_t i = 0; i < n; ++i) new (p + i) T{};
}

// Hosztosztály
template <typename T, typename AllocPolicy = MallocAlloc>
class Buffer : private NonCopyable<Buffer<T, AllocPolicy>> {
    T* data_ = nullptr;
    std::size_t size_ = 0;
    std::size_t capacity_ = 0;

    void ensure_capacity(std::size_t needed) {
        if (needed <= capacity_) return;
        std::size_t new_cap = std::max(needed, capacity_ * 2);
        T* new_data = AllocPolicy::template allocate<T>(new_cap);
        for (std::size_t i = 0; i < size_; ++i) {
            new (new_data + i) T(std::move(data_[i]));
            data_[i].~T();
        }
        if (data_) AllocPolicy::template deallocate<T>(data_, capacity_);
        data_ = new_data;
        capacity_ = new_cap;
    }

public:
    void push_back(const T& value) {
        ensure_capacity(size_ + 1);
        new (data_ + size_) T(value);
        ++size_;
    }
    // ...
};

Itt a Buffer hosztosztály a NonCopyable mixint használja, hogy letiltsa a másolást, a MallocAlloc politikát pedig a memóriafoglaláshoz. A initialize_memory függvény tag dispatch segítségével választ az inicializálási módok között – a policy vagy a hosztosztály dönthet arról, hogy melyik tag-et adja át.

27.4.2 Metaprogramming patterns

A policy-alapú tervezés szoros kapcsolatban áll a sablonmeta-programozás (TMP) eszköztárával. A gyakorlatban a következő mintákat érdemes ismerni és alkalmazni:

27.4.2.1 std::conditional_t és típusválasztás

Ha egy politika típusától függően más típust szeretnénk definiálni, a std::conditional_t hasznos. Például egy Buffer esetén a belső méret típusa lehet std::size_t vagy std::uint32_t a policy alapján:

template <typename SizePolicy>
using size_type = std::conditional_t<SizePolicy::is_fixed, std::uint32_t, std::size_t>;

27.4.2.2 if constexpr

C++17-től az if constexpr sok esetben átláthatóbbá teszi a fordítási idejű elágazást. Korábban ehhez tag dispatch-re vagy SFINAE-re volt szükség. A politika egy static constexpr logikai értéke alapján választhatunk implementációt:

template <typename AllocPolicy, typename T>
T* allocate_memory(std::size_t n) {
    if constexpr (AllocPolicy::is_pool) {
        return PoolAllocator<T>::allocate(n);
    } else {
        return MallocAllocator<T>::allocate(n);
    }
}

27.4.2.3 requires és concepts

A C++20 concepts lehetővé teszi, hogy a hosztosztály fordítási időben ellenőrizze a politika interfészét, és érthető hibát adjon, ha a követelmény nem teljesül. Ez drámaian javítja a hibaüzenetek minőségét. Például:

template <typename P, typename T>
concept AllocPolicy = requires(P, std::size_t n) {
    { P::template allocate<T>(n) } -> std::same_as<T*>;
    P::template deallocate<T>(static_cast<T*>(nullptr), n);
};

template <typename T, typename Alloc>
    requires AllocPolicy<Alloc, T>
class Buffer {
    // ...
};

Ha a Buffer-t olyan politikával példányosítjuk, amely nem teljesíti a AllocPolicy conceptet, a fordító már a template definíciójának helyén jelzi a hibát, nem pedig a mélyen a sablon belsejében.

27.4.2.4 Type list és policy kombinálás

Bonyolultabb rendszerekben a politikákat gyakran egy típuslistában (std::tuple vagy saját TypeList) tárolják, és a hosztosztály ezen iterál végig. Ez lehetővé teszi változó számú, egymástól független mixin hozzáadását. Például:

template <typename... Policies>
class Service : public Policies... {
    // ...
};

Ez a variadic mixin minta: minden policy egy-egy funkcionalitást ad a Service-hez, és a using Policies::... deklarációval hozzuk be a tagfüggvényeket. A std::tuple-alapú megközelítésnél a politikákat egy std::tuple<Policies...> tag tárolja, és std::get segítségével érjük el őket.

27.4.2.5 Metafüggvények és type traits

A policy-k gyakran definiálnak típusokat vagy konstansokat, amelyeket a hosztosztály metafüggvényekkel olvas le. Például egy AllocPolicy definiálhatja a pointer típust:

template <typename T>
struct MallocAlloc {
    using pointer = T*;
    // ...
};

template <typename T, typename Alloc>
class Buffer {
    using pointer = typename Alloc::template pointer<T>;
    // ...
};

A std::void_t és a detection idiom segítségével ellenőrizhetjük, hogy egy politika rendelkezik-e egy adott típusdefinícióval vagy tagfüggvénnyel, és ennek alapján választhatunk implementációt.

27.4.3 Labor: policy-based komponens tervezése

A fejezet laborjának célja egy olyan dynamic_array osztály megvalósítása, amely három független politikát használ:

  1. AllocPolicy – a memóriafoglalás módja (MallocAllocator vagy PoolAllocator).
  2. GrowthPolicy – a kapacitás növelésének stratégiája (DoubleGrowth vagy FixedIncrement).
  3. ThreadSafetyPolicy – a szálbiztosság kezelése (SingleThreaded vagy MutexProtected).

A komponensnek fordíthatónak kell lennie C++20 szabvány szerint, conceptekkel ellenőrzött politikákkal. A labor része a reprodukálható build, a tesztelés és a teljesítménymérés.

27.4.3.1 A komponens interfésze

A dynamic_array sablonparaméterei:

template <typename T,
          typename Alloc = MallocAllocator,
          typename Growth = DoubleGrowth,
          typename ThreadSafety = SingleThreaded>
    requires IsAllocPolicy<Alloc, T> &&
             IsGrowthPolicy<Growth> &&
             IsThreadSafetyPolicy<ThreadSafety>
class dynamic_array;

A dynamic_array a következő műveleteket támogatja:

  • push_back(const T&) és push_back(T&&)
  • size(), capacity()
  • operator[] (konstans és nem konstans)
  • destruktor, amely felszabadítja a memóriát és meghívja az elemek destruktorát
  • a másoló konstruktor és értékadás törölve (a labor egyszerűsítése miatt), a mozgató műveletek alapértelmezettek vagy egyszerűen implementáltak

A politikák definíciója:

// Allocator politikák
struct MallocAllocator {
    template <typename T>
    static T* allocate(std::size_t n) {
        if (n == 0) return nullptr;
        if (auto p = std::malloc(n * sizeof(T))) {
            return static_cast<T*>(p);
        }
        throw std::bad_alloc{};
    }

    template <typename T>
    static void deallocate(T* p, std::size_t) noexcept {
        std::free(p);
    }
};

struct PoolAllocator {
    // Nagyon egyszerű, nem túl hatékony pool, csak demonstrációra.
    // Valós rendszerben arena-alapú, előre lefoglalt memóriát használna.
    template <typename T>
    static T* allocate(std::size_t n) {
        if (n == 0) return nullptr;
        if (auto p = std::malloc(n * sizeof(T))) {
            return static_cast<T*>(p);
        }
        throw std::bad_alloc{};
    }

    template <typename T>
    static void deallocate(T* p, std::size_t) noexcept {
        std::free(p);
    }
};

// Növekedési politikák
struct DoubleGrowth {
    static std::size_t new_capacity(std::size_t current, std::size_t needed) {
        std::size_t new_cap = (current == 0) ? 1 : current * 2;
        while (new_cap < needed) new_cap *= 2;
        return new_cap;
    }
};

struct FixedIncrement {
    static std::size_t new_capacity(std::size_t current, std::size_t needed) {
        constexpr std::size_t increment = 1024;
        if (needed <= current) return current;
        return ((needed + increment - 1) / increment) * increment;
    }
};

// Szálbiztonsági politikák
struct SingleThreaded {
    void lock() noexcept {}
    void unlock() noexcept {}
};

struct MutexProtected {
    std::mutex mtx;
    void lock() { mtx.lock(); }
    void unlock() { mtx.unlock(); }
};

A conceptek:

template <typename P, typename T>
concept IsAllocPolicy = requires(P, std::size_t n) {
    { P::template allocate<T>(n) } -> std::same_as<T*>;
    P::template deallocate<T>(static_cast<T*>(nullptr), n);
};

template <typename P>
concept IsGrowthPolicy = requires(P, std::size_t current, std::size_t needed) {
    { P::new_capacity(current, needed) } -> std::convertible_to<std::size_t>;
};

template <typename P>
concept IsThreadSafetyPolicy = requires(P p) {
    p.lock();
    p.unlock();
};

A dynamic_array osztály vázlata:

template <typename T, typename Alloc, typename Growth, typename ThreadSafety>
    requires IsAllocPolicy<Alloc, T> &&
             IsGrowthPolicy<Growth> &&
             IsThreadSafetyPolicy<ThreadSafety>
class dynamic_array {
public:
    using value_type = T;
    using allocator_policy = Alloc;
    using growth_policy = Growth;
    using thread_safety_policy = ThreadSafety;

private:
    T* data_ = nullptr;
    std::size_t size_ = 0;
    std::size_t capacity_ = 0;
    ThreadSafety guard_;

    void ensure_capacity(std::size_t needed) {
        if (needed <= capacity_) return;
        std::size_t new_cap = Growth::new_capacity(capacity_, needed);
        T* new_data = Alloc::template allocate<T>(new_cap);
        for (std::size_t i = 0; i < size_; ++i) {
            new (new_data + i) T(std::move(data_[i]));
            data_[i].~T();
        }
        if (data_) Alloc::template deallocate<T>(data_, capacity_);
        data_ = new_data;
        capacity_ = new_cap;
    }

public:
    dynamic_array() = default;

    ~dynamic_array() {
        for (std::size_t i = 0; i < size_; ++i) {
            data_[i].~T();
        }
        if (data_) Alloc::template deallocate<T>(data_, capacity_);
    }

    dynamic_array(const dynamic_array&) = delete;
    dynamic_array& operator=(const dynamic_array&) = delete;

    dynamic_array(dynamic_array&& other) noexcept
        : data_(std::exchange(other.data_, nullptr)),
          size_(std::exchange(other.size_, 0)),
          capacity_(std::exchange(other.capacity_, 0)),
          guard_(std::move(other.guard_)) {}

    dynamic_array& operator=(dynamic_array&& other) noexcept {
        if (this == &other) return *this;
        for (std::size_t i = 0; i < size_; ++i) data_[i].~T();
        if (data_) Alloc::template deallocate<T>(data_, capacity_);
        data_ = std::exchange(other.data_, nullptr);
        size_ = std::exchange(other.size_, 0);
        capacity_ = std::exchange(other.capacity_, 0);
        return *this;
    }

    void push_back(const T& value) {
        std::lock_guard<ThreadSafety> lock(guard_);
        ensure_capacity(size_ + 1);
        new (data_ + size_) T(value);
        ++size_;
    }

    void push_back(T&& value) {
        std::lock_guard<ThreadSafety> lock(guard_);
        ensure_capacity(size_ + 1);
        new (data_ + size_) T(std::move(value));
        ++size_;
    }

    std::size_t size() const noexcept { return size_; }
    std::size_t capacity() const noexcept { return capacity_; }

    T& operator[](std::size_t i)              { return data_[i]; }
    const T& operator[](std::size_t i) const  { return data_[i]; }
};

A std::lock_guard<ThreadSafety> a ThreadSafety típusú guard_ tagot zárja. Mivel a SingleThreaded lock()/unlock() függvényei noexcept és üresek, a std::lock_guard példányosítása itt eltávolítható, így a szálbiztos változat sem jár overheaddel.

        std::lock_guard<ThreadSafety> lock(guard_);
        ensure_capacity(size_ + 1);
        new (data_ + size_) T(std::move(value));
        ++size_;
    }

    std::size_t size() const noexcept { return size_; }
    std::size_t capacity() const noexcept { return capacity_; }

    T& operator[](std::size_t i)              { return data_[i]; }
    const T& operator[](std::size_t i) const  { return data_[i]; }
};

int main() {
    // Teszt: int elemekkel
    {
        dynamic_array<int> arr;
        assert(arr.size() == 0);
        for (int i = 0; i < 1000; ++i) {
            arr.push_back(i);
        }
        assert(arr.size() == 1000);
        for (int i = 0; i < 1000; ++i) {
            assert(arr[i] == i);
        }
        std::cout << "int teszt ok\n";
    }

    // Teszt: std::string elemekkel (nem triviális destruktor)
    {
        dynamic_array<std::string> arr;
        arr.push_back("hello");
        arr.push_back("world");
        assert(arr.size() == 2);
        assert(arr[0] == "hello");
        assert(arr[1] == "world");
        std::cout << "string teszt ok\n";
    }

    // Teszt: mutexes politika
    {
        dynamic_array<int, MallocAllocator, DoubleGrowth, MutexProtected> arr;
        for (int i = 0; i < 100; ++i) arr.push_back(i);
        assert(arr.size() == 100);
        std::cout << "mutex teszt ok\n";
    }

    // Egyszerű benchmark
    constexpr std::size_t N = 1'000'000;
    auto start = std::chrono::steady_clock::now();
    {
        dynamic_array<int> arr;
        for (std::size_t i = 0; i < N; ++i) arr.push_back(static_cast<int>(i));
    }
    auto end = std::chrono::steady_clock::now();
    auto elapsed = std::chrono::duration_cast<std::chrono::milliseconds>(end - start).count();
    std::cout << "single_threaded double_growth: " << elapsed << " ms\n";

    start = std::chrono::steady_clock::now();
    {
        dynamic_array<int, MallocAllocator, FixedIncrement> arr;
        for (std::size_t i = 0; i < N; ++i) arr.push_back(static_cast<int>(i));
    }
    end = std::chrono::steady_clock::now();
    elapsed = std::chrono::duration_cast<std::chrono::milliseconds>(end - start).count();
    std::cout << "single_threaded fixed_increment: " << elapsed << " ms\n";

    start = std::chrono::steady_clock::now();
    {
        dynamic_array<int, MallocAllocator, DoubleGrowth, MutexProtected> arr;
        for (std::size_t i = 0; i < N; ++i) arr.push_back(static_cast<int>(i));
    }
    end = std::chrono::steady_clock::now();
    elapsed = std::chrono::duration_cast<std::chrono::milliseconds>(end - start).count();
    std::cout << "mutex double_growth: " << elapsed << " ms\n";

    return 0;
}

A tesztprogramot -fsanitize=address,undefined kapcsolóval futtatva a memóriakezelési hibák és az undefined behavior egy része is kiderül. A labor elvárása, hogy a tesztprogram hiba nélkül lefusson.

27.4.4 Gyakori hibák és elkerülésük

A policy-alapú tervezés során számos csapdába eshetünk. A leggyakoribbak:

  1. Nem dokumentált policy interfész. Ha a hosztosztály elvárja, hogy a politika rendelkezzen egy adott tagfüggvénnyel, de ezt nem írjuk le, a felhasználó csak a sablonhibákból találja ki. Megoldás: conceptek használata, amelyek formálisan definiálják az interfészt, és a hibát a template definíciójának helyén jelzik.

  2. Túl sok policy paraméter. Ha egy osztály nyolc különböző politikát igényel, a példányosítás nehézkessé válik. Ilyenkor érdemes a politikákat egyetlen konfigurációs struktúrába csoportosítani, vagy alapértelmezett template argumentumokat adni a gyakori kombinációkhoz.

  3. Rejtett függőségek a politikák között. Előfordulhat, hogy az egyik policy feltételezi egy másik policy jelenlétét vagy egy adott típusdefiníciót. Ez törékennyé teszi a rendszert. Megoldás: a politikák legyenek teljesen függetlenek; ha kapcsolat szükséges, azt a hosztosztály közvetítse.

  4. A std::enable_if helyett if constexpr vagy concepts használatának elmulasztása. A régebbi SFINAE alapú kód gyakran olvashatatlan és lassan fordul. C++20-ban a requires és a concept sokkal kifejezőbb. Ha a projekt még nem támogatja a C++20-at, törekedjünk a tag dispatch vagy a void_t detection idiom használatára, de a dokumentációban jelezzük, hogy a jövőben concepts-re kell áttérni.

  5. A politika túl sok felelősséget vállal. Egy jó politika egyetlen, jól körülhatárolt döntést valósít meg. Ha egy politika egyszerre kezeli az allokációt, a növekedést és a szálbiztonságot, akkor elveszíti a kombinálhatóság előnyét.

  6. A hosztosztály a politika típusától függő kódot if constexpr nélkül ír. Ez fordítási hibához vezet, ha a politika nem rendelkezik a feltételes ágban használt tagokkal. Az if constexpr garantálja, hogy a nem kiválasztott ág nem kerül példányosításra.

  7. A bináris méret növekedésének figyelmen kívül hagyása. Minden egyes policy kombináció új sablonpéldányt hoz létre, ami növeli a kódméretet. Ha sok kombinációt használunk, érdemes megfontolni a típus-erasure alkalmazását a ritkán változó részekre, vagy a policy-ket úgy tervezni, hogy a közös kód ne duplikálódjon.

27.4.5 Összefoglalás és önellenőrző kérdés

A policy-based design a C++ statikus polimorfizmusának egyik leghatékonyabb eszköze. Lehetővé teszi, hogy a viselkedést apró, független, fordítási időben cserélhető komponensekre bontsuk, így a kód rugalmas és teljesítmény szempontjából optimális marad. A mixinekkel és a tag dispatch-csel kombinálva a minta szinte bármilyen testreszabható komponens alapjául szolgálhat. A C++20 concepts bevezetése tovább javította a használhatóságot azáltal, hogy a politika interfészét formálisan ellenőrizhetjük, és a hibákat a sablon definíciójának helyén jelezhetjük.

A fejezet laborjában megvalósított dynamic_array három politikával mutatta be a minta gyakorlati alkalmazását. A hallgató feladata, hogy a kapott kódot lefordítsa, tesztelje, és saját méréseket végezzen, dokumentálva a környezetet és az eredményeket.
