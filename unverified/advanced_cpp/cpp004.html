2.3 Migráció, örökölt kód és modernizációs stratégia

A modern C++ könyvfejezet alábbi egysége a régi kódbázis fokozatos modernizálását tárgyalja. Nem cél, hogy mindent egyszerre cseréljünk le: a modernizálás akkor sikeres, ha kicsi, ellenőrizhető lépésekben haladunk, és a viselkedésváltozást méréssel és tesztekkel fogjuk közre. A C++03/11-időszaki kód nem attól kockázatos, hogy régi, hanem attól, ha nincs karakterizációs teszt, tisztázott ownership-modell és visszavonható bevezetési terv. Ez a fejezet ezt a három hiányt pótolja.

2.3.1 Miért fokozatosan?

A nagy kódbázisok C++03-ról vagy C++11-ről C++20/23-ra vitele ritkán valósítható meg egyetlen átírással. Az ilyen projekteknél a következő kedvezőtlen minták figyelhetők meg:

  • az átírást mindenki akarja, de senki sem meri elindítani, mert a viselkedés ismeretlen;
  • a modernizálás közben megváltozik a másolási/move szemantika, az overload-feloldás, a memóriadinamika vagy a generált kód, és ezt későn veszik észre;
  • az új kód nem fér vissza a régi modulok API-jához, így kevert nyelvű és kevert memóriamodellű rendszer keletkezik;
  • a kód formailag C++20 módban fordul, de a viselkedési háló nincs felállítva, ezért a „modern kód” hitéleti szerepet kap a mérés helyett.

A fokozatos stratégia ezzel szemben az evolúciót választja a forradalom ellenében. A meglevő kódbázis megmarad futó rendszerként, és a modernizálás lépései olyan kicsik, hogy mindegyik után ugyanaz a tesztkészlet, buildmátrix és mérési napló igazolja a paritást. A lépések nem keverednek: egy commit egy átalakítást, egy mérést és egy visszaállítható döntést tartalmaz.

2.3.2 Modernizációs lépcsők és a köztes standardek

A C++03/11 kód modernizálása általában szabványverziós lépcsőkön halad felfelé. Az egyes lépcsők nemcsak nyelvi lehetőségeket, hanem kockázatokat is hoznak:

Lépcső Nyelvi/könyvtári nyereség Tipikus kockázat
C++03 →\to C++11 move szemantika, lambdák, auto, nullptr, override, =default/=delete, scoped enums implicit move generálása három másolófüggvény esetén, overload-feloldás változás, std::auto_ptr eltávolítása
C++11 →\to C++14 std::make_unique, auto visszatérés, generic lambdas kevés, de a auto dedukció finomíthatja a túlterhelést
C++14 →\to C++17 [[nodiscard]], std::optional, std::variant, std::string_view, inline változók, if constexpr, strukturált kötések a std::string_view implicit konverziói élettartamhibát rejthetnek, ha az ownership továbbra is kézi
C++17 →\to C++20 concepts, std::span, ranges, coroutines, constexpr dynamic alloc (C++20), std::format a std::span átadás visszafelé kompatibilitási kérdése, a requires nélküli túlterhelések eltérő SFINAE-hangulatot eredményezhetnek
C++20 →\to C++23 std::expected, flat_map, std::ranges::to, kisebb nyelvi finomítások a fordítói támogatás szűkebb, a buildmátrixot könnyű túlvállalni

A migráció során a legnagyobb tévhit, hogy a standard verzió növelése önmagában modern kódot eredményez. A C++03 kód C++20 módban is fordulhat nyers pointerekkel, kézi new/delete-tel és NULL kompatibilis mutatókkal. A modernizálás tehát nem a build kapcsoló átírása, hanem a kód idiomáinak átalakítása. A fejezet célja, hogy ezt az átalakítást tanítsa meg.

Az egyes lépcsők között a következő eszközök segítenek eldönteni, hogy a fordító mit támogat: __cplusplus makró, __has_include, __has_cpp_attribute, valamint a buildrendszer feature-detekciós szkriptjei. A részletes feature detection a következő egységben (2.4) kerül elő, itt annyi a fontos, hogy a kód soha ne feltételezzen standardverziót, hanem a buildrendszer szabja meg a fordítás célszintjét.

2.3.3 Gyakori átalakítási minták C++03/11 →\to C++17/20

A régi kód modernizálásakor a következő mintákat érdemes keresni. Az alábbi megoldások nem triviális upgrade-ek, hanem az ownership, a hibakezelés és a szerződések explicit jelzésének lépései.

2.3.3.1 NULL →\to nullptr

A C++03 NULL makró általában 0, ezért a mutatóparaméter és a numerikus túlterhelés között elkerülhetetlen a félreértés. A nullptr bevezeti a std::nullptr_t típust, és egyértelmű mutatókörnyezethez köt.

// C++03 stílus
#include <cstddef>

bool is_valid(SampleBuffer* buffer) {
    if (buffer == NULL) return false;

    return buffer->count != 0;
}
// C++11/14, modernizált
#include <cstddef>

bool is_valid(SampleBuffer* buffer) {
    if (buffer == nullptr) return false;

    return buffer->count != 0;
}

A csere egyszerű, de a mutatóparamétereknél érdemes megfontolni a std::span vagy std::optional bevezetését, mert a nullptr önmagában nem oldja meg az élettartam-kérdést.

2.3.3.2 Mutató + hossz →\to std::span / std::string_view

A C++03 API-k gyakran várnak el egy mutatót és egy hosszt párban. Ez a kettő elválik egymástól, nem hordoz birtoklási előírást, és a hívó könnyen rossz hosszt ad át. A C++20 std::span és a C++17 std::string_view nem birtokol, de együtt transzportálja a kezdőcímet és a méretet, és kikényszeríti, hogy a hívó tudatosan jelölje meg a csupasz mutatót.

// C++03 stílus: double* + size_t
#include <cstddef>

double compute_average_from_range(const double* values, std::size_t count) {
    if (values == nullptr || count == 0) return 0.0;

    double sum = 0.0;
    for (std::size_t i = 0; i < count; ++i) {
        sum += values[i];
    }
    return sum / static_cast<double>(count);
}
// C++20 stílus: std::span
#include <span>

double compute_average_from_range(std::span<const double> samples) {
    if (samples.empty()) return 0.0;

    double sum = 0.0;
    for (double x : samples) {
        sum += x;
    }
    return sum / static_cast<double>(samples.size());
}

Az átalakítás nem csupán kényelem: a hívó oldalon a std::vector, std::array és a C tömb egyaránt implicit konvertálódhat std::span-né, és az üres literálok explicit std::span konstruálást igényelnek, ami megakadályozza a félreérthető nullptr+méret átadást.

2.3.3.3 Kézi memóriakezelés →\to RAII és Rule of 0/5

A C++03 kódok leggyakoribb sebei a kézi new/delete, a sekély másolás és a nem egyértelmű destrukció. A modern kódbázisban az ownership explicit kell legyen: std::unique_ptr az egyedi birtoklásra, std::shared_ptr a megosztottra, std::vector/std::array a konténerekre. A Rule of 0 szerint ha a tagok maguk birtokolnak, akkor az osztálynak nem kell destruktort, másolót vagy move-ot írnia; a Rule of 5 szerint ha saját erőforrás van, akkor mind az öt függvényt tudatosan kell kezelni.

// C++03 stílusú osztály: kézi memória, hiányzó/erőtlen ownership
#include <cstddef>
#include <algorithm>

class LegacyBuffer {
public:
    explicit LegacyBuffer(std::size_t size)
        : data_(new char[size]), size_(size) {}

    ~LegacyBuffer() { delete[] data_; }

    LegacyBuffer(const LegacyBuffer& other)
        : data_(new char[other.size_]), size_(other.size_) {
        std::copy(other.data_, other.data_ + other.size_, data_);
    }

    LegacyBuffer& operator=(const LegacyBuffer& other) {
        if (this != &other) {
            char* tmp = new char[other.size_];
            std::copy(other.data_, other.data_ + other.size_, tmp);
            delete[] data_;
            data_ = tmp;
            size_ = other.size_;
        }
        return *this;
    }

    char* data() { return data_; }
    std::size_t size() const { return size_; }

private:
    char* data_;
    std::size_t size_;
};

A LegacyBuffer működik, de a tulajdonjogot a kódoló intuitívan kezeli: a data() csupasz mutatót ad át, a másoló konstruktor és a másoló értékadó kézzel duplikál, nincs move, és a noexcept hiánya miatt acontainerek, algoritmusok nem tudják a leghatékonyabb kódot generálni.

Modernizált változat C++20-ban:

// C++20 stílus: unique_ptr, span, Rule of 0/5, nodiscard
#include <cstddef>
#include <memory>
#include <span>
#include <utility>
#include <algorithm>

class ModernBuffer {
public:
    explicit ModernBuffer(std::size_t size)
        : data_(std::make_unique<char[]>(size)), size_(size) {}

    ModernBuffer(const ModernBuffer& other)
        : data_(std::make_unique<char[]>(other.size_)), size_(other.size_) {
        std::copy_n(other.data_.get(), other.size_, data_.get());
    }

    ModernBuffer& operator=(const ModernBuffer& other) {
        if (this != &other) {
            auto tmp = std::make_unique<char[]>(other.size_);
            std::copy_n(other.data_.get(), other.size_, tmp.get());
            data_ = std::move(tmp);
            size_ = other.size_;
        }
        return *this;
    }

    ModernBuffer(ModernBuffer&&) noexcept = default;
    ModernBuffer& operator=(ModernBuffer&&) noexcept = default;

    [[nodiscard]] std::span<char> data() noexcept {
        return { data_.get(), size_ };
    }

    [[nodiscard]] std::span<const char> data() const noexcept {
        return { data_.get(), size_ };
    }

    [[nodiscard]] std::size_t size() const noexcept { return size_; }

private:
    std::unique_ptr<char[]> data_;
    std::size_t size_;
};

A modernizált osztály a következőket éri el:

  • a birtoklást a std::unique_ptr<char[]> egyértelművé teszi;
  • a data() std::span<char>-t ad vissza, így a hívó nem lát csupasz mutatót, és nem tud non-const hozzáférést kapni const objektumon;
  • a move konstruktor és move értékadó noexcept, ezért a std::vector és más tárolók újraelhelyezésnél mozgatni tudnak;
  • a [[nodiscard]] arra kötelezi a hívót, hogy a visszatérési értéket ne dobja el hallgatagon;
  • a másoló értékadó erős kivételbiztonságot ad: előbb elkészíti az új puffert, és csak akkor cserél, ha a foglalás és a másolás sikeres.

A Rule of 0 akkor léphet érvénybe, ha a puffert std::vector<char>-ként tároljuk: akkor a másoló, move, destruktor mind automatikusan helyes. A fenti std::unique_ptr megoldás a Rule of 5 tudatos változata, mert a másolást explicit módon akarjuk.

2.3.3.4 typedef →\to using, enum →\to enum class

A typedef nem teszi lehetővé a sablonaliasokat, és az olvasási irány kényelmetlen. A C++11 using alias ugyanezt a célt szolgálja, de jobban olvasható, és sablonoknál is működik.

// C++03 stílus
typedef std::vector<std::pair<int, std::string>> EntryList;

// C++11/14, modernizált
using EntryList = std::vector<std::pair<int, std::string>>;

A enum class bevezeti a típusbiztonságos, scopolt felsorolást. A régi enum neve belekerül a namespace-be, és implicit egész számmá konvertálódik, ami rejtett hibákat okozhat.

// C++03 stílus
enum State { IDLE, ACTIVE, STOPPED };

// C++11/14, modernizált
enum class State { Idle, Active, Stopped };

A default/delete és az override specifikátorok felfedik a szándékot. A korábbi C++03 kódban a destruktor vagy másoló hiánya néha implicit, nem szándékolt viselkedést eredményezett; a = default és = delete ma már a szerződés része.

2.3.3.5 for →\to tartományalapú for, std::transform/std::copy →\to algoritmusok

A C++03 kód nagy része indexelt vagy iterátoros hurkokat használ. A tartományalapú for nemcsak rövidebb, hanem kikényszeríti, hogy a konténer ne változzon méretben a bejárás közben, és kiküszöböli a tipográfiai indexhibákat.

// C++03 stílus
for (std::size_t i = 0; i < buffer.size(); ++i) {
    total += buffer.data()[i];
}

// C++20 stílus
for (char x : buffer.data()) {
    total += x;
}

A standard algoritmusok és a ranges könyvtár azáltal javítják a kódot, hogy a szándékot fejezik ki a lépések helyett. Ugyanakkor az algoritmusra váltás nem mindig gyorsabb, ezért a csere előtt és után mérni kell.

2.3.4 Rizikó, tesztelés és visszaállás

A modernizálás legfontosabb nem-kód eleme a karakterizációs teszt. A karakterizációs teszt rögzíti a jelenlegi viselkedést, beleértve a furcsa széleket is. Nem azt kérdezi, hogy a kód helyes-e, hanem azt, hogy mit csinál ma. Ez azért fontos, mert a modernizálás során a „hiba” kategóriába tartozó viselkedés megváltoztatása külön döntés legyen, nem az átírás mellékhatása.

Példa karakterizációs teszt a fenti compute_average_from_range régi változatához:

#include <cassert>
#include <cstddef>

double compute_average_from_range(const double* values, std::size_t count) {
    if (values == nullptr || count == 0) return 0.0;
    double sum = 0.0;
    for (std::size_t i = 0; i < count; ++i) {
        sum += values[i];
    }
    return sum / static_cast<double>(count);
}

int main() {
    double data[] = {1.0, 2.0, 3.0, 4.0};

    assert(compute_average_from_range(data, 4) == 2.5);
    assert(compute_average_from_range(nullptr, 0) == 0.0);
    assert(compute_average_from_range(data, 0) == 0.0);
}

A modernizált std::span-es változat ugyanezt a tesztet kell teljesítse, de a hívás módja megváltozik:

#include <cassert>
#include <span>
#include <vector>

double compute_average_from_range(std::span<const double> samples) {
    if (samples.empty()) return 0.0;
    double sum = 0.0;
    for (double x : samples) {
        sum += x;
    }
    return sum / static_cast<double>(samples.size());
}

int main() {
    std::vector<double> values{1.0, 2.0, 3.0, 4.0};

    assert(compute_average_from_range(values) == 2.5);
    assert(compute_average_from_range(std::span<const double>{}) == 0.0);
}

A két teszt egymás mellett él, amíg a régi API-t el nem távolítjuk. A visszaállás akkor gyors, ha egy commit egy átalakítást tartalmaz, és a commit üzenet megnevezi a régi és új API-t. A git bisect így megtalálja a hibás lépést.

A tesztelés mellett a következő mérési naplóra van szükség minden lépésnél:

  • futásidő (medián, szórással, rögzített bemenet és hardver mellett);
  • bináris méret (release és debug);
  • fordítási idő;
  • memóriahasználat (peak heap, allokációk száma).

Ezek a mértékek együttesen jelentik a modernizálás árát. A kódméret és a fordítási idő növekedése például a std::span-be csomagolásnál általában elhanyagolható, de a sablonmeta-programozás és a constexpr kódgenerálás lényegesen megnövelheti. A fejezet nem állítja, hogy a modern kód mindig kisebb vagy gyorsabb, mert ez függ a fordítótól, az optimalizációs szinttől és a munkaterheléstől.

A gyakorlatban a visszaállást az alábbi technikák támogatják:

  • minden modernizálási lépés saját branch-en történjen;
  • a régi és az új implementáció egy ideig párhuzamosan éljen: #if defined(LEGACY_BUFFER_IMPLEMENTATION) vagy buildrendszerbeli kapcsoló;
  • a feature flag a futásidőben vagy a linkelésben válasszon az implementációk között;
  • az éles rendszerben canary deployment: a forgalom kis részén az új implementáció fut;
  • a rollback nem a kód visszaírása, hanem a flag visszaállítása, miközben a commit history megőrzi a próbálkozást.

Az ABI-változások külön figyelmet igényelnek. Ha egy fejlécben megváltozik a LegacyBuffer layoutja, akkor az összes hívó binárisan inkompatibilis lesz. Ezért a fejlécben lévő osztály modernizálása előtt mérlegelni kell a Pimpl, a verziózott szimbólum vagy a kompatibilitási wrapper alkalmazását. A fejezet később (25.1–25.3) részletesen tárgyalja az ABI-t, itt elég annyi, hogy a fejléc-módosítás és a bináris kompatibilitás két külön döntés, és nem mindig oldható meg egy lépésben.

2.3.5 Örökölt kód és a modern idiomák határai

Nem minden régi kódot kell modernizálni. A következő esetekben a megtartás racionális lehet:

  • a modul stabil, tesztelt, a hívófelülete stabil, és nincs teljesítmény- vagy biztonsági probléma;
  • a modernizálás ABI-törést okozna, és az ABI a plugin-rendszer vagy a dinamikus könyvtár miatt kőbe van vésve;
  • a kód C-kompatibilis interfészt valósít meg, ahol a raw pointer és a size_t a kívánt megjelenítés;
  • a modul hamarosan megszűnik, és a modernizálás több erőforrást emésztene fel, mint amennyit megtakarít.

A modernizálás célja tehát nem a „gyönyörű” kód, hanem a kockázat csökkentése és a karbantarthatóság növelése. A C++03 kódot akkor érdemes modernizálni, ha:

  • nyers pointer és kézi memória van, amelynek ownership története nem dokumentált;
  • a hibakezelés int-kódon és out-paraméteren alapul, és a hívók gyakran rosszul használják;
  • a kód többszörösen másolható/move-olható, de a move hiánya miatt a tárolók nem optimalizálhatók;
  • a függvények szignatúrái nem fejezik ki az elő- és utófeltételeket.

2.3.6 A labor: modernizációs terv egy örökölt modulra

A fejezet laborfeladata egy örökölt C++03 modul modernizálásának megtervezése és végrehajtása. A példamodul egyszerű, de tartalmazza a tipikus problémákat: nyers pointer, hossztranszport, kézi memória és hibakezelés.

2.3.7 Kiinduló modul

// legacy_range_stats.h – C++03 stílus
#ifndef LEGACY_RANGE_STATS_H
#define LEGACY_RANGE_STATS_H

#include <cstddef>

struct SampleBuffer {
    double* values;
    std::size_t count;
};

double compute_average(const SampleBuffer* buffer);
double compute_min(const SampleBuffer* buffer);

#endif // LEGACY_RANGE_STATS_H
// legacy_range_stats.cpp – C++03 stílus
#include "legacy_range_stats.h"
#include <cstddef>

double compute_average(const SampleBuffer* buffer) {
    if (buffer == NULL || buffer->count == 0) return 0.0;

    double sum = 0.0;
    for (std::size_t i = 0; i < buffer->count; ++i) {
        sum += buffer->values[i];
    }
    return sum / static_cast<double>(buffer->count);
}

double compute_min(const SampleBuffer* buffer) {
    if (buffer == NULL || buffer->count == 0) return 0.0;

    double min_value = buffer->values[0];
    for (std::size_t i = 1; i < buffer->count; ++i) {
        if (buffer->values[i] < min_value) {
            min_value = buffer->values[i];
        }
    }
    return min_value;
}

A feladat:

  1. Rögzítsd a kiinduló modul viselkedését karakterizációs tesztekkel: compute_average és compute_min üres pufferen, egyetlen elemen és több elemen, nullptr esetén.

  2. Állítsd be a buildet C++17/20 módban. Fordítsd a kiinduló modult -Wall -Wextra -Wpedantic, MSVC esetén /W4 /permissive- kapcsolóval. Jegyezd fel a figyelmeztetéseket, de még ne javítsd őket.

  3. Add hozzá a modernizált interfészt ugyanabban a headerben, de std::span-nel:

    // modern_range_stats.h – C++20 kiegészítés
#include <span>

double compute_average(std::span<const double> samples);
double compute_min(std::span<const double> samples);

  4. Implementáld a modernizált függvényeket range-for-ral.

  5. Készíts teszteseteket, amelyek mind a régi, mind az új függvényt hívják, és ugyanazt az eredményt várják.

  6. Futtasd a teszteket ASan/UBSan alatt a régi és az új kódra is, és dokumentáld a leleteket.

  7. Készíts mérési naplót a futásidőről, a bináris méretről és a fordítási időről a következő táblázat szerint:

Az itt szereplő számok szemléltetőek; a laborban a ténylegesen mért értékeket kell beírni, és a mért és várt eredményt mindig külön oszlopban vagy sorban kell jelölni.

  1. Készíts visszaállási tervet: a régi API maradjon elérhető LEGACY_RANGE_STATS_API kapcsolóval, amíg az új API hívóit ki nem migrálják.
  2. Dokumentáld a modernizálási döntéseket: miért std::span és nem std::vector, mi történt a nullptr ággal, miért maradt meg a 0.0 visszatérés üres mintára, ha a régi API így viselkedett.
  3. A záró commit tartalmazzon: buildparancs, fordítóverzió, standardverzió, tesztnapló, mérési napló, és a mért/várt különbség indoklása.

2.3.8 Gyakori hibák és hogyan kerüld őket

Hiba: A modernizálás előtt nincs karakterizációs teszt, ezért az új kód „hibája” valójában a régi viselkedés megváltozása.
Helyes megoldás: Minden modernizálás előtt rögzítsd a régi API viselkedését tesztben, és a tesztet futtasd a régi implementáción is.

Hiba: A C++20 módra váltást összekeverik a kód modernizálásával, így a nyers pointer és a new/delete megmarad, csak a szabványverzió nő.
Helyes megoldás: Válaszd külön a buildkapcsoló-emelést a nyelvi idiómacseréktől; minden lépés egyetlen célt szolgáljon.

Hiba: Az új std::span-alapú API-t úgy vezetik be, hogy a régi hívók azonnal fordítási hibát kapnak, és a rollback csak kódvisszaírással lehetséges.
Helyes megoldás: Tartsd meg a régi API-t párhuzamosan, amíg az új API hívói készen nem állnak, és a feature flag választ.

Hiba: A teljesítményjavulást a modern kód látható szépsége alapján feltételezik, mérés nélkül.
Helyes megoldás: A modernizálás minden teljesítményállítása mérési naplóval igazolt legyen. A fenti táblázat sémája szerint rögzítsd a futásidőt, a bináris méretet és a fordítási időt.

2.3.9 Önellenőrző kérdések

  1. Miért nem elegendő egy C++03 kód modernizálásához az, hogy a buildet C++20 módra állítjuk?
    Válasz: Mert a nyelvi verzió növelése nem szünteti meg a nyers pointereket, a kézi memóriakezelést, a hiányzó ownership-modellt és a hibakezelési mintákat; a modernizálás a kód idiomáinak tudatos cseréje.

  2. Milyen három mérést kell rögzíteni a modernizálási lépések során, és miért nem elegendő csak a futásidő?
    Válasz: Futásidőt, bináris méretet és fordítási időt. A modern kód lehet gyorsabb, de nagyobb lehet a bináris vagy lassabb a fordítás; a három mérőszám együtt adja a tényleges árat.

  3. Hogyan biztosítod, hogy a modernizálás egy hibás lépése gyorsan visszaállítható legyen?
    Válasz: Egy commit egy átalakítást tartalmazzon; a régi és az új implementáció feature flag mögött éljen; a karakterizációs tesztek ugyanazt az eredményt várják; a rollback flag-visszaállítás, nem kódvisszaírás.

2.3.10 Továbbvitel

A következő egység (2.4) a fordítók és szabványverziók feature-detekciós technikáit tárgyalja. Az itt bevezetett buildmátrix és mérési napló ott válik teljes rendszerré: a __cplusplus, a __has_include és a __has_cpp_attribute használata lehetővé teszi, hogy a modernizált kód több fordítóval és több szabványcéllal is félelemmentesen forduljon. Ennek a fejezetnek a modernizálási lépcsői tehát nem légüres térben állnak: a következő rész azt mutatja meg, hogyan válasszuk szét a kódban azt, ami standard, attól, ami fordító- vagy platform-specifikus.
