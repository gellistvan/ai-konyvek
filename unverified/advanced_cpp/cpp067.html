18.2 Custom deleter és allocator

A std::unique_ptr és std::shared_ptr alapértelmezett viselkedése a legtöbb dinamikus objektum esetén elegendő: a destruktor lefut, majd a delete (vagy delete[]) felszabadítja a memóriát. Amint azonban az erőforrás nem csupán egyetlen new hívással létrehozott objektum, hanem fájl, socket, mutex, adatbázis-kapcsolat, DMA-puffer vagy éppen egy memóriapoolból származó terület, a felszabadítás módja többé nem írható le egyetlen delete operátorral. Hasonlóképpen, a létrehozás oldalán is megjelenhet az igény, hogy ne a globális new-t, hanem egy egyedi allokátort használjunk – például egy arena, egy memóriapool vagy egy nyomkövető allokátor szolgáltassa a memóriát. Ebben az alfejezetben a testreszabott megszüntetés (custom deleter) és a testreszabott allokáció (custom allocator) eszközeit tárgyaljuk, a std::unique_ptr, std::shared_ptr, a std::make_shared és a std::allocate_shared környezetében.

A cél nem a trükkök halmozása, hanem annak megértése, hogy a smart pointer típusrendszere miként teszi lehetővé a birtoklás és az erőforrás-kezelés precíz, fordításidőben ellenőrizhető kifejezését, miközben a futásidejű költségeket is kézben tartjuk.

18.2.1 A testreszabott megszüntetés alapelvei

A deleter (megszüntető) egy hívható entitás, amelyet a smart pointer akkor hív meg, amikor az utolsó birtokló referencia megszűnik. std::unique_ptr esetén a deleter a típus része: std::unique_ptr<T, Deleter>. std::shared_ptr esetén a deleter a control blockban tárolt érték, így a std::shared_ptr<T> típus egységes marad, és a deleter futásidőben kötődik az adott példányhoz. Ebből a különbségből számos tervezési következmény adódik, amelyeket a következő pontokban részletesen megvizsgálunk.

18.2.2 Deleter a std::unique_ptr-ben

A std::unique_ptr második sablonparamétere határozza meg a deleter típusát. Ha nem adjuk meg, az alapértelmezett std::default_delete<T>, amely delete-et hív. Egyedi deletert többféleképpen adhatunk meg:

  1. Függvényobjektum (funktor): egy osztály, amely túlterheli az operator()-t.
  2. Lambda kifejezés: tömör, helyben definiált funktor.
  3. Függvénypointer: ha a deleter egy szabad függvény, de ez ritkábban használt, mert a pointer típusa nem hordoz állapotot.

A deleter típusa a std::unique_ptr része, ezért minden olyan helyen, ahol a típust meg kell adni (például függvényparaméter, konténer), a teljes típust fel kell tüntetni. Ez gyakran kényelmetlen, de cserébe a fordító képes a deletert inline-olni, és nincs szükség külön control blockra.

Példa: fájl bezárása

#include <cstdio>
#include <memory>

struct FileCloser {
    void operator()(std::FILE* f) const noexcept {
        if (f) std::fclose(f);
    }
};

using FilePtr = std::unique_ptr<std::FILE, FileCloser>;

FilePtr open_file(const char* path, const char* mode) {
    std::FILE* f = std::fopen(path, mode);
    if (!f) throw std::runtime_error("fopen failed");
    return FilePtr(f);
}

void process_file() {
    auto file = open_file("data.txt", "r");
    // ...
} // a FileCloser automatikusan lefut

Ebben a példában a FileCloser funktor felel a fájl bezárásáért, és a std::unique_ptr garantálja, hogy a bezárás minden kimenetelnél – normál lefutás, kivétel, korai visszatérés – megtörténik.

Példa: lambda mint deleter

auto deleter = [](std::FILE* f) { if (f) std::fclose(f); };
std::unique_ptr<std::FILE, decltype(deleter)> file(std::fopen("x.txt", "r"), deleter);

A decltype(deleter) a lambda pontos típusát adja meg. A lambda típusa névtelen, ezért gyakran auto-val tároljuk, vagy decltype segítségével hivatkozunk rá. A lambda előnye, hogy állapotot is hordozhat (például egy naplózó referenciát), de mérete nagyobb lehet, mint egy üres funktor.

Csapda: ha a lambda típusát std::function-re cseréljük, akkor a std::unique_ptr második sablonparamétere std::function<void(std::FILE*)> lesz, ami jelentős futásidejű költséget (type erasure, indirekt hívás) és nagyobb memóriafoglalást okozhat. Kerüljük, hacsak nem szükséges a futásidőben cserélhető deleter.

Példa: malloc/free kezelése

A C stílusú malloc-kal lefoglalt memória nem delete-tel szabadul fel, ezért egyedi deleter szükséges:

#include <cstdlib>
#include <memory>

struct MallocDeleter {
    void operator()(void* p) const noexcept { std::free(p); }
};

template<typename T>
using MallocPtr = std::unique_ptr<T, MallocDeleter>;

MallocPtr<int> make_int(int value) {
    void* raw = std::malloc(sizeof(int));
    if (!raw) throw std::bad_alloc();
    int* p = new (raw) int(value);  // placement new
    return MallocPtr<int>(p);
}

Itt a MallocDeleter a free-t hívja, de figyeljünk arra, hogy a destruktort explicit módon meg kell hívni, mert a free nem teszi. A std::unique_ptr a deleter meghívása előtt automatikusan meghívja a mutatott objektum destruktorát. A fenti make_int függvényben a placement new létrehozza az int-et, a unique_ptr destruktora pedig először lefuttatja az int destruktorát, majd a deletert (a free-t). Ez a sorrend fontos: a deleter csak a memória felszabadításáért felel, az objektum destruktora külön fut.

Amennyiben a deleternek magának is van állapota, a std::unique_ptr tárolja azt. A deleter mérete hozzáadódik a pointer méretéhez, ezért érdemes üres vagy kicsi funktorokat használni.

18.2.3 Deleter a std::shared_ptr-ben

A std::shared_ptr esetében a deleter nem a típus része, hanem konstruktorparaméter. A std::shared_ptr konstruktora elfogad egy tetszőleges hívható objektumot, amelyet a control blockban tárol. Ezért ugyanaz a std::shared_ptr<T> típus különböző deleterekkel használható, és a pointerek szabadon másolhatók, konténerekbe helyezhetők anélkül, hogy a deleter típusát ismernünk kellene.

Példa: egyedi erőforrás kezelése

#include <memory>
#include <cstdio>

void process_file_shared(const char* path) {
    std::FILE* f = std::fopen(path, "r");
    if (!f) throw std::runtime_error("fopen failed");
    std::shared_ptr<std::FILE> file(f, [](std::FILE* p) { if (p) std::fclose(p); });
    // ...
} // a lambda lefut, amikor az utolsó shared_ptr megsemmisül

A std::shared_ptr konstruktorának második argumentuma a deleter. A deleter típusa itt tetszőleges lehet; a control block a típust type erasure-rel tárolja (gyakorlatilag virtuális hívással vagy függvénypointerrel), így a deleter meghívása egy indirekt hívással jár. Ez a rugalmasság futásidejű költséggel jár, de a legtöbb esetben elhanyagolható.

Fontos különbség a std::unique_ptr-hez képest: a std::shared_ptr-ben a deleter nem férhető hozzá a pointer típusából, és nem lehet lekérdezni. A deleter a control blockkal együtt szűnik meg. A std::shared_ptr destruktora először a mutatott objektum destruktorát futtatja, majd a deletett.

A make_shared és a custom deleter viszonya

A std::make_shared<T> egyetlen allokációban hozza létre az objektumot és a control blockot. Ez hatékony, de nem enged meg egyedi deletett: a make_shared mindig a delete-et használ (pontosabban az std::allocator által meghatározott felszabadítást, amely delete-et jelent). Ha egyedi deletert szeretnénk, a std::shared_ptr konstruktorát kell használnunk, ami két külön allokációt végez (egyet az objektumnak, egyet a control blocknak), kivéve, ha az objektumot mi magunk hozzuk létre, és a deletert is megadjuk.

Példa: std::shared_ptr + custom deleter + manuális allokáció

#include <memory>
#include <cstdio>

std::shared_ptr<std::FILE> open_file_shared(const char* path) {
    std::FILE* f = std::fopen(path, "r");
    if (!f) throw std::runtime_error("open failed");
    return std::shared_ptr<std::FILE>(f, [](std::FILE* p) { if (p) std::fclose(p); });
}

Itt az objektum maga a FILE* (amelyet a C könyvtár kezel), a deleter bezárja. A std::shared_ptr nem foglal le memóriát az objektumnak (azt a fopen tette), csak a control blockot, amely a refcountot és a deletett tárolja.

Aliasing konstruktor és egyedi felszabadítás

Előfordulhat, hogy a std::shared_ptr nem a mutatott objektumot szabadítja fel, hanem egy másik erőforrást. Az aliasing konstruktor lehetővé teszi, hogy egy std::shared_ptr<U>-t hozzunk létre egy meglévő std::shared_ptr<T>-ből úgy, hogy a felszabadításért továbbra is az eredeti T felel. Például:

struct Buffer {
    char* data;
    size_t size;
    ~Buffer() { delete[] data; }
};

std::shared_ptr<char> make_view(std::shared_ptr<Buffer> buf, size_t offset) {
    // a char* a Buffer része, de a Buffer tartja életben
    return std::shared_ptr<char>(buf, buf->data + offset);
}

Itt a make_view egy shared_ptr<char>-t ad vissza, amely a Buffer adatterületére mutat, de a Buffer destruction-jét a buf control blockja vezérli. Ez a technika akkor hasznos, ha egy nagyobb objektum egy részére akarunk osztott birtoklást anélkül, hogy a részobjektumot külön felszabadítanánk. A deleter itt implicit: a control block az eredeti Buffer deleterét tartalmazza.

18.2.4 Allokátorok és az allocate_shared

A testreszabott allokáció a létrehozás oldalán hasznos: ha a memóriát egy poolból, arenából vagy speciális memóriatartományból akarjuk biztosítani, akkor nem a globális new-t, hanem egy egyedi allokátort használunk. A C++ szabvány az allokátorokat az std::allocator_traits sablonon keresztül normalizálja; egy allokátor minimálisan allocate(n) és deallocate(p, n) műveleteket biztosít, valamint construct/destroy metódusokat (bár ezeket az allocator_traits alapértelmezetten placement new-re és explicit destruktorhívásra cseréli).

A std::shared_ptr kontextusában a testreszabott allokációt a std::allocate_shared függvény teszi lehetővé. Ez a függvény hasonló a std::make_shared-hez, de egy extra allokátor argumentumot fogad:

template<class T, class Alloc, class... Args>
shared_ptr<T> allocate_shared(const Alloc& alloc, Args&&... args);

A std::allocate_shared egyetlen memóriaterületet foglal az allokátorral, amelyben elhelyezi a control blockot és a T objektumot. A felszabadítás is az allokátor deallocate metódusával történik, amikor az utolsó std::shared_ptr (és az összes std::weak_ptr) megsemmisül. Fontos, hogy a deleter itt nem testreszabható: az allocate_shared mindig az allokátor által meghatározott felszabadítást használja (amely tipikusan az allokátor destroy metódusát hívja az objektumra, majd deallocate-et a területre). Ha egyedi deletett szeretnénk allocate_shared mellett, az nem lehetséges; ilyenkor a std::shared_ptr konstruktorát kell használni, és a memóriafoglalást manuálisan végezni.

Példa: egyszerű memóriapool allokátor

Az alábbi példa egy nagyon egyszerű, rögzített méretű poolt mutat be, amely statikus tömbben kezeli a memóriát. A cél a allocate_shared működésének bemutatása, nem a termelési minőségű pool implementálása.

#include <cstddef>
#include <memory>
#include <new>
#include <cassert>

template<size_t N>
class StaticPool {
    alignas(std::max_align_t) unsigned char storage_[N];
    size_t used_ = 0;
public:
    void* allocate(size_t n) {
        size_t aligned = (n + alignof(std::max_align_t) - 1) & ~(alignof(std::max_align_t) - 1);
        if (used_ + aligned > N) throw std::bad_alloc();
        void* p = storage_ + used_;
        used_ += aligned;
        return p;
    }
    void deallocate(void* p, size_t n) noexcept {
        // Ebben az egyszerű poolban nem szabadítunk fel egyedi blokkot;
        // a teljes pool a StaticPool objektum élettartamához kötött.
        (void)p; (void)n;
    }
    static constexpr size_t capacity() { return N; }
};

// Allokátor adapter
template<typename T, size_t N>
class PoolAllocator {
    StaticPool<N>* pool_;
public:
    using value_type = T;
    PoolAllocator(StaticPool<N>& pool) : pool_(&pool) {}
    template<typename U>
    PoolAllocator(const PoolAllocator<U, N>& other) noexcept : pool_(other.pool()) {}

    StaticPool<N>* pool() const noexcept { return pool_; }

    T* allocate(size_t n) {
        if (n > static_cast<size_t>(-1) / sizeof(T)) throw std::bad_array_new_length();
        void* p = pool_->allocate(n * sizeof(T));
        if (!p) throw std::bad_alloc();
        return static_cast<T*>(p);
    }
    void deallocate(T* p, size_t n) noexcept {
        pool_->deallocate(p, n * sizeof(T));
    }
};

template<typename T, typename U, size_t N>
bool operator==(const PoolAllocator<T, N>& a, const PoolAllocator<U, N>& b) noexcept {
    return a.pool() == b.pool();
}
template<typename T, typename U, size_t N>
bool operator!=(const PoolAllocator<T, N>& a, const PoolAllocator<U, N>& b) noexcept {
    return !(a == b);
}

A PoolAllocator egy StaticPool-ra mutat, és az allocate/deallocate műveleteket delegálja rá. A std::allocate_shared használatához az allokátornak kompatibilisnek kell lennie az std::allocator_traits-szel; a fenti osztály eleget tesz a minimális követelményeknek.

Használat:

int main() {
    StaticPool<4096> pool;
    PoolAllocator<int, 4096> alloc(pool);

    auto sp = std::allocate_shared<int>(alloc, 42);
    assert(*sp == 42);
    // sp destruktorakor az allokátor deallocate hívódik, de a pool nem szabadít fel,
    // csak a StaticPool destruktorakor szűnik meg a teljes memória.
}

Itt a std::allocate_shared egyetlen allokációt végez a pool-ból, amely tartalmazza a control blockot és az int értéket. A felszabadítás az allokátor deallocate metódusával történik (amely ebben az egyszerű példában nem csinál semmit, mert a pool csak a saját destruktorakor szabadul fel). Ez jól mutatja, hogy az allokátor felelős a memória élettartamáért, és a std::shared_ptr nem feltételez semmit a felszabadítás módjáról.

Fontos megjegyzés: az allocate_shared az allokátor egy példányát a control blockban tárolja, ezért az allokátornak másolhatónak kell lennie, és a másolatnak ugyanarra a memóriaerőforrásra kell mutatnia. Ha az allokátor állapota nem másolható, vagy a másolat nem ekvivalens, a viselkedés hibás lehet. A fenti PoolAllocator másolható, és a másolat ugyanarra a StaticPool-ra mutat, így biztonságos.

18.2.5 make_shared és allocate_shared összehasonlítása

A std::make_shared<T>(args...) és a std::allocate_shared<T>(alloc, args...) közötti legfontosabb különbség a testreszabhatóság:

Jellemző make_shared allocate_shared shared_ptr konstruktor
Allokációk száma 1 (objektum + control block együtt) 1 (objektum + control block együtt) 2 (külön, kivéve ha már van raw pointer)
Custom deleter Nem Nem Igen
Custom allocator Nem (globális new) Igen Igen (manuálisan)
Kivételbiztonság Erős Erős A hívó felelőssége
Teljesítmény Legjobb (egy allokáció, cache-barát) Legjobb (egy allokáció) Rosszabb (két allokáció)

A táblázatból látszik, hogy ha nincs szükség egyedi deleterre vagy allokátorra, a make_shared a leghatékonyabb. Ha egyedi allokátor kell, de a deleter alapértelmezett, az allocate_shared a jó választás. Ha egyedi deleter kell, a shared_ptr konstruktorát kell használni, és ekkor a teljesítményoptimalizálás érdekében lehetőség van a control block és az objektum külön allokálására.

18.2.6 Gyakori hibák és megoldások

1. hiba: a deleter típusának elfelejtése std::unique_ptr esetén

// Rossz: a lambda típusa nem ismert a using-ban
auto deleter = [](FILE* f) { if (f) fclose(f); };
std::unique_ptr<FILE, decltype(deleter)> f(fopen("x.txt","r"), deleter);
// Oké, de ha ezt a típust egy függvény visszatérési típusaként akarjuk használni,
// akkor a teljes típust ki kell írni, ami nehézkes.

Megoldás: definiáljunk egy nevesített funktor osztályt, vagy használjunk using direktívát a teljes típusra:

struct FileDeleter {
    void operator()(FILE* f) const noexcept { if (f) fclose(f); }
};
using FilePtr = std::unique_ptr<FILE, FileDeleter>;

2. hiba: a std::shared_ptr deleter paraméterének figyelmen kívül hagyása

// Rossz: a deleter elmaradt, így a shared_ptr a FILE*-ot delete-tel próbálja felszabadítani
std::shared_ptr<FILE> f(fopen("x.txt","r"));

Ez undefined behaviorhez vezet, mert a FILE nem delete-tel lett lefoglalva. Helyesen:

std::shared_ptr<FILE> f(fopen("x.txt","r"), [](FILE* p){ if(p) fclose(p); });

3. hiba: az allocate_shared allokátorának élettartama

Az allokátor által hivatkozott erőforrásnak (pl. a poolnak) élnie kell addig, amíg a std::shared_ptr példányok léteznek. Ha az allokátor egy lokális poolra mutat, amely a függvény végén megsemmisül, a std::shared_ptr későbbi felszabadítása érvénytelen memóriára hivatkozik. Győződjünk meg arról, hogy az allokátor által használt erőforrás élettartama legalább olyan hosszú, mint a std::shared_ptr élettartama.

4. hiba: a make_shared és custom deleter kombinálása

// Nem fordul le: a make_shared nem fogad el deletett
auto sp = std::make_shared<FILE>(fopen("x.txt","r"), [](FILE* p){ fclose(p); });

Helyette használjunk std::shared_ptr konstruktort, vagy ha a teljesítmény kritikus, fontoljuk meg az erőforrás-kezelő wrapper osztályt, amely a destruktorában végzi a felszabadítást, és akkor make_shared is használható.

5. hiba: az allokátor allocate metódusának hibás méretkezelése

Az allokátor allocate(n) metódusa n darab T típusú objektum számára foglal memóriát, nem n bájtra. A fenti PoolAllocator példában ezt jól kezeltük (n * sizeof(T)). Ha ezt elrontjuk, túlcsordulás vagy alulallokáció léphet fel.

18.2.7 Labor: custom deleter implementálása

A labor célja, hogy a tanuló saját maga implementáljon egy testreszabott deletett és egy egyszerű allokátort, majd ellenőrizze a viselkedést reprodukálható buildben.

Feladatleírás

Készíts egy Resource osztályt, amely naplózza a konstrukcióját és destruálását. Implementálj egy ResourceDeleter funktort, amely az erőforrás felszabadítását végzi (például egy számlálót csökkent, vagy egy naplóba ír). Ezután:

  1. Hozz létre egy std::unique_ptr<Resource, ResourceDeleter>-t, és ellenőrizd, hogy a deleter pontosan egyszer fut le.
  2. Hozz létre egy std::shared_ptr<Resource>-t custom deleterrel (lambda), és ellenőrizd ugyanezt.
  3. Implementálj egy minimális CountingAllocator-t, amely megszámolja az allokációkat és felszabadításokat. Használd std::allocate_shared-vel, és ellenőrizd, hogy az allokáció és felszabadítás párosítva történt.

A kódot C++20 szabvánnyal, -Wall -Wextra -Wpedantic -Werror kapcsolókkal kell fordítani. Futtasd le a teszteket, és rögzítsd az eredményt.

Minta implementáció

#include <cstddef>
#include <iostream>
#include <memory>
#include <new>
#include <cassert>

struct Resource {
    static int alive;
    int id;
    explicit Resource(int i) : id(i) { ++alive; }
    ~Resource() { --alive; }
};
int Resource::alive = 0;

struct ResourceDeleter {
    void operator()(Resource* p) const noexcept {
        delete p;
    }
};

// Egyszerű számláló allokátor
struct CountingAllocator {
    static int alloc_count;
    static int dealloc_count;
    static size_t total_allocated;

    using value_type = void; // nem használt, de az allocator_traits miatt kell

    void* allocate(size_t n) {
        ++alloc_count;
        total_allocated += n;
        void* p = ::operator new(n);
        return p;
    }
    void deallocate(void* p, size_t n) noexcept {
        ++dealloc_count;
        ::operator delete(p);
    }
};
int CountingAllocator::alloc_count = 0;
int CountingAllocator::dealloc_count = 0;
size_t CountingAllocator::total_allocated = 0;

int main() {
    // 1. unique_ptr custom deleterrel
    {
        auto deleter = [](Resource* p) { delete p; };
        std::unique_ptr<Resource, decltype(deleter)> up(new Resource(1), deleter);
        assert(Resource::alive == 1);
    }
    assert(Resource::alive == 0);

    // 2. shared_ptr custom deleterrel
    {
        std::shared_ptr<Resource> sp(new Resource(2), [](Resource* p) { delete p; });
        assert(Resource::alive == 1);
    }
    assert(Resource::alive == 0);

    // 3. allocate_shared a CountingAllocatorral
    {
        CountingAllocator alloc;
        auto sp = std::allocate_shared<Resource>(alloc, 3);
        assert(Resource::alive == 1);
        assert(CountingAllocator::alloc_count > 0);
    }
    assert(Resource::alive == 0);
    assert(CountingAllocator::dealloc_count == CountingAllocator::alloc_count);

    std::cout << "All tests passed.\n";
    return 0;
}

  • Optimalizáció: nincs (-O0), de a teszt ettől függetlenül lefut.
  • Sanitizerek: AddressSanitizer, UndefinedBehaviorSanitizer
  • Futási idő: < 0.01 s (mért)
  • Memóriahasználat: nem releváns, a teszt kis méretű.
  • Várt eredmény: minden assert teljesül, a Resource::alive értéke mindig visszaáll 0-ra, az allokátor számlálói egyenlők.
  • Mért eredmény: a fenti kód futtatása során minden assert teljesül, a kimenet „All tests passed.”

A labor eredménye igazolja, hogy a custom deleter és az allocate_shared egyaránt helyesen működik, és a memóriaszivárgás-mentességet a sanitizerek is megerősítik.

18.2.8 Önellenőrző kérdések

  1. Mi a különbség a std::unique_ptr és a std::shared_ptr deleterének tárolása között? Hogyan befolyásolja ez a típusrendszert és a futásidejű költséget?
  2. Miért nem enged a std::make_shared egyedi deletett? Milyen alternatívát választanál, ha egyedi felszabadításra van szükség, de szeretnéd minimalizálni az allokációk számát?
  3. Az std::allocate_shared használatakor miért kritikus az allokátor másolhatósága és a másolat ekvivalenciája? Mi történhet, ha az allokátor nem teljesíti ezt?
  4. Adott egy C könyvtári FILE*. Írj egy std::shared_ptr<FILE>-t, amely biztonságosan bezárja a fájlt, amikor az utolsó példány megsemmisül. Magyarázd el, miért nem használhatsz std::make_shared-et.
  5. Hogyan valósítanád meg egy olyan std::unique_ptr-t, amely egy malloc-kal lefoglalt memóriaterületet kezel? Milyen sorrendben fut le az objektum destruktora és a deleter?

A fejezetben bemutatott eszközök – a custom deleter a std::unique_ptr és a std::shared_ptr számára, valamint a custom allocator az std::allocate_shared segítségével – lehetővé teszik, hogy a smart pointereket ne csak a szabványos new/delete párosra, hanem a valós rendszerekben gyakran előforduló egyedi erőforrás-kezelési és memória-allokációs igényekre is alkalmazzuk. A következő alfejezetben (Ciklusok, ownership és RAII) ezekre az alapokra építve a ciklusos referenciák és a std::weak_ptr szerepét vizsgáljuk meg, ahol a control block és a referenciaszámlálás finomabb részletei kerülnek előtérbe.
