18.4 Gyakori memóriahibák és elkerülésük

A memóriakezelési hibák a C++ programok leggyakoribb hibái közé tartoznak, és súlyos következményekkel járhatnak: memóriaszivárgás, heap korrupció, undefined behavior, biztonsági rések. Bár a modern C++ eszköztára (RAII, smart pointerek, konténerek) drámaian csökkenti ezek előfordulását, a hibák továbbra is felbukkannak, különösen örökölt kódban, nyers pointereket használó interfészeknél, vagy amikor a fejlesztő figyelmen kívül hagyja az élettartam-szabályokat. Ez a fejezet a három leggyakoribb memóriahibát – a memóriaszivárgást, a kettős felszabadítást és a függő pointer használatát – járja körül, bemutatva a tipikus hibamintákat, a helyes megoldásokat, valamint a hibák felderítésére szolgáló sanitizereket és a megelőző code review szempontjait. A fejezet feltételezi a std::unique_ptr, std::shared_ptr, std::weak_ptr és a RAII alapjainak ismeretét, ahogyan azt az unique_ptr, shared_ptr és weak_ptr–Ciklusok, ownership és RAII alfejezetek tárgyalják.

18.4.1 1. Memóriaszivárgás (Memory Leak)

A memóriaszivárgás azt jelenti, hogy a program dinamikusan lefoglalt memóriát, de a mutatót elveszíti anélkül, hogy felszabadítaná. A szivárgott memória nem érhető el többé, és a program futása során felhalmozódik. Hosszú futású folyamatokban ez fokozatos memóriahasználat-növekedéshez, végül erőforrás-kimerüléshez vezet.

A legegyszerűbb eset:

void leak_basic() {
    int* p = new int(42);
    // p elvész a függvény végén, a memória szivárog
}

A hiba oka, hogy a p mutató megsemmisül, de a heap-en lefoglalt int objektum nem szabadul fel. A C++ nyelv nem rendelkezik szemétgyűjtővel, ezért a fejlesztő felelőssége a felszabadítás.

Gyakori okok és példák

  1. Korai visszatérés vagy kivétel: Ha a delete egy feltételes ágban vagy a függvény végén lenne, de egy return vagy kivétel megelőzi, a felszabadítás elmarad.
void unsafe_exception() {
    auto* p = new std::string("hello");
    some_function_that_may_throw(); // ha dob, a delete nem fut le
    delete p;
}

A megoldás: használjunk RAII objektumot, például std::unique_ptr-et, amelynek destruktora akkor is lefut, ha kivétel dobódik.

  1. Konténerben tárolt nyers pointerek: Ha egy konténer, például std::vector<T*>, nyers pointereket tárol, a konténer destruktora csak a pointereket szabadítja fel, a mutatott objektumokat nem. A tulajdonjog kérdése homályos, és gyakran szivárgáshoz vezet.
void vector_of_raw_pointers() {
    std::vector<int*> v;
    v.push_back(new int(1));
    v.push_back(new int(2));
    // v destruktora nem hív delete-et az elemekre -> szivárgás
}

Helyes megoldás: használjunk std::vector<std::unique_ptr<int>>-et, így a vektor destruktora felszabadítja az elemeket is.

  1. Ciklikus hivatkozások std::shared_ptr-rel: A std::shared_ptr referenciaszámlálója akkor csökken nullára, amikor az utolsó shared_ptr is megsemmisül. Ha két objektum kölcsönösen shared_ptr-rel hivatkozik egymásra, a számláló soha nem éri el a nullát, így mindkét objektum a heap-en marad. Ez a hiba gyakori gráf- vagy fa-adatszerkezetekben, ahol a szülő és gyermek csomópontok egymásra mutatnak.
struct Node {
    std::shared_ptr<Node> next;
    // std::shared_ptr<Node> prev; // ha ez is shared_ptr lenne, ciklus alakulna ki
    std::weak_ptr<Node> prev; // helyes: weak_ptr megtöri a ciklust
    ~Node() { /* ... */ }
};

void cyclic_shared_ptr() {
    auto a = std::make_shared<Node>();
    auto b = std::make_shared<Node>();
    a->next = b;
    b->prev = a; // weak_ptr, nem növeli a referenciaszámlálót
} // a és b felszabadulnak, mert a referenciaszámláló nullára csökken
  1. Kivételbiztonság hiánya összetett műveleteknél: Ha egy függvényben több nyers pointert foglalunk le, és a második lefoglalás kivételt dob, az első már lefoglalt memória szivárog. A std::make_unique és a std::make_shared használata ezt a problémát is kiküszöböli, mert a lefoglalás és a tárolás egyetlen kifejezésben történik, és a fordító biztosítja a kivételbiztonságot.

A memóriaszivárgás elkerülésének alapelvei

  • Soha ne használjunk csupasz new-t és delete-t, ha van RAII alternatíva.
  • Minden dinamikus erőforrásnak legyen egyértelmű tulajdonosa, lehetőleg egy RAII osztály.
  • Konténerekben tároljunk értékeket vagy smart pointereket, ne nyers pointereket.
  • Ciklikus hivatkozásokhoz használjunk std::weak_ptr-t.
  • Használjunk gyári függvényeket (std::make_unique, std::make_shared) a kivételbiztonság érdekében.

18.4.2 2. Kettős felszabadítás (Double Free)

Kettős felszabadításról beszélünk, ha ugyanazt a dinamikus memóriaterületet kétszer adjuk át a felszabadító függvénynek (delete, delete[], free). Ez undefined behavior, és a gyakorlatban a heap adatszerkezeteinek korrupciójához, összeomláshoz vagy kihasználható biztonsági réshez vezet.

A legegyszerűbb példa:

void double_free_basic() {
    int* p = new int(10);
    delete p;
    delete p; // UB: a második delete ugyanarra a memóriára mutat
}

A hiba oka, hogy ugyanarra az objektumra több tulajdonosi mutató is létezik, és mindegyik megpróbálja felszabadítani. A modern C++ ezt a problémát a kizárólagos tulajdonlást biztosító std::unique_ptr-rel és a másolást tiltó vagy mély másolást végző osztályokkal kezeli.

Gyakori okok és példák

  1. Sekély másolás: Ha egy osztály nyers pointert tárol, és a másoló konstruktor vagy az értékadó operátor nincs megvalósítva, a fordító által generált változat sekély másolást végez: mindkét objektum ugyanarra a memóriára mutat. Mindkettő destruktora megpróbálja felszabadítani ugyanazt a területet.
class BadString {
    char* data_;
public:
    explicit BadString(const char* s) {
        data_ = new char[strlen(s) + 1];
        strcpy(data_, s);
    }
    // hiányzik a másoló konstruktor és az értékadó operátor
    ~BadString() { delete[] data_; }
};

void use_bad_string() {
    BadString s1("hello");
    BadString s2 = s1; // sekély másolás
} // s2 és s1 destruktora is delete[]-et hív -> double free

A megoldás a Rule of 3/5 betartása: vagy tiltsuk le a másolást (= delete), vagy valósítsuk meg a mély másolást. A legegyszerűbb, ha a nyers pointert std::string-re cseréljük, és az osztály a Rule of 0-t követi.

  1. Helytelen move szemantika: Ha egy osztály nyers pointert tárol, és a move konstruktor nem nullázza ki a forrás mutatóját, akkor a forrás és a cél is ugyanarra mutat. Mindkettő destruktora felszabadítja ugyanazt a memóriát.
class BadBuffer {
    int* data_;
public:
    explicit BadBuffer(size_t n) : data_(new int[n]) {}
    // rossz move konstruktor: nem nullázza a forrást
    BadBuffer(BadBuffer&& other) noexcept : data_(other.data_) {}
    ~BadBuffer() { delete[] data_; }
};

void use_bad_buffer() {
    BadBuffer b1(10);
    BadBuffer b2(std::move(b1)); // b2.data_ és b1.data_ ugyanaz
} // mindkettő destruktora delete[]-et hív -> double free

A helyes move konstruktor a forrás mutatóját nullptr-re állítja:

BadBuffer(BadBuffer&& other) noexcept : data_(other.data_) {
    other.data_ = nullptr;
}

Ha std::unique_ptr-et használunk, ez automatikusan megtörténik.

  1. Nyers pointerek átadása és a tulajdonjog kétértelműsége: Ha egy függvény delete-et hív egy pointerre, amit a hívó is felszabadít, kettős felszabadítás lép fel. Az ilyen helyzetek elkerülésére soha ne adjunk át nyers pointert tulajdonosi szándékkal; használjunk smart pointert, amely egyértelművé teszi a tulajdonjogot.

A double free elkerülésének alapelvei

  • Minden dinamikus erőforrásnak pontosan egy tulajdonosa legyen.
  • Kövessük a Rule of 0/3/5 elvet: ha az osztály nem kezel erőforrást, ne legyen destruktora; ha kezel, akkor a másoló, move műveleteket vagy tiltsuk le, vagy valósítsuk meg helyesen.
  • Használjunk std::unique_ptr-et kizárólagos tulajdonlásra, std::shared_ptr-t megosztott tulajdonlásra, és soha ne keverjük a kettőt nyers pointerekkel.
  • Kerüljük a nyers new és delete használatát.

18.4.3 3. Függő pointer és use-after-free

Függő pointer (dangling pointer) olyan mutató, amely egy már megsemmisült objektumra vagy felszabadított memóriaterületre mutat. A függő pointer használata – olvasás, írás, dereferálás – undefined behavior, és gyakran use-after-free (UAF) néven emlegetik. Ez a hibatípus különösen veszélyes, mert a hiba gyakran nem azonnal jelentkezik, hanem később, más kódrészletben okozhat rejtélyes viselkedést, ami megnehezíti a hibakeresést.

Gyakori okok és példák

  1. Visszaadott referencia vagy mutató lokális objektumra: A lokális változók a függvényből való visszatéréskor megsemmisülnek, így a rájuk mutató pointer vagy referencia függővé válik.
int* bad_function() {
    int local = 42;
    return &local; // hiba: a lokális változó megsemmisül
}

void use_bad_function() {
    int* p = bad_function();
    std::cout << *p; // UB: use-after-scope
}

Helyes megoldás: térjünk vissza értékkel, ne mutatóval.

int good_function() {
    return 42;
}
  1. Konténer műveletek okozta iterátor- vagy referencia-invalidálódás: A konténerek módosítása érvénytelenítheti a korábban kinyert iterátorokat, referenciákat vagy pointereket. Például a std::vector::push_back újraallokálhatja a belső tárolót, ami érvényteleníti az összes korábbi iterátort, referenciát és pointert.
void iterator_invalidation() {
    std::vector<int> v{1, 2, 3};
    int& ref = v[0]; // referencia az első elemre
    v.push_back(4); // újraallokálhat, ref érvénytelenül
    std::cout << ref; // UB: dangling reference
}

Helyes megoldás: ha stabil referenciákra van szükség, használjunk olyan konténert, amely nem érvényteleníti a referenciákat (pl. std::deque, std::list), vagy foglaljunk előre elegendő kapacitást a reserve()-vel.

  1. View típusok (std::string_view, std::span) élettartamának helytelen kezelése: A view típusok nem birtokolják az adatot, csak egy mutatót és méretet tárolnak. Ha a mögöttes tároló megsemmisül, a view függővé válik.
std::string_view bad_view() {
    std::string s = "hello";
    return s; // s megsemmisül, a visszaadott string_view függővé válik
}

Helyes megoldás: térjünk vissza std::string-gel, vagy biztosítsuk, hogy a view ne élje túl a mögöttes adatot.

  1. Nyers pointer std::unique_ptr-ből: A get() metódus kinyeri a nyers pointert, de a unique_ptr továbbra is tulajdonos marad. Ha a unique_ptr megsemmisül vagy reset-et hívunk, a nyers pointer függővé válik.
void bad_unique_ptr_get() {
    auto p = std::make_unique<int>(42);
    int* raw = p.get();
    p.reset(); // felszabadítja a memóriát
    std::cout << *raw; // UB: dangling pointer
}

Helyes megoldás: ne tároljuk el a get() eredményét hosszú távra, és ne használjuk, ha a unique_ptr már nem él. Ha átmeneti hozzáférésre van szükség, a get() eredményét csak a unique_ptr élettartamán belül használjuk.

  1. Tároló megsemmisülése után megmaradó elemekre mutató pointerek: Ha egy konténer megsemmisül, az elemei is megsemmisülnek, így a rájuk mutató pointerek függővé válnak. Ez gyakori hiba, amikor valaki kimenti egy konténer elemének címét, majd a konténert eldobja.

A use-after-free elkerülésének alapelvei

  • Ne adjunk vissza referenciát vagy mutatót lokális objektumra.
  • Használjunk érték-szemantikát; a move szemantika hatékonyan kezeli a visszatérési értékeket.
  • Ismerjük a konténerek iterátor- és referencia-érvényességi szabályait, és ennek megfelelően válasszunk konténert.
  • A view típusokat csak akkor használjuk, ha a mögöttes adat élettartama garantáltan túléli a view-t.
  • A std::unique_ptr::get() eredményét ne tároljuk el, és ne használjuk a unique_ptr megsemmisülése után.
  • Használjunk std::weak_ptr-t, ha gyenge hivatkozást akarunk fenntartani; a lock() ellenőrzi az objektum életét.

18.4.4 4. Sanitizerek és statikus elemzés

A memóriahibák futás közbeni felderítésére a sanitizerek a leghatékonyabb eszközök. A GCC és Clang fordítók támogatják az AddressSanitizer (ASan), a LeakSanitizer (LSan) és az UndefinedBehaviorSanitizer (UBSan) használatát. Az ASan a heap, stack és globális memóriahozzáféréseket ellenőrzi, és képes észlelni a use-after-free, buffer overflow, double free és egyéb hibákat. Az LSan a program végén jelzi a memóriaszivárgásokat. Az UBSan az undefined behavior számos formáját észleli, például a null pointer dereferálást, a túlcsordulást és a rossz típusú hozzáférést.

Build és futtatás sanitizerekkel

Egy tipikus fordítási parancs:

g++ -std=c++20 -O0 -g -fsanitize=address,undefined -fno-omit-frame-pointer -o my_program my_program.cpp

A -fsanitize=address bekapcsolja az ASan-t és (Linuxon) az LSan-t, a -fsanitize=undefined az UBSan-t. A -fno-omit-frame-pointer javítja a hívási láncok megjelenítését a hibajelentésben. A program futtatásakor a sanitizer részletes jelentést ad, például:

A hibajelentés megadja a hiba típusát, a hozzáférés és a felszabadítás helyét, valamint a lefoglalás helyét, ami nagyban megkönnyíti a hiba lokalizálását.

A memóriaszivárgás jelzése a program kilépésekor történik, például:

Statikus elemzés

A statikus elemző eszközök, mint a clang-tidy, cppcheck vagy a fordítók beépített figyelmeztetései, futás nélkül is képesek bizonyos hibák felismerésére. Például a clang-tidy a bugprone-* és cppcoreguidelines-* ellenőrzésekkel jelezheti a nyers pointerek tulajdonosi használatát, a hiányzó Rule of 3 implementációt, vagy a gyanús élettartam-kezelést. A -Wall -Wextra -Wpedantic fordítási kapcsolók számos figyelmeztetést adnak, amelyeket érdemes komolyan venni.

Példa clang-tidy futtatásra:

clang-tidy my_program.cpp -- -std=c++20 -I.

Code review szempontok

A code review során a memóriabiztonságra különös figyelmet kell fordítani. Az alábbi ellenőrző kérdések segítenek a hibák felismerésében:

  • Ki a tulajdonos? Minden dinamikus erőforrásnak legyen egyértelmű tulajdonosa, lehetőleg RAII objektum.
  • Van-e nyers new vagy delete? Ha igen, indokolt-e, vagy helyettesíthető smart pointerrel?
  • A másoló és move műveletek helyesek-e? Rule of 0/3/5 betartása.
  • Vannak-e ciklikus shared_ptr hivatkozások? Ha igen, kell-e weak_ptr?
  • A függvények visszaadnak-e mutatót vagy referenciát lokális objektumra?
  • A konténer műveletek érvényteleníthetnek-e iterátorokat vagy referenciákat?
  • A view típusok (string_view, span) élettartama biztosított-e?
  • A get() eredményét nem tároljuk-e el a smart pointer élettartamán túl?

18.4.5 5. Labor: hibaminta-elemzés készítése

A labor célja, hogy a hallgató reprodukálható környezetben azonosítson és kijavítson memóriahibákat, majd sanitizerrel és code review-val ellenőrizze a megoldást. A feladat három szándékosan hibás kódminta elemzéséből áll: egy memory leak, egy double free és egy use-after-free esetből.

Feladat leírása:

  1. Hozzon létre egy C++20 projektet a következő három függvénnyel, amelyek a három hibatípust testesítik meg:
// demo.cpp
#include <iostream>
#include <memory>
#include <string>
#include <string_view>

void leak_demo() {
    int* p = new int(42);
    // szándékos hiba: nincs delete
}

void double_free_demo() {
    int* p = new int(10);
    delete p;
    delete p; // UB: double free
}

std::string_view use_after_free_demo() {
    std::string s = "hello";
    return s; // UB: dangling string_view
}

int main() {
    leak_demo();
    double_free_demo();
    auto sv = use_after_free_demo();
    std::cout << sv << '\n';
}
  1. Fordítsa le a kódot AddressSanitizerrel és UndefinedBehaviorSanitizerrel ellátott buildben, például:
g++ -std=c++20 -O0 -g -fsanitize=address,undefined -fno-omit-frame-pointer -o demo demo.cpp

  1. Futtassa a programot, és rögzítse a kimenetet a mérési naplóba. A várt eredmény: a sanitizer jelzi a double free hibát (és esetleg a use-after-free-t, ha a program eljut odáig; a double free miatt azonban lehet, hogy hamarabb leáll). A memory leak esetén a LeakSanitizer a program végén jelzi a szivárgást. Mivel a program a double free miatt összeomolhat, a leak detektálása nem garantált; ezért érdemes a három hibát külön-külön is tesztelni, például három külön programban, vagy a main-ben kommentezve a többi hívást.

  2. Készítsen egy táblázatot a mérési naplóban, amelyben elkülöníti a várt eredményt (melyik hibatípus milyen sanitizer-üzenetet vált ki) és a mért eredményt (a tényleges futási kimenet). Például:

Teszteset Várt eredmény Mért eredmény
leak_demo LeakSanitizer: leaked 4 bytes (valós kimenet)
double_free_demo AddressSanitizer: attempting double-free (valós kimenet)
use_after_free_demo AddressSanitizer: stack-use-after-scope vagy hasonló (valós kimenet)

A mérési naplóban rögzíteni kell a fordító verzióját, a standardverziót, a fordítási kapcsolókat, a futtatási környezetet (pl. Linux x86-64, kernel verzió) és a futtatások számát. A parancsokat és a teljes kimenetet is szerepeltetni kell.

  1. Javítsa ki a kódot a fejezetben tárgyalt helyes megoldásokkal:

    • a new-t cserélje std::make_unique-ra, így a memory leak megszűnik.
    • a double free-t szüntesse meg: használjon std::unique_ptr-t, vagy törölje a második delete-t.
    • a string_view visszaadást cserélje std::string visszaadásra, így a dangling view megszűnik.

    Fordítsa le ismét sanitizerekkel, és ellenőrizze, hogy a program hiba nélkül fut-e. A mérési naplóban rögzítse az új futtatás kimenetét is.

  2. Végezzen code review-t a saját javított kódján: ellenőrizze, hogy nincs-e nyers new/delete, a tulajdonjogok egyértelműek-e, és a Rule of 0/3/5 teljesül-e. Dokumentálja a megállapításokat.

Ellenőrzés: A labor akkor tekinthető sikeresnek, ha a hallgató bemutatja a hibás kód futtatásának sanitizer-kimenetét, a javított kód hiba nélküli futását, valamint a code review jegyzőkönyvet, amelyben a három hibatípus elkerülésére vonatkozó szabályokat alkalmazza.

18.4.6 6. Összefoglalás

A fejezetben bemutattuk a három leggyakoribb memóriahibát: a memóriaszivárgást, a kettős felszabadítást és a függő pointer használatát. Mindegyik hiba undefined behaviorhez vagy erőforrás-szivárgáshoz vezet, de a modern C++ eszközeivel – RAII, smart pointerek, konténerek, weak_ptr, view típusok körültekintő használata – jelentősen csökkenthető a kockázat. A sanitizerek és a statikus elemzés hatékonyan felderítik ezeket a hibákat, a code review pedig a megelőzésben segít. A következő fejezet (Placement new, alignment és object lifetime) az alacsony szintű memóriakezelésre, a placement new és az objektum-élettartam haladó kérdéseire épít majd.

Önellenőrző kérdések:

  1. Mi a különbség a memory leak és a double free között? Melyik melyik erőforrás-kezelési hibát jelenti?
  2. Hogyan előzhető meg a ciklikus shared_ptr hivatkozások okozta memóriaszivárgás?
  3. Milyen esetekben válhat egy std::string_view függővé?
  4. Melyik sanitizer alkalmas a use-after-free és a double free futás közbeni észlelésére?
  5. Mi a Rule of 0/3/5 lényege, és hogyan segít a double free elkerülésében?
