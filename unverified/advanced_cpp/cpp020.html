6.3 Teljes és részleges specializáció

A generikus kód akkor válik igazán hatékonnyá, ha a sablon által lefedett általános eset mellett képesek vagyunk egyes típusokra vagy típuscsaládokra eltérő, specializált viselkedést adni. A C++ sablonrendszerének egyik legnagyobb ereje éppen az, hogy a specializáció nem csupán futás közbeni elágazás, hanem fordítási időben választódik ki, nulla absztrakciós költséggel. Ebben az alfejezetben a teljes (full) és részleges (partial) specializáció mechanizmusát, a kiválasztási szabályokat (partial ordering) és a SFINAE-barát specializáció gyakorlatát vizsgáljuk meg. A cél, hogy ne csak szintaktikailag tudjunk specializációt írni, hanem értsük is, mit választ a fordító, és miért éppen azt.

6.3.1 A specializáció fogalma és szerepe

A sablon definíciója egy általános recept: a template<typename T> class Storage minden T-re ugyanolyan szerkezetet ír le. A specializáció ennek a receptnek a felülírása egy konkrét T-re vagy T-k egy jól körülhatárolt halmazára. A specializáció nem a sablon példánya, hanem a sablon definíciójának egy alternatívája, amelyet a fordító akkor használ, ha az adott argumentum illeszkedik a specializáció mintájára.

A specializáció két alapvető formája:

  • Teljes specializáció (full/explicit specialization): a sablon összes sablonparamétere konkrét értékre van rögzítve. Például Storage<int> egy teljes specializáció, ahol T = int.
  • Részleges specializáció (partial specialization): a sablonparaméterek egy része még mindig paraméter marad, de egy szűkebb mintát követ. Például Storage<T*> minden mutató típusra vonatkozik, ahol T még szabad. Részleges specializáció csak osztálysablonokra és változósablonokra (C++14-től) létezik; függvénysablonokra nem.

A specializációt nem szabad összekeverni a sablonpéldányosítással. Amikor a fordító találkozik a Storage<int> típussal, megnézi, van-e teljes specializáció Storage<int>-re. Ha igen, azt használja; ha nincs, akkor az elsődleges sablonból (primary template) példányosít T = int-tel. Ha van részleges specializáció, amely illeszkedik, akkor a leginkább specializált részleges specializációt választja, és abból példányosít.

6.3.2 Teljes specializáció (full specialization)

A teljes specializáció szintaxisa osztálysablonra a következő:

// Elsődleges sablon
template<typename T>
class Storage {
public:
    void store(const T& value) { data_ = value; }
    const T& get() const { return data_; }
private:
    T data_{};
};

// Teljes specializáció int-re
template<>
class Storage<int> {
public:
    void store(int value) { data_ = value; }
    int get() const { return data_; }
    // Pl. eltérő belső reprezentáció: int-re lehet bitművelet...
private:
    int data_{};
};

A specializációban a template<> üres sablon-fej jelzi, hogy az összes paraméter rögzített. A specializáció teljesen önálló osztálydefiníció: a tagfüggvények, adattagok, sőt a bázisosztályok is különbözhetnek az elsődleges sablontól. A Storage<int> típus a Storage<int> specializációból jön létre, és semmilyen kapcsolatban nem áll az általános Storage<T> példányokkal.

Teljes specializációt nem csak konkrét típusra, hanem konkrét értékre is készíthetünk nem-típusú sablonparaméter esetén:

template<typename T, std::size_t N>
class Buffer {
    // ...
};

template<typename T>
class Buffer<T, 0> {
    // Üres puffer specializált kezelése
};

Itt a második paraméter konkrétan 0, az első marad szabad. Ez részleges specializáció, mert nem minden paraméter konkrét: az első T még szabad. A teljes specializációhoz mindkettőt rögzíteni kellene: template<> class Buffer<int, 0> { ... };.

6.3.3 Függvénysablonok specializációja: miért kerüljük?

A függvénysablonok is specializálhatók, de a gyakorlatban ezt szinte mindig elkerüljük, és helyette túlterhelést használunk. A probléma abban rejlik, hogy a függvénysablon-specializáció nem vesz részt a túlterhelés feloldásában (overload resolution) úgy, ahogy azt várnánk. A specializáció csak egyetlen sablon definíciójának a variánsa, nem új túlterhelés. Ezért ha egy print függvénysablont szeretnénk int-re specializálni, az nem lesz látható a túlterhelés-feloldás során, amíg a sablon nevét nem választja ki a fordító. A megfelelő eszköz a sima túlterhelés:

template<typename T>
void print(const T& value) {
    std::cout << "generic: " << value << '\n';
}

// Nem specializáció, hanem túlterhelés:
void print(int value) {
    std::cout << "specialized int: " << value << '\n';
}

Ha mégis függvénysablon-specializációt írunk, az könnyen nem hordozható vagy meglepő viselkedéshez vezet, mert az ODR (One Definition Rule) szerint a specializációnak a használat előtt deklaráltnak kell lennie, és a túlterhelés-feloldás során a nem-sablon függvény előnyt élvez. A C++ Core Guidelines is a túlterhelés mellett foglal állást. Így ebben a fejezetben a specializációt elsősorban osztálysablonokra mutatjuk be.

6.3.4 Részleges specializáció (partial specialization)

A részleges specializáció lehetővé teszi, hogy a sablonparaméterek egy részét megtartsuk, de egy szűkebb mintát adjunk meg. A szintaxisban a template<...> fejben felsoroljuk azokat a paramétereket, amelyek még szabadok maradnak, a sablonnév után pedig a mintát írjuk.

Például mutatókra specializálunk:

template<typename T>
class Storage {
    // általános implementáció
};

// Részleges specializáció mutatókra
template<typename T>
class Storage<T*> {
public:
    void store(T* ptr) { ptr_ = ptr; }
    T* get() const { return ptr_; }
private:
    T* ptr_{nullptr};
};

Itt a Storage<T*> minden T* típusra illeszkedik, ahol T egy tetszőleges típus. A Storage<int*> példányosításakor a fordító a részleges specializációt választja, és abból képzi a konkrét típust T = int-tel.

Gyakori minta a tömbökre specializálás is:

template<typename T, std::size_t N>
class Storage<T[N]> {
    // Tömbre optimalizált implementáció, N ismert
};

Ebben az esetben a sablonparaméterek T és N szabadok maradnak, de a minta T[N] korlátozza az illeszkedést. Figyeljük meg, hogy a Storage<T> elsődleges sablonnak csak egy paramétere van (T), míg a részleges specializáció kettőt vezet be (T és N). Ez teljesen legális, mert a specializáció paraméterlistája eltérhet az elsődleges sablonétól; a fordító a mintából következteti ki a paramétereket.

Részleges specializáció készíthető bármilyen típusmintára, például:

  • Storage<const T>: konstans típusokra,
  • Storage<std::vector<T>>: bármely std::vector példányra,
  • Storage<std::unique_ptr<T, D>>: okos mutatókra,
  • Storage<T&>: referenciákra (bár ez ritkább),
  • Storage<T, std::enable_if_t<...>>: SFINAE alapú szűrés (lásd később).

Nem-típusú sablonparaméterek esetén is lehet részleges specializációt írni:

template<typename T, std::size_t N>
class Buffer {
    // általános
};

// N == 1 esetén
template<typename T>
class Buffer<T, 1> {
    // optimalizált, egy elemű puffer
};

Itt a második paraméter rögzített 1, az első szabad – ez a Buffer<T,1> minden T-re érvényes, tehát részleges specializáció.

6.3.5 Választás és partial ordering

Ha több specializáció is illeszkedik az adott sablonargumentumokra, a fordító a leginkább specializált változatot választja. Ezt a folyamatot nevezzük partial ordering-nek. A szabály lényege: egy A specializáció jobban specializált, mint egy B, ha minden argumentumlista, ami illeszkedik A-ra, illeszkedik B-re is, de fordítva nem feltétlenül. A fordító szintaktikus összehasonlítást végez a minták között.

Tekintsük a következő példát:

template<typename T>
class Trait { /* 1: elsődleges */ };

template<typename T>
class Trait<T*> { /* 2: mutatókra */ };

template<typename T>
class Trait<const T*> { /* 3: konstans elemre mutatókra */ };

A Trait<const int*> argumentumra a 2-es és 3-as is illeszkedik. A 3-as minta const T*, ahol T = int. A 2-es minta T*, ahol T = const int. A 3-as minta szűkebb: csak konstans elemre mutató pointerekre illeszkedik, míg a 2-es minden pointerre. Ezért a 3-as a jobban specializált, és a fordító azt választja. A választás a sablonparaméterek mintáinak összevetésével történik: a const T* minta minden T-re egy T* típus is (hiszen const int* egyfajta pointer), de nem minden T* egyben const U*. Így a 3-as specializáció „részhalmaza” a 2-esnek.

A partial ordering formálisabban: a fordító a két sablon definícióját úgy kezeli, mintha az egyik sablonparamétereit szabadon választott fiktív típusokkal helyettesítené, és megnézi, hogy a másik minta tud-e illeszkedni. Ha az egyik irányban igen, a másikban nem, akkor az egyik jobban specializált. Ha mindkét irányban illeszkedik, akkor a két specializáció ekvivalens lehet, és a program hibás (ambiguous). Ha egyik irányban sem, akkor a specializációk nem összehasonlíthatók, és szintén kétértelműség léphet fel.

Gyakorlati példa: Trait<const int*> esetén:

  • Vegyük a 3-as specializációt: Trait<const T*>. Helyettesítsük T-t egy fiktív U típussal: Trait<const U*>. Illeszkedik-e a 2-es mintára? A 2-es minta Trait<T2*>, ahol T2 szabad. const U* átadható-e T2*-nek? Igen, ha T2 = const U. Tehát a 3-asból következik a 2-es.
  • Most vegyük a 2-es specializációt: Trait<T2*>. Helyettesítsük T2-t fiktív V típussal: Trait<V*>. Illeszkedik-e a 3-as mintára? A 3-as Trait<const T*>, azaz a paraméter csak const T* alakú lehet. V* általában nem const T*, csak ha V maga konstans. Tehát nem minden V* illeszkedik a 3-asra. Ezért a 3-as jobban specializált.

Fontos, hogy a partial ordering csak a sablonparaméterek mintáit veszi figyelembe, nem a specializáció törzsét. A törzsben lévő requires-feltételek vagy static_assert-ek nem befolyásolják a választást, legfeljebb a példányosítás sikerét.

6.3.6 SFINAE-barát specializáció

A „SFINAE-barát” kifejezés azt jelenti, hogy a specializáció illeszkedése ne okozzon fordítási hibát olyan típusokra, amelyekre nem szántuk, hanem egyszerűen ne vegyen részt a túlterhelés feloldásában vagy a specializáció kiválasztásában. Bár a SFINAE (Substitution Failure Is Not An Error) elsősorban a függvénysablonok túlterhelésére vonatkozik, az osztálysablonok részleges specializációinál is fontos, hogy a minta ne legyen túl „kapzsi”, és ne illeszkedjen olyan esetekre, ahol a specializáció törzse nem fordul le.

Klasszikus példa: szeretnénk egy is_string_like<T> tulajdonságot, amely akkor igaz, ha T rendelkezik c_str() tagfüggvénnyel és size()-zal. Ezt megtehetjük részleges specializációval és SFINAE-val:

#include <type_traits>

// Elsődleges sablon: nem string-like
template<typename T, typename = void>
struct is_string_like : std::false_type {};

// Részleges specializáció, ha T-nek van c_str() és size()
template<typename T>
struct is_string_like<T, std::void_t<decltype(std::declval<T>().c_str()),
                                      decltype(std::declval<T>().size())>>
    : std::true_type {};

Itt a második sablonparaméter egy névtelen typename = void. A részleges specializáció akkor illeszkedik, ha a std::void_t<...> kifejezés jól formált, azaz T rendelkezik c_str() és size() tagfüggvényekkel. Ha nem, a helyettesítés sikertelen, és a specializáció nem jön szóba – ez a SFINAE-barát viselkedés. Ez a technika lehetővé teszi, hogy a specializációk csak a valóban támogatott típusokra aktiválódjanak, anélkül, hogy a nem megfelelő típusok fordítási hibát okoznának.

C++20-ban ugyanezt kifejezőbben, concepts segítségével is megtehetjük:

#include <concepts>

template<typename T>
concept StringLike = requires(T t) {
    { t.c_str() };
    { t.size() } -> std::convertible_to<std::size_t>;
};

template<typename T>
class Formatter;

template<StringLike T>
class Formatter<T> {
    // string-like típusra specializált
};

Ez a részleges specializáció csak akkor illeszkedik, ha T kielégíti a StringLike conceptet. A fordító a concept-ellenőrzést a specializáció kiválasztása során végzi el, és ha nem teljesül, a specializációt egyszerűen figyelmen kívül hagyja. Ez a modern, olvashatóbb megoldás.

A „SFINAE-barát specializáció” tehát azt a tervezési elvet jelenti, hogy a specializációk mintái ne legyenek túl általánosak, és ne rejtsenek el olyan eseteket, ahol a specializáció törzse hibás lenne. Használjunk std::void_t-et, std::enable_if-et vagy concepteket a specializáció aktiválásához.

6.3.7 A specializáció deklarációjának és definíciójának szabályai

A specializációnak a használat előtt deklaráltnak kell lennie, különben az elsődleges sablonból történik a példányosítás, ami ODR-sértést okozhat. Ez különösen fontos függvénysablon-specializációnál, de osztálysablonoknál is érvényes: a specializációt abban a fordítási egységben kell definiálni (vagy legalább deklarálni), ahol először használják. Ha a specializációt egy headerben deklaráljuk, a definíciót pontosan egy .cpp-ben kell elhelyezni, vagy inline-ként a headerben.

Példa a helyes sorrendre:

// header.h
template<typename T>
class Storage {
    // ...
};

// Deklaráció: a specializáció létezik, de definíció máshol
template<>
class Storage<int>;

// használat másik fájlban:
#include "header.h"
Storage<int> s; // OK: a specializáció deklarált, definíció linkeléskor

Ha a specializáció definíciója nem látható a használat helyén, a fordító az elsődleges sablont példányosítja, és a linkelés során ütközés lép fel, vagy – rosszabb esetben – a program csendben más viselkedést produkál. Ezért a specializációkat mindig deklaráljuk a headerben, és definiáljuk pontosan egyszer.

6.3.8 Gyakori hibák és buktatók

  1. Függvénysablon-specializáció túlterhelés helyett. Ahogy korábban említettük, a függvénysablon-specializáció nem vesz részt a túlterhelés-feloldásban, és könnyen ODR-sértéshez vezet. Használjunk sima túlterhelést vagy if constexpr-t a függvényen belül.

  2. Részleges specializáció függvénysablonra. A C++ nyelv nem engedélyezi függvénysablonok részleges specializációját. A következő kód hibás:

template<typename T>
void process(T* ptr); // OK

// HIBA: részleges specializáció függvénysablonra
template<typename T>
void process<T*>(T* ptr);

Helyette használjunk túlterhelést vagy tagfüggvény-specializációt osztályon belül.

  1. A specializáció definíciója a használat után. A fent leírt ODR-probléma elkerülése érdekében a specializációt a használat előtt kell deklarálni.

  2. Kétértelmű specializációk. Ha két specializáció egyformán illeszkedik, a program hibás. Például:

template<typename T, typename U> class A {};

template<typename T> class A<T, T> {};    // 1: mindkét típus azonos
template<typename T> class A<T, int> {};  // 2: a második típus int

A<int, int> a; // HIBA: kétértelmű (ambiguous), 1 és 2 egyaránt illeszkedik

A fordító ilyenkor hibát jelez, mert a partial ordering nem tud dönteni a két részleges specializáció között.

  1. A specializáció elfelejtése miatt az elsődleges sablon használata. Ha a specializációt nem deklaráljuk a headerben, a felhasználó kódja az általános verziót látja, ami futás közbeni hibához vezethet.

6.3.9 Labor: Általános és specializált implementáció készítése

A labor célja, hogy a fenti fogalmakat egy tesztelhető, fordítható programban rögzítsük. A feladat egy TypeInfo<T> osztálysablon megvalósítása, amely kiírja a típus nevét és méretét. Az általános implementáció a typeid(T).name()-et használja, de a laborban specializációkat adunk meg:

  • Teljes specializáció int-re: a nevét emberileg olvashatóan írja ki ("int").
  • Teljes specializáció std::string-re: kiírja, hogy sztring típus.
  • Részleges specializáció mutatókra (T*): kiírja, hogy „mutató” és a mutatott típus méretét.
  • Részleges specializáció std::vector<T>-re: kiírja, hogy vektor, és az elemtípus méretét.

A programban egy sizeof mérést is végzünk annak demonstrálására, hogy a specializációk eltérő belső reprezentációt is adhatnak. A laborhoz tartozó build-szerződés:

  • Fordító: GCC 13.1, Clang 17 vagy MSVC 19.38 (a hallgató választása szerint, de rögzítve).
  • Szabvány: C++20 (-std=c++20 vagy /std:c++20).
  • Optimalizáció: -O2 (a méréshez -O2 szükséges).
  • Figyelmeztetések: -Wall -Wextra -Wpedantic (GCC/Clang), /W4 (MSVC).
  • Sanitizerek (opcionális): -fsanitize=address,undefined a tesztfuttatáshoz.
  • A tesztkörnyezet: lokális konténer vagy virtuális gép.

A labor kódját a következőképp strukturáljuk:

// typeinfo_lab.cpp
#include <iostream>
#include <string>
#include <vector>
#include <typeinfo>
#include <cstddef>

// Elsődleges sablon
template<typename T>
class TypeInfo {
public:
    static const char* name() {
        return typeid(T).name(); // implementációfüggő, de általános
    }
    static std::size_t size() {
        return sizeof(T);
    }
    // Alapértelmezett flag: nem specializált
    static constexpr bool is_specialized = false;
};

// Teljes specializáció int-re
template<>
class TypeInfo<int> {
public:
    static const char* name() { return "int"; }
    static std::size_t size() { return sizeof(int); }
    static constexpr bool is_specialized = true;
};

// Teljes specializáció std::string-re
template<>
class TypeInfo<std::string> {
public:
    static const char* name() { return "std::string"; }
    static std::size_t size() { return sizeof(std::string); }
    static constexpr bool is_specialized = true;
};

// Részleges specializáció mutatókra
template<typename T>
class TypeInfo<T*> {
public:
    static std::string name() {
        return "pointer to " + std::string(typeid(T).name());
    }
    static std::size_t size() { return sizeof(T*); }
    static constexpr bool is_specialized = true;
};

// Részleges specializáció std::vector<T>-re
template<typename T>
class TypeInfo<std::vector<T>> {
public:
    static std::string name() {
        return "std::vector<" + std::string(typeid(T).name()) + ">";
    }
    static std::size_t size() { return sizeof(std::vector<T>); }
    static constexpr bool is_specialized = true;
};

int main() {
    std::cout << "TypeInfo<double>: " << TypeInfo<double>::name()
              << " size=" << TypeInfo<double>::size() << '\n';
    std::cout << "TypeInfo<int>: " << TypeInfo<int>::name()
              << " size=" << TypeInfo<int>::size() << '\n';
    std::cout << "TypeInfo<std::string>: " << TypeInfo<std::string>::name()
              << " size=" << TypeInfo<std::string>::size() << '\n';
    std::cout << "TypeInfo<int*>: " << TypeInfo<int*>::name()
              << " size=" << TypeInfo<int*>::size() << '\n';
    std::cout << "TypeInfo<std::vector<double>>: "
              << TypeInfo<std::vector<double>>::name()
              << " size=" << TypeInfo<std::vector<double>>::size() << '\n';

    // Ellenőrizzük a specializáció flagjét
    static_assert(!TypeInfo<double>::is_specialized);
    static_assert(TypeInfo<int>::is_specialized);
    static_assert(TypeInfo<int*>::is_specialized);
    static_assert(TypeInfo<std::vector<double>>::is_specialized);
}

A kódban az is_specialized statikus tag segítségével fordítási időben ellenőrizhetjük, hogy a megfelelő specializációt választotta-e a fordító. Ez a labor „várt eredmény” része: a static_assert-eknek fordulniuk kell, és a kimenetben a specializált neveknek kell megjelenniük.

A build parancs (GCC példa):

g++ -std=c++20 -O2 -Wall -Wextra -Wpedantic typeinfo_lab.cpp -o typeinfo_lab
./typeinfo_lab

A várt kimenet (implementációfüggő részekkel):

TypeInfo<double>: d size=8
TypeInfo<int>: int size=4
TypeInfo<std::string>: std::string size=32
TypeInfo<int*>: pointer to i size=8

(A typeid(T).name() rövidített neveket adhat, ez implementációfüggő; a laborban ezt dokumentáljuk.)

A tesztcsomag lehet egy Python szkript vagy shell szkript, amely lefuttatja a programot, és ellenőrzi, hogy a kimenet tartalmazza a várt specializált neveket. Például:

A mérési napló a következőket tartalmazza:

  • Fordító és verzió: pl. g++ (GCC) 13.1.0
  • Szabvány: C++20
  • Optimalizáció: -O2
  • Hardver: (pl. x86_64, 4 mag, 8 GB RAM)
  • Futtatások száma: 3 (a program indítása)
  • Mért érték: a program kimenete és a static_assert-ek sikeres fordítása.
  • Várt érték: a fenti kimeneti minta.
  • Következtetés: a specializációk a várt módon aktiválódtak; a mutató és vektor részleges specializációk, az int és std::string teljes specializációk.

A labor során a hallgatónak módosítania kell a kódot, hogy adjon hozzá egy újabb részleges specializációt pl. std::unique_ptr<T>-re, és ellenőrizze, hogy a static_assert továbbra is teljesül. Ezzel gyakorolja a partial ordering megértését is: ha hozzáadunk egy TypeInfo<const T*> specializációt, mi történik TypeInfo<const int*> esetén? A const T* jobban specializált, mint T*, ezért a const T*-t kell választani. Ezt a hallgatónak fel kell ismernie és bizonyítania.

6.3.10 Önellenőrző kérdés

Adott a következő kód:

template<typename T>
class Wrapper;

template<typename T>
class Wrapper<T*> {
public:
    static constexpr bool is_pointer = true;
};

template<typename T>
class Wrapper<const T*> {
public:
    static constexpr bool is_const_pointer = true;
};

int main() {
    Wrapper<const int*> w;
    static_assert(Wrapper<const int*>::is_const_pointer);
    // static_assert(Wrapper<const int*>::is_pointer); // ?
}

Magyarázza meg, miért nem fordul le a második static_assert, ha a is_pointer tag nem létezik a Wrapper<const T*> specializációban! Miért választja a fordító a const T* specializációt a T* helyett? Indokolja a partial ordering szabályai alapján.

Válasz: A Wrapper<const int*> argumentumra mindkét specializáció illeszkedik: a T* minta T = const int-tel adja a const int*-ot, a const T* minta T = int-tel. A partial ordering szerint a const T* minta jobban specializált, mert minden const T* egyben T* is (ha T = const U), de nem minden T* egyben const U*. Ezért a fordító a Wrapper<const T*> specializációt választja, amelyben nincs is_pointer tag. Így a második static_assert hibás lenne, mert a tag nem létezik. Ez jól mutatja, hogy a specializációk törzse teljesen eltérhet, és a tagok elérhetősége a kiválasztott specializációtól függ.

6.3.11 Összefoglalás

A teljes és részleges specializáció a C++ sablonrendszerének kulcsfontosságú építőkövei. A teljes specializáció egy konkrét argumentumra ad alternatív definíciót, a részleges specializáció pedig a sablonparaméterek egy mintájára szűkíti az illeszkedést. A specializációk közötti választást a partial ordering szabályai határozzák meg: a leginkább specializált minta nyer. A SFINAE-barát specializáció lehetővé teszi, hogy a specializációk csak a valóban támogatott típusokra aktiválódjanak, elkerülve a nem kívánt illeszkedést és a fordítási hibákat. A függvénysablonok specializációja helyett túlterhelést használjunk, a részleges specializációt pedig osztálysablonokra korlátozzuk. A laborban bemutatott TypeInfo példa gyakorlati keretet ad a specializációk kipróbálására és a választási szabályok megfigyelésére. A következő alfejezetben a variadikus sablonokra és paramétercsomagokra építünk, ahol a specializáció még nagyobb rugalmasságot kap.
