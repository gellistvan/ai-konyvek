26.4 Tesztelés, property-based testing és CI

A helyesség és a biztonság folyamatos ellenőrzése nem egyszeri audit, hanem a fejlesztési ciklusba épített, minden változtatásra kiterjedő visszajelzési folyamat. A C++ különösen érzékeny erre, mert az undefined behavior (UB), a memóriakezelési hibák és a konkurencia problémái gyakran csak adott platformon, adott optimalizációs szinten vagy adott ütemezés mellett jelentkeznek. A Hardening, secure coding és supply chain alfejezetben bemutatott sanitizerek, statikus elemzők és hardening-technikák a hiba detektálására szolgálnak; ebben az alfejezetben azt vizsgáljuk, hogyan válik ez a detektálás folyamatos, reprodukálható és a fejlesztési folyamatba szervesen illeszkedő ellenőrzéssé. A cél nem csupán a tesztek megírása, hanem egy olyan csővezeték kialakítása, amely a hibákat a lehető legkorábban, a lehető legkisebb költséggel fogja meg, és a mért eredményeket elkülönítve dokumentálja a várt értékektől.

A folyamatos ellenőrzés három pillére: a determinisztikus unit és property tesztek, a generált bemenetekkel dolgozó fuzz tesztek, valamint a lefedettség- és regresszióelemzés egy automatizált CI-környezetben. Mindhárom más-más hibát tár fel, és együttesen adnak védelmet a helyesség és a biztonság szempontjából.

26.4.1 A tesztpiramis és a folyamatos visszajelzés

A klasszikus tesztpiramis alján a gyors, izolált unit tesztek állnak; középen az integrációs tesztek, a csúcson pedig a lassú, de átfogó rendszer- és end-to-end tesztek. C++-ban ezt a képet kiegészítik a fordítási időben futó tesztek, a sanitizer-futtatások, a fuzz tesztek és a statikus elemzés. Az alfejezet a piramis aljára, valamint a folyamatos integrációra összpontosít, mert ezek adják a leggyorsabb visszajelzést, és ezekből lehet a legtöbb hibát a legolcsóbban kijavítani.

A folyamatos ellenőrzés azt jelenti, hogy minden commit, minden pull request és minden éjszakai build ugyanazt a pipeline-t futtatja. Ennek előfeltétele a reprodukálhatóság: rögzített fordítóverzió, rögzített szabványverzió, rögzített függőségek, rögzített buildkapcsolók és determinisztikus tesztvégrehajtás. Ha egy teszt csak a fejlesztő gépén fut le, az nem tekinthető folyamatos ellenőrzésnek. A CI-ben a „nálam futott” kifejezés helyettesítése a „a pipeline ezen a konfiguráción, ezen a kódon, ezzel a naplóval zöld” állítás.

26.4.2 Unit tesztek: a determinisztikus alap

Az unit teszt a legkisebb viselkedési egységet ellenőrzi, elszigeteli a környezetétől, és determinisztikusan, gyorsan lefut. C++-ban a unit tesztek különösen fontosak az osztályinvariánsok, a kivételbiztonság és az élettartam-kezelés ellenőrzésére. A tesztkeretek – például a GoogleTest, a Catch2, a doctest vagy a Boost.Test – eltérő makrókat és funkciókat kínálnak, de a cél közös: egyetlen sikertelen feltétel esetén a teszt bukjon meg, és a hibaüzenet azonosítsa a fájlt, a sort, valamint a tényleges és várt értéket.

A következő példa egy egyszerű, sablonos fixed_capacity_stack osztályt mutat be, amelyet a további tesztelési rétegek is használnak. Az osztály std::unique_ptr<T[]> tárolót használ, rögzített kapacitással, és a túlcsordulást, illetve az alulcsordulást kivétellel jelzi.

// fixed_capacity_stack.hpp
#pragma once
#include <cstddef>
#include <memory>
#include <stdexcept>
#include <utility>

template <typename T>
class fixed_capacity_stack {
public:
    explicit fixed_capacity_stack(std::size_t capacity)
        : capacity_(capacity), size_(0), data_(std::make_unique<T[]>(capacity)) {}

    fixed_capacity_stack(const fixed_capacity_stack&) = delete;
    fixed_capacity_stack& operator=(const fixed_capacity_stack&) = delete;

    bool empty() const noexcept { return size_ == 0; }
    bool full() const noexcept { return size_ == capacity_; }
    std::size_t size() const noexcept { return size_; }
    std::size_t capacity() const noexcept { return capacity_; }

    void push(const T& value) {
        if (full()) throw std::out_of_range("fixed_capacity_stack::push: stack is full");
        data_[size_++] = value;
    }

    void push(T&& value) {
        if (full()) throw std::out_of_range("fixed_capacity_stack::push: stack is full");
        data_[size_++] = std::move(value);
    }

    T pop() {
        if (empty()) throw std::out_of_range("fixed_capacity_stack::pop: stack is empty");
        return std::move(data_[--size_]);
    }

    const T& top() const {
        if (empty()) throw std::out_of_range("fixed_capacity_stack::top: stack is empty");
        return data_[size_ - 1];
    }

    T& top() {
        if (empty()) throw std::out_of_range("fixed_capacity_stack::top: stack is empty");
        return data_[size_ - 1];
    }

private:
    std::size_t capacity_;
    std::size_t size_;
    std::unique_ptr<T[]> data_;
};

Ez a kód C++17 és C++20 alatt is használható, amennyiben a T típus másolható vagy mozgatható. Az osztály pop függvénye a return std::move(data_[--size_]); kifejezéssel csökkenti a méretet, majd visszaadja az elemet. Ez int esetén tökéletes, de ha T move konstruktora dobhat, a méret már csökkent, mielőtt az érték visszaadása megtörténne, így az erős kivételgarancia sérül. A példa célja a tesztelés bemutatása, ezért a laborban ezt a korlátot is tesztelheted; a teljes kivételbiztos pop implementációhoz a std::is_nothrow_move_constructible_v<T> feltétel vagy más tervezés szükséges.

A unit tesztek ezen az osztályon a következők lehetnek. A példa a doctest keret szintaxisát használja; a pontos include-ok és makrók a keret verziójától függenek, ezért a futtatás előtt ellenőrizd a dokumentációt.

#define DOCTEST_CONFIG_IMPLEMENT_WITH_MAIN
#include <doctest/doctest.h>
#include "fixed_capacity_stack.hpp"

TEST_CASE("fixed_capacity_stack alapvető műveletek") {
    fixed_capacity_stack<int> stack(3);
    REQUIRE(stack.empty());
    REQUIRE(!stack.full());
    stack.push(1);
    stack.push(2);
    REQUIRE(stack.top() == 2);
    REQUIRE(stack.size() == 2);
    REQUIRE(stack.pop() == 2);
    REQUIRE(stack.pop() == 1);
    REQUIRE(stack.empty());
}

TEST_CASE("fixed_capacity_stack túlcsordulás kivételt dob") {
    fixed_capacity_stack<int> stack(1);
    stack.push(42);
    REQUIRE_THROWS_AS(stack.push(43), std::out_of_range);
    REQUIRE(stack.top() == 42);
}

Az ASSERT/REQUIRE makrók a feltétel hamissága esetén azonnal leállítják a tesztesetet, míg a CHECK/EXPECT makrók rögzítik a hibát, de a teszteset tovább fut. C++-ban érdemes az erőforrásokkal és kivételekkel kapcsolatos elvárásokat REQUIRE-rel, a nem kritikus, további diagnosztikát adó ellenőrzéseket pedig CHECK-kel írni. A halálozási tesztek (death test) olyan kódot futtatnak, amelynek meg kell szakadnia, például assert vagy std::terminate hívás miatt; ezeket a keretek külön folyamatban futtatják, így a tesztelő nem omlik össze.

26.4.3 Property-based testing: tulajdonságok és generátorok

A property-based testing a unit tesztek általánosítása: nem egyetlen konkrét bemenetre írunk elvárást, hanem egy tulajdonságot, amely a bemenetek egy egész osztályára igaz. A keret véletlenszerű bemeneteket generál, és ellenőrzi a tulajdonságot; ha hibát talál, a legegyszerűbb ellenpéldára zsugorítja (shrink), hogy a hibajavítás könnyű legyen. A C++-ban az egyik elterjedt eszköz a RapidCheck, amelynek pontos API-ja és szabványtámogatása verziófüggő; az alábbi példa a szemléltetést szolgálja, nem helyettesíti a dokumentációt.

A property-based teszt ereje abban rejlik, hogy a specifikációból származó algebrai törvényeket ellenőrzi, nem pedig az implementáció konkrét kimenetét. A verem esetében ilyen tulajdonságok:

  • LIFO: tetszőleges vektor elemeit pusholva, majd mindet popolva a fordított sorrendet kapjuk.
  • Méret megőrzés: a verem mérete mindig 0 és kapacitás között van, és a push/pop műveletek száma megegyezik a méret változásával.
  • Idempotencia: a top nem változtatja a méretet, és a pop után a verem mérete eggyel csökken.
  • Telítettség: ha a verem tele van, a push kivételt dob; ha üres, a pop kivételt dob.

A következő példa a RapidCheck szintaxisával írja meg ezeket a tulajdonságokat:

#include <rapidcheck.h>
#include "fixed_capacity_stack.hpp"

int main() {
    rc::check("LIFO property", [](const std::vector<int>& input) {
        fixed_capacity_stack<int> stack(input.size() + 1);
        for (int x : input) stack.push(x);
        for (auto it = input.rbegin(); it != input.rend(); ++it) {
            RC_ASSERT(stack.pop() == *it);
        }
        RC_ASSERT(stack.empty());
    });

    rc::check("size property", [](const std::vector<int>& input) {
        fixed_capacity_stack<int> stack(input.size() + 1);
        std::size_t expected = 0;
        for (int x : input) {
            stack.push(x);
            ++expected;
            RC_ASSERT(stack.size() == expected);
        }
        while (!stack.empty()) {
            stack.pop();
            --expected;
            RC_ASSERT(stack.size() == expected);
        }
    });

    rc::check("top is non-mutating", [](const std::vector<int>& input) {
        RC_PRE(!input.empty());
        fixed_capacity_stack<int> stack(input.size());
        for (int x : input) stack.push(x);
        const auto size_before = stack.size();
        const auto top_value = stack.top();
        RC_ASSERT(stack.size() == size_before);
        RC_ASSERT(top_value == input.back());
    });
}

A RC_ASSERT a RapidCheck makrója; a pontos nevet és viselkedést a használt verzió szerint ellenőrizni kell. A RC_PRE előfeltételt ad meg: a tulajdonság csak nem üres bemenetre értelmes. A generátorok típusa a lambda paraméter típusából következik, így a std::vector<int> automatikusan generálódik.

A property-based tesztelés nem mindenre való. Akkor hasznos, ha a bemeneti tér nagy, és a konkrét példák nem fedik le a szélső eseteket; ha a rendszernek algebrai tulajdonsága van, például sorrend, összefésülhetőség, idempotencia; ha a bemenetek és a kimenetek között inverz kapcsolat áll fenn. Ha a tulajdonság túl szoros, a teszt a refaktorálást akadályozza; ha túl gyenge, a hibák rejtve maradnak.

26.4.4 Fuzz teszt: generált bemenetek és robusztusság

A fuzz teszt nem tulajdonságot ellenőriz, hanem azt, hogy tetszőleges, gyakran szemét bemenetre a kód ne okozzon UB-t, ne omoljon össze, és ne szivárogtasson. A coverage-guided fuzzer – például a libFuzzer, az AFL++ vagy az OSS-Fuzz – a bemeneteket aszerint mutálja, hogy mely ágakat fedezték fel; így a tesztelés nem véletlenszerű, hanem a program bejárása által vezérelt.

A C++-ban a libFuzzer belépési pontja egy extern "C" függvény, amely egy bájtsorozatot kap, és azt tetszőlegesen értelmezheti. A következő példa a verem műveleteit vezérli a bemenet bájtjaival:

#include <cstddef>
#include <cstdint>
#include "fixed_capacity_stack.hpp"

extern "C" int LLVMFuzzerTestOneInput(const std::uint8_t* data, std::size_t size) {
    fixed_capacity_stack<int> stack(64);
    for (std::size_t i = 0; i < size; ++i) {
        switch (data[i] % 3) {
            case 0:
                if (!stack.full()) stack.push(static_cast<int>(data[i]));
                break;
            case 1:
                if (!stack.empty()) (void)stack.pop();
                break;
            case 2:
                if (!stack.empty()) (void)stack.top();
                break;
        }
    }
    return 0;
}

Ez a fuzz target soha nem okoz UB-t, mert a push, pop és top hívásokat mindig a megfelelő full() és empty() ellenőrzések védik. A fuzzer mégis hasznos lehet: ha a verem implementációjában rejtett hiba van, például off-by-one, a fuzz bemenete elérheti azt, és a sanitizer (ASan/UBSan) megállítja a futást. A futtatás Clang esetén például:

clang++ -std=c++20 -fsanitize=fuzzer,address,undefined fuzz_stack.cpp -o fuzz_stack
./fuzz_stack -max_total_time=60

A -fsanitize=fuzzer csak Clangben érhető el; GCC-vel az AFL++ használható, MSVC-n pedig a libFuzzer támogatása korlátozott. A pontos kapcsolók platformfüggők, ezért a buildmátrixban rögzíteni kell őket. A fuzz teszt izolált, eldobható környezetben fut, ahogyan a könyv biztonsági irányelvei is előírják.

A fuzzer által talált hibából mindig regressziós unit tesztet kell készíteni, mert a fuzz bemenet önmagában nem dokumentálja a hiba okát, és a futtatás nem része a gyors fejlesztői visszajelzésnek.

26.4.5 Coverage és regresszió

A kódlefedettség megmutatja, hogy a tesztek a forráskód mekkora részét érintik. A leggyakoribb típusok a sorlefedettség (line), az áglefedettség (branch) és a függvénylefedettség. A magas lefedettség szükséges, de nem elégséges: a lefedett kód is tartalmazhat hibát, a nem lefedett ágak pedig rejtik a hiányt. Ráadásul a C++ sablonok és inline függvények miatt a generált kód torzíthatja a mérést, ezért a lefedettségi jelentést nem szabad kizárólag százalékos célként kezelni.

A mérés eszközei platformfüggők: GCC/Clang esetén a --coverage kapcsolóval és a gcov/lcov vagy llvm-cov eszközzel, MSVC-n a natív fedettség használható, de a támogatás verziófüggő. A CI-ben a lefedettségi jelentést minden éjszakai buildben érdemes elkészíteni, és a kritikus biztonsági komponenseknél az áglefedettséget vagy akár az MC/DC-t is figyelembe venni.

A regressziós teszt a hibák visszatérését akadályozza meg. Minden javított hiba után egy olyan tesztet kell írni, amely a hibát reprodukálja. A fuzz által talált bemenetből készült unit teszt tipikus példa: a korpusz bemenetét beépítjük a tesztkészletbe, így a hiba a jövőben azonnal jelez. A regressziós védelem nem csak a kódra, hanem a buildre és a függőségekre is kiterjed: ha egy külső könyvtár frissítése megváltoztatja a viselkedést, a teszteknek ezt is jelezniük kell.

26.4.6 CI-terv: build mátrix és pipeline

A folyamatos ellenőrzés gerince a CI-pipeline, amely minden releváns konfigurációt automatizáltan futtat. A reprodukálhatóság alapkövetelmény: a buildkörnyezet rögzített, a lépések verziózottak, az eredmények naplózottak. A C++-projektek esetében a build mátrix legalább három fő fordítót és két szabványverziót foglal magában.

Egy tipikus pipeline szakaszai:

  1. Konfiguráció: CMake -DCMAKE_BUILD_TYPE=Debug vagy Release, -DCMAKE_CXX_STANDARD=20 vagy 23, -DCMAKE_CXX_COMPILER rögzítve.
  2. Build: párhuzamos fordítás, figyelmeztetések -Wall -Wextra -Wpedantic (MSVC-n /W4 /permissive-), a warnings-as-errors csak a saját kódban.
  3. Unit és property tesztek: gyors, determinisztikus sorrend, sikertelen teszt azonnali leállás.
  4. Sanitizerek: ASan, UBSan, TSan (csak ott, ahol értelmes) Debug módban; a tesztek ugyanazt a kódot futtatják instrumentálva.
  5. Statikus elemzés: clang-tidy, cppcheck, MSVC /analyze; a riportok archiválva.
  6. Fuzz rövid futtatás: limitált idő (például 1-2 perc) a korpusz frissítésére.
  7. Coverage: a unit tesztek lefedettségi jelentése, de nem blokkoló, ha küszöb alatt van, kivéve a kritikus modulokat.
  8. Benchmark: külön futtatás, mert a teljesítmény nem helyesség, de a regresszió jelezheti a nem várt lassulást.

A következő mérési napló kivonat a lényeges elveket mutatja: a várt és a mért érték külön oszlopban szerepel, és a platform, a fordítóverzió, a szabványverzió és a dátum rögzített.

Teszt Várt eredmény Mért eredmény Státusz
fixed_capacity_stack_basic 2 assert pass 2 assert pass OK
fixed_capacity_stack_overflow_throws std::out_of_range std::out_of_range OK
LIFO_property[100 cases] 100 pass 100 pass OK
fuzz_stack_60s no crash no crash, 0 korpusz OK
ASan_unit no error no error OK

A napló csak akkor tekinthető bizonyítéknak, ha a futtatás reprodukálható, és a környezet teljesen dokumentált. A könyv szabályai szerint a nem futtatott benchmarkot vagy ABI-állítást nem szabad ellenőrzött eredményként feltüntetni; ez a tesztnaplóra is érvényes.

A CI-ben a függőségek verziózása és a supply chain biztonság is megjelenik. A csomagkezelő által letöltött könyvtárakat hash vagy lock fájl rögzíti, és a pipeline nem futtat megbízhatatlan forrásból származó kódot. A build reprodukálhatóságát a CI naplók és a build environment rögzítése garantálja.

26.4.7 Tipikus hibák

A tesztelés és a CI során a leggyakoribb hibák a következők:

  • Flaky teszt: nemdeterminisztikus sorrend, időmérés, hálózat, fájlrendszer, rand() fix seed nélkül. A flaky teszt aláássa a bizalmat, mert a fejlesztő ignorálja a hibákat.
  • Globális állapot: statikus objektumok, singletonok, environment változók módosítása; a tesztek sorrendfüggővé válnak.
  • Túlzott mock: az interfész mögött a valós implementációt nem teszteljük; a mock a tesztet tautologikussá teszi.
  • Coverage mint cél: a tesztek a lefedettség növelésére íródnak, nem a specifikációra; a 100% sorlefedettség hamis biztonságérzetet ad.
  • Nem futtatott fuzz/sanitizerek: a CI-ben csak release build fut; a memóriahibák rejtve maradnak.
  • Nem kezelt regresszió: a hibajavítás után nincs reprodukáló teszt, így a hiba visszatérhet.
  • Nem rögzített környezet: a „nálam fut” nem bizonyíték; a CI a fejlesztői géptől eltér.
  • Kizárólag a futásidejű tesztekre hagyatkozás: a fordítási idejű ellenőrzések, például a static_assert, a concepts és a típusrendszer adta lehetőségek kihasználatlanok maradnak.

Ezek a hibák nem a tesztelés hiányából, hanem a tesztelés helytelen céljából erednek. A folyamatos ellenőrzés akkor működik, ha a tesztelés a specifikációt, a biztonsági invariánsokat és a hordozhatóságot szolgálja, nem pedig egy mutatót.

26.4.8 Labor: teszt- és CI-terv készítése

A labor célja, hogy a fenti fixed_capacity_stack (vagy egy saját, hasonlóan kis komponens) teszt- és CI-tervét elkészítsd. A tervnek tartalmaznia kell:

  • A komponens specifikációját: műveletek, előfeltételek, utófeltételek, kivételek.
  • Unit tesztek listáját: legalább öt konkrét eset.
  • Legalább három property-t és egy fuzz target.
  • A lefedettségi stratégiát és a regressziós eljárást.
  • A CI build mátrixot: fordítók, szabványverziók, build típusok, sanitizerek, statikus elemzők.
  • Buildparancsokat, kapcsolókat és mérési napló sablont.

Példa buildparancsok:

# Konfiguráció
cmake -S . -B build/debug-gcc -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_CXX_COMPILER=g++-13 -DCMAKE_CXX_STANDARD=20 \
  -DCMAKE_CXX_FLAGS="-Wall -Wextra -Wpedantic -fsanitize=address,undefined"

# Build és teszt
cmake --build build/debug-gcc --parallel
ctest --test-dir build/debug-gcc --output-on-failure

# Fuzz (külön build, Clang esetén)
clang++ -std=c++20 -fsanitize=fuzzer,address,undefined fuzz_stack.cpp -o fuzz_stack
./fuzz_stack -max_total_time=60

A -max_total_time=60 a libFuzzer kapcsolója; más fuzzer esetén a szintaxis eltér. A -fsanitize=fuzzer csak Clangben érhető el, ezért a buildmátrixban ezt jelezni kell. A CMakeLists.txt minimális vázlata:

cmake_minimum_required(VERSION 3.20)
project(stack_testing LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

add_library(stack_lib INTERFACE)
target_include_directories(stack_lib INTERFACE include)

add_executable(unit_tests tests/unit_tests.cpp)
target_link_libraries(unit_tests PRIVATE stack_lib doctest)

add_executable(property_tests tests/property_tests.cpp)
target_link_libraries(property_tests PRIVATE stack_lib rapidcheck)

A tesztkeretek és a RapidCheck feloldása a csomagkezelőtől függ; a laborban használhatsz például vcpkg-t vagy Conan-t, de a pontos csomagneveket és verziókat a környezetben ellenőrizni kell.

A leadandó: a terv dokumentációja, a futtatott tesztek naplója, a build konfiguráció, és a tapasztalatok leírása. A naplóban a mért és várt eredményeket külön táblázatban kell feltüntetni, a platform, a fordítóverzió, a szabványverzió és a dátum rögzítésével. A napló csak akkor fogadható el, ha a futtatás reprodukálható; a „lokálisan lefutott” megjegyzés nem elegendő.

26.4.9 Önellenőrző kérdések

  1. Mi a különbség az unit teszt és a property-based teszt között? Melyik mikor előnyös?
  2. Hogyan integrálható a fuzz teszt a CI-be anélkül, hogy a futási idő túllépné a korlátot?
  3. Miért nem elégséges a 100%-os sorlefedettség a helyesség igazolásához? Sorolj fel legalább két konkrét hibát.
  4. A verem példában a pop erős kivételgaranciája milyen feltétellel teljesül? Hogyan tesztelnéd ezt a property teszttel?
  5. Hogyan előzhető meg a flaky teszt? Adj meg három megelőző intézkedést.

A fenti kérdésekre adott válaszok nemcsak a fejezet anyagát ellenőrzik, hanem azt is, hogy a folyamatos ellenőrzés elveit képes vagy-e a gyakorlatban alkalmazni. A következő egység (Creational és structural patterns) a klasszikus és modern tervezési mintákat tárgyalja, és épít az itt bevezetett tesztelési és CI-szemléletre: a minták bemutatásánál is hangsúlyt kap, hogy a helyesség és a biztonság folyamatos ellenőrzése nem kiegészítő feladat, hanem a tervezés része.
