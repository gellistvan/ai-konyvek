11.3 Saját type erasure és interface-ek

A std::function, a std::any és a std::variant mögött ugyanaz az alapgondolat húzódik: egyetlen statikus típus képes heterogén, futásidőben meghatározott értékeket tárolni és kezelni. A szabványos eszközök kényelmesek, de nem mindig elég rugalmasak. Amikor saját, testreszabott erasure rétegre van szükség – például egyedi műveletekkel, garantált kis buffer optimalizációval vagy speciális allokátorhasználattal – a kézi type erasure a helyes út. Ez a rész bemutatja a testreszabott type erasure felépítését, a kézi vtable és manual dispatch technikáját, a kis buffer optimalizáció (SBO) megvalósítását, valamint a copy/move és allokátor-szemantika kezelését.

11.3.1 Miért írjunk saját type erasure-t?

A szabványos std::any típus tetszőleges másolható értéket tárol, de a benne rejlő konkrét típus kinyeréséhez any_cast-re van szükség, és a műveletek köre korlátozott (csak tárolás és visszanyerés). A std::function egy adott hívási szignatúrához kötött, és a hívás mellett csak a másolást, mozgatást és a target vizsgálatát támogatja. A std::variant zárt típushalmazzal dolgozik, nem igazi type erasure. Ha olyan absztrakciót akarunk, amely tetszőleges típust fogad, de közben egy jól definiált interfészt exponál – például egy draw(), serialize() vagy invoke() műveletet –, akkor saját erasure típust érdemes építeni.

A testreszabott type erasure klasszikus mintája a következő:

  1. Definiálunk egy belső, tisztán virtuális interfészt (concept), amely a kívánt műveleteket írja le.
  2. Készítünk egy sablonos burkolót (model<T>), amely a konkrét T típusra implementálja ezt az interfészt.
  3. A publikus erasure típus egy unique_ptr-hez hasonló módon birtokol egy ilyen interfészre mutató pointert, és a műveleteket rajta keresztül hívja.

Ez az ún. external polymorphism: a polimorfizmust nem a tárolt típus örökli, hanem egy külső sablonos réteg vezeti be. Ezzel bármilyen típus beilleszthető anélkül, hogy közös ősosztállyal kellene rendelkeznie, illetve anélkül, hogy a tárolt típusnak bármit is tudnia kellene az interfészről.

11.3.2 Kézi vtable és manual dispatch

A virtuális függvények mögött a fordító egy vtable-t (virtuális metódustáblát) generál. A type erasure esetében mi magunk is felépíthetünk egy explicit vtable-t, amely függvénymutatókat tartalmaz. Ez a megközelítés nagyobb kontrollt ad, mert pontosan meghatározhatjuk a műveletek halmazát, és elkerülhetjük a virtuális öröklésből adódó esetleges pluszköltségeket. Ráadásul a függvénymutatók táblája statikusan, a sablonpéldányosításkor jön létre, így nincs szükség külön virtuális osztályokra.

Egy jellemző vtable-szerkezet így néz ki:

struct vtable {
    void (*destroy)(void*) noexcept;
    void (*copy)(void* dest, const void* src);
    void (*move)(void* dest, void* src) noexcept;
    void (*print)(const void*);
    std::size_t (*size)() noexcept;
};

A model<T> sablon minden egyes T-re létrehoz egy statikus vtable példányt, amely a megfelelő függvényekre mutat. Az erasure osztály csak egy void*-ot tárol a konkrét objektumra, és egy pointert a vtable-re. A dispatch mindig a vtable-n keresztül történik:

obj.vtable_->print(obj.ptr_);

Ez a technika gyakran gyorsabb is, mint a többszörös virtuális hívás, mert egyetlen indirekciót jelent, és a függvény pointere közvetlenül hívható. Természetesen a gyakorlatban a különbség gyakran elhanyagolható, de a fő előny a rugalmasság: könnyen hozzáadhatunk olyan műveleteket, amelyek nem részei egyetlen virtuális interfésznek sem, és a táblát akár futásidőben is módosíthatjuk (bár ezt ritkán tesszük).

11.3.3 Kis buffer optimalizáció (SBO)

A fenti vtable-alapú megközelítés egyik hátránya, hogy minden egyes konstruáláskor heap allokációt igényel a tárolt objektum számára. Ezt elkerülhetjük, ha az erasure objektumon belül egy rögzített méretű, jól igazított puffert tartunk fenn, és a kis objektumokat közvetlenül ebbe a pufferbe konstruáljuk. Ezt nevezzük small buffer optimization-nek (SBO) vagy small object optimization-nek (SOO).

Az alapelv:

  • Definiálunk egy belső, std::aligned_storage-hoz hasonló puffert, például alignas(std::max_align_t) std::byte buffer_[N];
  • Ha a tárolandó objektum mérete ≤\le N és az igazítása ≤\le a puffer igazítása, akkor a puffert használjuk, és nem allokálunk.
  • Ha nem fér be, akkor heap allokációra váltunk, és a puffert nem használjuk.

A vtable függvényei mindkét esetet kezelni tudják: a destroy például megvizsgálja, hogy az objektum a pufferben van-e, és ha igen, explicit destruktort hív, különben delete-et. A legtöbb implementáció egy külön bool-t vagy egy enumot tárol erre a célra.

A puffer méretét gondosan kell megválasztani. Ha túl kicsi, a legtöbb valós típus nem fér be, és elveszítjük az SBO előnyét; ha túl nagy, az erasure objektum mérete megnő, ami ronthatja a cache-hatékonyságot és a másolási költséget. Gyakori választás a két-három pointer mérete, vagy például 16–32 bájt. A std::function egyes implementációkban ennél nagyobb puffert használ, de a pontos méret implementációfüggő.

11.3.4 A saját any_sbo tervezése

Készítsünk egy gyakorlati példát: egy any_sbo nevű típust, amely tetszőleges másolható típust tárol, és egy print() műveletet biztosít. A cél a type erasure és az SBO együttes bemutatása. A teljes, fordítható kód a következőképpen épül fel.

Először a belső vtable:

struct vtable {
    void (*destroy)(void*) noexcept;
    void (*copy)(void* dest, const void* src);
    void (*move)(void* dest, void* src) noexcept;
    void (*print)(const void*);
    std::size_t (*size)() noexcept;
};

A model<T> sablon minden egyes T-re implementálja a vtable-t:

template<typename T>
struct model {
    static void destroy(void* p) noexcept {
        static_cast<T*>(p)->~T();
    }
    static void copy(void* dest, const void* src) {
        ::new (dest) T(*static_cast<const T*>(src));
    }
    static void move(void* dest, void* src) noexcept {
        ::new (dest) T(std::move(*static_cast<T*>(src)));
        static_cast<T*>(src)->~T();
    }
    static void print(const void* p) {
        std::cout << *static_cast<const T*>(p);
    }
    static std::size_t size() noexcept {
        return sizeof(T);
    }
    static constexpr vtable value{
        destroy, copy, move, print, size
    };
};

Figyeljük meg, hogy a copy és move függvények placement new-t használnak, és a move a forrás objektumot is destruálja. A print feltételezi, hogy a T típus rendelkezik operator<<-vel, de ez a korlátozás a használat során derül ki.

Most a publikus any_sbo osztály. A puffer méretét sablonparaméterként adhatjuk meg, alapértelmezésként mondjuk 32 bájtot:

template<std::size_t BufferSize = 32>
class any_sbo {
public:
    // ...
private:
    alignas(std::max_align_t) std::byte buffer_[BufferSize];
    const vtable* vtable_ = nullptr;
    void* ptr_ = nullptr;
    bool in_buffer_ = false;
};

A konstruktorok és a destruktor kezelik az élettartamot. A sablonos konstruktor:

template<typename T, typename Decayed = std::decay_t<T>>
    requires (!std::is_same_v<Decayed, any_sbo>)
any_sbo(T&& value) {
    using ValueType = Decayed;
    if constexpr (sizeof(ValueType) <= BufferSize &&
                  alignof(ValueType) <= alignof(std::max_align_t) &&
                  std::is_nothrow_move_constructible_v<ValueType>) {
        ptr_ = ::new (buffer_) ValueType(std::forward<T>(value));
        in_buffer_ = true;
    } else {
        ptr_ = new ValueType(std::forward<T>(value));
        in_buffer_ = false;
    }
    vtable_ = &model<ValueType>::value;
}

Itt a requires feltétel kizárja a másoló konstruktort a sablonból, hogy ne lopja el a másolást. A std::decay_t eltávolítja a referenciát és a cv minősítőket, hogy a tárolt típus érték típus legyen. A std::is_nothrow_move_constructible ellenőrzése azért fontos, hogy a move konstruktor kivételbiztos lehessen; ha a típus move konstruktora dobhat, akkor inkább heap allokációt használunk, ahol a kivétel esetén a memória felszabadítható.

A copy konstruktor:

any_sbo(const any_sbo& other) {
    if (other.vtable_) {
        if (other.in_buffer_) {
            other.vtable_->copy(buffer_, other.ptr_);
            ptr_ = buffer_;
            in_buffer_ = true;
        } else {
            // heap allokáció másoláshoz: egyszerűen hívjuk a copy-t egy új heap objektumra
            ptr_ = ::operator new(other.vtable_->size());
            other.vtable_->copy(ptr_, other.ptr_);
            in_buffer_ = false;
        }
        vtable_ = other.vtable_;
    }
}

A heap másolásnál a tárolt objektum méretére van szükség; ezt a vtable size() függvénye adja vissza, amelyet a model<T> sizeof(T)-vel valósít meg. Így a másoló konstruktor a megfelelő méretű memóriát foglalja le, és a copy művelet oda konstruálja az új objektumot.

A move konstruktor hasonló, de a move függvényt hívja, és a forrást nullázza. A destruktor:

~any_sbo() {
    if (vtable_) {
        vtable_->destroy(ptr_);
        if (!in_buffer_) {
            ::operator delete(ptr_);
        }
    }
}

Az assignment operátorok a copy-and-swap idiómát követhetik, vagy külön kezelhetők. A print művelet:

void print() const {
    if (vtable_) {
        vtable_->print(ptr_);
    }
}

Ez a vázlat jól mutatja a lényeget. A laborban a diákoknak egy teljes, hibamentes implementációt kell készíteniük, beleértve a copy/move assignmentet, a size függvényt és a kivételbiztonságot.

11.3.5 Copy/move és allocator kezelés

A fenti példában a heap allokáció new-t és delete-et használ. Ez a legegyszerűbb, de nem teszi lehetővé egyedi allokátor használatát. A testreszabott type erasure gyakran igényel allokátor-támogatást, különösen beágyazott vagy játékfejlesztői környezetben. Ilyenkor a vtable-be fel kell venni egy clone és destroy műveletet, amelyek az allokátort is megkapják, vagy a vtable-t az allokátor típusával együtt sablonosítjuk.

Egy lehetséges megoldás, ha az erasure típus egy std::pmr::polymorphic_allocator-t tárol, és a model<T> vtable-függvényei ezt használják a memóriakezelésre. Például:

struct vtable {
    void (*destroy)(void*, std::pmr::memory_resource*) noexcept;
    void (*copy)(void* dest, const void* src, std::pmr::memory_resource*);
    // ...
};

Ekkor a destroy a memory_resource-on keresztül szabadítja fel a heap memóriát. A pufferben tárolt objektumoknál értelemszerűen nincs szükség az allokátorra.

A copy/move szemantika kulcskérdése, hogy a másolás során meg kell őrizni az allokátort. Ha az erasure objektum másolása megtörténik, akkor a célobjektum ugyanazt az allokátort kell, hogy használja (vagy egy azzal kompatibilis allokátort). Ezért a copy konstruktor általában átmásolja az allokátort is. A move konstruktor pedig általában ellopja az allokátort, ha az allokátor ezt támogatja, különben másol.

A kivételbiztonság szempontjából a copy konstruktorban a copy hívás dobhat. Ilyenkor biztosítani kell, hogy a már lefoglalt memória felszabaduljon. Ezért a copy függvénynek úgy kell működnie, hogy ha a konstruktor dob, akkor a foglalt memóriát felszabadítja (vagy a hívó kezeli). Az SBO puffernél nincs ilyen gond, mert a memória már a miénk.

11.3.6 A vtable alapú type erasure előnyei és hátrányai

Előnyök:

  • Nincs szükség virtuális öröklésre a tárolt típusok részéről.
  • A műveletek halmaza tetszőlegesen bővíthető.
  • A vtable statikus, így nincs külön objektumonkénti memóriahasználat.
  • Az SBO révén a legtöbb kis objektum heap allokáció nélkül tárolható.
  • A dispatch egyetlen függvénymutató-indirekció, ami gyors.

Hátrányok:

  • A megvalósítás bonyolultabb, mint a std::any vagy std::function használata.
  • A vtable mérete a műveletek számával nő, ami nagyobb kódméretet eredményezhet.
  • A típusbiztonságért mi felelünk; a print például fordítási hibát ad, ha a típus nem streamelhető, de ez a hiba a sablonpéldányosításkor jön elő, nem az erasure típus definiálásakor.
  • Az SBO puffer mérete kompromisszum; ha rosszul választjuk, nem hatékony.

11.3.7 Labor: saját any_sbo típus tervezése

A gyakorlat célja egy működő, tesztelt, mérésekkel alátámasztott any_sbo implementáció elkészítése. A labor a következő lépéseket foglalja magában:

  1. Implementáció: Készíts egy any_sbo osztálysablont, amely a fenti vtable + SBO mintát követi. A vtable tartalmazzon legalább a következő függvényeket: destroy, copy, move, print és size. A puffer mérete legyen sablonparaméter, alapértelmezés 32 bájt. A típus támogassa a másolást, mozgatást, és legyen kivételbiztos.

  2. Build rendszer: Használj CMake-et vagy más build eszközt. A következő fordítási kapcsolókkal dolgozz: GCC 13 vagy Clang 18, C++20 szabvány, -Wall -Wextra -Wpedantic -Werror. Használj AddressSanitizert és UndefinedBehaviorSanitizert a teszteléshez: -fsanitize=address,undefined.

  3. Tesztesetek: Írj legalább három tesztet:

    • Tárolj egy int értéket, és ellenőrizd a print kimenetét.
    • Tárolj egy std::string-et, másold le az any_sbo-t, és ellenőrizd, hogy a másolat független.
    • Tárolj egy nagyobb objektumot (pl. egy 100 bájtos struktúra), amely nem fér a pufferbe, és ellenőrizd a heap allokációt (pl. egy globális számlálóval a new/delete hívásokra). A tesztekhez használj assert-et vagy egy egyszerű tesztkeretet (pl. Catch2, doctest).

  4. Mérési napló: Mérd meg a konstruálási és destruálási időt, valamint a heap allokációk számát a következő esetekre:

    • Kis objektum (pl. int) SBO-val.
    • Nagy objektum (pl. 100 bájtos struct) heap allokációval.
    • Összehasonlításként ugyanez a std::any-vel. A méréshez használj std::chrono::steady_clock-ot, és futtass legalább 100 000 iterációt. Rögzítsd a fordító verzióját, az optimalizációs szintet (-O2), a hardver modelljét és az operációs rendszert. A mért értékeket foglald táblázatba, és külön jelöld a várt értékeket (pl. „0 heap allokáció kis objektum esetén”).

  5. Dokumentáció: Írj egy rövid README-t, amely leírja a típus használatát, a korlátait (pl. a print csak streamelhető típusokra működik), és a mérési eredményeket.

11.3.8 Példa a teljes vtable-re

A teljesség kedvéért álljon itt egy vtable, amely a size függvényt is tartalmazza:

struct vtable {
    void (*destroy)(void*) noexcept;
    void (*copy)(void* dest, const void* src);
    void (*move)(void* dest, void* src) noexcept;
    void (*print)(const void*);
    std::size_t (*size)();
};

template<typename T>
struct model {
    static void destroy(void* p) noexcept { static_cast<T*>(p)->~T(); }
    static void copy(void* dest, const void* src) {
        ::new (dest) T(*static_cast<const T*>(src));
    }
    static void move(void* dest, void* src) noexcept {
        ::new (dest) T(std::move(*static_cast<T*>(src)));
        static_cast<T*>(src)->~T();
    }
    static void print(const void* p) {
        std::cout << *static_cast<const T*>(p);
    }
    static std::size_t size() { return sizeof(T); }
    static constexpr vtable value{ destroy, copy, move, print, size };
};

A heap másolás most már így oldható meg a copy konstruktorban:

any_sbo(const any_sbo& other) {
    if (other.vtable_) {
        if (other.in_buffer_) {
            other.vtable_->copy(buffer_, other.ptr_);
            ptr_ = buffer_;
            in_buffer_ = true;
        } else {
            ptr_ = ::operator new(other.vtable_->size());
            try {
                other.vtable_->copy(ptr_, other.ptr_);
            } catch (...) {
                ::operator delete(ptr_);
                throw;
            }
            in_buffer_ = false;
        }
        vtable_ = other.vtable_;
    }
}

Figyeljük meg a kivételbiztos másolást: ha a copy dob, a lefoglalt memóriát felszabadítjuk, és a kivételt továbbengedjük.

11.3.9 Önellenőrző kérdés

Miért szükséges a vtable-be felvenni a tárolt objektum méretét, ha az erasure típus SBO-t használ? Gondolja végig, mi történne, ha a heap allokáció méretét nem ismernénk a copy konstruktorban.

Válasz: A heap allokációhoz a copy konstruktorban pontosan akkora memóriát kell lefoglalni, amekkora a tárolt objektum mérete. Ha a vtable nem tartalmazná a méretet, akkor nem tudnánk helyesen allokálni, és a copy művelet memóriahibát vagy helytelen viselkedést okozna. Az SBO puffer esetében a méretet a fordítási időben ismerjük (a puffer mérete fix), de a heap esetben futásidőben kell lekérdezni. Ezért a vtable-nek tartalmaznia kell egy size() függvényt.
