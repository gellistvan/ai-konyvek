7.3 Overload resolution és customization points

A túlterhelésfeloldás (overload resolution) a C++ egyik legfontosabb, de leggyakrabban félreértett mechanizmusa. A generikus kódban nem elég tudni, hogy egy függvénynek több túlterhelése van; azt is pontosan érteni kell, hogyan választja ki a fordító a legmegfelelőbbet, és hogyan lehet ezt a kiválasztást a típusok testre szabására használni. A testreszabási pontok (customization points) ebből a mechanizmusból nőttek ki: olyan hívási felületek, amelyeket a felhasználói típusok a saját szemantikájukhoz igazíthatnak anélkül, hogy a generikus kód módosítására lenne szükség.

Ebben az alfejezetben a túlterhelésfeloldás és a testreszabási pontok kapcsolatát vizsgáljuk. A hangsúly a gyakorlati mintán van: a klasszikus using std::swap; trükkön, az argumentumfüggő névfeloldáson (ADL), a C++20 niebloidokon és a testreszabásipont-objektumokon (CPO). A cél, hogy megértsük, miért alakultak ki ezek a minták, milyen hibákat kerülnek el, és hogyan tervezhetünk saját testreszabási pontot helyesen.

7.3.1 A túlterhelésfeloldás alapjai

A túlterhelésfeloldás akkor lép működésbe, ha egy függvényhívás több lehetséges függvényre is illeszkedhet. A folyamat három fő lépésből áll:

  1. Jelöltek (candidate functions) összegyűjtése – a hívás helyén látható összes azonos nevű függvény, plusz az ADL által bevont függvények.
  2. Megvalósítható jelöltek (viable functions) kiválasztása – azok, amelyek paraméterszáma illeszkedik, és minden argumentum konvertálható a megfelelő paramétertípusra.
  3. A legjobb illeszkedés kiválasztása – a konverziós rangok összehasonlításával.

A konverziós rangok csökkenő sorrendben:

  • pontos illeszkedés (exact match) – beleértve az azonos típusokat, a referenciakötéseket és a konstansság hozzáadását;
  • promóció (pl. int → long, float → double);
  • szabványos konverzió (pl. int → double, const T → T);
  • felhasználói konverzió (konstruktor vagy konverziós operátor).

Külön szabály vonatkozik a sablonokra: ha egy nem-sablon függvény és egy függvénysablon is azonos rangú illeszkedést ad, a nem-sablon nyer. Ha két sablon verseng, a specializáltabb (részlegesen rendezés szerint) nyer. Ez a szabály teszi lehetővé, hogy a felhasználói típusokra írt, nem-sablon swap vagy begin függvények elsőbbséget élvezzenek a standard sablonváltozatokkal szemben.

A túlterhelésfeloldás eredménye a generikus kódban is determinisztikus, de a jelöltek halmaza attól függ, mi látszik a hívás helyén. A std::swap például egy függvénysablon a <utility> fejlécben:

template< class T >
void swap( T& a, T& b ) noexcept(/*...*/);

Ha a generikus kódunkban pusztán std::swap(a, b)-t írunk, akkor kizárólag a std névtérbeli túlterhelések vesznek részt, és a felhasználói típusok saját swap függvénye nem látható, hacsak nem a std névtérben definiálták. Ez a gyakorlatban hibás, mert egy osztály hatékony swap műveletét a saját névterébe írják, nem a std-be. A megoldást az ADL és a using deklaráció kombinációja adja.

7.3.2 Argumentumfüggő névfeloldás (ADL)

Az ADL (argument-dependent lookup, más néven Koenig lookup) kiterjeszti a függvényjelöltek halmazát az argumentumok típusaihoz tartozó névterekkel. Ha a hívás argumentuma egy my::S típusú objektum, akkor a fordító automatikusan megvizsgálja a my névteret is, amikor a függvénynevet keresi. Ez az oka annak, hogy a következő kód működik:

namespace my {
    struct S {
        int x;
    };
    void swap(S& a, S& b) noexcept {
        std::swap(a.x, b.x);
    }
}

int main() {
    my::S a{1}, b{2};
    swap(a, b);  // ADL: megtalálja my::swap-ot
}

A swap(a, b) hívásban a my::S argumentum miatt a my::swap is jelölt lesz, annak ellenére, hogy semmilyen using deklaráció nincs. Az ADL a túlterhelésfeloldás jelölthalmazát bővíti, így a felhasználói függvény legyőzheti a standard sablont, ha jobb illeszkedést ad. Itt a my::swap nem-sablon, míg a std::swap sablon, ezért a my::swap nyer.

A generikus kód azonban gyakran nem támaszkodhat arra, hogy minden típusnak van saját ADL által elérhető swap-ja. Az alapértelmezett viselkedést a std::swap adja, de a testreszabást az ADL biztosítja. A kettő összekapcsolására szolgál a klasszikus minta:

template<class T>
void sort_and_swap(T& a, T& b) {
    // ... valamilyen feltételvizsgálat
    using std::swap;   // std::swap elérhető a hívásban
    swap(a, b);        // ADL + std::swap közötti választás
}

A using std::swap; deklaráció a std::swap-ot beemeli a hívás aktuális névterébe, így a jelöltek halmaza tartalmazza:

  • a std::swap sablont,
  • az argumentum típusához tartozó névtérben talált swap függvényeket (ADL),
  • minden más, a hívás helyén látható swap-ot.

A túlterhelésfeloldás ezután kiválasztja a legjobbat. Ha a típusnak van saját swap-ja, az általában pontos illeszkedést ad, és nem-sablon vagy specializáltabb sablon; ha nincs, a std::swap általános implementációja érvényesül. A minta tehát helyesen valósítja meg a „testreszabás, ha van, egyébként alapértelmezés” szemantikát.

Fontos, hogy a using std::swap; nem nyit ajtót a felhasználói swap explicit hívására; az ADL a típus névterét amúgy is bevonja. A using deklaráció célja csupán az, hogy a std::swap akkor is jelölt legyen, ha a hívás helyén nincs más swap a látható névtérben, és az ADL sem talál semmit.

Hasonló minta érvényes a std::begin és std::end függvényekre. A C++11 óta a <iterator> fejlécben elérhetők a szabad std::begin sablonok, és a generikus kód gyakran így néz ki:

template<class Container>
auto first_element(Container& c) {
    using std::begin;
    return begin(c);  // ADL + std::begin
}

Itt is az ADL teszi lehetővé, hogy a felhasználói konténer saját névterében definiált begin függvénye elsőbbséget élvezzen, míg a using std::begin; az alapértelmezett std::begin-t teszi elérhetővé.

7.3.3 Niebloidok és testreszabásipont-objektumok

A C++20 bevezette a niebloid és a customization point object (CPO) fogalmát, hogy a fenti mintát szabványosítsa és biztonságosabbá tegye. A niebloidok olyan függvényobjektumok, amelyek nem függvények, ezért nem vesznek részt az ADL-ben. A std::ranges::swap, std::ranges::begin, std::ranges::size stb. mind ilyen CPO-k. A CPO egy inline constexpr példány egy olyan osztályból, amelynek operator()-a tartalmazza a tényleges logikát.

A CPO elnevezés arra utal, hogy az objektum maga a testreszabási pont: a generikus kód nem using std::swap; swap(a,b);-t ír, hanem közvetlenül std::ranges::swap(a,b);-t. Mivel a std::ranges::swap egy objektum, nem függvény, az ADL nem vonja be a felhasználói névtér swap függvényét. A felhasználói típusokat a CPO belső logikája veszi figyelembe: a CPO operator()-a a megfelelő kifejezést (például a.swap(b) tagfüggvényt, vagy ADL-lel talált szabad swap-ot) hívja meg, és ezt a keresést a CPO saját, ellenőrzött környezetében végzi el.

A niebloid elnevezés tulajdonképpen arra a technikára utal, hogy a CPO-k nem hozhatók létre a hívó által, nem vehetők át referenciaként, és nem mutathatók rájuk. A standard ezt azzal éri el, hogy a CPO típusa nem megadott; a felhasználó csak a nevet látja, a típust nem. (A gyakorlatban a típus gyakran anonim struct-ként van definiálva egy inline constexpr objektum mellett.)

Példa egy leegyszerűsített std::ranges::swap CPO-ra (nem a tényleges szabványos implementáció, hanem annak szerkezete):

namespace std::ranges {
    inline constexpr struct SwapCPO {
        template<class T, class U>
        constexpr auto operator()(T&& t, U&& u) const
            noexcept(noexcept(swap_impl(std::forward<T>(t), std::forward<U>(u))))
        {
            return swap_impl(std::forward<T>(t), std::forward<U>(u));
        }

      private:
        template<class T, class U>
        static constexpr auto swap_impl(T&& t, U&& u)
            noexcept(noexcept(/* belső kifejezések */))
        {
            // 1. Ha létezik t.swap(u) tagfüggvény, hívd meg.
            // 2. Különben ha létezik szabad swap(t,u) ADL által, használd.
            // 3. Különben std::swap(t,u), ha érvényes.
        }
    } swap;
}

A valódi std::ranges::swap bonyolultabb, mert ellenőrzi a típusok konvertálhatóságát, az érvényes kifejezéseket és a noexcept feltételeket, de a szerkezet jól mutatja a lényeget: a CPO a hívó elől rejtett swap_impl-ben végzi a keresést, és nem engedi, hogy a hívó környezetéből származó túlterhelések beavatkozzanak.

A CPO előnyei a klasszikus using std::swap; mintával szemben:

  1. Nincs szükség a using deklarációra – a hívás egyértelmű és a szándék explicitebb.
  2. Az ADL nem szennyezheti a jelölthalmazt – a CPO objektum, nem függvény, így nem vehető fel ADL-jelöltként.
  3. Pontosabb diagnosztika – a CPO belső kifejezései jól ellenőrizhetők, és a hibák a CPO belsejébe mutatnak.
  4. Homogén felület – minden range-adaptor és algoritmus ugyanazt a CPO-stílust használja, így a generikus kód egységesebb.

A niebloidok használata különösen a std::ranges névtérben terjedt el. A std::ranges::begin például nem azonos a std::begin-nel. A std::begin még mindig elérhető, és továbbra is az ADL + using mintát igényli; a std::ranges::begin viszont CPO. A kettő közötti különbség fontos migrációs szempont.

7.3.4 std::swap és std::begin evolúciója

Tekintsük át röviden, hogyan változott a két legismertebb testreszabási pont.

7.3.5 std::swap

A std::swap a C++98 óta létezik, és a klasszikus minta ismert:

template<class T>
void sort(T* first, T* last) {
    // ...
    using std::swap;
    swap(*first, *last);
}

A C++20-ban megjelent a std::ranges::swap CPO, amely a következőket próbálja sorban:

  • ha létezik a.swap(b) tagfüggvény és az megfelelően hívható,
  • egyébként ha létezik szabad swap(a, b) ADL által,
  • egyébként a std::swap sablon általános implementációja (amely move-konstrukciót és move-értékadást használ).

A CPO verzió tehát ugyanazt a háromszintű feloldást végzi, mint a using std::swap; minta, de beépített, ellenőrzött módon. A felhasználónak nem kell using deklarációt írnia, csak std::ranges::swap(a, b);-t.

Fontos megjegyezni, hogy a std::swap és a std::ranges::swap együtt él. A régi generikus kód, amely a using std::swap; mintát használja, továbbra is működik, mert az ADL megtalálja a felhasználói swap-ot, és a std::swap az általános eset. Új kódban azonban érdemes a CPO-t használni.

7.3.6 std::begin és std::end

A std::begin és std::end szabad függvények a C++11 óta. A szabványos konténereknek van begin() tagfüggvényük, így az std::begin sablon hívja azt. A felhasználói konténerek a saját névterükben definiálhatnak szabad begin-t, és a using std::begin; begin(c); minta ezt felhasználja.

A C++20-ban bevezették a std::ranges::begin CPO-t, amely a következőképpen működik:

  • ha a tartomány rendelkezik begin() tagfüggvénnyel, azt hívja;
  • különben ha létezik szabad begin(c) az ADL szerint, azt hívja;
  • különben a tartomány nem tartomány, fordítási hiba.

A CPO tehát kiküszöböli a using std::begin; mintát, és a generikus kód egyszerűen std::ranges::begin(r)-t ír. A régi minta továbbra is működik, de a CPO egységesebb, és jobban illeszkedik a std::ranges ökoszisztémához.

7.3.7 Saját testreszabási pont tervezése

A CPO-k bevezetése után a fejlesztők saját testreszabási pontokat is tervezhetnek. Tegyük fel, hogy egy generikus hash_value függvényt szeretnénk, amely a felhasználói típusok számára testre szabható. A klasszikus ADL-alapú megoldás:

// klasszikus ADL-minta
template<class T>
size_t compute_hash(const T& value) {
    using std::hash;           // nincs ilyen szabad függvény, csak std::hash<T> funktor, tehát ez nem jó
    return hash_value(value);  // ADL keres hash_value-ot
}

Itt a std::hash nem szabad függvény, hanem sablonosztály. A hash_value viszont szabad függvény, és a felhasználói típus definiálhatja a saját névterében. A klasszikus minta tehát:

template<class T>
size_t compute_hash(const T& value) {
    using my::hash_value;  // ha van alapértelmezett
    return hash_value(value);
}

Ez működik, de CPO-val kényelmesebb és szabályosabb. Készítsünk egy hash_value CPO-t, amely a std::hash-hez hasonló testreszabást tesz lehetővé.

#include <concepts>
#include <cstddef>
#include <functional>
#include <type_traits>
#include <utility>

namespace my {

// Alapértelmezett hash_value függvény a hash kiterjesztéséhez
template<class T>
    requires std::is_integral_v<T> || std::is_enum_v<T> || std::is_pointer_v<T>
constexpr std::size_t hash_value_default(const T& value) noexcept {
    return std::hash<T>{}(value);
}

// A CPO típus
struct HashValueCPO {
    template<class T>
        requires requires(const T& t) { { hash_value_default(t) } -> std::convertible_to<std::size_t>; }
    constexpr std::size_t operator()(const T& value) const
        noexcept(noexcept(hash_value_default(value)))
    {
        return hash_value_default(value);
    }
};

// A nyilvános CPO példány
inline constexpr HashValueCPO hash_value{};

} // namespace my

Ez a CPO egyelőre csak az alapértelmezett hash_value_default-ot hívja, de most bővítsük ki ADL-támogatással: ha a típus saját hash_value szabad függvényt definiál a névterében, azt kell használni. A CPO belső logikája a következő lehet:

#include <concepts>
#include <cstddef>
#include <functional>
#include <type_traits>
#include <utility>

namespace my {

// helper függvény az ADL-hez: ezt a CPO hívja
namespace detail {
    // Ez az ADL hook: a felhasználói típus névterében keres hash_value-ot.
    // A 'void' cast elkerüli a "unused" hibákat.
    void hash_value_adl() = delete;
}

struct HashValueCPO {
    template<class T>
        requires requires(const T& t) {
            { hash_value_adl(t) } -> std::convertible_to<std::size_t>;
        }
    constexpr std::size_t operator()(const T& value) const
        noexcept(noexcept(hash_value_adl(value)))
    {
        return hash_value_adl(value);
    }

    // Fallback: ha nincs ADL hash_value, használjuk az alapértelmezettet
    template<class T>
        requires (!requires(const T& t) {
            { hash_value_adl(t) } -> std::convertible_to<std::size_t>;
        })
    constexpr std::size_t operator()(const T& value) const
        noexcept(noexcept(hash_value_default(value)))
    {
        return hash_value_default(value);
    }
};

inline constexpr HashValueCPO hash_value{};

} // namespace my

Itt a hash_value_adl egy eltávolított (deletált) függvényre mutató hívás látszik, de valójában ez a kifejezés a felhasználói névtérben található hash_value-ot keresi, mert a hash_value_adl névvel azonos? Nem, ez félreérthető. A helyes megvalósítás az, hogy a CPO belső operator()-a a hash_value nevet hívja, és az ADL-t egy segédfüggvényen keresztül keresi. A gyakorlatban a CPO így néz ki:

struct HashValueCPO {
    template<class T>
    constexpr std::size_t operator()(const T& value) const
        noexcept(noexcept(hash_value_impl(value)))
    {
        return hash_value_impl(value);
    }

  private:
    // Egy belső függvény, amelyik a felhasználói hash_value-ot ADL-lel keresi.
    template<class T>
    static constexpr auto hash_value_impl(const T& value)
        noexcept(noexcept(hash_value(value)))
    {
        return hash_value(value);  // Ez a hívás ADL-t használ!
    }
};

Itt a hash_value_impl nevű függvény belsejében a hash_value(value) hívás a value típusához tartozó névtereket vizsgálja, mert a hash_value név nem minősített. Így a CPO belseje megtalálja a felhasználói hash_value-ot. Azért kell belső függvénybe tenni, mert a CPO operator()-ában a hash_value nem ADL-t használ, hanem a CPO saját névterét; a belső tagfüggvényben viszont a hash_value nem található a CPO osztályában, ezért az ADL érvényesül. Ez a bevált technika.

A teljes CPO tehát:

#include <cstddef>
#include <functional>
#include <type_traits>
#include <utility>

namespace my {

// Alapértelmezett hash_value, ha nincs felhasználói.
template<class T>
std::size_t hash_value_default(const T& value) {
    if constexpr (std::is_integral_v<T> || std::is_enum_v<T>) {
        return std::hash<T>{}(value);
    } else if constexpr (std::is_pointer_v<T>) {
        return reinterpret_cast<std::uintptr_t>(value);
    } else {
        static_assert(std::is_integral_v<T> || std::is_enum_v<T> || std::is_pointer_v<T>,
                      "No default hash_value for this type");
    }
}

struct HashValueCPO {
    template<class T>
    constexpr std::size_t operator()(const T& value) const
        noexcept(noexcept(hash_value_impl(value)))
    {
        return hash_value_impl(value);
    }

  private:
    template<class T>
    static constexpr auto hash_value_impl(const T& value)
        noexcept(noexcept(hash_value(value)))  // ADL: a T névterében keresi hash_value-ot
    {
        return hash_value(value);
    }

    // Fallback: ha az ADL nem talál hash_value-ot, az alapértelmezettet használjuk.
    template<class T>
    static constexpr auto hash_value_impl(const T& value)
        noexcept(noexcept(hash_value_default(value)))
    {
        return hash_value_default(value);
    }
};

inline constexpr HashValueCPO hash_value{};

} // namespace my

A fenti kódban két hash_value_impl túlterhelés van: az egyik a hash_value(value) ADL-hívást, a másik a hash_value_default(value) hívást végzi. A túlterhelésfeloldás a hash_value_impl(value) hívásban a következőképpen dönt: ha a hash_value(value) kifejezés érvényes (azaz az ADL talál megfelelő függvényt), akkor az első túlterhelés megvalósítható, és mivel az pontos illeszkedést ad, míg a második is megvalósítható, de a hash_value és a hash_value_default azonos rangúak, ezért az első nyer, ha létezik. Ha az ADL nem talál hash_value-ot, az első túlterhelés megvalósíthatatlan, így a második nyer. Ez pontosan a kívánt viselkedés: felhasználói testreszabás, ha van, különben alapértelmezett.

A noexcept specifikációk gondoskodnak a kivételbiztonság konzisztenciájáról.

A CPO használata:

namespace user {
    struct Point {
        int x, y;
    };
    // Felhasználói testreszabás
    std::size_t hash_value(const Point& p) noexcept {
        return static_cast<std::size_t>(p.x) * 31 + p.y;
    }
}

int main() {
    user::Point p{3, 4};
    auto h = my::hash_value(p);  // ADL: user::hash_value hívódik

    int i = 42;
    auto h2 = my::hash_value(i); // nincs ADL, hash_value_default hívódik
}

Ez a példa mutatja a CPO erejét: a generikus kód egyetlen hívást használ, és a típus testreszabhatja a viselkedést anélkül, hogy a generikus kód módosulna. A my::hash_value CPO nem nyitott a hívó oldali using deklarációkra, és a jelöltek halmaza a CPO belsejében ellenőrzött.

7.3.8 A túlterhelésfeloldás és a CPO kapcsolata

A CPO belső logikája ugyanazt a túlterhelésfeloldást használja, mint bármely más kód, de a jelöltek halmazát a CPO szerzője szabályozza. A fenti hash_value példában a hash_value_impl két túlterhelése verseng, és a túlterhelésfeloldás dönt. A ADL-t csak a belső hash_value_impl első túlterhelése használja, a második a hash_value_default-ot hívja, ami viszont nem ADL, tehát az alapértelmezett verzió látható a CPO névterében. Ez a szerkezet megakadályozza, hogy a hívó oldali környezetből származó véletlen túlterhelések bekerüljenek a jelöltek közé.

Fontos megérteni, hogy a CPO operator()-a maga is túlterhelhető, de a hívó oldalon a CPO egyetlen neve szerepel. A CPO tehát egy jól definiált interfész, amely mögött a túlterhelésfeloldás rejtetten dolgozik.

A klasszikus using std::swap; minta lényegében ugyanezt a logikát valósítja meg, de nyíltan: a generikus kódba be kell írni a using deklarációt, és a hívó oldali környezet befolyásolhatja a jelölteket (például ha a hívó névtérben van egy másik swap függvény). A CPO ezt a befolyást zárja ki.

7.3.9 Tipikus hibák és buktatók

  1. Közvetlen std::swap hívás generikus kódban
    Ha a generikus kód std::swap(a, b);-t ír, a felhasználói swap nem vesz részt a túlterhelésfeloldásban, mert az ADL nem vonja be a felhasználói névteret. Ez gyakran teljesítményromláshoz vagy helytelen viselkedéshez vezet. A helyes megoldás a using std::swap; swap(a,b); vagy, C++20-tól, std::ranges::swap(a,b);.

  2. A using std::swap; elhagyása
    Ha a generikus kód swap(a,b);-t ír, de nincs using std::swap;, az ADL megtalálhatja a felhasználói swap-ot, de az alapértelmezett std::swap nem lesz jelölt. Ha a típusnak nincs saját swap-ja, a fordítás hibát ad. A using deklaráció biztosítja a fallback-et.

  3. A felhasználói swap helytelen definiálása a std névtérben
    A std névteret a felhasználó általában nem bővítheti (kivéve bizonyos speciális esetekben, pl. std::hash specializáció). A swap testreszabást a saját típus névterébe kell írni, és az ADL fogja megtalálni. Ha a std névtérbe írunk swap-ot, az sértheti a szabványt, és hiba vagy kétértelműség léphet fel.

  4. A CPO név nem egyezik a felhasználói függvény nevével
    Ha a CPO-t my::hash_value-ként tervezzük, akkor a felhasználói típusnak a saját névterében hash_value nevű függvényt kell definiálnia, nem my::hash_value-t. Az ADL a típus névterét vizsgálja, ezért a felhasználói függvénynek a típus névterében kell lennie.

  5. A niebloidok félreértése
    A std::ranges::swap nem függvény, hanem objektum. Nem lehet rá using deklarációt tenni, és nem lehet ADL-lel kiterjeszteni. A testreszabást a CPO belső logikája által támogatott formában kell megadni (pl. tagfüggvény vagy ADL által megtalálható szabad függvény). Ha a felhasználói típus nem a CPO által elvárt módon definiálja a testreszabást, a kód nem fog lefordulni.

  6. A túlterhelésfeloldás félreolvasása
    A std::swap sablon és a felhasználói swap közötti versenyben a nem-sablon nyer. Ez általában kívánatos, de ha a felhasználói swap maga is sablon, akkor a részleges rendezés dönt. Ez ritkán okoz problémát, de érdemes tudni.

  7. A noexcept specifikáció hiánya a CPO-ban
    A CPO operator()-ának noexcept specifikációját a belső kifejezésből kell származtatni. Ha ez hiányzik vagy rossz, a generikus kód nem tudja optimálisan kihasználni a kivételgaranciákat, és a hibaüzenetek is megtévesztők lehetnek.

7.3.10 Labor: Saját testreszabási pont tervezése

A labor célja egy saját CPO tervezése és tesztelése. A feladat egy hash_value testreszabási pont, amely a fenti mintát követi, és működik a felhasználói típusok ADL-alapú testreszabásával. A kódot reprodukálható környezetben kell lefordítani és tesztelni.

7.3.11 Feladatleírás

  1. Hozz létre egy hash_value CPO-t a my névtérben, amely:
    • a felhasználói típusok számára ADL-lel található hash_value szabad függvényt használ, ha az létezik;
    • egyébként egy alapértelmezett hash_value_default-ot hív, amely std::hash-et használ az integrál, enum és pointer típusokra;
    • noexcept specifikációt származtat.
  2. Definiálj egy Point típust a user névtérben, és adj hozzá saját hash_value függvényt.
  3. Írj teszteseteket, amelyek ellenőrzik:
    • my::hash_value(user::Point{...}) a saját függvény visszatérési értékét adja;
    • my::hash_value(42) az alapértelmezett std::hash<int> értékét adja;
    • a noexcept specifikáció helyes.
  4. Fordítsd a kódot C++20 szabvánnyal, és futtasd a teszteket.

7.3.13 Tesztprogram

// test_hash_value.cpp
#include <cassert>
#include <cstddef>
#include <functional>
#include <type_traits>
#include <utility>

namespace my {

template<class T>
std::size_t hash_value_default(const T& value) {
    if constexpr (std::is_integral_v<T> || std::is_enum_v<T>) {
        return std::hash<T>{}(value);
    } else if constexpr (std::is_pointer_v<T>) {
        return reinterpret_cast<std::uintptr_t>(value);
    } else {
        static_assert(std::is_integral_v<T> || std::is_enum_v<T> || std::is_pointer_v<T>,
                      "No default hash_value for this type");
    }
}

struct HashValueCPO {
    template<class T>
    constexpr std::size_t operator()(const T& value) const
        noexcept(noexcept(hash_value_impl(value)))
    {
        return hash_value_impl(value);
    }

  private:
    template<class T>
    static constexpr auto hash_value_impl(const T& value)
        noexcept(noexcept(hash_value(value)))  // ADL hook
    {
        return hash_value(value);
    }

    template<class T>
    static constexpr auto hash_value_impl(const T& value)
        noexcept(noexcept(hash_value_default(value)))
    {
        return hash_value_default(value);
    }
};

inline constexpr HashValueCPO hash_value{};

} // namespace my

namespace user {
    struct Point {
        int x, y;
    };

    std::size_t hash_value(const Point& p) noexcept {
        return static_cast<std::size_t>(p.x) * 31 + p.y;
    }
}

int main() {
    // 1. Felhasználói testreszabás
    user::Point p{3, 4};
    auto h1 = my::hash_value(p);
    assert(h1 == static_cast<std::size_t>(3) * 31 + 4);

    // 2. Alapértelmezett viselkedés
    int i = 42;
    auto h2 = my::hash_value(i);
    assert(h2 == std::hash<int>{}(42));

    // 3. noexcept ellenőrzés
    static_assert(noexcept(my::hash_value(p)));
    static_assert(noexcept(my::hash_value(i)));

    return 0;
}

7.3.15 Összefoglalás

Az alfejezetben megvizsgáltuk, hogyan kapcsolódik a túlterhelésfeloldás a testreszabási pontokhoz. A klasszikus using std::swap; minta az ADL-t és a túlterhelésfeloldást használja, hogy a felhasználói típusok testreszabhassák a generikus műveletet. C++20-tól a niebloidok és a CPO-k ezt a mintát szabványosították: a CPO objektum, nem függvény, így az ADL nem avatkozik be, a testreszabást pedig a CPO belső logikája, ellenőrzött keretek között végzi. A std::ranges::swap és std::ranges::begin példái mutatják a modern megközelítést, míg a saját hash_value CPO implementációja a gyakorlati tervezést.

A legfontosabb tanulságok:

  • A generikus kódban a testreszabást a típusok környezetébe kell helyezni, és az ADL-t kell használni a felfedezésére.
  • A using std::swap; minta biztosítja az alapértelmezett fallback-et.
  • A CPO-k kiküszöbölik a using deklarációt, és jobb hibadiagnosztikát adnak.
  • A saját CPO tervezésekor a noexcept specifikációt és a túlterhelésfeloldást gondosan kell kezelni.

7.3.16 Önellenőrző kérdés

Miért nem találja meg a következő generikus kód a felhasználói swap-ot, és hogyan javítanád?

template<class T>
void call_swap(T& a, T& b) {
    std::swap(a, b);   // ???
}

Válasz: A std::swap(a, b) hívás minősített névvel hívja a std névtérbeli swap-ot, így az ADL nem kerül alkalmazásra, ezért a T típus saját swap-ja nem vesz részt a túlterhelésfeloldásban. A javítás:

template<class T>
void call_swap(T& a, T& b) {
    using std::swap;
    swap(a, b);
}

vagy C++20-tól:

std::ranges::swap(a, b);

Mindkét esetben a felhasználói swap (ha van) elsőbbséget élvez, és a std::swap az alapértelmezett.
