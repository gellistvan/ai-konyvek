29.4 Modularitás, határok és deployment

A moduláris C++ rendszer és a telepítés (deployment) tervezése a komplex, hosszú élettartamú szoftverek egyik legkritikusabb architekturális döntése. A modularitás nem pusztán a forráskód szervezését jelenti, hanem a bináris összetevők, a futásidejű határok és a telepítési egységek tudatos kialakítását. Ebben a fejezetben a moduláris C++ rendszerek határait, a library–plugin–service hármas felosztást, a verziókezelést és a reprodukálható telepítést járjuk körül. A cél, hogy az olvasó képes legyen megindokolni egy moduláris architektúra döntéseit, felismerje a tipikus csapdákat, és elkészítsen egy ellenőrizhető modul- és deployment-tervet.

29.4.1 A moduláris C++ rendszer fogalma és alapelvei

A moduláris tervezés lényege, hogy egy nagy rendszert kisebb, jól definiált interfészekkel rendelkező egységekre bontunk, amelyek egymástól függetlenül fejleszthetők, tesztelhetők és telepíthetők. A C++ nyelvben a modularitás több szinten jelenik meg:

  • Forráskód szinten: a C++20 module és import kulcsszavai lehetővé teszik a header-alapú világ meghaladását, ahol a fordító számára egyértelműen deklarálható egy modul interfésze és implementációja. A modulok csökkentik a fordítási időt, javítják az izolációt, és explicitté teszik a függőségeket.
  • Bináris szinten: a statikus és dinamikus könyvtárak, valamint a pluginok olyan lefordított artefaktumok, amelyeket a linker vagy a futásidejű betöltő kapcsol össze.
  • Futásidejű szinten: a service-ek külön folyamatokban futnak, és hálózati protokollokon keresztül kommunikálnak, így a legerősebb izolációt biztosítják.

A moduláris C++ rendszer tervezésekor a következő alapelveket kell szem előtt tartani:

  1. Magas kohézió, alacsony csatolás: egy modul egy jól körülhatárolt feladatot lásson el, és minél kevesebb függősége legyen más modulokra. A csatolás irányát úgy kell kialakítani, hogy a magasabb szintű modulok függjenek az alacsonyabb szintűektől, ne fordítva (Dependency Inversion).
  2. Stabil interfészek: a modulok közötti kommunikáció csak a nyilvános interfészen keresztül történjen, amelynek megváltoztatása kompatibilitási törést okozhat. A C++20 modulok esetén az interfész az export-tal jelölt deklarációk halmaza; a header-alapú világban a nyilvános header-ek.
  3. Implementációs részletek elrejtése: a belső típusok, függvények és adattagok ne szivárogjanak ki az interfészre, mert ez szükségtelen függőségeket és ABI-korlátokat teremt. A Pimpl idiom, az opaque pointer és a pimpl with interface osztályok mind ezt szolgálják.
  4. A függőségek irányítása: kerüljük a körkörös függőségeket, mert azok megnehezítik a tesztelést, a párhuzamos fejlesztést és a linkelést. A C++20 moduloknál a körkörös import fordítási hibát okozhat, de a header-alapú világban is kerülendő.

A C++20 modulok használata jelentős előrelépés a modularitás terén. Egy egyszerű modul interfész és implementáció a következőképpen nézhet ki:

// math_core.ixx (modul interfész)
export module math_core;

export int add(int a, int b);
export int multiply(int a, int b);
// math_core.cpp (modul implementáció)
module math_core;

int add(int a, int b) { return a + b; }
int multiply(int a, int b) { return a * b; }

A fenti kód C++20 modult definiál. Fontos megjegyezni, hogy a modulok támogatása a gyakorlatban még nem teljesen egységes a főbb fordítók között (2023–2024-es állapot), ezért sok projekt továbbra is header-alapú vagy hibrid megközelítést használ. A modulok bevezetése nem szünteti meg az ABI-kérdéseket: a modulokból létrejövő objektumfájlok ugyanúgy a linkerhez kerülnek, és a C++ ABI platform- és fordítófüggő marad.

A határok kijelölésekor a következő kérdéseket érdemes feltenni:

  • Mely komponensek változnak gyakran, és melyek stabilak?
  • Mely komponenseknek kell futásidőben cserélhetőnek lenniük (plugin)?
  • Mely komponensek igényelnek külön skálázást vagy izolációt (service)?
  • Milyen a csapat szervezeti felépítése? (Conway törvénye: a rendszer architektúrája tükrözi a szervezet kommunikációs struktúráját.)

29.4.2 Library, plugin és service: a modularitás három szintje

A moduláris C++ rendszerekben három alapvető komponenstípust különböztetünk meg, amelyek a futásidejű határ erősségében és a telepítés módjában különböznek.

29.4.3 Library

A library (könyvtár) egy lefordított bináris egység, amelyet a rendszer más részeivel együtt linkelnek. Lehet statikus (.a, .lib) vagy dinamikus (.so, .dll, .dylib). A statikus könyvtár a linkelés során beépül a végrehajtható állományba, míg a dinamikus könyvtár futásidőben töltődik be, és több folyamat is megoszthatja.

A library határa a processz-memóriatéren belül van: a hívó és a hívott fél ugyanabban a címzési térben fut, a függvényhívások ugyanazt a hívási konvenciót használják, és a memória-hozzáférés közvetlen. Ezért a library interfésze C++ típusokat is használhat, beleértve a std:: osztályokat, feltéve, hogy a hívó és a library ugyanazzal a fordítóval és kompatibilis beállításokkal készült.

Példa egy egyszerű matematikai library interfészére:

// math_library.hpp
#pragma once
#include <cstdint>

namespace math {
    // API: forráskód-szintű kompatibilitás
    int32_t add(int32_t a, int32_t b) noexcept;
    int32_t multiply(int32_t a, int32_t b) noexcept;
}

A library fejlesztésekor a fő szempont az API stabilitása és az ABI megőrzése. Az API változásakor a library-t használó kódot újra kell fordítani; az ABI változásakor az összes binárisan linkelt komponenst újra kell építeni, vagy verziózott szimbólumokat kell használni.

29.4.4 Plugin

A plugin (beépülő modul) olyan dinamikus könyvtár, amelyet futásidőben tölt be a főprogram, és egy jól definiált interfészen keresztül kommunikál vele. A plugin lehetővé teszi a funkcionalitás bővítését az alkalmazás újrafordítása nélkül, ami különösen fontos olyan rendszerekben, ahol a felhasználók vagy harmadik felek bővíthetik a programot.

A plugin határa erősebb, mint a library-é: bár a plugin ugyanabban a processz-címtérben fut, a betöltés dinamikus, és a főprogram általában nem ismeri a plugin típusait a fordítási időben. Ezért a plugin interfésznek stabilnak és ABI-kompatibilisnek kell lennie, lehetőleg C-stílusú vagy minimalista C++ interfésszel.

A pluginok tipikus interfésze a következő elemeket tartalmazza:

  • Egy C-stílusú függvény a plugin inicializálására és leállítására.
  • Egy függvény a plugin által nyújtott funkcionalitás elérésére (pl. egy interfész osztályra mutató pointer visszaadása).
  • A C++ ABI instabilitása miatt gyakran extern "C" deklarációkkal és opaque pointerekkel (pl. void*) dolgoznak.

Példa egy egyszerű plugin interfészre:

// plugin_interface.hpp
#pragma once
#include <cstdint>

// Opaque pointer a plugin által kezelt állapotra
struct PluginContext;

// C interfész a stabil ABI érdekében
extern "C" {
    // Visszaad egy PluginContext* mutatót, vagy nullptr-t hiba esetén.
    PluginContext* plugin_create();
    void plugin_destroy(PluginContext* ctx);
    int32_t plugin_execute(PluginContext* ctx, int32_t input);
}

A plugin betöltése platformfüggő API-kon keresztül történik:

  • Linuxon: dlopen, dlsym, dlclose.
  • Windowson: LoadLibrary, GetProcAddress, FreeLibrary.
  • macOS-en: dlopen (a dlfcn.h fejléc).

A plugin verziókezelése kritikus: a főprogramnak ellenőriznie kell, hogy a betöltött plugin API-verziója kompatibilis-e. Ezt gyakran egy verziószámot visszaadó függvénnyel oldják meg:

// A plugin interfész része
extern "C" int plugin_api_version(); // pl. 1

A főprogram a betöltés után ellenőrzi, hogy a visszaadott verzió megegyezik-e az elvárt értékkel. Ha nem, a plugint el kell utasítani.

29.4.5 Service

A service (szolgáltatás) egy külön folyamatban futó komponens, amely hálózati protokollon keresztül kommunikál a rendszer többi részével. A service határa a legerősebb: a memóriaterek teljesen elkülönülnek, a kommunikáció sorosítást (serialization) és deszerializálást igényel. A service-ek lehetővé teszik a független skálázást, a technológiai heterogenitást (például egy C++ service kommunikálhat egy Python service-szel), és a hibák izolálását.

A service-ek tipikus kommunikációs protokolljai: HTTP/REST, gRPC, saját bináris protokoll TCP-n vagy UDP-n, üzenetsorok (pl. RabbitMQ, Kafka). A C++ service-ek gyakran aszinkron I/O-t használnak (pl. boost::asio, libuv), vagy magasabb szintű keretrendszereket (pl. cpprestsdk, Pistache, nghttp2).

A service-ek esetében a modularitás határa a hálózati API: a szolgáltatás interfészét a protokoll és az üzenetformátum definiálja, nem a C++ típusok. Ezért a verziózás itt a protokoll verziózását jelenti (pl. REST API verzió az URL-ben, gRPC esetén a protobuf definíciók verziózása).

A három komponenstípus összehasonlítása:

Jellemző Library Plugin Service
Határ Processz címtér Processz címtér, dinamikus betöltés Hálózati protokoll
Kommunikáció Függvényhívás Függvényhívás C interfészen Sorosított üzenetek
Skálázás Processz szinten Processz szinten Független, horizontális
Frissítés Újraindítás szükséges Gyakran futásidőben cserélhető Független, rolling update
Teljesítmény Legkisebb overhead Kis overhead Nagyobb overhead (hálózat, sorosítás)

A választás a rendszer követelményeitől függ: ha nagy teljesítmény és szoros integráció kell, library; ha futásidejű bővíthetőség, plugin; ha független skálázás és izoláció, service. Gyakran a három szint kombinálódik: egy service belsejében library-ket használnak, és pluginokkal bővíthető.

29.4.6 Verziózás és kompatibilitás

A moduláris rendszerek életciklusában a verziózás és a kompatibilitás kezelése elengedhetetlen. Két fő fogalmat kell megkülönböztetni:

  • API kompatibilitás (Application Programming Interface): forráskód-szintű kompatibilitás. Ha egy library új verziója API-kompatibilis, akkor a régi forráskód változtatás nélkül lefordítható az új verzióval. Az API változás például egy függvény szignatúrájának megváltoztatása, egy osztály eltávolítása vagy egy paraméter típusának módosítása.
  • ABI kompatibilitás (Application Binary Interface): bináris szintű kompatibilitás. Ha egy library új verziója ABI-kompatibilis, akkor a régi bináris (lefordított kód) változtatás nélkül futtatható az új library-vel. Az ABI magában foglalja a hívási konvenciót, az objektumlayoutot, a névmanipulációt (name mangling), a kivételkezelést és a szimbólumok elérhetőségét.

A C++ szabvány nem rögzíti az ABI-t, ezért a különböző fordítók (GCC, Clang, MSVC) és azok különböző verziói között nem garantált a bináris kompatibilitás. Még ugyanazon fordító esetén is a különböző standard verziók (pl. C++17 vs C++20) vagy a debug/release build beállítások ABI-törést okozhatnak. Ezért a stabil ABI-t igénylő interfészek (pl. pluginok, dinamikus library-k) gyakran C-stílusú interfészt használnak, mert a C ABI széles körben stabilnak tekinthető.

29.4.7 Szemantikus verziózás

A szemantikus verziózás (SemVer) egy elterjedt szabvány a verziószámok értelmezésére: MAJOR.MINOR.PATCH.

  • MAJOR: növelése API-törést vagy viselkedésbeli változást jelez. A MAJOR verzióváltás után a felhasználóknak át kell vizsgálniuk a kódjukat.
  • MINOR: új funkciók hozzáadása, visszafelé kompatibilis módon. A MINOR növelésekor a régi kód továbbra is működik.
  • PATCH: kompatibilis hibajavítások.

A SemVer-t a C++ projektekben is alkalmazzák, de fontos megjegyezni, hogy a C++ nyelvi sajátosságok miatt az API-kompatibilitás önmagában nem garantálja az ABI-kompatibilitást. Például egy új virtuális függvény hozzáadása egy osztályhoz megváltoztatja a vtable layout-ját, ami ABI-törés, még akkor is, ha az API nem változik. Ezért a C++ könyvtáraknál gyakran különbséget tesznek az API és az ABI verzió között.

29.4.8 Dinamikus könyvtárak verziózása

A dinamikus könyvtárak (.so Linuxon, .dll Windowson) verziózása platformfüggő mechanizmusokkal történik:

  • Linuxon a soname (shared object name) mechanizmus: a library fájl neve tartalmazza a verziót (pl. libmath.so.1.2.3), és a linker egy soname-et (pl. libmath.so.1) ágyaz be a függő binárisba. A futásidejű loader a soname alapján keresi a könyvtárat, így a MAJOR verzió váltásakor a soname is változik, megakadályozva az inkompatibilis keveredést.
  • Symbol versioning: a GNU ld version script lehetővé teszi, hogy ugyanazon szimbólumnév különböző verziói éljenek egymás mellett. Ezzel ABI-kompatibilis bővítés érhető el anélkül, hogy a régi szimbólumokat eltávolítanák.
  • Windowson a DLL-ek általában nem hordoznak soname-et; a verziózást a fájlnévben vagy beágyazott erőforrásban szokták jelölni. Az MSVC a C++ ABI-t is gyakran változtatja a compiler verziók között, ezért a stabil plugin interfészek itt is C interfészt használnak.

29.4.9 ABI-stabil interfészek tervezése

A stabil ABI-t igénylő komponenseknél (pluginok, dinamikus library-k) a következő gyakorlatokat érdemes követni:

  1. C interfész használata: extern "C" deklarációk, C típusok (alapvető típusok, C structok), nincs C++ kivétel, nincs std:: típus az interfészen. A C++ kivételek nem léphetik át a modulhatárt, mert a kivételkezelési mechanizmus ABI-függő.
  2. Opaque pointerek: a belső állapotot void* vagy előre deklarált struct pointer mögé rejtjük. A tényleges típust csak az implementáció ismeri, így annak layout-ja szabadon változtatható.
  3. Explicit verziókezelés: minden interfészhez tartozzon egy verziószám (pl. plugin_api_version()), és a betöltő ellenőrizze azt.
  4. Virtuális interfészek kerülése: a C++ virtuális függvények vtable-t igényelnek, amelynek layout-ja ABI-függő. Ha mégis szükséges, a vtable-t is C-stílusú függvénypointer-táblaként lehet megvalósítani.

Példa egy ABI-stabil plugin interfészre, amely egy műveletet hajt végre:

// stable_plugin_api.hpp
#pragma once
#include <cstdint>

// Opaque pointer a plugin kontextusra
struct PluginContext;

// Függvénypointer típusok
using CreateFn = PluginContext* (*)();
using DestroyFn = void (*)(PluginContext*);
using ExecuteFn = int32_t (*)(PluginContext*, int32_t);

// A plugin által exportált függvények
extern "C" {
    int plugin_api_version(); // visszaadja az API verziót
    PluginContext* plugin_create();
    void plugin_destroy(PluginContext* ctx);
    int32_t plugin_execute(PluginContext* ctx, int32_t input);
}

A plugin implementációja:

// my_plugin.cpp
#include "stable_plugin_api.hpp"
#include <cmath>

struct PluginContext {
    int32_t exponent = 2; // példa állapot
};

extern "C" int plugin_api_version() { return 1; }

extern "C" PluginContext* plugin_create() {
    return new PluginContext{};
}

extern "C" void plugin_destroy(PluginContext* ctx) {
    delete ctx;
}

extern "C" int32_t plugin_execute(PluginContext* ctx, int32_t input) {
    return static_cast<int32_t>(std::pow(input, ctx->exponent));
}

A főprogram a dlopen/LoadLibrary segítségével tölti be a plugint, és a dlsym/GetProcAddress segítségével szerzi meg a függvénypointereket. A verzió ellenőrzése után használhatja a plugint.

29.4.10 Verziózás a deploymentben

A deployment szempontjából a verziózás a csomagkezelésben is megjelenik. A függőségek pinelése (a pontos verzió rögzítése) biztosítja a reprodukálható buildet. A modern C++ csomagkezelők (pl. Conan, vcpkg) támogatják a verziókövetést és a függőségi gráf feloldását. A deployment-tervben rögzíteni kell, hogy mely függőségek mely verzióit használjuk, és hogyan kezeljük a biztonsági frissítéseket.

29.4.11 Deployment-terv és reprodukálható build

A deployment-terv az a dokumentum vagy folyamat, amely leírja, hogyan jutnak el a lefordított artefaktumok a célkörnyezetbe, és hogyan frissíthetők. Egy moduláris C++ rendszer esetében a deployment-terv a következőket tartalmazza:

  1. Artefaktumok listája: milyen binárisok (executable, shared library, plugin), konfigurációs fájlok, adatfájlok, erőforrások készülnek.
  2. Telepítési útvonalak: hová kerülnek az egyes artefaktumok a célrendszeren (pl. /usr/local/bin, /usr/local/lib, /etc/myapp/).
  3. Függőségek: milyen rendszerkönyvtárakra, harmadik féltől származó könyvtárakra van szükség, és hogyan telepítjük őket.
  4. Konfigurációkezelés: hogyan kezeljük a környezetfüggő beállításokat (pl. adatbázis URL, portszámok), lehetőleg környezeti változókkal vagy konfigurációs fájlokkal.
  5. Frissítési stratégia: hogyan történik a verzióváltás, a visszagörgetés lehetősége, a leállás nélküli frissítés.

A reprodukálható build elengedhetetlen a megbízható deploymenthez. Ez azt jelenti, hogy ugyanabból a forráskódból, ugyanazzal a build környezettel mindig ugyanaz a bináris áll elő. Ennek feltétele:

  • Rögzített compiler és standard verzió: a build rendszer explicit módon megadja a fordítót (pl. GCC 13.2, Clang 17, MSVC 19.38) és a C++ szabványt (pl. -std=c++20).
  • Hermetikus build: a build nem támaszkodik a rendszeren található, nem rögzített verziójú függőségekre. Ezt konténerizációval (Docker), vagy hermetikus build eszközökkel (Bazel, Nix) érhetjük el.
  • Build cache: a köztes objektumfájlok cache-elése gyorsítja az inkrementális buildet, de nem befolyásolja a reprodukálhatóságot.

A CMake a legelterjedtebb build eszköz C++ projektekhez. Egy moduláris rendszer CMake definíciója a következőképpen nézhet ki:

cmake_minimum_required(VERSION 3.20)
project(ModularSystem VERSION 1.0.0 LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_POSITION_INDEPENDENT_CODE ON)

# Core library
add_library(core SHARED
    src/core/math_core.cpp
)
target_include_directories(core PUBLIC include)

# Plugin (dinamikus betöltésű)
add_library(my_plugin MODULE
    src/plugin/my_plugin.cpp
)
target_include_directories(my_plugin PRIVATE include)

# Service (főprogram)
add_executable(service
    src/service/main.cpp
)
target_link_libraries(service PRIVATE core)

# Telepítési szabályok
install(TARGETS core service
    RUNTIME DESTINATION bin
    LIBRARY DESTINATION lib
)
install(FILES include/math_core.hpp DESTINATION include)

A fenti példában a core egy megosztott library, a my_plugin egy modul (dinamikus betöltésre), a service pedig egy végrehajtható program, amely a core-t linkeli. Az install szabályok meghatározzák a telepítési útvonalakat.

A tesztelés a deployment-terv része: a telepítés előtt automatikus teszteket kell futtatni. Ez magában foglalja a unit teszteket (pl. Catch2, GoogleTest), az integrációs teszteket (a plugin betöltésének tesztje), és az ABI kompatibilitási teszteket. Az ABI kompatibilitás ellenőrzésére eszközök állnak rendelkezésre (pl. abi-compliance-checker, libabigail), amelyek összehasonlítják a library különböző verzióinak ABI-ját.

29.4.12 Labor: modul- és deployment-terv készítése

Ebben a laborban a hallgató feladata egy kis moduláris rendszer megtervezése, megvalósítása, tesztelése és deployment-tervének elkészítése. A rendszer három részből áll:

  1. Core library: egy matematikai műveleteket végző dinamikus library (libmathcore), amely a math_core.hpp interfészt definiálja. A library a add és multiply függvényeket valósítja meg.
  2. Plugin: egy dinamikus betöltésű plugin (libpower_plugin), amely a power műveletet adja hozzá. A plugin a korábban bemutatott C-stílusú interfészt használja (plugin_api.hpp).
  3. Service: egy konzolos alkalmazás (math_service), amely a core library-t használja, és képes a plugint betölteni a futásidőben.

A labor elvégzéséhez a következő lépések szükségesek:

29.4.13 1. Build konfiguráció

Hozzunk létre egy CMake projektet a fenti struktúrával. A build parancsok:

cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DCMAKE_CXX_STANDARD=20
cmake --build build --parallel

A build során figyeljünk a figyelmeztetésekre, és használjunk -Wall -Wextra -Wpedantic kapcsolókat (GCC/Clang) vagy /W4 (MSVC). A build eredményeként a build/ könyvtárban létrejönnek a libmathcore.so, libpower_plugin.so (Linux) és a math_service binárisok.

29.4.14 2. Tesztelés

A teszteléshez készítsünk egy egyszerű tesztprogramot, amely ellenőrzi a core library működését és a plugin betöltését. A teszt lehet egy külön executable, vagy a service --test kapcsolóval futtatható öntesztje.

Példa teszteset (C++ program, amely a service része lehet):

// test_core.cpp (részlet)
#include "math_core.hpp"
#include <cassert>
#include <iostream>

int main() {
    using namespace math;
    assert(add(2, 3) == 5);
    assert(multiply(4, 5) == 20);
    std::cout << "Core tests passed." << std::endl;
    return 0;
}

A plugin betöltésének tesztelésére Linuxon a dlopen használható:

// test_plugin.cpp (részlet)
#include "plugin_api.hpp"
#include <dlfcn.h>
#include <cassert>
#include <iostream>

int main() {
    void* handle = dlopen("./libpower_plugin.so", RTLD_LAZY);
    if (!handle) {
        std::cerr << "Failed to load plugin: " << dlerror() << std::endl;
        return 1;
    }
    auto create = reinterpret_cast<PluginContext* (*)()>(dlsym(handle, "plugin_create"));
    auto execute = reinterpret_cast<int32_t (*)(PluginContext*, int32_t)>(dlsym(handle, "plugin_execute"));
    auto destroy = reinterpret_cast<void (*)(PluginContext*)>(dlsym(handle, "plugin_destroy"));
    auto api_version = reinterpret_cast<int (*)()>(dlsym(handle, "plugin_api_version"));

    assert(api_version && api_version() == 1);
    PluginContext* ctx = create();
    assert(ctx);
    assert(execute(ctx, 2) == 4); // 2^2
    assert(execute(ctx, 3) == 9); // 3^2
    destroy(ctx);
    dlclose(handle);
    std::cout << "Plugin tests passed." << std::endl;
    return 0;
}

A teszteket a build után futtassuk le. A tesztkimenet a “passed” üzenet, a várt eredmény az, hogy minden assert teljesül. A mért eredményt a hallgató rögzíti.

29.4.15 3. Mérési napló

A labor része a mérési napló elkészítése. A következő méréseket kell elvégezni, és a mért és várt értékeket elkülönítve rögzíteni:

  • Build idő: a cmake --build parancs futási ideje. Várt: néhány másodperc (pl. < 5 s). Mért: (a hallgató tölti ki).
  • Bináris méret: a libmathcore.so, libpower_plugin.so, math_service fájlok mérete. Várt: a core library < 100 KB, a plugin < 50 KB, a service < 50 KB (hozzávetőleges). Mért: (a hallgató tölti ki).
  • Futási teljesítmény: a service egy egyszerű benchmarkja, amely 1 000 000 add hívást végez el. Várt: a futási idő < 50 ms (modern hardveren). Mért: (a hallgató tölti ki).

A mérési naplóban rögzíteni kell a hardver specifikációt (CPU, RAM), az operációs rendszert, a fordítót és a standard verziót, valamint a futtatások számát (pl. 3 mérés átlaga).

29.4.16 4. Deployment-terv

A hallgató készítsen egy rövid deployment-tervet, amely tartalmazza:

  • Az artefaktumok listáját és a céltelepítési útvonalakat (pl. /usr/local/bin/math_service, /usr/local/lib/libmathcore.so.1.0.0, /usr/local/lib/mathcore-plugins/libpower_plugin.so).
  • A függőségek listáját (pl. C++20 szabvány, nincs külső függőség a core-hoz, a pluginhoz nincs).
  • A konfigurációkezelést (pl. a plugin elérési útja környezeti változóval).
  • A frissítési stratégiát (pl. a library MAJOR verzióváltásakor a service-t is újra kell indítani; a plugin csere lehetséges leállás nélkül, ha a plugin API verziója kompatibilis).

A deployment-terv részeként ellenőrizzük a verziózást: a core library soname-je libmathcore.so.1, a plugin API verziója 1, a service verziója 1.0.0. A tervben rögzítsük, hogy a jövőbeni MINOR változások (pl. új művelet hozzáadása a core-hoz) nem törhetik meg a kompatibilitást, de MAJOR változás (pl. a függvény szignatúrák megváltoztatása) igen.

29.4.18 Önellenőrző kérdés

Magyarázza meg a különbséget az API és az ABI kompatibilitás között, és indokolja meg, miért kritikus ez a pluginok esetében. Adjon egy konkrét példát arra, amikor egy C++ library API-kompatibilis, de ABI-törést okoz, és javasoljon egy megoldást a stabil plugin ABI fenntartására.

29.4.19 Összefoglalás

A moduláris C++ rendszer és a telepítés tervezése a komplex szoftverek alapvető építőköve. A library, plugin és service hármas felosztás lehetővé teszi a határok erősségének és a frissítési stratégiának a követelményekhez igazítását. A verziózás és a kompatibilitás kezelése – különösen az ABI stabilitás – a C++ nyelvi sajátosságok miatt fokozott figyelmet igényel. A reprodukálható build és a gondosan kidolgozott deployment-terv biztosítja, hogy a rendszer megbízhatóan telepíthető és karbantartható legyen. A fejezetben bemutatott alapelvek és a labor során elkészített modul- és deployment-terv megalapozza a következő egység (RTTI és custom reflection) számára a reflection és az interop témakörét, ahol a moduláris rendszerek dinamikus kiterjesztése és a különböző nyelvekkel való együttműködés kerül előtérbe.
