6.2 Template argument deduction és overload resolution

A sablonargumentum-dedukció a C++ sablonrendszerének egyik legfontosabb mechanizmusa: ez teszi lehetővé, hogy egy std::vector v{1, 2, 3}; vagy egy auto x = f(42); kifejezésben a fordító a kontextusból kikövetkeztesse a hiányzó típusokat. A dedukció nélkül minden sablonpéldányosításkor explicit módon kellene felsorolnunk a típusargumentumokat, ami a gyakorlatban elviselhetetlenül bőbeszédűvé tenné a generikus kódot. Ugyanakkor a dedukció nem varázslat: szigorú szabályok mentén, a függvényparaméterek típusából és a hívás argumentumaiból indul ki, és gyakran kölcsönhatásba lép a túlterhelésfeloldással. Ahhoz, hogy szakértőként megértsük, miért választ a fordító egy adott függvényt, miért nem dedukál egy másikat, és hogyan kerülhetjük el a tipikus csapdákat, pontosan ismernünk kell ezt a két folyamatot. Ez az alfejezet a sablonok alapjaira (Function és class templates) épít, és a következő alfejezet (Teljes és részleges specializáció) specializációs témáihoz is nélkülözhetetlen fogalmi alapot ad.

6.2.1 A sablonargumentum-dedukció alapjai

Amikor egy függvénysablont hívunk, a fordító megpróbálja meghatározni a sablonparaméterek konkrét értékeit úgy, hogy a függvényparaméterek típusa és a hívás argumentumainak típusa „összeilljen”. Tekintsük a legegyszerűbb esetet:

template <typename T>
T identity(T value) {
    return value;
}

int x = 42;
auto y = identity(x); // T = int

A T dedukciója a value paraméter típusából és az x argumentum típusából történik. A paraméter típusa T, az argumentum típusa int, így a fordító a T = int egyenletet oldja meg. Ha több paraméter van, akkor az összes paraméterből származó egyenletnek konzisztensnek kell lennie:

template <typename T>
void pair(T a, T b) {}

pair(1, 2);      // OK, T = int
pair(1, 2.0);    // hiba: T = int és T = double ellentmondás

A dedukció nem végez implicit konverziót: a második hívásnál a 2.0 típusa double, ezért a T számára két különböző értéket kapnánk, ami hibát okoz. Ez fontos eltérés a nem-sablon függvények túlterhelésfeloldásától, ahol az implicit konverziók megengedettek.

A dedukció során a paraméter típusában megjelenő sablonparamétereket a fordító mintának (pattern) tekinti, és az argumentum típusával hasonlítja össze. A minta lehet összetettebb is:

template <typename T>
void process(std::vector<T> const& vec);

std::vector<int> v;
process(v); // T = int

Itt a std::vector<T> const& mintából a T egyértelműen kikövetkeztethető. Vannak azonban úgynevezett nem dedukálható kontextusok is, ahol a minta nem határozza meg a sablonparamétert. Klasszikus példa a beágyazott típus:

template <typename T>
void print_first(typename std::vector<T>::const_iterator it);

std::vector<int>::const_iterator it = ...;
print_first<int>(it); // explicit T szükséges

A typename std::vector<T>::const_iterator kifejezésben a T a bal oldali std::vector<T> részen belül egy beágyazott típusnév előtt áll, és a nyelv szabályai szerint ez a kontextus nem dedukálható. A gyakorlatban ilyenkor explicit sablonargumentumot kell megadnunk, vagy a függvényt úgy kell átalakítani, hogy a dedukció működjön.

6.2.2 Érték, referencia és forwarding reference

A dedukció viselkedése alapvetően függ attól, hogy a paraméter típusa érték, balérték-referencia vagy jobbérték-referencia. Ez a szabályrendszer szoros kapcsolatban áll a move szemantikával és a perfect forwardinggal.

Ha a paraméter típusa érték (T), akkor a dedukció során az argumentum típusából eltávolítjuk a referenciát és a felső szintű const/volatile minősítőket:

template <typename T>
void sink(T value);

int x = 1;
const int cx = 2;
int& ref = x;
const int& cref = cx;

sink(x);    // T = int
sink(cx);   // T = int (a const eltávolítva)
sink(ref);  // T = int (a referencia eltávolítva)
sink(cref); // T = int (a referencia és a const eltávolítva)

Ez a viselkedés felel meg annak, hogy az érték szerinti paraméter saját másolatot kap, így a hívó oldal const-sága nem befolyásolja a függvény belsejét.

Ha a paraméter típusa balérték-referencia (T&), akkor a dedukció során az argumentum típusából csak a referenciát távolítjuk el, a const-ot megtartjuk:

template <typename T>
void observe(T& value);

int x = 1;
const int cx = 2;

observe(x);  // T = int
observe(cx); // T = const int

Ha a paraméter típusa jobbérték-referencia (T&&), akkor a dedukció két esetre bomlik. Ha az argumentum jobbérték, akkor a T maga az alap típus lesz, és a paraméter jobbérték-referenciaként viselkedik. Ha azonban az argumentum balérték, akkor a T balérték-referencia típus lesz, és a referencia összeolvadás (reference collapsing) szabályai miatt a paraméter típusa balérték-referenciává válik. Ezt a speciális esetet nevezzük forwarding reference-nek (korábban univerzális referenciának):

template <typename T>
void forward(T&& value);

int x = 1;
const int cx = 2;

forward(x);       // T = int&,        param típus: int&
forward(cx);      // T = const int&,  param típus: const int&
forward(42);      // T = int,         param típus: int&&

A forwarding reference alapvető fontosságú a perfect forwarding megvalósításához, mivel a T pontosan megőrzi az argumentum értékkategóriáját és const-ságát. A dedukció során a T lehet referencia típus is, ami elsőre szokatlan, de a referencia-összeolvadás szabályai ezt kezelhetővé teszik.

6.2.3 Tömb- és függvényparaméterek

A dedukció speciálisan kezeli a tömböket és a függvényeket, mert ezek a paraméterátadás során gyakran pointerré degradálódnak. Ha a paraméter típusa érték szerinti T, akkor a tömb argumentum pointerré alakul, és a T pointer típus lesz:

template <typename T>
void f(T value);

int arr[5];
f(arr); // T = int* (a tömb degradálódik)

Ha azonban a paraméter típusa T&, akkor a tömb nem degradálódik, és a T maga a tömb típus lesz, mérettel együtt:

template <typename T>
void g(T& value);

int arr[5];
g(arr); // T = int[5], param típus: int(&)[5]

Ez a viselkedés teszi lehetővé a tömb méretének fordítási idejű kinyerését:

template <typename T, std::size_t N>
constexpr std::size_t array_size(T (&)[N]) noexcept {
    return N;
}

int arr[5];
static_assert(array_size(arr) == 5);

A függvénytípusok hasonlóan viselkednek: érték szerinti paraméter esetén függvénypointer, referencia esetén függvényreferencia lesz.

6.2.4 auto és a dedukció

A auto típusdedukció a C++11 óta ugyanazokat a szabályokat követi, mint a függvénysablon-paraméterek dedukciója érték szerinti paraméter esetén, egyetlen kivétellel: a kapcsos inicializálólista kezelése. A auto segítségével a fordító a jobb oldali kifejezés típusából következtet:

int x = 1;
const int& cref = x;

auto a = x;      // int
auto b = cref;   // int (const és referencia eltávolítva)
auto& c = cref;  // const int& (explicit referencia megőrzi a const-ot)
auto&& d = 42;   // int&&
auto&& e = x;    // int&

A auto&& ugyanúgy forwarding reference-ként működik, mint a T&& a sablonban. A decltype(auto) ezzel szemben a decltype szabályait használja, így megőrzi a referencia- és const-ságot:

int x = 1;
const int& cref = x;

decltype(auto) f = x;    // int&
decltype(auto) g = cref; // const int&
decltype(auto) h = 42;   // int

A auto és a sablon-dedukció közötti apró eltérések (például a {} inicializáló) a gyakorlatban ritkán okoznak gondot, de érdemes tudni róluk.

6.2.5 Túlterhelésfeloldás sablonokkal

Amikor több függvény is szóba jöhet egy hívásnál, a fordító a túlterhelésfeloldás (overload resolution) folyamatát futtatja le. A folyamat három fő lépésből áll:

  1. Jelöltek összegyűjtése: a fordító összegyűjti az összes elérhető függvényt és függvénysablont, amelynek neve megegyezik a hívott névvel.
  2. Életképesség ellenőrzése: minden jelölt esetében ellenőrzi, hogy a hívás argumentumai megfelelnek-e a paramétereknek. Sablonoknál ez magában foglalja a sablonargumentum-dedukciót is. Ha a dedukció sikertelen, a jelölt kiesik (SFINAE kontextusban ez nem hiba, lásd lejjebb).
  3. Rangsorolás: az életképes jelöltek közül a „legjobb” kiválasztása a konverziós rangok alapján. A legjobb az, amelyik a legkevesebb implicit konverziót igényli.

Sablonok esetén a dedukció után a létrejött példányosítás ugyanúgy részt vesz a rangsorolásban, mint egy nem-sablon függvény. Ha egy sablon és egy nem-sablon függvény is életképes, és a konverziós rangok azonosak, akkor a nem-sablon függvény nyer. Ez a szabály biztosítja, hogy egy konkrét túlterhelés felülírja az általános sablont:

void f(int);
template <typename T>
void f(T);

f(42); // a nem-sablon f(int) hívódik

A rangsorolás a konverziós rangok alapján történik: az exact match (pontos egyezés) jobb, mint a promóció (pl. int → long), ami jobb, mint a konverzió (pl. int → double). A sablon-dedukció gyakran pontos egyezést eredményez, mert a paraméter típusa pontosan az argumentum típusához igazodik. Például:

void g(long);
template <typename T>
void g(T);

int x = 1;
g(x); // a sablon g<int>(int) pontos egyezés, a nem-sablon g(long) promóció

Itt a sablon nyer, mert a long-ra történő konverzió promóciónak számít, míg a sablon int paraméterrel pontosan illeszkedik.

A sablonok közötti rangsorolás további finomságokat rejt. Ha két sablon is életképes, és a dedukált típusok különbözőek, akkor a specifikusabb sablon nyer. A specifikusságot a partial ordering (részleges rendezés) szabályai határozzák meg. Például:

template <typename T>
void h(T);       // (1) általános

template <typename T>
void h(T*);      // (2) pointerre specifikusabb

int x = 1;
h(&x); // mindkettő életképes, de (2) specifikusabb, mert T* szűkebb, mint T

A részleges rendezés során a fordító szintetikusan megpróbálja az egyik sablont a másikkal szemben „dedukálni”: ha az egyik mintája sikeresen dedukálható a másikból, de fordítva nem, akkor az előbbi specifikusabb. A T* mintából a T nem dedukálható, mert a T* nem illeszthető minden T-re, így a pointeres változat nyer.

Fontos megjegyezni, hogy a túlterhelésfeloldás nem veszi figyelembe a függvények visszatérési típusát. A visszatérési típus csak a hívás eredményének felhasználása után válik ellenőrzötté. Ezért ha két függvény ugyanolyan paraméterlistával rendelkezik, de eltérő visszatérési típussal, az fordítási hibát okoz, kivéve, ha a kontextus egyértelművé teszi a választást.

6.2.6 SFINAE és a dedukciós hibák

A túlterhelésfeloldás során a sablon-dedukció sikertelensége nem feltétlenül fordítási hiba. A SFINAE (Substitution Failure Is Not An Error) elv alapján, ha a sablonparaméterek behelyettesítése a függvény szignatúrájában hibát okoz, akkor az adott jelölt egyszerűen kiesik a jelöltek közül, és a fordító más jelölteket próbál. Ez a mechanizmus a enable_if-es és a void_t-s technikák alapja, amelyeket a következő alfejezetben (SFINAE és enable_if) tárgyalunk részletesen. Itt elég annyit rögzítenünk, hogy a dedukció sikertelensége és a behelyettesítési hiba között különbség van: a dedukció hibája általában SFINAE-barát, míg a függvénytörzsben lévő hiba már fordítási hibát okoz.

6.2.7 Deduction guide és CTAD

A CTAD (Class Template Argument Deduction) a C++17-ben bevezetett nyelvi eszköz, amely lehetővé teszi, hogy osztálysablonok példányosításakor a sablonargumentumokat a konstruktor argumentumaiból következtesse ki a fordító, anélkül hogy explicit módon megadnánk azokat. A legegyszerűbb példa:

std::vector v{1, 2, 3}; // std::vector<int>
std::pair p{42, "hello"}; // std::pair<int, const char*>

A CTAD alapértelmezés szerint a konstruktorokból és az osztálysablon paramétereiből implicit módon generálódik. A fordító minden konstruktorhoz létrehoz egy implicit deduction guide-ot, amely a konstruktor paramétereinek típusából dedukálja az osztálysablon paramétereit. Ez a legtöbb esetben elegendő, de vannak helyzetek, amikor az implicit szabály nem megfelelő: például amikor a konstruktor nem tükrözi közvetlenül a tárolt típusokat, vagy amikor a dedukciót korlátozni szeretnénk.

A deduction guide egy explicit, a sablon paraméterlistájától független deklaráció, amely megadja, hogy adott konstruktor-paraméterekből hogyan származzanak az osztálysablon argumentumai. A szintaxis a következő:

template <typename T>
class MyContainer {
public:
    template <typename Iter>
    MyContainer(Iter first, Iter last);
};

// Dedukciós útmutató: iterátorokból az értéktípus
template <typename Iter>
MyContainer(Iter, Iter) -> MyContainer<typename std::iterator_traits<Iter>::value_type>;

Ezzel a MyContainer c(begin, end); kifejezésben a T az iterátor által mutatott értéktípus lesz, nem pedig az iterátor típusa. Az implicit deduction guide ebben az esetben nem tudná kitalálni, hogy a T mire vonatkozzon, mert a konstruktor sablonparamétere Iter, nem pedig a tárolt típus.

A deduction guide-oknak fontos szerepük van a kompatibilis API-k kialakításában. Például a std::array esetében a CTAD automatikusan működik, mert a konstruktor nem hordozza a méretet, ezért a szabványkönyvtár explicit deduction guide-ot ad:

template <typename T, typename... U>
array(T, U...) -> array<T, 1 + sizeof...(U)>;

Ez lehetővé teszi a std::array a{1, 2, 3}; kifejezést, ahol a méret fordítási időben derül ki. C++20-tól a std::array CTAD-je a std::to_array-rel együtt még kényelmesebb.

A deduction guide-ok túlterhelhetők, és a túlterhelésfeloldás ugyanúgy vonatkozik rájuk, mint a függvényekre. A fordító a konstruktorok és a deduction guide-ok halmazából választja ki a legjobbat. Ha egy deduction guide nem életképes, az SFINAE-ként kiesik. Ez lehetővé teszi, hogy a dedukciót feltételekhez kössük:

template <typename T>
class Wrapper {
public:
    Wrapper(T value);
};

// Csak egész típusokra engedélyezett dedukció
template <typename T>
requires std::integral<T>
Wrapper(T) -> Wrapper<T>;

6.2.8 CTAD és a auto

A CTAD és a auto közötti különbség fontos. A auto változódeklarációban nem hívható CTAD: a auto v = std::vector{1,2,3}; kifejezésben a jobb oldali kifejezés önálló CTAD-t igényel, ami működik, de a auto által dedukált típus pontosan a jobb oldali kifejezés típusa lesz. A auto v{1,2,3}; viszont std::initializer_list<int>-t dedukál, nem std::vector<int>-et. A CTAD kifejezetten osztálysablon-példányosításra vonatkozik, nem változódeklarációra.

6.2.9 Perfect forwarding

A perfect forwarding (tökéletes továbbítás) azt jelenti, hogy egy függvény a paramétereit pontosan ugyanolyan értékkategóriával és const-sággal adja tovább egy másik függvénynek, mint ahogyan megkapta. Ez a technika nélkülözhetetlen a wrapper függvények, factory függvények és a std::make_unique, std::make_shared, std::emplace stb. megvalósításához.

A perfect forwarding két pilléren nyugszik:

  1. Forwarding reference: a T&& paraméter, ahol T sablonparaméter, képes mind bal-, mind jobbértéket fogadni, és a dedukció során pontosan megőrzi az eredeti típust.
  2. std::forward: a <utility> fejlécben definiált segédfüggvény, amely a dedukált T alapján visszaállítja az eredeti értékkategóriát.

A std::forward lényege, hogy ha a T balérték-referencia, akkor balértéket ad vissza, egyébként jobbértéket. A hívás szintaxisa látszólag redundáns, mert explicit sablonargumentumot igényel:

template <typename T>
void wrapper(T&& arg) {
    sink(std::forward<T>(arg)); // T-t explicit megadjuk
}

A std::forward<T>(arg) kifejezés értékkategóriája a T típusától függ: - Ha T = int&, akkor std::forward<int&>(arg) balértéket ad, így a sink balérték-referenciát kap. - Ha T = int, akkor std::forward<int>(arg) jobbértéket ad, így a sink jobbérték-referenciát kap, és a move konstruktor hívódhat.

A std::forward implementációja tipikusan a következő (egyszerűsítve):

template <typename T>
constexpr T&& forward(std::remove_reference_t<T>& arg) noexcept {
    return static_cast<T&&>(arg);
}

template <typename T>
constexpr T&& forward(std::remove_reference_t<T>&& arg) noexcept {
    static_assert(!std::is_lvalue_reference_v<T>, "bad forward call");
    return static_cast<T&&>(arg);
}

A static_cast<T&&> a referencia-összeolvadás szabályai miatt adja vissza a megfelelő értékkategóriát. Ha T balérték-referencia, akkor T&& balérték-referenciává omlik össze; ha T nem referencia, akkor T&& jobbérték-referencia.

A perfect forwarding használata során gyakori hiba, hogy a fejlesztő a arg paramétert közvetlenül, std::move-val vagy std::forward nélkül adja tovább. Mivel a paraméternek neve van, az mindig balérték, még akkor is, ha a hívó jobbértéket adott át. Ezért a továbbítás előtt mindig std::forward<T>(arg)-ot kell használni, és a T-t pontosan a forwarding reference dedukciója szerint kell megadni. Például:

template <typename T>
void wrapper(T&& arg) {
    sink(arg);             // HIBÁS: mindig balértékként adja tovább
    sink(std::move(arg));  // HIBÁS: mindig jobbértékként adja tovább
    sink(std::forward<T>(arg)); // HELYES
}

A perfect forwarding variadic sablonokkal kombinálva a std::forward csomagban is működik:

template <typename... Args>
void make(Args&&... args) {
    return std::make_unique<Widget>(std::forward<Args>(args)...);
}

Itt minden Args-hoz tartozó std::forward megőrzi az adott argumentum értékkategóriáját.

A perfect forwarding a túlterhelésfeloldással is kölcsönhatásba lép: ha a továbbított argumentum egy nem-sablon és egy sablon túlterhelt függvény között választ, akkor a std::forward által visszaadott értékkategória határozza meg, melyik jelölt lesz jobb. Például ha a sink-nek van int& és int&& változata, akkor a továbbítás után a megfelelő változat hívódik.

6.2.10 Gyakori hibák és csapdák

A sablonargumentum-dedukció és a túlterhelésfeloldás számos olyan helyzetet teremt, ahol a fejlesztő téves elvárásokkal fordul a fordítóhoz. Néhány gyakori hiba:

6.2.11 1. Dedukció hiánya beágyazott típusoknál

Már említettük, hogy a typename beágyazott típusok nem dedukálhatók. Gyakori megoldás, hogy a függvényt átírjuk úgy, hogy a típus közvetlenül a paraméter mintájában szerepeljen:

// HIBÁS: nem dedukálható
template <typename T>
void print_first(typename std::vector<T>::const_iterator it);

// HELYES: T közvetlenül dedukálható
template <typename Iter>
void print_first(Iter it);

Ha a T-re szükség van, akkor a std::iterator_traits<Iter>::value_type segítségével kinyerhető.

6.2.12 2. Alapértelmezett argumentumok és sablonok

A függvénysablonok alapértelmezett argumentumai nem vesznek részt a dedukcióban. Ha egy paraméterhez alapértelmezett értéket adunk, attól még a sablonparamétert nem lehet kihagyni a hívásból, mert a dedukció csak a ténylegesen átadott argumentumokból indul ki. Ezért az ilyen paramétereket általában a sablonparaméterekben kell alapértelmezetten kezelni:

template <typename T, typename Alloc = std::allocator<T>>
class Container {
    // ...
};

Függvénysablonoknál az alapértelmezett függvényargumentumok nem befolyásolják a dedukciót, de a hívásnál elhagyhatók, ha a sablonparamétereket explicit módon megadjuk.

6.2.13 3. Sablon és nem-sablon túlterhelés váratlan győzelme

Azt hihetnénk, hogy a nem-sablon függvény mindig nyer, de ez csak akkor igaz, ha a konverziós rangok azonosak. Ha a nem-sablon rosszabb konverziót igényel, akkor a sablon nyerhet. Példa:

void f(long);
template <typename T>
void f(T);

f(42); // f<int>(int) nyer, mert pontos egyezés, míg a long promóció

Ezért ha pontos típusú túlterhelést akarunk kikényszeríteni, akkor azt a lehető legpontosabban kell megadnunk, vagy enable_if-et kell használnunk.

6.2.14 4. Forwarding reference és const-ság elvesztése

Ha a forwarding reference paramétert const T&&-ként deklaráljuk, az nem forwarding reference, mert a T&&-re vonatkozó speciális szabály csak akkor érvényes, ha a T közvetlenül, const nélkül szerepel. A const T&& csak jobbértékeket fogad, és a dedukció során a T nem lesz balérték-referencia, így a perfect forwarding nem működik. Ezért a forwarding reference mindig T&& formájú, ahol T a sablonparaméter.

6.2.15 5. CTAD és a deduction guide hiánya

Ha egy osztálysablonnak van olyan konstruktora, amely nem teszi lehetővé a helyes dedukciót, akkor CTAD-hibát kapunk, vagy nem kívánt típust dedukál. Például a std::vector esetében a std::vector v{1, 2, 3}; jól működik, de a std::vector v(10, 1); esetében a v típusa std::vector<int>, mert a konstruktor (size_type, const T&) mintája alapján a T dedukálható. A std::vector v(10); azonban nem fordul le, mert a konstruktor explicit vector(size_type), és a CTAD szabályok szerint ez nem elegendő a T dedukciójához – a szabvány explicit deduction guide-ot ír elő erre az esetre, ami a C++20-tól elérhető.

6.2.16 Labor: dedukciós hibák elemzése

A labor célja, hogy a résztvevő saját környezetben reprodukáljon és elemezzen tipikus dedukciós hibákat, és megtanulja a megoldási stratégiákat. A labor nem futtat éles rendszeren, minden példa izolált, saját buildben fut.

6.2.17 Környezet és build

  • Fordító: GCC 13.2 (vagy újabb), Clang 17 (vagy újabb), MSVC 19.38 (vagy újabb). A labor leírása GCC-re épül, de a többi fordítóval is ellenőrizhető.

  • Build fájl: egy CMakeLists.txt a laborhoz.

A labor egyetlen main.cpp-ből áll, amely a következő hibás és javított eseteket tartalmazza. Minden esethez egy-egy static_assert vagy futtatási ellenőrzés tartozik, amely dokumentálja a várt viselkedést.

6.2.18 1. eset: Nem dedukálható beágyazott típus

#include <vector>
#include <iterator>
#include <type_traits>

template <typename T>
void print_first_hibas(typename std::vector<T>::const_iterator it) {
    // ...
}

A fenti függvény hívása print_first_hibas(v.begin()) formában fordítási hibát okoz, mert a T nem dedukálható. A javított változat:

template <typename Iter>
void print_first_jav(Iter it) {
    using ValueType = typename std::iterator_traits<Iter>::value_type;
    static_assert(std::is_same_v<ValueType, int>);
}

6.2.19 2. eset: Konfliktusos dedukció

template <typename T>
void pair_hibas(T a, T b) {}

// Hívás: pair_hibas(1, 2.0); // fordítási hiba

A javított változat lehet két külön sablonparaméter:

template <typename T, typename U>
void pair_jav(T a, U b) {
    static_assert(std::is_same_v<T, int>);
    static_assert(std::is_same_v<U, double>);
}

6.2.20 3. eset: Perfect forwarding hiánya

#include <utility>
#include <memory>

struct Widget {
    explicit Widget(int) {}
    Widget(Widget&&) = default;
    Widget(const Widget&) = delete;
};

template <typename T>
std::unique_ptr<Widget> create_hibas(T&& arg) {
    return std::make_unique<Widget>(arg); // mindig balérték
}

template <typename T>
std::unique_ptr<Widget> create_jav(T&& arg) {
    return std::make_unique<Widget>(std::forward<T>(arg));
}

A create_hibas(42) fordítási hibát okoz, mert a arg balérték, és a Widget konstruktora csak jobbértéket fogad el. A create_jav(42) sikeresen lefut.

6.2.21 4. eset: CTAD és deduction guide

#include <vector>
#include <list>

template <typename T>
class MyRange {
public:
    template <typename Iter>
    MyRange(Iter first, Iter last) : first_(first), last_(last) {}
    // ...
private:
    // ...
};

// Dedukciós útmutató
template <typename Iter>
MyRange(Iter, Iter) -> MyRange<typename std::iterator_traits<Iter>::value_type>;

int main() {
    std::list<int> l{1,2,3};
    MyRange r(l.begin(), l.end()); // CTAD: MyRange<int>
    static_assert(std::is_same_v<decltype(r), MyRange<int>>);
}

A deduction guide nélkül a MyRange CTAD-je nem tudná a T-t dedukálni, mert az iterátor típusa nem jelzi a tárolt értéktípust. A guide hozzáadása után a kód fordul és a T helyesen int.

6.2.23 Összefoglalás

A sablonargumentum-dedukció és a túlterhelésfeloldás együtt alkotják a C++ generikus programozásának gerincét. A dedukció szabályai határozzák meg, hogy a fordító milyen típusokat következtet ki a függvényparaméterek mintáiból és a hívási argumentumokból; a túlterhelésfeloldás pedig kiválasztja a legjobb jelöltet a konverziós rangok és a specifikusság alapján. A forward reference és a std::forward segítségével a perfect forwarding lehetővé teszi, hogy a wrapper függvények pontosan megőrizzék az értékkategóriát és a const-ságot. A CTAD és a deduction guide-ok az osztálysablonok számára hozzák el ugyanezt a kényelmet, de gondos tervezést igényelnek, ha a konstruktor nem tükrözi közvetlenül a tárolt típusokat.

A hibák elemzésekor mindig a dedukció szabályait kell először ellenőrizni: van-e nem dedukálható kontextus, van-e konfliktus a paraméterek között, megfelelő-e a forwarding reference. A túlterhelésfeloldás váratlan győzelmeit a konverziós rangok és a részleges rendezés magyarázza, nem pedig a sablonok „varázslatos” viselkedése.

6.2.24 Önellenőrző kérdések

  1. Miért nem dedukálható a T a typename std::vector<T>::const_iterator paraméterből, és hogyan lehet ezt kikerülni?
  2. Magyarázza el, miért választja a fordító a sablon f(T) függvényt a nem-sablon f(long) helyett az f(42) hívásnál.
  3. Mi a különbség a T&& és a const T&& paraméter között a dedukció szempontjából?
  4. Hogyan működik a std::forward és miért van szükség explicit sablonargumentumra a hívásakor?
  5. Mire való a deduction guide, és miért van rá szükség egy iterátorokból építkező konténer esetén?
