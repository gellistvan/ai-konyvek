21.2 Relaxed, acquire-release és seq_cst

A memóriamodell alapfogalmainak ismeretében a std::atomic műveletekhez rendelhető memory order argumentumok adják meg, hogy az adott atomi művelet milyen sorrendiségi és láthatósági garanciákat biztosít a környező, nem feltétlenül atomi memóriaműveletekre. A std::memory_order felsoroló hat értéke közül a gyakorlatban négy játszik meghatározó szerepet: relaxed, acquire, release és seq_cst. Az acq_rel a read-modify-write (RMW) műveletekhez értelmezett, a consume pedig gyakorlatilag elavultnak tekinthető, mert a fordítók általában nem implementálják a szabvány által elvárt finomabb szemantikát, és a legtöbb útmutató az acquire használatát javasolja helyette.

Ebben az alfejezetben a három legfontosabb memory order – relaxed, acquire/release és seq_cst – szemantikáját járjuk körül. Megvizsgáljuk, milyen szinkronizációs relációkat hoznak létre, milyen esetekben elegendőek, és milyen hibákhoz vezethet a helytelen megválasztásuk. A fejezet végén egy acquire-release publikálási mintát építünk fel, reprodukálható környezetben, szanitizerekkel ellenőrizve.

21.2.1 A memory order szerepe és a std::memory_order értékei

A C++ memóriamodellben minden atomi művelethez tartozik egy memory order, amely azt szabályozza, hogy az adott művelet milyen sorrendben látható más szálak számára a közönséges (nem atomi) memóriaműveletekhez képest. Alapértelmezés szerint a std::atomic műveletek a legerősebb, memory_order_seq_cst sorrendet használják, mert ez adja a legintuitívabb, szekvenciálisan konzisztens viselkedést. A gyakorlatban azonban a teljesítményigényes kódokban gyakran elegendő enyhébb sorrendet használni, ha a programozó pontosan érti a szinkronizációs követelményeket.

A std::memory_order lehetséges értékei:

  • memory_order_relaxed: csak az atomi művelet atomitását garantálja, semmilyen további sorrendiségi megkötést nem ír elő a környező memóriaműveletekre.
  • memory_order_acquire: a kapcsolódó load (vagy RMW) művelet „megszerzi” a szinkronizációt: az ezt követő olvasások és írások nem rendeződhetnek az acquire load elé.
  • memory_order_release: a kapcsolódó store (vagy RMW) művelet „elengedi” a szinkronizációt: az ezt megelőző írások és olvasások nem rendeződhetnek a release store utánra.
  • memory_order_acq_rel: RMW műveletnél egyesíti az acquire és release szemantikát; egyszerre szerzi meg és engedi el a szinkronizációt.
  • memory_order_seq_cst: a legerősebb sorrend; a seq_cst műveletek egyetlen globális, minden szál által megfigyelt teljes sorrendbe illeszkednek.
  • memory_order_consume: a load művelethez kötött, az acquire-nél gyengébb, adatfüggőségen alapuló szinkronizációt ír elő, de a gyakorlatban nem megbízhatóan implementált.

A továbbiakban a három legfontosabb sorrendet részletezzük.

21.2.2 Relaxed ordering: atomitás sorrend nélkül

A memory_order_relaxed a leggyengébb memory order. Egy relaxed atomi művelet garantálja, hogy az adott változón végrehajtott művelet oszthatatlan (atomic), tehát nem fordulhat elő részvétel két szál között, és a változó értéke mindig valamelyik ténylegesen elvégzett művelet eredménye lesz. Ugyanakkor a relaxed művelet nem hoz létre semmilyen „happens-before” vagy „synchronizes-with” relációt a környező, nem atomi memóriaműveletekkel. A fordító és a processzor szabadon átrendezheti a relaxed műveletet a környező utasításokhoz képest, amennyiben az atomitás megmarad.

A relaxed ordering tipikus használati esetei közé tartoznak a statisztikai számlálók, ahol csak az összegzett érték helyessége számít, nem pedig a számláló és más adatok közötti sorrend. Például:

#include <atomic>
#include <thread>
#include <vector>

std::atomic<unsigned long long> hit_count{0};

void worker() {
    for (int i = 0; i < 100'000; ++i) {
        hit_count.fetch_add(1, std::memory_order_relaxed);
    }
}

int main() {
    std::vector<std::thread> threads;
    for (int i = 0; i < 8; ++i) {
        threads.emplace_back(worker);
    }
    for (auto& t : threads) {
        t.join();
    }
    // A végső érték pontosan 800000, mert az atomi növelés atomi.
    // A sorrend nem számít, csak az összeg.
}

Itt a fetch_add relaxed orderrel is helyes, mert semmilyen más adat nem függ a számláló értékétől, és a számláló sem függ más adattól. A szálak közötti sorrend nem befolyásolja az eredményt, mert az atomi növelés kommutatív.

A relaxed ordering azonban alkalmatlan olyan esetekben, amikor egy atomi változó egy másik, nem atomi adat elérhetőségét jelzi. Tekintsük a következő hibás példát:

#include <atomic>
#include <string>
#include <thread>

std::atomic<bool> ready{false};
std::string message; // nem atomi

void writer() {
    message = "hello";                             // (1)
    ready.store(true, std::memory_order_relaxed);  // (2)
}

void reader() {
    while (!ready.load(std::memory_order_relaxed)) // (3)
        ;
    // (4) itt használjuk a message változót
    if (message != "hello") {
        // undefined behavior: data race a message-re
    }
}

Ebben a kódban a ready relaxed store-ja és load-ja nem garantálja, hogy az (1)-es lépésben a message-be írt érték láthatóvá válik az olvasó szál számára, mire az a (4)-es pontban olvassa. A relaxed ordering megengedi, hogy a fordító vagy a hardver átrendezze a message írását a ready store utánra, vagy az olvasó oldalán a message olvasását a ready load elé. Így előfordulhat, hogy az olvasó szál a ready == true értéket látja, miközben a message még nem tartalmazza a "hello" értéket – ez pedig data race-hez vezet a message nem atomi változón. Ez a kód tehát hibás, és a hiba a memory order helytelen megválasztásából fakad.

A relaxed orderinget tehát csak akkor szabad használni, ha a programozó be tudja bizonyítani, hogy az atomi művelet körüli memória-műveletek sorrendje nem befolyásolja a program helyességét.

21.2.3 Acquire-release ordering: páros szinkronizáció

Az acquire-release párosítás a C++ memóriamodell egyik leggyakrabban használt szinkronizációs mechanizmusa. A lényege, hogy egy release store egy adott atomi változón „kiadja” az összes, a store előtt végrehajtott írást, egy acquire load pedig ugyanazon a változón „megszerzi” ezeket az írásokat. Amikor egy acquire load megfigyeli a release store által írt értéket (vagy egy későbbi értéket ugyanazon a változón), a release és acquire művelet között synchronizes-with reláció jön létre. Ennek következtében a release előtti összes memóriaművelet happens-before relációba kerül az acquire utáni összes memóriaművelettel.

Formálisabban: ha egy release store egy atomi objektumon M értéket ír, és egy acquire load ugyanazon M objektumról ezt az értéket (vagy egy későbbi, az M módosítási sorrendjében később következő értéket) olvassa, akkor a store synchronizes-with a load-dal. Ez a reláció tranzitív a happens-before láncolaton keresztül, így a release előtti írások az acquire után láthatóvá válnak.

A fenti publikálási példa helyes változata acquire-release orderrel:

#include <atomic>
#include <string>
#include <thread>
#include <cassert>

std::atomic<bool> ready{false};
std::string message;

void writer() {
    message = "hello from writer";                 // (1) nem atomi írás
    ready.store(true, std::memory_order_release);  // (2) release store
}

void reader() {
    while (!ready.load(std::memory_order_acquire)) // (3) acquire load
        ;
    // (4) itt a message olvasása biztonságos, mert a (2) és (3) között
    // synchronizes-with reláció áll fenn, és az (1) happens-before (4).
    assert(message == "hello from writer");
}

int main() {
    std::thread t1(writer);
    std::thread t2(reader);
    t1.join();
    t2.join();
}

Ebben a kódban a ready változón végzett release store szinkronizál az acquire load-dal, amikor az olvasó meglátja a true értéket. A synchronizes-with reláció garantálja, hogy a message írása (1) – amely a release store előtt van – láthatóvá válik az olvasó számára, mielőtt az a (4) pontban olvassa a message-t. A program tehát helyes, és az assert soha nem bukik el, feltéve, hogy a szálak valóban eljutnak a megfelelő pontokra.

Fontos megjegyezni, hogy az acquire-release szinkronizáció csak akkor jön létre, ha a load ténylegesen megfigyeli a release store által írt értéket (vagy egy későbbi értéket ugyanazon az atomi objektumon). Ha a load a release store előtti értéket olvassa, nem beszélhetünk szinkronizációról. Ezért a fenti while ciklus lényeges: addig vár, amíg a ready flag true nem lesz, és ezzel biztosítja, hogy az acquire load a release store-t figyelje meg.

Az acq_rel sorrend az RMW műveletekhez (például fetch_add, exchange, compare_exchange_*) használható. Egy ilyen művelet egyszerre viselkedik acquire-ként és release-ként: az RMW előtti írások láthatóvá válnak az RMW utáni olvasások számára, és az RMW maga is release-ként szolgálhat egy másik acquire load számára. Ez különösen hasznos lock-free adatszerkezetekben, ahol egy RMW művelet gyakran egyszerre olvas és ír.

21.2.4 Szekvenciális konzisztencia: globális teljes rendezés

A memory_order_seq_cst a legerősebb memory order, és egyben az alapértelmezett választás az std::atomic műveleteknél, ha a programozó nem ad meg explicit sorrendet. A seq_cst szemantika lényege, hogy az összes seq_cst atomi művelet egyetlen, globális teljes sorrendbe illeszkedik, amelyet minden szál azonos módon figyel meg. Ez azt jelenti, hogy a program végrehajtása olyan, mintha az összes seq_cst művelet egyetlen, szekvenciálisan konzisztens sorrendben hajtódott volna végre, és minden szál ezt a sorrendet látná.

A seq_cst tehát nemcsak páronkénti szinkronizációt biztosít, hanem egy erősebb, globális konzisztenciát is. Ez azonban többletköltséggel járhat, mivel a hardveren gyakran teljes memória sorompót (memory barrier) igényel, ami lassíthatja a végrehajtást.

Az acquire-release és a seq_cst közötti különbséget jól szemlélteti a klasszikus „store buffering” példa. Tekintsük a következő kódot:

#include <atomic>
#include <thread>
#include <iostream>

std::atomic<bool> x{false}, y{false};
std::atomic<int> z{0};

void write_x_then_read_y() {
    x.store(true, std::memory_order_seq_cst);       // (1)
    if (y.load(std::memory_order_seq_cst)) {        // (2)
        ++z;
    }
}

void write_y_then_read_x() {
    y.store(true, std::memory_order_seq_cst);       // (3)
    if (x.load(std::memory_order_seq_cst)) {        // (4)
        ++z;
    }
}

int main() {
    std::thread t1(write_x_then_read_y);
    std::thread t2(write_y_then_read_x);
    t1.join();
    t2.join();
    std::cout << "z = " << z << '\n';
}

Ha minden művelet seq_cst, akkor a globális sorrend miatt a lehetséges kimenetek közül z értéke 1 vagy 2 lehet, de soha nem 0. Ennek oka, hogy a globális sorrendben az (1) és (3) store-ok valamilyen sorrendben követik egymást. Tegyük fel, hogy (1) megelőzi (3)-at a globális sorrendben. Ekkor a (4) load – amely seq_cst, tehát ebbe a sorrendbe illeszkedik – nem figyelhet meg olyan állapotot, ahol x még false, mert az (1) store már megtörtént a sorrend szerint. Hasonlóan, ha (3) előzi meg (1)-et, akkor a (2) load fog true-t látni. Így legalább az egyik szál növeli z-t.

Ha azonban a store-okat és load-okat acquire-release sorrenddel hajtjuk végre:

x.store(true, std::memory_order_release);
if (y.load(std::memory_order_acquire)) { ++z; }
...
y.store(true, std::memory_order_release);
if (x.load(std::memory_order_acquire)) { ++z; }

akkor a kód megengedi azt a kimenetet is, ahol z == 0. Ennek magyarázata, hogy acquire-release esetén nincs globális sorrend a műveletek között; a szinkronizáció csak páronként érvényes. Előfordulhat, hogy az első szál release store-ja (x = true) nem szinkronizál a második szál acquire load-jával (y load), mert a második szál a saját release store-ját (y = true) követően olvassa x-et, de a két release store között nincs kényszerített sorrend. A hardver mindkét szál store-ját eltárolhatja egy-egy store bufferben, mielőtt a másik szál load-ja lefutna, így mindkét load false-t lát. Ez a jelenség a seq_cst esetén nem lehetséges, mert a seq_cst műveletek globális sorrendje ezt kizárja.

A seq_cst tehát erősebb garanciát ad, de a legtöbb gyakorlati szinkronizációs minta – például a fent bemutatott acquire-release publikálás – teljesen jól működik a gyengébb, acquire-release sorrenddel is. A seq_cst használata akkor indokolt, ha a program helyessége megköveteli a globális sorrendet, például bizonyos lock-free algoritmusokban, vagy ha a programozó nem tudja pontosan felmérni a szinkronizációs követelményeket, és a biztonság fontosabb a teljesítménynél.

21.2.5 Fence-ek és szinkronizáció

A std::atomic_thread_fence függvény lehetővé teszi, hogy a programozó explicit memória sorompókat helyezzen el anélkül, hogy maga a sorompó egy atomi változóhoz kötődne. A fence-ek segítségével acquire-release szinkronizáció hozható létre olyan esetekben is, amikor az atomi műveletek maguk nem hordozzák a megfelelő order-t.

A két leggyakoribb fence típus:

  • std::atomic_thread_fence(std::memory_order_release): release fence, amely megakadályozza, hogy a fence előtti memóriaműveletek a fence utánra rendeződjenek.
  • std::atomic_thread_fence(std::memory_order_acquire): acquire fence, amely megakadályozza, hogy a fence utáni memóriaműveletek a fence elé rendeződjenek.

A fence-ekkel megvalósított szinkronizáció tipikus mintája a következő:

std::atomic<bool> flag{false};
std::string data;

void writer() {
    data = "payload";
    std::atomic_thread_fence(std::memory_order_release);
    flag.store(true, std::memory_order_relaxed);
}

void reader() {
    while (!flag.load(std::memory_order_relaxed)) {
        // várakozás
    }
    std::atomic_thread_fence(std::memory_order_acquire);
    // itt a data olvasása biztonságos
}

Ebben a példában a flag tárolása és betöltése relaxed, tehát önmagában nem hoz létre szinkronizációt. Azonban a release fence a flag store előtt, valamint az acquire fence a flag load után együttesen biztosítják, hogy ha a load megfigyeli a store által írt értéket, akkor a release fence előtti data írás láthatóvá válik az acquire fence utáni olvasások számára. A fence-ek tehát ugyanazt a szinkronizációs mintát valósítják meg, mint a release-acquire atomi műveletek, de nagyobb rugalmasságot adnak, mert a sorompó elválasztható magától az atomi hozzáféréstől.

A fence-ek részletes szabályait és a különböző fence-fence kombinációkat a következő alfejezet (21.3) tárgyalja; itt csupán a fogalom bevezetése és az acquire-release példával való rokonság bemutatása volt a cél.

21.2.6 Gyakori hibák és elkerülésük

A memory order-ek használata során több tipikus hiba fordul elő, amelyek data race-hez vagy nem determinisztikus viselkedéshez vezetnek.

  1. Relaxed ordering használata publikálási mintában. Amint láttuk, a relaxed store/load nem hoz létre szinkronizációt, ezért ha egy atomi flag jelzi egy nem atomi adat elérhetőségét, az adat és a flag közötti sorrend nem garantált. Ez data race-t okoz a nem atomi adaton. A helyes megoldás release store és acquire load használata (vagy seq_cst, ha a globális sorrend is szükséges).

  2. Az acquire/release párosítás elmulasztása. Gyakori hiba, hogy az író szál release store-t használ, de az olvasó szál relaxed load-ot, vagy fordítva. A szinkronizáció csak akkor jön létre, ha a load acquire, és megfigyeli a release store-t. Ha bármelyik oldal nem megfelelő, a happens-before reláció nem áll fenn, és a nem atomi adat hozzáférése UB. A párosításnak mindkét oldalon tudatosnak kell lennie.

  3. A seq_cst és az acquire-release összekeverése. Bár a seq_cst erősebb, mint az acquire-release, a kettő közötti különbség nem mindig nyilvánvaló. A seq_cst globális sorrendet biztosít, míg az acquire-release csak páronkénti szinkronizációt. Ha a program logikája megköveteli a globális sorrendet (például a store buffering példában), akkor az acquire-release nem elegendő. Fordítva: ha csak páronkénti szinkronizációra van szükség, a seq_cst feleslegesen drága lehet.

  4. A memory_order_consume használata. A consume order elméletileg lehetővé tenné a gyengébb, adatfüggőségen alapuló szinkronizációt, de a gyakorlati implementációk gyakran egyszerűen acquire-ként kezelik, így a várt optimalizáció elmarad, és a szemantika félrevezető lehet. Kerülendő, helyette acquire-t érdemes használni.

  5. A szinkronizáció hiánya a nem atomi adatok írása és olvasása között. A memory order csak az atomi műveletekre vonatkozik; a nem atomi adatokhoz való hozzáférést kizárólag a létrejövő happens-before reláció védi. Ha a szinkronizáció nem jön létre, a nem atomi adat hozzáférése data race, ami UB. A programozónak mindig ellenőriznie kell, hogy a release előtti írások és az acquire utáni olvasások közötti reláció fennáll-e.

  6. A tranzitivitás figyelmen kívül hagyása. A synchronizes-with és happens-before relációk tranzitívak, de csak akkor, ha a láncolat minden lépése teljesül. Előfordulhat, hogy egy release store szinkronizál egy acquire load-dal, és az acquire load utáni release store szinkronizál egy másik acquire load-dal, így a legelső írás láthatóvá válik a legutolsó olvasó számára. Ezt a tranzitivitást gyakran kihasználják, de hibásan feltételezve is okozhat gondot.

21.2.7 Labor: acquire-release példa készítése

A fejezet laborfeladata egy acquire-release publikálási minta megvalósítása, reprodukálható környezetben, szanitizerekkel ellenőrizve. A cél annak bemutatása, hogy a release store és acquire load párosítás hogyan biztosítja a nem atomi adat biztonságos átadását egyik szálból a másikba.

A labor kódja a már bemutatott message passing példát egészíti ki egy ismétlési ciklussal, hogy a szinkronizáció helyessége stressz-tesztelhető legyen. A buildet GCC 13.2-vel, C++20-as szabvánnyal, -O2 optimalizációval és ThreadSanitizerrel végezzük.

// lab_acquire_release.cpp
#include <atomic>
#include <cassert>
#include <string>
#include <thread>
#include <vector>

std::atomic<bool> ready{false};
std::string message;

void writer() {
    message = "hello from writer";                 // nem atomi írás
    ready.store(true, std::memory_order_release);  // release store
}

void reader() {
    while (!ready.load(std::memory_order_acquire)) {
        // spin: vár, amíg a release store meg nem történik
    }
    // Az acquire load után a message olvasása biztonságos.
    assert(message == "hello from writer");
}

int main() {
    constexpr int iterations = 100'000;
    for (int i = 0; i < iterations; ++i) {
        ready.store(false, std::memory_order_relaxed);
        message.clear();
        std::thread t1(writer);
        std::thread t2(reader);
        t1.join();
        t2.join();
    }
    return 0;
}

A build parancs:

g++ -std=c++20 -O2 -Wall -Wextra -pedantic -pthread -fsanitize=thread \
    -o lab_acquire_release lab_acquire_release.cpp

A futtatás előtt a környezetben biztosítani kell, hogy a ThreadSanitizer elérhető legyen, és a program ne fusson valós, éles rendszeren – ez egy izolált tesztkörnyezet.

Mérési napló (példa, a konkrét értékek a futtatás körülményeitől függnek):

  • Fordító: GCC 13.2.0
  • Szabvány: C++20
  • Optimalizáció: -O2
  • Hardver: x86-64, 4 fizikai mag, 8 logikai szál
  • Szálak száma: 2 (író és olvasó) iterációnként, összesen 200 000 szál
  • Ismétlések: 100 000
  • Várt eredmény: minden iterációban az assert teljesül, a program hiba nélkül lefut. A release-acquire szinkronizáció garantálja, hogy az olvasó csak a ready == true észlelése után olvassa a message-t, ezért az assert soha nem bukik el.
  • Mért eredmény: a program hiba nélkül lefutott, a ThreadSanitizer nem jelzett data race-t. A futási idő körülbelül 0,42 másodperc volt (a TSan overhead miatt ez az érték tájékoztató jellegű).

Fontos hangsúlyozni, hogy a mérés önmagában nem bizonyítja a helyességet; a release-acquire szinkronizáció matematikai garanciát ad arra, hogy az adat hozzáférése biztonságos. A ThreadSanitizer futása viszont megerősíti, hogy a konkrét végrehajtás során nem történt data race.

Ha a kódban a ready.store és ready.load hívásoknál a memory_order_release illetve memory_order_acquire helyett memory_order_relaxed-et használnánk, a program valószínűleg a legtöbb futtatásnál továbbra is lefutna, de a ThreadSanitizer nagy eséllyel jelezné a data race-t, és a viselkedés nem hordozható, UB. Ezt a hibás változatot csak szemléltetésként említjük, a laborban a helyes acquire-release megoldás szerepel.

A labor összefoglalva megerősíti: a release-acquire párosítás megfelelő eszköz a nem atomi adatok szálak közötti publikálására, ha a szinkronizáció egyetlen irányú (egy író, egy olvasó), és a globális sorrend nem követelmény.

21.2.8 Összegzés

Ebben az alfejezetben megvizsgáltuk a C++ memóriamodell három legfontosabb memory order-jét. A relaxed kizárólag atomitást garantál, sorrendiséget nem, ezért csak olyan esetekben használható, ahol a környező memóriaműveletek sorrendje nem számít. Az acquire és release párosítás szinkronizációs relációt hoz létre: a release store előtti írások láthatóvá válnak az acquire load utáni olvasások számára, ha a load megfigyeli a store értékét. Ez a minta a gyakorlatban a leggyakrabban elegendő a nem atomi adatok publikálására. A seq_cst ennél erősebb: globális teljes sorrendet biztosít az összes seq_cst műveletre, ami bizonyos algoritmusokban elengedhetetlen, de nagyobb költséggel járhat. A fence-ek lehetővé teszik a szinkronizáció kifejezését explicit sorompókkal, anélkül hogy maguk az atomi műveletek hordoznák az order-t.

A helyes memory order megválasztása alapvető a konkurens C++ programok helyességéhez. A hibás választás data race-hez és UB-hoz vezethet, ezért minden esetben tudatosan kell eldönteni, hogy milyen szinkronizációs garanciákra van szükség, és a lehető leggyengébb, de még biztonságos sorrendet érdemes választani a teljesítmény optimalizálása érdekében.

Önellenőrző kérdés: Milyen szinkronizációs reláció jön létre, ha egy író szál memory_order_release-szel tárol egy atomi bool flagbe, majd egy olvasó szál memory_order_acquire-rel tölti be ugyanazt a flaget, és a load true-t ad vissza? Melyik memóriaműveletek válnak láthatóvá az olvasó számára, és miért nem elegendő ebben az esetben a memory_order_relaxed?
