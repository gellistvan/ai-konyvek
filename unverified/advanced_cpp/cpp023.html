7.2 Tag dispatch és detection idiom

A modern C++ sablonozás egyik legfontosabb lépése, amikor egy általános algoritmusnak nem egyetlen típusra, hanem típusok egy halmazára kell működnie, és a viselkedést a típus képességei alapján kell kiválasztani. Az előző egységben megismert SFINAE és std::enable_if elsősorban arra való, hogy egy túlterhelést eltávolítsunk a jelöltlistáról. Ebben az egységben két olyan, ezzel rokon, de attól jól elkülöníthető eszközt vizsgálunk meg: a címkealapú diszpécser (tag dispatch) és a detection idiom (típusdetektálás). Mindkettő a fordítási idejű döntéshozatalt szolgálja, de más kérdésre válaszol.

A tag dispatch akkor hasznos, ha a lehetséges viselkedések egy zárt, előre ismert kategóriarendszerbe sorolhatók, például iterátorkategóriákba vagy memóriaelrendezési sémákba. A detection idiom ezzel szemben azt vizsgálja, hogy egy adott típuson érvényes-e egy kifejezés, és ha igen, mi a típusa. A kettőt gyakran együtt használjuk: detektáljuk, hogy egy típus rendelkezik-e egy szükséges jellemzővel, majd címkediszpécserrel választjuk ki a megfelelő implementációt. Ez a felépítés C++17-ben is hordozható, és a C++20 concept eszközei előtt is jól érthető hidat alkot.

Először a tag dispatch működését és felépítését vizsgáljuk meg egy valósághű példán, majd részletesen kidolgozzuk az általános detektáló sablonokat. A fejezet végén a két technikát egy ellenőrzött, mérhető laborban kombináljuk.

7.2.1 Címketípus és túlterhelés

A tag dispatch alapötlete, hogy a döntést kifejező információt egy típusba csomagoljuk, nem pedig egy bool értékbe. Az ilyen típuskát címkének vagy tag típusnak nevezzük. A címketípus lehet teljesen üres:

struct row_major_t {};
struct column_major_t {};

A hívás helyén ebből általában létrehozunk egy értéket, és átadjuk egy belső, túlterhelt függvénynek:

template <typename Matrix, typename Vector>
void multiply_impl(const Matrix&, const Vector&, row_major_t);

template <typename Matrix, typename Vector>
void multiply_impl(const Matrix&, const Vector&, column_major_t);

template <typename Matrix, typename Vector>
void multiply(const Matrix& m, const Vector& v) {
    multiply_impl(m, v, typename Matrix::layout_type{});
}

A kulcs az, hogy a címke nem hordoz futásidejű állapotot, ezért a fordító a túlterhelés kiválasztása után a címkét és a hívást általában teljesen eltünteti. Az üres címkeértéket érték szerint adjuk át; a kód pontosan ugyanolyan gyors, mintha a megfelelő ágat közvetlenül megírtuk volna. A C++17 óta a címkéket inline constexpr változóként is elérhetővé lehet tenni:

struct row_major_t {};
struct column_major_t {};

inline constexpr row_major_t row_major{};
inline constexpr column_major_t column_major{};

Ezt azonban nem kötelező használni, a row_major_t{} kifejezés is elegendő. A beépített iterátorkategóriák, például a std::input_iterator_tag, a std::forward_iterator_tag, a std::bidirectional_iterator_tag és a std::random_access_iterator_tag, szintén ilyen címkék. A szabványos hierarchiában a kategóriatagok leszármazási láncot alkotnak:

input_iterator_tag
  `-- forward_iterator_tag
        `-- bidirectional_iterator_tag
              `-- random_access_iterator_tag

Ez az öröklődés nem futásidejű polimorfizmusra szolgál, hanem arra, hogy egy alaposztály-címke túlterhelése elfogadja a leszármazott címkét is. Ha például bekötünk egy std::random_access_iterator_tag értéket, az egzakt random_access_iterator_tag túlterhelés mindig jobb, mint a bidirectional_iterator_tag túlterhelés, mert az utóbbi báziskonverziót igényelne. A túlterhelési rangsor tehát együttműködik a címkehierarchiával.

7.2.2 Tag dispatch az iterátorokon

A std::advance szabványos implementációja is tag dispatch-et használ: az általános algoritmus nem tudja egyetlen forráskóddal hatékonyan léptetni az egyszeres, a kétirányú és a véletlen hozzáférésű iterátorokat. A kétirányú iterátornál negatív távolságot is kezelni kell, a véletlen hozzáférésű iterátornál pedig egyszerű it += n kifejezést akarunk. Az információt a std::iterator_traits<It>::iterator_category adja meg.

Kezdjük egy egyszerű, tudatosan lecsupaszított implementációval:

#include <iterator>

namespace detail {

template <typename It, typename Distance>
void advance_impl(It& it, Distance n, std::input_iterator_tag) {
    // Csak nemnegatív távolságra értelmes egyszeres iterátoroknál.
    while (n-- > 0) {
        ++it;
    }
}

template <typename It, typename Distance>
void advance_impl(It& it, Distance n, std::bidirectional_iterator_tag) {
    while (n > 0) {
        ++it;
        --n;
    }
    while (n < 0) {
        --it;
        ++n;
    }
}

template <typename It, typename Distance>
void advance_impl(It& it, Distance n, std::random_access_iterator_tag) {
    it += n;
}

} // namespace detail

template <typename It, typename Distance>
void advance(It& it, Distance n) {
    using category_t = typename std::iterator_traits<It>::iterator_category;
    detail::advance_impl(it, n, category_t{});
}

Mit történik a hívás során?

  1. Az advance kinyeri a category_t típust, például std::list<int>::iterator esetén std::bidirectional_iterator_tag-et.
  2. Létrehoz egy üres címkeértéket: category_t{}.
  3. Meghívja a detail::advance_impl túlterhelt függvényt.
  4. A túlterhelés kiválasztásakor a levezetés után az egzakt típushoz tartozó legjobb illeszkedés győz.

A std::vector<int>::iterator esetén a random_access_iterator_tag túlterhelés direkt illeszkedik, nem a bázisosztályos bidirectional_iterator_tag vagy input_iterator_tag verzió. Ennek köszönhetően a vektoriterátorra generált kód valóban a += operátort használja, míg a listánál a külön ++it és --it lépések maradnak.

A fenti kód azonban még nem elég védett. Ha valaki advance-t hív egy olyan típussal, amelynek nincs std::iterator_traits<It>::iterator_category bejegyzése, a hibaüzenet a typename std::iterator_traits<It>::iterator_category sorba rohan bele. Ez az üzenet gyakran hosszú, és nem mondja el a hívónak, hogy mi volt a valódi elvárás. A detection idiom segít abban, hogy ezt a helyzetet szándékosan, érthető static_assert üzenettel kezeljük.

7.2.3 Detection idiom: std::void_t és felderítő sablonok

A detection idiom általános célja, hogy egy érvényességi kérdést fordítsunk le true_type/false_type válasszá. A leggyakoribb eszköz a C++17 óta elérhető std::void_t, amelyet a <type_traits> fejléc definiál:

template <typename...>
using void_t = void;

Bár a definíció triviálisnak tűnik, a sablon aliasban rejlő SFINAE miatt nagy ereje van. A void_t<Valami> csak akkor helyettesíthető, ha a Valami sablonargumentum érvényes. Ha a Valami kifejezés hibát okoz, a helyettesítés elbukik, és a környező kontextustól függően a túlterhelés vagy a részleges specializáció eltűnik a jelöltlistáról.

A legegyszerűbb felderítő idióma egy típus beágyazott typedefjét vizsgálja:

#include <type_traits>
#include <vector>

template <typename T, typename = void>
struct has_value_type : std::false_type {};

template <typename T>
struct has_value_type<T, std::void_t<typename T::value_type>>
    : std::true_type {};

static_assert(has_value_type<std::vector<int>>::value);
static_assert(!has_value_type<int>::value);

A mechanizmus a következő:

  • Az elsődleges sablon második paramétere alapértelmezésben void.
  • A részleges specializáció akkor illeszkedik, ha a második sablonargumentum void, és a std::void_t<typename T::value_type> kifejezés érvényes.
  • Ha T::value_type nem létezik, a std::void_t kifejezés helyettesítése elbukik, a részleges specializáció kikerül, ezért az elsődleges false_type marad érvényben.

Ez a minta jól olvasható, de minden kérdéshez külön traitet kell írni, és a válasz csak egy bool érték. Sokszor szükség van magára a detektált típusra is, például T::value_type tényleges típusára vagy a a + b kifejezés eredménytípusára. Ilyenkor célszerű az általános is_detected sablonhasználat.

7.2.4 Általános is_detected és detected_t

Az általános detektor egy template template paramétert vesz át. A vizsgálandó kifejezést egy alias sablonban fogalmazzuk meg, például:

template <typename A, typename B>
using add_result_t = decltype(std::declval<A>() + std::declval<B>());

A detektor két dolgot adhat vissza:

  • value_t: std::true_type vagy std::false_type aszerint, hogy a vizsgált operáció érvényes-e.
  • type: az operáció tényleges eredménytípusa, ha elérhető, egyébként egy megadott Default típus.

A következő implementáció a Library Fundamentals TS std::experimental::is_detected mintáját követi, de nem támaszkodik kísérleti szabványkönyvtárra:

#include <type_traits>
#include <utility>

namespace detail {

struct nonesuch {
    nonesuch() = delete;
    ~nonesuch() = delete;
    nonesuch(const nonesuch&) = delete;
    void operator=(const nonesuch&) = delete;
};

template <class Default, class AlwaysVoid,
          template <class...> class Op, class... Args>
struct detector {
    using value_t = std::false_type;
    using type = Default;
};

template <class Default, template <class...> class Op, class... Args>
struct detector<Default, std::void_t<Op<Args...>>, Op, Args...> {
    using value_t = std::true_type;
    using type = Op<Args...>;
};

template <template <class...> class Op, class... Args>
using is_detected = typename detector<nonesuch, void, Op, Args...>::value_t;

template <template <class...> class Op, class... Args>
using detected_t = typename detector<nonesuch, void, Op, Args...>::type;

template <class Default, template <class...> class Op, class... Args>
using detected_or_t = typename detector<Default, void, Op, Args...>::type;

} // namespace detail

A detector elsődleges változata a sikertelen eset: value_t hamis, type pedig a hívó által megadott Default. A részleges specializáció akkor aktív, ha std::void_t<Op<Args...>> helyettesíthető, azaz Op<Args...> érvényes. Ilyenkor value_t igaz, type pedig a kifejezés típusával egyezik meg.

A nonesuch típus arra való, hogy az érvénytelen esetben ne lehessen véletlenül értéket létrehozni belőle. A törölt konstruktorok és destruktor megakadályozzák a nonesuch{} kiértékelését. Amikor a detektor sikertelen, a detected_t tehát egy ilyen tiltott típust ad vissza. Ezt a típust csak nem értékelt kontextusban szabad használni, vagy olyan kódban, ahol nem példányosítjuk. A gyakorlatban ezért a detected_t-t mindig csak egy előzetes is_detected vizsgálat után érdemes kiértékelni, vagy a detected_or_t biztonságos változatot kell használni.

Építsük fel ezzel az is_addable traitet:

#include <string>

namespace detail {
template <typename A, typename B>
using add_result_t = decltype(std::declval<A>() + std::declval<B>());
}

template <typename A, typename B>
using is_addable = detail::is_detected<detail::add_result_t, A, B>;

template <typename A, typename B>
using add_result_or_void_t =
    detail::detected_or_t<void, detail::add_result_t, A, B>;

static_assert(is_addable<int, double>::value);
static_assert(!is_addable<int, std::string>::value);

using sum_t = add_result_or_void_t<int, double>;
static_assert(std::is_same_v<sum_t, double>);

Itt a vizsgált kifejezés a + operátor. Az is_addable<int, double> igaz, mert az int és a double között van beépített aritmetikai konverzió. Az is_addable<int, std::string> hamis, mert a szabványos std::string túlterhelések nem fogadnak int bal oldali operandust. A detected_or_t<void, add_result_t, int, double> biztonságosan visszaadja a double eredményt, mert a detektálás sikeres.

Ugyanez a technika beágyazott típusra:

#include <vector>

namespace detail {
template <typename T>
using value_type_t = typename T::value_type;
}

template <typename T>
using has_value_type = detail::is_detected<detail::value_type_t, T>;

static_assert(has_value_type<std::vector<int>>::value);
static_assert(!has_value_type<int>::value);

Itt a vizsgált kifejezés maga a typename T::value_type típus. Ez jól mutatja, hogy a detection idiom nem csak kifejezéseket, hanem típusérvényességet is képes vizsgálni. C++20-tól ez a kérdés egy requires kifejezéssel közvetlenebbül leírható, de a void_t-alapú detektor továbbra is hasznos marad, ha a kódnak C++17-tel is kompatibilisnek kell lennie, vagy ha a meglévő metafüggvény-rendszerhez kell illeszkednie.

7.2.5 Közös hiba: a detektált típus érték nélküli példányosítása

A nonesuch szándékosan nem példányosítható. Tegyük fel, hogy valaki így ír kódot:

template <typename It>
void wrong_advance(It& it, int n) {
    using category_t = detail::detected_t<detail::iterator_category_t, It>;
    detail::advance_impl(it, n, category_t{}); // hiba, ha nincs ilyen kategória
}

Ha az It típus nem iterátor, a category_t nonesuch lesz, és a category_t{} kifejezés törölt konstruktort próbál hívni. A hibaüzenet nem a static_assert-ből, hanem a törölt konstruktor használatából származik. A megoldás az, hogy a nyilvános függvény először is_detected-tel ellenőriz, és a tényleges híváshoz detected_or_t-vel adunk egy biztonságos alapértelmezett címkét:

namespace detail {

template <typename It>
using iterator_category_t =
    typename std::iterator_traits<It>::iterator_category;

template <typename It>
using has_iterator_category = is_detected<iterator_category_t, It>;

template <typename It>
using iterator_category_or_input_t =
    detected_or_t<std::input_iterator_tag, iterator_category_t, It>;

} // namespace detail

template <typename It, typename Distance>
void safe_advance(It& it, Distance n) {
    static_assert(
        detail::has_iterator_category<It>::value,
        "safe_advance requires std::iterator_traits<It>::iterator_category");

    using category_t = detail::iterator_category_or_input_t<It>;
    detail::advance_impl(it, n, category_t{});
}

Itt a static_assert megállítja a fordítást, ha nincs iterátorkategória. A category_t ezután már garantáltan nem nonesuch; az iterator_category_or_input_t alapértelmezett std::input_iterator_tag-et ad, ha a detektálás sikertelen lenne, de ezt az ágat a static_assert miatt nem érhetjük el. Így a hibaüzenet rövid, szándékos és a hívó számára értelmezhető.

7.2.6 A tag dispatch és a detection összekapcsolása

Az alábbi teljes példa a fejezet két eszközét együtt mutatja be. A safe_advance detection segítségével ellenőrzi, hogy a típus rendelkezik-e iterátorjellemzővel, majd tag dispatch segítségével választja ki a kategóriának megfelelő implementációt.

#include <forward_list>
#include <iostream>
#include <iterator>
#include <list>
#include <string>
#include <type_traits>
#include <utility>
#include <vector>

namespace detail {

struct nonesuch {
    nonesuch() = delete;
    ~nonesuch() = delete;
    nonesuch(const nonesuch&) = delete;
    void operator=(const nonesuch&) = delete;
};

template <class Default, class AlwaysVoid,
          template <class...> class Op, class... Args>
struct detector {
    using value_t = std::false_type;
    using type = Default;
};

template <class Default, template <class...> class Op, class... Args>
struct detector<Default, std::void_t<Op<Args...>>, Op, Args...> {
    using value_t = std::true_type;
    using type = Op<Args...>;
};

template <template <class...> class Op, class... Args>
using is_detected = typename detector<nonesuch, void, Op, Args...>::value_t;

template <template <class...> class Op, class... Args>
using detected_t = typename detector<nonesuch, void, Op, Args...>::type;

template <class Default, template <class...> class Op, class... Args>
using detected_or_t = typename detector<Default, void, Op, Args...>::type;

template <typename It>
using iterator_category_t =
    typename std::iterator_traits<It>::iterator_category;

template <typename It>
using has_iterator_category = is_detected<iterator_category_t, It>;

template <typename It>
using iterator_category_or_input_t =
    detected_or_t<std::input_iterator_tag, iterator_category_t, It>;

template <typename It, typename Distance>
void advance_impl(It& it, Distance n, std::input_iterator_tag) {
    while (n-- > 0) {
        ++it;
    }
}

template <typename It, typename Distance>
void advance_impl(It& it, Distance n, std::bidirectional_iterator_tag) {
    while (n > 0) {
        ++it;
        --n;
    }
    while (n < 0) {
        --it;
        ++n;
    }
}

template <typename It, typename Distance>
void advance_impl(It& it, Distance n, std::random_access_iterator_tag) {
    it += n;
}

template <typename A, typename B>
using add_result_t = decltype(std::declval<A>() + std::declval<B>());

} // namespace detail

template <typename It, typename Distance>
void safe_advance(It& it, Distance n) {
    static_assert(
        detail::has_iterator_category<It>::value,
        "safe_advance requires std::iterator_traits<It>::iterator_category");

    using category_t = detail::iterator_category_or_input_t<It>;
    detail::advance_impl(it, n, category_t{});
}

template <typename A, typename B>
using is_addable = detail::is_detected<detail::add_result_t, A, B>;

template <typename A, typename B>
using add_result_or_void_t =
    detail::detected_or_t<void, detail::add_result_t, A, B>;

static_assert(is_addable<int, double>::value);
static_assert(!is_addable<int, std::string>::value);
static_assert(detail::has_iterator_category<std::vector<int>::iterator>::value);
static_assert(!detail::has_iterator_category<int>::value);

int main() {
    std::list<int> lst{1, 2, 3};
    auto li = lst.begin();
    safe_advance(li, 2);
    if (*li != 3) return 1;

    std::vector<int> vec{10, 20, 30, 40};
    auto vi = vec.begin();
    safe_advance(vi, 3);
    if (*vi != 40) return 2;
    safe_advance(vi, -1);
    if (*vi != 30) return 3;

    std::forward_list<int> fl{5, 6, 7};
    auto fi = fl.begin();
    safe_advance(fi, 2);
    if (*fi != 7) return 4;

    std::cout << "safe_advance checks passed\n";
    return 0;
}

A kódban a std::forward_list<int>::iterator kategóriája std::forward_iterator_tag. A forward_iterator_tag leszármazottja az input_iterator_tag-nek, ezért az input_iterator_tag túlterhelés elfogadja. Mivel a mi advance_impl implementációnkban nincs külön forward_iterator_tag túlterhelés, az input_iterator_tag-es változat fut le. Ez pozitív távolságra helyes, negatívra viszont nem értelmezhető, mert az egyszeres léptetésű iterátorból nem lehet hatékonyan visszafelé haladni. A laborban ezért a forward_list-re csak nemnegatív távolságot használunk.

A fenti táblázat összefoglalja, hogy a safe_advance milyen implementációt választ a különböző standard iterátorkategóriákra:

Iterátor típusa iterator_category Kiválasztott advance_impl Helyes negatív távolság?
std::forward_list<int>::iterator forward_iterator_tag input_iterator_tag nem
std::list<int>::iterator bidirectional_iterator_tag bidirectional_iterator_tag igen
std::vector<int>::iterator random_access_iterator_tag random_access_iterator_tag igen

A táblázat a címkediszpécser lényegét ragadja meg: a hierarchiából az egzakt legjobb illeszkedés győz. A forward_iterator_tag-nek nincs saját túlterhelése, ezért a bázis input_iterator_tag-re illeszkedik. A random_access_iterator_tag esetén az egzakt random-access túlterhelés jobb, mint a bidirekcionális vagy az input bázisváltozat.

7.2.7 Gyakori hibák és elkerülésük

A tag dispatch és a detection idiom használata közben több visszatérő hiba is előfordulhat.

7.2.7.1 Érték nélküli nonesuch példányosítás

Ahogy fentebb láttuk, a detected_t sikertelen detektálás esetén nonesuch-t ad, amelyből nem lehet értéket létrehozni. A hívás előtt mindig is_detected-tel ellenőrizzünk, vagy használjunk detected_or_t-t egy értelmes alapértelmezett típussal.

7.2.7.2 A detektor alias nem SFINAE-barát

A vizsgált kifejezést olyan alias sablonban kell megfogalmazni, amely csak közvetlen kontextusban hibázhat. A decltype(std::declval<A>() + std::declval<B>()) ilyen, mert a hiba a helyettesítés során lép fel. Ha a kifejezés hibája egy függvénytörzsben vagy egy másik, már példányosult sablonban jelenik meg, az nem feltétlenül SFINAE-barát, és kemény fordítási hibát kaphatunk. A detektor csak olyan Op alias sablonokkal működik megbízhatóan, amelyek a template paramétertől függő kifejezésben hibáznak.

7.2.7.3 Többértelmű címkehierarchia

A standard iterátorkategóriák egyetlen leszármazási láncot alkotnak. Ha saját címkerendszert tervezünk, kerüljük a többes öröklődést, mert az könnyen többszörös báziskonverziós utakat hoz létre. Például:

struct read_tag {};
struct write_tag {};
struct read_write_tag : read_tag, write_tag {};

// A read_tag és write_tag túlterhelések jelenléte esetén
// read_write_tag átadása többértelmű lehet.

A címkediszpécsernél a tervezési szabály egyszerű: a címkehierarchia legyen kifelé szűkülő, lineáris öröklődés, vagy használjunk egymástól független, egzakt címkéket.

7.2.7.4 Túl sok overload és rejtett összekapcsolás

A tag dispatch hatékony, de ha minden apró képességkülönbségre külön túlterhelést hozunk létre, a kód gyorsan áttekinthetetlenné válik. A C++20 concept és requires bevezetésével a legtöbb új kódban már korlátozott sablonparaméterekkel érdemes dolgozni, és a tag dispatch-t inkább a zárt, jól definiált kategóriák kiválasztására fenntartani. A C++17-es kódbázisokban viszont a tag dispatch továbbra is a legolvashatóbb módja annak, hogy egy általános algoritmus több kategóriát szolgáljon ki.

7.2.8 Labor

A labor célja egy reprodukálható buildben lefuttatni a fenti safe_advance és is_detected implementációt, és a mérési naplóban rögzíteni a tényleges eredményeket. Az alábbi parancsok Linux/GCC környezetre vonatkoznak, de a kód a szabványos fejlécekre épül, így Clang és MSVC alatt is fordíthatónak kell lennie. A konkrét verziókat mindig a labor futtatója rögzíti, például GCC 13.2.0, Clang 18.1.0 vagy MSVC 19.40. A standardverzió C++20.

Fájlnév: tag_detection_lab.cpp.

GCC build és futtatás:

g++ -std=c++20 -Wall -Wextra -Wpedantic -Werror -O2 -DNDEBUG \
    tag_detection_lab.cpp -o tag_detection_lab
./tag_detection_lab

Szükséges címkék a CT/ST ellenőrzéshez:

g++ -std=c++20 -Wall -Wextra -Wpedantic -Werror -O1 -g \
    -fsanitize=address,undefined \
    tag_detection_lab.cpp -o tag_detection_lab_san
./tag_detection_lab_san

A várt kimenet a következő:

safe_advance checks passed

A tesztesetek:

  1. std::list<int> iterátor: safe_advance(li, 2) után *li == 3.
  2. std::vector<int> iterátor: safe_advance(vi, 3) után *vi == 40.
  3. Ugyanaz a vektoriterátor negatív távolsággal: safe_advance(vi, -1) után *vi == 30.
  4. std::forward_list<int> iterátor: safe_advance(fi, 2) után *fi == 7.
  5. A static_assert-ek fordítási időben ellenőrzik az is_addable és a has_iterator_category eredményeit.
  6. A sanitizer futás nem jelez memóriahibát vagy undefined behavior-t.

A mérési naplóban a mért értéket különítsük el a várttól:

Mérési pont Várt Mért

A feladat nem teljesítményoptimalizálásra irányul, ezért a futásidőre nincs szigorú korlát. A mérési napló azonban a könyv szabályai szerint tartalmazza a hardver, az operációs rendszer és a fordító pontos verzióját is.

7.2.9 Önellenőrző kérdések

  1. Mi a különbség a tag dispatch és az enable_if között, ha mindkettő fordítási idejű túlterhelés-választást végez?
  2. Miért használjunk üres címketípusokat, és miért adjuk át őket érték szerint?
  3. Hogyan működik a std::void_t a detection idiomban?
  4. Miért nem szabad közvetlenül példányosítani a detected_t eredményét, ha a detektálás sikertelen?
  5. Írj egy has_begin_member traitet, amely std::is_detected segítségével vizsgálja, hogy egy típusnak van-e begin() tagfüggvénye.

A tag dispatch és a detection idiom együttesen a régebbi C++-szabványok egyik legfontosabb fenntartható általánosprogramozási eszköze. A modern concept alapú megoldások felé vezető úton is érdemes ezt a két mintát pontosan érteni, mert a C++17-es kódbázisokban, valamint a kényes SFINAE-alapú könyvtárakban ma is napi szinten találkozunk velük.
