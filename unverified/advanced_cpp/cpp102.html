27.1 Creational és structural patterns

A creational és structural minták elsődleges célja, hogy a forráskódot rugalmassá, bővíthetővé és karbantarthatóvá tegyük anélkül, hogy a nyelvi eszközöket megkerülve, felesleges indirekciót vezetnénk be. A C++11 utáni szabványok – különösen a move szemantika, a lambdák, a std::function, a variadic template-ek, a concepts és a std::variant – alapvetően megváltoztatták azt, ahogyan ezeket a klasszikus mintákat érdemes megvalósítani. Ebben az alfejezetben a leggyakrabban használt négy mintát vizsgáljuk: a factory családot, a builder-t, az adapter-t és a decorator-t. Nem receptgyűjteményt adunk, hanem a minták mögötti tervezési döntéseket, a tipikus hibákat és a modern C++-os alternatívákat hangsúlyozzuk.

A fejezet laborjában egy olyan kis rendszert építünk, amelyben egy factory és egy adapter együtt dolgozik, majd reprodukálható buildben és tesztkörnyezetben ellenőrizzük az eredményt. A teljesítményméréseket a könyv konvencióinak megfelelően rögzített környezetben végezzük, és a mért értékeket elkülönítjük a várt értékektől.

27.1.1 Factory minták

A factory minták azt a problémát oldják meg, hogy az objektumlétrehozás logikája ne szóródjon szét a hívó kódban, és a konkrét típus kiválasztása ne fordulási időben rögzüljön. Ahelyett, hogy a kliens közvetlenül hívná a konstruktort (new Circle(...), std::make_unique<Circle>(...)), egy factory függvény vagy osztály végzi el a létrehozást, és általában egy absztrakt interfészt (pl. std::unique_ptr<Shape>) ad vissza.

27.1.2 Egyszerű factory függvény

A legegyszerűbb forma egy nem tagfüggvény vagy statikus metódus, amely a bemeneti paraméterek alapján választja ki a konkrét típust:

#include <memory>
#include <string>
#include <stdexcept>

struct Shape {
    virtual ~Shape() = default;
    virtual double area() const = 0;
};

struct Circle : Shape {
    double r;
    explicit Circle(double radius) : r{radius} {}
    double area() const override { return 3.14159 * r * r; }
};

struct Rectangle : Shape {
    double w, h;
    Rectangle(double width, double height) : w{width}, h{height} {}
    double area() const override { return w * h; }
};

enum class ShapeType { Circle, Rectangle };

std::unique_ptr<Shape> make_shape(ShapeType type, double a, double b = 0.0) {
    switch (type) {
        case ShapeType::Circle:
            return std::make_unique<Circle>(a);
        case ShapeType::Rectangle:
            return std::make_unique<Rectangle>(a, b);
    }
    throw std::invalid_argument("Unknown shape type");
}

Itt a make_shape visszatérési típusa std::unique_ptr<Shape>, így a hívó nem ismeri a konkrét típust, és a memóriakezelés automatikus. A switch azonban karbantartási problémát okoz: minden új típusnál módosítani kell a factoryt, és a fordítási időben nyitott a bővítésre. Ez a megoldás akkor megfelelő, ha a típusok halmaza stabil.

27.1.3 Factory Method minta

A Factory Method minta egy lépéssel tovább megy: maga a létrehozás egy virtuális függvényben történik, amelyet a származtatott osztály felülír. Ez lehetővé teszi, hogy egy absztrakt ősosztály műveletei a megfelelő konkrét objektumot hozzák létre anélkül, hogy az ős ismerné a pontos típust.

Klasszikus példa egy dokumentumkezelő keretrendszer:

class Document {
public:
    virtual ~Document() = default;
    virtual void open() = 0;
    virtual void save() = 0;
};

class Application {
public:
    virtual ~Application() = default;
    // Factory method
    virtual std::unique_ptr<Document> createDocument() = 0;

    void newDocument() {
        auto doc = createDocument(); // a konkrét típust a leszármazott dönti el
        doc->open();
        // ...
    }
};

class TextDocument : public Document {
public:
    void open() override { /* ... */ }
    void save() override { /* ... */ }
};

class TextApplication : public Application {
public:
    std::unique_ptr<Document> createDocument() override {
        return std::make_unique<TextDocument>();
    }
};

A TextApplication::createDocument() hívása mindig TextDocument-et ad vissza, de a newDocument() metódus csak az absztrakt Document interfészt ismeri. Ez a minta akkor hasznos, ha az osztályhierarchia párhuzamos: az alkalmazás típusa és a dokumentum típusa együtt változik.

27.1.4 Abstract Factory

Az Abstract Factory akkor jön szóba, ha objektumcsaládokat kell létrehozni, amelyek egymással kompatibilisek. Például egy GUI keretrendszer különböző platformokon más-más vezérlőket (Button, Checkbox) igényel, de a kliens kód nem függhet a konkrét platformtól.

struct Button { virtual ~Button() = default; virtual void render() = 0; };
struct Checkbox { virtual ~Checkbox() = default; virtual void render() = 0; };

struct GUIFactory {
    virtual ~GUIFactory() = default;
    virtual std::unique_ptr<Button> createButton() = 0;
    virtual std::unique_ptr<Checkbox> createCheckbox() = 0;
};

struct WindowsButton : Button { void render() override { /* ... */ } };
struct WindowsCheckbox : Checkbox { void render() override { /* ... */ } };

struct WindowsFactory : GUIFactory {
    std::unique_ptr<Button> createButton() override { return std::make_unique<WindowsButton>(); }
    std::unique_ptr<Checkbox> createCheckbox() override { return std::make_unique<WindowsCheckbox>(); }
};

A kliens csak a GUIFactory interfészt használja, így a konkrét platform cseréje egyetlen objektum létrehozásán múlik.

27.1.5 Modern alternatívák a factory mintára

A fenti klasszikus megvalósítások gyakran túlzottan merevek, és rengeteg boilerplate-t igényelnek. Modern C++-ban gyakran elegendő egy függvényobjektum vagy egy lambda alapú factory, amelyet paraméterként adunk át. Például:

template<typename Factory>
void process_shapes(Factory&& make_shape_fn) {
    auto shape = make_shape_fn();
    // shape használata
}

Ez a megoldás elkerüli az absztrakt gyár interfészt, és a fordító pontos típusinformációt tud optimalizálni. Ha a factory által visszaadott típusnak egy adott interfészt kell teljesítenie, akkor concepts-szel ellenőrizhetjük:

template<typename F>
concept ShapeFactory = requires(F f) {
    { f() } -> std::convertible_to<std::unique_ptr<Shape>>;
};

A C++20 concepts segítségével a fordítási hibák sokkal olvashatóbbak, és a túlterhelés is biztonságosabb.

Egy másik modern alternatíva a dependency injection egyszerű formája: a hívó átadja a factory függvényt konstruktorban vagy setterrel, így a teszteléshez mock factory is használható. Ez különösen fontos akkor, ha a gyártott objektumok drága erőforrásokat foglalnak le, vagy ha a tesztkörnyezetben cserélni kell a létrehozási logikát.

Tipikus hibák a factory mintáknál:

  • Nyers new használata std::unique_ptr vagy std::shared_ptr helyett. Ez memóriaszivárgáshoz vezet, ha a hívó elfelejti a delete-et.
  • A factory által visszaadott nyers pointer (T*) birtoklási viszonya nem egyértelmű. Mindig okos pointert adjunk vissza, vagy dokumentáljuk, hogy a hívó nem birtokol.
  • A switch-alapú factoryban az új típus hozzáadásának elfelejtése futásidejű hibát okoz, amelyet a fordító nem észlel. Ilyenkor érdemes megfontolni egy regisztrációs mechanizmust, vagy std::variant-ot.
  • A factory által létrehozott objektum élettartamának helytelen kezelése: ha a factory egy statikus vagy globális objektumra mutató referenciát ad vissza, az élettartam lejárta után lógó referencia keletkezhet.

27.1.6 Builder minta

A builder minta akkor hasznos, ha egy objektumnak sok konfigurációs paramétere van, vagy ha az objektum létrehozása több lépésből áll, és közben invariánsokat kell betartani. Ahelyett, hogy egy hatalmas konstruktort vagy sok settert használnánk, egy külön builder osztály gyűjti össze a paramétereket, és a végén létrehozza a célobjektumot.

Példa egy hálózati kapcsolat konfigurációjára:

#include <string>
#include <optional>

class ConnectionConfig {
public:
    std::string host;
    uint16_t port;
    std::optional<std::string> user;
    std::optional<std::string> password;
    bool use_tls;

    // privát konstruktor, csak a builder hívhatja
private:
    ConnectionConfig(std::string h, uint16_t p, std::optional<std::string> u,
                     std::optional<std::string> pw, bool tls)
        : host{std::move(h)}, port{p}, user{std::move(u)}, password{std::move(pw)}, use_tls{tls} {}

public:
    class Builder {
    public:
        Builder& set_host(std::string h) { host_ = std::move(h); return *this; }
        Builder& set_port(uint16_t p) { port_ = p; return *this; }
        Builder& set_user(std::string u) { user_ = std::move(u); return *this; }
        Builder& set_password(std::string pw) { password_ = std::move(pw); return *this; }
        Builder& set_use_tls(bool t) { use_tls_ = t; return *this; }

        ConnectionConfig build() && {
            // Invariáns ellenőrzés
            if (host_.empty()) throw std::runtime_error("Host must not be empty");
            if (port_ == 0) throw std::runtime_error("Port must be set");
            return ConnectionConfig{std::move(host_), port_, std::move(user_),
                                    std::move(password_), use_tls_};
        }

    private:
        std::string host_;
        uint16_t port_{0};
        std::optional<std::string> user_;
        std::optional<std::string> password_;
        bool use_tls_{false};
    };
};

Használat:

auto config = ConnectionConfig::Builder{}
    .set_host("example.com")
    .set_port(443)
    .set_use_tls(true)
    .build();

A builder itt fluent interface-t valósít meg: minden setter visszaadja a builder referenciáját, így a hívásokat láncolni lehet. A build() metódus && minősítővel van ellátva, így csak ideiglenes builder objektumon hívható, ami megakadályozza, hogy egy félkész builderből többször hozzunk létre objektumot.

27.1.7 Modern alternatívák a builder helyett

C++20-tól a designated initializers és az aggregate initialization sok esetben feleslegessé teszi a buildert, ha nincs szükség futásidejű invariáns-ellenőrzésre:

struct ConnectionConfig {
    std::string host;
    uint16_t port{};
    std::optional<std::string> user;
    std::optional<std::string> password;
    bool use_tls{false};
};

ConnectionConfig config{
    .host = "example.com",
    .port = 443,
    .use_tls = true
};

Ez sokkal rövidebb, de nem ellenőrzi, hogy a host nem üres vagy a port nem nulla. Ha a cél egy immutable objektum, amelynek minden mezője csak egyszer állítható be, akkor a builder továbbra is jobb, mert a build() végén minden mezőt egyszerre lehet ellenőrizni.

Tipikus hibák a builder mintánál:

  • A setterek nem Builder&-et adnak vissza, hanem Builder-t érték szerint, ami felesleges másolásokat okoz, és megtöri a láncolást.
  • A build() metódus nem ellenőrzi az invariánsokat, így érvénytelen objektum jön létre.
  • A builder és a célobjektum között túl szoros csatolás: a builder közvetlenül hozzáfér a célobjektum privát tagjaihoz, ami sérti az egységbezárást. Ezt friend osztállyal lehet feloldani, de csak indokolt esetben.
  • Ha a célobjektum nem másolható, de a builder másolható marad, az élettartam-problémákhoz vezethet.

27.1.8 Adapter minta

Az adapter célja, hogy egy meglévő osztály vagy függvény interfészét egy másik, a kliens által elvárt interfészre alakítsa. Ez tipikusan akkor szükséges, ha régi kódot, harmadik fél könyvtárat vagy platformfüggő API-t kell integrálni egy modern C++-os rendszerbe.

Két fő formája van:

  • Osztályadapter: többszörös öröklődést használ, az egyik ős a célinterfész, a másik az adaptálandó osztály. Ez C++-ban ritkább, mert a többszörös öröklődés bonyolultságot visz be, és nem mindig lehetséges (pl. final osztályok).
  • Objektumadapter: kompozíciót használ, azaz az adapter tartalmaz egy példányt vagy mutatót az adaptálandó objektumra, és a célinterfész metódusait a belső objektum hívásaival valósítja meg.

Példa: egy régi C függvény, amely fájlból olvas karaktereket, modern std::istream-szerű interfészbe csomagolva. Egyszerűbb esetben egy függvényt vagy osztályt adaptálunk.

Tegyük fel, hogy van egy örökölt logging könyvtár, amely a következő interfészt nyújtja:

// Legacy logger (C stílusú)
class LegacyLogger {
public:
    void write_message(const char* msg) {
        // pl. fprintf(stderr, "%s\n", msg);
    }
};

A modern rendszerünk elvár egy ILogger interfészt:

struct ILogger {
    virtual ~ILogger() = default;
    virtual void log(std::string_view message) = 0;
};

Objektumadapter:

class LegacyLoggerAdapter : public ILogger {
    LegacyLogger& legacy_;
public:
    explicit LegacyLoggerAdapter(LegacyLogger& legacy) : legacy_{legacy} {}

    void log(std::string_view message) override {
        // A string_view-ból null-terminált C stringet kell készíteni,
        // mert a LegacyLogger csak const char*-ot fogad el.
        std::string owned{message};
        legacy_.write_message(owned.c_str());
    }
};

Az adapter a log(std::string_view) hívást átalakítja write_message(const char*) hívássá. Mivel a string_view nem garantáltan null-terminált, szükség van egy std::string másolatra – ez fontos élettartam-megfontolás.

27.1.9 Modern alternatívák az adapter mintára

Gyakran nincs szükség teljes osztály adapterre; elegendő egy lambda vagy std::function alapú adapter:

LegacyLogger legacy;
auto adapter = [&legacy](std::string_view msg) {
    std::string owned{msg};
    legacy.write_message(owned.c_str());
};

Ha az interfész csak egyetlen függvényt igényel, a std::function<void(std::string_view)> típusú adapter is megfelelő. Több metódus esetén viszont az osztályadapter jobb.

A C++ standard könyvtárban számos adapter létezik: a range adapterek (std::views::transform, filter, stb.) funkcionális adapterként szolgálnak, a std::span pedig a tömbök és konténerek egységes interfészét biztosítja. Például egy függvény, amely std::span<const int>-et vár, automatikusan elfogad std::vector<int>-et, std::array-t vagy C tömböt – ez nem klasszikus adapter, de hasonló célt szolgál.

Tipikus hibák az adapter mintánál:

  • Élettartam-kezelés: ha az adapter referencia vagy mutató alapú, a belső objektum nem élhet rövidebb ideig, mint az adapter. Használjunk std::unique_ptr-t vagy std::shared_ptr-t, ha az adapter birtokolja az adaptált objektumot, vagy explicit módon dokumentáljuk, hogy csak megfigyelő.
  • A null-terminált string követelmény figyelmen kívül hagyása: a std::string_view nem garantáltan null-terminált, ezért ha C API-nak adjuk át, másolatot kell készíteni.
  • Túlzott rétegzés: minden apró eltérésre új adapter osztályt létrehozni felesleges bonyolultságot okoz. Előbb vizsgáljuk meg, hogy egy lambda vagy egy std::function elegendő-e.
  • Az adapter szivárogtatja a belső típust: ha az adapter nyilvános metódusai visszaadják a belső objektum referenciáját vagy mutatóját, a kliens közvetlenül hozzáférhet, ami sérti az absztrakciót.

27.1.10 Decorator minta

A decorator minta lehetővé teszi, hogy egy objektum viselkedését dinamikusan, futásidőben bővítsük anélkül, hogy az osztályhierarchiát módosítanánk. A dekorátor ugyanazt az interfészt valósítja meg, mint a díszített objektum, és általában kompozícióval tartalmazza azt, miközben a hívások előtt/után extra logikát hajt végre.

Példa: egy Logger interfész köré logolási időmérést vagy szűrést adunk.

struct Logger {
    virtual ~Logger() = default;
    virtual void log(std::string_view msg) = 0;
};

class ConsoleLogger : public Logger {
public:
    void log(std::string_view msg) override {
        // stdout-ra ír
    }
};

// Decorator: időbélyeg hozzáadása
class TimestampedLogger : public Logger {
    std::unique_ptr<Logger> inner_;
public:
    explicit TimestampedLogger(std::unique_ptr<Logger> inner) : inner_{std::move(inner)} {}

    void log(std::string_view msg) override {
        auto now = std::chrono::system_clock::now();
        // formázott időbélyeg kiírása
        inner_->log(msg);
    }
};

// Decorator: szűrés, csak bizonyos szintű üzenetek
class FilteredLogger : public Logger {
    std::unique_ptr<Logger> inner_;
    int min_level_;
public:
    FilteredLogger(std::unique_ptr<Logger> inner, int min_level)
        : inner_{std::move(inner)}, min_level_{min_level} {}

    void log(std::string_view msg) override {
        if (level_ >= min_level_) inner_->log(msg);
    }
private:
    int level_{0}; // egyszerűsítés
};

Használatkor a dekorátorokat láncolhatjuk:

std::unique_ptr<Logger> logger = std::make_unique<ConsoleLogger>();
logger = std::make_unique<TimestampedLogger>(std::move(logger));
logger = std::make_unique<FilteredLogger>(std::move(logger), /*min_level=*/2);

A std::unique_ptr láncolás biztosítja az erőforrások automatikus felszabadítását, és megakadályozza a másolást, ami a dekorátoroknál gyakran nem értelmes.

27.1.11 Modern alternatívák a decorator mintára

Ha a dekoráció csak egyszerű függvényhívások köré épül, lambdákkal is megoldható:

auto base_logger = [](std::string_view msg) { /* ... */ };
auto timestamped_logger = [base_logger](std::string_view msg) {
    auto now = std::chrono::system_clock::now();
    base_logger(msg);
};

Ez különösen akkor hasznos, ha a dekorátorok száma kicsi, és nem akarunk osztályhierarchiát fenntartani. Ha több metódusból álló interfészt kell díszíteni, a std::function és a lambdák már nehézkesek, ilyenkor a klasszikus dekorátor osztály jobb.

Egy másik modern megközelítés a mixin technika: CRTP-vel vagy variadic template-ekkel „belekeverünk” viselkedést egy osztályba fordítási időben. Ez nem dinamikus dekoráció, de gyakran elegendő, és nulla futásidejű költséggel jár.

Tipikus hibák a decorator mintánál:

  • A dekorátor és a belső objektum közötti élettartam rossz kezelése: ha a dekorátor nyers pointert tárol, a belső objektum felszabadulhat a dekorátor előtt. Használjunk okos pointert.
  • A dekorátor interfésze nem pontosan egyezik a belső objektuméval, például hiányoznak metódusok vagy más a konstans minősítés. A override kulcsszó használata kötelező.
  • A dekorátorok túlzott láncolása átláthatatlan kódot eredményez, és nehéz debuggolni. Ilyenkor érdemes egy middleware-láncot vagy pipeline-t bevezetni.
  • A dekorátor megsérti az egységbezárást azzal, hogy a belső objektum belső állapotához fér hozzá. Kerüljük a friend dekorátorokat, hacsak nem elkerülhetetlen.

27.1.12 Tipikus hibák és elkerülésük – általános észrevételek

A fenti minták alkalmazásakor a leggyakoribb hibák a következő kategóriákba sorolhatók:

  1. Túlzott absztrakció: minden osztályhoz factoryt, buildert vagy adaptert készíteni felesleges bonyolultságot szül. A minta használatát mindig a változás várható iránya és a tesztelhetőség igénye indokolja.
  2. A nyelvi eszközök figyelmen kívül hagyása: a C++11 utáni eszközök (lambda, std::function, std::variant, std::span, concepts) sok esetben egyszerűbb és hatékonyabb megoldást adnak, mint a klasszikus osztályhierarchiák.
  3. Memóriakezelés: nyers pointerek használata, hiányzó destruktorok, másolási szemantika helytelen definiálása. Mindig az RAII elvet kövessük, és a Rule of 0/3/5-öt alkalmazzuk.
  4. Élettartam-problémák: különösen adaptereknél és dekorátoroknál, ahol a belső objektumra mutató referencia vagy pointer érvényessége kérdéses. Dokumentáljuk a birtoklási viszonyokat.
  5. A minták merev alkalmazása: a minták sablonok, nem törvények. Ha egy egyszerű konstruktor vagy függvény is megoldja a problémát, ne erőltessük a mintát.

27.1.13 Labor: factory és adapter együttműködése

A labor célja, hogy a factory és az adapter mintát egy kis, de valósághű rendszerben alkalmazzuk, és reprodukálható buildben, tesztkörnyezetben, mérési naplóval igazoljuk a működést.

27.1.14 Feladatleírás

Készíts egy parancs-feldolgozó keretrendszert, amely képes különböző típusú parancsokat létrehozni egy factory segítségével, és egy régi, C stílusú függvényt adapteren keresztül modern interfészbe illeszt.

  • Factory: hozzon létre Command interfészt megvalósító objektumokat std::string név alapján. A parancsok: EchoCommand, ExitCommand, HelpCommand. A factory std::unique_ptr<Command>-ot adjon vissza, ismeretlen név esetén std::invalid_argument kivételt dobjon.
  • Adapter: legyen egy örökölt függvény void legacy_execute(const char* command_line), amely kiírja a parancsot (pl. printf-fel). Csomagold be egy Command interfészt megvalósító adapter osztályba, amely a Command::execute() hívását átirányítja a legacy_execute-ra. Az adapter egy std::string-et tároljon, és a legacy_execute-nek null-terminált C stringet adjon át.
  • A főprogram olvasson be parancsokat a szabványos bemenetről, és mindegyiket hajtsa végre a factory által létrehozott objektumon keresztül.

27.1.15 Build és tesztelés

A projektet CMake-kel építjük, C++20 szabvánnyal. A fordító legyen GCC 13 vagy Clang 17, de a tesztmátrixban jelöljük az MSVC támogatását is. A tesztekhez doctest keretrendszert használunk, amely header-only, így könnyen integrálható.

CMakeLists.txt (részlet):

cmake_minimum_required(VERSION 3.20)
project(FactoryAdapterLab LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

add_library(command_lib STATIC
    src/command.cpp
    src/factory.cpp
    src/legacy_adapter.cpp
)

target_include_directories(command_lib PUBLIC include)

add_executable(lab main.cpp)
target_link_libraries(lab PRIVATE command_lib)

# Tesztek
enable_testing()
add_subdirectory(tests)

A tesztek ellenőrzik: - A factory visszaadja a helyes típust (dynamic_cast-tal vagy typeid-dal, de inkább viselkedés alapján). - Ismeretlen parancsnév kivételt dob. - Az adapter átadja a stringet a legacy_execute-nek, és nem okoz memóriaszivárgást. - A parancsok végrehajtása nem dob nem várt kivételt.

27.1.16 Mérési napló

A mérési naplóban a következőket rögzítsd:

  • Fordító és verzió: pl. GCC 13.2.0, Clang 17.0.6, MSVC 19.38.
  • Szabványverzió: C++20.
  • Optimalizációs szint: -O2 (Release) és -O0 -g (Debug).
  • Hardver: CPU, RAM, OS.
  • Fordítási idő: time cmake --build . --target lab (átlag, 3 futtatás).
  • Bináris méret: size lab (Release mód).
  • Futási idő: a program futtatása 1000 parancson keresztül, time paranccsal (átlag, 3 futtatás).
  • Memóriahasználat: valgrind --leak-check=full vagy AddressSanitizerrel (-fsanitize=address) ellenőrizni, hogy nincs szivárgás.

A mért és várt értékeket külön táblázatban tüntesd fel. Például:

Mérőszám Mért érték (átlag) Várt érték / elfogadható tartomány
Fordítási idő (Release) 2,1 s < 5 s
Bináris méret (Release) 85 432 byte < 500 KB
Futási idő 1000 parancsra 0,8 ms < 10 ms

A várt értékeket indokold: a rendszer egyszerű, ezért a futási időnek nagyon alacsonynak kell lennie, a bináris méret pedig a standard könyvtár dinamikus linkelése miatt kicsi. A memóriaellenőrzésnek minden esetben nullát kell mutatnia.

27.1.17 Lehetséges kiterjesztések

  • A factory regisztrációs mechanizmust kap, így új parancs hozzáadása nem igényli a factory kódjának módosítását (pl. statikus regisztráció vagy std::map-be való bejegyzés).
  • Az adapter helyett std::function-t használunk, és összehasonlítjuk a fordítási időt és a bináris méretet.
