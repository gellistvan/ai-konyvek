8.1 Concepts és requires

A sablonparaméterek korlátozása a C++ korai változataiban gyakran vezetett nehezen olvasható, törékeny kódhoz. A std::enable_if, a tag dispatch és a detection idiom egyaránt azt a célt szolgálta, hogy egy sablont csak akkor lehessen példányosítani, ha a paraméterei teljesítik a műveletekhez szükséges feltételeket. Ezek a technikák azonban a hibaüzeneteket hosszú, implementációs részletekkel teli szöveggé duzzasztották, és a szándékot nehezen tették kifejezhetővé. A C++20 bevezette a concepts nyelvi eszközt: olyan névvel ellátott predikátumot, amely fordítási időben eldönti, hogy egy típus vagy típuskombináció kielégít-e egy követelményhalmazt. A concept nem új absztrakciós réteg, hanem a meglévő fordítási idejű ellenőrzések egységes, olvasható és karbantartható kerete.

Ebben a fejezetben a conceptek alapjait, a requires kifejezéseket, a constraint-ek összetételét és a standard concepteket tárgyaljuk. A cél, hogy képes legyél saját követelményrendszert definiálni, alkalmazni és a gyakori hibákat felismerni. A következő egység (Constraint-ek és requirement-ek) erre építve mutatja be a constraints részletes formáit és a range-ekkel való együttműködést.

8.1.1 Concept: névvel ellátott követelmény

A concept formailag egy olyan sablon, amelynek típusparaméterei vannak, és a törzse egy fordítási idejű logikai kifejezés. Szintaxisa:

template <typename T>
concept Integral = std::is_integral_v<T>;

Itt az Integral névvel ellátott predikátum akkor igaz, ha T egész típus. A jobb oldalnak konstans kifejezésnek kell lennie, amely bool értéket ad. A leggyakoribb formában egy requires kifejezést vagy más concepteket kombinálunk. Például:

template <typename T>
concept Addable = requires(T a, T b) {
    a + b;
};

Az Addable concept igaz, ha a T típusra létezik az operator+. A requires kifejezés itt a concept jobb oldalán áll, és a törzse a követelmények listája.

A conceptek használhatók:

  • constrained template paraméterként: template<Integral T> void f(T);
  • requires clause-ban: template<typename T> requires Integral<T> void f(T);
  • abbreviated function template-ben (röviden): void f(Integral auto x); – ez a forma ugyanazt jelenti, de a paraméter típusát auto-val jelöljük.
  • static_assert-ben: static_assert(Integral<int>);

Fontos megkülönböztetni a concept definícióját és a concept használatát. A definíció egy logikai predikátumot ad meg; a használat egy constraint-et hoz létre, amely a fordítás során ellenőrzésre kerül.

8.1.2 A requires kifejezések

A requires kulcsszó két, egymástól jól elkülöníthető szerepben jelenik meg:

  1. Requires clause: a sablonparaméterekre vagy függvényekre vonatkozó korlátozás. Például template<typename T> requires std::integral<T> void f(T);.
  2. Requires expression: egy olyan kifejezés, amely adott típusokra nézve követelményeket fogalmaz meg, és bool konstanst ad. Például requires(T a, T b) { a + b; }.

A kettő szintaktikai együttese gyakran requires requires alakot eredményez, ami elsőre zavarba ejtő:

template <typename T>
concept Addable = requires(T a, T b) {
    a + b;
};

template <typename T>
    requires requires(T a, T b) { a + b; }
T add(T a, T b) { return a + b; }

Itt az első requires a függvény requires clause-ja, a második pedig a requires expression kezdete. Bár a requires requires szükséges lehet, ha a constraintet közvetlenül a függvényre írjuk, a gyakorlatban sokkal olvashatóbb, ha először definiálunk egy conceptet, majd azt alkalmazzuk.

A requires expression törzse a következő requirement típusokat tartalmazhatja:

8.1.3 Simple requirement

Egy olyan kifejezés, amelynek érvényesnek kell lennie. Nem ad vissza értéket, csak azt ellenőrzi, hogy a kifejezés jól formált-e.

template<typename T>
concept HasFoo = requires(T t) {
    t.foo();            // simple requirement: t.foo() érvényes kell legyen
};

8.1.4 Type requirement

Egy típusnév, amelynek léteznie kell. Például egy beágyazott típus vagy alias meglétének ellenőrzése.

template<typename T>
concept HasValueType = requires {
    typename T::value_type;   // T-nek rendelkeznie kell value_type típussal
};

A typename kulcsszó itt nem a típusparaméter bevezetésére szolgál, hanem a type requirement jelölésére.

8.1.5 Compound requirement

Egy kifejezésnek nemcsak érvényesnek kell lennie, hanem a visszatérési típusára is vonatkozik megkötés. A szintaxis:

{ expression } -> constraint;

ahol a constraint lehet egy concept, vagy egy típus, amelyre a visszatérési érték konvertálható.

template<typename T>
concept Incrementable = requires(T x) {
    { ++x } -> std::same_as<T&>;   // ++x T& típusú kell legyen
    { x++ } -> std::convertible_to<const T&>; // x++ konvertálható const T&-re
};

A -> std::same_as<T&> után a std::same_as<T&> egy concept, amely a visszatérési típust a második argumentummal veti össze. A std::convertible_to<const T&> szintén concept, amely a konvertálhatóságot ellenőrzi.

8.1.6 Nested requirement

Egy további requires kifejezés a törzsön belül, amely egy másodlagos feltételt ad meg.

template<typename T>
concept ContainerOfInt = requires(T c) {
    typename T::value_type;
    requires std::same_as<typename T::value_type, int>;
};

A belső requires egy nested requirement: ha az adott feltétel hamis, az egész requires expression hamis.

A requires expression eredménye egy bool konstans. Ha bármelyik requirement nem teljesül, az egész kifejezés hamis; ha mind teljesül, igaz. Fontos, hogy a requires expression csak akkor értékeli ki a törzset, ha a típusok helyettesítése sikeres, és soha nem okoz fordítási hibát a kontextusban, ahol concept definícióban szerepel. Ehelyett hamis eredményt ad, így a conceptek használata nem vezet SFINAE-szerű hibákhoz a concept definíciójában.

8.1.7 Constraint-ek és összetételük

A constraints (korlátozások) olyan logikai kifejezések, amelyeket a fordító a sablonparaméterekre és függvényekre alkalmaz. A legegyszerűbb constraint egy atomic constraint: egy olyan kifejezés, amely egy concept-id (pl. Integral<T>) vagy egy bool konstans kifejezés. Az atomic constraint-eket a && és || operátorokkal kombinálhatjuk.

Példa:

template<typename T>
concept Numeric = std::integral<T> || std::floating_point<T>;

A Numeric concept igaz, ha T vagy egész, vagy lebegőpontos. A jobb oldalon lévő std::integral<T> és std::floating_point<T> atomic constraint-ek, amelyeket a || köt össze.

Több concept kombinálható:

template<typename T>
concept TotalOrdered = std::equality_comparable<T> && std::totally_ordered<T>;

A std::equality_comparable<T> azt követeli meg, hogy a típus támogassa az == és != műveleteket, a std::totally_ordered<T> pedig a <, <=, >, >= relációkat rendezett módon.

A normalizálás során a concept definícióját a fordító a jobb oldalon lévő kifejezésre cseréli, majd a && és || operátorokat atomi szintre bontja. Ez lehetővé teszi a részleges rendezést a conceptek között, de ennek részletei a Constraint-ek és requirement-ek témája.

A requires clause a függvényekre és sablonparaméterekre is alkalmazható. Például:

template<typename T>
    requires Numeric<T>
T square(T x) {
    return x * x;
}

Itt a requires Numeric<T> azt jelenti, hogy a square csak olyan T-re hívható, amelyre Numeric<T> igaz. Ugyanez rövidebben:

template<Numeric T>
T square(T x) {
    return x * x;
}

A constrained template paraméter előnye a rövidebb szintaxis és az, hogy a conceptet közvetlenül a paraméter típusához kötjük.

8.1.8 Standard concepts a <concepts> fejlécben

A C++20 szabványosította a leggyakoribb követelményeket a <concepts> fejlécben. Ezek nem „varázslatos” nyelvi elemek, hanem a szabványkönyvtár által definiált conceptek. A legfontosabb kategóriák:

8.1.9 Nyelvi alapok

  • std::same_as<T, U>: T és U azonos típus (a cv-qualifier-ek elhanyagolásával).
  • std::derived_from<T, Base>: T Base-ből származik, vagy azonos vele.
  • std::convertible_to<From, To>: From implicit konvertálható To-ra.
  • std::common_with<T, U>: létezik olyan típus, amelyre mindkettő konvertálható.
  • std::common_reference_with<T, U>: létezik közös referenciatípus.
  • std::assignable_from<T, U>: U értékadható T-nek.
  • std::swappable<T>: T swapelhető a std::swap használatával.

8.1.10 Aritmetikai fogalmak

  • std::integral<T>: egész típus.
  • std::signed_integral<T>: előjeles egész.
  • std::unsigned_integral<T>: előjel nélküli egész.
  • std::floating_point<T>: lebegőpontos típus.

8.1.11 Objektumtulajdonságok

  • std::destructible<T>: destruálható objektum.
  • std::constructible_from<T, Args...>: T konstruálható az Args... argumentumokból.
  • std::default_initializable<T>: default konstruálható.
  • std::movable<T>: mozgatható és mozgatással konstruálható.
  • std::copyable<T>: másolható objektum (a movable követelményeit is magában foglalja).
  • std::semiregular<T>: másolható és default konstruálható, de nem feltétlenül összehasonlítható ==-gyel.
  • std::regular<T>: semiregular és equality_comparable; olyan típus, amely értékszemantikával viselkedik.

8.1.12 Összehasonlítási fogalmak

  • std::equality_comparable<T>: == és != támogatott.
  • std::totally_ordered<T>: a relációs operátorok teljes rendezést adnak.

8.1.13 Hívható fogalmak

  • std::invocable<F, Args...>: F hívható Args... argumentumokkal.
  • std::regular_invocable<F, Args...>: invocable és nem módosítja a hívható objektum állapotát.
  • std::predicate<F, Args...>: regular_invocable és az eredmény bool konvertálható.
  • std::relation<F, T, U>: predicate, amely két azonos vagy különböző típusú argumentumon értelmezett reláció.
  • std::equivalence_relation<F, T, U>: reflexív, szimmetrikus és tranzitív reláció.
  • std::strict_weak_order<F, T, U>: szigorú gyenge rendezést adó reláció.

Ezeket a concepteket gyakran közvetlenül használjuk a saját conceptjeinkben. Például:

template<typename T>
concept Container = requires(T c) {
    typename T::value_type;
    { c.begin() } -> std::input_or_output_iterator;
    { c.end() } -> std::input_or_output_iterator;
} && std::destructible<T>;

Itt a std::input_or_output_iterator a <iterator> fejlécben definiált concept, amelyet a cpp14 fejezet részletez. A fenti példa szemlélteti, hogy a standard conceptek építőkövekként szolgálnak a saját, magasabb szintű követelmények megfogalmazásához.

Fontos megjegyezni: a <concepts> fejlécben definiált conceptek C++20 óta érhetők el, és a listájuk a jelenlegi szabvány szerint stabil. Ha egy adott szabványverzióhoz kötött, frissen bevezetett conceptet keresel, mindig ellenőrizd a fordítód dokumentációját és a __cpp_concepts vagy hasonló feature-test makrókat.

8.1.14 Gyakorlati minta: saját concept definiálása

Tegyük fel, hogy egy Printable conceptet szeretnénk: olyan típusokat szeretnénk elfogadni, amelyeket egy std::ostream-re ki lehet írni a << operátorral. A definíció:

#include <concepts>
#include <iostream>

template<typename T>
concept Printable = requires(std::ostream& os, const T& x) {
    { os << x } -> std::convertible_to<std::ostream&>;
};

A requires kifejezésben deklaráljuk az os és x változókat. A compound requirement { os << x } -> std::convertible_to<std::ostream&> azt követeli meg, hogy az operator<< hívás eredménye konvertálható legyen std::ostream&-re. Ez a gyakori stream-operátorokra teljesül, mert általában std::ostream&-et adnak vissza.

Alkalmazzuk egy constrained függvényre:

template<Printable T>
void print(const T& value) {
    std::cout << value << '\n';
}

A static_assert segítségével ellenőrizhetjük a conceptet:

static_assert(Printable<int>);
static_assert(Printable<std::string>);
struct NotPrintable {};
static_assert(!Printable<NotPrintable>);

A Printable<int> igaz, mert az int kiírható. Az std::string is. A NotPrintable üres osztályra a concept hamis, mert nincs operator<<.

8.1.15 Tipikus hibák

8.1.15.1 1. A concept jobb oldalán nem bool kifejezés áll

A concept definíciójában a jobb oldalnak fordítási idejű bool értékűnek kell lennie. A requires expression eleve ilyen, de ha más kifejezést írunk, hibát kapunk. Például:

template<typename T>
concept Bad = T::value;  // HIBA: T::value nem feltétlenül bool

A helyes megoldás:

template<typename T>
concept Good = requires { typename T::value; } && std::convertible_to<decltype(T::value), bool>;

Vagy egyszerűbben:

template<typename T>
concept Good = std::convertible_to<decltype(T::value), bool>;

8.1.15.2 2. A requires kifejezés elhagyása, ahol szükséges

Ha közvetlenül a függvény requires clause-jában akarunk kifejezést ellenőrizni, gyakori hiba a belső requires elhagyása:

template<typename T>
    requires (T a, T b) { a + b; }  // HIBA: ez nem szintaktikailag érvényes
T add(T a, T b) { return a + b; }

Itt a requires clause után zárójelben lévő rész nem egy érvényes constraint. A helyes megoldás vagy egy conceptet definiálunk, vagy requires requires formát használunk:

template<typename T>
    requires requires(T a, T b) { a + b; }
T add(T a, T b) { return a + b; }

A requires requires rút, de néha szükséges. A legjobb gyakorlat: definiáljunk conceptet, és azt használjuk a clause-ban.

8.1.15.3 3. Túl szűk concept

A Container concept definiálásakor sokan csak a nem-konstans begin()-et ellenőrzik:

template<typename T>
concept BadContainer = requires(T c) {
    { c.begin() } -> std::input_or_output_iterator;
    { c.end() } -> std::input_or_output_iterator;
};

Ez a concept hamis lesz egy const T típusú konténerre, vagy olyan konténerre, amely csak konstans iterátorokat ad. Ha a szándék az, hogy a konténer mind T, mind const T esetén iterálható legyen, akkor a conceptet szélesíteni kell:

template<typename T>
concept Container = requires(T& c, const T& cc) {
    { c.begin() } -> std::input_or_output_iterator;
    { c.end() } -> std::input_or_output_iterator;
    { cc.begin() } -> std::input_or_output_iterator;
    { cc.end() } -> std::input_or_output_iterator;
} && std::destructible<T>;

A T& és const T& paraméterekkel biztosítjuk, hogy a concept a valós használati módokat tükrözze.

8.1.15.4 4. Túl tág concept

A concept definiálásakor könnyű pusztán szintaktikai követelményeket megadni, és elfelejteni a szemantikai elvárásokat. Például:

template<typename T>
concept Addable = requires(T a, T b) {
    a + b;
};

Ez igaz olyan típusra, ahol operator+ létezik, de annak eredménye nem feltétlenül értelmes matematikai összeg. A conceptek elsősorban szintaktikai feltételeket rögzítenek; a szemantikai garanciákat a megvalósításnak kell biztosítania és dokumentálnia. Ezért fontos a concept nevének megválasztása és a dokumentáció: az Addable név azt sugallja, hogy az összeadás kommutatív, de ezt a nyelv nem tudja ellenőrizni. A gyakorlatban a standard std::semiregular vagy std::regular conceptek gyakran elegendőek a szemantika egy részének rögzítésére.

8.1.15.5 5. A requires kifejezésben lévő változók deklarációja hibás

A requires kifejezés paraméterei a törzsön belül használt változókat vezetik be. Ha a törzsben olyan változót használunk, amely nincs deklarálva a requires paraméterlistájában, fordítási hiba lesz. Például:

template<typename T>
concept HasValue = requires {
    { T::value } -> std::convertible_to<bool>;  // HIBA: nincs változó, de rendben, mert T::value kifejezés
};

Ez valójában helyes, mert a T::value kifejezés nem igényel változót. De ha a T egy objektumát akarjuk használni:

template<typename T>
concept HasMethod = requires {
    T().foo();  // Ez ideiglenes T-t hoz létre, ami lehet, hogy default konstruálható, de nem garantált
};

Ha T nem default konstruálható, a concept hamis lesz, ami nem feltétlenül a szándék. A helyes megoldás a változó bevezetése a requires paraméterlistában, így a concept csak akkor teljesül, ha T default konstruálható, és a foo() hívható:

template<typename T>
concept HasMethod = requires(T t) {
    t.foo();
};

De ha nem akarjuk megkövetelni a default konstruálhatóságot, használhatunk std::declval<T>()-t:

template<typename T>
concept HasMethod = requires {
    { std::declval<T&>().foo() } -> std::same_as<void>;
};

A std::declval<T&>() nem hoz létre tényleges objektumot, csak típusszintű kifejezést ad, így nem követeli meg a konstruálhatóságot.

8.1.16 Labor: saját concept és ellenőrzés

A labor célja, hogy a fenti ismereteket egy kis, fordítható példán alkalmazd. A feladat: definiálj egy Incrementable nevű conceptet, amely azt követeli meg, hogy egy típus támogassa az elő- és utóinkrementálást a szokásos szemantikával. Ezután valósíts meg egy Counter osztályt, amely teljesíti a conceptet, és egy NoIncrement osztályt, amely nem. Ellenőrizd a conceptet static_assert-tel és egy constrained függvénnyel.

8.1.17 Feladatleírás

  1. Definiáld az Incrementable conceptet a <concepts> fejléc segítségével. A concept követelményei:
    • Az ++x kifejezés T& típusú.
    • Az x++ kifejezés T típusú (vagy T-re konvertálható).
  2. Definiálj egy Counter osztályt, amely egy egész értéket tárol, és támogatja az operator++ mindkét formáját.
  3. Definiálj egy NoIncrement osztályt, amelynek nincs operator++-a.
  4. Használj static_assert-et a concept igazolására (Incrementable<Counter> igaz, Incrementable<NoIncrement> hamis).
  5. Írj egy template<Incrementable T> void increment_twice(T& x) függvényt, amely kétszer hívja az ++x-et.
  6. Fordítsd le a kódot, és futtasd a Counter-re vonatkozó tesztet. A NoIncrement-re való hívásnak fordítási hibát kell adnia – ezt kommentben dokumentáld.

8.1.18 Kiinduló kód (példa)

#include <concepts>
#include <iostream>

// 1. Saját concept
template<typename T>
concept Incrementable = requires(T x) {
    { ++x } -> std::same_as<T&>;     // előinkrementálás T&-et ad
    { x++ } -> std::convertible_to<const T&>; // utóinkrementálás konvertálható const T&-re
};

// 2. Counter osztály
class Counter {
public:
    Counter(int value = 0) : value_(value) {}
    Counter& operator++() {
        ++value_;
        return *this;
    }
    Counter operator++(int) {
        Counter old = *this;
        ++(*this);
        return old;
    }
    int value() const { return value_; }
private:
    int value_;
};

// 3. NoIncrement osztály
class NoIncrement {
public:
    void other() {}
};

// 4. static_assert ellenőrzés
static_assert(Incrementable<Counter>);
static_assert(!Incrementable<NoIncrement>);

// 5. Constrained függvény
template<Incrementable T>
void increment_twice(T& x) {
    ++x;
    ++x;
}

int main() {
    Counter c{10};
    increment_twice(c);
    std::cout << c.value() << '\n';  // 12-t kell kiírnia
    // increment_twice(NoIncrement{}); // Fordítási hiba: NoIncrement nem Incrementable
}

8.1.19 Reprodukálható build és teszt

A laborhoz rögzített környezet szükséges. Az alábbi parancsok egy lehetséges buildet mutatnak:

  • Fordító: GCC 13.2 (a g++ --version ellenőrizhető)
  • Szabvány: C++20
  • Kapcsolók: -std=c++20 -Wall -Wextra -Werror -pedantic-errors

Fordítási parancs:

g++ -std=c++20 -Wall -Wextra -Werror -pedantic-errors -o incrementable_lab incrementable_lab.cpp

Futtatás:

./incrementable_lab

Várt kimenet:

12

Mért kimenet (példányosítva): a fenti parancsok futtatásakor a program a 12 értéket írja ki, és a fordítás sikeres. A NoIncrement-re vonatkozó increment_twice hívás kikommentelve van, mert az a concept nem teljesülése miatt fordítási hibát ad.

A labor nem futásidejű teljesítményt mér, hanem a concept helyes működését ellenőrzi. A mérési napló rögzítse:

  • A fordítás sikerességét (várt: sikeres; mért: sikeres).
  • A futás kimenetét (várt: 12; mért: 12).
  • A static_assert-ek eredményét (várt: mindkettő igaz; mért: fordítási hiba nélkül teljesül).
  • A kikommentált hibás hívás fordítási hibájának diagnosztikai üzenetét (várt: a hiba a concept megsértésére utal; mért: például error: constraints not satisfied vagy hasonló, a pontos szöveg fordítófüggő). Ez utóbbit érdemes dokumentálni, mert a concept-hibaüzenetek rövidebbek és célzottabbak, mint a régi SFINAE-hibák.

8.1.20 Önellenőrző kérdés

Definiálj egy TotalOrdered conceptet a <concepts> fejléc elemeinek felhasználásával, majd írj egy constrained_min függvényt, amely két azonos típusú argumentum közül a kisebbet adja vissza. Milyen concept(ek)et használsz, és miért? (A megoldás során gondold át, hogy a std::totally_ordered önmagában elegendő-e, vagy szükség van-e std::same_as-re a típusok egyezésének biztosításához.)

A fejezetben bemutatott eszközök – a concept definíció, a requires kifejezések, a constraint-ek összetétele és a standard conceptek – képezik az alapját a következő egységnek, ahol a constraint-ek részletesebb formáit, a normalizálást és a range-ekkel való integrációt tárgyaljuk. A labor eredményei megmutatják, hogy a conceptek nemcsak olvashatóbbá teszik a sablonokat, hanem a hibaüzeneteket is emberközelibbé alakítják, ami a nagyméretű kódbázisok karbantarthatóságának egyik kulcsa.
