10.2 CRTP és statikus polimorfizmus

A CRTP (Curiously Recurring Template Pattern) a C++ egyik leghatékonyabb eszköze statikus polimorfizmus megvalósítására. A minta lényege, hogy egy alapsablon a saját sablonparamétereként kapja meg a belőle származtatott osztály típusát, így az alaposztály fordítási időben hivatkozhat a származtatott típusra, és meghívhatja annak metódusait anélkül, hogy virtuális függvényekre vagy dinamikus diszpécsre lenne szükség. Ez a technika széles körben elterjedt a teljesítménykritikus könyvtárakban – például az Eigen lineáris algebrai könyvtárban, a Boost különböző komponenseiben, vagy a Microsoft Active Template Library-ben –, mert a virtuális hívások költségét és a vtable indirekcióját teljesen kiküszöböli, miközben megőrzi a kód újrafelhasználhatóságát és a típusbiztonságot.

A fejezet célja, hogy bemutassa a CRTP mint statikus felület működését, a derived-to-base cast mechanizmusát, valamint a statikus és dinamikus diszpécser közötti választás szempontjait. Az itt tárgyalt fogalmakra épít a következő egység, amely a mixineket és a policy-based designt tárgyalja, ezért fontos, hogy az olvasó pontosan értse a CRTP belső működését és korlátait.

10.2.1 A CRTP alapmintája

A legegyszerűbb CRTP-sémában egy sablon alaposztály a származtatott típust sablonparaméterként kapja meg, és a saját metódusaiban static_cast segítségével hivatkozik arra. Tekintsük a következő példát:

template <typename Derived>
class Base {
public:
    void interface() {
        // A statikus felület meghívja a származtatott implementációt.
        static_cast<Derived*>(this)->implementation();
    }

    // Az alaposztály biztosíthat közös adatokat vagy segédfüggvényeket is.
};

class Concrete : public Base<Concrete> {
public:
    void implementation() {
        // A tényleges művelet.
    }
};

A Concrete osztály a Base<Concrete>-ből származik, tehát a Base sablon a Derived = Concrete típussal példányosodik. Amikor a Base<Concrete>::interface() metódus fut, a static_cast<Derived*>(this) kifejezés a this mutatót Concrete* típusra alakítja, így a Base osztály közvetlenül eléri a Concrete::implementation() metódust. A hívás teljesen statikus: a fordító már fordítási időben ismeri a Derived típust, ezért a függvényhívás közvetlenül, virtuális indirekció nélkül történik.

Ez a minta azért „kuriózusan rekurzív”, mert a Base osztály definíciója a saját sablonparaméterére hivatkozik, ami formálisan egy rekurzív típusdefiníciót eredményez: Concrete örökli Base<Concrete>-t, amely Concrete-re hivatkozik, de ez a rekurzió csak a típus szintjén jelenik meg, futásidőben semmilyen rekurzív hívás nem történik. A fordító a sablon példányosításakor feloldja a típust, és a generált kódban nincs szükség virtuális táblára.

10.2.2 A statikus felület fogalma

A CRTP egyik leggyakoribb alkalmazása egy statikus felület definiálása. A hagyományos objektumorientált programozásban egy absztrakt alaposztály virtuális függvényekkel írja elő a származtatott osztályok számára a megvalósítandó interfészt. A CRTP ugyanezt a célt szolgálja, de a szerződést nem a virtuális függvény, hanem a sablonpéldányosítás kényszeríti ki.

Tekintsünk egy Printable mixint, amely egy print metódust ad minden olyan osztálynak, amelyik megvalósítja a do_print műveletet:

#include <iostream>

template <typename Derived>
class Printable {
public:
    void print(std::ostream& os) const {
        // A statikus felület meghívja a származtatott osztály privát vagy publikus implementációját.
        static_cast<const Derived*>(this)->do_print(os);
    }
};

class Point : public Printable<Point> {
    int x_, y_;
public:
    Point(int x, int y) : x_(x), y_(y) {}

    // A felület által megkövetelt implementáció.
    void do_print(std::ostream& os) const {
        os << '(' << x_ << ", " << y_ << ')';
    }
};

int main() {
    Point p{3, 4};
    p.print(std::cout); // Kiírja: (3, 4)
}

Ebben a példában a Printable<Point> osztály biztosítja a print nyilvános metódust, amely a static_cast<const Point*>(this)->do_print(os) hívással éri el a Point osztály do_print tagfüggvényét. A Point osztály nem rendelkezik virtuális függvényekkel, így az objektumok nem tartalmaznak vtable-mutatót, és a print hívás közvetlenül a do_print-re fordul. A do_print lehet akár privát is, ha a Printable alaposztályt friend-ként deklaráljuk, de a fenti példában publikus.

A statikus felület előnye, hogy a fordító teljesen ellenőrizni tudja a típusok helyességét. Ha a Point osztály nem definiálja a do_print metódust, a p.print() hívás fordítási hibát eredményez, mert a Printable<Point>::print() sablonpéldányosítása során a static_cast<const Point*>(this)->do_print(os) kifejezés érvénytelen lesz. A hibaüzenet ugyan néha hosszú és nehezen olvasható, de a C++20 concepts bevezetésével ez a helyzet jelentősen javítható (lásd a Concepts és requires egységet).

10.2.3 Derived-to-base cast és annak biztonsága

A CRTP alapvető művelete a static_cast<Derived*>(this), amely a Base<Derived> típusú objektumot a Derived típusra alakítja. Ez a cast azért érvényes, mert a Derived osztály nyilvánosan örökli a Base<Derived>-t, tehát a Base<Derived> egyértelmű alaposztálya a Derived-nek. A static_cast ebben az irányban (alaposztályról származtatottra) akkor szabályos, ha a mutató ténylegesen egy Derived objektumra mutat. Mivel a CRTP-ben a Base<Derived> csak akkor példányosodhat, ha a Derived valóban belőle származik, a cast gyakorlatilag mindig érvényes, feltéve, hogy a sablonparamétert helyesen adják meg.

A fő kockázatot a helytelen sablonparaméter jelenti. Tekintsük a következő hibás kódot:

class Wrong : public Base<Other> { // Other nem a Wrong osztály
public:
    void implementation() {}
};

Ebben az esetben a Base<Other> példányosodik, és a static_cast<Other*>(this) a Wrong objektumot Other*-ként kezeli, ami undefined behavior. A program lefordulhat, de futás közben váratlan viselkedést produkálhat. Ennek elkerülésére a CRTP alaposztály konstruktorában érdemes static_assert-et elhelyezni, amely ellenőrzi, hogy a Derived valóban a Base<Derived> leszármazottja:

template <typename Derived>
class Base {
protected:
    Base() {
        static_assert(std::is_base_of_v<Base<Derived>, Derived>,
                      "Derived must inherit from Base<Derived>");
    }
public:
    void interface() {
        static_cast<Derived*>(this)->implementation();
    }
};

Ez a static_assert a Base<Derived> konstruktorában fut le, és mivel a konstruktor csak akkor példányosodik, amikor egy Derived objektumot létrehoznak, a hibás használat fordítási időben kiderül. Fontos megjegyezni, hogy a static_assert a konstruktor törzsében van, nem a sablon definíciójában, mert a sablonpéldányosítás során a törzs csak akkor kerül kiértékelésre, ha a konstruktort ténylegesen használják. Ezzel elkerülhető a felesleges fordítási hiba, ha a sablont csak deklarálják, de nem példányosítják.

Egy másik tipikus hibaforrás, ha a static_cast-ot elfelejtik, és az alaposztály közvetlenül hívja a Derived metódust a this mutatón keresztül:

template <typename Derived>
class Base {
public:
    void interface() {
        // Hiba: a this típusa Base<Derived>*, nem Derived*.
        this->implementation(); // Fordítási hiba, ha nincs ilyen tag.
    }
};

A Base<Derived> osztályban nincs implementation tag, így ez a kód nem fordul le. A static_cast tehát elengedhetetlen a származtatott típus eléréséhez.

10.2.4 Statikus és dinamikus diszpécser összehasonlítása

A CRTP és a virtuális függvények közötti választás alapvető tervezési döntés, amelyet a futásidejű követelmények, a memória- és teljesítménycélok, valamint a kód karbantarthatósága határoz meg. A két mechanizmus közötti különbséget a következő táblázat foglalja össze:

Szempont Dinamikus diszpécser (virtuális) Statikus diszpécser (CRTP)
Hívás feloldása Futásidőben, vtable-n keresztül Fordítási időben, közvetlen hívás
Objektum mérete + egy vtable-mutató (általában 8 bájt) Nincs extra méret
Hívási költség Indirekt hívás, branch prediction nehéz Közvetlen hívás, gyakran inline-olható
Heterogén kollekció Támogatott (pl. vector<Base*>) Nem lehetséges (különböző típusok)
Kódduplikáció Egyetlen függvény minden leszármazottra Minden leszármazottra külön kód generálódik
Fordítási idő Kisebb Nagyobb lehet (több példányosítás)
Futásidejű típusinformáció RTTI elérhető Nincs dinamikus típus

A CRTP legnagyobb előnye a teljesítmény. Mivel a hívás célja fordítási időben ismert, a fordító beillesztheti a hívott függvény törzsét a hívás helyére, ami lehetővé teszi a további optimalizációkat (konstans propagálás, dead code elimination). Egy virtuális hívásnál a fordító általában nem tudja bizonyítani a tényleges típust, ezért kénytelen indirekt hívást generálni, ami a modern CPU-kon is többletköltséggel jár (a vtable beolvasása, a függvénymutató betöltése, az indirekt ugrás). Szűk belső ciklusokban ez a különbség jelentős lehet, amit a laborban méréssel is alátámasztunk.

Ugyanakkor a CRTP-nek ára van. A statikus polimorfizmus nem teszi lehetővé heterogén kollekciók létrehozását, mert a Base<Derived1> és a Base<Derived2> különböző típusok, és nincs közös alaposztályuk (hacsak nem vezetünk be egy virtuális alaposztályt, ami viszont visszahozza a dinamikus diszpécset). Továbbá minden egyes származtatott típushoz külön kód generálódik, ami növelheti a bináris méretet, különösen sok különböző típus esetén. Ez a kódduplikáció nem feltétlenül probléma, ha a metódusok kicsik és gyakran hívottak, de nagy függvényeknél a fordítási idő és a memóriaigény megnőhet.

A döntési szabály tehát: ha a típusok halmaza fordítási időben ismert, és nincs szükség futásidejű típusfeloldásra, a CRTP kiváló választás. Ha viszont a kódnak ismeretlen, bővíthető típusokkal kell dolgoznia (pl. plugin-rendszerek, dinamikus objektumhierarchiák), a virtuális függvények elkerülhetetlenek. A kettő kombinálható is: egy CRTP-alapú osztály virtuális függvényeket is tartalmazhat, ha szükséges, de ez a statikus diszpécser előnyeit részben eltörli.

10.2.5 CRTP-alapú mixinek

A mixin egy olyan osztály, amelyet arra terveztek, hogy más osztályokhoz örököljenek hozzá, és ezáltal kiegészítő funkcionalitást adjanak. A CRTP-vel kombinálva a mixin hozzáfér a származtatott osztály típusához, így a mixin metódusai a származtatott osztály specifikus műveleteire építhetnek. Ezzel a technikával könnyen összeállítható újrafelhasználható komponensek, amelyek a statikus polimorfizmus előnyeit élvezik.

Példaként tekintsünk egy Counted mixint, amely nyilvántartja az adott típusú objektumok számát:

#include <cstddef>

template <typename Derived>
class Counted {
    static inline std::size_t count_ = 0;
public:
    Counted() { ++count_; }
    Counted(const Counted&) { ++count_; }
    Counted(Counted&&) { ++count_; }
    ~Counted() { --count_; }

    static std::size_t instance_count() { return count_; }
};

class Widget : public Counted<Widget> {
    // Widget specifikus adatok és műveletek.
};

class Gadget : public Counted<Gadget> {
    // Gadget specifikus adatok.
};

Itt a Counted<Widget> és a Counted<Gadget> különálló sablonpéldányok, ezért a count_ statikus adattag mindegyik típushoz külön-külön létezik. A Widget osztály öröklése a Counted<Widget>-ből biztosítja, hogy minden Widget objektum létrehozása és megsemmisítése frissíti a számlálót, anélkül, hogy a Widget osztálynak bármit tennie kellene. A mixin tehát tiszta, újrafelhasználható funkcionalitást ad.

Egy másik gyakori mixin a Comparable, amely a < operátort valósítja meg egy compare metódusra építve:

template <typename Derived>
class Comparable {
public:
    bool operator<(const Derived& other) const {
        return static_cast<const Derived*>(this)->compare(other) < 0;
    }
    // Hasonlóan lehet >, <=, >=...
};

class Version : public Comparable<Version> {
    int major_, minor_;
public:
    Version(int major, int minor) : major_(major), minor_(minor) {}
    int compare(const Version& other) const {
        if (major_ != other.major_) return major_ - other.major_;
        return minor_ - other.minor_;
    }
};

A Comparable<Version> mixin a Version osztály compare metódusára támaszkodva biztosítja a < operátort. A Version osztályban nincs szükség az operátor külön megírására, és a hívás teljesen statikus.

A mixinek kombinálhatók is: egy osztály több CRTP-alapú mixinből is származhat, mindegyik a saját funkcionalitását adva hozzá. Például egy Widget lehet Counted<Widget> és Comparable<Widget> is, amennyiben a sablonparaméter mindig a tényleges osztálytípus.

10.2.6 Labor: CRTP-alapú mixin készítése

A labor célja, hogy a hallgató saját kezűleg implementáljon egy CRTP-alapú mixint, és ellenőrizze annak helyességét, valamint megmérje a statikus diszpécser teljesítménybeli előnyét a virtuális függvényes megoldással szemben. A feladat specifikációja a következő:

  1. Készíts egy Printable mixint, amely egy print metódust ad a származtatott osztályoknak. A mixin a származtatott osztály do_print metódusát hívja, amely egy std::ostream& paramétert kap. A mixin ne tartalmazzon virtuális függvényeket.

  2. Készíts egy Counted mixint, amely nyilvántartja az adott típusú példányok számát. A mixin konstruktorai és destruktora frissítik a számlálót, és egy statikus instance_count() metódus kérdezi le az aktuális értéket. A mixin legyen másolható és mozgatható, és a másolás/mozgatás során is helyesen tartsa nyilván a példányszámot.

  3. Definiálj egy Point osztályt, amely mindkét mixinből örököl: Point : public Printable<Point>, public Counted<Point>. A Point tárolja az x és y koordinátákat, és valósítsa meg a do_print metódust.

  4. Írj teszteket (pl. Catch2 vagy egyszerű assert makrók segítségével), amelyek ellenőrzik:

    • A print metódus a várt szöveget írja ki.
    • A Counted mixin helyesen számolja a példányokat, beleértve a másolást és mozgatást is.
    • A Point objektum mérete nem tartalmaz vtable-mutatót (használhatod a static_assert(sizeof(Point) == sizeof(int) * 2) ellenőrzést, ha nincs padding).

  5. Készíts egy virtuális függvényes alternatívát ugyanerre a funkcionalitásra, ahol a print egy virtuális függvény egy absztrakt alaposztályban, a számolás pedig virtuális destruktorral és statikus számlálóval történik.

  6. Mérj meg legalább a következőket:

    • A két megoldás bináris méretét (pl. size parancs Linuxon).
    • Egy egyszerű benchmark futásidejét, amely nagy számú (10^7) print hívást hajt végre mindkét változaton (a kiírást irányítsd egy std::ostringstream-be, hogy ne a konzol legyen a szűk keresztmetszet).
    • A Point objektum méretét mindkét esetben.

  7. Rögzítsd a mérési eredményeket egy naplófájlban, feltüntetve a fordító verzióját (pl. GCC 13.2), a szabványverziót (C++20), az optimalizációs szintet (-O2), a hardvert (CPU típus, memória), valamint a várt és mért értékeket. A várt eredmény az, hogy a CRTP-s változat binárisa kisebb, a futásideje rövidebb, és az objektum mérete nem tartalmaz vtable-mutatót. A tényleges mérési adatoknak ezt a tendenciát kell mutatniuk, de a pontos számok a környezettől függenek.

A feladat megoldásához ajánlott buildrendszer: CMake, amely a -Wall -Wextra -pedantic -Werror kapcsolókkal fordít. A kódot le kell futtatni AddressSanitizer és UndefinedBehaviorSanitizer alatt is, hogy kizárjuk a memóriahibákat és az undefined behaviort. A tesztfuttatásokat izolált környezetben végezd, és a mérési naplóban dokumentáld az eredményeket.

A labor megoldásának egy lehetséges váza:

// printable.hpp
#pragma once
#include <ostream>

template <typename Derived>
class Printable {
public:
    void print(std::ostream& os) const {
        static_cast<const Derived*>(this)->do_print(os);
    }
};

// counted.hpp
#pragma once
#include <cstddef>

template <typename Derived>
class Counted {
    static inline std::size_t count_ = 0;
public:
    Counted() { ++count_; }
    Counted(const Counted&) { ++count_; }
    Counted(Counted&&) { ++count_; }
    ~Counted() { --count_; }
    static std::size_t instance_count() { return count_; }
};

// point.hpp
#pragma once
#include "printable.hpp"
#include "counted.hpp"

class Point : public Printable<Point>, public Counted<Point> {
    int x_, y_;
public:
    Point(int x, int y) : x_(x), y_(y) {}
    void do_print(std::ostream& os) const {
        os << '(' << x_ << ", " << y_ << ')';
    }
};

A teszteléshez használhatunk egyszerű assert-eket vagy egy keretrendszert. A mérési naplóban külön kell feltüntetni a várt és a mért értékeket, például:

Metrika Várt (CRTP) Mért (CRTP) Várt (virtuális) Mért (virtuális)
Bináris méret kisebb pl. 12 345 bájt nagyobb pl. 13 456 bájt
Futásidő (10^7 hívás) gyorsabb pl. 0,12 s lassabb pl. 0,18 s
sizeof(Point) 8 bájt (nincs vtable) 8 bájt 16 bájt (vtable ptr) 16 bájt

A mérés során minden futtatást többször meg kell ismételni, és az átlagot, illetve a szórást is rögzíteni kell. A pontos módszertant a Profilozás és teljesítmény-mérés egység tárgyalja, de itt is érvényes, hogy a mérési körülményeket dokumentálni kell.

10.2.7 Tipikus hibák és elkerülésük

A CRTP használata során a leggyakoribb hibák a következők:

  1. Helytelen sablonparaméter: a származtatott osztály nem saját magát adja meg sablonargumentumként. Ez undefined behaviorhez vezethet. Megoldás: a static_assert a konstruktorban, ahogy fent bemutattuk.

  2. Hiányzó static_cast: az alaposztály a this mutatón keresztül próbálja elérni a származtatott osztály tagjait, ami fordítási hibát okoz. Megoldás: mindig static_cast<Derived*>(this) vagy static_cast<const Derived*>(this).

  3. Többszörös öröklődés és nem egyértelmű alaposztály: ha a Derived több Base-ből is örököl (pl. class D : public Base<D>, public OtherBase), a static_cast akkor is érvényes, de ügyelni kell arra, hogy a Base<D> egyértelmű alaposztály legyen. Ha a Derived virtuálisan örökli a Base-t, a CRTP nem működik, mert a virtuális alaposztály elrendezése eltérő.

  4. Objektumvágás (slicing): ha egy Base<Derived> objektumot érték szerint másolunk vagy tárolunk, a származtatott része elveszik, és a static_cast érvénytelen lesz. A CRTP-t használó osztályokat általában ne másoljuk érték szerint; ha mégis szükséges, gondoskodjunk arról, hogy a Base konstruktorai védettek legyenek, és a Derived osztály szabályozza a másolást.

  5. Végtelen rekurzió a sablonpéldányosításban: ha a Derived osztály definíciója a Base<Derived>-re hivatkozik, a fordító rekurzívan próbálhatja példányosítani a sablont. Ez általában nem fordul elő, mert a Derived típus előbb deklarálódik, mint hogy a Base<Derived> példányosodna, de bizonyos esetekben (pl. ha a Derived típusdefiníciója a Base<Derived> egy metódusában jelenik meg) előfordulhat. A megoldás a sablonparaméterek és a definíciók gondos rendezése.

  6. Túlzott kódduplikáció: ha a mixinek nagy metódusokat tartalmaznak, minden leszármazott osztályhoz külön kód generálódik. Ez megnövelheti a bináris méretet. Megoldás: a nagy, típusfüggetlen logikát érdemes nem-sablon segédfüggvényekbe kiszervezni, és a mixin csak a típusfüggő részt tartalmazza.

10.2.8 Összegzés és önellenőrző kérdés

A CRTP egy erőteljes eszköz a statikus polimorfizmus megvalósítására. Lehetővé teszi, hogy egy alaposztály hozzáférjen a származtatott típushoz, és annak metódusait virtuális függvények nélkül hívja meg. Ez a technika fordítási időben feloldott, gyors, és gyakran kisebb kódot eredményez, de nem támogatja a heterogén kollekciókat, és kódduplikációhoz vezethet. A mixinekkel kombinálva a CRTP újrafelhasználható, típusbiztos komponensek építését teszi lehetővé.

Önellenőrző kérdés: Magyarázd el, miért nem lehet egy std::vector<Base*> típusú kollekcióban tárolni CRTP-alapú osztályok objektumait, ha a Base egy CRTP-alaposztály. Milyen alternatívát javasolnál, ha szükség van heterogén tárolásra? (A válaszhoz gondold át a statikus és dinamikus típusok közötti különbséget, valamint a type erasure lehetőségét, amelyet a Type erasure alapelvei egység tárgyal.)
