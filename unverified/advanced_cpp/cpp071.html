19.2 Memory-mapped files és mmap

A fájlok memóriába képezése (memory-mapped file) az operációs rendszer lapkezelőjét használja arra, hogy egy fájl tartalmát közvetlenül a folyamat virtuális címterébe illessze. A hagyományos read()/write() rendszerhívások a kernel lapcache-e és a felhasználói puffer között másolnak; az mmap() ezt a másolást kerüli el, mert a lapok a kernel lapcache-éből a folyamat címterébe kerülnek. A fájl egy-egy tartománya így C++ pointerrel, std::span-nel és a megszokott memóriakezelési nyelvi elemekkel érhető el.

A módszer előnye a véletlen hozzáférés egyszerűsége, a lapok igény szerinti betöltése, valamint az, hogy ugyanazt a fizikai lapot több folyamat is oszthatja. Hátránya viszont, hogy a hibák egy része nem szinkron kivételként, hanem aszinkron jelként (például SIGBUS) jelentkezik, és a hordozhatóság platformfüggő. A C++ standard nem tartalmaz memory-mapped file eszközt; a jelen fejezet a POSIX mmap() API-t használja, és a Windows CreateFileMapping/MapViewOfFile eltéréseit szükség szerint jelöli.

19.2.1 A POSIX mmap API

A fájl leképezésének három alapvető rendszerhívása az mmap, az msync és a munmap. Az mmap létrehozza a leképezést, az msync a módosítások tartóssá tételét segíti, a munmap pedig felszabadítja a címterület-tartományt. A függvények deklarációja a <sys/mman.h> fejlécben található.

#include <sys/mman.h>

void *mmap(void *addr, size_t length, int prot, int flags, int fd, off_t offset);
int msync(void *addr, size_t length, int flags);
int munmap(void *addr, size_t length);

Az mmap paraméterei közül a hordozható C++ kódban az addr általában nullptr. Ezzel a kernelre bízzuk a cím választását. A length a leképezendő bájtok száma; ha nulla, az API sikerrel visszatérhet, de a terület elérése érvénytelen, ezért a wrapperünk ezt kezelni fogja. A prot a memória-hozzáférési védelmet adja meg: PROT_READ, PROT_WRITE, PROT_EXEC és PROT_NONE. Írásra olvasni is kell, ezért írásos leképezéshez PROT_READ | PROT_WRITE értéket használunk. A flags leggyakrabban MAP_SHARED vagy MAP_PRIVATE. A MAP_SHARED esetén a memóriába írt adatok visszakerülnek a fájlba; a MAP_PRIVATE copy-on-write módon dolgozik, tehát az írások csak a folyamat saját lapjait módosítják, a fájlt nem.

A fd egy nyitott fájldeszkriptor. A fájl méretét fstat()-tal kérdezzük le, és length-ként ezt használjuk. Az offset a fájlon belüli eltolás; egyszerű esetben nulla. Ha az offset nem laphatárhoz igazított, a kernel a leképezést laphatárra igazítja, de a visszaadott pointer az offset-hez tartozó első bájtra mutat. Hordozható kódban legjobb nulla offsetet használni.

Az mmap siker esetén a leképezés kezdőcímét adja vissza, hiba esetén a MAP_FAILED értéket, amely (void*)-1, nem pedig nullptr. A hibakódot az errno tartalmazza. Gyakori hibák: EACCES, ha a fájlt nem a prot-nak megfelelően nyitottuk meg; ENOMEM, ha nincs elegendő virtuális címterület; EINVAL, ha a paraméterek érvénytelenek.

Fontos, hogy az mmap nem foglal le fizikai memóriát. Címterületet és lapbejegyzéseket hoz létre; a tényleges lapok az első hozzáféréskor, laphiba útján töltődnek be. Ez a demand paging.

Az msync a leképezés egy tartományát szinkronizálja a háttértárral. A flags lehet MS_SYNC, amely blokkol a lemezre írás befejezéséig, vagy MS_ASYNC, amely ütemezi a visszaírást. A MS_INVALIDATE a többi leképezés cache-ét érvényteleníti. MAP_SHARED írásos leképezésnél a memóriába írt adatok a kernel lapcache-ébe kerülnek; a tartóssághoz msync(MS_SYNC) szükséges. A munmap is visszaírja a dirty lapokat, de a lemezre írás ütemezett maradhat; a munmap után a folyamat már nem használhatja a pointert.

A munmap eltávolítja a leképezést. A pointer a hívás után azonnal érvénytelen; a további hozzáférés use-after-unmap, ami undefined behavior.

19.2.2 RAII wrapper C++-ban

A nyers mmap hívás könnyen hibához vezet, ha a leképezést nem párosítjuk pontosan egy munmap hívással. Éppen ezért érdemes RAII osztályba zárni. A következő mmap_file osztály a konstruktorban megnyitja a fájlt, lekérdezi a méretet, leképezi a tartalmat, majd lezárja a fájldeszkriptort. A leképezés a close() után is él, mert a kernel a lapokat az inode-hoz köti, nem a descriptorhoz.

A destruktor mindig felszabadítja a leképezést, ha van. Az osztály move-only: a másolás nem egyértelmű, mert két objektum ugyanazt a leképezést birtokolná. A move konstruktor noexcept, a move assignment pedig akkor dobhat, ha a meglévő munmap hibát ad; ilyenkor az objektumot üres állapotba hozzuk, hogy a destruktor ne kíséreljen meg újabb felszabadítást.

// mmap_file.hpp
#ifndef MMAP_FILE_HPP
#define MMAP_FILE_HPP

#include <sys/mman.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <unistd.h>

#include <cerrno>
#include <cstddef>
#include <span>
#include <system_error>
#include <utility>

class mmap_file {
public:
    explicit mmap_file(const char* path, int prot = PROT_READ, int flags = MAP_SHARED)
        : addr_(nullptr), size_(0)
    {
        int open_flags = (prot & PROT_WRITE) ? O_RDWR : O_RDONLY;
        int fd = ::open(path, open_flags);
        if (fd == -1) {
            throw std::system_error(errno, std::generic_category(), "open");
        }

        struct stat st{};
        if (::fstat(fd, &st) != 0) {
            int e = errno;
            (void)::close(fd);
            throw std::system_error(e, std::generic_category(), "fstat");
        }

        if (st.st_size < 0) {
            (void)::close(fd);
            throw std::system_error(EINVAL, std::generic_category(), "negative file size");
        }

        std::size_t sz = static_cast<std::size_t>(st.st_size);
        if (sz != 0) {
            void* p = ::mmap(nullptr, sz, prot, flags, fd, 0);
            if (p == MAP_FAILED) {
                int e = errno;
                (void)::close(fd);
                throw std::system_error(e, std::generic_category(), "mmap");
            }
            addr_ = p;
            size_ = sz;
        }

        // A leképezés a close után is él. A close hibát itt elnyeljük,
        // mert a mapping létrehozása után a konstruktor már nem dobhat.
        (void)::close(fd);
    }

    ~mmap_file() noexcept {
        if (addr_) {
            (void)::munmap(addr_, size_);
            addr_ = nullptr;
            size_ = 0;
        }
    }

    mmap_file(const mmap_file&) = delete;
    mmap_file& operator=(const mmap_file&) = delete;

    mmap_file(mmap_file&& other) noexcept
        : addr_(std::exchange(other.addr_, nullptr)),
          size_(std::exchange(other.size_, 0)) {}

    mmap_file& operator=(mmap_file&& other) {
        if (this == &other) return *this;
        if (addr_) {
            if (::munmap(addr_, size_) != 0) {
                int e = errno;
                addr_ = nullptr;
                size_ = 0;
                throw std::system_error(e, std::generic_category(), "munmap");
            }
        }
        addr_ = std::exchange(other.addr_, nullptr);
        size_ = std::exchange(other.size_, 0);
        return *this;
    }

    std::size_t size() const noexcept { return size_; }

    std::span<const std::byte> data() const noexcept {
        if (size_ == 0) return {};
        return {static_cast<const std::byte*>(addr_), size_};
    }

    std::span<std::byte> data() noexcept {
        if (size_ == 0) return {};
        return {static_cast<std::byte*>(addr_), size_};
    }

    void sync(bool synchronous = true) {
        if (addr_ == nullptr || size_ == 0) return;
        int sync_flags = synchronous ? MS_SYNC : MS_ASYNC;
        if (::msync(addr_, size_, sync_flags) != 0) {
            throw std::system_error(errno, std::generic_category(), "msync");
        }
    }

private:
    void* addr_;
    std::size_t size_;
};

#endif

A data() metódus std::span<const std::byte>-ot ad vissza. A std::span C++20-ban nem birtokló nézet; érvényessége az mmap_file objektum élettartamához kötött. Ha az mmap_file-t move-oljuk, a régi objektum addr_ és size_ tagja nullára áll, ezért a régi data() által kiadott span érvénytelenné válik, bár a leképezés maga az új objektum tulajdonába kerül.

A sync() metódus csak MAP_SHARED írásoknál releváns. MAP_PRIVATE esetén a msync nem írja vissza a copy-on-write lapokat a fájlba, mert azok nem a fájlhoz tartoznak. A nem hordozható MAP_POPULATE, MAP_LOCKED és hasonló Linux-specifikus flag-eket a példában nem használunk.

19.2.3 Lapozás és hibatűrés

A leképezés lapokban történik. A lapméretet sysconf(_SC_PAGESIZE) adja vissza; tipikusan 4 KiB vagy 64 KiB. A kernel a fájl tartalmát lapokra osztva kezeli, és a folyamat virtuális memóriájában a lapok a kernel lapcache-ére mutatnak. Az első olvasás laphibát okoz, amelyet a kernel a fájl megfelelő részének betöltésével old fel.

A mmap hossza nem kötelezően lapméret többszöröse. Ha a fájl mérete például 10 000 bájt, a leképezés 10 000 bájt hosszú. Az utolsó lap a fájl végét tartalmazza; a lapnak a fájl vége utáni része nem elérhető. Ha a mmap hosszát nagyobbra vennénk a fájlméretnél, akkor a fájl vége utáni terület elérése SIGBUS jelet vált ki. Ezért a wrapper mindig pontosan a fstat() által kapott méretet használja.

A SIGBUS a memory-mapped file-ok tipikus aszinkron hibája. Akkor is előfordulhat, ha a fájlt leképeztük, majd egy másik folyamat truncate()-tel csökkenti a méretét. A leképezésben korábban érvényes lapok mögül eltűnik a háttértár; a hozzáférésre a kernel SIGBUS-t küld. Ennek kezelése signal handlerrel nehéz, mert a hibás utasítás újra lefut, ezért a megelőzés a helyes stratégia. Olyan fájlokat, amelyeket más folyamat is írhat vagy rövidíthet, vagy ne leképezzünk hosszú élettartammal, vagy gondoskodjunk fájlméret-zárról, illetve alkalmazzunk ftruncate()-et a várt méretre a leképezés előtt.

A SIGSEGV ezzel szemben a memória-hozzáférési védelem megsértésekor lép fel: például ha PROT_READ leképezésre írunk, vagy a munmap után használjuk a pointert. A kettő közötti különbség fontos a diagnosztikában.

A hibatűrés további eleme a msync visszatérési értékének ellenőrzése. Ha a lemez megtelik, a dirty lapok kiírása ENOSPC hibát adhat. Az msync(MS_SYNC) hibáját kivételként kezelhetjük, ahogy a wrapperünk teszi. A munmap hibáját a destruktorban elnyeljük, mert a C++ destruktor noexcept; ez a RAII kompromisszum.

A lapozás finomhangolására POSIX-ban a madvise() hívás ad javaslatokat. Például a MADV_SEQUENTIAL jelzi a kernelnek, hogy a fájlt szekvenciálisan fogjuk olvasni, ezért előreolvashat; a MADV_RANDOM éppen ellenkezőleg, a véletlen hozzáférést jelzi. Ezek a flag-ek Linuxon elérhetők, de nem hordozhatók, ezért csak akkor érdemes használni őket, ha a kód amúgy is platformfüggő.

19.2.4 Labor: mmap-alapú fájlolvasó

A labor célja egy mmap-alapú fájlolvasó tervezése és ellenőrzése. A program létrehoz egy 1 GiB méretű bináris fájlt, amelynek minden bájtja 0xAB. Ezután két módszerrel kiszámítja a bájtok összegét: mmap_file-en keresztül, valamint hagyományos std::ifstream-mel ellenőrzésként. A 0xAB kitöltés miatt a várt összeg egyszerűen számítható: file_size * 0xAB mod 2^64, mert az unsigned std::uint64_t túlcsordulása jól definiált.

A kód reprodukálható buildben fordul, rögzített compilerrel és standardverzióval. A mérési naplóban a mért és a várt értéket külön szekciókban közöljük.

// mmap_test.cpp
#include "mmap_file.hpp"

#include <algorithm>
#include <array>
#include <chrono>
#include <cstdint>
#include <cstdio>
#include <fstream>
#include <iostream>
#include <stdexcept>
#include <vector>

namespace {
constexpr std::size_t file_size = 1024ULL * 1024ULL * 1024ULL;
constexpr std::uint8_t fill_byte = 0xAB;
constexpr std::size_t io_buffer_size = 1024ULL * 1024ULL;

void create_test_file(const char* path, std::size_t size, std::uint8_t fill) {
    std::ofstream out(path, std::ios::binary | std::ios::trunc);
    if (!out) throw std::runtime_error("ofstream open failed");

    std::vector<char> buf(io_buffer_size, static_cast<char>(fill));
    std::size_t remaining = size;
    while (remaining > 0) {
        std::size_t n = std::min(io_buffer_size, remaining);
        out.write(buf.data(), static_cast<std::streamsize>(n));
        if (!out) throw std::runtime_error("ofstream write failed");
        remaining -= n;
    }
}

std::uint64_t sum_mmap(const char* path) {
    mmap_file m(path, PROT_READ, MAP_SHARED);
    std::uint64_t sum = 0;
    for (std::byte b : m.data()) {
        sum += std::to_integer<std::uint64_t>(b);
    }
    return sum;
}

std::uint64_t sum_ifstream(const char* path) {
    std::ifstream in(path, std::ios::binary);
    if (!in) throw std::runtime_error("ifstream open failed");

    std::array<char, io_buffer_size> buf{};
    std::uint64_t sum = 0;
    while (in) {
        in.read(buf.data(), static_cast<std::streamsize>(buf.size()));
        std::streamsize n = in.gcount();
        for (std::streamsize i = 0; i < n; ++i) {
            sum += static_cast<unsigned char>(buf[static_cast<std::size_t>(i)]);
        }
    }
    return sum;
}
} // namespace

int main(int argc, char* argv[]) {
    const char* path = (argc > 1) ? argv[1] : "/tmp/mmap_test.bin";

    std::cout << "generating " << file_size << " bytes...\n";
    create_test_file(path, file_size, fill_byte);

    std::uint64_t expected = static_cast<std::uint64_t>(file_size) * fill_byte;
    std::cout << "expected checksum: " << std::hex << expected << std::dec << '\n';

    auto t0 = std::chrono::steady_clock::now();
    std::uint64_t mmap_sum = sum_mmap(path);
    auto t1 = std::chrono::steady_clock::now();

    auto t2 = std::chrono::steady_clock::now();
    std::uint64_t ifstream_sum = sum_ifstream(path);
    auto t3 = std::chrono::steady_clock::now();

    std::cout << "mmap checksum: " << std::hex << mmap_sum << std::dec << '\n';
    std::cout << "ifstream checksum: " << std::hex << ifstream_sum << std::dec << '\n';
    std::cout << "match: " << (mmap_sum == expected && ifstream_sum == expected ? "yes" : "no") << '\n';

    double mmap_ms = std::chrono::duration<double, std::milli>(t1 - t0).count();
    double ifstream_ms = std::chrono::duration<double, std::milli>(t3 - t2).count();
    std::cout << "mmap time: " << mmap_ms << " ms\n";
    std::cout << "ifstream time: " << ifstream_ms << " ms\n";

    std::remove(path);
}

A build parancs Linuxon, GCC-vel:

g++ -std=c++20 -O2 -DNDEBUG -Wall -Wextra -pedantic \
    -fno-omit-frame-pointer -fsanitize=address,undefined \
    mmap_test.cpp -o mmap_test

Futtatás:

./mmap_test /tmp/mmap_test.bin

A mérési napló az alábbi szerkezetben rögzíthető. A mért értékeket a tényleges futtatás után kell kitölteni; az alábbi számok szemléltető helyőrzők.

A std::ifstream ellenőrző olvasás nem a mmap teljesítményelőnyének bizonyítására szolgál, hanem a kiszámított összeg helyességének megerősítésére. A mmap előnye akkor jelentkezik, ha a fájlt sokszor véletlenszerűen érjük el, vagy ha a lapok már a cache-ben vannak. A szekvenciális bájtösszegzésben a hagyományos read() is hasonlóan teljesíthet, mert mindkettő ugyanazt a kernel lapcache-t használja.

19.2.5 Tipikus hibák és helyes megoldás

Az mmap használata során a következő hibákat gyakran érdemes elkerülni:

  • A MAP_FAILED ellenőrzésének elhagyása. A mmap hiba esetén (void*)-1-et ad, nem nullptr-t; ha ezt nem ellenőrizzük, a munmap vagy a pointerhasználat undefined behaviorhez vezet.
  • A leképezés hosszának túl nagyra vétele. Ha a length nagyobb, mint a fájl mérete, a fájl vége utáni lapok elérése SIGBUS-t okoz. Mindig a fstat() által adott méretet használjuk.
  • Írás PROT_READ leképezésre. A kernel SIGSEGV-t küld; a mmap_file data() non-const változata ezt nem tudja ellenőrizni, ezért a hívó felelőssége a PROT_WRITE biztosítása.
  • Az msync elhagyása írás után. MAP_SHARED írások a lapcache-be kerülnek, de a lemezre írás nem garantált azonnal. A tartóssághoz msync(MS_SYNC) szükséges.
  • A MAP_PRIVATE félreértése. A MAP_PRIVATE írások nem jelennek meg a fájlban. Ha a fájl tartós módosítása a cél, MAP_SHARED-et kell használni.
  • Use-after-unmap. A munmap után a pointer és az abból készült std::span érvénytelen. Az mmap_file RAII-ja ezt megelőzi, de a data() által kiadott spant nem szabad a leképező objektum élettartamán túl használni.
  • A fájlméret futás közbeni csökkentésének figyelmen kívül hagyása. Ha a fájl mérete a leképezés alatt csökken, a leképezés egyes részei SIGBUS-t okozhatnak. Megelőzésként a fájlt nem szabad ilyen módon módosítani, vagy ftruncate()-tel rögzíteni kell a méretet.

19.2.6 Önellenőrzés és továbbvivő eredmények

A fejezet végén ellenőrizd a megértést:

  1. Miért kaphat egy folyamat SIGBUS-t egy mmap-elt fájl olvasása közben?
  2. Mi a különbség a MAP_SHARED és a MAP_PRIVATE leképezés között?
  3. Melyik rendszerhívással lehet garantálni, hogy a MAP_SHARED írások lemezre kerüljenek?
  4. Miért érvénytelen a régi objektum data() által visszaadott span az mmap_file move konstruktor után?

Az itt bevezetett mmap-elt memóriaterület közvetlen elérése alapozza meg a DMA-pufferek és a hardverregiszterek hasonló alacsony szintű kezelését; ott a volatile és a memóriabarrier szabályai kulcsfontosságúak lesznek.
