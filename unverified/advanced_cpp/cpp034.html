10.1 Expression templates

A kifejezések lusta, sablonos reprezentációja az egyik legnagyobb hatású, ugyanakkor leggyakrabban félreértett modern C++ technika. A hagyományos operátor-túlterheléssel megírt matematikai vagy tartomány-specifikus könyvtárak gyakran ontják az ideiglenes objektumokat, mert minden egyes +, * vagy más művelet azonnal kiértékelődik, és a részeredményt egy új tárolóba helyezi. Az expression template-ek ezt a kiértékelést elhalasztják: a műveleti kifejezést egy sabloncsomópontokból álló, fordítási idejű szerkezetté alakítják, amely csak akkor fut le, amikor ténylegesen értékre van szükség – jellemzően egy hozzárendeléskor vagy egy indexeléskor. Ebben az alfejezetben lépésről lépésre felépítünk egy ilyen, vektoraritmetikát megvalósító kis keretrendszert, bemutatjuk a csomópontok, a lusta kiértékelés és az optimalizáció elvét, majd azonosítjuk a tipikus élettartam- és típusdedukciós csapdákat. A cél nem az, hogy egy teljes, termelésre kész lineáris algebra könyvtárat hozzunk létre, hanem hogy megértsük, mi történik a fordító szintjén, és milyen kompromisszumokat kell kötni.

10.1.1 A probléma: ideiglenes objektumok és a kiértékelési hullám

Vegyünk egy egyszerű, std::array-t beburkoló vektorosztályt, amely a + operátort túlterheli, hogy két vektor elemenkénti összegét adja vissza.

#include <array>
#include <cstddef>

template <std::size_t N>
class NaiveVector {
public:
    NaiveVector() = default;

    NaiveVector(const std::array<double, N>& data) : data_(data) {}

    double& operator[](std::size_t i) { return data_[i]; }
    double operator[](std::size_t i) const { return data_[i]; }

    std::size_t size() const { return N; }

    NaiveVector operator+(const NaiveVector& rhs) const {
        NaiveVector result;
        for (std::size_t i = 0; i < N; ++i) {
            result[i] = (*this)[i] + rhs[i];
        }
        return result;
    }

private:
    std::array<double, N> data_{};
};

Ha a felhasználó egy olyan kifejezést ír, mint d = a + b + c;, akkor a fenti implementáció a következő lépéseket hajtja végre:

  1. Kiértékeli a + b-t: létrehoz egy NaiveVector<N> ideiglenest, kitölti az összegekkel.
  2. Kiértékeli (a + b) + c-t: újabb ideiglenest hoz létre, amelyet az előző ideiglenes és c elemeiből számol.
  3. Végül a d-be másolja az eredményt.

Minden + művelet egy teljes ciklust futtat, memóriát foglal (vagy legalábbis a veremben létrehozza a tömböt), és másol. Kis méret esetén a fordító szinte mindent optimalizálhat, de nagyobb, dinamikus méretű tárolóknál, vagy ha a kifejezések mélyek és bonyolultak, ez a költség jelentős lehet. Ráadásul a műveletek nem fuzionálhatók: a fordító nehezen látja át a teljes kifejezést, mert az egyes operátorhívások önálló függvényekként jelennek meg, és a köztes tárolók akadályozzák a cache-barát, egyetlen ciklusba való összevonást.

Az expression template-ek lényege, hogy az a + b + c kifejezést ne értékeljük ki azonnal. Ehelyett a kifejezés egy olyan típust kap, amely leírja a műveletet, de tényleges számítást nem végez. A kiértékelés akkor következik be, amikor a kifejezésből vektorrá konvertálunk, például egy értékadó operátorban. Ekkor a célvektor elemeit egyetlen ciklusban, a teljes kifejezésfát bejárva állítjuk elő. Nincs ideiglenes tároló, nincs felesleges másolat, és a fordító a rekurzívan beágyazott operator[] hívásokat agresszívan inline-olhatja.

10.1.2 Alapépítőkövek: a CRTP-alapú kifejezés interfész

Az expression template-ekben minden kifejezés – a levelek és a belső csomópontok is – egy közös interfészt valósítanak meg: rendelkeznek size() és operator[] tagfüggvénnyel. A size() a kifejezés dimenzióját adja vissza, az operator[] pedig a kifejezés adott indexű elemét számítja ki, anélkül, hogy a teljes eredményt tárolná. A gyakori tervezési minta a Curiously Recurring Template Pattern (CRTP), amellyel a közös műveleteket egy alaposztályba emelhetjük, és a származtatott típus önmagára hivatkozva adja meg a tényleges viselkedést.

#include <cstddef>

template <typename Derived>
struct VectorExpr {
    const Derived& self() const noexcept {
        return static_cast<const Derived&>(*this);
    }

    std::size_t size() const noexcept {
        return self().size();
    }

    double operator[](std::size_t i) const {
        return self()[i];
    }
};

Ez az alaposztály nem tárol semmit, csak egy kényelmes, statikus polimorfizmust biztosító réteg. A Vector osztályunk ebből származik, és megvalósítja a tényleges adattárolást.

#include <array>
#include <cassert>
#include <cstddef>

template <std::size_t N>
class Vector : public VectorExpr<Vector<N>> {
public:
    Vector() = default;

    Vector(const std::array<double, N>& data) : data_(data) {}

    Vector(const Vector&) = default;
    Vector& operator=(const Vector&) = default;

    double& operator[](std::size_t i) {
        assert(i < N);
        return data_[i];
    }

    double operator[](std::size_t i) const {
        assert(i < N);
        return data_[i];
    }

    std::size_t size() const noexcept {
        return N;
    }

private:
    std::array<double, N> data_{};
};

Fontos, hogy a Vector a VectorExpr<Vector<N>>-ből származik, így a többi kifejezéstípus is fogadhatja mint levélcsomópontot.

10.1.3 Csomóponttípusok: a műveletek lusta reprezentációi

Most definiáljuk a kifejezések belső csomópontjait. Kezdjük az összeadással: az AddExpr két alkifejezést tárol, és a size() valamint az operator[] rekurzívan hívja az operandusok megfelelő metódusait.

template <typename L, typename R>
class AddExpr : public VectorExpr<AddExpr<L, R>> {
public:
    AddExpr(const L& lhs, const R& rhs)
        : lhs_(lhs), rhs_(rhs) {}

    std::size_t size() const noexcept {
        return lhs_.size();
    }

    double operator[](std::size_t i) const {
        return lhs_[i] + rhs_[i];
    }

private:
    L lhs_;
    R rhs_;
};

Itt az L és R lehet Vector<N> vagy maga is egy kifejezéstípus, például AddExpr<...>. A sablonparaméterek érték szerint tárolják az operandusokat. Ez azt jelenti, hogy amikor egy kifejezés létrejön, az operandusok másolódnak. Kis vektoroknál ez elhanyagolható, de nagy, dinamikus tárolóknál a másolás ismét költséget jelent. A gyakorlatban ezért a levelek referenciaként, a belső csomópontok pedig érték szerint szoktak tárolódni. Az egyszerűség kedvéért itt mindent érték szerint tárolunk; a szöveg későbbi részeiben kitérünk a referenciatárolás élettartam-problémáira.

A skalárral való szorzás hasonló:

template <typename E>
class ScalarMulExpr : public VectorExpr<ScalarMulExpr<E>> {
public:
    ScalarMulExpr(const E& expr, double scalar)
        : expr_(expr), scalar_(scalar) {}

    std::size_t size() const noexcept {
        return expr_.size();
    }

    double operator[](std::size_t i) const {
        return expr_[i] * scalar_;
    }

private:
    E expr_;
    double scalar_;
};

A tagadás, a kivonás, a skalárral való osztás és más műveletek is ugyanerre a mintára épülnek. A kivonás például:

template <typename L, typename R>
class SubExpr : public VectorExpr<SubExpr<L, R>> {
public:
    SubExpr(const L& lhs, const R& rhs)
        : lhs_(lhs), rhs_(rhs) {}

    std::size_t size() const noexcept {
        return lhs_.size();
    }

    double operator[](std::size_t i) const {
        return lhs_[i] - rhs_[i];
    }

private:
    L lhs_;
    R rhs_;
};

A kulcs: ezek a típusok nem tárolnak tömböt, csak leírást; a tényleges számítás az operator[]-ben történik, amikor a hívó kéri.

10.1.4 Operátor-túlterhelések: kifejezésfák építése

Ahhoz, hogy a felhasználó a megszokott a + b szintaxist használhassa, túl kell terhelnünk az operátorokat. Az operátorok visszatérési értéke nem vektor, hanem a megfelelő kifejezéstípus. Mivel a Vector is VectorExpr-ből származik, írhatunk egy általános operátort, amely bármilyen kifejezést fogad.

template <typename L, typename R>
auto operator+(const VectorExpr<L>& lhs, const VectorExpr<R>& rhs) {
    return AddExpr<L, R>(lhs.self(), rhs.self());
}

template <typename L, typename R>
auto operator-(const VectorExpr<L>& lhs, const VectorExpr<R>& rhs) {
    return SubExpr<L, R>(lhs.self(), rhs.self());
}

template <typename E>
auto operator*(const VectorExpr<E>& expr, double scalar) {
    return ScalarMulExpr<E>(expr.self(), scalar);
}

template <typename E>
auto operator*(double scalar, const VectorExpr<E>& expr) {
    return ScalarMulExpr<E>(expr.self(), scalar);
}

Ezek a függvények nem végeznek számítást, csak összekötik az operandusokat egy új típusba. A lhs.self() hívás a VectorExpr CRTP-ből jön, és visszaadja a tényleges származtatott objektumot. Ezáltal a AddExpr<L, R> konstruktora a pontos típusú operandusokat kapja.

A fenti operátorok felhasználhatók összetett kifejezésekben:

Vector<4> a, b, c;
// ... inicializálás
auto expr = a + b + c; // típus: AddExpr<AddExpr<Vector<4>, Vector<4>>, Vector<4>>

Az expr nem vektor, hanem egy kifejezésfa, amely a + műveleteket írja le. A tényleges kiértékelés még nem történt meg. Ezt a típust akár ki is nyomtathatjuk typeid-dal, de általában nem szükséges: a felhasználó ritkán akarja explicit módon kezelni.

10.1.5 Lusta kiértékelés és a hozzárendelés

A kifejezésfa akkor válik hasznossá, amikor valamilyen tárolóba akarjuk írni az eredményt. A Vector osztályunknak szüksége van egy sablonos értékadó operátorra, amely elfogad bármilyen VectorExpr leszármazottat, és a size()-nek megfelelő módon kitölti a célobjektumot.

template <typename Expr>
Vector& operator=(const VectorExpr<Expr>& expr) {
    const Expr& e = expr.self();
    assert(e.size() == N);
    for (std::size_t i = 0; i < N; ++i) {
        data_[i] = e[i];
    }
    return *this;
}

Itt minden egyes e[i] hívás rekurzívan kiértékeli a kifejezést az adott indexre. Ez a lusta kiértékelés lényege: a számítás a hozzárendelés pillanatában, egyszerre, indexenként történik. A ciklus egyetlen bejárást végez a célvektoron, és minden elemhez a teljes kifejezésfa értékét számolja. Nincs köztes tároló, nincs felesleges másolat.

A Vector osztály konstruktorát is kiegészíthetjük hasonló módon, hogy kifejezésből lehessen vektort létrehozni:

template <typename Expr>
Vector(const VectorExpr<Expr>& expr) {
    const Expr& e = expr.self();
    assert(e.size() == N);
    for (std::size_t i = 0; i < N; ++i) {
        data_[i] = e[i];
    }
}

Ezáltal írhatunk:

Vector<4> d = a + b + c; // a konstruktor értékeli ki a kifejezést

Fontos megjegyezni, hogy ez a konstruktor nem explicit, így implicit konverzió történik. Ez általában kívánatos, mert a kifejezések használata így természetes, de ügyelni kell arra, hogy ne okozzon akaratlan konverziót más helyeken.

10.1.6 Optimalizáció: ideiglenesek elkerülése és loop fusion

Az expression template-ek egyik legfőbb előnye, hogy a fordító a teljes kifejezést egyetlen ciklusba tudja összevonni (loop fusion). A fenti hozzárendelési operátorban az e[i] rekurzív hívásláncot alakít ki, de mivel minden tagfüggvény konstans, inline lehet, és a fordító képes a ciklust kibontani és a rekurziót eltüntetni. A gyakorlatban a -O2 optimalizációs szinttel a generált kód közel azonos azzal, mintha kézzel írtunk volna egyetlen for ciklust, amely az összes műveletet egyesíti:

for (size_t i = 0; i < N; ++i) {
    d[i] = a[i] + b[i] + c[i];
}

Ezzel szemben a naiv operátor-túlterheléses változatban a kód három különálló ciklusra bomlik: az a+b kiértékelése, a (a+b)+c kiértékelése, majd a d-be másolás. Mindegyik ciklus memóriát ír és olvas, ami rontja a cache kihasználtságot, és nagy méreteknél akár többszörös lassulást is okozhat.

A kifejezésekben rejlő másik előny, hogy a típusban nem csak a műveletek, hanem az alkalmazott együtthatók is fordítási időben ismertek. Így a skalárral való szorzásnál a skalár konstansként bekerülhet az utasításba, elkerülve a memóriahozzáférést.

10.1.7 Tipikus hibák és csapdák

Az expression template-ek szépsége mellett számos buktatót rejtenek. Ezek közül a leggyakoribbakat érdemes alaposan megérteni, mert a hibakeresés ezekkel a típusokkal nem mindig intuitív.

10.1.8 auto és a kifejezés élettartama

A legveszélyesebb csapda az auto használata, amikor egy kifejezést akarunk tárolni. Tekintsük a következő kódot:

Vector<4> a{1, 2, 3, 4}, b{5, 6, 7, 8};
auto sum = a + b; // sum típusa: AddExpr<Vector<4>, Vector<4>>

Itt sum nem vektor, hanem egy AddExpr objektum, amely érték szerint másolatot tárol a-ról és b-ről. Ez ebben az esetben működik, de ha a kifejezés referenciákat tárolna (ami a gyakori optimalizáció), akkor a és b élettartama fontos lenne. Ha a kifejezést ideiglenes vektorokból hozzuk létre:

auto bad = makeVector(4) + makeVector(4); // a makeVector prvalue-kat ad vissza

A makeVector hívások által visszaadott prvalue-k a teljes kifejezés végén megsemmisülnek, ezért a bad-ben tárolt referenciák (ha azok lennének) danging mutatókká válnának. Mivel a mi implementációnk érték szerint tárol, ez a konkrét példa nem okoz gondot, de a gyakorlati könyvtárakban (például az Eigen) a referenciatárolás miatt az auto használata tilos, hacsak nem vagyunk tisztában a belső működéssel. A javaslat: ha egy kifejezés eredményét vektorként akarjuk tárolni, használjunk explicit típust, vagy decltype(auto) helyett Vector<N> result = a + b; formát. Ha mégis egy kifejezést akarunk későbbre elmenteni, gondoskodjunk arról, hogy az operandusok élettartama lefedje a kifejezését, vagy használjunk std::move-ot a kifejezés kiértékelésének pillanatában.

10.1.9 Többszörös kiértékelés mellékhatásos elemkifejezésekkel

A lusta kiértékelés miatt az operator[] minden hozzáféréskor újra kiszámolja az adott elemet. Ha a kifejezésben olyan tagfüggvény vagy függvény szerepel, amely mellékhatással bír, akkor az operator[] ismételt hívásai többször is lefuttathatják azt. Például:

struct WeirdVector : VectorExpr<WeirdVector> {
    double operator[](size_t i) const {
        std::cout << "index " << i << std::endl; // mellékhatás
        return i;
    }
    size_t size() const { return 4; }
};

Ha ezt beillesztjük egy kifejezésbe, majd a célvektorba másoljuk, az operator[] annyiszor hívódik meg, ahány elemet átmásolunk, és minden alkalommal lefuttatja a std::cout-ot. Ez általában nem kívánatos. A szabály: a kifejezésfákban csak tiszta, mellékhatásmentes műveleteket használjunk. A gyakorlati lineáris algebra könyvtárak ezt garantálják, mert a vektorok elemei konstans kifejezések.

10.1.10 Kivételbiztonság és a célobjektum állapota

A sablonos értékadó operátorban a ciklus egyszerre ír minden elemet. Ha a kifejezés kiértékelése közben kivétel dobódik, a célvektor félkész állapotba kerülhet. A robusztus megoldás a copy-and-swap idióma: hozzunk létre egy ideiglenes vektort a kifejezésből, és ha az sikeres, cseréljük ki a cél adatait. A mi rögzített méretű std::array alapú Vector-unknál ez triviális, mert a kivétel nem okoz részleges írást (az std::array elemei primitívek). Dinamikus tárolásnál azonban a kivételbiztonságot külön meg kell tervezni.

10.1.11 Sablonhiba-üzenetek és a concepts szerepe

Az expression template-ek mély, egymásba ágyazott típusokat hoznak létre. Ha a felhasználó rossz típusú kifejezést ad meg, a fordító hibaüzenetei hosszúak és nehezen olvashatók lehetnek. C++20-tól kezdve concepts-ekkel korlátozhatjuk az operátorok és a sablonos értékadó paramétereit, így a hiba korábban, érthetőbb formában jelenik meg. A laborban ezért egy egyszerű VectorLike conceptet definiálhatunk, és az operátorokat erre hivatkozva írhatjuk:

template <typename T>
concept VectorLike = requires(T t, size_t i) {
    { t.size() } -> std::convertible_to<size_t>;
    { t[i] } -> std::convertible_to<double>;
};

template <VectorLike L, VectorLike R>
auto operator+(const L& lhs, const R& rhs) {
    return AddExpr<L, R>(lhs, rhs);
}

Ez a gyakorlatban javítja a diagnosztikát és megakadályozza, hogy nem megfelelő típusok kerüljenek a kifejezésfába. A koncepciók tárgyalása a 8.1–8.2 egységekben részletesen megtörténik; itt csak annyit használunk, amennyi a példa tisztaságához szükséges.

10.1.12 Labor: egyszerű expression template implementáció

A labor célja, hogy az olvasó saját kezűleg építsen egy működő, mérhető expression template-keretrendszert, és vezessen mérési naplót a teljesítményéről. A következő lépéseket javasoljuk.

10.1.12.1 lépés: Az alaposztály és a vektor

Kezdje a fenti VectorExpr és Vector osztályok lemásolásával. Ügyeljen arra, hogy a Vector mérete sablonparaméter, és az operator[] mindkét (konstans és nem-konstans) változata ellenőrizze az indexhatárt.

10.1.12.2 lépés: A kifejezéscsomópontok

Valósítsa meg az AddExpr, ScalarMulExpr és opcionálisan a SubExpr, DivExpr osztályokat. Mindegyik a VectorExpr-ből származik, és size() valamint operator[] metódusokat ad.

10.1.12.3 lépés: Operátorok és értékadó

Definiálja a +, -, * operátorokat, és a Vector sablonos értékadó operátorát. Próbálja ki a kifejezést:

Vector<4> a{1, 2, 3, 4};
Vector<4> b{5, 6, 7, 8};
Vector<4> c{2, 2, 2, 2};

Vector<4> result = a + b * 3.0 - c;

Ellenőrizze az eredményt: result[0] = 1 + 53 - 2 = 14, result[1] = 2 + 63 - 2 = 18, stb. Írjon assert-ekkel működő tesztet.

10.1.12.4 lépés: Benchmark

Hasonlítsa össze három implementáció futásidejét: - a fenti expression template-es vektor, - egy naiv operátor-túlterheléses vektor, amely minden műveletet azonnal kiértékel, - egy kézzel írt, egyetlen ciklusos változat, amely közvetlenül számolja d[i] = a[i] + b[i]*s - c[i] stb.

Használjon rögzített méretű Vector<64>-et, és hajtson végre egymillió iterációt, minden iterációban újra kiértékelve ugyanazt a kifejezést más adatokkal. Mérje az időt std::chrono::steady_clock segítségével, és futtassa a mérést ötször, majd vegye az átlagot. A mérési naplóban rögzítse: - Fördítő és verzió (például GCC 13.2.0) - Standardverzió (C++20) - Optimalizációs szint (-O2 -DNDEBUG) - Hardver (CPU, memória) - Az input mérete (N = 64) - A futtatások száma (1 000 000 iteráció, 5 mérés) - A mért átlagidők és a szórás

A várt eredmény irányjellegű: az expression template-es változatnak legalább olyan gyorsnak kell lennie, mint a kézzel írt ciklus, és gyorsabbnak, mint a naiv változat. A pontos számok környezetfüggők, ezért a mért és várt értéket külön kell feltüntetni. A következő ábra (szöveges leírással) érzékelteti a várható tendenciát:

  • Naiv vektor: 1.00 (referencia)
  • Expression template: ~0.60–0.80
  • Kézzel írt ciklus: ~0.60–0.80

Azaz az expression template megszünteti az ideigleneseket, és a fordító képes a ciklusok összevonására, így a teljesítmény a kézzel írt optimalizált változathoz közelít.

10.1.12.5 lépés: Hiba forgatókönyv

Kísérletezzen az auto használatával:

auto sum = a + b; // típusa AddExpr...
// ...
Vector<4> d = sum; // működik, ha az operandusok még élnek

Magyarázza meg, miért veszélyes ez, ha a kifejezés referenciákat tárol, és mi a teendő ilyen esetben. Írjon egy példát, ahol a sum használata után az operandus vektorokat megsemmisítjük, és figyelje meg, hogy a jelenlegi, érték szerint tároló változat továbbra is működik-e, vagy sem.

10.1.13 Ellenőrző kérdések

  1. Mi a különbség a naiv operátor-túlterheléses vektor és az expression template-es vektor között a kiértékelés időzítésében?
  2. Miért nem ajánlott az auto használata expression template-ek eredményének tárolására, ha a könyvtár referenciákat tárol?
  3. Hogyan segít a CRTP az expression template-ekben?
  4. Milyen kivételbiztonsági megfontolásokat kell tenni dinamikus méretű tárolók esetén a sablonos értékadó operátorban?
  5. Mi a loop fusion, és miért előnyös a cache kihasználtság szempontjából?

10.1.14 Összefoglalás

Az expression template-ek a C++ sablonrendszerének egyik legerőteljesebb alkalmazásai. Lehetővé teszik, hogy a fordító a teljes kifejezést egyetlen fordítási egységként lássa, kiiktassa az ideiglenes tárolókat, és a műveleteket egyetlen optimalizált ciklusba fuzionálja. Az ár a megnövekedett típusbonyolultság, a nehezebben olvasható hibaüzenetek és az élettartam-kezelési csapdák. A fenti keretrendszer egyszerű, de jól szemlélteti az alapelveket; a valódi, termelésre kész könyvtárak (például az Eigen) ennél jóval kifinomultabb megoldásokat alkalmaznak, de a lényegi mechanizmus ugyanaz.

A következő alfejezet (10.2) a CRTP-t és a statikus polimorfizmust tárgyalja részletesebben, amely technikának itt is fontos szerepe volt. Az expression template-ekben használt VectorExpr alaposztály egy tipikus CRTP-alkalmazás, és a következő egységben megvizsgáljuk, hogyan lehet ezt a mintát általánosabban, mixinekkel és policy-based designnal kombinálni. Az itt megszerzett ismeretekre építve az olvasó képes lesz megérteni, hogyan lehet a statikus polimorfizmust teljesítmény és karbantarthatóság szempontjából hatékonyan kiaknázni.
