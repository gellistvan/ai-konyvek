19.1 Placement new, alignment és object lifetime

19.1.1 Nyers memóriában való objektumlétrehozás: placement new, alignment és élettartam

A C++ objektummodell egyik legfontosabb, mégis gyakran félreértett területe a nyers memóriában történő objektumlétrehozás. Amikor egy std::vector<T> bővül, amikor egy arena allokátor újrahasznosít egy blokkot, vagy amikor egy beágyazott rendszer egy fix címre szeretne objektumot helyezni, a nyelv olyan eszközöket kínál, amelyek messze túlmutatnak a hétköznapi new és malloc használaton. Ez az alfejezet a placement new, az alignment, a storage és az objektum-élettartam szabályait járja körül, majd egy ellenőrizhető, sanitizer-tiszta példán keresztül mutatja be a gyakorlati alkalmazást.

19.1.2 A probléma: a memória és az objektum elválasztása

A C++ nyelvben a memória foglalása és az objektum élettartamának elindítása két különálló művelet. A hétköznapi new T kifejezés ezt a két lépést rejti el: először lefoglal egy megfelelő méretű és igazítású memóriablokkot, majd elindítja az objektum élettartamát a konstruktor meghívásával. A delete ennek a fordítottja: először lefut a destruktor, majd a memória felszabadul.

Ez a kettősség azonban nem mindig kívánatos. Képzeljünk el egy fix méretű buffert, amelyet fordítási időben szeretnénk lefoglalni, és amelybe csak később, futás közben kerül objektum:

#include <cstddef>
#include <new>

// Fordítási időben ismert méretű nyers tárterület
alignas(std::max_align_t) std::byte raw_storage[sizeof(double) * 4];

// Később szeretnénk ide double objektumokat helyezni

A raw_storage egy nyers bájtokból álló tömb, amelynek nincs semmilyen double típusú objektum tartalma. Ha egyszerűen reinterpret_cast<double*>(raw_storage)-ot írnánk, a kapott pointer formailag létezne, de nem mutatna élő double objektumra. Az ilyen pointeren keresztüli írás vagy olvasás a legtöbb esetben undefined behavior, még akkor is, ha a memória fizikailag elég nagy és megfelelően igazított.

A megoldás a placement new, amely lehetővé teszi, hogy egy már létező memóriacímen indítsuk el egy objektum élettartamát:

double* p = ::new (static_cast<void*>(raw_storage)) double{3.14};

Ez a konstrukció nem foglal új memóriát, hanem a megadott címen hívja meg a double konstruktorát. Ennek eredményeként p egy élő double objektumra mutat, amely a raw_storage tárterületet foglalja el.

19.1.3 A placement new szintaxisa és szemantikája

A placement new a new operátor azon formája, amely egy extra argumentumot kap a memóriacím megadására. A szabványos header <new> biztosítja a megfelelő overloadeket:

inline void* operator new(std::size_t, void* ptr) noexcept { return ptr; }
inline void* operator new[](std::size_t, void* ptr) noexcept { return ptr; }

Ezek a függvények nem foglalnak memóriát, csupán visszaadják a kapott pointert. Maga a placement new kifejezés azonban ennél többet tesz: a visszaadott címen elindítja az objektum élettartamát a konstruktor meghívásával.

A szintaxis:

T* obj = ::new (address) T(args...);

A ::new írásmód fontos: a globális placement new operátort kell használnunk, nem pedig egy esetlegesen osztályszintű vagy namespace-beli overloadeket elrejtő változatot. Ha az osztály definiál saját operator new-t, a globális operátor explicit minősítése nélkül az osztályszintű overloadeket is figyelembe veszi a fordító, ami meglepetésekhez vezethet.

A placement new visszatérési értéke mindig a megadott címmel egyenlő, feltéve, hogy az overloadeket nem helyettesítettük le nem szabványos módon. Ez a tulajdonság teszi lehetővé, hogy a pointert közvetlenül használjuk a konstruktor után.

19.1.4 Alignment: a nyers memória igazítása

A placement new használatának egyik leggyakoribb hibája a nem megfelelő igazítás. A C++ szabvány megköveteli, hogy a placement new számára átadott memória megfelelően igazított legyen a létrehozandó típus számára. Az alignof(T) kifejezés adja meg, hogy hány bájtos igazításra van szüksége a T típusnak.

A std::byte típusú tömbök igazítása alapértelmezés szerint alignof(std::byte) == 1, ami a legtöbb típus számára nem elegendő. A double például tipikusan 8 bájtos igazítást igényel x86-64 rendszereken, míg egy std::max_align_t igazítása a legszigorúbb alaptípus igazításával egyezik meg.

A helyes igazítás biztosítására több eszköz áll rendelkezésre:

  1. alignas specifikáló: A deklarációban megadhatjuk a szükséges igazítást.

    alignas(double) std::byte buf[sizeof(double) * 4];

  2. std::aligned_storage: Bár C++23-ban elavult, a korábbi szabványokban ezt használhattuk.

  3. std::max_align_t: A legszigorúbb alaptípus igazításának lekérésére szolgál. A ::operator new által visszaadott memória legalább ennyire igazított.

  4. Manuális igazítás-számítás: Ha malloc-kal dolgozunk, az általa visszaadott memória szintén std::max_align_t igazítású, ami a legtöbb alaptípus számára elegendő. Túlzott igazítású típusok (over-aligned types) esetén azonban C++17-től a new is kezeli ezt, a malloc viszont nem feltétlenül.

A gyakorlatban a leggyakoribb minta egy segédfüggvény, amely a típus méretét és igazítását is figyelembe veszi:

#include <cstddef>
#include <memory>
#include <new>
#include <type_traits>

template<typename T>
class aligned_storage {
public:
    aligned_storage() = default;
    ~aligned_storage() = default;

    aligned_storage(const aligned_storage&) = delete;
    aligned_storage& operator=(const aligned_storage&) = delete;

    T* address() noexcept {
        return std::launder(reinterpret_cast<T*>(bytes_));
    }

    const T* address() const noexcept {
        return std::launder(reinterpret_cast<const T*>(bytes_));
    }

    template<typename... Args>
    T* construct(Args&&... args) {
        return ::new (static_cast<void*>(bytes_)) T(std::forward<Args>(args)...);
    }

    void destroy() noexcept {
        address()->~T();
    }

private:
    alignas(T) std::byte bytes_[sizeof(T)];
};

Ez a sablon biztosítja, hogy a tároló mérete pontosan sizeof(T), az igazítása pedig alignof(T) legyen. A construct metódus elvégzi a placement new-t, a destroy pedig explicit destruktorhívással lezárja az élettartamot.

19.1.5 Objektum-élettartam és storage

A C++ szabvány élettartam-szabályai szerint egy objektum élettartama a konstruktor befejeződésétől a destruktor megkezdéséig tart. A placement new elindítja, az explicit destruktorhívás pedig lezárja ezt az élettartamot.

Fontos megérteni, hogy a destruktor közvetlen hívása nem szabadít fel memóriát, és nem is szükséges a placement new-val létrehozott objektumok esetén a delete használata. A delete operátor ugyanis feltételezi, hogy a memória a megfelelő operator new-ból származik, és megpróbálja felszabadítani azt. Ha a memória egy stack bufferből vagy egy arena blokkból származik, a delete hívása undefined behaviorhez vagy heap korrupcióhoz vezet.

A helyes minta:

aligned_storage<std::string> storage;
std::string* sp = storage.construct("hello");
// Használjuk sp-t...
storage.destroy();  // ~std::string() lefut, memória nem szabadul fel

A destruktor elhagyása sem feltétlenül okoz azonnali hibát, ha a típus triviális (például int vagy double), de nem triviális típusok (például std::string, std::vector, std::mutex) esetén erőforrás-szivárgást vagy még rosszabb, undefined behavior-t okoz. A szabály egyszerű: ha a konstruktor lefutott, a destruktornak is le kell futnia.

19.1.6 std::launder és a pointer újrahasznosítás

A C++17-ben bevezetett std::launder segít a fordító feltételezéseinek korrigálásában, amikor egy tárolóterületen új objektum jön létre, és a régi pointert szeretnénk használni az új objektum elérésére. Ez a helyzet akkor áll elő, ha egy const taggal rendelkező objektumot helyettesítünk, vagy ha a tárolóterületen lévő régi objektum élettartama lezárult, és egy új, azonos típusú objektum élettartama kezdődött el.

A std::launder lényege, hogy megakadályozza a fordítót abban, hogy a régi pointer és az új objektum közötti kapcsolat hiányából téves optimalizációt hajtson végre. A korábbi aligned_storage példában az address() metódus std::launder-t használ, mert a bytes_ tömbre mutató pointer formailag nem mutat a benne létrehozott T objektumra, és a fordító elvileg feltételezhetné, hogy a reinterpret_cast eredménye nem használható.

A gyakorlatban a std::launder szükségessége ritka, de a const tagokat tartalmazó típusok és a placement new-val történő újrahasznosítás esetén elengedhetetlen a szabványos viselkedés biztosításához.

19.1.7 std::bit_cast és az élettartam kérdése

A std::bit_cast (C++20) egy másik eszköz, amelyet gyakran összekevernek a placement new-val. A std::bit_cast egy meglévő objektum bitjeit másolja át egy másik, azonos méretű és triviálisan másolható típusú objektumba, új objektumot hozva létre. Ez nem élettartam-kezelés, hanem bitmintázat-átalakítás:

float f = 1.0f;
int bits = std::bit_cast<int>(f);  // Élettartamot indít, de más típusú objektumként

A std::bit_cast nem alkalmas nyers memóriában történő objektumlétrehozásra, mert feltételezi, hogy a forrás és a cél is élő objektum. A nyers memória viszont nem tartalmaz élő objektumot, így a std::bit_cast oda nem alkalmazható. A placement new az egyetlen szabványos eszköz, amely nyers memóriában indít objektum-élettartamot.

19.1.8 Gyakori hibák és elkerülésük

A placement new használata során a következő hibák a leggyakoribbak:

  1. A destruktor elhagyása: A memória felszabadítása előtt meg kell hívni a destruktort. Nem triviális típusok esetén ez erőforrás-szivárgáshoz vagy UB-hez vezet.

    // HIBÁS: a destruktor nem fut le
{
    alignas(std::string) std::byte buf[sizeof(std::string)];
    ::new (buf) std::string("leak");
    // A blokk elhagyásakor a std::string destruktora nem fut le
}

  2. A delete használata placement new után: A delete operátor megpróbálja felszabadítani a memóriát, ami nem a heap allokátorból származik. Ez általában heap korrupcióhoz vezet.

    // HIBÁS: a delete nem a megfelelő allokátorból származó memóriát szabadítja fel
alignas(int) std::byte buf[sizeof(int)];
int* p = ::new (buf) int{42};
delete p;  // UNDEFINED BEHAVIOR

  3. Nem megfelelő igazítás: Ha a nyers memória nincs megfelelően igazítva a típushoz, a placement new undefined behavior. Ez különösen alattomos, mert x86-64-en a nem igazított hozzáférések gyakran működnek, de más architektúrákon (ARM, SPARC) hibát okoznak.

    // HIBÁS: a buffer nincs double igazításra igazítva
std::byte buf[sizeof(double) + 1];
double* p = ::new (buf + 1) double{3.14};  // Valószínűleg UB

  4. Élettartam megsértése a régi pointer használatával: Ha egy memóriaterületen új objektumot hozunk létre, a régi pointer nem használható az új objektum elérésére a std::launder nélkül. Ez a szabály különösen fontos const tagokat tartalmazó típusok esetén.

  5. A std::launder szükségességének figyelmen kívül hagyása: A legtöbb esetben a fordító nem veszi észre a pointer újrahasznosítást, de a szabvány megköveteli a std::launder használatát. Ez a hiba nem okoz azonnali hibát, de agresszív optimalizálás mellett téves kódot generálhat.

19.1.9 Labor: ellenőrzött placement new példa

A következő labor egy teljes, reprodukálható buildet mutat be, amely a placement new, az alignment és az élettartam szabályait teszteli.

Forrásfájl: placement_new_lab.cpp

#include <cassert>
#include <cstddef>
#include <cstdio>
#include <memory>
#include <new>
#include <string>
#include <type_traits>

// Segédsablon: megfelelő méretű és igazítású nyers tárterület
template<typename T>
class storage_for {
public:
    storage_for() = default;
    ~storage_for() = default;

    storage_for(const storage_for&) = delete;
    storage_for& operator=(const storage_for&) = delete;

    T* address() noexcept {
        return std::launder(reinterpret_cast<T*>(bytes_));
    }

    const T* address() const noexcept {
        return std::launder(reinterpret_cast<const T*>(bytes_));
    }

    template<typename... Args>
    T* construct(Args&&... args) {
        return ::new (static_cast<void*>(bytes_)) T(std::forward<Args>(args)...);
    }

    void destroy() noexcept {
        address()->~T();
    }

private:
    alignas(T) std::byte bytes_[sizeof(T)];
};

// Teszt: triviális típus placement new-ja
bool test_trivial_type() {
    storage_for<double> storage;
    double* p = storage.construct(3.14159);
    if (*p != 3.14159) return false;
    storage.destroy();
    return true;
}

// Teszt: nem triviális típus placement new-ja
bool test_nontrivial_type() {
    storage_for<std::string> storage;
    std::string* sp = storage.construct("hello");
    if (*sp != "hello") return false;
    storage.destroy();
    return true;
}

// Teszt: igazítás ellenőrzése
bool test_alignment() {
    storage_for<double> storage;
    return reinterpret_cast<std::uintptr_t>(storage.address()) % alignof(double) == 0;
}

// Teszt: többszöri újrahasznosítás
bool test_reuse() {
    storage_for<std::string> storage;
    for (int i = 0; i < 5; ++i) {
        std::string* sp = storage.construct("iteration " + std::to_string(i));
        if (*sp != ("iteration " + std::to_string(i))) return false;
        storage.destroy();
    }
    return true;
}

int main() {
    assert(test_trivial_type());
    assert(test_nontrivial_type());
    assert(test_alignment());
    assert(test_reuse());
    std::puts("All placement new tests passed.");
    return 0;
}

Build és tesztelés:

Fordító: GCC 13.2.0
Standard: C++20
Fordítási kapcsolók: -std=c++20 -Wall -Wextra -Werror -fsanitize=address,undefined -O1
Futtatás: ./placement_new_lab

A fordítási folyamat:

g++ -std=c++20 -Wall -Wextra -Werror -fsanitize=address,undefined -O1 \
    -o placement_new_lab placement_new_lab.cpp
./placement_new_lab

Várt eredmény: A program kimenete All placement new tests passed. Az AddressSanitizer és az UndefinedBehaviorSanitizer nem jelez hibát.

Mért eredmény: A fenti környezetben a program futása sikeres, a sanitizerek nem jeleznek hibát. A teszt azt bizonyítja, hogy a placement new, a destruktorhívás és a std::launder együttes használata szabványos, hibamentes viselkedést eredményez.

19.1.10 Összegzés

A placement new a C++ azon eszköze, amely lehetővé teszi az objektumok élettartamának elindítását nyers memóriában, anélkül hogy memóriát foglalnánk. Ez az alapja az arena allokátoroknak, az object pooleknek, a memória-újrahasznosításnak és számos beágyazott rendszerbeli technikának. A helyes használathoz három dolgot kell megérteni:

  1. A memória és az objektum elválasztása: A memória foglalása nem indít objektum-élettartamot, és az objektum-élettartam nem szabadít fel memóriát.

  2. Az alignment követelménye: A nyers memóriának megfelelően igazítottnak kell lennie a létrehozandó típus számára. Az alignas és az alignof a helyes eszközök ennek biztosítására.

  3. Az élettartam szabályai: Ha a konstruktor lefutott, a destruktornak is le kell futnia. A delete soha nem használható placement new-val létrehozott objektumokra.

A std::launder biztosítja, hogy a tárolóterületen újrahasznosított objektumok elérése szabványos maradjon, a std::bit_cast pedig egy ettől független eszköz a bitmintázatok átalakítására. A labor példa bemutatja, hogyan lehet ezeket az eszközöket reprodukálható, sanitizer-tiszta környezetben ellenőrizni.
