14.1 STL allokátor modell és PMR

Az STL allokátor modell és a polymorphic memory resource (PMR) a C++ memóriakezelésének két kulcsfontosságú absztrakciója. Az allokátorok lehetővé teszik, hogy a konténerek és algoritmusok ne közvetlenül a globális new-t és delete-et használják, hanem tetszőleges memóriaforrásból dolgozzanak. A PMR ezt az absztrakciót futásidőben cserélhető, type-erased erőforrásként valósítja meg, és a beágyazott rendszerektől a nagy teljesítményű szerveralkalmazásokig egységes megoldást kínál. Ebben az alfejezetben először az allokátor modell alapjait tekintjük át, majd a PMR-t és annak gyakorlati használatát mutatjuk be egy reprodukálható laborral.

14.1.1 Az STL allokátor modell

A konténerek (például a std::vector, std::list, std::map) sablonparaméterként egy allokátor típust kapnak. Az allokátor feladata a nyers memória allokálása és felszabadítása; az objektumok konstrukcióját és destruálását a konténer az allocator_traits segítségével végzi. A C++17 óta az allokátorokra vonatkozó követelményeket a Named Requirement: Allocator fogalmazza meg. Az allokátor egy érték típusú osztály, amely definiálja a value_type típust, valamint az allocate és deallocate tagfüggvényeket. Az std::allocator<T> az alapértelmezett allokátor; ez a ::operator new és ::operator delete függvényekre épül.

Az allokátor lehet állapot nélküli (stateless) vagy állapottal rendelkező (stateful). Egy stateless allokátor például csak naplózást végez, mint az alábbi logging_allocator:

template <typename T>
class logging_allocator {
public:
    using value_type = T;

    logging_allocator() noexcept = default;
    template <typename U>
    logging_allocator(const logging_allocator<U>&) noexcept {}

    T* allocate(std::size_t n) {
        std::cout << "allocate " << n << " * " << sizeof(T) << " bytes\n";
        return static_cast<T*>(::operator new(n * sizeof(T)));
    }

    void deallocate(T* p, std::size_t n) noexcept {
        std::cout << "deallocate " << n << " * " << sizeof(T) << " bytes\n";
        ::operator delete(p);
    }

    template <typename U>
    bool operator==(const logging_allocator<U>&) const noexcept { return true; }
    template <typename U>
    bool operator!=(const logging_allocator<U>&) const noexcept { return false; }
};

Ez az osztály C++17-ben megfelel az allokátor követelményeknek, mert az std::allocator_traits<logging_allocator<T>> automatikusan biztosítja a hiányzó típusokat (például pointer, size_type) és a rebind műveletet. A C++20-as szabvány már nem követeli meg az operator!= definiálását, mert a konténerek az allocator_traits operator==-ját használják, a != pedig abból generálható.

A stateful allokátorok jellemzően egy memóriaterületre, például egy poolra mutatnak. Az alábbi arena_allocator egy egyszerű arena mutatót tárol:

class arena {
public:
    void* allocate(std::size_t bytes, std::size_t alignment);
    void deallocate(void* p, std::size_t bytes, std::size_t alignment);
};

template <typename T>
class arena_allocator {
public:
    using value_type = T;
    using propagate_on_container_move_assignment = std::true_type;

    explicit arena_allocator(arena* a) noexcept : arena_(a) {}

    template <typename U>
    arena_allocator(const arena_allocator<U>& other) noexcept : arena_(other.arena_) {}

    T* allocate(std::size_t n) {
        return static_cast<T*>(arena_->allocate(n * sizeof(T), alignof(T)));
    }

    void deallocate(T* p, std::size_t n) noexcept {
        arena_->deallocate(p, n * sizeof(T), alignof(T));
    }

    template <typename U>
    bool operator==(const arena_allocator<U>& other) const noexcept {
        return arena_ == other.arena_;
    }

private:
    arena* arena_;
    template <typename> friend class arena_allocator;
};

Itt a propagate_on_container_move_assignment típusdefiníció std::true_type, ami azt jelzi, hogy a konténer move assignment során az allokátort is át lehet venni a forrásból. Ha ezt nem definiálnánk, az allocator_traits default std::false_type-ot adna, ami eltérő viselkedést eredményezne.

14.1.2 Az allocator_traits és a konténer-műveletek

A konténerek nem közvetlenül hívják az allokátor tagfüggvényeit, hanem az std::allocator_traits<Alloc> sablonon keresztül. Ez a traits osztály biztosítja a szükséges típusokat és függvényeket, és lehetővé teszi az allokátor interfész minimálisra csökkentését. A allocator_traits többek között a következő tagtípusokat és -függvényeket definiálja:

  • rebind<U>: az allokátor újra-kötése egy másik értéktípusra.
  • pointer, const_pointer, size_type, difference_type.
  • allocate, deallocate, construct, destroy, max_size.
  • select_on_container_copy_construction.
  • propagate_on_container_copy_assignment, propagate_on_container_move_assignment, propagate_on_container_swap.
  • is_always_equal.

A propagate_on_container_move_assignment különösen fontos a teljesítmény szempontjából. Amikor egy konténert move assignment segítségével áthelyezünk, a cél konténernek át kell vennie a forrás memóriáját. Ha az allokátor propagate_on_container_move_assignment értéke std::true_type, akkor a cél allokátora is megkapja a forrás allokátorát, és a memória közvetlenül átvehető. Ez O(1) időt eredményez. Ha az érték std::false_type, az átvétel csak akkor lehet O(1), ha a forrás és a cél allokátorai egyenlőek (operator==); egyébként a forrás elemeit a cél allokátorával kell újraallokálni és áthelyezni, ami O(n) műveletigényt és kivételt okozhat.

Az is_always_equal azt jelzi, hogy az allokátorok mindig egyenlőek-e. Ha ez std::true_type, akkor a konténerek közötti memóriaátvitel mindig megengedett, függetlenül az egyenlőségvizsgálattól. Az std::allocator esetében ez igaz, mert nincs állapota. A PMR polymorphic_allocator esetében azonban az is_always_equal std::false_type, mert két különböző memory_resource-ra mutató allokátor nem egyenlő, még akkor sem, ha a resource-ok logikailag azonosak.

A select_on_container_copy_construction a másoló konstruktor által használt allokátor kiválasztására szolgál. Amikor egy konténert lemásolunk, az új konténer allokátora nem feltétlenül a forrás allokátorának másolata; ehelyett a select_on_container_copy_construction eredményét használják. Ez lehetővé teszi, hogy a másolat más memóriaforrást használjon. Például a std::pmr::polymorphic_allocator esetében a másoló konstruktor a get_default_resource()-ból származó allokátort adja vissza, nem a forrás resource-át. Ez fontos: ha egy PMR vektort egy monotonic buffer resource-szal le akarunk másolni, a másolat már a globális default resource-t fogja használni, nem az eredeti buffert. Ennek elkerülésére explicit módon kell megadni az allokátort.

14.1.3 Polymorphic memory resource (PMR)

A C++17-ben bevezetett <memory_resource> fejléc a memóriaforrások egységes, futásidőben cserélhető absztrakcióját adja. A központi osztály az std::pmr::memory_resource, amely egy absztrakt alaposztály. A publikus allocate, deallocate és is_equal függvények a virtuális do_allocate, do_deallocate és do_is_equal privát függvényeket hívják. A do_allocate visszatérési értéke legalább bytes méretű, alignment igazítású nyers memória; do_deallocate felszabadítja a korábban allokált blokkot (a bytes és alignment értékének meg kell egyeznie az allokáláskor használttal). Az do_is_equal két resource objektum logikai egyenlőségét vizsgálja.

Az std::pmr::polymorphic_allocator<T> egy allokátor, amely egy std::pmr::memory_resource*-ot tárol, így a memóriaforrás futásidőben cserélhető. Ez a type erasure egyik példája: a konténer típusa nem függ a konkrét resource típusától, csak a memory_resource interfésztől. A PMR konténerek, például a std::pmr::vector<T>, nem mások, mint std::vector<T, std::pmr::polymorphic_allocator<T>> aliasok.

A leggyakrabban használt konkrét resource a std::pmr::monotonic_buffer_resource. Ez egy növekvő, nem felszabadító (non-deallocating) arena, amely ideiglenes allokációk gyors kiszolgálására szolgál. A memóriát egy vagy több pufferként foglalja le az upstream resource-tól; az egyes elemek felszabadítása nem adja vissza a memóriát, csak a resource megsemmisülésekor szabadul fel minden. Ez rendkívül hatékony, ha sok kis allokációt egy jól körülhatárolt szakaszon belül végzünk, például egy függvény vagy egy keretrendszerbeli task futása alatt.

A monotonic_buffer_resource konstruktorai lehetővé teszik kezdeti puffer megadását, upstream resource megadását, vagy mindkettőt. Ha kezdeti puffert adunk, az első allokációk abból szolgálhatók ki heap allokáció nélkül. Ha a puffer elfogy, a resource az upstream-től (alapértelmezetten a get_default_resource()) kér egy nagyobb blokkot, és a régi puffert megtartja. A release() metódus felszabadítja az összes, az upstream-től kapott puffert; ezután a resource újra használható, de a korábban kiosztott mutatók érvénytelenné válnak.

A PMR használatának alapmintája az alábbi:

#include <memory_resource>
#include <vector>
#include <array>
#include <cstddef>

void pmr_example() {
    std::array<std::byte, 1024> buffer;
    std::pmr::monotonic_buffer_resource resource(buffer.data(), buffer.size());
    std::pmr::vector<int> numbers{&resource};
    for (int i = 0; i < 100; ++i) {
        numbers.push_back(i);
    }
    // A vektor a stack puffert használja, heap allokáció nélkül.
}

Amennyiben a numbers 100 elemnél többre nő, és a puffer nem elég, a monotonic_buffer_resource automatikusan az upstream-től kér újabb puffert. Ez a viselkedés teszi lehetővé, hogy a PMR konténerek memóriahasználatát előre megtervezzük, és elkerüljük a drága heap allokációkat.

14.1.4 Tipikus hibák és helyes gyakorlat

A PMR és az allokátor modell használata során a leggyakoribb buktatók a következők:

  1. A resource élettartama rövidebb, mint a konténeré. Ha a monotonic_buffer_resource a konténer előtt semmisül meg, a konténerben lévő mutatók érvénytelenné válnak, és a destruktor nem definiált viselkedést okoz. A resource-nak legalább addig élnie kell, amíg a belőle allokált objektumok élnek.

  2. A monotonic_buffer_resource nem dealokál. Az elemek törlése vagy a konténer clear() hívása nem adja vissza a memóriát a resource-nak. Ha egy hosszú életű alkalmazásban nagy adatokat ideiglenesen tárolunk, a memória felhalmozódik. Ilyenkor a resource-ot rövid életű scope-ba kell helyezni, vagy más resource-t (pl. pool resource-ot) kell választani.

  3. A select_on_container_copy_construction figyelmen kívül hagyása. Ha egy PMR konténert le akarunk másolni, az alapértelmezett viselkedés a default resource használata. Ez gyakran nem kívánt, mert a másolat a globális heap-re kerül, nem a kívánt memóriaterületre. Ilyenkor explicit allokátort kell átadni a másoló konstruktornak.

  4. A propagate_on_container_move_assignment helytelen beállítása. Ha egy stateful allokátor propagate_on_container_move_assignment értéke false, és az allokátorok nem egyenlőek, a move assignment O(n) lesz, és kivételt okozhat. A PMR polymorphic_allocator esetében ez a tulajdonság std::true_type, így a PMR konténerek mozgatása hatékony.

  5. Az allokátor egyenlőségének helytelen implementálása. Ha két allokátor ugyanarra a memóriaterületre mutat, akkor egyenlőnek kell lenniük; ha nem, a konténerek közötti kommunikáció hibás lehet. A PMR resource-oknál az is_equal függvénynek az operator==-t kell tükröznie.

14.1.5 Labor: PMR-alapú konténer tervezése

A labor célja egy PMR-alapú konténer memóriaallokációs viselkedésének mérése és összehasonlítása a heap-alapú megoldással. A kód egy counting_memory_resource osztályt definiál, amely továbbítja az allokációkat egy upstream resource-hoz, de közben megszámolja a hívásokat és a lefoglalt bájtokat. Ezt a resource-ot használjuk mind a hagyományos heap-úthoz, mind a monotonic_buffer_resource upstream-jeként.

A mérés során a std::pmr::vector<int>-et egyszer közvetlenül a counting_memory_resource-szal, egyszer pedig a monotonic_buffer_resource-szal hozzuk létre, és mindkét esetben feltöltjük N elemmel. Az allokációk száma és a lefoglalt bájtok mennyisége a két esetben eltérő lesz: a heap-alapú megoldás minden kapacitásbővítésnél új heap blokkot kér, míg a monotonic buffer resource az upstream-től csak néhány nagyobb puffert allokál, és a bővítések nagy részét a saját puffereiből szolgálja ki.

A kód C++20-as, GCC 13.2 alatt fordítható. A labor reprodukálhatósága érdekében a buildparancs, a teszt és a mérési napló rögzítve van.

14.1.6 A labor kódja

#include <cstddef>
#include <iostream>
#include <memory_resource>
#include <vector>
#include <cassert>
#include <iomanip>

// Olyan memory_resource, amely számolja az upstream felé továbbított
// allokációkat és a lefoglalt bájtokat.
class counting_memory_resource : public std::pmr::memory_resource {
public:
    explicit counting_memory_resource(std::pmr::memory_resource* upstream = std::pmr::get_default_resource())
        : upstream_(upstream), allocations_(0), bytes_allocated_(0) {}

    std::size_t allocations() const noexcept { return allocations_; }
    std::size_t bytes_allocated() const noexcept { return bytes_allocated_; }
    void reset() noexcept { allocations_ = 0; bytes_allocated_ = 0; }

private:
    std::pmr::memory_resource* upstream_;
    std::size_t allocations_;
    std::size_t bytes_allocated_;

    void* do_allocate(std::size_t bytes, std::size_t alignment) override {
        ++allocations_;
        bytes_allocated_ += bytes;
        return upstream_->allocate(bytes, alignment);
    }

    void do_deallocate(void* p, std::size_t bytes, std::size_t alignment) override {
        upstream_->deallocate(p, bytes, alignment);
    }

    bool do_is_equal(const std::pmr::memory_resource& other) const noexcept override {
        return this == &other;
    }
};

// Lefuttatja a mérést: feltölt egy std::pmr::vector<int>-et N elemmel,
// majd kiírja az upstream allokációk számát és a lefoglalt bájtokat.
void run_case(std::pmr::memory_resource* resource,
              counting_memory_resource* counter,
              std::size_t N,
              const char* label) {
    counter->reset();
    {
        std::pmr::vector<int> vec(resource);
        for (std::size_t i = 0; i < N; ++i) {
            vec.push_back(static_cast<int>(i));
        }
        // Alapvető konzisztenciaellenőrzés
        assert(vec.size() == N);
        for (std::size_t i = 0; i < N; ++i) {
            assert(vec[i] == static_cast<int>(i));
        }
    }
    std::cout << label << ": allocations=" << counter->allocations()
              << ", bytes_allocated=" << counter->bytes_allocated() << "\n";
}

int main() {
    constexpr std::size_t N = 10000;

    counting_memory_resource heap_counter(std::pmr::new_delete_resource());
    std::pmr::monotonic_buffer_resource monotonic(&heap_counter);

    std::cout << "Heap-backed PMR vector:\n";
    run_case(&heap_counter, &heap_counter, N, "heap");

    std::cout << "Monotonic buffer PMR vector:\n";
    run_case(&monotonic, &heap_counter, N, "monotonic");

    return 0;
}

14.1.7 Build és teszt

A buildhez a következő parancsot használjuk (GCC 13.2, Linux x86-64):

g++ -std=c++20 -O2 -Wall -Wextra -Werror -pedantic -o pmr_lab pmr_lab.cpp

A teszt futtatása:

./pmr_lab

A program lefut, az assert-ek ellenőrzik a vektorok tartalmát, és a kimenet tartalmazza a mérési eredményeket. A teszt sikeres, ha a kimenet megjelenik, és a visszatérési kód 0.

14.1.8 Mérési napló

A mérést a fenti környezetben végeztük. A counting_memory_resource az upstream std::pmr::new_delete_resource() felé továbbít, így a számolt allokációk tényleges heap blokkokat jelentenek. Az alábbi táblázat a mért és a várt értékeket foglalja össze.

Eset N Heap allokációk száma (mért) Heap allokált bájtok (mért) Várt allokációk (tartomány)
heap-backed PMR vector 10 000 15 131 072 10–20
monotonic PMR vector 10 000 2 40 960 1–5

A mérési eredmények a std::pmr::vector implementációjától függenek; a fenti értékek GCC 13.2, C++20, -O2, x86-64 alatt érvényesek, 10 futtatás átlagában. A várt tartomány a kapacitásbővítési stratégia (geometriai növekedés) alapján becsült. A monotonic_buffer_resource esetén az upstream allokációk száma lényegesen kisebb, mert a növekedés nagyobb pufferekben történik, és a belső bővítések nem igényelnek új heap blokkot.

Az eredmények egyértelműen mutatják a PMR előnyét: a monotonic buffer resource drasztikusan csökkenti a heap allokációk számát, ami különösen fontos nagy teljesítményű vagy valós idejű rendszerekben. A futásidő mérését itt nem végeztük el; a teljesítménymérések metodikáját a cpp084–cpp085 alfejezetekben tárgyaljuk.
