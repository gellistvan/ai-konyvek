29.3 Hexagonal architecture és portok/adapters

A hexagonális architektúra – más néven ports and adapters – célja, hogy a rendszer magját, a domain logikát elszigetelje a külső technikai részletektől: adatbázisoktól, hálózati hívásoktól, felhasználói felületektől, fájlrendszertől, üzenetsoroktól. C++-ban ez a szétválasztás nem csupán esztétikai kérdés: a domain kódjának tisztán tartása közvetlen hatással van a tesztelhetőségre, a fordítási időre, a bináris modularitásra és a hosszú távú karbantarthatóságra. A fejezetben bemutatjuk a port, az adapter és a use case fogalmát, megvizsgáljuk a dependency inversion elvét, majd egy reprodukálható labor keretében felépítünk egy kis, ellenőrizhető rendszert.

29.3.1 Miért van szükség a domain és a külső rendszerek szétválasztására?

A klasszikus, rétegzett architektúrákban gyakran a domain réteg közvetlenül hívja az adatbázis-kezelőt, a hálózati klienst vagy a fájlrendszer-API-t. Ez rövid távon kényelmes, de három súlyos következménnyel jár:

  1. Tesztelhetetlenség – a domain logikát csak valódi adatbázissal, hálózattal vagy fájlrendszerrel lehet futtatni, ami lassú, törékeny és nem izolált.
  2. Szoros csatolás – a domain osztályai ismerik a technikai részleteket, így egy adatbázis-séma vagy egy külső API változása a domain kód módosítását kényszeríti ki.
  3. Nehéz párhuzamos fejlesztés – a domain és az infrastruktúra fejlesztése nem választható szét, mert a függőségek iránya a domain felől mutat a technikai réteg felé.

A hexagonális architektúra ezt a függőségi irányt megfordítja: a domain a portokon keresztül kommunikál a külvilággal, és a portokat adapterek valósítják meg. A domain kódja kizárólag a portok absztrakcióját ismeri, a konkrét adaptereket kívülről, általában konstruktor-injektálással kapja meg. Ennek eredményeként a domain logika teljesen izoláltan, gyors, determinisztikus tesztekkel ellenőrizhető, és a külső rendszerek cseréje nem érinti a domain kódját.

C++-ban ez a modell különösen fontos, mert a nyelv lehetővé teszi ugyan a fordítási idejű polimorfizmust (sablonok, CRTP), de a gyakorlatban a domain és az infrastruktúra szétválasztásához futásidejű absztrakcióra – absztrakt osztályokra, interfészekre van szükség. Ez lehetővé teszi, hogy a domain kódja egyetlen fordítási egységben maradjon, míg az adapterek külön könyvtárban vagy modulban implementálhatók, és a teszteléshez más adaptereket linkelünk be.

29.3.2 Port, adapter és use case

A három alapfogalom pontos jelentése:

  • Port – a domain által definiált interfész, amely egy külső képességet ír le. A port lehet bejövő (driving port), amelyen keresztül a külvilág kezdeményez műveletet a domain felé (például egy parancs végrehajtása), vagy kimenő (driven port), amelyen keresztül a domain kezdeményez műveletet a külvilág felé (például adat mentése vagy üzenet küldése). C++-ban egy port jellemzően egy absztrakt osztály, amely csak tisztán virtuális függvényeket tartalmaz, és virtuális destruktorral rendelkezik.
  • Adapter – a port konkrét implementációja, amely a külső rendszerhez kapcsolódik. Az adapter lehet elsődleges (primary adapter), amely a bejövő portot használja, például egy REST API vagy CLI parancs, és lehet másodlagos (secondary adapter), amely a kimenő portot valósítja meg, például egy SQL repository vagy egy HTTP kliens.
  • Use case – a domain szolgáltatás vagy alkalmazásszolgáltatás, amely a portokon keresztül hajt végre egy üzleti műveletet. A use case nem ismeri az adapterek konkrét típusát, csak a port interfészt, és a szükséges adaptereket referenciaként vagy pointerként kapja meg.

Egy egyszerű, de reprezentatív példa: képzeljünk el egy hőmérséklet-figyelő rendszert, amely egy szenzortól olvas értéket, és ha az meghalad egy küszöböt, riasztást küld. A domain logika – a küszöb ellenőrzése – nem függhet attól, hogy a szenzor valódi hardver, szimulált eszköz vagy tesztadat, és a riasztás sem függhet attól, hogy konzolra, fájlba vagy hálózati üzenetbe írjuk. A portok definiálják a szükséges műveleteket, az adapterek pedig megvalósítják azokat.

Az alábbi kód egy C++20 alapú, minimalista portdefiníciót mutat be:

// domain/ports.h
#pragma once
#include <optional>
#include <string>

// Kimenő port: hőmérséklet-szenzor olvasása
class TemperatureSensorPort {
public:
    virtual ~TemperatureSensorPort() = default;
    // Visszaadja a mért hőmérsékletet Celsiusban, ha elérhető.
    virtual std::optional<double> read() = 0;
};

// Kimenő port: riasztás küldése
class AlertPort {
public:
    virtual ~AlertPort() = default;
    virtual void send(std::string_view message) = 0;
};

A TemperatureSensorPort::read() std::optional<double>-t ad vissza, mert a szenzor időnként nem tud értéket szolgáltatni – ez a port szerződésének része, és a domain kód ennek megfelelően kezeli a hiányzó értéket. Az AlertPort::send() std::string_view paramétert fogad, ami lehetővé teszi, hogy az adapter döntse el, hogyan tárolja vagy továbbítja a szöveget.

A use case ezeket a portokat használja:

// domain/temperature_monitor.h
#pragma once
#include "ports.h"

class TemperatureMonitor {
public:
    TemperatureMonitor(TemperatureSensorPort& sensor,
                       AlertPort& alert,
                       double threshold)
        : sensor_(sensor), alert_(alert), threshold_(threshold) {}

    // Egyetlen ellenőrzési ciklus végrehajtása.
    void check();

private:
    TemperatureSensorPort& sensor_;
    AlertPort& alert_;
    double threshold_;
};

A konstruktor referencia-paramétereket vár, ami garantálja, hogy a use case nem birtokolja az adaptereket, és azok élettartamát a hívó fél kezeli. Ez a dependency injection legegyszerűbb formája: a függőségeket kívülről adjuk át, ahelyett hogy a use case maga hozná létre azokat. A referencia használata jelzi, hogy a függőség kötelező, és az objektum nem lehet üres.

A check() implementációja:

// domain/temperature_monitor.cpp
#include "temperature_monitor.h"
#include <string>

void TemperatureMonitor::check() {
    auto temp = sensor_.read();
    if (temp && *temp > threshold_) {
        alert_.send("Temperature exceeds threshold: " + std::to_string(*temp));
    }
}

Ez a kód kizárólag a port interfészekre támaszkodik, semmilyen konkrét szenzort vagy riasztási mechanizmust nem ismer. Ez a domain és a külső rendszerek szétválasztásának lényege.

Az adapterek most már külön fordítási egységben implementálhatók. Például egy teszteléshez használt, memóriában működő szenzor és egy vektorba gyűjtő riasztás:

// adapters/stub_sensor.h
#pragma once
#include "domain/ports.h"
#include <optional>

class StubSensor : public TemperatureSensorPort {
public:
    explicit StubSensor(std::optional<double> value) : value_(value) {}
    std::optional<double> read() override { return value_; }
private:
    std::optional<double> value_;
};
// adapters/vector_alert.h
#pragma once
#include "domain/ports.h"
#include <string>
#include <vector>

class VectorAlert : public AlertPort {
public:
    void send(std::string_view message) override {
        messages_.emplace_back(message);
    }
    const std::vector<std::string>& messages() const { return messages_; }
private:
    std::vector<std::string> messages_;
};

Ezek az adapterek a tesztkörnyezetben gyorsan és determinisztikusan futnak, nincs szükség valódi hardverre vagy hálózatra. A termelési környezethez tartozó adapterek – például egy SqlSensorRepository, amely egy adatbázisból olvas, vagy egy NetworkAlert, amely HTTP-kérést küld – ugyanezt a port interfészt valósítják meg, így a domain kód változtatás nélkül cserélhet közöttük.

A bejövő port fogalma is fontos: ez az az interfész, amelyen keresztül a külvilág vezérli a domaint. A fenti példában a bejövő port maga a TemperatureMonitor osztály publikus felülete (check() metódus), de nagyobb rendszerekben ezt gyakran külön interfészként definiálják, hogy a vezérlő adapterek (például egy HTTP handler vagy egy parancssori argumentum-feldolgozó) csak ezt az absztrakciót ismerjék. C++-ban ez jellemzően egy absztrakt osztály:

// domain/temperature_monitor_port.h
#pragma once
#include "domain/ports.h"

class TemperatureMonitorPort {
public:
    virtual ~TemperatureMonitorPort() = default;
    virtual void check() = 0;
};

A TemperatureMonitor ekkor ezt az interfészt implementálja, és a bejövő adapter ezen keresztül hívja a use case-t. Ez tovább növeli a modularitást, mert a felsőbb rétegek nem ismerik a konkrét use case típust.

29.3.3 Dependency inversion és a függőségi irány

A hexagonális architektúra szíve a dependency inversion principle (DIP): a magas szintű modulok (domain) nem függhetnek az alacsony szintű moduloktól (infrastruktúra), hanem mindkettőnek az absztrakcióktól (portok) kell függenie. C++-ban ezt úgy valósítjuk meg, hogy a domain kód csak a port interfészeket tartalmazza a fejlécében, és a konkrét adaptereket a hívó fél (például a main() függvény vagy egy kompozíciós gyökér) hozza létre, majd injektálja a use case-be.

A függőségi gráf ekkor így néz ki:

main (kompozíciós gyökér)
   |--> domain (TemperatureMonitor)
   |        `--> domain::ports (TemperatureSensorPort, AlertPort)
   |--> adapters (StubSensor, VectorAlert)
   |        `--> domain::ports
   `--> domain::ports

Figyeljük meg, hogy a domain és az adapters könyvtárak egyaránt a domain::ports fejlécekre támaszkodnak, de a domain nem ismeri az adapters-t. Ez a kulcs: a domain fordításakor nem szükséges az adapterek forráskódja, és a teszteléshez más adaptereket linkelhetünk anélkül, hogy a domain kódját újra kellene fordítani.

A bináris szintű szétválasztás C++-ban különösen előnyös, mert a build rendszer (CMake, Bazel) a domain könyvtárat önálló statikus vagy dinamikus könyvtárként fordíthatja, és az adapterek külön modulokban élnek. Ez csökkenti a fordítási időt és lehetővé teszi a párhuzamos fejlesztést. A port interfészek virtuális függvényei miatt a hívások egy indirekción keresztül történnek, ami némi futásidejű költséggel jár, de ez a gyakorlatban a legtöbb alkalmazásban elhanyagolható, és bőven kompenzálja a tesztelhetőség és a modularitás nyeresége. Ahol a teljesítmény kritikus, és a hívások száma nagyon magas, ott megfontolható a sablon alapú, fordítási idejű polimorfizmus (policy-based design), de az a domain és az adapterek fordítási időben történő összekapcsolását igényli, ami ellentétes a hexagonális architektúra futásidejű cserélhetőségével. A két megközelítés közötti választás mérnöki döntés, amelyet a fejezet későbbi részében a labor mérési eredményei is alátámaszthatnak.

29.3.4 Tesztelhetőség és a fake adapterek szerepe

A hexagonális architektúra egyik legnagyobb előnye a kiváló tesztelhetőség. Mivel a domain logika csak a portoktól függ, a tesztekben fake vagy mock adaptereket használhatunk, amelyek memóriában futnak, és pontosan szabályozhatók. A fake adapterek nem igényelnek hálózatot, adatbázist vagy fájlrendszert, így a tesztek determinisztikusak, gyorsak és párhuzamosíthatók.

A fenti példához tartozó teszt:

// tests/test_temperature_monitor.cpp
#include "domain/temperature_monitor.h"
#include "adapters/stub_sensor.h"
#include "adapters/vector_alert.h"
#include <cassert>
#include <string>

void test_no_alert_when_below_threshold() {
    StubSensor sensor(25.5);
    VectorAlert alert;
    TemperatureMonitor monitor(sensor, alert, 30.0);
    monitor.check();
    assert(alert.messages().empty());
}

void test_alert_when_above_threshold() {
    StubSensor sensor(35.0);
    VectorAlert alert;
    TemperatureMonitor monitor(sensor, alert, 30.0);
    monitor.check();
    assert(alert.messages().size() == 1);
    assert(alert.messages()[0] == "Temperature exceeds threshold: 35.000000");
}

int main() {
    test_no_alert_when_below_threshold();
    test_alert_when_above_threshold();
    return 0;
}

A teszt közvetlenül a domain és az adapterek fejléceire épül, és nem tartalmaz semmilyen külső hívást. A StubSensor mindig ugyanazt az értéket adja vissza, a VectorAlert pedig eltárolja a kiküldött üzeneteket, így pontosan ellenőrizhető a use case viselkedése. Valós projektben ezt általában egy tesztkeretrendszerrel (Catch2, GoogleTest, doctest) szervezzük, de itt a assert is elegendő a koncepció bemutatására.

A tesztelhetőség tovább fokozható azáltal, hogy a port interfészeket úgy tervezzük, hogy az adapterek állapota könnyen ellenőrizhető legyen – mint a VectorAlert::messages() metódus. Egy jól megtervezett port nem szivárogtat technikai részleteket; a tesztnek csak a domain szempontjából releváns műveleteket kell látnia.

Fontos megjegyezni, hogy a port interfészek ne legyenek túl szélesek. Ha egy port tíz virtuális függvényt tartalmaz, akkor minden adapternek mind a tízet implementálnia kell, még akkor is, ha csak kettőt használ. Ez a interface segregation principle (ISP) megsértése, és a tesztelés során felesleges boilerplate kódhoz vezet. A hexagonális architektúrában a portokat inkább kicsin, fókuszáltan érdemes definiálni, akár egy-egy műveletre.

29.3.5 Tipikus hibák és elkerülésük

A hexagonális architektúra bevezetése során a következő gyakori hibákat érdemes elkerülni:

  1. A domain közvetlenül hívja az adaptert – ha a use case #include-ol egy konkrét adapter fejlécét, vagy new-val példányosítja, akkor a függőségi irány megfordul, és elveszik a tesztelhetőség. A domain kódjában soha ne szerepeljen konkrét adapter típus.
  2. A port túl széles vagy technikai részleteket szivárogtat – a portoknak a domain nyelvén kell beszélniük, nem pedig az infrastruktúra fogalmaival. Például egy repository port save(const Entity&) metódusa helyes, de executeSql(const std::string&) már technikai részlet, és sérti az absztrakciót.
  3. A use case nem kezeli a portok hibáit vagy hiányzó értékeit – a portok szerződésének explicitnek kell lennie (pl. std::optional, std::expected visszatérés), és a domain kódnak minden lehetséges kimenetet kezelnie kell. A fenti példában a read() std::optional-t ad vissza, és a use case ellenőrzi a jelenlétet.
  4. A kompozíciós gyökér hiánya – ha az adapterek létrehozása és injektálása szétszóródik a kódban, akkor nehéz átlátni a függőségeket. Érdemes egyetlen helyen, például a main()-ben vagy egy gyártófüggvényben összeállítani az objektumgráfot.
  5. A port interfész nem rendelkezik virtuális destruktorral – ez undefined behaviorhez vezethet, ha az adaptert a port pointerén keresztül töröljük. Mindig adjunk virtual ~Port() = default; destruktort.
  6. A teszt valódi adaptert használ – ha a teszt például egy valódi adatbázishoz csatlakozik, akkor a teszt lassú és törékeny lesz. A unit tesztekben kizárólag fake adaptereket használjunk; az integrációs tesztek külön környezetben futhatnak valódi adapterekkel, de ott is izoláltan.

A fenti hibák felismerése és a helyes megoldás indoklása a fejezet egyik fő tanulási célja. A labor során a hallgató saját maga építi fel a vázat, így közvetlenül tapasztalja meg a függőségi irány és a tesztelhetőség kapcsolatát.

29.3.6 Labor: port- és adapter-vázlat készítése

A labor célja, hogy a fejezetben bemutatott fogalmakat egy reprodukálható buildben és tesztkörnyezetben alkalmazzuk. A feladat egy port- és adapter-vázlat elkészítése egy adott domainhez, majd annak lefordítása, tesztelése és mérése.

29.3.7 Feladatleírás

Készítsünk egy egyszerű inventory (készletnyilvántartó) rendszer vázát. A domain egy InventoryService use case, amely két kimenő portot használ:

  • ItemRepositoryPort – termékek keresése és készlet frissítése.
  • AuditLogPort – naplózás minden módosításról.

A use case egyetlen művelete: void updateStock(const std::string& itemId, int delta). A művelet megkeresi a terméket a repository-ban, ellenőrzi, hogy a készlet nem csökken nulla alá, frissíti a készletet, és naplózza a változást. A portok szerződése a következő:

  • ItemRepositoryPort:
    • std::optional<Item> find(const std::string& id) – visszaadja a terméket, ha létezik.
    • void save(const Item& item) – elmenti a termék aktuális állapotát.
  • AuditLogPort:
    • void log(std::string_view entry) – bejegyzést ír a naplóba.

Az Item egy egyszerű érték típus id és quantity mezőkkel.

A hallgató feladata:

  1. Definiálja a port interfészeket (ports.h).
  2. Implementálja az InventoryService use case-t.
  3. Készítsen két adaptert: egy in-memory repository-t (InMemoryItemRepository) és egy vektor alapú naplót (VectorAuditLog).
  4. Írjon unit tesztet, amely ellenőrzi a helyes viselkedést (sikeres frissítés, nem létező termék, negatív készlet).
  5. Állítson össze egy CMake buildet, amely a domain-t könyvtárként, az adaptereket külön statikus könyvtárként, a tesztet futtathatóként építi.
  6. Futtassa a tesztet sanitizerekkel (-fsanitize=address,undefined) és -Wall -Wextra -Werror kapcsolókkal.
  7. Mérje meg a fordítási időt, a teszt futási idejét és a bináris méretét, és rögzítse egy mérési naplóban.

29.3.8 Kiinduló kódváz

Az alábbiakban megadjuk a portok és a use case vázát, hogy a hallgató a lényegre koncentrálhasson. A teljes megoldást a labor jegyzőkönyv tartalmazza.

// domain/ports.h
#pragma once
#include <optional>
#include <string>

struct Item {
    std::string id;
    int quantity;
};

class ItemRepositoryPort {
public:
    virtual ~ItemRepositoryPort() = default;
    virtual std::optional<Item> find(const std::string& id) = 0;
    virtual void save(const Item& item) = 0;
};

class AuditLogPort {
public:
    virtual ~AuditLogPort() = default;
    virtual void log(std::string_view entry) = 0;
};
// domain/inventory_service.h
#pragma once
#include "ports.h"
#include <string>

class InventoryService {
public:
    InventoryService(ItemRepositoryPort& repo, AuditLogPort& audit)
        : repo_(repo), audit_(audit) {}

    // Frissíti a termék készletét. Ha a termék nem létezik, vagy a
    // művelet negatív készletet eredményezne, nem történik módosítás,
    // és a hiba naplózásra kerül.
    void updateStock(const std::string& itemId, int delta);

private:
    ItemRepositoryPort& repo_;
    AuditLogPort& audit_;
};

A updateStock implementációja:

// domain/inventory_service.cpp
#include "inventory_service.h"
#include <string>

void InventoryService::updateStock(const std::string& itemId, int delta) {
    auto item = repo_.find(itemId);
    if (!item) {
        audit_.log("Item not found: " + itemId);
        return;
    }
    if (item->quantity + delta < 0) {
        audit_.log("Insufficient stock for item: " + itemId);
        return;
    }
    item->quantity += delta;
    repo_.save(*item);
    audit_.log("Stock updated for item: " + itemId + ", new quantity: " +
               std::to_string(item->quantity));
}

Az adapterek:

// adapters/in_memory_repo.h
#pragma once
#include "domain/ports.h"
#include <map>
#include <optional>
#include <string>

class InMemoryItemRepository : public ItemRepositoryPort {
public:
    std::optional<Item> find(const std::string& id) override {
        auto it = items_.find(id);
        if (it == items_.end()) return std::nullopt;
        return it->second;
    }
    void save(const Item& item) override {
        items_[item.id] = item;
    }
private:
    std::map<std::string, Item> items_;
};
// adapters/vector_audit_log.h
#pragma once
#include "domain/ports.h"
#include <string>
#include <vector>

class VectorAuditLog : public AuditLogPort {
public:
    void log(std::string_view entry) override {
        entries_.emplace_back(entry);
    }
    const std::vector<std::string>& entries() const { return entries_; }
private:
    std::vector<std::string> entries_;
};

A teszt:

// tests/test_inventory_service.cpp
#include "domain/inventory_service.h"
#include "adapters/in_memory_repo.h"
#include "adapters/vector_audit_log.h"
#include <cassert>
#include <string>

void test_successful_update() {
    InMemoryItemRepository repo;
    VectorAuditLog audit;
    InventoryService service(repo, audit);

    // Kezdeti feltöltés
    repo.save(Item{"apple", 10});
    service.updateStock("apple", 5);
    auto item = repo.find("apple");
    assert(item && item->quantity == 15);
    assert(audit.entries().size() == 1);
    assert(audit.entries()[0].find("new quantity: 15") != std::string::npos);
}

void test_item_not_found() {
    InMemoryItemRepository repo;
    VectorAuditLog audit;
    InventoryService service(repo, audit);

    service.updateStock("missing", 1);
    assert(!repo.find("missing"));
    assert(audit.entries().size() == 1);
    assert(audit.entries()[0] == "Item not found: missing");
}

void test_insufficient_stock() {
    InMemoryItemRepository repo;
    VectorAuditLog audit;
    InventoryService service(repo, audit);

    repo.save(Item{"apple", 3});
    service.updateStock("apple", -5);
    auto item = repo.find("apple");
    assert(item && item->quantity == 3); // változatlan
    assert(audit.entries().size() == 1);
    assert(audit.entries()[0] == "Insufficient stock for item: apple");
}

int main() {
    test_successful_update();
    test_item_not_found();
    test_insufficient_stock();
    return 0;
}

29.3.11 Önellenőrző kérdések

  1. Mi a különbség a port és az adapter között? Adj példát mindkettőre a fenti inventory rendszerben.
  2. Hogyan valósul meg a dependency inversion a bemutatott kódban? Miért nem függ a InventoryService a konkrét repository-tól?
  3. Milyen hibához vezet, ha a port interfész nem rendelkezik virtuális destruktorral? Miért kötelező a virtual ~Port() = default;?
  4. Miért előnyös a fake adapter a valódi adapterrel szemben a unit tesztben? Milyen esetben használnánk valódi adaptert?
  5. A laborban miért választottuk a std::optional visszatérést a find metódusban? Hogyan kezeli a use case a hiányzó értéket?

A kérdésekre adott válaszoknak tükrözniük kell a fejezetben tárgyalt fogalmakat, és a hallgatónak képesnek kell lennie megindokolni a tervezési döntéseket. A labor sikeres elvégzése és a mérési napló kitöltése bizonyítja a tanulási célok elsajátítását.

29.3.12 Összefoglalás

A hexagonális architektúra C++-ban is hatékonyan megvalósítható absztrakt osztályokkal és konstruktor-injektálással. A domain logika portokon keresztül kommunikál a külvilággal, az adapterek pedig ezeket a portokat valósítják meg. Ez a szétválasztás tesztelhető, moduláris és karbantartható kódot eredményez, és lehetővé teszi a külső rendszerek cseréjét a domain érintése nélkül. A labor során felépített inventory váz demonstrálja a fogalmakat, a mérési napló pedig biztosítja a reprodukálhatóságot és a teljesítményjellemzők nyomon követését. A következő fejezet (29.4) erre az alapra építve tárgyalja a modularitás és a deployment kérdéseit.
