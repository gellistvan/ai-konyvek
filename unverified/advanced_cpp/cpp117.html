30.4 C, Python, JavaScript, Rust és WASM interop

30.4.1 Bevezetés és tanulási célok

Ez a fejezet a C++ és más nyelvek közötti együttműködés gyakorlati rétegét tárgyalja. A cél nem egy adott keretrendszer teljes dokumentációja, hanem azoknak a döntéseknek a megértése, amelyek a nyelvhatáron hozott ABI-, ownership- és hibakezelési választásokat meghatározzák. A fejezet elvégzése után képes leszel:

  • megmagyarázni, miért a C ABI a leggyakoribb közös nevező az FFI-ben;
  • megkülönböztetni a extern "C", a pybind11, az embind és a cxx rétegeit;
  • ő ownership-modellt választani C++, Python, JavaScript/WASM és Rust határán;
  • tipikus hibákat felismerni: C++ kivétel átengedése C határon, dupla felszabadítás, GIL megsértése, platformfüggő struct layout;
  • reprodukálható interop- és FFI-tervet készíteni, mérési naplóval.

A kódpéldák szemléltetők; a külső eszközök (pybind11, Emscripten/embind, cxx) pontos verzióját és API-ját minden buildben rögzíteni kell. Ahol az API gyorsan változhat – különösen az embind és a cxx esetében –, ott a hivatalos, az adott verzióhoz tartozó dokumentáció ellenőrzése kötelező, és ezt a szöveg is jelöli.

30.4.2 Az FFI réteg és az ABI szerepe

Az idegen nyelvi interfész (foreign function interface, FFI) lényege, hogy a hívó és a hívott fél közös bináris szerződést köt. Ez a szerződés nem C++ forrásszintű: a legtöbb rendszer a C ABI-t használja közös nevezőként, mert a C hívási konvenció, a primitív típusok és a mutatók szinte minden platformon stabilan definiáltak. A C++ ABI ezzel szemben fordítónként és platformonként eltérhet, például a névdekoráció, az osztálylayout, a kivételkezelés és a std::unique_ptr reprezentációja. Ezért a más nyelvekkel való együttműködés első lépése általában egy C-stílusú, extern "C" határfelület kialakítása.

A C ABI azonban nem hordoz gazdag típusinformációt. A hívó és a hívott fél közötti szerződést a következők határozzák meg:

  • a függvény pontos deklarációja (visszatérési típus, paraméterek sorrendje);
  • a mutatók mögötti memória tulajdonosa;
  • az élettartam-szabályok (ki hívja a felszabadítást);
  • a hibakezelés módja (return code, out paraméter, esetleg errno);
  • a szálbiztonsági garanciák.

Ha bármelyik elem nincs egyértelműen dokumentálva, a határfelület bizonytalan, és a hiba gyakran csak futásidőben, memóriasérülésként jelentkezik. A modern C++ interop-eszközök – pybind11, embind, cxx – ebből a szempontból magasabb szintű réteget adnak: a felhasználó C++ típusokat, osztályokat és kivételeket használ, a generált „ragasztó” kód pedig elvégzi a C ABI-ra fordítás, az ownership-nyilvántartás és a hibakonverzió nagy részét.

30.4.3 C-vel való együttműködés: extern "C" és opaque pointer

A legalacsonyabb szintű, de legstabilabb interop-minta a C API-val ellátott C++ könyvtár. A határfelület csak C típusokat és mutatókat használ, a C++ osztályt pedig egy átlátszatlan (void*) pointer mögé rejti.

// counter_api.h – C API deklaráció
#if defined(_WIN32) && defined(COUNTER_BUILD)
  #define COUNTER_API __declspec(dllexport)
#elif defined(_WIN32)
  #define COUNTER_API __declspec(dllimport)
#else
  #define COUNTER_API __attribute__((visibility("default")))
#endif

#include <stdint.h>

#ifdef __cplusplus
extern "C" {
#endif

COUNTER_API void* counter_create(int64_t initial);
COUNTER_API void  counter_destroy(void* handle);
COUNTER_API int32_t counter_increment(void* handle, int64_t delta, int64_t* out_value);

#ifdef __cplusplus
}
#endif

A void* paramétert hívó oldalról nem szabad értelmezni, és a megvalósítás sem adhatja át más típusként. A C++ implementáció az osztályt a counter_create-ben new operátorral hozza létre, és a counter_destroy hívja a delete-et:

// counter_impl.cc
#include "counter_api.h"
#include <stdexcept>
#include <new>

class Counter {
public:
    explicit Counter(std::int64_t initial) : value_{initial} {}
    std::int64_t increment(std::int64_t delta) {
        if (delta < 0)
            throw std::invalid_argument("delta must be non-negative");
        value_ += delta;
        return value_;
    }
private:
    std::int64_t value_;
};

extern "C" COUNTER_API void* counter_create(int64_t initial) {
    try {
        return new Counter(initial);
    } catch (...) {
        return nullptr; // a C hívó nem láthat C++ kivételt
    }
}

extern "C" COUNTER_API void counter_destroy(void* handle) {
    delete static_cast<Counter*>(handle);
}

extern "C" COUNTER_API int32_t counter_increment(void* handle, int64_t delta, int64_t* out_value) {
    if (!handle || !out_value) return -1;
    try {
        auto* counter = static_cast<Counter*>(handle);
        *out_value = counter->increment(delta);
        return 0;
    } catch (const std::invalid_argument&) {
        return -2;
    } catch (...) {
        return -1;
    }
}

A hibakezelés itt return kódokkal történik. C++ kivétel nem lépheti át a extern "C" határt; a szabvány szerint, ha egy C nyelvi kötésű függvény C++ kivétellel lép ki, a viselkedés nem definiált. Ezért a C API függvényeiben minden kivételt el kell kapni, és a hibát kóddal vagy out-paraméterrel kell jelezni.

Az ownership egyértelmű: a hívó a counter_create által kapott mutatót csak a counter_destroy-nak adhatja át, pontosan egyszer. A mutató dupla felszabadítása vagy a delete elmulasztása memóriahibához vezet. A C++ oldalon a Counter belső állapotát a C API nem látja, ezért az osztály belső elrendezése megváltoztatható anélkül, hogy a hívó újrafordulna; ez a bináris kompatibilitás egyik alapfeltétele.

30.4.4 Python: pybind11 és a GIL

A Python-nal való együttműködés leggyakoribb modern eszköze a pybind11. A pybind11 header-only, C++11/14/17/20-kompatibilis, és a Python C API fölé épít. A C++ osztályt, függvényt, operátort, std::vector-t, std::map-et, std::span-t (C++20-tól) közvetlenül regisztrálhatjuk. A pybind11 kezeli a Python és C++ típusok közötti konverziót, a C++ kivételeket Python kivételekké alakítja, és automatikusan nyilvántartja az objektumok tulajdonjogát.

#include <pybind11/pybind11.h>
#include <pybind11/stl.h>      // std::vector konverzió (opcionális)

class Counter {
public:
    explicit Counter(std::int64_t initial) : value_{initial} {}
    std::int64_t increment(std::int64_t delta) {
        if (delta < 0)
            throw std::invalid_argument("delta must be non-negative");
        value_ += delta;
        return value_;
    }
private:
    std::int64_t value_;
};

PYBIND11_MODULE(counter, m) {
    namespace py = pybind11;
    py::class_<Counter>(m, "Counter")
        .def(py::init<std::int64_t>())
        .def("increment", &Counter::increment);
}

A PYBIND11_MODULE makró létrehozza a Python modul inicializáló függvényét. A py::class_ regisztrálja a Counter osztály metódusait. A py::init<std::int64_t>() a konstruktort köti be; a Python oldalon Counter(42) hozza létre az objektumot, és a Python szemétgyűjtő fogja meghívni a C++ destruktort, amikor az objektum már nem kell.

A pybind11 kivételfordítása automatikus: a std::invalid_argument Python ValueError lesz. A C++ kivétel nem lép ki a modulból, mert a generált kód elkapja és a Python C API PyErr_SetString függvényét hívja. A Python oldalon a hívás normál kivételként jelenik meg.

A legfontosabb Python-specifikus szempont a globális interpreterzár (Global Interpreter Lock, GIL). Amikor egy Python-kötésű C++ függvény fut, a GIL általában tartva van. Ez garantálja, hogy a Python objektumokhoz való hozzáférés szálbiztos, de azt is jelenti, hogy egy hosszú, számításigényes C++ függvény blokkolja a többi Python-szálat. Ilyenkor a C++ oldalon ideiglenesen el kell engedni a GIL-t:

std::int64_t compute_heavy(std::int64_t n) {
    py::gil_scoped_release release; // GIL elengedése a számítás idejére
    std::int64_t result = 0;
    for (std::int64_t i = 0; i < n; ++i)
        result += i % 17;
    return result;
}

A py::gil_scoped_release élettartama alatt a C++ kód nem nyúlhat Python objektumokhoz. Ha mégis Python API-t hív, az határozatlan viselkedéshez vagy holtponthoz vezethet. A függvény visszatérése után a GIL automatikusan visszavételre kerül.

A pybind11 buildelése CMake-ben a pybind11_add_module paranccsal történik:

find_package(pybind11 REQUIRED)
pybind11_add_module(counter counter.cpp)

A modul betöltése Pythonban egyszerű:

import counter
c = counter.Counter(10)
assert c.increment(5) == 15

A pybind11 által nyújtott ownership-lehetőségek közül a leggyakoribb:

  • egyedi C++ objektum Python-birtoklásban (alapértelmezett a py::class_ esetén);
  • C++ oldalon tárolt std::unique_ptr átadása Pythonnak, ahol a Python nem birtokolja a mutatót (py::return_value_policy::reference);
  • Python objektum átadása C++ std::shared_ptr-nek, ami megosztott birtoklást eredményez.

Ha a C++ oldal egy Counter objektumra mutató raw pointert ad vissza, és a Python oldal is birtokolni akarja, akkor a tulajdonjogot explicit módon kell megadni. A pybind11 dokumentációja részletesen tárgyalja a return value policy lehetőségeit; az aktuális verzióhoz tartozó leírást mindig ellenőrizni kell.

30.4.5 JavaScript és WASM: embind

A WebAssembly (WASM) a C++ kódot egy homokozóban futtatja a JavaScript-motor mellett. Az Emscripten eszközlánc a C++ kódból WASM modult és JavaScript „ragasztó” kódot generál. A natív C ABI itt nem közvetlenül érhető el: a JavaScript oldal a WASM lineáris memóriáját és az exportált függvényeket látja. Az Emscripten embind rétege magasabb szintű C++-osztályokat, függvényeket, std::string-et, std::vector-t és std::map-et tesz elérhetővé JavaScriptből.

#include <emscripten/bind.h>
#include <stdexcept>

class Counter {
public:
    explicit Counter(std::int64_t initial) : value_{initial} {}
    std::int64_t increment(std::int64_t delta) {
        if (delta < 0)
            throw std::invalid_argument("delta must be non-negative");
        value_ += delta;
        return value_;
    }
private:
    std::int64_t value_;
};

EMSCRIPTEN_BINDINGS(counter) {
    emscripten::class_<Counter>("Counter")
        .constructor<std::int64_t>()
        .function("increment", &Counter::increment);
}

A build parancs (Emscripten 3.1.x, verziótól függően):

emcc --bind -std=c++20 counter.cpp -o counter.js

A JavaScript oldal:

const Module = require('./counter.js');
Module.onRuntimeInitialized = () => {
    const c = new Module.Counter(10);
    console.log(c.increment(5)); // 15
};

Az embind a JavaScript szemétgyűjtővel együttműködve kezeli a C++ objektumok birtoklását. Amikor a JavaScript Counter objektumra nincs több referencia, a generált kód meghívja a C++ destruktort. Ez hasonló a pybind11 modellhez, de itt a szemétgyűjtő ütemezése nem determinisztikus; a destruktor nem feltétlenül akkor fut, amikor a JavaScript változó kikerül a hatókörből. Ha a C++ objektum erőforrást tart nyitva (például fájlleírót), a JavaScript oldalon explicit delete() metódust kell hívni, vagy a C++ oldalon egy std::shared_ptr-t kell használni, hogy az életciklus egyértelmű legyen.

A C++ kivételeket az embind is elkapja, és JavaScript kivétellé alakítja. A fenti std::invalid_argument a JavaScript oldalon Error-ként jelenik meg. Fontos azonban, hogy a WASM modul és a JavaScript futási modellje eltér a natív környezettől: a WASM-ben nincs operációs rendszer által biztosított szál, a szálak megvalósítása (Web Workers, SharedArrayBuffer) külön konfigurációt igényel. Az embind nem szálbiztos alapértelmezés szerint; ha a C++ kód több Web Worker-ből is elérhető, az adatversenyhez vezethet.

A WASM interop egyik fő kihívása a memória átadása. A JavaScript oldal a WASM lineáris memóriájához Uint8Array nézeteken keresztül férhet hozzá. Az embind által generált string- és vektorátadás másolatot készít, ezért nagy adatoknál a teljesítmény kritikus lehet. Ilyenkor érdemes közvetlenül a memóriapufferen dolgozni, és a C++ oldalon std::span-t vagy nyers mutatót használni. Az Emscripten emscripten::val típusa lehetővé teszi a JavaScript objektumok elérését C++ oldalról, de ez már a magasabb szintű „embind val” réteghez tartozik, és a hívások iránya megfordul: C++ hív JavaScriptet.

30.4.6 Rust: cxx és a biztonságos híd

A Rust és C++ közötti együttműködés egyik modern eszköze a cxx crate. A cxx nem puszta C ABI: a #[cxx::bridge] makró egy deklaratív hidat generál, amely a C++ és Rust típusokat statikusan ellenőrzi, és a generált kód C ABI-t használ a két nyelv között, de a felhasználó elől elrejti a mutatók és a memóriakezelés részleteit.

A cxx egyik iránya: Rust oldali típusokat hívunk C++-ból. A #[cxx::bridge] modulban deklaráljuk a Rust típust és a függvényeket, a cxxbuild pedig legenerálja a C++ fejlécet (lib.rs.h).

Rust oldal (src/lib.rs):

#[cxx::bridge]
mod ffi {
    extern "Rust" {
        type Counter;
        fn create(initial: i64) -> Box<Counter>;
        fn increment(self: &mut Counter, delta: i64) -> i64;
    }
}

pub struct Counter {
    value: i64,
}

pub fn create(initial: i64) -> Box<Counter> {
    Box::new(Counter { value: initial })
}

pub fn increment(&mut self, delta: i64) -> i64 {
    if delta < 0 {
        panic!("delta must be non-negative");
    }
    self.value += delta;
    self.value
}

A C++ oldal (src/main.cc):

#include "counter/src/lib.rs.h"

int main() {
    rust::Box<ffi::Counter> counter = ffi::create(42);
    std::int64_t value = ffi::increment(*counter, 10);
    return value == 52 ? 0 : 1;
}

A cxxbridge a Rust Box<Counter>-et C++ oldalon rust::Box<ffi::Counter>-ként jeleníti meg. A rust::Box a cxx runtime osztálya, amely a Rust tulajdonjogot C++-ban is érvényesíti: a C++ oldal birtokolja a Rust objektumot, és amikor a rust::Box destruktora lefut, a Rust oldali drop hívódik meg. Ez kiküszöböli a dupla felszabadítás és a memóriaszivárgás egy részét, mert a tulajdonjog statikusan ellenőrzött.

A hibakezelés a cxx-ben eltér a C++ és a Python modelltől. A Rust panic! nem lépheti át a határt; a cxx által generált C ABI függvényekben a Rust oldali panic a folyamat leállítását vagy nem definiált viselkedést okozhat, hacsak a Rust oldal nem használ catch_unwind-ot. A cxx a hibák átadására a Rust Result típust és a C++ oldalon rust::Result-et használja. A bridge-ben a extern "Rust" blokkban Result<T, E> visszatérési értéket deklarálhatunk, ahol E egy cxx által támogatott hibatípus (például cxx::Exception vagy egy saját Rust típus, ha az implementálja a cxx::ExternType interfészt). A pontos API a crate verziójától függ, ezért a felhasznált cxx verzióhoz tartozó dokumentációt mindig ellenőrizni kell.

A cxx a C++ oldali kivételeket sem engedi át a Rust oldalra. Ha a C++ függvény throw-t dob, a cxx generált kódja elkapja és a Rust oldali catch_unwind-ba csomagolja, de ez nem garantált minden verzióban; a biztonságos megoldás a C++ oldalon is hibakód vagy std::expected (C++23) használata a határfelületen. A cxx a C++ típusok Rust oldali reprezentációját is kontrollálja: a std::string rust::String-ként, a std::vector<T> rust::Vec<T>-ként jelenik meg, a std::unique_ptr<T> rust::UniquePtr<T>-ként.

A cxx buildje a Cargo build.rs-ében konfigurálható:

// build.rs
fn main() {
    cxx_build::bridge("src/lib.rs")
        .file("src/main.cc")
        .std("c++20")
        .compile("counter_bridge");
}

A C++ oldal fordításához a cxx crate generál egy lib.rs.h fejlécet, amelyet a C++ forrásban be kell illeszteni. A teljes buildhez Cargo és egy C++20-at támogató fordító szükséges. A cxx jelenlegi stabil API-ja a 1.x sorozat; a pontos metódusnevek és a hibakezelési típusok eltérhetnek, ezért a felhasznált verzióhoz tartozó dokumentáció ellenőrzése kötelező.

30.4.7 Általános interop-tervezés: ownership, hibakezelés, életciklus

A nyelvhatárokon átívelő kód tervezésekor a következő kérdéseket érdemes explicit módon dokumentálni:

  1. Ki birtokolja a memóriát?
    A C ABI-ban a hívó és a hívott fél közötti szerződés a legfontosabb. A pybind11 és az embind alapértelmezésben a célnyelvi futási környezetre bízza a birtoklást, de a C++ oldal is átadhat nem birtokló mutatókat. A cxx esetében a rust::Box, rust::UniquePtr és a primitív típusok automatikusan kezelik a tulajdonjogot.

  2. Hogyan kezeljük a hibákat?
    C határon return kód, out-paraméter, esetleg errno. Pythonban a C++ kivételt Python kivételre kell fordítani. WASM/embind esetén a C++ kivétel JavaScript Error lesz. Rust/cxx esetén a Rust Result és a C++ std::expected (C++23) közötti konverzióra van szükség. A C++ kivétel soha nem lépheti át a C ABI-t.

  3. Milyen típuskonverziók engedélyezettek?
    A primitív típusok (int32_t, int64_t, double, bool) minden eszközben közvetlenül támogatottak. A std::string, std::vector, std::span, std::map esetén a pybind11, az embind és a cxx másolatot készít, vagy speciális nézetet ad. A raw pointerek és a void* mindig a legalacsonyabb szintű, legveszélyesebb megoldások.

  4. Milyen szálbiztonsági garanciákat adunk?
    A C ABI nem ad semmilyen garanciát. A Python GIL megvédi a Python objektumokat, de a C++ oldali hosszú futásnál a GIL-t explicit módon el kell engedni. Az embind alapértelmezésben egyszálú; a Web Worker-ök és a SharedArrayBuffer használata külön konfigurációt igényel. A cxx a Rust és C++ oldalon is a szokásos szálbiztonsági szabályokat követi: a megosztott mutable állapotot szinkronizálni kell.

  5. Hogyan biztosítjuk a bináris kompatibilitást?
    A C API-val ellátott C++ könyvtár belső osztálylayoutja megváltoztatható anélkül, hogy a hívó újrafordulna, feltéve, hogy a C API deklarációja nem változik. A pybind11 és az embind esetében a modul újrafordítása szükséges, ha a C++ osztály layoutja változik, mert a generált ragasztókód a C++ típusokra hivatkozik. A cxx ugyanezt a feltételt támasztja: a bridge deklaráció és a C++/Rust források együttes újrafordítása szükséges.

Az alábbi táblázat összefoglalja a három magasabb szintű eszköz főbb különbségeit a fejezetben vizsgált szempontok szerint:

Eszköz Célnyelv Ownership modell Hibakezelés ABI réteg
pybind11 Python Python GC birtokol, C++ oldal nem birtokló is lehet C++ kivétel →\to Python kivétel Python C API
embind JavaScript (WASM) JS GC birtokol, explicit delete() lehetséges C++ kivétel →\to JS Error WASM + Emscripten
cxx Rust rust::Box, rust::UniquePtr, érték típusok Rust Result ↔\leftrightarrow C++ std::expected/hibakód C ABI (generált)

A táblázat általános irányelveket mutat; a pontos viselkedést az adott keretrendszer verziójához tartozó dokumentációban ellenőrizni kell.

30.4.8 Gyakori hibák és elkerülésük

C++ kivétel átengedése C határon.
A extern "C" függvényből kidobott kivétel nem definiált viselkedés. Minden C API függvényt try/catch blokkba kell csomagolni, és a hibát return kóddal vagy out-paraméterrel jelezni.

Dupla felszabadítás vagy memóriaszivárgás.
Ha a C API hívója nem tudja, hogy a mutatót ki birtokolja, akkor a counter_destroy kétszeri meghívása vagy elmulasztása katasztrófa. A dokumentációban mindig rögzíteni kell az ownership szabályt. A magasabb szintű eszközök (pybind11, embind, cxx) ezt a hibát részben kiküszöbölik, de a nyers mutatók átadásakor a szabályok itt is érvényesek.

GIL megsértése Pythonban.
Ha egy pybind11 kötésű függvény elengedi a GIL-t, de közben Python API-t hív, a viselkedés nem definiált. A GIL-mentes szakaszban csak olyan C++ kód futhat, amely nem érint Python objektumokat. Hasonlóképpen, egy másik Python szálból érkező hívás esetén a C++ kódnak szálbiztosnak kell lennie.

Nem hordozható struct layout.
A C ABI-ban a struktúrák elrendezése platform- és fordítófüggő lehet. Ha C++ struktúrát adunk át C-nek vagy más nyelvnek, akkor a mezők sorrendje, a padding és az igazítás eltérhet. A #pragma pack használata nem hordozható megoldás; jobb, ha a határfelület csak primitív típusokat és opaque pointereket használ.

UTF-8 és karakterkódolás.
A std::string nem garantáltan UTF-8, bár a legtöbb modern platformon az. Ha a Python vagy a JavaScript oldalra szöveget adunk át, a pybind11 és az embind általában UTF-8-at feltételez. A C API-ban a const char* jelentése dokumentáció kérdése; a hívónak tudnia kell, hogy a mutató meddig érvényes, és milyen kódolású.

A WASM lineáris memória és a mutatók érvényessége.
Az embind által generált string- és vektorátadás másolatot készít. Ha a JavaScript oldal közvetlenül a WASM memóriájába ír, akkor a C++ oldali mutatók érvényessége a memória növekedésekor megváltozhat. A std::span-nel átadott pufferek esetén a méretet és az élettartamot explicit módon kell ellenőrizni.

30.4.9 Labor: interop- és FFI-terv

Ennek a fejezetnek a laborja egy reprodukálható interop- és FFI-terv elkészítése. A feladat célja, hogy a tanult eszközök közül legalább kettőt alkalmazz, és a mért eredményeket a várt értékektől elkülönítve dokumentáld.

30.4.10 Feladat

Készíts egy C++20/23 komponenst, amely egy kis funkcionalitást valósít meg (például egy monoton számláló, egy fixpontos szám, vagy egy üzenetkódoló). A komponenst tedd elérhetővé legalább két másik nyelvből az alábbi lehetőségek közül:

  • C API és egy C nyelvű tesztprogram;
  • Python pybind11 modul;
  • JavaScript WASM modul embinddel;
  • Rust cxx bridge.

A C++ komponens legyen kivételbiztos, és a hibákat a nyelvhatáron a célnyelvnek megfelelően kezeld. Az ownership szabályokat írd le a README-ben.

30.4.11 Build és tesztkörnyezet

A build legyen reprodukálható: rögzítsd a fordítót, a standardverziót, az optimalizációs szintet, a külső könyvtárak verzióját, a CMake/Cargo/Emscripten verzióját. Példa CMake konfiguráció a C API-hoz és a pybind11-hez:

cmake_minimum_required(VERSION 3.20)
project(counter_interop LANGUAGES CXX C)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_library(counter_core STATIC counter_impl.cc)
target_include_directories(counter_core PUBLIC ${CMAKE_CURRENT_SOURCE_DIR})

add_library(counter_c SHARED counter_api.c counter_impl.cc)
target_link_libraries(counter_c PRIVATE counter_core)

find_package(pybind11 REQUIRED)
pybind11_add_module(counter_py counter_pybind.cpp)
target_link_libraries(counter_py PRIVATE counter_core)

A tesztek tartalmazzanak legalább egy-egy sikeres és egy hibás hívást minden célnyelvből. A C API teszthez egy kis C programot írhatsz, amely ellenőrzi a visszatérési kódokat. A Python teszthez pytest-et, a WASM teszthez Node.js-t, a Rust teszthez cargo test-et használhatsz.

30.4.12 Mérési napló

Minden méréshez rögzítsd a következőket:

  • fordító és verzió (pl. GCC 13.2, Clang 18, MSVC 19.38 – ahol elérhető);
  • standardverzió (C++20 vagy C++23);
  • optimalizációs szint (-O2, -O3, -Os);
  • hardver (processzor, órajel, memória, operációs rendszer);
  • inputméret és a futtatások száma;
  • a várt és a mért eredmény külön oszlopban.

Mérési dimenziók lehetnek:

  • a határon átívelő hívás átlagos költsége (ns/hívás);
  • a build idő (másodperc);
  • a generált bináris mérete (bájt);
  • a memóriahasználat a célnyelvben (bájt).

Példa a mérési napló formátumára:

Mérés Várható Mért Megjegyzés
C API hívás átlagos ideje < 50 ns 38 ns GCC 13.2, -O2, 100 000 futtatás
pybind11 hívás átlagos ideje < 200 ns 145 ns Python 3.12, pybind11 2.11
bináris méret (C API) < 20 KiB 17 KiB strip után
build idő (teljes) < 30 s 22 s cold cache

A várt értékeket a mérés előtt, az adott platformra vonatkozó becslés alapján töltsd ki; a mért értékeket a mérés után. Ha a mért érték jelentősen eltér a vártól, vizsgáld meg az okát: más optimalizációs szint, hibás benchmark, a futási környezet zajossága, vagy a határfelület nem szándékolt másolatot készít.

30.4.13 Ellenőrzés és dokumentáció

A labor akkor tekinthető sikeresnek, ha:

  • a build reprodukálható a README-ben megadott parancsokkal;
  • a tesztek minden célnyelv esetén zöldek;
  • a mérési napló különválasztja a várt és a mért eredményt;
