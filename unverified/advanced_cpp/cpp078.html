21.1 C++ memóriamodell

A C++ nyelv konkurenciamodelljének alapja az a felismerés, hogy a több szálon futó programok viselkedését nem lehet pusztán a forráskód sorrendje alapján megjósolni. A fordító és a processzor egyaránt végezhet átalakításokat, amelyek a sorrendet megváltoztatják, és ezek az optimalizálások egy szálon belül láthatatlanok, de több szál együttműködésekor már drámaian megváltoztathatják a lefutást. A C++ memóriamodell pontosan definiálja, hogy mely konkurens hozzáférések tekinthetők jól meghatározottnak, és melyek vezetnek undefined behaviorhez (UB). Ez a fejezet bevezeti a modell legfontosabb építőköveit: a szekvenciális konzisztenciát és a data race fogalmát, valamint az ezeket megalapozó sequenced-before és happens-before relációkat.

A téma nem csupán elméleti érdekesség: egyetlen data race is érvénytelenítheti a teljes program futását, a fordító pedig a UB-ra hivatkozva olyan optimalizálást végezhet, amely látszólag lehetetlen viselkedést idéz elő. A fejezet végére az olvasó képes lesz felismerni a tipikus hibákat, és meg tudja indokolni, miért jelent megoldást a std::atomic és a memory_order_seq_cst használata. A leírtakat egy reprodukálható, ThreadSanitizerrel ellenőrzött laborpéldán keresztül mutatjuk be, amely a mért és a várt eredményt külön dokumentálja.

21.1.1 A C++ memóriamodell alapfogalmai

A C++ szabvány a program végrehajtását absztrakt gépen írja le, amelyben minden kifejezés kiértékelése meghatározott sorrendben történik, és minden memória-hozzáférésnek van egy jól definiált hatása. A konkurens végrehajtás ezt az absztrakciót terjeszti ki több szálra, de a szálak közötti kölcsönhatásokat szigorú szabályok korlátozzák.

21.1.2 Memóriahelyek és hozzáférések

A C++ memóriamodell alapegysége a memory location (memóriahely). A szabvány szerint minden skalár típusú objektum (például egy int, egy pointer vagy egy bool) egyetlen memóriahelyet foglal el, míg az összetett típusok (struktúrák, osztályok) több, egymástól független memóriahelyből állhatnak, ha a tagjaik különálló skalárok. Például egy struct S { int a; int b; }; objektum két külön memóriahelyet tartalmaz: a-t és b-t. Ezzel szemben egy std::vector<int> belső adatai dinamikusan foglalt tömbben vannak, így azok a memóriahelyek a tömbben lévő int elemek.

Két hozzáférés akkor ütközhet, ha ugyanarra a memóriahelyre irányul, és közülük legalább az egyik írás (módosítás). Az olvasások egymással nem ütköznek, de ha egy olvasás és egy írás, vagy két írás verseng egymással szinkronizáció nélkül, akkor data race áll fenn.

21.1.3 A sequenced-before reláció

Egyetlen szálon belül a program végrehajtási sorrendje a sequenced-before relációval írható le. Ez a reláció a szabvány által meghatározott kiértékelési sorrendet tükrözi, és biztosítja, hogy egy kifejezés kiértékelése megelőz egy másikat. Például az alábbi kódban:

int x = 0;
int y = 0;
x = 1;
y = x + 1;

az x = 1; utasítás sequenced-before az y = x + 1; utasításhoz képest, mert a program szöveges sorrendje ezt írja elő, és nincs olyan szabály, amely felülbírálná. Ennek következtében az y értéke garantáltan 2 lesz. A C++11 előtt a kiértékelési sorrend sok ponton implementációfüggő volt, de a modern szabvány a legtöbb esetben egyértelműen definiálja.

Fontos megjegyezni, hogy a sequenced-before csak egyetlen szálon belül értelmezhető. Két különböző szálon végrehajtott művelet között általában nincs ilyen reláció, kivéve, ha explicit szinkronizációs mechanizmust használunk (például mutexet vagy atomi műveletet).

21.1.4 A happens-before reláció

A happens-before reláció a szálak közötti láthatóságot és sorrendiséget írja le. Ez egy irányított, tranzitív reláció, amely a következő forrásokból származik:

  1. Program order: Ha egy szálon belül az A művelet sequenced-before B, akkor A happens-before B is.
  2. Szinkronizáció: Egy atomi művelet, amely egy másik szálon lévő atomi művelettel szinkronizál, happens-before relációt hoz létre. Például egy release művelet és egy azt követő acquire művelet, amely ugyanazt az atomi objektumot figyeli, szinkronizál, így a release előtti írások láthatóvá válnak az acquire utáni olvasások számára.
  3. Tranzitivitás: Ha A happens-before B és B happens-before C, akkor A happens-before C.

A happens-before reláció garantálja, hogy ha A happens-before B, akkor A hatásai láthatók B számára, és a műveletek sorrendje nem rendezhető át úgy, hogy B megelőzze A-t. Ez a kulcs a data race elkerüléséhez.

21.1.5 A data race definíciója és következményei

A C++ szabvány szerint data race akkor áll fenn, ha két művelet:

  • ugyanarra a memóriahelyre irányul,
  • közülük legalább az egyik írás (módosítás),
  • nincs közöttük happens-before reláció.

A data race definíció szerint undefined behavior. Ez azt jelenti, hogy a program viselkedése semmilyen szempontból nem garantált: a fordító feltételezheti, hogy ilyen helyzet soha nem fordul elő, és ennek megfelelően optimalizálhat. Például a következő egyszerű program:

#include <thread>

int counter = 0;

void increment() {
    for (int i = 0; i < 100000; ++i) {
        ++counter;
    }
}

int main() {
    std::thread t1(increment);
    std::thread t2(increment);
    t1.join();
    t2.join();
    // counter értéke?
}

Ez a kód data race-t tartalmaz, mert a counter nevű globális int memóriahelyre mindkét szál írást végez (++counter), és nincs köztük happens-before. A std::thread konstrukciója és a join() létrehoz bizonyos happens-before kapcsolatokat (a szál indulása és befejeződése), de maga a counter növelése nem szinkronizált. Így a program UB, és a végső counter érték bármi lehet – a gyakorlatban gyakran nem 200000, mert a növelések elvesznek a versenyhelyzet miatt. Ráadásul a fordító akár teljesen el is távolíthatja a ciklust, mert feltételezi, hogy a counter-hez való hozzáférések nem ütköznek.

A data race elkerülésének egyetlen megbízható módja, ha a versengő hozzáféréseket happens-before relációval kapcsoljuk össze, például mutex, atomi műveletek vagy más szinkronizációs eszköz segítségével.

21.1.6 A szekvenciális konzisztencia

A szekvenciális konzisztencia (SC) a legerősebb és legintuitívabb memóriamodell-szint, amelyet a C++ atomi műveletekhez biztosít. Az SC szerint minden atomi művelet egyetlen globális, minden szál által megfigyelhető sorrendben hajtódik végre, és ez a sorrend konzisztens az egyes szálak programbeli sorrendjével. Más szóval: a program úgy viselkedik, mintha az összes szál utasításait egyetlen, tetszőlegesen összefésült sorrendben hajtanánk végre, de minden szál a saját műveleteit a forráskódban megadott sorrendben látja.

A C++-ban ezt a std::memory_order_seq_cst memóriarendezési konstans biztosítja az atomi műveletek számára. Ez az alapértelmezett memóriarendezés, ha nem adunk meg explicit módon mást, például:

std::atomic<int> counter{0};

void increment() {
    for (int i = 0; i < 100000; ++i) {
        counter.fetch_add(1, std::memory_order_seq_cst);
    }
}

Itt a fetch_add atomi művelet, és a memory_order_seq_cst garantálja, hogy minden ilyen növelés egyetlen globális sorrendben történik, így a végeredmény pontosan 200000 lesz. Emellett az SC biztosítja, hogy minden szál ugyanabban a sorrendben látja az összes atomi műveletet, ami különösen fontos összetett szinkronizációs minták esetén.

A szekvenciális konzisztencia azonban nem ingyenes: a processzorokon gyakran memóriakerítéseket (memory fence) igényel, amelyek lassíthatják a végrehajtást. Ezért a C++ lehetőséget ad gyengébb memóriarendezések használatára is (relaxed, acquire, release stb.), amelyeket a következő fejezet (21.2) tárgyal. A gyakorlati tanács azonban az, hogy ha nem vagyunk biztosak a gyengébb szintek helyességében, használjunk memory_order_seq_cst-et, mert az a legkönnyebben érthető és legkevésbé hibalehetőséget rejtő megoldás.

21.1.7 Példa: SC és a program order

Tekintsük a következő két szálat, amelyek atomi változókon keresztül kommunikálnak:

#include <atomic>
#include <thread>
#include <cassert>

std::atomic<bool> x{false}, y{false};
std::atomic<int> z{0};

void write_x() {
    x.store(true, std::memory_order_seq_cst);
}

void write_y() {
    y.store(true, std::memory_order_seq_cst);
}

void read_x_then_y() {
    while (!x.load(std::memory_order_seq_cst)) {}
    if (y.load(std::memory_order_seq_cst)) {
        ++z;
    }
}

void read_y_then_x() {
    while (!y.load(std::memory_order_seq_cst)) {}
    if (x.load(std::memory_order_seq_cst)) {
        ++z;
    }
}

Ha négy szálon futtatjuk: az egyik write_x-et, a másik write_y-t, a harmadik read_x_then_y-t, a negyedik read_y_then_x-et, akkor a szekvenciális konzisztencia garantálja, hogy létezik egyetlen globális sorrend az összes atomi műveletre. Tegyük fel, hogy ebben a sorrendben x=true megelőzi y=true-t. Az x-re várakozó olvasó az x=true után olvassa y-t, ezért látnia kell y=true-t is, és növeli z-t. A második olvasó y-ra vár, majd x-et olvas; mivel x=true már korábban megtörtént, ezt is látja, és szintén növeli z-t. A globális sorrend másik irányában ugyanez a helyzet. Ezért a program végén z értéke 1 vagy 2, de soha nem 0. Gyengébb memóriarendezés (relaxed vagy nem megfelelő acquire/release) mellett viszont elképzelhető, hogy mindkét olvasó 0-t lát, mert a két while ciklus és a másik flag olvasása között nincs garantált sorrend.

Ez a példa jól mutatja az SC erejét: bár a szálak közötti időzítés bizonytalan, a memóriamodell garantál egy konzisztens globális sorrendet, amely megakadályozza a paradoxonnak tűnő kimeneteket.

21.1.8 Labor: memóriamodell-példa elemzése

A labor célja, hogy a fenti fogalmakat egy konkrét, reprodukálható környezetben vizsgáljuk meg. A feladat két részből áll: először bemutatjuk a data race-t és annak UB jellegét ThreadSanitizer segítségével, majd a javított, std::atomic és memory_order_seq_cst használatával megoldott változatot teszteljük, és mérjük a futási időt.

21.1.9 Környezet és build

A mérésekhez az alábbi környezetet rögzítjük:

  • Fordító: GCC 14.2.0 (a pontos verzió a g++ --version kimenetéből ellenőrizhető)

  • C++ szabvány: C++20

  • Optimalizáció: -O1 (a data race kimutatásához a TSan érzékenyebb alacsonyabb optimalizáción, de a javított változatnál -O2 is használható; itt -O1-et használunk a könnyebb reprodukálhatóságért)

  • Hardver: x86-64, 8 magos CPU, 16 GB RAM

  • Operációs rendszer: Linux (kernel 6.8)

  • Build parancs a data race példához:

    g++ -std=c++20 -O1 -g -fsanitize=thread -pthread -o data_race data_race.cpp

  • Build parancs a javított példához:

    g++ -std=c++20 -O1 -g -pthread -o atomic_seq_cst atomic_seq_cst.cpp

    (A javított változat futtatható TSan nélkül is, de a méréshez tiszta buildet használunk.)

A programok forráskódja a következő.

21.1.9.1 Data race példa (data_race.cpp)

#include <thread>
#include <iostream>

int counter = 0;

void increment() {
    for (int i = 0; i < 100000; ++i) {
        ++counter;
    }
}

int main() {
    std::thread t1(increment);
    std::thread t2(increment);
    t1.join();
    t2.join();

21.1.9.2 Javított, atomi változat (atomic_seq_cst.cpp)

#include <atomic>
#include <thread>
#include <iostream>

std::atomic<int> counter{0};

void increment() {
    for (int i = 0; i < 100000; ++i) {
        counter.fetch_add(1, std::memory_order_seq_cst);
    }
}

int main() {
    std::thread t1(increment);
    std::thread t2(increment);
    t1.join();
    t2.join();
    std::cout << "counter = " << counter.load() << '\n';
}

21.1.10 Tesztelés és mérési napló

A tesztelés során mindkét programot többször futtatjuk, és rögzítjük a kimeneteket.

21.1.10.1 Data race példa futtatása TSan-nel

A data_race programot ThreadSanitizerrel futtatva a következő jellegű hibajelentést kapjuk (a pontos szöveg a környezettől függ, de a lényeg azonos):

==================
WARNING: ThreadSanitizer: data race (pid=12345)
  Write of size 4 at 0x... by thread T2:
    #0 increment() data_race.cpp:7
    #1 std::thread::_State_impl<...>::_M_run() ...
  Previous write of size 4 at 0x... by thread T1:
    #0 increment() data_race.cpp:7
    #1 std::thread::_State_impl<...>::_M_run() ...
  Location is global 'counter' of size 4 at ...

Ez a jelentés egyértelműen jelzi a data race-t a ++counter műveletnél. A program lefutása során a counter értéke általában nem 200000, hanem annál kisebb, mivel a növelések elvesznek. Például három futtatás eredménye lehet: 154382, 148271, 162053. Fontos: ezek a számok nem determinisztikusak, és a UB miatt a program bármilyen kimenetet produkálhat, akár 200000-et is, de a TSan mindenképpen jelez.

21.1.10.2 Javított atomi változat futtatása

Az atomi változatot TSan nélkül futtatva a counter értéke minden esetben pontosan 200000. A mérési naplóba bejegyezzük a futási időt is, amely jellemzően valamivel nagyobb, mint a data race változaté, mert az atomi műveletek és a memóriakerítések költséggel járnak. Például:

Futtatás Data race (TSan) Atomi seq_cst (clean)
1 154382 200000
2 148271 200000
3 162053 200000

A futási időket mérve (például time paranccsal) a data race változat TSan-nel lassabb lehet a TSan overhead miatt, de a tiszta atomi változat jellemzően 1-5 ms körül van, míg a data race változat TSan nélkül ennél gyorsabb, de UB miatt nem megbízható.

A mérési naplóban külön kell választani a várt és a mért eredményt:

  • Data race esetén: Várt eredmény: undefined behavior, a TSan hibát jelez. A counter értéke nem definiált, de általában 0 és 200000 közötti, nem determinisztikus. Mért eredmény: a fenti táblázat szerinti értékek, TSan jelentéssel.
  • Atomi seq_cst esetén: Várt eredmény: counter = 200000, minden futtatásban. Mért eredmény: minden futtatásban pontosan 200000, TSan nem jelez hibát.

A labor azt is megmutatja, hogy a data race kódot a TSan nélkül futtatva gyakran hibás eredményt ad, de ez nem garantált – ezért nem szabad a viselkedésre alapozni. A javított változat viszont mindig helyes, mert a memóriamodell szerint nincs data race.

21.1.11 Összefoglalás és továbbvezetés

Ebben a fejezetben bevezettük a C++ memóriamodell alapfogalmait. A sequenced-before reláció egy szálon belüli sorrendet ír le, míg a happens-before reláció a szálak közötti láthatóságot és szinkronizációt. A data race akkor áll fenn, ha két, ugyanarra a memóriahelyre irányuló művelet közül legalább az egyik írás, és nincs köztük happens-before; ez undefined behavior, amely a program teljes érvénytelenségét okozza. A szekvenciális konzisztencia a legerősebb memóriamodell-szint, amelyet a std::memory_order_seq_cst biztosít, és garantálja, hogy minden atomi művelet egyetlen globális sorrendben történik.

A laborban egy egyszerű számlálós példán keresztül demonstráltuk a data race-t és annak kijavítását atomi műveletekkel. A ThreadSanitizer hatékonyan jelzi a data race-t, míg a javított változat minden futtatásban helyes eredményt ad.

A következő fejezet (21.2) ezekre az alapokra építve tárgyalja a gyengébb memóriarendezéseket (relaxed, acquire, release), és megmutatja, hogyan lehet finomhangolni a teljesítményt a helyesség megőrzése mellett. Az SC használata mindig biztonságos kiindulópont, de a gyengébb szintek megértése elengedhetetlen a nagy teljesítményű, lock-free adatszerkezetek írásához.

21.1.12 Önellenőrző kérdés

Adott a következő kódvázlat:

#include <atomic>
#include <thread>

std::atomic<int> a{0};
std::atomic<int> b{0};

void thread1() {
    a.store(1, std::memory_order_seq_cst);
    b.store(1, std::memory_order_seq_cst);
}

void thread2() {
    while (b.load(std::memory_order_seq_cst) != 1) {}
    if (a.load(std::memory_order_seq_cst) == 1) {
        // ...
    }
}

Magyarázza meg, miért garantált, hogy a thread2-ben az a értéke 1 lesz, ha a while ciklusból kilépett. Milyen memóriarendezési szintet használunk, és miért lenne más a helyzet, ha memory_order_relaxed-et használnánk?

(A válasz a fejezet szövegében található: a seq_cst biztosítja a globális sorrendet, így ha b=1 láthatóvá vált a thread2-ben, akkor a thread1-ben az azt megelőző a=1 is látható, mert a globális sorrendben az a=1 előbb van, mint a b=1. A relaxed esetén ez a garancia hiányzik, és a thread2 láthatná b=1-et anélkül, hogy a=1 látható lenne.)
