6.2 Rendszerhívások, ABI és libc

A rendszerhívási interfész (syscall) az operációs rendszer magjának az a programozási felülete, amelyen keresztül a felhasználói térben futó programok a kernel szolgáltatásait igénybe vehetik. A hordozható programozási felület ezzel szemben gyakran egy felhasználói könyvtár, tipikusan a libc, amely a nyers rendszerhívásokat a programozó számára ismerős függvényhívásokká alakítja. Ebben a fejezetben a kettő közötti határt, az ABI-t, valamint a libc wrapper réteget vizsgáljuk.

Először tisztázzuk a fogalmakat. Az API (Application Programming Interface) forráskód szintű szerződés: megmondja, hogy egy függvény milyen paramétereket vár, milyen típusú értéket ad vissza, és milyen szemantikát garantál. Az ABI (Application Binary Interface) ezzel szemben bináris szintű szerződés: meghatározza, hogy a lefordított kód milyen regiszterekben adja át az argumentumokat, milyen utasítással vált privilegizált módba, hogyan jelzi a hibát, és milyen struktúra-elrendezést használ. A rendszerhívási interfész elsősorban ABI, míg a libc által nyújtott felület API. A hordozhatóság érdekében a programozó általában az API-t használja, a rendszer futás közben az ABI-t.

A kernel szolgáltatásainak elérése privilegizált átmenetet igényel, mert a kernel a védett, magasabb jogosultságú szinten fut. A Privilegiszintek és a kernel/user tér átlépése fejezetben tárgyaltuk a privilege szinteket és a trap/syscall mechanizmust. Ebben a fejezetben feltételezzük, hogy van egy ilyen átmenetünk; most arra koncentrálunk, hogy mi történik azután, hogy a vezérlés a kernelbe került.

6.2.1 A rendszerhívási interfész alapjai

A kernel belépési pontja egy úgynevezett syscall dispatcher, amely a rendszerhívási szám alapján kiválasztja a megfelelő kernel függvényt. A rendszerhívási szám egy egész szám, amely egyedi azonosítót ad minden egyes szolgáltatásnak. A számokat általában központi fejlécfájlban definiálják, és a kernel egy táblázatban tárolja a hívható függvények mutatóit. Az alábbi egyszerű példa egy minimalistaker nelben mutatja a táblázatot és a dispatchert:

typedef long (*syscall_fn)(unsigned long, unsigned long, unsigned long,
                            unsigned long, unsigned long, unsigned long);

/* A rendszerhívási számok rögzítettek */
#define SYS_WRITE  1
#define SYS_EXIT   60
#define SYS_OPEN   2

static syscall_fn sys_call_table[256] = {
    [SYS_WRITE] = sys_write,
    [SYS_OPEN]  = sys_open,
    [SYS_EXIT]  = sys_exit,
};

long handle_syscall(unsigned long nr,
                    unsigned long a0, unsigned long a1, unsigned long a2,
                    unsigned long a3, unsigned long a4, unsigned long a5)
{
    if (nr >= ARRAY_SIZE(sys_call_table))
        return -ENOSYS;
    if (sys_call_table[nr] == NULL)
        return -ENOSYS;
    return sys_call_table[nr](a0, a1, a2, a3, a4, a5);
}

A példa C, szemléltetés. A -ENOSYS egy negatív hibakód; a kernel oldalán a hibákat negatív errno értékekkel szokás jelezni. Ez fontos eltérés a libc API-tól: a write() függvény hiba esetén -1-et ad vissza, és a hibakódot a errno globális (valójában szálhoz kötött) változóba írja, míg a kernel közvetlenül a negatív hibakódot adja vissza. A libc wrapper feladata ezt a konvenciót összekötni.

Nézzük az argumentumátadást. A felhasználói térből a kernelbe történő átmenetkor az argumentumok nem a szokásos függvényhívási konvenció szerint utaznak, hanem a syscall ABI szerint. Az x86-64 Linuxon például a rendszerhívási számot a rax regiszterben, az argumentumokat pedig a rdi, rsi, rdx, r10, r8, r9 regiszterekben adják át. A visszatérési érték a rax regiszterben érkezik. Más architektúrák eltérnek, de a lényeg ugyanaz: a hívó és a hívott oldal között pontos, bináris szinten rögzített szerződés van. A libc wrapper elrejti ezt a részletet; a programozó a write() függvényt hívja, a wrapper pedig a megfelelő regiszterekbe tölti az értékeket, kiadja a syscall utasítást, majd feldolgozza a visszatérést. A következő pszeudokód a write wrapper működését mutatja:

ssize_t write(int fd, const void *buf, size_t count)
{
    long ret;
    ret = syscall(SYS_write, fd, buf, count);
    if (ret < 0) {
        errno = -ret;
        return -1;
    }
    return ret;
}

Itt a syscall egy alacsony szintű függvény vagy makró, amely kiadja a tényleges trap utasítást és visszaadja a regiszter értékét. A hibakezelés kulcsa a negatív visszatérési érték felismerése. A kernel általában a hibakódok egy kis tartományát használja (Linuxon -4095 és -1 között), így a negatív érték egyúttal hibát is jelent. A ret < 0 ellenőrzés megfelelő, de a valódi glibc wrapper pontosabb: ellenőrzi, hogy az érték a hibakód tartományba esik-e. Ez azért lényeges, mert a syscall siker esetén nem ad vissza negatív értéket, de a konvenciót expliciten kezelni kell, hogy a jövőbeli változások ne okozzanak hibát.

A mutatóargumentumok külön figyelmet érdemelnek. A felhasználói program által átadott címek a felhasználói címtérbe mutatnak. A kernel nem dereferálhatja ezeket közvetlenül, mert (1) a kernel más címtérrel futhat, (2) a mutató érvénytelen lehet, ami kernel oops-hoz vezet, (3) a felhasználó megpróbálhat kernel memóriát olvasni. Ezért a kernelnek minden felhasználói mutatót ellenőriznie kell, és speciális másoló függvényekkel kell adatot mozgatnia a két tér között. A Linuxon ezek a copy_from_user és copy_to_user függvények. Az alábbi sys_write vázlat mutatja a helyes mintát:

long sys_write(unsigned int fd, const char __user *buf, size_t count)
{
    char kbuf[128];
    size_t to_copy = min(count, sizeof(kbuf));
    if (copy_from_user(kbuf, buf, to_copy) != 0)
        return -EFAULT;
    /* ... eszközre írás, például konzol */
    return to_copy;
}

Itt a __user annotáció dokumentálja, hogy a mutató felhasználói térből származik, és a copy_from_user végzi az ellenőrzést és másolást. A példa leegyszerűsített, de rávilágít a legfontosabb biztonsági szempontra.

6.2.2 ABI-stabilitás és verziózás

A rendszerhívási szám és a táblázat stabilitása az ABI-stabilitás sarokköve. Ha egyszer egy rendszerhívási számot publikáltak, a bináris kompatibilitás érdekében nem lehet újra felhasználni más célra, még akkor sem, ha az eredeti syscallt elavultnak nyilvánították. A Linux kernel különösen szigorú ebben: a felhasználói térbe exportált syscall ABI örök érvényű. Új szolgáltatásokhoz új rendszerhívási számokat vezetnek be, a régiek pedig megmaradnak. Ha egy struktúra mérete megváltozik, akkor vagy új syscallt hoznak létre (például az openat az open utódja), vagy gondosan verziózzák a struktúrát. A Windows esetében a helyzet kissé más: a hivatalos hordozható felület a Win32 API, amely mögött a natív rendszerhívási réteg (ntdll) nem garantáltan stabil; a Microsoft fenntartja a jogot a natív interfész megváltoztatására, ezért a programozóknak a dokumentált Win32 függvényeket kell használniuk.

A verziózás és a szimbólumkezelés a libc oldalán is megjelenik. A C könyvtár dinamikus linkelés esetén szimbólumverziókat használhat, hogy a régebbi binárisok továbbra is a nekik megfelelő implementációt kapják. A glibc például a GLIBC_2.2.5 verzióval látja el a szimbólumokat. Ha egy függvény viselkedése megváltozik, a régi verzió megmarad a régi szimbólum mögött, az új pedig új verziót kap. Ez lehetővé teszi, hogy ugyanaz a könyvtár egyszerre szolgálja ki a régi és az új programokat.

Egy másik fontos aspektus az ABI és az API közötti különbség a gyakorlatban: a forráskód újrafordítása az API-t használja, a lefordított bináris futtatása az ABI-t. Ha a programozó renameat2-t hív, akkor a forrásban a unistd.h deklarációját használja, és a fordító egy hívást generál a libc renameat2 függvényéhez, amely viszont a megfelelő syscallt hívja. A bináris azonban nem tartalmazza a syscall számot, csak a libc függvényhívást; a syscall szám a libc-n belül van. Ezért a libc frissítése önmagában megváltoztathatja a syscall hívást anélkül, hogy a programot újra kellene fordítani. Ez a rétegelt tervezés teszi lehetővé, hogy a kernel ABI-ja és a libc API-ja egymástól függetlenül fejlődjön.

A rendszerhívási számok és a kapcsolódó makrók általában a felhasználói tér számára is elérhetők. A Linux az __NR_write, __NR_exit nevű makrókat definiálja az asm/unistd.h fejlécben, amelyeket a programok a syscall() függvénnyel együtt használhatnak. Ez ugyan nem hordozható, de lehetővé teszi, hogy a fejlesztő közvetlenül a syscall ABI-t célozza. A hordozható programok ehelyett a libc magas szintű függvényeit használják, és a libc felel a megfelelő syscall kiválasztásáért. Például a fork() függvényt a libc a modern Linux kernelben a clone3 syscallra képezi le, de a programozó továbbra is a POSIX fork() API-t hívja.

6.2.3 A libc szerepe

A libc (C standard könyvtár) több, mint egyszerű syscall-gyűjtemény. Feladatai közé tartozik:

  • Wrapper függvények biztosítása: minden POSIX vagy C standard függvényhez, amely mögött syscall áll, egy olyan függvényt nyújt, amely kezeli a regisztereket, az errno-t és a visszatérési konvenciót.
  • errno kezelése: a hibaállapotot szálanként tárolja (thread-local storage, TLS), így a párhuzamos programokban nem keverednek össze a hibakódok.
  • Hordozhatóság: ugyanaz a C forrás több operációs rendszeren is lefordul, mert a libc elrejti a rendszerspecifikus hívásokat.
  • Dinamikus linkelés: a megosztott könyvtárak betöltését és a szimbólumfeloldást a dinamikus linker (például ld-linux-x86-64.so.2) végzi, amely maga is a libc része.
  • Magasabb szintű absztrakciók: a stdio pufferezése, a malloc memóriakezelő, a pthread szálkezelés mind a libc részei, és ezek jelentősen túlmutatnak a puszta syscall wrappereken.

A syscall() függvény egy speciális eszköz: lehetővé teszi tetszőleges syscall közvetlen meghívását a szám és az argumentumok megadásával. Nem hordozható, de hasznos lehet kernel fejlesztésénél vagy olyan új syscallok tesztelésekor, amelyekhez még nincs libc wrapper. A következő kód egy általános syscall() csomagolást mutat be Linux x86-64-re:

long syscall(long nr, long a0, long a1, long a2, long a3, long a4, long a5)
{
    register long rax asm("rax") = nr;
    register long rdi asm("rdi") = a0;
    register long rsi asm("rsi") = a1;
    register long rdx asm("rdx") = a2;
    register long r10 asm("r10") = a3;
    register long r8  asm("r8")  = a4;
    register long r9  asm("r9")  = a5;
    asm volatile("syscall"
                 : "+r"(rax)
                 : "r"(rdi), "r"(rsi), "r"(rdx), "r"(r10), "r"(r8), "r"(r9)
                 : "rcx", "r11", "memory");
    return rax;
}

Ez a függvény erősen architektúra-függő, és csak szemléltetésre szolgál. A valódi glibc syscall() hasonló elven működik, de hordozhatóbb módon, és a cél architektúrának megfelelően van lefordítva.

A libc wrapper generálása gyakran makrókkal történik, hogy elkerüljék az ismétlést. Például a Linux kernelben a SYSCALL_DEFINE makrók állítják elő a syscall bejegyzéseket, a libc oldalán pedig a weak_alias és a libc_hidden_def mechanizmusok segítenek a szimbólumok kezelésében. A hétköznapi fejlesztő számára azonban elegendő a deklarációk és a wrapper logika ismerete.

A statikus és dinamikus linkelés is érinti az ABI-t. Statikus linkelés esetén a libc kódja a végrehajtható fájlba kerül, így a futtatáshoz nincs szükség külső könyvtárra, de a bináris nagyobb, és a libc biztonsági frissítései nem érvényesülnek újrafordítás nélkül. Dinamikus linkelésnél a program a futás közben tölti be a megosztott libc-t, így a frissítések azonnal hatnak, de a binárisnak kompatibilisnek kell lennie a betöltött verzió ABI-jával. A szimbólumverziózás ezt a kompatibilitást hivatott biztosítani.

6.2.4 Labor: syscall-táblázat és libc-wrapperek vázlata

A labor célja egy egyszerű syscall-táblázat és libc-wrapperek vázlatának elkészítése egy emulált környezetben. A kiindulópont a Privilegiszintek és a kernel/user tér átlépése fejezetben bemutatott trap kezelő, amely már rendelkezik a felhasználói/kernel átmenettel. Most a dispatchert és a wrapper réteget adjuk hozzá.

Környezet: QEMU x86-64, 1 virtuális CPU, 128 MiB RAM, freestanding C, GCC vagy Clang. A pontos verziókat a reprodukciós jegyzőkönyvben rögzíteni kell. A boot mechanizmus adott (például a BIOS, UEFI és a bootfolyamat fejezetből), a labor a syscall rétegre koncentrál.

Feladat: Implementáljuk a sys_write és sys_exit rendszerhívásokat, valamint a dispatchert. Készítsünk egy felhasználói tesztprogramot, amely a libc wrapper vázlatot használja: my_write() és my_exit() függvényeket, amelyek a rendszerhívási ABI-t hívják, beállítják az errno-t, és a teszt kiírja a “hello syscall” üzenetet, majd 0 kóddal kilép.

A syscall táblázat és a dispatcher kódja megegyezhet a fenti példával. A wrapper vázlat a következő lehet:

/* userland tesztprogram, freestanding, saját minimalista libc */
typedef unsigned long size_t;
typedef long ssize_t;

static int errno;

static inline long raw_syscall(long nr, long a0, long a1, long a2)
{
    register long rax asm("rax") = nr;
    register long rdi asm("rdi") = a0;
    register long rsi asm("rsi") = a1;
    register long rdx asm("rdx") = a2;
    asm volatile("syscall"
                 : "+r"(rax)
                 : "r"(rdi), "r"(rsi), "r"(rdx)
                 : "rcx", "r11", "memory");
    return rax;
}

ssize_t my_write(int fd, const void *buf, size_t count)
{
    long ret = raw_syscall(1, fd, (long)buf, count);
    if (ret < 0) {
        errno = -ret;
        return -1;
    }
    return ret;
}

void my_exit(int status)
{
    raw_syscall(60, status, 0, 0);
    __builtin_unreachable();
}

Itt a raw_syscall inline assembly, x86-64-re specifikus. A wrapper pontosan a korábban leírt logikát követi: hívja a syscallt, ellenőrzi a negatív visszatérést, beállítja az errno-t. Az errno ebben a minimalista környezetben egy egyszerű globális változó; valós libc-ben TLS-ben lenne. A kód szemléltetés, nem éles rendszeren futtatandó.

Build és futtatás: A reprodukciós csomag tartalmazza a Makefile-t, a linker scriptet és a futtatási parancsot. Egy lehetséges parancssor:

make clean
make CFLAGS="-O0 -g -ffreestanding -nostdlib"
qemu-system-x86_64 -cpu qemu64 -m 128M -nographic -kernel kernel.bin

A verziók ellenőrzése szükséges: a QEMU, a GCC és a binutils pontos verzióját rögzíteni kell a naplóban.

Mérés: A syscall belépés és visszatérés idejét mérjük ciklusban. A mérési módszer: egy 1 000 000 iterációból álló ciklus, amely egy triviális syscallt hív (például my_write egy 0 hosszúságú pufferrel). A méréshez a rdtsc utasítást használjuk a ciklus előtt és után, majd az átlagot számoljuk. A pontos érték függ a QEMU módjától (TCG vs KVM), a hoszt CPU-tól és a kernel beállításaitól, ezért a mért értéket és a várt nagyságrendet elkülönítve közöljük. A várt eredmény az, hogy a syscall költsége a QEMU TCG módban nagyságrendileg 10 000–100 000 ciklus, míg natív KVM-en 100–1000 ciklus lehet; ezek az értékek csak tájékoztató jellegűek, és az aktuális mérést a jegyzőkönyvben rögzíteni kell. A mérési naplónak tartalmaznia kell a hoszt CPU típusát, órajelét, a QEMU verzióját, a fordítási beállításokat (-O0, -O2), és a mérési ciklusok számát. A mérési eredményeket nem szabad abszolút igazságként kezelni, mindig a reprodukciós körülményekkel együtt kell értelmezni.

Elvárt eredmény: A tesztprogram kiírja a “hello syscall” üzenetet, és 0 kilépési kóddal fejeződik be. A napló tartalmazza a mért ciklusszámokat, a hibakódokat és az esetleges eltéréseket a várt viselkedéstől.

6.2.5 Tipikus hibák és helyes megoldások

A gyakorlat során az alábbi tipikus hibák fordulhatnak elő:

  1. Hibás rendszerhívási szám. Ha a wrapperben 1 helyett 0-t írunk, a dispatcher ENOSYS hibát ad, vagy rossz függvényt hív. A megoldás: a syscall számokat központi fejlécfájlban definiáljuk, és a wrapper is ugyanazt a definíciót használja.

  2. Elmaradt argumentum-ellenőrzés a kernel oldalán. Ha a sys_write közvetlenül dereferálja a felhasználói mutatót, a kernel összeomolhat. A helyes megoldás a copy_from_user használata, valamint a hossz és a célpuffer ellenőrzése.

  3. Az errno beállításának hiánya. Ha a wrapper nem írja be az errno-t, a hívó félrevezető hibakódot kap, vagy nem is tudja, hogy hiba történt. A wrappernek mindig be kell állítania az errno-t, mielőtt -1-et ad vissza.

  4. A visszatérési érték helytelen értelmezése. A kernel negatív hibakódot ad vissza, de ha a wrapper azt hiszi, hogy a -1 a hibajelzés, és nem a negatív hibakódot, akkor rossz lesz az errno. A helyes minta az, hogy a ret negatív értékét vizsgáljuk, és az abszolút értékét adjuk az errno-nak.

  5. Típushibák a hosszoknál. A size_t és ssize_t keverése, valamint a 32/64 bites regiszterek közötti eltérés hibás adatátvitelhez vezet. A wrappernek pontosan követnie kell a syscall ABI típusait.

  6. ABI-törés a struktúrákban. Ha egy syscall argumentumaként struktúrát adunk át, és a struktúra elrendezése megváltozik, a régi binárisok eltörnek. A megoldás a struktúrák verziózása vagy új syscall bevezetése.

A fejezet végére az olvasó képes lesz elmagyarázni a rendszerhívási interfész és a hordozható programozási felület közötti különbséget, felépíteni egy egyszerű syscall táblázatot, és megírni a megfelelő libc wrapper vázlatot. A következő fejezet (Shell, init, daemonok és a userland felépítése) ezekre az alapokra épít, és bemutatja, hogyan épül fel a userland: a shell, az init folyamat és a daemonok.
