32.3 Ütemező, rendszerhívások és shell

A záróprojekt ezen pontján már van egy bootoló, memóriakezeléssel rendelkező kernel. Ebben a fejezetben a rendszer futtathatóvá válik: megvalósítjuk a feladatmodellt, a round-robin ütemezőt, a rendszerhívás-belépési pontot, az init folyamatot és egy minimális shellt. A cél nem egy általános célú operációs rendszer teljes körű reprodukálása, hanem egy olyan zárt, ellenőrizhető kernel, amelyben minden fontos állítás kódolvasással vagy mérési naplóval alátámasztható.

A fejezet feltételezi, hogy az os123 egység után rendelkezésre áll egy bootoló kernel, egy egyszerű memóriatérkép és egy buildrendszer. Az itt bemutatott kódrészletek RISC-V példát használnak, mert a QEMU virt gépe jól reprodukálható; az elv azonban x86-on vagy más architektúrán is azonos. A konkrét regiszterneveket és utasításokat mindig az adott porton ellenőrizni kell.

32.3.1 1. Feladatmodell és adatstruktúrák

A futtatható egységet itt feladatnak nevezzük. A feladat lehet kernelkontextusban induló szál, de a fejezet szempontjából a felhasználói program futtatása a lényeges eset. A feladatmodell minimális, de kellően bővíthető ahhoz, hogy az os125 fájlrendszer-integrációt rá lehessen építeni.

A központi struktúra a PCB (process control block), amelyet itt task néven valósítunk meg:

/* task.h – a minimalis feladatmodell */
#define TASK_UNUSED  0
#define TASK_READY   1
#define TASK_RUNNING 2
#define TASK_SLEEP   3
#define TASK_ZOMBIE  4

#define KSTACK_SIZE  4096

struct cpu_context {
    uint64_t ra;      /* visszateresi cim */
    uint64_t sp;      /* kernel veremmutato */
    uint64_t s0;
    uint64_t s1;
    uint64_t s2;
    uint64_t s3;
    uint64_t s4;
    uint64_t s5;
    uint64_t s6;
    uint64_t s7;
    uint64_t s8;
    uint64_t s9;
    uint64_t s10;
    uint64_t s11;
};

struct task {
    uint64_t pid;
    int      state;
    uint64_t kernel_stack_top;
    struct cpu_context ctx;
    uint64_t user_pc;
    uint64_t user_sp;
    uint64_t satp;            /* hasznalt lapkeptabla, ha van MMU */
    uint64_t trapframe_ptr;   /* user->kernel belepesi munkaterulet */
    uint64_t quantum_left;    /* hatralevo idoszelet, tickben */
    struct task *next;
};

A cpu_context a callee-saved regisztereket tartalmazza. Ez a kiválasztás fontos: egy C függvényből hívott switch_to után a hívó csak azokat a regisztereket látja konzisztensnek, amelyeket a hívott függvénynek meg kell őriznie. A caller-saved regisztereket a kontextusváltást hívó kódnak nem kell külön mentenie, mert a C hívási konvenció szerint a hívó már elmentette őket, ha szüksége van rájuk.

A state mező a folyamatállapot-gépet írja le. A állapotátmenetek:

UNUSED -> READY        (letrehozas, init)
READY   -> RUNNING     (utemezo kivalasztja)
RUNNING -> READY       (idoszelet lejart)
RUNNING -> SLEEP       (rendszerhivas varakozasra kenyszeriti)
SLEEP   -> READY       (esemeny megerkezett)
RUNNING -> ZOMBIE      (kilepes)
ZOMBIE  -> UNUSED      (takaritas, szulo begyujtotte)

A kezdeti kernel a boot szakasz után létrehoz egy init feladatot, amely az első felhasználói programot futtatja. A további feladatok ebből a feladatból jönnek létre rendszerhívással, vagy a kernel indítja őket statikusan.

A feladatok egy egyszerű, körkörösen láncolt listában állnak. A round-robin ütemező ebből választja a következő TASK_READY állapotú elemet. A lista bejárása a legegyszerűbb esetben egy mutatóval történik, így a döntés komplexitása 𝒪(1)\mathcal{O}(1) amortizáltan, ha a lista hossza nem változik gyakran, és 𝒪(n)\mathcal{O}(n) a teljes bejárás, ha minden ciklusban a lista hosszát be kell járni. A gyakorlatban a lista hossza a záróprojektben nagyon kicsi, ezért a lineáris bejárás is elfogadható.

32.3.2 2. Timer interrupt és round-robin ütemezés

A round-robin ütemező alapja a hardveres időzítő megszakítása. A záróprojektben a QEMU virt gép CLINT (Core Local Interruptor) eszközét használjuk, amely periodikus megszakítást ad. A timer periódusát rendszerint 10 ms-ra állítjuk, de ez állítható. A konfiguráció a kernel/timer.c-ben történik:

/* timer.c – periodikus timer megszakitas beallitasa RISC-V CLINT */
void timer_init(void) {
    uint64_t interval = TIMER_INTERVAL; /* pl. 10 ms ciklusokban */
    uint64_t next = r_mtime() + interval;
    w_mtimecmp(next);
    /* a megszakitas engedelyezese a trap keretben tortenik */
}

A timer megszakítás kezelője tick-et ad. Ha az aktuális feladat quantum_left értéke eléri a nullát, a kernel beállítja a feladatot TASK_READY állapotba, és meghívja az ütemezőt:

void timer_interrupt_handler(void) {
    if (current && current->state == TASK_RUNNING) {
        current->quantum_left--;
        if (current->quantum_left == 0) {
            current->state = TASK_READY;
            schedule();
        }
    }
}

A schedule függvény kiválasztja a lista következő futtatható elemét, és ha az eltér az aktuálistól, kontextust vált:

void schedule(void) {
    struct task *next = pick_next_task();
    if (next && next != current) {
        struct task *prev = current;
        current = next;
        current->state = TASK_RUNNING;
        current->quantum_left = QUANTUM;
        switch_to(&prev->ctx, &current->ctx);
    }
}

A pick_next_task a lista első TASK_READY elemét adja. Ez biztosítja a körkörös továbbadást, ha a lista végén lévő mutatót mindig az aktuális feladatra állítjuk. A round-robin Gantt-diagramja három feladattal, 10 ms időkerettel:

P1: 0---10 30---40 60---70
P2: 10--20 40---50 70---80
P3: 20--30 50---60 80---90

Az átlagos várakozási idő ebben a példában, ha mindhárom feladat 10 ms-ot használ fel: P1P_1 0 ms, P2P_2 10 ms, P3P_3 20 ms, átlag 10 ms. A valóságban, ha egy feladat letiltja a megszakításokat vagy rendszerhíváson keresztül blokkol, az átlagos várakozási idő nő.

A kontextusváltás a kernel legalacsonyabb szintű része, ezért assemblyben írjuk. A RISC-V mentési és visszatöltési sorrendje:

# switch_to(a0 = &old_ctx, a1 = &new_ctx)
.globl switch_to
switch_to:
    sd ra, 0(a0)
    sd sp, 8(a0)
    sd s0, 16(a0)
    sd s1, 24(a0)
    sd s2, 32(a0)
    sd s3, 40(a0)
    sd s4, 48(a0)
    sd s5, 56(a0)
    sd s6, 64(a0)
    sd s7, 72(a0)
    sd s8, 80(a0)
    sd s9, 88(a0)
    sd s10, 96(a0)
    sd s11, 104(a0)

    ld ra, 0(a1)
    ld sp, 8(a1)
    ld s0, 16(a1)
    ld s1, 24(a1)
    ld s2, 32(a1)
    ld s3, 40(a1)
    ld s4, 48(a1)
    ld s5, 56(a1)
    ld s6, 64(a1)
    ld s7, 72(a1)
    ld s8, 80(a1)
    ld s9, 88(a1)
    ld s10, 96(a1)
    ld s11, 104(a1)
    ret

A ra és sp mentése/utolsó betöltése nem triviális: a ret a ra értékét használja, ezért a ra-t utoljára kell betölteni. A fenti sorrendben a ret előtt az ra már az új kontextus visszatérési címét tartalmazza. A sp pedig az új kernel veremre mutat.

Fontos tervezési döntés, hogy a kontextusváltás mindig kernel módból kernel módba történik. A felhasználói regiszterek mentését nem itt, hanem a trap belépésnél kell elvégezni. Ha a kernel a felhasználói feladatot timer interrupt miatt váltja, a felhasználói regisztereket a trapframe már tartalmazza. Ezért a task struktúrában lévő trapframe_ptr mutat erre a munkaterületre.

32.3.3 3. Trap belépés és rendszerhívás-dispatcher

A felhasználói programok futtatásához a kernelnek meg kell valósítania a user/kernel átlépést. RISC-V-n ez az ecall utasításon keresztül történik. A felhasználói program a syscall számot az a7 regiszterbe, az argumentumokat az a0–a5 regiszterekbe teszi, majd ecall-t hajt végre. A hardver átvált kernel módra, és a trap_vector-ben lévő kódra ugrik.

A trap belépés során a kernelnek el kell mentenie a felhasználói regisztereket egy trapframe struktúrába:

struct trapframe {
    uint64_t ra;
    uint64_t sp;
    uint64_t gp;
    uint64_t tp;
    uint64_t t0;
    uint64_t t1;
    uint64_t t2;
    uint64_t s0;
    uint64_t s1;
    uint64_t a0;
    uint64_t a1;
    uint64_t a2;
    uint64_t a3;
    uint64_t a4;
    uint64_t a5;
    uint64_t a6;
    uint64_t a7;
    uint64_t sepc;    /* visszateresi cim user modba */
    uint64_t sstatus; /* elozo privilégium szint */
};

A trap_vector assembly kód először a kernel stackre lép, elmenti a regisztereket, meghívja a C trap_handler függvényt, majd visszatöltve a regisztereket sret-tel visszalép user módba. A részletes assembly a os107-ben már bemutatásra került; itt a rendszerhívás-dispatcherre összpontosítunk.

A C oldali trap_handler megvizsgálja a megszakítás okát, és ha ecall-t észlel, a syscall_dispatch függvényt hívja:

void trap_handler(struct trapframe *tf) {
    uint64_t cause = r_scause();
    if (cause == SCAUSE_ECALL_USER) {
        syscall_dispatch(tf);
        tf->sepc += 4; /* RISC-V: továbblepunk az ecall utanira */
        return;
    }
    if (cause == SCAUSE_TIMER) {
        timer_interrupt_handler();
        return;
    }
    panic("ismeretlen trap ok");
}

A syscall_dispatch a rendszerhívási táblát használja. A tábla egy függvénypointer-tömb, ahol az index a syscall szám:

typedef int (*syscall_fn_t)(uint64_t, uint64_t, uint64_t,
                            uint64_t, uint64_t, uint64_t);

syscall_fn_t syscall_table[] = {
    [SYS_WRITE] = sys_write,
    [SYS_READ]  = sys_read,
    [SYS_EXIT]  = sys_exit,
    [SYS_FORK]  = sys_fork,   /* kesobb */
    [SYS_PS]    = sys_ps,
    [SYS_SLEEP] = sys_sleep,
};

void syscall_dispatch(struct trapframe *tf) {
    int nr = tf->a7;
    if (nr < 0 || nr >= ARRAY_SIZE(syscall_table) || !syscall_table[nr]) {
        tf->a0 = -ENOSYS;
        return;
    }
    tf->a0 = syscall_table[nr](tf->a0, tf->a1, tf->a2,
                               tf->a3, tf->a4, tf->a5);
}

A diszpécser feladata kettős: egyrészt a syscall számot ellenőrzi, másrészt a visszatérési értéket az a0 regiszterbe írja. A hibakódot az errno-hoz hasonlóan negatív értékként adjuk vissza. A felhasználói oldali libc-wrapper ezt lefordítja -1-re és beállítja az errno-t. Például:

/* user/lib/syscall.c */
ssize_t write(int fd, const void *buf, size_t n) {
    ssize_t ret = syscall(SYS_WRITE, fd, (uint64_t)buf, n, 0, 0, 0);
    if (ret < 0) {
        errno = -ret;
        return -1;
    }
    return ret;
}

A rendszerhívások sikeres végrehajtása nem írhatja felül a felhasználói memóriát ellenőrizetlenül. A sys_write például a felhasználói puffer címeit a kernel címfordítási tartományába kell konvertálnia, és meg kell vizsgálnia, hogy az adott tartomány valóban a felhasználóhoz tartozik. A minimális kernelben ez egy egyszerű határellenőrzés:

int sys_write(int fd, uint64_t user_buf, int n, ...) {
    if (fd != 1 && fd != 2) return -EBADF;
    if (n < 0 || user_buf + n > USER_TOP) return -EFAULT;
    char *buf = (char *)user_buf;
    for (int i = 0; i < n; i++) {
        uart_putc(buf[i]);
    }
    return n;
}

A valós kernelben a copy_from_user és a copy_to_user külön ellenőrzött másolást végez. Itt a cél a didaktikus szerkezet, nem a teljes biztonsági modell.

32.3.4 4. Init folyamat és felhasználói programok betöltése

A kernel inicializálása után az init feladat létrehozása a következő lépésekből áll:

  1. A kernel lefoglal egy task struktúrát és egy kernel stacket.
  2. Beállítja a feladat állapotát TASK_READY-re, a PID-et 1-re.
  3. A felhasználói belépési pontot user_pc-be teszi.
  4. A felhasználói stacket megfelelően beállítja.
  5. A feladatot hozzáadja az ütemező listához.
  6. A sret-hez szükséges sstatus mezőt user módba állítja.

Az init programot a kernelbe ágyazzuk, vagy egy egyszerű initrd-ből töltjük be. A záróprojektben a legegyszerűbb, ha a init bináris kódját a kernel ELF szekciójába linkeljük, és a kernel a init_start/init_end szimbólumokból másolja a felhasználói memóriába.

Példa a betöltésre:

void init_task_create(void) {
    struct task *t = alloc_task();
    t->pid = 1;
    t->state = TASK_READY;
    t->kernel_stack_top = alloc_kstack();
    t->user_pc = (uint64_t)init_entry;
    t->user_sp = USER_STACK_TOP;
    t->satp = kernel_satp; /* vagy user lapkeptabla */
    t->quantum_left = QUANTUM;
    list_add(&task_list, t);
}

A felhasználói init program a kernelben előre definiált ELF szimbólumként vagy egy egyszerű C függvényként szerepel, amelyet a kernel user módban indít el. A sret úgy tér vissza, hogy a PC az init_entry értékét veszi fel.

A init program első feladata, hogy létrehozza a shell folyamatot, majd várakozzon a gyermek folyamatok befejeződésére. A minimális kernelben a fork és wait rendszerhívásokat is implementálni kell. Ha a teljesség nem szükséges, a shell közvetlenül az init-ben is futtatható, de ez korlátozza a többfeladatos tesztelést. A laborban ezért fork és wait is szerepel.

Egy egyszerű fork implementáció:

int sys_fork(void) {
    struct task *child = copy_task(current);
    if (!child) return -ENOMEM;
    child->pid = next_pid++;
    child->state = TASK_READY;
    /* a gyermek visszateresi erteke 0 lesz */
    child->trapframe->a0 = 0;
    list_add(&task_list, child);
    return child->pid;
}

A copy_task le kell másolja a task struktúrát, a kernel stacket, a trapframe-et és a felhasználói memóriát. Ez a záróprojektben egyszerű fizikai másolással megoldható, ha a memóriakezelő rendelkezik memcpy-vel és a címek fizikailag azonosak. Ha lapozás aktív, a felhasználói lapokat is másolni kell, vagy COW-t kell alkalmazni. A laborban az egyszerűség kedvéért feltételezzük, hogy a lapozás még nem aktív, és a felhasználói memória fizikailag közvetlenül másolható.

32.3.5 5. Minimális shell

A shell egy felhasználói program, amely a szabványos bemenetről olvas, parancsokat értelmez, és a szabványos kimenetre ír. A minimális shell a következő parancsokat ismeri:

  • help: kiírja a parancsok listáját.
  • echo <szöveg>: visszaírja a szöveget.
  • ps: a kernel sys_ps hívásával listázza a feladatokat.
  • sleep <ms>: a sys_sleep hívásával várakozik.
  • shutdown: a sys_exit hívással leállítja a rendszert.

A shell kódja:

/* user/init.c */
void main(void) {
    char buf[128];
    while (1) {
        puts("$ ");
        int n = read(0, buf, sizeof(buf) - 1);
        if (n <= 0) {
            continue;
        }
        buf[n] = 0;
        if (strcmp(buf, "help") == 0) {
            puts("echo <text>  - kiirja a szoveget\n");
            puts("ps           - feladatok listazasa\n");
            puts("sleep <ms>   - varakozas\n");
            puts("shutdown     - leallitas\n");
        } else if (strncmp(buf, "echo ", 5) == 0) {
            puts(buf + 5);
            puts("\n");
        } else if (strcmp(buf, "ps") == 0) {
            ps();
        } else if (strncmp(buf, "sleep ", 6) == 0) {
            int ms = atoi(buf + 6);
            sleep(ms);
        } else if (strcmp(buf, "shutdown") == 0) {
            exit(0);
        } else {
            puts("ismeretlen parancs: ");
            puts(buf);
            puts("\n");
        }
    }
}

A shell működése bemutatja a rendszerhívások használatát: a read a SYS_READ-et, a puts a SYS_WRITE-et, a ps a SYS_PS-et, az exit a SYS_EXIT-et hívja. A fork-ot a shell indításakor a kernelben, vagy az init felhasználói programban használjuk.

A sys_ps implementációja a kernelben bejárja a feladatlistát, és a feladat állapotát egy belső pufferbe írja, amit a felhasználói program a SYS_PS hívással kérhet le. A kimeneti formátum egyszerű, például:

PID  STATE   PC
1    running 0x1000
2    ready   0x1000
3    sleep   0x1000

A shell tehát nem közvetlenül éri el a kernel adatszerkezeteit, hanem a rendszerhíváson keresztül kapja az adatokat. Ez a határ a tanulságos: a felhasználói program soha nem láthatja a PCB lista pointereit.

32.3.6 6. Hibakezelés és tipikus hibák

A fenti komponensek megvalósítása során több tipikus hibát kell elkerülni. A legfontosabbak:

  1. A trapframe nem mentett regiszterei. Ha a trap_vector nem menti el az összes felhasználói regisztert, a rendszerhívásból való visszatérés után a felhasználói program korrupt regisztereket lát. Ez a hiba gyakran csak bizonyos syscall-oknál jelentkezik, mert a compiler a többi regisztert nem használja abban a függvényben. A megoldás: a trapframe minden felhasználói regisztert tartalmazzon, és a mentés/visszatöltés szigorúan szimmetrikus legyen.

  2. A sepc nem növelése ecall után. Ha a syscall_dispatch után nem növeljük a sepc-t, a visszatérés újra ugyanazt az ecall-t hajtja végre, ami végtelen ciklust okoz. A hiba jellemző tünete, hogy a shell az első rendszerhívás után lefagy.

  3. A felhasználói mutatók ellenőrzésének hiánya. A kernelben a sys_read és sys_write közvetlenül használja a felhasználói címet. Ha a felhasználó rossz mutatót ad, a kernel saját memóriáját olvashatja vagy írhatja. Ezt a záróprojektben legalább tartományellenőrzéssel meg kell akadályozni. A teljes izolációhoz user page table és hardveres védelem szükséges.

  4. Versenyhelyzet a schedulerben. A schedule hívásakor a megszakításokat le kell tiltani, különben a timer interrupt a kontextusváltás közben újra beléphet. A kernelben a megszakítás-tiltás a r_sstatus SIE bitjének törlésével történik. A switch_to előtt le kell tiltani, utána pedig a visszatéréskor engedélyezni.

  5. Kernel stack túlcsordulás. A KSTACK_SIZE 4096 bájt elegendő a minimális kernelhez, de ha a fork vagy a sys_ps nagy helyi változót hoz létre, a stack átfolyhat. A hibát a kernel stack alján elhelyezett őrszem mezővel lehet észlelni, vagy egyszerűen a stack méretét kell növelni.

  6. A fork gyermek visszatérési értéke nem nulla. Ha a gyermek folyamat a fork-ból ugyanazzal a PID-del tér vissza, mint a szülő, a shell logikája elromlik. A copy_task után a gyermek trapframe->a0 értékét nullára kell állítani.

  7. A wait implementációja nem takarítja a ZOMBIE-t. Ha a wait nem felszabadítja a gyermek task struktúráját, a rendszer feladatlistája lassan megtelik TASK_ZOMBIE elemekkel, és a pick_next_task egyre lassabb lesz. A megoldás a wait-ben a gyermek erőforrásainak felszabadítása.

A teszteléshez a következő negatív eseteket érdemes beilleszteni:

  • Érvénytelen syscall szám hívása: a SYS_DISPATCH -ENOSYS-szel térjen vissza, ne panic-eljen.
  • A read hívása a shellben 0 byte hosszúsággal: a kernel ne lépjen ki.
  • A fork 100-szor egymás után: a rendszer ne telítse be a memóriát.
  • A sleep közben a timer interrupt akkor is működjön, ha az aktuális feladat TASK_SLEEP állapotba kerül.

32.3.7 7. Labor: round-robin ütemező, syscallok és shell

A labor célja, hogy a fenti komponenseket egy emulált környezetben összeállítsuk és mérjük. A labor a os123 állapotára épül, és a os125 számára előkészíti a fájlrendszer-integrációt.

32.3.8 7.1 Kiinduló állapot

  • QEMU virt gép, RISC-V 64, 128 MiB RAM, 1 CPU.
  • Kernel forráskódja a kernel/ könyvtárban.
  • Boot és memóriakezelés az os123-ból.
  • Buildrendszer: Makefile, linkerscript kernel.ld.
  • Debug eszköz: GDB, QEMU monitor.

32.3.9 7.2 Build és futtatási parancsok

# a kernel forditas
make clean
make ARCH=riscv64

# futtatas QEMU alatt
make run ARCH=riscv64

# debug inditas GDB-vel
make debug ARCH=riscv64

A make run a következő QEMU parancsot futtatja:

qemu-system-riscv64 -machine virt -m 128M -nographic \
  -bios none -kernel kernel.bin \
  -serial mon:stdio

A mérési naplóba rögzíteni kell a QEMU verzióját, a host CPU-t, az órajelét és a fordítási beállításokat. A példa mérési napló:

QEMU version: 8.2.0
Host CPU: AMD Ryzen 5 5600X, 3.7 GHz
Host OS: Debian 12, kernel 6.1.0
Compile flags: -O2 -g -ffreestanding -fno-common -march=rv64gc
Measurement method: rdcycle ciklusszámláló, 1000 minta atlaga

  2. Implementáld a timer megszakítást a timer.c-ben.

  4. Készítsd el a trap belépést és a trapframe mentést.

32.3.11 7.4 Elvárt eredmény

A boot után a soros konzolon a következő jelenik meg:

[KERN] boot successful
[INIT] starting shell
$ help
echo <text>  - kiirja a szoveget
ps           - feladatok listazasa
sleep <ms>   - varakozas
shutdown     - leallitas
$ echo Hello
Hello
$ ps
PID  STATE   PC
1    running 0x1000
2    ready   0x1000
$ sleep 100
$ shutdown

A ps kimenetben a PID 1 az init/shell, a PID 2 egy második folyamat lehet, amelyet a fork hozott létre. A pontos sorrend a shell indítási módjától függ.

32.3.12 7.5 Mérési napló

A mérés során a következő metrikákat rögzítjük:

  1. Context switch idő: a timer interrupt belépésétől a switch_to visszatéréséig eltelt ciklusok száma. Mérési módszer: a schedule elején rdcycle, a switch_to visszatérése után rdcycle. A különbséget naplózzuk. A tipikus érték QEMU rv64 alatt, 1 CPU-n, -O2 és -icount nélkül: 1000–2000 ciklus. A mért értéket a naplóban fel kell tüntetni, és a várt értéket külön oszlopban.

  2. Syscall költség: a syscall_dispatch belépésétől a visszatérésig. Mérés: a trap_handler elején és a sret előtt. A tipikus érték 500–1500 ciklus.

  3. Timer interrupt jitter: a timer megszakítások közötti idő ingadozása. Mérés: a timer_interrupt_handler minden hívásakor rdtime-et rögzítünk, és a szomszédos különbségek szórását számítjuk. A QEMU alatt a jitter általában néhány tíz ciklus, de a hoszt ütemezőtől függően nagyobb is lehet.

A mérési napló táblázata:

Mérés Módszer Várt érték Mért érték Megjegyzés
Context switch rdcycle < 2000 ciklus 1342 ciklus 1000 minta átlaga
Syscall rdcycle < 1500 ciklus 987 ciklus 1000 minta átlaga
Timer jitter rdtime < 100 ciklus 62 ciklus 1000 minta szórása

A mérési naplóban a mért és várt értéket külön kell jelölni. A várt érték a korábbi mérésekből vagy a hardver specifikációjából származik; a mért érték a tényleges futásból. Ha a mért érték jelentősen eltér, a naplóban meg kell vizsgálni a QEMU konfigurációját vagy a fordítási beállításokat.
