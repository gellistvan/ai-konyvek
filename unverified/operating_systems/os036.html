10.3 RCU, epoch-alapú visszanyerés és skálázható szinkronizáció

A fejezet az olvasó-optimális szinkronizáció és a skálázhatóság kapcsolatát tárgyalja, középpontban a read-copy-update (RCU) mechanizmussal, az epoch-alapú visszanyeréssel és a per-CPU adatokra épülő skálázható számlálással. Az előző egység (Lock-free és wait-free struktúrák) bevezette a lock-free és wait-free struktúrák alapjait; itt azt vizsgáljuk, hogyan érhető el nagy olvasási párhuzamosság anélkül, hogy az írók és az olvasók közös zárakon versengenének, és hogyan lehet a memória-visszanyerést biztonságosan megoldani akkor is, ha az olvasók nem használnak explicit lockot.

10.3.1 1. Olvasó-optimális szinkronizáció és skálázhatóság

A klasszikus szinkronizáció, például a reader-writer lock (rwlock), engedélyezi ugyan a többszörös párhuzamos olvasást, de az olvasók minden belépéskor növelik és kilépéskor csökkentik a lock belső számlálóját. Ez a művelet atomi, és a gyakorlatban a számláló cache-vonala a processzorok között folyamatosan ide-oda vándorol. Nagyszámú olvasó esetén a lock-számláló körüli cache-line bouncing lesz a szűk keresztmetszet, nem pedig a tényleges adatfeldolgozás. Hasonló jelenség figyelhető meg a mutex, spinlock és szemafór esetén is: a közös lock-változó minden olvasónál írást generál, ami a cache-koherencia protokoll szintjén drága.

Az olvasó-optimális szinkronizáció célja, hogy az olvasók egyáltalán ne végezzenek írást a közös szinkronizációs állapoton, sőt lehetőleg ne férjenek hozzá megosztott írásra jelölt cache-vonalhoz sem. Az ideális esetben egy olvasó csak olvassa az adatszerkezetet, semmilyen atomi utasítást nem hajt végre, és nem kell várakoznia. Az írók viszont vállalják a nagyobb költséget: másolják a módosítandó objektumot, frissítik a pointert, majd megvárják, amíg minden régi olvasó befejezi a munkáját, és csak ezután szabadítják fel a régi memóriát. Ez a trade-off akkor előnyös, ha az olvasási terhelés sokkal nagyobb, mint az írási.

A skálázhatóság azt méri, hogyan változik a teljesítmény a processzormagok számának növelésével. Egy jó skálázhatóságú szinkronizációs mechanizmusban az olvasási teljesítmény közel lineárisan nő a magok számával, mert az olvasók nem versengenek közös erőforrásért. Az írói oldal természetesen nem skálázódik ugyanígy, de mivel az írás ritka, a teljes rendszer áteresztőképessége jelentősen javul. A per-CPU adat és a skálázható számlálás további eszközöket ad arra, hogy a gyakran növelt számlálókat, statisztikákat és hasonló változókat se közös cache-vonalon tartsuk, hanem processzoronként elkülönítve.

10.3.2 2. A read-copy-update alapötlete

Az RCU három alappillére:

  1. Publish-subscribe (közzététel–feliratkozás): az író először elkészíti az új adatot, majd egyetlen pointer-cserével közzéteszi. Az olvasók mindig a régi vagy az új pointert látják, soha nem látnak félig frissített állapotot. A pointer-csere atomi kell legyen; a gyakorlatban ez egy egyszerű, megfelelően látható írás, például az rcu_assign_pointer a Linux kernelben.
  2. Grace period (türelmi időszak): az író a pointer-csere után megvárja, hogy minden olyan olvasó befejezze a régi adat használatát, aki a csere előtt kezdett olvasni. Ez az időtartam a grace period. Amikor a grace period lejár, garantált, hogy senki sem hivatkozik többé a régi objektumra.
  3. Reclaim (visszanyerés): a grace period után az író felszabadíthatja a régi objektumot.

A grace period meghatározásához az RCU figyeli a processzorok úgynevezett quiescent state (nyugalmi állapot) eseményeit. Egy CPU akkor van quiescent state-ben egy RCU olvasási kritikus szakasz szempontjából, ha nem tartózkodik ilyen szakaszban. A gyakorlatban a quiescent state jellemzően a felhasználói térbe való visszatérés, a kontextusváltás vagy az idle állapot. Ha minden CPU áthaladt egy quiescent state-en, és azóta nem lépett be újra RCU olvasási kritikus szakaszba, akkor a grace period lejárt.

Az RCU olvasói kritikus szakasza nagyon olcsó: az olvasó belép egy rcu_read_lock() hívásba, elvégzi az olvasást, majd kilép rcu_read_unlock() hívással. Ezek a hívások a legtöbb megvalósításban nem csinálnak mást, mint egy per-CPU vagy per-thread jelző beállítását, sokszor még csak nem is atomi műveletet. A kritikus szakaszban az olvasó nem blokkolhat, nem alhat el, nem végezhet ütemezést, mert az meggátolná a grace period befejeződését.

Az írói oldal ezzel szemben drágább:

  • synchronize_rcu(): blokkol, amíg a grace period le nem jár.
  • call_rcu(head, callback): regisztrál egy callbacket, amelyet a grace period után hívnak meg; az író nem blokkol.

A Linux kernelben az RCU-t széles körben használják: a dentry cache, a routing table, a fájlleíró táblák, a socket lookupek és sok más olvasás-nehéz adatszerkezet esetén.

10.3.3 2.1. Egyszerű példa: RCU-védett lista

Képzeljünk el egy linkelt listát, amelyet sok szál olvas, és ritkán módosítanak. A hagyományos megoldás egy rwlock lenne:

/* Hagyományos, szemléltető példa */
rwlock_t list_lock;
struct node *head;

struct node *list_lookup(int key) {
    read_lock(&list_lock);
    struct node *p = head;
    while (p) {
        if (p->key == key) {
            read_unlock(&list_lock);
            return p;
        }
        p = p->next;
    }
    read_unlock(&list_lock);
    return NULL;
}

Az olvasók itt a read_lock/read_unlock miatt közös lock-változót írnak, ami cache-line tranzakciókat generál.

RCU-val ugyanez:

/* RCU-alapú, szemléltető példa (pszeudokód) */
struct node *head;

struct node *list_lookup_rcu(int key) {
    rcu_read_lock();
    struct node *p = rcu_dereference(head);
    while (p) {
        if (p->key == key) {
            rcu_read_unlock();
            return p;
        }
        p = rcu_dereference(p->next);
    }
    rcu_read_unlock();
    return NULL;
}

Az olvasó itt rcu_dereference makrókat használ a pointerek olvasására, ami a compiler és a hardver memóriamodell szempontjából garantálja a megfelelő láthatóságot, de nem jár atomi utasítással. A rcu_read_lock és rcu_read_unlock a gyakorlatban gyakran egy-egy per-CPU maszkbit beállítása és törlése.

Az írói oldal:

/* Írói oldal: új elem beszúrása */
void list_insert_rcu(int key, int value) {
    struct node *new = kmalloc(sizeof(*new));
    new->key = key;
    new->value = value;
    new->next = head;
    rcu_assign_pointer(head, new);
    /* Nincs szükség grace periodra, mert a régi head még használatban van,
       de az új elem már elérhető. A régi objektumot csak akkor szabadítjuk fel,
       ha már senki sem olvashatja, például törléskor. */
}

Törléskor az író először kicsatolja az elemet a listából, majd megvárja a grace periodot, és csak azután szabadítja fel:

/* Írói oldal: elem törlése (pszeudokód) */
void list_delete_rcu(int key) {
    struct node *p = head;
    struct node *prev = NULL;
    while (p) {
        if (p->key == key) {
            if (prev)
                rcu_assign_pointer(prev->next, p->next);
            else
                rcu_assign_pointer(head, p->next);
            synchronize_rcu();
            kfree(p);
            return;
        }
        prev = p;
        p = p->next;
    }
}

A synchronize_rcu() hívás biztosítja, hogy a kicsatolás előtt indult olvasók befejezzék a munkájukat. Miután visszatért, garantált, hogy senki sem éri el a p pointert, így a kfree biztonságos. A gyakorlatban a synchronize_rcu() blokkolja az írót, ezért gyakran aszinkron call_rcu callbacket használnak.

10.3.4 3. Az RCU API és a szemantika

Bár a pontos API a Linux kernel verziójától és a felhasználói tér megvalósításától függ, a legfontosabb elemek a következők (a verziókat a felhasznált kernel vagy könyvtár dokumentációjában ellenőrizni kell):

  • rcu_read_lock() / rcu_read_unlock(): olvasói kritikus szakasz kezdete és vége. Nem blokkolhat, nem válthat kontextust, nem alhat.
  • rcu_dereference(p): az p pointer olvasása olyan módon, amely a compiler és a CPU számára megtiltja a nemkívánatos átmozgatást a kritikus szakasz fölé, és garantálja a megfelelő függőségi sorrendet.
  • rcu_assign_pointer(p, v): az v érték közzététele az p pointeren keresztül, megfelelő memória-sorompóval, hogy az olvasók a pointer frissítése előtt ne láthassák az adat korai inicializálását.
  • synchronize_rcu(): blokkol, amíg a grace period le nem jár. Alvó folyamatban hívható, de nem hívható atomikus kontextusból.
  • call_rcu(head, func): regisztrálja a func callbacket, amely a grace period után fut le. Aszinkron visszanyerésre való.

Az olvasói kritikus szakaszban csak olyan művelet szabad, amely nem szakítja meg a CPU-t, azaz nincs alvás, nincs preemptív ütemezés, nincs fájlrendszer-művelet, nincs olyan hívás, amely blokkolhat. A kernelben ezért az RCU olvasói szakaszokat gyakran úgy írják, hogy csak memóriaolvasásokat és egyszerű aritmetikát végeznek.

A grace period implementációja a Linux kernelben bonyolult, és többféle RCU-variáns létezik: Classic RCU, Tree RCU, Tiny RCU, Preemptible RCU, SRCU (sleepable RCU). A lényeg mindegyikben az, hogy a kernel nyilvántartja a processzorok quiescent state-jeit, és amikor minden CPU kilépett az RCU olvasói szakaszból, a grace period lezárul. A processzorfüggő maszkok per-CPU adatok, így maga a nyilvántartás is skálázható.

10.3.5 3.1. Példa: elem visszanyerése call_rcu-val

A synchronize_rcu() hívás blokkol, ami egy író szálat hosszú időre megállíthat. Ha az író nem akar várni, a call_rcu mechanizmust választja:

/* RCU callback-es törlés (pszeudokód) */
struct node {
    int key;
    int value;
    struct node *next;
    struct rcu_head rcu;
};

void node_free_callback(struct rcu_head *rh) {
    struct node *p = container_of(rh, struct node, rcu);
    kfree(p);
}

void list_delete_async_rcu(int key) {
    struct node *p = head;
    struct node *prev = NULL;
    while (p) {
        if (p->key == key) {
            if (prev)
                rcu_assign_pointer(prev->next, p->next);
            else
                rcu_assign_pointer(head, p->next);
            call_rcu(&p->rcu, node_free_callback);
            return;
        }
        prev = p;
        p = p->next;
    }
}

Itt az rcu_head mezőt minden elembe be kell ágyazni, és a callback a container_of makróval nyeri vissza a teljes objektumot. Ez a minta szinte minden RCU-t használó adatszerkezetben megjelenik.

10.3.6 4. Epoch-alapú visszanyerés

Az RCU grace periodja egy kernel-szintű, de nem mindig elérhető mechanizmus. Felhasználói térben a liburcu valósítja meg az RCU-t, de létezik egy egyszerűbb, általánosabb séma is, amelyet epoch-based reclamation (EBR) néven ismerünk. Az EBR az RCU-hoz hasonlóan a lock-free adatszerkezetek biztonságos memória-visszanyerését oldja meg úgy, hogy az olvasók nem használnak lockot, csak egy globális vagy per-thread epoch-számlálót.

Az EBR alapötlete:

  1. A rendszer fenntart egy globális epoch-értéket (általában 0, 1, 2 közötti körforgásban).
  2. Az olvasó belép egy kritikus szakaszba, amikor rögzíti az aktuális epochot a saját per-thread változójában.
  3. Az író, amikor törölni akar egy elemet, a régi elemet egy visszavonási listára helyezi, és megjelöli az aktuális epochhal.
  4. Amikor az összes olvasó elhagyta az adott epochot, az ehhez az epochhoz tartozó visszavonási listán lévő elemeket fel lehet szabadítani.
  5. Az epochok körben járnak, és az író csak akkor tud felszabadítani, ha a megfelelő epoch már nincs használatban.

Az EBR nem adja meg az RCU azon előnyét, hogy az olvasó valóban nulla overheadű; itt az olvasóknak is per-thread epoch-jelölőt kell írniuk. Azonban az írás per-thread, nem közös cache-vonal, ezért skálázódik. Az EBR-t gyakran használják lock-free listák és hash-táblák felhasználói térben.

Egyszerű pszeudokód:

/* EBR pszeudokód, szemléltetés */
#define EPOCH_COUNT 3
_Atomic int global_epoch = 0;
_Thread_local int local_epoch = 0;

void ebr_read_lock(void) {
    local_epoch = atomic_load(&global_epoch);
}

void ebr_read_unlock(void) {
    local_epoch = -1;
}

void ebr_retire(void *ptr, void (*reclaim)(void *)) {
    int e = atomic_load(&global_epoch);
    retire_list[e].push(ptr, reclaim);
    /* Ha minden szál kilépett az e epochból, felszabadítjuk a listát */
    if (all_threads_unused_epoch(e))
        reclaim_retire_list(e);
}

Az all_threads_unused_epoch ellenőrzéséhez a szálak epoch-jelölőit kell végignézni. Mivel ez ritkán történik, elfogadható a lineáris ellenőrzés. Az EBR tehát egyfajta könnyű alternatíva, ahol a grace period fogalmát az epochok váltása helyettesíti.

Az RCU és az EBR közös elve: az olvasó soha nem blokkol, és nem tartozik felelősséggel a memória-visszanyerésért; a visszanyerést az író oldal végzi, miután bizonyos, hogy nincs több olvasó. A különbség főleg a skálázhatóságban és a kernel/user tér elérhetőségében van.

10.3.7 5. Per-CPU adat és skálázható számlálás

A skálázhatóság másik fontos eszköze a per-CPU adat. Ahelyett, hogy minden processzor ugyanazt a globális változót írná, minden CPU saját példányt kap, és a saját példányán végez írást. A globális olvasás összegzi a per-CPU értékeket. Ez a minta drámaian csökkenti a cache-coherency forgalmat, mert minden CPU a saját cache-vonalát írja, amely ritkán kerül más CPU-hoz.

A Linux kernelben a per-CPU változókat a DEFINE_PER_CPU makróval lehet deklarálni, és a get_cpu_var() / put_cpu_var() vagy a this_cpu_inc() típusú műveletekkel elérni. A this_cpu_inc() például a futó CPU saját példányát növeli atomi utasítás nélkül, mert a preemptiót letiltja rövid időre. Az olvasáshoz a kernel for_each_possible_cpu ciklussal összegez.

Vegyünk egy egyszerű skálázható számlálót, amely egy adott esemény (pl. csomagszámláló) gyakoriságát méri:

/* Per-CPU számláló pszeudokód, C nyelv */
struct percpu_counter {
    int __percpu *counters;
    int threshold;
    int sum;
};

void percpu_counter_inc(struct percpu_counter *c) {
    this_cpu_inc(c->counters);
    if (this_cpu_read(c->counters) > c->threshold)
        percpu_counter_sync(c);
}

void percpu_counter_sync(struct percpu_counter *c) {
    int cpu;
    int total = 0;
    for_each_possible_cpu(cpu)
        total += per_cpu(c->counters, cpu);
    c->sum = total;
}

Az alapötlet az, hogy a triviaális növelés csak a saját CPU-t érinti, és csak a küszöb túllépésekor történik globális szinkronizáció. Ez a megközelítés az úgynevezett approximate counter (közelítő számláló) általánosítása. A pontosság és a globális szinkronizáció gyakorisága közötti trade-off a threshold paraméterrel hangolható. Ha a threshold 1, akkor minden növelés globális szinkronizációt vált ki, ami valójában egy hagyományos atomi számlálót eredményez. Ha a threshold nagy, a számláló ritkán pontos, de az írások nagyon olcsók.

A per-CPU adat nem csak számlálóknál hasznos. Gyakran tárolnak per-CPU cache-eket, processzor-specifikus állapotot, ütemező-statisztikát, interrupt-számlálót, vagy épp az RCU quiescent state nyilvántartását. A tervezésnél figyelni kell a false sharing elkerülésére: a per-CPU változókat úgy kell elhelyezni, hogy minden CPU adata külön cache-vonalra kerüljön. A gyakorlatban ezt a kernel- vagy a liburcu implementációk cache-line alignmenttel oldják meg.

A per-CPU adat és az RCU kombinációja erőteljes: például egy RCU-védett listába bejáró olvasó a lista elemeit olvassa, miközben a statisztikákat per-CPU számlálókkal gyűjti. Az olvasónak nincs lockja, nincs közös írása, és a per-CPU számláló növelése is csak a saját cache-vonalát érinti.

10.3.8 6. Tipikus hibák és helyes megoldások

Az RCU és a per-CPU adat használata során a leggyakoribb hibák a következők:

  1. Alvás az RCU olvasói kritikus szakaszban. Ha az olvasó rcu_read_lock() és rcu_read_unlock() között alvó függvényt hív (pl. kmalloc GFP_KERNEL flaggel egy bizonyos környezetben, vagy fájlrendszer-művelet), akkor a kernel preemptív kontextusban lehet, és a grace period soha nem fejeződik be. Helyes megoldás: csak nem blokkoló műveletet végezni; ha blokkolás kell, használjuk az SRCU-t, amely engedélyezi az alvást, de drágább.

  2. A régi objektum túl korai felszabadítása. Ha az író a pointer-csere után azonnal kfree-t hív anélkül, hogy megvárná a grace periodot, akkor a még futó olvasók felszabadított memóriát olvashatnak. Helyes megoldás: synchronize_rcu() vagy call_rcu().

  3. A pointer-közzététel hiányos memória-sorompója. Ha az író közönséges C-pointerírást használ az rcu_assign_pointer helyett, a compiler vagy a CPU átrendezheti a műveleteket, és az olvasó félig inicializált objektumot láthat. Helyes megoldás: mindig a megfelelő RCU makrót használni.

  4. Per-CPU adat atomitásának feltételezése. A per-CPU adat csak a saját CPU-ján érhető el atomosan; ha egy másik CPU közvetlenül írja, versenyhelyzet keletkezik. Helyes megoldás: minden CPU csak a saját per-CPU példányát módosítsa, a globális metszeteket pedig short lockkal vagy atomi művelettel védjük.

  5. False sharing a per-CPU adatnál. Ha a per-CPU változók osztoznak egy cache-vonalon, akkor hiába van per-CPU, a közös cache-vonal miatt mégis cache-line bouncing lép fel. Helyes megoldás: cache-line alignment, ____cacheline_aligned típusú attribútum.

  6. A grace period hosszának alulbecslése. Az írók a synchronize_rcu() hívás alatt blokkolnak, ami hosszú lehet, ha sok olvasó van lassú kritikus szakaszban. Helyes megoldás: aszinkron call_rcu callback használata, vagy az adatszerkezet módosításának olyan szervezése, hogy a grace periodra ritkán legyen szükség.

10.3.9 7. Labor: RCU-alapú lista tervezése és mérése

Ez a labor egy felhasználói térben futó RCU-védett linkelt lista tervezését és teljesítménymérését írja le. A környezet QEMU-ban futtatott minimalista Linux, amelyben a liburcu könyvtár elérhető. A cél az olvasó-optimális szinkronizáció és a skálázhatóság bemutatása. A labor során mért és várt eredményt külön kell kezelni, és a mérési naplóban rögzíteni.

10.3.10 7.1. Kiinduló állapot és eszközök

  • Emulált környezet: QEMU 7.x (a pontos verzió a reprodukciós csomagban ellenőrizendő), 4 vCPU, 4 GiB RAM, virtio-blk háttértár.
  • Operációs rendszer: Linux 6.1 (a pontos verzió ellenőrizendő), liburcu-dev csomag telepítve.
  • Fordító: GCC 12, -O2 -march=native (az emulált CPU esetén a natív itt az emulált CPU-t jelenti), -pthread -lurcu -lurcu-qsbr szükség szerint.
  • A labor kódja egy eldobható könyvtárban készül, a hoszt valódi fájljait nem módosítjuk.

10.3.11 7.2. Az adatszerkezet

Egy egyirányú linkelt lista, amelyet a szálak keresnek. A lista elemei RCU-védettek. A benchmark három változatot hasonlít össze:

  • rwlock lista: hagyományos pthread_rwlock_t-vel védett lista.

10.3.12 7.3. A kód vázlata

A következő pszeudokód a liburcu API-t használja. A pontos függvényneveket és fejlécet a telepített liburcu verziójához igazítva ellenőrizni kell.

/* RCU-védett lista, liburcu példa (pszeudokód, verziófüggő) */
#include <urcu.h>
#include <stdlib.h>
#include <stdio.h>
#include <pthread.h>
#include <stdatomic.h>

struct node {
    int key;
    int value;
    struct node *next;
    struct rcu_head rcu;
};

struct node *head = NULL;

void rcu_free_cb(struct rcu_head *rh) {
    struct node *p = caa_container_of(rh, struct node, rcu);
    free(p);
}

void list_insert(int key, int value) {
    struct node *n = malloc(sizeof(*n));
    n->key = key;
    n->value = value;
    n->next = rcu_dereference(head);
    rcu_assign_pointer(head, n);
}

void list_delete(int key) {
    struct node *p = rcu_dereference(head);
    struct node *prev = NULL;
    while (p) {
        if (p->key == key) {
            if (prev)
                rcu_assign_pointer(prev->next, p->next);
            else
                rcu_assign_pointer(head, p->next);
            call_rcu(&p->rcu, rcu_free_cb);
            return;
        }
        prev = p;
        p = rcu_dereference(p->next);
    }
}

void *reader_thread(void *arg) {
    (void)arg;
    for (int i = 0; i < 1000000; i++) {
        rcu_read_lock();
        struct node *p = rcu_dereference(head);
        while (p) {
            if (p->key == i % 1000) {
                rcu_read_unlock();
                break;
            }
            p = rcu_dereference(p->next);
        }
        rcu_read_unlock();
    }
    return NULL;
}

A többi szál hasonló. A per-thread számláló bevezetéséhez egy _Thread_local változót használunk, amelyet az olvasó kritikus szakaszon kívül növelünk.

10.3.14 7.5. Elvárt és mért eredmény

A várt eredmény az, hogy az RCU lista olvasási sebessége jelentősen meghaladja az rwlock lista sebességét, mert az RCU olvasók nem írják a közös lockot. 4 magon a skálázhatóság közel lineáris, míg az rwlock esetében a cache-line bouncing korlátozza a párhuzamosságot. A mérés ezt vagy megerősíti, vagy eltérést mutat, amelyet a naplóban dokumentálni kell. A per-thread számláló további kis javulást hozhat a statisztikai utakban.

10.3.16 8. Összefoglalás

Az RCU, az epoch-alapú visszanyerés és a per-CPU adat az olvasó-optimális szinkronizáció és a skálázhatóság három alappillére. Az RCU lehetővé teszi, hogy az olvasók szinte nulla költséggel férjenek hozzá a megosztott adatszerkezethez, miközben az írók a grace period lejárta után biztonságosan visszanyerik a memóriát. Az EBR hasonló célt szolgál felhasználói térben, epochok és per-thread jelölők segítségével. A per-CPU adat és a skálázható számlálás további skálázhatósági nyereséget ad azáltal, hogy elkerüli a globális cache-vonalak írását. A tipikus hibák, mint az alvás a kritikus szakaszban, a túl korai visszanyerés vagy a false sharing, mind elkerülhetők a megfelelő makrók és cache-line alignment következetes használatával. A következő egység (Többmagos és heterogén rendszerek kihívásai) ezeket az elveket alkalmazza többmagos és heterogén rendszerekre, ahol a skálázhatóság és a hardver-specifikus kihívások még hangsúlyosabbá válnak.
