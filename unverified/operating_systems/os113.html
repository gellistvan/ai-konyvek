29.4 Shell és alapszolgáltatások

A minimális userland nem attól működik, hogy a kernel mindent el tud végezni; attól válik használhatóvá, hogy a felhasználói térben néhány apró, jól megírt program a fájlleírókat, a folyamatokat és a környezeti állapotot a POSIX-elvárásokhoz hasonlóan kezeli. Az os112 alfejezetben felépítettük a VFS-t és a fájlleíró réteget. Most arra a rétegre egy parancsértelmezőt és a hozzá tartozó alapszolgáltatásokat helyezünk. A kernel továbbra is ugyanaz marad: rendszerhívásokat ad, a munka nagy része a userlandben történik.

29.4.1 1. Mi a minimális userland?

A userland az operációs rendszer azon része, amely nem fut privilegizált módban. Egy minimális, oktatási célú rendszerben a userland általában a következőkből áll:

  • egy indító program (init vagy sh közvetlenül),
  • a rendszerhívások vékony C-burkolói (a libc helyett egy syscalls.h és syscalls.c),
  • egy parancsértelmező (shell),
  • néhány alapvető segédprogram (például cat, echo, ls, mkdir, rm),
  • szükség esetén egy-két eszközfájl (/dev/console, /dev/null) és a /bin könyvtár.

A cél az, hogy a rendszer elindulása után a felhasználó vagy a tesztkörnyezet parancsokat tudjon kiadni, scripteket tudjon futtatni, és ellenőrizni tudja a fájlrendszer, illetve a folyamatok működését.

A shell nem kernelkomponens. Ugyanolyan felhasználói program, mint a cat vagy a ls; annyi különbséggel, hogy a felhasználó által begépelt sorokat parancsokká alakítja, majd ezeket más programok futtatásával hajtja végre. Ez a kialakítás azért fontos, mert a parancsok nagy része nem a shell kódjában él, hanem külön futtatható fájlokban. A shell feladata a „társalgás” a felhasználóval és a folyamatok összekapcsolása.

29.4.2 2. A shell indítása és a fő ciklus

A minimális rendszer bootolás után, az os103 és os104 alfejezetekben leírt kernel-inicializálást követően elindítja az első felhasználói folyamatot. A leggyakoribb választás: a kernel megnyitja a /bin/sh fájlt, futtathatóvá teszi, majd átadja neki a konzolt mint szabványos be- és kimenetet. A shell ezután a következő ciklust futtatja:

  1. promptot ír a szabványos kimenetre;
  2. beolvas egy sort a szabványos bemenetről;
  3. a sort tokenekre bontja;
  4. ha beépített parancs, akkor közvetlenül végrehajtja;
  5. egyébként létrehoz egy gyermekfolyamatot, amely betölti a megfelelő programot;
  6. a szülő megvárja a gyermeket, majd kiértékeli a kilépési állapotot;
  7. visszatér az 1. lépésre.

Ezt mutatja a következő, szándékosan lecsupaszított C-vázlat. A kód nem éles rendszerre való, hanem a fejezetben épített emulált környezethez.

/* user/sh.c – minimális shell szemléltető vázlata */
#include "syscalls.h"

#define MAX_LINE 128
#define MAX_ARGS 16

static char line[MAX_LINE];
static char *argv[MAX_ARGS + 1];

int main(int argc, char **argv)
{
    (void)argc;
    (void)argv;

    for (;;) {
        ssize_t n;

        write(STDOUT_FILENO, "mini$ ", 6);

        n = read(STDIN_FILENO, line, sizeof(line) - 1);
        if (n <= 0) {
            /* EOF vagy hiba: a shell kilép */
            return n == 0 ? 0 : 1;
        }
        line[n] = '\0';

        if (tokenize(line, argv, MAX_ARGS) < 0) {
            write(STDERR_FILENO, "sh: túl sok argumentum\n", 23);
            continue;
        }

        if (argv[0] == NULL) {
            /* üres sor */
            continue;
        }

        if (run_builtin(argv) == 1) {
            continue;
        }

        if (run_external(argv) < 0) {
            /* run_external már kiírta a hibát */
        }
    }
}

A tokenize egyelőre csak a whitespace-ek mentén vág szét; a gyakorlatban a minimális shell is támogathatja a "..." és '...' idézést, illetve a \ escape-et. A laborban érdemes az idézést legalább alapszinten implementálni, mert enélkül a fájlnevekben lévő szóközök nem kezelhetők. A tokenize visszatérési értéke a tokenek száma lehet, hibánál -1; a példában -1 a túl hosszú sort jelzi.

29.4.3 3. Belső és külső parancsok

A shell parancsai két csoportba sorolhatók.

  • Belső parancsok (builtin): olyan parancsok, amelyek a shell saját processzét módosítják, vagy nem éri meg külön folyamatként futtatni őket. Például:
    • cd <útvonal> – a munkakönyvtár megváltoztatása; ha ezt külön folyamat tenné, a változás nem lenne hatással a szülő shellre.
    • exit [kód] – a shell kiléptetése.
    • export NÉV=ÉRTÉK – környezeti változó beállítása.
    • pwd – az aktuális munkakönyvtár kiírása.
    • help – a rendelkezésre álló belső parancsok listája.
  • Külső parancsok: önálló futtatható fájlok, például /bin/cat, /bin/ls. Ezeket a shell fork + execve + waitpid hármassal futtatja. A /bin könyvtárban lévő programok a minimális userland részét képezik.

A shell cd parancsának belső volta klasszikus hibaforrás. Ha valaki úgy próbálja megvalósítani, hogy fork után a gyermekben meghívja a chdir-t, akkor a gyermek munkakönyvtára megváltozik, de a szülőé nem; a shell a következő promptnál ugyanott marad, ahonnan indult. Ezért a cd-t a shell saját folyamatában kell végrehajtani.

A belső parancsok vázlata:

int run_builtin(char **argv)
{
    if (strcmp(argv[0], "cd") == 0) {
        const char *path = argv[1] ? argv[1] : "/";
        if (chdir(path) < 0) {
            perror("cd");
        }
        return 1; /* kezelve */
    }

    if (strcmp(argv[0], "exit") == 0) {
        int code = argv[1] ? atoi(argv[1]) : 0;
        exit(code);
    }

    if (strcmp(argv[0], "export") == 0) {
        if (argv[1] && strchr(argv[1], '=')) {
            setenv(argv[1]);
        } else {
            write(STDERR_FILENO, "használat: export NÉV=ÉRTÉK\n", 29);
        }
        return 1;
    }

    if (strcmp(argv[0], "pwd") == 0) {
        char buf[256];
        if (getcwd(buf, sizeof(buf)) == NULL) {
            perror("pwd");
        } else {
            write(STDOUT_FILENO, buf, strlen(buf));
            write(STDOUT_FILENO, "\n", 1);
        }
        return 1;
    }

    return 0; /* nem belső parancs */
}

Itt a chdir, a getcwd, a setenv és a strcmp a minimális libc-ből, illetve a rendszerhívás-burkolókból származnak. A tényleges implementáció a laborban az os112-ben már elkészített VFS-re épül.

29.4.4 4. Külső program futtatása: fork, execve, waitpid

A külső parancsok futtatása a folyamatkezelés három rendszerhívását használja.

29.4.5 fork

pid_t fork(void);

A fork létrehozza a hívó folyamat másolatát. A gyermek a hívás után a 0 értéket kapja vissza, a szülő a gyermek pozitív folyamatazonosítóját. Hibánál -1 a visszatérési érték, és a kernol az errno-t beállítja; tipikus értékek:

  • EAGAIN – nincs elég memória vagy elértük a folyamatszám-korlátot;
  • ENOMEM – a folyamattábla vagy a verem allokációja sikertelen.

A shell ezt használja arra, hogy a gyermekben lecserélje a programképet.

29.4.6 execve

int execve(const char *pathname, char *const argv[], char *const envp[]);

Az execve betölti a pathname fájlt, beállítja az argumentumlistát és a környezetet, majd lecseréli az aktuális folyamat címterét. Sikeres hívás nem tér vissza. Hiba esetén -1-gyel tér vissza, és az errno tartalmazza az okot. A leggyakoribb okok:

  • ENOENT – a fájl vagy egy PATH-elem nem létezik;
  • EACCES – nincs végrehajtási jog;
  • ENOEXEC – a fájl nem futtatható formátumú, vagy nincs érvényes fejléc;
  • E2BIG – az argumentumlista, a környezet vagy mindkettő túl nagy;
  • EFAULT – a felhasználói mutatók érvénytelenek.

A minimális rendszerben az execve a VFS open rétegén keresztül olvassa a fájlt, ellenőrzi az ELF-fejlécet, betölti a szegmenseket, beállítja a vermet, és az entry pontra ugrik. A shellnek a gyermekben az execve hiba után azonnal _exit(127)-et kell hívnia, különben a gyermek a shell kódját futtatná tovább, és egy második shellt indítana.

29.4.7 waitpid

pid_t waitpid(pid_t pid, int *_Nullable wstatus, int options);

A waitpid a szülőt várakoztatja a megadott gyermek befejeződésére. A wstatus mutató egy bitmezőt kap, amelyből a shell megállapíthatja a kilépés módját:

  • WIFEXITED(wstatus) igaz, ha a gyermek normálisan fejeződött be; ekkor WEXITSTATUS(wstatus) adja a kilépési kódot.
  • WIFSIGNALED(wstatus) igaz, ha a gyermeket szignál állította le; a shell ilyenkor 128 + jel kódot szokott visszaadni.

A shell run_external függvénye ezt a hármast foglalja össze:

int run_external(char **argv)
{
    char path[128];
    pid_t pid;
    int status;

    if (find_in_path(argv[0], path, sizeof(path)) < 0) {
        write(STDERR_FILENO, "sh: parancs nem található: ", 27);
        write(STDERR_FILENO, argv[0], strlen(argv[0]));
        write(STDERR_FILENO, "\n", 1);
        return -1;
    }

    pid = fork();
    if (pid < 0) {
        perror("fork");
        return -1;
    }

    if (pid == 0) {
        /* gyermek: program betöltése */
        execve(path, argv, environ);
        /*
         * Ide csak akkor jutunk, ha az execve hibázott.
         * A _exit megakadályozza, hogy a gyermek
         * a shell kódját futtassa tovább.
         */
        perror("execve");
        _exit(127);
    }

    /* szülő: várakozás a gyermekre */
    if (waitpid(pid, &status, 0) < 0) {
        perror("waitpid");
        return -1;
    }

    return report_status(status);
}

A find_in_path a shell saját segédfüggvénye. A PATH környezeti változót kettőspontok mentén bontja fel, és minden elemből útvonal/parancsnév jelöltet készít. A minimális rendszerben a PATH általában /bin:/usr/bin. A find_in_path megpróbálhatja az open-t O_RDONLY módban minden jelöltre; ha a fájl létezik, visszaadja az elérési utat. A végrehajthatósági bit ellenőrzése a VFS-ben és az execve-ben történik.

Az argumentumok átadása POSIX-konvenció szerint történik: argv[0] a program neve, argv[1] az első parancssori argumentum, és az argv tömb végét NULL jelöli. A shellnek ügyelnie kell arra, hogy a NULL lezáró elem elférjen, ezért a MAX_ARGS tömb mérete MAX_ARGS + 1.

29.4.8 5. Pipe és átirányítás

A shell igazi erejét a folyamatok közötti csővezetékek és a fájlba irányítások adják. A | karakter két parancsot köt össze: a bal oldali parancs szabványos kimenetét a jobb oldali szabványos bemenetére irányítja. Ehhez a kernel pipe rendszerhívását használjuk.

29.4.9 pipe

int pipe(int pipefd[2]);

A pipe egy csővezetéket hoz létre. A pipefd[0] az olvasó vég, a pipefd[1] az író vég. A csőben lévő adatok a kernel memóriájában tárolódnak; amíg van nyitott író vég, az olvasó blokkol, ha a cső üres; amikor az összes író vég bezáródik, az olvasó read hívása 0-t ad vissza, ami EOF-ot jelez. A minimális rendszerben a pipe puffer mérete például 4096 bájt lehet; a labor mérésénél ezt érdemes rögzíteni.

A csővezeték végrehajtásához a shell két gyermekfolyamatot hoz létre. A dup2 rendszerhívás segítségével a cső megfelelő végét a STDOUT_FILENO, illetve a STDIN_FILENO fájlleíróra másolja.

29.4.10 dup2

int dup2(int oldfd, int newfd);

A dup2 a newfd fájlleírót az oldfd-re mutató nyitott fájlleíró-másolatává teszi. Ha a newfd korábban nyitva volt, a kernel először bezárja. A shell ezt az átirányításoknál használja:

  • > fájl esetén: open("fájl", O_CREAT|O_WRONLY|O_TRUNC, 0644), majd dup2(fd, STDOUT_FILENO).
  • >> fájl esetén: O_CREAT|O_WRONLY|O_APPEND.
  • < fájl esetén: open("fájl", O_RDONLY), majd dup2(fd, STDIN_FILENO).

A pipe-os példa vázlata:

int run_pipeline(char **left_argv, char **right_argv)
{
    int fd[2];
    pid_t left, right;
    int left_status, right_status;

    if (pipe(fd) < 0) {
        perror("pipe");
        return -1;
    }

    left = fork();
    if (left < 0) {
        perror("fork");
        close(fd[0]);
        close(fd[1]);
        return -1;
    }

    if (left == 0) {
        /* bal oldali gyermek: írás a csőbe */
        close(fd[0]);
        if (dup2(fd[1], STDOUT_FILENO) < 0) {
            perror("dup2");
            _exit(1);
        }
        close(fd[1]); /* a dup2 után az eredeti felesleges */
        execve(left_path, left_argv, environ);
        perror("execve");
        _exit(127);
    }

    right = fork();
    if (right < 0) {
        perror("fork");
        close(fd[0]);
        close(fd[1]);
        return -1;
    }

    if (right == 0) {
        /* jobb oldali gyermek: olvasás a csőből */
        close(fd[1]);
        if (dup2(fd[0], STDIN_FILENO) < 0) {
            perror("dup2");
            _exit(1);
        }
        close(fd[0]);
        execve(right_path, right_argv, environ);
        perror("execve");
        _exit(127);
    }

    /*
     * Kulcsfontosságú lépés: a szülőnek mindkét csővéget
     * be kell zárnia. Különben a jobb oldali gyermek a
     * pipe EOF-ját soha nem látja, mert a szülőben nyitva
     * maradt az író vég.
     */
    close(fd[0]);
    close(fd[1]);

    waitpid(left, &left_status, 0);
    waitpid(right, &right_status, 0);

    return WIFEXITED(right_status) ? WEXITSTATUS(right_status) : 1;
}

A fenti kódban a left_path és a right_path kiszámítását a find_in_path végzi. A close(fd[0]) és close(fd[1]) a szülőben lévő felesleges fájlleírókat szünteti meg. Ez az egyik leggyakoribb hibaforrás: ha a szülő nem zárja be a cső író végét, a jobb oldali folyamat a read-ben örökre blokkolhat, mert az író vég sosem záródik be a szülő miatt.

A shell parser először a | és az átirányítási karakterek mentén bontja fel a sort. Az átirányítások elvileg tetszőleges sorrendben előfordulhatnak:

cat < /etc/motd | head > /tmp/elso_sor

Itt a bal oldali parancs bemenetét a /etc/motd fájlból, a jobb oldali parancs kimenetét a /tmp/elso_sor fájlba kell irányítani. A minimális shell kezdetben megelégedhet azzal, hogy a > és < jeleket egyetlen parancs után keresi, és a | jelet legfeljebb egyszer támogatja. A laborban ez elegendő a gyakorlati célhoz.

29.4.11 6. Környezeti változók és környezet átadása

A UNIX-szerű rendszerekben minden folyamat rendelkezik egy környezeti blokkal, amely NÉV=ÉRTÉK formájú sztringekből áll. A shell indulásakor ezt a blokkot a kerneltől kapja. A C-kódban a environ globális mutató hivatkozik rá:

extern char **environ;

A fork a gyermeknek ugyanazt a környezetet adja. Az execve harmadik paramétere a környezet; a shell a run_external és a run_pipeline hívásokban a saját environ mutatóját adja át. Ha a shell export parancsot kap, akkor a saját környezeti blokkját módosítja, és ez a változás a később indított gyermekekre is érvényes lesz.

A minimális setenv a következőket teheti:

  • megkeresi az adott névhez tartozó bejegyzést,
  • ha létezik, lecseréli az értéket,
  • ha nem létezik, új bejegyzést fűz a tömbhöz.

A környezeti tár mérete korlátozott; a laborban érdemes 32 vagy 64 bejegyzést engedélyezni, és a túlcsordulást -1 visszatéréssel jelezni.

A leggyakrabban használt környezeti változók:

  • PATH – a külső parancsok keresési útvonala;
  • HOME – a felhasználó otthoni könyvtára;
  • USER vagy LOGNAME – a felhasználónév;
  • PWD – az aktuális munkakönyvtár (informatív jelleggel; a tényleges állapotot a kernel tartja).

A shellnek a PATH-ot minden külső parancs előtt be kell olvasnia. Ha a felhasználó megváltoztatja a PATH-ot, a változásnak a következő parancsra már érvényesülnie kell. A biztonság szempontjából fontos, hogy a PATH-ba ne kerüljön a . (aktuális könyvtár) implicit módon; a minimális rendszerben ezt csak akkor vegyük fel, ha a felhasználó kifejezetten beállította.

29.4.12 7. Hibakódok, errno és kilépési állapot

A rendszerhívások hibáinak kezelése a userlandben két szinten történik.

A C-szinten a burkolók visszaadják a -1 értéket, és beállítják a errno nevű globális változót. A perror vagy a strerror segítségével a hiba szöveges leírása kiírható. A perror a hívás előtti szöveget, kettőspontot és az errno-hoz tartozó üzenetet írja a szabványos hibakimenetre. A minimális libc-ben a strerror csak a leggyakoribb hibakódokat ismerheti; a laborban legalább az ENOENT, EACCES, ENOMEM, EBADF, EINVAL, EIO és EEXIST kódokat érdemes leképezni.

A shell szintjén a kilépési állapot a következő:

  • 0 – sikeres végrehajtás;
  • 1 – általános hiba;
  • 2 – helytelen parancssori használat;
  • 127 – a parancs nem található, vagy az execve hibázott;
  • 128 + N – a folyamatot az N számú szignál állította le.

A shell a $? belső változóban tárolja az utolsó parancs kilépési állapotát. Ez a scripting alapja: egy script megvizsgálhatja, hogy az előző parancs sikeres volt-e.

A report_status függvény a waitpid által adott wstatus értéket alakítja át:

int report_status(int wstatus)
{
    if (WIFEXITED(wstatus)) {
        return WEXITSTATUS(wstatus);
    }
    if (WIFSIGNALED(wstatus)) {
        return 128 + WTERMSIG(wstatus);
    }
    return 1;
}

A shell a promptnál az utolsó kilépési állapotot a $? kérdésre adott válaszként jeleníti meg. A minimális megvalósításban ezt a változót a shell a run_external vagy a run_pipeline visszatérési értékéből frissíti.

29.4.13 8. Scripting a minimális userlandben

A shellscriptek használata akkor válik lehetővé, ha a rendszer két dolgot támogat:

  1. a futtatható szövegfájlokat a kernel vagy a shell interpreterhez tudja kötni;
  2. a shell képes soronként értelmezni egy fájlt, nem csak az interaktív bemenetet.

A hagyományos UNIX-rendszerekben az execve a fájl első két bájtját ellenőrzi. Ha azok #! karakterek, a kernel a második sorban megadott interpretert indítja el, és átadja neki a script elérési útját. A minimális rendszerben erre két lehetőség van:

  • a kernel execve-je felismeri a #!-et, és az interpreter programot tölti be;
  • a shell érzékeli, hogy a fájl nem bináris, hanem szöveges script, és maga olvassa be, majd soronként végrehajtja.

Az oktatási célú rendszerben gyakran a második megoldás az egyszerűbb, mert nem igényel kernelváltoztatást. Ekkor a shell source vagy közvetlenül a fájlnevet kapja argumentumként, és a read ciklust a szabványos bemenet helyett egy fájlból futtatja.

Egy minimális script:

#!/bin/sh
# laborbemutató.sh – nem éles rendszerre
echo "Mini OS shell indítása"
mkdir -p /tmp/log
cat /etc/motd > /tmp/log/motd_masolat
if [ $? -eq 0 ]; then
    echo "mentés sikeres"
else
    echo "mentés sikertelen"
fi

A mkdir -p az EEXIST hibát is elfogadja, ha a könyvtár már létezik. A [ parancs a minimális rendszerben lehet önálló program vagy a shell beépített feltételkezelése; a laborban elegendő a $? ellenőrzését és egyszerű if-et bevezetni. A script futtatása közben a shell a sorokat ugyanúgy tokenizálja, mint az interaktív módban, ezért a kód újrahasznosítható.

A script futtatásának lépései:

  1. a shell open-nel megnyitja a scriptfájlt;
  2. ha a fájl #!-tel kezdődik, az interpretert beazonosítja, és a scriptfájlt argumentumként átadva fork + execve segítségével elindítja;
  3. a kiválasztott interpreter a fájl tartalmát feldolgozza;
  4. a script kilépési állapota az interpreter kilépési állapota lesz.

A laborban a shell sh script.sh formában futtathat scripteket; ez kiváltja a kernel shebang-támogatását, és a shell maga olvassa be a fájlt.

29.4.14 9. Alapszolgáltatások: cat, echo, ls, mkdir, rm

A minimális userland néhány apró, jól körülhatárolt programot tartalmaz. Mindegyik ugyanazokat a rendszerhívásokat használja, mint a shell, így a VFS és a fájlleíró réteg egységesen tesztelhető.

29.4.15 cat

A cat a megadott fájlok tartalmát másolja a szabványos kimenetre. Ha nincs argumentum, a szabványos bemenetet olvassa. A megvalósítás kulcsa a read és write ciklus:

/* user/cat.c – fájl tartalmának másolása */
#include "syscalls.h"

static void copy_fd(int in_fd)
{
    char buf[512];
    ssize_t n;

    for (;;) {
        n = read(in_fd, buf, sizeof(buf));
        if (n < 0) {
            perror("read");
            return;
        }
        if (n == 0) {
            return;
        }
        if (write(STDOUT_FILENO, buf, (size_t)n) < 0) {
            perror("write");
            return;
        }
    }
}

int main(int argc, char **argv)
{
    int i;

    if (argc < 2) {
        copy_fd(STDIN_FILENO);
        return 0;
    }

    for (i = 1; i < argc; i++) {
        int fd = open(argv[i], O_RDONLY, 0);
        if (fd < 0) {
            perror("cat");
            continue;
        }
        copy_fd(fd);
        close(fd);
    }

    return 0;
}

29.4.16 echo

Az echo az argumentumait szóközzel elválasztva a szabványos kimenetre írja, majd egy újsor karaktert ad hozzá. A minimális verzió nem feltétlenül értelmezi a -n kapcsolót, de a laborban érdemes bevezetni, mert a scriptekben gyakran használják. Az echo belső parancs is lehet, de külön programként egyszerűbb tesztelni a fork + execve útvonalat.

29.4.17 ls

Az ls a VFS könyvtárbejegyzéseit listázza. A minimális rendszerben a getdents rendszerhívás vagy annak burkolója adja vissza a bejegyzések nevét. A program minden bejegyzést kiír, a . és .. kivételével. A hosszú formát, a jogosultságokat és a fájlméretet az os110 fájlrendszer-metaadatainak beolvasásával lehet megjeleníteni; a minimális laborban elég a nevek felsorolása.

29.4.18 mkdir és rm

A mkdir egy új könyvtárat hoz létre. A rm fájlt töröl; a könyvtárak törléséhez a minimális rendszerben külön rmdir programot vagy a rm -r kapcsolót implementálhatjuk. Mindkettő a VFS megfelelő műveletére támaszkodik, és a hibakódokat a szabványos módon jelzi.

A shell és a segédprogramok együttesen adják ki azt a minimális felhasználói környezetet, amelyen a kernel további részei, például a hálózat vagy a tesztelési keretrendszer, kényelmesen gyakorolhatók.

29.4.19 10. Gyakori hibák és helyes megoldások

A shell és a userland építése során a következő hibák a leggyakoribbak.

  1. Zombie folyamatok. Ha a szülő nem hívja a waitpid-et, a befejeződött gyermek a folyamattáblában marad. Idővel a rendszer kifogy a folyamat-helyekből. Megoldás: minden fork után a szülőben waitpid, vagy a SIGCHLD szignál kezelése.

  2. execve utáni kód futása. Ha az execve hibázik, a gyermek a shell kódját folytatja. Megoldás: a gyermek ágban azonnal _exit-et hívni, lehetőleg a 127 kilépési kóddal.

  3. Nyitva maradt pipe-végek. Ha a szülő nem zárja be a cső mindkét végét, a jobb oldali folyamat sosem kap EOF-ot, és a pipeline örökre blokkol. Megoldás: a fork után a szülőben close(fd[0]); close(fd[1]);, a gyermekekben pedig a felesleges végét zárni.

  4. A cd nem beépített. Ha a cd-t külön folyamat futtatja, a szülő munkakönyvtára nem változik. Megoldás: a cd-t a shell saját folyamatában kezelni.

  5. PATH-feloldás biztonsági hibája. Ha a find_in_path a .-t is figyelembe veszi, egy rosszindulatú program elfoglalhatja a rendszerparancs nevét. Megoldás: a . csak akkor legyen a PATH-ban, ha a felhasználó kifejezetten felvette.

  6. Puffer-túlcsordulás a tokenizálásban. A hosszú bemeneti sorok vagy a nagyszámú argumentum túlírhatja a vermet. Megoldás: hosszkorlát, MAX_ARGS ellenőrzés, és a tokenizáló nullázza a tömb végét.

  7. Az errno késői olvasása. A rendszerhívás után más hívások felülírhatják az errno értékét. Megoldás: a hibát azonnal le kell kérdezni, hibaüzenetet írni, és az errno-t nem szabad több hívás után feltételezni.

  8. A $? nem frissül. Ha a shell nem tárolja az utolsó kilépési állapotot, a scriptek feltételes elágazásai hibásan döntenek. Megoldás: a report_status visszatérési értékét a shell egy változóban tárolja, és a $? ezt olvassa.

29.4.23 Build és futtatási parancsok

A laborban használt parancsok szemléltető jellegűek; a pontos keresztszerkesztő és QEMU-változat a reprodukciós csomagban található.

# user/Makefile – a userland programok fordítása (szemléltetés)
CROSS    ?= riscv64-linux-gnu-
CFLAGS   := -O2 -march=rv64imac -mabi=lp64 -ffreestanding -nostdinc \
            -I../include
LD       := $(CROSS)ld
LDFLAGS  := -T user.ld -nostdlib

USER_PROGS := cat echo ls mkdir rm sh

all: $(USER_PROGS)

$(USER_PROGS): %: %.c ../lib/syscalls.c ../lib/string.c
    $(CROSS)gcc $(CFLAGS) -c $< -o $@.o
    $(CROSS)gcc $(CFLAGS) -c ../lib/syscalls.c -o syscalls.o
    $(CROSS)gcc $(CFLAGS) -c ../lib/string.c -o string.o
    $(LD) $(LDFLAGS) -o $@ $@.o syscalls.o string.o
    cp $@ ../initramfs/bin/

A QEMU futtatás:

qemu-system-riscv64 \
  -machine virt \
  -m 32M \
  -kernel build/kernel.elf \
  -initrd build/initramfs.cpio \
  -nographic

A shell prompt megjelenése után a fenti tesztek futtathatók. A labor reprodukálhatósága érdekében a kernelverziót, a fordítási konfigurációt és a QEMU-verziót rögzíteni kell.

29.4.25 12. Önellenőrző kérdés

A shell csővezeték futtatásakor a következő parancsot adjuk ki:

cat /etc/motd | cat > /home/motd2

A szülő shell a pipe és a két fork után mindkét csővéget bezárja, majd waitpid-del vár mindkét gyermekre. Tegyük fel, hogy a /etc/motd fájl 1024 bájt, a pipe puffer mérete 4096 bájt, és mindkét cat a read/write hívásokat 512 bájtos pufferekkel végzi. Válaszolj a következőkre:

  1. Miért nem fordulhat elő az, hogy a jobb oldali cat a read-ben örökre blokkol?
  2. Hány read hívást hajt végre a bal oldali cat, amíg az EOF-t meg nem kapja?
  3. Mi történik, ha a szülő elfelejti bezárni a pipe író végét a második fork után?

A válasz elemei:

  1. A bal oldali cat a fájl végére érve kilép, ami bezárja a pipe író végét. Mivel a szülő is bezárta a saját író végét, a pipe-nak nem marad nyitott írója, így a jobb oldali read 0-t ad vissza.
  2. A bal oldali cat 1024 / 512 = 2 read hívással beolvassa a fájlt, majd a harmadik read adja a 0 visszatérést; ezután nem olvas tovább. Tehát összesen 3 read, de ebből 2 szolgáltat adatot.
  3. Akkor a jobb oldali cat nem kap EOF-ot, mert a szülőben nyitva maradt az egyik író vég; a pipeline a read-ben blokkol, és a waitpid sosem tér vissza. Ez a klasszikus pipe-szivárgás.

A fejezetben bemutatott shell és alapszolgáltatások a következő egység (os114) számára alapot adnak: a tesztelési keretrendszer már parancssori eszközökkel indítható, a shell pedig alkalmas az automatikus tesztek futtatására és az eredmények összegyűjtésére.
