19.3 Csomagfeldolgozás, netfilter és eBPF

A hálózati csomagok feldolgozása az operációs rendszer egyik legkritikusabb útvonala. Egy csomag beérkezésétől a kézbesítésig, illetve egy kimenő csomag esetén a socketből a hálózati kártyáig számos kernelkomponens vesz részt. Ebben a fejezetben azt vizsgáljuk, hol és hogyan lehet beavatkozni ebbe a folyamatba: hogyan működik a netfilter csomagszűrő keretrendszere, hogyan követi a connection tracking a kapcsolatok állapotát, és hogyan ad az eBPF és az XDP lehetőséget a lehető legkorábbi, rugalmas csomagfeldolgozásra.

A fejezet előfeltételezi a socket API és a hálózati rendszerhívások alapjait (Socket API és hálózati rendszerhívások). A cél az alapfogalmak és a gyakorlati minták együttes bemutatása, valamint egy ellenőrizhető tűzfal- és csomagszűrési szabályterv elkészítése. A példák Linux kernel 5.x/6.x és nftables 1.x környezetet feltételeznek; a pontos verziófüggő szintaxist a helyi kézikönyvben ellenőrizni kell.

19.3.1 A kernel hálózati útvonala

A bejövő (ingress) csomag útja a hálózati kártyától a felhasználói folyamatig több fázisból áll. Az egyszerűség kedvéért a modern Linux kernelben a következő lépések figyelhetők meg:

  1. A hálózati kártya (NIC) megszakítást vált ki, vagy a kernel a NAPI (New API) mechanizmussal pollozza a csomaggyűrűt. A feldolgozás softirq kontextusban (NET_RX) történik.
  2. A meghajtó létrehoz egy sk_buff struktúrát, amely a csomag metaadatait (protokoll, bejövő interfész, időbélyeg, fejlécmutatók) és magát a puffert tartalmazza.
  3. Az illesztőprogram meghívja a netif_receive_skb() függvényt, amely a csomagot átadja a protokoll-veremnek: Ethernet, IP, majd TCP/UDP.
  4. A netfilter hookok a feldolgozási útvonal meghatározott pontjain vannak elhelyezve. A hookok előtt és után a kernel további feldolgozást végez, például routing döntést.

A netfilter öt alapvető hookpontot definiál:

  • NF_INET_PRE_ROUTING: minden bejövő csomag, közvetlenül a routing döntés előtt.
  • NF_INET_LOCAL_IN: a helyi gépre szánt csomagok, a routing döntés után.
  • NF_INET_FORWARD: a továbbítandó (forwardolt) csomagok, a routing döntés után.
  • NF_INET_LOCAL_OUT: a helyi folyamat által generált kimenő csomagok, a routing döntés előtt.
  • NF_INET_POST_ROUTING: minden kimenő csomag, közvetlenül a hálózati kártyára adás előtt.

A hookok sorrendjét az alábbi folyamatábra szemlélteti:

        bejövő csomag
             |
    [PRE_ROUTING]  (minden bejövő)
             |
       routing döntés
        /            \
  helyi cím          továbbítandó
        \            /
    [LOCAL_IN]    [FORWARD]
        |            |
      socket        |
        |            |
    [LOCAL_OUT]     |
        \          /
    [POST_ROUTING]  (minden kimenő)
             |
        kimenő csomag

A routing döntés a cél IP-cím alapján határozza meg, hogy a csomagot a helyi gépnek kell-e kézbesíteni, vagy továbbítani kell egy másik interfészre. A PRE_ROUTING hookban a csomag még az eredeti címeket hordozza; a POST_ROUTING hookban viszont már a kimenő interfész és a végső címek ismertek. Ez a sorrend kulcsfontosságú a szűrés és a NAT szempontjából.

A kimenő csomag útja hasonló: a socket rétegből indul, áthalad a LOCAL_OUT hookon, majd a POST_ROUTING hookon, végül a meghajtó elküldi a csomagot. A LOCAL_OUT azért fontos, mert itt még a helyi folyamat által generált forgalmat is meg lehet szűrni, például egy rosszindulatú program kimenő kapcsolatait.

19.3.2 Netfilter hookok és szűrés

A netfilter a Linux kernel csomagszűrő és -manipuláló keretrendszere. A hookokhoz úgynevezett táblák (table) és láncok (chain) csatlakoznak. A tábla határozza meg, hogy milyen típusú műveleteket végezhetnek a szabályok: szűrés (filter), címfordítás (nat), csomagmódosítás (mangle), kapcsolatkövetés kikapcsolása (raw), biztonsági házirend (security). A lánc egy adott hookponthoz kötött szabálylista, amelyet a kernel a csomag feldolgozása során sorban kiértékel.

A klasszikus iptables eszközben a filter tábla három láncot tartalmaz: INPUT, FORWARD, OUTPUT. A nat tábla láncai: PREROUTING, INPUT, OUTPUT, POSTROUTING. A mangle tábla mind az öt hookponton jelen lehet. A láncokhoz tartozik egy alapértelmezett szabály (policy), amelyet akkor alkalmaz a kernel, ha egyetlen szabály sem illeszkedik a csomagra. A policy lehet ACCEPT vagy DROP.

Egy iptables szabály két részből áll: illeszkedési feltétel (match) és cél (target). A feltétel lehet például a protokoll (-p tcp), a forrás vagy cél IP, a port (--dport), az interfész (-i eth0), vagy egy modul által biztosított komplexebb vizsgálat, például a kapcsolat állapota (-m state --state ESTABLISHED). A cél határozza meg, mi történjen a csomaggal: ACCEPT (továbbenged), DROP (csendben eldob), REJECT (eldob és hibaüzenetet küld), LOG (naplózza), DNAT, SNAT, MASQUERADE stb.

Egy tipikus, állapotalapú bejövő szűrést iptables-ben a következő parancsokkal lehet felépíteni:

# Alapértelmezés: mindent eldobunk, amit nem engedélyezünk
iptables -P INPUT DROP
iptables -P FORWARD DROP
iptables -P OUTPUT ACCEPT

# A már kialakult kapcsolatok visszatérő csomagjait engedjük
iptables -A INPUT -m state --state ESTABLISHED,RELATED -j ACCEPT

# A loopback interfész forgalmát mindig engedjük
iptables -A INPUT -i lo -j ACCEPT

# SSH bejövő forgalom engedélyezése
iptables -A INPUT -p tcp --dport 22 -m state --state NEW -j ACCEPT

# Minden más bejövő csomagot eldobunk és naplózunk
iptables -A INPUT -j LOG --log-prefix "input-drop: "
iptables -A INPUT -j DROP

A szabályok sorrendje kritikus: a kernel az első illeszkedő szabály célját alkalmazza, és nem vizsgálja tovább a láncot. Ha a -P INPUT DROP után rögtön egy engedő szabályt helyezünk el, az nem érvényesül, mert a policy csak akkor lép életbe, ha nincs találat. Ezért a gyakori forgalmat engedő szabályokat előre kell tenni, a tiltást pedig a lánc végére.

A modern nftables a netfilter új felülete, amely az iptables, ip6tables, arptables és ebtables funkcióit egyesíti. A szintaxis egységes, a szabálykészlet atomikusan frissíthető, és a teljesítmény is jobb, mert a kernel egyetlen belső reprezentációt használ. Az nftables-ben a táblák és láncok explicit módon jönnek létre, a hook és a priority a lánc definíciójában szerepel.

19.3.3 Connection tracking (conntrack)

A connection tracking (magyarul kapcsolatkövetés) a netfilter azon alrendszere, amely a csomagok alapján nyomon követi a hálózati kapcsolatokat. Nem szűrési mechanizmus, hanem olyan állapotinformációt szolgáltat, amelyre a szűrő és a NAT szabályok építhetnek. A conntrack minden kapcsolathoz egy bejegyzést hoz létre a kernelben, amely tartalmazza a kapcsolat azonosítóit (protokoll, forrás IP, forrás port, cél IP, cél port – az úgynevezett 5-tuple) és az aktuális állapotot.

A conntrack által használt állapotok:

  • NEW: a csomag új kapcsolatot kezdeményez, például a TCP SYN csomag.
  • ESTABLISHED: a csomag egy már létező, mindkét irányban felismert kapcsolathoz tartozik.
  • RELATED: a csomag egy másik, már meglévő kapcsolathoz kapcsolódik, például az FTP adatkapcsolat vagy egy ICMP hibaüzenet.
  • INVALID: a csomag nem illeszthető be egyetlen ismert kapcsolatba sem, például sérült fejléc vagy lejárt bejegyzés.

Az állapotalapú szűrés alapelve: engedjük a kimenő forgalmat, és a bejövő forgalomból csak azokat a csomagokat fogadjuk el, amelyek egy általunk kezdeményezett kapcsolat visszatérő csomagjai, illetve az ezekhez kapcsolódó csomagok. Ez gyakorlatilag az ESTABLISHED,RELATED állapotok elfogadását jelenti a bejövő láncban, míg az új kapcsolatokat csak a kívánt szolgáltatásokra (például SSH, HTTP) engedjük.

A conntrack szoros kapcsolatban áll a NAT-tal. Amikor a NAT szabály módosítja a forrás vagy cél címet, a conntrack bejegyzés eltárolja az eredeti és a leképezett cím közötti megfeleltetést. Így a visszairányú csomag automatikusan visszafordítható anélkül, hogy külön szabályt kellene írni. A conntrack nélkül a NAT nem tudná, melyik belső géphez tartozik egy visszatérő csomag.

A conntrack működéséhez a nf_conntrack kernelmodul betöltésére van szükség. A modul betöltése után a kernel automatikusan követi a kapcsolatokat. A conntrack tábla mérete korlátozott; ha megtelik, az új kapcsolatok INVALID állapotba kerülhetnek, és a szabályok nem a várt módon működnek. A tábla mérete a nf_conntrack_max rendszerparaméterrel állítható, a telítettség pedig a /proc/net/nf_conntrack vagy a conntrack eszköz segítségével ellenőrizhető.

19.3.4 NAT és masquerade

A NAT (Network Address Translation, hálózati címfordítás) a csomagok forrás vagy cél IP-címének (és gyakran a portjának) megváltoztatása. Két fő típusa van:

  • SNAT (Source NAT): a forrás címet cseréli le, tipikusan akkor, amikor egy belső hálózat gépei egy nyilvános címen keresztül kommunikálnak az internettel. A válaszcsomagot a conntrack automatikusan visszafordítja.
  • DNAT (Destination NAT): a cél címet cseréli le, tipikusan porttovábbítás (port forwarding) esetén, amikor egy külső címre érkező forgalmat egy belső szerverre irányítunk.

A MASQUERADE (álcázás) az SNAT speciális változata, amely nem igényel rögzített nyilvános IP-címet, hanem a kimenő interfész aktuális IP-címét használja. Ez különösen hasznos DHCP-vel konfigurált, változó IP-című kapcsolatok esetén, például otthoni routereknél.

Egy tipikus NAT-konfiguráció iptables-ben:

# Kimenő forgalom álcázása az eth0 interfészen
iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE

# Bejövő 80-as port átirányítása a belső 192.0.2.10-es szerverre
iptables -t nat -A PREROUTING -i eth0 -p tcp --dport 80 \
    -j DNAT --to-destination 192.0.2.10:80

A NAT és a szűrés együttműködésekor figyelembe kell venni a hookok sorrendjét. A PREROUTING hookban a DNAT már megtörténik, mielőtt a routing döntés és a FORWARD vagy INPUT lánc lefut. Ezért a szűrő szabályokban a DNAT utáni célcímet kell használni. Például ha a fenti DNAT szabály a 80-as portot a 192.0.2.10-es szerverre irányítja, akkor a FORWARD láncban a 192.0.2.10-es címre kell engedélyezni a forgalmat, nem a külső címre.

19.3.5 nftables a gyakorlatban

Az nftables a modern Linux rendszerekben az ajánlott tűzfal- és NAT-eszköz. A konfigurációt deklaratív módon, táblákba és láncokba szervezve lehet leírni. Az alábbi példa egy állapotalapú tűzfalat és NAT-ot mutat be egy átjáró (gateway) szerepű gépen:

table inet filter {
    chain input {
        type filter hook input priority 0; policy drop;
        ct state established,related accept
        iif "lo" accept
        tcp dport 22 accept
        counter drop
    }

    chain forward {
        type filter hook forward priority 0; policy drop;
        ct state established,related accept
        iifname "eth1" oifname "eth0" accept
        counter drop
    }

    chain output {
        type filter hook output priority 0; policy accept;
    }
}

table ip nat {
    chain postrouting {
        type nat hook postrouting priority 100; policy accept;
        oifname "eth0" masquerade
    }

    chain prerouting {
        type nat hook prerouting priority -100; policy accept;
        iifname "eth0" tcp dport 8080 dnat to 192.0.2.10:80
    }
}

A fenti szabálykészlet a következőket teszi:

  • A bejövő forgalomból csak a már kialakult kapcsolatokhoz tartozó csomagokat fogadja el, valamint a loopback forgalmat és az SSH-t (22/TCP).
  • A továbbított forgalomból csak a belső hálózatból (eth1) a külső interfész (eth0) felé haladó új kapcsolatokat engedi, a visszatérő csomagokat a conntrack állapota alapján.
  • A kimenő forgalmat nem korlátozza.
  • A kimenő forgalmat a POSTROUTING láncban álcázza az eth0 interfész IP-címére.
  • A bejövő 8080-as portot a belső 192.0.2.10-es gép 80-as portjára irányítja.

A szabálykészlet betöltése például a következő paranccsal történhet:

nft -f /etc/nftables.conf

Az nftables előnye, hogy a teljes szabálykészlet egyetlen atomikus művelettel cserélhető, így a hibás konfiguráció nem hagy nyitott időablakot. A szabályok ellenőrzésére a nft list ruleset parancs szolgál.

19.3.6 eBPF és XDP

Az eBPF (extended Berkeley Packet Filter) egy olyan virtuális gép a Linux kernelben, amely biztonságos, felügyelt módon hajt végre felhasználó által megírt programokat. Az eBPF programokat C nyelvhez hasonló szintaxissal lehet megírni, majd clang segítségével bpf bytecode-ra fordítani. A kernel verifier (ellenőrző) komponense a betöltés előtt statikusan elemzi a programot: ellenőrzi, hogy a program nem tartalmaz végtelen ciklust, minden memória-hozzáférés határellenőrzött, és a program nem fér hozzá tiltott kernelmemóriához. A programok ezután biztonságosan futhatnak kernelkontextusban.

A csomagfeldolgozás szempontjából az eBPF két fontos belépési pontot kínál:

  1. XDP (eXpress Data Path): a lehető legkorábbi pont, közvetlenül a hálózati kártya meghajtójában, még az sk_buff allokáció előtt. Az XDP program a nyers csomagpufferhez fér hozzá, és dönthet a csomag sorsáról. Mivel a feldolgozás a driverben történik, az overhead minimális.
  2. tc (traffic control) hook: a hálózati verembe már bekerült csomagokra alkalmazható, mind bejövő (ingress), mind kimenő (egress) irányban. A tc később fut, mint az XDP, de rugalmasabb, mert a teljes kernel-hálózati stack rendelkezésére áll.

Az XDP program visszatérési értékei:

  • XDP_DROP: a csomagot eldobja.
  • XDP_PASS: a csomagot továbbítja a hagyományos hálózati verembe.
  • XDP_TX: a csomagot visszaküldi ugyanazon az interfészen.
  • XDP_REDIRECT: a csomagot egy másik interfészre irányítja.
  • XDP_ABORTED: hibát jelez (általában nem használt).

Az alábbi egyszerű XDP program egy adott forrás IP-címről érkező csomagokat dob el:

#include <linux/bpf.h>
#include <bpf/bpf_helpers.h>
#include <linux/if_ether.h>
#include <linux/ip.h>

SEC("xdp_drop_ip")
int xdp_drop_ip(struct xdp_md *ctx) {
    void *data_end = (void *)(long)ctx->data_end;
    void *data = (void *)(long)ctx->data;

    struct ethhdr *eth = data;
    if ((void *)(eth + 1) > data_end)
        return XDP_PASS;

    struct iphdr *ip = (struct iphdr *)(eth + 1);
    if ((void *)(ip + 1) > data_end)
        return XDP_PASS;

    // Példa: 192.0.2.10 forrás cím eldobása
    __be32 drop_ip = bpf_htonl(0xc000020a); // 192.0.2.10
    if (ip->saddr == drop_ip)
        return XDP_DROP;

    return XDP_PASS;
}

char _license[] SEC("license") = "GPL";

A programot a következőképpen lehet lefordítani és betölteni (emulált környezetben):

clang -O2 -target bpf -c xdp_drop_ip_kern.c -o xdp_drop_ip_kern.o
ip link set dev eth0 xdp obj xdp_drop_ip_kern.o sec xdp_drop_ip

Az ip link set ... xdp parancs az eth0 interfészhez csatolja a programot. A betöltést a kernel verifier ellenőrzi, és csak akkor engedi meg, ha a program megfelel a biztonsági követelményeknek. A program a bpf_htonl() segédfüggvényt használja a bájtsorrend átalakítására; a XDP_DROP és XDP_PASS értékeket a bpf_helpers.h definiálja.

Az eBPF programok gyakran map-eket használnak, amelyek a felhasználói tér és a kernel között osztanak meg adatokat. Például egy XDP program egy map-ből olvashatja ki a tiltott IP-címek listáját, így a szűrés dinamikusan frissíthető anélkül, hogy a programot újra kellene fordítani. A map-ek létrehozása és kezelése a bpf() rendszerhíváson keresztül történik, de a gyakorlatban a libbpf könyvtár vagy a bpftool eszköz egyszerűsíti a folyamatot.

A tc hookhoz csatolt eBPF programok hasonlóak, de a belépési pont a tc osztályozó (classifier) vagy akció (action) mechanizmusa. A tc hook lehetővé teszi a kimenő forgalom szűrését is, ami XDP-vel nem megoldható.

19.3.7 Gyakori hibák és buktatók

A csomagfeldolgozás és a szűrés során a következő tipikus hibákat érdemes elkerülni:

  1. Hook sorrend félreértése. Gyakori hiba, hogy a fejlesztő a PREROUTING hookban szeretné eldobni a helyi gépre szánt csomagot, de a szabályt a FORWARD láncba teszi, vagy fordítva. A hookok sorrendjének ismerete nélkül a szabályok nem a várt ponton avatkoznak be.

  2. Conntrack állapot hiánya. Ha a conntrack modul nincs betöltve, az állapotalapú szabályok nem működnek, mert minden csomag INVALID állapotba kerül. A nf_conntrack modul betöltése és a szabályok ct state használata előtt ellenőrizni kell a modul állapotát.

  3. NAT és szűrés interakciója. A DNAT után a szűrő láncokban a módosított célcímet kell használni, nem az eredetit. Ha a szabályt a külső címre írják, a forgalom nem lesz engedélyezve, vagy éppen tiltva marad.

  4. eBPF verifier korlátok. Az eBPF programokban minden memória-hozzáférést határellenőrzéssel kell védeni, különben a verifier elutasítja a betöltést. A program nem tartalmazhat bizonyítottan végtelen ciklust, és nem hívhat tetszőleges kernel függvényeket, csak engedélyezett helpereket.

  5. Teljesítmény félreértése. Az XDP valóban alacsony overheadet kínál, de csak a bejövő forgalomra. A tc hook később fut, és nagyobb a feldolgozási költsége. A szabályok sorrendje a netfilterben is számít: a gyakran illeszkedő szabályokat előre kell tenni, különben minden csomag végigszalad a láncon.

  6. Tesztelés hiánya. A tűzfalszabályokat rendszeresen tesztelni kell, mert egy rosszul megírt szabály akár a teljes hálózati forgalmat blokkolhatja, vagy éppen nyitva hagyhat egy szolgáltatást. A laborban ezért hangsúlyos a mért és várt eredmények elkülönítése.

19.3.8 Labor: tűzfal- és csomagszűrési szabályterv

A labor célja egy állapotalapú tűzfal és NAT szabályterv elkészítése, tesztelése és dokumentálása emulált környezetben. A feladat nem éles rendszeren fut, hanem hálózati névterekben vagy virtuális gépen.

Kiinduló állapot. Hozzunk létre három hálózati névteret: ns1 (belső kliens), ns2 (belső szerver) és rtr (router). A névtereket veth párokkal kötjük össze: ns1 a rtr eth1 interfészéhez, ns2 a rtr eth2 interfészéhez kapcsolódik. A rtr rendelkezik egy eth0 interfésszel, amely a külvilágot szimulálja. A címek a dokumentációs tartományból származnak: ns1 IP-címe 192.0.2.10/24, ns2 IP-címe 192.0.2.20/24, a rtr eth1 címe 192.0.2.1/24, eth2 címe 192.0.2.2/24, eth0 címe 198.51.100.1/24. A ns1 és ns2 alapértelmezett átjárója a rtr megfelelő interfészcíme. A névterekben a szükséges szolgáltatások: ns2-n SSH (22/TCP) és HTTP (80/TCP) szerver fut, ns1-ről ezeket kívánjuk elérni, de más forgalmat tiltani.

Szabályterv. A rtr névtérben nftables szabálykészletet hozunk létre az alábbi követelményekkel:

  • A ns1 csak a ns2 SSH (22/TCP) és HTTP (80/TCP) szolgáltatásait érheti el.
  • A ns2 kimenő forgalma az eth0 irányába engedélyezett, és a POSTROUTING láncban masquerade szabályt alkalmazunk.
  • A rtr saját bejövő forgalma közül csak a már kialakult kapcsolatok és a loopback engedett.
  • Minden más továbbított forgalom eldobandó.

A szabálykészlet nftables szintaxissal:

table inet filter {
    chain input {
        type filter hook input priority 0; policy drop;
        ct state established,related accept
        iif "lo" accept
    }

    chain forward {
        type filter hook forward priority 0; policy drop;
        ct state established,related accept
        iifname "eth1" oifname "eth2" ip protocol tcp tcp dport { 22, 80 } accept
        iifname "eth2" oifname "eth0" accept
    }

    chain output {
        type filter hook output priority 0; policy accept;
    }
}

table ip nat {
    chain postrouting {
        type nat hook postrouting priority 100; policy accept;
        oifname "eth0" masquerade
    }
}

Tesztelés és mérési napló. A szabályterv betöltése után a következő teszteket futtatjuk le, és az eredményeket táblázatban rögzítjük:

Teszt Várt eredmény Mért eredmény Megjegyzés
ns1 → ns2 SSH (22/TCP) kapcsolat létrejön sikeres bejelentkezés conntrack NEW + ACCEPT
ns1 → ns2 HTTP (80/TCP) HTTP 200 válasz HTTP 200 conntrack NEW + ACCEPT
ns1 → ns2 egyéb port (pl. 3306) csomag eldobva, timeout timeout policy drop
ns2 → külső cím (198.51.100.10) ICMP válasz érkezik 0% csomagvesztés masquerade működik
ns1 → külső cím eldobva timeout nincs engedélyező szabály
rtr bejövő SSH eldobva timeout input policy drop, nincs engedély

A ping késleltetést is megmérjük szűrés nélkül és szűréssel, hogy lássuk a netfilter overheadjét. A mérési naplóban külön oszlopban jelöljük a mért és a várt értéket. Például:

  • Várt késleltetés szűrés nélkül: < 1 ms
  • Mért késleltetés szűrés nélkül: 0,3 ms
  • Várt késleltetés szűréssel: < 1 ms
  • Mért késleltetés szűréssel: 0,4 ms

Visszaállítás. A labor végén a szabályokat töröljük, a névtereket megszüntetjük:

nft flush ruleset
ip netns del ns1
ip netns del ns2
ip netns del rtr
ip link del veth1 2>/dev/null
ip link del veth2 2>/dev/null

Mérőszámok. A laborban a következő mérőszámokat rögzítjük: a szabályok száma, a csomagvesztés aránya, a késleltetés növekedése a szűrés hatására, és a tesztelt esetek száma.

19.3.9 Önellenőrző kérdések

  1. Nevezze meg a netfilter öt hookpontját, és írja le, hogy egy bejövő, helyi címre szánt csomag milyen sorrendben halad át rajtuk.
  2. Miért van szükség a connection trackingre a NAT működéséhez? Mi történik, ha a conntrack modul nincs betöltve?
  3. Milyen visszatérési értékeket adhat egy XDP program, és mi a különbség az XDP_DROP és az XDP_PASS között?

Ezek a kérdések a fejezet tanulási céljait ellenőrzik: a kernel hálózati útvonalának és a szűrésnek a megértését, a gyakorlati eszközök alkalmazását, valamint a tipikus hibák felismerését.
