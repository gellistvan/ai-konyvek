28.4 Naplózás, panic és hibakezelés

A kernel fejlesztése során a hibák elkerülhetetlenek. A userland programokban egy hibás mutató arra utal, hogy a folyamat megbukott, a rendszer többi része tovább működik. A kernelben ugyanez a hiba gyakran az egész rendszert veszélyezteti: nincs mögöttes védelmi háló, amely elkülönítené a hibás komponenst. Ezért a kernel saját hibakezelési eszközöket igényel: láthatóvá kell tenni a hibákat, diagnosztikai információt kell gyűjteni, és meg kell határozni, hogy a rendszer folytathatja-e a futást, vagy biztonságosan le kell állnia. Ebben a fejezetben a kernel naplózásának, a panic mechanizmusnak és a oops kezelésének alapelveit és gyakorlati mintáit tekintjük át. A cél nem csupán a Linux printk API ismertetése, hanem egy olyan gondolkodásmód kialakítása, amelyet a saját, minimális rendszerünkben is alkalmazni tudunk.

28.4.1 A kernel hibakezelés sajátosságai

A kernel futási környezete alapvetően különbözik a felhasználói térétől. Nincs libc, nincs szabványos printf, nincs fájlrendszer, ahová naplót írhatunk, és nincs processzhatár, amely a hibát lokálisan kezelné. A kernel a legmagasabb privilégiumú módban fut, közvetlen hozzáféréssel a hardverhez és a memóriához. Egy hibás memória-hozzáférés itt nem egyszerűen a hibás folyamat terminálását jelenti, hanem potenciálisan a kernel adatstruktúráinak megsérülését, eszközök hibás állapotba kerülését vagy váratlan rendszerleállást.

A hibakezelés három fő célja:

  1. Láthatóság – a hiba ne maradjon néma; a fejlesztő és a rendszeradminisztrátor értesüljön a bekövetkezéséről, annak körülményeiről.
  2. Diagnosztika – a naplóüzenet tartalmazzon elegendő kontextust (időbélyeg, processzor, folyamat, verem, regiszterek) a hiba okának azonosításához.
  3. Megbízható folytatás vagy biztonságos leállás – a kernelnek döntést kell hoznia: a hiba helyi és javítható-e, vagy a rendszer állapota már nem megbízható. Ez utóbbi esetben a legbiztonságosabb választás a panic, azaz a rendszer azonnali, szándékos leállítása.

A kernelben a hibakezelés egyszerű eszközökkel dolgozik, mert a hiba bekövetkeztekor nem támaszkodhatunk bonyolult futásidejű környezetre. A naplózásnak minimális függőségűnek kell lennie, és korán elérhetőnek – már a boot legelső fázisában is.

28.4.2 Kernel naplózás: printk és log szintek

A leggyakoribb kernelnaplózási mechanizmus a printk (print kernel). Ez a felhasználói printf analógja, de közvetlenül a kernelben fut, és a kimenetet nem a standard kimenetre, hanem egy körkörös puffere (ring buffer) írja. A printk függvény a formázott üzenetet előállítja, majd a megfelelő szinttel együtt a naplóba helyezi. A Linux kernelben a printk a következőképpen hívható:

printk(KERN_INFO "kernel booted, version %s\n", version);

A KERN_INFO makró nem külön argumentum, hanem a formátumstring elejére illesztett log szintet jelölő előtag. Fontos, hogy a log szint és a formátumstring egy literálban szerepel, így a fordító ellenőrizheti a paramétereket.

A log szintek jelentése:

  • KERN_EMERG – a rendszer használhatatlan, azonnali beavatkozás szükséges.
  • KERN_ALERT – súlyos hiba, azonnali figyelem szükséges.
  • KERN_CRIT – kritikus feltétel, például hardverhiba.
  • KERN_ERR – általános hiba, amely nem feltétlenül fatális.
  • KERN_WARNING – figyelmeztetés, potenciális probléma.
  • KERN_NOTICE – normál, de fontos esemény.
  • KERN_INFO – tájékoztató üzenet.
  • KERN_DEBUG – részletes, hibakereséshez használt üzenet.

A szintek hierarchiát alkotnak. A kernel egy console_loglevel (vagy default_message_loglevel) értéket tart nyilván, amely meghatározza, hogy mely üzenetek jussanak el a soros konzolra vagy a képernyőre. A magasabb prioritású (alacsonyabb numerikus értékű) szintek mindig megjelennek, a alacsonyabb prioritásúak csak akkor, ha a beállítás ezt engedi. Például ha a konzolszint KERN_WARNING, akkor a KERN_INFO és KERN_DEBUG üzeneteket a ring bufferbe írjuk, de a konzolra nem küldjük. Ezzel elkerülhető, hogy a rendszer indulásakor a konzolt elárasszák a részletes debug üzenetek, miközben a hibaüzenetek megmaradnak.

A printk implementációja több rétegből áll:

  1. Formázás – a vsnprintf segítségével a változó argumentumokból szöveges reprezentációt készít.
  2. Rekordkészítés – a formázott üzenethez hozzáfűzi a szintet, időbélyeget, processzorazonosítót és egyéb metaadatot.
  3. Ring bufferbe írás – a rekordot a körkörös pufferbe másolja.
  4. Konzolra küldés – ha a szint engedélyezi, a konzol drivernek átadja a szöveget.

A korai boot fázisban a konzoldriver még nem érhető el. Ilyenkor a printk üzenetek kizárólag a ring bufferbe kerülnek, és a konzol inicializálása után a buffer tartalma kiüríthető. Ezt a mechanizmust nevezzük korai naplózásnak; a Linux kernelben például a earlycon vagy earlyprintk paraméterekkel aktiválható.

A következő C kód egy minimális, freestanding printk vázlatot mutat be. A példa szemléltetés, nem teljes implementáció:

/* Minimal kernel log - illustrative only */
typedef enum {
    LOG_EMERG   = 0,
    LOG_ALERT   = 1,
    LOG_CRIT    = 2,
    LOG_ERR     = 3,
    LOG_WARNING = 4,
    LOG_NOTICE  = 5,
    LOG_INFO    = 6,
    LOG_DEBUG   = 7
} log_level_t;

/* Console log threshold: messages with level <= console_level go to console */
static log_level_t console_level = LOG_WARNING;

void serial_write(const char *s);  /* provided by UART driver */

static void log_putc(char c) {
    /* placeholder: push character to ring buffer and maybe serial */
    ring_buffer_put(c);
    if (console_level <= LOG_WARNING) {
        serial_write(&c);  /* caution: serial_write expects null-terminated */
    }
}

void kernel_log(log_level_t level, const char *fmt, ...) {
    /* in real code, use vsnprintf; here simplified */
    char buf[128];
    va_list args;
    va_start(args, fmt);
    /* vsnprintf(buf, sizeof(buf), fmt, args) must be implemented */
    /* ... */
    va_end(args);

    for (const char *p = buf; *p; p++) {
        log_putc(*p);
    }
}

A fenti vázlatban a ring_buffer_put és a serial_write függvényeket a hardver réteg biztosítja. A serial_write a soros portra ír, ami a legegyszerűbb konzol. A vsnprintf kényelmi függvény a formázáshoz, de a legkorábbi boot fázisban sok kernel saját, minimalista implementációt használ.

A log szintek használatakor alapelv, hogy a fejlesztő ne használjon magasabb prioritást a szükségesnél. A KERN_ERR szint a tényleges hibáké, a KERN_DEBUG a fejlesztői nyomkövetésé. A túlzottan magas szintű üzenetek elrejthetik a valódi problémákat, míg a túl alacsony szintűek hamis riasztást kelthetnek.

28.4.3 Ring buffer és naplófogyasztás

A kernel naplózásának központi adatszerkezete a körkörös puffer. Ennek fix mérete van, és a régebbi üzenetek felülíródnak, ha a puffer megtelik. Ez a kialakítás garantálja, hogy a naplózás soha nem blokkol, és nem fogyaszt dinamikus memóriát – ami hibakezelés közben kritikus. A ring buffer tipikusan néhány KiB-tól néhány MiB-ig terjed; mérete konfigurálható.

A Linux kernelben a ring bufferben minden üzenet egy rekord, amely a következő mezőket tartalmazza:

  • időbélyeg (timestamp),
  • processzorazonosító,
  • log szint,
  • a formázott szöveg,
  • sorozatszám.

A rekordokat egy olvasó (például a dmesg parancs) olvashatja ki a felhasználói térből. A kernel a /dev/kmsg eszközön keresztül teszi lehetővé a valós idejű olvasást, ahol minden rekord egyszer olvasható. A syslog rendszerhívás a klasszikus interfész, amely a ring buffer tartalmát másolja a felhasználói térbe.

A ring buffer fontos tulajdonsága, hogy lehetővé teszi a napló megőrzését akkor is, ha a rendszer összeomlik. Ha a kernel panic állapotba kerül, a ring buffer tartalma a memóriában marad, és a következő boot után a rendszerindítási folyamat visszaolvashatja, vagy a kdump mechanizmus a memóriaképet mentheti. Emiatt a ring buffernek a panic előtt flush-elhetőnek kell lennie, de ez nem garantált, ha a hardveres konzol nem elérhető.

A naplófogyasztás szempontjából a ring buffernek két mutatója van: az író (writer) és az olvasó (reader) pozíció. Az író mindig a legújabb szabad helyre ír, és ha eléri a végét, visszaugrik az elejére, esetleg felülírva a legrégebbi, még nem olvasott rekordot. Az olvasó az utolsó olvasott pozíciótól halad előre. Ezzel a struktúrával a napló elvesztése akkor következik be, ha a termelő sebessége tartósan meghaladja a fogyasztóét.

A tipikus hibrid megoldás: a ring buffer a teljes naplót tárolja, a soros konzol pedig csak a szűrt üzeneteket kapja. Ha a ring buffer túl kicsi, a hibakereséshez szükséges korai üzenetek elveszhetnek, de a konzol kimenet megőrizheti a legfontosabb eseményeket. A tervezésnél ezért a panic diagnózishoz elegendő naplót kell biztosítani: a hiba bekövetkezése előtti néhány száz üzenet általában elegendő a kontextus rekonstruálásához.

28.4.4 Panic, oops és helyreállítás

A kernelben a hibák két nagy kategóriába sorolhatók: fatális és nem fatális. A fatális hiba azt jelenti, hogy a kernel állapota nem megbízható, és a további futás nagyobb kockázatot jelent, mint a leállás. A nem fatális hiba esetén a rendszer tovább működhet, de a hibát naplózni kell.

28.4.5 Oops

A Linux kernelben az oops egy nem fatális, de súlyos hiba. Olyan helyeken fordul elő, ahol a kernel hibás állapotot észlel, például NULL pointer dereferencia egy olyan kontextusban, ahol a hiba visszaadható. Az oops kiírja a hibaüzenetet, a processzor regisztereit, a verem nyomkövetést és a releváns kernelmodulokat, majd a rendszer megpróbál folytatódni. A oops után a kernel megjelöli az érintett folyamatot, hogy az ne folytathassa, de a rendszer többi része fut tovább.

Az oops legfontosabb jellemzője, hogy a hibát tartalmazó művelet (például egy rendszerhívás) visszatérhet -EFAULT hibakóddal, vagy a folyamat SIGSEGV jelzést kaphat. A kernel saját adatstruktúrái azonban sérülhetnek, ezért az oops után a rendszer állapota gyanús. A Linux konfigurálható úgy, hogy az első oops után panic-et váltson ki (panic_on_oops), így elkerülve a további adatkorrupciót.

28.4.6 Panic

A panic a kernel szándékos leállítása. A panic függvény akkor hívódik, amikor a kernel olyan hibát észlel, amelyből nincs biztonságos visszatérés – például a scheduler adatstruktúrája sérült, egy BUG() makró aktiválódott, vagy a hardver végzetes hibát jelzett. A panic feladata:

  1. Megállítani a többi CPU-t – SMP rendszerben a többi processzor megszakításokkal leállítható, hogy ne módosítsa tovább az állapotot.
  2. Kiírni a panic üzenetet – a hiba leírása, a processzor és a folyamat azonosítója, a verem.
  3. Kiírni a regisztereket és a memóriát – a hibakereséshez szükséges nyers adat.
  4. Végrehajtani a konfigurált kilépési műveletet – alapértelmezésben a rendszer leáll; beállítható újraindítás, magasabb szintű hibakezelőnek való átadás (például hardveres watchdog), vagy hiba utáni kernelbe való átugrás (kexec).

A panic pszudokódja:

void kernel_panic(const char *fmt, ...) {
    /* Disable interrupts on this CPU */
    local_irq_disable();

    /* Stop other CPUs (SMP platform) */
    smp_send_stop();

    /* Print panic header */
    kernel_log(LOG_EMERG, "Kernel panic - not syncing: ");
    va_list args;
    va_start(args, fmt);
    /* print formatted message to console and ring buffer */
    /* ... */
    va_end(args);

    /* Dump registers and stack */
    dump_stack();
    dump_registers();

    /* Optional: flush ring buffer to console */
    console_flush();

    /* Execute configured action */
    if (panic_timeout == 0) {
        /* Hang forever */
        for (;;) {
            cpu_halt();
        }
    } else if (panic_timeout > 0) {
        /* Reboot after timeout */
        machine_restart();
    } else {
        /* Hand over to debugger or crash dump */
        machine_halt();
    }
}

A fenti pszudokód a panic_timeout változóval konfigurálhatóvá teszi a viselkedést. A local_irq_disable és smp_send_stop platformfüggő; a dump_stack és dump_registers a QEMU, GDB és kernel debugging fejezetben tárgyalt hibakereső eszközökre épül.

Fontos, hogy a panic kódjának minimálisnak és robusztusnak kell lennie. Nem szabad olyan függvényeket hívnia, amelyek maguk is hibát okozhatnak. Például a printk a panic közben nem foglalhat zárat, mert a hiba éppen egy zár miatt következhetett be. A kernel ezért a panic útvonalon közvetlenül a soros portra ír, megkerülve a normál naplózási réteget.

28.4.7 Helyreállítási stratégiák

A panic a végső eszköz, de bizonyos rendszerekben – különösen beágyazott vagy biztonság-kritikus környezetben – megengedett a részleges helyreállítás. Ilyen lehet:

  • Watchdog alapú újraindítás – a hardveres vagy szoftveres watchdog figyeli a rendszer életjelét. Ha a panic bekövetkezik, a rendszer leáll, és a watchdog újraindítja. Ez a leggyakoribb beágyazott megoldás.
  • Crash dump és elemzés – a kdump mechanizmus a panic előtt egy másik kernelbe ugrik, amely elmenti a memória tartalmát. A mentett kép később debuggerrel elemezhető.
  • Részleges hibatűrés – egyes mikrokernel architektúrákban a hibás szolgáltatás újraindítható anélkül, hogy az egész kernel leállna. Ez a megközelítés azonban a hibahatárok gondos tervezését igényli.
  • oops utáni korlátozott folytatás – ha a hiba nem érinti a központi állapotot, a kernel folytathatja, de a hibás modul letiltható.

A helyreállítási stratégia megválasztása a rendszer követelményeitől függ. Egy szerveren a panic utáni automatikus újraindítás elfogadható. Egy orvosi eszközön a leállás elfogadhatatlan, ezért a tervezésnek eleve el kell kerülnie a fatális hibákat.

28.4.8 Hibakezelési minták a kernelben

A kernelben a hibák jelzésére több makró és konvenció létezik:

  • BUG() – feltétel nélküli fatális hiba; hatása panic, hacsak nincs beállítva panic_on_oops. Az BUG() utasítás gyakran egy olyan utasításra fordítódik, amely a debuggert hívja.
  • BUG_ON(condition) – ha a feltétel igaz, BUG()-ot hív.
  • WARN() – hasonló az oops-hoz, de a rendszer folytatódik. A WARN() üzenetet naplóz, és opcionálisan stack trace-t ír.
  • WARN_ON(condition) – feltételes WARN().
  • assert() a kernelben általában nem használatos, mert a hiba súlyossága és a feloldás nem egyértelmű; helyette a fenti makrók szerepelnek.

A makrókat okosan kell használni. A BUG akkor indokolt, ha a feltétel megsértése garantáltan adatkorrupcióhoz vezet, és a továbbhaladás veszélyesebb, mint a leállás. A WARN akkor megfelelő, ha a hiba nem fatális, de jelezni kell a fejlesztőnek, mert váratlan állapotot tükröz. A WARN-t gyakran követi hibakód visszaadása, így a hívó fél tisztességesen kezelheti a helyzetet.

A hibakódok visszaadása a kernelben a -errno hagyományt követi: a függvények negatív hibakódot adnak vissza, pozitív értéket siker esetén. A pointert visszaadó függvények az ERR_PTR makróval hibakódot kódolnak pointerbe, a IS_ERR és PTR_ERR makrókkal ellenőrizhető.

Példa egy tipikus hibaellenőrzési mintára:

struct my_data *p = kmalloc(sizeof(*p), GFP_KERNEL);
if (!p) {
    pr_err("my_data allocation failed\n");
    return -ENOMEM;
}

if (some_condition) {
    WARN_ON(1);
    kfree(p);
    return -EINVAL;
}

Itt a pr_err a printk(KERN_ERR ...) rövidítése. A WARN_ON naplózza a hibát, de a függvény mégis visszatér.

28.4.9 Gyakorlati minta: minimális log és panic

A következő C kód egy egyszerű, de működőképes keretet mutat be egy tanulási célú kernelhez. A kód freestanding, tehát nem használ libc-t, és a hardverhez való hozzáférést a serial_write és hasonló függvények absztrahálják. A példa célja a naplózás és a panic működésének megértése, nem pedig éles rendszerben való használat.

/* minimal_log.h - illustrative kernel logging */
#ifndef MINIMAL_LOG_H
#define MINIMAL_LOG_H

typedef enum {
    LOG_EMERG   = 0,
    LOG_ALERT   = 1,
    LOG_CRIT    = 2,
    LOG_ERR     = 3,
    LOG_WARNING = 4,
    LOG_NOTICE  = 5,
    LOG_INFO    = 6,
    LOG_DEBUG   = 7
} log_level_t;

void kernel_log_init(void);
void kernel_log(log_level_t level, const char *fmt, ...);
void kernel_panic(const char *fmt, ...);
void kernel_oops(const char *fmt, ...);

#endif
/* minimal_log.c - simplified implementation */
#include <stdarg.h>
#include <stdint.h>
#include "minimal_log.h"

/* Platform-specific functions provided by UART or early console */
extern void serial_putchar(char c);
extern void machine_halt(void);
extern void machine_restart(void);
extern void local_irq_disable(void);
extern void local_irq_enable(void);
extern void dump_stack(void);

/* Ring buffer configuration */
#define LOG_BUFFER_SIZE 4096
static char log_buffer[LOG_BUFFER_SIZE];
static uint32_t log_wr = 0;
static uint32_t log_rd = 0;
static int log_lock = 0;  /* simple spinlock placeholder */

static log_level_t console_level = LOG_INFO; /* show INFO and above */

static void spin_lock(int *lock) {
    /* atomic test-and-set; actual implementation platform-specific */
    while (__sync_lock_test_and_set(lock, 1)) {
        /* spin */
    }
}

static void spin_unlock(int *lock) {
    __sync_lock_release(lock);
}

static void log_putc(char c) {
    /* Write to ring buffer */
    log_buffer[log_wr] = c;
    log_wr = (log_wr + 1) % LOG_BUFFER_SIZE;
    if (log_wr == log_rd) {
        /* Buffer full: advance reader to drop oldest */
        log_rd = (log_rd + 1) % LOG_BUFFER_SIZE;
    }

    /* Echo to console if level allows; we use a global current level? */
    /* The level check is done in kernel_log, not here. */
}

void kernel_log(log_level_t level, const char *fmt, ...) {
    if (level > console_level) {
        /* Message suppressed from console, but still stored? */
        /* In a real system, suppression usually means not printed at all,
           but for learning we still add to ring buffer with metadata. */
        /* Here we ignore completely; see note below. */
        return;
    }

    spin_lock(&log_lock);

    char buf[128];
    va_list args;
    va_start(args, fmt);
    /* Simplified formatting: just copy the string; assume fmt is plain text */
    int i = 0;
    while (fmt[i] && i < sizeof(buf) - 1) {
        buf[i] = fmt[i];
        i++;
    }
    buf[i] = '\0';
    va_end(args);

    for (const char *p = buf; *p; p++) {
        log_putc(*p);
    }

    spin_unlock(&log_lock);
}

void kernel_panic(const char *fmt, ...) {
    local_irq_disable();

    /* Try to print directly to console without lock */
    char buf[128];
    va_list args;
    va_start(args, fmt);
    int i = 0;
    while (fmt[i] && i < sizeof(buf) - 1) {
        buf[i] = fmt[i];
        i++;
    }
    buf[i] = '\0';
    va_end(args);

    for (const char *p = "KERNEL PANIC: "; *p; p++) {
        serial_putchar(*p);
    }
    for (const char *p = buf; *p; p++) {
        serial_putchar(*p);
    }
    serial_putchar('\n');

    dump_stack();
    /* Optionally flush ring buffer to console */
    for (uint32_t i = log_rd; i != log_wr; i = (i + 1) % LOG_BUFFER_SIZE) {
        serial_putchar(log_buffer[i]);
    }

    /* Decide action */
    machine_halt();  /* or machine_restart() */
}

void kernel_oops(const char *fmt, ...) {
    /* Non-fatal error: log and continue */
    char buf[128];
    va_list args;
    va_start(args, fmt);
    int i = 0;
    while (fmt[i] && i < sizeof(buf) - 1) {
        buf[i] = fmt[i];
        i++;
    }
    buf[i] = '\0';
    va_end(args);

    /* Use kernel_log with LOG_ERR level */
    kernel_log(LOG_ERR, "Oops: ");
    kernel_log(LOG_ERR, buf);
    kernel_log(LOG_ERR, "\n");
    dump_stack();
}

A kód több egyszerűsítést tartalmaz. A kernel_log formázása nem valódi vsnprintf; a gyakorlatban ezt a részt ki kell cserélni egy saját vsnprintf implementációra. A console_level ellenőrzése a kernel_log elején történik, és ha a szint alacsonyabb, az üzenet egyáltalán nem kerül a ring bufferbe. Ez leegyszerűsítés; a valódi kernelben a ring buffer minden üzenetet tárol, a konzolra csak a szűrt rész kerül. A tanulási verzióban ez elfogadható, de a laborban finomítható.

A panic függvény megszakítások letiltása után közvetlenül a soros portra ír, megkerülve a ring buffert és a zárat. A dump_stack függvény a verem tartalmát írja ki, amit a QEMU, GDB és kernel debugging fejezetben tárgyaltunk. A machine_halt platformfüggő; QEMU-ban például a hlt utasítás vagy a shutdown regiszter írása lehet.

28.4.10 Labor: kernel log- és panic-terv készítése

Ebben a laborban a feladat egy saját, minimális kernel naplózási és panic tervének elkészítése és emulált környezetben való tesztelése. A labor célja, hogy a fejlesztő megtapasztalja a naplózási réteg működését, és megtervezze a panic viselkedését. A reprodukálhatóság érdekében minden lépést dokumentálni kell, és a méréseket rögzíteni.

28.4.11 Előkészítés

Az emulált környezet QEMU, a vendég kernel a korábbi fejezetekben készített minimális rendszer. A konfiguráció rögzített:

  • CPU: -cpu cortex-a9 (vagy x86_64, a választott architektúra szerint)
  • Memória: 128 MiB
  • Soros konzol: -serial mon:stdio
  • Kernel: saját, freestanding ELF

A build parancsok a reprodukciós csomag részét képezik, például:

make clean
make CFLAGS="-O0 -g -fno-omit-frame-pointer"
qemu-system-arm -M virt -cpu cortex-a9 -m 128M -nographic -kernel kernel.elf

A GDB csatlakoztatásához:

qemu-system-arm -M virt -cpu cortex-a9 -m 128M -nographic -s -S -kernel kernel.elf
gdb-multiarch kernel.elf
(gdb) target remote :1234
(gdb) continue

28.4.12 Feladatok

  1. Ring buffer implementációának tesztelése. Írj egy tesztfüggvényt, amely 200 darab LOG_INFO szintű üzenetet generál, mindegyik egy sorszámmal. A ring buffer mérete legyen 256 bájt. Indítsd el a kernelt, és figyeld a soros kimenetet. Mérd meg:

    • hány üzenet jutott el a konzolra,
    • hány üzenet maradt meg a ring bufferben,
    • az üzenetvesztés arányát.

    A várt eredmény: a konzolra a beállított szint miatt minden LOG_INFO üzenet eljut, de a ring buffer csak az utolsó néhányat őrzi meg, a korábbiak felülíródnak. A mért eredményt naplózd.

  2. Log szintek szűrésének tesztje. Állítsd a console_level értékét LOG_WARNING-ra. Generálj 50 LOG_INFO és 10 LOG_ERR üzenetet. Ellenőrizd, hogy a konzolon csak a LOG_ERR üzenetek jelennek meg, míg a ring bufferben mindkettő megtalálható (ha a pufferméret elegendő). A mérés: a konzol kimenet sorainak száma, a ring bufferben lévő rekordok száma.

  3. Panic teszt. Szándékosan hívj kernel_panic("test panic from timer\n")-t egy időzítő megszakításból. Figyeld meg, hogy a panic üzenet megjelenik-e a soros konzolon, a regiszterek és a verem kiíródnak-e, és a rendszer leáll-e (nem folytatódik a futás). Mérd a panic hívásától a leállásig eltelt időt (például a QEMU napló időbélyegei alapján). Várt eredmény: a panic azonnal leállítja a rendszert, a kimenet tartalmazza a "KERNEL PANIC: test panic from timer" szöveget és a verem nyomkövetést.

  4. Naplóterv dokumentálása. Készíts egy rövid (1 oldalas) tervet, amely meghatározza:

    • a támogatott log szinteket és azok használati politikáját,
    • a ring buffer méretét és a felülírási stratégiát,
    • a panic viselkedését (újraindítás, leállás, watchdog),
    • a crash utáni diagnosztikai adatok mentésének módját (ha van ilyen). A tervet helyezd a labor jegyzetfüzetbe.

28.4.14 Önellenőrző kérdések

  1. Mi a különbség a kernel panic és az oops között? Melyik esetben folytatódhat a rendszer, és miért kockázatos ez?
  2. Miért használ a kernel körkörös puffert a naplózáshoz? Milyen előnyei vannak a dinamikus memóriaallokációval szemben?
  3. Tegyük fel, hogy a console_level értéke LOG_WARNING, és a kernel 100 LOG_DEBUG üzenetet generál. Mi történik ezekkel az üzenetekkel, ha a ring buffer mérete 1 KiB, és minden üzenet átlagosan 64 bájt?
  4. A panic függvény miért nem használhat normál kernelzárakat? Magyarázd el, milyen problémát okozhat egy zár használata a panic kódjában.

28.4.15 Összegzés

A kernel naplózás, a panic és a hibakezelés egymással szorosan összefüggő területek. A jól megtervezett naplózás lehetővé teszi a hibák gyors diagnosztizálását, míg a panic gondos implementációja biztosítja, hogy a rendszer a hibás állapotból ne okozzon további károkat. A gyakorlatban a printk, a log szintek és a ring buffer a leggyakoribb eszközök, amelyeket minden kernel fejlesztőjének ismernie kell.

A következő fejezet (Egyszerű fájlrendszer tervezése) az egyszerű fájlrendszer tervezésére épít, ahol a naplózás és hibakezelés elveit a fájlrendszer rétegben is alkalmazni fogjuk. A fájlrendszer-műveletek során fellépő hibákat ugyanúgy láthatóvá kell tenni, és a panic-re okot adó állapotokat gondosan el kell kerülni. A naplózási réteg kialakítása tehát nem öncélú, hanem a kernel további komponenseinek megbízhatóságát alapozza meg.
