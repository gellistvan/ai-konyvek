27.3 Memóriakezelés és ütemező tervezése

A boot utáni kernel két alrendszer nélkül nem tud tovább építkezni: memóriakezelés és feladatütemezés. Az os103 fejezetben a kernel elindult, a soros konzol már írni tud, és a verem a helyén van. Ebben a fejezetben olyan egyszerű, de valódi komponenseket tervezünk, amelyekre a rendszerhívások, a folyamatok és a userland a későbbi egységekben ráépülnek. A cél nem egy teljes virtuális memóriarendszer vagy egy fair ütemező, hanem egy ellenőrizhető váz, amelyben a fizikai lapok kiosztása, a címfordítás, a taskváltás és az időosztás működik.

27.3.1 1. Fizikai memória és frame allocator

A boot után a kernel rendelkezésére álló fizikai memória tartományát a bootloader vagy a firmware adja meg. A továbbiakban egy QEMU-ban futó, 128 MiB RAM-mal rendelkező, virt típusú emulált gépet feltételezünk; a RAM ebben a példában 0x80000000–0x88000000 között helyezkedik el. A tényleges tartomány hardverfüggő, ezért a kernel először ezt a tartományt rögzíti, és innen kezdve frame-ekkel, azaz 4 KiB méretű fizikai lapokkal dolgozik.

A frame allocator feladata, hogy a fizikai lapokat kiadja és visszavegye. Egy kis, oktatási célú kernelben a legegyszerűbb helyes megoldás a bitmap alapú allokátor. Ebben minden frame-hez egy bit tartozik: ha a bit 1, a lap foglalt, ha 0, szabad. A bitmap maga is memóriát foglal, ezért az inicializáláskor először a bitmap számára le kell foglalni egy darabot a kezelt tartomány elejéről.

A bitmap indexelése a következő összefüggéssel számítható:

𝑖𝑛𝑑𝑒𝑥=𝑝𝑎𝑑𝑑𝑟−𝑏𝑎𝑠𝑒4096 \mathit{index} = \frac{\mathit{paddr} - \mathit{base}}{4096}

A byte- és bitszintű pozíció:

𝑏𝑦𝑡𝑒=𝑖𝑛𝑑𝑒𝑥/8,𝑏𝑖𝑡=𝑖𝑛𝑑𝑒𝑥mod8 \mathit{byte} = \mathit{index} \mathrel{/} 8, \quad \mathit{bit} = \mathit{index} \bmod 8

A következő pszeudokód a frame_init lépéseit mutatja:

// A kód szemléltetés, nem végrehajtandó utasítás az éles gépen.
#define PAGE_SIZE  4096
#define FRAME_BASE 0x80000000UL
#define FRAME_END  0x88000000UL

static uint8_t *bitmap;
static uint32_t total_frames;

void frame_init(void) {
    total_frames = (FRAME_END - FRAME_BASE) / PAGE_SIZE;
    // A bitmap mérete: total_frames / 8 bájt, felfelé kerekítve.
    size_t bitmap_bytes = (total_frames + 7) / 8;
    bitmap = (uint8_t *)FRAME_BASE;
    // Az első frame-eket a bitmap számára lefoglaljuk.
    size_t reserved_frames = (bitmap_bytes + PAGE_SIZE - 1) / PAGE_SIZE;
    for (size_t i = 0; i < reserved_frames; ++i)
        bitmap_set(i, 1);
    // A többi frame szabad.
    for (size_t i = reserved_frames; i < total_frames; ++i)
        bitmap_set(i, 0);
}

A bitmap_set, bitmap_clear és bitmap_test segédfüggvények a fenti byte/bit felbontást valósítják meg. A frame_alloc és frame_free ezekre épül:

uintptr_t frame_alloc(void) {
    for (size_t i = 0; i < total_frames; ++i) {
        if (!bitmap_test(i)) {
            bitmap_set(i, 1);
            return FRAME_BASE + i * PAGE_SIZE;
        }
    }
    return 0; // nincs szabad frame
}

void frame_free(uintptr_t paddr) {
    if (paddr < FRAME_BASE || paddr >= FRAME_END || (paddr & (PAGE_SIZE - 1)))
        return; // hibás cím
    size_t index = (paddr - FRAME_BASE) / PAGE_SIZE;
    bitmap_clear(index);
}

A fenti vázlatban a 0 visszatérési érték hibát jelez, de ez veszélyes, mert a fizikai 0x00000000 cím ritkán ugyan, de nem keverendő össze a hibával. Érdemes inkább INVALID_FRAME konstanst használni, és a hívó oldalon mindig ellenőrizni. A tipikus hibák közé tartozik a kettős felszabadítás, amikor ugyanazt a frame-et kétszer adjuk vissza, és a határellenőrzés hiánya, ami a bitmapen kívüli memóriát módosíthat. A laborban ezért a frame_free előtt érdemes tesztelni, hogy a bit valóban 1-es-e, és csak akkor törölni.

A frame allocator teljesítménye ebben a formában lineáris, mert a szabad lapot keresve végig kell vizsgálni a bitmapet. Ez a célfeladathoz elegendő; a haladó fejezetekben a buddy és slab allocátorok ezt a keresést gyorsítják.

27.3.2 2. Virtuális memória és lapasztal

A fizikai memória önmagában csak egy sor frame. A virtuális memória lehetővé teszi, hogy minden feladat saját, védett címtérben fusson, és a kernel a fizikai lapokat szükség szerint képezze be. A címfordítást az MMU végzi a lapasztal (page table) alapján.

Ebben a fejezetben egy 32 bites, két szintű lapozást használunk, 4 KiB lapmérettel. A virtuális cím három részre oszlik:

  • Page Directory Index (PDI): a felső 10 bit.
  • Page Table Index (PTI): a középső 10 bit.
  • Offset: az alsó 12 bit.

A felbontás képlete:

𝑃𝐷𝐼=(𝑣𝑎𝑑𝑑𝑟≫22)&0x3FF \mathit{PDI} = (\mathit{vaddr} \gg 22) \mathrel{\&} 0x3FF

𝑃𝑇𝐼=(𝑣𝑎𝑑𝑑𝑟≫12)&0x3FF \mathit{PTI} = (\mathit{vaddr} \gg 12) \mathrel{\&} 0x3FF

𝑜𝑓𝑓𝑠𝑒𝑡=𝑣𝑎𝑑𝑑𝑟&0xFFF \mathit{offset} = \mathit{vaddr} \mathrel{\&} 0xFFF

A page directory minden bejegyzése egy page table-re mutat, a page table bejegyzései pedig fizikai frame-ekre. A bejegyzések alsó bitjei flag-ek: a PRESENT bit jelzi, hogy a lap a memóriában van, az RW bit az írási jogot, az USER bit a felhasználói hozzáférést vezérli. A kernel attól függően, hogy milyen architektúrán fut, eltérő flagkészletet használ, de az elv ugyanaz.

A lapkezelő API három műveletre épül:

  1. walk_page(pgdir, vaddr, alloc) – megkeresi a virtuális címhez tartozó page table bejegyzést. Ha a page table még nem létezik, és az alloc igaz, lefoglal egy frame-et a page table számára.
  2. map_page(pgdir, vaddr, paddr, flags) – bejegyzést hoz létre a virtuális cím és a fizikai frame között.
  3. unmap_page(pgdir, vaddr) – törli a bejegyzést.

A következő C-vázlat a walk_page és a map_page működését mutatja be. A példa feltételezi, hogy a kernel a korai fázisban identity mapped, vagyis a fizikai címeket közvetlenül eléri; a lapkezelő ezért fizikai címekkel dolgozik.

// Szemléltető C vázlat, nem végrehajtandó utasítás.
typedef uint32_t pte_t;
typedef uint32_t pde_t;

#define PTE_PRESENT  0x001
#define PTE_RW       0x002
#define PTE_USER     0x004

pte_t *walk_page(uint32_t *pgdir, uintptr_t vaddr, int alloc) {
    uint32_t *pde = &pgdir[(vaddr >> 22) & 0x3FF];

    if (!(*pde & PTE_PRESENT)) {
        if (!alloc)
            return NULL;
        uintptr_t pte_frame = frame_alloc();
        if (!pte_frame)
            return NULL;
        *pde = (pte_frame & 0xFFFFF000) | PTE_PRESENT | PTE_RW;
        // Az új page table-t nullázni kell.
        memset((void *)pte_frame, 0, PAGE_SIZE);
    }

    uint32_t *pt = (uint32_t *)(*pde & 0xFFFFF000);
    return &pt[(vaddr >> 12) & 0x3FF];
}

int map_page(uint32_t *pgdir, uintptr_t vaddr, uintptr_t paddr, uint32_t flags) {
    pte_t *pte = walk_page(pgdir, vaddr, 1);
    if (!pte)
        return -1;
    if (*pte & PTE_PRESENT)
        return -1; // a cím már le van képezve
    *pte = (paddr & 0xFFFFF000) | (flags & 0xFFF) | PTE_PRESENT;
    return 0;
}

A map_page hibát ad, ha a fizikai cím nincs laphatárra igazítva, vagy ha már létezik a leképezés. Az utóbbi ellenőrzés azért fontos, mert két feladat nem kaphatja meg ugyanazt a virtuális címet különböző jelentéssel ugyanabban a lapasztalban úgy, hogy az adat sérüljön. A gyakorlatban a kernel a saját lapozását identity mappinggel indítja, majd a feladatok számára külön page directory-t hoz létre.

A lapkezelő hívásakor a TLB (translation lookaside buffer) tartalma elavulhat. Ezért minden map_page és unmap_page után a megfelelő architektúra-specifikus TLB-invalidálást is el kell végezni. Ennek elmaradása a legnehezebben megtalálható memóriahibák egyike: a program néha a régi leképezést látja, néha az újat, attól függően, hogy a TLB-ben éppen mi van.

27.3.3 3. Feladatok és a task control block

A feladatok kezeléséhez a kernel minden végrehajtási egységhez egy Task Control Blockot (TCB) rendel. Ez a struktúra tárolja a feladat azonosítóját, állapotát, saját lapasztalát, veremmutatóját és a CPU kontextusát.

Egy kezdetleges, de tanítható TCB a következő mezőket tartalmazza:

typedef enum {
    TASK_READY,
    TASK_RUNNING,
    TASK_BLOCKED,
    TASK_EXITED
} task_state_t;

typedef struct task {
    uint32_t pid;
    task_state_t state;
    uint32_t *page_dir;     // a feladat saját lapasztala
    void *stack_top;        // a kernelstack teteje
    struct cpu_context *ctx; // mentett regiszterek
    uint32_t quantum_left;  // hátralévő kvantum
    struct task *next;      // láncolt lista
} task_t;

Az állapotátmenetek egy korai kernelben egyszerűek. A feladat a READY állapotból kerül RUNNING állapotba, amikor az ütemező kiválasztja. Ha a kvantum lejár, visszakerül READY-be. Ha egy eseményre vár, például egy jövőbeli I/O-műveletre, BLOCKED állapotba kerül, és az esemény bekövetkezése után újra READY lesz. A befejezett feladat EXITED állapotot kap, és a TCB felszabadítható.

A feladatok tárolása a legegyszerűbb módon egy statikus tömbben történik, a szabad helyeket egy láncolt lista, azaz free list tartja nyilván. Ebben a fázisban a feladatok száma kicsi, ezért a dinamikus memóriafoglalás helyett a statikus tömb is elegendő, és elkerüli a kernel heapjének korai inicializálását.

27.3.4 4. Round-robin ütemező

A round-robin ütemező a legegyszerűbb időosztásos algoritmus. Minden READY feladat azonos kvantumot kap, és a feladatok körkörös sorrendben futnak. Ha az aktuális feladat kvantuma lejár, az ütemező a következő READY feladatra vált, a lejárt feladatot pedig a sor végére állítja.

A működéshez egy ciklikus ready queue kell. A task_t struktúra next mezője erre a listára mutat. Az ütemező két fő függvénye a scheduler_tick és a schedule.

A scheduler_tick minden timer-interruptnál lefut, és csökkenti az aktuális feladat kvantumát. Ha a kvantum elfogy, a feladat kvantumát visszaállítja, és ütemezést kér:

#define QUANTUM 10 // 10 timer tick, 1 tick = 1 ms

void scheduler_tick(void) {
    if (current == NULL || current->state != TASK_RUNNING)
        return;
    if (--current->quantum_left <= 0) {
        current->quantum_left = QUANTUM;
        current->state = TASK_READY;
        schedule();
    }
}

A schedule kiválasztja a következő futásra kész feladatot. A ready listán a current next mutatójától kezdve keres. Ha nem talál más feladatot, az aktuális marad futásban. A feladatok cseréjéhez a context_switch függvényre van szükség, amelyet a következő szakasz tárgyal.

void schedule(void) {
    if (current == NULL)
        return;

    task_t *old = current;
    task_t *next = old->next;

    // Olyan feladatot keresünk, amelyik futásra kész.
    while (next != old && next->state != TASK_READY && next->state != TASK_RUNNING)
        next = next->next;

    if (next == old || next->state != TASK_READY)
        return; // nincs másik futtatható feladat

    old->state = (old->state == TASK_RUNNING) ? TASK_READY : old->state;
    next->state = TASK_RUNNING;
    task_t *prev = current;
    current = next;
    context_switch(&prev->ctx, &next->ctx);
}

A context_switch a két task kontextusát cseréli. A ready queue forgatását legegyszerűbben úgy lehet elvégezni, hogy a scheduler_tick lejárt kvantumnál az aktuális feladatot a lista végére fűzi, de ez a kódvázlatban a next kereséssel valósul meg. A fontos invariáns: mindig legyen legalább egy futásra kész feladat, különben a ready queue üres lesz, és a rendszer leáll.

A következő Gantt-diagram három feladat (P1, P2, P3) futását mutatja, 10 ms kvantummal:

Idő(ms):   0     10    20    30    40    50
         |  P1  |  P2  |  P3  |  P1  |  P2  |

Jelmagyarázat: egy cella egy teljes kvantum. A függőleges vonalak a timer-interrupt és a taskváltás pillanatai. A váltás időigénye ebben az ábrán elhanyagoltnak tekinthető, de a laborban érdemes mérni.

27.3.5 5. Kontextusváltás és idle task

A kontextusváltás az a pillanat, amikor a CPU az egyik feladat regisztereit és veremmutatóját elmenti, majd egy másik feladatét betölti. A mentendő állapotot cpu context-nek nevezzük. Ez legalább a következőket tartalmazza:

  • általános célú regiszterek,
  • veremmutató (ESP/RSP),
  • utasításmutató (EIP/RIP),
  • lapasztal regiszter (CR3),
  • állapotregiszter (EFLAGS/RFLAGS).

A váltás assembly szinten történik, mert a C nem fér hozzá közvetlenül a regiszterekhez. A következő pszeudokód a váltás vázlatát adja meg:

; Szemléltető assembly vázlat, nem végrehajtandó utasítás.
; context_switch(old_ctx, new_ctx)
context_switch:
    ; 1. A hívó által megőrzött regiszterek mentése a veremre.
    push ebp
    push ebx
    push esi
    push edi

    ; 2. Az aktuális veremmutató mentése az old_ctx-be.
    mov  eax, [esp + 20]   ; old_ctx címe
    mov  [eax], esp

    ; 3. Az új veremmutató betöltése.
    mov  ebx, [esp + 24]   ; new_ctx címe
    mov  esp, [ebx]

    ; 4. A regiszterek visszaállítása az új veremről.
    pop  edi
    pop  esi
    pop  ebx
    pop  ebp
    ret

Ez a vázlat csak a kernelstacket cseréli; a lapasztal cseréje a CR3 regiszter módosításával történik, amit a hívó C kód végez el a context_switch előtt vagy után. A kernel a saját lapozását minden feladatnál közösen használhatja, de a felhasználói címterek eltérőek. A pontos megvalósítás architektúrafüggő, és a os107 fejezet részletezi a kész kernelben.

Az idle task az a feladat, amely akkor fut, amikor nincs más futásra kész munka. A round-robin ütemezőben azért kritikus, mert a ready queue soha nem lehet üres: ha nincs felhasználói feladat, a CPU-n akkor is kell egy végrehajtási egység. Az idle task a legalacsonyabb prioritású, soha nem blokkol, és a CPU-t alacsony fogyasztású állapotba helyezi:

void idle_task(void) {
    for (;;) {
        asm volatile("hlt"); // x86: HLT, RISC-V: WFI
    }
}

A HLT vagy WFI utasítás leállítja a CPU futószalagját, amíg megszakítás nem érkezik. Így a timer interrupt felébreszti, a scheduler_tick lefut, és ha van READY feladat, az ütemező arra vált. Az idle task jelenléte a rendszer stabilitásának alapfeltétele.

27.3.6 6. Integráció és inicializálás

A memóriakezelő és az ütemező beüzemelése szigorú sorrendben történik. A boot utáni kernel inicializáló kódja a következő lépéseket hajtja végre:

  1. Frame allocator inicializálása – a rendelkezésre álló fizikai tartomány felmérése és a bitmap elhelyezése.
  2. Kernel lapozás felépítése – az első néhány MiB identity mappinggel, hogy a kernel továbbra is elérje a fizikai memóriát.
  3. Ütemező inicializálása – a task tömbből free list építése.
  4. Idle task létrehozása – a ready queue első eleme.
  5. Első felhasználói task létrehozása – a tesztfeladat saját lapasztallal és stackkel.
  6. Timer bekapcsolása – a timer interrupt engedélyezése, a scheduler_tick bekötése.
  7. Átadás az ütemezőnek – az első schedule hívás.

A folyamat pszeudokódban:

void kernel_init(void) {
    frame_init();
    init_kernel_page_table();
    init_scheduler();
    create_idle_task();
    create_first_task();
    enable_timer();
    schedule(); // innen kezdve a feladatok váltakozva futnak
}

A create_first_task egy olyan feladatot hoz létre, amely a saját page directoryjával rendelkezik, és a kernelből átmásolt kódot futtat. A feladat létrehozásakor a cpu_context kezdőértékét úgy kell beállítani, hogy a context_switch utáni ret a feladat belépési pontjára ugorjon, és a verem a megadott stack_top-on legyen.

27.3.7 7. Labor: lapkezelő és ütemező vázlat

A labor célja, hogy a fenti komponenseket egy emulált környezetben összeállítsa, és a működést mérje. A labor a os103 bootkódjára épül, és QEMU-ban fut. A kiinduló állapot: a kernel betöltődik, a soros konzol működik, de memóriakezelő és ütemező még nincs.

27.3.8 7.1. Konfiguráció és build

A reprodukálhatósághoz rögzítsük az emulált gépet:

  • qemu-system-riscv64 -machine virt -m 128M -kernel kernel.elf -nographic
  • CPU: rv64, a timer interrupt a virt gépben a mtimecmp és mtime regisztereken keresztül érhető el.
  • A kernel fordításához riscv64-unknown-elf-gcc és ld szükséges, a linker script a kernel.ld.

A labor minden lépését jegyzetfüzetben kell rögzíteni, ahol a buildparancs, a futtatási parancs és a napló együtt látható. A git kezdő commit a kiinduló állapot; a labor után a git diff mutatja a változtatásokat, így a visszaállítás egy git reset --hard paranccsal megoldható.

27.3.9 7.2. Feladatok

  1. Frame allocator – Implementálja a frame_init, frame_alloc, frame_free függvényeket a megadott memóriatartományra. Tesztelje, hogy az első lefoglalások a bitmap után következő szabad frame-eket adják vissza, és hogy a felszabadítás után a frame újra lefoglalható.
  2. Lapkezelő – Építse fel a saját kernel page directoryt. Képezze be a kernel első 8 MiB-ját identity mappinggel, majd hozzon létre egy teszt virtuális címet, például 0x40000000, amely egy frissen lefoglalt fizikai frame-re mutat.
  3. Ütemező – Hozzon létre három feladatot, amelyek mindegyike a soros konzolra írja a saját azonosítóját, majd yield-el. Az idle task egy WFI utasítást hajt végre. A timer interrupt 1 kHz-en fut, a kvantum 10 tick.
  4. Mérés – Mérje a kontextusváltás idejét ciklusszámlálóval. A mcycle regiszter olvasása a váltás előtt és után adja a különbséget. A mérést legalább 100 váltáson végezze el.

27.3.10 7.3. Elvárt és mért eredmény

A labor során külön kell választani a várt és a mért értékeket.

  3. Milyen lépésekből áll a map_page? Miért kell a page table-t nullázni az első lefoglalás után, és mi történik, ha a TLB-t nem invalidáljuk?

27.3.13 9. Összefoglalás

Ez a fejezet felépítette a kernel két alapvető alrendszerének vázát: a frame allocator és a lapkezelő a fizikai memória felosztásáért és a virtuális címek leképezéséért felel, az ütemező pedig a feladatok végrehajtását osztja időben. A round-robin algoritmus, a context switch és az idle task együtt biztosítják, hogy a rendszer soha ne álljon le, és a feladatok fair módon jussanak CPU-időhöz. A következő fejezet (os105) ezekre az alapokra építve bevezeti a rendszerhívásokat és a userland belépési pontját, amihez a lapkezelő USER flagje és az ütemező taskváltása már rendelkezésre áll.
