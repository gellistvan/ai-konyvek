28.2 Interruptkezelés, időzítő és kontextusváltás

28.2.1 7.7 Megszakításkezelés, időzítő és kontextusváltás

Az előző egységben (C és assembly alapok, fordítás és linkelés) felépítettük a kernelt C és assembly forráskódokból, és sikerült a bootolást egy minimális függvényhívásig eljuttatni. Ez a futtatható kép azonban még passzív: a CPU utasításról utasításra hajtja végre a kódot, de nem reagál a külvilág eseményeire, nem képes több folyamatot időosztásosan futtatni, és nem tudja megszakítani a felhasználói kódot. Ebben az alfejezetben a kernel “életre keltésének” három alappillérét építjük fel: a megszakítások (interrupt) tárgyalását, a rendszer időzítőjének (timer) bevezetését, valamint a folyamatok közötti átkapcsolást lehetővé tevő kontextusváltást (context switch).

Az itt bemutatott kód és viselkedés szorosan kapcsolódik az általános OS-elmélethez, de a megvalósítás szintjén az x86-64 architektúrát és az ahhoz kapcsolódó szabványos periféria-illesztőket (PIC, PIT) használjuk. Fontos megjegyezni, hogy ezek a hardverkomponensek a modern rendszerekben már javarészt újabb interfészeknek adták át a helyüket (APIC, HPET), de az emulált QEMU környezetben kiválóan alkalmasak az alapelvek tanítására, mivel programozásuk egyszerű, determinisztikus, és nem igényel bonyolult specifikációs réteget.

28.2.1.1 A megszakítások és az időzítő szerepe

Az operációs rendszer kernelének alapvető működési módja az eseményvezérelt (event-driven) modell. A CPU a felhasználói program végrehajtása vagy éppen az idle hurok közben külső eseményekről kell, hogy értesüljön. Ilyen esemény lehet egy billentyűleütés, egy hálózati csomag érkezése, egy lemez I/O befejezése, vagy éppen egy hibás memóriacím elérése.

A hardver és a CPU közötti kommunikáció két alapvető módja a polling és a megszakítás (interrupt). Polling esetén a kernel folyamatosan, aktívan kérdezgeti az eszközök állapotregisztereit, hogy történt-e esemény. Ez a megoldás rendkívül pazarló: a CPU feleslegesen pörög, és a késleltetési idő függ a lekérdezés gyakoriságától. A megszakítás ezzel szemben egy hardveres jelzés: az eszköz (vagy a CPU maga egy kivétel esetén) félbeszakítja a futó utasításfolyamot, és a vezérlést a kernel egy előre meghatározott belépési pontjára adja.

A megszakítások szerepe három fő pontban foglalható össze:

  1. Reaktivitás: A kernelnek azonnal tudnia kell reagálni a hardvereseményekre anélkül, hogy a futó felhasználói kódot együttműködésre kényszerítené.
  2. Védelem és hibakezelés: A kivételek (pl. nullával való osztás, érvénytelen cím elérése) szintén megszakítási mechanizmuson keresztül jutnak a kernel tudomására. Ez teszi lehetővé a folyamatok izolációját.
  3. Preemptív ütemezés: A kernel nem bízhat abban, hogy egy felhasználói program önként visszaadja a CPU-t. Az időzítő megszakítás az a “szívverés”, amely rendszeres időközönként visszaadja a vezérlést a kernel ütemezőjének.

Az időzítő (timer) tehát a megszakítási rendszer egyik legkritikusabb eleme. Az időzítő egy programozható oszcillátor (pl. az Intel 8253/8254 Programmable Interval Timer, PIT), amelyet úgy állítunk be, hogy periodikusan, például f=100f=100 Hz-es gyakorisággal megszakítást generáljon. Ennek periódusideje Ttick=1f=10,000μsT_{tick} = \frac{1}{f} = 10{,}000\ \mu\mathrm{s}. A kernel ezt a megszakítást “tick”-ként tartja nyilván. A tick szerepe kettős: egyrészt frissíti a rendszer belső óráját (uptime, jiffies), másrészt meghívja az ütemezőt (scheduler), amely eldönti, hogy az éppen futó folyamat lejárt-e már a rendelkezésére álló időszeletéből (time slice), és szükség van-e kontextusváltásra.

28.2.1.2 Az IDT és a megszakítási útvonal

Ahhoz, hogy a CPU tudja, hová ugorjon, ha egy megszakítás érkezik, egy speciális adatszerkezetre van szükség: az Interrupt Descriptor Table (IDT). Az IDT nem más, mint egy olyan bejegyzésekből (gate) álló tömb, amely a CPU által ismert megszakítási vektorokhoz (0-255) rendel belépési pontokat.

A Linux és a legtöbb modern x86-64 kernel a 0x20-as vektor felett használja a szoftveres megszakításokat, mivel a 0-31 közötti vektorok a CPU kivételei számára vannak fenntartva (pl. 0: Division Error, 13: General Protection Fault, 14: Page Fault). A hardveres megszakításokat (IRQ-k) a régi 8259A PIC (Programmable Interrupt Controller) alapból a 0x08-0x0F vektorokra irányítaná, ami ütközik a CPU kivételeivel. Ezért a PIC-et remapeljük, vagyis áthelyezzük a hardveres megszakításokat a 0x20-0x2F tartományba.

Egy IDT bejegyzés struktúrája C-ben a következőképpen írható le (a gép szóhosszának megfelelően x86-64 módban 16 bájt):

struct idt_entry {
    uint16_t base_low;    // A handler címének alsó 16 bitje
    uint16_t selector;    // Kernel kód szegmens szelektor (0x08)
    uint8_t  ist;         // Interrupt Stack Table index (itt 0)
    uint8_t  type_attr;   // 0x8E: Present, DPL=0, 32/64-bit Interrupt Gate
    uint16_t base_mid;    // A handler címének középső 16 bitje
    uint32_t base_high;   // A handler címének felső 32 bitje
    uint32_t zero;        // Fenntartva, kötelezően 0
} __attribute__((packed));

A kernel inicializálásakor (idt_init) a NULL pointerrel való hibás hívásra fenn kell tartanunk a 0. vektort, be kell töltenünk a CPU kivételeit kezelő rutinokat, majd a hardveres megszakításokra a megfelelő ISR-eket (Interrupt Service Routine). Az IDT eléréséhez használt mutatót az LIDT utasítással kell betölteni:

struct idt_ptr {
    uint16_t limit;
    uint64_t base;
} __attribute__((packed));

void idt_load(struct idt_ptr*);
; idt_load (assembly)
; Betölti az IDT mutatót az IDTR regiszterbe
global idt_load
idt_load:
    lidt [rdi]   ; RDI tartalmazza az idt_ptr* mutatót
    ret

A kernel inicializálásakor a load_idt meghívása után a CPU már képes megszakítást fogadni, bár a STI utasításig letiltott állapotban van. A STI (Set Interrupt Flag) engedélyezi a hardveres megszakítások fogadását.

28.2.1.3 ISR-ek és a megszakítási kód

A megszakítási vektorhoz tartozó függvényben assembly szinten kell elvégezni a “regisztermentést”. A C ABI (Application Binary Interface) szerint egy C függvény a regiszterek egy részét (caller-saved: RAX, RCX, RDX, RSI, RDI, R8-R11) szabadon módosíthatja. Ha a megszakítás egy felhasználói program futása közben érkezik, a megszakításkezelőből visszatérve a felhasználói program állapotát bitre pontosan ugyanabban az állapotban kell helyreállítani, mintha mi sem történt volna, kivéve, ha a kernel kontextusváltást tervez.

Ehhez egy interrupt stub-ot (csonkot) írunk assemblyben, amely elmenti a CPU regisztereit a veremre, meghívja a magas szintű C nyelvű kezelőt, majd visszatérés előtt visszaállítja a regisztereket és az IRETQ utasítással visszatér a megszakított kontextusba.

A hardveres megszakítások kezelésére az x86-64-ben a következő mintát alkalmazzuk:

; Megszakítási csonk (ISR stub)
%macro ISR_NOERRCODE 1
global isr_stub_%1
isr_stub_%1:
    push 0          ; Hamis hibakód a konzisztens veremképhez
    push %1         ; Megszakítási vektor száma
    jmp isr_common
%endmacro

%macro ISR_ERRCODE 1
global isr_stub_%1
isr_stub_%1:
    ; A CPU automatikusan tolja a hibakódot a verembe
    push %1         ; Megszakítási vektor száma
    jmp isr_common
%endmacro

; IRQ-k a remapelt vektorokon (0x20-0x2F)
ISR_NOERRCODE 32
ISR_NOERRCODE 33
; ... és így tovább ...

A közös belépési rutin (isr_common) menti a C ABI megőrzéséhez szükséges regisztereket. A legkritikusabb lépések: az RSP igazítása és a kernel stack használata. Amikor egy felhasználói folyamat fut, a CPU az RSP-t a felhasználói veremre állítva hívja meg a megszakítást. A kernelnek gondoskodnia kell arról, hogy a kernel adatai ne a felhasználói veremre kerüljenek. Ezt a feladatot a TSS (Task State Segment) RSP0 mezője oldja meg: amikor a CPU alacsonyabb privilégiumszintről (ring 3) magasabbra (ring 0) vált, automatikusan betölti a kernel veremmutatót az RSP0 mezőből. Ha már kernel módban vagyunk, a verem marad az aktuális kernel verem.

A isr_common lényege:

isr_common:
    ; C ABI szerinti callee-saved regiszterek mentése
    push rax
    push rcx
    push rdx
    push rsi
    push rdi
    push r8
    push r9
    push r10
    push r11

    ; Hívjuk a C nyelvű diszpécsert
    mov rdi, rsp        ; RDI = pointer a veremkeretre (pt_regs)
    call interrupt_handler

    ; Visszatérés a megszakításból
    pop r11
    pop r10
    pop r9
    pop r8
    pop rdi
    pop rsi
    pop rdx
    pop rcx
    pop rax

    ; Eltávolítjuk a vektor számát és a hibakódot
    add rsp, 16
    iretq

A C nyelvű interrupt_handler megkapja a veremkeretre mutató pointert. Ebből ki tudja olvasni a megszakítás számát, és el tudja dönteni, hogy kivételt (pl. laphiba) vagy hardveres megszakítást kapott-e.

struct pt_regs {
    uint64_t r11, r10, r9, r8;
    uint64_t rdi, rsi, rdx, rcx, rax;
    uint64_t int_no;      // Megszakítás vektora
    uint64_t err_code;    // Hibakód (ha van)
    uint64_t rip;         // Megszakított utasítás címe
    uint64_t cs;          // Kód szegmens
    uint64_t rflags;      // CPU flag-ek
    uint64_t rsp;         // Veremmutató a megszakítás pillanatában
    uint64_t ss;          // Verem szegmens
};

void interrupt_handler(struct pt_regs *regs) {
    if (regs->int_no == 14) {
        // Laphiba kezelése (lásd későbbi memória fejezet)
        // ...
        return;
    }
    if (regs->int_no >= 32 && regs->int_no <= 47) {
        // Hardveres megszakítás (IRQ 0-15)
        irq_handler(regs->int_no - 32);
    }
}

28.2.1.4 A PIT és a Timer Tick

A kontextusváltás rendszeres kiváltásához szükségünk van egy időforrásra. A QEMU-ban a legegyszerűbb a PIT (Programmable Interval Timer) használata. A PIT három csatornával rendelkezik, amelyek közül a 0. csatorna van a rendszer-időzítőhöz kötve. Az alap órajele 1,193,1821{,}193{,}182 Hz.

Ahhoz, hogy 100 Hz-es megszakítást kapjunk, ki kell számolnunk az osztó értékét: D=1,193,182100=11,931,82≈11,932D = \frac{1{,}193{,}182}{100} = 11{,}931{,}82 \approx 11{,}932 A valóságban, mivel a PIT csak egész osztót fogad el, a tényleges frekvencia freal=1,193,18211,932≈100,0007f_{real} = \frac{1{,}193{,}182}{11{,}932} \approx 100{,}0007 Hz lesz, ami elhanyagolható eltérés. A beállításhoz a 0x43-as portra írjuk a vezérlő bájtot (0x36), majd a 0x40-es portra két lépésben az osztó alsó és felső bájtját.

#define PIT_CHANNEL0 0x40
#define PIT_CMD      0x43

void timer_init(uint32_t frequency_hz) {
    uint32_t divisor = 1193182 / frequency_hz;

    // 0x36: 0011 0110
    // Csatorna 0, mindkét bájt kiírása, 3-as mód (négyszögjel)
    outb(PIT_CMD, 0x36);
    outb(PIT_CHANNEL0, (uint8_t)(divisor & 0xFF));
    outb(PIT_CHANNEL0, (uint8_t)((divisor >> 8) & 0xFF));
}

A rendszer futása során a kernel egy timer_ticks nevű globális változót növel. Az irq_handler-ben megvizsgáljuk az IRQ számát. Ha az 0 (azaz a remapelt 32-es vektor), akkor a PIT megszakadt.

volatile uint64_t timer_ticks = 0;

void irq_handler(unsigned int irq) {
    if (irq == 0) {
        // PIT tick
        timer_ticks++;
        // Itt hívjuk meg az ütemezőt (ld. kontextusváltás)
        scheduler_tick();
    }
    // EOI (End of Interrupt) elküldése a PIC-nek
    if (irq >= 8) {
        outb(0xA0, 0x20); // Slave PIC EOI
    }
    outb(0x20, 0x20); // Master PIC EOI
}

Kritikus hibaforrás: Ha az EOI (End of Interrupt) jelzést elfelejtjük elküldeni a PIC-nek, az nem fog több megszakítást generálni, így az időzítő megáll, és a rendszer lefagy. Ez az egyik leggyakoribb hiba a kezdő kernelhackelés során.

28.2.1.5 A kontextusváltás mechanizmusa

A kontextusváltás (context switch) az a folyamat, amikor a kernel a CPU vezérlését az egyik folyamatból (P1P_1) átadja egy másiknak (P2P_2). Ez a legbonyolultabb és legalacsonyabb szintű művelet a kernelben, mivel közvetlenül a CPU regisztereivel és a veremmel dolgozik.

Elméletben a kontextusváltás a következő lépésekből áll: 1. Belépés a kernelbe: Egy megszakítás (általában a timer tick) vagy egy rendszerhívás hatására a CPU kernel módba vált, és a folyamat kernel vermére ugrik. 2. Állapotmentés: A kernel elmenti az aktuális folyamat (P1P_1) architekturális állapotát (regiszterek, utasításmutató, veremmutató) a folyamat leíró táblájába (PCB). 3. Döntés: Az ütemező kiválasztja a következő futó folyamatot (P2P_2). 4. Állapot-visszaállítás: A kernel betölti P2P_2 PCB-jéből a korábban elmentett architekturális állapotot. 5. Visszatérés: A kernel visszatér a megszakításból, és a CPU a P2P_2 folyamat utolsó kernelbeli pontján folytatja a végrehajtást, majd visszatér a felhasználói térbe.

A gyakorlati megvalósítás során a context_switch függvénynek el kell mentenie a callee-saved regisztereket, át kell állítania a veremmutatót, majd vissza kell állítania az új folyamat regisztereit. Az x86-64 ABI szerint ezek az RBX, RBP, R12-R15 regiszterek.

A kontextusváltás egy egyszerű, de működő modelljét a következőképpen valósíthatjuk meg. Minden folyamatnak van egy task_struct (vagy PCB) struktúrája, amelynek első mezője a kernel stack tetejére mutató pointer (rsp). Amikor a folyamat fut, a kernel stack tetején vannak a callee-saved regiszterek és a visszatérési cím.

; context_switch(uint64_t *old_rsp, uint64_t new_rsp)
; RDI = mutató az aktuális folyamat rsp mezőjére
; RSI = az új folyamat rsp értéke
global context_switch
context_switch:
    ; Callee-saved regiszterek mentése a JELENLEGI kernel veremre
    push rbx
    push rbp
    push r12
    push r13
    push r14
    push r15

    ; Az aktuális kernel veremmutató elmentése az 'old_rsp' pointerre
    mov [rdi], rsp

    ; Az új veremmutató beállítása
    mov rsp, rsi

    ; Callee-saved regiszterek visszaállítása az ÚJ veremről
    pop r15
    pop r14
    pop r13
    pop r12
    pop rbp
    pop rbx

    ; Visszatérés az új folyamat context_switch hívása utáni pontjára
    ret

A fenti assembly kód kulcsfontosságú trükkje a ret utasítás. Amikor P1P_1 meghívja a context_switch-et, a call utasítás a P1P_1 visszatérési címét (R1R_1) a verem tetejére helyezi. A függvény elején ezt a címet további 6 regiszter mentése fedi. Amikor elmentjük az rsp-t, a P1P_1 kernel állapota félbehagyva marad.

Amikor legközelebb valaki visszakapcsol P1P_1-re, az rsp pontosan arra a pontra fog mutatni. A kód visszaállítja a regisztereket, majd a ret ezen a veremcímen a mentett R1R_1 címet fogja látni, és oda ugrik. Így P1P_1 számára úgy tűnik, mintha a context_switch függvény egyszerűen csak visszatért volna, miközben a valóságban közben milliónyi utasítást hajtott végre egy másik folyamat.

A preemptív ütemező kapcsolása: A scheduler_tick függvényben a tick számláló alapján eldönthetjük, hogy lejárt-e a folyamat időszelete. Ha igen, a context_switch segítségével átváltunk egy másik, futásra kész folyamatra.

Tegyük fel, hogy van egy nagyon egyszerű, round-robin ütemezőnk, ahol két folyamat (task_a és task_b) váltja egymást. A scheduler_tick megnézi, hogy az aktuális folyamat time_slice értéke elérte-e a 0-t. Ha igen, akkor meghívja a context_switch-et.

void scheduler_tick() {
    if (current->time_slice > 0) {
        current->time_slice--;
    }
    if (current->time_slice == 0) {
        // Váltsunk!
        struct task *next = (current == &task_a) ? &task_b : &task_a;
        next->time_slice = 10; // Adjunk 10 tick időt

        uint64_t old_rsp = current->rsp;
        current = next;

        // Assembly hívás: az aktuális verem mentése, új verem betöltése
        context_switch(&old_rsp, current->rsp);
    }
}

Fontos versenyhelyzeti megjegyzés: A context_switch hívása a megszakításkezelő kontextusában történik. Ez azt jelenti, hogy az új folyamat futtatása is a megszakításkezelő belsejében kezdődik. Ez a legtöbb oktatási kernelben így működik, de meg kell értenünk, hogy a context_switch-ből való visszatérés után az új folyamat a scheduler_tick függvényből tér vissza a megszakításkezelőbe, ahol az EOI-t elküldjük, majd az iretq-val a felhasználói folyamatra. Ez a minta biztosítja, hogy a váltás atomi, mert megszakítások tiltva vannak (vagy a folyamat éppen kernel módban van).

28.2.1.6 Hibakezelés és tipikus csapdák

A megszakításkezelés és a kontextusváltás során a legalattomosabb hibák általában nem fordítási hibák, hanem finom logikai vagy konvencióbeli eltérések:

  1. Hiányzó EOI: Ahogy korábban említettük, a PIC-hez nem küldött EOI után a rendszer lefagy. Ha a “timer tick” nyomkövetése azt mutatja, hogy egyszer lefut, majd megáll, ellenőrizzük az EOI logikát.
  2. ABI megsértése: Ha a isr_common rutinban elfelejtünk egy callee-saved regisztert elmenteni, a megszakításból visszatérve a futó program rejtélyes regiszterérték-korrupciót fog látni. Ez különösen akkor jelentkezik, ha a C kódot magas optimalizálási szinten (-O2) fordítjuk, ahol a fordító erősen támaszkodik az ABI-ra.
  3. Helytelen IDT bejegyzés: Ha a type_attr mezőben a Present bitet nem állítjuk be, vagy rossz a DPL (Descriptor Privilege Level) értéke, a CPU General Protection Fault-tal (#GP) fog leállni a megszakítás kiváltásának pillanatában.
  4. Veremigazítás hiánya: Az x86-64 System V ABI előírja, hogy a call utasítás előtt a verem 16 bájtra legyen igazítva. A megszakítási stubokban a hamis hibakódok és vektorok pusholása eltolhatja az igazítást. Ha a C függvényben SSE utasításokat használunk (pl. movaps), az hibás címhez vezet.
  5. Szelektor hiba: A kontextusváltás során a cs és ss szegmensszelektorokat nem szabad elfelejteni. Bár a modern x86-64-ben ezek nagyrészt statikusak, a felhasználói és kernel mód közötti váltásnál (iretq) a CPU ellenőrzi ezeket.

28.2.1.7 Labor: IDT- és interrupt-handler vázlat

A cél egy olyan minimumrendszer készítése, amely bizonyítja, hogy a megszakítási rendszerünk működik. A labor során a QEMU-ban futtatott kernelünk kap egy PIT által generált megszakítást, a megszakításkezelő megnövel egy számlálót, és a képernyőre írva vizuálisan is igazoljuk a működést.

Kiinduló állapot: Az os106 fejezetben elkészített freestanding C/Assembly build környezet (linker script, boot.s, kernel.c).

Feladatok:

  1. Hozz létre egy idt.c fájlt az IDT bejegyzések inicializálásához. Írj egy set_idt_gate függvényt, amely feltölti a struct idt_entry mezőit. A selector értéke 0x08 legyen, a type_attr értéke pedig 0x8E (Interrupt Gate, Ring 0).
  2. Hozz létre egy isr.s assembly fájlt a ISR_NOERRCODE makróval. Készíts el legalább 16 IRQ stubot a 32-től 47-ig terjedő vektorokon.
  3. Implementáld a isr_common rutint a regisztermentéssel. A interrupt_handler C függvény kezdetben csak naplózza a megszakítás számát.
  4. A kernel_main-ben hívd meg a timer_init(100)-et, töltsd be az IDT-t, és engedélyezd a megszakításokat (sti).
  5. A irq_handler-ben a timer_ticks értékét írasd ki a VGA pufferba (a C és assembly alapok, fordítás és linkelés alfejezetben már megismert módon).

Futtatási parancs (reprodukálható környezet): Az alábbi parancs a kernel lefordításához és futtatásához egy izolált, emulált környezetben. Ne futtasd a hoszt gépen közvetlenül!

# Fordítás
gcc -ffreestanding -mno-red-zone -m64 -c kernel.c -o kernel.o
nasm -f elf64 isr.s -o isr.o
ld -T linker.ld -o kernel.elf kernel.o isr.o

# Futtatás emulált környezetben (QEMU)
qemu-system-x86_64 -kernel kernel.elf -display curses -no-reboot -no-shutdown

Elvárt eredmény: A QEMU képernyőjén a timer_ticks számláló folyamatosan növekszik, jelezve, hogy a PIT megszakításai elérik a CPU-t, a CPU az IDT-n keresztül belép a csonkba, a C handler lefut, majd az EOI után a rendszer visszatér a normál futáshoz.

Hibakeresési tippek: Ha a rendszer lefagy, először ellenőrizzük, hogy a timer_ticks változó növekedett-e. Ha egyszer nőtt, majd megállt, az EOI hiányát jelzi. Ha Triple Fault lép fel (a QEMU hirtelen újraindul), az általában az IDT mutató hibás betöltésére vagy a stub címek rossz eltolására utal. A részletes nyomkövetést a következő alfejezetben (QEMU, GDB és kernel debugging) tárgyaljuk a QEMU monitor és a GDB integrációjával.
