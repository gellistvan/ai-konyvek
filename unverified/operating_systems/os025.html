7.4 IPC: pipe, üzenetsor, osztott memoria és szignál

A folyamatok izolációja az operációs rendszer egyik alapvető védelmi és stabilitási garanciája: az egyik folyamat nem írhat közvetlenül a másik memóriájába, nem hívhatja meg annak függvényeit, és nem férhet hozzá annak erőforrásaihoz. A gyakorlatban azonban a folyamatoknak gyakran együtt kell működniük: egy shell egy pipeline-ban adatot ad át egy szűrőnek, egy naplózó démon üzeneteket fogad, egy kiszolgáló a munkafolyamataival oszt meg puffert. Erre szolgálnak a folyamatok közötti kommunikáció (IPC, inter-process communication) mechanizmusai.

Ebben az alfejezetben a leggyakoribb IPC-eszközöket tekintjük át: a névtelen és nevesített csöveket, az üzenetsorokat, az osztott memóriát, a szignálokat, valamint röviden a socketeket és a szinkronizációs primitívek szerepét. A cél nem csupán az egyes API-k felsorolása, hanem annak megértése, hogy mikor melyik mechanizmus illeszkedik a feladat szemantikájához és teljesítményigényéhez. A fejezet végén egy reprodukálható laborfeladat segít a választási szempontok gyakorlásában.

7.4.1 Miért van szükség IPC-re?

Az operációs rendszer a folyamatokat külön címterekbe helyezi. A virtuális memória és a memóriavédelem miatt egy P1P_1 folyamat egy adott virtuális címe nem ugyanazt a fizikai lapot jelöli, mint P2P_2 azonos virtuális címe. Ez a tulajdonság megakadályozza, hogy egy hibás vagy rosszindulatú folyamat közvetlenül módosítsa egy másik adatait, ugyanakkor kizárja a közvetlen memóriacím alapú adatcserét is.

Az IPC mechanizmusai három nagy csoportba sorolhatók:

  1. Adatátviteli csatornák: pipe, FIFO, üzenetsor, socket. A kernel közvetítésével bájtsorozatot vagy rekordokat juttatnak el az egyik folyamattól a másikhoz.
  2. Osztott memória: két vagy több folyamat ugyanazt a fizikai memórialapot képezi le a saját címterébe. Ezzel a másolási költség elkerülhető, de a hozzáférést külön szinkronizálni kell.
  3. Értesítési és szinkronizációs mechanizmusok: szignálok, szemafórok, mutexek. Ezek nem feltétlenül szállítanak nagy adatmennyiséget, hanem eseményeket jeleznek, vagy összehangolják a hozzáférést.

E mechanizmusok nem egymás versenytársai, hanem kiegészítő eszközök. Egy robusztus rendszer gyakran kombinálja őket: például osztott memórián keresztül nagy puffert oszt meg, és egy szemafórral vagy pipe-pal jelzi az új adat érkezését.

7.4.2 Névtelen cső (pipe)

A pipe a legrégebbi és legegyszerűbb IPC-forma. Egyirányú, bájtsorozat-alapú adatcsatorna, amelyet a kernel egy rögzített méretű pufferként valósít meg. A csőnek két végpontja van: egy író és egy olvasó fájlleíró. Az író oldalon a write() rendszerhívás a kernelpufferbe másolja a bájtokat, az olvasó oldalon a read() pedig onnan olvassa ki.

A pipe létrehozása a pipe rendszerhívással történik:

int pipe(int pipefd[2]);

A paraméter egy két elemű tömb, amelybe a kernel beírja a két fájlleírót: pipefd[0] az olvasó vég, pipefd[1] az író vég. A visszatérési érték siker esetén 0, hiba esetén -1, és az errno tartalmazza a hiba okát (például EMFILE, ha a folyamatnak túl sok nyitott fájlleírója van).

A pipe tipikus használata szülő-gyermek folyamatok között:

#include <unistd.h>
#include <sys/wait.h>
#include <stdio.h>
#include <string.h>

int main(void) {
    int fd[2];
    if (pipe(fd) == -1) {
        perror("pipe");
        return 1;
    }

    pid_t pid = fork();
    if (pid == -1) {
        perror("fork");
        return 1;
    }

    if (pid == 0) {
        /* Gyermek: olvasó oldal */
        close(fd[1]);                 /* az író vég felesleges */
        char buf[32];
        ssize_t n = read(fd[0], buf, sizeof(buf) - 1);
        if (n > 0) {
            buf[n] = '\0';
            printf("gyermek kapta: %s\n", buf);
        }
        close(fd[0]);
        return 0;
    } else {
        /* Szülő: író oldal */
        close(fd[0]);                 /* az olvasó vég felesleges */
        const char *msg = "hello\n";
        write(fd[1], msg, strlen(msg));
        close(fd[1]);                 /* EOF jelzése az olvasónak */
        wait(NULL);
        return 0;
    }
}

A példában a fork után a gyermek örökli a pipe fájlleíróit. Mindkét fél azonnal bezárja a számára felesleges véget, így elkerülhető a fájlleíró-szivárgás, és az olvasó oldal pontosan akkor kap EOF-ot (nulla visszatérésű read), amikor minden író vég lezárult. Ha a gyermek nem zárná be az író véget, az olvasó read hívása a végtelenségig blokkolna, mert a kernel nem tudná, hogy nem érkezik több adat.

A pipe-ra vonatkozó fontos szemantikai szabályok:

  • A write hívás PIPE_BUF méretig (Linuxon általában 4096 bájt) atomi: a többi író nem ékelődhet közbe.
  • Ha az olvasó vég minden másolata zárva van, az írás SIGPIPE szignált vált ki, és a write -1 értékkel, EPIPE hibával tér vissza.
  • A read blokkol, amíg nincs adat, vagy az író vég nyitva van. Ha minden író vég zárva van, a read 0 értékkel tér vissza.
  • A pipe nem támogatja a véletlen hozzáférést (lseek), és nincs üzenethatár: a bájtfolyam tetszőlegesen darabolható.

A shell pipeline-ok is ezt a mechanizmust használják: a ls | wc -l parancsban a shell létrehoz egy pipe-ot, majd a két folyamat szabványos be- és kimenetét a pipe végpontjaira irányítja.

7.4.3 FIFO: nevesített cső

A névtelen pipe csak közös őssel rendelkező folyamatok között használható, mert a fájlleírókat öröklés útján lehet átadni. Ha két független folyamatnak kell kommunikálnia, nevesített csőre (FIFO) van szükség.

A FIFO egy speciális fájl a fájlrendszerben, amelyet a mkfifo rendszerhívással vagy paranccsal hozunk létre:

int mkfifo(const char *pathname, mode_t mode);

A pathname a FIFO elérési útja, a mode a jogosultságokat adja meg. A hívás 0 értékkel tér vissza siker esetén, hiba esetén -1 és errno beállításra kerül. A létrehozott FIFO nem tárol adatot a lemezen; csupán egy kernelbeli csatorna nevesített belépési pontja.

A használat során a folyamatok a szokásos open hívással nyitják meg a FIFO-t:

  • O_RDONLY nyitás blokkol, amíg egy író is meg nem nyitja.
  • O_WRONLY nyitás blokkol, amíg egy olvasó is meg nem nyitja.
  • Ha O_NONBLOCK flaget adunk meg, a nyitás és a későbbi read/write hívások nem blokkolnak; a pontos viselkedés ettől függ.

A FIFO előnye, hogy bármely folyamat, amelyik ismeri az elérési utat és jogosult a hozzáférésre, csatlakozhat a csatornához. Hátránya, hogy a fájlrendszerben maradó név miatt az életciklus-kezelésre külön figyelmet kell fordítani, és a jogosultságok ellenőrzése a fájlrendszer szabályai szerint történik.

7.4.4 Üzenetsorok

Az üzenetsorok rekordalapú kommunikációt biztosítanak. Ellentétben a pipe-pal, ahol a bájtfolyam tetszőlegesen darabolható, az üzenetsor megőrzi az üzenethatárokat: az olvasó pontosan egy üzenetet kap, amit az író egy hívásban küldött. Ez a tulajdonság akkor hasznos, ha a kommunikáció természetes egységei strukturált rekordok, például naplóbejegyzések vagy vezérlőparancsok.

Két fő üzenetsor-implementáció létezik: a POSIX üzenetsor és a System V üzenetsor. Mindkettő a kernelben tárolja az üzeneteket, de az interfészük és a névterük eltér.

7.4.5 POSIX üzenetsor

A POSIX üzenetsort az mq_open hívással hozzuk létre vagy nyitjuk meg:

mqd_t mq_open(const char *name, int oflag, mode_t mode,
              struct mq_attr *attr);

A name egy / karakterrel kezdődő, fájlrendszer-szerű név, például /app_logq. Az oflag lehet O_CREAT, O_EXCL, O_RDONLY, O_WRONLY, O_RDWR és O_NONBLOCK. A mode a létrehozáskor érvényes jogosultságokat adja meg. Az attr opcionális, ebben adható meg a maximális üzenetszám (mq_maxmsg) és az egy üzenet maximális mérete (mq_msgsize). A visszatérési érték egy üzenetsor-leíró (mqd_t), amely sikertelen hívás esetén (mqd_t)-1 és errno beállítás.

Az üzenetküldés és -fogadás:

int mq_send(mqd_t mqdes, const char *msg_ptr, size_t msg_len,
            unsigned int msg_prio);
ssize_t mq_receive(mqd_t mqdes, char *msg_ptr, size_t msg_len,
                   unsigned int *msg_prio);

A mq_send a msg_ptr által mutatott msg_len méretű puffert egyetlen üzenetként helyezi el a sorban. A msg_prio prioritás szerint rendezi az üzeneteket: a nagyobb értékű üzenet hamarabb kerül kiolvasásra. A mq_receive kiveszi a legmagasabb prioritású üzenetet. Ha a puffer mérete kisebb, mint az üzenet, a hívás EMSGSIZE hibával tér vissza. Ha a sor üres és a leíró nem nemblokkoló, a mq_receive blokkol.

A lezárás és a név eltávolítása:

int mq_close(mqd_t mqdes);
int mq_unlink(const char *name);

Az mq_close bezárja a leírót, de a sor a kernelben megmarad, amíg mq_unlink-kel nem távolítjuk el. Az mq_unlink után az újabb mq_open hívások nem találják a sort, de a már megnyitott leírók tovább használhatják.

Példa egy egyszerű üzenetküldésre:

#include <mqueue.h>
#include <stdio.h>
#include <string.h>

int main(void) {
    struct mq_attr attr = {0};
    attr.mq_maxmsg = 10;
    attr.mq_msgsize = 64;

    mqd_t mq = mq_open("/pelda_q", O_CREAT | O_RDWR, 0600, &attr);
    if (mq == (mqd_t)-1) {
        perror("mq_open");
        return 1;
    }

    const char *uzenet = "log: rendben";
    if (mq_send(mq, uzenet, strlen(uzenet) + 1, 0) == -1) {
        perror("mq_send");
        return 1;
    }

    char puffer[64];
    unsigned int prio = 0;
    ssize_t n = mq_receive(mq, puffer, sizeof(puffer), &prio);
    if (n >= 0) {
        printf("fogadva: %s\n", puffer);
    }

    mq_close(mq);
    mq_unlink("/pelda_q");
    return 0;
}

A példában a strlen + 1 azért szerepel, hogy a lezáró nullkarakter is az üzenet része legyen; ez lehetővé teszi a közvetlen printf használatát. Nagyobb rendszerekben gyakran bináris rekordokat küldenek, ilyenkor nincs szükség nullterminátorra.

7.4.6 System V üzenetsor

A System V üzenetsorok a POSIX-tól eltérő, régebbi interfészt használnak. A sort egy kulcs azonosítja:

int msgget(key_t key, int msgflg);

A key gyakran ftok() segítségével generálható, vagy konstans. A msgflg tartalmazza a jogosultságokat és az IPC_CREAT flaget. A visszatérési érték egy sorazonosító. Az üzenetküldés:

int msgsnd(int msqid, const void *msgp, size_t msgsz, int msgflg);
ssize_t msgrcv(int msqid, void *msgp, size_t msgsz, long msgtyp, int msgflg);

A msgp egy olyan struktúrára mutat, amelynek első mezője long mtype típusazonosító. Az msgsnd a msgsz hosszúságú adatrészt küldi el, a msgrcv pedig a msgtyp alapján választ üzenetet. Az msgctl hívással lehet törölni a sort vagy lekérdezni az állapotát.

Bár a System V üzenetsorok még megtalálhatók a Linux rendszerekben, új fejlesztésekben általában a POSIX interfészt vagy a socketeket érdemes előnyben részesíteni.

7.4.7 Osztott memória

Az osztott memória az egyetlen olyan IPC-mechanizmus, amely nem másolja az adatokat a kernel és a felhasználói tér között. A folyamatok ugyanazt a fizikai memóriaterületet képezik le a saját virtuális címterükbe, így az egyik folyamat által írt érték azonnal láthatóvá válik a másik számára. Ez nagy adatmennyiség vagy alacsony késleltetés esetén a leghatékonyabb választás.

A POSIX osztott memória létrehozása:

int shm_open(const char *name, int oflag, mode_t mode);

A name itt is / karakterrel kezdődő név. A hívás egy fájlleírót ad vissza, amelyet ezután ftruncate-tel a kívánt méretűre kell állítani, majd mmap-pel a címterünkbe kell képezni:

int ftruncate(int fd, off_t length);
void *mmap(void *addr, size_t length, int prot, int flags,
           int fd, off_t offset);

A mmap PROT_READ | PROT_WRITE védelemmel és MAP_SHARED flaggel a megosztott lapokat hozza létre. A shm_unlink a név eltávolítására szolgál.

Példa osztott memória létrehozására és írására:

#include <sys/mman.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <unistd.h>
#include <string.h>
#include <stdio.h>

int main(void) {
    int fd = shm_open("/pelda_shm", O_CREAT | O_RDWR, 0600);
    if (fd == -1) {
        perror("shm_open");
        return 1;
    }

    if (ftruncate(fd, 4096) == -1) {
        perror("ftruncate");
        return 1;
    }

    char *ptr = mmap(NULL, 4096, PROT_READ | PROT_WRITE,
                     MAP_SHARED, fd, 0);
    if (ptr == MAP_FAILED) {
        perror("mmap");
        return 1;
    }

    strcpy(ptr, "osztott memória üzenet");
    printf("írva: %s\n", ptr);

    munmap(ptr, 4096);
    close(fd);
    shm_unlink("/pelda_shm");
    return 0;
}

Az osztott memória legnagyobb kockázata a versenyhelyzet. Ha két folyamat egyszerre írja ugyanazt a területet, az eredmény nem definiált. Ezért az osztott memóriát mindig valamilyen szinkronizációs mechanizmussal kell összekapcsolni: például POSIX szemafórral vagy egy közös mutexszel. A szinkronizáció nélküli osztott memória használata az egyik leggyakoribb és legnehezebben felderíthető hibák forrása.

A System V osztott memória interfész a shmget, shmat, shmdt és shmctl hívásokból áll. A POSIX shm_open + mmap megközelítés általában rugalmasabb, mert a fájlleíró-alapú modellbe illeszkedik, és lehetővé teszi a jogosultságok és az életciklus egyszerűbb kezelését.

7.4.8 Szignálok

A szignálok aszinkron értesítési mechanizmust adnak a folyamatok számára. Egy szignál nem szállít nagy adatmennyiséget, csupán egy esemény bekövetkeztét jelzi: például a felhasználó megnyomta a Ctrl+C billentyűkombinációt (SIGINT), egy gyermekfolyamat befejeződött (SIGCHLD), vagy egy időzítő lejárt (SIGALRM). A szignálokat a kernel küldi a folyamatnak, de egy folyamat a kill vagy raise rendszerhívással más folyamatnak is küldhet.

A szignálkezelés alapvető interfészei:

void (*signal(int signum, void (*handler)(int)))(int);
int kill(pid_t pid, int sig);
int raise(int sig);

A signal a signum jelhez rendel egy handler függvényt. A kill a pid azonosítójú folyamatnak küld sig jelet; a raise a saját folyamatnak küld. A signal hordoz néhány platformfüggő viselkedést, ezért új kódban a sigaction használata javasolt:

int sigaction(int signum, const struct sigaction *act,
              struct sigaction *oldact);

A struct sigaction tartalmazza a handler függvényt (sa_handler vagy sa_sigaction), a kezelés közben blokkolandó szignálok halmazát (sa_mask) és a viselkedést módosító flageket (sa_flags). A sigaction lehetővé teszi a pontos szemantika beállítását, például a SA_RESTART flaget, amely a megszakított rendszerhívások automatikus újraindítását kéri.

A szignálkezelő függvényre szigorú szabályok vonatkoznak. Mivel a handler aszinkron módon, a folyamat bármely pontján lefuthat, csak async-signal-safe függvényeket hívhat. A POSIX szabvány felsorolja ezeket; ilyen például a write, a _exit és a sem_post. A printf, a malloc vagy a pthread_mutex_lock nem biztonságos, mert nem reentránsak vagy belső állapotuk miatt holtpontot okozhatnak.

A gyakorlatban a legegyszerűbb és legbiztonságosabb minta az, hogy a handler csupán egy volatile sig_atomic_t flaget állít be, a fő program pedig a flaget figyeli:

#include <signal.h>
#include <unistd.h>
#include <stdio.h>

volatile sig_atomic_t erkezett = 0;

void handler(int sig) {
    (void)sig;
    erkezett = 1;
}

int main(void) {
    struct sigaction sa = {0};
    sa.sa_handler = handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;
    sigaction(SIGUSR1, &sa, NULL);

    printf("várok a SIGUSR1 jelre...\n");
    while (!erkezett) {
        pause();   /* szünetel a jel érkezéséig */
    }
    printf("jel megérkezett\n");
    return 0;
}

A példában a pause blokkol, amíg bármilyen szignál nem érkezik; a handler lefut, beállítja a flaget, majd a pause visszatér, és a ciklus kilép. A volatile sig_atomic_t típus garantálja, hogy a flag olvasása és írása atomi művelet a szignálkezelés szempontjából.

A szignálok fontos tulajdonsága, hogy nem sorolódnak. Ha ugyanabból a szignálból több érkezik, mielőtt a folyamat kezelné, a kernel csak egyet kézbesít belőle. Ezért a szignál nem alkalmas események pontos számlálására vagy nagy gyakoriságú értesítésekre. A SIGKILL és SIGSTOP jeleket nem lehet elkapni, blokkolni vagy figyelmen kívül hagyni; ezek mindig érvényesülnek.

7.4.9 Socketek és szinkronizáció

A socketek az IPC általánosabb eszközei. A socketpair hívással létrehozható egy teljes duplex, bájtsorozat-alapú csatorna, amely hasonló a pipe-hoz, de mindkét irányban használható:

int socketpair(int domain, int type, int protocol, int sv[2]);

A domain általában AF_UNIX, a type pedig SOCK_STREAM (bájtsorozat) vagy SOCK_DGRAM (datagram). A socketpair két összekötött socket-leírót ad vissza. A pipe-pal ellentétben itt nincs külön író és olvasó vég: mindkét fél írhat és olvashat is.

A hálózati socketek (AF_INET, AF_INET6) lehetővé teszik az IPC-t akár különböző gépek között is, de ezzel a témával a hálózati stacket tárgyaló fejezet foglalkozik részletesen. Az AF_UNIX socketek a helyi gépen belüli kommunikációra szolgálnak, és a fájlrendszerben megjelenő elérési úttal is rendelkezhetnek.

A szinkronizációs primitívek – szemafórok, mutexek, feltételváltozók – önmagukban nem IPC-adatcsatornák, de elengedhetetlenek az osztott memória és más közös erőforrások védelméhez. A POSIX szemafór például a sem_open, sem_wait, sem_post és sem_close függvényekkel kezelhető. A szemafór egy számláló, amelyet a sem_wait eggyel csökkent (ha az érték nulla, blokkol), a sem_post pedig eggyel növel, és felébreszt egy várakozó folyamatot.

A termelő-fogyasztó minta tipikus példája az osztott memória és a szemafór kombinációjának. A termelő az osztott pufferbe ír, majd sem_post-tal jelzi, hogy új elem áll rendelkezésre. A fogyasztó sem_wait-tel várakozik, majd kiolvassa a puffert. A szemafór biztosítja, hogy a fogyasztó csak akkor olvasson, ha a termelő már befejezte az írást.

7.4.10 Mechanizmusválasztás

A megfelelő IPC-mechanizmus kiválasztása a következő szempontok mérlegelését igényli:

  • Adatmennyiség és gyakoriság: Nagy adatforgalom esetén az osztott memória kerüli a felesleges másolást, de szinkronizációt igényel. Kis üzenetekre a pipe vagy üzenetsor egyszerűbb és biztonságosabb.
  • Adatszerkezet: Ha az üzenethatárok fontosak, az üzenetsor természetes választás. Ha bájtsorozatot kell átvinni, a pipe vagy socket illik.
  • Folyamatok kapcsolata: Névtelen pipe csak közös őssel rendelkező folyamatok között használható. Független folyamatok esetén FIFO, üzenetsor, osztott memória névvel vagy socket szükséges.
  • Élettartam: Az üzenetsor és az osztott memória objektumai a kernelben tovább élnek a létrehozó folyamat befejeződése után is, amíg explicit módon el nem távolítják őket. A pipe és a socket automatikusan felszabadul az utolsó fájlleíró lezárásakor.
  • Szinkronizációs igény: Az osztott memória önmagában nem szinkronizál. Ha az adatcsere mellett eseményjelzésre is szükség van, kombinálni kell szignállal, szemafórral vagy pipe-pal.
  • Hordozhatóság: A POSIX interfészek (pipe, mkfifo, shm_open, mq_open, socketpair) széles körben támogatottak. A System V interfészek régebbiek, de még mindig elérhetők.

A gyakorlatban egy egyszerű pipeline-hoz pipe-ot, egy naplózó démonhoz üzenetsort vagy socketet, nagy puffer megosztásához pedig osztott memóriát szemafórral érdemes választani.

7.4.11 Tipikus hibák és megelőzésük

Az IPC-programozás során több visszatérő hiba jellemző:

  1. Fájlleíró-szivárgás pipe esetén. Ha a gyermek nem zárja be a felesleges író véget, az olvasó read soha nem kap EOF-ot, és a program végtelenségig blokkol. Mindig zárjuk be a nem használt végeket, lehetőleg közvetlenül a fork után.

  2. Részleges írás és olvasás. A write és read nem garantálja, hogy a teljes puffer átvitelre kerül. A visszatérési értéket mindig ellenőrizni kell, és ciklusban kell folytatni a műveletet.

  3. Szignálkezelőben nem biztonságos függvény hívása. A printf, malloc vagy bármely nem async-signal-safe függvény használata a handlerben holtponthoz vagy memóriahibához vezethet. Csak a szabvány által megengedett függvényeket használjuk, vagy csak flaget állítsunk.

  4. Osztott memória szinkronizáció nélkül. Az adatverseny nem definiált viselkedést okoz. Mindig használjunk szemafórt, mutexet vagy más mechanizmust a hozzáférés összehangolására.

  5. Üzenetsor-erőforrások eltávolításának elmulasztása. A POSIX üzenetsor és az osztott memória objektum a kernelben marad, ha elfelejtjük az mq_unlink vagy shm_unlink hívást. Ez fájlleíró- és memóriaszivárgáshoz hasonló problémákat okozhat.

  6. Blokkoló hívások holtpontja. Ha például egy FIFO-t nyitunk olvasásra, és senki sem nyitja írásra, a program blokkol. A O_NONBLOCK flag vagy timeoutok használatával elkerülhető a végtelen várakozás.

7.4.12 Labor: IPC-mechanizmus kiválasztása

A labor célja, hogy egy adott forgatókönyvhöz válasszunk IPC-mechanizmust, és azt emulált környezetben, méréssel ellenőrizzük.

Forgatókönyv: Egy naplózó rendszerben egy termelő folyamat másodpercenként 1000 darab, egyenként 512 bájtos naplórekordot állít elő. Egy fogyasztó folyamat ezeket a rekordokat fogadja, és egy fájlba írja. A termelő és a fogyasztó ugyanazon a gépen fut, de független folyamatként, nem szülő-gyermek kapcsolatban. A rendszerrel szemben az a követelmény, hogy a rekordhatárok megmaradjanak, és a késleltetés a termelő és a fogyasztó között legfeljebb 1 ms legyen. Az adatvesztés nem megengedett.

Feladat: Válasszon a pipe, FIFO, POSIX üzenetsor és osztott memória közül, indokolja a választást, és mérje a késleltetést emulált környezetben.

Kiinduló állapot: QEMU virtuális gép, 1 vCPU, 512 MiB RAM, Linux kernel 6.1, glibc 2.36, gcc 12.2. A méréshez a clock_gettime(CLOCK_MONOTONIC) hívást használjuk, és a termelő minden rekordhoz rögzíti a küldés időbélyegét, a fogyasztó pedig a fogadásét. A késleltetést a két időbélyeg különbsége adja.

Build- és futtatási parancs: A programot C nyelven írjuk, gcc -O2 -Wall -Wextra fordítási beállításokkal. A futtatás a QEMU vendégben történik: ./ipc_lab.

Elvárt eredmény: A mért átlagos késleltetés legfeljebb 1 ms, és a rekordok 100%-a megérkezik. A mérési naplóban rögzíteni kell a hardvert, a fordítási beállításokat, az órajelet és a mérési módszert.

A mért és a várt eredmény elkülönítése: A labor jegyzőkönyvben külön oszlopban szerepeljen a számított/elvárt késleltetési korlát (1 ms) és a ténylegesen mért átlag, minimum, maximum, valamint a szórás. A mért értékeket ne kerekítsük a várt értékre; az eltérés elemzése a feladat része.

Visszaállítás: A QEMU vendég leállítása után a snapshot visszaállítása biztosítja a tiszta kiinduló állapotot. A labor nem módosítja a hoszt rendszer lemezét vagy bootloaderét.

Megjegyzés a megoldáshoz: A forgatókönyvben a rekordhatárok megőrzése miatt a pipe és a FIFO kevésbé alkalmas, mert a bájtsorozatot magunknak kellene darabolni. Az osztott memória nagy sebességet kínál, de szinkronizációt igényel. A POSIX üzenetsor pontosan rekordalapú, és a kernel kezeli a határokat. A labor során érdemes megmérni az üzenetsor és egy explicit keretezést használó pipe vagy FIFO késleltetését is, hogy a választás mérési adatokkal legyen alátámasztva.

7.4.13 Önellenőrző kérdések

  1. Miért kap EOF-ot az olvasó egy pipe-on, ha az író bezárja a végét, és mi a szerepe a felesleges fájlleírók lezárásának a fork után?
  2. Mi a különbség a pipe és a FIFO között a folyamatok kapcsolata és a létrehozás módja szempontjából?
  3. Miért van szükség szinkronizációra osztott memória használatakor, és milyen primitívekkel oldható meg?
  4. Miért nem hívhatunk printf függvényt egy szignálkezelőben?
  5. Milyen szempontok alapján választana üzenetsort a pipe helyett?

A kérdésekre adott válaszok a fejezet anyagából levezethetők, és a labor során szerzett tapasztalatokkal mélyíthetők.

7.4.14 Összegzés

Ez az alfejezet bemutatta a folyamatok közötti kommunikáció fő mechanizmusait: a pipe-ot, a FIFO-t, az üzenetsorokat, az osztott memóriát, a szignálokat és a socketeket. Mindegyik más-más szemantikát és teljesítményprofil kínál, ezért a választás a konkrét feladat követelményeitől függ. A következő egység az ütemezési célokkal és algoritmusokkal foglalkozik, ahol az itt megismert folyamat- és szálfogalmakra építünk. Az IPC mechanizmusainak helyes használata a későbbi hálózati és biztonsági fejezetekben is alapvető fontosságú.
