31.1 SMP, preemption és valós idejű kiterjesztés

A Regresszió és kiadási minőség alfejezetben stabilizált egyprocesszoros kernel után a következő lépés a párhuzamos végrehajtás. Ez a szakasz a szimmetrikus többmagos (SMP) bővítést és a preemptív kernel viselkedését járja körül. A cél nem egy gyártásra kész SMP kernel, hanem azoknak a mechanizmusoknak a megértése, amelyek a többmagos helyes működéshez kellenek: spinlock, per-CPU adat és preempt_count. Ehhez kapcsolódik a PREEMPT_RT koncepció és a latency mérése is.

31.1.1 Miért más a többmagos kernel?

Az eddigi egyszerű kernelben egyetlen CPU futtatta a kernel kódját, így a közös globális adatok védelméhez elegendő volt a megszakítások rövid idejű tiltása, vagy egy egyszerű kölcsönös kizárás. Amikor két vagy több CPU ugyanazt a kernel kódot futtatja, akkor valódi párhuzamos végrehajtás jön létre: két processzor egyszerre írhatja ugyanazt a globális változót. A megszakítás tiltása egyetlen CPU-n nem akadályozza meg a másik CPU futását. Ezért a közös kernel állapotot explicit, CPU-k közötti szinkronizációval kell védeni.

Az SMP rendszerek legfontosabb tulajdonságai:

  • szimmetrikus: minden CPU azonos jogokkal és azonos memóriatérrel rendelkezik, ugyanazt a kernel képet futtatja;
  • cache-koherencia: a hardver biztosítja, hogy a CPU cache-ekben lévő másolatok konzisztensek legyenek, de ez nem zárja ki az alkalmazás szintű versenyhelyzetet;
  • atomi utasítások: a CPU-k rendelkeznek olyan utasításokkal, amelyek olvasnak és írnak egy memóriahelyet úgy, hogy közben másik CPU nem férhet hozzá (test-and-set, compare-exchange, load-linked/store-conditional).

A kernel kódjában ezért különbséget kell tennünk a CPU-lokális és a globális állapot között. A CPU-lokális állapotot nem kell lezárni, mert csak az adott CPU éri el; a globális állapotot viszont minden CPU hozzáférhet, ezért zárolni kell.

31.1.2 Spinlock: a legalapvetőbb CPU-k közötti zár

A spinlock olyan kölcsönös kizárási eszköz, amely akkor használható, amikor a kritikus szakasz nagyon rövid, és a várakozó CPU-nak nem érdemes aludnia. A spinlockot használó CPU aktívan pörög (spin-el), amíg a zárat meg nem kapja.

31.1.3 Működési elve

A spinlock egyetlen atomi memóriahelyre épül. A zárolás során a CPU atomikusan megkísérli a 0 értéket 1-re cserélni. Ha az eredmény 0, a zár az övé; ha 1, akkor a zár foglalt, és a CPU addig pörög, amíg a zár fel nem szabadul.

A következő példa egy egyszerű spinlockot mutat GCC beépített atomi függvényekkel. A kód szemléltetés, nem éles kernelhez való:

/* Egyszerű spinlock, csak oktatási célra.
 * A valós kernelben a lockolás előtt preempt_disable() is szükséges.
 */
typedef struct {
    volatile unsigned int locked;
} spinlock_t;

static inline void spin_lock(spinlock_t *l)
{
    /* Atomi test-and-set: if (locked == 0) { locked = 1; return 0; }
     * else return 1. A pörgés közben használjunk relaxált olvasást,
     * hogy a CPU ne terhelje feleslegesen a cache-összeköttetést.
     */
    while (__sync_lock_test_and_set(&l->locked, 1)) {
        while (__sync_fetch_and_or(&l->locked, 0))
            asm volatile("pause");
    }
}

static inline void spin_unlock(spinlock_t *l)
{
    /* Release szemantika: a kritikus szakasz minden írása látható,
     * mielőtt a zár felszabadul. */
    __sync_lock_release(&l->locked);
}

A példában a __sync_lock_test_and_set atomi test-and-set műveletet végez. A pause utasítás x86-on csökkenti a pörgés okozta energiafogyasztást és javítja a többi szál haladását. A __sync_lock_release release szemantikát ad, vagyis a kritikus szakaszban végzett írások nem rendeződhetnek a zár felszabadítása után.

Fontos, hogy a spinlock használata előtt le kell tiltani a kernel preemptiót is. Ha ugyanis a CPU a kritikus szakasz közepén preemptálódik, akkor a zár hosszú ideig foglalt maradhat, és a többi CPU feleslegesen pörög. A helyes minta tehát:

void spin_lock_correct(spinlock_t *l)
{
    preempt_disable();
    spin_lock(l);
}

void spin_unlock_correct(spinlock_t *l)
{
    spin_unlock(l);
    preempt_enable();
}

31.1.4 Tipikus hibák

  • Rekurzív spinlock: ha ugyanaz a CPU megpróbálja kétszer felvenni ugyanazt a spinlockot, a második hívás végtelen pörgésbe kerül, mert a zár már az adott CPU-é. A spinlock nem rekurzív.
  • Interrupt kontextusban való zárolás: ha a kernel megszakításkezelője olyan spinlockot próbál felvenni, amelyet ugyanaz a CPU már normál kontextusban tart, holtpont alakulhat ki, mert a megszakításkezelő nem tudja felszabadítani a zárat. Ezért interruptok alatt általában interrupt-tiltó spinlockot használunk.
  • Hosszú kritikus szakasz: a spinlock csak nagyon rövid műveletekhez való. Ha a kritikus szakasz memóriát másol vagy fájlrendszert jár be, a többi CPU pörgése jelentős késleltetést okoz.
  • Nincs preempt_disable: a preemptiós kernelben a zár felvétele előtti és utáni preempt állapot megváltoztathatja a CPU futását, ezért a lockolásnak mindig preempt tiltással kell együtt járnia.

31.1.5 Per-CPU adat: a cache-versengés csökkentése

A többmagos kernelben a globális számlálók és egyéb gyakran írt adatok komoly cache-invalidálást okozhatnak. Ha például minden CPU ugyanazt a globális packet_count változót növeli, akkor minden növelés során a cache-vonalat át kell mozgatni a CPU-k között. Ezt hívjuk cache-line ping-pong-nak.

A megoldás az, hogy az adatot CPU-nként külön példányban tároljuk, és csak akkor férünk hozzá, amikor tényleg szükséges. Ezt nevezzük per-CPU adatnak. A per-CPU adat nem igényel spinlockot, mert minden CPU csak a saját példányát módosítja. A gyűjtő művelet (például összegzés) azonban minden CPU példányát olvassa, de ez ritkábban történik, mint a növelés.

A következő egyszerű példa egy per-CPU számlálót mutat. A valós kernelben ez makrókkal történik, de a lényeg ugyanaz:

#define MAX_CPUS 8

struct per_cpu_counter {
    unsigned long count;
    unsigned char padding[64 - sizeof(unsigned long)];
        /* cache-vonal igazítás: elkerüljük a hamis osztást */
};

static struct per_cpu_counter counters[MAX_CPUS];

int current_cpu(void)
{
    /* Itt a CPU azonosítót az APIC vagy a per-CPU kernel stack
     * adja vissza. Például:
     *   return read_cpu_id();
     * A valós kernelben a preempt_disable védi a használatot.
     */
    return 0; /* egyszerűsített pszeudokód */
}

void increment_this_cpu_counter(void)
{
    int cpu = current_cpu();
    counters[cpu].count++;
}

unsigned long read_total_counter(void)
{
    unsigned long sum = 0;
    int cpu;
    for (cpu = 0; cpu < MAX_CPUS; cpu++) {
        sum += counters[cpu].count;
    }
    return sum;
}

A helyes hozzáférés érdekében a kernelben két feladatot kell elvégezni:

  1. A CPU azonosító lekérése előtt tiltjuk a preemptiót.
  2. A hozzáférés után visszaállítjuk a preempt állapotot.

Ez a get_cpu() / put_cpu() minta:

int cpu = get_cpu();
counters[cpu].count++;
put_cpu();

A get_cpu() visszaadja az aktuális CPU azonosítót, és megnöveli a preempt_count-ot, így a kernel nem válthat CPU-t a hozzáférés közben. A put_cpu() csökkenti a számlálót, és ha szükséges, ütemezést indít.

Tipikus hibák:

  • CPU váltás per-CPU mutatóval: ha valaki elmenti a per-CPU adat címét, majd a CPU-t átváltja a kernel, a mutató elavulttá válik, és másik CPU adatát írjuk.
  • Hamis cache-osztás: ha két per-CPU változó ugyanabba a cache-vonalba kerül, akkor a CPU-k egymás cache-vonalát invalidálják, hiába külön adatról van szó. Ezért a per-CPU struktúrákat cache-vonal méretre igazítjuk.
  • Túl sok per-CPU memória: a per-CPU adat a CPU-k számával szorozva foglal memóriát. A tervezésnél mérlegelni kell, hogy a gyors hozzáférés megéri-e a nagyobb lábnyomot.

31.1.6 A preempt count és a kernel preemptió

A preemptió azt jelenti, hogy a kernel futás közben átadhatja a CPU-t egy másik készen álló feladatnak, például egy magasabb prioritású folyamatnak. Ez javítja a válaszidőt, de veszélyezteti a kernel adatstruktúráinak konzisztenciáját. Ezért a kernelben bizonyos szakaszokban tilos a preemptió.

A preempt_count egy per-task számláló, amely megmutatja, hogy hány olyan réteg tiltja éppen a preemptiót. Ha a számláló értéke nagyobb, mint nulla, a kernel nem válthat kontextust. A számlálót a preempt_disable() növeli, a preempt_enable() pedig csökkenti. Amikor a számláló nullára csökken, a kernel megvizsgálja, hogy van-e függőben lévő ütemezési igény, és ha igen, ütemez.

A következő példa egy egyszerű preempt_count kezelést mutat. A valós Linux kernelben a preempt_count egy bitmező, amely a hardirq, softirq, preempt és NMI szinteket külön tárolja, de az alapelv ugyanez:

struct thread_context {
    int preempt_count;
    /* ... további mezők ... */
};

static inline void preempt_disable(void)
{
    current->preempt_count++;
    /* Compiler barrier: az írás nem rendeződhet át a
     * kritikus szakasz elé. */
    asm volatile("" ::: "memory");
}

static inline void preempt_enable(void)
{
    asm volatile("" ::: "memory");
    current->preempt_count--;
    if (current->preempt_count == 0 && need_resched())
        schedule();
}

A preempt_disable() és preempt_enable() hívások párban kell, hogy megjelenjenek. Minden tiltáshoz tartoznia kell egy engedélyezésnek. Ha a számláló nem nullára csökken, akkor még mindig marad tiltás, ezért nem szabad ütemezni.

A preempt_count használatával a kernel kódja kijelölheti a nem preemptálható szakaszokat anélkül, hogy a megszakításokat teljesen letiltaná. Ez fontos az SMP kernelben, mert a megszakítások tiltása csak az adott CPU-ra hat, míg a preempt_count a kernel folyamatán belüli konzisztenciát védi.

Tipikus hibák:

  • Preempt count szivárgás: ha a preempt_disable() után a függvény hibával visszatér, és nem hívja meg a preempt_enable()-t, a számláló nem nullázódik, ami a kernel preemptiójának blokkolásához vezet. A kernelben ilyenkor BUG() vagy WARN() jelzi a hibát.
  • Túlzott preempt tiltás: hosszú kritikus szakaszok alatt a preemptió tiltása késlelteti a magas prioritású feladatokat, és rontja a rendszer válaszidejét.
  • Preempt tiltás és alvás: ha a kernel kódja a preempt tiltott szakaszban alvó függvényt hív, az hibát okoz, mert a processzor nem adhatja át a vezérlést.

31.1.7 PREEMPT_RT és a latency fogalma

A hagyományos Linux kernelben a CONFIG_PREEMPT opció teszi lehetővé a kernel preemptióját, de bizonyos szakaszokban továbbra is tiltva van, és a spinlockok is tiltják a preemptiót. A PREEMPT_RT (real-time) patch célja, hogy a kernel minél több pontján preemptálható legyen, és a megszakításokat is kernel szálakban futtassa. Így a magas prioritású felhasználói feladatok rövidebb és determinisztikusabb késleltetéssel kapják meg a CPU-t.

A PREEMPT_RT legfontosabb átalakításai:

  • A spinlockok nagy részét preemptálható mutexekre cseréli. Ez azt jelenti, hogy a várakozó feladat elalszik, és a CPU-t más feladat kaphatja meg.
  • A hardveres megszakításkezelők egy részét kernel szálakba helyezi. A megszakításkezelő így alacsonyabb prioritással futhat, mint a valós idejű feladatok, így azok nem várnak a megszakításkezelőre.
  • Bevezeti a priority inheritance (prioritás öröklés) mechanizmust, hogy elkerülje a prioritás inverziót.

A latency két fontos összetevője:

  • Megszakítási késleltetés (LirqL_{irq}): a hardveres megszakítás érkezésétől a megszakításkezelő első utasításáig eltelt idő.
  • Ütemezési késleltetés (LschedL_{sched}): attól az időponttól, amikor egy feladat számára ébredési esemény történik (például egy megszakítás befejeződik), addig, amíg a feladat ténylegesen futni kezd.

A PREEMPT_RT célja ezeknek a késleltetéseknek a csökkentése és a maximális érték (worst-case) determinisztikussá tétele. A mérést általában cyclictest típusú programmal végzik, amely időzítő megszakításokkal ébreszti magát, és méri az ébredés és a futás közötti különbséget. A mérés során rögzíteni kell a hardvert, a kernel konfigurációt, az órajelfrekvenciát és a mérési módszert, ahogy a könyv általános mérési szabályai előírják.

A PREEMPT_RT állapotáról fontos megjegyezni: a mainline Linux különböző verziói eltérő mértékben tartalmazzák a real-time patcheket. 2025 elején a PREEMPT_RT jelentős része már be van olvasztva a mainline kernelbe, de az adott kernelverzió pontos támogatását a reprodukciós csomagban rögzíteni kell. Ez az állítás verzióellenőrzést igényel a konkrét kiadásnál.

31.1.9 Kiinduló állapot és környezet

  • Alap kernel: a Regresszió és kiadási minőség alfejezetben tesztelt, egyprocesszoros, naplózást és panic kezelést tartalmazó build. Commit azonosítóval rögzítve a reprodukciós csomagban.
  • Emulált hardver: QEMU x86_64, két virtuális CPU (-smp 2), 512 MiB RAM, hálózat nélkül, soros konzollal.
  • Build eszközök: a korábbi fejezetekben használt cross-toolchain, linker script és buildrendszer.
  • Fordítási beállítások: -O2 -g, -mno-red-zone, -ffreestanding, -fno-stack-protector (a pontos opciókat a buildnapló tartalmazza).

31.1.10 A terv elvárt tartalma

A dokumentumnak a következő szakaszokat kell tartalmaznia:

  1. Célkitűzések:
    • Két vCPU indítása és a kernel adatstruktúrák SMP-biztossá tétele.
    • Preemptív kernel bekapcsolása CONFIG_PREEMPT mintára.
    • Mérési terv a megszakítási késleltetés és a jitter meghatározására.
  2. Adatstruktúra-terv:
    • A globális kernel állapotok felmérése: melyek lesznek spinlockkal védve, melyek per-CPU adatok.
    • A spinlock_t mérete és igazítása: például 4 bájt, cache-vonalra igazítva.
    • A per-CPU adat blokk mérete és CPU-nkénti elrendezése: a per-CPU struktúra mérete 64 bájt cache-vonaligazítással.
    • A preempt_count mező elhelyezkedése a thread_context struktúrában, mérete és bitbeosztása (ha a valós bitmezőt használjuk).
  3. Szinkronizációs terv:
    • Melyik spinlock védi a folyamatkezelő globális listát, az ütemező futósorát és a napló puffert.
    • Hogyan oldják meg a spinlockok a preempt tiltást: spin_lock() belép előtt preempt_disable(), kilép után preempt_enable().
    • Per-CPU adatok elérése get_cpu() / put_cpu() mintával.
  4. Boot folyamat:
    • A másodlagos CPU-k indítása: az APIC vagy a QEMU által biztosított módszerrel. A tervben pszeudokóddal le kell írni, hogyan ébrednek a másodlagos CPU-k, és hol várnak az ütemezőre.
  5. Mérési terv:
    • Mért késleltetés: a kernel időzítő megszakításának kezelője feljegyzi az időbélyeget, amikor a megszakítás beérkezett. A cyclictest-hez hasonló kernel folyamat vagy egy egyszerű felhasználói program méri, mennyi idő telik el az ébresztés és a futás között.
    • Várt késleltetés: levezetett érték a kernel kód elemzése alapján. Például a megszakítás belépési út hossza TentryT_{entry} ciklusban, a handler ThandlerT_{handler} ciklusban. QEMU alatt a vCPU-ütemezés overheadje hozzáadódik; ezt a várt értéknél külön fel kell tüntetni.
    • Ciklusszám mérés: a megszakítás belépési és kilépési szakaszban rdtsc vagy más időbélyeg.
    • Mérési napló minta:

[ 0.001] CPU1: irq entry ts=0x0000000000101300, exit ts=0x0000000000101322, delta=34 cycles

[ 0.002] CPU1: wakeup latency min=430 cycles, max=2400 cycles, avg=730 cycles

31.1.13 Összefoglalás

Az SMP bővítés a kernelben nem egyszerűen a CPU-k számának növelését jelenti. A közös állapotok védelméhez atomi spinlockokra, a gyakran írt állapotokhoz per-CPU adatokra, a kernel preemptiójának szabályozásához pedig preempt_count-ra van szükség. A PREEMPT_RT ezeket a mechanizmusokat fejleszti tovább a determinisztikus válaszidő érdekében. A fejezet laborja egy tervdokumentum elkészítése volt, amely a mérésekkel együtt megalapozza a következő fejezetben bevezetendő hálózati és biztonsági modulok szinkronizációs igényeit. Minden mérésnél a várt értéket a hardver, a konfiguráció és a kernel kód elemzése alapján le kell vezetni, és a mért értéktől elkülönítve kell dokumentálni.
