30.4 Regresszió és kiadási minőség

30.4.1 Regressziós kapu és kiadási minőség

A szoftver nem állandó. Egy operációs rendszer kernelének fejlődése folyamatos változások sorozata: hibajavítások, új eszközmeghajtók, biztonsági foltok, teljesítményoptimalizálások és refaktorálások. Minden változás hordoz kockázatot: amit ma megjavítunk, holnap egy másik konfigurációban regresszióként térhet vissza. A regresszió fogalma azt jelenti, hogy egy korábban működő funkció, tulajdonság vagy teljesítményjellemző egy változás hatására leromlik vagy teljesen elromlik.

A kiadási minőség nem egyetlen pillanat, hanem folyamatosan fenntartott állapot. A regressziós kapu (regression gate) olyan automatikus vagy félautomata ellenőrzési pont, amelyen minden változásnak át kell haladnia, mielőtt a főágba kerülhet, vagy mielőtt kiadásra jelölhető. Célja, hogy a hibát még a fejlesztői környezetben elkapja, ne az éles rendszerben.

Ebben a fejezetben a változások biztonságos bevezetésének módszertanát dolgozzuk ki: a test matrix felépítését, a folyamatos integráció (CI) és a soak test szerepét, a rollback (visszagörgetés) mechanizmusait, valamint a hibajegy-kezelés fegyelmét. A cél nem csupán a fogalmak bemutatása, hanem egy működő mintarendszer megalkotása, amely egy egyszerű kernelmodulon vagy eszközmeghajtón keresztül mutatja be a regressziós kaput a gyakorlatban.

30.4.2 A változások biztonságos bevezetésének alapelvei

A kernel vagy bármely alacsony szintű rendszerkomponens esetében a változáskezelés nem merülhet ki abban, hogy „lefordul és elindul”. Egy biztonságos bevezetési folyamat a következő fázisokból áll:

  1. Változáskérés és indoklás: Minden változásnak legyen azonosítója és leírása. Miért szükséges? Milyen viselkedést érint? Milyen konfigurációkban releváns?
  2. Kód és teszt együtt: A változás csak akkor fogadható el, ha a hozzá tartozó tesztek is megérkeznek. A kernelkódban ez azt jelenti, hogy a meghajtóhoz tartozó unit teszt, a rendszerhíváshoz tartozó szintetikus hívás, vagy a hibajavításhoz tartozó reprodukciós teszt a patch része.
  3. Automatikus ellenőrzés: A build, a statikus elemzés, a unit tesztek és a célzott integrációs tesztek minden változásnál lefutnak. Ez a CI folyamat szíve.
  4. Emberi felülvizsgálat: Az automatikus ellenőrzés szükséges, de nem elégséges. A kernelkódban az erőforrás-tulajdonjog, a versenyhelyzetek és a hibakezelés emberi szemmel történő ellenőrzése is kötelező.
  5. Fokozatos bevezetés: A változás először egy izolált ágon, majd egy belső tesztkörnyezetben, végül egy korlátozott éles környezetben fut. Minden fázisban mérjük a regressziós mutatókat.
  6. Rollback terv: Mielőtt a változás élesbe kerül, előre meghatározzuk, hogyan lehet visszavonni. A kernel esetében ez lehet egy korábbi kernelimage, egy kapcsolóval letiltható funkció, vagy egy revert commit.

A regressziós kapu az a mechanizmus, amely ezeket a fázisokat összeköti. A kapu akkor nyílik meg, ha minden feltétel teljesül: a tesztek zöldek, a teljesítménymutatók a toleranciasávon belül vannak, a checklist ki van töltve, és a hibajegyekben nincs nyitott, magas súlyosságú regresszió.

30.4.3 Egy ellenőrizhető példa: a mailbox queue modul

A továbbiakban egy egyszerű, de valósághű kernelkomponensen dolgozunk: egy rögzített méretű, körkörös üzenetsoron (mailbox queue), amelyet két folyamat vagy megszakításkezelő és felhasználói szál közötti kommunikációra használunk. A példa azért jó, mert:

  • Kicsi, így a tesztek gyorsan lefutnak.
  • Van állapota, tehát a regresszió könnyen megfigyelhető.
  • Van párhuzamossági vetülete, így a versenyhelyzetek és a zárolási hibák is vizsgálhatók.
  • A hibák tipikusak: határeset a puffer tele/üres állapotánál, memóriatulajdonjog, megszakításbiztosság.

A modul kezdeti interfésze a következőképpen néz ki:

/* mailbox.h - egyszerű körkörös üzenetsor kernelkomponens */
#ifndef MAILBOX_H
#define MAILBOX_H

#include <stddef.h>
#include <stdbool.h>

#define MSG_SLOTS 8
#define MSG_DATA_LEN 16

struct msg {
    unsigned int sender;          /* küldő azonosítója */
    unsigned int seq;             /* sorszám a sorrend ellenőrzéséhez */
    char data[MSG_DATA_LEN];      /* hasznos adat, NUL-terminált */
};

struct mailbox {
    struct msg ring[MSG_SLOTS];   /* a körkörös puffer */
    size_t head;                  /* a következő írási pozíció */
    size_t tail;                  /* a következő olvasási pozíció */
    size_t count;                 /* a pufferben lévő üzenetek száma */
    bool initialized;             /* inicializálásjelző */
};

/* Inicializálja a leveleződobozt. Visszatérés: 0 siker, -1 ha már inicializált. */
int mailbox_init(struct mailbox *mb);

/* Üzenet hozzáadása. Visszatérés: 0 siker, -1 ha tele a puffer, -2 ha érvénytelen paraméter. */
int mailbox_send(struct mailbox *mb, const struct msg *msg);

/* Üzenet kivétele. Visszatérés: 0 siker, -1 ha üres a puffer, -2 ha érvénytelen paraméter. */
int mailbox_recv(struct mailbox *mb, struct msg *out);

#endif /* MAILBOX_H */

A példa szándékosan egyszerű, de már itt láthatók azok a pontok, ahol egy változás regressziót okozhat. A kezdeti implementáció:

/* mailbox.c - egyszerű körkörös üzenetsor implementáció */
#include "mailbox.h"

int mailbox_init(struct mailbox *mb)
{
    if (mb == NULL)
        return -2;
    if (mb->initialized)
        return -1;

    mb->head = 0;
    mb->tail = 0;
    mb->count = 0;
    mb->initialized = true;
    return 0;
}

int mailbox_send(struct mailbox *mb, const struct msg *msg)
{
    if (mb == NULL || msg == NULL)
        return -2;
    if (!mb->initialized)
        return -2;
    if (mb->count >= MSG_SLOTS)
        return -1;

    mb->ring[mb->head] = *msg;
    mb->head = (mb->head + 1) % MSG_SLOTS;
    mb->count++;
    return 0;
}

int mailbox_recv(struct mailbox *mb, struct msg *out)
{
    if (mb == NULL || out == NULL)
        return -2;
    if (!mb->initialized)
        return -2;
    if (mb->count == 0)
        return -1;

    *out = mb->ring[mb->tail];
    mb->tail = (mb->tail + 1) % MSG_SLOTS;
    mb->count--;
    return 0;
}

Ez a verzió helyesnek tűnik egy egyszálú környezetben. A tesztelés során azonban kiderül, hogy több szál esetén a count, a head és a tail módosítása nem atomi, így a puffer elveszíthet üzeneteket vagy duplikálhatja azokat. Tegyük fel, hogy a fejlesztő hozzáad egy spinlockot a struktúrához, és a következő verziót készíti el:

/* mailbox_v2.c - spinlockkal védett változat */
#include "mailbox.h"
#include "spinlock.h" /* példa: saját kernel-spinlock */

struct mailbox {
    struct msg ring[MSG_SLOTS];
    size_t head;
    size_t tail;
    size_t count;
    spinlock_t lock;      /* új mező */
    bool initialized;
};

int mailbox_send(struct mailbox *mb, const struct msg *msg)
{
    if (mb == NULL || msg == NULL)
        return -2;
    if (!mb->initialized)
        return -2;

    spin_lock(&mb->lock);
    if (mb->count >= MSG_SLOTS) {
        spin_unlock(&mb->lock);
        return -1;
    }
    mb->ring[mb->head] = *msg;
    mb->head = (mb->head + 1) % MSG_SLOTS;
    mb->count++;
    spin_unlock(&mb->lock);
    return 0;
}

Itt már látható a regresszió első gyanúja: a mailbox_init nem inicializálja a lock mezőt, mert a fejlesztő elfelejtette frissíteni az inicializáló függvényt. Ha a lock nem inicializált, a viselkedés nem definiált; bizonyos platformokon a spinlock nullázott értéke zárt állapotot jelent, másutt nem. Ez a tipikus „majdnem jó” változás, amelyet a regressziós kapunak el kell kapnia.

A unit teszt célja, hogy ezt a hibát még a commit előtt felfedje. A tesztváz:

/* test_mailbox.c - unit teszt a mailbox modulhoz */
#include "mailbox.h"
#include <assert.h>
#include <string.h>

static void test_send_recv_single(void)
{
    struct mailbox mb;
    struct msg m1, m2;

    assert(mailbox_init(&mb) == 0);

    memset(&m1, 0, sizeof(m1));
    m1.sender = 1;
    m1.seq = 100;
    strncpy(m1.data, "hello", MSG_DATA_LEN);

    assert(mailbox_send(&mb, &m1) == 0);
    assert(mb.count == 1);

    assert(mailbox_recv(&mb, &m2) == 0);
    assert(m2.sender == 1);
    assert(m2.seq == 100);
    assert(strcmp(m2.data, "hello") == 0);
    assert(mb.count == 0);
}

static void test_full_empty(void)
{
    struct mailbox mb;
    struct msg m;
    size_t i;

    assert(mailbox_init(&mb) == 0);

    /* Töltsük meg a puffert. */
    for (i = 0; i < MSG_SLOTS; i++) {
        m.sender = (unsigned int)i;
        m.seq = (unsigned int)i;
        assert(mailbox_send(&mb, &m) == 0);
    }
    /* A puffer most tele van. */
    assert(mailbox_send(&mb, &m) == -1);

    /* Ürítsük ki. */
    for (i = 0; i < MSG_SLOTS; i++) {
        assert(mailbox_recv(&mb, &m) == 0);
        assert(m.seq == i);
    }
    /* A puffer most üres. */
    assert(mailbox_recv(&mb, &m) == -1);
}

void run_mailbox_tests(void)
{
    test_send_recv_single();
    test_full_empty();
}

Ez a teszt azonban csak a funkcionális viselkedést ellenőrzi. Nem észleli a lock inicializálásának hiányát, mert egyszálú környezetben a nem inicializált spinlock gyakran „működik”. A párhuzamos tesztre később, a soak test kapcsán térünk vissza.

30.4.4 Test matrix

A test matrix (tesztmátrix) a támogatott környezetek és konfigurációk kombinációinak rendszerezett leírása. Célja, hogy a változásokat ne csak egyetlen gépen, egyetlen beállítással ellenőrizzük, hanem a lehetséges variációk reprezentatív halmazán.

Egy kernel esetében a test matrix dimenziói lehetnek:

  • Architektúra: x86_64, ARMv8, RISC-V, stb. (QEMU-ban vagy kereszthivatkozásos builddel)
  • Konfiguráció: SMP be/ki, preemptív be/ki, debug be/ki, KASAN (Kernel Address Sanitizer) be/ki
  • Eszközháttér: virtio-blk, NVMe emuláció, UART, hálózati eszköz
  • Fájlrendszer: initramfs, ext4, custom FS
  • Opcionális funkciók: a fejlesztés alatt álló modul be- és kikapcsolva

A mátrixot úgy kell megtervezni, hogy a kombinációk száma ne robbanjon fel. A gyakorlatban a teljes Descartes-szorzat helyett okosan választott, reprezentatív kombinációkat használunk. Például:

Kombináció Arch SMP Debug Sanitizer Fájlrendszer Cél
A1 x86_64 (QEMU) 1 igen KASAN initramfs alap funkcionalitás
A2 x86_64 (QEMU) 4 nem nincs ext4 SMP stressz
A3 ARMv8 (QEMU) 4 igen KASAN initramfs arch-specifikus hibák
A4 RISC-V (QEMU) 1 igen nincs initramfs hordozhatóság
B1 x86_64 (QEMU) 2 nem KASAN custom FS fájlrendszer-integráció

A táblázatban szereplő x86_64 (QEMU) és társai emulált környezeteket jelölnek. A valós hardveren történő tesztelés külön, dedikált laborban történik, soha nem a fejlesztői gépen. A QEMU konfigurációját a reprodukciós csomag tartalmazza: CPU modell, memória méret, csatolt eszközök, kernel parancssor.

A test matrix minden cellájához tartozik egy elvárt eredmény. Például az A1 kombinációban a mailbox unit tesztnek 0 hibával kell lefutnia, a rendszerindulásnak 2 másodpercen belül be kell fejeződnie, és a kernel logban nem szerepelhet panic vagy Oops. Ha bármelyik feltétel sérül, az adott cella pirosra vált, és a regressziós kapu zárva marad.

A mátrixot magát is verziózni kell. Ha egy új eszközmeghajtó kerül a kernelbe, a mátrix új sorral bővül. Ha egy régi architektúra támogatása megszűnik, a hozzá tartozó sor törlődik. A mátrix változása is review-köteles, hiszen egy rosszul definiált mátrix hamis biztonságérzetet ad.

30.4.5 Folyamatos integráció és a regressziós kapu

A folyamatos integráció (CI) az a gépesített folyamat, amely minden változásnál lefuttatja a test matrixot, és a regressziós kaput működteti. Egy kernelprojektben a CI rendszerint a következő állomásokból áll:

  1. Build stage: A kernel lefordítása minden támogatott architektúrára, a hozzá tartozó toolchainnel. Itt már elbukik a fordítási hiba, a hiányzó header, a rossz konfigurációs függőség.
  2. Unit test stage: A kernelmodulok unit tesztjei. Ezek lehetnek hoston futó tesztek (a modul C kódját a hoszt gépen, mockolt kernel API-val fordítjuk), vagy QEMU-ban futó tesztek, ahol a modul a kernelben töltődik be.
  3. Integration test stage: A teljes kernel bootolása az egyes matrix cellákban, majd a felhasználói térben futó tesztprogramok végrehajtása. Itt jelenik meg a mailbox párhuzamos tesztje is.
  4. Soak test stage: Hosszabb ideig tartó, terheléses teszt, amely a memóriaszivárgást, a fáradási hibákat és a ritka versenyhelyzeteket keresi. A soak test nem minden commitnál fut, hanem éjszakai vagy heti rendszerességgel; a kiadás előtt azonban kötelező.
  5. Packaging and release stage: A bevált változat leképezése, a binárisok előállítása, és a kiadási checklist automatizálható részének ellenőrzése.

Példa egy CI konfigurációra (YAML stílusban, szemléltetés):

# .ci/pipeline.yaml - regressziós kapu folyamat
stages:
  - build
  - unit
  - integration
  - soak
  - package

variables:
  QEMU_CPU: "cortex-a72"       # példa ARM CPU modell QEMU-hoz
  QEMU_MEM: "256M"
  TEST_TIMEOUT: "120s"

build:x86_64:
  stage: build
  script:
    - make ARCH=x86_64 defconfig
    - make ARCH=x86_64 -j$(nproc)
  artifacts:
    paths:
      - vmlinux

build:arm64:
  stage: build
  script:
    - make ARCH=arm64 defconfig
    - make ARCH=arm64 -j$(nproc) CROSS_COMPILE=aarch64-linux-gnu-
  artifacts:
    paths:
      - vmlinux.arm64

unit:mailbox:
  stage: unit
  script:
    - make -C tests/mailbox run
    - grep -q "ALL TESTS PASSED" tests/mailbox/test.log

integration:kasan:
  stage: integration
  script:
    - qemu-system-x86_64 -kernel vmlinux -append "console=ttyS0" \
        -nographic -enable-kvm -smp 4 -m 256M
    - expect tests/integration/run_suite.sh
  timeout: $TEST_TIMEOUT

soak:nightly:
  stage: soak
  script:
    - qemu-system-x86_64 -kernel vmlinux -append "console=ttyS0" \
        -nographic -smp 4 -m 256M
    - timeout 3600 tests/soak/run_soak.sh
  only:
    - schedules
  allow_failure: false

A fenti konfigurációban a soak:nightly job csak ütemezetten fut, és a allow_failure: false jelzi, hogy ha a soak teszt elbukik, a kapu zárva marad a kiadás előtt. A timeout paraméterek azt biztosítják, hogy egy beragadt teszt ne bénítsa meg a teljes folyamatot.

A regressziós kapu döntési logikája a következő:

  • Ha a build stage bármely cellája piros, a változás elutasításra kerül.
  • Ha a unit test stage bármely tesztje hibát jelez, a változás elutasításra kerül.
  • Ha az integration test stage bármely matrix cellája piros, a változás elutasításra kerül.
  • Ha a soak test (amikor fut) hibát vagy memóriaszivárgást jelez, a kiadási folyamat blokkolódik.
  • Ha minden zöld, de a checklist emberi része (review, dokumentáció, biztonsági átvilágítás) hiányos, a változás nem kerülhet a főágba.

A kapu nem csak bináris döntést hoz. A „zöld, de gyanús” állapot is létezik: ha például egy teszt a timeout határán belül, de a korábbi futáshoz képest 30%-kal lassabban fut le, a rendszer figyelmeztetést ad. A teljesítményregresszió ugyanolyan fontos, mint a funkcionális hiba.

30.4.6 Soak test és a ritka hibák felderítése

A soak test (áztatási teszt) hosszú időn át tartó, folyamatos terhelést jelent. Célja az olyan hibák felfedése, amelyek rövid tesztfutásokban nem jelentkeznek:

  • Memóriaszivárgás: a mailbox modulnál például egy rosszul kezelt hibakód miatt az üzenet puffere nem szabadul fel.
  • Ritka versenyhelyzet: a spinlock hibás használata miatt 10 000 műveletből egyszer duplikálódik egy üzenet.
  • Erőforrás-kimerülés: a fájlleírók, időzítők vagy hálózati pufferek lassú elfogyása.
  • Időzítési eltolódás: a rendszer órájának lassú driftje, amely hosszú futás után hibás időbélyegekhez vezet.

A soak test forgatókönyve a mailbox példánál:

  1. Indítsunk el N darab küldő szálat és M darab fogadó szálat.
  2. Minden küldő szál egyedi sorszámú üzeneteket küld, és naplózza a küldött sorszámokat.
  3. Minden fogadó szál fogadja az üzeneteket, ellenőrzi a sorszámok folytonosságát, és naplózza az eltéréseket.
  4. A teszt 8 órán át fut, közben a rendszer óránként pillanatképet készít a memóriahasználatról.
  5. A teszt végén a vezérlő összehasonlítja a küldött és fogadott sorszámok halmazát. Ha bármely sorszám hiányzik vagy duplikálva van, a teszt hibát jelez.

A soak test nem egyszerűen „hosszú unit teszt”. A terhelésnek változatosnak kell lennie: időnként a rendszer más komponensei is kapjanak terhelést (például egy párhuzamosan futó fájlrendszer-művelet), hogy a gyorsítótár- és ütemezőinterakciók is felszínre kerüljenek. A teszt során a megszakítások, a kontextusváltások és a laphibák száma is naplózandó.

A soak test eredményét a mérési napló tartalmazza. Példa a napló kivonatára:

[00:00] soak: mailbox stress started, senders=4, receivers=4
[01:00] soak: sent=118432, recv=118432, lost=0, dup=0, mem_free=198224 KiB
[02:00] soak: sent=236915, recv=236915, lost=0, dup=0, mem_free=197856 KiB
...
[07:59] soak: sent=948217, recv=948216, lost=1, dup=0, mem_free=194112 KiB
[08:00] soak: test FAILED, lost=1, first_lost_seq=572314

Itt látható a regresszió: a 8. órában egy üzenet elveszett. A napló megadja az első elveszett sorszámot, ami a hibakeresés kiindulópontja. A memóriacsökkenés (198 224 KiB-ról 194 112 KiB-ra) arra utal, hogy a kernel memóriája lassan fogy, ami önmagában is vizsgálatot igényel.

A soak test hosszúsága és gyakorisága a rendszer kritikusságától függ. Egy beágyazott, biztonsági kritikus rendszerben a soak test akár 72 órán át is futhat, és minden kiadás előtt kötelező. Egy fejlesztői ágon a napi 1 órás soak test is elegendő lehet a durva hibák kiszűrésére.

30.4.7 Rollback és visszagörgetési stratégiák

A legjobb tesztelés sem képes minden hibát elkapni. Ezért minden változáshoz tartozik egy előre meghatározott rollback stratégia. A rollback lényege, hogy a rendszer visszaállítható egy ismert jó állapotba anélkül, hogy a felhasználói adatok sérülnének vagy a szolgáltatás hosszabb időre kiesne.

Kernelkörnyezetben a rollbacknek több szintje van:

  • Commit szintű revert: A változás visszavonása a verziókezelőben. Ez a legegyszerűbb, de csak akkor alkalmazható, ha a változás még nem terjedt el. Ha a hibás commit után már több másik commit is született, a tiszta revert nehézkes lehet.
  • Fordítási kapcsoló: A funkció be- és kikapcsolható egy konfigurációs opcióval vagy kernelparanccsal. Ha a mailbox modul hibás, a mailbox.enable=0 paraméterrel letiltható, és a rendszer a régi, bevált kommunikációs mechanizmust használja.
  • Dupla kép (A/B): A rendszer két kernelimage-t tárol. Az aktív image mellett egy tartalék image is van. Ha az új kernel nem bootol vagy instabil, a bootloader egy számláló alapján automatikusan a tartalék image-re vált. Ez a módszer elterjedt beágyazott és mobil rendszerekben.
  • Csomag-visszaállítás: A disztribúciós csomagkezelő a kernelcsomag korábbi verzióját telepíti vissza. Ez a felhasználói térből is elvégezhető, de kernelpánik esetén a bootloader szintű visszaállítás is szükséges lehet.

A rollback terv része a visszaállítási út dokumentálása. Minden változáshoz fel kell jegyezni:

  • Melyik commit vagy csomag az utolsó ismert jó állapot?
  • Hogyan lehet a hibás állapotot észlelni? (Pl. panic a logban, magas latencia, hibás checksum.)
  • Milyen parancsokkal vagy lépésekkel lehet visszaállni?
  • Milyen adatok sérülhetnek a visszaállítás során, és hogyan lehet azokat helyreállítani?
  • Ki a felelős a visszaállítás végrehajtásáért?

A rollback nem a kudarc beismerése, hanem a mérnöki fegyelem része. A biztonságos bevezetés azt jelenti, hogy a rollback lehetősége már a változás tervezésekor létezik, nem akkor, amikor a hiba már élesben tombol.

Példa egy bootloader konfigurációra A/B visszaállítással:

# boot.conf - A/B rendszerindítási konfiguráció
# A jelenlegi (aktív) kernel
active = kernel_b.img
# A tartalék kernel
backup = kernel_a.img
# Hányszor próbálja meg az aktív kernelt elindítani, mielőtt váltana
max_attempts = 3
# Az utolsó sikeres boot időbélyege
last_success = 2025-03-28T11:45:00Z

Ha a kernel_b.img három egymást követő indítási kísérletben sem éri el a felhasználói tér inicializálását, a bootloader automatikusan a kernel_a.img-t tölti be, és hibajegyet generál.

30.4.8 Hibajegy-kezelés és a regressziós kapu kapcsolata

A hibajegy-kezelő rendszer (issue tracker) a regressziós kapu emberi oldalát képviseli. Minden automatikus teszteredményhez tartozik egy hibajegy, amely tartalmazza:

  • A hiba azonosítóját és súlyosságát.
  • A reprodukciós lépéseket, beleértve a pontos konfigurációt, a buildparancsot és a mérési naplót.
  • Az érintett komponenst (pl. mailbox.c).
  • A hibát bevezető commit azonosítóját vagy gyanús tartományát.
  • Az állapotot (nyitott, folyamatban, javított, ellenőrzött).
  • Az ellenőrzéshez használt tesztet, amely a jövőben regressziós tesztként fut.

A regressziós kapu szempontjából a hibajegyek súlyossági besorolása döntő:

  • Critical: A rendszer nem bootol, adatvesztés, biztonsági rés. A kapu zárva, a változás azonnal visszavonandó.
  • High: A funkció fő útvonala hibás, teljesítményregresszió a tűréshatáron túl. A kapu zárva, a javítás a következő ciklusban kötelező.
  • Medium: Nem kritikus funkció hibája, kozmetikai hiba, ritka körülmények között. A kapu nyitható, de a hiba a kiadási checklistre kerül, és a következő kiadásban javítandó.
  • Low: Kisebb eltérés a dokumentációtól, javasolt optimalizálás. A kapu nyitva, a hiba nyomon követve.

A hibajegy életciklusa a következő:

  1. Bejelentés: A teszt vagy a felhasználó jelzi a hibát. A bejelentéshez automatikusan csatolódik a tesztnapló, a konfiguráció és a reprodukciós lépések. A „nem tudom reprodukálni” állapot a jegy elutasításához vezet.
  2. Triage: A karbantartó meghatározza a súlyosságot és a felelőst. A critical hibák azonnali figyelmet kapnak.
  3. Javítás: A fejlesztő elkészíti a patch-et, és hozzáadja a regressziós tesztet.
  4. Ellenőrzés: A patch átmegy a regressziós kapun. Ha a teszt megbukott, a jegy visszakerül a fejlesztőhöz.
  5. Lezárás: A javítás a főágba kerül, a jegy lezárul, de a regressziós teszt a kapuban marad.

A mailbox példánál a folyamat így néz ki:

  • Bejelentés: „A 8 órás soak test során 1 üzenet elveszett. Első elveszett sorszám: 572314. A memóriahasználat 198 224 KiB-ról 194 112 KiB-ra csökkent.”
  • Triage: A hiba súlyossága High, mert adatvesztést okoz. A felelős a mailbox modul karbantartója.
  • Javítás: A fejlesztő megtalálja a hibát: a spinlock nem volt inicializálva, és bizonyos időzítéseknél a count mező nem volt konzisztens. A patch inicializálja a lockot, és a mailbox_init-be lock-inicializálást tesz. A fejlesztő hozzáad egy regressziós tesztet, amely 1 millió üzenetet küld és fogad párhuzamosan, és ellenőrzi a sorszámok folytonosságát.
  • Ellenőrzés: A patch átmegy a CI-n, a párhuzamos teszt és a soak test is zöld.
  • Lezárás: A jegy lezárul, a regressziós teszt a kapuban marad.

30.4.9 Kiadási checklist

A kiadási checklist a regressziós kapu emberi oldala. Az automatikus tesztek szükségesek, de nem elégségesek. A checklist biztosítja, hogy a nem automatizálható szempontok is érvényesüljenek. Egy kernelkiadás checklistje a következő elemeket tartalmazhatja:

  1. Kód és teszt elválasztása: A kiadásra jelölt commitban a kód és a teszt külön ellenőrzött. Nincs olyan kódrészlet, amely csak a teszt kedvéért került be.
  2. Dokumentáció: A változások leírása, a konfigurációs lehetőségek, a hibakódok és az ABI-módosítások dokumentálva vannak.
  3. Erőforrás-tulajdonjog: A kernelkódban minden lefoglalt erőforrás (memória, lock, fájlleíró) tulajdonjoga egyértelmű. Nincs double-free, nincs leak.
  4. Hibakezelés: Minden hibakódot ellenőriz a kód. A panic csak valóban végzetes, nem helyreállítható állapotban hívódik.
  5. Versenyhelyzetek: A közös állapotot védő lockok, atomi műveletek és memóriabarrierek helyesek. A lockolási sorrend dokumentált.
  6. Biztonsági átvilágítás: A felhasználói térből érkező mutatók, méretek és indexek ellenőrzöttek. Nincs puffertúlcsordulás, nincs use-after-free.
  7. Reprodukciós csomag: A kiadáshoz tartozik a buildparancs, a linker script, a futtatási parancs, a naplók és a mérési eredmények.
  8. Rollback terv: A kiadás előtt ellenőrizve, hogy a rollback mechanizmus működik, és a visszaállítási út dokumentált.
  9. Ismert korlátok: A nem javított, de elfogadott hibák listája a kiadási jegyzethez csatolva.

A checklisten minden tételhez tartozik egy felelős és egy állapot (teljesült, nem teljesült, nem alkalmazható). A regressziós kapu csak akkor nyílik meg, ha a checklisten nincs „nem teljesült” tétel.

30.4.10 Tipikus hibák és helyes megoldások

A regressziós kapu tervezése során gyakori hibák:

Hiba: A kapu csak a buildre és a unit tesztekre épít.
Következmény: Az integrációs és soak tesztek kimaradnak, így a párhuzamos hibák és a memóriaszivárgás észrevétlen marad.
Megoldás: A kapu minden fázist lefed, a soak test a kiadás előtt kötelező.

Hiba: A test matrix nem reprezentatív.
Következmény: A tesztek zöldek, de a valós környezetben mégis hiba jelentkezik, mert a mátrix nem tartalmazza az adott konfigurációt.
Megoldás: A mátrixot rendszeresen felülvizsgáljuk, és a felhasználói hibajelentések alapján új kombinációkat adunk hozzá.

Hiba: A regressziós teszt hiányzik a hibajavításból.
Következmény: Ugyanaz a hiba később újra bekerül, mert semmi sem akadályozza meg.
Megoldás: A hibajegy lezárásának feltétele a regressziós teszt megléte. A kapu ezt automatikusan ellenőrzi: ha a jegyhez tartozó teszt nem fut le, a kapu zárva marad.

Hiba: A rollback tervet a kiadás után készítik el.
Következmény: Amikor a hiba élesben jelentkezik, a visszaállítás kapkodva, adatvesztéssel történik.
Megoldás: A rollback terv a változás tervezési fázisában készül, és a checklist része.

Hiba: A mérési napló nem tartalmazza a várt és mért értéket külön.
Következmény: A teszteredmény nem reprodukálható, a regresszió megállapítása bizonytalan.
Megoldás: Minden mérési naplóban a várt értéket és a mért értéket külön oszlopban, a mértékegységgel együtt kell feltüntetni.

30.4.11 Labor: regressziós kapu és kiadási checklist

A labor nem valós hardvert használ, hanem QEMU-t vagy más emulátort, és a hoszt gép lemezét, bootloaderét vagy rendszerpartícióját tilos módosítani. A labor minden állomása egy eldobható, emulált környezetben fut.

30.4.12 Előkészítés

  1. Hozz létre egy munkakönyvtárat: mkdir ~/lab-os117 && cd ~/lab-os117.
  2. Készíts egy egyszerű C programot, amely a mailbox modult teszteli felhasználói térben. A modul kódját a fejezetben bemutatott mailbox.c-ből származtathatod, de a spinlock részt egy egyszerű, nem atomi változattal helyettesítheted a hiba szimulálásához.
  3. Készíts egy Python vagy shell tesztfuttatót, amely a programot N-szer lefuttatja, és a kimenetet naplózza.

30.4.13 A regressziós kapu futtatása

A laborban három tesztet futtatunk:

  1. Funkcionális teszt: A mailbox küldd- és fogadd-műveleteit ellenőrzi egyszálú környezetben. Várt eredmény: 0 hiba.
  2. Párhuzamos teszt: Két szál egyszerre küld és fogad. A teszt 10 000 üzenetet továbbít, és ellenőrzi a sorszámok folytonosságát. Várt eredmény: 0 elveszett vagy duplikált üzenet.
  3. Soak teszt (rövidített): A párhuzamos teszt 60 másodpercig fut, és közben a memóriahasználatot is naplózza. Várt eredmény: nincs szivárgás, nincs elveszett üzenet.

Példa a tesztfuttatóra (Python):

#!/usr/bin/env python3
# run_gate.py - regressziós kapu a mailbox példához
import subprocess
import time
import json
import sys

def run_test(name, command, expected_exit=0, timeout=5):
    start = time.monotonic()
    proc = subprocess.run(command, shell=True, capture_output=True,
                          text=True, timeout=timeout)
    elapsed = time.monotonic() - start
    result = {
        "name": name,
        "command": command,
        "exit_code": proc.returncode,
        "expected_exit": expected_exit,
        "elapsed_sec": round(elapsed, 3),
        "stdout": proc.stdout[-200:],
        "stderr": proc.stderr[-200:],
        "passed": proc.returncode == expected_exit
    }
    return result

def main():
    results = []
    results.append(run_test("functional",
        "./mailbox_test --test=functional"))
    results.append(run_test("parallel",
        "./mailbox_test --test=parallel --messages=10000"))
    results.append(run_test("soak_short",
        "./mailbox_test --test=soak --duration=60"))

    # Mentés JSON naplóba
    with open("gate_results.json", "w") as f:
        json.dump(results, f, indent=2)

    # A kapu döntése
    all_passed = all(r["passed"] for r in results)
    print(json.dumps(results, indent=2))
    if all_passed:
        print("GATE: PASS")
        sys.exit(0)
    else:
        print("GATE: FAIL")
        sys.exit(1)

if __name__ == "__main__":
    main()

A labor során először a hibás verziót futtasd le. A párhuzamos teszt valószínűleg néhány elveszett üzenetet jelez, mert a count mező nem atomi. A naplóban a mért eredmény (lost > 0) eltér a várt eredménytől (lost = 0). Ez a regressziós kapu zárva marad.

Ezután javítsd a hibát: adj hozzá egy egyszerű zárolást (például atomi műveletekkel), és futtasd újra a kaput. A naplóban most a mért és a várt eredmény megegyezik, a kapu nyílik.
