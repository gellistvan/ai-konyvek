29.3 VFS integráció és fájlleírók

A VFS-integráció akkor válik hasznos réteggé, amikor a fájlrendszer már nem a saját, belső hívásaival dolgozik, hanem beilleszkedik a rendszer közös, hierarchikus névterébe. Ebben a fejezetben azt vizsgáljuk meg, hogyan lehet egy egyszerű fájlrendszert csatlakoztatni a virtuális fájlrendszerhez (VFS), milyen adatszerkezetek és művelettáblák szükségesek ehhez, és miként kapcsolódik a mount, a dentry, az inode és a file object a folyamatok fájlleíró-táblájához. A cél nem egy teljes értékű kernel VFS felépítése, hanem egy ellenőrizhető, tanulható minimális minta, amelyen a fontos fogalmak mérhetők és reprodukálhatók.

29.3.1 1. Miért közös névtér?

A UNIX-szerű rendszerek egyik alapgondolata, hogy a felhasználói programok számára a tárolóeszközök nem külön betűjelekkel vagy külön API-val jelennek meg, hanem egyetlen hierarchikus fában. A merevlemez-partíció, az initrd, a hálózati fájlrendszer és a RAM-ban lévő ideiglenes tároló egyaránt ugyanazzal az open, read, write, close felülettel érhető el. A VFS ezt az egységesítést valósítja meg: a felső réteg egy közös rendszerhívás-felületet és közös adatszerkezeteket ad, az alsó réteg pedig az egyes fájlrendszerek specifikus műveleteit.

A réteges szerkezet a következőképpen ábrázolható:

felhasználói program
        |
      sys_open / sys_read / sys_write
        |
 +------+-------------------------+
 | VFS réteg: path feloldás, mount |
 | dentry, inode, file object      |
 +------+-------------------------+
        |
 +------+------------+------------+
 | memfs | ext4-szerű | ...       |
 | (RAM) | blokkfs    |            |
 +------+------------+------------+
        |
    blokk-eszköz driver (os111)

Jelmagyarázat: a folytonos nyíl a hívás irányát, a szaggatott réteghatár az alrendszerek határait mutatja. A VFS rétegnek nem szabad az alsó fájlrendszer belső lemezszerkezetéről tudnia.

29.3.2 2. A mount mint névtérkapcsoló

A mount művelet az a pillanat, amikor egy fájlrendszer gyökere bekerül a közös fába. A VFS ezért megkülönbözteti a fájlrendszer saját gyökerét (root dentry) és a beillesztési pontot (mountpoint dentry). A struct mount a kettő közötti kapcsolatot rögzíti. Egy egyszerűsített kernelbeli ábrázolás így nézhet ki:

struct mount {
    struct mount *next;
    struct dentry *mountpoint;   /* a közös fában lévő pont */
    struct dentry *root;         /* a csatolt fs gyökere */
    struct super_block *sb;      /* a csatolt fs szuperblokkja */
    unsigned int flags;
};

A mount folyamata lépésenként a következő:

  1. Ellenőrizzük, hogy a target útvonal létező könyvtárra mutat, és a dentry inode-ja valóban könyvtár.
  2. Az fstype alapján meghívjuk a fájlrendszer fill_super vagy mount metódusát, amely beolvassa a szuperblokkot, felépíti a gyökér-inode-ot és a root dentry-t.
  3. Lefoglalunk egy struct mount-ot, beállítjuk a mountpoint-ot és a root-ot.
  4. A mount-ot beillesztjük a processz mount-névterébe (egyszerű esetben egy globális listába).
  5. A path feloldás során a VFS ügyel arra, hogy ha a bejárás eléri a mountpoint-ot, átlépjen a hozzá tartozó root-ra.

Ezt a lépést egy szándékosan egyszerű függvényben így lehet összefoglalni:

int vfs_mount(const char *source, const char *target,
              const char *fstype, unsigned long flags)
{
    struct dentry *d = path_resolve(target);
    if (IS_ERR(d))
        return PTR_ERR(d);

    if (!S_ISDIR(d->d_inode->i_mode)) {
        dput(d);
        return -ENOTDIR;
    }

    struct file_system_type *fs = lookup_fs(fstype);
    if (!fs) {
        dput(d);
        return -ENODEV;
    }

    struct super_block *sb = fs->mount(source, flags);
    if (IS_ERR(sb)) {
        dput(d);
        return PTR_ERR(sb);
    }

    struct mount *mnt = kzalloc(sizeof(*mnt));
    if (!mnt) {
        sb->s_op->put_super(sb);
        dput(d);
        return -ENOMEM;
    }

    mnt->mountpoint = d;
    mnt->root = sb->s_root;
    mnt->sb = sb;
    mnt->flags = flags;

    mount_list_insert(mnt);
    return 0;
}

A példa adatszerkezetei szándékosan egyszerűsítettek; valós kernelben a mount névtér per processz, a lockolás finomabb, és a mount pontok referencia-számlálása is részletesebb. A lényeg az, hogy a source, target, fstype fogalmak már ebben a minimális modellben is szétválnak. A source lehet blokk-eszköz (/dev/vdb1) vagy virtuális forrás ("none" memfs esetén); a target mindig egy már létező könyvtár a közös fában.

A mount pont alatti korábbi tartalom nem vész el, csak átmenetileg eltűnik a path feloldás elől. Ha a mount-ot leválasztjuk, az eredeti dentry-inode pár ismét láthatóvá válik. Ezt a tulajdonságot a VFS-nek úgy kell kezelnie, hogy a path bejárás közben minden komponensnél megvizsgálja, van-e aktív mount az adott dentry-n.

29.3.3 3. Dentry: a névtér komponense

A dentry (directory entry) a VFS memóriabeli névtér-eleme. Nem feltétlenül egyezik meg a lemezen tárolt könyvtárbejegyzéssel; a VFS dentry-ket gyorsítótárként is használ. Egy dentry jellemzően a következő mezőket tartalmazza:

struct qstr {
    const char *name;
    unsigned int len;
};

struct dentry {
    struct qstr d_name;
    struct inode *d_inode;
    struct dentry *d_parent;
    int d_count;
};

A d_count referencia-számláló. A VFS szabály: amíg egy kód dentry-mutatót tart, a számlálót növelnie kell (dget), és ha már nincs szüksége rá, csökkentenie kell (dput). Ez megakadályozza, hogy a dentry-t felszabadítsuk, miközben egy másik útvonal-feloldás még használja. A d_parent a szülőre mutat, így a felfelé haladás és a relatív útvonalak is kezelhetők.

A dentry cache célja, hogy ugyanazon név feloldását ne kelljen minden open-nél a lemezen kezdeni. A VFS egy hash-táblában tárolja a (parent, name) párokat. A lookup nagyjából így működik:

struct dentry *d_lookup(struct dentry *parent, struct qstr *name)
{
    unsigned int hash = dentry_hash(parent, name);
    struct dentry *d;

    list_for_each_entry(d, &dentry_hashtable[hash], d_hash) {
        if (d->d_parent == parent &&
            qstr_equal(&d->d_name, name)) {
            dget(d);
            return d;
        }
    }
    return NULL;
}

Ha nincs találat, a VFS a szülő inode lookup műveletét hívja, amely a fájlrendszer-specifikus könyvtárbeolvasást végzi. A frissen talált inode-hoz dentry-t rendelünk (d_instantiate). Negatív dentry-ket is érdemes cache-elni: ha egy név nem létezik, a negatív bejegyzés gyors ENOENT választ ad a következő keresésnél.

Az útvonal-feloldás (path_resolve) komponensenként halad:

struct dentry *path_resolve(const char *path)
{
    struct dentry *d = current->fs->root;
    if (*path == '/') {
        d = current->fs->root;
        path++;
    }

    while (*path) {
        const char *end = strchrnul(path, '/');
        struct qstr name = { path, end - path };

        if (!S_ISDIR(d->d_inode->i_mode)) {
            dput(d);
            return ERR_PTR(-ENOTDIR);
        }

        d = d_lookup(d, &name);
        if (!d) {
            d = d->d_inode->i_op->lookup(d->d_inode, &name);
            if (IS_ERR(d))
                return d;
        }

        if (mount_here(d)) {
            d = mount_step(d);
        }

        path = end;
        if (*path == '/')
            path++;
    }

    dget(d);
    return d;
}

A mount_here ellenőrzi, hogy a dentry egy aktív mount point-e. Ha igen, a bejárás a csatolt fájlrendszer gyökerén folytatódik. Ezzel valósul meg az a megfigyelés, hogy a /mnt/demo.txt elérése a memfs gyökérben kezdődik, ha /mnt-re memfs van szerelve.

29.3.4 4. Inode és inode operations

Az inode az objektumot (fájlt, könyvtárat, eszközt) írja le a fájlrendszer szempontjából. A VFS inode nem a lemezes inode, hanem annak memóriabeli reprezentációja. A közös mezők mellett a fájlrendszer-specifikus adatok egy privát mutatóban élnek:

struct inode {
    unsigned long i_ino;
    uint32_t i_mode;
    size_t i_size;
    struct super_block *i_sb;
    const struct inode_operations *i_op;
    const struct file_operations *i_fop;
    void *i_private;       /* fs-specifikus adat */
    spinlock_t i_lock;
};

A i_mode a típust és a jogosultságokat hordozza; a S_ISDIR és S_ISREG makrókkal vizsgálható. A i_private például egy memfs esetén a RAM-beli inode-ra mutató pointer lehet.

Az inode-műveletek a névtér-műveletek egy részét fedik le:

struct inode_operations {
    struct dentry *(*lookup)(struct inode *dir,
                             const char *name, size_t len);
    int (*create)(struct inode *dir, const char *name,
                  size_t len, mode_t mode);
    int (*unlink)(struct inode *dir, const char *name,
                  size_t len);
    int (*mkdir)(struct inode *dir, const char *name,
                 size_t len, mode_t mode);
    int (*rmdir)(struct inode *dir, const char *name,
                 size_t len);
    int (*setattr)(struct dentry *d, struct iattr *attr);
    int (*getattr)(const struct path *p, struct kstat *stat);
};

A lookup feladata a könyvtárbejegyzés megkeresése. A memfs példában egy láncolt listát vagy tömböt járunk be:

struct memfs_inode {
    unsigned int ino;
    uint32_t mode;
    size_t size;
    unsigned char *data;
    struct list_head children; /* könyvtár bejegyzések */
};

A lookup implementáció például:

struct dentry *memfs_lookup(struct inode *dir,
                            const char *name, size_t len)
{
    struct memfs_inode *m = dir->i_private;
    struct memfs_entry *e;

    list_for_each_entry(e, &m->children, list) {
        if (strlen(e->name) == len &&
            memcmp(e->name, name, len) == 0) {
            struct inode *ino = memfs_iget(e->ino);
            return d_splice_alias(ino, NULL);
        }
    }

    return ERR_PTR(-ENOENT);
}

A d_splice_alias a dentry-t és az inode-ot összekapcsolja, és felviszi a dentry cache-be. A példa itt leegyszerűsített; a tanulási szempontból fontos, hogy a lookup nem hoz létre új fájlt, csak meglévőt keres. A létrehozás külön create művelet.

29.3.5 5. File operations és file object

Az inode a fájlrendszerben tárolt objektumot írja le, de a megnyitott fájlhoz tartozó állapotot a struct file tárolja. Ez a különválasztás az egyik leggyakoribb félreértés forrása: az inode nem tartalmaz fájlleíró-tulajdonságot, mint az aktuális eltolás (offset), a nyitási mód vagy a legutóbbi pozíció.

struct file {
    struct mutex f_lock;
    struct inode *f_inode;
    uint32_t f_flags;
    loff_t f_pos;                 /* aktuális offset */
    unsigned int f_mode;
    const struct file_operations *f_op;
    void *f_private;
};

A f_pos a következő olvasási vagy írási pozíció. A read és write rendszerhívás ezt a mezőt automatikusan növeli. A lseek rendszerhívás ezt a mezőt módosítja. A pread és pwrite ezzel szemben nem módosítják a f_pos-t.

A file_operations tábla a megnyitott fájlra vonatkozó műveleteket tartalmazza:

struct file_operations {
    int (*open)(struct inode *ino, struct file *f);
    ssize_t (*read)(struct file *f, void *buf, size_t count,
                    loff_t *pos);
    ssize_t (*write)(struct file *f, const void *buf,
                     size_t count, loff_t *pos);
    loff_t (*llseek)(struct file *f, loff_t offset, int whence);
    int (*release)(struct inode *ino, struct file *f);
};

A read és write implementációjának a pos mutatón keresztül kell frissítenie az offsetet. Ez a VFS-szerződés része, és a fájlrendszer írója nem hivatkozhat közvetlenül a f_pos mezőre a file_operations-ön belül. Egy példa memfs-olvasás:

ssize_t memfs_read(struct file *f, void *buf, size_t count,
                   loff_t *pos)
{
    struct inode *ino = f->f_inode;
    struct memfs_inode *m = ino->i_private;

    mutex_lock(&f->f_lock);

    if (*pos < 0) {
        mutex_unlock(&f->f_lock);
        return -EINVAL;
    }

    if (*pos >= m->size) {
        mutex_unlock(&f->f_lock);
        return 0; /* EOF */
    }

    size_t n = min(count, m->size - *pos);
    memcpy(buf, m->data + *pos, n);
    *pos += n;

    mutex_unlock(&f->f_lock);
    return n;
}

A f_lock zár biztosítja, hogy ugyanazon a file objecten párhuzamos olvasás és írás ne sérthesse az offsetet. Ha a fájlleírót egy dup hívás megosztja, akkor a megosztott struct file és így a közös f_lock is védi az offsetet.

29.3.6 6. Fájlleírók és offset kezelése

A felhasználói program számára a open visszatérési értéke egy kis egész szám, a fájlleíró (fd). A kernel ezt a számot indexként használja a folyamat files táblájában:

#define MAX_FD 256

struct task_struct {
    struct file *files[MAX_FD];
};

A fájlleíró-allokáció a legkisebb szabad indexet adja. A open sikeres végrehajtásakor a struct file mutató bekerül a táblába. Ettől kezdve a read, write, lseek, close mind ezen a számon hivatkozik a fájlra.

Az offset kezelése az egyik legkritikusabb VFS-szerződés. A struct file f_pos-a az open file description része, nem a fájlé. Ha ugyanazt a fájlt két külön open hívással nyitjuk meg, két külön struct file jön létre, és az offsetek függetlenek. Ha azonban a fájlleírót dup-pal vagy fork-kal másoljuk, a két fd ugyanarra a struct file-ra mutat, ezért az offsetet megosztják. Ez a POSIX-szemantika fontos oka annak, hogy a struct file referencia-számlálást is igényel.

Egy minimális dup implementáció a következő:

int sys_dup(int oldfd)
{
    struct file *f = fd_get(oldfd);
    if (!f)
        return -EBADF;

    int newfd = fd_alloc();
    if (newfd < 0)
        return -EMFILE;

    file_get(f);            /* növeli a struct file refcountját */
    fd_set(newfd, f);
    return newfd;
}

A file_get növeli a struct file referencia-számlálóját, így a két fd közös életciklusúvá válik. A close csak az egyik fd-t szünteti meg; a struct file akkor szabadul fel, amikor az utolsó hivatkozás is megszűnik.

A fájlleíró-tábla és a struct file kapcsolata a rendszerhívások rétegében:

ssize_t sys_read(int fd, void *ubuf, size_t count)
{
    struct file *f = fd_get(fd);
    if (!f)
        return -EBADF;

    if (!(f->f_mode & O_RDONLY))
        return -EBADF;

    return f->f_op->read(f, ubuf, count, &f->f_pos);
}

loff_t sys_lseek(int fd, loff_t offset, int whence)
{
    struct file *f = fd_get(fd);
    if (!f)
        return -EBADF;

    return f->f_op->llseek(f, offset, whence);
}

Az llseek tipikus megvalósítása ellenőrzi a whence értéket, és frissíti a f_pos-t:

loff_t generic_file_llseek(struct file *f, loff_t offset, int whence)
{
    loff_t newpos;

    switch (whence) {
    case SEEK_SET:
        newpos = offset;
        break;
    case SEEK_CUR:
        newpos = f->f_pos + offset;
        break;
    case SEEK_END:
        newpos = f->f_inode->i_size + offset;
        break;
    default:
        return -EINVAL;
    }

    if (newpos < 0)
        return -EINVAL;

    f->f_pos = newpos;
    return newpos;
}

Hibakódok és errno a VFS rétegben is szigorúan elválik: a kernel belső hívásai negatív hibakódot adnak vissza, a rendszerhívás réteg pedig a felhasználói térbe való visszatérés előtt beállítja a errno értéket és -1-et ad. A fejezet példáiban a return -ENOENT alakot használjuk a kernelbelsőben.

29.3.7 7. Integrációs példa: memfs mount a /mnt könyvtárra

A következő példa egy minimális memfs-t csatlakoztat a közös fába. A memfs nem használ blokk-eszközt; minden fájl és könyvtár a RAM-ban él. A mount source paramétere ilyenkor lehet "none", a fstype pedig "memfs".

A memfs mount metódusa felépíti a szuperblokkot és a gyökércsomópontot:

struct super_block *memfs_mount(const char *source,
                                unsigned long flags)
{
    struct super_block *sb = kzalloc(sizeof(*sb));
    if (!sb)
        return ERR_PTR(-ENOMEM);

    sb->s_blocksize = 4096;
    sb->s_magic = 0x4D454D46;   /* "MEMF" */
    sb->s_op = &memfs_super_ops;

    struct inode *root_ino = memfs_new_inode(S_IFDIR | 0755);
    if (!root_ino) {
        kfree(sb);
        return ERR_PTR(-ENOMEM);
    }

    sb->s_root = d_alloc_root(root_ino);
    if (!sb->s_root) {
        memfs_free_inode(root_ino);
        kfree(sb);
        return ERR_PTR(-ENOMEM);
    }

    return sb;
}

A mount után a felhasználói program a szokásos módon hívja az open-t:

int fd = open("/mnt/demo.txt", O_RDWR | O_CREAT, 0600);
if (fd < 0) {
    perror("open");
    return 1;
}

ssize_t n = write(fd, "hello\n", 6);
if (n != 6) {
    perror("write");
    close(fd);
    return 1;
}

lseek(fd, 0, SEEK_SET);
char buf[16] = {0};
n = read(fd, buf, sizeof(buf));
close(fd);

A kernelben ezek a hívások így kapcsolódnak össze:

  1. A open átadja a /mnt/demo.txt útvonalat a path_resolve-nak.
  2. A / komponenst a folyamat root dentry-je oldja fel.
  3. A mnt komponensnél a VFS észleli a memfs mount-ot, és átlép a memfs root-jára.
  4. A demo.txt komponenst a memfs lookup keresi; ha nincs ilyen fájl, a create művelet létrehozza.
  5. A VFS lefoglal egy struct file-ot, beállítja az f_op-ot a memfs file_operations-re, és beilleszti a files táblába.
  6. A read és write a struct file f_pos mezőjén keresztül frissíti az offsetet.

A O_CREAT és a mode paraméter a create inode-műveletbe kerül. A O_RDWR a file_operations open/read/write kiválasztását befolyásolja. A VFS ezeket a flag-eket már a open rendszerhívás rétegében ellenőrzi.

29.3.8 8. Tipikus hibák és helyes kezelésük

A VFS-integráció során a következő hibák fordulnak elő leggyakrabban:

  1. Az offset nem a file-ban, hanem az inode-ban él. Ha a fejlesztő az inode-ba teszi a pozíciót, akkor két párhuzamos open ugyanazt a pozíciót módosítja, és a dup szemantika is elromlik. Helyes megoldás: struct file f_pos, és a file_operations mindig a kapott pos pointerrel dolgozik.

  2. A dentry referencia-számláló hiánya. A path_resolve után a dentry d_count-ját növelni kell, és a használat után dput-ot hívni. Ha ez elmarad, a dentry felszabadítása use-after-free hibát okozhat. A dentry cache lookup és a mount átlépés során is meg kell őrizni a referenciákat.

  3. A mount pont alatti tartalom elvesztése. A path_resolve-nak minden komponensnél ellenőriznie kell a mount-táblát. Ha ezt kihagyjuk, a /mnt alatt a háttér-fájlrendszer könyvtára marad látható, és a csatolt fájlrendszer elérhetetlen.

  4. A read/write offset-ellenőrzés hiánya. Az offset lehet negatív (lseek után), vagy a count nagyobb, mint az off_t tartománya. A memfs_read-ben a *pos < 0 és a m->size - *pos ellenőrzés szükséges. Az EOVERFLOW vagy EINVAL hibát ilyenkor a VFS-nek kell visszaadnia.

  5. A fájlleíró-tábla túlcsordulása. A fd_alloc-nak ellenőriznie kell a MAX_FD határt, és EMFILE-t kell adnia, ha nincs szabad slot. A EBADF a nem létező fd-re utal, a kettőt nem szabad összekeverni.

  6. Versenyhelyzet a file offseten. Ha a read/write nem veszi fel a f_lock zárat, két szál párhuzamosan olvashatja és növelheti ugyanazt a pos-t. Ez adatvesztést okozhat. A struct file-hoz tartozó zárnak a teljes kritikus szakaszra kell kiterjednie.

  7. Hibakód-konverzió a user/kernel határon. A kernel negatív hibakódokat ad; a felhasználói tér felé ezt -1-re és errno értékre kell fordítani. Ha a read rendszerhívás -ENOENT-et ad vissza, a felhasználó -1-et és errno==ENOENT-et kap.

29.3.9 9. Labor: VFS-interfész és mount implementáció

Ez a labor a Blokk-eszköz és driver implementáció blokk-eszköz driverére épül, de a tanulási célhoz egy RAM-ban tárolt memfs is elegendő. A feladat egy működő vfs_mount, path_resolve, open, read, write, lseek, close lánc implementálása, majd a mount és a fájlműveletek reprodukálható mérése emulált környezetben.

Kiinduló állapot. A kernelünk a Blokk-eszköz és driver implementáció fejezet után már rendelkezik egy blokk-eszköz réteggel, például bd_read(sector) és bd_write(sector) hívásokkal. A fájlrendszer most egy memfs, amely a blokk-eszközt nem használja, de a mount pontján keresztül ugyanúgy elérhető. A hoszt lemezét nem módosítjuk, minden futás a QEMU vendég RAM-jában történik.

Konfiguráció. A reprodukciós csomag tartalma:

vfs-lab/
  Makefile
  qemu-run.sh
  kernel.ld
  src/
    vfs.c
    memfs.c
    block.c
    task.c
  README.md
  logs/

A QEMU alábbi paraméterekkel indul:

qemu-system-x86_64 -kernel build/kernel.bin \
  -m 128M -smp 1 -nographic \
  -no-reboot -no-shutdown

A vendég CPU qemu64, a memória 128 MiB, a megszakítások engedélyezve vannak a mérés alatt. A kernel a -O2 -fno-strict-aliasing kapcsolóval készül. A pontos GCC és QEMU verziót a README.md-ben rögzíteni kell, és a mért értékekhez csatolni.

A labor lépései.

  1. Másold a kiinduló kernel forrást a lab könyvtárába.
  2. Implementáld a vfs_mount és a mount-léptetés logikáját a path_resolve-ban.
  3. Implementáld a memfs lookup, create, read, write, llseek műveleteket.
  4. Indítsd el a kernelt, és hívd a következő tesztet:
static void vfs_test(void)
{
    int fd = open("/mnt/test.txt", O_RDWR | O_CREAT, 0600);
    assert(fd >= 0);

    const char *msg = "vfs-integration\n";
    ssize_t n = write(fd, msg, strlen(msg));
    assert(n == strlen(msg));

    lseek(fd, 0, SEEK_SET);
    char buf[32] = {0};
    n = read(fd, buf, sizeof(buf));
    assert(n == strlen(msg));
    assert(memcmp(buf, msg, n) == 0);

    close(fd);
    dmesg("vfs_test: OK");
}
  1. Mérd meg a VFS-műveletek idejét a következő mikrobenchmarkkal:
uint64_t start = rdtsc();
for (int i = 0; i < 1000; i++) {
    int fd = open("/mnt/file", O_RDWR);
    read(fd, tmp, 64);
    write(fd, tmp, 64);
    close(fd);
}
uint64_t end = rdtsc();

A cikluson belül ugyanazt a 4 KiB-os fájlt nyitjuk meg. A mérési pontok: open, read+write, close, valamint a teljes ciklus. A TSC-t rdtsc-vel olvassuk, és CPU órajelre normalizáljuk.

Kiinduló elvárás és a mért érték elkülönítése. A naplóban a következő táblázatot kell kitölteni:

| művelet        | várt trend          | mért átlag | szórás | min | max |
|----------------+---------------------+------------+--------+-----+-----|
| open           | dentry cache O(1)   | ? µs       | ?      | ?   | ?   |
| read+write 64B | O(64) memcpy        | ? µs       | ?      | ?   | ?   |
| close          | O(1)                | ? µs       | ?      | ?   | ?   |

Egyetlen mérési szám nem elegendő; rögzíteni kell a ciklusszámot, a cache-találati arányt a dentry cache-ben, és a laphibák számát (ha a kernel már támogatja a lapozást).

Elvárt működés. A vfs_test sikeres futtatása után a mount-névtér konzisztens: a /mnt/test.txt a memfs rootjában jön létre. A dentry cache találati aránya a második open-től kezdve nő, az open átlagos ideje csökken. A read/write idő a másolandó 64 bájttal közel lineáris, az offset mind a 1000 iterációban helyes marad.

Reprodukciós napló. A naplóba a következő parancsok kimenete tartozik:

make -C vfs-lab clean
make -C vfs-lab build
./qemu-run.sh | tee logs/boot.log

A boot.log végén a vfs_test: OK sor, a mérési táblázat és a verziók szerepelnek. A labot eldobható QEMU környezetben vagy külön vendégképen futtasd; a hoszt rendszerpartícióját és bootloaderét tilos módosítani.

29.3.10 10. Önellenőrző kérdések

  1. Mi a különbség a dentry, az inode és a struct file szerepe között? Melyik tárolja az offsetet és miért?
  2. Mit kell tennie a path_resolve-nak, amikor egy aktív mount point-ot ér el?
  3. Hogyan osztozik az offset két fájlleíró között dup után? Melyik kernelbeli adatszerkezet referencia-számlálóját kell növelni?
  4. Milyen hibát okoz, ha a read művelet közvetlenül az inode-ba menti a pozíciót, és miért nem elég az inode zára?
  5. Miért kell a dentry d_count referencia-számlálóját a d_lookup után növelni? Milyen hibakódot adunk, ha egy útvonalkomponens nem könyvtár?
