25.2 Android architektúra és HAL

Az Android egy rétegzett, Linux kernelre épülő platform, amelyben a hardvergyártók és a rendszerfejlesztők közötti szerződést a hardverabsztrakciós réteg (HAL) definiálja. Az alábbiakban áttekintjük az Android architekturális rétegeit, különös tekintettel a HAL-ra, a Binder IPC-re és az engedélyezési modellre. A fejezet nem ismétli meg a korábbi Linux kernel és beágyazott Linux alapokat (Beágyazott Linux és firmware), hanem az Android-specifikus kiegészítésekre és absztrakciókra összpontosít.

25.2.1 1. Az Android rétegei és a hardverabsztrakció helye

Az Android platform hagyományosan a következő fő rétegekre bontható (alulról felfelé):

  1. Linux kernel – a legalacsonyabb szintű erőforrás-kezelő, amelyet az Android specifikus igényeihez igazítottak (binder driver, low memory killer, wake locks, stb.). Ez a réteg biztosítja a processzorkezelést, a memóriakezelést, az eszközmeghajtókat és a processz-izolációt.
  2. Hardverabsztrakciós réteg (HAL) – egy interfészréteg, amely a hardvereszközök és a magasabb szintű keretrendszer közötti szerződést definiálja. A HAL célja, hogy a felső rétegek a hardver konkrét megvalósításától függetlenül, egységes interfészen keresztül férjenek hozzá az eszközökhöz (kamera, szenzorok, grafikus komponens, audio, GPS, stb.).
  3. Natív réteg – C és C++ könyvtárak, amelyek a rendszer szolgáltatásait és a HAL feletti funkcionalitást biztosítják. Ide tartoznak például a libc (bionic), a log rendszer, a media framework, a SQLite, az OpenGL ES, a WebKit stb. Ez a réteg közvetlenül kapcsolódik a HAL-hoz.
  4. Android Runtime (ART) – a futtatókörnyezet, amely a Dalvik bytecode-ot futtatja. Az ART JIT (Just-In-Time) és AOT (Ahead-Of-Time) fordítást is használ, valamint automatikus szemétgyűjtést (garbage collection). A Zygote folyamat előre betöltött osztályokkal és erőforrásokkal indul, és ebből ágaznak le az alkalmazásfolyamatok.
  5. App Framework (keretrendszer) – a Java/Kotlin nyelven elérhető magas szintű API-k gyűjteménye, például az Activity Manager, a Package Manager, a Window Manager, a Content Providers, a Location Manager, a Notification Manager, stb. Ezek a rendszerszolgáltatások a Binder IPC-n keresztül kommunikálnak egymással és a natív réteggel.
  6. Alkalmazások – a felhasználó által telepített és a rendszeralkalmazások (Launcher, telefon, kontaktok, stb.). Minden alkalmazás saját folyamatban fut, saját UID-del és homokozóval (sandbox).

A hardverabsztrakció tehát a Linux kernel és a natív réteg között helyezkedik el, de formailag a HAL modulok a kernel felett, user space-ben futnak. A HAL interfészek a hardvergyártóktól független definíciók, amelyeket a Google és a platform fejlesztői határoznak meg, az implementációt pedig a gyártók biztosítják. Így a felsőbb rétegek nem ismerik a konkrét hardverregisztereket vagy a gyártói illesztőprogramok részleteit.

25.2.2 2. A HAL célja és két generációja

A HAL réteg történetileg két jelentős szakaszon ment keresztül:

  • Legacy HAL (libhardware) – a korai Android verziókban a HAL modulok dinamikus könyvtárak voltak (*.so), amelyeket a rendszer a hw_get_module() függvénnyel töltött be. Minden modul egy hw_module_t struktúrát és egy hw_device_t struktúrát implementált. Az interfészek C nyelvű függvénypointerekkel voltak definiálva. Ez a megközelítés nem biztosított szigorú verziózást, és a folyamatok közvetlenül hívták a HAL-t.

  • Modern HAL (HIDL / AIDL) – az Android 8.0 (Oreo) óta a HAL interfészeket formális nyelvvel (HIDL, később AIDL) írják le. A HIDL (HAL Interface Definition Language) interfészeket definiál a HAL szolgáltatások és klienseik között. Az interfészek verzióval rendelkeznek, és a szolgáltatások a hwservicemanager daemonnál regisztrálódnak. A HIDL interfészek kétféleképpen használhatók:

    • Passthrough – a HAL implementáció közvetlenül a kliens folyamatába töltődik be, hasonlóan a legacy modulokhoz.
    • Binderized – a HAL szolgáltatás külön folyamatban fut, és a kliensek Binder IPC-n keresztül hívják. Ez a preferált mód, mert erős folyamat-izolációt és jogosultság-ellenőrzést tesz lehetővé.

Az Android 11-től kezdve a HIDL-t fokozatosan felváltja az AIDL (Android Interface Definition Language), amely egyesíti a HAL interfészeket az alkalmazás- és keretrendszer interfészekkel. Az AIDL alapú HAL-ok ugyanúgy a hwservicemanager-nél regisztrálódnak, de az interfész definíciók egységesebbek. A gyakorlatban ma már a legtöbb új HAL interfész AIDL-ben készül, míg a régebbi HAL-ok továbbra is HIDL formátumban élnek.

25.2.3 Példa egy HAL interfészre

Vegyünk egy egyszerű szenzor HAL interfészt HIDL-ben (pszeudokód):

package android.hardware.sensor@2.0;

interface ISensor {
    getSensorsList() generates (vec<SensorInfo> sensors);
    activate(int32_t sensorHandle, bool enabled) generates (Result result);
    poll(int32_t maxCount) generates (vec<Event> events);
};

Ugyanez az interfész AIDL-ben (pszeudokód):

package android.hardware.sensor;

interface ISensor {
    List<SensorInfo> getSensorsList();
    int activate(int sensorHandle, boolean enabled);
    List<Event> poll(int maxCount);
};

A gyakorlati implementáció során a gyártó létrehoz egy C++ osztályt, amely megvalósítja ezt az interfészt, majd regisztrálja azt a hwservicemanager-nél:

#include <android/hardware/sensor/2.0/ISensor.h>

using android::hardware::sensor::V2_0::ISensor;
using android::hardware::sensor::V2_0::implementation::Sensor;

int main() {
    // A Sensor osztály implementálja az ISensor interfészt.
    auto sensor = new Sensor();
    // Regisztrálás a HAL szolgáltatáskezelőnél.
    android::hardware::configureRpcThreadpool(4, true);
    android::status_t status = sensor->registerAsService();
    if (status != android::OK) {
        // Hibakezelés és naplózás.
        return 1;
    }
    android::hardware::joinRpcThreadpool();
    return 0;
}

A kliens oldalról a HAL szolgáltatást a getService() hívásával érik el, majd Binder proxy-n keresztül hívják a metódusokat. A fenti kód szemléltetés, nem közvetlenül futtatható éles környezetben.

25.2.4 3. Linux kernel Android-specifikus kiegészítései

Az Android kernel nem egy teljesen különálló kernel, hanem a mainline Linux kernelre épül, kiegészítve olyan alrendszerekkel, amelyeket az Android folyamatmodell és energiamenedzsment megkövetel. A legfontosabb Android-specifikus komponensek:

  • Binder driver – a kernelben megvalósított IPC mechanizmus, amely a rendszer folyamatai közötti hívásokat kezeli. A Binder az Android alapvető kommunikációs csatornája, és a HAL szolgáltatások eléréséhez is nélkülözhetetlen. A driver a /dev/binder eszközön keresztül érhető el, és támogatja a proxy/stub mintát, a hívások szinkronizációját és a jogosultság-ellenőrzést.

  • ashmem – anonim osztott memória, amely lehetővé teszi a folyamatok közötti memóriamegosztást, és a Binder tranzakciókban használt nagyméretű adatok átadását. Az ashmem a Linux tmpfs-hez hasonló, de nem igényel fájlleírót a megosztáshoz, és jobban illeszkedik a Binderhez.

  • ion / dmabuf – pufferek kezelése hardveres eszközök (GPU, kamera, kijelző) számára. Az ion a fizikailag folytonos memória lefoglalását és az eszközök közötti megosztását teszi lehetővé. Az újabb Android verziókban az ion-t fokozatosan felváltja a mainline dmabuf és a dma-heap mechanizmus.

  • Low Memory Killer (LMK) – a kernelben futó démon, amely a memórianyomás függvényében leállítja a legkevésbé fontos folyamatokat. Az LMK együttműködik a felhasználói térben futó lmkd daemonnal, és az Android folyamat prioritási osztályait (oom_score_adj) használja. Az újabb rendszerekben a LMK-t a psi (pressure stall information) alapú LMKD váltja fel.

  • Wake locks / wakeup sources – az energiamenedzsment része, amely megakadályozza, hogy a rendszer alvó állapotba kerüljön, amíg egy kritikus művelet (például média lejátszás, hálózati átvitel, szenzor olvasás) folyamatban van. A kernel wakeup_source struktúrákat használ, a felhasználói térben pedig az PowerManager API biztosít hozzáférést.

  • SELinux és egyéb biztonsági kiterjesztések – az Android szigorú SELinux policy-t alkalmaz, amelyben minden folyamat és erőforrás címkézett, és a hozzáféréseket a policy engedélyezi. Ezt a részletes jogosultsági modellt a 8. szakaszban tárgyaljuk.

Ezek a kiegészítések azt a célt szolgálják, hogy a Linux kernel által nyújtott általános erőforrás-kezelést az Android erősen izolált folyamatmodelljéhez, a hardveres eszközökhöz való biztonságos hozzáféréshez és az energiatakarékossághoz igazítsák.

25.2.5 4. ART és az app framework

Az Android futtatókörnyezet (ART) felelős a Dalvik Executable (DEX) formátumú bytecode futtatásáért. A DEX fájlok a Java/Kotlin forráskódból készülnek, és az ART betölti, ellenőrzi, optimalizálja és futtatja őket. Az ART a következő fő jellemzőkkel bír:

  • JIT és AOT fordítás – az ART kezdetben teljes AOT fordítást használt, ami hosszabb telepítési időt és nagyobb tárhelyet igényelt. Az újabb verziók hibrid megközelítést alkalmaznak: a telepítéskor csak a kritikus részeket fordítják AOT, majd futás közben a JIT fordító dinamikusan optimalizálja a gyakran futó kódrészeket. A profilvezérelt fordítás (profile-guided compilation) a valós használat alapján dönti el, mely metódusokat érdemes natív kódra fordítani.

  • Garbage collection – az ART több generációs, párhuzamos és részben konkurens szemétgyűjtőt használ, amely csökkenti a futás közbeni megállásokat. A memóriakezelés szorosan kapcsolódik a kernel memóriakezelőjéhez és a Zygote folyamat modelljéhez.

  • Zygote – egy speciális folyamat, amely a rendszerindítás során előre betölti a gyakori osztálykönyvtárakat és erőforrásokat. Amikor egy új alkalmazás indul, a Zygote fork() hívással létrehozza a gyermekfolyamatot, amely így megörökli a már betöltött osztályokat. Ez jelentősen csökkenti az alkalmazásindítási időt és a memóriafelhasználást (copy-on-write révén).

  • System Server – a rendszer központi folyamata, amely a keretrendszer szolgáltatásait futtatja. A System Server számos Java szolgáltatást tartalmaz, mint például az ActivityManagerService, a PackageManagerService, a WindowManagerService, a PowerManagerService, stb. Ezek a szolgáltatások a Binder IPC-n keresztül érhetők el az alkalmazások számára.

Az app framework (keretrendszer) az a Java API réteg, amelyet az alkalmazásfejlesztők használnak. Az Activity, Service, BroadcastReceiver, ContentProvider komponensek mind a framework részét képezik. A framework szolgáltatások a System Serverben futnak, és a Binder segítségével kommunikálnak az alkalmazásokkal.

25.2.6 5. Binder IPC

A Binder az Android elsődleges folyamatok közötti kommunikációs mechanizmusa. A Binder a következő jellemzőkkel rendelkezik:

  • Kernel driver – a Binder a Linux kernelben implementált driverrel rendelkezik (/dev/binder). A driver a tranzakciók átvitelét, a hívó azonosítását, a hivatkozások kezelését és a puffer memóriát végzi.

  • Proxy/stub minta – a Binder interfészeket egy felületleíró nyelvvel (AIDL) definiálják, amelyből a build rendszer Proxy és Stub osztályokat generál. A kliens oldalon a Proxy osztály a szerver oldali Stub osztályhoz intézett hívásokat csomagolja tranzakciókba, és a Binder driveren keresztül továbbítja. A szerver oldalon a Stub osztály kicsomagolja a paramétereket, és meghívja a tényleges implementációt. A válasz visszafelé ugyanezen az úton halad.

  • Tranzakciók és szinkronizáció – a Binder tranzakciók lehetnek szinkron (a hívó blokkolódik a válaszig) vagy aszinkron (a hívó nem vár választ). A szinkron hívások esetén a Binder gondoskodik a hívó és a szerver közötti adatátvitelről, és a hívás során a hívó folyamat nem foglalja el a szerver szálait. A Binder driver a tranzakciókat puffereli, és a szerver folyamat egy szálkészletből szolgálja ki azokat.

  • Jogosultság-ellenőrzés – a Binder hívásoknál a kernel driver rögzíti a hívó UID-jét és PID-jét, így a szerver oldalon a IPCThreadState::getCallingUid() hívásával ellenőrizhető a hívó azonosítója. Ez az alapja az Android permission modelljének.

25.2.7 Példa egy Binder interfészre

Az alábbi pszeudokód egy egyszerű AIDL interfészt mutat be, amely egy computeSum metódust definiál:

package com.example.compute;

interface ICalculator {
    int computeSum(int a, int b);
}

A generált Proxy és Stub osztályok lehetővé teszik, hogy a kliens oldalon a következőképpen hívjuk a metódust:

ICalculator calculator = ICalculator.Stub.asInterface(service);
int result = calculator.computeSum(3, 4);

A Binder driver kezeli a paraméterek sorosítását (parceling), a hívás átvitelét a szerver folyamatba, a metódus végrehajtását, majd az eredmény visszaküldését.

A Binder fontos tulajdonsága, hogy a tranzakciók mérete korlátozott (alapértelmezés szerint 1 MiB, de konfigurálható). A nagy adatok átadására az ashmem vagy a dmabuf használható, ami a memóriát osztottá teszi a folyamatok között.

25.2.8 6. Engedélyezési modell és sandbox

Az Android biztonsági modellje több rétegből áll:

  • UID-alapú izoláció – minden alkalmazás saját Linux UID-del és GID-del rendelkezik. Az alkalmazások nem férhetnek hozzá más alkalmazások fájljaihoz vagy processzeihez, kivéve, ha a SELinux policy vagy a megosztott UID ezt kifejezetten lehetővé teszi.

  • Permissions (engedélyek) – az alkalmazásoknak deklarálniuk kell az általuk igényelt jogosultságokat a AndroidManifest.xml fájlban. Az engedélyek két csoportra oszthatók:

    • Normal permissions – alacsony kockázatú engedélyek (pl. internet-hozzáférés), amelyeket a rendszer automatikusan megad a telepítés során.
    • Dangerous permissions – magasabb kockázatú engedélyek (pl. kamera, mikrofon, helyadatok, kapcsolatok), amelyeket a felhasználónak futás közben explicit módon jóvá kell hagynia (runtime permission). A rendszer az engedélyeket az alkalmazás UID-jéhez kapcsolja, és a Binder hívások során a szerver oldalon ellenőrzi azokat.

  • SELinux – a rendszer minden folyamata és erőforrása SELinux címkével rendelkezik, és a policy szabályozza a hozzáféréseket. A SELinux erősíti a UID-alapú izolációt, mert akkor is megtagadja a hozzáférést, ha az UID-ek megegyeznek, de a policy nem engedélyezi. A HAL szolgáltatások és a rendszerfolyamatok is SELinux domainekkel vannak ellátva.

  • seccomp – az Android a Linux seccomp szűrőket használ az alkalmazások és szolgáltatások rendszerhívásainak korlátozására. Ez csökkenti a kernel támadási felületét, mert a nem szükséges rendszerhívások blokkolva vannak.

  • App sandbox – az alkalmazások homokozóban futnak, ami azt jelenti, hogy csak a saját fájljaikhoz és a számukra engedélyezett erőforrásokhoz férnek hozzá. A homokozó a fenti mechanizmusok kombinációján alapul.

A HAL szolgáltatásokhoz való hozzáférést is a SELinux policy és a Binder jogosultság-ellenőrzés szabályozza. Például egy kamera HAL szolgáltatás csak olyan klienseket szolgálhat ki, amelyek rendelkeznek a megfelelő SELinux címkével és a kamera engedéllyel.

25.2.9 7. Gyakorlati példa: egy egyszerű HAL interfész vázlata

Az alábbiakban bemutatunk egy minimális HAL interfész definíciót AIDL-ben (pszeudokód), amely egy beágyazott szenzor (például hőmérséklet-érzékelő) absztrakcióját valósítja meg.

AIDL interfész definíció (fájl: IAmbientTemperature.aidl):

package android.hardware.ambienttemperature;

interface IAmbientTemperature {
    // Visszaadja a jelenlegi hőmérsékletet Celsius fokban.
    float getTemperature();
    // Regisztrál egy callback-et a hőmérséklet-változásokra.
    void registerCallback(ITemperatureCallback callback);
    // Törli a callback regisztrációt.
    void unregisterCallback(ITemperatureCallback callback);
}

interface ITemperatureCallback {
    void onTemperatureChanged(float newTemperature);
}

HAL szolgáltatás implementáció vázlat (C++ pszeudokód):

#include <android/hardware/ambienttemperature/IAmbientTemperature.h>
#include <android/hardware/ambienttemperature/ITemperatureCallback.h>
#include <android/binder_interface_utils.h>
#include <android/binder_manager.h>
#include <android/binder_process.h>
#include <cmath>
#include <mutex>
#include <vector>

using android::hardware::ambienttemperature::IAmbientTemperature;
using android::hardware::ambienttemperature::ITemperatureCallback;

class AmbientTemperature : public IAmbientTemperature {
public:
    AmbientTemperature() {}
    ~AmbientTemperature() {}

    float getTemperature() override {
        // Itt történne a tényleges hardver olvasás.
        // Példa: I2C buszról olvasott érték.
        return 23.5f; // helyőrző
    }

    void registerCallback(const std::shared_ptr<ITemperatureCallback>& callback) override {
        std::lock_guard<std::mutex> lock(mCallbacksMutex);
        mCallbacks.push_back(callback);
    }

    void unregisterCallback(const std::shared_ptr<ITemperatureCallback>& callback) override {
        std::lock_guard<std::mutex> lock(mCallbacksMutex);
        // Eltávolítás a listából.
    }

private:
    std::mutex mCallbacksMutex;
    std::vector<std::shared_ptr<ITemperatureCallback>> mCallbacks;
};

int main() {
    // Binder thread pool inicializálása.
    ABinderProcess_startThreadPool();
    // Szolgáltatás regisztrálása a hwservicemanager-nél.
    auto service = ndk::SharedRefBase::make<AmbientTemperature>();
    const std::string serviceName = "default";
    binder_status_t status = AServiceManager_addService(
        service->asBinder().get(), 
        "android.hardware.ambienttemperature.IAmbientTemperature/default");
    if (status != STATUS_OK) {
        // Hibanaplózás.
        return 1;
    }
    ABinderProcess_joinThreadPool();
    return 0;
}

A fenti kód szemlélteti a HAL szolgáltatás regisztrációját és egy interfész implementációját. A gyakorlatban a HAL szolgáltatások gyakran a hwservicemanager által kezelt default névvel regisztrálódnak, és a kliensek a AServiceManager_getService hívással érik el őket. A callback mechanizmus a Binder aszinkron hívásokra épül.

Kliens oldali használat (pszeudokód):

#include <android/hardware/ambienttemperature/IAmbientTemperature.h>
#include <android/binder_manager.h>

using android::hardware::ambienttemperature::IAmbientTemperature;

int main() {
    auto service = IAmbientTemperature::fromBinder(
        ndk::SpAIBinder(AServiceManager_getService(
            "android.hardware.ambienttemperature.IAmbientTemperature/default")));
    if (service == nullptr) {
        // A szolgáltatás nem elérhető.
        return 1;
    }
    float temp = service->getTemperature();
    // Felhasználás...
    return 0;
}

Ez a minta jól mutatja a HAL absztrakció lényegét: a kliens nem ismeri a hardver részleteit, csak az interfészt.

25.2.10 8. Tipikus hibák és helyes megoldások

Az Android architektúra és HAL fejlesztése során gyakori hibák:

  1. HAL interfész verzió eltérés – ha a HAL szolgáltatás egy másik verziójú interfészt implementál, mint amit a kliens vár, a Binder hívás sikertelen lesz vagy undefined behavior-t okoz. Helyes megoldás: mindig ellenőrizni kell a szolgáltatás verzióját a getService hívás után, és gondoskodni a kompatibilitásról. A HIDL/AIDL interfészek verziói szigorúan kezelendők.

  2. Binder tranzakció méret túllépés – ha egy tranzakció paraméterei meghaladják a Binder puffer méretét (általában 1 MiB), a hívás FAILED_TRANSACTION hibával megszakad. Helyes megoldás: nagy adatok átadására osztott memóriát (ashmem, dmabuf) vagy fájlleírót használni, nem pedig a Binder tranzakciót.

  3. Hiányzó vagy hibás SELinux policy – ha a HAL szolgáltatás nem rendelkezik a szükséges SELinux engedélyekkel, a hozzáférés megtagadásra kerül, és a hibanapló AVC denied üzeneteket tartalmaz. Helyes megoldás: a SELinux policy-t a gyártónak kell frissítenie, és a fejlesztés során a dmesg és logcat naplókat kell figyelni.

  4. Szolgáltatás nem indul el időben – a HAL szolgáltatásoknak a rendszerindítás során megfelelő sorrendben kell elindulniuk. Ha egy kliens túl korán próbálja elérni a szolgáltatást, a getService null értéket ad vissza. Helyes megoldás: a HAL szolgáltatást a megfelelő init script indítja, és a kliensek retry logikát vagy callback regisztrációt használnak.

  5. Deadlock a Binder hívásokban – ha egy HAL szolgáltatás egy másik Binder szolgáltatást hív, miközben az őt hívó folyamat is ugyanarra vár, deadlock alakulhat ki. Helyes megoldás: a hívási láncokat aszinkronná tenni, vagy a Binder thread pool méretét megfelelően beállítani.

  6. Engedély nélküli hozzáférés – a HAL szolgáltatásoknak ellenőrizniük kell a hívó UID-jét és a SELinux címkéjét, mielőtt érzékeny műveletet hajtanának végre. Helyes megoldás: a HAL implementációban a IPCThreadState::getCallingUid() használata, és a SELinux policy megfelelő konfigurálása.

25.2.11 9. Labor: Android-architektúra és HAL-interfész vázlat

Az alábbi labor egy emulált Android környezetben mutatja be a HAL szolgáltatások listázását és egy egyszerű HAL interfész vázlatának elkészítését. A labor célja, hogy a hallgató gyakorlatban is megfigyelje az Android rétegeit és a HAL működését.

25.2.12 Kiinduló állapot

  • Telepített Android SDK platform-tools és egy működő Android emulátor (például Android Studio Emulator vagy Cuttlefish). A laborhoz használt konfiguráció:
    • Emulátor: Android Virtual Device (AVD) név: os_hal_test
    • Rendszerkép: system-images;android-33;google_apis;x86_64
    • Architektúra: x86_64
    • RAM: 2 GiB
    • CPU: 2 mag
  • A adb parancs elérhető a PATH-ban.

25.2.13 Lépések

  1. Indítsd el az emulátort az alábbi paranccsal (terminálban):

    emulator -avd os_hal_test -no-window -no-audio -no-boot-anim &

    Várj a rendszer teljes indulásáig:

    adb wait-for-device
adb shell getprop sys.boot_completed

    A kimenetnek 1-et kell mutatnia.

  2. Listázd a futó HAL szolgáltatásokat:

    adb shell lshal --list

    A kimenetben megjelennek a regisztrált HAL interfészek, például:

    android.hardware.graphics.composer@2.1::IComposer
android.hardware.sensors@2.1::ISensors
android.hardware.audio@6.0::IDevicesFactory
...

  3. Válassz egy HAL interfészt (például android.hardware.sensors@2.1::ISensors), és kérd le a részletes információkat:

    adb shell lshal --debug | grep -A 5 "android.hardware.sensors"

    Vagy használd a dumpsys parancsot:

    adb shell dumpsys sensorservice

  4. Készíts egy egyszerű HAL interfész vázlatot (pszeudokódban vagy AIDL-ben) egy tetszőleges eszközhöz, például egy hőmérséklet-érzékelőhöz. A vázlat tartalmazza:

    • Az interfész nevét és csomagját.
    • Egy metódust az aktuális érték lekérdezésére.
    • Egy callback regisztrációs metódust.
    • Rövid leírást a szolgáltatás regisztrációjáról.

  5. Dokumentáld a folyamatot egy reprodukálható jegyzetfüzetben (például Markdown vagy Jupyter notebook). Rögzítsd az alábbi mérési naplót:

Mérési pont Parancs / művelet Mért eredmény Várt eredmény Eltérés
Rendszerindítás getprop sys.boot_completed 1 1 nincs
HAL lista lshal --list a kimenetben szerepel legalább 5 HAL interfész legalább 5 HAL interfész nincs
Szenzor HAL lshal --debug \| grep sensors a kimenet tartalmazza a android.hardware.sensors bejegyzést a bejegyzés jelen van nincs

25.2.14 Visszaállítás

A labor után állítsd le az emulátort:

adb emu kill

Töröld az AVD-t, ha szükséges:

avdmanager delete avd -n os_hal_test

A mért és várt eredményeket a fenti táblázatban külön tüntettük fel. A labor során keletkezett naplófájlokat mentsd el a reprodukciós csomag részeként.

25.2.16 11. Összefoglalás

Az Android architektúra rétegzett felépítése lehetővé teszi, hogy a hardvergyártók és a rendszerfejlesztők egymástól függetlenül dolgozzanak. A HAL interfészréteg kulcsszerepet játszik a hardver absztrakciójában, a Binder IPC pedig a folyamatok és szolgáltatások közötti biztonságos kommunikációt biztosítja. Az engedélyezési modell és a SELinux tovább erősíti az izolációt, így az Android platform alkalmas a modern mobil és beágyazott eszközök igényeinek kiszolgálására. A következő fejezet (iOS, biztonsági modell és sandbox) az iOS biztonsági modelljére és sandbox mechanizmusaira épít az itt bevezetett fogalmakra.
