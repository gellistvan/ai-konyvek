7.2 Shared memory és élettartam

A shared memory a CUDA memóriahierarchia egyik legnagyobb teljesítményt befolyásoló eleme. Míg a global memória a grid összes threadje számára elérhető, de nagy késleltetésű, a shared memory egyetlen blokk threadjei között osztozik, és a regiszterekhez hasonló nagyságrendű, néhány órajelciklusos hozzáférést biztosít. A gyakorlatban a shared memory a blokk szintű együttműködés alapja: a thread-ek ide gyűjtik be a global memóriából az adott számítási lépéshez szükséges adatokat, itt cserélnek részeredményeket, és innen olvassák vissza azokat a szomszédos thread-ek által előállított értékeket, amelyekre a következő lépésben szükség van. Ebben az alfejezetben a __shared__ deklaráció formáit, a dinamikus allokációt, a szinkronizáció szerepét és a shared memory bankokból fakadó bank conflict jelenséget tárgyaljuk, majd egy mátrixszorzó tiling kernelen keresztül mutatjuk be a gyakorlati használatot.

7.2.1 __shared__ és a shared memory élettartama

A shared memory-t a kernelben a __shared__ kulcsszóval deklaráljuk. A legegyszerűbb forma a statikus méretű tömb:

// CUDA C++ (C++17), nvcc 12.4 (ellenőrizendő)
__shared__ float tile[32][32];

Ez a deklaráció minden blokk számára létrehoz egy 32×32 elemű lebegőpontos tömböt. A memóriaterület a blokk indulásakor jön létre, és a blokk befejeződéséig létezik; a blokk threadjei közösen használják, de a blokkok között nincs megosztás. A shared memory fizikailag az SM-en belüli gyors memória, általában 64–256 KiB közötti méretű, a GPU generációjától és a konfigurációtól függően (például A100 esetén 164 KiB, de ez ellenőrizendő). A blokk maximális shared memory igényét a kernel fordításakor és a launch konfigurációban is meg kell adni, illetve a hardver korlátozza.

A statikus deklaráció mellett létezik dinamikus shared memory is. Ezt a kernelben extern __shared__ előtaggal jelezzük, a tényleges méretet pedig a kernel indításakor a launch konfiguráció harmadik paraméterében adjuk meg bájtokban:

// CUDA C++ (C++17), nvcc 12.4 (ellenőrizendő)
extern __shared__ float s[]; // méretét a launch adja meg

__global__ void kernelDinamikus(float* out, int n) {
    int tid = threadIdx.x;
    if (tid < n) {
        s[tid] = tid * 0.5f;
        __syncthreads();
        out[tid] = s[tid] * 2.0f;
    }
}

A kernel indítása:

// CUDA C++ (C++17), nvcc 12.4 (ellenőrizendő)
size_t sharedBytes = n * sizeof(float);
kernelDinamikus<<<gridDim, blockDim, sharedBytes, 0>>>(d_out, n);

Itt a sharedBytes értékét a n elemű float tömbhöz igazítjuk. Ha több dinamikus shared tömböt szeretnénk, akkor egyetlen extern __shared__ tömböt kell deklarálni, és azon belül kell pointer-aritmetikával elhelyezni a résztömböket. Például:

// CUDA C++ (C++17), nvcc 12.4 (ellenőrizendő)
extern __shared__ float s[];
float* a = s;                 // első rész
float* b = &s[n];             // második rész

A dinamikus allokáció előnye, hogy a kernel fordításakor nem kell ismerni a pontos méretet, így ugyanaz a bináris többféle blokkmérettel is futtatható, feltéve, hogy a shared memória igénye a hardveres korláton belül marad. A dinamikus shared memória méretét a cudaFuncSetAttribute függvénnyel is megadhatjuk, ha a kernel pointerét és a cudaFuncAttributeMaxDynamicSharedMemorySize attribútumot használjuk, de a launch paraméteres megoldás egyszerűbb és elterjedtebb.

A shared memory láthatósága kizárólag a blokk threadjeire terjed ki. A blokkon belül minden thread ugyanazt a memóriaterületet éri el, de az írások és olvasások sorrendjét szinkronizálni kell. A shared memory nem őrzi meg az értékeket a blokk befejezése után; a következő blokk ugyanarra a fizikai területre írhat, ezért a blokkok közötti kommunikációra nem használható.

7.2.2 Szinkronizáció: __syncthreads() és a veszélyes feltételes használat

A shared memory akkor hasznos, ha a thread-ek adatot cserélnek: az egyik thread ír, egy másik olvas. Mivel a thread-ek ütemezése nem garantált sorrendű, a szinkronizáció elengedhetetlen. A __syncthreads() barriere a blokk összes threadjét bevárja: minden thread csak akkor lép tovább, ha minden thread elérte ugyanezt a hívást. Ez biztosítja, hogy a barrier előtti írások minden thread számára láthatóvá válnak a barrier után.

A tiling kernel tipikus sémája:

// CUDA C++ (C++17), nvcc 12.4 (ellenőrizendő)
__shared__ float As[TILE][TILE + 1];
__shared__ float Bs[TILE][TILE + 1];

int tx = threadIdx.x, ty = threadIdx.y;
// global indexek
int row = blockIdx.y * TILE + ty;
int col = blockIdx.x * TILE + tx;

float sum = 0.0f;

for (int t = 0; t < (N + TILE - 1) / TILE; ++t) {
    // betöltés a global memóriából a shared tömbökbe
    As[ty][tx] = (row < N && t * TILE + tx < N) ? A[row * N + t * TILE + tx] : 0.0f;
    Bs[ty][tx] = (t * TILE + ty < N && col < N) ? B[(t * TILE + ty) * N + col] : 0.0f;

    __syncthreads(); // minden thread befejezte a betöltést

    // számítás a shared memóriából
    for (int k = 0; k < TILE; ++k) {
        sum += As[ty][k] * Bs[k][tx];
    }

    __syncthreads(); // a következő csempe betöltése előtt mindenki befejezte az olvasást
}

if (row < N && col < N) {
    C[row * N + col] = sum;
}

A két __syncthreads() nélkülözhetetlen. Az első biztosítja, hogy a teljes csempe betöltése megtörtént, mielőtt bármely thread elkezdené a szorzást. A második megakadályozza, hogy egy gyors thread a következő iterációban felülírja a shared memóriát, mielőtt a lassabb thread-ek befejezték volna az aktuális csempe olvasását. A barrier hiánya versenyhelyzetet okoz, ami hibás eredményhez vezet, és a hiba nemdeterminisztikusan jelentkezhet.

Gyakori hiba a __syncthreads() feltételes ágon belüli elhelyezése. A következő kód hibás:

// HIBÁS: a __syncthreads() csak egyes thread-ekre fut le
if (tx < 16) {
    // valamilyen részleges munka
    __syncthreads();
}

Mivel a barriernek a blokk összes threadjére ki kell terjednie, a feltétel miatt egyes thread-ek soha nem érik el a hívást, a többi pedig örökre várakozik – ez holtpontot okoz. A helyes minta az, hogy a __syncthreads() hívás a feltételen kívül, a vezérlési folyamattól függetlenül szerepeljen. Ha a feltételes munka után minden threadnek szinkronizálnia kell, a szinkronizációt a feltétel után kell elhelyezni, ügyelve arra, hogy minden thread elérje.

7.2.3 Bankok és bank conflict

A shared memory hardveres szervezése 32 bankra oszlik (a warp méretének megfelelően). Minden bank egy-egy 32 bites szót tárol, és a bankok ciklikusan oszlanak meg a memóriacímek között: a 0. cím a 0. bankba, az 1. cím az 1. bankba, …, a 31. cím a 31. bankba, a 32. cím újra a 0. bankba tartozik, és így tovább. Ha egy warp 32 threadje ugyanabban az órajelciklusban ugyanahhoz a bankhoz szeretne hozzáférni, de különböző címekre, akkor bank conflict lép fel, és a hozzáférést a hardver több lépésben sorosítja. Ez csökkenti a tényleges sávszélességet.

A legegyszerűbb esetben, ha a warp threadjei egyenletesen, stride = 1 módon érik el a memóriát (például s[threadIdx.x]), minden thread más bankba kerül, és nincs conflict. Ha stride = 2, akkor két thread osztozik ugyanazon a bankon, így 2-way conflict keletkezik. A legrosszabb eset a stride = 32, amikor mind a 32 thread ugyanabba a bankba ír vagy olvas, ami 32-way conflictet, azaz teljes sorosítást eredményez.

A bank conflict elkerülésére a leggyakoribb technika a padding, azaz a tömb dimenzióinak eggyel való megnövelése. A fenti mátrixszorzó példában As[ty][tx] indexelésnél a tx 0..31, a ty 0..31, így az As[ty][tx] címek a ty * (TILE + 1) + tx képletet követik. Ha a második dimenzió TILE + 1 (azaz 33), akkor a szomszédos sorok kezdőcímei 33-mal térnek el, ami nem osztható 32-vel, így az azonos tx indexű elemek különböző bankokba kerülnek. Ezáltal a betöltési és olvasási lépések során nincs bank conflict. Ha viszont a tömb mérete TILE (azaz 32) lenne, akkor a sorok kezdőcímei 32-vel térnének el, és minden sor ugyanabba a bankba esne, ami 32-way conflictet okozna.

A bank conflict mérésére a CUDA eszköztárban a cuda-memcheck --tool synccheck nem alkalmas, de a Nsight Compute profilozó a l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum és hasonló metrikákkal mutatja a shared memória bank conflictjeit. A fejezet laborjában ezt a mérést is elvégezzük, de a jelen leírásban csak a teljesítménykülönbséget vizsgáljuk.

7.2.4 Gyakorlati minta: shared memory tiling mátrixszorzással

A tiling célja, hogy a global memória ismételt olvasását csökkentsük azáltal, hogy az adatokat egyszer betöltjük a gyors shared memóriába, és onnan többször felhasználjuk. A mátrixszorzás klasszikus példa: a naiv kernel minden kimeneti elemhez a bemeneti mátrixok teljes sorát és oszlopát olvassa, ami nagy global memória forgalmat generál. A tilinges változat viszont egy TILE×TILE méretű csempét betölt a shared memóriába, és a csempén belüli szorzatösszegeket a shared memóriából számolja, így minden betöltött elemet TILE-szor használ fel.

A labor meghatározása szerint a feladat a shared memory tiling implementálása. Az alábbiakban bemutatjuk a naiv baseline kernelt, a tilinges kernelt, a launch paramétereket és a mérési környezetet. A kódok a CUDA C++ (C++17) nyelvet használják, és a hibakezelést a cudaGetLastError() és cudaDeviceSynchronize() hívásokkal végezzük.

Naiv kernel (baseline):

// CUDA C++ (C++17), nvcc 12.4 (ellenőrizendő)
__global__ void matmul_naive(const float* A, const float* B, float* C, int N) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    if (row < N && col < N) {
        float sum = 0.0f;
        for (int k = 0; k < N; ++k) {
            sum += A[row * N + k] * B[k * N + col];
        }
        C[row * N + col] = sum;
    }
}

Tilinges kernel:

// CUDA C++ (C++17), nvcc 12.4 (ellenőrizendő)
#define TILE 32

__global__ void matmul_tiled(const float* A, const float* B, float* C, int N) {
    __shared__ float As[TILE][TILE + 1]; // padding a bank conflict ellen
    __shared__ float Bs[TILE][TILE + 1];

    int tx = threadIdx.x;
    int ty = threadIdx.y;
    int row = blockIdx.y * TILE + ty;
    int col = blockIdx.x * TILE + tx;

    float sum = 0.0f;
    int numTiles = (N + TILE - 1) / TILE;

    for (int t = 0; t < numTiles; ++t) {
        // Betöltés a global memóriából, határellenőrzéssel
        int aRow = row;
        int aCol = t * TILE + tx;
        int bRow = t * TILE + ty;
        int bCol = col;

        if (aRow < N && aCol < N)
            As[ty][tx] = A[aRow * N + aCol];
        else
            As[ty][tx] = 0.0f;

        if (bRow < N && bCol < N)
            Bs[ty][tx] = B[bRow * N + bCol];
        else
            Bs[ty][tx] = 0.0f;

        __syncthreads();

        // Számítás a shared memóriából
        for (int k = 0; k < TILE; ++k) {
            sum += As[ty][k] * Bs[k][tx];
        }

        __syncthreads();
    }

    if (row < N && col < N) {
        C[row * N + col] = sum;
    }
}

A launch konfiguráció a következő:

// CUDA C++ (C++17), nvcc 12.4 (ellenőrizendő)
int N = 2048;
int TILE = 32;
dim3 block(TILE, TILE);              // 32 x 32 = 1024 thread
dim3 grid((N + TILE - 1) / TILE, (N + TILE - 1) / TILE); // 64 x 64 blokk
matmul_tiled<<<grid, block>>>(d_A, d_B, d_C, N);
// shared memória mérete statikus, így a harmadik paraméter 0

A kernelben a shared memória mérete 2 * TILE * (TILE + 1) * sizeof(float) = 2 * 32 * 33 * 4 = 8448 bájt, ami jóval a limit alatt van. A blokk mérete 1024 thread, ami maximális a legtöbb architektúrán, de a regiszterhasználat miatt az occupancyt ellenőrizni kell.

7.2.5 Labor: shared memory tiling implementálása és mérése

A labor célja a naiv és a tilinges mátrixszorzó kernel összehasonlítása, valamint a shared memory hatásának számszerűsítése. A mérési környezet az alábbi helyőrző paraméterekkel rendelkezik, mivel a labor izolált környezetben fut, és a megadott hardveradatok nem valós rendszerre vonatkoznak:

  • GPU: NVIDIA A100 (placeholder, izolált labor)
  • Driver: 550.54.15 (placeholder, ellenőrizendő)
  • CUDA verzió: 12.4 (ellenőrizendő)
  • Compute capability: 8.0
  • Operációs rendszer: Ubuntu 22.04 (placeholder)
  • Fordító: nvcc 12.4 (ellenőrizendő)
  • Optimalizálás: -O3 -arch=sm_80
  • Bemeneti méret: N = 2048, TILE = 32, float32 (FP32)
  • Mérési módszer: warm-up 5 iteráció, majd 10 mérés, átlag és szórás

Build parancs:

nvcc -O3 -arch=sm_80 -o matmul_shared matmul_shared.cu

Futtatási parancs:

./matmul_shared

A mérési napló (a számok helyőrzők, nem valós mérésből származnak; a labor szerződés szerinti formátumot illusztrálják):

kernel futásidő átlag (ms) szórás (ms) memória átbocsátás (GB/s)
matmul_naive 12.30 0.15 120
matmul_tiled 4.50 0.08 330

A várt eredmény az, hogy a tilinges kernel jelentősen gyorsabb a naivnál, mert a global memória tranzakciók száma körülbelül TILE-szorosára csökken. A naiv kernel minden kimeneti elemhez N darab global memória olvasást végez, ami N^3 = 2048^3 ≈ 8,59 milliárd float olvasást jelent a teljes mátrixra. A tilinges kernel ezzel szemben minden bemeneti elemet TILE-szor (32-szer) tölt be, ami a global memória forgalmat durván N^3 / TILE nagyságrendűre csökkenti, így a tilinges változat elméletileg akár 32-szer kisebb global memória forgalmat bonyolíthat. A gyakorlati gyorsulás ennél kisebb, mert a shared memória hozzáférések is időt vesznek igénybe, és a szinkronizáció is overheadet jelent. A mérési naplóban szereplő 2,7×-es gyorsulás (12,30 → 4,50 ms) reális lehet egy A100-as GPU-n, de a pontos érték erősen függ a memória órajeltől, az occupancytől és a bank conflict mértékétől. Fontos, hogy a fenti táblázat adatai nem ellenőrzöttek, ezért a labor tényleges futtatása során a saját környezetben kell mérni, és a naplót rögzíteni.

A mért eredmény a labor során keletkező tényleges adat. A fenti táblázatban szereplő számok nem valós mérésből származnak, hanem a helyőrző adatok a labor dokumentációjának formátumát mutatják. A valós méréshez a kernelt le kell fordítani, izolált laborban futtatni, és a cudaDeviceSynchronize() utáni futási időket rögzíteni. A mérés előtt a GPU-t fel kell melegíteni (warm-up), hogy az órajel és a memória állapota stabilizálódjon. A kapott átlag és szórás alapján lehet megítélni a teljesítményt.

A labor során érdemes a Nsight Compute profilozót is futtatni a shared memória bank conflictjeinek ellenőrzésére. A paddinggel ellátott kernelnél a bank conflict metrikának nullához közelinek kell lennie, míg a padding nélküli változatnál magas 32-way conflictet látunk. A labor átadandó eredménye tartalmazza a forráskódot, a build parancsot, a futtatási környezet rögzítését, a mérési naplót, valamint a várt és mért eredmények összehasonlítását.

7.2.6 Tipikus hibák és helyes megoldások

A shared memory használata során több gyakori hiba léphet fel. Az alábbiakban összefoglaljuk ezeket, és megadjuk a helyes megoldást.

  1. Hiányzó __syncthreads() a tiling ciklusban. Ha a betöltés után nincs szinkronizáció, egyes thread-ek még a régi shared memória tartalommal számolnak, mert a többi thread még nem fejezte be az írást. Ez hibás eredményhez vezet. A helyes minta: minden shared memória írás után, mielőtt bármely thread olvasná az adatot, __syncthreads() szükséges, és minden olvasás után, mielőtt a következő iterációban felülírnánk, szintén.

  2. Feltételes __syncthreads() használata. A korábban említett módon a barrier nem lehet feltételhez kötve, mert egyes thread-ek kihagyják, a többiek örökre várnak. A helyes megoldás az, hogy a szinkronizációt a feltételes blokkon kívülre helyezzük, és ügyelünk arra, hogy minden thread ténylegesen elérje.

  3. Túl nagy shared memória igény a launch konfigurációban. Ha a kernel statikus vagy dinamikus shared memória igénye meghaladja a hardveres limitet, a kernel indítása cudaErrorSharedMemoryTooSmall hibával tér vissza. A helyes megoldás a shared memória méretének csökkentése, például kisebb csempe (TILE) választásával, vagy a dinamikus shared memória méretének a rendelkezésre álló kapacitáshoz igazítása.

  4. Bank conflict figyelmen kívül hagyása. A shared memória tömbök méretének 32-vel oszthatónak választása (például [TILE][TILE], ahol TILE = 32) 32-way bank conflictet okoz, mert minden sor ugyanabba a bankba esik. A helyes megoldás a padding, azaz a második dimenzió TILE + 1-re állítása, így a sorok kezdőcímei eltolódnak, és a hozzáférések conflictmentessé válnak.

  5. A shared memória inicializálásának elmulasztása. A shared memória tartalma a blokk indulásakor definiálatlan. Ha a kernel a betöltés előtt olvassa, szemét értéket kap. A helyes megoldás az, hogy a használat előtt minden szükséges elemet explicit módon betöltünk, például a global memóriából, vagy nullázunk.

  6. A dinamikus shared memória pointerének hibás kezelése több tömb esetén. Ha több dinamikus tömböt szeretnénk, egyetlen extern __shared__ deklarációt kell használni, és azon belül pointer-aritmetikával kell elhelyezni a részeket. A pointereket a kernel elején, a __syncthreads() előtt kell beállítani. A helytelen pointer-számítás gyakori hiba.

Ezek a hibák mind a shared memory alapvető tulajdonságaiból fakadnak, és a fenti megoldásokkal elkerülhetők. A fejezet laborja során a paddinggel ellátott tiling kernel implementálása és a __syncthreads() helyes elhelyezése a fő ellenőrzési pont.
