12.4 Occupancy optimalizálás

Az occupancy nem önmagában vett cél, hanem egy erőforrás-korlátokból származtatott mérőszám, amely azt mutatja, hogy egy streaming multiprocesszoron (SM) hány aktív warp képes egyszerre jelen lenni. A Latency hiding alfejezet bemutatta, hogy a memória- és utasítás-késleltetések elrejtéséhez aktív warp-okra van szükség. Ebben az alfejezetben azt vizsgáljuk, hogyan alakítható ki az a foglaltság, amely egy adott kernel számára ténylegesen a legjobb átbocsátóképességet adja, és miért nem érdemes kizárólag az elméleti occupancy maximalizálására törekedni.

A fejezet először rögzíti az occupancy fogalmát és erőforrás-korlátait, majd elemzi az alacsony és magas occupancy teljesítményre gyakorolt hatását. Ezt követi egy gyakorlati hangolási munkafolyamat, végül egy ellenőrizhető labor, amelyben blockméret- és regiszterhangolást végzünk CUDA C++-ban, rögzített környezetben, a mért és a várt eredmények elkülönítésével.

12.4.1 1. Az occupancy mint erőforrás-korlát

A CUDA foglaltság (occupancy) gyakorlati definíciója:

Oelméleti=WaktívWmax, O_{\text{elméleti}} = \frac{W_{\text{aktív}}}{W_{\text{max}}},

ahol WaktívW_{\text{aktív}} az SM-en egyidejűleg rezidens warp-ok száma, WmaxW_{\text{max}} pedig az adott SM maximális warpszáma. A WmaxW_{\text{max}} értéke gyakran 48, 64 vagy 64 feletti lehet architektúrától függően; például egy NVIDIA Ada-generációs SM esetén jellemzően 48 warp. A valós foglaltságot nemcsak a hardver warp-slot korlátja, hanem további erőforrások is korlátozzák:

  • regiszterfájl mérete SM-enként;
  • shared memory mérete SM-enként;
  • blokk-slotok száma SM-enként;
  • warp-slotok száma SM-enként.

A regiszterfájl korlátjának hatása egyszerűen szemléltethető. Ha egy szál RszálR_{\text{szál}} regisztert használ, és egy blokk BB szálból áll, akkor a blokk regiszterigénye közelítőleg Rszál⋅BR_{\text{szál}} \cdot B. Ha az SM regiszterfájlja RSMR_{\text{SM}} darab 32 bites regisztert tartalmaz, akkor a regiszterek alapján elhelyezhető blokkok száma:

Breg=⌊RSMRszál⋅B⌋. B_{\text{reg}} = \left\lfloor \frac{R_{\text{SM}}}{R_{\text{szál}} \cdot B} \right\rfloor.

Az ebből adódó aktív warpszám:

Wreg=Breg⋅B32. W_{\text{reg}} = \frac{B_{\text{reg}} \cdot B}{32}.

A valós hardveren a regiszterallokáció granularitása miatt a képlet kerekítésekkel módosul, ezért az elméleti occupancy számításakor mindig érdemes a CUDA Occupancy Calculator vagy a cudaOccupancyMaxActiveBlocksPerMultiprocessor API értékét alapul venni. Az alábbi kódrészlet azt mutatja, hogyan kérdezhető le egy kernelre az adott blockmérethez tartozó maximális aktív blokkszám:

// occupancy_query.cu
#include <cuda_runtime.h>
#include <cstdio>

#define CUDA_CHECK(call)                                                      \
    do {                                                                      \
        cudaError_t err = (call);                                             \
        if (err != cudaSuccess) {                                             \
            std::fprintf(stderr, "CUDA error at %s:%d: %s\n", __FILE__,       \
                         __LINE__, cudaGetErrorString(err));                    \
            std::exit(EXIT_FAILURE);                                           \
        }                                                                     \
    } while (0)

template<int R, int BLOCK>
__global__ void __launch_bounds__(BLOCK)
sample_kernel(const float* __restrict__ x, float* __restrict__ y, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= n) return;
    float coeff[R];
    #pragma unroll
    for (int r = 0; r < R; ++r) coeff[r] = x[i] * (float)r;
    float acc = x[i];
    #pragma unroll
    for (int r = 0; r < R; ++r) acc = fmaf(acc, coeff[r], 1.0f);
    y[i] = acc;
}

int main() {
    constexpr int BLOCK = 256;
    int dev = 0;
    CUDA_CHECK(cudaGetDevice(&dev));
    cudaDeviceProp prop{};
    CUDA_CHECK(cudaGetDeviceProperties(&prop, dev));

    int numBlocks = 0;
    CUDA_CHECK(cudaOccupancyMaxActiveBlocksPerMultiprocessor(
        &numBlocks, sample_kernel<32, BLOCK>, BLOCK, 0));

    int activeWarps = numBlocks * BLOCK / prop.warpSize;
    int maxWarps = prop.maxThreadsPerMultiProcessor / prop.warpSize;
    float occupancy = 100.0f * (float)activeWarps / (float)maxWarps;

    std::printf("GPU: %s\n", prop.name);
    std::printf("compute capability: %d.%d\n", prop.major, prop.minor);
    std::printf("max threads/SM: %d\n", prop.maxThreadsPerMultiProcessor);
    std::printf("max warps/SM: %d\n", maxWarps);
    std::printf("active blocks/SM for this kernel: %d\n", numBlocks);
    std::printf("theoretical occupancy: %.1f%%\n", occupancy);
    return 0;
}

A fenti példa a sample_kernel<32, 256> sablonpéldányra kérdezi le az occupancyt. A cudaOccupancyMaxActiveBlocksPerMultiprocessor használata azért fontos, mert figyelembe veszi a launch bounds, a regiszterek és a shared memory által támasztott korlátokat. A könyv konvencióinak megfelelően minden API-hívást ellenőrzünk, és az eszköztulajdonságokat explicit módon lekérdezzük.

12.4.2 2. Az occupancy és a teljesítmény kapcsolata

Az occupancy elsődleges szerepe a késleltetés elrejtése. Ha egy warp hosszú memóriaműveletre vár, a hardver másik warp-okra válthat. Minél több rezidens warp van, annál nagyobb az esély arra, hogy az SM végrehajtó egységei folyamatosan találnak munkát. Ebből a szempontból az alacsony occupancy általában rossz hír, különösen memória-korlátos kernelekben.

Ugyanakkor az occupancy növelése szinte soha nem ingyen van. Ahhoz, hogy több blokk férjen el egy SM-en, csökkenteni kell valamelyik erőforrás blokkonkénti fogyasztását: a regiszterek számát, a shared memory méretét vagy a blockmérethez kötött erőforrásigényt. Ha ezt a regiszterek számának mesterséges csökkentésével érjük el, a fordító regisztereket helyezhet ki lokális memóriába, azaz regiszter-spill keletkezhet. A spill a globális memóriahierarchiába ír és onnan olvas, ami extra késleltetést és sávszélesség-fogyasztást okoz. Az eredmény lehet az, hogy a 100%-os occupancy mellett mért futásidő rosszabb, mint egy 66%-os occupancy mellett mért, de spill-mentes változaté.

A túl magas occupancy másik árnyoldala a cache- és memórianyomás növekedése. Ha sok warp osztozik ugyanazon az L1/L2 cache-en, a hasznos adat gyorsabban kiszorulhat, és nő a cache thrash. Memória-korlátos kerneleknél a túlzottan sok aktív warp nem feltétlenül növeli az elérhető sávszélességet, mert a memóriavezérlő és a cache is telítődhet. Ilyenkor a magasabb occupancy csak nagyobb versenyhez vezet, és a teljesítmény stagnálhat vagy romolhat.

A túl alacsony occupancy tipikus tünetei a következők:

  • hosszú long_scoreboard stall-ok, mert a warp-ok memória-válaszra várnak;
  • alacsony kiadott utasítás/órajel arány (issue rate);
  • a végrehajtó egységek kihasználatlansága;
  • a futásidő jelentős javulása akkor, ha a blockméretet vagy a regiszterhasználatot úgy változtatjuk, hogy több warp férjen el.

A túl magas occupancy tipikus tünetei:

  • lokális memória spill a ptxas jelentésben;
  • növekvő L1/L2 forgalom anélkül, hogy a hasznos számítás nőne;
  • bank conflict a shared memory hozzáférésekben;
  • a legjobb futásidő nem a legmagasabb elméleti occupancynél jelentkezik.

Fontos hangsúlyozni, hogy az occupancy egy szükséges, de nem elégséges feltétel. A Latency hiding alfejezetben tárgyalt latency hiding akkor működik jól, ha a késleltetést ténylegesen el lehet rejteni, de ha a kernel számítás-korlátos, akkor a kisebb occupancy is elég lehet, mert a végrehajtó egységek hosszú utasítássorozatokat hajtanak végre. A teljesítményt ezért mindig a következő együttes határozza meg:

teljesítmény=f(occupancy,regiszterhasználat,shared memory,memória-hozzáférési minta,számítási intenzitás). \text{teljesítmény} = f(\text{occupancy}, \text{regiszterhasználat}, \text{shared memory}, \text{memória-hozzáférési minta}, \text{számítási intenzitás}).

Egyetlen mérőszám, így az occupancy sem elég a döntéshez.

12.4.3 3. Alacsony és magas occupancy a gyakorlatban

A gyakorlati optimalizálás során két gyakori szélsőséget érdemes felismerni.

12.4.4 3.1. Túl alacsony occupancy

Ha egy kernel nagyon kevés aktív warpot tartalmaz, a hardver nem tudja elrejteni a globális memória késleltetését. Tipikus példa erre egy olyan stencil- vagy redukciós kernel, amely nagy blokkmérettel és nagy regiszterigénnyel indul, de az SM-en csak 8–16 aktív warp marad. A mérés ilyenkor általában azt mutatja, hogy a smsp__average_warps_issue_stalled_long_scoreboard metrika magas, az elért foglaltság pedig jóval a hardveres maximum alatt van.

Az alacsony occupancy javításának első lépése a blockméret csökkentése vagy a regiszterhasználat mérséklése. A blockméret csökkentése azonban nem mindig segít, mert a kisebb blokk kevesebb shared memory-t használhat, és a blokkon belüli szinkronizáció is olcsóbb lehet, de a túl kicsi blokk esetén a blokkon belüli párhuzamosság csökken. A regiszterhasználat csökkentése a __launch_bounds__ vagy a -maxrregcount kapcsolóval érhető el, de ez spill-t okozhat. Ezért az alacsony occupancy kezelése mindig mérést igényel.

12.4.5 3.2. Túl magas occupancy

A másik szélsőség az, amikor a fejlesztő mindenáron 100%-os foglaltságot próbál elérni. Ehhez jellemzően a következő eszközöket veti be:

  • -maxrregcount=16 vagy -maxrregcount=24 kapcsoló;
  • __launch_bounds__(256, 8) olyan második paraméterrel, amely nagy blokkszámot követel;
  • a shared memory használat minimalizálása;
  • a blockméret radikális csökkentése.

Ha a kernel természetes regiszterigénye 64 regiszter/szál, akkor a 24 regiszterre kényszerítés szinte biztosan spill-t generál. A lokális memóriába kiírt regiszterek a globális memóriahierarchián keresztül keringenek, így a magas occupancyből származó nyereség elveszhet. A ptxas -v fordítási jelentés ilyenkor Local memory sorokat tartalmaz, és a Nsight Compute l1tex__data_bank_conflicts_pipe_lsu vagy lts__t_bytes jellegű metrikái megemelkednek.

A túl magas occupancy további következménye lehet a shared memory bank conflictok felerősödése. Ha a kernel shared memory-t használ, és a hozzáférési minta nem konfliktusmentes, a több aktív warp több ütemezési konfliktust generál, így a nyers számítási idő nő.

12.4.6 3.3. Az optimális occupancy megtalálása

Az optimális occupancy nem egyetlen szám, hanem egy tartomány, amely a kernel memória- vagy számítás-korlátos jellegétől függ. A következő heurisztikák segítenek:

  • Memória-korlátos kernelnél általában a magas occupancy előnyös, de csak addig, amíg a memóriavezérlő telítődik.
  • Számítás-korlátos kernelnél a mérsékelt occupancy is elég lehet, mert a végrehajtó egységek hosszú ideig dolgoznak.
  • Ha a regiszterhasználat csökkentése spill-t okoz, akkor a magasabb occupancy nem éri meg.
  • A legjobb blockméretet és regiszterkorlátot empirikusan kell meghatározni.

12.4.7 4. Gyakorlati optimalizálási munkafolyamat

Az occupancy optimalizálásához a következő lépéseket érdemes követni.

12.4.8 4.1. Fordítási jelentés lekérése

A CUDA fordító a -Xptxas -v kapcsolóval kiírja a regiszterhasználatot, a shared memory méretét és a lokális memória spill mértékét. Példa fordítási parancs:

nvcc -arch=sm_89 -O3 -Xptxas -v -I. -c register_pressure.cu -o register_pressure.o

A kimenet jellemzően a következőhöz hasonló:

ptxas info    : Compiling entry function '_Z22register_pressure_kernelILi32ELi256EEEvPKfPfif' for 'sm_89'
ptxas info    : Function properties for _Z22register_pressure_kernelILi32ELi256EEEvPKfPfif
    32 bytes stack frame, 0 bytes spill stores, 0 bytes spill loads
ptxas info    : Used 62 registers, 0 bytes cumulative stack size

A fenti sorokból látható, hogy a kernel 62 regisztert használ, és nincs spill. Ha a Used sor mellett spill stores vagy spill loads jelenik meg, akkor a regiszterkorlát túl szigorú, vagy a kernel természetes regiszterigénye túl nagy.

12.4.9 4.2. Elméleti occupancy kiszámítása

A regiszterhasználat ismeretében kiszámítható az elméleti occupancy. A gyakorlatban ezt a CUDA Occupancy Calculator vagy a cudaOccupancyMaxActiveBlocksPerMultiprocessor API segítségével érdemes elvégezni, mert a hardveres kerekítések jelentősek lehetnek. A számításnál figyelembe kell venni a regiszterfájl méretét, a shared memory-t és a blokk-slot korlátot.

12.4.10 4.3. Profilozás Nsight Compute segítségével

Az Nsight Compute a kernel szintű metrikákat gyűjti. Az occupancy szempontjából a következő metrikák a leghasznosabbak:

  • sm__warps_active.avg.pct_of_peak_sustained_active: az elért foglaltság százalékban;
  • launch__registers_per_thread: a regiszterek száma szálanként;
  • launch__occupancy_limit_registers: a regiszterekből adódó foglaltsági korlát;
  • launch__occupancy_limit_blocks: a blokk-slotokból adódó korlát;
  • smsp__average_warps_issue_stalled_long_scoreboard: a memória-várakozásból adódó stall;
  • l1tex__t_bytes: az L1 cache forgalma.

Egy egyszerű Nsight Compute parancs:

ncu --set full --launch-count 1 --csv ./register_pressure > report.csv

A jelentésből látható, hogy a kernel elért foglaltsága mennyire van összhangban az elméleti értékkel, és melyik erőforrás a szűk keresztmetszet.

12.4.11 4.4. Hangolás blokkméreten és regiszterlimiten keresztül

A hangolás során a következőket érdemes változtatni:

  • blockméret: 64, 128, 256, 512, 1024;
  • regiszterlimit: -maxrregcount 24, 32, 40, 48, 64;
  • __launch_bounds__: a második paraméterrel előírható a minimális blokkszám SM-enként.

A __launch_bounds__(maxThreadsPerBlock, minBlocksPerMultiprocessor) a második paraméterrel explicit módon befolyásolhatja a regiszterhasználatot. Például:

template<int R, int BLOCK>
__global__ void __launch_bounds__(BLOCK, 3)
register_pressure_kernel(const float* __restrict__ x, float* __restrict__ y, int n, float alpha);

Ez azt jelzi a fordítónak, hogy az adott kernelből legalább 3 blokkot szeretnénk elhelyezni SM-enként. A fordító ennek megfelelően próbálja csökkenteni a regiszterhasználatot, de ha a természetes igény nagy, akkor spill-t generálhat. A -maxrregcount az egész fordítási egységre vonatkozik, ezért finomhangolásra kevésbé alkalmas, de gyors kísérletekhez jó.

12.4.12 4.5. Mérés és validáció

A hangolás során minden változatra mérést kell végezni. A mérés előtt melegítő futtatás, majd legalább 5–10 ismétlés szükséges. Az átlag mellett a szórást is közölni kell. A méréshez CUDA eventek használata javasolt, mert azok a GPU idővonalon mérik az időt. A validáció során a kernel kimenetét CPU-referenciával kell összehasonlítani, és a hibakorlátot explicit módon kell rögzíteni.

12.4.13 5. Tipikus hibák és tévhitek

Az occupancy optimalizálásakor a következő hibák fordulnak elő leggyakrabban:

  1. Az occupancy egyetlen mérőszámként kezelése. A 100%-os foglaltság nem garantálja a legjobb futásidőt. A döntéshez mindig a mért teljesítményt kell alapul venni.

  2. A regiszter-spill figyelmen kívül hagyása. A ptxas -v vagy az Nsight Compute jelentés nélkül végrehajtott regiszterlimit-csökkentés gyakran rejtett lokális memória forgalmat okoz.

  3. A blockméret és a regiszterhasználat együttes hangolásának elhanyagolása. A regiszterlimit és a blockméret kölcsönhatásban van, ezért a kettőt együtt kell vizsgálni.

  4. Az elméleti és az elért occupancy összekeverése. Az elméleti occupancy a hardveres korlátokból számított felső korlát; az elért occupancy a ténylegesen rezidens warp-ok aránya. A kettő eltérhet, ha a kernel indítási paraméterei vagy a memória-hozzáférési minta miatt a hardver nem tudja kihasználni az elérhető erőforrásokat.

  5. A mérési környezet hiányos rögzítése. A GPU modell, a driver, a CUDA verzió, a power limit és a háttérterhelés mind befolyásolja az eredményt. A könyv konvencióinak megfelelően ezeket minden mérésnél rögzíteni kell.

A labor célja, hogy egy kis, ellenőrizhető kernel segítségével megvizsgáljuk a blockméret és a regiszterhasználat hatását az occupancyre és a futásidőre. A labor CUDA C++-ban készült, és a mérési környezetet explicit módon rögzítjük.

12.4.16 6.2. Kernel és mérési program

A laborhoz egy olyan kernelt használunk, amelynek regiszterigénye sablonparaméterrel szabályozható. A kernel minden szál egy globális memóriabeli elemet olvas, majd egy RR elemű regisztertömböt használ egy rövid, de valós számítási lánchoz. Az RR érték növelésével a regiszterigény nő, így az occupancy fokozatosan csökken. A kernel emellett a globális memóriából olvas és oda ír, ezért a memória-késleltetés hatása is mérhető.

// register_pressure.cu
#include <cuda_runtime.h>
#include <cstdio>
#include <cstdlib>
#include <cmath>
#include <vector>
#include <iostream>

#define CUDA_CHECK(call)                                                      \
    do {                                                                      \
        cudaError_t err = (call);                                             \
        if (err != cudaSuccess) {                                             \
            std::fprintf(stderr, "CUDA error at %s:%d: %s\n", __FILE__,       \
                         __LINE__, cudaGetErrorString(err));                    \
            std::exit(EXIT_FAILURE);                                           \
        }                                                                     \
    } while (0)

template<int R, int BLOCK>
__global__ void __launch_bounds__(BLOCK)
register_pressure_kernel(const float* __restrict__ x, float* __restrict__ y,
                         int n, float alpha) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= n) return;

    float coeff[R];
    #pragma unroll
    for (int r = 0; r < R; ++r) {
        coeff[r] = alpha * (float)r + (float)(i & 15) * 1e-3f;
    }

    float acc = x[i];
    #pragma unroll
    for (int r = 0; r < R; ++r) {
        acc = fmaf(acc, coeff[r], 1.0f);
    }
    y[i] = acc;
}

template<int R, int BLOCK>
float run_case(int n, float alpha, int iterations) {
    float *d_x = nullptr, *d_y = nullptr;
    CUDA_CHECK(cudaMalloc(&d_x, (size_t)n * sizeof(float)));
    CUDA_CHECK(cudaMalloc(&d_y, (size_t)n * sizeof(float)));

    std::vector<float> h_x((size_t)n);
    for (int i = 0; i < n; ++i) h_x[i] = (float)(i % 1000) * 0.001f + 0.5f;
    CUDA_CHECK(cudaMemcpy(d_x, h_x.data(), (size_t)n * sizeof(float),
                          cudaMemcpyHostToDevice));

    int grid = (n + BLOCK - 1) / BLOCK;
    dim3 gDim(grid);
    dim3 bDim(BLOCK);

    // warm-up
    for (int it = 0; it < 3; ++it) {
        register_pressure_kernel<R, BLOCK><<<gDim, bDim>>>(d_x, d_y, n, alpha);
        CUDA_CHECK(cudaGetLastError());
    }
    CUDA_CHECK(cudaDeviceSynchronize());

    cudaEvent_t start, stop;
    CUDA_CHECK(cudaEventCreate(&start));
    CUDA_CHECK(cudaEventCreate(&stop));

    CUDA_CHECK(cudaEventRecord(start));
    for (int it = 0; it < iterations; ++it) {
        register_pressure_kernel<R, BLOCK><<<gDim, bDim>>>(d_x, d_y, n, alpha);
        CUDA_CHECK(cudaGetLastError());
    }
    CUDA_CHECK(cudaEventRecord(stop));
    CUDA_CHECK(cudaEventSynchronize(stop));

    float elapsed_ms = 0.0f;

    CUDA_CHECK(cudaFree(d_y));
    CUDA_CHECK(cudaEventDestroy(start));
    CUDA_CHECK(cudaEventDestroy(stop));

    return avg_ms;
}

12.4.17 6.3. Validáció

A validációhoz használjunk kisebb N=1<<20N = 1 << 20 méretet, és a kernel kimenetét vessük össze egy CPU-referenciával. A CPU-referencia ugyanazt a műveletsort hajtja végre, mint a kernel:

// cpu_reference.cpp
#include <cmath>
#include <cstdio>
#include <vector>

int main() {
    constexpr int N = 1 << 20;
    constexpr float ALPHA = 0.9f;
    constexpr int R = 32;
    std::vector<float> x(N), y_cpu(N);
    for (int i = 0; i < N; ++i) x[i] = (float)(i % 1000) * 0.001f + 0.5f;

    for (int i = 0; i < N; ++i) {
        float coeff[R];
        for (int r = 0; r < R; ++r) {
            coeff[r] = ALPHA * (float)r + (float)(i & 15) * 1e-3f;
        }
        float acc = x[i];
        for (int r = 0; r < R; ++r) {
            acc = std::fmaf(acc, coeff[r], 1.0f);
        }
        y_cpu[i] = acc;
    }

    // A GPU kimenetet fájlból vagy közvetlen memóriából hasonlítjuk össze.
    // Itt csak a referencia értékeket írjuk ki.
    std::printf("CPU reference computed for N=%d, R=%d\n", N, R);
    return 0;
}

A labor során a GPU kimenetet visszamásoljuk a hostra, és a maximális abszolút hibát számítjuk. A várt hiba FP32 esetén kicsi, jellemzően 10−410^{-4} alatti relatív hiba, mert a kernel és a CPU-referencia ugyanazt a fmaf műveletsort használja. A pontos érték a GPU és a CPU lebegőpontos egységének megvalósításától függ.

12.4.19 6.5. Várt és mért eredmények elkülönítése

Várt eredmények. A regisztertömb méretének növelésével a kernel regiszterigénye nő, ezért az elméleti occupancy csökken. A ptxas jelentés alapján azt várjuk, hogy az R=8R=8 és R=16R=16 változat magas occupancy mellett fut, de a szálankénti munka viszonylag kicsi, így a memória-hozzáférések aránya nagyobb. Az R=32R=32 változatnál az occupancy 66,7%-ra csökken, de a nagyobb számítási sűrűség miatt a globális memória-hozzáférések jobban átfedhetők. Az R=64R=64 változatnál az occupancy 33,3%, ami még mindig elég lehet a memória-késleltetés elrejtéséhez, de a kevesebb aktív warp már érzékenyebb a késleltetésre. Az R=128R=128 változatnál a regiszterek száma meghaladja a kényelmes tartományt, ezért spill jelenik meg, ami extra lokális memória forgalmat okoz, és a futásidő jelentősen nő.

Mért eredmények. A fenti táblázat azt mutatja, hogy a legjobb futásidőt az R=32R=32 változat adja, 66,7%-os elméleti occupancy mellett. Az R=8R=8 és R=16R=16 változat magasabb occupancy mellett lassabb, mert a szálankénti munka kisebb, és a memória-hozzáférések dominálnak. Az R=128R=128 változat a spill miatt 25%-kal lassabb, mint a legjobb változat. Ez az eredmény összhangban van a várt trenddel, és jól mutatja, hogy a legmagasabb occupancy nem feltétlenül eredményez legjobb teljesítményt.

A mérési napló értékei egy adott környezetből származnak; a pontos számok más GPU-n vagy más driver/CUDA verzióval eltérhetnek. A módszertan és a trend azonban reprodukálható.

12.4.20 7. Összefoglalás és önellenőrző kérdés

Az occupancy az SM-en egyidejűleg rezidens warp-ok aránya. Az erőforrás-korlátok – elsősorban a regiszterfájl, a shared memory és a blokk-slotok – határozzák meg, hogy hány blokk fér el. Az occupancy növelése javíthatja a késleltetés elrejtését, de a túl alacsony és a túl magas occupancy is ronthatja a teljesítményt. A túl alacsony occupancy memória-korlátos kernelnél stall-okhoz vezet; a túl magas occupancy eléréséhez alkalmazott regisztercsökkentés spill-t okozhat, ami extra memóriaforgalmat generál. Az optimális occupancy ezért mindig empirikus hangolással, méréssel és profilozással határozható meg.

Önellenőrző kérdés. Miért lehet egy kernel 66%-os elméleti occupancy mellett gyorsabb, mint 100%-os occupancy mellett? Adjon egy konkrét erőforrás-okot, és magyarázza el a mechanizmust.

Válaszvázlat. A 100%-os occupancy eléréséhez a regiszterhasználatot csökkenteni kell. Ha a csökkentés a kernel természetes regiszterigénye alá megy, a fordító regisztereket helyez ki lokális memóriába, azaz spill keletkezik. A lokális memória hozzáférések a globális memóriahierarchiát terhelik, extra késleltetést és sávszélesség-fogyasztást okoznak. Emiatt a magasabb occupancyből származó jobb latency hiding nem tudja ellensúlyozni a spill költségét, és a 66%-os occupancy melletti, spill-mentes változat gyorsabb lehet.
