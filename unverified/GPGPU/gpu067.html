18.2 Halo-csere és többblokkos stencil

A halo-csere akkor válik elsődleges helyességi és teljesítménykérdéssé, amikor a stencil rácsát több blokk között osztjuk szét. A gpu066 egységben a stencil-számítás alapjait, a rádiuszt és a shared memory tile gondolatát már bevezettük. Most azt vizsgáljuk, hogyan kezeljük a blokkhatárokon átnyúló függőségeket: mit kell betölteni a szomszédos blokkokból, hogyan biztosítja a globális memória az adatcserét, és milyen szinkronizációs szabályok mellett marad helyes a megoldás.

18.2.1 1. A blokkok közötti halo fogalma

Egy 2D, ötpontos Jacobi-stencil esetén az (i,j) cella új értéke:

ui,jt+1=14(ui−1,jt+ui+1,jt+ui,j−1t+ui,j+1t), u^{t+1}_{i,j} = \frac{1}{4}\left( u^t_{i-1,j}+u^t_{i+1,j}+u^t_{i,j-1}+u^t_{i,j+1} \right),

ha Dirichlet-peremmel a tartományon kívüli pontok értékét nullának tekintjük. A stencil rádiusza itt R=1, mert minden irányban egy cella távolságig van szükség a szomszédokra.

Ha a rácsot blokkonként feldolgozott csempékre bontjuk, akkor egy T×T belső méretű csempének a széle számításához a csempén kívüli, R szélességű gyűrű is kell. Ezt a gyűrűt nevezzük halonak vagy szellemcellának. A blokk által számított belső tartományt interior, a betöltött, de nem frissített szomszédos gyűrűt halo néven különböztetjük meg.

Egy T×T csempéhez H=R=1 esetén a teljes betöltött tartomány:

(T+2R)2=(T+2)2 (T+2R)^2 = (T+2)^2

cella, míg a belső, frissítendő tartomány T^2. A halo celláinak száma:

Nhalo=(T+2)2−T2=4T+4. N_{\mathrm{halo}} = (T+2)^2 - T^2 = 4T+4.

A halo-arány tehát:

NhaloNbetöltött=4T+4(T+2)2. \frac{N_{\mathrm{halo}}}{N_{\mathrm{betöltött}}} = \frac{4T+4}{(T+2)^2}.

Ez az arány a csempeméret növelésével csökken, tehát a nagyobb csempe kisebb relatív halo-forgalmat jelent. Ugyanakkor a csempe mérete nem nőhet korlátlanul, mert a shared memory és a regiszterkészlet korlátos.

Csempeméret T Betöltött cella (T+2)^2 Halo-cella Halo-arány
8 100 36 36,0%
16 324 68 21,0%
32 1156 132 11,4%
64 4356 260 6,0%

A táblázatban a halo-arány a blokk által a globális memóriából beolvasott adatmennyiség azon része, amely nem belső számítási munka. Ezért a csempeméret megválasztása nemcsak occupancy-kérdés, hanem memóriaforgalmi kérdés is.

18.2.2 2. Implicit és explicit halo-kezelés

A GPU-n a blokkok közötti halo-kezelésnek két gyakorlati alakja van.

18.2.3 Implicit halo globális memórián keresztül

A legegyszerűbb, és egyetlen GPU-n gyakran a legjobb módszer az, hogy nincsenek külön szellemtömbök. A teljes u és u_{\mathrm{next}} tömb a rács fizikai celláit tárolja nx×ny méretben. Minden blokk a saját tile-jához tartozó belső cellákat számítja, de a szükséges szomszédokat közvetlenül a globális memóriában lévő aktuális u tömbből olvassa be a shared memory tile-ba.

Ebben a modellben a halo-csere nem külön másolási lépés, hanem maga a globális memóriából való beolvasás. A szomszédos blokkok által előző iterációban kiírt értékeket a következő kernelindítás olvassa. Az iterációk közötti kernelindítás határa egyben globális szinkronizációs pont is: a kernel újraindulása előtt minden blokk befejezte az előző iteráció írását.

Ez a minta együtt jár a dupla puffereléssel:

for k in 0..K-1:
    stencil_kernel<<<grid, block>>>(u, u_next)
    swap(u, u_next)

A swap itt pointercserét jelent, nem adatmozgatást. A dupla pufferelés azért fontos, mert ha ugyanabba a tömbbe írnánk, amelyből olvasunk, akkor az egyik blokk már felülírhatná azt az értéket, amelyet egy másik blokk még nem olvasott be. A kernelindítások közötti implicit globális szinkronizáció ezt a versenyhelyzetet kiküszöböli.

18.2.4 Explicit halo-csere szellemtömbökkel

Bizonyos tervezési mintákban – például perzisztens blokkoknál, multi-GPU-s felosztásnál, vagy erősen particionált subdomain-tárolásnál – a csempéknek saját, külön tárolt szellemtartományuk van. Ekkor a belső cellák kiszámítása után egy külön lépésben kell a szomszédos csempék szélső celláit a megfelelő szellemtartományba másolni. Ezt nevezzük explicit halo-cserének.

A két modell közötti döntés egyszerűen megfogalmazható:

  • egyetlen GPU, iterációnként induló kernel → implicit halo;
  • perzisztens blokk, saját subdomain-tárolás, multi-GPU vagy specifikus overlap-terv → explicit halo.

18.2.5 3. Globális memória és szinkronizáció szabályai

A blokkok közötti adatcsere a globális memórián keresztül történik. A globális memória láthatósága a kernelhatárokon garantált: ha egy kernelben az egyik blokk kiír egy értéket, akkor a következő kernel már láthatja azt.

Ebből következik, hogy az implicit halo-minta esetén nem kell semmilyen blokkok közötti __syncthreads() hívás. A __syncthreads() csak egy blokk szálait szinkronizálja. Nem globális barrier, és blokkok közötti láthatóságot nem ad. Ha valaki például azt feltételezi, hogy a 0. blokk által kiírt szomszédos cella az 1. blokkban egy __syncthreads() után látható, az hibás: a blokkok ütemezése nem garantált, és a hardver nem ad ilyen szinkronizációt.

A kernelhatárok által adott globális szinkronizáció elegendő, de van egy ára: minden iterációban lezárul és újraindul egy kernel. Ez több ezer rövid stencil-lépés esetén számottevő launch overhead lehet. Ilyenkor megoldás lehet:

  • grid-stride loop és néhány iteráció egy kernelben, de ekkor a halo nem frissülhet az egyes belső lépések között, ezért csak olyan stencil esetén használható, ahol a régebbi halo érték is elfogadható, vagy
  • cooperative groups grid-szinkronizáció, amely bizonyos architektúrákon és feltételekkel kernelhatáron belül is ad globális szinkronizációt. Ezt a gpu032 egység tárgyalja; itt elég annyi, hogy ez haladó eszköz, és alapfeladatban a kernelhatár-alapú megoldás a megbízható kiindulópont.

18.2.6 4. Teljes példa: 2D Jacobi shared memory tile-vel és implicit haloval

Az alábbi CUDA C++ példa azt a javasolt mintát valósítja meg, amikor a halo a globális u tömbből kerül a shared memory tile-ba. A kernel 32×32 belső cellát számít blokkonként, és minden blokk egy 34×34 shared memory tile-t tölt fel.

// CUDA C++ (C++17)
// halo_stencil.cu
#include <cstdio>
#include <cstdlib>
#include <cmath>
#include <vector>
#include <algorithm>
#include <cuda_runtime.h>

#define CUDA_CHECK(call)                                                    \
  do {                                                                      \
    cudaError_t err = (call);                                               \
    if (err != cudaSuccess) {                                               \
      std::fprintf(stderr, "CUDA error %s:%d: %s\n",                       \
                   __FILE__, __LINE__, cudaGetErrorString(err));            \
      std::exit(EXIT_FAILURE);                                              \
    }                                                                       \
  } while (0)

using real = double;

constexpr int R = 1;
constexpr int TILE_X = 32;
constexpr int TILE_Y = 32;

// Tiled kernel: a halo-t a globális u tömbből tölti be.
__global__ void jacobi2d_tiled(const real* __restrict__ u,
                               real* __restrict__ un,
                               int nx, int ny)
{
  __shared__ real s[TILE_Y + 2 * R][TILE_X + 2 * R];

  const int tx0 = blockIdx.x * TILE_X;
  const int ty0 = blockIdx.y * TILE_Y;

  const int tile_w = TILE_X + 2 * R;
  const int tile_h = TILE_Y + 2 * R;

  // A tile-nek és a halo-nak megfelelő cellák betöltése.
  for (int idx = threadIdx.y * blockDim.x + threadIdx.x;
       idx < tile_w * tile_h;
       idx += blockDim.x * blockDim.y) {

    const int shx = idx % tile_w;
    const int shy = idx / tile_w;
    const int gx  = tx0 + shx - R;
    const int gy  = ty0 + shy - R;

    const bool inside_x = (gx >= 0 && gx < nx);
    const bool inside_y = (gy >= 0 && gy < ny);

    s[shy][shx] = (inside_x && inside_y) ? u[gy * nx + gx] : real(0);
  }

  __syncthreads();

  const int i = ty0 + threadIdx.y;
  const int j = tx0 + threadIdx.x;

  if (i < ny && j < nx) {
    const int sx = threadIdx.x + R;
    const int sy = threadIdx.y + R;

    const real left  = s[sy][sx - 1];
    const real right = s[sy][sx + 1];
    const real down  = s[sy - 1][sx];
    const real up    = s[sy + 1][sx];

    un[i * nx + j] = real(0.25) * (left + right + down + up);
  }
}

// Referenciakernel: ugyanaz a stencil közvetlen globális memóriaolvasással.
__global__ void jacobi2d_ref(const real* __restrict__ u,
                             real* __restrict__ un,
                             int nx, int ny)
{
  const int i = blockIdx.y * blockDim.y + threadIdx.y;
  const int j = blockIdx.x * blockDim.x + threadIdx.x;

  if (i >= ny || j >= nx) return;

  const real left  = (j > 0)       ? u[i * nx + j - 1] : real(0);
  const real right = (j + 1 < nx)  ? u[i * nx + j + 1] : real(0);
  const real down  = (i > 0)       ? u[(i - 1) * nx + j] : real(0);
  const real up    = (i + 1 < ny)  ? u[(i + 1) * nx + j] : real(0);

  un[i * nx + j] = real(0.25) * (left + right + down + up);
}

real* run_tiled(real* u, real* un, int nx, int ny, int iterations)
{
  dim3 block(TILE_X, TILE_Y);
  dim3 grid((nx + TILE_X - 1) / TILE_X,
            (ny + TILE_Y - 1) / TILE_Y);

  for (int k = 0; k < iterations; ++k) {
    jacobi2d_tiled<<<grid, block>>>(u, un, nx, ny);
    CUDA_CHECK(cudaGetLastError());
    std::swap(u, un);
  }

  return u;
}

real* run_ref(real* u, real* un, int nx, int ny, int iterations)
{
  dim3 block(32, 32);
  dim3 grid((nx + 31) / 32, (ny + 31) / 32);

  for (int k = 0; k < iterations; ++k) {
    jacobi2d_ref<<<grid, block>>>(u, un, nx, ny);
    CUDA_CHECK(cudaGetLastError());
    std::swap(u, un);
  }

  return u;
}

int main(int argc, char** argv)
{
  const int nx         = (argc > 1) ? std::atoi(argv[1]) : 2048;
  const int ny         = (argc > 2) ? std::atoi(argv[2]) : 2048;
  const int iterations = (argc > 3) ? std::atoi(argv[3]) : 20;

  const size_t n = static_cast<size_t>(nx) * ny;
  const size_t nbytes = n * sizeof(real);

  std::vector<real> h_u(n), h_zero(n, real(0)), h_tiled(n), h_ref(n);

  for (int i = 0; i < ny; ++i) {
    for (int j = 0; j < nx; ++j) {
      const real x = static_cast<real>(j);
      const real y = static_cast<real>(i);
      h_u[i * nx + j] =
          std::sin(real(0.02) * x) * std::cos(real(0.012) * y) +
          std::exp(-((x - nx / real(2)) * (x - nx / real(2)) +
                     (y - ny / real(2)) * (y - ny / real(2))) /
                   real(2000.0));
    }
  }

  real *d_u = nullptr, *d_un = nullptr;
  real *d_ref_u = nullptr, *d_ref_un = nullptr;

  CUDA_CHECK(cudaMalloc(&d_u, nbytes));
  CUDA_CHECK(cudaMalloc(&d_un, nbytes));
  CUDA_CHECK(cudaMalloc(&d_ref_u, nbytes));
  CUDA_CHECK(cudaMalloc(&d_ref_un, nbytes));

  CUDA_CHECK(cudaMemcpy(d_u, h_u.data(), nbytes, cudaMemcpyHostToDevice));
  CUDA_CHECK(cudaMemcpy(d_ref_u, h_u.data(), nbytes, cudaMemcpyHostToDevice));
  CUDA_CHECK(cudaMemcpy(d_un, h_zero.data(), nbytes, cudaMemcpyHostToDevice));
  CUDA_CHECK(cudaMemcpy(d_ref_un, h_zero.data(), nbytes, cudaMemcpyHostToDevice));

  // Warm-up: a mérés előtti első indítás ne torzítsa az időt.
  {
    dim3 block(TILE_X, TILE_Y);
    dim3 grid((nx + TILE_X - 1) / TILE_X,
              (ny + TILE_Y - 1) / TILE_Y);
    jacobi2d_tiled<<<grid, block>>>(d_u, d_un, nx, ny);
    CUDA_CHECK(cudaGetLastError());
    CUDA_CHECK(cudaDeviceSynchronize());
  }

  cudaEvent_t start, stop;
  CUDA_CHECK(cudaEventCreate(&start));
  CUDA_CHECK(cudaEventCreate(&stop));

  CUDA_CHECK(cudaEventRecord(start, 0));
  real* final_tiled = run_tiled(d_u, d_un, nx, ny, iterations);
  CUDA_CHECK(cudaEventRecord(stop, 0));
  CUDA_CHECK(cudaEventSynchronize(stop));

  float ms = 0.0f;
  CUDA_CHECK(cudaEventElapsedTime(&ms, start, stop));
  const double seconds = static_cast<double>(ms) / 1000.0;

  dim3 block(TILE_X, TILE_Y);
  dim3 grid((nx + TILE_X - 1) / TILE_X,
            (ny + TILE_Y - 1) / TILE_Y);

  const size_t loaded_cells =
      static_cast<size_t>(grid.x) * grid.y *
      (TILE_X + 2 * R) * (TILE_Y + 2 * R) * iterations;

  const size_t written_cells = n * static_cast<size_t>(iterations);

  const double moved_bytes =
      static_cast<double>(loaded_cells + written_cells) * sizeof(real);

  const double effective_bw_gbs =
      moved_bytes / (seconds * 1e9);

  real* final_ref = run_ref(d_ref_u, d_ref_un, nx, ny, iterations);
  CUDA_CHECK(cudaDeviceSynchronize());

  CUDA_CHECK(cudaMemcpy(h_tiled.data(), final_tiled,
                        nbytes, cudaMemcpyDeviceToHost));
  CUDA_CHECK(cudaMemcpy(h_ref.data(), final_ref,
                        nbytes, cudaMemcpyDeviceToHost));

  double max_abs_diff = 0.0;
  for (size_t idx = 0; idx < n; ++idx) {
    max_abs_diff = std::max(max_abs_diff,
                            std::abs(h_tiled[idx] - h_ref[idx]));
  }

  std::printf("nx=%d ny=%d iterations=%d tile=%dx%d\n",
              nx, ny, iterations, TILE_X, TILE_Y);
  std::printf("kernel time = %.3f ms\n", ms);
  std::printf("effective bandwidth = %.2f GB/s\n",
              effective_bw_gbs);
  std::printf("max abs diff vs reference = %.17g\n", max_abs_diff);

  CUDA_CHECK(cudaFree(d_u));
  CUDA_CHECK(cudaFree(d_un));
  CUDA_CHECK(cudaFree(d_ref_u));
  CUDA_CHECK(cudaFree(d_ref_un));
  CUDA_CHECK(cudaEventDestroy(start));
  CUDA_CHECK(cudaEventDestroy(stop));

  return 0;
}

A kódban a run_tiled minden iterációban újraindítja a kernelt, majd pointert cserél. A final_tiled pointer ezért az utolsó iteráció eredményét mutatja. A referenciakernel ugyanazon a topológián dolgozik, de nem használ shared memory tile-t; így a két futás numerikusan összehasonlítható.

A sávszélességszámítás itt a tényleges globális adatmozgást közelíti:

GB/s=[GxGy(Tx+2)(Ty+2)K+nxnyK]⋅8t⋅109, \mathrm{GB/s} = \frac{ \left[ G_x G_y (T_x+2)(T_y+2)K + n_x n_y K \right] \cdot 8 }{t \cdot 10^9},

ahol K az iterációk száma, G_x,G_y a rácsdimenzió, T_x,T_y a tile belső mérete, t pedig a mért futásidő másodpercben. Ez nem a hardver névleges csúcssávszélessége, hanem az algoritmus globális memóriaforgalmára számított effektív érték.

18.2.7 5. Explicit halo-csere egy egyszerű 1D modellen

Az explicit halo-csere oktatására az 1D eset a legáttekinthetőbb. Tegyük fel, hogy a fizikai tartományt T darab, egyenként W belső cellát tartalmazó csempére osztjuk. Minden csempe globális memóriában S = W + 2H hosszú szeletet foglal el, ahol H a halo szélessége. Egy csempe helyi indexei:

[0, H-1]               bal halo
[H, H+W-1]             belső cellák
[H+W, H+W+H-1]         jobb halo

A belső kernel kiszámítja a H és H+W-1 közötti frissített értékeket. Ezután a halo-kernel a bal szélső belső cellákat a szomszéd jobb halojába, a jobb szélső belső cellákat pedig a szomszéd bal halojába másolja.

// CUDA C++ (C++17) -- explicit 1D halo-másoló vázlat
constexpr int H = 1;

__global__ void halo1d_explicit(const real* __restrict__ src,
                                real* __restrict__ dst,
                                int tiles, int stride, int width)
{
  const int t = blockIdx.x;
  const int h = threadIdx.x;

  if (t >= tiles || h >= H) return;

  // Bal halo: a t-1-edik csempe utolsó H belső cellájából.
  if (t > 0) {
    dst[t * stride + h] =
        src[(t - 1) * stride + width + h];
  }

  // Jobb halo: a t+1-edik csempe első H belső cellájából.
  if (t < tiles - 1) {
    dst[t * stride + H + width + h] =
        src[(t + 1) * stride + H + h];
  }
}

Ez a vázlat egy blokkot indít csempénként, és blokkon belül H szálat használ. Nagy H vagy sok csempe esetén ez gyenge kihasználtságú lehet, de a helyességi gondolatot jól mutatja. Termelési kódban érdemes a másolást egyetlen kernelben, az összes halocella sorszámát egy 1D indexre leképezve megszervezni, vagy 2D esetben cudaMemcpy2DAsync hívásokkal a téglalap alakú szegélyeket másolni.

2D esetben az explicit halo-csere négy lépésből áll: felső, alsó, bal és jobb szegély másolása. Sorirányú szegélyekhez a cudaMemcpy2DAsync alkalmas, mert egyetlen hívásban másol W×H méretű sorcsíkot device pointerek között. A hívás sémája:

CUDA_CHECK(cudaMemcpy2DAsync(
    dst_ptr, dst_pitch,
    src_ptr, src_pitch,
    width * sizeof(real),
    height,
    cudaMemcpyDeviceToDevice,
    stream));

Ilyenkor a src_ptr a szomszédos csempe belső szegélyére, a dst_ptr a célcsempe megfelelő halosávjára mutat, a pitch pedig a tényleges byte-beli sortávolság. Ez a megoldás aszinkron streamen is futtatható, és nem igényel külön kernelkódot a másoláshoz.

18.2.8 6. Skálázás és a halo költsége

A halo-kezelés költsége a csempék felületével arányos, a hasznos számítás a csempék térfogatával. Ezért a blokkszám növelésével a halo-forgalom relatív súlya nő.

Erős skálázás esetén a rács mérete rögzített, a blokkok számát növeljük. Ekkor a csempék belső mérete csökken, így a halo-arány nő. Például egy 512×512 belső rács esetén:

Blokkrács Tile T Halo-arány
4×4 128 3,1%
8×8 64 6,0%
16×16 32 11,4%
32×32 16 21,0%

A gyakorlatban a T=16 már nagyon nagy halo-arányt jelent, ezért ilyen felbontásnál a blokkszámot nem érdemes túlzásba vinni. Emellett az occupancy is romolhat, ha a kis tile mellett ugyanakkora shared memory fenntartása felesleges.

Gyenge skálázás esetén a csempeméretet rögzítjük, és a rács növelésével arányosan növeljük a blokkok számát. Ekkor a halo-arány közel állandó, és a megoldás jól skálázható, amíg a GPU el nem éri a blokkok és szálak ütemezési korlátait. A gyakorlati optimumot úgy érdemes keresni, hogy a T értékét például 16, 32, 64 és 96 között futtatott mérésekkel vizsgáljuk, miközben rögzítjük az occupancyt, a shared memory méretét és a regiszterhasználatot.

18.2.9 7. Tipikus hibák és javításuk

18.2.10 Hiányzó __syncthreads() a tile betöltése után

Ha a shared memory tile-t feltöltő szálak és a stencilt számító szálak nem szinkronizálnak, akkor az egyik szál még a régi vagy részlegesen kiírt s értéket olvashatja. Helyes megoldás: a betöltési ciklus után mindig __syncthreads().

18.2.11 In-place frissítés

Ha a kernel ugyanabba a tömbbe ír, amelyből a szomszédos blokkok olvasnak, akkor a kiírás sorrendje nem szabályozott. Ez időben változó, nehezen reprodukálható eredményt ad. Helyes megoldás: dupla pufferelés, azaz u és u_next váltogatása.

18.2.12 Blokkok közötti __syncthreads() feltételezése

A __syncthreads() nem globális barrier. Ha a kód azt feltételezi, hogy az összes blokkhalo már frissült, akkor hibás. Helyes megoldás: a halo-cserét kernelhatárra bízni, vagy coop groups grid-szinkronizációt használni szigorú architekturális feltételek mellett.

18.2.13 Nem inicializált halocellák

A shared memory tile szélein a tartományon kívüli cellákba véletlen érték kerülhet, ha azokat nem állítjuk be. A példakódban a feltételen kívül eső cellák értéke 0, ami Dirichlet-peremet valósít meg. Neumann-perem esetén a belső szomszédból, periodikus perem esetén a szemközti oldalról kell tölteni.

18.2.14 Túl nagy csempeméret

A nagy T csökkenti a relatív halo-forgalmat, de növeli a shared memory foglalást, és csökkentheti az occupancyt. A 32×32 tile FP64 esetén (32+2)^2×8 ≈ 9,2 KiB shared memóriát foglal, ami több blokk egyidejű futtatását általában lehetővé teszi. A 96×96 tile már 98^2×8 ≈ 75,4 KiB, ami SM-enként csak néhány blokkot enged, így a latency hiding romolhat.

18.2.15 Nem ellenőrzött kernelhiba

A CUDA kernelindítás aszinkron, ezért a hiba sokszor nem azonnal jelentkezik. A kódban minden indítás után cudaGetLastError, a futtatás után pedig cudaDeviceSynchronize szükséges. Az out-of-bounds hibákat a compute-sanitizer --tool memcheck mutatja meg.

18.2.21 OpenCL és JAX kiegészítés

Ugyanez a minta OpenCL C-ben a __local memóriával valósítható meg. A kernelváza:

// OpenCL C (koncepcionális vázlat, fordítási ellenőrzéshez)
__kernel void jacobi2d_halo(__global const double* u,
                            __global double* un,
                            int nx, int ny)
{
  __local double s[34][34];

  int tx0 = get_group_id(0) * 32;
  int ty0 = get_group_id(1) * 32;

  int i = ty0 + get_local_id(1);
  int j = tx0 + get_local_id(0);

  // ... s feltöltése get_local_size(0), get_local_size(1) alapján ...
  barrier(CLK_LOCAL_MEM_FENCE);

  if (i < ny && j < nx) {
    un[i * nx + j] = 0.25 * (
        s[get_local_id(1) + 1][get_local_id(0)] +
        s[get_local_id(1) + 1][get_local_id(0) + 2] +
        s[get_local_id(1)][get_local_id(0) + 1] +
        s[get_local_id(1) + 2][get_local_id(0) + 1]);
  }
}

JAX-ban a blokkhalo kérdését a keretrendszer és a fordító kezeli. A funkcionális implementáció például jnp.roll és maszk segítségével adható meg:

# JAX (koncepcionális, GPU/TPU-vázlat)
import jax
import jax.numpy as jnp

@jax.jit
def jacobi_step(u):
    left = jnp.roll(u, 1, axis=1).at[:, 0].set(0.0)
    right = jnp.roll(u, -1, axis=1).at[:, -1].set(0.0)
    down = jnp.roll(u, 1, axis=0).at[0, :].set(0.0)
    up = jnp.roll(u, -1, axis=0).at[-1, :].set(0.0)
    return 0.25 * (left + right + down + up)

A JAX ebben a vázlatban a sharding és a halo kommunikációját a háttérben végzi; az explicit blokkszintű irányítás nem jelenik meg. A méréshez ezért külön kell rögzíteni a JAX verzióját, a háttér eszközt (GPU/TPU), valamint a sharding tervet. A TPU-ra vonatkozó szabályokat a gpu106–gpu109 egységek tárgyalják.
