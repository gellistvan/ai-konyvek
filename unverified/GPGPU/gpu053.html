14.4 Tiling és pipeline mérése

A tiling és a pipeline hatásának mérése nem egyszeri futásidő-mérésből áll. A memória-hozzáférési minták, az occupancy, a bankütközések és a latency hiding együttesen határozzák meg, hogy egy optimalizálás valóban csökkenti-e a végrehajtási időt. Ebben az alfejezetben egy olyan mérési keretet építünk fel, amely a tiling és a double buffering hatását reprodukálhatóan, számszerűen és Nsight-alapú metrikákkal vizsgálja. A példa egy mátrix transzponálás lesz; a módszertan azonban változtatás nélkül alkalmazható stencil-, konvolúció- vagy bármely memória-intenzív tiled kernelre.

14.4.1 1. Mérési keret és reprodukálhatóság

Mielőtt bármilyen GPU-n futó kísérletet értékelünk, rögzíteni kell a környezetet. A könyv mérési szerződése szerint minden állításhoz tartoznia kell GPU-modellnek, driververziónak, CUDA-verziónak, compute capabilitynek, operációs rendszernek, órajelnek, power limitnek, valamint annak, hogy ECC, MIG vagy virtuális GPU aktív-e. Ez nem formalitás: ugyanaz a kernel egy A100-on és egy RTX 4090-en más okból lehet gyors vagy lassú.

A mérési protokoll lépései:

  1. Warm-up. Az első kernelindítások inicializálják a modulokat, a konstans memóriát, a driver belső állapotait. Legalább 1–2 extra indítást végezzünk, mielőtt mérni kezdünk.
  2. Többszöri ismétlés. Minden konfigurációt legalább 5–10-szer futtassuk. Az átlag mellett közöljük a szórást vagy percentilist is, mert a GPU-órjel, a hőmérséklet és a háttérterhelés fluktuál.
  3. Azonos input. A tiling és pipeline összehasonlításánál ugyanazt a bemeneti mátrixot, ugyanazt a memóriafoglalást és ugyanazt a kimeneti puffert használjuk.
  4. Környezetrögzítés. A mérés előtt és után kérdezzük le a nvidia-smi-vel az órajelet, a hőmérsékletet és a power limitet. Ha a GPU throttlingol, a mérést meg kell ismételni.
  5. Hibakezelés. Minden CUDA-hívás után cudaGetLastError és cudaDeviceSynchronize; a kernelindítás után CHECK_CUDA(cudaDeviceSynchronize()).

A mérési célok három kernelvariánsra:

  • Baseline: naiv globális memóriás transzponálás.
  • Tiled: shared memory csempézés, bankütközés elkerülése paddinggel.
  • Pipelined: shared memory csempézés és aszinkron másolás (cp.async) double bufferinggel.

A várt hatás iránya ismert: a tiling csökkenti a globális memória tranzakciók számát, a pipeline pedig elrejti a globális memória késleltetését. A mérés feladata ennek számszerűsítése, nem pedig a „gyorsabb” kijelentés bizonyítása.

14.4.2 2. A példa: FP32 mátrix transzponálás

A transzponálás azért alkalmas kísérleti terep, mert memória-intenzív, és a naiv változat egyik memória-hozzáférése szükségképpen nem koaleszkált. A tiled változat mindkét irányban koaleszkált olvasást és írást valósít meg; a pipelined változat ezen felül a globális betöltést a számítás alá csúsztatja.

Input: A mátrix M sorral és N oszloppal, FP32 elemekkel. Output: B mátrix N sorral és M oszloppal, B[n, m] = A[m, n]. A teljes adatforgalom pontosan 2 * M * N * sizeof(float) byte, mert minden elemet egyszer olvasunk és egyszer írunk.

A kernelváltozatok vázlata CUDA C++-ban (C++17, nvcc):

#include <cuda_runtime.h>
#include <cstdio>
#include <cstdlib>

#define CHECK_CUDA(call)                                                       \
  do {                                                                         \
    cudaError_t err = call;                                                    \
    if (err != cudaSuccess) {                                                  \
      std::fprintf(stderr, "CUDA error at %s:%d: %s\n", __FILE__, __LINE__,    \
                   cudaGetErrorString(err));                                   \
      std::exit(EXIT_FAILURE);                                                 \
    }                                                                          \
  } while (0)

constexpr int TILE_DIM = 32;

// 1. Naive: global memory only
__global__ void transpose_naive(const float* A, float* B, int M, int N) {
    int x = blockIdx.x * blockDim.x + threadIdx.x;
    int y = blockIdx.y * blockDim.y + threadIdx.y;
    if (x < N && y < M) {
        B[x * M + y] = A[y * N + x]; // one side is uncoalesced
    }
}

// 2. Tiled: shared memory with padding
__global__ void transpose_tiled(const float* A, float* B, int M, int N) {
    __shared__ float tile[TILE_DIM][TILE_DIM + 1]; // padding avoids bank conflicts

    int x = blockIdx.x * TILE_DIM + threadIdx.x;
    int y = blockIdx.y * TILE_DIM + threadIdx.y;

    if (y < M && x < N) {
        tile[threadIdx.y][threadIdx.x] = A[y * N + x];
    }
    __syncthreads();

    x = blockIdx.y * TILE_DIM + threadIdx.x;
    y = blockIdx.x * TILE_DIM + threadIdx.y;

    if (y < N && x < M) {
        B[y * M + x] = tile[threadIdx.x][threadIdx.y]; // shared load, transposed
    }
}

A harmadik változat a cuda::pipeline API-t használja. A cél: amíg a blokk az aktuális shared memória csempét transzponálja, a következő csempe globális betöltése már folyamatban van. A vázlat:

#include <cuda_pipeline.h>

__global__ void transpose_pipelined(const float* A, float* B, int M, int N) {
    extern __shared__ float smem[];
    constexpr int TILE = 32;
    // two shared buffers with padding
    float* buf0 = smem;
    float* buf1 = smem + TILE * (TILE + 1);

    auto pipe = cuda::make_pipeline();

    int tile_x = blockIdx.x * TILE;
    int tile_y = blockIdx.y * TILE;

    // simplified: first stage global -> shared for buf0
    if (threadIdx.x < TILE && threadIdx.y < TILE) {
        int src_x = tile_x + threadIdx.x;
        int src_y = tile_y + threadIdx.y;
        if (src_y < M && src_x < N) {
            cuda::memcpy_async(block, buf0 + threadIdx.y * (TILE + 1) + threadIdx.x,
                               A + src_y * N + src_x, sizeof(float), pipe);
        }
    }
    pipe.producer_commit();
    pipe.consumer_wait();

    // transpose and write buf0, while loading buf1 asynchronously
    // ... (full implementation in lab)
}

A valós laboranyagban a pipeline teljes producer–consumer logikája megtalálható; itt a lényeg az, hogy a cuda::memcpy_async a globális memóriából a shared memóriába másolást a memória-utasítás szintjén aszinkron módon hajtja végre, és a producer_commit/consumer_wait szinkronizálja a fázisokat. A cp.async használatához compute capability 8.0 vagy újabb szükséges; régebbi hardveren a pipeline nem elérhető, ezért a laborkörnyezetben ellenőrizni kell a cudaDeviceProp::asyncEngineCount és a compute capability értékét.

A launch konfiguráció mindhárom kernelnél:

  • Naiv: dim3 block(32, 32, 1), grid: ((N + 31)/32, (M + 31)/32, 1).
  • Tiled: ugyanaz, de a tile méret TILE_DIM; a block dimenzió TILE_DIM x TILE_DIM.
  • Pipelined: ugyanaz, de a shared memória mérete 2 * TILE_DIM * (TILE_DIM + 1) * sizeof(float) byte.

A grid- és blockdimenziót minden mérési jegyzőkönyvben rögzíteni kell.

14.4.3 3. Mérési protokoll és Nsight-alapú vizsgálat

A mérésekhez rögzített környezet:

  • GPU: például NVIDIA A100 40 GB (helyőrző; a tényleges modellt a laborban kell beírni)
  • Driver: 535.xx (helyőrző)
  • CUDA Toolkit: 12.2
  • Compute capability: 8.0
  • Operációs rendszer: Ubuntu 22.04 LTS
  • Power limit: 400 W, ECC: bekapcsolva
  • MIG: nincs, virtualizáció: nincs

A kód build parancsa:

nvcc -O3 -std=c++17 -arch=sm_80 -o transpose_lab transpose_lab.cu

A futtatás előtt ellenőrizzük a hibákat, majd a mérési kernelt hívjuk:

./transpose_lab --m 8192 --n 8192 --repeat 10

A Nsight Compute profilozás parancsa egy adott kernelre:

ncu --set full --launch-count 1 --kernel-id ::transpose_tiled ./transpose_lab --m 8192 --n 8192

Célzott metrikák lekérdezése:

ncu --metrics gld_transactions,gst_transactions,l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum,sm__warps_active.avg.pct_of_peak_sustained_active,dram__bytes.sum ./transpose_lab --m 8192 --n 8192

A mérési naplóban külön oszlopban szerepeljen a várt (elméleti) érték és a mért érték. A várt értékeket a memóriamodellből, a tranzakciószámításból és az occupancy-előrejelzésből becsüljük, a mért értékeket pedig a Nsight-riportból vagy a saját timerből nyerjük.

Példa várt értékek:

  • Naiv globális tranzakciók: A transzponálásnál az egyik oldal nem koaleszkált. Egy 32 byte-os szektorral, FP32 elemekkel a naiv kernel minden második vagy negyedik szektort érinthet, ezért a globális load/store tranzakciók száma lényegesen magasabb, mint a minimális M*N/8 (ha 32 byte = 8 float). A pontos érték a hozzáférési mintától függ, de a tiled kernelhez képest többszörös tranzakciószám várható.
  • Tiled globális tranzakciók: Koaleszkált hozzáféréssel minden 32 byte-os szektor pontosan egyszer érintett: gld_transactions ≈ M*N/8, gst_transactions ≈ N*M/8.
  • Bankütközések: A TILE_DIM+1 padding miatt a shared memória olvasásnál a bankütközések száma közel nulla. Padding nélkül 32x32-es csempénél a transzponált olvasás 32-way bank conflictot okozna.
  • DRAM forgalom: Mindhárom kernelnél 2 * M * N * 4 byte, mert az alkalmazás minden elemet egyszer mozgat. A tiling nem csökkenti a teljes DRAM forgalmat, csak a tranzakciók számát és a késleltetést.
  • Sávszélesség: sávszélesség = 2 * M * N * 4 / (futásidő * 1e9) GB/s. A tiled kernelnek közelítenie kell a GPU memória-sávszélességének 80–90%-ához.

A mérési napló egy sora például:

Változat Tile Block Futásidő (µs) Szórás Sávszélesség (GB/s) gld_transactions Bank conflict Occupancy
naive – 32x32 mérendő mérendő mérendő mérendő – mérendő
tiled 32x32 32x32 mérendő mérendő mérendő mérendő mérendő mérendő

A várt értékeket a szövegben a fenti becslések adják, a mért értékeket a laborban kell rögzíteni. Fontos, hogy a mérési naplóban a várt és mért értékek elkülönüljenek, és a becslés képlete is szerepeljen.

14.4.4 4. Eredmények értelmezése: Nsight-metrikák és a hatásmechanizmus

A nyers futásidő önmagában keveset mond. A Nsight Compute metrikái megmutatják, miért változott a teljesítmény.

14.4.5 4.1. Globális memória tranzakciók

A gld_transactions és gst_transactions metrikák a ténylegesen végrehajtott globális memória tranzakciók számát adják. A naiv transzponálásnál az egyik oldal koaleszkálatlan, ezért egy warp 32 elemhez több 32 byte-os tranzakcióra van szükség. A tiled kernelben a shared memórián keresztül mindkét oldal koaleszkált: a betöltés soronként folyamatos, a kiírás is soronként folyamatos. A várt hatás a tranzakciószám drasztikus csökkenése.

A mérés során a gld_transactions és gst_transactions értékét összehasonlítva a tiled kernelnek közel a minimális M*N/8 értéket kell mutatnia. Ha a mért érték magasabb, akkor a hozzáférési minta nem optimális, vagy a grid méretezése miatt határfeltételek rontják a koaleszkálást.

14.4.6 4.2. Shared memory bankütközések

A tiled kernelnél a __shared__ float tile[TILE_DIM][TILE_DIM + 1] deklaráció a padding miatt elkerüli a bankütközést. A Nsight-ban a l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum metrika mutatja a shared memória olvasási bankütközéseit. Padding nélkül 32x32-es csempénél a transzponált olvasás során minden warp 32 thread-je ugyanabba a bankcsoportba ütközne, ami 32-szeres konfliktust jelent. A +1 oszlop eltolja a sorokat, így a konfliktus megszűnik.

A várt érték: paddinggel a bankütközések száma nulla vagy elhanyagolható. Ha a mért érték magas, akkor a paddinget elfelejtettük, vagy a tile méret és a bankek száma nem illeszkedik.

14.4.7 4.3. Occupancy és erőforrás-korlátok

Az sm__warps_active.avg.pct_of_peak_sustained_active metrika az aktív warpek arányát mutatja. A tiled kernel shared memóriát foglal: TILE_DIM * (TILE_DIM + 1) * 4 byte. 32x32-es tile esetén ez 32334 = 4224 byte blokkonként. A pipelined változat két puffert használ, így 8448 byte-ot. Egy A100 SM-en 164 KB shared memória áll rendelkezésre, ezért a shared memória nem korlátozza erősen az occupancyt. A regiszterhasználat azonban igen: ha a compiler túl sok regisztert rendel, az aktív warpek száma csökken.

A várt hatás: a tiled kernel occupancyje hasonló vagy kissé alacsonyabb a naiv kernelhez képest, de a csökkent memória-tranzakciók miatt a tényleges teljesítmény nő. A pipelined kernelben a double buffering miatt több shared memória kell, de a latency hiding javul, így a foglaltság csökkenése ellenére is gyorsabb lehet.

A mérésnél rögzíteni kell a regiszterhasználatot (launch__registers_per_thread) és a shared memória foglalást is, mert ezek magyarázzák az occupancyt.

14.4.8 4.4. DRAM forgalom és sávszélesség

A dram__bytes.sum metrika a tényleges DRAM-forgalmat mutatja. A várt érték mindhárom kernelnél azonos: 2 * M * N * 4 byte. Ha a mért érték ettől eltér, akkor a cache vagy a memória-hozzáférési minta extra forgalmat generál (például a határfeltételek miatt). A tiling és pipeline nem csökkenti a teljes forgalmat, csak a tranzakciók számát és a késleltetést.

A sávszélesség számítása a fenti képlettel történik. A naiv kernel sávszélessége alacsony, mert a koaleszkálatlan hozzáférések miatt a memória-vezérlő nem tudja kihasználni a burstöket. A tiled kernel sávszélessége megközelíti a memória-sávszélesség felső határát. A pipelined kernel tovább javíthatja a sávszélességet, mert a globális betöltés késleltetése el van rejtve, és a memória-vezérlő folyamatosan kap kéréseket.

14.4.9 4.5. A pipeline hatása: latency hiding

A cp.async pipeline lényege, hogy a globális memória kéréseket a számítással párhuzamosítja. A Nsight Compute-ben a smsp__average_warp_latency_per_inst_issued vagy a smsp__warp_issue_stalled_long_scoreboard_per_warp_active.pct metrika mutatja, mennyi időt töltenek a warpek memória-várakozással. A pipelined kernelben ennek az értéknek csökkennie kell a tiled kernelhez képest, mert a consumer nem közvetlenül a globális load után vár, hanem a már megérkezett shared pufferen dolgozik.

A várt eredmény: a pipelined kernel futásideje alacsonyabb, a memória-várakozási idő csökken, a sávszélesség pedig közelebb kerül a csúcshoz. Ha a csökkenés nem jelentkezik, akkor a pipeline szinkronizációja helytelen, vagy a blokk túl kevés munkát végez ahhoz, hogy a betöltés elrejthető legyen.

14.4.10 5. Tileméret-hangolás

A tile méretének megválasztása közvetlenül befolyásolja a shared memória foglalást, a bankütközéseket, az occupancyt és a határfeltételek kezelését. A hangolást méréssorozattal végezzük, ahol a tile méretet változtatjuk, és minden konfigurációra rögzítjük a fenti metrikákat.

Gyakori tile méretek FP32 transzponálásnál:

  • 8x8: kis shared memória, magas occupancy, de sok blokk és sok határfeltétel. A globális memória tranzakciók száma magasabb, mert a koaleszkálás rövidebb.
  • 16x16: 16174 = 1088 byte shared memória blokkonként. Jó egyensúly, de a bankütközések elkerülhetők paddinggel.
  • 32x32: 32334 = 4224 byte. A legtöbb GPU-n ez a standard választás, mert a warp méret (32) illeszkedik a sorhosszhoz, és a koaleszkálás optimális.
  • 64x64: 64654 = 16640 byte. Magas shared memória igény, alacsonyabb occupancy, de kevesebb blokk és határfeltétel. Nagy mátrixoknál előnyös lehet, de a latency hiding romolhat.

A mérési sorozat:

for tile in 8 16 32 64; do
    ./transpose_lab --m 8192 --n 8192 --tile $tile --repeat 10
done

A kapott futásidőket, sávszélességeket és occupancyket táblázatba foglaljuk. A várt trend: a 32x32-es tile közel optimális. A 64x64-es tile esetén a sávszélesség csökkenhet, mert az occupancy alacsonyabb, és a latency hiding kevésbé hatékony. A 8x8-as tile esetén a sok blokk overheadje és a rövidebb koaleszkált szegmensek rontják a teljesítményt.

A pipelined kernelnél a tile méret mellett a shared memória pufferek száma is hangolható. A double bufferinghez két puffer kell; ha a tile túl nagy, a pufferek kiszoríthatják a blokkokat az SM-ből, így az occupancy drasztikusan csökken. A mérés során a cudaFuncSetAttribute segítségével növelhetjük a shared memória limitet, de figyelni kell a maximális kapacitásra.

A hangolás eredményét a következő táblázatban rögzítjük (várt és mért külön):

Tile Shared memória/block (byte) Regiszter/thread Occupancy (várt) Sávszélesség (várt) Sávszélesség (mért)
8x8 894=288 mérendő magas közepes mérendő
16x16 16174=1088 mérendő magas jó mérendő
32x32 32334=4224 mérendő közepes/magas legjobb mérendő
64x64 64654=16640 mérendő alacsony csökkenő mérendő

A mért értékeket a Nsight és a saját timer alapján kell kitölteni. A várt occupancyt a cudaOccupancyMaxActiveBlocksPerMultiprocessor API-val előre lehet becsülni; a laborban ezt is érdemes lefuttatni.

14.4.11 6. Tipikus hibák és elhárításuk

14.4.12 6.1. Nem ellenőrzött környezet

Hiba: a mérés közben a GPU órajele változik, thermal throttling lép fel, vagy más folyamat terheli a GPU-t. A kapott eredmény nem reprodukálható.

Megoldás: mérés előtt és után nvidia-smi --query-gpu=clocks.sm,clocks.mem,power.draw,temperature.gpu --format=csv rögzítése. Ha throttlingot látunk, csökkentsük a mérés időtartamát, vagy alkalmazzunk hűtési szünetet. Többfelhasználós környezetben használjunk MIG-et vagy kérjünk dedikált GPU-időt.

14.4.13 6.2. Túl kicsi input

Hiba: a mátrix mérete kicsi, a kernelindítási overhead dominál, a tiling hatása nem mérhető.

Megoldás: legalább 4–8 MB adatot használjunk. 8192x8192 FP32 mátrix 256 MB, ami elegendő. Ha a memória korlátozott, válasszunk 4096x4096-ot, de ne menjünk 512x512 alá.

14.4.14 6.3. Csak egy mérés

Hiba: egyetlen futásidőt rögzítünk, a zajt nem szűrjük.

Megoldás: warm-up után legalább 10 ismétlés, átlag és szórás közlése. A szórás nagy értéke (pl. >5%) környezeti problémára utal.

14.4.15 6.4. Bankütközés figyelmen kívül hagyása

Hiba: a tiled kernelben __shared__ float tile[TILE_DIM][TILE_DIM] deklarációt használunk padding nélkül. A 32x32-es transzponált olvasás 32-way bank conflictot okoz, és a tiling előnye elvész.

Megoldás: mindig TILE_DIM + 1 oszlopot használjunk, vagy cudaFuncSetAttribute-tel állítsuk be a shared memória méretét úgy, hogy a sorok eltolása biztosított legyen. A Nsight bankütközés-metrikájával ellenőrizzük.

14.4.16 6.5. A cp.async pipeline helytelen szinkronizációja

Hiba: a cuda::pipeline producer és consumer fázisainak sorrendje hibás, például a consumer_wait előtt a shared puffert olvassuk, vagy a puffert felülírjuk, mielőtt a consumer végzett volna. Ez versenyhelyzetet okoz.

Megoldás: kövessük a pipeline API szabályait. A producer oldal a cuda::memcpy_async hívás után producer_commit-ot hajt végre; a consumer oldal consumer_wait-tel vár a másolás befejezésére, majd consumer_release-szel jelzi, hogy a puffer felszabadult. A shared memória puffereket két külön bufferre osztjuk, és a blokk-szintű __syncthreads-eket a fázisok között elhelyezzük. A full implementation a laborban található; itt a hibás minta:

// HIBÁS: nincs producer_commit, a consumer azonnal olvas
cuda::memcpy_async(block, buffer, source, bytes, pipe);
__syncthreads();
use(buffer); // lehet, hogy a másolás még nem fejeződött be

A helyes minta:

cuda::memcpy_async(block, buffer, source, bytes, pipe);
pipe.producer_commit();
pipe.consumer_wait();
__syncthreads();
use(buffer);
pipe.consumer_release();

14.4.17 6.6. Túl nagy tile, alacsony occupancy

Hiba: a 64x64-es tile csökkenti az aktív blokkok számát, a latency hiding romlik, és a kernel lassabb lesz.

Megoldás: mérjük az occupancyt, és a regiszterhasználatot (--maxrregcount vagy launch bounds) hangoljuk. Ha a shared memória a korlát, csökkentsük a tile méretet, vagy használjunk kisebb puffert a pipeline-ban. A cél az, hogy legalább 2–4 blokk aktív legyen SM-enként, hogy a warpütemező elrejthesse a memória-késleltetést.

14.4.18 7. Labor: Nsight-alapú elemzés

A labor célja, hogy a fenti három kernelváltozatot saját környezetben lefuttassa, és a mérési naplót Nsight-metrikákkal töltse ki. A kódot a mellékelt transpose_lab.cu tartalmazza; a fordítás és futtatás parancsai:

nvcc -O3 -std=c++17 -arch=sm_80 -o transpose_lab transpose_lab.cu
./transpose_lab --m 8192 --n 8192 --repeat 10

A Nsight Compute futtatás:

ncu --set full --launch-count 1 --kernel-id ::transpose_naive ./transpose_lab --m 8192 --n 8192
ncu --set full --launch-count 1 --kernel-id ::transpose_tiled ./transpose_lab --m 8192 --n 8192
ncu --set full --launch-count 1 --kernel-id ::transpose_pipelined ./transpose_lab --m 8192 --n 8192

A mérési naplóban rögzíteni kell:

  • GPU-modell, driver, CUDA-verzió, compute capability, operációs rendszer, power limit, ECC/MIG állapot.
  • A három kernel futásideje, szórása, sávszélessége.
  • A Nsight-ből: gld_transactions, gst_transactions, dram__bytes.sum, l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum, sm__warps_active.avg.pct_of_peak_sustained_active, regiszter/thread, shared memória/block.
  • A várt értékeket a fenti becslésekkel, a mért értékeket a kísérletből.

A labor átadandó dokumentuma egy rövid jelentés, amelyben a mért és várt értékeket táblázatban összeveti, és legalább egy Nsight-képernyőképet vagy riportrészletet mellékel. A jelentésben válaszolni kell a kérdésre: Miért nő a sávszélesség a tiled kernelnél, ha a DRAM-forgalom azonos? A válasz: a koaleszkált hozzáférések miatt a memória-vezérlő hatékonyabban használja a burstöket, és a tranzakciók száma csökken, így ugyanannyi byte mozgatása kevesebb időt vesz igénybe. A pipelined kernel pedig a globális memória késleltetését rejti el, így a memória-vezérlő folyamatosan telített.

Megjegyzés: A fenti parancsok és a kódvázlat szemléltető jellegű; a laborban a tényleges GPU-paramétereket és a mérési naplót a hallgatónak kell rögzítenie. A cp.async pipeline használatához compute capability 8.0+ szükséges; ha a labor GPU-ja régebbi, a pipeline részt ki kell hagyni, és a mérési jegyzőkönyvben ezt jelezni kell.

14.4.19 8. Összefoglalás és önellenőrző kérdés

A tiling és a pipeline hatásának mérése akkor értékes, ha a futásidő mellett a memória-tranzakciókat, a bankütközéseket, az occupancyt és a sávszélességet is vizsgáljuk. A mátrix transzponálás példáján a naiv, tiled és pipelined változat összehasonlítása megmutatja: a tiling a tranzakciók számát csökkenti, a pipeline a késleltetést rejti el, a tileméret pedig az erőforrás-korlátokon keresztül hangolja az optimális pontot.

Önellenőrző kérdés: Miért csökken a globális memória tranzakciók száma a tiled transzponálásnál, és miért nem csökken a DRAM-forgalom? Válaszát a Nsight-metrikák alapján indokolja.

A következő fejezet (L1 és L2 cache) a cache-ekre, az L2 persistence-re és a memóriamodellekre épít; az itt megismert mérési protokoll és a Nsight-metrikák ott is alapvető eszköztárként szolgálnak.
