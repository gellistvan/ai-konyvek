18.3 PDE és iteratív megoldók

A parciális differenciálegyenletek (PDE-k) diszkretizálása gyakran nagy, ritka lineáris egyenletrendszerekhez vezet: Ax = b, ahol A ritka mátrix, b a peremfeltételekből és forrástagból származó vektor. A direkt megoldók (pl. LU-felbontás) a feltöltődés miatt GPU-n általában nem hatékonyak, ezért iteratív módszereket használunk. Ebben az egységben három alapvető iteratív megoldót tárgyalunk: a Jacobi-, a Gauss–Seidel- és a konjugált gradiens (CG) módszert, kiemelve a GPU-s megvalósításukat, a konvergencia és reziduál szerepét, valamint a prekondicionálás alapjait. Az előző egységben (Halo-csere és többblokkos stencil) bevezetett stencil-számítás adja a mátrix-vektor szorzás magját; itt erre építünk.

Jacobi-iteráció GPU-n

A Jacobi-módszer a legegyszerűbb iteratív megoldó. A lineáris egyenletrendszert komponensenként frissítjük: xi(k+1)=bi−∑j≠iaijxj(k)aii. x_i^{(k+1)} = \frac{b_i - \sum_{j \neq i} a_{ij} x_j^{(k)}}{a_{ii}}. Mivel minden új xix_i csak az előző iteráció xjx_j értékeitől függ, a módszer természetesen párhuzamos: minden komponens egyszerre frissíthető. Ez ideális GPU-ra.

A stencil-számításnál az A mátrix implicit, tipikusan egy 5-pontos Laplace-operátor 2D rács esetén. A frissítési képlet egy súlyozott átlag: xi,j(k+1)=bi,j+c(xi−1,j(k)+xi+1,j(k)+xi,j−1(k)+xi,j+1(k))c0, x_{i,j}^{(k+1)} = \frac{b_{i,j} + c\left(x_{i-1,j}^{(k)} + x_{i+1,j}^{(k)} + x_{i,j-1}^{(k)} + x_{i,j+1}^{(k)}\right)}{c_0}, ahol cc a rácsállandó, c0c_0 a diagonális elem. A kernel minden belső rácspontra kiszámítja az új értéket. Fontos, hogy a Jacobi nem in-place: külön forrás- és céltömb kell, mert a szomszédok régi értékeit használjuk. A dupla buffer technikát alkalmazzuk: két tömböt allokálunk, és iterációnként cseréljük a mutatókat.

A GPU-s kernel egy egyszerű 2D indexeléssel dolgozik. A határpontokat (peremfeltételek) nem frissítjük, azokat külön kezeljük (pl. konstans érték). A kernel egy block/grid konfigurációt használ, például 16×16-os blokkok és a rácsméretnek megfelelő grid. A frissítéshez nincs szükség globális szinkronizációra, mert a kernel csak olvassa a régi tömböt; a kernel végén a __syncthreads() csak a blokkon belüli megosztott memória esetén kell, de ha minden szál globális memóriát olvas, nincs szükség szinkronizációra. A kernel befejezése után a host oldalon cudaDeviceSynchronize() biztosítja, hogy a következő iteráció csak a teljes frissítés után induljon.

A reziduál kiszámításához egy külön redukciós kernel szükséges, amely kiszámítja az ∥r∥2\|r\|_2 normát. Ezt lehet minden iterációban vagy ritkábban (pl. minden 10. iterációban) elvégezni a konvergencia ellenőrzésére. A redukciót a könyv korábbi fejezete (Redukciók) tárgyalja, itt csak felhasználjuk.

A Jacobi-módszer konvergenciájának feltétele a mátrix szigorú diagonális dominanciája vagy bizonyos speciális tulajdonságok. A Laplace-operátor diszkretizációja rendelkezik ezzel, ezért a Jacobi konvergál, bár lassan. A konvergencia sebessége a spektrálsugártól függ: minél közelebb van 1-hez, annál lassabb. A rácsfelbontás növelésével a konvergencia romlik, ezért nagy feladatoknál a Jacobi önmagában ritkán hatékony, de alapul szolgál a gyorsabb módszerekhez.

Kódpélda (Jacobi kernel)

A következő CUDA C++ kód szemlélteti a Jacobi-iteráció magját egy 2D Poisson-egyenletre. A kód a könyv laborjában futtatható; a hibakezelés és a mérés a későbbi laborleírásban szerepel.

// jacobi_kernel.cu (CUDA C++17, nvcc)
__global__ void jacobi_step(const double* __restrict__ u_old,
                            double* __restrict__ u_new,
                            const double* __restrict__ f,
                            int nx, int ny, double dx2, double dy2) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    int j = blockIdx.y * blockDim.y + threadIdx.y;
    if (i >= 1 && i < nx-1 && j >= 1 && j < ny-1) {
        int idx = j * nx + i;
        double inv_diag = 1.0 / (2.0/dx2 + 2.0/dy2);
        double sum = (u_old[idx-1] + u_old[idx+1]) / dx2
                   + (u_old[idx-nx] + u_old[idx+nx]) / dy2;
        u_new[idx] = inv_diag * (f[idx] + sum);
    }
}

A kernel a belső pontokat frissíti; a határpontokat a peremfeltétel szerint állítjuk be (pl. nullára). A dupla buffert a host oldalon kezeljük: két tömb, u0 és u1, minden iterációban felváltva. A konvergencia ellenőrzéséhez a reziduált egy másik kernelben számoljuk.

Gauss–Seidel GPU-n

A Gauss–Seidel (GS) módszer a Jacobihoz hasonló, de a frissítés során már az új értékeket használja: xi(k+1)=bi−∑j<iaijxj(k+1)−∑j>iaijxj(k)aii. x_i^{(k+1)} = \frac{b_i - \sum_{j<i} a_{ij} x_j^{(k+1)} - \sum_{j>i} a_{ij} x_j^{(k)}}{a_{ii}}. Ez a módszer sorosnak tűnik, mert az ii-edik komponens frissítése függ a korábbi komponensek új értékétől. A természetes rendezésben a párhuzamosítás nehéz. Azonban a rácsos szerkezetű mátrixoknál (pl. 2D Laplace) alkalmazható a red-black (piros-fekete) rendezés. A rácspontokat két színre osztjuk, mint egy sakktábla: a piros pontoknak csak fekete szomszédai vannak, és fordítva. Ekkor a piros pontok frissítésekor csak a fekete pontok régi értékeit használjuk, a fekete pontok frissítésekor pedig a piros pontok új értékeit. Így két fél-iterációban párhuzamosan frissíthető az összes azonos színű pont.

A red-black GS kernel két kernelből áll (vagy egy kernelből, amely a szín alapján választ). A következő kód a fekete pontok frissítését mutatja; a piros hasonló, csak a feltétel változik.

__global__ void gs_black_step(const double* __restrict__ u,
                              double* __restrict__ u_new,
                              const double* __restrict__ f,
                              int nx, int ny, double dx2, double dy2) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    int j = blockIdx.y * blockDim.y + threadIdx.y;
    if (i >= 1 && i < nx-1 && j >= 1 && j < ny-1) {
        // fekete pont: (i+j) % 2 == 0
        if ((i + j) % 2 == 0) {
            int idx = j * nx + i;
            double inv_diag = 1.0 / (2.0/dx2 + 2.0/dy2);
            double sum = (u_new[idx-1] + u_new[idx+1]) / dx2
                       + (u_new[idx-nx] + u_new[idx+nx]) / dy2;
            u_new[idx] = inv_diag * (f[idx] + sum);
        }
    }
}

Itt u_new már tartalmazza a piros pontok frissített értékeit, mert a piros kernel előbb futott. Fontos, hogy a két kernel között nincs globális szinkronizáció, de a kernelindítások sorrendje garantálja a memória láthatóságát (a CUDA streamben a kernelindítások sorrendben hajtódnak végre, és a memória írások láthatóvá válnak a következő kernel számára). A red-black GS jellemzően gyorsabban konvergál, mint a Jacobi, de a párhuzamosítási foka fele akkora, mert egyszerre csak a pontok fele frissül. A gyakorlatban a GS-t gyakran használják simítóként multigrid módszerekben.

Konjugált gradiens (CG) GPU-n

A konjugált gradiens módszer szimmetrikus pozitív definit (SPD) mátrixokra hatékony. A PDE-kből származó mátrixok gyakran SPD-k (pl. Laplace-operátor). A CG egy Krylov-altér módszer, amely minden iterációban minimalizálja a hibát az A-normában. Az algoritmus:

  1. Inicializálás: r0=b−Ax0r_0 = b - Ax_0, p0=r0p_0 = r_0.
  2. Minden iterációban: αk=rkTrkpkTApk, \alpha_k = \frac{r_k^T r_k}{p_k^T A p_k}, xk+1=xk+αkpk, x_{k+1} = x_k + \alpha_k p_k, rk+1=rk−αkApk, r_{k+1} = r_k - \alpha_k A p_k, βk=rk+1Trk+1rkTrk, \beta_k = \frac{r_{k+1}^T r_{k+1}}{r_k^T r_k}, pk+1=rk+1+βkpk. p_{k+1} = r_{k+1} + \beta_k p_k.

A módszer elméletileg legfeljebb nn iterációban konvergál (nn a dimenzió), de a gyakorlatban sokkal kevesebb is elég, ha a mátrix jól kondicionált. A GPU-n a CG minden iterációja a következő műveleteket igényli: SpMV (ApkA p_k), dot (skaláris szorzatok), axpy (vektor frissítés) és normaszámítás. Ezek a műveletek hatékonyan párhuzamosíthatók, de a dot műveletek redukciót igényelnek, amelyek globális szinkronizációt okoznak. A CG GPU-s teljesítményét gyakran a redukciók költsége korlátozza.

A gyakorlatban a CG-t könyvtárakkal valósítjuk meg: a cuBLAS a sűrű vektorműveletekhez, a cuSPARSE a ritka mátrix-vektor szorzáshoz. A következő kódvázlat a cuSPARSE és cuBLAS használatát mutatja (a hibakezelést elhagyva a tömörség kedvéért, de a teljes laborban kötelező):

// PCG vázlat (CUDA C++17, cuBLAS + cuSPARSE)
cublasHandle_t cublasH;
cusparseHandle_t cusparseH;
// ... mátrix és vektorok allokálása ...
cusparseSpMV(cusparseH, CUSPARSE_OPERATION_NON_TRANSPOSE,
             &alpha, mat, p, &beta, Ap, CUSPARSE_MV_ALG_DEFAULT, buffer);
// r^T r: cublasDdot(cublasH, n, r, 1, r, 1, &rr)
// p^T Ap: cublasDdot(cublasH, n, p, 1, Ap, 1, &pAp)
// axpy: cublasDaxpy(cublasH, n, &alpha, p, 1, x, 1)
// ...

A saját kernel implementáció esetén az SpMV-t a stencil kernel adja, a dot-ot pedig a redukciós kernel. A redukciót a korábbi fejezetben bemutatott módon végezhetjük (pl. shared memory redukció, majd atomics a globális eredményre). A CG általában gyorsabban konvergál, mint a Jacobi vagy GS, főleg nagy kondíciószámú feladatoknál, de a prekondicionálás tovább javíthatja.

Reziduál és konvergencia

A reziduál rk=b−Axkr_k = b - A x_k az egyenletrendszer hibájának mértéke. Mivel a pontos megoldás xx ismeretlen, a hibát ek=x−xke_k = x - x_k nem tudjuk közvetlenül számolni, de a reziduál kiszámítható. A leállási kritérium általában a relatív reziduál normája: ∥rk∥/∥b∥<tol\|r_k\| / \|b\| < \text{tol}, ahol tol egy előírt tűrés, pl. 10−610^{-6}. A norma lehet 2-es, végtelen vagy más. A 2-es norma számítása redukciót igényel, ami költséges, ezért gyakran csak minden néhány iterációban ellenőrizzük.

A konvergencia sebessége függ a mátrix spektrális tulajdonságaitól. Jacobi esetén a konvergencia feltétele a mátrix szigorú diagonális dominanciája (vagy bizonyos feltételek). A GS általában gyorsabb, de hasonló feltételekkel. A CG konvergenciája a kondíciószámtól függ: a hiba csökkenése ≈κ−1κ+1\approx \frac{\sqrt{\kappa}-1}{\sqrt{\kappa}+1} szerint halad, ahol κ\kappa a kondíciószám. A prekondicionálás célja a kondíciószám csökkentése.

Numerikus pontosság: a reziduál számítása érzékeny a kerekítési hibákra. FP32-ben a reziduál stagnálhat, mert a lebegőpontos pontosság korlátozza a csökkentést. A PDE-megoldóknál általában FP64 ajánlott, különösen a konvergencia ellenőrzéséhez. Mixed precision is lehetséges: a mátrix-vektor szorzást FP32-ben végezzük, de a reziduált és a skaláris szorzatokat FP64-ben, így gyorsabb, de pontosabb. A laborban rögzíteni kell a használt pontosságot.

Preconditionálás

A prekondicionálás során egy olyan M mátrixot alkalmazunk, amely közelíti A-t, de könnyen invertálható, és az M^{-1}A kondíciószáma kisebb, mint A-é. A prekondicionált CG (PCG) algoritmusban a prekondicionálót a reziduálra alkalmazzuk: zk=M−1rkz_k = M^{-1} r_k. A legegyszerűbb a Jacobi prekondicionáló, ahol M = diag(A). Ez csak a diagonális elemmel való skálázást jelent, rendkívül olcsó és párhuzamos. A Jacobi prekondicionáló gyenge, de javíthat a konvergencián, ha a diagonális domináns.

Erősebb prekondicionálók: blokk-Jacobi, ahol a mátrixot kis blokkokra osztjuk, és minden blokkot pontosan invertálunk (pl. LU-felbontással a blokkon belül). Ez GPU-n hatékony lehet, mert a blokkok függetlenek. Az inkomplett LU (ILU) prekondicionáló népszerű CPU-n, de soros jellege miatt GPU-n nehéz; léteznek párhuzamos változatok (pl. szintű ILU), de a teljesítmény korlátozott. A sparse approximate inverse (SPAI) prekondicionáló mátrixot explicit módon közelíti A^{-1}-gyel, és az alkalmazása SpMV-vel történik, ami GPU-barát. A gyakorlatban gyakran használnak polinomiális prekondicionálókat vagy multigridet, de ezek túlmutatnak ezen a fejezeten.

A PCG algoritmusban a prekondicionáló alkalmazása egy extra művelet iterációnként. A következő kód a Jacobi prekondicionáló alkalmazását mutatja a PCG-ben:

// Jacobi preconditioner alkalmazása: z = M^{-1} r
__global__ void jacobi_precond(const double* __restrict__ r,
                               double* __restrict__ z,
                               const double* __restrict__ diag,
                               int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        z[i] = r[i] / diag[i];
    }
}

A prekondicionáló megválasztása kompromisszum: minél erősebb, annál több számítást igényel az alkalmazása, de annál kevesebb iteráció kell. A GPU-s környezetben a párhuzamosan alkalmazható prekondicionálók előnyösek.

Labor: Jacobi-iteráció implementálása

A labor célja egy 2D Poisson-egyenlet megoldása Jacobi-iterációval CUDA C++-ban, a konvergencia mérésével. Az alábbi leírás egy teljes, futtatható keretet ad; a hallgató feladata a kód lefuttatása, a mérési napló kitöltése és a várt/mért eredmények összehasonlítása.

Feladat: Oldjuk meg a −Δu=f-\Delta u = f egyenletet az egységnégyzeten, Dirichlet peremfeltétellel u=0u=0 a határon. A forrástag legyen f(x,y)=2π2sin(πx)sin(πy)f(x,y) = 2\pi^2 \sin(\pi x) \sin(\pi y), amelynek analitikus megoldása u(x,y)=sin(πx)sin(πy)u(x,y) = \sin(\pi x) \sin(\pi y). A diszkretizálás 5-pontos stencillel, n×nn \times n rács, a rácsállandó h=1/(n+1)h = 1/(n+1).

Hardver és szoftver környezet (példa, a hallgató a sajátját rögzíti): - GPU: NVIDIA GeForce RTX 3080, compute capability 8.6 - Driver: 535.104.05, CUDA Toolkit: 12.2 - OS: Ubuntu 22.04 LTS - Órajel: 1710 MHz (boost), power limit: 320 W, ECC: off, MIG: off - Háttérterhelés: nincs (izolált futtatás)

Kód: A következő program tartalmazza a Jacobi kernelt, a reziduál számítását, a hibakezelést és az időmérést. A kód a könyv laborjában futtatható; az itt bemutatott változat nem tekinthető futtatottnak, amíg a hallgató nem hajtja végre.

// jacobi_lab.cu (CUDA C++17, nvcc)
#include <cuda_runtime.h>
#include <cstdio>
#include <cmath>
#include <chrono>

#define CUDA_CHECK(call) do { \
    cudaError_t err = call; \
    if (err != cudaSuccess) { \
        fprintf(stderr, "CUDA error %s:%d: %s\n", __FILE__, __LINE__, \
                cudaGetErrorString(err)); \
        cudaDeviceReset(); \
        exit(EXIT_FAILURE); \
    } \
} while (0)

__global__ void jacobi_step(const double* __restrict__ u_old,
                            double* __restrict__ u_new,
                            const double* __restrict__ f,
                            int n, double inv_h2) {
    int i = blockIdx.x * blockDim.x + threadIdx.x + 1;
    int j = blockIdx.y * blockDim.y + threadIdx.y + 1;
    if (i < n+1 && j < n+1) { // belső pontok: 1..n
        int idx = j * (n+2) + i;
        double inv_diag = 0.25 * h * h; // mivel 4/h^2 a diagonál
        double sum = (u_old[idx-1] + u_old[idx+1] + u_old[idx-(n+2)] + u_old[idx+(n+2)]) * inv_h2;
        u_new[idx] = (f[idx] + sum) * inv_diag;
    }
}

__global__ void residual_norm(const double* __restrict__ u,
                              const double* __restrict__ f,
                              const double* __restrict__ b,
                              double* __restrict__ partial,
                              int n, double inv_h2) {
    // A = 4/h^2 a diagonál, -1/h^2 a szomszédok
    int i = blockIdx.x * blockDim.x + threadIdx.x + 1;
    int j = blockIdx.y * blockDim.y + threadIdx.y + 1;
    double local = 0.0;
    if (i < n+1 && j < n+1) {
        int idx = j * (n+2) + i;
        double Au = 4.0 * inv_h2 * u[idx] - inv_h2 * (u[idx-1] + u[idx+1] + u[idx-(n+2)] + u[idx+(n+2)]);
        double r = b[idx] - Au;
        local = r * r;
    }
    // block redukció
    __shared__ double sdata[256];
    int tid = threadIdx.x + threadIdx.y * blockDim.x;
    sdata[tid] = local;
    __syncthreads();
    for (int s = blockDim.x * blockDim.y / 2; s > 0; s >>= 1) {
        if (tid < s) sdata[tid] += sdata[tid + s];
        __syncthreads();
    }
    if (tid == 0) atomicAdd(partial, sdata[0]);
}

int main(int argc, char** argv) {
    int n = 1024; // belső pontok száma egy irányban
    double tol = 1e-6;
    if (argc > 1) n = atoi(argv[1]);
    if (argc > 2) tol = atof(argv[2]);
    double h = 1.0 / (n + 1);
    double inv_h2 = 1.0 / (h * h);

    // Allokáció
    size_t size = (n + 2) * (n + 2) * sizeof(double);
    double *d_u0, *d_u1, *d_f, *d_b, *d_partial;
    CUDA_CHECK(cudaMalloc(&d_u0, size));
    CUDA_CHECK(cudaMalloc(&d_u1, size));
    CUDA_CHECK(cudaMalloc(&d_f, size));
    CUDA_CHECK(cudaMalloc(&d_b, size));
    CUDA_CHECK(cudaMalloc(&d_partial, sizeof(double)));

    // Inicializálás (host oldalon, majd másolás)
    // ... (a laborban a hallgató tölti ki, pl. f = 2π² sin(πx) sin(πy), b = f)
    // ...

    // Launch konfiguráció
    dim3 block(16, 16);
    dim3 grid((n + block.x - 1) / block.x, (n + block.y - 1) / block.y);

    // Iteráció
    double *u_old = d_u0, *u_new = d_u1;
    int max_iter = 10000;
    double res_norm = 1.0;
    int iter = 0;
    auto start = std::chrono::high_resolution_clock::now();
    for (iter = 0; iter < max_iter && res_norm > tol; ++iter) {
        jacobi_step<<<grid, block>>>(u_old, u_new, d_f, n, inv_h2);
        CUDA_CHECK(cudaGetLastError());
        // reziduál számítás minden 50. iterációban
        if (iter % 50 == 0) {
            CUDA_CHECK(cudaMemset(d_partial, 0, sizeof(double)));
            residual_norm<<<grid, block>>>(u_old, d_f, d_b, d_partial, n, inv_h2);
            CUDA_CHECK(cudaGetLastError());
            double partial;
            CUDA_CHECK(cudaMemcpy(&partial, d_partial, sizeof(double), cudaMemcpyDeviceToHost));
            res_norm = sqrt(partial);
            // normáljuk ||b||-vel
            // ...
        }
        // csere
        std::swap(u_old, u_new);
    }
    CUDA_CHECK(cudaDeviceSynchronize());
    auto end = std::chrono::high_resolution_clock::now();
    double elapsed = std::chrono::duration<double>(end - start).count();

    printf("Iterációk: %d, reziduál: %e, idő: %f s\n", iter, res_norm, elapsed);

    CUDA_CHECK(cudaFree(d_u0));
    CUDA_CHECK(cudaFree(d_u1));
    CUDA_CHECK(cudaFree(d_f));
    CUDA_CHECK(cudaFree(d_b));
    CUDA_CHECK(cudaFree(d_partial));
    return 0;
}

A fenti kódban a b vektor a forrástag, mert a stencil jobb oldala ff. A peremfeltételek miatt a határpontokon u=0u=0, ezért azokat nem kell frissíteni. A laborban a d_b-t inicializáljuk ff-fel.

Buildparancs:

nvcc -O3 -arch=sm_86 -o jacobi_lab jacobi_lab.cu

A hallgató a saját GPU-architektúrájához igazítja az -arch kapcsolót.

Futtatási parancs:

./jacobi_lab 1024 1e-6

Mérési napló: A mérés előtt warm-up futtatás szükséges (pl. 2 iteráció), majd legalább 5–10 ismétlés. A naplóban rögzíteni kell az alábbi adatokat: - GPU modell, driver, CUDA, compute capability, OS - Órajel, power limit, ECC, MIG, háttérterhelés - nn, tol, precision (FP64) - Minden ismétlés futási ideje, átlag, szórás - A reziduál értéke az utolsó iterációban - A várt eredmény (analitikus megoldás) és a mért eredmény összehasonlítása (pl. maximális eltérés a belső pontokon)

A mérési napló például így nézhet ki (a hallgató tölti ki a saját adataival):

Ismétlés Futásidő (s) Reziduál
1 12,34 9,8e-7
2 12,45 9,7e-7
… … …
Átlag 12,40 9,8e-7

Várt eredmény: A Jacobi-iterációnak konvergálnia kell a tűréshez. A konvergencia sebessége függ a rácsfelbontástól: nn növelésével a kondíciószám nő, ezért több iteráció kell. A reziduál csökkenése lineáris (log skálán közel egyenes). A mért megoldásnak közelítenie kell az analitikus megoldást; az eltérés a tűrés alatt kell legyen.

Tipikus hibák és megelőzésük

  1. Versenyhelyzet a halo-cserénél: Ha a Jacobi kernel nem dupla buffert használ, hanem in-place frissít, a szomszédok új értékeit olvashatja, ami a GS-hez hasonló viselkedést eredményez, de nem determinisztikus. Mindig dupla buffert használjunk, és a kernel végén ne feledkezzünk meg a mutatócseréről.

  2. Szinkronizáció hiánya: A kernelindítások közötti cudaDeviceSynchronize() elhagyása esetén a host oldali iteráció nem várja meg a GPU-t, és a mérés hamis lesz. A laborban minden iteráció után szinkronizáljunk, vagy használjunk streamet és eventet.

  3. Pontatlan FP32: A reziduál FP32-ben korán stagnálhat, és a megoldás nem éri el a kívánt pontosságot. Használjunk FP64-et a Jacobi-iterációhoz, vagy mixed precision esetén a reziduált FP64-ben számoljuk.

  4. Helytelen indexelés a határokon: A kernel feltételeinek pontosan meg kell határozniuk a belső pontokat. A határpontokat külön kell inicializálni, és nem szabad frissíteni.

  5. Redukció hibás blokkmérettel: A redukciós kernelben a shared memory méretét a blokk méretéhez kell igazítani, és a __syncthreads()-et minden lépésben hívni kell. A atomicAdd a részeredményekre biztosítja a helyes összegzést.

  4. Milyen prekondicionáló egyszerű és GPU-barát? Mi a hátránya?
