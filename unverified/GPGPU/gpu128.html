33.3 Optimalizálás és mérés

A záróprojekt ezen szakasza a Kernelimplementáció alfejezetben elkészült, funkcionálisan már helyes kernel teljesítményét veszi célba. A hangsúly nem az újabb funkciókon, hanem a mérésen, a profilkép értelmezésén és a hangolási döntések igazolásán van. A fejezet egy kis, ellenőrizhető 1D stencil kernelt használ, mert ezen a tiling, az occupancy és a stream-alapú átfedés hatása jól elkülöníthető, a numerikus ellenőrzés pedig triviális.

33.3.1 A teljesítmény hangolása mint mérésvezérelt folyamat

A teljesítmény hangolása nem azt jelenti, hogy „kipróbálunk néhány trükköt, és megnézzük, gyorsabb lett-e”. Ez egy irányított kísérleti ciklus:

  1. Baseline rögzítése: a jelenlegi változat futásideje, átbocsátóképessége, erőforrás-használata és környezeti paraméterei.
  2. Profilkép készítése: Nsight Compute vagy Nsight Systems segítségével megállapítjuk, hogy a kernel mire vár: memóriára, számításra, szinkronizációra vagy ütemezésre.
  3. Hipotézis: a profilkép alapján megfogalmazzuk, mi a szűk keresztmetszet, és milyen beavatkozás javíthat rajta.
  4. Beavatkozás: egyetlen változtatást hajtunk végre, például shared memory tilinget vezetünk be, módosítjuk a blokkméretet, vagy streamre bontjuk a feldolgozást.
  5. Mérés és döntés: a változtatást ugyanazon a bemeneten, azonos környezetben megmérjük; ha javult, megtartjuk, ha romlott, visszaállítjuk, és finomítjuk a hipotézist.

A folyamat legfontosabb eleme a mérés. GPU-n egyetlen futásidő nem bizonyíték: a boost-órajel, a hőmérséklet, a driver ütemezése és a háttérterhelés is torzíthat. Ezért minden állítást ismételt méréssel, szórással és rögzített környezettel kell alátámasztani.

Mielőtt bármit mérünk, rögzíteni kell a környezetet. A laborban használt minta-konfiguráció:

Ez a mező a tényleges eszközhöz igazítandó. A mérési jegyzőkönyvben akkor is szerepelnie kell, ha csak saját fejlesztőgépen dolgozunk.

33.3.3 Mérési protokoll

A kernel időmérésre a cudaEvent_t a legmegbízhatóbb, mert a GPU streamjén belül mér, és nem tartalmazza a host oldali std::chrono késleltetéseit. A minta:

cudaEvent_t start, stop;
CHECK(cudaEventCreate(&start));
CHECK(cudaEventCreate(&stop));

// Warm-up
for (int i = 0; i < 5; ++i) {
    stencil_naive<<<grid, block>>>(d_in, d_out, n);
}
CHECK(cudaDeviceSynchronize());

// Mérés: legalább 10 ismétlés
const int iters = 20;
CHECK(cudaEventRecord(start, 0));
for (int i = 0; i < iters; ++i) {
    stencil_naive<<<grid, block>>>(d_in, d_out, n);
}
CHECK(cudaEventRecord(stop, 0));
CHECK(cudaEventSynchronize(stop));

float elapsed_ms = 0.0f;
CHECK(cudaEventElapsedTime(&elapsed_ms, start, stop));
elapsed_ms /= iters;

Az átlag mellett a relatív szórást is közölni kell. Ha a szórás 5 %-nál nagyobb, akkor a mérés nem tekinthető stabilnak: ellenőrizni kell a boost-órajelet, a hőmérsékletet, a háttérfolyamatokat vagy a kernelben lévő nem determinisztikus műveleteket.

A sávszélességet mindig a tényleges adatmozgatásra számítjuk, nem a névleges csúcsértékre. Az 1D, 3 pontos stencil esetén a naiv kernel minden kimeneti elemhez 3 bemeneti olvasást és 1 kimeneti írást végez float pontossággal. Ez kimeneti elemenként (3 + 1) * 4 = 16 bájt. A tiled változat a halókból adódó kis többlettől eltekintve elemenként 1 olvasást és 1 írást végez, azaz (1 + 1) * 4 = 8 bájtot. A mérési jegyzőkönyvben mindkét adatot fel kell tüntetni, mert a „GB/s” csak így értelmezhető.

33.3.4 Tiling: a memóriaforgalom csökkentése

Az 1D stencil számítása:

out[i] = (in[i - 1] + in[i] + in[i + 1]) / 3.0f;

A naiv kernel közvetlenül a globális memóriából olvassa a három bemeneti elemet:

__global__ void stencil_naive(const float* __restrict__ in,
                              float* __restrict__ out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= n) return;

    float acc = 0.0f;
    for (int r = -RADIUS; r <= RADIUS; ++r) {
        int j = min(max(i + r, 0), n - 1);
        acc += in[j];
    }
    out[i] = acc / (2 * RADIUS + 1);
}

Itt minden bemeneti elemet három különböző szál is beolvas. Az L2 cache sokat elnyelhet, de a memóriaforgalom akkor is nagyobb a szükségesnél. A shared memory tiling lényege, hogy a blokk betölti a szükséges bemeneti tartományt a gyors on-chip memóriába, majd a belső számítások már onnan dolgoznak:

__global__ void stencil_tiled(const float* __restrict__ in,
                              float* __restrict__ out, int n) {
    extern __shared__ float s[];
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    int local = threadIdx.x + RADIUS;

    if (i < n) {
        s[local] = in[i];
    }

    if (threadIdx.x < RADIUS) {
        int left = blockIdx.x * blockDim.x - RADIUS + threadIdx.x;
        s[threadIdx.x] = (left >= 0) ? in[left] : in[0];

        int right = (blockIdx.x + 1) * blockDim.x + threadIdx.x;
        s[blockDim.x + RADIUS + threadIdx.x] =
            (right < n) ? in[right] : in[n - 1];
    }

    __syncthreads();

    if (i < n) {
        float acc = 0.0f;
        for (int r = -RADIUS; r <= RADIUS; ++r) {
            acc += s[local + r];
        }
        out[i] = acc / (2 * RADIUS + 1);
    }
}

A kernel indítása dinamikus shared memory-val:

const int block = 256;
const int shared_bytes = (block + 2 * RADIUS) * sizeof(float);
stencil_tiled<<<grid, block, shared_bytes>>>(d_in, d_out, n);

A __syncthreads() garantálja, hogy minden szál befejezte a shared memóriába írást, mielőtt bármelyik olvasná azt. A tiling itt azért hatékony, mert a 3 pontos stencil átfedő ablakokat használ: a blokk belső elemeit többször is felhasználjuk, de globális memóriából mindegyiket csak egyszer olvassuk be. A halókezelés a blokkhatároknál a szomszédos elemeket is elérhetővé teszi.

33.3.5 Bank conflict a tiled stencilben

A shared memóriás olvasás s[local - 1], s[local], s[local + 1] mintája szomszédos szálak esetén átfedő bankokat érint, ezért 2-way bank conflictot okozhat. Ez a jelen laborban nem domináns, mert a globális memóriaforgalom csökkenése nagyobb nyereséget ad, de Nsight Compute l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum metrikájával ellenőrizhető. Súlyosabb stencileknél érdemes a betöltést úgy átszervezni, hogy a szálak először a saját középső elemüket töltsék be, majd a szomszédos elemeket regiszterből vagy warp shuffle-lel cseréljék. A fejezet laborjában azonban a memóriaforgalom és az occupancy áll a középpontban.

33.3.6 Occupancy és launch paraméterek

A tiling önmagában nem elég, ha a kernel nem tud elég aktív warpot futtatni a késleltetés elrejtéséhez. Az occupancy azt mutatja meg, hogy az SM-en elérhető maximális warpszámhoz képest mennyi aktív warp van:

occupancy = aktív warpok / maximális warpok SM-enként

A korlátokat a regiszterhasználat és a shared memory adja. A példakódban a stencil_tiled block = 256 mérettel és shared_bytes = (256 + 2) * 4 = 1032 bájttal fut. Ha a fordító 32 regisztert használ szálanként, és az SM-enkénti regiszterkeret 65 536, akkor a regiszterkorlát:

65536 / (256 * 32) = 8 blokk

A shared memory korlátot 100 KB SM-enkénti kerettel számolva:

100 * 1024 / 1032 ≈ 99 blokk

A hardveres blokkszám-korlát és a warpszám-korlát is közbeszólhat, de ebben a példában a regiszterkorlát 8 blokkot enged, ami 8 × 8 = 64 aktív warp. Ha az SM maximális warpszáma 64, akkor az elméleti occupancy 100 %. Ez kedvező, de nem szabad vakon maximalizálni.

Az alacsonyabb occupancy nem mindig rossz. Ha egy kernel compute-bound, és a szálaknak több regiszterre van szükségük, a magas blokkszám miatti regiszterkiömlés (spill) drágább lehet, mint a kisebb foglaltság. Ilyenkor a __launch_bounds__ direktíva segíthet a fordítónak a regiszterhasználat korlátozásában:

__global__ __launch_bounds__(256, 2)
void stencil_tiled(...) { ... }

Ez azt mondja a fordítónak, hogy SM-enként legalább 2 blokkot szeretnénk futtatni. A nvcc ekkor úgy osztja el a regisztereket, hogy a cél elérhető legyen. A cudaOccupancyMaxActiveBlocksPerMultiprocessor API-val a futásidőben is lekérdezhetjük a tényleges foglaltságot:

int num_blocks_per_sm = 0;
CHECK(cudaOccupancyMaxActiveBlocksPerMultiprocessor(
    &num_blocks_per_sm, stencil_tiled, block, shared_bytes));

A laborban érdemes a blokkméretet 128, 256 és 512 között is megvizsgálni. A túl kicsi blokk növeli a halók relatív költségét, a túl nagy blokk csökkenti az ütemezési rugalmasságot, és a tail-effect miatt az utolsó blokk kihasználatlan lehet. A profilelemzőben a launch__occupancy_per_% vagy a Nsight Compute Occupancy szekciója megmutatja a tényleges értéket.

33.3.7 Streamek és átfedés

A záróprojekt gyakran nem egyetlen kernelből áll: host-device másolás, több kernel és utófeldolgozás is tartozik hozzá. Ha a host sorosan vár minden lépésre, a GPU kihasználatlan marad. A stream-ek segítségével a memóriamásolást és a kernelszámítást átfedhetjük.

Az 1D stencil streamesített változata a bemenetet négy darabra bontja, és minden darabhoz aszinkron másolást, kernelindítást és visszamásolást rendel:

const int num_chunks = 4;
const int chunk_size = n / num_chunks;
const int streams_count = 2;

cudaStream_t streams[streams_count];
for (int s = 0; s < streams_count; ++s) {
    CHECK(cudaStreamCreate(&streams[s]));
}

float* pinned_in = nullptr;
float* pinned_out = nullptr;
CHECK(cudaMallocHost(&pinned_in, n * sizeof(float)));
CHECK(cudaMallocHost(&pinned_out, n * sizeof(float)));

for (int c = 0; c < num_chunks; ++c) {
    int offset = c * chunk_size;
    cudaStream_t stream = streams[c % streams_count];

    CHECK(cudaMemcpyAsync(d_in + offset, pinned_in + offset,
                          chunk_size * sizeof(float),
                          cudaMemcpyHostToDevice, stream));

    stencil_tiled<<<(chunk_size + block - 1) / block,
                    block, shared_bytes, stream>>>(
        d_in + offset, d_out + offset, chunk_size);

    CHECK(cudaMemcpyAsync(pinned_out + offset, d_out + offset,
                          chunk_size * sizeof(float),
                          cudaMemcpyDeviceToHost, stream));
}

for (int s = 0; s < streams_count; ++s) {
    CHECK(cudaStreamSynchronize(streams[s]));
}

Fontos, hogy a host memória pinned (cudaMallocHost) legyen: a lapozható memóriából a DMA-motor nem tud aszinkron módon másolni. Az átfedés akkor működik, ha a másolások és a kernelek különböző streamekhez tartoznak, és a GPU-nak van szabad másoló és számító egysége. A Nsight Systems timeline nézete mutatja meg, hogy a H2D másolás, a kernel és a D2H másolás valóban átfed-e.

Ha csak egy streamet használunk, a hívások sorba állnak. A streames változat akkor hoz nyereséget, ha a másolási idő összemérhető a kernelidővel. Ha a kernel sokkal lassabb, mint a másolás, az átfedésből származó nyereség kicsi, és a több stream csak bonyolítja a kódot. Ezért ezt is méréssel kell igazolni.

33.3.8 Benchmark és összehasonlítás

A hangolás során minden változatot ugyanazzal a bemenettel, pontossággal és mérési protokollal kell összehasonlítani. A laborban az alábbi négy változatot érdemes megmérni:

Változat Rács Blokk Shared Regiszter Kernelidő Effektív sávszélesség Relatív Szórás
Naiv 262144 256 0 B 32 [mért] ms [mért] GB/s 1,0× [mért]
Tiled 262144 256 1032 B 32 [mért] ms [mért] GB/s [mért]× [mért]

A táblázatban a [mért] mezőket a labor során kell kitölteni. A „várt” becslést a memóriamodellből adhatjuk meg. Ha a bemenet N = 2^26 float elem, a naiv kernel N * 16 bájtot mozgat, a tiled pedig körülbelül N * 8 bájtot. Egy 400 GB/s effektív sávszélességet feltételezve a modell szerinti várt érték:

naiv:   2^26 * 16 / 400e9 ≈ 2,68 ms
tiled:  2^26 *  8 / 400e9 ≈ 1,34 ms

Ez a várt érték csak modellszámítás, nem ellenőrzött hardveres mérés. A laborban a tényleges mért értékek eltérhetnek a modelltől; az eltérés elemzése éppen a tanulási cél része. Ha a tiled változat mért értéke nem közelíti a becslést, akkor a profilkép alapján keresni kell az okot: lehet bank conflict, alacsony occupancy, vagy a halók miatti többlet.

33.3.9 Nsight-alapú optimalizálás

A Nsight Compute a kernelen belüli metrikákat mutatja meg. A laborban használt parancsok:

nvcc -O3 -arch=sm_89 -lineinfo stencil.cu -o stencil

# Teljes profil
ncu --set full --csv ./stencil --n 67108864 --block 256 > ncu_naive.csv

# Célzott mérés
ncu --section SpeedOfLight \
    --section Occupancy \
    --section MemoryWorkloadAnalysis \
    ./stencil --n 67108864 --block 256

A következő metrikákat érdemes figyelni:

  • gpu__time_duration.avg: a kernel átlagos futásideje.
  • sm__throughput.avg.pct_of_peak_sustained_elapsed: az SM-ek kihasználtsága a csúcsteljesítményhez képest.
  • l1tex__t_sectors_pipe_lsu_mem_global_op_ld.sum: a globális memóriából beolvasott 32 bájtos szektorok száma. A naiv és tiled változat között itt kell jelentős csökkenést látni.
  • l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum: shared memory bank conflict.
  • launch__occupancy_limit_shared_mem: a shared memory miatti occupancy korlát.
  • smsp__average_warp_latency_per_inst.ratio: átlagos warp-késleltetés.

A Nsight Systems a teljes alkalmazás idővonalát mutatja. A streames változat ellenőrzésére:

nsys profile --stats=true ./stencil --streams 2

Az elkészült report.nsys-rep fájlban a H2D, kernel és D2H sávok átfedése vizuálisan ellenőrizhető. Ha a sávok szorosan egymás után következnek, akkor az átfedés nem jött létre, és a memóriamásolás valószínűleg lapozható memóriából történik, vagy a stream szinkronizációs pontja sorosít.

33.3.10 Tipikus hibák és helyes megoldások

  1. Túl korai optimalizálás mérés nélkül.
    Hiba: valaki a kód első változatába azonnal beépíti a tilinget, az occupancy-hangolást és a streameket, de nem készít baseline-t.
    Helyes: először a naiv verziót mérjük meg, és a profilkép alapján döntünk.

  2. Csak a kernelidőt nézzük, a host-device másolást nem.
    Hiba: a kernel gyors, de a teljes alkalmazás lassú a sok cudaMemcpy miatt.
    Helyes: a mérési naplóban külön soroljuk fel a H2D, a kernel és a D2H időket.

  3. Az occupancy-t öncélként maximalizáljuk.
    Hiba: a regiszterhasználatot mesterségesen leszorítjuk, ami spillt okoz, csak hogy magasabb legyen az occupancy.
    Helyes: az occupancy-t a profilkép kontextusában értelmezzük. Ha a kernel memória-késleltetésre vár, akkor hasznos a magas foglaltság; ha számításkorlátos, akkor a kevesebb aktív warp is elég lehet.

  4. Bank conflict figyelmen kívül hagyása.
    Hiba: a tiled stencil szomszédos s[local - 1], s[local], s[local + 1] olvasása 2-way conflictot okoz, de ezt nem ellenőrizzük.
    Helyes: a Nsight Compute metrikájával mérjük, és szükség esetén a betöltési mintát vagy a paddinget módosítjuk.

  5. Nem elegendő ismétlés vagy hideg cache.
    Hiba: egyetlen futásból vonunk le következtetést.
    Helyes: warm-up után legalább 10 ismétlést mérünk, és közöljük a szórást.

  6. Változó órajel és hőmérséklet.
    Hiba: a GPU boost-órajele a mérés közben ingadozik, a mérési naplóban mégis állandó csúcsértékkel számolunk.
    Helyes: a mérés előtt rögzítjük a power limitet, az órajelet és a hőmérsékletet; szükség esetén nvidia-smi naplót készítünk.

  7. Stream esetén lapozható host memória.
    Hiba: cudaMalloc-cal foglalt host memóriából cudaMemcpyAsync-et hívunk, ami valójában szinkron másolásként viselkedik.
    Helyes: cudaMallocHost vagy cudaHostRegister használata.

  8. Nem ellenőrzött kernelhiba.
    Hiba: a kernel indítása után nem hívunk cudaGetLastError-t, és a mérési eredményt hibás kernelre is rögzítjük.
    Helyes: minden API-hívást ellenőrizni kell, a mérés előtt cudaDeviceSynchronize-et hívunk.

33.3.11 Labor: Nsight-alapú optimalizálás

33.3.12 Kiinduló kód

A labor az alábbi, teljes példát használja. A kód FP32 pontossággal, 1D, 3 pontos stencilt számol, és parancssori argumentumokból veszi az n méretet, a blokkméretet és a streamszámot.

// stencil.cu
// Fordítás: nvcc -O3 -arch=sm_89 -lineinfo stencil.cu -o stencil
#include <cstdio>
#include <cstdlib>
#include <algorithm>

#define CHECK(call)                                                    \
    do {                                                               \
        cudaError_t err = call;                                        \
        if (err != cudaSuccess) {                                      \
            std::fprintf(stderr, "CUDA error %s:%d: %s\n",             \
                         __FILE__, __LINE__, cudaGetErrorString(err));  \
            std::exit(1);                                              \
        }                                                              \
    } while (0)

constexpr int RADIUS = 1;

__global__ void stencil_naive(const float* __restrict__ in,
                              float* __restrict__ out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= n) return;

    float acc = 0.0f;
    for (int r = -RADIUS; r <= RADIUS; ++r) {
        int j = std::min(std::max(i + r, 0), n - 1);
        acc += in[j];
    }
    out[i] = acc / (2 * RADIUS + 1);
}

__global__ void stencil_tiled(const float* __restrict__ in,
                              float* __restrict__ out, int n) {
    extern __shared__ float s[];
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    int local = threadIdx.x + RADIUS;

    if (i < n) {
        s[local] = in[i];
    }

    if (threadIdx.x < RADIUS) {
        int left = blockIdx.x * blockDim.x - RADIUS + threadIdx.x;
        s[threadIdx.x] = (left >= 0) ? in[left] : in[0];

        int right = (blockIdx.x + 1) * blockDim.x + threadIdx.x;
        s[blockDim.x + RADIUS + threadIdx.x] =
            (right < n) ? in[right] : in[n - 1];
    }

    __syncthreads();

    if (i < n) {
        float acc = 0.0f;
        for (int r = -RADIUS; r <= RADIUS; ++r) {
            acc += s[local + r];
        }
        out[i] = acc / (2 * RADIUS + 1);
    }
}

int main(int argc, char** argv) {
    int n = (argc > 1) ? std::atoi(argv[1]) : (1 << 26);
    int block = (argc > 2) ? std::atoi(argv[2]) : 256;
    int streams_count = (argc > 3) ? std::atoi(argv[3]) : 0;

    const size_t bytes = n * sizeof(float);
    float* h_in = nullptr;
    float* h_out = nullptr;
    CHECK(cudaMallocHost(&h_in, bytes));
    CHECK(cudaMallocHost(&h_out, bytes));

    for (int i = 0; i < n; ++i) {
        h_in[i] = static_cast<float>(i % 1000) * 0.001f;
    }

    float* d_in = nullptr;
    float* d_out = nullptr;
    CHECK(cudaMalloc(&d_in, bytes));
    CHECK(cudaMalloc(&d_out, bytes));
    CHECK(cudaMemcpy(d_in, h_in, bytes, cudaMemcpyHostToDevice));

    const int grid = (n + block - 1) / block;
    const int shared_bytes = (block + 2 * RADIUS) * sizeof(float);

    cudaEvent_t start, stop;
    CHECK(cudaEventCreate(&start));
    CHECK(cudaEventCreate(&stop));

    // Warm-up
    for (int i = 0; i < 5; ++i) {
        stencil_naive<<<grid, block>>>(d_in, d_out, n);
    }
    CHECK(cudaDeviceSynchronize());

    const int iters = 20;
    CHECK(cudaEventRecord(start, 0));
    for (int i = 0; i < iters; ++i) {
        stencil_naive<<<grid, block>>>(d_in, d_out, n);
    }
    CHECK(cudaEventRecord(stop, 0));
    CHECK(cudaEventSynchronize(stop));

    float naive_ms = 0.0f;
    CHECK(cudaEventElapsedTime(&naive_ms, start, stop));
    naive_ms /= iters;

    CHECK(cudaEventRecord(start, 0));
    for (int i = 0; i < iters; ++i) {
        stencil_tiled<<<grid, block, shared_bytes>>>(d_in, d_out, n);
    }
    CHECK(cudaEventRecord(stop, 0));
    CHECK(cudaEventSynchronize(stop));

    float tiled_ms = 0.0f;
    CHECK(cudaEventElapsedTime(&tiled_ms, start, stop));
    tiled_ms /= iters;

    std::printf("naive: %.3f ms\n", naive_ms);
    std::printf("tiled: %.3f ms\n", tiled_ms);

    CHECK(cudaFree(d_in));
    CHECK(cudaFree(d_out));
    CHECK(cudaFreeHost(h_in));
    CHECK(cudaFreeHost(h_out));
    return 0;
}

33.3.13 Feladatok

  1. Baseline: futtasd a naiv és a tiled változatot n = 67 108 864 mérettel, block = 256 blokkmérettel. Töltsd ki a mérési napló táblázatát. Számítsd ki az effektív sávszélességet a tényleges adatmozgatásból.

  2. Tiling elemzése: készíts Nsight Compute profilt a naiv és a tiled kernelről. Hasonlítsd össze a gpu__time_duration.avg és a globális memória szektorok számát. Fogalmazd meg, hogy a tiling miért változtatta meg a memóriaforgalmat.

  3. Occupancy hangolás: futtasd a tiled kernelt block = 128, 256, 512 értékekkel. Jegyezd fel a regiszterhasználatot és a shared memory méretet. A Nsight Compute Occupancy szekciójával ellenőrizd a foglaltságot. Döntsd el, melyik blokkméret a legjobb, és indokold meg.

  4. Streamek: implementáld a 2 streames változatot a fenti minta alapján. Készíts Nsight Systems profilt, és ellenőrizd a H2D, kernel és D2H átfedést. Ha nincs átfedés, keresd meg a sorosítás okát.

  5. Dokumentáció: a mérési naplóban tüntesd fel a GPU típusát, a drivert, a CUDA-verziót, az FP32 pontosságot, a warm-up és ismétlésszámot, az átlagot és a szórást. A mért eredményt külön oszlopban jelöld, a modellből számított várt értéket pedig külön.

33.3.15 Önellenőrző kérdés

Miért nem elegendő a kernelidőt nézni akkor, ha a zárórendszer host-device másolást is végez?
Válaszvázlat: A teljes alkalmazás futásideje a H2D másolás, a kernel és a D2H másolás összege, illetve átfedés esetén azok időbeli ütemezése. Ha csak a kernelidőt mérjük, nem látjuk a lapozható memória, a szinkron másolás vagy a stream nélküli sorosítás hatását. A Nsight Systems timeline és külön eseményekkel mért fázisidők együttesen mutatják meg, hol vész el az idő, és hol érdemes streameket vagy pinned memóriát bevezetni.

33.3.16 Összegzés

A teljesítmény hangolása a záróprojektben nem egyetlen nagy optimalizálás, hanem egymásra épülő, méréssel igazolt lépések sorozata. A tiling csökkenti a globális memóriaforgalmat, az occupancy-hangolás a késleltetés elrejtését javítja, a streamek pedig a másolás és számítás átfedését teszik lehetővé. Minden beavatkozást ugyanazon bemeneten, rögzített környezetben kell mérni, és a profilképnek meg kell erősítenie a várt hatást. Csak így lehet különválasztani a valódi nyereséget a zajtól, és így készíthető elő a Validáció és dokumentáció alfejezetben következő validációs és dokumentációs szakasz.
