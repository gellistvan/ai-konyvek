29.2 Context, queue és memóriaobjektumok

Az OpenCL erőforrásmodelljének középpontjában három, egymásra épülő fogalom áll: a context, a command queue és a memóriaobjektum. Az előző egységben megismerkedtünk a platform és device kiválasztásával; most azt vizsgáljuk, hogyan szervezzük ezekből a végrehajtáshoz szükséges erőforrásokat. A context egy vagy több eszközt és a hozzájuk tartozó erőforrásokat fogja össze, a command queue az egyes eszközökre irányuló parancsokat sorolja be, a memóriaobjektumok pedig a host és a device közötti, illetve a device-ok közötti adatcserét valósítják meg. E három elem együttes használata nélkül nem lehet OpenCL-programot futtatni; a hibák jelentős része is ezen a rétegen keletkezik.

Ebben az egységben először a context és a queue szerepét, létrehozását és leggyakoribb beállításait tekintjük át, majd részletesen tárgyaljuk a buffer-memóriaobjektumokat és a másolási műveleteket. A lezáró labor egy olyan kis programot ad, amely létrehoz egy buffert, adatot másol a hostról a device-ra, device-ok között, majd vissza a hostra, és megméri a műveletek idejét. A példa segítségével bemutatjuk a hibakezelést, a warm-up és ismétlés módszertanát, valamint a mérési napló helyes kitöltését.

29.2.1 Context: az OpenCL erőforrások összefogója

A context az OpenCL-ben egy olyan objektum, amely egy adott platformhoz tartozó eszközök (például egy vagy több GPU, CPU vagy gyorsító) halmazát és a hozzájuk kapcsolódó erőforrásokat – parancssorokat, memóriaobjektumokat, programokat és kerneleket – egyetlen egységbe fogja. A context feladata, hogy biztosítsa az erőforrások közötti konzisztenciát és a hivatkozások érvényességét. Egy memóriaobjektumot mindig egy konkrét contexthez kell létrehozni, és az adott contexthez tartozó eszközök láthatják azt. Ugyanígy egy command queue is egy contexthez és azon belül egy device-hoz kötődik.

A context létrehozása a C++ bindingban a cl::Context konstruktorával történik. Az alábbi kódrészlet egyetlen GPU device-ot tartalmazó contextet hoz létre:

cl_int err;
cl::Context context(device, nullptr, nullptr, nullptr, &err);
if (err != CL_SUCCESS) {
    std::cerr << "Context creation failed: " << err << "\n";
    // hiba kezelése
}

A konstruktor paraméterei: a device-ok listája (itt egyetlen cl::Device), egy opcionális cl_context_properties tömb, egy opcionális hibakallback, egy opcionális user data pointer, és egy hibakód pointer. A properties tömb segítségével például platformot adhatunk meg, ha több platform van jelen; ezt gyakran a platform kiválasztása után érdemes beállítani. A C++ binding egyszerűsített konstruktora elfogad egy std::vector<cl::Device>-ot is, így több eszközt is egy contextbe foglalhatunk:

std::vector<cl::Device> devices = {gpu0, gpu1};
cl::Context context(devices);

A context élettartama alatt minden benne létrehozott erőforrásnak élnie kell. Ha a context megsemmisül, az összes hozzá tartozó queue, buffer, program és kernel érvénytelenné válik. A C++ binding automatikus referenciaszámlálást végez, de a nyers C API-ban a clReleaseContext hívás elmulasztása memóriaszivárgáshoz vezet. A context tehát nem csupán kényelmi csoportosítás, hanem az erőforrások életciklusának központi eleme.

Fontos megérteni, hogy egy context több device-ot is tartalmazhat, de a device-ok csak ugyanazon a platformon belül lehetnek. Ez azt jelenti, hogy nem lehet egyetlen contextben egyszerre egy NVIDIA GPU-t és egy Intel iGPU-t összekapcsolni, ha azok különböző platformokhoz tartoznak. Ilyenkor minden platformhoz külön contextet kell létrehozni. A context hatóköre meghatározza a memória láthatóságát is: a contexthez tartozó eszközök számára a memóriaobjektumok közvetlenül elérhetők, de más contextből nem. Több eszköz esetén a parancsok ütemezése és az adatmozgatás a contexten belül történik.

29.2.2 Command queue: a parancsok sorba állítása

A command queue (parancssor) az a mechanizmus, amelyen keresztül parancsokat küldünk egy adott device-nak. Minden parancssor pontosan egy device-hoz tartozik, és az adott device-ra vonatkozó kernelindításokat, memóriaműveleteket és szinkronizációs parancsokat sorolja be. A queue létrehozása a cl::CommandQueue konstruktorával történik:

cl_command_queue_properties props = CL_QUEUE_PROFILING_ENABLE;
cl::CommandQueue queue(context, device, props, &err);

A props paraméterrel szabályozhatjuk a queue viselkedését. A két leggyakoribb tulajdonság:

  • CL_QUEUE_OUT_OF_ORDER_EXEC_MODE_ENABLE: engedélyezi a parancsok sorrendtől független végrehajtását. Alapértelmezés szerint a queue in-order, azaz a parancsok abban a sorrendben hajtódnak végre, ahogyan a queue-ba kerültek. Ez a legegyszerűbb és legbiztonságosabb mód, mert a függőségek implicit módon érvényesülnek. Az out-of-order mód nagyobb átfedést tesz lehetővé, de akkor a parancsok közötti függőségeket explicit eseményekkel (event) kell kezelni.
  • CL_QUEUE_PROFILING_ENABLE: lehetővé teszi a parancsok időzítését. Ekkor a queue-ba beküldött parancsokhoz eseményobjektumokat rendelhetünk, és azokból kiolvashatjuk a parancs kezdő és befejező időpontját. Ez nélkülözhetetlen a teljesítményméréshez, de minimális többletköltséggel jár.

A parancssor használata a következő lépésekből áll: parancsok beküldése (enqueue), majd szinkronizáció (finish vagy flush). A finish() blokkol, amíg a queue összes korábban beküldött parancsa be nem fejeződik; a flush() csak a parancsokat küldi el a device-nak, de nem várja meg a befejezést. A finish() tipikusan a mérési ciklus végén vagy a program befejezése előtt szükséges, hogy az összes aszinkron művelet befejeződjön.

A parancsok három fő csoportba sorolhatók:

  1. Kernelvégrehajtás: enqueueNDRangeKernel vagy enqueueTask (utóbbi OpenCL 1.2-ben). Ezeket a következő egység tárgyalja részletesen.
  2. Memóriaműveletek: enqueueWriteBuffer, enqueueReadBuffer, enqueueCopyBuffer, enqueueMapBuffer, stb. Ezek a host és device közötti, illetve device-ok közötti adatmozgatást végzik.
  3. Szinkronizáció: enqueueMarker, enqueueBarrierWithWaitList (OpenCL 2.0+). Ezekkel jelölhetünk pontokat a queue-ban, vagy várhatunk eseményekre.

A parancsok minden esetben aszinkron módon kerülnek a queue-ba, kivéve, ha a hívás blokkoló (blocking == CL_TRUE). Például a enqueueWriteBuffer blokkoló változata megvárja, amíg az adat átmásolódik a device-ra, míg a nem blokkoló változat azonnal visszatér, és a tényleges másolás később történik. A blokkoló hívás egyszerűbb, de a teljesítmény szempontjából gyakran jobb, ha több nem blokkoló parancsot küldünk be, és egyetlen finish()-sel várjuk meg őket.

A hibakezelés szempontjából fontos, hogy a queue létrehozása is hibát adhat, például ha a megadott device nem tartozik a contexthez, vagy a tulajdonságok érvénytelenek. A C++ binding ilyenkor CL_INVALID_DEVICE vagy CL_INVALID_QUEUE_PROPERTIES hibát jelez. Mindig ellenőrizzük a visszatérési értéket vagy használjunk kivételt.

29.2.3 Memóriaobjektumok: buffer, image és pipe

Az OpenCL a device memóriát memóriaobjektumok formájában absztrahálja. A leggyakrabban használt típus a buffer, amely egy egydimenziós, folytonos memóriaterületet reprezentál. Emellett léteznek image objektumok (2D/3D textúrák), valamint OpenCL 2.0-tól pipe objektumok. Ebben a fejezetben a bufferre összpontosítunk, mivel a legtöbb adatpárhuzamos feladat ezt használja.

A buffer létrehozása a cl::Buffer konstruktorával történik:

cl::Buffer buffer(context, flags, size, host_ptr, &err);

A paraméterek:

  • context: a context, amelyhez a buffer tartozik.
  • flags: a buffer tulajdonságait leíró bitmaszk (cl_mem_flags).
  • size: a buffer mérete bájtban.
  • host_ptr: opcionális pointer a host memóriára, amelyet a flag-ek szerint használunk.
  • err: hibakód pointer.

A memóriaflag-ek határozzák meg a buffer hozzáférési módját és a host-memória kapcsolatát. A legalapvetőbb hozzáférési flag-ek:

  • CL_MEM_READ_WRITE: a kernel olvashatja és írhatja a buffert. Ez az alapértelmezés, ha nincs más megadva.
  • CL_MEM_READ_ONLY: a kernel csak olvashatja.
  • CL_MEM_WRITE_ONLY: a kernel csak írhatja.

Bár ezek a flag-ek deklarációs célt szolgálnak, a futás közbeni viselkedést a kernel deklarációja is befolyásolja; a flag-ek és a kernel paraméterei közötti inkonzisztencia hibához vezethet.

A host-memória használatát szabályozó flag-ek a következők:

  • CL_MEM_COPY_HOST_PTR: a létrehozáskor a host_ptr által mutatott adatot a device memóriába másolja. Ez a leggyakoribb mód, ha a host adatot egyszer fel kell tölteni a device-ra. A host pointert a hívás után azonnal fel lehet szabadítani, mert a device saját másolattal rendelkezik.
  • CL_MEM_USE_HOST_PTR: a device a megadott host memóriaterületet használja közvetlenül (vagy legalábbis arra hivatkozik). Ez lehetővé teszi a nullás másolást bizonyos eszközökön, de a host pointernek érvényesnek kell maradnia a buffer teljes élettartama alatt. A host oldali módosítások láthatóvá válhatnak a device számára, és viszont, de ez implementációfüggő; gyakran a host és device közötti koherenciát a clEnqueueMapBuffer vagy explicit másolás biztosítja.
  • CL_MEM_ALLOC_HOST_PTR: a device memóriát foglal, és egyúttal host számára is elérhető címet biztosít. Ez gyakran egyesített memória architektúrákon hatékony, de nem minden eszköz támogatja. A host_ptr paramétert ilyenkor nullptr-ként adjuk át, és a host pointert később a clEnqueueMapBuffer segítségével kérhetjük le.
  • CL_MEM_COPY_HOST_PTR | CL_MEM_ALLOC_HOST_PTR kombinációja: a device memóriát foglal, majd a host adatot bemásolja.

Az OpenCL 2.0 további flag-eket vezetett be a Shared Virtual Memory (SVM) támogatására:

  • CL_MEM_SVM_FINE_GRAIN_BUFFER: finom szemcséjű SVM, ahol a host és device memória szinkronban van.
  • CL_MEM_SVM_ATOMICS: atomi műveletek engedélyezése az SVM-ben.
  • CL_MEM_SVM_FINE_GRAIN_SYSTEM: rendszerszintű finom szemcséjű SVM.

Ezeket itt csak megemlítjük, mert a hagyományos buffer-kezelés a legtöbb feladatra elegendő.

A flag-eket bitenkénti VAGY (|) művelettel kombinálhatjuk. Például:

cl::Buffer buf(context, CL_MEM_READ_WRITE | CL_MEM_COPY_HOST_PTR, bytes, hostData.data(), &err);

Fontos, hogy a CL_MEM_USE_HOST_PTR és CL_MEM_COPY_HOST_PTR egyszerre nem adható meg, mert ellentmondanak egymásnak. Hasonlóképpen a CL_MEM_ALLOC_HOST_PTR önmagában nem igényel host_ptr-t.

A buffer létrehozása során fellépő gyakori hibák:

  • CL_INVALID_CONTEXT: a megadott context érvénytelen.
  • CL_INVALID_VALUE: a flag-ek érvénytelenek vagy egymással ütközők.
  • CL_INVALID_BUFFER_SIZE: a méret 0 vagy túl nagy.
  • CL_INVALID_HOST_PTR: a host_ptr érvénytelen (például CL_MEM_COPY_HOST_PTR esetén nullptr).
  • CL_MEM_OBJECT_ALLOCATION_FAILURE: a device memória foglalása nem sikerült.
  • CL_OUT_OF_RESOURCES vagy CL_OUT_OF_HOST_MEMORY: erőforrás-hiány.

A C++ bindingban a cl::Buffer objektum RAII-t valósít meg, tehát a buffer automatikusan felszabadul, amikor az objektum megsemmisül. A nyers C API-ban a clReleaseMemObject hívás szükséges.

29.2.4 Buffer-másolás: enqueueWriteBuffer, enqueueReadBuffer, enqueueCopyBuffer

A buffer létrehozása után adatot kell mozgatni a host és a device között. Az OpenCL erre a parancssoron keresztül nyújt lehetőséget:

  • enqueueWriteBuffer: a host memóriából a device bufferbe ír.
  • enqueueReadBuffer: a device bufferből a host memóriába olvas.
  • enqueueCopyBuffer: device bufferből egy másik device bufferbe másol.

Mindhárom függvény szignatúrája a C++ bindingban hasonló:

cl_int enqueueWriteBuffer(const Buffer& buffer, cl_bool blocking, size_t offset, size_t size, const void* ptr, const vector<Event>* events = nullptr, Event* event = nullptr);
cl_int enqueueReadBuffer(const Buffer& buffer, cl_bool blocking, size_t offset, size_t size, void* ptr, const vector<Event>* events = nullptr, Event* event = nullptr);
cl_int enqueueCopyBuffer(const Buffer& src, const Buffer& dst, size_t src_offset, size_t dst_offset, size_t size, const vector<Event>* events = nullptr, Event* event = nullptr);

A blocking paraméter CL_TRUE esetén a hívás blokkol, amíg a másolás be nem fejeződik; CL_FALSE esetén a parancs csak a queue-ba kerül, és a hívás azonnal visszatér. Az offset és size segítségével a buffer egy részét is kezelhetjük. Az events paraméterrel az előző parancsoktól függőséget adhatunk meg, az event kimenő paraméterrel pedig a parancs befejezését jelző eseményt kaphatunk (ez a profilinghoz is szükséges).

A másolási műveletek hibái:

  • CL_INVALID_COMMAND_QUEUE: a queue nem tartozik a contexthez.
  • CL_INVALID_MEM_OBJECT: a buffer érvénytelen.
  • CL_INVALID_VALUE: az offset vagy size túlcsordul, vagy nem illeszkedik a bufferhez.
  • CL_INVALID_EVENT_WAIT_LIST: a várakozási lista érvénytelen.
  • CL_EXEC_STATUS_ERROR_FOR_EVENTS_IN_WAIT_LIST: ha a várakozási listában szereplő esemény hibásan fejeződött be.

Fontos szempont, hogy a host pointer, amelyet a enqueueWriteBuffer vagy enqueueReadBuffer kap, érvényes legyen a hívás idején. Blokkoló hívásnál a hívás visszatérte után a pointer felszabadítható; nem blokkoló hívásnál viszont a pointernek érvényesnek kell maradnia, amíg a parancs be nem fejeződik. Ezért nem blokkoló hívásoknál gyakran szükséges egy cl::Event-et kérni, és később event.wait()-et hívni.

A laborban a blokkoló változatot használjuk, mert az egyszerűbb és a mérési ciklusban a finish() úgyis biztosítja a befejezést. A nem blokkoló változatot a későbbi fejezetekben, a stream-ek és az átfedés tárgyalásakor fogjuk kihasználni.

29.2.5 Tipikus hibák és megoldások

Az OpenCL context, queue és buffer kezelése során a kezdők leggyakrabban a következő hibákba ütköznek:

  1. Context hiánya vagy rossz device hozzárendelés. Ha egy memóriaobjektumot egy olyan contexthez próbálunk létrehozni, amely nem tartalmazza a kívánt device-ot, akkor a buffer létrehozása sikeres lehet, de a queue-val való használat CL_INVALID_CONTEXT hibát ad. Megoldás: mindig ellenőrizzük, hogy a device benne van-e a contextben, például a context.getInfo<CL_CONTEXT_DEVICES>() lekérdezéssel.

  2. Helytelen flag kombináció. A CL_MEM_COPY_HOST_PTR és CL_MEM_USE_HOST_PTR egyszerre való megadása érvénytelen. Hasonlóképpen a CL_MEM_READ_ONLY bufferbe írás a kernelből futás közbeni hibát okozhat. Megoldás: tanulmányozzuk a flag-ek dokumentációját, és csak olyan kombinációt használjunk, amelynek értelme van.

  3. Host pointer érvénytelensége. Ha CL_MEM_USE_HOST_PTR flaggel hozunk létre buffert, a host pointert nem szabad felszabadítani, amíg a buffer él. Ellenkező esetben a device memória érvénytelen területre mutat, ami futás közbeni hibákhoz vagy adatkorrupcióhoz vezet. Megoldás: használjunk CL_MEM_COPY_HOST_PTR-t, ha a host adatra nincs szükség a továbbiakban, vagy tartsuk életben a host bufferünket.

  4. Blokkoló és nem blokkoló hívások keverése. Ha nem blokkoló enqueueWriteBuffer után azonnal blokkoló enqueueReadBuffer-t hívunk, a read megelőzheti a write befejezését, és nem definiált adatot olvasunk. Megoldás: használjunk blokkoló hívásokat, vagy kérjünk eseményt a write-ból, és adjuk át a read várakozási listájára.

  5. Szinkronizáció hiánya. A queue parancsai aszinkron módon futnak; ha a program véget ér anélkül, hogy finish()-t hívnánk, a parancsok esetleg nem fejeződnek be, és a memóriaobjektumok felszabadulhatnak a parancsok befejezése előtt. Megoldás: a program végén mindig hívjunk queue.finish()-t, vagy használjunk RAII-t.

  6. Memóriaszivárgás. A nyers C API-ban minden clCreateBuffer után szükséges a clReleaseMemObject. A C++ binding automatikusan felszabadít, de ha dinamikusan hozunk létre objektumokat, ügyeljünk a pointerek életciklusára. Megoldás: lehetőleg használjuk a C++ bindingot, és kerüljük a nyers new/delete-et.

  7. Kihagyott hibakezelés. A legtöbb OpenCL hívás visszatérési értéket ad; ha nem ellenőrizzük, a hiba csak később, nehezen értelmezhető módon jelentkezik. Megoldás: minden hívás után ellenőrizzük a hibakódot, vagy használjunk kivételt dobó wrapper-t.

A fenti hibák többsége már a fejlesztés korai szakaszában, egyszerű tesztekkel kiszűrhető. A laborban bemutatott kód ezért szándékosan sok hibakezelést tartalmaz.

29.2.6 Labor: buffer létrehozása és másolása

Ebben a laborban egy olyan OpenCL-programot készítünk, amely létrehoz egy contextet, egy parancssort, két device buffert, majd adatot másol a hostról az egyik bufferbe, onnan a másikba, végül vissza a hostra. A program megméri a három másolási művelet teljes idejét, ellenőrzi az adatokat, és kiszámítja a host–device sávszélességet. A labor célja a context, queue és buffer fogalmak gyakorlati összekapcsolása.

29.2.8 Forráskód

Az alábbi kód a C++ bindingot használja. A hibakezelés egyszerű, de minden fontos lépést ellenőriz. A mérési ciklus előtt három warm-up ismétlést végzünk, majd tíz mérést rögzítünk. Minden iterációban a három másolási műveletet blokkoló módban hajtjuk végre, és a végén finish()-t hívunk. A mérési időt std::chrono segítségével rögzítjük.

#define CL_HPP_TARGET_OPENCL_VERSION 120
#define CL_HPP_MINIMUM_OPENCL_VERSION 120
#include <CL/opencl.hpp>
#include <iostream>
#include <vector>
#include <chrono>
#include <numeric>
#include <cmath>
#include <stdexcept>
#include <string>

const char* clErrorToString(cl_int err) {
    switch (err) {
        case CL_SUCCESS: return "CL_SUCCESS";
        case CL_INVALID_CONTEXT: return "CL_INVALID_CONTEXT";
        case CL_INVALID_QUEUE_PROPERTIES: return "CL_INVALID_QUEUE_PROPERTIES";
        case CL_INVALID_MEM_OBJECT: return "CL_INVALID_MEM_OBJECT";
        case CL_INVALID_VALUE: return "CL_INVALID_VALUE";
        case CL_INVALID_BUFFER_SIZE: return "CL_INVALID_BUFFER_SIZE";
        case CL_INVALID_HOST_PTR: return "CL_INVALID_HOST_PTR";
        case CL_MEM_OBJECT_ALLOCATION_FAILURE: return "CL_MEM_OBJECT_ALLOCATION_FAILURE";
        case CL_OUT_OF_RESOURCES: return "CL_OUT_OF_RESOURCES";
        case CL_OUT_OF_HOST_MEMORY: return "CL_OUT_OF_HOST_MEMORY";
        default: return "UNKNOWN";
    }
}

void checkErr(cl_int err, const std::string& name) {
    if (err != CL_SUCCESS) {
        std::cerr << "ERROR: " << name << " failed: "
                  << clErrorToString(err) << " (" << err << ")\n";
        throw std::runtime_error(name);
    }
}

int main() {
    try {
        // Platform és device kiválasztása (ld. gpu110)
        std::vector<cl::Platform> platforms;
        cl::Platform::get(&platforms);
        if (platforms.empty()) throw std::runtime_error("No OpenCL platforms");
        cl::Platform platform = platforms[0];

        std::vector<cl::Device> devices;
        platform.getDevices(CL_DEVICE_TYPE_GPU, &devices);
        if (devices.empty()) throw std::runtime_error("No GPU devices");
        cl::Device device = devices[0];
        std::cout << "Device: " << device.getInfo<CL_DEVICE_NAME>() << "\n";

        // 1) Context létrehozása
        cl_int err;
        cl::Context context(device, nullptr, nullptr, nullptr, &err);
        checkErr(err, "Context creation");

        // 2) Command queue létrehozása (in-order, profiling)
        cl_command_queue_properties props = CL_QUEUE_PROFILING_ENABLE;
        cl::CommandQueue queue(context, device, props, &err);
        checkErr(err, "CommandQueue creation");

        // 3) Buffer paraméterek
        const size_t N = 1 << 22;          // 4 Mi elem
        const size_t bytes = N * sizeof(float);
        std::vector<float> hostData(N);
        for (size_t i = 0; i < N; ++i)
            hostData[i] = static_cast<float>(i) * 0.001f;

        // Device buffer A: host adatból másol
        cl::Buffer deviceBufA(context, CL_MEM_READ_WRITE | CL_MEM_COPY_HOST_PTR,
                              bytes, hostData.data(), &err);
        checkErr(err, "Buffer A creation");

        // Device buffer B: csak device oldali
        cl::Buffer deviceBufB(context, CL_MEM_READ_WRITE, bytes, nullptr, &err);
        checkErr(err, "Buffer B creation");

        // Host visszaolvasási terület
        std::vector<float> hostResult(N, 0.0f);

        // 4) Warm-up
        const int warmup = 3;
        for (int i = 0; i < warmup; ++i) {
            queue.enqueueWriteBuffer(deviceBufA, CL_TRUE, 0, bytes, hostData.data());
            queue.enqueueCopyBuffer(deviceBufA, deviceBufB, 0, 0, bytes);
            queue.enqueueReadBuffer(deviceBufB, CL_TRUE, 0, bytes, hostResult.data());
            queue.finish();
        }

        // 5) Adatellenőrzés egyszer
        if (hostResult != hostData) {
            throw std::runtime_error("Data mismatch after copy");
        }
        std::cout << "Data verification: OK\n";

        // 6) Mérés
        const int iters = 10;
        std::vector<double> times(iters);
        for (int i = 0; i < iters; ++i) {
            auto start = std::chrono::steady_clock::now();
            queue.enqueueWriteBuffer(deviceBufA, CL_TRUE, 0, bytes, hostData.data());
            queue.enqueueCopyBuffer(deviceBufA, deviceBufB, 0, 0, bytes);
            queue.enqueueReadBuffer(deviceBufB, CL_TRUE, 0, bytes, hostResult.data());
            queue.finish();
            auto end = std::chrono::steady_clock::now();
            times[i] = std::chrono::duration<double, std::milli>(end - start).count();
        }

        double mean = std::accumulate(times.begin(), times.end(), 0.0) / iters;
        double sq_sum = 0.0;
        for (double t : times) sq_sum += (t - mean) * (t - mean);
        double stdev = std::sqrt(sq_sum / iters);

        // A host<->device sávszélesség: write + read (device-device copy nem terheli a host linket)
        double total_bytes = 2.0 * static_cast<double>(bytes);
        double bw_gbps = (total_bytes / (mean / 1000.0)) / 1e9;

        std::cout << "Mean time: " << mean << " ms\n";
        std::cout << "Std dev:   " << stdev << " ms\n";
        std::cout << "Host<->device bandwidth: " << bw_gbps << " GB/s\n";

        // RAII felszabadítja a queue-t, buffereket, contextet
        return 0;
    } catch (const cl::Error& e) {
        std::cerr << "OpenCL error: " << e.what() << " (" << e.err() << ")\n";
        return 1;
    } catch (const std::exception& e) {
        std::cerr << "Error: " << e.what() << "\n";
        return 1;
    }
}

29.2.12 Értelmezés

Az eredmény azt mutatja, hogy a buffer-másolási műveletek a PCIe sávszélesség közelében mozognak, ami azt jelzi, hogy a mérési overhead minimális. Ha a mért sávszélesség jelentősen eltér a várttól, érdemes ellenőrizni a következőket:

  • A GPU és a CPU közötti PCIe sávszélesség (például nvidia-smi topo -m vagy pcietop).
  • A háttérterhelés (más processzek).
  • Az energiagazdálkodási beállítások (a GPU órajele alacsony lehet).
  • A CPU oldali memória sávszélessége (ha a host adat nagy).

29.2.13 Önellenőrző kérdés

Mi a különbség a CL_MEM_COPY_HOST_PTR és CL_MEM_USE_HOST_PTR flag között? Melyik esetben módosítható a host pointer a buffer létrehozása után, és milyen következményekkel jár ez a device memóriára nézve?

Válasz: A CL_MEM_COPY_HOST_PTR esetén a létrehozáskor a host adatot a device memóriába másoljuk, így a host pointer a hívás után felszabadítható, és a host oldali módosítások nem befolyásolják a device buffert. A CL_MEM_USE_HOST_PTR esetén a device a megadott host memóriaterületet használja (vagy arra hivatkozik), ezért a host pointernek érvényesnek kell maradnia a buffer élettartama alatt. A host oldali módosítások elvileg láthatóvá válhatnak a device számára, de ez implementációfüggő; a biztonságos megoldás a clEnqueueMapBuffer használata vagy explicit másolás.
