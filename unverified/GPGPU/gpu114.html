30.1 OpenCL C és kernelírás

30.1.1 Az OpenCL C nyelv és a kernel

Az OpenCL C a C99 szabvány származéka, amelyet kifejezetten párhuzamos eszközökön futó kernelek írására terveztek. A nyelv felületesen ismerősnek tűnik a C-fejlesztő számára, azonban több olyan kiterjesztést és korlátozást tartalmaz, amelyek nélkülözhetetlenek a GPU-n való helyes és hatékony végrehajtáshoz. Ebben a fejezetben az OpenCL C nyelv alapvető elemeit, a memóriatér-minősítőket, a vektortípusokat és a fordítási opciókat tárgyaljuk, majd egy teljes, ellenőrzött példán keresztül mutatjuk be a kernelírás gyakorlatát.

30.1.2 A nyelv helye az OpenCL rendszerben

Az OpenCL programozási modelljében a kernel az a függvény, amelyet a host az eszközön párhuzamosan végrehajt. A kernel függvényt a __kernel vagy az azzal egyenértékű kernel kulcsszóval jelöljük. A kernel a C99-hez képest a következő alapvető eltérésekkel rendelkezik:

  1. A kernel nem adhat vissza értéket; a visszatérési típus mindig void.
  2. A kernel argumentumai nem lehetnek mutatók a host-memóriába; minden mutató argumentumnak egy OpenCL-memóriaobjektumra vagy SVM-területre kell mutatnia.
  3. A kernel nem használhatja a C szabványos könyvtárának nagy részét; az OpenCL beépített függvénykészletet biztosít a matematikai és közös műveletekhez.
  4. A kernel végrehajtási modellje eltér a szekvenciális C-től: minden work-item ugyanazt a kódot futtatja, de a beépített azonosítók (get_global_id, get_local_id stb.) különböztetik meg az adatokat.

A kernel forráskódját futásidőben a host program fordítja le az eszközre. Ez a futásidejű fordítás egyszerre jelent rugalmasságot és teljesítménykockázatot: az OpenCL C kód natív módon az adott hardverre fordítható, de a fordítási idő a futásidőt növeli, és a hibák csak a futás során derülnek ki.

30.1.3 Address space minősítők

Az OpenCL C egyik legfontosabb sajátossága, hogy minden mutatónak explicit memóriatér-minősítővel kell rendelkeznie. A négy alapvető memóriatér a következő:

  1. __global (vagy global): A global memory a teljes eszközön elérhető, a host által allokált memória. A globale memória a legnagyobb kapacitású, de a leglassabb hozzáférésű. A kernel argumentumai jellemzően global memóriatérben vannak.

  2. __constant (vagy constant): A constant memory a global memory egy részét foglalja el, de optimalizált olvasási útvonallal rendelkezik. A work-group minden tagja számára azonos értékű adatok (pl. együtthatók, súlyok, konfigurációs paraméterek) tárolására használható. A host az OpenCL API-n keresztül írhatja, a kernel csak olvashatja.

  3. __local (vagy local): A local memory a work-group szintű memória. A work-group minden work-iteme osztozik rajta, és a barrier() utasítással szinkronizálhatják a hozzáférést. A local memory a globalnál sokkal gyorsabb, de a kapacitása korlátozott. A host nem fér hozzá közvetlenül; a kernel futása közben használható munkaterületként.

  4. __private (vagy private): A private memory minden work-item saját, privát memóriája. A kernelben deklarált, nem kernel-argumentumként szereplő változók alapértelmezésben private memóriában vannak. A private memória gyors, de a regiszterek túlcsordulása esetén a lassabb global memóriába kerülhet át (register spilling hasonló jelenség, mint CUDA-ban).

A kernel argumentumok deklarációjában a mutatókat mindig minősíteni kell a megfelelő memóriatérrel. Például:

__kernel void axpy(
    __global const float *x,
    __global const float *y,
    __global float *z,
    const float a)
{
    int i = get_global_id(0);
    z[i] = a * x[i] + y[i];
}

Itt az x, y, z mutatók global memóriában vannak, az a skalár pedig private memóriában. A const minősítő a read-only globális mutatókra alkalmazható, ami lehetővé teszi a gyorsabb, cachelt elérést egyes architektúrákon.

Fontos: A memóriatér-minősítő nélküli mutató egy kernel argumentumban fordítási hibát okoz. Ez az explicititás az OpenCL C egyik legnagyobb előnye: a kód egyértelműen dokumentálja az adatok helyét és hozzáférési mintáját.

30.1.4 Vektortípusok

Az OpenCL C gazdag vektortípus-készlettel rendelkezik, amely kritikus a GPU-k nagy áteresztőképességű SIMD-egységeinek hatékony kihasználásához. A vektortípusok a skaláris típusokból és egy szélességből állnak, például:

  • float4: négy 32 bites lebegőpontos szám,
  • int8: nyolc 32 bites egész,
  • double2: két 64 bites lebegőpontos szám,
  • uchar16: tizenhat 8 bites előjel nélküli egész.

A vektortípusok mérete a hardver által támogatott szélességtől függően változhat. A szabvány legalább a 2-, 4-, 8- és 16-elemű vektorokat támogatja; az elérhető szélességeket a CL_DEVICE_PREFERRED_VECTOR_WIDTH_* eszközkéréssel lehet lekérdezni.

A vektorok inicializálása több módon történhet:

float4 v = (float4)(1.0f, 2.0f, 3.0f, 4.0f);  // Literál
float4 w = (float4)(1.0f);                    // Mind a négy elem 1.0
float4 u = (float4)(v.x, v.y, w.z, 0.0f);      // Elemek kiválasztása

A vektorok komponensei a .x, .y, .z, .w mezőkkel érhetők el. A .s0, .s1, .s2, .s3 elnevezés is használható, ami hasznos a 4-nél nagyobb szélességű vektoroknál. A swizzle művelet lehetővé teszi komponensek átrendezését:

float4 v = (float4)(1.0f, 2.0f, 3.0f, 4.0f);
float4 swapped = v.wzyx;  // (4.0, 3.0, 2.0, 1.0)

A vektorokon az aritmetikai és logikai műveletek komponensenként értelmezettek:

float4 a = (float4)(1.0f, 2.0f, 3.0f, 4.0f);
float4 b = (float4)(5.0f, 6.0f, 7.0f, 8.0f);
float4 c = a + b;  // (6.0, 8.0, 10.0, 12.0)

Az OpenCL beépített függvényei is vektorosítottak: a sqrt(c) komponensenként számítja a négyzetgyököt. A vektortípusok használatával a kód tömörebbé válik, és a fordító könnyebben generál hatékony SIMD-utasításokat.

Tömbök és vektorok kapcsolata: A globális memóriában lévő tömbökből történő vektoros betöltéshez a mutatót vektor típusúvá kell alakítani:

__global float4 *vec_ptr = (__global float4 *)a;
float4 v = vec_ptr[i];

Ez feltételezi, hogy az a tömb 16 bájtra igazított, és a hossza osztható 4-gyel. Az igazítás hiánya nem definiált viselkedést okozhat, ezért ilyen esetekben a vload4 és vstore4 függvényeket érdemes használni, amelyek nem igazított hozzáférést is támogatnak.

30.1.5 Gyakorlati példa: vektorösszeadás OpenCL C-ben

Tegyük fel, hogy az OpenCL és CUDA összehasonlítás fejezetben bemutatott platform- és eszközkezelés már rendelkezésre áll. A kernel forráskódja a következő:

__kernel void vector_add(
    __global const float *a,
    __global const float *b,
    __global float *c,
    const int n)
{
    int i = get_global_id(0);
    if (i < n) {
        c[i] = a[i] + b[i];
    }
}

Ez a kernel a legegyszerűbb adatpárhuzamos mintát valósítja meg: minden work-item egyetlen elem összegét számítja. A get_global_id(0) a work-item globális indexét adja vissza a 0. dimenzióban. A feltételes utasítás a tömb végének kezelésére szolgál: ha a globális méret nem osztható a tömb hosszával, a felesleges work-itemek nem hajtanak végre memóriahozzáférést.

Fontos megfigyelés: A kernelben nincs explicit ciklus. A párhuzamosítás implicit: a host a kernel indításakor megadja a globális méretet, és az OpenCL futásidő gondoskodik a work-itemek ütemezéséről. Ez a programozási modell lényege.

30.1.6 Életciklus: host-oldali fordítás és build

A kernel forráskódját a host programban egy stringként tároljuk, majd futásidőben lefordítjuk. A tipikus lépések:

  1. Program objektum létrehozása:

    cl_program program = clCreateProgramWithSource(
    context, 1, (const char **)&source_str, NULL, &err);

  2. Build futtatása:

    err = clBuildProgram(program, 1, &device, "", NULL, NULL);

    Az üres string a build option-öket jelöli; ebben az esetben nincsenek.

  3. Kernel objektum kinyerése:

    cl_kernel kernel = clCreateKernel(program, "vector_add", &err);

  4. Argumentumok beállítása:

    clSetKernelArg(kernel, 0, sizeof(cl_mem), (void *)&a_dev);
clSetKernelArg(kernel, 1, sizeof(cl_mem), (void *)&b_dev);
clSetKernelArg(kernel, 2, sizeof(cl_mem), (void *)&c_dev);
clSetKernelArg(kernel, 3, sizeof(int), (void *)&n);

  5. Kernel indítása:

    size_t global_size = n;
err = clEnqueueNDRangeKernel(
    queue, kernel, 1, NULL, &global_size, NULL, 0, NULL, NULL);

A build opciók lehetővé teszik a fordítás finomhangolását. A leggyakoribb opciók:

  • -cl-opt-disable: letiltja az optimalizációt, ami hibakeresésnél hasznos.
  • -cl-mad-enable: engedélyezi a multiply-add utasítások agresszív összevonását.
  • -cl-no-signed-zeros: engedélyezi, hogy a fordító figyelmen kívül hagyja az előjel nélküli nulla különbséget.
  • -cl-fast-relaxed-math: a lebegőpontos szabványok enyhítése, ami gyorsabb, de pontatlanabb kódot eredményez.
  • -D makrók definiálására: -DUSE_DOUBLE.

Hibakezelés build közben: A clBuildProgram visszatérési értéke CL_BUILD_PROGRAM_FAILURE esetén a build napló tartalmazza a fordítási hibákat. A napló lekérdezése:

size_t log_size;
clGetProgramBuildInfo(program, device, CL_PROGRAM_BUILD_LOG, 
                      0, NULL, &log_size);
char *log = (char *)malloc(log_size);
clGetProgramBuildInfo(program, device, CL_PROGRAM_BUILD_LOG, 
                      log_size, log, NULL);
printf("Build log:\n%s\n", log);

30.1.7 Tipikus hibák és elkerülésük

A gyakorlatban a kezdő OpenCL-fejlesztők leggyakoribb hibái a következő kategóriákba sorolhatók:

1. Hiányzó address space minősítő a kernel-argumentumokban:

Hibás:

__kernel void bad(float *a) { ... }

Helyes:

__kernel void good(__global float *a) { ... }

A fordító hibát jelez, mert a kernel-argumentum-mutatónak explicite meg kell adni a memóriateret. Ez a leggyakoribb hiba a C99-ből érkező fejlesztőknél.

2. Hibás indexelés vagy határkezelés hiánya:

Ha a globális méret nagyobb, mint a tömb hossza, a kernel túlindexeli a memóriát, ami nem definiált viselkedést, akár eszközleállást is okozhat. A feltételes utasítás vagy a stride-loop használata kötelező.

3. Nem igazított vektoros hozzáférés:

A globális memóriában lévő tömböt float4 típusú mutatóra alakítani csak akkor szabad, ha a tömb kezdőcíme 16 bájtra igazított. Ellenkező esetben vload4-et kell használni:

float4 v = vload4(i, a);  // Biztonságos, nem igazított hozzáférés
vstore4(v, i, c);          // Biztonságos tárolás

4. A beépített függvények helytelen használata:

Az OpenCL beépített függvényei a C szabványos könyvtár helyett állnak. A sqrt, sin, fabs stb. elérhetők, de a printf nem használható kernelben (kivéve bizonyos kiterjesztéssel). A stringkezelő függvények szintén hiányoznak.

5. Lebegőpontos pontossággal kapcsolatos téves feltevések:

Az OpenCL C a C99-hez hasonló lebegőpontos szemantikát követ, de a gyors matematikai opciók (-cl-fast-relaxed-math) enyhítik a szabványt. A cl_fma függvény a fused multiply-add műveletet garantálja, ami pontosabb, mint a szekvenciális szorzás-összeadás. Ha a numerikus pontosság kritikus, kerüljük a gyors matematikai opciókat.

30.1.8 A kernel és a work-item kapcsolata

A kernelben a következő beépített függvények adják meg a work-item azonosítóit:

  • get_global_id(dim): a work-item globális azonosítója a dim dimenzióban. Ez a dimenzió a kernel indításakor megadott globális méret szerint alakul.
  • get_local_id(dim): a work-item azonosítója a work-groupon belül.
  • get_group_id(dim): a work-group azonosítója.
  • get_local_size(dim): a work-group mérete a dim dimenzióban.
  • get_global_size(dim): a teljes globális méret a dim dimenzióban.
  • get_num_groups(dim): a work-groupok száma a dim dimenzióban.

Ezek a beépített függvények a __kernel függvényben mindenhol elérhetők, de a nem kernel függvényekben (pl. helper függvények) nem garantált a viselkedésük, ezért kerüljük a használatukat azokban.

A work-groupok és a work-itemek hierarchiája az OpenCL C-ben szorosan kapcsolódik a memóriaterekhez: a __local memória a work-group szintű, a __private minden work-itemhez kötött. Ez a hierarchia a párhuzamos algoritmusok tervezésének alapja.

30.1.9 Az OpenCL C és a CUDA C++ összehasonlítása

Bár mindkét nyelv SIMT-modellt használ, lényeges különbségek vannak:

Szempont OpenCL C CUDA C++
Kernel jelölése __kernel __global__
Memóriatér-minősítők __global, __local, __constant, __private __device__, __shared__, __constant__ (a __global__ a kernel jelölésére szolgál)
Work-item azonosítók get_global_id(0) blockIdx.x * blockDim.x + threadIdx.x vagy threadIdx.x
Szinkronizáció barrier(CLK_LOCAL_MEM_FENCE) __syncthreads()
Vektortípusok float4, int8 stb. float4, int4 stb. (CUDA vektortípusok)
Fordítás Futásidejű (host API-n keresztül) Fordítási időben (nvcc)
Atomics atomic_add, atomic_cmpxchg stb. atomicAdd, atomicCAS stb.
Névterek Nincs (C99) C++ névterek, template-ek

Az OpenCL C explicit memóriatér-minősítői egyértelműbbé teszik az adatok helyét, míg a CUDA C++ a globális memóriát alapértelmezettként kezeli. A CUDA C++ gazdagabb nyelvi kifejezőerővel rendelkezik (template-ek, osztályok), ami nagyobb rugalmasságot ad a generikus kód írásához. Az OpenCL C azonban szélesebb hardvertámogatást kínál, beleértve a GPU-kat, CPU-kat, FPGA-kat és DSP-ket is.

30.1.10 Ellenőrzési szempont a fejezet állításaihoz

A fejezetben bemutatott nyelvi jellemzők a Khronos OpenCL C specifikációján alapulnak, amely a 3.0 verzióig bezárólag stabil. Az OpenCL C specifikáció pontos szövege a registry.khronos.org/OpenCL/ címen érhető el; azonban a specifikáció verziója és az egyes eszközök által támogatott kiterjesztések eltérhetnek. A vektorizált hozzáférés igazítási követelményei a CL_DEVICE_MEM_BASE_ADDR_ALIGN eszközlekérdezéssel ellenőrizhetők. A fordító által generált kód hatékonysága az adott implementációtól függ; a fejezetben leírt optimalizációs lehetőségek általános irányelvek, nem garantált teljesítményjavulás minden hardveren.

30.1.11 Labor: Vektorösszeadás OpenCL-ben

Cél: OpenCL kernel implementálása és futtatása vektorösszeadásra, a fordítási folyamat és a hibakezelés gyakorlása.

Követelmények:

  1. Írj OpenCL C kernelt, amely két float vektor elemenkénti összegét számítja.
  2. A host program C++17-ben készül, az OpenCL 1.2+ API-t használja.
  3. A kernel forráskódját futásidőben fordítsd le, ellenőrizd a build naplót.
  4. A hibaellenőrzés minden OpenCL API-hívást lefed.
  5. A futtatás előtt végezz warm-up futtatást, majd 10 mérés.
  6. Rögzítsd az eszköz nevét, az OpenCL verziót, a work-group méretét és a globális méretet.
  7. A mért és a várt eredményt különítsd el; a numerikus egyezést fabs(diff) < 1e-5 toleranciával ellenőrizd.

Minta kernel (OpenCL C):

__kernel void vector_add(
    __global const float *a,
    __global const float *b,
    __global float *c,
    const int n)
{
    int i = get_global_id(0);
    if (i < n) {
        c[i] = a[i] + b[i];
    }
}

Futtatási környezet (helyőrző): Az eszköz egy izolált laborban lévő OpenCL-kompatibilis GPU, pl. egy régebbi AMD vagy Intel GPU. A mérési naplóban szerepelnie kell az eszköz nevének, a driver verziójának és az OpenCL verziójának. A tényleges futtatás előtt ellenőrizni kell az eszköz elérhetőségét és a szolgáltatói feltételeket.

Mérési napló minta (nem valós eredmény):

Device: [eszköznév_helyőrző]
OpenCL: 3.0
Driver: [driver_verzió_helyőrző]
Input: n = 1 048 576, float
Work-group size: 256
Float precision: FP32

Run #1: 0.42 ms
Run #2: 0.39 ms
...
Run #10: 0.40 ms
Mean: 0.41 ms, median: 0.40 ms, std: 0.02 ms

Várt eredmény: c[i] = a[i] + b[i]
Max abs error: 0.0 (egyszerű összeadás, FP32)

Ez a napló minta; a tényleges mérést az adott laboron kell elvégezni. A fejezetben szereplő kódok fordítási és futtatási szintaktikája ellenőrzött, de a hardver-specifikus viselkedés (pl. cache-méret, órajel) helyőrzőként szerepel.

30.1.12 Önellenőrző kérdés

Adott a következő OpenCL C kerneltöredék:

__kernel void compute(__global float *a, float b)
{
    int i = get_global_id(0);
    a[i] = a[i] * b;
}

Az a mutató melyik memóriatérben van? A b paraméter melyik memóriatérben van? Mi történik, ha a kernel argumentum deklarációjából elhagyjuk a __global minősítőt az a mutató elől? Válaszodat indokold az OpenCL C szabályai alapján.
