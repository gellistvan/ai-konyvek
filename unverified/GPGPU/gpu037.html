10.4 Tipikus CUDA-hibák és megelőzésük

Amikor egy CUDA-program hibát jelez, a hibaüzenet gyakran csak a felszín. A kernel aszinkron végrehajtása, a memóriaterek eltérő élettartama és a hardveres erőforrás-korlátok együttesen olyan hibamintákat hoznak létre, amelyek időnként determinisztikusnak tűnnek, máskor viszont csak adott foglalási sorrendben, órajel mellett vagy egy másik GPU-generáción reprodukálhatók. Ebben az alfejezetben ezért nem csupán egyes hibákat javítunk, hanem hibaminta-katalógust építünk: minden bejegyzéshez tartozik reprodukáló kód, várt eredmény, mért eredmény, magyarázat és megelőzési stratégia. A cél, hogy a tipikus hibákat azonnal felismerjük, és ne csak a tünetet, hanem a helyes megoldást is meg tudjuk indokolni.

A katalógus három nagy csoportra oszlik:

  1. szinkronizációs és API-hibák,
  2. memória-hozzáférési hibák,
  3. erőforrás- és launch-hibák.

Ezek a csoportok nem tisztán szétválaszthatók, mert egy hibás kernel például egyszerre okozhat illegális memória-hozzáférést és később sticky hibát, de a katalógusban a szétválasztás megkönnyíti a rendszerezést.

10.4.1 1. Hibaosztályozás és detektálási stratégiák

A CUDA futásidő hibái két nagy csoportba sorolhatók aszerint, hogy mikor jelentkeznek.

  • Azonnali hibák: például cudaMalloc, cudaMemcpy, cudaDeviceGetAttribute szinkron hívások hibái. Ezeket a hívás visszatérési értékéből azonnal látjuk.
  • Késleltetett hibák: a kernelindítás és az aszinkron másolás hibái gyakran csak a szinkronizáláskor válnak láthatóvá, mert a CPU továbbfut, miközben a GPU még dolgozik.

A korábbi alfejezetben bevezetett hibamakrót itt is használjuk, de kiegészítjük egy CHECK_LAUNCH makróval, amely a kernelindítás utáni cudaGetLastError és a cudaDeviceSynchronize hibáját is ellenőrzi:

// error_util.cuh
#pragma once
#include <cuda_runtime.h>
#include <cstdio>
#include <cstdlib>

#define CHECK_CUDA(call)                                                     \
    do {                                                                     \
        cudaError_t err = (call);                                            \
        if (err != cudaSuccess) {                                            \
            std::fprintf(stderr, "CUDA error in %s at %s:%d: %s\n",          \
                         #call, __FILE__, __LINE__, cudaGetErrorString(err)); \
            std::exit(EXIT_FAILURE);                                         \
        }                                                                    \
    } while (0)

#define CHECK_LAUNCH(kernel_call)                                            \
    do {                                                                     \
        kernel_call;                                                         \
        CHECK_CUDA(cudaGetLastError());                                      \
        CHECK_CUDA(cudaDeviceSynchronize());                                 \
    } while (0)

A CHECK_LAUNCH azért fontos, mert a cudaGetLastError() közvetlenül a <<<...>>> után sokszor már elkapja az érvénytelen launch-konfigurációt, de a kernel futása közben keletkező hibát – például illegális memória-hozzáférést – csak a cudaDeviceSynchronize() hozza felszínre.

Az 1. táblázat a leggyakoribb hibakategóriákat foglalja össze.

Nem szinkronizált hozzáférés időnként nulla, lefutott adat vagy szemét cudaDeviceSynchronize, cudaStreamSynchronize, event

10.4.2 2. Nem szinkronizált másolás és törött launch

10.4.3 2.1. Nem szinkronizált másolás

Az egyik leggyakoribb hiba, hogy a program cudaMemcpyAsync után azonnal olvassa a host oldali puffert. A cudaMemcpyAsync a default streamen vagy egy megadott streamen aszinkron módon másolhat, ezért a CPU a másolás befejezése előtt hozzáférhet a célterülethez. A hiba különösen akkor szembetűnő, ha a host memória pinned (page-locked), mert ilyenkor a másolás valóban aszinkron lehet. Ha a host memória pageable, a CUDA-meghajtó gyakran szinkron másolásra esik vissza, így a hiba véletlenül eltűnhet – ami még veszélyesebb, mert a kód egy másik környezetben hibázik.

Az alábbi példa szándékosan reprodukálja a hibát:

// E01_unsync_memcpy.cu
#include <cuda_runtime.h>
#include <cstdio>
#include "error_util.cuh"

__global__ void fill(float *dst, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) dst[i] = 3.1415f;
}

int main() {
    const int n = 1 << 20;
    float *d_a = nullptr;
    float *h_a = nullptr;

    CHECK_CUDA(cudaMalloc(&d_a, n * sizeof(float)));
    CHECK_CUDA(cudaMallocHost(&h_a, n * sizeof(float))); // pinned

    fill<<<(n + 255) / 256, 256>>>(d_a, n);
    CHECK_CUDA(cudaGetLastError());

    // Hibás: a másolás aszinkron, még nem biztos, hogy kész.
    CHECK_CUDA(cudaMemcpyAsync(h_a, d_a, n * sizeof(float),
                               cudaMemcpyDeviceToHost, 0));
    std::printf("h_a[0] szinkronizálás előtt: %f\n", h_a[0]); // verseny

    CHECK_CUDA(cudaDeviceSynchronize());
    std::printf("h_a[0] szinkronizálás után:  %f\n", h_a[0]);

    CHECK_CUDA(cudaFree(d_a));
    CHECK_CUDA(cudaFreeHost(h_a));
    return 0;
}

A várt eredmény az, hogy a h_a[0] szinkronizálás előtt értéke nem definiált; leggyakrabban a korábbi puffertartalom vagy nulla jelenik meg. A szinkronizálás utáni érték 3.141500. A mért eredményt a laborban rögzíteni kell; a lényeg, hogy az első kiírás nem garantált, tehát hibának számít. A helyes megoldás a másolás után a megfelelő streamet szinkronizálni:

CHECK_CUDA(cudaMemcpyAsync(h_a, d_a, n * sizeof(float),
                           cudaMemcpyDeviceToHost, 0));
CHECK_CUDA(cudaDeviceSynchronize()); // vagy cudaStreamSynchronize(stream)

Ha a másolás nem a default streamen fut, akkor cudaStreamSynchronize(stream) vagy egy CUDA event használandó. Ha a másolásnak mindenképpen szinkronnak kell lennie, akkor a cudaMemcpy a megfelelő választás. A cudaMemcpyAsync-hoz lehetőleg pinned memóriát használjunk, mert pageable memória esetén az aszinkronitás nem garantált, és a teljesítmény is rosszabb.

Ugyanez a minta más programozási modellekben is megjelenik. OpenCL-ben a clEnqueueReadBuffer után a host oldali olvasás előtt clFinish vagy wait event szükséges. JAX-ban az eszközön futó műveletek aszinkron dispatch-t használnak, ezért a NumPy tömbbé alakítás előtt block_until_ready() hívandó, ha azonnali host oldali értékre van szükség.

10.4.4 2.2. Törött launch

Törött launch alatt azt értjük, amikor a kernelindítás paraméterei érvénytelenek, vagy a kernel binárisa nem futtatható az adott eszközön. Ilyenkor a kernel el sem indul, de a hiba csak a cudaGetLastError vagy a szinkronizálás során látszik.

Klasszikus példa a blokkméret túllépése. A CUDA eszközökön a blokkonkénti szálak maximális száma jellemzően 1024, de ezt mindig a cudaDevAttrMaxThreadsPerBlock attribútumból kérdezzük le. A következő kód szándékosan 1025 szálat indít:

// E02_invalid_launch.cu
#include <cuda_runtime.h>
#include <cstdio>
#include "error_util.cuh"

__global__ void dummy(float *out) {
    if (threadIdx.x == 0) *out = 1.0f;
}

int main() {
    float *d_out = nullptr;
    CHECK_CUDA(cudaMalloc(&d_out, sizeof(float)));

    // blockDim.x = 1025 meghaladja a maximumot (általában 1024)
    dummy<<<1, 1025>>>(d_out);
    cudaError_t err = cudaGetLastError();
    if (err != cudaSuccess) {
        std::fprintf(stderr, "Launch hiba: %s\n", cudaGetErrorString(err));
    }
    CHECK_CUDA(cudaDeviceSynchronize());
    CHECK_CUDA(cudaFree(d_out));
    return 0;
}

A várt hiba cudaErrorInvalidConfiguration, a szöveges üzenet pedig általában invalid configuration argument. A cudaGetLastError közvetlenül a launch után már jelezheti a hibát, mert a launch-konfigurációt a vezérlő még a kernel indítása előtt ellenőrzi. Fontos azonban, hogy a cudaDeviceSynchronize hibáját is ellenőrizzük, mert egy későbbi aszinkron hiba itt is megjelenhet.

Egy másik törött launch akkor keletkezik, ha a kért shared memory mérete nagyobb, mint az eszköz által támogatott maximum:

// E04_shared_mem_over.cu
#include <cuda_runtime.h>
#include <cstdio>
#include "error_util.cuh"

__global__ void sm_kernel() {
    extern __shared__ float smem[];
    smem[threadIdx.x] = threadIdx.x;
}

int main() {
    int max_smem = 0;
    CHECK_CUDA(cudaDeviceGetAttribute(&max_smem,
        cudaDevAttrMaxSharedMemoryPerBlock, 0));
    std::printf("Max shared mem per block: %d byte\n", max_smem);

    // a kért shared memória eggyel nagyobb a megengedettnél
    sm_kernel<<<1, 32, (size_t)max_smem + 1>>>();
    cudaError_t err = cudaGetLastError();
    if (err != cudaSuccess) {
        std::fprintf(stderr, "Launch hiba: %s\n", cudaGetErrorString(err));
    }
    CHECK_CUDA(cudaDeviceSynchronize());
    return 0;
}

A cudaGetLastError itt szintén cudaErrorInvalidConfiguration vagy cudaErrorLaunchOutOfResources hibát adhat a környezettől függően. A pontos mért szöveget a labor naplójában rögzítsük.

A törött launch harmadik gyakori oka az architektúra-eltérés. Ha a kernelt csak sm_80 binárissal fordítjuk, de a futtató eszköz sm_70 vagy sm_89, akkor a cudaErrorNoKernelImageForDevice hibát kaphatjuk, amennyiben nincs kompatibilis PTX vagy megfelelő bináris. Ennek elkerülésére a fordításkor érdemes -gencode kapcsolóval több architektúrát is beágyazni, vagy -arch=native kapcsolót használni a fejlesztői gépen. A hordozható binárisokkal kapcsolatos részletek a CUDA ökoszisztéma és a hardvergenerációk és A CUDA toolkit és a driver telepítése alfejezetekben szerepelnek.

10.4.5 3. Erőforrás-kimerülés

Az erőforrás-kimerülés a hibák azon családja, amikor a program logikailag helyes, de az eszköz fizikai korlátjaiba ütközik. A legfontosabb erőforrások: globális memória, blokkonkénti shared memory, blokkonkénti regiszterek, blokkméret és gridméret.

10.4.6 3.1. Globális memória kimerülése

A cudaMalloc sikertelen lesz, ha nincs elegendő szabad eszközmemória. Ezt a hibát mindig kezelni kell, mert nagy pufferű tudományos kódokban a felhasználó gyakran szeretné a lehető legnagyobb adatot betölteni. Az alábbi kód lekérdezi a szabad memóriát, majd szándékosan nagyobb foglalást kísérel meg:

// E06_mem_exhaust.cu
#include <cuda_runtime.h>
#include <cstdio>
#include "error_util.cuh"

int main() {
    size_t free_mem = 0, total_mem = 0;
    CHECK_CUDA(cudaMemGetInfo(&free_mem, &total_mem));
    std::printf("Szabad: %.2f MiB / Összes: %.2f MiB\n",
                free_mem / 1048576.0, total_mem / 1048576.0);

    void *ptr = nullptr;
    cudaError_t err = cudaMalloc(&ptr, free_mem + (1ULL << 30)); // biztos túl nagy
    if (err != cudaSuccess) {
        std::printf("cudaMalloc sikertelen: %s\n", cudaGetErrorString(err));
    }
    return 0;
}

A várt hiba cudaErrorMemoryAllocation. A mért üzenet a laborban rögzítendő. Fontos, hogy a cudaMemGetInfo által jelentett szabad memória nem garancia arra, hogy egy azonos méretű foglalás sikeres lesz, mert a memória töredezett lehet, és a CUDA-kontextus, a futó kernelek vagy más folyamatok is foglalhatnak. Nagy allokációk előtt érdemes a tényleges foglalást kisérletként kezelni, és hiba esetén csökkenteni a méretet vagy más memóriastratégiát választani.

A kimerülés megelőzhető a munkakészlet csökkentésével, streaming feldolgozással, unified memory használatával vagy több GPU közötti elosztással. A hiba kezelésének soha nem szabad az lennie, hogy figyelmen kívül hagyjuk a cudaMalloc visszatérési értékét, mert a null mutatóval való későbbi kernelindítás illegális hozzáférést okoz.

10.4.7 3.2. Launch erőforrások kimerülése

A kernelindítás akkor is meghiúsulhat, ha a globális memória elegendő. A leggyakoribb launch erőforrás-korlátok:

  • maximális szálak száma blokkonként (cudaDevAttrMaxThreadsPerBlock),
  • maximális shared memory blokkonként (cudaDevAttrMaxSharedMemoryPerBlock),
  • maximális regiszterek száma blokkonként (cudaDevAttrMaxRegistersPerBlock),
  • maximális grid dimenziók (cudaDevAttrMaxGridDim).

A shared memory túllépését már láttuk. A regiszternyomás akkor okoz launch hibát, ha a kernel regiszterigénye és a blokkméret szorzata meghaladja a blokkonkénti regiszterlimitet. Például ha egy kernel 128 regisztert használ szálanként, és 1024 szálból álló blokkokat indítunk, akkor az elméleti igény 128 × 1024 = 131 072 regiszter, ami meghaladhatja a cudaDevAttrMaxRegistersPerBlock értékét (általában 65 536). Ilyenkor a launch cudaErrorLaunchOutOfResources hibát adhat.

A megoldás három irányból közelíthető:

  • csökkentsük a blokkméretet,
  • csökkentsük a regiszterhasználatot __launch_bounds__ vagy -maxrregcount segítségével,
  • egyszerűsítsük a kernel belső kifejezéseit, hogy a fordító kevesebb regisztert használjon.

A regiszterhasználat pontos mérésére az Nsight Compute és a --ptxas-options=-v fordítási kimenet alkalmas, de ez már a Regiszterhasználat és spill alfejezet részletes anyaga.

10.4.8 3.3. Sticky hibák és device lost

Az illegális memória-hozzáférés – például egy global memóriában történő túlindexelés – nem egyszerű kivétel, hanem gyakran úgynevezett sticky hiba. A CUDA-kontextus ilyenkor megromolhat, és minden további CUDA-hívás cudaErrorIllegalAddress vagy cudaErrorUnknown hibát adhat, amíg a kontextust újra nem inicializáljuk.

Az alábbi kód szándékos túlindexelést hajt végre:

// E03_oob_write.cu
#include <cuda_runtime.h>
#include <cstdio>
#include "error_util.cuh"

__global__ void oob_write(int *buf, int n) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx == n) buf[idx] = 1; // n index nem létezik
}

int main() {
    const int n = 128;
    int *d_buf = nullptr;
    CHECK_CUDA(cudaMalloc(&d_buf, n * sizeof(int)));

    oob_write<<<1, 129>>>(d_buf, n); // 129 szál, idx 128 túlír
    cudaError_t err = cudaDeviceSynchronize();
    if (err != cudaSuccess) {
        std::fprintf(stderr, "Szinkron hibája: %s\n", cudaGetErrorString(err));
    }
    // Sticky hiba esetén itt a további hívások is hibázhatnak.
    cudaError_t err2 = cudaFree(d_buf);
    if (err2 != cudaSuccess) {
        std::fprintf(stderr, "cudaFree hibája: %s\n", cudaGetErrorString(err2));
    }
    return 0;
}

A cudaDeviceSynchronize várt hibája cudaErrorIllegalAddress. Ezt követően a cudaFree is hibázhat, mert a kontextus megromlott. A legbiztonságosabb ilyenkor a folyamat befejezése vagy a cudaDeviceReset() hívása, de a cudaDeviceReset hatása az egész eszközkontextusra kiterjed, ezért éles kódban ritkán megfelelő. A hibás kernelt lehetőleg izolált folyamatban futtassuk, ahol a kontextus elvesztése nem érint más kódot.

A compute-sanitizer memcheck eszköze pontosan az ilyen hibákat képes még a sticky állapot kialakulása előtt jelenteni. A parancs:

compute-sanitizer --tool memcheck ./E03_oob_write

A várt kimenetben szerepelnie kell egy Invalid global write of size 4 típusú sornak. A mért kimenetet a laborban rögzítsük. A sanitizer használata különösen fontos akkor, ha a kernel látszólag helyesen fut, de néha véletlenül túlír.

10.4.12 4.3. Kiegészítő minta: versenyhelyzet megfogása

A shared memory versenyhelyzet többnyire nem determinisztikus, ezért a racecheck eszköz nélkül nehéz észrevenni. A következő minta a 2.2. alfejezetből hiányzó barrier hibát mutatja:

// E05_shared_race.cu
#include <cuda_runtime.h>
#include <cstdio>
#include "error_util.cuh"

__global__ void race_kernel(float *out) {
    __shared__ float s_val;
    if (threadIdx.x == 0) s_val = 1.0f;
    // Hibás: nincs __syncthreads()
    out[0] = s_val; // más szálak talán nem látják az írást
}

int main() {
    float *d_out;
    CHECK_CUDA(cudaMalloc(&d_out, sizeof(float)));
    race_kernel<<<1, 32>>>(d_out);
    CHECK_CUDA(cudaDeviceSynchronize());
    CHECK_CUDA(cudaFree(d_out));
    return 0;
}

A compute-sanitizer --tool racecheck ./main parancs possible write-read race üzenetet ad. A helyes megoldás a __syncthreads() hívása a shared memóriába írás után, még a kiolvasás előtt:

__global__ void race_kernel(float *out) {
    __shared__ float s_val;
    if (threadIdx.x == 0) s_val = 1.0f;
    __syncthreads(); // minden szál látja az írást
    out[0] = s_val;
}

Fontos, hogy a __syncthreads() a blokk minden szálának ugyanazt a végrehajtási ágat kell, hogy jelentse. Divergens ágban a barrier használata a legtöbb CUDA-modellben érvénytelen, és a racecheck vagy a futás közbeni hiba szintén jelezheti.

10.4.13 4.4. Értékelési szempontok

A labor akkor teljesített, ha:

  • legalább hat hibamintát tartalmaz a katalógus,
  • minden mintához tartozik fordítható CUDA C++ forrás,
  • a build parancs és a futtatási parancs rögzítve van,
  • minden API-hívás hibája ellenőrzött,
  • a mért és a várt eredmény külön oszlopban szerepel,
  • a compute-sanitizer kimenetek a memcheck és a racecheck eszközzel is dokumentáltak,
  • a katalógus tartalmazza a környezeti adatokat: GPU, driver, CUDA, OS, nvcc verzió.

Ez a katalógus a későbbi fejezetek hibakeresési munkájához is alapot ad, mert a Globális memória coalescing alfejezettől kezdődő teljesítményméréseknél gyakran először a helyességi hibákat kell kizárni.

10.4.14 5. Összefoglalás és önellenőrző kérdés

A leggyakoribb CUDA-hibák nem a nyelv bonyolultságából, hanem az aszinkron végrehajtásból, a memóriaterek eltérő szemantikájából és az eszköz erőforrás-korlátaiból adódnak. A hibaminta-katalógus rendszeres vezetése segít abban, hogy a hibákat ne egyedi esetként kezeljük, hanem felismerjük a mögöttes mintát.

Önellenőrző kérdés: Adott egy program, amely cudaMemcpyAsync hívással másol device-ról hostra, majd közvetlenül a másolás utáni sorban kiírja a host puffer első elemét. Miért helytelen ez a minta? Nevezze meg a két leggyakoribb javítást, és magyarázza el, miért fontos a pinned host memória használata az aszinkron másoláshoz.

A válaszban szerepelnie kell annak, hogy a cudaMemcpyAsync aszinkron lehet, ezért az olvasás versenyhelyzetet okoz. A javítás cudaDeviceSynchronize vagy cudaStreamSynchronize a másolás után, illetve szinkron cudaMemcpy használata, ha a szinkronitás követelmény. A pinned memória azért fontos, mert pageable memória esetén az aszinkron másolás nem garantált, és a teljesítmény is romlik.

Ezzel a katalógussal a következő alfejezet (Globális memória coalescing) már arra építhet, hogy a globális memória-hozzáférések teljesítményét elemezze anélkül, hogy helyességi hibák zavarnák a mérést.
