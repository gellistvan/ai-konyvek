17.3 Keresés és binary search

17.3.1 A párhuzamos keresés problémája

Az előző egység rendezési anyagára építve most feltesszük, hogy a bemeneti tömb monoton növekvően rendezett. A rendezett tömbön a keresés nem egyetlen elemi művelet, hanem egy egész lekérdezési család: megkereshetjük egy konkrét kulcs első előfordulását, azt az indexet, ahová a kulcs beszúrható, vagy egy intervallum két határát. A GPU-n a keresés nem úgy párhuzamosítható, hogy a logaritmikus lépéseket szétosztjuk a szálak között – ez a naiv szemlélet a bináris keresés belső függőségei miatt nem működik. A párhuzamosság forrása a lekérdezések tömege: ha sok kulcsot kell keresni ugyanabban a rendezett tömbben, minden kulcshoz tartozhat egy szál, és a szálak egymástól függetlenül futhatnak.

Ezt a mintát batch binary searchnek nevezzük. Ez a fejezet a batch binary search kernel építőköveit, a lower_bound és upper_bound szemantikáját, a SIMT-divergencia következményeit és a memóriaelérési mintákat tárgyalja. A hangsúly a gyakorlati, ellenőrizhető kernelíráson van; a következő egység (Selection és order statistics) az itteni alsó határt selection és order statistics feladatokban használja majd.

17.3.2 lower_bound és upper_bound a rendezett tömbön

A C++ STL lower_bound algoritmusa egy rendezett tartományban megadja azt a pozíciót, ahová a keresett kulcs a monoton növekvő sorrend megtartásával beilleszthető. Precízebben:

lower_bound(q)=|{j|0≤j<n,data[j]<q}|. \operatorname{lower\_bound}(q) = \left|\{\,j\;|\;0 \le j < n,\; data[j] < q\,\}\right|.

Ez az első olyan j index, amelyre data[j]≥qdata[j] \ge q teljesül, vagy n, ha ilyen elem nincs. A upper_bound az első olyan index, amelyre data[j]>qdata[j] > q, másképpen:

upper_bound(q)=|{j|0≤j<n,data[j]≤q}|. \operatorname{upper\_bound}(q) = \left|\{\,j\;|\;0 \le j < n,\; data[j] \le q\,\}\right|.

A kettő közötti tartomány az összes q-val egyenlő elem folytonos intervallumát adja. Tekintsük a következő kis példát:

data = [1, 3, 3, 5, 7]

lower_bound(3) -> 1
upper_bound(3) -> 3
lower_bound(4) -> 3
lower_bound(0) -> 0
lower_bound(8) -> 5

A GPU-s keresési kernelekben ritkán van szükség a std::lower_bound C++-os verziójának közvetlen hívására, de a szemantika pontos ismerete kritikus. A hibakezelés, a range query, a histogram és a join jellegű műveletek mind ezt az alsó/felső határ definíciót használják.

A párhuzamos keresés szempontjából a lower_bound azért előnyösebb a lineáris keresésnél, mert a lépésszáma O(logn)O(\log n). Ez a GPU-n azonban csak a lépések számát korlátozza; a memóriaelérés mintája ettől még lehet kedvezőtlen.

17.3.3 Batch binary search: a párhuzamosság forrása

A bináris keresés belső szerkezete szekvenciális: a következő középindex az aktuális intervallum határaitól függ. Egyetlen kulcs keresését nem lehet O(logn)O(\log n) lépésnél jobban párhuzamosítani a hagyományos összehasonlításos modellben. A GPU-n viszont három eltérő stratégiát érdemes megkülönböztetni.

  1. One-thread-per-query batch: minden szál egyetlen kulcsot keres. Ez a legegyszerűbb és a leggyakoribb olyan esetekben, amikor a lekérdezések száma nagy. A párhuzamosság a query-k darabszámából jön.
  2. Warp-per-query: egyetlen kulcs keresésére egy egész warp dolgozik. Az intervallumot a warp szálai közösen, ugrásszerűen vizsgálják; ez akkor hasznos, ha a query-k száma kicsi, és a memóriaelérést a warp jobban ki tudja használni.
  3. Redukció-alapú tartomány-összevonás: nagyon nagy tömb és kevés kulcs esetén minden blokk egy tartományt vizsgál, majd atomi művelettel vagy kétfázisú redukcióval áll elő a globális alsó határ.

A fejezet fókusza az első stratégia, mert ez a legjobban illeszkedik a rendezés utáni táblaműveletekhez, és a leggyakrabban használt minta. A második és harmadik stratégia akkor válik fontossá, ha a lekérdezési arány m/nm/n kicsi; ezt az optimalizálási szempontok között röviden érintjük.

17.3.4 Naiv batch lower_bound kernel

Az alábbi kernel egy CUDA C++ template, amely minden szálra elvégzi a szekvenciális lower_bound logikát:

// CUDA C++ (C++17)
template <typename T>
__global__ void batch_lower_bound_kernel(
    const T* __restrict__ data, std::size_t n,
    const T* __restrict__ queries, std::size_t m,
    int* __restrict__ out)
{
    std::size_t tid = static_cast<std::size_t>(blockIdx.x) * blockDim.x + threadIdx.x;
    if (tid >= m) return;

    const T q = queries[tid];
    std::size_t lo = 0;
    std::size_t hi = n;

    while (lo < hi) {
        std::size_t mid = lo + ((hi - lo) >> 1);
        if (data[mid] < q) {
            lo = mid + 1;
        } else {
            hi = mid;
        }
    }

    out[tid] = static_cast<int>(lo);
}

A kernelben a szekvenciális lower_bound szokásos szerkezetét tartjuk meg: _lo_ az alsó, _hi_ a felső nyílt intervallumhatár, _mid_ az egészrész közép. A data[mid] < q összehasonlítás után az intervallum feleződik, és az elágazás a keresett kulcs helye szerint dönt.

A kernel launch alakja:

dim3 block(256);
dim3 grid(static_cast<unsigned int>((m + block.x - 1) / block.x));
cudaStream_t stream = 0;

batch_lower_bound_kernel<int><<<grid, block, 0, stream>>>(
    d_data, n, d_queries, m, d_out);

A grid- és blockdimenziók a m lekérdezésszámhoz igazodnak. A data és queries pointerek const és __restrict__ minősítőt kapnak; a __restrict__ azt ígéri a fordítónak, hogy a mutatók nem aliasolódnak, így a compiler read-only cache-t és agresszívabb optimalizációt alkalmazhat. A kernelben az out[tid] írása coalesced, mert a szomszédos szálak szomszédos indexeket írnak. A queries[tid] olvasása szintén coalesced, ha a szálak lineárisan indexeltek. A nehéz memóriaelérés tehát nem ezeknél, hanem a data[mid] olvasásnál jelenik meg.

17.3.5 Divergencia és memóriaelérés

A batch binary search kernel legfontosabb jellemzője, hogy a szálak egymástól függetlenül, más-más intervallumhatárokkal dolgoznak. Egy warp 32 szálat futtat egyszerre. A while ciklus feltétele és a belső if elágazás miatt a szálak egy része különböző vezérlési útra lép.

A lépésszám-divergencia abból adódik, hogy a szekvenciális bináris keresés lépésszáma az intervallum hosszától és a kulcs elhelyezkedésétől függ. Ha nn nem kettőhatvány, a különböző kulcsoknál a ciklus hossza eltérhet. A laborban az n=224n = 2^{24} méretet ezért választjuk kettőhatványnak: ebben a speciális esetben a lépésszám minden szálra pontosan 24, így a lépésszám-divergencia eltűnik, és a megfigyelés a memóriaelérésre összpontosítható. Ez a választás didaktikailag fontos: a batch binary search megértéséhez a vezérlési és memória-divergenciát külön kell kezelni.

A memóriaelérési divergencia a gyakorlatban nagyobb teljesítményhatású. A data[mid] utasítás a warp 32 szálában 32 különböző címéről olvas, mert minden szál más mid-et számolt. A global memória coalescing – amelyet a Globális memória coalescing részletez – ilyenkor töredezetté válik. Egyetlen 4 bájtos int elemeket tartalmazó tömbben a 32 szál által kért 32 cím akár több tucat 128 bájtos cache line-t is érinthet, így a memória-alrendszer a hasznos 128 bájt helyett sokkal nagyobb adatmennyiséget mozgat. A bináris keresés memóriateljesítménye ezért inkább a véletlen hozzáférésű cache-viselkedéshez, nem a streaming sávszélességhez hasonlít.

A C++ kódban a const T* __restrict__ data segíti a fordítót abban, hogy a data hozzáférést a read-only cache (LDG) útvonalon keresztül valósítsa meg. Ez a lookup-tábla jellegű hozzáféréseknél csökkentheti a L1-nyomást, de a coalescing jellegzetességein nem változtat. Ha a rendezett tömb kicsi, a shared memory használata is szóba jöhet:

// Részlet: shared memory tiling, ha a rendezett tömb befér egy blokkba.
extern __shared__ int s_data[];
// Betöltés coalesced módon, __syncthreads() után a bináris keresés.

A shared memory-ben a bináris keresés sebességére a bank conflictok is hatással lesznek, mert a szálak itt is különböző címeket olvasnak. A legtöbb valós esetben a rendezett tömb jóval nagyobb, mint a shared memory, ezért a batch binary search global memory és cache-hierarchia függő.

Egy további optimalizálás a warp-aggregated binary search: ilyenkor a warp 32 szálát egyetlen kulcs keresésére állítjuk, és a szálak a vizsgált intervallum mentén egymás melletti elemeket olvasnak. Ez a minta a batch strategy helyett akkor nyerhet, ha a query-k száma kicsi, mert a warp memória-hozzáférése összefüggőbbé tehető. A batch binary search és a warp-aggregated search közötti választás a lekérdezések száma, a tömb mérete és a cache-paraméterek függvénye.

17.3.6 Gyakori hibák és helyes megoldások

A batch binary search kernelben több hiba ismétlődően felbukkan.

  1. Rendezetlen bemenet: ha a data nem monoton növekvő, a lower_bound eredménye undefined. Ez a leggyakoribb szemantikai hiba, mert a kernel nem ellenőrzi a rendezettséget. A labor előtt a generált data rendezettségét a CPU-oldali std::is_sorted-del ellenőrizni kell.
  2. Túlfolyás a középindexben: a (lo + hi) / 2 kifejezés nagy nn esetén túlcsordulhat. A helyes formula lo + (hi - lo) / 2 vagy lo + ((hi - lo) >> 1). A labor kód ezt használja.
  3. int méretindexek: ha nn meghaladja az INT_MAX-ot, a kimeneti index nem fér int-be. A laborban n=224n = 2^{24}, tehát az int elegendő, de nagyobb tömböknél size_t kimenetet kell használni.
  4. Nem ellenőrzött CUDA-hívások: a launch utáni cudaGetLastError és a cudaDeviceSynchronize hiánya elrejtheti a hibákat. A könyvlaborkód minden API-hívást a CUDA_CHECK makróval ellenőriz.
  5. Lépésszám-divergencia: ha nn nem kettőhatvány, a szálak különböző számú iterációt futnak. A kettőhatvány méret a labormérésben ezt kontrollálja.
  6. Rossz __restrict__/const minősítés: ha a data pointer nem const restrict, a compiler nem feltételezhet read-only hozzáférést, és a cache-útvonal kevésbé hatékony.
  7. Nincs warmup és túl rövid mérési ablak: a laborban 10 warm-up futtatást és 5 darab, egyenként 20 ismétlésből álló mérési kört írunk elő.
  8. Végtelen ciklusveszély: ha a kernelben a lo/hi frissítése hibás, a while ciklus sosem ér véget, és az eszköz leállását okozhatja. A labor kernelét izolált környezetben, időkorláttal kell futtatni.

A helyes alsó határ ebben a fejezetben a szekvenciális lower_bound szabályok pontos megtartásával, de a GPU párhuzamossági modelljéhez illesztve készül.

17.3.7 Labor: batch binary search

A labor célja egy fordítható, futtatható batch binary search kernel elkészítése, amely rendezett int tömbben végzi a lower_bound lekérdezést. A bemeneti méret n=224n = 2^{24}, a lekérdezések száma m=220m = 2^{20}. A kimenet minden kulcshoz az alsó határ indexe. A referencia a CPU std::lower_bound.

// CUDA C++ (C++17)
// batch_lower_bound.cu
#include <cuda_runtime.h>
#include <cstdio>
#include <cstdlib>
#include <cstddef>
#include <vector>
#include <algorithm>
#include <random>
#include <cmath>

#define CUDA_CHECK(call)                                                        \
  do {                                                                          \
    cudaError_t err_ = (call);                                                  \
    if (err_ != cudaSuccess) {                                                  \
      std::fprintf(stderr, "CUDA error at %s:%d: %s\n", __FILE__, __LINE__,     \
                   cudaGetErrorString(err_));                                   \
      std::exit(EXIT_FAILURE);                                                  \
    }                                                                           \
  } while (0)

#define CUDA_LAST_CHECK()                                                       \
  do {                                                                          \
    cudaError_t err_ = cudaGetLastError();                                      \
    if (err_ != cudaSuccess) {                                                  \
      std::fprintf(stderr, "CUDA last error at %s:%d: %s\n", __FILE__, __LINE__,\
                   cudaGetErrorString(err_));                                   \
      std::exit(EXIT_FAILURE);                                                  \
    }                                                                           \
  } while (0)

__global__ void batch_lower_bound_kernel(
    const int* __restrict__ data, std::size_t n,
    const int* __restrict__ queries, std::size_t m,
    int* __restrict__ out)
{
    std::size_t tid = static_cast<std::size_t>(blockIdx.x) * blockDim.x + threadIdx.x;
    if (tid >= m) return;

    const int q = queries[tid];
    std::size_t lo = 0;
    std::size_t hi = n;

    while (lo < hi) {
        std::size_t mid = lo + ((hi - lo) >> 1);
        if (data[mid] < q) {
            lo = mid + 1;
        } else {
            hi = mid;
        }
    }

    out[tid] = static_cast<int>(lo);
}

int main() {
    const std::size_t n = std::size_t{1} << 24;  // 16 777 216
    const std::size_t m = std::size_t{1} << 20;  // 1 048 576

    // Bemeneti rendezett tömb
    std::vector<int> data(n);
    for (std::size_t i = 0; i < n; ++i) {
        data[i] = static_cast<int>(i);
    }

    // Lekérdező kulcsok
    std::vector<int> queries(m);
    std::mt19937 rng(1234);
    std::uniform_int_distribution<int> dist(0, static_cast<int>(n - 1));
    for (std::size_t i = 0; i < m; ++i) {
        queries[i] = dist(rng);
    }

    // CPU referencia
    std::vector<int> ref(m);
    for (std::size_t i = 0; i < m; ++i) {
        ref[i] = static_cast<int>(
            std::lower_bound(data.begin(), data.end(), queries[i]) - data.begin());
    }

    // Device allokációk
    int* d_data = nullptr;
    int* d_queries = nullptr;
    int* d_out = nullptr;
    CUDA_CHECK(cudaMalloc(&d_data, n * sizeof(int)));
    CUDA_CHECK(cudaMalloc(&d_queries, m * sizeof(int)));
    CUDA_CHECK(cudaMalloc(&d_out, m * sizeof(int)));

    CUDA_CHECK(cudaMemcpy(d_data, data.data(), n * sizeof(int), cudaMemcpyHostToDevice));
    CUDA_CHECK(cudaMemcpy(d_queries, queries.data(), m * sizeof(int), cudaMemcpyHostToDevice));

    dim3 block(256);
    dim3 grid(static_cast<unsigned int>((m + block.x - 1) / block.x));
    cudaStream_t stream = 0;

    // Warm-up
    for (int i = 0; i < 10; ++i) {
        batch_lower_bound_kernel<<<grid, block, 0, stream>>>(
            d_data, n, d_queries, m, d_out);
        CUDA_LAST_CHECK();
    }
    CUDA_CHECK(cudaDeviceSynchronize());

    // Mérési kör
    cudaEvent_t start, stop;
    CUDA_CHECK(cudaEventCreate(&start));
    CUDA_CHECK(cudaEventCreate(&stop));

    const int outer_reps = 5;
    const int inner_reps = 20;
    std::vector<float> batch_ms;
    batch_ms.reserve(outer_reps);

    for (int b = 0; b < outer_reps; ++b) {
        CUDA_CHECK(cudaEventRecord(start, stream));
        for (int i = 0; i < inner_reps; ++i) {
            batch_lower_bound_kernel<<<grid, block, 0, stream>>>(
                d_data, n, d_queries, m, d_out);
            CUDA_LAST_CHECK();
        }
        CUDA_CHECK(cudaEventRecord(stop, stream));
        CUDA_CHECK(cudaEventSynchronize(stop));

        float elapsed_ms = 0.0f;
        CUDA_CHECK(cudaEventElapsedTime(&elapsed_ms, start, stop));
        batch_ms.push_back(elapsed_ms / inner_reps);
    }

    float avg_ms = 0.0f;
    for (float t : batch_ms) avg_ms += t;
    avg_ms /= static_cast<float>(batch_ms.size());

    float var_ms = 0.0f;
    for (float t : batch_ms) {
        float d = t - avg_ms;
        var_ms += d * d;
    }
    var_ms /= static_cast<float>(batch_ms.size());
    float std_ms = std::sqrt(var_ms);

    std::printf("batch_lower_bound: avg=%.4f ms, std=%.4f ms\n", avg_ms, std_ms);

    // Eredmény ellenőrzése
    std::vector<int> host_out(m);
    CUDA_CHECK(cudaMemcpy(host_out.data(), d_out, m * sizeof(int), cudaMemcpyDeviceToHost));

    std::size_t mismatches = 0;
    for (std::size_t i = 0; i < m; ++i) {
        if (host_out[i] != ref[i]) {
            if (mismatches < 10) {
                std::printf("mismatch at %zu: got=%d expected=%d\n",
                            i, host_out[i], ref[i]);
            }
            ++mismatches;
        }
    }
    std::printf("matches: %zu/%zu mismatches\n", m - mismatches, m);

    CUDA_CHECK(cudaEventDestroy(start));
    CUDA_CHECK(cudaEventDestroy(stop));
    CUDA_CHECK(cudaFree(d_data));
    CUDA_CHECK(cudaFree(d_queries));
    CUDA_CHECK(cudaFree(d_out));

    return mismatches == 0 ? EXIT_SUCCESS : EXIT_FAILURE;
}

A build- és futtatási parancs:

nvcc -O3 -std=c++17 -arch=sm_80 -o batch_lower_bound batch_lower_bound.cu
./batch_lower_bound

Az -arch=sm_80 azt feltételezi, hogy a labor NVIDIA A100 vagy azzal kompatibilis compute capability 8.0 eszközt használ. A konkrét értéket mindig a labor saját GPU-jához kell igazítani.

17.3.8 OpenCL és JAX kitekintés

A batch binary search ugyanazt az egy-szál-per-kulcs logikát követheti OpenCL-ben is:

// OpenCL C
__kernel void batch_lower_bound(
    __global const int* data, ulong n,
    __global const int* queries, ulong m,
    __global int* out)
{
    size_t tid = get_global_id(0);
    if (tid >= m) return;

    int q = queries[tid];
    size_t lo = 0;
    size_t hi = n;

    while (lo < hi) {
        size_t mid = lo + ((hi - lo) >> 1);
        if (data[mid] < q) {
            lo = mid + 1;
        } else {
            hi = mid;
        }
    }

    out[tid] = (int)lo;
}

A JAX eszközláncban a searchsorted funkcionális, vektorizált lekérdezést nyújt:

# JAX
import jax.numpy as jnp

# data: (n,) rendezett tömb, queries: (m,) lekérdezési tömb
idx_left = jnp.searchsorted(data, queries, side="left")   # lower_bound
# side="right" az upper_bound, de a viselkedés backendenként eltérhet

A JAX és XLA háttérrendszerén a searchsorted implementációja architektúra- és verziófüggő. A TPU-n a rendezettségi előfeltétel, a NaN-kezelés és a hibaszemantika nem minden változatban azonos a C++ STL-lel. Az OpenCL/JAX részletek itt csak API-szintű minták; a laborban a CUDA C++ verzió az ellenőrzött út. A hordozhatósági korlátokat minden valós mérés előtt a használt opencl/xla verzió dokumentációjával egyeztetni kell.
