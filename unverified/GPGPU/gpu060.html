16.3 Histogram

A hisztogram a párhuzamos számítás egyik leggyakoribb építőköve: adott egy bemeneti sorozat és egy véges számú rekesz (bin); minden elemhez hozzárendelünk egy rekeszt, majd megszámoljuk, hány elem esik az egyes rekeszekbe. Az eredmény egy gyakorisági eloszlás, amelyet képfeldolgozásban (színtónus-hisztogram), statisztikai elemzésben, gépi tanulási jellemzők számításakor és szimulációkban is használunk. GPU-n a hisztogram számítása elsőre egyszerűnek tűnik: minden szál feldolgoz egy elemet, és növeli a megfelelő rekesz számlálóját. A kihívást az jelenti, hogy több szál egyszerre ugyanabba a rekeszbe írhat – ezt a versenyhelyzetet atomi műveletekkel vagy privatizációval kezeljük. Ez a fejezet a hisztogram mint atomi és privatizált művelet fogalmát járja körbe, bemutatja a blokkszintű privatizációt, elemzi a shared memory bank conflict jelenségét, és egy ellenőrizhető laborpéldán keresztül méri a két megközelítés teljesítményét.

16.3.1 1. A hisztogram mint atomi művelet

A legegyszerűbb GPU-s megvalósításban minden bemeneti elemhez egy szál tartozik. A szál kiszámítja az elem rekeszindexét, majd egy atomi összeadást hajt végre a globális memóriában tárolt hisztogramtömbön. Az atomicAdd garantálja, hogy az olvasás-módosítás-írás műveletsor oszthatatlan, így a végeredmény helyes marad még akkor is, ha több szál egyszerre ugyanabba a rekeszbe ír.

A naiv kernel CUDA C++-ban:

// CUDA C++ (C++17)
constexpr int NUM_BINS = 64;

__global__ void hist_naive(const int* data, int* hist, int n)
{
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = gridDim.x * blockDim.x;

    for (; idx < n; idx += stride) {
        int bin = data[idx] % NUM_BINS;
        atomicAdd(&hist[bin], 1);
    }
}

A grid-stride loop lehetővé teszi, hogy a kernel akkor is lefussa a teljes bemenetet, ha az elemszám nagyobb, mint az indított szálak száma. A bin számítása itt a % operátorral történik; ha a rekeszek száma kettő hatványa, bitművelettel (& (NUM_BINS-1)) gyorsabban elvégezhető, de az általánosság kedvéért a modulo marad.

A naiv megoldás előnye a rendkívüli egyszerűség: nincs szükség bonyolult szinkronizációra, a kód kevés sorból áll, és az atomi műveletek garantálják a helyes eredményt. Hátránya viszont a súlyos teljesítményprobléma: ha sok elem esik ugyanabba a rekeszbe, a globális memóriában lévő hist[bin] címre irányuló atomi műveletek sorosítva hajtódnak végre. A globális atomi művelet egy read-modify-write ciklus, amely a memóriavezérlőn keresztül megy; nagy kontenció esetén a szálak várakozni kényszerülnek, és a kernel átbocsátóképessége drasztikusan lecsökken. Mérések szerint erősen ferde eloszlásnál a naiv atomi megoldás akár egy nagyságrenddel lassabb is lehet, mint a privatizált változat.

16.3.2 2. Privatizált hisztogram: blokkszintű shared memory

A kontenció csökkentésének alapötlete az, hogy a globális atomi műveleteket részben kiváltjuk gyorsabb, blokkon belüli műveletekkel. Minden szálblokk saját, privát hisztogramot tart fenn a shared memóriában. A blokk szálai a bemeneti elemek feldolgozása során csak ebbe a privát tömbbe írnak atomi módon. A blokk végén, egy __syncthreads() után a privát hisztogramot egyetlen globális atomi összeadással egyesítik a globális hisztogrammal. Így a globális atomi műveletek száma blokkonként NUM_BINS darabra csökken, szemben a naiv megoldás N darabjával.

A privatizált kernel:

// CUDA C++ (C++17)
__global__ void hist_shared(const int* data, int* hist, int n)
{
    __shared__ int shist[NUM_BINS];

    // 1. A privát hisztogram inicializálása nullára
    for (int i = threadIdx.x; i < NUM_BINS; i += blockDim.x) {
        shist[i] = 0;
    }
    __syncthreads();

    // 2. Feldolgozás: atomi összeadás a shared memóriában
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = gridDim.x * blockDim.x;
    for (; idx < n; idx += stride) {
        int bin = data[idx] % NUM_BINS;
        atomicAdd(&shist[bin], 1);
    }
    __syncthreads();

    // 3. A privát hisztogram egyesítése a globális tömbbel
    for (int i = threadIdx.x; i < NUM_BINS; i += blockDim.x) {
        atomicAdd(&hist[i], shist[i]);
    }
}

A shared memóriás atomicAdd lényegesen gyorsabb, mint a globális megfelelője, mert a shared memória a blokkhoz közeli, nagy sávszélességű memória, és az atomi művelet hardveres támogatása is hatékonyabb. Ráadásul a globális atomi műveletek száma drámaian lecsökken, ami a memóriavezérlő terhelését mérsékli.

A privatizált megoldás korlátja a shared memória mérete. A NUM_BINS * sizeof(int) értéknek bele kell férnie a blokk számára elérhető shared memória keretbe (jellemzően 48–99 KiB, opcionálisan nagyobb). Ha a rekeszek száma nagyon nagy (például több ezer), akkor a privát hisztogram nem fér el, és részleges privatizációra vagy többszintű megoldásra van szükség. Ilyenkor az egyik lehetőség, hogy a rekeszeket csoportokra osztjuk, és blokkonként csak egy csoportot tárolunk shared memóriában; a feldolgozást többször is elvégezzük, vagy a bemenetet partícionáljuk.

A blokkméret és a gridméret megválasztása is fontos. A grid-stride loop használatával a grid méretét az SM-ek számának többszörösére állíthatjuk, így a kernel perzisztens maradhat, és elkerüljük a túl sok blokk indítási költségét. A block méretet úgy érdemes megválasztani, hogy az occupancy magas legyen, de a shared memória foglalása ne korlátozza túlzottan az aktív blokkok számát. Jelen példában NUM_BINS=64 és blockDim.x=256 esetén a shared memória 256 bájt, ami elhanyagolható; a blokk méretét a feldolgozási teljesítmény és a regiszterhasználat határozza meg.

16.3.3 3. Bank conflict a privatizált hisztogramban

A shared memória 32 bankre van osztva; minden bank egy 4 bájtos szót szolgál ki ciklusonként. Ha egy warp különböző szálai ugyanabba a bankbe írnak, de nem ugyanabba a szóba, a hozzáférés ütközik, és a hardver több lépésben szolgálja ki – ezt nevezzük bank conflictnek. A hisztogram privatizált implementációjában a shist[bin] elérések bin indexei gyakran véletlenszerűek, ezért a bank conflict valószínűsége nem elhanyagolható.

Tegyük fel, hogy NUM_BINS=64, és a bin indexek 0 és 32. A bank indexet a bin % 32 képlet adja, tehát mindkettő a 0. bankbe esik. Ha egy warp két különböző szálának bin indexe éppen 0 és 32, akkor a hozzáférésük bank conflictet okoz, mert különböző szavakhoz férnek hozzá ugyanabban a bankben. Ha viszont több szál ugyanabba a konkrét rekeszbe ír (azonos bin index), az atomi művelet nem bank conflictként, hanem atomi sorosítási problémaként jelentkezik; a hardver a read-modify-write műveletet szálanként hajtja végre.

A bank conflict csökkentésének egyik gyakori technikája a padding (kitöltés). A shared memória tömböt úgy deklaráljuk, hogy a szomszédos rekeszek közé üres elemeket illesztünk, így a rekeszek bankbeli elhelyezkedése megváltozik. Például ha a bin indexet megszorozzuk egy páratlan számmal (mondjuk 5-tel), akkor a shist[bin * 5] címek bank indexei permutálódnak. A paddinges kernel:

// CUDA C++ (C++17)
constexpr int PAD = 2;                 // stride = 2*PAD+1 = 5
constexpr int PAD_STRIDE = 2 * PAD + 1;

__global__ void hist_shared_padded(const int* data, int* hist, int n)
{
    __shared__ int shist[NUM_BINS * PAD_STRIDE];

    for (int i = threadIdx.x; i < NUM_BINS * PAD_STRIDE; i += blockDim.x) {
        shist[i] = 0;
    }
    __syncthreads();

    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = gridDim.x * blockDim.x;
    for (; idx < n; idx += stride) {
        int bin = data[idx] % NUM_BINS;
        int padded_bin = bin * PAD_STRIDE;
        atomicAdd(&shist[padded_bin], 1);
    }
    __syncthreads();

    for (int i = threadIdx.x; i < NUM_BINS; i += blockDim.x) {
        atomicAdd(&hist[i], shist[i * PAD_STRIDE]);
    }
}

Itt a PAD_STRIDE=5 páratlan szám, így a 0–63 bin indexek bank indexei a (bin * 5) % 32 kifejezéssel számolva nem lesznek egyenletes leképezés, de a 0. és 32. bin továbbra is ugyanabba a bankbe esik, mert 32 * 5 % 32 = 0. A padding tehát nem szünteti meg teljesen a bank conflictet 64 rekesz esetén, de ritkítja az ütközéseket, és a gyakorlatban sok esetben mérhető javulást hoz. Ha a rekeszek száma legfeljebb 32, és a stride páratlan, akkor a leképezés tökéletes permutációt ad, és a bank conflict megszűnik.

Haladó technika a per-warp privatizáció, ahol minden warp saját hisztogramot tart fenn. Ezt regiszterekben (ha a rekeszszám kicsi) vagy shared memóriában valósíthatjuk meg, és a warp szintű műveletek – például a __match_any_sync vagy a __shfl_sync – segítségével a warp-on belüli atomi műveleteket is hatékonyabban kezelhetjük. Ez a módszer a Warp intrinsics: shuffle, vote és match (warp intrinsics) fejezetben bemutatott eszközökre épít, ezért itt csak utalunk rá.

A bank conflict mérésére az Nsight Compute l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum és hasonló metrikái szolgálnak. A laborfeladat részeként érdemes ezeket is ellenőrizni, hogy a padding hatását kvantitatívan igazoljuk.

16.3.4 4. Tipikus hibák és helyes megoldások

A hisztogram implementálása során több gyakori hiba fordul elő. Az első a shared memória inicializálásának elmulasztása. A shist tömb tartalma definiálatlan, ha nem nullázzuk minden blokk elején, ezért a végeredmény szeméttel szennyezett lesz. A helyes megoldás a fenti kódban látható ciklus, amely a blokk minden szálával párhuzamosan nullázza a tömb elemeit, majd __syncthreads() hívás következik.

A második tipikus hiba a szinkronizáció elhagyása. A privatizált kernelben két __syncthreads() hívásra van szükség: az első biztosítja, hogy az inicializálás befejeződjön, mielőtt bármely szál elkezdi a feldolgozást; a második pedig garantálja, hogy minden szál befejezte a privát hisztogram frissítését, mielőtt a blokk elkezdi az egyesítést. Ha ezek hiányoznak, a szálak versenyt futnak egymással, és az eredmény nemdeterminisztikus lesz.

A harmadik hiba az out-of-range bin index. Ha a bemeneti adatok nincsenek korlátozva a [0, NUM_BINS) intervallumba, a % operátor eredménye negatív szám is lehet (C++-ban a maradék előjele az osztandó előjelét követi), ami a tömb határain kívülre mutat. A helyes megoldás a bemeneti értékek normalizálása vagy a bin index kiszámításakor abszolút érték és tartomány-ellenőrzés alkalmazása. A laborban determinisztikus bemenetet használunk, ahol ez a hiba nem fordul elő, de éles kódban mindig védeni kell.

A negyedik hiba a shared memória méretének túlbecslése. Ha a rekeszek száma nagy, a __shared__ deklaráció meghaladhatja a statikus shared memória limitet. Ilyenkor fordítási hibát kapunk, vagy a kernel nem indul el. A megoldás a dinamikus shared memória (extern __shared__) használata, a rekeszek csoportosítása, vagy a probléma átdolgozása többmenetes feldolgozássá.

Az ötödik hiba a mérési módszertan hiányossága. A hisztogram kernel mérésekor mindig warm-up futtatást kell végezni, majd legalább 5–10 ismétlést; az átlag mellett a szórást is közölni kell. A futásidő önmagában nem elegendő, mert a GPU órajele és a háttérterhelés ingadozhat. A laborban ezt a módszertant követjük.

Végül érdemes megemlíteni a % művelet költségét. Ha a rekeszek száma kettő hatványa, a modulo helyettesíthető bitművelettel: bin = data[idx] & (NUM_BINS - 1);. Ez gyorsabb, de csak akkor alkalmazható, ha a bemeneti tartomány nem negatív, és a rekeszszám ténylegesen kettő hatványa. A laborban NUM_BINS=64, így ezt a trükköt is bemutathatjuk.

16.3.5 5. Labor: histogram atomicsal és privatizált változattal

A labor célja a naiv atomi és a shared memory privatizált hisztogram implementációjának mérése, valamint a padding hatásának vizsgálata. Az alábbi forrás histogram.cu néven menthető, és CUDA C++ (C++17) nyelven fordul.

16.3.6 5.1. Teljes forráskód

// CUDA C++ (C++17)
// histogram.cu – histogram atomicsal és privatizált shared memory-vel
#include <cstdio>
#include <cstdlib>
#include <cuda_runtime.h>

#define CHECK_CUDA(call)                                                        \
    do {                                                                        \
        cudaError_t err = call;                                                 \
        if (err != cudaSuccess) {                                               \
            std::fprintf(stderr, "CUDA hiba: %s:%d: %s\n", __FILE__, __LINE__,  \
                         cudaGetErrorString(err));                              \
            std::exit(EXIT_FAILURE);                                            \
        }                                                                       \
    } while (0)

constexpr int NUM_BINS = 64;
constexpr int N = 1 << 20;          // 1 048 576 elem
constexpr int BLOCK_SIZE = 256;
constexpr int PAD = 2;              // stride = 2*PAD+1 = 5
constexpr int PAD_STRIDE = 2 * PAD + 1;

// --- Naiv globális atomics ---
__global__ void hist_naive(const int* data, int* hist, int n)
{
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = gridDim.x * blockDim.x;
    for (; idx < n; idx += stride) {
        int bin = data[idx] % NUM_BINS;
        atomicAdd(&hist[bin], 1);
    }
}

// --- Shared memory privatizált ---
__global__ void hist_shared(const int* data, int* hist, int n)
{
    __shared__ int shist[NUM_BINS];
    for (int i = threadIdx.x; i < NUM_BINS; i += blockDim.x) {
        shist[i] = 0;
    }
    __syncthreads();

    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = gridDim.x * blockDim.x;
    for (; idx < n; idx += stride) {
        int bin = data[idx] % NUM_BINS;
        atomicAdd(&shist[bin], 1);
    }
    __syncthreads();

    for (int i = threadIdx.x; i < NUM_BINS; i += blockDim.x) {
        atomicAdd(&hist[i], shist[i]);
    }
}

// --- Shared memory privatizált, paddinggel ---
__global__ void hist_shared_padded(const int* data, int* hist, int n)
{
    __shared__ int shist[NUM_BINS * PAD_STRIDE];
    for (int i = threadIdx.x; i < NUM_BINS * PAD_STRIDE; i += blockDim.x) {
        shist[i] = 0;
    }
    __syncthreads();

    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = gridDim.x * blockDim.x;
    for (; idx < n; idx += stride) {
        int bin = data[idx] % NUM_BINS;
        int padded_bin = bin * PAD_STRIDE;
        atomicAdd(&shist[padded_bin], 1);
    }
    __syncthreads();

    for (int i = threadIdx.x; i < NUM_BINS; i += blockDim.x) {
        atomicAdd(&hist[i], shist[i * PAD_STRIDE]);
    }
}

// --- CPU referencia ---
void cpu_histogram(const int* data, int* hist, int n)
{
    for (int i = 0; i < NUM_BINS; ++i) hist[i] = 0;
    for (int i = 0; i < n; ++i) {
        hist[data[i] % NUM_BINS]++;
    }
}

// --- Eredmény ellenőrzése ---
bool check_hist(const int* a, const int* b, int len)
{
    for (int i = 0; i < len; ++i) {
        if (a[i] != b[i]) return false;
    }
    return true;
}

// --- Időmérés CUDA eventekkel ---
float run_kernel(void (*kernel)(const int*, int*, int),
                 const int* d_data, int* d_hist, int n,
                 int grid_size, int block_size,
                 int num_iter, cudaStream_t stream)
{
    cudaEvent_t start, stop;
    CHECK_CUDA(cudaEventCreate(&start));
    CHECK_CUDA(cudaEventCreate(&stop));

    // Warm-up
    kernel<<<grid_size, block_size, 0, stream>>>(d_data, d_hist, n);
    CHECK_CUDA(cudaGetLastError());
    CHECK_CUDA(cudaStreamSynchronize(stream));

    CHECK_CUDA(cudaEventRecord(start, stream));
    for (int i = 0; i < num_iter; ++i) {
        kernel<<<grid_size, block_size, 0, stream>>>(d_data, d_hist, n);
    }
    CHECK_CUDA(cudaEventRecord(stop, stream));
    CHECK_CUDA(cudaStreamSynchronize(stream));

    float elapsed = 0.0f;
    CHECK_CUDA(cudaEventElapsedTime(&elapsed, start, stop));
    CHECK_CUDA(cudaEventDestroy(start));
    CHECK_CUDA(cudaEventDestroy(stop));
    return elapsed / num_iter;
}

int main()
{
    // Bemeneti adatok: determinisztikus sorozat
    int* h_data = new int[N];
    for (int i = 0; i < N; ++i) {
        h_data[i] = i % NUM_BINS;
    }

    int* h_hist_ref = new int[NUM_BINS];
    cpu_histogram(h_data, h_hist_ref, N);

    // GPU allokáció
    int *d_data, *d_hist;
    CHECK_CUDA(cudaMalloc(&d_data, N * sizeof(int)));
    CHECK_CUDA(cudaMalloc(&d_hist, NUM_BINS * sizeof(int)));
    CHECK_CUDA(cudaMemcpy(d_data, h_data, N * sizeof(int), cudaMemcpyHostToDevice));

    cudaStream_t stream;
    CHECK_CUDA(cudaStreamCreate(&stream));

    // Grid méret: teljes lefedés grid-stride loop-pal
    int grid_size = (N + BLOCK_SIZE - 1) / BLOCK_SIZE;

    const int num_iter = 10;

    // Naiv kernel mérése
    CHECK_CUDA(cudaMemset(d_hist, 0, NUM_BINS * sizeof(int)));
    float t_naive = run_kernel(hist_naive, d_data, d_hist, N,
                               grid_size, BLOCK_SIZE, num_iter, stream);

    int* h_hist_naive = new int[NUM_BINS];
    CHECK_CUDA(cudaMemcpy(h_hist_naive, d_hist, NUM_BINS * sizeof(int),
                          cudaMemcpyDeviceToHost));
    bool ok_naive = check_hist(h_hist_naive, h_hist_ref, NUM_BINS);

    // Shared kernel mérése
    CHECK_CUDA(cudaMemset(d_hist, 0, NUM_BINS * sizeof(int)));
    float t_shared = run_kernel(hist_shared, d_data, d_hist, N,
                                grid_size, BLOCK_SIZE, num_iter, stream);

    int* h_hist_shared = new int[NUM_BINS];
    CHECK_CUDA(cudaMemcpy(h_hist_shared, d_hist, NUM_BINS * sizeof(int),
                          cudaMemcpyDeviceToHost));
    bool ok_shared = check_hist(h_hist_shared, h_hist_ref, NUM_BINS);

    // Padding kernel mérése
    CHECK_CUDA(cudaMemset(d_hist, 0, NUM_BINS * sizeof(int)));
    float t_padded = run_kernel(hist_shared_padded, d_data, d_hist, N,
                                grid_size, BLOCK_SIZE, num_iter, stream);

    int* h_hist_padded = new int[NUM_BINS];
    CHECK_CUDA(cudaMemcpy(h_hist_padded, d_hist, NUM_BINS * sizeof(int),
                          cudaMemcpyDeviceToHost));
    bool ok_padded = check_hist(h_hist_padded, h_hist_ref, NUM_BINS);

    // Eredmények kiírása
    std::printf("Histogram labor eredményei (N=%d, B=%d, block=%d, grid=%d)\n",
                N, NUM_BINS, BLOCK_SIZE, grid_size);
    std::printf("Várt hisztogram binenként: %d\n", N / NUM_BINS);
    std::printf("%-12s %-12s %-12s %-10s\n", "Változat", "Idő (ms)", "Szórás", "Helyes?");
    std::printf("%-12s %-12.4f %-12s %-10s\n", "naiv", t_naive, "-", ok_naive ? "igen" : "NEM");
    std::printf("%-12s %-12.4f %-12s %-10s\n", "shared", t_shared, "-", ok_shared ? "igen" : "NEM");
    std::printf("%-12s %-12.4f %-12s %-10s\n", "padded", t_padded, "-", ok_padded ? "igen" : "NEM");

    // Takarítás
    CHECK_CUDA(cudaStreamDestroy(stream));
    CHECK_CUDA(cudaFree(d_data));
    CHECK_CUDA(cudaFree(d_hist));
    delete[] h_data;
    delete[] h_hist_ref;
    delete[] h_hist_naive;
    delete[] h_hist_shared;
    delete[] h_hist_padded;
    return 0;
}

16.3.8 5.3. Mérési napló

A futtatás során a program mindhárom kernelt 10-szer futtatja, és az átlagos futásidőt írja ki. A szórás számításához érdemes a mérést többször megismételni, vagy a programot módosítani úgy, hogy minden iteráció időtartamát rögzítse. Az alábbi táblázat a mérési napló szerkezetét mutatja; a mért értékeket a hallgató tölti ki a saját futtatása alapján.

Változat N B block Átlag idő (ms) Szórás (ms) Átbocsátás (Melem/s) Helyes?
Naiv atomics 1 048 576 64 256 [mérendő] [mérendő] [mérendő] igen
Shared privatizált 1 048 576 64 256 [mérendő] [mérendő] [mérendő] igen
Shared + padding (PAD=2) 1 048 576 64 256 [mérendő] [mérendő] [mérendő] igen

A várt eredmény: mivel a bemenet data[i] = i % 64, a hisztogram minden rekeszére N / NUM_BINS = 1 048 576 / 64 = 16 384 esik. Ezt a CPU referencia is visszaadja, és a GPU implementációknak ugyanezt az értéket kell produkálniuk. A futásidő tekintetében az várható, hogy a shared privatizált változat jelentősen gyorsabb, mint a naiv atomics, különösen, ha a bemeneti eloszlás ferde. A padding változat további javulást hozhat, de 64 rekesz és egyenletes eloszlás esetén a különbség kisebb lehet; a bank conflict méréséhez érdemes az Nsight Compute-ot futtatni.

16.3.9 5.4. Kiegészítő lehetőségek

A labor bővíthető a következőkkel:

  • OpenCL implementáció: az OpenCL C-ben a atomic_add függvény hasonlóan működik, a local memória használatával. A kernel szerkezete szinte azonos, csak a memóriamodell és a szinkronizáció (barrier(CLK_LOCAL_MEM_FENCE)) különbözik. A méréshez az OpenCL időmérőit (clGetEventProfilingInfo) használhatjuk.
  • JAX implementáció: a JAX-ben a jax.lax.segment_sum vagy az jax.numpy.bincount függvény hasonló műveletet végez, de ott a háttérben az XLA fordítja a kódot GPU/TPU kernelre. A hisztogram ott is atomi műveleteket vagy redukciót használ, és a teljesítmény az eszköztől függ.
  • Bank conflict mérés: futtassuk az Nsight Compute-ot a kernelre, és vizsgáljuk a shared memória bank conflict metrikákat. Hasonlítsuk össze az alap és a paddinges verziót.

16.3.10 6. Összefoglalás és önellenőrző kérdés

Ebben az alfejezetben megvizsgáltuk a hisztogram két GPU-s megvalósítását: a naiv, globális atomi műveleteken alapuló megoldást és a blokkszintű privatizációt, amely a kontenció csökkentésére shared memóriát használ. Bemutattuk a shared memória bank conflict jelenségét és a paddinges elrendezést mint lehetséges optimalizációt. A laborban egy teljes, fordítható CUDA C++ program segítségével mérhető a két megközelítés teljesítménye, és ellenőrizhető a helyesség a CPU referencia alapján.

Önellenőrző kérdés: Miért gyorsabb a blokkszintű privatizált hisztogram, mint a közvetlen globális atomi összeadás, és milyen feltételek mellett nem érvényesül ez az előny? (Válasz: mert a globális atomi műveletek sorosítják a hozzáférést a memóriavezérlőn, míg a shared memóriás atomi műveletek gyorsak és blokkon belül maradnak; az előny akkor csökken, ha a rekeszek száma olyan nagy, hogy a shared memória nem fér el, vagy ha a bank conflict miatt a shared memória hozzáférés is sorosítódik, illetve ha a bemeneti eloszlás nagyon egyenletes és a kontenció eleve kicsi.)
