23.2 CUTLASS

A CUTLASS (CUDA Templates for Linear Algebra Subroutines and Solvers) az NVIDIA nyílt forráskódú, kizárólag C++ sablonokra épülő könyvtára, amely hatékony GPU-implementációkat ad a lineáris algebrai primitívekhez, elsősorban a GEMM-hez. A CUTLASS nem egy fekete doboz: a fejlesztő fordítási időben dönt a tile méretekről, a memória-elrendezésről, a pipeline mélységéről és az epilogue műveletéről. Ez a fejezet a CUTLASS GEMM hierarchiáját mutatja be, és egy izolált laboron keresztül demonstrálja a használatát.

23.2.1 A CUTLASS sablonkönyvtár és a GEMM hierarchia

A CUTLASS alapgondolata az, hogy a GEMM-et rétegesen bontja fel, és minden réteget külön sablonparaméterként kezel. A hierarchia alulról felfelé a következő:

  • Thread szint: a legelemibb szint, amely a memória-hozzáférésekért és az epilogue műveleteiért felel. Itt történik a vektorizált betöltés, a kimeneti elemek megformázása, valamint a skálázás és az aktiváció.
  • Warp szint: a warpok a Tensor Core mma.sync utasításokat hajtják végre, és a hozzájuk tartozó fragmenteket kezelik. A CUTLASS itt definiálja a warp tile méreteit, amelyek meghatározzák, hogy egy warp hány adatelemen dolgozik egyszerre.
  • Threadblock szint: egy SM-re kerülő szálblokk, amely a threadblock tile-t birtokolja. A threadblock felelős a shared memory-ba való betöltésért, a warpok közötti munkamegosztásért és a K dimenzió mentén történő iterációért.
  • Kernel szint: a GPU kernel függvénye, amely a gridet és a threadblockok közötti swizzle-t vezérli.
  • Device szint: a teljes GEMM művelet, amely a kernel launch konfigurációját, a workspace memóriát és a streamet foglalja össze.

A hierarchia lelkét a tile fogalma adja. A CUTLASS a teljes mátrixszorzást kisebb, jól meghatározott méretű blokkokra osztja. Például egy FP16 Tensor Core GEMM esetében tipikus konfiguráció:

using Gemm = cutlass::gemm::device::Gemm<
    cutlass::half_t, cutlass::layout::RowMajor,   // A
    cutlass::half_t, cutlass::layout::RowMajor,   // B
    float, cutlass::layout::RowMajor,             // C
    float,                                         // akkumulátor
    cutlass::arch::OpClassTensorOp,                // Tensor Core
    cutlass::arch::Sm80,                           // compute capability
    cutlass::gemm::GemmShape<128, 128, 32>,        // threadblock tile
    cutlass::gemm::GemmShape<64, 64, 32>,          // warp tile
    cutlass::gemm::GemmShape<16, 8, 8>,            // instruction shape
    cutlass::epilogue::thread::LinearCombination<
        float, 128 / cutlass::sizeof_bits<float>::value,
        float, float>,
    cutlass::gemm::threadblock::GemmIdentityThreadblockSwizzle<>,
    3                                                // pipeline stages
>;

Ebben a konfigurációban a threadblock tile 128×128×32: minden szálblokk egy 128 sorból, 128 oszlopból és 32 K-mélységből álló mátrixszeletet dolgoz fel. A warp tile 64×64×32: a threadblock 4 warpja (2×2) ilyen altile-eket kap. Az instruction shape 16×8×8 az FP16 Tensor Core mma.sync utasítás geometriája. A pipeline stages értéke 3, ami azt jelenti, hogy a CUTLASS a K dimenzió mentén három K-tile-t tölt be előre a shared memory-ba, átfedve a memória-hozzáférést és a számítást.

23.2.2 Tile, warp és threadblock

A CUTLASS GEMM végrehajtása a következő lépésekből áll. A grid a M és N dimenziók mentén osztja fel a kimeneti mátrixot. Minden threadblock egy (CTileM × CTileN) kimeneti régiót kap. A K dimenzió mentén a threadblock szekvenciálisan halad: minden iterációban betölt egy (CTileM × CTileK) méretű A-szeletet és egy (CTileK × CTileN) méretű B-szeletet a global memóriából a shared memory-ba. Ezt követően a warpok a shared memory-ból olvasnak, és a Tensor Core mma utasításokkal kiszámítják a részösszeget, amelyet a regiszterekben akkumulálnak. Amikor a teljes K dimenziót bejárták, az epilogue kiírja az eredményt a global memóriába.

A threadblock tile méretének megválasztása kulcsfontosságú. A nagyobb tile jobb adat-újrafelhasználást tesz lehetővé, mert a shared memory-ból többször olvassák be ugyanazt az elemet, csökkentve a global memória forgalmát. Ugyanakkor a nagyobb tile több shared memory-t fogyaszt, és kevesebb szálblokk fér el egy SM-en, ami rontja az occupancy-t. A CUTLASS a shared memory igényt a tile méretekből és a pipeline stage-ekből számítja ki. Ha a konfiguráció nem fér el az SM shared memory limitjében, a fordító hibát ad.

A warp tile határozza meg, hogy a threadblockon belül hogyan oszlanak meg a feladatok. A fenti példában a 128×128-as threadblock tile-t 2×2-es warp rácsra osztjuk, így minden warp egy 64×64-es altile-t kap. A warp az MmaTensorOp operátorral dolgozik, amely a Tensor Core mma.sync utasítást használja. Az instruction shape 16×8×8 azt jelenti, hogy egyetlen mma.sync hívás 16×8×8 elemet számol ki. A warp a saját altile-jét több ilyen mma utasításra bontja.

A CUTLASS 3.x-ben a cute (CUDA Templates for Efficient) absztrakció tovább egyszerűsíti a hierarchiát. A cute::gemm ugyanazt a hardvert célozza, de magasabb szintű, funkcionálisabb felületet ad. A klasszikus CUTLASS 2.x API azonban továbbra is elérhető, és jól szemlélteti a hierarchikus tiling fogalmát. A laborban ezért a klasszikus API-t használjuk.

23.2.3 Epilogue

Az epilogue a CUTLASS azon rétege, amely a Tensor Core kimeneti fragmentjeit feldolgozza és a global memóriába írja. Az epilogue elkülönítése azért fontos, mert a GEMM magja nem változik, ha például bias-t, ReLU-t vagy skálázást akarunk hozzáadni. A CUTLASS az epilogue-ot funktorként valósítja meg, így a felhasználó saját epilogue-ot írhat anélkül, hogy a kernel többi részét módosítaná.

A leggyakoribb epilogue a cutlass::epilogue::thread::LinearCombination, amely a
C=α⋅A⋅B+β⋅C C = \alpha \cdot A \cdot B + \beta \cdot C műveletet végzi. A fenti sablonparaméterben a LinearCombination az ElementC típusú kimeneti elemeket kezeli, és az FP32 akkumulátor értékeket a kívánt kimeneti típusra konvertálja. Az epilogue a thread szinten fut, és a fragmenteket a kimeneti layout szerint írja.

Egyéni epilogue készítéséhez a CUTLASS a cutlass::epilogue::thread::LinearCombination-t lehet alapul venni, vagy a cutlass::epilogue::thread::Epilogue sablont közvetlenül testreszabni. Például egy ReLU epilogue a következőképpen nézhet ki:

struct ReluEpilogue {
    template <typename FragmentC, typename FragmentD>
    void operator()(FragmentC &acc, FragmentD &out) {
        #pragma unroll
        for (int i = 0; i < acc.size(); ++i) {
            out[i] = (acc[i] > 0.0f) ? acc[i] : 0.0f;
        }
    }
};

Ezt a funktort a CUTLASS epilogue pipeline-jába illesztve a GEMM kimenetén közvetlenül ReLU aktivációt alkalmazhatunk. A CUTLASS 2.x-ben a cutlass::epilogue::threadblock::Epilogue és a cutlass::epilogue::thread::Epilogue sablonok együttese biztosítja ezt a rugalmasságot.

23.2.4 Streamk

A hagyományos data-parallel GEMM a gridet az M és N dimenziók mentén osztja fel, és minden threadblock a teljes K dimenziót bejárja. Ez a megközelítés akkor optimális, ha a threadblockok száma jól illeszkedik az SM-ek számához, és a K dimenzió elegendően nagy ahhoz, hogy a pipeline feltöltődjön. Ha azonban a K dimenzió rövid, vagy a threadblockok száma nem tölti ki a GPU-t, a terhelés egyenetlen lesz, mert néhány SM hamarabb végez, mint a többi.

A stream-K a CUTLASS 3.x egyik fontos újdonsága. Ahelyett, hogy minden threadblock a teljes K dimenziót dolgozná fel, a stream-K a K dimenzió mentén is partícionál. Minden threadblock egy (M-tile, N-tile, K-szelet) darabot kap, és a részösszegeket atomikusan adja össze a global memóriában. Ez a módszer jobb terheléselosztást eredményez, mert a threadblockok kisebb K-tartományokat dolgoznak fel, és a GPU hullámossága kiegyenlítettebbé válik.

A stream-K különösen akkor előnyös, ha a teljes K dimenzió nem osztható egyenletesen a pipeline stage-ekre, vagy ha a mátrix mérete nem ideálisan illeszkedik a threadblock rácsra. A CUTLASS 3.x a cutlass::gemm::kernel::GemmUniversal sablonban a KernelSchedule::StreamK opcióval választható. A laborban a hagyományos data-parallel konfigurációt használjuk, mert a CUTLASS 2.x API-ban a stream-K nem érhető el, és a hierarchia fogalmai a klasszikus konfiguráción keresztül jobban szemléltethetők.

23.2.5 Gyakori hibák és megoldások

A CUTLASS használata során a következő tipikus hibákra érdemes figyelni:

  1. A shared memory limit figyelmen kívül hagyása. A túl nagy tile vagy túl sok pipeline stage miatt a szükséges shared memory meghaladja az SM kapacitását. Fordítási hiba keletkezik, amelyet a -Xptxas -v kapcsolóval ellenőrizhetünk. Megoldás: csökkentsük a tile méretet vagy a stage-ek számát.

  2. A mutatók 16 byte-os igazításának elhagyása. A CUTLASS vectorizált betöltést használ, amely feltételezi, hogy a global memória pointerek 16 byte-ra igazítottak. Ha ez nem teljesül, a kernel lelassul, vagy hibás eredményt ad. Megoldás: cudaMalloc helyett cudaMallocManaged-et vagy cudaMalloc-ot használjunk megfelelő igazítással, illetve a CUTLASS device_memory::allocation osztályát.

  3. Az epilogue típusainak eltévesztése. Ha a kimeneti mátrix típusa FP16, de az epilogue FP32-re van beállítva, a LinearCombination nem konvertál megfelelően, és a numerikus tartomány túlcsordulhat. Megoldás: mindig ellenőrizzük az ElementC és az epilogue ElementOutput típusainak egyezését.

  4. A stream-K atomikus hozzáadásainak nem determinisztikus sorrendje. A stream-K modellben a részösszegeket atomikusan adják össze, ami a lebegőpontos kerekítés miatt nem garantál bit-azonos eredményt. Ha determinizmus szükséges, használjunk hagyományos data-parallel konfigurációt, vagy rögzítsük a végrehajtási sorrendet.

  5. A pipeline stage-ek helytelen beállítása. Túl kevés stage nem fedi át a memória-hozzáférést és a számítást, túl sok stage pedig feleslegesen foglalja a shared memory-t. A legtöbb Tensor Core konfigurációnál a 3–5 stage optimális.

23.2.8 CUDA C++ kód

#include <iostream>
#include <vector>
#include <cuda_runtime.h>
#include <cutlass/cutlass.h>
#include <cutlass/gemm/device/gemm.h>
#include <cutlass/util/host_tensor.h>
#include <cutlass/util/device_memory.h>

#define CUDA_CHECK(call) { \
    cudaError_t err = call; \
    if (err != cudaSuccess) { \
        std::cerr << "CUDA error at " << __FILE__ << ":" << __LINE__ << ": " \
                  << cudaGetErrorString(err) << std::endl; \
        std::exit(EXIT_FAILURE); \
    } \
}

#define CUTLASS_CHECK(status) { \
    cutlass::Status status_ = (status); \
    if (status_ != cutlass::Status::kSuccess) { \
        std::cerr << "CUTLASS error at " << __FILE__ << ":" << __LINE__ << std::endl; \
        std::exit(EXIT_FAILURE); \
    } \
}

using ElementA = cutlass::half_t;
using ElementB = cutlass::half_t;
using ElementC = float;
using ElementAccumulator = float;
using LayoutA = cutlass::layout::RowMajor;
using LayoutB = cutlass::layout::RowMajor;
using LayoutC = cutlass::layout::RowMajor;

using Gemm = cutlass::gemm::device::Gemm<
    ElementA, LayoutA,
    ElementB, LayoutB,
    ElementC, LayoutC,
    ElementAccumulator,
    cutlass::arch::OpClassTensorOp,
    cutlass::arch::Sm80,
    cutlass::gemm::GemmShape<128, 128, 32>,
    cutlass::gemm::GemmShape<64, 64, 32>,
    cutlass::gemm::GemmShape<16, 8, 8>,
    cutlass::epilogue::thread::LinearCombination<
        ElementC,
        128 / cutlass::sizeof_bits<ElementC>::value,
        ElementAccumulator,
        ElementAccumulator>,
    cutlass::gemm::threadblock::GemmIdentityThreadblockSwizzle<>,
    3
>;

int main() {
    const int M = 16384, N = 16384, K = 16384;

    // Host mátrixok
    cutlass::HostTensor<ElementA, LayoutA> A({M, K});
    cutlass::HostTensor<ElementB, LayoutB> B({K, N});
    cutlass::HostTensor<ElementC, LayoutC> C({M, N});

    for (int i = 0; i < M * K; ++i) A.host_data()[i] = cutlass::half_t(0.5f);
    for (int i = 0; i < K * N; ++i) B.host_data()[i] = cutlass::half_t(0.5f);
    for (int i = 0; i < M * N; ++i) C.host_data()[i] = 0.0f;

    // Device allokáció
    cutlass::device_memory::allocation<uint8_t> d_A(A.bytes());
    cutlass::device_memory::allocation<uint8_t> d_B(B.bytes());
    cutlass::device_memory::allocation<uint8_t> d_C(C.bytes());

    CUDA_CHECK(cudaMemcpy(d_A.get(), A.host_data(), A.bytes(), cudaMemcpyHostToDevice));
    CUDA_CHECK(cudaMemcpy(d_B.get(), B.host_data(), B.bytes(), cudaMemcpyHostToDevice));
    CUDA_CHECK(cudaMemcpy(d_C.get(), C.host_data(), C.bytes(), cudaMemcpyHostToDevice));

    // CUTLASS argumentumok
    cutlass::gemm::GemmCoord problem_size(M, N, K);
    ElementAccumulator alpha = 1.0f;
    ElementAccumulator beta = 0.0f;

    cutlass::gemm::GemmArguments args(
        problem_size,
        reinterpret_cast<ElementA*>(d_A.get()), K,
        reinterpret_cast<ElementB*>(d_B.get()), N,
        reinterpret_cast<ElementC*>(d_C.get()), N,
        reinterpret_cast<ElementC*>(d_C.get()), N,
        &alpha, &beta);

    Gemm gemm;
    CUTLASS_CHECK(gemm(args, nullptr, nullptr));   // warm-up

    const int num_runs = 10;
    float total_ms = 0.0f;
    float best_ms = 0.0f;
    for (int i = 0; i < num_runs; ++i) {
        cudaEvent_t start, stop;
        cudaEventCreate(&start);
        cudaEventCreate(&stop);
        cudaEventRecord(start);
        CUTLASS_CHECK(gemm(args, nullptr, nullptr));
        cudaEventRecord(stop);
        cudaEventSynchronize(stop);
        float elapsed_ms;
        cudaEventElapsedTime(&elapsed_ms, start, stop);
        total_ms += elapsed_ms;
        if (i == 0) best_ms = elapsed_ms;
        else if (elapsed_ms < best_ms) best_ms = elapsed_ms;
        cudaEventDestroy(start);
        cudaEventDestroy(stop);
    }
    float avg_ms = total_ms / num_runs;

    // Eredmény visszamásolása
    CUDA_CHECK(cudaMemcpy(C.host_data(), d_C.get(), C.bytes(), cudaMemcpyDeviceToHost));

    // Ellenőrzés CPU referencia ellen
    float max_error = 0.0f;
    for (int i = 0; i < M * N; ++i) {
        float expected = static_cast<float>(K) * 0.5f * 0.5f;  // 4096.0
        max_error = std::max(max_error, std::abs(C.host_data()[i] - expected));
    }

    double flops = 2.0 * static_cast<double>(M) * static_cast<double>(N) * static_cast<double>(K);
    double tflops = flops / (avg_ms * 1e-3) / 1e12;

    std::cout << "Avg time: " << avg_ms << " ms (" << num_runs << " runs)" << std::endl;
    std::cout << "Best time: " << best_ms << " ms" << std::endl;
    std::cout << "Achieved TFLOPS: " << tflops << std::endl;
    std::cout << "Max abs error: " << max_error << std::endl;

    return 0;
}

23.2.9 Build és futtatás

A buildparancs (a CUTLASS include útvonalait a saját környezethez kell igazítani):

nvcc -std=c++17 -O3 \
     -I/path/to/cutlass/include \
     -I/path/to/cutlass/tools/util/include \
     cutlass_gemm_lab.cu -o cutlass_gemm_lab -lcuda

A kernel regiszter- és shared memory használatát a következő kapcsolóval ellenőrizhetjük:

nvcc -std=c++17 -O3 -Xptxas -v \
     -I/path/to/cutlass/include \
     -I/path/to/cutlass/tools/util/include \
     cutlass_gemm_lab.cu -o cutlass_gemm_lab -lcuda

Futtatás:

./cutlass_gemm_lab
