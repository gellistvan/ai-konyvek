24.1 GEMM és a deep learning

24.1.1 A lineáris réteg és a GEMM kapcsolata

A mélytanulási hálózatok leggyakoribb építőköve a lineáris réteg, amelyet sok keretrendszer fully connected, dense vagy linear néven ismer. A réteg matematikailag egy affin transzformációt hajt végre:

𝐘=𝐗𝐖𝖳+𝐛, \mathbf{Y} = \mathbf{X}\,\mathbf{W}^{\mathsf{T}} + \mathbf{b},

ahol

  • 𝐗∈ℝN×K\mathbf{X} \in \mathbb{R}^{N \times K} a bemeneti köteg (batch), NN mintával és KK bemeneti jellemzővel,
  • 𝐖∈ℝM×K\mathbf{W} \in \mathbb{R}^{M \times K} a súlymátrix, MM kimeneti jellemzővel,
  • 𝐛∈ℝM\mathbf{b} \in \mathbb{R}^{M} a torzítás (bias),
  • 𝐘∈ℝN×M\mathbf{Y} \in \mathbb{R}^{N \times M} a kimeneti aktiváció.

A kifejezés egy mátrixszorzásból és egy soronkénti eltolásból áll. A mátrixszorzás a GEMM (general matrix multiply) művelet, amely a számítási igény túlnyomó részét adja. Egyetlen kimeneti elem kiszámítása KK szorzást és K−1K-1 összeadást igényel, így a teljes réteg műveletigénye

2NMK+NM 2\,N\,M\,K + N\,M

lebegőpontos művelet, ahol az utolsó tag a bias hozzáadásából származik. Nagy KK és MM esetén a bias elhanyagolható, és a művelet gyakorlatilag tisztán GEMM.

A CPU-n megszokott mátrixszorzás-optimalizálások (blokkosítás, vektorizáció, cache-barát sorrend) a GPU-n is érvényesek, de a GPU hierarchikus végrehajtási modellje miatt a tile-ok mérete, a shared memory használata és a warp-szintű adatcsere válik kulcskérdéssé. A lineáris réteg GPU-ra vitele ezért nem egyszerűen egy könyvtári hívás: meg kell értenünk a batch és layout fogalmát, a GEMM hívási konvencióit, és azt, hogy a különböző könyvtárak (cuBLAS, CUTLASS) hogyan térképezik a réteget hardveres erőforrásokra.

24.1.2 Batch és layout

A mélytanulási keretrendszerekben a bemeneti adatokat általában kétféle elrendezésben tárolják:

  • row-major (C-szerű) layout: az utolsó index változik leggyorsabban. A 𝐗\mathbf{X} mátrix (n,k)(n,k) eleme a memóriában az n⋅K+kn \cdot K + k pozíción van.
  • column-major (Fortran-szerű) layout: az első index változik leggyorsabban. Itt az (n,k)(n,k) elem pozíciója k⋅N+nk \cdot N + n.

A CUDA-ökoszisztéma alapértelmezésben a row-major tárolást használja a saját kerneleknél, de a cuBLAS – a BLAS szabványnak megfelelően – column-major tárolást vár. Ez a forrása a leggyakoribb hibáknak, mert ugyanaz a N×KN \times K mátrix row-major és column-major tárolásban transzponáltnak tűnik.

Tekintsük a lineáris réteg számítását:

𝐘=𝐗𝐖𝖳+𝐛. \mathbf{Y} = \mathbf{X} \mathbf{W}^{\mathsf{T}} + \mathbf{b}.

Ha 𝐗\mathbf{X} row-major, akkor a memóriában a N×KN \times K mátrix sorai egymás után helyezkednek el. A 𝐖\mathbf{W} súlymátrixot általában (M,K)(M, K) alakban tároljuk, ahol a sorok a kimeneti neuronok, az oszlopok a bemeneti jellemzők. A GEMM számára ez azt jelenti, hogy

𝐂=𝐀⋅𝐁𝖳, \mathbf{C} = \mathbf{A} \cdot \mathbf{B}^{\mathsf{T}},

ahol 𝐀=𝐗\mathbf{A} = \mathbf{X} (N×KN \times K), 𝐁=𝐖\mathbf{B} = \mathbf{W} (M×KM \times K), és a 𝐁\mathbf{B}-t transzponálni kell, hogy a belső dimenzió KK legyen. A cuBLAS-ban ezt az CUBLAS_OP_T (transzponált) művelettel adjuk meg.

A leading dimension (vezető dimenzió) fogalma a BLAS-ban elengedhetetlen. Egy N×KN \times K mátrixnál a leading dimension (általában lda) azt adja meg, hogy a memóriában hány elem van két szomszédos sor kezdőcíme között. Row-major tárolásnál lda = K, mert egy sor hossza KK elem. Column-major tárolásnál lda = N, mert egy oszlop hossza NN elem. Ha a mátrixot nagyobb memóriaterületbe ágyazzuk (például paddinggel), a leading dimension eltérhet a logikai dimenziótól. A cuBLAS hívásokban a leading dimension paramétereket mindig a tényleges memóriaelrendezéshez kell igazítani.

Batch feldolgozás azt jelenti, hogy a bemeneti 𝐗\mathbf{X} mátrix első dimenziója a batch méret NN. A lineáris réteg egyetlen GEMM-mel feldolgozza az összes mintát. A kimenet 𝐘\mathbf{Y} alakja N×MN \times M. Amennyiben a hálózat több, független réteget futtat párhuzamosan (például egy-egy minta különböző ágakon), használhatunk batched GEMM-et is, amely egyszerre több mátrixpárt szoroz össze, de ez a lineáris rétegnél ritkábban szükséges.

24.1.3 cuBLAS és a GEMM

A cuBLAS a NVIDIA által szállított, nagy teljesítményű BLAS implementáció. A lineáris réteg leggyakrabban a cublasSgemm (FP32), cublasDgemm (FP64), cublasHgemm (FP16) vagy a cublasGemmEx (vegyes pontosság) függvénnyel valósítható meg. A következő példa egy FP32 lineáris réteg forward passzát mutatja be cuBLAS-szal.

// CUDA C++ (C++17) – lineáris réteg cuBLAS-szal (FP32)
#include <cuda_runtime.h>
#include <cublas_v2.h>
#include <cstdio>
#include <cstdlib>

#define CHECK_CUDA(call)                                            \
    do {                                                            \
        cudaError_t err = call;                                     \
        if (err != cudaSuccess) {                                   \
            fprintf(stderr, "CUDA error at %s:%d: %s\n", __FILE__,  \
                    __LINE__, cudaGetErrorString(err));             \
            exit(EXIT_FAILURE);                                     \
        }                                                           \
    } while (0)

#define CHECK_CUBLAS(call)                                          \
    do {                                                            \
        cublasStatus_t st = call;                                   \
        if (st != CUBLAS_STATUS_SUCCESS) {                          \
            fprintf(stderr, "cuBLAS error at %s:%d\n", __FILE__,    \
                    __LINE__);                                      \
            exit(EXIT_FAILURE);                                     \
        }                                                           \
    } while (0)

int main(int argc, char** argv) {
    int N = 1024;          // batch méret
    int K = 4096;          // bemeneti jellemzők
    int M = 4096;          // kimeneti jellemzők

    // Host memória (row-major, mint a keretrendszerekben)
    float* h_X = (float*)malloc(N * K * sizeof(float));
    float* h_W = (float*)malloc(M * K * sizeof(float));
    float* h_b = (float*)malloc(M * sizeof(float));
    float* h_Y = (float*)malloc(N * M * sizeof(float));

    // Inicializálás (pl. véletlen vagy determinisztikus értékek)
    for (int i = 0; i < N * K; ++i) h_X[i] = 0.001f * (i % 100);
    for (int i = 0; i < M * K; ++i) h_W[i] = 0.0001f * (i % 97);
    for (int i = 0; i < M; ++i)     h_b[i] = 0.01f;

    // Device memória
    float *d_X, *d_W, *d_b, *d_Y;
    CHECK_CUDA(cudaMalloc(&d_X, N * K * sizeof(float)));
    CHECK_CUDA(cudaMalloc(&d_W, M * K * sizeof(float)));
    CHECK_CUDA(cudaMalloc(&d_b, M * sizeof(float)));
    CHECK_CUDA(cudaMalloc(&d_Y, N * M * sizeof(float)));

    CHECK_CUDA(cudaMemcpy(d_X, h_X, N * K * sizeof(float), cudaMemcpyHostToDevice));
    CHECK_CUDA(cudaMemcpy(d_W, h_W, M * K * sizeof(float), cudaMemcpyHostToDevice));
    CHECK_CUDA(cudaMemcpy(d_b, h_b, M * sizeof(float), cudaMemcpyHostToDevice));

    cublasHandle_t handle;
    CHECK_CUBLAS(cublasCreate(&handle));

    const float alpha = 1.0f;
    const float beta  = 0.0f;  // a bias-t külön adjuk hozzá, mert a GEMM nem kezeli

    // Y = 1.0 * X * W^T + 0.0 * Y
    // A = X (N x K), B = W (M x K), C = Y (N x M)
    // A tárolás row-major, de a cuBLAS column-major-t vár, ezért
    // a transzponált műveletekkel kompenzálunk.
    CHECK_CUBLAS(cublasSgemm(
        handle,
        CUBLAS_OP_N,        // A-t nem transzponáljuk
        CUBLAS_OP_T,        // B-t transzponáljuk (W-ből W^T lesz)
        N,                  // sorok száma C-ben = batch
        M,                  // oszlopok száma C-ben = kimeneti jellemzők
        K,                  // belső dimenzió = bemeneti jellemzők
        &alpha,
        d_X, K,             // A row-major, leading dimension = K
        d_W, K,             // B row-major, leading dimension = K
        &beta,
        d_Y, M              // C row-major, leading dimension = M
    ));

    // Bias hozzáadása: Y(n,m) += b(m)
    // Ezt megtehetjük egy külön kernelben, vagy a GEMM beta=1 és
    // előre feltöltött bias mátrixszal, de egyszerűbb kernelhívással.
    // Itt csak a fogalmat mutatjuk: a valós kódban használjunk kernelt.
    // (A példa nem futtatott, ezért a bias kernel elhagyható.)

    CHECK_CUDA(cudaDeviceSynchronize());
    CHECK_CUDA(cudaMemcpy(h_Y, d_Y, N * M * sizeof(float), cudaMemcpyDeviceToHost));

    // Ellenőrzés CPU-val (itt elhagyva a hosszúság miatt)

    cublasDestroy(handle);
    cudaFree(d_X); cudaFree(d_W); cudaFree(d_b); cudaFree(d_Y);
    free(h_X); free(h_W); free(h_b); free(h_Y);
    return 0;
}

A példa jól mutatja a layout-konvenció fontosságát. A cuBLAS column-major bemenetet vár, ezért a row-major tárolású mátrixainkat transzponált műveletként adjuk át. A d_X mátrixot CUBLAS_OP_N-nel (nincs transzponálás) és lda = K-val adjuk meg, ami azt jelenti, hogy a cuBLAS számára ez egy K×NK \times N méretű column-major mátrix, valójában a mi N×KN \times K row-major mátrixunk. Hasonlóan a d_W súlymátrixot CUBLAS_OP_T-vel és ldb = K-val adjuk, ami a column-major konvencióban egy K×MK \times M mátrixként jelenik meg, éppen a transzponált 𝐖𝖳\mathbf{W}^{\mathsf{T}}. A kimenet d_Y ldc = M-mel M×NM \times N column-major mátrix, ami a mi N×MN \times M row-major kimenetünk. Ez a leképezés működik, de aki nem figyel, könnyen felcserélheti a dimenziókat, és hibás eredményt kap.

A bias hozzáadását a GEMM önmagában nem végzi el; azt külön kernelben vagy egy második GEMM-mel (például egy N×MN \times M mátrix és egy M×1M \times 1 vektor szorzatával) lehet megoldani. A gyakorlatban a keretrendszerek gyakran egy fused kernelt használnak, amely a GEMM epilógusában adja hozzá a bias-t, így elkerülve egy külön globális memória kört. Ezt a CUTLASS „epilogue” mechanizmusa támogatja.

A cublasGemmEx és a cublasLt lehetővé teszi vegyes pontosságú számítást, például TF32, FP16 vagy BF16 bemenettel és FP32 akkumulációval. Ez a modern GPU-k Tensor Core egységeit használja, és a lineáris réteg teljesítményét több nagyságrenddel növelheti, de a numerikus pontosságot gondosan ellenőrizni kell. A következő alfejezet (Convolution kernelek) részletesen foglalkozik a konvolúciós és attention kernelekkel, ahol a cuBLAS és a CUTLASS integrációja még fontosabb.

24.1.4 CUTLASS szerepe

A CUTLASS (CUDA Templates for Linear Algebra Subroutines) egy nyílt forráskódú sablonkönyvtár, amely a GEMM és más lineáris algebrai műveletek hatékony implementálásához ad építőelemeket. A cuBLAS-szal ellentétben a CUTLASS nem egy előre lefordított könyvtár, hanem C++ sablonok gyűjteménye, amelyek a fordítási időben specializálódnak a pontos adattípusra, tile méretre, warp elrendezésre és az úgynevezett epilógus műveletre.

A CUTLASS alapvető szerkezete a hierarchikus tiling:

  1. Thread block tile: minden blokk egy CC kimeneti mátrix blokkját számítja ki, például 128×128128 \times 128 elemet. A bemeneti AA és BB mátrixok megfelelő tile-jait shared memory-ba tölti.
  2. Warp tile: a blokkon belül minden warp egy kisebb részt, például 64×6464 \times 64 elemet kap.
  3. Thread-level: a warpen belül minden szál egy 8×88 \times 8-as vagy 16×816 \times 8-as mikro-tile-t számol, gyakran a Tensor Core mma (matrix multiply accumulate) utasításával.

A CUTLASS a tensor core használatát teszi elérhetővé a mma utasításokon keresztül, amelyek egy 16×16×1616 \times 16 \times 16-os vagy kisebb mátrixszorzást végeznek el egyetlen utasításban. A FP16, BF16 és TF32 bemenetekkel az FP32 akkumulátorban számoló mma utasítások a mélytanulási terhelések gerincét adják. A CUTLASS emellett támogatja az epilógus kiterjesztést, amely a GEMM kimenetére további műveleteket alkalmazhat, például bias hozzáadást, ReLU aktivációt vagy kvantálást, anélkül hogy a kimenetet visszaírnánk a globális memóriába. Ez különösen fontos a lineáris rétegnél, mert a bias hozzáadása és az aktiváció egy lépésben elvégezhető, csökkentve a memóriaforgalmat.

Egy CUTLASS alapú lineáris réteg váza a következőképpen nézhet ki:

// CUDA C++ (C++17) – CUTLASS vázlat (nem futtatott, csak koncepcionális)
#include <cutlass/gemm/device/gemm.h>
#include <cutlass/epilogue/thread/linear_combination_bias_relu.h>

using ElementA = float;
using ElementB = float;
using ElementC = float;
using Accumulator = float;

using ThreadblockShape = cutlass::gemm::GemmShape<128, 128, 32>;
using WarpShape        = cutlass::gemm::GemmShape<64, 64, 32>;
using InstructionShape = cutlass::gemm::GemmShape<16, 8, 8>;

using EpilogueOp = cutlass::epilogue::thread::LinearCombinationBiasRelu<
    ElementC, 128 / cutlass::sizeof_bits<ElementC>::value,
    Accumulator, Accumulator>;

using Gemm = cutlass::gemm::device::Gemm<
    ElementA, cutlass::layout::RowMajor,
    ElementB, cutlass::layout::RowMajor,
    ElementC, cutlass::layout::RowMajor,
    Accumulator,
    cutlass::arch::OpClassTensorOp,
    cutlass::arch::Sm80,
    ThreadblockShape, WarpShape, InstructionShape,
    EpilogueOp,
    cutlass::gemm::threadblock::GemmIdentityThreadblockSwizzle<>,
    2>;

// A tényleges hívásnál a CUTLASS elvégzi a tilinget, a shared memória
// feltöltést és az mma utasításokat. A fenti sablon paraméterezés
// illusztráció, a pontos típusok a CUTLASS verziójától függenek.

A CUTLASS előnye, hogy a fejlesztő pontosan szabályozhatja a tile méreteket, a warp elrendezést és az adatfolyamot, míg a cuBLAS egy fekete doboz. A hátránya a hosszabb fejlesztési idő és a sablonok bonyolultsága. A gyakorlatban a mélytanulási keretrendszerek (PyTorch, TensorFlow) sokszor a cuBLAS-t vagy a CUTLASS-t használják a lineáris réteg mögött, attól függően, hogy melyik adott hardveren gyorsabb.

24.1.5 Lineáris réteg saját kernelből: tiled GEMM

A tanulás szempontjából elengedhetetlen, hogy a lineáris réteget egy saját, oktatási célú kernelben is megvalósítsuk. Az alábbi CUDA kernel egy batch lineáris réteget számol shared memory tilinggel, bias hozzáadással. A kernel TM = TN = TILE_DIM méretű kimeneti tile-okat állít elő, és a bemeneti 𝐗\mathbf{X} valamint a transzponált 𝐖\mathbf{W} tile-jait shared memory-ba tölti.

// CUDA C++ (C++17) – lineáris réteg saját kernel, FP32, tiled GEMM
#define TILE_DIM 32

__global__ void linear_layer_kernel(
    const float* __restrict__ X,      // (N, K) row-major
    const float* __restrict__ W,      // (M, K) row-major
    const float* __restrict__ bias,   // (M) vagy nullptr
    float* __restrict__ Y,            // (N, M) row-major
    int N, int K, int M)
{
    // A block dim (TILE_DIM, TILE_DIM). A blockIdx.x az oszlop (M)
    // irányt, blockIdx.y a batch (N) irányt jelöli.
    int c_row = blockIdx.y * TILE_DIM + threadIdx.y;   // batch index
    int c_col = blockIdx.x * TILE_DIM + threadIdx.x;   // kimeneti index

    __shared__ float As[TILE_DIM][TILE_DIM];   // X tile (TM x K-tile)
    __shared__ float Bs[TILE_DIM][TILE_DIM];   // W^T tile (TN x K-tile)

    float acc = 0.0f;
    int tiles = (K + TILE_DIM - 1) / TILE_DIM;

    for (int t = 0; t < tiles; ++t) {
        int k = t * TILE_DIM + threadIdx.x;   // belső dimenzió index

        // As betöltése: As[threadIdx.y][threadIdx.x] = X[c_row][k]
        if (c_row < N && k < K) {
            As[threadIdx.y][threadIdx.x] = X[c_row * K + k];
        } else {
            As[threadIdx.y][threadIdx.x] = 0.0f;
        }

        // Bs betöltése: Bs[threadIdx.y][threadIdx.x] = W[out][k],
        // ahol out = blockIdx.x * TILE_DIM + threadIdx.y.
        int out_idx = blockIdx.x * TILE_DIM + threadIdx.y;
        if (out_idx < M && k < K) {
            Bs[threadIdx.y][threadIdx.x] = W[out_idx * K + k];
        } else {
            Bs[threadIdx.y][threadIdx.x] = 0.0f;
        }
        __syncthreads();

        // Accumulate: C[threadIdx.y][threadIdx.x] +=
        //   sum_k As[threadIdx.y][k] * Bs[threadIdx.x][k]
        #pragma unroll
        for (int kk = 0; kk < TILE_DIM; ++kk) {
            acc += As[threadIdx.y][kk] * Bs[threadIdx.x][kk];
        }
        __syncthreads();
    }

    if (c_row < N && c_col < M) {
        float val = acc + (bias ? bias[c_col] : 0.0f);
        Y[c_row * M + c_col] = val;
    }
}

A kernel működése:

  • Minden blokk egy TILE_DIM x TILE_DIM méretű kimeneti részt számol. A threadIdx.x az oszlopot, a threadIdx.y a sort azonosítja a kimeneti tile-on belül.
  • A K dimenziót tiles számú szakaszra bontjuk. Minden iterációban a szükséges XX és W𝖳W^{\mathsf{T}} tile-okat a shared memóriába másoljuk, ott szinkronizálunk, majd minden szál egy belső szorzatot halmoz fel az acc regiszterben.
  • A Bs betöltésekor a WW mátrixból a kimeneti index (out_idx) és a belső index (k) segítségével olvasunk. Mivel a Bs sorindexe az out dimenzió, oszlopindexe a k dimenzió, ezért a Bs a transzponált súlymátrix tile-ját tárolja. A számítás során Bs[threadIdx.x][kk] a threadIdx.x kimeneti oszlophoz tartozó súlyvektor kk-adik eleme, míg As[threadIdx.y][kk] a bemeneti sorvektoré.
  • A határok kezelése paddinggel történik: ha a globális index túlmutat a mátrixon, nullát töltünk. Ez egyszerűsíti a kódot, de a valós implementációkban gyakran hatékonyabb, ha a határfeltételeket a kernel végén csak a tényleges elemekre írjuk ki.
  • A bias hozzáadása a kimeneti elem kiszámítása után történik, feltéve, hogy a bias mutató nem nullptr.

A kernel launch alakja:

dim3 block(TILE_DIM, TILE_DIM);
dim3 grid((M + TILE_DIM - 1) / TILE_DIM,
          (N + TILE_DIM - 1) / TILE_DIM);
linear_layer_kernel<<<grid, block>>>(d_X, d_W, d_bias, d_Y, N, K, M);

Ez a kernel didaktikus, de nem éri el a cuBLAS vagy CUTLASS teljesítményét, mivel nem használ Tensor Core-okat, nem végez dupla buffering-et, és a shared memory betöltés nem vektorizált. A következő fejezetekben (GEMM és a deep learning alfejezetet követően) látni fogjuk, hogyan lehet ezt tovább optimalizálni.

24.1.6 Tipikus hibák és a helyes megoldás

A lineáris réteg GEMM-mel történő implementálásakor a következő hibák a leggyakoribbak:

  1. Layout mismatch: A bemeneti mátrixot row-majorban tároljuk, de a cuBLAS column-major konvenciót vár. A megoldás vagy a transzponálási flag-ek átgondolt használata (mint a példában), vagy a mátrixok tényleges transzponálása a memóriában. Sokan a CUBLAS_OP_N helyett CUBLAS_OP_T-t adnak meg, és az eredmény transzponált lesz.

  2. Hibás leading dimension: Az lda, ldb, ldc paramétereket a tényleges memóriaelrendezéshez kell igazítani. Ha a mátrixot paddinggel tároljuk, a leading dimension nagyobb, mint a logikai dimenzió. A cuBLAS hibás lépésközzel túlindexel, ami memóriahibához vagy rossz eredményhez vezet.

  3. Transzponálási hiba a saját kernelben: A Bs betöltésekor könnyű felcserélni a threadIdx.x és threadIdx.y indexeket. A fenti kernelben a Bs[threadIdx.y][threadIdx.x] = W[out_idx * K + k] sor helyesen a threadIdx.y-t használja a kimeneti dimenzióhoz, mert a Bs sorindexe az out dimenzió. Ha valaki W[k * M + out_idx]-et ír, az a WW transzponáltjának rossz elrendezését eredményezi.

  4. Bias hozzáadásának elmulasztása: A GEMM önmagában nem adja hozzá a bias-t. Ha a bias-t külön kernelben adjuk hozzá, győződjünk meg arról, hogy a kernel a kimeneti dimenzió mentén fut, és a batch dimenziót nem keveri.

  5. Batch és feature dimenziók felcserélése: A bemeneti mátrix alakja (N,K)(N, K), a súlyé (M,K)(M, K). Ha a felhasználó (K,N)(K, N) alakú bemenetet ad meg, a GEMM dimenziói rosszak lesznek, és a kimenet mérete sem egyezik. A cuBLAS hívásnál az M (sorok száma C-ben) a batch méret, az N (oszlopok száma C-ben) a kimeneti jellemzők száma.

  6. Osztási maradék és tile padding: A saját kernelben a tiles számítást (K + TILE_DIM - 1) / TILE_DIM képlettel végezzük, hogy a K nem osztható TILE_DIM-mel. A határfeltételeknél a k < K ellenőrzés elengedhetetlen, különben a global memory-ból való olvasás túlmutat a lefoglalt területen.

  7. Szinkronizáció hiánya: A shared memory feltöltése után __syncthreads() nélkül a szálak még azelőtt olvashatják a shared memóriát, hogy minden szál befejezte volna az írást. Ez versenyhelyzetet okoz. A fenti kernelben mind a betöltés után, mind a belső ciklus végén van szinkronizáció.

  8. Bank conflict a shared memóriában: A As és Bs tile-ok elérése a belső szorzat során As[threadIdx.y][kk] és Bs[threadIdx.x][kk] mintával történik. Ez általában bank conflict-mentes, de ha a TILE_DIM nem kettő hatvány, vagy a hozzáférési minta megváltozik, teljesítményromlás léphet fel. A bankokkal a későbbi fejezetekben részletesen foglalkozunk.

24.1.7 Labor: lineáris réteg kernel implementálása

A labor célja, hogy a fenti saját kernelt egy teljes programban futtassa, összehasonlítsa a CPU referencia implementációval, és mérést végezzen. Az alábbiakban megadjuk a szükséges környezetet, build- és futtatási parancsokat, valamint a mérési napló sablonját.

24.1.8 Környezet

  • GPU: NVIDIA A100 40 GB (vagy az elérhető hasonló, pl. RTX 3090)
  • Driver: 535.104.05 (ellenőrizd a nvidia-smi kimenetét)
  • CUDA Toolkit: 12.4
  • Operációs rendszer: Ubuntu 22.04 LTS
  • Compute capability: 8.0 (A100 esetén)
  • Power limit / ECC: alapértelmezett, nincs MIG

24.1.9 Build parancs

A forrásfájl neve linear_layer.cu. Fordítás:

nvcc -O3 -arch=sm_80 -Xptxas -v -o linear_layer linear_layer.cu

A -Xptxas -v kiírja a regiszterhasználatot és a shared memory méretet, amely a mérési naplóhoz szükséges.

24.1.10 Futtatási parancs

./linear_layer 1024 4096 4096

ahol az argumentumok: N (batch), K (bemeneti jellemzők), M (kimeneti jellemzők). A program a bemeneteket determinisztikusan inicializálja, lefuttatja a CUDA kernelt, ellenőrzi az eredményt a CPU referencia ellen, és kiírja a futásidőt.
