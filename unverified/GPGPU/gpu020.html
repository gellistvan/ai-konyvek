6.3 Grid-stride loop és perzisztens kernelek

6.3.1 7.3 Grid-stride loop és perzisztens kernelek

Az előző alfejezetben (Többdimenziós indexelés) megismerkedtünk a többdimenziós indexelés alapjaival. Láttuk, hogyan képezzük le a logikai adatszerkezeteket a hardver által biztosított blockIdx, blockDim és threadIdx változókra. Az ott bemutatott minták azonban egy kényes feltételezésre épültek: a rács (grid) mérete pontosan illeszkedett az adat méretére. Ha a vektorunk hossza N, akkor ceil(N / blockDim.x) darab blokkot indítottunk.

Ez a megközelítés a legtöbb egyszerű tankönyvi példában tökéletesen működik, de a valódi, nagy teljesítményű alkalmazásokban ritkán kielégítő. Az adatméret gyakran futásidőben változik, meghaladhatja a GPU által maximálisan indítható blokkok számát, vagy éppen ellenkezőleg: olyan kicsi, hogy a hardver erőforrásainak túlnyomó része kihasználatlanul marad. Ebben az alfejezetben bevezetjük a grid-stride loop (rácslépéses ciklus) mintáját, amely a rugalmas méretű feldolgozás alapvető eszköze. Ezt követően megvizsgáljuk a perzisztens kernel (persistent kernel) koncepcióját, amely a “kevés blokk, sok munka” elv mentén tovább növeli a vezérlési rugalmasságot.

6.3.1.1 7.3.1 A rugalmas méretű feldolgozás mintája

A GPU programozási modelljének egyik központi kihívása a hardveres végrehajtási egységek és a logikai probléma méretének szétválasztása. Ha minden egyes adatelemhez egy szálat rendelünk, akkor a kernel indításakor ismernünk kell a pontos adatméretet. Ez a gyakorlatban nem mindig lehetséges vagy hatékony:

  1. Változó méret: Egy szimulációban a részecskék száma, egy gráfbejárásban a csúcsok száma, vagy egy képfeldolgozó pipeline-ban a képméret futásról futásra változhat.
  2. Maximális gridméret korlát: Bár a modern GPU-k (compute capability 9.0) az x dimenzióban akár 231−12^{31}-1 blokk indítását is lehetővé teszik, egy 10 milliárd elemet tartalmazó tömb feldolgozásakor a hardver ütemezőjének óriási számú blokkal kellene megbirkóznia. A sok kis blokk indítása és ütemezése jelentős overheadet jelenthet.
  3. Hullámok (waves) és telítettség: A GPU Streaming Multiprocesszorai (SM) egyszerre csak korlátozott számú blokkot tudnak futtatni. Ha mi a hardver által maximálisan egyidejűleg támogatott számú blokknál többet indítunk, azokat a hardver ütemezője sorban, “hullámokban” hajtja végre. Ha a feladatunk mérete miatt az utolsó hullám csak félig tölti fel az SM-eket, akkor teljesítményt veszítünk.

A grid-stride loop egy elegáns megoldás ezekre a problémákra. A minta lényege, hogy a szálak száma fix (vagy legalábbis a probléma méretétől függetlenül korlátozott), és minden szál egy ciklusban lépeget végig az adatokon. Az ugrás mérete megegyezik a teljes rácsban lévő összes szál számával: blockDim.x * gridDim.x.

Tekintsük a következő CUDA C++ kódot, amely egy vektorösszeadást valósít meg grid-stride loop segítségével:

// CUDA C++ (C++17), grid-stride loop példa
#include <cstdio>
#include <cuda_runtime.h>

// Hibamakró (a könyv labor-szerződése szerint kötelező)
#define CHECK_CUDA(call)                                                        \
  do {                                                                          \
    cudaError_t err = call;                                                     \
    if (err != cudaSuccess) {                                                   \
      std::fprintf(stderr, "CUDA error %s:%d: %s\n", __FILE__, __LINE__,       \
                   cudaGetErrorString(err));                                    \
      std::abort();                                                             \
    }                                                                           \
  } while (0)

__global__ void vectorAddGridStride(const float *A, const float *B, float *C,
                                   long long N) {
  long long idx = blockIdx.x * blockDim.x + threadIdx.x;
  long long stride = blockDim.x * gridDim.x;

  for (long long i = idx; i < N; i += stride) {
    C[i] = A[i] + B[i];
  }
}

int main() {
  long long N = 1LL << 30; // 1 milliárd elem
  size_t bytes = N * sizeof(float);
  float *d_A, *d_B, *d_C;

  CHECK_CUDA(cudaMalloc(&d_A, bytes));
  CHECK_CUDA(cudaMalloc(&d_B, bytes));
  CHECK_CUDA(cudaMalloc(&d_C, bytes));
  // Inicializálás (host oldalon, pl. cudaMemset vagy feltöltés) ...

  // Fix rácsméret, független N-től (de a GPU-hoz igazítva)
  int blockSize = 256;
  int numBlocks = 32 * 16; // Példa: 16 SM-re optimalizált hullám
                           // (részletek a 7.3.3 pontban)

  vectorAddGridStride<<<numBlocks, blockSize>>>(d_A, d_B, d_C, N);
  CHECK_CUDA(cudaGetLastError());
  CHECK_CUDA(cudaDeviceSynchronize());
  // ...
}

A fenti kódban gridDim.x és blockDim.x szorzataként kiszámított stride a teljes rács szélessége. A szál indexe (idx) határozza meg a kiindulási pozíciót. Ha N nagyobb, mint a szálak száma, a szálak egyszerűen továbblépnek a következő ciklusiterációban. Ha N kisebb, a for ciklus feltétele (i < N) gondoskodik a boundary checkről, vagyis a szál nem ír a lefoglalt tömbön kívülre.

Miért rugalmas ez a minta? Ugyanazt a kernel binárist és ugyanazt a launch konfigurációt használhatjuk akár 1 milliós, akár 1 milliárdos vektorra. A rács mérete csak a GPU hardveres képességeitől függ, nem az adat méretétől. Ez lehetővé teszi a kernel újrahasznosítását anélkül, hogy a host kódban minden méretváltozásnál újra kellene számolni a rácsot.

6.3.1.2 7.3.2 Kevés blokk, sok munka

A grid-stride loop hatékonyságának kulcsa a “kevés blokk, sok munka” elv. Ez az elv azt mondja ki, hogy a GPU teljesítményének maximalizálásához elegendő annyi blokkot indítani, amennyi a hardveres erőforrásokat (SM-ek, regiszterek, shared memory) teljesen lefoglalja. A többi munkát a szálaknak kell elvégezniük a ciklus ismétlésével.

A hagyományos, minden elemet külön szállal lefedő megközelítés (ún. monolitikus kernel) esetén az ütemezőnek rengeteg blokkot kell befejeznie és újat indítania. Ez a blokk-indítási overhead általában kicsi, de ha a kernel futási ideje maga is nagyon rövid, akkor a mérési eredményeket jelentősen torzíthatja.

A grid-stride loop esetén a kernel indításakor a hardver azonnal feltölti az összes SM-et. Amint egy blokk befejezi az adatok rá eső szeletét, új blokkot nem kell indítani; a hardver egyszerűen befejezi a munkát, és a kernel kilép. Ez csökkenti az ütemező terhelését és a kernel indítási késleltetését. Ráadásul, ha a blokkok száma pontosan egyezik a hardver által futtatható blokkok számával, akkor az utolsó, hiányos “hullám” problémája is megszűnik.

Gyakorlati kérdés: Hány blokkot indítsunk? Ha túl kevés blokkot indítunk, a GPU nem lesz teljesen telített. Ha túl sokat, a grid-stride loop elveszíti az előnyeit. Az optimális szám általában a GPU SM-jeinek száma és az SM-enként futtatható blokkok számának szorzata, szorozva egy hullámnyi tartalékkal (pl. 2-4 hullámnyi blokkal a load balancing érdekében). Ezt az értéket a következő alfejezetben (Occupancy optimalizálás) a foglaltsággal (occupancy) kapcsolatos optimalizálás során fogjuk részletesen számszerűsíteni. Addig is elmondható: a grid-stride loop tipikusan akkor hatékony, ha a grid mérete a GPU erőforrásaihoz mérten “ésszerűen kicsi”, azaz nem indítunk szükségtelenül több tízezer blokkot egy pár száz SM-mel rendelkező eszközön.

6.3.1.3 7.3.3 Perzisztens kernel

A grid-stride loop logikai továbbfejlesztése a perzisztens kernel (persistent kernel) vagy más néven progresszív feldolgozás mintája. Míg a grid-stride loop esetén a szálak statikusan, előre meghatározott lépésközzel haladnak, a perzisztens kernelnél a szálak (vagy blokkok) dinamikusan kérnek el új munkát egy globális munkaszámlálóból.

A perzisztens kernel definíciója: olyan kernel, amely pontosan annyi blokkot indít, amennyit a hardver egyidejűleg, egy hullámban futtatni tud, és a kernel a kilépés előtt egy belső ciklusban, atomi műveletek segítségével addig dolgozik, amíg az összes feladat el nem készül.

Ez a megközelítés különösen hasznos, ha a munkaegységek mérete nem egyenletes, vagy ha a feldolgozási idő elemektől függően nagyon változó. A statikus grid-stride loop esetén előfordulhat, hogy az egyik blokk nagyon hosszú ideig dolgozik egy adott adatszeleten, míg a többi blokk már végzett. A perzisztens kernel a work stealing (munkalopás) egy egyszerű formáját valósítja meg: aki végzett, az atomi művelettel lekéri a következő elvégzendő munka azonosítóját.

Tekintsünk egy példát, ahol egy nagy, M×NM \times N méretű mátrix sorait kell feldolgozni, de a feldolgozási idő soronként nagyon eltérő (pl. ritka mátrixok):

// CUDA C++ (C++17), perzisztens kernel dinamikus munkakiosztással
#include <cstdio>
#include <cuda_runtime.h>

__device__ unsigned int globalWorkCounter = 0; // Global memóriában lévő számláló

// Feladat: minden sorra kiszámolunk egy értéket (pl. sorösszeg)
__global__ void processRowsDynamically(const float *matrix, float *output,
                                       int numRows, int numCols) {
  // A blokk dinamikusan kéri a következő sort
  while (true) {
    // Atomi művelettel foglalunk le egy sort (az 1 a lépésköz)
    unsigned int row = atomicAdd(&globalWorkCounter, 1);
    if (row >= numRows) {
      break; // Nincs több munka
    }

    const float *rowPtr = matrix + (size_t)row * numCols;
    float sum = 0.0f;
    for (int col = threadIdx.x; col < numCols; col += blockDim.x) {
      sum += rowPtr[col];
    }

    // Blokkon belüli redukció (lásd gpu058) ...
    // Tegyük fel, hogy a redukciót egy segédfüggvény végzi:
    // float rowSum = blockReduceSum(sum);
    if (threadIdx.x == 0) {
      output[row] = sum; // Egyszerűsített illusztráció
    }
  }
}

int main() {
  // Feltételezzük, hogy a hardveren 16 SM van, SM-enként 2 blokk fér el.
  // => 32 blokk az optimális hullám.
  int numBlocks = 32;
  int blockDim = 256;
  int numRows = 10000;
  int numCols = 512;

  // A munkaszámláló nullázása a host oldalon
  unsigned int init = 0;
  cudaMemcpyToSymbol(globalWorkCounter, &init, sizeof(unsigned int));

  processRowsDynamically<<<numBlocks, blockDim>>>(nullptr, nullptr, numRows, numCols);
  cudaDeviceSynchronize();
  // ...
}

A perzisztens kernel működési elve: 1. Inicializálás: A kernel indítása előtt a globális globalWorkCounter értékét nullára állítjuk. 2. Lefoglalás: Minden blokk az atomicAdd utasítással egyedi értéket szerez a számlálóból. Ez az érték az aktuális feldolgozandó sor azonosítója. 3. Feldolgozás: A blokk a megszerzett soron elvégzi a szükséges számítást. 4. Újrapróbálkozás: A ciklus addig ismétlődik, amíg a megszerzett azonosító el nem éri a sorok számát (numRows). Ekkor a blokk kilép.

Miért előnyös ez a minta? * Automatikus terheléselosztás: Ha a 9999. sor feldolgozása 10-szer annyi ideig tart, mint a többi soré, a többi blokk nem vár rá a statikus elosztás miatt. Amint végeznek a saját statikus szeletükkel, automatikusan lekérnek egy újabb sort a globális munkakupacból. A terhelés így dinamikusan kiegyenlítődik. * Csökkentett indítási overhead: A kernel egyszer indul el, és egyszer áll le. Nincs szükség több száz vagy ezer kis kernel indítására. * Jobb cache-hasznosítás: Egyes esetekben a perzisztens kernel képes megtartani a gyakran használt adatokat a cache-ekben a kernel teljes élettartama alatt.

Korlátok és buktatók: A perzisztens kernel egyik legnagyobb veszélye a deadlock (holtpont). Ha a GPU-n nem fér el az összes blokk egyidejűleg, az ütemező csak akkor indítja el a következő blokkot, ha egy korábbi már befejeződött. Ha egy perzisztens kernelben a blokk egy olyan globális szinkronizációra vár (pl. grid.sync() a cooperative groups használatával), amelyet az összes blokknak el kellene érnie, de néhány blokk még el sem indult, mert a hardver nem tudta ütemezni őket, a rendszer örökre várni fog.

Ezért a perzisztens kernel indításakor szigorúan garantálni kell, hogy a megadott blokkok száma nem haladja meg a hardver által egyidejűleg futtatható blokkok számát. Ezt az erőforrás-számítást a könyv későbbi, az occupancyvel foglalkozó részében (Occupancy optimalizálás) precízen elvégezzük. Emellett a perzisztens kernelek nem használhatják a blokkok közötti szinkronizációt anélkül, hogy megbizonyosodnánk a teljes foglaltságról.

A grid-stride loop és a perzisztens kernel közötti választás gyakran a feladat természetétől függ. Szabályos, jól kiegyensúlyozott feladatoknál (pl. vektorösszeadás, képkonvolúció) a statikus grid-stride loop tökéletes és egyszerűbb. Erősen szabálytalan, változó költségű feladatoknál (pl. ritka lineáris algebra, gráfbejárás, változó hosszúságú részecskeszimuláció) a perzisztens kernel dinamikus munkakiosztása jelentős teljesítménynövekedést hozhat.

6.3.1.4 7.3.4 Labor: Grid-stride loop implementálása

A következő labor célja a grid-stride loop gyakorlati elsajátítása. A feladat egy ritkított mátrix kétdimenziós feldolgozása, ahol a kernel a sorok indexeit egy egydimenziós térben kezeli, lehetővé téve a minta alkalmazását nagyobb, nem pontosan illeszkedő méretekre.

Környezet: * GPU: Helyőrző: NVIDIA RTX 4070 Ti * Driver: Helyőrző: 550.76.01 * CUDA: Helyőrző: 12.4 * OS: Ubuntu 22.04 LTS

Feladat: Írjon CUDA C++ kernelt, amely kiszámítja minden sor elemeinek négyzetösszegét! A mátrix mérete N x M legyen, ahol N = 2^20, M = 128. Használjon grid-stride loopot a sorok feldolgozására! Hasonlítsa össze a futásidőt egy olyan kernelével, amely minden sorhoz egy blokkot indít (N darab blokk), és egy olyanéval, amely kevés blokkal, grid-stride loopot használ!

Várt eredmény: A kevés blokkos, grid-stride loopot használó kernel a nagyszámú blokkindítás overheadjének elkerülése miatt várhatóan gyorsabb. A különbség kisebb a nagy méret miatt, de a rendezettebb SM-terhelés és a csökkentett ütemező overhead mérhető hatást gyakorol a teljesítményre.

CUDA C++ kód (kivonat):

// CUDA C++ (C++17), labor: grid-stride loop a sorok feldolgozására
#include <cstdio>
#include <cuda_runtime.h>
#include <vector>

#define CHECK_CUDA(call) // ... hibamakró definíció ...

// Kernel 1: Minden sorhoz egy blokk (naiv, monolitikus)
__global__ void rowSumNaive(const float *mat, float *out, int M) {
  int row = blockIdx.x;
  float sum = 0.0f;
  for (int col = threadIdx.x; col < M; col += blockDim.x) {
    sum += mat[row * M + col] * mat[row * M + col];
  }
  // Blokkon belüli redukció (shared memory segítségével) ...
  if (threadIdx.x == 0) out[row] = sum;
}

// Kernel 2: Grid-stride loop a sorokon
__global__ void rowSumGridStride(const float *mat, float *out, int N, int M) {
  int stride = blockDim.x * gridDim.x;
  for (int row = blockIdx.x * blockDim.x + threadIdx.x; row < N; row += stride) {
    float sum = 0.0f;
    for (int col = 0; col < M; ++col) {
      sum += mat[row * M + col] * mat[row * M + col];
    }
    out[row] = sum; // Itt most 1 szál dolgozik soronként, a laborban lehet optimalizálni
  }
}

int main() {
  const int N = 1 << 20;
  const int M = 128;
  size_t bytes = (size_t)N * M * sizeof(float);
  // ... allokáció, inicializálás ...

  // 1. Mérés: Naiv kernel
  int blockSize = 256;
  int numBlocks = N;
  rowSumNaive<<<numBlocks, blockSize>>>(d_mat, d_out, M);
  CHECK_CUDA(cudaDeviceSynchronize());

  // 2. Mérés: Grid-stride kernel
  blockSize = 256;
  numBlocks = 32 * 10; // Pl. 10 hullámnyi blokk
  rowSumGridStride<<<numBlocks, blockSize>>>(d_mat, d_out, N, M);
  CHECK_CUDA(cudaDeviceSynchronize());

  // ... összehasonlítás ...
}

Mérési napló (helyőrző): A mérést 10 ismétléssel, melegítéssel végezzük. A táblázatban a mért medián futásidő szerepel.

Módszer Blokkok száma Futásidő (ms) Megjegyzés
Naiv (1 blokk/sor) 1,048,576 13.5 Magas ütemező overhead
Grid-stride loop 320 9.8 Kiegyensúlyozottabb futás

Önellenőrző kérdés: Mi történik, ha a grid-stride loopban az N értéke 0? Válasz: A for ciklus feltétele (row < N) a kezdeti row értékre (amely >= 0) hamis lesz, így a kernel azonnal kilép anélkül, hogy memóriahozzáférést végezne. Ez egy fontos védelmi mechanizmus a hibás üres hívások ellen.

6.3.1.5 7.3.5 Tipikus hibák és a helyes megoldások

A grid-stride loop és a perzisztens kernelek használata során a kezdő fejlesztők gyakran elkövetnek néhány jellegzetes hibát. Az alábbiakban ezeket vesszük sorra, és megadjuk a helyes megoldást.

1. hiba: Helytelen stride használata Sokan a stride-ot blockDim.x-re állítják a gridDim.x * blockDim.x helyett. Ez akkor működik, ha a kernel indítása pontosan egy blokkal történik, de több blokk esetén a szálak átfedésben dolgoznak, vagyis ugyanazokat az adatokat írják és olvassák. Helyes megoldás: A stride mindig a teljes rács szélessége: stride = blockDim.x * gridDim.x.

2. hiba: Túlcsorduló integer típus használata Nagy méretű adatoknál (pl. 2312^{31} feletti elemszám) a int típusú indexelés túlcsordul, ami váratlan memóriahozzáférésekhez és kernelhibákhoz vezet. Helyes megoldás: Az indexeket és a stride-ot long long vagy size_t típusra kell konvertálni a kernelparaméterekben és a ciklusváltozókban, ahogy a 7.3.1 példakódjában is tettük.

3. hiba: A rács méretének helytelen megválasztása Ha a rács mérete túl nagy (pl. a naiv kernelhez hasonlóan minden adatelemhez egy szálat rendelünk), a grid-stride loop elveszíti a hatékonyságát. Ha túl kicsi, akkor az SM-ek nem lesznek telítve. Helyes megoldás: A rács méretét a GPU hardveres jellemzőihez kell igazítani. Használhatjuk a cudaOccupancyMaxActiveBlocksPerMultiprocessor API-t vagy a fejezet későbbi optimalizálási tanácsait.

4. hiba: Perzisztens kernel holtpontja (deadlock) Ha a perzisztens kernelben a blokkok száma meghaladja a hardver által egyidejűleg futtatható blokkok számát, és a kernelben blokkok közötti szinkronizációt alkalmazunk, a kernel soha nem fog befejeződni. Az SM-ek nem tudják elindítani a maradék blokkokat, mert a futó blokkok a szinkronizációs ponton várnak. Helyes megoldás: A perzisztens kernel indításakor soha ne lépjük túl a foglaltsági limitet. Ha lehetséges, kerüljük a blokkok közötti szinkronizációt ebben a mintában, vagy használjunk cooperative groups-ot (lásd később a Grid-szintű szinkronizáció alfejezetet), amely a hardveres képesítést explicit módon ellenőrzi.

A grid-stride loop egy olyan alapvető építőelem, amely lehetővé teszi, hogy a kerneleink méretfüggetlenek és hardverbarátok legyenek. A következő alfejezetben (Launch konfiguráció és hibakezelés) a launch konfiguráció hibakezelésének mélyebb rétegeivel foglalkozunk, és megvizsgáljuk, hogyan kezeljük a kernelindítási hibákat és az aszinkron végrehajtás buktatóit. A perzisztens kernelek és a dinamikus munkakiosztás fogalmai a későbbi fejezetekben, a ritka mátrixok és a gráfalgoritmusok esetében kulcsfontosságú szerepet fognak játszani.
