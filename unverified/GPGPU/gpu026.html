8.1 Blokk-szintű szinkronizáció

A blokkon belüli szálak akkor tudnak hatékonyan együttműködni, ha van egy közös, gyors adatterületük – ez jellemzően a shared memory. A shared memory azonban csak akkor válik használhatóvá, ha a szálak írásai és olvasásai között megfelelő sorrendet biztosítunk. Erre szolgál a CUDA blokk-szintű szinkronizációs eszköze, a __syncthreads().

8.1.1 A __syncthreads szemantikája

A __syncthreads() egy blokk-szintű barrier, azaz szinkronizációs korlát. A hívás helye a kernel végrehajtásában egy olyan pontot jelöl ki, ahol a blokk minden szála találkozik. Amikor egy szál eléri a __syncthreads() hívást, nem lép tovább addig, amíg a blokk összes többi szála is el nem érte ugyanezt a hívást. Amint minden szál elérte a barriert, mindegyikük folytathatja a végrehajtást.

A __syncthreads() kettős szerepet tölt be:

  1. Végrehajtási szinkronizáció: biztosítja, hogy a barrier előtti utasítások minden szálon befejeződjenek, mielőtt bármelyik szál a barrier utáni utasításokat elkezdené.
  2. Memória-láthatóság: a barrier előtti írások – akár global memory-ba, akár shared memory-ba – a barrier után minden szál számára láthatóvá válnak. Ez a blokk szintű memória-konzisztencia alapja.

Fontos, hogy a __syncthreads() csak a blokkon belül szinkronizál. Különböző blokkok szálai nem találkoznak ezen a barriern; a blokkok közötti szinkronizációhoz más eszközökre van szükség (például kernelhatárokra vagy a később tárgyalt cooperative groups-ra).

A __syncthreads() a CUDA C++ nyelvi kiterjesztés része, és nem igényel külön include-ot. A hívásnak a kernelben minden szál által elérhetőnek kell lennie. A hívás szintaxisa egyszerű:

__syncthreads();

A függvény nem ad vissza értéket, és nem fogad paramétert. A hívás során a szál felfüggeszti a végrehajtását, amíg a blokk többi szála is el nem éri ugyanezt a hívást.

8.1.2 Szinkronizációs pontok a kernelben

A __syncthreads() hívások a kernel logikai szakaszokra bontását teszik lehetővé. Egy tipikus minta a következő:

  1. Minden szál betölt egy értéket a global memory-ból a shared memory-ba.
  2. A szálak elérik a __syncthreads() barriert.
  3. A barrier után minden szál a shared memory-ban lévő, már teljesen feltöltött adatokat használja.

Ez a minta biztosítja, hogy egyik szál se kezdjen el olyan shared memory-beli adatot olvasni, amelyet egy másik szál még nem írt meg. A barrier előtti és utáni szakaszok közötti határvonalat szinkronizációs pontnak nevezzük.

Tekintsük a következő egyszerű példát, amelyben egy blokk szálai egy-egy lebegőpontos értéket írnak a shared memory-ba, majd a 0. szál összegzi azokat:

__global__ void block_sum_kernel(const float* input, float* output, int n) {
    __shared__ float sdata[256];
    int tid = threadIdx.x;
    int idx = blockIdx.x * blockDim.x + tid;

    // Betöltés global memory-ból shared memory-ba
    sdata[tid] = (idx < n) ? input[idx] : 0.0f;

    // Szinkronizációs pont: minden szál befejezte az írást
    __syncthreads();

    // A 0. szál összegzi a blokk részösszegét
    if (tid == 0) {
        float sum = 0.0f;
        for (int i = 0; i < blockDim.x; ++i) {
            sum += sdata[i];
        }
        output[blockIdx.x] = sum;
    }
}

Ebben a kernelben a __syncthreads() előtt minden szál a saját sdata[tid] rekeszébe ír. A barrier nélkül a 0. szál elkezdhetné az összegzést, mielőtt a többi szál befejezte volna az írást, ami versenyhelyzetet okozna. A __syncthreads() garantálja, hogy az összegzés csak akkor kezdődik el, amikor a teljes sdata tömb már feltöltődött.

A szinkronizációs pontok száma és elhelyezése jelentős hatással van a teljesítményre. Minden barrier várakozást jelenthet, ha a blokk szálai nem egyszerre érkeznek. Ezért a szinkronizációs pontokat tudatosan kell elhelyezni, és kerülni kell a felesleges hívásokat.

8.1.3 A __syncthreads korlátai

A __syncthreads() használatának szigorú szabályai vannak. A leggyakoribb hibák az alábbi korlátok figyelmen kívül hagyásából adódnak.

8.1.4 Feltételes hívás és divergens barrier

A __syncthreads()-et a blokk minden szálának el kell érnie. Ha a hívás egy feltételes ágban van, akkor a feltételnek a blokk minden szálára azonosan kell kiértékelődnie. Ellenkező esetben a barrier holtpontot okozhat, vagy a viselkedés meghatározatlan (undefined behavior).

A következő kód hibás:

__global__ void wrong_kernel(float* data, int n) {
    __shared__ float sdata[256];
    int tid = threadIdx.x;

    if (tid < n) {
        sdata[tid] = data[tid];
        __syncthreads();  // HIBA: nem minden szál éri el
    }

    // ... további feldolgozás
}

Ha n < blockDim.x, akkor a tid >= n szálak nem lépnek be az if ágba, így nem hívják a __syncthreads()-et. A belépő szálak viszont várakozni fognak, ami holtpontot eredményez. Még ha n éppen egyenlő is a blokkmérettel, a kód akkor is veszélyes, mert a feltétel a szálak indexétől függ, és a jövőbeli módosítások során könnyen hibássá válhat.

A helyes megoldás az, hogy a barrier a feltételes ágon kívül helyezkedik el, így minden szál eléri:

__global__ void correct_kernel(float* data, int n) {
    __shared__ float sdata[256];
    int tid = threadIdx.x;

    if (tid < n) {
        sdata[tid] = data[tid];
    }
    __syncthreads();  // Minden szál eléri

    // ... további feldolgozás
}

Ebben a változatban a feltétel csak azt befolyásolja, hogy mely szálak írnak a shared memory-ba, de a barrier minden szál számára közös. Ez biztosítja, hogy az írások befejeződése után minden szál továbbléphessen.

8.1.5 Különböző ágakban elhelyezett barrierek

Előfordulhat, hogy a fejlesztő több __syncthreads() hívást helyez el, például egy if-else szerkezet két ágában. Ez akkor helyes, ha a feltétel minden szálra azonosan értékelődik ki. Ha azonban a feltétel szálanként eltérő, akkor a két ág szálai nem ugyanazon a barriern találkoznak, ami holtponthoz vezet. Ezért a barriereket lehetőleg a feltételes szerkezeteken kívül kell elhelyezni, vagy biztosítani kell, hogy a feltétel a teljes blokkra nézve egységes legyen.

8.1.6 Ciklusok és változó iterációszám

Hasonló probléma léphet fel, ha a __syncthreads() egy olyan ciklusban van, amelynek iterációszáma szálanként eltérő. Például:

__global__ void wrong_loop_kernel(float* data, int n) {
    __shared__ float sdata[256];
    int tid = threadIdx.x;

    for (int i = tid; i < n; i += blockDim.x) {
        sdata[tid] += data[i];
        __syncthreads();  // HIBA: az iterációszám eltérő
    }
}

Itt a szálak különböző számú iterációt hajthatnak végre, így a barrier hívások száma eltér, ami holtpontot vagy meghatározatlan viselkedést okoz. A megoldás az, hogy a ciklust úgy szervezzük, hogy minden szál azonos számú iterációt végezzen, vagy a barriert a cikluson kívülre helyezzük, esetleg a ciklus előtt és után.

8.1.7 Nem blokkok közötti szinkronizáció

A __syncthreads() nem alkalmas arra, hogy különböző blokkok szálait szinkronizálja. A blokkok egymástól függetlenül futnak, és a GPU ütemezője nem garantálja, hogy minden blokk egyszerre van jelen az SM-eken. Ezért a blokkok közötti szinkronizációhoz más mechanizmusok szükségesek, például a kernel befejezése és egy új kernel indítása, vagy a cooperative groups grid-szintű szinkronizációja (amelyet a későbbi fejezetben tárgyalunk).

8.1.8 A blokkméret hatása

A __syncthreads() a teljes blokkra vonatkozik, ezért a blokkméret növelése növeli a barrier várakozási idejét is, ha a szálak nem egyszerre érkeznek. A nagy blokkméret azonban nem okoz helyességi problémát, csak teljesítménycsökkenést. A blokkméretet az erőforrás-korlátok (regiszterek, shared memory) és a feldolgozási logika alapján kell megválasztani.

8.1.9 A __syncthreads hardveres háttere

Bár a __syncthreads() magas szintű absztrakciónak tűnik, a hardveren a barrier a blokk warpjainak szinkronizálásával valósul meg. Minden blokk warpokból áll, és a barrier akkor teljesül, ha a blokk összes warpja elérte a barriert. Az SM-en a warpütemező figyeli a warpok állapotát; amikor egy warp a barrierhez ér, várakozó állapotba kerül. Amint az utolsó warp is megérkezik, az összes warp felszabadul, és folytathatja a végrehajtást.

Fontos, hogy amíg egy blokk várakozik a barriern, az SM más blokkokat is futtathat. Ez azt jelenti, hogy a barrier nem feltétlenül okoz üresjáratot a hardveren, ha elegendő másik blokk van, amelyekkel az SM ki tudja tölteni a várakozási időt. Ez a latency hiding része, amelyet a későbbi fejezetekben részletesen tárgyalunk.

A __syncthreads() a PTX szinten egy bar.sync utasításnak felel meg. A PTX ISA dokumentációja leírja, hogy a barrier a blokk szintjén működik, és a szálak elérik a barriert. A CUDA C++ fordító ezt az utasítást generálja, és a hardver hajtja végre.

8.1.10 Gyakori hibák és megelőzésük

A fenti korlátokon túl érdemes áttekinteni a leggyakoribb hibákat, amelyek a __syncthreads() használatával kapcsolatban felmerülnek.

8.1.11 1. Elfelejtett barrier

A leggyakoribb hiba, amikor a fejlesztő shared memory-ba ír, majd szinkronizáció nélkül olvassa azt egy másik szálból. Ez versenyhelyzetet okoz, mert az olvasó szál még azelőtt olvashat, hogy az író szál befejezte volna az írást. A tünet gyakran nem determinisztikus: a program néha helyes eredményt ad, néha hibásat, attól függően, hogy az ütemező milyen sorrendben futtatta a szálakat. A megoldás mindig az, hogy az írás és az olvasás közé __syncthreads() kerüljön.

8.1.12 2. Felesleges barrier

Bár a __syncthreads() hasznos, a felesleges hívások fölösleges várakozást okozhatnak. Ha nincs szükség arra, hogy minden szál befejezze az írást a következő olvasás előtt, akkor a barrier elhagyható. Például ha minden szál csak a saját sdata[tid] rekeszét írja és olvassa, akkor nincs szükség barrierre. A barrierre akkor van szükség, ha egy szál más szál által írt adatot olvas.

8.1.13 3. A barrier utáni feltételezések

A __syncthreads() csak a blokkon belüli láthatóságot garantálja. Nem szabad feltételezni, hogy a barrier után a global memory-ba írt adatok más blokkok számára is láthatóvá válnak. A blokkok közötti láthatósághoz kernelhatár vagy más szinkronizációs mechanizmus szükséges.

8.1.14 4. A __syncthreads() hiánya az elágazás után

Gyakori minta, hogy a szálak egy feltételes részben dolgoznak, majd a feltételes rész után közös kód következik, amely a feltételes részben módosított shared memory-t használja. Ilyenkor a feltételes rész után mindig szükség van egy __syncthreads()-re, még akkor is, ha a feltételes részben volt már barrier. Ez azért fontos, mert a feltételes részben a szálak eltérő utakat járhatnak be, és a közös kód előtt ismét szinkronizálni kell.

Például:

__global__ void example_kernel(float* data, int n) {
    __shared__ float sdata[256];
    int tid = threadIdx.x;

    if (tid % 2 == 0) {
        sdata[tid] = data[tid] * 2.0f;
    } else {
        sdata[tid] = data[tid] * 0.5f;
    }

    __syncthreads();  // Szükséges, mert a közös kód minden sdata elemet olvas

    // Közös feldolgozás, amely az sdata minden elemét használja
    float val = sdata[(tid + 1) % blockDim.x];
    // ...
}

Itt a __syncthreads() nélkül az sdata[(tid + 1) % blockDim.x] olvasása versenyhelyzetet okozna.

8.1.15 Labor: shared memory-t használó kernel szinkronizálása

A labor célja a __syncthreads() helyes használatának bemutatása egy egyszerű, ellenőrizhető példán keresztül. A feladat egy olyan kernel írása, amely egy blokkban összegzi a bemeneti tömb elemeit úgy, hogy a szálak először a saját értéküket a shared memory-ba írják, majd a barrier után a 0. szál kiszámítja az összeget. A kernel futását CUDA eventekkel mérjük, és az eredményt a CPU által számított referenciaértékkel hasonlítjuk össze.

8.1.16 Kernel implementáció

A korábban bemutatott block_sum_kernel alkalmas erre a célra. Az alábbiakban a teljes CUDA C++ programot adjuk meg, amely tartalmazza a hibakezelést és a mérést is.

#include <cuda_runtime.h>
#include <iostream>
#include <vector>
#include <numeric>
#include <cmath>

// Hibakezelő makró
#define CUDA_CHECK(call)                                                      \
    do {                                                                      \
        cudaError_t err = call;                                               \
        if (err != cudaSuccess) {                                             \
            std::cerr << "CUDA hiba: " << cudaGetErrorString(err)             \
                      << " (" << __FILE__ << ":" << __LINE__ << ")"           \
                      << std::endl;                                           \
            std::exit(EXIT_FAILURE);                                          \
        }                                                                     \
    } while (0)

// Kernel: blokkszintű összegzés shared memory-val és __syncthreads()-szel
__global__ void block_sum_kernel(const float* input, float* output, int n) {
    __shared__ float sdata[256];
    int tid = threadIdx.x;
    int idx = blockIdx.x * blockDim.x + tid;

    // Betöltés global memory-ból shared memory-ba
    sdata[tid] = (idx < n) ? input[idx] : 0.0f;

    // Szinkronizációs pont: minden szál befejezte az írást
    __syncthreads();

    // A 0. szál összegzi a blokk részösszegét
    if (tid == 0) {
        float sum = 0.0f;
        for (int i = 0; i < blockDim.x; ++i) {
            sum += sdata[i];
        }
        output[blockIdx.x] = sum;
    }
}

int main() {
    const int N = 1024;          // Bemeneti elemek száma
    const int BLOCK_SIZE = 256;  // Blokkméret
    const int GRID_SIZE = (N + BLOCK_SIZE - 1) / BLOCK_SIZE;

    // Bemeneti adatok előkészítése
    std::vector<float> h_input(N);
    std::iota(h_input.begin(), h_input.end(), 0.0f); // 0, 1, 2, ..., N-1
    float h_output[GRID_SIZE] = {0.0f};

    float* d_input;
    float* d_output;
    CUDA_CHECK(cudaMalloc(&d_input, N * sizeof(float)));
    CUDA_CHECK(cudaMalloc(&d_output, GRID_SIZE * sizeof(float)));
    CUDA_CHECK(cudaMemcpy(d_input, h_input.data(), N * sizeof(float),
                          cudaMemcpyHostToDevice));

    // CUDA eventek az időméréshez
    cudaEvent_t start, stop;
    CUDA_CHECK(cudaEventCreate(&start));
    CUDA_CHECK(cudaEventCreate(&stop));

    // Warm-up
    block_sum_kernel<<<GRID_SIZE, BLOCK_SIZE>>>(d_input, d_output, N);
    CUDA_CHECK(cudaDeviceSynchronize());
    CUDA_CHECK(cudaGetLastError());

    // Mérés: 10 ismétlés
    const int REPEAT = 10;
    float total_time_ms = 0.0f;
    for (int i = 0; i < REPEAT; ++i) {
        CUDA_CHECK(cudaEventRecord(start));
        block_sum_kernel<<<GRID_SIZE, BLOCK_SIZE>>>(d_input, d_output, N);
        CUDA_CHECK(cudaEventRecord(stop));
        CUDA_CHECK(cudaEventSynchronize(stop));
        float elapsed_ms = 0.0f;
        CUDA_CHECK(cudaEventElapsedTime(&elapsed_ms, start, stop));
        total_time_ms += elapsed_ms;
    }

    float avg_time_ms = total_time_ms / REPEAT;
    float variance_ms = 0.0f;
    // A szóráshoz újra kellene mérni az egyes időket; itt a példa kedvéért
    // feltételezzük, hogy az átlag körüli szórás 0.05 ms alatt van.
    // Valós mérésnél minden iteráció idejét el kell tárolni.
    // Itt csak a módszertant mutatjuk be.

    // Eredmény visszamásolása
    CUDA_CHECK(cudaMemcpy(h_output, d_output, GRID_SIZE * sizeof(float),
                          cudaMemcpyDeviceToHost));

    // Referencia számítás CPU-n
    float ref_sum = std::accumulate(h_input.begin(), h_input.end(), 0.0f);

    // GPU összegzés: a blokkok részösszegeit összegezzük
    float gpu_sum = 0.0f;
    for (int i = 0; i < GRID_SIZE; ++i) {
        gpu_sum += h_output[i];
    }

    // Ellenőrzés
    float abs_err = std::fabs(gpu_sum - ref_sum);
    std::cout << "Referencia összeg (CPU): " << ref_sum << "\n";
    std::cout << "GPU összeg:              " << gpu_sum << "\n";
    std::cout << "Abszolút hiba:           " << abs_err << "\n";
    std::cout << "Átlagos kernel idő:      " << avg_time_ms << " ms\n";
    std::cout << "Ismétlések száma:        " << REPEAT << "\n";

    if (abs_err < 1e-3f) {
        std::cout << "Ellenőrzés: SIKERES\n";
    } else {
        std::cout << "Ellenőrzés: SIKERTELEN\n";
    }

    // Takarítás
    CUDA_CHECK(cudaFree(d_input));
    CUDA_CHECK(cudaFree(d_output));
    CUDA_CHECK(cudaEventDestroy(start));
    CUDA_CHECK(cudaEventDestroy(stop));

    return 0;
}

8.1.19 A divergens __syncthreads hiba szemléltetése

A labor során érdemes kipróbálni egy hibás változatot is, hogy a holtpont jelensége saját tapasztalatból ismertté váljon. Ehhez a block_sum_kernel egy módosított változatát használjuk, ahol a __syncthreads() egy feltételes ágba kerül:

__global__ void wrong_block_sum_kernel(const float* input, float* output, int n) {
    __shared__ float sdata[256];
    int tid = threadIdx.x;
    int idx = blockIdx.x * blockDim.x + tid;

    sdata[tid] = (idx < n) ? input[idx] : 0.0f;

    if (tid == 0) {
        __syncthreads();  // HIBA: csak a 0. szál éri el
    }

    if (tid == 0) {
        float sum = 0.0f;
        for (int i = 0; i < blockDim.x; ++i) {
            sum += sdata[i];
        }
        output[blockIdx.x] = sum;
    }
}

Ha ezt a kernelt futtatjuk, a 0. szál a __syncthreads()-nél várakozni fog, mert a többi szál nem éri el a barriert. A kernel nem tér vissza, és a cudaDeviceSynchronize() hívás végtelenül blokkol. Az ilyen hibák a gyakorlatban az eszköz leállásához vezethetnek, ezért a laborban izolált környezetben, timeout beállításával szabad csak kipróbálni. A mérési környezetben a nvidia-smi és a konténer erőforrás-korlátai biztosítják, hogy a hiba ne érintse a többi felhasználót.

A hibás kernel futtatása előtt ellenőrizzük a GPU állapotát, és legyen terv a visszaállításra (például a CUDA context megszakítása vagy a folyamat leállítása). A jelenség megértése segít elkerülni a hasonló hibákat a valós kódban.

8.1.20 Önellenőrző kérdés

Mi történik, ha a következő kódot futtatjuk?

__global__ void faulty_kernel() {
    __shared__ float sdata[64];
    int tid = threadIdx.x;

    if (tid % 2 == 0) {
        sdata[tid] = 1.0f;
        __syncthreads();
    }

    // ...
}

Válasz: A páros tid-vel rendelkező szálak belépnek az if ágba, és elérik a __syncthreads() hívást, míg a páratlan szálak nem. A páros szálak várakozni fognak a barriern, de a páratlan szálak soha nem érkeznek meg, így a kernel holtpontra jut. A viselkedés meghatározatlan, és a GPU leállhat. A helyes megoldás az, ha a __syncthreads() a feltételes ágon kívülre kerül.

8.1.21 Összefoglalás

A __syncthreads() a CUDA blokk-szintű szinkronizáció alapvető eszköze. Megfelelő használatával biztosítható, hogy a blokk szálai által közösen használt shared memory-ban lévő adatok konzisztensek legyenek. A barrier előtti írások a barrier után minden szál számára láthatóvá válnak, és a barrier garantálja, hogy minden szál befejezte a barrier előtti utasításokat. A __syncthreads() azonban szigorú szabályokhoz kötött: minden szálnak el kell érnie ugyanazt a hívást, és a hívás nem lehet feltételes ágban, ha a feltétel nem egységes a blokkra nézve. A divergens barrier holtpontot okoz, és a program meghatározatlan viselkedéséhez vezet. A helyes minta az, hogy a szinkronizációs pontokat a feltételes szakaszokon kívül, a logikai fázisok határára helyezzük, és a barriereket tudatosan, a szükségességük szerint alkalmazzuk. A következő alfejezet az atomi műveletekre épít, amelyek a szinkronizáció alternatíváját kínálják olyan esetekben, amikor a barrier nem elegendő vagy nem hatékony.
