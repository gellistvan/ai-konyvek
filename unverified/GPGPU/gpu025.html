7.4 Memóriaterek kiválasztása

A memóriaterek kiválasztása a CUDA-kernel tervezésének egyik legnagyobb hatású döntése. Nem az a kérdés, hogy „melyik memóriatér a leggyorsabb”, hanem az, hogy egy adott adat melyik memóriatérben éri el a legjobb kompromisszumot a késleltetés, a sávszélesség és a láthatóság szempontjából. A regiszterek gyakorlatilag nulla késleltetésűek, de csak egyetlen szálra látszanak. A global memory a teljes grid számára elérhető, de a DRAM-késleltetés több száz ciklus is lehet. A shared, constant, local és texture terek közé esnek; a helyes választás a hozzáférési mintától, az élettartamtól és az írási/olvasási igénytől függ. Ebben az alfejezetben egy döntési keretet építünk fel, megvizsgáljuk egy kernel memóriaprofilját, majd egy ellenőrizhető laborban elkészítjük a memóriatér-döntési táblázatot.

7.4.1 Döntési keret: latency, bandwidth és scope

A memóriatér-választás három műszaki tengelye a következő.

Latency (késleltetés): Az az idő, amennyi egy memóriaművelet elindítása és az adat rendelkezésre állása között telik el. A GPU a késleltetést elsősorban szálak közötti átfedéssel (latency hiding) rejti el, de a forrás memóriatér nagyságrendileg meghatározza a várakozási időt. A regiszterek hozzáférése gyakorlatilag az utasítás végrehajtásának része. A shared memory késleltetése jellemzően 20–40 ciklus nagyságrendű, míg a global memory elérése cache nélkül több száz ciklust is jelenthet. A constant memória késleltetése broadcast esetén közel áll a regiszterhez, konfliktus esetén viszont drámaian romlik.

Bandwidth (sávszélesség): A másodpercenként átvihető bájtok mennyisége. A global memória sávszélessége a DRAM-ból származik, és tipikusan a GPU egyik legszűkebb erőforrása. A shared memory sávszélessége nagyságrenddel nagyobb, mert on-chip memória. A constant memória széles sávszélességet tud biztosítani, ha a warp minden szála ugyanazt a címet olvassa (broadcast). A local memória valójában a global memóriába kerül, tehát sávszélessége a global memoryéval megegyező, hiába neve „local”. A texture memória sávszélessége a textúra gyorsítótáron keresztül a 2D-s térbeli lokalitást használja ki.

Scope (láthatóság): Azt mondja meg, hogy egy adat mely végrehajtási egységek számára elérhető. A CUDA-végrehajtási hierarchiában a szál, a warp, a block, a grid és a host szintjei léteznek. A regiszterek szál-szintűek, a shared memory block-szintű, a global memory grid-szintű, a constant memória grid-szintű (írásra host-oldalról, olvasásra device-szinten), a local memória szál-szintű, de fizikailag global memóriában lakik. A scope megszabja, hogy egy adatot milyen szinkronizációs mechanizmussal lehet megosztani, és milyen élettartamot várhatunk el.

A döntési folyamat első lépése tehát az adat életciklusának és hozzáférési mintájának feltérképezése. Kérdezzük meg:

  • Hány szál használja ugyanazt az adatot?
  • Csak olvasásra vagy írásra is?
  • Mennyi az adat mérete?
  • Milyen időközönként férünk hozzá?
  • Van-e térbeli vagy időbeli lokalitás?
  • Kell-e a host és a device között mozgatni?
  • Lehet-e a hozzáférést broadcasttá alakítani?

Ezekre a kérdésekre adott válaszokból áll össze a döntési táblázat.

7.4.2 Az öt klasszikus CUDA-memóriatér döntési szempontjai

A korábbi alfejezetekben már bemutattuk az egyes memóriaterek technikai hátterét, itt kifejezetten a kiválasztás szempontjait foglaljuk össze.

7.4.3 Global memory

A global memory az alapértelmezett nagyméretű, grid-szintű memóriatér. Ide kerülnek a cudaMalloc-kal allokált pufferek, a cudaMemcpy-vel feltöltött tömbök és a kernelparaméterként átadott mutatók által címzett adatok. Használata akkor indokolt, ha:

  • az adat mérete meghaladja a shared vagy constant memória kapacitását,
  • az adatot több block, a teljes grid vagy a host és a device közösen használja,
  • írásra is szükség van,
  • az adat élettartama túlnyúlik egyetlen kernelhíváson.

A global memory költsége csökkenthető coalesced hozzáféréssel, vectorizált betöltéssel és L1/L2 cache-barát mintával. Ha egy adatot csak egyszer olvasunk, és nincs más lehetőség, akkor a global memory a természetes választás. Ha azonban ugyanazt a blokkon belül többször újraolvassuk, érdemes megfontolni a shared memory-ba másolást.

7.4.4 Shared memory

A shared memory block-szintű, on-chip, programozható, alacsony késleltetésű memóriatér. Akkor válasszuk, ha:

  • ugyanazt az adatot egy blockon belül több szál szeretné elérni,
  • a hozzáférések között adatcsere vagy csoportos redukció szükséges,
  • egy global memóriából betöltött adatdarabot újrahasznosítunk tiling vagy stencil során,
  • a hozzáférést bank-konfliktusmentesre tudjuk szervezni.

A shared memory mérete korlátozott: tipikusan 48–164 KiB SM-enként, a konfigurációtól és architektúrától függően. Ha a teljes probléma elférne, akkor is figyelni kell arra, hogy a shared memory használata csökkenti az occupancy-t, mert egy SM-en a blockok száma korlátozott. A döntés során ezért mindig ellenőrizni kell, hogy a shared memória által elért global-memory-megtakarítás nagyobb-e, mint az occupancy-csökkenésből adódó latency-hiding romlás.

7.4.5 Constant memory

A constant memory grid-szintű, olvasható a device számára, de írni jellemzően a host írhat (cudaMemcpyToSymbol). Akkor előnyös, ha:

  • ugyanazt a néhány bájtnyi paramétert a warp minden szála olvassa anélkül, hogy a hozzáférési címek különböznének,
  • a hozzáférés broadcast mintájú: például egy skála, offset, filter együttható vagy táblázat,
  • az adat nem változik a kernel futása alatt.

A constant memória broadcast sávszélessége kiváló, de ha egy warpen belül különböző címekről olvasnak a szálak, a hozzáférés sorosodik, és a teljesítmény drasztikusan romlik. Ezért az olyan adat, amelyet a szálak különböző indexekkel érnek el, nem ide való. Ha a táblázat mérete nagy és véletlenszerű indexekkel olvassuk, a global memory vagy a texture memória jobb választás lehet.

7.4.6 Local memory

A local memory fogalma megtévesztő: ez szál-szintű, de fizikailag a global memóriában tárolódik. Akkor használja a fordító, ha a bemeneti forráskódban szereplő lokális változó nem fér el a regiszterekben, vagy ha a tömb indexelése dinamikus, és a tömb nem konvertálható regiszterekre. A local memória használata rendszerint kerülendő:

  • ha egy tömb mérete kicsi és a hozzáférések statikusak, akkor a fordító regiszterekben tarthatja;
  • ha nagy, dinamikusan indexelt privát tömb szükséges, akkor is gondoljunk arra, hogy a valódi adatmegosztás lehetőségét kihasználjuk shared memory segítségével.

A local memory a kernel memóriaprofiljában gyakran a „local load/store” tranzakciókban jelenik meg, és gyengíti a teljesítményt. A döntési táblázatban a local memory elsősorban figyelmeztető bejegyzés: ha a profilban nagy local forgalom látható, akkor a kernel regiszter- vagy shared-memory-kialakítását újra kell gondolni.

7.4.7 Texture memory

A texture memory egy speciális, read-only elérési út, amelyet textúraobjektumokkal vagy textúra referenciákkal érhetünk el. Akkor használjuk, ha:

  • 2D/3D térbeli lokalitás van a hozzáférésekben, és a cache-sorok kihasználása fontos,
  • interpolációt, normalizált koordinátákat vagy címzési módokat szeretnénk használni,
  • a hozzáférés read-only, és a hardware textúra gyorstár kihasználása előnyös.

A modern GPU-ken a textúra memória sok esetben a global memory cache-elt eléréséhez hasonló, így nem szabad automatikusan „gyorsabbnak” tekinteni. A döntés során a textúra akkor indokolt, ha a mintavételi mód, a szűrés vagy a határkezelés hardveres támogatása csökkenti a kód komplexitását, illetve ha a hozzáférési minták miatt a textúra cache jobb találati arányt ad.

7.4.9 Kernel memóriaprofiljának felépítése

A memóriatér-döntés nem szakadhat el a méréstől. Egy kernel memóriaprofilja azt mondja meg, hogy a kernel futása során milyen memóriaterekből mennyi adatot mozgatunk, milyen hatékonysággal, és hol keletkeznek várakozások. A profil elkészítésének lépései:

  1. Felmérjük a hasznos adatforgalmat. Hány bájtot olvasunk és írunk a global memoryból? Hány bájtot töltünk be a shared memorybe? A hasznos forgalom az algoritmus által ténylegesen megkívánt adatmennyiség.

  2. Megnézzük a tényleges memóriatranzakciókat. A global memória nem bájtonként, hanem 32-, 64- vagy 128 bájtos szektorokban mozog. A memóriaprofilból kiderül, hogy a kért szektorok hány százalékát használjuk ki. A coalescing hatékonysága a hasznos bájtok és a ténylegesen beolvasott szektorok bájtjainak aránya.

  3. Megvizsgáljuk a shared memory bank konfliktusokat. A shared memory elérési mintája lehet conflict-free, vagy okozhat 2-, 4-, 8-utas konfliktust. A profilban a bank conflictok száma azt jelzi, hogy a döntés egyébként helyes, de a adatelrendezés nem optimális.

  4. Azonosítjuk a local memory spillt. Ha a regiszterhasználat meghaladja a rendelkezésre álló regisztereket, a fordító local memóriába ír. A profilban a local load/store tranzakciók jelennek meg. Ezt a döntési táblázatban a local memória sorához kapcsoljuk.

  5. Értelmezzük a cache találati arányokat. Az L1 és L2 találati arányok megmutatják, hogy a global memory hozzáférésekből mennyit sikerül elkerülni. A shared memory tiling célja gyakran az, hogy a global hozzáférések helyett L1/shared hozzáféréseket használjunk.

  6. Összevetjük a mért sávszélességet a névleges csúccsal. A Roofline-modellből ismert, hogy a kernel lehet memória-korlátos vagy számítás-korlátos. A memóriaprofilból kiolvasott forgalom és idő hányadosa adja a tényleges sávszélességet, amelyet a GPU specifikációjával kell összehasonlítani.

A Nsight Compute ilyen mutatói közé tartoznak például:

  • l1tex__t_sectors_pipe_lsu_mem_global_op_ld.sum
  • l1tex__t_sectors_pipe_lsu_mem_global_op_st.sum
  • l1tex__data_bank_conflicts_pipe_lsu_mem_shared.sum
  • smsp__sass_inst_executed_op_local_ld.sum
  • smsp__sass_inst_executed_op_local_st.sum
  • gpu__time_duration.sum

Ezeket a metrikaneveket a Nsight Compute verziója és architektúra szerint ellenőrizni kell, és a laborban a pontos név szerepeljen. A cél az, hogy a memóriatér-döntés számszerűen is igazolható legyen.

7.4.10 Labor: memóriatér-döntési táblázat és mérés

Az alábbi labor egy olyan kis CUDA-projektet mutat be, amelyben ugyanaz a feladat több memóriatér-kialakítással fut. A feladat egyszerű: egy bemeneti vektort skálázunk egy konstanssal, eltolunk egy konstanssal, majd blokkonként összegezzük a részeredményeket. A kialakítások lehetőséget adnak a global, constant, shared és local memória szerepének demonstrálására.

7.4.11 Kernelváltozatok

  1. Global-only változat: minden szál kiolvassa a bemeneti elemet a global memoryból, elvégzi a skálázást és eltolást, majd kiírja az eredményt.
  2. Constant-táras változat: a skála és az offset értékeket constant memóriába tesszük, így a warp minden szála broadcast hozzáférést kap.
  3. Shared-redukciós változat: a blokk beolvassa a bemeneti szegmenst, a szálak az egyes elemeket shared memóriába írják, majd fa-struktúrájú redukcióval blokkonkénti összeget számolnak.
  4. Local-memory-büntetés változat: egy privát tömböt dinamikusan indexelünk, hogy a fordító local memoryt használjon; ezzel megmutatjuk a local memória árát.

7.4.12 CUDA C++ példakód

// fordítás: nvcc -O3 -arch=sm_89 -o memlab memlab.cu
// megjegyzés: a kód a labor izolált környezetéhez készült,
// éles rendszeren és hitelesítő adattal ne futtassuk.
#include <cuda_runtime.h>
#include <cstdio>
#include <cmath>
#include <vector>

#define CUDA_CHECK(call)                                                     \
    do {                                                                     \
        cudaError_t err__ = (call);                                          \
        if (err__ != cudaSuccess) {                                          \
            std::fprintf(stderr, "CUDA hiba: %s, fajl: %s, sor: %d\n",       \
                         cudaGetErrorString(err__), __FILE__, __LINE__);     \
            return err__;                                                    \
        }                                                                    \
    } while (0)

__constant__ float c_scale;
__constant__ float c_offset;

template <int BLOCK>
__global__ void global_only_scale(const float* __restrict__ x,
                                  float* __restrict__ y,
                                  float scale,
                                  float offset,
                                  int n)
{
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        float v = x[i];
        y[i] = fmaf(v, scale, offset);
    }
}

template <int BLOCK>
__global__ void constant_scale(const float* __restrict__ x,
                               float* __restrict__ y,
                               int n)
{
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        float v = x[i];
        y[i] = fmaf(v, c_scale, c_offset);
    }
}

template <int BLOCK>
__global__ void shared_reduce(const float* __restrict__ x,
                              float* __restrict__ block_sum,
                              int n)
{
    __shared__ float sdata[BLOCK];
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    float v = (i < n) ? x[i] : 0.0f;
    v = fmaf(v, c_scale, c_offset);
    sdata[threadIdx.x] = v;
    __syncthreads();

    for (int stride = BLOCK / 2; stride > 0; stride >>= 1) {
        if (threadIdx.x < stride) {
            sdata[threadIdx.x] += sdata[threadIdx.x + stride];
        }
        __syncthreads();
    }

    if (threadIdx.x == 0) {
        block_sum[blockIdx.x] = sdata[0];
    }
}

__global__ void local_penalty(const float* __restrict__ x,
                              float* __restrict__ y,
                              int n,
                              int kMax)
{
    // A tmp[] dinamikusan indexelt, ezért a fordító nagy valószínűséggel
    // local memoryt használ. A kMax paraméter miatt a ciklus nem unrollható.
    float tmp[128];
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        for (int k = 0; k < kMax; ++k) {
            tmp[k] = x[i] * static_cast<float>(k);
        }
        float sum = 0.0f;
        for (int k = 0; k < kMax; ++k) {
            sum += tmp[k];
        }
        y[i] = sum;
    }
}

A local_penalty kernelben a tmp tömb mérete 128 float. A fordító akkor tudná regiszterben tartani, ha minden hozzáférést konstans indexszel oldana fel. Mivel a k változó futás közben, a kMax paramétertől függően változik, a tömböt valószínűleg local memoryba helyezi. Ezt a mérési profilban a local tranzakciók növekedése mutatja majd.

A host oldalon a mérési ciklus:

int main()
{
    constexpr int N = 1 << 22;
    constexpr int BLOCK = 256;
    constexpr int GRID = (N + BLOCK - 1) / BLOCK;
    constexpr int ITER_WARMUP = 5;
    constexpr int ITER_MEAS = 10;

    size_t nBytes = N * sizeof(float);
    std::vector<float> h_in(N), h_out(N);
    for (int i = 0; i < N; ++i) h_in[i] = 1.0f;

    float *d_x, *d_y, *d_sum;
    CUDA_CHECK(cudaMalloc(&d_x, nBytes));
    CUDA_CHECK(cudaMalloc(&d_y, nBytes));
    CUDA_CHECK(cudaMalloc(&d_sum, GRID * sizeof(float)));
    CUDA_CHECK(cudaMemcpy(d_x, h_in.data(), nBytes, cudaMemcpyHostToDevice));

    float scale = 0.5f, offset = 1.0f;
    CUDA_CHECK(cudaMemcpyToSymbol(c_scale, &scale, sizeof(float)));
    CUDA_CHECK(cudaMemcpyToSymbol(c_offset, &offset, sizeof(float)));

    cudaEvent_t start, stop;
    CUDA_CHECK(cudaEventCreate(&start));
    CUDA_CHECK(cudaEventCreate(&stop));

    // Warm-up
    for (int it = 0; it < ITER_WARMUP; ++it) {
        global_only_scale<BLOCK><<<GRID, BLOCK>>>(d_x, d_y, scale, offset, N);
    }
    CUDA_CHECK(cudaDeviceSynchronize());

    // Mérés: global-only
    float times[ITER_MEAS];
    for (int it = 0; it < ITER_MEAS; ++it) {
        CUDA_CHECK(cudaEventRecord(start));
        global_only_scale<BLOCK><<<GRID, BLOCK>>>(d_x, d_y, scale, offset, N);
        CUDA_CHECK(cudaEventRecord(stop));
        CUDA_CHECK(cudaEventSynchronize(stop));
        CUDA_CHECK(cudaEventElapsedTime(&times[it], start, stop));
    }
    float avg = 0.0f, var = 0.0f;
    for (int it = 1; it < ITER_MEAS; ++it) avg += times[it];
    avg /= (ITER_MEAS - 1);
    for (int it = 1; it < ITER_MEAS; ++it) var += (times[it] - avg) * (times[it] - avg);
    var /= (ITER_MEAS - 1);
    std::printf("[global-only] atlag: %.3f ms, szoras: %.3f ms\n", avg, std::sqrt(var));

    // Hasonló mérés a constant_scale és shared_reduce esetén
    // A local_penalty kernel mérésénél a kMax legyen pl. 64.

    CUDA_CHECK(cudaFree(d_x));
    CUDA_CHECK(cudaFree(d_y));
    CUDA_CHECK(cudaFree(d_sum));
    return 0;
}

A mérésnél az első iterációt a warm-up után a mérésből kihagytuk, a maradékból átlagot és szórást számolunk. A constant_scale-hez hasonló mérési ciklus kell. A shared_reduce kimeneti tömbje a blokkonkénti összeg, így a global írás forgalom kisebb. A local_penalty esetén a kMax értékét a híváskor adjuk meg, például 64.

  • Bemenet: N = 1<<22 float, BLOCK = 256, GRID = 16384.

Ez a konfiguráció a mérési napló fejlécébe tartozik.

7.4.14 Mérési napló (várt és mért elkülönítve)

A laborátadandó egy olyan táblázat, amelyben a várt tendencia oszlop a memóriatér-döntési érvelésből következik, a mért oszlop pedig a saját futásból származik. Az alábbi táblázat a várt tendenciákat és a mérési mezőket mutatja. A mért értékek a könyv szövegében nem ellenőrzött futásból származnak, ezért a labor során kell kitölteni.

7.4.15 A memóriatér-döntési táblázat kitöltése

A labor végső eredménye egy memóriatér-döntési táblázat, amely a kerneltervezéshez használható. A fenti összefoglaló táblázatot a mérési eredményekkel pontosítjuk. A laborátadandó a következő formátumban készülhet:

Döntési kérdés Válasz Választott memóriatér Indoklás
Az adat mérete nagy (>1 MB)? Igen Global Shared nem elég nagy
Több block is használja? Igen Global Scope megköveteli
Csak egy blockon belül használt? Igen Shared Alacsony késleltetés
Ugyanazt az értéket olvassa minden szál? Igen Constant Broadcast
Dinamikus indexelés privát tömbre? Nem Regiszter Local elkerülése
Írni kell a host felől? Igen Global Constant read-only

A laborban a hallgató ezt a táblázatot a saját kernelére is el kell tudja készíteni, és a mérési naplóval igazolni a választást.

7.4.16 OpenCL párhuzam

Az OpenCL programozási modellben a CUDA-memóriatereknek megfelelnek a következő címterek:

CUDA OpenCL Scope
Regiszter Private Work-item
Local memory Private (fizikailag DRAM) Work-item
Shared memory Local Work-group
Constant memory Constant Work-group/global, read-only
Global memory Global Minden work-group

A döntési táblázat az OpenCL-ben is használható, de az OpenCL C kernelben a __private, __local, __constant és __global minősítőket használjuk. A memóriatér-választás szempontjai azonosak. Az OpenCL-ben a constant memória használata gyakran a kernel argumentumaira korlátozódik, és a shared memoryt a __local paraméter vagy __local változó adja. A döntéshez az OpenCL eszköz CL_DEVICE_LOCAL_MEM_SIZE és CL_DEVICE_MAX_CONSTANT_BUFFER_SIZE értékeit is figyelembe kell venni.

7.4.17 OpenCL példa

// Fordítási ellenőrzésre szánt OpenCL C példa.
// A laborban a CUDA kernellel párhuzamosan csak akkor futtassuk,
// ha OpenCL eszköz elérhető és az izolált környezet engedi.
kernel void scale_shared(global const float* x,
                         global float* block_sum,
                         local float* sdata,
                         constant float scale,
                         constant float offset,
                         int n)
{
    size_t gid = get_global_id(0);
    size_t lid = get_local_id(0);
    float v = (gid < n) ? x[gid] : 0.0f;
    v = mad(v, scale, offset);
    sdata[lid] = v;
    barrier(CLK_LOCAL_MEM_FENCE);
    for (size_t stride = get_local_size(0) / 2; stride > 0; stride >>= 1) {
        if (lid < stride) sdata[lid] += sdata[lid + stride];
        barrier(CLK_LOCAL_MEM_FENCE);
    }
    if (lid == 0) block_sum[get_group_id(0)] = sdata[0];
}

Itt a constant float scale és constant float offset a CUDA constant memória analógiája, a local float* sdata pedig a shared memory.

7.4.18 JAX/XLA megfontolások

A JAX-ben a felhasználó általában nem választ közvetlenül memóriateret; az XLA fordító dönt arról, hogy egy adott műveletet hogyan valósít meg GPU-n vagy TPU-n. A memóriatér-döntés azonban itt is fontos, csak a füst alatt. A JAX-kódban a jax.numpy vagy jax.lax hívásokból XLA HLO gráf lesz, amelyből a háttér a hardvernek megfelelő kernel(eke)t generál. A shared memory és registers allokációt a kernelgenerátor végzi.

A döntési táblázat JAX szempontból így módosul:

  • A global memoryt a JAX pufferek és a device-okon tárolt tömbök képviselik.
  • A constant memóriát a fordító a warpenként uniform konstansokra használhatja, de explicit CUDA-konstans nincs a JAX-ben.
  • A shared memoryt az XLA az olyan redukciókhoz, konvolúciókhoz használja, ahol a blockon belüli újrafelhasználás nagy.
  • A local memoryt a JAX közvetlenül nem teszi láthatóvá, de a rosszul optimalizált kernel okozhat regiszter spillt, amit a profilban local tranzakcióként látunk.

Egy JAX-példa, amely ugyanazt a skálázást és blokkredukciót XLA-ra bízza:

# JAX példa, illusztráció; valós TPU/GPU futtatáshoz izolált környezet kell.
# A memóriatér-választást itt az XLA végzi.
import jax
import jax.numpy as jnp

key = jax.random.key(0)
x = jax.random.normal(key, (1 << 22,), dtype=jnp.float32)

@jax.jit
def scale_and_sum(x):
    # A scale és offset XLA-konstansként beolvadhat,
    # a redukció során a back-end shared/constant trafikot optimalizál.
    return jnp.sum(0.5 * x + 1.0)

result = scale_and_sum(x)
print(result.block_until_ready())

A JAX-ben a memóriatér-döntést a kernelprofilban az XLA HLO alapján követhetjük nyomon, de a felhasználói kód szintjén a „scope” és a „latency” nem közvetlenül vezérelhető. A labor döntési táblázatában ezért a JAX sorban azt tüntetjük fel, hogy a memóriatér-választást a fordító garantálja, a mérési naplóban pedig az XLA back-end profilját adjuk meg.

7.4.19 Tipikus hibák és helyes választások

A memóriatér-kiválasztás során gyakori hibák a következők.

Hiba 1: minden megosztott adatot shared memoryba teszünk. A shared memory kapacitása korlátozott, és használata csökkenti az occupancy-t. Ha egy adatot a blockon belül csak egyszer olvasunk, a global memoryból való coalesced olvasás gyakran jobb, mint a shared-be másolás.

Hiba 2: constant memoryba teszünk véletlenszerűen indexelt tömböt. A constant memória akkor gyors, ha egy warp minden szála ugyanazt a címet olvassa. Ha a szálak különböző elemeket kérnek, a hozzáférés sorosodik, és a teljesítmény összeomlik. Ilyen adatot global vagy texture memóriába tegyünk.

Hiba 3: a local memóriát „helyi gyorsítótárnak” képzeljük. A local memória a global memóriában lakik. A local_penalty kernel megmutatja, hogy a privát tömbök rossz indexelése miatt a DRAM-forgalom megnő. A megoldás az, hogy a tömböt regiszterekben tartsuk, vagy ha a méret nagy, shared memoryt használjunk.

Hiba 4: a texture memóriát automatikusan gyorsabbnak gondoljuk. A textúra memória előnye a speciális címzési és szűrési módokban, valamint a 2D/3D cache-optimalizációban van, nem pedig egy minden esetben nagyobb nyers sávszélességben. Ha nincs interpoláció vagy speciális határkezelés, a global memory read-only cache-sel gyakran ugyanolyan jó.

Hiba 5: nem mérjük a memóriaprofil sávszélességét. A kernel lehet felszínesen „gyors”, de a globális memóriatranzakciók száma magas. A Nsight Compute profilban a sector/request mutatók megmutatják, hogy a döntés hatékony-e. A laborban minden kernelváltozathoz rögzíteni kell a global load/store szektorok számát.

7.4.20 A döntési folyamat összefoglalása

A memóriatér-kiválasztás ismételhető lépései:

  1. Az adat életciklusának felmérése: Milyen hosszan él, hány szál látja, kell-e írni?
  2. A hozzáférési minta elemzése: Coalesced, broadcast, strided, véletlen, 2D-s?
  3. A méret ellenőrzése: Elfér-e shared/constant memóriában? Mekkora a local memória spill?
  4. A döntési táblázat alkalmazása: Válasszunk a fenti táblázat soraiból.
  5. Költség-haszon elemzés: A választás javítja-e a sávszélességet, csökkenti-e a késleltetést, vagy csak az occupancy-t rontja?
  6. Mérés és profil: A választott kialakítást futtassuk le, mérjük a memóriaprofil-mutatókat, és hasonlítsuk a várt tendenciához.
  7. Iteráció: Ha a profil nem igazolja a várt hatást, vizsgáljuk meg a bank konfliktusokat, a coalescinget vagy a cache találatokat.

A memóriaterek közötti döntés tehát nem egyetlen szabály, hanem egy keret, amelyet mérésekkel kell validálni. A laborban elkészített táblázat a későbbi fejezetekben is alapul szolgál: a shared memory tiling, a coalescing és a cache-optimalizálás mind visszavezethető erre a döntési folyamatra.

7.4.21 Önellenőrző kérdés

Egy kernelben egy 1024 elemű súlytáblázatot használunk. A súlyokat minden szál olvassa, de a szálak indexe a táblázatban különböző: az 1. szál a 0. elemet, a 2. szál az 1. elemet, és így tovább. A súlyok nem változnak a kernel futása alatt. Melyik memóriateret választanád?

Válasz: A constant memória rossz választás lenne, mert a hozzáférés nem warp-uniform: a szálak különböző címeket olvasnak, ami sorosodáshoz vezet. Ha a táblázat kicsi, érdemes a shared memoryba tölteni a block elején, mert a blokk szintű újrafelhasználás kihasználható. Ha a táblázat nagyobb és a hozzáférés read-only, a global memory vagy a texture memory lehet jó választás. A döntési táblázatban a constant sorát tehát csak broadcast hozzáférésnél használjuk.
