22.4 Könyvtárak integrálása

A CUDA-könyvtárak akkor válnak igazán értékessé, amikor nem izolált fekete dobozként hívjuk őket, hanem a saját kerneljeinkkel, streamekkel és memóriakezelésünkkel összehangoltan dolgoznak. Ez a fejezet azt a mérnöki réteget tárgyalja, amely a könyvtári hívások és a saját kód közötti határfelületen húzódik. Három pillért járunk körbe: az API-interopot, a stream- és memóriamenedzsmentet, valamint a verzió- és ABI-kérdéseket. A fejezet végén egy integrációs és buildtervet adunk, amelyet a későbbi, CUTLASS- és tensor core-os fejezetek is felhasználnak.

22.4.1 1. A könyvtárak és a saját kód együttműködése

A CUDA-ökoszisztéma könyvtárai két nagy csoportra oszthatók abból a szempontból, hogyan illeszthetők a saját kódba. A handle-alapú könyvtárak – mint a cuBLAS, cuSPARSE, cuFFT és cuRAND – egy kontextusobjektumot (például cublasHandle_t, cusparseHandle_t) használnak, amely tárolja a művelethez szükséges állapotot: a streamet, az esetleges pointer mode-ot, a matematikai módot és a belső munkaterületre vonatkozó beállításokat. A header-only template könyvtárak – a Thrust és a CUB – ezzel szemben fordítási időben illeszkednek a kódba, és gyakran közvetlenül a kernelben vagy a kernel és a host közötti vékony rétegben használjuk őket.

A két csoport együttműködése a saját kóddal más természetű, ezért külön érdemes megvizsgálni.

22.4.2 1.1. Handle-alapú könyvtárak és a saját kernel

A handle-alapú könyvtárak általában host oldali API-t kínálnak: a hívást a CPU indítja, a tényleges munka a GPU-n, aszinkron módon történik. A saját kernelünk és a könyvtári művelet közötti adatcsere device pointereken keresztül valósul meg. A könyvtárak cudaMalloc-kal vagy azzal kompatibilis módon lefoglalt eszközmemóriát várnak, ezért a saját kernelünk által feltöltött puffert közvetlenül átadhatjuk a könyvtárnak, és viszont.

Tekintsünk egy tipikus mintát: a saját kernel feltölt egy mátrixot, majd a cuBLAS cublasSgemm függvénye mátrixszorzást hajt végre rajta. A kód vázlata a következő lehet:

// CUDA C++17, nvcc 12.4, -arch=sm_86
#include <cuda_runtime.h>
#include <cublas_v2.h>
#include <cstdio>

#define CHECK_CUDA(call)                                              \
    do {                                                              \
        cudaError_t err = (call);                                     \
        if (err != cudaSuccess) {                                     \
            std::fprintf(stderr, "CUDA error at %s:%d: %s\n",         \
                         __FILE__, __LINE__, cudaGetErrorString(err)); \
            std::exit(EXIT_FAILURE);                                  \
        }                                                             \
    } while (0)

#define CHECK_CUBLAS(call)                                            \
    do {                                                              \
        cublasStatus_t st = (call);                                   \
        if (st != CUBLAS_STATUS_SUCCESS) {                            \
            std::fprintf(stderr, "cuBLAS error at %s:%d: %d\n",       \
                         __FILE__, __LINE__, static_cast<int>(st));   \
            std::exit(EXIT_FAILURE);                                  \
        }                                                             \
    } while (0)

__global__ void fillMatrixKernel(float* A, int n, float val) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < n * n) {
        A[idx] = val;
    }
}

int main() {
    constexpr int n = 1024;
    constexpr size_t bytes = sizeof(float) * n * n;

    cublasHandle_t handle;
    CHECK_CUBLAS(cublasCreate(&handle));

    float *d_A, *d_B, *d_C;
    CHECK_CUDA(cudaMalloc(&d_A, bytes));
    CHECK_CUDA(cudaMalloc(&d_B, bytes));
    CHECK_CUDA(cudaMalloc(&d_C, bytes));

    // Saját kernel futtatása a default streamen
    int threads = 256;
    int blocks = (n * n + threads - 1) / threads;
    fillMatrixKernel<<<blocks, threads>>>(d_A, n, 1.0f);
    fillMatrixKernel<<<blocks, threads>>>(d_B, n, 2.0f);

    const float alpha = 1.0f;
    const float beta  = 0.0f;
    // cuBLAS hívás ugyanazon a streamen (a handle alapértelmezetten a default stream)
    CHECK_CUBLAS(cublasSgemm(handle, CUBLAS_OP_N, CUBLAS_OP_N,
                             n, n, n, &alpha, d_A, n, d_B, n, &beta, d_C, n));

    CHECK_CUDA(cudaDeviceSynchronize());
    // ...
}

Ebben a példában a saját kernel és a cuBLAS hívás között nincs explicit szinkronizáció, mert mindkettő ugyanazon a streamen fut: a kernel befejezése után a cuBLAS művelet következik. Ez a minta csak akkor működik, ha a cuBLAS handle streamje megegyezik a kernel indítási streamjével – itt mindkettő a default stream. A gyakorlatban azonban érdemes saját streameket használni, és a handle-hez rendelni azokat, ahogy a 2. szakaszban látni fogjuk.

A saját kernel és a könyvtári hívás közötti hibahatár szintén fontos. A könyvtárak a saját hibakódjaikat adják vissza (cublasStatus_t, cusparseStatus_t stb.), míg a kernelhibákat cudaGetLastError-rel és cudaDeviceSynchronize-szal kérdezhetjük le. A két réteget egyaránt ellenőrizni kell, mert egy hibás könyvtári hívás után a GPU állapota bizonytalan lehet. A fenti kód CHECK_CUDA és CHECK_CUBLAS makrói ezt a célt szolgálják.

22.4.3 1.2. Header-only könyvtárak: Thrust és CUB

A Thrust és a CUB nem igényel külön linkelést, mert a sablonjaik a fejlécekben élnek. A Thrust konténerei (thrust::device_vector) és algoritmusai a device pointerekkel is együttműködnek. Ha a saját kernelünk egy float* mutatót tölt fel, akkor azt thrust::device_ptr<float>-ként becsomagolva közvetlenül átadhatjuk egy Thrust-algoritmusnak:

#include <thrust/device_ptr.h>
#include <thrust/reduce.h>

// d_C a korábbi cuBLAS kimenet
float sum = thrust::reduce(thrust::device_pointer_cast(d_C),
                           thrust::device_pointer_cast(d_C + n * n),
                           0.0f);

A thrust::device_pointer_cast nem végez másolást, csupán egy típusos burkolót hoz létre, így a saját kernel és a Thrust között nincs adatvesztés. Fordított irányban, ha egy Thrust konténer mögöttes nyers mutatójára van szükségünk, a thrust::raw_pointer_cast használható.

A CUB ezzel szemben elsősorban eszközoldali primitíveket biztosít: BlockReduce, BlockScan, WarpReduce és hasonlók, amelyeket a saját kernelünkön belül hívhatunk. Ez a legerősebb integrációs forma, mert a CUB kódja a kernel részeként fordul le, és nincs szükség külön memóriafoglalásra vagy streamkezelésre. Példa egy blokkszintű redukcióra:

#include <cub/cub.cuh>

__global__ void reduceBlockKernel(const float* input, float* output, int n) {
    // Minden blokk a saját szeletét redukálja
    typedef cub::BlockReduce<float, 256> BlockReduce;
    __shared__ typename BlockReduce::TempStorage temp_storage;

    int tid = threadIdx.x;
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    float val = (idx < n) ? input[idx] : 0.0f;

    float block_sum = BlockReduce(temp_storage).Sum(val);

    if (tid == 0) {
        output[blockIdx.x] = block_sum;
    }
}

A CUB itt teljesen a kernelbe ágyazódik, így a saját kód és a könyvtár közötti határ eltűnik: a CUB csupán egy jól optimalizált, újrahasznosítható építőelem. Ugyanakkor a CUB fejlécek verziója és a CUDA toolkit verziója közötti kompatibilitásra figyelni kell, amit a 3. szakasz tárgyal.

22.4.4 1.3. A könyvtárak és a saját kód közötti munkamegosztás

Az integráció során érdemes világosan elhatárolni, hogy melyik réteg mit végez. A saját kernel általában a feladat-specifikus elő- és utófeldolgozást végzi: adatgenerálás, formátumkonverzió, peremfeltételek, ritka mátrix összeállítása. A könyvtárak a nagy számítási magot szolgáltatják: GEMM, SpMV, FFT, random generálás, redukció, rendezés. A határfelületen a következő szabályokat érdemes betartani:

  • A device pointereket soha ne dereferáljuk a hoston; minden adatátadás a GPU memóriájában történjen.
  • A könyvtári hívások előtt és után a szükséges szinkronizációt explicit módon kezeljük streamekkel és eseményekkel.
  • A könyvtárak által igényelt munkaterületet (workspace) a hívás előtt le kell foglalni, és a méretét a könyvtár által szolgáltatott _bufferSize vagy _getWorkspaceSize függvénnyel kell lekérdezni.

A következő szakasz ezeket a stream- és memóriaszempontokat részletezi.

22.4.5 2. Stream és memória

A GPU-n futó műveletek sorrendjét a streamek határozzák meg. A könyvtárak alapértelmezés szerint a default streamen hajtódnak végre, de a legtöbb handle-alapú könyvtár lehetővé teszi, hogy egy adott streamhez kössük őket. Ez az integráció egyik legfontosabb lépése, mert csak így garantálható, hogy a saját kernel és a könyvtári hívás közötti sorrendiség explicit legyen, és kihasználhassuk az átfedést.

22.4.6 2.1. Stream hozzárendelése a könyvtárakhoz

A cuBLAS esetében a cublasSetStream függvénnyel rendelhetünk streamet a handle-hez:

cudaStream_t stream1, stream2;
CHECK_CUDA(cudaStreamCreate(&stream1));
CHECK_CUDA(cudaStreamCreate(&stream2));

cublasSetStream(handle, stream1);

Ezután minden cuBLAS hívás a stream1-en fut. Hasonló a helyzet a cuSPARSE-nál (cusparseSetStream), a cuFFT-nél (cufftSetStream) és a cuRAND-nál (curandSetStream). A saját kernelünket pedig a <<<..., stream1>>> szintaxissal indíthatjuk ugyanarra a streamre, így a sorrend garantált.

Fontos, hogy a stream hozzárendelése a handle-hez nem szinkronizálja a korábbi műveleteket; csupán a későbbi hívások streamjét állítja be. Ha egy handle-t több streamen akarunk használni, akkor vagy több handle-t hozunk létre, vagy minden hívás előtt átállítjuk a streamet – ez utóbbi azonban többletköltséggel járhat, és a párhuzamos végrehajtást is megnehezíti. Több stream esetén a legtisztább megoldás, ha minden streamhez külön handle tartozik.

22.4.7 2.2. Aszinkron végrehajtás és események

Ha a saját kernel és a könyvtári hívás különböző streameken fut, a köztük lévő függőséget eseményekkel kell kifejezni. Tegyük fel, hogy a saját kernel feltölt egy mátrixot a stream1-en, majd a cuBLAS a stream2-n fogja használni. Ekkor a stream2-t meg kell várakoztatni a kernel befejezésére:

cudaEvent_t event;
CHECK_CUDA(cudaEventCreate(&event));

// Kernel indítása stream1-en
fillMatrixKernel<<<blocks, threads, 0, stream1>>>(d_A, n, 1.0f);

// Esemény rögzítése stream1-en a kernel után
CHECK_CUDA(cudaEventRecord(event, stream1));

// stream2 várakoztatása az eseményre
CHECK_CUDA(cudaStreamWaitEvent(stream2, event, 0));

// cuBLAS hívás stream2-n (a handle streamje stream2)
cublasSetStream(handle, stream2);
CHECK_CUBLAS(cublasSgemm(handle, ...));

Az esemény rögzítése és a cudaStreamWaitEvent biztosítja, hogy a cuBLAS csak a kernel befejezése után induljon, annak ellenére, hogy a két művelet más streamen van. Ez a minta elengedhetetlen az átfedés maximalizálásához: míg a stream2 a cuBLAS-t futtatja, a stream1 már a következő kernelre léphet.

A könyvtárak általában aszinkron módon működnek: a hívás visszatérése nem jelenti a művelet befejezését. Ezért a mérés előtt mindig szinkronizálni kell a streamet vagy az eszközt. A cudaDeviceSynchronize a legegyszerűbb, de minden streamet várakoztat; ha csak egy adott streamre vagyunk kíváncsiak, használjunk cudaStreamSynchronize-t.

22.4.8 2.3. Memóriaallokáció és workspace

A könyvtárak gyakran igényelnek ideiglenes munkaterületet. A cuSPARSE SpMV például a cusparseSpMV_bufferSize hívással kéri le a szükséges bájtok számát, majd a cusparseSpMV függvénynek át kell adni egy ekkora puffert:

cusparseSpMatDescr_t matA;
cusparseDnVecDescr_t vecX, vecY;
// ... leírók létrehozása ...

size_t bufferSize = 0;
CHECK_CUSPARSE(cusparseSpMV_bufferSize(handle, CUSPARSE_OPERATION_NON_TRANSPOSE,
                                       &alpha, matA, vecX, &beta, vecY,
                                       CUDA_R_32F, CUSPARSE_SPMV_ALG_DEFAULT,
                                       &bufferSize));

void* dBuffer = nullptr;
CHECK_CUDA(cudaMalloc(&dBuffer, bufferSize));

CHECK_CUSPARSE(cusparseSpMV(handle, CUSPARSE_OPERATION_NON_TRANSPOSE,
                            &alpha, matA, vecX, &beta, vecY,
                            CUDA_R_32F, CUSPARSE_SPMV_ALG_DEFAULT, dBuffer));

A workspace mérete függ az algoritmustól és az adatméretektől, ezért mindig a _bufferSize függvénnyel kell lekérdezni. A cuFFT hasonlóan cufftMakePlanMany és cufftEstimate* függvényekkel, vagy a cufftSetWorkArea segítségével kezeli a munkaterületet. A cuBLAS újabb verziói (cuBLASLt) szintén workspace-t igényelhetnek.

A memóriaallokáció módja is integrációs kérdés. A hagyományos cudaMalloc mellett a CUDA 11.2 óta elérhető cudaMallocAsync streamhez kötött memóriát biztosít, amely a stream szinkronizációjával automatikusan felszabadul. Ez csökkentheti az allokációs költséget, és jól illeszkedik a könyvtárak streamkezeléséhez. A managed memory (cudaMallocManaged) használata esetén a könyvtárak is képesek a migrációt kezelni, de a teljesítmény érdekében cudaMemPrefetchAsync-szel explicit módon a megfelelő eszközre kell húzni az adatot.

Fontos megjegyezni, hogy a könyvtárak általában nem támogatják a memóriaaliasolást: a bemeneti és kimeneti pufferek nem fedhetik át egymást, hacsak a dokumentáció másként nem rendelkezik. A saját kernelünk és a könyvtári hívás közötti adatátadásnál ezért mindig külön puffereket használjunk, és a szükséges másolásokat a GPU-n belül, például cudaMemcpyAsync-vel végezzük.

22.4.9 2.4. Stream és memória a gyakorlatban

A következő vázlat egy olyan integrációs mintát mutat, amelyben a saját kernel, a cuBLAS, a cuSPARSE és a CUB együtt dolgozik két streamen, eseményekkel szinkronizálva:

// Feltételezve, hogy a handle-ek és a streamek létre vannak hozva
cublasSetStream(cublasHandle, stream1);
cusparseSetStream(cusparseHandle, stream1);

// 1. Saját kernel feltölti az A mátrixot a stream1-en
fillMatrixKernel<<<blocksA, threads, 0, stream1>>>(d_A, n, 1.0f);

// 2. cuBLAS GEMM a stream1-en
cublasSgemm(cublasHandle, CUBLAS_OP_N, CUBLAS_OP_N, n, n, n,
            &alpha, d_A, n, d_B, n, &beta, d_C, n);

// 3. Esemény rögzítése a stream1 végére
cudaEventRecord(event, stream1);

// 4. stream2 várakoztatása, majd cuSPARSE SpMV futtatása
cudaStreamWaitEvent(stream2, event, 0);
cusparseSetStream(cusparseHandle, stream2);
cusparseSpMV(cusparseHandle, CUSPARSE_OPERATION_NON_TRANSPOSE,
             &alpha, matA, vecX, &beta, vecY,
             CUDA_R_32F, CUSPARSE_SPMV_ALG_DEFAULT, dBuffer);

// 5. CUB DeviceReduce az összegzéshez (host oldali hívás, stream2-n)
cub::DeviceReduce::Sum(d_temp_storage, temp_storage_bytes, d_Y, d_sum, n,
                       stream2);

Itt a CUB eszközoldali redukciója host oldali API-val, de stream paraméterrel történik, így a stream2-höz kötődik. A CUB DeviceReduce szintén workspace-t igényel, amelynek méretét a cub::DeviceReduce::Sum első hívása adja meg nullptr pufferrel.

22.4.10 3. Verzió és ABI

A könyvtárak integrálásakor a verziók és az ABI-kompatibilitás kezelése kritikus, mert a hibás kombináció futásidejű hibákhoz, nem determinisztikus viselkedéshez vagy akár eszközleálláshoz vezethet. Ez a szakasz a leggyakoribb buktatókat és a buildtervezéshez szükséges alapelveket foglalja össze.

22.4.11 3.1. CUDA toolkit, driver és compute capability

A CUDA programok futtatásához három verziót kell megkülönböztetni:

  • CUDA toolkit verzió (például 12.4): ez határozza meg a fejléceket, a fordítót (nvcc) és a könyvtárak binárisait.
  • Driver verzió (például 550.54.14): a kernel betöltéséhez és a futáshoz szükséges; a drivernek kompatibilisnek kell lennie a toolkit által generált kóddal. A CUDA kisebb verziói általában visszafelé kompatibilisek a driverrel, de a nagyobb verziók (például CUDA 13) újabb drivert igényelhetnek.
  • Compute capability (például 8.6 az RTX 3080 esetén): a hardver architektúráját jelöli, és a -arch=sm_86 kapcsolóval kell megadni a fordítás során. A compute capability határozza meg, mely utasítások és szolgáltatások érhetők el (például tensor core-ok, async copy).

A build során mindhárom verziót rögzíteni kell, és a laborban ezt meg is tesszük. A nvcc a -arch kapcsolóval a megfelelő SASS vagy PTX kódot generálja; ha a futtató GPU compute capability-je nem egyezik, a CUDA runtime JIT-fordítással próbálhatja a PTX-et adaptálni, de ez nem mindig lehetséges, és teljesítménycsökkenéssel járhat.

22.4.12 3.2. Könyvtári verziók és ABI

A cuBLAS, cuSPARSE, cuFFT és cuRAND a CUDA toolkit részei, és verziójuk általában a toolkit verzióját követi. Például a CUDA 12.4 cuBLAS 12.4-et, cuSPARSE 12.4-et szállít. A fejlécekben definiált API-k és a dinamikus könyvtárak (.so Linuxon, .dll Windowson) közötti ABI-kompatibilitás a következőképpen alakul:

  • A minor verziófrissítések (pl. 12.4 → 12.5) általában ABI-kompatibilisek: a régebbi binárisok futnak az újabb könyvtárral, és fordítva is, feltéve, hogy a driver támogatja. A CUDA dokumentáció ezt a compatibility fejezetben tárgyalja; mindig ellenőrizni kell az aktuális táblázatot.
  • A major verzióváltások (pl. CUDA 11 → 12) gyakran API-változásokat is hoznak, és előfordulhat, hogy a forráskódot módosítani kell. Az ABI ilyenkor nem garantált.
  • A header-only könyvtárak (Thrust, CUB) nem rendelkeznek külön bináris ABI-val, de a fejlécek verziója és a CUDA toolkit verziója közötti kompatibilitás számít. Ha például egy külső forrásból származó, újabb CUB fejlécet használunk egy régebbi toolkitkel, az inkompatibilis lehet a nvcc belső fejléceivel. Ezért ajánlott a toolkithez mellékelt CUB-ot használni.

A gyakorlatban a legbiztonságosabb stratégia, ha a könyvtárakat a CUDA toolkitkel együtt telepítjük, és a build során a toolkit include és lib könyvtárait használjuk. A CMake FindCUDAToolkit modulja automatikusan felismeri a toolkit verzióját és a könyvtárakat.

22.4.13 3.3. Statikus és dinamikus linkelés

A CUDA könyvtárak dinamikus és statikus változatban is elérhetők. A dinamikus linkelés (alapértelmezett) a következőképpen néz ki:

nvcc -std=c++17 -arch=sm_86 -o app app.cu -lcublas -lcusparse -lcufft -lcurand

Ez kisebb binárist eredményez, de a futtatógépen a megfelelő CUDA runtime könyvtáraknak jelen kell lenniük. A statikus linkelés:

nvcc -std=c++17 -arch=sm_86 -o app app.cu \
    -lcublas_static -lcusparse_static -lcufft_static -lcurand_static \
    -lcudart_static

A statikus változat nagyobb binárist hoz létre, de csökkenti a futásidejű függőségeket. A statikus linkelésnél figyelni kell a könyvtárak sorrendjére és a -lcudart_static jelenlétére, különben feloldatlan szimbólumok miatt hibát kapunk. A gyakorlatban a dinamikus linkelés a kényelmesebb, és a CUDA runtime általában elérhető a GPU-s környezetekben.

A cuBLASLt külön könyvtár (-lcublasLt), amely a cuBLAS „lightweight” API-ját tartalmazza. A cuSPARSE, cuFFT és cuRAND hasonlóan külön könyvtárak. Minden használt könyvtárat explicit módon linkelni kell, mert a nvcc nem automatikusan húzza be őket.

22.4.14 3.4. Verzió-ellenőrzés futásidőben

A könyvtárak általában biztosítanak verziólekérdező függvényeket. Például:

int cublasVersion = 0;
cublasGetVersion(handle, &cublasVersion);
printf("cuBLAS version: %d\n", cublasVersion);

int cusparseVersion = 0;
cusparseGetVersion(handle, &cusparseVersion);
printf("cuSPARSE version: %d\n", cusparseVersion);

A Thrust és a CUB verziója fordítási időben a THRUST_VERSION és a CUB_VERSION makrókból érhető el. Ezeket a számokat érdemes naplózni a mérési környezet rögzítésekor, mert a teljesítmény és a viselkedés verziófüggő lehet.

A buildtervnek ezért a következőket kell tartalmaznia:

  • CUDA toolkit verzió (pl. 12.4)
  • Driver verzió (pl. 550.54.14)
  • Compute capability (pl. 8.6)
  • A használt könyvtárak és verzióik (cuBLAS, cuSPARSE, cuFFT, cuRAND, Thrust, CUB)
  • A linkelés módja (dinamikus/statikus)
  • A fordítóparancs és a környezeti változók (pl. CUDA_HOME, LD_LIBRARY_PATH)

22.4.15 4. Labor: integrációs és buildterv

A következő labor egy olyan kis alkalmazást mutat be, amely a fenti elveket gyakorlatba ülteti. A feladat egy integrációs és buildterv elkészítése, amely saját kernelt, cuBLAS-t, cuSPARSE-t, Thrust/CUB-ot és streameket használ. A labor nem helyettesíti a teljes körű benchmarkot, de alkalmas az együttműködés ellenőrzésére és a tipikus hibák felismerésére.

22.4.16 4.1. Laborcél és környezet

Cél: Egy olyan CUDA C++17 program írása, amely: 1. Saját kernelrel feltölt egy 1024×1024-es mátrixot és egy 1024 hosszú vektort. 2. cuBLAS cublasSgemm segítségével mátrixszorzást végez. 3. cuSPARSE cusparseSpMV segítségével egy ritka mátrix-vektor szorzást hajt végre. 4. CUB DeviceReduce segítségével kiszámolja az eredményvektor összegét. 5. A műveleteket két streamen futtatja, eseményekkel szinkronizálva. 6. A hibákat minden API-hívásnál ellenőrzi, és a verziókat naplózza.

Rögzített környezet (helyőrző – a laborban cseréld a sajátodra): - GPU: NVIDIA RTX 3080 (compute capability 8.6) - Driver: 550.54.14 - CUDA toolkit: 12.4 - nvcc: 12.4 - cuBLAS: 12.4 - cuSPARSE: 12.4 - Thrust/CUB: a toolkit része (CUB 2.1.0, Thrust 2.1.0) - OS: Ubuntu 22.04 LTS - Fordítás: dinamikus linkelés

22.4.17 4.2. A program váza

Az alábbi kód a teljes integrációs mintát tartalmazza. A kommentek jelzik a kulcslépéseket, és a hibamakrók biztosítják az ellenőrzést. A kód fordítható, de a labor során a mérési részt a valós környezethez kell igazítani.

// lab_integr.cu – CUDA C++17, nvcc 12.4, -arch=sm_86
// Helyőrző környezet: RTX 3080, driver 550.54.14, CUDA 12.4
#include <cuda_runtime.h>
#include <cublas_v2.h>
#include <cusparse.h>
#include <cub/cub.cuh>
#include <thrust/version.h>
#include <cstdio>
#include <cstdlib>
#include <cmath>

#define CHECK_CUDA(call)                                              \
    do {                                                              \
        cudaError_t err = (call);                                     \
        if (err != cudaSuccess) {                                     \
            std::fprintf(stderr, "CUDA error at %s:%d: %s\n",         \
                         __FILE__, __LINE__, cudaGetErrorString(err)); \
            std::exit(EXIT_FAILURE);                                  \
        }                                                             \
    } while (0)

#define CHECK_CUBLAS(call)                                            \
    do {                                                              \
        cublasStatus_t st = (call);                                   \
        if (st != CUBLAS_STATUS_SUCCESS) {                            \
            std::fprintf(stderr, "cuBLAS error at %s:%d: %d\n",       \
                         __FILE__, __LINE__, static_cast<int>(st));   \
            std::exit(EXIT_FAILURE);                                  \
        }                                                             \
    } while (0)

#define CHECK_CUSPARSE(call)                                          \
    do {                                                              \
        cusparseStatus_t st = (call);                                 \
        if (st != CUSPARSE_STATUS_SUCCESS) {                          \
            std::fprintf(stderr, "cuSPARSE error at %s:%d: %d\n",     \
                         __FILE__, __LINE__, static_cast<int>(st));   \
            std::exit(EXIT_FAILURE);                                  \
        }                                                             \
    } while (0)

__global__ void fillMatrixKernel(float* A, int n, float val) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < n * n) A[idx] = val;
}

__global__ void fillVectorKernel(float* x, int n, float val) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < n) x[idx] = val;
}

int main() {
    constexpr int n = 1024;            // mátrixméret
    constexpr int nnz = 1024;          // ritka mátrix nemnulla elemei
    constexpr size_t matBytes = sizeof(float) * n * n;
    constexpr size_t vecBytes = sizeof(float) * n;

    // Verziók kiírása
    int cublasVer = 0, cusparseVer = 0;
    cublasHandle_t cublasHandle;
    cusparseHandle_t cusparseHandle;
    CHECK_CUBLAS(cublasCreate(&cublasHandle));
    CHECK_CUSPARSE(cusparseCreate(&cusparseHandle));
    CHECK_CUBLAS(cublasGetVersion(cublasHandle, &cublasVer));
    CHECK_CUSPARSE(cusparseGetVersion(cusparseHandle, &cusparseVer));
    std::printf("cuBLAS version: %d\n", cublasVer);
    std::printf("cuSPARSE version: %d\n", cusparseVer);
    std::printf("Thrust version: %d\n", THRUST_VERSION);
    std::printf("CUB version: %d\n", CUB_VERSION);

    // Streamek létrehozása
    cudaStream_t stream1, stream2;
    CHECK_CUDA(cudaStreamCreate(&stream1));
    CHECK_CUDA(cudaStreamCreate(&stream2));

    // Handle-ek streamhez kötése
    CHECK_CUBLAS(cublasSetStream(cublasHandle, stream1));
    CHECK_CUSPARSE(cusparseSetStream(cusparseHandle, stream2));

    // Eszközmemória foglalás
    float *d_A, *d_B, *d_C, *d_x, *d_y, *d_sum;
    CHECK_CUDA(cudaMalloc(&d_A, matBytes));
    CHECK_CUDA(cudaMalloc(&d_B, matBytes));
    CHECK_CUDA(cudaMalloc(&d_C, matBytes));
    CHECK_CUDA(cudaMalloc(&d_x, vecBytes));
    CHECK_CUDA(cudaMalloc(&d_y, vecBytes));
    CHECK_CUDA(cudaMalloc(&d_sum, sizeof(float)));

    // Saját kernelek indítása a stream1-en
    int threads = 256;
    int blocksMat = (n * n + threads - 1) / threads;
    int blocksVec = (n + threads - 1) / threads;
    fillMatrixKernel<<<blocksMat, threads, 0, stream1>>>(d_A, n, 1.0f);
    fillMatrixKernel<<<blocksMat, threads, 0, stream1>>>(d_B, n, 2.0f);
    fillVectorKernel<<<blocksVec, threads, 0, stream1>>>(d_x, n, 3.0f);

    // cuBLAS GEMM a stream1-en
    const float alpha = 1.0f;
    const float beta  = 0.0f;
    CHECK_CUBLAS(cublasSgemm(cublasHandle, CUBLAS_OP_N, CUBLAS_OP_N,
                             n, n, n, &alpha, d_A, n, d_B, n, &beta, d_C, n));

    // Esemény rögzítése a stream1 végére
    cudaEvent_t event;
    CHECK_CUDA(cudaEventCreate(&event));
    CHECK_CUDA(cudaEventRecord(event, stream1));

    // stream2 várakoztatása, majd ritka mátrix-vektor szorzás
    CHECK_CUDA(cudaStreamWaitEvent(stream2, event, 0));

    // Ritka mátrix létrehozása CSR formátumban (diagonális minta)
    int* h_csrOffsets = new int[n + 1];
    int* h_csrColumns = new int[nnz];
    float* h_csrValues = new float[nnz];
    for (int i = 0; i < n + 1; ++i) h_csrOffsets[i] = i;
    for (int i = 0; i < nnz; ++i) {
        h_csrColumns[i] = i;
        h_csrValues[i] = 1.0f;
    }

    int *d_csrOffsets, *d_csrColumns;
    float *d_csrValues;
    CHECK_CUDA(cudaMalloc(&d_csrOffsets, sizeof(int) * (n + 1)));
    CHECK_CUDA(cudaMalloc(&d_csrColumns, sizeof(int) * nnz));
    CHECK_CUDA(cudaMalloc(&d_csrValues, sizeof(float) * nnz));
    CHECK_CUDA(cudaMemcpyAsync(d_csrOffsets, h_csrOffsets, sizeof(int) * (n + 1),
                               cudaMemcpyHostToDevice, stream2));
    CHECK_CUDA(cudaMemcpyAsync(d_csrColumns, h_csrColumns, sizeof(int) * nnz,
                               cudaMemcpyHostToDevice, stream2));
    CHECK_CUDA(cudaMemcpyAsync(d_csrValues, h_csrValues, sizeof(float) * nnz,
                               cudaMemcpyHostToDevice, stream2));

    // cuSPARSE leírók
    cusparseSpMatDescr_t matA;
    cusparseDnVecDescr_t vecX, vecY;
    CHECK_CUSPARSE(cusparseCreateCsr(&matA, n, n, nnz,
                                     d_csrOffsets, d_csrColumns, d_csrValues,
                                     CUSPARSE_INDEX_32I, CUSPARSE_INDEX_32I,
                                     CUSPARSE_INDEX_BASE_ZERO, CUDA_R_32F));
    CHECK_CUSPARSE(cusparseCreateDnVec(&vecX, n, d_x, CUDA_R_32F));
    CHECK_CUSPARSE(cusparseCreateDnVec(&vecY, n, d_y, CUDA_R_32F));

    // Workspace méret lekérése
    size_t bufferSize = 0;
    CHECK_CUSPARSE(cusparseSpMV_bufferSize(cusparseHandle,
                                           CUSPARSE_OPERATION_NON_TRANSPOSE,
                                           &alpha, matA, vecX, &beta, vecY,
                                           CUDA_R_32F, CUSPARSE_SPMV_ALG_DEFAULT,
                                           &bufferSize));
    void* dBuffer = nullptr;
    CHECK_CUDA(cudaMalloc(&dBuffer, bufferSize));

    // SpMV végrehajtása stream2-n
    CHECK_CUSPARSE(cusparseSpMV(cusparseHandle,
                                CUSPARSE_OPERATION_NON_TRANSPOSE,
                                &alpha, matA, vecX, &beta, vecY,
                                CUDA_R_32F, CUSPARSE_SPMV_ALG_DEFAULT, dBuffer));

    // CUB DeviceReduce az összeg kiszámításához stream2-n
    void* d_temp_storage = nullptr;
    size_t temp_storage_bytes = 0;
    cub::DeviceReduce::Sum(d_temp_storage, temp_storage_bytes, d_y, d_sum, n, stream2);
    CHECK_CUDA(cudaMalloc(&d_temp_storage, temp_storage_bytes));
    cub::DeviceReduce::Sum(d_temp_storage, temp_storage_bytes, d_y, d_sum, n, stream2);

    // Szinkronizáció
    CHECK_CUDA(cudaDeviceSynchronize());

    // Ellenőrzés: az összegnek 3 * 1024 = 3072-nek kell lennie
    float h_sum = 0.0f;
    CHECK_CUDA(cudaMemcpy(&h_sum, d_sum, sizeof(float), cudaMemcpyDeviceToHost));
    std::printf("Computed sum: %f, expected: %f\n", h_sum, 3.0f * n);

    // Tisztítás
    delete[] h_csrOffsets;
    delete[] h_csrColumns;
    delete[] h_csrValues;
    CHECK_CUDA(cudaFree(d_A)); CHECK_CUDA(cudaFree(d_B)); CHECK_CUDA(cudaFree(d_C));
    CHECK_CUDA(cudaFree(d_x)); CHECK_CUDA(cudaFree(d_y)); CHECK_CUDA(cudaFree(d_sum));
    CHECK_CUDA(cudaFree(d_csrOffsets)); CHECK_CUDA(cudaFree(d_csrColumns));
    CHECK_CUDA(cudaFree(d_csrValues)); CHECK_CUDA(cudaFree(dBuffer));
    CHECK_CUDA(cudaFree(d_temp_storage));
    CHECK_CUSPARSE(cusparseDestroySpMat(matA));
    CHECK_CUSPARSE(cusparseDestroyDnVec(vecX));
    CHECK_CUSPARSE(cusparseDestroyDnVec(vecY));
    CHECK_CUBLAS(cublasDestroy(cublasHandle));
    CHECK_CUSPARSE(cusparseDestroy(cusparseHandle));
    CHECK_CUDA(cudaEventDestroy(event));
    CHECK_CUDA(cudaStreamDestroy(stream1));
    CHECK_CUDA(cudaStreamDestroy(stream2));

    return 0;
}

22.4.19 4.4. Mérési terv és napló

A program jelenlegi formája funkcionális ellenőrzést végez, de teljesítménymérést nem. A mérési tervhez a következő lépéseket kell hozzáadni:

  1. A műveletek időméréséhez cudaEvent-eket kell rögzíteni a streameken a kernel- és könyvtári hívások körül.
  2. Warm-up futtatás: a teljes szekvenciát egyszer le kell futtatni a hideg indítási hatások kiküszöbölésére.
  3. Ezután legalább 10 ismétlést kell végezni, és az átlagot, szórást és percentiliseket kell számolni.
  4. A sávszélességet a tényleges adatmozgás alapján kell kiszámolni: a GEMM esetén 2 * n^3 * sizeof(float) bájt olvasás/írás, az SpMV esetén a CSR struktúra és a vektorok mérete.

  • A cublasSgemm 1024×1024-es mátrixokra egy RTX 3080-on (FP32) körülbelül 10-15 ms futásidőt ér el. Ez a korábbi mérések alapján nagyságrendi becslés; a pontos érték a laborban mérendő.
  • A cusparseSpMV diagonális CSR mátrixszal (1024 nemnulla elem) elhanyagolható futási időt igényel, mert a mátrix rendkívül ritka. A mérési naplóban ezért nagy szórás várható; a hangsúly a funkcionális helyességen van.

22.4.20 5. Gyakori hibák és megoldások

Az integráció során a következő hibák fordulnak elő leggyakrabban, és a megoldásuk is egyszerű, ha ismerjük őket:

  1. A handle streamje nincs beállítva. Ha a cuBLAS handle alapértelmezett streamen fut, miközben a saját kernel egy egyéni streamen, a sorrend nem garantált. Megoldás: minden handle-hez rendeljünk streamet a cublasSetStream-mel (vagy a megfelelő függvénnyel), és a kernelindításnál ugyanazt a streamet adjuk meg.

  2. Hiányzó vagy rossz méretű workspace. A cuSPARSE, cuFFT és a CUB DeviceReduce workspace-t igényel. Ha a puffert nem foglaljuk le, vagy a méretét nem a _bufferSize függvénnyel kérdezzük le, a hívás hibát ad vagy memóriatúllépést okozhat. Megoldás: először nullptr pufferrel kérdezzük le a szükséges méretet, majd foglaljuk le, és csak utána hívjuk a műveletet.

  3. Skalár pointer mode hibája. A cuBLAS cublasSetPointerMode segítségével lehet beállítani, hogy a skalár argumentumok (alpha, beta) host vagy device pointeren vannak-e. Ha a mód nem egyezik a tényleges átadással, a hívás CUBLAS_STATUS_INVALID_VALUE hibát ad. Megoldás: mindig állítsuk be a pointer mode-ot, és a skalárokat ennek megfelelően adjuk át.

  4. Szinkronizáció hiánya a mérés előtt. A könyvtári hívások aszinkronok; ha cudaDeviceSynchronize vagy cudaStreamSynchronize nélkül próbálunk eredményt olvasni, érvénytelen adatot kapunk. Megoldás: minden mérési pont előtt szinkronizáljuk a megfelelő streamet.

  5. CUB fejléc verzióeltérés. Ha a CUB fejléceket külön töltjük le, és azok verziója nem egyezik a CUDA toolkit belső fejléceivel, fordítási hibák léphetnek fel. Megoldás: a toolkithez mellékelt CUB-ot használjuk, és a CUB_VERSION makrót naplózzuk.

  6. Statikus linkelés könyvtári sorrendje. A statikus linkelésnél a könyvtárakat a függőségi sorrendben kell felsorolni, és a -lcudart_static-ot is meg kell adni. A nvcc általában kezeli a sorrendet, de ha kézzel adjuk meg a linkerlibrary-kat, ügyeljünk a -l kapcsolók sorrendjére.

  7. Compute capability eltérés. Ha a -arch nem egyezik a futtató GPU képességével, a program futhat, de a teljesítmény nem optimális, vagy a JIT-fordítás miatt lassabb lesz. Megoldás: a build során pontosan adjuk meg a célhardver compute capability-jét.

Ezek a hibák mind megelőzhetők a fenti minták követésével és a verziók, streamek, memória és workspace gondos kezelésével.

22.4.21 Összefoglalás

A CUDA-könyvtárak és a saját kód integrálása három területet igényel: az API-interop, a stream- és memóriamenedzsment, valamint a verzió- és ABI-kezelés. A handle-alapú könyvtárakat streamekhez kell kötni, a workspace-eket a _bufferSize függvényekkel kell lefoglalni, és a műveletek közötti függőségeket eseményekkel kell kifejezni. A header-only könyvtárak, mint a Thrust és a CUB, szorosan illeszkednek a saját kódba, de a fejlécverziókat ellenőrizni kell. A buildtervnek rögzítenie kell a CUDA toolkit, a driver és a compute capability verzióit, valamint a linkelés módját. A laborban bemutatott integrációs példa ezeket az elveket egyetlen, ellenőrizhető programban foglalja össze.

Önellenőrző kérdés: Miért kell a cuBLAS handle-hez streamet rendelni, ha a saját kernel és a könyvtári hívás között sorrendiséget akarunk biztosítani? Válasz: mert a handle streamje határozza meg, melyik streamen fut a könyvtári művelet. Ha a kernel egy egyéni streamen indul, a cuBLAS pedig a default streamen, a két művelet sorrendje nem garantált, és az adatfüggőség sérülhet. A cublasSetStream hívással a handle-t ugyanahhoz a streamhez kötjük, így a kernel és a könyvtári hívás ugyanabban a sorban hajtódik végre, és az adatcsere helyes lesz.
