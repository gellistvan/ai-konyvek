29.3 Kernel és launch

Az OpenCL kernel az a programegység, amely a device-on fut; a work-group a work-itemek azon csoportja, amelyek együtt ütemeződnek, és bizonyos erőforrásokat megosztanak. A kernel és a work-group fogalma nem választható el a global és local work size megadásától, valamint az aszinkron végrehajtást vezérlő eseményektől. Ebben az alfejezetben ezeket a fogalmakat járjuk körbe egy vektorösszeadó laboron keresztül, amely a gpu111-ben bevezetett platform, context, queue és memóriaobjektum-modellre épít.

29.3.1 1. Az OpenCL kernel és a work-group

Az OpenCL kernel egy olyan függvény, amelyet a hoszt a device-on hajt végre. A kernel forrása OpenCL C nyelven íródik, és a __kernel minősítő jelöli, hogy az adott függvény belépési pont a device-on. A kernel minden egyes meghívása egy work-itemet hoz létre, amely a CUDA thread fogalmának felel meg. A work-itemek azonban nem független szálakként léteznek, hanem work-groupokba rendeződnek. A work-group a work-itemek olyan halmaza, amelyek együtt futnak egy számítási egységen, és közös local memóriát, valamint szinkronizációs lehetőséget kapnak.

A kernel a bemeneti és kimeneti adatokat a memóriaobjektumokon keresztül éri el. Az OpenCL C négy címtérminősítőt ismer:

  • __global – a device globális memóriája, a hoszt által írt és olvasott pufferek.
  • __constant – a device konstans memóriája, hoszt által inicializált, a kernelben csak olvasható.
  • __local – a work-group által megosztott memória, a kernelben deklarálható vagy hosztból allokálható.
  • __private – a work-item privát memóriája, alapértelmezés szerint a kernelben deklarált változók itt élnek.

A kernel a saját indexeit beépített függvényekkel kérdezi le. A leggyakrabban használt függvények:

  • get_global_id(dim) – a work-item globális indexe a dim dimenzióban.
  • get_local_id(dim) – a work-item indexe a saját work-groupján belül.
  • get_group_id(dim) – a work-group indexe.
  • get_global_size(dim) – a teljes work-itemek száma a dim dimenzióban.
  • get_local_size(dim) – a work-group mérete a dim dimenzióban.
  • get_num_groups(dim) – a work-groupok száma a dim dimenzióban.

Ezek a függvények a kernel futása során állandóak, és a hoszt által megadott global_work_size és local_work_size értékekből származnak. A work-itemek egy dimenziós, két dimenziós vagy három dimenziós indexeléssel azonosíthatók; a dimenziók száma a kernel indításakor adható meg.

Példa egy egyszerű kernelre, amely két vektor elemenkénti összegét számítja ki:

// OpenCL C 1.2, clBuildProgram
__kernel void vector_add(__global const float* a,
                         __global const float* b,
                         __global float* c) {
    const int i = get_global_id(0);   // globális index
    c[i] = a[i] + b[i];
}

Itt a get_global_id(0) adja meg, hogy az adott work-item melyik elemet dolgozza fel. A kernel maga nem ismeri a vektor hosszát; azt a hosztnak kell ellenőriznie, vagy a kernelnek kell határellenőrzést végeznie, ha a global work size nem egyenlő a vektor hosszával. A fenti kernel feltételezi, hogy a global work size pontosan a vektor hossza.

A work-group szerepe akkor válik fontossá, ha a work-itemeknek együtt kell működniük. A work-groupon belüli szinkronizáció a barrier() függvénnyel érhető el, amely a work-group összes work-itemjét várakoztatja, amíg mindegyik el nem éri a hívási pontot. A barrier() a work-groupon belüli memóriahozzáférések rendezését is biztosítja. A work-groupok között nincs ilyen szinkronizációs lehetőség; a work-groupok közötti függőséget csak a hoszt tudja kezelni újabb kernelindítással vagy eseményekkel.

A work-group méretét a hoszt adja meg, és a választható értékeket a device hardveres korlátai befolyásolják. A lekérdezés a clGetDeviceInfo függvénnyel történik, például CL_DEVICE_MAX_WORK_GROUP_SIZE és CL_DEVICE_MAX_WORK_ITEM_SIZES paraméterekkel. A gyakorlatban a work-group méret jellemzően 32, 64, 128 vagy 256, de ez hardverfüggő. A CUDA-ból ismert warpmérethez hasonlóan az OpenCL eszközök is bizonyos work-item csoportokban ütemeznek, ezért a work-group méret megválasztása jelentősen befolyásolja a teljesítményt. Ezzel a gpu113 és későbbi fejezetek foglalkoznak részletesen.

29.3.2 2. Global és local work size

A kernel indításakor a hoszt megadja a global work size-ot, amely a teljes végrehajtandó work-itemek számát határozza meg, és opcionálisan a local work size-ot, amely a work-group méretét adja meg. Az OpenCL API-ban ezt a clEnqueueNDRangeKernel függvény végzi:

cl_int clEnqueueNDRangeKernel(
    cl_command_queue command_queue,
    cl_kernel kernel,
    cl_uint work_dim,
    const size_t* global_work_offset,
    const size_t* global_work_size,
    const size_t* local_work_size,
    cl_uint num_events_in_wait_list,
    const cl_event* event_wait_list,
    cl_event* event);

A work_dim értéke 1, 2 vagy 3 lehet. A global_work_size egy size_t tömb, amelynek hossza work_dim. A local_work_size egy size_t tömb, vagy NULL. Ha NULL, az implementáció választja meg a work-group méretet, de ilyenkor a kernel nem feltételezhet konkrét work-group méretet. A global_work_offset eltolást adhat meg, de a legtöbb esetben NULL (nulla eltolás). A event_wait_list és num_events_in_wait_list a kernel indítását megelőző eseményeket adja meg; a event pedig a kernel végrehajtását jelző eseményt fogja visszaadni.

A global work size és a local work size közötti kapcsolat kritikus. A global work size minden dimenzióban osztható kell legyen a local work size-szal, különben az OpenCL a CL_INVALID_WORK_GROUP_SIZE hibát adja. Ha a local work size NULL, akkor ez a feltétel automatikusan teljesül, mert az implementáció választ a global work size-hoz illeszkedő méretet. Ha a hoszt explicit local work size-ot ad meg, akkor a global work size minden dimenzióban osztható kell legyen a megfelelő local work size-szal.

Például ha a vektor hossza 1024, akkor választhatunk:

  • 1D: global_work_size = {1024}, local_work_size = {256} → 4 work-group
  • 2D: global_work_size = {32, 32}, local_work_size = {8, 8} → 4×4 = 16 work-group
  • 3D: global_work_size = {8, 8, 16}, local_work_size = {4, 4, 4} → 2×2×4 = 16 work-group

Ha a vektor hossza nem osztható a kívánt work-group mérettel, például 1000 elemet szeretnénk feldolgozni 256-os work-groupökkel, akkor a global work size-ot fel kell kerekíteni a következő osztható értékre, például 1024-re, és a kernelben határellenőrzést kell végezni:

// OpenCL C 1.2, clBuildProgram
__kernel void vector_add_safe(__global const float* a,
                              __global const float* b,
                              __global float* c,
                              const int n) {
    const int i = get_global_id(0);
    if (i < n) {
        c[i] = a[i] + b[i];
    }
}

Ilyenkor a hoszt a global_work_size-t 1024-re állítja, és a kernel a n segítségével eldönti, hogy az adott work-itemnek van-e érvényes munkája. Ez a minta megegyezik a CUDA-ban megszokott grid-stride loop vagy határellenőrzés mintájával.

A work-group méret megválasztásánál figyelembe kell venni a device hardveres korlátait. A clGetDeviceInfo lekérdezéssel kaphatjuk meg a CL_DEVICE_MAX_WORK_GROUP_SIZE értéket, amely a maximális work-item szám egy work-groupben. Emellett a CL_DEVICE_MAX_WORK_ITEM_SIZES egy size_t tömb, amely dimenziónként adja meg a maximális work-item számot. Például egy eszközön lehet, hogy a maximális work-group méret 1024, de a 2D-s maximális méret {1024, 1024, 64}. A work-group méret nem haladhatja meg ezeket a korlátokat, és a device által támogatott work-group méretek halmaza gyakran a warpméret többszöröse.

A kernelben a work-group mérete a get_local_size(0) függvénnyel kérdezhető le. Ez hasznos például akkor, ha a kernel a work-group méretétől függően végez számítást, vagy ha a local memória méretét dinamikusan kell meghatározni.

29.3.3 3. Események

Az OpenCL parancssor aszinkron modellt követ. A hoszt parancsokat ad ki a queue-ba, de a parancsok végrehajtása nem feltétlenül azonnal történik. A hoszt és a device közötti szinkronizációhoz, valamint a parancsok közötti függőségek kifejezéséhez az OpenCL eseményeket használ.

Egy esemény (cl_event) egy parancs állapotát reprezentálja. A legtöbb clEnqueue* függvény utolsó paramétere egy cl_event* mutató, amelyre a függvény az esemény objektumot írja. Az esemény állapotát a clGetEventInfo függvénnyel lehet lekérdezni, például CL_EVENT_COMMAND_TYPE, CL_EVENT_COMMAND_EXECUTION_STATUS. Az állapot lehet CL_QUEUED, CL_SUBMITTED, CL_RUNNING vagy CL_COMPLETE.

A hoszt a clWaitForEvents függvénnyel várhat egy vagy több esemény befejezésére:

cl_int clWaitForEvents(cl_uint num_events, const cl_event* event_list);

Ez blokkolja a hosztot, amíg a megadott események mindegyike CL_COMPLETE állapotba nem kerül. A clFinish függvény a queue összes parancsának befejezését várja, ami gyakran egyszerűbb, ha nincs szükség finomabb vezérlésre.

Az események használhatók a parancsok közötti függőségek kifejezésére is. Ha például egy kernel csak akkor indulhat, ha egy másik kernel befejeződött, akkor a második kernel clEnqueueNDRangeKernel hívásában a event_wait_list paraméterrel megadhatjuk az első kernel eseményét. Ez biztosítja, hogy a második kernel csak az első befejezése után kerüljön végrehajtásra, anélkül, hogy a hosztnak explicit várakoznia kellene.

Az események callback mechanizmust is támogatnak. A clSetEventCallback függvénnyel regisztrálhatunk egy visszahívó függvényt, amely akkor fut le, amikor az esemény eléri a megadott állapotot. Ez lehetővé teszi eseményvezérelt hosztprogramok írását.

A teljesítményméréshez az események különösen hasznosak. Ha a queue-t a CL_QUEUE_PROFILING_ENABLE zászlóval hozzuk létre, akkor a clGetEventProfilingInfo függvénnyel lekérdezhetjük a parancs időbélyegeit:

  • CL_PROFILING_COMMAND_QUEUED – a parancs queue-ba kerülésének időpontja.
  • CL_PROFILING_COMMAND_SUBMITTED – a parancs elküldésének időpontja.
  • CL_PROFILING_COMMAND_START – a parancs végrehajtásának kezdete.
  • CL_PROFILING_COMMAND_END – a parancs végrehajtásának vége.

A kernel futási ideje a CL_PROFILING_COMMAND_END és CL_PROFILING_COMMAND_START különbsége nanomásodpercben. Ez a módszer pontosabb, mint a hoszt oldali időmérés, mert nem tartalmazza a queue-ba állás és a szinkronizáció idejét.

Példa a profilkérésre:

cl_event kernel_event;
clEnqueueNDRangeKernel(queue, kernel, 1, NULL, &global_size, &local_size, 0, NULL, &kernel_event);
clWaitForEvents(1, &kernel_event);

cl_ulong start, end;
clGetEventProfilingInfo(kernel_event, CL_PROFILING_COMMAND_START, sizeof(cl_ulong), &start, NULL);
clGetEventProfilingInfo(kernel_event, CL_PROFILING_COMMAND_END, sizeof(cl_ulong), &end, NULL);
printf("kernel time: %llu ns\n", (unsigned long long)(end - start));

Az események fontos szerepet játszanak a memóriaobjektumok olvasásánál is. A clEnqueueReadBuffer függvény szintén aszinkron, és a hoszt csak akkor olvashatja a puffert, ha a másolás befejeződött. Ezt a clFinish hívással vagy a clEnqueueReadBuffer eseményére való várakozással biztosíthatjuk.

29.3.4 4. Labor: OpenCL vektorösszeadó kernel

A labor célja egy teljes OpenCL program létrehozása, amely két float vektort ad össze a GPU-n, majd ellenőrzi az eredményt. A program a következő lépéseket hajtja végre:

  1. Platform és device kiválasztása.
  2. Context és queue létrehozása.
  3. Pufferek allokálása és feltöltése.
  4. Kernel forrásának betöltése és lefordítása.
  5. Kernel argumentumok beállítása.
  6. Kernel indítása a megfelelő global és local work size-szal.
  7. Eredmény visszaolvasása.
  8. Ellenőrzés és mérési napló.

A kernel forrása:

// vector_add.cl – OpenCL C 1.2
__kernel void vector_add(__global const float* a,
                         __global const float* b,
                         __global float* c,
                         const int n) {
    const int i = get_global_id(0);
    if (i < n) {
        c[i] = a[i] + b[i];
    }
}

A hosztprogram C++17-ben, OpenCL 3.0 API-val:

// main.cpp – C++17, g++ 12, OpenCL 3.0
#include <CL/cl.h>
#include <cstdio>
#include <cstdlib>
#include <cstring>
#include <vector>

#define CL_CHECK(expr)                                                       \
    do {                                                                      \
        cl_int err = (expr);                                                  \
        if (err != CL_SUCCESS) {                                              \
            fprintf(stderr, "OpenCL hiba: %s:%d: %d\n", __FILE__, __LINE__,  \
                    err);                                                     \
            exit(EXIT_FAILURE);                                               \
        }                                                                     \
    } while (0)

int main() {
    const int n = 1 << 20; // 1 048 576 elem
    const size_t local_size = 256;
    const size_t global_size = ((n + local_size - 1) / local_size) * local_size;

    // 1. Platform és device
    cl_platform_id platform;
    cl_device_id device;
    CL_CHECK(clGetPlatformIDs(1, &platform, NULL));
    CL_CHECK(clGetDeviceIDs(platform, CL_DEVICE_TYPE_GPU, 1, &device, NULL));

    // 2. Context és queue
    cl_context context = clCreateContext(NULL, 1, &device, NULL, NULL, NULL);
    if (!context) { fprintf(stderr, "Context hiba\n"); return EXIT_FAILURE; }
    cl_command_queue queue = clCreateCommandQueue(context, device, CL_QUEUE_PROFILING_ENABLE, NULL);
    if (!queue) { fprintf(stderr, "Queue hiba\n"); return EXIT_FAILURE; }

    // 3. Pufferek
    std::vector<float> a(n), b(n), c(n);
    for (int i = 0; i < n; ++i) {
        a[i] = static_cast<float>(i) * 0.1f;
        b[i] = static_cast<float>(i) * 0.2f;
    }
    cl_mem d_a = clCreateBuffer(context, CL_MEM_READ_ONLY | CL_MEM_COPY_HOST_PTR,
                                n * sizeof(float), a.data(), NULL);
    cl_mem d_b = clCreateBuffer(context, CL_MEM_READ_ONLY | CL_MEM_COPY_HOST_PTR,
                                n * sizeof(float), b.data(), NULL);
    cl_mem d_c = clCreateBuffer(context, CL_MEM_WRITE_ONLY,
                                n * sizeof(float), NULL, NULL);
    if (!d_a || !d_b || !d_c) { fprintf(stderr, "Buffer hiba\n"); return EXIT_FAILURE; }

    // 4. Kernel fordítás
    const char* source = R"(
        __kernel void vector_add(__global const float* a,
                                 __global const float* b,
                                 __global float* c,
                                 const int n) {
            const int i = get_global_id(0);
            if (i < n) {
                c[i] = a[i] + b[i];
            }
        }
    )";
    cl_program program = clCreateProgramWithSource(context, 1, &source, NULL, NULL);
    if (!program) { fprintf(stderr, "Program hiba\n"); return EXIT_FAILURE; }
    cl_int build_err = clBuildProgram(program, 1, &device, "", NULL, NULL);
    if (build_err != CL_SUCCESS) {
        char log[8192];
        clGetProgramBuildInfo(program, device, CL_PROGRAM_BUILD_LOG, sizeof(log), log, NULL);
        fprintf(stderr, "Build hiba:\n%s\n", log);
        return EXIT_FAILURE;
    }
    cl_kernel kernel = clCreateKernel(program, "vector_add", NULL);
    if (!kernel) { fprintf(stderr, "Kernel hiba\n"); return EXIT_FAILURE; }

    // 5. Argumentumok
    CL_CHECK(clSetKernelArg(kernel, 0, sizeof(cl_mem), &d_a));
    CL_CHECK(clSetKernelArg(kernel, 1, sizeof(cl_mem), &d_b));
    CL_CHECK(clSetKernelArg(kernel, 2, sizeof(cl_mem), &d_c));
    CL_CHECK(clSetKernelArg(kernel, 3, sizeof(int), &n));

    // 6. Kernel indítás
    cl_event kernel_event;
    CL_CHECK(clEnqueueNDRangeKernel(queue, kernel, 1, NULL, &global_size,
                                    &local_size, 0, NULL, &kernel_event));

    // 7. Eredmény visszaolvasása
    cl_event read_event;
    CL_CHECK(clEnqueueReadBuffer(queue, d_c, CL_TRUE, 0, n * sizeof(float),
                                 c.data(), 1, &kernel_event, &read_event));
    CL_CHECK(clWaitForEvents(1, &read_event));

    // 8. Ellenőrzés
    bool ok = true;
    for (int i = 0; i < n; ++i) {
        const float expected = a[i] + b[i];
        if (std::fabs(c[i] - expected) > 1e-5f) {
            ok = false;
            fprintf(stderr, "Eltérés az indexen %d: várt %.6f, kapott %.6f\n",
                    i, expected, c[i]);
            break;
        }
    }
    printf("Ellenőrzés: %s\n", ok ? "sikeres" : "sikertelen");

    // Profil
    cl_ulong start, end;
    clGetEventProfilingInfo(kernel_event, CL_PROFILING_COMMAND_START, sizeof(cl_ulong), &start, NULL);
    clGetEventProfilingInfo(kernel_event, CL_PROFILING_COMMAND_END, sizeof(cl_ulong), &end, NULL);
    printf("Kernel futási idő: %.3f ms\n", (end - start) * 1e-6);

    // Takarítás
    clReleaseEvent(kernel_event);
    clReleaseEvent(read_event);
    clReleaseKernel(kernel);
    clReleaseProgram(program);
    clReleaseMemObject(d_a);
    clReleaseMemObject(d_b);
    clReleaseMemObject(d_c);
    clReleaseCommandQueue(queue);
    clReleaseContext(context);
    return ok ? EXIT_SUCCESS : EXIT_FAILURE;
}

A fordítás és futtatás Linux környezetben, OpenCL ICD-vel:

g++ -O2 -std=c++17 main.cpp -lOpenCL -o vector_add
./vector_add

A fenti kódban a global_size kiszámítása ((n + local_size - 1) / local_size) * local_size módon történik, így a global work size osztható local_size-szal, és a kernelben a if (i < n) határellenőrzés kezeli a felesleges work-itemeket. A clEnqueueReadBuffer hívásban a blocking paraméter CL_TRUE, így a hoszt várakozik a másolás befejezésére, de a kernel_event megadása biztosítja, hogy a másolás csak a kernel befejezése után kezdődjön. A read_event-re való várakozás redundáns, de bemutatja az események használatát.

Összehasonlító CUDA és JAX példák. A teljesség kedvéért a vektorösszeadás CUDA C++ és JAX megfelelője is megadható, de ebben a fejezetben csak illusztrációként, futtatás nélkül szerepelnek:

// CUDA C++17, nvcc 12.4, nem futtatott illusztráció
__global__ void vector_add_cuda(const float* a, const float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) c[i] = a[i] + b[i];
}
# JAX, jax 0.4, nem futtatott illusztráció
import jax.numpy as jnp
a = jnp.arange(n, dtype=jnp.float32) * 0.1
b = jnp.arange(n, dtype=jnp.float32) * 0.2
c = a + b

A JAX esetén a kernelindítás és a memóriakezelés rejtve marad; a kifejezés a JIT-fordítás után a TPU/GPU-ra kerül. A részletes JAX és TPU kezelés a gpu106–gpu109 alfejezetekben található.

29.3.5 5. Tipikus hibák és megoldások

  1. CL_INVALID_WORK_GROUP_SIZE. A global work size nem osztható a local work size-szal, vagy a local work size meghaladja a device korlátját. Megoldás: kerekítsük fel a global work size-ot, és a kernelben végezzünk határellenőrzést; ellenőrizzük a CL_DEVICE_MAX_WORK_GROUP_SIZE és CL_DEVICE_MAX_WORK_ITEM_SIZES értékeket.

  2. Helytelen kernel argumentumok. A kernel argumentumok sorrendje vagy típusa nem egyezik a clSetKernelArg hívásokkal. Ez gyakran CL_INVALID_ARG_SIZE vagy CL_INVALID_ARG_INDEX hibát okoz. Megoldás: a kernel szignatúráját és a hoszt hívásait együtt ellenőrizzük, a clSetKernelArg minden hívásánál a CL_CHECK makrót használjuk.

  3. Build hiba figyelmen kívül hagyása. A clBuildProgram visszatérési értékét ellenőrizni kell, és hiba esetén a build logot ki kell írni. A build log kiíratása nélkül a hibás kernel forrás rejtve marad.

  4. Nem várt aszinkron végrehajtás. A hoszt a clEnqueueNDRangeKernel után azonnal olvassa a puffert, de a kernel még nem fejeződött be. Megoldás: a clEnqueueReadBuffer hívásban adjuk meg a kernel eseményét, vagy hívjunk clFinish-t az olvasás előtt.

  5. Memóriaobjektumok felszabadításának elmulasztása. A clCreateBuffer, clCreateKernel, clCreateProgram stb. hívások által lefoglalt erőforrásokat a megfelelő clRelease* függvényekkel kell felszabadítani, különben erőforrás-szivárgás lép fel.

  6. A work-group méret nem optimális. A device által támogatott maximális work-group méret nem feltétlenül a leggyorsabb. A teljesítményoptimalizáláshoz a gpu113 és a gpu115 fejezetek adnak útmutatást.

29.3.6 6. Önellenőrző kérdés
