30.2 Work-group, barrier és local memory

Az OpenCL végrehajtási modelljének középpontjában a work-group áll: ez az a szerveződési szint, ahol a work-itemek egymással szinkronizálhatnak, és ahol a local memory megosztott tárolóként jelenik meg. A work-group fogalma analóg a CUDA thread blockjával, de az OpenCL terminológiája és egyes részletszabályai sajátosak.

30.2.1 1. A work-group mint a szinkronizáció alapegysége

Az OpenCL kernel indításakor a host egy N-dimenziós indexteret (NDRange) ad meg. Az NDRange felosztható work-groupökre; minden work-group azonos méretű, és a work-itemeket a csoport indexével azonosítjuk. A work-group méretét a kernel indításakor az enqueueNDRangeKernel utolsó argumentumában adjuk meg. A work-itemek a következő beépített függvényekkel kérdezhetik le saját helyüket:

  • get_global_id(dim) – a work-item globális azonosítója az adott dimenzióban.
  • get_local_id(dim) – a work-item azonosítója a work-groupön belül.
  • get_group_id(dim) – a work-group azonosítója.
  • get_local_size(dim) – a work-group mérete.
  • get_num_groups(dim) – a work-groupök száma.
  • get_global_size(dim) – a teljes indexméret.
  • get_work_dim() – az NDRange dimenzióinak száma.

Ezek a függvények lehetővé teszik, hogy a kernel a globális indexből kiszámítsa a feldolgozandó adatelem helyét. Az 1D-s esetben a következő azonosság érvényes:

global_id = group_id * local_size + local_id

Többdimenziós esetben minden dimenzióra külön kell elvégezni ezt a számítást. A work-group méretét a get_local_size értéke adja; ez a kernel indításakor rögzített, és a kernel belsejében csak lekérdezhető, nem módosítható.

A work-groupök egymástól függetlenül hajtódnak végre: az ütemező bármilyen sorrendben futtathatja őket, akár párhuzamosan, akár sorosan. Ezért a globális szinkronizáció nem megoldható a work-groupök között a kernel belsejében; az OpenCL nem definiál grid-szintű barriert. A work-groupön belüli szinkronizáció viszont a barrier függvénnyel lehetséges, és ez az együttműködés alapegysége. A work-groupök közötti adatcsere csak a kernel befejeződése után, a globális memórián keresztül, vagy atomi műveletekkel oldható meg, de ez utóbbi nem garantálja a teljes szinkronizációt.

30.2.2 2. Local memory: a work-group gyors memóriája

A local memory az OpenCL memóriamodelljének az a rétege, amely egy work-groupön belül osztozik. A CUDA shared memory megfelelője, azzal a különbséggel, hogy az OpenCL terminológiájában a local a work-group láthatóságú memóriát jelöli, míg a private a work-item saját változóit. A local memory a device-on belüli gyors, alacsony késleltetésű tároló, amelynek mérete korlátozott; a tipikus GPU-kon néhány tíz KiB (például 48–96 KiB) áll rendelkezésre work-groupönként. A pontos méretet a CL_DEVICE_LOCAL_MEM_SIZE eszközadat adja meg.

A local memory a kernelben a __local minősítővel jelölhető. Kétféleképpen allokálható:

  1. Statikus allokáció a kernelben: a kernel törzsében __local float tile[256]; alakban. A méretnek fordítási időben ismert konstansnak kell lennie.
  2. Dinamikus allokáció kernelargumentumként: a kernel egy __local float* paramétert kap, és a host a kernel indítása előtt megadja a méretet bájtban. Ez lehetővé teszi, hogy ugyanaz a kernel különböző work-group méretekkel fusson anélkül, hogy újra kellene fordítani.

A következő kernelrészlet dinamikus local memóriát használ:

// Fordítás: OpenCL C 1.2+
__kernel void use_local(__global const float* input,
                        __global float* output,
                        __local float* tile) {
    int lid = get_local_id(0);
    int gid = get_global_id(0);
    tile[lid] = input[gid];
    // ... további feldolgozás
}

A host oldalon a local memória méretét a clSetKernelArg hívással adjuk meg; az argumentum értéke NULL, a méret pedig a szükséges bájtok száma:

// OpenCL C++ API
clSetKernelArg(kernel, 2, local_bytes, nullptr);

A local_bytes értéke például workgroup_size * sizeof(float). Fontos, hogy a local memória mérete nem haladhatja meg az eszköz által támogatott maximumot, és a kernel által igényelt local memória mérete befolyásolja az occupancyt: minél nagyobb local memóriát foglal egy work-group, annál kevesebb work-group lehet egyszerre aktív egy compute uniton.

A local memory élettartama a work-group végrehajtásához kötött; amikor a work-group befejeződik, a local memória tartalma elvész. A host közvetlenül nem férhet hozzá; az adatokat a kernelnek kell feltöltenie a globális memóriából, és az eredményt a kernelnek kell visszaírnia.

30.2.3 3. Barrier és memóriakerítés

A barrier függvény a work-groupön belüli szinkronizáció eszköze. A hívás azt jelenti, hogy a work-group minden work-itemjének el kell érnie a barriert, mielőtt bármelyikük továbbhaladhat. A barrier opcionális memóriakerítési zászlókat is kaphat:

  • CLK_LOCAL_MEM_FENCE: a local memóriába írt adatoknak a work-group többi work-itemje számára láthatóvá kell válniuk.
  • CLK_GLOBAL_MEM_FENCE: a globális memóriába írt adatoknak a work-group többi work-itemje számára kell láthatóvá válniuk.

A memóriakerítés nélkül a work-itemek által végrehajtott írások sorrendje nem garantált; a barrier biztosítja, hogy a barrier előtti írások befejeződjenek, mielőtt a barrier utáni olvasások megkezdődnek.

A legegyszerűbb és leggyakoribb minta a következő:

// 1. Minden work-item betölt egy értéket a local memóriába
tile[lid] = input[gid];

// 2. Barrier: minden betöltésinek be kell fejeződnie
barrier(CLK_LOCAL_MEM_FENCE);

// 3. Most már olvasható a local memória
float value = tile[lid + 1];

A barrier nélkül az egyik work-item olvashatná a local memóriát, mielőtt a másik work-item befejezte volna az írást, ami nem determinisztikus és hibás eredményhez vezet.

A fa-alapú redukcióban a barriert minden iterációban meg kell hívni:

for (int offset = local_size / 2; offset > 0; offset >>= 1) {
    if (lid < offset) {
        tile[lid] += tile[lid + offset];
    }
    barrier(CLK_LOCAL_MEM_FENCE);
}

Itt a barrier azért szükséges, mert a következő iterációban a work-itemek a tile[lid + offset] értéket olvassák, amelyet az előző iterációban egy másik work-item írhatott. A barrier garantálja, hogy az összes írás befejeződött, mielőtt bármely work-item a következő iterációba lép.

A barrier használatakor a leggyakoribb hiba a divergens barrier. Ez akkor fordul elő, ha a barrier hívása feltételes ágban van, és nem minden work-item éri el. Például a következő kód hibás:

// HIBÁS: a barrier csak azoknak fut le, akik beléptek az if ágba
if (lid < offset) {
    tile[lid] += tile[lid + offset];
    barrier(CLK_LOCAL_MEM_FENCE); // <-- hibás!
}

A fenti esetben a barrier nem garantálja, hogy minden work-item eléri; a work-group viselkedése nem definiált, tipikusan holtpont vagy hibás eredmény. A helyes megoldás az, hogy a barriert a feltételes ágon kívül, minden work-item által végrehajtott helyen hívjuk:

if (lid < offset) {
    tile[lid] += tile[lid + offset];
}
barrier(CLK_LOCAL_MEM_FENCE); // <-- helyes

Általános szabály, hogy a kernelben a barrier hívásoknak a work-group minden work-itemje által elérhető úton kell lenniük. A fordító nem mindig figyelmeztet a divergens barrierre, ezért a fejlesztő felelőssége a helyes használat.

30.2.4 4. Bank conflict a local memoryben

A local memory a GPU-kon bankokra oszlik, hogy a párhuzamos hozzáférést gyorsítsa. A tipikus kialakítás 32 bank, mindegyik 32 bites szóval. Ha egy hullámfront (warp) work-itemjei egyszerre ugyanabba a bankba, de különböző címekre próbálnak írni vagy olvasni, akkor a hozzáférés sorosítva történik, ami bank conflictet okoz. A bank conflict nem ad helytelen eredményt, de a memória-hozzáférést lassítja, és jelentős teljesítménycsökkenést okozhat.

A bank conflict leggyakoribb forrása a local memóriában tárolt mátrix transzponálása. Tekintsünk egy 32×32-es float mátrixot:

__kernel void transpose_naive(__global const float* in,
                              __global float* out,
                              __local float tile[32][32]) {
    int x = get_global_id(0);
    int y = get_global_id(1);
    int lx = get_local_id(0);
    int ly = get_local_id(1);

    tile[ly][lx] = in[y * get_global_size(0) + x];
    barrier(CLK_LOCAL_MEM_FENCE);

    out[x * get_global_size(1) + y] = tile[lx][ly];
}

A fenti kernelben a tile[lx][ly] olvasás oszlopos hozzáférést jelent. Egy hullámfronton belül a work-itemek az x dimenzió mentén szomszédosak, így lx változik, ly pedig fix. A local memória címe (lx * 32 + ly) * 4 bájt. A bank indexét a cím 32 bájtos bankokra osztásával kapjuk: (lx * 32 + ly) mod 32 = ly mod 32. Mivel ly ugyanaz minden work-itemre a hullámfrontban, mind ugyanabba a bankba próbálnak olvasni, ami 32-szeres bank conflictet okoz.

A megoldás a padding: a local memória tömbjét eggyel szélesebbre választjuk, például tile[32][33] méretűre. Ekkor a sor hossza 33, és a bank index számítása (lx * 33 + ly) mod 32 = (lx + ly) mod 32 lesz, ami a hullámfronton belül változik, így a hozzáférés conflictmentessé válik:

__kernel void transpose_padded(__global const float* in,
                               __global float* out,
                               __local float tile[32][33]) {
    // ... ugyanaz, mint fent ...
}

A padding tehát egyetlen extra oszloppal megszünteti a bank conflictet. Az OpenCL specifikáció nem írja elő a bankok számát, ezért a padding méretét az adott hardverhez kell igazítani; a gyakorlatban a 32 bank és a 32 bites szó a leggyakoribb. A bank conflict fogalma analóg a CUDA shared memory bank conflictjével, de az OpenCL-ben a local memory bankok elrendezése implementációfüggő, ezért a méréseknek mindig hardverspecifikusnak kell lenniük.

30.2.5 5. Tipikus hibák és megelőzés

A work-group, barrier és local memory használata során a következő hibák fordulnak elő leggyakrabban:

  1. Divergens barrier: a barrier feltételes ágban van, és nem minden work-item hívja meg. Megelőzés: a barrier hívásokat mindig a vezérlési gráf olyan pontjára helyezzük, amelyet minden work-item elér; a feltételes ágakban csak a memóriaműveletek vannak, a barrier utána következik.

  2. Local memory inicializálás elmulasztása: a local memória a work-group indulásakor nem definiált tartalommal rendelkezik. Ha a kernel nem tölti fel, akkor hibás eredményt adhat. Megelőzés: a local memóriába mindig írunk, mielőtt olvasnánk, és a barrier után olvasunk.

  3. Bank conflict figyelmen kívül hagyása: a local memória elérési mintája sorosítást okoz, ami lassítja a kernelt. Megelőzés: padding, vagy az elérési minta átalakítása (például soronkénti feldolgozás).

  4. Work-group méret és local memory méret korlátjainak túllépése: ha a work-group túl nagy, a kernel nem fordul le, vagy az occupancy drasztikusan csökken. Megelőzés: a CL_DEVICE_MAX_WORK_GROUP_SIZE és a CL_DEVICE_LOCAL_MEM_SIZE eszközadatok lekérdezése; a clGetKernelWorkGroupInfo a kernelre vonatkozó korlátokat is megadja.

  5. A globális szinkronizáció téves feltételezése: a work-groupök közötti függőséget nem lehet barrierrel megoldani. Megelőzés: a kernelhatárokra vagy atomi műveletekre kell támaszkodni, és a tervezés során a work-groupök függetlenségét kell alapul venni.

30.2.6 6. Labor: local memoryt használó OpenCL redukció

A labor célja egy olyan OpenCL kernel írása, amely work-groupönként egy részösszeget számít ki local memory és barrier használatával. Az eredményt a host CPU-s referenciával ellenőrzi, és mérési naplót készít. A kernel a korábban bemutatott fa-alapú redukciót valósítja meg.

30.2.7 6.1. Kernel

A kernel dinamikus local memóriát használ, így a work-group mérete a host oldalon megadható anélkül, hogy a kernelt újra kellene fordítani. A kernel argumentumai: bemeneti tömb, kimeneti tömb (work-groupönként egy érték), és a local memória pointer.

// Fordítás: OpenCL C 1.2+
// Feltétel: a globális méret = num_groups * workgroup_size
__kernel void partial_reduce(
    __global const float* input,
    __global float* output,
    __local float* tile)
{
    int gid = get_global_id(0);
    int lid = get_local_id(0);
    int group_id = get_group_id(0);
    int local_size = get_local_size(0);

    // 1. lépés: betöltés a globális memóriából a local memóriába
    tile[lid] = input[gid];

    // Minden work-itemnek el kell érnie a barriert,
    // mielőtt bármelyik olvasná a local memóriát.
    barrier(CLK_LOCAL_MEM_FENCE);

    // 2. lépés: fa-alapú redukció a work-groupön belül
    for (int offset = local_size / 2; offset > 0; offset >>= 1) {
        if (lid < offset) {
            tile[lid] += tile[lid + offset];
        }
        // A barrier a ciklusban is kötelező:
        // a következő iteráció olvasása csak akkor kezdődhet,
        // ha az összes hozzáadás befejeződött.
        barrier(CLK_LOCAL_MEM_FENCE);
    }

    // 3. lépés: az eredmény kiírása
    if (lid == 0) {
        output[group_id] = tile[0];
    }
}

A kernel a __local float* tile argumentumot dinamikus local memóriaként kapja; a méretet a host adja meg.

30.2.8 6.2. Host kód

A host kód C++ és az OpenCL C++ API-t használja. A hibaellenőrzéshez egy CHECK_CL makró szolgál. Az alábbi kód a teljes futtatást mutatja be, de a rövidség kedvéért a platform- és eszközkiválasztás részleteit egyszerűsítjük.

// Fordítás: g++ -std=c++17 -lOpenCL
#include <CL/cl.hpp>
#include <vector>
#include <iostream>
#include <cassert>
#include <numeric>

#define CHECK_CL(err, msg) \
    if (err != CL_SUCCESS) { \
        std::cerr << msg << ": " << err << std::endl; \
        return 1; \
    }

int main() {
    constexpr size_t workgroup_size = 256;
    constexpr size_t num_groups = 4096;
    constexpr size_t N = workgroup_size * num_groups;

    // Helyőrző: platform- és eszközkiválasztás
    std::vector<cl::Platform> platforms;
    cl::Platform::get(&platforms);
    if (platforms.empty()) { std::cerr << "Nincs OpenCL platform\n"; return 1; }
    cl::Platform platform = platforms[0]; // helyőrző: válasszuk ki a GPU-t

    std::vector<cl::Device> devices;
    platform.getDevices(CL_DEVICE_TYPE_GPU, &devices);
    if (devices.empty()) { std::cerr << "Nincs GPU\n"; return 1; }
    cl::Device device = devices[0];

    cl::Context context(device);
    cl::CommandQueue queue(context, device, CL_QUEUE_PROFILING_ENABLE);

    // Kernel forráskód
    std::string source = R"(
        __kernel void partial_reduce(
            __global const float* input,
            __global float* output,
            __local float* tile)
        {
            int gid = get_global_id(0);
            int lid = get_local_id(0);
            int group_id = get_group_id(0);
            int local_size = get_local_size(0);
            tile[lid] = input[gid];
            barrier(CLK_LOCAL_MEM_FENCE);
            for (int offset = local_size / 2; offset > 0; offset >>= 1) {
                if (lid < offset) {
                    tile[lid] += tile[lid + offset];
                }
                barrier(CLK_LOCAL_MEM_FENCE);
            }
            if (lid == 0) {
                output[group_id] = tile[0];
            }
        }
    )";

    cl::Program program(context, source);
    cl_int build_err = program.build({device});
    if (build_err != CL_SUCCESS) {
        std::cerr << "Build hiba: "
                  << program.getBuildInfo<CL_PROGRAM_BUILD_LOG>(device) << std::endl;
        return 1;
    }

    cl::Kernel kernel(program, "partial_reduce");

    // Bemenet inicializálása
    std::vector<float> input(N);
    for (size_t i = 0; i < N; ++i) input[i] = static_cast<float>(i % 100) * 0.01f; // helyőrző adat
    std::vector<float> output(num_groups);

    cl::Buffer d_input(context, CL_MEM_READ_ONLY, sizeof(float) * N);
    cl::Buffer d_output(context, CL_MEM_WRITE_ONLY, sizeof(float) * num_groups);

    queue.enqueueWriteBuffer(d_input, CL_TRUE, 0, sizeof(float) * N, input.data());

    // Kernel argumentumok
    size_t local_bytes = workgroup_size * sizeof(float);
    kernel.setArg(0, d_input);
    kernel.setArg(1, d_output);
    kernel.setArg(2, local_bytes, nullptr);

    // Végrehajtás méréssel
    cl::Event event;
    queue.enqueueNDRangeKernel(kernel, cl::NullRange,
                               cl::NDRange(N),
                               cl::NDRange(workgroup_size),
                               nullptr, &event);
    queue.finish();

    // Időmérés
    cl_ulong start = event.getProfilingInfo<CL_PROFILING_COMMAND_START>();
    cl_ulong end = event.getProfilingInfo<CL_PROFILING_COMMAND_END>();
    double elapsed_ms = (end - start) * 1e-6;

    queue.enqueueReadBuffer(d_output, CL_TRUE, 0, sizeof(float) * num_groups, output.data());

    // CPU referencia
    std::vector<float> reference(num_groups);
    for (int g = 0; g < num_groups; ++g) {
        float sum = 0.0f;
        for (int i = 0; i < workgroup_size; ++i) {
            sum += input[g * workgroup_size + i];
        }
        reference[g] = sum;
    }

    // Ellenőrzés
    bool ok = true;
    for (int g = 0; g < num_groups; ++g) {
        if (std::abs(output[g] - reference[g]) > 1e-5f) {
            std::cerr << "Eltérés a(z) " << g << ". csoportban: "
                      << output[g] << " vs " << reference[g] << std::endl;
            ok = false;
            break;
        }
    }
    if (ok) std::cout << "Az eredmény helyes.\n";
    std::cout << "Futásidő: " << elapsed_ms << " ms\n";

    return 0;
}

A kód a CL/cl.hpp fejlécet használja, amely a régebbi OpenCL C++ API része; újabb környezetekben a CL/cl2.hpp vagy a C API ajánlott. A laborban a lényeg az algoritmus és a mérési módszertan, nem a konkrét API-változat.

A várt és mért eredmény elkülönítése:

  • Várt eredmény: a CPU által kiszámított részösszegek a bemeneti tömb elemeiből. A bemeneti értékek ismeretében a várt érték pontosan meghatározható. A fa-alapú redukció sorrendje eltérhet a CPU szekvenciális összegzésétől, ezért az FP32 kerekítési hiba miatt kis eltérés megengedett; a tűréshatár 1e-5.
  • Mért eredmény: a kernel futása után a kimeneti pufferből kiolvasott részösszegek. A laborban a mért eredményt a check ciklus hasonlítja össze a várt értékkel; ha az eltérés a tűréshatáron belül van, az eredmény helyes.

A fenti naplóban a futásidő és a sávszélesség helyőrző; a valós méréshez a kódot a saját GPU-n kell lefuttatni. A mérési módszertan szerint a warm-up után legalább 5–10 ismétlés szükséges, és az átlag mellett a szórást is közölni kell. A sávszélességet a tényleges adatmozgatásra kell számítani: itt a kernel beolvassa a teljes bemeneti tömböt (4 MiB), a kimenet mérete elhanyagolható.

30.2.10 6.4. Elemzés

A redukciós kernel jól szemlélteti a work-group, barrier és local memory együttműködését. A local memóriába való betöltés után a barrier biztosítja, hogy minden work-item lássa a többiek által beírt értékeket. A fa-alapú redukció minden iterációja után a barrier garantálja a közbülső részösszegek láthatóságát. A kernel mérési eredménye a local memória sávszélességét is tükrözi, de a teljesítményt a bank conflict is befolyásolhatja. A bemutatott redukcióban a tile[lid] és tile[lid + offset] hozzáférések a legtöbb GPU-n nem okoznak jelentős bank conflictet, mert a szomszédos work-itemek szomszédos bankokat érnek el.

30.2.11 7. Önellenőrző kérdés

A következő kernelrészlet egy work-groupön belüli prefix összeget próbál megvalósítani local memóriában. Melyik hiba található benne, és hogyan javítható?

__kernel void broken_scan(__global const float* input,
                          __global float* output,
                          __local float tile[256]) {
    int lid = get_local_id(0);
    int gid = get_global_id(0);
    tile[lid] = input[gid];
    if (lid < 128) {
        tile[lid] += tile[lid + 128];
    }
    barrier(CLK_LOCAL_MEM_FENCE);
    if (lid < 64) {
        tile[lid] += tile[lid + 64];
    }
    barrier(CLK_LOCAL_MEM_FENCE);
    // ...
    output[gid] = tile[lid];
}

Válasz vázlata: A barrier hívások a feltételes ágakon kívül vannak, ezért a szinkronizáció helyes. A hiba a prefix összeg logikájában van: a második iterációban a tile[lid] += tile[lid + 64] hozzáadás csak azokra a work-itemekre igaz, amelyek lid < 64, de a többi work-item nem frissíti a saját tile[lid] értékét, ezért a kimenet nem lesz a teljes prefix összeg. A fejezet témájához kötődően a barrier használata ebben a kódban nem divergens; a hiba az algoritmusban van, nem a szinkronizációban. A kérdés célja annak felismerése, hogy a barrier helyes használata önmagában nem garantálja az algoritmus helyességét.
