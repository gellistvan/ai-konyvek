9.4 Összetett együttműködési minták

A thread block, a cluster és a grid együttműködési szintjei külön-külön is hatékony eszközöket adnak, de a valódi erejüket akkor mutatják meg, amikor egyetlen kernelben kombináljuk őket. Ez a fejezet azt a gyakorlati mintát járja körül, amelyben egy többlépcsős számítás egyidejűleg támaszkodik blokkszintű szinkronizációra, klaszteren belüli megosztott memóriára, valamint grid-szintű zárolásra. A cél nem az egyes csoporttípusok újbóli bemutatása – azokat a megelőző alfejezetek tárgyalták –, hanem azok összehangolt alkalmazása, a belőlük adódó teljesítmény-, hordozhatósági és helyességi kérdésekkel együtt.

9.4.1 Miért van szükség kombinált együttműködésre?

A GPU programozási modellje hierarchikus. Egy tipikus, adatpárhuzamos kernel esetében a rácson belüli blokkok egymástól függetlenül, a hardver által meghatározott ütemezésben futnak. Ez a laza csatolás egyszerűvé és skálázhatóvá teszi a végrehajtást, ugyanakkor korlátozza azokat az algoritmusokat, amelyekben a blokkoknak részeredményeket kell kicserélniük anélkül, hogy a globális memórián keresztül drága, kétszeres körüljárást végeznének.

A Cooperative Groups API három szinten vezetett be finomabb vezérlést:

  1. Blokkszintű csoportok (thread_block, tile_partition): a hagyományos __syncthreads() általánosítása, amely lehetővé teszi alcsoportok explicit szinkronizálását és kollektív műveletek használatát.
  2. Klaszterek (thread_block_cluster): a Hopper (CC 9.0) és újabb architektúrákon a hardver lehetővé teszi blokkok egy csoportjának szoros együttműködését, klaszterszintű zárolással (cluster.sync()) és klaszteren belüli megosztott memóriával (Distributed Shared Memory, DSM). A blokkok így közvetlenül olvashatják egymás shared memóriáját, anélkül hogy a globális memórián keresztül kellene kommunikálniuk.
  3. Grid-szintű csoport (grid_group): a this_grid().sync() olyan barrier, amelyet a rács minden blokkjának el kell érnie. Ez kizárólag kooperatív kernelindítás (cudaLaunchCooperativeKernel) esetén garantálható, amikor a futtatókörnyezet biztosítja, hogy az összes blokk egyidejűleg rezidens legyen az SM-eken.

A három szint kombinálása lehetővé teszi olyan algoritmusok hatékony megvalósítását, amelyek korábban csak többszöri kernelindítással, globális memórián keresztüli kommunikációval vagy atomi műveletekkel voltak megoldhatók. A tipikus alkalmazási területek közé tartoznak az iteratív megoldók (például Jacobi- vagy Gauss–Seidel-stencilek), a többszintű redukciók, a szemcsés részecskeszimulációk, valamint a mélytanulási kernelek bizonyos rétegei, ahol a blokk és a grid közötti finom adatcsere elengedhetetlen.

9.4.2 A kombinált minta általános szerkezete

Egy összetett, többlépcsős kernel általában a következő fázisokra bontható:

  1. Lokális számítás: minden blokk a saját, globális memóriából beolvasott adattartományán dolgozik, és az eredményt a saját shared memóriájában vagy regisztereiben tartja.
  2. Klaszterszintű együttműködés: a klaszter blokkjai kicserélik a szükséges részeredményeket a DSM-en keresztül, majd cluster.sync()-kel biztosítják, hogy minden blokk befejezte az írást, mielőtt bármelyikük olvasna.
  3. Grid-szintű szinkronizáció: amikor a klaszterek közötti adatcsere is szükséges – például egy újabb iteráció megkezdése előtt – a kernel eléri a this_grid().sync() pontot. Ez biztosítja, hogy az előző fázis minden klaszterben befejeződött.
  4. Második számítási fázis: a kernel a frissen elérhető adatokkal folytatja a munkát, például egy korrekciós lépést hajt végre, vagy egy következő időlépést számol.

Ez a minta akkor előnyös, ha a fázisok közötti adatmennyiség kicsi a számítási munkához képest, és ha a grid-szintű szinkronizáció ritkán következik be – tipikusan egy-egy iteráció végén. Ellenkező esetben a globális barrier miatt kialakuló várakozás felemésztheti a nyereséget.

A következő kódvázlat egy ilyen mintát mutat be vázlatos formában. A példa nem egy teljes, fordítható alkalmazás, hanem a szerkezet illusztrálására szolgál; a laborban ennél konkrétabb változatot építünk.

// CUDA C++ (illusztráció, nem teljes kernel)
#include <cooperative_groups.h>
namespace cg = cooperative_groups;

__global__ void combined_pattern_kernel(float* data, float* result, int n) {
    // 1. Blokkszintű csoport
    cg::thread_block block = cg::this_thread_block();
    
    // 2. Klaszter csoport (csak CC 9.0+; a klaszterméretet a launch konfiguráció adja meg)
    cg::thread_block_cluster cluster = cg::this_cluster();
    
    // 3. Lokális számítás: minden blokk kiszámítja a saját részeredményét
    //    (itt például egy tile feldolgozása)
    float local_sum = 0.0f;
    // ... adatbetöltés, számítás ...
    
    // 4. Klaszterszintű adatcsere DSM-en keresztül
    //    Tételezzük fel, hogy a klaszter minden blokkja egy parciális összeget ír
    //    a saját shared memóriájába. A klaszter.tömb segítségével lekérdezhetjük
    //    a klasztertársak shared memóriájának mutatóját.
    extern __shared__ float smem[];
    unsigned int cluster_rank = cg::this_cluster().block_rank();
    unsigned int cluster_size = cg::this_cluster().dim_blocks().x;
    
    // Feltételezés: minden blokk a saját shared memóriájának első elemébe írja a részösszeget
    if (block.thread_rank() == 0) {
        smem[0] = local_sum;
    }
    block.sync(); // biztosítjuk, hogy az írás befejeződött a blokkon belül
    
    // Klaszterszintű barrire: minden blokk elérte ezt a pontot, a DSM olvasható
    cluster.sync();
    
    // Klaszterszintű redukció: minden blokk kiolvassa a többi blokk részösszegét
    float cluster_sum = 0.0f;
    for (int i = 0; i < cluster_size; ++i) {
        // A DSM elérése: a klaszter i-edik blokkjának shared memóriáját olvassuk
        // A pontos API: cluster.map_shared_rank(...) vagy hasonló; itt leegyszerűsítve.
        float* remote_smem = cluster.map_shared_address(smem, i); // ellenőrizendő API
        cluster_sum += *remote_smem;
    }
    
    // 5. Grid-szintű szinkronizáció a klaszterek közötti adatcsere előtt
    cg::grid_group grid = cg::this_grid();
    grid.sync(); // minden blokk, minden klaszterben várakozik
    
    // 6. Második fázis: a klaszterek a friss adatokkal számolnak
    //    például normalizálják az eredményt a globális összeg alapján
    //    (feltételezzük, hogy egy globális bufferbe írták a klaszter_összegeket)
    // ...
}

Ebben a vázlatban jól látszik a három szint kombinációja: block.sync(), cluster.sync() és grid.sync(). A cluster.map_shared_address() hívás pontos szintaxisa a CUDA verziójától és a dokumentált API-tól függ; a példa csak a koncepciót mutatja, és a laborban a megfelelő, dokumentált formát használjuk.

9.4.3 Munkaelosztás a kombinált kernelben

A többlépcsős kernel egyik legfontosabb tervezési döntése, hogy a számítási munkát miként osztjuk fel a grid, a klaszter és a blokk szintjei között. A helyes felosztás határozza meg, hogy a szinkronizációs pontokon mennyi időt kell várakozni, és mennyire használjuk ki az SM-ek erőforrásait.

9.4.4 Hierarchikus tiling

A leggyakoribb megközelítés a hierarchikus lapkázás (tiling). A globális adattartományt négy szintre bonthatjuk:

  • Grid-szint: a rács felel az adatok nagy, diszjunkt tartományaiért. Kooperatív indítás esetén a rács mérete nem lehet nagyobb annál, amennyi blokk egyidejűleg rezidens az összes SM-en, ezért a tartományok száma korlátozott. Emiatt gyakran érdemes perzisztens kernel stílust használni: minden blokk egy for ciklusban több kisebb tartományt dolgoz fel (grid-stride loop), ahelyett hogy a rács mérete egyenlő lenne a feldolgozandó részek számával.
  • Cluster-szint: a klaszter a blokkok egy közeli csoportját fogja össze. A klaszteren belül a blokkok közösen fednek le egy nagyobb, összefüggő adatterületet, és a szomszédos határokon átnyúló adatcserét a gyors DSM-mel oldják meg. A klaszter méretét a hardverkorlát (jellemzően 8 blokk klaszterenként, de ez architektúrafüggő, ellenőrizendő) és a feladat szomszédsági szerkezete határozza meg.
  • Blokk-szint: egy blokk a klaszter által lefedett tartomány egy aldobozát kapja. A blokkméretet a memória-hozzáférési minták, a szükséges shared memória és a regiszterhasználat együttesen befolyásolják.
  • Warp- és thread-szint: a blokkon belül a warpok és threadek végeznek vektorizált betöltést és számítást. A cg::tile_partition segítségével a blokkot kisebb, önállóan szinkronizálható csoportokra oszthatjuk, ami lehetővé teszi finomabb párhuzamosítást.

A hierarchikus felosztás előnye, hogy minden szinten a lehető legkisebb kommunikációs távolságot használjuk: a leggyakoribb adatcsere a blokkon belül shared memórián, a ritkább klaszteren belül DSM-en, a legritkább pedig grid-szinten, globális memórián keresztül történik.

9.4.5 Példa: stencil iteratív megoldó

Vegyünk egy 2D hővezetési egyenletet explicit Euler-módszerrel. A szokásos megoldás minden iterációban kiszámítja a cellák új értékét a szomszédok alapján. A párhuzamosítás során a tartományt lapkákra osztjuk, és minden lapka szélén egy halo-réteget kell cserélni a szomszédos lapkákkal.

Kombinált együttműködéssel ez a következőképpen valósítható meg:

  1. Minden blokk betölti a saját lapkáját a globális memóriából, beleértve a halo-cellákat is, és a belső cellákat a shared memóriába másolja.
  2. A klaszter blokkjai közötti határokon a halo-cserét DSM-mel végezzük: a blokk megosztja a saját szélső celláit a szomszédos blokkal, majd cluster.sync() után minden blokk kiolvassa a szomszédos blokk megfelelő celláit.
  3. Minden blokk kiszámítja a következő iterációs értékeket a saját belső celláira.
  4. A klaszterek közötti határokon a halo-csere még mindig globális memórián keresztül zajlik. Itt jön be a grid-szintű szinkronizáció: miután minden blokk kiírta a szükséges szélső cellákat a globális memóriába, a grid.sync() biztosítja, hogy minden klaszter befejezte az írást, és a következő iteráció elején minden blokk biztonságosan beolvashatja a globális halo-t.
  5. A ciklus a következő iterációval folytatódik.

Ez a felépítés csökkenti a globális memórián keresztüli adatforgalmat, mert a klaszteren belüli határokon nem kell a lassú utat használni, csak a klaszterek közötti határokon. A grid-szinkronizáció itt csak iterációnként egyszer következik be, így a várakozási költsége eloszlik a teljes számítási munkán.

9.4.6 Perzisztens kernelek és grid-stride loop

A kooperatív indítás egyik következménye, hogy a rács mérete legfeljebb annyi blokk lehet, amennyi egyidejűleg rezidens. Ha egy problémához több független tartomány tartozik, mint amennyi blokk elfér, akkor a blokkoknak több tartományt kell feldolgozniuk. Ezt a gyakorlatban grid-stride loop segítségével érjük el:

// Grid-stride loop perzisztens kernelben (vázlat)
__global__ void persistent_kernel(float* data, int n) {
    cg::grid_group grid = cg::this_grid();
    for (int tid = blockIdx.x * blockDim.x + threadIdx.x; tid < n; tid += gridDim.x * blockDim.x) {
        // feldolgozás
    }
    // időszakos grid-szinkronizáció, ha szükséges
    if (need_sync) grid.sync();
}

Ez lehetővé teszi, hogy a kernel a teljes futás alatt az eszközön maradjon, és a globális barrierrel szabályozza a fázisokat. A grid-stride loop azonban gondos indexelést igényel, különösen akkor, ha a grid.sync() a loop belsejében van: a ciklusfeltételnek minden blokkban azonosan kell viselkednie, különben holtpont alakul ki.

9.4.7 Szinkronizációs szabályok és gyakori hibák

A kombinált minta helyessége szempontjából a legfontosabb, hogy minden szinten betartsuk a csoportokra vonatkozó kollektív hívások szabályait. A leggyakoribb hibák a következők:

9.4.8 1. Hiányzó vagy nem kollektív sync

A cluster.sync() és a grid.sync() kollektív művelet: a csoport minden tagjának ugyanazt a hívást kell végrehajtania, vezérlésfüggő ágakon kívül. Ha például egy blokk egy if feltétel miatt kihagyja a cluster.sync() hívást, a többi blokk örökre várakozni fog.

Hibás minta:

// HIBÁS: a sync feltételes ágban van, nem minden blokk éri el
__global__ void bad_cluster_sync(float* data) {
    cg::thread_block_cluster cluster = cg::this_cluster();
    if (threadIdx.x == 0) {
        // csak egyetlen thread végzi el a munkát, de a sync az egész blokkra vonatkozik
        // ...
        cluster.sync(); // HIBA: itt csak a 0. thread hívja, a többi nem
    }
    // a többi thread soha nem jut el ide, mert a sync-et várja
}

Helyes megoldás: a szinkronizálást a csoport minden tagjának, minden feltételtől függetlenül el kell érnie, vagy a feltételt úgy kell megfogalmazni, hogy a csoport minden tagja azonos döntést hozzon. A klasszikus blokkszintű szinkronizációhoz hasonlóan a cluster.sync()-et is a lehető legegyszerűbb vezérlési útra kell helyezni.

9.4.9 2. A grid-szinkronizáció nem kooperatív indítással

A cg::this_grid().sync() csak akkor biztonságos, ha a kernelt kooperatív indítással futtattuk, és a rács minden blokkja egyszerre rezidens. Ha egyszerű <<<grid, block>>> indítást használunk, a futtatókörnyezet nem garantálja, hogy minden blokk egyszerre fut, így a barrier várakozása holtponthoz vezethet.

Hibás minta:

// HIBÁS: grid.sync() normál <<< >>> indítással
__global__ void bad_grid_sync() {
    cooperative_groups::grid_group grid = cooperative_groups::this_grid();
    grid.sync(); // VESZÉLYES: normál indításnál deadlock lehet
}

// hívás:
// bad_grid_sync<<<num_blocks, block_size>>>();

Helyes megoldás: a kernelt cudaLaunchCooperativeKernel függvénnyel kell indítani, és előtte ellenőrizni kell, hogy a kívánt blokkszám és egyéb erőforrások lehetővé teszik-e a kooperatív futást. A cudaOccupancyMaxActiveBlocksPerMultiprocessor segítségével meghatározható, hogy hány blokk lehet rezidens egy SM-en, és ebből a maximális rácsméret.

// Helyes vázlat: kooperatív indítás
int numBlocksPerSm = 0;
cudaOccupancyMaxActiveBlocksPerMultiprocessor(&numBlocksPerSm, kernel, blockSize, smemSize);
int maxBlocks = numBlocksPerSm * numSMs;
if (gridDim > maxBlocks) {
    // csökkenteni kell a grid méretét vagy más stratégiát használni
}
void* args[] = { ... };
cudaLaunchCooperativeKernel((void*)kernel, dim3(gridDim), dim3(blockSize), args, smemSize, stream);

A grid méretének ellenőrzése kötelező, mert a hardver erőforrás-korlátai miatt előfordulhat, hogy a kért blokkszám nem fér el egyszerre. A túl nagy grid méret a cudaErrorCooperativeLaunchTooLarge hibát eredményezi, vagy rosszabb esetben definiálatlan viselkedést.

9.4.10 3. DSM hozzáférés cluster.sync nélkül

A Distributed Shared Memory lehetővé teszi, hogy egy blokk olvassa egy másik, ugyanabban a klaszterben lévő blokk shared memóriáját. Az olvasás előtt azonban biztosítani kell, hogy a forrásblokk befejezte az írást. Ezt a cluster.sync() hívás garantálja, amely a klaszter összes blokkját szinkronizálja.

Hibás minta:

// HIBÁS: DSM olvasás cluster.sync() nélkül
__global__ void bad_dsm_access(float* data) {
    cg::thread_block_cluster cluster = cg::this_cluster();
    extern __shared__ float smem[];
    
    if (cluster.block_rank() == 0) {
        smem[0] = 1.0f; // 0. blokk ír
    }
    // HIÁNYZIK a cluster.sync()
    
    float* remote = cluster.map_shared_address(smem, 0);
    float val = remote[0]; // versenyhelyzet: lehet, hogy az írás még nem történt meg
}

Helyes megoldás: minden DSM írás után, de még a DSM olvasás előtt hívjuk meg a cluster.sync()-et. A block.sync() nem elegendő, mert az csak a blokkon belüli láthatóságot biztosítja, a többi blokk számára nem.

9.4.11 4. A cluster méret és a hardverkorlát figyelmen kívül hagyása

A klaszterek mérete architektúrafüggő. A Hopper (CC 9.0) példájában a maximális klaszterméret jellemzően 8 blokk, de ez a pontos CUDA verziótól és a GPU típusától függ. A klaszter dimenzióit a launch konfigurációban kell megadni, és a kernelben a this_cluster() által visszaadott csoport dimenziói a ténylegesen elindított értéket tükrözik. Ha a kód feltételezi, hogy a klaszter mindig egy bizonyos méretű, akkor a hordozhatóság sérül.

Helyes megoldás: a kernelben dinamikusan kérdezzük le a klaszter dimenzióit, és a kódot úgy írjuk meg, hogy bármilyen támogatott méretre működjön, vagy fordítási időben ellenőrizzük a feltételeket és static_assert-et használunk a nem támogatott esetek kiszűrésére.

9.4.12 Teljesítmény és hordozhatóság

A kombinált együttműködési minták teljesítménye erősen függ attól, hogy a szinkronizációs pontok mennyire ritkák, és hogy a DSM-mel kiváltott globális memóriaforgalom mekkora megtakarítást eredményez.

9.4.13 Klaszter előnyei

A klaszter használatának legnagyobb előnye a blokkok közötti kommunikáció felgyorsítása. A DSM hozzáférés késleltetése lényegesen alacsonyabb, mint a globális memória elérése, ezért az olyan minták, amelyek gyakori szomszédos blokkok közötti adatcserét igényelnek, jelentős sávszélesség-megtakarítást érhetnek el. A klaszter emellett lehetővé teszi a shared memória együttes kihasználását: a klaszter teljes shared memóriája az egyes blokkok erőforrásainak összege, ami nagyobb, összefüggő tartományok lapkázását teszi lehetővé anélkül, hogy az adatot a globális memórián keresztül kellene mozgatni.

Ugyanakkor a klaszter használata növeli a regiszter- és shared memória nyomást, mert a blokkoknak további indexelést és címszámítást kell végezniük. A cluster.sync() hívás is többletköltséggel jár, ezért érdemes megfontolni, hogy egy adott feladatban tényleg szükség van-e klaszterre, vagy a hagyományos blokkszintű megoldás is elegendő.

9.4.14 Grid-szinkronizáció költsége

A grid.sync() a teljes rácsot szinkronizálja, ami azt jelenti, hogy a leglassabb blokk befejeződéséig minden más blokk várakozik. A várakozási idő a blokkok munkamennyiségének kiegyensúlyozatlanságától függ: ha az egyes blokkok terhelése eltérő, a barrier miatt a leggyorsabb blokkok is a leglassabbhoz igazodnak. Ezért a grid-szintű szinkronizációt lehetőleg ritkán, és csak akkor érdemes használni, ha a fázisok közötti adatfüggőség valóban megköveteli.

Ráadásul a kooperatív indítás korlátozza a rács méretét, ami csökkentheti az occupancy-t, ha a kernel egyébként sok blokkal jobban skálázna. A perzisztens kernelek és a grid-stride loop ezt a korlátot enyhítik, de a tervezés során mindig mérni kell, hogy a grid-szinkronizációból származó nyereség ellensúlyozza-e a kisebb rács miatti veszteséget.

9.4.15 Hordozhatósági megfontolások

A kombinált minták hordozhatósága két szinten korlátozott:

  • Hardver-szint: a klaszterek csak a Hopper (CC 9.0) és újabb architektúrákon érhetők el. A grid-szinkronizáció viszont már a Pascal (CC 6.0) óta támogatott, de a pontos feltételek (kooperatív indítás, maximális rácsméret) architektúránként változnak. A kódot ezért érdemes úgy megírni, hogy a klasztert igénylő részeket feltételes fordítás és futásidejű ellenőrzés védje.
  • Szoftver-szint: a Cooperative Groups API a CUDA 9.0 óta elérhető, de a thread_block_cluster és a DSM csak a CUDA 11.8/12.0 környékén, a Hopper támogatással együtt jelent meg. A pontos verziókat a fejlesztői dokumentáció adott kiadásában ellenőrizni kell; e sorok írásakor a klaszterek a CUDA 12.x-es eszközlánccal és CC 9.0-val működnek, de ez a jövőben változhat.

A gyakorlatban a hordozhatóság érdekében a következő stratégiát érdemes követni:

  1. A kernel magját úgy írjuk meg, hogy a thread_block és tile_partition szintű együttműködés mindig elérhető legyen, mert ezek a legszélesebb körben támogatottak.
  2. A klasztert használó kódot külön függvénybe vagy fordítási egységbe szervezzük, és #ifdef-fel vagy futásidejű cudaDeviceGetAttribute ellenőrzéssel kapcsoljuk be, ha az eszköz támogatja.
  3. A grid-szinkronizációt igénylő részt úgy tervezzük, hogy alternatív, többszöri kernelindításon alapuló megoldás is létezzen azokra az eszközökre, ahol a kooperatív indítás nem elérhető vagy nem hatékony.

OpenCL-ben a munkacsoportok (work-group) közötti közvetlen szinkronizáció és megosztott memória nem része a hordozható mag szabványnak; a hasonló mintát általában több kernelindítással vagy atomi műveletekkel kell megvalósítani. JAX/XLA esetében a magas szintű, gráf alapú modell elrejti a blokkok közötti kommunikációt, így az ilyen finomhangolású együttműködés nem közvetlenül alkalmazható.

9.4.16 Labor: többlépcsős kernel tervezése

Az alábbi labor célja, hogy a kombinált együttműködési mintát egy mérhető, ellenőrizhető példán keresztül gyakorolja. A labor a klaszter és a grid-szinkronizáció együttműködését egy iteratív stencilszámításon keresztül mutatja be.

9.4.17 Feladatleírás

Valósítson meg egy 2D hővezetési szimulációt explicit Euler-módszerrel, amely a következő lépésekből áll:

  • A tartomány N x N rács, ahol minden cella egy float érték.
  • Minden iterációban az új érték a négy közvetlen szomszéd átlagával egyenlő:
    u_new[i][j] = 0.25f * (u[i-1][j] + u[i+1][j] + u[i][j-1] + u[i][j+1]).
  • A kernel egyetlen kooperatív indítással futtatja a szimulációt T iteráción keresztül.
  • A tartományt a grid blokkjai lapkákra osztják. A klaszterek a lapkák egy csoportját fogják össze, és a klaszteren belüli szomszédos lapkák közötti halo-cserét DSM-mel végzik. A klaszterek közötti határokon a halo-csere globális memórián keresztül történik, és ezt this_grid().sync() szinkronizálja minden iteráció végén.

A labor kódja CUDA C++ nyelvű, és legalább a következő komponenseket tartalmazza:

  • Kooperatív kernel indítása cudaLaunchCooperativeKernel-lel.
  • Blokkszintű csoport cg::this_thread_block() használata.
  • Klaszter csoport cg::this_cluster() és DSM hozzáférés.
  • Grid csoport cg::this_grid() és grid.sync().
  • Hibakezelés: minden CUDA API-hívás ellenőrzése.

A pontos implementációt a fejezet kódmelléklete tartalmazza; itt a legfontosabb vázlatot mutatjuk be.

9.4.18 Kernelvázlat

// CUDA C++ – labor vázlat (nem teljes, de a szerkezetet mutatja)
#include <cooperative_groups.h>
#include <cuda_runtime.h>
namespace cg = cooperative_groups;

// Stencil kernel: T iterációt futtat egyetlen kooperatív indítással
__global__ void stencil_cooperative(const float* __restrict__ u_old,
                                    float* __restrict__ u_new,
                                    int N, int T) {
    cg::thread_block block = cg::this_thread_block();
    cg::thread_block_cluster cluster = cg::this_cluster();
    cg::grid_group grid = cg::this_grid();

    // lapka méretek: TILE_X, TILE_Y (befordítva)
    // határok, indexelés...
    extern __shared__ float smem[]; // saját shared memória

    for (int iter = 0; iter < T; ++iter) {
        // 1. Betöltés globális memóriából a shared memóriába,
        //    beleértve a halo cellákat is.
        load_tile(u_old, smem, N);

        // 2. Klaszteren belüli halo-csere DSM-mel.
        //    A klasztertársakkal megosztjuk a szélső cellákat.
        exchange_halo_cluster(smem, cluster);
        cluster.sync();

        // 3. Számítás: a belső cellák új értéke.
        compute_interior(smem, block);

        // 4. Klaszterek közötti halo-csere globális memórián keresztül.
        //    Írjuk a szükséges szélső cellákat egy átmeneti bufferbe.
        write_global_halo(u_new, smem, N);

        // 5. Grid-szinkronizáció: minden blokk befejezte az írást,
        //    mielőtt a következő iterációban olvasná a globális halo-t.
        grid.sync();

        // 6. A következő iterációhoz olvassuk a frissített értékeket.
        //    (Az egyszerűség kedvéért itt u_old <-> u_new cserét feltételezünk.)
    }
}

// Indítási függvény
void run_stencil(const float* d_u0, float* d_u1, int N, int T, 
                 dim3 grid, dim3 block, int smem_size, cudaStream_t stream) {
    void* args[] = { (void*)&d_u0, (void*)&d_u1, (void*)&N, (void*)&T };
    cudaError_t err = cudaLaunchCooperativeKernel(
        (void*)stencil_cooperative, grid, block, args, smem_size, stream);
    CHECK_CUDA_ERROR(err);
}

A fenti vázlatban a load_tile, exchange_halo_cluster, compute_interior és write_global_halo eszközfüggvények a tényleges számítást végzik; ezek implementálása a laborfeladat része. A halo-csere pontos DSM indexelése a CUDA dokumentációban leírt map_shared_rank és map_shared_address API-t használja, amelyet a labor kódjában ellenőrizni kell.

9.4.19 Build és futtatási környezet

A méréshez rögzíteni kell a következő környezetet (példaértékek; a tényleges laborban a mért értékeket kell feltüntetni):

  • GPU: NVIDIA H100 (vagy más CC 9.0+), például H100 PCIe 80 GB
  • Driver: 535.104.05 (példa)
  • CUDA: 12.3
  • Operációs rendszer: Ubuntu 22.04 LTS
  • Fordító: nvcc V12.3.103

Build parancs (vázlat):

nvcc -arch=sm_90 -rdc=true -o stencil_lab stencil_lab.cu -I.

Futtatás:

./stencil_lab --N 4096 --T 100 --block 256 --cluster 4

A -rdc=true az eszközkód szétválasztott fordításához szükséges lehet, ha a kooperatív csoportok használata ezt megköveteli; a pontos szükségletet a CUDA verziója és a kód szerkezete határozza meg.

9.4.20 Mérési napló és kiértékelés

A futás során mérjük a kernel végrehajtási idejét, és hasonlítsuk össze egy olyan baseline verzióval, amely nem használ klasztert és grid-szinkronizációt, hanem minden iterációt külön kernelindítással végez el. A méréshez legalább 5–10 ismétlést végezzünk, és az átlag mellett a szórást is közöljük.

Példa mérési táblázat:

Verzió Grid méret Blokk méret Klaszterméret Átlagidő (ms) Szórás (ms) Megjegyzés
Baseline (külön kernelek) 64×64 16×16 – 12.4 0.8 minden iteráció új kernel
Kooperatív, klaszter nélkül 64×64 16×16 – 10.9 0.6 grid.sync minden iterációban
Kooperatív, klaszterrel 64×64 16×16 4 blokk 9.1 0.5 DSM a klaszteren belüli halo-ra

A pontos számok a labor során mért értékektől függenek; a fenti táblázat csak a szerkezetet mutatja. A mérési naplóban fel kell tüntetni a GPU órajelét, a power limitet, az ECC állapotát és a háttérterhelést is, mert ezek befolyásolják az eredményt.

Az ellenőrzéshez számítsuk ki a szimulációt CPU-n (például egy egyszerű C++ implementációval), és hasonlítsuk össze a GPU eredményeket az FP32 pontosság keretein belül. A hiba jellemzően kicsi, de az iteratív algoritmusoknál a felhalmozódó kerekítések miatt nem nulla; a laborban adjuk meg a maximális abszolút hibát.

9.4.21 Ellenőrző kérdés

A fejezet lezárásaként válaszolja meg a következő kérdést:

Milyen feltételek mellett biztonságos a this_grid().sync() hívása egy kernelben, és mi történik, ha a rács egyik blokkja nem éri el ezt a hívást?

A helyes válasznak tartalmaznia kell, hogy a kernelnek kooperatív indítással kell futnia, a rács minden blokkjának egyidejűleg rezidensnek kell lennie, és a szinkronizálási hívásnak minden blokkban ugyanazon a vezérlési úton kell elhelyezkednie. Ha egy blokk nem éri el a hívást, a többi blokk örökre várakozik, ami holtponthoz vezet.

9.4.22 Összegzés

A Cooperative Groups eszköztárának kombinált használata lehetővé teszi olyan összetett, többlépcsős kernelek írását, amelyek a blokkszintű finom szinkronizációt, a klaszteren belüli gyors adatcserét és a grid-szintű fázisvezérlést egyetlen kernelben egyesítik. A minta hatékonysága azon múlik, hogy a munkaelosztást hierarchikusan tervezzük-e, a szinkronizációs pontokat ritkán és szabályosan helyezzük-e el, valamint hogy tiszteletben tartjuk-e a hardver- és szoftverkorlátokat. A laborban mért eredmények azt mutatják, hogy a klaszterekkel támogatott DSM csökkentheti a globális memóriaforgalmat, és a kooperatív indítással elkerülhető a többszöri kernelindítás overheadje, de a pontos nyereség erősen függ a probléma méretétől és a GPU architektúrájától. A következő fejezet a CUDA hibakezelésének és debuggolásának részleteivel foglalkozik, amely a kombinált minták helyességének ellenőrzéséhez is elengedhetetlen.
