24.2 Convolution kernelek

A konvolúciós réteg a mélytanulási hálózatok egyik legnagyobb számítási igényű komponense. A GPU-kon két fő megközelítés terjedt el: a konvolúciót vagy közvetlenül, dedikált kernelben számítjuk, vagy visszavezetjük egy általános mátrixszorzásra (GEMM). Ez a szakasz a két utat, az im2col és az implicit GEMM technikát, valamint a csatorna- és tile-kezelést tárgyalja. A korábbi fejezet (GEMM és a deep learning) bevezette a GEMM optimalizálását; itt azt használjuk ki, hogy a konvolúció nagy része GEMM-mé alakítható, de a közvetlen kernel is nélkülözhetetlen, ha a memória- vagy számítási mintázat ezt indokolja.

24.2.1 A konvolúció definíciója és dimenziói

Legyen a bemeneti tenzor XX mérete N×C×H×WN \times C \times H \times W, ahol NN a batch, CC a bemeneti csatornák, H,WH,W a térbeli dimenziók. A szűrő WfW_f mérete K×C×R×SK \times C \times R \times S, ahol KK a kimeneti csatornák, R,SR,S a szűrő magassága és szélessége. A kimeneti tenzor YY mérete N×K×P×QN \times K \times P \times Q, ahol P,QP,Q a kimeneti magasság és szélesség. A kimeneti elem számítása:

y[n,k,p,q]=∑c=0C−1∑r=0R−1∑s=0S−1x[n,c,p⋅stride−pad+r,q⋅stride−pad+s]⋅w[k,c,r,s]+b[k] y[n,k,p,q] = \sum_{c=0}^{C-1}\sum_{r=0}^{R-1}\sum_{s=0}^{S-1} x[n,c, p\cdot \mathrm{stride} - \mathrm{pad} + r,\; q\cdot \mathrm{stride} - \mathrm{pad} + s] \cdot w[k,c,r,s] + b[k]

ahol b[k]b[k] a bias, a padding és stride paraméterek pedig a határkezelést és a lépésközt szabályozzák. A képletben a bemeneti indexek negatívak vagy túl nagyok lehetnek, ilyenkor az értéket nullának tekintjük (zero padding), vagy más határkezelést alkalmazunk (reflect, replicate). A gyakorlatban a legtöbb CNN-réteg stride=1, pad=1, 3×3-as szűrőt használ, így a kimenet mérete megegyezik a bemenettel.

A számítási igény: minden kimeneti elemhez C⋅R⋅SC \cdot R \cdot S szorzás-összeadás tartozik, így a teljes FLOP mennyiség N⋅K⋅P⋅Q⋅C⋅R⋅SN \cdot K \cdot P \cdot Q \cdot C \cdot R \cdot S. Egy tipikus rétegben ez milliárd nagyságrendű lehet, ezért a memóriahasználat és az adatmozgatás optimalizálása döntő.

24.2.2 A konvolúció mint GEMM: im2col és implicit GEMM

A GEMM-alapú megközelítés lényege, hogy a konvolúciót egy mátrixszorzássá alakítjuk. Ehhez a bemeneti tenzort egy kétdimenziós mátrixba rendezzük, a szűrőt pedig egy másik mátrixba.

24.2.3 im2col

Az im2col eljárás minden kimeneti pixelhez kiválasztja a bemeneti tenzor azon elemeit, amelyek a szűrővel szorozódnak, és ezeket egy sorba rendezi. Az így kapott AA mátrix mérete NPQ×CRSN\!P\!Q \times C\!R\!S, ahol minden sor egy kimeneti pixel bemeneti ablakának lineáris kiterítése. A szűrőből képzett BB mátrix mérete CRS×KC\!R\!S \times K, mert minden kimeneti csatornához tartozik egy oszlop, amely a szűrő összes súlyát tartalmazza. Ekkor a konvolúció:

Y=A⋅B+b Y = A \cdot B + b

ahol YY mérete NPQ×KN\!P\!Q \times K. Ezután a GEMM kernel (például a GEMM és a deep learning alfejezetben tárgyalt tiling és shared memory optimalizálással) közvetlenül alkalmazható.

Az im2col előnye, hogy a jól optimalizált GEMM kernel újrahasznosítható, és a konvolúciót pusztán mátrixszorzásként kezelhetjük. Hátránya viszont a jelentős memória overhead: az AA mátrix mérete C⋅R⋅SC\cdot R\cdot S-szeresére növeli a bemeneti adatmennyiséget, és ez a másolat a globális memóriában tárolandó. Egy 3×3-as, 64 bemeneti csatornás rétegnél ez 576-szoros adatduplikációt jelent. Ez nagy memóriát és sávszélességet fogyaszt, ezért a gyakorlatban gyakran kerülik a tényleges materializálást.

24.2.4 Implicit GEMM

Az implicit GEMM elkerüli az AA mátrix fizikai létrehozását. A GEMM kernel indexelését módosítjuk úgy, hogy az AA mátrix elemeit menet közben, a bemeneti tenzorból számolja ki. A GEMM tiling és a shared memory használata megmarad, de a betöltéskor az eredeti bemeneti tenzorból olvasunk, a szükséges indexeket a konvolúciós paraméterekből számítva. Az implicit GEMM tehát a GEMM kernel számítási magját használja, de a memória-hozzáférést a konvolúcióra optimalizálja.

A CUTLASS könyvtár például implicit GEMM-et használ a konvolúciós rétegekhez. A kernelben a GEMM MM dimenziója a batch és a kimeneti pixelek száma (N⋅P⋅QN \cdot P \cdot Q), az NN dimenzió a kimeneti csatornák száma KK, a KK dimenzió pedig a bemeneti csatornák és a szűrőterület szorzata C⋅R⋅SC \cdot R \cdot S. A tiling a GEMM szabályai szerint történik, de az AA mátrix betöltésekor az indexeket a bemeneti tenzorból számítjuk.

24.2.5 Közvetlen convolution kernel

A közvetlen kernelben nem alakítjuk GEMM-re, hanem minden szál közvetlenül a konvolúciós összeget számolja. A legegyszerűbb változatban minden szál egy kimeneti elemet állít elő, és bejárja a bemeneti csatornákat, a szűrőt. Az alábbi CUDA C++ kód ezt mutatja be:

// CUDA C++ (C++17), naiv conv2d kernel
// Feltételezés: stride=1, pad=1, zero padding
__global__ void conv2d_naive(const float* __restrict__ x,
                              const float* __restrict__ w,
                              float* __restrict__ y,
                              int N, int C, int H, int W,
                              int K, int R, int S,
                              int P, int Q, int pad, int stride) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    int total = N * K * P * Q;
    if (idx >= total) return;

    int q = idx % Q;
    int p = (idx / Q) % P;
    int k = (idx / (Q * P)) % K;
    int n = idx / (Q * P * K);

    float acc = 0.0f;
    for (int c = 0; c < C; ++c) {
        for (int r = 0; r < R; ++r) {
            int h = p * stride - pad + r;
            for (int s = 0; s < S; ++s) {
                int w_in = q * stride - pad + s;
                if (h >= 0 && h < H && w_in >= 0 && w_in < W) {
                    acc += x[((n * C + c) * H + h) * W + w_in] *
                           w[((k * C + c) * R + r) * S + s];
                }
            }
        }
    }
    y[idx] = acc;
}

A kernel a szálak lineáris indexét osztja fel a kimeneti dimenziókra. A memória-hozzáférés azonban nem optimális. A szomszédos szálak (szomszédos qq értékek) a bemenet különböző ablakait olvassák, amelyek átfednek ugyan, de a hozzáférés nem folytonos, így a globális memória tranzakciók nem coalescingek. Ráadásul minden szál újraolvassa a szűrőt, ami bár kicsi, de a gyorsítótáron kívül eshet.

A közvetlen kernel tipikus hibái:

  • Határkezelés elmaradása: ha a padding miatt negatív vagy túl nagy index keletkezik, a memória-hozzáférés érvénytelen. A fenti kódban az if feltétel véd, de ez divergenciát okoz a warpban, ha a szálak különböző határhelyzetben vannak.
  • Uncoalesced hozzáférés: a bemeneti tenzor indexelése nem folytonos, mert a szálak a kimeneti térben szomszédosak, de a bemeneti ablakok eltolódnak. Ez a globális memória sávszélesség kihasználatlanságához vezet.
  • Szűrő ismételt betöltése: minden szál a teljes szűrőt olvassa, ami redundáns globális memória forgalmat okoz. Bár a szűrő kicsi, nagy batch és kimeneti csatorna esetén a forgalom jelentős lehet.
  • Divergencia a határokon: a padding és a szélek miatt az if feltétel warp-divergenciát okoz, ami csökkenti a kihasználtságot.

24.2.6 Csatorna és tile

A konvolúció teljesítményét alapvetően a csatornák kezelése és a tile-ok határozzák meg. A bemeneti csatornák száma CC gyakran 64, 128 vagy akár 512, a kimeneti csatornák száma KK hasonló nagyságrendű. A számítási hurokban a csatornák feletti összegzés a legbelső ciklus, ezért a csatorna dimenzió optimalizálása kulcsfontosságú.

24.2.7 Csatorna-loop és csatorna-tiling

A naiv kernelben a csatorna loop a legbelső, minden szál a teljes CC csatornát bejárja. Ez azt jelenti, hogy a szálak újra és újra ugyanazokat a bemeneti csatornákat olvassák, de mivel a szomszédos kimeneti pixelekhez ugyanazokra a bemeneti csatornákra van szükség, a hozzáférés redundáns. A shared memory tiling ezt úgy oldja meg, hogy egy blokk egy kimeneti tile-t számol, és a bemeneti csatornák egy-egy csoportját közösen tölti be a shared memoryba. A csatornákat kifelé visszük, és a szűrő megfelelő részét is a shared memoryba tesszük. Így a globális memória forgalom a csatornák számával osztódik, mert minden bemeneti elemet csak egyszer olvasunk be a blokk számára.

24.2.8 Bemeneti tile és halo

A kimeneti tile TH×TWT_H \times T_W pixelből áll. A hozzá tartozó bemeneti ablak mérete (TH+R−1)×(TW+S−1)(T_H + R - 1) \times (T_W + S - 1), ha stride=1. Ezt a bemeneti tile-t kell a shared memoryba tölteni. A halo a szűrő méretéből adódó átfedés: a szomszédos kimeneti pixelek bemeneti ablakai átfednek, ezért a tile szélein a szomszédos blokkok bemeneti elemeit is be kell tölteni. A halo mérete ⌊R/2⌋\lfloor R/2 \rfloor és ⌊S/2⌋\lfloor S/2 \rfloor mindkét oldalon. A shared memory mérete tehát (TH+2⋅⌊R/2⌋)×(TW+2⋅⌊S/2⌋)(T_H + 2 \cdot \lfloor R/2 \rfloor) \times (T_W + 2 \cdot \lfloor S/2 \rfloor) (ha a csatornák egyelőre egyesével töltődnek).

A betöltés során a szálak a bemeneti tenzorból olvasnak. Fontos, hogy a hozzáférés coalescing legyen: a szálak úgy legyenek kiosztva, hogy a szomszédos szálak a bemeneti tenzor szomszédos elemeit olvassák. Ez általában úgy érhető el, ha a betöltő ciklusban a szálak lineáris indexét a bemeneti tile lineáris memóriájára képezzük, nem pedig a kimeneti pixelekre.

24.2.9 Szűrő tiling

A szűrőt is érdemes a shared memoryba tölteni, mert minden szál ugyanazt a szűrőt használja. A szűrő mérete K×C×R×SK \times C \times R \times S, ami nagy lehet. A gyakorlatban a szűrőt a csatorna-tilinggel együtt kezelik: egy blokk a szűrő egy szeletét (például egy kimeneti csatornához tartozó összes súlyt, vagy annak egy részét) tölti be, és a kimeneti csatornák egy részét számolja. Ez csökkenti a shared memory igényt és lehetővé teszi a csatorna-loop kifelé vitelét.

24.2.10 Bank conflict elkerülése

A shared memoryba való betöltéskor és onnan való olvasáskor ügyelni kell a bank конфликтokra. A bemeneti tile-t gyakran úgy rendezik, hogy a szélesség paddinget kap, például 32+1 oszloppal, hogy a szomszédos szálak ne ugyanabba a bankba írjanak. A szűrő esetében a súlyok lineáris elrendezése általában nem okoz konfliktust, mert az olvasás minta egyszerű.

24.2.11 Gyakorlati CUDA implementáció: közvetlen kernel shared memory tiling

Az alábbiakban egy egyszerűsített, de működő tiled conv2d kernelt mutatunk be. A példa a labor alapját képezi, ezért a feltételezések: batch=1, bemeneti csatorna C=1C=1, kimeneti csatorna K=1K=1, szűrő 3×3, stride=1, pad=1. A bemenet mérete 32×3232 \times 32, a kimenet 32×3232 \times 32. Ez a minimalista eset jól mutatja a tiling előnyeit anélkül, hogy a csatorna-loop bonyolítaná a kódot. A valós alkalmazásokban a csatornák száma nagyobb, és a kernel bővíthető, de az alapelvek ugyanazok.

// CUDA C++ (C++17), conv2d shared memory tiling
// Feltételezés: C=1, K=1, R=S=3, stride=1, pad=1, batch=1
#define TILE_H 16
#define TILE_W 16
#define R 3
#define S 3

// Hibakezelő makró (a laborban kötelező)
#define CHECK_CUDA(call) {                                    \
    cudaError_t err = call;                                   \
    if (err != cudaSuccess) {                                 \
        std::cerr << "CUDA hiba: " << cudaGetErrorString(err) \
                  << " (" << __FILE__ << ":" << __LINE__ << ")" \
                  << std::endl;                               \
        exit(EXIT_FAILURE);                                   \
    }                                                         \
}

__global__ void conv2d_tiled(const float* __restrict__ x,
                              const float* __restrict__ w,
                              float* __restrict__ y,
                              int H, int W, int P, int Q) {
    // Tegyük fel, hogy P=H, Q=W (same padding)
    __shared__ float smem[TILE_H + 2][TILE_W + 2]; // bemeneti tile + halo
    // Szűrő súlyait regiszterben tartjuk (mert kicsi)
    float w0 = w[0], w1 = w[1], w2 = w[2];
    float w3 = w[3], w4 = w[4], w5 = w[5];
    float w6 = w[6], w7 = w[7], w8 = w[8];

    int tx = threadIdx.x;
    int ty = threadIdx.y;
    int out_x = blockIdx.x * TILE_W + tx;   // kimeneti x koordináta
    int out_y = blockIdx.y * TILE_H + ty;   // kimeneti y koordináta

    // Bemeneti tile betöltése a shared memoryba
    // A tile mérete (TILE_H+2) x (TILE_W+2)
    int smem_idx = ty * (TILE_W + 2) + tx;  // lineáris index a betöltéshez
    int total_smem = (TILE_H + 2) * (TILE_W + 2);
    for (int i = smem_idx; i < total_smem; i += blockDim.x * blockDim.y) {
        int smem_y = i / (TILE_W + 2);
        int smem_x = i % (TILE_W + 2);
        int glob_y = blockIdx.y * TILE_H - 1 + smem_y; // -1 a halo miatt
        int glob_x = blockIdx.x * TILE_W - 1 + smem_x;
        if (glob_y >= 0 && glob_y < H && glob_x >= 0 && glob_x < W) {
            smem[smem_y][smem_x] = x[glob_y * W + glob_x];
        } else {
            smem[smem_y][smem_x] = 0.0f; // zero padding
        }
    }
    __syncthreads();

    if (out_x < Q && out_y < P) {
        float acc = 0.0f;
        for (int r = 0; r < R; ++r) {
            for (int s = 0; s < S; ++s) {
                // A bemeneti tile-ban a megfelelő pozíció:
                // out_y - blockIdx.y*TILE_H + 1 + r, stb.
                int smem_y = ty + r;   // mivel a halo az elején van
                int smem_x = tx + s;
                acc += smem[smem_y][smem_x] * w[r * S + s];
            }
        }
        y[out_y * Q + out_x] = acc;
    }
}

A kernel a blokk méretét dim3(16,16)-nak feltételezi, a grid mérete pedig dim3((W+TILE_W-1)/TILE_W, (H+TILE_H-1)/TILE_H). A shared memory mérete (16+2)×(16+2)=18×18(16+2)\times(16+2)=18\times18 float, ami 1296 bájt. A szűrőt regiszterekben tartjuk, mert 9 elem kicsi.

A betöltő ciklusban a szálak lineárisan járják be a shared memory területet, így a globális memória-hozzáférés coalescing lesz, ha a szomszédos szálak szomszédos bemeneti elemeket olvasnak. A padding kezelése az if feltétellel történik, ami némi divergenciát okoz a határokon, de a blokk belsejében a feltétel igaz.

A kernel indítása:

dim3 block(TILE_W, TILE_H); // 16x16
dim3 grid((32 + TILE_W - 1) / TILE_W, (32 + TILE_H - 1) / TILE_H); // 2x2
conv2d_tiled<<<grid, block>>>(d_x, d_w, d_y, H, W, P, Q);

A hibakezeléshez a kernel indítása után CHECK_CUDA(cudaGetLastError()); és CHECK_CUDA(cudaDeviceSynchronize()); szükséges.

A labor célja egy közvetlen conv2d kernel implementálása, futtatása és mérése. A feladat az iménti tiled kernel és egy naiv kernel összehasonlítása. A kódot izolált környezetben futtatjuk, a hibás kernel esetén timeout beállítással.

24.2.13 Kiinduló kód

A laborhoz a fenti conv2d_tiled kernelt és a naiv conv2d_naive kernelt használjuk. A naiv kernel a korábban bemutatott, de a C=1, K=1 esetre egyszerűsítve:

// CUDA C++ (C++17), naiv conv2d (C=1, K=1)
__global__ void conv2d_naive(const float* __restrict__ x,
                              const float* __restrict__ w,
                              float* __restrict__ y,
                              int H, int W, int P, int Q,
                              int pad, int stride) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    int total = P * Q;
    if (idx >= total) return;
    int q = idx % Q;
    int p = idx / Q;
    float acc = 0.0f;
    for (int r = 0; r < 3; ++r) {
        int h = p * stride - pad + r;
        for (int s = 0; s < 3; ++s) {
            int w_in = q * stride - pad + s;
            if (h >= 0 && h < H && w_in >= 0 && w_in < W) {
                acc += x[h * W + w_in] * w[r * 3 + s];
            }
        }
    }
    y[idx] = acc;
}

A teljes program tartalmazza a CPU-referenciát (egyszerű C++ ciklusokkal), a GPU allokációt, az adatmásolást, a kernel indítását, a hibakezelést, az időmérést CUDA events segítségével, és az eredmények összehasonlítását.

24.2.16 JAX kitekintés

A JAX-ban a konvolúció magas szintű függvényekkel érhető el, például a jax.lax.conv_general_dilated segítségével. Az XLA fordító a konvolúciót gyakran implicit GEMM-ként vagy közvetlen kernelként alacsonyabb szintre bontja, attól függően, hogy a hardver (GPU, TPU) melyiket támogatja jobban. A fejlesztőnek nem kell kézzel írnia a kernelt, de a teljesítmény szempontjából hasznos megérteni a mögöttes transzformációt. A következő fejezet (Attention kernelek) az attention kerneleket tárgyalja, ahol a GEMM-alapú megközelítés és a közvetlen kernel hasonló dilemmája jelenik meg.

24.2.17 Összefoglalás és önellenőrző kérdés

A konvolúció GPU-n való implementálásának két fő útja a GEMM-re visszavezetés (im2col vagy implicit GEMM) és a közvetlen kernel. Az im2col nagy memória overheaddel jár, de a GEMM kernel újrahasznosítható; az implicit GEMM megtartja a GEMM optimalizálásait, de elkerüli a másolatot. A közvetlen kernel a memória-hozzáférést a konvolúcióra szabja, tilinggel és shared memory-val csökkenti a globális forgalmat. A csatornák kezelése és a tile-ok kialakítása kulcsfontosságú a nagy csatornaszámú rétegekben.

Önellenőrző kérdés: Miért növeli az im2col a memóriaigényt, és hogyan csökkenti az implicit GEMM ezt a többletet anélkül, hogy elveszítené a GEMM kernel optimalizálásait? Válaszában térjen ki a csatorna- és tile-kezelésre is.
