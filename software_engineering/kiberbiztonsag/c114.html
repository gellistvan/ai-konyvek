30.2 Architektúra és kontrollok

A Követelmények és fenyegetésmodell egységben elkészítetted a TerraSecure záróprojekt követelményeit, a fenyegetésmodellt, a bizalmi határok első vázlatát és az elfogadási kritériumokat. Most ebből a modellből építünk tovább: konkrét architekturális rétegeket, trust boundary-ket és azokhoz rendelt védelmi kontrollokat tervezünk. A cél nem egy újabb általános elméleti fejezet, hanem egy olyan kontrollmátrix és diagramkészlet, amelyet a következő egységben (Implementáció és tesztelés) közvetlenül implementációra és tesztelésre fordíthatsz.

Ebben a fejezetben a védő nézőpontjából dolgozunk. A támadó tevékenysége csak annyiban jelenik meg, amennyiben a fenyegetésmodellből származó támadási útvonalakat ellenőrizzük. A laborban kizárólag a saját, izolált TerraSecure tervezési munkakörnyezetét használjuk; valós rendszer elleni támadás nem megengedett.

30.2.1 1. Rétegek, trust boundary-k és védelmi kontrollok jelentése

30.2.2 1.1 Rétegzett védelem

A rétegzett védelem (defense in depth) azt jelenti, hogy egyetlen hibás vagy áttört kontroll ne tegye lehetővé a teljes rendszer kompromittálódását. A rétegek egymásra épülnek, de önállóan is értelmes védelmet nyújtanak:

  • Hálózati réteg: tűzfal, szegmentáció, hálózati naplózás.
  • Alkalmazásréteg: bemenet-ellenőrzés, kimeneti kódolás, session-kezelés.
  • Adatréteg: titkosítás, maszkolás, hozzáférés-vezérlés.
  • Identitásréteg: hitelesítés, MFA, jogosultságkezelés.
  • Üzemeltetési réteg: naplózás, detektálás, incidenskezelés, patchkezelés.

Ha például egy támadó átjut a hálózati szegmentáción, még mindig hitelesítenie kell magát az API felé. Ha ellop egy tokenet, a rövid élettartam és a scope korlátozza a hatását. Ha mégis adatbázishoz fér, a mezőszintű titkosítás és a minimális jogú adatbázis-felhasználó csökkenti a kárt.

30.2.3 1.2 Trust boundary

A trust boundary (bizalmi határ) olyan vonal egy adatfolyam-diagramon, amely elválasztja a különböző megbízhatósági szintű komponenseket. Minden adat, kérés vagy kódátvitel, amely átlépi ezt a határt, potenciálisan ellenségesnek tekintendő. A határon belül sem szabad vakon megbízni a komponensekben, de az ellenőrzések intenzitása és típusa a határ jellegétől függ.

Tipikus határok a TerraSecure példájában:

  • Internet → Edge (CDN/WAF): minden bejövő kérés ellenséges; itt DDoS-védelem, TLS, rate limiting és WAF-szabályok szükségesek.
  • Edge → Web frontend: az edge-nek csak korlátozott forrásból szabad kapcsolódnia; a web frontend hitelesíti a felhasználót, és soha nem bízik az edge által átengedett fejlécekben.
  • Web frontend → API gateway: a böngészőből érkező hívásokat az API gateway újra hitelesíti; a frontend nem kaphat közvetlen adatbázis-elérést.
  • API → szolgáltatások: szolgáltatásközi hívások mTLS-sel és scope-ellenőrzéssel; a szolgáltatás nem bízik a hívó által megadott felhasználói azonosítóban.
  • Szolgáltatás → adatbázis: az adatbázis csak a szolgáltatás dedikált, minimális jogú fiókját fogadja el.
  • CI/CD → production: a build rendszer által előállított artefaktum aláírt; a production környezet csak aláírt artefaktumot telepít.
  • Adminisztrátor → vezérlősík: az admin hozzáférés minden ponton külön hitelesítési és auditkört igényel, lehetőleg just-in-time jogosultsággal.

Egy trust boundary ábrán ezeket a határokat vastag szaggatott vagy folytonos vonallal jelöljük, és minden átlépő adatfolyam mellé odatesszük a szükséges kontrollt.

30.2.4 1.3 Védelmi kontrollok

A védelmi kontroll olyan intézkedés, amely egy fenyegetés bekövetkezési valószínűségét vagy hatását csökkenti. A kontrollokat négy nagy csoportba soroljuk:

  1. Prevenciós (megelőző): például bemenet-ellenőrzés, erős hitelesítés, tűzfalszabály.
  2. Detektáló (észlelő): például naplózás, SIEM-riasztás, anomáliadetektálás.
  3. Helyreállító (corrective/recovering): például backup, automatikus rollback, incidenskezelési runbook.
  4. Kompenzáló: ha egy elsődleges kontroll nem megvalósítható, más intézkedéssel csökkentjük a kockázatot.

Egy jól megtervezett architektúrában minden kritikus fenyegetésre több, különböző típusú kontroll jut. Például SQL injection ellen:

  • Prevenció: paraméterezett lekérdezések, ORM, input validálás.
  • Detektálás: alkalmazásnapló a sikertelen lekérdezésekről, WAF-riasztás.
  • Helyreállítás: legutóbbi jó adatbázis-állapot visszaállítása, incidenskezelés.

30.2.5 2. TerraSecure architektúra: rétegek és határok gyakorlatban

A záróprojektben egy kis, de valósághű rendszert tervezünk. A TerraSecure egy dokumentummegosztó alkalmazás: felhasználók regisztrálnak, feltöltenek fájlokat, megosztják azokat csoportokkal, és auditnaplót látnak a saját fájljaikról. Az architektúra a következő komponensekből áll:

  • Böngésző (felhasználó): HTML/CSS/JS frontend.
  • Edge réteg: CDN és WAF (például a laborban egy konténeres WAF, mint a ModSecurity).
  • Web frontend: Node.js vagy Python konténer, amely kiszolgálja a statikus állományokat és a felhasználói felületet.
  • API gateway: hitelesítést, rate limitinget és útválasztást végez.
  • Azonosításszolgáltató (IDP): OIDC és WebAuthn; a laborban lehet Keycloak konténer.
  • Dokumentumszolgáltatás: fájlok feltöltése, vírusellenőrzés, titkosítás.
  • Metaadat-szolgáltatás: fájlok metaadatainak, megosztási linkek és csoporttagság kezelése.
  • Adatbázis: PostgreSQL.
  • Objektumtároló: S3-kompatibilis tároló a fájltartalmaknak.
  • Naplózási pipeline: minden szolgáltatás strukturált naplót küld egy központi naplózóba (például Loki + Grafana).
  • CI/CD pipeline: build, tesztelés és aláírt artefaktum telepítése a production környezetbe.
  • Adminisztrátor: just-in-time hozzáféréssel dolgozó üzemeltető, külön vezérlőhálózaton.

A trust boundary diagram a következőképpen nézhet ki (szöveges ábrázolás, a laborban diagramkészítő eszközzel):

A bizalmi határok:

  • H1: internet ↔︎ edge. Minden kérés ellenségesnek tekintendő.
  • H2: edge ↔︎ web frontend. Csak a WAF által átengedett forgalom; a web frontend nem bízik az edge által beszúrt fejlécekben.
  • H3: web frontend ↔︎ API gateway. A felhasználói tokeneket itt érvényesítjük; a gateway nem bízik a frontend által megadott felhasználói azonosítóban.
  • H4: API gateway ↔︎ szolgáltatások. Szolgáltatásközi hitelesítés mTLS-sel; a gateway nem adhat át olyan jogosultságot, amellyel a felhasználó nem rendelkezik.
  • H5: szolgáltatások ↔︎ adatbázis/objektumtároló. Csak dedikált, minimális jogú hozzáférések.
  • H6: CI/CD ↔︎ production. Csak aláírt artefaktum, pull request review, auditnapló.
  • H7: adminisztrátor ↔︎ minden rendszer. Külön vezérlőhálózat, just-in-time jogosultság, minden lépés naplózott.

A diagramon külön jelölendő, a trust boundary-khoz tartozó szereplők és adatfolyamok:

  • OIDC böngészőátirányítás: a böngésző authorization requestet küld az IDP-nek (PKCE code_challenge, state, nonce), az IDP authorization code-dal irányítja vissza, majd a frontend vagy az API gateway végzi a code exchange-et. Ez a folyam a H3 határt keresztezi, és nem tévesztendő össze az API bearer tokenes hívásaival.
  • API erőforrás-szerver: az API gateway minden bearer tokennél ellenőrzi az aláírást, az issuer-t, az audience-t, a scope-ot és a lejáratot; a token birtoklása önmagában nem jogosultság.
  • CI/CD pipeline: a H6 határon keresztül csak aláírt artefaktumot telepít; a pipeline szereplője külön identitással és minimális jogosultsággal rendelkezik.
  • Adminisztrátor: a H7 határon keresztül, just-in-time jogosultsággal ér el, minden művelete auditnaplóba kerül.
  • Központi naplógyűjtő: minden komponens strukturált naplót küld neki; ez a T6 detektáló kontrolljának végpontja, és maga is védett, írásvédett célpont.

Minden határnál fel kell tennünk a kérdést: mi történik, ha a bal oldali komponens kompromittálódik? A válasz alapján állítjuk be a jobb oldali komponens védelmi kontrolljait.

30.2.6 3. Kontrollmátrix: fenyegetés → kontroll → réteg → tulajdonos → verifikáció

A kontrollmátrix egy olyan dokumentum, amely a fenyegetésmodell minden elfogadhatatlan kockázatú támadási útvonalához hozzárendel legalább egy kontrollt. A mátrixnak tartalmaznia kell:

  • Fenyegetés azonosítója (pl. a Követelmények és fenyegetésmodell alfejezetben STRIDE-ból származó T1, T2).
  • Leírás: rövid, egyértelmű támadási forgatókönyv.
  • Érintett trust boundary (például H3).
  • Kontroll rétege: hálózat, alkalmazás, adat, identitás, üzemeltetés.
  • Kontroll típusa: prevenciós, detektáló, helyreállító, kompenzáló.
  • Konkrét kontroll: technikai intézkedés.
  • Tulajdonos: ki felel a megvalósításért és üzemeltetésért (például backend csapat, DevOps, biztonsági mérnök).
  • Verifikáció: hogyan ellenőrizzük, hogy a kontroll valóban működik (például SAST, DAST, manuális kódreview, naplóteszt).
  • Maradék kockázat: rövid indoklás, hogy miért fogadható el a maradék kockázat.

Egy kivonat a TerraSecure kontrollmátrixból:

ID Fenyegetés Határ Kontroll (réteg, típus) Konkrét intézkedés Tulajdonos Verifikáció
T1 SQL injection a metaadat-lekérdezésben H5 Alkalmazás (prevenció) Paraméterezett lekérdezések, ORM, input validálás Backend SAST + DAST + kódreview
T2a OIDC engedélykód elfogása a böngésző–IdP átirányításban H3 Identitás (prevenció) PKCE S256, pontos redirect URI, state és nonce, egyszer használatos, rövid élettartamú kód, bizalmas kliens API csapat OIDC flow-teszt hibás verifierrel és redirect URI-val
T2b CSRF cookie-alapú munkamenettel H3 Alkalmazás + identitás (prevenció) SameSite=Lax/Strict cookie, anti-CSRF token, Origin/Referer ellenőrzés, állapotváltoztató művelet nem GET Backend Keresztoldali kérés tesztje
T2c Már megszerzett bearer token visszajátszása H3 Identitás (prevenció + detektálás) Rövid élettartamú access token (5–15 perc), issuer/audience/scope ellenőrzés, sender-constrained token (DPoP, RFC 9449, vagy mTLS-kötés), refresh token rotáció és reuse detection API csapat Lejárt token és más kulcshoz kötött token visszajátszási tesztje
T3 Fájlfeltöltés rosszindulatú tartalommal H4 Alkalmazás (prevenció) Vírusellenőrzés, MIME-típus ellenőrzés, sandbox futtatás Backend Fájlalapú teszt
T4 Túl széles hálózati hozzáférés a DB-hez H5 Hálózat (prevenció) Szegmentáció, tűzfal, csak a szolgáltatás IP-jéből DevOps Hálózati átvizsgálás
T5 Admin jogosultság kiszivárgása H7 Identitás + üzemeltetés (prevenció + detektálás) MFA, just-in-time hozzáférés, auditnapló minden admin műveletről Security Naplóteszt, jogosultság-audit
T6 Naplók hiánya miatt észrevétlen támadás H7 Üzemeltetés (detektálás) Központi naplózás, SIEM, riasztási szabályok Security Riasztásteszt

A mátrix minden sorának mérhetőnek kell lennie. A verifikáció oszlopban szereplő tesztet az Implementáció és tesztelés alfejezetben el fogjuk végezni; itt csak rögzítjük az elvárást.

A T2 három részre bontása azért szükséges, mert a kontrollok nem helyettesítik egymást: a PKCE az engedélykód elfogása ellen véd, a CSRF-token a cookie-val járó keresztoldali kérés ellen, de egyik sem akadályozza meg a már megszerzett bearer token visszajátszását. Utóbbihoz rövid token-élettartam, szigorú audience/scope ellenőrzés és sender-constrained token kell. A rövid élettartam csak az időablakot csökkenti, a token a lejáratig így is használható; a sender-constrained token (DPoP vagy mTLS-kötés) a tokent egy kulcshoz köti, ezért az ellopott token önmagában nem használható.

30.2.7 4. Tipikus támadási és védelmi minták, ellenpéldák

30.2.8 4.1 Támadási minták

A fenyegetésmodellből és a korábbi fejezetekből ismert támadási minták közül a leggyakoribbak:

  • Injection: SQL, parancs, template. Akkor fordul elő, ha a felhasználói bemenet közvetlenül kerül értelmezésre.
    Védekezés értelmezőnként: SQL-nél kötött paraméteres lekérdezés vagy ORM (nem string-összefűzés); OS-parancsnál shell nélküli API, amely argumentumvektort kap (például subprocess.run([...], shell=False)), allowlistelt végrehajthatóval; template-nél context-aware autoescaping és logika nélküli sablon, eval/exec nélkül. A kimeneti kódolás az XSS/HTML kontextus védelme, nem helyettesíti az SQL- vagy parancsparaméterezést.

  • Broken Access Control / IDOR: a felhasználó közvetlenül hivatkozik egy erőforrásra (például /files/123), és a rendszer nem ellenőrzi a jogosultságot.
    Védekezés: minden hozzáférési döntés a szerveren történik, nem a kliensben; a resource owner az adatbázisban tárolt policy.

  • SSRF: a szerver oldali kérés a támadó által megadott URL-re megy.
    Védekezés: címzett allowlist, IP-szűrés a privát tartományok ellen, DNS rebinding elleni védelem.

  • Titok kiszivárgása: API kulcs, adatbázis-jelszó, privát kulcs a forráskódban, környezeti változóban vagy naplóban.
    Védekezés: secrets manager, titkosítás, titkosítási séma szerinti átalakítás, CI/CD secret scanning.

  • Ellátási lánc támadás: függőség vagy build eszköz kompromittálása.
    Védekezés: aláírt artefaktum, SBOM, reprodukálható build, pinelt verziók, dependabot figyelés.

  • Cloud metadata exfiltráció: SSRF segítségével a támadó eléri a 169.254.169.254 metaadat-végpontot.
    Védekezés: IMDSv2 használata, hálózati szegmentáció, SSRF-védelem.

30.2.9 4.2 Védelmi minták

  • Zero trust: minden hívás hitelesített, még a belső hálózaton is. A hálózati pozíció nem jelent jogosultságot.
  • Least privilege: minden szolgáltatás csak a szükséges erőforrásokhoz fér hozzá, és csak a szükséges ideig.
  • Fail safe / deny by default: ha egy hozzáférési döntés nem egyértelmű, az alapértelmezés a megtagadás.
  • Defense in depth: egymástól független kontrollok egymásra rétegzése.
  • Security by design: a fenyegetésmodell már a tervezéskor elkészül, a biztonsági követelmények a felhasználói történetek részei.
  • Naplózás és megfigyelhetőség: minden kritikus művelet strukturált naplót generál, amelyből detektálási szabály építhető.

30.2.10 4.3 Ellenpéldák – amit ne csináljunk

  1. Túl széles hálózati szabály: a production adatbázis elérése 0.0.0.0/0-ról.
    Helyes döntés: csak a szolgáltatás alhálózatából, lehetőleg egyedi hálózati politikával.

  2. Titkos token a frontend JavaScriptben: például API kulcs a S3-hoz.
    Helyes döntés: a böngésző soha nem kap tartós kulcsot; a feltöltés presigned URL-lel vagy szerver oldali proxyval történik.

  3. Monolitikus trust: a web frontend közvetlenül éri el az adatbázist, mert „a tűzfal védi”.
    Helyes döntés: a frontend csak az API-n keresztül beszélhet, az adatbázis pedig csak a szolgáltatások hálózatából érhető el.

  4. Nincs admin audit: az adminisztrátorok minden művelete láthatatlan.
    Helyes döntés: minden admin műveletet külön naplóba írunk, riasztással és rendszeres felülvizsgálattal.

  5. Dev és prod azonos hálózaton: a fejlesztői laptopról közvetlenül elérhető a production.
    Helyes döntés: teljes szegmentáció, külön hálózat, csak auditált, just-in-time hozzáférés.

30.2.11 5. Ellenőrzés, naplózás és dokumentáció

Az architektúra nem létezik dokumentáció nélkül. A záróprojektben a következő dokumentumokat kell előállítani:

  • Trust boundary diagram: legalább egy rétegdiagram és egy adatfolyam-diagram, amelyen minden határ és kontroll látszik.
  • Kontrollmátrix: a fenti táblázat, minden fenyegetésre legalább egy sor.
  • Architecture Decision Record (ADR): minden fontos biztonsági döntésről rövid feljegyzés: mi volt a döntés, miért, milyen alternatívák voltak, milyen következményekkel.
  • Naplózási séma: melyik szolgáltatás milyen eseményeket naplóz, milyen mezőkkel, hova kerülnek a naplók, meddig őrizzük őket.
  • Verifikációs terv: melyik kontrollt hogyan teszteljük az Implementáció és tesztelés alfejezetben.

30.2.12 5.1 Ellenőrzési szempontok

Minden kontroll esetén fel kell tennünk a kérdést: honnan tudjuk, hogy működik?

  • Prevenciós kontrollnál: tudjuk-e mérni, hogy a nem kívánt kérés elakad? Például a WAF blokkolja-e a teszt payloadot?
  • Detektáló kontrollnál: a tesztesemény generál-e riasztást a SIEM-ben? Mennyi idő alatt?
  • Helyreállító kontrollnál: a backup visszaállítható-e a megadott RPO/RTO-n belül?

Az ellenőrzéshez használhatunk detect-as-code teszteket, például egy szintetikus SQL injection kérést, amelynek naplórekordot kell generálnia. Fontos, hogy ezeket a teszteket csak a saját laborban futtassuk, ne productionben.

30.2.13 5.2 Naplózási szempontok

A naplózás tervezésekor rögzítsük:

  • Mely eseményeket naplózzuk: sikeres/sikertelen bejelentkezés, jogosultság-módosítás, fájlfeltöltés, letöltés, hozzáférés-megtagadás, admin művelet.
  • Milyen mezőkkel: időbélyeg, felhasználói azonosító, IP-cím, user-agent, művelet azonosítója, erőforrás azonosítója, eredmény.
  • Formátum: strukturált JSON, hogy a SIEM könnyen elemezze.
  • Tárolás: központi naplózó, írásvédett, hosszú távú retention.
  • Integritás: hash, esetleg append-only log.

A naplókat nem szabad naplózni a production adatbázisba, mert az támadó által törölhető lehet. Külön pipeline-ra van szükség.

  4. Ellenőrizd az ellenpéldákat. Nézz utána a saját tervedben a 4.3 szakaszban felsorolt hibáknak. Ha találsz hasonlót, javítsd ki, és dokumentáld a döntést egy ADR-ben.

  5. Készíts egy minimális YAML kontrollmátrixot a fent bemutatott formátumban. Ez lesz az Implementáció és tesztelés bemenete.

  6. (Opcionális) Ellenőrző szkript. Az alábbi szkript beolvassa a YAML mátrixot, ellenőrzi a kötelező mezőket és azok típusát, a stabil threat_id-k egyediségét, a kontrollok ismert fenyegetéshez tartozását, valamint azt, hogy minden deklarált fenyegetéshez van-e legalább egy prevenciós és egy detektáló kontroll. A bemeneti fájl neve a példában controls.yaml; a szkript alapértéke is ez. A függőség a PyYAML 6.x, amelyet virtualenvben kell telepíteni.

#!/usr/bin/env python3
"""Kontrollmátrix kapuellenőrzés.

Függőség: Python 3.10+ és PyYAML 6.x.
Telepítés:
    python3 -m venv .venv
    . .venv/bin/activate
    python3 -m pip install "PyYAML>=6.0,<7"

Használat:
    python3 check_controls.py controls.yaml
    python3 check_controls.py --report controls.yaml

Kilépési kódok:
    0 – minden deklarált fenyegetéshez van prevenciós és detektáló kontroll
    1 – a mátrix érvényes YAML, de a lefedettség vagy a mezők hibásak
    2 – használati hiba, hiányzó fájl vagy érvénytelen YAML

A parancs alapértelmezésben kapu: hiba esetén nem nulla kóddal áll le.
A --report mód ugyanazt a vizsgálatot végzi, de riportként mindig 0-val
lép ki, hogy CI-ben a hibák jelentésként is megjelenjenek.
"""
from __future__ import annotations

import sys
from pathlib import Path
from typing import Any

try:
    import yaml
except ImportError:
    print(
        "HIBA: a PyYAML csomag nem érhető el. "
        "Telepítés: python3 -m pip install 'PyYAML>=6.0,<7'",
        file=sys.stderr,
    )
    raise SystemExit(2)

REQUIRED_THREAT_FIELDS = {"threat_id": str, "name": str, "risk": str}
REQUIRED_CONTROL_FIELDS = {
    "control_id": str,
    "threat_id": str,
    "boundary": str,
    "layer": str,
    "type": str,
    "measure": str,
    "owner": str,
    "verification": str,
}
RISK_LEVELS = {"low", "medium", "high", "critical"}
CONTROL_TYPES = {"preventive", "detective", "corrective", "compensating"}
BOUNDARIES = {f"H{i}" for i in range(1, 8)}
LAYERS = {"network", "application", "data", "identity", "operations"}


def check_record(
    record: Any,
    required: dict[str, type],
    label: str,
    errors: list[str],
) -> bool:
    """Ellenőrzi, hogy a rekord szótár, és a kötelező mezők a várt típusúak."""
    if not isinstance(record, dict):
        errors.append(f"{label}: nem szótár (dict)")
        return False
    ok = True
    for field, expected_type in required.items():
        if field not in record:
            errors.append(f"{label}: hiányzó mező: {field}")
            ok = False
        elif not isinstance(record[field], expected_type):
            errors.append(
                f"{label}: a {field} mező típusa "
                f"{type(record[field]).__name__}, elvárt {expected_type.__name__}"
            )
            ok = False
    return ok


def main(argv: list[str]) -> int:
    report = False
    args = argv[1:]
    if args and args[0] == "--report":
        report = True
        args = args[1:]
    if len(args) > 1:
        print(
            "Használat: python3 check_controls.py [--report] [controls.yaml]",
            file=sys.stderr,
        )
        return 2
    path = Path(args[0]) if args else Path("controls.yaml")

    try:
        with path.open(encoding="utf-8") as handle:
            data = yaml.safe_load(handle)
    except FileNotFoundError:
        print(f"HIBA: a fájl nem található: {path}", file=sys.stderr)
        return 2
    except yaml.YAMLError as exc:
        print(f"HIBA: érvénytelen YAML: {exc}", file=sys.stderr)
        return 2

    if not isinstance(data, dict):
        print("HIBA: a gyökér nem szótár (dict)", file=sys.stderr)
        return 1

    errors: list[str] = []
    threats = data.get("threats")
    controls = data.get("controls")
    if not isinstance(threats, list):
        errors.append("a threats mező hiányzik vagy nem lista")
        threats = []
    if not isinstance(controls, list):
        errors.append("a controls mező hiányzik vagy nem lista")
        controls = []

    declared: dict[str, dict[str, Any]] = {}
    for index, threat in enumerate(threats, start=1):
        label = f"threats[{index}]"
        if not check_record(threat, REQUIRED_THREAT_FIELDS, label, errors):
            continue
        threat_id = threat["threat_id"]
        if threat_id in declared:
            errors.append(f"{label}: ismétlődő threat_id: {threat_id}")
            continue
        if threat["risk"] not in RISK_LEVELS:
            errors.append(
                f"{label}: ismeretlen risk érték: {threat['risk']} "
                f"(elfogadott: {', '.join(sorted(RISK_LEVELS))})"
            )
        declared[threat_id] = threat

    if not declared:
        errors.append("a threats lista nem tartalmaz érvényes fenyegetést")

    seen_controls: set[str] = set()
    covered: dict[str, set[str]] = {threat_id: set() for threat_id in declared}
    for index, control in enumerate(controls, start=1):
        label = f"controls[{index}]"
        if not check_record(control, REQUIRED_CONTROL_FIELDS, label, errors):
            continue
        control_id = control["control_id"]
        if control_id in seen_controls:
            errors.append(f"{label}: ismétlődő control_id: {control_id}")
        seen_controls.add(control_id)
        if control["type"] not in CONTROL_TYPES:
            errors.append(
                f"{label}: ismeretlen type: {control['type']} "
                f"(elfogadott: {', '.join(sorted(CONTROL_TYPES))})"
            )
        if control["boundary"] not in BOUNDARIES:
            errors.append(f"{label}: ismeretlen boundary: {control['boundary']}")
        if control["layer"] not in LAYERS:
            errors.append(f"{label}: ismeretlen layer: {control['layer']}")
        threat_id = control["threat_id"]
        if threat_id not in declared:
            errors.append(f"{label}: ismeretlen threat_id: {threat_id}")
            continue
        covered[threat_id].add(control["type"])

    for threat_id in declared:
        missing = {"preventive", "detective"} - covered[threat_id]
        if missing:
            errors.append(
                f"{threat_id}: hiányzó kontrolltípus: "
                f"{', '.join(sorted(missing))}"
            )

    if errors:
        print("A kontrollmátrix ellenőrzése sikertelen:", file=sys.stderr)
        for error in errors:
            print(f"  - {error}", file=sys.stderr)
        if report:
            print("Riportmód: a hibák ellenére a kilépési kód 0.", file=sys.stderr)
            return 0
        return 1

    print(
        f"Rendben: {len(declared)} fenyegetés, {len(controls)} kontroll, "
        "minden fenyegetéshez van prevenciós és detektáló kontroll."
    )
    return 0


if __name__ == "__main__":
    raise SystemExit(main(sys.argv))

A --report kapcsoló nélkül a parancs kapu: érvényes és teljes mátrixnál 0-val, lefedettségi vagy mezőhibánál 1-gyel, használati hiba, hiányzó fájl vagy érvénytelen YAML esetén 2-vel lép ki. A --report mód ugyanazt a vizsgálatot végzi, de riportként mindig 0-val lép ki. A két példa (controls.yaml és controls-incomplete.yaml) a kapu pozitív, illetve negatív bemenete.

30.2.19 6.4 Mit tanultunk, hogyan védjük ki

Mit tanultunk: a bizalmi határok azonosítása nélkül a védelmi kontrollok véletlenszerűen kerülnek a rendszerbe. A kontrollmátrix a fenyegetésmodellt és az architektúrát egyetlen áttekinthető dokumentumban kapcsolja össze, és verifikálhatóvá teszi a döntéseket.

Hogyan védjük ki: a laborban feltárt hibákat (például túl széles hálózati szabály) azonnal javítjuk a tervben. A jövőben minden architekturális változtatásnál frissítenünk kell a diagramot és a mátrixot, és újra kell futtatni az ellenőrző szkriptet.
