9.2 Secure coding checklist és kódreview

A biztonságos kódolási ellenőrzőlista és a kódellenőrzés célja nem az, hogy a fejlesztőből biztonsági kutatót képezzünk, hanem hogy a mindennapi kódreview során felismerje a leggyakoribb, nyelvspecifikus hibákat, és indokolni tudja a védelmi döntést. Ebben a fejezetben a Threat modeling a tervezésben alfejezetben bevezetett fenyegetésmodellből indulunk ki: a fenyegetésmodell azonosította a bizalmi határokat és a támadási felületet, most arra koncentrálunk, hogy a forráskód e határokon belül hogyan védhető meg.

A kódreview két szinten működik: egyrészt automatikus ellenőrzőeszközökkel (lásd a következő fejezet, SAST, DAST, IAST és fuzzing), másrészt emberi áttekintéssel. Ez a fejezet az emberi review-hoz ad eszközt: egy olyan ellenőrzőlistát, amely nyelvspecifikus buktatókra és általános védelmi mintákra egyaránt kiterjed. A lista nem helyettesíti a gondolkodást, de rendszerezi a figyelmet, és csökkenti annak esélyét, hogy egy jól ismert hibaosztály elkerülje a figyelmet.

9.2.1 Nyelvspecifikus hibák és review-szempontok

Minden programozási nyelvnek megvannak a maga biztonsági buktatói. A review során ezeket külön kell vizsgálni, mert ugyanaz a hibaosztály más szintaxissal jelentkezik. Az alábbiakban a leggyakoribb nyelvek tipikus hibáit és a hozzájuk tartozó védelmi mintákat tekintjük át.

9.2.2 C és C++

A C/C++ a memóriabiztonság hiánya miatt különösen érzékeny. A fő hibaosztályok:

  • Buffer overflow: határellenőrzés nélküli másolás. Példa hibás kód:
/* HIBÁS: nincs határellenőrzés */
char buf[16];
strcpy(buf, user_input);

A strcpy addig másol, amíg nullbájtot nem talál, tehát hosszabb bemenet túlírja a veremkeretet. A védelmi minta: hosszkorlátos másolás vagy biztonságos könyvtári függvények. Például:

/* JAVÍTOTT: hosszkorlátos másolás */
char buf[16];
if (strlen(user_input) >= sizeof(buf)) {
    /* kezelés */
}
strncpy(buf, user_input, sizeof(buf) - 1);
buf[sizeof(buf) - 1] = '\0';

Fontos: a strncpy önmagában nem elég, mert nem garantálja a lezáró nullbájtot; a fenti példa ezt expliciten kezeli. A snprintf ugyancsak biztonságosabb, mert mindig lezárja a puffert, ha a méret nagyobb nullánál.

  • Format string: ha a formátumsztring felhasználói bemenetből származik.
/* HIBÁS: felhasználói bemenet mint formátumsztring */
printf(user_input);

A támadó %n-nel írhat a memóriába. Javítás: mindig rögzített formátumsztringet használjunk.

/* JAVÍTOTT */
printf("%s", user_input);

  • Integer overflow: például size_t len = user_len + 1; túlcsordulhat, ha a user_len közel van a típus maximumához. Ellenőrizni kell a művelet előtt: if (user_len > SIZE_MAX - 1).

  • Use-after-free és double free: dinamikus memória felszabadítása után még hivatkozunk rá. A pointer nullázása csak azt az egy pointert védi, amelyiket nullázzuk; ha ugyanarra az objektumra másik alias is mutat, az továbbra is eléri a felszabadított memóriát:

/* HIBÁS: a nullázás nem védi a másik aliast */
char *p = malloc(32);
char *q = p;          /* második alias ugyanarra az objektumra */
free(p);
p = NULL;             /* q változatlanul a felszabadított objektumra mutat */
strcpy(q, "x");       /* use-after-free */

A helyes megoldás a tulajdonjog egyértelművé tétele: egy objektumnak egy tulajdonosa legyen, a felszabadítás után ne maradjon másik alias, és a kölcsönzés (borrowing) élettartama ne nyúljon túl a tulajdonosén. C++-ban RAII-t és smart pointereket (std::unique_ptr, indokolt esetben std::shared_ptr) használunk; Rustban a fordítási idő ellenőrzi a tulajdonjogot és a kölcsönzést. A free(p); p = NULL; csak a p-n keresztüli double free-et akadályozza meg, a q-n keresztüli use-after-free-et nem.

9.2.3 Python

A Python memóriabiztos, de dinamikus jellege más hibákat hoz.

  • eval és exec: soha ne használjuk felhasználói adattal. Ha dinamikus kifejezés kell, használjunk szigorúan korlátozott parser bibliotékát.

  • pickle.loads: nem biztonságos nem megbízható adatból, mert tetszőleges kód futtatását teszi lehetővé a deszerializáció során.

  • subprocess shell=True: shell injectionhez vezet. Példa:

# HIBÁS: shell injection
import subprocess
subprocess.call(f"ping -c 1 {host}", shell=True)

Ha a host értéke például ; rm -rf /, a parancs végrehajtódik. Javítás: ne használjunk shellt, hanem argumentumlistát.

# JAVÍTOTT: nincs shell, argumentumlista, szűk cél- és hatókör-ellenőrzés
import ipaddress
import subprocess

def ping_lab_target(host: str) -> None:
    target = ipaddress.ip_address(host)  # csak literál IP-t fogad el
    lab = ipaddress.ip_network("192.0.2.0/24")
    if target not in lab:
        raise ValueError("a cél kívül esik a labor hatókörén")
    subprocess.run(
        ["ping", "-c", "1", "-W", "2", str(target)],
        check=True,
        timeout=5,
    )

A shell kikapcsolása megszünteti a parancsinjekciót, de nem helyettesíti a cél validálását: a host továbbra is lehet érvényes, de nem engedélyezett cím. Ezért a függvény csak literál IP-t fogad el, és a labor 192.0.2.0/24 dokumentációs tartományára szűkít. Nagyobb rendszerben a protokollt (ICMP), a portot és a forrásirányt is a hatókörhöz kell kötni.

  • yaml.load: régi PyYAML esetén tetszőleges objektumokat hozhat létre. Használjunk yaml.safe_load-ot.

  • Path traversal: fájlkezelésnél ellenőrizni kell a kanonikus elérési utat.

# HIBÁS: path traversal
file_path = os.path.join(base_dir, user_file)
with open(file_path, 'r') as f:
    ...

Ha user_file értéke ../../etc/passwd, a base_dir-en kívülre kerülünk. A realpath és a prefix-ellenőrzés önmagában azonban TOCTOU-hibás: ha a támadó írhatja a könyvtárat vagy a szülőútvonalat, az ellenőrzés és a megnyitás között a fájlnevet vagy egy symlinket kicserélhet. A javítás ezért vagy a támadó írási jogát zárja ki, vagy olyan megnyitást használ, amely a fájlazonosítóhoz kötött:

# JAVÍTOTT: könyvtárhoz kötött megnyitás, symlink követése nélkül
import os

base_fd = os.open(base_dir, os.O_RDONLY | os.O_DIRECTORY)
try:
    fd = os.open(user_file, os.O_RDONLY | os.O_NOFOLLOW, dir_fd=base_fd)
except OSError:
    raise ValueError("Invalid path")
with os.fdopen(fd, "r") as f:
    ...
finally:
    os.close(base_fd)

A dir_fd és az O_NOFOLLOW a megnyitást a base_fd könyvtárhoz köti, és nem követi a symlinket; Linuxon a openat2 RESOLVE_BENEATH beállítása ennél is szigorúbban korlátozza a feloldást. A laborban a base_dir olyan könyvtár, amelybe a támadó nem írhat; ha ez nem teljesül, a realpath-ellenőrzés csak jelzés, nem biztonsági garancia. A generált fájlazonosító (a kliens által megadott név helyett) szintén kizárja a név-alapú versenyhelyzetet.

9.2.4 Java

  • Deszerializáció: ObjectInputStream.readObject() nem megbízható forrásból. Védelmi minta: osztályfehérlista (whitelist) vagy ObjectInputFilter.

  • XXE (XML External Entity): az XML-feldolgozó külső entitásokat olvashat be. A DocumentBuilderFactory esetén le kell tiltani a DTD-t és a külső entitásokat.

  • Log injection: ha felhasználói adat kerül a naplóba, CRLF injekciót hajthat végre. A paraméterezett logger önmagában nem védi ki a CR/LF karaktereket: az csak a formátumstring-injekciót akadályozza meg, a naplóba írt értéket változatlanul átadja. A naplózásnál strukturált formátumot (például JSON-t, amely a vezérlőkaraktereket escape-eli) vagy explicit vezérlőkarakter-kódolást kell használni, és a naplózandó adatot cél szerint minimalizálni kell.

// HIBÁS: a paraméterezett logger is változatlanul naplózza a CR/LF-et
logger.info("User: {}", userInput);
// JAVÍTOTT: vezérlőkarakter-kódolás és célhoz kötött, minimális mezők
private static String logSafe(String value) {
    return value.replace("\r", "\\r").replace("\n", "\\n");
}
logger.info("event=user_lookup user={}", logSafe(userInput));

A CR/LF kódolása mellett a naplóbejegyzés ne tartalmazzon felesleges személyes adatot: az IP-cím és a felhasználóazonosító önmagában is személyes adat lehet, ezért csak a naplózási célhoz szükséges mértékben, dokumentált megőrzési idővel és – ahol lehet – pszeudonimizálva kerüljön a naplóba.

  • SQL injection: Statement helyett PreparedStatement kötelező.

9.2.5 JavaScript és Node.js

  • eval és new Function: ugyanaz, mint Pythonnál.

  • child_process.exec: shell injection. Használjunk execFile-ot vagy argumentumlistát.

  • Prototype pollution: ha nem ellenőrzött objektumokba merge-ölünk, a __proto__ szennyezésével globális viselkedést változtathatunk meg. Védelmi minta: kulcsok ellenőrzése, Object.create(null) használata.

  • NoSQL injection: például MongoDB esetén, ha a bemenet objektum lehet.

// HIBÁS: NoSQL injection
db.collection('users').find({ username: req.body.username });

Ha req.body.username egy objektum, például { $ne: null }, akkor minden felhasználó visszakerül. Javítás: a bemenetet mindig típusellenőrzött skalárként kezeljük.

  • A vm modul nem biztonsági határ; ne használjuk sandboxként.

9.2.6 Go

  • SQL injection: string összefűzés a lekérdezésben. A helyőrző szintaxisa driverfüggő: a database/sql a paramétert a drivernek adja át, és a driver dönti el, hogy ? vagy $1 alakot vár. PostgreSQL-nél például a github.com/jackc/pgx/v5 (és a lib/pq) $1-et használ, a modernc.org/sqlite és a MySQL driver ?-t.
// HIBÁS: string összefűzés (a példában PostgreSQL/pgx driver)
rows, err := db.Query("SELECT username FROM users WHERE id = " + userInput)

// JAVÍTOTT: a driverhez illő helyőrző, kötött paraméterrel
rows, err := db.Query("SELECT username FROM users WHERE id = $1", userID)

  • Template: text/template nem escape-el HTML-t. Webes kimenethez html/template-et használjunk.

  • Path traversal: http.ServeFile ellenőrzés nélkül kiszolgáltathat a web gyökerén kívüli fájlokat. A http.Dir önmagában nem biztonsági határ: a gyökér alatti, kifelé mutató symlinket követi, ezért a gyökéren kívüli fájl is elérhetővé válhat. A viselkedés izolált laborban így ellenőrizhető:

# A http.Dir a symlinket követi: a gyökéren kívüli marker is elérhetővé válhat
mkdir -p /tmp/c030-www /tmp/c030-outside
printf 'labor-marker\n' > /tmp/c030-outside/marker.txt
ln -s /tmp/c030-outside/marker.txt /tmp/c030-www/link.txt
curl --path-as-is http://127.0.0.1:8080/link.txt

A javítás: a kiszolgált gyökér legyen root tulajdonú és a szolgáltatást futtató, illetve a támadó által nem írható; a symlinkeket a telepítéskor ellenőrizni kell, vagy Go 1.24+ esetén os.Root-tal kell a fájlműveleteket a gyökérhez kötni. A http.Dir használata csak a gyökér kijelölése, nem védelem.

  • os/exec: kerüljük a sh -c-t; argumentumlistát adjunk át.

9.2.7 C

  • Deszerializáció: BinaryFormatter, NetDataContractSerializer nem biztonságos. Védelmi minta: JSON-szerializálás típusellenőrzéssel.

  • LDAP injection: LDAP-szűrők összeállításánál escape-elni kell a speciális karaktereket.

  • SQL injection: paraméterezett lekérdezés (SqlCommand paraméterekkel).

A fenti áttekintés célja, hogy a review során a nyelvspecifikus buktatókat azonnal észrevegyük. A következő szakaszban ezeket általános review-szempontokba rendezzük.

9.2.8 Általános review-szempontok és védelmi minták

A secure coding checklist kategóriák szerint rendezi az ellenőrzési pontokat. A review során minden módosított kódrészletet végig kell nézni ezeken a kategóriákon.

9.2.9 1. Bemenetkezelés

Minden bemenet nem megbízható: HTTP-paraméterek, fejlécek, sütik, fájlfeltöltések, külső API-válaszok, parancssori argumentumok. A védelmi minta:

  • Whitelist előnyben részesítése a blacklisttel szemben.
  • Canonicalizálás: az elérési utakat, URL-eket kanonikus formába hozzuk.
  • Hossz- és tartalomellenőrzés: minden bemenetre maximális hossz, megengedett karakterkészlet.
  • Típusellenőrzés: az API szerződés szerint például egész szám, dátum, felsorolt érték.

Példa hibás kód (Python, Flask):

# HIBÁS: nincs bemeneti validáció
@app.route('/search')
def search():
    query = request.args.get('q', '')
    return render_template('search.html', query=query)

Javítás: a q paramétert hossz- és tartalomellenőrzésnek vetjük alá, mielőtt feldolgozzuk.

9.2.10 2. Kimenetkezelés

A kimenetet a kontextusnak megfelelően kell kódolni:

  • HTML-környezetben HTML-escape.
  • JavaScript-környezetben JavaScript-escape.
  • SQL-ben paraméterezett lekérdezés.
  • Shellben argumentumlista.
  • URL-ben percent-encoding.

A templating motorok általában automatikusan escape-elnek, de csak akkor, ha a megfelelő kontextusban használjuk őket. Például a Jinja2 HTML-escape-el, a Go html/template szintén, de a text/template nem. A review során ellenőrizni kell, hogy a kimenet a megfelelő kódolással kerül-e a válaszba.

9.2.11 3. Hitelesítés és session

A hitelesítésnél a korábbi fejezetek (Jelszavak, MFA és passkeys/WebAuthn, Session, token, OAuth 2.1 és OIDC) részletesen tárgyalták a jelszavak, tokenek és MFA kérdéseit. A kódreview-ban az alábbiakat ellenőrizzük:

  • Jelszavak tárolása: kizárólag erős, adaptív hash (Argon2, bcrypt, scrypt), soha nem plaintext, nem MD5/SHA-1/SHA-256 önmagában.
  • Session tokenek: CSPRNG-ből, megfelelő entrópiával, HttpOnly, Secure, SameSite attribútumok.
  • Session fixation: bejelentkezés után a session ID cseréje.
  • Tokenek validálása minden védett végponton.

9.2.12 4. Hozzáférés-vezérlés

Minden erőforrás-hozzáférésnél ellenőrizni kell, hogy a felhasználó jogosult-e rá. A hibaosztály tipikus példája az IDOR (Insecure Direct Object Reference): a felhasználó az objektum azonosítóját módosítva más adatát érheti el.

# HIBÁS: nincs tulajdonosi ellenőrzés
@app.route('/orders/<int:order_id>')
def get_order(order_id):
    order = Order.query.get(order_id)
    return render_template('order.html', order=order)

Javítás: a lekérdezésbe beletesszük az aktuális felhasználó azonosítóját.

# JAVÍTOTT: tulajdonosi ellenőrzés
@app.route('/orders/<int:order_id>')
def get_order(order_id):
    order = Order.query.filter_by(id=order_id, user_id=current_user.id).first()
    if order is None:
        abort(404)
    return render_template('order.html', order=order)

9.2.13 5. Kriptográfia

A kriptográfiai döntéseknél a Hash, MAC és integritás–Gyakori kriptográfiai hibák és ellenőrzésük fejezetekre támaszkodunk. A review pontjai:

  • CSPRNG használata (secrets Pythonban, SecureRandom Java-ban, crypto/rand Go-ban).
  • Kulcskezelés: kulcs soha ne legyen a kódban, hanem konfigurációban vagy titokkezelőben.
  • AEAD üzemmód (pl. AES-GCM, ChaCha20-Poly1305) az integritás és titkosság együttes biztosítására.
  • Jelszóhash: csak adaptív algoritmus.

9.2.14 6. Naplózás

A naplózásnál két irányban kell gondolkodni: mit naplózzunk, és mit NE naplózzunk.

  • Mit naplózzunk: hitelesítési események, jogosultsági döntések, adminisztratív műveletek, hibák. A bejegyzés tartalma: időbélyeg, esemény típusa, szereplő, erőforrás, eredmény.
  • Mit NE naplózzunk: jelszót, tokent, session cookie-t, hitelkártyaszámot, személyes adatot (PII). A személyes adat köre kontextusfüggő: az IP-cím és a felhasználóazonosító is lehet személyes adat, ezért csak a naplózási célhoz szükséges mértékben, dokumentált megőrzési idővel és lehetőség szerint pszeudonimizálva kerüljön a naplóba. A log injection megelőzéséhez a felhasználói adatot strukturált formátumban kell naplózni, a vezérlőkaraktereket (CR/LF) kódolva; a puszta paraméterezett logger ehhez nem elég.

9.2.15 7. Hibakezelés

A hibakezelésnél a biztonsági elv: fail closed. Ha egy biztonsági ellenőrzés nem hajtható végre, a kérést meg kell tagadni, nem pedig engedélyezni. A felhasználó felé ne kerüljön ki stack trace vagy belső implementációs részlet; a naplóba viszont kerüljön be elegendő diagnosztikai adat.

9.2.16 8. Konfiguráció

A biztonsági beállításoknál a default deny elvet kövessük: alapértelmezésben minden tiltott, és csak explicit engedélyezéssel válik elérhetővé. A titkokat környezeti változóban vagy titokkezelőben tároljuk, nem a verziókezelőben.

9.2.17 9. Fájlkezelés

  • Path traversal elleni védelem.
  • Fájlfeltöltésnél: típusellenőrzés, méretkorlát, tartalom-ellenőrzés, végrehajtható kiterjesztések tiltása, a tárolás webgyökéren kívül.
  • Zip slip: archívumból történő kibontásnál ellenőrizni kell a célutat.

9.2.18 10. Függőségek

A függőségek kezelése a Csomagfüggőségek és verziókezelés–Reprodukálható build és CI/CD fejezetben részletes, de a kódreview során is ellenőrizni kell:

  • A függőség verziója rögzített-e (lock fájl).
  • Ismert sebezhetőség van-e a függőségben (pl. npm audit, pip-audit, OWASP Dependency-Check).
  • A függőség forrása megbízható-e.

9.2.19 Secure coding checklist – áttekintő táblázat

Az alábbi táblázat a review során használható ellenőrzőlista. A kategória után a fő ellenőrző kérdés, majd a tipikus hibajel szerepel.

Kategória Ellenőrző kérdés Tipikus hibajel
Bemenetkezelés Minden bemenetre van hossz-, típus- és tartalomellenőrzés? Nyers request.args.get használata validáció nélkül
Kimenetkezelés A kimenet a kontextusnak megfelelően van kódolva? innerHTML használata, render_template_string HTML-escape nélkül
Hitelesítés A jelszavak erős hash-sel vannak tárolva? A tokenek megfelelő attribútumokkal rendelkeznek? hashlib.sha256(password) vagy plaintext tárolás
Hozzáférés-vezérlés Minden erőforrás-hozzáférésnél ellenőrzött a tulajdonos? SELECT ... WHERE id = ? felhasználói azonosító nélkül
Kriptográfia CSPRNG-ből származnak a kulcsok, tokenek? AEAD van használva? random.random() token generálás, AES-CBC MAC nélkül
Naplózás A napló nem tartalmaz titkot, és véd a log injection ellen? logger.info(f"Password: {password}")
Hibakezelés Fail closed elv érvényesül? A felhasználó nem kap belső hibát? except: pass biztonsági ellenőrzésnél, stack trace a válaszban
Konfiguráció Default deny? Titkok nem a kódban? API kulcs a forráskódban
Fájlkezelés Path traversal ellen védett? Feltöltés ellenőrzött? os.path.join ellenőrzés nélkül, Content-Type alapú döntés
Függőségek Verzió rögzített, sebezhetőség ellenőrzött? Folyamatosan változó függőség, ismert critical CVE

Ez a táblázat használható minden kódreview-nál, akár manuálisan, akár egy review-hoz készült sablonban. A laborban ezt fogjuk kitölteni.

9.2.20 Ellenőrzési, naplózási és dokumentációs szempontok

A kódreview nem ér véget a hibák megtalálásával. Az eredményt dokumentálni kell, és a naplózási gyakorlatot is a kód részeként kell kezelni.

9.2.21 A review dokumentációja

A review során a checklist minden pontjára rögzíteni kell a döntést: megfelelő, nem megfelelő, nem alkalmazható. A nem megfelelő pontokhoz javítási javaslat tartozik, és a javítás után újra ellenőrizni kell. A dokumentáció a következőket tartalmazza:

  • A review tárgya (PR azonosító, commit hash).
  • A review-t végző személy(ek) és időpont.
  • A checklist kitöltött állapota.
  • A talált hibák súlyossági besorolása (pl. CVSS-pontszám vagy egyszerűbb: magas, közepes, alacsony).
  • A javítási döntés és a felelős.
  • A kiadási kapu döntése (engedélyezett, feltételesen engedélyezett, elutasított).

9.2.22 Audit napló a kódban

A biztonsági szempontból releváns eseményeket az alkalmazásnak naplóznia kell. A naplóbejegyzésnek tartalmaznia kell:

  • Esemény időbélyegét (UTC, ISO 8601).
  • Esemény típusát (pl. login_success, order_access_denied).
  • A szereplő azonosítóját (felhasználó vagy szolgáltatás).
  • Az érintett erőforrást.
  • Az eredményt (siker, sikertelen, hiba).
  • A szükséges kontextust (pl. IP-cím, User-Agent, de PII nélkül).

A naplózási szabályokat a kódban konzisztensen kell alkalmazni, és a review során ellenőrizni kell, hogy a naplózás nem szivárogtat-e titkot.

9.2.23 A kódban lévő biztonsági döntések dokumentálása

Ha a kódban biztonsági okból eltérünk a megszokott mintától, azt kommentben dokumentálni kell. Például:

# A bemeneti hossz ellenőrzése azért szigorúbb,
# mert a downstream rendszer 255 karakternél elszakad.
if len(name) > 200:
    abort(400)

Ez segíti a későbbi karbantartót, hogy ne távolítsa el a védelmet tévedésből.

  1. Konténer indítása: a függőséget előre, a kép építésekor rögzítjük, ezért a belső hálózaton futó konténernek nem kell pip-pel elérnie a csomagforrást. Készíts egy Dockerfile-t a labor könyvtárában:

A takarítás név szerint történik:

  1. A hibás kód: az app.py a következő sebezhető végpontokat tartalmazza. A séma, a seed és az init_db() közös mindkét változatban, így a hibás és a javított kód ugyanazon az adatokon reprodukálható:
# HIBÁS: SQL injection a keresésben, XSS/SSTI a visszavert kifejezésben
import sqlite3
import logging
from flask import Flask, request, render_template_string, abort

app = Flask(__name__)
logging.basicConfig(level=logging.INFO)
DB_PATH = 'terra.db'

def init_db():
    conn = sqlite3.connect(DB_PATH)
    try:
        conn.execute("CREATE TABLE IF NOT EXISTS users (id INTEGER PRIMARY KEY, username TEXT, email TEXT)")
        conn.executemany(
            "INSERT OR IGNORE INTO users (id, username, email) VALUES (?, ?, ?)",
            [(1, 'alice', 'alice@example.invalid'), (2, 'bob', 'bob@example.invalid')],
        )
        conn.commit()
    finally:
        conn.close()

@app.route('/users/<int:user_id>')
def get_user(user_id):
    conn = sqlite3.connect(DB_PATH)
    try:
        user = conn.execute(
            f"SELECT username, email FROM users WHERE id = {user_id}"
        ).fetchone()
    finally:
        conn.close()
    if user:
        return render_template_string(f"<h1>{user[0]}</h1><p>{user[1]}</p>")
    abort(404)

@app.route('/search')
def search():
    q = request.args.get('q', '')
    conn = sqlite3.connect(DB_PATH)
    try:
        rows = conn.execute(
            f"SELECT username FROM users WHERE username LIKE '%{q}%'"
        ).fetchall()
    finally:
        conn.close()
    items = "".join(f"<li>{row[0]}</li>" for row in rows)
    return render_template_string(f"<h1>Keresés: {q}</h1><ul>{items}</ul>")

if __name__ == '__main__':
    init_db()
    app.run(host='0.0.0.0', port=5000, threaded=True)

A hibák:

  • SQL injection: a /users/<int:user_id> útvonalon az int konverter jelenleg véd, és a -1 értéket is a konverter utasítja el, mielőtt a függvény lefutna. A stringformázás ott is rossz, törékeny minta, de a ténylegesen bizonyítható injekció a /search q paramétere, amelyet a kód közvetlenül fűz a LIKE mintába.
  • XSS és SSTI: a render_template_string az f-stringgel együtt a q értékét sablonforrásként értelmezi. A <script>alert(1)</script> visszavert XSS-t ad; a {{7*7}} bemenet 49-ként renderelődik, ami SSTI-t bizonyít. A seedelt alice/bob adat szándékosan ártalmatlan, ezért az XSS-t nem a fixture-ön, hanem a visszavert keresőkifejezéssel kell bemutatni.
  • Hiányzó hibakezelés: nincs try/except az adatbázis-hibákra, csak try/finally; a hiba a felhasználó felé nem kezelt.
  • Kapcsolatkezelés: a kapcsolat kérésenként jön létre, nem globális, így a Flask szálas kiszolgálása nem ütközik az SQLite szálhoz kötöttségével. A globális kapcsolat külön hibaminta lenne, de ebben a laborban nem az.

A /users/<id> végpont szándékosan nyilvános: nincs hitelesítés és objektumszintű engedélyezés. A labor kódreview-gyakorlat, nem többfelhasználós profilrendszer; a gyártási változatban a profil személyes adataihoz hozzáférés-vezérlés és tulajdonosellenőrzés kell.

  1. A checklist kitöltése: a fenti táblázat alapján jelöljük meg a hibákat. A hallgató töltse ki a táblázatot, majd indokolja a súlyosságot.

  2. Javítás: a hallgató javítja a kódot. A javított változat:

# JAVÍTOTT: közös init_db(), kérésenkénti kapcsolat, paraméterezett lekérdezés, escape
import sqlite3
import logging
from flask import Flask, abort, render_template, request

app = Flask(__name__)
logging.basicConfig(level=logging.INFO)
DB_PATH = 'terra.db'

def get_db():
    conn = sqlite3.connect(DB_PATH)
    conn.row_factory = sqlite3.Row
    return conn

def init_db():
    conn = get_db()
    try:
        conn.execute("CREATE TABLE IF NOT EXISTS users (id INTEGER PRIMARY KEY, username TEXT, email TEXT)")
        conn.executemany(
            "INSERT OR IGNORE INTO users (id, username, email) VALUES (?, ?, ?)",
            [(1, 'alice', 'alice@example.invalid'), (2, 'bob', 'bob@example.invalid')],
        )
        conn.commit()
    finally:
        conn.close()

@app.route('/users/<int:user_id>')
def get_user(user_id):
    conn = get_db()
    try:
        user = conn.execute(
            "SELECT username, email FROM users WHERE id = ?",
            (user_id,),
        ).fetchone()
    except sqlite3.Error:
        logging.exception("Database error while fetching user id=%d", user_id)
        abort(500)
    finally:
        conn.close()
    if user is None:
        abort(404)
    logging.info("User profile fetched for id=%d", user_id)
    return render_template('user.html', username=user['username'], email=user['email'])

@app.route('/search')
def search():
    q = request.args.get('q', '')
    conn = get_db()
    try:
        rows = conn.execute(
            "SELECT username FROM users WHERE username LIKE '%' || ? || '%'",
            (q,),
        ).fetchall()
    except sqlite3.Error:
        logging.exception("Database error during search")
        abort(500)
    finally:
        conn.close()
    logging.info("Search performed, rows=%d", len(rows))
    return render_template('search.html', q=q, rows=rows)

if __name__ == '__main__':
    init_db()
    app.run(host='0.0.0.0', port=5000, threaded=True)

A templates/user.html tartalma:

<!doctype html>
<title>Profil</title>
<h1>{{ username }}</h1>
<p>{{ email }}</p>

A templates/search.html tartalma:

<!doctype html>
<title>Keresés</title>
<h1>Keresés: {{ q }}</h1>
<ul>{% for row in rows %}<li>{{ row['username'] }}</li>{% endfor %}</ul>

A Jinja2 a {{ }} szintaxissal automatikusan HTML-escape-el, ezért a visszavert q és a felhasználónév is szövegként jelenik meg. A LIKE '%' || ? || '%' kötött paramétert használ, így az injekciós bemenet szó szerinti minta lesz. A napló csak az eseményt és a találatok számát rögzíti, a keresőkifejezést nem, mert az személyes adatot tartalmazhat. Az init_db() és a seed ugyanaz, mint a hibás változatban, és a __main__ belépési pont mindkettőt futtathatóvá teszi.

GET /users/1 200 Az alice profilja, escape-elt kimenettel
GET /users/999 404 Nincs ilyen felhasználó
GET /users/abc 404 Az int konverter a függvény előtt elutasítja

A hibás változatnál ugyanezek a kérések a /search esetében ' OR 1=1-- bemenetre mindkét felhasználót visszaadják, a <script> nyers tagként jelenik meg, a {{7*7}} pedig 49-re értékelődik. A /users/-1 ott is 404, mert azt a konverter utasítja el, nem a függvény saját ellenőrzése.

9.2.30 Önellenőrző kérdés

Adott egy Java kódrészlet, amely egy felhasználói azonosítót vár, és a következőt hajtja végre:

String query = "SELECT * FROM users WHERE id = " + userId;
Statement stmt = connection.createStatement();
ResultSet rs = stmt.executeQuery(query);

Melyik review-szempontot sérti a kód, és milyen védelmi mintát alkalmaznál? Válaszodban indokold meg a döntést.

Elvárt válasz: A kód SQL injectionre hajlamos, mert a userId felhasználói bemenetet közvetlenül fűzi a lekérdezésbe. A védelmi minta a paraméterezett lekérdezés PreparedStatement használatával:

String query = "SELECT * FROM users WHERE id = ?";
PreparedStatement stmt = connection.prepareStatement(query);
stmt.setString(1, userId);
ResultSet rs = stmt.executeQuery();

A paraméterezett lekérdezés biztosítja, hogy a bemenet ne lehessen SQL kód része, mert az adatbázismotor külön kezeli a paramétert.
