5.1 Modulok és láthatóság: header nélküli világ

5.1.1 Motiváció: miért nincs header?

Egy tipikus C++-projektben egy új típushoz legalább két fájl tartozik: a store.hpp deklarációval, include guarddal vagy #pragma once-szal, és a store.cpp definícióval. A headerben ügyelni kell arra, hogy csak teljes típusokra mutató okos pointerek és referenciák szerepeljenek, ha el akarjuk kerülni a fölösleges include-okat; a ciklikus függőséghez előre deklaráció kell; a namespace rkv_core nyitó-záró blokkok pedig vizuálisan növelik a zajt. A helyes include-sorrend, a rejtett ODR-hiba és a sablonok headerbe kényszerítése mind a fejlesztő terhe.

A Rust ezt a problémát nyelvi szinten eltávolítja: nincs header, nincs include guard, és nincs külön deklarációs és definíciós fázis. A modulrendszer a crate-en belül hierarchikusan rendezi a kódot, a láthatóságot pedig a pub kulcsszó és a modulhatárok szabályozzák. A névterek szerepét maguk a modulok töltik be, de a láthatóság alapértelmezése éppen fordított, mint C++-ban: ami pub, az publikus, minden más privát.

5.1.2 Fogalmak és szabályok

Definíció (modul). A modul a Rust szervezési egysége: típusokat, függvényeket, konstansokat és más modulokat tartalmazó névtér. A modulok a mod kulcsszóval jönnek létre, és fizikailag fájlba vagy könyvtárba szervezhetők.

Definíció (crate gyökér). Minden crate-nek egyetlen gyökere van: könyvtári crate-nél a src/lib.rs, bináris crate-nél a src/main.rs. Ez a gyökér jelenti a modulhierarchia tetejét; a crate:: útvonal innen indul.

Szabály (privát alapértelmezés). Ha egy elem – modul, típus, mező, függvény – elé nem írunk pub-ot, akkor az az adott modulban és annak leszármazott moduljaiban látható, más modulok számára nem.

Szabály (gyermekmodul hozzáférése). A gyermekmodul látja a szülő privát elemeit is; a privát határ nem a fájlok, hanem a modulok között húzódik. A szülő modul viszont nem látja a gyermekmodul privát elemeit.

Szabály (fordítási egység = crate). A Rust-fordító a crate-et fordítja le; a modulokra bontás nem hoz létre külön fordítási egységet. A use nem szúr be kódot, mint a #include, hanem csak rövidített elérési utat vezet be. Ennek következménye, hogy a modulok sorrendje és a fájlok közötti függőség nem befolyásolja a deklarációk elérhetőségét – a teljes crate „egyszerre” látható a fordító számára.

A láthatósági szintek:

  • pub – mindenki számára látható, a crate-en kívül is;
  • pub(crate) – csak az aktuális crate belsejében látható. Egy workspace több crate-ből áll (itt rkv-core, rkv-cli, rkv-server), és ezek egymás számára külső crate-ek: az rkv-core pub(crate) eleme az rkv-cli-ből és az rkv-server-ből nem látható;
  • pub(super) – a szülőmodulban (és annak leszármazottaiban) látható;
  • pub(in path) – csak a megadott, a környező modulok közül való útvonalon belül látható (például pub(in crate::outer));
  • nincs módosító – privát.

Három szintű modulhierarchián mutatjuk meg a szabályokat, konkrét engedett és tiltott útvonalakkal. A példa önálló (rustc vagy cargo new); a tiltott sorok kommentben állnak, a fordító üzenetével:

mod outer {
    pub struct Visible;           // pub típus, de a hatókörét a privát `outer` korlátozza
    fn secret() {}                // privát: `outer` és a gyermekei látják
    pub(super) fn for_parent() {} // pub(super): a szülő (itt a crate gyökér) is látja

    mod hidden {
        pub struct Exposed;       // pub típus egy PRIVÁT modulban
    }
    pub fn make_exposed() -> impl std::fmt::Debug {
        let _ = hidden::Exposed;  // `outer`-ből elérhető
        "Exposed"
    }

    pub mod middle {
        pub(in crate::outer) fn inner_only() {} // csak `outer`-en belül látható
        pub mod inner {
            pub fn call_up() {
                super::super::secret();     // OK: a gyermek látja a szülő privát elemét
                super::super::for_parent(); // OK
                super::inner_only();        // OK: pub(in crate::outer), és outer-en belül vagyunk
            }
        }
    }
}

fn main() {
    outer::for_parent();             // OK: pub(super), a crate gyökér a szülő
    let _v = outer::Visible;         // OK: a gyökér látja a privát `outer`-t (testvérmodul), Visible pub
    outer::middle::inner::call_up(); // OK: minden köztes modul pub
    println!("{:?}", outer::make_exposed());
    // outer::secret();              // E0603: function `secret` is private
    // outer::middle::inner_only();  // E0603: function `inner_only` is private (main nincs outer-ben)
    // let _e = outer::hidden::Exposed; // E0603: module `hidden` is private, bár Exposed pub
}

Ellenőrzött viselkedés: a kód lefordul és a "Exposed" sort írja ki; a három kikommentezett sor egyenként E0603 hibát ad. A tanulság: a pub elem hozzáférhetősége a teljes útvonal láthatóságán múlik (a privát hidden modulban lévő pub típus kívülről nem érhető el), a pub(super) a szülőtől látható, a pub(in path) pedig csak a megnevezett modulban.

A pub(crate) és a workspace határa külön fogalom:

Kódblokk — fájl: core/src/lib.rs és cli/src/main.rs (két crate-es próba-workspace, a cli path-függősége a core) · művelet: új fájlok · ellenőrzés: cargo build → E0624 az cli-ben

// core/src/lib.rs
pub struct Store;
impl Store {
    pub fn new() -> Self { Store }
    pub(crate) fn apply(&mut self) {} // csak a `core` crate-en belül
}
pub fn internal(s: &mut Store) { s.apply(); } // azonos crate-ből hívható

// cli/src/main.rs
fn main() {
    let mut s = core::Store::new();
    s.apply(); // error[E0624]: method `apply` is private
}

A use és a pub use közötti különbség kulcsfontosságú: a use store::Store; csak a jelenlegi modulban hozza létre a rövid nevet, míg a pub use store::Store; a nevet a modul API-jának részeként kifelé is elérhetővé teszi. Ez utóbbit újraexportálásnak (re-exportnak) nevezzük, és az idiomatikus Rust gyakran így takarja el a belső modulszerkezetet.

5.1.3 C++ és Rust összevetés

A C++-oldalon a névtér és a header gondoskodik a szervezésről:

// store.hpp
#pragma once
#include <string>
#include <unordered_map>

namespace rkv_core {
class Store {
public:
    void set(const std::string& key, const std::string& value);
private:
    std::unordered_map<std::string, std::string> data_;
};
}

A Rust-megfelelő egy modulfájl, amelyben a láthatóság minden elemnél explicit:

// src/store.rs
use std::collections::HashMap;

pub struct Store {
    data: HashMap<String, String>,
}

impl Store {
    pub fn set(&mut self, key: String, value: String) {
        self.data.insert(key, value);
    }
}

A legfontosabb különbség: a Rust-kódban a Store típus pub, ezért a crate-en kívül is elérhető; a data mező viszont privát, ezért kívülről nem lehet közvetlenül elérni. A C++ private: szakasz helyett itt a mező előtti pub hiánya jelzi ugyanezt. A Rust névtere a modulokhoz kötődik; ezek lehetnek külön fájlban, de inline is (mod name { ... } szabályos kapcsos blokkos modul), nem pusztán zárójel-párral jönnek létre, hanem a modulhatárokkal, és nem kell külön header és forrásfájl közötti deklaráció-egyezést karbantartani.

A pub(crate) tipikus belső API-khoz való: olyan segédfüggvényhez, amelyet a crate más moduljai használnak, de a könyvtár felhasználója nem hívhat:

// src/store.rs
impl Store {
    // Az rkv-core más moduljai (például a command) használják; az rkv-cli és az
    // rkv-server külön crate, ezért onnan nem látható. Ahhoz `pub` kellene.
    pub(crate) fn apply(&mut self, cmd: &crate::command::Command) -> Result<(), crate::error::Error> {
        // ...
    }
}

A use szintaxisa hasonlít a C++ using-ra, de nem hoz létre másolatot vagy láthatósági összefonódást:

using rkv_core::Store;   // C++: név bevezetése
use crate::store::Store; // Rust: rövid név bevezetése

Kódblokk — fájl: rkv-core/src/store.rs · művelet: új fájl (a korábbi lib.rs tartalma, a tesztekkel együtt) · ellenőrzés: cargo test -p rkv-core

// rkv-core/src/store.rs
use std::collections::HashMap;

/// A kulcs–érték tároló. A kulcs `String`, az érték `Vec<u8>`.
///
/// A `data` mező privát: a külső kód csak a publikus API-n keresztül férhet hozzá.
#[derive(Debug, Default)]
pub struct Store {
    data: HashMap<String, Vec<u8>>,
}

impl Store {
    /// Üres tároló létrehozása.
    pub fn new() -> Self {
        Self {
            data: HashMap::new(),
        }
    }

    /// Kulcs–érték pár beillesztése. Felülírja a korábbi értéket.
    pub fn set(&mut self, key: String, value: Vec<u8>) {
        self.data.insert(key, value);
    }

    /// Egy kulcs értékének lekérdezése. `None`, ha nincs ilyen kulcs.
    pub fn get(&self, key: &str) -> Option<&Vec<u8>> {
        self.data.get(key)
    }

    /// Kulcs törlése. Visszaadja a törölt értéket, ha létezett.
    pub fn delete(&mut self, key: &str) -> Option<Vec<u8>> {
        self.data.remove(key)
    }

    /// Az összes kulcs rendezetlen listája.
    pub fn keys(&self) -> Vec<String> {
        self.data.keys().cloned().collect()
    }

    /// Az összes kulcs törlése.
    pub fn clear(&mut self) {
        self.data.clear();
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn set_and_get() {
        let mut store = Store::new();
        store.set("kulcs".to_string(), b"ertek".to_vec());
        assert_eq!(store.get("kulcs"), Some(&b"ertek".to_vec()));
    }

    #[test]
    fn delete_returns_old_value() {
        let mut store = Store::new();
        store.set("a".to_string(), vec![1, 2, 3]);
        let old = store.delete("a");
        assert_eq!(old, Some(vec![1, 2, 3]));
        assert!(store.get("a").is_none());
    }
}

Kódblokk — fájl: rkv-core/src/error.rs · művelet: új fájl · ellenőrzés: cargo build -p rkv-core

// rkv-core/src/error.rs
use std::fmt;

/// Az rkv-core hibáinak közös típusa.
#[derive(Debug)]
pub enum Error {
    KeyNotFound,
    Io(std::io::Error),
}

impl fmt::Display for Error {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            Error::KeyNotFound => write!(f, "kulcs nem található"),

    }
}

impl std::error::Error for Error {}

5.1.4.3 3. ábra: a modulszerkezet

rkv-core (crate gyökér: lib.rs)
  ├── mod store    (store.rs)
  ├── mod command  (command.rs)
  └── mod error    (error.rs)

A három modul a crate gyökerének testvére (nem egymás almodulja);
a lib.rs re-exportjai (pub use) teszik elérhetővé a típusokat kívülről.

A modulfa azt mutatja, hogy a külső crate-ek a lib.rs re-exportjain keresztül érik el a típusokat; a modulok közötti belső kapcsolatot a crate:: kezdetű útvonalak adják (például use crate::error::Error).

Ellenőrzési pont. Az rkv-core három modulból áll (command, error, store), a gyökérből a Command, Error és Store re-exportálva. A cargo build --workspace hibátlan, a cargo test --workspace az rkv-core 4 és az rkv-cli 2 tesztjét sikeresen futtatja; a Store API-ja ugyanaz, mint a Structok és metódusok: impl blokkok, asszociált függvények végén.

Továbbvitt eredmény. Ez a store, command és error modulokra épülő szerkezet az alapja a Saját hibatípusok: enum-hibák, thiserror, anyhow alfejezet Error bővítésének; a Trait-ek és generikusok alfejezet itt vezeti be a Storage traitet a Store fölé; a Unit-, integrációs és dokumentációs tesztek alfejezet pedig ezeket a modulokat teszteli külön fájlokban.

5.1.5 Tipikus hibák és átállási csapdák

  1. Minden pub C++-os beidegződésből. A C++ public: osztályszakaszhoz szokott fejlesztő gyakran minden mezőt és metódust pub-ra állít, hogy „majd később elrejti”. Ezzel azonban a Rust éppen a fő előnyét veszíti el: a privát adat invariánsát a fordító kényszeríti ki. A helyes stratégia: kezdetben minden privát, és csak a valóban szükséges elem kapjon pub-ot. A pub(crate) a belső használatra való.

  2. A use és a #include összemosása. A C++ #include a fájlt szó szerint beszúrja, és a sorrend befolyásolhatja a fordítást. A Rust use pusztán rövidítés: ha a use-t elhagyjuk, a teljes útvonal (crate::store::Store) ugyanúgy működik. Nincs szükség include guardra, és a modulok sorrendje sem számít – a fordító a crate minden modulját egyszerre látja.

  3. A moduldeklaráció és a modulfájl összekeverése. Két különböző hiba tartozik ide, és a fordító mást mond rájuk. (a) Ha létrehozzuk a src/store.rs fájlt, de a lib.rs-be nem írjuk be a mod store; sort, a fordító a fájlt egyszerűen nem tölti be: a puszta létezése semmilyen hibát nem okoz. A hiba csak ott jelentkezik, ahol a modulra hivatkozunk: a use crate::store::Store; sor a következő diagnosztikát adja:

error[E0432]: unresolved import `crate::store`
  1. Fordítva, ha a lib.rs-ben ott a pub mod store;, de a fájl hiányzik (vagy elírtuk a nevét), a következő hibát kapjuk:
error[E0583]: file not found for module `store`

A fordító azt javasolja, hogy hozzuk létre a src/store.rs vagy a src/store/mod.rs fájlt. A C++-szal ellentétben tehát a fájlrendszer önmagában nem része a fordításnak: modul csak mod deklarációval lesz egy fájlból.

  1. Re-export nélküli, mélyen tagolt API. Ha a külső kód minden típust a teljes útvonalon (rkv_core::store::Store) kénytelen elérni, a belső átszervezés minden felhasználót megtör. Az idiomatikus megoldás a pub use a crate gyökerében: a felhasználó a stabil rkv_core::Store nevet látja, a belső modulok pedig szabadon mozgathatók.

5.1.6 Feladatok

5.1.6.1 1. Feladat – Lefordul-e és miért?

Adott a következő kód:

mod service {
    pub struct Config {
        pub(crate) timeout_ms: u64,
    }

    pub fn create_config() -> Config {
        Config { timeout_ms: 1000 }
    }
}

fn main() {
    let cfg = service::create_config();
    println!("{}", cfg.timeout_ms);
}

Fordul-e a kód? Magyarázd el, hogy a pub(crate) láthatóság mit enged meg ebben a bináris crate-ben, és mi lenne a helyzet, ha a pub(crate) helyett pub(super) állna?

5.1.6.2 2. Feladat – C++-kód átírása idiomatikus Rustra

Alakítsd át a következő C++ fejlécet egyetlen Rust modullá (src/message.rs), ügyelve a láthatóságra és a privát alapértelmezésre:

#pragma once
#include <string>

namespace mail {
class Message {
public:
    explicit Message(std::string body);
    const std::string& body() const;
private:
    std::string body_;
};
}

A modul legyen pub, a típus pub, a mező privát. A body() visszatérési típusa Rustban &str legyen.

5.1.6.3 3. Feladat – rkv-bővítés: parancs-feldolgozó a command modulban

Az rkv-core/src/command.rs fájlban hozz létre egy pub fn parse(line: &str) -> Result<Command, crate::error::Error> függvényt, amely a szöveges protokoll egy sorát a Mintaillesztés: match, if let, let else és a minták alfejezetben rögzített nyelvtan szerint értelmezi; a hibát egy új Error::Parse(String) variáns jelezze. Ezzel az értelmező a CLI-ből a könyvtárba kerül, így a későbbi szerver is ugyanazt használhatja. A kulcsellenőrzést végző segédfüggvény legyen pub(crate): a crate-en belül bárhol hívható, de az rkv-core publikus API-jának nem része.

5.1.6.4 4. Feladat – Hibajavítás: láthatóság és re-export

A következő kis crate nem fordul. Javítsd a kódot úgy, hogy a main.rs hozzáférjen a Store típushoz a gyökérből (demo::Store néven), a data mező viszont maradjon privát.

// src/lib.rs
mod store {
    pub struct Store {
        data: Vec<u8>,
    }

    impl Store {
        pub fn new() -> Self {
            Store { data: Vec::new() }
        }
    }
}

// src/main.rs
fn main() {
    let s = demo::Store::new();
    println!("{:?}", s.data);
}

5.1.7 Megoldások

5.1.7.1 1. Feladat megoldása

A kód lefordul. A pub(crate) láthatóság a teljes aktuális crate-en belül érvényes, tehát a main függvény (amely ugyanabban a bináris crate-ben van) eléri a timeout_ms mezőt. Ha pub(super) állna, a mező csak a service modul szülőjében, azaz a crate gyökerében lenne látható – mivel a main a crate gyökerében van, az is működne. Ha viszont a service modul egy gyermekmodulban lenne, a pub(super) már nem engedné a hozzáférést a gyermekmodulból.

5.1.7.2 2. Feladat megoldása

// src/message.rs
pub struct Message {
    body: String,
}

impl Message {
    pub fn new(body: String) -> Self {
        Self { body }
    }

    pub fn body(&self) -> &str {
        &self.body
    }
}

A moduldeklaráció a lib.rs-ben: pub mod message;. A body mező privát, a body() metódus publikusan ad olvasási hozzáférést.

5.1.7.3 3. Feladat megoldása

Az error.rs bővítése az új variánssal és a Display ágával:

Kódblokk — fájl: rkv-core/src/error.rs · művelet: módosításrészlet: új variáns az Error-ban, új ág a Display-ben

// rkv-core/src/error.rs, az Error enumban:
    Parse(String),

// a Display match-jében:
            Error::Parse(msg) => write!(f, "értelmezési hiba: {msg}"),

A command.rs új függvényei. A nyelvtan ugyanaz, mint a Mintaillesztés: match, if let, let else és a minták parse_command-jáé; a különbség csak a hibatípus. A ? operátort itt még nem használjuk (azt a Result, a ? operátor és a panic helye vezeti be), helyette a Result::map és a match alakítja a hibát:

Kódblokk — fájl: rkv-core/src/command.rs · művelet: beillesztés az impl Command blokk után · ellenőrzés: cargo test -p rkv-core

// rkv-core/src/command.rs
use crate::error::Error;

/// Kulcs (vagy prefix) ellenőrzése a protokoll nyelvtana szerint.
/// `pub(crate)`: a crate-en belül újrahasznosítható, kívülről nem látszik.
pub(crate) fn parse_key(s: &str) -> Result<String, Error> {
    if s.is_empty() || s.chars().any(|c| c.is_whitespace() || c.is_control()) {
        Err(Error::Parse(format!("érvénytelen kulcs: {s:?}")))
    } else {
        Ok(s.to_string())
    }
}

/// A szöveges protokoll egy sorát `Command`-dá alakítja (nyelvtan: r009).
pub fn parse(line: &str) -> Result<Command, Error> {
    let (verb, rest) = match line.split_once(' ') {
        Some((verb, rest)) => (verb, Some(rest)),
        None => (line, None),
    };
    match (verb, rest) {
        ("GET", Some(key)) => parse_key(key).map(Command::Get),
        ("DEL", Some(key)) => parse_key(key).map(Command::Delete),
        ("SET", Some(rest)) => match rest.split_once(' ') {
            Some((_, value)) if value.is_empty() || value.contains(['\n', '\r']) => {
                Err(Error::Parse("a SET értéke üres vagy sortörést tartalmaz".into()))
            }
            Some((key, value)) => parse_key(key).map(|k| Command::Set(k, value.to_string())),
            None => Err(Error::Parse("SET érték nélkül".into())),
        },
        ("LIST", None) => Ok(Command::List(None)),
        ("LIST", Some(prefix)) => parse_key(prefix).map(|p| Command::List(Some(p))),
        ("GET" | "DEL" | "SET", None) => Err(Error::Parse(format!("{verb} argumentum nélkül"))),
        (other, _) => Err(Error::Parse(format!("ismeretlen parancs: {other:?}"))),
    }
}

Ez a függvény pub, tehát kívülről is hívható: az rkv-cli a saját parse_command-ja helyett rkv_core::command::parse-t hívhat. A parse_key pub(crate), ezért az rkv-cli nem látja; ha megpróbálná, E0603 („function parse_key is private”) hibát kapna. A GET k extra itt is hiba (a "k extra" kulcs szóközt tartalmaz), a SET k hello world értéke pedig a teljes "hello world".

5.1.7.4 4. Feladat megoldása

A hiba oka: a store modul mod (privát) deklarációval jön létre, és a típus nincs re-exportálva a gyökérbe. Javítás:

// src/lib.rs
pub mod store {
    pub struct Store {
        data: Vec<u8>,
    }

    impl Store {
        pub fn new() -> Self {
            Store { data: Vec::new() }
        }
    }
}

pub use store::Store;

A pub use után a demo::Store név a crate gyökerében elérhető. A data mező továbbra is privát, így a main.rs-ben a println!("{:?}", s.data); sor továbbra is hibát ad; ezt a sort el kell távolítani, vagy egy publikus gettert kell bevezetni.

5.1.8 Rövid összefoglaló

A Rust modulrendszer header és include guard nélkül szervezi a kódot. A crate gyökere a lib.rs vagy main.rs; a mod deklaráció hozza létre a modulnévtérben a store, command és error egységeket. A láthatóság alapértelmezése privát; a pub kifelé, a pub(crate) a crate-en belül tesz elérhetővé, a pub(super) a szülőmodulra korlátoz. A use rövidített útvonal, a pub use újraexportálja a nevet a modul API-jába; ezért a külső kód rkv_core::Store, rkv_core::Command és rkv_core::Error néven éri el a típusokat. Az rkv-core moduljai: store.rs (Store, pub(crate) fn apply), command.rs (Command), error.rs (Error). Továbbvitt eredmény: ez a modulszerkezet az alapja a Saját hibatípusok, a Trait-ek és generikusok és a Tesztelés alfejezeteknek.
