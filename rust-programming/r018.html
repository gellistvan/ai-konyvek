9.1 Slice-ok, String és &str, UTF-8

9.1.1 Motiváció

A C++-ban a std::string_view megjelenése óta természetes, hogy string-függvények nem birtokló nézetet fogadnak, nem teljes std::string másolatot. A std::string_view azonban nem véd meg a dangling pointertől: ha az a std::string, amelyre mutat, kikerül a hatóköréből, a program viselkedése definiálatlan. Rustban a &str ugyanezt a koncepcionális szerepet tölti be, de a Élettartam-annotációk és az elision szabályai alfejezetben tanult lifetime-rendszerrel a fordító fordítási időben kizárja, hogy a nézet túlélje a birtokolt puffert. Ebben az alfejezetben a slice-ok, a String/&str páros és az UTF-8 kezelés C++-os megfelelőit járjuk körbe.

9.1.2 Fogalmak és szabályok

9.1.2.1 Definíciók

Definíció (slice). A &[T] típusú slice fat pointer: egy adatmutató és egy hossz. Nem tulajdonos, nem allokál; csak egy meglévő, egybefüggő [T] tömbre mutat. A &mut [T] mutálható nézet, de a hossza ekkor is rögzített.

Definíció (&str). A &str string slice: egy UTF-8 kódolású bájtsorozatra mutató fat pointer (mutató + bájthossz). Garantáltan érvényes UTF-8, és nem tulajdonos. A &str nem null-végű – a hosszt a fat pointer tárolja.

Definíció (String). A String birtokolt, heap-en tárolt, UTF-8 kódolású szövegpuffer. A Vec<u8>-hoz hasonlóan három szóból álló tulajdonos: mutató, hossz, kapacitás. A String tulajdonosa a puffernek, és a Drop implementáció felszabadítja.

9.1.2.2 Szabályok

Szabály (paramétertípus-választás). Függvényparaméterben szöveget &str-ként, bájtpuffert pedig &[T]-ként fogadjunk, ha a függvény csak olvassa az adatot, vagy ha az eltárolt értéke a bemenet élettartamához kötött marad (nézet-típus, például Parser<'a>). A String vagy Vec<T> paraméter arra való, ha a függvény birtokba veszi az értéket, és a bemenettől független, hosszabb életű tulajdonként tárolja vagy módosítja. A másolás költsége a tényleges átalakításhoz kötött: tulajdonjog-átadásnál (String) nincs másolat, &str-ből tulajdon készítésekor van.

Továbbvitt eredmény. Ezt a paramétertípus-választási döntést a API-tervezés Rustban: irányelvek és ergonómia alfejezetben általános API-elvként, a C ABI: extern “C”, repr(C), bindgen és cbindgen alfejezetben pedig az FFI-határokra alkalmazva visszük tovább.

Szabály (deref coercion). Ahol &str várt, &String is átadható, mert a String automatikusan kölcsönözhető &str-ként. A részletes mechanizmust (a Deref traitet) a A standard trait-ek: konverziók, formázás, Default, Deref, Borrow alfejezet tárgyalja; itt annyit jegyzünk meg, hogy a paraméter típusa legyen &str, és a hívás &my_string-gel is működik.

Szabály (UTF-8 indexelés). A String és a &str nem indexelhető [] operátorral egyetlen számmal, mert a s[i] bájtot adna, nem karaktert. A s[i..j] szeletelés bájtindexekkel dolgozik, és pánikol, ha a határok nem Unicode skalárérték-határok. A „karakter” szónak három különböző egysége van:

Egység Mit jelent Eszköz Példa: é előre komponálva (U+00E9) Példa: e + kombináló ékezet (U+0065 U+0301)
bájt UTF-8 kódolt bájt len(), bytes(), s[a..b] 2 3
Unicode skalárérték a char típus egy értéke chars(), char_indices() 1 2
grapheme cluster a felhasználó által látott karakter külső crate (unicode-segmentation) 1 1

A két é megjelenése azonos, a bájtsorozatuk és skalárértékeik száma viszont eltér, és ==-vel nem egyenlők. A chars() és a char_indices() skalárértéket, nem látható karaktert kezelnek: egy kombinált ékezetes szövegen a chars().take(3) három skalárértéket ad, ami akár két látható karakter is lehet. Látható karakterekhez grapheme-szegmentálás kell, amelyet a standard könyvtár nem tartalmaz.

9.1.3 C++ és Rust összevetés

C++-ban a std::string_view a nem birtokló nézet; a programozó felelőssége, hogy ne lógjon a levegőben:

#include <string>
#include <string_view>
#include <iostream>

std::string_view first_word(std::string_view s) {
    auto pos = s.find(' ');
    return pos == std::string_view::npos ? s : s.substr(0, pos);
}

int main() {
    std::string text = "hello world";
    std::string_view word = first_word(text);
    std::cout << word << '\n'; // hello
    // Ha text kikerül a hatókörből, a word dangling lesz.
}

A Rust-megfelelő ugyanazt a nem birtokló nézetet használja, de az élettartamot a fordító ellenőrzi:

fn first_word(s: &str) -> &str {
    match s.find(' ') {
        Some(pos) => &s[..pos],
        None => s,
    }
}

fn main() {
    let text = String::from("hello world");
    let word = first_word(&text);
    println!("{word}"); // hello
    // A borrow checker garantálja, hogy word nem éli túl textet.
}

A különbség: a C++ kódban a string_view élettartama a programozón múlik; a Rust kódban a &str visszatérési típusához az elision szabályok alapján a bemenő &str élettartama kötődik, így a hívó String nem mozdulhat el, amíg a word él. A &s[..pos] kifejezés pedig slice-ot készít: ugyanarra a pufferre mutató fat pointert, nem másolatot.

A String és a &str viszonyát a memóriában az alábbi ábra szemlélteti:

A word ugyanarra a kupacpufferre mutat, mint a s, de a hossza csak 5, tehát a "hello" előtagot látja. A kupacpuffer adatai nem másolódnak; a String és a &str is ugyanazt a memóriát használja.

9.1.4 Kidolgozott labor: UTF-8 határok és &str

Munkakönyvtár: ~/rust-labor/r018-slices.

Hozzuk létre az önálló kísérleti crate-et:

cargo new r018-slices
cd r018-slices

A src/main.rs tartalma:

fn first_word(s: &str) -> &str {
    match s.find(' ') {
        Some(pos) => &s[..pos],
        None => s,
    }
}

fn print_chars(s: &str) {
    println!("String: {s:?}, byte hossz: {}", s.len());
    for (byte_idx, ch) in s.char_indices() {
        println!("  byte {byte_idx}: {ch:?}");
    }
}

fn main() {
    let text = String::from("hello world");
    let word = first_word(&text);
    println!("first word: {word}");

    let s = String::from("árvíz");
    print_chars(&s);

    // Fél-nyílt bájttartományok: a vég kizárt, és karakterhatárra kell esnie.
    for range in [0..2, 0..1] {
        match s.get(range.clone()) {
            Some(sub) => println!("{range:?} mint str: {sub}"),
            None => println!("{range:?} nem karakterhatár"),
        }
    }
}

Futtatás:

cargo run

Várt kimenet:

first word: hello
String: "árvíz", byte hossz: 7
  byte 0: 'á'
  byte 2: 'r'
  byte 3: 'v'
  byte 4: 'í'
  byte 6: 'z'
0..2 mint str: á
0..1 nem karakterhatár

Magyarázat: az árvíz string hossza 7 bájt, de 5 karakter. A char_indices() a karakterek kezdő bájtindexét adja: 0, 2, 3, 4, 6, a szöveg vége pedig a 7. Egy a..b tartomány fél-nyílt: a b indexű bájt már nem tartozik bele, és mindkét végpontnak e határok (0, 2, 3, 4, 6, 7) egyikére kell esnie. A 0..2 ezért érvényes, és az "á" két bájtját adja; a 0..1 viszont az "á" közepén végződne, így a get None-t ad. A &s[0..1] ugyanerre pánikolna; a get változat biztonságos. A char_indices() bájt-indexeket ad vissza karakterenként, így láthatjuk, hogy a karakterek nem egyenlő szélességűek.

9.1.5 Slice-szerű nézetek a szövegen túl: OsStr, Path, CStr, Cow

A &str nem az egyetlen nem birtokló szövegnézet. A Rust standard könyvtára a következő típusokat kínálja, amikor a String/&str nem megfelelő:

  • OsStr/OsString: platformfüggetlen, nem feltétlenül UTF-8 szövegnézet. Unixon tetszőleges bájtsor; Windowson a belső reprezentáció platformfüggő implementációs részlet (a Windows API-val széles karakteres, UTF-16 átalakítással kommunikál), ezért az OsStr belső kódolása nem hordozható szerződés. Fájlnevekhez és környezeti változókhoz használjuk, mert a fájlrendszer nem garantál UTF-8-at.
  • Path/PathBuf: OsStr-ön alapuló elérésiút-típusok. A Path a nem birtokló, a PathBuf a birtokolt változat.
  • CStr/CString: null-végű bájtsorozat, belső nullbájt nélkül, és nem feltétlenül UTF-8. A &CStr kölcsönzött, a CString birtokolt változat. Szerepük a C-s const char*-é, de maguk nem C ABI-típusok: az extern "C" függvények aláírásában mindig nyers mutató (*const c_char, illetve *mut c_char) áll, a CStr/CString a Rust-oldali biztonságos kezelést adja. A kapcsolat: a CString::new ellenőrzi, hogy nincs belső nullbájt (különben NulError); az as_ptr() egy *const c_char mutatót ad a hívás idejére (a CString-nek addig élnie kell); a C-től kapott mutatóból az unsafe CStr::from_ptr készít kölcsönzött nézetet; a to_str() ellenőrzi az UTF-8-at. Ha a tulajdonjog átkerül a C-oldalra, a CString::into_raw adja át a puffert, és csak a CString::from_raw veheti vissza (a Rust allokátorával kell felszabadítani, nem C free-vel). A C ABI: extern “C”, repr(C), bindgen és cbindgen alfejezet ugyanezt a szerződést használja.

A C++-os párok: a std::filesystem::path megfelelője a PathBuf/Path, a const char* megfelelője (szerepében) a &CStr (az ABI-n *const c_char), a std::string megfelelője a String. A választási szempont mindig az: ha a szöveg UTF-8 és a funkció nem igényel C ABI-t, használjunk String-et/&str-t; fájlrendszer-műveletnél Path-ot; C-FFI-nál a határon nyers *const c_char-t, a Rust-oldalon CStr/CString-et.

A std::borrow::Cow<'a, str> a clone-on-write típus. Akkor hasznos, ha egy függvény néha birtokolt String-et, néha kölcsönzött &str-t akar visszaadni anélkül, hogy mindig allokálna:

Szerződés: az expand_tabs a bemeneti szövegben minden tabulátort négy szóközre cserél. Ha nincs tabulátor, a bemenetet változtatás nélkül, allokáció nélkül adja vissza (Cow::Borrowed); ha van, új bájtokat kell előállítani, ezért Cow::Owned-ot ad. (Egy trim_start() nem alkalmas példa: az is &str szeletet ad, új bájtok nélkül.)

use std::borrow::Cow;

fn expand_tabs(s: &str) -> Cow<'_, str> {
    if s.contains('\t') {
        Cow::Owned(s.replace('\t', "    "))
    } else {
        Cow::Borrowed(s)
    }
}

Ellenőrzött viselkedés: expand_tabs("alma") → Cow::Borrowed("alma") (nincs allokáció); expand_tabs("a\tb") → Cow::Owned("a b").

Ha nincs elvégzendő munka, a függvény allokáció nélkül adja vissza a bemenetet; ha új bájtokat kell előállítani, akkor allokál. Ezt a Teljesítmény: mérés, profilozás, allokáció, release-beállítások alfejezetben visszük tovább.

Továbbvitt eredmény. A Cow<'a, str> típus használata a Teljesítmény: mérés, profilozás, allokáció, release-beállítások alfejezetben jelenik meg újra, ahol az allokáció elkerülését mérjük és hangoljuk.

9.1.6 Tipikus hibák és átállási csapdák

9.1.6.1 1. &String paraméter használata &str helyett

fn bad(s: &String) {
    println!("{s}");
}

fn good(s: &str) {
    println!("{s}");
}

fn main() {
    let s = String::from("hello");
    bad(&s);       // működik, mert &String
    // bad("hello"); // NEM fordul: &str nem &String
    good(&s);      // működik, deref coercion
    good("hello"); // működik
}

A bad függvényt nem lehet &str-rel hívni; ezért a paraméter általában &str. Ez irányelv, nem nyelvi tiltás: ha a függvénynek String-specifikus API kell (például s.capacity(), amely &str-en nem létezik), az &String indokolt, és a clippy::ptr_arg sem jelzi. A cél a hívó rugalmassága, nem a típus kerülése.

9.1.6.2 2. Byte-szeletelés karakter közepén

let s = String::from("árvíz");
let sub = &s[0..1]; // pánikol: end byte index 1 is not a char boundary

Ez a kód lefordul, de futás közben pánikol, mert az 1. bájtindex az "á" karakter (0–1. bájt) közepére esik; a &s[0..2] viszont szabályos, és "á"-t ad. A pontos üzenet verziófüggő, de a lényeg mindig a karakterhatár-sértés. Javítás: használjunk get-et és Option-t, vagy karakter-alapú iterátorokat.

9.1.6.3 3. clone() a borrow checker „legyőzésére”

fn takes_string(s: String) {
    println!("{s}");
}

fn main() {
    let text = String::from("hello");
    takes_string(text.clone()); // felesleges allokáció
    // Helyesebb: fn takes_str(s: &str) és takes_str(&text)
}

A clone() megkerüli a borrow checkert, de felesleges allokációt és másolást végez. A helyes megoldás a kölcsönzés (&str), ha a függvény nem veszi birtokba az értéket.

9.1.7 Feladatok

9.1.7.1 a) Fogalmi kérdés

Melyik függvényparaméter a jobb, és miért: fn f(s: &String) vagy fn f(s: &str)? Mi a különbség hívásnál?

9.1.7.2 b) C++ kód átírása idiomatikus Rustra

Fordítsd le a következő C++ kódot idiomatikus Rustra. A std::span<const int> a nem birtokló nézet, amely a Rust &[i32] slice-nak felel meg:

#include <span>
#include <iostream>

void print_first(std::span<const int> xs) {
    if (!xs.empty()) {
        std::cout << xs[0] << '\n';
    }
}

9.1.7.3 c) Implementációs feladat az rkv előkészítésére

Írj egy parse_command(line: &str) -> Option<(&str, &str)> függvényt, amely a szöveges protokoll sorait bontja parancsnévre és maradékra. Szerződés: az elválasztó egyetlen ASCII szóköz (tabulátor nem); a GET pontosan egy, nem üres, szóközt nem tartalmazó argumentumot kér; a SET nem üres kulcsot és nem üres értéket (az érték szóközt tartalmazhat); a visszaadott maradék a GET esetén a kulcs, a SET esetén a kulcs érték rész; minden más bemenet (üres sor, ismeretlen parancs, hiányzó vagy többletargumentum, tabulátoros sor) None. A visszatérési típus &str legyen, ne String, és használj split_once-t. (Ez bontás, nem teljes protokoll-elemző: az értékvalidálást a Mintaillesztés: match, if let, let else és a minták parsere végzi.) (Ezt a paramétertípus-választást visszük tovább a API-tervezés Rustban: irányelvek és ergonómia és a C ABI: extern “C”, repr(C), bindgen és cbindgen alfejezetben.)

9.1.7.4 d) Hibajavítás

Az alábbi függvény pánikolhat egyes bemenetekre. Adj meg egy ilyen bemenetet, és javítsd a függvényt úgy, hogy Option<&str>-t adjon vissza (Some, ha legalább három Unicode skalárérték van, egyébként None), és ne pánikoljon. A név jelezze, hogy skalárértékről, nem látható karakterről van szó:

fn first_three_chars(s: &str) -> &str {
    &s[0..3] // hibás: byte, nem karakter
}

9.1.8 Megoldások

9.1.8.1 a) Megoldás

Az &str a jobb választás, mert a &String-et csak &String-gel lehet hívni, míg az &str-t &String és &str értékkel is (deref coercion révén). Ha a függvénynek nincs szüksége a tulajdonjogra, &str-t fogadjon.

9.1.8.2 b) Megoldás

fn print_first(xs: &[i32]) {
    if let Some(x) = xs.first() {
        println!("{x}");
    }
}

fn main() {
    let v = vec![1, 2, 3];
    print_first(&v);
}

A &v &Vec<i32>-ből &[i32]-re deref coercion történik. A C++ std::span<const int> a &[i32]-nek felel meg; az ürességvizsgálat Rustban a first() Option-jával történik.

9.1.8.3 c) Megoldás

fn parse_command(line: &str) -> Option<(&str, &str)> {
    let (cmd, rest) = line.split_once(' ')?;
    match cmd {
        "GET" if !rest.is_empty() && !rest.contains(' ') => Some((cmd, rest)),
        "SET" => {
            let (key, value) = rest.split_once(' ')?;
            if key.is_empty() || value.is_empty() { None } else { Some((cmd, rest)) }
        }
        _ => None,
    }
}

Ellenőrzött kimenetek: "" → None; "GET" → None; "GET a" → Some(("GET", "a")); "GET a b" → None; "SET k" → None; "SET k v" → Some(("SET", "k v")); "SET k v w" → Some(("SET", "k v w")); "GET\ta" (tabulátor) → None; "FOO x" → None; "GET " → None. A split_once &str-eket ad vissza, nem allokál. A valódi protokoll elemzésénél a DEL és LIST parancsokat is kezelni kell; ez a gyakorlat a &str alapú bontás mintáját mutatja.

9.1.8.4 d) Megoldás

Pánikoló bemenet például "éé" (két darab 2 bájtos karakter, hossz 4 bájt), ahol a 3. bájt a második karakter közepén van, így &s[0..3] pánikol.

Javítás (a név jelzi, hogy skalárértékekről van szó):

fn first_three_scalars(s: &str) -> Option<&str> {
    // a skalárértékek kezdő bájtindexei + a szöveg vége
    let mut ends = s.char_indices().map(|(i, _)| i).chain(std::iter::once(s.len()));
    let end = ends.nth(3)?; // None, ha 3-nál kevesebb skalárérték van
    s.get(..end)
}

Ellenőrzött viselkedés: first_three_scalars("árvíz") → Some("árv"); first_three_scalars("ab") → None; first_three_scalars("") → None; first_three_scalars("éé") → None (csak két skalárérték). A függvény skalárértékeket vág, nem látható karaktereket: a kombinált ékezetes "e\u{301}ab" szövegre Some("e\u{301}a")-t ad, ami három skalárérték, de csak két látható karakter. Pontosan három látható karakterhez grapheme-szegmentálás kellene. Az s.get(..end) biztonságosan ellenőrzi a karakterhatárt, ezért nem pánikol.

9.1.9 Rövid összefoglaló

A &[T] és a &str fat pointer: adatmutató és hossz, nem tulajdonos nézet. A String birtokolt, heap-en tárolt UTF-8 puffer, a Vec<u8>-hoz hasonló tulajdonosi szereppel. A függvényparaméterekben szöveget mindig &str-ként, bájtsorozatot &[T]-ként fogadjunk, hacsak a függvény nem szerzi meg a tulajdonjogot; ezt a döntést a API-tervezés Rustban: irányelvek és ergonómia és a C ABI: extern “C”, repr(C), bindgen és cbindgen alfejezet viszi tovább. A String nem indexelhető bájtonként, mert a karakterek több bájtosak lehetnek; használjunk chars(), bytes(), char_indices() vagy get() metódusokat. A Cow<'a, str> clone-on-write típus, amelyet a Teljesítmény: mérés, profilozás, allokáció, release-beállítások alfejezetben vizsgálunk tovább.

9.1.10 Források és ellenőrzési hiányok

A slice-ok, a String/&str, a char_indices, a split_once és a Cow a Rust standard könyvtár stabil API-jának részei; a hivatalos leírások a Rust Bookban és a std dokumentációjában találhatók. A példákban szereplő pontos pánik- és hibaüzenetek szövege verziófüggő; érdemes ellenőrizni a fejezet készítésekor használt toolchainen. A cargo new és a cargo run parancsok stabilak, a bemutatott kód a 2021-es és 2024-es edition szerint is lefordítható.
