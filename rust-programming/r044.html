19.1 C ABI: extern “C”, repr(C), bindgen és cbindgen

19.1.1 Motiváció

Egy évtizedes C++-kódbázis ritkán cserélhető le egyik napról a másikra Rustra. A gyakorlatban a két nyelv ugyanabban a folyamatban él: meglévő C vagy C++ könyvtárat hívunk Rustból, vagy egy új Rust komponenst teszünk elérhetővé a régi C++ kliens számára. A közös nevező a C ABI: a C függvényhívási konvenció, a C adatszerkezetek és a C stringek. A Rust nem beszéli a C++ osztályok, túlterhelt függvények, kivételek vagy sablonok nyelvét, de a C ABI-n keresztül bármilyen C++ kód elérhető, ha extern "C" függvényekbe csomagoljuk.

Az rkv mintaprojektben most azt a hidat építjük meg, amelyen a későbbi C++ kliens átkelhet: az rkv-ffi crate egy C API-t exportál, amelyet a C++-együttműködés a cxx crate-tel és a fokozatos migráció alfejezet használ tovább, a záróprojektben pedig a teljes rendszer része lesz.

19.1.2 Fogalmak és szabályok

Definíció. Az ABI (application binary interface) az a bináris szerződés, amely meghatározza, hogyan adjuk át az argumentumokat, hogyan rendezzük a struktúrákat, és hogyan nevezzük a szimbólumokat. A Rust alapértelmezett ABI-ja nem stabil, ezért C-vel való együttműködésnél mindig explicit extern "C" blokkot használunk.

Definíció. A #[repr(C)] attribútum C-kompatibilis memóriaelrendezést ad a Rust típusoknak: a mezők sorrendje megegyezik a deklaráció sorrendjével, nincs újrarendezés, és a padding a C szabályait követi. A #[repr(Rust)] (az alapértelmezett) esetén a fordító szabadon átrendezheti a mezőket, ezért C-nek átadott struktúrákhoz mindig #[repr(C)] kell.

Két külön kérdés. Egy FFI-határ tervezésekor két dolgot kell szétválasztani. (1) Az ABI-kompatibilitás azt dönti el, hogy a két oldal ugyanúgy értelmezi-e a bájtokat: #[repr(C)] elrendezés, C-kompatibilis mezőtípusok (c_int, mutatók, repr(C) structok, nem String/Vec/&T), a hívási konvenció (extern "C"). (2) Az értékérvényességi és ownership szerződés azt, hogy az átadott bájtok érvényes értéket jelentenek-e, ki szabadítja fel őket, meddig élnek, és használhatók-e egyszerre több szálról. Egy *const c_char ABI-szempontból tökéletes, a szerződés (NUL-végű? UTF-8? meddig él?) viszont nincs a típusában: ezt dokumentálni és ellenőrizni kell. Fordítva, egy repr(C) struct mezői csak akkor C-kompatibilisek, ha maguk is azok.

Ajánlás (nyers mutatók a határon). A Rust referencia (&T, &mut T) a C ABI-ban hívási szinten mutatóként adódna át, de a Rust-oldali érvényességi garanciái (nem null, igazított, él, kizárólagos vagy megosztott) C-ből nem kényszeríthetők ki. Ezért az egyszerű határ-API-ban nyers mutatókat (*const T, *mut T) használunk, és a függvény belsejében ellenőrizzük őket (null, hossz), mielőtt referenciát képzünk belőlük. Az ownership-átadásról a hívóval egyértelműen megállapodunk.

Szabály (panic a határon). Egy extern "C" függvényből kilépő Rust pánik nem terjedhet a C hívóba. A Rust 1.81 óta az extern "C" függvényből kilépő pánik a folyamat leállítását (abort) okozza (korábban UB volt). Három külön eset van: (a) Rust pánik az extern "C" Rust-exportban: abort, hacsak a függvény törzsét catch_unwind-del nem védjük; (b) külföldi kivétel (például C++ throw), amely Rust frame-eken át terjedne: szintén abort extern "C"-nél; ha ilyen terjedést szándékosan engedünk, az extern "C-unwind" ABI kell mindkét oldalon; (c) a panic = "abort" profil: ekkor nincs unwind, a catch_unwind nem fog el semmit, a pánik azonnal leállítja a folyamatot.

Az rkv-ffi explicit policyja: a crate panic = "unwind" profillal készül (ez a Cargo alapértelmezése dev és release profilban is), és minden exportált függvény törzse a guarded segédfüggvényen megy át, amely a pánikot RKV_PANIC státuszkóddá alakítja. A catch_unwind itt a ténylegesen pánikolható határ védelme, nem mindent felfogó háló: a szokásos hibákat (Result) továbbra is státuszkóddá alakítjuk, a catch_unwind csak a váratlan pánikot kezeli. Ha a projekt panic = "abort" profilt választ, a dokumentáció ezt vállalja: a pánik leállítja a folyamatot, RKV_PANIC nem keletkezik.

Szabály. A #[no_mangle] attribútum megakadályozza a szimbólum átnevezését, így a függvény neve a C linker számára látható marad. A Rust 2024-es editionben ez az attribútum az unsafe attribútumok közé került, ezért #[unsafe(no_mangle)] formában kell írni; a 2021-es editionben a #[no_mangle] továbbra is működik. (Ellenőrzési igény: a pontos szintaxis a telepített toolchain verziójától függ.)

19.1.3 C hívása Rustból: extern blokk és bindgen

Egy meglévő C könyvtár legegyszerűbb hívása kézzel írt extern blokkal történik. A 2024-es editionben az extern blokk unsafe extern "C", a C int Rust-megfelelője pedig a platformfüggetlen c_int (std::ffi::c_int), nem az i32:

// mylib.h
int add(int a, int b);
use std::ffi::c_int;

// Kézzel írt kötés (2024 edition: unsafe extern)
unsafe extern "C" {
    fn add(a: c_int, b: c_int) -> c_int;
}

fn main() {
    // SAFETY: a C függvénynek nincs előfeltétele, és a hívás nem sért Rust-invariánst.
    let sum = unsafe { add(2, 3) };
    println!("{sum}");
}

A linkeléshez a build.rs-ben meg kell adni a könyvtárat. Nagyobb C fejléchez a kézi fordítás hibalehetőség; erre való a bindgen, amely a C fejlécből generálja a Rust kötést. Az alábbi teljes, ellenőrzött példa a C forrást is lefordítja (a cc crate), a kötést az OUT_DIR-be generálja (nem a forrásfába), és onnan include!-olja. A Cargo.toml-ban [build-dependencies] közé cc és bindgen kerül; a bindgen a libclang könyvtárat igényli (Ubuntu: libclang-dev), amely a natív toolchain része.

Kódblokk — fájl: build.rs · művelet: új fájl egy önálló cargo new projektben (mellé mylib.c, mylib.h, wrapper.h, ahol a wrapper.h a #include "mylib.h" sort tartalmazza) · ellenőrzés: cargo run → 5

use std::env;
use std::path::PathBuf;

fn main() {
    println!("cargo:rerun-if-changed=mylib.c");
    println!("cargo:rerun-if-changed=mylib.h");
    println!("cargo:rerun-if-changed=wrapper.h");

    // A C forrás fordítása és statikus könyvtárba csomagolása (libmylib.a, a linkelést a cc crate kéri a Cargótól).
    cc::Build::new().file("mylib.c").compile("mylib");

    // A kötés generálása az OUT_DIR-be (nem a forrásfába).
    let bindings = bindgen::Builder::default()
        .header("wrapper.h")
        .generate()
        .expect("bindgen hiba");
    let out = PathBuf::from(env::var("OUT_DIR").unwrap());
    bindings.write_to_file(out.join("bindings.rs")).expect("a bindings írása nem sikerült");
}

Kódblokk — fájl: src/main.rs · művelet: teljes csere · ellenőrzés: cargo run → 5

#![allow(non_upper_case_globals, non_camel_case_types, non_snake_case, dead_code)]
include!(concat!(env!("OUT_DIR"), "/bindings.rs"));

A bindgen a függvényeket unsafe extern "C" blokkba generálja (a kimenet edition-kompatibilis), és a c_int típust használja. A generált fájl edition-függő részeit (allow attribútumok) a fogadó modul kezeli. A bindgen verziója az eszköz kimenetét befolyásolja, ezért a Cargo.lock rögzítse.

19.1.4 Stringek a határon: CStr és CString

A C string null-terminált bájtsorozat; a Rust String heap-en allokált, hossz- és kapacitásmezőkkel ellátott UTF-8 puffert. A kettő között a std::ffi modul típusai konvertálnak:

  • CStr: kölcsönzött C string, mint a &str, de bájt-alapú és null-terminált.
  • CString: birtokolt C string, mint a String, de null-terminált, és nem tartalmazhat belső null bájtot.

A CStr::from_ptr unsafe függvény, mert a mutatónak érvényes, null-terminált stringre kell mutatnia. A CString::new ellenőrzi, hogy nincs-e belső null bájt, és NulError-t ad vissza, ha van. A C++-ban a std::string::c_str() automatikusan null-terminált mutatót ad; a Rustban ezt explicit konverzióval és hibakezeléssel kell megtenni.

#include <string>
extern "C" void c_library_set(const char* key, const char* value, size_t value_len);

void set_value(const std::string& key, const std::string& value) {
    c_library_set(key.c_str(), value.data(), value.size());
}
use std::ffi::{CString, c_char};

unsafe extern "C" {
    fn c_library_set(key: *const c_char, value: *const c_char, value_len: usize);
}

fn set_value(key: &str, value: &str) -> Result<(), std::ffi::NulError> {
    let key = CString::new(key)?;
    let value = CString::new(value)?;
    // SAFETY: a CString érvényes, null-terminált puffert ad, és a hívás alatt él.
    unsafe {
        c_library_set(key.as_ptr(), value.as_ptr(), value.as_bytes().len());
    }
    Ok(())
}

A különbség: a C++ automatikusan kezeli a null-terminálást, de a Rustban a CString explicit, és a belső null bájt hibát okoz. Bináris adatoknál (mint az rkv Vec<u8> értékei) ezért nem null-terminált stringet, hanem mutató + hossz párt adunk át, és a Rust oldalon std::slice::from_raw_parts-szel rekonstruáljuk a slice-ot.

19.1.5 Ownership a határon

A C ABI-n nincs Rust tulajdonjog: a hívó és a hívott közötti megállapodás határozza meg, ki szabadít fel. A leggyakoribb minták:

Az alapszabály: minden memóriát ugyanaz az allokátor szabadít fel, amelyik lefoglalta. A Rust globális allokátora és a C malloc/free párosa nem keverhető, akkor sem, ha egy adott platformon véletlenül ugyanaz a malloc van alattuk.

  • A Rust oldal allokál, és a C hívó engedi el: Box::into_raw vagy CString::into_raw a Rust oldalon; a C hívó nem free-t hív, hanem a Rust által exportált, dedikált felszabadító függvényt (például rkv_buffer_free), amely Box::from_raw-val (illetve CString::from_raw-val) veszi vissza és dobja el a puffert.
  • A C oldal allokál (malloc, strdup), és a Rust oldal használja: a Rust CStr::from_ptr-rel kölcsönzött nézetként olvassa, szükség esetén to_owned()-dal saját másolatot készít. Ha a szerződés szerint a Rust-é a felszabadítás, azt a C free-vel (például a libc::free hívásával) kell végeznie, nem CString drop-pal.

Fontos csapda: a CString::from_raw csak olyan mutatót fogadhat, amelyet a CString::into_raw hozott létre. Ha a C kód malloc-kal allokált mutatót ad át, és a Rust CString::from_raw-t hív rá, az undefined behavior. A C-ből érkező mutatót a Rust oldalon CStr::from_ptr-ként kezeljük, és nem szabadítjuk fel, kivéve ha a szerződés szerint a Rust-é a felszabadítás.

A Box::into_raw elveszi a Rust Box-ot, és visszaadja a nyers mutatót; a memória felszabadításához Box::from_raw kell. Ez a minta biztosítja, hogy a Rust allocator párosuljon a Rust deallokátorral.

19.1.6 Panic és hibakódok

A pánik-policy a „Fogalmak” szakaszban szerepel. A gyakorlatban a státuszkódot egy int-ként adjuk vissza, és a C oldal a RKV_* állandókkal vizsgálja. A visszatérési kód egyértelműen megkülönbözteti a lehetséges kimeneteleket: siker (RKV_OK), hiányzó kulcs (RKV_NOT_FOUND, ez nem hiba), érvénytelen argumentum (RKV_INVALID_ARG: null mutató, nem UTF-8 kulcs), belső hiba (RKV_ERROR) és pánik (RKV_PANIC). A catch_unwind feltételezi, hogy a profilban a pánik nem abort; a viselkedést a kiadási profillal külön ellenőrizzük: a guarded segéd egységtesztje cargo test és cargo test --release alatt is lefut.

fn guarded(f: impl FnOnce() -> c_int) -> c_int {
    catch_unwind(AssertUnwindSafe(f)).unwrap_or(RKV_PANIC)
}

//! C ABI az rkv tárolóhoz.
//!
//! Szerződés (a generált `rkv_ffi.h`-ban is szerepel):
//! * Minden függvény `int` státuszkódot ad (`RKV_OK`, `RKV_NOT_FOUND`, `RKV_INVALID_ARG`,
//!   `RKV_ERROR`, `RKV_PANIC`).
//! * A kulcs NUL-végű, érvényes UTF-8 C string; az érték tetszőleges bájtsorozat (pointer + hossz).
//! * A `RkvStore` kezelő több szálról egyszerre is használható (belül zár védi), kivéve a
//!   `rkv_store_free`-t: az kizárólagos, egyszeri, és minden más hívás után következhet.
//! * A Rust által lefoglalt kimeneti puffert a `rkv_buffer_free(ptr, len)` szabadítja fel, pontosan egyszer.
use std::ffi::{CStr, c_char, c_int};
use std::panic::{AssertUnwindSafe, catch_unwind};
use std::ptr;

use rkv_core::{MemStore, SharedStore};

pub const RKV_OK: c_int = 0;
pub const RKV_NOT_FOUND: c_int = 1;
pub const RKV_INVALID_ARG: c_int = 2;
pub const RKV_ERROR: c_int = 3;
pub const RKV_PANIC: c_int = 4;

/// Átlátszatlan kezelő: a C oldal csak mutatót lát (`typedef struct RkvStore RkvStore;`).
pub struct RkvStore {
    inner: SharedStore,
}

/// Minden exportált függvény törzse ezen megy át: a pánikot státuszkóddá alakítja.
/// Ez csak `panic = "unwind"` profilban működik; `panic = "abort"` mellett a pánik
/// leállítja a folyamatot (ezt a könyv nem vállalja el: a csomag profilja `unwind`).
fn guarded(f: impl FnOnce() -> c_int) -> c_int {
    catch_unwind(AssertUnwindSafe(f)).unwrap_or(RKV_PANIC)
}

/// Új, memóriabeli tároló. A kezelőt a `rkv_store_free`-vel kell felszabadítani.
#[unsafe(no_mangle)]
pub extern "C" fn rkv_store_new() -> *mut RkvStore {
    let store = RkvStore { inner: SharedStore::new(MemStore::new()) };
    Box::into_raw(Box::new(store))
}

/// A kezelő felszabadítása.
///
/// # Safety
/// `store` null, vagy a `rkv_store_new` által adott, még fel nem szabadított kezelő.
/// A hívás kizárólagos: közben más szál nem használhatja a kezelőt, és utána senki sem.
#[unsafe(no_mangle)]
pub unsafe extern "C" fn rkv_store_free(store: *mut RkvStore) {
    if !store.is_null() {
        // SAFETY: a szerződés szerint a mutató a Box::into_raw eredménye, egyszer szabadítjuk.
        drop(unsafe { Box::from_raw(store) });
    }
}

/// Segéd: a kezelő megosztott referenciája (nincs `&mut`, a zár a SharedStore-ban van).
///
/// # Safety
/// `store` null vagy érvényes, élő kezelő.
unsafe fn handle<'a>(store: *const RkvStore) -> Option<&'a RkvStore> {
    // SAFETY: a hívó garantálja az érvényességet és az élettartamot.
    unsafe { store.as_ref() }
}

/// Segéd: NUL-végű UTF-8 kulcs.
///
/// # Safety
/// `key` null vagy érvényes, NUL-végű C string, amely a hívás alatt él.
unsafe fn key_str<'a>(key: *const c_char) -> Option<&'a str> {
    if key.is_null() {
        return None;
    }
    // SAFETY: a hívó szerződése szerint érvényes, NUL-végű.
    unsafe { CStr::from_ptr(key) }.to_str().ok()
}

/// Érték beállítása. Az érték tetszőleges bájtsorozat; `value` lehet null, ha `value_len == 0`.
///
/// # Safety
/// `store` érvényes kezelő; `key` NUL-végű C string; `value` legalább `value_len` olvasható bájtra mutat.
#[unsafe(no_mangle)]
pub unsafe extern "C" fn rkv_set(
    store: *const RkvStore,
    key: *const c_char,
    value: *const u8,
    value_len: usize,
) -> c_int {
    guarded(|| {
        // SAFETY: lásd a függvény # Safety szakaszát.
        let (Some(store), Some(key)) = (unsafe { handle(store) }, unsafe { key_str(key) }) else {
            return RKV_INVALID_ARG;
        };
        let bytes = if value_len == 0 {
            Vec::new()
        } else if value.is_null() {
            return RKV_INVALID_ARG;
        } else {
            // SAFETY: value_len olvasható bájt, a szerződés szerint.
            unsafe { std::slice::from_raw_parts(value, value_len) }.to_vec()
        };
        match store.inner.set(key.to_owned(), bytes) {
            Ok(()) => RKV_OK,
            Err(_) => RKV_ERROR,
        }
    })
}

/// Érték lekérdezése. Siker (`RKV_OK`) esetén `*out_value` egy Rust által lefoglalt puffer
/// (`*out_len` bájt; az üres érték hossza 0, a mutató ekkor is nem null), amelyet a
/// `rkv_buffer_free(*out_value, *out_len)` szabadít fel. Hiányzó kulcsra `RKV_NOT_FOUND`,
/// a kimenetek `NULL` és `0`.
///
/// # Safety
/// `store` érvényes kezelő; `key` NUL-végű C string; `out_value` és `out_len` írható mutatók.
#[unsafe(no_mangle)]
pub unsafe extern "C" fn rkv_get(
    store: *const RkvStore,
    key: *const c_char,
    out_value: *mut *mut u8,
    out_len: *mut usize,
) -> c_int {
    guarded(|| {
        if out_value.is_null() || out_len.is_null() {
            return RKV_INVALID_ARG;
        }
        // SAFETY: a kimeneti mutatók írhatók, a szerződés szerint.
        unsafe {
            *out_value = ptr::null_mut();
            *out_len = 0;
        }
        // SAFETY: lásd a függvény # Safety szakaszát.
        let (Some(store), Some(key)) = (unsafe { handle(store) }, unsafe { key_str(key) }) else {
            return RKV_INVALID_ARG;
        };
        match store.inner.get(key) {
            Ok(Some(value)) => {
                let boxed = value.into_boxed_slice();
                let len = boxed.len();
                // SAFETY: a kimeneti mutatók írhatók.
                unsafe {
                    *out_len = len;
                    *out_value = Box::into_raw(boxed).cast::<u8>();
                }
                RKV_OK
            }
            Ok(None) => RKV_NOT_FOUND,
            Err(_) => RKV_ERROR,
        }
    })
}

/// Törlés. `RKV_OK`, ha a kulcs létezett és törlődött; `RKV_NOT_FOUND`, ha nem létezett.
///
/// # Safety
/// `store` érvényes kezelő; `key` NUL-végű C string.
#[unsafe(no_mangle)]
pub unsafe extern "C" fn rkv_delete(store: *const RkvStore, key: *const c_char) -> c_int {
    guarded(|| {
        // SAFETY: lásd a függvény # Safety szakaszát.
        let (Some(store), Some(key)) = (unsafe { handle(store) }, unsafe { key_str(key) }) else {
            return RKV_INVALID_ARG;
        };
        match store.inner.delete(key) {
            Ok(true) => RKV_OK,
            Ok(false) => RKV_NOT_FOUND,
            Err(_) => RKV_ERROR,
        }
    })
}

/// A `rkv_get` által adott puffer felszabadítása.
///
/// # Safety
/// `ptr` és `len` pontosan a `rkv_get` által adott `*out_value` és `*out_len`, még fel nem szabadítva;
/// `ptr == NULL` esetén a hívás nem tesz semmit.
#[unsafe(no_mangle)]
pub unsafe extern "C" fn rkv_buffer_free(ptr: *mut u8, len: usize) {
    if !ptr.is_null() {
        // SAFETY: a puffert Box<[u8]>-ból adtuk ki pontosan ekkora hosszal.
        drop(unsafe { Box::from_raw(ptr::slice_from_raw_parts_mut(ptr, len)) });
    }
}

19.1.8 Tipikus hibák és átállási csapdák

  1. Rust String átadása C-nek. A String belső elrendezése nem C-kompatibilis; közvetlenül soha ne adjuk át. Szöveghez CString + as_ptr/into_raw, bináris adathoz mutató + hossz.
  2. A hívó felszabadításának elmulasztása. A rkv_get által adott puffert a C hívónak kell a rkv_buffer_free(ptr, len)-nel felszabadítania. Ha elmulasztja, memóriaszivárgás; ha kétszer hívja, double free; ha rossz hosszat ad, a Rust oldali rekonstrukció hibás.
  3. Panik átengedése a határon. catch_unwind nélkül a pánik az extern "C" határán leállítja a folyamatot (Rust 1.81 óta abort). A guarded segéd RKV_PANIC-ot ad, de csak panic = "unwind" profilban; panic = "abort" mellett a leállás a vállalt viselkedés.
  4. Rossz felszabadító. A rkv_get eredményére a C hívó nem hívhat free()-t, csak rkv_buffer_free()-t (a Rust allokátorával foglalt memóriát csak a Rust szabadíthatja). Fordítva ugyanígy: C malloc-kal foglalt mutatót nem szabad Box::from_raw/CString::from_raw útján eldobni.
  5. Nem #[repr(C)] struktúra átadása C-nek. Az rkv-ffi-ben az RkvStore átlátszatlan típus, ezért nem kell #[repr(C)], de ha a C kód hozzáfér a mezőkhöz, akkor kötelező, és a mezők típusának is C-kompatibilisnek kell lennie.
  6. Linkelési sorrend. gcc -lrkv_ffi main.c (a könyvtár a forrás előtt) feloldatlan szimbólumot adhat; a forrás/object mindig előzze meg a -l kapcsolót.
  7. A free és egy másik hívás versenye. A rkv_store_free kizárólagos: ha egy másik szál közben még használja a kezelőt, use-after-free keletkezik. A C hívónak kell biztosítania, hogy a free az összes többi hívás befejezése után fut.

19.1.9 Feladatok

  1. Fogalmi kérdés: Miért nem lehet a Rust &str-et közvetlenül C függvénynek átadni? Milyen típust használunk helyette, és miért? Mi a különbség az ABI-kompatibilitás és az értékérvényességi szerződés között?
  2. C++ kód átírása: Írjon C++ függvényt, amely std::string-et fogad, és egy C könyvtárnak adja át char*-ként, a könyvtár pedig a pufferrel a saját free()-jével szabadít. Írja meg a Rust megfelelőjét unsafe extern "C" deklarációval, és indokolja, miért nem jó itt a CString::into_raw.
  3. Implementációs feladat: Egészítse ki az rkv-ffi crate-et egy rkv_exists(store, key) függvénnyel, amely RKV_OK-t ad, ha a kulcs létezik, RKV_NOT_FOUND-ot, ha nem. Generálja újra a headert, és tesztelje a Rust egységtesztben.
  4. Tervezési döntés: Tervezze meg egy rkv_list függvény szerződését, amely sok kulcsot ad vissza. Milyen kimeneti paraméterek kellenek, ki foglal és ki szabadít, hogyan kezelendő az üres lista és a bináris/nem UTF-8 kulcs?

19.1.10 Megoldások

  1. A &str nem null-terminált, és fat pointer (adatmutató + hossz). A C egy char*-ot vár, null-terminált bájtsorozatot. A CString biztosítja a null-terminált, birtokolt puffert; a &CStr a kölcsönzött nézetet. Az ABI-kompatibilitás azt jelenti, hogy a bájtok elrendezése és a hívási konvenció egyezik (például *const c_char); az értékérvényességi szerződés azt, hogy a mutató mögötti bájtok jelentése is rögzített (NUL-végű? UTF-8? ki szabadítja? meddig él?). A mutató típusa az elsőt garantálja, a másodikat dokumentálni és ellenőrizni kell.
  2. C++ oldal: std::string s = "alma"; c_library_set_takes_ownership(strdup(s.c_str())); — itt a hívó ad át tulajdonjogot. Rust oldal:
use std::ffi::{CString, c_char};

unsafe extern "C" {
    fn c_library_set_takes_ownership(key: *mut c_char);
}

fn set_value(key: &str) -> Result<(), std::ffi::NulError> {
    let key = CString::new(key)?;
    // A C könyvtár a kapott puffert később free()-vel engedi el, ezért azt a
    // C allokátorral kell lefoglalni; a CString::into_raw puffere ide nem jó.
    let bytes = key.as_bytes_with_nul();
    // SAFETY: a malloc-ot a C allokátor szolgálja ki; null esetén nem írunk.
    let buf = unsafe { libc::malloc(bytes.len()) } as *mut c_char;
    if buf.is_null() {
        std::alloc::handle_alloc_error(std::alloc::Layout::array::<u8>(bytes.len()).unwrap());
    }
    // SAFETY: buf legalább bytes.len() bájtos, friss, a forrással nem átfedő puffer.
    unsafe { std::ptr::copy_nonoverlapping(bytes.as_ptr().cast::<c_char>(), buf, bytes.len()) };
    // SAFETY: a malloc-kal foglalt puffer tulajdonjogát átadjuk; a C könyvtár a saját free()-jével szabadítja fel, pontosan egyszer.
    unsafe { c_library_set_takes_ownership(buf) };
    Ok(())
}

A libc::malloc a libc crate-et igényli (libc = "0.2"). A CString::into_raw pointerét nem szabad a C free-nek átadni: az a Rust allokátorával készült, ezért csak a CString::from_raw veheti vissza. Ha a C API-t mi tervezzük, jobb megoldás, ha a könyvtár egy felszabadító callbacket vagy egy saját free függvényt is kap, vagy ha a hívás csak kölcsönveszi a stringet (const char*), és saját másolatot készít.

  1. A rkv_exists implementációja (az rkv-ffi/src/lib.rs-be):

Kódblokk — fájl: rkv-ffi/src/lib.rs · művelet: beillesztés a rkv_buffer_free elé · ellenőrzés: cargo test -p rkv-ffi

/// Létezik-e a kulcs? `RKV_OK`, ha igen; `RKV_NOT_FOUND`, ha nem.
///
/// # Safety
/// `store` érvényes kezelő; `key` NUL-végű C string.
#[unsafe(no_mangle)]
pub unsafe extern "C" fn rkv_exists(store: *const RkvStore, key: *const c_char) -> c_int {
    guarded(|| {
        // SAFETY: lásd a függvény # Safety szakaszát.
        let (Some(store), Some(key)) = (unsafe { handle(store) }, unsafe { key_str(key) }) else {
            return RKV_INVALID_ARG;
        };
        match store.inner.get(key) {
            Ok(Some(_)) => RKV_OK,
            Ok(None) => RKV_NOT_FOUND,
            Err(_) => RKV_ERROR,
        }
    })

  1. A rkv_list szerződése. A Rust foglalja a kimenetet, és egyetlen felszabadító függvény engedi el; a kulcsok mutató + hossz párok (nem NUL-végű), így a belső 0 és a nem UTF-8 bájt sem csonkít. Egy lehetséges alak: a rkv_list(store, prefix, &mut out_items, &mut out_count) egy RkvEntry { const uint8_t *key; size_t key_len; ... } tömböt (repr(C) struct, kizárólag C-kompatibilis mezőkkel) és annak elemszámát adja; az üres lista RKV_OK, count == 0, a mutató NULL. A hívó a rkv_list_free(items, count)-tal szabadítja fel az egészet (a tömböt és a benne lévő kulcspuffereket együtt, hogy ne kelljen mindegyiket külön követni). A szerződésnek ki kell mondania a szálbiztonságot (a lista pillanatkép, a tároló közben módosulhat) és hogy a free pontosan egyszer hívható.

19.1.11 Rövid összefoglaló

A C ABI a Rust és C/C++ együttműködés alapja. A Rust unsafe extern "C" blokkokkal hív C függvényeket (a C int megfelelője a c_int), amelyeket a bindgen generálhat C fejlécekből (az OUT_DIR-be írva, include!-dal beillesztve); a #[unsafe(no_mangle)] (2024 editionben) és a pub extern "C" fn exportálja a Rust függvényeket C számára. A határon két dolgot választunk szét: az ABI-kompatibilitást (repr(C), C-kompatibilis típusok) és az értékérvényességi/ownership szerződést (NUL-végű? ki szabadít? szálbiztos?). A pánik-policy: a pánik az extern "C" határán nem terjedhet tovább (Rust 1.81 óta abort); az rkv-ffi panic = "unwind" profillal készül, és a guarded segéd RKV_PANIC-ká alakítja. Az rkv-ffi kezelője átlátszatlan RkvStore, az érték mutató + hossz, a státusz külön kód (RKV_OK, RKV_NOT_FOUND, RKV_INVALID_ARG, RKV_ERROR, RKV_PANIC), a kimeneti puffert a rkv_buffer_free szabadítja. A cbindgen cpp_compat beállítással C és C++ számára is használható headert ad. Továbbvitt eredmény: ez a C API (rkv-ffi, rkv_ffi.h) az alapja a C++-együttműködés a cxx crate-tel és a fokozatos migráció és a Záróprojekt: az rkv teljes rendszerként alfejezeteknek.
