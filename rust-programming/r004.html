3.1 Változók, mutabilitás, skalár típusok és konverziók

3.1.1 Motiváció

Egy C++-fejlesztő számára a mutabilitás és az implicit konverzió a mindennapi rutin része: int x = 10; x++; magától értetődő, és a uint8_t b = 300; is lefordul (legfeljebb figyelmeztetéssel), csendben 44-re csonkolva, az int túlcsordulása pedig egyenesen definiálatlan viselkedés. A Rust ezeken a pontokon azonnal feszegeti a beidegződéseket: a kötés alapértelmezetten nem változtatható, a típusok között nincs néma átjárás, a túlcsordulás pedig nem „csak egy lehetséges hibafajta”, hanem szabályozott, ellenőrizhető művelet. Ez az alfejezet a nyelv legalapvetőbb építőköveit mutatja be úgy, hogy a C++-párhuzamot minden ponton explicit módon kimondja.

A cél nem a szintaxis bemagolása, hanem annak megértése, hogy a Rust miért kényszeríti ki a hosszabb kódot: mert a hosszabb kód a hibát a fordítás vagy a teszt idejére hozza előre, nem az üzembe helyezés utáni hibakeresésre.

3.1.2 Fogalmak és szabályok

3.1.2.1 let, let mut és shadowing

Definíció. A let kötés (binding) egy nevet és egy értéket kapcsol össze. Az így létrehozott kötés alapértelmezetten immutábilis, azaz a névhez rendelt érték a kötés élettartama alatt nem cserélhető. A let mut mutábilis kötést hoz létre, amelynél az = operátorral új érték rendelhető a névhez.

Szabály. A let/let mut azt dönti el, hogy a kötés által elért tulajdonolt hely közvetlenül újraírható-e. A C++ const a típus minősítője, és ott az állandóság a kivétel; Rustban az alapértelmezés a változtathatatlan kötés, és a változtatáshoz kifejezetten let mut kell. Három dolgot érdemes szétválasztani: (1) a tulajdonolt hely közvetlen újraírása (x = 20, x += 1) a mut kötést igényli; (2) a referencia típusa (&T vagy &mut T) azt mondja meg, hogy a hivatkozott értéket szabad-e módosítani; ehhez a &mut kölcsönzéshez maga az eredeti kötésnek is mut-nak kell lennie; (3) a belső mutabilitás (Cell, RefCell, Mutex, atomikus típusok; ezeket a Belső mutabilitás: Cell, RefCell és a futásidejű kölcsönzés és a Mutex, RwLock, csatornák és a megosztott rkv alfejezet tárgyalja) olyan kivétel, ahol megosztott (&T) hivatkozáson keresztül is változtatható az érték, mert a szabályt futásidőben vagy atomikus műveletekkel tartják be.

let x = 10;
// x = 20; // E0384: cannot assign twice to immutable variable

let mut y = 10;
y = 20; // rendben

A &mut hivatkozáson keresztüli módosításhoz is mut kötés kell az eredeti változón:

let mut x = 10;
let r = &mut x; // változtatható kölcsönzés: x-nek mut kötésnek kell lennie
*r += 1;
println!("{x}"); // 11
// let z = 5; let q = &mut z; // E0596: cannot borrow `z` as mutable

A shadowing nem összekeverendő a mutabilitással.

Definíció. A shadowing (leárnyékolás) ugyanazon scope-ban ugyanazzal a névvel létrehozott új let kötés. A régi kötés a shadowing után már nem elérhető, az új kötés értéke és típusa is eltérhet. A shadowing nem módosítja a régi értéket, hanem új kötést hoz létre.

let width = 100;        // i32
let width = width as u8; // u8, új kötés

let mut value = 42;
value += 1;
let value = value;      // a továbbiakban immutábilis kötés

A let mut esetén a típus rögzített marad:

let mut counter = 0u32;
counter = 10u32;
// counter = 10u64; // típushiba, a mutabilitás nem típusváltás

A const és a static a C++ globális konstansainak és globálisainak felel meg, de a Rust-szabályok mások.

Szabály. A const elem fordítási idejű konstans, amelyet a felhasználási helyen beépít a fordító; a static elemnek rögzített memóriahelye van. A const deklaráció típusannotációt igényel, a static mutábilis változatát (static mut) az unsafe szabályai miatt el kell kerülni.

const MAX_RETRIES: u32 = 3;
static APP_NAME: &str = "rkv";

A C++-ban a const int max_retries = 3; és a constexpr int max_retries = 3; közötti különbség Rustban nincs jelen ebben a formában: a const maga a fordítási idejű konstans.

3.1.2.2 Skalár típusok

A Rust skalár típusai a C++ fejlesztő számára többnyire ismerősek, de a nevek és a char jelentése pontosan tisztázandó.

Rust C++ közeli megfelelő Megjegyzés
bool bool true és false
i8, i16, i32, i64, i128, isize std::int8_t, … isize pointer méretű előjeles típus
u8, u16, u32, u64, u128, usize std::uint8_t, … usize pointer méretű előjel nélküli típus
f32, f64 float, double az alapértelmezett lebegőpontos típus f64
char nincs közvetlen megfelelő Unicode scalar value, nem char és nem wchar_t

Az egész literálok típusa alapértelmezés szerint i32, hacsak a kontextus vagy egy típusutótag mást nem diktál. A 42u8 utótaggal u8 jön létre. A usize és isize pointer méretű, Linux 64 bites platformon 64 bites, ezért a gyűjtemények indexelése usize típust igényel; a C++ size_t és ptrdiff_t párja.

A Rust char négy bájtot foglal, és egy Unicode scalar value-t tárol. Ez nem a C++ char, amely egy bájt, és nem is a wchar_t, amely platformfüggő. A char például '€', '中' és 'a' is lehet. A UTF-8 kódolás miatt ugyanazon karakter bájtokban mért hossza változó; a char::len_utf8() ezt adja meg.

3.1.2.3 Túlcsordulás: debug panic, release wrapping

A C++ előjeles egész túlcsordulása definiálatlan viselkedés, ezért a fordító optimalizálhat arra, hogy nem következik be. A Rust ezt a területet is szabályozza.

Szabály. Egész típusú túlcsordulás esetén a +, -, * és hasonló operátorok viselkedését a Cargo overflow-checks profilbeállítása dönti el. Az alapértelmezett profilokban a dev (debug) profilnál az ellenőrzés be van kapcsolva, ezért a túlcsordulás panicet okoz (attempt to add with overflow); a release profilnál ki van kapcsolva, ezért kétkomplements wrapping történik. Mindkettő definiált viselkedés (szemben a C++ előjeles túlcsordulásával), de a Cargo.toml-ban az overflow-checks átírható, tehát a szabály az alapértelmezett profilokra érvényes. Ha az érték már fordítási időben ismert, a fordító hibát ad, profiltól függetlenül (arithmetic_overflow lint). A viselkedés explicit módszerekkel buildtípustól függetlenül szabályozható.

A három eset külön jelölve (a kimenetek Rust 1.99.1-ből):

// 1. FORDÍTÁSI HIBA (debug és release is): error: this arithmetic operation will overflow
// let x = i32::MAX; let y = x + 1;
// let b: u8 = 256; // error: literal out of range for `u8`

// 2. FUTÁSI PANIC debugban, WRAPPING releaseben: a fordító nem tudja előre
fn bump(n: i32) -> i32 {
    n + 1 // n = i32::MAX esetén: debug panic, release -2147483648
}

// 3. DEFINIÁLT, build-független viselkedés explicit módszerrel
let m = i32::MAX;
let a = m.checked_add(1);    // None
let b = m.wrapping_add(1);   // -2147483648
let c = m.saturating_add(1); // 2147483647
Kifejezés Eredmény
200u8.checked_add(100) None
200u8.wrapping_add(100) 44
200u8.saturating_add(100) 255
200u8.overflowing_add(100) (44, true)

A checked_* Option<T>-t ad vissza: Some eredményt, ha nincs túlcsordulás, különben None-t. A wrapping_* mindig kétkomplements wrappinget végez. A saturating_* a típus alsó vagy felső határán telíti az eredményt. Az overflowing_* visszaadja a wrapped értéket és egy bool-t, amely jelzi a túlcsordulást. A checked_*, wrapping_*, saturating_* és overflowing_* minden egész típuson elérhetők, és a hívó dönti el, mi történjen túlcsorduláskor.

3.1.2.4 Nincs implicit konverzió

Szabály. A Rust nem végez implicit numerikus konverziót. Minden konverzió kifejezett: as, From/Into vagy TryFrom/TryInto.

Az as operátor C++-os értelemben explicit cast, és veszteséges, nem ellenőrzött szűkítésre is képes: szűkítésnél csonkol, előjelváltásnál kétkomplements átalakítást végez, lebegőpontos értéknél telít. Fontos: ez nem unsafe művelet. Az as teljesen safe Rust, használatához nincs szükség unsafe blokkra; a „nem biztonságos” itt a számérték megőrzésére vonatkozik, nem a memóriabiztonságra.

let x: i32 = 10;
let y: i64 = x as i64;        // rendben, kiterjesztés
let z: u8 = 300u16 as u8;     // 44, mert 300 - 256 = 44
let w: u32 = -1i32 as u32;    // 4294967295

A From/Into az olyan átalakításokra való, amelyek sosem hibáznak és az értéket megőrzik (értékmegőrző konverziók); a reprezentáció azért megváltozhat: az f32::from(7i16) létezik, mert minden i16 pontosan ábrázolható f32-ben, az f32::from(i32) viszont nincs, mert nem minden i32 az. A From tehát nem általános „matematikai veszteségmentesség”, hanem az adott típuspárra a standard könyvtár által vállalt, hibamentes értékmegőrzés. Fordítási időben eldől, hogy létezik-e az implementáció. A TryFrom/TryInto fallible konverziókra való, és Result-ot ad vissza. A 2021-es vagy újabb editionben a TryFrom és TryInto a prelude részét képezi, korábbi kiadásokban use std::convert::TryFrom; kell.

let big: u32 = u32::from(10u8);                 // szélesítés, mindig sikerül
let fits: Option<u16> = u16::try_from(300u32).ok(); // Some(300): belefér
let small: Option<u8> = u8::try_from(300u32).ok();  // None: u8-ba nem fér

A From/Into, valamint a TryFrom/TryInto igazi ereje a generikus határokban lesz; ezt a Trait-ek és generikusok: sablonok és concepts helyett alfejezetben fejtjük ki.

3.1.2.5 Típuskikövetkeztetés

A Rust típuskikövetkeztetése hasonlít a C++ auto mechanizmusára, de a numerikus literálok esetén van egy fontos különbség. A let x = 42; i32-t ad, a let y = 3.14; f64-et, mert ezek az alapértelmezett típusok. A literál típusát azonban a kontextus is befolyásolhatja:

let x: u8 = 10;
let y = x + 20; // y: u8, mert a kontextusból a 20 is u8-ra kényszerül

C++-ban az auto x = 42; mindig int-et ad, függetlenül a későbbi használattól. Rustban a literál típusa a kötés annotációjából, a függvényhatárokból és a műveletben részt vevő többi típusból vezethető le.

3.1.3 C++ és Rust összevetés

A kiinduló C++-kód természetesnek tűnik, de implicit konverziót, definiálatlan viselkedést és alulbecsült const használatot is tartalmaz:

#include <cstdint>
#include <iostream>
#include <limits>

int main() {
    int max = 100;
    max = max + 1;                  // ok, de a mutabilitás alapértelmezett

    const int kMaxRetries = 3;      // az állandóság a kivétel

    uint8_t byte = 300;             // implicit szűkítés: 300 mod 256 = 44,
                                    // jól definiált, de csendes adatvesztés
    int overflow = std::numeric_limits<int>::max();
    overflow += 1;                  // előjeles túlcsordulás: definiálatlan viselkedés

    std::cout << byte << "\n";      // karakterként írja ki!
}

Három különböző szabály dolgozik itt, amelyeket C++-ban is érdemes szétválasztani. (1) Konverzió előjel nélküli céltípusra: a szabvány szerint az eredmény a forrásérték modulo 2n2^n, ahol nn a céltípus bitszáma; a uint8_t byte = 300 tehát garantáltan 44, se nem UB, se nem implementációfüggő (csak a fordító figyelmeztethet a szűkítésre). (2) Előjeles aritmetikai túlcsordulás: az INT_MAX + 1 definiálatlan viselkedés. (3) Egészpromóció: a int-nél kisebb típusok (például uint8_t, uint16_t) aritmetikája előbb int-re léptetve történik, ezért két uint16_t összege maga nem csordul túl, csak a visszakonvertálás csonkol (az (1) szabály szerint). Az előjeles céltípusra végzett, nem ábrázolható konverzió C++20 óta szintén modulo-definiált; korábban implementációfüggő volt.

A Rust-megfelelő minden kockázatot fordítási vagy futási időben kezel:

fn main() {
    let max = 100;                  // i32, immutábilis kötés
    let max = max + 1;              // shadowing: új kötés, nem mutáció

    const MAX_RETRIES: i32 = 3;

    // let byte: u8 = 300;          // fordítási hiba: literal out of range
    let byte: u8 = 300u16 as u8;    // explicit csonkolás, 44
    println!("{byte}");             // 44, nem karakter

    let overflow = i32::MAX;
    // let overflow = overflow + 1; // FORDÍTÁSI HIBA: arithmetic_overflow (profiltól független)
    let overflow = overflow.saturating_add(1); // definiált: 2147483647
}

A leglényegesebb különbség három pontban fogalmazható meg: a Rustban az immutabilitás az alap, a konverzió explicit, a túlcsordulás pedig definiált viselkedés, amelyet a buildprofil és a választott metódus határoz meg.

3.1.4 Kidolgozott példa: labor a r004 munkakönyvtárban

Ez a labor önállóan futtatható, nem módosítja az rkv workspace-t. A cél a shadowing, az explicit konverziók és a túlcsordulás-kezelő metódusok kipróbálása.

Munkakönyvtár:

mkdir -p ~/rust-labor
cd ~/rust-labor
cargo new r004
cd r004

A src/main.rs tartalma:

fn main() {
    // Shadowing: típusváltás új kötéssel, nem mutáció.
    let limit = 100;                // i32
    let limit = limit as u16;       // új kötés, u16
    println!("limit = {limit}");

    // Túlcsordulás ellenőrzött, wrapping, saturating módszerekkel.
    let a: u16 = u16::MAX;
    let wrapped = a.wrapping_add(1);
    let checked = a.checked_add(1);
    let saturated = 250u8.saturating_add(20);

    println!("wrapped = {wrapped}");
    println!("checked = {checked:?}");
    println!("saturated = {saturated}");

    // Explicit konverziók: as és TryFrom.
    let narrowed: u8 = 300u16 as u8;        // 44: csonkolás
    let fits = u16::try_from(300u32);       // Ok(300): a 300 belefér az u16-ba
    let too_big = u8::try_from(300u32);     // Err: az u8 legfeljebb 255
    let at_max = u16::try_from(u32::from(u16::MAX));     // Ok(65535)
    let over_max = u16::try_from(u32::from(u16::MAX) + 1); // Err

    println!("narrowed = {narrowed}");
    println!("fits = {fits:?}");
    println!("too_big = {too_big:?}");
    println!("at_max = {at_max:?}, over_max = {over_max:?}");

    // char = Unicode scalar value, nem bájt.
    let ch = '€';
    println!("{ch} UTF-8 hossza: {}", ch.len_utf8());
}

A futtatás és a várt kimenet:

cargo run
limit = 100
wrapped = 0
checked = None
saturated = 255
narrowed = 44
fits = Ok(300)
too_big = Err(TryFromIntError(PosOverflow))
at_max = Ok(65535), over_max = Err(TryFromIntError(PosOverflow))
€ UTF-8 hossza: 3

A checked_add(1) None lesz, mert u16::MAX után nincs értelmezhető u16 eredmény. A 300u16 as u8 csonkolása 44. (A TryFromIntError Debug-kimenetének belső része, itt PosOverflow, toolchainenként eltérhet; a kimenet a Rust 1.99.1-é.) A TryFrom ugyanerre a szűkítésre (u8::try_from(300u32)) hibát ad ahelyett, hogy csonkolna, a 300 viszont belefér az u16-ba, ezért ott a konverzió sikeres. A határon az u16::MAX még átalakítható, az eggyel nagyobb érték már nem. A € karakter Unicode scalar value-ként char típusú, UTF-8 kódolásban 3 bájt, ezért a len_utf8() 3-at ad.

A debug és release közötti különbséget a következő függvénnyel lehet kitapintani:

fn overflow_demo(a: u8) -> u8 {
    a + 100
}

fn main() {
    println!("{}", overflow_demo(200));
}

Debug buildben a a + 100 kifejezés 200 + 100 esetén panicol: attempt to add with overflow. Release buildben ugyanez a hívás 44-et ad, mert a u8 túlcsordulás wrappinget végez. A C++ a uint8_t esetén hasonló csonkolást adna, de a Rust ezt a buildprofil alapján eltérően kezeli, és a két üzemmód közötti különbség szándékos.

3.1.5 Tipikus hibák és átállási csapdák

1. A const-reflex érvényesítése let mut nélkül. A C++ fejlesztő a Rustban is minden változót let mut-ként akar létrehozni, mert a C++-ban a const a kivétel. Ez a Rustban felesleges mutabilitást visz be, és elrejti a szándékot. A helyes gyakorlat: először let, és csak akkor mut, ha a kód ténylegesen írja a kötést.

2. Shadowing használata mutáció helyett. A let x = 5; let x = x + 1; nem ugyanaz, mint a x += 1. Az előbbi új kötést hoz létre, az utóbbi a meglévőt módosítja. Ha a szándék a „változó” fogalom, akkor let mut kell; ha a szándék a „új érték, új típus”, akkor shadowing.

3. Az as mint „biztonságos” implicit konverzió. A as nem biztonságos, mert csonkol és előjelváltásnál nem őrzi az előjelet. Például -1i32 as u32 4294967295 lesz, nem hiba. Ha a konverzió lehetetlen kimenetele is elfogadhatatlan, TryFrom-ot kell használni.

4. A release wrapping elfelejtése. Debug buildben a túlcsordulás panicet okoz, ezért a fejlesztő azt hiheti, hogy a kód soha nem csordul túl. Release buildben ugyanez a kód wrappinget ad, és csendes adatsérülést okozhat. A domain-invariánsokat checked_* vagy saturating_* hívásokkal kell kifejezni, nem a buildprofilra hagyatkozni.

5. A char bájtként kezelése. A char nem bájt, hanem Unicode scalar value. A char és a u8 között nincs implicit konverzió; ha bájtokkal kell dolgozni, u8 vagy &str / String kell, nem char.

3.1.6 Feladatok

1. Feladat (lefordul-e és miért?). Döntse el mindkét kódrészletről, hogy lefordul-e, és ha nem, miért:

let x = 10;
x = 20;
let x = 10;
let x = x + 1.5;

2. Feladat (C++-kód átírása idiomatikus Rustra). A következő C++ függvény implicit konverziót és hallgatólagos túlcsordulást rejt:

#include <cstdint>

uint16_t add_pair(uint16_t a, uint16_t b) {
    return a + b; // implicit int promóció, majd narrowing
}

Írjon Rust függvényt, amely Option<u16> visszatérési értékkel jelzi a túlcsordulást, és indokolja, miért jobb ez a C++ csendes csonkolásánál.

3. Feladat (implementációs feladat: hosszmezős keret). Az rkv szöveges, soralapú protokollt használ (lásd Az rkv hálózati szerver: TCP, protokoll, kecses leállás), de sok bináris protokoll hosszmezővel keretez: a keret első bájtja a payload hossza, utána pontosan ennyi bájt következik. Készítsen fn frame(payload: &[u8]) -> Option<Vec<u8>> függvényt, amely u8 hosszmezős keretet épít, és None-t ad, ha a payload nem fér bele. Miért hibás itt a hossz telítése (255-re vágása)? Írjon unit tesztet 255 és 256 bájtos payloadra.

4. Feladat (hibajavítás és tervezési döntés). Az alábbi Rust-kód nem fordul le:

let length: u32 = 1024;
let small: u16 = length; // típushiba

Javítsa a kódot kétféleképpen: as operátorral és TryFrom-mal. Melyik megoldást választaná biztonsági szempontból nem megbízható bemenet esetén, és miért?

3.1.7 Megoldások

1. Megoldás. Az első kódrészlet nem fordul le: x immutábilis kötés, ezért x = 20; E0384 hibát ad. A második kódrészlet szintén nem fordul le: x i32 típusú, a 1.5 f64 típusú, és a + operátor nem konvertálja implicit módon a típusokat; mismatched types hibát ad.

2. Megoldás.

fn add_pair(a: u16, b: u16) -> Option<u16> {
    a.checked_add(b)
}

A checked_add a Rust szintjén ad vissza None-t túlcsorduláskor, ahelyett, hogy a hívó hallgatólagosan megkapná a csonkolt eredményt. A C++-ban az a + b előbb int-re lépteti mindkét operandust (egészpromóció), az összeg ott nem csordul túl; a visszatéréskor végzett uint16_t-re konverzió viszont modulo 2162^{16} csonkol. Ez jól definiált, nem UB és nem implementációfüggő, de csendes adatvesztés: add_pair(65535, 1) eredménye 0. A Rustban a típus kényszeríti ki, hogy a hívó foglalkozzon a hibával.

3. Megoldás.

fn frame(payload: &[u8]) -> Option<Vec<u8>> {
    // Hibát jelző konverzió: 255 bájt fölött nincs keret.
    let len = u8::try_from(payload.len()).ok()?;
    let mut out = Vec::with_capacity(1 + payload.len());
    out.push(len);
    out.extend_from_slice(payload);
    Some(out)
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn length_field_matches_payload() {
        let max = vec![7u8; 255];
        let f = frame(&max).unwrap();
        assert_eq!(f[0], 255);
        assert_eq!(f.len() - 1, 255); // a deklarált hossz = az elküldött bájtok
        assert_eq!(frame(&[7u8; 256]), None); // nincs csendes levágás
        assert_eq!(frame(&[]), Some(vec![0]));
    }
}

A telítés (u8::try_from(len).unwrap_or(u8::MAX)) itt hibás terv: egy 256 bájtos payloadnál a hosszmező 255-öt mondana, a keretben mégis 256 bájt következne, így a fogadó egy bájttal később kezdené a következő keretet, és a keretezés szétcsúszna. Hosszmezőnél a túl nagy üzenetet el kell utasítani (vagy nagyobb hosszmezőt, például u32-t kell választani). A telítés ott helyes, ahol a határérték maga is értelmes eredmény, például egy hangerő- vagy progresszjelzőnél. A ? operátor az Option-on itt csak annyit tesz, hogy None esetén azonnal visszatér; részletesen a Result, a ? operátor és a panic helye alfejezet tárgyalja.

Továbbvitt eredmény. Az itt bemutatott explicit konverziós és túlcsordulás-kezelési minták alapozzák meg a Saját hibatípusok: enum-hibák, thiserror, anyhow alfejezetben az Error típusra épülő konverziókat, valamint a Trait-ek és generikusok: sablonok és concepts helyett alfejezetben a From/Into és TryFrom/TryInto implementációit. Az elv: ahol a csonkolás vagy a telítés adatot hamisítana, ott hibát jelző TryFrom kell.

4. Megoldás.

let length: u32 = 1024;

let small_as: u16 = length as u16;
let small_try: u16 = u16::try_from(length).unwrap_or(u16::MAX);

Az as verzió egyszerű, de csonkol; a TryFrom verzió explicit módon kezeli a hibát. Nem megbízható bemenet esetén a TryFrom a jobb választás, mert a hívó kénytelen dönteni a hiba lekezeléséről, ahelyett, hogy a csonkolt érték csendben tovább szivárogna. A TryFrom Err ága később a ? operátorral a teljes hibatípusba is átfordítható.

3.1.8 Rövid összefoglaló

Az r004 alfejezetben a Rust kötései, skalár típusai, túlcsordulási szabályai és konverziói kerültek terítékre. A let alapértelmezetten immutábilis, a let mut kivétel; a shadowing új kötést hoz létre, és típusváltozást is lehetővé tesz. Az egész típusok a debug buildben panicelnek túlcsorduláskor, release buildben kétkomplements wrappinget végeznek; a checked_*, wrapping_*, saturating_* és overflowing_* metódusok buildtípustól függetlenül vezérlik ezt a viselkedést. A Rust nem végez implicit numerikus konverziót: az as explicit, de nem biztonságos, a From/Into veszteségmentes, a TryFrom/TryInto fallible konverziót ad. A char Unicode scalar value, nem bájt. A laborban a r004 crate mutatta be a műveleteket; a frame feladat azt mutatta meg, hogy hosszmezős keretezésnél a túl nagy értéket hibával kell elutasítani, nem telíteni. Ez előkészíti az Error és a generikus From/TryFrom implementációkat a későbbi fejezetekben.

3.1.9 Források és ellenőrzési hiányok

A fejezet a Rust Reference (https://doc.rust-lang.org/reference/) és a Rust Book (https://doc.rust-lang.org/book/) megfelelő fejezeteire támaszkodik. A túlcsordulás, a let/let mut és a konverziós szabályok stabil nyelvi viselkedések; a fordítói hibakódok stabilak, a hibaüzenetek szövege a könyv rögzített toolchainjére (Rust 1.99.1) vonatkozik, más verzióban eltérhet. A TryFrom és a TryInto a 2021-es és újabb editionök preludejában van, régebbi editionben importálni kell. A debug/release túlcsordulási viselkedés a Cargo alapértelmezett profiljaiban érvényes, az overflow-checks beállítással felülírható.
