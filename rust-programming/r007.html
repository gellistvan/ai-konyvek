4.1 Structok és metódusok: impl blokkok, asszociált függvények

4.1.1 Motiváció

C++-ban egy osztály (class) egyszerre csomagolja az adattagokat és a rajtuk dolgozó tagfüggvényeket, és ezt gyakran rejtett, implicit this mutatóval teszi: a tagfüggvényen belül x irányulhat a this->x mezőre, a const tagfüggvény pedig megígéri, hogy nem módosítja az objektumot. A konstruktorok, a túlterhelés és az öröklés mind része ennek a modellnek. A Rust radikálisan szétválasztja az adatot és a viselkedést, és nincs sem implicit this, sem konstruktor-szintaxis, sem implementációs öröklés. Ez a fejezet megmutatja, hogyan kell C++-os fejjel jól strukturálni Rust-struktúrákat és metódusaikat.

4.1.2 Fogalmak és szabályok

Definíció. A Rust struct olyan típus, amely heterogén, névvel ellátott (vagy pozícióalapú, vagy üres) mezőket foglal magába. A Rust a struct három alakját különbözteti meg:

  • Named-field struct: a mezőknek nevük van, és a struct Point { x: f64, y: f64 } szintaxissal definiáljuk.
  • Tuple struct: a mezőknek nincs nevük, csak pozíciójuk: struct Rgb(u8, u8, u8);.
  • Unit struct: egyáltalán nincs mező, csak típusnév: struct Marker;.

Definíció. Az impl blokk egy típushoz tartozó asszociált elemeket definiál. Két dolgot tehetünk bele: asszociált függvényeket (amelyek nem vesznek fel self-et) és metódusokat (amelyek első paramétere self, &self vagy &mut self). Az adatot a struct (és az enum) írja le, a viselkedést az impl blokk; class kulcsszó nincs.

Szabály. A metódusok első paramétere (a receiver) leggyakrabban az alábbi három alak valamelyike; ez bevezető felsorolás, nem teljes lista:

  • self: a hívó értéket átveszi: nem Copy típusnál mozgatás történik, és utána az eredeti változó nem használható; Copy típusnál másolat kerül a hívásba, ezért az eredeti tovább használható.
  • &self: a hívó értéket kölcsönzi (shared borrow); ez a C++ const tagfüggvény Rust-megfelelője, de nem csak const szempontú, hanem aliasing-korlátozott is. A „nem módosítható” a megosztott referencián keresztül a mezők típusától függ: Cell, RefCell, Mutex és atomikus mezők megosztott (&) hivatkozáson át is módosíthatók (belső mutabilitás, lásd Belső mutabilitás: Cell, RefCell és a futásidejű kölcsönzés, Mutex, RwLock, csatornák és a megosztott rkv); a &self tehát nem általános „senki sem módosíthatja” garancia.
  • &mut self: kizárólagos, módosító kölcsönzés (mutable borrow); ez a C++ nem-const tagfüggvény megfelelője.

Vannak további receiver-alakok is, amelyeket később, a megfelelő témánál tárgyalunk: a mut self (átvett, de módosítható érték), a self: Box<Self>, a self: Rc<Self> és a self: Pin<&mut Self> (Box, Rc, Arc és Weak, Pin, Unpin, async trait-ek).

Szabály. Ha egy függvény egy impl blokkban nem vesz fel self-et, akkor asszociált függvény; ilyen a new konvenció. A Rustban nincs nyelvi szintű konstruktor: a new csak egy megegyezés, és a típushoz kapcsolt asszociált függvény. Bármennyi ilyen függvényt írhatunk, de túlterhelés nincs — különböző nevek kellenek, vagy a Default trait és a builder minta használható.

Szabály. Nincs implementációs öröklés Rustban. Egy struct nem örökölhet más struct-ból. A viselkedés újrafelhasználása trait-ekkel, kompozícióval és generikusokkal történik, amelyeket a későbbi fejezetek tárgyalnak (lásd Trait-ek és generikusok).

Szabály. A . operátor automatikusan referenciát illeszt be a hívás helyén: ha a metódus &self-et vagy &mut self-et vár, és a hívó oldalon érték van, akkor a fordító automatikusan & vagy &mut kölcsönzést hoz létre. Ezért írhatunk point.norm()-ot annak ellenére, hogy norm &self-et kér.

A mezők inicializálásakor van egy hasznos rövid alak: ha a változó neve megegyezik a mező nevével, akkor a x: x helyett elegendő a x írása.

4.1.3 C++ és Rust összevetés

Tekintsünk egy egyszerű geometriai típust C++-ban és Rustban.

// C++: osztály, konstruktor, const/non-const tagfüggvények
#include <cmath>

class Point {
    double x_, y_;
public:
    Point(double x, double y) : x_(x), y_(y) {}

    double norm() const {
        return std::sqrt(x_ * x_ + y_ * y_);
    }

    void scale(double factor) {
        x_ *= factor;
        y_ *= factor;
    }

    double x() const { return x_; }
    double y() const { return y_; }
};

A Rust megfelelő:

struct Point {
    x: f64,
    y: f64,
}

impl Point {
    // asszociált függvény; a `Self` a jelenlegi típus aliasa
    fn new(x: f64, y: f64) -> Self {
        Self { x, y }
    }

    // metódus, &self kölcsönöz, nem veszi át a tulajdont
    fn norm(&self) -> f64 {
        (self.x * self.x + self.y * self.y).sqrt()
    }

    // metódus, &mut self módosít
    fn scale(&mut self, factor: f64) {
        self.x *= factor;
        self.y *= factor;
    }

    // getterek: &self; a kisméretű `Copy` mezőt (itt f64) érték szerint adjuk vissza,
    // nagyobb vagy nem `Copy` mezőnél (például String) &T-t adnánk
    fn x(&self) -> f64 {
        self.x
    }

    fn y(&self) -> f64 {
        self.y
    }
}

A lényeges különbség: a Rustban nincs implicit this; a metódus paraméterlistája nyíltan kimondja, hogyan fér hozzá az objektumhoz. A C++ const tagfüggvény nem tudja módosítani az objektumot, de ez nem garantálja, hogy más szál nem módosítja eközben. A Rust &self ezen felül kizárja az egyidejű módosítást is a kölcsönzési szabályok által. A scale C++-ban hallgatólagosan módosít a this-en, míg Rustban a &mut self explicit.

4.1.4 Kidolgozott labor: az rkv Store struktúrája

Munkakönyvtár: ~/rust-labor/rkv/

Az rkv mintaprojektben a Store a központi adatszerkezet, amely a kulcs–érték tárolást valósítja meg. Ebben a laborban a korábban (Az rkv mintaprojekt indítása: Cargo-workspace és első CLI) felvázolt Store struktúrát elemezzük, és rögzítjük a típusválasztás indoklását.

1. lépés: Nyissuk meg a rkv-core/src/lib.rs fájlt. A kiinduló állapot az Az rkv mintaprojekt indítása: Cargo-workspace és első CLI alfejezet végén elkészült Store. Az egyetlen API-változás az új clear metódus; a többi metódus szignatúrája változatlan, csak a dokumentációs kommentek bővülnek a típusválasztás indoklásával.

Kódblokk — fájl: rkv-core/src/lib.rs · művelet: teljes csere (az rkv mintaprojekt indítása: Cargo-workspace és első CLI alfejezetbeli Store + clear) · ellenőrzés: cargo build --workspace → az rkv-cli változatlanul fordul

use std::collections::HashMap;

/// A kulcs–érték tároló.
///
/// A kulcsok mindig `String` típusúak, mert a szöveges protokoll
/// (`GET`, `SET`, `DEL`, `LIST`) sorokkal dolgozik. Az értékek
/// `Vec<u8>` típusúak: a tároló (és a későbbi JSON-perzisztencia) tetszőleges
/// bájtsort veszteség nélkül tárol, nem korlátozzuk érvényes UTF-8-ra. A
/// hálózati protokoll szöveges rétege csak szöveg-biztos értékeket visz át;
/// tetszőleges bájtokhoz a későbbi `SETX`/`GETX` hexa réteg szolgál (r040).
#[derive(Debug, Default)]
pub struct Store {
    data: HashMap<String, Vec<u8>>,
}

impl Store {
    /// Üres tároló létrehozása.
    pub fn new() -> Self {
        Self {
            data: HashMap::new(),
        }
    }

    /// Kulcs–érték pár beillesztése. Felülírja a korábbi értéket.
    pub fn set(&mut self, key: String, value: Vec<u8>) {
        self.data.insert(key, value);
    }

    /// Egy kulcs értékének lekérdezése. `None`, ha nincs ilyen kulcs.
    /// A `get` `&str`-et fogad, mert így a hívó nem kényszerül fölösleges
    /// `String`-t létrehozni; a `HashMap` `String` kulcsa esetén
    /// `&str`-rel is lehet keresni.
    pub fn get(&self, key: &str) -> Option<&Vec<u8>> {
        self.data.get(key)
    }

    /// Kulcs törlése. Visszaadja a törölt értéket, ha létezett.
    pub fn delete(&mut self, key: &str) -> Option<Vec<u8>> {
        self.data.remove(key)
    }

    /// Az összes kulcs rendezetlen listája.
    pub fn keys(&self) -> Vec<String> {
        self.data.keys().cloned().collect()
    }

    /// Az összes kulcs törlése.
    pub fn clear(&mut self) {
        self.data.clear();
    }
}

2. lépés: Ellenőrizzük a típusválasztást. A get metódus &str-et fogad, holott a HashMap kulcsa String. Ez működik, mert a HashMap::get általános kulcsmintát vár, és a String kulcs esetén a &str is érvényes keresőkulcs. Ez hasonló a C++20 heterogén lookupjához, amely például std::unordered_map<std::string, V> find tagját std::string_view-val is meghívja. A C++ hagyományos std::unordered_map viszont csak const std::string&-et fogad, ami fölösleges másolást okozhat.

3. lépés: Futtassunk unit teszteket. A laborban a cargo test -p rkv-core paranccsal ellenőrizzük, hogy a Store a várt módon viselkedik. Ehhez adjunk a lib.rs végéhez egy tesztmodult.

Kódblokk — fájl: rkv-core/src/lib.rs · művelet: beillesztés a fájl végére · ellenőrzés: cargo test -p rkv-core → 2 sikeres teszt

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn set_and_get() {
        let mut store = Store::new();
        store.set("kulcs".to_string(), b"ertek".to_vec());
        assert_eq!(store.get("kulcs"), Some(&b"ertek".to_vec()));
    }

    #[test]
    fn delete_returns_old_value() {
        let mut store = Store::new();
        store.set("a".to_string(), vec![1, 2, 3]);
        let old = store.delete("a");
        assert_eq!(old, Some(vec![1, 2, 3]));
        assert!(store.get("a").is_none());
    }
}

Egy ezt követő cargo run -p rkv-cli -- get hello viszont NOTFOUND-ot ad, mert minden folyamat új, üres Store-ral indul (lásd az rkv mintaprojekt indítása: Cargo-workspace és első CLI 4. lépését); a tároló helyes működését egy folyamaton belül a fenti unit tesztek igazolják. A set a kulcs utáni első argumentumot veszi értéknek; a szóközt tartalmazó érték idézőjelek közt adható meg (set hello "szép világ"), mert a shell ezt egyetlen argumentumként adja át.

Ellenőrzési pont. A cargo build --workspace hibátlan, a cargo test -p rkv-core 2 sikeres tesztet futtat. Az rkv-core API-ja: Store::new, set(String, Vec<u8>), get(&str) -> Option<&Vec<u8>>, delete(&str) -> Option<Vec<u8>>, keys() -> Vec<String>, clear(); a Store Debug és Default.

Továbbvitt eredmény. Ebben a laborban rögzítettük a Store struktúrát (rkv-core/src/lib.rs): privát data: HashMap<String, Vec<u8>> mezővel, new asszociált függvénnyel, valamint set, get, delete, keys és clear metódusokkal. A get Option<&Vec<u8>>-t ad vissza, amit a Az enum mint összeg-típus és az Option a null helyett alfejezet tanít. A set &mut self-et kér, ami az Ownership: minden értéknek egy tulajdonosa van alfejezetben lesz a középpontban. A jelenlegi set és delete nem ad hibát, ezt a Result, a ? operátor és a panic helye alfejezet pontosítja.

4.1.5 Tipikus hibák és átállási csapdák

  1. self használata &self helyett. C++-ban a tagfüggvény általában this-en dolgozik, de az objektumot a hívó nem „veszíti el”. Rustban a self átveszi a tulajdont, és a metódus hívása után az eredeti változó érvénytelen. Ha egy metódus csak olvassa az adatot, akkor &self-et kell használni.
// Ez a változat szándékosan nem fordul le:
struct S { x: i32 }
impl S {
    fn get_x(self) -> i32 { self.x }
}
fn main() {
    let s = S { x: 5 };
    println!("{}", s.get_x());
    println!("{}", s.x); // hiba: s mozgatva lett
}

A fordító hibakódja E0382 (use of moved value). A javítás: fn get_x(&self) -> i32 { self.x }.

  1. Gettermásolás. C++-ban a getter gyakran értéket ad vissza, mert a const std::string& visszaadása élettartam-problémákat okozhat. Rustban a &str vagy &T visszaadása biztonságos, mert a kölcsönzés szabályai garantálják, hogy a referenciák érvényesek maradnak. Ne klónozzunk minden getterben.

  2. Konstruktor-túlterhelés hiánya. C++-ban természetes, hogy egy osztálynak több konstruktora van. Rustban nincs túlterhelés; a new konvenció egyetlen függvény, de írhatunk több, nevükben különböző asszociált függvényt: from_config, with_capacity, vagy a Default trait-et és a builder mintát használhatjuk.

  3. A this hiánya. C++-ban a mezők elérése a tagfüggvényben automatikus. Rustban mindig self.mező_neve formát kell írni; a mező_neve önmagában a metódusban nem hivatkozik a struktúra mezőjére.

4.1.6.1 (a) Fordul-e, és miért?

impl Buffer {

4.1.6.2 (b) Írd át C++-ból Rustra

Az alábbi C++ osztállyal modellezz egy hőmérséklet-érzékelő mintát. Készítsd el a Rust megfelelőt strukturával, impl blokkal, asszociált new függvénnyel és a megfelelő self-fajtákkal.

class TemperatureReading {
    double celsius_;
public:
    TemperatureReading(double celsius) : celsius_(celsius) {}

    double celsius() const { return celsius_; }
    double fahrenheit() const { return celsius_ * 9.0 / 5.0 + 32.0; }

    void adjust(double delta) { celsius_ += delta; }
};

4.1.6.3 (c) Bővítsd az rkv Store-t

Adj az rkv-core/src/lib.rs Store impl blokkjához egy contains metódust (&self, &str paraméter, bool visszatérés), valamint egy replace metódust, amely &mut self-et, String kulcsot és Vec<u8> értéket vár, és visszaadja a korábbi értéket Option<Vec<u8>>-ként. Futtass hozzá unit tesztet.

4.1.7 Megoldások

4.1.7.1 (a)

Nem fordul le. A clear metódus self-et vár, ami átveszi a buf tulajdont. A hívás után buf mozgatott, érvénytelen, ezért a buf.data.len() hozzáférése E0382 hibát okoz. Javítás: a metódus &mut self-et használjon, ha nem akarja megsemmisíteni a puffert:

struct Buffer {
    data: Vec<u8>,
}

impl Buffer {
    fn clear(&mut self) {
        self.data.clear();
    }
}

4.1.7.2 (b)

struct TemperatureReading {
    celsius: f64,
}

impl TemperatureReading {
    fn new(celsius: f64) -> Self {
        Self { celsius }
    }

    fn celsius(&self) -> f64 {
        self.celsius
    }

    fn fahrenheit(&self) -> f64 {
        self.celsius * 9.0 / 5.0 + 32.0
    }

    fn adjust(&mut self, delta: f64) {
        self.celsius += delta;
    }
}

A celsius és fahrenheit metódus csak olvas, ezért &self; az adjust módosít, ezért &mut self. A new asszociált függvény nem vesz fel self-et.

4.1.7.3 (c)

Az rkv-core/src/lib.rs bővítése:

impl Store {
    // ... korábbi metódusok ...

    pub fn contains(&self, key: &str) -> bool {
        self.data.contains_key(key)
    }

    pub fn replace(&mut self, key: String, value: Vec<u8>) -> Option<Vec<u8>> {
        self.data.insert(key, value)
    }
}

Unit teszt a tests modulban:

#[test]
fn contains_and_replace() {
    let mut store = Store::new();
    store.set("a".to_string(), vec![1]);
    assert!(store.contains("a"));
    assert!(!store.contains("b"));

    let old = store.replace("a".to_string(), vec![2, 3]);
    assert_eq!(old, Some(vec![1]));
    assert_eq!(store.get("a"), Some(&vec![2, 3]));
}

A HashMap::insert már eleve visszaadja a korábbi értéket, így a replace egyszerű továbbítás.

4.1.7.4 (d)

A hiba a fn increment(self) szignatúrában van. A self átveszi a Counter tulajdont, ezért az első counter.increment() hívás után a counter érvénytelen, és a második hívás E0382 hibát okoz. Javítás: a metódus &mut self-et kapjon, és a hívónál a counter legyen mut – ez már így is megvan.

struct Counter {
    count: u32,
}

impl Counter {
    fn new() -> Self {
        Self { count: 0 }
    }

    fn increment(&mut self) {
        self.count += 1;
    }

    fn value(&self) -> u32 {
        self.count
    }
}

4.1.8 Rövid összefoglaló

A Rust struct három alakban létezik: named-field, tuple és unit struct. A viselkedés nem a struktúra része, hanem külön impl blokkban definiáljuk. A metódusok első paramétere explicit self, &self vagy &mut self, ami pontosan meghatározza, hogyan fér hozzá a hívó objektumhoz. Nincs konstruktor, nincs túlterhelés, nincs implementációs öröklés; a new asszociált függvény konvenció, a Default trait és a builder minta pedig helyettesíti a konstruktor-túlterhelést. A laborban rögzítettük az rkv Store típusát (rkv-core/src/lib.rs): privát data: HashMap<String, Vec<u8>> mezővel, new asszociált függvénnyel, és set, get, delete, keys, clear metódusokkal. Az értékek Vec<u8> típusúak, a kulcsok String típusúak. Továbbvitt eredmény: a Store a Az enum mint összeg-típus és az Option a null helyett alfejezetben az Option használata, a Ownership, borrowing, lifetime: a Rust szíve rész fejezeteiben a kölcsönzési szabályok, a Result, a ? operátor és a panic helye alfejezetben pedig a hibakezelés szempontjából kerül továbbfejlesztésre.
