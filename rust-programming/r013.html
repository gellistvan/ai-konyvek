6.2 Copy, Clone és Drop: másolás és RAII Rustban

6.2.1 Motiváció

A C++-ban a másolás és a mozgatás vezérlése a programozó kezében van: másolási konstruktort, mozgatási konstruktort és értékadó operátorokat írhatunk, ezek döntik el, hogy egy értékből kettő vagy egy marad-e. A Rust ezt megfordítja: a mozgatás az alapértelmezett, és csak azok a típusok másolhatók implicit módon, amelyek ezt kifejezetten vállalják a Copy trait segítségével. A mély másolás sosem történik meg automatikusan; azt a Clone trait explicit hívása végzi. A RAII mindkét nyelv központi eleme, de Rustban a destruktor a Drop trait, amelynek szabályai és korlátai vannak – például hibát nem tud visszaadni, ez pedig alapvetően befolyásolja, hová tehetjük a perzisztenciát.

6.2.2 Fogalmak és szabályok

Definíció (Copy). A Copy trait egy olyan jelölő (marker) trait, amely azt mondja ki: a típus értéke bitenkénti másolással biztonságosan duplikálható úgy, hogy az eredeti érték érvényes marad. Ha egy típus implementálja a Copy-t, akkor a hozzárendelés és a függvényargumentum-átadás másolást végez, nem mozgatást.

Szabály. Egy típus akkor és csak akkor lehet Copy, ha minden mezője Copy, és a típus nem implementálja a Drop traitet. A Drop és a Copy kölcsönösen kizárják egymást, mert a bitenkénti másolás megkerülné a destruktor logikáját.

Definíció (Clone). A Clone trait explicit, felhasználó által hívott másolást valósít meg. A clone() metódus tetszőlegesen összetett lehet: végezhet mély másolást, foglalhat új memóriát, vagy akár olcsó is lehet. A Rust nem hívja automatikusan a clone()-t, ezért a drága művelet mindig látható a hívás helyén.

Definíció (Drop). A Drop trait a Rust destruktora. Aláírása fn drop(&mut self): az egyetlen paramétere a &mut self, más argumentumot nem kap, és nem ad vissza értéket, így hibát sem tud jelezni. A drop metódus akkor fut le, amikor az érték kimegy a hatókörből, és a mezők automatikus eldobása előtt lehetőséget ad erőforrások lezárására. A drop-ot közvetlenül nem lehet hívni; korai eldobáshoz a std::mem::drop szolgál.

Szabály (drop-sorrend). Két külön szabály van, és a kettő ellentétes irányú:

  1. A lokális változók a hatókör végén a deklaráció fordított sorrendjében dobódnak el: először az utoljára deklarált. Ez megegyezik a C++ automatikus változóinak destruktor-sorrendjével.
  2. Egy struktúra mezői a deklaráció sorrendjében dobódnak el: először az első mező. Ez eltér a C++-tól, ahol a tagok fordított sorrendben semmisülnek meg. Ha a struktúrának saját Drop implementációja van, először a Drop::drop fut le (a mezők ekkor még érvényesek), és csak utána dobódnak el automatikusan a mezők.
struct Noisy(&'static str);

impl Drop for Noisy {
    fn drop(&mut self) {
        println!("drop {}", self.0);
    }
}

struct Pair {
    a: Noisy,
    b: Noisy,
}

impl Drop for Pair {
    fn drop(&mut self) {
        // A mezők itt még érvényesek.
        println!("drop Pair ({}, {})", self.a.0, self.b.0);
    }
}

fn main() {
    {
        let _a = Noisy("lokális a");
        let _b = Noisy("lokális b");
    }
    let _p = Pair { a: Noisy("mező a"), b: Noisy("mező b") };
}

A kimenet (Rust 1.99.1):

drop lokális b
drop lokális a
drop Pair (mező a, mező b)
drop mező a
drop mező b

Szabály (std::mem segédfüggvények). A std::mem::drop egy üres függvény, amely azonnal eldobja az argumentumát; a std::mem::take egy &mut T-ből kicseréli az értéket a Default-jára és visszaadja a régit; a std::mem::replace egy megadott értékre cseréli a régit; a std::mem::swap két &mut T értéket cserél meg.

6.2.3 C++ és Rust összevetés

C++-ban a másolás és mozgatás szabályait az osztály konstruktorai és értékadó operátorai határozzák meg:

struct Buffer {
    char* data;
    size_t len;

    // Másolási konstruktor: mély másolás
    Buffer(const Buffer& other)
        : data(new char[other.len]), len(other.len) {
        std::copy(other.data, other.data + len, data);
    }

    // Mozgatási konstruktor: erőforrás átvétele
    Buffer(Buffer&& other) noexcept
        : data(other.data), len(other.len) {
        other.data = nullptr;
        other.len = 0;
    }

    ~Buffer() { delete[] data; }
};

A Rust-ban ugyanezt a Clone (explicit mély másolás) és a Drop (erőforrás-felszabadítás) fejezi ki, míg a mozgatás automatikus, bitenkénti:

struct Buffer {
    data: Vec<u8>,
}

impl Clone for Buffer {
    fn clone(&self) -> Self {
        Self { data: self.data.clone() }
    }
}

impl Drop for Buffer {
    fn drop(&mut self) {
        // A Vec automatikusan felszabadítja a kupacot,
        // itt csak akkor kell Drop, ha más erőforrást is kezelünk.
        println!("Buffer dropped");
    }
}

A kulcskülönbség: C++-ban a mozgatási konstruktort explicit módon kell megírni, és a mozgatás után az eredeti objektum „kiürült” állapotban marad. Rustban a mozgatás bitenkénti másolás, de a mozgatott érték statikusan érvénytelenné válik, és nem férhetünk hozzá többé. A másolás viszont csak akkor történik, ha a típus Copy, vagy ha explicit clone()-t hívunk.

6.2.4 Labor: rkv Store mentése Drop-ban – és miért nem jó ötlet

Munkakönyvtár: ~/rust-labor/rkv/

A labor célja, hogy a rkv-core crate Store típusához perzisztenciát adjunk, és megvizsgáljuk, miért nem a Drop a megfelelő hely a mentésre. A Store jelenleg csak memóriában tárol, de hamarosan fájlba is írni fog. A perzisztencia hibát okozhat (I/O hiba), a Drop viszont nem tud hibát visszaadni.

A kiinduló állapot a Függőségek, feature-ök, verziózás és workspace-ek ellenőrzési pontja: a Store a rkv-core/src/store.rs-ben, a hibatípus a rkv-core/src/error.rs-ben él (Modulok és láthatóság: header nélküli világ).

1. lépés: nyissuk meg a rkv-core/src/store.rs fájlt, és adjunk egy dirty mezőt a Store-hoz. A módosító metódusok (set, delete, clear) ezt igazra állítják; a get és a keys változatlan.

Kódblokk — fájl: rkv-core/src/store.rs · művelet: módosításrészlet: a Store definíciója, a new, set, delete és clear cseréje; a többi metódus és a tesztek változatlanok · ellenőrzés: cargo test -p rkv-core → 4 sikeres teszt

#[derive(Debug, Default)]
pub struct Store {
    data: HashMap<String, Vec<u8>>,
    /// Igaz, ha az utolsó mentés óta módosult a tároló.
    dirty: bool,
}

impl Store {
    pub fn new() -> Self {
        Self {
            data: HashMap::new(),
            dirty: false,
        }
    }

    pub fn set(&mut self, key: String, value: Vec<u8>) {
        self.data.insert(key, value);
        self.dirty = true;
    }

    pub fn delete(&mut self, key: &str) -> Option<Vec<u8>> {
        let old = self.data.remove(key);
        if old.is_some() {
            self.dirty = true;
        }
        old
    }

    pub fn clear(&mut self) {
        if !self.data.is_empty() {
            self.dirty = true;
        }
        self.data.clear();
    }

    // get és keys: változatlan
}

A dirty mező jelzi, hogy történt-e mentetlen módosítás.

2. lépés: kísérlet a Drop implementálására.

Egy naiv megoldás, hogy a Drop-ban megpróbáljuk menteni, ha dirty igaz:

impl Drop for Store {
    fn drop(&mut self) {
        if self.dirty {
            // Itt kellene kiírni a fájlt, de a hibát nem tudjuk kezelni!
            // eprintln!("Warning: unsaved changes in Store");
            // A flush() Result-ot adna, amit itt nem tudunk továbbadni.
        }
    }
}

Probléma: a Drop::drop nem adhat vissza Result-ot, így az esetleges I/O hibát nem tudjuk a hívónak jelenteni. Ha a mentés itt történne, a hiba elveszne, vagy a programnak panikálnia kellene, ami nem elfogadható könyvtári kódban. Ráadásul a Drop futásakor a program esetleg már nem is tud helyesen reagálni a hibára.

3. lépés: a helyes megoldás: explicit flush metódus.

A perzisztenciát a Store felhasználójának kell kezdeményeznie egy flush metódussal, amely Result-ot ad vissza. A hibatípus a Modulok és láthatóság: header nélküli világ alfejezetben létrehozott crate::error::Error, amelynek Io variánsa épp az I/O-hibák továbbadására való:

Kódblokk — fájl: rkv-core/src/store.rs · művelet: beillesztés: a fájl elejére a use crate::error::Error; sor, az impl Store blokkba a flush metódus · ellenőrzés: cargo build -p rkv-core

use crate::error::Error;

impl Store {
    pub fn flush(&mut self) -> Result<(), Error> {
        if self.dirty {
            // Itt jön majd a tényleges fájlírás (későbbi alfejezetekben).
            // Most csak szimuláljuk a mentést.
            // Például: std::fs::write("store.dat", serialize(&self.data))?;
            self.dirty = false;
        }
        Ok(())
    }
}

A Drop implementációt teljesen elhagyjuk, mert a Store nem birtokol olyan erőforrást, amelyet a memória felszabadításán túl kezelnie kellene. A HashMap maga felszabadítja a kupacot, így nincs szükség Drop-ra.

4. lépés: a labor kiegészítése mem::take-kel.

Ha a Drop-ban mégis szeretnénk valamit tenni, akkor a std::mem::take segítségével kiüresíthetjük a data-t, hogy a memória felszabadulása biztos legyen, de ez itt felesleges, mert a HashMap alapértelmezetten is felszabadul. A mem::take inkább akkor hasznos, ha egy &mut T-ből akarunk értéket kivenni anélkül, hogy a típust Default nélkül kellene hagyni. A flush implementációban viszont használhatjuk a mem::take-et, ha a data-t ki akarjuk cserélni egy üres mapre:

pub fn flush(&mut self) -> Result<(), Error> {
    if self.dirty {
        let data = std::mem::take(&mut self.data);
        // data-val dolgozunk, majd betesszük vissza vagy mentjük
        self.data = data;
        self.dirty = false;
    }
    Ok(())
}

Ez a minta később, a hibakezelés és a párhuzamosság témakörében visszatér majd.

Továbbvitt eredmény. A Store típus a dirty mezővel és az explicit flush metódussal a Borrowing: referenciák és a kölcsönzési szabály alfejezetben kap kölcsönzési mintákat; a Result-alapú hibakezelést a Result, a ? operátor és a panic helye alfejezet mélyíti el, a mem::take mintát pedig a Box, Rc, Arc és Weak alfejezet is használja.

6.2.5 Tipikus hibák és átállási csapdák

  1. A clone() használata a borrow checker „legyőzésére”. Amikor a kölcsönzési hiba miatt a kód nem fordul, a kezdő Rust-fejlesztő gyakran clone()-t hív, hogy a fordítót kielégítse. Ez működhet, de felesleges allokációt és teljesítményromlást okoz. A helyes megoldás a kölcsönzési és lifetime-szabályok megértése, nem a másolás.

  2. A Copy és Clone összekeverése. Sok fejlesztő azt várja, hogy a derive(Clone, Copy) minden típust automatikusan másolhatóvá tesz. A Copy csak bitenkénti másolásra alkalmas típusoknál működik, és csak akkor deriválható, ha a típus minden mezője Copy. A String, Vec, HashMap nem Copy, így az ilyen típusokat tartalmazó struktúra sem lehet az.

  3. A Drop implementálása hibakezelést igénylő műveletre. Mivel a Drop nem adhat vissza Result-ot, a benne végzett I/O vagy hálózati művelet hibája elveszik. Ilyen műveleteket explicit metódusokba kell tenni, a Drop pedig csak csendes takarításra való.

6.2.6 Feladatok

  1. Fogalmi kérdés: Miért nem lehet egyszerre egy típus Copy és Drop? Mondjon egy konkrét példát arra, mi történne, ha mégis megengedné a nyelv.

  2. C++ kód átírása: Adott a következő C++ osztály, amely fájlmutatót birtokol, és másoláskor duplikálja a fájlleírót (a példa kedvéért dup-pal), destruktorkor pedig bezárja. Írja át Rustra a megfelelő idiomatikus kóddal, Clone és Drop használatával.

    struct File {
    int fd;
    File(int fd) : fd(fd) {}
    File(const File& other) : fd(dup(other.fd)) {}
    ~File() { close(fd); }
};

    A Rust verzióban használjon File típust a std::fs-ből, és magyarázza el, hogyan valósul meg a duplikálás és a lezárás.

  3. Implementációs feladat: Készítsen egy CleaningBuffer típust, amely egy Vec<u8>-ot tárol, és Drop implementációjában kiírja a puffer hosszát a standard hibára, majd üríti a puffert a std::mem::take segítségével. Tesztelje, hogy a Drop akkor is lefut, ha a változót std::mem::drop-pal korán eldobjuk.

  4. Refaktorálás: A laborban szereplő Store flush metódusa jelenleg szimulálja a fájlba írást. Egészítse ki úgy, hogy a data mapet JSON formátumba szerializálja (például serde_json használatával), és írja ki egy fájlba. A flush hibát adjon vissza, ha a szerializálás vagy a fájlírás sikertelen. A Drop-ot ne módosítsa.

6.2.7 Megoldások

  1. A Copy bitenkénti másolást jelent, ami megkerülné a Drop::drop logikáját. Ha egy típus Copy és Drop is lenne, akkor a másoláskor az erőforrás-birtoklás duplikálódna anélkül, hogy a destruktor tudomást szerezne róla, így a erőforrás kétszer szabadulna fel vagy sérülne. Például egy File típus, amely lezárja a fájlt a Drop-ban, nem lehet Copy, mert a bitmásolás után mindkét példány ugyanazt a fájlleírót birtokolná, és mindkettő lezárná.

  2. A Rust megfelelő:

    use std::fs::File;
use std::io;

struct MyFile {
    file: File,
}

impl MyFile {
    /// Hibázható duplikálás: a `dup` (itt `File::try_clone`) elbukhat
    /// (például elfogyott a fájlleíró), ezért `io::Result`-ot adunk vissza.
    fn try_clone(&self) -> io::Result<Self> {
        Ok(Self { file: self.file.try_clone()? })
    }
}

// A Drop nem szükséges, mert a File maga lezárja a fájlt a hatókör végén.

    A File típus a std::fs-ben már implementálja a RAII-t: a hatókör végén automatikusan bezárja a fájlt. A MyFile szándékosan nem implementálja a Clone traitet, mert a Clone::clone aláírása nem hibázhat (fn clone(&self) -> Self), a fájlleíró duplikálása viszont igen; egy panikoló unwrap mögé rejtett hiba megtévesztő volna. Ezért a duplikálás try_clone() -> io::Result<Self>. Fontos következmény: a duplikált leíró ugyanarra a megnyitott fájlleírásra mutat, ezért a fájlpozíció közös. Ellenőrzött viselkedés: ha az eredeti fájlból 3 bájtot olvasunk az abcdef tartalomból (abc), a másolatból a következő olvasás def-et ad.

  3. Példa implementáció:

    struct CleaningBuffer {
    data: Vec<u8>,
}

impl CleaningBuffer {
    fn new(data: Vec<u8>) -> Self {
        Self { data }
    }
}

impl Drop for CleaningBuffer {
    fn drop(&mut self) {
        eprintln!("Dropping buffer of length {}", self.data.len());
        // Demonstráció: a mem::take kicseréli a mezőt egy üres Vec-re (Default),
        // és az eredeti tartalmat adja vissza. Manuális ürítésre a memória
        // felszabadításához nincs szükség: a Vec automatikus dropja elegendő.
        let old_data = std::mem::take(&mut self.data);
        eprintln!("old_data.len() = {}, self.data.len() = {}", old_data.len(), self.data.len());
        // old_data.len() == 4, self.data.len() == 0; az old_data itt dobódik el.
    }
}

fn main() {
    let buf = CleaningBuffer::new(vec![1, 2, 3, 4]);
    std::mem::drop(buf); // korai eldobás
    println!("End of main");
}

    A std::mem::drop hatására a drop metódus azonnal lefut: a standard hibára old_data.len() = 4, self.data.len() = 0 kerül (a take után az eredeti négy elem az old_data-ban van, a mezőben üres Vec marad), és csak ezután jelenik meg a “End of main”. A mem::take itt szemléltetés: a Vec automatikus dropja a memóriát manuális ürítés nélkül is felszabadítaná.

  4. A flush kibővítése:

    use serde_json::json;

pub fn flush(&mut self) -> Result<(), Error> {
    if self.dirty {
        let json = json!(&self.data);
        let serialized = serde_json::to_string(&json)
            .map_err(|e| Error::Io(std::io::Error::new(std::io::ErrorKind::InvalidData, e)))?;
        std::fs::write("store.json", serialized)
            .map_err(Error::Io)?;
        self.dirty = false;
    }
    Ok(())
}

    A serde_json a Cargo.toml-ben serde_json = "1" függőségként szerepel. A hibát Error::Io-ba csomagoljuk.

6.2.8 Rövid összefoglaló

A Copy trait bitenkénti másolást jelöl, és csak olyan típusoknál alkalmazható, amelyek minden mezője Copy és nincs Drop implementációjuk. Az implicit másolás sosem történik meg a Clone nélkül, így a drága mély másolás mindig látható. A Drop a RAII destruktora, amely nem adhat vissza hibát, ezért csak csendes takarításra való; a perzisztencia és más hibalehetőséget rejtő műveletek explicit metódusokba tartoznak. A laborban a rkv-core::Store típushoz dirty mezőt és flush metódust adtunk, amely Result<(), Error>-t ad vissza; a Drop implementációt elvetettük, mert a mentési hibát nem tudná továbbítani. A std::mem::take, replace, swap és drop segédfüggvények az erőforrás-kezelés fontos eszközei. A Store és a flush a további alfejezetekben (Referenciák és a kölcsönzési szabály: sok olvasó XOR egy író, Box, Rc, Arc és Weak, Result, a ? operátor és a panic helye) alapul szolgál.
