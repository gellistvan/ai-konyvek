11.2 Saját hibatípusok: enum-hibák, thiserror, anyhow

11.2.1 Motiváció

C++-ban a hibakezelés gyakran kivételhierarchiákon alapul: std::runtime_error, std::ios_base::failure, saját store_error osztályok. A hívó fél számára azonban nem mindig világos, hogy egy függvény pontosan milyen kivételeket dobhat, és a catch blokkok sorrendje, illetve a catch (...) gyakran elfedi a hibák valódi típusát. Ha egy Store::load függvény fájlművelet közben std::ios_base::failure-t, rossz adatformátum esetén std::runtime_error-t dob, a hívó kód csak a what() szövegére hagyatkozhat, vagy bonyolult dynamic_cast vizsgálatokat írhat.

A Rust ezt a problémát a hibák típusként való modellezésével oldja meg: egy függvény Result<T, E>-t ad vissza, ahol E általában egy saját enum. A hívó match segítségével pontosan meg tudja különböztetni az egyes hibaeseteket, a fordító pedig ellenőrzi, hogy minden lehetséges variánst kezelünk-e. A ? operátorral a hibák automatikusan konvertálhatók a saját típusunkra, ha biztosítjuk a megfelelő From implementációkat. Ebben az alfejezetben megtervezzük az rkv könyvtár saját Error típusát, és bevezetjük az alkalmazásoldali anyhow-t a kontextusgazdag hibakezeléshez.

11.2.2 Fogalmak és szabályok

Definíció (hiba trait). A Rust standard könyvtárában a std::error::Error trait jelöli azokat a típusokat, amelyek hibaként használhatók: pub trait Error: Debug + Display. A Debug és a Display tehát szupertrait-korlátok, nem az Error metódusai: egy típus csak akkor lehet Error, ha a Debug traitet (diagnosztikai kiírás, általában #[derive(Debug)]) és a Display traitet (az ember által olvasható leírás) is implementálja. Magának az Error traitnek a fontos, felülírható metódusa a source(), amely a hibát kiváltó alacsonyabb szintű hibát adja vissza, ha van ilyen; alapértelmezett implementációja None.

Definíció (hibalánc, source-lánc). Ha egy magasabb szintű hiba egy alacsonyabb szintű hibát burkol be – például egy fájlműveleti hiba egy io::Error-t –, akkor a két hibát láncba fűzhetjük. A Rust Error trait source() metódusa ezt a láncot teszi bejárhatóvá: minden hiba visszaadhatja az őt kiváltó okot. A Display implementáció általában a közvetlen hibát írja le, a lánc további elemeit a leképező eszközök (pl. anyhow {:#} formázása) jelenítik meg.

Szabály (könyvtár vs. alkalmazás hibastratégiája). Könyvtári kódban saját, strukturált hibatípust (enum) használjunk, amely pontosan felsorolja a lehetséges hibaeseteket, és From implementációkkal támogatja a ? operátort. Alkalmazásban (CLI, szerver) gyakran elegendő az anyhow::Result<T> (vagy anyhow::Error), amely típuserázott hibákat kezel, és kontextust adhatunk hozzájuk. A kettő közötti határ a hívó fél szerződése: ha a hívónak programozottan kell döntenie a hibáról, használjunk enumot; ha csak emberi olvasásra és naplózásra kell, az anyhow praktikusabb.

Szabály (a ? operátor From-konverziója). A ? operátor egy Result<T, E> értéken meghívva a hiba esetén megkísérli a hibát From<E> for F segítségével konvertálni a környező függvény F hibatípusára. Ezért ha a hibatípusunkra implementáljuk a From<io::Error>-t, akkor a File::open(...)? kifejezés automatikusan a mi hibánkká alakítja az I/O hibát.

11.2.3 C++ és Rust összevetés

Tekintsünk egy C++ függvényt, amely egy fájlból olvas be egy egész számot, és különböző hibákat dob:

#include <fstream>
#include <stdexcept>
#include <string>

class parse_error : public std::runtime_error {
public:
    explicit parse_error(const std::string& msg) : std::runtime_error(msg) {}
};

int load_count(const std::string& path) {
    std::ifstream file(path);
    if (!file.is_open()) {
        throw std::ios_base::failure("cannot open file");
    }
    int value = 0;
    file >> value;
    if (file.fail()) {
        throw parse_error("invalid integer");
    }
    return value;
}

A hívónak két különböző kivételt kell elkapnia, ráadásul ezek típusa nem derül ki a függvény szignatúrájából. (Figyelem, a két változat nem azonos szerződésű: a C++ file >> value az első szóközzel elválasztott szót olvassa, a maradékot figyelmen kívül hagyja, tehát a "42abc" és a "42 7" tartalmú fájl is 42-t ad; a lenti Rust változat a teljes, trim-melt tartalmat értelmezi, ezért ugyanazokat ParseIntError-ral utasítja el. Ez szándékos szigorítás; az első szó olvasásához content.split_whitespace().next() kell — de a parse a "42abc"-t ezután is elutasítja; a C++ prefix-olvasás Rust-megfelelője a számjegyek előzetes kiválasztása (take_while(char::is_ascii_digit)), majd parse.) A Rust megfelelője saját hibát enummal írja le:

use std::{fmt, fs, io, num::ParseIntError};

#[derive(Debug)]
enum LoadError {
    Io(io::Error),
    Parse(ParseIntError),
}

impl fmt::Display for LoadError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            LoadError::Io(e) => write!(f, "I/O hiba: {e}"),
            LoadError::Parse(e) => write!(f, "számformátum hiba: {e}"),
        }
    }
}

impl std::error::Error for LoadError {
    fn source(&self) -> Option<&(dyn std::error::Error + 'static)> {
        match self {
            LoadError::Io(e) => Some(e),
            LoadError::Parse(e) => Some(e),
        }
    }
}

// A ? operátor ezeken keresztül alakítja át a két alacsonyabb szintű hibát.
impl From<io::Error> for LoadError {
    fn from(e: io::Error) -> Self {
        LoadError::Io(e)
    }
}

impl From<ParseIntError> for LoadError {
    fn from(e: ParseIntError) -> Self {
        LoadError::Parse(e)
    }
}

fn load_count(path: &str) -> Result<i32, LoadError> {
    let content = fs::read_to_string(path)?;   // io::Error -> LoadError
    let value = content.trim().parse::<i32>()?; // ParseIntError -> LoadError
    Ok(value)
}

A ? operátor automatikusan konvertálja a hibákat, mert a LoadError implementálja a két From-ot; ha bármelyiket elhagynánk, a megfelelő ? sor E0277-tel (the trait `From<io::Error>` is not implemented for `LoadError`) nem fordulna le. A hívó match-csel pontosan kezelheti a két hibautat:

fn main() {
    match load_count("count.txt") {
        Ok(n) => println!("érték: {n}"),
        Err(LoadError::Io(e)) => eprintln!("nem olvasható: {e}"),
        Err(LoadError::Parse(e)) => eprintln!("rossz formátum: {e}"),
    }
}

A fenti kézzel írt Display, Error és From implementáció azonban sok boilerplate; a thiserror derive ezt jelentősen lerövidíti, amint a laborban látni fogjuk.

11.2.4 Labor: az rkv Error típusa és anyhow a CLI-ben

Ebben a laborban az rkv-core könyvtár hibatípusát (rkv-core/src/error.rs, Modulok és láthatóság: header nélküli világ) a thiserror crate-tel a végleges, kanonikus alakjára hozzuk, és bevezetjük az anyhow-t a rkv-cli binárisban. A kiinduló állapot a Result, a ? operátor és a panic helye ellenőrzési pontja.

Munkakönyvtár: ~/rust-labor/rkv

Migráció. A Modulok és láthatóság: header nélküli világ alfejezetbeli Error két variánsa (KeyNotFound, Io) helyett a kanonikus Error a következő: Io(io::Error), KeyNotFound(String) (most már hordozza a hiányzó kulcsot), InvalidCommand(String) (a Modulok és láthatóság: header nélküli világ 3. feladatának Parse variánsa ezen a néven él tovább). Az I/O és szerializáció: fájlok, pufferelés, serde alfejezet egyetlen variánst ad hozzá (Serialization); ettől kezdve az Error nem változik, és minden crate ezt használja. A meglévő kódban az Error-t egyedül a Store::flush említi, és csak a típusnevén, ezért a csere más fájlt nem érint. (Aki megoldotta a Modulok és láthatóság: header nélküli világ 3. feladatát, a command.rs-ben az Error::Parse(...) hívásokat Error::InvalidCommand(...)-ra cseréli.)

11.2.4.2 2. lépés: Az rkv-core hibatípusa

Kódblokk — fájl: rkv-core/src/error.rs · művelet: teljes csere · ellenőrzés: cargo build -p rkv-core

// rkv-core/src/error.rs
use std::io;
use thiserror::Error;

/// Az rkv tároló hibáinak típusa.
#[derive(Debug, Error)]
pub enum Error {
    /// Fájl- vagy egyéb I/O művelet hibája.
    #[error("I/O hiba: {0}")]
    Io(#[from] io::Error),

    /// A kért kulcs nem található a tárolóban.
    #[error("kulcs nem található: {0}")]
    KeyNotFound(String),

    /// Érvénytelen parancs vagy protokollüzenet.
    #[error("érvénytelen parancs: {0}")]
    InvalidCommand(String),
}

/// Az rkv-core műveleteinek eredménytípusa.
pub type Result<T> = std::result::Result<T, Error>;

A #[derive(Error)] implementálja a std::error::Error traitet, a #[error("...")] attribútumok a Display-et. A #[from] az Io variánson generálja a From<io::Error> for Error implementációt, így a ? operátor közvetlenül használható minden io::Result<T>-t visszaadó hívásnál, és a source() is az eredeti io::Error-t adja vissza, tehát a hibalánc megmarad. A Result<T> alias a gyakori Result<T, Error> rövidítése; a crate gyökerében is exportáljuk:

Kódblokk — fájl: rkv-core/src/lib.rs · művelet: a pub use error::Error; sor cseréje · ellenőrzés: cargo build --workspace

pub use error::{Error, Result};

Így a crate-en belül crate::Result<T>, kívülről rkv_core::Result<T> használható.

11.2.4.3 3. lépés: Kontextus az anyhow-val a CLI-ben

A CLI eddig minden futtatásnál egyetlen parancsot hajtott végre egy üres tárolón. Most egy --script <fájl> kapcsolót adunk hozzá: a fájl minden sora egy protokollparancs, amelyet a CLI a parancssori parancs előtt, ugyanazon a tárolón hajt végre. Így egy folyamaton belül több parancs is futhat, és két valódi hibaút is keletkezik: a fájl olvasása (io::Error) és egy hibás sor (Error::InvalidCommand). Mindkettőhöz az anyhow ad kontextust.

Kódblokk — fájl: rkv-cli/src/main.rs · művelet: a use sorok, a Cli struktúra és a main cseréje, új run_script függvény; a CliCommand, parse_key, parse_command, execute és a tesztek változatlanok · ellenőrzés: cargo test -p rkv-cli

use std::path::{Path, PathBuf};

use anyhow::{Context, Result};
use clap::{Parser, Subcommand};
use rkv_core::{Command, Error, Store};

/// rkv parancssori kliens
#[derive(Parser)]
#[command(name = "rkv-cli", version, about)]
struct Cli {
    /// Parancsfájl: soronként egy protokollparancs, a megadott parancs előtt fut le
    #[arg(long)]
    script: Option<PathBuf>,
    #[command(subcommand)]
    command: CliCommand,
}

// ... CliCommand, parse_key, parse_command és execute változatlanul ...

/// Végrehajtja a parancsfájl sorait; az üres sorokat átugorja.
fn run_script(store: &mut Store, path: &Path) -> Result<()> {
    let text = std::fs::read_to_string(path)
        .with_context(|| format!("a(z) {} parancsfájl olvasása", path.display()))?;
    for (index, line) in text.lines().enumerate() {
        if line.is_empty() {
            continue;
        }
        let command = parse_command(line)
            .map_err(Error::InvalidCommand)
            .with_context(|| format!("{}:{}", path.display(), index + 1))?;
        println!("{}", execute(store, command));
    }
    Ok(())
}

fn main() -> Result<()> {
    let cli = Cli::parse();
    let mut store = Store::new();
    if let Some(path) = &cli.script {
        run_script(&mut store, path)?;
    }
    let command = match cli.command {
        CliCommand::Get { key } => Command::Get(key),
        CliCommand::Set { key, value } => Command::Set(key, value),
        CliCommand::Del { key } => Command::Delete(key),
        CliCommand::List { prefix } => Command::List(prefix),
    };
    let command = parse_command(&command.to_line())
        .map_err(Error::InvalidCommand)
        .context("érvénytelen parancssori argumentum")?;
    println!("{}", execute(&mut store, command));
    Ok(())
}

A with_context (és a context) az anyhow::Context traitből származik: ha a Result Err, a hibát anyhow::Error-rá alakítja, és elé fűzi a megadott szöveges kontextust; az eredeti hiba a lánc következő eleme (source) marad. A with_context lusta: a formázott üzenet csak hiba esetén készül el. A main anyhow::Result<()>-t ad vissza; ha Err-rel tér vissza, a program a hibát és a teljes láncát Error: ... Caused by: ... formában a standard hibakimenetre írja, és 1-es kilépési kóddal áll le.

Próbáljuk ki egy működő és két hibás úttal:

printf 'SET name Alice\nSET city Szeged\n' > init.txt
cargo run -q -p rkv-cli -- --script init.txt get name
cargo run -q -p rkv-cli -- --script nincs.txt get name
printf 'SET name Alice\nGET name extra\n' > rossz.txt
cargo run -q -p rkv-cli -- --script rossz.txt get name

Várt kimenet (a cargo saját sorai nélkül; az Error: kezdetű blokkok a standard hibakimenetre kerülnek, a kilépési kód 1; az os error 2 szövege rendszerfüggő):

OK
OK
VALUE name Alice
Error: a(z) nincs.txt parancsfájl olvasása

Caused by:
    No such file or directory (os error 2)
OK
Error: rossz.txt:2

Caused by:
    érvénytelen parancs: invalid key: "name extra"

Az első futtatás mutatja, hogy egy folyamaton belül a SET után a GET már látja az értéket. A második és a harmadik futtatás a két hibautat: a kontextus megmondja, mit csináltunk (melyik fájlt olvastuk, melyik sorban jártunk), a lánc következő eleme pedig, hogy mi romlott el.

#[cfg(test)]
mod tests {
    use super::*;
    use std::error::Error as _;

    #[test]
    fn io_error_converted_to_error() {
        let io_err = io::Error::new(io::ErrorKind::NotFound, "file not found");

11.2.5 Tipikus hibák és átállási csapdák

  1. unwrap/expect a könyvtárban. C++-ban megszokott, hogy hibás fájlműveletnél kivételt dobunk; Rustban a File::open(path).expect("nem nyitható") pánikot okoz a könyvtári kódban, ami a hívó alkalmazás összeomlásához vezet. Ehelyett minden felhasználói bemenettől függő műveletnek Result-ot kell visszaadnia, és a ? operátort kell használni. A pánik csak ténylegesen helyrehozhatatlan programozói hibánál elfogadható (pl. belső invariáns megsértése).

  2. anyhow használata könyvtári API-ban. Az anyhow::Error típuserázott: a hívó nem tud enumvariánsokra statikusan, kimerítően match-elni. Programozottan dönteni mégis lehet downcast_ref-fel és a hibalánc bejárásával (chain()), de ez futásidejű, nem ellenőrzi a fordító. Ezért könyvtári API-ban a saját enum a megfelelő alapértelmezés (nem kivétel nélküli szabály); az alkalmazásban az anyhow már elfogadható, mert ott a hibák emberi fogyasztásra és naplózásra valók.

  3. Box<dyn Error> örökölt reflexe. C++-ban a std::exception polimorfikus hivatkozás a természetes; Rustban a Box<dyn Error> hasonló, de típuserázott: a match nem tud variánsokra illeszkedni. A konkrét típus a downcast_ref::<T>()-tel utólag kideríthető: e.downcast_ref::<io::Error>() egy Option<&io::Error>-t ad, amelyből a map(io::Error::kind) a hibakategóriát (Some(ErrorKind::NotFound)) nyeri; a downcast_ref::<MyErr>() None-t ad, ha a hiba nem ilyen típusú. Ez futásidejű típusvizsgálat: csak a feltételezett típusokat lehet végigpróbálni, és a fordító nem ellenőrzi a teljességet. Ezért a könyvtár a strukturált enumot részesíti előnyben: az enum pontos szerződés (a fordító jelzi, ha egy variánst nem kezelünk), a Box<dyn Error> és az anyhow pedig az alkalmazás szintjére való.

  4. A map_err és a source() láncának félreértése. A source() lánc nem a map_err-től vagy a From-tól függ, hanem attól, hogy a hibatípus Error::source metódusa visszaadja-e a burkolt hibát. Ugyanarra az Error::Io variánsra map_err(Error::Io) és From + ? használatával azonos source() lánc adódik (ellenőrzött kimenet mindkettőre: source = nincs fájl). A thiserror #[from] attribútuma a From implementációt generálja, a #[source] (és a #[from] implicit módon) pedig a source() metódust.

11.2.6 Feladatok

11.2.6.1 a) Fogalmi kérdés

Egy könyvtár fejlesztője a következő függvényt írja:

fn load_config(path: &str) -> Result<String, Box<dyn std::error::Error>> {
    let content = std::fs::read_to_string(path)?;
    Ok(content)
}

Miért nem ideális ez a hibatípus egy olyan könyvtárban, ahol a hívónak meg kell különböztetnie a „fájl nem található” és a „JSON formátum hiba” eseteket? Hogyan lehetne jobbá tenni? Fogalmazd meg a választ a könyvtár vs. alkalmazás stratégia alapján.

11.2.6.2 b) C++-kód átírása idiomatikus Rustra

Adott a C++ függvény:

#include <stdexcept>
#include <fstream>

int read_seed(const std::string& path) {
    std::ifstream file(path);
    if (!file) throw std::runtime_error{"cannot open seed file"};
    int seed;
    file >> seed;
    if (file.fail()) throw std::runtime_error{"invalid seed format"};
    return seed;
}

Írd át Rustra a laborban bemutatott Error enum mintájára: hozz létre egy SeedError enumot a thiserror használatával, amely io::Error-t és ParseIntError-t tud burkolni, majd írd meg a read_seed függvényt Result<i32, SeedError> visszatéréssel. Használd a ? operátort.

11.2.6.3 c) Implementációs feladat az rkv-ban

Bővítsd az rkv-core Error enumját egy Serialization variánssal, amely serde_json::Error-t fogad be #[from]-mal. Ehhez vedd fel a serde_json = "1" függőséget az rkv-core/Cargo.toml-be. Írj egy függvényt parse_record(data: &str) -> Result<(), Error> néven, amely a serde_json::from_str::<serde_json::Value>(data)? kifejezést használja, és sikeres parse esetén Ok(())-t ad. Futtasd a teszteket.

11.2.6.4 d) Hibajavítás és refaktorálás

Tekintsd a következő Rust kódot:

fn process_file(path: &str) -> Result<(), Box<dyn std::error::Error>> {
    let data = std::fs::read_to_string(path)?;
    let value: i32 = data.trim().parse()?;
    println!("{value}");
    Ok(())
}

Refaktoráld a process_file függvényt úgy, hogy a laborban definiált rkv_core::Error-t használja, és adj hozzá kontextust az anyhow segítségével egy CLI-hívásban: ha a fájl nem nyitható, a hibaüzenet tartalmazza a fájl elérési útját. (Tipp: a process_file-t hívó kód anyhow::Result<()>-t adjon vissza, és használja a with_context metódust.)

11.2.7 Megoldások

11.2.7.1 a) Megoldás

A Box<dyn Error> típuserázott: a hívó a fordítási időben nem tudja, hogy a hibát io::Error vagy serde_json::Error okozta-e. A match nem tud különbséget tenni; a konkrét típus csak a downcast_ref::<T>() futásidejű próbálgatásával, illetve a source() lánc bejárásával derül ki, ami körülményes és nem teljességellenőrzött. Könyvtárban saját enumot kell használni, például:

#[derive(Debug, thiserror::Error)]
pub enum ConfigError {
    #[error("I/O hiba: {0}")]
    Io(#[from] std::io::Error),
    #[error("JSON hiba: {0}")]
    Json(#[from] serde_json::Error),
}

A hívó így match-csel pontosan kezelheti a variánsokat. Az anyhow::Error csak alkalmazásban ajánlott, ahol nincs szükség programozott döntésre.

11.2.7.2 b) Megoldás

use std::{fs, io, num::ParseIntError};
use thiserror::Error;

#[derive(Debug, Error)]
enum SeedError {
    #[error("I/O hiba a seed fájlnál: {0}")]
    Io(#[from] io::Error),

    #[error("érvénytelen seed formátum: {0}")]
    Parse(#[from] ParseIntError),
}

fn read_seed(path: &str) -> Result<i32, SeedError> {
    let content = fs::read_to_string(path)?;
    let seed = content.trim().parse::<i32>()?;
    Ok(seed)
}

A ? operátor automatikusan konvertálja az io::Error-t és a ParseIntError-t a SeedError megfelelő variánsaira a generált From-ok révén.

11.2.7.3 c) Megoldás

Az rkv-core/Cargo.toml:

[dependencies]
thiserror = "2"
serde_json = "1"

Az rkv-core/src/error.rs frissített változata:

use std::io;
use thiserror::Error;

#[derive(Debug, Error)]
pub enum Error {
    #[error("I/O hiba: {0}")]
    Io(#[from] io::Error),

    #[error("kulcs nem található: {0}")]
    KeyNotFound(String),

    #[error("érvénytelen parancs: {0}")]
    InvalidCommand(String),

    #[error("szerializációs hiba: {0}")]
    Serialization(#[from] serde_json::Error),
}

A parse_record függvény az rkv-core/src/lib.rs-ben vagy egy új modulban:

pub fn parse_record(data: &str) -> Result<(), Error> {
    // A `?` automatikusan Error::Serialization-vá alakítja a serde_json hibát.
    let _: serde_json::Value = serde_json::from_str(data)?;
    Ok(())
}

A cargo test -p rkv-core lefuttatása után minden tesztnek sikeresnek kell lennie.

11.2.7.4 d) Megoldás

A könyvtári függvény saját hibával:

// rkv-core/src/lib.rs (vagy egy megfelelő modulban)
pub fn process_file(path: &str) -> Result<(), Error> {
    let data = std::fs::read_to_string(path)?;
    let value: i32 = data.trim().parse().map_err(|_| Error::InvalidCommand("nem szám".into()))?;
    println!("{value}");
    Ok(())
}

A parse hiba ParseIntError, amit egyelőre InvalidCommand-ra képezünk le, mert az Error-ban nincs parse variáns. (A későbbi fejezetekben ezt finomíthatjuk.)

A CLI-ben:

use anyhow::Context;
use rkv_core::process_file;

fn main() -> anyhow::Result<()> {
    let path = "/tmp/rkv-seed.txt";
    process_file(path).with_context(|| format!("fájl feldolgozása: {path}"))?;
    Ok(())
}

Ha a fájl nem nyitható, az anyhow a láncban megőrzi az eredeti rkv_core::Error-t, és a kiíráskor a kontextus is megjelenik.

11.2.8 Rövid összefoglaló

Az rkv könyvtár saját hibatípusa az rkv_core::Error enum, amelyet a thiserror derive-tal definiáltunk az rkv-core/src/error.rs fájlban. A variánsok: Io(#[from] io::Error), KeyNotFound(String), InvalidCommand(String), és a feladatban hozzáadott Serialization(#[from] serde_json::Error). A #[from] attribútumok generálják a From implementációkat, így a ? operátor automatikusan konvertálja az alacsonyabb szintű hibákat, és a source() lánc is megmarad. A rkv-cli binárisban bevezettük az anyhow::Result-et és a with_context metódust, és a --script kapcsolóval két valódi hibautat (fájlolvasás, hibás sor) kontextussal mutattunk be; a CLI minden parancsa működik, todo!() nélkül. A könyvtár és az alkalmazás közötti határ: könyvtárban strukturált enum, alkalmazásban anyhow a rugalmasságért. Továbbvitt eredmény: az Error típus a későbbi fejezetekben a tényleges I/O-műveletek, a Storage trait, a hálózati szerver és az FFI hibakezelésének alapja.
