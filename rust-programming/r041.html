17.5 Naplózás és megfigyelhetőség: tracing

17.5.1 Motiváció

Egy C++-ban írt TCP-szerver naplózása gyakran std::cerr-re írt sorokból vagy egy spdlog-hoz hasonló könyvtárból áll. A kérések nyomon követéséhez kézzel kell egyedi azonosítókat (request_id) generálni, és minden logüzenetbe beilleszteni. A konkurrens kérések esetén a naplóbejegyzések összekeverednek, és utólag nehéz rekonstruálni, hogy melyik sor melyik kéréshez tartozott. A szűrés szintje és modulja gyakran fordítási időben rögzült, vagy bonyolult konfigurációt igényel.

A Rust tracing crate-je ezt a problémát strukturált naplózással és span-ekkel oldja meg. Egy span egy műveleti hatókör (például egy kérés feldolgozása), amelybe a benne lévő események automatikusan beletartoznak. Így egyetlen #[instrument] attribútummal minden kapcsolathoz (nem kérés-szinten) egy span jön létre, amelynek belső azonosítóját a tracing kezeli (ez a formázott kimenetben alapból nem jelenik meg, lásd lent), és a napló szűrése futás közben, környezeti változóval állítható. Az alapformázó a span nevét és a rajta rögzített mezőket írja ki; a belső span-Id és az átfutási idő csak külön beállítással (például FmtSpan::CLOSE, illetve saját időmérés) kerül a kimenetbe. Az rkv-server már rendelkezik a Stats típusú atomikus számlálókkal a Atomikus műveletek és memóriarendezés alfejezetből; ebben a laborban ezeket tesszük megfigyelhetővé.

17.5.2 Fogalmak és szabályok

Definíció. A tracing crate három alapfogalma:

  • Event (tracing::info!, debug!, warn!, error!, trace!): egy időpontban bekövetkező esemény, hasonló a klasszikus naplóbejegyzéshez, de strukturált mezőket tartalmazhat.
  • Span (tracing::span! vagy a #[instrument] attribútum): egy időintervallumot átfogó, hierarchikus kontextus. A span-ek egymásba ágyazhatók, és az események a legbelső aktív span-hez tartoznak.
  • Subscriber: a naplófogyasztó, amely a span-eket és eventeket megkapja, és formázva kiírja, szűri vagy továbbítja. A tracing-subscriber a leggyakoribb implementáció.

Definíció. Az EnvFilter a tracing-subscriber szűrője, amely környezeti változóból (RUST_LOG) olvassa be a naplózási szinteket, például:

RUST_LOG=info
RUST_LOG=rkv_server=debug
RUST_LOG=info,tokio=warn

Ez modulonként (crate-enként) állítja be a minimális szintet.

Szabály. A #[tracing::instrument] attribútum egy függvényre írva automatikusan span-t nyit a függvény belépésekor, és bezárja kilépéskor. Alapértelmezés szerint a span neve a függvény neve, és a paramétereket strukturált mezőkként rögzíti (ha azok implementálják a Debug trait-et; a skip paraméterrel kihagyhatók).

Szabály (async kontextus). Async függvényekben a span-eknek át kell ívelniük az .await pontokon. A tracing modern verziói (0.1.x) a tracing-futures integrációval és az Instrument trait-tel ezt automatikusan kezelik; a #[instrument] async függvényekre is működik, mert a proc-macro a jövőt instrumentálja.

17.5.3 C++ és Rust összevetés

C++-ban egy szokásos időmérő és naplózó scope-segéd:

#include <spdlog/spdlog.h>
#include <chrono>

class ScopedLog {
public:
    ScopedLog(const std::string& name)
        : name_(name), start_(std::chrono::steady_clock::now()) {
        spdlog::info("{} start", name_);
    }
    ~ScopedLog() {
        auto ms = std::chrono::duration_cast<std::chrono::milliseconds>(
            std::chrono::steady_clock::now() - start_).count();
        spdlog::info("{} end ({} ms)", name_, ms);
    }
private:
    std::string name_;
    std::chrono::steady_clock::time_point start_;
};

void handle_request(const Request& req) {
    ScopedLog log("handle_request");
    // ...
}

A Rust megfelelője ugyanez, de nyelvi szinten és async-tudatosan:

#[tracing::instrument]
async fn handle_request(socket: TcpStream) {
    // ...
}

A különbség: a Rust #[instrument] nem csupán időt mér, hanem egy span-t hoz létre, amely a naplófogyasztó számára hierarchiát jelent. C++-ban ehhez nem nyelvi eszköz kell, hanem könyvtári megoldás: az OpenTelemetry C++ spanjei, a Boost.Log scope-olt attribútumai vagy egy thread-local kontextus (például spdlog-formázóval) hasonló hierarchiát adnak. A request_id kézi átadása csak az egyik, könyvtár nélküli lehetőség; a lényegi különbség, hogy C++-ban a követhetőség szerződését a választott naplózó könyvtárnak kell meghatároznia és a hívóknak követniük, míg a Rust attribútum a függvény szignatúrájához kötött instrumentálást generál.

17.5.4 Kidolgozott példa: tracing alapok

Először egy önálló kis programot írunk, hogy lássuk a span-ek és az EnvFilter működését.

Munkakönyvtár: ~/rust-labor/r041-tracing/

cargo new r041-tracing
cd r041-tracing

Cargo.toml:

[dependencies]
tracing = "0.1"
tracing-subscriber = { version = "0.3", features = ["env-filter"] }

src/main.rs:

use tracing::{debug, info, warn};
use tracing_subscriber::fmt::format::FmtSpan;
use tracing_subscriber::EnvFilter;

#[tracing::instrument]
fn compute(value: u64) -> u64 {
    debug!(value, "számítás indul");
    let result = value * 2;
    info!(result, "számítás kész");
    result
}

fn main() {
    // RUST_LOG hiányában INFO szint; a span lezárását is eseményként kiírjuk.
    let filter = EnvFilter::try_from_default_env().unwrap_or_else(|_| EnvFilter::new("info"));
    tracing_subscriber::fmt()
        .with_env_filter(filter)
        .with_span_events(FmtSpan::CLOSE)
        .without_time() // a mintakimenet determinisztikus legyen
        .with_ansi(false) // szín nélküli, másolható kimenet
        .with_target(false)
        .init();

    warn!("példa indul");
    compute(21);
}

Az EnvFilter::from_default_env() önmagában nem ad INFO alapértelmezést: ha a RUST_LOG nincs beállítva (vagy üres), csak az ERROR szintet engedi át, így a példa semmit nem írna ki. Ezért használjuk az EnvFilter::try_from_default_env()-et explicit tartalékkal: ha a változó hiányzik, EnvFilter::new("info") lép életbe. A #[tracing::instrument] önmagában nem ír ki sort a span lezárásakor; ehhez a formázót kell beállítani (with_span_events(FmtSpan::CLOSE)). A mezők a span nevében jelennek meg (compute{value=21}), az eseményekhez fűzött mezők (result=42) a szöveg után.

Futtatás RUST_LOG nélkül (és ugyanígy RUST_LOG=info mellett):

cargo run

Kimenet (Rust 1.99.1, tracing-subscriber 0.3, a .without_time() és a .with_ansi(false) miatt determinisztikus és szín nélküli):

 WARN példa indul
 INFO compute{value=21}: számítás kész result=42
 INFO compute{value=21}: close

A debug! üzenet nem jelenik meg, mert az alapértelmezett szint INFO. A RUST_LOG=debug cargo run kimenete:

 WARN példa indul
DEBUG compute{value=21}: számítás indul value=21
 INFO compute{value=21}: számítás kész result=42
 INFO compute{value=21}: close

Szemben ezzel, ha a tartalékot elhagyjuk, és csak az EnvFilter::from_default_env()-et használjuk, a RUST_LOG nélküli futás nem ír ki semmit, RUST_LOG=warn mellett pedig csak a WARN sort.

Span-azonosító és request_id. A tracing subscriberje belsőleg számon tart egy span-azonosítót (Id), de ez a szokásos formázott kimenetben nem jelenik meg, és folyamatok vagy gépek között nem követhető. Ha egy kérést a naplókban végigkövetni kell, azt explicit mezőként vesszük fel (request_id), amely a span nevében minden eseménynél megjelenik.

17.5.5.2 2. Aktív kapcsolatok: RAII őr a Stats-ban

Az aktív kapcsolatok számlálója csak akkor megbízható, ha a csökkentés minden kilépési úton lefut: normál zárásnál, hibánál (?) és akkor is, ha a kapcsolatot kezelő taskot megszakítják (abort, vagy a leállítási határidő lejár). Ezt a Drop-alapú őr garantálja: a Stats::connection_opened egy ConnectionGuard-ot ad, amelynek eldobása csökkenti a számlálót.

Kódblokk — fájl: rkv-core/src/stats.rs · művelet: az active_connections mező és az új impl/típus/tesztek hozzáadása az Atomikus műveletek és memóriarendezés-ös fájlhoz · ellenőrzés: cargo test -p rkv-core stats

// a Stats struktúrába: active_connections: AtomicU64,
// a fájl elejére: use std::sync::Arc;
impl Stats {
    /// Az éppen nyitott kapcsolatok száma.
    pub fn active_connections(&self) -> u64 {
        self.active_connections.load(Ordering::Relaxed)
    }

    /// Új kapcsolatot jegyez be. A visszaadott őr `Drop`-ja csökkenti a számlálót,
    /// ezért normál kilépésnél, hibánál és a task megszakításakor (abort) is lefut.
    pub fn connection_opened(self: &Arc<Self>) -> ConnectionGuard {
        self.active_connections.fetch_add(1, Ordering::Relaxed);
        ConnectionGuard(Arc::clone(self))
    }
}

/// RAII őr: a kapcsolat élettartama alatt él, eldobáskor csökkenti az aktív kapcsolatok számát.
#[derive(Debug)]
pub struct ConnectionGuard(Arc<Stats>);

impl Drop for ConnectionGuard {
    fn drop(&mut self) {
        self.0.active_connections.fetch_sub(1, Ordering::Relaxed);
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn guard_decrements_on_drop() {
        let stats = Arc::new(Stats::default());
        let guard = stats.connection_opened();
        assert_eq!(stats.active_connections(), 1);
        drop(guard);
        assert_eq!(stats.active_connections(), 0);
    }

    #[test]
    fn guard_decrements_on_panic_unwind() {
        let stats = Arc::new(Stats::default());
        let s = Arc::clone(&stats);
        let result = std::panic::catch_unwind(move || {
            let _guard = s.connection_opened();
            panic!("hiba a kapcsolat közben");
        });
        assert!(result.is_err());
        assert_eq!(stats.active_connections(), 0);
    }
}

(A Stats struktúra kiegészül egy active_connections: AtomicU64 mezővel, a lib.rs-ben pedig a pub use stats::{ConnectionGuard, Stats}; sor exportálja az új típust.)

17.5.5.3 3. A szerver instrumentálása

A handle_client függvényre #[tracing::instrument] kerül: a span minden kapcsolathoz hozzáadja a peer mezőt, és a függvény minden eseménye ebben a kontextusban jelenik meg. A skip_all kikapcsolja a paraméterek automatikus naplózását (a socket és a tároló nem Debug-barát). A függvény elején jegyezzük be a kapcsolatot, az őr a függvény végéig él. A spawn_blocking külön szálon fut, ezért a tracing szál-lokális span-kontextusa nem öröklődik automatikusan: a Span::current()-et a closure előtt el kell menteni, és a szinkron munkát in_scope-ban kell futtatni, különben a process_line_with eseményei span nélkül jelennek meg. Ez egyben a megfigyelhetőség határa is: a blokkoló szálon belül minden esemény az átadott span alá kerül, de a spawn_blocking saját életciklus-eseményei (indítás, befejezés) nem. A következő részlet a függvény elejét mutatja:

#[tracing::instrument(skip_all, fields(peer = %peer))]
async fn handle_client(
    socket: TcpStream,
    peer: SocketAddr,
    store: SharedStore,
    token: CancellationToken,
    max_frame: usize,
    max_response: usize,
) -> io::Result<()> {
    // Az őr a függvény végéig él: normál kilépésnél, hibánál (`?`) és
    // a task megszakításakor is csökkenti a számlálót.
    let _guard = store.stats().connection_opened();
    info!("kapcsolat nyitva");
    // ... a korábbi ciklus, a TooLong ágban warn!(max_frame, ...), a kérésnél debug!(bytes = ..., "kérés") ...
    info!("kapcsolat zárul");
    writer.shutdown().await
}

use std::io;
use std::net::SocketAddr;
use std::sync::Arc;
use std::time::Duration;

use rkv_core::{Command, Response, SharedStore, Stats};
use tokio::io::{AsyncBufRead, AsyncBufReadExt, AsyncReadExt, AsyncWriteExt, BufReader, BufWriter};
use tokio::net::{TcpListener, TcpStream};
use tokio::sync::Semaphore;
use tokio::task::JoinSet;
use tokio_util::sync::CancellationToken;
use tracing::{debug, info, warn};

/// A szerver erőforráskorlátai.
#[derive(Debug, Clone)]
pub struct ServerConfig {
    /// Egy kérés (a sorvéggel együtt) legfeljebb ennyi bájt lehet: a kulcs és az érték együtt.
    pub max_frame: usize,
    /// Egyidejű kapcsolatok felső határa; a többletet "ERR server busy" válasszal utasítjuk el.
    pub max_connections: usize,
    /// A leállás 2. fázisának határideje: eddig várunk a futó klienstaskokra.
    pub shutdown_grace: Duration,
    /// Egy válasz legfeljebb ennyi bájt (a `LIST` miatt); a nagyobbat `ERR response too large` váltja fel.
    pub max_response: usize,
}

impl Default for ServerConfig {
    fn default() -> Self {
        Self {
            max_frame: 64 * 1024,
            max_connections: 1024,
            shutdown_grace: Duration::from_secs(5),
            max_response: 1024 * 1024,
        }
    }
}

/// A `max_frame` felső határa: a `take(max_frame + 1)` és a puffer lefoglalása ennél nagyobbra nem értelmes.
pub const MAX_FRAME_LIMIT: usize = 64 * 1024 * 1024;

impl ServerConfig {
    /// A belépési ponton is érvényesített ellenőrzés: a publikus mezők a builderen kívül is
    /// beállíthatók, ezért a `run_server_with` ezt hívja. A `Semaphore` kapacitáshatárát is betartja.
    pub fn validate(&self) -> Result<(), ConfigError> {
        if self.max_frame == 0 {
            return Err(ConfigError::Zero("max_frame"));
        }
        if self.max_frame > MAX_FRAME_LIMIT {
            return Err(ConfigError::TooLarge("max_frame"));
        }
        if self.max_connections == 0 {
            return Err(ConfigError::Zero("max_connections"));
        }
        if self.max_connections > Semaphore::MAX_PERMITS {
            return Err(ConfigError::TooLarge("max_connections"));
        }
        if self.max_response == 0 {
            return Err(ConfigError::Zero("max_response"));
        }
        Ok(())
    }
}

/// A `ServerConfig` érvénytelen korlátja (a `validate` és a builder `build` hibája).
#[derive(Debug, PartialEq, Eq)]
#[non_exhaustive]
pub enum ConfigError {
    /// A megnevezett korlát nulla, ami a szervert használhatatlanná tenné.
    Zero(&'static str),
    /// A megnevezett korlát a megengedett felső határnál nagyobb.
    TooLarge(&'static str),
}

impl std::fmt::Display for ConfigError {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        match self {
            ConfigError::Zero(field) => write!(f, "a(z) {field} korlát nem lehet nulla"),
            ConfigError::TooLarge(field) => write!(f, "a(z) {field} korlát túl nagy"),
        }
    }
}

impl std::error::Error for ConfigError {}

/// Egy beolvasott keret eredménye.
#[derive(Debug, PartialEq, Eq)]
enum Frame {
    /// Teljes, `\n`-nel lezárt sor van a pufferben.
    Line,
    /// A sor hosszabb a megengedettnél (a puffer legfeljebb `max_frame + 1` bájtot tartalmaz).
    TooLong,
    /// A kapcsolat lezárult (egy csonka, sorvég nélküli maradékot eldobunk).
    Eof,
}

/// Egy sort olvas legfeljebb `max_frame` bájtig. A `take` korlátozza a pufferbe kerülő
/// bájtok számát, így sorvég nélküli, végtelen bemenet sem növeli a memóriát.
async fn read_frame<R>(reader: &mut R, buf: &mut Vec<u8>, max_frame: usize) -> io::Result<Frame>
where
    R: AsyncBufRead + Unpin,
{
    buf.clear();
    let n = reader
        .take(max_frame as u64 + 1)
        .read_until(b'\n', buf)
        .await?;
    Ok(if n == 0 {
        Frame::Eof
    } else if buf.len() > max_frame {
        Frame::TooLong
    } else if buf.ends_with(b"\n") {
        Frame::Line
    } else {
        Frame::Eof
    })
}

/// Egy kérés feldolgozása: értelmezés, végrehajtás, válasz. Szinkron és blokkolhat
/// (a `FileStore` fájlműveleteket végez), ezért a hívó `spawn_blocking`-ben futtatja.
///
/// Két réteg van: a szöveges `GET/SET/DEL/LIST` az olvasható, szöveg-biztos
/// kulcsokra és értékekre való; a `GETX/SETX` hexa kulccsal és értékkel bármilyen
/// bájtsort átvisz (az üres értéket a `-` jelöli).
pub fn process_line(line: &str, store: &SharedStore) -> String {
    if let Some(reply) = process_binary(line, store) {
        return reply;
    }
    let command = match line.parse::<Command>() {
        Ok(command) => command,
        Err(e) => return single_line(&format!("ERR {e}")),
    };
    let response = match store.apply(&command) {
        Ok(response) => response,
        Err(e) => return single_line(&format!("ERR {e}")),
    };
    match (&command, response) {
        (_, Response::Ok) => "OK".to_string(),
        (_, Response::NotFound) => "NOTFOUND".to_string(),
        (Command::Get(key), Response::Value(bytes)) => match text_safe(key, &bytes) {
            Some(text) => format!("VALUE {key} {text}"),
            None => "ERR value is not text-safe, use GETX".to_string(),
        },
        (_, Response::Entries(items)) => {
            let mut out = String::new();
            for (key, bytes) in items {
                match text_safe(&key, &bytes) {
                    Some(text) => out.push_str(&format!("VALUE {key} {text}\n")),
                    // Ami szövegként nem ábrázolható, az hexa alakban jön: VALUEX <hexkulcs> <hexérték>
                    None => out.push_str(&format!(
                        "VALUEX {} {}\n",
                        to_hex(key.as_bytes()),
                        to_hex(&bytes)
                    )),
                }
            }
            out.push_str("OK");
            out
        }
        (_, Response::Value(_)) => "ERR internal error".to_string(),
    }
}

/// Szöveg-biztos-e a bejegyzés: a kulcs érvényes protokollkulcs (nem üres, nincs benne
/// szóköz vagy vezérlőkarakter), az érték érvényes UTF-8 és nincs benne vezérlőkarakter
/// (így nem tud új választ kezdeni).
fn text_safe<'a>(key: &str, bytes: &'a [u8]) -> Option<&'a str> {
    let key_ok = !key.is_empty() && !key.chars().any(|c| c.is_whitespace() || c.is_control());
    let text = std::str::from_utf8(bytes).ok()?;
    (key_ok && !text.is_empty() && !text.chars().any(char::is_control)).then_some(text)
}

fn to_hex(bytes: &[u8]) -> String {
    if bytes.is_empty() {
        return "-".to_string();
    }
    bytes.iter().map(|b| format!("{b:02x}")).collect()
}

fn from_hex(text: &str) -> Result<Vec<u8>, String> {
    if text == "-" {
        return Ok(Vec::new());
    }
    if text.is_empty() || !text.len().is_multiple_of(2) || !text.is_ascii() {
        return Err("invalid hex".to_string());
    }
    (0..text.len())
        .step_by(2)
        .map(|i| u8::from_str_radix(&text[i..i + 2], 16).map_err(|_| "invalid hex".to_string()))
        .collect()
}

/// `SETX <hexkulcs> <hexérték|->` és `GETX <hexkulcs>`; más sorra `None`.
fn process_binary(line: &str, store: &SharedStore) -> Option<String> {
    let (verb, rest) = line.split_once(' ').unwrap_or((line, ""));
    let result = match verb {
        "SETX" => {
            let (k, v) = rest.split_once(' ')?;
            decode_key(k).and_then(|key| {
                let value = from_hex(v)?;
                store.set(key, value).map_err(|e| e.to_string())?;
                Ok("OK".to_string())
            })
        }
        "GETX" => {
            decode_key(rest).and_then(|key| match store.get(&key).map_err(|e| e.to_string())? {
                Some(bytes) => Ok(format!(
                    "VALUEX {} {}",
                    to_hex(key.as_bytes()),
                    to_hex(&bytes)
                )),
                None => Ok("NOTFOUND".to_string()),
            })
        }
        _ => return None,
    };
    Some(result.unwrap_or_else(|e| single_line(&format!("ERR {e}"))))
}

fn decode_key(hex: &str) -> Result<String, String> {
    let bytes = from_hex(hex)?;
    match String::from_utf8(bytes) {
        Ok(key) if !key.is_empty() => Ok(key),
        _ => Err("key must be non-empty UTF-8".to_string()),
    }
}

/// A protokoll soronkénti: a hibaüzenetekből eltávolítjuk a sortörést.
fn single_line(text: &str) -> String {
    text.replace(['\n', '\r'], " ")
}

async fn reply<W>(writer: &mut W, response: &str) -> io::Result<()>
where
    W: AsyncWriteExt + Unpin,
{
    writer.write_all(response.as_bytes()).await?;
    writer.write_all(b"\n").await?;
    writer.flush().await
}

#[tracing::instrument(skip_all, fields(peer = %peer))]
async fn handle_client(
    socket: TcpStream,
    peer: SocketAddr,
    store: SharedStore,
    token: CancellationToken,
    max_frame: usize,
    max_response: usize,
) -> io::Result<()> {
    // Az őr a függvény végéig él: normál kilépésnél, hibánál (`?`) és a task megszakításakor is csökkenti a számlálót.
    let _guard = store.stats().connection_opened();
    info!("kapcsolat nyitva");
    let (read_half, write_half) = socket.into_split();
    let mut reader = BufReader::new(read_half);
    let mut writer = BufWriter::new(write_half);
    let mut buf = Vec::new();

    loop {
        // A beolvasás megszakítható (a leállítás kilép a ciklusból); a már beolvasott
        // parancsot viszont mindig végrehajtjuk és megválaszoljuk.
        let frame = tokio::select! {
            _ = token.cancelled() => break,
            frame = read_frame(&mut reader, &mut buf, max_frame) => frame?,
        };
        match frame {
            Frame::Eof => break,
            Frame::TooLong => {
                warn!(max_frame, "túl hosszú kérés, a kapcsolat lezárul");
                // A keretezés nem állítható vissza: hibaüzenet, majd lezárás.
                reply(&mut writer, "ERR line too long").await?;
                break;
            }
            Frame::Line => {
                let line = buf.strip_suffix(b"\n").unwrap_or(&buf);
                let line = line.strip_suffix(b"\r").unwrap_or(line);
                debug!(bytes = line.len(), "kérés");
                let response = match std::str::from_utf8(line) {
                    Ok(line) => {
                        let (line, store) = (line.to_owned(), store.clone());
                        // A tárolóművelet blokkolhat: nem az executor szálán fut.
                        // A span nem öröklődik a blokkoló szálra, ezért explicit átadjuk.
                        let span = tracing::Span::current();
                        tokio::task::spawn_blocking(move || {
                            span.in_scope(|| process_line_with(&line, &store, max_response))
                        })
                        .await
                        .unwrap_or_else(|_| "ERR internal error".to_string())
                    }
                    Err(_) => "ERR request is not valid UTF-8".to_string(),
                };
                reply(&mut writer, &response).await?;
            }
        }
    }
    // A puffer ürítése és a küldő irány lezárása kilépés előtt.
    info!("kapcsolat zárul");
    writer.shutdown().await
}

/// A szerver az alapértelmezett korlátokkal.
pub async fn run_server(listener: TcpListener, store: SharedStore, token: CancellationToken) {
    run_server_with(listener, store, token, ServerConfig::default()).await;
}

/// A szerver megadott korlátokkal. Visszatérése előtt minden klienstaskot megvár (vagy határidő után megszakít).
pub async fn run_server_with(
    listener: TcpListener,
    store: SharedStore,
    token: CancellationToken,
    config: ServerConfig,
) {
    config.validate().expect("érvénytelen ServerConfig");
    const REJECT_LIMIT: usize = 64;
    let reject_slots = Arc::new(Semaphore::new(REJECT_LIMIT));
    let slots = Arc::new(Semaphore::new(config.max_connections));
    let mut clients = JoinSet::new();
    loop {
        tokio::select! {
            _ = token.cancelled() => break,
            res = listener.accept() => {
                let (mut socket, addr) = match res {
                    Ok(v) => v,
                    Err(e) => { warn!("accept hiba: {e}"); continue; }
                };
                let Ok(permit) = Arc::clone(&slots).try_acquire_owned() else {
                    // Betelt a kapcsolatkeret: rövid, korlátos idejű elutasítás, korlátos számú
                    // párhuzamos elutasító taskkal; a többi többlet-kapcsolat azonnal lezárul.
                    if let Ok(reject_permit) = Arc::clone(&reject_slots).try_acquire_owned() {
                        clients.spawn(async move {
                            let _reject_permit = reject_permit;
                            let _ = tokio::time::timeout(
                                Duration::from_millis(200),
                                socket.write_all(b"ERR server busy\n"),
                            ).await;
                        });
                    }
                    continue;
                };
                let (store, token) = (store.clone(), token.clone());
                clients.spawn(async move {
                    // A permit a task végéig él: a kapcsolat bezárásakor felszabadul.
                    let _permit = permit;
                    if let Err(e) = handle_client(socket, addr, store, token, config.max_frame, config.max_response).await {
                        warn!(%addr, "kliens hiba: {e}");
                    }
                });
            }
            // A befejeződött taskok eredményét folyamatosan begyűjtjük.
            Some(res) = clients.join_next(), if !clients.is_empty() => {
                if let Err(e) = res {
                    warn!("klienstask: {e}");
                }
            }
        }
    }

    // 1. fázis: új kapcsolatot nem fogadunk.
    drop(listener);

    // 2. fázis: a futó parancsok befejezése és a válaszok ürítése, határidővel.
    let drain = async {
        while let Some(res) = clients.join_next().await {
            if let Err(e) = res {
                warn!("klienstask: {e}");
            }
        }
    };
    if tokio::time::timeout(config.shutdown_grace, drain).await.is_err() {
        warn!(clients = clients.len(), "a leállítási határidő lejárt, a maradék kliens megszakad");
        clients.shutdown().await;
    }
}

/// Periodikus metrikajelentés: a `Stats` publikus getterein keresztül olvas.
pub async fn metrics_loop(stats: Arc<Stats>, every: Duration) {
    let mut interval = tokio::time::interval(every);
    interval.tick().await; // az első tick azonnali: kihagyjuk
    loop {
        interval.tick().await;
        info!(
            get = stats.get_count(),
            set = stats.set_count(),
            delete = stats.delete_count(),
            list = stats.list_count(),
            active = stats.active_connections(),
            "metrikák"
        );
    }
}

A metrics_loop a Stats publikus getterein keresztül olvas (get_count(), set_count(), … active_connections()), nem a mezőkhöz nyúl; a getterek Relaxed rendezést használnak, ami a metrikákhoz elegendő (Atomikus műveletek és memóriarendezés).

17.5.5.4 4. Subscriber inicializálása és a metrikatask indítása

A subscriber-t a serve függvény elején, a block_on által a runtime-on futtatott aszinkron törzsben inicializáljuk, a szerver indítása előtt. (Ez már a tokio runtime belsejében van, nem előtte.) A subscriber a runtime-tól független, ezért ez a hely megfelelő; fontos, hogy csak egyszer hívjuk.)

Kódblokk — fájl: rkv-server/src/main.rs · művelet: teljes csere · ellenőrzés: cargo build -p rkv-server

use std::time::Duration;

use anyhow::Result;
use rkv_core::{FileStore, MemStore, SharedStore};
use rkv_server::{metrics_loop, run_server};
use tokio::net::TcpListener;
use tokio_util::sync::CancellationToken;
use tracing::info;
use tracing_subscriber::EnvFilter;

fn main() -> Result<()> {
    let rt = tokio::runtime::Runtime::new()?;
    let outcome = rt.block_on(serve());
    // A runtime eldobása a futó `spawn_blocking` munkát korlátlanul megvárná: időkorlát.
    rt.shutdown_timeout(Duration::from_secs(5));
    outcome
}

async fn serve() -> Result<()> {
    // RUST_LOG hiányában INFO szint: az `EnvFilter::from_default_env()` hiányzó
    // változónál csak az ERROR szintet engedné át.
    let filter = EnvFilter::try_from_default_env().unwrap_or_else(|_| EnvFilter::new("info"));
    tracing_subscriber::fmt().with_env_filter(filter).init();

    // Használat: rkv-server [cím] [--data-dir <könyvtár>]
    // `--data-dir` nélkül memóriabeli tároló; vele a FileStore (snapshot + napló) fut.
    let mut addr = "127.0.0.1:8080".to_string();
    let mut data_dir: Option<std::path::PathBuf> = None;
    let mut args = std::env::args().skip(1);
    while let Some(arg) = args.next() {
        if arg == "--data-dir" {
            data_dir = Some(
                args.next()
                    .ok_or_else(|| anyhow::anyhow!("a --data-dir érték hiányzik"))?
                    .into(),
            );
        } else {
            addr = arg;
        }
    }
    let listener = TcpListener::bind(&addr).await?;
    info!(%addr, "rkv-server indul");

    let store = SharedStore::new(MemStore::new());
    let token = CancellationToken::new();
    let shutdown_token = token.clone();

    tokio::spawn(async move {
        if let Err(e) = tokio::signal::ctrl_c().await {
            tracing::error!("ctrl_c hiba: {e}");
            return;
        }
        info!("leállítási jel érkezett");
        shutdown_token.cancel();
    });

    let metrics = tokio::spawn(metrics_loop(store.stats(), Duration::from_secs(10)));
    run_server(listener, store, token).await;
    metrics.abort();
    info!("leállás kész");
    Ok(())
}

17.5.5.5 5. Szűrés környezeti változóval

A szerver futtatása előtt beállíthatjuk a kívánt szintű naplózást. RUST_LOG nélkül a main fenti tartaléka miatt INFO szint érvényes:

Ha csak a saját crate naplóit szeretnénk DEBUG szinten, a külső crate-eket (például a tokio belső üzeneteit) pedig WARN szinten:

A RUST_LOG támogatja a többszörös modulszűrést vesszővel elválasztva. Az info szinten a szerver indulása, a kapcsolatok nyitása/zárása és a metrikák jelennek meg; a debug szint a kérésenkénti kérés eseményeket is hozzáadja. A kimenet pontos formátuma (időbélyeg, színek, a span mezőinek megjelenítése) a tracing-subscriber beállításától függ.

17.5.5.6 6. Teszt: az aktív kapcsolatok száma visszatér a kiinduló értékre

Kódblokk — fájl: rkv-server/tests/metrics.rs · művelet: új fájl · ellenőrzés: cargo test -p rkv-server --test metrics → 2 sikeres teszt

use std::time::Duration;

use rkv_core::{MemStore, SharedStore};

/// Addig vár, amíg a feltétel igaz nem lesz (legfeljebb 5 s).
async fn eventually(mut condition: impl FnMut() -> bool) {
    timeout(Duration::from_secs(5), async {
        while !condition() {
            sleep(Duration::from_millis(10)).await;
        }
    })
    .await
    .expect("a feltétel 5 s alatt sem teljesült");
}

#[tokio::test]
async fn active_connections_return_to_the_baseline() {
    let store = SharedStore::new(MemStore::new());
    let stats = store.stats();
    let listener = TcpListener::bind("127.0.0.1:0").await.unwrap();
    let addr = listener.local_addr().unwrap();
    let token = CancellationToken::new();
    let server = tokio::spawn(run_server(listener, store, token.clone()));

    let baseline = stats.active_connections();
    assert_eq!(baseline, 0);

    let mut client = BufReader::new(TcpStream::connect(addr).await.unwrap());
    client.get_mut().write_all(b"SET k v\n").await.unwrap();
    let mut line = String::new();
    timeout(Duration::from_secs(5), client.read_line(&mut line)).await.unwrap().unwrap();
    assert_eq!(line.trim_end(), "OK");
    assert_eq!(stats.active_connections(), baseline + 1); // nyitott kapcsolat
    assert_eq!(stats.set_count(), 1);

    drop(client); // bezárás
    eventually(|| stats.active_connections() == baseline).await;

    token.cancel();
    timeout(Duration::from_secs(10), server).await.unwrap().unwrap();
}

#[tokio::test]
async fn guard_is_released_when_the_task_is_aborted() {
    let store = match &data_dir {
        Some(dir) => {
            std::fs::create_dir_all(dir)?;
            SharedStore::new(FileStore::open(
                dir.join("state.json"),
                dir.join("append.log"),
            )?)
        }
        None => SharedStore::new(MemStore::new()),
    };
    let stats = store.stats();

    let held = stats.clone();
    let task = tokio::spawn(async move {
        let _guard = held.connection_opened();
        std::future::pending::<()>().await; // a kapcsolat "örökké" tart
    });
    eventually(|| stats.active_connections() == 1).await;

    task.abort(); // a task megszakítása eldobja a future-t, vele az őrt
    assert!(task.await.unwrap_err().is_cancelled());
    assert_eq!(stats.active_connections(), 0);
}

Az első teszt egy kapcsolat megnyitása után egyet, bezárása után újra a kiinduló értéket olvassa; a második a task-megszakítási utat ellenőrzi: az abort eldobja a future-t, és vele az őrt, így a számláló nem marad „beragadva”.

A kapcsolatkezelés során a span-ek a formázott kimenetben a handle_client{peer=127.0.0.1:...} előtaggal jelennek meg, jelezve a hierarchiát.

Ellenőrzési pont. Az rkv-server instrumentált (tracing), a Stats az aktív kapcsolatokat is számolja (ConnectionGuard), a metrics_loop a getterekből jelent; a cargo test --workspace és a clippy -D warnings hibátlan.

17.5.6 Tipikus hibák és átállási csapdák

  1. A subscriber többszöri inicializálása. A kód lefordul: a hiba futási hiba. Ha például egy tesztmodulban minden teszt lefutásakor meghívjuk a tracing_subscriber::fmt().init()-et, a második hívás pánikol (Unable to install global subscriber: SetGlobalDefaultError(...), ellenőrzött viselkedés). A két indító metódus szerződése eltér: az init() pánikkal jelzi, ha már van globális subscriber; a try_init() Result<(), TryInitError>-t ad vissza, a második hívásra Err-t, pánik nélkül. Megoldás: a subscriber-t egyszer, a main-ben vagy egy Once/OnceLock segítségével inicializáljuk, vagy a tesztekben a try_init()-et használjuk, és az Err eredményt tudatosan eldobjuk (let _ = ...), mert a már működő subscriber elfogadható.

  2. A span.enter() guard tartása .await-en át. Az enter() guardja a szálhoz köti az aktív spant; ha a guard az .await-en át él, a task felfüggesztésekor a span a szálon marad, és egy másik task eseményei rossz (beágyazott) span alá kerülnek. Két váltakozva futó task hibás naplója:

 INFO kérés{id=1}: kezdet
 INFO kérés{id=1}:kérés{id=2}: kezdet
 INFO kérés{id=1}:kérés{id=2}: vég
 INFO kérés{id=1}: vég

A helyes megoldás a teljes future instrumentálása (future.instrument(span), vagy #[tracing::instrument] async függvényen), amely a spant pollolásonként lépteti be és ki; ekkor mindkét task a saját spanje alatt naplóz (kérés{id=1}, kérés{id=2}). Await nélküli szinkron szakaszra a span.in_scope(|| ...) való. Az .instrument(info_span!("kérés", id)) változat kimenete (Rust 1.99.1, tokio::join! egyszálú runtime-on):

 INFO kérés{id=1}: kezdet
 INFO kérés{id=2}: kezdet
 INFO kérés{id=2}: vég
 INFO kérés{id=1}: vég

  1. Túlzott strukturálás. Minden kis lépést span-be csomagolni zajossá teszi a naplót. A span-eket műveleti határokhoz (például kérés, parancs) rendeljük, ne minden egyes függvényhíváshoz.

  2. A RUST_LOG figyelmen kívül hagyása, és a rejtett ERROR alapértelmezés. Ha fix szintet adunk meg EnvFilter helyett, a szint csak újrafordítással változtatható; az EnvFilter a RUST_LOG-ot az induláskor olvassa be, tehát az sem változik futás közben. Élő újraszűréshez külön tracing_subscriber::reload réteg kell (a reload::Layer egy kezelőt ad, amellyel a szűrő cserélhető); ezt a könyv nem tárgyalja. Az EnvFilter::from_default_env() tartalék nélkül változó hiányában csak az ERROR szintet engedi át, ezért a „semmi nem jelenik meg” hibakereséskor ez az első gyanú. Használjunk explicit tartalékot (try_from_default_env().unwrap_or_else(|_| EnvFilter::new("info"))).

17.5.7 Feladatok

  1. Fogalmi kérdés. Mi történik, ha a compute függvényben a #[tracing::instrument] attribútumot elhagyjuk, de a függvényen belül továbbra is van info! makró? A kimenetben mi változik a span nélkül?

  2. C++ átírás. A következő C++ kódrészlet egy kérést naplóz request_id-vel. Írd át Rustra tracing span-nel úgy, hogy a request_id ne legyen kézzel átadott paraméter, hanem a span automatikusan rögzítse.

void handle_request(int request_id, const Request& req) {
    spdlog::info("request {}: start", request_id);
    // ...
    spdlog::info("request {}: end", request_id);
}

  1. Implementáció. Adj a szerverhez egy új metrikát: az elutasított kapcsolatok számát (ERR server busy). Használj AtomicU64-et a Stats struktúrában, növeld az elutasításkor, add hozzá a metrics_loop kimenetéhez, és írj tesztet, amely a max_connections = 1 korlát túllépése után ellenőrzi a számláló értékét.

  2. Hibajavítás. A következő kód lefordul, de futáskor pánikol, mert a subscriber-t kétszer inicializálja (az init() a második hívásnál pánikol). Javítsd úgy, hogy a második inicializálás ne okozzon hibát.

fn init_logging() {
    tracing_subscriber::fmt().init();
}

fn main() {
    init_logging();
    init_logging(); // hibát okoz
    info!("hello");
}

17.5.8 Megoldások

  1. Fogalmi kérdés. A span nélkül az info! event-ek továbbra is megjelennek, de nem tartoznak egyetlen műveleti kontextushoz sem. A formázott kimenetben nem lesz span-azonosító, és a compute függvény belépését/kilépését nem látjuk automatikusan. Az event-ek lapos listát alkotnak, és nem lehet őket összekapcsolni.

  2. C++ átírás. A Rust változat span-t használ:

#[tracing::instrument(skip(req))]
fn handle_request(req: &Request) {
    info!("feldolgozás kezdődik");
    // ...
    info!("feldolgozás kész");
}

A request_id-t nem kell explicit paraméterként átadni: a span a saját mezőjeként rögzítheti, és a tracing-subscriber alapformázója a span mezőit az események prefixében megjeleníti (handle_request{request_id=7}: feldolgozás kezdődik). Fontos, hogy a tracing belső span-Id-ja ettől külön dolog: az alapformázó azt nem írja ki, ezért a kérés követhetőségéhez a saját request_id mező (vagy egy erre felkészített subscriber-réteg) kell. Ha a hívást blokkoló szálra adjuk át (spawn_blocking), a szál-lokális span-kontextus nem öröklődik automatikusan: a Span::current()-et át kell adni a closure-nek, és in_scope-ban kell futtatni. Például:

use std::sync::atomic::{AtomicU64, Ordering};
use tracing::Span;

static NEXT_REQUEST_ID: AtomicU64 = AtomicU64::new(1);

#[tracing::instrument(skip(req), fields(request_id = NEXT_REQUEST_ID.fetch_add(1, Ordering::Relaxed)))]
fn handle_request(req: &Request) {
    info!("feldolgozás kezdődik");
    // ...
    info!("feldolgozás kész");
}

fn offload(req: Request) {
    let span = Span::current();
    std::thread::spawn(move || span.in_scope(|| handle_request(&req)));
}
  1. Implementáció. A Stats-ba új mező, getter és egy pub(crate) növelő kerül, a SharedStore pedig egy publikus metódust ad a szervernek (a számláló mezői privátak, a szerver csak a publikus API-t látja):
// rkv-core/src/stats.rs
rejected_connections: AtomicU64, // új mező a Stats-ban

impl Stats {
    pub fn rejected_connections(&self) -> u64 {
        self.rejected_connections.load(Ordering::Relaxed)
    }

    /// Elutasított kapcsolat bejegyzése (a szerver hívja, ezért publikus).
    pub fn connection_rejected(&self) {
        self.rejected_connections.fetch_add(1, Ordering::Relaxed);
    }
}

A szerverben, az elutasító ágban (let Ok(permit) = ... else { ... }) a store.stats().connection_rejected(); hívás növeli a számlálót, a metrics_loop-ba pedig a rejected = stats.rejected_connections() mező kerül. A teszt a max_connections = 1 konfigurációval két kapcsolatot nyit: a másodikra ERR server busy érkezik, és a stats.rejected_connections() 1. A növelés a kapcsolat elfogadásakor történik (nem őrrel), mert az elutasított kapcsolat nem kezdett el élni.

  1. Hibajavítás. Az eredeti kód futási pánikot okoz a második init()-nél. A try_init Result-ot ad vissza, így a második hívás Err-t kap, pánik nélkül; az eredményt itt tudatosan eldobjuk (let _ =), mert a már beállított subscriber megfelelő:
fn init_logging() {
    let _ = tracing_subscriber::fmt().try_init();
}

fn main() {
    init_logging();
    init_logging(); // a második try_init() Err-t ad, de nem pánikol
    info!("hello");
}

17.5.9 Rövid összefoglaló

A tracing crate strukturált naplózást és hierarchikus span-eket biztosít. Az eventek (info!, debug!, warn!, error!) klasszikus naplóbejegyzések, míg a span-ek műveleti hatókörök, amelyeket a #[tracing::instrument] attribútum automatikusan nyit és zár. A tracing-subscriber EnvFilter-je a RUST_LOG környezeti változóval modulonként és szintenként szűri a naplót; tartalék nélkül (from_default_env()) a változó hiányában csak az ERROR szintet engedi át, ezért az rkv-server explicit INFO tartalékot ad. A span lezárásának kiírásához FmtSpan::CLOSE kell. Async kódban a #[instrument] a teljes future-t instrumentálja. Az rkv-serverben a tényleges szervert instrumentáltuk (handle_client, peer mezővel), a Stats megkapta az aktív kapcsolatok számlálóját és a Drop-alapú ConnectionGuard-ot (normál kilépésnél, hibánál és task-megszakításnál is csökkent), a metrics_loop pedig a publikus getterekből jelent. Továbbvitt eredmény. A megfigyelhető szerver (rkv-server/src/lib.rs, main.rs) és a Stats biztosítja a Záróprojekt: az rkv teljes rendszerként alfejezetben a rendszer állapotának áttekintését.
