10.1 Expression templates

A kifejezések lusta, sablonos reprezentációja az egyik legnagyobb hatású, ugyanakkor leggyakrabban félreértett modern C++ technika. A hagyományos operátor-túlterheléssel megírt matematikai vagy tartomány-specifikus könyvtárak gyakran ontják az ideiglenes objektumokat, mert minden egyes +, * vagy más művelet azonnal kiértékelődik, és a részeredményt egy új tárolóba helyezi. Az expression template-ek ezt a kiértékelést elhalasztják: a műveleti kifejezést egy sabloncsomópontokból álló, fordítási idejű szerkezetté alakítják, amely csak akkor fut le, amikor ténylegesen értékre van szükség – jellemzően egy hozzárendeléskor vagy egy indexeléskor. Ebben az alfejezetben lépésről lépésre felépítünk egy ilyen, vektoraritmetikát megvalósító kis keretrendszert, bemutatjuk a csomópontok, a lusta kiértékelés és az optimalizáció elvét, majd azonosítjuk a tipikus élettartam- és típusdedukciós csapdákat. A cél nem az, hogy egy teljes, termelésre kész lineáris algebra könyvtárat hozzunk létre, hanem hogy megértsük, mi történik a fordító szintjén, és milyen kompromisszumokat kell kötni.

10.1.1 A probléma: ideiglenes objektumok és a kiértékelési hullám

Vegyünk egy egyszerű, std::array-t beburkoló vektorosztályt, amely a + operátort túlterheli, hogy két vektor elemenkénti összegét adja vissza.

#include <array>
#include <cstddef>

template <std::size_t N>
class NaiveVector {
public:
    NaiveVector() = default;

    NaiveVector(const std::array<double, N>& data) : data_(data) {}

    double& operator[](std::size_t i) { return data_[i]; }
    double operator[](std::size_t i) const { return data_[i]; }

    std::size_t size() const { return N; }

    NaiveVector operator+(const NaiveVector& rhs) const {
        NaiveVector result;
        for (std::size_t i = 0; i < N; ++i) {
            result[i] = (*this)[i] + rhs[i];
        }
        return result;
    }

private:
    std::array<double, N> data_{};
};

Ha a felhasználó egy olyan kifejezést ír, mint d = a + b + c;, akkor a fenti implementáció a következő lépéseket hajtja végre:

  1. Kiértékeli a + b-t: létrehoz egy NaiveVector<N> ideiglenest, kitölti az összegekkel.
  2. Kiértékeli (a + b) + c-t: újabb ideiglenest hoz létre, amelyet az előző ideiglenes és c elemeiből számol.
  3. Végül a d-be másolja az eredményt.

Minden + művelet egy teljes ciklust futtat, memóriát foglal (vagy legalábbis a veremben létrehozza a tömböt), és másol. Kis méret esetén a fordító szinte mindent optimalizálhat, de nagyobb, dinamikus méretű tárolóknál, vagy ha a kifejezések mélyek és bonyolultak, ez a költség jelentős lehet. Ráadásul a műveletek nem fuzionálhatók: a fordító nehezen látja át a teljes kifejezést, mert az egyes operátorhívások önálló függvényekként jelennek meg, és a köztes tárolók akadályozzák a cache-barát, egyetlen ciklusba való összevonást.

Az expression template-ek lényege, hogy az a + b + c kifejezést ne értékeljük ki azonnal. Ehelyett a kifejezés egy olyan típust kap, amely leírja a műveletet, de tényleges számítást nem végez. A kiértékelés akkor következik be, amikor a kifejezésből vektorrá konvertálunk, például egy értékadó operátorban. Ekkor a célvektor elemeit egyetlen ciklusban, a teljes kifejezésfát bejárva állítjuk elő. Nincs ideiglenes tároló, nincs felesleges másolat, és a fordító a rekurzívan beágyazott operator[] hívásokat agresszívan inline-olhatja.

10.1.2 Alapépítőkövek: a CRTP-alapú kifejezés interfész

Az expression template-ekben minden kifejezés – a levelek és a belső csomópontok is – egy közös interfészt valósítanak meg: rendelkeznek size() és operator[] tagfüggvénnyel. A size() a kifejezés dimenzióját adja vissza, az operator[] pedig a kifejezés adott indexű elemét számítja ki, anélkül, hogy a teljes eredményt tárolná. A gyakori tervezési minta a Curiously Recurring Template Pattern (CRTP), amellyel a közös műveleteket egy alaposztályba emelhetjük, és a származtatott típus önmagára hivatkozva adja meg a tényleges viselkedést.

#include <cstddef>

template <typename Derived>
struct VectorExpr {
    const Derived& self() const noexcept {
        return static_cast<const Derived&>(*this);
    }

    std::size_t size() const noexcept {
        return self().size();
    }

    double operator[](std::size_t i) const {
        return self()[i];
    }
};

Ez az alaposztály nem tárol semmit, csak egy kényelmes, statikus polimorfizmust biztosító réteg. A Vector osztályunk ebből származik, és megvalósítja a tényleges adattárolást.

#include <algorithm>
#include <array>
#include <cassert>
#include <cstddef>
#include <initializer_list>

template <std::size_t N>
class Vector : public VectorExpr<Vector<N>> {
public:
    Vector() = default;

    Vector(const std::array<double, N>& data) : data_(data) {}

    // elemlistás konstruktor: Vector<4> a{1, 2, 3, 4};
    Vector(std::initializer_list<double> init) {
        assert(init.size() == N);
        std::copy_n(init.begin(), std::min(init.size(), N), data_.begin());
    }

    Vector(const Vector&) = default;
    Vector& operator=(const Vector&) = default;

    double& operator[](std::size_t i) {
        assert(i < N);
        return data_[i];
    }

    double operator[](std::size_t i) const {
        assert(i < N);
        return data_[i];
    }

    std::size_t size() const noexcept {
        return N;
    }

private:
    std::array<double, N> data_{};
};

Fontos, hogy a Vector a VectorExpr<Vector<N>>-ből származik, így a többi kifejezéstípus is fogadhatja mint levélcsomópontot.

10.1.3 Csomóponttípusok: a műveletek lusta reprezentációi

Most definiáljuk a kifejezések belső csomópontjait. A tárolási szabály: a levelek (Vector<N>) const referenciaként, a belső csomópontok (a könnyű, csak referenciákat és skalárokat hordozó kifejezésobjektumok) érték szerint kerülnek a csomópontba. Így az a + b + c kifejezésfa nem másolja le az a, b, c tömbjeit. Ennek ára az élettartam-kötöttség (lásd az auto csapdát lentebb). A szabályt egy kis tulajdonságsablon fejezi ki:

#include <cstddef>

template <std::size_t N> class Vector;   // előre deklaráció

template <typename E>
struct Stored { using type = E; };              // belső csomópont: érték szerint

template <std::size_t N>
struct Stored<Vector<N>> { using type = const Vector<N>&; };   // levél: referencia

Az összeadásnál az AddExpr két alkifejezést tárol, a size() és az operator[] rekurzívan hívja az operandusok megfelelő metódusait. A konstruktor ellenőrzi, hogy a két operandus mérete megegyezik.

#include <cassert>

template <typename L, typename R>
class AddExpr : public VectorExpr<AddExpr<L, R>> {
public:
    AddExpr(const L& lhs, const R& rhs)
        : lhs_(lhs), rhs_(rhs) {
        assert(lhs.size() == rhs.size());   // előfeltétel mindkét oldalra
    }

    std::size_t size() const noexcept {
        return lhs_.size();
    }

    double operator[](std::size_t i) const {
        return lhs_[i] + rhs_[i];
    }

private:
    typename Stored<L>::type lhs_;
    typename Stored<R>::type rhs_;
};

Itt az L és R lehet Vector<N> vagy maga is egy kifejezéstípus, például AddExpr<...>. A Vector levél referenciaként tárolódik, ezért a kifejezés létrehozása nem másol tömböt. Ha a leveleket is érték szerint tárolnánk, az a + b + c felépítése többszörösen lemásolná az a, b, c teljes tömbjét, vagyis épp azt a költséget hozná vissza, amelyet az expression template meg akar szüntetni. A referenciatárolás ára az élettartam: a kifejezésfa nem élheti túl a leveleket (lásd az auto csapdát).

A skalárral való szorzás hasonló:

template <typename E>
class ScalarMulExpr : public VectorExpr<ScalarMulExpr<E>> {
public:
    ScalarMulExpr(const E& expr, double scalar)
        : expr_(expr), scalar_(scalar) {}

    std::size_t size() const noexcept {
        return expr_.size();
    }

    double operator[](std::size_t i) const {
        return expr_[i] * scalar_;
    }

private:
    typename Stored<E>::type expr_;
    double scalar_;   // futásidejű adattag, nem része a típusnak
};

A tagadás, a kivonás, a skalárral való osztás és más műveletek is ugyanerre a mintára épülnek. A kivonás például:

template <typename L, typename R>
class SubExpr : public VectorExpr<SubExpr<L, R>> {
public:
    SubExpr(const L& lhs, const R& rhs)
        : lhs_(lhs), rhs_(rhs) {
        assert(lhs.size() == rhs.size());
    }

    std::size_t size() const noexcept {
        return lhs_.size();
    }

    double operator[](std::size_t i) const {
        return lhs_[i] - rhs_[i];
    }

private:
    typename Stored<L>::type lhs_;
    typename Stored<R>::type rhs_;
};

A kulcs: ezek a típusok nem tárolnak tömböt, csak leírást (a leveleknél referenciát); a tényleges számítás az operator[]-ben történik, amikor a hívó kéri.

10.1.4 Operátor-túlterhelések: kifejezésfák építése

Ahhoz, hogy a felhasználó a megszokott a + b szintaxist használhassa, túl kell terhelnünk az operátorokat. Az operátorok visszatérési értéke nem vektor, hanem a megfelelő kifejezéstípus. Mivel a Vector is VectorExpr-ből származik, írhatunk egy általános operátort, amely bármilyen kifejezést fogad.

template <typename L, typename R>
auto operator+(const VectorExpr<L>& lhs, const VectorExpr<R>& rhs) {
    return AddExpr<L, R>(lhs.self(), rhs.self());
}

template <typename L, typename R>
auto operator-(const VectorExpr<L>& lhs, const VectorExpr<R>& rhs) {
    return SubExpr<L, R>(lhs.self(), rhs.self());
}

template <typename E>
auto operator*(const VectorExpr<E>& expr, double scalar) {
    return ScalarMulExpr<E>(expr.self(), scalar);
}

template <typename E>
auto operator*(double scalar, const VectorExpr<E>& expr) {
    return ScalarMulExpr<E>(expr.self(), scalar);
}

Ezek a függvények nem végeznek számítást, csak összekötik az operandusokat egy új típusba. A lhs.self() hívás a VectorExpr CRTP-ből jön, és visszaadja a tényleges származtatott objektumot. Ezáltal a AddExpr<L, R> konstruktora a pontos típusú operandusokat kapja.

A fenti operátorok felhasználhatók összetett kifejezésekben:

Vector<4> a, b, c;
// ... inicializálás
auto expr = a + b + c; // típus: AddExpr<AddExpr<Vector<4>, Vector<4>>, Vector<4>>

Az expr nem vektor, hanem egy kifejezésfa, amely a + műveleteket írja le. A tényleges kiértékelés még nem történt meg. Ezt a típust akár ki is nyomtathatjuk typeid-dal, de általában nem szükséges: a felhasználó ritkán akarja explicit módon kezelni.

10.1.5 Lusta kiértékelés és a hozzárendelés

A kifejezésfa akkor válik hasznossá, amikor valamilyen tárolóba akarjuk írni az eredményt. A Vector osztályunknak szüksége van egy sablonos értékadó operátorra, amely elfogad bármilyen VectorExpr leszármazottat, és a size()-nek megfelelő módon kitölti a célobjektumot.

template <typename Expr>
Vector& operator=(const VectorExpr<Expr>& expr) {
    const Expr& e = expr.self();
    assert(e.size() == N);
    for (std::size_t i = 0; i < N; ++i) {
        data_[i] = e[i];
    }
    return *this;
}

Itt minden egyes e[i] hívás rekurzívan kiértékeli a kifejezést az adott indexre. Ez a lusta kiértékelés lényege: a számítás a hozzárendelés pillanatában, egyszerre, indexenként történik. A ciklus egyetlen bejárást végez a célvektoron, és minden elemhez a teljes kifejezésfa értékét számolja. Nincs köztes tömbtároló és nincs tömbmásolat (a levelek referenciaként szerepelnek a fában).

A Vector osztály konstruktorát is kiegészíthetjük hasonló módon, hogy kifejezésből lehessen vektort létrehozni:

template <typename Expr>
Vector(const VectorExpr<Expr>& expr) {
    const Expr& e = expr.self();
    assert(e.size() == N);
    for (std::size_t i = 0; i < N; ++i) {
        data_[i] = e[i];
    }
}

Ezáltal írhatunk:

Vector<4> d = a + b + c; // a konstruktor értékeli ki a kifejezést

Fontos megjegyezni, hogy ez a konstruktor nem explicit, így implicit konverzió történik. Ez általában kívánatos, mert a kifejezések használata így természetes, de ügyelni kell arra, hogy ne okozzon akaratlan konverziót más helyeken.

10.1.6 Optimalizáció: ideiglenesek elkerülése és loop fusion

Az expression template-ek egyik legfőbb előnye, hogy a fordító a teljes kifejezést egyetlen ciklusba tudja összevonni (loop fusion). A fenti hozzárendelési operátorban az e[i] rekurzív hívásláncot alakít ki, de mivel minden tagfüggvény konstans, inline lehet, és a fordító képes a ciklust kibontani és a rekurziót eltüntetni. A gyakorlatban a -O2 optimalizációs szinttel a generált kód közel azonos azzal, mintha kézzel írtunk volna egyetlen for ciklust, amely az összes műveletet egyesíti:

for (size_t i = 0; i < N; ++i) {
    d[i] = a[i] + b[i] + c[i];
}

Ezzel szemben a naiv operátor-túlterheléses változatban a kód három különálló ciklusra bomlik: az a+b kiértékelése, a (a+b)+c kiértékelése, majd a d-be másolás. Mindegyik ciklus memóriát ír és olvas, ami rontja a cache kihasználtságot, és nagy méreteknél akár többszörös lassulást is okozhat.

A kifejezéstípusban a műveletek szerkezete fordítási időben ismert, az együtthatók viszont nem: a ScalarMulExpr a skalárt futásidejű double tagként tárolja, ezért az nem része a típusnak. Ha az együtthatót is a típusba akarjuk vinni, nem típusú sablonparaméteres (NTTP) változat kell, például ConstMulExpr<E, 3> egész együtthatóval (lebegőpontos NTTP C++20-tól megengedett, de fordítónként ellenőrizendő); ekkor a konstans az utasításba kerülhet.

10.1.7 Tipikus hibák és csapdák

Az expression template-ek szépsége mellett számos buktatót rejtenek. Ezek közül a leggyakoribbakat érdemes alaposan megérteni, mert a hibakeresés ezekkel a típusokkal nem mindig intuitív.

10.1.8 auto és a kifejezés élettartama

A legveszélyesebb csapda az auto használata, amikor egy kifejezést akarunk tárolni. Tekintsük a következő kódot:

Vector<4> a{1, 2, 3, 4}, b{5, 6, 7, 8};
auto sum = a + b; // sum típusa: AddExpr<Vector<4>, Vector<4>>

Itt sum nem vektor, hanem egy AddExpr objektum, amely a-ra és b-re referenciát tárol (a levelek referenciaként tárolódnak). Ez addig működik, amíg a és b él. Ha a kifejezést ideiglenes vektorokból hozzuk létre:

auto bad = makeVector() + makeVector(); // a makeVector prvalue Vector<4>-et ad vissza
Vector<4> d = bad;                      // HIBA: UB, a levelek már megsemmisültek

A makeVector() által visszaadott ideiglenesek a teljes kifejezés végén megsemmisülnek, ezért a bad-ben tárolt referenciák lógó (dangling) referenciák, és d = bad kiértékelése nem definiált viselkedés. A hiba csak a kifejezés kiértékelése előtti megsemmisítéssel mutatkozik meg: az auto önmagában még nem hiba, a lógó referencián át történő olvasás az. Az std::move nem segít: nem hosszabbítja meg a már megsemmisült operandus élettartamát, és a kiértékelést sem kényszeríti ki.

A javaslat: ha az eredményt vektorként akarjuk tárolni, a célobjektum típusát adjuk meg explicit módon (Vector<4> result = a + b;), mert ez kiértékeli a fát, mielőtt az ideiglenesek megszűnnének. A valódi könyvtárak (például az Eigen) dokumentációja ugyanezt a szabályt mondja ki az auto-ra expression objektumoknál; ez nem általános tilalom, hanem a konkrét kifejezés élettartamának ismerete. Ha mégis kifejezést akarunk elmenteni, az operandusok élettartamának le kell fednie a kifejezését, vagy a könyvtár adjon explicit materializáló műveletet (például egy .eval()-szerű tagfüggvényt).

10.1.9 Többszörös kiértékelés mellékhatásos elemkifejezésekkel

A lusta kiértékelés miatt az operator[] minden hozzáféréskor újra kiszámolja az adott elemet. Ha a kifejezésben olyan tagfüggvény vagy függvény szerepel, amely mellékhatással bír, akkor az operator[] ismételt hívásai többször is lefuttathatják azt. Például:

struct WeirdVector : VectorExpr<WeirdVector> {
    double operator[](size_t i) const {
        std::cout << "index " << i << std::endl; // mellékhatás
        return i;
    }
    size_t size() const { return 4; }
};

Ha ezt beillesztjük egy kifejezésbe, majd a célvektorba másoljuk, az operator[] annyiszor hívódik meg, ahány elemet átmásolunk, és minden alkalommal lefuttatja a std::cout-ot. Ez általában nem kívánatos. A szabály: a kifejezésfákban csak tiszta, mellékhatásmentes műveleteket használjunk, és kerüljük a költséges elemszámítást.

A többszörös kiértékelés másik, gyakorlatban súlyosabb következménye a költség: ha egy részkifejezés elemei drágák (például egy mátrixszorzat egy eleme egy teljes skalárszorzat), és a fa többször olvassa ugyanazt az elemet, az elemenkénti újraszámolás nagyságrendi lassulást okozhat. Ezért az olyan könyvtárak, mint az Eigen, bizonyos műveleteknél a részeredményt előre kiértékelik (materializálják).

A klasszikus aliasing-probléma: ha a célvektor szerepel a jobb oldalon is, például v = f(v) jellegű kifejezésnél, ahol az f az elem i-edik értékét más elemektől is függővé teszi (például eltolás vagy mátrixszorzás), a ciklus már átírt elemeket olvashat vissza, és hibás eredményt kap. Elemenkénti műveleteknél (v = v + w) ez ártalmatlan, mert az i-edik elem csak az i-edik régi értéktől függ.

10.1.10 Kivételbiztonság és a célobjektum állapota

A sablonos értékadó operátorban a ciklus egyszerre ír minden elemet. Ha a kifejezés kiértékelése közben kivétel dobódik, a célvektor félkész állapotba kerülhet. A robusztus megoldás a copy-and-swap idióma: hozzunk létre egy ideiglenes vektort a kifejezésből, és ha az sikeres, cseréljük ki a cél adatait. A sablonos értékadás ebben a változatban csak basic garanciát ad: ha az e[i] valamelyik elemnél kivételt dob, a korábbi elemek már átíródtak (részleges írás) akkor is, ha az elemek double típusúak, mert a kivétel a kifejezés kiértékeléséből jön, nem az elemtípusból. Strong garanciához előbb egy ideiglenes Vector-ba kell kiértékelni, és csak sikeres kiértékelés után másolni (vagy cserélni) a célba. Dinamikus tárolásnál a kivételbiztonságot külön meg kell tervezni.

10.1.11 Sablonhiba-üzenetek és a concepts szerepe

Az expression template-ek mély, egymásba ágyazott típusokat hoznak létre. Ha a felhasználó rossz típusú kifejezést ad meg, a fordító hibaüzenetei hosszúak és nehezen olvashatók lehetnek. C++20-tól kezdve concepts-ekkel korlátozhatjuk az operátorok és a sablonos értékadó paramétereit, így a hiba korábban, érthetőbb formában jelenik meg. A laborban ezért egy VectorLike conceptet definiálhatunk, és az operátorokat erre hivatkozva írhatjuk. A concept szándékosan a VectorExpr-ből való származást vizsgálja, nem pusztán a size() és operator[] meglétét: egy, a megszorítás nélküli „van size() és operator[]” concept globális, mohó operátort adna, amely például két std::vector<double>-re is illeszkedne, és kifejezésfát építene, valamint ütközne a VectorExpr-es túlterhelésekkel.

#include <concepts>

template <typename T>
concept VectorLike = std::derived_from<T, VectorExpr<T>>;

template <VectorLike L, VectorLike R>
auto operator+(const L& lhs, const R& rhs) {
    return AddExpr<L, R>(lhs, rhs);
}

Az L és R a const L& paraméterből const nélkül kerül levezetésre, ezért a concept nem const T-t vizsgál; a kiértékelés const tagfüggvényeken át történik, ami viszont még nem jelent mellékhatásmentességet. Ha ezt a túlterhelést használjuk, a korábbi VectorExpr<L>-es operator+ helyett használjuk (a kettő együtt nem szerepelhet, mert kétértelmű lenne).

Ez a gyakorlatban javítja a diagnosztikát és megakadályozza, hogy nem megfelelő típusok kerüljenek a kifejezésfába. A koncepciók tárgyalása a 8.1–8.2 egységekben részletesen megtörténik; itt csak annyit használunk, amennyi a példa tisztaságához szükséges.

10.1.12 Labor: egyszerű expression template implementáció

A labor célja, hogy az olvasó saját kezűleg építsen egy működő, mérhető expression template-keretrendszert, és vezessen mérési naplót a teljesítményéről. A következő lépéseket javasoljuk.

10.1.12.1 1. lépés: Az alaposztály és a vektor

Kezdje a fenti VectorExpr és Vector osztályok lemásolásával. Ügyeljen arra, hogy a Vector mérete sablonparaméter, és az operator[] mindkét (konstans és nem-konstans) változata ellenőrizze az indexhatárt.

10.1.12.2 2. lépés: A kifejezéscsomópontok

Valósítsa meg az AddExpr, ScalarMulExpr és opcionálisan a SubExpr, DivExpr osztályokat. Mindegyik a VectorExpr-ből származik, és size() valamint operator[] metódusokat ad.

10.1.12.3 3. lépés: Operátorok és értékadó

Definiálja a +, -, * operátorokat, és a Vector sablonos értékadó operátorát. Próbálja ki a kifejezést (az elemlistás konstruktor a Vector-ban szerepel; enélkül Vector<4> a{std::array<double, 4>{1, 2, 3, 4}}; formát kell használni):

Vector<4> a{1, 2, 3, 4};
Vector<4> b{5, 6, 7, 8};
Vector<4> c{2, 2, 2, 2};

Vector<4> result = a + b * 3.0 - c;

Ellenőrizze az eredményt: result[0] = 1 + 53 - 2 = 14, result[1] = 2 + 63 - 2 = 18, stb. Írjon assert-ekkel működő tesztet.

10.1.12.4 4. lépés: Benchmark

Hasonlítsa össze három implementáció futásidejét: - a fenti expression template-es vektor, - egy naiv operátor-túlterheléses vektor, amely minden műveletet azonnal kiértékel, - egy kézzel írt, egyetlen ciklusos változat, amely közvetlenül számolja d[i] = a[i] + b[i]*s - c[i] stb.

Használjon rögzített méretű Vector<64>-et, és hajtson végre egymillió iterációt, minden iterációban újra kiértékelve ugyanazt a kifejezést más adatokkal. Mérje az időt std::chrono::steady_clock segítségével, és futtassa a mérést ötször, majd vegye az átlagot. A mérési naplóban rögzítse: - Fordító és verzió (például GCC 13.2.0) - Standardverzió (C++20) - Optimalizációs szint (-O2 -DNDEBUG) - Hardver (CPU, memória) - Az input mérete (N = 64) - A futtatások száma (1 000 000 iteráció, 5 mérés) - A mért átlagidők és a szórás

A várt eredmény hipotézis, nem előírt eredmény: az expression template-es változat várhatóan a kézzel írt ciklus közelébe kerül, a naiv változatnál pedig gyorsabb lehet, de ez fordítótól, optimalizációs szinttől és hardvertől függ, és a fordító a naiv ciklusokat is összevonhatja vagy kiértékelheti. Ezért a mért és a várt értéket külön kell feltüntetni; a mérési napló mért oszlopát az olvasó futtatás után tölti ki, ebben a kiadásban nincs mért adat. Csak az eredményt használó (például volatile kimenetbe író vagy összegző) mérés védett az elhagyás ellen.

Változat Várt (hipotézis) Mért (kitöltendő)
Naiv operátor-túlterhelés referencia <mért>
Expression template a kézi ciklus közelében <mért>
Kézzel írt ciklus a legjobb vagy hasonló <mért>

Az expression template célja, hogy az ideiglenes tömböket kiiktassa, és lehetővé tegye a ciklusok összevonását; ennek tényleges hatását a mérés dönti el.

10.1.12.5 5. lépés: Hiba forgatókönyv

Kísérletezzen az auto használatával:

auto sum = a + b; // típusa AddExpr...
// ...
Vector<4> d = sum; // működik, ha az operandusok még élnek

Magyarázza meg, miért veszélyes ez, ha a kifejezés referenciákat tárol, és mi a teendő ilyen esetben. Írjon egy példát, ahol az operandus vektorokat a kifejezés kiértékelése előtt megsemmisítjük (például egy blokk végén, vagy ideiglenesekből építve a kifejezést), és figyelje meg a viselkedést a jelenlegi, a leveleket referenciaként tároló változatnál. Ez nem definiált viselkedés; csak izolált környezetben, -fsanitize=address mellett próbálja ki, és ne tekintse „működő” eredménynek. Összehasonlításul tárolja a leveleket érték szerint is, és vesse össze a másolási költséggel.

10.1.13 Ellenőrző kérdések

  1. Mi a különbség a naiv operátor-túlterheléses vektor és az expression template-es vektor között a kiértékelés időzítésében?
  2. Miért nem ajánlott az auto használata expression template-ek eredményének tárolására, ha a könyvtár referenciákat tárol?
  3. Hogyan segít a CRTP az expression template-ekben?
  4. Milyen kivételbiztonsági megfontolásokat kell tenni dinamikus méretű tárolók esetén a sablonos értékadó operátorban?
  5. Mi a loop fusion, és miért előnyös a cache kihasználtság szempontjából?

Megoldásvázlat. (1) A naiv változat minden operátornál azonnal kiértékel és ideiglenest hoz létre; az expression template csak a hozzárendeléskor, egyetlen ciklusban értékel. (2) Mert a levelek referenciaként tárolódnak: a kifejezés túlélheti az operandusokat, és a kiértékelés lógó referenciát olvasna (UB). (3) A CRTP statikus polimorfizmust ad: a közös size()/operator[] interfész virtuális hívás nélkül, inline-olhatóan érhető el. (4) Az értékadás részleges írást hagyhat; strong garanciához ideiglenesbe értékelés és csere kell. (5) Az összevont ciklus egyszer járja be a memóriát, ideiglenes tömbök olvasása/írása nélkül, így kevesebb a memóriaforgalom.

10.1.14 Összefoglalás

Az expression template-ek a C++ sablonrendszerének egyik legerőteljesebb alkalmazásai. Lehetővé teszik, hogy a fordító a teljes kifejezést egyetlen kifejezésként, egyetlen ciklusként lássa, kiiktassa az ideiglenes tárolókat, és a műveleteket egyetlen optimalizált ciklusba fuzionálja. Az ár a megnövekedett típusbonyolultság, a nehezebben olvasható hibaüzenetek és az élettartam-kezelési csapdák. A fenti keretrendszer egyszerű, de jól szemlélteti az alapelveket; a valódi, termelésre kész könyvtárak (például az Eigen) ennél jóval kifinomultabb megoldásokat alkalmaznak, de a lényegi mechanizmus ugyanaz.

A következő alfejezet (10.2) a CRTP-t és a statikus polimorfizmust tárgyalja részletesebben, amely technikának itt is fontos szerepe volt. Az expression template-ekben használt VectorExpr alaposztály egy tipikus CRTP-alkalmazás, és a következő egységben megvizsgáljuk, hogyan lehet ezt a mintát általánosabban, mixinekkel és policy-based designnal kombinálni. Az itt megszerzett ismeretekre építve az olvasó képes lesz megérteni, hogyan lehet a statikus polimorfizmust teljesítmény és karbantarthatóság szempontjából hatékonyan kiaknázni.
